# How to Write a SKILL.md File

### A Senior Engineer's Guide for the New Intern

---

## First, Let's Talk About the Problem

Imagine you just hired five new interns on your team. You give them all the same task: "Go convert this uploaded file into a Word document." Each intern will do it differently. One will write a Python script using `python-docx`. Another will try to use Pandoc. A third will fumble for thirty minutes just figuring out which library to install. None of them know that your team has already figured out the best approach — that `docx` is preinstalled, that page size defaults to A4 unless you override it, and that using `\n` inside a paragraph will silently break everything.

Now replace "intern" with "Claude." Claude is a very smart assistant, but it does not have a memory of how your team works. It does not know your project's conventions, your preferred libraries, or the specific gotchas your senior engineers discovered through painful trial and error. Every single time you give Claude a task, it starts fresh.

A `SKILL.md` file is how you solve that problem. It is a plain text file that gives Claude a pre-loaded briefing before it starts working on a specific type of task. Think of it as the "onboarding document" you wish you had on your first day, but written for an AI instead of a human.

---

## How the Whole System Works

Before Claude responds to anything, it checks a list of available skills. This list lives in the system context and contains the **name** and a short **description** of every skill that has been installed. Claude reads all these descriptions and makes a decision: "Does this task match any of the skills I have available?"

Here is the important part — Claude reads only the name and description at this stage. The full content of the `SKILL.md` file is NOT loaded yet. This is intentional. Loading hundreds of skill files for every single conversation would be wasteful and slow. So the system uses a two-step approach:

```
Step 1: Claude sees only the skill description (always in context)
                          |
                          | Does the task match?
                          |
              +-----------+----------+
              |                      |
             YES                     NO
              |                      |
    Claude loads the full        Claude ignores
    SKILL.md into context        this skill entirely
              |
    Claude reads instructions,
    then does the work
```

This means the **description** field in your `SKILL.md` is the gatekeeper. If the description does not capture what the skill is for, Claude will walk right past it even if the rest of the file is perfectly written. This is the single most common mistake people make when writing skills — they write a great body but a weak description.

---

## The File Structure

A skill lives in a folder. At minimum, the folder contains one required file:

```
my-skill/
└── SKILL.md                  ← required, always

```

But as skills grow more complex, the folder can contain optional supporting files:

```
my-skill/
├── SKILL.md                  ← required
├── scripts/
│   └── create_report.py      ← reusable script Claude can run
├── references/
│   └── api-docs.md           ← supplementary docs Claude reads on demand
└── assets/
    └── template.xlsx         ← a file Claude uses as a starting point
```

You do not need all of these folders. Start with just `SKILL.md` and add the others only when you feel Claude is repeating work that could be automated or needs reference material that is too long to put inside `SKILL.md` directly.

---

## Anatomy of a SKILL.md File

Every `SKILL.md` file has two parts. The top section is called **frontmatter** and it is written in a format called YAML. The rest of the file is regular Markdown that contains the actual instructions for Claude.

Here is what a minimal file looks like:

```markdown
---
name: my-skill-name
description: "A clear explanation of WHEN to trigger this skill and WHAT it does."
---

# My Skill Title

The actual instructions for Claude go here in plain Markdown.
```

The three dashes `---` are the delimiters that tell the system where the YAML frontmatter starts and ends. Everything between the first `---` and the second `---` is metadata. Everything after the second `---` is the instruction body.

Let us go through each piece in detail.

---

## The `name` Field

This is just a short identifier for your skill. It should be lowercase, use hyphens instead of spaces, and be descriptive without being long. Think of it like a package name.

Good examples: `docx`, `pdf-report`, `kafka-consumer-gen`, `postgres-migration`

Bad examples: `My DOCX Skill`, `the-skill-that-helps-you-make-word-documents`

The name is used internally for organization and for the packaging system when you distribute a skill. Keep it clean.

---

## The `description` Field — The Most Important Part

Here is where most people go wrong. They write a description that explains what the skill does, but they forget to explain when Claude should use it. These are two different things, and both must be in the description.

The description is the only thing Claude reads before deciding whether to load your skill. So it must be a complete, slightly "pushy" advertisement for your skill. When in doubt, be more specific rather than less. If your skill handles `.docx` files, mention `.docx`. If it triggers on the word "Word document," mention that phrase explicitly.

Here is a bad description:

> "Helps with document creation."

That tells Claude almost nothing. What kind of document? When should it be used? What does it not cover?

Here is a good description:

> "Use this skill whenever the user wants to create, read, edit, or manipulate Word documents (.docx files). Triggers on any mention of 'Word doc', 'word document', '.docx', or requests to produce professional documents with formatting like tables of contents or page numbers. Do NOT use for PDFs, spreadsheets, or Google Docs."

Notice the structure: what triggers it (explicit phrases and file types), what it covers, and what it explicitly does NOT cover. The negative boundary is just as important as the positive one. Without it, Claude may apply your skill in situations where a different approach would be better.

One more thing: write the description in the imperative voice as if you are talking directly to Claude. "Use this skill when..." not "This skill is used when..."

---

## The Body — Writing Instructions That Actually Work

The body of your `SKILL.md` is where you write the instructions Claude will follow. This is standard Markdown, so you can use headings, code blocks, tables, and emphasis. Here are the principles that separate a skill that actually works from one that does not.

**Explain the "why," not just the "what."**

Claude is not a dumb rule-follower. It understands context and can reason. So instead of writing:

> "Never use `\n` in paragraphs."

Write:

> "Never use `\n` to create line breaks inside paragraphs — the docx library treats paragraphs as the atomic unit of text layout, and injecting newlines directly into a paragraph's text will silently break rendering. Use separate `Paragraph` elements instead."

When Claude understands why a rule exists, it can apply the spirit of the rule even in edge cases you did not think to write about. When it only knows the rule without the reason, it follows the letter of the rule and fails the moment something unexpected comes up.

**Put the most critical information early.**

Claude reads your skill from top to bottom. If there is a constraint that affects the entire task — like "this library is already installed, do not run npm install" — that should appear near the top, not buried at the bottom. Think of your skill like a briefing document: put the executive summary first, then the details.

**Use code blocks liberally.**

When you want Claude to run a specific command or follow a specific code pattern, put it in a fenced code block. This makes it unambiguous that this is executable code, not a prose description.

```bash
# This is the exact command to convert the document
python scripts/office/soffice.py --headless --convert-to pdf output.docx
```

**Tell Claude when to read supplementary files.**

If you have put reference material in a `references/` folder, you must tell Claude when to read it and why. Do not assume it will automatically look there. A good pattern is:

> "If the user's task involves a REST API integration, read `references/rest-api-patterns.md` before writing any code. It contains pre-approved request/response patterns your team uses."

**Keep the body under 500 lines ideally.**

If your skill is getting very long, that is a signal to move some content into reference files and point to them from the body. A skill that is too long becomes hard for Claude to process effectively. Think of it like a README — it should be comprehensive but not encyclopedic.

## A Three-Level Loading System

The system is designed with three levels of loading, and understanding this will help you decide where to put different pieces of information:

```
Level 1: name + description
         ┌──────────────────────────────────────────────┐
         │  Always in Claude's context, for every       │
         │  conversation. Extremely lightweight.        │
         │  ~100 words max.                             │
         └──────────────────────────────────────────────┘
                           │
                     Skill triggers
                           │
                           ▼
Level 2: SKILL.md body
         ┌──────────────────────────────────────────────┐
         │  Loaded when the skill is triggered. This     │
         │  is your main instruction set.                │
         │  Keep under 500 lines.                        │
         └──────────────────────────────────────────────┘
                           │
                  Claude decides it needs
                  supplementary material
                           │
                           ▼
Level 3: references/, scripts/, assets/
         ┌──────────────────────────────────────────────┐
         │  Loaded on demand, referenced from the body.  │
         │  No hard size limit. Scripts can be executed  │
         │  without even being read into context.         │
         └──────────────────────────────────────────────┘
```

Use Level 1 to answer: "When should this skill activate?" Use Level 2 to answer: "How should Claude approach this task?" Use Level 3 to answer: "What are the details and helper tools Claude may need?"

## A Complete Real-World Example

Let's say you are building a skill for your team so Claude always generates Kafka consumer boilerplate in Go using your team's preferred patterns. Here is what a well-written `SKILL.md` would look like:

```markdown
---
name: kafka-consumer-go
description: "Use this skill whenever the user asks to create, scaffold, or generate
a Kafka consumer in Go. Triggers on: 'new consumer', 'kafka consumer', 'scaffold consumer',
'handler for topic', or any request involving reading from a Kafka topic in a Go service.
Also use when the user asks to add a new topic handler to an existing consumer. Do NOT use
for Kafka producers, RabbitMQ consumers, or non-Go languages."
---

# Kafka Consumer Scaffolding — Go

This skill generates production-ready Kafka consumer boilerplate using the `kafka-go`
library with the Handler Registry pattern our team uses across all services in HR360.

## Why we use kafka-go and not confluent-kafka-go

Our team standardized on `segmentio/kafka-go` because it is a pure Go implementation
with no CGO dependency, which simplifies our Docker builds and CI pipelines. Do not
switch to `confluent-kafka-go` even if the user asks — file a discussion with the team
lead if there is a strong reason to reconsider.

## The Handler Registry Pattern

Every consumer in our system follows this pattern. The registry decouples the routing
logic from the business logic, which means adding a new topic handler never requires
touching the core consumer loop.

If the user is adding a new topic to an existing consumer, only generate the handler
function and the registry registration line — do not regenerate the entire consumer
boilerplate.

## Code structure to generate

See `references/handler-registry-template.md` for the full template with inline
comments explaining each section. Always use that file as the base rather than
writing from memory.

## Mandatory gotchas

Always check for context cancellation at the top of the consumer loop. Our Kubernetes
setup sends SIGTERM with a 30-second grace period, and consumers that ignore context
cancellation will be force-killed, potentially losing unacknowledged messages.

Never call `reader.CommitMessages()` inside a goroutine without proper synchronization —
this has caused offset corruption in production before.
```

Notice a few things about this example. The description tells Claude exactly which phrases should trigger it. The body explains the "why" behind the library choice, not just the rule. It tells Claude when to go read a supplementary file. And it surfaces the critical gotchas that come from real production experience — the kind of knowledge that takes a team months to accumulate.

---

## The Most Common Mistakes

The first mistake is a vague description. If your description could apply to five different scenarios, Claude will either not trigger on it at all or trigger when it should not. Be specific. Mention exact file extensions, exact phrases, exact library names.

The second mistake is putting all the content in one flat document without structure. Long walls of text are hard for Claude to use effectively. Use headings to create scannable sections, especially if some sections apply only in specific situations.

The third mistake is writing rules without reasons. "Never do X" is weak. "Never do X because it causes Y in production" is a rule Claude will actually understand and generalize from.

The fourth mistake is forgetting the negative boundary. Always include at least one "Do NOT use for..." clause in your description. This prevents the skill from being triggered in adjacent situations where it does not belong.

---

## Summary

A `SKILL.md` is a pre-written briefing document that Claude reads before starting a specific type of task. It lives in a folder alongside optional scripts and reference files. The file has two parts: a YAML frontmatter with a name and description, and a Markdown body with the actual instructions.

The description is the trigger mechanism — write it like a persuasive summary that tells Claude exactly when this skill should activate. The body is the instruction set — write it like you are briefing a very smart colleague who is new to your team's specific conventions. Explain the why behind every important rule. Keep the most critical information near the top. Point to supplementary files rather than embedding everything directly.

If you get the description right and the body explains the reasoning behind your team's conventions, Claude will behave like a senior engineer who has been on your team for months — not a smart-but-clueless outsider who has to rediscover every pitfall from scratch.
