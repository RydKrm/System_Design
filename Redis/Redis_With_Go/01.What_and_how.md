# Redis with Golang — A Production Guide
---
## What Even Is Redis, Really?

Before we touch a single line of Go code, I want you to understand what Redis actually is at its core, because a lot of engineers cargo-cult the setup without knowing why they're doing what they're doing.

Redis stands for **Remote Dictionary Server**. At heart, it is a single-threaded, in-memory data store that keeps everything in RAM. That's why it's blindingly fast. A typical PostgreSQL query on a well-indexed row might take 1–5 milliseconds. A Redis `GET` takes somewhere around 0.1–0.5 milliseconds. That's an order of magnitude faster.

But here's the thing you need to internalize early: **Redis is not a replacement for your database.** It is a complement. You still keep your source of truth in PostgreSQL. Redis is where you keep things that need to be accessed a hundred times per second, things like session tokens, rate-limit counters, leaderboard scores, and cached query results.

```
  Client Request
       │
       ▼
  ┌─────────────┐
  │  API Gateway│
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐     Cache HIT     ┌────────────────┐
  │  Go Service │──────────────────▶│  Redis (RAM)   │
  └──────┬──────┘                   └────────────────┘
         │                                  ▲
         │  Cache MISS                      │ SET result
         ▼                                  │
  ┌─────────────┐                           │
  │ PostgreSQL  │───── query result ────────┘
  └─────────────┘
```

When a request comes in, your Go service first checks Redis. If the answer is there (a cache hit), it returns immediately. If not (a cache miss), it goes to PostgreSQL, fetches the data, writes it into Redis for next time, and then returns the result. This pattern alone can cut your database load by 80–90% for read-heavy workloads.

## The Go Redis Client Landscape

There are two main libraries in the Go ecosystem for talking to Redis. You need to know both exist, but on this team, we pick one and stick with it.

**`go-redis/redis`** — This is the one we use. It is the community standard, actively maintained, supports Redis Cluster, Sentinel, and pipelines out of the box. It handles context propagation properly, which matters a lot when you're doing distributed tracing with OpenTelemetry (and we do).

**`redigo`** — An older library. You'll see it in older codebases. It works, but it's more low-level and you end up writing more boilerplate. We don't use it for new services.

```
  ┌─────────────────────────────────────┐
  │          Go Application             │
  │                                     │
  │   ┌────────────────────────────┐    │
  │   │     go-redis/redis/v9      │    │
  │   │  (our chosen client)       │    │
  │   └────────────┬───────────────┘    │
  └────────────────┼────────────────────┘
                   │  TCP connection (port 6379)
                   ▼
  ┌────────────────────────────────────┐
  │         Redis Server               │
  │  (standalone / sentinel / cluster) │
  └────────────────────────────────────┘
```

## Setting Up the Module

First things first, in your service directory, you pull in the library:

```bash
go get github.com/redis/go-redis/v9
```

Notice the `v9` at the end. This is important. Version 9 is the current major version and it introduced proper `context.Context` support throughout the entire API. Every Redis operation now takes a context as its first argument. This is not optional — it is how we do timeouts and cancellation correctly in production.

## Connecting to Redis the Right Way

Here is something I see interns and even mid-level engineers get wrong all the time. They create a new Redis client inside a function, use it, and the connection just sits there. Or they create one per request, which opens thousands of TCP connections and kills both the application and Redis.

The correct pattern is: **create one client, once, at application startup, and share it everywhere.**

```
  Application Startup
         │
         ▼
  ┌──────────────────┐
  │  NewRedisClient()│  ← called ONCE
  └────────┬─────────┘
           │ creates a connection pool
           ▼
  ┌──────────────────────────────────────┐
  │         Connection Pool              │
  │  ┌──────┐ ┌──────┐ ┌──────┐          │
  │  │conn 1│ │conn 2│ │conn 3│  ...     │
  │  └──────┘ └──────┘ └──────┘          │
  └──────────────────────────────────────┘
           │
           │ goroutines borrow connections from pool
           ▼
  ┌──────┐ ┌──────┐ ┌──────┐
  │ req A│ │ req B│ │ req C│  ...concurrent requests
  └──────┘ └──────┘ └──────┘
```

go-redis manages a connection pool internally. You don't see individual connections — you just call `.Get()` or `.Set()` and the library borrows a connection from the pool, uses it, and returns it. This is exactly what we want.

Here is how a production-grade Redis client setup looks in Go:

```go
package redisclient

import (
    "context"
    "fmt"
    "time"

    "github.com/redis/go-redis/v9"
)

// Config holds all the settings we need to connect to Redis.
// We read these from environment variables at startup — never hardcode them.
type Config struct {
    Host         string
    Port         int
    Password     string
    DB           int  // Redis supports 16 logical databases (0–15). We use 0 by default.
    PoolSize     int  // How many connections to keep open simultaneously.
    MinIdleConns int  // Keep at least this many connections alive even when idle.
    DialTimeout  time.Duration
    ReadTimeout  time.Duration
    WriteTimeout time.Duration
}

// NewClient creates and validates a Redis client.
// This should be called once during application initialization and the
// returned *redis.Client should be passed around via dependency injection.
func NewClient(cfg Config) (*redis.Client, error) {
    rdb := redis.NewClient(&redis.Options{
        Addr:     fmt.Sprintf("%s:%d", cfg.Host, cfg.Port),
        Password: cfg.Password,
        DB:       cfg.DB,

        // Pool settings — these matter enormously under load.
        PoolSize:     cfg.PoolSize,     // max connections in pool
        MinIdleConns: cfg.MinIdleConns, // keep N connections warm always

        // Timeout settings.
        // DialTimeout: how long to wait when establishing a new TCP connection.
        // ReadTimeout: how long to wait for a reply from Redis after sending a command.
        // WriteTimeout: how long to wait to send a command to Redis.
        DialTimeout:  cfg.DialTimeout,
        ReadTimeout:  cfg.ReadTimeout,
        WriteTimeout: cfg.WriteTimeout,
    })

    // Always ping on startup. If Redis is unreachable, fail fast and loud
    // rather than discovering it silently during the first real request.
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    if err := rdb.Ping(ctx).Err(); err != nil {
        return nil, fmt.Errorf("redis: failed to connect to %s:%d — %w", cfg.Host, cfg.Port, err)
    }

    return rdb, nil
}
```

And the default production values you'd plug into that config:

```go
cfg := redisclient.Config{
    Host:         os.Getenv("REDIS_HOST"),     // e.g. "redis" in Docker Compose
    Port:         6379,
    Password:     os.Getenv("REDIS_PASSWORD"),
    DB:           0,
    PoolSize:     10,             // a safe starting point for most services
    MinIdleConns: 3,              // 3 connections always warm and ready
    DialTimeout:  5 * time.Second,
    ReadTimeout:  3 * time.Second,
    WriteTimeout: 3 * time.Second,
}
```

The `PoolSize` of 10 is not a magic number — it is a starting point. For HR360, where multiple goroutines process Kafka messages concurrently, you might bump this to 20–30. You tune it by watching the `pool_stats` metrics in Grafana and seeing whether connections are being waited on.

## The Context is Not Optional

Every single Redis call in production code must use a context with a deadline or timeout. No exceptions. Here is why.

Imagine Redis is under heavy load and takes 30 seconds to respond to a query. Without a timeout, your goroutine sits there waiting. If you have 1000 concurrent requests, you now have 1000 goroutines all stuck, your connection pool is exhausted, and your whole service grinds to a halt. This is called a cascading failure, and it is one of the most common causes of total outages in microservices systems.

```
  WITHOUT context timeout:
  ┌─────────────┐
  │  goroutine  │──── waits 30s ────▶ Redis (slow)
  └─────────────┘
       ...x1000 goroutines
  Result: service is completely frozen

  WITH context timeout:
  ┌─────────────┐     timeout after 3s
  │  goroutine  │──────────────────▶ error returned
  └─────────────┘   Redis (slow)    goroutine is free
       ...x1000 goroutines
  Result: 1000 errors, but service stays alive
```

In code, it looks like this:

```go
func (s *CacheService) GetUserSession(userID string) (*Session, error) {
    // Always derive a context with a deadline from the incoming request context.
    // If there is no incoming context, use context.Background() with a manual timeout.
    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel() // always defer cancel to free resources

    key := fmt.Sprintf("session:%s", userID)

    val, err := s.rdb.Get(ctx, key).Result()
    if err == redis.Nil {
        // redis.Nil is NOT an error — it just means the key doesn't exist.
        // This is a cache miss. Go fetch from the database.
        return nil, nil
    }
    if err != nil {
        // A real error: timeout, network failure, etc.
        return nil, fmt.Errorf("cache: failed to get session for user %s — %w", userID, err)
    }

    var session Session
    if err := json.Unmarshal([]byte(val), &session); err != nil {
        return nil, fmt.Errorf("cache: failed to decode session — %w", err)
    }

    return &session, nil
}
```

That `redis.Nil` check is critically important. New engineers treat it as an error, which breaks the cache-miss logic entirely. When a key does not exist in Redis, `Get` returns `redis.Nil`. This is expected and normal — it just means "not in cache." Any other error means something genuinely went wrong.

## Setting Values with TTL (Time-to-Live)

In production, **every key you write to Redis must have an expiry time set.** This is non-negotiable.

Here is the problem: if you never set an expiry, keys accumulate forever. Redis lives in RAM. RAM is finite. If you fill it up, Redis either starts evicting keys randomly (depending on your eviction policy) or it crashes. Neither is what you want during a surge in traffic.

```
  Key WITHOUT TTL:
  ┌──────────────────────────────────────────┐
  │  Redis Memory                            │
  │                                          │
  │  session:user_001  → {...}  (forever)    │
  │  session:user_002  → {...}  (forever)    │
  │  session:user_003  → {...}  (forever)    │
  │  ...100k users later...                  │
  │  ██████████████████████ MEMORY FULL ██   │
  └──────────────────────────────────────────┘

  Key WITH TTL of 24h:
  ┌──────────────────────────────────────────┐
  │  Redis Memory                            │
  │                                          │
  │  session:user_001  → {...}  TTL: 23:59   │
  │  session:user_002  → {...}  TTL: 12:30   │
  │  session:user_003  → {...}  TTL: 01:15   │  ← expires, gone
  │  Memory stays healthy and bounded        │
  └──────────────────────────────────────────┘
```

```go
func (s *CacheService) SetUserSession(session *Session, ttl time.Duration) error {
    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()

    data, err := json.Marshal(session)
    if err != nil {
        return fmt.Errorf("cache: failed to encode session — %w", err)
    }

    key := fmt.Sprintf("session:%s", session.UserID)

    // The third argument to Set is the TTL. Setting it to 0 means no expiry.
    // In production code, 0 should almost never be used.
    if err := s.rdb.Set(ctx, key, data, ttl).Err(); err != nil {
        return fmt.Errorf("cache: failed to set session for user %s — %w", session.UserID, err)
    }

    return nil
}
```

For HR360 specifically, we use different TTLs for different data types:

- Session tokens: 24 hours (the user's working day)
- OTP codes: 5 minutes (they should expire fast for security)
- Rate-limit counters: matches the window — e.g., 1 minute
- Cached query results: 5–15 minutes, depending on how stale the data can be

## Key Naming Conventions

This is something that nobody teaches you in tutorials but matters enormously when your Redis database has 50 different services writing to it. Without a naming convention, you end up with keys like `user1`, `session`, `data`, and nobody knows what owns what or what format the value is in.

The convention we follow is:

```
  {service}:{entity}:{identifier}
```

```
  ┌────────────────────────────────────────────────────┐
  │  Key Naming Convention Examples for HR360          │
  │                                                    │
  │  auth:session:{user_id}                            │
  │  auth:otp:{user_id}                                │
  │  employee:profile:{employee_id}                    │
  │  leave:balance:{employee_id}:{year}                │
  │  payroll:slip:{employee_id}:{month}                │
  │  ratelimit:login:{ip_address}                      │
  │  notification:unread_count:{user_id}               │
  └────────────────────────────────────────────────────┘
```

The colon (`:`) is the conventional separator in Redis. Redis won't enforce this, but the redis-cli and monitoring tools like RedisInsight use it to group keys into a tree-like view, which makes debugging infinitely easier.

## Pipelines — Batch Your Commands

Every time your Go code calls `rdb.Get(ctx, key)`, it sends a network round-trip to Redis and waits for the reply. If you are calling 10 Redis commands in a loop, that is 10 round-trips, each adding maybe 0.3ms. That is 3ms of pure network overhead.

A pipeline lets you send all 10 commands in a single network trip and receive all 10 responses at once.

```
  Without pipeline (10 round trips):
  Go ──GET──▶ Redis
  Go ◀──val── Redis        round trip 1 (0.3ms)
  Go ──GET──▶ Redis
  Go ◀──val── Redis        round trip 2 (0.3ms)
  ...
  Total: 3ms of overhead

  With pipeline (1 round trip):
  Go ──GET,GET,GET,...──▶ Redis
  Go ◀──val,val,val,...── Redis   1 round trip (0.3ms)
  Total: 0.3ms of overhead
```

```go
func (s *CacheService) GetMultipleEmployeeProfiles(ids []string) (map[string]*EmployeeProfile, error) {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    // Start a pipeline. Commands queued inside are NOT sent until Exec() is called.
    pipe := s.rdb.Pipeline()

    // Queue all the GET commands. None of them hit the network yet.
    cmds := make([]*redis.StringCmd, len(ids))
    for i, id := range ids {
        key := fmt.Sprintf("employee:profile:%s", id)
        cmds[i] = pipe.Get(ctx, key)
    }

    // Execute sends all queued commands in a single network trip.
    _, err := pipe.Exec(ctx)
    // Note: pipe.Exec returns an error if ANY command failed.
    // But individual commands may also have errors (like redis.Nil for missing keys).
    // We handle both.
    if err != nil && err != redis.Nil {
        return nil, fmt.Errorf("cache: pipeline execution failed — %w", err)
    }

    profiles := make(map[string]*EmployeeProfile, len(ids))
    for i, cmd := range cmds {
        val, err := cmd.Result()
        if err == redis.Nil {
            continue // not in cache, skip
        }
        if err != nil {
            continue // log this, but don't fail the whole operation
        }

        var profile EmployeeProfile
        if err := json.Unmarshal([]byte(val), &profile); err != nil {
            continue // malformed data, skip
        }
        profiles[ids[i]] = &profile
    }

    return profiles, nil
}
```

Use pipelines whenever you are doing more than 3 Redis operations in the same logical unit of work.

## The Cache-Aside Pattern in Full

This is the pattern you will use 90% of the time. It is also called "lazy loading" because you only populate the cache when someone actually asks for the data.

```
  ┌───────────────────────────────────────────────────────┐
  │                Cache-Aside Flow                       │
  │                                                       │
  │  Incoming request for employee profile #42            │
  │             │                                         │
  │             ▼                                         │
  │      Check Redis cache                                │
  │        key: employee:profile:42                       │
  │             │                                         │
  │     ┌───────┴────────┐                                │
  │  HIT│                │MISS                            │
  │     ▼                ▼                                │
  │  Return data    Query PostgreSQL                      │
  │  immediately    SELECT * FROM employees WHERE id=42   │
  │                      │                                │
  │                      ▼                                │
  │                 Store in Redis                        │
  │                 SET employee:profile:42 {...} EX 300  │
  │                      │                                │
  │                      ▼                                │
  │                 Return data to caller                 │
  └───────────────────────────────────────────────────────┘
```

```go
func (s *EmployeeService) GetEmployeeProfile(ctx context.Context, id string) (*EmployeeProfile, error) {
    cacheKey := fmt.Sprintf("employee:profile:%s", id)

    // Step 1: Try the cache.
    val, err := s.cache.Get(ctx, cacheKey).Result()
    if err == nil {
        // Cache hit. Decode and return immediately.
        var profile EmployeeProfile
        if err := json.Unmarshal([]byte(val), &profile); err != nil {
            // The cached data is corrupted. Fall through to the database.
            // This is rare but you must handle it.
            s.logger.Warn("cache: corrupted data for key", "key", cacheKey)
        } else {
            return &profile, nil
        }
    } else if err != redis.Nil {
        // Redis returned a real error (network, timeout, etc.)
        // We log it but do NOT fail the request — we fall through to the database.
        // This is called "cache stampede protection" philosophy:
        // your cache failing should degrade performance, not break functionality.
        s.logger.Error("cache: get failed, falling through to db", "error", err)
    }

    // Step 2: Cache miss or error. Go to PostgreSQL.
    profile, err := s.repo.FindEmployeeByID(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("service: failed to get employee %s — %w", id, err)
    }

    // Step 3: Write to cache for next time.
    // We do this asynchronously so we don't make the caller wait for the cache write.
    go func() {
        data, err := json.Marshal(profile)
        if err != nil {
            s.logger.Error("cache: failed to marshal profile", "error", err)
            return
        }
        writeCtx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
        defer cancel()
        if err := s.cache.Set(writeCtx, cacheKey, data, 5*time.Minute).Err(); err != nil {
            s.logger.Error("cache: failed to set profile", "error", err)
        }
    }()

    return profile, nil
}
```

There is an important nuance here. Notice that when Redis itself fails (not a cache miss, but a real error), we log it and continue to the database. This is intentional. Redis going down should not take your entire service with it. The degraded experience is "slower responses" not "complete outage." This is a design principle called **graceful degradation**, and it is the difference between a 3 AM incident and a 3 AM non-event.

## Cache Invalidation — The Hard Part

Cache invalidation is famously one of the two hard problems in computer science ("naming things" being the other). But the principle is actually straightforward: **when you write to the database, you must delete or update the corresponding cache entry.**

```
  Update Employee Salary:
  ┌────────────────────────────────────────────────────────┐
  │                                                        │
  │  Step 1: Write to PostgreSQL                           │
  │  UPDATE employees SET salary = 95000 WHERE id = '42'  │
  │                 │                                      │
  │                 ▼                                      │
  │  Step 2: Invalidate Redis cache                        │
  │  DEL employee:profile:42                               │
  │                 │                                      │
  │                 ▼                                      │
  │  Next GET for employee:42 → cache miss → fresh DB read │
  │                                                        │
  └────────────────────────────────────────────────────────┘
```

```go
func (s *EmployeeService) UpdateEmployeeSalary(ctx context.Context, id string, newSalary float64) error {
    // Step 1: Update the source of truth.
    if err := s.repo.UpdateSalary(ctx, id, newSalary); err != nil {
        return fmt.Errorf("service: failed to update salary — %w", err)
    }

    // Step 2: Invalidate the cache.
    // We delete rather than update because it's simpler and avoids subtle race conditions
    // between the DB write and the cache write.
    cacheCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    cacheKey := fmt.Sprintf("employee:profile:%s", id)
    if err := s.cache.Del(cacheCtx, cacheKey).Err(); err != nil {
        // This is a soft failure — log it, but don't return an error.
        // The cache entry will expire on its own via TTL.
        // The window of stale data is bounded by the TTL we set (5 minutes).
        s.logger.Error("cache: failed to invalidate employee profile", "key", cacheKey, "error", err)
    }

    return nil
}
```

The reason we delete rather than update the cache is subtle but important. After a database write, there is a tiny window where the database has the new data but the cache write hasn't happened yet. Another goroutine could read the stale cache value in that window. By deleting, we guarantee the next read will go to the database and get fresh data. This is the safer strategy.

## Rate Limiting with Redis INCR

One of the most elegant use cases for Redis is rate limiting. The idea is: for every incoming request, increment a counter in Redis. If the counter exceeds a threshold, reject the request. The counter expires automatically after the time window.

```
  Rate Limiting Flow (10 requests per minute per IP):
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Request from IP 192.168.1.5                             │
  │        │                                                 │
  │        ▼                                                 │
  │  INCR ratelimit:login:192.168.1.5                        │
  │  (if key doesn't exist, Redis creates it at 0 first)     │
  │        │                                                 │
  │   ┌────┴────────┐                                        │
  │   │ count ≤ 10? │                                        │
  │   └────┬────────┘                                        │
  │      YES│           NO                                   │
  │        ▼             ▼                                   │
  │  Allow request   Return 429 Too Many Requests            │
  │  EXPIRE key 60s  (if count was just 1, set EXPIRE too)   │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

```go
func (s *RateLimiter) Allow(ctx context.Context, key string, limit int64, window time.Duration) (bool, error) {
    rateCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    // INCR atomically increments the counter and returns the new value.
    // If the key doesn't exist, Redis creates it with a value of 0, then increments to 1.
    count, err := s.rdb.Incr(rateCtx, key).Result()
    if err != nil {
        // If Redis is down, fail open (allow the request) rather than blocking everyone.
        // This is a business decision — for some endpoints you might want to fail closed.
        s.logger.Error("ratelimit: redis error, allowing request", "error", err)
        return true, nil
    }

    // Only set the expiry on the very first request in this window.
    // If we set it every time, we'd reset the window on every request, which defeats the purpose.
    if count == 1 {
        if err := s.rdb.Expire(rateCtx, key, window).Err(); err != nil {
            s.logger.Error("ratelimit: failed to set expiry", "key", key, "error", err)
        }
    }

    return count <= limit, nil
}
```

Usage in a Gin middleware:

```go
func RateLimitMiddleware(limiter *RateLimiter) gin.HandlerFunc {
    return func(c *gin.Context) {
        ip := c.ClientIP()
        key := fmt.Sprintf("ratelimit:api:%s", ip)

        allowed, err := limiter.Allow(c.Request.Context(), key, 100, time.Minute)
        if err != nil {
            c.Next() // fail open on error
            return
        }

        if !allowed {
            c.JSON(http.StatusTooManyRequests, gin.H{
                "error": "rate limit exceeded, please slow down",
            })
            c.Abort()
            return
        }

        c.Next()
    }
}
```

## Distributed Locking with SETNX

When multiple instances of your service are running (which they always are in production), sometimes you need to make sure only one of them does a particular thing at a time. The classic example is sending a welcome email: if a user registers and two service instances pick up the same event, you don't want to send two emails.

Redis solves this with a distributed lock. The idea is: whoever sets the lock key first gets the right to proceed. Everyone else sees the key already exists and backs off.

```
  2 instances of employee-service both receive "user_42_registered" event:

  Instance A:          Redis:               Instance B:
       │                  │                      │
       ├─ SETNX lock ────▶│                      │
       │                  │◀─ SETNX lock ────────┤
       │◀─ 1 (got it!) ───┤                      │
       │                  ├─ 0 (already set) ───▶│
  [A does the work]       │               [B skips — someone else has it]
       │                  │                      │
       ├─ DEL lock ──────▶│                      │
       │                  │                      │
```

```go
func (s *EmployeeService) ProcessRegistrationEvent(ctx context.Context, userID string) error {
    lockKey := fmt.Sprintf("lock:registration:%s", userID)

    // SET key value NX EX seconds
    // NX = only set if Not eXists (atomic check-and-set)
    // 30s = the lock auto-expires in 30 seconds, so we can't deadlock forever
    acquired, err := s.rdb.SetNX(ctx, lockKey, "locked", 30*time.Second).Result()
    if err != nil {
        return fmt.Errorf("lock: redis error — %w", err)
    }

    if !acquired {
        // Another instance has this lock. This is not an error — it's expected.
        return nil
    }

    // We have the lock. Always release it when done.
    defer s.rdb.Del(context.Background(), lockKey)

    // Do the work that should only happen once.
    return s.sendWelcomeEmail(ctx, userID)
}
```

This is a simplified version. For production-grade distributed locking, look into the **Redlock** algorithm (implemented in go-redis as `rueidis` lock extension or available via separate libraries). The simple `SETNX` approach works for most cases but has edge cases in network partition scenarios.

## Pub/Sub for Real-Time Events

Redis has a publish/subscribe messaging system built in. For HR360, we use this to broadcast real-time notifications — for example, when a leave request is approved, the notification service publishes to a Redis channel and the WebSocket service picks it up and pushes to the browser.

```
  ┌───────────────────────────────────────────────────────────────┐
  │  Leave Service   Redis Pub/Sub    WebSocket Service           │
  │                                                               │
  │  Leave approved      │                  │                     │
  │       │              │                  │                     │
  │       ├─ PUBLISH ───▶│                  │                     │
  │       │  channel:    │                  │                     │
  │       │ leave_updates|                  │                     │
  │       │              │── broadcast ────▶│                     │
  │       │              │                  ├─ push to browser    │
  │       │              │                  │                     │
  └───────────────────────────────────────────────────────────────┘
```

```go
// Publisher side (in leave-service):
func (s *LeaveService) ApproveLeaveRequest(ctx context.Context, requestID string) error {
    // ... update database ...

    event := LeaveApprovedEvent{
        RequestID:  requestID,
        EmployeeID: "emp_42",
        ApprovedAt: time.Now(),
    }
    data, _ := json.Marshal(event)

    channel := "channel:leave_updates"
    if err := s.rdb.Publish(ctx, channel, data).Err(); err != nil {
        // Pub/Sub failure is non-fatal — the database write already happened.
        s.logger.Error("pubsub: failed to publish leave event", "error", err)
    }

    return nil
}

// Subscriber side (in notification-service):
func (s *NotificationService) SubscribeToLeaveUpdates(ctx context.Context) {
    sub := s.rdb.Subscribe(ctx, "channel:leave_updates")
    defer sub.Close()

    ch := sub.Channel() // returns a Go channel that delivers incoming messages

    for {
        select {
        case msg, ok := <-ch:
            if !ok {
                s.logger.Info("pubsub: channel closed")
                return
            }
            var event LeaveApprovedEvent
            if err := json.Unmarshal([]byte(msg.Payload), &event); err != nil {
                s.logger.Error("pubsub: failed to decode event", "error", err)
                continue
            }
            s.handleLeaveApproved(ctx, event)

        case <-ctx.Done():
            return
        }
    }
}
```

One important note: Redis Pub/Sub is fire-and-forget. If the subscriber is offline when the message is published, the message is lost. For guaranteed delivery, use Kafka (which we already have in HR360) rather than Redis Pub/Sub. Redis Pub/Sub is for low-stakes, real-time broadcast where occasional loss is acceptable, like "refresh your dashboard" notifications.

## Structured Logging and Observability

In production, you need to know when your Redis operations are slow or failing. The cleanest way to add observability is through the hook system that go-redis provides.

```go
// RedisLogger is a custom hook that logs slow Redis commands.
type RedisLogger struct {
    logger    *slog.Logger
    slowThreshold time.Duration
}

func (l *RedisLogger) BeforeProcess(ctx context.Context, cmd redis.Cmder) (context.Context, error) {
    return context.WithValue(ctx, "cmd_start_time", time.Now()), nil
}

func (l *RedisLogger) AfterProcess(ctx context.Context, cmd redis.Cmder) error {
    startTime, ok := ctx.Value("cmd_start_time").(time.Time)
    if !ok {
        return nil
    }

    duration := time.Since(startTime)

    if cmd.Err() != nil && cmd.Err() != redis.Nil {
        l.logger.Error("redis: command failed",
            "cmd", cmd.Name(),
            "duration_ms", duration.Milliseconds(),
            "error", cmd.Err(),
        )
    } else if duration > l.slowThreshold {
        l.logger.Warn("redis: slow command",
            "cmd", cmd.Name(),
            "duration_ms", duration.Milliseconds(),
        )
    }

    return nil
}

// Attach it when creating the client:
rdb.AddHook(&RedisLogger{
    logger:        logger,
    slowThreshold: 100 * time.Millisecond, // anything over 100ms is worth knowing about
})
```

For full OpenTelemetry integration (traces and metrics), go-redis has a first-party instrumentation package:

```bash
go get github.com/redis/go-redis/extra/redisotel/v9
```

```go
import "github.com/redis/go-redis/extra/redisotel/v9"

// After creating the client:
if err := redisotel.InstrumentTracing(rdb); err != nil {
    log.Fatal("failed to instrument redis tracing", err)
}
if err := redisotel.InstrumentMetrics(rdb); err != nil {
    log.Fatal("failed to instrument redis metrics", err)
}
```

This automatically creates spans for every Redis call in your OpenTelemetry traces, so in Grafana you can see exactly which Redis operations are being called, how long they take, and which ones are failing — all correlated with the full distributed trace across your 12 services.

## Docker Compose Setup for Local Development

For local development, we run Redis in Docker alongside your Go service. Here is a production-imitating setup:

```yaml
# docker-compose.yml
services:
  redis:
    image: redis:7-alpine      # always pin the major version
    container_name: hr360-redis
    restart: unless-stopped
    ports:
      - "6379:6379"            # expose to host for redis-cli debugging
    command: >
      redis-server
      --requirepass ${REDIS_PASSWORD}
      --maxmemory 256mb
      --maxmemory-policy allkeys-lru
      --save 60 1              # persist to disk every 60s if at least 1 key changed
      --loglevel notice
    volumes:
      - redis_data:/data       # persist data across container restarts
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  redis_data:
```

The `--maxmemory 256mb` and `--maxmemory-policy allkeys-lru` settings are important even for local dev because they teach you how Redis behaves in production. When Redis is full, `allkeys-lru` evicts the least recently used keys — which is the correct behavior for a cache. The alternative `noeviction` policy causes Redis to start returning errors when full, which is almost never what you want for a cache workload.

## The Full Production Wiring

Putting it all together, here is how the dependency flows in a real service:

```
  main.go
    │
    ├── Load config from env variables
    │
    ├── NewRedisClient(cfg)   ← connection pool, ping check
    │        │
    │        └── Add OpenTelemetry hooks
    │
    ├── NewCacheService(redisClient)
    │
    ├── NewEmployeeRepository(db)
    │
    ├── NewEmployeeService(repo, cacheService, logger)
    │
    ├── NewRateLimiter(redisClient)
    │
    └── NewHTTPServer(employeeService, rateLimiter)
            │
            └── Register routes, start server
```

The Redis client flows down through constructor injection. You never use a global variable for it. This makes the code testable — in tests, you can swap in a real Redis instance (using `miniredis` for unit tests or a real Redis for integration tests) without changing any business logic.

## A Quick Word on Testing

For unit tests, use `miniredis` — it's an in-memory Redis implementation that runs inside your test process:

```bash
go get github.com/alicebob/miniredis/v2
```

```go
func TestGetUserSession_CacheMiss(t *testing.T) {
    // Start a fake Redis server inside the test
    mr, err := miniredis.Run()
    require.NoError(t, err)
    defer mr.Close()

    rdb := redis.NewClient(&redis.Options{Addr: mr.Addr()})
    svc := NewCacheService(rdb)

    // Cache is empty, so GetUserSession should return nil, nil
    result, err := svc.GetUserSession("user_42")
    require.NoError(t, err)
    require.Nil(t, result)
}
```

No Docker required, tests run in milliseconds, and you can simulate Redis failures by calling `mr.SetError("LOADING")` — exactly what you need to test your graceful degradation logic.

## Summary: The Mental Model

The whole thing boils down to this picture:

```
  ┌─────────────────────────────────────────────────────────────────┐
  │                    HR360 Caching Architecture                   │
  │                                                                 │
  │  Go Service Instance 1        Go Service Instance 2             │
  │  ┌────────────────────┐       ┌────────────────────┐            │
  │  │ CacheService       │       │ CacheService       │            │
  │  │ - Get(ctx, key)    │       │ - Get(ctx, key)    │            │
  │  │ - Set(ctx, k, v)   │       │ - Set(ctx, k, v)   │            │
  │  │ - Del(ctx, key)    │       │ - Del(ctx, key)    │            │
  │  └────────┬───────────┘       └───────────┬────────┘            │
  │           │  connection pool              │  connection pool    │
  │           └──────────────┬───────────────┘                      │
  │                          ▼                                      │
  │               ┌──────────────────┐                              │
  │               │  Redis Server    │  ← shared across all         │
  │               │  (port 6379)     │    service instances         │
  │               │  maxmem: 256mb   │                              │
  │               │  policy: LRU     │                              │
  │               └────────┬─────────┘                              │
  │                        │ cache miss only                        │
  │                        ▼                                        │
  │               ┌──────────────────┐                              │
  │               │   PostgreSQL     │  ← source of truth           │
  │               └──────────────────┘                              │
  └─────────────────────────────────────────────────────────────────┘

  Rules we always follow:
  1. One Redis client, created once at startup, shared everywhere
  2. Every operation takes a context with a timeout
  3. Every key has a TTL — nothing lives forever
  4. redis.Nil is a cache miss, not an error
  5. Redis failure degrades performance, never breaks functionality
  6. Write to DB first, invalidate cache second
  7. Name your keys: {service}:{entity}:{id}
```

That's Redis with Go. Start simple — just caching your heaviest database queries with a 5-minute TTL. Once that's working and measurable in Grafana, add rate limiting, then pub/sub if needed. Don't build everything at once. The cache that's running and saving 80% of your DB queries is infinitely better than the perfectly designed cache that's still being architected.
