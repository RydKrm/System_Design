## 1. What Is Domain-Driven Design and Why It Exists

Before you write a single line of code, you must understand the _problem_ that Domain-Driven Design (DDD) was invented to solve. Imagine you join a company that has been building an ERP system for ten years. The codebase has a folder called `utils`, another called `helpers`, and another called `services`. Every file references every other file. When a business manager asks you to change how an invoice is finalized, you discover that invoice logic is scattered across fourteen different files, mixed in with payroll logic, warehouse logic, and user authentication. Nobody dares to change anything because changing one thing silently breaks three other things. This nightmare is what Eric Evans described in his 2003 book _"Domain-Driven Design: Tackling Complexity in the Heart of Software"_ — and DDD is the systematic escape from it.

The central philosophy of DDD is simple, even if the implementation is not: **the structure and language of your code should match the structure and language of the business.** When your business analyst says "when a purchase order is approved, the inventory must be reserved," your code should contain exactly those concepts — a `PurchaseOrder`, an `Approve` operation, and an `Inventory` with a `Reserve` operation — not a generic `UpdateStatus` function buried inside a `database.go` file.

In an ERP system with more than 1,000 database tables, the business logic is extraordinarily complex. You have Accounts Receivable, Accounts Payable, General Ledger, Fixed Assets, Human Resources, Payroll, Procurement, Inventory, Manufacturing, Sales Orders, and dozens of other modules. Each module has its own rules, its own lifecycle, and its own data. But these modules are not isolated islands — they constantly interact. A Sales Order affects Inventory. A Purchase Order affects Accounts Payable. Payroll affects the General Ledger. DDD gives you the architecture to manage this complexity without descending into chaos.

## 2. The Core Mental Models You Must Internalize

### The Ubiquitous Language

Every domain has its own language. Accountants speak differently from warehouse managers. A "product" to the sales team is a "stock-keeping unit" (SKU) to the inventory team and a "finished good" to the manufacturing team. DDD demands that within each domain, every concept has exactly one name, and that name is used consistently everywhere — in conversations, in requirements documents, in database table names, in function names, in variable names, and in comments.

This shared vocabulary is called the **Ubiquitous Language**. It is not optional. When you sit in a meeting and the business analyst says "when the goods receipt is posted, the open purchase order quantity should be reduced," your code should contain a function called `PostGoodsReceipt` that calls `ReduceOpenQuantity` on a `PurchaseOrder`. If your code says `updateRecord(id, qty-1)` instead, you have broken the Ubiquitous Language, and future engineers will be unable to connect the business requirement to the code.

### Bounded Contexts

A Bounded Context is the most important strategic concept in DDD. Think of it as a fence around a part of the business where a specific model and its Ubiquitous Language are exclusively valid. Within the Inventory Bounded Context, the word "product" means one specific thing with specific attributes. Within the Pricing Bounded Context, "product" might mean something slightly different. Rather than trying to build one giant, unified model of a "product" that satisfies everyone (which inevitably satisfies nobody perfectly), DDD says: build separate models in separate contexts, and define explicit contracts between them.

```
┌─────────────────────────────────────────────────────────────────────┐
│                        ERP SYSTEM BOUNDARY                          │
│                                                                     │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────────────┐     │
│  │  INVENTORY   │   │    SALES     │   │    PROCUREMENT       │     │
│  │   CONTEXT    │   │   CONTEXT    │   │      CONTEXT         │     │
│  │              │   │              │   │                      │     │
│  │ - StockItem  │   │ - Product    │   │ - PurchaseOrder      │     │
│  │ - Warehouse  │   │ - SalesOrder │   │ - Supplier           │     │
│  │ - Movement   │   │ - Customer   │   │ - GoodsReceipt       │     │
│  └──────┬───────┘   └──────┬───────┘   └──────────┬───────────┘     │
│         │                  │                       │                │
│         └──────────────────┴───────────────────────┘                │
│                    Context Map (Integration)                        │
└─────────────────────────────────────────────────────────────────────┘
```

Each Bounded Context is an independent module. It has its own database schema (or at minimum its own schema namespace in PostgreSQL), its own codebase, and its own team ownership. This independence is what makes large-scale ERP systems maintainable.

### The Domain Model vs The Data Model

One of the most dangerous assumptions a backend developer makes is that the database table structure should mirror the code structure. In DDD, these are two completely different things. The **Domain Model** represents business concepts, rules, and behavior in code. The **Data Model** represents how that information is persisted in a database. They are related, but they are never the same thing.

For example, a `PurchaseOrder` domain entity might contain a list of `PurchaseOrderLine` objects as an in-memory collection. In the database, these are stored in two separate tables with a foreign key. The domain entity does not know about this — it only knows about the business rule that "a purchase order must have at least one line item." The job of the **Repository** is to translate between these two worlds.

## 3. The Strategic Design Layer — Thinking at Scale

### Identifying Your Bounded Contexts in an ERP

For a large ERP system, your Bounded Contexts might look like the following. Note that this is a starting point — real domain discovery happens through workshops with business stakeholders, a process called **Event Storming**.

```
│                        ERP BOUNDED CONTEXTS                              │
├──────────────────┬──────────────────┬──────────────────┬─────────────────┤

│                  │                  │                  │                 │

│ • Budgeting      │ • Logistics      │ • Performance    │                 │
│ • TaxManagement  │                  │                  │                 │
└──────────────────┴──────────────────┴──────────────────┴─────────────────┘
```

### The Context Map — Defining Relationships Between Contexts

Contexts do not live in isolation. They interact. The **Context Map** is a diagram (and a document) that describes the relationships between Bounded Contexts. There are several standard relationship patterns:

**Partnership** means two teams coordinate closely and evolve together. **Customer-Supplier** means one context (downstream) depends on another (upstream) and must negotiate with that team for changes. **Conformist** means the downstream team simply accepts whatever the upstream publishes with no negotiation power. **Anti-Corruption Layer (ACL)** means the downstream context builds a translation layer so that the upstream context's model does not "corrupt" the downstream model's Ubiquitous Language. **Published Language** means a well-documented, shared format (like an event schema or an API contract) used to communicate between contexts.

In our ERP, when a Sales Order is confirmed, the Inventory Context needs to reserve stock. The Sales Context does not call the Inventory Context directly — that would create tight coupling. Instead, the Sales Context publishes a `SalesOrderConfirmed` domain event, and the Inventory Context subscribes to it. This is the **Published Language / Event-Driven** relationship, and it is the dominant pattern in a large ERP.

```
                     CONTEXT MAP

   ┌────────────┐    event bus    ┌────────────────┐
   │   Sales    │──────────────►  │   Inventory    │
   │  Context   │                 │    Context     │
   └────────────┘                 └────────────────┘
         │                               │
         │ Published Language            │ ACL
         ▼                               ▼
   ┌────────────┐                ┌────────────────┐
   │  Accounts  │◄───────────────│   Procurement  │
   │ Receivable │  Customer /    │    Context     │
   │  Context   │  Supplier      └────────────────┘
   └────────────┘
```

## 4. The Tactical Design Layer — Writing the Code

The tactical patterns are the building blocks you use inside a single Bounded Context. These are the actual Go structs and interfaces you write every day.

### Entity

An Entity is a domain object that has a unique identity and a lifecycle. Its identity persists over time even as its attributes change. An `Invoice` is an entity — it has an `InvoiceID`, and it moves through states (Draft → Approved → Paid → Cancelled). An invoice that has been paid is still the same invoice; only its state has changed. In Go, an entity is typically a struct with an `ID` field and methods that enforce business rules.

```go
// domain/finance/accounts_receivable/entity/invoice.go

package entity

import (
    "errors"
    "time"
    "erp/domain/finance/accounts_receivable/valueobject"
)

type InvoiceStatus string

const (
    InvoiceStatusDraft     InvoiceStatus = "DRAFT"
    InvoiceStatusApproved  InvoiceStatus = "APPROVED"
    InvoiceStatusPaid      InvoiceStatus = "PAID"
    InvoiceStatusCancelled InvoiceStatus = "CANCELLED"
)

type Invoice struct {
    id          InvoiceID
    customerID  CustomerID
    lineItems   []InvoiceLineItem
    status      InvoiceStatus
    totalAmount valueobject.Money
    dueDate     time.Time
    createdAt   time.Time
    updatedAt   time.Time
    
    // Domain events that occurred during this entity's lifecycle
    domainEvents []DomainEvent
}

// Approve enforces the business rule that only DRAFT invoices can be approved.
// Notice how the method name uses the Ubiquitous Language of the finance domain.
func (i *Invoice) Approve(approvedBy UserID) error {
    if i.status != InvoiceStatusDraft {
        return errors.New("only a draft invoice can be approved")
    }
    if len(i.lineItems) == 0 {
        return errors.New("cannot approve an invoice with no line items")
    }
    
    i.status = InvoiceStatusApproved
    i.updatedAt = time.Now()
    
    // Record that this event occurred — it will be published after the transaction commits
    i.addDomainEvent(InvoiceApprovedEvent{
        InvoiceID:  i.id,
        CustomerID: i.customerID,
        Amount:     i.totalAmount,
        ApprovedBy: approvedBy,
        ApprovedAt: time.Now(),
    })
    
    return nil
}

func (i *Invoice) addDomainEvent(event DomainEvent) {
    i.domainEvents = append(i.domainEvents, event)
}

func (i *Invoice) PullDomainEvents() []DomainEvent {
    events := i.domainEvents
    i.domainEvents = nil // clear after pulling
    return events
}
```

### Value Object

A Value Object has no identity. It is defined entirely by its attributes. Two value objects with the same attributes are identical and interchangeable. A `Money` value object containing `{amount: 100.00, currency: "USD"}` is exactly the same as any other `Money` with the same values. Value objects are always immutable — you never modify them; you replace them with new ones. In Go, this means value objects have no setter methods, and all their fields are unexported.

```go
// domain/shared/valueobject/money.go

package valueobject

import (
    "errors"
    "fmt"
)

type Currency string

const (
    CurrencyUSD Currency = "USD"
    CurrencyEUR Currency = "EUR"
    CurrencyBDT Currency = "BDT"
)

// Money is a Value Object. It is immutable. It cannot be modified after creation.
type Money struct {
    amount   int64    // stored in smallest unit (cents) to avoid float precision issues
    currency Currency
}

func NewMoney(amount int64, currency Currency) (Money, error) {
    if amount < 0 {
        return Money{}, errors.New("money amount cannot be negative")
    }
    return Money{amount: amount, currency: currency}, nil
}

// Add returns a NEW Money object. It never modifies the receiver.
func (m Money) Add(other Money) (Money, error) {
    if m.currency != other.currency {
        return Money{}, fmt.Errorf("cannot add %s and %s", m.currency, other.currency)
    }
    return Money{amount: m.amount + other.amount, currency: m.currency}, nil
}

func (m Money) Amount() int64    { return m.amount }
func (m Money) Currency() Currency { return m.currency }
func (m Money) Equals(other Money) bool {
    return m.amount == other.amount && m.currency == other.currency
}
```

### Aggregate and Aggregate Root

This is the most critical and most misunderstood concept in DDD. An **Aggregate** is a cluster of related entities and value objects that are treated as a single unit for data changes. The **Aggregate Root** is the single entry point into this cluster — the only entity that the outside world is allowed to hold a reference to and interact with.

Consider a `PurchaseOrder`. It contains `PurchaseOrderLines`. Nobody in the application is allowed to directly add a line to the database — they must always go through the `PurchaseOrder` aggregate root. This is how business invariants are enforced. The `PurchaseOrder` can check "is this order already confirmed? Then you cannot add more lines." If code could bypass the aggregate root and directly insert a database row, these invariants would be impossible to protect.

```
┌────────────────────────────────────────────────────┐
│              PURCHASE ORDER AGGREGATE              │
│                                                    │
│   ┌────────────────────────────────────────────┐   │
│   │         PurchaseOrder (Aggregate Root)     │   │
│   │                                            │   │
│   │  - ID                                      │   │
│   │  - SupplierID                              │   │
│   │  - Status                                  │   │
│   │  - DeliveryAddress (Value Object)          │   │
│   │  - [] PurchaseOrderLine (Entity)           │   │
│   └────────────────────────────────────────────┘   │
│              │                                     │
│              ▼                                     │
│   ┌────────────────────────────────────────────┐   │
│   │       PurchaseOrderLine (Entity)           │   │
│   │                                            │   │
│   │  - LineID                                  │   │
│   │  - ProductID                               │   │
│   │  - Quantity (Value Object)                 │   │
│   │  - UnitPrice (Money Value Object)          │   │
│   └────────────────────────────────────────────┘   │
│                                                    │
│  ⚠ RULE: Nothing outside this box may directly    │
│    modify PurchaseOrderLine. All changes go        │
│    through PurchaseOrder methods only.             │
└────────────────────────────────────────────────────┘
```

### Repository

A Repository is the translation layer between the domain model and the persistence layer. The domain layer defines a **repository interface** (what operations it needs), and the infrastructure layer **implements** that interface using PostgreSQL. This is the Dependency Inversion Principle in action. The domain does not know that PostgreSQL exists — it only knows that something will save and load its aggregates.

```go
// domain/supply_chain/procurement/repository/purchase_order_repository.go

package repository

import (
    "context"
    "erp/domain/supply_chain/procurement/entity"
)

// PurchaseOrderRepository is an interface defined in the DOMAIN layer.
// The domain does not know how this is implemented.
type PurchaseOrderRepository interface {
    FindByID(ctx context.Context, id entity.PurchaseOrderID) (*entity.PurchaseOrder, error)
    FindBySupplier(ctx context.Context, supplierID entity.SupplierID) ([]*entity.PurchaseOrder, error)
    Save(ctx context.Context, po *entity.PurchaseOrder) error
    Delete(ctx context.Context, id entity.PurchaseOrderID) error
    NextID() entity.PurchaseOrderID
}
```

### Domain Service

Sometimes business logic does not naturally belong to any single entity or value object. When a calculation requires data from multiple aggregates, or when an operation involves coordinating between several domain concepts, you place that logic in a **Domain Service**. For example, "calculate the total outstanding balance for a customer across all their open invoices" requires reading multiple `Invoice` aggregates and does not belong on any single `Invoice` entity. This becomes a Domain Service.

```go
// domain/finance/accounts_receivable/service/customer_balance_service.go

package service

import (
    "context"
    "erp/domain/finance/accounts_receivable/entity"
    "erp/domain/finance/accounts_receivable/repository"
    "erp/domain/shared/valueobject"
)

type CustomerBalanceService struct {
    invoiceRepo repository.InvoiceRepository
}

func (s *CustomerBalanceService) CalculateOutstandingBalance(
    ctx context.Context,
    customerID entity.CustomerID,
    currency valueobject.Currency,
) (valueobject.Money, error) {
    invoices, err := s.invoiceRepo.FindOpenByCustomer(ctx, customerID)
    if err != nil {
        return valueobject.Money{}, err
    }
    
    total, _ := valueobject.NewMoney(0, currency)
    for _, invoice := range invoices {
        total, err = total.Add(invoice.OutstandingAmount())
        if err != nil {
            return valueobject.Money{}, err
        }
    }
    return total, nil
}
```

### Application Service

The Application Service is the orchestrator. It lives in the **application layer**, not the domain layer. It receives commands from the outside world (HTTP handlers, message queue consumers, gRPC handlers), calls domain entities and domain services, commits the transaction, and then publishes any domain events that were generated. The Application Service contains no business logic — it is purely coordination logic. If you find yourself writing an `if` statement in an application service that is about business rules (not about infrastructure concerns), that logic belongs in the domain layer.

```go
// application/supply_chain/procurement/command/approve_purchase_order.go

package command

import (
    "context"
    "erp/domain/supply_chain/procurement/repository"
    "erp/domain/supply_chain/procurement/entity"
    "erp/infrastructure/eventbus"
)

type ApprovePurchaseOrderCommand struct {
    PurchaseOrderID string
    ApprovedByUserID string
}

type ApprovePurchaseOrderHandler struct {
    purchaseOrderRepo repository.PurchaseOrderRepository
    eventBus          eventbus.EventBus
    unitOfWork        UnitOfWork
}

func (h *ApprovePurchaseOrderHandler) Handle(ctx context.Context, cmd ApprovePurchaseOrderCommand) error {
    return h.unitOfWork.Execute(ctx, func(ctx context.Context) error {
        // 1. Load the aggregate from the repository
        poID := entity.PurchaseOrderID(cmd.PurchaseOrderID)
        po, err := h.purchaseOrderRepo.FindByID(ctx, poID)
        if err != nil {
            return err
        }
        
        // 2. Execute the domain operation — business logic lives HERE (in the entity)
        userID := entity.UserID(cmd.ApprovedByUserID)
        if err := po.Approve(userID); err != nil {
            return err // business rule violation
        }
        
        // 3. Persist the updated aggregate
        if err := h.purchaseOrderRepo.Save(ctx, po); err != nil {
            return err
        }
        
        // 4. Publish domain events that were generated during the operation
        for _, event := range po.PullDomainEvents() {
            if err := h.eventBus.Publish(ctx, event); err != nil {
                return err
            }
        }
        
        return nil
    })
}
```

## 5. Cross-Domain Communication — The Heart of ERP Complexity

This section addresses your specific concern: what happens when one domain's data change requires another domain's data to update? This is the most important architectural question in a large ERP.

### The Golden Rule: Aggregates Are Transaction Boundaries

The first rule of aggregate design is: **one transaction, one aggregate.** You never modify two aggregates in the same database transaction. This sounds impossible for an ERP system where approving a purchase order must update inventory. But it is not impossible — it requires a different way of thinking.

Instead of doing everything in one transaction, you do things in **eventual consistency** steps, coordinated by domain events.

```
WRONG ❌ — Two aggregates in one transaction:
┌──────────────────────────────────────────┐
│  BEGIN TRANSACTION                       │
│    Update PurchaseOrder (status=APPROVED)│
│    Update Inventory (reservedQty++)      │  ← Different aggregate!
│  COMMIT                                  │
└──────────────────────────────────────────┘

RIGHT ✅ — One aggregate per transaction, events for the rest:
┌──────────────────────────────────────────┐    ┌────────────────────────────┐
│  BEGIN TRANSACTION                       │    │  (Later, separate process) │
│    Update PurchaseOrder (status=APPROVED)│    │  BEGIN TRANSACTION         │
│    Save event: PurchaseOrderApproved     │───►│    Update Inventory        │
│  COMMIT                                  │    │  COMMIT                    │
└──────────────────────────────────────────┘    └────────────────────────────┘
```

### The Outbox Pattern — Guaranteed Event Delivery

Publishing an event after committing a transaction has a fatal flaw: what if the process crashes between the commit and the event publish? The inventory will never be updated. The **Outbox Pattern** solves this by saving the event to the database in the same transaction as the aggregate change. A separate background process then reads the outbox table and publishes the events to the message bus. This guarantees at-least-once delivery.

```
┌───────────────────────────────────────────────────────────────────┐
│                    THE OUTBOX PATTERN                             │
│                                                                   │
│  ┌───────────────┐    same DB tx    ┌────────────────────────┐    │
│  │ PurchaseOrder │ ──────────────►  │ outbox_events (table)  │    │
│  │    Table      │                  │                        │    │
│  └───────────────┘                  │ id, event_type,        │    │
│                                     │ payload, published_at  │    │
│                                     └───────────┬────────────┘    │
│                                                 │ polling         │
│                                                 ▼                 │
│                                     ┌────────────────────────┐    │
│                                     │   Outbox Dispatcher    │    │
│                                     │   (background worker)  │    │
│                                     └───────────┬────────────┘    │
│                                                 │                 │
│                                                 ▼                 │
│                                     ┌────────────────────────┐    │
│                                     │   RabbitMQ / Message   │    │
│                                     │        Bus             │    │
│                                     └────────────────────────┘    │
└───────────────────────────────────────────────────────────────────┘
```

### The Saga Pattern — Long-Running Cross-Domain Processes

Some business processes span multiple domains and can take minutes or hours. Creating a Purchase Order involves: Procurement (creating the PO) → Finance (budget check) → Supplier (sending the PO) → Inventory (updating expected arrivals). If any step fails, some steps must be compensated (rolled back at the business level). This pattern is called a **Saga**.

There are two types of sagas. A **Choreography Saga** means each service listens for events and reacts — there is no central coordinator. A **Orchestration Saga** means a central Saga Orchestrator tells each service what to do and handles failures. For complex ERP workflows, Orchestration Sagas are easier to debug and monitor.

```
ORCHESTRATION SAGA: Purchase Order Approval Workflow

┌─────────────┐
│   Saga      │
│ Orchestrator│
└──────┬──────┘
       │
       │ 1. CheckBudget command
       ▼
┌─────────────┐     Success       ┌─────────────┐
│  Finance    │ ───────────────►  │   Saga      │
│  Context    │                   │ Orchestrator│
└─────────────┘                   └──────┬──────┘
                                         │
                                         │ 2. ReserveInventory command
                                         ▼
                                  ┌─────────────┐     Success
```

```go
import (
    "context"
    "erp/domain/supply_chain/procurement/entity"
    domainrepo "erp/domain/supply_chain/procurement/repository"
    "erp/infrastructure/persistence/postgres/model/supply_chain"

type PostgresPurchaseOrderRepository struct {
    db *sqlx.DB
}

func NewPostgresPurchaseOrderRepository(db *sqlx.DB) domainrepo.PurchaseOrderRepository {
    return &PostgresPurchaseOrderRepository{db: db}
}

func (r *PostgresPurchaseOrderRepository) FindByID(
    ctx context.Context,
    id entity.PurchaseOrderID,
) (*entity.PurchaseOrder, error) {
    var poModel model.PurchaseOrderModel
    err := r.db.GetContext(ctx, &poModel,
        `SELECT id, supplier_id, status, total_amount_cents, currency, created_at, updated_at
         FROM supply_chain.purchase_orders WHERE id = $1`, string(id))
    if err != nil {
        return nil, err
    }
    
    var lineModels []model.PurchaseOrderLineModel
    err = r.db.SelectContext(ctx, &lineModels,
        `SELECT id, purchase_order_id, product_id, quantity, unit_measure, unit_price_cents, currency
         FROM supply_chain.purchase_order_lines WHERE purchase_order_id = $1 ORDER BY created_at`,
        string(id))
    if err != nil {
        return nil, err
    }
    
    // Reconstruct the domain entity from the DB models
    return mapModelToPurchaseOrder(poModel, lineModels)
}

func (r *PostgresPurchaseOrderRepository) Save(
    ctx context.Context,
    po *entity.PurchaseOrder,
) error {
    poModel, lineModels := mapPurchaseOrderToModel(po)
    
    tx, err := r.db.BeginTxx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()
    
    _, err = tx.NamedExecContext(ctx, `
        INSERT INTO supply_chain.purchase_orders 
            (id, supplier_id, status, total_amount_cents, currency, created_at, updated_at)
        VALUES (:id, :supplier_id, :status, :total_amount_cents, :currency, :created_at, :updated_at)
        ON CONFLICT (id) DO UPDATE SET
            status = EXCLUDED.status,
            total_amount_cents = EXCLUDED.total_amount_cents,
            updated_at = EXCLUDED.updated_at
    `, poModel)
    if err != nil {
        return err
    }
```

### The Outbox Implementation

```go
// infrastructure/persistence/postgres/shared/outbox_repository.go

package shared

import (
    "context"
    "encoding/json"
    "erp/domain/shared/event"
    "github.com/jmoiron/sqlx"
    "time"
)

type OutboxEntry struct {
    ID          string    `db:"id"`
    EventName   string    `db:"event_name"`
    AggregateID string    `db:"aggregate_id"`
    Payload     []byte    `db:"payload"`
    CreatedAt   time.Time `db:"created_at"`
    PublishedAt *time.Time `db:"published_at"`
}

type OutboxRepository struct {
    db *sqlx.DB
}

// SaveWithinTransaction saves the event to the outbox within the SAME transaction
// as the aggregate save. This is the critical guarantee of the Outbox Pattern.
func (r *OutboxRepository) SaveWithinTransaction(
    ctx context.Context,
    tx *sqlx.Tx,
    domainEvent event.DomainEvent,
) error {
    payload, err := json.Marshal(domainEvent)
    if err != nil {
        return err
    }
    
    _, err = tx.ExecContext(ctx, `
        INSERT INTO shared.outbox_events (id, event_name, aggregate_id, payload, created_at)
        VALUES (gen_random_uuid(), $1, $2, $3, NOW())
    `, domainEvent.EventName(), domainEvent.AggregateID(), payload)
    
    return err
}
```

## 8. Database Design in DDD with PostgreSQL

### Schema-Per-Bounded-Context

In PostgreSQL, each Bounded Context gets its own **schema** (not a separate database). This provides logical separation while allowing JOINs when absolutely necessary (they should be rare).

```sql
-- Schemas map to Bounded Contexts
CREATE SCHEMA finance;
CREATE SCHEMA supply_chain;
CREATE SCHEMA human_capital;
CREATE SCHEMA shared;

-- The outbox lives in shared schema (used by all contexts)
CREATE TABLE shared.outbox_events (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_name   VARCHAR(255) NOT NULL,
    aggregate_id VARCHAR(255) NOT NULL,
    payload      JSONB NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    published_at TIMESTAMPTZ NULL,
    error        TEXT NULL,
    attempt      INT NOT NULL DEFAULT 0
);

CREATE INDEX idx_outbox_unpublished ON shared.outbox_events(created_at)
    WHERE published_at IS NULL;

-- Supply chain context tables
CREATE TABLE supply_chain.purchase_orders (
    id                UUID PRIMARY KEY,
    supplier_id       UUID NOT NULL,
    status            VARCHAR(50) NOT NULL DEFAULT 'DRAFT',
    total_amount_cents BIGINT NOT NULL DEFAULT 0,
    currency          CHAR(3) NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    
    CONSTRAINT chk_po_status CHECK (
        status IN ('DRAFT', 'PENDING_APPROVAL', 'APPROVED', 'RECEIVED', 'CANCELLED')
    ),
    CONSTRAINT chk_positive_amount CHECK (total_amount_cents >= 0)
);

CREATE TABLE supply_chain.purchase_order_lines (
    id               UUID PRIMARY KEY,
    purchase_order_id UUID NOT NULL REFERENCES supply_chain.purchase_orders(id),
    product_id       UUID NOT NULL,
    quantity         NUMERIC(15, 4) NOT NULL,
    unit_measure     VARCHAR(20) NOT NULL,
    unit_price_cents BIGINT NOT NULL,
    currency         CHAR(3) NOT NULL,
    
    CONSTRAINT chk_positive_qty CHECK (quantity > 0),
    CONSTRAINT chk_positive_price CHECK (unit_price_cents > 0)
);
```

### Aggregate IDs as UUIDs

Always use UUIDs as aggregate IDs. Sequential integers leak information (a competitor can guess how many orders you have by looking at order IDs), they create hotspots in distributed databases, and they prevent client-side ID generation (which is valuable in DDD).

### Soft Deletes and Audit Trails

In an ERP system, data is almost never truly deleted. You use soft deletes and keep a full audit trail of every change.

```sql
-- Every important table has these audit columns
ALTER TABLE supply_chain.purchase_orders ADD COLUMN deleted_at TIMESTAMPTZ NULL;
ALTER TABLE supply_chain.purchase_orders ADD COLUMN created_by UUID NOT NULL;
ALTER TABLE supply_chain.purchase_orders ADD COLUMN updated_by UUID NOT NULL;

-- Audit log table (one per context, or one global)
CREATE TABLE shared.audit_log (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    table_schema  VARCHAR(100) NOT NULL,
    table_name    VARCHAR(100) NOT NULL,
    record_id     UUID NOT NULL,
    operation     CHAR(6) NOT NULL, -- INSERT, UPDATE, DELETE
    old_values    JSONB,
    new_values    JSONB,
    changed_by    UUID NOT NULL,
    changed_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 9. The Anti-Corruption Layer

When your Inventory Context needs to know about a Product, but the Product is owned by the Catalog Context, the Inventory Context should not use the Catalog Context's `Product` entity directly. If the Catalog team changes their `Product` entity, it would break the Inventory Context. Instead, the Inventory Context builds an **Anti-Corruption Layer (ACL)** — a translation layer that converts the upstream model into a model that makes sense in the Inventory's own Ubiquitous Language.

```go
// application/supply_chain/inventory/acl/catalog_acl.go

package acl

import (
    "context"
    "erp/domain/supply_chain/inventory/entity"
)

// CatalogProduct is the Catalog context's model (as seen by Inventory).
// We define THIS struct in our context — we do not import the Catalog's entity.
type CatalogProduct struct {
    ID          string
    SKU         string
    Name        string
    UnitMeasure string
    IsActive    bool
}

// CatalogService is the interface Inventory uses to get catalog data.
// The implementation might call Catalog's HTTP API, read from a shared DB view,
// or consume events. Inventory does not care which.
type CatalogService interface {
    GetProduct(ctx context.Context, productID string) (*CatalogProduct, error)
}

// InventoryProductTranslator translates a CatalogProduct into an Inventory-domain concept.
// This is the Anti-Corruption Layer in action.
type InventoryProductTranslator struct{}

func (t *InventoryProductTranslator) ToStockableItem(cp *CatalogProduct) (*entity.StockableItem, error) {
    // Inventory only cares about a subset of catalog data,
    // expressed in Inventory's own language.
    return entity.NewStockableItem(
        entity.ProductID(cp.ID),
        cp.SKU,
        entity.UnitOfMeasure(cp.UnitMeasure),
    )
}
```

## 10. Event-Driven Architecture within DDD

### The EventBus Interface

The application layer uses an `EventBus` interface. The infrastructure layer provides the RabbitMQ implementation.

```go
// infrastructure/messaging/eventbus.go

package messaging

import (
    "context"
    "erp/domain/shared/event"
)

// EventBus is used by the application layer to publish domain events.
// The application layer does not know about RabbitMQ.
type EventBus interface {
    Publish(ctx context.Context, event event.DomainEvent) error
    Subscribe(eventName string, handler EventHandler) error
}

type EventHandler func(ctx context.Context, payload []byte) error
```

### The Event Consumer in Another Context

```go
// application/supply_chain/inventory/event_handler/on_po_approved.go

    reserveStockHandler *command.ReserveStockForPOHandler

    }

        PurchaseOrderID: event.AggregateID(),
        // ... map other fields
    }
    
    return h.reserveStockHandler.Handle(ctx, cmd)
}
```

## 11. Testing Strategy in DDD

### Testing the Domain Layer in Pure Isolation

The domain layer has zero external dependencies, which makes it the most testable part of the application. Domain tests are fast (they run in microseconds) and require no database, no HTTP server, and no message broker.

```go
// domain/supply_chain/procurement/entity/purchase_order_test.go

package entity_test

import (
    "testing"
    "erp/domain/supply_chain/procurement/entity"
    "erp/domain/shared/valueobject"
)

func TestPurchaseOrder_CannotApproveEmptyOrder(t *testing.T) {
    po := entity.NewPurchaseOrder(
        entity.NewPurchaseOrderID(),
        entity.SupplierID("supplier-1"),
    )
    
    err := po.Approve(entity.UserID("user-1"))
    
    if err == nil {
        t.Fatal("expected error when approving empty purchase order, got nil")
    }
    if err.Error() != "cannot approve a purchase order with no lines" {
        t.Errorf("unexpected error message: %s", err.Error())
    }
}

func TestPurchaseOrder_ApprovalGeneratesDomainEvent(t *testing.T) {
    po := entity.NewPurchaseOrder(
        entity.NewPurchaseOrderID(),
        entity.SupplierID("supplier-1"),
    )
    
    price, _ := valueobject.NewMoney(10000, valueobject.CurrencyUSD)
    po.AddLine("product-1", 5, "PCS", price)
    
    _ = po.Approve(entity.UserID("user-1"))
    
    events := po.PullDomainEvents()
    if len(events) != 1 {
        t.Fatalf("expected 1 domain event, got %d", len(events))
    }
    if events[0].EventName() != "procurement.purchase_order.approved" {
        t.Errorf("unexpected event name: %s", events[0].EventName())
    }
}
```

## 12. Common Mistakes Every New Engineer Makes

**Putting business logic in the application layer.** When you write an `if` statement in an application service that says "if the purchase order is from a preferred supplier, skip the budget check," that business rule belongs in a domain service or in the `PurchaseOrder` entity itself. Application services only coordinate — they do not decide.

**Letting HTTP concerns leak into the domain.** Your domain entities should never have JSON struct tags. They should never have HTTP error codes. They should never return HTTP responses. The moment you see `json:"invoice_id"` on a domain entity's field, something is wrong.

**Directly querying across Bounded Contexts.** You will be tempted to write a SQL JOIN between `supply_chain.purchase_orders` and `finance.accounts_payable` tables. This creates an invisible dependency between contexts. When the finance team changes their schema, your supply chain query breaks. Instead, each context maintains its own read model or communicates through events.

**Ignoring the Ubiquitous Language.** When your code says `updateStatus(1)` instead of `ApprovePurchaseOrder()`, future engineers cannot understand what business event is happening. Use the exact words your business stakeholders use.

**Making aggregates too large.** When you are unsure, make your aggregate smaller. An aggregate that contains twenty entities with fifty invariants is nearly impossible to work with. Prefer many small, focused aggregates connected by IDs rather than one giant aggregate.

**Breaking the one-aggregate-per-transaction rule.** It is tempting to modify an `Invoice` and a `LedgerEntry` in the same transaction because it feels safe. But this couples two contexts at the database level. Accept eventual consistency and use the Outbox Pattern.

**Skipping the Anti-Corruption Layer.** When the HR context imports the Payroll context's `Employee` entity directly, the HR context is now hostage to any change the Payroll team makes. Always define your own local representation of external concepts and translate at the boundary.

## 13. Glossary of Terms

**Aggregate** — A cluster of related domain objects (entities and value objects) that are treated as a single unit for data changes. Has a single Aggregate Root.

**Aggregate Root** — The single entity within an Aggregate that the outside world is allowed to interact with. Guards all invariants of the aggregate.

**Anti-Corruption Layer (ACL)** — A translation layer built by a downstream Bounded Context to protect itself from the model of an upstream context.

**Bounded Context** — A logical boundary within which a particular domain model and Ubiquitous Language apply. The fence around a sub-domain.

**CQRS (Command Query Responsibility Segregation)** — Separating write operations (Commands) from read operations (Queries) into different models and handlers.

**Domain Event** — An immutable record of something significant that happened in the business domain. Used to communicate between Bounded Contexts.

**Domain Service** — A stateless service that contains domain logic which does not naturally fit within a single Entity or Value Object.

**Entity** — A domain object with a unique, stable identity. Two entities with the same attributes but different IDs are different entities.

**Eventual Consistency** — A consistency model where, given no new updates, all replicas (or dependent data) will converge to the same value over time. Used across Bounded Contexts.

**Outbox Pattern** — A reliability pattern where domain events are stored in a database "outbox" table within the same transaction as the aggregate change, then published asynchronously.

**Repository** — An abstraction that provides collection-like access to aggregates. The domain defines the interface; the infrastructure implements it.

**Saga** — A pattern for managing long-running, distributed business transactions that span multiple Bounded Contexts, with compensation logic for failure scenarios.

**Ubiquitous Language** — The shared vocabulary between developers and domain experts, consistently used in code, conversations, and documentation within a Bounded Context.

**Unit of Work** — A pattern that tracks all changes made during a business operation and commits them in a single transaction.

**Value Object** — A domain object defined entirely by its attributes, with no identity. Immutable. Two value objects with the same attributes are identical.
