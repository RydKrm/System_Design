# Secrets in ENV — Leaked via docker inspect

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Safe With a Glass Door

A bank installs a safe in its vault to store its most sensitive documents: customer account numbers, authorization codes, signing certificates. The safe is constructed from thick steel, uses a combination lock, and sits behind a locked vault door. But the manufacturer, in a peculiar design decision, installed a glass panel on the front of the safe so that bank employees could confirm the safe was not empty without opening it. Through the glass, every document is fully legible. Anyone who can see through the glass can read every document inside.

The vault door — the physical barrier that limits access to authorized personnel — is the Docker daemon's access control. The glass panel — the design decision that makes secrets visible regardless of access — is the plaintext storage of credentials in Docker environment variables. Any user who has access to the Docker socket (any user in the `docker` group on the host, any process with the socket mounted, any CI agent with Docker API access) can run `docker inspect <container_id>` and receive a JSON document containing every environment variable set on every running container, displayed in complete, unredacted plaintext. The lock on the safe is real — Docker daemon access is gated — but for anyone who passes through that gate legitimately, the glass panel makes everything inside fully visible.

## 2. The Three Vectors of ENV Secret Exposure

Environment variable secrets in Docker are not exposed through a single vulnerability — they are exposed through three independent vectors, each requiring a different mitigation, and an application that patches only one of the three remains vulnerable through the others.

**Vector 1 — `docker inspect` by any Docker user.** This is the most direct exposure. Any process or user with access to the Docker daemon — which includes every member of the `docker` group on the host, any CI system that has been granted Docker API access, and any container with the Docker socket mounted — can enumerate all running containers and read their complete environment in plaintext. The command requires no elevated privileges beyond Docker group membership, and it reveals secrets for all containers on the host simultaneously, not just containers the caller owns or manages.

**Vector 2 — Image layer history.** When a developer or CI pipeline writes `ENV DB_PASSWORD=supersecret` directly in a Dockerfile, the environment variable is baked into an image layer and stored permanently in the image's metadata. This layer persists through every image build that derives from this base. The secret is visible in `docker history <image>`, in any registry that stores the image, and in every container ever created from the image or any of its descendants. Even if the secret is later removed from the Dockerfile, the old layer containing it still exists in the image registry unless the entire image history is rebuilt and repushed — a non-trivial operation. Secrets baked into image layers are frequently discovered through registry audits, security scans, or when images are shared with contractors or third parties.

**Vector 3 — CI/CD log leakage.** CI systems commonly log the environment of processes they execute for debugging purposes. A GitHub Actions workflow, GitLab CI pipeline, or Jenkins job that runs `docker run` commands or `docker-compose up` may print the container's environment to the build log. Build logs in many CI systems are accessible to all members of an organization, not just to the team that wrote the pipeline. Secrets injected as environment variables into CI-triggered container runs are frequently captured in build logs and become accessible to anyone with read access to the CI system.

```
              ENV Secret Exposure — Three Independent Vectors
              ==================================================

  Secret: DB_PASSWORD=supersecret123

  Vector 1 — docker inspect (runtime):
  ─────────────────────────────────────────────────────────────────────
  $ docker inspect api_container | jq '.[0].Config.Env'
  [
    "PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin",
    "DB_PASSWORD=supersecret123",   ← PLAINTEXT ❌
    "REDIS_URL=redis://...",
    "STRIPE_KEY=sk_live_abc123"     ← ALL SECRETS EXPOSED ❌
  ]
  Access required: Docker daemon socket (docker group membership)
  Attack path: any developer on the team, any CI agent, any compromised
               container with socket mounted can run this.

  Vector 2 — docker history (build-time):
  ─────────────────────────────────────────────────────────────────────
  Dockerfile:
    ENV DB_PASSWORD=supersecret123   ← Baked into image layer ❌

  $ docker history myapp:latest
  IMAGE         CREATED      CREATED BY                                     SIZE
  abc123def456  2 weeks ago  ENV DB_PASSWORD=supersecret123                 0B ← ❌
  ...

  $ docker image inspect myapp:latest | jq '.[0].Config.Env'
  ["DB_PASSWORD=supersecret123", ...]   ← In image metadata FOREVER ❌

  Published to registry → accessible to: all registry users, security
  scanners, anyone who pulls the image. Cannot be removed from history
  without rebuilding the entire image from scratch.

  Vector 3 — CI build log leakage:
  ─────────────────────────────────────────────────────────────────────
  GitHub Actions workflow:
    - run: docker run -e DB_PASSWORD=${{ secrets.DB_PASSWORD }} myapp:latest
  GitHub Actions: may log the expanded command line in workflow debug mode.
  If debug logging is enabled: "DB_PASSWORD=supersecret123" in log. ❌

  docker-compose up in CI:
  GitLab CI may capture stdout of docker compose, including env var output
  from containers that print their configuration on startup. ❌

  Access required: organization member with repo/pipeline read access.
  Blast radius: all organization members who can view CI logs.
```

## 3. Why `ENV` in Dockerfile Is Permanently Dangerous

The `ENV` instruction in a Dockerfile does not merely set a runtime environment variable — it creates a new image layer that permanently records the key-value pair in the image's metadata. This distinction is critical: runtime environment variables (set via `docker run -e` or Compose `environment:`) are properties of container instances and can be changed between runs. Build-time `ENV` instructions are properties of the image itself and persist across every container ever created from that image, including all future images that use it as a base.

```dockerfile
# THIS IS PERMANENTLY DANGEROUS — the secret lives in the image layer

FROM golang:1.23-alpine AS builder
# ...

FROM gcr.io/distroless/static:nonroot

# ❌ This creates a layer in the image:
# Layer content: {"Env": ["DB_PASSWORD=supersecret123"]}
# Visible in: docker history, docker image inspect, registry metadata,
#             every security scanner that scans this image.
ENV DB_PASSWORD=supersecret123

COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

```
              Image Layer Permanence — Why Removing ENV Later Doesn't Help
              ================================================================

  Build 1: ENV DB_PASSWORD=oldpassword → Layer SHA: abc123
  Build 2: ENV DB_PASSWORD=newpassword → Layer SHA: def456
           (removed the old layer, but old image tag still in registry)

  Build 3: Remove ENV DB_PASSWORD entirely → Layer SHA: ghi789

  State of the registry after Build 3:
  ├── Latest image: no DB_PASSWORD in layers ✅ (for new containers)
  ├── But: myapp:v1.0 still tagged in registry with Layer abc123 ← ❌
  ├── And: myapp:v1.1 still tagged in registry with Layer def456 ← ❌
  ├── And: any developer who pulled v1.0 or v1.1 has it in local cache ❌
  └── And: any container ever run from v1.0 or v1.1 had the secret injected ❌

  To truly eliminate: delete ALL image tags that contain the layer.
  Force-garbage-collect the registry. Rotate the secret.
  All of the above. This is a significant operational undertaking.
  Prevention is orders of magnitude cheaper than remediation.
```

## 4. The Correct Secrets Storage Hierarchy

Replacing environment variable secrets requires understanding the hierarchy of available secrets storage mechanisms and choosing the appropriate one for each deployment context. These mechanisms exist on a spectrum from "slightly better than ENV" to "production-grade zero-plaintext-exposure":

```
              Secrets Storage Hierarchy — Worst to Best
              ============================================

  ❌ WORST: ENV in Dockerfile
  Baked into image layers. Permanent. Visible in history. Registry-wide.

  ❌ BAD: environment: in docker-compose.yml (committed to repo)
  Secret in version control. Visible to all repo members.
  Plain text in file. Leaks via git log, PR reviews, branch access.

  ⚠️ BETTER: .env file (not committed) + environment: in docker-compose.yml
  Secret not in version control (if .gitignored).
  But: still visible via docker inspect. Still plaintext on host filesystem.
  Still captured by CI logs if the CI system logs expanded commands.

  ✅ GOOD: Docker Secrets (Swarm) — filesystem-based injection
  Secret mounted as file at /run/secrets/<name>.
  NOT visible in docker inspect (not an env var).
  Transmitted over encrypted Swarm channel.
  Application reads file, not env var.
  Access: restricted per-service in Swarm configuration.

  ✅ GOOD: Mounted secrets file (non-Swarm)
  Secret file on host filesystem, mounted read-only into container.
  Application reads file path, not env var.
  Not visible in docker inspect (it's a volume, not env).
  Host file must still be protected via host OS permissions.

  ✅ BEST: External Secrets Manager (Vault, AWS Secrets Manager, GCP SM)
  Secret never touches the filesystem of the container host.
  Application fetches at runtime via authenticated API.
  Access is audited (every read logged).
  Automatic rotation without container restarts.
  IAM-scoped: each service can only read its own secrets.
```

## 5. Docker Secrets — The Correct Implementation

Docker Secrets is the production-grade mechanism for secret injection in Docker Swarm deployments. Secrets are stored encrypted in Swarm's raft log, distributed over TLS to nodes that host containers needing them, and mounted as files in the container's `/run/secrets/` directory — never exposed as environment variables. The critical operational difference is that `docker inspect` on a container using Secrets shows only the secret name and whether it is mounted, never the secret's value:

```bash
# Create secrets in Swarm (production):
echo "supersecret123" | docker secret create db_password -
echo "sk_live_abc123" | docker secret create stripe_key -
echo "redis-secret" | docker secret create redis_password -

# Verify secrets exist (values are NEVER shown):
docker secret ls
# ID                          NAME             CREATED          UPDATED
# v7x3k2mq9p8n4l6j...        db_password      2 minutes ago   2 minutes ago
# w8y4l3nr0q9o5m7k...        stripe_key       1 minute ago    1 minute ago

# docker secret inspect shows metadata, NOT the value:
docker secret inspect db_password
# [{
#   "ID": "v7x3k2mq9p8n4l6j...",
#   "Spec": { "Name": "db_password", "Labels": {} },
#   "CreatedAt": "...", "UpdatedAt": "..."
# }]
# ← Secret value: not shown. Cannot be retrieved after creation. ✅
```

```yaml
# docker-compose.yml (Swarm deploy) — Secrets as filesystem injection

version: "3.9"

secrets:
  db_password:
    external: true       # Pre-created with docker secret create
  stripe_key:
    external: true
  redis_password:
    external: true

services:
  api:
    build: .
    # No environment: block with secrets. Secrets are files, not env vars. ✅
    environment:
      DB_HOST: postgres         # Non-secret config: safe as env var
      DB_PORT: "5432"
      DB_NAME: myapp
      DB_USER: appuser
      ENVIRONMENT: production
      PORT: "8080"
    secrets:
      - db_password             # Mounted at /run/secrets/db_password ✅
      - stripe_key              # Mounted at /run/secrets/stripe_key ✅
      # redis_password NOT mounted here — api uses DB_URL with embedded auth,
      # redis connection string built from file read in application code

  postgres:
    image: postgres:16.2-alpine3.19@sha256:...
    environment:
      POSTGRES_USER: appuser
      POSTGRES_DB:   myapp
      # POSTGRES_PASSWORD_FILE: tells the official postgres image to read
      # the password from a file rather than the POSTGRES_PASSWORD env var.
      # The file content is provided by the db_password secret below. ✅
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password             # Only the database needs the DB password ✅

  redis:
    image: redis:7.2-alpine3.19@sha256:...
    command: sh -c "redis-server --requirepass $(cat /run/secrets/redis_password)"
    secrets:
      - redis_password          # Only Redis needs its own password ✅
```

```go
// config.go — Reading secrets from files in Go
package config

import (
    "fmt"
    "os"
    "strings"
)

// Config holds all application configuration.
type Config struct {
    DBHost     string
    DBPort     string
    DBName     string
    DBUser     string
    DBPassword string // Loaded from file, never from env var
    StripeKey  string // Loaded from file
    Port       string
}

// Load reads configuration from environment variables (non-sensitive)
// and Docker Secrets files (sensitive values).
// This separation is intentional: non-sensitive config is fine as env vars,
// sensitive credentials must come from file paths.
func Load() (*Config, error) {
    dbPassword, err := readSecretFile("/run/secrets/db_password")
    if err != nil {
        return nil, fmt.Errorf("loading db_password: %w", err)
    }

    stripeKey, err := readSecretFile("/run/secrets/stripe_key")
    if err != nil {
        return nil, fmt.Errorf("loading stripe_key: %w", err)
    }

    return &Config{
        DBHost:     requireEnv("DB_HOST"),
        DBPort:     getEnvOrDefault("DB_PORT", "5432"),
        DBName:     requireEnv("DB_NAME"),
        DBUser:     requireEnv("DB_USER"),
        DBPassword: dbPassword,  // From file — not in env — not in docker inspect ✅
        StripeKey:  stripeKey,   // From file — not in env — not in docker inspect ✅
        Port:       getEnvOrDefault("PORT", "8080"),
    }, nil
}

// readSecretFile reads a secret value from a Docker Secrets file path.
// Falls back to an environment variable with the uppercased name for
// local development environments where Docker Swarm is not running.
func readSecretFile(path string) (string, error) {
    // Production path: Docker Secret file
    if data, err := os.ReadFile(path); err == nil {
        value := strings.TrimSpace(string(data))
        if value == "" {
            return "", fmt.Errorf("secret file %s is empty", path)
        }
        return value, nil
    }

    // Development fallback: environment variable with uppercased basename
    // Example: /run/secrets/db_password → DB_PASSWORD
    base := strings.ToUpper(strings.ReplaceAll(
        strings.TrimPrefix(path, "/run/secrets/"), "-", "_",
    ))
    if value := os.Getenv(base); value != "" {
        return value, nil
    }

    return "", fmt.Errorf("secret not found at %s or in env var %s", path, base)
}

func requireEnv(key string) string {
    value := os.Getenv(key)
    if value == "" {
        panic(fmt.Sprintf("required environment variable %s is not set", key))
    }
    return value
}

func getEnvOrDefault(key, defaultValue string) string {
    if value := os.Getenv(key); value != "" {
        return value
    }
    return defaultValue
}
```

## 6. The `docker inspect` Before and After — Verifying the Improvement

The clearest validation of correct secret handling is comparing `docker inspect` output before and after the migration from env vars to secrets:

```bash
# ── BEFORE (ENV vars) — docker inspect shows plaintext secrets ────────────────
docker inspect api_container | jq '.[0].Config.Env'
# [
#   "PATH=/usr/local/sbin:/usr/local/bin",
#   "DB_HOST=postgres",
#   "DB_PASSWORD=supersecret123",      ← PLAINTEXT ❌
#   "STRIPE_KEY=sk_live_abc123...",    ← PLAINTEXT ❌
#   "REDIS_PASSWORD=redis-secret"      ← PLAINTEXT ❌
# ]

# ── AFTER (Docker Secrets) — docker inspect shows nothing sensitive ────────────
docker inspect api_container | jq '.[0].Config.Env'
# [
#   "PATH=/usr/local/sbin:/usr/local/bin",
#   "DB_HOST=postgres",           ← Non-sensitive: safe as env var ✅
#   "DB_PORT=5432",               ← Non-sensitive ✅
#   "DB_NAME=myapp",              ← Non-sensitive ✅
#   "DB_USER=appuser",            ← Non-sensitive ✅

#   "PORT=8080"                   ← Non-sensitive ✅

# Secrets are visible only as mount metadata, not values:
```

## 7. Development Workflow Without Docker Swarm

Docker Secrets requires Docker Swarm mode, which is not commonly used in local development environments. The development workflow uses `.env` files with the secret file reading fallback built into the application — combined with strict `.gitignore` rules:

```bash
# Development: .env file (NEVER committed to git)
# .env:
DB_PASSWORD=dev-only-password
STRIPE_KEY=sk_test_dev_key_not_real
REDIS_PASSWORD=dev-redis-password
```

```yaml
# docker-compose.yml (development) — uses env var fallback in the app
# In development, secrets come from .env via the fallback in readSecretFile().
# In production (Swarm), secrets come from Docker Secrets files.
# The application code handles both transparently.

services:
  api:
    build: .
    env_file: .env          # Provides DB_PASSWORD etc. as env vars for dev fallback
    environment:
      DB_HOST:   postgres
      DB_PORT:   "5432"
      DB_NAME:   myapp
      DB_USER:   appuser
      ENVIRONMENT: development
```

```bash
# .gitignore — MANDATORY
.env
.env.*
!.env.example       # Commit only the example

# .env.example — committed to repository, contains only placeholder values
DB_PASSWORD=replace_with_real_password
STRIPE_KEY=replace_with_real_stripe_key
REDIS_PASSWORD=replace_with_real_redis_password
```

```bash
# Audit: verify no secrets are in git history
git log --all --full-history --oneline -- ".env" | head
# Any output here means a .env file was committed at some point.
# If found: rotate ALL credentials immediately. They are permanently exposed
# via git history to anyone with repo access.

# Scan for hardcoded secrets in source code:
git log --all --full-history -p | grep -i "password\|secret\|api_key" | grep "^+" | head -20
# Any matches should be reviewed. This is a rough heuristic.
# For thorough scanning: use trufflehog or git-secrets.

# Verify no secrets are in the built Docker image:
docker run --rm --entrypoint env myapp:latest | grep -iE "password|secret|key|token"
# Any output: credential in image environment. Fix: remove from Dockerfile ENV.
```

## 8. The Kubernetes Equivalents — Sealed Secrets and Vault Agent Injector

For Kubernetes deployments, the equivalent mechanisms to Docker Secrets are Kubernetes Secrets (base64-encoded, not encrypted at rest by default), Sealed Secrets (asymmetrically encrypted Kubernetes Secrets that can be safely committed to git), and the HashiCorp Vault Agent Injector (runtime secret injection into pods without the secret ever touching Kubernetes etcd):

```yaml
# Kubernetes — Secret as file mount (not environment variable)
# apiVersion: v1, kind: Secret is base64 encoded but NOT encrypted at rest by default.
# Use Sealed Secrets or KMS encryption for production.

apiVersion: v1
kind: Secret
metadata:
  name: api-secrets
type: Opaque
stringData:
  db_password: "supersecret123"
  stripe_key: "sk_live_abc123"

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  template:
    spec:
      containers:
        - name: api
          image: myapp:latest
          env:
            # Non-sensitive config: safe as env var
            - name: DB_HOST
              value: postgres-service
            - name: DB_PORT
              value: "5432"
          volumeMounts:
            # Mount secrets as FILES, not env vars.
            # Not visible in kubectl describe pod (values not shown).
            - name: api-secrets
              mountPath: /run/secrets
              readOnly: true
      volumes:
        - name: api-secrets
          secret:
            secretName: api-secrets
            # defaultMode: 0400 = readable only by owner (container process)
            defaultMode: 0400
```

## 9. The Golden Rule

> Environment variables are a broadcast medium, not a secure vault. Every value injected as an environment variable into a Docker container is permanently accessible through `docker inspect` to any user or process with Docker daemon access. When an `ENV` instruction is used in a Dockerfile, the secret becomes a permanent resident of every image layer built from that point forward, visible in `docker history`, readable by anyone who pulls the image, and impossible to remove without rebuilding and retagging the entire image. Environment variables captured in CI logs become accessible to every member of the organization with CI read access. The correct separation is categorical: non-sensitive configuration (hostnames, port numbers, feature flags, log levels, environment names) is appropriate as environment variables. Sensitive credentials (database passwords, API keys, signing secrets, certificates, private keys) must never appear in environment variables. They must be injected through a secrets management mechanism that stores values encrypted, delivers them as filesystem-mounted files rather than env vars, and never exposes them through container inspection commands. For Docker Swarm: Docker Secrets. For Kubernetes: Secret volume mounts (not `env.valueFrom.secretKeyRef`). For cloud deployments: AWS Secrets Manager, GCP Secret Manager, or HashiCorp Vault with runtime injection. Application code must be written to read credentials from file paths rather than environment variables, with a development fallback that reads from env vars only when the secret file path does not exist. The transition from env var secrets to file-based secrets is not optional — it is a prerequisite for production-grade security posture.

A secret stored in an environment variable is a secret shared with everyone who has Docker access. A secret mounted as a file is a secret shared with no one but the application that reads it.
