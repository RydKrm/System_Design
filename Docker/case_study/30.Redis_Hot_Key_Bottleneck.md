# Redis Hot Key Bottleneck

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The One Librarian Everyone Needs

A large university library employs a single head librarian — Elena — who is extraordinarily efficient and can process requests incredibly fast. The library also has a reference desk staffed by many assistants who handle most patron requests. But there is one particular reference book — the annual course catalogue — that every student needs, and they have been told to ask Elena specifically for it because she is the authoritative source for that document.

During enrollment week, thousands of students arrive. Every student needs the course catalogue. Every student goes to Elena. Elena can process requests at a remarkable rate, but she is one person with one pair of hands. While she is handing the catalogue to one student, the next student waits. While she is handing it to that student, the next fifty wait. The line for Elena extends out the door. Meanwhile, the other library assistants sit largely idle — they are not the bottleneck. Elena is. And the tragedy is that the course catalogue barely changes — it is the same document every student receives. Elena hands the same thing to every person in the queue. The bottleneck is not the data itself — it is the single point of access to that data.

This is the Redis hot key problem in precise miniature. Redis is extraordinarily fast — capable of handling hundreds of thousands of commands per second. But Redis is single-threaded in its command processing: one command executes completely before the next begins. When fifty API replicas each request the same key every 100ms, Redis must process those fifty requests sequentially. The key itself may be tiny — a few kilobytes of trending post IDs. The data barely changes — it is updated perhaps once per minute. But every request to that key must go through Redis's single command thread, and at sufficient request rate, that thread becomes saturated. All other Redis operations — session lookups, rate limit checks, distributed locks — queue behind the hot key reads and experience latency regardless of their own complexity.

---

## 2. Redis's Threading Model — Why One Key Can Saturate a Server

Redis's architecture is built around a single-threaded event loop for command execution. When a client sends a command, Redis's event loop receives it, processes it completely — reading the data, encoding the response — and then moves to the next queued command. This design eliminates locking and synchronization overhead, which is why Redis can achieve sub-millisecond response times for individual commands. The trade-off is that all commands are serialized: no two commands execute simultaneously, regardless of how many CPU cores the Redis server has.

Modern Redis (6.0+) introduced I/O threading for network read/write operations, which parallelizes the network layer while keeping command execution single-threaded. This improves throughput for workloads with many small commands but does not change the fundamental serialization of command execution. A `GET trending_posts` command that takes 0.5ms to execute — reading the data, serializing it, sending the response — still blocks all other commands for that 0.5ms while it runs.

```
              Redis Single-Threaded Command Execution — Hot Key Saturation
              ================================================================

  Redis event loop (single thread):

  t=0.000ms: GET trending_posts ← from api-replica-1
  t=0.500ms: [completed] response sent to replica-1
  t=0.500ms: GET trending_posts ← from api-replica-2
  t=1.000ms: [completed] response sent to replica-2
  t=1.000ms: GET trending_posts ← from api-replica-3
  ...

  Meanwhile, queued behind the hot key reads:
  GET session:user-1023       ← arrived at t=0.000ms, waiting... ← 25ms delay ❌
  INCR ratelimit:192.168.1.5  ← arrived at t=0.000ms, waiting... ← 25ms delay ❌
  SET lock:order-7849 1       ← arrived at t=0.000ms, waiting... ← 25ms delay ❌

  50 replicas × 10 req/s = 500 GET trending_posts per second
  Each GET: 0.5ms execution time
  Total time consumed by hot key: 500 × 0.5ms = 250ms per second
  Available time for ALL other commands: 750ms per second (out of 1000ms)
  Other commands see: 1.33× latency inflation from queue wait ← degraded ❌

  At 1000 req/s on hot key (100 replicas × 10 req/s):
  Total time consumed by hot key: 1000 × 0.5ms = 500ms per second
  Available time for other commands: 500ms per second
  Other commands: 2× latency inflation ← significant degradation ❌

  At 2000 req/s on hot key:
  Total time consumed: 2000 × 0.5ms = 1000ms per second
  Available time for other commands: 0ms ← FULLY SATURATED ❌❌❌
  Redis CPU: 100%. All operations experience extreme latency.
  Connections queue. Timeouts begin. Application-wide degradation. ❌

  The throughput ceiling for this hot key:
  1000ms / 0.5ms per command = 2000 commands/second maximum
  Reached at: 2000 / 10 req/s = 200 API replicas
  Scaling beyond 200 replicas: the hot key is the ceiling, not Redis capacity.
```

The critical insight in the diagram above is that the hot key does not merely saturate itself — it saturates Redis for all operations. A Redis instance that is fully consumed processing hot key reads cannot promptly respond to session lookups, rate limit increments, or distributed lock acquisitions. The entire application's Redis-dependent operations degrade simultaneously, even though most of them have nothing to do with the hot key. From the monitoring perspective, this looks like a global Redis performance problem, not a single key problem — which is why it is often misdiagnosed.

## 3. Identifying Hot Keys — The Diagnostic Approach

Redis provides built-in tooling for identifying hot keys, but the tools must be used correctly because naive approaches have significant performance impact:

```bash
# ── Method 1: Redis --hotkeys flag (Redis 4.0+, non-blocking scan) ─────────────
# Scans the entire keyspace and reports the most frequently accessed keys.
# Uses OBJECT FREQ which requires LFU maxmemory-policy to be set.
# Configure redis.conf first:
# maxmemory-policy allkeys-lfu   (or volatile-lfu)
# Then:
redis-cli --hotkeys -a <password>
# Output:
# -------- summary -------
# Sampled 15432 keys in the keyspace.
# hot key found with counter: 0       keyname: trending_posts         ← HOT KEY ❌
# hot key found with counter: 0       keyname: feature_flags
# ...

# ── Method 2: Redis MONITOR command (CAUTION: performance impact) ──────────────
# Streams ALL commands processed by Redis in real-time.
# WARNING: can reduce Redis throughput by 50%+ under load. Use briefly only.
redis-cli -a <password> MONITOR | head -200
# Output (filtered for hot key):
# 1695123456.789 [0 172.20.0.5:52341] "GET" "trending_posts"
# 1695123456.790 [0 172.20.0.6:52342] "GET" "trending_posts"
# 1695123456.791 [0 172.20.0.7:52343] "GET" "trending_posts"
# ... (same key, different client IPs, every millisecond)

# ── Method 3: Redis DEBUG SLEEP + latency monitoring (safe) ───────────────────
# Enable Redis latency monitoring for commands exceeding threshold:
redis-cli -a <password> CONFIG SET latency-monitor-threshold 1  # 1ms threshold
redis-cli -a <password> CONFIG SET latency-tracking yes
redis-cli -a <password> LATENCY HISTORY event
redis-cli -a <password> LATENCY LATEST
# Shows commands exceeding threshold — hot key commands will dominate. ✅

# ── Method 4: Application-level key access counter ────────────────────────────
# The cleanest approach: count key accesses in your application.
# Before every Redis GET, increment a local counter:
# hot_key_counter.Add("trending_posts", 1)
# Export as Prometheus metric: redis_key_access_total{key="trending_posts"} 4523
# Alert if any key exceeds threshold. ✅

# ── Method 5: Redis keyspace notifications (async, no performance impact) ──────
# Configure Redis to publish notifications when keys are accessed:
redis-cli -a <password> CONFIG SET notify-keyspace-events "KExg"
# Subscribe to keyspace notifications:
redis-cli -a <password> SUBSCRIBE '__keyevent@0__:get'
# Every GET triggers a notification. Count notifications per key. ✅ (low overhead)
```

## 4. Solution 1 — Local In-Process Cache with Short TTL

The most effective and lowest-latency solution for hot read keys is a local in-process cache — a simple `sync.Map` or `map` with a mutex inside each API instance. When a replica needs the trending posts, it first checks its local in-memory cache. If the cache entry is fresh (within TTL), it returns the locally cached value without contacting Redis at all. The Redis hot key request rate drops from `replicas × requests_per_second` to `replicas × (1 / TTL_seconds)`:

```
              Request Rate Reduction — Local Cache with 5s TTL
              ==================================================

  Without local cache:
  50 replicas × 10 req/s = 500 Redis GET/s on trending_posts ❌

  With local cache (TTL = 5 seconds):
  Each replica: refreshes from Redis once every 5 seconds
  50 replicas × (1 / 5s) = 50 / 5 = 10 Redis GET/s total ✅
  Reduction: 500 → 10 = 98% fewer Redis requests for this key ✅

  Trade-off: each instance may serve slightly stale data (up to 5 seconds old).
  For trending posts, leaderboards, feature flags: acceptable. ✅
  For financial balances, inventory counts: unacceptable. Use Redis directly. ❌
```

```go
// localcache/cache.go — Thread-safe local in-process cache with TTL and stampede protection

package localcache

import (
    "context"
    "fmt"
    "math/rand"
    "sync"
    "time"
)

// entry represents a single cached value with its expiration time.
type entry struct {
    value     []byte
    expiresAt time.Time
    // refreshingAt: set by the goroutine performing a background refresh.
    // Prevents multiple goroutines from refreshing the same key simultaneously
    // (cache stampede protection).
    refreshingAt time.Time
}

// Cache is a local in-process key-value cache with TTL and stampede protection.
// Intended as a Layer 1 cache above Redis (Layer 2) for hot keys.
type Cache struct {
    mu      sync.RWMutex
    entries map[string]*entry
    baseTTL time.Duration
    jitter  float64 // TTL jitter fraction (0.1 = ±10%)
}

func New(baseTTL time.Duration, jitter float64) *Cache {
    c := &Cache{
        entries: make(map[string]*entry),
        baseTTL: baseTTL,
        jitter:  jitter,
    }
    // Background goroutine: clean expired entries periodically.
    go c.cleanLoop()
    return c
}

// jitteredTTL returns baseTTL ± jitter fraction.
// Randomizing TTL prevents all instances from refreshing a key simultaneously
// when the TTL expires — the "thundering herd" or "cache stampede" problem.
// Example: baseTTL=5s, jitter=0.1 → TTL between 4.5s and 5.5s
func (c *Cache) jitteredTTL() time.Duration {
    delta := float64(c.baseTTL) * c.jitter
    jitter := (rand.Float64()*2 - 1) * delta // random in [-delta, +delta]
    return c.baseTTL + time.Duration(jitter)
}

// GetOrFetch returns the cached value for key, calling fetchFn if the cache
// misses or the entry has expired. Uses a single-flight pattern to prevent
// multiple concurrent fetches for the same key (cache stampede protection).
func (c *Cache) GetOrFetch(ctx context.Context, key string, fetchFn func(ctx context.Context) ([]byte, error)) ([]byte, error) {
    // Fast path: read lock — check if cache entry is valid.
    c.mu.RLock()
    if e, ok := c.entries[key]; ok && time.Now().Before(e.expiresAt) {
        value := e.value
        c.mu.RUnlock()
        return value, nil // Cache hit. No Redis call. ✅
    }
    c.mu.RUnlock()

    // Slow path: write lock — fetch and populate cache.
    c.mu.Lock()
    defer c.mu.Unlock()

    // Double-check: another goroutine may have populated the cache
    // between releasing the read lock and acquiring the write lock.
    if e, ok := c.entries[key]; ok && time.Now().Before(e.expiresAt) {
        return e.value, nil // Someone else refreshed it. Use theirs. ✅
    }

    // Check if a refresh is already in progress (stampede protection).
    // If refreshingAt is recent (< 500ms ago), return stale data while
    // the in-progress refresh completes.
    if e, ok := c.entries[key]; ok && time.Since(e.refreshingAt) < 500*time.Millisecond {
        // Return stale value while background refresh is running.
        // Better than having N goroutines all call Redis simultaneously. ✅
        return e.value, nil
    }

    // Mark this key as being refreshed.
    now := time.Now()
    if existing, ok := c.entries[key]; ok {
        existing.refreshingAt = now
    } else {
        c.entries[key] = &entry{refreshingAt: now}
    }

    // Release lock during the (potentially slow) Redis fetch.
    c.mu.Unlock()
    value, err := fetchFn(ctx)
    c.mu.Lock()

    if err != nil {
        // Fetch failed: if we have a stale entry, serve it rather than returning error.
        // Graceful degradation: slightly stale data > error response. ✅
        if e, ok := c.entries[key]; ok && len(e.value) > 0 {
            return e.value, nil
        }
        return nil, fmt.Errorf("fetching %s: %w", key, err)
    }

    // Store fresh value with jittered TTL.
    c.entries[key] = &entry{
        value:     value,
        expiresAt: time.Now().Add(c.jitteredTTL()),
    }

    return value, nil
}

func (c *Cache) cleanLoop() {
    ticker := time.NewTicker(30 * time.Second)
    defer ticker.Stop()
    for range ticker.C {
        c.mu.Lock()
        now := time.Now()
        for key, e := range c.entries {
            if now.After(e.expiresAt) && time.Since(e.expiresAt) > 60*time.Second {
                delete(c.entries, key)
            }
        }
        c.mu.Unlock()
    }
}
```

```go
// usage in the API handler

package handler

import (
    "context"
    "encoding/json"
    "time"

    "github.com/redis/go-redis/v9"
    "yourapp/localcache"
)

type FeedHandler struct {
    redis      *redis.Client
    localCache *localcache.Cache
}

func NewFeedHandler(redisClient *redis.Client) *FeedHandler {
    return &FeedHandler{
        redis: redisClient,
        // Local cache: 5 second TTL, ±10% jitter.
        // Each API instance independently caches the result.
        // 50 instances × (1/5s) = 10 Redis requests/s total. ✅
        localCache: localcache.New(5*time.Second, 0.10),
    }
}

func (h *FeedHandler) GetTrendingPosts(ctx context.Context) ([]Post, error) {
    // GetOrFetch: returns local cache hit without touching Redis.
    // On miss: calls the fetch function (Redis GET) and caches the result.
    raw, err := h.localCache.GetOrFetch(ctx, "trending_posts", func(ctx context.Context) ([]byte, error) {
        // This function is called at most once per TTL window per instance.
        // 50 instances × once every 5s = 10 Redis requests/s. ✅
        return h.redis.Get(ctx, "trending_posts").Bytes()
    })
    if err != nil {
        return nil, err
    }

    var posts []Post
    return posts, json.Unmarshal(raw, &posts)
}
```

## 5. Solution 2 — Background Refresh with Staggered Timing

For data that must be as fresh as possible without triggering cache stampedes, the background refresh pattern maintains the in-process cache by proactively refreshing it in the background before expiry — eliminating the cache miss entirely:

```go
// bgcache/bgcache.go — Background proactive refresh cache

package bgcache

import (
    "context"
    "log"
    "sync"
    "sync/atomic"
    "time"
    "unsafe"
)

// atomicValue holds a value that can be swapped atomically.
// Readers get a consistent snapshot; the writer replaces the whole value.
type atomicValue struct {
    p unsafe.Pointer // *[]byte
}

func (v *atomicValue) Load() []byte {
    p := atomic.LoadPointer(&v.p)
    if p == nil {
        return nil
    }
    return *(*[]byte)(p)
}

func (v *atomicValue) Store(b []byte) {
    atomic.StorePointer(&v.p, unsafe.Pointer(&b))
}

// BackgroundCache maintains a hot-path cache entry refreshed on a schedule.
// Reads are lock-free (atomic pointer swap). Writers run in a single background goroutine.
// Zero latency on reads: always serves the last known value. ✅
type BackgroundCache struct {
    key         string
    value       atomicValue
    refreshErr  error
    mu          sync.RWMutex // protects refreshErr
    fetchFn     func(ctx context.Context) ([]byte, error)
    baseInterval time.Duration
    jitter       time.Duration
}

func New(key string, baseInterval, jitter time.Duration, fetchFn func(ctx context.Context) ([]byte, error)) *BackgroundCache {
    c := &BackgroundCache{
        key:          key,
        fetchFn:      fetchFn,
        baseInterval: baseInterval,
        jitter:       jitter,
    }

    // Initial load: synchronous. Block until first value is available.
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    if data, err := fetchFn(ctx); err == nil {
        c.value.Store(data)
    }

    // Background refresh goroutine: runs forever, refreshes on schedule.
    go c.refreshLoop()
    return c
}

// Get returns the current cached value. Lock-free. Always fast. ✅
func (c *BackgroundCache) Get() ([]byte, error) {
    val := c.value.Load()
    c.mu.RLock()
    err := c.refreshErr
    c.mu.RUnlock()

    if val == nil && err != nil {
        return nil, err // Never successfully loaded
    }
    return val, nil // Returns last known good value even if last refresh failed ✅
}

func (c *BackgroundCache) refreshLoop() {
    for {
        // Stagger: add random jitter to prevent all instances refreshing simultaneously.
        // baseInterval=5s, jitter=500ms → sleep between 4.5s and 5.5s. ✅
        jitterMs := time.Duration(float64(c.jitter) * (2*rand.Float64() - 1))
        sleepDuration := c.baseInterval + jitterMs
        time.Sleep(sleepDuration)

        ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
        data, err := c.fetchFn(ctx)
        cancel()

        if err != nil {
            log.Printf("[BGCache] Refresh failed for key %q: %v. Serving stale data.", c.key, err)
            c.mu.Lock()
            c.refreshErr = err
            c.mu.Unlock()
            continue
        }

        c.value.Store(data)
        c.mu.Lock()
        c.refreshErr = nil
        c.mu.Unlock()
    }
}
```

## 6. Solution 3 — Redis Cluster with Read Replicas for Extreme Scale

For workloads where even the local in-process cache is insufficient — extremely large data that cannot be cached in every process's memory, or data that must be near-real-time with sub-second staleness — Redis Cluster with read replicas provides horizontal read scaling. In Redis Cluster, each slot is managed by a primary node with one or more replica nodes. Read commands can be directed to replicas (via `READONLY` mode or client-side replica preference), distributing the read load across multiple nodes:

```
              Redis Cluster Read Scaling — Hot Key Distribution
              ====================================================

  Standard Redis (single node):
  50 replicas × 10 req/s = 500 GET/s → all to one Redis node → SATURATION ❌

  Redis Cluster (3 primaries + 3 replicas, read-from-replica):
  trending_posts key → hashes to slot 8273 → Primary-2 (and Replica-2)

  50 replicas × 10 req/s = 500 GET/s:
  Client configured to prefer reads from replicas:
  → 250 GET/s to Primary-2   (50% of reads)
  → 250 GET/s to Replica-2   (50% of reads)
  Total per node: 250 GET/s → below saturation threshold ✅

  With 2 replicas (Primary + 2 Replicas):
  → 167 GET/s per node ← well distributed ✅

  Trade-off: replication lag means replica may serve slightly stale data.
  Replication lag: typically 1-5ms (acceptable for most use cases).

  Implementation in Go (redis/go-redis v9):
```

```go
// redis_cluster.go — Read from replicas for hot key read scaling
package cache

import (
    "context"

    "github.com/redis/go-redis/v9"
)

func NewClusterClient(addrs []string) *redis.ClusterClient {
    return redis.NewClusterClient(&redis.ClusterOptions{
        Addrs: addrs, // ["redis-1:6379", "redis-2:6379", "redis-3:6379"]

        // RouteRandomly: distribute reads across all nodes (primaries and replicas).
        // Each GET is sent to a random node in the cluster, including replicas. ✅
        RouteRandomly: true,

        // Alternatively: RouteByLatency routes to the lowest-latency node.
        // RouteByLatency: true,

        // Pool configuration per node:
        PoolSize:        10,
        MinIdleConns:    3,
        ConnMaxLifetime: 30 * time.Minute,
    })
}

// ReadHotKey reads a hot key, routing to a random cluster node (may be replica).
// Acceptable for read-heavy keys where slight staleness (replication lag) is tolerable.
func ReadHotKey(ctx context.Context, client *redis.ClusterClient, key string) (string, error) {
    // With RouteRandomly=true, this GET may go to a replica.
    // Replicas are read-only, so WRITE commands must still go to primaries.
    return client.Get(ctx, key).Result()
}
```

## 7. The Cache Stampede — Why TTL Jitter Is Not Optional

The cache stampede (also called thundering herd on cache miss) is a secondary problem that emerges when the local in-process cache is implemented without TTL jitter. If all fifty API instances start simultaneously (a common scenario after a deployment) and all set the same fixed TTL for `trending_posts`, they will all expire at approximately the same time — and all fifty will simultaneously attempt to refresh from Redis. The hot key problem returns briefly at full intensity every TTL interval, in a predictable burst:

```
              Cache Stampede — Fixed TTL vs Jittered TTL
              ==============================================

  50 instances deployed simultaneously at t=0.
  All cache "trending_posts" with TTL = exactly 5.000 seconds.

  t=0.000s: Deployment. All 50 instances: cache miss → all GET trending_posts
            50 simultaneous Redis requests. Hot key spike. ⚠️

  t=5.000s: All 50 instances: TTL expires simultaneously.
            All 50: cache miss → all GET trending_posts simultaneously.
            50 simultaneous Redis requests. Stampede. ❌
            Redis: 50× normal load for ~200ms.

  t=10.000s: Exact same pattern. Every 5 seconds. Predictable spike. ❌

  WITH TTL JITTER (baseTTL=5s, ±10% = 4.5s to 5.5s, random per instance):

  t=0.000s: Deployment. First request: cache miss per instance.
            Staggered by request timing → not all simultaneous. ⚠️ (once)

  t=4.5s to 5.5s: Instances expire individually, spread over 1 second.
                  Each instance: 1 Redis GET at its own individual expiry time.
                  Redis: 50 requests spread over 1 second = 50 req/s. Normal load. ✅

  No spike. No stampede. Load is naturally distributed over the jitter window. ✅

  Stagger calculation:
  50 instances × (max 1 GET / 5s per instance) = 10 GET/s average (even) ✅
  With jitter, peak is: 50 instances / 1 second jitter window = 50 GET/s peak
  vs stampede: 50 GET/s for 200ms. Similar peak but no synchronization. ✅
```

## 9. The Decision Matrix — Which Solution to Apply

```
              Hot Key Mitigation Strategy — Selection Guide
              ===============================================

  Data Characteristic            Recommended Solution
  ─────────────────────────────────────────────────────────────────────
  Staleness tolerance: 1-60s    Local in-process cache (TTL + jitter)
  Changes: infrequently          Most common solution. Simplest. ✅
  Example: trending posts,
           feature flags, config

  Staleness tolerance: < 1s     Background refresh (proactive, no miss)
  Must minimize cache misses     All reads served from in-process cache.
  Example: live leaderboards     Redis fetched on schedule, not on demand. ✅

  Data too large for process     Redis Cluster + read replicas
  memory (MBs per key)           Horizontal Redis read scaling.
  Staleness: sub-second          Higher operational complexity. ✅
  Example: large product catalog

  Staleness: zero                No local cache. Optimize Redis directly:
  Financial, inventory counts    - Pipeline commands to reduce round trips
  Correctness > performance      - Use Redis pipelining or MULTI/EXEC
                                 - Vertical scale Redis (faster hardware) ✅

  Write-heavy hot keys           Lua scripting (atomic read-modify-write)
  (counters, real-time scores)   Redis sorted sets for leaderboards
                                 Redis INCRBYFLOAT for score accumulation ✅

  ─────────────────────────────────────────────────────────────────────
  Key question: "How stale can this data be?"
  The answer determines your caching strategy. If the answer is "not at
  all," you have a design problem — reconsider whether the key needs to
  be global, or whether the data model can be restructured to shard it.
```

## 10. The Golden Rule

> A cache can have its own bottleneck. Redis is extraordinarily fast as a standalone server, but it processes commands in a single thread — every `GET`, `SET`, `INCR`, and `EXPIRE` executes sequentially. A single key accessed at sufficient rate can saturate Redis's command processing thread, causing latency degradation for every other operation on the server regardless of how unrelated they are. This is the hot key problem: not a data problem, not a Redis bug, but a serialization bottleneck caused by a single point of concentrated access. The solution is a second cache layer — a local in-process cache inside each API instance with a short TTL. With fifty replicas each caching a key for five seconds, the Redis request rate drops from fifty times ten requests per second to ten requests per second total: a 98% reduction. Two implementation details are essential: first, randomize the TTL by ±10% (jitter) to prevent all instances from expiring and stampeding Redis simultaneously; second, protect against concurrent cache misses within a single instance using a single-flight pattern — multiple goroutines waiting for the same cache miss should trigger only one Redis fetch, not one per goroutine. The local cache layer accepts a trade-off: data may be up to TTL seconds stale. This is acceptable for trending content, leaderboards, feature flags, and configuration. It is not acceptable for financial balances or inventory counts. The design question is always: "how stale can this data be?" The answer determines whether a local cache is appropriate, and if so, what TTL is safe.

Caches can be bottlenecks too. The fix for a hot cache is another cache, closer to the consumer.
