# Go GC Thinks It Has the Whole Host RAM

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The New Employee Who Didn't Read the Budget Memo

A department in a large company has been allocated a quarterly budget of ten thousand dollars. The budget memo was sent to the department head, but a new employee — eager, capable, and entirely well-intentioned — never received a copy. The new employee begins making purchasing decisions on the department's behalf, each one individually reasonable. They order equipment, book conference rooms, commission reports. Each purchase looks prudent in isolation. But because the employee has no knowledge of the department's actual budget constraint, they have been spending based on their mental model of "what a department this size probably has to spend" — which, in a company this large, might be a hundred thousand dollars. By the end of the month, the department has spent sixty thousand dollars against a ten thousand dollar budget. The finance department freezes the account. All further operations halt.

The employee was not reckless. They were not ignoring the budget deliberately. They simply were never told what the budget was, and they operated on an incorrect assumption about its size. The department head's mistake was not failing to constrain the employee's judgment — it was failing to communicate the actual constraint.

This is precisely the Go runtime's situation in a containerized environment without explicit memory limit configuration. The Go garbage collector — the component responsible for deciding when to reclaim heap memory — needs to know how much memory is available to the process in order to make informed decisions about when to trigger a collection cycle. It obtains this information by reading `/proc/meminfo`, a virtual file in the Linux kernel that reports total and available system memory. In a container running on a 64 GB server, `/proc/meminfo` reports 64 GB — because it reflects the host's physical memory, not the container's cgroup memory limit. The Go runtime sees 64 GB, configures its GC to allow the heap to grow to many gigabytes before triggering a collection, and your container quietly accumulates memory until the cgroup hard limit is reached and the kernel OOM-kills the process. The container never ran out of work to do. The GC was never given the information it needed to prevent the situation.

## 2. How the Go Garbage Collector Works — The GOGC Parameter and Heap Target

The Go garbage collector is a concurrent, tri-color mark-and-sweep collector. Understanding its triggering behavior requires understanding one fundamental parameter: **GOGC**. The `GOGC` environment variable (or its equivalent `runtime/debug.SetGCPercent()`) controls when the garbage collector triggers relative to the current heap occupancy. The default value is 100.

`GOGC=100` means: trigger a garbage collection cycle when the heap has grown to **100% above** its size at the end of the previous collection cycle. In other words, the GC triggers when the live heap has doubled. If the previous GC cycle ended with 50 MB of live heap, the next cycle is triggered when the heap reaches 100 MB. If the previous cycle ended with 200 MB of live heap, the next cycle triggers at 400 MB.

This doubling behavior is intentional and beneficial: it amortizes the cost of garbage collection across a larger amount of allocation work, reducing the frequency of GC cycles and thus the CPU overhead of collection. For a process with abundant memory, allowing the heap to double before collecting is an excellent trade-off. For a process constrained to a specific memory limit, it is a trap.

```
              GOGC=100 Heap Target Calculation — Without GOMEMLIMIT
              ========================================================

  Scenario: Go service in a container with memory limit = 512 MB
            Host machine: 64 GB RAM
            Go version: 1.18 or earlier (no GOMEMLIMIT)

  What the Go runtime reads at startup:
  cat /proc/meminfo | grep MemTotal
  MemTotal: 65536000 kB  ← 64 GB (host RAM, not container limit) ❌

  GC target calculation (simplified):
  ├── Previous GC ended with live heap: 64 MB (typical Go service startup)
  ├── GOGC = 100: next GC triggers at 64 MB × (1 + 100/100) = 128 MB
  ├── GC runs at 128 MB. Live heap after: 70 MB.
  ├── Next target: 70 × 2 = 140 MB.
  ├── GC runs at 140 MB. Live heap after: 75 MB.
  ├── Next target: 75 × 2 = 150 MB.
  ├── Load increases. Requests handling more data. Live heap grows faster.
  ├── GC runs at 200 MB. Live heap after: 120 MB.
  ├── Next target: 120 × 2 = 240 MB.
  ├── GC runs at 400 MB. Live heap after: 210 MB.
  ├── Next target: 210 × 2 = 420 MB.
  ├── Container memory limit: 512 MB ← approaching ⚠️
  ├── GC runs at 420 MB. Live heap after: 250 MB. (successful)
  ├── Next target: 250 × 2 = 500 MB. ← still within limit (barely)
  └── Next spike: live heap 260 MB → target 520 MB → container limit 512 MB ← BREACH
      Kernel OOM kills container. Exit 137. OOMKilled: true.

  Root cause: GC target (520 MB) exceeded container limit (512 MB)
  before GC could trigger and reduce the heap.
  The Go runtime had no knowledge of the 512 MB container limit.
  It was operating as if 64 GB were available and scheduled GC accordingly.

  What the engineer sees:
  ├── Container memory: 400 MB (reported by docker stats)
  ├── GC activity: infrequent (running on a 64 GB mental model)
  ├── Container exits suddenly with code 137
  ├── docker inspect: OOMKilled: true
  └── Confusion: "The service was only using 400 MB, why was it OOM killed?"
      Answer: the GC target crossed 512 MB before the collection triggered.
```

The confusion in the final bullet point is characteristic of this failure mode. `docker stats` shows memory usage of 400 MB — well within the 512 MB limit. The engineer expects the OOM kill to only occur if usage reached 512 MB, and it never appeared to reach that in the monitoring dashboards. What the dashboards showed was the heap size between GC cycles. What the kernel enforced was the instantaneous allocation crossing the cgroup limit — which occurred at the moment the Go runtime attempted to grow the heap toward its 520 MB target, even if it had not yet reached that target size at the last monitoring sample.

## 3. The `/proc/meminfo` Visibility Problem — What the Container Kernel Reports

The fundamental technical issue is that the Linux kernel's `/proc/meminfo` file was designed for a pre-container world where the process asking about available memory was entitled to know about all of the system's memory. When containers were introduced, `/proc/meminfo` was not updated to reflect cgroup memory limits — it continued to report host-level memory. A process inside a container with a 512 MB memory limit reads `/proc/meminfo` and sees the host's total physical RAM, because `/proc/meminfo` is a window into the host kernel's memory accounting, not into the container's cgroup accounting.

This behavior was changed in Linux kernel 4.6 with the introduction of cgroup v2 and, for containers specifically, the introduction of a virtualized `/proc/meminfo` in some distributions. However, many production systems ran on kernels and distributions where this virtualization was not present or not enabled, meaning Go runtimes before Go 1.19 universally read incorrect memory information in containerized deployments.

```
              /proc/meminfo — What the Container Process Reads
              ==================================================

  Host: 64 GB RAM
  Container: memory limit 512 MB (enforced by cgroup v1)

  Inside the container, before Go 1.19 workaround:
  $ cat /proc/meminfo
  MemTotal:       65536000 kB    ← 64 GB (HOST total, not container limit) ❌
  MemFree:        41943040 kB    ← Free on host
  MemAvailable:   52428800 kB    ← Available on host
  Buffers:           65536 kB
  Cached:          8388608 kB
  ...

  What it SHOULD show (container-aware):
  MemTotal:          524288 kB    ← 512 MB (container limit) ✅
  MemFree:           131072 kB    ← Remaining within container limit
  ...

  Cgroup v2 + kernel ≥ 5.4 (modern distributions):
  /proc/meminfo may be virtualized to show container-scoped values ✅
  BUT: Go's runtime historically read from /proc/meminfo, which varied.
  GOMEMLIMIT is explicit and reliable regardless of kernel version. ✅

  Other runtimes affected by the same problem:
  ├── JVM (Java): reads /proc/meminfo for heap sizing until JDK 8u191
  │   Fix: -XX:+UseContainerSupport (default in JDK 10+)
  │         -XX:MaxRAMPercentage=75.0
  ├── Node.js: V8 heap limit historically set from OS memory query
  │   Fix: --max-old-space-size=<MB>
  ├── Ruby MRI: GC parameters tuned from system memory
  │   Fix: RUBY_GC_HEAP_GROWTH_MAX_SLOTS, MALLOC_ARENA_MAX
  └── Python: less affected (reference counting GC, different behavior)
```

## 4. The GOMEMLIMIT Solution — Go 1.19+

Go 1.19 introduced `GOMEMLIMIT` — an environment variable that sets a **soft memory limit** for the Go runtime. When `GOMEMLIMIT` is set, the GC transitions from the GOGC-based doubling strategy to a more aggressive collection mode when the heap approaches the specified limit. The GC runs more frequently to keep the heap below the limit, trading increased CPU usage for reduced memory footprint. If allocation pressure is so high that the GC cannot keep up even with aggressive collection, the runtime allows the heap to slightly exceed the limit before falling back to GOGC-based behavior — it is a soft limit, not a hard one, giving the application a chance to handle allocation pressure gracefully rather than being killed.

The recommended value for `GOMEMLIMIT` is **90% of the container's memory limit**. This 10% margin accounts for non-heap memory allocations that the Go runtime makes — goroutine stacks, the Go runtime's own data structures, cgo-allocated memory, and OS-level overhead. Setting GOMEMLIMIT to exactly the container limit would mean the Go heap alone could fill the entire limit, leaving no headroom for these additional allocations, and the cgroup would still kill the process when the non-heap allocations pushed total RSS over the limit.

```
              GOMEMLIMIT — Heap Management with Awareness of Container Limit
              =================================================================

  Same scenario: Go service, container limit 512 MB, host 64 GB.
  GOMEMLIMIT=460MiB (90% of 512 MB)

  GC target calculation with GOMEMLIMIT:
  ├── Live heap: 64 MB. GOGC target: 128 MB. GOMEMLIMIT: 460 MB.
  │   GC triggers at: min(GOGC_target, approaching_GOMEMLIMIT) = 128 MB ✅
  ├── Live heap grows to 200 MB. GOGC target: 400 MB. GOMEMLIMIT: 460 MB.
  │   GC triggers at: 400 MB (still within GOMEMLIMIT headroom) ✅
  ├── Live heap 250 MB. GOGC target: 500 MB (exceeds GOMEMLIMIT!).
  │   GOMEMLIMIT kicks in: GC becomes aggressive BEFORE heap reaches 460 MB.
  │   GC frequency increases. Collections happen earlier than GOGC would dictate.
  │   Heap kept below 460 MB through frequent collection. ✅
  ├── Memory pressure extremely high (leak scenario):
  │   GC runs as fast as possible. Cannot keep heap below 460 MB.
  │   GOMEMLIMIT allows brief exceedance (soft limit behavior).
  │   Application logs GC pressure. Goroutines may be slowed (back-pressure). ✅
  │   Total RSS: ~480 MB (heap 460 MB + runtime overhead ~20 MB)
  │   Container limit: 512 MB. No OOM kill. Application degrades gracefully. ✅
  └── At true pathological leak: heap grows beyond all GC effort.
      Total RSS approaches 512 MB limit.
      Container OOMKilled. Exit 137. ✅ But only under genuine load, not prematurely.

  Comparison: with GOMEMLIMIT vs without

  Without GOMEMLIMIT (Go ≤1.18):
  ├── GC sees 64 GB available. Schedules lazily.
  ├── At moderate load: heap reaches 520 MB before GC triggers.
  ├── 520 MB > 512 MB limit → OOMKilled. ❌
  └── Container restarts. Appears to be random crash.

  With GOMEMLIMIT=460MiB (Go ≥1.19):
  ├── GC sees 460 MB as the target ceiling. Collects more aggressively.
  ├── At same moderate load: heap kept below 460 MB through frequent GC.
  ├── Total RSS: ~480 MB < 512 MB limit → stable operation. ✅
  └── Under true pathological leak: graceful degradation before OOMKill.
```

## 5. Implementing GOMEMLIMIT — All Three Methods

**Method 1 — Environment Variable (Simplest, Recommended for Most Cases)**

```yaml
# docker-compose.yml
services:
  api:
    build: .
    environment:
      # GOMEMLIMIT: set to 90% of the container's memory limit.
      # Container limit: 512m (set in deploy.resources.limits.memory below)
      # GOMEMLIMIT: 512 × 0.9 = 460.8 → use 460MiB
      # Supported units: B, KiB, MiB, GiB, TiB (Go 1.19+ accepts these)
      GOMEMLIMIT: "460MiB"

      # GOGC can be left at default (100) with GOMEMLIMIT set.
      # Or raise GOGC to reduce GC frequency under low memory pressure
      # (GOMEMLIMIT will override when approaching the limit):
      GOGC: "100"

    deploy:
      resources:
        limits:
          memory: 512m     # ← Container hard limit (cgroup enforcement)
          cpus: "1.0"
        reservations:
          memory: 256m
          cpus: "0.25"
    restart: unless-stopped
```

```dockerfile
# Dockerfile — Set GOMEMLIMIT as a build-time default
# (can still be overridden at runtime via environment)
FROM golang:1.23.0-alpine3.19@sha256:... AS builder
WORKDIR /build
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app ./cmd/api

FROM gcr.io/distroless/static:nonroot@sha256:...
COPY --from=builder /app /app

# Set as image default — will be overridden by Compose environment: block
# if a different value is needed per deployment.
ENV GOMEMLIMIT=460MiB
ENV GOGC=100

USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

**Method 2 — `runtime/debug.SetMemoryLimit()` (Programmatic, Adaptive)**

The programmatic approach allows the application to read the cgroup memory limit at runtime and configure GOMEMLIMIT automatically, making the Dockerfile and Compose configuration self-documenting and removing the need to manually calculate 90% of each deployment's memory limit:

```go
// main.go — Adaptive GOMEMLIMIT from cgroup at startup
package main

import (
    "bufio"
    "fmt"
    "log"
    "math"
    "os"
    "runtime/debug"
    "strconv"
    "strings"
)

// configurGCMemoryLimit reads the container's cgroup memory limit and sets
// GOMEMLIMIT to 90% of that value, making the Go GC aware of the container
// boundary without requiring manual GOMEMLIMIT configuration per deployment.
func configureGCMemoryLimit() {
    limit, err := readCgroupMemoryLimit()
    if err != nil {
        log.Printf("[GC] Could not read cgroup memory limit: %v. Using default GC behavior.", err)
        return
    }

    // "max" means no limit is set in the cgroup (unlimited container)
    if limit <= 0 {
        log.Printf("[GC] No cgroup memory limit detected (unlimited container). Using default GC behavior.")
        return
    }

    // Set GOMEMLIMIT to 90% of the cgroup limit.
    // The 10% margin covers:
    // - Go runtime overhead (goroutine stacks, runtime structs)
    // - cgo allocations (if any)
    // - OS-level memory overhead
    goMemLimit := int64(math.Floor(float64(limit) * 0.90))
    previous := debug.SetMemoryLimit(goMemLimit)

    log.Printf(
        "[GC] Cgroup memory limit: %d MB. GOMEMLIMIT set to: %d MB (90%%). Previous: %d.",
        limit/(1024*1024),
        goMemLimit/(1024*1024),
        previous,
    )
}

// readCgroupMemoryLimit reads the memory limit from the cgroup filesystem.
// Supports both cgroup v1 and cgroup v2.
func readCgroupMemoryLimit() (int64, error) {
    // cgroup v2 (modern Linux: Ubuntu 22.04+, RHEL 9+, Debian 11+)
    if data, err := os.ReadFile("/sys/fs/cgroup/memory.max"); err == nil {
        value := strings.TrimSpace(string(data))
        if value == "max" {
            return -1, nil // No limit
        }
        return strconv.ParseInt(value, 10, 64)
    }

    // cgroup v1 (older Linux: Ubuntu 20.04, many production systems)
    if data, err := os.ReadFile("/sys/fs/cgroup/memory/memory.limit_in_bytes"); err == nil {
        value := strings.TrimSpace(string(data))
        limit, err := strconv.ParseInt(value, 10, 64)
        if err != nil {
            return 0, err
        }
        // cgroup v1 reports 9223372036854771712 (~9.2 EB) when no limit is set
        const noLimit = int64(9223372036854771712)
        if limit >= noLimit {
            return -1, nil // No limit
        }
        return limit, nil
    }

    return 0, fmt.Errorf("cgroup memory limit file not found (neither v1 nor v2)")
}

func main() {
    // First thing on startup: configure GC before any significant allocations
    configureGCMemoryLimit()

    // ... rest of application startup
}
```

**Method 3 — The `automaxprocs` Pattern Extended to Memory**

The `uber-go/automaxprocs` package automatically sets `GOMAXPROCS` (Go's parallelism setting) to match the container's cgroup CPU quota. A similar pattern exists for memory through the `KimMachineGun/go-memlimit` package, which reads the cgroup limit and sets `GOMEMLIMIT` automatically:

```go
// main.go — Using go-memlimit for automatic GOMEMLIMIT configuration
import (
    _ "github.com/KimMachineGun/automemlimit" // Auto-sets GOMEMLIMIT from cgroup
    _ "go.uber.org/automaxprocs"              // Auto-sets GOMAXPROCS from cgroup CPU quota
)

// Both packages use init() functions — importing them with blank identifier
// triggers their initialization logic automatically before main() runs.
// No additional code required. ✅

func main() {
    // GOMEMLIMIT is already configured to 90% of cgroup limit by automemlimit.
    // GOMAXPROCS is already configured to cgroup CPU quota by automaxprocs.
    // Application starts with correct resource awareness. ✅
}
```

## 6. GOMAXPROCS — The CPU Quota Blindness Problem

The same category of problem affects CPU allocation. Go's `GOMAXPROCS` setting controls the number of OS threads that can execute Go goroutines simultaneously. By default, Go sets `GOMAXPROCS` to the number of logical CPU cores on the host — which it reads from `/proc/cpuinfo`. On a 32-core host with a container CPU limit of `cpus: "2.0"`, Go launches 32 threads but the container is throttled to 2 CPU-equivalents by the cgroup. The result is 32 threads competing for 2 CPU slots, producing excessive context switching overhead and reduced throughput.

```
              GOMAXPROCS Without Container Awareness
              ========================================

  Host: 32 CPU cores
  Container: cpus: "2.0" (cgroup quota: 200ms CPU per 100ms window)

  Without automaxprocs:
  GOMAXPROCS = 32 (reads host /proc/cpuinfo)
  Go creates 32 OS threads.
  All 32 threads compete for 2 CPU-equivalents of actual compute time.
  Scheduler: massive context switching between 32 threads on 2 effective cores.
  CPU efficiency: poor. Goroutine scheduling overhead: high.
  Observed performance: worse than a correctly configured 2-core setup. ❌

  With automaxprocs (import _ "go.uber.org/automaxprocs"):
  Reads: /sys/fs/cgroup/cpu.max (cgroup v2) or cpu quota files (cgroup v1)
  Calculates: 200ms quota / 100ms period = 2 effective cores.
  Sets: GOMAXPROCS = 2 ✅
  Go creates 2 OS threads for goroutine execution.
  No excessive context switching. Scheduler operates efficiently.
  CPU efficiency: optimal for the allocated quota. ✅
```

## 7. The JVM Equivalent — UseContainerSupport

Java applications in containers suffered from the same problem before JDK 8 Update 191. The JVM reads `/proc/meminfo` to determine default heap sizing (`-Xmx` defaults to 25% of total system memory) and reads `/proc/cpuinfo` to set the default GC thread count and JIT compilation parallelism. On a 64 GB host with a 512 MB container limit, the JVM would configure a maximum heap of 16 GB — far exceeding the container limit and guaranteeing an OOMKill during heap growth.

The fix was introduced as `UseContainerSupport` — a JVM flag that enables container-aware resource detection by reading cgroup limits instead of `/proc/meminfo`. It has been enabled by default since JDK 10 (and backported to JDK 8u191), but it requires verification because older base images or specific JVM distributions may not have it enabled:

```dockerfile
# Dockerfile — JVM with explicit container-aware memory configuration

FROM eclipse-temurin:21-jre-alpine@sha256:...

# UseContainerSupport: enabled by default in JDK 10+.
# Explicit inclusion ensures correctness if using JDK 8 backports.
# MaxRAMPercentage: set JVM max heap to 75% of container limit.
# (25% headroom for JVM metaspace, direct memory, native memory, OS)
ENV JAVA_OPTS="-XX:+UseContainerSupport \
               -XX:MaxRAMPercentage=75.0 \
               -XX:InitialRAMPercentage=50.0 \
               -XX:MinRAMPercentage=25.0"

COPY app.jar /app/app.jar

ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar /app/app.jar"]
```

```yaml
# docker-compose.yml — JVM service with correct memory limit and JVM flags
services:
  java-api:
    build: .
    environment:
      # 75% of 1GB container limit = 768 MB max heap
      JAVA_OPTS: >-
        -XX:+UseContainerSupport
        -XX:MaxRAMPercentage=75.0
        -Djava.security.egd=file:/dev/./urandom
    deploy:
      resources:
        limits:
          memory: 1g     # JVM max heap: 768 MB. Remaining 256 MB: metaspace + overhead.
          cpus: "2.0"
        reservations:
          memory: 512m
          cpus: "0.5"
```

## 8. Observing GC Behavior — Verifying the Fix Works

After applying GOMEMLIMIT or JVM container support, the most important validation is to observe GC behavior under realistic load and confirm that the runtime is collecting before the cgroup limit is reached:

```bash
# ── Go: Enable GC tracing to observe collection frequency ────────────────────
# Add GODEBUG=gctrace=1 to the container environment:
docker run -e GODEBUG=gctrace=1 -e GOMEMLIMIT=460MiB \
    --memory=512m my-go-service:latest

# GC trace output format:
# gc N @Xs: M%: P+Q+R ms clock, A+B+C ms cpu, D->E->F MB, G MB goal, I P
# gc 1 @0.014s: 0%: 0.012+0.45+0.002 ms clock, 0.1+0/0.4+0.0 ms cpu, 4->4->2 MB, 5 MB goal

# Key fields:
# D->E->F MB: heap size before GC → heap size after marking → heap size after GC
# G MB goal:  what GOMEMLIMIT + GOGC calculate as the next GC trigger point
# Healthy:    goal should be < GOMEMLIMIT (460 MiB)
# Problem:    goal > GOMEMLIMIT → GC not triggered before limit breach

# ── docker stats: watch memory approach limit without crossing it ─────────────
docker stats --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}" api_container
# MEM USAGE / LIMIT should stabilize below 90% (GOMEMLIMIT doing its job)
# If MEM % approaches 100% consistently: GOMEMLIMIT may be set too high

# ── Check if container was OOMKilled after a restart ─────────────────────────
docker inspect api_container --format='OOMKilled: {{.State.OOMKilled}}'
# false → GOMEMLIMIT is working correctly ✅
# true  → GOMEMLIMIT not set or set too high → container limit still being breached ❌

# ── Go runtime metrics via expvar or Prometheus ──────────────────────────────
# Add to your Go app for runtime metric exposure:
import (
    "expvar"
    "net/http"
    _ "net/http/pprof"  // Also enables profiling endpoints
    "runtime"
)

func publishRuntimeMetrics() {
    expvar.Publish("go_memstats", expvar.Func(func() interface{} {
        var m runtime.MemStats
        runtime.ReadMemStats(&m)
        return map[string]uint64{
            "HeapInuse":    m.HeapInuse,    // Heap bytes in use
            "HeapIdle":     m.HeapIdle,     // Heap bytes idle (returned to OS)
            "HeapSys":      m.HeapSys,      // Heap bytes obtained from OS
            "HeapReleased": m.HeapReleased, // Heap bytes released to OS
            "NumGC":        uint64(m.NumGC),// Number of GC cycles
            "PauseTotalNs": m.PauseTotalNs, // Total GC pause time
        }
    }))
}
// Expose at: GET /debug/vars
// HeapInuse < GOMEMLIMIT → GC is keeping the heap in check ✅
```

## 10. The Golden Rule

> Garbage-collected language runtimes calibrate their collection behavior against the amount of memory they believe is available. They obtain this information by querying the operating system — typically through `/proc/meminfo` on Linux. In a containerized environment, the operating system reports the host's total physical memory, not the container's cgroup memory limit, because `/proc/meminfo` was designed before containers existed and predates the cgroup memory accounting system. The result is that a Go application configured with a 512 MB container limit may have a GC that behaves as if it has 64 GB available, allowing the heap to grow to many hundreds of megabytes before triggering a collection — crossing the container's cgroup limit and triggering an OOMKill before the GC ever had a chance to intervene. The fix for Go 1.19+ is `GOMEMLIMIT`, set to 90% of the container memory limit to leave headroom for runtime and OS overhead. The fix for the JVM is `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0`. The fix for Node.js is `--max-old-space-size`. For Go specifically, the `automemlimit` package reads the cgroup limit at startup and configures GOMEMLIMIT automatically, making the runtime correctly container-aware with a single blank import. Always pair GOMEMLIMIT with `automaxprocs` — both the memory and the CPU visibility problems affect Go's runtime concurrently. The Go runtime is not broken; it was simply never told about the container. Tell it.

The GC cannot collect what it does not know it is spending. Give your runtime a budget, and it will respect it.
