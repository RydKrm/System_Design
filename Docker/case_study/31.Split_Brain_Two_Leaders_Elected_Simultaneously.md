# Split Brain — Two Leaders Elected Simultaneously

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Ship With Two Captains

A cargo ship crosses the ocean with a captain and two officers. The captain is the authority: they decide the course, authorize cargo releases, and sign manifests. If the captain becomes incapacitated, Officer A takes command. Officer B is the backup to Officer A.

During a storm, the captain is briefly knocked unconscious — for about thirty seconds. The communications between the bridge and the lower decks are disrupted by the storm's electrical interference. Officer A, on the bridge and unable to reach the captain on the radio, concludes that the captain is incapacitated and declares himself acting captain. Simultaneously, Officer B in the engine room, unable to reach either the captain or Officer A by radio, also concludes that both above her are incapacitated — and declares herself acting captain.

For the next three minutes, both officers are issuing independent orders as captain. Officer A orders the ship to turn ten degrees north to avoid the storm. Officer B orders the ship to maintain course south to reach the port. The helmsman executes whichever command arrives at his station first. The purser receives cargo release authorizations from both "captains" — for different cargo, at different prices, to different buyers. The cargo manifest becomes inconsistent. When the actual captain recovers and the communications are restored, there is no clean way to determine which orders were authoritative, which cargo releases were legitimate, or what the ship's actual intended course was.

The three minutes of dual captaincy have produced data corruption that the ship cannot resolve on its own. Manual reconciliation — determining which decisions were made by which "captain," which should be honored and which should be revoked — will take far longer than the original outage.

This is split-brain: the condition in a distributed system where a network partition causes multiple nodes to simultaneously believe they hold a role that should be held by only one node at a time. The partition heals. The data does not.

## 2. The Physics of Network Partitions — Why This Is Inevitable

A network partition is a period during which some nodes in a distributed system cannot communicate with other nodes. From each node's perspective, the nodes it cannot reach appear to have failed. Partitions happen not only in dramatic datacenter-wide outages — they happen constantly in subtle ways: a network switch restarting and dropping packets for 200ms, an overloaded VM hypervisor that pauses network I/O for 500ms during a CPU spike, an AWS Availability Zone experiencing elevated packet loss, a Docker container that is briefly frozen by the OOM killer before being restarted.

The fundamental challenge is that in a distributed system, a node that has lost communication with another node cannot distinguish between two scenarios: the other node is dead and truly gone, or the other node is alive but the network path between them is temporarily unavailable. Both scenarios produce the same observable symptom: no response to messages. This ambiguity is the root of split-brain.

```
              Network Partition — The Two Indistinguishable Scenarios
              ==========================================================

  3-node cluster: Node A (Primary), Node B (Follower), Node C (Follower)
  Network link A ↔ C develops transient packet loss (200ms window)

  Node A's perspective:            Node C's perspective:
  ─────────────────────────────    ─────────────────────────────
  Sends heartbeat to B: ✅         Sends heartbeat to A: ❌ (no response)
  Sends heartbeat to C: ❌ (lost)  Sends heartbeat to B: ✅
  C doesn't respond.               A doesn't respond.
  Conclusion: "C is dead"          Conclusion: "A is dead"
  Action: none (still primary)     Action: "I must become primary"
                                   C promotes itself to primary.

  Result: A thinks it is primary.  C thinks it is primary.
  Both are processing writes.      Both are processing writes.
  Database entries being written by A and C simultaneously.
  SPLIT BRAIN ACTIVE. ❌

  Timeline from partition to data corruption:
  ─────────────────────────────────────────────────────────────────────
  t=0ms:    Network link A↔C degrades (packet loss starts).
  t=100ms:  C's heartbeat timeout expires. C concludes A is dead.
  t=101ms:  C promotes itself. C begins accepting writes as primary.
  t=101ms:  A still active as primary. A accepts writes.
  t=200ms:  Network link A↔C recovers. Partition healed.
            Both A and C have accepted writes for 100ms.
            A's writes: ORDER #7841, #7842, #7843 (status: "shipped")
            C's writes: ORDER #7842 (status: "refunded") ← CONFLICT ❌
            ORDER #7842 exists in two states. Cannot determine truth.
  t=200ms+: A and C reconnect. Both claim to be primary.
            Whichever resolves the conflict last wins — arbitrary. ❌
            Data loss guaranteed: one set of writes will be discarded. ❌
```

The 100ms window sounds brief. But in a high-throughput system processing thousands of transactions per second, 100ms of dual-primary writes produces thousands of conflicting records. An e-commerce platform may process tens of orders in 100ms. A financial system may record hundreds of balance updates. A healthcare system may update dozens of patient records. Every one of those records is now in an ambiguous state.

## 3. The Custom Leader Election Anti-Pattern

The custom leader election implementation — the root cause of this failure — typically looks deceptively simple. A developer builds a system that needs exactly one active worker (a scheduler, a batch processor, a singleton service) and implements election logic that seems correct in a local test environment:

```go
// ❌ BROKEN: Custom leader election — DO NOT USE IN PRODUCTION

package election

import (
    "context"
    "database/sql"
    "log"
    "os"
    "time"
)

// BrokenLeaderElection attempts to elect a leader using a database row.
// This implementation has a fatal flaw: the gap between checking and claiming.
var hostname = os.Getenv("HOSTNAME")

func BrokenTryBecomeLeader(db *sql.DB) bool {
    tx, _ := db.Begin()
    defer tx.Rollback()

    var currentLeader string
    var lastHeartbeat time.Time

    err := tx.QueryRow(
        `SELECT leader_id, last_heartbeat FROM leader_election WHERE id = 1`,
    ).Scan(&currentLeader, &lastHeartbeat)

    // If the leader hasn't sent a heartbeat in 5 seconds, assume it's dead.
    leaderDead := err != nil || time.Since(lastHeartbeat) > 5*time.Second

    if leaderDead {
        // ← RACE CONDITION HERE: two nodes check simultaneously and both see
        //   the leader as dead. Both proceed to claim leadership.
        //   Without SELECT FOR UPDATE or atomic SETNX, both win. ❌

        _, err = tx.Exec(
            `UPDATE leader_election SET leader_id = $1, last_heartbeat = NOW() WHERE id = 1`,
            hostname,
        )
        if err != nil {
            return false
        }
        tx.Commit()
        log.Printf("[Election] %s became leader.", hostname)
        return true
    }

    tx.Rollback()
    return currentLeader == hostname
}
// Problems:
// 1. Check-then-act is not atomic → two nodes can both "win" the election.
// 2. No fencing token → old leader's writes accepted after new leader elected.
// 3. Clock drift: `time.Since(lastHeartbeat)` uses local clock, different per node.
// 4. The 5-second timeout is arbitrary → too long = slow failover, too short = false positives.
```

The `UPDATE` without a lock does not prevent concurrent updates. If two nodes execute this code within the same millisecond — which is exactly what happens during a network partition when both nodes simultaneously detect the "failure" of the same third node — both will see the leader as dead and both will succeed in updating the table. The database's `UPDATE` will execute sequentially, but both will return "1 row affected" because the second update sees a different value in `leader_id` but no condition prevents it from proceeding.

## 4. The Fencing Token Problem — Why Elect Alone Is Not Enough

Even a correctly implemented leader election that uses atomic primitives (Redis SETNX, PostgreSQL advisory locks, etcd) must address a secondary problem: **the fencing token**. Consider this scenario: Node A is elected leader. Node A begins a long-running write operation. Node A's process pauses — the Linux process scheduler preempts it, or the JVM's garbage collector runs a stop-the-world pause, or the container is briefly frozen by Docker. During Node A's pause, Node A misses its lease renewal heartbeat. The election mechanism correctly detects the missed heartbeat and elects Node B as the new leader. Node A resumes execution, unaware that it lost its leadership. Node A completes its write as the "old leader." Node B is also writing as the "new leader." Split brain again — at the write level, not the election level.

The fencing token solves this: every time leadership changes, the token (a monotonically increasing number) is incremented. All writes to shared storage must include the current fencing token. The storage system rejects writes with a token lower than the highest it has seen — meaning old leader writes are rejected even if they arrive after the new leader's writes:

```
              Fencing Token — Preventing Stale Leader Writes
              ==================================================

  t=0:   Node A elected leader. Fencing token: 42.
         All writes from Node A include: X-Fencing-Token: 42

  t=5s:  Node A pauses (GC stop-the-world: 8 seconds).
         Misses lease renewal heartbeat.

  t=6s:  Election detects missed heartbeat. Node B elected.
         Fencing token incremented to: 43.
         All writes from Node B include: X-Fencing-Token: 43

  t=13s: Node A resumes from GC pause. Unaware it lost leadership.
         Node A sends write: UPDATE orders SET status='shipped' WHERE id=9999
         With: X-Fencing-Token: 42

  Storage layer (database proxy / custom middleware):
         Sees write with token 42.
         Highest seen token: 43.
         42 < 43 → REJECT write. ✅
         Node A's stale write is rejected.
         Node B's writes with token 43: accepted. ✅

  Without fencing token:
         Node A's write: accepted (looks valid to DB).
         Node B's write: accepted (looks valid to DB).
         Order #9999: written twice with conflicting values. ❌
```

## 5. The Correct Implementations — Proven Distributed Primitives

**Implementation 1 — Redis SETNX with Fencing Token**

```go
// election/redis.go — Correct leader election using Redis

package election

import (
    "context"
    "fmt"
    "log"
    "os"
    "strconv"
    "time"

    "github.com/redis/go-redis/v9"
)

const (
    leaderKey    = "leader:election"
    fenceKey     = "leader:fencing-token"
    leaseDuration = 10 * time.Second
    renewInterval = 3 * time.Second  // Renew at 30% of lease duration
)

var nodeID = os.Getenv("HOSTNAME")

type RedisLeaderElection struct {
    client *redis.Client
}

// TryAcquireLeadership attempts to atomically acquire leadership.
// Returns (fencing_token, true) if elected, (0, false) if another node is leader.
//
// Uses SET key value NX PX milliseconds:
// NX = only set if key does NOT exist (atomic check-and-set)
// PX = expire after milliseconds (automatic release if node dies)
// This is atomic: no race condition between check and set. ✅
func (e *RedisLeaderElection) TryAcquireLeadership(ctx context.Context) (int64, bool, error) {
    // Atomic SET NX PX: either succeeds (we are leader) or fails (another node is leader).
    ok, err := e.client.SetNX(ctx, leaderKey, nodeID, leaseDuration).Result()
    if err != nil {
        return 0, false, fmt.Errorf("redis SetNX: %w", err)
    }
    if !ok {
        return 0, false, nil // Another node holds the lease
    }

    // Atomically increment the fencing token counter.
    // Every leadership acquisition increments this monotonically. ✅
    token, err := e.client.Incr(ctx, fenceKey).Result()
    if err != nil {
        // If we can't get a fencing token, relinquish leadership to be safe.
        e.client.Del(ctx, leaderKey)
        return 0, false, fmt.Errorf("incrementing fencing token: %w", err)
    }

    log.Printf("[Election] Node %s acquired leadership. Fencing token: %d", nodeID, token)
    return token, true, nil
}

// RenewLease extends the leader's lease. Must be called before lease expires.
// Returns false if we no longer hold the lease (another node took over). ✅
func (e *RedisLeaderElection) RenewLease(ctx context.Context) (bool, error) {
    // Lua script: atomic check-and-extend.
    // Only extend if WE still hold the key (value matches our nodeID).
    // Prevents extending a lease that was legitimately taken by a new leader. ✅
    script := redis.NewScript(`
        if redis.call("GET", KEYS[1]) == ARGV[1] then
            redis.call("PEXPIRE", KEYS[1], ARGV[2])
            return 1
        else
            return 0
        end
    `)

    result, err := script.Run(ctx, e.client, []string{leaderKey},
        nodeID,
        strconv.FormatInt(leaseDuration.Milliseconds(), 10),
    ).Int()
    if err != nil {
        return false, err
    }

    if result == 0 {
        log.Printf("[Election] Node %s lost leadership (lease taken by another node).", nodeID)
        return false, nil
    }
    return true, nil
}

// RunLeader continuously renews the lease and executes leaderFn while leader.
// When leadership is lost: exits cleanly. Caller should re-run election loop. ✅
func (e *RedisLeaderElection) RunLeader(ctx context.Context, fencingToken int64, leaderFn func(ctx context.Context, token int64)) {
    ticker := time.NewTicker(renewInterval)
    defer ticker.Stop()

    leaderCtx, cancel := context.WithCancel(ctx)
    defer cancel()

    // Run leader work in a separate goroutine.
    go leaderFn(leaderCtx, fencingToken)

    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            ok, err := e.RenewLease(ctx)
            if err != nil {
                log.Printf("[Election] Lease renewal error: %v. Stepping down.", err)
                cancel() // Signal leader goroutine to stop
                return
            }
            if !ok {
                log.Printf("[Election] Lease lost. Stepping down.")
                cancel()
                return
            }
        }
    }
}

// Complete election loop — runs continuously, re-elects when leadership is lost:
func ElectionLoop(ctx context.Context, client *redis.Client, leaderFn func(ctx context.Context, token int64)) {
    e := &RedisLeaderElection{client: client}

    for {
        select {
        case <-ctx.Done():
            return
        default:
        }

        token, elected, err := e.TryAcquireLeadership(ctx)
        if err != nil {
            log.Printf("[Election] Election attempt failed: %v. Retrying in 5s.", err)
            time.Sleep(5 * time.Second)
            continue
        }

        if !elected {
            // Another node is leader. Wait and retry.
            time.Sleep(renewInterval)
            continue
        }

        // We are leader. Run until we lose leadership or ctx is cancelled.
        e.RunLeader(ctx, token, leaderFn)
    }
}
```

**Implementation 2 — PostgreSQL Advisory Locks**

```go
// election/postgres.go — Leader election using PostgreSQL session advisory locks

package election

import (
    "context"
    "database/sql"
    "log"
    "time"
)

const (
    // Advisory lock key: unique integer for this election.
    // Use a hash of the service name to get a stable 64-bit integer.
    advisoryLockKey = 8675309 // unique per election namespace
)

type PostgresLeaderElection struct {
    db *sql.DB
}

// TryAcquireLeadership attempts to acquire a PostgreSQL session advisory lock.
// pg_try_advisory_lock: non-blocking. Returns true immediately if lock acquired.
// The lock is automatically released when the database session ends (connection dropped).
// This means a crashed node automatically releases leadership. ✅
func (e *PostgresLeaderElection) TryAcquireLeadership(ctx context.Context) (bool, error) {
    var acquired bool
    err := e.db.QueryRowContext(ctx,
        `SELECT pg_try_advisory_lock($1)`,
        advisoryLockKey,
    ).Scan(&acquired)
    if err != nil {
        return false, err
    }

    if acquired {
        log.Printf("[Election] PostgreSQL advisory lock acquired. This node is leader.")
    }
    return acquired, nil
}

// ReleaseLeadership explicitly releases the advisory lock.
// Called on clean shutdown. Otherwise: lock released automatically on disconnect. ✅
func (e *PostgresLeaderElection) ReleaseLeadership(ctx context.Context) error {
    _, err := e.db.ExecContext(ctx,
        `SELECT pg_advisory_unlock($1)`,
        advisoryLockKey,
    )
    return err
}

// KeepAlive maintains a long-lived transaction that holds the advisory lock.
// If this goroutine dies, the transaction rolls back, releasing the lock. ✅
func (e *PostgresLeaderElection) KeepAlive(ctx context.Context) error {
    // Hold a dedicated connection (not pool-managed) for the advisory lock.
    // Pool management might close and reopen the connection, releasing the lock.
    conn, err := e.db.Conn(ctx)
    if err != nil {
        return err
    }
    defer conn.Close()

    var acquired bool
    if err := conn.QueryRowContext(ctx,
        `SELECT pg_try_advisory_lock($1)`, advisoryLockKey,
    ).Scan(&acquired); err != nil || !acquired {
        return fmt.Errorf("could not acquire advisory lock")
    }

    // Block until context is cancelled (process shutdown or leadership lost).
    <-ctx.Done()

    // Explicitly release before the connection closes.
    conn.ExecContext(context.Background(), `SELECT pg_advisory_unlock($1)`, advisoryLockKey)
    return nil
}
```

## 6. The Split-Brain Failure Matrix — What Breaks, What Survives

Understanding which architectures are vulnerable to split-brain and which are immune helps in designing systems that degrade gracefully rather than catastrophically:

```
              Split-Brain Vulnerability Matrix
              ==================================

  Architecture                          Split-Brain Risk   Notes
  ──────────────────────────────────────────────────────────────────────
  Custom heartbeat-based election        CRITICAL ❌        Race between check-and-claim.
  (check DB, update if expired)                             Two nodes win simultaneously.

  Redis SETNX + TTL lease                LOW ✅             Atomic. Only one SET NX succeeds.
  (with fencing token)                                      TTL auto-releases on crash.
                                                            Vulnerable to Redis split-brain.

  PostgreSQL advisory lock               LOW ✅             Session-scoped. Auto-releases.
  (pg_try_advisory_lock)                                    Postgres must be HA for this to
                                                            be resilient to Postgres failure.

  etcd leader election                   VERY LOW ✅        Raft consensus. Requires quorum.
  (kubernetes/client-go or etcd client)                     Designed for exactly this problem.
                                                            Correct even under network partition.

  ZooKeeper leader election              VERY LOW ✅        Similar to etcd. ZAB consensus.
                                                            Ephemeral znodes auto-release. ✅

  Singleton Kubernetes pod               LOW ✅             K8s guarantees at-most-one pod
  (replicas: 1, no HPA)                                     running. PodDisruptionBudget for
                                                            safe evictions.

  Stateless replicas (no leader)         NONE ✅            Ideal. No election, no split-brain.
  All state in external store                               Design for this when possible.

  ──────────────────────────────────────────────────────────────────────
  Key principle: the election mechanism must itself be immune to split-brain.
  Redis SETNX is atomic per-node; Redis Sentinel adds HA.
  etcd is the gold standard: Raft consensus provides partition tolerance.
```

## 7. Designing for Idempotency — The Split-Brain Safety Net

Even with correct leader election, idempotent operations provide a critical safety net for the inevitable edge cases — redelivered messages, retried requests, or brief split-brain windows that occur before the election mechanism detects the partition. An idempotent operation is one where applying it multiple times produces the same result as applying it once:

```go
// idempotent_writer.go — Database writes with idempotency key protection

package writer

import (
    "context"
    "database/sql"
    "fmt"
)

// IdempotentOrderUpdate updates an order's status.
// Uses an idempotency key (fencing_token + order_id) to prevent duplicate writes.
// If the same operation is applied twice (same fencing token), the second is a no-op. ✅
func IdempotentOrderUpdate(ctx context.Context, db *sql.DB, orderID string, status string, fencingToken int64) error {
    // The fencing_token in the idempotency key ensures:
    // 1. Old leader writes (lower token) are rejected even without a proxy layer. ✅
    // 2. Duplicate writes from the same leader are no-ops. ✅
    idempotencyKey := fmt.Sprintf("order-status-%s-token-%d", orderID, fencingToken)

    _, err := db.ExecContext(ctx, `
        INSERT INTO idempotency_log (key, executed_at)
        VALUES ($1, NOW())
        ON CONFLICT (key) DO NOTHING
        RETURNING key
    `, idempotencyKey)

    if err != nil {
        return fmt.Errorf("idempotency check: %w", err)
    }

    // The INSERT above is a no-op if the key already exists.
    // Check if we actually inserted (operation is new) or skipped (already processed):
    var exists bool
    db.QueryRowContext(ctx,
        `SELECT EXISTS(SELECT 1 FROM idempotency_log WHERE key = $1)`,
        idempotencyKey,
    ).Scan(&exists)

    if !exists {
        // Already processed by this leader with this token. Skip. ✅
        return nil
    }

    // Proceed with the actual write:
    _, err = db.ExecContext(ctx,
        `UPDATE orders SET status = $1, updated_at = NOW() WHERE id = $2`,
        status, orderID,
    )
    return err
}
```

## 8. Detection and Recovery — What to Do When Split-Brain Occurs

Prevention is the primary goal, but detection and recovery procedures are essential because split-brain can occur in scenarios where even correct implementations have gaps — particularly during the initial deployment of a previously single-node system, or during a database failover that itself causes a brief election window:

```bash
# ── Detecting split-brain through data anomalies ────────────────────────────

# Check for duplicate primary key violations or conflicting record versions:
psql -U appuser myapp -c "
SELECT id, COUNT(*) as duplicate_count
FROM orders
GROUP BY id
HAVING COUNT(*) > 1;"
# Any results: duplicate writes. Split-brain likely occurred.

# Check for impossible state transitions:
psql -U appuser myapp -c "
SELECT id, status, updated_at, updated_by_node
FROM orders
WHERE (status = 'shipped' AND EXISTS (
    SELECT 1 FROM order_history
    WHERE order_id = orders.id AND status = 'refunded'
    AND changed_at > orders.updated_at
))
ORDER BY updated_at DESC
LIMIT 100;"
# Orders that are "shipped" but also have a "refunded" history entry after shipping:
# impossible under correct operation → split-brain artifact.

# ── Redis SETNX: check current leader ─────────────────────────────────────
redis-cli -a <password> GET leader:election
# Output: "api-replica-3"  ← only one node should ever be in this key
redis-cli -a <password> TTL leader:election
# Output: 7  ← seconds remaining on lease. Should always be positive.
# 0 or -1: lease expired and not renewed → leader died, new election pending.

# ── Check election log for concurrent acquisitions ─────────────────────────
docker compose logs | grep "\[Election\]" | grep "acquired leadership" | sort -k3
# Should show: at most one node per time window.
# Two "acquired leadership" lines within the same second = split-brain window.
```

## 9. The Golden Rule

> Split-brain is the condition where two nodes simultaneously believe they hold an exclusive role — leader, primary, master — that by definition only one node should hold. The data corruption it produces is not like a crash or a dropped request — it is silent, gradual, and discovered hours or days after the fact, when operations team members begin noticing records in impossible states. The root cause is always the same: a node that cannot communicate with other nodes cannot distinguish between "the other node is dead" and "I cannot reach the other node." Custom leader election implementations that check a shared record and update it if the current leader appears dead are not atomic — two nodes executing this pattern simultaneously both win, both become leaders, both write to the same data store, and the data diverges. The correct solution is to never implement custom leader election. Use primitives that are atomic at the distributed level: Redis `SET NX PX` for simple deployments (one atomic operation, one winner guaranteed), PostgreSQL session advisory locks for deployments where the database is already the single source of truth, or etcd/ZooKeeper for environments requiring strong partition tolerance with Raft or ZAB consensus. Always pair the election mechanism with a fencing token — a monotonically increasing counter that invalidates old leader writes even if they arrive after the new leader has started writing. Design all writes to shared state as idempotent operations: applying the same write twice should produce the same result as applying it once. Prevention handles 99% of cases. Idempotency handles the remaining 1%. Neither is optional in a system with more than one node.

Split-brain is worse than downtime. A system that is down can be restarted. A system that has two conflicting leaders produces data corruption that may take weeks to reconcile.
