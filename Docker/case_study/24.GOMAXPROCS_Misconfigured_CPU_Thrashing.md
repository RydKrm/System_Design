# GOMAXPROCS Misconfigured — CPU Thrashing

### A Senior Engineer's Deep Dive for the Curious Intern

## 1. Setting the Scene — The Kitchen With Too Many Cooks and Two Stoves

Picture a restaurant kitchen with two stove burners available for cooking. The kitchen manager, reading from a staffing manual that was written for a much larger establishment, assigns sixty-four line cooks to the kitchen simultaneously. Each cook is fully trained, capable, and eager to work. But there are only two burners. Every cook who wants to prepare a dish must wait for a burner to become available. Cooks elbow each other out of the way. Time is spent negotiating access to the burners rather than actually cooking. A cook who finally gets to a burner barely begins their preparation before another cook insists on their turn. The coordinating overhead — the negotiation, the waiting, the handoff — consumes more of the kitchen's productive time than the actual cooking does. The restaurant prepares fewer dishes per hour with sixty-four cooks than it would with two, because the bottleneck was never the number of cooks. It was always the number of burners.

The Go runtime's GOMAXPROCS problem in a CPU-limited container is exactly this situation. GOMAXPROCS is the number of OS threads that Go's scheduler can use simultaneously to run goroutines. By default, the Go runtime sets this to the result of `runtime.NumCPU()` — the number of logical CPU cores visible to the process. In a containerized environment, `NumCPU()` reads from `/proc/cpuinfo` and returns the host's total CPU count: sixty-four on a modern cloud instance with hyperthreading. But the container's cgroup quota limits it to two CPU-equivalents — two burners, in the kitchen analogy. Sixty-four threads are created, each competing for scheduling time on two CPU slots. The operating system's scheduler must context-switch between sixty-four runnable threads on two execution units, spending more time on bookkeeping than on actual Go code execution. Throughput degrades. Latency increases. And because the CPU usage metrics show the container operating at or near its two-CPU quota, no obvious signal points to thread scheduling inefficiency as the root cause.

## 2. How GOMAXPROCS and Go's Scheduler Work — The P, M, G Model

Go's runtime implements its own goroutine scheduler on top of OS threads, using a design called the GMP model: **G** (goroutine), **M** (machine — OS thread), and **P** (processor — logical execution context). Understanding this model is essential for understanding why GOMAXPROCS misconfiguration hurts performance.

A **goroutine** (G) is a lightweight, cooperatively-scheduled unit of execution managed entirely by the Go runtime. Goroutines have very small initial stacks (2-8 KB) and can number in the millions within a single process without excessive memory overhead.

A **P** (processor) is a logical execution context — a runtime object that holds the run queue of goroutines waiting to execute, the current goroutine being run, and various runtime state. The number of P objects is controlled by `GOMAXPROCS`. Creating a P requires no OS resource; it is a pure Go runtime concept.

An **M** (machine) is an OS thread — a real kernel thread allocated through the operating system. Each M must be attached to a P to run goroutines. The number of M objects can exceed GOMAXPROCS (blocked goroutines may cause new M objects to be created), but only GOMAXPROCS M objects can be actively executing Go code simultaneously.

```
              Go GMP Scheduler — GOMAXPROCS = 2 (correct) vs = 64 (wrong)
              ================================================================

  Host: 64 logical CPUs
  Container: cpus: "2.0" (2 CPU-equivalents via cgroup quota)

  ── CORRECT: GOMAXPROCS = 2 (automaxprocs, or manual) ────────────────────────

  Ps (processors):  [P0]  [P1]
                     │      │
  Ms (OS threads):  [M0]  [M1]    (exactly 2 threads actively running)
                     │      │
  Gs (goroutines):  [G1]  [G4]    (current goroutines on each P)

  Local run queues: P0: [G2, G5, G8, G11, ...]
                    P1: [G3, G6, G9, G12, ...]

  Global run queue: [...overflow goroutines if local queues full...]

  OS scheduler: 2 threads → 2 CPU slots. Perfect 1:1 mapping. No contention.
  Context switches: only when goroutine blocks on I/O or explicitly yields.
  CPU efficiency: near 100% of allocated quota used for Go code. ✅

  ── WRONG: GOMAXPROCS = 64 (default, reading host NumCPU) ────────────────────

  Ps (processors):  [P0][P1][P2][P3]...[P62][P63]  (64 processors)

  Each P needs an M to run.
  Ms (OS threads):  [M0][M1][M2][M3]...[M62][M63]  (64+ OS threads created)

  OS scheduler task: run 64 threads on 2 CPU slots.
  Strategy: time-slice all 64 threads across 2 CPUs.

  Each thread gets: 2 CPUs × 1ms time slice = 2ms per cycle
  Divided among 64 threads: 2ms / 64 = 0.03ms per thread per cycle.
  In 0.03ms, a thread can:
  ├── Execute ~30,000-100,000 CPU instructions (useful work)
  └── But first it must: restore registers, reload L1/L2 cache lines,
      TLB warm-up, branch predictor re-initialization.
      Context switch cost: 2-10 microseconds = 2,000-10,000 ns per switch.
      At 64 threads on 2 CPUs: thousands of switches per second.

  Context switch overhead as % of total compute:
  Switches per second: ~(64 threads × 2 CPUs) × (1000ms / timeslice_ms)
  If timeslice = 4ms: 64 × 250 = 16,000 switches/second
  Each switch: 5 µs overhead = 16,000 × 5µs = 80ms overhead per second
  On 2 CPUs: 2000ms available per second.
  Overhead: 80ms / 2000ms = 4% lost to context switching. ❌

  Reality is worse: Go goroutines block on I/O, causing additional M creation.
  M count may grow beyond 64 during high I/O load.
  Context switch overhead under real load: 10-20% of compute wasted.
```

The CPU efficiency loss to context switching is not the only consequence. Each OS thread context switch on modern CPUs carries an additional hidden cost: cache invalidation. When the scheduler preempts Thread M0 that was executing goroutines in a hot code path, the CPU registers are saved, and another thread M17 is loaded. M17 runs code from a different goroutine, accessing different data. The L1 cache lines that M0 was actively using are now cold for M0 when it eventually resumes. This cache thrashing multiplies the effective cost of each context switch beyond the raw register save/restore overhead, causing memory access latency to spike for every goroutine that resumes after a preemption.

## 3. The CPU Quota Mechanism — How cgroups Limit CPU Time

To understand why GOMAXPROCS should match the CPU quota rather than the CPU count, you need to understand how cgroup CPU quotas work. Docker's `cpus:` setting translates directly to two cgroup parameters: `cpu.cfs_quota_us` and `cpu.cfs_period_us`. The period is typically 100,000 microseconds (100ms). The quota is `cpus × period`. For `cpus: "2.0"`: quota = 200,000 µs, period = 100,000 µs — meaning 200ms of CPU time per 100ms wall clock window.

The Linux scheduler enforces this quota by throttling threads that exceed it. When a container's threads collectively consume 200ms of CPU time within a 100ms window, all threads in that container are suspended for the remainder of the window. They resume at the start of the next window. This throttling is invisible to the application — processes do not receive signals, do not observe their own suspension, and cannot distinguish throttle-induced pauses from regular scheduler preemption. From the application's perspective, execution simply slows down unpredictably.

```
              cgroup CPU Throttling — 64 Threads on 2 CPU Quota
              ====================================================

  Period: 100ms. Quota: 200ms (cpus: "2.0")

  t=0ms:  64 threads begin executing. Two CPU cores assigned.
  t=100ms: Window checkpoint.
           200ms of CPU time consumed (2 CPUs × 100ms).
           Quota exhausted. ALL 64 threads throttled. ← Throttle! ❌

  t=100ms to t=200ms: All threads suspended. CPU sits idle. Latency spikes.
  t=200ms: New window begins. Quota refilled. Threads resume.
  t=300ms: Quota exhausted again. Throttle.
  ...

  Throttle ratio: 50% of wall clock time spent throttled.
  Observed CPU steal: high (50% of time, the process cannot run).
  p99 latency: every request that arrives during a throttle window
               waits 100ms for the window to reset. p99 latency += 100ms. ❌

  With GOMAXPROCS = 2 (correct):
  t=0ms:  2 threads executing. 2 CPU cores assigned.
  t=100ms: 200ms consumed (2 threads × 2 CPUs × 100% efficiency).
           Quota exhausted. 2 threads throttled.
  t=200ms: Resume. Same throttle ratio BUT:
  ├── No wasted context switching between 64 threads. ✅
  ├── No cache thrashing between 64 different execution contexts. ✅
  ├── Each thread works continuously until quota exhausts. ✅
  └── Result: same quota, ~15-30% more actual Go code executed per window. ✅

  CRITICAL: throttling behavior is the same with 2 or 64 threads
  (quota is quota), but with 64 threads the overhead is compounded
  by context switching ON TOP of the throttling. Double the pain.
```

## 4. Diagnosing the Problem — Seeing the Mismatch

The mismatch between GOMAXPROCS and the container's CPU allocation is immediately visible through a small set of diagnostic observations. The most direct signal is the output of `runtime.NumCPU()` compared to the container's `cpus:` setting:

```go
// startup-check.go — Log CPU configuration mismatch at startup
package main

import (
    "log"
    "runtime"
)

func logCPUConfiguration() {
    numCPU := runtime.NumCPU()           // What the OS reports (host CPU count)
    maxProcs := runtime.GOMAXPROCS(0)   // Current GOMAXPROCS (passing 0 reads without setting)

    log.Printf("[RUNTIME] NumCPU (host): %d | GOMAXPROCS (goroutine threads): %d",
        numCPU, maxProcs)

    if numCPU > 4 && maxProcs == numCPU {
        log.Printf("[WARNING] GOMAXPROCS matches NumCPU (%d). If running in a " +
            "CPU-limited container, this may cause CPU thrashing. " +
            "Consider: import _ \"go.uber.org/automaxprocs\"", numCPU)
    }
}
```

## 5. The `automaxprocs` Fix — Automatic cgroup-Aware GOMAXPROCS

The `uber-go/automaxprocs` package is the standard, production-proven solution for this problem in the Go ecosystem. It performs three operations at import time, before `main()` is called: reads the cgroup CPU quota from the kernel cgroup filesystem (supporting both cgroup v1 and v2), calculates the equivalent number of CPUs by dividing quota by period, and calls `runtime.GOMAXPROCS()` with the calculated value. The entire fix is a single blank import:

```go
// main.go — The complete fix: one import line
package main

import (
    "log"
    "net/http"
    "os"

    _ "go.uber.org/automaxprocs"  // ← ENTIRE FIX IS THIS ONE LINE
                                   // Sets GOMAXPROCS = cgroup CPU quota at init()
                                   // Logs the value it set for visibility
                                   // No-op outside containers (sets to NumCPU)
)

func main() {
    // At this point, GOMAXPROCS is already correctly set.
    // automaxprocs' init() ran before main(). Log confirms it:
    // Output: "maxprocs: Updating GOMAXPROCS=2: determined from CPU quota"

    port := os.Getenv("PORT")
    if port == "" {
        port = "8080"
    }

    log.Printf("Starting server on :%s with GOMAXPROCS=%d", port, runtime.GOMAXPROCS(0))
    log.Fatal(http.ListenAndServe(":"+port, nil))
}
```

The `automaxprocs` package's behavior deserves detailed examination, because it handles edge cases that a naive implementation would miss:

```

              ===================================================

  Context 1: Container with cpus: "2.0" (cgroup quota = 200000/100000 = 2.0)
  automaxprocs reads quota → 2.0 → sets GOMAXPROCS = 2 ✅
  Log: "maxprocs: Updating GOMAXPROCS=2: determined from CPU quota"

  Context 2: Container with cpus: "0.5" (quota = 50000/100000 = 0.5)
  automaxprocs reads quota → 0.5 → rounds up → sets GOMAXPROCS = 1 ✅
  (Fractional CPUs are always rounded up to minimum 1)
  Log: "maxprocs: Updating GOMAXPROCS=1: determined from CPU quota"

  Context 3: Container with no CPU limit (quota = -1 / unlimited)
  automaxprocs detects unlimited quota → uses NumCPU()
  No GOMAXPROCS change. Falls back to standard behavior. ✅

  Context 4: Non-container (bare metal or VM, no cgroups)
  automaxprocs cannot read cgroup files → falls back to NumCPU() ✅

  Log: "maxprocs: Leaving GOMAXPROCS=64: no cgroup"

  Context 5: Kubernetes pod with resource limits
  Kubernetes sets cgroup quota from resources.limits.cpu.
  automaxprocs reads the same cgroup files → correct GOMAXPROCS. ✅
  Works without any Kubernetes-specific configuration.

  Context 6: GOMAXPROCS already set via environment variable
  If GOMAXPROCS env var is set, automaxprocs respects it and does not override.
  The env var takes precedence. ✅
```

## 6. Manual Configuration — When You Don't Want the Package

For applications where adding a dependency is undesirable, or where the CPU allocation is well-known and stable, manual GOMAXPROCS configuration is perfectly valid. The key is that it must happen before any goroutines are spawned that depend on parallelism:

```go
// main.go — Manual GOMAXPROCS configuration without external packages

package main

import (
    "bufio"
    "fmt"
    "log"
    "math"
    "os"
    "runtime"
    "strconv"
    "strings"
)

func init() {
    // Call from init() to ensure it runs before main() and before
    // any goroutines that depend on the parallelism setting.
    if err := setGOMAXPROCSFromCgroup(); err != nil {
        log.Printf("[RUNTIME] Could not auto-configure GOMAXPROCS: %v. Using default: %d",
            err, runtime.GOMAXPROCS(0))
    }
}

// setGOMAXPROCSFromCgroup reads the container's CPU quota from cgroup
// and sets GOMAXPROCS to match, rounding fractional CPUs up to minimum 1.
func setGOMAXPROCSFromCgroup() error {
    quota, period, err := readCPUQuota()
    if err != nil {
        return err
    }

    // -1 quota means unlimited (no cgroup CPU limit)
    if quota == -1 {
        return fmt.Errorf("no CPU quota set (unlimited container)")
    }

    cpus := float64(quota) / float64(period)
    procs := int(math.Ceil(cpus))  // Always round up: 0.5 CPUs → 1 GOMAXPROCS
    if procs < 1 {
        procs = 1
    }

    previous := runtime.GOMAXPROCS(procs)
    log.Printf("[RUNTIME] GOMAXPROCS set to %d (%.2f CPU quota). Was: %d. Host CPUs: %d",
        procs, cpus, previous, runtime.NumCPU())

    return nil
}

func readCPUQuota() (quota, period int64, err error) {
    // Try cgroup v2 first (modern distributions)
    if data, readErr := os.ReadFile("/sys/fs/cgroup/cpu.max"); readErr == nil {
        parts := strings.Fields(strings.TrimSpace(string(data)))
        if len(parts) == 2 {
            if parts[0] == "max" {
                return -1, 0, nil // No quota limit
            }
            q, e1 := strconv.ParseInt(parts[0], 10, 64)
            p, e2 := strconv.ParseInt(parts[1], 10, 64)
            if e1 == nil && e2 == nil {
                return q, p, nil
            }
        }
    }

    // Try cgroup v1
    quotaData, e1 := os.ReadFile("/sys/fs/cgroup/cpu/cpu.cfs_quota_us")
    periodData, e2 := os.ReadFile("/sys/fs/cgroup/cpu/cpu.cfs_period_us")
    if e1 == nil && e2 == nil {
        q, pe1 := strconv.ParseInt(strings.TrimSpace(string(quotaData)), 10, 64)
        p, pe2 := strconv.ParseInt(strings.TrimSpace(string(periodData)), 10, 64)
        if pe1 == nil && pe2 == nil {
            if q == -1 {
                return -1, 0, nil // No quota limit
            }
            return q, p, nil
        }
    }

    return 0, 0, fmt.Errorf("cgroup CPU quota files not found")
}
```

## 7. The Combined Runtime Configuration — GOMAXPROCS + GOMEMLIMIT Together

The GOMAXPROCS misconfiguration and the GOMEMLIMIT misconfiguration from the previous case study are two sides of the same coin — the Go runtime's blindness to container resource boundaries. They should always be fixed together. An application that fixes only GOMEMLIMIT but not GOMAXPROCS will have correct memory behavior but poor CPU efficiency. An application that fixes only GOMAXPROCS but not GOMEMLIMIT may have efficient CPU scheduling but will be OOMKilled when GC targets exceed the container's memory limit:

```go
// main.go — Complete container-aware Go runtime initialization
package main

import (
    "log"
    "os"
    "runtime"

    _ "github.com/KimMachineGun/automemlimit"  // Sets GOMEMLIMIT from cgroup
    _ "go.uber.org/automaxprocs"               // Sets GOMAXPROCS from cgroup CPU quota
)

func main() {
    // Both are set before main() via their init() functions.
    // Log the runtime configuration for operational visibility:
    log.Printf("[RUNTIME] Container-aware initialization complete:")
    log.Printf("[RUNTIME]   GOMAXPROCS = %d (goroutine scheduler threads)",
        runtime.GOMAXPROCS(0))
    log.Printf("[RUNTIME]   NumCPU (host) = %d (informational only)",
        runtime.NumCPU())
    log.Printf("[RUNTIME]   GOMEMLIMIT = %s (from env or cgroup)",
        os.Getenv("GOMEMLIMIT"))

    // Start your application...
}
```

## 9. The Golden Rule

> Go's `GOMAXPROCS` is the number of OS threads the Go scheduler can use simultaneously to execute goroutines. Its default value is `runtime.NumCPU()`, which reads the host's total CPU count from `/proc/cpuinfo` — a file that reports the host's physical CPU topology, not the container's cgroup CPU quota. In a container with `cpus: "2.0"` running on a 64-core host, Go creates 64 OS threads, all competing for 2 CPU slots. The operating system's scheduler must time-slice 64 threads across 2 execution units, spending a significant fraction of the available CPU budget on context switches, register saves/restores, and cache line invalidations rather than executing Go code. The fix is one import line: `import _ "go.uber.org/automaxprocs"`. This package reads the cgroup CPU quota at startup and calls `runtime.GOMAXPROCS()` with the correct value before `main()` executes. It is a no-op outside containers. It works with both cgroup v1 and cgroup v2. It respects the `GOMAXPROCS` environment variable if already set. It should be treated as mandatory for every containerized Go application, paired with `automemlimit` for GOMEMLIMIT configuration, as they address the same category of problem: the Go runtime's blindness to the container boundary. The performance improvement is not marginal — p99 latency reductions of 50-90% are typical on CPU-limited containers running on dense multi-core hosts.

The Go runtime does not know it is in a container. You must tell it. One import line is all it takes.
