# Volume Fills Disk — Silent Death

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Warehouse That Never Ships Out

Imagine a warehouse receiving deliveries every hour, around the clock. Trucks arrive, unload their cargo, and the warehouse staff dutifully log each delivery and stack the goods in organized rows. The warehouse is large — forty thousand square feet — and when it opened, the operators estimated it would take years to fill. Nobody installed a measurement system that would alert them as capacity approached. Nobody defined a policy for removing outdated inventory. The goods simply accumulated, week after week, month after month.

Then one Monday morning, a delivery truck arrives and the staff attempt to unload it. There is no space. Every aisle is full. Every rack is packed floor to ceiling. The staff cannot accept the delivery. But the problem is not merely that this one truck cannot be unloaded. The warehouse's function is to receive and temporarily hold goods before redistributing them. When it is full, nothing can come in. The entire supply chain that depends on this warehouse — every upstream supplier, every downstream recipient — grinds to a halt simultaneously. A problem that was invisible and harmless at 50% capacity, unremarkable at 80% capacity, and only mildly inconvenient at 95% capacity becomes catastrophic at 100%.

This is exactly how disk exhaustion kills a Docker host. Every named volume, every container log, every pulled image layer accumulates on the host filesystem under `/var/lib/docker`. The growth is continuous and mostly invisible. Each individual accumulation source — PostgreSQL WAL files, Redis AOF log, container stdout logs, image layer cache — seems harmless in isolation. Together, over weeks and months of continuous operation, they fill the host disk completely. When the disk reaches 100%, it is not one container that fails: it is every container on the host simultaneously, because all of them share the same underlying filesystem. Postgres goes read-only. Application containers cannot write logs. New processes cannot be forked. The system does not crash cleanly — it degrades in bizarre, unpredictable ways that make diagnosis difficult precisely because the failure mode of a full disk does not resemble any single application error.

## 2. The Anatomy of `/var/lib/docker` — Where Space Goes

The first step in managing disk exhaustion is understanding precisely what occupies space under `/var/lib/docker` — the default root directory where Docker stores all its data on Linux hosts. This directory is the warehouse, and its contents fall into four major categories, each with its own growth characteristics and retention management strategy.

```
              /var/lib/docker — Space Consumption Breakdown
              ================================================

  /var/lib/docker/
  ├── overlay2/          ← IMAGE LAYERS + CONTAINER WRITABLE LAYERS
  │   ├── <sha256>/      Each pulled image layer: 50-500 MB per layer
  │   ├── <sha256>/      Multiple images share layers (deduplication)
  │   └── ...            Old images accumulate if not pruned
  │   Growth: Unbounded. Each new image version adds new layers.
  │   Risk: Pulling postgres:16.2, 16.3, 16.4 sequentially without pruning
  │         leaves all three versions occupying disk.
  │
  ├── volumes/           ← NAMED VOLUME DATA
  │   ├── pgdata/
  │   │   └── _data/     PostgreSQL data directory
  │   │       ├── base/              User tables: grows with your data ✅ (expected)
  │   │       ├── pg_wal/            Write-Ahead Log: grows with write load ⚠️
  │   │       │   └── (WAL segments) Normally recycled, but replication lag
  │   │       │                      or archive_command failure → unbounded ❌
  │   │       └── pg_log/            PostgreSQL server logs (if log_directory set)
  │   ├── redisdata/
  │   │   └── _data/
  │   │       ├── appendonly.aof     Redis append-only file: GROWS FOREVER ❌
  │   │       │                      without auto-rewrite enabled
  │   │       └── dump.rdb           Redis snapshot: bounded, overwrites itself ✅
  │   └── ...
  │   Growth: Potentially unbounded per data type.
  │
  ├── containers/        ← CONTAINER METADATA + LOGS
  │   └── <container_id>/
  │       └── <container_id>-json.log  ← STDOUT/STDERR LOG FILE
  │           Growth: Unbounded by default (no log rotation configured) ❌
  │           A verbose container can generate GBs of logs per day.
  │
  └── buildcache/        ← BUILD LAYER CACHE
      Growth: Accumulates build layers from docker build. Rarely cleared.
      Risk: Active CI on the same host → cache grows rapidly.
```

Of these four categories, three have a habit of growing without bounds in production deployments that have not been explicitly configured for retention: the container log files, the Redis AOF file, and the PostgreSQL WAL directory under specific failure conditions. Understanding each growth pattern allows you to apply the correct retention control.

## 3. The Three Silent Growers — WAL, AOF, and Container Logs

**The PostgreSQL WAL — Write-Ahead Log Accumulation**

The PostgreSQL Write-Ahead Log is the mechanism that guarantees crash recovery and enables replication. Before PostgreSQL writes any data change to its main data files, it first records the change in the WAL. This ensures that if the server crashes mid-write, the WAL can be replayed on restart to bring the database to a consistent state. WAL segments are fixed-size files (16 MB by default) stored in the `pg_wal/` directory.

Under normal operation, PostgreSQL automatically recycles WAL segments after they are no longer needed — after they have been replayed by all active replication subscribers, and after any configured WAL archiving has copied them. When PostgreSQL operates in isolation with no replication configured, WAL segments are recycled rapidly and the `pg_wal/` directory remains bounded in size. The growth problem emerges in three scenarios: (1) a replica falls significantly behind the primary and the primary must retain WAL segments until the replica catches up — this can hold thousands of WAL files; (2) a WAL archive command is configured but begins failing silently, and PostgreSQL retains all WAL segments from the last successful archive point; (3) `wal_keep_size` is set to a large value without understanding the disk implications at high write volumes.

```
              PostgreSQL WAL Growth — Normal vs Failure Scenarios
              ======================================================

  Normal WAL cycle (no replication, no archiving):
  pg_wal/ holds: min_wal_size to max_wal_size (default: 80MB to 1GB)
  PostgreSQL recycles files within this range. Size stays bounded. ✅

  Scenario A — Replication lag (replica is 2 hours behind):
  Every 16 MB WAL segment written must be retained for the lagging replica.
  At 100 MB/sec write throughput: 100 × 3600 × 2 = 720,000 MB = ~703 GB WAL ❌
  pg_wal/ grows until the replica catches up or replication is disabled.

  Scenario B — Archive command failing silently:
  postgresql.conf: archive_mode = on
                   archive_command = 'aws s3 cp %p s3://backup/%f'
  AWS credentials expire. archive_command returns exit code 1.
  PostgreSQL: retains ALL WAL segments since last successful archive.
  Growth rate: exactly equal to database write throughput. Unbounded. ❌
  Log evidence: "archive_command failed ... still waiting for archiver" ← check this

  Scenario C — wal_keep_size misconfiguration:
  postgresql.conf: wal_keep_size = 10GB
  High write load: 1 GB WAL generated per hour.
  pg_wal/ maintains at least 10 GB at all times.
  If host disk is 50 GB total: 10 GB reserved for WAL always.
  Not a crisis alone, but combined with data growth: eventual disk exhaustion.

  Monitoring query (run inside postgres container):
  SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0')) AS wal_size;
  SELECT count(*), pg_size_pretty(sum(size)) FROM pg_ls_waldir();
  -- If WAL directory shows hundreds of 16 MB files: growth problem confirmed.
```

**The Redis AOF — Append-Only File Without Rewrites**

Redis provides two persistence mechanisms: RDB snapshots (point-in-time dumps that overwrite a single file) and AOF (append-only file, where every write command is logged in sequence). When `appendonly yes` is configured, Redis writes every `SET`, `HSET`, `LPUSH`, and similar command to the AOF file. The file grows by the size of each command string for every write operation Redis processes.

The critical configuration that prevents unbounded AOF growth is `auto-aof-rewrite-percentage` and `auto-aof-rewrite-min-size`. When these are configured, Redis periodically rewrites the AOF file by loading the current dataset and generating the minimal set of commands needed to reproduce that dataset — effectively compressing the entire command history into a much smaller file. Without this rewrite, the AOF file accumulates every write command since Redis started, including commands that have since been overwritten by later commands. A Redis instance that has had a key set to `"hello"` one million times has stored one million `SET` commands for that key, when the entire history could be represented by a single `SET` command — the most recent one.

```
              Redis AOF Growth — Without vs With Rewrite
              ============================================

  Application behavior: session store, updating 10,000 session keys/second.
  Each SET command in AOF: ~50 bytes (key + value + command overhead).

  Without auto-aof-rewrite (default in some Redis configs):
  ─────────────────────────────────────────────────────────────────────
  AOF entries per second: 10,000 commands × 50 bytes = 500 KB/second
  AOF entries per day:    500 KB × 86,400 = ~42 GB/day
  After 1 week:           ~294 GB of AOF log
  Actual unique data:     ~50 MB (10,000 sessions × 5 KB each)
  Waste ratio:            5,880× the actual data size ❌

  With auto-aof-rewrite:
  ─────────────────────────────────────────────────────────────────────
  # redis.conf configuration:
  appendonly yes
  auto-aof-rewrite-percentage 100  # Rewrite when AOF doubles since last rewrite
  auto-aof-rewrite-min-size 64mb   # Don't rewrite until AOF is at least 64 MB

  AOF grows until it doubles its post-rewrite size.
  Rewrite runs: produces minimal AOF representing current state.
  After rewrite: AOF size ≈ size of current dataset (50 MB).
  AOF grows again → doubles to 100 MB → rewrite → back to 50 MB → cycle.
  Maximum AOF size: ~2× current dataset size ✅ (bounded and predictable)
```

**Container Stdout/Stderr Logs — The Invisible Accumulator**

Every container's stdout and stderr output is captured by Docker's log driver and written to a JSON-formatted file under `/var/lib/docker/containers/<container_id>/<container_id>-json.log`. By default, Docker applies no size limit and no rotation to this file. A container that produces verbose output — debug-level logging, request logging for a high-traffic API, stack traces from a buggy service — will grow this file without bounds until the host disk is full.

This is the most commonly overlooked source of disk exhaustion because developers test their applications with the default log driver, log rotation is not a concern at development scale, and the growing log file is completely invisible unless you specifically check its size. Production systems that have been running for months may have log files measured in tens or hundreds of gigabytes.

```bash
# Find the largest container log files on the host:
du -sh /var/lib/docker/containers/*/json.log 2>/dev/null | sort -rh | head -20
# Example output (terrifying):
# 47G  /var/lib/docker/containers/abc123.../abc123...-json.log  ← 47 GB for one container
# 12G  /var/lib/docker/containers/def456.../def456...-json.log
# 1.2G /var/lib/docker/containers/ghi789.../ghi789...-json.log
```

## 4. The Cascade Failure — What Happens When Disk Reaches 100%

The failure mode at 100% disk utilization is catastrophic and affects the entire host simultaneously. This is qualitatively different from a single container failure — it is a host-wide event. Understanding the cascade helps appreciate why the alert threshold must be 70%, not 90% or 95%.

```
              Disk Exhaustion Cascade — Timeline to Total Failure
              ======================================================

  Host disk: 100 GB total | 95 GB used | 5 GB remaining

  t=0:     AOF rewrite triggered. Redis needs temp space for the new AOF.
           Needs ~1 GB temp file. Writes ~800 MB. Disk at 99.8%.
  t=1min:  PostgreSQL WAL segment rotation. Needs 16 MB for new segment.
           Disk at 100%. Write fails. ← First hard failure.
  t=1min:  PostgreSQL: "PANIC: could not write to file "pg_wal/...":
           No space left on device"
           PostgreSQL enters recovery mode. Database goes read-only. ❌
  t=2min:  Container stdout logging: all containers attempt to write logs.
           Docker log driver: "write /var/lib/docker/containers/.../json.log:
           no space left on device"
           Docker suppresses log writes silently. Logs stop appearing. ❌
  t=2min:  Application containers: any write operation fails.
           File uploads: fail. Temp file creation: fail. Cache writes: fail.
           Application returns 500s for all write-dependent paths. ❌
  t=3min:  New processes cannot be forked (fork requires temp memory → disk).
           Systemd health checks fail. Container restarts begin.
           Container restarts require writing to disk. Restart fails.
           Containers enter restart loop. System grinds. ❌
  t=5min:  SSH to the host: may succeed or may hang (depends on whether
           sshd needs to write to disk for session setup).
           If SSH fails: remote access lost. On-call engineer cannot log in.
           Physical console or out-of-band management required. ❌
  t=5min:  All monitoring agents: cannot write their own data.
           Monitoring goes dark at exactly the moment you need it most. ❌

  Recovery from 100% disk is not a simple restart. It requires:
  1. Identifying which files can be safely deleted (while system is barely responsive)
  2. Freeing enough space for the system to function
  3. Restarting services in the correct order
  4. Verifying data consistency (PostgreSQL may need recovery)
  5. Implementing the retention policies that should have been there from day one.
  Total downtime: 30 minutes to several hours.
```

The loss of SSH access deserves special attention. When a host's disk is completely full and the SSH daemon cannot write session files or update login records, remote access becomes unreliable or impossible. Engineers responding to the incident may find themselves locked out of the very machine they need to remediate. This is why the phrase "silent death" in the case study title is apt — the system does not crash with a clear error message that points to a specific cause. It degrades in a dozen different ways simultaneously, all of which are symptoms of the same root cause, and the root cause may not be diagnosable remotely if the host becomes inaccessible.

## 5. The Solutions — Prevention, Configuration, and Monitoring

Preventing disk exhaustion requires addressing each growth source with an appropriate retention policy, establishing proactive monitoring with an alert threshold well below 100%, and performing regular housekeeping operations.

**Docker Log Driver Configuration — The First Priority**

Container log rotation is the simplest, highest-impact configuration change for preventing disk exhaustion. It should be applied to every production container without exception:

```json
// /etc/docker/daemon.json — Host-level default log configuration
// Applied to ALL containers on this host unless overridden per-container.
{
    "log-driver": "json-file",
    "log-opts": {
        "max-size": "50m",    // Rotate log file when it reaches 50 MB
        "max-file": "5"       // Keep up to 5 rotated files (250 MB total per container)
    }
}
```

```yaml
# docker-compose.yml — Per-service log configuration (overrides daemon.json)
services:
  api:
    build: .
    logging:
      driver: json-file
      options:
        max-size: "50m"    # Each log file: max 50 MB
        max-file: "5"      # Keep 5 files: up to 250 MB total
        # Compressed rotated files: add 'compress: "true"' to save more space

  postgres:
    image: postgres:16.2-alpine3.19
    logging:
      driver: json-file
      options:
        max-size: "10m"   # Database container is less chatty
        max-file: "3"

  redis:
    image: redis:7.2-alpine3.19
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

After changing `daemon.json`, restart the Docker daemon (`systemctl restart docker`) for the defaults to take effect. Note that existing containers must be recreated — the log driver configuration is set at container creation time and does not change for running containers.

**Redis AOF Rewrite Configuration**

```
# redis.conf — Correct persistence configuration for production

# Enable persistence
appendonly yes

# AOF rewrite thresholds: rewrite when AOF is 100% larger than after last rewrite
# AND at least 64 MB in size. Keeps AOF at ~2× current dataset size.
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# AOF fsync policy:
# always: fsync every write → safest, slowest
# everysec: fsync every second → good balance (lose at most 1 sec of data on crash)
# no: let OS decide → fastest, least durable
appendfsync everysec

# Disable fsync during AOF rewrite (prevents I/O stall):
no-appendfsync-on-rewrite yes

# RDB snapshot schedule (complementary to AOF):
save 900 1      # Snapshot if at least 1 change in 900 seconds
save 300 10     # Snapshot if at least 10 changes in 300 seconds
save 60 10000   # Snapshot if at least 10,000 changes in 60 seconds

# Maximum memory limit — prevents Redis from consuming all host RAM:
maxmemory 2gb
maxmemory-policy allkeys-lru  # Evict least-recently-used keys when limit reached
```

**PostgreSQL WAL Configuration and Monitoring**

```sql
-- postgresql.conf — WAL size management

-- Bounds on WAL directory size:
min_wal_size = 80MB     -- Minimum WAL directory size
max_wal_size = 2GB      -- Maximum WAL directory size before forcing checkpoint

-- If using replication, set a reasonable wal_keep_size:
-- This retains WAL for replicas even if they are temporarily unavailable.
-- Set to how much WAL a replica can fall behind before requiring re-sync.
wal_keep_size = 512MB   -- Retain 512 MB of WAL for replicas

-- If using WAL archiving, monitor archive status:
-- archive_mode = on
-- archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
-- Monitor for archive failures:
```

```sql
-- Run inside PostgreSQL to detect WAL growth problems:

-- Check WAL directory size:
SELECT count(*) AS wal_files,
       pg_size_pretty(sum(size)) AS total_wal_size
FROM pg_ls_waldir();
-- Healthy: a few dozen files, < 1 GB
-- Problematic: hundreds of files, > 5 GB → investigate replication lag or archiving

-- Check replication lag (if using streaming replication):
SELECT client_addr,
       state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn))  AS send_lag,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, write_lsn))             AS write_lag,
       pg_size_pretty(pg_wal_lsn_diff(write_lsn, flush_lsn))            AS flush_lag,
       pg_size_pretty(pg_wal_lsn_diff(flush_lsn, replay_lsn))           AS replay_lag
FROM pg_stat_replication;
-- Large values in any lag column = WAL accumulation risk

-- Check archive status:
SELECT archived_count,
       last_archived_wal,
       last_archived_time,
       failed_count,
       last_failed_wal,
       last_failed_time
FROM pg_stat_archiver;
-- failed_count > 0 and growing = archive failing = WAL accumulation risk ❌
```

## 6. Monitoring — Alert at 70%, Not 100%

The most important operational principle for disk exhaustion prevention is setting alert thresholds at 70% disk utilization, not 90% or 95%. The reasoning is straightforward: many disk-consuming operations are bursty. A database backup, a WAL accumulation during replication lag, a log flush spike — each can consume gigabytes in minutes. An alert at 90% gives you a narrow window to respond. An alert at 70% gives you time to diagnose, plan, and remediate without an active production incident pressuring you.

```bash
# ── Docker-native disk inspection ────────────────────────────────────────────
# Comprehensive breakdown of Docker's disk usage:
docker system df
# TYPE            TOTAL     ACTIVE    SIZE       RECLAIMABLE
# Images          14        5         8.234GB    6.121GB (74%)
# Containers      8         8         1.234GB    0B (0%)
# Local Volumes   3         3         47.23GB    0B (0%)
# Build Cache     0         0         0B         0B

docker system df -v
# Verbose: lists each image, container, and volume individually with sizes.
# Immediately shows which volume is the space hog.

# ── Host-level disk monitoring ───────────────────────────────────────────────
df -h /var/lib/docker
# Filesystem      Size  Used  Avail  Use%  Mounted on
# /dev/sda1        100G   73G   27G   73%  /

# ── Find the specific large files ────────────────────────────────────────────
# Container log files (most common culprit):
du -sh /var/lib/docker/containers/*/json.log 2>/dev/null | sort -rh | head -10

# Volume data sizes:
du -sh /var/lib/docker/volumes/*/_data 2>/dev/null | sort -rh | head -10

# PostgreSQL WAL directory specifically:
docker exec <postgres_container> du -sh /var/lib/postgresql/data/pg_wal/
# Expected: < 2 GB. Problematic: > 5 GB.

# Redis AOF file:
docker exec <redis_container> du -sh /data/appendonly.aof
# Expected: < 2× maxmemory. Problematic: growing without bound.

# ── Reclaim space safely (without data loss) ─────────────────────────────────
# Remove unused images (not referenced by any container):
docker image prune -a
# WARNING: removes ALL images not currently used. Will re-pull on next deploy.
# Safer alternative — remove only dangling (untagged) images:
docker image prune

# Remove stopped containers:
docker container prune

# Remove unused volumes (DANGEROUS — verify before running):
docker volume prune
# Only removes volumes NOT referenced by any container.
# Safe in theory, but verify with: docker volume ls --filter dangling=true

# Remove build cache:
docker builder prune --all

# One command to clean everything unused (NEVER on production without review):
docker system prune -a
```

```yaml
# Prometheus alert rules for disk exhaustion prevention
# Add to your alertmanager or equivalent monitoring system:

# alert_rules.yml:
groups:
  - name: docker_host_disk
    rules:
      # Alert at 70% — early warning, time to investigate
      - alert: DockerHostDiskUsageHigh
        expr: (node_filesystem_size_bytes{mountpoint="/var/lib/docker"} -
               node_filesystem_free_bytes{mountpoint="/var/lib/docker"}) /
               node_filesystem_size_bytes{mountpoint="/var/lib/docker"} > 0.70
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Docker host disk usage above 70%"
          description: "Disk at {{ $value | humanizePercentage }}. Investigate growth."

      # Alert at 85% — elevated urgency, remediation required within hours
      - alert: DockerHostDiskUsageCritical
        expr: (node_filesystem_size_bytes{mountpoint="/var/lib/docker"} -
               node_filesystem_free_bytes{mountpoint="/var/lib/docker"}) /
               node_filesystem_size_bytes{mountpoint="/var/lib/docker"} > 0.85
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Docker host disk usage above 85% — URGENT"
          description: "Disk at {{ $value | humanizePercentage }}. Risk of host failure."
```

## 7. The Regular Housekeeping Crontab

Even with correct configuration, regular housekeeping prevents gradual accumulation of Docker artifacts — old image layers from deployments, completed container writable layers, and build cache entries. A weekly housekeeping job run during off-peak hours keeps the host clean without risking data loss:

```bash
#!/bin/bash
# /etc/cron.weekly/docker-housekeeping
# Runs weekly to clean Docker artifacts. Safe — does not touch running containers or volumes.

set -euo pipefail
LOG_FILE="/var/log/docker-housekeeping.log"

echo "=== Docker Housekeeping: $(date) ===" >> "$LOG_FILE"

# Log disk usage before cleanup
echo "BEFORE:" >> "$LOG_FILE"
df -h /var/lib/docker >> "$LOG_FILE"
docker system df >> "$LOG_FILE"

# Remove dangling images (untagged layers from old builds):
docker image prune -f >> "$LOG_FILE" 2>&1

# Remove stopped containers (containers that exited normally):
docker container prune -f >> "$LOG_FILE" 2>&1

# Remove dangling volumes (volumes not referenced by any container):
# Safe: dangling volumes have no container using them.
docker volume prune -f >> "$LOG_FILE" 2>&1

# Remove build cache older than 7 days:
docker builder prune --filter "until=168h" -f >> "$LOG_FILE" 2>&1

# Log disk usage after cleanup
echo "AFTER:" >> "$LOG_FILE"
df -h /var/lib/docker >> "$LOG_FILE"
docker system df >> "$LOG_FILE"

echo "Housekeeping complete: $(date)" >> "$LOG_FILE"
```

## 8. The Golden Rule

> A Docker volume is not an abstraction — it is a directory on the host filesystem, and the host filesystem has a fixed capacity. Every byte written to a volume, every container log line, every WAL segment, and every Redis AOF entry occupies real space on the host disk. When that space is exhausted, the failure is not graceful: it is simultaneous, host-wide, and partially self-reinforcing, because the remediation steps themselves require writing to disk. The defenses are simple and must be applied before the problem occurs, not during the incident. Configure Docker's log driver with `max-size` and `max-file` for every container. Enable Redis AOF rewrite with `auto-aof-rewrite-percentage 100`. Monitor PostgreSQL's WAL directory size and archive status. Monitor host disk utilization and alert at 70% — the threshold that gives you hours to respond calmly rather than minutes to respond frantically. Run `docker system df` weekly; it is the `du` command for Docker's entire storage footprint. Unbounded growth is not a growth problem — it is a missing retention policy. Set the policy before the disk sets it for you.

The disk does not fail loudly. It fills quietly, one log line at a time, until nothing on the host can write another byte.
