# RabbitMQ Consumer Scale — Message Thundering Herd

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Loudspeaker vs. The Ticket Counter

A large company has a daily announcement system. Every morning, the office manager makes announcements over the building's loudspeaker: "Today's lunch menu is pasta", "The fire drill is at 3pm", "The all-hands meeting is moved to Thursday." Every person in the building hears every announcement simultaneously. This is the correct and intended behavior — an announcement is information that everyone should receive. Nobody says "only one employee should hear about the fire drill."

The company also has a ticket counter for receiving and processing customer support requests. A ticket arrives, a support agent picks it up, processes it, and closes it. When there is a backlog, the manager hires more support agents and places them behind the same counter. Each new ticket is picked up by exactly one available agent. Two agents never pick up the same ticket. The system distributes work across agents automatically. This, too, is the correct and intended behavior — a support ticket is work that should be done exactly once.

Now imagine the manager, seeing a backlog of support tickets and knowing that announcements work well for the whole building, decides to route support tickets through the loudspeaker instead of the ticket counter. Each new ticket is announced over the loudspeaker. Every support agent — all twenty of them — hears the ticket and starts working on it simultaneously. The same customer is called by twenty agents. The same problem is "solved" twenty times. The database is updated twenty times with conflicting results. Twenty agents charge the customer's card for the same order. This is not scaling. This is catastrophe, dressed up as efficiency.

This is precisely the failure when RabbitMQ workers are connected to a fanout exchange instead of a shared queue. The fanout exchange is the loudspeaker — it delivers every message to every bound queue, and therefore to every consumer. The work queue pattern — a single shared queue with competing consumers — is the ticket counter. The two mechanisms are not interchangeable. Using the wrong one when scaling from one worker to twenty does not increase throughput by twenty times; it processes every message twenty times, with all of the data corruption and idempotency violations that entails.

## 2. RabbitMQ Exchange Types — The Delivery Semantics Model

RabbitMQ's routing model has three components: **producers** publish messages to **exchanges**, exchanges route messages to **queues** based on their type and routing rules, and **consumers** read messages from queues. The exchange type is the critical architectural decision that determines delivery semantics — specifically, whether a message is delivered to one consumer or to all consumers.

```
              RabbitMQ Routing Architecture — Exchanges and Queues
              ========================================================

  Producer → Exchange → (routing logic) → Queue(s) → Consumer(s)
                ↑
                Exchange Type determines routing logic

  ── FANOUT Exchange ───────────────────────────────────────────────────

  Producer
      │
      ▼
  [fanout-exchange]
      │
      ├──► [queue-A] ──► Consumer 1 (worker-1)    ← Gets the message
      ├──► [queue-B] ──► Consumer 2 (worker-2)    ← Gets the message ❌ duplicate
      ├──► [queue-C] ──► Consumer 3 (worker-3)    ← Gets the message ❌ duplicate
      └──► [queue-D] ──► Consumer 4 (worker-4)    ← Gets the message ❌ duplicate

  Message delivery: BROADCAST — delivered to ALL bound queues.
  Each consumer gets a copy. Routing key: ignored.
  Use case: pub/sub notifications, event broadcasting, log fanout.
  Worker scaling effect: adding consumers MULTIPLIES processing, not distributes it. ❌

  ── DIRECT/TOPIC Exchange (Work Queue Pattern) ────────────────────────

  Producer
      │
      ▼
  [direct-exchange] ──routing-key="orders"──► [shared-orders-queue]
                                                    │
                                                    ├──► Consumer 1 (worker-1) ← Gets msg A
                                                    ├──► Consumer 2 (worker-2) ← Gets msg B
                                                    ├──► Consumer 3 (worker-3) ← Gets msg C
                                                    └──► Consumer 4 (worker-4) ← Gets msg D

  Message delivery: COMPETING CONSUMERS — each message delivered to ONE consumer.
  RabbitMQ round-robins (or load-balances) across all consumers on the queue.
  Use case: task distribution, work queues, job processing. ✅
  Worker scaling effect: adding consumers DISTRIBUTES work, not duplicates it. ✅

  ── How worker containers bind ────────────────────────────────────────

  WRONG (fanout pattern — each worker creates its own queue):
  worker-1 starts → declares exclusive queue "worker-1-queue" → binds to fanout-exchange
  worker-2 starts → declares exclusive queue "worker-2-queue" → binds to fanout-exchange
  worker-3 starts → declares exclusive queue "worker-3-queue" → binds to fanout-exchange
  Each worker has its own queue. Fanout sends to all three. Each gets every message. ❌

  CORRECT (work queue pattern — all workers share one queue):
  worker-1 starts → connects to existing "orders-queue" → begins consuming
  worker-2 starts → connects to existing "orders-queue" → begins consuming
  worker-3 starts → connects to existing "orders-queue" → begins consuming
  All workers share one queue. RabbitMQ distributes each message to one worker. ✅
```

## 3. The Fanout Duplicate Processing Disaster — A Concrete Timeline

To understand the severity of this failure, trace the exact sequence when an e-commerce order message is published to a fanout exchange with twenty worker consumers:

```
              Fanout Duplicate Processing — Order Processing Timeline
              ==========================================================

  Setup: 20 worker containers, each bound to the same fanout exchange
         with their own unique auto-generated queue.
         fanout-exchange → [q-worker-1] → worker-1
         fanout-exchange → [q-worker-2] → worker-2
         ...
         fanout-exchange → [q-worker-20] → worker-20

  t=0.000s: Order #7849 placed. Payment pre-authorized: $149.99
            Producer publishes to "orders" fanout exchange.
            Message: {order_id: 7849, user_id: 1023, amount: 149.99, items: [...]}

  t=0.001s: RabbitMQ fanout exchange: routes message to all 20 bound queues.
            All 20 workers receive the message simultaneously.

  t=0.002s: All 20 workers begin processing order #7849 in parallel.
            Each executes:
            1. SELECT * FROM orders WHERE id = 7849; (all 20 see status='pending')
            2. UPDATE orders SET status='processing' WHERE id=7849; (race condition ❌)
            3. Charge payment: stripe.charge(7849, 149.99) ← called 20 times ❌
            4. Reserve inventory ← called 20 times ❌
            5. Send confirmation email ← called 20 times ❌
            6. Generate shipping label ← called 20 times ❌

  t=0.050s: Stripe processes 20 payment capture requests for order #7849.
            First capture: success. Customer charged $149.99. ✅
            Captures 2-20: may succeed or fail depending on Stripe dedup logic.
            If Stripe's idempotency key not set: customer charged up to $2,999.80. ❌❌❌

  t=0.051s: 20 confirmation emails sent to customer. ❌
            Customer inbox: 20 identical "Your order has been confirmed" emails.

  t=0.052s: Inventory table:
            20 concurrent updates attempt to decrement stock by order quantity.
            If item stock = 5 and order qty = 3:
            Without proper locking: stock updated to 2 (correct) by one worker,
            then updated to -1, -4, -7... by subsequent workers. ❌
            Negative inventory. Database constraint violation (if enforced). ❌

  t=0.100s: 19 of 20 workers: UPDATE orders SET status='processing'
            fails or overwrites each other's results. Order status undefined. ❌

  Customer experience: 20 confirmation emails, possibly charged multiple times.
  Database state: corrupted.
  Inventory: negative.
  Support ticket: filed immediately.
  Root cause in logs: invisible (every worker reports "processed successfully").
```

What makes this failure mode particularly dangerous is that every worker reports success. From the perspective of each individual worker, it received a message, processed it, and completed without error. The error is not visible in any single worker's log — it is visible only at the data level, where the same record has been processed twenty times. By the time the corruption is detected, the damage is done: payments charged, emails sent, inventory corrupted.

## 4. Why This Mistake Happens — The Development-to-Production Gap

The fanout mistake follows a predictable pattern. A developer builds the initial system with one worker. With one worker, a fanout exchange and a direct exchange with a shared queue are functionally identical: one publisher, one queue, one consumer, every message processed exactly once. The choice between exchange types makes no observable difference at this scale.

```
              Why Single-Worker Development Hides the Bug
              ==============================================

  Single worker deployment (development / first production deploy):
  ─────────────────────────────────────────────────────────────────────
  fanout-exchange → [q-worker-1] → worker-1

  Message published → one queue → one consumer → processed once ✅
  fanout: identical behavior to work queue at this scale.
  Tests pass. Production works. Monitoring shows no anomalies.

  Scaled deployment (after traffic grows):
  ─────────────────────────────────────────────────────────────────────
  fanout-exchange → [q-worker-1]  → worker-1  ←┐
  fanout-exchange → [q-worker-2]  → worker-2  ←┤ All get every message ❌
  fanout-exchange → [q-worker-3]  → worker-3  ←┘
  ... (20 workers)

  The bug was always present in the architecture.
  It was invisible at scale 1. It becomes catastrophic at scale 20.
  The scaling operation is the trigger, not the cause.

  How the fanout binding typically happens in code:
  ─────────────────────────────────────────────────────────────────────
  // Common incorrect pattern: each worker declares its own queue
  queueName := fmt.Sprintf("orders-%s", os.Getenv("HOSTNAME"))  // "orders-worker-1"
  q, _ := ch.QueueDeclare(queueName, true, false, false, false, nil)
  ch.QueueBind(q.Name, "", "orders-fanout-exchange", false, nil)
  ch.Consume(q.Name, ...)

  // With HOSTNAME env var per container:
  // worker-1: declares "orders-worker-1" queue, binds to fanout
  // worker-2: declares "orders-worker-2" queue, binds to fanout
  // Each container creates a unique queue → all bound to fanout → all get all messages. ❌
```

## 5. The Correct Implementation — Work Queue with Competing Consumers

The correct pattern for task distribution is a single shared queue declared once (not per-worker), with all worker instances consuming from the same queue. RabbitMQ automatically distributes messages round-robin across all consumers attached to the queue. The exchange type should be `direct` (or `topic` for routing-key-based filtering), not `fanout`:

```go
// rabbitmq.go — Correct work queue consumer pattern in Go
package worker

import (
    "context"
    "fmt"
    "log"
    "time"

    amqp "github.com/rabbitmq/amqp091-go"
)

// WorkerConfig holds the RabbitMQ configuration for a work queue consumer.
type WorkerConfig struct {
    URL          string
    ExchangeName string        // "orders" (direct exchange)
    ExchangeType string        // "direct" or "topic"
    RoutingKey   string        // "orders.created"
    QueueName    string        // "orders.processing" — SHARED, not per-worker
    PrefetchCount int          // 1 = one message at a time (fairest distribution)
}

// StartWorker connects to RabbitMQ, declares the shared work queue,
// and begins consuming messages — one at a time, with manual acknowledgment.
func StartWorker(ctx context.Context, cfg WorkerConfig, handler func([]byte) error) error {
    conn, err := connectWithRetry(cfg.URL, 10)
    if err != nil {
        return fmt.Errorf("connecting to RabbitMQ: %w", err)
    }
    defer conn.Close()

    ch, err := conn.Channel()
    if err != nil {
        return fmt.Errorf("opening channel: %w", err)
    }
    defer ch.Close()

    // ── QoS: prefetch_count = 1 ───────────────────────────────────────────────
    // Tell RabbitMQ: send me only ONE unacknowledged message at a time.
    // Only after I ack a message will RabbitMQ send the next one.
    //
    // Without prefetch: RabbitMQ pre-loads all pending messages to each consumer.
    // A fast worker gets hundreds of messages in its buffer; a slow worker gets none.
    // Result: unfair distribution. Some workers overloaded, others idle.
    //
    // With prefetch=1: RabbitMQ sends the next message only after the previous is acked.
    // Result: fair distribution. Busy workers get fewer new messages. Idle workers get more.
    err = ch.Qos(
        cfg.PrefetchCount, // prefetch count: 1 = fairest distribution ✅
        0,                 // prefetch size: 0 = no limit on message size
        false,             // global: false = per-consumer (not per-channel)
    )
    if err != nil {
        return fmt.Errorf("setting QoS: %w", err)
    }

    // ── Declare the exchange (direct, not fanout) ─────────────────────────────
    err = ch.ExchangeDeclare(
        cfg.ExchangeName, // "orders"
        cfg.ExchangeType, // "direct" ← NOT "fanout" ✅
        true,             // durable: survives RabbitMQ restart
        false,            // auto-delete: don't delete when last consumer disconnects
        false,            // internal: not internal-only
        false,            // no-wait
        nil,
    )
    if err != nil {
        return fmt.Errorf("declaring exchange: %w", err)
    }

    // ── Declare the SHARED queue ──────────────────────────────────────────────
    // CRITICAL: all workers declare and consume from the SAME queue name.
    // The queue is not per-worker. It is the single shared work queue.
    // All workers compete for messages on this one queue.
    q, err := ch.QueueDeclare(
        cfg.QueueName,  // "orders.processing" — same name across ALL workers ✅
        true,           // durable: queue survives RabbitMQ restart
        false,          // auto-delete: do NOT auto-delete (workers may disconnect briefly)
        false,          // exclusive: false — MULTIPLE consumers allowed ✅
                        // (exclusive=true would be per-consumer, breaking the pattern)
        false,          // no-wait
        amqp.Table{
            // Dead letter exchange: messages that fail processing go here.
            "x-dead-letter-exchange":    "orders.dlx",
            "x-dead-letter-routing-key": "orders.dead",
            // Message TTL: 24 hours. Unprocessed messages expire.
            "x-message-ttl": int64(24 * time.Hour / time.Millisecond),
        },
    )
    if err != nil {
        return fmt.Errorf("declaring queue: %w", err)
    }

    // ── Bind the shared queue to the exchange with routing key ────────────────
    // With a direct exchange: only messages published with routing key "orders.created"
    // are delivered to this queue. Other routing keys are unaffected. ✅
    err = ch.QueueBind(
        q.Name,           // The shared queue name
        cfg.RoutingKey,   // "orders.created" — routing key for order events
        cfg.ExchangeName, // "orders" exchange
        false,
        nil,
    )
    if err != nil {
        return fmt.Errorf("binding queue: %w", err)
    }

    // ── Start consuming: competing consumer on the shared queue ──────────────
    // All worker instances consume from the same queue.
    // RabbitMQ delivers each message to exactly ONE consumer. ✅
    msgs, err := ch.Consume(
        q.Name,        // Shared queue
        "",            // Consumer tag: empty = auto-generated (unique per connection) ✅
        false,         // auto-ack: false — MANUAL acknowledgment ✅
                       // (auto-ack=true: message removed from queue before processing.
                       //  If worker crashes mid-processing: message is LOST. ❌)
        false,         // exclusive: false — allow competing consumers ✅
        false,         // no-local
        false,         // no-wait
        nil,
    )
    if err != nil {
        return fmt.Errorf("starting consumer: %w", err)
    }

    log.Printf("[Worker] Started consuming from shared queue %q. PrefetchCount: %d",
        q.Name, cfg.PrefetchCount)

    for {
        select {
        case <-ctx.Done():
            log.Printf("[Worker] Context cancelled. Shutting down gracefully.")
            return nil

        case msg, ok := <-msgs:
            if !ok {
                return fmt.Errorf("consumer channel closed unexpectedly")
            }

            // Process the message. If processing fails: Nack and requeue.
            // If processing succeeds: Ack to remove from queue.
            if err := handler(msg.Body); err != nil {
                log.Printf("[Worker] Processing failed: %v. Nacking message.", err)
                // Nack with requeue=true: message returns to queue for retry.
                // Nack with requeue=false: message goes to dead letter exchange.
                msg.Nack(false, true) // false=single message, true=requeue
                continue
            }

            // Ack: message successfully processed. Remove from queue. ✅
            // Only ONE worker sent this Ack — only ONE worker processed this message. ✅
            msg.Ack(false) // false = single message acknowledgment
        }
    }
}
```

```go
// producer.go — Publishing to the direct exchange with routing key
package producer

import (
    "context"
    "encoding/json"
    "fmt"

    amqp "github.com/rabbitmq/amqp091-go"
)

type OrderCreatedEvent struct {
    OrderID  uint64  `json:"order_id"`
    UserID   uint64  `json:"user_id"`
    Amount   float64 `json:"amount"`
}

// PublishOrderCreated publishes an order event to the direct exchange.
// Routing key "orders.created" matches the binding on the work queue.
// Only workers consuming "orders.processing" queue will receive this. ✅
func PublishOrderCreated(ch *amqp.Channel, event OrderCreatedEvent) error {
    body, err := json.Marshal(event)
    if err != nil {
        return fmt.Errorf("marshaling event: %w", err)
    }

    return ch.PublishWithContext(
        context.Background(),
        "orders",          // exchange name
        "orders.created",  // routing key ← matches queue binding ✅
        true,              // mandatory: return error if no queue bound ✅
        false,             // immediate
        amqp.Publishing{
            ContentType:  "application/json",
            DeliveryMode: amqp.Persistent, // Survives RabbitMQ restart ✅
            Body:         body,
            // Idempotency key: prevents duplicate processing if the
            // producer retries a publish that may have already succeeded.
            MessageId: fmt.Sprintf("order-%d", event.OrderID),
        },
    )
}
```

## 6. Idempotency — Defense in Depth Against Duplicates

Even with the correct work queue pattern, duplicate delivery can occur. RabbitMQ guarantees **at-least-once** delivery — a message may be redelivered if the consumer crashes after processing but before acknowledging. A consumer that processes a message and then crashes before calling `msg.Ack()` will have the message requeued and redelivered to another worker. If the processing is not idempotent — if processing the same message twice produces different side effects — the duplicate delivery becomes a data integrity problem.

The correct defense is to build idempotent handlers using a processing record stored in the database:

```go
// handler.go — Idempotent order processing handler
package handler

import (
    "context"
    "database/sql"
    "encoding/json"
    "errors"
    "fmt"
    "log"
)

var ErrAlreadyProcessed = errors.New("message already processed")

type OrderHandler struct {
    db     *sql.DB
    stripe StripeClient
    mailer Mailer
}

// ProcessOrder handles an order created event idempotently.
// If the message has been processed before (by a previous delivery attempt),
// it is acknowledged without re-processing. No duplicate side effects. ✅
func (h *OrderHandler) ProcessOrder(body []byte) error {
    var event OrderCreatedEvent
    if err := json.Unmarshal(body, &event); err != nil {
        return fmt.Errorf("unmarshaling event: %w", err)
    }

    return h.processIdempotent(context.Background(), event)
}

func (h *OrderHandler) processIdempotent(ctx context.Context, event OrderCreatedEvent) error {
    // ── Idempotency check: have we already processed this order? ─────────────
    // Use a database transaction to atomically check and mark as processing.
    // The idempotency key is the order_id — each order should be processed exactly once.
    tx, err := h.db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
    if err != nil {
        return fmt.Errorf("beginning transaction: %w", err)
    }
    defer tx.Rollback()

    var exists bool
    err = tx.QueryRowContext(ctx,
        `SELECT EXISTS(SELECT 1 FROM processed_messages WHERE message_id = $1)`,
        fmt.Sprintf("order-%d", event.OrderID),
    ).Scan(&exists)
    if err != nil {
        return fmt.Errorf("checking idempotency: %w", err)
    }

    if exists {
        // Already processed. Ack the message without re-processing.
        // This handles at-least-once redelivery gracefully. ✅
        log.Printf("[Handler] Order %d already processed. Skipping (idempotent ack).", event.OrderID)
        return nil
    }

    // ── Mark as processing (within the transaction) ───────────────────────────
    _, err = tx.ExecContext(ctx,
        `INSERT INTO processed_messages (message_id, processed_at) VALUES ($1, NOW())`,
        fmt.Sprintf("order-%d", event.OrderID),
    )
    if err != nil {
        return fmt.Errorf("recording processing: %w", err)
    }

    // ── Execute business logic (within the transaction where possible) ─────────
    _, err = tx.ExecContext(ctx,
        `UPDATE orders SET status='processing', updated_at=NOW() WHERE id=$1 AND status='pending'`,
        event.OrderID,
    )
    if err != nil {
        return fmt.Errorf("updating order status: %w", err)
    }

    if err := tx.Commit(); err != nil {
        return fmt.Errorf("committing transaction: %w", err)
    }

    // ── Side effects outside the transaction (after commit) ───────────────────
    // These are at-most-once operations. The idempotency record above ensures
    // they are not called again on redelivery.
    if err := h.stripe.CapturePayment(event.OrderID, event.Amount); err != nil {
        // Payment failed: the processed_message record is committed.
        // On redelivery: skipped (exists=true). Manual intervention required.
        log.Printf("[Handler] Payment capture failed for order %d: %v", event.OrderID, err)
        return err // Nack: message requeued for retry
    }

    if err := h.mailer.SendConfirmation(event.OrderID, event.UserID); err != nil {
        log.Printf("[Handler] Email failed for order %d: %v. Continuing.", event.OrderID, err)
        // Non-critical: log and continue. Don't fail the whole processing.
    }

    log.Printf("[Handler] Order %d processed successfully.", event.OrderID)
    return nil
}
```

## 7. Exchange Type Selection — The Decision Framework

```
              RabbitMQ Exchange Types — When to Use Each
              ==============================================

  FANOUT Exchange:
  ─────────────────────────────────────────────────────────────────────
  Delivery: ALL bound queues receive a copy of every message.
  Routing key: IGNORED. All bindings receive all messages.

  Use when: every subscriber needs every message.
  ✅ Real-time notifications pushed to all connected clients
  ✅ Cache invalidation broadcast to all service instances
  ✅ Audit log fanout to multiple logging destinations
  ✅ Event sourcing: broadcast domain events to multiple projectors
  ❌ NEVER for work queues: each worker creates its own queue → duplicates ❌

  DIRECT Exchange:
  ─────────────────────────────────────────────────────────────────────
  Delivery: queues whose binding key EXACTLY matches the routing key.
  Routing key: exact string match.

  Use when: route different types of messages to different queues.
  ✅ Work queues: all workers bind the same queue with the same key → one consumer
  ✅ Priority routing: "orders.high" → high-priority queue, "orders.low" → low-priority
  ✅ Service-specific routing: "email.send" → email service, "sms.send" → SMS service

  TOPIC Exchange:
  ─────────────────────────────────────────────────────────────────────
  Delivery: queues whose binding pattern matches the routing key.
  Routing key: dot-separated words. Patterns: * (one word), # (zero or more words).

  Use when: flexible routing with pattern matching.
  ✅ "orders.#" matches "orders.created", "orders.updated", "orders.cancelled"
  ✅ "*.critical.*" matches "payment.critical.retry", "auth.critical.lockout"
  ✅ Multi-tenant: "tenant.1234.orders" → tenant-specific queues

  HEADERS Exchange:
  ─────────────────────────────────────────────────────────────────────
  Delivery: based on message header attributes, not routing key.
  Use when: routing based on message metadata rather than topic.
  Rare in practice. Prefer topic exchange for most cases.

  ──────────────────────────────────────────────────────────────────────
  WORK QUEUE RULE:
  Always use DIRECT or TOPIC exchange + ONE shared queue + multiple consumers.
  NEVER use FANOUT for work distribution. FANOUT is broadcast, not distribution.
```

```
  │ All 2450 deliveries will be processed. ← DATA CORRUPTION ❌     │
  └─────────────────────────────────────────────────────────────────┘
```

## 9. The Golden Rule

> RabbitMQ's exchange type is an architectural decision that determines whether a message is a task to be done once or an event to be broadcast to everyone. A fanout exchange is a loudspeaker — every bound queue receives a copy of every message, regardless of how many consumers exist. Scaling consumers behind a fanout exchange does not distribute work; it multiplies processing, and each replica processes every message independently. This distinction is invisible when there is only one consumer — one consumer on one queue receives every message exactly once regardless of exchange type. The bug manifests when you scale to multiple consumers, each creating its own queue and binding it to the fanout exchange. The correct pattern for work distribution is a single shared queue bound to a direct or topic exchange, with all worker instances consuming from that same queue. RabbitMQ then delivers each message to exactly one available consumer, round-robin. The `prefetch_count=1` QoS setting is essential for fair dispatch — without it, RabbitMQ pre-loads messages into each consumer's buffer, giving some workers hundreds of pending messages while others are idle. Even with the correct exchange type and queue structure, implement idempotent handlers using a database-backed processing record, because RabbitMQ guarantees at-least-once delivery — a crash between processing and acknowledgment causes redelivery to another worker. The combination of a shared queue, prefetch=1, and idempotent handlers gives you correct, fair, and resilient work distribution at any scale.

Fanout is broadcast. Work queues are distribution. Choosing the wrong one silently multiplies your side effects by the number of workers you scale to.
