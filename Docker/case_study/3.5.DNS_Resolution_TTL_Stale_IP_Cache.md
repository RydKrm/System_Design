# DNS Resolution TTL — Stale IP Cache

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Telephone Directory That Never Gets Updated

Before the age of mobile phones, households and businesses relied on printed telephone directories — thick books published annually that listed every subscriber's name alongside their telephone number. The system worked well in a stable world: people rarely moved, businesses rarely changed their numbers, and a directory published in January was still largely accurate in December. But imagine a city that began growing at an explosive pace — thousands of new residents arriving every month, existing residents moving constantly, businesses opening and closing weekly. The printed directory, now outdated within days of publication, would lead callers to dial numbers that connected to entirely different people. A call intended for Dr. Chen's medical practice would connect to the apartment of someone who moved in after Dr. Chen relocated. The number in the book is real and was correct when it was printed. It is simply no longer correct for the entity the caller is trying to reach.

This is the DNS TTL stale cache problem in containerized environments, except the pace of change is not monthly but potentially per-minute. In Docker, every time a container is restarted, it may receive a different IP address from the subnet pool — its old IP is returned to the pool and a new one is assigned. Docker's embedded DNS resolver always knows the current mapping from service name to container IP, because it is the authoritative source of that information and updates it in real time. But any process that resolved the service name before the restart and cached the returned IP address continues using the old, now-invalid address until it re-resolves the name. During the window between the container restart and the next DNS re-resolution, connections to the stale IP fail with `connection refused`, `no route to host`, or simply hang until they time out.

## 2. How DNS TTL and Caching Work — The Intended Mechanism

The Time-To-Live value in a DNS response is a field that the DNS server includes in every answer record it returns. It represents the number of seconds for which the resolver receiving this response is permitted to cache the record before it must re-query the authoritative server. A TTL of 300 means the resolver may use the cached answer for up to five minutes. A TTL of 0 means the resolver must not cache the record at all and must re-query the authoritative server on every lookup. TTL values are a balance between performance — avoiding the latency of a DNS query on every operation — and freshness — ensuring that changes to DNS records are propagated to resolvers within a reasonable time.

Docker's internal DNS server — the resolver at `127.0.0.11` that we examined in the Service Discovery Confusion case study — returns DNS records for service names on Docker networks with a TTL of zero or a very small value. The intent is precisely to avoid stale caching: because container IPs can change when containers are restarted, Docker's DNS server signals to resolvers that its answers should not be cached for extended periods. This is the correct and intended behavior for a dynamic container environment.

The problem is that many runtime environments and application frameworks do not respect or faithfully implement DNS TTL values. They resolve a hostname once, store the resulting IP address in an internal data structure, and reuse that cached address for the lifetime of a connection pool, a process, or in the worst cases for the lifetime of the entire application process. The DNS TTL returned by Docker's resolver — instructing the client not to cache the result — is simply ignored.

```
              DNS TTL — Intended Flow vs. Caching Runtimes
              ===============================================

  Docker DNS Server (127.0.0.11):
  Query: "What is the IP of postgres?"
  Response:
    postgres. 0 IN A 172.20.0.3   ← TTL = 0: DO NOT CACHE
    (or TTL = 1 — cache for 1 second maximum)

  Well-behaved resolver (ideal):
  ──────────────────────────────────────────────────────────────────
  t=0s:    Resolves postgres → 172.20.0.3. Caches for 0 seconds.
  t=1s:    Needs to connect again. Re-resolves. Gets fresh IP.
  t=5s:    Container restarts. postgres gets new IP: 172.20.0.7
  t=6s:    Next resolution → 172.20.0.7 ✅ Always fresh. Never stale.

  Go's net.DefaultResolver (common behavior):
  ──────────────────────────────────────────────────────────────────
  t=0s:    Connection pool resolves postgres → 172.20.0.3.
           Stores 172.20.0.3 in internal dial cache. Uses it for all connections.
  t=5s:    Container restarts. postgres gets new IP: 172.20.0.7
           Docker DNS now returns 172.20.0.7 for queries.
  t=6s:    Connection pool: still using 172.20.0.3 (cached). No re-resolution.
  t=6s:    New connection attempt → 172.20.0.3 → connection refused ❌
  t=7s:    Another attempt → 172.20.0.3 → connection refused ❌
  t=8s:    And again → 172.20.0.3 → connection refused ❌
  ...
  t=30s:   Connection pool's error threshold reached → re-resolves
  t=30s:   172.20.0.7 returned → connections succeed ✅
  Duration of failure: 20-30 seconds of connection errors post-restart

  JVM (Java) with default security properties:
  ──────────────────────────────────────────────────────────────────
  t=0s:    JVM resolves postgres → 172.20.0.3. Caches INDEFINITELY.
           networkaddress.cache.ttl = -1 (default: cache forever)
  t=5s:    Container restarts. postgres gets new IP: 172.20.0.7
  t=6s:    JVM: 172.20.0.3 still cached. No re-resolution. EVER.
  Duration of failure: until the JVM process itself is restarted ❌
```

The JVM case deserves particular attention because it is the most severe. Java's security architecture originally included the indefinite DNS caching behavior as a security measure against DNS spoofing attacks, where an adversary might poison a DNS cache and redirect traffic from a legitimate server to a malicious one. If the JVM had already cached the correct IP, a spoofed DNS response could not redirect it. This security reasoning made sense in a world of static infrastructure. In a containerized environment where legitimate IP changes happen constantly and are expected, caching forever transforms a security feature into an operational catastrophe.

## 3. The Failure Timeline — What Post-Restart Errors Look Like in Practice

To understand the operational impact, consider the concrete failure timeline that occurs during a routine container restart — an operation that happens multiple times daily in any active development or deployment workflow. The postgres container is restarted due to a configuration change, a software update, or a crash recovery. The restart completes quickly — perhaps in two to five seconds. The container is healthy and accepting connections. But the Go application's connection pool has the old IP cached in its dialer, and the pool's existing connections to the old IP have been closed by the kernel when the old container's network namespace was destroyed.

```
              Post-Restart Failure Timeline — Go Connection Pool
              ====================================================

  t=0s:    System operator runs: docker-compose restart postgres
  t=0.1s:  Docker stops postgres container. Old IP 172.20.0.3 destroyed.
           All TCP connections to 172.20.0.3: RST sent. Pool connections closed.
  t=2s:    New postgres container starts. New IP: 172.20.0.7 assigned.
           postgres is healthy and listening on 172.20.0.7:5432.
           Docker DNS: "postgres" → 172.20.0.7 (updated immediately).
  t=3s:    Go app receives first request after restart.
           Pool has 0 open connections (all were RST'd when old container died).
           Pool attempts to open new connection.
           Dialer: looks up "postgres" → uses cached entry 172.20.0.3 ❌
           TCP SYN to 172.20.0.3:5432 → no host at that address → ETIMEDOUT
  t=3s:    HTTP request returns 500: "dial tcp 172.20.0.3:5432: i/o timeout" ❌
  t=4s:    Next request → same cached IP → same failure ❌
  t=5s:    Next request → same ❌
  ...
  t=25s:   Pool's connection retry attempts with cached IP accumulate.
           On some implementations: error count triggers re-resolution.
  t=25s:   Pool resolves "postgres" fresh → 172.20.0.7 ✅
  t=25.1s: Connection established. Service restored.
  t=25.2s: Users: 22 seconds of 500 errors on database-dependent endpoints.

  Metrics view during this window:
  ├── Error rate spike: 100% of DB-dependent endpoints failing
  ├── Latency spike: connection timeout (seconds) per request
  ├── No container health check alerts (postgres is healthy!)
  └── No Kubernetes pod restarts (app pod is healthy!)
  Engineer on call sees: spike in errors. No obvious infrastructure event.
  Cause: routine postgres restart that completed 22 seconds ago.
```

The mismatch between infrastructure state (postgres is healthy) and application behavior (returning 500s) is the defining characteristic of this failure mode. Every monitoring system shows green — the postgres container is healthy, the app container is healthy, the Docker network is healthy. But users are experiencing errors. Without understanding the DNS TTL caching behavior of the application runtime, an on-call engineer may restart the application container (which does fix the problem, because it forces a fresh DNS resolution on startup) without ever understanding why the restart was necessary. The restart masks the root cause without addressing it, and the problem will recur on the next postgres restart.

## 4. The Runtime-Specific Caching Behaviors — A Taxonomy

Different language runtimes and frameworks handle DNS TTL with dramatically different behaviors. Understanding which runtime you are working with and what its default caching behavior is allows you to predict the severity of the stale IP problem and choose the appropriate mitigation.

**Go** uses `net.DefaultResolver` which, depending on how it is compiled and configured, may use either the system's `cgo`-based resolver or Go's pure-Go resolver. The pure-Go resolver (used when `CGO_ENABLED=0`, which is standard for statically compiled Docker images) performs DNS resolution through the system's `resolv.conf` configuration and applies TTL-based caching internally. However, Go's connection pool — specifically `http.Transport`'s `DialContext` — caches resolved IP addresses in its internal dialer for the duration of a connection's lifetime. When connection pools are used with long-lived connections to databases (via `database/sql`'s connection pool), the resolved IP can be cached for the lifetime of those connections — which in healthy systems can be hours.

**Java (JVM)** has already been described as the most aggressive cacher. The default behavior with `networkaddress.cache.ttl = -1` means no re-resolution ever occurs for successfully resolved names. The fix is to set `networkaddress.cache.ttl = 5` (five seconds) and `networkaddress.cache.negative.ttl = 0` in the JVM security properties.

**Node.js** uses its own DNS implementation that does not cache results between individual `dns.lookup()` calls by default. The C library `getaddrinfo`, which Node.js uses through `libuv`, does not cache results. However, Node.js HTTP/HTTPS connection pooling in the `http.Agent` class keeps persistent connections open to resolved IP addresses, and those persistent connections bypass DNS lookup entirely for subsequent requests on the same connection. If a connection in the pool stays open to an old IP and the pool does not detect that the connection has been broken, it will continue using the stale connection.

**Python** (using the `requests` library with `urllib3` connection pooling) exhibits similar behavior to Node.js: `getaddrinfo` performs no caching, but connection pooling means that once a connection is established to a resolved IP, that IP is used for the lifetime of the connection regardless of DNS changes.

```
              DNS Caching Behavior — Runtime Comparison Matrix
              ==================================================

  Runtime / Library         Default Cache Policy         Severity
  ──────────────────────────────────────────────────────────────────
  Java JVM                  Forever (networkaddress       CRITICAL
                            .cache.ttl = -1 default)     JVM restart required ❌

  Go net.DefaultResolver    Process lifetime for          HIGH
  (with connection pool)    pooled connections             Minutes of errors ❌

  Node.js (http.Agent)      Per-connection (no DNS        MEDIUM
                            cache, but pool reuse)        Until connection breaks ⚠️

  Python (urllib3)          Per-connection                MEDIUM
                            (no DNS cache, pool reuse)    Until connection breaks ⚠️

  curl (CLI tool)           Never caches (one-shot)       NONE ✅
                            Re-resolves every call

  Docker Compose service    TTL=0 (intentional)           N/A
  DNS (127.0.0.11)          Always returns current IP     Source is always fresh ✅

  ──────────────────────────────────────────────────────────────────
  Rule: The problem is never Docker's DNS — it is always the client's
  caching of what Docker's DNS returned. Re-resolve to fix.
```

## 5. The Solutions — Re-Resolution Strategies by Runtime

The universal principle of the solution is: **re-resolve the DNS name on connection failure, before retrying**. Docker's DNS is the authoritative and always-current source of the service's current IP. The problem is exclusively on the client side — stale cached IPs. Any solution that causes the client to discard the cached IP and issue a fresh DNS query to `127.0.0.11` will retrieve the correct, current IP and allow connections to succeed.

**Go — Forcing Re-Resolution Per Connection Attempt**

The most robust Go solution configures the `http.Transport` or `database/sql` pool to resolve the hostname on every new connection rather than caching the resolved IP. For HTTP clients, this is achieved by providing a custom `DialContext` function that creates a new resolver on each call. For database connections, the `pgx` PostgreSQL driver and `database/sql` manage connection pools, but you can force re-resolution by implementing a custom dialer:

```go
// transport.go — HTTP transport that re-resolves DNS on every dial
package httpclient

import (
    "context"
    "net"
    "net/http"
    "time"
)

// NewFreshDNSTransport returns an http.Transport configured to
// perform a fresh DNS resolution on every new TCP connection.
// This prevents stale IP caching from causing post-restart failures
// in dynamic container environments.
func NewFreshDNSTransport() *http.Transport {
    return &http.Transport{
        // DialContext is called for each new connection in the pool.
        // By creating a new net.Resolver here rather than using the
        // cached resolver, we force a fresh DNS lookup on every dial.
        DialContext: func(ctx context.Context, network, addr string) (net.Conn, error) {
            // Split addr into host and port (addr is "hostname:port")
            host, port, err := net.SplitHostPort(addr)
            if err != nil {
                return nil, err
            }

            // Fresh resolver: does not use Go's default cached resolver.
            // Each call to LookupHost goes directly to the DNS server.
            resolver := &net.Resolver{
                PreferGo: true,
                Dial: func(ctx context.Context, network, address string) (net.Conn, error) {
                    // Connect directly to Docker's embedded DNS.
                    d := net.Dialer{Timeout: 2 * time.Second}
                    return d.DialContext(ctx, "udp", "127.0.0.11:53")
                },
            }

            // Perform fresh DNS lookup. Returns current container IPs.
            addrs, err := resolver.LookupHost(ctx, host)
            if err != nil {
                return nil, err
            }
            if len(addrs) == 0 {
                return nil, fmt.Errorf("no addresses found for host %s", host)
            }

            // Dial the freshly resolved address.
            d := net.Dialer{Timeout: 5 * time.Second}
            return d.DialContext(ctx, network, net.JoinHostPort(addrs[0], port))
        },
        MaxIdleConns:       100,
        IdleConnTimeout:    30 * time.Second,  // Short idle timeout: evict stale conns
        DisableKeepAlives:  false,
    }
}

// Usage:
client := &http.Client{
    Transport: NewFreshDNSTransport(),
    Timeout:   10 * time.Second,
}
```

For database connections in Go using `database/sql` with a pgx driver, a simpler and production-proven approach is to configure the pool with a short `MaxConnLifetime` — forcing the pool to periodically close and re-establish connections, which includes a fresh DNS resolution during the re-dial:

```go
// database.go — Short connection lifetime forces periodic re-resolution
db, err := sql.Open("pgx", os.Getenv("DB_URL"))
if err != nil {
    log.Fatalf("failed to open database: %v", err)
}

// MaxConnLifetime: close and re-establish each connection after 5 minutes.
// Re-establishment includes a fresh DNS lookup for the hostname.
// This bounds the maximum stale IP cache duration to 5 minutes.
db.SetMaxConnLifetime(5 * time.Minute)

// MaxConnIdleTime: close idle connections after 30 seconds.
// Idle connections are most likely to be pointing at stale IPs
// when the target container has restarted since the connection was opened.
db.SetConnMaxIdleTime(30 * time.Second)

// SetMaxOpenConns: bound the pool size to prevent connection storms
// during re-establishment after a container restart.
db.SetMaxOpenConns(25)
db.SetMaxIdleConns(5)
```


**Node.js — Connection Pool Idle Timeout**

```javascript
// For database connections (node-postgres pg library):
const { Pool } = require('pg');

const pool = new Pool({
    connectionString: process.env.DB_URL,

    // idleTimeoutMillis: close idle connections after 10 seconds.
    // When the next request needs a connection, the pool re-dials
    // the hostname, which includes a fresh DNS resolution.
    idleTimeoutMillis: 10_000,

    // connectionTimeoutMillis: fail fast if re-dial fails.
    // Triggers the retry logic faster than waiting for TCP timeout.
    connectionTimeoutMillis: 3_000,
});

// For HTTP calls (using got or node-fetch with agent):
const http = require('http');
const agent = new http.Agent({
    // keepAlive false: close connection after each request.
    // Eliminates pooled connection reuse — re-resolves on every request.
    // Trade-off: higher latency per request. Use only if stale IP is a real problem.
    keepAlive: false,
});
```

## 6. Retry with Fresh Lookup — The Universal Pattern

Regardless of the runtime, the most resilient pattern for handling stale IP failures is a connection retry loop that forces a fresh DNS resolution on each retry attempt. This pattern is language-agnostic and handles the post-restart error window gracefully from the application's perspective, converting what would otherwise be user-visible 500 errors into a brief, transparent internal retry:

```go
// retry.go — Universal retry with DNS re-resolution for Go
package retry

import (
    "context"
    "errors"
    "net"
    "time"
)

// WithDNSRefresh retries the given operation up to maxAttempts times.
// On each retry, it clears any cached DNS state and re-resolves the hostname.
// This pattern handles post-restart IP changes transparently to the caller.
func WithDNSRefresh(ctx context.Context, maxAttempts int, op func() error) error {
    var lastErr error
    for attempt := 1; attempt <= maxAttempts; attempt++ {
        if err := op(); err != nil {
            lastErr = err
            // Check if this is a network-level error (stale IP category)
            var netErr *net.OpError
            if errors.As(err, &netErr) {
                // Network error: likely stale IP after container restart.
                // Wait briefly, then retry — the next attempt will re-resolve
                // if the dialer is configured with fresh resolution.
                backoff := time.Duration(attempt) * 200 * time.Millisecond
                select {
                case <-time.After(backoff):
                case <-ctx.Done():
                    return ctx.Err()
                }
                continue
            }
            // Non-network error (e.g., SQL syntax error): don't retry
            return err
        }
        return nil // Success
    }
    return fmt.Errorf("all %d attempts failed, last error: %w", maxAttempts, lastErr)
}
```

## 7. The `resolv.conf` and `ndots` Interaction

A subtle related issue involves the `ndots` option in the container's `/etc/resolv.conf` file. The `ndots` setting controls how many dots must appear in a hostname before the resolver treats it as fully qualified and queries it directly, versus treating it as a relative name and appending the search domain suffixes first. Docker sets `ndots:0` in containers by default, which means all hostnames are treated as fully qualified and queried directly without search domain appending. This is the correct setting for Docker service name resolution.

However, applications that configure their own DNS resolver or override `/etc/resolv.conf` settings may inadvertently increase the `ndots` value, causing Docker service names to be appended with the container's search domains before the authoritative query is made. This introduces additional DNS round-trips and can cause the first lookup to fail before the resolver tries the unqualified name — adding latency on top of the stale cache problem. Verifying the `ndots` setting is an important step when debugging unexpected DNS resolution latency:

```bash
# Inspect DNS configuration inside a running container
docker exec <container> cat /etc/resolv.conf
# Expected output in a Docker container:
# nameserver 127.0.0.11
# options ndots:0

# If ndots is higher (e.g., ndots:5 from Kubernetes):
# First lookup: postgres.namespace.svc.cluster.local → NXDOMAIN
# Second lookup: postgres.svc.cluster.local → NXDOMAIN
# Third lookup: postgres.cluster.local → NXDOMAIN
# Fourth lookup: postgres → 172.20.0.7 ✅ (five extra DNS queries per resolution!)
# Each NXDOMAIN round-trip adds ~1ms. Under load: significant latency.

# Kubernetes-specific: use fully qualified service names to bypass ndots appending
# Instead of: postgres:5432
# Use: postgres.my-namespace.svc.cluster.local:5432
# This bypasses all search domain appending and resolves on the first query.
```

## 8. Monitoring and Detecting Stale IP Issues in Production

The characteristic metric signature of a stale IP cache problem is a short burst of connection errors following a container restart, with a clean return to normal behavior after 20 to 60 seconds. This signature distinguishes the stale IP problem from other failure modes: a crashed database produces sustained errors, a network partition produces sustained errors with no recovery, a code deployment bug produces a different error class entirely. The transient, self-resolving nature of the stale IP spike — combined with a recent container restart event in the deployment log — is the fingerprint to look for.

```
              Metric Signature — Stale IP Post-Restart Spike
              =================================================

  DB connection error rate over time:

  Normal:   ▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁
                                                  ▲
                                             postgres restart
                                                  │
  Spike:    ▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁█████▁▁▁▁▁▁▁
                                                  ↑   ↑
                                               t=0s  t=25s
                                           (restart) (recovery)

  Key characteristics that indicate stale IP (not other failure):
  ├── Duration: 15-60 seconds (not indefinite)
  ├── Recovery: clean and sudden (not gradual)
  ├── Correlation: matches a container restart event exactly
  ├── Error type: "connection refused" or "i/o timeout" (not "query failed")
  ├── Target: single upstream service (not all dependencies simultaneously)
  └── Health checks: all green throughout (misleadingly so)

  Recommended alert:
  Alert when: connection_error_rate > 1% for 10 seconds
  AND: recent container restart event within 60 seconds
  → Likely stale DNS cache. Check runtime DNS TTL configuration.
```

## 9. The Golden Rule

> In dynamic container environments, a DNS name is a stable identifier but the IP address it resolves to is ephemeral. Every container restart can produce a new IP address. Any application component that caches a resolved IP address — whether through the JVM's indefinite DNS cache, Go's connection pool dialer, or any other runtime mechanism — will experience connection failures for the duration of its cache TTL after a container restart. Docker's embedded DNS resolver at `127.0.0.11` always returns the current, correct IP for any service name, but it can only help you if you ask it. The solutions exist at every layer: configure your runtime's DNS cache TTL to a small value (five seconds or less), set a short `MaxConnLifetime` on database connection pools to force periodic re-dial, implement retry logic that re-resolves the hostname on network errors, and for Java, explicitly set `networkaddress.cache.ttl=5` in JVM security properties. The cardinal rule is: on connection failure, discard the cached IP, re-resolve the DNS name, and retry. Docker's DNS will give you the right answer. Trust it, and ask it again.

A post-restart error spike that resolves itself in 30 seconds is not a flaky network — it is a stale DNS cache. Fix the TTL, not the network.
