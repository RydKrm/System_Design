# No Resource Limits — Container Kills the Host

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Tenant Who Floods the Building

Imagine a six-unit apartment building where the landlord, in a gesture of trust, installs no water pressure regulators on individual apartments. Each tenant shares the building's common water main. The building has enough water pressure for all six apartments to run their taps simultaneously at normal usage. One day, Tenant 3 has a plumbing malfunction — a burst pipe begins flooding water at maximum pressure, continuously, without shutting off. Within minutes, the water pressure for the entire building drops to near zero. Tenants 1, 2, 4, 5, and 6 turn on their taps and get nothing. Their appliances malfunction. Their pipes run dry. The landlord receives six simultaneous calls about water failures, when the root cause is a single unregulated tenant whose pipe failure consumed the common resource.

This is the architecture of an unconstrained Docker deployment on a shared host: multiple containers sharing the host's RAM and CPU, with no boundaries between them. The host's Linux kernel is the water main. Memory is the water pressure. A container that develops a memory leak — a Go service with a goroutine accumulation, a Node.js application retaining large JSON objects in a closure, a Redis misconfiguration loading an enormous dataset into RAM — consumes memory continuously, without any limit stopping it, until the host kernel's Out-of-Memory killer activates. The OOM killer does not selectively kill the misbehaving container. It kills whichever process the kernel scores as the best candidate for termination, which is frequently not the leaking service but rather PostgreSQL or Redis — processes that happen to be large in memory at the moment of the kill decision. The leaking service survives. The database dies. Data may be corrupted. And the engineers who receive the alert see a dead database, not a memory-leaking API server.

## 2. The Linux OOM Killer — How It Chooses Its Victims

The Out-of-Memory killer is a component of the Linux kernel that activates when the system has exhausted all available physical memory and swap space and a memory allocation cannot be satisfied. Its job is to select one or more processes to terminate in order to free enough memory for the system to continue functioning. The OOM killer does not have business domain knowledge — it does not know that PostgreSQL is more important than your API server, that Redis holds critical session state, or that the container causing the allocation pressure is the guilty party. It applies a scoring algorithm based on heuristics that estimate the value of killing each process.

The OOM score for a process is calculated from the process's current memory usage relative to available memory, adjusted by a configured `oom_score_adj` value that can weight processes as more or less likely to be killed. Processes with high memory usage and neutral `oom_score_adj` values are the most likely victims. A well-tuned PostgreSQL instance, holding gigabytes of shared memory buffers and active data, presents a high memory footprint and thus a high OOM score — making it a prime target for the OOM killer, even though it is behaving perfectly correctly and the API container causing the leak has a much smaller footprint because it is adding memory slowly and has not yet reached the same magnitude.

```
              OOM Killer Scoring — Why the Database Dies First
              ==================================================

  Host: 8 GB RAM total. No swap. No container memory limits.

  Memory footprint at the moment of OOM condition:

  Container          Process            RSS (Resident Set Size)   OOM Score
  ──────────────────────────────────────────────────────────────────────────
  postgres_container  postgres            3.8 GB (shared_buffers   HIGH ❌
                                          + active data)           Victim candidate
  redis_container     redis               1.2 GB (dataset in RAM)  MEDIUM ⚠️
                                                                   Victim candidate
  api_container       node (leaking)      1.5 GB (leaking, growing) MEDIUM
                                                                   CAUSING the leak
  worker_container    node                200 MB (normal)          LOW
  nginx_container     nginx               50 MB (normal)           VERY LOW

  Total: 6.75 GB / 8 GB. Allocation that pushed over the edge: api container
  requesting another 1.3 GB in a burst → total demand: 8.05 GB → OOM triggered.

  OOM Killer decision:
  ├── Scores all processes by memory footprint + oom_score_adj
  ├── postgres has highest actual RSS: 3.8 GB → HIGHEST OOM score
  ├── OOM Killer selects: postgres ← KILLED ❌
  ├── Memory freed: 3.8 GB. OOM condition resolved.
  └── api container: still running, still leaking. Root cause survives. ❌

  Aftermath:
  ├── PostgreSQL: killed mid-transaction. WAL may be inconsistent.
  ├── Recovery on restart: WAL replay (1-5 minutes).
  ├── Any uncommitted transactions: rolled back (data loss possible).
  ├── api container: continues leaking. Will trigger OOM again in hours.
  └── Engineers: receive "PostgreSQL down" alert. Investigate database.
      Find nothing wrong with PostgreSQL itself. Root cause: invisible.
```

The scenario where the victim is the wrong process — the database killed to relieve pressure caused by the application — is not an edge case. It is the predictable outcome of the OOM scoring algorithm in the typical memory footprint distribution of a web application stack. PostgreSQL and Redis, by design, hold large amounts of data in RAM for performance. Their memory footprints are large and stable. A leaking application grows slowly before triggering the OOM condition, often still smaller in absolute bytes than the database at the moment of the kill. The OOM killer kills the largest process, which is the database.

## 3. How Containers Share Host Memory Without Limits

Every container on a Docker host, unless explicitly constrained, has access to the entirety of the host's physical memory. This is not a Docker design flaw — it is a consequence of how the Linux kernel manages cgroups and memory allocation. Docker uses cgroups to implement resource limits, but cgroup memory limits are opt-in. Without a memory limit configured on a container, the container's cgroup has no upper bound on memory allocation. The container's processes can allocate as much memory as the kernel will provide, up to the total physical RAM plus any configured swap.

When multiple containers share a host without memory limits, the total memory demand across all containers can arbitrarily exceed the host's physical RAM. The kernel manages this through paging — moving less recently used memory pages to swap space — but when swap is exhausted as well, the kernel has no options remaining and activates the OOM killer. The entire host's stability depends on all containers behaving within their fair share of memory, which is a trust arrangement enforced by nothing.

```
              Memory Allocation Without Limits — The Trust Architecture
              =============================================================

  Host: 8 GB RAM, 2 GB swap (10 GB total addressable)

  Container memory allocations over time (no limits):

  t=0h:    postgres:  3.5 GB  redis: 1.0 GB  api: 256 MB  Total: 4.76 GB ✅
  t=4h:    postgres:  3.5 GB  redis: 1.0 GB  api: 512 MB  Total: 5.01 GB ✅
  t=8h:    postgres:  3.5 GB  redis: 1.1 GB  api: 1.2 GB  Total: 5.8 GB  ✅
  t=12h:   postgres:  3.6 GB  redis: 1.1 GB  api: 2.4 GB  Total: 7.1 GB  ✅
  t=14h:   postgres:  3.6 GB  redis: 1.1 GB  api: 3.5 GB  Total: 8.2 GB  ⚠️ swap
  t=15h:   postgres:  3.6 GB  redis: 1.1 GB  api: 4.6 GB  Total: 9.3 GB  ⚠️ swap
  t=15.5h: postgres:  3.6 GB  redis: 1.1 GB  api: 5.1 GB  Total: 9.8 GB  ⚠️ swap heavy
  t=15.8h: New allocation request: api requests 300 MB.
           Physical RAM + swap: 10 GB. Current: 9.8 GB. Request: 300 MB.
           9.8 + 0.3 = 10.1 GB > 10 GB. Cannot satisfy. OOM condition. ❌
           OOM Killer activates. Largest process: postgres (3.6 GB) → KILLED.

  With memory limits configured (correct):

  postgres: limit 4 GB   redis: limit 1.5 GB   api: limit 1 GB
  Total maximum: 6.5 GB < 8 GB host RAM (1.5 GB headroom)

  t=15.8h: api's leak has consumed its entire 1 GB limit.
           api: next allocation request fails.
           api container: OOMKilled (only this container) ✅
           postgres: still running. Redis: still running. ✅
           Kubernetes/Compose: restarts api container (fresh, no leak). ✅
           Engineers: receive "api OOMKilled" alert. Investigate api. ✅
           Root cause: visible, contained, and correctly attributed. ✅
```

The contrast between the two scenarios reveals the purpose of resource limits: they transform a host-wide catastrophic failure into a contained, correctly-attributed, self-recovering single-container failure. The container with the memory leak is killed. The correct container is killed. The other services on the host are unaffected. The monitoring system generates an alert pointing at the correct service. The on-call engineer investigates the correct service. The container restarts from a clean state, clearing the leak temporarily, while the underlying bug is investigated. This is the resilience model that containerization is supposed to enable.

## 4. Configuring Resource Limits in Docker Compose

Docker Compose provides two levels of resource constraints: **limits** (hard ceiling — the container is killed if it exceeds this) and **reservations** (soft floor — the scheduler uses this to guarantee minimum availability). Both are configured under the `deploy.resources` key in Compose format v3 and above:

```yaml
# docker-compose.yml — Production resource limits for a typical web stack

version: "3.9"

services:
  nginx:
    image: nginx:1.25-alpine@sha256:...
    deploy:
      resources:
        limits:
          memory: 128m      # nginx is memory-efficient; 128 MB is generous
          cpus: "0.25"      # 25% of one CPU core is more than enough
        reservations:
          memory: 64m       # Guarantee at least 64 MB for scheduler placement
          cpus: "0.10"
    restart: unless-stopped

  api:
    build: .
    deploy:
      resources:
        limits:
          # Set the limit to the maximum memory your application legitimately needs
          # under peak load, with a reasonable safety margin (~20-30% above observed peak).
          # If the app exceeds this due to a leak: it is killed, not your database.
          memory: 1g        # 1 GB hard limit
          cpus: "1.0"       # 1 full CPU core
        reservations:
          memory: 256m      # Guarantee 256 MB for baseline operation
          cpus: "0.25"
    restart: unless-stopped

  worker:
    build: .
    command: ["node", "worker.js"]
    deploy:
      resources:
        limits:
          memory: 512m
          cpus: "0.5"
        reservations:
          memory: 128m
          cpus: "0.10"
    restart: unless-stopped

  postgres:
    image: postgres:16.2-alpine3.19@sha256:...
    environment:
      POSTGRES_SHARED_BUFFERS: 512MB    # Must be < memory limit
      POSTGRES_EFFECTIVE_CACHE_SIZE: 1GB
    deploy:
      resources:
        limits:
          # PostgreSQL's shared_buffers + work_mem × max_connections
          # must be less than this limit. Set limit to 2× shared_buffers
          # as a safe starting point.
          memory: 2g
          cpus: "2.0"
        reservations:
          memory: 512m
          cpus: "0.5"
    restart: unless-stopped

  redis:
    image: redis:7.2-alpine3.19@sha256:...
    command: >
      redis-server
      --maxmemory 768mb
      --maxmemory-policy allkeys-lru
    deploy:
      resources:
        limits:
          # Set slightly above Redis's own maxmemory to account for overhead.
          # Redis has its own memory limit; this is a belt-and-suspenders guard.
          memory: 1g
          cpus: "0.5"
        reservations:
          memory: 256m
          cpus: "0.10"
    restart: unless-stopped

# Host RAM budget summary (8 GB host):
# nginx:    max 128 MB
# api:      max 1 GB
# worker:   max 512 MB
# postgres: max 2 GB
# redis:    max 1 GB
# ─────────────────
# Total:    max 4.64 GB / 8 GB available
# Headroom: 3.36 GB (42%)  ← Safe. OS, kernel, Docker daemon also need RAM.
```

The headroom percentage deserves explicit attention. The total of all container memory limits should not equal the host's physical RAM. The host operating system, the Docker daemon, the container runtime, and kernel buffers all require memory. A host with 8 GB RAM running containers with a combined limit of 7.8 GB will still experience OOM conditions when all containers simultaneously reach their limits, because there is nothing left for the OS. A safe rule of thumb is to allocate no more than 70% of host RAM to container limits in aggregate, leaving 30% as operating headroom.

## 5. Understanding Container Memory Metrics — RSS vs Virtual Memory

When setting memory limits, it is important to understand what Docker and the Linux kernel actually measure and constrain. The `memory` limit in Docker applies to the **RSS** (Resident Set Size) — the amount of physical RAM currently occupied by the process's pages that are present in memory. It does not apply to virtual memory (VSZ), which includes memory-mapped files, shared libraries, and pages that have been swapped out. For most application processes, RSS is the meaningful measure of actual physical memory consumption.

```
              Memory Measurement Concepts — What the Limit Actually Constrains
              =================================================================

  Process memory layout (Linux):
  ┌─────────────────────────────────────────────────────────────────┐
  │  Virtual Address Space (VSZ — may be GBs, not limited by Docker)│
  │  ┌────────────────────────────────────────────────────────────┐ │
  │  │ Resident Set (RSS — pages actually in RAM right now)        │ │
  │  │ ← Docker memory limit constrains THIS ←                    │ │
  │  │  ┌──────────────────────────────────────────────┐          │ │
  │  │  │ Anonymous pages (heap, stack, mmap private)  │          │ │
  │  │  │  ← What your application's data lives in     │          │ │
  │  │  └──────────────────────────────────────────────┘          │ │
  │  │  ┌──────────────────────────────────────────────┐          │ │
  │  │  │ File-backed pages (shared libs, mmapped files)│          │ │
  │  │  └──────────────────────────────────────────────┘          │ │
  │  └────────────────────────────────────────────────────────────┘ │
  │  Swapped pages (on disk — not in RAM, not counted in RSS)       │
  └─────────────────────────────────────────────────────────────────┘

  Docker memory limit behavior:
  Container RSS < memory limit:    Normal operation ✅
  Container RSS = memory limit:    Kernel begins applying memory pressure
                                   Process may be asked to release pages (oom_score)
  Container RSS > memory limit:    Container is OOMKilled ❌
                                   Exit code: 137 (SIGKILL from OOM killer)
                                   docker stats: shows "OOMKilled: true"

  Reading memory stats:
  docker stats <container>
  # CONTAINER   CPU %   MEM USAGE / LIMIT       MEM %    NET I/O       BLOCK I/O
  # api         12.3%   834MiB / 1GiB            81.5%   ...
  #                     ↑ current RSS   ↑ limit
  # At 81.5%: approaching limit. Investigate if unexpected. ⚠️

  Detecting OOMKill after the fact:
  docker inspect <container> --format='{{.State.OOMKilled}}'
  # true  ← This container was killed by the OOM killer ← memory leak confirmed
```

## 6. CPU Throttling — The Less Dramatic But Equally Important Limit

While memory exhaustion produces the most dramatic failure mode — other containers dying — CPU exhaustion produces a more insidious failure: universal latency degradation. A container consuming 100% of CPU cycles starves other containers of their compute time, causing all services on the host to become slow simultaneously. Unlike memory exhaustion, CPU exhaustion does not kill processes — it slows them, producing timeouts, missed health checks, increased response latency, and request queue buildup across the entire host.

The `cpus` limit in Docker is implemented as a cgroup CPU quota. A setting of `cpus: "1.0"` means the container can use the equivalent of one full CPU core — but if the host has 8 cores, this is one eighth of the total compute. The container is not pinned to a specific core; it can run on any core, but its total CPU time over any 100ms scheduling period is capped at 100ms (one core-equivalent). If the container attempts to use more, the scheduler throttles it — suspending the container's processes for the remainder of the scheduling period.

```
              CPU Throttling — Quota vs. Shares
              =====================================

  Host: 8 CPU cores, 4 containers, no CPU limits (wrong):
  Each container can burst to 100% of all 8 cores simultaneously.
  Total CPU demand: up to 800% (8 cores × 100%).
  Result: scheduler round-robins at process level. All containers slow. ❌

  With CPU limits configured (correct):
  api:      cpus: "1.0"   (100ms CPU per 100ms window, any core)
  worker:   cpus: "0.5"   (50ms CPU per 100ms window)
  postgres: cpus: "2.0"   (200ms CPU per 100ms window)
  redis:    cpus: "0.5"   (50ms CPU per 100ms window)
  Total:    cpus: "4.0"   (400ms / 100ms window = 4 core-equivalents / 8 available)

  If api has a CPU-intensive bug (e.g., infinite JSON serialization loop):
  Without limits: api takes 8 cores. postgres, redis get near-zero time. ❌
  With limits:    api throttled to 1 core. postgres gets its 2 cores. ✅
                  Redis gets its 0.5 cores. Services remain responsive. ✅
                  api becomes slow (throttled) but is the CORRECT service to slow. ✅

  Checking CPU throttling:
  docker stats
  # CONTAINER   CPU %   ...
  # api         99.9%   ← At limit. Being throttled.
  #                       High CPU % approaching cpus limit = investigate.
```

## 7. Monitoring Resource Usage — `docker stats` and cAdvisor

Resource limit configuration is incomplete without monitoring that alerts when containers approach their limits. Docker provides built-in resource monitoring through `docker stats`, and the Prometheus ecosystem provides the `cAdvisor` (Container Advisor) agent for production-grade metric collection and alerting.

```bash
# ── docker stats — Real-time resource monitoring ──────────────────────────────
# One-shot snapshot (good for quick checks):
docker stats --no-stream
# CONTAINER   CPU %   MEM USAGE / LIMIT   MEM %   NET I/O     BLOCK I/O   PIDS
# api         8.2%    423MiB / 1GiB       41.3%   1.2MB / 800kB  0B / 0B   12
# postgres    2.1%    1.2GiB / 2GiB       60.0%   400kB / 200kB  50MB / 10MB  45
# redis       0.3%    512MiB / 1GiB       50.0%   200kB / 100kB  0B / 0B   4

# Watch continuously:
docker stats

# Check if any container was OOMKilled:
docker ps -a --format "{{.Names}}: OOMKilled={{.Status}}" | grep -i oom
# Or inspect specifically:
for name in $(docker ps --format '{{.Names}}'); do
    oom=$(docker inspect $name --format='{{.State.OOMKilled}}')
    echo "$name: OOMKilled=$oom"
done
```

```yaml
# docker-compose.yml — cAdvisor for Prometheus metrics collection

services:
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:v0.47.0
    privileged: true          # Needs host-level access to read cgroup stats
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:rw
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
      - /dev/disk/:/dev/disk:ro
    ports:
      - "127.0.0.1:8080:8080"  # Metrics endpoint: http://localhost:8080/metrics
    devices:
      - /dev/kmsg
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 256m   # cAdvisor itself needs limits too ✅
          cpus: "0.25"
```

```yaml
# Prometheus alert rules for container resource limits:
groups:
  - name: container_resources
    rules:
      # Alert when a container uses more than 80% of its memory limit
      - alert: ContainerMemoryUsageHigh
        expr: >
          (container_memory_rss{name!=""} /
           container_spec_memory_limit_bytes{name!=""}) > 0.80
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Container {{ $labels.name }} memory usage above 80%"
          description: "Memory at {{ $value | humanizePercentage }} of limit. Possible leak."

      # Alert when a container is being CPU throttled significantly
      - alert: ContainerCpuThrottlingHigh
        expr: >
          rate(container_cpu_throttled_seconds_total{name!=""}[5m]) /
          rate(container_cpu_usage_seconds_total{name!=""}[5m]) > 0.25
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "Container {{ $labels.name }} CPU throttling >25%"
          description: "Container is CPU-throttled. May need higher cpus limit or optimization."

      # Alert on OOMKill event
      - alert: ContainerOOMKilled
        expr: kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} > 0
        labels:
          severity: critical
        annotations:
          summary: "Container {{ $labels.container }} was OOMKilled"
          description: "Memory limit too low or memory leak detected. Investigate immediately."
```

## 8. Setting the Right Limits — Sizing Methodology

The most common mistake after understanding the need for limits is setting them too low, causing containers to be OOMKilled under normal peak load, or too high, defeating the purpose of isolation. The correct methodology is empirical: measure first, then limit.

```bash
# Step 1: Run without limits in a staging environment under realistic load
# Step 2: Observe peak memory and CPU usage during load tests:
docker stats --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}" --no-stream

# Step 3: Set limits at peak_observed + 30% safety margin

# Example observations under peak load test:
# api:      CPU: 45%, Memory: 680 MiB peak
# worker:   CPU: 30%, Memory: 310 MiB peak
# postgres: CPU: 80%, Memory: 1.4 GiB peak
# redis:    CPU: 10%, Memory: 620 MiB peak

# Calculated limits (peak + 30%):
# api:      memory: 884m → round up to: 1g     cpus: "0.6" → round to: "1.0"
# worker:   memory: 403m → round up to: 512m   cpus: "0.4" → round to: "0.5"
# postgres: memory: 1.82g → round up to: 2g    cpus: "1.04" → round to: "2.0"
# redis:    memory: 806m → round up to: 1g     cpus: "0.13" → round to: "0.5"

# Step 4: Deploy with limits. Monitor OOMKill rate.
# OOMKilled frequently: limit is too low for real traffic → increase
# Memory usage always < 50% of limit: limit may be too high → reduce for tighter isolation

# Step 5: Set memory reservations at typical (non-peak) usage:
# This helps the scheduler understand the container's baseline footprint.
# api reservation: 256m (typical), limit: 1g (peak)
```

## 9. The Golden Rule

> A container without resource limits is a process with unlimited access to the host's CPU and RAM, separated from other containers only by namespace isolation — not by resource isolation. The entire value proposition of containerization for multi-tenant deployments is resource isolation: the guarantee that one service's misbehavior cannot degrade or destroy other services on the same host. Without `memory` and `cpus` limits, this guarantee does not exist. A memory leak in one service activates the Linux OOM killer, which kills processes based on memory footprint rather than culpability — and the largest process, typically the database, is killed first while the leaking service survives. Always set memory limits on every container, sized at peak observed usage plus a 30% safety margin. Always set the aggregate of all container limits to no more than 70% of host RAM, leaving headroom for the operating system and Docker daemon. Set Redis's `maxmemory` inside the Redis configuration to stay below the container's memory limit. Set PostgreSQL's `shared_buffers` to fit within the container's memory limit. Monitor memory usage as a percentage of the limit using `docker stats` or cAdvisor, and alert at 80% to give time to investigate before the container reaches 100% and is killed. Resource limits transform a host-wide catastrophic failure into a contained, correctly-attributed, self-recovering single-container event. That transformation is the difference between an incident that resolves itself and one that takes down your entire production stack.

Containers are not isolated by default. Resource limits are the enforcement mechanism. Apply them to every container, every time.
