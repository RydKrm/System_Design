# The Exposed vs Published Port Confusion

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Unmarked Door in the Walled Garden

Imagine a large private estate surrounded by a high perimeter wall. Inside the wall are several buildings: a main house, a greenhouse, and a workshop. The residents of these buildings move freely between them through a network of internal pathways — the main house can visit the greenhouse, the greenhouse can deliver produce to the workshop, and all of them communicate through a shared internal courtyard. None of the outside world can see or reach any of these internal buildings; the perimeter wall ensures complete separation.

Now imagine that one of the buildings has a door on its exterior wall facing inward to the courtyard, and the architect has placed a small sign next to that door that reads "entrance." The sign is informational — it tells anyone inside the courtyard that this door exists and that people are expected to enter here. But the sign does not create a corresponding door in the perimeter wall. The outside world still cannot reach the building. The sign is purely documentation for those already inside the estate.

This is precisely the distinction between Docker's `EXPOSE` instruction and port publishing. The `EXPOSE` instruction in a Dockerfile is the sign on the interior door — a piece of documentation intended for people who are already inside the Docker network, informing them which port the service listens on. It does not create any opening in the perimeter wall, which is the host machine's network interface. It does not bind any port on the host. It does not make the container reachable from outside the Docker network in any way whatsoever. Port publishing — through `-p` on `docker run` or `ports:` in Docker Compose — is the act of cutting a corresponding door in the perimeter wall and routing traffic from the outside world through it into the container.

## 2. What `EXPOSE` Actually Does — Documentation and Metadata

When Docker was first designed, the `EXPOSE` instruction served two loosely related purposes, both of which have become less relevant over time as Docker's networking model has matured. Understanding both purposes helps clarify why the instruction exists at all and why it is so commonly misunderstood.

The first purpose of `EXPOSE` is **image metadata documentation**. When you include `EXPOSE 6379` in a Redis Dockerfile, you are recording in the image manifest that the service inside this image listens on port 6379. Anyone who inspects the image with `docker inspect` can read this metadata and understand which port to map when running the container. Tools like `docker-compose` and container orchestration platforms can read this metadata programmatically. This is useful as a communication mechanism between the image author and the image consumer — it says, "if you want to use this service, you will need to interact with port 6379."

The second purpose, which applied to an older and now deprecated Docker feature called the **legacy link system**, was that `EXPOSE` granted linked containers knowledge of which ports to expect. In the early Docker networking model before user-defined networks existed, containers were connected through `--link` flags that created environment variable injections and basic DNS aliases between containers. `EXPOSE` was part of this mechanism. That system has been deprecated and replaced by user-defined networks with DNS-based service discovery, making this second purpose entirely historical.

```
              What EXPOSE Does vs. What It Does NOT Do
              ==========================================

  Dockerfile:
  FROM redis:7.2-alpine
  EXPOSE 6379          ← This line

  What EXPOSE DOES:
  ──────────────────────────────────────────────────────────────────
  ✅ Adds port 6379 to the image manifest metadata
  ✅ Visible in: docker inspect redis:7.2 → ExposedPorts → "6379/tcp":{}
  ✅ Shows in: docker ps → PORTS column shows "6379/tcp" (without binding)
  ✅ Informs operators which port the service uses (documentation)
  ✅ Allows --publish-all (-P) to know which ports to randomly assign

  What EXPOSE DOES NOT DO:
  ──────────────────────────────────────────────────────────────────
  ❌ Does NOT bind any port on the host machine
  ❌ Does NOT publish the port to the outside world
  ❌ Does NOT make the container reachable from the host
  ❌ Does NOT create any firewall rule
  ❌ Does NOT affect container-to-container networking in any way
  ❌ Does NOT require any port to actually be listening

  Proof:
  $ docker run -d --name redis redis:7.2-alpine
  $ redis-cli -h 127.0.0.1 -p 6379 ping
  Could not connect to Redis at 127.0.0.1:6379: Connection refused ❌

  $ docker exec redis redis-cli ping
  PONG ✅  (works because exec runs inside the container's network namespace)
```

The observable evidence of this distinction is precisely the symptom described in the case study summary. A developer pulls the official Redis image, which contains `EXPOSE 6379` in its Dockerfile. They run the container with `docker run -d redis:7.2-alpine`. They open their Redis desktop client — perhaps RedisInsight, TablePlus, or their own application running on the host — and attempt to connect to `localhost:6379`. The connection is refused. They then run `docker exec redis redis-cli ping` and receive `PONG` immediately. The Redis server is clearly running and responding. The container is alive. But the port is not reachable from the host because `EXPOSE` never created a binding on the host network interface — it only documented the port for intra-Docker-network use.

## 3. The Three Distinct Connectivity Zones in Docker Networking

To understand the full implications of this distinction, you must build a mental model of the three distinct connectivity zones in a Docker deployment, each with different access characteristics, different mechanisms for communication, and different security implications.

The first zone is the **container's own internal network namespace**. Within this zone, the process running inside the container can reach any port on its own loopback interface (`127.0.0.1`) or on its container-local network interface. This zone is always accessible through `docker exec`, which attaches your terminal to a process running inside the container's network namespace. The `docker exec redis redis-cli ping` command works precisely because it runs the `redis-cli` binary inside the same network namespace as the Redis server, where `127.0.0.1:6379` is a locally-bound address.

The second zone is the **Docker network** — the virtual bridge or overlay network that Docker creates and manages, connecting containers to each other. Within this zone, containers on the same user-defined network can reach each other using their service names or IP addresses. `EXPOSE` is relevant to this zone in the historical sense, but modern Docker networking makes all ports accessible across the network regardless of whether they are `EXPOSE`d. The `EXPOSE` instruction has no functional effect on container-to-container communication on user-defined networks.

The third zone is the **host and external network** — the physical or virtual network interface of the machine running Docker. This zone is where your laptop's browser, your database GUI tool, your monitoring agent, and the external internet live. To make a container port reachable from this zone, you must explicitly **publish** the port — creating a binding on the host's network interface and a NAT rule that forwards traffic from that host port to the container port.

```
              Three Connectivity Zones — Visual Architecture
              ================================================

  ZONE 3 — External World (Internet, host tools, host processes)
  ╔══════════════════════════════════════════════════════════════╗
  ║  Your browser, curl, TablePlus, redis-cli on host          ║
  ║  Host IP: 192.168.1.100                                     ║
  ║                                                              ║
  ║  Can reach:                                                  ║
  ║  ├── Host ports that Docker has published: ✅               ║
  ║  └── Only through published port mappings                   ║
  ╚═══════════════════════╦══════════════════════════════════════╝
                          ║ PUBLISHED PORT BOUNDARY
                          ║ (only if ports: configured)
  ╔═══════════════════════╩══════════════════════════════════════╗
  ║  ZONE 2 — Docker Network (docker0 bridge / user-defined)    ║
  ║  Virtual switch managed by Docker                            ║
  ║                                                              ║
  ║  api container ←──────────────────→ redis container         ║
  ║  IP: 172.20.0.2                     IP: 172.20.0.3          ║
  ║                                     Port 6379: accessible   ║
  ║                                     to api via DNS ✅       ║
  ║                                                              ║
  ║  EXPOSE 6379: informational only in this zone               ║
  ║  All ports accessible between containers on same network    ║
  ╚══════════════════════════════════════════════════════════════╝
          ║                               ║
  ╔═══════╩═══════╗               ╔═══════╩═══════╗
  ║  ZONE 1       ║               ║  ZONE 1       ║
  ║  api container║               ║  redis        ║
  ║  namespace    ║               ║  container    ║
  ║  127.0.0.1    ║               ║  namespace    ║
  ║  (private)    ║               ║  127.0.0.1:6379║
  ║               ║               ║  (private)    ║
  ╚═══════════════╝               ╚═══════════════╝
```

Understanding these three zones transforms the debugging process entirely. When a connection fails, the first diagnostic question is: "which zone is the source of the connection, and which zone is the destination?" If the source is Zone 3 (host tools) and the destination is a container port that is not published, the failure is expected and the solution is to add port publishing. If the source is Zone 2 (another container) and the destination is a container on the same network, EXPOSE is irrelevant and the service name DNS approach is correct. If the source is Zone 1 (same container, via `docker exec`), any listening port is accessible.

## 4. Port Publishing — The Mechanics of Host Binding

Port publishing is the process of instructing Docker to create a binding on the host's network interface and establish a network address translation (NAT) rule that forwards traffic from that host-side binding into the container. Docker implements this using the Linux kernel's `iptables` (or `nftables` on newer systems) NAT subsystem, creating DNAT rules that redirect packets arriving at the host port to the container's private IP and port.

When you specify `-p 6379:6379` in a `docker run` command or `ports: ["6379:6379"]` in a Docker Compose file, Docker adds a DNAT rule to the host's `iptables` configuration in the `DOCKER` chain. This rule intercepts any TCP packet arriving at port 6379 on any of the host's network interfaces (unless a specific host IP is specified) and rewrites the destination address to the container's internal IP and port before forwarding it through the bridge network to the container. From the container's perspective, it receives an ordinary TCP connection arriving at `0.0.0.0:6379`. The NAT translation is invisible at the application layer.

```
              Port Publishing — How NAT Connects Zone 3 to Zone 1
              ======================================================

  docker run -p 6379:6379 redis:7.2-alpine
  (or in Compose: ports: ["6379:6379"])

  Result: iptables DNAT rule created on host:
  DNAT for TCP dpt:6379 → 172.20.0.3:6379

  Traffic flow when host tool connects to localhost:6379:
  ──────────────────────────────────────────────────────────────────
  [redis-cli on host]
       │ TCP SYN → 127.0.0.1:6379 (host loopback)
       │
       ▼
  [iptables DOCKER chain]
       │ Rule: if dst_port=6379, DNAT to 172.20.0.3:6379
       │ Rewrites: dst → 172.20.0.3:6379
       │
       ▼
  [docker0 bridge network]
       │ Packet forwarded to 172.20.0.3
       │
       ▼
  [redis container] (172.20.0.3)
       │ Redis receives TCP connection at 0.0.0.0:6379
       ▼
  Redis responds: PONG ✅

  Port publishing syntax options:
  ─────────────────────────────────────────────────────────────
  ports: ["6379:6379"]     → binds ALL host interfaces:6379 → container:6379
  ports: ["127.0.0.1:6379:6379"] → binds ONLY loopback:6379 → container:6379
  ports: ["6380:6379"]     → binds host:6380 → container:6379 (different ports)
  ports: ["6379"]          → binds RANDOM host port → container:6379
```

The port binding syntax `[host_ip:][host_port:]container_port` offers precise control over which network interface and port number Docker uses for the binding. This control is critically important for security. The default behavior — when no host IP is specified — binds the port on all network interfaces of the host, including the public-facing interface if the host has one. This means that `ports: ["6379:6379"]` on a cloud server with a public IP makes your Redis instance reachable from the entire internet on port 6379. The more secure variant, `ports: ["127.0.0.1:6379:6379"]`, binds only to the loopback interface of the host, making the port reachable only from processes running on that same machine — appropriate for local development, not appropriate for production database access.

## 5. The Security Trap — Accidentally Publishing Production Databases

The most consequential misapplication of port publishing occurs when developers who use `ports:` extensively in their local development Compose files carry those same configurations into production or staging deployments. In a local development environment, publishing the database port is often convenient — it allows you to connect your preferred database GUI tool directly to the container, inspect data, run manual queries, and debug schema issues without having to `docker exec` into the container every time. This convenience is entirely legitimate for local development.

The danger arises when this Compose file, or a derivative of it, is deployed to a server. If `ports: ["5432:5432"]` is present for the PostgreSQL service and the server has a public IP address, the PostgreSQL instance is now bound to `0.0.0.0:5432` on that server. It is reachable from the entire internet. Automated scanning tools — which continuously probe the public internet for open database ports — will detect the exposed PostgreSQL port within minutes of the server coming online. Depending on the PostgreSQL configuration, this exposure may allow unauthenticated access (if `trust` authentication is configured), brute-force attacks on credentials, or exploitation of database engine vulnerabilities. The vast majority of database ransom attacks and data breaches that target small and medium companies originate from exactly this class of misconfiguration.

```
              The Production Database Exposure Risk
              ========================================

  Development Compose (safe — local machine only):
  ──────────────────────────────────────────────────────────────
  services:
    postgres:
      ports:
        - "5432:5432"   ← Fine locally: your laptop, no public IP
      # Allows: TablePlus, DBeaver, psql from your own Mac ✅

  Production Server (same Compose — DANGEROUS):
  ──────────────────────────────────────────────────────────────
  Server public IP: 203.0.113.45

  services:
    postgres:
      ports:
        - "5432:5432"   ← iptables binds 0.0.0.0:5432
                          = 203.0.113.45:5432 is open to the internet ❌

  Timeline after deployment:
  t=0min:    Server goes online. PostgreSQL published on :5432.
  t=3min:    First automated scan detects open port 5432 (Shodan, Censys).
  t=7min:    Brute-force tool begins attempting default credentials.
  t=15min:   If 'postgres' user has weak/default password: data exfiltrated.
  t=15min:   Ransom note left in database. All tables dropped.

  Correct production configuration:
  ──────────────────────────────────────────────────────────────
  services:
    postgres:
      # No 'ports:' block at all.
      # PostgreSQL is reachable ONLY from the api service via Docker network.
      # The internet cannot reach it. Scanners cannot reach it. ✅
      networks:
        - datastore

  Result: postgres:5432 accessible to api container via DNS ✅
          203.0.113.45:5432 does not exist — port not published ✅
```

The correct security principle for production deployments is straightforward: never publish database ports, cache ports, or internal service ports to the host network interface. The only ports that belong in the `ports:` configuration of a production Compose file are those that intentionally face the outside world — typically port 80 and 443 for an HTTP/HTTPS frontend service or API gateway. All internal service communication should go exclusively through the Docker network, using DNS-based service names, with no host-side port binding whatsoever.

## 6. The `--publish-all` Flag and EXPOSE's One Practical Use

There is one scenario in which the `EXPOSE` instruction has a concrete functional effect beyond documentation: the `--publish-all` flag, abbreviated as `-P`. When you run `docker run -P <image>`, Docker automatically publishes all ports that are `EXPOSE`d in the image, assigning a random high-numbered port on the host for each exposed container port. This feature exists primarily for rapid prototyping and testing scenarios where you want to run an image and quickly reach it from the host without knowing in advance which port to map.

```bash
# Automatically publish all EXPOSE'd ports to random host ports
docker run -d -P redis:7.2-alpine

# Find the randomly assigned host port
docker port redis
# Output: 6379/tcp -> 0.0.0.0:32768

# Connect using the randomly assigned port
redis-cli -h 127.0.0.1 -p 32768 ping
# PONG ✅
```

While `-P` is occasionally useful for quick exploration, it is never appropriate for production use. Random port assignments change every time the container is restarted, breaking any hardcoded references to that port. The host-side binding — like all port publishing — exposes the port on all host interfaces by default, creating the same security risk as explicit publishing. Production configurations should always specify explicit, deliberate port mappings with explicit host IP bindings, and should never rely on random port assignment.

## 7. The `host` Network Mode — When NAT Becomes Unnecessary

For completeness, Docker supports a networking mode called `host` network mode, in which the container shares the host's network namespace entirely rather than having its own isolated namespace. In host network mode, there is no NAT, no bridge network, and no port publishing — the container process binds directly to the host's network interfaces as if it were a bare-metal process. A Redis container in host network mode that binds to `0.0.0.0:6379` is directly listening on port 6379 of the host, and `redis-cli -h localhost -p 6379` on the host works immediately without any `-p` flag.

Host network mode achieves the highest possible networking performance because it eliminates NAT overhead, and it can be useful for specific high-performance scenarios such as network monitoring tools, packet capture applications, or services that need to bind to privileged ports. However, it comes at a significant security cost: the container's network is completely shared with the host, the isolation boundary between container and host network is eliminated, and any port the container binds to is immediately accessible on the host's public interfaces without any firewall rules or NAT mapping in between. For general application deployments, host network mode should be considered an advanced option used only when the performance benefits have been demonstrated to be necessary and the security implications have been explicitly accepted.

```
              Network Mode Comparison Summary
              ==================================

  Mode          Isolation    Performance   Port Publishing   Use Case
  ────────────────────────────────────────────────────────────────────
  bridge        Isolated     Good (NAT)    Explicit via -p   Default, most services
  host          Shared       Best (no NAT) Not needed        Performance-critical tools
  none          No network   N/A           N/A               Security isolation
  overlay       Isolated     Good          Swarm/K8s needed  Multi-host deployments
  macvlan       Layer 2      Very good     Direct IP assign  Legacy network compat
  ────────────────────────────────────────────────────────────────────

  For virtually all containerized applications: use bridge (default).
  Never use host mode for databases or application services in production.
```

## 8. Practical Compose Patterns — Development vs. Production Configuration

Experienced engineering teams handle the divergence between development and production port publishing needs through one of two approaches. The first approach uses Docker Compose's override file mechanism, where a base `docker-compose.yml` contains the production-safe configuration with no database port publishing, and a `docker-compose.override.yml` file — applied automatically when running `docker-compose up` in development — adds the convenience port bindings for local tooling.

```yaml
# docker-compose.yml (base — safe for all environments, committed to git)
services:
  api:
    build: .
    ports:
      - "8080:8080"     # API is intentionally public-facing ✅
    environment:
      DB_URL: postgres://appuser:secret@postgres:5432/myapp

  postgres:
    image: postgres:16.2-alpine3.19
    environment:
      POSTGRES_USER:     appuser
      POSTGRES_PASSWORD: secret
      POSTGRES_DB:       myapp
    volumes:
      - pgdata:/var/lib/postgresql/data
    # NO 'ports:' block. Postgres is internal only. ✅

  redis:
    image: redis:7.2-alpine3.19
    # NO 'ports:' block. Redis is internal only. ✅

volumes:
  pgdata:
```

```yaml
# docker-compose.override.yml (dev convenience — git-ignored or clearly marked)
# Applied automatically by docker-compose up when present.
# NEVER deploy this file to production servers.
services:
  postgres:
    ports:
      - "127.0.0.1:5432:5432"   # Only loopback — not all interfaces ✅
                                  # Allows: TablePlus, psql from host

  redis:
    ports:
      - "127.0.0.1:6379:6379"   # Only loopback ✅
                                  # Allows: redis-cli, RedisInsight from host
```

By binding to `127.0.0.1` rather than `0.0.0.0` in the override file, even the development configuration limits exposure to the local machine only. A developer running Docker on their laptop with this configuration can connect to both PostgreSQL and Redis from their host tools, while an accidental deployment of the override file to a server would still not expose the ports to the internet. This is a defense-in-depth approach that makes the configuration safe even when accidentally misapplied.

## 9. Verifying Your Port Configuration — The Diagnostic Commands

When investigating why a service is or is not reachable, a small set of commands provides complete visibility into the current port binding and NAT configuration:

```bash
# ── Check what ports a container has bound and published ──────────────────────
docker port redis
# Output if published:      6379/tcp -> 0.0.0.0:6379
# Output if not published:  (empty — no host bindings)

# ── Check docker ps for port information ──────────────────────────────────────
docker ps
# PORTS column:
# "6379/tcp"              → EXPOSE'd only, NOT published ← confusing!
# "0.0.0.0:6379->6379/tcp" → published to all interfaces
# "127.0.0.1:6379->6379/tcp" → published to loopback only

# ── Check what is actually bound on the host ──────────────────────────────────
# On Linux host:
ss -tlnp | grep 6379
# If published: LISTEN  0  128  0.0.0.0:6379  ...  docker-proxy
# If not published: (empty line)

# On macOS/Windows (Docker Desktop uses VM):
# Check Docker Desktop dashboard or:
docker inspect redis --format='{{json .HostConfig.PortBindings}}'
# Published: {"6379/tcp":[{"HostIp":"","HostPort":"6379"}]}
# Not published: {}

# ── Inspect EXPOSE metadata vs actual bindings ──────────────────────────────
docker inspect redis:7.2 --format='{{json .Config.ExposedPorts}}'
# Shows: {"6379/tcp":{}}  ← EXPOSE metadata, NOT bindings

docker inspect <running_container> --format='{{json .NetworkSettings.Ports}}'
# Shows actual runtime port bindings (may include host ports)

# ── Test connectivity from host ────────────────────────────────────────────────
nc -zv 127.0.0.1 6379
# Connection succeeded: port is published and Redis is running ✅
# Connection refused: port not published ❌

# ── Test connectivity from another container (zone 2) ─────────────────────────
docker exec api nc -zv redis 6379
# Connection succeeded: containers are on same network ✅
# No EXPOSE or publishing needed for this to work
```

The `docker ps` output deserves special attention because it is the most common source of confusion. The `PORTS` column shows `6379/tcp` without any arrow notation when a port is `EXPOSE`d but not published. This display makes the port look like it might be accessible, when in fact it is merely documented metadata. Only when you see the arrow notation — `0.0.0.0:6379->6379/tcp` or `127.0.0.1:6379->6379/tcp` — is the port actually published and accessible from the host.

## 10. The Golden Rule

> `EXPOSE` in a Dockerfile is a documentation annotation — an author's note that says "this service listens on this port." It creates no network bindings, opens no firewall rules, and makes no service reachable from outside the Docker network. Port publishing through `-p` on `docker run` or `ports:` in Docker Compose is the actual mechanism that binds a host port, creates a NAT rule, and makes a container port reachable from the host and the outside world. In production, publish only the ports that are intentionally public-facing — your HTTP or HTTPS ingress. Never publish database ports, cache ports, or internal service ports to the host network in production; internal service communication belongs entirely within the Docker network using DNS-based service names. In development, when host-tool access to databases is needed for debugging, bind to `127.0.0.1` rather than `0.0.0.0` to limit exposure to the local machine only. The single most common Docker security misconfiguration is a production database with its port published to `0.0.0.0` — discoverable by internet scanners within minutes.

The rule is elegant in its simplicity: if a service is internal, give it no `ports:` entry and it is invisible to the world. If a service is public, give it an explicit `ports:` entry and it becomes reachable. The wall is the default. Publishing is the deliberate act of opening a door.
