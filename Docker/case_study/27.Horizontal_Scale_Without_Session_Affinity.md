# Horizontal Scale Without Session Affinity

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Hotel With Five Receptionists Who Don't Share Notes

A hotel has one receptionist — Marie — who manages all guest check-ins. When a guest checks in, Marie records their room number, their preferences, their loyalty tier, and their authorization to access the pool, the gym, and the restaurant account in a notebook on her desk. Every subsequent guest interaction — requesting a late checkout, ordering room service, accessing the minibar account — goes through Marie, who consults her notebook. The system works flawlessly.

The hotel grows. Occupancy increases. The manager hires four additional receptionists to handle peak load: Jacques, Fatima, Kenji, and Amara. Each stands at their own desk, serving guests simultaneously. But nobody set up a shared information system. Each receptionist has their own notebook. When a guest checks in with Marie, their information is in Marie's notebook. When that same guest approaches Fatima's desk an hour later to charge a meal to their room, Fatima's notebook has no record of this guest. From Fatima's perspective, this person has not checked in. The guest is turned away. The guest complains. From the guest's perspective, they properly checked in — they have the key, the wristband, everything — but the hotel seems to have forgotten them. The problem is not that any receptionist is incompetent. The problem is that state that should be shared is isolated in individual notebooks.

This is exactly the horizontal scaling failure for stateful applications. One API server instance works correctly because all state — session tokens, rate limit counters, upload progress, websocket subscriptions, authentication caches — lives in its process memory. When you scale to five instances behind a load balancer, each incoming request is routed to whichever instance has capacity. The instance that served the login request and stored the session in memory is not necessarily the instance that serves the next request from the same user. The new instance has no knowledge of the session. Authentication fails. The user is effectively logged out despite having just logged in.

## 2. The Anatomy of In-Process State — What Breaks When You Scale

State that lives in a process's memory is, by definition, local to that process. It is invisible to every other process on the system — whether on the same host or a different host. When a Go API server stores a session token in a `map[string]Session`, that map lives in the heap of that specific process instance. No other process can read it, no other process can write to it, and when the process restarts the map is cleared. This is the fundamental constraint of horizontal scaling: adding more instances adds more processes, and each process has its own isolated memory.

The failure modes that result from in-process state vary by what type of state is being stored:

```
              In-Process State Types — How Each Fails at Scale
              ===================================================

  State Type             Stored In              Failure Mode at Scale (N > 1)
  ─────────────────────────────────────────────────────────────────────────────
  Server-side sessions   map[sessionID]Session  User authenticated to Instance A.
  (session tokens)       in process heap        Next request routes to Instance B.
                                                B has no session → 401 Unauthorized.
                                                Symptom: random logouts. ❌

  Rate limit counters    map[IP]int             User sends 10 requests/sec across
                         in process heap        5 instances = 2 req/sec per instance.
                                                Each instance sees 2 req/sec limit ✅
                                                but the true rate is 10 req/sec.
                                                Rate limiting is 5× too permissive. ❌

  In-memory cache        map[key]Value          Cache MISS on every non-owning instance.
                         in process heap        5 instances = 5 separate caches.
                                                Cache hit rate: 20% instead of ~80%.
                                                Cache miss storm: 5× more DB load. ❌

  WebSocket connections  map[userID]*ws.Conn    User connected to Instance A.
                         in process heap        Server broadcasts to Instance B.
                                                B has no connection for this user.
                                                Message lost. Silent failure. ❌

  File upload state      Temp files in          Upload chunk 1 → Instance A (writes temp)
                         /tmp on instance       Upload chunk 2 → Instance B (no temp file)
                                                Reassembly fails. Upload broken. ❌

  Background job queue   []Job slice or         Job enqueued to Instance A.
                         channel in process     Instance A restarts. Queue cleared.
                                                Job lost. No retry. ❌

  CSRF tokens            map[token]bool         Token generated on Instance A.
                         in process heap        Validation request → Instance B.
                                                Token not found → CSRF validation fails.
                                                Form submission rejected. ❌
```

The rate limit failure deserves particular attention because it is counterintuitive. An engineer might reason that rate limiting is correctly distributed across instances — five instances, each enforcing 100 req/min, means the system enforces 500 req/min in aggregate. But the purpose of rate limiting is typically per-user or per-IP enforcement, not aggregate enforcement. If a single malicious client sends 100 requests per minute to the load balancer, they arrive approximately equally distributed across five instances: 20 req/min at each instance. Each instance sees the client under its 100 req/min limit. All requests pass. The client has effectively bypassed a 100 req/min limit with a 100 req/min actual rate — by taking advantage of the distribution. Without a shared counter, per-identity rate limiting is impossible at scale.

## 3. The Failure Timeline — A Concrete Login Scenario

To make the failure concrete, consider the exact sequence of events when a user logs into an application that stores sessions in a Go process map, deployed as five replicas behind Nginx with round-robin load balancing:

```
              Session State Failure — Five-Replica Load-Balanced Login
              ===========================================================

  Infrastructure:
  Nginx (load balancer, round-robin) → [API-1, API-2, API-3, API-4, API-5]
  Each API instance: sessions map[string]User{} in process memory

  t=0s: User (Alice) submits login form
        Nginx: routes to API-3 (round-robin)
        API-3: validates credentials against DB ✅
        API-3: generates sessionID = "sess_abc123"
        API-3: stores sessions["sess_abc123"] = User{ID: 42, Role: "admin"}
        API-3: returns Set-Cookie: session=sess_abc123
        Alice's browser: stores cookie session=sess_abc123 ✅

  t=1s: Alice's browser: GET /api/dashboard
        Cookie: session=sess_abc123 (sent automatically)
        Nginx: routes to API-1 (next in round-robin)
        API-1: looks up sessions["sess_abc123"]
        API-1: sessions["sess_abc123"] → nil (not found) ← KEY FAILURE
        API-1: returns 401 Unauthorized ❌
        Browser: redirects to login page.
        Alice: sees login page. She JUST logged in. ❌
        Alice: "Why am I being logged out?"

  t=2s: Alice submits login form again (frustrated)
        Nginx: routes to API-5
        API-5: validates ✅, generates sess_xyz789, sets cookie.
        API-5: stores sessions["sess_xyz789"] = User{ID: 42, ...}
        Alice: redirected to dashboard ✅

  t=3s: Alice clicks "Reports"
        Nginx: routes to API-2 (round-robin)
        API-2: looks up sessions["sess_xyz789"] → nil ❌
        API-2: 401 Unauthorized ❌
        Alice: logged out AGAIN.

  Symptom pattern from monitoring:
  ├── Auth failure rate: ~80% (only ~20% of requests hit the correct instance)
  ├── Login rate: 5× higher than expected (users keep re-logging in)
  ├── Error logs: "session not found" on API-1, API-2, API-4, API-5
  ├── API-3 logs: "session found" (it has the only valid sessions)
  └── Database: login query rate 5× normal (users retrying repeatedly)

  The application works correctly with 1 replica.
  The application breaks completely with 5 replicas.
  The scaling operation itself is the trigger for the failure.
```

## 4. The Wrong Fix — Sticky Sessions

The first solution many engineers reach for when they encounter this failure is **sticky sessions** (also called session affinity): configuring the load balancer to route all requests from a given user to the same backend instance for the duration of their session. With sticky sessions enabled, Alice always hits API-3, so her in-process session is always found.

Sticky sessions solve the immediate symptom but introduce a new set of problems that make the system worse at scale than it was with one instance:

```
              Sticky Sessions — Solving One Problem, Creating Three More
              =============================================================

  Problem 1 — Uneven load distribution:
  Without sticky sessions (round-robin): requests distributed evenly.
  With sticky sessions: distribution follows user-to-instance assignment.
  Power users generate 100× more requests than light users.
  If power users are hashed to Instance-1: Instance-1 at 300% load.
  Instance-5 (light users): at 20% load. Imbalanced. ❌

  Problem 2 — Instance failure causes mass session loss:
  Without sticky sessions: instance failure → users re-routed seamlessly.
  With sticky sessions: Instance-3 dies → ALL users stuck to Instance-3 lose sessions.
  They are all logged out simultaneously. ❌
  This makes a single instance failure cause a user-visible outage.
  The purpose of having 5 instances (redundancy) is defeated. ❌

  Problem 3 — Deployment and rolling updates:
  Rolling update: replace one instance at a time.
  Users stuck to Instance-3: logged out when Instance-3 is replaced.
  To do a zero-downtime deploy, you must maintain session state during rotation.
  This requires external state storage anyway — defeating the purpose of sticky sessions.

  Problem 4 — Cannot scale down cleanly:
  Scaling from 5 to 3 replicas: Instance-4 and Instance-5 must be drained.
  Draining means waiting for all sticky users to naturally end their sessions.
  Sessions may last hours. Scaling takes hours. ❌

  Conclusion: sticky sessions are a band-aid that violates horizontal scalability.
  They delay the inevitable rearchitecture while adding operational complexity.
  The correct solution is statelessness, not affinity.
```

## 5. The Correct Solutions — Externalizing State

The correct architectural response to the in-process state problem is to move each type of state to an external, shared storage system that all replicas can read and write. The state no longer belongs to any specific replica — it belongs to the external system, which becomes the single source of truth. Every replica consults the external system for state, and the replica that served a previous request is no longer relevant to the replica serving the current request.

**Solution 1 — JWT Tokens (Stateless Authentication)**

The most elegant solution for authentication is to eliminate server-side session state entirely by using JSON Web Tokens (JWT). A JWT is a cryptographically signed token that contains the user's identity and claims within the token itself. The server signs the token with a private key at login and sends it to the client. On subsequent requests, the client sends the token back. Any server instance can verify the token's signature using the public key — no session lookup required, no shared state needed. The token is self-contained.

```go
// auth.go — Stateless JWT authentication in Go

package auth

import (
    "fmt"
    "os"
    "time"

    "github.com/golang-jwt/jwt/v5"
)

// Claims defines the JWT payload structure.
// These are embedded in the token itself — no server-side storage. ✅
type Claims struct {
    UserID uint64 `json:"uid"`
    Role   string `json:"role"`
    Email  string `json:"email"`
    jwt.RegisteredClaims
}

// jwtSecret is loaded from an environment variable / Docker Secret.
// All instances use the SAME secret (or public/private key pair).
// This is what allows any instance to verify tokens issued by any other instance.
var jwtSecret = []byte(mustGetSecret("/run/secrets/jwt_secret", "JWT_SECRET"))

// GenerateToken creates a signed JWT for the authenticated user.
// The token is returned to the client. No server-side storage. ✅
func GenerateToken(userID uint64, role, email string) (string, error) {
    claims := Claims{
        UserID: userID,
        Role:   role,
        Email:  email,
        RegisteredClaims: jwt.RegisteredClaims{
            // Token expires in 24 hours. Client must re-authenticate after expiry.
            ExpiresAt: jwt.NewNumericDate(time.Now().Add(24 * time.Hour)),
            IssuedAt:  jwt.NewNumericDate(time.Now()),
            Issuer:    "myapp",
        },
    }

    token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
    return token.SignedString(jwtSecret)
}

// ValidateToken verifies the token signature and extracts claims.
// Any instance can call this — no shared state required. ✅
// Works correctly with any number of replicas. ✅
func ValidateToken(tokenString string) (*Claims, error) {
    token, err := jwt.ParseWithClaims(tokenString, &Claims{},
        func(token *jwt.Token) (interface{}, error) {
            if _, ok := token.Method.(*jwt.SigningMethodHMAC); !ok {
                return nil, fmt.Errorf("unexpected signing method: %v", token.Header["alg"])
            }
            return jwtSecret, nil
        },
    )
    if err != nil {
        return nil, fmt.Errorf("invalid token: %w", err)
    }

    claims, ok := token.Claims.(*Claims)
    if !ok || !token.Valid {
        return nil, fmt.Errorf("invalid token claims")
    }

    return claims, nil
}

// Middleware: validates JWT on every request. Stateless. Any replica. ✅
func AuthMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        tokenString := extractToken(r) // From Authorization: Bearer <token>
        claims, err := ValidateToken(tokenString)
        if err != nil {
            http.Error(w, "Unauthorized", http.StatusUnauthorized)
            return
        }
        // Inject claims into context for downstream handlers
        ctx := context.WithValue(r.Context(), claimsKey, claims)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func mustGetSecret(filePath, envKey string) string {
    if data, err := os.ReadFile(filePath); err == nil {
        return strings.TrimSpace(string(data))
    }
    if v := os.Getenv(envKey); v != "" {
        return v
    }
    panic(fmt.Sprintf("secret not found: %s or env %s", filePath, envKey))
}
```

**Solution 2 — Redis for Shared State (Rate Limiting, Caching, Queues)**

For state that cannot be expressed as a self-contained token — rate limit counters, shared caches, session stores for tokens that need revocation, distributed locks — Redis provides a fast, shared, in-memory store accessible by all replicas:

```go
// ratelimit.go — Distributed rate limiting using Redis atomic INCR
package ratelimit

import (
    "context"
    "fmt"
    "time"

    "github.com/redis/go-redis/v9"
)

type RedisRateLimiter struct {
    client     *redis.Client
    maxRequests int
    window      time.Duration
}

func NewRedisRateLimiter(client *redis.Client, maxRequests int, window time.Duration) *RedisRateLimiter {
    return &RedisRateLimiter{
        client:      client,
        maxRequests: maxRequests,
        window:      window,
    }
}

// Allow checks if the given key (e.g., IP address or user ID) is within the rate limit.
// Uses Redis INCR + EXPIRE for atomic counter increment.
// Shared across ALL replicas — accurate global rate limiting. ✅
func (r *RedisRateLimiter) Allow(ctx context.Context, key string) (bool, error) {
    redisKey := fmt.Sprintf("ratelimit:%s", key)

    // Lua script: atomic INCR + EXPIRE in a single Redis round trip.
    // Atomic: no race condition between INCR and EXPIRE. ✅
    script := redis.NewScript(`
        local current = redis.call("INCR", KEYS[1])
        if current == 1 then
            redis.call("EXPIRE", KEYS[1], ARGV[1])
        end
        return current
    `)

    result, err := script.Run(ctx, r.client,
        []string{redisKey},
        int(r.window.Seconds()),
    ).Int()
    if err != nil {
        // Fail open: if Redis is unavailable, allow the request.
        // Prevents Redis outage from becoming API outage.
        // Log the failure for alerting.
        return true, fmt.Errorf("rate limiter redis error: %w", err)
    }

    return result <= r.maxRequests, nil
}

// Usage: the same Redis key "ratelimit:192.168.1.100" is incremented
// regardless of which API replica receives the request.
// 5 replicas, each seeing 20 req/min from the same IP:
// Redis counter: correctly shows 100 req/min → enforces limit. ✅
```

```go
// session.go — Redis-backed session store (for when JWT revocation is needed)
package session

import (
    "context"
    "encoding/json"
    "fmt"
    "time"

    "github.com/redis/go-redis/v9"
)

type Session struct {
    UserID    uint64    `json:"user_id"`
    Role      string    `json:"role"`
    CreatedAt time.Time `json:"created_at"`
}

type RedisSessionStore struct {
    client *redis.Client
    ttl    time.Duration
}

func NewRedisSessionStore(client *redis.Client) *RedisSessionStore {
    return &RedisSessionStore{
        client: client,
        ttl:    24 * time.Hour,
    }
}

// Set stores a session in Redis. Any replica can subsequently read it. ✅
func (s *RedisSessionStore) Set(ctx context.Context, sessionID string, sess Session) error {
    data, err := json.Marshal(sess)
    if err != nil {
        return err
    }
    return s.client.Set(ctx, "session:"+sessionID, data, s.ttl).Err()
}

// Get retrieves a session from Redis — works on ANY replica. ✅
func (s *RedisSessionStore) Get(ctx context.Context, sessionID string) (*Session, error) {
    data, err := s.client.Get(ctx, "session:"+sessionID).Bytes()
    if err == redis.Nil {
        return nil, fmt.Errorf("session not found")
    }
    if err != nil {
        return nil, err
    }
    var sess Session
    return &sess, json.Unmarshal(data, &sess)
}

// Delete explicitly revokes a session (logout). JWT cannot do this. ✅
// All replicas: next lookup returns "not found" → user is truly logged out.
func (s *RedisSessionStore) Delete(ctx context.Context, sessionID string) error {
    return s.client.Del(ctx, "session:"+sessionID).Err()
}
```

## 6. The Complete Stateless Architecture — Docker Compose for 5 Replicas

```yaml
# docker-compose.yml — Stateless API ready for horizontal scaling

version: "3.9"

services:
  nginx:
    image: nginx:1.25-alpine
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    ports:
      - "80:80"
    depends_on:
      - api
    networks:
      - frontend

  api:
    build: .
    deploy:
      replicas: 5              # 5 instances — all stateless, all equivalent ✅
      resources:
        limits:
          memory: 512m
          cpus: "1.0"
    environment:
      DB_URL:       postgres://appuser:secret@postgres:5432/myapp
      REDIS_URL:    redis://:redis-secret@redis:6379/0
      # JWT_SECRET: loaded from Docker Secret file in application code
      # All 5 replicas use the SAME JWT_SECRET — tokens are cross-instance valid ✅
    secrets:
      - jwt_secret            # Same secret for all replicas ✅
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    networks:
      - frontend
      - backend
    # NO in-process session storage.
    # NO in-process rate limit counters.
    # NO in-process cache (or only idempotent caches like compiled templates). ✅

  postgres:
    image: postgres:16.2-alpine3.19
    volumes:
      - pgdata:/var/lib/postgresql/data

      test: ["CMD-SHELL", "pg_isready -U appuser -d myapp -q"]

      - backend

      - redisdata:/data

      test: ["CMD", "redis-cli", "-a", "redis-secret", "ping"]
      interval: 5s
      retries: 5
    networks:
      - backend
    deploy:
      resources:
        limits:
          memory: 1.5g
          cpus: "1.0"

networks:
  frontend:
  backend:

volumes:
  pgdata:
  redisdata:
```

```nginx
upstream api_backend {
    # Docker Compose with replicas: Docker DNS returns all 5 IPs for "api"
    # Nginx resolves and round-robins across all of them. No ip_hash. ✅
    server api:8080;

    # With least_conn: routes to instance with fewest active connections.
    # Better than round-robin for variable request duration.
    least_conn;

    # Keepalive: maintain persistent connections to backends.
    keepalive 32;
}

server {
    listen 80;

    location / {
        proxy_pass         http://api_backend;
        proxy_http_version 1.1;
        proxy_set_header   Connection "";     # Enable keepalive to backends
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;

        # NO ip_hash directive → no sticky sessions → truly stateless ✅
    }
}
```

## 7. The Statelessness Test — Verifying Your Application Can Scale

Before deploying scaled replicas in production, a simple statelessness verification test can be run in development. It routes requests deliberately to different instances and verifies that authentication and session state work correctly regardless of which instance serves each request:

```bash
#!/bin/bash
# test-statelessness.sh — Verify API is horizontally scalable

BASE_URL="http://localhost:80"

echo "=== Statelessness Test ==="

# Step 1: Login — get JWT token
echo "1. Logging in..."
LOGIN_RESPONSE=$(curl -s -X POST "$BASE_URL/api/login" \
    -H "Content-Type: application/json" \
    -d '{"email":"test@example.com","password":"testpass"}')

TOKEN=$(echo "$LOGIN_RESPONSE" | jq -r '.token')
if [ -z "$TOKEN" ] || [ "$TOKEN" = "null" ]; then
    echo "FAIL: Login failed. Response: $LOGIN_RESPONSE"
    exit 1
fi
echo "   Token obtained: ${TOKEN:0:20}..."

# Step 2: Send 20 requests with the token.
# With 5 replicas: each instance serves ~4 requests.
# ALL should succeed if the app is stateless.
echo "2. Sending 20 authenticated requests (5 replicas, ~4 per instance)..."
FAILURES=0
for i in $(seq 1 20); do
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
        -H "Authorization: Bearer $TOKEN" \
        "$BASE_URL/api/dashboard")

    if [ "$STATUS" != "200" ]; then
        echo "   Request $i: FAIL (HTTP $STATUS) ← Session not found on this replica ❌"
        ((FAILURES++))
    else
        echo "   Request $i: OK (HTTP 200) ✅"
    fi
done

echo ""
if [ "$FAILURES" -eq 0 ]; then
    echo "=== PASS: All 20 requests succeeded. Application is stateless. ✅ ==="
else
    echo "=== FAIL: $FAILURES/20 requests failed. In-process session state detected. ❌ ==="
    echo "    Fix: externalize session storage to Redis or use JWT. ==="
fi
```

## 8. The State Externalization Decision Matrix

```
              State Type → Correct External Storage
              ========================================

  State Type               Correct External Storage      Notes
  ────────────────────────────────────────────────────────────────────────
  Authentication           JWT (stateless token)         No revocation possible.
  (no revocation needed)   stored client-side            Use for most auth. ✅

  Authentication           Redis session store           Revocation possible.
  (revocation required)    (key: sessionID)              Logout invalidates session. ✅

  Rate limit counters      Redis INCR + EXPIRE           Atomic. Cross-instance. ✅

  Cache (idempotent data)  Redis (shared cache)          One cache, all instances share.
                                                         Hit rate: same as 1 instance. ✅

  WebSocket pub/sub state  Redis pub/sub adapter         Socket.IO Redis adapter.
                                                         See WebSocket case study. ✅

  Uploaded files           S3 / MinIO / GCS              Shared object storage.
                           (shared object store)         Any instance reads/writes. ✅

  Background job queue     Redis (Bull/BullMQ)           Persistent queue. Shared.
                           or RabbitMQ / SQS             Any instance dequeues. ✅

  Distributed locks        Redis SETNX + TTL             Prevents double-processing.
                           or Redlock algorithm          Cross-instance mutex. ✅

  User-uploaded large files Shared NFS / EFS / Azure FS For streaming/chunked uploads.
                            or presigned S3 URLs         Client uploads directly. ✅

  Configuration/feature     Database or config service   Read on startup + cache locally.
  flags                     (LaunchDarkly, Flagsmith)    Re-read periodically. ✅

  ────────────────────────────────────────────────────────────────────────
  Rule: if the data must be read by more than one process instance,
        it cannot live in any single process's memory.
```

## 9. The Golden Rule

> A process that holds state cannot be scaled horizontally. This is not a guideline or a best practice — it is an architectural law. Adding more replicas of a stateful process does not increase capacity proportionally; it creates a system where each replica has a different, partial, inconsistent view of the application's state, and requests that cross replica boundaries produce errors. Sticky sessions — routing each user to the same replica — paper over the symptom while preserving the architectural flaw, and they introduce new failure modes: uneven load distribution, mass session loss on instance failure, and inability to perform rolling updates cleanly. The correct architectural response is to move all state that must be shared across requests into external storage systems that all replicas can access: JWT tokens for stateless authentication (the user's identity travels in the token itself, signed by a key shared across all instances), Redis for rate limit counters (atomic INCR ensures accuracy across all replicas), Redis for session state that requires revocation, shared object storage (S3, MinIO) for files, and Redis-backed message queues for background work. The test for statelessness is simple: authenticate through instance A, then deliberately route all subsequent requests to instances B, C, D, and E. If any request fails with an authentication error, the application is stateful and cannot be scaled horizontally. Fix the state before scaling the instances — retrofitting statelessness into a running production system is significantly harder than designing for it from the beginning.

If you cannot run ten identical replicas without state bugs, the state is in the wrong place. Move it.
