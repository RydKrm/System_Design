# Health Check That Lies

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Guard Who Reports All Clear While the City Burns

In the medieval practice of city watch, sentinels were posted at watchtowers around a city's perimeter. Their sole function was to observe their assigned sector and raise the alarm if anything was wrong. The city's defense depended entirely on the accuracy of those reports. Now imagine a sentinel who, rather than observing the city, simply looked at the sky above his tower. If the sky was clear, he sent the report "all clear." The sentinel was not lying in the conventional sense — the sky above his tower was indeed clear — but his report was fundamentally disconnected from the question it was supposed to answer. While he gazed at cloudless skies, an invading army could enter through the eastern gate, and the city would receive his reassuring "all clear" right up until the moment soldiers appeared in the town square.

This is precisely what a superficial health check does inside a containerized system. A health check that simply fetches the application's root URL and verifies it returns HTTP 200 is observing the sky above the tower. It confirms that the web server process is alive and capable of accepting an HTTP connection. It tells you nothing about whether the database pool has been exhausted, whether the cache layer is unreachable, whether the message queue consumer has stalled, or whether the application's background workers have silently deadlocked. The load balancer, seeing the health check return 200, continues routing user traffic to this instance with complete confidence. Users receive errors. Engineers see spikes in error metrics. The monitoring dashboard shows all instances as healthy. Nobody can explain why a system in which every component is reporting healthy is nonetheless producing errors for every user. This is the phantom healthy instance, and it is one of the most maddening operational failure modes in distributed systems.

## 2. What a Health Check Actually Is — The Infrastructure Contract

To understand why superficial health checks are so dangerous, you must first understand what role health checks play in the architecture of a containerized distributed system and how multiple layers of infrastructure consume and act upon health check results.

In the Docker ecosystem, the `HEALTHCHECK` instruction in a Dockerfile defines a command that the Docker daemon executes at a regular interval inside the container. Docker evaluates the exit code of this command: exit code zero indicates healthy, any non-zero exit code indicates unhealthy. Docker tracks a history of recent health check results and uses them to determine the container's health state — either `healthy`, `unhealthy`, or `starting`. This health state is visible through `docker inspect` and `docker ps`, and container orchestrators can use it to make scheduling decisions.

In a Kubernetes environment, the health check concept is elevated into two distinct probe types — the liveness probe and the readiness probe — each with a different purpose, a different effect when it fails, and a fundamentally different role in the container lifecycle. Understanding the distinction between these two probe types is essential to designing a health check strategy that actually reflects the real operational state of an application.

```
              Health Check Consumers — The Infrastructure Stack
              ==================================================

  Layer 1 — Docker Daemon:
  ┌───────────────────────────────────────────────────────────┐
  │  Executes: HEALTHCHECK CMD every N seconds                 │
  │  Reads: exit code (0=healthy, non-zero=unhealthy)         │
  │  Reports: container health state in docker inspect        │
  │  Action: (alone) marks unhealthy but does NOT restart     │
  │  Restart requires: --restart policy or orchestrator       │
  └───────────────────────────────────────────────────────────┘
             │
             ▼
  Layer 2 — Container Orchestrator (Kubernetes):
  ┌───────────────────────────────────────────────────────────┐
  │  Liveness Probe:                                           │
  │    Fails → Kubelet kills and restarts the container        │
  │    Purpose: "Is the process frozen/deadlocked?"            │
  │                                                            │
  │  Readiness Probe:                                          │
  │    Fails → Pod removed from Service Endpoints             │
  │    Purpose: "Is this instance ready to serve traffic?"    │
  │    Action: load balancer stops routing here               │
  └───────────────────────────────────────────────────────────┘
             │
             ▼
  Layer 3 — Load Balancer / Ingress:
  ┌───────────────────────────────────────────────────────────┐
  │  Reads: Service Endpoint list (managed by Kubernetes)      │
  │  Routes traffic to: only Ready pods                        │
  │  If readiness probe lies → broken pods receive traffic ❌  │
  └───────────────────────────────────────────────────────────┘
```

The load balancer routes traffic only to instances that the orchestrator has declared ready. The orchestrator declares an instance ready based on the result of the readiness probe. The readiness probe returns its result based on what the application's health endpoint reports. If the health endpoint reports a 200 OK while the database connection pool is exhausted, the chain of trust that connects user traffic distribution to actual application capability is broken at its source. Every subsequent layer in the infrastructure operates correctly — the orchestrator correctly forwards traffic to instances its readiness probe marked as ready, the load balancer correctly routes to those instances — but the foundational signal they are all relying upon is false.

## 3. The Root URL Anti-Pattern — Why It Always Lies

The most common implementation of a health check endpoint is one of the simplest possible HTTP handlers: a function registered to the root path or to `/health` that immediately returns an HTTP 200 response containing a static body such as `{"status":"ok"}`. This implementation is written in minutes, added to the Dockerfile's `HEALTHCHECK` instruction, and committed with a feeling of responsible engineering. It is entirely wrong for production use.

The fundamental problem with a static 200 response health endpoint is that it tests only one thing: that the process is alive and the HTTP server framework is initialized. It does not test anything about the application's actual capability to serve user requests correctly. Consider the realistic failure scenario. Your application is running correctly, connected to a PostgreSQL database with a connection pool of twenty connections. Traffic increases unexpectedly. All twenty connections are checked out from the pool and are occupied processing slow queries. A twenty-first request arrives and attempts to acquire a connection, waits until the pool timeout expires, and receives an error. The application returns a 500 to the user. Twenty-second, twenty-third, twenty-fourth request — all fail the same way. Every user request is failing because the database connection pool is exhausted.

During all of this, your health check endpoint at `/health` continues to return 200 without interruption. The handler for this endpoint does not touch the database. It never calls `db.Ping()`. It never attempts to acquire a connection from the pool. It simply returns a hard-coded response string, and it will continue returning that same 200 until the process itself crashes. The orchestrator sees a healthy pod. The load balancer routes traffic here. Users continue receiving errors. The monitoring dashboard shows healthy instances and spiking error rates simultaneously — a contradiction that engineers will spend significant time trying to reconcile, because the infrastructure is telling them everything is fine while users are clearly experiencing a broken service.

```
              The Anatomy of a Lying Health Check
              =====================================

  Reality inside the container:
  ┌──────────────────────────────────────────────────────────────┐
  │  PostgreSQL connection pool: 20/20 connections exhausted     │
  │  Every /api/* request: waiting for pool → timeout → 500 ❌  │
  │  Redis: connection refused (redis pod restarted) ❌          │
  │  Background job queue: stalled, no workers processing ❌     │
  │  Application functionally: DEAD for all user-facing work     │
  └──────────────────────────────────────────────────────────────┘

  Health check executes: GET http://localhost:8080/health
  Handler code:
    func healthHandler(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
        w.Write([]byte(`{"status":"ok"}`))
        // Nothing else. No DB ping. No dependency check.
    }
  Health check result: HTTP 200 ✅ (from load balancer's perspective)

  Load balancer decision: "This instance is healthy. Send more traffic."
  User experience: Every single request fails with 500. ❌

  What every monitoring system reports:
  ├── Health check status:       HEALTHY ✅ (LIE)
  ├── Error rate:                100%    ❌ (TRUTH)
  ├── DB connection pool usage:  100%    ❌ (TRUTH)
  └── Active instances:          "All healthy" ✅ (LIE)

  Engineer looking at dashboards: utterly confused.
  Time to identify root cause: 30 to 90 minutes of investigation.
```

The situation becomes even more pernicious when the failing instance is one of several replicas behind a load balancer. Because the load balancer continues to route traffic to the lying healthy instance alongside genuinely healthy instances, the failure is intermittent from the user's perspective. Some requests succeed — those routed to the genuinely healthy replicas. Some fail — those routed to the broken replica. The intermittent nature of the failure makes it harder to reproduce consistently, harder to correlate with a specific deployment event, and harder to diagnose through logs because the errors appear scattered across multiple instances rather than concentrated on one clearly broken pod.

## 4. The Scale Trigger — When Dependency Failures Cascade Through Phantom Health

The phantom healthy instance problem becomes a cascade amplifier during infrastructure failures — precisely the moments when your health checking system should be working hardest to protect users. When a database server experiences elevated latency, connection timeouts, or becomes temporarily unavailable due to a failover event, a correctly implemented health check system should detect this condition within seconds, mark the dependent application instances as unhealthy, remove them from the load balancer's rotation, and either restart them (if a liveness probe detects the issue) or hold them out of rotation until the database recovers (if a readiness probe manages this).

With a lying health check, none of this protective behavior occurs. The database begins experiencing connection timeouts. Application instances attempt to serve user requests and fail when their database calls time out. The health check runs at its regular interval, receives a cheerful 200 from the static handler, and reports all instances as healthy. The load balancer continues routing traffic uniformly across all instances. As the database situation worsens — perhaps the connection pool on each instance becomes exhausted — the failure rate climbs from sporadic errors to near-total unavailability. At peak failure, you have a system where every instance is reporting healthy, the orchestrator is routing full traffic loads to all of them, and nearly every user request is failing. The health check system, which exists specifically to prevent this scenario, is actively making it worse by providing false assurance that prevents any automatic protective action from triggering.

```
              Cascade Failure With Lying vs. Honest Health Check
              ====================================================

  Event: PostgreSQL primary goes down. Failover to replica begins.
  Failover duration: 30 to 90 seconds of database unavailability.

  WITH LYING HEALTH CHECK (/health returns static 200):
  ─────────────────────────────────────────────────────────────
  t=0s:    DB goes down. All app instances: cannot query DB.
  t=0-90s: Every user request → 500 error (DB unavailable)
           Health check → 200 OK (static, never checks DB)
           Load balancer → routes full traffic to all instances
           Users impacted: 100% during full 90-second window ❌

  t=90s:   DB failover completes. App reconnects. Service recovers.
  Total user impact: 90 seconds of 100% error rate. Full blast.

  WITH HONEST HEALTH CHECK (/healthz checks db.Ping()):
  ─────────────────────────────────────────────────────────────
  t=0s:    DB goes down. All app instances: cannot query DB.
  t=5s:    Readiness probe fires: db.Ping() fails → returns 503
           Kubernetes: removes all instances from Service Endpoints
           Load balancer: routes zero traffic (returns 503 from LB itself)
           Users impacted: receive clear 503 "Service Unavailable" ← honest ✅

  t=90s:   DB failover completes. Readiness probe: db.Ping() succeeds → 200
  t=95s:   Kubernetes: adds instances back to Service Endpoints
  t=95s:   Load balancer: resumes routing traffic
  t=95s:   Users: service restored cleanly.

  Net difference: Both scenarios have 90 seconds of DB unavailability.
  Lying health check: 90s of silent 500 errors scattered unpredictably.
  Honest health check: 90s of clean 503 + instant recovery. Zero phantom traffic.
```

The honest health check does not make the database failure shorter. The database is down for ninety seconds in both scenarios. What it changes is the user experience of that failure and the operational clarity with which the engineering team can observe and respond to it. A 503 from the load balancer is semantically correct — it means the service is temporarily unavailable — and it is cacheable, retryable, and understandable to calling clients. A 500 from the application scattered intermittently across users implies an application bug, confuses retry logic, corrupts client-side caches, and leaves engineers hunting for a code regression that does not exist.

## 5. The Liveness vs. Readiness Distinction — Two Different Questions

One of the most important architectural insights in health check design is recognizing that "is this container worth keeping alive?" and "is this container ready to serve traffic right now?" are two fundamentally different questions that require two fundamentally different answers. Kubernetes formalizes this distinction through its liveness probe and readiness probe, and understanding the purpose and failure semantics of each is essential to designing a health check strategy that behaves correctly across all failure scenarios.

The **liveness probe** answers the question: "Is this process still in a valid, functioning state, or has it entered a state from which it cannot recover without being restarted?" The canonical failure mode that a liveness probe is designed to detect is a deadlock or an infinite loop — a situation where the process is running, consuming CPU or memory, but is no longer making progress and will never recover without external intervention. When a liveness probe fails, Kubernetes kills the container and restarts it. This is a destructive action and should be triggered only by conditions from which the process genuinely cannot recover on its own. Triggering a liveness probe failure due to a slow database causes Kubernetes to restart your application constantly during database degradation — which makes the overall situation significantly worse, not better, because you now have both a database problem and constantly-restarting application instances.

The **readiness probe** answers the question: "Is this particular instance currently capable of serving user traffic correctly?" A readiness probe failure does not restart the container — it merely removes the pod from the load balancer's endpoint list, shielding users from a temporarily degraded instance while leaving the process intact and potentially able to recover. This is the correct response to dependency failures like database connection exhaustion or cache unavailability. The application process should remain alive so that it can detect when the dependency recovers and become ready again, without requiring the overhead of a full container restart.

```
              Liveness vs. Readiness — Design Decision Framework
              ====================================================

  LIVENESS PROBE (/livez) — "Am I alive at all?"
  ──────────────────────────────────────────────────────────────
  Checks:
  ├── HTTP server is accepting connections              ✅ include
  ├── No deadlock detected (goroutine count reasonable) ✅ include
  ├── Process not in unrecoverable panic state          ✅ include
  ├── Database connectivity                             ❌ exclude
  └── External service availability                    ❌ exclude

  Failure action: Container is KILLED and RESTARTED by kubelet.
  Set failure threshold HIGH (e.g., 3 failures × 30s = 90s before restart).
  The cost of a false positive here is a container restart under load.

  READINESS PROBE (/readyz) — "Am I ready to serve users?"
  ──────────────────────────────────────────────────────────────
  Checks:
  ├── HTTP server is accepting connections              ✅ include
  ├── Database: db.Ping() succeeds                     ✅ include
  ├── Redis: PING command returns PONG                 ✅ include
  ├── Connection pool: available connections > threshold ✅ include
  ├── Critical external API reachable                  ✅ include (if sync dependency)
  └── Cache warmed / migrations complete               ✅ include (if required)

  Failure action: Pod REMOVED from Service Endpoints (not killed).
  Set failure threshold LOW (e.g., 1 failure = immediately out of rotation).
  Recovery is automatic when checks start passing again.

  Separate URL, separate logic, separate consequences.
```

The critical implication of this distinction is that you should almost never include external dependency checks in your liveness probe. A liveness probe that checks database connectivity will kill and restart your container every time the database has a brief hiccup — creating a thundering herd of restarting containers that hammer the recovering database with new connection attempts simultaneously, potentially delaying the database's recovery rather than aiding it. Liveness probes should test only conditions that are intrinsic to the process itself and from which the process cannot self-recover. Readiness probes should test every external dependency that is required for the instance to correctly serve user traffic.

## 6. Implementing an Honest Health Check — In Depth

A well-designed health check endpoint is a small but precise piece of engineering that requires careful thought about which dependencies to check, how to check them efficiently, what timeouts to apply, and how to aggregate and report the results. The goal is to accurately reflect the application's ability to serve user traffic in a check that executes in well under one second, does not itself add meaningful load to the dependencies it checks, and returns actionable information when something is wrong.

The following implementation demonstrates a production-grade dual health check endpoint for a Go application that depends on PostgreSQL and Redis. The `/livez` endpoint performs only process-level checks, while the `/readyz` endpoint performs a comprehensive dependency health verification with individual timeouts to prevent the health check itself from hanging indefinitely if a dependency is severely degraded:

```go
// handlers/health.go
package handlers

import (
    "context"
    "database/sql"
    "encoding/json"
    "net/http"
    "time"

    "github.com/redis/go-redis/v9"
)

type HealthStatus struct {
    Status       string            `json:"status"`
    Dependencies map[string]string `json:"dependencies,omitempty"`
}

// LivezHandler answers: "Is the process alive and not deadlocked?"
// Used as a Kubernetes liveness probe.
// Never checks external dependencies — that would cause restarts on DB outages.
func LivezHandler(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusOK)
    json.NewEncoder(w).Encode(HealthStatus{Status: "alive"})
}

// ReadyzHandler answers: "Is this instance ready to serve user traffic?"
// Used as a Kubernetes readiness probe.
// Checks all critical dependencies. Returns 503 if any are unavailable.
func ReadyzHandler(db *sql.DB, rdb *redis.Client) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // Use a short context timeout for the entire health check.
        // Health checks must never hang — if a dependency is completely
        // unreachable, we want to fail fast, not wait indefinitely.
        ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
        defer cancel()

        statuses := make(map[string]string)
        allHealthy := true

        // --- Check 1: PostgreSQL ---
        // db.PingContext uses a connection from the pool and sends a lightweight
        // query. It verifies the pool has available connections AND the DB responds.
        if err := db.PingContext(ctx); err != nil {
            statuses["postgres"] = "unhealthy: " + err.Error()
            allHealthy = false
        } else {
            statuses["postgres"] = "healthy"
        }

        // --- Check 2: Redis ---
        // PING is the lightest possible Redis command — O(1), no data access.
        if err := rdb.Ping(ctx).Err(); err != nil {
            statuses["redis"] = "unhealthy: " + err.Error()
            allHealthy = false
        } else {
            statuses["redis"] = "healthy"
        }

        // --- Check 3: Connection pool saturation guard ---
        // If pool is heavily utilized, start shedding traffic before it exhausts.
        stats := db.Stats()
        if stats.OpenConnections > 0 {
            utilization := float64(stats.InUse) / float64(stats.OpenConnections)
            if utilization > 0.9 {
                statuses["db_pool"] = "warning: pool utilization above 90%"
                // Consider failing readiness here to prevent pool exhaustion.
                allHealthy = false
            } else {
                statuses["db_pool"] = "healthy"
            }
        }

        w.Header().Set("Content-Type", "application/json")

        if !allHealthy {
            // 503 Service Unavailable — semantically correct for a
            // temporarily degraded instance. Kubernetes removes pod from
            // endpoint list. Load balancer stops routing here.
            w.WriteHeader(http.StatusServiceUnavailable)
            json.NewEncoder(w).Encode(HealthStatus{
                Status:       "unhealthy",
                Dependencies: statuses,
            })
            return
        }

        w.WriteHeader(http.StatusOK)
        json.NewEncoder(w).Encode(HealthStatus{
            Status:       "healthy",
            Dependencies: statuses,
        })
    }
}
```

The same pattern implemented for a Node.js application using Express:

```javascript
// routes/health.js

// GET /livez — liveness: is the process alive?
// Kubernetes liveness probe. Never fails due to external dependencies.
router.get('/livez', (req, res) => {
    res.status(200).json({ status: 'alive' });
});

// GET /readyz — readiness: can we serve user traffic right now?
// Kubernetes readiness probe. Fails if any critical dependency is down.
router.get('/readyz', async (req, res) => {
    const statuses = {};
    let allHealthy = true;

    // Check PostgreSQL
    try {
        await db.query('SELECT 1');  // Lightweight connectivity check
        statuses.postgres = 'healthy';
    } catch (err) {
        statuses.postgres = `unhealthy: ${err.message}`;
        allHealthy = false;
    }

    // Check Redis
    try {
        await redisClient.ping();   // Redis PING command
        statuses.redis = 'healthy';
    } catch (err) {
        statuses.redis = `unhealthy: ${err.message}`;
        allHealthy = false;
    }

    if (!allHealthy) {
        return res.status(503).json({ status: 'unhealthy', dependencies: statuses });
    }

    res.status(200).json({ status: 'healthy', dependencies: statuses });
});
```

And the corresponding Dockerfile `HEALTHCHECK` and Kubernetes probe configuration:

```dockerfile
# Dockerfile — use the readiness endpoint for Docker's HEALTHCHECK
# --interval: check every 30 seconds
# --timeout: fail the check if it takes more than 5 seconds
# --start-period: grace period at startup before checks count (migration time)
# --retries: require 3 consecutive failures before marking unhealthy
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
    CMD wget -qO- http://localhost:8080/readyz || exit 1
```

```yaml
# kubernetes/deployment.yaml — probe configuration
containers:
  - name: myapp
    livenessProbe:
      httpGet:
        path: /livez
        port: 8080
      initialDelaySeconds: 15    # Give app time to start
      periodSeconds: 30          # Check every 30 seconds
      timeoutSeconds: 5          # Fail if no response in 5s
      failureThreshold: 3        # Restart after 3 consecutive failures (90s)

    readinessProbe:
      httpGet:
        path: /readyz
        port: 8080
      initialDelaySeconds: 5     # Check sooner — affects traffic routing
      periodSeconds: 10          # Check more frequently — faster recovery detection
      timeoutSeconds: 3          # Tighter timeout — health check must be fast
      failureThreshold: 1        # Remove from rotation after 1 failure (10s detection)
      successThreshold: 2        # Require 2 successes before re-admitting to rotation
```

## 7. What to Check — Dependency Prioritization

Not every dependency that an application uses should necessarily be included in the readiness probe. The inclusion of a dependency in the health check should be proportional to two factors: how critical that dependency is to the application's ability to serve its primary function, and how reliably the dependency can be checked without introducing false positives. A thoughtful dependency prioritization framework helps you decide what to include:

```
              Dependency Inclusion Decision Framework
              ==========================================

  Dependency         Critical?  Check Type          Include in /readyz?
  ────────────────────────────────────────────────────────────────────────
  Primary database   YES        db.Ping() / SELECT 1  Always ✅
  Session cache      YES        PING                  Always ✅
  Message queue      YES        queue.Ping()          Yes, if sync consumer ✅
  Object storage     MAYBE      HEAD /bucket          Yes, if writes are sync ⚠️
  Email provider     NO         (async, has retry)    No — tolerate brief outage ❌
  SMS gateway        NO         (async, has retry)    No — failure is buffered ❌
  Analytics system   NO         (async, best-effort)  Never — non-critical ❌
  Feature flag svc   MAYBE      /flags health         Only if blocking on startup ⚠️
  ────────────────────────────────────────────────────────────────────────

  Rule of thumb: Include a dependency if and only if
  a failure in that dependency makes your instance unable
  to produce correct responses to the primary user-facing operations.
  Asynchronous, retried, or degraded-mode-capable dependencies
  should generally NOT block readiness.
```

The inclusion of a dependency in a readiness check introduces a coupling between that dependency's availability and your application's routing status. For truly non-critical dependencies — email providers, analytics pipelines, audit log writers — this coupling produces more harm than good. A transient unavailability of your email-sending service should not cause your entire application to drop out of the load balancer's rotation. Design your health check inclusions to reflect the actual impact of each dependency's failure on your application's ability to serve its core purpose.

## 8. The Response Body as Operational Intelligence

A health check endpoint that returns only an HTTP status code is minimally functional. A health check endpoint that returns a structured body containing the individual status of each checked dependency, the current timestamp, the application version, and optionally the duration of each dependency check transforms a binary signal into a rich source of operational intelligence. When an on-call engineer is investigating why the readiness probe is failing, the ability to hit the `/readyz` endpoint in a browser or with `curl` and immediately see which specific dependency is reporting unhealthy — and what error message it is producing — can reduce mean time to root cause identification from minutes to seconds.

```json
{
  "status": "unhealthy",
  "version": "v1.2.3",
  "timestamp": "2025-09-23T09:45:01Z",
  "dependencies": {
    "postgres": {
      "status": "unhealthy",
      "error": "dial tcp 10.0.1.45:5432: connect: connection refused",
      "duration_ms": 3001
    },
    "redis": {
      "status": "healthy",
      "duration_ms": 2
    },
    "db_pool": {
      "status": "healthy",
      "open_connections": 15,
      "in_use": 8,
      "utilization_pct": 53
    }
  }
}
```

This response body tells the engineer, in under five seconds of reading, that PostgreSQL is refusing connections — likely the primary database is unreachable — while Redis is healthy and the connection pool utilization is normal. The `duration_ms` field reveals that the postgres check timed out after three seconds, strongly suggesting a network-level issue rather than an application-level error. The on-call engineer can now proceed directly to investigating the database network path rather than spending time eliminating irrelevant hypotheses.

## 9. The Golden Rule

> A health check that does not reflect the real operational capability of the application is not a safety net — it is a mask that conceals failure from the infrastructure that is supposed to respond to it. The load balancer routes traffic to what the health check calls healthy; if the health check lies, the load balancer routes traffic to broken instances. The monitoring system escalates alerts based on health check failures; if the health check never fails when the application is broken, no alert ever fires. The entire automated resilience apparatus of a distributed system — automatic traffic rerouting, pod replacement, on-call notification — depends on the accuracy of the signal that health checks provide. Implement a `/readyz` endpoint that pings every critical dependency with an appropriate timeout and returns 503 if any fail. Implement a separate `/livez` endpoint that tests only process-level liveness and never fails due to external dependencies. Never check the database in your liveness probe and never return a static 200 from your readiness probe. The ten minutes invested in writing an honest health check will prevent the hours of confused investigation that a lying health check reliably produces at the worst possible moment.

A phantom healthy instance is a ghost in your infrastructure — invisible to your tools, invisible to your orchestrator, but entirely visible to your users, in the form of errors.
