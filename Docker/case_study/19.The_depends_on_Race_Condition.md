# The depends_on Race Condition

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Restaurant That Opens Before the Kitchen Is Ready

A restaurant opens its doors at noon. The host begins seating customers immediately. Customers are seated, menus are distributed, and orders are taken. But the kitchen staff only finished setting up their stations at 12:04. For those first four minutes, every order placed goes to a kitchen that cannot yet fulfill it. The waitstaff take the orders in good faith, the kitchen processes says it is running, but the actual capacity to serve food does not exist yet. Orders placed in those first four minutes either return as errors — "sorry, the kitchen isn't ready yet" — or sit in a queue until the kitchen comes online, depending on how the restaurant handles the gap.

The `depends_on` directive in Docker Compose is a restaurant that opens its doors — starts seating customers, in this case starting the application container — the moment it confirms the kitchen building is occupied, without verifying that the kitchen is actually operational and ready to accept orders. The application container starts, its process begins, and its very first action is to connect to the database. PostgreSQL, however, is still in the middle of its initialization sequence: loading shared memory, starting background workers, loading the WAL, and finally binding to its port and accepting connections. That initialization takes two to five seconds on a fast machine, longer on slow CI hardware. The application's first connection attempt lands in the middle of this initialization window and receives `connection refused` — not because PostgreSQL is broken, but because it is not ready yet.

## 2. What `depends_on` Actually Controls — Container State vs. Service Readiness

The `depends_on` directive controls the **container start order** — the sequence in which Docker Compose sends `docker start` signals to containers. It is a coordination mechanism at the container orchestration layer, not at the application readiness layer. When you write `depends_on: postgres`, Docker Compose guarantees that the `postgres` container will be started before the `api` container receives its start signal. It does not, cannot, and was never designed to guarantee that the PostgreSQL process inside the `postgres` container is ready to accept connections at the moment the `api` container starts.

This distinction is fundamental and must be internalized: **a running container is not a ready service**. A container transitions to the "running" state the moment the kernel has created the container's namespaces, started the specified process, and confirmed that the process has not immediately exited. For PostgreSQL, this moment corresponds to the instant the `docker-entrypoint.sh` script begins executing. PostgreSQL's own initialization — loading the data directory, starting the checkpointer, the autovacuum daemon, the WAL writer, the background writer, binding the listening socket, and finally accepting connections — follows over the next several seconds. The container is running throughout all of this. But the service is not ready.

```
              depends_on Start Order vs. Service Readiness — The Gap
              ==========================================================

  docker compose up (without health check condition):

  t=0.0s:  Docker Compose resolves dependency order:
           postgres must start before api (depends_on: postgres)

  t=0.1s:  Docker starts postgres container.
           docker-entrypoint.sh begins executing as root.
           Container state: RUNNING ✅ (kernel reports process is alive)
           PostgreSQL state: INITIALIZING (not ready for connections) ❌

  t=0.1s:  Docker Compose: "postgres is running" → start api container.
           (depends_on with no condition = waits only for RUNNING state)

  t=0.2s:  Docker starts api container.
           Application process begins. First action: connect to postgres.
           DB connect attempt: postgres://postgres:5432/myapp

  t=0.2s:  api TCP SYN → postgres container port 5432
           PostgreSQL not yet listening on :5432 → connection refused ❌
           Migration runner: "Error: connect ECONNREFUSED 172.20.0.3:5432"
           Application exits with code 1. ❌

  t=2.5s:  PostgreSQL finishes initialization. Port 5432 now open.
           Listening. Ready to accept connections. ✅
           api container: already crashed. Nobody is connecting. ✅ (too late)

  Meanwhile, postgres container:
  ├── t=0.1s: docker-entrypoint.sh starts (root, initializes data directory if new)
  ├── t=0.3s: initdb completes (or skips if data dir exists)
  ├── t=0.8s: PostgreSQL process starts, loads config
  ├── t=1.5s: Background workers starting (checkpointer, autovacuum, WAL writer)
  ├── t=2.0s: WAL recovery complete (if restarting from crash)
  └── t=2.5s: Port 5432 bound. LOG: "database system is ready to accept connections" ✅

  The gap between t=0.2s (api starts) and t=2.5s (postgres ready): 2.3 seconds.
  The probability of hitting this gap: HIGH on cold start. Deterministic on CI.
```

The probabilistic nature of this failure is what makes it so frustrating in practice. On a developer's fast local machine with a warm Docker image cache, the gap may be narrow enough that the application starts in 60–70% of cases without error. The remaining 30–40% of cold starts produce a connection refused error. The developer runs `docker compose up` again, it works, and they conclude the first failure was a fluke. They do not investigate further. When the same Compose file is used in CI — where hardware is often slower, image caches may be cold, and every pipeline run is a fresh environment — the failure rate climbs to near 100%, and the team is forced to confront a bug that local development made seem inconsequential.

## 3. The PostgreSQL Startup Sequence — What Happens Inside the Container

To appreciate why the gap exists, it helps to understand what PostgreSQL is doing during those two to five seconds between container start and connection acceptance. The PostgreSQL official Docker image uses a layered entrypoint script that performs several operations before the database process even begins:

```
              PostgreSQL Container Startup — Detailed Phase Breakdown
              ==========================================================

  Phase 1 — Entrypoint Script Initialization (runs as root):
  ─────────────────────────────────────────────────────────────────────
  ├── Check if data directory ($PGDATA) is empty or initialized
  ├── If empty: run initdb to create a new cluster
  │   ├── Creates pg_hba.conf, postgresql.conf, PG_VERSION file
  │   ├── Creates template0 and template1 databases
  │   └── Duration: 0.5 – 3.0 seconds (depends on disk speed)
  ├── Apply POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB environment vars
  │   ├── Creates the specified database and user
  │   └── Duration: 0.1 – 0.5 seconds
  ├── Process /docker-entrypoint-initdb.d/ scripts (SQL or shell)
  │   └── Duration: depends on scripts (could be seconds to minutes)
  └── chown data directory to postgres user, exec gosu postgres postgres

  Phase 2 — PostgreSQL Process Startup (runs as postgres user):
  ─────────────────────────────────────────────────────────────────────
  ├── Load postgresql.conf and pg_hba.conf
  ├── Allocate shared memory buffers (shared_buffers)
  ├── Start background processes:
  │   ├── checkpointer
  │   ├── background writer
  │   ├── WAL writer
  │   ├── autovacuum launcher
  │   └── stats collector
  ├── WAL recovery (if recovering from unclean shutdown)
  │   └── Duration: seconds to minutes depending on WAL backlog
  ├── Bind listening socket on port 5432
  └── LOG: "database system is ready to accept connections" ✅

  Total cold start duration (first ever run, creating database):  3 – 10 seconds
  Total warm start duration (data directory exists, clean shutdown): 1 – 3 seconds
  Total recovery duration (data directory exists, dirty shutdown):  2 – 60 seconds

  The application's connection attempt lands somewhere in this sequence.
  Only after the LAST step is the connection guaranteed to succeed.
```

The variability in startup time is the core reason why retry logic is necessary even when health checks are in place. A health check configured with `interval: 5s` and `start_period: 10s` may pass during the initial grace period, triggering the dependent container to start just as PostgreSQL begins WAL recovery from a crash — recovery that takes longer than the health check grace period anticipated. The application starts, connects successfully during a brief window when PostgreSQL accepts connections, and then loses the connection mid-recovery. Robust retry logic with exponential backoff handles this edge case gracefully regardless of the timing.

## 4. The `condition: service_healthy` Solution — Health Checks as Readiness Gates

Docker Compose provides the `condition` key on `depends_on` declarations, which changes the dependency from "wait for container start" to "wait for health check to pass." This transforms `depends_on` from a container orchestration directive into a service readiness gate. The dependent container is not started until the dependency's health check has passed the configured number of consecutive times.

```yaml
# docker-compose.yml — Correct depends_on with health check readiness gate

version: "3.9"

services:
  api:
    build: .
    environment:
      DB_URL:    postgres://appuser:secret@postgres:5432/myapp
      REDIS_URL: redis://redis:6379/0
    depends_on:
      postgres:
        condition: service_healthy   # ← Wait for pg_isready to pass ✅
      redis:
        condition: service_started   # ← Redis starts fast; started is sufficient
    ports:
      - "8080:8080"

  migration:
    build: .
    command: ["sh", "-c", "npm run migrate"]
    environment:
      DB_URL: postgres://appuser:secret@postgres:5432/myapp
    depends_on:
      postgres:
        condition: service_healthy   # ← Migrations need a truly ready DB ✅
    restart: "no"                    # Run once, don't restart

  postgres:
    image: postgres:16.2-alpine3.19@sha256:...
    environment:
      POSTGRES_USER:     appuser
      POSTGRES_PASSWORD: secret
      POSTGRES_DB:       myapp
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      # pg_isready: lightweight tool that checks if PostgreSQL is accepting connections.
      # -U: the user to check with
      # -d: the database to check (optional but more specific than checking any db)
      # -q: quiet mode — only exit code matters, no output on success
      test: ["CMD-SHELL", "pg_isready -U appuser -d myapp -q"]
      interval: 5s        # Run the check every 5 seconds
      timeout: 5s         # Mark unhealthy if check takes longer than 5 seconds
      retries: 10         # Allow 10 consecutive failures before marking unhealthy
      start_period: 30s   # Don't count failures during the first 30 seconds
                          # (gracefully handles slow machines, WAL recovery)
    restart: unless-stopped

  redis:
    image: redis:7.2-alpine3.19@sha256:...
    command: redis-server --appendonly yes --auto-aof-rewrite-percentage 100
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    restart: unless-stopped

volumes:
  pgdata:
  redisdata:
```

The `start_period` directive deserves particular attention — it is one of the most important and most underused health check configuration options. During the `start_period` window, health check failures do not count toward the `retries` limit. The container is considered in a "starting" state rather than "unhealthy." This is critical for PostgreSQL because the first time a container runs — when it must execute `initdb` to create the cluster — the initialization can take ten or more seconds on slow hardware. Without `start_period`, the health check would immediately begin counting failures from t=0, mark the container unhealthy after 50 seconds (10 retries × 5 second intervals), and prevent the dependent container from ever starting. With `start_period: 30s`, the health check gives PostgreSQL a generous window to complete initialization before failure counting begins.

```
              With condition: service_healthy — Correct Timeline
              =====================================================

  t=0.0s:  Compose starts postgres container.
           PostgreSQL begins initialization.

  t=0.5s:  Compose runs first health check: pg_isready → exit 1 (not ready yet)
           start_period active → failure NOT counted toward retries

  t=5.0s:  Second health check: pg_isready → exit 1 (still initializing)
           start_period active → failure NOT counted

  t=2.5s:  PostgreSQL finishes initialization.
           LOG: "database system is ready to accept connections"

  t=5.0s:  Health check: pg_isready → exit 0 (READY) ✅
           Container status: healthy ✅

  t=5.1s:  Compose condition: service_healthy satisfied.
           Compose starts api container.

  t=5.3s:  api process begins. Connects to postgres://postgres:5432/myapp
           Connection succeeds ✅
           Migrations run ✅
           Application serves requests ✅

  Zero connection refused errors. Deterministic startup every time.
```

## 5. Application-Level Retry Logic — Defense in Depth

Health checks with `condition: service_healthy` solve the Docker Compose startup ordering problem. But they do not solve the general problem of transient database unavailability that can occur at any point during an application's lifetime — not just on startup. The database can restart due to a configuration change, a crash, a planned maintenance operation, or a Kubernetes pod eviction. An application that panics on the first failed connection attempt will crash-loop every time the database has a transient hiccup. Application-level retry logic with exponential backoff is the defense that makes the application resilient to all forms of transient database unavailability, not just startup race conditions.

```go
// Go — Database connection with retry and exponential backoff at startup
package database

import (
    "database/sql"
    "fmt"
    "log"
    "time"

    _ "github.com/jackc/pgx/v5/stdlib"
)

// Connect attempts to establish and verify a database connection,
// retrying with exponential backoff until maxAttempts is reached.
// This handles both the depends_on startup race and any transient
// DB unavailability during the application's lifetime.
func Connect(dsn string) (*sql.DB, error) {
    const (
        maxAttempts     = 10
        initialInterval = 500 * time.Millisecond
        maxInterval     = 30 * time.Second
        backoffFactor   = 2.0
    )

    var (
        db       *sql.DB
        err      error
        interval = initialInterval
    )

    for attempt := 1; attempt <= maxAttempts; attempt++ {
        db, err = sql.Open("pgx", dsn)
        if err != nil {
            // sql.Open rarely fails — it only validates the DSN format.
            // An error here is configuration, not connectivity.
            return nil, fmt.Errorf("invalid database DSN: %w", err)
        }

        // Ping verifies the connection is actually alive and the database
        // is ready to accept queries. This is the actual readiness check.
        if pingErr := db.Ping(); pingErr != nil {
            db.Close()
            log.Printf(
                "[DB] Attempt %d/%d: connection failed (%v). Retrying in %s...",
                attempt, maxAttempts, pingErr, interval,
            )

            if attempt == maxAttempts {
                return nil, fmt.Errorf(
                    "database unavailable after %d attempts: %w",
                    maxAttempts, pingErr,
                )
            }

            time.Sleep(interval)

            // Exponential backoff with cap
            interval = time.Duration(float64(interval) * backoffFactor)
            if interval > maxInterval {
                interval = maxInterval
            }
            continue
        }

        // Connection verified. Configure pool.
        db.SetMaxOpenConns(25)
        db.SetMaxIdleConns(5)
        db.SetConnMaxLifetime(5 * time.Minute)
        db.SetConnMaxIdleTime(30 * time.Second)

        log.Printf("[DB] Connected successfully on attempt %d.", attempt)
        return db, nil
    }

    // Unreachable, but satisfies compiler
    return nil, fmt.Errorf("database connection failed")
}
```

```javascript
// Node.js — pg Pool with startup retry
const { Pool } = require('pg');

async function createDatabasePool(connectionString) {
    const pool = new Pool({
        connectionString,
        max:              20,
        idleTimeoutMillis: 10_000,
        connectionTimeoutMillis: 3_000,
    });

    const maxAttempts = 10;
    let interval = 500; // ms

    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
            // Attempt to acquire a connection from the pool.
            const client = await pool.connect();
            await client.query('SELECT 1'); // Verify DB is functional
            client.release();

            console.log(`[DB] Connected successfully on attempt ${attempt}.`);
            return pool;
        } catch (err) {
            console.warn(
                `[DB] Attempt ${attempt}/${maxAttempts} failed: ${err.message}. ` +
                `Retrying in ${interval}ms...`
            );

            if (attempt === maxAttempts) {
                throw new Error(`Database unavailable after ${maxAttempts} attempts: ${err.message}`);
            }

            await new Promise(resolve => setTimeout(resolve, interval));
            interval = Math.min(interval * 2, 30_000); // Exponential backoff, max 30s
        }
    }
}

// Usage in application startup:
async function startServer() {
    const pool = await createDatabasePool(process.env.DB_URL);
    await runMigrations(pool);

    app.locals.db = pool;
    app.listen(3000, () => console.log('Server listening on :3000'));
}

startServer().catch(err => {
    console.error('Fatal startup error:', err.message);
    process.exit(1);
});
```

## 6. The Migration Ordering Problem — A Separate But Related Race

Applications that run database migrations on startup — a common pattern in Go, Node.js, and Python applications using tools like `migrate`, `Flyway`, `golang-migrate`, or Sequelize — face a more specific version of the depends_on race condition: the migration must complete before the application begins serving requests, and both must complete after PostgreSQL is ready.

The cleanest architectural solution is to separate the migration process from the application process as a distinct Compose service with `restart: "no"`. The application service then depends on both the postgres service (via `service_healthy`) and the migration service (via `service_completed_successfully`):

```yaml
services:
  # Run migrations as a one-shot service
  migrate:
    build: .
    command: ["./migrate", "-path", "./migrations", "-database", "$DB_URL", "up"]
    environment:
      DB_URL: postgres://appuser:secret@postgres:5432/myapp
    depends_on:
      postgres:
        condition: service_healthy   # ← Postgres must be ready ✅
    restart: "no"                    # Run once. Don't restart on success.

  api:
    build: .
    environment:
      DB_URL: postgres://appuser:secret@postgres:5432/myapp
    depends_on:
      postgres:
        condition: service_healthy          # ← Postgres must be ready ✅
      migrate:
        condition: service_completed_successfully  # ← Migrations must be done ✅
    ports:
      - "8080:8080"

  postgres:
    image: postgres:16.2-alpine3.19
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d myapp -q"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 30s
```

```
              Migration Ordering — Correct Three-Stage Startup
              ===================================================

  Stage 1: postgres container starts.
           Health check: pg_isready runs every 5s.
           Waits until PostgreSQL is ready to accept connections.
           Status: service_healthy ✅

  Stage 2: migrate container starts (depends_on postgres: service_healthy).
           Runs golang-migrate, Flyway, or similar.
           Applies all pending migration files to the database.
           Exits 0 on success.
           Status: service_completed_successfully ✅

  Stage 3: api container starts (depends_on migrate: service_completed_successfully).
           Database is ready AND schema is up to date.
           Application begins serving requests immediately. ✅

  No race conditions. No partial schema. Deterministic every time.
  In CI: same behavior. On cold start: same behavior. On warm start: same.
```

## 7. The `pg_isready` Command — What It Actually Checks

The `pg_isready` command, which is the standard health check tool for PostgreSQL in Docker environments, is worth understanding in detail because its behavior is nuanced. `pg_isready` performs a TCP connection to the specified host and port and sends a startup packet. PostgreSQL's response to this packet — even before authentication — indicates whether the server is accepting connections. `pg_isready` does not authenticate, does not run any queries, and does not verify that the database or user exists. It simply confirms that PostgreSQL is listening and responsive at the network level.

This means that `pg_isready` can pass even if the specified database does not yet exist (if the container is still running `initdb` scripts to create it), or if the specified user does not yet exist. For most use cases, `pg_isready -U appuser -d myapp` is a sufficiently specific check because PostgreSQL will only accept connection attempts on the specified database once the database exists. For cases requiring higher specificity, a more thorough health check that actually executes a query is available:

```yaml
healthcheck:
  # More thorough: actually connects and runs a query
  # Catches cases where pg_isready passes but the database isn't usable
  test: >
    CMD-SHELL
    psql -U appuser -d myapp -c "SELECT 1" -q --no-align --tuples-only
    | grep -q "^1$"
  interval: 5s
  timeout: 5s
  retries: 10
  start_period: 30s
```

## 8. Diagnosing the Race in the Wild

When intermittent startup failures occur and the `depends_on` race is suspected, a small set of diagnostic observations confirms or rules it out quickly:

```bash
# ── Observe the startup timing gap directly ───────────────────────────────────
# Terminal 1: watch postgres health status in real time
watch -n 0.5 'docker inspect postgres_container \
    --format="Status: {{.State.Status}} | Health: {{.State.Health.Status}}"'
# Watch for: Status: running | Health: starting → Health: healthy
# The transition from "starting" to "healthy" is when the api should start.

# ── Check container health in docker compose ps ──────────────────────────────
docker compose ps
# SERVICE     STATUS              PORTS
# postgres    running (healthy)   5432/tcp    ← healthy = pg_isready passing
# api         running             0.0.0.0:8080->8080/tcp

# ── Inspect health check history ────────────────────────────────────────────
docker inspect postgres_container \
    --format='{{range .State.Health.Log}}{{.Start}} | Exit: {{.ExitCode}} | {{.Output}}{{"\n"}}{{end}}'
# Shows last N health check results with timestamps and exit codes.
# ExitCode 0: healthy ✅
# ExitCode 1: unhealthy ❌ — PostgreSQL not yet accepting connections

# ── Confirm the race is the root cause ───────────────────────────────────────
docker compose logs api | grep -i "connection refused\|ECONNREFUSED\|could not connect"
docker compose logs api | head -20  # First log lines show startup error timing

docker compose logs postgres | grep "ready to accept connections"
# Timestamp on "ready to accept" vs timestamp on api's first connection error:
# If api error BEFORE postgres "ready": race condition confirmed ✅

# ── Verify depends_on condition is set ───────────────────────────────────────
docker compose config | grep -A 5 "depends_on"
# Should show:
# depends_on:
#   postgres:
#     condition: service_healthy   ← Correct ✅
# NOT:
# depends_on:
#   - postgres                    ← Only checks "started", not "healthy" ❌
```

## 9. The Golden Rule

> `depends_on` in Docker Compose controls the order in which containers are started, not the order in which services become ready to accept work. A container that is running is not necessarily a service that is ready. PostgreSQL, Redis, RabbitMQ, MongoDB, and every other data service requires some seconds after container start to complete their initialization sequences before accepting connections. The correct approach has two independent layers of defense: first, configure `condition: service_healthy` on every `depends_on` declaration that involves a stateful service, paired with an appropriate health check that verifies actual service readiness (not just container liveness); second, implement retry logic with exponential backoff in application startup code for every external dependency connection, because health checks and orchestration can never account for every form of transient unavailability that can occur during a long-running system's lifetime. The `start_period` directive on health checks provides a graceful window for slow initialization without immediately marking the service as unhealthy. Combine `condition: service_healthy` with `start_period`, `retries`, and application-level retry — and startup race conditions become structurally impossible rather than probabilistically unlikely.

A started container and a ready service are two different things separated by a non-trivial amount of time. Always design for that gap.
