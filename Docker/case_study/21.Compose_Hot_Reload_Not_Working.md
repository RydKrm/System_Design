# Compose Hot-Reload Not Working

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Security Camera That Films the Wrong Room

A building manager installs a motion-detection security camera in Room A, wired to an alarm in Room B. The intention is straightforward: when someone moves in Room A, the camera detects the motion, sends a signal, and the alarm in Room B activates. The system is tested — a technician waves in front of the camera in Room A, the alarm triggers immediately in Room B, and the test passes.

Now imagine that between the camera and the alarm is a translation relay — a small box that receives the motion signal from Room A and converts it into a format the alarm in Room B understands. Most of the time this relay works perfectly. But occasionally, under certain building configurations, the relay discards certain types of signals: it receives them, processes them partially, and then silently drops them without forwarding anything to the alarm. The camera continues recording. The alarm continues waiting. Room A has activity. Room B's alarm never sounds. From the operator's perspective, the motion detection system is "running" — all components are powered on, all connections are made — but the events are simply not propagating through the relay.

This is precisely the situation with file change notifications on Docker Desktop for macOS and Windows. The file watcher inside the container — whether nodemon, Air, Vite's HMR server, or webpack-dev-server — is running correctly. The bind mount is configured correctly. Files are genuinely changing on the host filesystem. But between the macOS or Windows host filesystem and the Linux file watcher inside the container lies a translation relay: the virtual machine that Docker Desktop uses to run the Linux container environment. inotify events — the Linux kernel mechanism for file change notifications — are simply not generated or propagated across this VM boundary in the way that file watchers expect, and the silent result is a watcher that appears to be running but never triggers a reload.

## 2. The Architecture of Docker Desktop — Why the VM Boundary Exists

Docker containers require a Linux kernel. The container runtime, the namespace isolation, the cgroup resource limits, the OverlayFS filesystem — all of these mechanisms are Linux kernel features. On a Linux host, containers run natively because the host kernel is already Linux. On macOS and Windows, there is no Linux kernel — only macOS's XNU kernel or the Windows NT kernel. Docker Desktop bridges this gap by running a lightweight Linux virtual machine and running all container processes inside that VM. The Docker daemon itself runs inside the VM.

On macOS (since Docker Desktop 4.x), Docker uses the Apple Hypervisor framework with a custom lightweight Linux kernel — originally HyperKit, then evolving to use Apple's Virtualization.framework. On Windows, Docker Desktop uses WSL2 (Windows Subsystem for Linux 2), which is a full Linux kernel running as a VM managed by Hyper-V. In both cases, when you mount a directory from your macOS or Windows host into a container, Docker Desktop uses a filesystem sharing mechanism to make the host directory accessible inside the VM and from there into the container.

```
              Docker Desktop Architecture — The File Change Event Path
              ===========================================================

  macOS / Windows Host                │  Linux VM           │  Container
  ──────────────────────────────────  │  ─────────────────  │  ──────────────
  Developer edits file.js             │                     │
  in VS Code on host filesystem       │                     │
         │                            │                     │
         ▼                            │                     │
  macOS: FSEvents notification        │                     │
  Windows: ReadDirectoryChangesW      │                     │
         │                            │                     │
         ▼                            │                     │
  Docker Desktop filesystem sync      │                     │
  (VirtioFS / gRPC FUSE / SMB)        │                     │
         │                            │                     │
         │ ← THE RELAY ─────────────→ │                     │
         │   File change propagated?  │ Linux inotify       │
         │   Depends on sync backend  │ event generated?    │
         │                            │    │                │
         │                            │    ▼                │
         │                            │  IN_MODIFY, IN_CLOSE_WRITE, etc.
         │                            │    │                │
         │                            │    │ ─────────────→ │
         │                            │    ▼                │
         │                            │  Container process  │
         │                            │  listening with:    │
         │                            │  inotify_add_watch  │
         │                            │  (Air, nodemon,     │
         │                            │   webpack, Vite)    │
         │                            │                     │
  The event chain breaks at the       │                     │
  filesystem sync layer:              │                     │
  Host edit → sync layer (may not     │ inotify never fires │ Watcher waits
  generate Linux inotify events)      │                     │ forever ❌
```

The core of the problem is that the filesystem sharing mechanism between the macOS/Windows host and the Linux VM was designed primarily for data correctness — ensuring that files written on the host are readable inside the container and vice versa — not for event fidelity. Generating correct Linux `inotify` events from host filesystem events requires additional infrastructure, and historically this infrastructure has been incomplete, unreliable, or dependent on specific versions of Docker Desktop and specific filesystem sharing backends.

## 3. Linux inotify — What File Watchers Actually Use

To understand why the VM boundary breaks file watching, you need to understand what file watchers use under the hood. Every file watcher in the Linux ecosystem — nodemon, Air, webpack-dev-server, Vite's HMR, Rollup's watch mode, `fswatch`, `watchman` — ultimately relies on one of two operating system mechanisms: inotify (the modern standard) or polling (the fallback).

**inotify** is a Linux kernel subsystem that allows a process to register a "watch" on a file or directory and receive events through a file descriptor whenever the watched file system object changes. The events are specific and granular: `IN_MODIFY` (file was modified), `IN_CLOSE_WRITE` (writable file was closed), `IN_CREATE` (new file created in directory), `IN_DELETE`, `IN_MOVED_FROM`, `IN_MOVED_TO`, and others. This mechanism is highly efficient because it is event-driven — the watching process sleeps until an event is delivered, consuming zero CPU while idle. The kernel itself tracks the change and notifies the watcher immediately when it occurs.

**Polling** is the fallback mechanism. The watcher periodically reads the metadata (modification timestamp, file size) of every watched file and compares it to previously recorded values. If any metadata has changed, the watcher triggers its reload logic. Polling does not depend on kernel event infrastructure — it works correctly on any filesystem and across any VM boundary, because it directly reads file content rather than waiting for a kernel event. Its cost is the CPU consumed by the periodic metadata reads, which scales linearly with the number of watched files and inversely with the polling interval.

```
              inotify vs Polling — Mechanism Comparison
              ============================================

  inotify (event-driven):
  ─────────────────────────────────────────────────────────────────────
  Setup:
    fd = inotify_init()
    inotify_add_watch(fd, "/app/src/", IN_MODIFY | IN_CLOSE_WRITE)
    // Watcher process now sleeps, consuming 0 CPU

  On file change:
    Kernel: detects change in watched path
    Kernel: writes inotify event to fd
    Watcher: wakes from sleep, reads event
    Watcher: triggers reload
    Total latency: ~1ms. CPU: 0% while idle. ✅

  On Docker Desktop (Mac/Windows) with bind mount:
    Developer edits file on host
    Host FS change → VirtioFS/FUSE sync → Linux VM filesystem
    Kernel in Linux VM: may or may not generate inotify event ⚠️
    If event generated: watcher works normally ✅
    If event NOT generated: watcher sleeps forever ❌
    Result: non-deterministic. Depends on sync backend version.

  Polling (periodic scan):
  ─────────────────────────────────────────────────────────────────────
  Setup:
    for each file in watch_list:
        record mtime, size = stat(file)

  Every N milliseconds:
    for each file in watch_list:
        current_mtime, current_size = stat(file)
        if current_mtime != recorded_mtime:
            trigger reload
            update recorded_mtime

  On Docker Desktop (Mac/Windows) with bind mount:
    stat() reads actual file metadata from the filesystem
    Filesystem sync delivers file content changes (reliably) ✅
    stat() sees updated mtime after change ✅
    Polling watcher triggers reload ✅

  Cost: CPU usage proportional to watch_list size × poll frequency
  1000 files × 1s polling: ~5-15% CPU continuously ❌
  100 files × 2s polling: ~0.5-1% CPU ✅ (acceptable)
```

## 4. Docker Desktop's Filesystem Sync Evolution — A Moving Target

Docker Desktop has used several different filesystem sharing backends over its history, and the inotify propagation behavior has varied between them. Understanding this history explains why some developers report that hot reload "works fine" on their Docker Desktop installation while others on the same version report it never works — the behavior depends on the operating system version, the Docker Desktop version, the filesystem being shared, and the specific sync backend selected.

On **macOS**, Docker Desktop has progressed through several filesystems sharing backends:
- **osxfs** (legacy): Slow, but generated inotify events via a custom kernel extension. Reliable for hot reload but notorious for poor I/O performance.
- **gRPC FUSE**: Introduced for better performance. inotify event propagation was inconsistent.
- **VirtioFS** (current default on Apple Silicon and modern Intel Macs): Uses Apple's Virtualization.framework and the VirtIO filesystem protocol. inotify propagation improved but still dependent on the specific mount type and file operation type. `IN_CLOSE_WRITE` events may not propagate reliably, which is the specific event that many file watchers depend on.

On **Windows with WSL2**: Files stored in the Windows NTFS filesystem (your `C:\Users\...` directory) and accessed through WSL2 mount at `/mnt/c/...` suffer from unreliable inotify propagation because the WSL2 filesystem driver has to translate Windows file events into Linux inotify events, with gaps in coverage. Files stored natively in the WSL2 filesystem (inside the WSL2 distro's own ext4 filesystem) generate inotify events correctly, but this requires keeping project files inside WSL2 rather than on the Windows filesystem — a significant workflow change.

```
              Platform/Backend Matrix — inotify Reliability for Hot Reload
              ================================================================

  Platform            Backend           inotify Events    Hot Reload Works
  ─────────────────────────────────────────────────────────────────────────
  Linux (native)      Native FS         Always correct    ✅ Reliably
  macOS (osxfs)       Legacy FUSE       Usually correct   ✅ Usually
  macOS (gRPC FUSE)   gRPC FUSE         Inconsistent      ⚠️ Sometimes
  macOS (VirtioFS)    VirtioFS          Usually correct   ✅ Usually (improved)
  Windows WSL2        DrvFS (C:\)       Unreliable        ❌ Often broken
  Windows WSL2        ext4 (WSL2 FS)    Correct           ✅ Works if files in WSL2
  Windows Hyper-V     SMB               Unreliable        ❌ Broken

  KEY INSIGHT: The matrix changes with each Docker Desktop release.
  What "works" today may break after an automatic update.
  Polling is the only reliable cross-platform solution.
```

This variability is why experienced Docker engineers always configure file watchers for polling mode in cross-platform team setups, regardless of whether their own machine happens to work correctly today. The developer who sees hot reload working on their Mac with VirtioFS commits the non-polling configuration to the repository. The developer on Windows who pulls the repository finds that hot reload never triggers. The polling configuration is the only one that works reliably for every developer on every platform.

## 5. The Solutions — Polling Mode and `docker compose watch`

**Solution 1 — Enable Polling Mode in the File Watcher**

Every major file watcher in the Node.js and Go ecosystems provides a polling mode that bypasses inotify entirely and uses the reliable periodic stat approach:

```yaml
# docker-compose.yml — Development configuration with polling-mode file watchers

services:
  # Node.js with nodemon — polling mode for cross-platform compatibility
  api-node:
    build:
      context: .
      dockerfile: Dockerfile.dev
    volumes:
      - ./src:/app/src          # Source code bind mount
      - /app/node_modules       # Anonymous volume: prevent host node_modules override
    command: >
      nodemon
      --legacy-watch            # ← Enable polling mode (uses setInterval + stat)
      --watch /app/src          # Watch the mounted source directory
      --ext js,ts,json          # File extensions to watch
      --exec "node -r ts-node/register src/index.ts"
    environment:
      NODE_ENV: development
    ports:
      - "3000:3000"

  # Go with Air — polling mode for Docker Desktop compatibility
  api-go:
    build:
      context: .
      dockerfile: Dockerfile.dev
    volumes:
      - .:/app                  # Full project bind mount for Go
    working_dir: /app
    command: air
    environment:
      - GO_ENV=development
    ports:
      - "8080:8080"
```

**Solution 2 — `docker compose watch` (Modern Approach, Docker Desktop 4.23+)**

Docker Compose 2.22+ introduced `docker compose watch` — a first-class development workflow command that handles file synchronization and hot reload through Docker's own sync layer rather than relying on inotify inside the container. It uses `docker compose watch` to monitor the host filesystem directly and either sync changed files into the container or trigger a container rebuild, depending on the configuration. Because the sync is handled by Docker's own daemon on the host rather than by an inotify-based watcher inside the container, it works reliably on macOS and Windows without requiring polling:

```yaml
# docker-compose.yml — docker compose watch configuration

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile.dev
    develop:
      watch:
        # Action: sync — copy changed files into the running container
        # Use for files that can be hot-reloaded without process restart
        - action: sync
          path: ./src              # Host path to watch
          target: /app/src         # Container path to sync into
          ignore:
            - node_modules/        # Never sync node_modules

        # Action: sync+restart — sync file AND restart the container process
        # Use for config files that require a restart to take effect
        - action: sync+restart
          path: ./config
          target: /app/config

        # Action: rebuild — rebuild the image and recreate the container
        # Use for dependency changes (package.json, go.mod)
        - action: rebuild
          path: package.json

        - action: rebuild
          path: package-lock.json

    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
```

```bash
# Start the watch mode:
docker compose watch

# This command:
# 1. Starts all services defined in docker-compose.yml
# 2. Watches the host filesystem for changes in the paths defined under 'watch:'
# 3. For 'sync' actions: copies changed files directly into the running container
#    WITHOUT relying on inotify inside the container ✅
# 4. For 'sync+restart': syncs file then sends SIGTERM to restart the process ✅
# 5. For 'rebuild': triggers a docker compose build + recreate ✅
#
# Works on macOS, Windows, and Linux. No polling. No inotify dependency.
# The synchronization happens through Docker Desktop's daemon on the host.
```

**Solution 3 — WSL2 Native Filesystem (Windows-Specific)**

On Windows, if Docker Desktop with WSL2 is the deployment target, moving project files from the Windows NTFS filesystem (`C:\Users\...`) into the WSL2 native ext4 filesystem (`~/projects/...` inside the WSL2 distro) gives inotify events that work correctly without polling. This is because within the WSL2 Linux environment, file operations on the WSL2 ext4 filesystem generate native Linux inotify events that are not subject to the NTFS→Linux translation problem:

```
              WSL2 File Storage — Two Locations with Different inotify Behavior
              ====================================================================

  Windows NTFS filesystem (❌ inotify unreliable):
  C:\Users\developer\projects\myapp\
  Accessed in WSL2 as: /mnt/c/Users/developer/projects/myapp/
  inotify events: generated by Windows NTFS, translated to Linux → unreliable

  WSL2 ext4 filesystem (✅ inotify works correctly):
  /home/developer/projects/myapp/   (inside the WSL2 distro)
  inotify events: generated natively by Linux kernel → perfectly reliable

  Recommended Windows development setup:
  1. Install Docker Desktop with WSL2 backend
  2. Install VS Code with "Remote - WSL" extension
  3. Clone projects inside WSL2: cd ~; git clone <repo>
  4. Open VS Code from WSL2: code .
  5. Run docker compose from WSL2 terminal: docker compose up
  → inotify works. No polling needed. Native Linux performance. ✅

  Trade-off:
  ├── Better performance for file I/O and inotify ✅
  ├── Can still access files from Windows Explorer via \\wsl$\ ✅
  └── Files are stored inside WSL2's virtual disk image ⚠️
      Requires managing backup of WSL2 disk image separately.
```

## 6. The `node_modules` Volume Trick — Preventing Host Override

A closely related problem that surfaces when bind-mounting Node.js project directories is the `node_modules` collision. When you mount the entire project directory into the container (`- .:/app`), the host's `node_modules` directory (which may be absent or built for macOS/Windows architecture) overwrites the container's `node_modules` directory (which was built for Linux inside the image). The result is missing native modules, wrong binary architectures, or a completely absent `node_modules` on the host that leaves the container with an empty module directory.

The solution is the **anonymous volume trick**: mount an anonymous volume over the `node_modules` path inside the container. Docker processes volume mounts in order, and a volume mount takes precedence over a bind mount for the same path. The anonymous volume allows the container to maintain its own Linux-built `node_modules` entirely separately from whatever exists on the host:

```yaml
services:
  api:
    build: .
    volumes:
      - .:/app                  # Bind mount: host project directory → /app
      - /app/node_modules       # Anonymous volume: shields /app/node_modules
                                # from the bind mount above.
                                # Container uses its own node_modules ✅
                                # Host node_modules never seen by container ✅
```

```
              node_modules Volume Trick — Layer Override Order
              ==================================================

  Mount processing order for /app:

  Step 1: Bind mount applied: .:/app
          /app/ now shows host directory contents.
          If host has no node_modules: /app/node_modules is empty or absent.
          If host has macOS node_modules: wrong architecture ❌

  Step 2: Anonymous volume applied: /app/node_modules
          Docker creates an anonymous volume for this path.
          Volume contents = what was in the IMAGE at /app/node_modules
          (built during docker build, correct Linux architecture) ✅

  Result:
  /app/src/          → from bind mount (host, hot-reload target) ✅
  /app/package.json  → from bind mount (host) ✅
  /app/node_modules/ → from anonymous volume (image build, Linux) ✅

  When node_modules needs updating (new package added):
  → Rebuild the image: docker compose build api
  → Docker installs new packages for Linux in the image layer
  → New anonymous volume picks up the updated node_modules ✅
```

## 7. Diagnostic Commands — Verifying Hot Reload and Sync Behavior

When hot reload is not working, a systematic approach identifies whether the problem is in the file watcher configuration, the bind mount, or the inotify propagation:

```bash
# ── Step 1: Verify the bind mount is correctly configured ────────────────────
docker inspect <container_name> \
    --format='{{range .Mounts}}Type:{{.Type}} Src:{{.Source}} Dst:{{.Destination}}{{"\n"}}{{end}}'
# Look for: Type:bind Src:/host/path/to/src Dst:/app/src
# If not present: bind mount not configured in docker-compose.yml

# ── Step 2: Verify the file change reaches the container ─────────────────────
# Edit a file on the host, then immediately check its mtime inside the container:
docker exec <container_name> stat /app/src/index.ts
# Check: Modify time should reflect the edit you just made.
# If mtime is stale: filesystem sync is failing (Docker Desktop issue)
# If mtime is current: the file change reached the container ✅

# ── Step 3: Test if inotify fires inside the container ────────────────────────
# Install inotify-tools in the container (dev image only):
docker exec -it <container_name> sh -c "apk add inotify-tools && inotifywait -r -e modify /app/src/"
# Now edit a file on the host.
# If inotifywait prints the event: inotify works → file watcher config problem
# If inotifywait hangs forever: inotify events not propagating ← use polling ❌

# ── Step 4: Verify the watcher process is running in polling mode ─────────────
# For nodemon:
docker exec <container_name> ps aux | grep nodemon
docker logs <container_name> | grep -i "watch\|poll\|legacy"
# nodemon with --legacy-watch outputs: "[nodemon] watching path(s): src/**/*"
# Look for: "Using legacy watcher" or "poll" in logs

# For Air:
docker exec <container_name> ps aux | grep air
docker logs <container_name> | grep -i "poll\|watch"
# Air with poll.enabled = true outputs: "polling mode enabled"

# ── Step 5: Manually test reload trigger ──────────────────────────────────────
# Touch a file (updates mtime without changing content):
docker exec <container_name> touch /app/src/index.ts
# If watcher triggers: inotify works, problem is on the host→container sync path
# If watcher does not trigger: watcher configuration problem or inotify broken
```

## 8. The Golden Rule

> Docker Desktop on macOS and Windows runs containers inside a Linux virtual machine, and the boundary between the host filesystem and the Linux VM is a translation layer that does not reliably propagate the `inotify` events that file watchers depend on. This is not a bug that will be "fixed" in the next Docker Desktop release — it is a fundamental architectural consequence of running Linux containers on non-Linux hosts, and while specific backends (VirtioFS, WSL2 ext4) have improved over time, the cross-platform guarantee does not exist for inotify-based file watching. The reliable cross-platform solutions are three: configure your file watcher to use polling mode (`--legacy-watch` for nodemon, `poll.enabled = true` for Air) — polling is slower and consumes more CPU than inotify but works on every platform without exception; adopt `docker compose watch` which handles synchronization at the host level through Docker's daemon rather than relying on in-container inotify events; or on Windows, move project files into the WSL2 native ext4 filesystem where inotify is generated by the Linux kernel directly. Always test your development hot-reload setup across all platforms your team uses before committing a configuration to the repository. A configuration that silently fails for half your team is worse than a slightly less elegant one that works for everyone.

On Linux, inotify is free and reliable. On Docker Desktop, polling is the price of cross-platform portability.
