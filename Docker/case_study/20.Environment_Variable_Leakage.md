# Environment Variable Leakage Across Services

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Master Keyring Distributed to Every Employee

Imagine a large hotel with hundreds of employees: housekeepers, concierge staff, kitchen workers, maintenance engineers, and security personnel. Each role requires access to certain areas. Housekeepers need the keys to guest rooms. Kitchen workers need the keys to the supply pantry and refrigeration rooms. Security personnel need the keys to the surveillance room and the safe. Maintenance engineers need the keys to utility corridors.

Now imagine that the hotel manager, for administrative convenience, creates a single master keyring containing every key in the hotel and distributes a copy to every employee. Every housekeeper now carries keys to the surveillance room and the safe. Every kitchen worker carries keys to every guest room. The hotel is operationally functional — everyone can access what they need — but the security model has collapsed. The moment a housekeeper's keyring is lost or stolen, every room, every safe, and every secure area in the hotel is compromised. The principle of least privilege — the foundational security rule that every person or system should have access only to what they need to perform their specific function — has been traded away for the convenience of a single keyring.

This is precisely what happens when a single `.env` file is used as the `env_file` source for every service in a Docker Compose deployment. The `.env` file accumulates every credential, every connection string, every API key, and every secret in the system. Every service — the web server, the background worker, the migration runner, the monitoring agent — receives a copy of the entire file in its environment. Every process inside every container can read every secret in the system by simply calling `os.Getenv("POSTGRES_PASSWORD")` or by reading its own `/proc/self/environ`. When any one of those containers is compromised through an application vulnerability, the attacker inherits the complete credential set for the entire system.

## 2. How Environment Variables Work — Visibility and Inheritance

To understand why this matters, you need to understand precisely how environment variables are exposed to a process in Linux. When a container starts, Docker injects the configured environment variables into the process by constructing the environment for the root process of the container — the PID 1 process. These variables are stored in the process's environment block, which is accessible through the `/proc/self/environ` pseudo-file. Every child process spawned by PID 1 inherits a copy of this environment unless the parent explicitly clears variables before spawning the child.

The critical implications of this model are three-fold. First, environment variables are visible to the entire process and all its descendants — there is no scoping within a single process's runtime. A Node.js application that injects `process.env.POSTGRES_PASSWORD` into a template variable makes that password available to the entire JavaScript runtime, not just the function that reads it. Second, environment variables are readable from the `/proc` filesystem by any process with sufficient permissions on the same host — which includes any process running as root inside a container if the host uses the default Linux security model without user namespaces. Third, environment variables are dumped in their entirety to process listings, core dumps, error reporting tools, and any framework that logs the process environment on startup — which many frameworks do by default in debug mode.

```
              Environment Variable Visibility — What Can See Your Secrets
              ==============================================================

  Container: api_container
  Injected env (from a monolithic .env):
  DB_URL=postgres://appuser:secretpassword@postgres:5432/myapp
  REDIS_PASSWORD=redis-secret-key
  RABBITMQ_PASSWORD=mq-super-secret
  STRIPE_SECRET_KEY=sk_live_abc123...
  AWS_SECRET_ACCESS_KEY=AKIA...
  SENDGRID_API_KEY=SG.abc...

  Who can read these inside the container:
  ─────────────────────────────────────────────────────────────────────
  ├── The application process: process.env.X or os.Getenv("X") ✅ (intended)
  ├── Any child process spawned by the app: inherits full env ✅/⚠️
  ├── Any subprocess: exec("sh -c 'env'") dumps all secrets to stdout ⚠️
  ├── /proc/self/environ: readable by any process with access to /proc ⚠️
  ├── /proc/<pid>/environ: readable by root or same-UID processes ⚠️
  ├── docker inspect api_container: shows ALL env vars to host root ⚠️
  ├── docker exec api_container env: dumps all vars ⚠️
  └── Application error reporter (Sentry, Datadog): may capture env on crash ❌

  Attack scenario — RCE in the api container:
  ├── Attacker exploits SQL injection or deserialization vulnerability
  ├── Attacker executes: cat /proc/self/environ | tr '\0' '\n'
  ├── Output: POSTGRES_PASSWORD=secretpassword
  │           REDIS_PASSWORD=redis-secret-key
  │           RABBITMQ_PASSWORD=mq-super-secret
  │           STRIPE_SECRET_KEY=sk_live_abc123...
  │           AWS_SECRET_ACCESS_KEY=AKIA...
  └── Attacker now has credentials for: database, cache, message queue,
      payment processor, and cloud provider. Full system compromise. ❌

  What the attacker needed to compromise to get these:
  └── One RCE vulnerability in the api container.
      Just one. The blast radius is the entire system.
```

The process inspection attack (`cat /proc/self/environ`) is not a sophisticated exploit — it is a one-line command available to any process running inside the container. In a containerized application with an RCE vulnerability, this is typically one of the first commands an attacker executes, because it immediately reveals every credential available to the compromised process.

## 3. The Single `.env` Anti-Pattern — How It Grows

The monolithic `.env` file anti-pattern almost never starts as a deliberate architectural decision. It grows organically from a development convenience. A developer starts with a minimal `.env` file containing the database URL. The application grows, a Redis cache is added, and the Redis connection string is appended to the `.env` file. A message queue is added, its credentials go into the `.env` file. The `.env` file is already referenced as `env_file: .env` in the Compose file for the API service, so when the worker service is added, copying the same `env_file: .env` is the path of least resistance. Within a few months, every service in the system has `env_file: .env` and the `.env` file contains every secret in the deployment.

```
              The Growth of a Monolithic .env — A Realistic Timeline
              ==========================================================

  Month 1 — MVP (2 services, 3 vars):
  .env:
    DB_URL=postgres://...
    PORT=8080
    JWT_SECRET=dev-secret

  services:
    api: {env_file: .env}
    postgres: {env_file: .env}

  Month 2 — Redis added (4 vars):
  .env:
    DB_URL=postgres://...
    REDIS_URL=redis://:password@redis:6379
    REDIS_PASSWORD=password        ← Now in api AND postgres AND redis envs
    PORT=8080
    JWT_SECRET=dev-secret

  Month 4 — RabbitMQ, worker service (7 vars):
  .env:
    DB_URL=postgres://...
    REDIS_URL=redis://:password@redis:6379
    REDIS_PASSWORD=password
    RABBITMQ_URL=amqp://admin:secret@rabbitmq:5672
    RABBITMQ_PASSWORD=secret       ← In every container's env
    PORT=8080
    JWT_SECRET=dev-secret

  services:
    api:     {env_file: .env}      ← Gets ALL 7 vars
    worker:  {env_file: .env}      ← Gets ALL 7 vars (only needs 3)
    postgres:{env_file: .env}      ← Gets ALL 7 vars (needs 1: POSTGRES_PASSWORD)
    redis:   {env_file: .env}      ← Gets ALL 7 vars (needs 1: REDIS_PASSWORD)
    rabbitmq:{env_file: .env}      ← Gets ALL 7 vars (needs 1: RABBITMQ_PASSWORD)

  Month 8 — Stripe, SendGrid, AWS (15 vars):
  STRIPE_SECRET_KEY=sk_live_...   ← In every container ❌
  AWS_SECRET_ACCESS_KEY=AKIA...   ← In every container ❌
  SENDGRID_API_KEY=SG.abc...      ← In every container ❌

  Security reality: 15 secrets accessible in every container.
  A compromised nginx container (which needs zero secrets) has all 15.
```

## 4. The Correct Pattern — Scoped Environment Variables Per Service

The solution is to apply the principle of least privilege to environment variable injection: each service receives only the environment variables it needs to perform its function. Nothing more. A service that connects to the database but not to Redis should receive `DB_URL` but not `REDIS_PASSWORD`. A service that sends email through SendGrid but does not touch the database should receive `SENDGRID_API_KEY` but not `DB_URL`. A reverse proxy that handles TLS termination and load balancing should receive no application secrets at all.

The implementation in Docker Compose involves replacing the monolithic `env_file: .env` with explicit, per-service environment variable declarations using either the `environment:` key (for non-sensitive values) or targeted `env_file:` references pointing to service-specific `.env` files:

```
# Directory structure — scoped env files per service:
project/
├── .env.api           ← API server secrets only
├── .env.worker        ← Worker secrets only
├── .env.postgres      ← PostgreSQL initialization secrets only
├── .env.redis         ← Redis secrets only
├── .env.rabbitmq      ← RabbitMQ secrets only
├── .env.shared        ← Non-sensitive shared config (PORT, LOG_LEVEL)
└── docker-compose.yml
```

```bash
# .env.api — Only what the API needs
# Not a good practice to store secrets in files — use secrets manager in prod.
# For development/staging only.
DB_URL=postgres://appuser:db-secret@postgres:5432/myapp
REDIS_URL=redis://:redis-secret@redis:6379/0
STRIPE_SECRET_KEY=sk_live_abc123
SENDGRID_API_KEY=SG.abc...
JWT_SECRET=jwt-signing-key
PORT=8080

# .env.worker — Only what the worker needs
DB_URL=postgres://appuser:db-secret@postgres:5432/myapp
RABBITMQ_URL=amqp://mquser:mq-secret@rabbitmq:5672
SENDGRID_API_KEY=SG.abc...   # Worker sends emails too

# .env.postgres — Only what PostgreSQL initialization needs
POSTGRES_USER=appuser
POSTGRES_PASSWORD=db-secret
POSTGRES_DB=myapp

# .env.redis — Only what Redis needs
REDIS_PASSWORD=redis-secret

# .env.rabbitmq — Only what RabbitMQ needs
RABBITMQ_DEFAULT_USER=mquser
RABBITMQ_DEFAULT_PASS=mq-secret
RABBITMQ_DEFAULT_VHOST=/
```


## 5. Docker Secrets — The Production-Grade Solution

For production deployments using Docker Swarm, the `secrets` feature provides a significantly more secure mechanism for credential injection than environment variables. Docker Secrets stores sensitive values in the Swarm's encrypted raft log, transmits them to container processes over an encrypted channel, and mounts them as files in the container's filesystem at `/run/secrets/<secret_name>` — never exposing them as environment variables that appear in process listings, `/proc/environ` dumps, or log output.

The application reads the secret by reading the file path rather than calling `os.Getenv()`. This means the secret is not visible in `docker inspect`, not included in `docker exec env` output, and not captured by application frameworks that log the process environment on startup:

```yaml
# docker-compose.yml (Swarm mode with Docker Secrets)
version: "3.9"

secrets:
  # Secrets are defined once and referenced per-service.
  # Values stored encrypted in Swarm raft log.
  db_password:
    external: true        # Pre-created with: docker secret create db_password -
  redis_password:
    external: true
  stripe_key:
    external: true
  jwt_secret:
    external: true

services:
  api:
    build: .
    environment:
      DB_HOST:   postgres
      DB_PORT:   "5432"
      DB_USER:   appuser
      DB_NAME:   myapp
      # Note: no DB_PASSWORD here — read from file at /run/secrets/db_password
    secrets:
      - db_password       # Mounted at /run/secrets/db_password ✅
      - stripe_key        # Mounted at /run/secrets/stripe_key ✅
      - jwt_secret        # Mounted at /run/secrets/jwt_secret ✅
      # redis_password NOT included — api doesn't need it directly ✅

  postgres:
    image: postgres:16.2-alpine3.19
    environment:
      POSTGRES_USER: appuser
      POSTGRES_DB:   myapp
      # POSTGRES_PASSWORD_FILE tells postgres to read password from a file
      # rather than from POSTGRES_PASSWORD env var:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password       # Only the secret this service actually needs ✅
```

```go
// Go — Reading Docker Secrets from the filesystem
package config

import (
    "fmt"
    "os"
    "strings"
)

// ReadSecret reads a Docker Secret value from the /run/secrets/ path.
// Falls back to an environment variable with the same name (uppercased)
// for non-Swarm development environments.
func ReadSecret(name string) (string, error) {
    // Try Docker Secrets file path first (production: Swarm)
    secretPath := fmt.Sprintf("/run/secrets/%s", name)
    if data, err := os.ReadFile(secretPath); err == nil {
        return strings.TrimSpace(string(data)), nil
    }

    // Fall back to environment variable (development: Compose without Swarm)
    envKey := strings.ToUpper(strings.ReplaceAll(name, "-", "_"))
    if value := os.Getenv(envKey); value != "" {
        return value, nil
    }

    return "", fmt.Errorf("secret %q not found in /run/secrets/ or environment", name)
}

// Usage:
func LoadConfig() (*Config, error) {
    dbPassword, err := ReadSecret("db_password")
    if err != nil {
        return nil, fmt.Errorf("loading db_password: %w", err)
    }

    stripeKey, err := ReadSecret("stripe_key")
    if err != nil {
        return nil, fmt.Errorf("loading stripe_key: %w", err)
    }

    return &Config{
        DBPassword: dbPassword,
        StripeKey:  stripeKey,
    }, nil
}
```

## 6. External Secrets Managers — The Cloud-Native Production Pattern

For production deployments beyond Docker Swarm — specifically Kubernetes, AWS ECS, or bare-metal with cloud provider access — external secrets managers provide the most robust and auditable credential management. The principle is that secrets never live in files, environment variables, or container images. They are fetched at runtime from the secrets manager using the application's IAM role or service account credentials, which are themselves short-lived and automatically rotated by the cloud provider.

```
              Secrets Manager Integration — Runtime Secret Fetching
              ========================================================

  AWS Secrets Manager pattern:

  Application starts
       │
       ├── Reads AWS_REGION from environment (non-secret, safe in env) ✅
       │
       ├── Assumes IAM Role (via instance metadata / pod service account)
       │   IAM Role has: secretsmanager:GetSecretValue on specific ARNs only
       │   No static AWS credentials in the container ✅
       │
       ├── Fetches: aws secretsmanager get-secret-value --secret-id prod/myapp/db
       │   Returns: {"DB_PASSWORD": "actual-prod-password", "DB_USER": "appuser"}
       │
       ├── Fetches: aws secretsmanager get-secret-value --secret-id prod/myapp/stripe
       │   Returns: {"STRIPE_SECRET_KEY": "sk_live_abc123"}
       │
       └── Constructs DB connection string in memory. Never written to disk.
           Never stored in environment variable. Never logged. ✅

  Benefits over env vars:
  ├── Secrets are never baked into the image ✅
  ├── Secrets are never in process environment (not visible in /proc) ✅
  ├── Access is audited: every secret read is logged in CloudTrail ✅
  ├── Rotation: secrets can be rotated without redeploying containers ✅
  ├── IAM scoping: each service's role grants access only to its secrets ✅
  └── No secret distribution problem: the secret store IS the distribution ✅
```

```go
// Go — AWS Secrets Manager integration at startup
package secrets

import (
    "context"
    "encoding/json"
    "fmt"

    "github.com/aws/aws-sdk-go-v2/config"
    "github.com/aws/aws-sdk-go-v2/service/secretsmanager"
)

// FetchSecret retrieves a JSON secret from AWS Secrets Manager
// and unmarshals it into the provided target struct.
func FetchSecret(ctx context.Context, secretID string, target interface{}) error {
    cfg, err := config.LoadDefaultConfig(ctx)
    if err != nil {
        return fmt.Errorf("loading AWS config: %w", err)
    }

    client := secretsmanager.NewFromConfig(cfg)

    output, err := client.GetSecretValue(ctx, &secretsmanager.GetSecretValueInput{
        SecretId: &secretID,
    })
    if err != nil {
        return fmt.Errorf("fetching secret %q: %w", secretID, err)
    }

    return json.Unmarshal([]byte(*output.SecretString), target)
}

// Usage:
type DBCredentials struct {
    Host     string `json:"host"`
    Port     int    `json:"port"`
    User     string `json:"user"`
    Password string `json:"password"`
    DBName   string `json:"dbname"`
}

func LoadDBCredentials(ctx context.Context) (*DBCredentials, error) {
    var creds DBCredentials
    secretID := fmt.Sprintf("%s/myapp/db", os.Getenv("ENVIRONMENT")) // e.g., "prod/myapp/db"
    if err := FetchSecret(ctx, secretID, &creds); err != nil {
        return nil, err
    }
    return &creds, nil
}
```

## 7. The `.env` File Security Checklist

Even after implementing scoped environment variables or secrets managers, the `.env` files themselves require careful operational hygiene to prevent credential leakage through a different vector — the files being committed to version control, distributed in Docker images, or accessible through container build contexts:

```bash
# ── .gitignore — MANDATORY: never commit .env files with real secrets ──────────
# .gitignore:
.env
.env.*
!.env.example    # Commit only the example file with placeholder values

# ── .dockerignore — Prevent .env from being included in build context ──────────
# .dockerignore:
.env
.env.*
.git/
*.log

# Verify the build context does not include .env files:
docker build --no-cache . 2>&1 | grep -i "env"
# Or inspect the image for accidentally baked-in env files:
docker run --rm --entrypoint ls myapp:latest /app | grep env
# Correct output: nothing. .env files should not exist inside the image.

# ── Audit what environment variables are actually set per container ─────────────
# List env vars in a running container (run during development audit):
docker exec <container> env | sort
# Review: are any credentials present that this service should NOT have?

# ── Detect monolithic env_file usage in Compose files ────────────────────────
grep -r "env_file" docker-compose*.yml
# Inspect each env_file reference: does it point to a service-specific file
# or a shared monolithic .env file?

# ── Scan for credentials accidentally committed to git ────────────────────────
# Using git-secrets or trufflehog:
git log --all --full-history -- "*.env" | head -20
# Check: has any .env file ever been committed to this repository?
# If yes: rotate all credentials immediately. The secret is permanently
# in git history and cannot be removed without a full history rewrite.
```

## 8. The `env` Subcommand Audit — Verifying Least Privilege

The simplest way to audit whether your scoping is correctly applied is to inspect the environment of each running container and verify that it contains only the variables appropriate for that service:

```bash
#!/bin/bash
# audit-env-vars.sh — Verify least privilege for environment variables

SENSITIVE_VARS="PASSWORD SECRET KEY TOKEN CREDENTIAL API_KEY"

echo "=== Environment Variable Audit ==="
echo "Checking for sensitive variables in services that should not have them"
echo ""

for service in nginx api worker postgres redis rabbitmq; do
    container=$(docker compose ps -q $service 2>/dev/null)
    if [ -z "$container" ]; then
        echo "[$service] Not running, skipping."
        continue
    fi

    echo "[$service] Environment variables:"
    # Get all env vars, redact values, show only names
    docker exec "$container" env | \
        awk -F= '{print "  " $1}' | \
        sort

    # Check for cross-contamination of known sensitive vars
    for pattern in $SENSITIVE_VARS; do
        found=$(docker exec "$container" env | grep -i "$pattern" | awk -F= '{print $1}')
        if [ -n "$found" ]; then
            echo "  ⚠️  SENSITIVE: $found"
        fi
    done
    echo ""
done
```

## 9. The Golden Rule

> Environment variables are the most convenient and the most dangerous form of secret injection. They are convenient because every language, every framework, and every tool knows how to read them. They are dangerous because they are globally visible to the entire process, all its children, all its threads, and through `/proc/self/environ` to any attacker who achieves code execution inside the container. The principle of least privilege applied to secret injection is simple: each service receives only the credentials it needs to perform its specific function, and no others. A reverse proxy that needs no credentials should receive none. A background worker that sends emails but does not process payments should receive the email API key but not the payment API key. Implement this scoping in three layers: in development, use per-service `.env` files and explicit `environment:` declarations rather than a monolithic `env_file`; in production, use Docker Secrets (Swarm) or an external secrets manager (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager) to eliminate environment variable exposure entirely; always verify your scoping with a periodic `docker exec <container> env` audit. The blast radius of a container compromise is determined by the credentials that container holds. Minimize the blast radius before the compromise, not after.

An attacker who can read your environment can own your entire system. A correctly scoped environment limits that ownership to the blast radius of a single service.
