# Network Namespace Isolation Surprise

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Two Private Office Buildings

Imagine a large corporate campus with a central parking lot. Two companies have each built their own private office building on this campus. Company A's building has its own internal telephone exchange, its own hallways, and its own cafeteria. Company B's building has the same. The employees of each company can communicate freely with their colleagues in their own building using the internal phone system. However, despite both buildings being on the same campus and visible to each other from the windows, an employee in Company A cannot simply pick up the internal phone and dial someone in Company B. The two telephone exchanges are entirely separate. To communicate across buildings, a special external line must be set up — a dedicated connection between the two exchanges that both companies have agreed to establish.

This is precisely the topology of Docker Compose networking when two separate Compose projects run on the same Docker host. Each Compose project automatically creates its own isolated network — a private "office building" with internal telephone service. Containers within Stack A can reach each other using DNS service names. Containers within Stack B can do the same. But despite both stacks running on the same physical Docker host and appearing in the same `docker ps` output, a container in Stack A cannot reach a container in Stack B by service name or by IP address, because the two automatically-created networks are entirely separate and isolated from each other. The realization that "both containers are on Docker" does not imply "both containers can communicate" is the essential insight that this case study exists to drive home.

## 2. How Compose Projects Create Isolated Networks

When you run `docker-compose up` for a project named `frontend`, Docker Compose performs several setup operations automatically. Among these is the creation of a default network for the project, named according to the convention `<project_name>_default`. Every service defined in the Compose file, unless explicitly configured otherwise, is attached to this `<project_name>_default` network and only to this network. The project name is derived either from the `--project-name` flag, the `name:` field at the top of the Compose file, or by default from the name of the directory containing the `docker-compose.yml` file.

This automatic network creation is elegant and desirable for isolation purposes — it ensures that services in one Compose project cannot accidentally interfere with services in another project through networking. The `frontend_default` network is a complete virtual network with its own subnet, its own embedded DNS resolver, and its own set of IP address assignments. The `backend_default` network, created by a different Compose project, has its own separate subnet, its own DNS resolver, and its own IP assignments. Even if both networks use the same RFC 1918 private subnet range internally — which Docker prevents through subnet management — there is no routing path between them from the perspective of container processes.

```
              Two Compose Stacks — Isolated by Default
              ==========================================

  DOCKER HOST
  ┌──────────────────────────────────────────────────────────────────┐
  │                                                                    │
  │  Stack A (project: "frontend", dir: ./frontend)                   │
  │  Network: frontend_default (172.20.0.0/16)                        │
  │  ┌────────────────────────────────────────────────┐               │
  │  │  frontend_nginx (172.20.0.2)                   │               │
  │  │  frontend_api   (172.20.0.3)                   │               │
  │  │  frontend_redis (172.20.0.4)                   │               │
  │  │                                                │               │
  │  │  DNS: nginx, api, redis (resolve within stack) │               │
  │  └────────────────────────────────────────────────┘               │
  │                         ▲ No route                                 │
  │                         │ between                                  │
  │                         ▼ these                                    │
  │  Stack B (project: "backend", dir: ./backend)                      │
  │  Network: backend_default (172.21.0.0/16)                         │
  │  ┌────────────────────────────────────────────────┐               │
  │  │  backend_worker  (172.21.0.2)                  │               │
  │  │  backend_api     (172.21.0.3)                  │               │
  │  │  backend_rabbitmq(172.21.0.4)                  │               │
  │  │                                                │               │
  │  │  DNS: worker, api, rabbitmq (own stack only)   │               │
  │  └────────────────────────────────────────────────┘               │
  │                                                                    │
  │  frontend_api tries: curl http://rabbitmq:5672                     │
  │  DNS resolution fails: "Name or service not known" ❌              │
  │  frontend_api tries: curl http://172.21.0.4:5672                  │
  │  Result: "No route to host" ❌                                     │
  │                                                                    │
  │  Both stacks visible in docker ps. Neither can see the other.     │
  └──────────────────────────────────────────────────────────────────┘
```

The isolation is enforced at the kernel level through Linux bridge networking and iptables rules. Docker creates a separate bridge interface for each user-defined network. The kernel does not route packets between separate bridge interfaces unless explicitly configured to do so through IP forwarding and routing rules. Docker's iptables rules include `DOCKER-ISOLATION` chains that actively drop packets attempting to travel between Docker-managed bridge networks that are not intended to be connected. This means that even if a container somehow discovered the IP address of a container on a different Compose network, the kernel would drop the packets before they arrived.

## 3. The Real-World Scenarios That Surface This Problem

The cross-stack isolation surprise appears in several distinct scenarios in real engineering environments, each with its own specific frustration profile. Understanding these scenarios helps you recognize the pattern quickly when you encounter it.

The first and most common scenario is the **shared infrastructure service** problem. An engineering organization runs multiple independent Compose-based applications on a single Docker host — perhaps a staging server or a developer workstation. Rather than each application running its own Redis or RabbitMQ instance, someone decides that a single, shared Redis container should serve all the applications. They start the Redis container in one Compose project — perhaps an `infrastructure` project — and then update the configuration of each application to point to the shared Redis. The connection string uses `redis` as the hostname because that is the service name in the `infrastructure` Compose file. Every application fails to connect, because the `redis` service name is only resolvable within the `infrastructure_default` network, and none of the application containers are connected to that network.

The second scenario is the **split microservices architecture**. As an application grows, the monolithic single Compose file becomes cumbersome. An engineering team splits it into multiple Compose files organized by service domain — one for the user-facing services, one for the background processing services, one for the data pipeline. Each Compose file works perfectly in isolation. When the team attempts to run all three simultaneously and have the background workers call the user-facing API, or have the data pipeline consume from the background worker's message queue, all cross-file service calls fail.

The third scenario is the **incremental containerization** path. A developer is containerizing a legacy application piece by piece. The database was containerized first and runs in one Compose project. The application server was containerized second and runs in a different Compose project. The developer expects them to communicate because they are both "in Docker," not yet aware that separate Compose projects mean separate network islands.

```
              Three Scenarios That Surface the Cross-Stack Isolation Problem
              =================================================================

  Scenario 1 — Shared Infrastructure Service:
  ────────────────────────────────────────────────────────────────────
  infrastructure/docker-compose.yml:
    services:
      redis:    ← redis resolvable only on infrastructure_default
      rabbitmq: ← rabbitmq resolvable only on infrastructure_default

  app_a/docker-compose.yml:
    services:
      api:
        environment:
          REDIS_URL: redis://redis:6379    ← fails: redis not on app_a_default ❌

  Scenario 2 — Split Microservice Compose Files:
  ────────────────────────────────────────────────────────────────────
  frontend/docker-compose.yml (network: frontend_default):
    services: nginx, api, auth

  backend/docker-compose.yml (network: backend_default):
    services: worker, scheduler, emailer

  auth service (in frontend) needs to validate tokens via worker (in backend):
    WORKER_URL: http://worker:8081  ← fails: worker not on frontend_default ❌

  Scenario 3 — Incremental Containerization:
  ────────────────────────────────────────────────────────────────────
  databases/docker-compose.yml:
    services:
      postgres: (on databases_default)

  application/docker-compose.yml:
    services:
      api:
        DB_URL: postgres://postgres:5432/myapp ← fails: not on databases_default ❌
```

## 4. The Solution — External Shared Networks

Docker Compose provides a clean mechanism for connecting containers across multiple Compose projects: **external networks**. An external network is a Docker network that exists independently of any Compose project — it was created manually with `docker network create` and persists whether any Compose project is running or not. Compose projects that need to participate in cross-project communication declare this external network in their Compose file and attach relevant services to it alongside their own internal project network. Containers attached to the external network can then communicate with any other container that is also attached to that network, regardless of which Compose project manages them.

The workflow has three steps. First, create the external network once, manually, on the Docker host. Second, declare the network as external in each Compose file that needs to participate. Third, attach the services that need cross-project communication to that external network. Services that should remain internal-only stay on their project's private default network. The result is a deliberate, explicit network topology where cross-project connectivity is opt-in rather than default.

```bash
# Step 1: Create the external network once on the Docker host.
# This network persists independently of any Compose project.
# Choose a meaningful name that identifies its purpose.
docker network create shared-services-net

# Verify it was created:
docker network ls | grep shared-services-net
# NETWORK ID     NAME                 DRIVER    SCOPE
# a3b4c5d6e7f8   shared-services-net  bridge    local
```

```yaml
# infrastructure/docker-compose.yml
# The project that hosts shared services (Redis, RabbitMQ)

networks:
  # The project's own private network for internal communication
  default:
    name: infrastructure_default

  # The external shared network — already created via docker network create
  # 'external: true' tells Compose NOT to create this network — it pre-exists
  shared-services-net:
    external: true

services:
  redis:
    image: redis:7.2-alpine3.19@sha256:...
    networks:
      - default              # Accessible as "redis" within this stack
      - shared-services-net  # Accessible as "redis" to all stacks on shared net ✅
    volumes:
      - redisdata:/data

  rabbitmq:
    image: rabbitmq:3.13-management-alpine@sha256:...
    networks:
      - default
      - shared-services-net  # Accessible across stacks ✅
    environment:
      RABBITMQ_DEFAULT_USER: admin
      RABBITMQ_DEFAULT_PASS: secret

volumes:
  redisdata:
```

```yaml
# app_a/docker-compose.yml
# An application that consumes the shared Redis and RabbitMQ

networks:
  # App A's own private internal network
  default:
    name: app_a_default

  # Connect to the same external shared network
  shared-services-net:
    external: true

services:
  api:
    build: .
    networks:
      - default              # Talks to its own internal services
      - shared-services-net  # Talks to redis and rabbitmq ✅
    environment:
      # Use the service name "redis" — resolvable via shared network DNS
      REDIS_URL:    redis://redis:6379/0
      RABBITMQ_URL: amqp://admin:secret@rabbitmq:5672/

  worker:
    build: .
    networks:
      - default
      - shared-services-net
    environment:
      RABBITMQ_URL: amqp://admin:secret@rabbitmq:5672/
```

```yaml
# app_b/docker-compose.yml
# A second application on the same Docker host, also consuming shared services

networks:
  default:
    name: app_b_default

  shared-services-net:
    external: true

services:
  service:
    build: .
    networks:
      - default
      - shared-services-net
    environment:
      REDIS_URL: redis://redis:6379/1    # Different Redis DB index for isolation
      RABBITMQ_URL: amqp://admin:secret@rabbitmq:5672/
```

## 5. How DNS Resolution Works Across the Shared Network

Understanding precisely how Docker DNS resolves service names across the shared external network is important for correctly constructing connection strings and for diagnosing resolution failures. When a container is attached to multiple networks, its embedded DNS resolver — the Docker-managed server at `127.0.0.11` — is aware of all the networks the container participates in and can resolve service names from any of them.

When the `api` container in `app_a` resolves the hostname `redis`, its DNS resolver searches through all networks the `api` container is connected to and returns the IP address of the first container named `redis` it finds. Because the `api` container is on both `app_a_default` and `shared-services-net`, and the `redis` container is on `shared-services-net`, the DNS resolver successfully returns the `redis` container's IP address on the `shared-services-net` subnet. The TCP connection then travels through the shared bridge network to the Redis container.

```
              DNS Resolution Across External Network — Full Flow
              ====================================================

  api container (app_a):
  ├── Connected to: app_a_default (172.22.0.0/16)
  └── Connected to: shared-services-net (172.23.0.0/16)

  redis container (infrastructure):
  ├── Connected to: infrastructure_default (172.20.0.0/16)
  └── Connected to: shared-services-net (172.23.0.0/16)
      redis's IP on shared-services-net: 172.23.0.5

  api resolves "redis":
  ┌─────────────────────────────────────────────────────────────┐
  │  DNS query → 127.0.0.11 (api's embedded resolver)          │
  │  Resolver searches:                                          │
  │    app_a_default: no container named "redis" → not found    │
  │    shared-services-net: "redis" → 172.23.0.5 ✅            │
  │  Returns: 172.23.0.5                                         │
  └─────────────────────────────────────────────────────────────┘

  api opens TCP connection to 172.23.0.5:6379
  Packet travels through shared-services-net bridge
  Redis container receives connection
  Redis responds: PONG ✅

  Ambiguity warning:
  If two different stacks both have a service named "redis",
  DNS resolution may return either one — the result is non-deterministic.
  Use network aliases to disambiguate (see Section 7).
```

## 6. Network Topology Patterns — Choosing the Right Architecture

The external shared network is the most direct solution, but it is not the only architectural pattern for managing cross-project communication. The correct choice depends on the number of projects involved, the permanence of the cross-project dependencies, and the organizational ownership of the services in question.

**Pattern 1 — External Shared Network (recommended for shared infrastructure):** Create one or more named external networks for services that are genuinely shared across multiple independent applications. This pattern works well for shared Redis, RabbitMQ, internal monitoring services, and service meshes. The shared service owns its participation in the external network; consuming services opt in explicitly. This is the most flexible and explicit pattern.

**Pattern 2 — Single Compose File (recommended for related services):** If the services that need to communicate are part of the same logical application — just separated into different files for organizational reasons — consolidate them into a single Compose file. This eliminates cross-project networking complexity entirely. Docker Compose supports the `include:` directive (Compose v2.20+) that allows a single root Compose file to include other Compose files, giving you organizational separation without network isolation:

```yaml
# docker-compose.yml (root file, includes all related stacks)
# Compose v2.20+ with include directive
include:
  - path: ./frontend/docker-compose.yml
  - path: ./backend/docker-compose.yml
  - path: ./workers/docker-compose.yml

# All included services share the same network by default.
# No external network configuration required.
```

**Pattern 3 — Service Mesh or API Gateway (recommended for microservices at scale):** When the number of cross-project service dependencies grows large and changes frequently, a dedicated service mesh or API gateway provides a more scalable architecture than manually managing external networks. Each service exposes itself through a well-known gateway hostname, and consumers call the gateway rather than the service directly. This pattern is more appropriate for Kubernetes-scale deployments and is beyond the scope of single-host Docker Compose.

```
              Architecture Pattern Selection Guide
              ======================================

  Question 1: Are the services part of the same application?
    YES → Pattern 2: Single Compose file or 'include' directive
           Simplest, least configuration, shared network automatically
    NO  → Continue to Question 2

  Question 2: Do the services share common infrastructure (Redis, DB, MQ)?
    YES → Pattern 1: External shared network for infrastructure services
           Each app opts in explicitly. Shared infra on shared-services-net.
    NO  → They probably should not communicate directly at all.
           Consider API calls between services with proper authentication.

  Question 3: Is this a large microservices architecture (20+ services)?
    YES → Pattern 3: API Gateway / Service Mesh (Kubernetes territory)
           Docker Compose on a single host is not the right tool at this scale.
    NO  → Pattern 1 or 2 is sufficient.

  Anti-pattern: Connecting all stacks to a single giant shared network.
  This recreates the problem you were trying to solve with isolation.
  Shared networks should be purpose-specific and narrow in scope.
```

## 7. Network Aliases — Resolving DNS Ambiguity Across Projects

When multiple Compose projects each define a service that has the same name — for example, both `app_a` and `app_b` have a service named `api` — and both are connected to the same external shared network, DNS resolution for the name `api` becomes ambiguous. Docker's embedded DNS will return one of the containers named `api`, but which one is non-deterministic. Network aliases provide the solution to this ambiguity problem.

A network alias is an additional DNS name assigned to a container on a specific network. Unlike the service name — which is automatically derived from the Compose service definition — a network alias is explicitly configured and can be chosen to be globally unique within the shared network. This allows you to give each service a unique, unambiguous identity on the shared network while retaining the convenient short name for internal use within its own project:

```yaml
# app_a/docker-compose.yml
services:
  api:
    build: .
    networks:
      default:
        aliases:
          - api              # Resolvable as "api" within app_a_default
      shared-services-net:
        aliases:
          - app-a-api        # Uniquely resolvable as "app-a-api" on shared net ✅
    # Other services on shared-services-net use "app-a-api" to reach this service.

# app_b/docker-compose.yml
services:
  api:
    build: .
    networks:
      default:
        aliases:
          - api              # Resolvable as "api" within app_b_default
      shared-services-net:
        aliases:
          - app-b-api        # Uniquely resolvable as "app-b-api" on shared net ✅
```

```
              Network Aliases — Disambiguating Same-Named Services
              ======================================================

  shared-services-net:
  ┌─────────────────────────────────────────────────────────────────┐
  │  redis       (172.23.0.5)  ← infrastructure stack               │
  │  rabbitmq    (172.23.0.6)  ← infrastructure stack               │
  │  app-a-api   (172.23.0.7)  ← alias for app_a's api service      │
  │  app-b-api   (172.23.0.8)  ← alias for app_b's api service      │
  └─────────────────────────────────────────────────────────────────┘

  app_a's api internally: DNS "api" → its own container (within app_a_default)
  Any service on shared-services-net: DNS "app-a-api" → app_a's api ✅
  Any service on shared-services-net: DNS "app-b-api" → app_b's api ✅
  DNS "api" on shared network: AMBIGUOUS → avoid ❌
```

## 8. Operational Management — Creating and Inspecting External Networks

Managing external shared networks in a multi-project Docker environment requires a small amount of operational discipline: the shared network must exist before any Compose project that references it is started, and it must be destroyed carefully since multiple projects depend on it. The following patterns represent the standard operational workflow:

```bash
# ── Creating the shared network (one-time setup) ──────────────────────────────
# Use --driver bridge for single-host deployments
# Use --driver overlay for Docker Swarm multi-host deployments
docker network create \
    --driver bridge \
    --subnet 172.23.0.0/16 \
    --label project=shared-infrastructure \
    --label managed-by=ops-team \
    shared-services-net

# ── Verify the network exists before starting stacks ──────────────────────────
docker network ls --filter name=shared-services-net
docker network inspect shared-services-net

# ── Verify containers are on the correct networks after stack startup ──────────
docker network inspect shared-services-net \
    --format='{{range .Containers}}{{.Name}} ({{.IPv4Address}}){{"\n"}}{{end}}'
# Expected output shows all containers from all stacks that joined this network

# ── Safe teardown order ───────────────────────────────────────────────────────
# Stop consuming stacks first (those that use the shared services)
cd app_a && docker-compose down
cd app_b && docker-compose down

# Then stop the infrastructure stack (the one that provides shared services)
cd infrastructure && docker-compose down

# Finally, if the network should be removed:
docker network rm shared-services-net
# If any container is still connected: Docker returns an error
# The error protects against accidentally orphaning connected containers

# ── Startup order dependency (important) ──────────────────────────────────────
# 1. Create external network (if not exists)
# 2. Start infrastructure stack (provides Redis, RabbitMQ)
# 3. Start application stacks (consume Redis, RabbitMQ)
# Application stacks will fail with "network not found" if step 1 is skipped.

# Automate this in a startup script:
docker network create shared-services-net 2>/dev/null || true
# The '|| true' prevents script failure if network already exists
docker-compose -f infrastructure/docker-compose.yml up -d
docker-compose -f app_a/docker-compose.yml up -d
docker-compose -f app_b/docker-compose.yml up -d
```

## 9. Debugging Cross-Stack Connectivity — The Diagnostic Approach

When a service fails to connect to a container in another Compose stack, the diagnostic approach follows a clear sequence that isolates the problem to either DNS resolution, network membership, or routing:

```bash
# ── Step 1: Verify the shared network exists ──────────────────────────────────
docker network ls | grep shared-services-net
# If not found: network was never created. Run docker network create first.

# ── Step 2: Verify both containers are connected to the shared network ─────────
docker network inspect shared-services-net \
    --format='{{range .Containers}}{{.Name}}{{"\n"}}{{end}}'
# Both the source container and the target container must appear here.
# If source is missing: add the shared network to its Compose file.
# If target is missing: add the shared network to target's Compose file.

# ── Step 3: Test DNS resolution from the source container ─────────────────────
docker exec <source_container> nslookup redis
# Expected: returns an IP address on the shared network subnet
# Failure: "server can't find redis" → source not on shared net, or name wrong

# ── Step 4: Test TCP connectivity ─────────────────────────────────────────────
docker exec <source_container> nc -zv redis 6379
# Success: "Connection to redis 6379 port succeeded" ✅
# "No route to host": containers on different networks, no shared bridge route
# "Connection refused": network works, but Redis not listening (different problem)

# ── Step 5: Check container's network memberships ──────────────────────────────
docker inspect <source_container> \
    --format='{{range $net, $conf := .NetworkSettings.Networks}}{{$net}}{{"\n"}}{{end}}'
# Should list both the project's own network AND shared-services-net

# ── Common mistakes quick-check ────────────────────────────────────────────────
# 1. Compose file declares external network but docker network create was not run:
docker network ls | grep shared-services-net
# Fix: docker network create shared-services-net

# 2. Service attached to external network but Compose not restarted after adding:
docker-compose up -d --force-recreate <service_name>
# Containers must be recreated for new network attachments to take effect

# 3. Network name typo (case-sensitive):
# docker-compose.yml says: shared-Services-Net
# docker network create: shared-services-net
# These are DIFFERENT names. Docker network names are case-sensitive.
```

## 10. The Golden Rule

> Docker Compose project isolation is not a bug — it is a deliberate security feature that prevents services in one project from accidentally interfering with or reaching services in another project. Each Compose project gets its own private network, and the isolation between those networks is enforced at the kernel level. The consequence of this isolation is that services in different Compose projects cannot communicate with each other through service DNS names or by IP address unless they are explicitly connected to a shared external network. When cross-project communication is required, create a named external network with `docker network create`, declare it as `external: true` in the Compose files of every project that needs it, and attach only the services that genuinely need cross-project visibility to that network. Keep internal-only services on their project's private network. The principle of least privilege applies to networking as much as it applies to file permissions and process capabilities: services should be visible only to those that have a legitimate reason to reach them.

Connecting two Compose stacks is not the default — it is a deliberate architectural decision that must be expressed explicitly in code.
