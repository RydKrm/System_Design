# Case Study 01 — The EAV (Entity-Attribute-Value) Trap

---

## The Setup — The "Flexible" Schema That Became a Prison

A startup is building a user profiling system. The product team keeps changing their minds about what attributes a user should have. This week they want `age`, `city`, and `occupation`. Next week they want `favorite_color`, `subscription_tier`, and `last_login_device`. The week after that, they want to add `account_manager_id` and `preferred_language`. The attributes keep changing, and the developers are tired of writing database migrations every time a new one is requested.

A developer with prior experience proposes what seems like an elegant, future-proof solution: instead of adding a new column to the `users` table every time a new attribute is needed, design the database to store attributes generically. Three columns. Any attribute. Infinitely extensible. No migrations ever again. The schema looks like this:

```sql
-- The "flexible" schema that seems clever at design time:
CREATE TABLE user_attributes (
    entity_id        BIGINT      NOT NULL,  -- The user ID
    attribute_name   TEXT        NOT NULL,  -- e.g., 'age', 'city', 'occupation'
    attribute_value  TEXT        NOT NULL,  -- e.g., '32', 'Dhaka', 'Engineer'
    PRIMARY KEY (entity_id, attribute_name)
);
```

Now, adding a new attribute requires no schema migration — simply insert a new row. Need to store `favorite_color` for user 42? Just insert `(42, 'favorite_color', 'blue')`. The product team is happy. The developers feel clever. The system ships.

Six months later, the database has 2 million users, each with an average of 12 attributes — 24 million rows in `user_attributes`. The product team asks for a dashboard that shows all users who are older than 30 AND live in Dhaka AND have an `enterprise` subscription tier AND joined in the last 90 days. A developer sits down to write the query. Three hours later, the developer is still working on it. What results is one of the most grotesque SQL queries ever written in the company's history — a query with twelve self-joins, that runs for 45 seconds, and cannot be optimized because the data it needs is buried in text strings in a `value` column. This is the **EAV trap**, and the startup has walked directly into it.

---

## What EAV Is — The Pattern and Its Origin

EAV stands for **Entity-Attribute-Value**, and it is a data modeling pattern with a specific structure: a table with three columns representing the entity being described (a user ID, a product ID, etc.), the name of an attribute of that entity (a string), and the value of that attribute (also a string, or sometimes a generic type column). Every attribute for every entity becomes a row in this table, regardless of how different those attributes are from each other.

The EAV pattern has a legitimate — if narrow — historical origin. In the 1970s and 1980s, when relational databases were new and hardware was expensive, EAV was used in medical record systems (like Epic Healthcare's software still uses today) to represent clinical observations that genuinely could not be known at schema design time. A patient could have an observation for `blood_pressure`, `temperature`, `hemoglobin_level`, or ten thousand other possible clinical measurements, and the set of possible measurements was both enormous and unpredictable. EAV was a pragmatic choice for that specific problem domain.

The trap that modern developers fall into is applying EAV to problems where it is entirely unnecessary. When a developer does not know what attributes a user will have **yet**, but expects to discover and stabilize those attributes over time, EAV is not the solution. Adding columns is the solution. Database schema migrations are not the failure mode they are feared to be — modern migration tools like Flyway, Liquibase, and Go's `migrate` library make column additions safe, versioned, and reversible. The "I don't know the schema yet" justification for EAV almost always evaporates under scrutiny: the developer does know the schema, at least for now, and future schema changes are manageable with proper tooling.

```
EAV Schema vs. Normalized Schema — The Structural Comparison:
======================================================================

EAV Schema (the anti-pattern):
  Table: user_attributes
  +----------+------------------+-----------------+
  | entity_id| attribute_name   | attribute_value |
  +----------+------------------+-----------------+
  |    1     | age              | 32              |
  |    1     | city             | Dhaka           |
  |    1     | occupation       | Engineer        |
  |    1     | subscription     | enterprise      |
  |    1     | signup_date      | 2024-03-15      |
  |    1     | preferred_lang   | bn              |
  |    2     | age              | 28              |
  |    2     | city             | Dhaka           |
  |    2     | subscription     | free            |
  ...24 million rows for 2 million users with 12 attributes each...

  Every attribute is a row. Every value is a TEXT string.
  No type safety (ages and dates stored as text). No constraints.
  No ability to index specific attributes efficiently.

Normalized Schema (the correct approach):
  Table: users
  +----+-----+-------+------------+--------------+-------------+
  | id | age | city  | occupation | subscription | signup_date |
  +----+-----+-------+------------+--------------+-------------+
  |  1 |  32 | Dhaka | Engineer   | enterprise   | 2024-03-15  |
  |  2 |  28 | Dhaka | NULL       | free         | 2024-09-01  |
  ...2 million rows, one per user...

  Every attribute is a typed column. Indexes are direct.
  Type safety enforced by the schema.
  Simple WHERE clauses. Fast queries.
======================================================================
```

## The Query Complexity Explosion — Self-Joins as Far as the Eye Can See

The most viscerally painful consequence of EAV is what it does to the queries you need to write. In a normalized schema, filtering users by multiple attributes is a simple `WHERE` clause with multiple conditions. In an EAV schema, each attribute filter requires a separate join of the entire `user_attributes` table to itself. This is called a **self-join**, and it is one of the most expensive operations in relational algebra.

Let us trace exactly what a query for "users older than 30 who live in Dhaka and have an enterprise subscription" looks like in both schemas:

```sql
-- NORMALIZED SCHEMA — simple, readable, fast:
SELECT id, age, city, occupation, subscription
FROM users
WHERE age > 30
  AND city = 'Dhaka'
  AND subscription = 'enterprise';
-- Execution plan: Index scans or bitmap scans on indexed columns.
-- No joins. Linear complexity. Milliseconds.

-- EAV SCHEMA — the horror:
SELECT e.entity_id
FROM user_attributes e
-- Join #1: Get users where age > 30
JOIN user_attributes age_attr
    ON age_attr.entity_id = e.entity_id
    AND age_attr.attribute_name = 'age'
    AND CAST(age_attr.attribute_value AS INTEGER) > 30
-- Join #2: Get users where city = 'Dhaka'
JOIN user_attributes city_attr
    ON city_attr.entity_id = e.entity_id
    AND city_attr.attribute_name = 'city'
    AND city_attr.attribute_value = 'Dhaka'
-- Join #3: Get users where subscription = 'enterprise'
JOIN user_attributes sub_attr
    ON sub_attr.entity_id = e.entity_id
    AND sub_attr.attribute_name = 'subscription'
    AND sub_attr.attribute_value = 'enterprise'
WHERE e.attribute_name = 'age'  -- Anchor the base table
GROUP BY e.entity_id;

-- Three filters = three joins of a 24-million-row table to itself.
-- Ten filters = ten self-joins.
-- Each join multiplies the intermediate result set size.
```

To fully appreciate the horror, let us count the operations the query planner must perform for the three-attribute query on a table with 24 million rows:

```
Self-Join Complexity Analysis:
======================================================================

  Table size: 24 million rows (2M users * 12 attributes each)

  Base scan: 24M rows scanned to find the anchor set.

  Join #1 (age > 30):
    For each row in the base scan, look up the 'age' attribute
    for that entity_id. The subquery scans the 24M row table AGAIN
    to find rows where attribute_name = 'age'.
    Result: ~2M rows (all users have an age attribute).
    Then filter: CAST(value AS INTEGER) > 30 (type conversion on every row!)
    CAST cannot use any index because the column type is TEXT.
    Intermediate result: ~1.4M users (70% are > 30 in this example).

  Join #2 (city = 'Dhaka'):
    For each of the 1.4M rows, look up the 'city' attribute.
    Another 24M row scan to find city attributes.
    Filter to those matching 'Dhaka'.
    Intermediate result: ~140K users.

  Join #3 (subscription = 'enterprise'):
    For each of the 140K rows, look up subscription attribute.
    Another 24M row scan.
    Filter to 'enterprise'.
    Final result: ~14K users.

  Total rows scanned: 24M + 24M + 24M + 24M = 96 million row accesses
  Total joins: 3 (each joining a 24M-row table to itself)
  Type conversions: 2M CAST(TEXT -> INTEGER) operations (unindexable)
  Query time: 45+ seconds

  Normalized equivalent:
  Total rows scanned: 2M (single table scan with index assistance)
  Total joins: 0
  Type conversions: 0 (age is already an INTEGER column)
  Query time: ~50ms (with proper indexes)

  Performance ratio: 45,000ms / 50ms = 900x slower
======================================================================
```

And this is for only three attributes. The real query the product team asked for had four attributes. A fifteen-attribute filter would require fifteen self-joins of a 24-million-row table, producing a query that is not just slow but effectively impossible to optimize — no amount of indexing, query rewriting, or hardware upgrade can make fifteen self-joins on a 24-million-row table fast.

## The Type Safety Catastrophe

Beyond the query complexity problem, EAV introduces a type safety catastrophe that causes subtle data quality issues that are very difficult to detect and nearly impossible to enforce. In an EAV schema, every attribute value is stored as TEXT. There is no database-level constraint preventing a user's `age` from being stored as `'thirty-two'` instead of `'32'`, or as `'32.5'` instead of `'32'`, or as `null_string` instead of being absent. Every type validation must be done in application code, which means every application that writes to the EAV table must implement the same validation — and if any of them miss a case, bad data enters the database silently.

```
Type Safety Issues in EAV:
======================================================================

  Normalized column (INTEGER): age
  +------------------+------------------+
  | Valid inserts     | Invalid (blocked)|
  +------------------+------------------+
  | 32               | 'thirty-two'     |
  | 28               | 'N/A'            |
  | 0                | -1 (if constrained)|
  +------------------+------------------+
  DB enforces: type, range constraints, NOT NULL if specified.
  Developer cannot accidentally insert wrong type.

  EAV attribute_value (TEXT): 'age'
  +------------------+------------------+
  | Stored silently   | Stored silently  |
  +------------------+------------------+
  | '32'             | 'thirty-two'     |
  | '28'             | 'N/A'            |
  | '0'              | 'NULL'           |
  | '-1'             | ' 32 ' (spaces!) |
  +------------------+------------------+
  DB enforces: nothing. All values are valid TEXT.
  CAST(attribute_value AS INTEGER) fails at query time for bad data.
  Bad data discovered only when queries break.

  Real-world consequences:
  - Reports that silently exclude users with malformed age values
  - SUM(CAST(revenue AS NUMERIC)) failing because one row has 'N/A'
  - Sorting by 'age' giving lexicographic order ('9' > '32' in text sort!)
  - No ability to use CHECK constraints on attribute values
  - No referential integrity between attribute values and other tables
======================================================================
```

The lexicographic sort problem deserves special mention. In a normalized schema, `ORDER BY age DESC` sorts numerically: 45, 32, 28, 19. In EAV, `ORDER BY attribute_value DESC WHERE attribute_name = 'age'` sorts lexicographically: '9', '45', '32', '28', '19'. The value `'9'` sorts before `'45'` in text comparison because `'9' > '4'` character by character. This means any report that sorts by a numeric attribute stored in EAV will produce silently wrong results unless the developer remembers to cast — and every developer who ever writes such a query must remember this, forever.

## The Indexing Impossibility

The third catastrophic limitation of EAV is that meaningful indexing is essentially impossible. In a normalized schema, you can create an index on the `age` column and the database can use it for any query that filters on `age`. In EAV, any index you create on `attribute_value` is shared across all attribute types — the index entry for `'32'` (someone's age) sits alongside the index entry for `'Dhaka'` (someone's city) and `'enterprise'` (someone's subscription tier). To filter specifically for users where `attribute_name = 'age' AND attribute_value > '30'`, the query must first filter on `attribute_name` and then on `attribute_value` — a composite condition that standard B-tree indexes handle poorly, especially with the type cast required for numeric comparison.

You can create a partial index on specific attribute names, but this requires knowing in advance which attributes will be queried — which defeats the entire stated purpose of EAV (not knowing the schema in advance):

```sql
-- Attempting to add an index for the 'age' attribute:
CREATE INDEX idx_user_age
ON user_attributes (entity_id)
WHERE attribute_name = 'age';
-- This only helps lookup by entity_id where attribute_name = 'age'.
-- It does NOT help range queries like CAST(attribute_value AS INT) > 30,
-- because the cast prevents index usage on the value column.

-- The "correct" EAV index (still inadequate):
CREATE INDEX idx_user_attr_name_value
ON user_attributes (attribute_name, attribute_value);
-- This helps equality lookups: attribute_name='city' AND attribute_value='Dhaka'.
-- But: CAST(attribute_value AS INTEGER) > 30 STILL cannot use this index.
-- The cast operation is performed after the index lookup, not during it.
-- Range queries on numeric attributes stored as TEXT are always full scans.

-- The only solution that provides proper index support for a numeric attribute:
-- Move it to a proper typed column. There is no EAV index that matches this:
CREATE INDEX idx_users_age ON users (age);
-- Simple. Fast. Range queries, equality queries, and sorting all use this index.
```

## Solution One — Normalized Columns: The Right Tool for Known Attributes

For attributes that are known at design time — or discovered within the first weeks of development and then stabilized — the correct solution is a proper relational schema with typed columns. Adding a column to a table is not the dangerous, risky operation that EAV advocates fear. With modern PostgreSQL and migration tooling, adding a nullable column to a large table is an instantaneous operation (it does not rewrite the table — it only updates the catalog), and adding a column with a default value has been online and non-blocking since PostgreSQL 11.

```sql
-- The normalized users table — the correct approach:
CREATE TABLE users (
    id                BIGSERIAL PRIMARY KEY,
    email             TEXT        NOT NULL UNIQUE,
    age               INTEGER     CHECK (age BETWEEN 0 AND 150),
    city              TEXT,
    occupation        TEXT,
    subscription_tier TEXT        NOT NULL DEFAULT 'free'
                                  CHECK (subscription_tier IN ('free', 'starter', 'enterprise')),
    signup_date       DATE        NOT NULL DEFAULT CURRENT_DATE,
    preferred_lang    CHAR(2),    -- ISO 639-1 language code
    account_manager_id BIGINT     REFERENCES staff(id),
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Efficient, simple indexes on the columns that queries filter on:
CREATE INDEX idx_users_age         ON users (age);
CREATE INDEX idx_users_city        ON users (city);
CREATE INDEX idx_users_subscription ON users (subscription_tier);
CREATE INDEX idx_users_signup_date ON users (signup_date);

-- The query that took 45 seconds with EAV now takes ~50ms:
SELECT id, age, city, occupation, subscription_tier
FROM users
WHERE age > 30
  AND city = 'Dhaka'
  AND subscription_tier = 'enterprise'
  AND signup_date > CURRENT_DATE - INTERVAL '90 days';

-- Query plan: bitmap index scan on age, city, subscription_tier indexes.
-- No joins. No casts. No full table scans. Fast.
```

Adding new attributes as business requirements evolve is simply a matter of adding columns:

```sql
-- New requirement: add favorite_color. This is instant in PostgreSQL 11+:
ALTER TABLE users ADD COLUMN favorite_color TEXT;
-- No table rewrite. No downtime. Existing rows get NULL for the new column.
-- Index it if queries will filter on it:
CREATE INDEX CONCURRENTLY idx_users_favorite_color ON users (favorite_color);
-- CONCURRENTLY means no lock on the table while the index builds.
```

## Solution Two — JSONB Column: For Genuinely Flexible Attributes

There is a legitimate use case that sits between "fully normalized" and "full EAV": a system that has a known, stable core schema but genuinely needs to store a variable, unpredictable set of additional attributes per entity. A SaaS platform where each enterprise customer can define their own custom fields for their users is a real example. The core schema is known (name, email, signup date), but the custom fields vary by customer and cannot be known at schema design time.

PostgreSQL's **JSONB** column type is the correct solution for this case. JSONB stores structured data in a binary JSON format that is indexed, queryable, and type-safe within its domain. It provides the flexibility of a key-value store while retaining the queryability of a relational column, including GIN index support for fast containment queries:

```sql
-- Hybrid approach: normalized columns for known attributes, JSONB for flexible ones
CREATE TABLE users (
    id                BIGSERIAL PRIMARY KEY,
    email             TEXT        NOT NULL UNIQUE,
    age               INTEGER,
    city              TEXT,
    subscription_tier TEXT        NOT NULL DEFAULT 'free',
    signup_date       DATE        NOT NULL DEFAULT CURRENT_DATE,

    -- JSONB column for genuinely flexible, customer-specific attributes
    custom_fields     JSONB       NOT NULL DEFAULT '{}'
);

-- GIN index on the JSONB column for fast key-existence and value lookups:
CREATE INDEX idx_users_custom_fields_gin
ON users USING GIN (custom_fields);

-- For frequent queries on a specific JSONB key, a specialized functional index:
CREATE INDEX idx_users_account_tier
ON users ((custom_fields->>'account_tier'));
```

The JSONB approach allows queries that combine normalized columns (fast, indexed) with JSONB attribute filters (indexed via GIN), all in a single table without any joins:

```sql
-- Query combining normalized columns and JSONB attributes:
SELECT id, email, age, city
FROM users
WHERE age > 30
  AND city = 'Dhaka'
  AND subscription_tier = 'enterprise'
  AND custom_fields @> '{"account_manager": "Riya Sultana"}'  -- GIN index used
  AND custom_fields->>'region' = 'Asia Pacific';              -- Also GIN indexed

-- Inserting custom fields:
UPDATE users
SET custom_fields = custom_fields || '{"account_manager": "Riya Sultana", "region": "Asia Pacific"}'
WHERE id = 42;

-- Query users who have a specific custom field key (any value):
SELECT id, email FROM users WHERE custom_fields ? 'account_manager';
-- The ? operator checks key existence. Efficiently served by GIN index.

-- Query users where a numeric JSONB field meets a condition:
SELECT id, email FROM users
WHERE (custom_fields->>'priority_score')::INTEGER > 80;
-- Note: type cast still needed for JSONB numeric values,
-- but a functional index can make this efficient for frequent queries.
```

```
JSONB vs. EAV — The Comparison:
======================================================================

  Feature              | EAV               | JSONB
  ---------------------|-------------------|---------------------------
  Flexible attributes  | YES               | YES
  Type safety          | NO (all TEXT)     | Partial (JSON types)
  Indexed queries      | Very limited      | YES (GIN index)
  Multi-attribute query| Self-joins needed | Single WHERE clause
  Readability          | Very poor         | Good
  PostgreSQL support   | Manual            | Native, first-class
  Document databases   | Alternative       | Alternative
  NULL handling        | Missing rows      | Absent keys (natural)
  Migration needed     | Never             | Never (for JSONB fields)
  Performance          | Poor to terrible  | Good to excellent
  Known-attribute perf | Poor              | Good (use normal columns)
  Aggregation          | Extremely painful | Manageable
======================================================================
```

## Solution Three — Document Databases: When Truly Schemaless Is Right

There is one scenario where neither normalized columns nor JSONB is the right tool: when the data is genuinely, deeply schemaless — when different entities have not just different values but completely different structures, with no shared core schema, and where the queries are primarily key-based lookups rather than cross-attribute filtering. For this genuinely schemaless case, a document database like **MongoDB**, **CouchDB**, or **DynamoDB** is the appropriate tool. These systems are designed from the ground up for variable-structure documents, and their query engines are optimized for the access patterns of document data.

However, before reaching for a document database, it is worth asking honestly whether the data is truly schemaless or merely unfamiliar. In nearly every case where a developer considers EAV or a document database, the honest answer is that the schema is known — it just has not been written down yet. Writing it down, as SQL column definitions with proper types and constraints, is almost always the right first move.

## Migrating Away From an Existing EAV Schema

If you have inherited an EAV-based system and need to migrate it to a proper relational or hybrid schema, the process is methodical and can be done without downtime using PostgreSQL's online DDL capabilities:

```sql
-- Step 1: Audit the existing EAV data to understand what attributes exist
SELECT
    attribute_name,
    COUNT(DISTINCT entity_id)  AS entities_with_attribute,
    COUNT(*)                   AS total_values,
    MIN(attribute_value)       AS sample_min,
    MAX(attribute_value)       AS sample_max,
    -- Detect if values appear to be numeric:
    SUM(CASE WHEN attribute_value ~ '^-?[0-9]+(\.[0-9]+)?$' THEN 1 ELSE 0 END)
        AS numeric_value_count
FROM user_attributes
GROUP BY attribute_name
ORDER BY entities_with_attribute DESC;

-- Step 2: Add normalized columns for the stable, high-frequency attributes
ALTER TABLE users ADD COLUMN age INTEGER;
ALTER TABLE users ADD COLUMN city TEXT;
ALTER TABLE users ADD COLUMN subscription_tier TEXT;
ALTER TABLE users ADD COLUMN signup_date DATE;

-- Step 3: Backfill the normalized columns from EAV data (batched!)
-- Use the batch update pattern from Case Study 07 to avoid large transaction rollback
UPDATE users u
SET age = CAST(a.attribute_value AS INTEGER)
FROM user_attributes a
WHERE a.entity_id = u.id
  AND a.attribute_name = 'age'
  AND a.attribute_value ~ '^[0-9]+$'  -- Only migrate clean numeric values
  AND u.age IS NULL;
-- (Run in batches of 5000-10000 rows)

UPDATE users u
SET city = a.attribute_value
FROM user_attributes a
WHERE a.entity_id = u.id
  AND a.attribute_name = 'city'
  AND u.city IS NULL;

-- Step 4: For remaining flexible attributes, migrate to JSONB
ALTER TABLE users ADD COLUMN custom_fields JSONB NOT NULL DEFAULT '{}';

-- Aggregate remaining EAV attributes into JSONB per user:
UPDATE users u
SET custom_fields = (
    SELECT jsonb_object_agg(attribute_name, attribute_value)
    FROM user_attributes a
    WHERE a.entity_id = u.id
      AND a.attribute_name NOT IN ('age', 'city', 'subscription_tier', 'signup_date')
)
WHERE custom_fields = '{}';

-- Step 5: Add indexes on newly populated columns
CREATE INDEX CONCURRENTLY idx_users_age          ON users (age);
CREATE INDEX CONCURRENTLY idx_users_city         ON users (city);
CREATE INDEX CONCURRENTLY idx_users_subscription ON users (subscription_tier);
CREATE INDEX CONCURRENTLY idx_users_custom_gin   ON users USING GIN (custom_fields);

-- Step 6: Verify data quality before dropping EAV table
SELECT
    u.id,
    u.age,
    a.attribute_value AS eav_age
FROM users u
JOIN user_attributes a ON a.entity_id = u.id AND a.attribute_name = 'age'
WHERE u.age != CAST(a.attribute_value AS INTEGER)
  AND a.attribute_value ~ '^[0-9]+$';
-- Zero rows returned = migration was correct. Then DROP the EAV table.

-- Step 7: After verification, drop the EAV table (or archive it)
-- DROP TABLE user_attributes;  -- Only after thorough verification
```

## Diagnosing an EAV System — How to Measure the Damage

```sql
-- Query 1: Count EAV table size and estimate query complexity
SELECT
    relname                    AS table_name,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    n_live_tup                 AS row_count,
    n_live_tup / NULLIF(
        (SELECT COUNT(DISTINCT entity_id) FROM user_attributes), 0
    )                          AS avg_attributes_per_entity
FROM pg_stat_user_tables
WHERE relname = 'user_attributes';

-- Query 2: Find the most queried attribute names (most likely to need normalization)
SELECT
    attribute_name,
    COUNT(DISTINCT entity_id) AS entity_count,
    COUNT(*)                  AS total_rows,
    ROUND(100.0 * COUNT(DISTINCT entity_id) /
        (SELECT COUNT(DISTINCT entity_id) FROM user_attributes), 1) AS pct_entities
FROM user_attributes
GROUP BY attribute_name
ORDER BY entity_count DESC;
-- Attributes present in > 80% of entities are strong candidates for normalization.
-- Attributes present in < 20% are candidates for JSONB.

-- Query 3: Detect type inconsistency (values that cannot be cast to a number
-- despite the attribute appearing to be numeric in most rows)
SELECT
    attribute_name,
    attribute_value,
    entity_id
FROM user_attributes
WHERE attribute_name = 'age'
  AND attribute_value !~ '^[0-9]+$'  -- Values that are NOT pure integers
ORDER BY entity_id;
-- Non-zero result = data quality problem that normalized schema would have prevented.

-- Query 4: Find slow queries caused by EAV self-joins
SELECT
    query,
    calls,
    mean_exec_time,
    total_exec_time
FROM pg_stat_statements
WHERE query ILIKE '%user_attributes%'
  AND query ILIKE '%JOIN%user_attributes%'   -- Self-joins are the EAV fingerprint
ORDER BY mean_exec_time DESC
LIMIT 10;
-- Queries with multiple self-joins and high execution time are the EAV victims.
```

## The Complete Mental Model

```
THE EAV TRAP — COMPLETE MENTAL MODEL:
======================================================================

The Three-Column Illusion:
  entity_id | attribute_name | attribute_value
  -> Looks flexible. Feels clever. Is a trap.

The Query Complexity Explosion:
  Attributes in filter  | Joins required | Query time
  ----------------------|----------------|------------
  1                     | 1 self-join    | 2 seconds
  3                     | 3 self-joins   | 15 seconds
  5                     | 5 self-joins   | 45 seconds
  10                    | 10 self-joins  | Minutes
  15                    | 15 self-joins  | Timeout
  Complexity grows with number of attributes. Cannot be optimized.

Why EAV Fails:
  1. Self-joins exponentially expensive (n attributes = n joins of full table)
  2. Type safety gone (everything is TEXT, casts break indexes)
  3. Indexing impossible for range queries on numeric text values
  4. Data quality unenforceable (no CHECK constraints, no typed columns)
  5. Sort order wrong (lexicographic not numeric for TEXT columns)

When EAV Is Chosen:
  "We don't know the schema yet"  -> You do. Write it down.
  "Attributes change frequently"  -> ALTER TABLE ADD COLUMN is instant.
  "Custom fields per customer"    -> Use JSONB for custom fields.
  "True schemaless data needed"   -> Use MongoDB / document database.

The Three Correct Solutions:
  1. Normalized columns:    For known, stable attributes.
     - Types enforced       - Indexes work natively
     - Constraints work     - Simple WHERE clauses
     - Fast queries         - Standard SQL tooling

  2. JSONB column:          For genuinely flexible, variable attributes.
     - GIN index for fast lookups
     - Single column, no joins
     - Combined with normalized columns for hybrid approach
     - Functional index for frequently-queried JSONB keys

  3. Document database:     For truly schemaless data with key-value access.
     - MongoDB, DynamoDB    - Only when cross-attribute queries are rare
     - Do not use if complex filtering across attributes is needed

The Migration Path:
  Audit EAV table -> Identify stable attributes (> 80% present)
  -> Add columns with ALTER TABLE -> Backfill in batches
  -> Remaining attributes -> JSONB column
  -> Add indexes with CONCURRENTLY -> Verify -> Drop EAV table

The Rule:
  If you are writing a self-join query, you have a schema problem.
  The correct fix is ALWAYS at the schema level, not the query level.
  EAV moves schema complexity to the query. Queries cannot be optimized.
  Schemas can.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

The EAV trap teaches a fundamental lesson about the relationship between schema design and query expressiveness: **the schema is not a limitation to be worked around — it is the foundation that makes efficient queries possible**. When you encode your schema inside the data (as string keys in the `attribute_name` column), you remove the database's ability to reason about the structure of your data at planning time. The query planner cannot optimize a query that it cannot understand, and it cannot understand a query that requires it to join a table to itself twelve times just to retrieve twelve fields that should have been columns.

The fear of database migrations — the impulse that drives developers toward EAV — is almost always disproportionate to the actual cost of migrations. Adding a column to a table in PostgreSQL 11+ is a metadata-only operation that takes milliseconds regardless of table size. Adding a nullable column does not rewrite a single row. With proper migration tooling and a disciplined version-controlled migration workflow, schema evolution is not a problem to be avoided — it is a normal, safe, routine part of a healthy development process.

The JSONB column is the modern PostgreSQL answer to the legitimate subset of EAV use cases: genuinely flexible, customer-defined, or late-binding attributes that cannot be known at schema design time. It provides the flexibility of a key-value store with the queryability of a relational column, indexed by GIN for fast containment queries. The correct architecture for most systems is a hybrid: normalized, typed columns for the stable, universal attributes that all entities share, and a JSONB `custom_fields` column for the genuinely variable attributes that differ per entity or per customer.

EAV is a well-documented anti-pattern. It moves schema complexity from the database — where it can be optimized by the query planner — to the application and the queries — where it cannot. Recognize it, refuse to build it, and migrate away from it when you inherit it.
