# Case Study 08 — The Nullable Column with False NULL Semantics

---

## The Setup — One Column, Three Secrets

A billing engineer at a growing SaaS company needs to add discount functionality to the subscriptions table. The requirements come in stages over several months. First: some customers get a percentage discount off their base price. Second: a customer with 0% discount (full price, no reduction) needs to be distinguishable from a customer who was never assigned a discount. Third: suspended accounts should not be billed, and the billing team wants to track this state in the same table for convenience.

The engineer, under deadline pressure, reaches for the simplest possible schema change: a single nullable numeric column:

```sql
ALTER TABLE subscriptions ADD COLUMN discount NUMERIC(5,2) NULL;
-- Verbal documentation (only in the PR description, never in the schema):
-- NULL   = customer has no discount record (never processed)
-- 0.00   = customer is at full price (explicitly set, 0% discount)
-- 0.01 to 100.00 = customer has this percentage discount
-- -1.00  = customer account is suspended, do not bill
```

The column ships. The billing job that runs nightly reads subscriptions and applies discounts. Three months later, a new engineer joins the team and is asked to fix a bug in the billing report. The engineer writes a query to find all customers who should be billed at a discounted rate:

```sql
-- New engineer's query (intent: find customers with a discount):
SELECT customer_id, amount, discount
FROM subscriptions
WHERE discount IS NOT NULL;
```

The query returns suspended accounts (where `discount = -1`). The engineer does not know that `-1` means "suspended" — that convention was only in a PR description from three months ago. The billing report now incorrectly includes suspended accounts as "discounted" customers. The finance team runs this report for the quarterly board presentation, and the numbers are wrong.

A third engineer, fixing the bug the new engineer introduced, writes:

```sql
-- Third engineer's fix (intent: find customers with a real discount):
WHERE discount IS NOT NULL AND discount >= 0;
```

But this now accidentally includes the `discount = 0` rows — customers explicitly set to full price — in the "discounted customers" count, because `0 >= 0` is true. The discount rate column is now a minefield. Every developer who touches it must first excavate the hidden semantic conventions that no schema constraint enforces, no type system expresses, and no column name reveals. The only place this information exists is in PR descriptions and the memory of engineers who are increasingly leaving the company.

## What NULL Actually Means — The SQL Standard Definition

Before examining why overloading NULL with false semantics is catastrophic, it is worth understanding what NULL is supposed to mean, because the SQL standard is unambiguous about this and the definition has been consistent since SQL was first standardized.

In SQL, NULL represents **the absence of a known value**. Not zero. Not false. Not empty string. Not "not applicable." Not "a sentinel value for a special case." The absence of a known value — meaning that the value either does not exist, is unknown, or is not applicable to this particular row. This is called the **three-valued logic** of SQL (true, false, and unknown), and it is what makes NULL propagation work the way it does: any arithmetic or comparison involving NULL produces NULL (unknown), because you cannot know the result of an operation where one of the operands is unknown.

The two legitimate uses of NULL in SQL are:

**"Not applicable":** A `delivered_at TIMESTAMPTZ NULL` column in an orders table is NULL for orders that have not yet been delivered. The timestamp is not unknown — the delivery simply has not happened yet. NULL is used to say "this attribute does not apply to this row in its current state."

**"Unknown":** A `date_of_birth DATE NULL` column on a user profile is NULL when the user did not provide their birth date. The value exists in reality (everyone has a birth date) but is not known to the system. NULL correctly represents "we do not know this."

What NULL is **not** intended to represent:
- A specific state in a state machine ("suspended" is a state, not an absence of knowledge)
- A sentinel value with special application logic ("if discount is NULL, skip billing")
- A boolean flag overloaded onto a numeric column ("-1 means inactive")
- An alternative encoding of a categorical concept that belongs in a separate column

```
The SQL Three-Valued Logic — Why NULL Semantics Matter for Queries:
======================================================================

  NULL propagates through every operation:

  discount = -1   -> IS NULL? No. Is it = -1? Yes.
  discount = 0    -> IS NULL? No. Is it = 0? Yes. Is it > 0? No.
  discount = NULL -> IS NULL? Yes. Is it = NULL? UNKNOWN (not true!).
                      Is it > 0? UNKNOWN. Is it <= 0? UNKNOWN.

  Critical SQL behavior:
  WHERE discount = NULL   <- NEVER returns rows. Even where discount IS NULL.
  WHERE discount != NULL  <- NEVER returns rows. (NULL != NULL is UNKNOWN)
  WHERE discount IS NULL  <- Correctly finds rows with no value.

  When you have three semantic states hidden in one nullable column:
  NULL  = "never processed"
  0     = "no discount (full price)"
  -1    = "suspended"
  0-100 = "percentage discount"

  Query: "Find accounts that need billing" (should exclude NULL and -1):
  WHERE discount IS NOT NULL AND discount != -1
  -> Correct... IF every developer knows the convention.
  -> Incorrect: WHERE discount > 0  (excludes full-price customers with 0)
  -> Incorrect: WHERE discount IS NOT NULL  (includes -1 suspended accounts)
  -> Incorrect: WHERE discount >= 0  (correct exclusion of -1, but includes 0 with discounts)
     Wait — does including discount=0 mean "bill at full price"? YES.
     Is that correct? ONLY if you know that 0 != NULL.
     The semantics are now too complex to write a correct query without
     a full verbal explanation from another engineer.

  Every query touching this column is a correctness landmine.
======================================================================
```

## The Three-State Encoding — How the Bug Multiplies

The discount column encoding is not just one design mistake — it is a pattern of compounding mistakes that grows worse with every new state added. The original column had one state: a discount percentage. The first addition (NULL for "never processed") was defensible. The second addition (-1 for "suspended") is where the anti-pattern becomes catastrophic. And the anti-pattern, once established, attracts further overloading. In the real codebase this pattern came from, the column eventually gained `-2` for "grandfathered legacy pricing," `-3` for "trial period," and `999` for "contact sales team." Each addition required updating every developer's mental model, every comment in every query file, and every piece of business logic that touched the column.

```
The Overloading Evolution — How One Column Becomes a Protocol:
======================================================================

  Version 1 (launch):
  discount NUMERIC NULL
  -> NULL = no discount record

  Version 2 (3 months later): "We need to track explicit 0% discount"
  discount NUMERIC NULL
  -> NULL = no discount record
  -> 0    = explicit full price (no discount)
  All existing code must now distinguish NULL from 0. Some code doesn't.
  First bugs appear.

  Version 3 (6 months later): "Add suspended state to discount column"
  discount NUMERIC NULL
  -> NULL = no discount record
  -> 0    = explicit full price
  -> -1   = suspended (do not bill)
  All existing code must now handle -1. Some code treats it as a discount.
  Critical billing bug: suspended accounts are invoiced.

  Version 4 (9 months later): "Legacy customers need a different flag"
  discount NUMERIC NULL
  -> NULL = no discount record
  -> 0    = explicit full price
  -> -1   = suspended
  -> -2   = legacy pricing (use separate legacy_price column)
  Code that does WHERE discount < 0 now catches both suspended and legacy.
  Code that does WHERE discount = -1 still works. Code that doesn't — doesn't.

  Version 5 (12 months later): Marketing adds a trial flag
  discount NUMERIC NULL
  -> NULL = no discount record
  -> 0    = explicit full price
  -> -1   = suspended
  -> -2   = legacy pricing
  -> -3   = trial period (first month free)
  By now, the column is a protocol specification.
  Writing a correct WHERE clause requires reading a design document.
  Testing is impossible — too many state combinations to enumerate.
  Every new developer reads the column name ("discount"), assumes it is
  a number, and introduces a bug within their first two weeks.

  The column started as one concept and became five.
  The schema has zero record of this evolution.
  The code is littered with magic number comparisons.
  The tests do not cover all state combinations.
======================================================================
```

## The Invisible Bug Factory — Three Categories of Production Failure

The overloaded NULL column produces bugs in three distinct categories, each of which is notoriously difficult to detect in testing because the bugs are sensitive to specific combinations of data values that rarely appear in test datasets.

**Category One: Aggregation Errors.** Financial aggregations on the discount column produce wrong results because NULL values are excluded from aggregate functions (`SUM`, `AVG`, `COUNT`) and negative sentinel values contaminate arithmetic results. `AVG(discount)` on a table containing -1 values will produce a negative average that is mathematically meaningless. `SUM(amount * (1 - discount/100))` will produce a negative billing amount for suspended accounts (-1 discount gives `amount * 1.01` — a 1% surcharge rather than no billing). These errors appear in financial reports and are only discovered during audit.

**Category Two: Incorrect Filtering.** Developers who do not know the full convention write WHERE clauses that match the wrong rows. `WHERE discount IS NULL` intending to find "customers without a discount" also finds "customers who were never processed." `WHERE discount > 0` intending to find "discounted customers" misses full-price customers (discount = 0). `WHERE discount IS NOT NULL` intending to find "active billing" includes suspended customers. Each incorrect filter produces silently wrong results — no error, no exception, just the wrong data.

**Category Three: Cross-System Inconsistency.** The convention exists only in the application's institutional knowledge. A data analyst writing SQL directly against the database does not know the convention. A reporting tool generating queries does not know the convention. An external data pipeline consuming the table does not know the convention. Every consumer of the table must independently discover and correctly implement the magic number protocol. Those that fail produce incorrect reports, incorrect dashboards, and incorrect data exports — all silently, because the data is syntactically valid.

```
The Three Bug Categories in Concrete Queries:
======================================================================

  Data:
  id | customer_id | amount  | discount | expected_billing
  ---+-------------+---------+----------+-----------------
   1 |     101     | 100.00  | NULL     | (skip — never processed)
   2 |     102     | 100.00  | 0.00     | 100.00 (full price)
   3 |     103     | 100.00  | 10.00    | 90.00  (10% off)
   4 |     104     | 100.00  | -1.00    | (skip — suspended)
   5 |     105     | 100.00  | 25.00    | 75.00  (25% off)

  Correct billing query (requires knowing ALL conventions):
  SELECT customer_id, amount * (1 - COALESCE(discount, 0)/100) AS bill
  FROM subscriptions
  WHERE discount IS NOT NULL    -- Exclude never-processed
    AND discount >= 0;          -- Exclude suspended (-1)
  Result: rows 2, 3, 5. Correct.

  BUG CATEGORY 1: Aggregation error
  SELECT AVG(discount) FROM subscriptions;
  Result: AVG(NULL, 0, 10, -1, 25) = AVG(0, 10, -1, 25) = 8.5
  Real meaning: average of valid discounts = AVG(0, 10, 25) = 11.67
  Wrong by 38%. Used in pricing model analysis. Decision made on bad data.

  BUG CATEGORY 2: Wrong filter (missing suspended exclusion)
  SELECT customer_id, amount FROM subscriptions
  WHERE discount IS NOT NULL;  -- New engineer's query
  Result: rows 2, 3, 4, 5 (includes suspended customer 104)
  Suspended customer invoiced. Chargeback received. Customer escalates.

  BUG CATEGORY 3: Cross-system inconsistency
  Data analyst in BI tool:
  SELECT customer_id, amount * (1 - discount/100) AS discounted_amount
  FROM subscriptions
  WHERE discount IS NOT NULL AND discount > 0;
  Result for row 4 (discount=-1): 100 * (1 - (-1)/100) = 100 * 1.01 = 101.00
  Customer "billed" $101 in the BI report. Finance team asks why.
  Analyst has no idea about the -1 convention. Three-hour investigation.
======================================================================
```

## Solution One — Separate Columns for Separate Concepts

The root of the problem is conflating multiple distinct concepts into one column. The discount column is simultaneously encoding: existence of a discount record, the discount percentage, account status. These are three separate concepts that belong in separate columns. Separating them makes each column unambiguous, makes constraints expressible, and makes every query self-documenting:

```sql
-- The correct schema: one concept, one column, zero ambiguity:
ALTER TABLE subscriptions
    -- Step 1: Add a proper status column with an ENUM-like constraint
    ADD COLUMN account_status VARCHAR(20) NOT NULL DEFAULT 'active'
        CHECK (account_status IN ('active', 'suspended', 'trial', 'legacy', 'cancelled')),

    -- Step 2: Add a clean discount column for ONLY the percentage value
    -- NULL here means "no discount" — its one legitimate semantic meaning
    ADD COLUMN discount_pct NUMERIC(5,2) NULL
        CHECK (discount_pct IS NULL OR (discount_pct >= 0 AND discount_pct <= 100)),

    -- Step 3: Add a boolean to distinguish "no discount" from "explicitly at full price"
    -- if that distinction is needed (often it is NOT needed and can be dropped)
    ADD COLUMN discount_explicitly_set BOOLEAN NOT NULL DEFAULT false;

-- Now every query is unambiguous:

-- Find active accounts with a discount:
SELECT customer_id, amount, discount_pct
FROM subscriptions
WHERE account_status = 'active'
  AND discount_pct IS NOT NULL
  AND discount_pct > 0;

-- Find active accounts at full price:
SELECT customer_id, amount
FROM subscriptions
WHERE account_status = 'active'
  AND (discount_pct IS NULL OR discount_pct = 0);

-- Find suspended accounts:
SELECT customer_id
FROM subscriptions
WHERE account_status = 'suspended';
-- No magic number. No IS NULL check. Crystal clear.

-- Calculate billing amount — impossible to accidentally bill suspended:
SELECT
    customer_id,
    amount,
    discount_pct,
    amount * (1 - COALESCE(discount_pct, 0) / 100) AS billing_amount
FROM subscriptions
WHERE account_status = 'active';
-- account_status = 'active' is the only guard needed.
-- discount_pct is a clean numeric or NULL. No magic values. No traps.
-- COALESCE(discount_pct, 0) correctly handles NULL as "no discount" (0% off).
-- A new engineer can read this query and understand it in 10 seconds.

-- Aggregate without contamination:
SELECT AVG(discount_pct) FROM subscriptions WHERE discount_pct IS NOT NULL;
-- Only real discount percentages in the average. Suspended accounts not included.
-- Result is the actual average discount among customers with a discount. Correct.
```

## Solution Two — PostgreSQL ENUM Type for Status

When a column encodes a fixed set of categorical states — like account status — PostgreSQL's `ENUM` type is the most semantically precise tool. An ENUM column can only hold values that were explicitly defined when the type was created. Any other value, including magic numbers and undeclared states, is rejected by the database with a clear error:

```sql
-- Define the account status ENUM type:
CREATE TYPE account_status_enum AS ENUM (
    'active',
    'suspended',
    'trial',
    'legacy',
    'cancelled'
);

-- Use the ENUM type in the table:
ALTER TABLE subscriptions
    ADD COLUMN account_status account_status_enum NOT NULL DEFAULT 'active';

-- The ENUM type enforces valid values at the database level:
UPDATE subscriptions SET account_status = 'active';   -- OK
UPDATE subscriptions SET account_status = 'suspended'; -- OK
UPDATE subscriptions SET account_status = -1;          -- ERROR: invalid input for ENUM
UPDATE subscriptions SET account_status = 'frozen';    -- ERROR: 'frozen' not in enum

-- Adding new values to the ENUM (non-blocking in PostgreSQL 9.1+):
ALTER TYPE account_status_enum ADD VALUE 'grandfathered' AFTER 'legacy';
-- This operation is instant and does not lock the table.

-- Trade-offs of ENUM vs CHECK constraint:
-- ENUM:  - Type-safe at DB level  - Slightly harder to add values (ALTER TYPE)
--        - Stored as integer internally (efficient)
--        - Values visible in pg_type catalog
-- CHECK: - Easier to modify (just ALTER COLUMN ... SET CHECK)
--        - Stored as the actual string
--        - More flexible for different column types
-- Recommendation: Use ENUM for stable state machines. Use CHECK for simpler
-- validation or when values change frequently.
```

## Solution Three — The Status Lookup Table (For Complex State Machines)

When the set of statuses has associated metadata — transition rules, display labels, billing implications, email templates — a dedicated lookup table is the most expressive design:

```sql
-- Status lookup table: the states themselves become first-class entities
CREATE TABLE account_statuses (
    code            VARCHAR(30) PRIMARY KEY,
    display_label   VARCHAR(100) NOT NULL,
    is_billable     BOOLEAN NOT NULL DEFAULT true,
    is_active       BOOLEAN NOT NULL DEFAULT true,
    allows_login    BOOLEAN NOT NULL DEFAULT true,
    description     TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

INSERT INTO account_statuses VALUES
('active',      'Active',           true,  true,  true,  'Normal billing and access'),
('suspended',   'Suspended',        false, false, false, 'Temporarily blocked'),
('trial',       'Trial Period',     false, true,  true,  'Free trial, no billing'),
('legacy',      'Legacy Pricing',   true,  true,  true,  'Grandfathered pricing plan'),
('cancelled',   'Cancelled',        false, false, false, 'Account closed');

ALTER TABLE subscriptions
    ADD COLUMN account_status_code VARCHAR(30) NOT NULL DEFAULT 'active'
    REFERENCES account_statuses(code);

-- Now billing query is self-documenting and join-based:
SELECT s.customer_id, s.amount, a.is_billable
FROM subscriptions s
JOIN account_statuses a ON a.code = s.account_status_code
WHERE a.is_billable = true;
-- "Bill all accounts where the status is marked as billable."
-- No magic numbers. No IS NULL acrobatics.
-- A new engineer sees 'is_billable = true' and immediately understands.

-- Adding a new status never breaks any existing queries:
INSERT INTO account_statuses VALUES
('paused', 'Paused', false, true, true, 'Temporarily paused, no billing');
-- All queries that filter on is_billable = true automatically exclude paused.
-- Zero code changes required. Zero risk of forgetting to handle the new state.
```

## The Migration — Moving From Overloaded to Clean Schema

When you inherit an overloaded nullable column and need to migrate it to a clean schema, the process requires careful mapping of the old magic values to new explicit columns:

```sql
-- Migration: from overloaded discount column to clean separate columns

-- Step 1: Add new columns (non-blocking, instant)
ALTER TABLE subscriptions
    ADD COLUMN account_status  VARCHAR(20) NOT NULL DEFAULT 'active',
    ADD COLUMN discount_pct    NUMERIC(5,2) NULL;

-- Step 2: Backfill the new columns from the old magic-number column
-- Map the old encoding to the new explicit columns:
UPDATE subscriptions SET
    account_status = CASE
        WHEN discount = -1  THEN 'suspended'
        WHEN discount = -2  THEN 'legacy'
        WHEN discount = -3  THEN 'trial'
        ELSE 'active'         -- NULL, 0, and positive values are 'active'
    END,
    discount_pct = CASE
        WHEN discount >= 0  THEN discount   -- Preserve real discount values
        ELSE NULL                            -- Sentinel values -> no discount
    END
WHERE true;  -- Update all rows (use batch pattern for large tables)

-- Step 3: Add constraints on the new columns
ALTER TABLE subscriptions
    ADD CONSTRAINT chk_account_status
    CHECK (account_status IN ('active','suspended','trial','legacy','cancelled')),

    ADD CONSTRAINT chk_discount_pct_range
    CHECK (discount_pct IS NULL OR (discount_pct >= 0 AND discount_pct <= 100));

-- Step 4: Verify the migration is correct:
-- Old encoding: discount = -1 should map to suspended
SELECT COUNT(*) FROM subscriptions
WHERE discount = -1 AND account_status != 'suspended';
-- Expected: 0. Any non-zero count = migration bug.

-- Old encoding: discount >= 0 should map to the same discount_pct
SELECT COUNT(*) FROM subscriptions
WHERE discount >= 0 AND (discount_pct IS NULL OR discount_pct != discount);
-- Expected: 0. Any non-zero count = migration bug.

-- Step 5: Update all application code to use new columns
-- (This is the slowest step — must update every query, ORM model, and report)

-- Step 6: Drop the old column after all code is updated
-- ALTER TABLE subscriptions DROP COLUMN discount;  -- Final cleanup

-- Step 7: Add indexes on the new columns:
CREATE INDEX CONCURRENTLY idx_subscriptions_status
ON subscriptions (account_status);

CREATE INDEX CONCURRENTLY idx_subscriptions_status_discount
ON subscriptions (account_status, discount_pct)
WHERE account_status = 'active';  -- Partial: only active subscriptions
```

## Go Implementation — Handling Clean Nullable Columns Correctly

In Go, the correct mapping of a clean nullable `discount_pct NUMERIC NULL` column uses `sql.NullFloat64` or a `*float64` pointer — not a magic sentinel value:

```go
// WRONG: Using magic sentinel values in Go (mirrors the DB anti-pattern)
type Subscription struct {
    CustomerID int64
    Amount     float64
    Discount   float64  // -1 means suspended, 0 means full price...
}

func (s Subscription) BillingAmount() float64 {
    if s.Discount == -1 { return 0 }            // Magic number
    if s.Discount < 0  { return 0 }             // Defensive check
    return s.Amount * (1 - s.Discount/100)
}

// CORRECT: Using proper types and separate fields (mirrors the clean schema)
type AccountStatus string

const (
    AccountStatusActive    AccountStatus = "active"
    AccountStatusSuspended AccountStatus = "suspended"
    AccountStatusTrial     AccountStatus = "trial"
    AccountStatusLegacy    AccountStatus = "legacy"
    AccountStatusCancelled AccountStatus = "cancelled"
)

type Subscription struct {
    CustomerID    int64
    Amount        decimal.Decimal  // Use decimal library, not float64 (Case Study 04)
    AccountStatus AccountStatus
    DiscountPct   *decimal.Decimal // nil = no discount, value = percentage
}

// Self-documenting business logic — no magic numbers:
func (s Subscription) IsBillable() bool {
    return s.AccountStatus == AccountStatusActive ||
           s.AccountStatus == AccountStatusLegacy
}

func (s Subscription) BillingAmount() decimal.Decimal {
    if !s.IsBillable() {
        return decimal.Zero
    }
    if s.DiscountPct == nil {
        return s.Amount  // No discount — full price
    }
    discount := s.Amount.Mul(*s.DiscountPct).Div(decimal.NewFromInt(100))
    return s.Amount.Sub(discount)
}

// Scanning from the database — clean nullable handling:
func GetSubscription(db *sql.DB, id int64) (*Subscription, error) {
    s := &Subscription{}
    var discountPct sql.NullFloat64
    var statusStr string

    err := db.QueryRow(`
        SELECT customer_id, amount, account_status, discount_pct
        FROM subscriptions WHERE id = $1
    `, id).Scan(&s.CustomerID, &s.Amount, &statusStr, &discountPct)
    if err != nil { return nil, err }

    s.AccountStatus = AccountStatus(statusStr)
    if discountPct.Valid {
        d := decimal.NewFromFloat(discountPct.Float64)
        s.DiscountPct = &d
    }
    // s.DiscountPct remains nil when discountPct.Valid is false (NULL in DB)
    // nil in Go = no discount. No sentinel values. No magic numbers.

    return s, nil
}

// Query only what makes business sense:
func GetBillableSubscriptions(db *sql.DB) ([]*Subscription, error) {
    rows, err := db.Query(`
        SELECT customer_id, amount, account_status, discount_pct
        FROM subscriptions
        WHERE account_status IN ('active', 'legacy')
        ORDER BY customer_id
    `)
    // "active OR legacy" — readable, explicit, no magic numbers.
    // A developer who has never seen this codebase understands this query.
    if err != nil { return nil, err }
    defer rows.Close()
    // ... scan rows ...
    return nil, nil
}
```

## Detecting Overloaded NULL Columns in an Existing Schema

```sql
-- Audit 1: Find nullable numeric columns with suspiciously diverse value ranges
-- (negative values in a discount or quantity column are a red flag)
SELECT
    tablename,
    attname AS column_name,
    n_distinct,
    most_common_vals,
    most_common_freqs
FROM pg_stats
WHERE tablename = 'subscriptions'
  AND attname = 'discount'
ORDER BY tablename, attname;
-- If most_common_vals contains negative numbers like -1, -2, -3 in a
-- column that should only store non-negative values, magic sentinel encoding is present.

-- Audit 2: Find the actual distinct negative values in suspect columns
SELECT DISTINCT discount
FROM subscriptions
WHERE discount < 0
ORDER BY discount;
-- Non-empty result in a "discount" column = magic sentinel values present.

-- Audit 3: Count rows per magic value to understand the population size:
SELECT
    discount,
    COUNT(*) AS row_count,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS percentage
FROM subscriptions
GROUP BY discount
ORDER BY discount NULLS FIRST;
-- This reveals the full encoding:
-- NULL: 45,000 rows (32%)
-- -1:    5,000 rows (4%)  <- suspended (magic value)
-- 0:    20,000 rows (14%)
-- 10:   40,000 rows (28%)
-- 25:   30,000 rows (21%)

-- Audit 4: Identify queries that might have incorrect logic (via pg_stat_statements)
SELECT query, calls, mean_exec_time
FROM pg_stat_statements
WHERE query ILIKE '%discount%'
  AND (
      query ILIKE '%= -1%'     OR  -- Direct magic number comparison
      query ILIKE '%< 0%'      OR  -- Implicit sentinel check
      query ILIKE '%discount IS NULL%'  -- May be ambiguous
  )
ORDER BY calls DESC;
-- These queries may be implementing the magic-number convention correctly or incorrectly.
-- Each one is a candidate for review and refactoring.
```

## The Complete Mental Model

```
THE NULLABLE COLUMN WITH FALSE NULL SEMANTICS — COMPLETE MENTAL MODEL:
======================================================================

What NULL Actually Means in SQL:
  NULL = "this value is unknown or not applicable"
  NOT: "status code -1"
  NOT: "this record was never processed"
  NOT: "suspended"
  NOT: "use a different code path"

The Anti-Pattern:
  discount NUMERIC NULL where:
  -> NULL  = never processed (a state)
  -> 0     = full price (a value)
  -> -1    = suspended (a different state)
  -> 1-100 = discount percentage (the intended meaning)

  One column encoding: 1 measurement + 3 status states.
  Zero constraints enforcing the convention.
  Zero type system expression of the protocol.
  Only institutional knowledge (PR comments, oral tradition).

Why It Produces Bugs:
  1. Aggregations: AVG(discount) includes -1. Results are wrong.
  2. Filtering: WHERE discount IS NOT NULL includes suspended. Bills wrong accounts.
  3. Filtering: WHERE discount > 0 excludes full-price customers. Report is wrong.
  4. Cross-system: BI tools, analysts, pipelines don't know the convention.
  5. New developers: Column name says "discount". They assume it IS a discount.
  6. Evolution: New state added -> ALL existing code must be audited. Usually isn't.

The Three Correct Solutions:

  1. Separate Columns (always start here):
     account_status VARCHAR(20) CHECK (status IN ('active','suspended',...))
     discount_pct NUMERIC(5,2) CHECK (discount_pct IS NULL OR discount_pct BETWEEN 0 AND 100)
     -> NULL in discount_pct means ONE thing: no discount. Unambiguous.
     -> account_status is self-documenting. No reading old PRs required.

  2. PostgreSQL ENUM Type:
     CREATE TYPE account_status_enum AS ENUM ('active','suspended','trial',...);
     -> DB enforces valid values. Magic numbers impossible.
     -> Invalid states caught at insert time, not at application crash time.

  3. Status Lookup Table (for complex state machines):
     account_statuses: code, is_billable, allows_login, description
     -> Status metadata in the DB, not hardcoded in application code.
     -> Adding new status: INSERT INTO account_statuses. Zero code changes.

Go Pattern:
  WRONG: discount float64 = -1 (mirrors DB anti-pattern in application)
  CORRECT: AccountStatus = "suspended", DiscountPct *decimal.Decimal = nil
  Magic numbers in Go code = the DB anti-pattern has leaked into application.

Migration:
  Map magic values: discount=-1 -> account_status='suspended'
  Map real values:  discount>=0 -> discount_pct=discount
  Verify zero mismatches. Add CHECK constraints. Update all code. Drop old column.

The Diagnostic Test for False NULL Semantics:
  Ask: "Can NULL in this column mean more than one thing?"
  YES -> You have false NULL semantics.
  Ask: "Does this column contain negative values in a non-negative domain?"
  YES -> You have magic sentinel values.
  Ask: "Can I correctly query this column without reading the comments?"
  NO  -> You have overloaded semantics.

The Rule:
  NULL means "unknown" or "not applicable". One meaning. Always.
  Status belongs in a status column with a constrained set of valid values.
  Measurements belong in measurement columns with appropriate CHECK constraints.
  Flags belong in boolean columns with NOT NULL DEFAULT false.
  Never put two concepts in one column.
  The schema is your documentation. If the schema cannot express the meaning,
  the meaning is not enforced. Unenforced meaning produces bugs.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

The overloaded NULL column is a schema design failure that operates at the deepest level — the level of meaning. Every other case study in this series describes failures of performance, scale, or correctness in quantitative terms: milliseconds too slow, gigabytes too large, transactions failing under concurrency. The overloaded NULL column describes a failure of **semantic clarity** — the schema says one thing, the application means another, different parts of the codebase disagree on what is correct, and the database has no way to detect or prevent any of it.

The principle that resolves this class of problem is **one column, one concept**. A column that stores a discount percentage should store only discount percentages. A column that records account status should store only account status values. When a column is asked to do more than one job — to simultaneously represent a measurement and encode a state machine through magic values — it can do neither job correctly, because the constraints that would make each job correct are mutually incompatible.

NULL has exactly two legitimate meanings in SQL: "unknown" and "not applicable." These meanings are consistent with SQL's three-valued logic and with the mathematical foundations of relational theory. Any other use of NULL — as a sentinel value, as a state indicator, as a flag that triggers special code paths — is a misuse that creates ambiguity in every query that touches the column. The ambiguity compounds over time as new developers join, as new states are added to the overloaded encoding, and as the convention drifts between the application code, the reporting code, and the analytical code that all share the same table.

The fix is always the same: identify the distinct concepts that the overloaded column is encoding, give each concept its own column with the appropriate type and constraints, verify that the constraints enforce the valid values for each concept, and then write queries that read each concept from its own column. The resulting queries are longer in character count but shorter in cognitive load — they can be read and understood by any developer in any context without excavating the institutional knowledge encoded in the magic number convention.
