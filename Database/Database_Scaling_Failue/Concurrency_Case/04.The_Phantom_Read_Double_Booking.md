# Case Study 04 — The Phantom Read Double-Booking

---

## The Setup — Two Customers, One Seat, Both Confirmed

It is the night of the biggest football match of the year. The ticketing platform opens sales at 8:00 PM. Thousands of fans refresh the page simultaneously. Two fans — let us call them Maya and Ravi — both find that Seat A14 is available. Both click "Book Now" within milliseconds of each other. Both receive confirmation emails. Both print their tickets. Both arrive at the stadium. Both try to sit in Seat A14 at the same time.

This is not a story about hardware failure or network error or a bad deployment. The database is running perfectly. Every query executed successfully. Every transaction committed without error. Both bookings are sitting in the database right now, confirmed and valid. The system worked exactly as the code instructed it to. And the code is completely wrong.

This failure is called the **phantom read double-booking**, and it is the most business-damaging concurrency bug in existence. Unlike the lost update (Case Study 03), which corrupts data silently, the double-booking is discovered publicly — by angry customers at the point of service, by hotel front desks, by airline gate agents, by event security staff. It generates refunds, complaints, regulatory issues, and reputational damage that no amount of technical correctness can easily repair.

Understanding why it happens requires understanding a subtle but fundamental concept: the difference between what a transaction cannot see (uncommitted data from other transactions) and what it can see (committed data that was committed while the transaction was in progress). This distinction is the crack in which double-bookings live.

---

## The Phantom Read Explained — What Read Committed Actually Guarantees (And Doesn't)

Before tracing the double-booking step by step, you must understand precisely what PostgreSQL's default isolation level — **Read Committed** — promises and what it deliberately does not promise.

Read Committed guarantees exactly one thing: every statement within your transaction sees only **committed** data as of the moment that statement begins executing. It does not see data that other transactions have written but not yet committed (no dirty reads). This is a reasonable and useful guarantee. It prevents you from making decisions based on data that might be rolled back.

What Read Committed does **not** guarantee is that two statements within the same transaction see the same snapshot of committed data. If a new row is committed by another transaction between your first `SELECT` and your second `SELECT`, your second `SELECT` will see that new row. The new row that your second read sees but your first read did not is called a **phantom** — it appeared between your two reads like a ghost, and your transaction has no way to know it happened.

In a booking system, the phantom is the other person's booking. Transaction A checks for existing bookings (`SELECT COUNT(*)`), sees zero, decides the seat is available. Between A's check and A's insert, Transaction B also checks, also sees zero (because A has not committed yet), also decides the seat is available. Then both insert. Both succeed. The phantom that Transaction A's check failed to see was Transaction B's booking — because it did not exist yet when A checked, but it was inserted before A could protect the seat.

```
The Phantom Read — What Each Transaction Sees vs. Reality:
======================================================================

  bookings table before the concert sale begins:
  +------------+----------+----------+
  | booking_id | seat_id  | user_id  |
  +------------+----------+----------+
  |   (empty)  |          |          |
  +------------+----------+----------+

  Time  Transaction A (Maya)            Transaction B (Ravi)
  ----  --------------------------       --------------------------
  t=0   A: BEGIN

  t=1   A: SELECT COUNT(*) FROM
             bookings WHERE seat_id=14
          -> returns 0
          -> A decides: "seat is free!"

  t=2                                    B: BEGIN

  t=3                                    B: SELECT COUNT(*) FROM
                                              bookings WHERE seat_id=14
                                           -> returns 0   (A hasn't inserted yet)
                                           -> B decides: "seat is free!"

  t=4   A: INSERT INTO bookings
             (seat_id, user_id)
             VALUES (14, 'Maya')

  t=5   A: COMMIT
          -> Maya's booking is now committed.

  t=6                                    B: INSERT INTO bookings
                                              (seat_id, user_id)
                                              VALUES (14, 'Ravi')
                                           -> No error. No constraint violated.
                                              (Without a unique constraint, DB
                                               happily allows this.)

  t=7                                    B: COMMIT

  Final state of bookings table:
  +------------+----------+----------+
  | booking_id | seat_id  | user_id  |
  +------------+----------+----------+
  |     1      |    14    |  Maya    |  <- both confirmed
  |     2      |    14    |  Ravi    |  <- DOUBLE BOOKED
  +------------+----------+----------+

  What each transaction saw at its CHECK time vs. reality at COMMIT time:
  - A saw:  0 bookings for seat 14. Reality at commit: still 0. (Correct snap)
  - B saw:  0 bookings for seat 14. Reality at commit: 1 (Maya's). (STALE snap)
  - B's check result was VALID when B read it, but INVALID by the time B acted on it.
  - This is the phantom: Maya's booking did not exist when B checked, but existed
    when B committed. B's decision was based on a world that no longer existed.
======================================================================
```

The critical insight here is subtle and important: **Transaction B did not see dirty (uncommitted) data — it saw no data from A at all, because A had not yet committed when B read.** Read Committed protected B from seeing A's uncommitted insert. But it could not protect B from the fact that A's booking became real between B's read and B's write. The problem is not about seeing uncommitted data — it is about a check becoming stale between the reading and the acting.

## Why This Is Different From the Lost Update

It is worth pausing to contrast the phantom read double-booking with the lost update (Case Study 03), because they feel similar but are fundamentally different problems with different solutions.

In the **lost update**, two transactions read the same existing value, both modify it, and one write overwrites the other. The problem is at the level of a single existing row's value — the row existed before either transaction started, and both transactions are modifying it.

In the **phantom read double-booking**, the problem is about the absence of a row. Both transactions check for the existence of a row (a booking), find it absent, and then both create it. No existing row is overwritten. A new row simply appears twice — once per transaction. This is fundamentally a **write skew** or **phantom** anomaly: Transaction B makes a decision (`seat is available, I will book it`) based on a condition (`no existing booking`) that becomes false as a result of Transaction A's concurrent execution.

```
Lost Update vs. Phantom Read — The Key Distinction:
======================================================================

  LOST UPDATE (Case Study 03):
  Existing row:  [balance = 100]
  Txn A reads 100, computes 150, writes 150.
  Txn B reads 100, computes 150, writes 150.
  Result: [balance = 150] should be 200. One write LOST.
  Problem: Two writes on ONE EXISTING ROW in conflict.

  PHANTOM READ (This Case Study):
  Existing rows: [no bookings for seat 14]
  Txn A reads 0 bookings, decides available, inserts booking.
  Txn B reads 0 bookings, decides available, inserts booking.
  Result: TWO ROWS inserted for same seat. Double booking.
  Problem: A DECISION made on a condition that changed.
           The phantom is the row that APPEARED between check and act.

  Solutions differ:
  Lost update:   Atomic SQL, SELECT FOR UPDATE on the ROW being modified.
  Phantom read:  Unique constraint, SELECT FOR UPDATE on a RESOURCE row,
                 Advisory locks, or Serializable isolation.
                 Cannot just lock the booking row — it doesn't exist yet!
======================================================================
```

This distinction matters enormously for understanding the solutions. In the lost update, you lock the row you are about to modify. In the phantom read, **there is no row to lock** — the booking row does not exist yet. You need to lock something else to prevent the phantom: the resource being claimed (the seat row), or use a uniqueness constraint that makes the second insert fail, or use Serializable isolation which prevents the entire anomaly class.

## Why Application-Level Checks Are Insufficient

The most common first attempt at preventing double-bookings is to check availability in application code before inserting. Engineers write a check like: "if the seat has no bookings, then book it." This check is exactly what our example above does, and it is exactly why the double-booking occurs. Let us be very explicit about why no amount of additional checking in application code can fix this problem without database-level coordination.

Imagine you add a more thorough check — you count the bookings, you check a dedicated `seats.is_available` flag, you even recheck after the insert using a final `SELECT`. None of these help. The race condition exists in the gap between any read and any subsequent write. No matter how many reads you add, each one is a snapshot of the world at that instant, and the world can change before the next statement. Two concurrent transactions will always be able to both fall through any number of application-level checks if those checks are not backed by database-level locks or constraints.

```
Why Adding More Checks Does Not Help:
======================================================================

  ATTEMPT 1: Add a second check after insert
  -----------------------------------------------
  SELECT COUNT(*) ... -> 0 -> decide to book
  INSERT booking...
  SELECT COUNT(*) ... -> 2 -> rollback!

  Problem: Txn B's second check DOES see both bookings.
  But by then, BOTH transactions have already inserted.
  One must now detect and rollback. But which one?
  And what if both see count=2 simultaneously and both rollback?
  Then NOBODY gets the seat despite it being available. Race condition.

  ATTEMPT 2: Check a 'is_available' flag
  -----------------------------------------------
  SELECT is_available FROM seats WHERE seat_id=14 -> true
  -> both see true simultaneously -> both insert -> same problem.
  The flag check has the same race condition as the COUNT check.

  ATTEMPT 3: Update the flag to false before inserting
  -----------------------------------------------
  UPDATE seats SET is_available = false WHERE seat_id=14 AND is_available = true
  -> This actually WORKS (returns 0 rows if already false)
  -> But only because you are now using a write to lock the resource row.
  -> This is essentially SELECT FOR UPDATE implemented manually.

  FUNDAMENTAL RULE:
  Any number of reads cannot prevent concurrent writes from racing.
  Only a WRITE (lock acquisition) on a resource can serialize access to it.
  Either lock the resource row, use a unique constraint, or use Serializable.
======================================================================
```

## Solution One — Unique Constraint: The Database-Level Safety Net

The simplest and most robust first line of defense against double-booking is a **unique constraint** on the combination of columns that defines uniqueness for a booking. For a seat booking system, the constraint is that no two rows in the `bookings` table can have the same `seat_id` and `event_id`. The database enforces this constraint at the physical level, regardless of isolation level, regardless of application code, regardless of race conditions:

```sql
-- The uniqueness rule encoded at the database level.
-- This is your mandatory safety net, always, without exception.
ALTER TABLE bookings
ADD CONSTRAINT unique_seat_booking
UNIQUE (event_id, seat_id);

-- Alternative: a partial unique index for more complex rules
-- (e.g., only one CONFIRMED booking per seat, but multiple CANCELLED allowed):
CREATE UNIQUE INDEX unique_confirmed_booking
ON bookings (event_id, seat_id)
WHERE status = 'confirmed';
```

With this constraint in place, the sequence of events changes fundamentally. Both Transaction A and Transaction B can still both check availability and both decide the seat is free. But when both try to insert:

- Transaction A inserts first and commits. The constraint is satisfied (one row for `(event_id=1, seat_id=14)`).
- Transaction B inserts second. PostgreSQL checks the unique constraint. A row with `(event_id=1, seat_id=14)` already exists (committed by A). The insert **fails** with `ERROR: duplicate key value violates unique constraint`. Transaction B is rolled back automatically.

The unique constraint is the **last line of defense** — it guarantees correctness even when all other mechanisms fail. It does not provide a good user experience on its own (one customer gets an error rather than a graceful "seat just became unavailable" message), but it is non-negotiable as a safety net. Every booking system must have it.

```go
// Handling the unique constraint violation in Go:
func BookSeat(db *sql.DB, eventID, seatID, userID int64) error {
    _, err := db.Exec(`
        INSERT INTO bookings (event_id, seat_id, user_id, status, booked_at)
        VALUES ($1, $2, $3, 'confirmed', NOW())
    `, eventID, seatID, userID)

    if err != nil {
        // Check if this is a unique constraint violation (SQLSTATE 23505)
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) && pgErr.Code == "23505" {
            // This seat was just booked by someone else.
            // Return a business-friendly error for the application to handle.
            return ErrSeatAlreadyBooked
        }
        return fmt.Errorf("booking insert failed: %w", err)
    }
    return nil
}
```

The unique constraint is necessary but not sufficient on its own. While it guarantees no double-booking makes it into the database, it does not prevent the race condition from occurring and failing noisily. Under heavy load, many transactions will fail with constraint violations, each requiring a retry or a user-visible error. For a better user experience — where the system gracefully tells users a seat is unavailable before they attempt to book it — you need the locking solutions below.

## Solution Two — `SELECT FOR UPDATE` on the Resource Row

The most practical solution for booking systems is to acquire an exclusive lock on the **seat row** before checking its availability. This transforms the check-then-act pattern from a non-atomic two-step operation into a properly serialized sequence. When Transaction A acquires a `FOR UPDATE` lock on the seat row, Transaction B must wait until Transaction A finishes — meaning B will see the world after A has committed, including A's booking:

```go
// The correct booking implementation using SELECT FOR UPDATE:
func BookSeatSafe(db *sql.DB, eventID, seatID, userID int64) error {
    tx, err := db.Begin()
    if err != nil { return err }
    defer tx.Rollback()

    // Step 1: Lock the SEAT ROW with FOR UPDATE.
    // This lock prevents any other transaction from also locking this row
    // until we commit or rollback. Anyone else trying to book this same seat
    // will WAIT here until we are done.
    var capacity, bookedCount int
    err = tx.QueryRow(`
        SELECT s.capacity,
               COUNT(b.booking_id) AS booked_count
        FROM seats s
        LEFT JOIN bookings b ON b.seat_id = s.seat_id
                             AND b.event_id = $1
                             AND b.status = 'confirmed'
        WHERE s.seat_id = $2
        GROUP BY s.capacity
        FOR UPDATE OF s                -- Lock ONLY the seat row, not the bookings
    `, eventID, seatID).Scan(&capacity, &bookedCount)
    if err != nil {
        return fmt.Errorf("checking seat availability: %w", err)
    }

    // Step 2: Check availability. This check is now SAFE.
    // We hold the lock on the seat row. Any concurrent transaction that reaches
    // Step 1 for the same seat is blocked until we finish.
    // When they unblock, they will re-read AFTER our transaction commits,
    // seeing our booking included in bookedCount.
    if bookedCount >= capacity {
        return ErrSeatFullyBooked
    }

    // Step 3: Insert the booking. No race condition possible.
    // We hold the lock. No other transaction has been able to insert between
    // our check (Step 2) and our insert (Step 3).
    _, err = tx.Exec(`
        INSERT INTO bookings (event_id, seat_id, user_id, status, booked_at)
        VALUES ($1, $2, $3, 'confirmed', NOW())
    `, eventID, seatID, userID)
    if err != nil {
        return fmt.Errorf("inserting booking: %w", err)
    }

    return tx.Commit()
    // Commit releases the seat row lock.
    // Any waiting transactions (other booking attempts for the same seat)
    // now proceed, re-read the availability, and correctly see the seat as booked.
}
```

The power of this solution is in the `FOR UPDATE OF s` clause. By locking the seat row at the time of the availability check, we ensure that the check and the subsequent insert are a single atomic logical operation — no other transaction can observe the state "after our check but before our insert." The lock creates a serialization point: all booking attempts for the same seat are processed one at a time, in the order they acquire the lock.

```
The Flow WITH SELECT FOR UPDATE:
======================================================================

  seats table:
  +---------+----------+
  | seat_id | capacity |
  +---------+----------+
  |   14    |    1     |
  +---------+----------+

  Time  Txn A (Maya)                      Txn B (Ravi)
  ----  ----------------------------       ----------------------------
  t=0   A: BEGIN
  t=1   A: SELECT ... FROM seats
             WHERE seat_id=14
             FOR UPDATE
          -> Acquires EXCLUSIVE LOCK on seat row 14.
          -> Returns: capacity=1, booked=0

  t=2                                      B: BEGIN
  t=3                                      B: SELECT ... FROM seats
                                                WHERE seat_id=14
                                                FOR UPDATE
                                             -> Row locked by A. B WAITS.

  t=4   A: Check: booked(0) < capacity(1). Seat available!
  t=5   A: INSERT booking for Maya.
  t=6   A: COMMIT. Lock released.

  t=7                                      B: UNBLOCKED. Lock acquired.
                                           -> Re-reads: capacity=1, booked=1
                                           -> Check: booked(1) >= capacity(1).
                                           -> SEAT FULL. Returns ErrSeatFullyBooked.

  t=8                                      B: ROLLBACK.

  Result: Maya books seat 14. Ravi gets a clear "seat unavailable" message.
  CORRECT. No double booking. No constraint violation. No angry customers.
======================================================================
```

This is the correct user experience: Maya succeeds, Ravi is immediately informed that the seat is no longer available, and Ravi can choose a different seat. The system handles the concurrency gracefully, not by crashing one transaction with a constraint error, but by serializing the booking attempts and giving the second attempt accurate information.

## Solution Three — Serializable Isolation: Catch the Write Skew Automatically

The phantom read double-booking is a specific instance of a broader anomaly called **write skew**. Write skew occurs when two transactions read overlapping data, make decisions based on those reads, and then write in a way that, had they executed sequentially, would have been prevented. Serializable isolation is specifically designed to detect and prevent write skew.

When both transactions run under `SERIALIZABLE` isolation, PostgreSQL's **Serializable Snapshot Isolation (SSI)** engine tracks all reads and writes across concurrent transactions. When it detects that the concurrent execution produced a result that could not have occurred in any sequential ordering (Maya books then Ravi checks and fails, or Ravi books then Maya checks and fails), it aborts one of the transactions with a serialization failure (`SQLSTATE 40001`).

```go
// Using SERIALIZABLE isolation for the booking — PostgreSQL handles the detection
func BookSeatSerializable(db *sql.DB, eventID, seatID, userID int64) error {
    maxRetries := 3

    for attempt := 0; attempt < maxRetries; attempt++ {
        tx, err := db.BeginTx(context.Background(), &sql.TxOptions{
            Isolation: sql.LevelSerializable,
        })
        if err != nil { return err }

        // Under SERIALIZABLE isolation, PostgreSQL tracks that we read
        // from bookings WHERE seat_id=X. If another transaction writes
        // a row matching that predicate concurrently, PSI detects the
        // conflict and aborts one transaction.
        var bookedCount int
        err = tx.QueryRow(`
            SELECT COUNT(*)
            FROM bookings
            WHERE event_id = $1 AND seat_id = $2 AND status = 'confirmed'
        `, eventID, seatID).Scan(&bookedCount)
        if err != nil {
            tx.Rollback()
            return err
        }

        if bookedCount > 0 {
            tx.Rollback()
            return ErrSeatAlreadyBooked
        }

        _, err = tx.Exec(`
            INSERT INTO bookings (event_id, seat_id, user_id, status, booked_at)
            VALUES ($1, $2, $3, 'confirmed', NOW())
        `, eventID, seatID, userID)
        if err != nil {
            tx.Rollback()
            return fmt.Errorf("inserting booking: %w", err)
        }

        if err := tx.Commit(); err != nil {
            tx.Rollback()
            // Serialization failure: PostgreSQL detected the write skew.
            // One of the two concurrent transactions is aborted here.
            if isSerializationFailure(err) {
                if attempt < maxRetries-1 {
                    time.Sleep(time.Duration(attempt+1) * 10 * time.Millisecond)
                    continue
                }
                return ErrSeatAlreadyBooked // Treat as "seat taken after retry"
            }
            return fmt.Errorf("commit failed: %w", err)
        }
        return nil
    }
    return ErrMaxRetriesExceeded
}
```

Serializable isolation is the most theoretically correct solution — it handles not just the double-booking but every class of concurrency anomaly automatically. Its trade-off is performance: Serializable isolation has more overhead than Read Committed, and under high contention it aborts more transactions, requiring retries. For booking systems with high concurrency on the same seats, `SELECT FOR UPDATE` combined with a unique constraint tends to be more practical.

## Solution Four — Advisory Locks: Application-Level Mutual Exclusion

PostgreSQL provides a powerful feature called **advisory locks** — user-defined locks that applications can acquire and release at will, with no automatic connection to any database row or table. They are "advisory" in the sense that the database does not enforce them — the application must agree to use them consistently. But when used consistently, they provide flexible, application-defined serialization with very low overhead.

Advisory locks are particularly useful for booking systems where you want to serialize access to a logical resource (a seat in an event) without necessarily holding a row-level lock for the entire duration of the booking flow — which might include sending a confirmation email or calling a payment API (activities that should never happen inside a database transaction):

```go
// Advisory lock-based booking: serialize at the application level
// without holding a DB transaction open during external calls

func BookSeatWithAdvisoryLock(db *sql.DB, eventID, seatID, userID int64) error {
    // Create a unique integer key for this seat+event combination.
    // Advisory locks work on int64 keys, so we derive one deterministically.
    lockKey := hashSeatKey(eventID, seatID) // e.g., eventID*1000000 + seatID

    // Acquire a session-level advisory lock.
    // pg_try_advisory_lock returns true if the lock was acquired,
    // false if someone else already holds it.
    var acquired bool
    err := db.QueryRow("SELECT pg_try_advisory_lock($1)", lockKey).Scan(&acquired)
    if err != nil { return err }

    if !acquired {
        // Another request is currently processing a booking for this seat.
        return ErrSeatBookingInProgress
    }

    // IMPORTANT: Always release the advisory lock when done.
    // Use defer to guarantee release even on error paths.
    defer db.Exec("SELECT pg_advisory_unlock($1)", lockKey)

    // Now we have exclusive access to this seat's booking logic.
    // No other goroutine/process will proceed past pg_try_advisory_lock
    // for this same seat until we release the lock.

    // Step 1: Check availability (safe — we hold the advisory lock)
    var bookedCount int
    err = db.QueryRow(`
        SELECT COUNT(*) FROM bookings
        WHERE event_id = $1 AND seat_id = $2 AND status = 'confirmed'
    `, eventID, seatID).Scan(&bookedCount)
    if err != nil { return err }

    if bookedCount > 0 {
        return ErrSeatAlreadyBooked
    }

    // Step 2: Process payment (OUTSIDE the DB transaction — safe because
    // we hold the advisory lock, preventing concurrent booking of this seat)
    if err := processPayment(userID, seatPrice); err != nil {
        return fmt.Errorf("payment failed: %w", err)
    }

    // Step 3: Confirm the booking in the database
    _, err = db.Exec(`
        INSERT INTO bookings (event_id, seat_id, user_id, status, booked_at)
        VALUES ($1, $2, $3, 'confirmed', NOW())
    `, eventID, seatID, userID)
    return err

    // defer runs: pg_advisory_unlock releases the lock.
    // Next concurrent request for the same seat can now proceed.
}

func hashSeatKey(eventID, seatID int64) int64 {
    // Simple deterministic hash — combine event and seat into a unique int64.
    // In production, use a more robust hash to avoid collisions across events.
    return eventID*10_000_000 + seatID
}
```

The advisory lock approach is powerful because it decouples the serialization from the database transaction boundary. You can hold the advisory lock across payment processing, email sending, and other external operations — activities that would be catastrophic to include inside a database transaction (as we learned in Case Study 03). The lock is held for the entire logical booking operation, not just the database portion.

## The Layered Defense — Combining All Solutions

In a production booking system, no single solution is sufficient on its own. The correct approach is a layered defense where each layer catches what the previous layer might have missed:

```
Layered Booking System Defense:
======================================================================

  Layer 1 (First Defense): Advisory Lock or SELECT FOR UPDATE
  -----------------------------------------------------------
  Purpose: Serialize concurrent booking attempts BEFORE they occur.
  What it prevents: Both transactions proceeding past the availability check.
  What happens when it works: Second booker is told "seat unavailable" cleanly.
  What happens on failure: Second booker gets through (e.g., lock timeout).

  Layer 2 (Second Defense): Unique Constraint on (event_id, seat_id)
  -----------------------------------------------------------
  Purpose: Database-level guarantee of uniqueness.
  What it prevents: The second INSERT from succeeding even if Layer 1 fails.
  What happens when it works: Second INSERT fails with SQLSTATE 23505.
  What happens on failure: Nothing — this is mathematically uncircumventable.

  Layer 3 (Third Defense): Reconciliation and Monitoring
  -----------------------------------------------------------
  Purpose: Detect any double-bookings that slipped through all layers.
  How: Periodic reconciliation queries comparing bookings to seat capacity.
  What happens when it detects an issue: Alert engineering, trigger compensation.

  Combined Booking Flow:
  ======================

  Request arrives: "Book seat 14 for event 1"
       |
       v
  Acquire advisory lock for (event=1, seat=14)
  -> If lock held: return "booking in progress, try again" [Layer 1]
       |
       v
  BEGIN transaction
  SELECT ... FROM seats WHERE seat_id=14 FOR UPDATE  [Row-level safety]
       |
       v
  Check availability: is booked_count < capacity?
  -> No: ROLLBACK. Return "seat unavailable".  [Accurate availability check]
       |
       v
  INSERT INTO bookings (event_id=1, seat_id=14, user_id=X)
  -> On SQLSTATE 23505: ROLLBACK. Return "seat just booked". [Layer 2 safety net]
       |
       v
  COMMIT.
  Release advisory lock.
  Send confirmation email.  [AFTER commit, not during transaction]
       |
       v
  Return "Booking confirmed" to user.

  Result: Both layers prevent double-booking.
          Unique constraint ensures mathematical impossibility.
          Reconciliation catches anything unprecedented.
======================================================================
```

## Diagnosing Double-Bookings in Production

If double-bookings have already occurred in a live system, the diagnostic and remediation approach must be systematic. The first step is measuring the extent of the damage, the second is identifying the code path, and the third is implementing the fix with a data correction:

```sql
-- Step 1: Find all double-booked seats (the damage assessment query)
SELECT
    event_id,
    seat_id,
    COUNT(*) AS booking_count,
    ARRAY_AGG(user_id ORDER BY booked_at) AS users_who_booked,
    ARRAY_AGG(booked_at ORDER BY booked_at) AS booking_times
FROM bookings
WHERE status = 'confirmed'
GROUP BY event_id, seat_id
HAVING COUNT(*) > 1               -- More than one confirmed booking per seat
ORDER BY event_id, seat_id;

-- Step 2: Check if the unique constraint exists (it should)
SELECT
    conname   AS constraint_name,
    contype   AS constraint_type,
    pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'bookings'::regclass
  AND contype = 'u';              -- 'u' = unique constraint

-- Step 3: Add the missing unique constraint (prevents future double-bookings)
-- Use a partial unique index to handle complex business rules:
CREATE UNIQUE INDEX CONCURRENTLY unique_confirmed_seat
ON bookings (event_id, seat_id)
WHERE status = 'confirmed';

-- Step 4: Check current concurrency hotspots (seats under heavy concurrent load)
SELECT
    seat_id,
    event_id,
    COUNT(*) AS booking_attempts_per_minute
FROM booking_audit_log
WHERE attempted_at > NOW() - INTERVAL '1 minute'
GROUP BY seat_id, event_id
ORDER BY booking_attempts_per_minute DESC
LIMIT 10;
-- High counts here identify the seats needing the most serialization attention.

-- Step 5: Monitor for concurrent booking attempts (real-time lock contention)
SELECT
    pid,
    now() - query_start AS waiting_for,
    left(query, 120) AS query_text,
    wait_event
FROM pg_stat_activity
WHERE wait_event = 'tuple'       -- Row-level lock waits
  AND query LIKE '%bookings%'
ORDER BY waiting_for DESC;
```

## The Complete Mental Model

```
THE PHANTOM READ DOUBLE-BOOKING — COMPLETE MENTAL MODEL:
======================================================================

The Core Anomaly: Write Skew via Phantom Read
  Txn A reads: "seat 14 has 0 bookings" -> decides: "book it"
  Txn B reads: "seat 14 has 0 bookings" -> decides: "book it"
  Txn A writes: booking for Maya. COMMITS.
  Txn B writes: booking for Ravi. COMMITS.
  Result: 2 bookings for 1 seat. Neither transaction made a mistake alone.
  The problem: B's read (0 bookings) was valid when B read it,
               but invalid by the time B's INSERT committed.
               The phantom is Maya's row, which appeared between
               B's check and B's insert.

Why Read Committed fails:
  Read Committed = "every statement sees committed data at statement start"
  B's SELECT ran BEFORE A committed -> B correctly saw 0 bookings.
  B's INSERT ran AFTER A committed -> database did not recheck the condition.
  The isolation level protected B from seeing uncommitted data (good)
  but did not protect B from acting on a stale availability decision (bad).

The Four Solutions:

  1. Unique Constraint (MANDATORY, always):
     ALTER TABLE bookings ADD CONSTRAINT unique_seat UNIQUE(event_id, seat_id)
     -> Second INSERT fails with 23505. Data integrity guaranteed.
     -> User experience: error message instead of double booking.
     -> REQUIRED as the safety net under all other solutions.

  2. SELECT FOR UPDATE (RECOMMENDED for most systems):
     SELECT ... FROM seats WHERE seat_id=X FOR UPDATE
     -> Lock seat row before checking availability.
     -> Second booker WAITS, then re-reads, sees seat taken, fails gracefully.
     -> Good UX: "seat unavailable" not "error".

  3. Advisory Locks (for complex flows with external calls):
     pg_try_advisory_lock(seat_key)
     -> Serialize the ENTIRE booking flow including payment.
     -> Lock held OUTSIDE DB transaction boundary.
     -> Best when booking involves external service calls.

  4. Serializable Isolation (most comprehensive):
     BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE
     -> PostgreSQL detects write skew automatically.
     -> One transaction aborts with SQLSTATE 40001.
     -> Requires retry logic. Higher overhead.

  The Non-Solution (common mistake):
     Application-level checks with no DB coordination.
     "If count == 0, then insert" in application code.
     -> NEVER works. Race condition exists regardless of check complexity.
     -> Two concurrent transactions both see count==0 before either inserts.

  Production Implementation Order:
  1. Add unique constraint (CONCURRENTLY, safe in production).
  2. Add SELECT FOR UPDATE to booking check query.
  3. Add retry logic with exponential backoff.
  4. Add reconciliation monitoring query.
  5. Consider advisory locks if payment is in the booking flow.
```

## Key Takeaways — The Principles to Carry Forward

The phantom read double-booking is the concurrency bug that most directly translates into customer harm. Lost updates cause data corruption that may be discovered later. Deadlocks cause transaction failures that users see as errors. But double-bookings result in two humans physically showing up to claim the same resource — a situation no amount of database rollback can fix once the confirmation has been sent.

The fundamental principle is that **Read Committed isolation is not sufficient for any system that makes decisions based on the absence of data**. If your code checks whether something does not exist and then creates it, you are in phantom-read territory. Availability checks, slot reservation, appointment booking, inventory claiming — all of these are check-then-act patterns that Read Committed cannot protect. You need either a database-level uniqueness constraint (always), a row-level lock on the resource being claimed (`SELECT FOR UPDATE` on the seat/slot/item), advisory locks for complex flows, or Serializable isolation.

The unique constraint deserves special emphasis: it is not a substitute for proper locking, but it is a mandatory backstop that you must always have. It is the guarantee that no amount of application code bugs, race conditions, or unexpected concurrent behavior can result in two confirmed bookings for the same seat entering your database. It is your last line of defense, and it should be your first line of implementation. Add the unique constraint today. Add the `FOR UPDATE` logic after. But the constraint comes first — it is the one thing that makes the data mathematically correct regardless of everything else.

Read Committed isolation is not enough for booking systems. Two concurrent readers both see "available" and both book. Only a lock or a constraint can prevent it.
