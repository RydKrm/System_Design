# Case Study 02 — The Deadlock Cascade

---

## The Setup — Two Transactions, Two Rows, A Perfect Storm

Consider a banking application where users can transfer money between accounts. The operation is conceptually simple: subtract the transfer amount from the sender's account and add it to the recipient's account. Because both operations must succeed or fail together — you cannot take money from one account without giving it to another — a database transaction is the natural, correct tool. The implementation looks reasonable:

```go
func TransferFunds(db *sql.DB, fromID, toID int64, amount float64) error {
    tx, _ := db.Begin()
    defer tx.Rollback()

    tx.Exec("UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, fromID)
    tx.Exec("UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID)

    return tx.Commit()
}
```

This code works perfectly when only one transfer is happening at a time. It works fine when two transfers happen that involve completely different accounts. The system runs smoothly in testing, in staging, and in early production when traffic is light. Then, one afternoon, two transfers happen at exactly the same moment:

- **User Alice** transfers $100 from Account 1 to Account 2.
- **User Bob** transfers $50 from Account 2 to Account 1.

Transaction A (Alice's transfer) locks Account 1, then tries to lock Account 2. Transaction B (Bob's transfer) locks Account 2, then tries to lock Account 1. Transaction A is waiting for B to release Account 2. Transaction B is waiting for A to release Account 1. Neither can proceed. Neither will ever proceed. Both are waiting for each other, indefinitely, in a **deadlock**.

PostgreSQL detects this cycle within `deadlock_timeout` (default: 1 second) and breaks it by rolling back one of the two transactions with the error: `ERROR: deadlock detected`. That transaction's Go code receives an error, the user gets a failure response, and the developer stares at the error log wondering what just happened — because both transactions look individually correct. And they are individually correct. The problem is not in either transaction alone. The problem is in the interaction between them.

---

## What a Deadlock Actually Is — The Precise Definition

A deadlock is a situation in which two or more transactions are each waiting for a lock that another one of them holds, forming a **circular dependency** that can never resolve itself. No transaction can make progress because each is waiting for a resource that another waiting transaction possesses. The system is stuck.

Deadlocks are not a database bug or a rare edge case. They are a mathematically inevitable consequence of three conditions occurring simultaneously:

1. **Mutual exclusion** — a resource (a row lock) can be held by only one transaction at a time.
2. **Hold and wait** — a transaction holds resources while waiting to acquire more.
3. **Circular wait** — Transaction A waits for B, and B waits for A (or a longer cycle: A waits for B, B waits for C, C waits for A).

When all three conditions are simultaneously true, a deadlock exists. PostgreSQL does not prevent deadlocks from forming — it allows them to form and then detects and resolves them. The detection mechanism is a **wait-for graph** that PostgreSQL periodically examines to find cycles. When a cycle is found, PostgreSQL chooses the transaction with the least work done (the cheapest to roll back) as the **deadlock victim**, rolls it back, and allows the other transaction(s) to proceed.

This is important: **PostgreSQL saves the system from being permanently stuck, but it cannot prevent the deadlock from occurring in the first place**. Prevention is entirely the application's responsibility, achieved through disciplined lock acquisition ordering.

```
The Classic Deadlock — Visualized Step by Step:
======================================================================

                     Account 1 (id=1)    Account 2 (id=2)
                         [balance:$500]      [balance:$200]

Time -->   T1 (ms)       T2 (ms)

t=0        Txn A: BEGIN
t=1        Txn A: UPDATE accounts SET balance=balance-100 WHERE id=1
           -> LOCKS Account 1
           [Account 1: LOCKED by A]

t=2                      Txn B: BEGIN

t=3                      Txn B: UPDATE accounts SET balance=balance-50 WHERE id=2
                         -> LOCKS Account 2
                         [Account 2: LOCKED by B]

t=4        Txn A: UPDATE accounts SET balance=balance+100 WHERE id=2

           DEADLOCK STATE. Neither can proceed. Ever.

           Wait-for graph analysis: A -> B -> A (cycle detected!)
           Victim chosen: Txn B (less work done)
           Txn B: ROLLBACK (automatic)

           Bob's transfer: ERROR: deadlock detected (must be retried by app)
======================================================================
```

## Understanding the Wait-For Graph — How PostgreSQL Detects the Cycle

PostgreSQL's deadlock detection is built around a data structure called the **wait-for graph**. Every time a transaction tries to acquire a lock that is already held by another transaction, PostgreSQL adds a directed edge to this graph: "Transaction A is waiting for Transaction B." The graph represents the entire universe of lock dependencies in the system at any given moment.

A deadlock exists if and only if this graph contains a **cycle** — a path from some node back to itself. In the simple two-transaction case, the cycle is A → B → A. In more complex scenarios involving three or more transactions, the cycle can be longer: A → B → C → A. PostgreSQL's deadlock detection algorithm traverses the wait-for graph periodically (controlled by the `deadlock_timeout` parameter) looking for these cycles.

The `deadlock_timeout` parameter (default: 1 second) is the amount of time PostgreSQL waits after a lock is blocked before starting to check for deadlocks. This design is intentional: lock waits are common and usually resolve quickly, so running the expensive deadlock detection algorithm on every lock acquisition would be wasteful. By waiting `deadlock_timeout` first, PostgreSQL ensures it only runs the cycle-detection algorithm when a lock has been blocked long enough to be genuinely suspicious.

```
Wait-For Graph at Deadlock State:
======================================================================

  Nodes = Active transactions
  Edges = "waiting for" relationships

  Simple deadlock (2 transactions):
         +----->---+
         |         |
    [Txn A]     [Txn B]
         |         |
         +---<-----+
  Txn A -> Txn B (A waits for B to release Account 2)
  Txn B -> Txn A (B waits for A to release Account 1)
  Cycle: A -> B -> A  [DEADLOCK]

  Complex deadlock (3 transactions):
    [Txn A] -> [Txn B] -> [Txn C] -> [Txn A]
  Cycle: A -> B -> C -> A  [DEADLOCK]
  All three are stuck. PostgreSQL must pick one to sacrifice.

  No deadlock (linear wait):
    [Txn A] -> [Txn B] -> [Txn C]
  C is blocked by B. B is blocked by A.
  No cycle. When A commits, B proceeds, then C proceeds.
  This is normal lock queuing, not a deadlock.

  PostgreSQL algorithm:
  1. Wait deadlock_timeout (default: 1000ms)
  2. Build the current wait-for graph from pg_locks
  3. Run cycle detection (DFS on the graph)
  4. If cycle found: choose victim, issue ROLLBACK to victim
  5. Log: "ERROR: deadlock detected" with full context
======================================================================
```

## Real-World Patterns Where Deadlocks Appear

Deadlocks do not occur randomly. They appear at specific, predictable points in application logic where multiple rows must be locked in a sequence, and where different code paths can acquire those same rows in different orders. Understanding the common patterns helps you recognize and prevent them before they are written.

**Pattern One: Bidirectional Financial Transfers.** The canonical example from our opening. Any system where "A sends to B" and "B sends to A" can happen concurrently will deadlock if both code paths lock the accounts in the order they are specified in the request (from-account first, to-account second). The solution is to always lock accounts in a canonical order — for example, always locking the lower account ID first — regardless of which direction the transfer flows.

**Pattern Two: Multi-Item Cart Checkout.** An e-commerce checkout process that reserves inventory for multiple items in a cart. If one user's cart contains items [5, 3, 8] and another user's cart contains items [8, 3, 5], and both execute `SELECT ... FOR UPDATE` on those items in the order they appear in the cart (which may differ between users), they can deadlock when they both reach an item that the other has already locked. The solution is to sort the item IDs before locking: always lock items in ascending ID order, regardless of how they appear in the cart.

**Pattern Three: Hierarchical Data Updates.** Systems that update parent and child records in a hierarchy — for example, updating a department's budget aggregate when an employee's salary changes, while simultaneously updating the employee record when a department restructuring happens. One operation locks the employee then the department; the other locks the department then the employee. Consistent ordering (always parent before child, or always child before parent, globally) eliminates this cycle.

**Pattern Four: ORM-Generated Lock Ordering.** Many ORM frameworks do not guarantee a consistent order when acquiring locks across multiple records. If your ORM generates `SELECT ... FOR UPDATE WHERE id IN (1, 2, 3, 4)` statements, the physical order in which those locks are acquired depends on the execution plan, which may vary between queries, between database restarts, or between PostgreSQL versions. Explicit `ORDER BY id` on your `FOR UPDATE` queries is the only reliable fix.

## The Scaling Behavior — Why Deadlocks Are Rare at Low Traffic but Devastating at High Traffic

One of the most important characteristics of deadlocks is how their rate scales with transaction volume. At low concurrency — say, 10 transactions per second — the probability that two specific transactions hit the exact timing window required for a deadlock is very low. Transactions complete quickly and rarely overlap. A developer might test the fund transfer code for months without ever seeing a deadlock.

But deadlock probability grows non-linearly with concurrency. The mathematical relationship is roughly proportional to the square of the transaction rate (for simple two-transaction deadlocks) — doubling the transaction rate quadruples the deadlock rate. At 1,000 transactions per second with many involving the same set of popular rows, deadlocks can become a constant stream of failures rather than a rare anomaly.

```
Deadlock Rate vs. Transaction Volume:
======================================================================

  Deadlocks/sec
  ^
  100 |                                            *
   80 |                                        *
   60 |                                    *
   40 |                                *
   20 |                           *
   10 |                      *
    5 |                 *
    1 |           *
  0.1 |      *
 0.01 |  *
    0 +--+----+----+----+------+------+------+------+--> TPS
       10  50  100  200   500  1000   2000   5000  10000

  At 10 TPS:    deadlocks are rare (seconds or minutes between them)
  At 100 TPS:   deadlocks are occasional (every few minutes)
  At 1000 TPS:  deadlocks are constant (several per second)
  At 10000 TPS: deadlocks are catastrophic without proper ordering

  Why: Each transaction has ~N chances to overlap with N other transactions.
       With M concurrent transactions, there are M*(M-1)/2 pairs that could deadlock.
       Doubling M quadruples the potential deadlock pairs.

  Consequence: Code that seems fine in development and staging
               becomes a constant failure source in production at scale.
======================================================================
```

This scaling behavior is why deadlocks are so treacherous: they are essentially invisible during development and light-load testing, yet they become a high-frequency failure mode in production under real-world traffic. By the time you discover the problem, you have often already suffered production incidents, partial data corruption from rolled-back transactions, and user-facing errors.

## The Symptoms — Reading the Evidence

When deadlocks are occurring in production, the evidence appears simultaneously in several places, forming a distinctive pattern that an experienced engineer learns to recognize immediately.

The most direct symptom is the PostgreSQL log entry itself. When a deadlock is detected and a victim is chosen, PostgreSQL writes a detailed log entry that includes the error message, the blocking query, and the context of the deadlock. If you have proper PostgreSQL logging configured, this appears in your log file or log aggregation system:

```
ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 67890;
        blocked by process 11111.
        Process 11111 waits for ShareLock on transaction 12345;
        blocked by process 12345.
HINT: See server log for query details.
CONTEXT: while updating tuple (0,42) in relation "accounts"
```

At the application level, in Go, the deadlock appears as an `error` return from `tx.Exec()`, `tx.QueryRow()`, or `tx.Commit()` — whichever operation was executing on the victim transaction when it was rolled back. The error message will contain `deadlock detected`. An application without proper deadlock handling will surface this as a 500 Internal Server Error to the user.

A secondary symptom is **intermittent, apparently random transaction failures** with no clear pattern. Unlike other failures (connection timeouts, constraint violations) which tend to occur on specific operations or under specific conditions, deadlocks can affect any transaction that is unlucky enough to be chosen as the victim. Users and engineers see occasional failures on operations that "should work" and that work fine when retried immediately — because the deadlock cycle has been broken by the time the retry executes.

```sql
-- Monitor for deadlock frequency in PostgreSQL:
SELECT
    datname,
    deadlocks,
    blks_hit,
    blks_read
FROM pg_stat_database
WHERE datname = 'your_database_name';
-- The 'deadlocks' column counts deadlocks since the last stats reset.
-- A non-zero and growing value here is your early warning signal.
-- Run this query periodically and alert if the delta is > 0 per minute.

-- For real-time deadlock investigation — find currently blocked queries:
SELECT
    pid,
    now() - query_start AS blocked_for,
    query,
    wait_event,
    wait_event_type
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
  AND wait_event = 'relation'
ORDER BY blocked_for DESC;
```

## The Fix — Lock Acquisition Order is Everything

The canonical, universal fix for deadlocks is brutally simple once you understand it: **always acquire locks on multiple rows in the same global order, across every code path in your application**. If every transaction that touches rows A and B always locks A before B — never B before A — then the circular dependency that defines a deadlock becomes impossible. Transaction 1 locks A then waits for B. Transaction 2 also wants to lock A first, but A is already held by Transaction 1. Transaction 2 waits for A. This is a linear wait chain, not a circular one. No deadlock. Transaction 1 eventually completes, releases A, and Transaction 2 proceeds.

The most commonly used canonical ordering is **ascending primary key order**. If you always lock rows with lower IDs before rows with higher IDs, you establish a total order that all transactions follow, making circular dependencies impossible.

Here is how to apply this to the fund transfer example:

```go
// DEADLOCK-PRONE: locks accounts in transfer direction order (inconsistent)
func TransferFundsUnsafe(db *sql.DB, fromID, toID int64, amount float64) error {
    tx, err := db.Begin()
    if err != nil { return err }
    defer tx.Rollback()

    // If Alice transfers 1->2: locks 1 first, then 2.
    // If Bob transfers 2->1:  locks 2 first, then 1.
    // Alice + Bob concurrent = DEADLOCK.
    tx.Exec("UPDATE accounts SET balance = balance - $1 WHERE id = $2 RETURNING balance", amount, fromID)
    tx.Exec("UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID)

    return tx.Commit()
}

// DEADLOCK-SAFE: always locks in ascending ID order (consistent global order)
func TransferFundsSafe(db *sql.DB, fromID, toID int64, amount float64) error {
    tx, err := db.Begin()
    if err != nil { return err }
    defer tx.Rollback()

    // Determine the lock order: always lock the lower ID first.
    firstID, secondID := fromID, toID
    if toID < fromID {
        firstID, secondID = toID, fromID
    }

    // Step 1: Lock BOTH accounts in canonical order (lower ID first).
    // This SELECT FOR UPDATE acquires the locks without modifying data.
    // Crucially: both locks are acquired in the same global order,
    // regardless of which direction the transfer flows.
    rows, err := tx.Query(`
        SELECT id, balance
        FROM accounts
        WHERE id IN ($1, $2)
        ORDER BY id ASC          -- THE KEY: explicit ordering prevents deadlock
        FOR UPDATE
    `, firstID, secondID)
    if err != nil { return fmt.Errorf("locking accounts: %w", err) }
    defer rows.Close()

    // Read both balances into a map for use below.
    balances := make(map[int64]float64)
    for rows.Next() {
        var id int64
        var balance float64
        if err := rows.Scan(&id, &balance); err != nil { return err }
        balances[id] = balance
    }
    if err := rows.Err(); err != nil { return err }

    // Validate sufficient balance
    if balances[fromID] < amount {
        return ErrInsufficientFunds
    }

    // Step 2: Perform the actual updates. Locks are already held.
    // Order of UPDATE statements no longer matters — locks are already acquired.
    _, err = tx.Exec("UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, fromID)
    if err != nil { return fmt.Errorf("debiting account: %w", err) }

    _, err = tx.Exec("UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID)
    if err != nil { return fmt.Errorf("crediting account: %w", err) }

    return tx.Commit()
}
```

The `ORDER BY id ASC` in the `SELECT ... FOR UPDATE` is the critical line. It ensures that no matter which direction the transfer flows — from account 1 to account 2, or from account 2 to account 1 — the lock on account 1 is always acquired before the lock on account 2. The circular dependency is structurally impossible because every transaction follows the same total order.

## Applying the Pattern to Multi-Item Cart Checkout

The same principle applies to the multi-item cart checkout scenario. The naive implementation locks items in cart order, which varies per user. The correct implementation sorts by item ID before locking:

```go
// DEADLOCK-PRONE: locks items in cart order (varies per user)
func CheckoutUnsafe(db *sql.DB, tx *sql.Tx, cartItemIDs []int64) error {
    for _, itemID := range cartItemIDs {
        // If User A's cart is [5, 3, 8] and User B's cart is [8, 3, 5],
        // they will deadlock when both reach item 3 — A has 5, B has 8.
        _, err := tx.Exec(`
            UPDATE inventory
            SET reserved = reserved + 1
            WHERE item_id = $1 AND available > 0
        `, itemID)
        if err != nil { return err }
    }
    return nil
}

// DEADLOCK-SAFE: sorts item IDs before locking (consistent global order)
func CheckoutSafe(db *sql.DB, tx *sql.Tx, cartItemIDs []int64) error {
    // Create a sorted copy — never modify the caller's slice.
    sorted := make([]int64, len(cartItemIDs))
    copy(sorted, cartItemIDs)
    sort.Slice(sorted, func(i, j int) bool { return sorted[i] < sorted[j] })

    // Lock all items in ascending ID order before modifying any.
    // Use a single SELECT FOR UPDATE with ORDER BY for atomic, ordered locking.
    placeholders := make([]string, len(sorted))
    args := make([]interface{}, len(sorted))
    for i, id := range sorted {
        placeholders[i] = fmt.Sprintf("$%d", i+1)
        args[i] = id
    }

    lockQuery := fmt.Sprintf(`
        SELECT item_id, available
        FROM inventory
        WHERE item_id IN (%s)
        ORDER BY item_id ASC      -- CONSISTENT GLOBAL ORDER
        FOR UPDATE
    `, strings.Join(placeholders, ","))

    rows, err := tx.Query(lockQuery, args...)
    if err != nil { return fmt.Errorf("locking inventory: %w", err) }
    defer rows.Close()

    available := make(map[int64]int)
    for rows.Next() {
        var id int64
        var avail int
        if err := rows.Scan(&id, &avail); err != nil { return err }
        available[id] = avail
    }

    // Validate availability before any modifications
    for _, id := range sorted {
        if available[id] <= 0 {
            return fmt.Errorf("item %d is out of stock", id)
        }
    }

    // Now perform all updates — locks already held in correct order
    for _, id := range sorted {
        _, err := tx.Exec(`
            UPDATE inventory SET reserved = reserved + 1, available = available - 1
            WHERE item_id = $1
        `, id)
        if err != nil { return fmt.Errorf("reserving item %d: %w", id, err) }
    }
    return nil
}
```

## Retry with Exponential Backoff — The Essential Companion

Even with proper lock ordering, deadlocks can occasionally occur due to subtle ORM behaviors, third-party library interactions, or complex multi-table operations where maintaining a global order is impractical. For these cases, **retry with exponential backoff** is the essential companion to proper ordering. The retry handles the small residual deadlock rate gracefully, while the ordering fix handles the large structural deadlock rate.

A retry without backoff creates a new problem: if ten transactions all deadlock at the same moment and all retry immediately, they are highly likely to deadlock again immediately, creating a **retry storm** that is as damaging as the original deadlock cascade. Exponential backoff — waiting progressively longer between retries — breaks the synchronization that causes retry storms:

```go
// Retry wrapper with exponential backoff for deadlock-prone transactions:
func WithDeadlockRetry(ctx context.Context, db *sql.DB, maxRetries int, fn func(*sql.Tx) error) error {
    var lastErr error

    for attempt := 0; attempt < maxRetries; attempt++ {
        if attempt > 0 {
            // Exponential backoff: 10ms, 20ms, 40ms, 80ms...
            // Add jitter to prevent synchronized retries (thundering herd).
            baseDelay := time.Duration(10<<uint(attempt-1)) * time.Millisecond
            jitter := time.Duration(rand.Intn(int(baseDelay / 2)))
            backoff := baseDelay + jitter

            select {
            case <-time.After(backoff):
                // Continue to retry after backoff
            case <-ctx.Done():
                return fmt.Errorf("context cancelled during retry backoff: %w", ctx.Err())
            }
        }

        tx, err := db.BeginTx(ctx, nil)
        if err != nil {
            return fmt.Errorf("beginning transaction: %w", err)
        }

        err = fn(tx)
        if err != nil {
            tx.Rollback()

            // Check if this is a deadlock error from PostgreSQL
            if isDeadlockError(err) {
                lastErr = err
                // Log the deadlock for monitoring — deadlocks should be rare
                // after proper fix; frequent deadlocks indicate a code problem.
                log.Printf("WARN: deadlock on attempt %d/%d: %v", attempt+1, maxRetries, err)
                continue // Retry
            }
            // Not a deadlock — do not retry, return the error immediately
            return err
        }

        if err := tx.Commit(); err != nil {
            tx.Rollback()
            if isDeadlockError(err) {
                lastErr = err
                continue // Retry on commit-time deadlock too
            }
            return fmt.Errorf("committing transaction: %w", err)
        }
        return nil // Success
    }

    return fmt.Errorf("transaction failed after %d attempts (last error: %w)", maxRetries, lastErr)
}

// isDeadlockError checks if a PostgreSQL error is a deadlock (SQLSTATE 40P01)
func isDeadlockError(err error) bool {
    if err == nil { return false }
    // PostgreSQL deadlock error code is 40P01
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) {
        return pgErr.Code == "40P01"
    }
    // Fallback: check error message string
    return strings.Contains(err.Error(), "deadlock detected")
}

// Usage example:
func HandleTransfer(db *sql.DB, fromID, toID int64, amount float64) error {
    ctx := context.Background()
    return WithDeadlockRetry(ctx, db, 3, func(tx *sql.Tx) error {
        return transferWithinTx(tx, fromID, toID, amount)
    })
}
```

## PostgreSQL Configuration — Tuning the Deadlock Detector

Two PostgreSQL configuration parameters directly control deadlock behavior, and understanding them helps you tune the system for your workload:

```sql
-- deadlock_timeout: How long to wait before checking for a deadlock.
-- Default: 1s. Lower values detect deadlocks faster but add overhead
-- because the detection algorithm runs more frequently.
-- For high-traffic systems: 100ms to 500ms is a good range.
-- Too low: excessive CPU overhead from frequent cycle detection.
-- Too high: blocked transactions wait longer before being freed.
deadlock_timeout = '500ms'

-- lock_timeout: Maximum time a transaction waits for any lock.
-- If a lock is not acquired within this time, the transaction aborts
-- with "ERROR: canceling statement due to lock timeout".
-- This is a complementary safety net to deadlock detection.
-- Without this, a legitimate long lock wait (not a deadlock) could
-- hold a connection for minutes.
lock_timeout = '10s'

-- log_lock_waits: Logs a warning whenever a lock wait exceeds deadlock_timeout.
-- Essential for diagnosing lock contention without needing a full deadlock.
log_lock_waits = on

-- Set per-role for fine-grained control:
ALTER ROLE app_user SET deadlock_timeout = '500ms';
ALTER ROLE app_user SET lock_timeout = '10s';
ALTER ROLE app_user SET log_lock_waits = on;
```

With `log_lock_waits = on`, PostgreSQL writes a log entry whenever any transaction waits longer than `deadlock_timeout` for a lock — including waits that eventually succeed without a deadlock. This is valuable because it reveals lock contention problems before they escalate to deadlocks. If you see many `lock wait time` log entries on a specific table or query, you have a contention problem that is on its way to becoming a deadlock problem at higher traffic.

## Diagnosing Deadlocks in Production — The Complete Playbook

```sql
-- 1. Check if deadlocks are happening at all (run periodically, alert on increase):
SELECT datname, deadlocks, conflicts
FROM pg_stat_database
WHERE datname = current_database();

-- 2. See the current state of all lock waits (run during an incident):
SELECT
    blocked_locks.pid       AS blocked_pid,
    blocked_activity.query  AS blocked_query,
    blocking_locks.pid      AS blocker_pid,
    blocking_activity.query AS blocker_query,
    now() - blocked_activity.query_start AS wait_duration
FROM pg_catalog.pg_locks AS blocked_locks
JOIN pg_catalog.pg_stat_activity AS blocked_activity
    ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks AS blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
   AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
   AND blocking_locks.page    IS NOT DISTINCT FROM blocked_locks.page
   AND blocking_locks.tuple   IS NOT DISTINCT FROM blocked_locks.tuple
   AND blocking_locks.granted = true
   AND blocked_locks.granted = false
JOIN pg_catalog.pg_stat_activity AS blocking_activity
    ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted
ORDER BY wait_duration DESC;

-- 3. Find which tables are most involved in lock contention:
SELECT
    relation::regclass AS table_name,
    locktype,
    mode,
    granted,
    count(*) AS lock_count
FROM pg_locks
WHERE relation IS NOT NULL
GROUP BY relation, locktype, mode, granted
ORDER BY lock_count DESC;
-- Tables with many 'granted = false' entries are your hot contention points.

-- 4. After a deadlock, examine PostgreSQL logs for the detailed context:
-- grep "deadlock detected" /var/log/postgresql/postgresql-*.log
-- The log will show exactly which queries were involved and which rows they fought over.
-- This is the most direct path to identifying the code paths that need lock ordering fixes.
```

## The Complete Mental Model — Everything in One Picture

```
THE DEADLOCK CASCADE — COMPLETE MENTAL MODEL:
======================================================================

The Root Cause: Circular Lock Dependency
  Txn A holds Lock(row_1), wants Lock(row_2)
  Txn B holds Lock(row_2), wants Lock(row_1)
  A waits for B. B waits for A. Forever. DEADLOCK.

Why It Happens: Inconsistent Lock Ordering
  Code Path 1: transfer(from=1, to=2) -> lock(1) then lock(2)
  Code Path 2: transfer(from=2, to=1) -> lock(2) then lock(1)
  Different ordering = circular dependency possible = deadlock inevitable

The Detection Timeline:
  t=0ms:   Deadlock formed. Both transactions blocked.
  t=500ms: deadlock_timeout elapses. PostgreSQL checks wait-for graph.
  t=501ms: Cycle found: A -> B -> A.
  t=502ms: Victim chosen (Txn B, less work done). ROLLBACK issued.
  t=503ms: Txn B receives "ERROR: deadlock detected".
           Txn B's connection released. Lock freed.
           Txn A resumes. Acquires remaining lock. Commits.
  t=510ms: Txn B's Go handler returns error. Application retries (hopefully).

The Universal Fix: Consistent Global Lock Ordering
  WRONG:  lock(min(from,to)), lock(max(from,to))... NO. Don't do this ad-hoc.
  RIGHT:  Always lock rows in ascending ID order. Without exception.

  for transfers:
    firstID = min(fromID, toID)
    secondID = max(fromID, toID)
    SELECT ... WHERE id IN ($firstID, $secondID) ORDER BY id ASC FOR UPDATE

  for multi-row operations:
    sort(ids)  // ascending, before ANY lock acquisition
    SELECT ... WHERE id IN (...) ORDER BY id ASC FOR UPDATE

The Scaling Problem:
  Low TPS   -> deadlocks rare     -> "never happens in dev"
  High TPS  -> deadlocks frequent -> "production is broken"
  Quadratic growth: 2x TPS = 4x deadlock rate (for same bad code)

The Four-Layer Defense:
  Layer 1: ORDER BY id ASC on all FOR UPDATE queries        (eliminate root cause)
  Layer 2: WithDeadlockRetry() with exponential backoff     (handle residuals)
  Layer 3: deadlock_timeout = '500ms', lock_timeout = '10s' (fast detection)
  Layer 4: pg_stat_database.deadlocks monitoring + alerting (visibility)

The Golden Rule:
  If your transaction touches N rows for UPDATE,
  those N rows must always be locked in the SAME ORDER
  by EVERY transaction in your ENTIRE application.
  One exception = one deadlock opportunity.
```

## Key Takeaways — The Principles to Carry Forward

The deadlock case study contains a lesson that transcends database engineering and speaks to a fundamental principle of concurrent programming: **shared resources acquired in inconsistent order always create the potential for circular deadlock**. This is true in databases, in operating systems (mutex lock ordering), in distributed systems (resource reservation ordering), and in any system where concurrent agents compete for exclusive access to multiple resources.

The mental model to internalize is this: whenever you write code that acquires locks on more than one thing simultaneously, ask yourself — "Is there any other code path in this system that acquires these same locks in a different order?" If the answer is yes, or if you are not certain, you have a deadlock waiting to happen. The fix is always the same: establish a global canonical order for all lock acquisitions across the entire application and enforce it without exceptions.

PostgreSQL's deadlock detection is a safety net, not a solution. The database saves you from being permanently stuck, but it does not make the circular dependency go away — it breaks it by sacrificing one transaction's work. The retry that follows puts load back on the system and risks re-deadlocking if the ordering problem is not fixed. Every `ERROR: deadlock detected` in your logs is the database telling you that your application has a concurrency bug in its lock acquisition logic. The correct response is to fix the ordering, not to add more retries.

Deadlocks are always application logic bugs. The database detects and breaks them, but you must prevent the circular dependency.
