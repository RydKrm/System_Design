# Case Study 03 — The Lost Update Under Concurrency

---

## The Setup — The Bug That Hides in Plain Sight

Of all the concurrency bugs in database systems, the lost update is the most subtle, the most widespread, and the most dangerous precisely because it leaves no error, no exception, and no stack trace behind. The application code looks correct. The database accepts the writes without complaint. The queries execute successfully. And yet, silently, data disappears — balances are wrong, counts do not add up, inventory numbers are impossible. The bug manifests as a data inconsistency problem discovered long after the fact, often by users who notice their account balance is less than it should be, or by operations teams running reconciliation reports that simply do not balance.

Let us trace exactly how this happens with the simplest possible example. An application manages user account balances. Two separate API requests arrive almost simultaneously: both are for the same user, and both intend to add $50 to their balance. The user's current balance is $100. The expected result after both operations complete is $200. The actual result, under certain concurrency conditions, is $150. One of the two additions simply vanishes — it is lost, silently, without any error.

Here is the application code that causes this:

```go
// This function looks completely correct when read in isolation.
// It is not. It is a lost update waiting to happen.
func AddToBalance(db *sql.DB, userID int64, amount float64) error {
    // Step 1: Read the current balance from the database.
    var currentBalance float64
    err := db.QueryRow(
        "SELECT balance FROM accounts WHERE user_id = $1",
        userID,
    ).Scan(&currentBalance)
    if err != nil {
        return fmt.Errorf("reading balance: %w", err)
    }

    // Step 2: Compute the new balance in application memory.
    newBalance := currentBalance + amount  // 100 + 50 = 150

    // Step 3: Write the new balance back to the database.
    _, err = db.Exec(
        "UPDATE accounts SET balance = $1 WHERE user_id = $2",
        newBalance, userID,
    )
    return err
    // No error. No problem visible. But one update is about to be lost.
}
```

Read this code carefully. It reads the balance, adds the amount, and writes the result back. Each individual step is correct. The logic is sound. The intention is clear. And yet this code is fundamentally broken for any system where more than one request can execute this function for the same user at the same time — which is every production system ever built.

## The Exact Moment the Data Disappears — A Frame-by-Frame Analysis

The lost update does not happen because of a bug in any single execution of `AddToBalance`. It happens because of the timing relationship between two concurrent executions. To understand it fully, you need to watch both transactions simultaneously, step by step, with millisecond precision:

```
The Lost Update — Frame by Frame:
======================================================================

  Database state at start:
  +----------+----------+
  | user_id  | balance  |
  +----------+----------+
  |    42    |  100.00  |
  +----------+----------+

  Timeline (time flows downward):

  Request A (add $50)              Request B (add $50)
  ----------------                 ----------------

  t=0ms:  A reads balance
          SELECT balance ...
          -> gets 100.00
                                   t=1ms:  B reads balance
                                           SELECT balance ...
                                           -> gets 100.00

  t=2ms:  A computes: 100 + 50 = 150

                                   t=3ms:  B computes: 100 + 50 = 150

  t=4ms:  A writes: balance = 150
          UPDATE accounts SET
          balance = 150 WHERE
          user_id = 42
          -> Success. 1 row updated.

                                   t=5ms:  B writes: balance = 150
                                           UPDATE accounts SET
                                           balance = 150 WHERE
                                           user_id = 42
                                           -> Success. 1 row updated.

  Final database state:
  +----------+----------+
  | user_id  | balance  |
  +----------+----------+
  |    42    |  150.00  |  <- Should be 200.00. $50 is gone. No error. No trace.
  +----------+----------+

  What happened:
  - A read 100, computed 150, wrote 150. Correct for A alone.
  - B read 100 (BEFORE A wrote 150), computed 150, wrote 150.
  - B's write OVERWROTE A's write with the same stale value.
  - The $50 that A added effectively disappears when B writes.
  - Neither A nor B received an error. Both believe they succeeded.
======================================================================
```

The key moment is at `t=1ms`: Request B reads the balance while Request A has not yet written its result. B reads the same stale value of `100.00` that A read. Both transactions independently compute `150.00` as the new balance. Whichever writes second wins — and its win erases the other's work entirely. This is the **lost update anomaly**, formally recognized in database theory as one of the classic concurrency problems that proper isolation levels are designed to prevent.

## Why This Bug Is So Hard to Find in Testing

The lost update is notoriously difficult to reproduce in testing environments, and this is not an accident — it is a direct consequence of the precise timing conditions required. For the bug to manifest, two concurrent transactions must execute their READ operations at nearly the same instant, before either has completed their WRITE. At low concurrency — one user, or even ten users using your application — the probability of this overlap is very low. Each request typically completes in a few milliseconds, and the chance that two requests for the same user arrive within that window is small.

Consider the mathematics of this. If `AddToBalance` completes in 5ms and your application serves 10 requests per second for a particular user, the requests arrive on average every 100ms. The window of vulnerability — the period between the READ and the WRITE — is roughly 3ms out of every 100ms. The probability that another request falls into that 3ms window is approximately 3%. So in testing with moderate load, you will see the bug roughly 3 times per 100 executions. But in testing, you are typically using test accounts that do not have real concurrent load — you run one test at a time, see correct results, and conclude the code is correct.

```
Probability of Lost Update vs. Concurrency:
======================================================================

  Probability
  of lost update
  per operation
      ^
 100% |                                            *  *  *
  90% |                                        *
  80% |                                    *
  60% |                               *
  40% |                          *
  20% |                    *
  10% |               *
   5% |          *
   1% |     *
 0.1% | *
      +---+----+----+----+----+----+----+----+----+--> Concurrent
       1   2    5   10   50  100  500 1000 5000 10000  writers on
                                                        same row

  Formula (approximate):
  P(lost update) ≈ 1 - (1 - window/interval)^(concurrent_writers - 1)
  Where:
    window   = time between READ and WRITE (~3ms)
    interval = average time between requests for same row

  At 1 concurrent writer:    P = 0%     (no one to conflict with)
  At 10 concurrent writers:  P ~= 3%    (rare, easy to miss in testing)

  Testing uses 1 concurrent writer -> 0% probability -> bug invisible.
  Production uses 1000 concurrent writers -> 95% -> constant data corruption.
======================================================================
```

This probability curve explains the pattern engineers repeatedly encounter: a feature works perfectly in development, passes all tests, deploys successfully, and then silently corrupts data in production as traffic grows. The bug was always there — it was simply waiting for sufficient concurrency to become visible.

## The Isolation Level Connection — Why Read Committed Is Not Enough

PostgreSQL, like most relational databases, defaults to the **Read Committed** isolation level. At this level, each statement within a transaction sees the most recently committed data at the time that statement executes. This is a reasonable default for most operations, but it does not protect against the lost update. Here is why.

Isolation levels define what each transaction can *see* about other transactions' uncommitted work. Read Committed ensures Transaction B does not see Transaction A's *uncommitted* write — but it says nothing about Transaction B seeing Transaction A's *committed* write when B already read the data before A committed. The lost update occurs precisely in this gap: B reads before A commits, B computes with the stale data, B writes after A commits, and B's write — based on stale data — overwrites A's correct write.

To understand this properly, you need to understand what each isolation level actually guarantees:

```
Isolation Level Comparison — What Each Level Prevents:
======================================================================

  Anomaly              | Read Committed | Repeatable Read | Serializable
  ---------------------|----------------|-----------------|-------------
  Dirty Read           |   Prevented    |   Prevented     |  Prevented
  (read uncommitted    |                |                 |
   data from another   |                |                 |
   transaction)        |                |                 |
  ---------------------|----------------|-----------------|-------------
  Non-Repeatable Read  |  NOT Prevented |   Prevented     |  Prevented
  (read same row       |                |                 |
   twice, get          |  [DEFAULT PG]  |                 |
   different values)   |                |                 |
  ---------------------|----------------|-----------------|-------------
  Lost Update          |  NOT Prevented |   Prevented*    |  Prevented
  (read-compute-write  |                |  (*in PG, with  |
   race condition)     |  VULNERABLE    |   FOR UPDATE)   |  SAFE
  ---------------------|----------------|-----------------|-------------
  Phantom Read         |  NOT Prevented |  NOT Prevented  |  Prevented
  (query returns       |                |  (in PG, reads  |
   different rows      |                |   snapshot)     |
   on repeat)          |                |                 |

  PostgreSQL Default: READ COMMITTED -> Lost updates ARE possible.
======================================================================
```

The safest isolation level for protecting against lost updates is **Serializable**, which guarantees that concurrent transactions produce results equivalent to some sequential execution. If the same result cannot be achieved sequentially, PostgreSQL will detect the conflict and abort one of the transactions with a serialization failure. However, Serializable isolation comes with performance overhead and requires your application to be prepared to retry aborted transactions. For most applications, the targeted locking approaches described in the solutions section are more practical.

## Four Solutions — From Simplest to Most Comprehensive

### Solution One — The Atomic Increment: The Right Tool, Always

The simplest, most reliable, and most performant solution to the lost update is to perform the computation entirely inside the database using a **single atomic SQL statement** rather than a read-compute-write cycle in the application. Instead of reading the balance, adding to it in Go, and writing it back, you express the entire computation as a single `UPDATE` statement:

```go
// WRONG: Read-Compute-Write pattern (vulnerable to lost updates)
balance, _ := readBalance(db, userID)
newBalance := balance + amount
writeBalance(db, userID, newBalance)

// RIGHT: Atomic increment — the computation happens inside the DB
_, err := db.ExecContext(ctx, `
    UPDATE accounts
    SET balance = balance + $1
    WHERE user_id = $2
`, amount, userID)
```

The difference is profound. `UPDATE accounts SET balance = balance + $1` is a single, atomic operation in PostgreSQL. When this statement executes, PostgreSQL reads the current value of `balance`, adds `$1` to it, and writes the result back — all within a single, indivisible operation protected by the row-level lock that the `UPDATE` statement implicitly holds. There is no gap between reading and writing during which another transaction can slip in and overwrite the value. Two concurrent executions of this statement will serialize correctly: the second one to acquire the row lock will read the value written by the first, producing the mathematically correct result.

```
Atomic Increment — How It Executes Safely Under Concurrency:
======================================================================

  Same scenario: 2 requests, both adding $50, initial balance = $100

  Request A (UPDATE balance = balance + 50)
  Request B (UPDATE balance = balance + 50)

  t=0ms:  A sends UPDATE to PostgreSQL.
          PostgreSQL acquires exclusive row lock on user_id=42.

  t=1ms:  B sends UPDATE to PostgreSQL.
          PostgreSQL: row locked by A. B WAITS.

  t=2ms:  PostgreSQL executes A's update atomically:
          Reads balance: 100
          Computes: 100 + 50 = 150
          Writes: balance = 150
          Releases lock.

  t=3ms:  B's wait ends. Lock acquired. Executes atomically:
          Reads balance: 150  <- sees A's committed result
          Computes: 150 + 50 = 200
          Writes: balance = 200
          Releases lock.

  Final state: balance = 200.00  CORRECT!
  No lost update. No errors. No data corruption.

  The key: reading and writing happen inside ONE SQL statement,
  under ONE row lock. There is no window between read and write
  for another transaction to interfere.
======================================================================
```

This pattern — expressing the entire computation as a SQL expression rather than reading into the application, computing, and writing back — applies to a vast range of common operations. Every counter increment, every balance adjustment, every seat reservation, every inventory decrement should use this form whenever possible.

```go
// Examples of atomic SQL expressions (CORRECT):
// Increment a counter:
db.Exec("UPDATE posts SET like_count = like_count + 1 WHERE post_id = $1", postID)

// Decrement inventory:
db.Exec("UPDATE inventory SET quantity = quantity - $1 WHERE item_id = $2 AND quantity >= $1", qty, itemID)

// Conditional update (only if sufficient balance):
result, _ := db.Exec(`
    UPDATE accounts
    SET balance = balance - $1
    WHERE user_id = $2
      AND balance >= $1
`, amount, userID)
rows, _ := result.RowsAffected()
if rows == 0 {
    return ErrInsufficientFunds  // Either user not found or insufficient funds
}
```

### Solution Two — `SELECT FOR UPDATE`: Lock Before Reading

When the computation is more complex than a simple increment — for example, when you need to read the current balance, apply business logic that Go code must participate in, then write the result — the atomic SQL expression is not sufficient. In these cases, you must explicitly lock the row before reading it, preventing any other transaction from modifying it during your computation.

`SELECT FOR UPDATE` acquires an exclusive row lock at the moment of the `SELECT`, the same lock that would normally only be acquired at the `UPDATE`. By locking the row when you read it, you ensure that no other transaction can read or write that row until your transaction completes:

```go
// WRONG: Read-Compute-Write without lock (race condition)
func ProcessWithdrawal(db *sql.DB, userID int64, amount float64) error {
    var balance float64
    db.QueryRow("SELECT balance FROM accounts WHERE user_id = $1", userID).Scan(&balance)
    // <-- Any other transaction can modify balance here. RACE CONDITION.
    if balance < amount {
        return ErrInsufficientFunds
    }
    db.Exec("UPDATE accounts SET balance = $1 WHERE user_id = $2", balance-amount, userID)
    return nil
}

// CORRECT: SELECT FOR UPDATE locks the row before reading (no race condition)
func ProcessWithdrawal(db *sql.DB, userID int64, amount float64) error {
    tx, err := db.Begin()
    if err != nil { return err }
    defer tx.Rollback()

    // SELECT FOR UPDATE: acquires exclusive row lock IMMEDIATELY.
    // Any concurrent transaction that tries to UPDATE or SELECT FOR UPDATE
    // the same row will WAIT until this transaction commits or rolls back.
    var balance float64
    err = tx.QueryRow(`
        SELECT balance
        FROM accounts
        WHERE user_id = $1
        FOR UPDATE          -- <- This is the critical addition
    `, userID).Scan(&balance)
    if err != nil { return fmt.Errorf("reading balance: %w", err) }

    // This check is now SAFE. The row is locked. No one else can modify balance
    // between this check and the UPDATE below.
    if balance < amount {
        return ErrInsufficientFunds
    }

    // Apply complex business logic in Go (e.g., different fee structures,
    // loyalty point calculations, etc.) that cannot be expressed in pure SQL.
    newBalance := applyComplexBusinessLogic(balance, amount)

    // Write back the computed result. Safe because we hold the lock.
    _, err = tx.Exec(`
        UPDATE accounts
        SET balance = $1, last_updated = NOW()
        WHERE user_id = $2
    `, newBalance, userID)
    if err != nil { return fmt.Errorf("updating balance: %w", err) }

    return tx.Commit()
    // Commit releases the row lock. Any waiting transactions now proceed.
}
```

`SELECT FOR UPDATE` is the correct choice when: the computation is too complex for atomic SQL, you need to enforce application-level business rules before writing, or you need to read from one row and write to multiple related rows based on the read result.

### Solution Three — Optimistic Locking with Version Column

`SELECT FOR UPDATE` is a **pessimistic** approach — it assumes conflicts will happen and prevents them by holding a lock. For systems where conflicts are rare but the operation must be protected, **optimistic locking** takes the opposite philosophy: it assumes conflicts are uncommon, allows transactions to proceed without locks, and detects conflicts at write time using a version number.

The version column pattern was introduced in Case Study 01 for the hot row bottleneck, but it applies equally well to lost updates:

```go
// Optimistic locking for balance update:
func AddToBalanceOptimistic(db *sql.DB, userID int64, amount float64) error {
    maxRetries := 3

    for attempt := 0; attempt < maxRetries; attempt++ {
        // Step 1: Read current state including version
        var balance float64
        var version int64
        err := db.QueryRow(`
            SELECT balance, version
            FROM accounts
            WHERE user_id = $1
        `, userID).Scan(&balance, &version)
        if err != nil { return fmt.Errorf("reading balance: %w", err) }

        // Step 2: Compute new value in application (e.g., complex business logic)
        newBalance := applyBusinessLogic(balance, amount)

        // Step 3: Write ONLY if version hasn't changed (conditional update)
        result, err := db.Exec(`
            UPDATE accounts
            SET balance = $1,
                version = version + 1,    -- Increment version on every write
                last_updated = NOW()
            WHERE user_id = $2
              AND version = $3             -- Only write if nobody else changed it
        `, newBalance, userID, version)
        if err != nil { return fmt.Errorf("updating balance: %w", err) }

        rowsAffected, _ := result.RowsAffected()
        if rowsAffected == 1 {
            return nil  // Success: our version was still current
        }

        // 0 rows affected means version changed — someone else updated concurrently.
        // Retry: re-read the new version and try again.
        if attempt < maxRetries-1 {
            time.Sleep(time.Duration(attempt+1) * 10 * time.Millisecond)
        }
    }

    return ErrConcurrentModification
}
```

Optimistic locking is elegant for low-to-medium contention scenarios. Its weakness under high contention is the same as discussed in the deadlock case study: many concurrent attempts all fail and retry simultaneously, creating a retry storm that can be as harmful as the original problem. For high-contention rows, either atomic SQL expressions or `SELECT FOR UPDATE` (pessimistic locking) are more appropriate.

### Solution Four — Serializable Isolation: Let PostgreSQL Handle It

The most comprehensive solution, and the one that requires the least custom logic in application code, is to raise the transaction isolation level to **Serializable**. At this level, PostgreSQL guarantees that the execution of concurrent transactions is equivalent to some sequential ordering of those transactions. If any concurrent transaction would produce a result that cannot be achieved sequentially, PostgreSQL automatically detects the conflict and aborts one of the transactions with a **serialization failure** (`SQLSTATE 40001`).

```go
// Using Serializable isolation — PostgreSQL handles the conflict detection
func AddToBalanceSerializable(db *sql.DB, userID int64, amount float64) error {
    maxRetries := 3

    for attempt := 0; attempt < maxRetries; attempt++ {
        // Begin transaction with SERIALIZABLE isolation
        tx, err := db.BeginTx(context.Background(), &sql.TxOptions{
            Isolation: sql.LevelSerializable,
        })
        if err != nil { return err }

        // Now this read-compute-write pattern IS safe at Serializable level.
        // PostgreSQL tracks all reads and writes and will detect if the result
        // would be inconsistent with a sequential execution.
        var balance float64
        err = tx.QueryRow("SELECT balance FROM accounts WHERE user_id = $1", userID).Scan(&balance)
        if err != nil {
            tx.Rollback()
            return err
        }

        newBalance := balance + amount  // Read-compute-write is safe here

        _, err = tx.Exec("UPDATE accounts SET balance = $1 WHERE user_id = $2", newBalance, userID)
        if err != nil {
            tx.Rollback()
            return err
        }

        err = tx.Commit()
        if err != nil {
            tx.Rollback()
            if isSerializationFailure(err) {
                // PostgreSQL detected a conflict. Retry the entire transaction.
                time.Sleep(time.Duration(attempt+1) * 10 * time.Millisecond)
                continue
            }
            return err
        }
        return nil // Success
    }
    return ErrMaxRetriesExceeded
}

// isSerializationFailure checks for PostgreSQL SQLSTATE 40001
func isSerializationFailure(err error) bool {
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) {
        return pgErr.Code == "40001"  // serialization_failure
    }
    return strings.Contains(err.Error(), "could not serialize")
}
```

Serializable isolation is the most correct and the most safe option, but it comes with a real performance cost: additional bookkeeping, more frequent transaction aborts under high concurrency, and the requirement that every transaction in your application is prepared to retry on serialization failure. For most applications, a targeted combination of atomic SQL expressions and `SELECT FOR UPDATE` achieves the necessary safety with better performance than global Serializable isolation.

## Real-World Examples — Where Lost Updates Silently Corrupt Data

Understanding the abstract mechanism is valuable, but recognizing the pattern in the specific forms it takes in production code is what allows you to prevent it before it ships. The read-compute-write anti-pattern appears constantly, in slightly different disguises, across virtually every application that handles shared mutable state.

**Like Counts and Vote Tallies.** Social platforms and content voting systems frequently implement like counts as application-level increments: read the current count, add one, write the new count. Under high concurrency (a viral post receiving hundreds of likes per second), the vast majority of these increments are lost. The correct implementation is `UPDATE posts SET like_count = like_count + 1 WHERE post_id = $1`, which is atomic and correct regardless of concurrency.

**Inventory Reservation.** An e-commerce system reads the available quantity, subtracts the ordered quantity in application code, and writes the new quantity. Two concurrent orders for the last item in stock will both read `quantity = 1`, both subtract 1, and both write `quantity = 0` — and both orders will be confirmed even though only one item exists. The atomic form is `UPDATE inventory SET quantity = quantity - $1 WHERE item_id = $2 AND quantity >= $1` which returns 0 rows affected if the item is out of stock.

**Session/Access Token Rotation.** Security-sensitive code that reads a token, generates a new one, and writes the new token back can — under certain timing conditions — allow a rotated token to be silently overwritten by a concurrent rotation, leaving the user's session in an inconsistent state.

**Aggregate Recalculation.** Code that reads a set of child records, computes a sum or average in application code, and writes the result to a parent record is vulnerable if child records can be modified concurrently. The result stored in the parent can be stale or incorrect as soon as it is written.

```go
// Pattern Recognition: Identifying the lost update in your codebase
// Any code that follows this shape is potentially vulnerable:

// DANGEROUS SHAPE:
// 1. Read: SELECT value FROM table WHERE id = X
var value SomeType
db.QueryRow("SELECT value FROM table WHERE id = $1", id).Scan(&value)

// 2. Compute: modify value in application code
newValue := transform(value)  // Any computation

// 3. Write: UPDATE table SET value = newValue WHERE id = X
db.Exec("UPDATE table SET value = $1 WHERE id = $2", newValue, id)

// IF any other goroutine/request can execute steps 1-3 for the SAME id
// concurrently, you have a potential lost update.

// HOW TO FIX (choose the appropriate solution):
// Option A - If computation can be expressed in SQL (preferred):
db.Exec("UPDATE table SET value = value + delta WHERE id = $1", id)

// Option B - If complex Go logic needed:
tx, _ := db.Begin()
tx.QueryRow("SELECT value FROM table WHERE id = $1 FOR UPDATE", id).Scan(&value)
newValue = complexGoLogic(value)
tx.Exec("UPDATE table SET value = $1 WHERE id = $2", newValue, id)
tx.Commit()
```

## Diagnosing Lost Updates — The Detective Work

Lost updates are uniquely difficult to diagnose because they leave no error trail. The only evidence is the wrong data itself, often discovered long after the fact. The diagnostic approach requires looking at the data's historical patterns and the code's structure, not at error logs.

```sql
-- Step 1: Detect data anomalies that suggest lost updates
-- For account balances: check if the sum of all transactions matches the current balance
SELECT
    a.user_id,
    a.balance                              AS current_balance,
    COALESCE(SUM(t.amount), 0)             AS sum_of_transactions,
    a.balance - COALESCE(SUM(t.amount), 0) AS discrepancy
FROM accounts a
LEFT JOIN transactions t ON t.user_id = a.user_id
GROUP BY a.user_id, a.balance
HAVING ABS(a.balance - COALESCE(SUM(t.amount), 0)) > 0.01
ORDER BY ABS(a.balance - COALESCE(SUM(t.amount), 0)) DESC;

-- A non-empty result here is definitive evidence of lost updates.
-- The 'discrepancy' column shows how much data was lost.

-- Step 2: Check for high-contention rows that are likely candidates
-- Look for rows that are updated very frequently (the hot targets)
SELECT
    relname   AS table_name,
    n_tup_upd AS total_updates,
    n_live_tup AS live_rows,
    round(n_tup_upd::numeric / NULLIF(n_live_tup, 0), 1) AS updates_per_row
FROM pg_stat_user_tables
ORDER BY updates_per_row DESC
LIMIT 10;
-- Tables with extremely high updates_per_row are candidates for lost update bugs.

-- Step 3: Enable detailed logging to catch suspicious patterns
-- Turn on statement logging for a period during high-traffic:
ALTER SYSTEM SET log_min_duration_statement = '0ms';  -- Log ALL statements
SELECT pg_reload_conf();
-- Then grep logs for SELECT followed immediately by UPDATE on same table/ID.
-- This is the read-compute-write fingerprint in the logs.
-- Remember to turn this off after diagnosis (very high log volume):
ALTER SYSTEM SET log_min_duration_statement = '1000ms';
SELECT pg_reload_conf();
```

## Key Takeaways — The Principles to Carry Forward

The lost update anomaly reveals a truth about concurrent programming that is counterintuitive to engineers accustomed to single-threaded thinking: **correct code, executed correctly, by correct applications, can still produce incorrect results when multiple instances of that code run concurrently on shared data**. Each individual execution of `AddToBalance` is correct in isolation. It reads the right data, computes the right result, and writes it back successfully. The incorrectness emerges only from the interaction between two correct executions — from the gap between reading and writing that exists in every read-compute-write pattern.

The solution hierarchy is straightforward once the problem is understood. Express computations atomically in SQL wherever possible — `balance + $1` is the database's version of an atomic increment, and it is safe under any concurrency. When application logic must participate in the computation, hold a row lock for the duration of that logic using `SELECT FOR UPDATE`. When you need the flexibility of optimistic concurrency and can tolerate retries, use a version column. When you need the strongest guarantee and are willing to pay the performance cost, use Serializable isolation.

The practical lesson for everyday development is this: any time you write `SELECT` followed by a computation followed by an `UPDATE` on the same row, within a code path that could be executed concurrently, stop and ask: "Is this computation expressible as a single SQL expression?" If yes — and it very often is — rewrite it that way. If not, add `FOR UPDATE` to the `SELECT` and wrap the whole thing in a transaction. This habit, applied consistently, eliminates the lost update from your codebase before it has a chance to silently corrupt your data.

Read-modify-write is never safe under concurrency without locking or atomic operations. Never read a value, compute a new value in application memory, then write it back without holding the lock the entire time.
