# The Invoice That Came After Itself: How Storing Numbers as Numbers Fixed Sort Order and Made Indexes Usable

> _"A database column's data type is not merely a formatting choice — it is a statement about the meaning of the data and how it will be compared, sorted, and indexed. When you store a number as a string, the database treats it as a string. Strings sort alphabetically. Numbers sort numerically. These are not the same thing, and the difference will surprise you at the worst possible moment."_

---

## Setting the Scene

You are a backend developer at a professional services company that invoices clients monthly. The invoicing system has been running for four years. Invoices are numbered sequentially with a human-readable prefix: `INV-000001`, `INV-000002`, and so on up to the current count of about seventy-five thousand invoices. The prefix makes invoices easy to identify in emails, in phone conversations, and on printed documents — "I am calling about invoice INV-003421" is clear and unambiguous.

The `invoices` table has an `invoice_number` column of type `VARCHAR(20)`, and this column contains values like `INV-000001` through `INV-075000`. The column has an index on it, since invoice number lookups are common — clients call in asking about specific invoices by number.

One afternoon, a senior accountant files a bug report. She has been using the invoice listing screen, which shows invoices sorted by invoice number, to review this month's invoices in order. She has noticed something disturbing: the list is not in the correct order. Invoice `INV-10000` appears before `INV-9999`. Invoice `INV-20000` appears before `INV-9999`. The entire list is sorted in what she describes as "completely random and useless" order.

You pull up the query driving the invoice list screen:

```sql
SELECT invoice_number, client_name, amount, issued_date
FROM invoices
ORDER BY invoice_number
LIMIT 50 OFFSET 0;
```

You run it yourself and see immediately what she means. The ordering is: `INV-00001`, `INV-000010`, `INV-000100`, `INV-001000`, `INV-010000`, `INV-10000`, `INV-100000`... The numbers are sorted as if they were words in a dictionary, not as the sequential invoice numbers they represent.

Your senior engineer takes one look and says: _"The database is doing exactly what you told it to. You told it these are strings. It is sorting them as strings. If you want them sorted as numbers, you need to store them as numbers."_

---

## Understanding Lexicographic vs Numeric Sort Order

The root of the problem is the difference between how strings and numbers are compared and sorted — two fundamentally different operations that produce dramatically different results when applied to the same data.

**Numeric sort order** is what humans expect when sorting numbers: 1, 2, 3, ..., 9, 10, 11, ..., 99, 100, 101, ..., 999, 1000. The comparison is based on the mathematical value of the number. Nine is less than ten because the value 9 is less than the value 10.

**Lexicographic sort order** — also called dictionary order or string sort order — compares strings character by character from left to right. The first character of one string is compared to the first character of the other. If they are equal, the second character is compared, and so on. The comparison is based on the character code values (or the locale's collation order), not on any numeric interpretation.

When you sort the strings `"INV-9"` and `"INV-10"` lexicographically, the comparison proceeds as: `I` vs `I` (equal), `N` vs `N` (equal), `V` vs `V` (equal), `-` vs `-` (equal), `9` vs `1` (differs). The character `'1'` has a lower code point than the character `'9'` in ASCII and Unicode. Therefore, `"INV-10"` is considered **less than** `"INV-9"` in lexicographic order. The string "10" comes before the string "9" in the dictionary — just as "a10" would come before "a9" alphabetically.

```
LEXICOGRAPHIC vs NUMERIC SORT — The same sequence, two orderings

  Invoice numbers, as strings, in lexicographic order:
  ┌─────────────────────────────────────────────────────────────┐
  │  INV-000001  ← '0' comes before '1' comes before '9'       │
  │  INV-000002                                                 │
  │  ...                                                        │
  │  INV-000009                                                 │

  │  ...                                                        │
  │  INV-1       ← 1 digit: 'INV-1...' < 'INV-2...' < 'INV-9'  │
  │  INV-10      ← 'INV-10' < 'INV-2' because '1' < '2' in ASCII│
  │  INV-100                                                    │
  │  INV-1000                                                   │
  │  INV-10000                                                  │

  │  ...                                                        │
  └─────────────────────────────────────────────────────────────┘
  Correct numeric sequence: completely violated.

  Invoice numbers, as integers (the sequence column), in numeric order:
  ┌─────────────────────────────────────────────────────────────┐
  │  1  → displayed as INV-000001                               │

  │  ...                                                        │
  └─────────────────────────────────────────────────────────────┘
  Perfect sequence. Exactly what the accountant expects.
```

This is not a PostgreSQL bug. It is not a database limitation. It is the correct and expected behaviour of lexicographic string comparison — the same comparison used in every programming language, every file system directory listing, and every alphabetical index since the invention of the dictionary. The database did exactly what it was told. The problem is that it was told the wrong thing.

## The Workaround That Cannot Use an Index

Faced with this problem, the previous developer implemented a workaround: strip the prefix with `REPLACE()` and cast the result to an integer for sorting purposes:

```sql
SELECT invoice_number, client_name, amount, issued_date
FROM invoices
ORDER BY CAST(REPLACE(invoice_number, 'INV-', '') AS INTEGER)
LIMIT 50 OFFSET 0;
```

This produces the correct sort order. `REPLACE(invoice_number, 'INV-', '')` strips the prefix, leaving `'000001'`, `'000002'`, etc., and `CAST(... AS INTEGER)` converts those to the integers 1, 2, 3, making numeric comparison possible. The accounting team sees invoices in the right order.

But this workaround has a critical performance flaw: **functions applied to column values in `ORDER BY` prevent index usage**.

The index on `invoice_number` stores the raw string values `'INV-000001'`, `'INV-000002'`, etc., in lexicographic order. The sort expression `CAST(REPLACE(invoice_number, 'INV-', '') AS INTEGER)` is a transformation of the column value — not the column value itself. PostgreSQL cannot use the index on `invoice_number` to satisfy an order by `CAST(REPLACE(...))`, because the index does not know what `CAST(REPLACE(...))` would produce for each value. It would need to compute the expression for every row and then sort the results — which is exactly what a sequential scan with an explicit sort does.

```
WHY THE WORKAROUND CANNOT USE THE INDEX

  The index on invoice_number:
  ┌──────────────────────────────────────────────────────────────┐
  │  Index entries (in lexicographic order):                     │
  │  'INV-000001' → page 1, row 3                               │
  │  'INV-000002' → page 1, row 7                               │
  │  'INV-000010' → page 1, row 12  ← wrong numeric position    │
  │  'INV-000100' → page 2, row 4   ← wrong numeric position    │
  │  ...                                                         │
  └──────────────────────────────────────────────────────────────┘

  Query: ORDER BY CAST(REPLACE(invoice_number, 'INV-', '') AS INTEGER)

  The database asks: "Can I use the index to produce rows in
  CAST(REPLACE(invoice_number, 'INV-', '') AS INTEGER) order?"

  Answer: No.
  - The index is in lexicographic order by invoice_number.
  - The sort key is a computed expression.
  - The index has no knowledge of what CAST(REPLACE(...)) produces.
  - To sort by this expression, every row must be read and evaluated.

  Execution plan:
  ┌──────────────────────────────────────────────────────────────┐
  │  Seq Scan on invoices                                        │
  │  → Read ALL 75,000 rows (full table scan)                    │
  │  → Compute CAST(REPLACE(invoice_number,'INV-','') AS INT)    │
  │    for EACH row (75,000 string operations)                   │
  │  → Sort all 75,000 computed values                           │
  │  → Return LIMIT 50                                           │
  └──────────────────────────────────────────────────────────────┘
  The index is not consulted at all.
  All 75,000 rows are read and processed for every page load.
```

At seventy-five thousand invoices, this full-table-scan-with-sort takes about a hundred to two hundred milliseconds — noticeable but not catastrophic. But as the invoice count grows to five hundred thousand, one million, or five million, the runtime grows proportionally. A sort query that cannot use an index will always scale linearly with table size — O(N log N) for the sort — whereas an index-based sort is O(log N) for the first row retrieval and essentially free for subsequent rows if they are retrieved in index order.

## The Root Cause: Data Stored in the Wrong Type

The fundamental design error was storing a number — the sequential invoice identifier — as a string. The human-readable format `INV-000001` is a **display format**, not a data format. It is how the number should be presented to a human reading a document. It is not how the number should be stored in a database where it will be sorted, indexed, compared, and computed on.

This distinction — between data format and display format — is one of the most important concepts in database design. The data format is what the database stores and operates on. The display format is what the application presents to the user. These two things should almost never be the same when the data has semantic meaning beyond its literal textual representation.

Consider how other systems handle this. A database stores a date as an internal binary representation (seconds since epoch, or a Julian day count) and formats it as "September 13, 2025" or "13/09/25" or "2025-09-13" depending on locale and context. It does not store the string "September 13, 2025" and then try to sort it. A database stores a monetary amount as `NUMERIC(10,2)` and formats it as "$1,234.56" or "€1.234,56" depending on locale. It does not store the string "$1,234.56". The same principle applies to sequential identifiers with a prefix: store the integer, display the formatted string.

## The Solution: Separate the Number from the Label

The solution separates the invoice identifier into two conceptually distinct things: the **sequence** (the integer, used for storage, sorting, indexing, and computation) and the **label** (the human-readable formatted string, used only for display).

```sql
-- Migration: add the integer sequence column
ALTER TABLE invoices
ADD COLUMN invoice_sequence INTEGER;

-- Backfill from existing invoice_number values
UPDATE invoices
SET invoice_sequence = CAST(
    REPLACE(invoice_number, 'INV-', '') AS INTEGER
);

-- Make the sequence column NOT NULL and add a unique constraint
ALTER TABLE invoices
ALTER COLUMN invoice_sequence SET NOT NULL;

ALTER TABLE invoices
ADD CONSTRAINT invoices_sequence_unique UNIQUE (invoice_sequence);

-- Create an index for fast sorting and range lookups
CREATE INDEX idx_invoices_sequence ON invoices (invoice_sequence);

-- The invoice_number column can now be:
-- Option A: Keep as a stored string (for legacy compatibility, lookups)
-- Option B: Convert to a GENERATED ALWAYS computed column
ALTER TABLE invoices
DROP COLUMN invoice_number;

ALTER TABLE invoices
ADD COLUMN invoice_number TEXT
GENERATED ALWAYS AS (
    'INV-' || LPAD(invoice_sequence::TEXT, 6, '0')
) STORED;
```

The `GENERATED ALWAYS AS ... STORED` syntax creates a **generated column** — a column whose value is automatically computed by the database from an expression, stored physically on disk, and kept automatically in sync whenever the source column changes. The `invoice_number` column is now derived from `invoice_sequence` at all times, without any application code required. The application can still read `invoice_number` for display purposes, but it never writes to it — it only writes `invoice_sequence`.

```
THE SEPARATED SCHEMA

  invoices table — what is stored:
  ┌────────────────────────────────────────────────────────────────┐
  │ id │ invoice_sequence │ invoice_number (GENERATED) │ client  │ │
  │    │   (INTEGER)       │    (TEXT, computed)         │ ...    │ │
  ├────────────────────────────────────────────────────────────────┤
  │  1 │             1    │ 'INV-000001'                │ ACME   │ │
  │  2 │             2    │ 'INV-000002'                │ Globe  │ │
  │  3 │            10    │ 'INV-000010'                │ Atlas  │ │
  │  4 │             9    │ 'INV-000009'                │ Zenith │ │
  └────────────────────────────────────────────────────────────────┘

  Sorting by invoice_sequence (INTEGER, correct):
    1 → INV-000001
    2 → INV-000002
    9 → INV-000009  ← correct: 9 before 10
   10 → INV-000010  ← correct: 10 after 9

  Sorting by invoice_number (TEXT, wrong):
    'INV-000001'  ← lexicographic order begins
    'INV-000002'
    'INV-000009'
    'INV-00001'   ← 5-digit strings sort differently from 6-digit
    'INV-00002'
    ...

  All sorting, indexing, and range queries now use invoice_sequence.
  invoice_number is read-only display label, generated automatically.
```

## The New Query: Index-Powered Sorting

With `invoice_sequence` as an integer column with its own index, the invoice listing query becomes:

```sql
-- Sort and paginate by the integer sequence
SELECT invoice_number, client_name, amount, issued_date
FROM invoices
ORDER BY invoice_sequence
LIMIT 50 OFFSET 0;
```

This query can use the index on `invoice_sequence` directly. The index stores integers in ascending numeric order — 1, 2, 3, ..., 75000 — which is exactly the order the query requests. The database traverses the index to find the first 50 entries, fetches the corresponding heap rows, and returns them. No full table scan. No expression evaluation. No sort operation.

For pagination — fetching page 2, page 3, page 1500 — the `OFFSET` approach still degrades with depth (as covered in the cursor pagination case study), but the fundamental sort is now index-powered. Even better, cursor pagination using `invoice_sequence` is clean and unambiguous:

```sql
-- Cursor pagination using integer sequence (fast, no degradation)
SELECT invoice_number, client_name, amount, issued_date
FROM invoices
WHERE invoice_sequence > :last_seen_sequence
ORDER BY invoice_sequence
LIMIT 50;
```

## The Generated Column: Keeping display_number in Sync Automatically

The `GENERATED ALWAYS AS ... STORED` column deserves a closer look because it is an elegant solution to what would otherwise be a maintenance problem.

Without a generated column, keeping `invoice_number` in sync with `invoice_sequence` would require application code to compute the formatted string every time a new invoice is created — `'INV-' || LPAD(sequence::TEXT, 6, '0')` — and insert it alongside the sequence number. This is not particularly complex, but it is duplicated logic: the formatting rule exists in the application code, and any bug or change in the formatting rule must be coordinated between the application and the database.

With a generated column, the formatting rule is defined once, in the database schema. The database computes `invoice_number` automatically from `invoice_sequence` on every insert and update. There is no application code responsible for this computation. There is no possibility of the two columns drifting out of sync. The rule is enforced at the schema level, in one place, forever.

```sql
-- The generated column definition:
ADD COLUMN invoice_number TEXT
GENERATED ALWAYS AS (
    'INV-' || LPAD(invoice_sequence::TEXT, 6, '0')
) STORED;

-- What this means:
-- When invoice_sequence = 1:
--   invoice_number = 'INV-' || LPAD('1', 6, '0') = 'INV-000001'
-- When invoice_sequence = 75000:
--   invoice_number = 'INV-' || LPAD('75000', 6, '0') = 'INV-075000'

-- The application NEVER writes to invoice_number.
-- The application writes invoice_sequence.
-- The database handles invoice_number.

-- If you later need 7-digit invoice numbers:
ALTER TABLE invoices
ALTER COLUMN invoice_number
    SET GENERATED ALWAYS AS (
        'INV-' || LPAD(invoice_sequence::TEXT, 7, '0')
    ) STORED;
-- One schema change, everywhere consistent.
```

The `STORED` keyword means the generated value is physically stored in the row — it is not recomputed on every read. This means it can be indexed, included in covering indexes, and returned as efficiently as any regular column. It behaves like a regular column in every way except that its value is always derived from the expression and cannot be manually overridden.

## The Broader Pattern: Type Semantics and Semantic Types

The invoice number problem is a specific instance of a broader principle that senior database engineers call **semantic typing** — the practice of choosing column types that match the semantic meaning of the data, not merely its textual representation.

Numbers have a natural comparison order, support arithmetic, and can be indexed for range queries. Text has lexicographic comparison order, does not support arithmetic, and is indexed for prefix or full-text searches. When you store a number as text, you lose the ability to sort it correctly, to do arithmetic on it, to do range queries efficiently, and to use integer-optimised indexes. You gain nothing in return.

The same problem manifests in many common scenarios beyond invoice numbers:

A **phone number** stored as `VARCHAR` — `(212) 555-1234` — cannot be efficiently sorted numerically, cannot be range-queried, and requires stripping and casting for any computation. Stored as `BIGINT` and formatted at display time, it is sortable, comparable, and space-efficient.

A **version number** stored as `VARCHAR` — `'2.10.1'` — sorts `'2.9.0'` after `'2.10.1'` because `'9'` > `'1'` in the second segment. Stored as three integer columns (`major`, `minor`, `patch`), sorting is correct and composable.

A **percentage stored as `'75%'`** — with the percent sign — cannot be compared numerically. Stored as `NUMERIC(5,2)` and formatted as a percentage at display time, it is fully sortable and comparable.

A **currency amount stored as `'$1,234.56'`** — with currency symbol and thousands separator — cannot be compared, aggregated, or sorted correctly. Stored as `NUMERIC(15,2)` and formatted by the application, it supports all arithmetic operations.

```
THE SEMANTIC TYPE RULE — Store in the type that matches meaning

  ┌────────────────────────────────────────────────────────────────┐
  │  Data                │ Wrong type      │ Right type            │
  ├────────────────────────────────────────────────────────────────┤
  │  Invoice sequence    │ VARCHAR 'INV-1' │ INTEGER + generated   │
  │  Phone number        │ VARCHAR '(212)' │ BIGINT (strip symbols)│
  │  Version number      │ VARCHAR '2.10'  │ INTEGER major/minor   │
  │  Percentage          │ VARCHAR '75%'   │ NUMERIC(5,2)          │
  │  Currency amount     │ VARCHAR '$1,200'│ NUMERIC(15,2)         │
  │  Date from API       │ VARCHAR '2024'  │ DATE or TIMESTAMPTZ   │
  │  Boolean flag        │ VARCHAR 'Y'/'N' │ BOOLEAN               │
  │  IP address          │ VARCHAR '192..' │ INET                  │
  └────────────────────────────────────────────────────────────────┘

  Rule: If you will ever sort it, compare it, range-query it,
        or do arithmetic on it — store it as its semantic type.
        Format it as a human-readable string only at display time.
```

The guiding question is: "What operations will I perform on this data?" If the operations include sorting, comparing, range queries, or arithmetic, the type must be chosen to support those operations efficiently. The display format is a concern for the presentation layer, not the storage layer.

## The Migration Strategy for Existing Data

For a production system with existing data in the wrong type, migration follows a safe, staged approach:

```sql
-- Step 1: Add the new integer column (nullable initially for safety)
ALTER TABLE invoices ADD COLUMN invoice_sequence INTEGER;

-- Step 2: Backfill by extracting the integer from existing strings
UPDATE invoices
SET invoice_sequence = CAST(
    REGEXP_REPLACE(invoice_number, '[^0-9]', '', 'g')
    AS INTEGER
);
-- REGEXP_REPLACE removes all non-digit characters, leaving just the number

-- Step 3: Verify the backfill is correct
SELECT
    invoice_number,
    invoice_sequence,
    'INV-' || LPAD(invoice_sequence::TEXT, 6, '0') AS computed_display
FROM invoices
WHERE 'INV-' || LPAD(invoice_sequence::TEXT, 6, '0') != invoice_number
LIMIT 10;
-- If this returns zero rows, the backfill is perfect.

-- Step 4: Add constraints and index
ALTER TABLE invoices ALTER COLUMN invoice_sequence SET NOT NULL;
CREATE UNIQUE INDEX ON invoices (invoice_sequence);
-- (Build index CONCURRENTLY in production to avoid table lock)

-- Step 5: Update application code to write invoice_sequence on insert
-- (deploy application changes that use integer sequence)

-- Step 6: Convert invoice_number to a generated column (optional)
ALTER TABLE invoices DROP COLUMN invoice_number;
ALTER TABLE invoices ADD COLUMN invoice_number TEXT
    GENERATED ALWAYS AS ('INV-' || LPAD(invoice_sequence::TEXT, 6, '0')) STORED;

-- Or keep invoice_number as a regular column for legacy compatibility
-- and maintain both, now that application is writing sequence only.
```

The migration is safe to run on a live production system because each step is incremental and non-destructive. The old `invoice_number` column remains usable throughout. The new `invoice_sequence` column is added alongside it. The application is updated to use the integer column before the old string column is removed. At no point is the system in an inconsistent state.

## The Result: Correct Order and 10× Faster Sorting

The combination of storing the integer sequence and indexing it produced two distinct improvements: correctness and speed.

**Correctness** was restored immediately. Invoices now sort in the order 1, 2, 3, ..., 75000, which the accounting team sees as `INV-000001`, `INV-000002`, `INV-000003`, ..., `INV-075000`. The `INV-10` before `INV-9` problem was eliminated permanently. There is no workaround, no casting, no application-level re-sorting — the database produces the correct order natively.

**Speed** improved ten-fold for the current table size, with the improvement growing as the table grows, because the indexed integer sort is O(log N + K) where K is the number of rows returned, while the expression-based sort was O(N log N) where N is the full table size.

```

  After:  INV-9 sorts before INV-10 (numeric order)
```

## The Lesson That Stays With You

The invoice number problem is deceptively simple, yet it recurs constantly in software systems because the intuition behind it — "I'll just store the whole formatted string, it's easier" — is exactly backwards from what a database needs. The formatted string is for humans. The semantic value is for the database.

The core discipline to develop is to always ask, at the moment of designing a column: "What operations will be performed on this data?" If the answer includes sorting, comparing, range queries, or arithmetic, the data must be stored in a type that natively supports those operations. The human-readable format — the prefix, the separators, the padding, the currency symbol, the unit — is the concern of the presentation layer, derived from the stored value at the moment of display. It is never the stored value itself.

Stored types are permanent decisions. Changing a column's data type after a table has millions of rows requires a migration. The cost of a one-week migration is always higher than the cost of a one-minute type decision made correctly at design time. When you pause and ask "should this be an integer or a string?" before adding a column, you are doing the most valuable possible database engineering — prevention, not remediation.

---

## Summary

This case study follows an invoice system that stored invoice identifiers as `VARCHAR` values in the format `INV-000001`. Because the database treated these as strings, `ORDER BY invoice_number` used lexicographic sort order, placing `INV-10` before `INV-9` and producing a sequence that accountants found baffling and unusable. The workaround — `ORDER BY CAST(REPLACE(invoice_number, 'INV-', '') AS INTEGER)` — restored the correct sort order but prevented index usage, forcing a full table scan and in-memory sort on every page load.

The solution was to add an `invoice_sequence INTEGER` column containing only the numeric portion of the invoice identifier, indexed with a standard B-Tree index. The `invoice_number` display string was converted to a generated column computed automatically from `invoice_sequence` by the database engine, eliminating the need for application code to maintain the formatted string. Queries sorting by `invoice_sequence` used the index natively — with the `LIMIT` clause short-circuiting after exactly fifty rows — producing correct numeric sort order without any expression evaluation and with no full table scan. Sort query time improved ten-fold for the current table size, with the gap widening as the table grows.

The lesson is the type semantics principle: store data in the type that matches its semantic meaning, not its display format. Numbers should be stored as integers or numerics. Dates should be stored as date types. Booleans should be stored as booleans. The formatted, human-readable representation is derived at display time, not stored. When a column's data type matches its semantic type, the database can sort it correctly, index it efficiently, and query it accurately — without casting, without expression evaluation, and without the class of bugs that arise when a number is treated as a string.
