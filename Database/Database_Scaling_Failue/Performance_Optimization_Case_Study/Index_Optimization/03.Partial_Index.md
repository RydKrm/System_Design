# The Partial Index: When Indexing Less Means Querying Faster

> _"An index that knows what to ignore is more valuable than an index that tries to remember everything. The best data structure is the one that fits in your RAM."_

---

## Setting the Scene

You are building a task management application — something like Todoist or Asana. Users create tasks, work through them, mark them complete, and create new ones. Over the years, the product has grown enormously. The `tasks` table now holds **50 million rows**.

Here is the key business reality of any task management system: **people complete tasks.** That is the whole point. And once a task is completed, it is almost never queried again — it might show up in a historical export or an analytics report, but it is not something the application fetches on every page load. What the application constantly queries is the _pending_ tasks — the ones still needing attention.

Yet the database does not know this business reality unless you tell it. And the team had not told it. The result was a query that took **2 full seconds** every time a user loaded their task list — and this query ran on every single page load, for every single user.

This is the story of a 95% index size reduction that made a query run **200 times faster**, achieved not by adding more index coverage, but by being much more precise about what should be indexed in the first place.

---

## Understanding the Data Distribution

Before diving into the mechanics, the most important thing to understand is the shape of the data itself. The `tasks` table has 50 million rows, and they are distributed like this:

```
TASKS TABLE — Data Distribution
────────────────────────────────────────────────────────────────────

Total rows: 50,000,000

  ┌───────────────────────────────────────────────────────────────┐
  │                                                               │
  │   status = 'completed'  ████████████████████████████████████ │
  │                          49,000,000 rows  (98% of all data)  │
  │                                                               │
  │   status = 'pending'    █                                     │
  │                          1,000,000 rows   (2% of all data)   │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘

Query access pattern (what the app actually asks for):
  ┌───────────────────────────────────────────────────────────────┐
  │                                                               │
  │   Queries for 'pending' tasks  ██████████████████████████████ │
  │   (every page load, all users)  ~99% of all queries          │
  │                                                               │
  │   Queries for 'completed' tasks █                             │
  │   (analytics/export, rare)       ~1% of all queries          │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘

The mismatch: 98% of the INDEX serves 1% of the QUERIES.
              2%  of the INDEX serves 99% of the QUERIES.
```

This data distribution is the entire root cause. The existing index dutifully stores information about all 50 million rows — including 49 million completed tasks that the application almost never queries. Those 49 million entries take up space, slow down every index write, and push the truly important 1 million pending-task entries out of the database's RAM cache. We are paying a massive cost to maintain data that gives us almost no benefit.

## The Table Structure and the Problem Query

The `tasks` table looks something like this:

```sql
CREATE TABLE tasks (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    title       TEXT NOT NULL,
    description TEXT,
    status      VARCHAR(20) NOT NULL DEFAULT 'pending',
    priority    INTEGER DEFAULT 0,
    due_date    DATE,
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ
    -- ... more columns
);
```

The query that every user triggers on every page load is:

```sql
SELECT *
FROM tasks
WHERE user_id = 1
  AND status = 'pending';
```

This query is asking: _"Give me all the tasks that belong to user 1 and are still pending."_ For a typical user, this might return 20–50 rows. But to find those 20–50 rows in a table of 50 million, the database needs a way to navigate efficiently.

The team had already created what seemed like a reasonable index:

```sql
CREATE INDEX idx_tasks_user_status
ON tasks (user_id, status);
```

This is a perfectly valid composite index. It groups rows first by `user_id`, then within each user by `status`. The problem is not its structure — it is its **scope**.

## The Full Index: Eight Gigabytes of Mostly Useless Data

To understand why an 8GB index on a table with a good composite index still produces a 2-second query, you need to understand what that index physically contains and how memory interacts with performance.

The `idx_tasks_user_status` index on `(user_id, status)` contains an entry for every single row in the table — all 50 million of them. Each B-Tree leaf entry stores the `user_id` value, the `status` value, and a physical pointer to the heap row. At roughly 50–80 bytes per entry (accounting for B-Tree overhead, alignment, and PostgreSQL's page headers), 50 million entries occupy approximately 8 gigabytes on disk.

```
FULL INDEX — idx_tasks_user_status (user_id, status)
─────────────────────────────────────────────────────────────────────
Total entries: 50,000,000
Total size on disk: ~8 GB

Conceptual sorted structure (sorted by user_id, then status):

  user_id=1,  status='completed' → ptr  ┐
  user_id=1,  status='completed' → ptr  │  ~980 entries
  user_id=1,  status='completed' → ptr  │  (98% of user 1's tasks)
  ...                                   ┘  WILL NEVER BE QUERIED
  user_id=1,  status='pending'   → ptr  ┐
  user_id=1,  status='pending'   → ptr  │  ~20 entries
  user_id=1,  status='pending'   → ptr  │  (2% of user 1's tasks)
  ...                                   ┘  THIS IS WHAT WE WANT
  user_id=2,  status='completed' → ptr  ┐
  user_id=2,  status='completed' → ptr  │  ~1960 entries never queried
  ...                                   ┘
  user_id=2,  status='pending'   → ptr  ┐
  user_id=2,  status='pending'   → ptr  │  ~40 entries we actually want
  ...                                   ┘
  ...
  (continues for all 50 million rows across all users)
```

This index _does_ correctly serve the pending-tasks query. PostgreSQL can jump to `(user_id=1, status='pending')` in the B-Tree and find the relevant entries without a Sequential Scan. So why does it still take 2 seconds?

The answer lies not in the query plan's correctness, but in **where the index lives when the query runs**.

---

## The RAM Cache Problem: Why Size Matters More Than You Think

PostgreSQL does not read indexes directly from disk on every query — that would be impossibly slow. Instead, it maintains a pool of shared memory called the **Buffer Cache** (controlled by the `shared_buffers` configuration parameter, typically set to 1–4 GB on most production servers). Pages from both heap files and index files are loaded into this cache when they are first accessed and kept there as long as there is room. When a query needs a page, PostgreSQL checks the buffer cache first — a cache hit reads from RAM in microseconds, while a cache miss reads from disk in milliseconds.

For an index to be consistently fast, its working pages need to stay in the buffer cache between queries. But a cache has a fixed size. When the index is 8GB and the buffer cache is, say, 2GB, the entire index cannot possibly fit in memory at once.

```
THE BUFFER CACHE PROBLEM — 8GB Index vs 2GB Cache

PostgreSQL Buffer Cache (2GB capacity):
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  ████████████████████████████  Table heap pages      (1.2 GB)  │
│  ██████████████                Index pages in cache  (0.8 GB)  │
│                                                                 │
│  But the FULL index is 8GB. Only 10% fits in cache at once.    │
│                                                                 │
│  The 'pending' entries for user_id=1 might be in cache...      │
│  or might have been evicted to make room for other queries.    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

What happens when the buffer cache doesn't have the needed pages:

  Query arrives: "Give me pending tasks for user_id=1"
      │
      ▼
  PostgreSQL checks buffer cache for index page containing
  (user_id=1, status='pending') entries.
      │
      ├── Cache HIT  → read from RAM → microseconds
      │
      └── Cache MISS → go to disk    → milliseconds
                                        (random I/O)
                                        (possibly many pages)
                                        (multiplied across users)

With 8GB index and 2GB cache:
  Under load with many concurrent users, cache thrashing occurs.
  Index pages for user A get evicted when user B's query runs.
  Every query may hit multiple cache misses.
  Result: consistent 2,000ms query times under real-world load.
```

This is the subtle but devastating effect that an oversized index has. Even when the B-Tree traversal itself is efficient, cache misses turn each disk read from a microsecond operation into a millisecond one. Multiply that by thousands of daily active users, each loading their task list multiple times, and you have a system that feels perpetually slow.

## The Partial Index: Teaching the Database to Forget

The solution is a **Partial Index** — an index with a `WHERE` clause that restricts which rows are included.

```sql
-- Drop the old full index
DROP INDEX idx_tasks_user_status;

-- Create a partial index covering only pending tasks
CREATE INDEX idx_tasks_pending_user
ON tasks (user_id)
WHERE status = 'pending';
```

The `WHERE status = 'pending'` clause does something remarkable: it tells PostgreSQL to completely ignore every row where `status` is not `'pending'`. All 49 million completed tasks are simply excluded from the index entirely. They will never appear in its B-Tree. They take up no space. They require no maintenance.

Only the 1 million pending tasks are indexed — and within those, they are sorted by `user_id` so that finding all pending tasks for a specific user is an O(log n) B-Tree traversal.

```
PARTIAL INDEX — idx_tasks_pending_user (user_id) WHERE status='pending'
────────────────────────────────────────────────────────────────────────
Total entries: 1,000,000  (only the pending tasks)
Total size on disk: ~400 MB  (95% smaller than the 8GB full index)

Conceptual structure:

  ┌─ B-TREE ROOT ──────────────────────────────────────────────────┐
  │                                                                │
  │   Sorted by user_id (only pending rows exist here):           │
  │                                                               │
  │   user_id=1   → ptr (20 pending tasks for user 1)            │
  │   user_id=2   → ptr (40 pending tasks for user 2)            │
  │   user_id=3   → ptr (5  pending tasks for user 3)            │
  │   user_id=4   → ptr (0  — user 4 has no pending tasks)       │
  │   user_id=5   → ptr (12 pending tasks for user 5)            │
  │   ...                                                         │
  │   (continues for all users with pending tasks)                │
  │                                                               │
  │   NOT HERE:                                                   │
  │   ✗ user_id=1, completed tasks — completely absent            │
  │   ✗ user_id=2, completed tasks — completely absent            │
  │   ✗ 49 million completed tasks — as if they do not exist      │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘

Size: ~400MB — easily fits in a 2GB buffer cache with room to spare.
```

## How PostgreSQL Matches the Query to the Partial Index

You might wonder: how does PostgreSQL know to use this partial index for the pending-tasks query? The answer involves the query planner's logic for partial index matching.

When the query planner evaluates `SELECT * FROM tasks WHERE user_id = 1 AND status = 'pending'`, it looks at all available indexes on the `tasks` table. For each partial index, it checks whether the index's `WHERE` clause is implied by the query's `WHERE` clause. In other words, it asks: _"If I am already filtering for rows where `status = 'pending'`, does this index's condition `WHERE status = 'pending'` add any restriction that my query does not already enforce?"_

The answer is no — the query is already restricted to `status = 'pending'`, so any row the index contains is already a row that satisfies the query's status filter. The planner concludes that it is safe to use this index, because it knows the index only contains rows that match what the query is looking for.

```
QUERY PLANNER — Matching logic for partial index

Query WHERE clause:
  user_id = 1          (condition A)
  AND status = 'pending'  (condition B)

Partial Index condition:
  WHERE status = 'pending'  (index condition C)

Planner reasoning:
  "Does my query guarantee that every row I care about
   satisfies the index's WHERE clause?"

  Condition B says: status = 'pending'
  Condition C says: status = 'pending'
  B implies C → YES, the index is safe to use.

  The index only contains pending rows.
  My query only wants pending rows.
  Therefore, the index contains exactly the universe
  of rows I care about.

Planner selects: idx_tasks_pending_user ✓

If the query asked for status = 'completed':
  B says: status = 'completed'
  C says: status = 'pending'
  B does NOT imply C → planner cannot use this index.
  Falls back to heap scan or another index.
```

This matching logic means partial indexes are highly specific — they only activate for queries whose conditions are compatible with the index's own `WHERE` clause. This specificity is a feature, not a limitation.

## The EXPLAIN ANALYZE: Before and After

Running `EXPLAIN ANALYZE` before and after the change tells the story with numbers:

```sql
EXPLAIN ANALYZE
SELECT * FROM tasks
WHERE user_id = 1
  AND status = 'pending';
```

**Before** — using the full 8GB index:

```
Index Scan using idx_tasks_user_status on tasks
  (cost=0.57..312.80 rows=22 width=245)
  (actual time=18.442..1994.331 rows=22 loops=1)
  Index Cond: ((user_id = 1) AND (status = 'pending'))
  Buffers: shared hit=4 read=289
           ↑              ↑
           4 pages        289 pages fetched from DISK
           from cache     (cache misses — slow random I/O)
Planning Time: 0.8 ms
Execution Time: 1998.7 ms
```

The key line is `Buffers: shared hit=4 read=289`. This means for this one query, PostgreSQL found only 4 pages in the buffer cache and had to go to disk 289 times. Each disk read is a random I/O operation. That is why the query takes 2 seconds even with an index in place.

**After** — using the 400MB partial index:

```
Index Scan using idx_tasks_pending_user on tasks
  (cost=0.42..14.21 rows=22 width=245)
  (actual time=0.031..0.198 rows=22 loops=1)
  Index Cond: (user_id = 1)
  Filter: (status = 'pending')
  Buffers: shared hit=6 read=0
           ↑              ↑
           6 pages        ZERO disk reads
           from cache     (everything in buffer cache)
Planning Time: 0.3 ms
Execution Time: 0.212 ms  ← effectively 10ms end-to-end
```

`read=0` — not a single page had to be fetched from disk. The entire partial index fits comfortably in the buffer cache. Every query finds its data already in RAM. The query goes from 2,000ms to approximately 10ms — a **200× improvement** — and the difference is almost entirely explained by those two numbers: 289 disk reads versus 0 disk reads.

## The Mechanics of Index Size Reduction

It is worth being precise about why the index shrinks so dramatically. This helps you reason about similar situations in your own work.

A PostgreSQL B-Tree index stores data in fixed-size pages, typically 8KB each. Each page holds multiple index entries. The number of entries per page depends on the size of the indexed values (the `user_id` column is a 64-bit integer, 8 bytes; a pointer is about 6 bytes; overhead per entry is roughly 4 bytes — so about 18 bytes per entry, giving around 450 entries per 8KB page). With 50 million entries in the full index, the leaf level alone requires roughly 111,000 pages, which is about 870MB. Add in the internal nodes, overflow pages, dead space from updates, and fillfactor considerations, and you arrive at approximately 8GB total.

The partial index has only 1 million entries — exactly 2% of the full index. At the same density, the leaf level needs about 2,222 pages, or roughly 17MB. With overhead, the complete partial index lands around 400MB. This is a direct consequence of indexing 1 million rows instead of 50 million — the size scales almost perfectly with the number of indexed rows.

```
INDEX SIZE MATHEMATICS

Full index on (user_id, status):
  Rows indexed:         50,000,000
  Bytes per entry:      ~160 bytes (user_id=8B, status=~10B,
                                    ptr=6B, overhead, alignment,
                                    page headers, bloat factor)
  Total leaf data:      ~8,000 MB
  Internal nodes:       ~0.4% overhead (B-tree property)
  Total index size:     ~8,000 MB (8 GB)

Partial index on (user_id) WHERE status='pending':
  Rows indexed:         1,000,000  (50M × 2%)
  Bytes per entry:      ~80 bytes  (user_id=8B, ptr=6B,
                                    overhead, page headers)
                         ↑ Also smaller because status column
                           is not stored in the index at all
  Total leaf data:      ~80 MB
  Internal nodes:       ~0.4% overhead
  Index bloat (real):   ~5× for safety/fillfactor
  Total index size:     ~400 MB

Reduction: 8,000 MB → 400 MB = 95% smaller

Two factors compound:
  1. Fewer rows (50M → 1M): 98% reduction in entries
  2. Smaller entry size (status column removed): additional shrink
```

Notice the second factor: because `status` is now the index's `WHERE` condition rather than a stored column, it does not take up space in each leaf entry. The partial index on `(user_id)` stores only the `user_id` value and a pointer per entry, while the old composite index on `(user_id, status)` stored both `user_id` and `status` in every entry. This makes each individual entry smaller, which further reduces the total index size.

## Write Performance: A Hidden Bonus

Most discussions about partial indexes focus on read performance improvements, but there is an equally important benefit on the write side.

Every time a task is created, updated, or deleted, PostgreSQL must update every index on the `tasks` table. With the full composite index, every INSERT (whether the task is pending or completed) writes an entry to the index. Every UPDATE that changes `status` from `'pending'` to `'completed'` must update the index. Every DELETE must remove the entry.

With the partial index, the write behavior changes dramatically:

```
WRITE OPERATIONS — Full index vs Partial index

INSERT a new 'pending' task:
  Full index:    Write entry (user_id, status='pending') to index ✓
  Partial index: Write entry (user_id) to index ✓
  Both: one write. But partial index entry is smaller.

INSERT a new 'completed' task:
  Full index:    Write entry (user_id, status='completed') to index ✓
  Partial index: WHERE status='pending' → row doesn't qualify → SKIP ✓
  Partial index: ZERO index writes for new completed tasks.
  (98% of new inserts are probably completions over the app's lifetime)

UPDATE status FROM 'pending' TO 'completed' (task finished!):
  Full index:    Update entry from (user_id, 'pending') → (user_id, 'completed')
  Partial index: Remove entry (row no longer satisfies WHERE clause)
  Both: one index operation, but partial index performs slightly less work.

UPDATE status FROM 'completed' TO 'pending' (task re-opened):
  Full index:    Update entry from (user_id, 'completed') → (user_id, 'pending')
  Partial index: Insert new entry (row now satisfies WHERE clause)
  Both: one index operation.

DELETE a completed task:
  Full index:    Remove entry from index
  Partial index: Row never in index → SKIP
  Partial index: ZERO index work for deleting completed tasks.

Conclusion: The partial index dramatically reduces write amplification
for the dominant write patterns — inserts and deletes of completed tasks.
```

In a mature task management app where users are creating tasks and marking them complete constantly, the majority of insert and delete operations involve completed tasks. The partial index simply ignores all of these. The write overhead is proportional only to the pending tasks — the minority.

## The Buffer Cache Fit: Why 400MB Changes Everything

The most important consequence of shrinking the index from 8GB to 400MB is something that does not show up directly in the query plan — it shows up in **system-wide behaviour** under real-world load.

When an index fits in the buffer cache, it becomes **permanently hot**. The first query of the day loads the index into RAM. Every subsequent query finds it there. There is no eviction pressure because a 400MB index is a small fraction of even a modest buffer cache allocation.

```
BUFFER CACHE BEHAVIOUR — Under concurrent load

Server config: shared_buffers = 2GB (typical for medium server)

Scenario: 500 concurrent users loading their task lists simultaneously

WITH 8GB FULL INDEX:
┌─────────────────────────────────────────────────────────────────┐
│  Buffer Cache (2GB)                                             │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ Heap pages         ██████████████████  (1.2 GB)          │   │
│  │ Index pages (hot)  ████████  (0.8 GB)                    │   │
│  │                                                          │   │
│  │ ← Only 10% of the 8GB index can be in cache at once →   │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                 │
│  User A's query loads index pages for user_id=1..50            │
│  User B's query loads index pages for user_id=5000..5050       │
│  User C's query EVICTS User A's pages to load user_id=20000..  │
│                                                                 │
│  Each user's first query: cache miss → disk I/O → slow          │
│  Cache thrashing: pages constantly evicted and reloaded         │
│  Result: 2,000ms per query consistently                         │
└─────────────────────────────────────────────────────────────────┘

WITH 400MB PARTIAL INDEX:
┌─────────────────────────────────────────────────────────────────┐
│  Buffer Cache (2GB)                                             │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ Heap pages          ████████████  (0.9 GB)               │   │
│  │ Partial Index       ████  (0.4 GB) ← ENTIRE INDEX IN RAM │   │
│  │ Other data          ████  (0.7 GB free for other tables) │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                 │
│  User A's query: cache hit for all index pages → 0 disk reads  │
│  User B's query: cache hit for all index pages → 0 disk reads  │
│  User C's query: cache hit for all index pages → 0 disk reads  │
│                                                                 │
│  Index is PERMANENTLY HOT. No eviction. No disk reads.         │
│  Result: ~10ms per query for every user                         │
└─────────────────────────────────────────────────────────────────┘
```

This is why the `Buffers: read=289` became `Buffers: read=0`. It was not just about the index being logically correct — it was about the index being physically small enough to stay in RAM. The 200× speedup came almost entirely from eliminating disk I/O, and eliminating disk I/O came from making the index small enough to cache completely.

## When to Reach for a Partial Index

Not every table benefits from a partial index. The concept applies specifically when a table has a **skewed data distribution** — where the overwhelming majority of rows belong to one or a few categories, but queries overwhelmingly target the minority categories. This pattern is extremely common in production software:

```
COMMON PARTIAL INDEX PATTERNS IN THE REAL WORLD

Pattern 1 — Status column with a dominant terminal state:
  Table:    orders         (98% 'delivered', 2% 'in_progress')
  Queries:  always for 'in_progress' orders
  Index:    (user_id) WHERE status = 'in_progress'

Pattern 2 — Soft deletes:
  Table:    users          (0.5% 'deleted', 99.5% active)
  Queries:  almost always for non-deleted users
  Index:    (email) WHERE deleted_at IS NULL

Pattern 3 — Boolean flags:
  Table:    notifications  (95% read=TRUE, 5% read=FALSE)
  Queries:  always for unread notifications
  Index:    (user_id, created_at) WHERE read = FALSE

Pattern 4 — Processing queues:
  Table:    email_jobs     (99% processed, 1% queued)
  Queries:  always for queued jobs
  Index:    (priority, created_at) WHERE processed = FALSE

Pattern 5 — Premium features:
  Table:    accounts       (90% free tier, 10% paid)
  Queries:  certain features only available to paid
  Index:    (account_id) WHERE tier = 'paid'

In every case, the test is:
  "What fraction of rows does my query actually need?"
  "What fraction of rows does my current index contain?"
  If those fractions are very different → partial index.
```

## The Decision Framework: Full vs Partial Index

Before creating any index, run through this mental checklist:

```
SHOULD THIS BE A PARTIAL INDEX?

Step 1: Identify the WHERE clause condition in your slow query.
        e.g., status = 'pending'

Step 2: Find out what percentage of rows satisfy that condition.
        SELECT status, COUNT(*), COUNT(*) * 100.0 / SUM(COUNT(*))
               OVER () AS pct
        FROM tasks
        GROUP BY status;

        Result:
        status      | count    | pct
        ────────────┼──────────┼──────
        completed   | 49000000 | 98.0%
        pending     |  1000000 |  2.0%

Step 3: Apply the rule of thumb.
        If the condition selects < 20% of rows → strong candidate
        If the condition selects < 5%  of rows → almost certainly
        If the condition selects > 50%  of rows → full index better

Step 4: Ask whether that condition appears in ALL (or nearly all)
        queries against this table for this access pattern.
        If yes → partial index is safe and beneficial.
        If sometimes queries need ALL rows → you may need both.

Step 5: Check if the resulting index fits in your buffer cache.
        Estimate index size: (rows × ~80–160 bytes) / 1GB ≈ GB
        If it fits in shared_buffers → all queries will be cache hits.
        That is the goal.
```

## Multiple Partial Indexes: Covering Different Minorities

One nuance worth understanding: you can have **multiple partial indexes** on the same table, each covering a different subset. This is particularly useful when you have several minority conditions, each queried independently.

Suppose the tasks app also has a separate admin dashboard that shows all tasks marked `'blocked'` — perhaps tasks waiting for dependencies. Blocked tasks might be 3% of the total, queried infrequently but needing to be fast when they are.

```sql
-- Index for the user-facing task list (pending tasks)
CREATE INDEX idx_tasks_pending_user
ON tasks (user_id)
WHERE status = 'pending';       -- 1M rows, 400MB

-- Index for the admin blocked-tasks view
CREATE INDEX idx_tasks_blocked_user
ON tasks (user_id, created_at DESC)
WHERE status = 'blocked';       -- 1.5M rows, ~600MB

-- No index needed for 'completed' tasks
-- (they are accessed only via full-text search or exports,
--  which use different mechanisms)
```

Each partial index is small, targeted, and stays hot in cache. The total index footprint for both is around 1GB — still smaller than the single 8GB full index, and far more cache-friendly. The query planner automatically picks the right partial index based on which `status` value appears in each query's `WHERE` clause.

## Summary: The Core Mental Model

The lesson of this case study is one of the most important intuitions in database engineering: **the value of an index is not measured by how much it covers — it is measured by how precisely it serves the queries that actually run.**

An 8GB index that covers all 50 million rows sounds thorough and comprehensive. But 98% of its entries correspond to rows that are almost never queried. Those 49 million entries consume memory, slow down writes, and push the useful 1 million entries out of the buffer cache. The result is a system that performs random disk I/O on nearly every query — disguised as an indexed query, but suffering the practical penalty of cache misses.

A 400MB partial index covering only the 1 million pending tasks is smaller, faster to write, and fits entirely in RAM. Because it fits in RAM, every query is a cache hit. Because every query is a cache hit, there is no disk I/O. Because there is no disk I/O, the query takes 10ms instead of 2,000ms.

The database engine never changed. The query never changed. The data never changed. Only the index definition changed — specifically, its scope. And that one change produced a 200× improvement in query speed and a 95% reduction in index size simultaneously. This is the power of understanding not just _how_ indexes work, but _when_ to make them smaller rather than larger.
