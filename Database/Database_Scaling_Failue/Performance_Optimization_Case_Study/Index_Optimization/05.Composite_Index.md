# The Composite Index Column Order: Sequence Is Everything

> _"An index with the wrong column order is like a dictionary sorted by the last letter of each word. Technically sorted. Completely useless for how you actually search."_

---

## Setting the Scene

You are working on a logistics platform — the kind of system that tracks shipments moving between warehouses and customers. Think of companies like FedEx, Aramex, or a large e-commerce fulfillment network. The `shipments` table is the beating heart of the system. Every shipment created, every status update, every warehouse assignment writes a row here.

The table has **200 million rows**. Operations run 24/7. Warehouse managers constantly open dashboards that ask: _"Show me everything currently in transit from warehouse 5 in the last 7 days."_ This query runs thousands of times per hour. And it takes **3 seconds** every single time.

The frustrating part? There is already a composite index on the relevant columns. The team did the right thing — they indexed the columns the query filters on. But they put them in the wrong order. And column order, in a composite B-Tree index, is not a minor detail. It is everything.

---

## The Table and the Query

The `shipments` table looks something like this:

```sql
CREATE TABLE shipments (
    id             BIGSERIAL PRIMARY KEY,
    warehouse_id   INTEGER NOT NULL,
    status         VARCHAR(30) NOT NULL,
    origin         VARCHAR(100),
    destination    VARCHAR(100),
    carrier        VARCHAR(50),
    weight_kg      DECIMAL(8,2),
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    delivered_at   TIMESTAMPTZ
    -- ... more columns
);
```

And the slow dashboard query:

```sql
SELECT *
FROM shipments
WHERE status       = 'in_transit'
  AND warehouse_id = 5
  AND created_at   > NOW() - INTERVAL '7 days';
```

Three conditions, all perfectly reasonable for a logistics dashboard:

- `status = 'in_transit'` — an **equality** condition, filtering to one specific status value
- `warehouse_id = 5` — an **equality** condition, filtering to one specific warehouse
- `created_at > NOW() - INTERVAL '7 days'` — a **range** condition, filtering to the last week

The existing composite index that was supposed to serve this query:

```sql
CREATE INDEX idx_shipments_old
ON shipments (created_at, status, warehouse_id);
```

This index contains exactly the right columns. But the order is wrong in a way that fundamentally undermines how B-Tree indexes work. Understanding why requires understanding how a multi-column B-Tree is structured.

---

## How a Composite B-Tree Index Is Physically Organised

A composite index sorts its entries by the **first column first**, and only within groups of equal first-column values does it sort by the second column, and only within groups of equal first- and second-column values does it sort by the third. This is called **lexicographic ordering** — the same principle by which a dictionary is organised.

Consider how words are sorted in an English dictionary: first by the first letter, then among words starting with the same letter by the second letter, and so on. The word "zoo" is at the very end not because of its second or third letters, but because 'z' comes last. A dictionary is only useful if you know the first letter of the word you want. If you only know the last letter, the dictionary's sorted order gives you zero navigation advantage.

A composite B-Tree index works exactly the same way. Here is what the index on `(created_at, status, warehouse_id)` looks like structurally:

```
INDEX: (created_at, status, warehouse_id) — The WRONG Order
─────────────────────────────────────────────────────────────────────

Entries sorted lexicographically — first by created_at, then status,
then warehouse_id within each timestamp group:

  created_at=2024-10-14 08:00:01 | status='cancelled'    | wh=12 → ptr
  created_at=2024-10-14 08:00:01 | status='delivered'    | wh=3  → ptr
  created_at=2024-10-14 08:00:01 | status='in_transit'   | wh=1  → ptr
  created_at=2024-10-14 08:00:01 | status='in_transit'   | wh=5  → ptr  ← want this
  created_at=2024-10-14 08:00:02 | status='cancelled'    | wh=7  → ptr
  created_at=2024-10-14 08:00:02 | status='in_transit'   | wh=5  → ptr  ← want this
  created_at=2024-10-14 08:00:03 | status='delivered'    | wh=9  → ptr
  created_at=2024-10-14 08:00:03 | status='in_transit'   | wh=2  → ptr
  created_at=2024-10-14 08:00:04 | status='in_transit'   | wh=5  → ptr  ← want this
  ...
  (continues for every second of the past 7 days)
  ...
  created_at=2024-10-21 23:59:59 | status='in_transit'   | wh=5  → ptr  ← want this

The rows we want (in_transit, warehouse 5, last 7 days) are scattered
throughout the entire 7-day range — one matching row interspersed among
many non-matching rows at every timestamp.

Total entries in the 7-day range: ~40,000,000 rows
Matching entries (in_transit, wh=5, last 7d): ~50,000 rows

To find those 50,000 rows, the index must be scanned sequentially
across all 40,000,000 entries in the date range.
```

This is the core problem. The B-Tree can efficiently navigate to the start of the date range — "find the first entry where `created_at > NOW() - INTERVAL '7 days'`" — because timestamps are continuous and the index is sorted by them first. But once it arrives at that starting point, it faces an unbroken sequence of 40 million entries spanning the entire 7-day window. Within that window, entries are sorted by `(status, warehouse_id)` within each individual timestamp value, but across different timestamps, they alternate freely between all statuses and all warehouses. There is no way to jump directly to "all in_transit entries for warehouse 5" — they are woven throughout the 40-million-entry range, one per timestamp cluster.

## The Selectivity Concept: Not All Filters Are Created Equal

To understand why column order matters so profoundly, you need to understand **selectivity** — one of the most important concepts in query optimisation.

Selectivity is a measure of how much a condition narrows down the dataset. A **high-selectivity** condition eliminates most rows — it is a very precise filter. A **low-selectivity** condition leaves most rows intact — it is a coarse filter.

Let us measure the selectivity of each condition in our query against 200 million rows:

```
SELECTIVITY ANALYSIS — 200 million total rows

Condition 1: created_at > NOW() - INTERVAL '7 days'
  ┌──────────────────────────────────────────────────────────────┐
  │ Rows matching: ~40,000,000                                   │
  │ Rows eliminated: 160,000,000 (80%)                           │
  │ Rows remaining: 40,000,000  (20% of table)                   │
  │ Selectivity: LOW-MEDIUM                                      │
  │                                                              │
  │ Explanation: Shipments accumulate for years. 7 days is a     │
  │ relatively small slice of the total timeline, but 7 days of  │
  │ a busy logistics platform still means 40M rows.              │
  └──────────────────────────────────────────────────────────────┘

Condition 2: status = 'in_transit'
  ┌──────────────────────────────────────────────────────────────┐
  │ Possible statuses: pending, in_transit, delivered,           │
  │                    cancelled, returned (~5 values)           │
  │ Rows matching: ~40,000,000 (20% of all shipments             │
  │                are currently in_transit at any time)         │
  │ Selectivity: LOW-MEDIUM                                      │
  │                                                              │
  │ Explanation: 'in_transit' is a live status — a large portion │
  │ of all shipments are always in this state.                   │
  └──────────────────────────────────────────────────────────────┘

Condition 3: warehouse_id = 5
  ┌──────────────────────────────────────────────────────────────┐
  │ Number of warehouses: ~200                                   │
  │ Rows for warehouse 5: ~1,000,000 (0.5% of all rows)          │
  │ Selectivity: HIGH                                            │
  │                                                              │
  │ Explanation: Each of 200 warehouses handles roughly equal    │
  │ volume. One warehouse = ~0.5% of all shipments.              │
  └──────────────────────────────────────────────────────────────┘

Combined effect of all three conditions:
  After warehouse_id=5:   ~1,000,000 rows remain
  After status='in_transit': ~200,000 rows remain
  After created_at range:    ~50,000 rows remain  ← final result set

The most powerful filter is warehouse_id (eliminates 99.5% of rows).
The second most powerful is status (eliminates ~80% of what remains).
The least powerful is created_at range (still leaves 25% of what remained).
```

The fundamental rule of composite index column ordering falls directly out of this selectivity analysis: **put the most selective conditions first**. More specifically, equality conditions almost always come before range conditions — and among equality conditions, the more selective one (fewer matching rows) should come first.

## Why Range Conditions Must Come Last: The Broken Prefix Property

There is a precise technical reason why range conditions break composite index usefulness when placed before other columns. It is called the **Index Prefix Property**, and understanding it will permanently change how you design indexes.

A composite index can only be efficiently navigated using a **prefix** of its columns — a contiguous sequence starting from the leftmost column. Once the query uses a range condition on a column, the index cannot be used for filtering on any column to the right of it. The range condition acts like a wall.

Here is why. When the B-Tree resolves a range condition like `created_at > '2024-10-14'`, it finds the starting point and then must read forward through all entries until the range ends. It cannot skip non-matching entries during this scan because those entries are sorted by `created_at`, not by `status` or `warehouse_id`. Within the range, different timestamps interleave different statuses and warehouse IDs in no particular global order. The index cannot jump from "all in_transit entries at 08:00:01" to "all in_transit entries at 08:00:02" — those entries are not adjacent.

```
THE PREFIX PROPERTY — Which columns the index can serve

Index: (created_at, status, warehouse_id)

Query uses: created_at > range_start
                ↑
     Range condition on column 1

  Column 1 (created_at): ✓ Used for range navigation
                              (finds starting point, scans forward)
  Column 2 (status):     ✗ CANNOT filter efficiently
                              (status values are interleaved within range)
  Column 3 (warehouse_id): ✗ CANNOT filter efficiently
                              (same reason — blocked by range in col 1)

Result: Index scan covers all 40M entries in the date range.
        status and warehouse_id filters applied as post-scan filters.
        40M index entries scanned → 50K matching rows returned.
        Most of the work is wasted.

─────────────────────────────────────────────────────────────────────

Index: (warehouse_id, status, created_at)  ← CORRECT ORDER

Query uses: warehouse_id = 5 (equality)
              AND status = 'in_transit' (equality)
              AND created_at > range_start (range)

  Column 1 (warehouse_id): ✓ Equality — navigates directly to wh=5
                              Eliminates 99.5% of the index immediately
  Column 2 (status):        ✓ Equality — within wh=5, jumps to 'in_transit'
                              Eliminates ~80% of warehouse 5's entries
  Column 3 (created_at):    ✓ Range — scans forward from the date boundary
                              within the (wh=5, in_transit) group only

Result: Index scans only the (warehouse_id=5, status='in_transit')
        subrange, then applies the date filter within that subrange.
        ~50K entries scanned → ~50K matching rows returned.
        Almost zero wasted work.
```

The range condition consuming column 3 is completely fine — there is nothing to its right in the index that it could block. By the time the index reaches the range condition, it has already applied both equality filters and narrowed the working set from 200 million rows down to roughly 200,000. The range condition then makes one final, precise cut through those 200,000 entries to return the 50,000 in the target window.

## EXPLAIN ANALYZE: Reading the Evidence Before and After

Running `EXPLAIN ANALYZE` on the query before the fix reveals the planner choosing the wrong-ordered index and paying dearly for it:

```sql
EXPLAIN ANALYZE
SELECT *
FROM shipments
WHERE status       = 'in_transit'
  AND warehouse_id = 5
  AND created_at   > NOW() - INTERVAL '7 days';
```

**Before — index on `(created_at, status, warehouse_id)`:**

```
Index Scan using idx_shipments_old on shipments
  (cost=0.57..984201.33 rows=51200 width=312)
  (actual time=0.081..2991.442 rows=51847 loops=1)
  Index Cond: (created_at > (now() - '7 days'::interval))
  Filter: ((status = 'in_transit') AND (warehouse_id = 5))
  Rows Removed by Filter: 39948153
Planning Time: 0.9 ms
Execution Time: 3002.1 ms
```

Decode this output carefully — every line tells a story.

`Index Cond: (created_at > ...)` — Only `created_at` is used as the actual index navigation condition. The planner used the first column of the index to find the starting point in the B-Tree, then scanned forward through the date range.

`Filter: ((status = 'in_transit') AND (warehouse_id = 5))` — The other two conditions, `status` and `warehouse_id`, are applied as **post-index filters**. They are not used to navigate the index — they are applied _after_ the index scan returns rows, row by row. This is the key signal in EXPLAIN output: when a condition appears under `Filter` rather than `Index Cond`, the index is not being used to eliminate those rows efficiently.

`Rows Removed by Filter: 39,948,153` — The index scan returned 39,948,153 + 51,847 = roughly 40 million rows from the date range, and then the filter discarded 39.9 million of them. Almost 40 million rows were loaded and checked and thrown away.

**After — index on `(warehouse_id, status, created_at)`:**

```
Index Scan using idx_shipments_new on shipments
  (cost=0.57..9841.33 rows=51200 width=312)
  (actual time=0.031..12.441 rows=51847 loops=1)
  Index Cond: ((warehouse_id = 5)
               AND (status = 'in_transit')
               AND (created_at > (now() - '7 days'::interval)))
  Rows Removed by Filter: 0
Planning Time: 0.4 ms
Execution Time: 14.9 ms
```

The contrast is stark. `Index Cond` now lists **all three conditions** — `warehouse_id`, `status`, and `created_at` are all used as index navigation conditions. The planner traversed the B-Tree using all three columns, arriving directly at the relevant entries. `Rows Removed by Filter: 0` — not a single row was loaded and discarded. Every row the index returned was a genuine match. The query went from 3,002ms to 14.9ms — a **200× improvement** from reordering three column names.

## The ESR Rule: A Formula for Getting Column Order Right

Professional database engineers use a mnemonic called the **ESR Rule** to remember the correct ordering strategy for composite indexes. It stands for **Equality — Sort — Range**, and it defines the optimal left-to-right column order:

```
THE ESR RULE — Composite Index Column Ordering

E — EQUALITY conditions first
    Columns used with = or IN operators
    These pin the B-Tree traversal to an exact position
    Most selective equality condition should come first

S — SORT columns second (if applicable)
    Columns used in ORDER BY or GROUP BY
    Placing sort columns here lets the index serve the
    sort without a separate sort operation in memory
    Only include if your query actually sorts or groups

R — RANGE conditions last
    Columns used with >, <, >=, <=, BETWEEN, or LIKE prefix
    Range conditions must come last because they terminate
    the precise-navigation phase of the B-Tree traversal

Applied to our query:
  WHERE warehouse_id = 5           → E (equality)
    AND status = 'in_transit'      → E (equality)
    AND created_at > 7_days_ago    → R (range)

  Optimal index: (warehouse_id, status, created_at)
                      E              E         R

Between the two equality columns:
  warehouse_id has ~200 unique values → higher selectivity
  status       has ~5  unique values  → lower selectivity
  Put warehouse_id first (more selective = eliminates more rows sooner)

Final answer: (warehouse_id, status, created_at)  ✓
```

The ESR rule is a heuristic, not an absolute law — there are edge cases and exceptions. But it is correct in the overwhelming majority of real-world queries, and following it consistently will keep you out of the most common composite index pitfalls.

## Selectivity Within Equality Columns: Which Equality Condition Goes First?

The ESR rule tells you that equality conditions come before range conditions. But when a query has multiple equality conditions — as ours does, with both `warehouse_id` and `status` — you need a secondary rule for ordering _among_ the equality columns.

The guideline is to put the **more selective** equality condition first — the one that eliminates more rows. Here is how to reason through it:

```
ORDERING EQUALITY COLUMNS BY SELECTIVITY

Our two equality conditions:
  warehouse_id = 5    → 1 of 200 warehouses → ~0.5% of rows → HIGH selectivity
  status = 'in_transit' → 1 of 5 statuses   → ~20% of rows  → MEDIUM selectivity

If warehouse_id comes first: (warehouse_id, status, created_at)
  Step 1: Jump to warehouse_id=5 → eliminates 99.5% of rows immediately
           Working set: ~1,000,000 rows
  Step 2: Within wh=5, jump to status='in_transit' → eliminates ~80%
           Working set: ~200,000 rows
  Step 3: Apply date range → Working set: ~50,000 rows  ← Final result
  Index entries examined: ~200,000

If status comes first: (status, warehouse_id, created_at)
  Step 1: Jump to status='in_transit' → eliminates 80% of rows
           Working set: ~40,000,000 rows
  Step 2: Within 'in_transit', jump to warehouse_id=5 → eliminates 99.5%
           Working set: ~200,000 rows
  Step 3: Apply date range → Working set: ~50,000 rows  ← Final result
  Index entries examined: ~200,000

Wait — same result?
  In this specific case, yes. Both column orderings among the equality
  columns result in the same final working set size because the planner
  applies both equality conditions before the range condition either way.

  The difference emerges in index organisation efficiency:
  - (warehouse_id, status) groups: 200 warehouses × 5 statuses = 1,000 groups
  - (status, warehouse_id) groups: 5 statuses × 200 warehouses = 1,000 groups
  - Same number of groups, same size — genuinely equivalent here.

When selectivity ordering within equality columns matters most:
  Scenario: Query sometimes uses warehouse_id ALONE (no status filter)
    Index (warehouse_id, status, created_at): warehouse_id alone → ✓ (prefix match)
    Index (status, warehouse_id, created_at): warehouse_id alone → ✗ (not a prefix)

  The more commonly queried equality column should come first —
  it enables the index to serve partial-condition queries too.
```

The deeper lesson here is that composite index ordering affects not just the one query you are optimising, but every query that might use this index. A well-ordered index serves the most common access patterns and gracefully degrades for less common ones.

## The Index Prefix Rule: One Index Serving Multiple Queries

One of the most practically valuable properties of composite indexes is that a single index can serve multiple different queries, as long as those queries filter on a **left-side prefix** of the index columns.

With the new index `(warehouse_id, status, created_at)`, here are all the queries it can serve efficiently:

```
INDEX: (warehouse_id, status, created_at)

Queries this index can serve:

  Query 1: WHERE warehouse_id = 5
    → Uses column 1 as prefix ✓
    → Efficient: jumps to wh=5, scans all entries

  Query 2: WHERE warehouse_id = 5 AND status = 'in_transit'
    → Uses columns 1+2 as prefix ✓
    → Efficient: jumps to (wh=5, in_transit) group

  Query 3: WHERE warehouse_id = 5 AND status = 'in_transit'
             AND created_at > 7_days_ago
    → Uses all 3 columns ✓
    → Maximally efficient: the query we optimised

  Query 4: WHERE warehouse_id = 5 AND created_at > 7_days_ago
    → Uses column 1 ✓, skips column 2, uses column 3
    → PARTIAL use: navigates to wh=5, then scans ALL statuses
    → Less efficient than query 3, but still uses the index

Queries this index CANNOT serve efficiently:

  Query 5: WHERE status = 'in_transit'
    → Column 1 (warehouse_id) not in WHERE clause
    → Not a left-side prefix → Sequential Scan or different index needed

  Query 6: WHERE created_at > 7_days_ago
    → Column 1 and 2 not in WHERE clause
    → Not a left-side prefix → Sequential Scan or different index needed

  Query 7: WHERE status = 'in_transit' AND created_at > 7_days_ago
    → Starts with column 2 (status), skipping column 1
    → Not a left-side prefix → Sequential Scan

The Prefix Rule: An index on (A, B, C) efficiently supports queries
that filter on: A alone | A+B | A+B+C | A+C (partially)
But NOT: B alone | C alone | B+C | C+A (out of order)
```

This prefix property has a practical implication for index design in production systems: if you have several related queries filtering on overlapping sets of columns, carefully choosing the column order of one composite index can make it serve all of them, avoiding the need to create separate indexes for each query pattern.

## Deploying Safely: The Transition Plan

Changing an index in production on a 200-million-row table requires a careful sequence to avoid downtime and ensure correctness. The approach follows four steps:

```sql
-- Step 1: Create the new index concurrently (no table lock, no downtime)
--         This may take 20-40 minutes on 200M rows — that is fine
--         The old index continues serving queries during this time
CREATE INDEX CONCURRENTLY idx_shipments_new
ON shipments (warehouse_id, status, created_at);

-- Step 2: Verify the new index is being used by the target query
EXPLAIN ANALYZE
SELECT * FROM shipments
WHERE status       = 'in_transit'
  AND warehouse_id = 5
  AND created_at   > NOW() - INTERVAL '7 days';
-- Confirm output shows: Index Scan using idx_shipments_new

-- Step 3: Monitor production for 24-48 hours
--         Check pg_stat_user_indexes to confirm the new index is being hit
SELECT indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'shipments'
ORDER BY idx_scan DESC;

-- Step 4: Drop the old index once confident the new one is working
--         DROP INDEX CONCURRENTLY avoids locking the table
DROP INDEX CONCURRENTLY idx_shipments_old;
```

The critical insight in this sequence is the **never-drop-before-create** principle. You always build the replacement index first, verify it works correctly, give it time to accumulate usage statistics, and only then remove the old one. Running without any index, even briefly, on a 200-million-row table under production load would be catastrophic.

## Common Anti-Patterns: What to Recognise and Avoid

The wrong-column-order problem is one specific instance of a broader family of composite index anti-patterns. Here are the most common ones you will encounter:

```
COMPOSITE INDEX ANTI-PATTERNS

Anti-Pattern 1: Range column first  ← This case study
  WRONG:   (created_at, status, warehouse_id)
  CORRECT: (warehouse_id, status, created_at)
  Why wrong: Range condition blocks efficient use of remaining columns

Anti-Pattern 2: Low-selectivity column first among equalities
  WRONG:   (status, user_id)          -- status has 5 values
  CORRECT: (user_id, status)          -- user_id has millions of values
  Why wrong: Low-selectivity first means large initial working set
  Note: Only matters significantly in some query patterns

Anti-Pattern 3: Column in ORDER BY placed before WHERE columns
  WRONG:   (created_at, user_id)  for  WHERE user_id=? ORDER BY created_at
  CORRECT: (user_id, created_at)
  Why wrong: Sort column being first makes WHERE filter less efficient

Anti-Pattern 4: Missing the range column entirely
  Index: (warehouse_id, status)  for  WHERE wh=5 AND status='x'
                                         AND created_at > range
  Issue: Without created_at in the index, every matched row requires
         a heap fetch to check the date — Index Scan + Heap Fetches

Anti-Pattern 5: Redundant column at the end after range
  Index: (warehouse_id, status, created_at, carrier)
  For:   WHERE wh=5 AND status='x' AND created_at > range
  Issue: carrier after the range column cannot be used for filtering
         It only helps if carrier is in SELECT and you want a covering index
         Otherwise it wastes space with no benefit

QUICK DIAGNOSTIC — If EXPLAIN ANALYZE shows:
  • Conditions under Filter: instead of Index Cond: → wrong column order
    (some conditions not used for index navigation)
  • Rows Removed by Filter: > 10× the result set size → wrong column order
    (too many rows fetched and discarded)
  • High cost estimate despite using an index → selectivity mismatch
    (index not narrowing the working set efficiently)
```

## A Practical Decision Framework for Composite Index Design

Before creating any composite index, run through this sequence of questions:

```
COMPOSITE INDEX DESIGN FRAMEWORK

Step 1: List all WHERE clause conditions and classify them
        ┌─────────────────────┬────────────────────────────┐
        │ Condition           │ Type                       │
        ├─────────────────────┼────────────────────────────┤
        │ warehouse_id = 5    │ Equality (=)               │
        │ status = 'x'        │ Equality (=)               │
        │ created_at > date   │ Range (>)                  │
        │ price BETWEEN a,b   │ Range (BETWEEN)            │
        │ name LIKE 'abc%'    │ Range (prefix LIKE)        │
        └─────────────────────┴────────────────────────────┘

Step 2: Check if there is an ORDER BY or GROUP BY
        If ORDER BY uses a column that is not in WHERE,
        include it between equality and range columns (the S in ESR)

Step 3: Apply ESR ordering
        E → Equality columns (most selective first)
        S → Sort/Group columns (if applicable)
        R → Range column(s) (always last)

Step 4: Consider covering index potential
        If SELECT needs columns not in the WHERE/ORDER BY,
        add them to the index to enable Index Only Scan
        (but only if they are frequently needed — index size grows)

Step 5: Check the prefix property
        Does this index also serve other common queries as prefixes?
        If not, can you reorder columns to make it serve more queries?

Step 6: Verify with EXPLAIN ANALYZE
        ALL WHERE conditions should appear under Index Cond:
        Rows Removed by Filter: should be close to 0
        The cost estimate should be dramatically lower
```

## Summary: The Core Mental Model

The lesson of this case study is deceptively simple to state but surprisingly easy to get wrong in practice: **in a composite B-Tree index, the order of columns determines which parts of a query the index can actually navigate efficiently.**

A B-Tree index is a sorted structure. Its navigational power comes from the sorted order of its first column. The second column is sorted within groups of equal first-column values. The third column is sorted within groups of equal first- and second-column values. When a query places a range condition on the first column, the remaining columns lose their sorting benefit within that range, because values of different second and third column values are interspersed throughout the range — the index cannot skip to them.

The old index on `(created_at, status, warehouse_id)` placed the range condition first. The planner used it to find the start of the 7-day range and then scanned 40 million entries, applying the equality filters row by row as a post-scan operation. Only the first column provided navigational benefit. The other two columns were structurally present but functionally useless for filtering.

The new index on `(warehouse_id, status, created_at)` places the equality conditions first, in descending selectivity order, with the range condition last. The planner traverses the B-Tree in three precise steps — jumping to warehouse 5, then to `in_transit` within warehouse 5, then scanning forward from the date boundary within that narrow group. All three conditions are used for navigation. Only the 50,000 matching entries are examined. Zero rows are loaded and discarded.

The result is 3,000ms falling to 15ms — the same query, the same data, the same hardware, the same three columns. Just the order changed.
