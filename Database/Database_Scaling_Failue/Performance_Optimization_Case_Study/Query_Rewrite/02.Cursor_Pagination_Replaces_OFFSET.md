# The Scroll That Broke the Feed: How Replacing OFFSET with Cursor Pagination Made Deep Scrolling 2,666× Faster

> _"OFFSET is a lie the database tells you politely. It says 'skip these rows,' but what it actually does is read all of them and throw them away."_

---

## Setting the Scene

Imagine you are working as a backend engineer at a growing social media company. The product has been live for two years, the user base has expanded considerably, and the flagship feature — an infinitely scrollable feed of posts — is the heart of the entire experience. Users can scroll endlessly, and each time they reach the bottom of the visible content, the frontend silently fires a network request to load the next batch of twenty posts.

Everything worked beautifully in the early days. The database had a few hundred thousand posts, the team was small, and nobody thought deeply about pagination because pagination was not causing any problems. But now, a year and a half later, the posts table holds thirty million rows. The engineering team starts receiving automated alerts: API response times for the feed endpoint are spiking above eight seconds for some users. Support tickets pile up. Users are complaining that "the feed freezes when you scroll down far enough." A product manager messages the engineering channel: "Why does our app get slower the more engaged our users are?"

This is the situation you are walking into. And the answer, as you are about to discover, is buried inside a single innocent-looking SQL keyword: `OFFSET`.

---

## The Offending Query

The query powering the infinite scroll feed looks like this:

```sql
SELECT *
FROM posts
ORDER BY created_at DESC
OFFSET 50000
LIMIT 20;
```

The intention behind this query is clear and sensible. The frontend keeps track of which "page" the user is on. Each page contains twenty posts. When the user scrolls to the bottom and triggers a request for the next batch, the application calculates the offset — page number multiplied by page size — and sends it to the database. The database is then asked to sort all posts by recency, skip the first fifty thousand of them, and return the next twenty.

This approach is called **OFFSET pagination**, and it is one of the oldest and most widely taught patterns for implementing paginated data retrieval. It is simple to understand, simple to implement, and it works. The tragedy is that it works only up to a certain scale — and beyond that point, it becomes extraordinarily expensive in ways that are completely invisible from the application side.

---

## Understanding How OFFSET Actually Works Inside the Database

Here is the thing about `OFFSET` that the documentation rarely emphasises strongly enough: the database does not have a magic teleportation ability that lets it jump directly to row fifty thousand and start returning results from there. It cannot skip rows without reading them, because the rows in a heap file are not pre-sorted by `created_at`. They are stored in insertion order, scattered across disk pages. The only way to know which rows are the fifty thousandth through fifty-twentieth-thousandth newest posts is to sort all the posts by recency and then count through them.

What this means in practice is that every time you ask the database for `OFFSET 50000 LIMIT 20`, the database must do the following. It must first identify all posts (or use an index to walk them in created_at order), then sort them by `created_at DESC`, then count through the first fifty thousand rows one by one, discard every single one of them, then pick up the next twenty rows, and return those to you. The fifty thousand discarded rows represent real work: real memory, real CPU cycles, real I/O — all completely wasted.

```
WHAT THE DATABASE DOES FOR OFFSET 50000 LIMIT 20

Posts table (30,000,000 rows, sorted by created_at DESC in the index):

  ┌─────────────────────────────────────────────────────────────────┐
  │  Row 1      (newest)  ← Read, count, DISCARD                   │
  │  Row 2                ← Read, count, DISCARD                   │
  │  Row 3                ← Read, count, DISCARD                   │
  │  Row 4                ← Read, count, DISCARD                   │
  │  ...                                                           │
  │  ...        (50,000 rows read, counted, and thrown away)       │
  │  ...                                                           │
  │  Row 49,998           ← Read, count, DISCARD                   │
  │  Row 49,999           ← Read, count, DISCARD                   │
  │  Row 50,000           ← Read, count, DISCARD                   │
  │  ─────────────────────────────────────────────────────────────  │
  │  Row 50,001           ← KEEP ✓ (page starts here)             │
  │  Row 50,002           ← KEEP ✓                                 │
  │  ...                                                           │
  │  Row 50,020           ← KEEP ✓ (20th row, return to client)   │
  │  ─────────────────────────────────────────────────────────────  │
  │  Row 50,021 onwards   ← Never even looked at                   │
  └─────────────────────────────────────────────────────────────────┘

  Work done: 50,020 rows processed
  Work returned to client: 20 rows
  Efficiency ratio: 20 / 50,020 = 0.04%
```

The efficiency ratio is devastating. For every twenty rows of useful data returned to the user, the database has processed fifty thousand rows that it immediately throws away. And critically — this cost is not constant. It grows linearly with how deep into the feed the user has scrolled. A user on page one experiences almost no waste. A user on page two thousand five hundred — which is where `OFFSET 50000` puts us — forces the database to wade through all fifty thousand preceding rows on every single request.

This is the core architectural failure: **a system whose cost scales with user engagement.** The more a user loves your product and scrolls through it, the more expensive each of their requests becomes. Your most engaged users are the ones punishing your database the hardest.

## Reading the Evidence: EXPLAIN ANALYZE

When the team ran `EXPLAIN ANALYZE` on the problematic query, the output confirmed the diagnosis immediately:

```sql
EXPLAIN ANALYZE
SELECT *
FROM posts
ORDER BY created_at DESC
OFFSET 50000
LIMIT 20;
```

```
Limit  (cost=7234.50..7234.73 rows=20 width=420)
       (actual time=7891.234..7891.251 rows=20 loops=1)
  ->  Index Scan Backward using idx_posts_created_at on posts
      (cost=0.57..10234.00 rows=30000000 width=420)
      (actual time=0.031..7654.112 rows=50020 loops=1)
        Rows Removed by Limit: 50000

Planning Time: 0.3 ms
Execution Time: 7891.3 ms
```

Two numbers in this output tell the entire story. The first is `Execution Time: 7891.3 ms` — nearly eight seconds to deliver twenty rows of data. The second, and more revealing, is `Rows Removed by Limit: 50000`. The database read fifty thousand rows and removed them before applying the limit. Even though an index existed on `created_at` and the index scan was being used, the database still had to traverse fifty thousand index entries and fetch their corresponding heap rows, all to satisfy the OFFSET clause.

Notice that the planner is using an `Index Scan Backward` — it is walking the index in descending created_at order, which is correct and efficient. But no amount of indexing can fix the fundamental problem: OFFSET requires counting from the beginning, every time, no matter what.

## Understanding Why the Problem Gets Worse Over Time

The linear degradation of OFFSET pagination is not an edge case or a pathological scenario. It is a mathematical certainty built into the design of the pattern. To see why, consider what happens as a user scrolls through a feed over the course of a long session.

When the user opens the app and sees their feed for the first time, the application requests `OFFSET 0 LIMIT 20`. The database reads twenty rows and returns them instantly. No waste whatsoever. The user scrolls down, the next request is `OFFSET 20 LIMIT 20` — twenty rows read, twenty returned. Still effectively instant. The user keeps scrolling. After a few hundred rows, they have been using the app for a while and are clearly engaged. The request is now `OFFSET 500 LIMIT 20` — five hundred rows scanned to return twenty. Slightly more work, but still fast.

Now imagine a very engaged user who scrolls for an hour. They have seen two thousand five hundred pages of twenty posts each — fifty thousand posts. The next request is `OFFSET 50000 LIMIT 20`. The database must scan fifty thousand rows before returning the next twenty. The work is proportional to the depth, and at deep depths, that proportional cost becomes intolerable.

```
OFFSET PAGINATION: COST GROWS LINEARLY WITH DEPTH

  Response Time
  │
  8s │                                              ●  ← OFFSET 50,000
     │
  6s │                                         ●
     │
  4s │                                    ●
     │
  2s │                          ●
     │              ●
 <1s │    ●    ●
     │
  0  └────┬────┬────┬────┬────┬────┬────┬────┬────► Scroll Depth
         1k   5k   10k  15k  20k  25k  30k  40k  50k rows seen

  Every additional scroll = more wasted work = slower response
  Most loyal users = worst experience
```

This graph encapsulates the philosophical wrongness of OFFSET pagination for infinite scroll: the curve is strictly upward. Performance degrades in direct proportion to user engagement. There is no ceiling and no optimisation that can bend this curve — it is a consequence of the pattern's design, not an implementation flaw.

## The Solution: Keyset Pagination (Cursor Pagination)

The fix the team implemented is called **keyset pagination**, also commonly referred to as **cursor pagination** or **seek pagination**. Instead of telling the database "skip the first N rows," you tell it "give me rows that come after this specific row." The distinction sounds minor but the performance implications are profound.

The rewritten query looks like this:

```sql
SELECT *
FROM posts
WHERE created_at < :last_seen_ts
  AND id < :last_seen_id
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

In this query, `:last_seen_ts` is the `created_at` timestamp of the very last post the user saw in the previous batch, and `:last_seen_id` is that post's `id`. The frontend stores these two values after receiving each batch of results and sends them back with the next scroll request. Instead of asking the database to count rows from the beginning, you are giving the database a precise landmark — the exact row where the previous page ended — and asking it to start from there.

This is the difference between telling someone "start at page fifty thousand" and telling them "start right after this specific book." The first instruction requires counting. The second instruction just requires finding one specific thing.

---

## Why Keyset Pagination Is So Fast: The Index Jump

The magic of keyset pagination becomes clear when you understand how the database executes the rewritten query. Because the `posts` table has an index on `(created_at DESC, id DESC)` — a composite index covering both columns — the database can use that index to jump directly to the precise starting position without reading a single unnecessary row.

```
KEYSET PAGINATION: DIRECT INDEX JUMP

Composite index on (created_at DESC, id DESC):

  ┌────────────────────────────────────────────────────────┐
  │  Index entry: 2024-12-01 14:32:01, id=9999923         │
  │  Index entry: 2024-12-01 14:31:58, id=9999911         │
  │  ...                                                   │
  │  ─────── Cursor: created_at='2024-11-15', id=8823451 ──│ ← Jump here
  │  Index entry: 2024-11-15 09:12:44, id=8823449  ← KEEP │
  │  Index entry: 2024-11-15 09:11:01, id=8823105  ← KEEP │
  │  Index entry: 2024-11-14 23:59:58, id=8822870  ← KEEP │
  │  ...                                                   │
  │  (20 entries taken, then STOP)                         │
  └────────────────────────────────────────────────────────┘

  Rows scanned: 20
  Rows returned: 20
  Rows discarded: 0
  Efficiency ratio: 100%
```

The database uses the B-Tree index to perform a binary search directly to the cursor position. From that position, it reads exactly twenty entries and stops. It does not matter whether the user is on page one or page fifty thousand — the number of rows the database touches is always exactly twenty. The operation is O(log N) to find the starting position, then O(20) to read the results. Compare this to OFFSET's O(offset + 20), which grows without bound.

When the team ran `EXPLAIN ANALYZE` on the rewritten query, the contrast was dramatic:

```sql
EXPLAIN ANALYZE
SELECT *
FROM posts
WHERE created_at < '2024-11-15 09:12:45'
  AND id < 8823451
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

```
Limit  (cost=0.57..8.91 rows=20 width=420)
       (actual time=0.041..0.093 rows=20 loops=1)
  ->  Index Scan Backward using idx_posts_created_at_id on posts
      (cost=0.57..12500.91 rows=29875000 width=420)
      (actual time=0.038..0.081 rows=20 loops=1)
        Index Cond: ((created_at < '2024-11-15 09:12:45') AND (id < 8823451))
        Rows Removed by Filter: 0

Planning Time: 0.2 ms
Execution Time: 2.9 ms
```

`Rows Removed by Filter: 0`. Not a single row wasted. Not a single row read unnecessarily. The database jumped straight to the right position in the index, read twenty entries, and returned them. Execution time: 2.9 milliseconds, whether the user is on their first scroll or their ten-thousandth. The performance is now **constant with respect to scroll depth** — which is the critical property that makes this approach scale.

## The Composite Cursor: Solving the Tie-Breaking Problem

You may have noticed something interesting in the rewritten query: it uses two columns in the `WHERE` clause — `created_at < :last_seen_ts AND id < :last_seen_id` — and two columns in the `ORDER BY` clause. You might wonder: why do we need the `id` at all? If we are paginating by `created_at`, why not just use `WHERE created_at < :last_seen_ts`?

The answer lies in a subtle but important data integrity problem called **tie-breaking**. In any sufficiently active social media platform, it is entirely possible — even likely — that multiple posts will share the exact same `created_at` timestamp down to the millisecond. Perhaps a popular event causes a burst of simultaneous posts. Perhaps the application server rounds timestamps in a way that causes collisions.

If you paginate purely by `created_at`, and you have ten posts that all share the exact same timestamp, you have no way to reliably split them across page boundaries. A query like `WHERE created_at < '2024-11-15 09:12:45' LIMIT 20` might include some of those ten simultaneous posts in one page and some in the next, or it might skip some entirely, or it might repeat some. The behaviour is undefined because among equal timestamps, the ordering is arbitrary. Different query executions might order them differently, leading to posts disappearing from the feed or appearing twice.

```
THE TIE-BREAKING PROBLEM

Posts at the exact same timestamp:
  ┌──────────────────────────────────────────────────────┐
  │  Post A: created_at = 2024-11-15 09:12:44.000       │
  │  Post B: created_at = 2024-11-15 09:12:44.000       │
  │  Post C: created_at = 2024-11-15 09:12:44.000       │ ← Three posts,
  │  Post D: created_at = 2024-11-15 09:12:44.000       │   same timestamp
  └──────────────────────────────────────────────────────┘

Without id as tie-breaker:
  Page 1 ends at → created_at = 09:12:44.000
  Page 2 starts with → WHERE created_at < 09:12:44.000
  ⚠️  Posts A, B, C, D all get SKIPPED — none appear on page 2!
  ⚠️  User never sees these 4 posts. They vanish from the feed.

With id as tie-breaker:
  Page 1 ends at → created_at=09:12:44.000, id=8823451 (Post C)
  Page 2 starts with → WHERE created_at < 09:12:44.000
                          OR (created_at = 09:12:44.000 AND id < 8823451)
  ✓  Post D (id=8823449) appears correctly on page 2.
  ✓  No posts skipped. No posts duplicated.
```

By adding `id` as a second sorting column and a second cursor value, you create a globally unique, stable ordering. Since each post has a unique `id`, no two posts can tie on both `created_at` and `id` simultaneously. The composite cursor `(created_at, id)` forms a precise, unambiguous position in the sorted sequence of posts, and pagination across that sequence becomes perfectly reliable.

The composite index `(created_at DESC, id DESC)` is what makes this efficient. The index already stores entries sorted by both columns in sequence, so the database can use a single index range scan to satisfy both the `created_at` condition and the `id` condition in one pass.

## How the Frontend Maintains the Cursor

One practical implication of cursor pagination that engineers sometimes find uncomfortable at first is that the application code must be slightly more aware of the pagination mechanism. With OFFSET pagination, the frontend simply increments a page number, and the backend does the arithmetic. With cursor pagination, the backend must return cursor information to the frontend with each response, and the frontend must store and echo that cursor back on the next request.

In practice, this looks something like the following. The API response for a batch of posts includes not just the posts themselves but also a cursor value — typically the `created_at` timestamp and `id` of the last post in the batch. The frontend stores these values, perhaps in component state or in a session store. When the user scrolls and triggers the next page load, the frontend includes these cursor values as query parameters. The backend uses them as the `WHERE` clause conditions in the keyset query and returns the next batch along with a new cursor pointing to the end of that batch.

```
CURSOR PAGINATION: THE REQUEST/RESPONSE FLOW

Initial load (no cursor):
  Frontend → GET /api/feed
  Backend  → SELECT * FROM posts ORDER BY created_at DESC, id DESC LIMIT 20
  Response → { posts: [...20 posts...], next_cursor: { ts: "2024-11-15T09:12:44", id: 8823451 } }

Second scroll:
  Frontend → GET /api/feed?cursor_ts=2024-11-15T09:12:44&cursor_id=8823451
  Backend  → SELECT * FROM posts WHERE created_at < '2024-11-15T09:12:44'
               AND id < 8823451 ORDER BY created_at DESC, id DESC LIMIT 20
  Response → { posts: [...next 20 posts...], next_cursor: { ts: "2024-11-14T22:05:11", id: 8802341 } }

Third scroll:
  Frontend → GET /api/feed?cursor_ts=2024-11-14T22:05:11&cursor_id=8802341
  ...and so on.

  Each request is O(log N) regardless of scroll depth.
  Each response is exactly 20 rows. Zero waste.
```

This pattern can feel like more bookkeeping compared to simple page numbers, but it is worth it. In fact, many modern APIs — Twitter's timeline API, Facebook's Graph API, GitHub's API — use cursor-based pagination for exactly the same reason. It is the industry-standard approach for any feed or list that needs to scale.

## What Cursor Pagination Sacrifices: The Honest Tradeoffs

No engineering decision is purely positive, and cursor pagination does come with genuine limitations that you should understand clearly before adopting it.

The most significant limitation is that **you cannot jump to an arbitrary page**. With OFFSET pagination, you can implement "jump to page 50" by simply setting `OFFSET 1000`. With cursor pagination, you can only navigate sequentially — forward from the current position to the next batch. You cannot land directly in the middle of a result set because you do not have a cursor for that position without having visited all the preceding positions first. For infinite scroll feeds, this limitation is completely acceptable — users never want to "jump to page 347" of their social feed. But for administrative interfaces where users might want to navigate to a specific page number, OFFSET pagination is sometimes still appropriate despite its performance cost.

The second limitation is that **real-time inserts can cause the cursor to behave unexpectedly** in certain edge cases. If new posts are inserted into the feed between two consecutive page loads — which is common in an active social platform — those new posts will appear at the top of the feed but will not "shift" the cursor. Posts that were below the cursor before the new posts were added will still appear below the cursor in subsequent loads. This means the user sees a stable, consistent view of content from the moment they started scrolling, which is actually the desirable behaviour for infinite scroll. However, for use cases where the user needs to see a perfectly real-time, globally consistent view of the entire dataset, additional complexity is required.

## A Side-by-Side Comparison

To solidify the mental model, here is a direct comparison of both approaches across the dimensions that matter most:

```
OFFSET PAGINATION vs. KEYSET PAGINATION

                        OFFSET              KEYSET (Cursor)
────────────────────────────────────────────────────────────────
Query Cost at page 1:   Fast (read 20)      Fast (read 20)
Query Cost at page 100: Slow (read 2,020)   Fast (read 20)
Query Cost at page 2500:Very slow (50,020)  Fast (read 20)
Cost scales with depth: YES (linear)        NO (constant)
Jump to arbitrary page: YES                 NO
Real-time stable view:  NO (can shift)      YES (stable)
Index effectiveness:    Partial (counts)    Full (seeks)
Duplicate rows on insert:Possible           No
Skipped rows on insert: Possible            No
Implementation effort:  Simple              Moderate

────────────────────────────────────────────────────────────────
```

The table reveals an important nuance: neither approach is universally superior. OFFSET is simpler to implement and supports arbitrary page navigation, making it appropriate for administrative data grids with relatively small datasets and infrequent deep navigation. Keyset pagination is the correct choice for any infinite scroll or feed-style interface where the dataset is large and users may navigate deeply — which describes the vast majority of modern social and content applications.

## The Result: 8,000ms → 3ms, and Constant From There

After the team deployed the keyset pagination implementation, the impact was immediate and complete. The eight-second feed loads for deep scrollers dropped to under three milliseconds. And unlike the OFFSET version, the response time no longer degraded with scroll depth — a user on their first scroll and a user on their ten-thousandth scroll experienced identical response times.

The `EXPLAIN ANALYZE` comparison tells the final story:

```
BEFORE (OFFSET 50000):
  Execution Time: 7,891ms
  Rows processed: 50,020
  Rows returned: 20
  Cost grows with: depth

AFTER (Keyset cursor):
  Execution Time: 2.9ms
  Rows processed: 20
  Rows returned: 20
  Cost grows with: nothing
```

A 2,666-fold improvement. And the improvement is not a one-time thing at this specific depth — it is a permanent architectural guarantee. The system will never again slow down as users engage more deeply with the feed, because the database operation is now completely decoupled from the concept of "how many rows came before this one."

## The Lesson That Stays With You

The OFFSET pagination problem is one of the clearest examples in software engineering of a pattern that appears to work but contains a hidden time bomb. OFFSET feels natural because it maps cleanly to the human concept of pages and page numbers. It is easy to explain, easy to implement, and produces correct results. The flaw is invisible at small scale and catastrophic at large scale, and by the time it manifests in production, the pattern has often been in place for years.

What this case study teaches you — beyond the specific technique of cursor pagination — is to always ask yourself: "What is the database actually doing to execute this operation, and does that cost scale acceptably with my data?" OFFSET scanning fifty thousand rows to return twenty is not a bug. It is exactly what the database is supposed to do when asked. The bug is in the choice of pattern, not the implementation. Understanding the difference between logical intent and physical execution is the foundation of effective database performance engineering.

When you next find yourself implementing pagination for any list or feed, pause and ask the question: "Will users ever scroll deep into this list? Will this dataset grow?" If the answer to either is yes, cursor pagination is almost certainly the right choice, even if it requires more implementation effort. The work you invest now saves your users from waiting, your database from suffering, and your team from emergency on-call incidents at three in the morning.

## Summary

This case study examines one of the most pervasive and avoidable performance failures in web application development. An infinite scroll feed on a social platform used OFFSET-based pagination, which requires the database to read and discard every row preceding the requested page on every single request. At a scroll depth of fifty thousand rows, this meant processing fifty thousand rows to return twenty — a 0.04% efficiency ratio, resulting in eight-second response times for deeply engaged users.

The fix was to adopt keyset pagination, also called cursor pagination. By replacing `OFFSET N` with a `WHERE` clause that anchors to the last-seen row using a composite cursor of `(created_at, id)`, the database can use its index to jump directly to the correct starting position without scanning or discarding any preceding rows. The number of rows processed is now always exactly twenty, regardless of how deep into the feed the user has scrolled. Response time dropped from eight thousand milliseconds to three milliseconds — a 2,666-fold improvement — and, more importantly, performance is now constant and will remain so as both the dataset and user engagement grow without limit.

The principle to carry forward is this: OFFSET pagination trades simplicity of implementation for a cost that grows linearly with depth, while keyset pagination trades a small increase in implementation complexity for guaranteed constant-time performance at any depth. For any feed, timeline, or list that users can scroll into deeply, cursor pagination is not an optimisation — it is a necessity.
