# The OR That Blinded Both Eyes: How Splitting a Search Query Into UNION ALL Unlocked Two Indexes at Once

> _"An OR condition in a WHERE clause can be thought of as asking the database to look in two different places simultaneously. But a database engine, like a person, cannot look in two different places at once — so it often gives up and reads everything instead. UNION ALL gives it permission to look in each place separately, one after the other, using the most efficient tool available for each."_

---

## Setting the Scene

You are a backend engineer at an e-commerce company that sells office supplies and electronics. The product catalogue contains five million products, each identified by a unique barcode and described by a name. The search feature on the website allows users to find products in two different ways: by typing part of a product's name (a fuzzy text search), or by typing an exact barcode if they have one from a physical label or a receipt.

Both search modes are used regularly. A procurement manager might type "wireless keyboard" to find all wireless keyboards. A warehouse worker with a barcode scanner might scan a product label and paste the resulting number directly into the search bar to look up that specific product instantly.

The original search query was written to handle both cases in a single, elegant SQL statement:

```sql
SELECT *
FROM products
WHERE name ILIKE '%keyboard%'
   OR barcode = '123456789';
```

The `ILIKE` operator performs a case-insensitive text match, and the `%` wildcards on both sides of the search term allow it to match any product whose name contains the word "keyboard" anywhere within it. The `barcode` comparison is a straightforward exact match. The `OR` between them means: return a product if it matches either condition.

For months, this worked acceptably when the products table was small — a few hundred thousand rows. But as the catalogue grew to five million products, the search began degrading. Users typing in the search box experienced a twenty-second wait before results appeared. The feature was becoming unusable. The product team filed a critical bug, and the search is assigned to you.

You run `EXPLAIN ANALYZE` on the query and see something that immediately tells you what is wrong:

```
Seq Scan on products  (cost=0.00..2250000.00 rows=1250 width=420)
                      (actual time=0.021..19834.334 rows=8 loops=1)
  Filter: (((name)::text ~~* '%keyboard%'::text) OR (barcode = '123456789'::text))
  Rows Removed by Filter: 4999992

Planning Time: 0.4 ms
Execution Time: 19,876 ms
```

`Seq Scan`. `Rows Removed by Filter: 4,999,992`. The database read every single one of the five million rows in the products table, evaluated both conditions for each one, and returned eight matching products. Nearly twenty seconds to find eight rows. Your senior engineer takes one look at this and says: _"The OR is the problem. It is forcing the planner to abandon both indexes and read the entire table. We need to teach the query to use each index independently."_

## Understanding Why OR Defeats Index Usage

To understand why the `OR` operator causes the database to abandon indexes and fall back to a sequential scan, you need to understand how indexes work at a fundamental level and what constraint they impose on query execution.

An index on a column — say, an index on `barcode` — allows the database to quickly locate all rows where `barcode` equals a specific value. It is a sorted, pre-built lookup structure. Given the value `'123456789'`, the database traverses the index in logarithmic time and finds the matching row almost instantly. The index is usable because the query can be expressed as a precise, bounded range lookup: "find all index entries where the key equals this value."

A GIN index on a `tsvector` or with `pg_trgm` on the `name` column similarly allows efficient text search — it maintains an inverted index mapping word fragments or trigrams to the rows that contain them. Given the search term `'keyboard'`, the index can quickly identify which row IDs contain that trigram pattern.

Now consider what happens when you combine these two conditions with `OR`. The database must return a row if **either** condition is true. This creates a logical union: the result should be the union of (rows matching the barcode) and (rows matching the name pattern). In theory, the database could execute both index lookups independently and then merge the results — this is called a **Bitmap OR** strategy, where the database uses two bitmap scans and ORs the resulting bitmaps together.

PostgreSQL does support Bitmap OR scans in certain situations. However, this strategy breaks down when the two conditions use fundamentally different kinds of indexes that cannot be combined in a bitmap operation. Specifically, a standard B-Tree index on `barcode` and a GIN trigram index on `name` produce incompatible bitmap structures. The planner cannot OR them together effectively. Faced with this incompatibility, and particularly faced with a leading wildcard pattern (`%keyboard%`) which even a trigram index can only partially help with, the planner makes a fatalistic choice: if it cannot use both indexes together, it uses neither, and falls back to a sequential scan of the entire table.

```
WHY OR DEFEATS BOTH INDEXES

  The query: WHERE name ILIKE '%keyboard%' OR barcode = '123456789'

  Index 1: GIN trigram index on name
           Can find rows containing 'keyboard'
           ┌──────────────────────────────────────┐
           │ 'key' → rows: {12, 45, 891, 2341...} │
           │ 'eyb' → rows: {12, 45, 891...}       │
           │ 'ybo' → rows: {12, 45, 891...}        │
           └──────────────────────────────────────┘
           Result: row IDs matching name pattern

  Index 2: B-Tree index on barcode
           Can find rows where barcode = '123456789'
           ┌──────────────────────────────────────┐
           │ '123456789' → row: {8823}            │
           └──────────────────────────────────────┘
           Result: row IDs matching barcode

  The problem: How do you OR these together?
  ┌─────────────────────────────────────────────────────────┐
  │  GIN result:    {12, 45, 891, 2341, 8823, ...}          │
  │  B-Tree result: {8823}                                  │
  │  OR together:   {12, 45, 891, 2341, 8823, ...}          │
  │                                                         │
  │  PostgreSQL cannot efficiently bitmap-OR a GIN result   │
  │  with a B-Tree result for this query shape.             │
  │                                                         │
  │  Planner's decision: give up on both indexes,           │
  │  do a full sequential scan instead.                     │
  └─────────────────────────────────────────────────────────┘

  → 5,000,000 rows read, 4,999,992 discarded, 20 seconds wasted.
```

This failure mode is particularly insidious because the solution — separating the conditions with `OR` — seems like exactly the right way to express "match either of these two things." The logic is correct. The performance consequence is invisible at small scale and catastrophic at large scale.

## A Deeper Look: The GIN Index and Text Search

The `name ILIKE '%keyboard%'` condition deserves special attention because its leading wildcard (`%keyboard%` rather than `keyboard%`) makes it fundamentally harder to index than a trailing-only wildcard. Understanding this helps explain why the OR situation is so problematic.

A standard B-Tree index on a text column can support prefix searches — queries like `name ILIKE 'key%'` that match strings starting with a known prefix. The index is sorted alphabetically, so the database can jump directly to the first name starting with "key" and scan forward. But a leading wildcard — `'%keyboard%'` — means the matching substring can appear anywhere in the name, not just at the start. A standard B-Tree index cannot help with this at all, because "flying keyboard stand" starts with "flying", not "keyboard", and would not be adjacent to "keyboard USB hub" in an alphabetically sorted index.

The appropriate index for containment searches on text is a **GIN index with the `pg_trgm` extension** (trigram index). A trigram index breaks every text value into all possible three-character substrings (trigrams) and builds an inverted index mapping each trigram to the rows containing it. To find all names containing "keyboard", the database computes the trigrams of "keyboard" (`'key'`, `'eyb'`, `'ybo'`, `'oar'`, `'ard'`), looks each one up in the GIN index, finds the row sets containing all those trigrams, intersects them, and retrieves the matching rows. This is fast even for leading-wildcard patterns.

```
TRIGRAM INDEX — How GIN finds '%keyboard%'

  'keyboard' broken into trigrams:
  k-e-y = 'key'
  e-y-b = 'eyb'
  y-b-o = 'ybo'
  b-o-a = 'boa'
  o-a-r = 'oar'
  a-r-d = 'ard'

  GIN index lookup (intersection):
  rows containing 'key': {12, 45, 891, 2341, 8823, 15000, ...}
  rows containing 'eyb': {12, 45, 891, 2341, 8823, ...}
  rows containing 'ybo': {12, 45, 891, 2341, 8823, ...}
  rows containing 'boa': {12, 45, 891, 2341, ...}
  ...

  Intersection of all trigram sets: {12, 45, 891, 2341, ...}
  ↑ These are the product rows whose names contain 'keyboard'

  Efficient even for leading-wildcard ILIKE — but only
  when used ALONE, without an OR to a different index.
```

The GIN trigram index is a powerful tool. The B-Tree barcode index is also a powerful tool. The problem is that the `OR` prevents either from being used, because the planner cannot efficiently combine their outputs.

---

## The Solution: UNION ALL Gives Each Branch Its Own Index

The fix is to decompose the single `OR` query into two separate queries, each targeting exactly one search condition, and then combine their results using `UNION ALL`:

```sql
-- Branch 1: Exact barcode match (uses B-Tree index on barcode)
SELECT *
FROM products
WHERE barcode = '123456789'

UNION ALL

-- Branch 2: Name text search (uses GIN trigram index on name)
--           excluding any row already found by the barcode search
SELECT *
FROM products
WHERE name ILIKE '%keyboard%'
  AND barcode != '123456789';
```

Notice the `AND barcode != '123456789'` condition on the second branch. This is a critical detail: it prevents rows that match **both** conditions from appearing twice in the result. If a product named "Keyboard 123456789 Edition" happened to have barcode `'123456789'` and also matched the name search, it would appear in both branches without this exclusion. The `AND barcode != '123456789'` ensures the second branch only captures rows not already captured by the first.

The `UNION ALL` operator combines the results of both branches without any deduplication — it simply appends the second result set after the first. This is why the exclusion on the second branch is necessary: `UNION ALL` trusts you to ensure no duplicates arise, which is more efficient than `UNION`, which would sort and deduplicate all combined rows after the fact.

## Why UNION ALL Unlocks Both Indexes

The reason this rewrite is so dramatically faster comes down to a fundamental change in how the query planner sees the problem. With the `OR` version, the planner must satisfy a single condition that requires reading from two different index structures and combining their results — a combination it cannot do efficiently. With `UNION ALL`, the planner sees **two completely independent queries**, each of which it can optimise entirely on its own.

For the first branch — `WHERE barcode = '123456789'` — the planner sees a simple equality condition on an indexed column. It immediately and confidently chooses an `Index Scan` on the barcode B-Tree index. The lookup is O(log N), finds at most one or a handful of rows, and completes in well under a millisecond.

For the second branch — `WHERE name ILIKE '%keyboard%' AND barcode != '123456789'` — the planner sees a trigram text search combined with an inequality filter. It chooses a `Bitmap Index Scan` using the GIN trigram index for the name condition, fetches the matching rows from the heap, applies the `barcode !=` filter, and returns the result. The GIN index narrows the search from five million rows down to perhaps a few dozen keyboard-related products, and the subsequent heap fetch is small.

```
UNION ALL EXECUTION — Each branch uses its own optimal index

Branch 1: WHERE barcode = '123456789'
  ┌─────────────────────────────────────────────────────────┐
  │  Index Scan on idx_products_barcode                     │
  │  Index Cond: (barcode = '123456789')                    │
  │  Rows read: 1  (B-Tree finds exact match instantly)     │
  │  Time: < 1ms                                            │
  └─────────────────────────────────────────────────────────┘
                        ║
                        ║  UNION ALL (append results)
                        ║
Branch 2: WHERE name ILIKE '%keyboard%' AND barcode != '123456789'
  ┌─────────────────────────────────────────────────────────┐
  │  Bitmap Index Scan on idx_products_name_trgm (GIN)      │
  │  Recheck Cond: (name ILIKE '%keyboard%')                │
  │  Filter: (barcode != '123456789')                       │
  │  Rows read from index: ~45 (trigram intersection)       │
  │  Rows after filter: 7                                   │
  │  Time: ~99ms                                            │
  └─────────────────────────────────────────────────────────┘
                        ║
                        ▼
  Combined result: 8 products
  Total time: ~100ms

  Neither branch reads the full 5,000,000-row table.
  Each uses the most powerful index available for its condition.
```

The total work is the sum of two fast, index-powered operations, rather than one slow sequential scan. The planner has been given the freedom to optimise each sub-query independently, and it does so correctly and efficiently.

## The EXPLAIN ANALYZE Comparison

Running `EXPLAIN ANALYZE` on both versions makes the contrast definitive. The original `OR` version:

```
Seq Scan on products  (cost=0.00..2250000.00 rows=1250 width=420)
                      (actual time=0.021..19834.334 rows=8 loops=1)
  Filter: (((name)::text ~~* '%keyboard%'::text) OR
           (barcode = '123456789'::text))
  Rows Removed by Filter: 4,999,992

Execution Time: 19,876 ms
```

Every signal in this output is bad: `Seq Scan` means the table was read top to bottom. `Rows Removed by Filter: 4,999,992` means 99.9998% of all rows read were discarded. The query returned eight rows after reading five million.

The rewritten `UNION ALL` version:

```
Append  (cost=0.57..48.23 rows=18 width=420)
        (actual time=0.041..99.334 rows=8 loops=1)
  ->  Index Scan using idx_products_barcode on products
      (cost=0.57..8.59 rows=1 width=420)
      (actual time=0.038..0.041 rows=1 loops=1)
        Index Cond: (barcode = '123456789'::text)
  ->  Bitmap Heap Scan on products
      (cost=20.34..39.64 rows=17 width=420)
      (actual time=12.334..99.221 rows=7 loops=1)
        Recheck Cond: ((name)::text ~~* '%keyboard%'::text)
        Filter: (barcode <> '123456789'::text)
        Rows Removed by Filter: 0
        ->  Bitmap Index Scan on idx_products_name_trgm
            (cost=0.00..20.30 rows=45 width=0)
            (actual time=12.112..12.112 rows=45 loops=1)
              Index Cond: ((name)::text ~~* '%keyboard%'::text)

Execution Time: 99.7 ms
```

The `Seq Scan` is completely gone. In its place are an `Index Scan` (for the barcode lookup — the fastest possible access pattern) and a `Bitmap Heap Scan` backed by a `Bitmap Index Scan on idx_products_name_trgm` (for the text search). The `Rows Removed by Filter` in the second branch is zero — the GIN index delivered exactly the right rows and nothing was wasted. Execution time: 99.7 milliseconds.

## Understanding the UNION vs UNION ALL Choice

The choice of `UNION ALL` rather than `UNION` is not accidental, and the distinction deserves careful explanation because confusing the two is a common mistake with significant performance consequences.

`UNION` combines two result sets and removes duplicates from the combined output. To remove duplicates, the database must sort or hash the entire combined result and eliminate repeated rows. This is an extra step that takes time proportional to the size of the combined result. It is the `DISTINCT` problem applied to set combination.

`UNION ALL` combines two result sets and returns all rows from both, including any duplicates, without any deduplication step. It is simply an append operation — take all rows from the first result, then all rows from the second result, and return them together. This is O(N + M) where N and M are the sizes of the two result sets — no sorting, no hashing, no extra memory.

In the rewritten search query, we used `UNION ALL` because we deliberately prevented duplicates by adding `AND barcode != '123456789'` to the second branch. The two branches are mutually exclusive by construction — a row can appear in the first branch (matching the barcode exactly) or in the second branch (matching the name but having a different barcode), but it cannot appear in both. Given this guarantee, `UNION ALL` is both correct and optimal.

```
UNION vs UNION ALL

UNION:
  Branch 1 result: [row A, row B, row C]
  Branch 2 result: [row B, row D, row E]  ← row B is a duplicate
  Combined:        [row A, row B, row C, row D, row E]
  UNION deduplicates → sorts all combined rows → emits unique ones
  Cost: O((N+M) log(N+M))  — sort of the combined result

UNION ALL:
  Branch 1 result: [row A, row B, row C]
  Branch 2 result: [row D, row E]          ← no duplicates by design
  Combined:        [row A, row B, row C, row D, row E]
  UNION ALL appends → no sort, no dedup
  Cost: O(N+M)  — pure append, nothing discarded

  Using UNION where UNION ALL suffices adds a sort cost for no benefit.
  Using UNION ALL where UNION is needed produces incorrect duplicate rows.

  The correct choice depends on whether you have guaranteed
  that no row can appear in both branches simultaneously.
```

When rewriting `OR` to `UNION ALL`, your primary responsibility is to ensure the branches are mutually exclusive. The most common way to do this is to add an exclusion condition to all branches except the first — each subsequent branch excludes rows already captured by earlier branches. Alternatively, if the conditions are naturally mutually exclusive (e.g., `WHERE status = 'active'` and `WHERE status = 'pending'` — a row cannot be both active and pending), no additional exclusion conditions are needed.

## When OR Can Be Handled by the Planner: Bitmap OR

Before you rush to rewrite every `OR` query as `UNION ALL`, it is important to understand when the planner is capable of handling `OR` efficiently on its own, because sometimes the rewrite is unnecessary.

PostgreSQL supports a strategy called **Bitmap OR** that can use two indexes simultaneously for OR conditions, provided both conditions are expressed as index scans over the same kind of index (typically both B-Tree). The planner performs two separate `Bitmap Index Scan` operations, produces two bitmap arrays of matching row IDs, ORs the bitmaps together, and then fetches the corresponding heap rows using the combined bitmap.

This works well when both conditions use B-Tree indexes on different columns of the same table:

```sql
-- The planner CAN use Bitmap OR for this:
SELECT * FROM products
WHERE barcode = '123456789'
   OR sku = 'KBD-001';
-- (assuming B-Tree indexes on both barcode and sku)
```

The Bitmap OR strategy breaks down in two situations. First, when the index types are incompatible — a GIN index and a B-Tree index cannot be combined in a bitmap OR because their internal bitmap representations are different. Second, when one of the conditions involves a sequential scan anyway — a leading-wildcard `ILIKE` on a column without a trigram index would force a sequential scan for that branch, and ORing a sequential scan with an index scan is pointless.

```
WHEN THE PLANNER CAN USE BITMAP OR (no rewrite needed)

  WHERE col_A = value1 OR col_B = value2
  (both using B-Tree indexes → Bitmap OR works)

  ┌────────────┐   OR   ┌────────────┐
  │ Bitmap Scan│        │ Bitmap Scan│
  │ on idx_A   │        │ on idx_B   │
  └─────┬──────┘        └─────┬──────┘
        │                     │
        └──────── OR ──────────┘
                  │
         Bitmap Heap Scan

  Planner handles this automatically. No UNION ALL needed.

WHEN UNION ALL IS NEEDED

  WHERE col_A ILIKE '%text%' OR col_B = value2
  (GIN + B-Tree → incompatible for Bitmap OR)
  → Planner falls back to Seq Scan
  → Manual UNION ALL rewrite required
```

The practical diagnostic is simple: run `EXPLAIN` on your `OR` query. If you see `Seq Scan` and `Rows Removed by Filter` on a large table, the planner has given up on indexes and the `UNION ALL` rewrite is warranted. If you see `Bitmap Index Scan` and `BitmapOr` nodes, the planner is handling it efficiently and no rewrite is needed.

## A Practical Guide to the UNION ALL Rewrite Pattern

The pattern for rewriting an `OR` query to `UNION ALL` follows a consistent structure once you have seen it a few times. The goal is always the same: give each condition its own query branch, ensure mutual exclusivity between branches, and combine with `UNION ALL`.

For a two-condition OR, the pattern is:

```sql
-- Original (OR forcing Seq Scan):
SELECT cols FROM table WHERE conditionA OR conditionB;

-- Rewritten (UNION ALL, branches mutually exclusive):
SELECT cols FROM table WHERE conditionA
UNION ALL
SELECT cols FROM table WHERE conditionB AND NOT (conditionA);
```

For a three-condition OR, the pattern extends naturally:

```sql
-- Original:
SELECT cols FROM table WHERE condA OR condB OR condC;

-- Rewritten:
SELECT cols FROM table WHERE condA
UNION ALL
SELECT cols FROM table WHERE condB AND NOT condA
UNION ALL
SELECT cols FROM table WHERE condC AND NOT condA AND NOT condB;
```

Each branch captures rows that match its condition but do not match any earlier branch. This guarantees the branches are mutually exclusive and `UNION ALL` produces a correct, duplicate-free result.

In the specific case of the search query, the pattern is clean because the barcode is an exact match that produces at most one row. Including `AND barcode != '123456789'` in the name search branch is a trivially cheap check that a B-Tree index satisfies almost for free.

## The Broader Principle: Index-Unfriendly Operators and Query Shapes

The `OR` problem is part of a broader category of query shapes that prevent effective index use. Understanding the broader category helps you recognise similar problems in other contexts.

Any query shape that requires the database to consider more than one "access path" simultaneously — that is, to look up rows from two or more different locations in the index structure and combine the results — is a candidate for this kind of breakdown. The database engine optimises each query to use a single access path (or a small, compatible set of paths), and when the query shape does not permit a single clean access path, it falls back to a sequential scan.

Other examples of index-unfriendly query shapes include: using `OR` between conditions on columns in different tables (requires cross-table index combination, which is never possible); using negation operators (`!=`, `NOT IN`, `NOT LIKE`) as the primary filter (indexes are not useful for "everything except this", which is almost all rows); and using functions on indexed columns in the `WHERE` clause (`WHERE YEAR(created_at) = 2024` prevents the index on `created_at` from being used, because the index stores `created_at` values, not `YEAR(created_at)` values).

The `UNION ALL` rewrite specifically addresses the `OR`-across-incompatible-indexes problem. For the other patterns, different rewrites apply — using `>= DATE` and `< DATE` instead of `YEAR()` functions, using `EXISTS` or `IN` instead of `NOT IN`, and so on. The common thread is: understand what shape your query needs to be in for the database to use an index, and write it in that shape.

## The Result: 20,000ms → 100ms

After the search query was rewritten using `UNION ALL`, the five-second search page load dropped to something imperceptible. Users typing in the search box saw results appear in under a hundred milliseconds — fast enough to feel like the results were being filtered in real time as they typed.

```
BEFORE — OR with Seq Scan:
  Access method:         Sequential Scan (no indexes used)
  Rows read:             5,000,000
  Rows returned:         8
  Wasted row reads:      4,999,992 (99.9998% waste)
  Disk I/O:              Full table scan (~2GB read)
  Execution time:        19,876ms (20 seconds)

AFTER — UNION ALL with per-branch index usage:
  Branch 1: Index Scan on barcode  → 1 row, <1ms
  Branch 2: Bitmap Scan via GIN    → 7 rows, ~99ms
  Total rows read from index:      46 (45 + 1)
  Total rows returned:             8
  Disk I/O:                        Minimal (index pages only)
  Execution time:                  99ms

  Improvement: 19,876ms ÷ 99ms = 201× faster
  Rows read reduction: 5,000,000 → 46 (99.999% reduction)
```

The 201-fold improvement comes entirely from index utilisation. The same data, the same answer, the same five million rows in the products table — but the database now touches only 46 of them instead of all five million.

## The Lesson That Stays With You

The `OR` operator is one of SQL's most deceptively dangerous tools for performance. It reads naturally — "match this, or match that" — and its logical correctness is unimpeachable. But when the two conditions it combines require different indexes to evaluate efficiently, the database planner faces a combinatorial problem it often cannot solve elegantly, and it retreats to the safety of a sequential scan.

The mental model to carry with you is this: when you write `OR` in a `WHERE` clause, ask yourself whether both conditions can be served by the same index access path, or whether they each need their own index. If they can share one path, the planner will handle it correctly. If they need separate paths — particularly when one involves a GIN text index and the other involves a B-Tree equality index — consider whether `UNION ALL` would give each condition the clean, independent optimisation opportunity it deserves.

`UNION ALL` is not a workaround for a broken feature. It is a precise, intentional instruction to the query planner: "these are two independent search strategies, each optimised for its own access path — execute them separately and combine the results." When the question you are asking genuinely has two independent search dimensions, `UNION ALL` is the most honest and most efficient way to express it.

## Summary

This case study examines a product search query that used `OR` to combine a text search condition (`name ILIKE '%keyboard%'`) with an exact barcode lookup (`barcode = '123456789'`). The `OR` prevented the query planner from using either the GIN trigram index on `name` or the B-Tree index on `barcode`, because the two index types cannot be efficiently combined in a bitmap OR operation. Forced to abandon both indexes, the planner fell back to a sequential scan of five million rows, reading and discarding 99.9998% of them to return eight matching products — a process taking twenty seconds.

The fix was to decompose the single OR query into two `UNION ALL` branches: the first containing only the barcode equality condition, allowing the planner to use an `Index Scan` on the B-Tree barcode index; the second containing only the name text search condition with an additional `AND barcode != '123456789'` to prevent duplicates, allowing the planner to use a `Bitmap Index Scan` on the GIN trigram index. Each branch used its own optimal index independently. Execution time dropped from 19,876 milliseconds to 99 milliseconds — a 201-fold improvement — and rows read by the database dropped from five million to forty-six.

The principle is: `OR` across conditions that require incompatible indexes forces the planner to abandon both indexes and perform a sequential scan. `UNION ALL` gives each condition its own optimisation context, allowing each branch to use its own index without interference from the others. When `EXPLAIN ANALYZE` shows a `Seq Scan` on a large table where each individual `OR` condition should be indexable, `UNION ALL` is the rewrite to consider. Ensure the branches are mutually exclusive to avoid duplicates, and use `UNION ALL` — not `UNION` — to avoid an unnecessary deduplication sort.
