# The Filter That Arrived After the Flood: How Pushing a WHERE Clause Inside a Subquery Cut a 3-Minute Query to 8 Seconds

> _"Filtering data is always cheaper before a join than after one. A join multiplies rows. A filter reduces them. The order in which you apply these two operations — reduce then multiply, or multiply then reduce — is one of the most consequential decisions in all of query design."_

---

## Setting the Scene

You have just joined an analytics platform team at a large e-commerce company. The platform serves internal analysts and data scientists who run complex reports over the company's transactional data — reports about order trends, product performance, customer behaviour, and operational metrics. The data lives in a normalized relational schema: an `orders` table, an `order_items` table, a `products` table, a `customers` table, and several others.

One of the most important reports on the platform is the "2024 Order Line Item Analysis" — a report that joins order data with their individual line items to produce a per-item breakdown of sales in the year 2024. Analysts run this report every morning. It was built six months ago when the data volume was manageable, and it ran in about twenty seconds then. But as the company's order volume has grown, the report has slowed dramatically. Now it takes over three minutes, and analysts have started filing complaints — "the morning report is broken," "I can't start my day until this loads," "we need to fix this."

You pull up the query that drives the report. At first glance it looks reasonable — a subquery that joins orders and order items, wrapped in an outer query that filters and selects. But after a few seconds of reading it carefully, you begin to feel the unease of a doctor recognising a familiar symptom pattern:

```sql
SELECT
    sub.order_id,
    sub.customer_id,
    sub.product_id,
    sub.quantity,
    sub.unit_price,
    sub.line_total,
    sub.created_at
FROM (
    SELECT
        o.id         AS order_id,
        o.customer_id,
        o.created_at,
        oi.product_id,
        oi.quantity,
        oi.unit_price,
        oi.quantity * oi.unit_price AS line_total
    FROM orders o
    JOIN order_items oi ON o.id = oi.order_id
) sub
WHERE sub.created_at > '2024-01-01';
```

The filter `WHERE sub.created_at > '2024-01-01'` sits in the outer query. The subquery performs the join with no filtering at all. You run `EXPLAIN ANALYZE` and the output confirms what you feared: the join produces five hundred million rows, and the filter reduces them to ten million afterward. The five hundred million row intermediate result is where the three minutes are being spent.

Your senior engineer leans over and says: _"The filter is arriving after the flood. We need to move it inside — filter first, join second. Let the river narrow before it meets the dam, not after."_

---

## Understanding the Query Structure: Inside-Out Evaluation

To understand why the filter placement matters so much, you need to understand how the database evaluates nested queries — the relationship between the subquery and the outer query, and what each one sees when it runs.

A subquery in the `FROM` clause — also called a **derived table** or **inline view** — is conceptually evaluated first, producing a result set that the outer query then operates on. The outer query cannot "reach inside" the subquery's logic and influence how it runs — it only receives the subquery's output as its input. This means that if the subquery produces five hundred million rows, the outer query starts with five hundred million rows, regardless of how selective the outer `WHERE` clause is.

Think of it as a pipeline: water flows in one direction, from the innermost part of the query outward. The subquery is the first stage of the pipeline, producing its output. The outer query is the second stage, receiving that output and applying further processing. A filter placed in the second stage does not help the first stage produce less — the first stage runs fully regardless, and delivers its entire output before the second stage discards most of it.

```
QUERY EVALUATION ORDER — Where the data flows

  Outer query:
    SELECT sub.order_id, sub.customer_id, ...
    FROM ( ← subquery result enters here
        [subquery]
    ) sub
    WHERE sub.created_at > '2024-01-01'  ← filter applied HERE (too late)

  Execution order:
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 1: Execute subquery                                    │
  │         FROM orders o JOIN order_items oi ON o.id = oi.id  │
  │         → Produces: 500,000,000 rows                        │
  │         → Memory/disk consumed: ~100 GB                     │
  │         → Time: ~2.5 minutes                               │
  │                                                             │
  │ Step 2: Apply outer WHERE filter to subquery result         │
  │         WHERE sub.created_at > '2024-01-01'                 │
  │         → 500M rows evaluated, 490M discarded               │
  │         → Keeps: 10,000,000 rows                            │
  │         → Time: ~30 seconds                                 │
  └─────────────────────────────────────────────────────────────┘

  Total: 3 minutes to return 10 million rows from 500 million processed.
  The filter that could have prevented most of this work
  arrived only after 500 million rows were already created.
```

The join between `orders` and `order_items` operates on the full, unfiltered orders table. The `orders` table contains five hundred million rows representing several years of order history. The `order_items` table is even larger — perhaps two billion rows, since each order has multiple items. The join between these two tables at full scale produces an enormous intermediate result that must be materialised in memory or spilled to disk before the outer `WHERE` clause can evaluate it.

## The Cost of Joining Before Filtering: A Mathematical Perspective

The scale of the waste becomes quantifiable when you think about what the join is doing before the filter arrives. The `orders` table has five hundred million rows. Of those, approximately ten million were created after 2024-01-01 — the ones the filter actually wants. The other four hundred and ninety million rows, representing years of historical orders, are irrelevant to the query.

But the join does not know this. The join between `orders` and `order_items` matches every order — all five hundred million of them — with their corresponding order items. A typical order has three to five line items, so the join produces roughly one-and-a-half to two-and-a-half billion rows. Then the outer filter reduces this to approximately thirty to fifty million rows (the 2024 orders, each with their line items).

```
THE JOIN SIZE EXPLOSION — Before and After Filtering

Without filter (current query — filter applied after join):

  orders: 500,000,000 rows (all years)
       × avg 3-5 items per order
  ────────────────────────────────────────────────────
  Join result: ~1,500,000,000 to 2,500,000,000 rows   ← ENORMOUS

  Then outer filter: keep only 2024 orders
  Final result: ~30,000,000 to 50,000,000 rows

  Work done: 2 billion rows joined
  Work kept: 30-50 million rows
  Rows discarded: ~95%

With filter pushed in (filter applied before join):

  orders: 500,000,000 rows
  Apply WHERE created_at > '2024-01-01' → 10,000,000 rows remain

  10,000,000 filtered orders
       × avg 3-5 items per order
  ────────────────────────────────────────────────────
  Join result: ~30,000,000 to 50,000,000 rows         ← MANAGEABLE

  Work done: 30-50 million rows joined
  Work kept: 30-50 million rows
  Rows discarded: 0% (none wasted)

  Join size reduction: 2,000,000,000 → 40,000,000 rows = 50× less work
```

By moving the filter before the join, the join input is reduced from five hundred million rows to ten million — a fifty-fold reduction. A join on ten million rows produces thirty to fifty million rows in the result. A join on five hundred million rows produces one and a half to two and a half billion rows. The difference in compute, memory, and disk I/O is dramatic.

## The Solution: Moving the Filter Inside the Subquery

The fix is elegantly simple. Move the `WHERE created_at > '2024-01-01'` condition from the outer query into the subquery, so that the filter is applied to the `orders` table before the join happens:

```sql
SELECT
    sub.order_id,
    sub.customer_id,
    sub.product_id,
    sub.quantity,
    sub.unit_price,
    sub.line_total,
    sub.created_at
FROM (
    SELECT
        o.id         AS order_id,
        o.customer_id,
        o.created_at,
        oi.product_id,
        oi.quantity,
        oi.unit_price,
        oi.quantity * oi.unit_price AS line_total
    FROM orders o
    JOIN order_items oi ON o.id = oi.order_id
    WHERE o.created_at > '2024-01-01'   -- ← Filter moved inside
) sub;
```

The outer `WHERE` clause is removed entirely. The filter now lives inside the subquery, applied directly to the `orders` table before the join with `order_items` runs. This means the join operates on ten million rows instead of five hundred million, and the intermediate result is fifty times smaller.

With an index on `orders.created_at`, the planner can use an **Index Range Scan** to retrieve only the 2024 orders directly, without reading the other four hundred and ninety million historical order rows at all. The join then runs on this pre-filtered set, producing a result that is small enough to fit comfortably in memory and return quickly.

```
FIXED QUERY EXECUTION — Filter first, then join

  Step 1: Apply filter to orders (inside subquery)
          WHERE o.created_at > '2024-01-01'
          Index scan on idx_orders_created_at
          → Reads: 10,000,000 rows (only 2024 orders)
          → Skips: 490,000,000 rows (never touched)
          → Time: ~1 second

  Step 2: Join 10M filtered orders with order_items
          10,000,000 orders × avg 4 items = ~40,000,000 join result rows
          → Fits in memory (no disk spill)
          → Time: ~6 seconds

  Step 3: Outer SELECT (trivial, no further filtering needed)
          → Time: < 1 second

  Total: ~8 seconds
  Before: ~180 seconds (3 minutes)
  Improvement: 180s ÷ 8s = 22.5×
```

## Why Doesn't the Planner Fix This Automatically? Predicate Pushdown

At this point, a natural and important question arises: if moving the filter inside the subquery is so clearly better, why doesn't the query planner do it automatically? This is not a rhetorical question — the answer teaches you something important about the limits of automated optimization and when manual intervention is necessary.

Database query planners implement a technique called **predicate pushdown** — automatically moving filter conditions from outer query levels into inner subqueries or derived tables to reduce intermediate result sizes. Modern PostgreSQL does perform predicate pushdown in many cases, and in fact, for simple subqueries, the planner will often perform this optimisation automatically, making the location of the filter in your SQL text irrelevant to performance.

The key phrase is "in many cases." Predicate pushdown is limited by a set of conditions. The planner can push a predicate inside a subquery when the subquery is a simple `SELECT ... FROM ... WHERE ...` or `SELECT ... JOIN ...` without any `GROUP BY`, `HAVING`, `DISTINCT`, `LIMIT`, `WINDOW`, or `SET` operations. These operations change the semantics of predicate pushdown — moving a filter past a `GROUP BY` or `DISTINCT` is not always semantically equivalent, so the planner conservatively refuses to do it.

In the case of our query, the planner may have inlined the subquery and pushed the filter down automatically — or it may not have, depending on the subquery's complexity, the presence of other features, or whether CTE materialization was in effect. The `EXPLAIN ANALYZE` output showing `Rows Removed by Filter: 490,000,000` on a sequential scan tells us definitively that, in this case, the planner did not push the filter. Whether due to a complex subquery structure, stale statistics, or a subtle semantic concern, the filter remained late.

```
WHEN THE PLANNER PUSHES PREDICATES AUTOMATICALLY

  Simple subquery (planner CAN push):
  SELECT * FROM (SELECT * FROM orders) sub
  WHERE sub.created_at > '2024-01-01'
  → Planner rewrites to: SELECT * FROM orders WHERE created_at > '2024-01-01'
  → Predicate pushed, filter applied early. OK.

  Subquery with GROUP BY (planner CANNOT safely push):
  SELECT * FROM (
      SELECT customer_id, SUM(amount) AS total
      FROM orders
      GROUP BY customer_id
  ) sub
  WHERE sub.total > 1000
  → Cannot move WHERE total > 1000 inside the GROUP BY
    (total doesn't exist until after aggregation)
  → Filter must stay outside. Planner cannot help.

  Subquery with JOIN across multiple tables (planner MAY push):
  SELECT * FROM (
      SELECT o.*, oi.*
      FROM orders o JOIN order_items oi ON o.id = oi.order_id
  ) sub
  WHERE sub.created_at > '2024-01-01'
  → Planner might push, might not — depends on statistics,
    complexity, version, and other factors.
  → EXPLAIN ANALYZE is the only way to know for certain.
  → If it doesn't push: move the filter manually.
```

The lesson is not to rely on the planner to push predicates correctly in complex queries. The planner is a powerful optimizer, but its predicate pushdown has limits, and complex multi-join subqueries are precisely where those limits are most likely to be reached. Writing the filter in the correct position manually — inside the subquery, before the join — removes all ambiguity and guarantees early filtering regardless of what the planner decides.

## The Filter-First Principle: A Generalised Design Rule

The specific fix in this case study is an instance of a broader principle that applies throughout query design at every level of complexity. The principle is: **apply filters as early as possible in the query execution pipeline, before data is joined, aggregated, or otherwise multiplied.**

This principle has a mathematical basis. A join between two tables of sizes N and M produces a result of size proportional to N × M (in the worst case). A filter with selectivity f reduces a table of size N to f × N rows. If you filter before the join, you join f × N rows with M rows, producing f × N × M result rows. If you filter after the join, you join N rows with M rows first (producing N × M rows) and then filter, still ending up with f × N × M rows — but you paid the cost of building and processing N × M rows instead of f × N × M rows.

In our case: f = 10/500 = 0.02 (10 million 2024 orders out of 500 million total). N = 500 million, M = 2 billion (order_items). Filtering before the join: join 10M × 2B (but only the matching order_items, so ~40M join result). Filtering after: join 500M orders with 2B order_items first — a vastly larger operation — then discard 98% of the result.

```
THE FILTER-FIRST PRINCIPLE — Applied to multi-stage queries

  General rule: reduce data volume before each expansion operation.

  Expansion operations (increase row count):
    JOIN — multiplies rows
    UNION ALL — adds rows
    CROSS JOIN — multiplies all rows by all rows (extreme)
    Unnesting arrays — multiplies rows by array length

  Reduction operations (decrease row count):
    WHERE — filters rows
    HAVING — filters groups
    LIMIT — caps rows
    GROUP BY — collapses rows into groups
    DISTINCT — deduplicates rows

  Ideal query structure:
  ┌──────────────────────────────────────────────────────────────┐
  │  1. Apply WHERE filters first (reduce before expanding)      │
  │  2. Then JOIN (expand on already-reduced data)               │
  │  3. Then GROUP BY (aggregate the expanded result)            │
  │  4. Then HAVING (filter aggregate results)                   │
  │  5. Then ORDER BY and LIMIT (sort and cap the final output)  │
  └──────────────────────────────────────────────────────────────┘

  Anti-pattern (what the original query did):
  ┌──────────────────────────────────────────────────────────────┐
  │  1. JOIN first (expand 500M rows into 2B rows)               │
  │  2. THEN apply WHERE filter (reduce 2B rows to 40M rows)     │
  │  → Built 2 billion rows only to discard 95% of them         │
  └──────────────────────────────────────────────────────────────┘
```

This filter-first principle should become a reflex. Every time you write a query involving both a filter and a join, ask yourself: "Is the filter applied before the join runs, or after?" If it is after, and if the filter is selective (it eliminates a significant fraction of rows), then moving the filter before the join is almost always a worthwhile change.

## More Complex Cases: Filters That Can and Cannot Be Pushed

Not every filter can be pushed inside every subquery. Understanding the constraints on pushing will help you apply this principle correctly and avoid inadvertently changing the query's semantics.

A filter can be safely pushed inside a subquery when: it references only columns from a single table (not computed columns that depend on the join or aggregation), and pushing it does not change the set of rows the outer query would have seen. In our case, `created_at > '2024-01-01'` references only `orders.created_at`, a column that exists in the `orders` table before the join. Pushing this filter inside the subquery, directly onto the `orders` table, produces exactly the same result as applying it after the join, because `created_at` values are not changed by the join.

A filter cannot be safely pushed inside a subquery when: it references a column that is computed by the subquery (such as a column alias defined by an expression inside the subquery); the subquery uses `GROUP BY` or `DISTINCT` and the filter references an aggregate result (like `WHERE sub.total_amount > 1000` where `total_amount` is `SUM(amount)`); or the subquery uses `LEFT JOIN` and the filter is on the nullable side (pushing such a filter would effectively convert a `LEFT JOIN` to an `INNER JOIN`, changing semantics).

```
FILTER PUSHDOWN — SAFE VS UNSAFE

  SAFE: Filter references a source column, not a computed one
  ┌────────────────────────────────────────────────────────────┐
  │ FROM (SELECT o.*, oi.* FROM orders o JOIN order_items oi  │
  │       ON o.id = oi.order_id) sub                          │
  │ WHERE sub.created_at > '2024-01-01'   ← source column     │
  │                                                            │
  │ Becomes: ... WHERE o.created_at > '2024-01-01'            │
  │ Same result. Safe to push.                                 │
  └────────────────────────────────────────────────────────────┘

  UNSAFE: Filter references an aggregate computed by the subquery
  ┌────────────────────────────────────────────────────────────┐
  │ FROM (SELECT customer_id, SUM(amount) AS total            │
  │       FROM orders GROUP BY customer_id) sub               │
  │ WHERE sub.total > 5000  ← computed aggregate              │
  │                                                            │
  │ Cannot push WHERE total > 5000 inside the GROUP BY.       │
  │ 'total' doesn't exist until after aggregation.            │
  │ Must stay outside. This is correct SQL — use HAVING       │
  │ inside the subquery if the filter on aggregate is needed  │
  │ before the outer query uses the result.                   │
  └────────────────────────────────────────────────────────────┘

  UNSAFE: Filter on nullable side of LEFT JOIN changes semantics
  ┌────────────────────────────────────────────────────────────┐
  │ FROM (SELECT c.*, o.amount FROM customers c              │
  │       LEFT JOIN orders o ON c.id = o.customer_id) sub    │
  │ WHERE sub.amount > 100  ← filters out NULLs              │
  │                                                            │
  │ Moving this inside converts LEFT JOIN to INNER JOIN.      │
  │ Customers with no orders would disappear.                 │
  │ Semantically different result. Unsafe to push blindly.   │
  └────────────────────────────────────────────────────────────┘
```

The practical rule is: when pushing a filter, reason carefully about whether the moved filter can see the column it references (the column must exist before the operation that defines it), and whether the filter changes the semantics of outer joins (if it eliminates rows that a LEFT JOIN would have preserved as NULLs).

## Refactoring Multi-Level Nested Queries for Filter Position

In real production codebases, queries are rarely as clean as the textbook example. They often have multiple layers of nesting, several joins, computed columns, and complex filter expressions. Here is a practical approach to auditing and improving filter positions in complex nested queries.

The first step is always to read the query from the inside out and map the data flow: what does each subquery produce, how many rows, and when does the filter that reduces those rows finally appear? If there is a large discrepancy between the rows a subquery produces and the rows the outer filter keeps, that is the signal to act.

The second step is to identify which filters reference only source table columns and can be moved earlier without semantic changes. These are the candidates for pushdown.

The third step is to restructure the query — move the identified filters inside the appropriate subqueries, as close to their source tables as possible. Then run `EXPLAIN ANALYZE` to verify that the filter is now being applied at the correct level, that index scans are being used where expected, and that the intermediate row counts have dropped as anticipated.

```
MULTI-LEVEL QUERY AUDIT: Reading Flow and Finding Early-Filter Opportunities

  FROM (
      SELECT ...
      FROM (
          SELECT *
          FROM orders o               ← SOURCE TABLE (500M rows)
          JOIN order_items oi ON ...
      ) inner_sub                     ← inner_sub: 2B rows
      JOIN products p ON ...
  ) outer_sub                         ← outer_sub: 5B rows?
  WHERE outer_sub.created_at > '2024-01-01'  ← FILTER HERE (too late!)
    AND outer_sub.category = 'Electronics'    ← FILTER HERE (too late!)

  Audit finding: both filters reference source columns
                 created_at is from orders, category is from products
                 Both can be pushed to their source tables.

  Fixed:
  FROM (
      SELECT ...
      FROM (
          SELECT *
          FROM orders o
          WHERE o.created_at > '2024-01-01'   ← filter at source
          JOIN order_items oi ON ...
      ) inner_sub
      JOIN products p ON ...
      WHERE p.category = 'Electronics'         ← filter at source
  ) outer_sub

  The join now operates on 10M orders (not 500M) and
  only Electronics products (not all products).
  Intermediate results: dramatically smaller at every level.
```

## The Result: 3 Minutes → 8 Seconds

After the filter was moved inside the subquery, the report execution time dropped from one hundred and eighty seconds to approximately eight seconds — a twenty-two-fold improvement. The hash table that previously required four gigabytes and sixty-four disk spill batches now fit in five hundred megabytes in a single in-memory batch. The sequential scan of five hundred million rows was replaced by an index scan of ten million rows.

```
BEFORE — Filter applied after the join:
  Orders scanned:              500,000,000 (full table, Seq Scan)
  Join result rows:            ~2,000,000,000 (2B rows produced)
  Hash table size:             4 GB (spilled to disk, 64 batches)
  Rows discarded by filter:    490,000,000 (after the join)
  Final result rows:           ~42,000,000
  Execution time:              178,891ms (~3 minutes)

AFTER — Filter pushed inside the subquery:
  Orders scanned:              10,000,000 (Index Scan, 2024 only)
  Join result rows:            ~42,000,000 (50× smaller)
  Hash table size:             512 MB (single in-memory batch)
  Rows discarded by filter:    0 (filter applied before join)
  Final result rows:           ~42,000,000
  Execution time:              7,934ms (~8 seconds)

Improvement: 178,891ms ÷ 7,934ms = 22.5× faster
Join size reduction: 2,000,000,000 → 42,000,000 rows = 47.6× smaller
Disk spill eliminated: 4GB → 0 (fits entirely in memory)
```

The final result is identical — the same forty-two million rows — because the filter is logically equivalent in both positions. Only the path to that result changed. One path builds two billion rows and discards 98% of them. The other path builds the forty-two million rows you actually wanted from the start.

## The Lesson That Stays With You

The placement of filter conditions is one of the most impactful and least visible design decisions in SQL query authorship. When you read a query, the `WHERE` clause always appears at the bottom — it is syntactically the last thing you write. This visual placement can create a subconscious impression that filtering is a final step, something done at the end after all the data is assembled. But in the database engine's execution pipeline, filtering should almost always happen as early as possible — as the very first thing done with each table's data, before any joins amplify the row count.

The mental model to carry with you is the funnel: data should narrow down before it is combined with other data. A narrow stream joining another narrow stream produces a manageable result. Two full floods colliding produce an ocean that then needs to be drained to find the few drops you actually needed. Your job as a query author is to narrow each stream before the collision, not after.

Whenever you write or review a query with both joins and filters, ask: "Is this filter applied to the source tables directly, or to the result of a join?" If it is applied to the result of a join, and if it could be applied to a source table instead without changing semantics, move it. Run `EXPLAIN ANALYZE` before and after to verify. The improvement may be modest if the filter is not very selective, or it may be dramatic — as in this case, twenty-two times faster — if it significantly reduces the join input.

## Summary

This case study examines a three-minute analytics report that joined the `orders` table (five hundred million rows) with the `order_items` table in a subquery, and then applied a date filter in the outer query. Because the filter was applied after the join — outside the subquery — the join ran on the full five hundred million order rows, producing approximately two billion intermediate rows, before four hundred and ninety million were discarded by the date filter. The hash join spilled four gigabytes to disk across sixty-four batches, and the total query time was approximately three minutes.

The fix was to move the date filter inside the subquery, directly onto the `orders` table, before the join with `order_items`. With an index on `orders.created_at`, the filtered scan retrieved only ten million 2024 orders instead of five hundred million. The join then operated on this pre-filtered ten million row set, producing approximately forty-two million rows — the same final result as before, but arrived at by building only the rows that were actually needed. Execution time dropped from 178,891 milliseconds to 7,934 milliseconds — a 22.5-fold improvement.

The lesson is the filter-first principle: apply filters as early as possible in the query execution pipeline, before joins multiply the row count. A filter applied before a join reduces the join's inputs by its selectivity factor. A filter applied after a join discards rows that should never have been produced. The mathematical difference between these two orderings grows with the size of the tables and the selectivity of the filter, and at the scales common in modern production systems, the difference is the gap between a query that works and one that does not.
