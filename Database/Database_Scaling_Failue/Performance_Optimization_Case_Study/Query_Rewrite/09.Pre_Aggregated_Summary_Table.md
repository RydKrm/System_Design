# The Dashboard That Counted Five Hundred Million Orders Every Morning: How Pre-Aggregation Reduced a 45-Second Load to 2ms

> _"A dashboard that re-derives the same answer from five hundred million rows on every page load is not a reporting system — it is a punishment. The data from three years ago did not change overnight. The answer from yesterday's aggregation is still correct today. A system that knows this, and acts on it, is a system that scales."_

---

## Setting the Scene

You are a backend engineer at a large online marketplace. The company has been operating for three years, processing orders every minute of every day across dozens of product categories and hundreds of thousands of sellers. The `orders` table has grown to five hundred million rows — a testament to the company's success, and a time bomb for the analytics infrastructure.

The executive team starts every morning with a review of the revenue dashboard. This dashboard shows a bar chart: total revenue per day for the last three hundred and sixty-five days. It is a simple, elegant visualization — one bar per day, each bar's height representing that day's total order revenue. Twelve months of business performance, at a glance, in one chart.

The problem is that loading this dashboard takes forty-five seconds. Not forty-five milliseconds. Forty-five full seconds of watching a spinner while the CFO waits, the CEO waits, and the weekly business review meeting is delayed because the page has not finished loading. The infrastructure team has thrown hardware at the problem — more CPU, more RAM, faster SSDs — and it helped some, but the query still takes over thirty seconds on the beefiest machine they provisioned.

Your senior engineer is brought in. She looks at the query, looks at the schema, looks at the growth trajectory of the orders table, and says something precise and memorable: _"The historical data from three years ago is not going to change. We are paying to re-count those orders every single morning. We should count them once and remember the answer."_

This case study is about the difference between computing an answer and remembering an answer — and why, for certain classes of problems, remembering is the only approach that scales.

---

## The Offending Query

The query that drives the revenue dashboard looks like this:

```sql
SELECT
    DATE(created_at) AS revenue_date,
    SUM(amount)      AS total_revenue,
    COUNT(*)         AS order_count
FROM orders
WHERE created_at > NOW() - INTERVAL '1 year'
GROUP BY DATE(created_at)
ORDER BY revenue_date;
```

This query asks the database to look at every order placed in the last twelve months, extract the date portion of the order timestamp, group all orders by that date, sum the amounts within each group, count the orders, and return one row per day. The result is 365 rows — one for each day in the past year.

The logic is correct. The performance is catastrophic. To produce those 365 rows, the database must scan every one of the roughly one hundred and eighty million orders placed in the last twelve months (assuming roughly five hundred million total across three years), apply the `DATE()` function to every `created_at` timestamp, sort or hash all one hundred and eighty million rows into their date groups, and compute the sum and count for each group. All of this happens from scratch, every single time the dashboard loads.

```
WHAT THE DATABASE DOES FOR EVERY DASHBOARD LOAD

  orders table: 500,000,000 rows total
  Orders in last 12 months: ~180,000,000 rows

  Step 1: Scan index on created_at
          Find all rows where created_at > (NOW - 1 year)
          → Touch 180,000,000 index entries

  Step 2: Fetch heap rows (or use index-only scan)
          → Read 180,000,000 rows of (created_at, amount)

  Step 3: Apply DATE() function to each created_at
          → 180,000,000 function evaluations

  Step 4: Hash or sort into 365 date buckets
          → 180,000,000 rows sorted into groups

  Step 5: SUM(amount) and COUNT(*) per group
          → 365 aggregates computed

  Step 6: Return 365 rows

  Result: 365 rows
  Rows processed to produce them: 180,000,000
  Ratio: 1 result row per 493,151 rows processed
  Time: 45 seconds
  This happens every time anyone opens the dashboard.
```

The inefficiency ratio is almost incomprehensible: the database processes nearly half a million rows for every single row it returns. And this computation is repeated from scratch every time the dashboard is loaded — which for a busy executive team might happen twenty or thirty times per day.

## Understanding the Nature of the Data: Historical Immutability

Before we discuss the solution, we need to understand something fundamental about the data being aggregated — something that the original query treats as irrelevant but which is actually the key to solving the problem.

The orders placed on January 15th of last year are **immutable**. They happened. They were processed. They were counted at the time. The revenue from that day was whatever it was. No new orders will be added to January 15th of last year — the day is over, the records are sealed, and the aggregate values (total revenue, order count) for that day will never change again for as long as the database exists.

This immutability is a profound opportunity that the original query completely ignores. Every time the dashboard loads, it re-reads and re-aggregates data from 364 days ago, 363 days ago, 362 days ago — data whose aggregate values have not changed since the day after those orders were placed. The database is computing `SUM(amount) WHERE created_at >= '2024-01-15' AND created_at < '2024-01-16'` every single morning, even though the answer has been the same for over a year and will never change.

```
THE IMMUTABILITY OF HISTORICAL ORDER DATA

  Today: September 13, 2025

  Order data from Sep 13, 2024 → IMMUTABLE (365 days ago)
  Daily revenue: $847,234.50
  Order count: 12,441
  → This will never change. Ever.
  → We have computed it 365 times already this year alone.
  → We will compute it 365 more times next year.

  Order data from Sep 12, 2024 → IMMUTABLE (366 days ago)
  Daily revenue: $921,105.00
  Order count: 13,287
  → Same story. Computed hundreds of times. Will be computed hundreds more.

  Only today's partial data changes as new orders arrive.
  The other 364 days in the chart are completely frozen.
  Yet we re-aggregate all 365 days on every load.
```

Once you see this immutability clearly, the solution becomes obvious: compute each day's aggregates once, when the day is complete, store the result, and read from that stored result forever after. The work of aggregating one hundred and eighty million historical orders needs to be done exactly once for the historical days — not once per dashboard load.

---

## The Solution: A Pre-Aggregated Summary Table

The solution is to create a dedicated summary table whose entire purpose is to store pre-computed aggregate values, one row per day:

```sql
-- Create the summary table
CREATE TABLE revenue_daily (
    revenue_date   DATE        NOT NULL,
    total_revenue  NUMERIC     NOT NULL DEFAULT 0,
    order_count    INTEGER     NOT NULL DEFAULT 0,
    last_updated   TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    PRIMARY KEY (revenue_date)
);

-- The dashboard query now reads from this tiny table
SELECT
    revenue_date,
    total_revenue,
    order_count
FROM revenue_daily
WHERE revenue_date > CURRENT_DATE - INTERVAL '1 year'
ORDER BY revenue_date;
```

The dashboard query has been transformed from a hundred-and-eighty-million-row aggregation into a three-hundred-and-sixty-five-row lookup. The `revenue_daily` table has a primary key on `revenue_date`, which is automatically indexed. Reading 365 rows from a primary key index is so fast it is essentially instantaneous — two milliseconds, compared to forty-five seconds.

```
ARCHITECTURE SHIFT: FROM COMPUTE-ON-READ TO COMPUTE-ON-WRITE

Old architecture (compute on every read):
  ┌──────────────────────────────────────────────────────────────┐
  │  Dashboard loads                                             │
  │        │                                                     │
  │        ▼                                                     │
  │  Query: SELECT DATE(created_at), SUM(amount)                │
  │         FROM orders WHERE ... GROUP BY ...                   │
  │        │                                                     │
  │        ▼                                                     │
  │  Scan 180M rows → compute aggregates → return 365 rows       │
  │  Cost: 45 seconds, every load, for every user               │
  └──────────────────────────────────────────────────────────────┘

New architecture (compute on write, read pre-computed result):
  ┌──────────────────────────────────────────────────────────────┐
  │  New order arrives                                           │
  │        │                                                     │
  │        ▼                                                     │
  │  INSERT INTO orders ...                                      │
  │  UPDATE revenue_daily SET total_revenue += amount,          │
  │                           order_count += 1                  │
  │  Cost: microseconds extra per order write                    │
  │                                                             │
  │  Dashboard loads                                             │
  │        │                                                     │
  │        ▼                                                     │
  │  Query: SELECT * FROM revenue_daily WHERE ...               │
  │  Scan 365 rows → return 365 rows                            │
  │  Cost: 2ms, every load, for every user, forever            │
  └──────────────────────────────────────────────────────────────┘
```

The architecture shift is from **compute-on-read** to **compute-on-write**. Instead of doing all the aggregation work at the moment the dashboard is read, you do a tiny amount of incremental work at the moment each order is written. The work is spread across millions of order insertions — each one adding a fractional increment to the daily total — instead of being concentrated into one enormous computation at dashboard load time.

## Strategy 1: Trigger-Based Real-Time Updates

The first approach to keeping the `revenue_daily` table current is to use a database trigger — a function that the database executes automatically every time an order row is inserted, updated, or deleted.

```sql
-- The trigger function
CREATE OR REPLACE FUNCTION update_revenue_daily()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO revenue_daily (revenue_date, total_revenue, order_count)
        VALUES (DATE(NEW.created_at), NEW.amount, 1)
        ON CONFLICT (revenue_date) DO UPDATE
            SET total_revenue  = revenue_daily.total_revenue  + EXCLUDED.total_revenue,
                order_count    = revenue_daily.order_count    + EXCLUDED.order_count,
                last_updated   = NOW();

    ELSIF TG_OP = 'DELETE' THEN
        UPDATE revenue_daily
        SET total_revenue  = total_revenue  - OLD.amount,
            order_count    = order_count    - 1,
            last_updated   = NOW()
        WHERE revenue_date = DATE(OLD.created_at);

    ELSIF TG_OP = 'UPDATE' THEN
        -- Handle amount change: subtract old, add new
        UPDATE revenue_daily
        SET total_revenue  = total_revenue - OLD.amount + NEW.amount,
            last_updated   = NOW()
        WHERE revenue_date = DATE(OLD.created_at);
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach the trigger to the orders table
CREATE TRIGGER trg_orders_revenue_daily
AFTER INSERT OR UPDATE OF amount OR DELETE ON orders
FOR EACH ROW
EXECUTE FUNCTION update_revenue_daily();
```

With this trigger in place, every order insertion updates the `revenue_daily` summary table atomically within the same transaction. If the order insertion is rolled back, the summary table update is rolled back with it. The summary table is always perfectly consistent with the orders table.

```
TRIGGER EXECUTION: WHAT HAPPENS ON EACH ORDER INSERT

  BEGIN TRANSACTION
  │
  ├──► INSERT INTO orders (customer_id, amount, created_at, ...)
  │    VALUES (12345, 89.99, '2025-09-13 14:23:01', ...)
  │
  │    [Database fires trigger automatically]
  │
  ├──► INSERT INTO revenue_daily (revenue_date, total_revenue, order_count)
  │    VALUES ('2025-09-13', 89.99, 1)
  │    ON CONFLICT (revenue_date) DO UPDATE
  │        SET total_revenue += 89.99, order_count += 1
  │
  └──► COMMIT
  (Both changes committed atomically — always consistent)

  Overhead per order: ~0.1ms (one indexed upsert to a small table)
  Benefit: dashboard always reads current, pre-computed data
```

The trigger approach keeps the summary table perfectly up to date in real time. The dashboard always shows the very latest data, including orders placed seconds ago. The cost per order write is minimal — a single `UPSERT` into a small table with a primary key lookup, which completes in microseconds.

The tradeoff is that the trigger adds a small but non-zero overhead to every order insertion. On a system processing one thousand orders per second, this overhead is negligible. On a system processing ten thousand orders per second, it warrants benchmarking. And on a system with complex order editing, cancellation, and refund workflows, the trigger logic becomes more complex to handle all the update and delete cases correctly.

## Strategy 2: Scheduled Batch Aggregation Job

The second approach avoids adding any overhead to order writes by accepting a small delay in the freshness of the summary data. Instead of updating the summary table on every order write, a scheduled job runs once per day (or once per hour) and recomputes the aggregates for recent periods.

```sql
-- Nightly job: recompute aggregates for the last 2 days
-- (yesterday in case of any late-arriving orders, today for partial data)
INSERT INTO revenue_daily (revenue_date, total_revenue, order_count, last_updated)
SELECT
    DATE(created_at)   AS revenue_date,
    SUM(amount)        AS total_revenue,
    COUNT(*)           AS order_count,
    NOW()              AS last_updated
FROM orders
WHERE created_at >= CURRENT_DATE - INTERVAL '2 days'
GROUP BY DATE(created_at)
ON CONFLICT (revenue_date) DO UPDATE
    SET total_revenue  = EXCLUDED.total_revenue,
        order_count    = EXCLUDED.order_count,
        last_updated   = EXCLUDED.last_updated;
```

This job runs once per day, aggregates only the last two days' worth of orders (a small fraction of the total), and upserts the results into the summary table. For historical days beyond the two-day window, the aggregates are already correct and never need to be recomputed. For today and yesterday, the aggregates are refreshed to reflect any new or adjusted orders.

```
BATCH JOB STRATEGY: Recompute Only What Changed

  orders table: 500,000,000 rows (3 years)
  Historical days (immutable, aggregates stored permanently):
  ┌────────────────────────────────────────────────────────┐
  │ 2022-09-13: $923,441  12,221 orders  ← never changes  │
  │ 2022-09-14: $887,123  11,834 orders  ← never changes  │
  │ ...  (3 years × 365 = ~1,095 rows, permanently stored) │
  │ 2025-09-11: $1,012,234 13,441 orders ← never changes  │
  └────────────────────────────────────────────────────────┘

  Yesterday (may have late corrections):
  ┌────────────────────────────────────────────────────────┐
  │ 2025-09-12: $998,441  13,102 orders  ← refresh daily  │
  └────────────────────────────────────────────────────────┘

  Today (accumulating throughout the day):
  ┌────────────────────────────────────────────────────────┐
  │ 2025-09-13: $234,112   3,021 orders  ← refresh hourly │
  └────────────────────────────────────────────────────────┘

  Batch job scans only 2 days of orders (≈ ~26,000 rows)
  instead of 500,000,000.
  Job completes in milliseconds.
```

The batch job approach is simpler to implement and has zero impact on order write performance. Its limitation is that the dashboard data is not perfectly real-time — it is as fresh as the last job run. For an executive dashboard showing revenue trends over the past year, a five-minute or even one-hour delay in seeing today's partial totals is entirely acceptable. For a real-time operational dashboard where someone is watching live transaction volume, the trigger approach is more appropriate.

## Strategy 3: PostgreSQL Materialized Views

PostgreSQL provides a built-in mechanism for pre-aggregated views called **materialized views**. A materialized view is defined exactly like a regular view — as a SQL query — but its result is physically stored on disk rather than re-evaluated on every access. It combines the semantic clarity of a view with the performance characteristics of a pre-computed table.

```sql
-- Create the materialized view
CREATE MATERIALIZED VIEW revenue_daily_mv AS
SELECT
    DATE(created_at) AS revenue_date,
    SUM(amount)      AS total_revenue,
    COUNT(*)         AS order_count
FROM orders
WHERE created_at > NOW() - INTERVAL '1 year'
GROUP BY DATE(created_at)
ORDER BY revenue_date
WITH DATA;  -- Immediately populate with current data

-- Create an index on the date column for fast lookups
CREATE UNIQUE INDEX ON revenue_daily_mv (revenue_date);

-- Refresh the view (run this on a schedule or when needed)
REFRESH MATERIALIZED VIEW CONCURRENTLY revenue_daily_mv;
```

The `REFRESH MATERIALIZED VIEW CONCURRENTLY` command rebuilds the materialized view in the background while allowing concurrent reads from the existing data. Without `CONCURRENTLY`, a refresh would lock the view and block all reads for its duration — unacceptable for a dashboard used by executives. With `CONCURRENTLY`, the view is rebuilt into a new copy, then swapped atomically, and the old copy is discarded. Readers always see a consistent, complete dataset.

The materialized view approach is the closest to "automatic" — the SQL definition is maintained in one place, the refresh is triggered by a schedule, and the dashboard query simply reads from the view without needing to know that it is pre-computed. The limitation is that `REFRESH` rebuilds the entire view from scratch each time, which for a one-year window of five hundred million orders would still be an expensive operation. For the incrementally updated summary table approach, only new rows need to be processed.

```
THREE STRATEGIES COMPARED

                      Trigger        Batch Job      Materialized View
─────────────────────────────────────────────────────────────────────
Implementation         Complex        Simple         Moderate
Data freshness         Real-time      Delayed        Delayed
Write overhead         Small          None           None
Refresh scope          Per-row        Recent days    Full rebuild
Handles deletes/edits  Yes            Yes (recompute) Yes (full rebuild)
Concurrent reads       Always         Always         With CONCURRENTLY
Best for               Live dashboards Daily reports  Moderate-traffic
─────────────────────────────────────────────────────────────────────
```

The right choice depends on your specific requirements. For the executive revenue dashboard in this case study — where data is viewed in daily granularity and a delay of a few minutes is acceptable — the batch job approach is typically the simplest and most robust. For a live operations dashboard, the trigger approach provides the real-time freshness that operators need.

## Bootstrapping: Populating the Summary Table for Historical Data

Whatever strategy you choose for keeping the summary table current going forward, you first need to populate it for all the historical data that already exists. This is a one-time operation, and it looks like the original slow query — but it only needs to run once:

```sql
-- One-time historical backfill (run during a maintenance window or off-peak)
INSERT INTO revenue_daily (revenue_date, total_revenue, order_count, last_updated)
SELECT
    DATE(created_at) AS revenue_date,
    SUM(amount)      AS total_revenue,
    COUNT(*)         AS order_count,
    NOW()            AS last_updated
FROM orders
GROUP BY DATE(created_at)
ORDER BY revenue_date
ON CONFLICT (revenue_date) DO UPDATE
    SET total_revenue = EXCLUDED.total_revenue,
        order_count   = EXCLUDED.order_count,
        last_updated  = EXCLUDED.last_updated;
```

This query will take a while to run — it is aggregating five hundred million rows, after all — but it only runs once. After this backfill completes, the summary table is populated for all historical dates, and from that point forward, only the trigger or batch job keeps it current. The forty-five-second aggregation is replaced by a two-millisecond lookup, permanently.

A pragmatic detail worth noting: when running the backfill on a large table, it is wise to process it in date-range chunks rather than as one monolithic query, to avoid holding a single enormous transaction open and generating an excessive WAL volume:

```sql
-- Chunked historical backfill (process one month at a time)
-- Repeat for each month from the earliest date to today

INSERT INTO revenue_daily (revenue_date, total_revenue, order_count, last_updated)
SELECT
    DATE(created_at),
    SUM(amount),
    COUNT(*),
    NOW()
FROM orders
WHERE created_at >= '2022-01-01'
  AND created_at <  '2022-02-01'
GROUP BY DATE(created_at)
ON CONFLICT (revenue_date) DO UPDATE
    SET total_revenue = EXCLUDED.total_revenue,
        order_count   = EXCLUDED.order_count,
        last_updated  = EXCLUDED.last_updated;

-- Repeat for '2022-02-01' to '2022-03-01', etc.
```

Each month processes roughly fifteen million rows — fast, non-disruptive, and safe to interrupt and resume if needed.

## The Broader Principle: Separating Write-Time and Read-Time Computation

The pre-aggregation pattern is an instance of one of the most fundamental design principles in high-performance data systems: **separate the cost of computation from the moment of reading results.** This principle goes by many names in different contexts — materialisation, denormalisation, caching, event sourcing with projections, CQRS (Command Query Responsibility Segregation) — but the underlying idea is always the same.

When a computation is expensive and its result is stable (either because the input data is immutable, or because small changes in the input produce small, easily computed changes in the output), it is almost always more efficient to compute the result once and store it, rather than recomputing it on every read. The cost of computation is amortised over all the reads that benefit from it, potentially thousands or millions of reads per single computation.

This principle applies not just to database aggregations but to many layers of a software system. A web server that computes complex page layouts on every HTTP request is doing more work than necessary if those layouts rarely change. A search engine that scores documents on every query is slower than one that pre-scores them when they are indexed. A reporting system that scans raw event logs on every report load is less scalable than one that maintains pre-aggregated projections.

```
THE GENERALISED PRE-AGGREGATION PRINCIPLE

  Expensive computation (run once on data write):
  ┌──────────────────────────────────────────────────────────┐
  │  500,000,000 rows → aggregate → 365 result rows          │
  │  Cost: 45 seconds (paid once, or once per day)           │
  │  Result: stored in revenue_daily table                   │
  └──────────────────────────────────────────────────────────┘

  Cheap retrieval (run on every dashboard load):
  ┌──────────────────────────────────────────────────────────┐
  │  365 stored rows → read → 365 result rows                │
  │  Cost: 2ms (paid on every read, by every user)           │
  └──────────────────────────────────────────────────────────┘

  If the dashboard is loaded 50 times per day:
  Before: 50 × 45,000ms = 2,250,000ms of computation daily
  After:  1 × refresh cost + 50 × 2ms = refresh + 100ms daily

  The savings scale with read frequency.
  The more the dashboard is loaded, the greater the benefit.
```

This is why pre-aggregation is such a powerful pattern for dashboards specifically. Dashboards are read-heavy by nature — they are opened by many users, refreshed frequently, and expected to respond instantly. The underlying data they display is almost always aggregated from a large raw event table. And the aggregation result is often small — 365 rows for a daily chart, 52 rows for a weekly chart, 12 rows for a monthly chart. The ratio of computation work to result size is enormous, making pre-aggregation extremely efficient.

## When Pre-Aggregation Is the Right Pattern — And When It Is Not

Like any architectural pattern, pre-aggregation is not universally appropriate. Understanding when to apply it and when to look for other solutions will make you a more well-rounded engineer.

Pre-aggregation is the right pattern when: the query aggregates a very large table into a very small result set (the "many rows in, few rows out" shape); the aggregated result is stable or changes only incrementally (historical data is immutable; today's data grows slowly); the query is executed frequently, especially by multiple users simultaneously (the savings scale with read frequency); and the granularity of aggregation is fixed and known in advance (days, weeks, regions, categories — you know which dimension to pre-aggregate by).

Pre-aggregation is not the right pattern when: users need to slice the data by arbitrary dimensions that cannot be anticipated (an ad-hoc analytics tool where users can group by any column combination); the result set is not small (if you pre-aggregate but still produce millions of rows, you have not solved the problem); the underlying data changes so frequently that maintaining the summary table in sync with the source becomes more complex than the original query; or the query is rarely executed (if the dashboard is loaded twice per month, the forty-five-second load time may simply be acceptable).

```
WHEN TO PRE-AGGREGATE

  Pre-aggregate when:
  ✓ Raw table has millions or billions of rows
  ✓ Query result is small (days, regions, categories, etc.)
  ✓ Query runs frequently (multiple times per hour/day)
  ✓ Historical data is immutable
  ✓ Aggregation dimension is known and fixed

  Don't pre-aggregate when:
  ✗ Users need arbitrary ad-hoc grouping dimensions
  ✗ Result set is still large after aggregation
  ✗ Data changes constantly and updates are very frequent
  ✗ Query runs rarely (weekly or monthly)
  ✗ The complexity of maintaining the summary table
    outweighs the performance benefit
```

## The Result: 45,000ms → 2ms

After the `revenue_daily` summary table was created, bootstrapped with historical data, and connected to the dashboard via the batch job, the executive revenue chart went from a forty-five-second ordeal to a two-millisecond response.

```
BEFORE — Runtime aggregation:
  Rows scanned:         ~180,000,000 (last 12 months of orders)
  Function calls:       180,000,000 (DATE() per row)
  Rows grouped:         180,000,000 (hashed into 365 buckets)
  Disk I/O:             ~36 GB read from orders table
  Execution time:       45,000ms (45 seconds)
  Cost per dashboard:   45 seconds of CPU + I/O + memory
  Cost per day (50 loads): 2,250 seconds of wasted computation

AFTER — Pre-aggregated summary table:
  Rows scanned:         365 (primary key index scan)
  Function calls:       0
  Rows grouped:         0 (already grouped)
  Disk I/O:             ~15 KB read from revenue_daily table
  Execution time:       2ms
  Cost per dashboard:   2ms
  Cost per day (50 loads): 100ms total

Improvement: 45,000ms ÷ 2ms = 22,500×
I/O reduction: 36 GB → 15 KB = 2,500,000× less data read
```

The 22,500-fold improvement is one of the largest in this entire case study series. It is so large because the problem was so structurally misaligned: asking the database to recount five hundred million orders every time someone opens a chart was never reasonable at this data scale. The pre-aggregation pattern did not optimise the query — it made the original query unnecessary.

## The Lesson That Stays With You

The deepest insight from this case study is not a SQL trick or a database tuning parameter — it is an architectural realisation. Some computations should not happen at read time. When the result of an aggregation over immutable historical data is the same today as it was yesterday, computing it afresh today is pure waste. When a dashboard is opened fifty times per day and each open triggers a forty-five-second scan of five hundred million rows, you are doing 2,250 seconds of unnecessary computation every day, every week, every year — and the waste grows as the table grows.

The discipline to develop is recognising the shape of this problem early. Whenever you see a query that aggregates a very large table into a small result, ask: "How often does this run? How much of the input data is immutable? Could I compute this once and store it?" If the answer to "how often" is "multiple times per day or more," and the answer to "how much is immutable" is "most of it," then pre-aggregation is the appropriate solution, and implementing it will produce the most dramatic performance improvements you will ever achieve in your career.

A database that stores answers is always faster than a database that recomputes them.

## Summary

This case study examines an executive revenue dashboard that displayed daily revenue totals for the past twelve months. The underlying query aggregated an orders table containing five hundred million rows, scanning approximately one hundred and eighty million rows on every dashboard load to produce 365 output rows — one per day. The query took forty-five seconds to complete, and this cost was paid on every dashboard load, by every user, for every refresh, forever.

The solution was to create a `revenue_daily` summary table containing one pre-aggregated row per day. Historical days — whose order data is permanently immutable — are computed once during a bootstrapping job and stored permanently. Today's and yesterday's rows are refreshed periodically by a lightweight batch job that scans only recent orders, or updated in real time by a database trigger that increments the daily totals with each new order. The dashboard query was rewritten to read from this summary table, scanning 365 rows with a primary key index lookup instead of one hundred and eighty million rows from the full orders table. Execution time dropped from 45,000 milliseconds to 2 milliseconds — a 22,500-fold improvement.

The principle is one of the most powerful in all of data systems engineering: separate the cost of computation from the moment of reading results. When a computation is expensive, its result is stable, and it is read frequently, pre-aggregate and store the result. A database that remembers answers scales; a database that recomputes them does not.
