# Case Study 21 — The Index on a Low-Cardinality Boolean Column

---

## The Setup — What Were We Even Trying to Do?

Imagine you are working on a product that has grown to serve millions of users. Over the years, instead of permanently deleting users from the database — perhaps for audit reasons, compliance, or simply because it felt "safer" — the engineering team decided to mark users as deleted using a simple flag. This is an extremely common and widely adopted pattern in the industry known as **soft deletion**. Rather than running a `DELETE FROM users WHERE id = 123` statement, the application instead runs `UPDATE users SET is_deleted = true WHERE id = 123`. The row stays in the database physically, but the application agrees to treat it as if it no longer exists by always adding a `WHERE is_deleted = false` filter to every query.

At first glance, this sounds perfectly reasonable. And in most small to medium-sized systems, it works just fine. The trouble begins the moment your table crosses a certain scale — and in our story, that scale is **10 million rows**.

---

## Understanding the Problem — The Nature of Cardinality

Before we go any further, we need to understand a word that will define this entire case study: **cardinality**. In the context of database columns, cardinality simply refers to how many distinct values a column can hold. A column like `user_id`, which holds a unique identifier for every single user, has **very high cardinality** — millions of distinct values. A column like `country_code` might hold a few hundred distinct values — **medium cardinality**. And a column like `is_deleted`, which is a boolean and can only ever hold one of two values — `true` or `false` — has the **lowest possible cardinality**.

This distinction is not merely academic. It has profound, real-world consequences for how a database engine makes decisions about how to execute your queries. The entire point of an index is to allow the database engine to quickly narrow down the set of rows it needs to look at. A well-designed index acts like a well-organized library catalog — you look up the catalog, get the shelf number, and walk directly to that book. But here is the critical insight: **if almost every book in the library is on the same shelf, the catalog becomes useless**. Looking up the catalog and walking to that shelf is no faster than simply walking through every row of shelves from start to finish.

---

## The Data Distribution — Where the Real Problem Lives

In our scenario, the table has **10 million rows**. Of those 10 million rows, **9.9 million rows** have `is_deleted = false`, and only **100,000 rows** have `is_deleted = true`. Let us visualize what this distribution looks like inside the table.

```
Table: users (10,000,000 rows total)
=============================================================
|  is_deleted = false  |ooooooooooooooooooooooooooooooooooo|
|      9,900,000       |ooooooooooooooooooooooooooooooooooo|
|       (99%)          |ooooooooooooooooooooooooooooooooooo|
=============================================================
|  is_deleted = true   |##|
|       100,000        |##|
|        (1%)          |##|
=============================================================

  [o] = 99% of the table      [#] = 1% of the table
```

Now, consider what happens when a developer, trying to do the right thing, creates an index on this column:

```sql
CREATE INDEX idx_users_is_deleted ON users (is_deleted);
```

The intent is good. The developer thinks, "We always filter by `is_deleted` in our queries, so let us index it." But the reality of what an index on a boolean column produces is deeply counterintuitive until you understand how a database query planner works.

---

## How a Database Index Actually Works — A Mental Model

Think of a database index as a separate, sorted data structure that lives alongside your main table. When you create an index on a column, the database engine builds this structure and keeps it updated whenever rows are inserted, updated, or deleted. The index stores the column's values in a sorted manner, along with pointers (physical addresses) back to the actual rows in the table.

When you run a query like `SELECT * FROM users WHERE is_deleted = false`, the database's **query planner** — the component responsible for deciding the most efficient way to execute your query — looks at the available indexes and makes a decision. It asks a very important question: "If I use this index to find the rows where `is_deleted = false`, how many rows will that give me?"

The answer, in our case, is **9.9 million rows**. That is 99% of the entire table. The query planner now faces a dilemma. Using the index would mean:

1. Traversing the index structure to find all entries where `is_deleted = false`.
2. For each of those 9.9 million entries, following the pointer back to the actual table row (this is called a **heap fetch** or a **random I/O operation**).

That is 9.9 million random disk reads. Compare this to the alternative: a **sequential table scan** (also called a full table scan), where the database simply reads the entire table from top to bottom in one continuous sweep. Sequential reads are dramatically faster than random reads because modern storage hardware — both spinning disks and SSDs — is optimized for sequential access patterns.

```
Using the Full Index (BAD for is_deleted = false):
---------------------------------------------------
  Index Lookup
      |
      v
  [Index Node: false -> row#1, row#3, row#5, ..., row#9,900,000]
      |
      v  (9.9 million random jumps back to the table)
  [Table Page 1] -> fetch row
  [Table Page 4] -> fetch row     <- RANDOM I/O (very expensive)
  [Table Page 2] -> fetch row
  [Table Page 8] -> fetch row
  ...9,900,000 times...

Using a Sequential Scan (BETTER for is_deleted = false):
---------------------------------------------------------
  [Table Page 1] -> read all rows
  [Table Page 2] -> read all rows  <- SEQUENTIAL I/O (cheap)
  [Table Page 3] -> read all rows
  ...read entire table in order...
```

The query planner is smart enough to recognize this. It will look at the statistics it maintains about the data distribution in each column (stored in system tables like `pg_statistic` in PostgreSQL), see that 99% of the table has `is_deleted = false`, and simply **choose to ignore the index**. It will perform a full sequential scan instead, because that is genuinely faster.

---

## The Query Planner's Decision — Statistics and Selectivity

The concept that governs the query planner's decision is called **selectivity**. Selectivity is a measure of how well an index or a filter condition narrows down the result set. A highly selective condition is one that eliminates most rows — for example, `WHERE user_id = 42` is extremely selective because it matches exactly one row out of 10 million. A condition with low selectivity is one that matches most of the table — `WHERE is_deleted = false` is the very definition of low selectivity in our dataset.

Every major relational database — PostgreSQL, MySQL, SQL Server, Oracle — maintains internal statistics about the distribution of values in each column. In PostgreSQL, this information lives in the `pg_statistic` system catalog and is updated periodically by the `AUTOVACUUM` process (or manually via the `ANALYZE` command). The query planner consults these statistics when deciding whether to use an index. When it sees that a condition will match 99% of the table, it correctly concludes that the cost of using the index outweighs the benefit, and it opts for the sequential scan.

This means you have paid the storage cost of maintaining that index — every `INSERT`, `UPDATE`, and `DELETE` now has to keep the index updated — and you receive absolutely no benefit for the most common query pattern. You have created overhead with no upside.

```
Cost-Benefit Analysis of the Full Boolean Index:
==========================================================
COSTS (always paid):
  - Extra disk space to store the index (~hundreds of MB)
  - Slower INSERT: must update the table AND the index
  - Slower UPDATE: must update the index on every change
  - Slower DELETE: must remove the entry from the index
  - Increased VACUUM overhead (PostgreSQL-specific)

BENEFITS RECEIVED:
  - Query WHERE is_deleted = false  -> Planner IGNORES index  [x]
  - Query WHERE is_deleted = true   -> Planner USES index     [OK]
==========================================================
Net Result: You pay for everything, you gain almost nothing.
```

---

## The One Case Where It Helps — The Minority Value

Here is where things get slightly nuanced, and it is important to understand this precisely. The index on `is_deleted` is **not entirely useless** — it does help for queries that filter on `is_deleted = true`, because only 100,000 rows out of 10 million match that condition. That is 1% of the table. Using an index to jump directly to those 100,000 rows is a genuine win compared to scanning all 10 million rows sequentially.

But here is the uncomfortable truth: in a real-world application using the soft-delete pattern, **almost no business logic queries for deleted users**. The 99.9% of queries running through your application are filtering on `is_deleted = false` — "give me all active users," "find me active users in New York," "show me active orders." The queries that look at `is_deleted = true` are rare — perhaps a background cleanup job, or an admin dashboard's "show me deleted users" feature. So you have an index that:

- Does nothing for your most frequent, performance-critical queries.
- Helps only for your rarest queries (which also tend to be admin-only and not latency-sensitive).
- Costs you storage and write performance on every single data modification.

This is a deeply unfavorable trade-off.

---

## The Solution — Partial Indexes

This is where one of the most elegant features of modern relational databases comes into play: the **partial index** (also sometimes called a **filtered index** in SQL Server terminology). A partial index is an index that is built only on a **subset of the rows in a table**, determined by a `WHERE` clause specified at index creation time.

Instead of creating an index on the entire `is_deleted` column across all 10 million rows, you create an index that only covers the rows that actually need to be quickly accessible. In our case, that would be the index used to efficiently look up active (non-deleted) users:

```sql
-- The old, problematic approach (full index on boolean):
CREATE INDEX idx_users_is_deleted ON users (is_deleted);

-- The correct, partial index approach:
CREATE INDEX idx_users_active ON users (id) WHERE is_deleted = false;
```

Let us carefully unpack what this second statement does. It creates an index that:

1. Only includes rows where `is_deleted = false`.
2. Stores the `id` column as the indexed value (though you could index any column or combination of columns useful for your queries).
3. Contains only the 9.9 million active rows — not the 100,000 deleted ones.

Wait — you might be asking: "But if 9.9 million rows are in the index, is this not the same problem?" And this is a brilliant question that gets to the heart of why partial indexes are so powerful. The answer lies in **how the query planner uses this index** in conjunction with the rest of your query's conditions.

---

## Why the Partial Index is Dramatically Better — A Deep Dive

When you write a query like `SELECT * FROM users WHERE is_deleted = false AND city = 'New York'`, the full boolean index on `is_deleted` is useless because it gives 9.9 million rows for the `is_deleted = false` part alone. But the partial index changes the game entirely.

The partial index exists **specifically for the universe of non-deleted users**. When the query planner sees `WHERE is_deleted = false AND city = 'New York'`, it now has a powerful option. The partial index allows the query planner to use it confidently in combination with other conditions. More importantly, if you have a compound partial index like:

```sql
CREATE INDEX idx_users_active_city ON users (city) WHERE is_deleted = false;
```

Now a query like `SELECT * FROM users WHERE is_deleted = false AND city = 'New York'` can use this index extremely efficiently. The index already knows it only contains active users, so filtering by `city = 'New York'` within those 9.9 million rows using a B-tree structure is very fast.

But the truly critical advantage of the partial index — even the simple one — is its **dramatically smaller size**:

```
Index Size Comparison:
======================================================================

Full Index on is_deleted (all 10M rows):
  +----------------------------------------------------------+
  |  false -> [ptr1, ptr2, ptr3, ... ptr9,900,000 pointers]  |
  |  true  -> [ptr1, ptr2, ... ptr100,000 pointers]          |
  +----------------------------------------------------------+
  Approximate size: ~400-600 MB (stores pointers for all 10M rows)
  Useful for WHERE is_deleted = false?   NO  [IGNORED]
  Useful for WHERE is_deleted = true?    YES [USED] (but rare queries)

Partial Index WHERE is_deleted = false (9.9M rows):
  +--------------------------------------------------------------+
  |  [id=1, ptr], [id=2, ptr], [id=3, ptr], ... [id=9.9M, ptr]  |
  +--------------------------------------------------------------+
  Approximate size: ~200-350 MB
  Useful for all queries filtering active users? YES [OK]
  Can be combined with other indexes?            YES [OK]

Compound Partial Index (city) WHERE is_deleted = false:
  +---------------------------------------------------------------+
  |  Sorted by city, but ONLY for non-deleted users               |
  |  "Auckland" -> [ptr5, ptr22, ptr891, ...]                     |
  |  "Boston"   -> [ptr3, ptr7,  ptr44,  ...]                     |
  |  "New York" -> [ptr1, ptr2,  ptr19,  ...]  <- fast lookup!    |
  +---------------------------------------------------------------+
  Dramatically smaller than a full city index (excludes 100K rows)
  Perfectly selective for soft-deleted-aware queries [OK]
======================================================================
```

The partial index is smaller because it contains fewer rows. A smaller index fits more easily into the database server's memory (the **buffer pool** or **shared buffers**), which means more of the index can be cached in RAM rather than being read from disk. An index that lives in memory is orders of magnitude faster than one that must be fetched from disk.

## The Lifecycle of a Query — Before and After the Fix

To truly cement this understanding, let us trace the journey of a single query through the database system before and after we apply the partial index solution.

**Before the fix — the harmful full boolean index:**

```
Query: SELECT id, name, email FROM users WHERE is_deleted = false AND city = 'New York'

  Application
      |
      v
  PostgreSQL Query Parser
      |  Parses SQL, checks syntax, resolves table/column names
      v
  Query Planner / Optimizer
      |  Checks pg_statistic -> sees is_deleted=false matches 99% of rows
      |  Decides: using idx_users_is_deleted is WORSE than a seq scan
      |  Looks for index on 'city' column -> none exists
      |  Decision: SEQUENTIAL SCAN on users table + filter
      v
  Executor
      |  Reads ALL 10,000,000 rows from disk page by page
      |  Discards rows where is_deleted = true (100,000 rows)
      |  Filters remaining 9,900,000 rows for city = 'New York'
      v
  Result: ~50,000 rows returned
  Cost: Read 10 million rows. Slow. Very slow.
```

**After the fix — the partial index:**

```
Query: SELECT id, name, email FROM users WHERE is_deleted = false AND city = 'New York'

  Application
      |
      v
  PostgreSQL Query Parser
      |
      v
  Query Planner / Optimizer
      |  Sees partial index idx_users_active_city (city) WHERE is_deleted=false
      |  Recognizes: this index perfectly matches our WHERE clause
      |  The index already excludes deleted rows -- no extra filtering needed
      |  Estimates: city='New York' is selective within active users
      |  Decision: INDEX SCAN on idx_users_active_city
      v
  Executor
      |  Navigates B-tree index to 'New York' entries (microseconds)
      |  Follows ~50,000 pointers to the actual table rows
      |  Returns results
      v
  Result: ~50,000 rows returned
  Cost: Read ~50,000 rows. Blazing fast.
```

The difference in execution time between these two plans, at 10 million rows, can easily be the difference between a query that takes **8–15 seconds** and one that takes **50–100 milliseconds**. That is a difference of two orders of magnitude — 100 times faster — and it comes purely from choosing the right kind of index.

---

## The Write Performance Overhead — An Often-Overlooked Cost

There is another dimension of this problem that is frequently overlooked by engineers who are new to database internals: the cost of **maintaining an index during write operations**. Every time a row is inserted into the `users` table, the database must also insert an entry into every index defined on that table. Every time a row is updated, the database must update the relevant index entries. Every time a row is deleted, the database must remove the corresponding index entries.

With the full boolean index, every single insert, update, and delete on the `users` table incurs the overhead of maintaining this essentially useless index. At 10 million rows with a busy application, this can add up to significant cumulative overhead — not a dramatic slowdown on a single operation, but a consistent tax paid on every write, which compounds over millions of operations per day.

The partial index mitigates this as well. Because the partial index only covers rows where `is_deleted = false`, the maintenance overhead is more targeted:

- When a new active user is created (`is_deleted = false`), the partial index is updated. This is expected and necessary.
- When a user is soft-deleted (updated from `is_deleted = false` to `is_deleted = true`), the row is **removed** from the partial index (because it no longer satisfies `WHERE is_deleted = false`). This is a one-time removal per soft-delete event.
- When other columns are updated on an active user, the partial index is updated only if the indexed column (e.g., `city`) changes.
- Rows with `is_deleted = true` are **never touched by this index** at all.

This means your write-heavy, high-throughput operations are carrying a lighter indexing burden, which contributes to better overall database performance.

## The Broader Lesson — Low-Cardinality Columns and Index Design Philosophy

This case study is not just about `is_deleted`. It is a specific instance of a much broader and more fundamental lesson in database design: **the effectiveness of an index is directly tied to its selectivity**. A full index on any low-cardinality column is almost always the wrong tool for the job. Consider these analogous situations:

A `status` column on an `orders` table that can be `'pending'`, `'processing'`, `'shipped'`, or `'delivered'`. If 95% of orders are `'delivered'`, an index on `status` is nearly useless for the `status = 'delivered'` query, but very useful for `status = 'pending'`. A partial index on `status IN ('pending', 'processing')` — the actionable, business-critical statuses — would be dramatically more effective.

A `is_active` column on a `products` table in an e-commerce platform. If the business rarely retires products, the vast majority of products are active, and the same analysis applies.

A `role` column on a `users` table where 99.9% of users are `'customer'` and 0.1% are `'admin'`. Indexing on `role = 'admin'` with a partial index is efficient for administrative lookups; a full index on `role` wastes resources.

The governing principle in all these cases is the same: **you should index the data that is rare and needs to be found quickly, not the data that is common and will be scanned regardless**.

## How to Diagnose This Problem in Production

If you suspect that your database is suffering from a poorly designed boolean index, PostgreSQL gives you powerful tools to investigate. The `EXPLAIN ANALYZE` command is your best friend. Running it on a slow query will reveal exactly what plan the query planner chose and why:

```sql
-- Run this to see the actual execution plan
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, name, email
FROM users
WHERE is_deleted = false
AND city = 'New York';
```

If the output shows something like `Seq Scan on users` with a very high row estimate, you know the planner decided a full table scan was cheaper than using the available index. This is a clear diagnostic signal that your index design needs to be revisited.

You can also inspect how much your existing indexes are actually being used by querying the `pg_stat_user_indexes` system view:

```sql
-- Check if your index is actually being used
SELECT
    indexrelname AS index_name,
    idx_scan     AS times_used_by_planner,
    idx_tup_read AS tuples_read_via_index,
    idx_tup_fetch AS tuples_fetched_from_table
FROM pg_stat_user_indexes
WHERE relname = 'users'
ORDER BY idx_scan DESC;
```

If `times_used_by_planner` is zero or very low for your `idx_users_is_deleted` index despite the column being used in many queries, that is definitive evidence that the index is being ignored by the planner. You are paying its maintenance cost for zero benefit.

## The Correct Implementation — Step by Step

Here is how you would properly remediate this situation in a production PostgreSQL database, written as a safe, step-by-step migration:

```sql
-- Step 1: Create the new, correct partial index.
-- Use CONCURRENTLY to build it without locking the table (safe for production).
CREATE INDEX CONCURRENTLY idx_users_active
ON users (id)
WHERE is_deleted = false;

-- Step 2: Create a more useful compound partial index for common query patterns.
-- This allows efficient querying by city for active users only.
CREATE INDEX CONCURRENTLY idx_users_active_city
ON users (city)
WHERE is_deleted = false;

-- Step 3: Verify the new indexes are being used by the query planner.
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name, email
FROM users
WHERE is_deleted = false
AND city = 'New York';
-- You should now see "Index Scan using idx_users_active_city" in the output.

-- Step 4: Once verified, drop the old, useless full boolean index.
-- This reclaims disk space and removes the write overhead.
DROP INDEX CONCURRENTLY idx_users_is_deleted;
```

The `CONCURRENTLY` keyword is critical in a production environment. Without it, `CREATE INDEX` acquires a lock that prevents all writes to the table for the duration of the index build — which could be many minutes for a 10 million row table. `CREATE INDEX CONCURRENTLY` builds the index in the background, allowing normal reads and writes to continue, at the cost of taking slightly longer to complete.

## Key Takeaways — The Principles to Carry Forward

The lesson from this case study is not merely a technical trick to memorize. It is a window into how experienced database engineers think. They do not just ask "should I add an index to this column?" They ask "what is the **data distribution** of this column, and does an index on it actually help the **query planner** make better decisions?" They think about the **cost of maintaining** an index, not just the benefit of using it. They understand that a query planner is a sophisticated, statistics-driven decision engine, and they learn to work with it rather than against it.

A full index on a boolean column is almost always a mistake. Boolean columns, by definition, have the lowest possible cardinality — two distinct values. Unless your data is approximately evenly split between `true` and `false`, a full index will either be ignored by the planner for the majority value, or it will be used but provide only marginal benefit. The correct tool is always the partial index, scoped precisely to the value or values that represent the minority of your data — the rare rows that queries actually need to find efficiently.

Every time you find yourself writing `WHERE some_boolean_column = true/false` in a performance-critical query, stop and ask yourself: "What percentage of the table does this condition match? Should I be using a partial index here?" That habit of questioning, rather than blindly adding indexes, is what separates a developer who writes database queries from one who truly understands database engineering.
