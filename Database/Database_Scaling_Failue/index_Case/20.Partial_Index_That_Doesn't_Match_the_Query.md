# The Partial Index That Doesn't Match the Query

### A PostgreSQL Performance Case Study — Explained for Beginners

---

## Introduction: Close Enough Is Not Close Enough

There is a particular kind of frustration that experienced backend developers know well — the frustration of doing the right thing and having it not work. Not because the technique is wrong, but because the technique has a precision requirement that was not fully understood. You followed the advice. You created the partial index. You checked that the column is indexed. And yet the query planner ignores the index entirely, runs a sequential scan, and the query is just as slow as before you did any of this.

This is the case study of partial indexes and the exactness they demand. A partial index is one of PostgreSQL's most powerful and most underused features. When applied correctly, it creates a tiny, highly selective index that covers only the rows your queries actually care about — making reads blazing fast and keeping the index small enough that write overhead is minimal. But partial indexes operate under a rule of strict logical implication that has no tolerance for approximation. "Close enough" is not the same as "logically implies," and the query planner is not forgiving about the difference.

Understanding why this happens requires building a careful mental model of what a partial index actually is, how the query planner decides whether to use one, and what the precise mathematical relationship must exist between a query's `WHERE` clause and an index's `WHERE` clause for the planner to consider the index eligible. This is not a complex concept once it is explained correctly — but explained incorrectly, or not explained at all, it produces exactly the kind of invisible performance failure this case study is about.

---

## Chapter 1: What a Partial Index Actually Is

Before examining the failure mode, let us establish a thorough understanding of what a partial index is and why it exists.

A regular index — the kind you create with `CREATE INDEX idx_orders_user_id ON orders(user_id)` — covers every single row in the table. If the `orders` table has ten million rows, the index has ten million entries. This is appropriate when your queries need to access rows from any part of the table's data distribution.

A **partial index** is an index that covers only a subset of a table's rows — specifically, the rows that satisfy a `WHERE` clause specified at index creation time. That `WHERE` clause is called the **index predicate**. When you write:

```sql
CREATE INDEX idx_orders_active_user ON orders(user_id)
WHERE status = 'active';
```

You are telling PostgreSQL: _"Build an index on the `user_id` column, but only include rows where `status = 'active'`."_ Every row in the `orders` table where `status` is anything other than `'active'` — rows where `status = 'completed'`, `'cancelled'`, `'pending'`, `'refunded'` — is completely absent from this index. It does not exist in the index structure at all.

The power of this becomes obvious when you consider data distributions in real applications. In a typical order management system, the vast majority of orders are in a terminal state — `'completed'` or `'cancelled'` — and only a small, active fraction are in an `'active'` state. If 95% of orders are completed and 5% are active, a partial index on the `'active'` subset covers only 5% of the rows that a full index would cover. It is approximately 20 times smaller, 20 times faster to scan, consumes 20 times less memory in the shared buffer cache, and generates 20 times less write overhead for maintenance.

```
Full Index vs. Partial Index — Physical Size Comparison:

  orders table: 10,000,000 rows
  status distribution:
    'completed':  8,500,000 rows  (85%)
    'cancelled':  1,000,000 rows  (10%)
    'active':       500,000 rows  ( 5%)  ← the only rows we query frequently

  ┌──────────────────────────────────────────────────────────┐
  │ Full Index: CREATE INDEX ON orders(user_id)              │
  │                                                          │
  │ Index entries: 10,000,000                                │
  │ Index size: ~800 MB                                      │
  │ Write overhead: maintained on every INSERT/UPDATE/DELETE │
  └──────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────┐
  │ Partial Index: CREATE INDEX ON orders(user_id)           │
  │               WHERE status = 'active'                   │
  │                                                          │
  │ Index entries: 500,000  (only active rows)               │
  │ Index size: ~40 MB  (20× smaller)                        │
  │ Write overhead: only maintained when status = 'active'   │
  └──────────────────────────────────────────────────────────┘

  Same query speed benefit. One twentieth of the cost.
  This is why partial indexes are so powerful when used correctly.
```

The efficiency gains are genuine and significant. But those gains depend entirely on the query planner being willing to use the partial index — and that willingness is governed by a rule of strict logical implication that the developer creating the index must understand precisely.

## Chapter 2: The Rule of Logical Implication

The rule that governs whether the query planner will use a partial index is called the **constraint exclusion** rule, and it can be stated as follows:

> _The query planner will use a partial index only if the query's `WHERE` clause logically implies the index's `WHERE` clause — meaning that any row satisfying the query's condition is guaranteed to also satisfy the index's predicate._

This is a statement of formal logic, and it needs to be understood as such. Let us make it concrete.

The partial index has the predicate `WHERE status = 'active'`. For the planner to use this index, it needs to be certain that every row the query might retrieve is a row that exists in the index. If the query could potentially retrieve a row where `status = 'pending'`, that row does not exist in the index — and therefore the index cannot be trusted to return complete results. The planner will not use it.

The test is not "does the query mention `status = 'active'`?" The test is a strict logical one: _"Is it mathematically impossible for any row matching the query's `WHERE` clause to have `status` be anything other than `'active'`?"_ Only if the answer is yes — only if the query's `WHERE` clause is logically stronger than the index's predicate — will the planner consider the index eligible.

Let us trace through several examples to make this rule visceral:

```
Partial Index Predicate: WHERE status = 'active'

Query 1: WHERE user_id = 1 AND status = 'active'
  Can this query return a row where status ≠ 'active'? NO.
  The AND status = 'active' condition is explicit.
  The query's WHERE logically implies the index's WHERE.
  → Planner WILL use the partial index. ✓

Query 2: WHERE user_id = 1
  Can this query return a row where status ≠ 'active'? YES.
  It returns ALL orders for user 1, regardless of status.
  The query's WHERE does NOT imply the index's WHERE.
  → Planner WILL NOT use the partial index. ✗

Query 3: WHERE user_id = 1 AND (status = 'active' OR status = 'pending')
  Can this query return a row where status ≠ 'active'? YES.
  A row with status = 'pending' satisfies this WHERE clause
  but does NOT exist in the partial index.
  The query's WHERE does NOT logically imply the index's WHERE.
  → Planner WILL NOT use the partial index. ✗

Query 4: WHERE user_id = 1 AND status IN ('active', 'pending')
  Logically identical to Query 3. IN is syntactic sugar for OR.
  Can this return status = 'pending' rows? YES.
  → Planner WILL NOT use the partial index. ✗

Query 5: WHERE user_id = 1 AND status = 'active' AND created_at > NOW() - INTERVAL '7 days'
  Can this return status ≠ 'active' rows? NO.
  The additional AND condition makes it MORE restrictive,
  not less. It still logically implies status = 'active'.
  → Planner WILL use the partial index. ✓
```

The pattern emerging from these examples reveals something important: the `AND` operator is the friend of partial index eligibility, and the `OR` operator is its enemy. Adding `AND` conditions to a query makes its `WHERE` clause more restrictive — it narrows the set of rows that can be returned, which means it is more likely (not less) to logically imply the index's predicate. Adding `OR` conditions makes the `WHERE` clause less restrictive — it widens the set of rows that can be returned, potentially including rows that are outside the index's coverage.

## Chapter 3: The Exact Failure Mode — The OR That Breaks Everything

The specific scenario described in this case study is worth examining in complete detail because it represents the failure mode that catches developers most often. The partial index and the query look superficially related. They both involve `status` and `user_id`. A developer reading both, quickly, might conclude they are compatible. The planner's rejection of the index seems arbitrary and mysterious — until the logic is traced carefully.

The partial index:

```sql
CREATE INDEX idx_orders_active_user ON orders(user_id)
WHERE status = 'active';
```

The query:

```sql
SELECT * FROM orders
WHERE user_id = 1
  AND (status = 'active' OR status = 'pending');
```

Let us apply the logical implication test very carefully to this pair.

The index predicate says: _"Only rows where `status = 'active'` are in this index."_

The query says: _"Give me all rows for user 1 where status is either `'active'` OR `'pending'`."_

Now apply the test: _"Is it possible for the query to request a row that is not in the index?"_ Absolutely yes — any row with `status = 'pending'` satisfies the query's `WHERE` clause perfectly, but `status = 'pending'` rows are completely absent from the index. If the planner used the index, it would return results for `status = 'active'` rows but silently omit all `status = 'pending'` rows. The query result would be wrong.

The planner is not being unreasonable. It is being correct. The index cannot serve this query because the index does not contain all the rows the query is entitled to return. Using the index would produce incorrect results, and PostgreSQL will never sacrifice correctness for performance.

```
The Logic of Incompatibility, Visualized:

  Index Coverage                  Query Coverage
  (WHERE status = 'active')       (WHERE status = 'active' OR status = 'pending')

  ┌─────────────────────┐         ┌──────────────────────────────────────────┐
  │                     │         │                                          │
  │   status='active'   │         │   status='active'  │  status='pending'  │
  │   rows (500K)       │         │   rows (500K)      │  rows (200K)       │
  │                     │         │                                          │
  └─────────────────────┘         └──────────────────────────────────────────┘
        Index covers                      Query needs BOTH regions
        only this region                  Index covers only the LEFT half

  The query asks for more than the index contains.
  The planner CANNOT use the index without returning incomplete results.
  It falls back to a sequential scan of the full table.
```

The cruelty of this failure mode is that the developer can look at the query, see that it includes `status = 'active'` as one of its conditions, and believe the index should be used for at least the `'active'` half of the result set. This intuition is not entirely wrong — in fact, PostgreSQL _can_ in some cases use a partial index for one branch of a query and combine it with other scans. But the conditions under which this happens are specific and complex, and the general rule remains: if the query's `WHERE` clause is not a logical superset of the index's predicate, the planner will not choose the index as the primary access path.

## Chapter 4: The Superset Principle — Understanding Logical Strength

The relationship required between a query's `WHERE` clause and a partial index's predicate can be expressed precisely using the concept of **set containment**. Think of every possible `WHERE` clause as describing a _set of rows_ — the set of all rows in the table that satisfy that condition.

A query's `WHERE` clause is a **superset** of an index's predicate if every row that satisfies the index predicate also satisfies the query condition. In mathematical notation: if `P` is the set of rows satisfying the index predicate and `Q` is the set satisfying the query condition, then `P ⊆ Q` (P is a subset of Q, or equivalently, Q is a superset of P).

When `P ⊆ Q`, the planner knows: _"Every row in this index is a row the query is interested in. The index contains a subset of the query's answer. I can use the index to find those rows, and I know I won't be missing any index rows that the query needs."_

When `P ⊄ Q` — when the index predicate describes rows that are _not_ in the query's scope — the reverse situation holds but does not help. And when the query's scope extends _beyond_ the index's coverage — as in the OR example — the planner knows it cannot get a complete answer from the index alone.

```
Set Containment Visualized:

  Case 1: Query WHERE is a superset of Index WHERE
  ─────────────────────────────────────────────────
  Index predicate P:  {rows where status = 'active'}
  Query condition Q:  {rows where status = 'active' AND user_id = 1}

  Wait — this is WRONG direction. Let's restate:
  Index predicate P: {rows where status = 'active'}     500K rows
  Query condition Q: {rows where status = 'active'
                      AND user_id = 1}                    ~20 rows

  Q ⊆ P here, meaning every row the query wants IS in the index.
  The index is a superset of what the query needs.
  → Planner CAN use the index. ✓

  Case 2: Query WHERE extends beyond Index WHERE
  ─────────────────────────────────────────────────
  Index predicate P: {rows where status = 'active'}     500K rows
  Query condition Q: {rows where status = 'active'
                      OR status = 'pending'}             700K rows

  Q ⊄ P — some rows in Q (the 'pending' rows) are NOT in P.
  The index cannot return a complete answer for Q.
  → Planner CANNOT use the index. ✗

  The Correct Mental Model:
  "Will every row the query returns be found in the index?"
  If YES → Index eligible.
  If NO  → Index cannot be used, planner falls back to seq scan.
```

The cleaner way to remember this rule is a single question you ask yourself when creating a partial index: _"Will every row my query might return be guaranteed to satisfy the index's predicate?"_ If there is any row the query could legitimately return that does not satisfy the predicate — any row that would be absent from the index — the index cannot serve that query.

## Chapter 5: Diagnosing the Problem — EXPLAIN ANALYZE and pg_stat_user_indexes

When a partial index is not being used, the diagnosis is straightforward using the same two tools from the previous case studies: `EXPLAIN ANALYZE` and `pg_stat_user_indexes`.

`EXPLAIN ANALYZE` tells you immediately whether the planner chose the index or a sequential scan, and — critically — it tells you what it chose and why it estimated the costs the way it did:

```sql
-- Run this on the problematic query:
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders
WHERE user_id = 1
  AND (status = 'active' OR status = 'pending');

-- Example output when partial index is NOT being used:
-- Seq Scan on orders
--   (cost=0.00..210580.00 rows=12 width=184)
--   (actual time=0.421..8943.221 rows=7 loops=1)
--   Filter: ((user_id = 1) AND ((status = 'active') OR (status = 'pending')))
--   Rows Removed by Filter: 9999993
-- Planning Time: 0.7 ms
-- Execution Time: 8943.8 ms   ← 9 seconds for 7 rows!

-- Now compare with a query the partial index DOES serve:
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders
WHERE user_id = 1
  AND status = 'active';

-- Example output when partial index IS being used:
-- Index Scan using idx_orders_active_user on orders
--   (cost=0.29..8.31 rows=3 width=184)
--   (actual time=0.021..0.034 rows=3 loops=1)
--   Index Cond: (user_id = 1)
--   Filter: (status = 'active')
-- Planning Time: 0.3 ms
-- Execution Time: 0.1 ms      ← 0.1 milliseconds for 3 rows
```

The difference in execution time — nine seconds versus a tenth of a millisecond — for logically similar queries demonstrates precisely why it matters whether the partial index is eligible. And the output makes the planner's reasoning transparent: in the first query, it sees a sequential scan because the `OR` condition prevents index use; in the second, it navigates directly through the partial index.

`pg_stat_user_indexes` confirms the diagnosis at a broader level:

```sql
-- Check if the partial index has ever been used:
SELECT
    indexrelname    AS index_name,
    idx_scan        AS times_used,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY idx_scan ASC;

-- A partial index with idx_scan = 0 after weeks of production
-- traffic almost certainly has an eligibility problem:
-- a query pattern mismatch between what was indexed and what
-- the application actually queries.
```

A partial index showing `idx_scan = 0` over a representative observation window is the clearest possible signal that the index and the application's query patterns are not aligned. The index exists, it is valid, the planner can see it — and the planner is rationally choosing never to use it because no query ever presents a `WHERE` clause that logically implies the index's predicate.

## Chapter 6: The Solutions — Aligning Index and Query

Once the mismatch has been diagnosed, there are three solution strategies available, and the correct choice depends on what the application actually needs.

**Solution One: Rewrite the query to match the index.** If the partial index was correctly designed for the dominant query pattern, and the problematic query is a newer addition that deviated from that pattern, the cleanest fix may be to rewrite the query so that its `WHERE` clause logically implies the index predicate.

```sql
-- Original query (breaks partial index eligibility):
SELECT * FROM orders
WHERE user_id = 1
  AND (status = 'active' OR status = 'pending');

-- Rewrite as UNION to serve each status with its own index:
SELECT * FROM orders
WHERE user_id = 1 AND status = 'active'

UNION ALL

SELECT * FROM orders
WHERE user_id = 1 AND status = 'pending';

-- Now create a second partial index for the 'pending' pattern:
CREATE INDEX idx_orders_pending_user ON orders(user_id)
WHERE status = 'pending';

-- Each branch of the UNION uses its matching partial index.
-- Both branches are index scans. No sequential scan needed.
```

The `UNION ALL` approach is genuinely effective when the two status values have meaningfully different query frequencies or data volumes. If `'active'` and `'pending'` orders are both genuinely important subsets, two targeted partial indexes may outperform any alternative.

**Solution Two: Create a partial index whose predicate matches the OR.** If the query pattern — filtering for both `'active'` and `'pending'` orders together — is a genuine and fixed requirement, create a partial index whose predicate exactly covers that combined condition:

```sql
-- Create a partial index that matches the OR condition:
CREATE INDEX idx_orders_open_user ON orders(user_id)
WHERE status = 'active' OR status = 'pending';

-- Now this query is eligible to use the index:
SELECT * FROM orders
WHERE user_id = 1
  AND (status = 'active' OR status = 'pending');

-- The query's WHERE is now logically implied by the index predicate.
-- status must be 'active' or 'pending' for ANY row in this index.
-- The query only requests rows where status is 'active' or 'pending'.
-- → Every row the query wants is guaranteed to be in the index. ✓
```

This works because the predicate `WHERE status = 'active' OR status = 'pending'` in the index matches the condition in the query — any row satisfying `status = 'active' OR status = 'pending'` is in the index, and any row the query returns satisfies `status = 'active' OR status = 'pending'`. The logical implication holds.

**Solution Three: Use a different index type when OR patterns are too variable.** If the `OR` conditions vary widely — sometimes `'active'` only, sometimes `'pending'` only, sometimes both, sometimes with a third status — a partial index may not be the right tool. A composite index on `(user_id, status)` serves all these patterns without the predicate constraint:

```sql
-- A composite index serves all status filter variations:
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- Now all of these queries can use the index:
SELECT * FROM orders WHERE user_id = 1 AND status = 'active';
SELECT * FROM orders WHERE user_id = 1 AND status = 'pending';
SELECT * FROM orders WHERE user_id = 1 AND status IN ('active', 'pending');
SELECT * FROM orders WHERE user_id = 1;  -- uses leftmost prefix
```

The composite index is larger than either partial index (it covers all rows, not just the minority), but it is more flexible. The choice between a partial index and a composite index depends on the specifics: if one or two status values represent a tiny minority of rows and those values are queried with near-exclusive frequency, partial indexes win on efficiency. If query patterns are varied and unpredictable, the composite index's flexibility justifies its size.

## Chapter 7: Common Partial Index Mistakes Beyond OR

The `OR` condition is the most common partial index eligibility trap, but it is not the only one. Several other patterns produce the same failure — the query looks related to the partial index but fails the logical implication test — and being aware of them prevents the same invisible failure from recurring in different forms.

**The NOT condition failure.** A partial index created with a negative predicate can fail in the mirror image of the OR problem:

```sql
-- Partial index on rows where status is NOT 'completed':
CREATE INDEX idx_orders_open ON orders(user_id)
WHERE status != 'completed';

-- This query seems like it should use the index:
SELECT * FROM orders WHERE user_id = 1 AND status = 'active';
-- But this query CAN return status = 'active' rows — can it return
-- status = 'completed' rows? NO. So this should be eligible...
-- Actually, PostgreSQL IS often smart enough to infer this.
-- BUT: This query definitely breaks it:
SELECT * FROM orders WHERE user_id = 1 AND status != 'refunded';
-- Can this return status = 'completed' rows? YES.
-- → Planner CANNOT use the index. ✗
```

**The NULL condition failure.** Partial indexes are frequently created to exclude NULL values, and the matching query must be explicit about this:

```sql
-- Partial index excluding NULLs:
CREATE INDEX idx_orders_with_customer ON orders(customer_id)
WHERE customer_id IS NOT NULL;

-- This query CANNOT use the index:
SELECT * FROM orders WHERE customer_id = 123;
-- Reason: WHERE customer_id = 123 does logically exclude NULLs
-- (NULL = 123 is false), but PostgreSQL's constraint exclusion
-- may not always infer this. Verify with EXPLAIN ANALYZE.

-- This query explicitly matches the predicate and WILL use it:
SELECT * FROM orders WHERE customer_id = 123 AND customer_id IS NOT NULL;
-- Redundant? Yes, logically. But it makes the implication explicit
-- and guarantees the planner recognizes the eligibility.
```

**The parameter substitution failure.** When queries use bound parameters (as all properly written application queries should, for SQL injection prevention), the planner must evaluate eligibility based on the parameter's type, not its runtime value. In most cases this works correctly, but with complex predicates, the planner may not be able to prove at planning time that the parameter value will satisfy the index predicate:

```sql
-- Partial index for a specific category:
CREATE INDEX idx_products_electronics ON products(price)
WHERE category = 'electronics';

-- In application code (Go example):
rows, err := db.QueryContext(ctx,
    "SELECT * FROM products WHERE category = $1 AND price < $2",
    "electronics", 500.00)

-- The planner sees $1 as a parameter placeholder, not the literal
-- string 'electronics'. It may or may not recognize that $1 = 'electronics'
-- implies the index predicate. In PostgreSQL, for simple equality
-- predicates, this usually works. But for complex predicates,
-- ALWAYS verify with EXPLAIN ANALYZE using the actual values:
EXPLAIN ANALYZE
SELECT * FROM products
WHERE category = 'electronics' AND price < 500.00;
```

## Chapter 8: Testing Partial Index Eligibility — A Disciplined Workflow

Given that partial index eligibility is determined by strict logical rules that are easy to get wrong, the disciplined engineering practice is to **always test eligibility explicitly** before treating a partial index as a solved problem. The workflow is simple but must become a habit.

Step one is to create the partial index with a clearly documented comment explaining its intended query pattern. This is not just good hygiene — it is a reference point for future engineers who need to understand why the index exists and what queries it serves:

```sql
-- Clearly document the intended query pattern:
CREATE INDEX idx_orders_active_user ON orders(user_id)
WHERE status = 'active';
-- Intended query: SELECT ... FROM orders WHERE user_id = $1 AND status = 'active'
-- Owner: Order Processing Service
-- Created: [date], Ticket: [link]
-- Review after: 90 days, verify idx_scan > 0
```

Step two is to run `EXPLAIN ANALYZE` immediately after creating the index, using the exact query the index is intended to serve, and verify that the output shows an **Index Scan** (not a Seq Scan) referencing the new index by name:

```sql
-- Immediately after CREATE INDEX, verify usage:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE user_id = 42
  AND status = 'active';

-- What you want to see in the output:
-- Index Scan using idx_orders_active_user on orders
--   Index Cond: (user_id = 42)
-- ← The index name confirms the partial index is being used.

-- What is a red flag:
-- Seq Scan on orders
--   Filter: ((user_id = 42) AND (status = 'active'))
-- ← The planner chose not to use the index. Something is wrong.
```

Step three is to test boundary cases — the queries that seem similar but might break eligibility — to confirm the index is not being used for queries it should not serve:

```sql
-- Boundary test: OR condition (should NOT use the partial index):
EXPLAIN SELECT * FROM orders
WHERE user_id = 42
  AND (status = 'active' OR status = 'pending');
-- Expected: Seq Scan (or a different index). Not idx_orders_active_user.

-- Boundary test: Missing the status condition (should NOT use it):
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- Expected: Seq Scan or full index. Not idx_orders_active_user.
```

This boundary testing is important for two reasons. First, it confirms your logical implication reasoning was correct. Second, it prevents a false confidence scenario where the index happens to be used for a nearby query through some quirk of the planner, which could change after a PostgreSQL version upgrade or statistics update.

## Chapter 9: When to Choose Partial Indexes and When Not To

This case study should not leave you cautious about partial indexes — it should leave you precise about them. When applied correctly, partial indexes are genuinely one of the best tools in the PostgreSQL performance toolkit. The key is knowing when they are the right choice and when a different design is more appropriate.

Partial indexes are the ideal choice when your data has a clearly asymmetric distribution where a small minority of rows are disproportionately queried. The canonical examples are: a `jobs` table where `status = 'pending'` represents 0.1% of rows but 100% of the operational queries; a `users` table where `email_verified = false` represents 2% of users but is the target of all verification follow-up logic; an `orders` table where `status = 'active'` represents 5% of rows but is queried in every active session. In all these cases, a partial index covering only the minority creates a tiny, fast, inexpensive index that perfectly serves the dominant query pattern.

Partial indexes are less appropriate — or need to be accompanied by additional indexes — when query patterns are genuinely varied: sometimes querying active orders, sometimes pending, sometimes both, sometimes by date range without any status filter. In these cases, the strict eligibility rules of partial indexes mean that a single partial index will serve only one of those patterns, and you end up needing multiple partial indexes or a composite index to cover the rest. At that point, the complexity may outweigh the efficiency benefit.

```
Choosing the Right Index Type:

  Scenario: orders table, 10M rows, query access patterns:

  Pattern A: Query ONLY status='active' orders by user_id      (90% of queries)
  Pattern B: Query ONLY status='pending' orders by user_id     (9% of queries)
  Pattern C: Query EITHER active OR pending by user_id         (1% of queries)

  Best choice:
  CREATE INDEX idx_orders_active_user ON orders(user_id)
    WHERE status = 'active';       ← serves 90% of queries, tiny index

  CREATE INDEX idx_orders_pending_user ON orders(user_id)
    WHERE status = 'pending';      ← serves 9% of queries, tiny index

  Pattern C: rewrite as UNION ALL, each branch uses its partial index.
  Total index size: ~80MB (vs. ~800MB for a full composite index)

  ─────────────────────────────────────────────────────────────────

  Scenario: queries are spread across all statuses and combinations

  Pattern A: WHERE status = 'active' AND user_id = 1         (25%)
  Pattern B: WHERE status = 'pending' AND user_id = 1        (25%)
  Pattern C: WHERE status IN ('active','pending','shipped')   (25%)
  Pattern D: WHERE user_id = 1  (all statuses)               (25%)

  Best choice:
  CREATE INDEX idx_orders_user_status ON orders(user_id, status);
  ← Composite index serves ALL four patterns.
  ← Larger than partial indexes, but necessary for this distribution.
```

## Chapter 10: The Precision That Makes Partial Indexes Powerful

There is a final insight about partial indexes that reframes everything covered in this case study from a limitation into a feature. The strict logical implication rule — the very rule that causes the failure this case study is named after — is also the reason partial indexes are so efficient.

A partial index is small, fast, and cheap to maintain precisely _because_ it is exact. By specifying a precise predicate, you are making a binding declaration to PostgreSQL: _"I guarantee that all queries using this index will only need rows satisfying this condition."_ In exchange for that guarantee, PostgreSQL gives you an index that is radically smaller and faster than any general-purpose alternative. The strictness is the trade-off. Exactness in, efficiency out.

When a partial index fails — when it sits with `idx_scan = 0` because no query's `WHERE` clause logically implies its predicate — the failure is informative. It is telling you that the guarantee you thought you were making was not actually being made. Your queries have a wider scope than your index covers. The fix is to either narrow the queries (when the OR pattern was unintentional and can be eliminated) or widen the index predicate (when the OR pattern is legitimate and the index needs to cover it).

Either way, the fix is a question of alignment: ensuring that the index predicate and the query's `WHERE` clause describe the same logical set of rows, with the query's set being a subset of the index's set. When that alignment exists, partial indexes are one of the most elegant and efficient tools PostgreSQL offers. When it does not exist, the planner's rejection of the index is not a failure of PostgreSQL — it is a correct and honest answer to the question of whether the index can safely serve the query.

```
The Precision Principle — Summary:

  Partial Index Predicate          Query WHERE Clause
  ─────────────────────────────────────────────────────────────
  WHERE status = 'active'          AND status = 'active'        → USED ✓
                                   AND status = 'active'
                                   AND created_at > NOW()-'7d'  → USED ✓
                                   (no status filter)           → NOT USED ✗
                                   OR status = 'pending'        → NOT USED ✗
                                   AND status != 'completed'    → NOT USED ✗

  The Rule: Query's WHERE must be a logical subset of Index's WHERE.
  Every row the query returns MUST exist in the index.
  One possible exception row → index is ineligible → seq scan.

  Always verify with: EXPLAIN (ANALYZE, BUFFERS) [your exact query];
  Always audit with:  SELECT idx_scan FROM pg_stat_user_indexes
                      WHERE indexrelname = 'your_partial_index';
```

## Conclusion: Exactness as Engineering Discipline

Partial indexes sit at an interesting intersection in software engineering: they are simultaneously one of the most powerful optimizations available and one of the easiest to get subtly wrong. The power comes from the exactness. The risk comes from the same exactness — because "close enough" produces a zero-scan index that provides no benefit while consuming maintenance overhead.

The senior engineer's discipline when working with partial indexes is threefold. First, understand the logical implication rule deeply enough to evaluate index-query compatibility by inspection, before running a single query. Second, always verify with `EXPLAIN ANALYZE` immediately after creation — never assume. Third, monitor `pg_stat_user_indexes` regularly to catch the silent failure of a partial index that has been outgrown by evolving query patterns.

A partial index with `idx_scan = 0` is not a failed index. It is a precise instrument that was aimed at the wrong target. Adjusting the aim — either by realigning the query or recreating the index with the correct predicate — is usually a small change. Catching it before it has silently wasted months of maintenance overhead is why the monitoring discipline matters.
