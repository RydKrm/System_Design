# The Index Bloat Explosion

### A PostgreSQL Performance Case Study — Explained for Beginners

---

## Introduction: The Slow, Silent Rot

There is a particular category of production database problem that is uniquely cruel in the way it manifests. Unlike a missing index — which causes immediate, obvious slowness from the moment traffic hits a large table — index bloat operates on a completely different timescale. It is invisible at launch. It is invisible after one month. The queries run fine. The dashboards are green. Engineers celebrate a successful deployment.

Then, somewhere between two and six months later, engineers start noticing that certain queries are getting slower. Not dramatically — just a few hundred milliseconds more than before. A week passes, and it is a little slower still. There are no new deployments, no schema changes, no traffic spikes. Nothing has changed, and yet performance is measurably degrading, week over week, in a perfectly steady, linear decline. By the time monitoring alerts fire, the index is three to five times larger than it needs to be, and the database is doing an enormous amount of unnecessary work on every single read.

This is index bloat. It is invisible without monitoring, it compounds continuously over time, and it has brought down systems that appeared perfectly healthy the day before the crisis. Understanding it — not just at the level of "run this command to fix it" but at the level of why PostgreSQL accumulates dead index entries and what that costs at the physical storage level — is one of the most important things a backend developer working with PostgreSQL can learn.

---

## Chapter 1: How PostgreSQL Updates Data — The MVCC Foundation

To understand index bloat, you must first understand how PostgreSQL handles updates and deletes at the storage layer. PostgreSQL uses an architecture called **Multi-Version Concurrency Control**, universally abbreviated as **MVCC**. This architecture is the key to PostgreSQL's ability to allow many readers and writers to operate simultaneously without blocking each other — but it has a very specific physical consequence that creates the bloat problem.

In a naive database design, when you update a row, the database overwrites the old value with the new value in place. The old data is gone. Simple, but problematic — what if another transaction started reading that row a moment before you updated it? That transaction would suddenly see different data mid-read, which leads to inconsistent results and a class of bugs called **phantom reads**.

PostgreSQL solves this by never overwriting data in place. Instead, when you update a row, PostgreSQL:

1. Writes a completely new version of the row to a new location on disk.
2. Marks the old version of the row as "dead" (expired) by recording a transaction ID that indicates it is no longer visible to new transactions.
3. Leaves the old version physically in the table until something comes along to clean it up.

This means that simultaneously, two versions of the same row exist on disk: the old one (visible only to transactions that started before the update) and the new one (visible to transactions that started after). Every active transaction sees a consistent snapshot of the database at the moment it began. No locking required. No blocking. This is the beauty of MVCC.

```
MVCC Update — What Physically Happens on Disk:

  BEFORE UPDATE:
  ┌──────────────────────────────────────────────┐
  │ Table Heap (Physical Pages)                  │
  │                                              │
  │  [Row: id=7, status='pending', xmin=101]     │ ← Live row
  └──────────────────────────────────────────────┘

  AFTER: UPDATE orders SET status='shipped' WHERE id=7;
  ┌──────────────────────────────────────────────┐
  │ Table Heap (Physical Pages)                  │
  │                                              │
  │  [Row: id=7, status='pending', xmin=101,     │
  │         xmax=205]                            │ ← Dead row (marked expired)
  │                                              │
  │  [Row: id=7, status='shipped', xmin=205]     │ ← New live row
  └──────────────────────────────────────────────┘

  Both versions exist on disk simultaneously.
  Old version is INVISIBLE to new transactions but
  PHYSICALLY PRESENT until VACUUM removes it.
```

The cleanup process — the mechanism that eventually removes dead row versions — is called **VACUUM**. It is a background process that periodically scans tables, identifies dead rows that are no longer visible to any active transaction, and marks those physical storage locations as available for reuse.

This architecture is elegant and highly effective for the table data itself. But it creates a very specific and serious problem for indexes.

## Chapter 2: Why Indexes Cannot Use MVCC's Dead Row Strategy

Here is the problem. When PostgreSQL creates a new version of a row (due to an update), it must also update every index that covers any column of that row. The index entry must now point to the new physical location of the row, not the old one.

But here is where the fundamental asymmetry appears. In the table heap (where row data lives), old dead row versions sit quietly, physically present but flagged as invisible. VACUUM eventually reclaims them in bulk. This is efficient.

In the B-Tree index, however, the situation is different. The index is a sorted tree structure. The old index entry — the one pointing to the old, dead row version — cannot simply be left in place and flagged "dead" in the same way, because the B-Tree structure's integrity depends on its sorted properties, and dead entries accumulate without being cleaned up as readily as table heap dead rows are. While VACUUM does eventually clean up dead index entries too, the process is less aggressive, less immediate, and under high write volumes, it often cannot keep up.

The result: under a workload that constantly updates rows — changing order statuses, updating user activity timestamps, flipping boolean flags — the index accumulates a growing population of entries that point to rows that no longer exist in any meaningful sense. These are called **dead index entries** or **dead index tuples**, and they take up physical space in the index's B-Tree pages.

```
B-Tree Index State Under Heavy Updates:

  3 months after launch (high update rate on status column):

  ┌─────────────────────────────────────────────────────────┐
  │              B-Tree Index on orders.status              │
  │                                                         │
  │  Page 1: [→ row_v1 DEAD] [→ row_v3 DEAD] [→ row_v8]   │
  │  Page 2: [→ row_v2 DEAD] [→ row_v5 DEAD] [→ row_v7]   │
  │  Page 3: [→ row_v4 DEAD] [→ row_v6 DEAD] [→ row_v9]   │
  │  Page 4: [→ row_v10]     [→ row_v11]      [EMPTY]      │
  │  ...                                                    │
  │  Page 847: [→ row_v812 DEAD] [→ row_v901]              │
  │                                                         │
  │  Total pages: 847  |  Pages with live data: ~200        │
  │  Bloat ratio: ~4x                                       │
  └─────────────────────────────────────────────────────────┘

  When a query uses this index, PostgreSQL must read ALL
  847 pages — including the 647 that are mostly dead entries.
  That is 4x more disk I/O than should be necessary.
```

The index now has to be read almost entirely — dead entries and all — every time a query uses it. Because the B-Tree structure does not distinguish between a "dead-entry page" and a "live-entry page" when deciding which pages to traverse, the entire bloated structure must be navigated, disk read by disk read.

## Chapter 3: The Tables That Suffer Most

Not all tables accumulate index bloat at the same rate. Bloat is directly proportional to the **write churn** — the rate at which rows are updated or deleted. A read-heavy reference table (like a `countries` table) will have essentially zero bloat. A high-churn operational table will accumulate bloat continuously.

The archetypes of high-churn tables that every production system tends to have are strikingly similar across industries and application domains. An **order status table** in an e-commerce system is a classic example. Every order passes through states — `pending`, `processing`, `payment_confirmed`, `shipped`, `delivered`, `returned` — and each transition is an `UPDATE` on that row. For a platform processing ten thousand orders a day, every single order row is updated five to eight times. The index on the `status` column accumulates dead entries at a relentless pace.

An **event log table** where records are initially written with a processing state and later marked as `processed` or `failed` follows the same pattern. A **user session table** where `last_active_at` is updated on every API request — potentially thousands of times per day per active user — is even more aggressive. A **job queue table** where status flips between `queued`, `running`, and `completed` at high throughput can accumulate bloat faster than almost anything else in a typical application.

```
Bloat Accumulation Rate by Table Type:

  Table Type                      Updates/Day    Bloat Rate
  ──────────────────────────────────────────────────────────
  countries (reference data)      ~0             Negligible
  users (profile updates)         ~1 per user    Very slow
  orders (status transitions)     5-8 per order  Moderate
  sessions (last_active_at)       100s/user/day  Fast
  job_queue (status cycling)      Many/job       Very fast
  event_log (with updates)        Varies         Fast

  Higher write churn = faster bloat accumulation
  Bloat is invisible without monitoring tools
```

The insidious part is the timescale. In the first week after launching a new table, there is essentially no bloat. Performance is excellent. After one month of production traffic, there is modest bloat — perhaps a 1.3x size inflation — and the performance impact is minimal enough to be undetectable in normal monitoring. After three months, the index might be 2x its logical size. After six months, 4x. The degradation is never sudden enough to trigger alerts, and yet the cumulative impact on read performance compounds steadily the entire time.

## Chapter 4: What Bloat Actually Costs — The Physics of Wasted I/O

To make the performance impact of index bloat concrete, we need to talk about what PostgreSQL physically does when it uses a B-Tree index to answer a query.

When a query uses an index, PostgreSQL navigates the B-Tree from the root page down to the leaf pages. The leaf pages are where the actual index entries live — the values of the indexed column paired with the physical location (called a `ctid`, which is a combination of page number and position within that page) of the corresponding table row. To get a leaf page into memory for reading, PostgreSQL must fetch it from disk into the **shared buffer cache** (PostgreSQL's in-memory page cache).

The shared buffer cache is finite in size (configured by `shared_buffers`, typically set to 25% of total RAM). Pages compete for space in it. When a query reads a page from an index, it brings that page into cache. If the cache is full, some other page must be evicted to make room. This is a fundamental trade-off — every wasted page (a page full of dead index entries) that gets read and cached takes up space that a useful page could have occupied.

Now consider the bloated index from our earlier diagram. At 4x bloat, a 200-page worth of useful index data has expanded to 847 physical pages. When a query traverses this index, it must read through all 847 pages, bringing them into the shared buffer cache. It is effectively poisoning the cache with dead data — wasting 75% of both the I/O budget and the cache space that the operation consumes.

```
Impact of Bloat on Shared Buffer Cache Efficiency:

  Healthy Index (1x, no bloat):
  ┌─────────────────────────────────────────────────┐
  │ Shared Buffer Cache (after index traversal)     │
  │                                                 │
  │  ████████████████████████████████  (200 pages)  │
  │  ← All 200 pages contain LIVE, USEFUL data →   │
  │                                                 │
  │  Cache efficiency: 100%                         │
  └─────────────────────────────────────────────────┘

  Bloated Index (4x, 75% dead entries):
  ┌─────────────────────────────────────────────────┐
  │ Shared Buffer Cache (after index traversal)     │
  │                                                 │
  │  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  (647 pages)  │
  │  ← Dead entries — wasted cache space →         │
  │                                                 │
  │  ████████████████████████          (200 pages)  │
  │  ← Live entries — actually useful →            │
  │                                                 │
  │  Cache efficiency: 23%                          │
  │  I/O: 4.2x more than necessary                  │
  └─────────────────────────────────────────────────┘

  The bloated index is evicting useful cached data
  from every other query to make room for dead pages.
```

This is why index bloat causes a slow, compounding performance degradation. As the index grows, each query using it reads more pages, consumes more cache space, triggers more cache evictions, and increasingly forces other queries to re-fetch their data from disk rather than finding it already cached. The system gradually begins thrashing — spending more and more effort on disk I/O for the same amount of useful work.

## Chapter 5: How to See the Bloat — Measuring What Is Invisible

The first step in managing index bloat is making the invisible visible. PostgreSQL provides several tools for this, ranging from rough estimates to highly precise measurements.

The simplest starting point is querying `pg_stat_user_indexes` and `pg_stat_user_tables` together to compare index size against table size. In a healthy database, indexes on high-update tables should not be dramatically larger than the table data itself. When an index is 3x, 4x, or 5x larger than the table it indexes, that is a strong signal of significant bloat.

```sql
-- Rough size comparison: table vs its indexes
SELECT
    t.relname                            AS table_name,
    pg_size_pretty(pg_relation_size(t.oid))  AS table_size,
    i.indexrelname                       AS index_name,
    pg_size_pretty(pg_relation_size(i.indexrelid)) AS index_size,
    i.idx_scan                           AS times_used
FROM pg_stat_user_tables t
JOIN pg_stat_user_indexes i ON t.relname = i.relname
ORDER BY pg_relation_size(i.indexrelid) DESC;
```

For a precise measurement of how much of an index is dead versus live, PostgreSQL provides the `pgstattuple` extension. This extension physically scans the index and reports exactly how many pages contain live data versus dead data. Unlike the simple size query above, `pgstattuple` gives you the actual bloat ratio:

```sql
-- Install the extension (one-time, requires superuser):
CREATE EXTENSION IF NOT EXISTS pgstattuple;

-- Measure bloat on a specific index:
SELECT * FROM pgstatindex('idx_orders_status');

-- Key columns in the result:
-- leaf_pages:       total number of leaf pages
-- dead_leaf_pages:  pages that are entirely dead (reclaimable)
-- avg_leaf_density: percentage of each page that is live data
--                   (below 50% is a clear sign of significant bloat)
```

A healthy index will have an `avg_leaf_density` in the range of 70–90%. An index with significant bloat will show densities of 20–40%, meaning that 60–80% of the space in each page is occupied by dead entries that serve no purpose.

```sql
-- A broader bloat audit query using pgstattuple_approx
-- (faster than pgstatindex for large tables — uses sampling):
SELECT
    indexrelid::regclass  AS index_name,
    (pgstattuple_approx(indexrelid)).dead_tuple_percent AS dead_percent,
    pg_size_pretty(pg_relation_size(indexrelid)) AS current_size
FROM pg_stat_user_indexes
WHERE pg_relation_size(indexrelid) > 10 * 1024 * 1024  -- indexes > 10MB
ORDER BY dead_percent DESC;
```

Running this audit on a production system that has never been monitored for bloat is often a startling exercise. It is common to discover that several critical indexes have dead percentages of 60% or higher — meaning the database has been doing two to three times more I/O than necessary for months.

## Chapter 6: The Fix — `REINDEX CONCURRENTLY`

Once you have identified bloated indexes, the straightforward fix is to rebuild them. Rebuilding an index discards the entire old structure — dead entries and all — and constructs a fresh, compact B-Tree from scratch using only the current live row data. The resulting index is precisely the right size, with maximum data density in every page.

The naive command to rebuild an index is `REINDEX INDEX index_name`. However, this command takes an **exclusive lock** on the table for the duration of the rebuild. For a large, bloated index, the rebuild can take minutes to hours. During that entire time, no reads or writes can touch the table. In a production system with live traffic, this is completely unacceptable.

PostgreSQL provides the solution: `REINDEX CONCURRENTLY`. This variant builds the new index in the background while the old index continues to serve queries. It does not take an exclusive lock. Writes continue to flow. Reads continue to use the old index. Once the new index is fully built and validated, PostgreSQL swaps it in atomically and drops the old structure.

```sql
-- NEVER do this on a live production table:
REINDEX INDEX idx_orders_status;
-- ↑ Takes exclusive lock. Table is completely inaccessible
--   until the rebuild finishes. DO NOT use in production.


-- The correct, safe approach for production systems:
REINDEX INDEX CONCURRENTLY idx_orders_status;
-- ↑ Builds new index in background. Old index serves queries.
--   Zero downtime. Slightly higher write overhead during build.


-- Rebuild all indexes on a table concurrently:
REINDEX TABLE CONCURRENTLY orders;


-- Rebuild all indexes in a schema concurrently
-- (run during low-traffic window for large databases):
REINDEX SCHEMA CONCURRENTLY public;
```

There are a few important caveats with `REINDEX CONCURRENTLY`. It takes longer than a regular `REINDEX` because it must be careful not to interfere with ongoing operations — the same reason it is safer also makes it slower. It also requires additional disk space during the rebuild, because both the old index and the new index exist simultaneously until the swap completes. For very large, very bloated indexes, this can temporarily require significant additional disk space, which is worth accounting for in capacity planning.

If disk space is tight, an alternative for tables with extremely simple access patterns is to drop and recreate the index using `CREATE INDEX CONCURRENTLY`, which accomplishes the same result as `REINDEX CONCURRENTLY` but gives you explicit control over the process:

```sql
-- Step 1: Create new index concurrently (old index still in use)
CREATE INDEX CONCURRENTLY idx_orders_status_new
ON orders(status);

-- Step 2: Verify the new index is valid and used by the planner
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending';

-- Step 3: Drop the old bloated index (instant, no lock required)
DROP INDEX CONCURRENTLY idx_orders_status;

-- Step 4: Rename new index to the expected name
ALTER INDEX idx_orders_status_new RENAME TO idx_orders_status;
```

## Chapter 7: Prevention — Tuning `fillfactor` to Fight Bloat at the Source

Rebuilding a bloated index fixes the current problem. But if the underlying write pattern has not changed — if the table is still a high-churn table with constant updates — the bloat will return. In three months, you will be running `REINDEX CONCURRENTLY` again. And again. This is a maintenance treadmill, not a real solution.

The more elegant approach is to reduce how quickly bloat accumulates in the first place. PostgreSQL provides a setting called **`fillfactor`** that controls how densely the database packs data into a new index page when the index is initially created or rebuilt.

The default `fillfactor` for a B-Tree index is `90`, meaning PostgreSQL fills each new page to 90% capacity, leaving 10% free space. This free space is reserved specifically for future updates — when a row that already has an index entry gets updated, the new index entry can sometimes be placed on the same page as the old entry, rather than having to allocate a new page. This is called a **"HOT update"** (Heap Only Tuple), and it is PostgreSQL's primary mechanism for reducing index bloat on high-update tables.

For tables with very high update rates, setting a lower `fillfactor` reserves more space per page, which dramatically increases the rate of HOT updates and reduces bloat accumulation:

```sql
-- Create an index with lower fillfactor for a high-churn table
-- 70% means 30% of each page is left free for in-place updates
CREATE INDEX idx_orders_status ON orders(status)
WITH (fillfactor = 70);

-- You can also set fillfactor on the TABLE itself,
-- which helps HOT updates work even more effectively:
ALTER TABLE orders SET (fillfactor = 70);

-- After changing table fillfactor, run VACUUM FULL to
-- rebuild with the new density (requires maintenance window):
VACUUM FULL orders;
-- Note: VACUUM FULL takes exclusive lock — use during downtime
```

The trade-off with a lower `fillfactor` is that the initial index is larger than it needs to be at creation time — you are deliberately leaving space empty. A `fillfactor = 70` index uses approximately 43% more pages than a `fillfactor = 100` index of the same data. However, for a high-churn table, this upfront "waste" pays for itself many times over in reduced bloat accumulation over months of production operation.

```
fillfactor Trade-off for a High-Churn Orders Table:

                    fillfactor=90    fillfactor=70
                    (default)        (high-churn tuned)
  ─────────────────────────────────────────────────────
  Initial size:     100 MB           143 MB (+43%)
  Size after 3mo:   380 MB (+280%)   175 MB (+22%)
  Size after 6mo:   620 MB (+520%)   210 MB (+47%)
  REINDEX needed:   Every 2-3 months  Every 8-12 months
  HOT update rate:  Low               High
  ─────────────────────────────────────────────────────

  The 43MB "waste" upfront saves 410MB of bloat after 6 months
  and eliminates two emergency REINDEX operations per year.
```

## Chapter 8: The Role of VACUUM — Automatic Maintenance That Can Fall Behind

PostgreSQL's autovacuum process is the first line of defense against bloat accumulation. When autovacuum runs on a table, it does two things relevant to indexes: it marks dead row versions in the heap as reusable, and it cleans up dead entries in the indexes that cover that table.

However, autovacuum has a fundamental limitation: it is reactive, not proactive. It only triggers when a certain threshold of dead rows has accumulated. By default, this threshold is 20% of the table's row count plus 50 rows. For a very large, high-churn table, this means autovacuum might only trigger after millions of dead rows have already accumulated.

Furthermore, autovacuum is designed to be gentle on the system — it throttles itself to avoid consuming too much I/O and CPU, which means that on a heavily-loaded system, it may not be able to keep up with the rate of dead tuple accumulation. When the rate of dead tuple creation exceeds the rate at which autovacuum can clean them up, bloat grows continuously regardless of autovacuum being active.

```sql
-- Check autovacuum's current performance on your tables:
SELECT
    relname                  AS table_name,
    n_dead_tup               AS dead_tuples,
    n_live_tup               AS live_tuples,
    ROUND(n_dead_tup::numeric /
          NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2)
                             AS dead_percent,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY dead_percent DESC;
```

For tables where autovacuum cannot keep up, you have two options. You can tune autovacuum's aggressiveness per-table, making it trigger more frequently and work faster:

```sql
-- Tune autovacuum specifically for a high-churn table:
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor   = 0.01,  -- trigger at 1% dead rows (not 20%)
    autovacuum_vacuum_cost_delay     = 2,     -- milliseconds between I/O bursts (lower = faster)
    autovacuum_vacuum_cost_limit     = 400    -- work units per vacuum burst (higher = more work done)
);
```

Alternatively, for extremely high-churn tables during business-critical periods, you can manually trigger VACUUM at scheduled intervals:

```sql
-- Manual VACUUM (does NOT take exclusive lock, safe in production):
VACUUM (VERBOSE, ANALYZE) orders;

-- This cleans dead tuples and updates statistics simultaneously.
-- Schedule this during lower-traffic windows for best results.
```

## Chapter 9: Building a Bloat Monitoring Strategy

Since index bloat is invisible without deliberate observation, the correct engineering response is to make it visible through systematic monitoring. A mature PostgreSQL monitoring strategy incorporates three layers of bloat visibility.

The first layer is **size tracking over time**. Recording the physical sizes of your largest indexes daily, and graphing them over time, reveals the characteristic signature of bloat: an index that grows at a rate significantly faster than its underlying table is almost certainly accumulating bloat. If your `orders` table grows by 10% per month but the index on `status` grows by 40% per month, that discrepancy is the bloat making itself visible in size metrics.

```sql
-- Track index sizes (run daily, store results for trending):
SELECT
    schemaname || '.' || indexrelname          AS index_fqn,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    pg_relation_size(indexrelid)               AS size_bytes,
    idx_scan,
    NOW()                                      AS recorded_at
FROM pg_stat_user_indexes
ORDER BY size_bytes DESC
LIMIT 20;
```

The second layer is **periodic bloat ratio checks** using `pgstattuple_approx`. This is more expensive than a simple size query (it samples pages from the index to estimate dead tuple percentages), so it should not run continuously — but scheduling it weekly on your largest indexes gives you a clear picture of bloat health:

```sql
-- Weekly bloat health check (run during off-peak hours):
SELECT
    indexrelid::regclass                   AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS total_size,
    (pgstattuple_approx(indexrelid)).dead_tuple_percent  AS dead_pct,
    (pgstattuple_approx(indexrelid)).avg_leaf_density    AS live_density
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
  AND pg_relation_size(indexrelid) > 50 * 1024 * 1024  -- > 50MB indexes
ORDER BY dead_pct DESC;
```

The third layer is **alerting on thresholds**. Any index with a dead tuple percentage above 30% should trigger an informational notification. Any index above 50% dead should trigger a warning that prompts immediate scheduling of `REINDEX CONCURRENTLY`. This transforms bloat from a silent crisis into a routine maintenance event, caught before it impacts users.

```
Bloat Health Classification:

  dead_tuple_percent    avg_leaf_density    Status & Action
  ─────────────────────────────────────────────────────────────
  0% – 20%              80% – 100%          Healthy. No action.
  20% – 35%             65% – 80%           Acceptable. Monitor closely.
  35% – 50%             50% – 65%           Elevated. Schedule REINDEX.
  50% – 70%             30% – 50%           Warning. REINDEX soon.
  70%+                  < 30%               Critical. REINDEX immediately.
  ─────────────────────────────────────────────────────────────
```

## Chapter 10: The Complete Mental Model — Lifecycle of a Bloated Index

To solidify everything covered in this case study, here is the complete lifecycle of index bloat on a high-churn table, from creation to crisis to recovery to prevention:

```
Birth (Month 0):
  Table created. Index created. fillfactor default (90).
  Pages: 100 | Dead: 0% | Performance: Excellent

Growing (Month 1–2):
  High update rate. VACUUM runs but cannot fully keep pace.
  Pages: 180 | Dead: 20% | Performance: Excellent (bloat not felt yet)

Degrading (Month 3–4):
  Bloat compounds. Index pages mostly contain dead entries.
  Pages: 320 | Dead: 45% | Performance: Noticeably slower
  Engineers: "Hmm, queries seem a bit slower lately..."

Crisis (Month 5–6):
  Index is 4x logical size. Queries read 4x unnecessary data.
  Pages: 420 | Dead: 65% | Performance: Significantly degraded
  Engineers: "Something is wrong — paging DBA..."

Recovery:
  REINDEX CONCURRENTLY idx_orders_status;
  Pages: 100 | Dead: 0% | Performance: Excellent again
  Time taken: 15–45 minutes depending on index size

Prevention (Post-Recovery):
  ALTER INDEX idx_orders_status SET (fillfactor = 70);
  REINDEX CONCURRENTLY idx_orders_status;  (apply new fillfactor)
  Tune autovacuum thresholds on orders table.
  Add weekly pgstattuple monitoring.
  Pages grow much more slowly. REINDEX needed annually, not quarterly.
```

The key insight from this lifecycle is that index bloat is not an emergency that appears suddenly — it is a slow drift away from optimal conditions. The engineers who handle it best are not the ones who react fastest to the crisis at month six, but the ones who caught the trend at month two and scheduled a quiet maintenance window before users ever noticed anything.

## Chapter 11: The `pg_stat_user_indexes` Zero-Scan Audit Revisited

One final monitoring practice connects this case study back to the previous one. After running `REINDEX CONCURRENTLY` or otherwise maintaining your indexes, revisit `pg_stat_user_indexes` and look at the `idx_scan` counts. PostgreSQL resets these counts when an index is rebuilt, which means you can use them as a freshness indicator — an index rebuilt six months ago with `idx_scan = 0` is telling you that in six months of production traffic, not a single query has used it.

```sql
-- Find indexes that are large, potentially bloated, AND unused:
SELECT
    i.schemaname || '.' || i.indexrelname    AS index_name,
    pg_size_pretty(pg_relation_size(i.indexrelid)) AS size,
    i.idx_scan                               AS scans_since_last_reindex,
    t.n_live_tup                             AS table_live_rows
FROM pg_stat_user_indexes i
JOIN pg_stat_user_tables t ON i.relname = t.relname
WHERE pg_relation_size(i.indexrelid) > 10 * 1024 * 1024  -- > 10MB
  AND i.idx_scan < 100           -- barely used
ORDER BY pg_relation_size(i.indexrelid) DESC;
```

An index that is large, heavily bloated, and never used is accumulating the write overhead penalty (every insert and update must maintain it) with zero read benefit. The correct action for such an index is not to rebuild it — it is to drop it. This is one of those cases where the correct fix is radical: the index should not exist at all, and its removal will simultaneously reclaim disk space and speed up every write to the table.

---

## Conclusion: From Firefighter to Custodian

The engineers who handle database performance best over long timescales think of themselves not as firefighters — waiting for crises and then responding heroically — but as **custodians** of a system that requires steady, proactive maintenance to stay healthy.

Index bloat is the canonical example of the problem that custodial thinking prevents and firefighting thinking fails to catch. It grows slowly, invisibly, and continuously. By the time it is obvious to users, it has been obvious to careful monitoring for months. The gap between "obvious to monitoring" and "obvious to users" is exactly the window in which proactive maintenance — a scheduled `REINDEX CONCURRENTLY`, a `fillfactor` adjustment, an autovacuum tuning — costs almost nothing and saves a significant production crisis.

The three disciplines this case study requires you to internalize are: understand that every update and delete on a high-churn table is silently contributing to index bloat; measure that bloat regularly with `pgstattuple` before it becomes a problem; and address it on your schedule — with `REINDEX CONCURRENTLY` and `fillfactor` tuning — not on the database's schedule, which means in the middle of your highest-traffic day when users are already complaining.

```
The Three Disciplines:

  MEASURE:   Weekly pgstattuple_approx on large indexes
             Daily size tracking for trend detection

  MAINTAIN:  REINDEX CONCURRENTLY when dead_pct > 35%
             Schedule during low-traffic windows
             Never use plain REINDEX on live tables

  PREVENT:   fillfactor = 70 on high-churn tables
             Tune autovacuum per-table for fast writers
             Drop indexes with idx_scan = 0 after rebuild
```

A database that is regularly monitored, maintained, and tuned does not have index bloat crises. It has index bloat, managed quietly in the background, at predictable intervals, by engineers who saw it coming and handled it before it became someone else's emergency.
