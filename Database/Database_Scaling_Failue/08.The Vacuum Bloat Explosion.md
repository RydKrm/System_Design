# The Vacuum Bloat Explosion — A Case Study in PostgreSQL's Hidden Maintenance Tax

> *Explained by a senior engineer to someone who is just starting out. This case study is unique to PostgreSQL, and understanding it requires you to learn something that most database courses skip entirely: PostgreSQL does not delete data when you delete it. This sounds absurd, but it is one of PostgreSQL's most powerful architectural decisions — and when you do not maintain it correctly, it becomes one of the most destructive failure modes you will ever encounter in production.*

---

## The Setup — Understanding How PostgreSQL Actually Stores Data

Before we can talk about what goes wrong, you need to understand something fundamental about how PostgreSQL works internally. This is not common knowledge, and most developers spend years using PostgreSQL without ever learning it. But it is the foundation of everything in this case study.

In PostgreSQL, when you run `UPDATE` or `DELETE` on a row, **the old version of the row is not immediately removed from disk**. Instead, PostgreSQL marks the old row as "dead" — it becomes invisible to new transactions, but the physical bytes that represented it remain on disk, occupying space in the table's data files. A new version of the row is written elsewhere on disk. For an `UPDATE`, you end up with two physical copies of the row on disk: the old dead version and the new live version. For a `DELETE`, you end up with one dead version that sits on disk doing nothing except wasting space.

This behavior is not a bug. It is a deliberate architectural choice called **Multi-Version Concurrency Control** (MVCC). It is what allows PostgreSQL to give multiple concurrent transactions a consistent view of the data without readers blocking writers. An old transaction that started before your `UPDATE` can still see the original row value because the original physical bytes are still on disk. The transaction reads the old version; newer transactions read the new version. Both are happy, and neither blocks the other.

```
What happens on disk when you UPDATE a row:

  BEFORE UPDATE:
  ┌─────────────────────────────────────────────────────┐
  │  Table data file (heap)                             │
  │                                                     │
  │  Page 1:                                            │
  │  ┌────────────────────────────────────────────────┐ │
  │  │ Row (id=1, status='pending', txid_min=100)     │ │  ← LIVE row
  │  └────────────────────────────────────────────────┘ │
  └─────────────────────────────────────────────────────┘

  AFTER UPDATE (status = 'completed') at transaction 200:
  ┌─────────────────────────────────────────────────────┐
  │  Table data file (heap)                             │
  │                                                     │
  │  Page 1:                                            │
  │  ┌────────────────────────────────────────────────┐ │
  │  │ Row (id=1, status='pending',  txid_min=100,    │ │  ← DEAD tuple
  │  │      txid_max=200)           [invisible to     │ │    (still on disk!)
  │  │                               new transactions]│ │
  │  ├────────────────────────────────────────────────┤ │
  │  │ Row (id=1, status='completed', txid_min=200)   │ │  ← LIVE tuple
  │  └────────────────────────────────────────────────┘ │
  │                                                     │
  │  Both versions exist physically on disk.            │
  │  The dead one is invisible but occupies real space. │
  └─────────────────────────────────────────────────────┘
```

PostgreSQL has a background process called **VACUUM** whose entire purpose is to go through tables and reclaim the space occupied by these dead tuples. VACUUM identifies dead tuples that are no longer needed by any active transaction, marks their space as reusable, and eventually returns the space for new data. Without VACUUM running regularly, dead tuples accumulate indefinitely. The table grows without limit. Performance degrades. Disks fill up. And this is exactly what goes wrong in the Vacuum Bloat Explosion.

---

## What VACUUM Cannot Do — The Long Transaction Problem

VACUUM has one critical constraint that is the heart of this case study: **VACUUM cannot remove a dead tuple if any currently active transaction could still see that tuple**. Even if the tuple was marked dead a week ago by a committed transaction, if there is a single open transaction anywhere in the database that started before the tuple was deleted, VACUUM must leave it in place. The open transaction might need to see the old version of the data for MVCC consistency.

This is where the "long-running transaction" part of the case becomes catastrophic.

Imagine your company has a data analytics team. Every night at midnight, they run a large analytics job that opens a database connection, starts a transaction, and runs a series of complex queries that take several hours to complete. The transaction starts at midnight and commits at 6 AM. During those six hours, the transaction is "open" — it has a transaction ID (txid) assigned at midnight.

Meanwhile, your production application is running all night long. It processes orders, updates statuses, deletes records, inserts new rows. In a high-write e-commerce system, this might mean millions of UPDATE and DELETE operations between midnight and 6 AM, each one creating dead tuples that pile up on disk.

Here is the disaster: VACUUM cannot remove **any** of those dead tuples created after midnight, because the analytics transaction — which started at midnight — technically could still see them. VACUUM sees the open transaction's transaction ID, sees that the dead tuples were created after that transaction started, and conservatively leaves them all in place. For six hours, dead tuples accumulate at the full rate of your production write load, with VACUUM unable to touch any of them.

```
The Long Transaction Blocking VACUUM:

  Midnight: Analytics job starts transaction (txid = 5000)
  ──────────────────────────────────────────────────────────

  12:01 AM  Production: UPDATE orders... → dead tuple created (txid 5001)
  12:02 AM  Production: DELETE users...  → dead tuple created (txid 5002)
  12:03 AM  Production: UPDATE inventory → dead tuple created (txid 5003)
  ...
  5:59 AM   Production: UPDATE orders... → dead tuple created (txid 86,400)

  VACUUM runs at 1:00 AM and sees:
  "Oldest open transaction is txid 5000 (analytics job).
   Cannot remove any dead tuple with txid > 5000.
   That is ALL dead tuples created since midnight.
   Skipping 85,400 dead tuples. Nothing to reclaim."

  6:00 AM: Analytics job commits. Transaction 5000 closes.
  
  VACUUM now runs again:
  "85,400 dead tuples are now reclaimable. Reclaiming..."
  But by this time, the table has 85,400 dead tuples bloating it.
  
  Next night: the same thing happens again.
  And again. And again. The bloat compounds.
```

After weeks or months of this pattern, the table has accumulated millions of dead tuples that VACUUM reclaims in bursts, but never fast enough to keep up with the rate of accumulation. The table's physical size on disk grows far beyond what the live data would require. A table storing 10GB of live data might physically occupy 100GB on disk because 90GB is dead tuple garbage waiting to be reclaimed.

## Why Bloat Is Catastrophic — The Three Ways It Destroys Performance

Table and index bloat are not just a storage problem. They actively degrade query performance in three distinct and compounding ways.

The first way is through **wasted I/O**. When PostgreSQL reads data from disk, it reads in units called pages, typically 8KB each. A bloated table has many pages filled with dead tuples mixed in with live ones. When PostgreSQL scans the table for a query, it must read those pages — including all the dead tuple space — even though the dead tuples are invisible and useless to the query. A table that should require reading 10GB of data to complete a sequential scan now requires reading 100GB, because 90% of its physical pages contain dead garbage.

```
Effect of bloat on sequential scan:

  Without bloat (10GB live data):
  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
  │L │L │L │L │L │L │L │L │L │L │  All pages are LIVE data
  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
  Read 10GB → find all live rows. Fast.

  With bloat (10GB live + 90GB dead):
  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
  │L │D │D │D │D │D │D │D │D │L │D │D │D │D │D │D │D │D │L │D │
  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
  L = Live page   D = Dead tuple bloat
  Read 100GB → find same live rows. 10× slower.
```

The second way is through **index bloat**. Every index in PostgreSQL is also affected by MVCC. When a row is updated or deleted, the corresponding index entry also becomes dead and must eventually be removed by VACUUM. If VACUUM is blocked, dead index entries accumulate. A bloated index is physically larger than it needs to be, takes more memory to cache, and takes more time to traverse. The B-Tree height may effectively increase because the index is bloated with dead entries, meaning more page reads per lookup.

The third way is through **query plan changes**. PostgreSQL's query planner makes decisions based on table statistics — estimates of how many rows the table contains, how the data is distributed, and how large the table is physically. Autovacuum also runs `ANALYZE` to update these statistics. When a table becomes severely bloated and statistics become stale or misleading, the planner may make incorrect cost estimates and choose a wrong execution plan. It might choose a sequential scan when an index scan would be faster, or choose the wrong join strategy. These plan regressions compound the performance problem in unpredictable ways.

## Autovacuum — The Automatic Defense That Can Fail

PostgreSQL has a background daemon called **autovacuum** that is supposed to run VACUUM automatically on tables that accumulate dead tuples, without requiring manual intervention. For most healthy databases with normal workloads, autovacuum works well and dead tuple accumulation is never noticeable. But autovacuum has limits and tunable parameters that can cause it to fall behind under heavy write workloads.

By default, autovacuum triggers a VACUUM on a table when the number of dead tuples exceeds `autovacuum_vacuum_threshold` (default: 50 rows) plus `autovacuum_vacuum_scale_factor` (default: 20%) of the table's row count. On a table with one million rows, autovacuum triggers when there are more than 200,050 dead tuples (50 + 20% × 1,000,000). On a table with 100 million rows, the threshold is 20,000,050 dead tuples. For a high-write table, you might accumulate 20 million dead tuples quite quickly — but autovacuum waits until you cross that enormous threshold before acting.

Additionally, autovacuum runs with throttled I/O by default to avoid disrupting foreground queries. The parameters `autovacuum_vacuum_cost_delay` and `autovacuum_vacuum_cost_limit` control this throttling. The default settings are conservative — autovacuum runs slowly to be a "nice" background process. On high-write tables on fast modern hardware, this means autovacuum can genuinely run too slowly to keep up with the rate of dead tuple creation, even without a long-running transaction blocking it.

```
Autovacuum can fall behind when:

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  1. Long-running transactions block VACUUM from          │
  │     removing old dead tuples (most common cause)         │
  │                                                          │
  │  2. Scale factor threshold too high for large tables     │
  │     (default 20% means 20M tuples on 100M-row table)    │
  │                                                          │
  │  3. Autovacuum cost throttling too aggressive            │
  │     (default settings designed for spinning disk era)    │
  │                                                          │
  │  4. Too many tables to vacuum simultaneously             │
  │     (autovacuum_max_workers default = 3)                 │
  │                                                          │
  │  5. Autovacuum disabled accidentally or intentionally    │
  │     (never disable autovacuum on production)             │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

## How to Monitor Vacuum Health — What to Watch

Monitoring vacuum health is something every PostgreSQL operator must do. PostgreSQL provides several system catalog views that give you real-time visibility into the state of dead tuple accumulation and VACUUM activity across all tables.

The most important view is `pg_stat_user_tables`, which shows per-table statistics including the number of live rows, dead rows, the time of the last automatic VACUUM run, and the time of the last automatic ANALYZE run.

```sql
-- Find tables with dangerous levels of dead tuple accumulation
SELECT
    schemaname,
    tablename,
    n_live_tup                              AS live_rows,
    n_dead_tup                              AS dead_rows,
    ROUND(n_dead_tup::NUMERIC /
          NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2)
                                            AS dead_pct,
    last_autovacuum,
    last_autoanalyze,
    pg_size_pretty(pg_total_relation_size(
        quote_ident(schemaname) || '.' ||
        quote_ident(tablename))) AS total_size
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;
```

A `dead_pct` above 10–20% on a large table is a warning sign. A `dead_pct` above 50% is an emergency. The `last_autovacuum` column tells you when autovacuum last ran on the table — if this timestamp is hours or days old on a high-write table, autovacuum is falling behind.

To find the long-running transaction that is blocking VACUUM, you can query `pg_stat_activity`:

```sql
-- Find long-running transactions that may be blocking VACUUM
SELECT
    pid,
    usename,
    application_name,
    now() - xact_start    AS transaction_age,
    now() - query_start   AS query_age,
    state,
    LEFT(query, 100)      AS query_snippet
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND now() - xact_start > INTERVAL '5 minutes'
ORDER BY transaction_age DESC;
```

Any transaction older than a few minutes on a high-write database is suspicious. A transaction that has been open for hours — the analytics job in our example — is actively blocking VACUUM from reclaiming dead tuples. Once you identify it, you can either wait for it to complete, or terminate it with `SELECT pg_terminate_backend(pid)` if the business cost of the bloat outweighs the cost of restarting the analytics job.

## The Solutions — Three Layers of Defense

Solving the vacuum bloat problem requires addressing it at three layers: preventing the blocking transaction, tuning autovacuum to be aggressive enough, and repairing tables that have already become bloated.

The first and most important layer is **eliminating long-running transactions from your OLTP workload**. The analytics job that runs a six-hour transaction against the production database should not be running against the production database at all. It should run against a **read replica** — a separate copy of the database that receives streaming replication from the primary but is used exclusively for read-heavy analytical queries. The replica's VACUUM state is independent of the primary's. The analytics job can hold open transactions on the replica for hours without affecting the primary's vacuum health at all.

If a read replica is not immediately available, the analytics job should be restructured to work in short-transaction batches — reading a manageable chunk of data, committing, reading another chunk, committing, and so on — rather than holding one enormous transaction for the entire duration of the job.

The second layer is **tuning autovacuum to be more aggressive** on high-write tables. You can configure autovacuum parameters per-table using `ALTER TABLE ... SET (...)`, which allows you to lower the threshold and scale factor for specific tables that are known to have high write volume, without affecting the global settings for the entire database:

```sql
-- Make autovacuum much more aggressive on a high-write table
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor    = 0.01,  -- Trigger at 1% dead tuples (not 20%)
    autovacuum_vacuum_threshold       = 100,   -- Plus 100 rows minimum
    autovacuum_analyze_scale_factor   = 0.005, -- Re-analyze at 0.5% change
    autovacuum_vacuum_cost_delay      = 2,     -- Faster I/O (ms, lower = faster)
    autovacuum_vacuum_cost_limit      = 400    -- More I/O budget per vacuum cycle
);
```

For modern SSDs, the default cost throttling is far too conservative. Raising `autovacuum_vacuum_cost_limit` and lowering `autovacuum_vacuum_cost_delay` allows autovacuum to run more aggressively on fast storage without meaningfully impacting foreground queries.

The third layer is **repairing tables that are already bloated**. Regular VACUUM can reclaim dead tuple space for reuse by new rows, but it does not return the space to the operating system and does not shrink the physical file. The only way to physically compact a bloated table and return disk space is `VACUUM FULL` — which rewrites the entire table from scratch, but locks the table exclusively for the entire operation (potentially hours on a large table). For production systems, the correct tool is `pg_repack`, an extension that rewrites the table in the background without taking an exclusive lock, allowing your application to continue running normally while the table is being compacted.

```sql
-- pg_repack: compact a bloated table without locking it
-- (must be installed as an extension first)
-- Run from the command line:
-- pg_repack --no-superuser-check -d your_database -t orders

-- Or from within PostgreSQL after installing the extension:
SELECT pg_repack.repack_table('orders');
```

## The Lesson — Vacuum Health Is as Important as Index Health

In any other database system, this case study would not exist. MySQL, SQL Server, Oracle — they all handle dead row cleanup differently and do not require an explicit vacuum process. But PostgreSQL is different, and its MVCC-based architecture makes vacuum a first-class operational concern that you must monitor and maintain just as carefully as you monitor your indexes and query performance.

The mental model shift this case study demands is simple but profound: **in PostgreSQL, a table is not just a collection of live rows. It is a collection of live rows mixed with dead rows of varying ages, and the health of the ratio between them is your ongoing operational responsibility.** Neglect vacuum, and the table degrades. A long-running transaction blocks vacuum, and the table degrades rapidly. A missed autovacuum run on a high-write table, and the table degrades. The degradation is invisible until it is severe, and then it manifests as mysterious slowdowns, changing query plans, and disks that fill up without apparent cause.

Every PostgreSQL operator must have vacuum monitoring in their dashboards. The `n_dead_tup` column in `pg_stat_user_tables` should be tracked and alerted on, just like you would alert on high CPU or high disk usage. The age of the oldest open transaction should be monitored, with alerts firing when any transaction is more than a few minutes old. These are not optional best practices. For a high-write PostgreSQL database, they are survival requirements.
