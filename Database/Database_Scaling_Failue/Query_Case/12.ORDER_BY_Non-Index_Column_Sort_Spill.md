# The ORDER BY Non-Index Column Sort Spill

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. The Query That Hides Its Cost

Imagine you are building a leaderboard for a gaming platform. Millions of players, each with a `score` column updated every time they finish a match. You need the top 100 players. You write:

```sql
SELECT * FROM players ORDER BY score DESC LIMIT 100;
```

In development, with ten thousand players, this query returns in under 10 milliseconds. It feels instant. The query looks clean, the logic is correct, and there is no obvious error to catch. You ship it.

Three months later, your game becomes popular. You now have 50 million players. That same leaderboard endpoint starts taking 40 seconds to respond. Your database server's disk I/O pegs at 100%. Memory consumption spikes every time the query runs. Users see a spinner. The leaderboard — the most visited page on your platform — becomes the most unreliable one.

The `EXPLAIN ANALYZE` output shows something that many developers have never seen before:

```
Sort  (cost=2847291.00..2972291.00 rows=50000000 width=412)
  Sort Key: score DESC
  Sort Method: external merge  Disk: 18432kB
  ->  Seq Scan on players ...
```

Two words that should send a chill down any engineer's spine: **external merge**. The database ran out of memory while trying to sort your data, wrote it to disk, and is now performing a multi-pass merge sort across temporary disk files. This is the **ORDER BY Non-Index Column Sort Spill** — a performance failure that arrives slowly and invisibly, and hits hardest precisely when your application is at its most successful and under its heaviest load.

---

## 2. What the Database Must Do Without a Sorted Index

To understand the problem at its root, you need to understand what a database does when it encounters `ORDER BY` on a column that has no index. There is no shortcut available. The database has exactly one path forward: retrieve every row that might qualify, sort them all, and then return the top portion you asked for.

This process is called a **full sort**. Even though you only want 100 rows, the database cannot know which 100 rows will rank highest without examining every row in the table first. Think about it from first principles: if you have 50 million players and you want the top 100 by score, there is no way to know who those top 100 are without looking at every single score. One player at row 49,999,992 might have the highest score in the entire table. You cannot skip to the top without having seen everything.

```
  The Full Sort Problem — Why LIMIT Doesn't Save You
  =====================================================

  Query: SELECT * FROM players ORDER BY score DESC LIMIT 100

  What you want:    top 100 players by score
  What DB must do:  examine ALL 50 million players

  ┌────────────────────────────────────────────────────────┐
  │  Step 1: Sequential Scan                               │
  │  Read all 50 million rows from disk into memory        │
  │  Cost: full table I/O                                  │
  └─────────────────────────┬──────────────────────────────┘
                            │
                            ▼
  ┌────────────────────────────────────────────────────────┐
  │  Step 2: Sort all 50 million rows by score DESC        │
  │  Memory available (work_mem): 4MB (PostgreSQL default) │
  │  Memory needed: ~50M rows × 412 bytes ≈ 19GB          │
  │  Result: CANNOT FIT IN MEMORY                          │
  └─────────────────────────┬──────────────────────────────┘
                            │
                            ▼
  ┌────────────────────────────────────────────────────────┐
  │  Step 3: Sort Spill to Disk (external merge sort)      │
  │  DB writes sorted chunks to temp files on disk         │
  │  Merges chunks in multiple passes                      │
  │  Reads and writes disk repeatedly                      │
  │  Cost: massive disk I/O, slow, blocks other queries    │
  └─────────────────────────┬──────────────────────────────┘
                            │
                            ▼
  ┌────────────────────────────────────────────────────────┐
  │  Step 4: Return top 100 rows from sorted result        │
  │  49,999,900 rows sorted, processed, and discarded      │
  └────────────────────────────────────────────────────────┘
```

That last detail is the most painful part of this entire picture: 49,999,900 rows were sorted, given an ordering, and then thrown away. You paid the cost for all of them to get the result for 100. The `LIMIT 100` at the end of the query does not reduce the sort cost — it only reduces the final result set size. The sort still happened on everything.

## 3. The Sort Algorithm and Why Memory Matters

PostgreSQL uses a variant of **quicksort** for in-memory sorting and a **disk-based external merge sort** when the data exceeds available memory. Understanding both helps you understand exactly what you are seeing in EXPLAIN and what it costs.

When all the data fits in the memory allocated for sorting — controlled by the `work_mem` parameter in PostgreSQL — the sort is performed entirely in RAM. In-memory quicksort is fast: sorting 50 million integers in 4GB of RAM takes a few seconds. Not great for a real-time API, but manageable.

When the data exceeds `work_mem`, PostgreSQL switches to **external merge sort**. This algorithm works in two phases. In the first phase, PostgreSQL reads as much data as fits in `work_mem`, sorts it in memory, and writes the sorted chunk (called a **run**) to a temporary file on disk. It then repeats this for the next chunk, and the next, until all rows have been processed. In the second phase, PostgreSQL reads all those sorted runs simultaneously and merges them into a final sorted sequence — which it must also write to and read from disk. If there are too many runs to merge in a single pass, it does multiple rounds of merging.

```
  External Merge Sort — What Actually Happens on Disk
  =====================================================

  work_mem = 4MB, table = 50 million rows (~19GB total)

  Phase 1: Create sorted runs
  ────────────────────────────
  Read chunk 1 (4MB) → sort in memory → write sorted run #1 to disk
  Read chunk 2 (4MB) → sort in memory → write sorted run #2 to disk
  Read chunk 3 (4MB) → sort in memory → write sorted run #3 to disk
  ... repeat ~4,750 times ...
  Result: ~4,750 sorted temporary files on disk

  Phase 2: Merge the runs
  ────────────────────────
  Open all 4,750 run files simultaneously
  Repeatedly pick the smallest/largest value across all open files
  Write final merged output to disk
  (May require multiple merge passes if too many runs to merge at once)

  Total disk I/O: ~2× the table size on reads + writes
  Approximate time: minutes, not milliseconds
  Temp disk space consumed: up to 2× the table size

  EXPLAIN shows: Sort Method: external merge  Disk: 18432kB
  ← This number is just the temp space for one sort batch,
    not the total I/O performed
```

The `work_mem` parameter defaults to 4 megabytes in PostgreSQL — a setting designed for databases running on machines with limited RAM in the 1990s. On modern servers with 64GB or 128GB of RAM, this default causes unnecessary sort spills for almost any non-trivial sort operation. Importantly, `work_mem` is the memory limit per sort operation per query — and a complex query might have multiple sort operations happening simultaneously. Setting it too high globally can cause memory exhaustion if many concurrent queries each use their full allocation.

## 4. The Diagnostic Signature in EXPLAIN ANALYZE

The sort spill has a distinctive and unmistakable signature in `EXPLAIN ANALYZE` output. Learning to read it gives you immediate situational awareness when investigating a slow query.

Here is the full diagnostic output for the leaderboard query on a 50-million-row table:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM players ORDER BY score DESC LIMIT 100;
```

```
Limit  (cost=2847291.00..2847291.25 rows=100 width=412)
       (actual time=38291.441..38291.452 rows=100 loops=1)
  Buffers: shared hit=12839 read=391028 temp read=589234 written=591882
  ->  Sort  (cost=2847291.00..2972291.00 rows=50000000 width=412)
             (actual time=38291.439..38291.441 rows=100 loops=1)
        Sort Key: score DESC
        Sort Method: external merge  Disk: 18432kB
        Buffers: shared hit=12839 read=391028 temp read=589234 written=591882
        ->  Seq Scan on players
              (cost=0.00..946531.00 rows=50000000 width=412)
              (actual time=0.024..4821.331 rows=50000000 loops=1)
Planning Time: 0.192 ms
Execution Time: 38291.502 ms   ← 38 seconds
```

The critical signals are scattered through this output, and each one tells you something specific. `Sort Method: external merge` means the sort could not fit in `work_mem` and spilled to disk. `Disk: 18432kB` is the amount of temporary disk space used for this sort batch — if you see this number, the spill happened. `temp read=589234 written=591882` in the Buffers line counts the number of 8KB disk pages read and written for temporary sort files — nearly 600,000 pages written and 600,000 read, over 4.5GB of disk I/O for a single query execution. And `Seq Scan on players` with 50 million rows confirms that the entire table was scanned before sorting.

Compare this to what you see after adding the correct index:

```
Limit  (actual time=0.031..0.114 rows=100 loops=1)
  ->  Index Scan Backward using idx_players_score on players
        (actual time=0.029..0.091 rows=100 loops=1)
Planning Time: 0.144 ms
Execution Time: 0.119 ms   ← 0.1 milliseconds
```

No sort node at all. No sequential scan. No disk writes. The index is already sorted in descending order — the database simply walks the index from the highest value down, collecting rows as it goes, and stops as soon as it has 100. The improvement is not 2× or 10×. It is **321,000×** — 38 seconds versus 0.1 milliseconds.

## 5. Why This Is Particularly Insidious at Scale

Every anti-pattern we have discussed degrades with scale. But the ORDER BY sort spill has a degradation curve that is uniquely punishing because it crosses a phase boundary — the moment the data exceeds `work_mem`. Below that threshold, the sort is in-memory and relatively fast. Above it, the sort moves to disk and becomes catastrophically slow.

```
  Performance Degradation: In-Memory vs Disk Sort
  =================================================

  work_mem = 256MB (generously configured)
  Row size = ~400 bytes

  Rows that fit in memory:  ~640,000 rows

  Rows: 100,000     → In-memory sort  ~15ms  ✅
  Rows: 500,000     → In-memory sort  ~80ms  ✅ (still fits)
  Rows: 700,000     → Spills to disk ~2,100ms ⚠️ (crossed threshold)
  Rows: 1,000,000   → Disk sort      ~3,500ms 🔴
  Rows: 10,000,000  → Disk sort      ~45,000ms 💥
  Rows: 100,000,000 → Disk sort      ~600,000ms ☠️

  Notice the cliff: going from 500K to 700K rows is a 26× performance drop,
  not a proportional 1.4× increase. This is the spill boundary.
  Systems that seem fine at one scale can catastrophically fail
  at a scale that is only slightly larger.
```

The phase transition is particularly dangerous because it can happen between your last load test and your production deployment, or between Tuesday and Thursday after a viral moment brings in a surge of new users. You can go to bed with a healthy system and wake up to pages because a table crossed the sort spill threshold overnight.

This effect is also compounded by concurrency. A single sort spill consuming 18GB of temp disk space is manageable. Twenty concurrent users all requesting the leaderboard simultaneously, each triggering their own sort spill, competing for the same disk I/O bandwidth — that is a full-scale database outage.

## 6. Solution One — Index the ORDER BY Column

The most direct and most effective solution is to create a B-Tree index on the column used in `ORDER BY`. A B-Tree index is, by its nature, a sorted structure. The database does not need to sort data that is already sorted — it simply reads the index in the order you need.

```sql
-- Create the index
CREATE INDEX idx_players_score ON players (score DESC);

-- The query now uses Index Scan Backward — no sort operation at all
SELECT * FROM players ORDER BY score DESC LIMIT 100;
```

When you specify `DESC` in the index definition, PostgreSQL stores the entries in descending order. A query with `ORDER BY score DESC` can then scan the index forward (from the highest value) without even needing to read it backward. For a `LIMIT 100` query, the engine reads exactly 100 index entries and 100 table rows. No matter how many rows exist in the table — 50 million or 500 million — this query always reads exactly 100 entries.

The benefit extends to `LIMIT` queries specifically through an optimisation called **early termination**. When the database can walk a sorted index and collect rows in order, it can stop the moment it has collected enough rows to satisfy the `LIMIT`. This is why an indexed `ORDER BY score DESC LIMIT 100` reads exactly 100 rows regardless of table size — as opposed to an unindexed sort, which must examine everything first.

```
  Indexed ORDER BY with LIMIT — How Early Termination Works
  ==========================================================

  Index on score DESC (entries already in descending order):
  ┌────────────┬──────────────┐
  │ score      │ row pointer  │
  ├────────────┼──────────────┤
  │ 99,842     │ → row #412   │ ← Read row 1  ┐
  │ 99,831     │ → row #8821  │ ← Read row 2  │
  │ 99,819     │ → row #303   │ ← Read row 3  │ Collect 100 rows
  │ 99,801     │ → row #51    │ ← Read row 4  │ then STOP
  │ ...        │ ...          │ ...           │
  │ 99,544     │ → row #9021  │ ← Read row 100│
  └────────────┴──────────────┘ ← STOP HERE ─┘

  Remaining 49,999,900 entries in the index: NEVER READ
  Table rows not in top 100: NEVER READ

  This is O(LIMIT) complexity — completely independent of table size.
  100 rows returned whether table has 10K or 10 billion rows.
```

For composite ORDER BY queries — `ORDER BY category, score DESC` — the index must match the composite sort:

```sql
-- For: ORDER BY category ASC, score DESC LIMIT 100
CREATE INDEX idx_players_category_score ON players (category ASC, score DESC);
```

The column order and sort direction in the index must match the ORDER BY clause exactly, for the same reason composite WHERE indexes must match their query patterns: the sort is hierarchical, and the outer sort must be established before the inner sort is meaningful.

## 7. Solution Two — Increase work_mem for Sort-Heavy Workloads

Sometimes indexing the sort column is not feasible. The sort might be on a computed expression, a column that changes too frequently to index efficiently, or a combination of conditions that produces a different sort order on each query. In these cases, increasing `work_mem` can prevent the disk spill, keeping the sort in memory where it is orders of magnitude faster.

`work_mem` controls the maximum amount of memory that a single sort or hash operation can use before spilling to disk. Increasing it allows larger datasets to be sorted entirely in RAM.

```sql
-- Set work_mem for the current session only (safest approach)
SET work_mem = '256MB';
SELECT * FROM players ORDER BY score DESC LIMIT 100;

-- Or set it for a specific transaction
BEGIN;
SET LOCAL work_mem = '512MB';
SELECT * FROM players ORDER BY score DESC LIMIT 100;
COMMIT;

-- Or increase it globally for sort-heavy database roles
ALTER ROLE analytics_user SET work_mem = '1GB';
```

The key warning with `work_mem` is that it is **per operation, per query, per connection**. If your PostgreSQL server has 64GB of RAM and you set `work_mem = 4GB`, and 20 concurrent users all run sort-heavy queries, the server might attempt to allocate 80GB of RAM — causing the OS to swap memory to disk, which is worse than the sort spill you were trying to avoid.

```
  work_mem — The Global vs Session Risk
  =======================================

  Server RAM: 64GB
  Max connections: 100
  work_mem set globally to: 1GB

  Worst case memory consumption:
  100 connections × 1GB work_mem × (multiple sort ops per query)
  = potential RAM demand far exceeding 64GB

  Safer patterns:
  ┌──────────────────────────────────────────────────────────┐
  │ Keep global work_mem at a conservative value (64MB)      │
  │ Raise it per-session for known sort-heavy operations     │
  │ Set it per-role for analytics users who run big sorts    │
  │ Use SET LOCAL inside transactions to scope it tightly    │
  └──────────────────────────────────────────────────────────┘
```

Increasing `work_mem` is best understood as a tuning knob for sorts that are inherently required by the query's nature — not as a substitute for proper indexing when indexing is applicable.

## 8. Solution Three — Materialised Views for Pre-Sorted Results

For leaderboards and ranked feeds where the ranking changes relatively infrequently — perhaps updated every minute, every five minutes, or on a schedule — the most scalable architectural solution is to pre-compute and pre-sort the ranking into a **materialised view** that is refreshed periodically. The live query then reads from the pre-sorted materialised view, which is simply a table scan of a small, already-ordered result set.

```sql
-- Create a materialised view that pre-computes the top players
CREATE MATERIALIZED VIEW top_players_leaderboard AS
SELECT
    player_id,
    username,
    score,
    rank() OVER (ORDER BY score DESC) AS rank
FROM players
ORDER BY score DESC
LIMIT 1000;

-- Create an index on the materialised view for fast access
CREATE INDEX idx_top_players_rank ON top_players_leaderboard (rank);

-- Refresh the materialised view on a schedule (cron job, pg_cron, etc.)
-- This is the expensive sort — happens once, not per request
REFRESH MATERIALIZED VIEW CONCURRENTLY top_players_leaderboard;

-- Leaderboard query — fast, reads from small pre-sorted table
SELECT * FROM top_players_leaderboard
ORDER BY rank
LIMIT 100;
```

The expensive sort now happens once per refresh cycle — not once per user request. A leaderboard that refreshes every five minutes and receives 10,000 requests per minute has reduced its sort cost by a factor of 50,000. The refresh itself might take 10 seconds on a 50-million-row table, but that 10 seconds happens in the background, not on the critical path of any user's request.

```
  Materialised View — Request Pattern Transformation
  ====================================================

  Without materialised view:
  ─────────────────────────────────────────────────────
  Request 1 → full sort of 50M rows → 38 seconds
  Request 2 → full sort of 50M rows → 38 seconds
  ...
  Request 10,000 → full sort of 50M rows → 38 seconds
  (10,000 users all waiting, DB overwhelmed)

  With materialised view (refreshed every 5 minutes):
  ─────────────────────────────────────────────────────
  Every 5 minutes: background refresh → full sort once → ~10 seconds
  Request 1 → read from pre-sorted view → 0.5ms ✅
  Request 2 → read from pre-sorted view → 0.5ms ✅
  ...
  Request 10,000 → read from pre-sorted view → 0.5ms ✅
  Total sort cost: 1 sort per 5 minutes instead of 10,000 per minute
```

The trade-off is **staleness**: the leaderboard shows the ranking as of the last refresh, not the real-time ranking. For most leaderboards this is perfectly acceptable — players understand that rankings update every few minutes. For real-time financial systems or competitive gaming platforms where millisecond ranking freshness matters, a different approach is needed.

## 9. Solution Four — Redis Sorted Sets for Real-Time Rankings

When real-time ranking freshness is genuinely required and the ranking needs to reflect every score update the moment it happens, a relational database with periodic sort operations is the wrong tool entirely. **Redis Sorted Sets** are purpose-built for exactly this use case.

A Redis Sorted Set stores members (player IDs) each associated with a floating-point score. Internally, Redis maintains this data structure in a way that keeps members always sorted by score — a combination of a skip list and a hash table. Every insert and update operation maintains the sort order automatically, so the top-N query is always instantaneous.

```
  Redis Sorted Set Architecture for Real-Time Leaderboard
  =========================================================

  When a player's score changes (after every match):
  ─────────────────────────────────────────────────────
  1. UPDATE players SET score = 99842 WHERE id = 412   (PostgreSQL — source of truth)
  2. ZADD leaderboard 99842 "player:412"               (Redis — live ranking)

  ZADD is O(log N) — microseconds regardless of leaderboard size

  When a user requests the leaderboard:
  ─────────────────────────────────────
  ZREVRANGE leaderboard 0 99 WITHSCORES  (Redis — top 100 in O(log N + 100))

  Result: sub-millisecond response, always reflects the latest scores
  No sort operation. No disk I/O. No database load.

  Data flow:
  ┌────────────────────────────────────────────────────────┐
  │  Game Server: "Player 412 scored 99842"                │
  └──────┬─────────────────────────────────────────────────┘
         │
         ├─► PostgreSQL: UPDATE players SET score = 99842   (persistence)
         │
         └─► Redis: ZADD leaderboard 99842 "player:412"     (live ranking)

  ┌────────────────────────────────────────────────────────┐
  │  User: "Show me the leaderboard"                       │
  └──────┬─────────────────────────────────────────────────┘
         │
         └─► Redis: ZREVRANGE leaderboard 0 99             (instantaneous)
             (PostgreSQL never touched for leaderboard reads)
```

In Go, the Redis Sorted Set operations are straightforward with the `go-redis` library:

```go
import "github.com/redis/go-redis/v9"

// After a match: update both PostgreSQL and Redis
func UpdatePlayerScore(ctx context.Context, db *sql.DB, rdb *redis.Client,
                       playerID int64, newScore float64) error {

    // Persist to PostgreSQL (source of truth)
    _, err := db.ExecContext(ctx,
        "UPDATE players SET score = $1 WHERE id = $2",
        newScore, playerID)
    if err != nil {
        return err
    }

    // Update Redis Sorted Set (live ranking)
    return rdb.ZAdd(ctx, "leaderboard", redis.Z{
        Score:  newScore,
        Member: fmt.Sprintf("player:%d", playerID),
    }).Err()
}

// Leaderboard request: read entirely from Redis
func GetTopPlayers(ctx context.Context, rdb *redis.Client, limit int) ([]string, error) {
    return rdb.ZRevRange(ctx, "leaderboard", 0, int64(limit-1)).Result()
}
```

The key architectural principle here is **separation of concerns**: PostgreSQL is the durable source of truth for player data, and Redis is the real-time ranking engine. They stay in sync through the update path. Leaderboard reads never touch PostgreSQL at all. Each system is doing what it is best at.

## 10. Choosing the Right Solution

With four distinct solutions available, the right choice depends on how frequently scores change and how fresh the ranking must be:

```
  Decision Framework for Ranked Query Performance
  =================================================

  ┌─────────────────────────────────────────────────────────────────┐
  │ Is the sort column stable or slowly changing?                   │
  │ (e.g. total_purchases, lifetime_value, reputation_score)        │
  └──────┬──────────────────────────────────────────────────────────┘
         │ YES
         ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Add a B-Tree index on the ORDER BY column.                      │
  │ CREATE INDEX idx_... ON table (column DESC);                    │
  │ Best for: any query where indexing is applicable.               │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │ Can the ranking be slightly stale (minutes)?                    │
  │ (e.g. weekly leaderboard, game season rankings)                 │
  └──────┬──────────────────────────────────────────────────────────┘
         │ YES
         ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Materialised view, refreshed on schedule.                       │
  │ Expensive sort happens once per refresh, not per request.       │
  │ Best for: high-read, infrequent-update rankings.                │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │ Does ranking need to be real-time?                              │
  │ (e.g. live match leaderboard, competitive rankings)             │
  └──────┬──────────────────────────────────────────────────────────┘
         │ YES
         ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Redis Sorted Set alongside PostgreSQL.                          │
  │ PostgreSQL = source of truth. Redis = live ranking.             │
  │ Leaderboard reads never touch PostgreSQL.                       │
  │ Best for: real-time rankings, gaming, live competitions.        │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │ Is sort on a computed expression you cannot index?              │
  │ (e.g. ORDER BY (views * 0.6 + likes * 0.4) DESC)               │
  └──────┬──────────────────────────────────────────────────────────┘
         │ YES
         ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Increase work_mem for the session, OR store the computed        │
  │ score as a pre-computed column and index that column.           │
  │ Materialised view or Redis if this is a hot path.               │
  └─────────────────────────────────────────────────────────────────┘
```

## 11. The Pre-Computed Score Column Pattern

One more pattern worth knowing: for ranking queries based on a **formula** — such as a feed ranking algorithm that combines recency, engagement, and relevance scores — you can pre-compute and store the ranking score as a dedicated column, then index that column. This trades write complexity (you must update the column whenever the inputs change) for read performance (the sort is now on a plain indexed column).

```sql
-- Add a pre-computed ranking score column
ALTER TABLE posts ADD COLUMN feed_score FLOAT
    GENERATED ALWAYS AS (
        (EXTRACT(EPOCH FROM created_at) / 86400.0) * 0.4 +
        (likes * 0.35) +
        (comments * 0.25)
    ) STORED;

-- Index the pre-computed score
CREATE INDEX idx_posts_feed_score ON posts (feed_score DESC);

-- The feed query is now a fast indexed scan
SELECT * FROM posts ORDER BY feed_score DESC LIMIT 50;
```

The generated column is computed and stored when a row is inserted or updated. The index on `feed_score` is a plain B-Tree on a simple numeric column. The `ORDER BY feed_score DESC LIMIT 50` query uses early termination — reading exactly 50 index entries regardless of table size.

The trade-off is that updating `likes` or `comments` on a post must now also update `feed_score` and maintain the index. For write-heavy feeds this adds overhead. Whether that trade-off is acceptable depends on your read-to-write ratio — for most content feeds where reads vastly outnumber writes, it is a clear win.

---

## 12. The Golden Rule

> Every `ORDER BY` on a column without a supporting index forces the database to sort the entire qualifying result set before it can return the first row. At small data sizes this is invisible. At scale it becomes a full-table-read followed by either an in-memory sort (acceptable) or a disk-based external merge sort (catastrophic). The `LIMIT` clause offers no protection — the sort happens before the limit is applied. Index the sort column to enable early termination; use materialised views to pre-sort expensive rankings; use Redis Sorted Sets when rankings must be real-time. And when you see `Sort Method: external merge Disk:` in an EXPLAIN output, understand that you are looking at your database writing gigabytes to temporary disk files on every execution of that query.

The sort that looked free in development is paying its bill in production. Now you know exactly what that bill looks like — and how to avoid it.
