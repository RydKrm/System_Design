# The Wildcard Leading LIKE Killer

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — What Even Is a Database Index?

Before we talk about what goes wrong, let us take a moment to understand what a database index truly is, because without that foundation, nothing else will make sense.

Imagine you walk into a massive library with ten million books, and someone asks you to find every book whose title contains the word "keyboard." If the books are arranged randomly on the shelves, you have no choice but to pick up every single book, open the cover, read the title, and decide whether it matches. That is exhausting, slow, and completely unscalable. Now imagine the library has a catalogue — an alphabetically sorted card system where each card points you to the exact shelf and row. You could go straight to the "K" section, find "Keyboard," and retrieve your books in seconds.

A **B-Tree index** in a relational database like PostgreSQL or MySQL is precisely that catalogue. When you create an index on a column, the database builds an internal, sorted tree structure — called a **Balanced Tree** or B-Tree — that organises the values in that column in a predictable, ordered fashion. Every node in this tree stores a range of values and pointers to child nodes, allowing the database engine to perform a technique called **binary search**. Instead of scanning ten million rows one by one, the engine can bisect the tree repeatedly, narrowing down to the target value in a matter of microseconds. The savings in time and CPU are astronomical.

```
                        B-Tree Index on `name` column
                        ================================

                          [ "keyboard" | "monitor" ]
                         /              |              \
          ["apple"..."java"]  ["keyboard"..."laptop"]  ["monitor"..."zebra"]
               |                      |                        |
          [row pointers]        [row pointers]           [row pointers]
```

The critical word here is **sorted**. A B-Tree index only works because the data inside it is in a known, predictable order. The engine can say: "I need everything starting with the letter 'k' — I can jump directly to that section without looking elsewhere." This is what makes indexed lookups blindingly fast.

## 2. The SQL LIKE Operator — A Gentle Introduction

The `LIKE` operator in SQL is one of the most commonly used tools for searching text. It allows you to specify a pattern using two special wildcard characters. The percent sign `%` means "zero or more of any character," and the underscore `_` means "exactly one of any character."

So when you write:

```sql
SELECT * FROM products WHERE name LIKE 'keyboard%';
```

You are asking the database: "Give me every product whose name **begins with** the word 'keyboard'." This is a **trailing wildcard**, and it is perfectly fine. The database can still use a B-Tree index here because it knows exactly where to start its search in the sorted tree — at the point where values begin with "keyboard" — and it reads forward from there.

But when you write:

```sql
SELECT * FROM products WHERE name LIKE '%keyboard%';
```

You are asking something fundamentally different: "Give me every product whose name **contains** the word 'keyboard' **anywhere** — at the beginning, in the middle, or at the end." This is a **leading wildcard**, and it is the heart of the problem we are discussing today.

---

## 3. Why the Leading Wildcard Destroys Index Usage

Here is where the internals truly matter. Remember that a B-Tree is sorted. Its entire purpose is to let you skip to a known starting point. When you ask for `LIKE '%keyboard%'`, you are telling the database that the match can start at **any position** within the string. There is no known starting point. There is no place in the sorted tree where the engine can begin a targeted lookup.

Think of it like this: if someone asks you to find every page in a dictionary that **contains** the sequence of letters "key" somewhere in the page — not necessarily at the start of any word — you cannot use the alphabetical ordering of the dictionary at all. You must read every single page from cover to cover. The dictionary's sorted structure becomes completely useless to you.

The database faces exactly the same problem. When the query planner encounters a leading `%`, it recognises that no amount of navigating the B-Tree will help. The only option is a **sequential scan** — also called a **full table scan** — where the database engine reads every single row in the table, examines the `name` column for each one, and decides whether the pattern matches. Every. Single. Row.

```
  Query: SELECT * FROM products WHERE name LIKE '%keyboard%'

  What the DB Engine Must Do
  ===========================

  Row 1:  "Apple MacBook Pro"      → does it contain 'keyboard'? No.  Skip.
  Row 2:  "Mechanical Keyboard RGB" → does it contain 'keyboard'? Yes! Return.
  Row 3:  "USB-C Hub"              → does it contain 'keyboard'? No.  Skip.
  Row 4:  "Wireless Keyboard Black" → does it contain 'keyboard'? Yes! Return.
  ...
  Row 10,000,000: "Gaming Mouse"   → does it contain 'keyboard'? No.  Skip.

  ❌ B-Tree index: COMPLETELY IGNORED
  ❌ All 10 million rows: READ from disk
  ❌ Result: Full Sequential Scan
```

On a table of one thousand products, this sequential scan completes in a few milliseconds and nobody notices anything wrong. The query feels instant. This is the insidious nature of this particular anti-pattern — it hides during development and testing, only to ambush you in production once real data accumulates.

---

## 4. The Scale Trap — Why Development Never Catches This

This is perhaps the most important lesson any intern or junior developer needs to internalise: **your development database is lying to you.** When you are building a product search feature locally or in a staging environment, you might have a few hundred or a few thousand rows in the `products` table. A sequential scan of one thousand rows takes less than a millisecond. The query returns instantly. You deploy to production feeling confident.

Then, six months later, your product catalogue grows to ten million items. Suddenly, every single search box request on your website triggers a full scan of ten million rows. Each of those scans reads data off disk — a disk that is simultaneously serving thousands of other queries. Your database CPU climbs to one hundred percent. Search requests that used to take 50 milliseconds now take 30 seconds. Users see spinning loaders. The page times out. Your on-call engineers wake up at 3 AM. The business loses revenue every minute.

The timeline of this disaster always follows the same arc:

```
  Performance Timeline
  ====================

  Rows: 1,000       → Query time: ~2ms    ✅ "Works great in dev!"
  Rows: 100,000     → Query time: ~50ms   ⚠️ "A little slow, maybe later..."
  Rows: 1,000,000   → Query time: ~800ms  🔴 "Users are complaining"
  Rows: 10,000,000  → Query time: ~30s    💥 "Site is down. All hands on deck."
```

The reason is linear: a sequential scan's cost grows in direct proportion to the number of rows. Double the rows, double the time. Triple the rows, triple the time. This is called **O(n) complexity** — it scales linearly. A B-Tree index lookup, by contrast, is **O(log n)** — even if you quadruple the data, the lookup time barely increases. The difference between these two growth rates is the difference between a system that scales and one that collapses under its own success.

---

## 5. The Symptoms You Will See in the Real World

When this anti-pattern has taken hold in a production system, you will observe a very specific constellation of symptoms. Knowing how to recognise them is half the battle.

The first symptom is **search page timeout errors**. Users click the search button, and after ten or fifteen seconds, they receive a gateway timeout or a "something went wrong" error. The backend service is waiting on the database, which is grinding through millions of rows and simply cannot finish in time.

The second symptom is **database CPU spikes that correlate exactly with search activity**. If you look at your monitoring dashboards — whether that is Datadog, Grafana, or CloudWatch — you will see the CPU line on your database server jump sharply every time someone uses the search feature, then drop back down when search activity decreases. This is a strong signal that those queries are doing far more work than they should.

The third symptom, and the most technically revealing one, is what you will see when you run `EXPLAIN ANALYZE` on the offending query in PostgreSQL:

```sql
EXPLAIN ANALYZE SELECT * FROM products WHERE name LIKE '%keyboard%';
```

The output will contain a line that reads something like `Seq Scan on products` with a frighteningly high `rows` estimate and actual execution time in the seconds. You will see no mention of an index being used. The query planner is telling you plainly: "I have no choice but to scan everything."

## 6. The Solutions — How Senior Engineers Actually Fix This

Now that we understand the problem deeply, let us walk through the real solutions. There are three main approaches, each appropriate for different situations.

### Solution 1 — PostgreSQL Full-Text Search with tsvector and GIN Index

PostgreSQL has a built-in full-text search system that is remarkably powerful. It works by pre-processing text into a special data type called `tsvector` — a sorted list of **lexemes** (normalised word stems) with their positions within the document. Instead of storing the raw string "Mechanical RGB Keyboard with Backlight," it stores a compact representation like `'backlight':4 'keyboard':3 'mechan':1 'rgb':2`. The language parser strips stop words ("with", "the", "a"), reduces words to their roots ("mechanical" → "mechan"), and records positions.

You then create a **GIN index** (Generalised Inverted Index) on this tsvector column. A GIN index works differently from a B-Tree — instead of sorting values, it builds a mapping from each lexeme to the list of rows that contain it. When you search for "keyboard," the engine goes directly to that lexeme in the GIN index and retrieves only the relevant row pointers. It never touches the rows that do not match.

```sql
-- Step 1: Add a tsvector column to store preprocessed text
ALTER TABLE products ADD COLUMN name_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('english', name)) STORED;

-- Step 2: Build a GIN index on that column
CREATE INDEX idx_products_name_fts ON products USING GIN (name_tsv);

-- Step 3: Query using full-text search operators
SELECT * FROM products
WHERE name_tsv @@ to_tsquery('english', 'keyboard');
```

The `@@` operator is the full-text search match operator. `to_tsquery` converts your search term into a query object that can be matched against the tsvector. This query will use the GIN index and return results in milliseconds even on tables with tens of millions of rows.

```
  Full-Text Search Architecture
  ==============================

  Raw text: "Mechanical RGB Keyboard with Backlight"
       |
       v
  tsvector: 'backlight':4 'keyboard':3 'mechan':1 'rgb':2
       |
       v
  GIN Index (inverted index map):
    'backlight' → [row 5, row 12, row 88, ...]
    'keyboard'  → [row 2, row 5, row 34, ...]   ← query hits here directly
    'mechan'    → [row 5, row 21, row 34, ...]
    'rgb'       → [row 5, row 19, row 34, ...]

  Query: to_tsquery('keyboard')
  Engine: look up 'keyboard' in GIN → fetch rows [2, 5, 34, ...] directly
  ✅ No sequential scan. Blazing fast.
```

### Solution 2 — Trigram Index with pg_trgm Extension

Full-text search is excellent but it has one limitation: it matches whole words. If a user types "keybo" as a partial word (common in autocomplete boxes), full-text search will not find "keyboard." For this use case, **trigram indexing** is the correct tool.

A trigram is simply every sequence of three consecutive characters within a string. The word "keyboard" produces the trigrams: `key`, `eyb`, `ybo`, `boa`, `oar`, `ard`. The `pg_trgm` extension in PostgreSQL indexes all of these trigrams. When you search for `%keybo%`, the engine can look up the trigrams for "keybo" — `key`, `eyb`, `ybo` — and find the intersection of rows containing all of them, without a sequential scan.

```sql
-- Enable the extension (once per database)
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- Create a GIN trigram index on the name column
CREATE INDEX idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);

-- Now your LIKE query will use the index!
SELECT * FROM products WHERE name ILIKE '%keyboard%';
```

The beautiful thing about trigram indexes is that they work transparently with your existing `LIKE` queries. You do not need to change the query syntax — you just need the index to exist, and the PostgreSQL query planner will automatically choose to use it. This makes trigram indexing an excellent quick fix when you need to add search capabilities to an existing system without rewriting queries.

### Solution 3 — Elasticsearch for Serious Search Requirements

For large-scale, complex search requirements — faceted search, relevance ranking, multi-language support, fuzzy matching, synonym expansion, autocomplete with typo tolerance — neither PostgreSQL full-text search nor trigram indexing is sufficient. This is where **Elasticsearch** enters the picture.

Elasticsearch is a dedicated search engine built on top of Apache Lucene. It stores your data in **inverted indexes** optimised specifically for search workloads, distributes data across multiple shards for horizontal scalability, and provides a rich query language for expressing complex search logic. The architecture for using Elasticsearch alongside PostgreSQL looks like this:

```
  Production Search Architecture with Elasticsearch
  ===================================================

  [User types in search box]
          |
          v
  [Application Server]
     |            |
     |            v
     |     [Elasticsearch Cluster]
     |       - Fast full-text search
     |       - Returns matching product IDs
     |            |
     |            v
     v     [Application gets IDs]
  [PostgreSQL]
    - Source of truth for all data
    - Queried by ID (uses primary key index)
    - Returns full product records
          |
          v
  [Results returned to user]

  Sync strategy:
  PostgreSQL → [Change Data Capture / Message Queue] → Elasticsearch
```

When a user searches, the application queries Elasticsearch for matching product IDs using its powerful full-text query language. Elasticsearch returns the IDs in milliseconds. The application then fetches the full product records from PostgreSQL using those IDs — which is an extremely fast primary key lookup. PostgreSQL is the authoritative data store; Elasticsearch is the search index. They are separate concerns serving separate purposes.

## 7. Putting It All Together — Decision Framework

As a developer, you need to know which solution to reach for in which situation. Here is how to think about it.

If your search requirements are modest — straightforward keyword matching, a few million rows, a single language — PostgreSQL full-text search with a `tsvector` column and a GIN index is your first choice. It lives inside your existing database, requires no additional infrastructure, and handles most common use cases beautifully.

If your users need substring matching or autocomplete where they type partial words and expect instant results, add a `pg_trgm` trigram GIN index on top. It is low-effort, requires no query rewrites, and is surprisingly effective even at tens of millions of rows.

If you are building a product with serious search at its core — a marketplace, an e-commerce platform, a documentation search engine — invest in Elasticsearch from the beginning. The operational overhead of maintaining a separate search cluster pays for itself many times over in search quality and scalability.

What you should never do, under any circumstances, is let a leading wildcard `LIKE` query reach a production database table with significant data volume. It is one of the easiest performance problems to introduce and one of the most painful to diagnose and fix after the fact.

---

## 8. The Golden Rule

> A leading wildcard — `LIKE '%something'` or `LIKE '%something%'` — makes the entire B-Tree index invisible to the database engine. The engine has no choice but to scan every row in the table. On small datasets this is invisible; on large datasets it is catastrophic. The solution is never to optimise the `LIKE` query itself, but to replace the query strategy entirely with a purpose-built search index.

Every time you see a search box wired to a `LIKE '%...'` query against a growing table, you are looking at a ticking time bomb. Now you know exactly why, and exactly how to defuse it.
