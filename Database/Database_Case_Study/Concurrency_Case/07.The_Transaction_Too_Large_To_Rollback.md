# Case Study 07 — The Transaction Too Large to Rollback

---

## The Setup — The Migration That Could Not Undo Itself

A product team decides to backfill a new column. Over the past two years, the `users` table has accumulated 100 million rows, and a new feature requires that every user has a computed value in a column called `normalized_email` — the user's email address, lowercased and trimmed, used for deduplication. The data is all there, the transformation is simple, and a developer writes what appears to be a clean, professional migration script:

```go
func RunEmailNormalizationMigration(db *sql.DB) error {
    tx, err := db.Begin()
    if err != nil { return err }
    defer tx.Rollback()

    log.Println("Starting email normalization for 100 million users...")

    _, err = tx.Exec(`
        UPDATE users
        SET normalized_email = LOWER(TRIM(email))
        WHERE normalized_email IS NULL
    `)
    if err != nil {
        log.Printf("Migration failed: %v — rolling back...", err)
        return err
    }

    log.Println("Migration complete. Committing...")
    return tx.Commit()
}
```

The developer runs this script in staging with 50,000 users. It completes in 3 seconds. Confident, the developer schedules the migration for the production database during a maintenance window on a Saturday night. The migration begins. Hours pass. The migration has processed roughly 99 million rows when the database server's WAL disk fills up — there is not enough disk space to hold the WAL records for 99 million row updates that have not yet been committed. PostgreSQL halts the update with an error: `ERROR: could not write to file "pg_wal/00000001000000350000007A": No space left on device`.

The `defer tx.Rollback()` triggers. And now the real horror begins.

The database must undo 99 million row changes. Every single one of those 100 million UPDATE operations must be reversed — the original `normalized_email = NULL` must be restored, the MVCC dead tuples created by the updates must be handled, the WAL records for the rollback must be written. The rollback takes longer than the original migration. Far longer. It takes seven hours. During those seven hours, the `users` table is effectively locked for most write operations, replication is overwhelmed, and the database appears frozen to monitoring systems. The maintenance window that was scheduled for two hours becomes a nine-hour ordeal that spills into Sunday morning, and at the end of it, the `users` table is in exactly the same state it was before the migration started — 100 million rows with `normalized_email = NULL`. Zero progress has been made. The entire night was lost.

## The Mechanics of Rollback — Why It Costs as Much as the Forward Operation

The most important concept in this case study is understanding that **a transaction's rollback cost is roughly equal to its commit cost**. This is not obvious, and it runs counter to the intuition of many engineers who think of rollback as a "cancel" button that simply discards work. In PostgreSQL's architecture, rollback is not a discard — it is an active undoing of every change that was made, which requires as much I/O and processing as making the changes in the first place.

Here is why. PostgreSQL uses **Write-Ahead Logging (WAL)** for crash recovery and durability. Every modification — every insert, update, and delete — is recorded in the WAL before it is applied to the actual data pages. The WAL record contains enough information to both **redo** the operation (apply it to a page that did not reflect it yet) and **undo** it (reverse it on a page that already reflected it). These are the two halves of the WAL's purpose: redo for crash recovery, undo for rollback.

When a transaction is rolled back, PostgreSQL reads the WAL records for that transaction in reverse order and applies the undo information for each one. For an UPDATE that changed `normalized_email` from NULL to a value, the undo record restores `normalized_email` to NULL. For every one of the 99 million updates that were written to the WAL, there is an undo record that must be processed. This undo processing requires reading the WAL records (I/O), writing the restored values to the data pages (I/O), updating indexes (I/O), and writing WAL records for the rollback itself (more I/O). The rollback can actually be more expensive than the original forward operation because the WAL records may not be in memory anymore — they may need to be read back from disk.

```
The Symmetric Cost of Forward and Rollback Operations:
======================================================================

  Forward Pass (UPDATE 99 million rows):
  +---------------------------------------+
  | For each of 99 million rows:          |
  |  1. Read data page from disk (I/O)    |
  |  2. Acquire row lock (memory)         |
  |  3. Write new value to page (memory)  |
  |  4. Write WAL record (disk I/O)       |
  |  5. Update indexes (disk I/O)         |
  +---------------------------------------+
  Total: ~6 hours of I/O operations
  WAL generated: ~200 GB
  Net result: 99M rows updated, 99M WAL records written

  Rollback (undo 99 million changes):
  +-----------------------------------------------+
  | For each of 99 million WAL records (reversed):|
  |  1. Read WAL record from disk (I/O)           |
  |  2. Read original data page from disk (I/O)  |
  |  3. Restore original value to page (I/O)      |
  |  4. Update indexes back to original (I/O)     |
  |  5. Write rollback WAL record (I/O)           |
  +-----------------------------------------------+
  Total: ~7 hours of I/O (WAL may be cold, more disk reads needed)
  WAL generated during rollback: ~200 GB MORE

  Total I/O cost of the failed migration: ~13 hours, ~400 GB WAL
  Rows actually modified at the end: 0 (back to starting state)
  Progress achieved: NONE
======================================================================
```

The WAL disk filling up during the rollback is a secondary disaster within the primary disaster. The 200 GB of WAL generated by the forward pass may not have fully flushed from disk yet, and the rollback is now generating its own WAL records on top. If the WAL disk fills completely during rollback, PostgreSQL can enter a state where it cannot accept any transactions — including the rollback itself — until disk space is freed. This can render the database entirely unavailable until a database administrator manually intervenes to either free disk space or extend the volume.

## The Three Compounding Disasters

The transaction-too-large-to-rollback failure is not a single problem — it is three separate disasters that occur in sequence, each building on the previous one.

**Disaster One: The Forward Pass Consumes All Resources.** The 99-million-row UPDATE holds exclusive locks on every row it has processed so far. The `users` table is effectively under write lock for hours. Any write operation that needs to modify a row that the migration has already touched must wait for the transaction to commit or roll back. User registration, profile updates, authentication token refreshes — all writes to the `users` table are blocked or severely delayed. The application degrades progressively as the migration advances through more and more of the table. Connection pools fill with waiting write requests.

**Disaster Two: The WAL Disk Fills Up.** PostgreSQL must keep WAL records for uncommitted transactions — these records are needed for crash recovery (to undo the uncommitted changes if the server crashes) and for the rollback itself. A 100-million-row update generates an enormous volume of WAL data. If the WAL disk (or the tablespace containing WAL) does not have sufficient free space, PostgreSQL will eventually fail with a disk-full error. This failure triggers the rollback. Ironically, the rollback itself generates more WAL data — WAL records describing the undo operations — which further stresses the same disk that just ran out of space.

**Disaster Three: The Rollback Freezes the Database.** During rollback, PostgreSQL is exclusively focused on undoing the enormous transaction. The database remains in a state of severe stress — I/O is maxed, WAL is being consumed at a high rate, and the `users` table remains unavailable for writes until the rollback completes. Monitoring systems show the database as "up" (PostgreSQL is running and accepting connections), but queries against the `users` table either timeout or wait indefinitely. The database is functionally frozen from the application's perspective. Engineers watching the monitoring dashboards see a transaction that started six hours ago that appears to be getting older, not younger — because the transaction ID timestamp is the start of the original forward pass, and it is still active because the rollback has not yet completed.

```
The Three-Disaster Timeline:
======================================================================

  t=00:00  Migration begins. 100M row UPDATE starts.
           Locks accumulating on processed rows.

  t=02:00  50M rows updated. WAL: ~100 GB generated.
           Application writes to users table: SLOW (lock waits).
           WAL disk: 60% full.

  t=05:00  99M rows updated. WAL: ~198 GB generated.
           WAL disk: 98% full. Application writes: SEVERE delays.
           Engineers notice latency spike but don't yet know why.

  t=06:00  ERROR: No space left on device (WAL disk full)
           Migration query aborted. defer tx.Rollback() triggers.
           DISASTER TWO begins.

  t=06:01  Rollback starts. Must undo 99 million changes.
           WAL disk: 100% full. Rollback itself needs WAL space.
           DBA must immediately expand disk / delete WAL archives.

  t=06:30  Disk space freed by DBA. Rollback resumes.
           DB I/O: maxed. Rollback reading WAL from disk.
           Application: users table writes completely blocked.
           DISASTER THREE fully in effect.

  t=09:00  Engineers consider killing the rollback.
           (Killing it would require restart + crash recovery = even longer)
           Decision: let the rollback complete.

  t=13:00  Rollback completes. 7 hours of rollback.
           users table: back to original state (normalized_email = NULL).
           AUTOVACUUM: massive backlog of dead tuples to clean.
           Replication lag: peaked at 3 hours, slowly recovering.
           Application: recovering but slow for hours.

  Final state:
  - Migration progress: 0 rows normalized. Zero. Back to start.
  - Time lost: 13 hours (6 forward + 7 rollback)
  - User impact: 13 hours of degraded application performance
  - Remaining work: still 100 million rows to migrate (start over, correctly)
======================================================================
```

## Why Engineers Make This Mistake — The Staging Environment Illusion

The staging environment illusion is the direct cause of this failure, and it is worth understanding deeply because it affects every large-scale data operation. Staging environments are essential for testing code correctness, but they are almost universally inadequate for testing operational safety at scale. The reasons are structural:

Staging databases typically have a small fraction of production data — perhaps 50,000 rows versus 100 million. The migration runs in 3 seconds on staging because 50,000 rows × the per-row processing cost is negligible. The engineer sees success and gains false confidence. What the staging test did not reveal is that 100 million rows × the same per-row cost is a fundamentally different animal — not just 2,000× slower, but 2,000× more WAL generated, 2,000× more locks held simultaneously, and 2,000× more work for the rollback if something goes wrong.

The mental model error is treating database operations as having linear cost with no phase transitions. In reality, large transactions have non-linear cost profiles: at small scale, the cost is compute-bound (CPU doing the transformation); at large scale, the cost becomes I/O-bound (WAL writes, disk access, replication) and resource-bound (WAL disk capacity, lock table memory, connection pool slots). The transition between these regimes happens at a scale that staging environments never reach.

```
The Staging Illusion — Why Testing With Small Data Hides the Problem:
======================================================================

  Staging (50,000 rows):
    Execution time:    3 seconds
    WAL generated:     ~100 MB        (fits easily in buffer)
    Memory for locks:  ~5 MB          (negligible)
    Rollback time:     ~3 seconds     (symmetric)
    Disk space needed: trivial
    Test result:       PASS

  Production (100,000,000 rows):
    Execution time:    6 hours         (2000x longer, I/O bound)
    WAL generated:     ~200 GB         (2000x more, may exceed disk)
    Memory for locks:  ~10 GB          (significant, may cause memory pressure)
    Rollback time:     7 hours         (symmetric + WAL cold = even slower)
    Disk space needed: 400+ GB WAL     (may not have this)
    Test result:       CATASTROPHE

  The problem: Staging tests CORRECTNESS. It cannot test SAFETY at scale.
  The solution: Treat large data operations as operational concerns,
               not just correctness concerns. Plan for scale explicitly.

  Rules for migrating large tables:
  - Count the rows. Know the number before you write a single line of code.
  - Estimate WAL generation (rows * avg_row_size * ~3x for WAL overhead).
  - Ensure WAL disk has 2x that estimate as free space.
  - Batch the operation so rollback cost per unit is small.
  - Design idempotency so partial completion is safe.
  - Test the rollback scenario explicitly.
======================================================================
```

## Solution One — Batched Updates with Progress Tracking

The correct approach is the same discipline we applied to the bulk delete (Case Study 06): break the enormous single transaction into thousands of small transactions, each committing immediately after processing a bounded number of rows. But for data migrations and backfills, there is an additional requirement that does not apply to deletes: the job must be **resumable**. If the migration fails halfway through (disk issue, network partition, job timeout, deployment), you need to be able to restart it from where it left off — not from the beginning.

This requires **idempotent design** and a **progress marker**. Idempotent means that running the migration multiple times produces the same result as running it once. For our email normalization example, the natural idempotency condition is `WHERE normalized_email IS NULL` — rows that have already been processed have a non-NULL `normalized_email`, so the migration naturally skips them on restart.

The progress marker is a record of where the migration last stopped, so on restart it can pick up from the right position without re-scanning already-processed rows:

```go
// The correct migration architecture: batched, committed, idempotent, resumable:

// Step 1: Create a progress tracking table in the database:
const createProgressTableSQL = `
CREATE TABLE IF NOT EXISTS migration_progress (
    migration_name  TEXT PRIMARY KEY,
    last_processed_id BIGINT NOT NULL DEFAULT 0,
    rows_processed  BIGINT NOT NULL DEFAULT 0,
    started_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    status          TEXT NOT NULL DEFAULT 'running'  -- running, completed, failed
);
`

// Step 2: The batch migration function — idempotent, resumable, safely interruptible
func RunEmailNormalizationSafe(db *sql.DB) error {
    const migrationName = "email_normalization_v1"
    const batchSize = 5000
    const sleepBetweenBatches = 100 * time.Millisecond

    // Initialize or resume progress tracking
    _, err := db.Exec(createProgressTableSQL)
    if err != nil { return fmt.Errorf("creating progress table: %w", err) }

    var lastProcessedID int64
    var totalProcessed int64
    err = db.QueryRow(`
        INSERT INTO migration_progress (migration_name, last_processed_id, rows_processed)
        VALUES ($1, 0, 0)
        ON CONFLICT (migration_name) DO UPDATE
            SET last_updated_at = NOW()
        RETURNING last_processed_id, rows_processed
    `, migrationName).Scan(&lastProcessedID, &totalProcessed)
    if err != nil { return fmt.Errorf("initializing progress: %w", err) }

    log.Printf("Resuming email normalization from user ID > %d (already processed: %d rows)",
        lastProcessedID, totalProcessed)

    batchNumber := 0
    for {
        batchNumber++

        // Each iteration is a SEPARATE, SMALL transaction.
        // If this batch fails, only this batch is rolled back (5000 rows max).
        // The migration restarts from lastProcessedID, not from the beginning.

        // Find the next batch of IDs to process (cursor-based, not OFFSET)
        rows, err := db.Query(`
            SELECT id
            FROM users
            WHERE id > $1
              AND normalized_email IS NULL    -- Idempotency: skip already-done rows
            ORDER BY id ASC
            LIMIT $2
        `, lastProcessedID, batchSize)
        if err != nil { return fmt.Errorf("fetching batch %d: %w", batchNumber, err) }

        var batchIDs []int64
        for rows.Next() {
            var id int64
            if err := rows.Scan(&id); err != nil {
                rows.Close()
                return fmt.Errorf("scanning ID: %w", err)
            }
            batchIDs = append(batchIDs, id)
        }
        rows.Close()
        if err := rows.Err(); err != nil { return err }

        // No more rows to process — migration complete!
        if len(batchIDs) == 0 {
            _, err = db.Exec(`
                UPDATE migration_progress
                SET status = 'completed', last_updated_at = NOW()
                WHERE migration_name = $1
            `, migrationName)
            log.Printf("Migration complete! Total rows processed: %d", totalProcessed)
            return err
        }

        // Process this batch in a single, small transaction
        maxID := batchIDs[len(batchIDs)-1]
        minID := batchIDs[0]

        tx, err := db.Begin()
        if err != nil { return fmt.Errorf("beginning batch %d: %w", batchNumber, err) }

        // The actual migration work — bounded to batchSize rows maximum
        result, err := tx.Exec(`
            UPDATE users
            SET normalized_email = LOWER(TRIM(email))
            WHERE id >= $1
              AND id <= $2
              AND normalized_email IS NULL   -- Idempotency guard
        `, minID, maxID)
        if err != nil {
            tx.Rollback()
            // Only 5000 rows need to be rolled back. Not 99 million.
            return fmt.Errorf("batch %d update failed: %w", batchNumber, err)
        }

        rowsUpdated, _ := result.RowsAffected()

        // Update progress in the same transaction — atomic with the data change
        _, err = tx.Exec(`
            UPDATE migration_progress
            SET last_processed_id = $1,
                rows_processed = rows_processed + $2,
                last_updated_at = NOW()
            WHERE migration_name = $3
        `, maxID, rowsUpdated, migrationName)
        if err != nil {
            tx.Rollback()
            return fmt.Errorf("updating progress for batch %d: %w", batchNumber, err)
        }

        if err := tx.Commit(); err != nil {
            return fmt.Errorf("committing batch %d: %w", batchNumber, err)
        }

        // Update local tracking variables
        lastProcessedID = maxID
        totalProcessed += rowsUpdated

        log.Printf("Batch %d: processed IDs %d-%d, updated %d rows (total: %d)",
            batchNumber, minID, maxID, rowsUpdated, totalProcessed)

        // Breathe — let AUTOVACUUM and application queries have some I/O time
        time.Sleep(sleepBetweenBatches)
    }
}
```

```
Batched Migration vs. Single Transaction Migration — Safety Comparison:
======================================================================

  Single Transaction Migration (WRONG):
    Batch 1 of 1:    UPDATE 100M rows...
    If it fails at row 99M: ROLLBACK 99M rows (~7 hours)
    Restart: must begin from row 0 again (no progress saved)
    Worst case: multiple failures = multiple full restarts

  Batched Migration with Progress (CORRECT):
    Batch 1:   UPDATE rows 1-5000.     COMMIT. Progress saved: ID=5000
    Batch 2:   UPDATE rows 5001-10000. COMMIT. Progress saved: ID=10000
    ...
    Batch 9999: UPDATE rows ...        COMMIT. Progress saved: ID=49,995,000
    [FAILURE occurs here]
    Rollback:  Only batch 9999 rolled back. ~5000 rows. ~5ms.
    Restart:   Reads progress table: last_processed_id = 49,995,000.
               Resumes from ID 49,995,001. No work is lost.

    Maximum rollback cost at any failure: 5000 rows * per-row cost
    = seconds, not hours.
======================================================================
```

## The Idempotency Requirement — Why It Is Not Optional

Idempotency deserves its own section because it is the property that makes the batch migration architecture robust under real-world conditions. A migration is idempotent if running it twice — or running it on rows that have already been processed — produces the same result as running it once. Without idempotency, a migration that crashes partway through cannot safely be restarted: you do not know which rows were already processed, and processing them again might corrupt them.

In our email normalization example, idempotency is naturally provided by the `WHERE normalized_email IS NULL` clause. After a batch sets `normalized_email` for a row, that row will not satisfy the `IS NULL` condition on the next run, so it will never be processed again. This is the simplest form of idempotency — the migration condition itself is its own guard.

For migrations where natural idempotency is not available, you must design it explicitly. The most robust approach is to separate the "state before" and "state after" columns:

```go
// For migrations without natural idempotency:
// Bad: UPDATE users SET salary = salary * 1.1 WHERE department = 'engineering'
// This is NOT idempotent. Running twice gives 21% raise, not 10%.

// Good: Use a status column or a separate tracking table:

// Option A: Status column approach
_, err = tx.Exec(`
    UPDATE users
    SET salary = salary * 1.1,
        salary_adjusted_2025 = true    -- New column: marks this row as processed
    WHERE id >= $1 AND id <= $2
      AND salary_adjusted_2025 IS NULL OR salary_adjusted_2025 = false
`, minID, maxID)
// Now idempotent: the flag prevents double-processing.

// Option B: Separate migration tracking table
_, err = tx.Exec(`
    INSERT INTO salary_adjustments_2025 (user_id, old_salary, new_salary, processed_at)
    SELECT id, salary, salary * 1.1, NOW()
    FROM users
    WHERE id >= $1 AND id <= $2
      AND id NOT IN (SELECT user_id FROM salary_adjustments_2025)
    ON CONFLICT (user_id) DO NOTHING  -- Idempotent: ignore duplicate attempts
`, minID, maxID)

// Then apply the changes based on the tracking table:
_, err = tx.Exec(`
    UPDATE users u
    SET salary = sa.new_salary
    FROM salary_adjustments_2025 sa
    WHERE u.id = sa.user_id
      AND u.id >= $1 AND u.id <= $2
      AND u.salary != sa.new_salary  -- Only apply if not yet applied
`, minID, maxID)
```

## Solution Two — Pre-Validate Before Touching Data

One of the lessons from the WAL disk filling up is that the failure happened at row 99 million — after 99% of the work was already done. A better practice is to validate all preconditions **before** the migration begins modifying any data. This catches problems like insufficient disk space before you are committed to a rollback:

```go
// Pre-flight validation before starting a large migration:
func PreflightChecks(db *sql.DB) error {
    // Check 1: How many rows will this migration process?
    var rowCount int64
    db.QueryRow(`
        SELECT COUNT(*) FROM users WHERE normalized_email IS NULL
    `).Scan(&rowCount)
    log.Printf("Migration will process %d rows", rowCount)

    // Estimate WAL generation: approximately (avg_row_size * 3) per row
    var avgRowSize float64
    db.QueryRow(`
        SELECT AVG(pg_column_size(users.*)) FROM users LIMIT 10000
    `).Scan(&avgRowSize)
    estimatedWALGB := float64(rowCount) * avgRowSize * 3.0 / 1024 / 1024 / 1024
    log.Printf("Estimated WAL generation: %.1f GB", estimatedWALGB)

    // Check 2: Available disk space for WAL
    var walDirSizeGB float64
    db.QueryRow(`
        SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0') / 1024 / 1024 / 1024
    `).Scan(&walDirSizeGB)
    // Also check actual available disk space via OS if possible

    // Check 3: Replication lag — don't start a large migration if already lagging
    var maxReplicationLagSeconds float64
    db.QueryRow(`
        SELECT COALESCE(
            MAX(EXTRACT(EPOCH FROM (NOW() - pg_last_xact_replay_timestamp()))),
            0
        )
    `).Scan(&maxReplicationLagSeconds)
    if maxReplicationLagSeconds > 60 {
        return fmt.Errorf("replication lag is %.0f seconds — do not start migration", maxReplicationLagSeconds)
    }

    // Check 4: Estimate time based on a small test batch
    start := time.Now()
    db.Exec(`
        UPDATE users SET normalized_email = LOWER(TRIM(email))
        WHERE normalized_email IS NULL
        LIMIT 1000
    `)
    // ROLLBACK this test immediately
    db.Exec(`UPDATE users SET normalized_email = NULL WHERE normalized_email IS NOT NULL LIMIT 1000`)
    testDuration := time.Since(start)

    estimatedTotalHours := float64(rowCount) / 1000.0 * testDuration.Seconds() / 3600.0
    log.Printf("Estimated migration duration: %.1f hours at current DB speed", estimatedTotalHours)

    log.Println("Pre-flight checks passed. Ready to run migration.")
    return nil
}
```

## Solution Three — The `pg_cancel_backend` Emergency Escape

If a large transaction is currently running and you need to stop it before it runs to completion (to prevent WAL disk exhaustion, or because you discovered an error in the migration logic), you must understand the options and their consequences:

```sql
-- Option 1: Cancel the query (soft cancel — transaction remains open, then rollback)
-- pg_cancel_backend sends SIGINT to the backend process.
-- The running query is interrupted. The transaction then automatically rolls back.
-- This is the PREFERRED option — it is graceful.
SELECT pg_cancel_backend(pid)
FROM pg_stat_activity
WHERE query LIKE '%UPDATE users SET normalized_email%'
  AND state = 'active';

-- After cancellation, the rollback begins immediately.
-- For a large transaction, the rollback will take a long time.
-- DO NOT kill the process during rollback — this will require crash recovery.

-- Option 2: Terminate the connection (hard kill)
-- pg_terminate_backend sends SIGTERM to the backend process.
-- PostgreSQL will still roll back the transaction, but via crash recovery on restart.
-- Only use this if pg_cancel_backend does not respond.
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE pid = <problematic_pid>;

-- NEVER Option 3: kill -9 the PostgreSQL backend process directly
-- This bypasses PostgreSQL's own cleanup and can corrupt the database.
-- PostgreSQL's crash recovery will handle the rollback on restart,
-- but the restart itself may be lengthy.

-- Monitoring the rollback in progress:
-- The rollback cannot be seen as a separate query — it runs in the backend process.
-- You will see the transaction disappearing from pg_stat_activity
-- as the rollback completes and the connection is closed.
-- Monitor pg_stat_activity for the disappearance of the large transaction.

-- Check WAL disk usage during rollback (critical to monitor):
SELECT pg_size_pretty(sum(size)) AS wal_directory_size
FROM pg_ls_waldir();
-- This should be declining as rollback WAL records are written and old segments archived.
```

## Diagnosing a Large Transaction in Progress

```sql
-- Step 1: Find large in-flight transactions and their age:
SELECT
    pid,
    usename,
    application_name,
    now() - xact_start   AS transaction_age,
    now() - query_start  AS current_query_age,
    state,
    left(query, 120)     AS current_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY transaction_age DESC;
-- Any transaction older than 5 minutes during a migration is a warning sign.

-- Step 2: Estimate how much WAL the transaction has generated:
-- (WAL written since the transaction started, approximately)
SELECT
    pid,
    now() - xact_start AS transaction_age,
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            '0/0'::pg_lsn  -- Compare to start (approximate)
        )
    ) AS approximate_wal_since_transaction
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND state != 'idle'
ORDER BY transaction_age DESC;

-- Step 3: Monitor migration progress (via progress table):
SELECT
    migration_name,
    last_processed_id,
    rows_processed,
    now() - started_at AS running_for,
    last_updated_at,
    status,
    -- Estimate rows per hour based on progress so far:
    ROUND(
        rows_processed::numeric /
        EXTRACT(EPOCH FROM (now() - started_at)) * 3600
    ) AS rows_per_hour
FROM migration_progress
WHERE status = 'running';

-- Step 4: Check WAL disk pressure:
SELECT
    pg_size_pretty(sum(size))        AS total_wal_size,
    count(*)                         AS wal_segment_count,
    max(modification)                AS newest_wal_segment
FROM pg_ls_waldir()
WHERE name ~ '^[0-9A-F]{24}$';     -- Only WAL segments, not other files
-- Alert if total_wal_size > 50% of WAL partition capacity.
```

## The Complete Mental Model

```
THE TRANSACTION TOO LARGE TO ROLLBACK — COMPLETE MENTAL MODEL:
======================================================================

The Core Trap:
  Large transaction = large forward cost + EQUAL rollback cost
  If commit cost is 6 hours, rollback cost is 6-7 hours.
  You cannot "cancel" work already done — you can only UNDO it.
  And undoing 99M rows takes as long as doing them.

The Three Compounding Disasters:
  1. Forward pass: holds 99M row locks for hours (blocks application)
  2. WAL disk fills: update fails near the end (triggers rollback)
  3. Rollback: 7 more hours of I/O, database appears frozen

Why Staging Doesn't Catch It:
  50K rows -> 3 seconds. Passes test.
  100M rows -> 6 hours. WAL disk explosion.
  Staging tests CORRECTNESS. It cannot test SAFETY at scale.

The Correct Architecture:

  1. BATCHED TRANSACTIONS (primary solution):
  +--------------------------------------------+
  | Batch 1: UPDATE ids 1-5000.    COMMIT.     |  <- 5ms if fails
  | Batch 2: UPDATE ids 5001-10000. COMMIT.    |  <- 5ms if fails
  | ...                                        |
  | Batch N: UPDATE ids X-Y.       COMMIT.     |  <- 5ms if fails
  +--------------------------------------------+
  Max rollback cost: 5000 rows * per-row cost = SECONDS
  Progress tracking: saved after every batch
  Resumability: restart from last committed batch
  Application impact: near zero (brief locks per batch)

  2. IDEMPOTENCY (enables safe resumption):
  WHERE normalized_email IS NULL     <- natural idempotency
  ON CONFLICT (id) DO NOTHING        <- explicit idempotency
  AND processed_flag = false         <- flag-based idempotency

  3. PROGRESS TRACKING TABLE:
  migration_progress: {last_processed_id, rows_processed, status}
  Commit progress atomically with each data batch.
  Restart = read last_processed_id, resume from there.

  4. PRE-FLIGHT VALIDATION:
  Count rows to process -> estimate WAL -> verify disk has 2x capacity
  Sample 1000 rows -> estimate total time -> alert if > maintenance window
  Check replication lag -> don't start if already lagging

The WAL Disk Rule:
  Available WAL disk space must be >= 2 * (estimated WAL generation).
  Estimated WAL = row_count * avg_row_size * 3 (WAL overhead factor).
  For a batched migration, WAL pressure is steady and manageable.
  For a single large transaction: all WAL at once. Disk may fill.

The Golden Rule:
  A transaction's rollback cost equals its commit cost.
  If you cannot afford to roll back N row changes,
  do not put N row changes in one transaction.
  Batch size should be: "what can I afford to roll back in seconds?"
  At 5ms per 1000 rows: batch of 1000 = 5ms rollback. Acceptable.
  At 5ms per 1000 rows: batch of 100M = 500,000ms = 8 hours. Not acceptable.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

The transaction-too-large-to-rollback failure teaches a principle that fundamentally changes how you design large data operations: **a transaction is a unit of reversibility, and you must be able to afford to reverse it**. Before writing a large data migration or backfill, the first question to ask is not "how long will this take to run?" but "how long would the rollback take if it fails at the very last row?" If the answer is "hours," the transaction is too large.

The batch-with-progress-tracking architecture is the universal solution for large data operations. It requires slightly more code than a simple `UPDATE ... WHERE ...` statement, but it provides four properties that the simple approach completely lacks: bounded rollback cost (seconds per batch, not hours), resumability (restart from where you left off), application safety (brief locks per batch, not hours of locks), and operational visibility (progress table shows exactly how far along the job is).

Idempotency is not a bonus feature — it is a correctness requirement for any migration that might fail and need to be retried. A non-idempotent migration that fails halfway is a migration that cannot be safely resumed. Designing idempotency in from the start — using natural idempotency conditions, status flags, or conflict-handling SQL — is what transforms a migration from a "run once and hope it works" operation into a robust, retriable, production-grade data pipeline.

The staging environment will never reveal these problems. The only defense is understanding the principles — that rollback cost equals commit cost, that WAL generation is proportional to rows modified, that large transactions hold large amounts of locks — and designing around them before you write the first line of migration code.
