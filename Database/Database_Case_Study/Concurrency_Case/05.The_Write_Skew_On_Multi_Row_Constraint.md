# Case Study 05 — The Write Skew on a Multi-Row Constraint

---

## The Setup — Two Responsible Doctors, Zero On-Call Coverage

A hospital's scheduling application enforces one critical business rule: there must always be at least one doctor on call at any given time. This is not a nice-to-have — it is a patient safety requirement. The system has two doctors scheduled for tonight: Dr. Ana and Dr. Ben. Both are on call. Both receive personal emergencies and simultaneously open the application to mark themselves as off call.

Before going off call, the application performs what seems like a thorough safety check: it queries the database and asks, "Is there at least one other doctor still on call?" Dr. Ana's request runs the check. It sees Dr. Ben is on call. The check passes — Ana can safely go off call. Simultaneously, Dr. Ben's request runs the same check. It sees Dr. Ana is on call. The check passes — Ben can safely go off call. Both mark themselves as off call. Both transactions commit successfully.

The database is now in a state that the application explicitly designed to prevent: zero doctors on call. The safety rule was checked by both transactions. The rule appeared to be satisfied by both transactions. And yet the rule is now violated. Nobody made a mistake they could have detected. The database integrity constraint that was supposed to prevent this does not exist at the database level — it only exists as application logic. And application logic, under concurrent execution, is not enough.

This is **write skew on a multi-row constraint** — the most subtle and the most intellectually difficult concurrency anomaly to reason about. It is the anomaly that even experienced engineers, who know about lost updates and phantom reads, often fail to anticipate. It is the anomaly that Serializable isolation was specifically designed to catch.

---

## The Formal Definition — What Write Skew Actually Is

Write skew is a concurrency anomaly that occurs when two transactions both read an overlapping set of data, make individual decisions that appear locally valid, and then each writes to a different part of the shared data set — with the net effect that the combined result violates a constraint that neither transaction individually violated.

The key characteristic that distinguishes write skew from the other anomalies we have studied is this: **each transaction writes to a different row**. In the lost update (Case Study 03), both transactions write to the same row and one overwrites the other. In the phantom read (Case Study 04), both transactions write new rows and both writes succeed when only one should. In write skew, Transaction A writes to row X and Transaction B writes to row Y — and nobody overwrites anything. The violation emerges not from any single write but from the combination of A's write and B's write taken together, evaluated against a constraint that spans both rows.

This is what makes write skew invisible to most concurrency control mechanisms. Row-level locking prevents conflicts on individual rows — but write skew involves no row-level conflict. The two writes are on different rows. There is nothing for the lock manager to detect. The constraint that is violated exists at a level of abstraction above individual rows, and most isolation levels — including Snapshot Isolation (Repeatable Read in PostgreSQL) — do not track these cross-transaction dependencies.

```
Write Skew — The Formal Structure:
======================================================================

  The Invariant (the rule that must always hold):
    COUNT(*) FROM doctors WHERE on_call = true >= 1

  Transaction A reads: {Dr. Ana: on_call=true, Dr. Ben: on_call=true}
    -> COUNT of on_call doctors = 2. Rule holds. Ana can go off call.
  Transaction A writes: {Dr. Ana: on_call = false}

  Transaction B reads: {Dr. Ana: on_call=true, Dr. Ben: on_call=true}
    -> COUNT of on_call doctors = 2. Rule holds. Ben can go off call.
  Transaction B writes: {Dr. Ben: on_call = false}

  Final state: {Dr. Ana: on_call=false, Dr. Ben: on_call=false}
    -> COUNT of on_call doctors = 0. RULE VIOLATED.

  The crucial observation:
  - Txn A wrote ONLY to Dr. Ana's row. It never touched Dr. Ben's row.
  - Txn B wrote ONLY to Dr. Ben's row. It never touched Dr. Ana's row.
  - There is NO row-level conflict between A and B.
  - Neither transaction modified data that the other transaction also modified.
  - The violation exists ONLY in the combination of both writes.
  - Row-level locking detects NOTHING because there is no shared row.

  This is the essence of write skew:
  A reads R1 and R2. Writes W1.
  B reads R1 and R2. Writes W2.
  W1 and W2 are on different rows. No conflict.
  But W1 + W2 together violate the invariant that A and B both read.
======================================================================
```

## The Snapshot Isolation Failure — Why Even Repeatable Read Is Insufficient

Many engineers, upon learning about write skew, immediately think: "Surely Repeatable Read would prevent this — it gives each transaction a consistent snapshot of the database." This is a reasonable intuition, and it is wrong. Understanding precisely why Repeatable Read fails here is essential to understanding why Serializable isolation is needed.

Under **Repeatable Read** (also called Snapshot Isolation), each transaction works from a consistent snapshot of the database taken at the moment the transaction begins. Transaction A sees the database as it was at t=0 — Dr. Ana on call, Dr. Ben on call. Transaction B also sees the database as it was at t=0 — Dr. Ana on call, Dr. Ben on call. This snapshot is consistent and does not change during the transaction. So far, so good.

But here is the critical behavior: under Snapshot Isolation, a transaction's reads are protected (it always sees its own consistent snapshot), but **its writes are still allowed to proceed** even if another concurrent transaction has also written to related data. Snapshot Isolation prevents a transaction from seeing another transaction's uncommitted writes (dirty reads) and prevents a transaction from seeing its snapshot change during the transaction (non-repeatable reads). What it does not prevent is two transactions from each reading a consistent snapshot and then writing in a way that, in combination, violates a cross-row invariant.

```
Why Snapshot Isolation Fails to Prevent Write Skew:
======================================================================

  Database at t=0:
  +----------+---------+
  | doctor   | on_call |
  +----------+---------+
  | Dr. Ana  |  true   |
  | Dr. Ben  |  true   |
  +----------+---------+

  Txn A (Snapshot at t=0):          Txn B (Snapshot at t=0):
  Sees: Ana=true, Ben=true           Sees: Ana=true, Ben=true
  [Reads are CORRECT for the snapshot - Repeatable Read works fine here]

  Txn A writes: Ana = false          Txn B writes: Ben = false
  [Writes are to DIFFERENT rows - no conflict detected by lock manager]

  Txn A: COMMIT. Success.            Txn B: COMMIT. Success.
  [Snapshot Isolation sees no violation - each txn's writes are independent]

  Final state:
  +----------+---------+
  | doctor   | on_call |
  +----------+---------+
  | Dr. Ana  |  false  |
  | Dr. Ben  |  false  |  <- INVARIANT VIOLATED: 0 doctors on call
  +----------+---------+

  Snapshot Isolation's blind spot:
  It tracks per-row write conflicts (if A and B both write to the SAME row,
  one will fail). But A writes to Ana's row and B writes to Ben's row.
  These are different rows. No conflict is detected. Both commits succeed.

  The invariant (at least 1 on_call) is a CROSS-ROW constraint.
  Snapshot Isolation has no mechanism to detect cross-row constraint violations
  caused by concurrent writes to different rows.

  Only SERIALIZABLE isolation (SSI) can detect this pattern.
======================================================================
```

This is why the lesson says "snapshot isolation does NOT prevent write skew." It is not that snapshot isolation is weak — it is quite strong and prevents many anomalies. But write skew is specifically the class of anomaly that falls through the gap between snapshot isolation's read protection and its lack of cross-transaction write coordination.

## Real-World Patterns — Where Write Skew Hides in Production

The on-call doctor scenario is the canonical example, but write skew appears under a wide variety of business rules that span multiple rows. Learning to recognize the structural pattern — "at least N," "no more than N," "sum must remain positive" — is what allows you to identify and prevent write skew before it causes harm.

**At-Least-N Constraints.** The on-call doctor rule is "at least 1." This pattern appears everywhere: at least one administrator per organization, at least one active payment method per account, at least one admin-level user per team, at least one open shift per day. Any time your application enforces a lower bound on a count across a set of rows, write skew can reduce that count below the lower bound under concurrency.

**No-More-Than-N Constraints.** An organization allows at most 5 concurrent active sessions per user. Two login requests arrive simultaneously, both check "does this user have fewer than 5 active sessions?", both see 4, both create a new session, and the user now has 6. The rule was checked by both — the rule appears satisfied by both — the rule is violated by both together.

**Sum-Must-Remain-Positive Constraints.** A shared bank account with two users. The rule is the combined balance must stay above $0. User A checks: "is our balance above the amount I want to withdraw?" Yes ($500). User B checks simultaneously: "is our balance above the amount I want to withdraw?" Yes ($500). Both withdraw $400. Combined balance is now -$300. The constraint that the sum of all accounts for this household must remain non-negative is violated, even though each individual check appeared to pass.

**Uniqueness Across a Computed Dimension.** A meeting scheduling system where only one meeting can occupy a conference room for any given time slot. Two meetings are being created simultaneously for the same room and overlapping time. Each transaction checks: "is there any existing meeting in this room during this time?" Both see no conflict. Both insert. The room is now double-booked. (This is also a phantom read, but the constraint is a temporal uniqueness constraint rather than a simple equality uniqueness.)

```
Write Skew Pattern Recognition:
======================================================================

  ANY rule of the form:
    COUNT(rows WHERE condition) >= N          <- at-least-N
    COUNT(rows WHERE condition) <= N          <- at-most-N
    SUM(column WHERE condition) >= threshold  <- aggregate lower bound
    NOT EXISTS (rows WHERE complex_condition) <- absence constraint
    MAX/MIN(column WHERE condition) IN range  <- range constraint

  ...that is enforced ONLY by application code (not DB constraints) is
  vulnerable to write skew when multiple transactions can concurrently
  modify rows that participate in that aggregation.

  The structural fingerprint:
    Txn A: READ many rows -> CHECK aggregate condition -> WRITE one row
    Txn B: READ same rows -> CHECK same condition -> WRITE different row
    Concurrent: Both reads see condition as satisfied.
    Combined writes: condition is no longer satisfied.

  Real examples:
  - "At least 1 admin per organization"          -> Write skew risk
  - "At most 5 concurrent logins per user"       -> Write skew risk
  - "Account balance never goes below $0"        -> Write skew risk
  - "Conference room not double-booked"          -> Write skew risk
  - "Only 1 process runs a batch job at a time" -> Write skew risk
======================================================================
```

## Solution One — Serializable Isolation: The Complete Answer

The cleanest and most theoretically correct solution to write skew is **Serializable isolation**, specifically PostgreSQL's implementation of **Serializable Snapshot Isolation (SSI)**. SSI extends Snapshot Isolation with additional tracking of read-write dependencies between transactions. When SSI detects that the concurrent execution of two transactions produces a result that could not have been produced by any sequential execution of those same transactions, it aborts one of them with `SQLSTATE 40001` (serialization failure).

What SSI does under the hood is track "anti-dependency" edges in the transaction dependency graph. When Transaction A reads rows that Transaction B later writes, SSI records this dependency. When Transaction B reads rows that Transaction A later writes, SSI records the reverse dependency. When these dependencies form a cycle — A reads data that B changed, and B reads data that A changed — SSI concludes that the execution is not serializable and aborts one transaction.

For the on-call doctor scenario, SSI observes that both A and B read the `doctors` table rows (creating read dependencies) and that A writes to Dr. Ana's row (which B also read) and B writes to Dr. Ben's row (which A also read). The cycle: A reads B's row, B reads A's row, A writes A's row, B writes B's row. This is a dangerous cycle. SSI aborts one transaction.

```go
// Serializable isolation prevents write skew automatically:
func GoOffCall(db *sql.DB, doctorID int64) error {
    maxRetries := 3

    for attempt := 0; attempt < maxRetries; attempt++ {
        tx, err := db.BeginTx(context.Background(), &sql.TxOptions{
            Isolation: sql.LevelSerializable,  // SSI active
        })
        if err != nil { return err }

        // Check the invariant: at least 1 other doctor must be on call.
        // Under SERIALIZABLE, SSI tracks this read as a dependency.
        // If another transaction concurrently writes to rows in this result set,
        // SSI will detect the conflict and abort one of the transactions.
        var otherOnCallCount int
        err = tx.QueryRow(`
            SELECT COUNT(*)
            FROM doctors
            WHERE on_call = true
              AND doctor_id != $1         -- Count OTHER doctors on call, not self
        `, doctorID).Scan(&otherOnCallCount)
        if err != nil {
            tx.Rollback()
            return fmt.Errorf("checking on-call coverage: %w", err)
        }

        if otherOnCallCount < 1 {
            tx.Rollback()
            return ErrLastDoctorOnCall  // Can't go off call: you're the only one
        }

        // Go off call. Under SSI, this write creates an anti-dependency
        // that SSI tracks against the reads above.
        _, err = tx.Exec(`
            UPDATE doctors SET on_call = false WHERE doctor_id = $1
        `, doctorID)
        if err != nil {
            tx.Rollback()
            return fmt.Errorf("updating on-call status: %w", err)
        }

        err = tx.Commit()
        if err != nil {
            tx.Rollback()
            if isSerializationFailure(err) {
                // SSI detected the write skew. One of the two concurrent
                // "go off call" transactions is aborted here.
                // The other one succeeds. This is exactly correct behavior:
                // one doctor successfully goes off call, one is told to try again
                // (and on retry, will find otherOnCallCount < 1 and be refused).
                if attempt < maxRetries-1 {
                    time.Sleep(time.Duration(attempt+1) * 15 * time.Millisecond)
                    continue
                }
                return ErrLastDoctorOnCall
            }
            return fmt.Errorf("committing: %w", err)
        }
        return nil  // Successfully went off call
    }
    return ErrMaxRetriesExceeded
}

func isSerializationFailure(err error) bool {
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) {
        return pgErr.Code == "40001"
    }
    return strings.Contains(err.Error(), "could not serialize")
}
```

The elegance of SSI is that you do not need to change the structure of your query or add explicit locks. You write the code as it logically should be, and SSI handles the concurrency detection. One transaction succeeds, the other is aborted and retried — and on retry, it correctly finds only one on-call doctor and refuses to allow the second off-call.

## Solution Two — Explicit `SELECT FOR UPDATE`: Materializing the Check as a Lock

When Serializable isolation's performance overhead is unacceptable for high-throughput workloads, or when you want deterministic behavior without relying on SSI's probabilistic detection, you can prevent write skew by explicitly locking all the rows that participate in the invariant check. This forces the two concurrent transactions to serialize through the lock acquisition, ensuring that the second transaction sees the world after the first has written.

The technique is called **materializing the constraint** into a set of lockable rows. Instead of reading rows and checking an aggregate, you lock all the relevant rows before reading them, ensuring your check is performed with exclusive access to all participants in the invariant:

```go
// Explicit SELECT FOR UPDATE on ALL rows participating in the invariant:
func GoOffCallWithLocking(db *sql.DB, doctorID int64, shiftID int64) error {
    tx, err := db.Begin()
    if err != nil { return err }
    defer tx.Rollback()

    // Lock ALL doctors in this shift with FOR UPDATE.
    // This ensures that both transactions cannot simultaneously be in
    // the "check if others are on call" phase — one must wait for the other.
    // When the waiting transaction reads, it sees the updated state.
    rows, err := tx.Query(`
        SELECT doctor_id, on_call
        FROM doctors
        WHERE shift_id = $1
        ORDER BY doctor_id ASC          -- Consistent order prevents deadlocks
        FOR UPDATE                      -- Lock ALL rows in this shift
    `, shiftID)
    if err != nil {
        return fmt.Errorf("locking shift doctors: %w", err)
    }
    defer rows.Close()

    var onCallCount int
    var selfCurrentlyOnCall bool
    for rows.Next() {
        var id int64
        var onCall bool
        if err := rows.Scan(&id, &onCall); err != nil { return err }
        if onCall { onCallCount++ }
        if id == doctorID { selfCurrentlyOnCall = onCall }
    }
    if err := rows.Err(); err != nil { return err }

    // If we ourselves are not on call, nothing to do
    if !selfCurrentlyOnCall {
        return nil
    }

    // Check the invariant: if we go off call, will at least 1 remain?
    // onCallCount includes ourselves. After going off call: onCallCount - 1.
    if onCallCount-1 < 1 {
        return ErrLastDoctorOnCall
    }

    // Safe to go off call. All other rows are locked — no concurrent
    // transaction can pass the FOR UPDATE above until we commit.
    _, err = tx.Exec(`
        UPDATE doctors SET on_call = false WHERE doctor_id = $1
    `, doctorID)
    if err != nil { return fmt.Errorf("updating on-call: %w", err) }

    return tx.Commit()
    // Commit releases ALL the FOR UPDATE locks.
    // Concurrent transaction now proceeds, re-reads with updated data,
    // correctly sees onCallCount-1 = 0, and refuses.
}
```

```
The Flow WITH SELECT FOR UPDATE on ALL Relevant Rows:
======================================================================

  Time  Txn A (Dr. Ana going off call)      Txn B (Dr. Ben going off call)
  ----  --------------------------------     --------------------------------
  t=0   A: BEGIN
  t=1   A: SELECT ... FROM doctors
             WHERE shift_id = $1
             FOR UPDATE
          -> Locks BOTH Ana's row AND Ben's row.
          -> Reads: Ana=true, Ben=true. onCallCount=2.
          -> 2-1=1 >= 1. Safe to go off call.

  t=2                                         B: BEGIN
  t=3                                         B: SELECT ... FROM doctors
                                                   WHERE shift_id = $1
                                                   FOR UPDATE
                                              -> BOTH rows locked by A. B WAITS.

  t=4   A: UPDATE Ana.on_call = false.
  t=5   A: COMMIT. Locks released. Ana now off call.

  t=6                                         B: UNBLOCKED. Reads fresh data:
                                              Ana=false, Ben=true. onCallCount=1.
                                              -> 1-1=0 < 1. REFUSED.
                                              -> B: ROLLBACK.
                                              -> Ben stays on call. CORRECT.

  Result: Ana goes off call. Ben cannot. Hospital has 1 doctor on call.
  Invariant preserved. No write skew. Correct behavior.
======================================================================
```

The critical design decision in this solution is that you must lock **all** rows that participate in the invariant check — not just the row you are about to write. If you only lock the row you are writing (Ana's row), then both Ana and Ben can simultaneously lock their own rows, both check the full count (seeing the other still on call), both pass the check, and both go off call — write skew still occurs. Locking all rows in the relevant set is what serializes the check-and-act operation.

## Solution Three — Materialize the Constraint into a Single Lockable Row

The most architecturally elegant solution is to reshape the data model so that the constraint is represented by a **single row** rather than an aggregate across multiple rows. When the constraint lives in a single row, any transaction that needs to check or update the constraint can lock that single row with `SELECT FOR UPDATE`, and the problem reduces to a standard hot-row locking scenario — which we already know how to handle.

For the on-call doctor scenario, you would create a dedicated row representing the shift's current on-call count:

```sql
-- Introduce a materialized constraint row:
CREATE TABLE shift_oncall_state (
    shift_id       BIGINT PRIMARY KEY,
    oncall_count   INT    NOT NULL DEFAULT 0,
    minimum_required INT NOT NULL DEFAULT 1,
    CHECK (oncall_count >= minimum_required)  -- DB-enforced lower bound!
);

-- Initialize each shift:
INSERT INTO shift_oncall_state (shift_id, oncall_count, minimum_required)
VALUES (1, 2, 1);  -- Shift 1 starts with 2 on-call doctors, minimum 1

-- Going off call: update the counter row atomically
-- The CHECK constraint enforces oncall_count >= 1 at the DB level
UPDATE shift_oncall_state
SET oncall_count = oncall_count - 1
WHERE shift_id = $1
  AND oncall_count > minimum_required;  -- Guard: only decrement if still safe

-- Also update the doctor's own row:
UPDATE doctors SET on_call = false WHERE doctor_id = $2;
```

```go
// Using the materialized constraint row for write-skew-safe off-call logic:
func GoOffCallMaterialized(db *sql.DB, doctorID int64, shiftID int64) error {
    tx, err := db.Begin()
    if err != nil { return err }
    defer tx.Rollback()

    // Step 1: Atomically decrement the shift counter, but ONLY if the
    // result will remain >= minimum_required.
    // This is a single-row atomic operation — no write skew possible.
    result, err := tx.Exec(`
        UPDATE shift_oncall_state
        SET oncall_count = oncall_count - 1
        WHERE shift_id = $1
          AND oncall_count > minimum_required   -- Ensures count stays above minimum
    `, shiftID)
    if err != nil { return fmt.Errorf("decrementing shift counter: %w", err) }

    rowsAffected, _ := result.RowsAffected()
    if rowsAffected == 0 {
        // The update matched 0 rows: oncall_count was already at minimum.
        // Going off call would violate the constraint. Refuse.
        return ErrLastDoctorOnCall
    }

    // Step 2: Update the doctor's own on_call flag.
    // The counter decrement above serializes all concurrent off-call requests
    // through the single-row atomic update — exactly like the inventory
    // decrement pattern from Case Study 01 (Hot Row Bottleneck).
    _, err = tx.Exec(`
        UPDATE doctors SET on_call = false WHERE doctor_id = $1
    `, doctorID)
    if err != nil { return fmt.Errorf("updating doctor status: %w", err) }

    return tx.Commit()
}
```

This solution is architecturally powerful because it converts a multi-row constraint into a single-row constraint, and single-row constraints are something the database can enforce natively with `CHECK` constraints and atomic updates. The `CHECK (oncall_count >= minimum_required)` on the `shift_oncall_state` table is a true database-level constraint — not application code — and it will never be violated regardless of concurrency, isolation level, or application bugs.

The trade-off is the need to keep the `oncall_count` row in sync with the actual state of the `doctors` rows. If a doctor's `on_call` status is ever changed without updating the counter, the counter becomes stale. This can be mitigated with a database trigger that automatically updates the counter whenever `doctors.on_call` changes.

## Solution Four — Advisory Locks with a Logical Mutex

For cases where neither Serializable isolation nor data model redesign is practical in the short term, **advisory locks** can be used to implement a logical mutex around the entire check-and-act operation. By acquiring an advisory lock keyed to the shift (or whatever scope defines the invariant), you ensure that all operations affecting that shift's on-call count are serialized:

```go
// Advisory lock creates a logical mutex for the entire shift's oncall operations:
func GoOffCallWithAdvisoryLock(db *sql.DB, doctorID int64, shiftID int64) error {
    // Acquire an advisory lock for this shift.
    // All concurrent off-call requests for the same shift will serialize here.
    var acquired bool
    err := db.QueryRow("SELECT pg_try_advisory_lock($1)", shiftID).Scan(&acquired)
    if err != nil { return err }

    if !acquired {
        // Another operation is modifying this shift's on-call state.
        // Could wait (pg_advisory_lock, blocking) or return immediately.
        return ErrShiftLocked  // Let the caller retry
    }
    defer db.Exec("SELECT pg_advisory_unlock($1)", shiftID)

    // Now we have exclusive access to this shift's oncall operations.
    // No other goroutine/process can pass the advisory_lock above for this shift
    // until we release it. The check-and-act is now serialized.

    // Check the invariant with no race condition possible:
    var otherOnCallCount int
    err = db.QueryRow(`
        SELECT COUNT(*) FROM doctors
        WHERE shift_id = $1 AND on_call = true AND doctor_id != $2
    `, shiftID, doctorID).Scan(&otherOnCallCount)
    if err != nil { return err }

    if otherOnCallCount < 1 {
        return ErrLastDoctorOnCall
    }

    // Safe to go off call:
    _, err = db.Exec(`
        UPDATE doctors SET on_call = false WHERE doctor_id = $1
    `, doctorID)
    return err
    // defer releases advisory lock when function returns
}
```

## Choosing the Right Solution — The Decision Matrix

Each solution has a different cost-benefit profile. Choosing correctly depends on how frequently the invariant is checked and modified, how much concurrency hits the same invariant, and how much architectural change is acceptable:

```
Solution Decision Matrix:
======================================================================

                    | Serializable  | FOR UPDATE   | Materialize  | Advisory
                    | Isolation     | All Rows     | Constraint   | Lock
--------------------|---------------|--------------|--------------|----------
Prevents write skew | YES (auto)    | YES          | YES          | YES
Requires code change| Minimal       | Moderate     | Significant  | Moderate
Requires schema chg | NO            | NO           | YES          | NO
Performance overhead| Moderate      | High (locks) | Low          | Low
Works at high TPS   | Good with SSI | Moderate     | Best         | Good
Handles retries     | Must implement| Rarely needed| Rarely needed| Must implement
DB constraint support| No           | No           | YES (CHECK)  | No
Recommended for     | General use   | Low-medium   | High TPS     | Long operations
                    | when unsure   | concurrency  | or critical  | with ext calls

  Recommended Decision Tree:
  ---------------------------
  Is this a simple aggregate invariant (count, sum)?
    YES: Can you redesign with a single materialized row?
      YES: Use MATERIALIZED CONSTRAINT ROW. Strongest solution.
      NO:  Use SERIALIZABLE ISOLATION with retry.
    NO (complex temporal/conditional constraint):
      Use SELECT FOR UPDATE on all relevant rows + SERIALIZABLE as backup.

  Is the operation latency-sensitive at very high TPS?
    YES: Use MATERIALIZED CONSTRAINT ROW (single-row atomic update, fastest).
    NO:  Use SERIALIZABLE ISOLATION (simplest code).

  Does the operation include external service calls?
    YES: Use ADVISORY LOCKS (hold lock outside DB transaction).
    NO:  Use any of the above.

  Always add as a secondary defense:
    DB-level CHECK constraints wherever the schema allows it.
    Reconciliation queries that periodically verify invariants.
======================================================================
```

## Monitoring — Detecting Write Skew Violations After the Fact

Because write skew violations produce no database error (unless you have a `CHECK` constraint or Serializable isolation), the only way to detect them without these protections is through active monitoring of business invariants. Every critical multi-row constraint should have a corresponding monitoring query that runs periodically and alerts when the constraint is violated:

```sql
-- Monitor 1: Shifts with zero on-call doctors (the doctor scenario)
SELECT
    s.shift_id,
    s.shift_date,
    s.ward,
    COUNT(d.doctor_id) FILTER (WHERE d.on_call = true) AS oncall_count
FROM shifts s
LEFT JOIN doctors d ON d.shift_id = s.shift_id
WHERE s.shift_date = CURRENT_DATE
GROUP BY s.shift_id, s.shift_date, s.ward
HAVING COUNT(d.doctor_id) FILTER (WHERE d.on_call = true) < 1;
-- ALERT IMMEDIATELY if any rows returned.

-- Monitor 2: Users with more active sessions than allowed
SELECT
    user_id,
    COUNT(*) AS active_session_count
FROM user_sessions
WHERE status = 'active'
  AND expires_at > NOW()
GROUP BY user_id
HAVING COUNT(*) > 5;  -- Assuming max 5 concurrent sessions
-- ALERT if any rows returned (write skew in session creation)

-- Monitor 3: Accounts with combined balance below threshold
SELECT
    household_id,
    SUM(balance) AS total_balance
FROM accounts
GROUP BY household_id
HAVING SUM(balance) < 0;
-- ALERT if any rows returned (write skew in concurrent withdrawals)

-- Monitor 4: Conference rooms with overlapping confirmed bookings
SELECT
    room_id,
    b1.booking_id AS booking1,
    b2.booking_id AS booking2,
    b1.start_time AS conflict_start,
    b1.end_time AS conflict_end
FROM room_bookings b1
JOIN room_bookings b2
    ON b1.room_id = b2.room_id
   AND b1.booking_id < b2.booking_id       -- Avoid double-counting
   AND b1.status = 'confirmed'
   AND b2.status = 'confirmed'
   AND b1.start_time < b2.end_time         -- Overlap condition
   AND b2.start_time < b1.end_time
WHERE b1.booking_date = CURRENT_DATE;
-- ALERT if any rows returned (write skew in concurrent room booking)
```

These monitoring queries are not a substitute for preventing write skew — they are a safety net for detecting violations when prevention fails. Run them every minute during business hours via a scheduled job, and alert on-call engineers immediately when they return results.

## The Complete Mental Model

```
THE WRITE SKEW ON A MULTI-ROW CONSTRAINT — COMPLETE MENTAL MODEL:
======================================================================

The Pattern:
  Invariant: aggregate condition over a SET of rows must hold.
  Txn A: reads the set -> condition satisfied -> writes to row_X in set.
  Txn B: reads the set -> condition satisfied -> writes to row_Y in set.
  A and B write to DIFFERENT rows. No row conflict. Both commit.
  Invariant: NOW VIOLATED by the combined effect of both writes.

Why Normal Isolation Fails:
  Read Committed:    Each statement sees latest committed data.
                     Both transactions' reads are "correct" for their moment.
                     Both writes succeed. No mechanism catches the combination.

  Snapshot Isolation (Repeatable Read):
                     Each transaction sees a consistent snapshot.
                     Both see the constraint satisfied in THEIR snapshot.
                     Both write to different rows. No conflict detected.
                     Still vulnerable to write skew.

  Serializable (SSI): Tracks read-write anti-dependencies.
                     Detects: A read rows that B wrote, B read rows that A wrote.
                     Cycle detected = serialization failure on one transaction.
                     PREVENTS write skew correctly.

The Four Solutions (in recommended order of implementation):

  1. MATERIALIZE the constraint into a single row:
     shift_oncall_state.oncall_count with CHECK constraint.
     -> Converts multi-row invariant to single-row DB constraint.
     -> Strongest: DB-enforced, no application code needed.
     -> Best performance. Requires schema change.

  2. SERIALIZABLE ISOLATION (SSI):
     db.BeginTx(..., &sql.TxOptions{Isolation: sql.LevelSerializable})
     -> SSI detects anti-dependency cycles automatically.
     -> One transaction aborts with SQLSTATE 40001.
     -> Requires retry logic. Moderate overhead.

  3. SELECT FOR UPDATE on ALL rows in the invariant:
     SELECT ... FROM doctors WHERE shift_id=$1 ORDER BY id FOR UPDATE
     -> All participants locked -> check is serialized.
     -> Lock all relevant rows (not just the one you're writing).
     -> No retries needed. Higher lock contention.

  4. ADVISORY LOCK on the invariant's scope:
     pg_try_advisory_lock(shiftID)
     -> Application-level mutex for the invariant.
     -> Works outside DB transactions for long-running flows.

  Always add MONITORING as a safety net:
     Periodic reconciliation queries that verify invariants.
     Alert immediately on any violation.

The Golden Rule for Write Skew:
  Any multi-row business invariant that is enforced ONLY by application
  code (not by a DB constraint) is vulnerable to write skew under
  concurrent load. The fix is ALWAYS one of:
  (a) Move the invariant into the database as a constraint/single row.
  (b) Use Serializable isolation.
  (c) Explicitly lock all invariant participants before checking.
  Never assume that "checking before writing" is thread-safe.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

Write skew is the concurrency anomaly that humbles even experienced database engineers, because it violates an intuition that feels deeply correct: "I checked the condition before I acted — how can the condition be violated?" The answer is that the check and the act are only an atomic unit if some mechanism prevents other transactions from affecting the condition between the check and the act. Without Serializable isolation, explicit locking of all relevant rows, or a schema redesign that materializes the constraint, no amount of careful checking prevents write skew.

The deeper lesson is about the relationship between isolation levels and guarantees. Read Committed — the PostgreSQL default and the default of most databases and ORMs — guarantees almost nothing about cross-transaction consistency. It prevents dirty reads and nothing else. Snapshot Isolation (Repeatable Read in PostgreSQL) prevents dirty reads, non-repeatable reads, and phantom reads, but specifically does not prevent write skew. Only Serializable isolation prevents write skew, and it does so at a performance cost that must be consciously accepted.

The most durable solution — and the one that engineers should reach for first when the data model permits it — is to materialize the constraint into a single row with a database-level `CHECK` constraint. When a multi-row invariant becomes a single-row atomic update, the problem reduces to the hot row bottleneck (Case Study 01), which we know how to solve. The invariant becomes something the database enforces unconditionally, regardless of isolation level, regardless of application code, regardless of concurrent transactions. That unconditional enforcement is the strongest form of data integrity available to us, and it should be designed in from the start wherever possible.

Snapshot isolation does not prevent write skew. Only Serializable or explicit locking does. Every multi-row business constraint enforced only by application code is a write skew vulnerability waiting to be triggered by concurrent load.
