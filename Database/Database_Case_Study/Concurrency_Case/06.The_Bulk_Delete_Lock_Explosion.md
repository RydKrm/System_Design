# Case Study 06 — The Bulk Delete Lock Explosion

---

## The Setup — The Cleanup Job That Became a Crisis

Every production system accumulates data over time. Events are logged, audit trails are recorded, temporary records are created, soft-deleted items pile up. At some point, a decision is made to clean up the old data — to reclaim disk space, improve query performance on live data, and satisfy data retention policies. A developer is tasked with writing a cleanup job. The logic is straightforward: delete everything older than one year. The developer writes the obvious SQL:

```sql
DELETE FROM events WHERE created_at < NOW() - INTERVAL '1 year';
```

The developer tests this in a staging environment. It works. It deletes the old records cleanly. The job is scheduled to run every night at 2:00 AM, which seems like a quiet time. Everything looks correct.

On the first night the job runs against the production database, which has been accumulating records for three years, the query begins executing at 2:00 AM. It acquires exclusive row locks on every single row it is about to delete — all 500 million of them. The query runs. And runs. And runs. It runs for four hours. During those four hours, every other query that touches the `events` table is blocked, queued, or killed by timeouts. The application's connection pool fills with waiting requests. Users who try to access any feature that queries the events table get errors. The engineering team is woken up at 4:00 AM by a cascade of alerts. By 6:00 AM, when the delete finally finishes, hundreds of thousands of users have experienced failures, and the business has suffered a self-inflicted, entirely preventable outage that lasted four hours.

The developer did not write a bug in the traditional sense. The SQL is syntactically and semantically correct. The data was deleted successfully. But the way the deletion was performed — all 500 million rows in a single transaction — is a design error that turns a routine maintenance operation into a production disaster.

---

## What a Bulk Delete Actually Does — Inside the Engine

To understand why a bulk delete is so dangerous, you must understand what PostgreSQL does when you execute a `DELETE` statement, at the level of the storage engine and the lock manager. Most engineers think of a `DELETE` as simply removing rows. The reality is significantly more complex and significantly more expensive.

When PostgreSQL executes `DELETE FROM events WHERE created_at < NOW() - INTERVAL '1 year'`, it performs the following sequence of operations for every single qualifying row:

First, it acquires an **exclusive row-level lock** on that row. This lock prevents any other transaction from reading the row with `SELECT FOR UPDATE`, updating it, or deleting it concurrently. In PostgreSQL's MVCC model, the lock is held until the transaction commits or rolls back — meaning all 500 million locks are held simultaneously throughout the entire duration of the delete operation.

Second, it marks the row as **dead** in its storage page — this is a PostgreSQL MVCC operation. The row is not immediately removed from disk. Instead, PostgreSQL sets a "deleted by transaction X" marker on the row's header. The row remains physically present in the table's data pages. The space is only actually reclaimed later when VACUUM runs and cleans up dead tuples.

Third, it writes a **WAL (Write-Ahead Log) entry** for every single deleted row. Every modification in PostgreSQL — inserts, updates, and deletes — is first written to the WAL for crash recovery and replication. Deleting 500 million rows generates an enormous amount of WAL data, which must be written to disk and replicated to standby servers before the transaction can commit. This causes massive I/O pressure and can cause replication lag to balloon to hours.

Fourth, when the transaction finally commits, PostgreSQL releases all the locks simultaneously and flushes the transaction's WAL records. The commit itself can take minutes when the transaction spans hundreds of gigabytes of WAL data.

```
What PostgreSQL Does For Every Single Deleted Row (x500 million):
======================================================================

  Row in storage:
  +--------+-----------+-----+---------------------+--------+
  | xmin   | xmax      | ... | created_at          | data   |
  +--------+-----------+-----+---------------------+--------+
  | 10000  | [empty]   | ... | 2022-01-15 14:30:00 | ...    |  <- LIVE
  +--------+-----------+-----+---------------------+--------+

  After DELETE statement processes this row:
  +--------+-----------+-----+---------------------+--------+
  | xmin   | xmax      | ... | created_at          | data   |
  +--------+-----------+-----+---------------------+--------+
  | 10000  | 99999     | ... | 2022-01-15 14:30:00 | ...    |  <- DEAD
  +--------+-----------+-----+---------------------+--------+
  (xmax = transaction ID of the deleting transaction)
  (Row still physically on disk! Space not reclaimed until VACUUM.)

  Per-row cost:
  1. Acquire exclusive tuple lock                [lock manager]
  2. Mark row as dead (set xmax)                 [heap write]
  3. Write WAL record for the deletion           [WAL I/O]
  4. Update any indexes referencing this row     [index write x num_indexes]
  5. Hold the lock until transaction commits     [lock table memory]

  For 500 million rows:
  - 500 million lock entries in the lock table   (GBs of RAM)
  - 500 million dead tuple markers               (no space reclaimed yet)
  - Hundreds of GB of WAL data                   (I/O + replication pressure)
  - All 500 million locks held simultaneously    (blocking all other queries)
  - VACUUM cannot reclaim space until commit     (table bloat during operation)
======================================================================
```

The lock explosion is the most immediate impact. While the delete transaction is running and has not yet committed, all 500 million row locks are held in PostgreSQL's shared memory lock table. Any other transaction that tries to read these rows with `SELECT FOR UPDATE`, update them, or delete them must wait. Regular `SELECT` queries (without `FOR UPDATE`) can still read the rows under MVCC — they see the rows as they existed before the delete transaction started — but writes are completely blocked for the duration.

## The Cascade of Failures — Four Hours of Self-Inflicted Pain

The bulk delete does not cause a single, clean failure. It triggers a cascade of failures that compound over time, each making the next worse, until the system is effectively down for the duration of the delete operation.

The first cascade is the **connection pool exhaustion**. The application's backend services have queries they run against the `events` table — fetching recent events for the user feed, counting events for analytics dashboards, joining events to other tables for reporting. These queries all use `UPDATE` or `SELECT FOR UPDATE` statements in their transaction context, which are blocked by the 500 million exclusive locks. These requests pile up in the connection pool, each holding a connection slot open while waiting for the delete to finish. Within minutes, the connection pool is exhausted. New requests cannot get a connection, and the application begins returning errors across every endpoint that touches the events table.

The second cascade is **WAL pressure on replication**. The delete's WAL stream is enormous. PostgreSQL's physical streaming replication sends WAL data to standby servers, which apply it to stay in sync. Under normal conditions, replication lag is measured in milliseconds. A bulk delete generating hundreds of gigabytes of WAL can cause replication lag to grow to minutes, then hours. Read replicas that serve read traffic — user-facing queries that the application deliberately routes to replicas to reduce load on the primary — begin serving stale data that is hours behind. Eventually, if the replica falls far enough behind, the primary PostgreSQL server may stop accepting new transactions to protect replication integrity.

The third cascade is **VACUUM starvation**. PostgreSQL's AUTOVACUUM process continuously runs in the background, cleaning up dead tuples left by previous DELETE and UPDATE operations. AUTOVACUUM cannot clean a page that has any active transactions that might still reference old row versions. During the four-hour bulk delete, the enormous transaction holds a snapshot that prevents AUTOVACUUM from cleaning up dead tuples across the entire table. When the delete finally commits, AUTOVACUUM faces a backlog of hundreds of millions of dead tuples spread across thousands of pages. The subsequent VACUUM run takes hours more, during which table performance is degraded.

```
The Cascade Timeline — 4 Hours of Escalating Damage:
======================================================================

  t=00:00  Bulk delete begins.
           Events table: 500M rows all locked by the delete transaction.

  t=00:05  Connection pool begins filling.
           Application queries that write to events table: BLOCKED.
           User features begin timing out.

  t=00:15  Connection pool exhausted.
           All application endpoints touching events table: FAILING.
           Error rate: 40% and climbing.
           DB CPU: 85% (massive I/O from WAL writes for deletions)
           Replication lag: 5 minutes and growing.

  t=00:30  Alerts firing across all dashboards.
           On-call engineer woken up.
           Error rate: 65%.
           Replication lag: 25 minutes.
           AUTOVACUUM: blocked entirely by open bulk delete transaction.

  t=01:00  Error rate: 80%.
           Replication lag: 1 hour.
           Standby replicas serving data that is 1 hour stale.
           Connection pool: 100% full, all waiting.

  t=04:00  Bulk delete finally completes. COMMIT.
           All 500 million row locks released simultaneously.
           All queued transactions unblock simultaneously.
           DB CPU spikes to 100% as 1000+ waiting queries all execute.
           A second wave of failures as the sudden load spike causes
           new timeouts.

  t=04:30  AUTOVACUUM begins cleaning up 500M dead tuples.
           Table performance still degraded for hours.
           Replication lag slowly draining.

           Disk space: UNCHANGED until VACUUM finishes.
           (The delete freed no disk space yet — MVCC dead tuples remain.)
======================================================================
```

One of the cruelest aspects of this failure is the final note above: after four hours of production outage, the disk space that the bulk delete was supposed to reclaim is **not yet reclaimed**. Because of PostgreSQL's MVCC model, dead tuples remain physically on disk until VACUUM runs. The DELETE statement marks rows as dead, but only VACUUM removes them from the storage pages and makes the space available for reuse. A four-hour delete is followed by another multi-hour VACUUM run. The disk space goal of the entire operation is achieved only after many more hours of degraded performance.

## Solution One — Batch Deletes with Commits and Sleep

The correct approach to large-scale data deletion is to break the single enormous transaction into thousands of small transactions, each deleting a limited number of rows, committing immediately, sleeping briefly to give other queries a chance to run, and then repeating. This is called **batch deletion**, and it is the standard, universally-applicable solution to the bulk delete problem.

The key properties of the batch delete approach are: each batch deletes a bounded number of rows (typically 500 to 5,000), each batch commits immediately after deleting its rows (releasing all locks instantly), and there is a sleep interval between batches (giving AUTOVACUUM and other queries time to interleave). The total data deleted is the same. The total time taken is roughly the same or slightly longer. But the impact on the application is reduced from a four-hour outage to near-zero impact — other queries run freely between batches, connection pools never exhaust, WAL pressure is steady and manageable, and AUTOVACUUM keeps up with the deletion in real time.

```go
// Batch delete implementation in Go — the correct way to delete large datasets:
func BatchDeleteOldEvents(db *sql.DB, olderThan time.Time) error {
    const batchSize = 1000         // Delete 1000 rows per batch
    const sleepBetweenBatches = 50 * time.Millisecond  // 50ms rest between batches

    totalDeleted := 0
    batchNumber := 0

    for {
        batchNumber++

        // Delete a small, bounded batch. This transaction takes milliseconds,
        // holds locks for milliseconds, and releases them immediately on commit.
        // Other queries can run freely during the sleep between batches.
        result, err := db.Exec(`
            DELETE FROM events
            WHERE id IN (
                SELECT id
                FROM events
                WHERE created_at < $1
                ORDER BY id ASC     -- Consistent ordering prevents table fragmentation
                LIMIT $2            -- Strictly bounded batch size
            )
        `, olderThan, batchSize)
        if err != nil {
            return fmt.Errorf("batch %d delete failed: %w", batchNumber, err)
        }

        rowsDeleted, err := result.RowsAffected()
        if err != nil { return err }

        totalDeleted += int(rowsDeleted)

        // Log progress for observability — crucial for long-running operations
        log.Printf("Batch %d: deleted %d rows (total: %d)",
            batchNumber, rowsDeleted, totalDeleted)

        // No more rows to delete — we're done
        if rowsDeleted == 0 {
            log.Printf("Batch deletion complete. Total rows deleted: %d", totalDeleted)
            return nil
        }

        // Sleep between batches: lets AUTOVACUUM run, lets application queries
        // execute without competition, prevents the cleanup job from consuming
        // all database I/O capacity.
        time.Sleep(sleepBetweenBatches)
    }
}

// Usage — schedule this to run as a background goroutine:
func RunDailyCleanup(db *sql.DB) {
    cutoff := time.Now().AddDate(-1, 0, 0)  // 1 year ago
    if err := BatchDeleteOldEvents(db, cutoff); err != nil {
        log.Printf("ERROR: Daily cleanup failed: %v", err)
        // Alert on-call engineer
    }
}
```

```
Batch Delete vs. Bulk Delete — Impact Comparison:
======================================================================

BULK DELETE (500 million rows, single transaction):
  Duration: 4 hours
  Locks held: 500M rows locked for 4 hours simultaneously
  WAL generated: ~500 GB (all at once, huge I/O spike)
  Application impact: COMPLETE OUTAGE for 4 hours
  Replication lag: Hours of lag, replicas serving stale data
  AUTOVACUUM: Blocked for 4 hours, huge backlog after
  Disk space freed: ZERO (until VACUUM runs, hours later)

BATCH DELETE (1000 rows per batch, 500,000 batches):
  Duration: ~7 hours (1000 rows x 500,000 batches + sleep)
  Locks held: 1000 rows locked for ~5ms at a time, then released
  WAL generated: ~500 GB total, spread over 7 hours (steady, manageable)
  Application impact: NEAR ZERO (queries run between batches)
  Replication lag: <100ms (steady WAL stream, replicas keep up)
  AUTOVACUUM: Runs between batches, keeps pace with deletion
  Disk space freed: Incrementally, throughout the 7 hours

  The batch approach takes slightly longer in total wall-clock time,
  but the APPLICATION EXPERIENCES NO DOWNTIME.
  This is the correct trade-off.
======================================================================
```

The `ORDER BY id ASC` in the inner `SELECT` is important and worth explaining. Deleting rows in primary key order ensures that batches process the table's pages in a predictable sequence, which is better for AUTOVACUUM (which can then clean up pages from the beginning of the table progressively) and avoids fragmenting the deletion across random page locations. It also makes the batches deterministic and reproducible, which simplifies debugging and monitoring.

## Tuning the Batch Size and Sleep — Finding the Right Balance

The two key parameters of the batch delete — `batchSize` and `sleepBetweenBatches` — need to be tuned based on your specific workload and performance requirements. There is no universal correct value, but there are principled ways to reason about them.

The batch size controls how many rows are deleted in each transaction. Smaller batches mean shorter lock-holding windows (better for application availability) but more overhead per row (more commit overhead, more AUTOVACUUM check-ins). Larger batches are more efficient per-row but hold locks longer and generate larger WAL records per transaction. For most production systems, a batch size between 500 and 5,000 rows is appropriate. Start at 1,000 and adjust based on observed lock wait times.

The sleep between batches is a throttle that limits how aggressively the cleanup job consumes database I/O and CPU. Without sleep, a batch delete loop will run as fast as the database allows, potentially consuming all available I/O bandwidth and starving other queries. A sleep of 50ms to 200ms between batches is usually sufficient to prevent the cleanup job from affecting application performance noticeably. For systems with very low-latency requirements or very high traffic, increase the sleep; for systems that need to delete data quickly or run during a maintenance window, decrease or eliminate the sleep.

A more sophisticated approach uses adaptive throttling — monitoring database metrics and adjusting the sleep dynamically:

```go
// Adaptive batch delete with throttling based on observed delete duration:
func AdaptiveBatchDelete(db *sql.DB, olderThan time.Time) error {
    const batchSize = 1000
    const targetBatchDuration = 50 * time.Millisecond  // Each batch should take ~50ms
    const minSleep = 10 * time.Millisecond
    const maxSleep = 500 * time.Millisecond

    sleepDuration := 100 * time.Millisecond  // Start with 100ms sleep

    for {
        start := time.Now()

        result, err := db.Exec(`
            DELETE FROM events
            WHERE id IN (
                SELECT id FROM events
                WHERE created_at < $1
                ORDER BY id ASC
                LIMIT $2
            )
        `, olderThan, batchSize)
        if err != nil { return err }

        batchDuration := time.Since(start)
        rowsDeleted, _ := result.RowsAffected()

        if rowsDeleted == 0 { return nil }  // Done

        // Adaptive throttling: if the batch took longer than the target,
        // increase sleep (DB is under stress). If it was fast, decrease sleep.
        if batchDuration > targetBatchDuration*2 {
            // DB is slow — increase sleep to reduce pressure
            sleepDuration = min(sleepDuration*2, maxSleep)
        } else if batchDuration < targetBatchDuration/2 {
            // DB is fast — can afford to decrease sleep
            sleepDuration = max(sleepDuration/2, minSleep)
        }

        log.Printf("Deleted %d rows in %v, sleeping %v",
            rowsDeleted, batchDuration, sleepDuration)

        time.Sleep(sleepDuration)
    }
}
```

## Solution Two — Table Partitioning: The Zero-Downtime Alternative

Batch deletion, while far better than bulk deletion, still takes time — hours for very large datasets. For systems with strict data retention requirements on very large tables, the most elegant and most powerful solution is **table partitioning with partition dropping**.

The idea is to design the table so that data is physically stored in separate partition tables, organized by time range. Instead of one massive `events` table, you have `events_2023`, `events_2024`, `events_2025`, and so on — each containing only one year's worth of data. When you need to delete an entire year's worth of old data, instead of deleting individual rows, you simply drop the partition table:

```sql
-- Create a partitioned events table:
CREATE TABLE events (
    id          BIGSERIAL,
    user_id     BIGINT,
    event_type  TEXT,
    payload     JSONB,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- Create yearly partitions:
CREATE TABLE events_2023
    PARTITION OF events
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE events_2024
    PARTITION OF events
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE events_2025
    PARTITION OF events
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- Data retention: instead of DELETE, drop the partition:
-- This operation is INSTANTANEOUS. No row-by-row deletion.
-- No locks on individual rows. Just a metadata operation.
DROP TABLE events_2023;

-- Or detach first (keeps the table structure) then drop:
ALTER TABLE events DETACH PARTITION events_2023;
-- Now events_2023 is a standalone table. Can archive to cold storage first.
DROP TABLE events_2023;  -- Instant. ~1 millisecond.
```

The difference in performance is staggering and almost magical when you first encounter it:

```
DELETE vs. DROP PARTITION — Performance Comparison:
======================================================================

  Deleting 500 million rows (one year of events):

  Method 1: DELETE statement (unbatched):
    Execution time: 4+ hours
    Locks: 500M row locks held for 4+ hours
    WAL generated: ~500 GB
    AUTOVACUUM work after: Multi-hour VACUUM run
    Disk space freed: Only after VACUUM (hours later)
    Application impact: COMPLETE OUTAGE

  Method 2: Batch DELETE (1000 rows per batch):
    Execution time: 6-8 hours
    Locks: 1000 row locks held for ~5ms at a time
    WAL generated: ~500 GB spread over 6-8 hours
    AUTOVACUUM work after: Minimal (kept up in real time)
    Disk space freed: Incrementally, in real time
    Application impact: NEAR ZERO

  Method 3: DROP TABLE events_2023 (partition drop):
    Execution time: ~1 millisecond
    Locks: Table-level lock for ~1ms
    WAL generated: A few KB (just the catalog update)
    AUTOVACUUM work after: NONE (files removed at OS level)
    Disk space freed: IMMEDIATELY, in full
    Application impact: ZERO (1ms lock on partition only)

  The partition drop is not 4 hours faster.
  It is 14,400,000× faster. And it frees disk space instantly.
======================================================================
```

The partition drop works at the speed of a file system operation because that is exactly what it is. PostgreSQL stores each partition as a separate file on disk. Dropping a partition is equivalent to deleting that file — a metadata operation that takes milliseconds regardless of how many rows the partition contains. No row-by-row locking, no WAL records for individual rows, no VACUUM needed afterward.

The trade-off is that partitioning must be designed into the schema from the beginning. You cannot retroactively partition an existing table without significant migration work. But for any table where time-based data retention is a known requirement — events, logs, metrics, audit trails — designing with partitioning from the start is almost always the right architectural choice.

## Solution Three — Archive Before Delete

For systems where the data must be retained in some form — for compliance, analytics, or auditing — but should be removed from the hot primary database, the **archive-then-delete** pattern is appropriate. Data is first exported to cold storage (an object storage bucket like S3, a data warehouse, or a cold PostgreSQL tablespace), and only after successful archiving is it deleted from the primary database. The deletion itself uses batch deletes or partition drops as described above.

```go
// Archive-then-delete workflow:
func ArchiveAndDeleteOldEvents(db *sql.DB, s3Client *s3.Client, olderThan time.Time) error {
    // Phase 1: Export old data to S3 in chunks (non-blocking, reads only)
    // This phase uses simple SELECTs — no locks on live data, no impact on writes.
    if err := exportToS3InBatches(db, s3Client, olderThan); err != nil {
        return fmt.Errorf("archive phase failed: %w", err)
    }

    // Phase 2: Verify archive integrity before deleting
    if err := verifyArchiveCompleteness(db, s3Client, olderThan); err != nil {
        return fmt.Errorf("archive verification failed, NOT deleting: %w", err)
    }

    // Phase 3: Batch delete from primary DB (now that archive is confirmed safe)
    if err := BatchDeleteOldEvents(db, olderThan); err != nil {
        return fmt.Errorf("deletion phase failed: %w", err)
    }

    log.Printf("Successfully archived and deleted events older than %v", olderThan)
    return nil
}

func exportToS3InBatches(db *sql.DB, s3Client *s3.Client, olderThan time.Time) error {
    const batchSize = 10000
    var lastID int64 = 0

    for {
        rows, err := db.Query(`
            SELECT id, user_id, event_type, payload, created_at
            FROM events
            WHERE created_at < $1
              AND id > $2             -- Cursor-based pagination, no OFFSET
            ORDER BY id ASC
            LIMIT $3
        `, olderThan, lastID, batchSize)
        if err != nil { return err }

        var batch []Event
        for rows.Next() {
            var e Event
            rows.Scan(&e.ID, &e.UserID, &e.EventType, &e.Payload, &e.CreatedAt)
            batch = append(batch, e)
            lastID = e.ID
        }
        rows.Close()

        if len(batch) == 0 { break }  // All data exported

        // Write batch to S3 as Parquet or JSON Lines
        if err := writeBatchToS3(s3Client, batch); err != nil { return err }

        log.Printf("Exported %d events to S3 (last ID: %d)", len(batch), lastID)
        time.Sleep(10 * time.Millisecond)  // Gentle throttle
    }
    return nil
}
```

## Solution Four — Partitioning for an Existing Table (Migration Strategy)

If you have an existing large unpartitioned table that needs to become partitioned, here is the migration approach that avoids downtime:

```sql
-- Step 1: Create the new partitioned table structure
CREATE TABLE events_partitioned (
    id          BIGSERIAL,
    user_id     BIGINT,
    event_type  TEXT,
    payload     JSONB,
    created_at  TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

-- Step 2: Create all necessary partition tables
CREATE TABLE events_2023 PARTITION OF events_partitioned
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
CREATE TABLE events_2024 PARTITION OF events_partitioned
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE events_2025 PARTITION OF events_partitioned
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- Step 3: Copy data in batches (non-blocking, can take as long as needed)
-- Run this in a loop with batches to avoid locking:
INSERT INTO events_partitioned
SELECT * FROM events
WHERE created_at >= '2023-01-01' AND id <= 1000000;
-- Continue for all ID ranges...

-- Step 4: Once data is copied, switch the application over:
-- (Requires a brief maintenance window for the rename + index recreation)
ALTER TABLE events RENAME TO events_old;
ALTER TABLE events_partitioned RENAME TO events;

-- Step 5: Drop the old table (can be done with batch deletes if needed)
-- Since it is now renamed, the live system is unaffected.
DROP TABLE events_old CASCADE;  -- Or batch delete if disk space is critical

-- Going forward: automatic partition management
-- Create a cron job that creates next month's/year's partition in advance
-- and drops partitions older than the retention period.
```

## The Production Runbook — What to Do During an Active Bulk Delete Disaster

If a bulk delete is currently running and causing an outage, here is the emergency response:

```sql
-- Step 1: Find the bulk delete transaction (the root cause)
SELECT
    pid,
    now() - xact_start AS transaction_age,
    now() - query_start AS query_age,
    state,
    left(query, 100) AS query_text
FROM pg_stat_activity
WHERE query ILIKE '%DELETE%'
ORDER BY transaction_age DESC;

-- Step 2: Check how many rows have been deleted so far (progress check)
SELECT
    n_dead_tup AS dead_rows_so_far,   -- Rows deleted but not yet vacuumed
    n_live_tup AS live_rows_remaining,
    now() - last_autovacuum AS since_last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'events';

-- Step 3: Cancel the bulk delete (soft cancel — preserves connection)
-- This rolls back ALL deletions done so far. Data is restored. Lock released.
SELECT pg_cancel_backend(<pid_from_step_1>);

-- If cancel doesn't work (query may be in an uninterruptible state):
SELECT pg_terminate_backend(<pid_from_step_1>);

-- Step 4: Verify recovery — confirm locks are released and app is recovering
SELECT state, count(*) FROM pg_stat_activity GROUP BY state;
-- Active connections should drop rapidly after the bulk delete is cancelled.

-- Step 5: Re-run using the batch delete approach (not the bulk delete)
-- See BatchDeleteOldEvents() Go function above.
-- Schedule it to run during off-peak hours with appropriate batch size and sleep.
```

## Diagnosing and Monitoring Bulk Delete Impact

```sql
-- Monitor WAL generation rate during a delete (high rate = high I/O pressure):
SELECT
    pg_current_wal_lsn() AS current_wal_position,
    pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0'::pg_lsn) / 1024 / 1024
        AS total_wal_mb;
-- Run this twice with a 60s interval, subtract to get MB/minute of WAL generation.
-- Normal: <100 MB/min. During bulk delete: potentially thousands of MB/min.

-- Monitor replication lag (rising lag = delete is overwhelming replication):
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    pg_wal_lsn_diff(sent_lsn, replay_lsn) / 1024 / 1024 AS lag_mb,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication;
-- ALERT if lag_mb > 100 or replay_lag > 30 seconds.

-- Monitor AUTOVACUUM status during/after delete:
SELECT
    relname         AS table_name,
    n_dead_tup      AS dead_tuples_to_clean,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
WHERE relname = 'events';
-- Large n_dead_tup after a delete = AUTOVACUUM has work to do.
-- Monitor until n_dead_tup drops to near-zero.

-- Alert query: detect large DELETE transactions in flight
SELECT count(*)
FROM pg_stat_activity
WHERE query ILIKE '%DELETE%'
  AND state = 'active'
  AND now() - query_start > interval '30 seconds';
-- ALERT if count > 0. No DELETE should run for more than 30 seconds.
```

           -> Instant. Frees disk immediately. Zero locks on rows.
           -> Requires partitioned schema design upfront.

  Good:    Batch delete with sleep
           DELETE ... LIMIT 1000 in a loop with time.Sleep(50ms)
           -> Each batch: 1000 locks held for ~5ms, then released.
           -> AUTOVACUUM keeps up. Other queries run freely.
           -> Application impact: near zero.
           -> Works with any existing schema.

  Never:   Single bulk DELETE without batching
           -> Hours of outage. Use only in maintenance windows with
              the application explicitly stopped.

Batch delete parameters:
  batchSize    = 1000   (start here, tune up to 5000 if DB handles it)
  sleepMs      = 50ms   (start here, tune based on DB I/O metrics)
  ORDER BY id  = always (prevents fragmentation, enables AUTOVACUUM progress)

The rule of thumb for production safety:
  If you cannot answer "how long will this DELETE take?" with confidence,
  add LIMIT and batch it. Always.

Monitoring a cleanup job:
  - Replication lag should stay < 1s              (ALERT if > 30s)
  - Dead tuple count should be low, AUTOVACUUM running  (ALERT if rising fast)
  - Connection pool usage should stay < 70%       (ALERT if > 90%)
  - Cleanup job itself: log rows deleted per batch for progress visibility

Schema design principle:
  Any table with time-based data retention = design as partitioned table.
  ALWAYS. From day one. Before the first row is inserted.
  Retrofitting partitioning after 500 million rows exist is painful.
  Designing it in from the start costs almost nothing extra.

## Key Takeaways — The Principles to Carry Forward

The bulk delete lock explosion teaches a lesson about the difference between correctness and safety. The single `DELETE FROM events WHERE created_at < NOW() - INTERVAL '1 year'` statement is **correct** — it will delete exactly the right rows, satisfy the data retention requirement, and commit a valid database state. But it is not **safe** for production use because of the duration and exclusivity of the locks it holds, the WAL pressure it generates, the AUTOVACUUM it blocks, and the application outage it causes.

Production systems must prioritize safety alongside correctness. A cleanup job that correctly deletes old data while causing a four-hour outage is not a successful operation — it is a failure that happened to achieve its stated goal as a side effect. The batch delete approach achieves the exact same outcome with near-zero application impact. The partition drop achieves it instantaneously. Both are safer approaches that responsible production engineering demands.

The broader principle is to treat large data operations — any operation that touches millions of rows — with the same level of care and testing as major code deployments. Large deletes, large updates, index creation, schema changes — all of these operations have the potential to cause production outages if executed naively. Staging environments with production-scale data, dry runs with `EXPLAIN ANALYZE`, explicit planning for lock management and WAL pressure, and monitoring throughout the operation are not optional steps for large data operations. They are the minimum bar for responsible production database management.

Never delete millions of rows in a single transaction. Always batch with commits and sleep. And if you are designing a new system with time-based data retention requirements, design it with table partitioning from the very first day.
