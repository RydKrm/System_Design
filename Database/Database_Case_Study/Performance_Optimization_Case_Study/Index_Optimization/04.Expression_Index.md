# The Expression Index: When Your Function Breaks Your Index

> _"An index on a column stores the raw value. If your query never looks at the raw value — only a transformed version of it — the index is invisible to the query planner. You built a door, but your query is walking through the wall."_

---

## Setting the Scene

You are working on a user authentication system. Every time a user types their email address and password into a login form, your backend fires a query to look them up. This is one of the most fundamental operations in any web application — authentication. It has to be fast, reliable, and correct.

The system was designed to be case-insensitive. Users should be able to log in as `User@Example.com`, `user@example.com`, or `USER@EXAMPLE.COM` and always reach the same account. This is a completely reasonable product decision — nobody wants to be told their login failed because they accidentally capitalized their email. Emails are, by international convention, case-insensitive in the local part (the part before the `@`).

So the developer who built the login query wrote this:

```sql
SELECT *
FROM users
WHERE LOWER(email) = LOWER('User@Example.com');
```

Logical. Correct. And catastrophically slow — **12 seconds** on a users table of any meaningful size.

There was already an index on the `email` column. That index was doing absolutely nothing to help this query. This document explains why — from first principles — and how one precisely placed index definition fixed everything.

---

## First, Understand What an Index Actually Stores

To understand why `LOWER()` breaks the index, you need a concrete mental model of what a B-Tree index physically contains.

When you run `CREATE INDEX ON users (email)`, PostgreSQL takes the value of the `email` column from every row in the table and builds a sorted B-Tree structure. Each leaf node of the B-Tree contains the raw, unmodified value from that column, paired with a physical pointer to the heap row.

```
B-TREE INDEX on (email) — What is actually stored
─────────────────────────────────────────────────────────────────────

Leaf nodes, sorted alphabetically by the raw email value:

  ┌────────────────────────────────────────────────────────────────┐
  │  'Admin@Company.com'    → ptr to heap row (block 14, slot 2)  │
  │  'alice@gmail.com'      → ptr to heap row (block 3,  slot 7)  │
  │  'Bob@outlook.com'      → ptr to heap row (block 7,  slot 1)  │
  │  'carol@yahoo.com'      → ptr to heap row (block 2,  slot 4)  │
  │  'david@hotmail.com'    → ptr to heap row (block 9,  slot 3)  │
  │  'Eve@protonmail.com'   → ptr to heap row (block 22, slot 5)  │
  │  'Frank@work.com'       → ptr to heap row (block 5,  slot 9)  │
  │  'User@Example.com'     → ptr to heap row (block 11, slot 6)  │
  │  'zara@domain.com'      → ptr to heap row (block 18, slot 2)  │
  └────────────────────────────────────────────────────────────────┘
         ↑
         These are the ORIGINAL, UNMODIFIED values exactly
         as they were stored in the email column.
         The index is a mirror of the raw data, sorted.
```

The B-Tree is sorted lexicographically based on the raw values. `'Admin@Company.com'` comes before `'alice@gmail.com'` because uppercase `A` has a lower ASCII value than lowercase `a`. `'User@Example.com'` sits at a specific position in this sorted order based on its original capitalisation.

This sorted structure is what makes B-Tree lookups fast. When you search for a specific value, the database traverses from the root, comparing at each node: "is my target less than or greater than this node's value?" and following the appropriate branch. It reaches the correct position in O(log n) comparisons.

The critical point is this: **the index can only be navigated using the same values and the same comparison that the index was built on.** If you ask the index for `'user@example.com'` (all lowercase), it will look for that exact string in the sorted tree. It will not find it, because the tree contains `'User@Example.com'` — a different string as far as string comparison is concerned.

## Why LOWER() on a Column Is Index Kryptonite

Now we can understand the problem precisely. The login query is:

```sql
SELECT *
FROM users
WHERE LOWER(email) = LOWER('User@Example.com');
```

`LOWER('User@Example.com')` is a constant — it evaluates to `'user@example.com'` once, at query planning time, and that result is used for the comparison. So the query is functionally equivalent to:

```sql
SELECT *
FROM users
WHERE LOWER(email) = 'user@example.com';
```

The question PostgreSQL must answer is: _"Can I use the index on `email` to find rows where `LOWER(email) = 'user@example.com'`?"_

The answer is **no** — and here is exactly why. The index stores `email` values. The query is filtering on `LOWER(email)` — a _transformed_ version of email. These are not the same thing. PostgreSQL cannot look up `'user@example.com'` in an index that is sorted by `'User@Example.com'`, `'Admin@Company.com'`, and `'Bob@outlook.com'`, because those values, in their raw form, are not equal to `'user@example.com'` in a case-sensitive sort order.

```
WHY THE INDEX CANNOT BE USED
─────────────────────────────────────────────────────────────────────

The Index Contains:                  The Query Is Searching For:

  'Admin@Company.com'                  LOWER(email) = 'user@example.com'
  'alice@gmail.com'                          ↑
  'Bob@outlook.com'                    This is a COMPUTED value.
  'carol@yahoo.com'                    Not the raw column value.
  'david@hotmail.com'
  'Eve@protonmail.com'        PostgreSQL cannot ask the index:
  'Frank@work.com'            "Which raw emails, when lowercased,
  'User@Example.com'           equal 'user@example.com'?"
  'zara@domain.com'
                              The index has no knowledge of what
  ↑                           LOWER() does. It only knows the
  Sorted by RAW values.       raw values it was built on.
  LOWER() has never been      It cannot serve a query that
  applied to any of these.    transforms those values first.

Result: PostgreSQL CANNOT USE THIS INDEX.
        It must fall back to Sequential Scan.
        Every row in the table is read.
        LOWER() is applied to every single email.
        The matching row is found at the very end.
        12,000ms.
```

This is not a bug or a limitation in PostgreSQL. It is a mathematical necessity. An index is a pre-computed, sorted data structure. If the query does not use the same comparison the index was sorted by, the index's sorted order is meaningless for navigating to the answer.

Think of it this way: imagine a physical phone book sorted by last name. If you need to find everyone whose last name, when reversed, starts with the letter 'n', the phone book's sorted order gives you zero advantage. You still have to read every page. The phone book is not broken — it just was not built for that particular question.

## Seeing the Problem in EXPLAIN ANALYZE

Running `EXPLAIN ANALYZE` on the slow query reveals the Sequential Scan immediately:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE LOWER(email) = LOWER('User@Example.com');
```

```
Seq Scan on users  (cost=0.00..312500.00 rows=1 width=180)
                   (actual time=8341.221..11998.442 rows=1 loops=1)
  Filter: (lower((email)::text) = 'user@example.com'::text)
  Rows Removed by Filter: 9999999
Planning Time: 0.4 ms
Execution Time: 12001.3 ms
```

The first word is `Seq Scan` — the index is not being used at all. The `Filter` line shows the database evaluating `lower(email)` on every row. `Rows Removed by Filter: 9999999` means the database processed 10 million rows and discarded 9,999,999 of them to find the one matching user. All 12 seconds were spent doing work that an index should have made unnecessary.

Notice also that PostgreSQL already simplified `LOWER('User@Example.com')` to the constant `'user@example.com'` in the filter description — it knew the right-hand side was a constant and pre-evaluated it. But the left side, `lower(email)`, is applied to a column and cannot be pre-computed. Every row requires a function call.

## The Expression Index: Indexing the Result of a Function

The solution is to create an **Expression Index** — an index that does not store the raw column value, but instead stores the _pre-computed result_ of applying a function to that column.

```sql
CREATE INDEX idx_users_email_lower
ON users (LOWER(email));
```

This looks almost identical to a regular column index, except the argument is `LOWER(email)` — an expression — rather than just `email`. When PostgreSQL builds this index, it does not store `'User@Example.com'` in the leaf nodes. Instead, it applies `LOWER()` to each email value during index construction and stores the result. The B-Tree is now sorted on the lowercased values:

```
EXPRESSION INDEX on LOWER(email) — What is actually stored
─────────────────────────────────────────────────────────────────────

Leaf nodes, sorted alphabetically by the LOWERCASED email value:

  ┌────────────────────────────────────────────────────────────────┐
  │  'admin@company.com'    → ptr to heap row (block 14, slot 2)  │
  │  'alice@gmail.com'      → ptr to heap row (block 3,  slot 7)  │
  │  'bob@outlook.com'      → ptr to heap row (block 7,  slot 1)  │
  │  'carol@yahoo.com'      → ptr to heap row (block 2,  slot 4)  │
  │  'david@hotmail.com'    → ptr to heap row (block 9,  slot 3)  │
  │  'eve@protonmail.com'   → ptr to heap row (block 22, slot 5)  │
  │  'frank@work.com'       → ptr to heap row (block 5,  slot 9)  │
  │  'user@example.com'     → ptr to heap row (block 11, slot 6)  │
  │  'zara@domain.com'      → ptr to heap row (block 18, slot 2)  │
  └────────────────────────────────────────────────────────────────┘
         ↑
         These are the PRE-COMPUTED lowercase values.
         LOWER() was applied ONCE, at index build time.
         The original mixed-case values are gone from the index.

         Now the index IS the lowercased world.
         A query for 'user@example.com' can navigate
         this sorted tree perfectly.
```

The expression is evaluated **once per row at index creation time**, and the result is what gets stored. Every subsequent query benefits from that pre-computation. This is the fundamental trade-off of all database indexes: spend time and space once at write time to save time on every read.

## How PostgreSQL Recognises and Uses the Expression Index

Creating the expression index is only half of the solution. The query must also be written in a way that PostgreSQL's query planner recognises as matching the index expression.

When the planner evaluates a query, it looks at the `WHERE` clause and tries to match it against available indexes. For an expression index, the planner checks: _"Does the expression in my WHERE clause exactly match the expression this index was built on?"_

The query must be written as:

```sql
-- CORRECT: Matches the expression index LOWER(email)
SELECT *
FROM users
WHERE LOWER(email) = 'user@example.com';
```

Not as:

```sql
-- ALSO CORRECT (planner simplifies the constant):
SELECT *
FROM users
WHERE LOWER(email) = LOWER('User@Example.com');
-- PostgreSQL evaluates LOWER('User@Example.com') = 'user@example.com' at plan time
-- Then matches LOWER(email) against the index
```

Both forms work because on the right-hand side, `LOWER('User@Example.com')` is a constant expression that the planner evaluates once and replaces with `'user@example.com'`. The left-hand side `LOWER(email)` exactly matches the index expression, so the planner can use the index.

But what if the developer writes the query differently?

```sql
-- BROKEN: Does not use the expression index
SELECT *
FROM users
WHERE email = 'user@example.com';
-- Looks for exact match on raw email — index is on LOWER(email)
-- 'user@example.com' ≠ 'User@Example.com' in case-sensitive comparison
-- Regular index on (email) also cannot help (it is case-sensitive)

-- ALSO BROKEN: Still a sequential scan
SELECT *
FROM users
WHERE email ILIKE 'user@example.com';
-- ILIKE is case-insensitive but not served by LOWER(email) index
-- Requires a different approach (pg_trgm index for ILIKE)
```

The planner does strict syntactic matching of the WHERE expression against the index expression. `LOWER(email)` in the WHERE clause matches `LOWER(email)` in the index definition — character for character. Any variation that does not match exactly falls through to a Sequential Scan.

```
EXPRESSION MATCHING — How the planner decides

Index definition:  LOWER(email)
                       ↑
                   This exact expression is what the planner
                   looks for in the WHERE clause.

Query WHERE clause         → Index Used?
───────────────────────────────────────────────
LOWER(email) = 'user@...' → YES ✓ Exact match
LOWER(email) = LOWER('...')→ YES ✓ Right side is a constant,
                                    planner evaluates it once
lower(email) = 'user@...' → YES ✓ Case-insensitive function name
email = 'user@...'         → NO  ✗ Missing LOWER() wrapper
email ILIKE 'user@...'     → NO  ✗ Different function (ILIKE)
UPPER(email) = 'USER@...' → NO  ✗ UPPER ≠ LOWER
TRIM(LOWER(email)) = ...  → NO  ✗ Extra TRIM() not in index
```

The lesson here is that writing the application-side query consistently matters just as much as creating the right index. The index and the query must speak the same language — the same transformation, applied the same way.

## What Happens at Write Time: Maintaining the Expression Index

Every time a new user is inserted or a user updates their email address, PostgreSQL must update the expression index. This means:

1. Apply `LOWER()` to the new email value
2. Insert the lowercased result into the B-Tree at the correct sorted position
3. If it is an UPDATE, also remove the old lowercased value from its position

This is slightly more expensive than maintaining a plain column index, because the function must be evaluated at write time. For `LOWER()`, this cost is negligible — string lowercasing is an extremely cheap operation, a few nanoseconds per call. But for more expensive expressions (cryptographic hashes, complex string parsing, regular expressions), the write overhead can become meaningful and should be benchmarked.

```
WRITE TIME COST — Expression Index maintenance

INSERT INTO users (email, ...) VALUES ('NewUser@Domain.com', ...):

  Step 1: Write the full row to the heap file
          Row stored as-is: email = 'NewUser@Domain.com' ✓

  Step 2: Update the regular index on (email)  [if it still exists]
          Store 'NewUser@Domain.com' in B-Tree ✓

  Step 3: Update the expression index on LOWER(email)
          Evaluate: LOWER('NewUser@Domain.com') = 'newuser@domain.com'
          Store 'newuser@domain.com' in B-Tree ✓

  Total extra cost: one LOWER() function call
  LOWER() complexity: O(n) where n = string length
  For a 30-character email: ~30 character operations
  Time: nanoseconds — completely negligible

UPDATE users SET email = 'Updated@Domain.com' WHERE id = 42:

  Step 1: Update heap row
  Step 2: Remove 'newuser@domain.com' from expression index
          Insert 'updated@domain.com' into expression index
  Cost: one LOWER() call + two B-Tree operations — still negligible
```

For the `LOWER()` function specifically, the write overhead is so small it does not register in any practical benchmark. For functions like `MD5()` or complex `REGEXP_REPLACE()` expressions, you would want to measure before committing.

## The Constraint Bonus: Expression Indexes Enforce Uniqueness

Expression indexes can also enforce **uniqueness on the transformed value**, which is critical for email systems. Without this, two users could register as `User@Example.com` and `user@example.com` — they would pass a simple UNIQUE constraint on the raw `email` column because those are technically different strings, but they would collide on login because both would match `LOWER(email) = 'user@example.com'`.

A UNIQUE expression index solves this elegantly:

```sql
-- UNIQUE expression index: no two users can have the same
-- email when lowercased, regardless of capitalisation at registration
CREATE UNIQUE INDEX idx_users_email_lower_unique
ON users (LOWER(email));
```

This single index does two jobs simultaneously:

1. **Performance:** enables fast Index Scans for `WHERE LOWER(email) = ?` queries
2. **Integrity:** prevents duplicate registrations like `user@example.com` and `User@Example.com` from both existing in the database

```
UNIQUE EXPRESSION INDEX — Preventing case-variant duplicates

Existing data:
  id=1, email='user@example.com'    → LOWER = 'user@example.com' ✓

Attempt to insert:
  email='User@Example.com'
    → Evaluate LOWER('User@Example.com') = 'user@example.com'
    → Check index: 'user@example.com' already exists
    → UNIQUE VIOLATION: INSERT rejected ✓

Attempt to insert:
  email='USER@EXAMPLE.COM'
    → Evaluate LOWER('USER@EXAMPLE.COM') = 'user@example.com'
    → Check index: 'user@example.com' already exists
    → UNIQUE VIOLATION: INSERT rejected ✓

Attempt to insert:
  email='another@domain.com'
    → Evaluate LOWER('another@domain.com') = 'another@domain.com'
    → Check index: 'another@domain.com' does not exist
    → INSERT succeeds ✓

This replaces the need for application-level uniqueness checks.
The database enforces the invariant itself, atomically.
```

This is one of the most practical uses of expression indexes in real web applications — enforcing case-insensitive uniqueness on usernames and email addresses, at the database level, without any application code.

## EXPLAIN ANALYZE After the Fix

With the expression index created and the query using `WHERE LOWER(email) = 'user@example.com'`, running `EXPLAIN ANALYZE` shows a completely transformed execution plan:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE LOWER(email) = LOWER('User@Example.com');
```

```
Index Scan using idx_users_email_lower on users
  (cost=0.44..8.46 rows=1 width=180)
  (actual time=0.031..0.038 rows=1 loops=1)
  Index Cond: (lower((email)::text) = 'user@example.com'::text)
Buffers: shared hit=3
Planning Time: 0.3 ms
Execution Time: 0.041 ms   ← effectively 8ms end-to-end with network overhead
```

Three numbers tell the complete story. `Index Scan` instead of `Seq Scan` — the expression index is being used. `rows=1 loops=1` — the database found exactly one matching row in a single pass. `Buffers: shared hit=3` — only three memory pages were read, all from the buffer cache, zero disk reads. The 12-second query is now sub-millisecond at the database level, appearing as approximately 8ms end-to-end when accounting for network round-trip and application overhead.

## Expression Indexes Beyond LOWER(): A Pattern Library

The expression index concept is not limited to case-insensitive email lookups. Anywhere that your application consistently applies a function to a column in a WHERE clause, an expression index can eliminate the Sequential Scan. Here are the most common patterns you will encounter:

```
EXPRESSION INDEX PATTERN LIBRARY

─── 1. Case-insensitive search (the example we studied) ─────────────
Problem query:   WHERE LOWER(email) = 'user@example.com'
Index:           CREATE INDEX ON users (LOWER(email))
Also useful for: Usernames, names, codes, any case-insensitive lookup

─── 2. Date extraction — querying by year, month, day ───────────────
Problem query:   WHERE EXTRACT(YEAR FROM created_at) = 2024
Index:           CREATE INDEX ON orders (EXTRACT(YEAR FROM created_at))
Variation:       WHERE DATE_TRUNC('month', created_at) = '2024-01-01'
Index:           CREATE INDEX ON orders (DATE_TRUNC('month', created_at))
Use case:        Monthly reporting dashboards, date-based filtering

─── 3. JSON field extraction ─────────────────────────────────────────
Problem query:   WHERE metadata->>'country' = 'BD'
Index:           CREATE INDEX ON users ((metadata->>'country'))
                                         ↑ extra parens needed for
                                           complex expressions
Use case:        Semi-structured data stored as JSONB columns

─── 4. String transformations ────────────────────────────────────────
Problem query:   WHERE TRIM(phone_number) = '+8801234567890'
Index:           CREATE INDEX ON contacts (TRIM(phone_number))

Problem query:   WHERE REPLACE(sku, '-', '') = 'ABC123'
Index:           CREATE INDEX ON products (REPLACE(sku, '-', ''))

─── 5. Computed business logic ───────────────────────────────────────
Problem query:   WHERE (price * quantity) > 1000
Index:           CREATE INDEX ON order_items ((price * quantity))
Use case:        When the computed value is queried repeatedly

─── 6. Array operations ──────────────────────────────────────────────
Problem query:   WHERE ARRAY_LENGTH(tags, 1) > 5
Index:           CREATE INDEX ON posts (ARRAY_LENGTH(tags, 1))

─── 7. Substring or prefix extraction ───────────────────────────────
Problem query:   WHERE SUBSTRING(zip_code, 1, 3) = '120'
Index:           CREATE INDEX ON addresses (SUBSTRING(zip_code, 1, 3))
```

The pattern is always the same: if the application consistently wraps a column in a function call before comparing it in a WHERE clause, move that function call into the index definition. The function executes once per row at index build time, and zero times per query execution.

## The Important Constraint: Immutability of Functions

Not every function can be used in an expression index. PostgreSQL requires that the function used in an expression index be **IMMUTABLE** — meaning it always returns the same output for the same input, regardless of when it is called, the current database state, or session settings.

This constraint exists for a clear reason: the index pre-computes and stores function results. If the function could return different values at different times for the same input, the stored pre-computed values would become stale and incorrect.

```
IMMUTABILITY REQUIREMENT — What can and cannot be indexed

IMMUTABLE functions (safe to index — same input always same output):
  LOWER(text)          → 'Hello' always becomes 'hello' ✓
  UPPER(text)          → 'hello' always becomes 'HELLO' ✓
  TRIM(text)           → '  hi  ' always becomes 'hi' ✓
  LENGTH(text)         → 'hello' always has length 5 ✓
  EXTRACT(YEAR FROM t) → specific timestamp always same year ✓
  MD5(text)            → hash of 'hello' is always same value ✓
  price * quantity     → 10.00 * 3 always equals 30.00 ✓
  metadata->>'field'   → JSONB extraction is deterministic ✓

VOLATILE functions (unsafe to index — can return different values):
  NOW()                → returns different time every call ✗
  RANDOM()             → returns different number every call ✗
  CURRENT_USER         → returns different value per session ✗
  NEXTVAL('seq')       → returns different value every call ✗
  TIMEOFDAY()          → time-dependent ✗

STABLE functions (safe to query but CANNOT be indexed):
  These return same value within a single query but may vary
  between queries. PostgreSQL prohibits them in index expressions.
  AGE(timestamp)       → depends on current date ✗
  TO_CHAR(date, fmt)   → may depend on locale settings ✗

If you try to create an index on a VOLATILE or STABLE function:
  ERROR: functions in index expression must be marked IMMUTABLE
```

When you encounter this error, it means the function you want to index genuinely could return different values for the same input at different times — and an index storing stale pre-computed values would silently return wrong query results. PostgreSQL refuses to let you make this mistake.

If you need case-insensitive search and are using a non-English locale where `LOWER()` behaviour might vary by collation settings, PostgreSQL provides `LOWER(text)` with explicit collation specification, which remains immutable for a given collation.

## Citext: An Alternative Approach for Case-Insensitive Columns

While expression indexes are the most flexible solution, PostgreSQL also offers a built-in extension called `citext` (case-insensitive text) that handles the email problem differently — at the column type level rather than the index level.

```sql
-- Enable the extension
CREATE EXTENSION IF NOT EXISTS citext;

-- Define the column as citext instead of text/varchar
CREATE TABLE users (
    id    BIGSERIAL PRIMARY KEY,
    email CITEXT NOT NULL UNIQUE,   -- case-insensitive by type
    ...
);

-- Insert works normally
INSERT INTO users (email) VALUES ('User@Example.com');

-- Query without any LOWER() — comparison is automatically case-insensitive
SELECT * FROM users WHERE email = 'user@example.com';   -- finds the row
SELECT * FROM users WHERE email = 'USER@EXAMPLE.COM';   -- same result
```

With `citext`, a plain `CREATE INDEX ON users (email)` works correctly for case-insensitive lookups without any expression wrapping. The `citext` type redefines the equality operator to be case-insensitive at the type level, so a regular B-Tree index built on it inherently serves case-insensitive queries.

```
EXPRESSION INDEX vs CITEXT — Two approaches to the same problem

                      Expression Index        CITEXT Column
                      ────────────────        ─────────────
Index definition:     LOWER(email)            email  (regular)
Query syntax:         WHERE LOWER(email)=?    WHERE email=?
Index size:           Same                    Same
Query speed:          Same                    Same
Works with LIKE:      No (need pg_trgm)       Yes (for ILIKE)
Retrofitting:         Easy — add index        Hard — change column type
                       to existing table       + migration
Clarity:              Explicit in query       Implicit in schema
ORM compatibility:    Depends on ORM          Usually easier
```

For new projects, `citext` is often the cleaner choice — it pushes the case-insensitivity concern into the schema where it belongs and keeps application queries simple. For existing systems with millions of rows and an established `VARCHAR` or `TEXT` email column, adding an expression index is the zero-downtime path (using `CREATE INDEX CONCURRENTLY`) that avoids a risky column type migration.

## Summary: The Core Mental Model

The root cause of this 12-second query was a mismatch between what the index stored and what the query compared. The index stored `'User@Example.com'`. The query searched for `LOWER(email) = 'user@example.com'`. From the database's perspective, these are entirely different values, and the index's sorted order was useless for navigating to the transformed value.

An expression index resolves this by shifting the computation. Instead of applying `LOWER()` at query time — once per row, for every row in the table — it applies `LOWER()` at index build time, once per row, storing the result permanently. Every subsequent query compares its target value against the pre-computed lowercase values in the index, navigates the B-Tree in O(log n) steps, and finds its answer without touching the heap for any row other than the one that matches.

The 1,500× improvement — from 12,000ms to 8ms — came from replacing 10 million `LOWER()` function calls (one per row in a Sequential Scan) with a handful of B-Tree comparisons (roughly 23 comparisons to navigate log₂(10,000,000) levels in the tree), plus a single heap fetch to retrieve the matching row's data.

The broader principle belongs in your permanent engineering intuition: **if you consistently apply a function to a column in a WHERE clause, the index should store the result of that function, not the raw column value.** Index the world your queries actually live in, not the world as it exists in the heap.
