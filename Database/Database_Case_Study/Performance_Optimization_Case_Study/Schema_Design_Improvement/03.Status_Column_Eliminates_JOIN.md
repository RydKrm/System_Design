# The Notification Badge That Checked Two Tables on Every Page Load: How a Single Boolean Column and a Partial Index Achieved a 200× Speedup

> _"A relational database teaches you to store each fact once and derive everything else through queries. But engineering is the art of knowing when to break the rules wisely. Sometimes storing a fact in two places — once in a junction table for completeness, and once in a denormalized column for speed — is not laziness. It is the correct design for the access pattern you actually have."_

---

## Setting the Scene

You are working on the backend of a project management web application. Every user of the application has a notification inbox — alerts about comments on their tasks, mentions in discussions, deadline reminders, and team announcements. The application displays a small red badge in the header navigation bar showing how many unread notifications the user has. Every page load triggers this count, because the badge must always show the current number.

The notification system was designed carefully by the previous team. There is a `notifications` table containing all notifications ever sent to every user. There is a separate `reads` table — a junction table — that records which notifications each user has read. This design is clean and normalised: the act of reading a notification is recorded as a separate entity, and the "unread" state of any notification is derived by checking whether a corresponding read record exists.

The query that powers the unread count badge looks like this:

```sql
SELECT COUNT(*)
FROM notifications n
LEFT JOIN reads r
    ON n.id = r.notification_id AND r.user_id = n.user_id
WHERE r.id IS NULL
  AND n.user_id = 1;
```

This is an **anti-join** pattern — it finds notifications for which no corresponding read record exists. The `LEFT JOIN` matches each notification with its read record if one exists; the `WHERE r.id IS NULL` filter keeps only the notifications where no read record was found (meaning they are unread).

The logic is correct. When the application had a few thousand users and a few hundred notifications per user, it ran in about fifty milliseconds. Today, the application has three hundred thousand users, the notifications table has one hundred and fifty million rows, and the reads table has two hundred million rows. And the unread count query, which runs on every single page load for every user, takes two seconds.

Two seconds to display a badge number. Users notice it. The application feels sluggish. The mobile app's header renders blank for two seconds before the badge appears. The engineering team has started calling it "the badge tax" — the price you pay on every navigation, every refresh, every click, just to know how many notifications are unread.

Your senior engineer examines the schema and the query, runs `EXPLAIN ANALYZE`, and then leans back with the expression of someone who has solved this exact problem before. She says: _"We are normalising information that we need to read on every page load. We can afford to denormalise one boolean. The write cost of flipping a flag is nothing compared to the read cost of joining two large tables a million times a day."_

## Understanding the Anti-Join: Why It Is Expensive

The anti-join pattern — using `LEFT JOIN` combined with `WHERE foreign_key IS NULL` to find rows in one table that have no match in another — is one of the most common patterns in relational database work, and one of the most expensive to execute at scale.

To understand why, you need to trace what the database does to answer the question "which notifications for user 1 have no corresponding read record?"

The database must first find all notifications belonging to user 1. Suppose this user has eight hundred notifications accumulated over two years of using the application. The database uses an index on `notifications.user_id` to find these eight hundred rows quickly.

Then, for each of those eight hundred notifications, the database must check whether a corresponding row exists in the `reads` table. This check requires probing the `reads` table — specifically, looking for a row where `reads.notification_id = n.id AND reads.user_id = 1`. If an index exists on `(reads.notification_id, reads.user_id)`, this is an index lookup. If not, it is a scan.

Finally, the `LEFT JOIN` semantics mean that notifications with no match in `reads` produce a row with `r.id = NULL` in the join result — and the `WHERE r.id IS NULL` condition keeps only those rows. The result is a set of notification IDs representing unread notifications, which the outer `COUNT(*)` then counts.

This sequence of operations — find notifications, probe reads for each one, filter for nulls, count — is not conceptually complicated. But it involves two tables, two index lookups per row in the outer set, and the materialisation of a join result that includes null columns — all for the purpose of answering the simple binary question: "how many unread notifications does user 1 have?"

```
ANTI-JOIN EXECUTION: What the database does to find unread count

  Step 1: Find user 1's notifications
  ┌─────────────────────────────────────────────────────────────┐
  │  Index scan on notifications(user_id)                       │
  │  WHERE user_id = 1                                          │
  │  → Found: 800 notification rows                             │
  └─────────────────────────────────────────────────────────────┘
                        │
                        ▼
  Step 2: For each of 800 notifications, check reads table
  ┌─────────────────────────────────────────────────────────────┐
  │  For notification id=101:                                   │
  │    Probe reads WHERE notification_id=101 AND user_id=1     │
  │    → Found read record → this notification is READ         │
  │  For notification id=102:                                   │
  │    Probe reads WHERE notification_id=102 AND user_id=1     │
  │    → No read record found → this notification is UNREAD    │
  │  For notification id=103: ... (repeat 798 more times)       │
  └─────────────────────────────────────────────────────────────┘
                        │
                        ▼
  Step 3: LEFT JOIN result (800 rows, some with null r.id)
  ┌─────────────────────────────────────────────────────────────┐
  │  n.id=101, r.id=5234  → READ    → WHERE r.id IS NULL → skip│
  │  n.id=102, r.id=NULL  → UNREAD  → WHERE r.id IS NULL → keep│
  │  n.id=103, r.id=9812  → READ    → WHERE r.id IS NULL → skip│
  │  ...                                                        │
  └─────────────────────────────────────────────────────────────┘
                        │
                        ▼
  Step 4: COUNT(*) of remaining unread notifications
  → Answer: 47 unread notifications
  
  Operations: 1 index scan + 800 reads-table probes + 800 join rows
  This executes on every single page load, for every user.
```

On the surface, eight hundred probes against an indexed table sounds fast. But consider the reality at production scale. The application has three hundred thousand daily active users, each loading pages an average of fifteen times per day. That is four and a half million badge count queries per day. Each query performs eight hundred index lookups against the reads table. That is 3.6 billion index probes per day against the reads table, just to display badge numbers. The reads table is under constant, heavy probe pressure, causing cache contention, I/O amplification, and the two-second response times that are making the application feel slow.

The fundamental problem is not the query's correctness — it is the fact that answering a simple read-state question requires two-table interaction on every read. The reads table must be consulted on every page load because that is where the read state is stored. The read state, expressed as the presence or absence of a row in a junction table, is inherently expensive to check — you must do a lookup to find the absence of something.

## The Root Cause: Normalisation in the Wrong Place

The previous team's decision to track read state in a separate `reads` table was motivated by a genuine normalisation principle: reading a notification is an event — it has a timestamp, it might have additional metadata, and it is conceptually distinct from the notification itself. Storing it as a separate row in a junction table honours this.

But this normalisation decision has a hidden cost: the state that the application reads on every page load — "is this notification read or not?" — is represented as the presence or absence of a row in another table. Checking presence is easy. Checking **absence** — the anti-join — requires a table probe that returns empty, which is slower than a probe that returns data, and which cannot be short-circuited the way `EXISTS` can be.

More importantly, the unread count is not derived by reading each individual notification's state. It is derived by counting across many notifications. This aggregation over a derived boolean — read or not read — is precisely the kind of computation that benefits enormously from materialising the boolean directly on the notification row rather than deriving it from the presence of another row.

```
WHERE THE READ STATE LIVES — Two approaches

Normalised (junction table):
  notifications table:
  ┌────────────────────────────────────────────────────┐
  │ id=101 │ user_id=1 │ message='...' │ (no read info)│
  │ id=102 │ user_id=1 │ message='...' │ (no read info)│
  │ id=103 │ user_id=1 │ message='...' │ (no read info)│
  └────────────────────────────────────────────────────┘
  reads table:
  ┌──────────────────────────────────────────────────────────┐
  │ id=5234 │ notification_id=101 │ user_id=1 │ read_at=... │
  │ id=5235 │ notification_id=103 │ user_id=1 │ read_at=... │
  └──────────────────────────────────────────────────────────┘
  To find unread count: join two tables, find the gap.

Denormalised (status column):
  notifications table:
  ┌──────────────────────────────────────────────────────────────┐
  │ id=101 │ user_id=1 │ message='...' │ is_read=TRUE           │
  │ id=102 │ user_id=1 │ message='...' │ is_read=FALSE ← unread │
  │ id=103 │ user_id=1 │ message='...' │ is_read=TRUE           │
  └──────────────────────────────────────────────────────────────┘
  To find unread count: scan notifications for user_id=1, is_read=FALSE.
  One table. One index. Constant speed.
```

The `is_read` column is technically redundant — the same information is derivable from the `reads` table. But it is the right kind of redundancy: targeted, controlled denormalisation that makes a specific, critically hot read path dramatically faster, at the cost of a trivially small write overhead.

## The Solution: Add `is_read`, Add a Partial Index

The fix involves two changes: a schema change and an index creation.

**Schema change:** Add a boolean `is_read` column to the `notifications` table with a default of `FALSE`. When the application marks a notification as read (the user opens the notification panel, or all notifications are bulk-marked as read), it updates this column.

```sql
-- Add the status column
ALTER TABLE notifications
ADD COLUMN is_read BOOLEAN NOT NULL DEFAULT FALSE;

-- Backfill existing notifications that have read records
UPDATE notifications n
SET is_read = TRUE
WHERE EXISTS (
    SELECT 1 FROM reads r
    WHERE r.notification_id = n.id
      AND r.user_id = n.user_id
);
```

The backfill query syncs the new column with the existing junction table data. It uses `EXISTS` (efficient, short-circuits) rather than a `JOIN` to avoid the same anti-join overhead. After this backfill, `is_read` is accurate for all historical notifications.

**Application change:** When a user reads a notification, the application that previously inserted a row into the `reads` table now also updates the `notifications` row:

```sql
-- When user marks notification as read:
BEGIN;

-- Keep the reads table if needed for audit/history
INSERT INTO reads (notification_id, user_id, read_at)
VALUES (102, 1, NOW())
ON CONFLICT DO NOTHING;

-- Also update the denormalized flag
UPDATE notifications
SET is_read = TRUE
WHERE id = 102;

COMMIT;
```

The `reads` table can be kept for audit history — knowing when each notification was read — while the `is_read` flag on the notification row serves the hot query path. Both are maintained atomically within the same transaction, so they are never out of sync.

**The partial index:** This is the key that makes the solution truly fast. A partial index is an index that covers only a subset of the table's rows — specifically, only the rows where a given condition is true. For the unread count query, the only rows that ever matter are the unread ones. Read notifications are never counted again. A partial index that covers only `is_read = FALSE` rows is dramatically smaller than a full index on all notifications, because it contains only the fraction of rows that are currently unread.

```sql
-- Partial index: only indexes UNREAD notifications
CREATE INDEX idx_notifications_unread
ON notifications (user_id)
WHERE is_read = FALSE;
```

This index contains only the entries for notifications where `is_read = FALSE`. On a table of one hundred and fifty million notifications, if the average user has forty-seven unread notifications, the partial index contains approximately 300,000 users × 47 unread = roughly 14 million entries — a tiny fraction of the full table. And when a notification is marked as read, its entry is **automatically removed from the partial index** by PostgreSQL — the index stays lean and current without any manual intervention.

## The New Query: Clean, Fast, Single-Table

With `is_read` in place and the partial index created, the unread count query becomes:

```sql
SELECT COUNT(*)
FROM notifications
WHERE user_id = 1
  AND is_read = FALSE;
```

This is about as simple as a database query can be. One table. Two filter conditions. Both conditions covered by the partial index. The database performs a single partial index range scan — scanning only the entries in `idx_notifications_unread` where `user_id = 1` — counts them, and returns. The entire operation is an index-only scan if the index covers all needed columns, touching no heap pages at all.

```
NEW QUERY EXECUTION: What the database does now

  Query: SELECT COUNT(*) FROM notifications WHERE user_id=1 AND is_read=FALSE

  Step 1: Locate partial index idx_notifications_unread
  ┌─────────────────────────────────────────────────────────────┐
  │  Partial index covers: all rows WHERE is_read = FALSE       │
  │  Index entries for user_id = 1:                            │
  │    user_id=1, n.id=102  (notification 102 is unread)       │
  │    user_id=1, n.id=247  (notification 247 is unread)       │
  │    ... (47 total entries)                                   │
  └─────────────────────────────────────────────────────────────┘

  Step 2: Count the index entries
  → Answer: 47 unread notifications

  Operations: 1 partial index scan covering 47 entries
  No join. No reads table. No null checks.
  No heap access (index-only scan).
  Time: ~10ms (index traversal for 47 entries)

  vs. Before:
  1 index scan + 800 reads-table probes + 800 join rows = 2,000ms
```

The partial index is especially elegant because of its self-maintaining nature. When notification 102 is marked as read — `UPDATE notifications SET is_read = TRUE WHERE id = 102` — PostgreSQL automatically removes id=102 from the partial index, because the row no longer satisfies the `WHERE is_read = FALSE` condition. The index shrinks with every read action. The index never grows stale. And because only unread notifications are indexed, the index is always as small as possible — it never accumulates the tombstone weight of read notifications that are no longer relevant to the query.

## The Write Overhead: What You Are Trading

Denormalization is never truly free — the write overhead that the junction-table design eliminated now reappears as a column update. Whenever a notification is marked as read, the application must now execute an additional `UPDATE notifications SET is_read = TRUE WHERE id = ?` in addition to the `INSERT INTO reads` it was already performing.

It is important to evaluate this overhead honestly. A single-row `UPDATE` on a `BIGINT` primary key is one of the most efficient database operations possible — an index lookup on the primary key (O(log N)), a single row modification, and a WAL record. On a modern database server, this takes approximately one to two milliseconds for a single row, and the primary key index traversal is nearly always served from cache.

The reads table insertion was already this cheap. The notification update adds the same order of cost. The total write cost per "user reads a notification" event goes from approximately two milliseconds to approximately four milliseconds — double the write cost, but from two milliseconds to four milliseconds. This is an acceptable tradeoff in almost any scenario where the read path executes millions of times more frequently than the write path.

```
WRITE COST ANALYSIS — What each read action costs

Before (without is_read column):
  User marks notification as read:
  ┌────────────────────────────────────────────────────────────┐
  │  INSERT INTO reads (notification_id, user_id, read_at)    │
  │  VALUES (102, 1, NOW())                                   │
  │  Cost: ~2ms (index lookup + insert + WAL write)           │
  └────────────────────────────────────────────────────────────┘

After (with is_read column):
  User marks notification as read:
  ┌────────────────────────────────────────────────────────────┐
  │  INSERT INTO reads (notification_id, user_id, read_at)    │
  │  VALUES (102, 1, NOW())                                   │
  │  Cost: ~2ms                                               │
  │                                                            │
  │  UPDATE notifications SET is_read = TRUE WHERE id = 102   │
  │  Cost: ~2ms                                               │
  │                                                            │
  │  Total: ~4ms (double the write cost)                       │
  └────────────────────────────────────────────────────────────┘

Read frequency vs write frequency (typical notification system):
  Page loads per day (read path executes): 4,500,000
  Read actions per day (write path executes): ~180,000

  Ratio: 25 reads for every 1 write.

  Cost of doing it wrong (reads at 2,000ms each):
    4,500,000 × 2,000ms = 9,000,000,000ms = 2,500 hours of CPU time/day

  Cost of the extra write overhead (2ms extra per write action):
    180,000 × 2ms = 360,000ms = 6 minutes of CPU time/day

  The write overhead is 6 minutes. The read savings is 2,500 hours.
  The tradeoff is not even close.
```

This asymmetry — where the read operation is vastly more frequent than the write operation — is precisely the condition under which deliberate denormalization for read performance is the correct architectural decision. The "correct" normalised design is also the unaffordable one. The "slightly incorrect" denormalized design is the one that keeps the application responsive.

## The Partial Index: A Deeper Appreciation

The partial index deserves additional attention because it is one of PostgreSQL's most powerful and underused features, and its behaviour in this scenario is particularly elegant.

A standard index on `notifications (user_id)` would contain one hundred and fifty million entries — one for every notification row, regardless of whether it is read or unread. This index is useful for any query filtering by `user_id`, but it is large, takes time to update on every insert, and contains many entries that the unread count query will never use (the read notifications).

The partial index `CREATE INDEX ON notifications (user_id) WHERE is_read = FALSE` contains only entries for currently unread notifications. If one percent of all notifications are unread (a typical pattern — most notifications get read eventually), this index is approximately one percent the size of a full index — 1.5 million entries instead of 150 million. It fits in a fraction of the cache space, updates faster, and serves the unread count query with zero wasted entries.

The behaviour when a notification is marked read is particularly noteworthy. When `is_read` changes from `FALSE` to `TRUE`, the row transitions from satisfying `WHERE is_read = FALSE` to not satisfying it. PostgreSQL automatically removes this row from the partial index during the update. The partial index self-maintains to reflect only the current state of unread notifications. This self-maintaining property means the index never becomes stale and never needs manual cleanup.

```
PARTIAL INDEX SELF-MAINTENANCE OVER TIME

  Day 1: User 1 receives 10 new notifications
  Partial index for user_id=1: 10 entries (all unread)
  ┌────────────────────────────────────────────────────────┐
  │ (user_id=1, n.id=101) (user_id=1, n.id=102) ...       │
  │ (user_id=1, n.id=110)                                  │
  │ Index size: 10 entries                                 │
  └────────────────────────────────────────────────────────┘

  Day 2: User reads notifications 101-108
  UPDATE notifications SET is_read=TRUE WHERE id IN (101,102,...,108)
  → PostgreSQL removes entries 101-108 from partial index automatically
  Partial index for user_id=1: 2 entries
  ┌────────────────────────────────────────────────────────┐
  │ (user_id=1, n.id=109) (user_id=1, n.id=110)           │
  │ Index size: 2 entries                                  │
  └────────────────────────────────────────────────────────┘

  Day 3: User receives 5 new notifications
  INSERT INTO notifications ... (5 rows with is_read=FALSE)
  → PostgreSQL adds 5 entries to partial index automatically
  Partial index for user_id=1: 7 entries
  ┌────────────────────────────────────────────────────────┐
  │ (user_id=1, n.id=109) (user_id=1, n.id=110)           │
  │ (user_id=1, n.id=211) ... (user_id=1, n.id=215)       │
  │ Index size: 7 entries                                  │
  └────────────────────────────────────────────────────────┘

  The index always contains exactly the right entries.
  No maintenance required. No scheduled cleanup. No staleness.
  It reflects the current unread state of the notifications table.
```

A full index on `(user_id, is_read)` would also work and would serve the same query. But the partial index is strictly better: it is smaller, updates faster (only on inserts of unread notifications and updates to mark as read), and covers the exact access pattern without wasted space. The partial index is an expression of the specific query it was designed to serve, written directly into the index definition.

## Generalising the Pattern: When a Status Column Eliminates an Anti-Join

The specific solution in this case study — a boolean status column paired with a partial index — is an instance of a broader pattern that applies whenever you have an expensive anti-join powering a hot read path.

The anti-join pattern appears when you have a "main" table and a "completion" or "acknowledgement" table, and your hot query needs to find main-table rows for which no completion record exists. This pattern is extremely common:

- `notifications` + `reads` → find unread notifications (this case study)
- `tasks` + `completions` → find incomplete tasks
- `messages` + `deliveries` → find undelivered messages
- `invoices` + `payments` → find unpaid invoices
- `emails` + `opens` → find unopened emails
- `alerts` + `acknowledgements` → find unacknowledged alerts

In every one of these cases, the same analysis applies: if the hot read query is "find the main-table rows for which no completion record exists," and if this query runs far more frequently than the action that creates completion records, then a denormalized boolean status column on the main table — with a partial index covering only the incomplete/unread/unpaid state — will produce an order-of-magnitude improvement in query performance at a negligible increase in write cost.

```
THE GENERAL PATTERN: Status Column + Partial Index

  Before (anti-join, expensive):
  ┌─────────────────────────────────────────────────────────────┐
  │  SELECT COUNT(*) FROM main_table m                          │
  │  LEFT JOIN completion_table c ON m.id = c.main_id          │
  │    AND c.user_id = m.user_id                                │
  │  WHERE c.id IS NULL AND m.user_id = :user_id               │
  │                                                             │
  │  Cost: join + hash + null filter for every page load       │
  └─────────────────────────────────────────────────────────────┘

  After (status column + partial index, cheap):
  ┌─────────────────────────────────────────────────────────────┐
  │  ALTER TABLE main_table                                     │
  │  ADD COLUMN is_complete BOOLEAN NOT NULL DEFAULT FALSE;     │
  │                                                             │
  │  CREATE INDEX idx_main_incomplete ON main_table (user_id)   │
  │  WHERE is_complete = FALSE;                                 │
  │                                                             │
  │  SELECT COUNT(*) FROM main_table                            │
  │  WHERE user_id = :user_id AND is_complete = FALSE;          │
  │                                                             │
  │  Cost: partial index scan of only incomplete rows           │
  └─────────────────────────────────────────────────────────────┘

  Apply when: read frequency >> write frequency
              query needs count or list of "missing completion" rows
              write cost of maintaining status column is acceptable
```

The pattern is not appropriate when: the "complete" or "read" state is complex and cannot be represented as a single boolean; when the action of completing is accompanied by many reads of the status (making the write and read frequencies comparable); or when the completion status is frequently reversed or re-applied (a notification might be marked unread again, requiring the `is_read = FALSE` partial index to be updated on both mark-read and mark-unread actions).

## The Result: 2,000ms → 10ms

After adding the `is_read` column, backfilling it from the existing reads table, and creating the partial index, the unread count query went from nearly two seconds to just under ten milliseconds — a two-hundred-fold improvement. The notification badge in the application header became effectively instantaneous. The "badge tax" was eliminated.

```
BEFORE — Anti-join (LEFT JOIN + IS NULL):
  Tables accessed:          2 (notifications + reads)
  Hash table built:         200,000 read records for user (44ms)
  Index probes:             800 (one per notification)
  Join rows produced:       800
  Null-filtered rows kept:  47
  Heap page reads:          Many
  Execution time:           1,988ms

AFTER — Status column + partial index:
  Tables accessed:          1 (notifications only)
  Hash table built:         None
  Index probes:             47 (directly into partial index)
  Join rows produced:       None (no join)
  Null filtering:           None (no nulls)
  Heap page reads:          0 (index-only scan)
  Execution time:           9.7ms

Improvement: 1,988ms ÷ 9.7ms = 204× faster
Daily CPU savings:
  Before: 4,500,000 loads × 1.988s = 9,000,000s = 2,500 hours/day
  After:  4,500,000 loads × 0.010s =    45,000s = 12.5 hours/day
  Savings: 2,487 CPU hours per day — freed for other work
```

The four million five hundred thousand daily page loads that previously consumed two thousand five hundred CPU hours of database work now consume just twelve and a half hours. The database has vastly more capacity available for other queries, other users, and other operations. The application's overall responsiveness improved as the database stopped being the bottleneck.

## The Lesson That Stays With You

This case study illustrates one of the most important balancing acts in database design: the tension between normalisation for correctness and denormalisation for performance. The normalised design — tracking read state as rows in a junction table — is conceptually cleaner and avoids data redundancy. But it makes the hot read path expensive, and in a system where the hot read path executes millions of times per day, that expense accumulates into a serious performance problem.

The resolution is not to abandon normalisation wholesale — it is to apply targeted, intentional denormalisation at precisely the points where the performance need is greatest and the write overhead is smallest. The `is_read` boolean column is a few bytes per notification row. It is maintained with a single `UPDATE` on each read action. And it enables an index-only scan of a partial index covering only the rows the query actually needs. The cost is trivial. The benefit is enormous.

The broader lesson is about access patterns. Every schema design decision should be evaluated not just for semantic correctness but for its performance characteristics under the actual access patterns of the application. The question to ask is not only "is this the right way to model the data?" but also "how many times per second will the application read from this schema, and how expensive will each read be?" When the answer to the second question is "millions of times per day, and two seconds each time," the schema needs to be redesigned for the access pattern, even if the redesign introduces a controlled redundancy.

A well-designed partial index is one of the most expressive tools in PostgreSQL's arsenal. It encodes, directly in the database schema, the specific query it was built to serve. Reading the index definition tells you exactly what query it optimises: "count unread notifications for a user." That clarity of purpose — schema elements designed for specific access patterns — is the hallmark of a mature database design.

## Summary

This case study examines a notification system whose unread count query — displayed as a badge on every page load — took two seconds because it used an anti-join pattern: `LEFT JOIN reads ... WHERE r.id IS NULL`. The anti-join required the database to find eight hundred notifications for a user, build a hash table of two hundred thousand read records, probe the hash table for each notification, and filter for the nulls — all for the purpose of counting forty-seven unread notifications. This query executed four and a half million times per day, consuming two thousand five hundred CPU hours of database work daily.

The solution was to add a denormalized `is_read BOOLEAN NOT NULL DEFAULT FALSE` column to the `notifications` table, updating it atomically alongside the existing `reads` table insertion whenever a user reads a notification. A partial index `CREATE INDEX ON notifications (user_id) WHERE is_read = FALSE` was created, covering only currently-unread notification rows — a fraction of the full table. The unread count query was rewritten to a single-table `SELECT COUNT(*) WHERE user_id = 1 AND is_read = FALSE`, which the database resolved with an index-only scan of the partial index, touching zero heap pages. Execution time dropped from 1,988 milliseconds to 9.7 milliseconds — a 204-fold improvement.

The lesson is that targeted denormalization — adding a status column that derives from an existing junction table — is the appropriate architectural response when an anti-join powers a high-frequency read path. The write overhead of maintaining a boolean flag is measured in milliseconds and scales with write frequency. The read benefit is measured in orders-of-magnitude improvement and scales with read frequency. When reads vastly outnumber writes, the tradeoff is overwhelmingly in favour of the status column. Normalisation is the starting point; the access pattern is what determines where intentional denormalization is warranted.
