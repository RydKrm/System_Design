# The Migration That Talked to the Database Fifty Million Times: How Batching Replaced Three Hours of Per-Row Updates with Four Minutes

> _"A relational database was designed to operate on sets of rows with a single instruction. An application that issues one instruction per row is not using a relational database — it is using an extremely expensive and slow key-value store, one round trip at a time."_

---

## Setting the Scene

Picture a backend engineering team at a consumer technology company. The product has been running for four years and has accumulated fifty million registered users. The business has decided to introduce a loyalty tier system — users will be classified as either "gold" tier if their total historical spend exceeds one thousand dollars, or "silver" tier otherwise. A new `tier` column needs to be populated on the `users` table for all fifty million existing accounts before the feature can be launched.

The task seems straightforward. There is already a `spend` column on the `users` table containing each user's total lifetime spend. The logic for determining the tier is simple: if `spend > 1000`, assign `'gold'`; otherwise assign `'silver'`. A junior engineer is given the task on a Friday afternoon and told to have it done before the Monday morning launch.

The junior engineer writes what seems like perfectly reasonable code:

```python
users = db.execute("SELECT id, spend FROM users").fetchall()

for user in users:
    tier = 'gold' if user.spend > 1000 else 'silver'
    db.execute(
        "UPDATE users SET tier = ? WHERE id = ?",
        (tier, user.id)
    )
    db.commit()
```

The script starts running. An hour passes. The progress bar — based on row counts — shows it is about eleven percent complete. The engineer does a quick calculation: eleven percent in one hour means roughly nine hours total. Not Friday-to-Monday anymore. The engineer messages the team lead in a panic.

The team lead looks at the code, looks at the time, and says with the calm of someone who has seen this exact situation before: _"Stop the script. I am going to show you one of the most fundamental things there is to know about databases. The problem is not your logic — the problem is that you are treating the database like it processes one row at a time, when the entire point of a relational database is that it does not have to."_

---

## Understanding the True Cost of One Update Per Row

To understand why the per-row approach is so slow, you need to think carefully about everything that happens when your application code executes a single `UPDATE` statement against a database.

The first cost is **network latency**. Unless your application and database server are running on the same physical machine — which they almost never are in production — every database operation requires a round trip over the network. The application serialises the SQL statement, sends it across the network to the database server, the server processes it, serialises the result, and sends it back. Even on a fast local network, this round trip takes somewhere between half a millisecond and five milliseconds. On a cloud environment where application servers and database servers are in the same data centre but on different machines, you might expect one to two milliseconds per round trip.

One to two milliseconds sounds trivial. Multiplied by fifty million, it becomes fifty thousand to one hundred thousand seconds — between thirteen and twenty-eight hours of pure network latency, before the database has done a single moment of useful work.

The second cost is **transaction overhead**. Each `db.commit()` call in the loop causes the database to flush the transaction log to durable storage before acknowledging completion. This write-ahead log (WAL) flush is a relatively expensive operation involving a disk I/O cycle. Committing fifty million individual transactions means fifty million WAL flushes — an enormous amount of disk I/O that serves no purpose beyond satisfying the artificial constraint of one-transaction-per-row.

The third cost is **lock acquisition and release**. Every `UPDATE` statement must acquire a row-level lock on the target row, perform the update, and release the lock. Fifty million lock acquisitions and releases, one at a time, generate significant overhead in the database's lock management subsystem.

The fourth cost is **query parsing and planning**. Even though the query text is the same each time, the database must parse the SQL, check the schema, and produce a query plan for each of the fifty million executions. With a prepared statement, the parsing cost is eliminated — but the planning and execution overhead remains.

```
WHAT HAPPENS FOR EACH OF 50 MILLION UPDATE STATEMENTS

  Application Server                    Database Server
  ─────────────────                    ───────────────
  1. Prepare SQL string                      │
  2. Serialize parameters                    │
  3. Send over network ──────────────────────► 4. Receive query
  Wait...                                    5. Parse SQL
  Wait...                                    6. Plan query
  Wait...                                    7. Acquire row lock
  Wait...                                    8. Locate row on disk
  Wait...                                    9. Write new value
  Wait...                                    10. Write WAL entry
  Wait...                                    11. Flush WAL to disk
  Wait...                                    12. Release lock
  13. Receive acknowledgement ◄──────────────13. Send result
  14. Call db.commit()                        │
  Send COMMIT over network ─────────────────► 15. Flush WAL again
  Wait for flush...                           │
  16. Receive commit ack ◄────────────────────16. Send ack
  17. Start next iteration                    │

  Total per row: ~2-5ms
  Total for 50 million rows: 100,000 – 250,000 seconds
  In hours: 28 to 70 hours
  Observed: ~3 hours (with autocommit off, batched implicit transaction)
            Still unacceptably slow.

  Useful work done (changing tier value): microseconds per row.
  Overhead (network, locking, WAL, parsing): milliseconds per row.
  Overhead-to-work ratio: 1000:1 or worse.
```

This is the fundamental pathology of the per-row update pattern. The overhead is not proportional to the complexity of the work — it is a fixed cost per round trip, per transaction, per lock cycle. The actual work of changing a text column from one value to another takes microseconds. But you are paying milliseconds of overhead to do it. When you do this fifty million times, the overhead dominates the runtime entirely.

## Why SQL Was Designed as a Set-Based Language

To understand why there is such a dramatically better approach, you need to understand something fundamental about what relational databases are and what they were designed to do.

A relational database is built around **set-based operations**. When E.F. Codd proposed the relational model in 1970, the central idea was that you express data manipulations in terms of entire sets of rows at once, and the database engine figures out the most efficient physical way to execute that set operation. SQL — Structured Query Language — is the language that implements this relational model. Its `UPDATE`, `DELETE`, `INSERT`, and `SELECT` statements are inherently set-based: they operate on all rows that satisfy a condition, simultaneously, in a single database engine operation.

When you write `UPDATE users SET tier = 'gold' WHERE spend > 1000`, you are not telling the database "find a user whose spend is greater than one thousand and update their tier, then find another such user, then another." You are telling the database: "here is a set of rows, defined by this condition, and here is the new value for them." The database engine receives this instruction once, plans how to execute it once, acquires the necessary locks in an efficient batch, writes all the changes, writes one WAL entry covering all the changes, and commits once. The overhead costs — network round trips, WAL flushes, planning cycles — are paid once, regardless of whether the affected set contains ten rows or ten million rows.

This is the philosophy that the per-row update loop violates. Instead of expressing the operation as a set, it decomposes it into fifty million individual operations, each paying the full overhead cost independently. The application is doing the loop that the database engine was specifically designed to do internally, far more efficiently.

## Solution 1: The Direct Bulk SQL UPDATE

The first and most straightforward solution is to express the entire tier assignment as a single SQL statement using a `CASE` expression:

```sql
UPDATE users
SET tier = CASE
    WHEN spend > 1000 THEN 'gold'
    ELSE 'silver'
END;
```

This single statement replaces all fifty million individual `UPDATE` statements. The database engine reads the instruction once, scans the `users` table once (or uses whatever access path it deems most efficient), evaluates the `CASE` expression for each row, writes all modified values, writes one covering WAL entry, and commits. The network round trip happens once. The transaction overhead happens once. The query planning happens once.

The `CASE` expression is a conditional value expression that the database evaluates inline, row by row, during its own internal scan — not through application-level iteration. Each row is read, the `CASE` condition is evaluated against the `spend` column value that is right there in the same row, and the appropriate tier string is written. This is the database doing exactly what it was designed to do.

```
SOLUTION 1: SINGLE BULK UPDATE

Before (50 million statements):
┌─────────────────────────────────────────────────────────────────┐
│  App → DB: UPDATE users SET tier='silver' WHERE id=1  (2ms)    │
│  App → DB: UPDATE users SET tier='gold'   WHERE id=2  (2ms)    │
│  App → DB: UPDATE users SET tier='silver' WHERE id=3  (2ms)    │
│  ...                                                           │
│  (50,000,000 round trips × 2ms = 100,000 seconds ≈ 28 hours)  │
└─────────────────────────────────────────────────────────────────┘

After (1 statement):
┌─────────────────────────────────────────────────────────────────┐
│  App → DB: UPDATE users SET tier = CASE                        │
│                WHEN spend > 1000 THEN 'gold'                   │
│                ELSE 'silver'                                   │
│            END;                                                │
│  (1 round trip, 1 WAL flush, 1 commit)                         │
│  DB scans table internally, evaluates CASE per row             │
│  Done in: ~3 minutes                                           │
└─────────────────────────────────────────────────────────────────┘
```

This approach works beautifully when the logic for determining the new value can be expressed as a SQL expression over columns that already exist in the same table. In our case, the tier is determined entirely by the `spend` column that is already in the `users` table — so the logic is perfectly self-contained in SQL and requires no data from the application side.

However, there is an important practical consideration for large tables: a single `UPDATE` that modifies fifty million rows is a single transaction. This transaction holds locks on all modified rows for its entire duration. It generates an enormous WAL entry. And if anything goes wrong partway through — a database crash, a network interruption — the entire operation must be rolled back and started from scratch. For a three-to-four-minute operation, this risk is acceptable. For a migration that might take thirty minutes or more (on truly enormous tables or very slow disk), you might want a more carefully managed approach.

## Solution 2: COPY to Temp Table, Then Joined UPDATE

The second solution is more sophisticated and more appropriate when the new values cannot be computed purely from the existing table columns — for example, when the tiers are calculated externally, perhaps by a machine learning model, a complex business rules engine, or a data pipeline that aggregates from multiple sources.

This approach has two phases. In the first phase, you load all the new `(user_id, tier)` pairs into the database using `COPY` — PostgreSQL's ultra-fast bulk data loading mechanism. `COPY` bypasses much of the overhead of individual `INSERT` statements and can load millions of rows in seconds by streaming data directly into the database in a compact binary or CSV format. The data is loaded into a temporary table that exists only for the duration of the session.

In the second phase, you execute a single `UPDATE` that joins the `users` table against the temporary table and pulls the new tier values across:

```sql
-- Phase 1: Load new tier values into a temp table (via COPY or bulk INSERT)
CREATE TEMP TABLE temp_tiers (
    user_id  BIGINT,
    new_tier TEXT
);

-- COPY streams 50 million rows from application to DB in seconds
COPY temp_tiers (user_id, new_tier) FROM STDIN WITH (FORMAT csv);
-- (application streams CSV data here)

-- Phase 2: Single joined UPDATE
UPDATE users
SET tier = t.new_tier
FROM temp_tiers t
WHERE users.id = t.user_id;
```

The `UPDATE ... FROM` syntax is PostgreSQL's mechanism for updating one table using data from another. The database executes this as a join internally — it can use a hash join or merge join between `users` and `temp_tiers`, efficiently matching rows by `user_id` and applying the new tier values in a single pass.

```
SOLUTION 2: COPY + JOINED UPDATE

Phase 1: COPY (bulk load, no round trips per row)
  Application streams CSV to database:
  ┌────────────────────────────────────────────────────────┐
  │  COPY temp_tiers FROM STDIN                           │
  │  1,silver\n                                           │
  │  2,gold\n                                             │
  │  3,silver\n                                           │
  │  ...                                                  │
  │  50000000,gold\n                                      │
  │                                                       │
  │  50M rows loaded in: ~60 seconds                      │
  │  Round trips: 1 (one streaming COPY command)          │
  └────────────────────────────────────────────────────────┘

Phase 2: Joined UPDATE (one statement)
  ┌────────────────────────────────────────────────────────┐
  │  UPDATE users                                         │
  │  SET tier = t.new_tier                                │
  │  FROM temp_tiers t                                    │
  │  WHERE users.id = t.user_id                           │
  │                                                       │
  │  Execution plan: Hash Join (temp_tiers → users)       │
  │  50M rows updated in: ~180 seconds                    │
  │  Round trips: 1                                       │
  └────────────────────────────────────────────────────────┘

Total: ~4 minutes, 2 database commands, no per-row overhead.
```

The COPY-based approach is particularly powerful for data migrations where the new values come from an external source or a complex computation. It separates the concern of "producing the new values" (which can be done in the application or data pipeline) from "applying them to the database" (which is done in a single efficient database operation).

## The Write-Ahead Log: Why Bulk Operations Are Easier on the Database Internals

A detail that is worth understanding at a slightly deeper level is why bulk operations are so much gentler on the database's internal machinery, beyond just the obvious reduction in round trips.

Every modification to a PostgreSQL database — every `INSERT`, `UPDATE`, or `DELETE` — is first written to the **Write-Ahead Log (WAL)** before the actual data pages are modified. This is how PostgreSQL ensures durability: if the server crashes after a WAL record is written but before the data page is updated on disk, the WAL record allows the modification to be replayed during crash recovery. The WAL is the database's safety net.

When you commit fifty million individual transactions, you generate fifty million WAL records — one per commit — and each commit triggers a flush of the WAL to durable storage (a `fsync` call). Each `fsync` takes somewhere between one and twenty milliseconds depending on the storage hardware. Fifty million `fsync` calls is a catastrophic number of disk I/O operations, and on many storage systems, it is the dominant cost of the per-row update approach.

When you execute a single bulk `UPDATE`, PostgreSQL groups all the WAL records for all fifty million modified rows into a single transaction's WAL output. There is one `fsync` at commit time, not fifty million. The database's WAL writer can buffer and coalesce these records efficiently, writing them to disk in large sequential chunks rather than fifty million tiny random writes. Sequential disk writes are orders of magnitude faster than random writes on both traditional spinning disks and, to a lesser extent, on SSDs.

```
WAL WRITE PATTERN: Per-Row vs Bulk

Per-row approach (50 million transactions):
  ┌──────────────────────────────────────────────────────────┐
  │  WAL: [txn1: update user1] → fsync → [txn2: update user2]│
  │       → fsync → [txn3: update user3] → fsync → ...      │
  │                                                          │
  │  50,000,000 fsyncs                                       │
  │  Each fsync: 1-20ms                                      │
  │  WAL fsync total: 50,000 to 1,000,000 seconds           │
  │  (This alone would take hours)                           │
  └──────────────────────────────────────────────────────────┘

Bulk approach (1 transaction):
  ┌──────────────────────────────────────────────────────────┐
  │  WAL: [txn1: update user1, user2, user3, ... user50M]   │
  │       → single fsync at commit                           │
  │                                                          │
  │  1 fsync                                                 │
  │  WAL fsync total: 1-20ms                                 │
  └──────────────────────────────────────────────────────────┘
```

This WAL difference is often the single largest contributor to the performance gap between per-row and bulk operations, particularly on storage systems where `fsync` is slow — which describes most network-attached storage, many cloud disk volumes, and all spinning disks under high I/O load.

## The Safe Middle Ground: Batched Chunked Updates for Production

The two solutions described above represent the ideal in terms of performance, but they come with one important practical caveat that matters deeply in production systems: both approaches lock all fifty million rows simultaneously within a single transaction.

For a migration running during a maintenance window, locking all rows is fine. But for a migration running on a live production database — one that is simultaneously serving user traffic — holding locks on fifty million rows for three to four minutes means that any concurrent `UPDATE` or `SELECT FOR UPDATE` on any of those rows must wait for the migration transaction to complete. On a busy system, this can cause application-level timeouts and a terrible user experience, even though the migration itself is running quickly.

The professional practice for large live migrations is a **chunked batch approach**: divide the fifty million rows into chunks of ten thousand or fifty thousand, and process each chunk as a single transaction. This gives you most of the performance benefit of bulk operations (each chunk does ten thousand or fifty thousand updates in one round trip), while keeping individual transaction durations short (a few hundred milliseconds per chunk) and lock hold times minimal.

```sql
-- Safe chunked approach for live production migrations
DO $$
DECLARE
    batch_size  INT := 50000;
    last_id     BIGINT := 0;
    max_id      BIGINT;
    rows_updated INT;
BEGIN
    SELECT MAX(id) INTO max_id FROM users;

    WHILE last_id < max_id LOOP

        UPDATE users
        SET tier = CASE
            WHEN spend > 1000 THEN 'gold'
            ELSE 'silver'
        END
        WHERE id > last_id
          AND id <= last_id + batch_size;

        GET DIAGNOSTICS rows_updated = ROW_COUNT;
        last_id := last_id + batch_size;

        -- Brief pause to let other queries breathe
        PERFORM pg_sleep(0.01);

        RAISE NOTICE 'Updated through id %. Rows this batch: %', last_id, rows_updated;
    END LOOP;
END $$;
```

```
CHUNKED BATCH APPROACH

Total rows: 50,000,000
Batch size: 50,000
Number of batches: 1,000

Each batch:
  ┌────────────────────────────────────────────────────────┐
  │  1 round trip                                         │
  │  1 WAL flush                                          │
  │  50,000 rows updated                                  │
  │  Locks held: ~200ms (then released)                   │
  │  Other queries: can proceed during 10ms sleep         │
  └────────────────────────────────────────────────────────┘

All 1,000 batches:
  ┌────────────────────────────────────────────────────────┐
  │  1,000 round trips (vs 50,000,000 before)             │
  │  1,000 WAL flushes (vs 50,000,000 before)             │
  │  Total time: ~5-8 minutes                             │
  │  Maximum lock hold at any moment: ~200ms              │
  │  Production traffic: largely unaffected               │
  └────────────────────────────────────────────────────────┘
```

The chunked approach is the professional middle ground. You give up a few minutes of additional time compared to the pure single-statement approach, in exchange for not disrupting your live users and not holding a five-minute exclusive transaction open on your production database. This is almost always the right tradeoff for a large live migration.

## The Application Architecture Lesson: Set-Based Thinking vs Imperative Thinking

The per-row update loop is not just a performance mistake — it is a symptom of a particular way of thinking about data manipulation that is natural for application code but fundamentally at odds with how relational databases work.

Application programming languages like Python, Go, and Java are **imperative** — they describe a sequence of steps to be executed one at a time. A `for` loop is the natural way to process a collection of things: get one thing, do something to it, get the next thing, do something to it, and so on. Developers who primarily think in terms of application code naturally reach for this pattern when they need to update many database rows.

SQL is **declarative and set-based** — it describes a transformation over a set of rows, leaving the implementation details to the database engine. When you write `UPDATE users SET tier = CASE WHEN spend > 1000 THEN 'gold' ELSE 'silver' END`, you are not instructing the database to loop over users one at a time. You are declaring a transformation — "for all users, the tier should be this function of their spend" — and leaving the database to implement that transformation as efficiently as it can.

The mental shift required is to move from thinking "how do I visit each row and change it?" to thinking "how do I describe the entire set of changes I want to make in one expression?" This shift in thinking is one of the most important transitions in becoming an effective backend engineer. It unlocks the database's true capabilities and avoids the pathological overhead of treating a set-based system as a row-at-a-time system.

```
TWO WAYS OF THINKING ABOUT THE SAME PROBLEM

Imperative (application code) thinking:
  "For each user in the users table:
     Look at their spend.
     If it's over 1000, set tier to gold.
     Otherwise, set tier to silver.
     Save the change."

  → 50 million individual operations
  → 50 million network round trips
  → 3 hours

Set-based (SQL) thinking:
  "The tier for every user should equal:
     'gold' if their spend exceeds 1000,
     'silver' otherwise.
     Make it so."

  → 1 database operation
  → 1 network round trip
  → 4 minutes

Same result. Different paradigm. 45× difference in time.
```

The set-based way of thinking is not just about performance — it is also about correctness and maintainability. A set-based SQL operation is atomic: either all fifty million rows are updated, or none are. There is no possibility of a partial update where the first twenty million users have the correct tier and the last thirty million still have the old value, because the script was interrupted. The imperative per-row approach does not have this atomicity guarantee unless you very carefully manage transactions across all fifty million operations — which is exactly what makes it even slower.

## When Per-Row Updates Are Unavoidable — and How to Minimise Their Cost

In the interest of completeness, it is worth acknowledging that there are genuine situations where per-row application-level updates cannot be avoided — where the new value for each row depends on a complex computation that cannot be expressed in SQL, involving external API calls, machine learning model inferences, or business logic too complex to encode in a single query.

In these cases, the right approach is to minimise the overhead as much as possible. Using a **prepared statement** eliminates the per-query parsing cost. Grouping updates into **explicit transactions of several hundred or a few thousand rows** dramatically reduces the number of WAL flushes and transaction overhead cycles. Using **pipelining** (sending multiple statements without waiting for each acknowledgement before sending the next) reduces the impact of network round-trip latency. And batching the logic on the application side to produce bulk `INSERT ... ON CONFLICT DO UPDATE` or `UPDATE ... FROM` statements with many rows of values eliminates most of the per-row overhead even in complex cases.

But whenever the new values can be expressed in SQL — which is more often than developers initially assume — the right answer is always to push the computation into a single set-based SQL operation and let the database engine do the work it was designed to do.

## The Result: 3 Hours → 4 Minutes

After the junior engineer's per-row script was stopped and the bulk SQL update was executed, the tier column was populated across all fifty million users in approximately four minutes. The operation used one network round trip, one WAL flush, and zero application-level iteration. The launch proceeded on schedule.

```
BEFORE — Per-row update loop:
  Individual UPDATE statements:   50,000,000
  Network round trips:            50,000,000
  WAL flushes (commits):          50,000,000
  Total execution time:           ~3 hours (extrapolated)
  Risk of partial completion:     High

AFTER — Single bulk UPDATE:
  Individual UPDATE statements:   1
  Network round trips:            1
  WAL flushes (commits):          1
  Total execution time:           ~4 minutes
  Risk of partial completion:     None (atomic transaction)

Improvement: 180 minutes ÷ 4 minutes = 45× faster
```

The performance improvement of forty-five times comes almost entirely from eliminating overhead, not from any clever algorithmic optimisation. The actual work — reading each user's spend value and writing a tier string — is the same in both approaches. The difference is that the bulk approach pays the fixed overhead costs once, while the per-row approach pays them fifty million times.

## The Lesson That Stays With You

The pattern of updating rows one at a time from application code is one of the most common performance mistakes in backend engineering, and it is common precisely because it is the most natural way to think about the problem when you come from an application programming background. The `for` loop is intuitive. The SQL `UPDATE` with a `CASE` expression is slightly less intuitive. But the gap in performance is so vast — hours versus minutes, or minutes versus seconds — that learning to think set-based is one of the highest-return skills you can develop as a backend engineer.

Before you write any application-level loop that sends one database statement per row, pause and ask: "Can I express this as a single SQL operation over the entire set of affected rows?" In most cases — data migrations, bulk status updates, tier recalculations, flagging records based on criteria — the answer is yes. And when the answer is yes, the set-based SQL approach is almost always faster by a factor of ten to one thousand, requires less application code, and gives you atomicity guarantees that the loop-based approach cannot provide without significant additional complexity.

The database is extraordinarily good at operating on sets of rows. Use it for what it is good at.

## Summary

This case study follows a data migration that needed to populate a `tier` column on fifty million user rows based on their historical spend. The initial approach — a Python loop executing one `UPDATE` statement per user — was on track to take several hours due to the accumulated overhead of fifty million individual network round trips, fifty million WAL flush operations, and fifty million transaction management cycles. The actual work of changing a text value took microseconds per row, but the overhead took milliseconds per row, making the ratio of useful work to overhead approximately one to one thousand.

The first solution was to replace the loop with a single `UPDATE ... SET tier = CASE WHEN spend > 1000 THEN 'gold' ELSE 'silver' END` statement, which expressed the entire transformation as a set-based SQL operation and let the database engine execute it internally in a single pass, with one round trip, one WAL flush, and one commit. Execution time dropped from hours to approximately four minutes. The second solution — for cases where new values come from external sources — was to stream the new values into a temporary table via `COPY` and then apply them with a single joined `UPDATE ... FROM` statement.

The deeper lesson is one of paradigm: SQL is a set-based, declarative language, and the database engine is optimised to operate on sets of rows with single instructions. Application code that decomposes set operations into per-row loops forfeits all of these optimisations and pays a fixed overhead cost for every row it touches. The professional practice is to push data transformations into SQL whenever possible, batch unavoidable application-level updates into chunks rather than individual statements, and always ask "can the database do this as a set operation?" before writing any loop that iterates over rows.
