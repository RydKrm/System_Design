# The Query That Fooled the Planner: How Rewriting a Subquery as a JOIN Made an HR Report 450× Faster

> _"Two SQL queries can ask the exact same question and receive the exact same answer, yet one may take eighteen seconds while the other takes forty milliseconds. The difference lies not in what you ask, but in how you ask it."_

---

## Setting the Scene

Picture yourself as a junior backend engineer, two months into your first job at a mid-sized technology company. The product is an internal HR management system — the kind of software that HR teams use to manage employee records, run payroll, generate compliance reports, and track headcount across different regions. It is not a consumer-facing product, but it is mission-critical: senior leadership uses it every morning to pull reports before their daily stand-up calls.

One day, the HR operations team files a complaint with engineering. Their most important daily report — a query that fetches a list of all employees working in departments located in the Asia region — has started taking an agonising amount of time to load. What used to feel instantaneous now takes nearly eighteen full seconds every time they run it. The VP of HR is furious. Eighteen seconds of staring at a loading spinner, first thing in the morning, every morning, is not acceptable.

Your senior engineer pulls up the query and takes a long look at it. Within thirty seconds, she says calmly: _"I know what this is. Let me show you something that will change how you think about SQL for the rest of your career."_

This is that lesson.

---

## The Offending Query

The query that is causing all the pain looks like this:

```sql
SELECT *
FROM employees
WHERE department_id IN (
    SELECT id
    FROM departments
    WHERE region = 'Asia'
);
```

To a human reading this, the logic is perfectly clear and beautifully expressed. You are asking: _"Give me all employees whose department is one of the departments located in the Asia region."_ It reads almost like plain English. It is intuitive, it is correct, and it will return exactly the right data. And yet, it takes eighteen thousand milliseconds to do so.

The `employees` table contains five hundred thousand rows — half a million employees spread across the company's global operations. The `departments` table is much smaller, containing only a few hundred rows at most. The query needs to match each employee's `department_id` against the list of Asian department IDs.

---

## Before We Understand the Problem, We Must Understand the Players

To truly grasp why this query is slow, you need to understand two things that are happening behind the scenes: what a **subquery** is and who the **query planner** is.

A subquery is simply a query nested inside another query. In our case, the inner query is `SELECT id FROM departments WHERE region = 'Asia'`. This inner query runs and produces a result set — a list of department IDs, say something like `(5, 12, 17, 23, 41)`. The outer query then uses this list to filter employees. The concept is elegant: you ask one question to get an intermediate answer, and then you feed that answer into a second question.

The query planner, also sometimes called the query optimizer, is one of the most sophisticated pieces of software inside a database engine. When you send a SQL query to PostgreSQL, the raw text of your query does not run directly. Instead, a piece of software — the planner — reads your query, thinks deeply about it, considers all the possible ways it could physically execute that query, estimates the cost of each approach, and then chooses the strategy it believes will be fastest. Think of the planner as a very clever strategist who, given the instructions "travel from New York to Los Angeles," decides whether you should fly, drive, or take a train based on current traffic conditions, your budget, and your luggage.

The tragedy of our slow query is that the planner made a poor strategic choice — and the query's shape invited it to do so.

---

## The Root Cause: The Correlated Subquery Trap

When the senior engineer ran `EXPLAIN` — a command that shows you the query planner's execution strategy without actually running the query — she saw something alarming.

```sql
EXPLAIN
SELECT *
FROM employees
WHERE department_id IN (
    SELECT id
    FROM departments
    WHERE region = 'Asia'
);
```

The output looked something like this:

```
Seq Scan on employees  (cost=0.00..8750000.00 rows=125000 width=320)
  Filter: (SubPlan 1)
  SubPlan 1
    ->  Seq Scan on departments  (cost=0.00..17.50 rows=25 width=4)
          Filter: ((region)::text = 'Asia'::text)
```

That innocent-looking `SubPlan 1` underneath the employees scan is the disaster. Let us decode what is happening here.

The planner decided to execute the subquery as what is called a **correlated subquery** — meaning it executes the inner `SELECT id FROM departments WHERE region = 'Asia'` query once for every single row in the `employees` table. It does not run the inner query once to produce the list of Asian department IDs and then use that list. Instead, it goes row by row through the employees table and for each employee, it asks: "is this employee's department_id in the set returned by the subquery?" — and to answer that, it re-executes the subquery from scratch.

```
THE CORRELATED SUBQUERY EXECUTION — What the database actually does

  employees table (500,000 rows)
  ┌─────────────────────────────────────────────────┐
  │  Row 1: Alice,  dept_id=5                       │
  │                    │                            │
  │                    └──► Run subquery:           │
  │                         SELECT id FROM depts    │
  │                         WHERE region='Asia'     │
  │                         Result: {5,12,17,23,41} │
  │                         Is 5 in {5,12,17,23,41}?│
  │                         YES → include row       │
  │                                                 │
  │  Row 2: Bob,    dept_id=7                       │
  │                    │                            │
  │                    └──► Run subquery AGAIN:     │
  │                         SELECT id FROM depts    │
  │                         WHERE region='Asia'     │
  │                         Result: {5,12,17,23,41} │
  │                         Is 7 in {5,12,17,23,41}?│
  │                         NO → skip row           │
  │                                                 │
  │  Row 3: Carol,  dept_id=12                      │
  │                    │                            │
  │                    └──► Run subquery AGAIN:     │
  │                         (same query, same result│
  │                          but executed fresh)    │
  │                                                 │
  │  ... (repeated 500,000 times) ...               │
  └─────────────────────────────────────────────────┘

  Total subquery executions: 500,000
  Departments table scanned: 500,000 times
  ↑ This is why it takes 18 seconds.
```

The math is brutal. Five hundred thousand employees, each triggering one execution of the subquery, which itself scans the departments table. Even though the departments table is small, scanning it half a million times adds up catastrophically. This is the database equivalent of looking up a word in a dictionary — and then throwing the dictionary away and looking up the same word again for every sentence you write, instead of just remembering the definition.

---

## But Wait — Why Doesn't the Planner Optimize This?

This is the question that every engineer asks at this point, and it is a great question. If the result of the subquery is always the same — it will always return the same set of Asian department IDs — why does the database not just run it once, cache the result, and reuse it? That would be the smart thing to do, and a sufficiently clever planner should figure this out automatically, right?

The honest answer is: sometimes it does, and sometimes it does not. Database query planners are extraordinarily sophisticated, but they are not perfect. The planner makes its decisions based on **statistics** — approximate information it maintains about each table, such as how many rows there are, how many distinct values exist in each column, and how those values are distributed. The planner uses these statistics to estimate the cost of different execution strategies and chooses the one it thinks will be cheapest.

In this particular case, the planner's statistics and cost estimation led it to believe that treating the `IN (subquery)` as a correlated nested loop was acceptable. Perhaps the statistics were stale. Perhaps the table had recently grown from fifty thousand rows to five hundred thousand rows and the statistics had not been updated. Perhaps the planner's cost model simply did not penalize the nested loop approach heavily enough for this particular combination of data sizes.

The deeper lesson here is one of the most important things you can internalize as a backend engineer: **the query planner is not infallible.** It is a heuristic system that makes educated guesses. Your job, especially on performance-sensitive queries, is to understand what the planner is doing and, when necessary, give it a better shape to work with.

---

## The Solution: Rewriting as an Explicit JOIN

The fix that the senior engineer applied was elegantly simple. She did not add an index. She did not change any database configuration. She did not restructure the tables. She rewrote the query into a shape that communicates the same intention but forces the planner into a different — and dramatically more efficient — execution strategy.

The rewritten query looks like this:

```sql
SELECT e.*
FROM employees e
JOIN departments d ON e.department_id = d.id
WHERE d.region = 'Asia';
```

This query asks exactly the same question as the original. The results are identical, byte for byte. But look at what happens when you run `EXPLAIN` on this version:

```
Hash Join  (cost=18.50..9250.00 rows=125000 width=320)
  Hash Cond: (e.department_id = d.id)
  ->  Seq Scan on employees e  (cost=0.00..8500.00 rows=500000 width=320)
  ->  Hash  (cost=17.50..17.50 rows=80 width=4)
        ->  Seq Scan on departments d  (cost=0.00..17.50 rows=80 width=4)
              Filter: ((region)::text = 'Asia'::text)
```

The first word has changed from `Seq Scan` to `Hash Join`. This is everything. Let us understand what a Hash Join is and why it is so much better.

---

## The Hash Join: Why It Is Blazingly Fast

A Hash Join is one of the smartest and most efficient algorithms a database can use to combine two tables. It works in two phases, and understanding these two phases will permanently change how you think about database performance.

In the first phase, called the **build phase**, the database takes the smaller of the two tables — in our case, the `departments` table filtered down to only the Asian departments — and reads every row from it. For each row it reads, it runs the department's `id` value through a hash function and stores the result in an in-memory hash table. A hash function is simply a mathematical formula that converts any value into a short, fixed-size code, like a fingerprint. Departments with similar IDs do not get similar fingerprints — the hash function deliberately scatters values so that lookups can be done in near-constant time.

In the second phase, called the **probe phase**, the database reads through the `employees` table exactly once. For each employee row it encounters, it takes the `department_id` value, runs it through the same hash function, and checks whether that fingerprint exists in the in-memory hash table that was built in phase one. If it does, the employee is in an Asian department — include them. If it does not, move on.

```
HASH JOIN EXECUTION — What the database does with the rewritten query

Phase 1: BUILD (run once, on the smaller table)
─────────────────────────────────────────────────────────────
  Scan departments table (only ~300 rows):
  Filter for region = 'Asia' → 25 matching rows

  Build hash table in memory:
  ┌─────────────────────────────────────────┐
  │  Hash Table (tiny, fits in RAM easily)  │
  │  hash(5)  → dept_id=5  ✓               │
  │  hash(12) → dept_id=12 ✓               │
  │  hash(17) → dept_id=17 ✓               │
  │  hash(23) → dept_id=23 ✓               │
  │  hash(41) → dept_id=41 ✓               │
  │  (25 entries total)                     │
  └─────────────────────────────────────────┘
  Cost: One single scan of a 300-row table. Negligible.

Phase 2: PROBE (run once, on the larger table)
─────────────────────────────────────────────────────────────
  Scan employees table (500,000 rows), one pass only:

  Row: Alice,  dept_id=5  → hash(5) in table? YES → include
  Row: Bob,    dept_id=7  → hash(7) in table? NO  → skip
  Row: Carol,  dept_id=12 → hash(12) in table? YES → include
  Row: David,  dept_id=99 → hash(99) in table? NO  → skip
  ...
  (500,000 employees checked, each in O(1) time)

Total cost: 1 small table scan + 1 large table scan
            Subquery executions: 1 (not 500,000)
            Result: ~40ms
```

The contrast with the correlated subquery is stark. The Hash Join scans the departments table exactly one time. The Hash Join scans the employees table exactly one time. Each lookup into the hash table is an O(1) operation — constant time, regardless of how many entries are in the table — because hash functions are designed for this purpose. The total work is proportional to the sum of the two table sizes, not their product.

The correlated subquery, by contrast, performs work proportional to the product: five hundred thousand employees multiplied by the cost of scanning the departments table. In computer science terms, one approach is O(N + M) and the other is O(N × M). For large values of N and M, the difference is the difference between a working system and a broken one.

## Why Are IN (Subquery) and JOIN Logically Equivalent?

This is a subtle but important point that deserves careful attention. The two queries — the original with `IN (subquery)` and the rewritten one with `JOIN` — produce identical results. They are logically equivalent. So why does one perform so differently from the other?

The answer lies in what SQL actually is as a language. SQL is a **declarative** language. When you write a SQL query, you are describing **what** you want, not **how** to compute it. You are saying "give me employees in Asian departments" — you are not instructing the database to use a hash join, or a nested loop, or any particular algorithm. The choice of algorithm is entirely left to the query planner.

The `IN (subquery)` syntax, despite being logically equivalent to a JOIN, carries a **different syntactic signal** that some query planners interpret differently. Some planners — especially older versions or in certain edge cases — see `IN (subquery)` and more readily reach for the correlated nested loop execution strategy. The `JOIN` syntax, on the other hand, is an explicit declaration of a relationship between two tables, and planners are heavily optimized to handle JOINs efficiently with Hash Joins, Merge Joins, or other smart algorithms.

Modern query planners — like those in recent versions of PostgreSQL — have become quite good at transforming `IN (subquery)` into an equivalent join internally. But they do not always succeed, especially when the subquery is complex, when statistics are stale, or when the cost model is miscalibrated. The practical lesson is: when you know you are expressing a relationship between two tables, writing it as an explicit JOIN both communicates your intent more clearly and gives the planner the best possible starting point.

## Understanding EXPLAIN: Your Most Powerful Diagnostic Tool

No discussion of query performance would be complete without a thorough understanding of `EXPLAIN` and `EXPLAIN ANALYZE`. These commands are your X-ray machine — they let you see inside the database's mind and understand exactly what it is planning to do, or what it actually did.

`EXPLAIN` alone shows you the query plan without executing the query. It is safe to run on production systems because it does not actually touch the data. `EXPLAIN ANALYZE` actually executes the query, measures the real time taken at each step, and reports both the planner's estimates and the actual measured results side by side. This is invaluable for diagnosing cases where the planner's estimates are wildly off from reality — which is often the root cause of poor plan choices.

When reading an `EXPLAIN` output, you read it from the most-indented lines upward, like reading a tree from its leaves to its root. Each node in the plan tree is an operation, and the tree structure tells you how data flows — the output of inner operations feeds into outer ones. The key terms to watch for are `Seq Scan` (sequential full table scan — a red flag on large tables), `Index Scan` (the planner is using an index — generally good), `Hash Join` (efficient joining via a hash table), `Nested Loop` (row-by-row joining — efficient only when the inner side is tiny or indexed), and `SubPlan` (a correlated subquery executed repeatedly — almost always a performance concern).

```
HOW TO READ EXPLAIN OUTPUT

EXPLAIN output is a tree, read bottom-up / inside-out:

Hash Join  (cost=18.50..9250.00)          ← outermost: the final join
  →  Seq Scan on employees                 ← probe side: scanned once
  →  Hash                                  ← build the hash table
       →  Seq Scan on departments           ← innermost: scanned once
            Filter: region = 'Asia'         ← filter applied here

Data flows upward:
departments scan → filter → hash table → employees scan → join → result
```

The most important habit you can develop as an engineer working with databases is to run `EXPLAIN ANALYZE` on every query that is either slow or that operates on large tables, before you deploy it to production. Looking at query plans is not an advanced skill reserved for database administrators — it is a fundamental practice that every backend engineer should be comfortable with from early in their career.

## The Broader Principle: Query Shape Affects Execution Strategy

The deepest lesson this case study teaches is one that goes far beyond this particular query or this particular database. It is a principle that applies across almost every database system you will ever work with: **the way you shape a query influences the strategy the planner uses to execute it, and different execution strategies have wildly different performance characteristics.**

SQL's declarative nature is both its greatest strength and a source of occasional frustration. Its strength is that you can express complex data retrieval logic in very readable, high-level terms without worrying about the implementation details. The frustration comes when the planner chooses a suboptimal implementation — because you gave it a query shape that did not clearly communicate the most efficient approach.

This is why experienced database engineers do not just think about "what SQL produces the correct result." They also think about "what SQL produces the correct result AND guides the planner toward an efficient execution strategy." These are two separate concerns, and ignoring the second one leads to exactly the kind of crisis we saw here — a query that is logically correct but practically unusable.

When you are dealing with `IN` clauses that involve subqueries, it is worth remembering a simple mental model: `IN (subquery)` says "check if this value appears in this list that you must compute somehow," while `JOIN` says "combine these two sets of rows by matching on this key." The latter is a much clearer instruction for the planner, and it opens the door to a much wider range of efficient join algorithms.

---

## When This Pattern Applies — And When It Does Not

It is worth noting that the rewrite from `IN (subquery)` to `JOIN` is not always the right answer, and understanding the nuances will make you a more careful and thoughtful engineer.

The `IN (subquery)` pattern is most likely to cause trouble when the subquery is what database literature calls **uncorrelated** — meaning its result does not depend on values from the outer query — but the planner fails to recognize this and treats it as correlated. This is the situation we encountered. The inner query `SELECT id FROM departments WHERE region = 'Asia'` produces the same result regardless of which employee row is being evaluated. A perfect planner would compute it once and reuse the result. An imperfect planner may not.

The `JOIN` rewrite is generally safe and correct when you are looking for rows in one table that have a matching row in another table, which is the most common use case for `IN (subquery)`. However, there are cases where the semantics differ subtly. For instance, if the joined table can have multiple matching rows for a single row in the main table, a `JOIN` will return duplicate rows whereas `IN` will not. In our example, each department has a unique ID, so each employee can match at most one department, and duplicates are not a concern. But if the structure were different — say, you were checking `IN (SELECT employee_id FROM project_assignments WHERE project = 'X')` and an employee could appear multiple times in `project_assignments` — a naive `JOIN` would return duplicate employee rows. In such cases, you would need to add `DISTINCT` or use an `EXISTS` clause instead of converting directly to a `JOIN`.

The `EXISTS` clause deserves special mention here. It is another way to express the same kind of membership check, and modern planners tend to handle it very well:

```sql
SELECT e.*
FROM employees e
WHERE EXISTS (
    SELECT 1
    FROM departments d
    WHERE d.id = e.department_id
      AND d.region = 'Asia'
);
```

`EXISTS` short-circuits as soon as a match is found and does not return a value — it only needs to know if at least one matching row exists. Modern PostgreSQL handles both `EXISTS` and the explicit `JOIN` very efficiently. The explicit `JOIN` is generally preferred for readability when you also need columns from the joined table, while `EXISTS` is preferred when you only want to filter rows from the main table without risking duplicates.

## The Result: 18,000ms → 40ms

After the query was rewritten and deployed, the HR team's morning report began loading in under a second. The eighteen-second wait vanished. The `EXPLAIN ANALYZE` output on the rewritten query told the story clearly:

```

           (actual time=1.231..38.992 rows=87432 loops=1)
  Hash Cond: (e.department_id = d.id)
  ->  Seq Scan on employees e
      (actual time=0.012..15.234 rows=500000 loops=1)
  ->  Hash  (actual time=0.891..0.891 rows=25 loops=1)
```

Notice the critical detail in the hash table line: `Memory Usage: 9kB`. Nine kilobytes. The entire set of Asian department IDs fit into nine kilobytes of RAM, built once, and then used to check all five hundred thousand employees in a single blazing-fast pass. From eighteen thousand milliseconds down to thirty-nine milliseconds — a four-hundred-and-fifty-fold improvement — achieved by changing nothing about the database structure, nothing about the hardware, and nothing about the data. Only the shape of the query changed.

## The Lesson That Stays With You

The engineers who built the original query were not incompetent. The subquery version is a perfectly natural way to express the logic in SQL. It is the kind of query that any developer with reasonable SQL knowledge would write on their first attempt. And at the scale where the system started — perhaps ten thousand employees when the codebase was first written — it likely worked just fine. The problem only revealed itself at five hundred thousand rows, by which point the architectural choice had been locked in for years.

This is one of the most dangerous failure modes in software engineering: **a design choice that is perfectly adequate at small scale but becomes catastrophically expensive at large scale**. The code works, the tests pass, the development database is fast, and everyone ships confidently — and then one day, six months after launch, with real production data, everything falls apart. Understanding this failure mode early in your career is a genuine competitive advantage.

The practical lessons you should carry with you are these. When you write a query that uses `IN (subquery)`, always consider rewriting it as an explicit `JOIN` and comparing the query plans. When a query is unexpectedly slow, run `EXPLAIN ANALYZE` before making any assumptions about the cause — the output will tell you precisely where time is being spent and give you a concrete starting point for optimization. Understand that SQL is declarative and the planner is not infallible — you have both the right and the responsibility to guide it toward efficient execution strategies by choosing clear, well-structured query shapes. And finally, never assume that a query that is fast today will remain fast as your data grows — performance at ten thousand rows and performance at five hundred thousand rows can be in entirely different universes.

## A Mental Model to Carry Forward

To help you remember the core insight of this case study, think of the database as a chef working in a restaurant kitchen. You are the customer, and your SQL query is your order.

When you write `IN (subquery)`, it is like telling the chef: "Please check if this dish uses any ingredient from our pantry that meets certain conditions. Oh, and please go check the pantry again for each dish you make, even if they all have the same ingredient list." The chef dutifully walks to the pantry half a million times.

When you write a `JOIN`, it is like telling the chef: "Look, here is a printed list of all the qualifying ingredients. Keep this list on your counter and just check against it as you work." The chef checks the pantry once to make the list, pins it to the counter, and then works through all five hundred thousand dishes efficiently, glancing at the list each time.

Same result. Radically different amount of walking.

```
THE CHEF ANALOGY

IN (subquery):
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│  For employee #1:                                              │
│    → Walk to pantry (departments table)                        │
│    → Check if dept is in 'Asia' region                         │
│    → Walk back                                                 │
│    → Decide: include or skip                                   │
│                                                                │
│  For employee #2:                                              │
│    → Walk to pantry AGAIN                                      │
│    → Check AGAIN (same pantry, same question)                  │
│    → Walk back AGAIN                                           │
│    → Decide                                                    │
│                                                                │
│  (500,000 pantry trips total)                                  │
└────────────────────────────────────────────────────────────────┘

JOIN (Hash Join):
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│  Once, at the start:                                           │
│    → Walk to pantry (departments table)                        │
│    → Write down all Asian dept IDs on a notepad               │
│    → Pin the notepad to the counter                            │
│                                                                │
│  For employee #1:  Glance at notepad → decide                  │
│  For employee #2:  Glance at notepad → decide                  │
│  ...                                                           │
│  For employee #500,000: Glance at notepad → decide             │
│                                                                │
│  (1 pantry trip total)                                         │
└────────────────────────────────────────────────────────────────┘
```

This mental model generalizes beautifully. Whenever you see a computation being repeated unnecessarily — in SQL, in application code, anywhere — ask yourself: "Can I compute this once and reuse the result?" That instinct, applied consistently, is one of the most powerful performance optimization tools you have.

## Summary

This case study walks through one of the most instructive performance problems you will encounter as a backend engineer working with relational databases. An HR report that filtered employees by their department's region used an `IN (subquery)` pattern that the query planner executed as a correlated nested loop — re-running the inner query five hundred thousand times, once per employee row. The result was an eighteen-second execution time on a half-million-row table.

The fix was a single, clean rewrite: replacing the `IN (subquery)` with an explicit `JOIN`. This gave the planner the information it needed to choose a Hash Join strategy — building a tiny in-memory hash table from the departments data once and then probing it once per employee in constant time. The execution time dropped from eighteen thousand milliseconds to forty milliseconds — a four-hundred-and-fifty-times improvement with no schema changes, no index additions, and no hardware upgrades.

The deeper truth behind this case study is that SQL's declarative nature means the planner must infer how to execute your query from the shape of the query text, and sometimes the shape you choose inadvertently leads it toward an inefficient strategy. Writing `JOIN` instead of `IN (subquery)` is not merely a stylistic preference — it is a concrete signal to the planner that can unlock dramatically more efficient execution algorithms. `EXPLAIN ANALYZE` is the tool that makes all of this visible, and developing the habit of using it regularly is one of the highest-leverage investments you can make as an engineer who works with databases.
