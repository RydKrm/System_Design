# The Planner That Knew Too Much: How Forcing CTE Materialization Turned a 45-Second Query into a 200ms One

> _"A query planner that can see inside your carefully designed CTEs is like a clever but overconfident assistant who rearranges all your organised desk drawers because they think they have a better system. They may be intelligent. They are not always right."_

---

## Setting the Scene

Imagine you are a senior data engineer at a financial services company. The analytics team has built a complex reporting query over several weeks — a query designed to produce a daily reconciliation report that combines customer transaction data, account balance snapshots, product fee schedules, and regional compliance thresholds into a single coherent summary. The query is genuinely complex, involving five Common Table Expressions (CTEs) stacked in sequence, each building on the result of the previous one to progressively narrow and enrich the dataset before the final output is produced.

The query was designed carefully. Each CTE was crafted to do a specific, well-scoped job — filter a large transaction table down to relevant records, join it against account data, apply fee calculations, enforce compliance filters, and finally format the output. The engineers who wrote it thought of CTEs as a way to break a complex problem into manageable, sequential steps. The logic was clear, readable, and maintainable.

For several months, the query ran acceptably — about eight seconds, which was considered borderline but tolerable for a report that ran once per day. Then the company upgraded the database from PostgreSQL 11 to PostgreSQL 12, applied a routine `VACUUM ANALYZE` to refresh statistics, and something unexpected happened. The next morning, the reconciliation report took forty-five seconds. The following morning, fifty-three seconds. The morning after that, it timed out entirely.

The infrastructure team immediately suspected a hardware problem. They checked disk I/O, checked memory, checked CPU. Everything was normal. The database was healthy. The data volume had not changed significantly. The query itself had not been modified. And yet it had gone from eight seconds to timing out overnight.

Your senior engineer looks at this situation and says something that will stick with you: _"The database upgrade didn't break the query. It made the planner smarter — and the planner's new intelligence made a catastrophically bad decision. We need to take some of that intelligence away."_

---

## Understanding CTEs: What They Are and What They Are Supposed to Do

Before we can understand the problem, we need to understand what a CTE actually is and what guarantee — or lack of guarantee — it provides about how the database executes it.

A Common Table Expression, written using the `WITH` keyword, is a way to define a named, temporary result set that can be referenced later in the same query. You can think of it as giving a name to a subquery, allowing you to write complex logic in clearly labelled steps rather than nesting subqueries inside subqueries inside subqueries until the code becomes unreadable.

The reconciliation query looks something like this (simplified to capture the essential structure):

```sql
WITH
recent_transactions AS (
    SELECT t.account_id, t.amount, t.transaction_date, t.product_id
    FROM transactions t
    WHERE t.transaction_date >= CURRENT_DATE - INTERVAL '90 days'
      AND t.status = 'SETTLED'
),
account_details AS (
    SELECT rt.account_id, rt.amount, rt.transaction_date, rt.product_id,
           a.customer_id, a.account_type, a.region
    FROM recent_transactions rt
    JOIN accounts a ON rt.account_id = a.id
),
fee_applied AS (
    SELECT ad.customer_id, ad.amount, ad.transaction_date, ad.account_type,
           ad.region,
           ad.amount * f.rate AS fee_amount
    FROM account_details ad
    JOIN fee_schedules f ON ad.product_id = f.product_id
                        AND ad.account_type = f.account_type
),
compliance_filtered AS (
    SELECT fa.customer_id, fa.amount, fa.fee_amount,
           fa.transaction_date, fa.region
    FROM fee_applied fa
    JOIN compliance_thresholds ct ON fa.region = ct.region
    WHERE fa.amount > ct.minimum_reportable_amount
),
final_summary AS (
    SELECT customer_id,
           COUNT(*)          AS transaction_count,
           SUM(amount)       AS total_amount,
           SUM(fee_amount)   AS total_fees,
           transaction_date
    FROM compliance_filtered
    GROUP BY customer_id, transaction_date
)
SELECT *
FROM final_summary
ORDER BY customer_id, transaction_date;
```

Reading this query, you can see the intended data flow clearly. `recent_transactions` filters the enormous transactions table down to only the last ninety days of settled records — perhaps from two billion rows down to five million. `account_details` enriches those records with account information. `fee_applied` calculates the applicable fee for each transaction. `compliance_filtered` applies regulatory thresholds to keep only reportable transactions. `final_summary` aggregates the result into a per-customer, per-day summary.

Each step reduces and enriches the dataset in sequence. The engineers designed it this way deliberately: by filtering the transactions table down to five million rows in the very first CTE before any joins are performed, the subsequent joins operate on a small, manageable dataset rather than the full two-billion-row table.

## The PostgreSQL 12 Change That Started Everything

In PostgreSQL 11 and earlier versions, CTEs were **always materialized**. This is a technical term meaning the database always executed the CTE's query completely, stored the result in a temporary in-memory structure (or on disk if the result was large), and then used that stored result whenever the CTE was referenced later in the query. The CTE result was opaque to the outer query — the planner had to treat it as a pre-computed, fixed table and plan around it accordingly.

This had a very important consequence: the planner could not "see inside" a CTE to reorganize its execution relative to other parts of the query. Each CTE was a black box, a concrete intermediate result, a planning fence. The engineers who wrote the reconciliation query were relying on this behaviour — they knew that by filtering transactions down to five million rows in the first CTE, all subsequent joins would operate on five million rows rather than two billion. The sequential, step-by-step execution they intended was guaranteed by the always-materialized semantics.

PostgreSQL 12 changed this. In a well-intentioned attempt to improve performance, the PostgreSQL team made CTEs **inline by default**. Inlining means the planner no longer treats a CTE as a black box — instead, it expands the CTE's definition in place, as if you had written the CTE's body directly as a subquery wherever it is referenced. After inlining, the planner can see the entire query as one large expression and apply its global join reordering optimisations across all of it.

```
CTE INLINING: What PostgreSQL 12+ does by default

What you wrote (with CTEs as separate steps):
  recent_transactions → account_details → fee_applied → compliance_filtered → final_summary

What the planner sees after inlining (one giant expression):
  SELECT customer_id, COUNT(*), SUM(amount), SUM(amount * rate)
  FROM transactions t
  JOIN accounts a ON t.account_id = a.id
  JOIN fee_schedules f ON t.product_id = f.product_id AND a.account_type = f.account_type
  JOIN compliance_thresholds ct ON a.region = ct.region
  WHERE t.transaction_date >= CURRENT_DATE - INTERVAL '90 days'
    AND t.status = 'SETTLED'
    AND t.amount > ct.minimum_reportable_amount
  GROUP BY ...

  The planner can now reorder these four joins in any order it chooses.
  It has full visibility and full freedom.
  This freedom is the source of the disaster.
```

On the surface, giving the planner more visibility seems like it should only help. If the planner can see the entire computation, it can choose the globally optimal join order, right? In theory, yes. In practice, the planner's ability to find the globally optimal join order depends entirely on the accuracy of its **row count estimates**, and those estimates are based on table statistics that are often imperfect, especially for complex multi-join queries.

## Why the Planner Chose a Catastrophic Plan

When the planner sees the inlined version of the reconciliation query — four tables being joined with several filter conditions — it must decide the order in which to perform the joins. Join order matters enormously because the output of each join becomes the input to the next, and the size of these intermediate results directly affects how much work subsequent steps must do.

The planner estimated, based on its statistics, that the `compliance_thresholds` table join would be highly selective — that it would dramatically reduce the number of rows before any other joins were performed. This seemed like a clever optimisation: do the most selective filter first, then join the smaller result against the large tables.

The fatal flaw was that the statistics were wrong. The `compliance_thresholds` table had very low cardinality — only a small number of distinct regions — and the planner's estimate of how many transactions would survive the compliance filter was wildly optimistic. The planner thought perhaps five thousand rows would come out of that join. In reality, hundreds of thousands of rows survived it.

Based on its (incorrect) estimate of five thousand rows, the planner chose a **Nested Loop Join** between `transactions` (two billion rows) and the compliance-filtered result. A Nested Loop Join works by taking each row from one input and scanning the other input looking for matches. When one side is small, this is very efficient. When both sides are large, it is catastrophic. The planner thought it was doing a nested loop between two billion rows and five thousand rows — expensive but manageable. What it actually executed was a nested loop between two billion rows and several hundred thousand rows, producing a computation cost in the trillions of row comparisons.

```
THE CATASTROPHIC JOIN ORDER CHOSEN BY THE PLANNER

What the planner thought it was doing:
  ┌───────────────────────────────────────────────────────────────┐
  │  Step 1: Scan compliance_thresholds (tiny, ~50 rows)          │
  │  Step 2: Nested Loop with transactions                        │
  │          → Planner estimates ~5,000 surviving rows            │
  │          → Actual surviving rows: ~400,000                    │
  │  Step 3: Join ~5,000 rows with accounts (planner thinks)      │
  │          → Actual: Join ~400,000 rows with accounts           │
  │  Step 4: Join result with fee_schedules                       │
  └───────────────────────────────────────────────────────────────┘
  Planner estimated cost: manageable
  Actual cost: catastrophic (wrong estimate at step 2 cascades)

What the ENGINEERS intended (with CTEs as fences):
  ┌───────────────────────────────────────────────────────────────┐
  │  CTE 1: Filter transactions → 5,000,000 rows (90 days only)   │
  │         [Materialized — planner cannot reorder this]          │
  │  CTE 2: Join 5M rows with accounts                            │
  │         [Planner works with known 5M-row input]               │
  │  CTE 3: Join result with fee_schedules                        │
  │  CTE 4: Apply compliance filter → smaller result              │
  │  CTE 5: Aggregate                                             │
  └───────────────────────────────────────────────────────────────┘
  Execution is predictable. First CTE does the heavy filtering.
  All subsequent joins are on a manageable intermediate result.
```

The engineers' original design was correct. Filter first, join later on small data. But when the planner inlined the CTEs, it took away the sequential guarantee they were relying on and substituted its own (flawed) global join ordering — an ordering that turned a well-designed query into a combinatorial disaster.

The critical evidence is `loops=48` on the transaction scan and `loops=19200000` on the accounts index scan. Because `compliance_thresholds` has 48 rows, the planner ran the nested loop against transactions 48 times — performing 48 full or near-full scans of a two-billion-row table. Each of those 48 scans itself drove 400,000 inner iterations against the accounts index — hence 48 × 400,000 = 19,200,000 total accounts index lookups.

The `loops` numbers are the fingerprint of a nested loop join gone wrong. When you see large `loops` values on expensive scan nodes in `EXPLAIN ANALYZE`, you are almost certainly looking at a nested loop join where one or both sides are far larger than the planner expected.

## The Solution: Forcing CTE Materialization

The fix is to explicitly tell PostgreSQL to materialize the CTEs — to treat them as concrete intermediate results rather than inlineable expressions. In PostgreSQL 12 and later, you do this by adding the `MATERIALIZED` keyword to the CTE definition:

```sql
WITH
recent_transactions AS MATERIALIZED (
    SELECT t.account_id, t.amount, t.transaction_date, t.product_id
    FROM transactions t
    WHERE t.transaction_date >= CURRENT_DATE - INTERVAL '90 days'
      AND t.status = 'SETTLED'
),
account_details AS MATERIALIZED (
    SELECT rt.account_id, rt.amount, rt.transaction_date, rt.product_id,
           a.customer_id, a.account_type, a.region
    FROM recent_transactions rt
    JOIN accounts a ON rt.account_id = a.id
),
fee_applied AS MATERIALIZED (
    SELECT ad.customer_id, ad.amount, ad.transaction_date, ad.account_type,
           ad.region,
           ad.amount * f.rate AS fee_amount
    FROM account_details ad
    JOIN fee_schedules f ON ad.product_id = f.product_id
                        AND ad.account_type = f.account_type
),
compliance_filtered AS MATERIALIZED (
    SELECT fa.customer_id, fa.amount, fa.fee_amount,
           fa.transaction_date, fa.region
    FROM fee_applied fa
    JOIN compliance_thresholds ct ON fa.region = ct.region
    WHERE fa.amount > ct.minimum_reportable_amount
),
final_summary AS MATERIALIZED (
    SELECT customer_id,
           COUNT(*)          AS transaction_count,
           SUM(amount)       AS total_amount,
           SUM(fee_amount)   AS total_fees,
           transaction_date
    FROM compliance_filtered
    GROUP BY customer_id, transaction_date
)
SELECT *
FROM final_summary
ORDER BY customer_id, transaction_date;
```

The only change is the addition of `AS MATERIALIZED` after each CTE name. These two words restore the planning fence behaviour that PostgreSQL 11 provided by default. The planner can no longer inline the CTEs and reorganize the entire computation globally. It must execute each CTE in sequence, store its result, and then use that stored result as input to the next CTE.

## What MATERIALIZED Actually Does: The Planning Fence

The term "planning fence" is a useful mental model for what `MATERIALIZED` does. Think of the planner's job as trying to find the optimal route through a complex city. Without materialization, the planner can see all roads, choose any route, and optimize globally — but if its map is inaccurate (statistics are wrong), it might choose a route that looks good on paper but is actually stuck in traffic.

With `MATERIALIZED`, you are placing toll booths at certain checkpoints in the city. The planner must pass through each checkpoint in order. It can optimize within each segment between checkpoints, but it cannot choose a route that bypasses the checkpoints or crosses them in a different sequence. The toll booths are planning fences — they divide the query into mandatory sequential steps.

```
THE PLANNING FENCE CONCEPT

WITHOUT MATERIALIZED (inlining — planner has full freedom):

  transactions ──┐
  accounts     ──┤ ← Planner sees ALL of these at once
  fee_schedules──┤    and can join them in ANY order
  comp_thresholds┘    using its (potentially wrong) estimates

  Result: Planner chooses catastrophic order based on bad estimates.

WITH MATERIALIZED (fenced — planner has sequential structure):

  transactions         accounts      fee_schedules  comp_thresholds
       │                  │               │               │
       ▼                  │               │               │
  ┌────────────┐          │               │               │
  │ CTE 1      │          │               │               │
  │ (5M rows)  │◄─────────┘               │               │
  └─────┬──────┘  ← Planner optimizes     │               │
        │           only this join        │               │
        ▼                                 │               │
  ┌────────────┐                          │               │
  │ CTE 2      │◄─────────────────────────┘               │
  │ (5M rows)  │  ← Planner optimizes only this join      │
  └─────┬──────┘                                          │
        ▼                                                 │
  ┌────────────┐                                          │
  │ CTE 3      │◄─────────────────────────────────────────┘
  │ (filtered) │  ← Planner optimizes only this join
  └─────┬──────┘
        ▼
  ┌────────────┐
  │ CTE 4      │
  │ (summary)  │
  └─────┬──────┘
        ▼
      Result

  Each CTE is executed completely before the next begins.
  The planner only optimizes within each fence segment.
  The engineers' intended data flow is guaranteed.
```

Within each fenced segment, the planner is still free to choose the best execution strategy — it can use hash joins, index scans, or whatever is most appropriate for that isolated join. What it cannot do is decide that it would be smarter to join `transactions` and `compliance_thresholds` directly before the 90-day filter is applied. The materialization fence prevents that catastrophic reordering.

## The Crucial Mechanics: Why Materialization Helps with Bad Estimates

The reason materialization restores correct behaviour is not merely about controlling execution order in the abstract — it is specifically about the planner's **cardinality estimation** (its estimate of how many rows flow through each step).

When a CTE is materialized, the database executes it completely, counts the actual rows in the result, and stores that count in the materialized table's metadata. When the next CTE or query step references the materialized result, the planner has an **exact row count** — not a statistical estimate — to work with. This exact count allows the planner to make much more accurate decisions about how to execute the subsequent join.

With inlining, the planner must estimate how many rows the CTE would produce based on table statistics and selectivity models. These estimates can be wildly incorrect, especially for queries with multiple filter conditions applied simultaneously to large tables with correlated columns. The estimate feeds into the join cost model, and a bad estimate propagates — once the planner thinks one intermediate result is much smaller than it actually is, every subsequent decision is made on a false foundation, and the errors compound.

```
HOW BAD CARDINALITY ESTIMATES COMPOUND

Step 1: Estimate transactions after 90-day filter
  Planner estimates: 500,000 rows
  Reality:         5,000,000 rows
  Error factor:    10×

Step 2: Estimate after joining with compliance_thresholds
  Planner uses 500,000 as input → estimates 5,000 rows survive
  Reality uses 5,000,000 as input → 400,000 rows survive
  Error factor:    80× (errors compound!)

Step 3: Choose join algorithm based on estimated 5,000 rows
  Planner picks Nested Loop (correct for 5,000 rows)
  Reality: Nested Loop runs against 400,000 rows
  Result: catastrophic

With MATERIALIZED after Step 1:
  Planner executes CTE and stores ACTUAL 5,000,000 rows
  Step 2 planning starts with exact count: 5,000,000
  Estimate for Step 2 is now accurate → correct join chosen
  No compounding error cascade.
```

This is the deepest reason why materialization fixes the problem. It breaks the chain of compounding estimation errors by inserting exact, empirically measured row counts at each CTE boundary.

## The History of CTE Materialization: Understanding the Change

To fully appreciate why this situation arose with the PostgreSQL 12 upgrade, it helps to understand the history and the reasoning behind the change.

In PostgreSQL 11 and earlier, CTEs were always materialized. This was actually a performance limitation in many cases — if a CTE was referenced only once in a simple query, materializing it meant creating an unnecessary temporary structure that added overhead rather than saving work. Developers and database administrators frequently complained that CTEs were "optimization fences" that prevented the planner from making beneficial optimisations, particularly when a CTE was used for organizational clarity rather than as a performance tool.

PostgreSQL 12 responded to this feedback by making inlining the default for single-reference CTEs that the planner determined could be safely inlined without changing semantics. The feature was genuine progress — for many simpler queries, it eliminated unnecessary materialization overhead and allowed better global optimisation. But it had the unintended consequence of breaking queries that were specifically relying on the materialization fence behaviour to control join ordering in complex, multi-CTE analytics queries.

The `MATERIALIZED` keyword was added simultaneously as the explicit opt-in for the old behaviour, and `NOT MATERIALIZED` was added as the explicit opt-in for the new inlining behaviour. This gives developers full control:

```
CTE MATERIALIZATION CONTROL IN POSTGRESQL 12+

WITH my_cte AS (SELECT ...)
← Default: planner decides (usually inlines for single-reference CTEs)

WITH my_cte AS MATERIALIZED (SELECT ...)
← Explicit: always materialize, create concrete intermediate table
← Use when: you need a planning fence, or the CTE is referenced
             multiple times and you want the result computed once

WITH my_cte AS NOT MATERIALIZED (SELECT ...)
← Explicit: always inline, treat as a subquery
← Use when: materialization would add overhead and inlining
             allows better index push-down or predicate pushdown
```

Understanding which keyword to use in which situation is the practical skill this case study is teaching.

## When to Use MATERIALIZED and When to Avoid It

`MATERIALIZED` is a powerful tool, but like all tools, it should be applied thoughtfully rather than universally. Using it inappropriately can actually hurt performance.

The cases where `MATERIALIZED` is beneficial are those where you have a CTE that performs meaningful work — significant filtering, joins, aggregation — that reduces a large dataset to a substantially smaller one, and where you have specific knowledge that the sequential execution of this reduction before subsequent joins is the correct approach. It is also valuable when you observe (through `EXPLAIN ANALYZE`) that the planner is choosing catastrophically wrong join orders due to bad cardinality estimates, and the materialization boundary gives the planner accurate intermediate row counts to reason from. It is particularly important when a CTE is referenced **multiple times** in the same query — without materialization, the CTE would be re-evaluated once for each reference; with materialization, it is computed once and the result is reused.

The cases where `MATERIALIZED` is harmful are those where the CTE is simple — perhaps just a filter on a single column — and the planner could use index push-down to make the query dramatically faster if it could see inside the CTE. For example, if a CTE does `SELECT * FROM products WHERE category = 'Electronics'`, and the outer query then filters on `price > 100`, an inlined version allows the planner to push both filters down to a single index scan. A materialized version forces the CTE to execute first (producing all electronics regardless of price), then applies the price filter afterward — potentially reading far more rows than necessary.

```
WHEN TO USE MATERIALIZED vs NOT MATERIALIZED

  Use MATERIALIZED when:
  ┌─────────────────────────────────────────────────────────┐
  │ ✓ The CTE does heavy filtering that reduces data a lot  │
  │ ✓ You observe bad join plans (large loops in EXPLAIN)   │
  │ ✓ The CTE is referenced multiple times (avoids repeat)  │
  │ ✓ Statistics are stale and estimates are unreliable     │
  │ ✓ You know the sequential order is the right order      │
  └─────────────────────────────────────────────────────────┘

  Avoid MATERIALIZED when:
  ┌─────────────────────────────────────────────────────────┐
  │ ✗ The CTE is simple (single filter, single table)       │
  │ ✗ You want the planner to push predicates inside it     │
  │ ✗ The CTE produces a large result that might not fit    │
  │   in memory (forces disk spill)                         │
  │ ✗ The CTE is referenced only once in a simple join      │
  │   (inlining allows better index use)                    │
  └─────────────────────────────────────────────────────────┘

  Golden rule: measure with EXPLAIN ANALYZE before and after.
  Never add MATERIALIZED blindly — verify it helps.
```

## The Broader Lesson: When You Know More Than the Planner

This case study exposes a nuanced but important truth about the relationship between a SQL developer and a database query planner. The planner is extraordinarily powerful and gets the right answer most of the time. But it operates on statistics and heuristics — and when those statistics are imperfect, or when the data has unusual distributions, or when the combination of multiple join conditions interacts in ways the planner's cost model does not fully account for, the planner can make decisions that are dramatically wrong.

As an engineer, you sometimes have knowledge that the planner does not — and cannot — have. You know that the 90-day filter on the transactions table dramatically reduces the dataset. You know the intended sequential data flow of your multi-CTE query. You know that the compliance filter, despite having few distinct values, is applied at a specific stage for a good reason. The planner knows none of this semantic intent; it only knows table sizes and column statistics.

The `MATERIALIZED` keyword is the mechanism by which you communicate some of that semantic knowledge to the planner. It is you saying: "I know this step should happen first. I know this intermediate result is the right foundation for subsequent joins. Trust my ordering, not your estimates."

This is not an admission of defeat or a workaround for a broken planner. It is the appropriate exercise of engineering judgment in a situation where the engineer's domain knowledge exceeds the planner's statistical knowledge. The planner is a very powerful assistant, but the best engineers know when to delegate to it freely and when to provide it with explicit guidance.

## The Result: 45,000ms → 200ms

The addition of `AS MATERIALIZED` to five CTE definitions transformed the query's behaviour completely. The forty-five-second reconciliation report became a 200-millisecond one. The timeouts ceased. The analytics team got their morning report reliably, every morning, before the executive meeting.

```
BEFORE — CTEs inlined, planner chose catastrophic join order:
  Nested loop iterations: ~19,200,000
  Execution time:          44,987ms (45 seconds)
  Daily reliability:       Sometimes times out

AFTER — CTEs materialized, sequential execution enforced:
  Each CTE executed: exactly once, in order
  Execution time:    199ms
  Daily reliability: Always completes

Improvement: 44,987ms ÷ 199ms = 226× faster

The only change: adding "AS MATERIALIZED" to 5 CTE definitions.
Total characters added: approximately 80.
Performance gain: 226×.
```

This is one of the highest return-on-investment fixes in all of database performance engineering — a handful of words in the SQL text, producing a two-hundred-fold improvement in execution time, with no schema changes, no index additions, no hardware changes, and no application code modifications.

## Summary

This case study examines a subtle but devastating performance regression caused by a PostgreSQL version upgrade. A carefully designed five-CTE analytics query that relied on sequential CTE execution as a planning fence stopped working correctly after upgrading to PostgreSQL 12, which introduced CTE inlining as the default behaviour. With CTEs inlined, the query planner gained full visibility into the entire query and chose a globally reorganised join order based on its (incorrect) cardinality estimates. The result was a catastrophic nested loop join that scanned a two-billion-row transactions table dozens of times, turning a tolerable query into a forty-five-second ordeal that frequently timed out.

The fix was to add the `MATERIALIZED` keyword to each CTE definition, restoring the pre-12 behaviour of treating each CTE as a concrete intermediate result rather than an inlineable expression. Materialization broke the chain of compounding cardinality estimation errors by providing exact row counts at each CTE boundary, prevented the planner from reordering joins across those boundaries, and enforced the sequential data flow that the engineers had deliberately designed to filter the large transactions table before any joins were performed. Execution time dropped from 44,987 milliseconds to 199 milliseconds — a 226-fold improvement.

The lesson to carry into your career is that CTEs with `MATERIALIZED` are planning fences. They are the appropriate tool when you have domain knowledge about the correct execution order that the planner cannot derive from its statistics alone. Use them when you observe nested loop joins with large loop counts in `EXPLAIN ANALYZE`, when CTEs are referenced multiple times, and when sequential filtering is essential to keeping intermediate result sizes manageable. But verify with `EXPLAIN ANALYZE` before and after — materialization is a surgical tool, and understanding when to apply it versus when to let the planner work freely is one of the marks of a mature database engineer.
