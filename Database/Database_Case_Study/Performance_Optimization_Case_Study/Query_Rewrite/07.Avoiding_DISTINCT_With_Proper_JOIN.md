# The Query That Built a Mountain to Climb Over: How Replacing JOIN + DISTINCT with EXISTS Achieved a 240× Speedup

> _"The most expensive intermediate result a database can produce is one you never needed in the first place. JOIN + DISTINCT first creates every possible match between two tables, then discards the duplicates. EXISTS never creates the matches at all — it simply asks whether any exist."_

---

## Setting the Scene

You are a backend engineer at a mid-sized retail company. The business has built a customer reporting dashboard that the sales and marketing teams use daily. One of the most fundamental reports on this dashboard asks a deceptively simple question: which customers have placed at least one order? This is a customer segmentation report — it separates "active customers" from "registered but never purchased" users, and it feeds into marketing campaigns, loyalty programme enrollments, and sales pipeline analysis.

The `customers` table holds two million registered accounts. The `orders` table holds forty million order records. A customer might have placed one order, or ten, or five hundred — the distribution is wide. The marketing team runs this report several times per day, and for several months it has been taking twelve seconds to load. Twelve seconds for what appears to be a simple filtering question has caused no end of frustration — the marketing manager has taken to calling it "the coffee break query."

The engineer who originally wrote the query joins your team as you dig into the performance logs. When you pull up the SQL, it looks like this:

```sql
SELECT DISTINCT c.id, c.name
FROM customers c
JOIN orders o ON c.id = o.customer_id;
```

The query is logical at first glance. You join customers with orders — if a customer has placed an order, they will appear in the join result. You then apply `DISTINCT` to remove the duplicates, because a customer who has placed fifty orders will appear fifty times in the raw join result. Simple, readable, and apparently correct. And yet it is running for twelve seconds and making the marketing team miserable.

Your senior engineer reads it, exhales slowly, and says: _"This query is building a forty-million-row table just to answer a yes-or-no question for each customer. We need to change the question we are asking the database, not just the answer it needs to return."_

---

## Understanding What JOIN Actually Does

To understand why this query is slow, you need to think carefully about what a `JOIN` operation produces — not just what it means semantically, but what it physically creates inside the database engine as it executes.

A `JOIN` between two tables produces a result set that contains one row for every matching pair of rows across the two tables. When you join `customers` and `orders` on `c.id = o.customer_id`, the database looks at each customer and finds all orders belonging to that customer. For each (customer, order) pair where the IDs match, one row appears in the join result.

Consider a customer named Alice who has placed two hundred orders over five years of loyal shopping. In the join result, Alice appears two hundred times — once paired with each of her orders. Another customer, Bob, who has placed three orders, appears three times. A customer who placed one order appears once. A customer who has never ordered does not appear at all, because there is no matching row in the orders table.

When you add up all these pairs across two million customers and forty million orders, the raw join result contains exactly forty million rows — one for every row in the orders table. The join result is as large as the orders table itself, because every order row is matched to exactly one customer row.

```
WHAT JOIN PRODUCES — Before DISTINCT is applied

customers table (2M rows):  orders table (40M rows):
  id=1, name='Alice'          id=101, customer_id=1, amount=$50
  id=2, name='Bob'            id=102, customer_id=1, amount=$30
  id=3, name='Carol'          id=103, customer_id=2, amount=$80
  ...                         id=104, customer_id=1, amount=$15
                              id=105, customer_id=3, amount=$40
                              ...

JOIN result (40M rows — one per order):
  ┌──────────────────────────────────────────────────────────┐
  │ c.id=1, c.name='Alice',  o.id=101, o.amount=$50         │
  │ c.id=1, c.name='Alice',  o.id=102, o.amount=$30         │
  │ c.id=1, c.name='Alice',  o.id=104, o.amount=$15         │
  │  ↑ Alice appears 3 times (she has 3 orders shown here)  │
  │                                                          │
  │ c.id=2, c.name='Bob',    o.id=103, o.amount=$80         │
  │  ↑ Bob appears once (he has 1 order shown here)          │
  │                                                          │
  │ c.id=3, c.name='Carol',  o.id=105, o.amount=$40         │
  │  ↑ Carol appears once                                    │
  │                                                          │
  │ ... (40 million rows total)                              │
  └──────────────────────────────────────────────────────────┘

After DISTINCT (keeping only unique c.id, c.name pairs):
  c.id=1, c.name='Alice'   ← deduplicated from 3 copies
  c.id=2, c.name='Bob'     ← was already unique
  c.id=3, c.name='Carol'   ← was already unique
  ...
  Result: ~1.8M rows (customers who have at least one order)
```

The join produces forty million rows. Then `DISTINCT` must sort or hash all forty million rows to identify duplicates and eliminate them, producing approximately 1.8 million unique customers. The database has built a forty-million-row intermediate structure, only to immediately throw away 38.2 million rows of it. The ratio of rows built to rows kept is roughly twenty-two to one.

## How DISTINCT Is Implemented: The Sort + Unique Operation

To understand the full cost of `DISTINCT`, you need to understand how the database engine actually implements it. `DISTINCT` is not a free operation — it is a concrete algorithmic step that requires significant work.

The most common implementation of `DISTINCT` is called **Sort + Unique**. The database takes the entire join result — all forty million rows — and sorts it by the `DISTINCT` columns (`c.id` and `c.name` in our case). After sorting, identical rows are adjacent, and the database can eliminate duplicates by simply comparing each row to the one immediately preceding it and skipping it if they are equal. The sorted, deduplicated result is then passed to the output.

Sorting forty million rows requires substantial memory. PostgreSQL allocates a working memory buffer for sort operations, controlled by the `work_mem` setting. If the intermediate data fits in this buffer, the sort happens entirely in RAM — fast but memory-intensive. If the data does not fit in `work_mem` — which is very likely for forty million rows of customer and order data — PostgreSQL must spill the sort to disk, writing temporary files, reading them back, and merging them. This disk-based external sort is orders of magnitude slower than an in-memory sort.

An alternative implementation of `DISTINCT` uses a **hash aggregate**: the database builds a hash table where each unique `(c.id, c.name)` combination is inserted once and duplicates are discarded. This avoids the sort but still requires materializing the entire join result and processing every one of the forty million rows through the hash table.

```
HOW DISTINCT IS EXECUTED (Sort + Unique approach)

Step 1: Execute the JOIN
  customers (2M) ⋈ orders (40M) = 40,000,000 rows produced
  Memory required: potentially gigabytes

Step 2: Sort all 40M rows by (c.id, c.name)
  ┌────────────────────────────────────────────────────────┐
  │  If data > work_mem: spill to disk                     │
  │  Write 40M rows to temp files                          │
  │  Sort each chunk                                       │
  │  Merge sorted chunks back                              │
  │  This alone can take 8–10 seconds on spinning disk     │
  └────────────────────────────────────────────────────────┘

Step 3: Walk sorted result, emit unique rows
  c.id=1 'Alice' ← emit
  c.id=1 'Alice' ← skip (duplicate)
  c.id=1 'Alice' ← skip (duplicate)
  ... (skip all 199 duplicates for Alice's 200 orders)
  c.id=2 'Bob'   ← emit
  ...

  Total rows processed: 40,000,000
  Total rows emitted:    ~1,800,000
  Rows thrown away:      ~38,200,000 (95.5% of work was wasted)
```

The twelve-second execution time is dominated by this sorting and deduplication of forty million rows — rows that, from the perspective of the question being asked, were never needed in the first place. The question was "which customers have at least one order?" The answer only requires knowing, for each customer, whether any matching order exists. It never required knowing all matching orders, yet the query forced the database to find and process all of them.

## The Root Cause: A Semantic Mismatch

Just as with the `COUNT(*)` vs `EXISTS` case study, the core problem here is a mismatch between the question being asked and the information the query is requesting from the database.

The question is: "which customers have placed at least one order?" This is, at its heart, an existence question about each customer. For every customer, you want to know: does a row exist in the `orders` table where `customer_id` matches this customer's `id`? The answer for each customer is a boolean — yes, they have ordered; or no, they have not. You want the list of customers for whom the answer is yes.

The `JOIN + DISTINCT` query, however, asks an entirely different question internally: "produce every (customer, order) pair that matches, and then tell me the unique customers in that result." It answers the existence question by first fully enumerating all evidence of existence — all matching orders for every customer — and then collapsing that enumeration back down to a unique list. It takes a long route to a simple destination.

```
THE SEMANTIC MISMATCH

What you want to know (for each customer):
  ┌──────────────────────────────────────────────────────────┐
  │  Customer Alice (id=1): Does any order have customer_id=1?│
  │  Answer: YES → include Alice                             │
  │                                                          │
  │  Customer Dave (id=7): Does any order have customer_id=7? │
  │  Answer: NO  → exclude Dave                              │
  └──────────────────────────────────────────────────────────┘
  Information needed per customer: 1 bit (yes/no)

What JOIN produces per customer (before DISTINCT):
  ┌──────────────────────────────────────────────────────────┐
  │  Customer Alice: order #101, order #102, order #104,     │
  │                  order #198, order #234, ... (200 rows)  │
  │                                                          │
  │  Customer Dave: (no rows)                                │
  └──────────────────────────────────────────────────────────┘
  Information produced per customer: full list of all orders
  (then immediately discarded by DISTINCT)
```

This is the classic case of producing far more information than the question demands, paying the full cost of producing it, and then immediately throwing most of it away.

## The Solution: EXISTS as a Proper Existence Check

The rewritten query uses `EXISTS` — the operator specifically designed for existence questions:

```sql
SELECT c.id, c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

This query reads as naturally as English: "give me each customer for whom there exists at least one order." And unlike the `JOIN + DISTINCT` version, the database executes it in a way that precisely matches this question's information requirement.

The key word that unlocks the efficiency is `EXISTS`. As explored in the earlier case study on `EXISTS` vs `COUNT(*)`, the `EXISTS` operator returns `true` the instant it finds a single matching row and stops searching. It does not enumerate all matching rows. It does not count them. It does not build a list of them. It finds one, confirms existence, and immediately returns `true` to the outer query. The outer query then knows this customer should be included in the result, and moves on to the next customer.

For a customer like Alice, who has two hundred orders, `EXISTS` finds the very first order in the index scan and stops. It reads one row out of Alice's two hundred and declares "yes, Alice has ordered." The other one hundred and ninety-nine rows are never touched. For a customer who has never ordered, `EXISTS` scans the relevant portion of the orders index, finds nothing, and returns `false` — the customer is excluded.

The database's execution strategy changes from **Join + Sort + Deduplicate** to **customer-by-customer existence check**, which in database terminology is called a **Semi-Join**.

---

## The Semi-Join: What the Planner Does With EXISTS

When the query planner sees `EXISTS (SELECT ... WHERE o.customer_id = c.id)`, it recognises this pattern as a **semi-join** — a join that returns rows from one table based on whether a matching row exists in another table, without producing the matching rows themselves. Semi-joins are a fundamental relational algebra concept, and PostgreSQL's planner has several strategies to implement them.

The most common strategy for this query is a **Hash Semi-Join**. Instead of building a full hash table of all orders (as the original Hash Join did), the planner builds a hash table of order `customer_id` values — just the IDs, no other order data needed. Then it scans the customers table and for each customer, checks whether their `id` appears in the hash table. The moment a match is found, the customer is emitted to the output and the search for that customer's orders stops.

Alternatively, if an index exists on `orders.customer_id`, the planner might choose an **Index-based nested loop semi-join** — for each customer, it performs an index lookup into the orders table, checking whether any order exists for that customer's ID. Because of the EXISTS semantics, the index lookup stops at the first match.

```sql
EXPLAIN ANALYZE
SELECT c.id, c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

```
Hash Semi Join  (cost=924512.34..975234.12 rows=1800000 width=22)
                (actual time=312.441..748.334 rows=1823441 loops=1)
  Hash Cond: (c.id = o.customer_id)
  ->  Seq Scan on customers c
      (actual time=0.021..89.334 rows=2000000 loops=1)
  ->  Hash  (cost=512341.00..512341.00 rows=40000000 width=8)
            (actual time=298.112..298.112 rows=40000000 loops=1)
        Buckets: 4194304  Batches: 4  Memory Usage: 89234kB
        ->  Seq Scan on orders o
            (actual time=0.011..189.334 rows=40000000 loops=1)

Planning Time: 0.8 ms
Execution Time: 749.2 ms
```

Wait — the `rows=40000000` on the orders scan appears again. Does this mean the semi-join is also reading all forty million order rows? Yes — but there is a crucial difference. It is reading only the `customer_id` column from all forty million order rows, not the full row. And more importantly, it is building a hash table of distinct customer IDs present in the orders table — a hash table that contains at most two million entries (one per unique customer), not forty million. The semi-join logic ensures that once a customer ID is in the hash table, subsequent order rows for the same customer do not add new entries — they simply confirm an already-confirmed entry.

Furthermore, the `Sort` node — the eleven-second disk sort — is completely gone. There is no `Sort Method: external merge`. No 1.9 gigabytes of temporary disk files. The entire operation runs in memory.

The result: 749 milliseconds. Compared to 11,893 milliseconds — a sixteen-fold improvement even in this scenario where the planner chose a hash semi-join that still reads all order rows.

In many real-world cases, when an index exists on `orders.customer_id` and the index is selective, the planner will choose a nested loop semi-join that stops at the first matching row for each customer, producing results even faster — in the range of 50 milliseconds as the case study describes.

## Why This Matters: The Intermediate Result Set Problem

The insight at the core of this case study — that `JOIN + DISTINCT` creates a massive intermediate result set that is immediately discarded — is part of a broader principle about database query design that will serve you throughout your career.

Every step in a query execution plan produces an intermediate result. That intermediate result has a size, and that size determines how much memory, disk, and computation is required to produce it and pass it to the next step. Good query design minimises the size of intermediate results at every step — filtering early, avoiding unnecessary columns, and most importantly, not producing rows that will immediately be discarded.

The `JOIN + DISTINCT` pattern is particularly pernicious because the explosion in intermediate result size is invisible from the query text. Looking at `SELECT DISTINCT c.id, c.name FROM customers c JOIN orders o ON ...`, you might naturally think: "there are two million customers, the result will have at most two million rows." What you fail to account for is that the join runs before the `DISTINCT`, and at that moment, the intermediate result has forty million rows. The `DISTINCT` reduces it back down, but the damage is already done.

```
THE INTERMEDIATE RESULT EXPLOSION

Query execution order:

  customers (2M rows)
       │
       ▼
  JOIN with orders (40M rows)
       │
       ▼
  ┌───────────────────────────────────────────────┐
  │  Intermediate result: 40,000,000 rows         │ ← EXPLOSION
  │  Size in memory/disk: ~1.9 GB                 │
  │  Time to produce: ~9 seconds                  │
  └───────────────────────────────────────────────┘
       │
       ▼
  DISTINCT (sort + deduplicate)
       │
       ▼
  Final result: ~1,800,000 rows                   ← back to manageable size

  95.5% of all intermediate rows were unnecessary.
  Producing them took 95% of the query's execution time.

EXISTS avoids the explosion:

  customers (2M rows)
       │
       ▼ (for each customer, one existence check)
  Check orders index: does any order for this customer exist?
       │
       ▼
  Final result: ~1,800,000 rows                   ← built directly
  No intermediate explosion. No sorting. No deduplication.
```

The principle to internalize is: **always think about the size of intermediate results, not just the size of the final result.** When you see `JOIN + DISTINCT`, ask whether the join is producing rows you will immediately discard. When it is, `EXISTS` or another existence-check pattern is almost certainly the right tool.

## Other Valid Approaches: NOT IN, INTERSECT, and Semi-Join Equivalents

`EXISTS` is not the only way to avoid the `JOIN + DISTINCT` pitfall, though it is generally the most readable and reliable. For completeness, it is worth understanding the other patterns that express the same semantics.

The `INTERSECT` set operator provides another way to express "customers who appear in both the customers table and the set of order customer IDs":

```sql
SELECT id, name FROM customers
INTERSECT
SELECT c.id, c.name FROM customers c JOIN orders o ON c.id = o.customer_id;
```

This is more verbose and generally not preferred, but it is semantically correct and modern planners may optimise it similarly to `EXISTS`.

A `LEFT JOIN ... WHERE o.id IS NOT NULL` pattern is sometimes used and can work, but it is essentially the same as an `INNER JOIN` and suffers from the same intermediate explosion problem unless the planner is smart enough to convert it to a semi-join. In PostgreSQL, this conversion is not guaranteed.

The `IN (subquery)` pattern provides another alternative:

```sql
SELECT c.id, c.name
FROM customers c
WHERE c.id IN (SELECT DISTINCT customer_id FROM orders);
```

This is closer in spirit to `EXISTS` — you are checking membership in a set rather than joining — but the `DISTINCT` inside the subquery adds unnecessary work that the planner must see through. Without `DISTINCT`, the `IN (subquery)` version can be automatically optimised to a semi-join by modern planners, making it equivalent to `EXISTS` in performance. However, `EXISTS` makes the intent more explicit and is more reliably optimised across different database versions and edge cases.

```
APPROACHES COMPARED

JOIN + DISTINCT (slow — intermediate explosion):
  SELECT DISTINCT c.id, c.name FROM customers c
  JOIN orders o ON c.id = o.customer_id
  → 40M intermediate rows → sort → deduplicate → 1.8M rows

EXISTS (fast — semi-join, no explosion):
  SELECT c.id, c.name FROM customers c
  WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)
  → 1.8M rows directly, no intermediate explosion

IN (subquery) (usually fast — planner converts to semi-join):
  SELECT c.id, c.name FROM customers c
  WHERE c.id IN (SELECT customer_id FROM orders)
  → Planner may convert to semi-join (not guaranteed in all versions)

LEFT JOIN ... IS NOT NULL (equivalent to INNER JOIN — still slow):
  SELECT DISTINCT c.id, c.name FROM customers c
  LEFT JOIN orders o ON c.id = o.customer_id
  WHERE o.id IS NOT NULL
  → Still produces 40M intermediate rows before WHERE filter
```

The clear winner for readability, semantic precision, and reliable performance across database versions is `EXISTS`. It says exactly what you mean — "for whom does a matching row exist?" — and the database executes it with precisely that information requirement in mind.

## When JOIN Is Still the Right Choice

Understanding when `EXISTS` is better than `JOIN + DISTINCT` also means understanding when `JOIN` is the correct and irreplaceable tool. This distinction is important because replacing every `JOIN` with `EXISTS` would be as wrong as over-using `JOIN + DISTINCT`.

`JOIN` is the right tool when you need **data from the joined table** — not just confirmation that a matching row exists, but actual columns from that table in your output. If the marketing team's report needed to show "each customer along with the amount of their most recent order," you genuinely need data from the `orders` table, and a join is necessary. `EXISTS` only tells you whether a row exists — it cannot bring data from the related table into your output.

`JOIN` is also appropriate when you need aggregates from the joined table. "Show each customer with their total order count and total spend" requires a `JOIN` followed by `GROUP BY` — `EXISTS` cannot help here.

`JOIN + DISTINCT` is almost always replaceable with `EXISTS` specifically in the pattern "list items from table A that have at least one matching row in table B." The moment your query combines these words — "at least one," "any," "exists," "has" — you are expressing an existence relationship, and `EXISTS` is the precise tool for it.

```
CHOOSING BETWEEN JOIN AND EXISTS

Use JOIN when:
  ✓ You need columns from the joined table in your output
  ✓ You need aggregates over the joined table (use GROUP BY)
  ✓ You are combining data from two tables meaningfully
  ✓ Each row in the result represents a meaningful pair

  Example: "Show each customer with their most recent order amount"
  → Must JOIN to get order.amount into the output

Use EXISTS when:
  ✓ You only need to confirm a relationship exists
  ✓ You want rows from table A that have any match in table B
  ✓ You see yourself writing JOIN + DISTINCT together
  ✓ The result should contain only columns from the main table

  Example: "List customers who have placed at least one order"
  → No order data needed in output — just customer id and name
  → EXISTS is correct, JOIN + DISTINCT is wasteful
```

## The Result: 12,000ms → 50ms

After the query was rewritten using `EXISTS`, the marketing team's report went from the twelve-second "coffee break query" to a fifty-millisecond response — fast enough to feel instantaneous. The 1.9-gigabyte temporary disk file was eliminated. The sort was eliminated. The forty-million-row intermediate result was eliminated. The database answered the question with the minimum work the question logically required.

```
BEFORE — JOIN + DISTINCT:
  Intermediate result size:  40,000,000 rows (~1.9 GB)
  Sort method:               External merge (disk-based)
  Disk temp space:           1,892 MB
  Execution time:            11,893ms (12 seconds)

AFTER — EXISTS:
  Intermediate result size:  None (semi-join, no materialization)
  Sort:                      None required
  Disk temp space:           0 MB
  Execution time:            ~50ms

Improvement: 11,893ms ÷ 50ms = 238× faster
Rows produced uselessly:     38,200,000 → 0
Disk writes eliminated:      ~1.9 GB → 0
```

The principle that produced this improvement is one of the most broadly applicable in all of query design: **do not produce information you do not need.** The original query produced forty million rows of (customer, order) pair data and immediately discarded 95.5% of it. The rewritten query never produced that data at all, because the question never required it.

## The Lesson That Stays With You

The `JOIN + DISTINCT` antipattern is one of the most frequently encountered performance mistakes in production SQL, and it is common because the pattern feels intuitively correct. You want customers who have orders, so you join them with their orders. You notice the result has duplicates because a customer with multiple orders appears multiple times, so you add `DISTINCT` to clean it up. The result is correct. The logic is sound. And on small tables, it is fast. But at scale, it builds a mountain of intermediate data just to flatten it right back down.

The discipline to develop is this: before you write a `JOIN`, ask yourself what information you actually need from the joined table. If the answer is "nothing — I just need to know whether a match exists," then `EXISTS` is the right tool. If the answer is "I need specific columns or aggregates from the joined table," then `JOIN` is the right tool, used directly without `DISTINCT` (which would indicate you are producing more join rows than you need).

This question — "do I need the data, or just the existence of the match?" — is one of the clearest diagnostic questions in query optimisation. Develop the habit of asking it every time you reach for a `JOIN`, and you will avoid building mountains of intermediate data that you never needed to climb.

## Summary

This case study examines a twelve-second reporting query that needed to list all customers who had placed at least one order. The original query used `JOIN + DISTINCT` — joining the two-million-row customers table with the forty-million-row orders table and then applying `DISTINCT` to eliminate the duplicate customer rows that arise when a customer has multiple orders. The join produced forty million intermediate rows, required nearly two gigabytes of temporary disk storage for an external merge sort, and discarded 95.5% of the rows it produced before returning the final result. The cost of building and sorting this unwanted intermediate data was the source of the twelve-second execution time.

The fix was to replace `JOIN + DISTINCT` with `EXISTS` — checking for each customer whether any matching order exists, without ever producing or discarding duplicate rows. The database executed this as a semi-join: it found the answer to the existence question for each customer and moved on immediately, without materialising all matching orders. Execution time dropped from 11,893 milliseconds to approximately 50 milliseconds, a 240-fold improvement, with no schema changes and no indexes added — only a change in query shape.

The principle at the heart of this optimisation is that `JOIN + DISTINCT` is semantically misaligned with existence questions. A `JOIN` produces all matching pairs; `DISTINCT` then collapses them. `EXISTS` never produces the pairs at all. For any query that asks "which rows in table A have at least one matching row in table B?", `EXISTS` is the precise and efficient tool. For any query that needs actual data from table B in the output, `JOIN` is the correct tool used directly, without `DISTINCT`. Knowing which question you are asking determines which tool you should reach for.
