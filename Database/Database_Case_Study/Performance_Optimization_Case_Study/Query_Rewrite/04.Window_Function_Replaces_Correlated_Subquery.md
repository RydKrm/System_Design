# The Report That Re-Read Ten Million Orders Ten Million Times: How a Window Function Replaced a Two-Minute Query with an 800ms One

> _"A correlated subquery in the SELECT clause is the database equivalent of recalculating the sum of a running total from the very beginning every time you add a new number to a list. A window function is the equivalent of simply keeping a running total as you go."_

---

## Setting the Scene

You are working as a data engineer at an e-commerce company. The business intelligence team runs a critical analytics report every morning before the executive meeting — a report titled "Customer Lifetime Value by Order." The purpose of this report is to answer a specific, powerful question for every single order in the database: at the moment this order was placed, how much had this customer spent with the company in total, including this order?

This metric is deeply valuable for business analysis. It tells you whether your customers are gradually spending more over time. It allows you to identify the exact order at which a customer crossed a revenue milestone. It lets you correlate marketing campaigns with changes in cumulative spend trajectories. The finance team loves it. The product team loves it. The CEO references it in board presentations.

The problem is that running this report has become an ordeal. The orders table has accumulated ten million rows over several years of operation. When the analytics team triggers the report, the database server begins groaning under the load. Application query logs show the query running for two full minutes — sometimes more. On particularly busy mornings, the database runs out of time before the query finishes, and the report page shows nothing but an error message.

Your senior engineer looks at the query responsible for this report. She is quiet for a moment, reading it carefully. Then she pulls out her chair, sits down, and says: _"Sit with me. What this query is doing is one of the most instructive examples of repeated unnecessary work I have ever seen in production SQL. By the time we are done, you are going to understand window functions, and you are never going to write a query like this one again."_

---

## The Offending Query

The query powering the Lifetime Value report looks like this:

```sql
SELECT
    o.id,
    o.customer_id,
    o.amount,
    o.created_at,
    (
        SELECT SUM(o2.amount)
        FROM orders o2
        WHERE o2.customer_id = o.customer_id
          AND o2.created_at <= o.created_at
    ) AS lifetime_value_at_order
FROM orders o
ORDER BY o.customer_id, o.created_at;
```

Read this query carefully. For every row in the `orders` table — every one of the ten million orders — there is a subquery in the `SELECT` clause. This subquery takes the current order's `customer_id` and `created_at`, and then goes back into the `orders` table to sum up all the amounts for the same customer up to and including that order's date. The idea is correct: for order number seven from customer A, you want the sum of orders one through seven from customer A. For order number eight from customer A, you want the sum of orders one through eight. And so on.

The logic is impeccable. The performance is catastrophic.

---

## Understanding Correlated Subqueries in the SELECT Clause

You have already encountered correlated subqueries in the context of `WHERE` clauses in the previous case study. But a correlated subquery in the `SELECT` clause — sometimes called a **scalar subquery** because it must return exactly one value to populate a single column — is a subtly different beast that deserves its own careful examination.

When a subquery appears in the `SELECT` clause, the database must evaluate it for every single row in the result set. Not once. Not a few times. Once per row. For ten million rows, the subquery runs ten million times. Each of those ten million subquery executions is itself a database operation — it opens the `orders` table, applies the `WHERE` conditions, sums the matching amounts, and returns a single number. Even if that subquery is individually fast — say, it takes twelve milliseconds per execution — ten million executions times twelve milliseconds equals one hundred and twenty thousand seconds of database work, which translates into the two-minute query time the team was experiencing.

The most painful aspect of this situation is what happens when you look closely at what each subquery execution is actually computing. Consider a customer who has placed one thousand orders over their lifetime with the company. To compute the lifetime value at order one, the subquery sums one row. To compute the lifetime value at order two, the subquery sums two rows — including the row it already summed for order one. To compute the lifetime value at order three, the subquery sums three rows — including the two rows it already summed previously. To compute the lifetime value at order one thousand, the subquery sums one thousand rows — including all nine hundred and ninety-nine rows that have already been summed in previous iterations.

```
THE REPEATED WORK OF A CORRELATED SUBQUERY

Customer A has 5 orders: [$10, $25, $15, $30, $20]

Computing lifetime_value_at_order for each row:

  Order 1 ($10):  SUM($10)                      = $10
                  [subquery reads: 1 row]

  Order 2 ($25):  SUM($10 + $25)                = $35
                  [subquery reads: 2 rows — row 1 already summed before!]

  Order 3 ($15):  SUM($10 + $25 + $15)          = $50
                  [subquery reads: 3 rows — rows 1 & 2 already summed!]

  Order 4 ($30):  SUM($10 + $25 + $15 + $30)    = $80
                  [subquery reads: 4 rows — rows 1,2,3 already summed!]

  Order 5 ($20):  SUM($10 + $25 + $15 + $30 + $20) = $100
                  [subquery reads: 5 rows — rows 1,2,3,4 already summed!]

  Total rows read by subquery for this one customer: 1+2+3+4+5 = 15
  Total rows needed if done intelligently:           5 (one pass)

  For a customer with 1,000 orders:
  Subquery reads: 1+2+3+...+1000 = 500,500 rows
  Intelligent reads:              1,000 rows
  Waste factor: 500×

  For 10,000,000 orders across all customers: catastrophic.
```

The waste grows quadratically within each customer's order history. A customer with N orders causes N² / 2 total rows to be read by the correlated subqueries computing their lifetime values. This is not a linear cost — it is a cost that explodes as order history grows. And in a mature e-commerce platform with loyal, long-term customers who have placed hundreds or thousands of orders, the explosion is severe.

## The Mental Model: What We Really Want the Database to Do

Before introducing the solution, let us think about what we would ideally want the database to do if it were to execute this computation as intelligently as possible.

Imagine the most efficient possible way to compute the running total of spend for every customer, in order. You would sort all orders by `(customer_id, created_at)`. Then you would walk through them from beginning to end, keeping a running sum for each customer. When you encounter the first order for customer A, your running sum for customer A starts at that order's amount. When you encounter the second order for customer A, you add its amount to the running sum. When you encounter the first order for customer B, you start a fresh running sum for customer B. And so on, until you have processed all ten million rows in a single forward pass.

```
THE IDEAL SINGLE-PASS COMPUTATION

Orders sorted by (customer_id, created_at):

  customer_id=1, order=$10  → running_sum=10   → lifetime_value: $10
  customer_id=1, order=$25  → running_sum=35   → lifetime_value: $35
  customer_id=1, order=$15  → running_sum=50   → lifetime_value: $50
  customer_id=2, order=$40  → running_sum=40   → lifetime_value: $40  (reset for new customer)
  customer_id=2, order=$60  → running_sum=100  → lifetime_value: $100
  customer_id=3, order=$5   → running_sum=5    → lifetime_value: $5   (reset for new customer)
  ...

  Total rows read: 10,000,000 (one pass)
  Total rows read by correlated subquery: hundreds of millions (many passes)

  This single-pass approach is exactly what a window function does.
```

This single-pass computation is exactly as efficient as the task logically requires. You process each row once, maintain a running state for each customer, and produce the output in one sweep through the data. No row is ever read twice.

This ideal computation is what **window functions** make possible in SQL.

## Window Functions: SQL's Most Powerful and Least Understood Feature

Window functions are one of the most powerful features in modern SQL, and also one of the most underused, primarily because their syntax is unfamiliar to engineers who learned SQL from basic tutorials. The concept behind them, however, is actually quite intuitive once you understand what problem they solve.

A window function performs a calculation across a **set of rows that are related to the current row** — what SQL calls a **window** — without collapsing those rows into a single result the way `GROUP BY` and aggregate functions do. The key distinction is crucial: with `GROUP BY`, you get one output row per group. With a window function, you get one output row per input row, but each output row has access to computations performed over a window of related rows.

In the case of our lifetime value query, the "window" for each order row is defined as: all orders for the same customer (`PARTITION BY customer_id`) that occurred up to and including the current order's date (`ORDER BY created_at ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`). The window function computes `SUM(amount)` over this window for every row, all in a single efficient pass.

The rewritten query looks like this:

```sql
SELECT
    id,
    customer_id,
    amount,
    created_at,
    SUM(amount) OVER (
        PARTITION BY customer_id
        ORDER BY created_at
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS lifetime_value_at_order
FROM orders
ORDER BY customer_id, created_at;
```

The results of this query are identical, row for row and value for value, to the original correlated subquery version. But the execution strategy is entirely different.

## Anatomy of the OVER Clause: Reading the Window Definition

The `OVER (...)` clause is the defining feature of every window function. It is the part that specifies what the "window" of rows is for each computation. Let us dissect its three components carefully, because understanding each one is essential to writing window functions confidently.

The first component is `PARTITION BY customer_id`. This divides the entire result set into independent partitions — one partition per `customer_id`. The window function resets its state at the beginning of each partition. This is conceptually similar to `GROUP BY`, but instead of collapsing the partition into one row, it processes each row within the partition while maintaining awareness of all other rows in the same partition. In our case, this ensures that the running sum for customer A never bleeds into the running sum for customer B.

The second component is `ORDER BY created_at`. Within each partition, this defines the order in which rows are processed. For a running total, the order matters enormously — you need to add amounts in chronological sequence so that "lifetime value up to this order's date" has a meaningful definition. The `ORDER BY` inside the `OVER` clause affects only the window computation; it does not determine the final sort order of the output query (that is handled by the outer `ORDER BY`).

The third component is `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. This is the **frame specification**, and it defines precisely which rows within the partition are included in the window for each row. `UNBOUNDED PRECEDING` means "start from the very first row of the partition." `CURRENT ROW` means "end at the row currently being processed." Together, they define a window that grows with each successive row — for the first row, the window contains one row; for the second row, the window contains two rows; and so on. This is the definition of a running total.

```
ANATOMY OF THE OVER CLAUSE

SUM(amount) OVER (
    PARTITION BY customer_id         ← divide into independent groups
    ORDER BY created_at              ← process rows in this order
    ROWS BETWEEN UNBOUNDED PRECEDING ← window starts at partition's first row
              AND CURRENT ROW        ← window ends at the current row
)

Visualised for a single customer partition (customer_id = 1):

  Row 1: amount=$10, created_at=Jan
    Window: [Row 1]                  → SUM = $10

  Row 2: amount=$25, created_at=Feb
    Window: [Row 1, Row 2]           → SUM = $35

  Row 3: amount=$15, created_at=Mar
    Window: [Row 1, Row 2, Row 3]    → SUM = $50

  Row 4: amount=$30, created_at=Apr
    Window: [Row 1, Row 2, Row 3, Row 4] → SUM = $80

  ↑ The window grows by one row at a time.
  ↑ The database maintains an internal running total — no re-reading.
```

The critical implementation detail — the one that makes window functions so efficient — is that the database engine does not recompute the sum from scratch for each row. It maintains an internal accumulator as it moves through the partition. When it advances from row three to row four, it simply adds row four's amount to the already-computed sum of rows one through three. The cost of advancing from one row to the next is constant — it does not depend on how many rows came before. This is the single-pass computation we described as the ideal approach.

## What the Query Planner Does Differently

When you run `EXPLAIN ANALYZE` on the correlated subquery version, the output reveals the nested structure of repeated work:

```
Sort  (cost=999999.99..1024999.99 rows=10000000 width=52)
      (actual time=118432.112..121054.334 rows=10000000 loops=1)
  ->  Seq Scan on orders o
      (actual time=0.012..119234.221 rows=10000000 loops=1)
      SubPlan 1
        ->  Aggregate  (cost=9.83..9.84 rows=1 width=8)
            (actual time=0.011..0.011 rows=1 loops=10000000)
          ->  Index Scan on orders o2
              (cost=0.57..9.33 rows=200 width=8)
              (actual time=0.004..0.008 rows=200 loops=10000000)
                Index Cond: (customer_id = o.customer_id)
                Filter: (created_at <= o.created_at)

Planning Time: 2.3 ms
Execution Time: 121,847 ms
```

The smoking gun is `loops=10000000` on the inner index scan. The database executed the inner aggregate query ten million times — once for each row in the outer scan. Even though each individual subquery execution was fast (roughly twelve microseconds), ten million of them accumulate to over two minutes.

Now the window function version:

```
WindowAgg  (cost=1624755.42..1824755.42 rows=10000000 width=52)
           (actual time=42312.112..783.445 rows=10000000 loops=1)
  ->  Sort  (cost=1624755.42..1649755.42 rows=10000000 width=44)
            (actual time=42311.889..55234.112 rows=10000000 loops=1)
        Sort Key: customer_id, created_at
        ->  Seq Scan on orders
            (actual time=0.021..12341.334 rows=10000000 loops=1)

Planning Time: 0.5 ms
Execution Time: 798 ms
```

The plan has only three nodes: a sequential scan of the orders table (done once), a sort by `(customer_id, created_at)` (done once), and a `WindowAgg` node that sweeps through the sorted data computing the running sum (done once). The inner aggregate operation that previously ran ten million times is completely gone. The database reads each of the ten million rows exactly one time, processes it through the window function accumulator, and emits it to the output. Total execution time: 798 milliseconds.

## The Sorting Cost: Understanding the One Genuine Tradeoff

Looking at the `EXPLAIN ANALYZE` output for the window function version, you will notice that the sort step — `Sort Key: customer_id, created_at` — takes a significant portion of the total time. This is the genuine cost that window functions must pay.

Before the window function can sweep through the data in a single pass, the data must be in the correct order. To compute running totals partitioned by `customer_id` and ordered by `created_at`, the database must first sort all ten million rows by `(customer_id, created_at)`. This sort operation — on ten million rows — takes real time and real memory. On large datasets, the sort might even spill to disk if the working memory is insufficient, making it slower still.

This is why the window function approach, despite being dramatically faster than the correlated subquery, still takes 798 milliseconds rather than something trivially small. The single sort of ten million rows is the irreducible minimum cost of this computation — and it is a cost the correlated subquery also paid implicitly, buried inside each of its ten million individual subquery executions. The window function surfaces this cost transparently and pays it once.

```
WHERE THE TIME GOES (Window Function version, 798ms total)

  ┌──────────────────────────────────────────────────────────────┐
  │  Sequential Scan (10M rows read):        ~12,000ms           │
  │  Sort (10M rows by customer, date):      ~42,000ms           │
  │  Window Aggregation (single pass):       ~44,000ms           │  ← still fast
  │                                                              │
  │  Total:                                   ~798ms             │
  │  (numbers approximate, measured in parallel with pipeline)   │
  └──────────────────────────────────────────────────────────────┘

  WHERE THE TIME WENT (Correlated Subquery version, 121,847ms total)

  ┌──────────────────────────────────────────────────────────────┐
  │  Outer table scan (10M rows):             ~12,000ms          │
  │  Inner subquery × 10,000,000 executions:  ~109,000ms         │
  │    Each inner query: reads ~200 rows avg                     │
  │    Total inner rows read: ~2,000,000,000                     │
  │                                                              │
  │  Total:                                   ~121,847ms         │
  └──────────────────────────────────────────────────────────────┘

  The correlated subquery reads approximately 2 billion rows total.
  The window function reads approximately 10 million rows total.
  Ratio: 200×
```

If an index already exists on `(customer_id, created_at)` — which is likely in a well-designed orders table — the database might use an **index scan** instead of a sequential scan followed by a sort, since the index already stores data in the required order. In that case, the window function can skip the sorting step entirely and sweep through the pre-sorted index entries directly, making the computation even faster. This is one reason why creating a composite index on the columns referenced in a window function's `PARTITION BY` and `ORDER BY` is often a high-value optimisation for analytic queries.

## The Frame Specification: A World of Possibilities

The `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` frame specification we used is the most common choice for running totals, but the frame specification system in SQL is remarkably expressive, allowing you to define windows of almost any shape. Understanding the broader frame specification syntax will give you a sense of how versatile window functions truly are.

The frame can be defined using either `ROWS` mode, which counts individual rows, or `RANGE` mode, which includes all rows with values equal to the current row's `ORDER BY` value. For most running total use cases, `ROWS` mode is more predictable and performant.

The start and end of the frame are expressed using combinations of `UNBOUNDED PRECEDING` (the very first row of the partition), `N PRECEDING` (N rows before the current row), `CURRENT ROW`, `N FOLLOWING` (N rows after the current row), and `UNBOUNDED FOLLOWING` (the very last row of the partition).

```
FRAME SPECIFICATION EXAMPLES

  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ← Running total from start of partition to current row
  Example: cumulative spend, running count

  ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ← Rolling 7-row window (current + 6 before it)
  Example: 7-day moving average of daily sales

  ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
  ← Sum from current row to end of partition
  Example: remaining balance, future commitments

  ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ← Entire partition (same as a simple GROUP BY aggregate)
  Example: percentage of partition total for each row

  ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING
  ← Centered 7-row sliding window
  Example: smoothed time series analysis
```

Each of these frame specifications enables a different kind of analytical computation, all expressed within the same clean `OVER (...)` syntax, and all executed in a single efficient pass over the partitioned data.

## Common Window Functions Beyond SUM

`SUM()` with a cumulative frame is just one member of a large family of window functions. Understanding the full family will help you recognise when a window function is the right tool and which specific function to reach for.

`ROW_NUMBER()` assigns a sequential integer to each row within its partition, starting at one. This is invaluable for ranking use cases — finding the first order per customer, the top-three products per category, or the most recent event per user. `RANK()` and `DENSE_RANK()` are similar but handle tied values differently: `RANK()` skips numbers after a tie (1, 1, 3, 4...) while `DENSE_RANK()` does not (1, 1, 2, 3...).

`LAG()` and `LEAD()` give you access to the values from previous or subsequent rows within the partition, without a self-join. `LAG(amount, 1)` retrieves the `amount` from the previous row in the ordered partition — perfect for computing period-over-period differences, such as "how much did this order differ from the previous order by the same customer?"

`FIRST_VALUE()` and `LAST_VALUE()` retrieve the first and last values in the window frame, making it easy to compute things like "what was this customer's first order amount" for every row in the customer's history.

`AVG()`, `MIN()`, `MAX()`, and `COUNT()` all work as window functions when combined with an `OVER` clause, enabling rolling averages, running counts, and cumulative extremes with the same single-pass efficiency.

```
WINDOW FUNCTION FAMILY — A Reference

  SUM(col)    OVER (...)  → Running / rolling sum
  AVG(col)    OVER (...)  → Running / rolling average
  COUNT(col)  OVER (...)  → Running / rolling count
  MIN(col)    OVER (...)  → Running minimum seen so far
  MAX(col)    OVER (...)  → Running maximum seen so far

  ROW_NUMBER()   OVER (...)  → Sequential row number within partition
  RANK()         OVER (...)  → Rank with gaps on ties (1,1,3,4)
  DENSE_RANK()   OVER (...)  → Rank without gaps on ties (1,1,2,3)
  PERCENT_RANK() OVER (...)  → Relative rank as 0.0 to 1.0

  LAG(col, n)    OVER (...)  → Value from n rows before current row
  LEAD(col, n)   OVER (...)  → Value from n rows after current row

  FIRST_VALUE(col) OVER (...) → First value in the window frame
  LAST_VALUE(col)  OVER (...) → Last value in the window frame
  NTH_VALUE(col,n) OVER (...) → Nth value in the window frame

  NTILE(n)       OVER (...)  → Divide partition into n equal buckets
  CUME_DIST()    OVER (...)  → Cumulative distribution (0.0 to 1.0)
```

## Recognising the Pattern: When a Correlated Subquery Can Become a Window Function

The transformation from correlated subquery to window function follows a recognisable pattern that, once you have seen it, you will spot repeatedly in real codebases. The signal to watch for is a correlated subquery in the `SELECT` clause (or occasionally the `WHERE` clause) that performs an **aggregation** over **related rows** of the **same table** — related by some grouping key and potentially ordered by some column.

Whenever you see a subquery of the form `(SELECT AGG(col) FROM same_table WHERE grouping_key = outer.grouping_key AND ordering_col <= outer.ordering_col)`, you are almost certainly looking at a pattern that can be expressed more efficiently as a window function. The mapping is direct: the `WHERE grouping_key = outer.grouping_key` becomes `PARTITION BY grouping_key` in the `OVER` clause, and the `AND ordering_col <= outer.ordering_col` becomes `ORDER BY ordering_col ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

```
THE TRANSFORMATION PATTERN

Correlated subquery:
  SELECT o.id,
         (SELECT AGG(o2.col)
          FROM orders o2
          WHERE o2.customer_id = o.customer_id    ← grouping condition
            AND o2.created_at <= o.created_at)    ← ordering condition
  FROM orders o

Equivalent window function:
  SELECT id,
         AGG(col) OVER (
             PARTITION BY customer_id             ← same grouping condition
             ORDER BY created_at                  ← same ordering condition
             ROWS BETWEEN UNBOUNDED PRECEDING
                      AND CURRENT ROW             ← "up to and including current"
         )
  FROM orders

  Same result. One pass instead of N passes.
  Transformation is mechanical once you see the pattern.
```

This transformation works for any standard aggregate function: `SUM`, `COUNT`, `AVG`, `MIN`, `MAX`. It also works for more complex aggregation patterns, though those may require careful attention to the frame specification.

## The Result: 120,000ms → 800ms

After the window function rewrite was deployed, the analytics report that had been timing out went from a two-minute ordeal to a sub-second operation. The business intelligence team's morning report was available instantly, reliably, and without any database strain.

The numbers tell a clear story:

```
BEFORE — Correlated Subquery:
  Inner subquery executions:   10,000,000
  Approximate rows read total: ~2,000,000,000
  Execution time:              121,847ms (over 2 minutes)
  Timed out on busy mornings:  Yes

AFTER — Window Function:
  Passes over the data:        1
  Rows read total:             10,000,000
  Execution time:              798ms
  Timed out on busy mornings:  Never

Improvement: 121,847ms ÷ 798ms = 152× faster
Data read:   2,000,000,000 rows ÷ 10,000,000 rows = 200× less I/O
```

The improvement of 150× is not merely a performance optimisation — it is the difference between a report that cannot be relied upon and one that is always available when it is needed. The same data. The same results. The same analytical value. But produced by a fundamentally different and more intelligent approach to the computation.

## The Lesson That Stays With You

The deepest lesson this case study imparts is one about recognising when you are asking the database to do redundant work and knowing the tool that eliminates that redundancy.

A correlated subquery in the `SELECT` clause is the database equivalent of computing a running total by, for each new number, going back to the very beginning of the list and adding everything up from scratch. Every experienced engineer knows that the right way to compute a running total is to maintain an accumulator — add the new number to the current total, and you are done. Window functions are SQL's built-in accumulator mechanism. They compute the aggregation once, progressively, as data flows through in a single ordered pass.

The pattern to memorise is this: whenever you see a correlated subquery that aggregates over related rows of the same table, partitioned by some key and ordered by some column, you are looking at a candidate for a window function. The conversion is mechanical, the syntax is learnable in an afternoon, and the performance improvement is often dramatic — particularly on large tables where the N² cost of the correlated approach becomes crushing.

Window functions are not a niche feature for database specialists. They are a fundamental tool for any engineer who writes analytical SQL, and investing time in learning them deeply will pay dividends throughout your career every time you encounter aggregate computations over ordered, partitioned data.

## Summary

This case study follows the investigation and resolution of a two-minute analytics query that was computing the running lifetime value for every customer across ten million orders. The original query used a correlated subquery in the `SELECT` clause — re-running a `SUM(amount)` aggregation for each of the ten million rows, each time scanning all preceding orders for that customer from scratch. The total work was proportional to the square of each customer's order history, resulting in billions of rows processed and a two-minute (often timed-out) execution time.

The fix was to replace the correlated subquery with a window function using `SUM(amount) OVER (PARTITION BY customer_id ORDER BY created_at ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`. The window function sorts the data once by `(customer_id, created_at)` and then sweeps through it in a single forward pass, maintaining a running accumulator per customer that is updated by adding each new row's amount — without ever re-reading previous rows. Total data read dropped from approximately two billion rows to ten million rows. Execution time dropped from 121,847 milliseconds to 798 milliseconds — a 152-fold improvement.

The lesson to carry forward is direct: any correlated subquery that aggregates over a partition of the same table, ordered by some column, can be expressed as a window function. The correlated version performs N passes over the data for N rows. The window function version performs one pass. On large tables, this is not a subtle difference — it is the difference between a query that destroys database performance and one that runs comfortably within any reasonable time budget.
