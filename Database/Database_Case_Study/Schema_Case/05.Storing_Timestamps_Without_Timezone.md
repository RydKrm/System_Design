# Case Study 05 — Storing Timestamps Without Timezone

---

## The Setup — The Migration That Moved the Clock

A logistics company runs a shipment tracking platform. Orders are created, picked up, shipped, and delivered — each event timestamped in the database. The platform starts as a single-region deployment in Singapore. The database server's OS timezone is `Asia/Singapore` (UTC+8). The schema uses `TIMESTAMP` (without timezone) for all event columns:

```sql
CREATE TABLE shipments (
    id              BIGSERIAL PRIMARY KEY,
    order_id        BIGINT NOT NULL,
    status          TEXT NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),  -- <-- No timezone
    picked_up_at    TIMESTAMP,
    delivered_at    TIMESTAMP
);
```

For eighteen months, everything works fine — all users are in Singapore, the server is in Singapore, and the local time stored is what users expect to see. No one notices anything unusual.

The company expands to Australia. A second server is spun up in Sydney (UTC+11 in summer, UTC+10 in winter). The operations team migrates the database to AWS Sydney for lower latency. During the migration, the DB server timezone changes from `Asia/Singapore` (UTC+8) to `Australia/Sydney` (UTC+10 or +11 depending on DST).

The next morning, the Singapore customer support team opens the dashboard and notices something alarming: every shipment created before the migration appears to have been created two hours in the future. A package recorded as "delivered at 14:00" in Singapore is now showing as "delivered at 16:00." Eighteen months of historical shipment timestamps are wrong — not off by a random amount, but wrong by exactly the UTC offset difference between `Asia/Singapore` (+8) and `Australia/Sydney` (+10). Two hours.

But the migration did not change any data. Not a single row was updated. The timestamps stored in the database are byte-for-byte identical to what they were before the migration. What changed is the context that PostgreSQL uses to interpret those timestamp values — the server's timezone. A timestamp stored as `TIMESTAMP` (without timezone) is a naked wall-clock reading with no timezone metadata. When the server's clock context changes, the meaning of every stored value changes with it.

---

## `TIMESTAMP` vs `TIMESTAMPTZ` — The Critical Difference

PostgreSQL has two distinct timestamp types, and the difference between them is fundamental rather than superficial. Understanding this difference in depth is the key to never making this mistake.

**`TIMESTAMP` (without time zone)**, also written as `TIMESTAMP WITHOUT TIME ZONE`: This type stores a date and a time — year, month, day, hour, minute, second, microsecond — as a literal wall-clock reading with no timezone information attached. When you store `2025-03-15 14:00:00` in a `TIMESTAMP` column, PostgreSQL stores the literal string of digits representing that date and time, and nothing else. There is no record of what timezone the person or system who created that timestamp was in. The stored value means "14:00 on March 15, 2025 in whatever timezone happens to be relevant when you read it."

**`TIMESTAMPTZ` (with time zone)**, also written as `TIMESTAMP WITH TIME ZONE`: This type stores a single, absolute point in time — an instant on the universal timeline, independent of any timezone. Internally, PostgreSQL stores `TIMESTAMPTZ` values as **microseconds since 2000-01-01 00:00:00 UTC**. When you insert `2025-03-15 14:00:00+08:00` (Singapore time), PostgreSQL converts it to UTC (`2025-03-15 06:00:00 UTC`) and stores the UTC-equivalent number of microseconds. When you read the value, PostgreSQL converts from UTC back to the timezone configured for your session or specified in your query. The stored value means "the instant that was simultaneously 06:00 UTC, 14:00 Singapore time, 17:00 Sydney time, and 01:00 New York time."

```
TIMESTAMP vs TIMESTAMPTZ — What PostgreSQL Actually Stores:
======================================================================

  INSERT statement: "Package delivered at 2:00 PM Singapore time"
  Delivered_at value: '2025-03-15 14:00:00'

  Scenario A: Column is TIMESTAMP (no timezone)
  +--------------------------------------------------+
  | What PostgreSQL stores: 2025-03-15 14:00:00      |
  | What timezone is this?  UNKNOWN. Not stored.      |
  | Read by Singapore server (+8): 2025-03-15 14:00  |
  | Read by Sydney server (+10):   2025-03-15 14:00  | <- WRONG: shows 14:00
  | Read by London server (+0):    2025-03-15 14:00  | <- WRONG: shows 14:00
  |                                                  |
  | The number 14:00 is stored and returned as-is.   |
  | The server timezone changes nothing about what   |
  | is returned — but the MEANING changes completely.|
  | Singapore users expected 14:00 to mean their 2PM.|
  | Now it means Sydney's 2PM (which is Singapore's  |
  | 12PM), or London's 2PM (Singapore's 10PM).       |
  +--------------------------------------------------+

  Scenario B: Column is TIMESTAMPTZ (with timezone)
  +--------------------------------------------------+
  | Inserted as: '2025-03-15 14:00:00+08' (SGT)      |
  | PostgreSQL converts to UTC: 06:00:00 UTC          |
  | What PostgreSQL stores: 2025-03-15 06:00:00 UTC   |
  |                                                  |
  | Read by Singapore session (SET timezone='+8'):   |
  | Returns: 2025-03-15 14:00:00+08  (CORRECT)       |
  |                                                  |
  | Read by Sydney session (SET timezone='AEST+10'): |
  | Returns: 2025-03-15 16:00:00+10  (CORRECT)       |
  |                                                  |
  | Read by London session (SET timezone='UTC'):     |
  | Returns: 2025-03-15 06:00:00+00  (CORRECT)       |
  |                                                  |
  | Every user in every timezone sees the correct    |
  | local equivalent of the same absolute instant.  |
  | Server migration changes nothing — the UTC value |
  | stored in the database is timeless and immutable.|
  +--------------------------------------------------+
======================================================================
```

The profound difference is that `TIMESTAMP` stores a description of a clock face reading, while `TIMESTAMPTZ` stores a position on the universal timeline. A clock face reading is meaningless without knowing which clock it came from. A position on the universal timeline is unambiguous everywhere and for all time.

## The Three Failure Scenarios — When Naive Timestamps Break

The `TIMESTAMP` type fails in three distinct situations, each with its own flavor of damage.

### Failure Scenario One: Server Migration or Timezone Change

This is the scenario from our opening story. When the database server's OS timezone changes — whether because of physical migration to a different region, cloud migration, or an administrator changing the `TimeZone` setting in `postgresql.conf` — every `TIMESTAMP` value in the database acquires a new meaning. A value that represented "14:00 Singapore time" now represents "14:00 Sydney time" — which is a different instant by the UTC offset difference (2 hours in this case).

The insidious part is that **no data changed**. The bytes on disk are identical before and after the migration. The timestamp `2025-03-15 14:00:00` is stored and returned exactly as-is by both the Singapore-timezone server and the Sydney-timezone server. But the human interpretation of what that number means is completely different. Eighteen months of history shifts by two hours, silently, without any error, without any warning, without any change to the database itself.

### Failure Scenario Two: Daylight Saving Time (DST)

DST is where `TIMESTAMP` storage creates logically impossible situations. In many regions, clocks "spring forward" in spring (losing one hour) and "fall back" in autumn (gaining one hour). When a server configured for a DST-aware local timezone uses `TIMESTAMP` storage:

**During the "fall back":** At 2:00 AM clocks are set back to 1:00 AM. This means the hour between 1:00 AM and 2:00 AM occurs twice. Events that happen during the second occurrence of that hour will have timestamps that are indistinguishable from events that happened during the first occurrence. A log entry at "01:30 AM" could refer to either the first or second 1:30 AM — there is no way to tell which. With `TIMESTAMPTZ`, these events have different UTC times and are perfectly distinguishable.

**During the "spring forward":** At 1:00 AM clocks are set forward to 2:00 AM. The hour between 1:00 AM and 2:00 AM does not exist on local time. A timestamp of "01:30 AM" on this day is not a valid local time — it never occurred. Any event that actually happened at what was 01:30 AM UTC+X has no valid local time representation.

```
DST — The Duplicate and Missing Hours:
======================================================================

  "Fall back": 2:00 AM local → 1:00 AM local (clocks go back 1 hour)
  Using TIMESTAMP (local time):

  00:59:00  Event A recorded. Timestamp: '2025-11-02 00:59:00'
  01:00:00  Event B recorded. Timestamp: '2025-11-02 01:00:00'  <- 1st occurrence
  01:30:00  Event C recorded. Timestamp: '2025-11-02 01:30:00'  <- AMBIGUOUS
  01:59:00  Event D recorded. Timestamp: '2025-11-02 01:59:00'  <- 1st or 2nd?
  [CLOCK FALLS BACK TO 01:00:00]
  01:00:00  Event E recorded. Timestamp: '2025-11-02 01:00:00'  <- 2nd occurrence
  01:30:00  Event F recorded. Timestamp: '2025-11-02 01:30:00'  <- SAME as Event C!
  02:00:00  Event G recorded. Timestamp: '2025-11-02 02:00:00'

  SELECT * FROM events ORDER BY timestamp;
  Result: A, B, C, D, E, F, G
  But C and F have identical timestamps. Which came first? UNKNOWN.
  The database is ordered wrong (D actually happened BEFORE E, but they
  appear in the correct position only by coincidence of their sub-second value).
  Audit logs, order histories, financial ledgers — all potentially wrong.

  "Spring forward": 2:00 AM local → 3:00 AM local (1 hour skipped)
  Any event at '2025-03-09 02:30:00' in the US Eastern timezone:
  -> This time NEVER EXISTED on local clocks.
  -> If stored as TIMESTAMP: represents a time that did not happen.
  -> If read back: creates a phantom event in a non-existent time slot.

  Using TIMESTAMPTZ:
  All events are stored as UTC. UTC has no DST. UTC is monotonically
  increasing. No ambiguity. No missing hours. No duplicate hours. Ever.
  Event C: stored as UTC 06:30:00. Event F: stored as UTC 07:30:00.
  Different UTC values, one hour apart, perfectly ordered and unambiguous.
======================================================================
```

### Failure Scenario Three: Multi-Region and Multi-Timezone Users

When a platform serves users in multiple timezones — which describes virtually every platform with more than local reach — `TIMESTAMP` columns create an invisible correctness problem for any query that compares times across timezone boundaries. "Show me all orders created today" has different answers depending on whose "today" you mean. A user in UTC-5 (New York) and a user in UTC+5:30 (Kolkata) have different "todays" — they differ by 10.5 hours. A query using `TIMESTAMP` and `WHERE created_at >= CURRENT_DATE` produces different results depending on the server's timezone, not the user's timezone, making it unreliable for any multi-timezone application.

## The Correct Solution — `TIMESTAMPTZ` Everywhere

The fix is a schema-level decision that costs nothing beyond a schema column type change, but prevents an entire class of time-related bugs permanently:

```sql
-- The correct schema — TIMESTAMPTZ for every timestamp column:
CREATE TABLE shipments (
    id              BIGSERIAL       PRIMARY KEY,
    order_id        BIGINT          NOT NULL REFERENCES orders(id),
    status          TEXT            NOT NULL DEFAULT 'created',
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    picked_up_at    TIMESTAMPTZ,                -- NULL until pickup
    delivered_at    TIMESTAMPTZ,                -- NULL until delivery
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- Key properties of TIMESTAMPTZ that make it correct:
-- 1. NOW() returns the current instant as UTC — always correct regardless
--    of what timezone the client session is in.
-- 2. Values are stored as microseconds since 2000-01-01 UTC — a pure number,
--    independent of any timezone.
-- 3. When read by clients, PostgreSQL converts from UTC to the client's
--    timezone setting transparently.
-- 4. Comparisons and sorting work correctly across all timezones.
-- 5. No DST anomalies — UTC never has DST.
-- 6. Server migration, timezone configuration changes: zero impact on stored data.

-- Demonstrate correct behavior across timezones:
SET timezone = 'Asia/Singapore';
SELECT NOW();
-- 2025-03-15 14:00:00+08

SET timezone = 'Australia/Sydney';
SELECT NOW();
-- 2025-03-15 16:00:00+11 (same instant, different display)

SET timezone = 'UTC';
SELECT NOW();
-- 2025-03-15 06:00:00+00 (same instant, UTC display)

-- All three SELECTs return the SAME instant. The stored value never changes.
-- Only the display adapts to the session timezone.
```

## The PostgreSQL Timezone Architecture — How It Actually Works

Understanding how PostgreSQL handles timezones end-to-end helps engineers write correct application code and avoid subtle bugs even with `TIMESTAMPTZ` columns.

PostgreSQL maintains a **session timezone** setting that controls two things: how incoming timestamp strings without explicit offset are interpreted during inserts, and how `TIMESTAMPTZ` values are displayed when read. The session timezone is set via `SET timezone = 'Region/City'` or `SET TIME ZONE 'UTC'`, or it defaults to the server's `timezone` configuration parameter, which defaults to the OS timezone.

When you insert a `TIMESTAMPTZ` value, PostgreSQL converts the input to UTC using the session timezone if no explicit offset is provided in the input string. When you read a `TIMESTAMPTZ` value, PostgreSQL converts the stored UTC value to the session timezone for display. The stored value itself is always UTC.

```sql
-- Demonstrate the session timezone mechanism:

-- Insert in Singapore timezone context:
SET timezone = 'Asia/Singapore';  -- UTC+8
INSERT INTO shipments (order_id, status, delivered_at)
VALUES (42, 'delivered', '2025-03-15 14:00:00');
-- PostgreSQL sees no explicit offset on '14:00:00'
-- Uses session timezone (Singapore, +8) to interpret: 14:00+08 = 06:00 UTC
-- Stores: 2025-03-15 06:00:00 UTC

-- Read in Singapore context:
SET timezone = 'Asia/Singapore';
SELECT delivered_at FROM shipments WHERE order_id = 42;
-- Returns: 2025-03-15 14:00:00+08  (CORRECT: 2PM Singapore)

-- Read in Sydney context:
SET timezone = 'Australia/Sydney';
SELECT delivered_at FROM shipments WHERE order_id = 42;
-- Returns: 2025-03-15 17:00:00+11  (CORRECT: 5PM Sydney = same instant)

-- Read in UTC context:
SET timezone = 'UTC';
SELECT delivered_at FROM shipments WHERE order_id = 42;
-- Returns: 2025-03-15 06:00:00+00  (CORRECT: 6AM UTC = same instant)

-- Explicit offset in the input string — always unambiguous:
SET timezone = 'UTC';  -- Session timezone doesn't matter when offset is explicit
INSERT INTO shipments (order_id, status, delivered_at)
VALUES (43, 'delivered', '2025-03-15 14:00:00+08');  -- Explicit SGT offset
-- PostgreSQL: 14:00+08 = 06:00 UTC. Stores UTC regardless of session timezone.

-- BEST PRACTICE: Always include explicit timezone offset in inserts,
-- or always use UTC as the session timezone in your application.
-- Never rely on implicit session timezone interpretation.
```

## Writing Correct Go Code — UTC by Default, Always

In Go, the `time.Time` type always carries timezone information internally. The key discipline is ensuring that every `time.Time` value that enters or exits the database is explicitly in UTC. The Go standard library makes this straightforward, but there are common pitfalls:

```go
// Correct Go patterns for TIMESTAMPTZ with database/sql:

import (
    "database/sql"
    "time"
)

// When inserting timestamps: always use time.Now().UTC()
// time.Now() returns local time (server's OS timezone).
// time.Now().UTC() returns the same instant in UTC.
// Both store the same value in a TIMESTAMPTZ column.
// But UTC() is explicit about intent — no ambiguity.

func CreateShipment(db *sql.DB, orderID int64) error {
    now := time.Now().UTC()  // Explicit UTC — never time.Now() alone for DB values

    _, err := db.Exec(`
        INSERT INTO shipments (order_id, status, created_at, updated_at)
        VALUES ($1, 'created', $2, $2)
    `, orderID, now)
    return err
}

// When reading timestamps: PostgreSQL's TIMESTAMPTZ driver
// returns time.Time in UTC when using pgx or lib/pq.
// Always verify and convert to UTC on read for safety:

type Shipment struct {
    ID          int64
    OrderID     int64
    Status      string
    CreatedAt   time.Time
    DeliveredAt *time.Time  // Nullable: use pointer
}

func GetShipment(db *sql.DB, id int64) (*Shipment, error) {
    s := &Shipment{}
    var deliveredAt sql.NullTime  // handles NULL TIMESTAMPTZ

    err := db.QueryRow(`
        SELECT id, order_id, status, created_at, delivered_at
        FROM shipments WHERE id = $1
    `, id).Scan(&s.ID, &s.OrderID, &s.Status, &s.CreatedAt, &deliveredAt)
    if err != nil { return nil, err }

    // Normalize to UTC — pgx/pq usually returns UTC but be explicit:
    s.CreatedAt = s.CreatedAt.UTC()

    if deliveredAt.Valid {
        t := deliveredAt.Time.UTC()
        s.DeliveredAt = &t
    }
    return s, nil
}

// When displaying to users: convert FROM UTC TO user's timezone
// at the presentation layer — NEVER in the database or business logic layer.
func DisplayDeliveryTime(deliveredAt time.Time, userTimezone string) string {
    loc, err := time.LoadLocation(userTimezone)
    if err != nil {
        // Fallback to UTC if timezone is invalid
        return deliveredAt.UTC().Format("2006-01-02 15:04:05 UTC")
    }
    // Convert UTC to user's local time for display only
    localTime := deliveredAt.In(loc)
    return localTime.Format("2006-01-02 15:04:05 MST")
}

// Usage:
// deliveredAt := time.Date(2025, 3, 15, 6, 0, 0, 0, time.UTC)  // 06:00 UTC
// DisplayDeliveryTime(deliveredAt, "Asia/Singapore")
// -> "2025-03-15 14:00:00 SGT"   (correct: 2PM Singapore)
// DisplayDeliveryTime(deliveredAt, "Australia/Sydney")
// -> "2025-03-15 17:00:00 AEDT"  (correct: 5PM Sydney)
// DisplayDeliveryTime(deliveredAt, "America/New_York")
// -> "2025-03-15 02:00:00 EDT"   (correct: 2AM New York)

// CRITICAL: Set the database connection timezone to UTC
// This ensures that any timestamp strings without explicit offset
// are interpreted as UTC when inserted through the driver:
func OpenDB(dsn string) (*sql.DB, error) {
    db, err := sql.Open("pgx", dsn)
    if err != nil { return nil, err }

    // Set connection timezone to UTC — run on every new connection:
    db.SetConnMaxLifetime(time.Hour)
    _, err = db.Exec("SET timezone = 'UTC'")
    if err != nil { return nil, err }
    return db, nil
}

// Better: set timezone in the DSN connection string:
// dsn := "host=... user=... dbname=... TimeZone=UTC"
// Or in pgx config:
// config.RuntimeParams["TimeZone"] = "UTC"
```

## The Insidious `CURRENT_TIMESTAMP` vs `NOW()` Detail

A subtle but important detail about how PostgreSQL generates timestamps in queries:

```sql
-- NOW() and CURRENT_TIMESTAMP both return TIMESTAMPTZ in PostgreSQL.
-- Both return the current transaction start time, not the current wall clock.
-- Within a transaction, they return the same value even across multiple calls.

-- SAFE — returns TIMESTAMPTZ (current transaction start time in UTC internally):
INSERT INTO events (created_at) VALUES (NOW());
INSERT INTO events (created_at) VALUES (CURRENT_TIMESTAMP);

-- Both work correctly with TIMESTAMPTZ columns. PostgreSQL stores UTC internally.

-- The danger zone: using AT TIME ZONE to convert for storage
-- This is a common mistake that converts TIMESTAMPTZ to TIMESTAMP:
INSERT INTO events (created_at)
VALUES (NOW() AT TIME ZONE 'Asia/Singapore');
-- NOW() returns a TIMESTAMPTZ. Adding AT TIME ZONE converts it to a
-- TIMESTAMP (without timezone) in Singapore time.
-- You have just removed the timezone information — do not do this for storage.

-- AT TIME ZONE is for DISPLAY, not storage:
-- Display the current time in Singapore:
SELECT NOW() AT TIME ZONE 'Asia/Singapore';  -- For display only, not for storage

-- Correctly store NOW() in TIMESTAMPTZ column (no conversion needed):
INSERT INTO events (created_at) VALUES (NOW());
-- PostgreSQL: NOW() is already TIMESTAMPTZ. Column is TIMESTAMPTZ.
-- No conversion. Stored as UTC. Perfect.

-- STATEMENT_TIMESTAMP() vs NOW() vs CLOCK_TIMESTAMP():
-- NOW() = CURRENT_TIMESTAMP: returns transaction start time (stable within txn)
-- STATEMENT_TIMESTAMP(): returns statement start time (changes per statement)
-- CLOCK_TIMESTAMP(): returns actual wall clock time (changes even mid-row scan)
-- For created_at/updated_at: use NOW() (transaction-level consistency)
-- For event logging with real wall-clock times: use CLOCK_TIMESTAMP()
```

## Migrating Existing TIMESTAMP Columns to TIMESTAMPTZ

The migration from `TIMESTAMP` to `TIMESTAMPTZ` requires a critical decision upfront: **what timezone were the existing values stored in?** The answer determines how to convert them. If the server has always been in UTC, the migration is trivial. If the server was in a local timezone, you must apply the offset correction explicitly:

```sql
-- Step 1: Determine what timezone the existing data is in
-- Check the server's current and historical timezone:
SHOW timezone;  -- Current setting
-- Check postgresql.conf for history, or ask the team.

-- Step 2A: If the server was always UTC (or if you want to declare UTC):
-- The TIMESTAMP values already represent UTC moments — just change the type.
ALTER TABLE shipments
ALTER COLUMN delivered_at TYPE TIMESTAMPTZ
USING delivered_at AT TIME ZONE 'UTC';
-- AT TIME ZONE 'UTC' converts TIMESTAMP -> TIMESTAMPTZ by declaring
-- that the stored local time IS UTC. No numeric adjustment.

-- Step 2B: If the server was in a local timezone (e.g., Asia/Singapore):
-- The TIMESTAMP values represent Singapore local time — convert to UTC.
ALTER TABLE shipments
ALTER COLUMN delivered_at TYPE TIMESTAMPTZ
USING delivered_at AT TIME ZONE 'Asia/Singapore';
-- This declares "the stored values ARE Singapore time" and converts to
-- TIMESTAMPTZ (which PostgreSQL stores as UTC internally).
-- A 14:00 Singapore value becomes 06:00 UTC in the new column.

-- Step 3: Verify the migration was correct by sampling rows:
SELECT
    id,
    delivered_at,                                                    -- TIMESTAMPTZ
    delivered_at AT TIME ZONE 'Asia/Singapore' AS singapore_display,  -- Local view
    delivered_at AT TIME ZONE 'UTC' AS utc_display                    -- UTC view
FROM shipments
LIMIT 10;
-- Verify: the singapore_display column shows the original local times.
-- The UTC display shows the converted UTC values.

-- Step 4: Set the database-level default timezone (in postgresql.conf):
-- timezone = 'UTC'
-- This ensures all new connections interpret ambiguous inputs as UTC.
-- Log the change, restart PostgreSQL, verify.

-- Step 5: Update application code to always send timestamps with
-- explicit UTC offset or use parametrized queries with time.Time (UTC).
```

## Diagnosing Timezone Problems in Production

```sql
-- Audit 1: Find all TIMESTAMP (without timezone) columns in the schema
SELECT
    table_name,
    column_name,
    data_type,
    column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND data_type = 'timestamp without time zone'  -- The problematic type
ORDER BY table_name, column_name;
-- Every row returned is a potential timezone bug.
-- 'timestamp with time zone' (TIMESTAMPTZ) is safe.

-- Audit 2: Check the current server timezone
SHOW timezone;
-- Should return 'UTC'. If it returns a local timezone, timestamps
-- inserted without explicit offset are being stored in local time.

-- Audit 3: Check for DST ambiguity in historical data
-- Find the DST transition window for a specific timezone and check for
-- duplicate or missing timestamps in that window:
SELECT
    COUNT(*) AS event_count,
    DATE_TRUNC('hour', event_timestamp) AS hour_bucket
FROM events
WHERE event_timestamp BETWEEN '2025-11-02 01:00:00' AND '2025-11-02 02:00:00'
GROUP BY hour_bucket
ORDER BY hour_bucket;
-- With TIMESTAMP + DST: you might see double counts in one bucket
-- because two different wall-clock 01:xx AM moments were stored identically.
-- With TIMESTAMPTZ: clean counts, no ambiguity.

-- Audit 4: Detect likely timezone-offset errors in timestamps
-- (data that makes no business sense given expected hours of operation):
SELECT
    id,
    created_at,
    EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Singapore') AS sg_hour
FROM shipments
WHERE EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Singapore')
      BETWEEN 2 AND 5  -- Orders created 2-5 AM Singapore time are suspicious
  AND created_at > '2024-01-01'
ORDER BY created_at
LIMIT 20;
-- If many orders appear at 2-5 AM Singapore time, they might actually be
-- orders created at normal business hours that are stored in the wrong timezone.
```

```
              Get it right before migrating.

The Absolute Rule:
  Every timestamp in the database MUST be UTC.
  Timezone conversion is a display concern, not a storage concern.
  TIMESTAMPTZ enforces this at the type level.
  TIMESTAMP does not. Use TIMESTAMPTZ. Always.

```

## Key Takeaways — The Principles to Carry Forward

The timezone-naive timestamp bug teaches a lesson that operates at a deeper level than "use the right data type." It teaches the principle of **representation independence** — the idea that stored data should carry enough information to be unambiguously interpreted regardless of the context in which it is later read. A `TIMESTAMP` value fails this principle because its meaning depends on the context (the server timezone) that is not stored alongside the value. A `TIMESTAMPTZ` value satisfies it because the stored UTC microseconds encode a unique, unambiguous position on the universal timeline.

The discipline of "store in UTC, display in local time" is not merely a recommendation — it is the only design that maintains representation independence across server migrations, timezone changes, DST transitions, and global user populations. UTC is the universal reference frame for time. Every other timezone is a presentation of UTC. The database is storage, not a presentation layer, so it should hold the universal representation and let the presentation layer handle the local conversion.

The practical impact of this principle in code is straightforward: every timestamp value that enters the database must be in UTC, either via `time.Now().UTC()` in Go, via explicit `+00` offset in SQL strings, or via a session-level `SET timezone = 'UTC'` guarantee. Every timestamp that leaves the database for display must be converted to the user's timezone in application code, not in the database query. The database is a UTC archive. The application is a timezone-aware display layer. These concerns must never be mixed.

There is one final principle worth stating explicitly: `TIMESTAMP` is not always wrong. For data that represents "wall clock time in a known, fixed local context" — for example, a schedule for a specific location that will never need to be compared to times in other timezones — `TIMESTAMP` can be appropriate. A "store opens at 09:00" fact for a specific store might legitimately use `TIME` without timezone because the store has one location and one timezone that never changes. But for any event timestamp — `created_at`, `updated_at`, `completed_at`, `delivered_at` — any timestamp that records when something happened in the real world must be `TIMESTAMPTZ`. Because something happening in the real world happens at a specific instant on the universal timeline, and that instant must be preserved exactly, forever, regardless of where the data is later read.
