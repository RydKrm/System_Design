# Case Study 03 — The Polymorphic Association Without an Index

---

## The Setup — The Comment Box That Slows Everything Down

A social platform is growing quickly. It has posts, videos, photos, and products — all of which users can comment on. The engineering team needs to build a comment system. The obvious, flexible design is to make comments "polymorphic": rather than having separate `post_comments`, `video_comments`, `photo_comments`, and `product_comments` tables, build one universal `comments` table that can point to any entity type. This is a common, well-understood pattern — Ruby on Rails has built-in support for it, and virtually every ORM has some equivalent facility.

The schema looks like this:

```sql
CREATE TABLE comments (
    id               BIGSERIAL PRIMARY KEY,
    commentable_type VARCHAR(50)  NOT NULL,  -- 'Post', 'Video', 'Photo', 'Product'
    commentable_id   BIGINT       NOT NULL,  -- The ID of the target entity
    user_id          BIGINT       NOT NULL REFERENCES users(id),
    body             TEXT         NOT NULL,
    created_at       TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- The developer adds an index — they know IDs need indexes:
CREATE INDEX idx_comments_commentable_id ON comments (commentable_id);
```

The index is there. The developer is confident. The code ships. It works perfectly in development and staging, where the `comments` table has perhaps 50,000 rows. Months pass. The platform grows. The `comments` table now has 20 million rows — comments on posts, videos, photos, and products all mixed together. The application runs a query to load comments for a specific post:

```sql
SELECT * FROM comments
WHERE commentable_type = 'Post'
  AND commentable_id = 12345
ORDER BY created_at DESC
LIMIT 50;
```

This query is now taking 800 milliseconds. Users notice the comment section is slow to load. An engineer runs `EXPLAIN ANALYZE` and stares at the output in disbelief — the query is performing a bitmap index scan on `idx_comments_commentable_id`, finding 5,000 rows with `commentable_id = 12345` (because ID 12345 exists in multiple entity types — Post #12345, Video #12345, Photo #12345, Product #12345 all exist and all have comments), and then filtering those 5,000 rows down to the ~180 comments that actually belong to the Post type. The index helped with the ID lookup, but it returned a result set that is 28 times larger than what the query needs, and every one of those extra rows had to be fetched from the heap and discarded. The index was designed for only half of the query's filtering condition.

---

## Understanding Polymorphic Associations — The Two-Column Pointer

A polymorphic association is a way of expressing a relationship from one table to rows in multiple different tables, without knowing at schema design time which specific table will be referenced. Instead of a single foreign key to a specific table (like `post_id BIGINT REFERENCES posts(id)`), a polymorphic association uses two columns working together:

- A **type column** (`commentable_type`) that stores a string identifying which table the referenced row lives in — for example `'Post'`, `'Video'`, or `'Product'`.
- An **ID column** (`commentable_id`) that stores the primary key of the referenced row within that table.

Together, these two columns form a logical foreign key that points to a row in the table specified by the type column. To look up the actual entity, the application first reads the type to know which table to query, then uses the ID to look up the specific row.

This pattern is powerful because it requires no schema changes when new entity types are added. If the platform adds a `Story` feature, comments on stories can be stored in the same `comments` table by setting `commentable_type = 'Story'` — no new column, no migration, no application code change beyond registering the new type. This is the genuine appeal of polymorphic associations, and it explains why they are so popular in frameworks like Rails.

The problem is that this two-column logical key needs to be treated as a **composite unit** for indexing purposes, and many developers only index the ID column — the half that looks like a foreign key to them — while ignoring the type column, the half that makes the ID meaningful within a specific table.

```
How Polymorphic IDs Overlap Across Types — Why ID-Only Index Fails:
======================================================================

  comments table (20 million rows):

  id   | commentable_type | commentable_id | user_id | body
  -----+------------------+----------------+---------+-----
   101 | Post             | 12345          |   55    | "Great post!"
   102 | Video            | 12345          |   66    | "Love this video!"
   103 | Photo            | 12345          |   77    | "Beautiful shot!"
   104 | Product          | 12345          |   88    | "Works great!"
   105 | Post             | 12345          |   99    | "I agree!"
   ...

  IDs are independent per entity type. Post #12345, Video #12345,
  Photo #12345, and Product #12345 all exist simultaneously and independently.
  It is entirely normal for each entity type to have used the same ID number
  (they each have their own auto-increment sequence).

  Index on (commentable_id) only:
  idx_comments_commentable_id:
  +----------------+---------------------+
  | commentable_id | row locations       |
  +----------------+---------------------+
  | ...            | ...                 |
  | 12345          | rows 101,102,103,104,105,... (ALL types combined!) |
  | 12346          | ...                 |
  +----------------+---------------------+

  Query: WHERE commentable_type='Post' AND commentable_id=12345
  Step 1: Index lookup for commentable_id=12345
          -> Returns ALL rows with id=12345 regardless of type
          -> Might return 5,000 rows (1,250 per type * 4 types)
  Step 2: Heap fetch for all 5,000 rows (disk reads!)
  Step 3: Filter by commentable_type='Post' in memory
          -> Keeps ~1,250 rows. Discards 3,750 rows.
          -> 3,750 unnecessary heap fetches = pure waste.

  Composite index on (commentable_type, commentable_id):
  idx_comments_polymorphic:
  +------------------+----------------+---------------------+
  | commentable_type | commentable_id | row locations       |
  +------------------+----------------+---------------------+
  | Photo            | 12344          | ...                 |
  | Photo            | 12345          | rows 103            |
  | Photo            | 12346          | ...                 |
  | Post             | 12344          | ...                 |
  | Post             | 12345          | rows 101,105,...    |  <- DIRECT!
  | Post             | 12346          | ...                 |
  | Product          | 12345          | rows 104            |
  | Video            | 12345          | rows 102            |
  +------------------+----------------+---------------------+

  Query: WHERE commentable_type='Post' AND commentable_id=12345
  Step 1: Composite index lookup: type='Post' AND id=12345
          -> Returns ONLY Post comments with id=12345
          -> Returns exactly ~1,250 rows. Zero waste.
  Step 2: Heap fetch for 1,250 rows (only what we need)
  Step 3: No filter needed — index already returned the right rows.

  Result: 4x fewer heap fetches. 4x faster. Grows linearly with data.
======================================================================
```

## Why the Bug Is Invisible at Small Scale

The polymorphic association indexing bug has the same invisibility property as many of the other concurrency and schema bugs in this series: it is completely undetectable on small datasets and becomes catastrophically obvious on large ones. The mathematical reason is precise and worth understanding.

At small scale — say, 50,000 total comments with 10,000 unique entity IDs — even a full table scan of all rows with `commentable_id = 12345` might return only 5 rows (because ID 12345 has only been commented on a handful of times across all types). The filter from 5 rows to 1–2 Post comments is trivial. The query completes in 1 millisecond.

At large scale — 20 million comments with the same 10,000 unique entity IDs — ID 12345 might have accumulated 5,000 comments across all four entity types. The heap fetch of 5,000 rows before type-filtering is expensive. And this problem scales with the total number of comments per entity ID, not with any configuration or hardware upgrade. As popular entities accumulate more comments, the index-only-on-ID approach grows slower at a rate proportional to total comments per entity, regardless of how powerful the database server is.

```
Performance Degradation Over Time:
======================================================================

  Comments per popular entity  | ID-only index time | Composite index time
  ----------------------------|--------------------|--------------------
  100 total (25 per type)     | ~1 ms              | ~0.5 ms
  1,000 total (250 per type)  | ~5 ms              | ~0.8 ms
  5,000 total (1250 per type) | ~25 ms             | ~1.5 ms
  10,000 total (2500 per type)| ~80 ms             | ~2.0 ms
  50,000 total (12500/type)   | ~400 ms            | ~3.0 ms
  100,000 total (25000/type)  | ~800 ms            | ~4.0 ms

  ID-only index: grows linearly with comments per entity ID.
  Composite index: nearly flat — directly seeks the right rows.

  The performance gap is not fixed — it WIDENS as the system grows.
  What is 5ms at launch is 800ms at maturity. What is 800ms at maturity
  will be 8,000ms (8 seconds) when the platform is 10x its current size.
  The composite index stays at ~4ms regardless.
======================================================================
```

## The Exact Query Plan — Reading EXPLAIN ANALYZE Output

Understanding how to read the query plan is the skill that allows engineers to diagnose this problem quickly. When you run `EXPLAIN (ANALYZE, BUFFERS)` on the slow query, you will see output like this:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM comments
WHERE commentable_type = 'Post'
  AND commentable_id = 12345
ORDER BY created_at DESC
LIMIT 50;
```

The output with the wrong index (ID-only):
```
Limit  (cost=5234.12..5234.24 rows=50 width=112)
        (actual time=812.45..812.48 rows=50 loops=1)
  Buffers: shared hit=4221 read=892
  ->  Sort  (cost=5234.12..5237.25 rows=1252 width=112)
            (actual time=812.40..812.41 rows=50 loops=1)
        Sort Key: created_at DESC
        Sort Method: top-N heapsort  Memory: 37kB
        ->  Bitmap Heap Scan on comments
                (cost=78.12..5198.44 rows=1252 width=112)
                (actual time=4.22..798.33 rows=1247 loops=1)
              Recheck Cond: (commentable_id = 12345)    <- ID ONLY
              Filter: ((commentable_type)::text = 'Post')  <- TYPE IS A FILTER, NOT SEEK
              Rows Removed by Filter: 3753              <- 3753 WASTED HEAP READS
              Buffers: shared hit=4221 read=892
              ->  Bitmap Index Scan on idx_comments_commentable_id
                    (cost=0.00..77.81 rows=5000 width=0)
                    (actual time=3.89..3.89 rows=5000 loops=1)
                  Index Cond: (commentable_id = 12345)
Planning Time: 0.18 ms
Execution Time: 812.58 ms

-- KEY SIGNALS OF THE BUG:
-- "Filter: (commentable_type = 'Post')" with "Rows Removed by Filter: 3753"
-- The type column appears as a FILTER (post-scan elimination)
-- rather than as an Index Cond (pre-scan selection).
-- 3753 rows were fetched from the heap and then thrown away.
-- This is the precise diagnostic signature of the polymorphic index bug.
```

After adding the composite index, the same query produces:
```
Limit  (cost=0.56..12.45 rows=50 width=112)
        (actual time=0.82..1.23 rows=50 loops=1)
  Buffers: shared hit=57 read=3
  ->  Index Scan using idx_comments_polymorphic on comments
        (cost=0.56..297.34 rows=1252 width=112)
        (actual time=0.79..1.19 rows=50 loops=1)
        Index Cond: ((commentable_type = 'Post')   <- TYPE IS NOW INDEX COND
                 AND (commentable_id = 12345))      <- BOTH CONDITIONS IN INDEX
        Buffers: shared hit=57 read=3
Planning Time: 0.12 ms
Execution Time: 1.41 ms

-- KEY SIGNALS OF THE FIX:
-- "Index Cond: (commentable_type = 'Post') AND (commentable_id = 12345)"
-- BOTH conditions are served by the index — zero heap reads for discarded rows.
-- Buffer reads dropped from 5113 to 60. Execution time from 812ms to 1.4ms.
-- 578x speedup from a single index change.
```

The two lines to always check in EXPLAIN output for polymorphic association queries are `Rows Removed by Filter` and whether `commentable_type` appears in `Index Cond` or in `Filter`. If the type appears in `Filter` rather than `Index Cond`, you have the polymorphic index bug.

## The Fix — A Composite Index in the Correct Column Order

The fix is a single SQL statement, and it is one of the highest-ratio effort-to-impact changes in database optimization. One line of SQL that can take a query from 800ms to 1.4ms — a 578x improvement — and that improvement persists and scales as the table grows:

```sql
-- The fix: composite index with type FIRST, then ID
-- (type must come first because it is the higher-level discriminator)
CREATE INDEX CONCURRENTLY idx_comments_polymorphic
ON comments (commentable_type, commentable_id);

-- After creating the new index, you can DROP the old ineffective one:
DROP INDEX CONCURRENTLY idx_comments_commentable_id;

-- Why type comes before id in the composite index?
-- B-tree indexes are sorted left-to-right. Queries that filter on the
-- leftmost column can use the index for range scans.
-- "WHERE commentable_type = 'Post' AND commentable_id = 12345":
--   -> The index is sorted by type first, then by id within each type.
--   -> PostgreSQL seeks directly to the 'Post' section of the index.
--   -> Within the 'Post' section, it seeks directly to id=12345.
--   -> Returns exactly the rows for Post #12345. Zero waste.
--
-- If id came first: "WHERE commentable_id = 12345" could use the index,
-- but then filtering by type requires scanning all rows with that id
-- across all types. The same bug, slightly mitigated but not fixed.
```

The `CONCURRENTLY` option is critical for production use. Without it, `CREATE INDEX` holds a lock that prevents writes to the `comments` table for the duration of the index build. `CREATE INDEX CONCURRENTLY` builds the index without blocking writes — it takes slightly longer to build, but the application continues operating normally throughout. For a 20-million-row table, the build might take 5–15 minutes. With `CONCURRENTLY`, that is 5–15 minutes of slightly elevated I/O with no application impact. Without `CONCURRENTLY`, it is 5–15 minutes of the `comments` table being locked for writes.

## Additional Optimization — Including Frequently Queried Columns

For the specific query pattern of loading comments for a specific entity — which almost always requires `user_id`, `body`, and `created_at` — a **covering index** eliminates even the heap fetch entirely:

```sql
-- Covering index: includes all columns the query SELECT needs
-- This allows PostgreSQL to satisfy the query entirely from the index,
-- without touching the table's main heap storage at all.
CREATE INDEX CONCURRENTLY idx_comments_polymorphic_covering
ON comments (commentable_type, commentable_id, created_at DESC)
INCLUDE (user_id, body);

-- The INCLUDE columns are stored in the index leaf pages but not in
-- the internal B-tree structure. They are not searchable but are
-- accessible without a heap fetch.

-- Query that uses the covering index (zero heap reads):
SELECT user_id, body, created_at
FROM comments
WHERE commentable_type = 'Post'
  AND commentable_id = 12345
ORDER BY created_at DESC
LIMIT 50;
-- Execution plan: Index Only Scan (no heap reads at all)
-- Fastest possible query for this pattern.
```

The trade-off with covering indexes is their size — they store additional column data in the index, making the index larger. For a high-frequency query path (every page load that shows comments), this trade-off is almost always worth it.

## The Partial Index Alternative — When Types Have Vastly Different Volumes

If one entity type has dramatically more comments than others — for example, Posts have 90% of all comments while Photos have 5% — you can create **partial indexes** per entity type. Each partial index is smaller and more selective than a single composite index spanning all types:

```sql
-- Partial indexes per type — useful when type distribution is highly skewed:
CREATE INDEX CONCURRENTLY idx_comments_post
ON comments (commentable_id, created_at DESC)
WHERE commentable_type = 'Post';

CREATE INDEX CONCURRENTLY idx_comments_video
ON comments (commentable_id, created_at DESC)
WHERE commentable_type = 'Video';

CREATE INDEX CONCURRENTLY idx_comments_photo
ON comments (commentable_id, created_at DESC)
WHERE commentable_type = 'Photo';

-- Each partial index only contains rows of its specific type.
-- For Post comments (90% of data): 18M rows indexed in this partial index.
-- For Photo comments (5% of data): 1M rows in the photo partial index.
-- Each index is smaller and more cache-friendly than one composite index.

-- PostgreSQL will automatically use the correct partial index:
-- WHERE commentable_type = 'Post' AND commentable_id = X
-- -> Uses idx_comments_post (only Post rows, highly selective)
-- WHERE commentable_type = 'Photo' AND commentable_id = X
-- -> Uses idx_comments_photo (only Photo rows, even more selective)
```

Partial indexes are most valuable when: different entity types have very different comment volumes, you need to add type-specific sort columns (like `ORDER BY created_at` which you can encode in the partial index), or you want to exclude rare types from index maintenance overhead entirely.

## The Deeper Solution — Separate Tables Per Entity Type

The composite index fix is fast, simple, and immediately effective. But it is worth stepping back to consider whether the polymorphic association is the right design for this system at all. The composite index fixes the query performance, but it does not fix the schema design limitation: the `comments` table still cannot have proper foreign key constraints, the database cannot enforce referential integrity between a comment and the post it belongs to, and all comments for all entity types must share the same schema.

For systems where comments on different entity types genuinely have different shapes — for example, product reviews have a `star_rating` and a `verified_purchase` flag that post comments do not have — separate tables are the more correct long-term design:

```sql
-- Separate tables: maximum type safety and referential integrity
CREATE TABLE post_comments (
    id          BIGSERIAL PRIMARY KEY,
    post_id     BIGINT      NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    user_id     BIGINT      NOT NULL REFERENCES users(id),
    body        TEXT        NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON post_comments (post_id, created_at DESC);
-- This index is perfectly efficient by design. No type column needed.
-- post_id IS the complete reference. No polymorphism, no wasted reads.

CREATE TABLE product_reviews (
    id                BIGSERIAL PRIMARY KEY,
    product_id        BIGINT      NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    user_id           BIGINT      NOT NULL REFERENCES users(id),
    body              TEXT        NOT NULL,
    star_rating       SMALLINT    NOT NULL CHECK (star_rating BETWEEN 1 AND 5),
    verified_purchase BOOLEAN     NOT NULL DEFAULT false,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON product_reviews (product_id, created_at DESC);

-- Typed foreign key: the database enforces that post_comments.post_id
-- must reference a valid post. This constraint is impossible with polymorphism.
-- If a post is deleted: ON DELETE CASCADE automatically cleans up its comments.
-- With polymorphic associations: application code must handle this cleanup.
```

The choice between fixing the composite index on the polymorphic table versus migrating to separate tables depends on several factors:

```
Polymorphic Association vs. Separate Tables — The Decision:
======================================================================

  Use Polymorphic Association (with composite index) WHEN:
  [ ] All entity types need exactly the same comment fields
  [ ] New entity types are added frequently (no schema change needed)
  [ ] Cross-type comment queries are common (e.g., "all recent comments")
  [ ] Referential integrity loss is acceptable (no typed FK constraints)
  [ ] Team uses an ORM with built-in polymorphic support (Rails, etc.)

  Use Separate Tables WHEN:
  [ ] Different entity types need different comment fields
      (reviews need star_rating, posts do not)
  [ ] Referential integrity is important (DB-enforced FK + CASCADE)
  [ ] Different types have different access patterns or volume
  [ ] The number of entity types is fixed and known
  [ ] You want the query planner to have accurate per-type statistics

  Always (regardless of choice):
  [x] COMPOSITE index on (commentable_type, commentable_id) if polymorphic
  [x] type column MUST come FIRST in the composite index
  [x] Use INCLUDE columns for covering indexes on hot query paths
  [x] Verify with EXPLAIN ANALYZE that type appears in Index Cond, not Filter
======================================================================
```

## Applying the Pattern to Other Polymorphic Tables — Likes, Notifications, Audit Logs

The polymorphic association pattern appears in many tables beyond comments. Every system that applies a single behavior to multiple entity types — likes, reactions, notifications, audit logs, activity feeds, tags, attachments — faces the same indexing challenge. The fix is always the same: composite index with type first, ID second.

```sql
-- Likes/reactions table (same pattern as comments):
CREATE TABLE likes (
    id              BIGSERIAL PRIMARY KEY,
    likeable_type   TEXT    NOT NULL,   -- 'Post', 'Comment', 'Photo', etc.
    likeable_id     BIGINT  NOT NULL,
    user_id         BIGINT  NOT NULL REFERENCES users(id),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (likeable_type, likeable_id, user_id)  -- Prevent duplicate likes
);
-- COMPOSITE index is mandatory:
CREATE INDEX idx_likes_polymorphic ON likes (likeable_type, likeable_id);

-- Notifications table:
CREATE TABLE notifications (
    id              BIGSERIAL PRIMARY KEY,
    notifiable_type TEXT    NOT NULL,   -- 'User', 'Company', etc.
    notifiable_id   BIGINT  NOT NULL,
    message         TEXT    NOT NULL,
    is_read         BOOLEAN NOT NULL DEFAULT false,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
-- Composite index for "load notifications for this user":
CREATE INDEX idx_notifications_polymorphic
ON notifications (notifiable_type, notifiable_id, created_at DESC);

-- Audit log table:
CREATE TABLE audit_logs (
    id              BIGSERIAL PRIMARY KEY,
    auditable_type  TEXT    NOT NULL,
    auditable_id    BIGINT  NOT NULL,
    action          TEXT    NOT NULL,   -- 'create', 'update', 'delete'
    changed_fields  JSONB,
    performed_by    BIGINT  REFERENCES users(id),
    performed_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
-- Composite index for "show audit history for this entity":
CREATE INDEX idx_audit_polymorphic
ON audit_logs (auditable_type, auditable_id, performed_at DESC);

-- Attachments table:
CREATE TABLE attachments (
    id               BIGSERIAL PRIMARY KEY,
    attachable_type  TEXT    NOT NULL,
    attachable_id    BIGINT  NOT NULL,
    filename         TEXT    NOT NULL,
    file_url         TEXT    NOT NULL,
    file_size_bytes  BIGINT,
    content_type     TEXT,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_attachments_polymorphic
ON attachments (attachable_type, attachable_id);
```

Every single one of these tables, if given only an index on the ID column, will exhibit the same performance degradation at scale. Every single one needs the composite index with type first. This is not a rule of thumb — it is a mathematical necessity given how B-tree indexes work and how polymorphic data is structured.

## Production Audit — Checking Your Existing Polymorphic Tables

```sql
-- Find all tables with the polymorphic pattern (type + id column pairs)
-- that might be missing the composite index:
SELECT
    t.table_name,
    type_col.column_name  AS type_column,
    id_col.column_name    AS id_column
FROM information_schema.tables t
JOIN information_schema.columns type_col
    ON type_col.table_name = t.table_name
    AND type_col.column_name LIKE '%_type'
JOIN information_schema.columns id_col
    ON id_col.table_name = t.table_name
    AND id_col.column_name = REPLACE(type_col.column_name, '_type', '_id')
WHERE t.table_schema = 'public'
  AND t.table_type = 'BASE TABLE'
ORDER BY t.table_name;

-- For each table found, check if the composite index exists:
SELECT
    t.relname                               AS table_name,
    i.relname                               AS index_name,
    array_agg(a.attname ORDER BY ix.indnatts) AS indexed_columns
FROM pg_class t
JOIN pg_index ix ON ix.indrelid = t.oid
JOIN pg_class i  ON i.oid = ix.indexrelid
JOIN pg_attribute a ON a.attrelid = t.oid AND a.attnum = ANY(ix.indkey)
WHERE t.relname IN ('comments', 'likes', 'notifications', 'audit_logs')
  AND t.relkind = 'r'
GROUP BY t.relname, i.relname
ORDER BY t.relname, i.relname;
-- Check the output: does any index include BOTH the type AND id columns?
-- If you only see indexes on the id column alone, you have the bug.

-- Confirm the bug is causing slow queries — check for high filter removal:
SELECT
    query,
    calls,
    mean_exec_time,
    total_exec_time,
    rows / calls AS avg_rows_per_call
FROM pg_stat_statements
WHERE query ILIKE '%commentable_type%'
   OR query ILIKE '%likeable_type%'
   OR query ILIKE '%notifiable_type%'
ORDER BY mean_exec_time DESC
LIMIT 10;
-- Queries with high mean_exec_time and the type column present are the victims.

-- After adding the composite index, verify it is being used:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM comments
WHERE commentable_type = 'Post' AND commentable_id = 12345
ORDER BY created_at DESC LIMIT 50;
-- Look for: "Index Cond: (commentable_type = 'Post') AND (commentable_id = 12345)"
-- NOT: "Filter: (commentable_type = 'Post')" with "Rows Removed by Filter"
```

## The Complete Mental Model

```
THE POLYMORPHIC ASSOCIATION WITHOUT AN INDEX — COMPLETE MENTAL MODEL:
======================================================================

The Structure:
  comments: id | commentable_type | commentable_id | user_id | body
  (Also: likes, notifications, audit_logs, attachments, tags, etc.)

Why IDs Overlap Across Types:
  Post #12345, Video #12345, Photo #12345, Product #12345 — all exist.
  Each entity type has its own independent ID sequence.
  commentable_id=12345 is NOT unique — it refers to different entities
  in different tables depending on commentable_type.

The Wrong Index:
  INDEX ON (commentable_id)              <- ID ONLY
  Query: WHERE type='Post' AND id=12345
  Step 1: Index finds ALL rows with id=12345 (all types mixed)
  Step 2: Heap fetch ALL those rows (disk reads for ALL types)
  Step 3: Filter to type='Post' in memory (discard other types)
  Waste: (total_types - 1) / total_types * heap_fetches are discarded.
  With 4 types: 75% of heap reads are wasted. Grows with data.

The Correct Index:
  INDEX ON (commentable_type, commentable_id)   <- COMPOSITE, TYPE FIRST
  Query: WHERE type='Post' AND id=12345
  Step 1: Index seeks directly to type='Post' section
  Step 2: Within that section, seeks directly to id=12345
  Step 3: Returns only Post comments with that ID. Zero waste.
  No filtering step. No wasted heap reads. Scales linearly with result size.

The Diagnostic Signature in EXPLAIN ANALYZE:
  BUG:  Filter: (commentable_type = 'Post')
        Rows Removed by Filter: [large number]   <- WASTED READS
  FIX:  Index Cond: ((commentable_type = 'Post') AND (commentable_id = 12345))
        Rows Removed by Filter: 0                <- PERFECT

The Index Column Order Rule:
  Type column MUST come FIRST in the composite index.
  Why: Puts the higher-cardinality discriminator first.
       Allows index range scans within a single type.
       Queries filtering by type only (no id) can also use the index.
  Wrong order: INDEX ON (commentable_id, commentable_type)
               Works for equality queries but forces a scan when
               type distribution is skewed within the id range.
  Correct order: INDEX ON (commentable_type, commentable_id)
                 Scans only the section for the requested type.

Covering Index for Maximum Performance:
  INDEX ON (commentable_type, commentable_id, created_at DESC)
  INCLUDE (user_id, body)
  -> Satisfies SELECT user_id, body, created_at ... ORDER BY created_at
     WITHOUT touching the heap (Index Only Scan)
  -> Fastest possible execution for the comment-loading query.

The Universal Rule:
  ANY table with a (X_type, X_id) polymorphic pair MUST have
  a composite index: (X_type, X_id) with type FIRST.
  No exceptions. No "I'll add it later." Add it on table creation.
  The bug is invisible at small scale and catastrophic at large scale.
  When you see the table being created, the composite index goes in
  at the same time. Always.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

The polymorphic association indexing bug is among the most common and most easily prevented performance problems in production database systems. It is common because the pattern — storing a type string alongside an ID to create a flexible reference — is genuinely useful and appears in every application that has implemented likes, comments, notifications, or audit logs. It is easily prevented because the fix requires exactly one line of SQL and costs almost nothing in development time.

The core concept to internalize is that a polymorphic association is a **composite key** — the type and the ID together form the complete reference, and neither column is meaningful without the other. An index on the ID column alone is an index on half of the key. It helps with lookups, but it returns an over-broad result set that the database must then filter down using the type condition as a post-scan predicate rather than as an index-time selector. The result is heap fetches for every comment by every entity type with that ID, with all but the target type's comments being discarded after being fetched from disk.

The rule is absolute and has no exceptions in practice: every polymorphic table must have a composite index with the type column first. This index should be created at the same time as the table — not added later when performance complaints arrive. It should be verified with `EXPLAIN ANALYZE` after creation to confirm that the type column appears in `Index Cond` rather than in `Filter`. And for high-traffic query paths, a covering index with `INCLUDE` columns should be considered to eliminate heap fetches entirely.

Polymorphic associations always need a composite index that includes the type column. The type column must come first. Never just the ID.
