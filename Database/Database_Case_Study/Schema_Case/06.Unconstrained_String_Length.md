# Case Study 06 — Unconstrained String Length

---

## The Setup — The Username That Filled the Disk

A developer bootstraps a new SaaS application. Registration is the first feature. The schema is written quickly, with the focus on getting something working:

```sql
CREATE TABLE users (
    id         BIGSERIAL PRIMARY KEY,
    email      VARCHAR,     -- no limit
    name       VARCHAR,     -- no limit
    bio        VARCHAR,     -- no limit
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

The application validates inputs in the API layer before they reach the database: names must be between 2 and 100 characters, bios must be under 500 characters. The developer reasons that since the application validates first, there is no need for database-level constraints. The application is the first line of defense, and it is working correctly in testing. The schema ships.

Eight months later, a security researcher submits a bug report. The API's authentication middleware has a subtle flaw: under certain conditions involving a malformed JWT token, the middleware passes the request through to the handler without validating the body. The attacker crafts a request that bypasses the name length validator. The name field contains 10 megabytes of the letter "A." The database accepts it without complaint — `VARCHAR` with no length limit stores exactly what it receives. The row is now 10 MB. The index on the `name` column now contains a 10 MB entry. The B-tree index on a column that was supposed to contain short strings is now handling an entry as large as a full PostgreSQL page, which triggers special handling and causes index bloat.

The attacker runs the script 1,000 times before the team detects it. The `users` table is now 10 GB larger than it should be. The name index is corrupted with outsized entries. Queries on the users table are slow because the table pages are enormous and the index can no longer efficiently cache in RAM. Cleaning up requires a full table rebuild. The incident costs the team two days of engineering time, one production maintenance window, and a difficult conversation with the CISO.

The fix was one line of SQL that should have been written eight months ago.

## Understanding PostgreSQL String Storage — What Actually Happens

Before explaining why the lack of a length limit is dangerous, it is worth understanding exactly how PostgreSQL stores variable-length strings at the physical level. This understanding is what makes the performance and storage consequences concrete rather than theoretical.

PostgreSQL has three string types that are often confused with each other:

**`CHAR(n)` or `CHARACTER(n)`:** Fixed-length strings, always padded to exactly n characters with trailing spaces. Virtually never the right choice in modern applications — it wastes space for shorter strings, adds comparison complexity because of padding, and has no real advantage over `VARCHAR(n)` in PostgreSQL. Only useful for fixed-format codes where length is always identical (ISO country codes, currency codes).

**`VARCHAR(n)` or `CHARACTER VARYING(n)`:** Variable-length strings with a maximum of n characters (not bytes — characters in PostgreSQL are measured in characters, so a 4-byte UTF-8 character counts as one character). This is the correct type for most string data with a known maximum length.

**`TEXT` or `VARCHAR` without length:** Variable-length strings with no upper limit. In PostgreSQL, `TEXT` and `VARCHAR` without a limit are internally identical — they are stored in exactly the same way, have the same performance characteristics, and are in fact the same type under the hood. The only difference between `VARCHAR(255)` and `TEXT` is that `VARCHAR(255)` has a length enforcement constraint.

```
PostgreSQL String Storage — The Physical Reality:
======================================================================

  String storage for a column defined as VARCHAR or TEXT:

  Short strings (≤ 127 bytes after compression):
  +--------+---------------+
  | 1 byte | string data   |
  | header | (inline)      |
  +--------+---------------+
  Stored inline in the row. Fast access. No overhead.

  Medium strings (128 bytes to ~2000 bytes):
  +--------+---------------+
  | 4 bytes| string data   |
  | header | (inline)      |
  +--------+---------------+
  Still inline in the row. Header grows to 4 bytes.

  Large strings (> 2000 bytes, approximately):
  PostgreSQL's TOAST (The Oversized Attribute Storage Technique) kicks in.
  The large value is compressed and/or moved to a separate TOAST table.

  +--------+-----------+     +---------------------------+
  | 4 bytes| TOAST ptr | --> | pg_toast_<table_oid>      |
  | header | (18 bytes)|     | chunk_id | chunk_seq | data|
  +--------+-----------+     +---------------------------+

  TOAST consequences:
  - The main table row now contains a small pointer (18 bytes).
  - The actual data lives in the TOAST table (separate physical file).
  - Reading a toasted column requires TWO I/O operations:
    1. Read the main table row to get the TOAST pointer.
    2. Read the TOAST table to get the actual data.
  - A query that scans 1M rows but only needs the id column STILL reads
    the TOAST table if the query planner believes it might need the value.
  - Indexes on the toasted column store the first 2712 bytes for comparison,
    causing the index to bloat with large values.

  A 10MB name value:
  - Main row: 18-byte TOAST pointer (tiny, deceptive)
  - TOAST table: ~10MB of data in multiple chunks
  - Each TOAST chunk is 2KB. 10MB = ~5000 TOAST chunks PER ROW.
  - 1000 rows × 10MB = 10GB of TOAST data + 50M TOAST chunks to scan.
  - Index on name: stores first 2712 bytes per entry. 1000 entries × 2.7KB = 2.7MB
    of index data for values that should be 2-100 bytes each.
======================================================================
```

## The Four Damage Vectors — One Unconstrained Column, Four Problems

An unconstrained string column is not merely a storage problem. It causes damage in four distinct ways, each compounding the others.

### Damage Vector One: Unbounded Storage Consumption

The most direct consequence is the one the setup described: without a length constraint, a single malicious or buggy input can consume arbitrary amounts of storage. A 10MB string takes 10MB. A 100MB string takes 100MB. A 1GB string takes 1GB. There is no database-level protection. If the application's validation layer has a bug, a race condition, or is bypassed entirely (through a direct API call, a forgotten endpoint, or a dependency vulnerability), the database will accept whatever arrives.

Unlike many resource exhaustion attacks, which require sustained sustained traffic, a storage exhaustion attack against an unconstrained column can succeed with a single request. One carefully crafted row with a 10GB "name" can fill the disk entirely, crash the database, and cause a complete outage — from a single HTTP request.

### Damage Vector Two: Index Bloat and Performance Degradation

Indexes are built on column values. When a column stores a 10MB value, the index must handle that 10MB value as an index entry. PostgreSQL's B-tree indexes truncate very long values for comparison purposes — they only store the first 2,712 bytes (the "index deduplication limit" for comparison) — but the presence of these oversized values bloats the index significantly compared to normal short-string entries, makes cache efficiency terrible (one index entry now takes many memory pages), and forces the query planner to adopt different, often slower strategies for queries that touch the indexed column.

### Damage Vector Three: TOAST Table Thrashing

As described above, strings longer than approximately 2,000 bytes trigger TOAST storage, which moves the data off the main table into a secondary table. TOAST storage is transparent to SQL — queries still work — but it adds a mandatory second I/O operation for every row that has a toasted column. When a table has thousands of rows with 10MB names, every query that touches the `users` table — even a query that only needs `id` and `email` — incurs TOAST overhead because the planner may need to dereference the TOAST pointer for filtering purposes. The TOAST table itself becomes enormous, with millions of 2KB chunks that AUTOVACUUM must maintain.

### Damage Vector Four: Cascading Application Memory Consumption

When the application reads user records from the database, it allocates memory to hold the returned data. A query that returns 100 user records normally allocates perhaps 100 × 500 bytes = 50KB of memory. A query that returns 100 user records where each has a 10MB name allocates 100 × 10MB = 1GB of memory, potentially exhausting the application's heap and causing an out-of-memory crash. The database-level storage problem becomes an application-level availability problem the moment any code attempts to read the bloated records.

```
The Four Damage Vectors Cascading:
======================================================================

  [Attack / Bug]: 10MB string submitted as 'name'

  Damage Vector 1: STORAGE
  +---------------------------------+
  | users table: 10MB per bad row   |
  | pg_toast table: 5000 chunks     |
  | 1000 rows: 10GB wasted          |
  | Disk may fill: DB crash         |
  +---------------------------------+
              |
              v
  Damage Vector 2: INDEX BLOAT
  +---------------------------------+
  | idx_users_name grows            |
  | Each entry: 2.7KB (truncated)   |
  | 1000 entries: 2.7MB in index    |
  | Normal: 1000 entries ≈ 15KB     |
  | Index misses RAM cache          |
  | All name-based queries: slow    |
  +---------------------------------+
              |
              v
  Damage Vector 3: TOAST THRASHING
  +---------------------------------+
  | Every SELECT on users table     |
  | may dereference TOAST pointer   |
  | Each row: 2 I/Os not 1         |
  | AUTOVACUUM: 50M TOAST chunks    |
  | Continuous I/O overhead         |
  +---------------------------------+
              |
              v
  Damage Vector 4: APP MEMORY CRASH
  +---------------------------------+
  | SELECT * FROM users LIMIT 100   |
  | Returns 100 rows × 10MB each    |
  | = 1GB memory allocation         |
  | Application OOM crash           |
  | Service unavailable             |
  +---------------------------------+

  All four triggered by: one missing VARCHAR(n) constraint.
  Fix: ALTER TABLE users ALTER COLUMN name TYPE VARCHAR(100);
  Prevention cost: one line of SQL at schema design time.
  Remediation cost: two engineer-days, production maintenance window.
======================================================================
```

## The Defence Layers — Why Application Validation Alone Is Not Enough

The most common argument against database-level length constraints is: "We validate in the application layer, so we don't need the database to enforce it." This argument fails for five distinct reasons, any one of which is sufficient to refute it:

**Reason One: Validation bypass through bugs.** The entire case study opening demonstrates this. A middleware bug, a race condition in the validation pipeline, a new code path that a developer forgot to add validation to — any of these can allow invalid data to reach the database. Application code is complex and changes frequently. Database constraints are simple and change rarely. Defence in depth requires both layers.

**Reason Two: Direct database access.** Production systems are often accessed directly by DBAs, data engineers running ad-hoc queries, migration scripts, seeding scripts, and internal tools that bypass the application layer entirely. A database constraint is enforced for every access path, including direct `psql` access and manual SQL execution. An application validation rule is enforced only by application code.

**Reason Three: Multiple application codebases.** A production system typically has multiple clients: a web API, a mobile API, an internal admin panel, a CLI tool, a webhook handler, a background job processor. Each of these is a separate codebase that must independently implement the same validation rules. When those rules change, every codebase must be updated simultaneously. A database constraint is one place, one rule, enforced everywhere.

**Reason Four: Consistency across application versions.** During rolling deployments, multiple versions of the application code run simultaneously. Version 1 validates names up to 100 characters. Version 2 changes the limit to 50 characters. During the rollout, some requests go to Version 1 servers (which accept up to 100 characters) and some to Version 2 servers (which accept up to 50 characters). The database constraint represents the single, authoritative, version-independent truth about what data is valid.

**Reason Five: The database is the last line of defence.** Application code is fallible. Validation frameworks have bugs. HTTP parsers can be tricked. The database is the authoritative guardian of data integrity. If the application allows bad data through, the database should reject it. If the database also allows bad data through, there is no recovery — the corruption is permanent.

```
The Defence Layer Architecture:
======================================================================

  HTTP Request: { "name": "[10MB of 'A' characters]" }
       |
       v
  Layer 1: Network / WAF (rate limiting, payload size limit)
  -> If configured: reject requests over 1MB total body size.
  -> This is INFRASTRUCTURE-level protection.
       |
       v (bypassed if WAF not configured or limit too high)
  Layer 2: Application Framework Validation
  -> Request body parsing: check name length <= 100
  -> Schema validation (JSON Schema, struct tags, middleware)
  -> If valid: pass to handler. If invalid: return 400 Bad Request.
  -> This is APPLICATION-level protection.
       |
       v (bypassed if validator has bug, or if code path skips it)
  Layer 3: Business Logic Validation
  -> Handler code: explicit validation checks
  -> Service layer: domain rule enforcement
  -> This is DOMAIN-level protection.
       |
       v (bypassed if bug, forgotten code path, or direct DB access)
  Layer 4: Database Constraint (THE LAST LINE)
  -> VARCHAR(100): PostgreSQL enforces. No bypass possible.
  -> CHECK (LENGTH(name) >= 2): enforced at every insert/update.
  -> If violated: ERROR 22001 (string data too long). Transaction rolls back.
  -> This is DATABASE-level protection. CANNOT be bypassed.

  An attack or bug must defeat ALL FOUR LAYERS simultaneously.
  Without Layer 4 (DB constraint), defeating Layer 2 is sufficient.
  Defence in depth requires all layers. The DB layer is non-negotiable.
======================================================================
```

## The Correct Schema — Sensible Limits for Every String Column

The fix is straightforward: every `VARCHAR` or `TEXT` column must have a length constraint appropriate to its domain. The constraint should be set to the maximum value that the business domain could legitimately require — not a round number chosen arbitrarily, but a limit that reflects the actual maximum valid input for that field.

```sql
-- The correct schema — length-constrained and CHECK-constrained:
CREATE TABLE users (
    id              BIGSERIAL       PRIMARY KEY,

    -- Email: RFC 5321 defines max 254 characters total.
    email           VARCHAR(254)    NOT NULL UNIQUE,

    -- Display name: industry convention is 50-100 characters.
    -- 100 gives room for longer cultural names without being unbounded.
    name            VARCHAR(100)    NOT NULL
                    CHECK (LENGTH(TRIM(name)) >= 2),  -- Minimum length

    -- Username: typically alphanumeric, shorter than display name.
    username        VARCHAR(50)     NOT NULL UNIQUE
                    CHECK (username ~ '^[a-zA-Z0-9_]{3,50}$'),  -- Pattern constraint

    -- Bio: user-supplied free text. 500 characters is generous for a bio.
    -- If truly unlimited bio is needed, use TEXT but limit at app layer.
    bio             VARCHAR(500),   -- Nullable: bio is optional

    -- Phone: E.164 format max is 15 digits + '+' = 16 characters.
    phone           VARCHAR(20),    -- Allow some formatting characters

    -- Country code: ISO 3166-1 alpha-2 is exactly 2 characters.
    country_code    CHAR(2)         CHECK (country_code ~ '^[A-Z]{2}$'),

    -- Timezone: IANA timezone names max ~40 characters ('America/Argentina/...')
    timezone        VARCHAR(50)     CHECK (timezone ~ '^[A-Za-z_/]{1,50}$'),

    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- Add constraints explicitly, not just in column definition,
-- for better error messages and easier management:
ALTER TABLE users
    ADD CONSTRAINT chk_email_format
    CHECK (email ~ '^[^@]+@[^@]+\.[^@]+$');  -- Basic email format

ALTER TABLE users
    ADD CONSTRAINT chk_name_no_leading_trailing_spaces
    CHECK (name = TRIM(name));  -- Reject names with leading/trailing whitespace

-- For tables storing content (posts, comments, descriptions):
CREATE TABLE posts (
    id          BIGSERIAL       PRIMARY KEY,
    author_id   BIGINT          NOT NULL REFERENCES users(id),
    title       VARCHAR(300)    NOT NULL CHECK (LENGTH(TRIM(title)) >= 5),
    slug        VARCHAR(300)    NOT NULL UNIQUE
                CHECK (slug ~ '^[a-z0-9-]{3,300}$'),  -- URL-safe slug
    body        TEXT            NOT NULL CHECK (LENGTH(body) >= 10),
    -- body is TEXT (unlimited) but with a minimum check.
    -- The maximum is enforced at application layer (e.g., 50000 chars).
    -- For body, a maximum DB constraint would be impractical (too strict),
    -- so application validation + WAF payload limits are the protection.
    created_at  TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
```

## Using `CHECK` Constraints for Richer Validation

Beyond simple length limits, PostgreSQL's `CHECK` constraints allow encoding business rules directly in the schema. These constraints are enforced atomically with every INSERT and UPDATE, making them the most reliable form of data validation:

```sql
-- Pattern-based constraints for format validation:
ALTER TABLE users
ADD CONSTRAINT chk_username_format
CHECK (username ~ '^[a-zA-Z0-9][a-zA-Z0-9_]{1,48}[a-zA-Z0-9]$');
-- Starts and ends with alphanumeric. Only alphanumeric and underscore in between.

-- Minimum meaningful length after trimming whitespace:
ALTER TABLE posts
ADD CONSTRAINT chk_title_meaningful
CHECK (LENGTH(TRIM(title)) >= 5);
-- Prevents "    a   " (5 spaces and one character) from passing length check.

-- Enum-like constraint for string columns with a finite set of valid values:
ALTER TABLE orders
ADD CONSTRAINT chk_status_valid
CHECK (status IN ('draft', 'pending', 'confirmed', 'shipped', 'delivered', 'cancelled'));
-- More explicit error messages than ENUM type, easier to add values later.

-- Combined minimum and maximum with content check:
ALTER TABLE products
ADD CONSTRAINT chk_sku_format
CHECK (
    LENGTH(sku) BETWEEN 3 AND 50
    AND sku = UPPER(sku)          -- Must be uppercase
    AND sku ~ '^[A-Z0-9\-]+$'    -- Only uppercase letters, digits, hyphens
    AND sku NOT LIKE '%--%--%'    -- No consecutive hyphens
);

-- Cross-column consistency constraint:
ALTER TABLE users
ADD CONSTRAINT chk_bio_requires_name
CHECK (
    (bio IS NULL)  -- No bio is always fine
    OR (name IS NOT NULL AND LENGTH(name) >= 2)  -- Bio requires a real name
);
```

## Enforcing Constraints in Go — The Correct Layered Approach

The correct implementation validates at every layer, with the database as the final, authoritative guard. In Go, this means both struct-level validation before the database call and handling the database constraint error gracefully:

```go
// Validation at the Go struct level (first layer):
type CreateUserRequest struct {
    Email    string `json:"email"    validate:"required,email,max=254"`
    Name     string `json:"name"     validate:"required,min=2,max=100"`
    Username string `json:"username" validate:"required,min=3,max=50,alphanum_"`
    Bio      string `json:"bio"      validate:"omitempty,max=500"`
}

// validate struct tags are processed by a validation library (e.g., go-playground/validator)
func ValidateCreateUser(req *CreateUserRequest) error {
    validate := validator.New()
    if err := validate.Struct(req); err != nil {
        // Return structured validation errors to the client
        var validationErrors validator.ValidationErrors
        if errors.As(err, &validationErrors) {
            msgs := make([]string, 0, len(validationErrors))
            for _, e := range validationErrors {
                msgs = append(msgs, fmt.Sprintf("%s: %s", e.Field(), e.Tag()))
            }
            return fmt.Errorf("validation failed: %s", strings.Join(msgs, ", "))
        }
        return err
    }
    return nil
}

// Database interaction with constraint error handling (last layer):
func CreateUser(db *sql.DB, req *CreateUserRequest) (*User, error) {
    // Layer 1: Validate in Go before touching the DB
    if err := ValidateCreateUser(req); err != nil {
        return nil, fmt.Errorf("invalid input: %w", err)
    }

    // Layer 2: Additional business logic checks
    // (e.g., check if username is reserved, if email domain is allowed, etc.)

    // Layer 3: Database insert — DB constraints are the final guard
    var user User
    err := db.QueryRow(`
        INSERT INTO users (email, name, username, bio)
        VALUES ($1, $2, $3, $4)
        RETURNING id, email, name, username, bio, created_at
    `,
        strings.ToLower(strings.TrimSpace(req.Email)),  // Normalize before insert
        strings.TrimSpace(req.Name),
        strings.ToLower(strings.TrimSpace(req.Username)),
        strings.TrimSpace(req.Bio),
    ).Scan(&user.ID, &user.Email, &user.Name, &user.Username, &user.Bio, &user.CreatedAt)

    if err != nil {
        // Handle PostgreSQL constraint violations gracefully:
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) {
            switch pgErr.Code {
            case "22001":  // string_data_right_truncation — value too long
                return nil, ErrInputTooLong
            case "23505":  // unique_violation — email or username already exists
                if strings.Contains(pgErr.ConstraintName, "email") {
                    return nil, ErrEmailAlreadyExists
                }
                if strings.Contains(pgErr.ConstraintName, "username") {
                    return nil, ErrUsernameAlreadyExists
                }
                return nil, ErrAlreadyExists
            case "23514":  // check_violation — CHECK constraint failed
                return nil, fmt.Errorf("data validation failed: %s", pgErr.ConstraintName)
            }
        }
        return nil, fmt.Errorf("creating user: %w", err)
    }

    return &user, nil
}
```

The PostgreSQL error code `22001` (`string_data_right_truncation`) is what you receive when a value exceeds a `VARCHAR(n)` limit. Handling it explicitly — rather than letting it bubble up as a generic database error — allows the API to return a meaningful `400 Bad Request` response to the client, even if the validation bypass somehow allowed an oversized value to reach the database.

## Identifying and Fixing Unconstrained Columns in an Existing Schema

```sql
-- Audit 1: Find all unconstrained VARCHAR/TEXT columns in the schema
SELECT
    c.table_name,
    c.column_name,
    c.data_type,
    c.character_maximum_length,   -- NULL means no limit
    c.is_nullable
FROM information_schema.columns c
WHERE c.table_schema = 'public'
  AND c.data_type IN ('character varying', 'text')
  AND c.character_maximum_length IS NULL   -- No length constraint
ORDER BY c.table_name, c.column_name;
-- Every row returned is a potential unconstrained column.
-- Review each one: should it have a limit? What is the domain maximum?

-- Audit 2: Find columns with very large actual values (bloat already present)
SELECT
    attname                                    AS column_name,
    pg_size_pretty(MAX(pg_column_size(name)))  AS max_value_size,
    pg_size_pretty(AVG(pg_column_size(name)))  AS avg_value_size,
    MAX(length(name))                          AS max_char_length,
    AVG(length(name))                          AS avg_char_length
FROM users
-- Replace with actual column references for your tables:
GROUP BY attname;

-- Simpler version — check actual max lengths in a specific column:
SELECT
    MAX(LENGTH(name))   AS max_name_length,
    AVG(LENGTH(name))   AS avg_name_length,
    PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY LENGTH(name)) AS p99_length
FROM users;
-- If p99_length is 95 and you set VARCHAR(100), you're safe.
-- If max is 10000000 (10MB), you have a problem to clean up first.

-- Audit 3: Add a length constraint to an existing column (safe, online):
-- First, clean up any existing violations:
UPDATE users
SET name = LEFT(name, 100)  -- Truncate oversized values (or delete/flag them)
WHERE LENGTH(name) > 100;

-- Then add the constraint (instant metadata change for VARCHAR limit addition):
ALTER TABLE users ALTER COLUMN name TYPE VARCHAR(100);

-- Add a CHECK constraint separately for minimum length and format:
ALTER TABLE users
ADD CONSTRAINT chk_name_length
CHECK (LENGTH(TRIM(name)) BETWEEN 2 AND 100);
-- Note: ALTER TABLE ADD CONSTRAINT validates all existing rows.
-- If any rows violate the new constraint, the ALTER fails.
-- Clean up violations first, then add the constraint.

-- Audit 4: Find suspiciously large rows (potential bloat from past exploits)
SELECT
    id,
    pg_column_size(name)    AS name_bytes,
    pg_column_size(bio)     AS bio_bytes,
    pg_column_size(users.*) AS total_row_bytes
FROM users
ORDER BY total_row_bytes DESC
LIMIT 20;
-- Rows with total_row_bytes in the millions are severely bloated.
-- These need to be identified, cleaned up, and reported to the security team.
```

## The Complete Mental Model

```
UNCONSTRAINED STRING LENGTH — COMPLETE MENTAL MODEL:
======================================================================

The Vulnerability:
  VARCHAR or TEXT with no length limit.
  PostgreSQL accepts any length of input: 1 byte, 10MB, 10GB.
  No error. No warning. Silent storage of whatever arrives.

The Four Damage Vectors:
  1. Storage exhaustion: One 10MB row × 1000 requests = 10GB table.
     Disk fills. Database crashes. Recovery: rebuild table.
  2. Index bloat: Name index entries balloon from ~20 bytes to 2.7KB each.
     Cache efficiency collapses. All name-based queries slow.
  3. TOAST thrashing: Values > 2KB stored off-page.
     Every row read = 2 I/Os. AUTOVACUUM overwhelmed by TOAST chunks.
  4. Application OOM: SELECT returning 100 rows × 10MB = 1GB allocation.
     Application server crashes. Service unavailable.

Why "App Validation Is Enough" Is Wrong:
  - App validation has bugs -> middleware bypass, missing code path
  - Direct DB access (psql, scripts, migrations) bypasses app
  - Multiple codebases each need the same rule
  - Rolling deploys: v1 allows 100 chars, v2 allows 50 -> inconsistency
  - DB is last line of defence: if app fails, DB must not accept garbage

The Fix:
  VARCHAR(n) with domain-appropriate limit:
  email:    VARCHAR(254)  -- RFC 5321
  name:     VARCHAR(100)  -- cultural names fit in 100 chars
  username: VARCHAR(50)   -- platform convention
  bio:      VARCHAR(1000) -- generous for user content
  url:      VARCHAR(2048) -- browser practical maximum
  token:    VARCHAR(512)  -- JWT + OAuth tokens

  CHECK constraints for richer validation:
  CHECK (LENGTH(TRIM(name)) >= 2)         -- Minimum meaningful length
  CHECK (name = TRIM(name))               -- No leading/trailing whitespace
  CHECK (username ~ '^[a-zA-Z0-9_]+$')   -- Pattern validation
  CHECK (status IN ('active','inactive')) -- Enum-like finite set

Go Error Handling:
  SQLSTATE 22001 (string_data_right_truncation) = value too long for VARCHAR(n)
  Handle explicitly -> return 400 Bad Request, not 500 Internal Server Error.
  The DB constraint is a validation gate, not just a storage rule.

The Defence Layers (all required):
  Layer 1: WAF / payload size limit (infrastructure)
  Layer 2: Framework validation (struct tags, middleware)
  Layer 3: Business logic checks (domain rules)
  Layer 4: Database VARCHAR(n) and CHECK constraints (immovable last line)

The Schema Design Rule:
  For every VARCHAR or TEXT column you create, answer this question:
  "What is the maximum valid value for this field in this domain?"
  Then set VARCHAR(that maximum). Always.
  If you cannot answer the question, default to VARCHAR(255) and refine later.
  Never leave it unconstrained. Never. The cost of one missing limit
  is potentially unlimited storage consumption and application failure.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

The unconstrained string length problem is unique among the schema design failures in this series because it is both a performance problem and a security problem — the two concerns that engineers care about most. It is a performance problem because unbounded column values cause storage bloat, index degradation, and TOAST thrashing. It is a security problem because it provides attackers with a direct lever for storage exhaustion, denial-of-service attacks, and potentially data exfiltration if the bloated values are logged or transmitted.

The principle that this case study illustrates is **defence in depth at the data layer**. Application validation is necessary and valuable, but it is not sufficient. Every layer that data passes through on its way to storage should validate it independently. The application validates for user experience — to return helpful error messages. The database validates for integrity — to guarantee that invalid data simply cannot exist, regardless of how it arrived. These two forms of validation serve different purposes and must coexist.

The practical discipline is simple: for every `VARCHAR` or `TEXT` column in every schema, answer the question "what is the maximum valid value for this field in this domain?" The answer is almost always a specific, reasoned number — 254 for email, 100 for a human name, 50 for a username, 2048 for a URL. Set `VARCHAR(that number)`. Add a `CHECK` constraint for minimum length and format where the domain specifies it. Handle the PostgreSQL `22001` error code in application code and return a meaningful client error when the database constraint fires.

The database is the last line of defence. It must be armed. A schema with unconstrained string columns is a schema with a gap in its defences at the most fundamental level — the level where data is permanently stored. Fill that gap at design time. It costs one word in a column definition. It prevents unbounded damage in production.
