# Case Study 04 — Storing Money as FLOAT Disaster

---

## The Setup — The Invoice That Never Adds Up

A fintech startup builds an invoicing platform. Engineers design the schema quickly, model amounts as `FLOAT` because that is what they use in JavaScript and Go for displaying prices, and ship the product. Everything looks fine. Invoices display correctly because the frontend rounds to two decimal places before showing numbers to users. Payments process without apparent errors. The product ships on time.

Six months later, the accounting team runs their first quarterly reconciliation report. They export all invoice line items, sum them up in Excel, and compare the total to the sum stored in the `invoices.total_amount` column. The numbers do not match. Not by a lot — the discrepancy is $0.03 on a quarter with $2.4 million in invoiced revenue. But it is a discrepancy, and in accounting, a discrepancy of any size is unacceptable. It means the books do not close, auditors get involved, and engineers get paged.

A second problem surfaces the same week. The tax calculation service is computing sales tax by multiplying the line item amount by the tax rate. For a $12.99 item at a 7.5% tax rate, the expected tax is $0.97425, which rounds to $0.97. The float arithmetic is producing `0.97424999999999997` in the database — which, depending on which rounding algorithm the downstream system uses, can round to either `$0.97` or `$0.98`. Some customers are being charged a penny too much. Other customers are getting a penny discount. Across 50,000 invoices, this creates both a customer service problem and a tax compliance problem.

The engineers look at the schema and find the root cause immediately: `price DOUBLE PRECISION`, `tax_amount DOUBLE PRECISION`, `total_amount DOUBLE PRECISION`. The entire financial engine of the product is built on a data type that is fundamentally incapable of representing decimal monetary amounts exactly. Not approximately. Exactly. And in finance, "approximately" is not acceptable. It is wrong.

## The Physics of Floating-Point — Why 0.1 Does Not Exist in Binary

To understand why floating-point fails for money, you need to understand what floating-point numbers actually are at the hardware level. The `FLOAT` type (single precision) and `DOUBLE PRECISION` type (double precision) in SQL — equivalent to `float32` and `float64` in Go — represent numbers using the **IEEE 754** binary floating-point standard. In this standard, numbers are stored as a binary fraction — a sum of powers of two — multiplied by a binary exponent.

The problem with money is that decimal fractions — numbers like `0.10` (ten cents), `0.25` (a quarter), or `0.99` (ninety-nine cents) — cannot be exactly represented in binary fractions. This is the same reason that one-third cannot be exactly represented in decimal (it requires an infinite sequence: `0.3333...`). Binary fractions can exactly represent `0.5` (which is `1/2`) and `0.25` (which is `1/4`) and `0.125` (which is `1/8`), but they cannot represent `0.1` (which is `1/10`) because 10 is not a power of 2. Any decimal fraction whose denominator has a prime factor other than 2 requires an infinite binary fraction to represent exactly.

The IEEE 754 standard handles this by truncating the infinite binary fraction to a finite number of bits — 23 bits for float32, 52 bits for float64. This truncation introduces a tiny rounding error at the moment the number is stored. The error for `0.1` in float64 is approximately `5.5 × 10^-18` — invisible in isolation, but it accumulates with every arithmetic operation, and financial systems perform millions of arithmetic operations over their lifetimes.

```
The Binary Representation of Decimal Fractions:
======================================================================

  Decimal 0.1 in binary (base 2):
  0.1 = 0.0001100110011001100110011001100110011... (repeating forever)

  Stored as float64 (52 bits of mantissa):
  0.1 ≈ 0.1000000000000000055511151231257827021181583404541015625
  Error: +5.55 × 10^-18

  Decimal 0.2 in binary:
  0.2 = 0.001100110011001100110011001100110011... (repeating forever)

  Stored as float64:
  0.2 ≈ 0.200000000000000011102230246251565404236316680908203125
  Error: +1.11 × 10^-17

  0.1 + 0.2 in float64 arithmetic:
  Result = 0.30000000000000004440892098500626161694526672363281250
  Expected = 0.30000000000000000000000000000000000000000000000000000
  Error = +4.44 × 10^-17 (the famous "0.1 + 0.2 != 0.3" result)

  In PostgreSQL:
  SELECT (0.1::FLOAT + 0.2::FLOAT) = 0.3::FLOAT;
  Result: false     <- 0.1 + 0.2 is NOT EQUAL to 0.3 in float arithmetic

  SELECT (0.1::NUMERIC + 0.2::NUMERIC) = 0.3::NUMERIC;
  Result: true      <- 0.1 + 0.2 IS EQUAL to 0.3 in NUMERIC arithmetic

  This is not a PostgreSQL bug. It is not a hardware bug.
  It is mathematically inevitable given how IEEE 754 works.
  The only fix is to not use FLOAT for decimal arithmetic. Ever.
======================================================================
```

## How Errors Accumulate — The $0.03 Mystery Explained

The $0.03 discrepancy on $2.4 million in revenue is not random. It is the predictable result of floating-point errors accumulating across millions of arithmetic operations. Each individual operation introduces an error of roughly ±10^-16 relative to the value being computed. Over one million operations, these errors accumulate — not necessarily randomly, because financial systems tend to use the same tax rates and price points repeatedly, meaning errors at the same magnitude tend to compound in the same direction.

Consider a simplified model: 100,000 invoices, each with a line item priced at $12.99 and a 7.5% tax rate.

```
Error Accumulation Over 100,000 Transactions:
======================================================================

  Single transaction (FLOAT arithmetic):
  price:          12.99  (stored as 12.9899999999999999289457264239899814128875732...)
  tax_rate:        0.075 (stored as 0.074999999999999999722444243843710......)
  tax:  12.99 * 0.075 = 0.97425
        In float64: 0.97424999999999997157829056959599...
        Rounded to cents: 0.97  (CORRECT)

  But stored UNrounded in float column:
  tax_amount: 0.97424999999999997...   <- stored, not rounded

  Over 100,000 identical transactions:
  SUM(tax_amount) in float arithmetic:
    Expected: 100,000 × 0.97425 = $97,425.00
    Float result: $97,424.97 (approximately)
    Discrepancy: $0.03 — exactly what the accounting team found

  The mechanism:
  Each row stores an amount that is 0.00000000000000003 too small.
  100,000 rows × 0.00000000000000003 error = 0.000000000003 total error.
  Wait — that is tiny. Why is it $0.03?

  The real accumulation: each addition in SUM() introduces its own
  floating-point rounding error. After 100,000 additions, the accumulated
  rounding error in the SUM itself is on the order of:
  sqrt(n) × machine_epsilon × magnitude ≈ sqrt(100000) × 10^-16 × 10^5
  ≈ 316 × 10^-16 × 10^5 ≈ 3.16 × 10^-9
  ... which is still tiny.

  The $0.03 comes from systematic bias: the float representation of 0.97425
  is consistently LESS THAN 0.97425. Over 100,000 transactions, the sum of
  100,000 systematically-too-small values is systematically too small by
  approximately 100,000 × 3 × 10^-7 = 0.03.

  With NUMERIC: SUM of 100,000 × 0.97425 = exactly 97,425.00000. Always.
======================================================================
```

## The Three Real-World Failure Modes

Floating-point money storage fails in three distinct ways, each manifesting at a different point in the application lifecycle.

**Failure Mode One: Accumulation in SUM Queries.** Financial reports aggregate large numbers of transactions. Every `SUM(amount)`, `SUM(tax)`, or `SUM(total)` on a FLOAT column accumulates floating-point rounding errors across the entire dataset. The result diverges from the exact correct answer by a small but consistent amount. Quarterly reconciliation reports are where this is first discovered, because that is typically the first time anyone computes the authoritative aggregate over the entire dataset and compares it to an external reference.

**Failure Mode Two: Rounding Inconsistency.** Different parts of a system may round floating-point results differently. The database might store `0.97424999999999997`, the application might display `$0.97` (floor), and the tax authority's formula might specify `$0.97` (round-half-up) or `$0.97` (banker's rounding). When the rounding happens at the wrong level — applied to a float rather than to an exact decimal — different rounding conventions can disagree on whether the result is `$0.97` or `$0.98`. A single penny discrepancy per transaction, across 50,000 transactions, is $500 in tax collected incorrectly.

**Failure Mode Three: Equality Comparison Failures.** Application code that checks whether a payment amount matches an invoice amount — for example, to confirm that a payment has been fully settled — will fail intermittently when using float comparison. `payment_amount == invoice_total` is not a reliable comparison for floats. The payment might be computed via a different path than the invoice total, producing a float with a slightly different rounding error, making two amounts that should be equal appear unequal. This causes payment matching failures, manual reconciliation work, and customer support incidents for transactions that are actually fully paid.

```
The Three Failure Modes in Code:
======================================================================

  FAILURE 1: SUM accumulation in financial reports
  -------------------------------------------------
  -- Using FLOAT:
  SELECT SUM(amount) FROM line_items WHERE invoice_date = '2025-Q1';
  -- Result: 97424.96999999997 (expected: 97425.00)
  -- Accounting team cannot close the books.

  -- Using NUMERIC:
  SELECT SUM(amount) FROM line_items WHERE invoice_date = '2025-Q1';
  -- Result: 97425.0000 (exact, always)
  -- Books close cleanly.

  FAILURE 2: Rounding inconsistency across systems
  -------------------------------------------------
  -- Database stores: tax_amount = 0.97424999999999997 (FLOAT)
  -- Application displays: "$0.97" (math.Floor(0.97424999...*100)/100)
  -- Tax authority formula: $0.974... rounds to "$0.97" (round-half-up)
  -- But on some transactions: stored value is 0.97425000000000003
  -- Application displays: "$0.97" (floor)
  -- Tax authority formula: "$0.97" rounds to "$0.97" (same)
  -- Two different float errors, same display, different tax ledger entry.
  -- Auditors find inconsistency. Questions asked. Engineers paged.

  FAILURE 3: Equality comparison breaks payment matching
  -------------------------------------------------------
  invoice.total = 149.99  (computed as sum of float line items)
  Stored float: 149.98999999999999772626324556767940521240234375

  payment.amount = 149.99  (entered by payment processor)
  Stored float: 149.99000000000000198951966012828052043914794921875

  invoice.total == payment.amount ?
  -> false   (they differ at the 15th decimal place)
  -> Payment matching fails. Manual review required. Customer confused.
  -> Correct answer: the payment IS complete. The comparison is wrong.
======================================================================
```

## Solution One — `NUMERIC(19,4)`: The Correct Type for Money

PostgreSQL's `NUMERIC` type (also called `DECIMAL` — they are identical) is an **exact numeric type**. It stores decimal numbers exactly, using variable-length binary-coded decimal representation rather than IEEE 754 binary floating-point. No rounding errors in storage. No rounding errors in arithmetic. `0.1 + 0.2` equals exactly `0.3`. `SUM` of a million `NUMERIC` values equals exactly the mathematical sum of those values.

The recommended specification for monetary amounts is `NUMERIC(19,4)`:
- **19** is the total number of significant digits (precision). This allows amounts up to `999,999,999,999,999.9999` — approximately one quadrillion, sufficient for any real-world monetary amount in any currency including the Japanese Yen, Indonesian Rupiah, and others with large face values.
- **4** is the number of digits after the decimal point (scale). Four decimal places handles currencies that require sub-cent precision for tax calculations (tax rates are often specified to four decimal places: 7.5% = 0.0750, 8.875% = 0.0875), as well as cryptocurrency amounts where sub-cent precision is common.

```sql
-- The correct schema for financial amounts:
CREATE TABLE invoices (
    id               BIGSERIAL PRIMARY KEY,
    customer_id      BIGINT      NOT NULL REFERENCES customers(id),
    currency         CHAR(3)     NOT NULL DEFAULT 'USD',  -- ISO 4217
    subtotal         NUMERIC(19,4) NOT NULL CHECK (subtotal >= 0),
    tax_rate         NUMERIC(8,6) NOT NULL CHECK (tax_rate >= 0 AND tax_rate <= 1),
    tax_amount       NUMERIC(19,4) NOT NULL GENERATED ALWAYS AS
                         (ROUND(subtotal * tax_rate, 4)) STORED,
    discount_amount  NUMERIC(19,4) NOT NULL DEFAULT 0 CHECK (discount_amount >= 0),
    total_amount     NUMERIC(19,4) NOT NULL GENERATED ALWAYS AS
                         (subtotal + tax_amount - discount_amount) STORED,
    status           TEXT        NOT NULL DEFAULT 'draft',
    issued_at        DATE,
    due_at           DATE,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE line_items (
    id               BIGSERIAL PRIMARY KEY,
    invoice_id       BIGINT      NOT NULL REFERENCES invoices(id) ON DELETE CASCADE,
    description      TEXT        NOT NULL,
    quantity         NUMERIC(10,4) NOT NULL CHECK (quantity > 0),
    unit_price       NUMERIC(19,4) NOT NULL CHECK (unit_price >= 0),
    amount           NUMERIC(19,4) NOT NULL GENERATED ALWAYS AS
                         (ROUND(quantity * unit_price, 4)) STORED,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Verify arithmetic correctness in PostgreSQL:
SELECT
    (0.1::NUMERIC + 0.2::NUMERIC) = 0.3::NUMERIC  AS sum_correct,
    (0.1::FLOAT   + 0.2::FLOAT)   = 0.3::FLOAT    AS sum_wrong;
-- sum_correct: true
-- sum_wrong:   false   <- This is why FLOAT must never be used for money

-- Financial aggregate query — exact result guaranteed:
SELECT
    customer_id,
    SUM(total_amount)   AS total_invoiced,
    SUM(tax_amount)     AS total_tax,
    COUNT(*)            AS invoice_count
FROM invoices
WHERE issued_at BETWEEN '2025-01-01' AND '2025-03-31'
GROUP BY customer_id;
-- Every SUM here returns the exact mathematical sum. No accumulation error.
-- Accounting team can close the books. Auditors find nothing to question.
```

## Solution Two — Store in Smallest Currency Unit as INTEGER

An alternative approach that is popular in high-performance payment systems is to store all monetary amounts as integers in the **smallest currency unit**: cents for USD, pence for GBP, sen for JPY (though JPY has no sub-unit in practice), satoshis for Bitcoin. This approach completely eliminates the floating-point question because integers are represented exactly in binary. There is no approximation, no rounding error, and no IEEE 754 problem when working with integers.

```sql
-- Integer-based money storage (in cents/pence/smallest unit):
CREATE TABLE transactions (
    id              BIGSERIAL PRIMARY KEY,
    amount_cents    BIGINT  NOT NULL,   -- In smallest currency unit
    currency        CHAR(3) NOT NULL,   -- ISO 4217 currency code
    -- $149.99 is stored as 14999
    -- $0.01 is stored as 1
    -- $1,000,000.00 is stored as 100000000
    -- £12.50 is stored as 1250 (pence)
    -- ¥1000 is stored as 1000 (yen, no sub-unit)
    description     TEXT    NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- The conversion factor is stored alongside or known by convention:
-- USD, EUR, GBP, CAD: 100 cents per major unit
-- JPY, KRW: 1 (no sub-unit, amounts are already integers)
-- BHD (Bahraini Dinar): 1000 fils per dinar

-- Arithmetic on integers is always exact:
-- $12.99 + $0.01 = 1299 + 1 = 1300 cents = $13.00 EXACT
-- No floating-point, no rounding errors, no NUMERIC overhead

-- Converting to decimal for display (only at the presentation layer):
SELECT
    amount_cents,
    currency,
    CASE currency
        WHEN 'USD' THEN amount_cents::NUMERIC / 100
        WHEN 'JPY' THEN amount_cents::NUMERIC         -- No decimal
        WHEN 'BHD' THEN amount_cents::NUMERIC / 1000  -- 3 decimal places
        ELSE             amount_cents::NUMERIC / 100
    END AS display_amount
FROM transactions;
```

```go
// Go implementation — using integers for money avoids float entirely:
package money

import (
    "fmt"
    "math"
)

// Money represents an amount in the smallest currency unit (e.g., cents for USD).
// All arithmetic is done on integers — no float64 ever touches financial values.
type Money struct {
    AmountCents int64
    Currency    string  // ISO 4217
}

// Add two monetary amounts of the same currency. Always exact.
func (m Money) Add(other Money) (Money, error) {
    if m.Currency != other.Currency {
        return Money{}, fmt.Errorf("cannot add %s and %s", m.Currency, other.Currency)
    }
    return Money{AmountCents: m.AmountCents + other.AmountCents, Currency: m.Currency}, nil
}

// Multiply by a rate (e.g., tax rate). Returns exact result in cents.
// Rate is expressed as a fraction of 10000 (e.g., 750 for 7.50%)
// to avoid float entirely.
func (m Money) MultiplyByRateBasisPoints(basisPoints int64) Money {
    // 1 basis point = 0.01%. 100 basis points = 1%.
    // 750 basis points = 7.50%.
    // Multiply first (integer), divide by 10000 (integer division rounds down).
    // For round-half-up: add 5000 before dividing by 10000.
    rawAmount := m.AmountCents * basisPoints
    rounded := (rawAmount + 5000) / 10000  // Round half-up
    return Money{AmountCents: rounded, Currency: m.Currency}
}

// Format for display: converts cents to human-readable string
func (m Money) Format() string {
    switch m.Currency {
    case "USD", "EUR", "GBP", "CAD", "AUD":
        return fmt.Sprintf("%s %d.%02d", m.Currency, m.AmountCents/100, abs(m.AmountCents%100))
    case "JPY", "KRW":
        return fmt.Sprintf("%s %d", m.Currency, m.AmountCents)  // No decimal
    default:
        return fmt.Sprintf("%s %.2f", m.Currency, float64(m.AmountCents)/100)
    }
}

func abs(x int64) int64 {
    if x < 0 { return -x }
    return x
}

// Example: $12.99 item + 7.5% tax
func ExampleTaxCalculation() {
    price := Money{AmountCents: 1299, Currency: "USD"}  // $12.99
    taxRateBasisPoints := int64(750)                     // 7.50%

    tax := price.MultiplyByRateBasisPoints(taxRateBasisPoints)
    // 1299 * 750 = 974,250. (974,250 + 5000) / 10000 = 97. = $0.97 EXACT

    total, _ := price.Add(tax)
    fmt.Println(price.Format())   // USD 12.99
    fmt.Println(tax.Format())     // USD 0.97
    fmt.Println(total.Format())   // USD 13.96
    // No floating-point arithmetic anywhere in this calculation.
    // The result is mathematically guaranteed to be correct.
}
```

## How to Handle the Rounding Decision — The Most Critical Subtlety

One of the most important and most overlooked aspects of financial arithmetic is that rounding must be an explicit, deliberate decision — not an implicit consequence of floating-point truncation. Rounding rules matter for tax compliance. Different jurisdictions, different industries, and different contract types have different rounding rules:

- **Round half-up** (most common in everyday business): 0.975 → 0.98
- **Round half-down**: 0.975 → 0.97
- **Banker's rounding** (round half to even): 0.975 → 0.98, 0.985 → 0.98 (the trailing digit is rounded to even)
- **Truncation** (floor): 0.979 → 0.97 (always round down, no matter the digit)

With floating-point storage, the rounding decision is made implicitly by the binary-to-decimal conversion, and different systems make this decision differently. With `NUMERIC` or integer storage, rounding is an explicit operation that you control:

```sql
-- Explicit rounding with NUMERIC — you control which rule applies:

-- Round half-up (standard commercial rounding):
SELECT ROUND(12.99 * 0.075, 2);  -- 0.97 (correct: 0.97425 rounds to 0.97)
SELECT ROUND(12.99 * 0.085, 2);  -- 1.10 (correct: 1.10415 rounds to 1.10)

-- PostgreSQL ROUND uses "round half away from zero" (round half-up for positive):
SELECT ROUND(0.5, 0);   -- 1
SELECT ROUND(1.5, 0);   -- 2
SELECT ROUND(2.5, 0);   -- 3 (not banker's rounding: that would give 2)

-- Banker's rounding in PostgreSQL (round half to nearest even):
-- PostgreSQL does not have a built-in banker's rounding function,
-- but you can implement it:
CREATE OR REPLACE FUNCTION round_bankers(val NUMERIC, scale INT)
RETURNS NUMERIC LANGUAGE plpgsql AS $$
DECLARE
    shifted NUMERIC := val * power(10, scale);
    floored NUMERIC := FLOOR(shifted);
    frac    NUMERIC := shifted - floored;
BEGIN
    IF frac = 0.5 THEN
        -- Round to nearest even
        IF MOD(floored::BIGINT, 2) = 0 THEN
            RETURN floored / power(10, scale);
        ELSE
            RETURN CEIL(shifted) / power(10, scale);
        END IF;
    ELSE
        RETURN ROUND(val, scale);  -- Normal rounding for non-half cases
    END IF;
END;
$$;

SELECT round_bankers(0.5, 0);   -- 0 (nearest even)
SELECT round_bankers(1.5, 0);   -- 2 (nearest even)
SELECT round_bankers(2.5, 0);   -- 2 (nearest even)
SELECT round_bankers(3.5, 0);   -- 4 (nearest even)
```

The critical discipline is: **choose your rounding rule once, at the schema/business logic level, and apply it consistently everywhere**. Document which rounding rule your system uses. Encode it in a shared library function that all parts of the application call. Never let rounding happen implicitly through floating-point arithmetic.

## Migrating Existing FLOAT Columns to NUMERIC

If you have an existing system with FLOAT money columns and need to migrate, the process requires care because of the imprecision already stored in the existing float values:

```sql
-- Step 1: Add the new NUMERIC columns alongside the existing FLOAT columns
ALTER TABLE invoices ADD COLUMN total_amount_numeric NUMERIC(19,4);
ALTER TABLE line_items ADD COLUMN unit_price_numeric NUMERIC(19,4);

-- Step 2: Migrate data — ROUND to 4 decimal places to eliminate float noise
-- IMPORTANT: Round to a reasonable precision, not to arbitrary float precision.
-- The existing float values are "approximately correct" — rounding to 4dp
-- eliminates the floating-point noise while preserving the intended value.
UPDATE invoices
SET total_amount_numeric = ROUND(total_amount::NUMERIC, 4)
WHERE total_amount_numeric IS NULL;

UPDATE line_items
SET unit_price_numeric = ROUND(unit_price::NUMERIC, 4)
WHERE unit_price_numeric IS NULL;

-- Step 3: Validate — check for any unexpected large discrepancies
SELECT
    id,
    total_amount              AS float_value,
    total_amount_numeric      AS numeric_value,
    ABS(total_amount::NUMERIC - total_amount_numeric) AS difference
FROM invoices
WHERE ABS(total_amount::NUMERIC - total_amount_numeric) > 0.01
ORDER BY difference DESC;
-- Differences > $0.01 are suspicious and need manual review.
-- Differences < $0.01 are normal floating-point noise, fixed by rounding.

-- Step 4: Rename columns (requires brief maintenance window)
ALTER TABLE invoices RENAME COLUMN total_amount TO total_amount_float_deprecated;
ALTER TABLE invoices RENAME COLUMN total_amount_numeric TO total_amount;

-- Step 5: Add constraints that were impossible with FLOAT
ALTER TABLE invoices ADD CONSTRAINT chk_total_positive CHECK (total_amount >= 0);
ALTER TABLE invoices ALTER COLUMN total_amount SET NOT NULL;

-- Step 6: Drop the old float column after validation period
-- ALTER TABLE invoices DROP COLUMN total_amount_float_deprecated;
```

## Auditing Your Schema for Money-as-Float Violations

```sql
-- Find all FLOAT and DOUBLE PRECISION columns in your schema
-- These are candidates for money storage violations:
SELECT
    table_name,
    column_name,
    data_type,
    numeric_precision,
    is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND data_type IN ('real', 'double precision', 'float')
ORDER BY table_name, column_name;
-- Review each result: is this column storing money? If yes, it is a bug.
-- Is it storing a scientific measurement, a percentage for display? Maybe OK.

-- Check the magnitude of float errors in existing money columns:
-- (This query detects float noise by checking if values have many decimal places)
SELECT
    id,
    total_amount,
    total_amount::TEXT AS stored_text,    -- Shows the actual float representation
    ROUND(total_amount::NUMERIC, 2)::TEXT AS rounded_text
FROM invoices
WHERE total_amount::TEXT != ROUND(total_amount::NUMERIC, 2)::TEXT
LIMIT 20;
-- Rows where stored_text != rounded_text have float noise.
-- Example: stored_text='149.98999999...', rounded_text='149.99'
-- Every such row is a data integrity problem.

-- Detect accumulation errors in SUM queries:
SELECT
    DATE_TRUNC('month', created_at) AS month,
    SUM(total_amount::FLOAT)        AS float_sum,     -- Incorrect (float arithmetic)
    SUM(total_amount::NUMERIC)      AS numeric_sum,   -- Correct (exact arithmetic)
    SUM(total_amount::NUMERIC) - SUM(total_amount::FLOAT)::NUMERIC AS discrepancy
FROM invoices
GROUP BY month
ORDER BY month;
-- Non-zero discrepancy column = evidence of float accumulation error.
```

```
  There are no exceptions. Not "mostly fine for small amounts."
  Not "we'll fix it later when it matters." NUMERIC or INTEGER. Always.
  The cost of using FLOAT is paid later, in audit findings,
  in customer refund requests, and in regulatory compliance failures.
  The cost of using NUMERIC is paid upfront, in a single schema decision.
  Pay it upfront.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

The money-as-float disaster teaches a principle that sits at the intersection of computer science theory and business reality: **the choice of numeric type is not a performance decision — it is a correctness decision**. When you choose `FLOAT` for a monetary column, you are choosing a number system that cannot represent the values you are trying to store. It is not a matter of sufficient precision or acceptable approximation. It is a matter of mathematical incompatibility. The decimal monetary system and the binary floating-point system are built on fundamentally different mathematical foundations, and no amount of careful programming can bridge this gap at the data layer.

The two correct alternatives — `NUMERIC(19,4)` and integer cents — are both exact representations of decimal monetary values. NUMERIC uses PostgreSQL's variable-precision decimal arithmetic, which is slower than float arithmetic but exact by design. Integer cents use standard integer arithmetic, which is both fast and exact. The choice between them is primarily a matter of system design preference and multi-currency handling: NUMERIC is more ergonomic for general-purpose financial data, while integer cents are more explicit and more cache-friendly for high-throughput payment processing systems.

The rounding discipline is the companion to the type discipline. Even with `NUMERIC`, rounding decisions must be made explicitly and consistently. The database performs exact arithmetic, but at some point a four-decimal-place tax amount must be rounded to a two-decimal-place cent amount. That rounding operation has a defined rule — round half-up, banker's rounding, truncation — and that rule must be the same everywhere in the system: in the database trigger that computes `tax_amount`, in the application service that totals an invoice, and in the reporting query that aggregates monthly revenue. Inconsistent rounding rules, even with exact `NUMERIC` arithmetic, can still produce pennies-off discrepancies that fail audits.

Floating-point is fundamentally incompatible with financial arithmetic. There are no exceptions. Every monetary amount in every financial system must be stored as either `NUMERIC`/`DECIMAL` with explicit precision and scale, or as an integer in the smallest currency unit. This is not a preference or a recommendation — it is a correctness requirement.
