# Case Study 02 — The God Table

---

## The Setup — One Table to Rule Them All

A software architect is designing the data layer for a new SaaS platform. The platform will have several different types of entities: individual users, company accounts, product listings, and orders. The architect notices something that feels like an insight: all of these entities share some common fields. They all have an `id`, a `name`, a `created_at` timestamp, and a `status` field. They all need to be referenced by other records. They all participate in a notification system that tracks events by entity ID.

The architect, in a moment of what feels like elegant abstraction, makes a decision: instead of four separate tables, build one universal table called `entities`. Add a `type` column to distinguish what kind of entity each row represents. All shared fields go in the table. Type-specific fields go in the same table, just only used for the appropriate type. The schema is born:

```sql
CREATE TABLE entities (
    id                    BIGSERIAL PRIMARY KEY,
    type                  TEXT NOT NULL,   -- 'user', 'company', 'product', 'order'
    name                  TEXT,
    status                TEXT,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- User-specific columns (NULL for company, product, order)
    email                 TEXT,
    password_hash         TEXT,
    date_of_birth         DATE,
    profile_picture_url   TEXT,
    last_login_at         TIMESTAMPTZ,
    two_factor_enabled    BOOLEAN,
    subscription_tier     TEXT,

    -- Company-specific columns (NULL for user, product, order)
    tax_id                TEXT,
    company_registration  TEXT,
    industry              TEXT,
    employee_count        INTEGER,
    billing_address       TEXT,
    accounts_payable_email TEXT,
    annual_revenue_usd    NUMERIC(15,2),

    -- Product-specific columns (NULL for user, company, order)
    sku                   TEXT,
    unit_price            NUMERIC(10,2),
    weight_kg             NUMERIC(6,3),
    inventory_count       INTEGER,
    category_id           BIGINT,
    supplier_id           BIGINT,
    is_digital            BOOLEAN,

    -- Order-specific columns (NULL for user, company, product)
    customer_entity_id    BIGINT,
    total_amount          NUMERIC(12,2),
    payment_status        TEXT,
    shipping_address      TEXT,
    delivery_date         DATE,
    tracking_number       TEXT,
    discount_code         TEXT
    -- ... and so on, more columns added over time
);
```

Today this table has 200 columns and 50 million rows. Only a small fraction of those columns are populated for any given row. A user row has populated `email`, `password_hash`, and `subscription_tier` — but `tax_id`, `sku`, `unit_price`, `total_amount`, and a hundred other columns are NULL. A product row has `sku`, `unit_price`, and `inventory_count` — but `email`, `date_of_birth`, `billing_address`, and another hundred columns are NULL.

Queries are slow. The table is enormous. Schema changes require coordinating across every part of the application that uses the table, which is every part of the application. Engineers have started referring to it privately as "The God Table" — the one table that knows everything, controls everything, and is responsible for most of the database's performance problems. It has become a liability that the entire engineering team works around but cannot easily escape.

---

## What the God Table Is — The Anti-Pattern Formally Named

The God Table is a database design anti-pattern where a single table is used to store multiple fundamentally different entity types, distinguished by a `type` or `kind` column, with type-specific attributes stored as nullable columns that are irrelevant to other types. It is the database equivalent of the "God Object" anti-pattern in object-oriented programming — an object that knows too much and does too much, creating tight coupling between conceptually unrelated things.

The God Table goes by several names in database literature. Object-Relational Mappers like Ruby on Rails call the legitimate, controlled subset of it **Single Table Inheritance (STI)** when it is used deliberately for related entities in an inheritance hierarchy. The problematic version — where genuinely unrelated entities are forced into one table — is sometimes called **polymorphic table design** or, informally among database engineers, simply "the wide table problem." Whatever name it goes by, the symptoms are the same: a table with many columns, most of which are NULL for any given row, a `type` discriminator column, and a growing maintenance burden that slows down every operation from querying to schema evolution.

```
God Table Structure — The Physical Reality:
======================================================================

  entities table (50 million rows, 200 columns):

  id | type     | name       | email  | tax_id | sku    | total_amount | [190 more cols]
  ---+----------+------------+--------+--------+--------+--------------+----------------
   1 | user     | Alice      | a@x.com| NULL   | NULL   | NULL         | [190 NULLs]
   2 | user     | Bob        | b@x.com| NULL   | NULL   | NULL         | [190 NULLs]
   3 | company  | Acme Corp  | NULL   | TAX-01 | NULL   | NULL         | [190 NULLs]
   4 | product  | Widget Pro | NULL   | NULL   | SKU-42 | NULL         | [190 NULLs]
   5 | order    | NULL       | NULL   | NULL   | NULL   | 149.99       | [190 NULLs]
  ...50 million rows...

  For a user row (200 columns total):
    Populated columns:  ~10  (email, password, name, status, etc.)
    NULL columns:      ~190  (all company, product, order specific)
    NULL ratio:         95%

  For a product row (200 columns total):
    Populated columns:  ~12  (sku, price, weight, inventory, etc.)
    NULL columns:      ~188  (all user, company, order specific)
    NULL ratio:         94%

  Physical consequence:
  PostgreSQL stores NULLs efficiently (null bitmap), but the row header,
  alignment padding between columns, and TOAST overhead for wide rows
  all grow with column count regardless of NULL values.
  A 200-column row is significantly larger than a 20-column row, even with
  190 NULLs, because the row must carry a 25-byte null bitmap header
  and column alignment padding for the physical layout.
======================================================================
```

## Why the God Table Fails — Five Compounding Problems

The God Table does not fail in one way. It fails in five distinct ways simultaneously, and the damage compounds as the table grows larger and the type list grows longer.

### Problem One: Storage Bloat from NULL Overhead

PostgreSQL handles NULL values more efficiently than many engineers assume — it uses a **null bitmap** in the row header to mark which columns are NULL, rather than storing a placeholder value for each one. However, "more efficient" does not mean "free." Every row in PostgreSQL carries a 23-byte header. If any column in the row is NULL, an additional null bitmap is appended to the header — one bit per column. For a 200-column table, the null bitmap adds 25 bytes (ceil(200/8)) to every single row, regardless of whether only one column is NULL or all 199 are.

Beyond the null bitmap, wide rows increase alignment padding between columns. PostgreSQL aligns certain data types to their natural byte boundary — integers to 4-byte boundaries, timestamps to 8-byte boundaries. In a narrow table with only the columns you actually use, this alignment overhead is minimal. In a 200-column table, the alignment gaps between the 10 meaningful columns and the 190 NULL columns add up. Additionally, very wide rows increase the probability of triggering TOAST (The Oversized Attribute Storage Technique), where large values are compressed or moved off the main table heap — adding I/O overhead for every row access that involves a toasted value.

```
Row Size Comparison — God Table vs. Separate Tables:
======================================================================

  God Table: user row (200 columns, 190 NULL):
  +-------------------+-------------------+-----------+
  | Row header (23B)  | Null bitmap (25B) | User data |
  +-------------------+-------------------+-----------+
  | Alignment padding between 200 columns              |
  +---------------------------------------------------+
  Approximate size per user row: ~180 bytes
  (vs. what it should be: ~85 bytes in a proper users table)

  Separate users table (15 columns, 0 NULL on most rows):
  +-------------------+-------------------+-----------+
  | Row header (23B)  | No null bitmap!   | User data |
  +-------------------+-------------------+-----------+
  Approximate size per user row: ~85 bytes

  For 20 million user rows:
  God Table storage: 20M * 180B = ~3.4 GB for user rows alone
  Separate table:    20M *  85B = ~1.7 GB
  Overhead from God Table: ~1.7 GB wasted (NULLs, headers, padding)

  That extra 1.7 GB must be read from disk for every full table scan,
  held in RAM in the buffer cache, and written to WAL for every UPDATE.
  The waste is not just at rest — it is a performance tax on every operation.
======================================================================
```

### Problem Two: Index Inefficiency and Bloat

Indexes on the God Table are fundamentally compromised by the presence of multiple entity types. Consider an index on the `email` column, which is only meaningful for user rows. In a proper `users` table with 20 million rows, an index on `email` contains 20 million entries. In the God Table with 50 million rows of all types, an index on `email` contains 50 million entries — 30 million of which are NULL (for company, product, and order rows). PostgreSQL does not index NULL values in a standard B-tree index, so those 30 million NULL entries are excluded — the index actually still contains 20 million entries. But the table itself is now 2.5× as large, which means every query that cannot use the index must scan 2.5× as much data as it should.

More critically, composite indexes that would efficiently serve the most common query patterns become impossible to design properly. A query like `SELECT * FROM entities WHERE type = 'user' AND status = 'active' AND subscription_tier = 'enterprise'` needs an index on `(type, status, subscription_tier)` — but that index spans the entire table and must include rows for all entity types, making it both larger and less selective than a purpose-built index on the `users` table alone.

### Problem Three: Query Planner Confusion and Cardinality Errors

The PostgreSQL query planner makes decisions about how to execute a query based on **statistics** — specifically, estimates of how many rows a particular condition will match. These statistics are collected by AUTOVACUUM using `pg_statistic`, which stores column-level histograms and most-common-value lists.

In the God Table, the statistics for every column are computed across all entity types simultaneously. The `status` column, for example, might have values like `'active'`, `'inactive'`, `'pending'`, `'shipped'`, `'delivered'`, `'cancelled'` — where some values are meaningful for users, others for orders, and others for companies. The planner's statistics for `status` represent a mixture of all these entity types, making its cardinality estimates inaccurate for any query that filters on both `type` and `status`. The planner may drastically misestimate the number of rows a type-filtered query will return, leading to suboptimal execution plans — choosing a sequential scan when an index scan would be better, or vice versa.

```
Query Planner Confusion — Statistics Corruption:
======================================================================

  God Table: entities (50M rows)
  type distribution: 40% users, 20% companies, 30% products, 10% orders

  Column: status
  Values: 'active'(35%), 'inactive'(15%), 'pending'(10%), 'shipped'(20%),
          'delivered'(15%), 'cancelled'(5%)

  Query: WHERE type = 'user' AND status = 'active'
  Planner estimate (using full-table statistics):
    type='user': 40% of 50M = 20M rows
    status='active': 35% of 50M = 17.5M rows
    Combined (independent): 40% * 35% = 14% = 7M rows  <- ESTIMATE

  Actual result: users with status='active' = 16M
  (Because 80% of users are active, but the planner used the table-wide
   35% statistic which is diluted by order/product status distributions.)

  Planner error: estimated 7M, actual 16M = 2.3x underestimate
  Result: planner chooses index scan (expecting 7M rows = worth the index cost)
          actual execution scans 16M rows via index = wrong choice
          should have chosen sequential scan

  In separate users table (20M rows):
  status='active': 80% = 16M rows  <- accurate, planner makes correct choice
  Planner error: near-zero. Correct plan chosen every time.
======================================================================
```

### Problem Four: Schema Changes Are System-Wide Events

In a properly normalized schema, adding a new column to the `products` table affects only the `products` table. The `users` table, the `orders` table, and the `companies` table are completely unaffected. Only the code that works with products needs to change.

In the God Table, adding a new product-specific column adds a column to the one table that everything depends on. Every index on the table may need evaluation. The null bitmap grows. Any ORM or query builder that generates `SELECT *` queries will now return an additional column for every entity type, not just products. The migration itself must be applied carefully, and the rollback plan must account for the fact that removing the column later (if the feature is rolled back) requires a separate migration on the same God Table. Every schema change is now a system-wide event with system-wide risk.

### Problem Five: Constraint Impossibility

Database-level constraints become either impossible or meaningless in the God Table. Consider the `email` column: in a proper `users` table, you would have `email TEXT NOT NULL UNIQUE`. In the God Table, you cannot have `NOT NULL` because company, product, and order rows do not have an email — they would fail the constraint. You cannot have a simple `UNIQUE` constraint because NULL values are not equal to each other in SQL (NULL != NULL), so multiple non-user rows with NULL email would all pass uniqueness. You could write a partial unique index (`CREATE UNIQUE INDEX ON entities(email) WHERE type = 'user'`), but this is a workaround for a problem that would not exist in a properly separated schema.

Similarly, foreign key constraints become awkward. The `customer_entity_id` in an order row should reference a user — but in the God Table, it references the `entities` table, which contains users, companies, products, and other orders. There is no database-level way to express "this ID must reference a row where `type = 'user'`" using standard SQL foreign key constraints.

## The Access Pattern Mismatch

Beyond the structural problems, the God Table creates a fundamental mismatch between physical data layout and access patterns. PostgreSQL stores table rows in pages of 8KB each. When you query for all active users, PostgreSQL must scan pages that contain user rows, company rows, product rows, and order rows — because they are all mixed together in the same physical storage. Only the user rows are relevant to your query, but you must read every page that might contain a user row, which is essentially every page in the table.

In a proper `users` table, a sequential scan of active users reads only pages that contain user rows. In the God Table, the same query reads the entire 50-million-row table — which is 2.5× larger than the user subset alone — to find the user rows mixed in among company, product, and order rows.

```
Physical Page Layout — God Table vs. Separate Tables:
======================================================================

  God Table (50M rows, all types mixed):
  +--Page 1 (8KB)-----+--Page 2 (8KB)-----+--Page 3 (8KB)-----+
  | user   row #1      | product  row #200  | user   row #450    |
  | company row #10    | order    row #210  | order   row #460   |
  | product row #20    | user     row #220  | company row #470   |
  | user   row #30     | company  row #230  | product row #480   |
  | order  row #40     | user     row #240  | user    row #490   |
  +--------------------+--------------------+--------------------+
  Rows are physically interleaved. To find ALL user rows,
  you must read ALL pages (contains non-user rows on every page).

  SELECT * FROM entities WHERE type = 'user' AND status = 'active'
  -> Must read ALL 50M rows (sequential scan) or ALL index pages
  -> Relevant rows: 20M (40% of table)
  -> Wasted I/O: 30M rows read, discarded because type != 'user'

  Separate users table (20M rows):
  +--Page 1 (8KB)-----+--Page 2 (8KB)-----+--Page 3 (8KB)-----+
  | user row #1        | user row #200      | user row #400      |
  | user row #2        | user row #201      | user row #401      |
  | user row #3        | user row #202      | user row #402      |
  | user row #4        | user row #203      | user row #403      |
  +--------------------+--------------------+--------------------+
  ALL pages contain only user rows.

  SELECT * FROM users WHERE status = 'active'
  -> Reads only users pages: 20M rows, ALL relevant
  -> Zero wasted I/O
  -> 2.5x fewer pages to read
  -> Sequential scan is 2.5x faster
  -> Index scans are more selective
======================================================================
```

## Solution One — Proper Separate Tables with a Shared Notifications Linkage

The cleanest, most performant, and most maintainable solution is to give each entity type its own properly normalized table. The perceived benefit of the God Table — that a single entity ID can be referenced by shared systems like notifications or audit logs — can be preserved through a polymorphic reference table or by using a shared sequence for IDs across tables.

```sql
-- Each entity gets its own properly shaped table:
CREATE TABLE users (
    id                BIGSERIAL PRIMARY KEY,
    email             TEXT        NOT NULL UNIQUE,
    password_hash     TEXT        NOT NULL,
    name              TEXT        NOT NULL,
    status            TEXT        NOT NULL DEFAULT 'active'
                                  CHECK (status IN ('active', 'inactive', 'suspended')),
    subscription_tier TEXT        NOT NULL DEFAULT 'free',
    date_of_birth     DATE,
    last_login_at     TIMESTAMPTZ,
    two_factor_enabled BOOLEAN    NOT NULL DEFAULT false,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
    -- Only columns that belong to a user. No NULLs by design.
);

CREATE TABLE companies (
    id                    BIGSERIAL PRIMARY KEY,
    name                  TEXT        NOT NULL,
    tax_id                TEXT        UNIQUE,
    company_registration  TEXT,
    industry              TEXT,
    employee_count        INTEGER     CHECK (employee_count > 0),
    billing_address       TEXT,
    accounts_payable_email TEXT,
    annual_revenue_usd    NUMERIC(15,2),
    status                TEXT        NOT NULL DEFAULT 'active',
    created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()
    -- Only columns that belong to a company.
);

CREATE TABLE products (
    id              BIGSERIAL PRIMARY KEY,
    sku             TEXT        NOT NULL UNIQUE,
    name            TEXT        NOT NULL,
    unit_price      NUMERIC(10,2) NOT NULL CHECK (unit_price >= 0),
    weight_kg       NUMERIC(6,3),
    inventory_count INTEGER     NOT NULL DEFAULT 0 CHECK (inventory_count >= 0),
    category_id     BIGINT      REFERENCES product_categories(id),
    supplier_id     BIGINT      REFERENCES suppliers(id),
    is_digital      BOOLEAN     NOT NULL DEFAULT false,
    status          TEXT        NOT NULL DEFAULT 'active',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
    -- Only columns that belong to a product.
);

CREATE TABLE orders (
    id               BIGSERIAL PRIMARY KEY,
    customer_user_id BIGINT      NOT NULL REFERENCES users(id),  -- TYPED foreign key!
    company_id       BIGINT      REFERENCES companies(id),
    total_amount     NUMERIC(12,2) NOT NULL,
    payment_status   TEXT        NOT NULL DEFAULT 'pending',
    shipping_address TEXT,
    delivery_date    DATE,
    tracking_number  TEXT,
    discount_code    TEXT,
    status           TEXT        NOT NULL DEFAULT 'pending',
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
    -- Only columns that belong to an order.
);

-- For systems that need a global entity ID (notifications, audit logs):
-- Use a polymorphic reference table that maps global IDs to specific tables.
CREATE TABLE entity_registry (
    global_id    BIGSERIAL PRIMARY KEY,
    entity_type  TEXT    NOT NULL CHECK (entity_type IN ('user','company','product','order')),
    local_id     BIGINT  NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (entity_type, local_id)
);

-- Notifications table that references ANY entity type cleanly:
CREATE TABLE notifications (
    id           BIGSERIAL PRIMARY KEY,
    entity_type  TEXT    NOT NULL,
    entity_id    BIGINT  NOT NULL,   -- References the local table's ID
    message      TEXT    NOT NULL,
    is_read      BOOLEAN NOT NULL DEFAULT false,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
    -- entity_type + entity_id forms a polymorphic reference.
    -- Application resolves the actual entity by entity_type.
);
```

With separate tables, every query is surgically precise. There is no type-filter overhead, no wasted I/O reading irrelevant entity types, no index inefficiency, no constraint compromise:

```sql
-- Queries that were slow on the God Table are fast on separate tables:

-- Find active enterprise users (God Table: full scan needed, type filter overhead)
SELECT id, email, name, subscription_tier
FROM users
WHERE status = 'active'
  AND subscription_tier = 'enterprise';
-- Index scan on (status, subscription_tier). Reads ONLY the users table.
-- No company, product, or order rows ever read.

-- Find products below reorder threshold (type-specific query)
SELECT id, sku, name, inventory_count
FROM products
WHERE inventory_count < 10
  AND status = 'active'
ORDER BY inventory_count ASC;
-- Index on inventory_count. Reads ONLY the products table.

-- Join orders to users (natural join, typed foreign key)
SELECT o.id, o.total_amount, u.email, u.name
FROM orders o
JOIN users u ON u.id = o.customer_user_id
WHERE o.payment_status = 'pending'
  AND o.created_at > NOW() - INTERVAL '24 hours';
-- Clean, typed foreign key. Query planner has accurate cardinality estimates.
```

## Solution Two — Single Table Inheritance: When the God Table Is Appropriate

It would be intellectually dishonest to declare every form of multi-type single table as wrong. There is a legitimate, well-understood use case called **Single Table Inheritance (STI)** where a single table is the correct choice: when you have a true inheritance hierarchy of closely related types that share the majority of their columns, with only minor differences between them.

The canonical example is a content moderation system with `article`, `comment`, and `review` entity types. All three share `author_id`, `body`, `status`, `created_at`, `upvote_count`, and `report_count`. They differ in minor ways: articles have a `title` and `category_id`, comments have a `parent_article_id`, reviews have a `star_rating` and `product_id`. The divergence is small — perhaps 3-5 type-specific columns out of 12 total. The access patterns are similar (all types queried by `status`, by `author_id`, filtered by `created_at`). A single table with a `type` column and a handful of nullable type-specific columns is reasonable here.

```sql
-- APPROPRIATE use of Single Table Inheritance:
-- Related content types with high column overlap (~80% shared)
CREATE TABLE content_items (
    id              BIGSERIAL PRIMARY KEY,
    type            TEXT NOT NULL CHECK (type IN ('article', 'comment', 'review')),
    author_id       BIGINT NOT NULL REFERENCES users(id),
    body            TEXT NOT NULL,
    status          TEXT NOT NULL DEFAULT 'published',
    upvote_count    INTEGER NOT NULL DEFAULT 0,
    report_count    INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- Article-specific (NULL for comment, review) — few columns
    title           TEXT,          -- articles only
    category_id     BIGINT,        -- articles only

    -- Comment-specific (NULL for article, review) — few columns
    parent_article_id BIGINT,      -- comments only

    -- Review-specific (NULL for article, comment) — few columns
    star_rating     SMALLINT CHECK (star_rating BETWEEN 1 AND 5),  -- reviews only
    reviewed_product_id BIGINT     -- reviews only
);

-- NULL ratio: ~3 NULL columns out of 14 total per row. Reasonable.
-- Access patterns are the same for all types. Shared indexes work well.
-- This is appropriate STI. Not a God Table.

-- CONTRAST: When STI becomes a God Table:
-- If articles, companies, orders, and IoT sensor readings all end up here
-- with 200 columns and 95% NULL ratio per row -> GOD TABLE. Not acceptable.
```

The key question to ask when deciding between STI and separate tables is: **what percentage of columns are shared across all types, and are the access patterns similar?** If more than 80% of columns are shared and the entities are queried the same way, STI is reasonable. If less than 50% of columns are shared, or if different types have fundamentally different access patterns (users are queried by email, products by SKU and category, orders by customer and date range), separate tables are the correct choice.

```
The STI Decision Checklist:
======================================================================

  Use Single Table Inheritance (one table) WHEN:
  [ ] Types share > 80% of columns                    [REQUIRED]
  [ ] Types have similar access patterns              [REQUIRED]
  [ ] Type-specific columns number < 5 per type       [RECOMMENDED]
  [ ] Total NULL ratio per row < 20%                  [RECOMMENDED]
  [ ] All types appear in the same WHERE clauses      [INDICATOR]
  [ ] Reporting needs cross-type queries frequently   [INDICATOR]

  Use Separate Tables WHEN:
  [ ] Types share < 50% of columns                    [REQUIRED]
  [ ] Types are queried by different columns           [REQUIRED]
  [ ] Types have different business rules/constraints [REQUIRED]
  [ ] NULL ratio per row > 30%                        [WARNING SIGN]
  [ ] > 10 type-specific columns per type             [WARNING SIGN]
  [ ] Adding a column for one type forces changes     [REQUIRED]
      on all other types' code paths
  [ ] Different types have different growth rates     [INDICATOR]
      (e.g., products grow slowly, orders grow fast)
======================================================================
```

## Solution Three — Class Table Inheritance: The Best of Both Worlds

When entities genuinely do share common attributes that benefit from being stored together — for joins, for shared queries, for the notification/audit use case — but also have substantial type-specific attributes, the **Class Table Inheritance** pattern provides an elegant middle ground. A shared base table stores the common attributes, and separate extension tables store the type-specific attributes, linked by a shared primary key.

```sql
-- Class Table Inheritance: shared base + type-specific extension tables
-- Base table: only the truly universal attributes
CREATE TABLE entities_base (
    id           BIGSERIAL PRIMARY KEY,
    entity_type  TEXT NOT NULL CHECK (entity_type IN ('user','company','product','order')),
    name         TEXT,
    status       TEXT NOT NULL DEFAULT 'active',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
-- This table is small, clean, and queryable for cross-type operations.
-- Notifications, audit logs, and activity feeds reference this table.

-- Type-specific extension tables: linked by shared primary key
CREATE TABLE users_ext (
    entity_id         BIGINT PRIMARY KEY REFERENCES entities_base(id),
    email             TEXT NOT NULL UNIQUE,
    password_hash     TEXT NOT NULL,
    date_of_birth     DATE,
    subscription_tier TEXT NOT NULL DEFAULT 'free',
    last_login_at     TIMESTAMPTZ,
    two_factor_enabled BOOLEAN NOT NULL DEFAULT false
    -- Zero NULLs: every column belongs to users and is meaningful for users.
);

CREATE TABLE companies_ext (
    entity_id             BIGINT PRIMARY KEY REFERENCES entities_base(id),
    tax_id                TEXT UNIQUE,
    company_registration  TEXT,
    industry              TEXT,
    employee_count        INTEGER,
    billing_address       TEXT,
    annual_revenue_usd    NUMERIC(15,2)
    -- Zero NULLs: every column belongs to companies.
);

CREATE TABLE products_ext (
    entity_id        BIGINT PRIMARY KEY REFERENCES entities_base(id),
    sku              TEXT NOT NULL UNIQUE,
    unit_price       NUMERIC(10,2) NOT NULL,
    weight_kg        NUMERIC(6,3),
    inventory_count  INTEGER NOT NULL DEFAULT 0,
    category_id      BIGINT,
    is_digital       BOOLEAN NOT NULL DEFAULT false
);

-- Usage: query users with their specific data
SELECT b.id, b.status, b.created_at, u.email, u.subscription_tier
FROM entities_base b
JOIN users_ext u ON u.entity_id = b.id
WHERE b.entity_type = 'user'
  AND b.status = 'active'
  AND u.subscription_tier = 'enterprise';

-- Query across all types (for notification system):
SELECT b.id, b.entity_type, b.name, b.status
FROM entities_base b
WHERE b.created_at > NOW() - INTERVAL '24 hours'
ORDER BY b.created_at DESC;
-- Fast: only reads the small, clean base table. No type-specific data needed.
```

Class Table Inheritance is more complex than either STI or fully separate tables, but it is the correct choice when: you genuinely need cross-type queries (for notifications, activity feeds, admin dashboards), and different types have substantial type-specific attributes that would create a high NULL ratio in a single table.

## Migrating Away From the God Table

If you are sitting on an existing God Table and need to migrate to a better structure, the process requires careful planning but can be done without downtime using online DDL and data copying:

```sql
-- Step 1: Create the new target tables (empty, with correct schemas)
-- (CREATE TABLE users, companies, products, orders as shown above)

-- Step 2: Copy data in batches (does not block the God Table)
-- Copy users:
INSERT INTO users (id, email, name, status, subscription_tier, created_at, updated_at)
SELECT id, email, name, status, subscription_tier, created_at, updated_at
FROM entities
WHERE type = 'user'
  AND id > $last_id   -- cursor-based batching
LIMIT 10000;

-- Step 3: Set up dual-write during the migration window
-- Application writes to BOTH entities (old) and the new table simultaneously.
-- This ensures no data is lost during the migration.

-- Step 4: Verify row counts and data consistency
SELECT
    (SELECT COUNT(*) FROM entities WHERE type = 'user')  AS god_table_users,
    (SELECT COUNT(*) FROM users)                         AS new_table_users;
-- Must be equal before proceeding.

-- Step 5: Migrate foreign key references (audit_logs, notifications, etc.)
-- Update references to use new table IDs and table-specific foreign keys.

-- Step 6: Switch application reads to the new tables.
--         Monitor for errors. Keep the God Table as fallback for 24-48 hours.

-- Step 7: Once stable, drop the God Table.
-- DROP TABLE entities CASCADE;  -- Only after thorough verification.

-- Monitoring the God Table NULL density before migration (helps prioritize):
SELECT
    attname    AS column_name,
    null_frac  AS null_fraction,
    n_distinct AS distinct_values
FROM pg_stats
WHERE tablename = 'entities'
ORDER BY null_frac DESC;
-- Columns with null_frac > 0.5 are type-specific and belong in separate tables.
-- Columns with null_frac near 0.0 are universal and belong in the base table.
```

## The Complete Mental Model

```
THE GOD TABLE — COMPLETE MENTAL MODEL:
======================================================================

The Structure:
  entities: id | type | [200 columns] | [NULL * 190 per row]
  type IN ('user', 'company', 'product', 'order')
  One table. All entity types. 90-95% NULL per row.

The Five Failures:
  1. Storage bloat:    NULL bitmap + alignment overhead.
                       Each row carries penalty of all 200 columns.
  2. Index inefficiency: Indexes span all entity types.
                          Less selective. Wrong cardinality estimates.
  3. Query planner confusion: Statistics are diluted by type mixing.
                               Wrong execution plans. Slow queries.
  4. System-wide schema changes: Add a product column -> change affects
                                  users, companies, orders code too.
  5. Constraint impossibility: Cannot do NOT NULL, UNIQUE, FK constraints
                                on type-specific columns without workarounds.

The Three Solutions:

  1. Separate Tables (most cases):
     CREATE TABLE users (...);
     CREATE TABLE companies (...);
     CREATE TABLE products (...);
     CREATE TABLE orders (...);
     -> Correct constraints. Efficient storage. Fast queries.
     -> Accurate statistics. Proper indexes. Zero NULL waste.

  2. Single Table Inheritance (limited, appropriate use):
     When: >80% shared columns, similar access patterns, <20% NULL ratio
     -> STI is APPROPRIATE for closely related types
     -> STI is NOT appropriate for unrelated entities (the God Table)

  3. Class Table Inheritance (hybrid):
     entities_base: id, entity_type, name, status, created_at
     users_ext:     entity_id, email, password_hash, subscription_tier
     companies_ext: entity_id, tax_id, industry, revenue
     -> Base table: cross-type queries (notifications, activity feeds)
     -> Extension tables: zero NULLs, correct constraints per type

The Diagnostic Test:
  Measure NULL density: SELECT attname, null_frac FROM pg_stats WHERE tablename='X'
  null_frac > 0.30 for a column = that column does not belong to all row types.
  null_frac > 0.50 for multiple columns = likely a God Table situation.
  Separate those columns into type-specific tables.

The Golden Rule:
  A NULL value in a column means "this attribute does not apply to this row."
  A column that is NULL for 50% of rows means that column belongs to only
  50% of the entities in the table.
  Those entities should be in their own table.
  NULL is not a data value. It is a schema design signal.
  When you see many NULLs, you are seeing entities that do not belong together.
======================================================================
```

## Key Takeaways — The Principles to Carry Forward

The God Table teaches a lesson that every database designer must internalize: **NULL is not an empty value — it is a schema design signal**. When a column is NULL for a large fraction of rows in a table, it is the database's way of telling you that those rows do not have that attribute — which means those rows are a different kind of entity than the rows where the column is populated. Different kinds of entities belong in different tables.

The instinct that creates God Tables — the desire to abstract away differences and create a unified, flexible structure — is a reasonable engineering instinct in the right context. In object-oriented programming, inheritance and polymorphism are powerful tools. But the relational database model is not an object model, and the tools that work for object hierarchies (single inheritance table, generic entity IDs) produce the wrong results at the database layer. Relational databases are optimized for structured, typed, dense data. The more a table deviates from "every column applies to every row," the more it deviates from what the relational model is good at.

The correct mapping of the flexibility instinct to the database layer is not the God Table — it is the combination of properly normalized tables for stable, known entity types, JSONB columns for genuinely flexible attributes within a type, and Class Table Inheritance for the cases where cross-type unified references genuinely matter. These tools together provide all the flexibility that any real application needs, without sacrificing the type safety, constraint support, index efficiency, and query performance that the relational model provides.

A NULL-heavy wide table is always a sign that multiple entities are being forced into one schema. Separate them. Let each entity type own its columns, its constraints, and its indexes. The brief inconvenience of writing `JOIN` queries for cross-type operations is far less painful than the long-term performance, maintainability, and correctness problems that the God Table inevitably creates.
