# Case Study 07 — The Missing Soft Delete Index

---

## The Setup — The "Safe" Deletion That Crippled the Database

A product team chooses the soft delete pattern for their users table. The reasoning is sound: users who delete their accounts might want to reactivate them; compliance requirements mandate retaining user data for regulatory audits; the history of user activity must be preserved even after account closure. Instead of physically removing rows with `DELETE`, the application sets a `deleted_at` timestamp when a user closes their account. All queries that fetch active users add `WHERE deleted_at IS NULL` to filter out the deleted ones.

The schema:

```sql
CREATE TABLE users (
    id            BIGSERIAL    PRIMARY KEY,
    email         VARCHAR(254) NOT NULL UNIQUE,
    name          VARCHAR(100) NOT NULL,
    deleted_at    TIMESTAMPTZ  NULL,  -- NULL = active, timestamp = deleted
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- Standard index on email for login lookup:
CREATE INDEX idx_users_email ON users (email);
-- An index on id (primary key, already exists).
-- No partial index on deleted_at IS NULL.
```

The application adds `WHERE deleted_at IS NULL` to every query that should operate on active users. In the repository layer:

```go
func GetActiveUserByEmail(db *sql.DB, email string) (*User, error) {
    var u User
    err := db.QueryRow(`
        SELECT id, email, name, created_at
        FROM users
        WHERE email = $1
          AND deleted_at IS NULL
    `, email).Scan(&u.ID, &u.Email, &u.Name, &u.CreatedAt)
    return &u, err
}
```

In development with 10,000 users, this query runs in 1 millisecond. The team ships. Two years later, the `users` table has 100 million rows. Ninety million are active (`deleted_at IS NULL`). Ten million are deleted (`deleted_at IS NOT NULL`). The `WHERE email = $1 AND deleted_at IS NULL` query is now taking 800 milliseconds. The email lookup is using the `idx_users_email` index correctly — it finds the single row with that email address in under a millisecond. But then the `AND deleted_at IS NULL` condition must be verified for that row, which costs nothing on its own.

The real problem is elsewhere. Every other query in the application that does not have an email-specific filter but needs active users — listing users for an admin panel, counting active users by region, finding users who signed up in the last 30 days, fetching users for a batch notification job — all of these queries must scan the entire 100-million-row table, reading ninety million active rows and ten million deleted rows, discarding the ten million, and returning the ninety million. Every single one of these queries is a full sequential scan.

The engineering team adds a `WHERE deleted_at IS NULL` condition to every query, thinking they are filtering correctly. What they do not realize is that without a supporting index, `WHERE deleted_at IS NULL` on a 100-million-row table is not a filter — it is a full table scan with a filter applied afterward. The condition does not reduce the I/O. It reduces the output. Every row in the table is still read. Every page in the table is still loaded into memory. Only after all 100 million rows have been visited does the database discard the 10 million deleted ones. The condition is evaluated on each row, not used to select rows.

---

## Why Standard Indexes Cannot Help `WHERE deleted_at IS NULL`

To understand why the soft delete pattern without a partial index is a performance trap, you need to understand how B-tree indexes handle NULL values and why a standard full-column index on `deleted_at` is paradoxically useless for the most common query.

A standard B-tree index on `deleted_at` stores an ordered list of all non-NULL values in the column, along with pointers to the table rows that contain those values. NULL values are not stored in a standard B-tree index — they are excluded because NULL has no defined ordering relationship in SQL (NULL is not greater than, equal to, or less than any value). This has two consequences for the soft delete pattern:

**Consequence One:** A query `WHERE deleted_at IS NULL` cannot use a standard B-tree index on `deleted_at` at all, because the index does not contain any entries for NULL rows. To find all rows where `deleted_at IS NULL`, the database must scan the entire table and check the column value for every row — a full sequential scan.

**Consequence Two:** A query `WHERE deleted_at IS NOT NULL` (finding deleted users) can potentially use the standard index, because it is looking for specific non-NULL values that are in the index. But this query is rare — most applications rarely need to find deleted users.

The situation is deeply counterintuitive: the most common query pattern in a soft-delete system (`WHERE deleted_at IS NULL`, which returns 90% of rows) cannot use any standard index. The rare query (`WHERE deleted_at IS NOT NULL`, returning 10% of rows) could in principle use a standard index, but even then the low selectivity (10% of rows) means a full scan is often chosen by the planner anyway.

```
Why a Standard Index on deleted_at IS Useless for IS NULL Queries:
======================================================================

  Standard B-tree index on deleted_at (100M rows):
  +----------------------------------+
  | B-tree index contents:           |
  |   2024-01-15 10:23:00+00 -> row  |
  |   2024-01-15 11:04:22+00 -> row  |
  |   ...                            |
  |   10,000,000 entries (non-NULL)  |
  |   NULL values: NOT STORED        |
  +----------------------------------+

  Query: WHERE deleted_at IS NULL
  Database asks index: "Where are all the NULL entries?"
  Index answers:       "I have no NULL entries. I cannot help."
  Database response:   Sequential scan of all 100M rows.
  I/O: 100M row reads. Returns 90M rows. Discards 10M. Slow.

  Query: WHERE deleted_at IS NOT NULL
  Database asks index: "Where are all the non-NULL entries?"
  Index answers:       "Here are 10M entries."
  Database may use index, but: 10% selectivity means often prefers seq scan.

  The paradox:
  The query we run MOST OFTEN (IS NULL = 90% of table) gets NO index benefit.
  The query we run LEAST OFTEN (IS NOT NULL = 10% of table) may get index benefit.
  A standard index on deleted_at is optimizing for the rare case,
  completely failing the common case. It is useless for the soft-delete pattern.

  Standard index on deleted_at: ~300MB (10M non-NULL entries)
  Benefit for IS NULL queries:  NONE
  Storage cost:                 300MB of index that does not help
  Maintenance cost:             Written on every soft-delete operation
  Conclusion: Do NOT create a standard index on deleted_at. It is waste.
======================================================================
```

## The Partial Index — The Correct Solution

A **partial index** is an index that covers only a subset of rows in a table, defined by a `WHERE` clause in the `CREATE INDEX` statement. Only rows that satisfy the `WHERE` condition are included in the index. Rows that do not satisfy the condition are not indexed at all.

For the soft delete pattern, a partial index on active rows is the exact solution:

```sql
-- Partial index: only indexes rows where deleted_at IS NULL (active users)
-- This index covers the 90 million active rows. The 10 million deleted rows
-- are NOT in this index at all.
CREATE INDEX CONCURRENTLY idx_users_active
ON users (id)
WHERE deleted_at IS NULL;

-- The index is small: 90M entries for id (8 bytes each) ≈ 720MB, not 800MB
-- But more importantly: the index covers EXACTLY the rows most queries need.
-- The query planner can use this index for queries that include deleted_at IS NULL.
```

```
Partial Index on (id) WHERE deleted_at IS NULL:
======================================================================

  Partial index contents (90M rows, active users only):
  +----------------------------------+
  | B-tree index contents:           |
  |   id=1       -> row 1   (active) |
  |   id=2       -> row 2   (active) |
  |   id=3       (DELETED — not here)|
  |   id=4       -> row 4   (active) |
  |   ...                            |
  |   90,000,000 entries             |
  |   Deleted rows: NOT STORED       |
  +----------------------------------+

  Query: WHERE deleted_at IS NULL AND id = 42
  Database: checks partial index. id=42 is in the index -> active user found.
  I/O: 1 index lookup + 1 heap fetch. Instant.

  Query: WHERE deleted_at IS NULL AND created_at > NOW() - INTERVAL '30 days'
  Database: Hmm — the index on (id) doesn't help with created_at range.
  -> Use idx_users_active (partial) to satisfy deleted_at IS NULL,
     then apply created_at filter on the 90M rows. Still a partial scan.
  -> Better: add created_at to the partial index (see below).
======================================================================
```

However, the value of the partial index becomes much greater when it is designed to match the actual query patterns of the application. A partial index on `(id)` helps the planner know which rows are active, but the most common queries need to search by specific columns — email, name, region, created_at — while also filtering on active status. The partial index must be designed to cover those search columns:

```sql
-- The correct set of partial indexes for a soft-delete system:

-- 1. Email lookup for active users (login, uniqueness check):
CREATE UNIQUE INDEX CONCURRENTLY idx_users_email_active
ON users (email)
WHERE deleted_at IS NULL;
-- Unique: enforces email uniqueness AMONG ACTIVE USERS ONLY.
-- A deleted user's email can be re-used by a new registration.
-- This constraint is impossible with a standard UNIQUE index on email
-- (which would prevent re-use even after deletion).
-- Covers: WHERE email = $1 AND deleted_at IS NULL

-- 2. Temporal queries — active users who signed up recently:
CREATE INDEX CONCURRENTLY idx_users_created_active
ON users (created_at DESC)
WHERE deleted_at IS NULL;
-- Covers: WHERE deleted_at IS NULL AND created_at > NOW() - INTERVAL '30 days'
-- ORDER BY created_at DESC LIMIT 100

-- 3. Combined lookup for admin dashboards and batch jobs:
CREATE INDEX CONCURRENTLY idx_users_active_id
ON users (id)
WHERE deleted_at IS NULL;
-- Covers: WHERE deleted_at IS NULL (general active user scans)
-- Smaller than a full index (excludes deleted rows), faster for planners.

-- For a query that also filters by region:
CREATE INDEX CONCURRENTLY idx_users_region_active
ON users (region, created_at DESC)
WHERE deleted_at IS NULL;
-- Covers: WHERE deleted_at IS NULL AND region = 'APAC'
-- ORDER BY created_at DESC
```

## The Partial Index vs. Standard Index — Size and Performance Comparison

The storage and performance advantages of a partial index over a standard index are not marginal — they are proportional to the fraction of the table that is excluded. For the soft delete pattern where 90% of rows are active, the partial index on active rows is very similar in size to a full index (90% of rows). But as the table ages and more rows are deleted, the advantage grows. A table where 50% of rows are deleted will have a partial index half the size of a full index, with half the maintenance overhead.

The more important advantage is **semantic correctness**: the partial index contains exactly the rows that the queries care about, making it more likely that the query planner will choose to use it, and making every use of the index directly relevant:

```
Full Index vs. Partial Index — The Comparison Over Time:
======================================================================

  Table: users (100M rows)
  Active rows: 90M (90%)
  Deleted rows: 10M (10%)

  Standard index on email (all rows):
    Index size:           ~3.6 GB (100M entries × ~36 bytes per entry)
    Covers:               All rows (active + deleted)
    For IS NULL queries:  CANNOT use for NULL filtering
    For IS NOT NULL:      Can use (rarely needed)
    Maintenance:          Written on every user registration AND every deletion
    Cache efficiency:     Poor — index contains deleted rows that queries skip

  Partial index on email WHERE deleted_at IS NULL:
    Index size:           ~3.24 GB (90M entries × ~36 bytes)
    Covers:               Only active rows (exactly what queries need)
    For IS NULL queries:  YES — this index was built FOR these queries
    For IS NOT NULL:      Cannot use (deleted users not in index — correct!)
    Maintenance:          Written on registration. REMOVED on deletion.
    Cache efficiency:     Excellent — every entry in the index is relevant

  As the table ages (1 year later, 30% deleted):
  Active rows: 70M. Deleted rows: 30M.

  Standard email index:  ~3.6 GB (unchanged — still covers all 100M rows)
  Partial email index:   ~2.52 GB (shrinks! 70M entries × 36 bytes)

  The partial index gets SMALLER and FASTER as more rows are soft-deleted.
  The standard index stays the same size forever.
  The partial index tracks only the relevant population.
======================================================================
```

## The Unique Partial Index — The Bonus Benefit

One of the most powerful and least-known advantages of the partial index for soft delete is that it enables **conditional uniqueness**: email addresses can be unique among active users only, allowing a deleted user's email to be re-registered by a new user. This is a common business requirement that is impossible to implement with a standard unique constraint:

```sql
-- Standard UNIQUE constraint: prevents re-use of email after deletion
-- (WRONG for most soft-delete systems)
CREATE UNIQUE INDEX idx_users_email_wrong ON users (email);
-- Problem: if user alice@example.com deletes her account and a new person
-- tries to register with alice@example.com, this index BLOCKS the registration.
-- The deleted row still exists in the table with email='alice@example.com'.
-- The new registration fails with "duplicate key" error.

-- Unique PARTIAL index: enforces uniqueness only among active users
-- (CORRECT for soft-delete systems with email re-registration support)
CREATE UNIQUE INDEX idx_users_email_active
ON users (email)
WHERE deleted_at IS NULL;
-- Now: deleted alice@example.com does NOT appear in this index.
-- New registration with alice@example.com: unique check passes, registration succeeds.
-- Active users: email uniqueness still fully enforced.
-- This is both a performance optimization AND a business logic implementation.
```

## Designing Partial Indexes for Common Soft-Delete Query Patterns

The soft delete pattern generates a predictable set of query shapes that appear in every application using it. Each query shape needs a corresponding partial index. Designing these indexes upfront — at schema creation time — prevents the full-scan-on-every-query disaster:

```sql
-- QUERY SHAPE 1: Find active record by primary key
-- Pattern: WHERE id = $1 AND deleted_at IS NULL
-- Solution: The primary key index already handles id. The partial index
-- helps the planner confirm the row is active without a heap fetch.
-- A separate partial index on (id) is of marginal value if the PK is used.
-- The main benefit comes from compound cases.

-- QUERY SHAPE 2: Find active record by unique field (email, username, slug)
-- Pattern: WHERE email = $1 AND deleted_at IS NULL
CREATE UNIQUE INDEX idx_users_email_active ON users (email) WHERE deleted_at IS NULL;

-- QUERY SHAPE 3: List active records with ordering and pagination
-- Pattern: WHERE deleted_at IS NULL ORDER BY created_at DESC LIMIT 50
CREATE INDEX idx_users_created_active ON users (created_at DESC) WHERE deleted_at IS NULL;

-- QUERY SHAPE 4: Filter active records by categorical field
-- Pattern: WHERE deleted_at IS NULL AND region = 'APAC' ORDER BY created_at DESC
CREATE INDEX idx_users_region_created_active
ON users (region, created_at DESC)
WHERE deleted_at IS NULL;

-- QUERY SHAPE 5: Count active records (admin dashboard, monitoring)
-- Pattern: SELECT COUNT(*) FROM users WHERE deleted_at IS NULL
-- Partial index on any column allows index-only scan for COUNT:
CREATE INDEX idx_users_active_count ON users (id) WHERE deleted_at IS NULL;
-- COUNT(*) with this index: PostgreSQL scans only the partial index (small, fast)
-- instead of the full table (100M rows, slow).

-- QUERY SHAPE 6: Active records with status filter
-- Pattern: WHERE deleted_at IS NULL AND status = 'premium' AND region = 'EU'
CREATE INDEX idx_users_status_region_active
ON users (status, region)
WHERE deleted_at IS NULL;

-- QUERY SHAPE 7: Find recently active records
-- Pattern: WHERE deleted_at IS NULL AND last_login_at > NOW() - INTERVAL '30 days'
CREATE INDEX idx_users_last_login_active
ON users (last_login_at DESC)
WHERE deleted_at IS NULL;
```

## The `is_deleted BOOLEAN` Alternative — When Nullable Timestamps Create Confusion

Some teams prefer a `is_deleted BOOLEAN NOT NULL DEFAULT false` column over `deleted_at TIMESTAMPTZ NULL`. The boolean approach has clearer semantics for the `IS NULL` check and allows slightly simpler partial index syntax, but loses the "when was it deleted?" information. For most systems, `deleted_at TIMESTAMPTZ` is strictly better because it provides both the deletion flag and the deletion timestamp in one column. However, when teams use both (`is_deleted` AND `deleted_at`), the system often becomes inconsistent — the two flags can disagree.

The best practice is `deleted_at TIMESTAMPTZ NULL` as the single source of truth, with the partial index on `WHERE deleted_at IS NULL`:

```sql
-- Recommended: deleted_at TIMESTAMPTZ as single truth (gives timestamp + flag)
CREATE TABLE posts (
    id          BIGSERIAL    PRIMARY KEY,
    author_id   BIGINT       NOT NULL REFERENCES users(id),
    title       VARCHAR(300) NOT NULL,
    body        TEXT         NOT NULL,
    deleted_at  TIMESTAMPTZ  NULL,        -- NULL=active, timestamp=deleted
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- Partial indexes for the posts table:
CREATE INDEX idx_posts_author_active
ON posts (author_id, created_at DESC)
WHERE deleted_at IS NULL;
-- "Show me all active posts by this author, newest first"

CREATE INDEX idx_posts_created_active
ON posts (created_at DESC)
WHERE deleted_at IS NULL;
-- "Show me the 50 most recently created active posts (home feed)"

-- Soft delete query — sets deleted_at to now, removing from partial index:
UPDATE posts SET deleted_at = NOW() WHERE id = $1 AND deleted_at IS NULL;

-- After this UPDATE, the row is automatically excluded from all partial indexes.
-- No manual index cleanup. PostgreSQL maintains the partial index automatically:
-- The deleted row fails the WHERE deleted_at IS NULL condition and is removed
-- from the partial index entries. This happens automatically on UPDATE.

-- Restore (undelete) — sets deleted_at back to NULL, re-adding to partial index:
UPDATE posts SET deleted_at = NULL WHERE id = $1 AND deleted_at IS NOT NULL;
-- The row re-satisfies WHERE deleted_at IS NULL and is automatically re-added
-- to the partial index. Undelete is free of index maintenance complexity.
```

## A Complete Soft-Delete Schema Template

Here is a complete, production-ready soft-delete schema for a common `users` table, with all the correct partial indexes designed upfront:

```sql
-- Complete soft-delete users table with all correct partial indexes:
CREATE TABLE users (
    id                BIGSERIAL       PRIMARY KEY,
    email             VARCHAR(254)    NOT NULL,
    username          VARCHAR(50)     NOT NULL,
    name              VARCHAR(100)    NOT NULL    CHECK (LENGTH(TRIM(name)) >= 2),
    status            VARCHAR(20)     NOT NULL    DEFAULT 'active'
                                      CHECK (status IN ('active', 'suspended', 'pending')),
    region            VARCHAR(10),
    subscription_tier VARCHAR(20)     NOT NULL    DEFAULT 'free',
    last_login_at     TIMESTAMPTZ,
    deleted_at        TIMESTAMPTZ     NULL,       -- NULL = active (soft delete)
    deleted_by        BIGINT,                     -- Who performed the deletion
    created_at        TIMESTAMPTZ     NOT NULL    DEFAULT NOW(),
    updated_at        TIMESTAMPTZ     NOT NULL    DEFAULT NOW()
);

-- ============================================================
-- PARTIAL INDEXES (the critical ones for soft-delete systems):
-- ============================================================

-- Email uniqueness: enforced only among active users
-- Allows re-registration with a previously deleted email
CREATE UNIQUE INDEX idx_users_email_active
ON users (email)
WHERE deleted_at IS NULL;

-- Username uniqueness: enforced only among active users
CREATE UNIQUE INDEX idx_users_username_active
ON users (username)
WHERE deleted_at IS NULL;

-- Active users by creation time (newest users list, admin dashboards)
CREATE INDEX idx_users_created_active
ON users (created_at DESC)
WHERE deleted_at IS NULL;

-- Active users by last login (inactive user detection, re-engagement campaigns)
CREATE INDEX idx_users_last_login_active
ON users (last_login_at DESC NULLS LAST)
WHERE deleted_at IS NULL;

-- Active users by region (regional analytics, targeted notifications)
CREATE INDEX idx_users_region_active
ON users (region, created_at DESC)
WHERE deleted_at IS NULL;

-- Active users by subscription tier (billing, plan upgrade campaigns)
CREATE INDEX idx_users_tier_active
ON users (subscription_tier, created_at DESC)
WHERE deleted_at IS NULL;

-- Active users by status (moderation queue, suspended user review)
CREATE INDEX idx_users_status_active
ON users (status)
WHERE deleted_at IS NULL;

-- ============================================================
-- STANDARD INDEXES (for queries that DO need deleted records):
-- ============================================================

-- Look up any user by ID (includes deleted — for admin recovery panels)
-- (Primary key already provides this)

-- Find all accounts deleted by a specific admin (audit trail)
CREATE INDEX idx_users_deleted_by
ON users (deleted_by, deleted_at DESC)
WHERE deleted_at IS NOT NULL;  -- Partial: only deleted users

-- ============================================================
-- SOFT DELETE OPERATIONS:
-- ============================================================

-- Soft delete: sets deleted_at, row automatically leaves partial indexes
-- Soft delete: sets deleted_at, row automatically leaves partial indexes
-- Use deleted_at IS NULL in WHERE to prevent double-deletion errors
UPDATE users
SET deleted_at = NOW(), deleted_by = $2, updated_at = NOW()
WHERE id = $1
  AND deleted_at IS NULL;   -- Idempotent: no-op if already deleted

-- Restore (undelete): clears deleted_at, row automatically rejoins partial indexes
UPDATE users
SET deleted_at = NULL, deleted_by = NULL, updated_at = NOW()
WHERE id = $1
  AND deleted_at IS NOT NULL;  -- Only restore if currently deleted

-- Hard delete after retention period (GDPR compliance, after X years):
DELETE FROM users
WHERE deleted_at < NOW() - INTERVAL '2 years';
-- Use batch delete pattern (Case Study 06 Concurrency) to avoid lock explosion
```

  -> CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL

The Rule:
  Any table with deleted_at IS NULL MUST have at least one partial index
  with WHERE deleted_at IS NULL that covers the most common filter columns.
  Soft delete without a partial index = full-table-scan-on-every-query.
  Design the partial indexes at the same time as you design the soft delete.
  Not after. Not when performance complaints arrive. At design time.

## Key Takeaways — The Principles to Carry Forward

The missing soft delete index is a perfect example of a pattern that is conceptually clean but operationally incomplete without its supporting infrastructure. The soft delete pattern — using `deleted_at IS NULL` to distinguish active from inactive records — is a well-understood, widely-used, and genuinely useful design choice. It preserves history, enables recovery, satisfies audit requirements, and avoids the complexity of cascade deletions. None of those benefits disappear. But the pattern requires a partial index to function correctly at scale. Without the partial index, every query that uses the soft delete filter becomes a full table scan, and the pattern that was chosen to make deletions safer instead makes queries catastrophically slower.

The two principles that this case study crystallizes are deeply connected. The first is that **NULL values are invisible to B-tree indexes** — a query `WHERE column IS NULL` cannot be served by a standard index, and a developer who adds `AND deleted_at IS NULL` to a query expecting it to "narrow down" the result set via an index is mistaken. The WHERE clause narrows the output, not the I/O. Only an index that specifically covers the rows of interest can narrow the I/O.

The second principle is that **partial indexes are underused but extraordinarily powerful**. A partial index is not an approximation of a full index — it is an index that is precisely tailored to a specific query predicate. It contains exactly the rows the queries care about, which makes it smaller, faster to scan, more cache-efficient, and automatically maintained by the database as rows move in and out of the indexed subset. For any table with a discriminating condition that most queries share — soft delete being the canonical example, but also `status = 'active'`, `is_verified = true`, `tier = 'premium'` — a partial index on that condition is the architecturally correct choice, and a missing partial index is a full-table-scan hiding in plain sight inside every query in the codebase.
