# The DISTINCT Performance Trap

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. The Query That Looks Trivially Simple

You are building an analytics feature. The product team wants to know how many unique users have generated any event in the last 30 days — active user counts for a monthly dashboard. You look at your `events` table and write what feels like the most direct expression of the question:

```sql
SELECT DISTINCT user_id
FROM events
WHERE created_at > NOW() - INTERVAL '30 days';
```

Simple. Clean. Correct. On your development database with 50,000 events, it returns in 40 milliseconds. You feel good about it. You deploy.

Four months later, your events table has 800 million rows — which is normal for a product that logs every user action. The same query now takes 12 minutes. Your analytics dashboard, which calls this endpoint, times out on every load. An engineer adds a caching layer in front of it as a temporary fix, which helps — until the cache expires and the underlying query brings the database to its knees again.

The root problem is that `DISTINCT` is not a simple filter. It is a fundamentally expensive operation that the database must perform on the entire result set, and its cost grows with the size of that result set in ways that most developers do not anticipate when writing what looks like a trivial query.

---

## 2. What DISTINCT Actually Requires the Database to Do

The word `DISTINCT` in a SQL query gives the database a deceptively simple instruction: "Remove duplicate rows from the result." Simple to state. Expensive to execute. To understand why, think about what it means to eliminate duplicates from a large set.

Imagine you have a pile of 200 million cards, each with a user ID written on it. You want to remove the duplicates and keep only one card per user ID. There are exactly two ways to do this. The first way: sort the entire pile. Once sorted, all cards with the same ID sit next to each other, so you can walk through the sorted pile and discard every card that matches the one before it. The second way: build a hash table. For each card you pick up, check whether that user ID is already in the hash table. If it is, discard the card. If it is not, put it in the hash table and keep the card. When you are done, the hash table contains one entry per unique user ID.

These are exactly the two strategies a database engine uses to implement `DISTINCT`:

```
  How DISTINCT is Implemented Internally
  ========================================

  Strategy 1: Sort-based deduplication
  ──────────────────────────────────────
  Step 1: Retrieve all qualifying rows (full result before deduplication)
  Step 2: Sort all rows by the SELECT columns
          (in-memory if fits in work_mem, spills to disk if not)
  Step 3: Walk the sorted result and emit only rows that differ
          from the previous row

  Cost: O(N log N) sort + O(N) scan
  Memory: must hold sorted result in work_mem or spill to disk

  Strategy 2: Hash-based deduplication
  ──────────────────────────────────────
  Step 1: Retrieve all qualifying rows
  Step 2: For each row, compute a hash of the DISTINCT columns
          Check whether this hash is already in the hash table
          If not: emit the row, add to hash table
          If yes: discard the row
  Step 3: Return all emitted rows

  Cost: O(N) hash operations
  Memory: must hold hash table in work_mem or spill to disk

  Both strategies share a fundamental property:
  ┌──────────────────────────────────────────────────────────────────┐
  │ DISTINCT requires processing the ENTIRE qualifying result set    │
  │ before it can return even a single row.                          │
  │                                                                  │
  │ The database cannot return user_id=1 until it has seen ALL       │
  │ other rows — because some later row might also be user_id=1,     │
  │ and without seeing all rows, it cannot know whether user_id=1   │
  │ is truly unique in the result.                                   │
  └──────────────────────────────────────────────────────────────────┘
```

That last property is the core cost. `DISTINCT` is a **blocking operation** — it must consume the entire input before it can produce any output. A regular `SELECT` with a `LIMIT` can return the first N rows as soon as it finds them. A `SELECT DISTINCT` with a `LIMIT` cannot — it must gather all qualifying rows, deduplicate them, and only then apply the limit. The `LIMIT` saves network bandwidth on the way out, but it does nothing to reduce the deduplication work inside the database.

## 3. The Mental Model — DISTINCT Is a Hidden GROUP BY

The single most useful mental model for thinking about `DISTINCT` is this: **DISTINCT is exactly equivalent to GROUP BY on all the SELECT columns, with no aggregate functions**. They produce the same result through the same underlying mechanism, and they have the same cost.

```sql
-- These two queries are semantically identical
-- and have identical execution plans in PostgreSQL:

SELECT DISTINCT user_id
FROM events
WHERE created_at > NOW() - INTERVAL '30 days';

-- Is exactly the same as:

SELECT user_id
FROM events
WHERE created_at > NOW() - INTERVAL '30 days'
GROUP BY user_id;
```

Run `EXPLAIN` on both and you will see the same plan — typically a `HashAggregate` or `Sort → Unique` node on top of the table scan. The database does not treat these differently. They are two ways of writing the same operation.

Why does this mental model matter? Because when you see `DISTINCT` in a query, you should mentally substitute `GROUP BY` and ask: "Would I write this as a GROUP BY on every column in my SELECT list?" Usually the answer makes the cost more viscerally obvious. A `GROUP BY` on 200 million rows sounds expensive. A `DISTINCT` on 200 million rows sounds simple — but they are the same thing.

```
  DISTINCT = GROUP BY, Same Execution Plan
  ==========================================

  SELECT DISTINCT user_id FROM events WHERE created_at > NOW() - '30d';

  EXPLAIN output:
  HashAggregate  (cost=... rows=500000 ...)
    Group Key: user_id
    ->  Index Scan on idx_events_created_at  (... rows=200000000 ...)
          Index Cond: (created_at > (now() - '30 days'::interval))

  ← Same "HashAggregate" node you would see with GROUP BY user_id
  ← 200 million rows must flow through the HashAggregate
  ← Hash table for 500,000 unique users must fit in work_mem

  Rewrite with GROUP BY — identical plan, identical cost:

  SELECT user_id FROM events WHERE created_at > NOW() - '30d' GROUP BY user_id;

  HashAggregate  (cost=... rows=500000 ...)   ← Same node, same cost
    Group Key: user_id
    ->  Index Scan on idx_events_created_at  (... rows=200000000 ...)
```

When you see the execution plan, the `HashAggregate` or `Sort → Unique` node tells you exactly what the database is doing. The `rows=200000000` beneath it tells you how much input it has to process to produce the `rows=500000` distinct user IDs. Two hundred million rows processed to produce five hundred thousand results — a 400× reduction ratio that the database pays for in full.

## 4. Why DISTINCT Causes Sort Spills

The link between `DISTINCT` and sort spills is direct and important. When the database uses the sort-based strategy for deduplication, it faces the same memory constraint described in the ORDER BY Sort Spill anti-pattern: the `work_mem` parameter limits how much data can be held in memory during the sort. When the qualifying rows exceed `work_mem`, the sort spills to disk.

For the events query above — 200 million qualifying rows of, say, 50 bytes each — the data to be sorted is approximately 10GB. With a default `work_mem` of 4MB, this triggers thousands of sort runs and multiple merge passes. The diagnostic signature is identical to what we saw in the sort spill anti-pattern, now attached to a DISTINCT query:

```sql
EXPLAIN ANALYZE
SELECT DISTINCT user_id
FROM events
WHERE created_at > NOW() - INTERVAL '30 days';
```

```
HashAggregate  (cost=4821983.00..4826983.00 rows=500000 width=8)
               (actual time=724831.228..724833.441 rows=500000 loops=1)
  Group Key: user_id
  Batches: 147  Memory Usage: 4096kB  Disk Usage: 892831kB
  ← "Batches: 147" means the hash table spilled 147 times to disk
  ← "Disk Usage: 892831kB" = ~872MB of temporary disk I/O just for the hash
  ->  Index Scan using idx_events_created_at on events
        (cost=0.56..3821983.00 rows=200000000 width=8)
        (actual time=0.018..448291.331 rows=200000000 loops=1)
        Index Cond: (created_at > (now() - '30 days'::interval))

Planning Time: 0.441 ms
Execution Time: 724833.441 ms   ← 12 minutes
```

`Batches: 147` is the key signal for hash-based deduplication spill — the hash table was too large for `work_mem`, so it was split into 147 separate batches, each processed independently and merged. `Disk Usage: 892831kB` tells you how much temporary disk was written for this single query execution. Nearly a gigabyte of disk I/O, 147 passes over the data in batches, for a query that looks like a simple unique-values request.

## 5. The Scale Trap — Where DISTINCT Gets Dangerous

The cost of `DISTINCT` is governed by two numbers that both grow independently as your system scales: the number of qualifying input rows (driven by data volume and filter selectivity) and the number of distinct output values (driven by data cardinality). Both matter, and their interaction determines the true cost.

```
  DISTINCT Cost Dimensions
  =========================

  Cost driver 1: Input rows (must all be processed)
  ─────────────────────────────────────────────────
  events in last 30 days: 1,000     → fast (fits in work_mem easily)
  events in last 30 days: 1,000,000 → manageable (may fit in work_mem)
  events in last 30 days: 200,000,000 → disk spill, slow

  Cost driver 2: Distinct output values (hash table size)
  ───────────────────────────────────────────────────────
  Unique user_ids: 500     → tiny hash table, always in memory
  Unique user_ids: 500,000 → medium hash table, may need work_mem
  Unique user_ids: 10,000,000 → large hash table, likely spills

  The expensive combination:
  ┌─────────────────────────────────────────────────────────┐
  │ High input rows + high distinct count                   │
  │ = processing 200M rows to produce 10M distinct values  │
  │ = massive hash table + massive sort + disk spill        │
  │ = minutes of execution time                             │
  └─────────────────────────────────────────────────────────┘

  The misleadingly cheap combination (development trap):
  ┌─────────────────────────────────────────────────────────┐
  │ Low input rows + low distinct count                     │
  │ = processing 5,000 rows to produce 200 distinct values  │
  │ = tiny hash table, entirely in work_mem                 │
  │ = feels instant in development                          │
  └─────────────────────────────────────────────────────────┘

  As the product grows, both numbers increase.
  The query that felt instant at launch becomes the query
  that brings down production.
```

There is also a particularly insidious form of DISTINCT misuse that compounds the problem: `SELECT DISTINCT` across multiple columns, especially when those columns include wide types like VARCHAR, TEXT, or JSONB. More columns in the SELECT list means more data per row for the hash function, larger hash table entries, faster memory exhaustion, and earlier spill to disk.

## 6. Solution One — EXISTS for Presence Checking

The most important insight for fixing DISTINCT queries is recognising what question the query is really answering and whether there is a more targeted way to express it. The most common reason developers reach for `SELECT DISTINCT user_id FROM events WHERE ...` is to answer one of two questions: "Which users did X?" or "Did this specific user do X?"

For the second question — "Did this specific user do X?" — `SELECT DISTINCT` is a dramatic overkill. The right tool is `EXISTS`, which short-circuits as soon as it finds the first qualifying row. It never needs to scan all rows, never builds a deduplication structure, and never spills to disk.

```sql
-- Question: "Show me all users who have generated an event in the last 30 days"

-- ❌ DISTINCT approach — processes ALL 200M qualifying events
SELECT DISTINCT user_id
FROM events
WHERE created_at > NOW() - INTERVAL '30 days';

-- ✅ EXISTS approach — for each user, stops at the FIRST matching event
SELECT u.id, u.name
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM events e
    WHERE e.user_id = u.id
      AND e.created_at > NOW() - INTERVAL '30 days'
);
```

The `EXISTS` version approaches the problem from the users table outward. For each user, it checks whether any event exists in the last 30 days. The moment it finds one event — the very first one — it stops looking and marks that user as active. If a user has 50,000 events in the last 30 days, `EXISTS` still reads only one of them before moving on.

```
  DISTINCT vs EXISTS — Execution Strategy Comparison
  ====================================================

  User ID 42 has 15,000 events in the last 30 days.

  DISTINCT approach:
    Read event 1 for user 42 → add user_id=42 to hash table
    Read event 2 for user 42 → user_id=42 already in hash, discard
    Read event 3 for user 42 → user_id=42 already in hash, discard
    ...
    Read event 15,000 for user 42 → discard
    Result: user_id=42 included once
    Events read for this user: 15,000

  EXISTS approach:
    Read event 1 for user 42 → EXISTS condition satisfied → STOP
    Result: user 42 included
    Events read for this user: 1

  For a user with 15,000 events: EXISTS reads 15,000× fewer rows.
  This is O(1) per user (with good index) vs O(events_per_user).

  With an index on (user_id, created_at):
  EXISTS: Index Seek to user_id=42, check first entry → done
  DISTINCT: Index Seek to user_id=42, read all 15,000 entries → done
```

For `EXISTS` to achieve this short-circuit behaviour efficiently, the `events` table needs a composite index on `(user_id, created_at)` — so the engine can immediately navigate to a specific user's recent events without scanning unrelated rows.

```sql
-- Index that makes EXISTS fast
CREATE INDEX idx_events_user_created ON events (user_id, created_at DESC);

-- Now EXISTS navigates directly to the target user's recent events
-- and stops at the very first one found
```

PostgreSQL often transforms `EXISTS` subqueries internally into a **semi-join** — an optimised join variant that stops as soon as the first match is found on the inner side, without materialising the full inner result. The execution plan will show this as a `Hash Semi Join` or `Nested Loop Semi Join`, which is significantly more efficient than the full hash aggregation required by DISTINCT.

## 7. Solution Two — Index-Only Scan for DISTINCT on Indexed Columns

When you genuinely need the list of distinct values — not just a presence check — there is a scenario where DISTINCT can be made dramatically more efficient: when the column being deduplicated is a **leading column in an index**, and you need only that column in the result. In this case, the database can perform a **skip scan** or an **index-only scan** that reads only the index, never touching the heap.

The concept is simple. A B-Tree index on `user_id` is already sorted by `user_id`. If you want all distinct `user_id` values, you do not need to read all 200 million rows and deduplicate — you can scan the index, and every time you encounter a new `user_id` value, emit it and skip forward past all entries with that value. Instead of processing 200 million rows, you process only as many index entries as there are distinct users — perhaps 500,000.

```sql
-- If you have an index on events (user_id):
CREATE INDEX idx_events_user_id ON events (user_id);

-- PostgreSQL can use this for a fast distinct scan in some cases
-- especially if combined with the WHERE clause in a covering index:
CREATE INDEX idx_events_user_created ON events (user_id, created_at);

-- With the right index, EXPLAIN may show:
-- Index Only Scan using idx_events_user_created on events
--   Index Cond: (created_at > ...)
-- rather than a full heap scan + hash aggregate
```

However, there is an important caveat: PostgreSQL does not currently implement a true "skip scan" for arbitrary DISTINCT queries the way some other databases do. It can use an index-only scan to avoid touching the heap, but it still reads every qualifying entry in the index, not just one per distinct value. The real benefit of the covering index is avoiding heap access — the deduplication work still happens.

For the scenario of "give me a small list of distinct values from a high-cardinality column", the most reliable route to efficiency is still EXISTS (if presence checking is the real goal) or a materialised view (if you genuinely need the distinct list frequently).

## 8. Solution Three — Materialised Views for Repeated Distinct Aggregations

If the distinct user list is a core analytical result that many queries and dashboards depend on — not a one-off check but a frequently accessed aggregate — pre-computing it as a materialised view is the right architectural choice. The expensive DISTINCT operation runs once per refresh cycle, not once per request.

```sql
-- Pre-compute the distinct active users list
CREATE MATERIALIZED VIEW active_users_last_30d AS
SELECT DISTINCT user_id
FROM events
WHERE created_at > NOW() - INTERVAL '30 days'
WITH DATA;

-- Index the materialised view for fast lookups by user_id
CREATE UNIQUE INDEX idx_active_users_uid ON active_users_last_30d (user_id);

-- Refresh on a schedule (e.g. every hour via pg_cron or an external cron job)
-- This is the expensive operation — happens once per hour, not per request
REFRESH MATERIALIZED VIEW CONCURRENTLY active_users_last_30d;

-- Application queries — instantaneous, reading a small pre-computed table
SELECT COUNT(*) FROM active_users_last_30d;
-- → "How many active users in the last 30 days?"

SELECT a.user_id, u.name
FROM active_users_last_30d a
JOIN users u ON u.id = a.user_id
ORDER BY u.name;
-- → "List of active users with names"

SELECT EXISTS (
    SELECT 1 FROM active_users_last_30d WHERE user_id = $1
);
-- → "Is this specific user active?"
```

The materialised view approach converts a query that takes 12 minutes into one that returns in milliseconds — at the cost of the result being stale by up to the refresh interval (one hour in the example above). For a monthly active users dashboard, one-hour staleness is completely acceptable. For a real-time "is this user currently active" check, it might not be.

```
  Materialised View — Request Pattern Transformation
  ====================================================

  Without materialised view:
  Dashboard load → SELECT DISTINCT on 200M events → 12 minutes → timeout
  Next load → same → 12 minutes → timeout
  50 concurrent users → 50 × 12 minutes of work → DB collapse

  With materialised view (refreshed hourly):
  Hourly refresh → SELECT DISTINCT on 200M events → 12 minutes → stored
  Dashboard load → SELECT COUNT(*) FROM active_users_last_30d → 2ms ✅
  Next load → 2ms ✅
  50 concurrent users → 50 × 2ms → trivial load

  Net effect: 12 minutes of work amortised across all queries in one hour
  The expensive DISTINCT happens once. All consumers benefit.
```

For the concurrent refresh to work correctly — allowing reads to continue while the refresh runs — use `REFRESH MATERIALIZED VIEW CONCURRENTLY`. This requires the materialised view to have a unique index, which is why we created `idx_active_users_uid` above.

## 9. Solution Four — HyperLogLog for Approximate Distinct Counts

For the specific use case of counting distinct values — `SELECT COUNT(DISTINCT user_id)` — there is a powerful and often underused tool for scenarios where an approximate answer is acceptable: **HyperLogLog**. This is a probabilistic data structure that can estimate the count of distinct values across billions of rows using only a few kilobytes of memory, with a typical error rate of less than 1%.

PostgreSQL supports HyperLogLog through the `postgresql-hll` extension. For analytics use cases — "approximately how many unique users visited this week?" — a 0.8% error margin is often entirely acceptable, and the performance improvement over an exact `COUNT(DISTINCT ...)` is enormous.

```sql
-- Enable the HyperLogLog extension
CREATE EXTENSION IF NOT EXISTS hll;

-- Pre-aggregate HLL sketches by day (much faster to maintain than raw data)
CREATE TABLE events_hll_daily (
    event_date  DATE    NOT NULL,
    user_hll    hll     NOT NULL,
    PRIMARY KEY (event_date)
);

-- When inserting events, add to the daily HLL sketch
-- (done in application code or via trigger)
INSERT INTO events_hll_daily (event_date, user_hll)
VALUES (CURRENT_DATE, hll_add(hll_empty(), hll_hash_integer($user_id)))
ON CONFLICT (event_date) DO UPDATE
SET user_hll = hll_union(events_hll_daily.user_hll,
                          hll_add(hll_empty(), hll_hash_integer($user_id)));

-- Query: approximate distinct users over any date range — instant
SELECT ROUND(hll_cardinality(hll_union_agg(user_hll)))::bigint AS approx_distinct_users
FROM events_hll_daily
WHERE event_date >= CURRENT_DATE - INTERVAL '30 days';
```

The query over the HLL table reads 30 rows (one per day), each containing a tiny sketch, unions them in microseconds, and returns an approximate count. Compare this to scanning 200 million event rows for an exact count. For a dashboard showing "2,847,291 active users this month," the difference between displaying "2,847,291" (exact) and "2,849,034" (HLL approximate) is invisible to any business consumer.

In Go, if you are storing HLL sketches as binary blobs, libraries like `axiomhq/hyperloglog` provide the HLL implementation in-process, letting you maintain sketches in Redis or PostgreSQL without the extension:

```go
import "github.com/axiomhq/hyperloglog"

sketch := hyperloglog.New16()  // 16-bit precision, ~0.1% error

// On each event, add the user ID to the sketch
sketch.Insert([]byte(fmt.Sprintf("user:%d", userID)))

// Estimate distinct count — O(1), no scanning
estimate := sketch.Estimate()

// Sketches can be serialised and stored, union'd across time ranges
data, _ := sketch.MarshalBinary()
```

## 10. The DISTINCT on JOIN Problem — Where It Becomes Truly Expensive

A particularly common and expensive pattern is using `DISTINCT` to paper over unintentional row duplication introduced by a JOIN. When you join a one-to-many relationship without aggregating the many side, you get multiple rows per parent record. Developers sometimes reach for `DISTINCT` to collapse those duplicates rather than fixing the underlying query structure.

```sql
-- ❌ DISTINCT to hide row multiplication from JOIN
SELECT DISTINCT u.id, u.name
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at > '2024-01-01';

-- What this actually does:
-- 1. Join users to orders: produces N rows per user (one per order)
-- 2. DISTINCT collapses them back to one row per user
-- 3. You have materialised and then thrown away all the duplicate rows
-- Cost: full JOIN result materialized, then full DISTINCT deduplication

-- ✅ EXISTS — never materialises the order rows at all
SELECT u.id, u.name
FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.user_id = u.id
      AND o.created_at > '2024-01-01'
);

-- ✅ GROUP BY — collapse at aggregate time, not post-factum
SELECT u.id, u.name
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at > '2024-01-01'
GROUP BY u.id, u.name;
```

The `DISTINCT` version first multiplies rows (the join) and then contracts them (the deduplication). It pays the cost of both operations. `EXISTS` never multiplies the rows in the first place — each user is evaluated independently with a short-circuit check. `GROUP BY` contracts rows during the aggregation, not after, making the contraction part of the join processing rather than a separate pass.

This pattern — `DISTINCT` used to undo row multiplication from a JOIN — is one of the most common forms of DISTINCT misuse in production code, because it appears as a simple fix for a confusing result and hides the performance implications entirely.

## 11. Decision Framework — Which Solution for Which Situation

```
  When You Are Tempted to Write SELECT DISTINCT — Decision Tree
  ==============================================================

  What question are you actually answering?
  │
  ├── "Does any record exist that matches X for a given entity?"
  │   (e.g. "has this user done any action in the last 30 days?")
  │   └── Use EXISTS — short-circuits at first match, O(1) per check
  │
  ├── "Which entities have at least one related record matching X?"
  │   (e.g. "show me all users who have an active order")
  │   └── Use EXISTS subquery from the parent table, not DISTINCT on child
  │       → avoids JOIN row explosion + deduplication cost
  │
  ├── "Give me all unique values of column X across the whole table"
  │   (e.g. "list all distinct user IDs active in the last month")
  │   │
  │   ├── Needed in real-time, result changes constantly?
  │   │   └── Index on the column for index-only scan
  │   │       Accept the full-table cost; minimise with good indexes
  │   │
  │   ├── Needed frequently, result changes infrequently?
  │   │   └── Materialised view refreshed on schedule
  │   │
  │   └── Needed as an approximate COUNT only?
  │       └── HyperLogLog — 0.1–1% error, O(1) query time
  │
  └── "DISTINCT to fix duplicates from a JOIN"
      └── Stop. Fix the JOIN instead.
          Use EXISTS if you need a presence check.
          Use GROUP BY if you need aggregation.
          Use a different join type if the duplication is unintended.
```

## 12. The Compound Query — DISTINCT + ORDER BY + LIMIT

A final pattern worth understanding is `SELECT DISTINCT ... ORDER BY ... LIMIT N` — seemingly a reasonable way to get "the top N unique values." The combination is more expensive than it appears, because `DISTINCT` must be resolved before `ORDER BY` can be applied, and both must complete before `LIMIT` can reduce the output.

```sql
-- This seems like it should be fast — only returning 10 rows
SELECT DISTINCT user_id
FROM events
WHERE created_at > NOW() - INTERVAL '30 days'
ORDER BY user_id
LIMIT 10;

-- But the execution order is:
-- 1. Scan events table (200 million rows) with WHERE filter
-- 2. DISTINCT deduplication of all qualifying rows (spills to disk)
-- 3. Sort the deduplicated result by user_id
-- 4. Take the first 10

-- The LIMIT 10 does not reduce the work in steps 1, 2, or 3.
-- You pay the full cost of deduplicating 200 million rows
-- to return 10 user IDs.
```

The fix, as usual, depends on what you actually need. If you want the 10 users with the most events, that is a COUNT + GROUP BY + ORDER BY + LIMIT — a single aggregation pass. If you want any 10 distinct user IDs from recent events, EXISTS or a JOIN-based approach against the users table is far more appropriate than DISTINCT.

## 13. The Golden Rule

> `DISTINCT` is not a filter — it is a deduplication operation that requires the database to process every qualifying row before it can return the first result. It is semantically equivalent to `GROUP BY` on all selected columns, and it carries the same cost: a full hash aggregation or sort of the entire input, with potential spill to disk when the data exceeds `work_mem`. When you reach for `DISTINCT`, first ask what question you are truly answering. If you need to check whether a record exists, use `EXISTS` — it short-circuits at the first match. If you need to collapse JOIN-induced row duplication, fix the JOIN. If you genuinely need the full list of distinct values and it is queried frequently, pre-compute it in a materialised view. If an approximate count is sufficient, use HyperLogLog. `DISTINCT` should appear in your SQL only when no other approach can express the requirement — not as a convenient way to make result sets "look clean."

The query that adds one word and multiplies the cost by millions. Now you know exactly what that word costs — and what to write instead.
