# The OFFSET Pagination Collapse — A Case Study in Hidden Performance Decay

> *Explained by a senior engineer to someone who is just starting out. This one is particularly treacherous because it works perfectly in development, passes every test, and then quietly degrades in production over months until one day a simple "next page" request brings your database to its knees.*

---

## The Setup — A Page of Results

Pagination is something every application needs. When a user opens a product listing on an e-commerce site, a feed on a social platform, or a list of orders in an admin dashboard, you cannot return millions of rows at once. You return a manageable chunk — say, 20 results — and then let the user navigate to the next page, and the next, and so on. This is pagination, and it is one of the most fundamental patterns in web development.

The most natural way to implement pagination in SQL is to use two keywords that every developer learns early: `LIMIT` and `OFFSET`. `LIMIT` tells the database how many rows to return. `OFFSET` tells the database how many rows to skip before it starts returning results. Together, they feel like a clean, logical solution: to get page 1, skip 0 rows and return 20. To get page 2, skip 20 rows and return 20. To get page 3, skip 40 rows and return 20.

Your database table looks like this:

```
┌──────────────────────────────────────────────────────┐
│                       posts                          │
├────────┬───────────────────────┬─────────────────────┤
│   id   │        title          │     created_at      │
├────────┼───────────────────────┼─────────────────────┤
│      1 │ "Hello World"         │ 2023-01-01 09:00    │
│      2 │ "My First Tutorial"   │ 2023-01-02 11:30    │
│      3 │ "Deep Dive into SQL"  │ 2023-01-03 14:15    │
│    ... │         ...           │         ...         │
│ 900019 │ "Latest News"         │ 2025-08-01 08:00    │
│ 900020 │ "Breaking Story"      │ 2025-08-01 09:00    │
│ 900021 │ "Page 45001 starts"   │ 2025-08-01 10:00    │
└────────┴───────────────────────┴─────────────────────┘
```

Nine hundred thousand rows. A perfectly realistic size for a mature blogging platform, news site, or e-commerce catalog. And your pagination query looks like this for page 45,001:

```sql
SELECT * FROM posts
ORDER BY created_at DESC
OFFSET 900000
LIMIT 20;
```

This query will run. It will return the correct 20 rows. And it will be, quietly, an act of self-destruction.

## What OFFSET Actually Does — The Dirty Secret Nobody Tells You

Here is the thing that the SQL documentation does not advertise loudly enough: **OFFSET does not mean "start from row N."** What it actually means, under the hood, is **"read and discard the first N rows, then return the next batch."**

This is not a limitation of one specific database. It is true of PostgreSQL, MySQL, SQLite, SQL Server, and Oracle. It is a fundamental consequence of how OFFSET is defined in the SQL standard. When you write `OFFSET 900000`, you are telling the database: "Please scan through 900,000 rows, throw all of them away, and then give me the 20 rows that come after."

To understand why the database must do this, you need to understand how sorting works. When you add `ORDER BY created_at DESC` to your query, the database cannot simply jump to position 900,000 in a pre-sorted list. The data on disk is not permanently stored in your desired sort order. The database has to perform the sort first — either by scanning an index in order, or by collecting rows and sorting them in memory — and then, only after it has the sorted sequence, can it count forward to the offset position. There is no shortcut. There is no index structure that lets you say "give me the element at position 900,000 in sorted order" in constant time.

The mental model you should have is of a very long physical queue:

```
What the database does for OFFSET 900000 LIMIT 20:

  Sorted result set (imagine it as a long line of people):

  [row 1][row 2][row 3]...[row 899,999][row 900,000][row 900,001]...[row 900,020]
   ↑                                                  ↑              ↑
   Start here                                    You want          You want
   (database begins                              these 20 rows     these 20 rows
    scanning here)
                          ← walk past 900,000 rows → then return these

  The database physically traverses every row from 1 to 900,000
  before it can hand you the 20 rows you asked for.
```

Every single time a user clicks "Next Page" on page 45,001, your database walks through 900,000 rows. Not once total — every single request. There is no caching of the offset position between requests. Each new request starts the same marathon from scratch.

## The Performance Cliff — Why It Gets Worse Over Time

The relationship between your offset value and your query execution time is essentially linear. Doubling the offset roughly doubles the time the query takes. This creates a pattern that looks fine in development and during early production, but reveals itself as a slow-burning catastrophe as your data grows and users paginate deeper.

```
Query performance across pages (approximate, 1M row table):

  Page      OFFSET    Approx. Query Time
  ───────   ──────    ──────────────────
  Page 1         0    ~1 ms
  Page 10      180    ~1 ms       ← feels instantaneous, passes all QA tests
  Page 100    1980    ~3 ms       ← still acceptable
  Page 1000  19980    ~30 ms      ← starting to feel slow
  Page 5000  99980    ~150 ms     ← users notice this
  Page 10000 199980   ~300 ms     ← painful
  Page 50000 999980   ~1,500 ms   ← unacceptable, timeouts possible
  Page 45001 900000   ~1,200 ms   ← your real scenario

                                  ▲
                                  │                              ╱
                             Time │                           ╱
                                  │                       ╱
                                  │                   ╱
                                  │              ╱
                                  │         ╱
                                  │    ╱
                                  │╱
                                  └────────────────────────────────►
                                                          Page number
```

This is a linear growth curve. There is no plateau, no leveling off. The deeper users paginate, the worse every query becomes, without exception. And notice the critical detail: **your test suite will never catch this**. In development, your database has a few hundred rows of seed data. Page 1 through page 10 load instantly. Tests pass. You ship. Six months later your table has a million rows, a power user loads page 5,000, and your database grinds.

## What the Database Is Doing Internally — The Work Behind the Scenes

Let us be precise about the computational work involved. When your query hits the database with `ORDER BY created_at DESC OFFSET 900000 LIMIT 20`, the query planner has to make a decision. If you have an index on `created_at`, it will walk that index in reverse order, which is efficient. But "efficient" is relative — it still has to traverse 900,020 index entries to give you 20 rows. Each index entry is a pointer to a row. For an index-based scan, the process looks like this:

```
Index on created_at (stored as B-Tree, traversed in DESC order):

  Root Node
     │
     ├── Branch: 2025-08 entries ──► Leaf: [row 900020, row 900019, ...]
     │                               ↑ Database starts reading here
     │
     │   READ: row 900020  → discard (offset not reached yet)
     │   READ: row 900019  → discard
     │   READ: row 900018  → discard
     │   ...
     │   (continues for 900,000 entries)
     │   ...
     │   READ: row 21      → discard
     │   READ: row 20      → discard (offset = 900000, now stop discarding)
     │   READ: row 19      → RETURN ✓
     │   READ: row 18      → RETURN ✓
     │   ...
     │   READ: row  1      → RETURN ✓  (20 rows returned)
     │
     └── Done.
```

Even when using an index, the database is doing real work for every skipped row. It is reading index pages, following pointers, counting. At 900,000 skipped rows, this is a meaningful workload. Now multiply this by concurrent users. Ten users simultaneously paginating to deep pages means ten of these full traversals happening in parallel, competing for database CPU, I/O, and memory. The database slows down for everybody — not just the deep paginators. Your home page, your checkout flow, your search results — all of them suffer because the database is busy executing 900,000-row traversals for a handful of users on page 45,001.

## The Real-World Pattern — How This Happens in Practice

The OFFSET pagination pattern appears everywhere because it maps so naturally to how humans think about pages. "Page 2 means skip page 1's items." It also maps to common URL structures that every web developer recognizes:

```
/api/posts?page=2&limit=20
/api/products?offset=40&count=20
/admin/orders?p=5000
```

Backend frameworks like Django, Rails, Laravel, and Spring all have built-in pagination helpers that generate OFFSET-based queries by default. You call `paginate(page: 5, per_page: 20)` and the framework silently translates it into `OFFSET 80 LIMIT 20`. There is no warning, no flag, no documentation footnote that says "this will eventually destroy your database."

The pattern also appears in search interfaces, admin dashboards, data export flows, and any feature where users can browse through a large collection of records. In each case, the early pages work fine and the problem is invisible until the table is large and a user or an automated process reaches the deep pages.

## The Solution — Keyset Pagination (Cursor-Based Pagination)

The correct solution to this problem requires a fundamental change in how you think about "where you are" in a result set. Instead of thinking in terms of page numbers and row counts — "I am on page 45,001 of 50,000" — you think in terms of **your last seen position** — "the last row I saw had an ID of 12,345, give me the next 20 rows after that."

This approach is called **keyset pagination** or **cursor-based pagination**, and it completely eliminates the OFFSET problem. The query for the first page looks like this:

```sql
-- Page 1: No cursor yet, just get the first 20 rows
SELECT * FROM posts
ORDER BY id DESC
LIMIT 20;
```

This returns rows with IDs from, say, 900020 down to 900001. The last row you received has `id = 900001`. You store this value — this is your **cursor**. For the next page, instead of telling the database "skip 20 rows", you tell it "give me rows that come before ID 900001":

```sql
-- Page 2: Using the cursor from the previous page
SELECT * FROM posts
WHERE id < 900001
ORDER BY id DESC
LIMIT 20;
```

For page 3, the last row was `id = 899981`:

```sql
-- Page 3: Using the new cursor
SELECT * FROM posts
WHERE id < 899981
ORDER BY id DESC
LIMIT 20;
```

This is the complete mental model transformation:

```
OFFSET Pagination (old way):
  ┌──────────────────────────────────────────────────────────┐
  │  "I want page 45,001"                                    │
  │  Database: OK, count 900,000 rows, discard them, return  │
  │            the next 20. (O(offset) work every time)      │
  └──────────────────────────────────────────────────────────┘

Keyset Pagination (new way):
  ┌──────────────────────────────────────────────────────────┐
  │  "I want the 20 rows where id < 12345"                   │
  │  Database: OK, look up id 12345 in the index in O(log N) │
  │            then read the next 20 entries. Done.          │
  └──────────────────────────────────────────────────────────┘
```

Why is the keyset approach so dramatically faster? Because the `WHERE id < :cursor` condition can use an index lookup directly. Instead of walking through 900,000 index entries, the database does a **binary search** on the B-Tree index — O(log N) work instead of O(N) work. It finds the position of the cursor value in the index tree in a handful of steps (a million-row table's B-Tree index is only about 20 levels deep), and then reads the next 20 entries forward. The work is the same whether you are on "page 2" or "page 45,001." Query time becomes constant.

```
Performance comparison across pages:

  Page / Cursor      OFFSET time    Keyset time
  ───────────────    ──────────     ───────────
  Page 1             ~1 ms          ~1 ms
  Page 100           ~3 ms          ~1 ms
  Page 1,000         ~30 ms         ~1 ms
  Page 10,000        ~300 ms        ~1 ms
  Page 45,001        ~1,200 ms      ~1 ms

  OFFSET: O(N)     Keyset: O(log N) — effectively constant
```

## Handling the Trade-offs — What You Give Up With Keyset Pagination

Keyset pagination is not a free lunch. It solves the performance problem completely, but it introduces constraints that you need to design around. Understanding these trade-offs is what separates a thoughtful engineer from one who simply applies a pattern without thinking.

The most significant trade-off is that **you can no longer jump to an arbitrary page number**. With OFFSET pagination, the URL `/posts?page=500` is meaningful — the database can skip 9,980 rows and start there. With keyset pagination, you can only go forward or backward from your current cursor. There is no way to say "jump to page 500" because page numbers no longer mean anything. Each page's position is defined by the cursor value of the previous page, forming a chain.

```
OFFSET: Random access to any page
  Page 1  Page 2  Page 3  ...  Page 500  Page 501
    ↑       ↑       ↑              ↑         ↑
  Can jump directly to any of these

Keyset: Sequential chain only
  [Page 1] ──► cursor ──► [Page 2] ──► cursor ──► [Page 3] ──► ...
    ↑
  Must follow the chain. Cannot jump to page 500 directly.
```

For many applications — infinite scrolling social feeds, "load more" buttons, API endpoints for clients that process pages sequentially — this is absolutely fine. Nobody using Instagram's feed needs to jump to "post number 847,293." The "next page" / "previous page" model is the only one they use.

For applications where users need to jump to specific pages — some admin dashboards, certain search interfaces, or anywhere you display a page selector — you either need to keep OFFSET for those specific use cases and accept the cost, or redesign the UI to eliminate arbitrary page jumping.

The second trade-off is that **the cursor column must be unique and stable**. If you paginate by `created_at` and two posts were created at exactly the same timestamp, your cursor becomes ambiguous — "give me rows where `created_at` < X" might skip rows or return duplicates. The safest approach is to always include a unique, sequential column like `id` as a tiebreaker in your sort and cursor:

```sql
-- Safe: composite cursor using both created_at and id as tiebreaker
SELECT * FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

This ensures that even if many rows share the same `created_at` value, the `id` tiebreaker makes every position in the sequence unambiguous.

## What About the Index? — Making Sure the Database Uses It

Keyset pagination is only fast if the database can use an index to answer the `WHERE id < :cursor` condition efficiently. If your table does not have an index on the pagination column, the database will fall back to a sequential scan, and you will have traded one performance problem for another.

For the most common case of paginating by a single column like `id` (which is almost always the primary key and always indexed), you get index usage for free. For more complex cases — paginating by `created_at` in descending order — you should verify that an index exists:

```sql
-- Create an index that matches your pagination query's sort order
CREATE INDEX idx_posts_created_at_desc ON posts (created_at DESC, id DESC);

-- Then verify the planner uses it
EXPLAIN ANALYZE
SELECT * FROM posts
WHERE (created_at, id) < ('2025-08-01 10:00', 900021)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- You want to see "Index Scan" in the output, NOT "Seq Scan"
```

The `EXPLAIN ANALYZE` output will tell you exactly how the database is executing the query. The presence of "Index Scan using idx_posts_created_at_desc" confirms you are getting O(log N) performance. The presence of "Seq Scan" tells you the index is not being used and you need to investigate why.

## How to Detect the Problem in Production

If you have an existing application with OFFSET pagination and you suspect it is causing problems, there are several ways to confirm this. The most direct approach is to look at your slow query log or `pg_stat_statements` in PostgreSQL. Queries with `OFFSET` in them, sorted by total execution time, will tell you exactly where the cost is being paid.

```
pg_stat_statements output revealing OFFSET pain:

query                                              | calls  | mean_time | total_time
---------------------------------------------------|--------|-----------|------------
SELECT * FROM posts ORDER BY created_at DESC       |        |           |
  OFFSET $1 LIMIT $2                               | 12,847 | 847 ms    | 10,892 sec

↑ This query averaged 847ms and consumed 10,892 seconds of database
  time in the reporting period. The OFFSET parameter ($1) is varying,
  meaning users are hitting different pages — deep page users are
  dragging up the average for everyone.
```

You can also simulate the problem directly by running your own pagination query with progressively larger OFFSET values and timing the results. The linear degradation will be immediately visible and quantifiable.

## The Migration Path — Moving From OFFSET to Keyset

If you have a live application using OFFSET pagination, migrating to keyset pagination is not trivial, but it is absolutely worth doing. The typical approach is to change your API to support both modes simultaneously during a transition period: continue to accept `page` and `offset` parameters for backward compatibility, but introduce a new `cursor` parameter for keyset pagination. Document to your consumers that `cursor`-based pagination is the recommended approach going forward, and gradually migrate your frontend and any API clients.

The backend change itself is relatively contained — it is a change to how you construct the SQL query and how you compute and return the cursor value in your API response. A common pattern is to return the cursor as part of the API response alongside the results:

```json
{
  "data": [
    { "id": 900020, "title": "Breaking Story", "created_at": "2025-08-01T09:00:00Z" },
    { "id": 900019, "title": "Latest News",    "created_at": "2025-08-01T08:00:00Z" },
    ...
  ],
  "pagination": {
    "next_cursor": "eyJpZCI6IDkwMDAwMSwgImNyZWF0ZWRfYXQiOiAiMjAyNS0wNy0zMSJ9",
    "has_next_page": true
  }
}
```

The `next_cursor` value is typically a Base64-encoded JSON object containing the cursor values (e.g., the `id` and `created_at` of the last row returned). The client sends this token back with its next request, and your backend decodes it to construct the `WHERE (created_at, id) < (...)` clause. The client never needs to know what is inside the cursor — it is an opaque token. This also prevents clients from constructing arbitrary cursors, which adds a layer of safety.

## The Lesson — OFFSET Is O(offset), Always

The core insight of this entire case study is deceptively simple: **the cost of an OFFSET query grows linearly with the offset value, always and without exception**. There is no configuration you can change, no index you can add, and no database engine that escapes this. It is a mathematical property of what OFFSET means — "skip N rows" requires reading and discarding N rows.

OFFSET pagination is one of those patterns that feels intuitive, works perfectly in development, and fails gracefully enough in early production that nobody notices until the problem is severe. By the time slow queries start appearing in your monitoring dashboards, your users have already been suffering for weeks. The fix — switching to keyset pagination — is not complicated technically, but it requires changing how you think about "where you are" in a result set, from a page number to a position marker.

As an engineer, your responsibility is to anticipate this before it becomes a crisis. Any time you build a feature that paginates through a table that could grow large, ask yourself: "Will this query still perform acceptably if the table has ten million rows and a user paginates to page 10,000?" If the answer is no, use keyset pagination from the beginning. It is far easier to build it correctly the first time than to migrate a live API under production traffic.
