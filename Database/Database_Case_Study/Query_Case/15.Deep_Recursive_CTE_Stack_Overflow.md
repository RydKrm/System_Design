# The Deep Recursive CTE Stack Overflow

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. The Query That Works on Clean Data and Explodes on Real Data

You are building an HR management system. Every employee has a manager, and every manager is also an employee. You need to display the full reporting chain from the CEO down to every individual contributor — a classic organisational hierarchy. You learn about **recursive CTEs**, write a clean implementation, test it against your sample data, and it works beautifully:

```sql
WITH RECURSIVE org_chart AS (
    -- Base case: start with the CEO (no manager)
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive case: find each person's direct reports
    SELECT e.id, e.name, e.manager_id, oc.depth + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart ORDER BY depth, name;
```

On your test dataset — a clean hierarchy of 500 employees with a proper tree structure — this query completes in 15 milliseconds. You feel confident. The logic is clean, the results are correct, and the performance is acceptable. You ship it to production.

Three months later, a data entry operator makes a mistake. They update an employee's `manager_id` to point to someone who, further up the chain, reports to that employee. A cycle is born: Alice reports to Bob, Bob reports to Carol, Carol reports to Alice. Your recursive CTE begins traversing this cycle. Alice → Bob → Carol → Alice → Bob → Carol → Alice — forever. The query does not return. The database connection hangs. The database server's memory begins climbing as the recursive working table grows without bound. Eventually, the server runs out of memory, crashes, or a timeout kills the query — but not before degrading every other query running on that server.

This is the **Deep Recursive CTE Stack Overflow** — the anti-pattern where a query that is logically correct for well-formed data becomes catastrophically unsafe the moment the data violates the assumptions the query was written for. And with hierarchical data entered by humans, those violations are not edge cases. They are certainties.

## 2. How Recursive CTEs Work — The Mechanism You Must Understand

Before understanding what goes wrong, you need a precise mental model of how a recursive CTE actually executes. The name is slightly misleading — it is not truly recursive in the programming sense of a function calling itself. It is an **iterative process** that PostgreSQL executes step by step until a termination condition is met.

A recursive CTE has two mandatory parts separated by `UNION ALL`. The first part is the **base case** — a non-recursive query that produces the starting set of rows (the "seed"). The second part is the **recursive member** — a query that joins back to the CTE itself, using the current iteration's results to produce the next iteration's rows. PostgreSQL calls the current iteration's rows the **working table**. When the recursive member produces zero new rows, the iteration stops.

```
  Recursive CTE — Iterative Execution Model
  ===========================================

  WITH RECURSIVE org_chart AS (
      SELECT id, name, manager_id, 1 AS depth        ← Base case
      FROM employees WHERE manager_id IS NULL

      UNION ALL

      SELECT e.id, e.name, e.manager_id, oc.depth+1  ← Recursive member
      FROM employees e
      JOIN org_chart oc ON e.manager_id = oc.id      ← joins to current working table
  )

  Execution trace (clean tree data):
  ─────────────────────────────────────────────────────
  Iteration 1 (seed):
    Base case runs once
    Working table: [ (CEO, depth=1) ]
    Accumulated result: [ (CEO, depth=1) ]

  Iteration 2:
    Recursive member joins employees to working table
    Finds: VP_Engineering, VP_Sales, VP_Marketing
    Working table: [ (VP_Eng, 2), (VP_Sales, 2), (VP_Mktg, 2) ]
    Accumulated result: [ CEO, VP_Eng, VP_Sales, VP_Mktg ]

  Iteration 3:
    Recursive member joins to new working table
    Finds all direct reports of VPs
    Working table: [ (Eng_Lead, 3), (Sales_Lead, 3), ... ]
    Accumulated result: growing...

  Iteration N:
    Recursive member finds no new employees to add
    Working table: [] (empty)
    ← STOP — empty working table is the termination condition

  Final result: entire accumulated result returned
```

The termination condition is critical: **the recursion stops when the recursive member produces an empty result set**. On clean tree data, this happens naturally when you reach the leaf nodes — employees who have no direct reports. At that point, the recursive member finds no employees whose `manager_id` matches any ID in the current working table, so it produces nothing, and the iteration ends.

On **cyclic data**, the recursion never naturally terminates. When Alice's manager_id points to Bob, Bob's manager_id points to Carol, and Carol's manager_id points to Alice, the recursive member will always find a new row to add on every iteration — because every iteration that processes Alice will find Bob, every iteration that processes Bob will find Carol, and every iteration that processes Carol will find Alice. The working table is never empty. The accumulated result grows without bound. The recursion never stops.

```
  Recursive CTE on Cyclic Data — Infinite Loop
  =============================================

  Cycle in data: Alice (id=10) → manager=Bob (id=20)
                 Bob   (id=20) → manager=Carol (id=30)
                 Carol (id=30) → manager=Alice (id=10)  ← CYCLE

  Iteration 1 (seed — finds CEO):
    Working table: [ CEO ]

  Iteration 2:
    Finds CEO's direct reports including Alice
    Working table: [ Alice (id=10) ]

  Iteration 3:
    Finds Alice's report = Bob (id=20)
    Working table: [ Bob (id=20) ]

  Iteration 4:
    Finds Bob's report = Carol (id=30)
    Working table: [ Carol (id=30) ]

  Iteration 5:
    Finds Carol's report = Alice (id=10)  ← cycle detected... but not by the DB
    Working table: [ Alice (id=10) ]       ← same Alice as iteration 2!

  Iteration 6:
    Finds Alice's report = Bob (id=20)    ← seen before, but DB doesn't know
    Working table: [ Bob (id=20) ]

  ... repeat forever ...

  Accumulated result: grows by 3 rows every 3 iterations, forever
  Memory consumed: increases without bound
  Query: never terminates
  Server: OOM crash or manual timeout kill
```

## 3. The Real-World Trigger — Why Cycles Always Appear

A common response from developers when warned about cycles is: "Our data doesn't have cycles — we prevent them in the application." This is, almost without exception, an optimistic belief rather than a guaranteed invariant. Real production systems accumulate cycles through a variety of mechanisms that application-level validation does not always intercept.

The most frequent source is **bulk data imports**. When data is migrated from an old system, when a CSV file is imported from a third-party tool, or when a legacy database is merged into a new one, the data often bypasses your application's validation logic and goes directly into the database. If the source data contained a cycle — even an accidental one from a data entry error in the source system — it arrives in your database intact, invisible until a recursive query discovers it catastrophically.

The second source is **concurrent updates**. Two database transactions can each see consistent snapshots of the data that individually appear cycle-free, but when both commit, they together create a cycle. Transaction A changes Alice's manager to Bob. Transaction B changes Bob's manager to Alice. Both changes look valid in isolation — Alice can report to Bob, Bob can report to Alice is only a problem together. Without a database-level constraint that validates the entire hierarchy on every update (expensive and complex), concurrent transactions can introduce cycles that application validation cannot prevent.

The third source is **manual database operations** — a DBA or engineer running a direct UPDATE in a production console to "quickly fix" something, bypassing all application logic. In high-pressure incident situations, direct database edits are common. And in those situations, nobody is carefully checking for cycle introduction.

```
  How Cycles Enter Production Data
  ==================================

  ┌──────────────────────────────────────────────────┐
  │  Source                    │ Prevention bypassed  │
  ├──────────────────────────────────────────────────┤
  │  Bulk CSV/SQL import       │ App validation       │
  │  DB migration scripts      │ App validation       │
  │  Legacy system merge       │ App validation       │
  │  Concurrent transactions   │ App validation       │
  │  Manual admin UPDATE       │ App validation       │
  │  ORM without constraints   │ App validation       │
  │  Third-party integrations  │ App validation       │
  └──────────────────────────────────────────────────┘

  In every case: app validation doesn't run, cycle enters DB.

  Question: does your system reliably run app validation
  on 100% of writes to the hierarchy table?
  Honest answer for most production systems: no.

  Correct posture: assume cycles can exist; protect the query.
```

The defensively correct engineering posture is not "our data doesn't have cycles." It is "our query is safe regardless of whether the data has cycles." A query that requires clean data to be safe is a liability. A query that remains safe on any data is an asset.

## 4. The Deep Hierarchy Problem — Even Without Cycles

Separate from the cycle problem, there is a related issue that affects even well-formed, cycle-free hierarchical data: **extreme depth**. When a hierarchy is genuinely deep — 10,000 levels, 50,000 levels, or more — the recursive CTE accumulates a working table for each level, and the intermediate state stored during traversal can exhaust available memory.

This is more common than it sounds. Consider a category tree for a large e-commerce platform where categories can be nested arbitrarily. A subcategory can contain subcategories, which can contain more subcategories — and over years of organic growth, some branches of the tree can become hundreds of levels deep. Or consider a social graph where "follows" relationships create chains that could theoretically extend for thousands of hops. Or a bill of materials system where a product contains components that contain sub-components, down through many levels of assembly.

```
  Deep Hierarchy — Even Without Cycles, Memory Grows
  ===================================================

  Scenario: category tree with 50,000 nodes and max depth 5,000

  Iteration 1:    working table = [root category]           ~1 row
  Iteration 10:   working table = [nodes at depth 10]       ~10 rows
  Iteration 100:  working table = [nodes at depth 100]      ~100 rows
  Iteration 1000: working table = [nodes at depth 1000]     ~1,000 rows
  Iteration 5000: working table = [nodes at depth 5000]     ~5,000 rows

  Accumulated result table: 50,000 rows → kept in memory until query finishes
  Working table at each step: up to several thousand rows
  Total memory pressure: manageable for 50K nodes

  BUT if the hierarchy is 1,000,000 nodes deep with branching factor 1
  (a linked list, essentially):
  Accumulated result: 1,000,000 rows, held in memory
  Iterations: 1,000,000
  Time: proportional to 1,000,000 iterations of query evaluation

  With a cycle, a 3-node cycle in a million-node tree:
  Accumulated result: grows to infinity
  Time: infinity
  Memory: infinity (until OOM)
```

For deep but non-cyclic hierarchies, the solution is a **depth limit** — a guard that stops the recursion when it exceeds a configurable maximum depth, preventing runaway resource consumption even if the data is technically valid.

## 5. The Diagnostic Evidence — What You See When It Happens

The symptoms of an infinite recursive CTE are distinct enough to be recognisable, but they share characteristics with other types of runaway queries, so knowing the specific signals matters.

The first symptom is a query that **never returns a result**. Unlike a slow query that returns eventually, a recursive CTE on cyclic data runs indefinitely. The database connection stays open, the application waits, and nothing comes back. This is the most common first signal — an API endpoint or a background job that simply hangs.

The second symptom is **escalating memory consumption on the database server**. Because the recursive CTE's accumulated result table grows without bound, the server's RAM usage climbs continuously from the moment the query starts. In monitoring tools, this shows as a steadily increasing memory graph correlating with the query start time.

The third symptom is what you see when you look at active queries:

```sql
-- Check active queries and their runtime
SELECT pid, now() - pg_stat_activity.query_start AS duration, query, state
FROM pg_stat_activity
WHERE (now() - pg_stat_activity.query_start) > INTERVAL '5 seconds'
ORDER BY duration DESC;

-- You might see:
--  pid  │ duration  │ state  │ query
-- ──────┼───────────┼────────┼──────────────────────────────────────────
--  8821 │ 00:47:13  │ active │ WITH RECURSIVE org_chart AS (
--       │           │        │   SELECT id, name, manager_id, 1 AS depth
--       │           │        │   FROM employees WHERE ...
```

A recursive CTE query that has been running for 47 minutes with no result is a strong indicator of an infinite loop. You can terminate it:

```sql
-- Terminate a specific query by PID
SELECT pg_terminate_backend(8821);
```

The fourth symptom, which you see in the PostgreSQL logs when the situation escalates, is an out-of-memory error:

```
ERROR:  out of memory
DETAIL:  Failed on request of size 8192 in memory context "ExecutorState".
CONTEXT:  recursive CTE org_chart
```

The context line — `recursive CTE org_chart` — tells you exactly which query consumed the memory. This is the database's way of saying: "The recursive CTE grew until there was no memory left."

## 6. Solution One — PostgreSQL CYCLE Clause (PostgreSQL 14+)

PostgreSQL 14 introduced a native `CYCLE` clause for recursive CTEs that provides built-in cycle detection with minimal code change. It is the cleanest and most expressive solution when you are on a compatible PostgreSQL version.

```sql
WITH RECURSIVE org_chart AS (
    -- Base case: start from the CEO
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive member: find direct reports
    SELECT e.id, e.name, e.manager_id, oc.depth + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
)
-- The CYCLE clause: track the id column for cycles
-- If id is seen again, mark the row as a cycle and STOP
CYCLE id SET is_cycle USING path
SELECT * FROM org_chart WHERE NOT is_cycle ORDER BY depth, name;
```

The `CYCLE id SET is_cycle USING path` clause tells PostgreSQL three things. First, `id` is the column to track for cycle detection — if the same `id` value appears twice in any path through the recursion, that is a cycle. Second, `is_cycle` is a boolean column that PostgreSQL will add to the result — it will be `true` for any row where a cycle was detected, `false` otherwise. Third, `path` is an array column PostgreSQL will add to track the entire path of IDs visited from the root to the current row — useful for displaying the hierarchy path and for debugging which cycle was found.

```
  CYCLE Clause — What It Adds to the Execution
  ==============================================

  Data with cycle: Alice (10) → Bob (20) → Carol (30) → Alice (10) [CYCLE]

  Without CYCLE clause:
  Iteration 2: [ Alice (id=10) ]
  Iteration 3: [ Bob (id=20) ]
  Iteration 4: [ Carol (id=30) ]
  Iteration 5: [ Alice (id=10) ] ← same id seen again — infinite loop
  ...forever

  With CYCLE id SET is_cycle USING path:
  Iteration 2: [ Alice (id=10, is_cycle=false, path=[CEO_id, 10]) ]
  Iteration 3: [ Bob (id=20, is_cycle=false, path=[CEO_id, 10, 20]) ]
  Iteration 4: [ Carol (id=30, is_cycle=false, path=[CEO_id, 10, 20, 30]) ]
  Iteration 5: id=10 seen in path [CEO_id, 10, 20, 30, 10]?
               YES → mark is_cycle=true, DO NOT recurse further
  Result: [ Alice(is_cycle=false), Bob(is_cycle=false),
            Carol(is_cycle=false), Alice(is_cycle=true) ]

  WHERE NOT is_cycle filters out the cycle marker row.
  Query terminates. Cycle reported, not followed.
```

The `path` column also gives you something invaluable for debugging: the exact sequence of node IDs that form the cycle. When a cycle is detected, you can query for `WHERE is_cycle = true` and look at the `path` column to identify which employees are involved in the circular reporting chain — a critical feature for a data quality dashboard.

```sql
-- Find all cycles in the hierarchy with their full paths
WITH RECURSIVE org_chart AS (
    SELECT id, name, manager_id, 1 AS depth
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, oc.depth + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
)
CYCLE id SET is_cycle USING path
SELECT id, name, path AS cycle_path
FROM org_chart
WHERE is_cycle = true;
-- Returns each row where a cycle was encountered, with the full path
-- showing exactly which nodes form the cycle
```

## 7. Solution Two — Manual Path Tracking (Pre-PostgreSQL 14)

For PostgreSQL versions before 14, or for databases that do not support the `CYCLE` clause (MySQL, SQLite), you implement cycle detection manually by maintaining an array of visited node IDs and checking each new node against that array before adding it to the working table.

```sql
WITH RECURSIVE org_chart AS (
    -- Base case: CEO, with path array containing just the starting ID
    SELECT
        id,
        name,
        manager_id,
        1                AS depth,
        ARRAY[id]        AS path,     ← track visited IDs
        false            AS is_cycle
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive member: only follow edges to unvisited nodes
    SELECT
        e.id,
        e.name,
        e.manager_id,
        oc.depth + 1,
        oc.path || e.id,              ← append current ID to path
        e.id = ANY(oc.path)           ← is this ID already in our path?
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
    WHERE NOT oc.is_cycle             ← don't recurse into already-cycled paths
      AND e.id != ANY(oc.path)        ← don't follow edges to visited nodes
)
SELECT id, name, depth, path
FROM org_chart
WHERE NOT is_cycle
ORDER BY depth, name;
```

The path array grows with each recursion step, appending the current node's ID. Before following an edge to a new node, the WHERE clause checks whether that node's ID is already in the path — `e.id != ANY(oc.path)`. If it is, the edge is skipped, preventing the cycle from being followed. The `is_cycle` flag marks rows where the cycle was about to be entered, allowing the outer query to filter them out.

```
  Manual Path Tracking — How the Array Guard Works
  =================================================

  Iteration 2: Alice (id=10) entered
               path = [CEO_id, 10]
               is_cycle = false

  Iteration 3: Bob (id=20) entered
               path = [CEO_id, 10, 20]
               is_cycle = false

  Iteration 4: Carol (id=30) entered
               path = [CEO_id, 10, 20, 30]
               is_cycle = false

  Iteration 5: Try to follow Carol's manager = Alice (id=10)
               Check: 10 = ANY([CEO_id, 10, 20, 30])?
               YES → skip this edge (WHERE e.id != ANY(oc.path) fails)
               Alice is NOT added to working table

  Working table is now empty → recursion terminates ✅
  Cycle silently avoided. Query returns cleanly.
```

The trade-off of the manual approach is memory and CPU overhead: every recursion step must maintain and check the path array, and for very deep hierarchies, these arrays can become large. For most organisational hierarchies (depths of 5–20 levels), this is negligible. For social graph traversals that might go hundreds of hops deep, the array approach adds meaningful overhead.

## 8. Solution Three — Depth Limit Guard

Even with cycle detection, an extremely deep hierarchy can cause problems — thousands of iterations consume time and memory even without cycling. A depth limit adds a hard ceiling on how deep the recursion will go, protecting against both accidental depth from clean data and any edge cases in cycle detection.

```sql
WITH RECURSIVE org_chart AS (
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.id, e.name, e.manager_id, oc.depth + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
    WHERE oc.depth < 100            ← hard depth limit: never go deeper than 100
      AND e.id != ANY(oc.path)      ← cycle protection combined
)
CYCLE id SET is_cycle USING path
SELECT * FROM org_chart WHERE NOT is_cycle;
```

The `WHERE oc.depth < 100` condition on the recursive member means: "Only recurse into child nodes if the current node is at depth less than 100." When the depth reaches 100, no further recursion happens, and the working table becomes empty at the next iteration, terminating the recursion cleanly.

The depth limit value should be chosen based on the nature of the hierarchy:

```
  Choosing a Depth Limit
  ========================

  Organisational hierarchy:     LIMIT 50
  (Most orgs have < 15 levels;
   50 is generous and safe)

  Category tree (e-commerce):   LIMIT 20
  (Deeply nested categories are
   usually a data quality issue)

  Bill of materials:            LIMIT 100
  (Component assemblies can
   legitimately be deep)

  Social graph (hops):          LIMIT 6–10
  (Six degrees of separation;
   beyond 10 hops is rarely useful)

  File system traversal:        LIMIT 50–100
  (Deeply nested directories
   are unusual but possible)

  Generic/unknown:              LIMIT 100
  (Conservative default that
   prevents runaway while allowing
   any legitimate use case)
```

## 9. Solution Four — Validate Data Before Querying

Cycle protection in the query is essential, but it is a defensive measure — it handles cycles gracefully without preventing them from existing. A more proactive approach is to detect and report cycles in the data itself, allowing data quality issues to be fixed at the source rather than quietly tolerated by every query.

A cycle detection query can be run as a scheduled job, a data quality check, or a pre-condition in a migration script:

```sql
-- Detect all cycles in the employees hierarchy
-- Returns the full path of each cycle found
WITH RECURSIVE cycle_check AS (
    SELECT id, manager_id, ARRAY[id] AS path, false AS cycle_found
    FROM employees
    WHERE manager_id IS NOT NULL

    UNION ALL

    SELECT e.id, e.manager_id, cc.path || e.id,
           e.id = ANY(cc.path)
    FROM employees e
    JOIN cycle_check cc ON e.id = cc.manager_id
    WHERE NOT cc.cycle_found
      AND array_length(cc.path, 1) < 50
)
SELECT DISTINCT path AS cycle_path
FROM cycle_check
WHERE cycle_found = true;
```

In Go, you might run this check as part of a data quality service or as a validation step before running any hierarchy traversal:

```go
func DetectHierarchyCycles(ctx context.Context, db *sql.DB) ([][]int64, error) {
    query := `
        WITH RECURSIVE cycle_check AS (
            SELECT id, manager_id, ARRAY[id] AS path, false AS cycle_found
            FROM employees
            WHERE manager_id IS NOT NULL
            UNION ALL
            SELECT e.id, e.manager_id, cc.path || e.id,
                   e.id = ANY(cc.path)
            FROM employees e
            JOIN cycle_check cc ON e.id = cc.manager_id
            WHERE NOT cc.cycle_found
              AND array_length(cc.path, 1) < 50
        )
        SELECT DISTINCT path FROM cycle_check WHERE cycle_found = true
    `

    rows, err := db.QueryContext(ctx, query)
    if err != nil {
        return nil, fmt.Errorf("cycle detection query failed: %w", err)
    }
    defer rows.Close()

    var cycles [][]int64
    for rows.Next() {
        var path pq.Int64Array
        if err := rows.Scan(&path); err != nil {
            return nil, err
        }
        cycles = append(cycles, path)
    }
    return cycles, nil
}

// Run before any hierarchy traversal
func GetOrgChart(ctx context.Context, db *sql.DB) ([]Employee, error) {
    cycles, err := DetectHierarchyCycles(ctx, db)
    if err != nil {
        return nil, err
    }
    if len(cycles) > 0 {
        return nil, fmt.Errorf("hierarchy contains %d cycle(s): %v",
            len(cycles), cycles)
    }
    // safe to run full traversal
    return traverseOrgChart(ctx, db)
}
```

## 10. Solution Five — Database-Level Constraint (The Gold Standard)

The most robust solution is to prevent cycles from entering the database in the first place, using a constraint that validates the hierarchy on every INSERT and UPDATE. This is more complex to implement but provides the strongest guarantee.

PostgreSQL does not have a built-in "no-cycles" constraint, but you can implement one using a **constraint trigger** — a trigger that fires after an INSERT or UPDATE and validates that the resulting data does not contain a cycle:

```sql
-- Function that checks whether a new or updated edge would create a cycle
CREATE OR REPLACE FUNCTION check_employee_cycle()
RETURNS TRIGGER AS $$
DECLARE
    cycle_exists BOOLEAN;
BEGIN
    -- If manager_id is NULL, no cycle possible
    IF NEW.manager_id IS NULL THEN
        RETURN NEW;
    END IF;

    -- Walk up from the new manager to see if we encounter NEW.id
    WITH RECURSIVE ancestors AS (
        SELECT id, manager_id
        FROM employees
        WHERE id = NEW.manager_id

        UNION ALL

        SELECT e.id, e.manager_id
        FROM employees e
        JOIN ancestors a ON e.id = a.manager_id
        WHERE e.id != NEW.id        -- stop if we find the node being inserted
          AND array_length(ARRAY(
              SELECT a2.id FROM ancestors a2
          ), 1) < 100               -- depth limit on the validation traversal
    )
    SELECT EXISTS (
        SELECT 1 FROM ancestors WHERE id = NEW.id
    ) INTO cycle_exists;

    IF cycle_exists THEN
        RAISE EXCEPTION
            'Cycle detected: setting manager_id=% for employee id=% '
            'would create a cycle in the hierarchy',
            NEW.manager_id, NEW.id;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach the constraint trigger
CREATE CONSTRAINT TRIGGER trg_no_employee_cycle
AFTER INSERT OR UPDATE OF manager_id ON employees
DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION check_employee_cycle();
```

With this trigger in place, any INSERT or UPDATE that would create a cycle raises an exception and rolls back the transaction. The cycle never enters the database. Every query on the hierarchy — recursive CTE or otherwise — can operate with the guarantee that the data is cycle-free.

The trigger is `DEFERRABLE INITIALLY DEFERRED`, which means it runs at the end of the transaction rather than immediately after each statement. This is necessary for bulk operations that might temporarily create apparent cycles during loading (e.g., inserting a manager and their direct report in a single transaction where the manager row is inserted second).

## 11. The Complete Production-Ready Pattern

Combining all the defences into a single production-ready recursive CTE gives you something that is safe, debuggable, and informative:

```sql
-- Production-ready org chart traversal with all protections
WITH RECURSIVE org_chart AS (
    -- Base case: root nodes (employees with no manager)
    SELECT
        id,
        name,
        manager_id,
        title,
        department,
        1                       AS depth,
        ARRAY[id]               AS path,
        CAST(name AS TEXT)      AS path_names
    FROM employees
    WHERE manager_id IS NULL     -- or: WHERE id = $starting_employee_id

    UNION ALL

    -- Recursive member: find direct reports
    SELECT
        e.id,
        e.name,
        e.manager_id,
        e.title,
        e.department,
        oc.depth + 1,
        oc.path || e.id,
        oc.path_names || ' → ' || e.name
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
    WHERE e.id != ANY(oc.path)    -- cycle guard: skip visited nodes
      AND oc.depth < 50           -- depth limit: never exceed 50 levels
)
-- PostgreSQL 14+ native cycle detection as additional safety layer
CYCLE id SET is_cycle USING cycle_path
SELECT
    id,
    name,
    title,
    department,
    depth,
    path_names      AS reporting_chain,
    is_cycle        AS data_quality_flag
FROM org_chart
WHERE NOT is_cycle
ORDER BY depth, name;
```

This version gives you: clean results for well-formed data, graceful termination on cyclic data, a hard ceiling on depth for any unexpected deep hierarchy, a readable reporting chain in `path_names` for display, and a `data_quality_flag` for rows that would have caused cycles — useful for a data quality dashboard to surface problems to administrators.

## 12. The Golden Rule

> A recursive CTE terminates when the recursive member produces an empty result set. On cyclic data, that termination never comes — the recursion follows cycles forever, accumulating rows without bound until memory is exhausted or the query is manually killed. Hierarchical data entered by humans will always contain cycles — from data import errors, concurrent transactions, manual database edits, and missing database constraints. The correct posture is never to assume cycle-free data; it is to protect every recursive CTE with cycle detection. On PostgreSQL 14 and later, use the `CYCLE` clause. On earlier versions, track visited IDs in a path array and guard with `WHERE id != ANY(path)`. Always add a depth limit as a second layer of protection. And consider a constraint trigger to prevent cycles at the data level — making safe traversal a property of the schema, not just of the query.

The query works perfectly on clean data. Clean data is a temporary condition. Write the query to survive dirty data — because dirty data is the permanent state of production.
