# The SELECT * Over-Fetch

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. The Deceptively Simple Query That Costs a Fortune

There is a line of SQL that every developer writes on their very first day of learning databases. It is short, elegant, and universally taught as the starting point for querying data:

```sql
SELECT * FROM users;
```

The asterisk — that little star — feels friendly. It means "give me everything," and when you are exploring data or prototyping a feature, that is exactly what you want. You do not need to think about which columns exist. You do not need to update your query when the schema changes. You just ask for everything and let the database figure it out. It feels like a convenience.

In production, at scale, that convenience becomes one of the most expensive habits a developer can have. Not because the query is wrong in a syntactic sense — it is perfectly valid SQL — but because of what the database actually does when it executes it, and what happens to all that data as it flows from disk to database memory to network to application server to your code. This case study is about understanding that full journey, and why paying attention to every stop along the way is the mark of an engineer who genuinely understands their system.

---

## 2. How a Database Actually Retrieves Your Data — The Full Journey

To understand why `SELECT *` is costly, you first need to understand what happens physically when a query runs. Most beginners imagine the process as simple: you write a query, the database finds the rows, and the data appears in your application. The reality involves several distinct stages, each of which has a cost, and each of which is multiplied by the amount of data you ask for.

The journey begins on **disk**. A relational database stores its tables in fixed-size blocks called **pages** — typically 8 kilobytes each in PostgreSQL. When you ask for rows from the `users` table, the database engine must load the relevant pages from disk into its **buffer pool** (an in-memory cache). If a row is 10 kilobytes wide because it contains a large `TEXT` biography field, a `JSONB` blob of user preferences, and a `BYTEA` column containing a profile picture thumbnail, then even a single row might span more than one page. The wider the row, the more pages must be loaded from disk.

Once the rows are in the buffer pool, the database engine processes them — applying filters, performing joins, evaluating conditions. Then the resulting rows must be **serialised** — converted from the database's internal format into a wire protocol format — and transmitted across the **network** to your application server. Your application then deserialises that data, allocates memory to hold it, and finally your code accesses the three columns it actually needed.

```
  The Full Journey of a SELECT * Query
  ======================================

  [Disk Storage]
    Pages containing ALL columns of matching rows
    (id, name, email, phone, address, bio, avatar,
     preferences_json, metadata_json, created_at,
     updated_at, deleted_at, ... 80 columns total)
         |
         | I/O cost: reading ALL column data from disk pages
         v
  [Database Buffer Pool / Memory]
    Full row data loaded and held in DB memory
    10KB average row × 100,000 rows = ~1GB in DB RAM
         |
         | Serialisation cost: converting ALL columns to wire format
         v
  [Network Transfer]
    ~1GB of data travels from DB server → App server
    (your app only asked for 3 of those 80 columns)
         |
         | Deserialisation + allocation cost
         v
  [Application Server Memory]
    ORM hydrates objects with all 80 fields
    Your code accesses: user.id, user.name, user.email
    The other 77 fields sit in RAM doing nothing
         |
         v
  [Your Code]
    return { id: user.id, name: user.name, email: user.email }
    → 77 fields worth of data was moved and allocated for zero reason
```

Every stage in this pipeline has a real cost — I/O operations, memory allocation, CPU cycles for serialisation, and network bandwidth. When you use `SELECT *`, you pay every one of these costs for every column in the table, regardless of whether your code ever touches those columns. When you specify only the columns you need, you pay only for what you use. The difference, at scale, is not marginal — it is often the difference between a system that works and one that does not.

## 3. The Real Pattern — How SELECT * Ends Up in Production Code

Understanding the technical cost is only half the picture. The other half is understanding how this anti-pattern persists in real codebases, because it is never born from malice or ignorance — it always comes from one of a small number of very understandable habits.

The most pervasive source is **ORM default behaviour**. Object-Relational Mappers like Django ORM, ActiveRecord in Rails, GORM in Go, TypeORM in Node.js, and Hibernate in Java all share a common default: when you query for records without specifying columns, they issue a `SELECT *` on your behalf. Consider the following GORM code, which is representative of how most developers interact with databases through an ORM:

```go
// This looks innocent. Underneath, GORM issues:
// SELECT * FROM users WHERE id = ?
var user User
db.Where("id = ?", userID).First(&user)

// You then do this:
response := UserResponse{
    ID:    user.ID,
    Name:  user.Name,
    Email: user.Email,
}
```

The code looks clean. The abstraction hides the SQL. There is no visible asterisk anywhere. But the ORM has dutifully fetched all eighty columns, hydrated a full `User` struct in memory with all of them, and your code then picks three fields off of it. The other seventy-seven fields — the biography text, the preferences blob, the avatar bytes — were loaded from disk, transmitted across the network, allocated in memory, and immediately discarded. This happens on every single request that touches a user record.

The second source is **copy-pasted queries**. A developer writes `SELECT * FROM users` during debugging or exploration, and the query gets copied into application code because it works. Nobody stops to ask whether it should be scoped. The table at that point might have twenty columns. A year later, when the schema has grown to eighty columns and the user base has grown to millions, that same query is still running unchanged in production.

The third source is the **safety mindset** — "I'll just grab everything in case I need it later." This feels like forward-thinking but it is actually the opposite. It trades a guaranteed ongoing cost (the over-fetching, on every request, forever) for the avoidance of a hypothetical future inconvenience (having to add a column to a query). The calculus never works out in favour of `SELECT *`.

## 4. The Mathematics of Waste — Making the Cost Concrete

Abstract warnings about performance are easy to dismiss. Numbers are harder to ignore. Let us make the cost of `SELECT *` concrete with arithmetic that reflects a realistic production scenario.

Suppose you have a `users` table with eighty columns. A typical row — including a short biography, a JSON blob of preferences, a JSON blob of metadata, and assorted indexed fields — averages out to approximately ten kilobytes per row. Your application has grown to one hundred thousand active users. You have a dashboard page that lists users with their name, email, and account status. You run this query for every page load of that dashboard:

```
  The Arithmetic of Over-Fetching
  =================================

  Average row width:          10 KB  (with TEXT, JSONB, BYTEA columns)
  Rows returned per query:    100,000
  Columns in table:           80
  Columns actually used:      3  (id, name, email)

  Data transferred with SELECT *:
    10 KB × 100,000 rows = 1,000,000 KB = ~1 GB per query execution

  Data transferred with SELECT id, name, email:
    ~100 bytes × 100,000 rows = ~10 MB per query execution

  Waste ratio:  1 GB vs 10 MB  →  you are moving ~100× more data than necessary

  If this dashboard is loaded 50 times per day:
    SELECT *  → 50 GB of unnecessary data transferred daily
    SELECT id, name, email → 500 MB total — a perfectly reasonable number
```

One gigabyte of data moving from your database server to your application server per query execution. Fifty times per day. That is fifty gigabytes of network traffic that buys you absolutely nothing. It saturates your internal network, fills your application server's memory, triggers garbage collection, slows down every other concurrent operation sharing that network link, and degrades the experience for every user on the platform simultaneously.

And this is not an extreme example. These numbers are conservative. Tables with binary data, rich JSONB documents, or long text fields routinely have average row widths far exceeding ten kilobytes. At ten million users instead of one hundred thousand, the numbers become catastrophic.

## 5. The Symptom That Fools You — Why EXPLAIN Lies

This anti-pattern has a particularly cruel property: the most common debugging tool — the `EXPLAIN ANALYZE` output in PostgreSQL — can actively mislead you when the bottleneck is data transfer rather than query execution.

When you run `EXPLAIN ANALYZE` on a `SELECT *` query that has a proper index, you might see output like this:

```
EXPLAIN ANALYZE SELECT * FROM users WHERE account_status = 'active';

Index Scan using idx_users_status on users
  (cost=0.43..8.45 rows=1000 width=10240)
  (actual time=0.015..2.341 rows=98432 loops=1)
Planning Time: 0.182 ms
Execution Time: 2.341 ms       ← Database says: "Done in 2ms!"
```

The database is telling you the query finished in 2.3 milliseconds. That sounds excellent. You look at this output and conclude: "The query is fast. The index is being used. There is no problem here." You close the terminal and move on.

But what `EXPLAIN ANALYZE` measures is the time it takes for the database engine to identify and retrieve the rows into its own memory. It does not measure the time it takes to serialise all eighty columns, transmit that data across the network, or for the application to deserialise and allocate it. Those costs are invisible to the database's own timing. The query can be "fast" by database metrics while simultaneously being the single biggest performance problem your application has — and you will never find it by only looking at EXPLAIN output.

```
  The Measurement Gap
  ====================

  What EXPLAIN ANALYZE measures:
  ┌─────────────────────────────────────────────┐
  │  DB Engine: find rows, load from pages      │
  │  Reported execution time: 2.3ms  ✅          │
  └─────────────────────────────────────────────┘

  What EXPLAIN ANALYZE does NOT measure:
  ┌─────────────────────────────────────────────┐
  │  Serialise 80 columns per row → wire format │
  │  Transmit ~1GB across network               │  ← This is where
  │  App: deserialise, allocate structs in RAM  │     your 8 seconds
  │  App: garbage collect dead fields           │     went
  └─────────────────────────────────────────────┘

  User experience: "Why does this page take 8 seconds?"
  EXPLAIN says:    "Query execution: 2.3ms"
  Both are true. They measure different things.
```

This gap between database execution time and application response time is one of the most confusing and time-consuming bugs a developer can face. The database looks healthy. The application is slow. The network layer — invisible to most monitoring tools unless you are specifically measuring it — is where your performance is disappearing. Knowing that `SELECT *` produces this exact symptom profile is the key to diagnosing it quickly.

## 6. The Symptoms as They Appear in Production

When the `SELECT *` anti-pattern has taken hold in a production system, the symptoms manifest in a very recognisable pattern across your monitoring stack. Knowing what to look for allows you to identify the problem before users report it, and to know immediately where to look when they do.

The first and most telling symptom is **elevated network bandwidth between your application servers and your database server**. In a well-optimised system, this bandwidth should be modest — databases are supposed to return results, not stream raw data. If you observe hundreds of megabytes or gigabytes per minute flowing from your database to your application on a routine basis, `SELECT *` on wide tables is very likely the cause. Cloud providers like AWS and GCP expose this metric in their RDS and CloudSQL dashboards; it is one of the first things to look at during a performance investigation.

The second symptom is **slow application response times that do not correlate with slow database query times**. This is the diagnostic signature described in the previous section. Your APM tool (Application Performance Monitoring — New Relic, Datadog APM, Sentry Performance) shows an API endpoint taking three to eight seconds to respond. Your slow query log shows nothing for that endpoint. The database considers itself to be performing well. The bottleneck is hiding in the serialisation and transfer layer, which neither tool naturally exposes.

The third symptom is **memory pressure on your application servers**. When your code fetches wide rows and instantiates large objects in memory — even if it only uses three fields from each — those objects occupy RAM for the duration of their lifecycle. On high-throughput systems, this means thousands of fat objects alive in memory simultaneously. You will see garbage collection pressure in your application metrics: frequent GC pauses in JVM-based systems, high heap usage in Node.js processes, elevated RSS (Resident Set Size) in Go services. The application is not doing more work — it is simply carrying more weight per unit of work.

## 7. The Solutions — What Senior Engineers Actually Do

The fix for `SELECT *` is conceptually simple, but applying it consistently across a real codebase requires both discipline and the right tooling patterns.

### The Fundamental Fix — Explicit Column Lists

The baseline solution is also the most important one: always name the columns you need in your SELECT statement. This is not about writing more code — it is about writing more intentional code. Every query should be a precise description of the data contract your code requires.

```sql
-- ❌ The anti-pattern: asks for everything, uses almost nothing
SELECT * FROM users WHERE account_status = 'active';

-- ✅ The correct approach: asks for exactly what the code needs
SELECT id, name, email, account_status FROM users WHERE account_status = 'active';
```

The right way to think about this is: **your SELECT list is a contract**. It says "my code requires exactly these fields." When you write `SELECT *`, you have no contract at all. When the schema changes and a large column is added, your query silently becomes more expensive. When you specify columns explicitly, a new column's addition has zero impact on queries that do not need it.

### ORM Projections — Deferring and Selecting Specific Fields

Since most production applications use ORMs rather than raw SQL, the practical skill is knowing how to express column selection through your ORM's API. Every major ORM provides this capability, though the syntax differs.

```go
// GORM — select specific columns only
var users []User
db.Select("id", "name", "email").
   Where("account_status = ?", "active").
   Find(&users)
// Generates: SELECT id, name, email FROM users WHERE account_status = 'active'

// GORM — defer large columns (fetch everything except the heavy ones)
db.Omit("bio", "preferences", "metadata").
   Where("account_status = ?", "active").
   Find(&users)
// Generates: SELECT id, name, email, phone, ... (all columns EXCEPT bio, preferences, metadata)
```

```typescript
// TypeORM — select specific columns
const users = await userRepository.find({
  select: ["id", "name", "email"],
  where: { accountStatus: "active" }
});
// Generates: SELECT id, name, email FROM users WHERE account_status = 'active'
```

```python
# Django ORM — values() for dictionary projection
users = User.objects.filter(
    account_status='active'
).values('id', 'name', 'email')
# Generates: SELECT id, name, email FROM users WHERE account_status = 'active'

# Django ORM — defer() to exclude heavy columns
users = User.objects.filter(
    account_status='active'
).defer('bio', 'preferences', 'metadata')
# Fetches everything except the deferred columns
```

The ORM approach of using `defer` or `omit` is particularly valuable for the case where a table has a few extremely large columns that are only needed in specific contexts — a user biography shown on the profile page but not needed in the user list. You can defer those columns by default and load them only when the relevant page is actually being served.

### The Use-Case-Specific View Pattern

For applications with many different consumers of the same table — an admin panel, a user profile page, a search results list, an API endpoint — a powerful pattern is to define **database views** or explicit **query builder functions** that encode the right column selection for each context. Rather than having every developer decide which columns to select, you centralise that decision.

```sql
-- A view for the user list context: only what list pages need
CREATE VIEW users_list_view AS
  SELECT id, name, email, account_status, created_at
  FROM users;

-- A view for the profile context: richer but still not everything
CREATE VIEW users_profile_view AS
  SELECT id, name, email, phone, address, bio, account_status, created_at
  FROM users;

-- Raw table access with full columns: only for admin and internal tools
-- SELECT * FROM users -- reserved for admin contexts with explicit justification
```

Application code then queries the view rather than the base table. This creates a hard architectural boundary: it is impossible to accidentally over-fetch if the view does not contain the heavy columns.

### Covering Indexes — Moving the Solution to the Storage Layer

For queries where performance is absolutely critical — hot paths that run thousands of times per second — you can go a step further and use **covering indexes**. A covering index is an index that contains all the columns a query needs, so the database engine can answer the query entirely from the index without touching the main table data at all. This is called an **index-only scan**.

```sql
-- Create a covering index that includes all columns the list query needs
CREATE INDEX idx_users_status_covering
ON users (account_status)
INCLUDE (id, name, email);

-- This query can now be answered entirely from the index
SELECT id, name, email FROM users WHERE account_status = 'active';
-- Query plan will show: Index Only Scan — never reads the table pages at all
```

```
  Covering Index — Index Only Scan
  ==================================

  Regular query (even with index on account_status):
    Index → find matching rows → fetch main table pages → return all columns
    Cost: index lookup + table page I/O

  With covering index (INCLUDE id, name, email):
    Index → find matching rows → return id, name, email directly from index
    Cost: index lookup only — zero table page I/O
    ✅ Fastest possible execution for this query
```

The covering index approach is not appropriate for every query, but for your most frequently executed, performance-critical queries, it is one of the most powerful tools available.

## 8. Building the Habit — Column Selection as a First Principle

The deepest lesson here is not a technical one — it is a discipline one. `SELECT *` persists in codebases not because developers do not know better, but because it is easier and faster in the short term. The key to preventing it is making column selection a **first principle** rather than an afterthought.

In practice, this means treating the select list as part of your data contract definition. When you design a feature, you think explicitly about what data it needs. When you write a query or an ORM call, that explicit list of fields is not an optional detail — it is a core part of the implementation. When you review code, `SELECT *` or an ORM call without explicit field selection is a signal to ask: "What columns does this actually need?" The same way you would not accept `catch (Exception e) {}` that swallows every error, you should not accept `SELECT *` that requests every column.

```
  The Developer Mindset Shift
  ============================

  ❌ Old thinking:
     "I'll grab everything and let the code pick what it needs."
     Cost: paid at runtime, on every request, forever, by every user

  ✅ New thinking:
     "My query is a contract. I specify exactly what I need."
     Cost: paid once, at development time, by the developer writing the query
```

The economics are stark. The developer pays a few extra seconds to write `id, name, email` instead of `*`. The alternative is the database paying gigabytes of unnecessary I/O on every request for the entire lifetime of the application. As an engineer, it is your job to take on the small costs so your systems do not pay the large ones.

---

## 9. The Golden Rule

> Every byte your database sends to your application costs CPU, memory, network bandwidth, and time. `SELECT *` charges you for every column in every row — the vast majority of which your code will never read. The discipline of writing explicit column lists is not pedantry; it is the recognition that data does not move for free. Specify only what you need, and your system will spend its resources on work that matters.

The asterisk is for exploration. Explicit columns are for production. Every senior engineer you will ever work with knows the difference. Now you do too.
