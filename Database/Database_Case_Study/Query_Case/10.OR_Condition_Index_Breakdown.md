# The OR Condition Index Breakdown

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. The Query That Feels Like It Should Work

You are building a login system. A user can sign in with their email address, their phone number, or their username — whichever they registered with, whichever they remember today. On the backend, you need to find the user record regardless of which identifier they provided. You look at your `users` table, you see that `email`, `phone`, and `username` all have indexes on them, and you write what feels like the obvious query:

```sql
SELECT * FROM users
WHERE email = 'alice@example.com'
   OR phone = '555-1234'
   OR username = 'alice_92';
```

This is logically correct. It expresses your intent precisely. The three columns are indexed. You run it on your development database and it returns instantly. You ship it.

Six months later, your user base has grown from ten thousand to five million. Your login endpoint starts timing out under load. Your on-call engineer pulls up the EXPLAIN output and discovers something baffling: the query is doing a full sequential scan of five million rows — despite the fact that all three columns have individual indexes sitting right there, ready to be used. The indexes exist. The query uses those columns. And yet: sequential scan.

This is the OR Condition Index Breakdown, and it is particularly confusing because the failure mechanism is less obvious than the previous anti-patterns we have discussed. It is not about functions destroying index keys, and it is not about wildcards preventing seeks. It is about a fundamental limitation in how query engines handle multiple independent indexes simultaneously — a limitation with important architectural implications for how you design identity lookups in your systems.

---

## 2. Why Two Indexes Cannot Both Be Used for OR — The Core Problem

To understand the problem, let us first be precise about what it means to use an index for a query. When the query planner decides to use an index, it performs an **index scan**: it navigates the B-Tree for that index to find the matching entries and retrieves the corresponding rows. This is fast because the index is sorted and the scan is targeted — it reads only the rows that satisfy the condition.

Now consider the OR condition: `WHERE email = 'a@b.com' OR phone = '555-1234'`. Think about what the query engine actually needs to produce: a set of rows where **at least one** of these conditions is true. Some rows might match only the email condition. Some might match only the phone condition. A row that matches both should appear exactly once in the results. The final result set is the **union** of two sets of rows.

The challenge for the query planner is that these two sets live in completely separate indexes. The index on `email` knows nothing about `phone`. The index on `phone` knows nothing about `email`. To produce the correct union, the planner would need to:

1. Scan the `email` index and collect matching row identifiers
2. Scan the `phone` index and collect matching row identifiers
3. Merge both sets of identifiers, deduplicating any row that appears in both
4. Fetch the actual rows by those combined identifiers

```
  The Index Merge Problem
  ========================

  Index on email:                     Index on phone:
  ┌────────────────────────────┐      ┌────────────────────────────┐
  │ 'alice@example.com' →  #42 │      │ '555-0001' → #1            │
  │ 'bob@example.com'   →  #91 │      │ '555-1234' → #42  ←──────┐ │
  │ ...                        │      │ '555-9999' → #88          │ │
  └────────────────────────────┘      └────────────────────────────┘
          │                                      │
          │ Scan 1: find email match             │ Scan 2: find phone match
          │ → row #42                            │ → row #42
          │                                      │
          └──────────────────┬───────────────────┘
                             │
                    Merge + deduplicate
                    → row #42  (appears in both → include once)

  This is called an "Index Merge (Union)" operation.
  It is possible in some databases but has significant overhead.
  Most query planners abandon it for a sequential scan once
  the estimated benefit does not outweigh the merge cost.
```

Some databases, including PostgreSQL and MySQL, do support a technique called **Index Merge (Union)**, where they perform exactly this two-index-scan-and-merge approach. But here is the critical detail that many developers miss: the query planner only chooses this approach when it estimates the merge will be cheaper than a sequential scan. That estimation depends on statistics — specifically, on how selective the query planner believes each condition to be.

When your table is small, the planner's estimates are reasonable and it may choose Index Merge. When your table grows to millions of rows, the planner's statistics might suggest that too many rows match each condition, making the merge overhead appear more expensive than just scanning the table linearly. At that point, it abandons both indexes and falls back to a sequential scan — and you get the scenario described at the beginning: five million rows scanned despite three available indexes.

## 3. Reading the Evidence in EXPLAIN

The EXPLAIN output for this anti-pattern can take a few different forms depending on the database version, table size, and planner statistics. Understanding all of them will make you a much more effective diagnostician.

The first and most alarming form is the pure sequential scan, which the planner chooses when it estimates neither index individually nor a merge between them would be efficient:

```sql
EXPLAIN ANALYZE
SELECT * FROM users
WHERE email = 'alice@example.com'
   OR phone = '555-1234';
```

```
Seq Scan on users
  (cost=0.00..182435.00 rows=2 width=486)
  (actual time=0.041..9842.331 rows=1 loops=1)
  Filter: ((email = 'alice@example.com') OR (phone = '555-1234'))
  Rows Removed by Filter: 4999999
Planning Time: 0.211 ms
Execution Time: 9842.331 ms     ← nearly 10 seconds
```

Five million rows removed by filter. Ten seconds. One matching row found. The indexes on `email` and `phone` were completely ignored.

The second form — which looks better on the surface but is often still poor — is the Bitmap OR scan, which PostgreSQL may choose for medium-sized tables:

```
BitmapOr
  → Bitmap Index Scan on idx_users_email
      Index Cond: (email = 'alice@example.com')
  → Bitmap Index Scan on idx_users_phone
      Index Cond: (phone = '555-1234')
→ Bitmap Heap Scan on users
    Recheck Cond: ((email = ...) OR (phone = ...))
```

This is the planner attempting the Index Merge Union approach. Both indexes are scanned, the results are combined using bitmap OR operations, and then the heap (actual table rows) is accessed for the combined set. This is better than a full sequential scan, but it still carries the overhead of scanning two indexes, building two bitmaps, ORing them together, and then rechecking the original condition. For a login query that should complete in under a millisecond, even this approach is not good enough at scale.

## 4. Why This Pattern Appears Everywhere

Before discussing solutions, it is worth understanding why this pattern is so pervasive. The multi-field identity lookup — "find a user by any of their identifiers" — is not an edge case. It is a core requirement in a huge proportion of real-world applications:

Authentication systems need to look up a user by email, phone, or username — whichever the user provides at login time. Customer support tools need to find a customer by any identifier a support agent might have: email, phone, account number, order number. Search-by-any-field forms in admin panels let operators search for records using whatever information they have at hand. API endpoint lookups might accept either an external UUID or an internal ID depending on the caller.

```
  The Multi-Identity Lookup Pattern — Extremely Common
  ======================================================

  "Find me this user" — but the caller might have any of:
  ┌──────────────────────────────────────────────────────┐
  │  email        alice@example.com                      │
  │  phone        +1-555-1234                            │
  │  username     alice_92                               │
  │  account_id   ACC-00042                              │
  │  oauth_sub    google:1092384756                      │
  └──────────────────────────────────────────────────────┘

  Naive query:
  WHERE email = ? OR phone = ? OR username = ? OR account_id = ?

  Result at scale: full sequential scan, every time
```

The pattern feels natural and the query expresses the intent perfectly. But natural and performant are different things at database scale, and the job of the senior engineer is to bridge that gap — to find the way of expressing the intent that the database can execute efficiently.

## 5. Solution One — UNION ALL Across Separate Queries

The most universally effective solution is to decompose the single OR query into multiple separate queries, each targeting one indexed column, and combine their results with `UNION ALL`. This works because each individual query can use its own index cleanly and independently — there is no merge overhead, no planner uncertainty, no estimation gamble.

```sql
-- ❌ Single query with OR: may not use indexes at scale
SELECT * FROM users
WHERE email = 'alice@example.com'
   OR phone = '555-1234'
   OR username = 'alice_92'
LIMIT 1;

-- ✅ UNION ALL: each sub-query uses its own index cleanly
SELECT * FROM users WHERE email    = 'alice@example.com'
UNION ALL
SELECT * FROM users WHERE phone    = '555-1234'
UNION ALL
SELECT * FROM users WHERE username = 'alice_92'
LIMIT 1;
```

Each of the three sub-queries in the `UNION ALL` is a simple equality lookup on a single indexed column. The planner can use the index for each one without hesitation. The results are concatenated (UNION ALL preserves duplicates, which is fine here — we add LIMIT 1 to stop as soon as the first matching row is found).

```
  UNION ALL Execution Plan
  =========================

  Sub-query 1: SELECT ... WHERE email = 'alice@example.com'
  ┌────────────────────────────────────────────────────────┐
  │ Index Scan on idx_users_email                          │
  │ Found: row #42  → return immediately (LIMIT 1 hit)     │
  └────────────────────────────────────────────────────────┘
  ← Query stops here because LIMIT 1 is satisfied

  Sub-query 2 and 3: never executed — short-circuit by LIMIT
  Execution time: ~0.2ms  ✅
```

An important subtlety: with `UNION ALL` and `LIMIT 1`, PostgreSQL is smart enough to stop executing sub-queries once the limit is satisfied. If the email sub-query finds a match, the phone and username sub-queries never run at all. In the common case where any one identifier is sufficient, this means the query almost always executes only a single index scan.

**Implementing UNION ALL in application code** requires a small shift in how you structure queries. In Go with GORM, raw SQL union queries are the clearest approach:

```go
func FindUserByAnyIdentifier(db *gorm.DB, email, phone, username string) (*User, error) {
    var user User
    err := db.Raw(`
        SELECT * FROM users WHERE email    = ?
        UNION ALL
        SELECT * FROM users WHERE phone    = ?
        UNION ALL
        SELECT * FROM users WHERE username = ?
        LIMIT 1
    `, email, phone, username).Scan(&user).Error

    if err != nil {
        return nil, err
    }
    return &user, nil
}
```

In Node.js with Knex:

```typescript
async function findUserByAnyIdentifier(
    email: string,
    phone: string,
    username: string
): Promise<User | null> {
    const result = await knex.raw(`
        SELECT * FROM users WHERE email    = ?
        UNION ALL
        SELECT * FROM users WHERE phone    = ?
        UNION ALL
        SELECT * FROM users WHERE username = ?
        LIMIT 1
    `, [email, phone, username]);

    return result.rows[0] ?? null;
}
```

## 6. Solution Two — The Normalised Lookup Table

The `UNION ALL` approach is effective and should be your first choice for many situations. But it has one architectural weakness: every time you add a new type of identifier — say, an OAuth subject ID or a legacy account number — you need to add another sub-query to every place in your codebase that performs this lookup. In a large codebase with many services, that becomes a maintenance burden and a source of bugs where some services are updated and others are not.

A more elegant and scalable architectural approach is to normalise all user identifiers into a dedicated **lookup table**. Instead of storing email, phone, and username as separate columns on the `users` table, you store all identifiers in a single table with a `value` column and a `type` column. The `value` column gets a single B-Tree index, and every lookup — regardless of identifier type — becomes a simple equality query on that one indexed column.

```sql
-- The normalised lookup table design
CREATE TABLE user_identifiers (
    id         BIGSERIAL    PRIMARY KEY,
    user_id    BIGINT       NOT NULL REFERENCES users(id),
    type       VARCHAR(32)  NOT NULL,  -- 'email', 'phone', 'username', 'oauth_google', ...
    value      VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- Single composite index: unique per type+value, fast lookup by value alone
CREATE UNIQUE INDEX idx_user_identifiers_type_value
    ON user_identifiers (type, value);

-- Optional: index on value alone for cross-type lookups
CREATE INDEX idx_user_identifiers_value
    ON user_identifiers (value);
```

With this design, a user who has an email, phone number, and username has three rows in `user_identifiers` — one for each identifier — all pointing to the same `user_id`. When you need to look up a user by any identifier, the query is always the same simple form:

```sql
-- Find user by any identifier (email, phone, username, or anything else)
SELECT u.*
FROM users u
JOIN user_identifiers ui ON u.id = ui.user_id
WHERE ui.value = 'alice@example.com'   -- or '555-1234', or 'alice_92', or anything
LIMIT 1;
```

```
  Normalised Lookup Table — Architecture
  ========================================

  users table:
  ┌─────┬──────────────┬─────────────────────────────────┐
  │ id  │ display_name │ ... (non-identity columns only)  │
  ├─────┼──────────────┼─────────────────────────────────┤
  │ 42  │ Alice        │ ...                              │
  └─────┴──────────────┴─────────────────────────────────┘

  user_identifiers table (single value column, indexed):
  ┌─────┬─────────┬─────────────────┬──────────────────────┐
  │ id  │ user_id │ type            │ value                │
  ├─────┼─────────┼─────────────────┼──────────────────────┤
  │ 1   │ 42      │ 'email'         │ 'alice@example.com'  │
  │ 2   │ 42      │ 'phone'         │ '555-1234'           │
  │ 3   │ 42      │ 'username'      │ 'alice_92'           │
  │ 4   │ 42      │ 'oauth_google'  │ 'google:10923847'    │
  └─────┴─────────┴─────────────────┴──────────────────────┘

  Lookup query:
  WHERE ui.value = 'alice@example.com'   ← single index scan, always fast
  JOIN to users on user_id               ← primary key lookup, instant
```

The lookup is now a single indexed equality scan on `user_identifiers.value`, followed by a primary key join to `users`. Both operations are O(log n) — fast regardless of how many users or identifiers exist. Adding a new identifier type requires no schema change and no query change: you insert a new row in `user_identifiers` with the new type and value. The lookup query works identically for every type of identifier that will ever exist.

This pattern also naturally handles the deduplication problem: a user can have multiple identifiers of the same type (two email addresses, for instance) simply by having multiple rows with different values. Revoking an identifier is a simple row deletion. Auditing who last used which identifier becomes straightforward to add.

## 7. Solution Three — Partial UNION in Application Code

Sometimes the cleanest solution is to not write this query in SQL at all for the general case, but instead to structure the application logic so that the database always receives a single-column lookup. This is the pattern used by many high-scale authentication systems.

When a user submits a login form with a single identifier, your application code can determine the type of the identifier before hitting the database — an email always contains `@`, a phone matches a numeric pattern, everything else is a username. You then issue a targeted, single-column query:

```go
func FindUserByIdentifier(db *gorm.DB, identifier string) (*User, error) {
    var user User
    var err  error

    switch IdentifierType(identifier) {
    case IdentifierEmail:
        err = db.Where("email = ?", identifier).First(&user).Error
    case IdentifierPhone:
        err = db.Where("phone = ?", identifier).First(&user).Error
    case IdentifierUsername:
        err = db.Where("username = ?", identifier).First(&user).Error
    }

    if err != nil {
        return nil, err
    }
    return &user, nil
}

// Classify the identifier before touching the database
func IdentifierType(s string) string {
    if strings.Contains(s, "@") {
        return IdentifierEmail
    }
    if phoneRegex.MatchString(s) {
        return IdentifierPhone
    }
    return IdentifierUsername
}
```

This approach is attractive because it produces the cleanest possible SQL — a single equality condition on a single indexed column — and the logic cost of classification is trivial (a string operation taking nanoseconds). The trade-off is that the classification logic must be correct and maintained. If the business rules about what constitutes a valid email, phone, or username change, you need to update the classification function. This is a manageable trade-off for most applications.

## 8. Choosing the Right Solution

With three solid approaches available, the question becomes: which one belongs in which situation? The answer depends on the nature of your lookup requirements and the expected evolution of your schema.

If your identifiers are few, fixed, and unlikely to change — just email and phone, perhaps — the **UNION ALL** approach is the right choice. It is simple, explicit, produces clean execution plans, and adds no schema complexity. You can implement it quickly and it will perform correctly at any scale.

If your identifiers are numerous, evolving, or need to be managed dynamically — multiple email addresses per user, OAuth providers that you add over time, legacy external IDs from acquired companies — the **normalised lookup table** is the right architecture. It requires more upfront schema work but pays for itself in flexibility and maintainability. This is the pattern used by large-scale identity systems.

If the identifier type can always be determined before the database query is issued — which is more common than developers initially assume — the **application-level classification** approach produces the cleanest SQL and is worth considering as a first option, especially in new systems where you control both the data model and the input validation logic.

```
  Decision Framework
  ===================

  Few, fixed identifier types?
  └── YES → UNION ALL (simple, effective, no schema changes)
       └── Can you classify the type in application code?
            └── YES → Single-column targeted query (cleanest SQL)

  Many, evolving identifier types?
  └── YES → Normalised lookup table (most flexible, best long-term)

  Legacy system, cannot change queries?
  └── YES → Check if expression index or covering index helps;
             consider adding lookup table alongside existing schema
```

## 9. The Deeper Lesson — OR Across Columns Is Structurally Hard

The reason this anti-pattern is worth studying carefully — more carefully than a simple performance fix — is that it reveals something important about the nature of indexing itself. Indexes are built on the assumption that you are looking for specific values in a specific column. The B-Tree is sorted by one thing at a time. When your query condition spans multiple independent columns with OR, you are asking the database to answer a question that its index structure was not designed to answer natively.

The solutions we have discussed — UNION ALL, normalised tables, application classification — all share a common strategy: they decompose the multi-column OR problem into multiple single-column equality problems, each of which the database can answer cleanly with a single index. This decomposition is the insight. Any time you see OR across different columns in a performance-critical query, your instinct should be to ask: "How can I rewrite this as a union of independent lookups?"

This intuition extends beyond the specific login example. A product search that says "find items where category = X OR tag = Y OR brand = Z" has the same structure and the same problem. A notification system that says "find events where user_id = ? OR group_id = ?" has the same structure. The pattern recurs constantly, and recognising it is the first step to knowing how to handle it.

---

## 10. The Golden Rule

> OR across different columns is one of the hardest conditions to index efficiently, because each column's index is independent — the database cannot use both simultaneously to produce a merged result without significant overhead. At scale, the query planner often abandons both indexes entirely and falls back to a full sequential scan. The solution is always to decompose the OR into independent single-column lookups — through UNION ALL in SQL, through a normalised lookup table in schema design, or through type classification in application code — so that each lookup lands cleanly on its own index. Always verify with EXPLAIN: an indexed column in an OR clause is no guarantee that the index will be used.

OR across columns looks indexed. At scale, it is not. Now you know the difference — and three ways to fix it.
