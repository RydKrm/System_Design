# The Unbounded IN Clause — A Case Study in Growing Yourself Into a Wall

> *Explained by a senior engineer to someone who is just starting out. This case study is about a pattern that starts as a clever optimization — avoiding N+1 queries by batching IDs — and then slowly mutates into something that can crash your query planner, exhaust your database memory, and bring down your application. It is a story about a good idea taken too far, without a guard rail.*

---

## The Setup — A Caching Layer and a List of IDs

Imagine you are building a social media feed. When a user loads their home feed, you need to show posts from all the people they follow. Your system has a separate caching layer — perhaps Redis — that stores which user IDs each person follows. Loading the follower list from Redis is extremely fast, nearly instant. The cache returns a list of user IDs: `[42, 107, 891, 2034, 5901, ...]`.

Now you need to fetch the actual posts from the database for those users. You have a list of IDs and you need the rows from the `posts` table that correspond to them. The most natural, readable SQL for this is:

```sql
SELECT * FROM posts
WHERE user_id IN (42, 107, 891, 2034, 5901)
ORDER BY created_at DESC
LIMIT 50;
```

This is a perfectly legitimate query. `IN` with a handful of values is standard SQL, supported by every database, efficient, and correct. You test it, it works beautifully, and you ship it.

Six months later, your platform has grown. Some of your most active users follow tens of thousands of accounts — influencers, news sources, brands, friends. The cache still returns correctly — a list of user IDs. But now that list has 50,000 entries. And your query looks like this:

```sql
SELECT * FROM posts
WHERE user_id IN (42, 107, 891, 2034, 5901, 6002, 7843, 9001, 10234, ...,
                  49871, 49902, 49933, 49964, 49995, 50000, 50001, 50002,
                  -- ... 49,990 more values ...
                  )
ORDER BY created_at DESC
LIMIT 50;
```

That query is 50,000 IDs long. And it is going to hurt the database in ways you did not anticipate.

---

## What the Database Planner Has to Do With an IN List — The Hidden Cost

To understand why a large `IN` list is a problem, you need to understand what happens inside the database the moment your query arrives. Before the database executes a single line of work to retrieve rows, it must go through its **query planning** phase. The planner is the part of the database that looks at your query and figures out the most efficient way to execute it — which indexes to use, in what order to scan tables, how to combine results.

For an `IN` clause, the planner must process the list of values you provided as part of its planning work. It needs to understand the distribution of those values, decide whether to use an index lookup for each value individually, or convert the `IN` list into a different internal representation. With a small IN list — 10, 50, perhaps even a few hundred values — this planning work is negligible. The planner handles it in microseconds.

But with 50,000 values, the planning work becomes significant. The planner must:

```
What the query planner does with IN (50,000 values):

  ┌─────────────────────────────────────────────────────────────┐
  │  PLANNING PHASE (before any data is read):                  │
  │                                                             │
  │  1. Parse the IN list                                       │
  │     → Tokenize and validate 50,000 integer literals         │
  │     → Build an internal data structure holding all 50,000   │
  │                                                             │
  │  2. Deduplicate the list                                     │
  │     → Sort 50,000 values (O(N log N) work)                  │
  │     → Remove duplicates                                     │
  │                                                             │
  │  3. Plan the execution strategy                             │
  │     → Consider: index lookups for each value?               │
  │     → Consider: convert to a hash join with a temp set?     │
  │     → Consider: bitmap AND operations on index results?     │
  │     → Cost-estimate each approach for 50,000 values         │
  │                                                             │
  │  4. Serialize the plan                                      │
  │     → The plan itself may contain all 50,000 values         │
  │                                                             │
  │  All of this before a single data page is read.             │
  │  Planning time: can be 100ms–several seconds at 50,000 IDs  │
  └─────────────────────────────────────────────────────────────┘
```

On top of planning time, the query itself arrives at the database as a SQL string. A list of 50,000 integers, separated by commas and enclosed in parentheses, is not a small string. At roughly 6 characters per average integer plus a comma and space, 50,000 values is approximately 400,000 characters — 400 kilobytes of SQL text. Every time a user loads their feed, your application sends 400KB of SQL text across the network to the database, which must then parse all of it. At 1,000 users loading their feeds simultaneously, that is 400MB per second of SQL text just being transmitted and parsed, before a single row of data is fetched.

---

## The Symptoms — What Goes Wrong and When

The degradation from an unbounded IN clause does not happen in a single dramatic moment. It creeps up gradually as the lists grow larger, and it manifests in several different ways depending on how large the lists get.

At moderate sizes — a few hundred to a couple thousand values — the query is slower than it needs to be, but it runs. Users on your platform who follow many accounts have slightly slower feed loads. Monitoring might show elevated query latency for that specific query without anyone understanding why.

At larger sizes — tens of thousands of values — the planner starts to struggle. Different database versions behave differently here, but PostgreSQL, for instance, has historically had known performance cliffs where the query planner's behavior changes dramatically at certain IN list sizes. The planner may abandon sophisticated join strategies in favor of simpler but slower brute-force approaches because the cost estimation for 50,000 values becomes unreliable.

At extreme sizes — hundreds of thousands of values — the query may simply fail. PostgreSQL has internal limits on the size of data structures used during planning. Some database versions will throw errors when IN lists exceed certain thresholds. Even if the query does not error out, sending hundreds of kilobytes of SQL for a single query is an abuse of the database protocol that can cause connection handling overhead and memory pressure on the database server.

```
IN list size vs. behavior:

  IN list size    │  Planner behavior           │  User experience
  ────────────────┼─────────────────────────────┼──────────────────────────
  IN (1–10)       │  Simple, optimal plan        │  < 1ms, excellent
  IN (10–100)     │  Efficient, index lookups    │  1–5ms, great
  IN (100–1000)   │  Still good, minor overhead  │  5–20ms, fine
  IN (1000–5000)  │  Planning overhead visible   │  20–100ms, slow
  IN (5000–20000) │  Planner struggles, subopt.  │  100ms–1s, bad
  IN (20000+)     │  Planner may give up, errors │  1s+, broken
  IN (100000+)    │  Errors, OOM possible        │  Request fails
```

The particularly cruel aspect of this degradation is that it is user-dependent. Users who follow 50 people have fast feeds. Users who follow 50,000 people have broken feeds. The problem is invisible in your test suite because your test users follow a handful of accounts. The problem is invisible in your monitoring averages because power users are a small fraction of your total user base. But those power users are often your most engaged, most vocal users — the ones most likely to tweet about your site being broken.

## The Network and Memory Cost — An Angle People Forget

Beyond the query planner cost, the unbounded IN clause has a dimension that developers often overlook entirely: the cost of transmitting and holding the query in memory.

Your application builds the IN list as a string, perhaps by joining an array of integers with commas. That string must be transmitted from your application server to the database server over the network. The database server must hold the entire query string in memory while parsing and planning it. If you have a connection pool with 20 connections, and all 20 connections are simultaneously executing 400KB IN-clause queries, your database is holding 8MB of raw SQL text in memory at any given moment, in addition to all the data pages, query plans, and connection state it normally manages.

This might sound trivial, but consider that this memory pressure competes with the database's **buffer pool** — the precious shared memory region where the database caches data pages from disk. When memory pressure increases because of enormous query strings, the buffer pool may need to evict cached data pages to make room. This causes more disk reads for every subsequent query, slowing down your entire system — not just the feed queries.

```
Memory pressure cascade:

  Application sends 400KB IN-clause query
       │
       ▼
  Database holds query text in memory (400KB)
  Database holds parsed query tree in memory (~2MB)
  Database holds query plan in memory (~1MB)
       │
       ▼
  20 concurrent connections × ~3.4MB = ~68MB of query overhead
       │
       ▼
  Buffer pool (say, 4GB total) loses 68MB to query overhead
       │
       ▼
  Data pages get evicted from buffer pool
       │
       ▼
  More disk reads for subsequent queries
       │
       ▼
  Overall database performance degrades
```

## Solution 1 — Batching Into Fixed-Size Chunks

The simplest and most immediately applicable fix requires no schema changes and no architectural redesign. Instead of passing all 50,000 IDs in a single query, you split the list into fixed-size chunks and execute multiple smaller queries, combining the results in your application code.

If you decide each chunk should be at most 500 IDs, then 50,000 IDs becomes 100 queries of 500 IDs each. Each of those queries is fast, plans efficiently, and stays within the comfortable operating range of the database. The total work done is similar — you are still fetching the same data — but the per-query overhead is dramatically lower, and you can interleave these queries with other work or even parallelize them across multiple connections.

```python
def fetch_posts_for_users(user_ids: list[int], chunk_size: int = 500) -> list:
    all_posts = []

    # Split the massive list into safe-sized chunks
    for i in range(0, len(user_ids), chunk_size):
        chunk = user_ids[i : i + chunk_size]

        posts = db.query(
            "SELECT * FROM posts WHERE user_id = ANY($1) "
            "ORDER BY created_at DESC LIMIT 50",
            chunk
        )
        all_posts.extend(posts)

    # Merge and re-sort results from all chunks in application memory
    all_posts.sort(key=lambda p: p.created_at, reverse=True)
    return all_posts[:50]
```

The trade-off with batching is that you now make multiple round trips to the database instead of one, and you must merge and re-sort the results in application memory. For most practical cases, this is acceptable — 100 queries of 500 IDs each, each taking 5ms, totals 500ms if run sequentially. You can reduce this significantly by running chunks in parallel across multiple connections. The merged result is correct and the database is never overwhelmed.

## Solution 2 — Temporary Table + JOIN

For cases where you genuinely need all the results in a single database operation — perhaps because you need accurate pagination or a single consistent view of the data — the right approach is to load your IDs into a **temporary table** and then JOIN against it.

A temporary table is a regular table that exists only for the duration of your database session. It disappears automatically when your connection closes. You insert your 50,000 IDs into it as actual rows, and then write your main query as a JOIN instead of an IN clause. This gives the query planner a completely different — and far more efficient — set of tools to work with.

```sql
-- Step 1: Create a temporary table for this request
CREATE TEMP TABLE feed_user_ids (user_id BIGINT PRIMARY KEY);

-- Step 2: Bulk insert the IDs (efficient, single operation)
INSERT INTO feed_user_ids (user_id)
VALUES (42), (107), (891), (2034), (5901), ...;
-- (or use COPY for very large sets)

-- Step 3: JOIN instead of IN — the planner can now use a hash join
--         or merge join efficiently, choosing the best strategy
--         based on the actual data distribution
SELECT p.*
FROM posts p
JOIN feed_user_ids f ON p.user_id = f.user_id
ORDER BY p.created_at DESC
LIMIT 50;

-- Step 4: Cleanup (or let it drop automatically at session end)
DROP TABLE feed_user_ids;
```

Why is a JOIN to a temp table so much more efficient than a large IN clause? Because the query planner treats the temp table as a real table with statistics. It can build a hash table of the 50,000 IDs in memory, scan the `posts` table, and probe the hash table for each post's `user_id` — a hash join. Or, if both sides are sorted on `user_id`, it can do a merge join that is even faster. The planner has real choices and can make an optimal decision. With a raw IN list of 50,000 literals, the planner's cost estimation degrades because it does not have statistics for a raw value list the same way it does for a table.

PostgreSQL also supports passing arrays directly as parameters, which the driver handles efficiently without embedding all values in the SQL string:

```sql
-- Using PostgreSQL array parameter — cleaner than a long IN list
SELECT * FROM posts
WHERE user_id = ANY($1::BIGINT[])
ORDER BY created_at DESC
LIMIT 50;

-- Pass the array as a parameter, not embedded SQL text
-- The wire protocol handles the array efficiently
```

The `= ANY($1)` form is semantically equivalent to `IN (...)` but passes the values as a structured parameter through the database wire protocol rather than as SQL text. This avoids the SQL text size problem entirely — the IDs are transmitted as binary data, not as a comma-separated string.

## Solution 3 — Restructure the Query to Eliminate the IN Entirely

The deepest and most architecturally sound solution is to question why you need an IN clause at all. If the IN list exists because you are doing a round trip through a cache — fetching IDs from Redis and then querying the database — you might be able to eliminate the cache round trip entirely by keeping the relationship in the database and querying it directly.

Instead of:
```
1. Application → Redis: "Give me the user_ids that user 999 follows"
2. Redis → Application: [42, 107, 891, ..., 50000] (50,000 IDs)
3. Application → Database: "Give me posts WHERE user_id IN (42, 107, ...)"
```

You could keep the follow relationship in the database and write a single query:
```sql
-- No IN list, no cache round trip, single database query
SELECT p.*
FROM posts p
JOIN follows f ON p.user_id = f.followed_id
WHERE f.follower_id = 999
ORDER BY p.created_at DESC
LIMIT 50;
```

This query joins `posts` directly against the `follows` table (which records who follows whom) filtered by the current user's ID. The database has full visibility into the data, can use indexes on both sides of the join, and the query planner can make an optimal decision. There is no IN list. There is no cache round trip. The data stays in the database where the database can work with it efficiently.

```
Architectural comparison:

  Cache-mediated approach (unbounded IN problem):
  ┌──────────┐    IDs    ┌───────┐   SQL with IN   ┌──────────┐
  │   App    │──────────►│ Redis │                  │    DB    │
  │          │◄──────────│       │                  │          │
  │          │  50K IDs  └───────┘                  │          │
  │          │──────────────────────────────────────►          │
  │          │◄──────────────────────────────────────          │
  └──────────┘          huge IN clause               └──────────┘

  Database-join approach (clean):
  ┌──────────┐                                       ┌──────────┐
  │   App    │────────── single JOIN query ──────────►    DB    │
  │          │◄─────────────────────────────────────          │
  └──────────┘           50 result rows               └──────────┘
```

The database-join approach is not always possible — sometimes the data that determines your ID list lives outside the database by design, and that is a valid architectural choice. But it is always worth asking whether the cache is truly necessary, or whether it was added as a premature optimization that introduced more complexity (and more failure modes) than it eliminated.

## How to Detect the Problem Before It Becomes Critical

The unbounded IN clause is detectable before it causes catastrophic failures if you are watching the right signals. The most useful thing to monitor is the **size of queries being sent to the database**. Most application performance monitoring (APM) tools can capture query sizes alongside query times. If you see queries growing in byte size as your application runs, that is a signal that something is building increasingly large SQL strings.

In PostgreSQL's `pg_stat_statements`, the query is normalized — the IN list values are replaced with a single parameter placeholder — so you will see the query as `WHERE id = ANY($1)` or `WHERE id IN ($1, $2, ...)` without the actual values. However, the `mean_time` and `max_time` for that query shape will reveal degradation over time. If the maximum time for a query is growing week over week, and the query involves an IN clause, suspect that the list is growing.

You can also add explicit guard rails in your application code to detect and alert when a list exceeds a threshold:

```python
MAX_IN_CLAUSE_SIZE = 1000

def fetch_posts_for_users(user_ids: list[int]) -> list:
    if len(user_ids) > MAX_IN_CLAUSE_SIZE:
        # Log a warning, route to the batching or temp table path
        logger.warning(
            f"Large IN clause detected: {len(user_ids)} IDs. "
            f"Routing to batch fetch to protect database."
        )
        return fetch_posts_batched(user_ids)
    
    # Safe to use direct IN for small lists
    return db.query("SELECT * FROM posts WHERE user_id = ANY($1)", user_ids)
```

This guard rail serves two purposes: it protects the database from unbounded lists, and it creates a visible signal in your logs every time a user's ID list exceeds the threshold. Tracking these log events over time tells you exactly how your power users are growing and whether the problem is accelerating.

## The Lesson — Every Variable-Length List Needs an Upper Bound

The deeper lesson of the unbounded IN clause is not just about IN clauses. It is about a category of bugs that arise when something that should be bounded — a list, a queue, a string, a request — is allowed to grow without limit. These bugs are invisible during development because development data is always bounded. They emerge in production as the system's actual usage patterns reveal themselves.

Any time your code builds a list that is then passed to the database — or to any external system — you must ask: what is the maximum size this list can reach? What happens to the system if this list contains 1,000 items? What about 10,000? What about 1,000,000? If the answer to any of those questions is "the system breaks," you need an upper bound enforced in code, not as an assumption.

This is a general principle of defensive systems engineering: **never pass an unbounded collection to a subsystem that was not designed to handle infinite scale**. Databases, APIs, caches, message queues — all of them have practical limits on the size of inputs they can handle efficiently. Your job as an engineer is to know those limits and ensure that your code can never exceed them, even in the worst case.
