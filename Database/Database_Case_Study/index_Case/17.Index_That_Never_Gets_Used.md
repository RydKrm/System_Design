# The Index That Never Gets Used

### A PostgreSQL Performance Case Study — Explained for Beginners

---

## Introduction: A Trap That Fools Even Experienced Developers

There is a deeply satisfying moment when a developer creates an index on a slow column, reruns the query, and watches the response time drop from five seconds to fifty milliseconds. The index worked. Problem solved.

But there is a far more frustrating — and far more common — experience: you create the index, you rerun the query, and absolutely nothing changes. The query is still slow. You check the table. The index is there. You can see it with your own eyes. And yet the database is not using it.

This is the case study of that experience. It is not about a missing index. It is about an index that exists in your database, visible in your schema, consuming disk space — and being completely ignored by the query planner every single time a query runs. Understanding why this happens requires understanding how PostgreSQL decides to use an index in the first place, and that decision is far more nuanced than most developers initially expect.

---

## Chapter 1: The Query Planner — The Brain Behind Every Query

Before we can understand why an index gets ignored, we need to understand who is doing the ignoring. When you send a SQL query to PostgreSQL, it does not immediately start fetching data. It first hands your query to something called the **Query Planner** (also called the Query Optimizer).

The Query Planner's job is to figure out the most efficient way to retrieve the data you asked for. It considers every available path — should it scan the entire table? Should it use this index? That index? Should it join tables in a different order? — and it estimates the **cost** of each option. The cost is measured in an abstract unit that represents a combination of CPU work, memory usage, and disk I/O. Once the planner has estimated the cost of all viable strategies, it picks the cheapest one and executes it.

The critical word here is **estimates**. The query planner does not run each strategy and time it. It uses statistical models and metadata about your data — how many rows are in the table, how spread out the values are, what percentage of rows match a given condition — to predict which strategy will be fastest. These statistics are stored in a system catalog called `pg_statistic`, and they are updated by a process called `ANALYZE`.

This is the foundation of every problem in this case study: the query planner's decision is only as good as the information it has. Give it wrong information, and it makes wrong decisions. Give it a situation where the index genuinely is not helpful, and it correctly chooses to ignore it.

```
Your SQL Query
      │
      ▼
┌─────────────────────────────────────────────┐
│              Query Planner                  │
│                                             │
│  Option A: Sequential Scan                  │
│    Estimated cost: 1,200                    │
│                                             │
│  Option B: Index Scan on idx_status         │
│    Estimated cost: 45,800  ← higher!        │
│                                             │
│  Decision: Choose Option A (Sequential Scan)│
└─────────────────────────────────────────────┘
      │
      ▼
Executes Sequential Scan — ignores the index
even though the index EXISTS on the table
```

The planner chose the sequential scan. Not because it made a mistake, but because based on its information, the index scan was estimated to be MORE expensive. Whether that estimation was correct is a separate question — and that is exactly what this case study explores.

## Chapter 2: Cause One — Low Selectivity (The Most Common Culprit)

The single most common reason an index goes unused is called **low selectivity**. To understand selectivity, we need to think about what makes an index useful.

An index is valuable when it helps the database narrow down a large table to a small set of rows quickly. If you have a `users` table with ten million rows, and you query by `email`, an index on `email` is enormously useful — it immediately jumps to the single matching row out of ten million. That index has **high selectivity** because the values in that column are highly unique, and any given value matches a very small fraction of total rows.

Now consider a column called `is_active`. This is a boolean — it can only ever be `true` or `false`. In most applications, the vast majority of users are active. Let us say 98% of your ten million users have `is_active = true`, leaving only 200,000 with `is_active = false`.

```sql
SELECT * FROM users WHERE is_active = true;
```

When this query runs, PostgreSQL considers using the index on `is_active`. But then it estimates: _"The condition `is_active = true` matches approximately 9,800,000 out of 10,000,000 rows."_ That is 98% of the table. Now the planner faces a stark reality — if it uses the index, it will have to visit the index structure, find 9.8 million index entries, and then fetch 9.8 million rows from the actual table heap on disk. Each one of those row fetches is a separate disk I/O operation, jumping around randomly to different physical locations on disk.

Compare that to a sequential scan, which reads the entire table in one continuous sweep from start to finish, which is extremely efficient for large numbers of rows because sequential disk reads are much faster than random reads. When the planner does the math, the sequential scan wins — not because the index is broken, but because for 98% of a table, it genuinely is faster to just read everything sequentially.

```
Selectivity Spectrum:

  email column (10M rows, all unique values)
  ┌────────────────────────────────────┐
  │  WHERE email = 'alice@example.com' │
  │  Matches: 1 out of 10,000,000 rows │
  │  Selectivity: 0.00001%             │
  │  Index: ALWAYS USED ✓              │
  └────────────────────────────────────┘

  is_active column (10M rows, 98% = true)
  ┌─────────────────────────────────────────────┐
  │  WHERE is_active = true                     │
  │  Matches: 9,800,000 out of 10,000,000 rows  │
  │  Selectivity: 98%                           │
  │  Index: NEVER USED — seq scan is cheaper ✗  │
  └─────────────────────────────────────────────┘

  status column (10M rows, 5 distinct values, even spread)
  ┌─────────────────────────────────────────────┐
  │  WHERE status = 'pending'                   │
  │  Matches: ~2,000,000 out of 10,000,000 rows │
  │  Selectivity: 20%                           │
  │  Index: Maybe — planner will calculate      │
  └─────────────────────────────────────────────┘
```

The lesson here is not that you created a bad index. It is that the index is being correctly ignored. The solution for this situation is a **partial index**, which we will cover in a dedicated chapter later.

## Chapter 3: Cause Two — Stale Statistics (The Silent Liar)

Imagine you handed someone a map of a city from the year 2005 and asked them to navigate using it in 2025. The streets might look familiar, but entire new neighborhoods have been built, roads have been rerouted, and the map is fundamentally lying about current reality. The query planner faces this exact problem when statistics are stale.

As established in Chapter 1, the query planner relies on statistics about your data stored in `pg_statistic`. These statistics include things like: how many rows are in this table? What fraction of rows have a particular value in a given column? How spread out are the values?

These statistics are not updated automatically in real time. They are updated by a process called `ANALYZE`, which can be run manually or automatically by a background process called **autovacuum**. The problem arises when your data changes significantly faster than `ANALYZE` runs.

Consider this scenario: you have a `logs` table that was created last week and had 1,000 rows when `ANALYZE` last ran. Since then, your application has been busy, and the table now has 50 million rows. The planner still believes this table has roughly 1,000 rows. It looks at your query, thinks _"this is a tiny table, sequential scan is trivially cheap"_, and ignores your index entirely. Meanwhile, the actual sequential scan takes forty-five seconds because there are fifty million rows — not one thousand.

```
Reality vs. Planner's Belief (Stale Statistics):

┌──────────────────────────┬────────────────────────────┐
│ What the Planner Believes│ What Actually Exists       │
├──────────────────────────┼────────────────────────────┤
│ Table rows:  ~1,000      │ Table rows:  50,000,000    │
│ Seq scan cost: trivial   │ Seq scan cost: 45 seconds  │
│ Index scan: unnecessary  │ Index scan: 2 milliseconds │
└──────────────────────────┴────────────────────────────┘

The planner makes a "rational" decision based on wrong data.
Running ANALYZE updates the statistics and corrects the plan.
```

The fix is straightforward:

```sql
-- Update statistics for a specific table
ANALYZE orders;

-- Update statistics for the entire database
ANALYZE;

-- See when a table was last analyzed
SELECT relname, last_analyze, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

After `ANALYZE` runs, the planner has accurate row count and distribution data, and it re-evaluates its strategy with correct information. In most cases where stale statistics were the cause, the index immediately starts being used.

It is also worth tuning autovacuum's `analyze` thresholds for large, rapidly growing tables — by default, autovacuum triggers `ANALYZE` after 20% of the table's rows have changed, which means for a 50-million-row table, 10 million row changes need to happen before stats are refreshed. For fast-growing tables, you should lower this threshold per-table.

## Chapter 4: Cause Three — The Implicit Type Cast

This cause is subtler and often the hardest to notice because the SQL looks perfectly correct to a human reading it. An **implicit type cast** occurs when the data type of the value in your `WHERE` clause does not exactly match the data type of the column being compared — and PostgreSQL silently converts one to match the other.

Consider a table where the `user_id` column is defined as `INTEGER`, but somewhere in your application, the value being passed is a `VARCHAR` (text). Your query ends up looking like this internally:

```sql
-- What you wrote (looks fine):
SELECT * FROM orders WHERE user_id = '123';

-- What PostgreSQL actually evaluates (implicit cast):
SELECT * FROM orders WHERE CAST(user_id AS VARCHAR) = '123';
-- or equivalently:
SELECT * FROM orders WHERE user_id::text = '123';
```

When PostgreSQL needs to apply a function or cast to the **column itself** in order to make the comparison work, the index on that column becomes completely useless. The index is built on the raw values of `user_id` as integers. It has no knowledge of what those values look like after being cast to text. To use a function or cast on the column in a `WHERE` clause is to effectively ask a question that the index was never built to answer.

A more realistic and equally dangerous version of this problem involves timestamps:

```sql
-- This index CANNOT be used — function applied to the column:
SELECT * FROM events WHERE DATE(created_at) = '2024-01-15';

-- This index CAN be used — the column itself is untouched:
SELECT * FROM events
WHERE created_at >= '2024-01-15 00:00:00'
  AND created_at <  '2024-01-16 00:00:00';
```

In the first query, `DATE(created_at)` wraps the `created_at` column in a function. The index on `created_at` stores raw timestamp values, not their date-truncated equivalents, so it cannot be used. In the second query, `created_at` is compared directly against constant values — the index can serve this query perfectly.

```
Index Usability by Query Pattern:

  Index on: orders.user_id (INTEGER)
  ┌─────────────────────────────────────────────────────┐
  │  WHERE user_id = 123           → Index USED ✓       │
  │  WHERE user_id = '123'         → Implicit cast, ✗   │
  │  WHERE user_id::text = '123'   → Explicit cast, ✗   │
  │  WHERE user_id IN (1,2,3)      → Index USED ✓       │
  └─────────────────────────────────────────────────────┘

  Index on: events.created_at (TIMESTAMPTZ)
  ┌─────────────────────────────────────────────────────┐
  │  WHERE created_at = '2024-01-15 10:00:00' → USED ✓  │
  │  WHERE DATE(created_at) = '2024-01-15'    → NOT ✗   │
  │  WHERE EXTRACT(YEAR FROM created_at) = 24 → NOT ✗   │
  │  WHERE created_at >= '2024-01-15'         → USED ✓  │
  └─────────────────────────────────────────────────────┘
```

The rule is absolute: **never apply a function or cast to the column side of a comparison if you want the index to be usable.** If you need to query by a derived value, create a **function-based index** (called an expression index in PostgreSQL) on that exact expression:

```sql
-- Create an index on the expression itself:
CREATE INDEX idx_events_date ON events (DATE(created_at));

-- Now this query CAN use the index:
SELECT * FROM events WHERE DATE(created_at) = '2024-01-15';
```

## Chapter 5: Cause Four — The Table Is Just Too Small

This is the cause that surprises developers the most, because it feels counterintuitive. You have an index. You have a query that perfectly matches the indexed column. And the planner still ignores it.

If the table has fewer than roughly 1,000 rows (and often even for tables with tens of thousands of rows, depending on row size and configuration), PostgreSQL will almost always choose a sequential scan — and it will be **correct to do so**.

Here is the reasoning. An index scan requires the database to first visit the index structure (which lives in separate disk pages), retrieve the matching row identifiers, and then fetch each row from the actual table pages using those identifiers. Each of those table fetches is a random I/O operation, jumping to a potentially different page on disk.

A sequential scan, by contrast, simply reads the table from beginning to end in one uninterrupted sweep. For a small table that fits entirely in memory (or even just a few disk pages), that sweep takes almost no time at all. The overhead of navigating the index structure, looking up row pointers, and performing random page fetches would actually be slower than just reading the whole tiny table.

This is not a bug. This is the planner being intelligent. If you are testing on a database with small data volumes — as most development environments are — you may never see your indexes get used, even if they are perfectly designed. Only when the table grows to a meaningful size does the index's advantage over a sequential scan become real.

The practical takeaway is this: always test query plans with **production-representative data volumes**. A query that runs in 2ms on a 500-row development table with a sequential scan may run in 45 seconds on a 50-million-row production table doing the same sequential scan.

## Chapter 6: Cause Five — `random_page_cost` Set Wrong for Your Storage

This cause operates at the configuration level, not the data level. It involves a PostgreSQL setting called `random_page_cost`, and understanding it requires a brief understanding of how disk I/O works differently across storage types.

Reading data from a hard disk drive (HDD) involves a physical read head moving across spinning magnetic platters. When you need data scattered in random locations on the disk, that read head must physically move between positions — a process called "seeking." This mechanical movement takes measurable time (milliseconds). Sequential reads, by contrast, let the read head stay in one place while the platter spins, which is much faster.

The speed difference between random reads and sequential reads on a traditional HDD is significant — often 10x to 100x. PostgreSQL's planner knows about this. The `random_page_cost` setting tells the planner how expensive a random disk page fetch is, relative to a sequential one. The default value is `4.0`, meaning the planner assumes random reads are four times more expensive than sequential ones.

But modern servers often use **NVMe SSDs** (Non-Volatile Memory Express Solid State Drives). These have no moving parts. A random read and a sequential read on an NVMe SSD take almost the same amount of time — the difference is often less than 1.1x, not 4x.

If your server has NVMe storage but `random_page_cost` is still set to `4.0`, the planner systematically overestimates the cost of index scans (which require random I/O) and underestimates the relative cost of sequential scans. This can cause it to choose sequential scans when index scans would actually be significantly faster on your hardware.

```
random_page_cost Impact on Index vs Seq Scan Decision:

  Storage: NVMe SSD (actual random/seq ratio ≈ 1.1x)

  ┌──────────────────────────────────────────────────────┐
  │ random_page_cost = 4.0 (default, tuned for HDD)     │
  │                                                      │
  │  Index Scan estimated cost:  4,200  (inflated)      │
  │  Sequential Scan estimated cost: 3,800               │
  │  Planner chooses: Sequential Scan ✗                  │
  │  Actual index scan time: 12ms                        │
  │  Actual seq scan time:   890ms                       │
  └──────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────┐
  │ random_page_cost = 1.1 (tuned for NVMe SSD)         │
  │                                                      │
  │  Index Scan estimated cost:  1,155 (accurate)       │
  │  Sequential Scan estimated cost: 3,800               │
  │  Planner chooses: Index Scan ✓                       │
  │  Actual index scan time: 12ms                        │
  └──────────────────────────────────────────────────────┘
```

The fix is to adjust the setting in `postgresql.conf` or at the session/database level:

```sql
-- For NVMe SSD storage (set in postgresql.conf):
random_page_cost = 1.1

-- Or set per-session for testing:
SET random_page_cost = 1.1;

-- Or set for a specific database:
ALTER DATABASE mydb SET random_page_cost = 1.1;
```

If you are running PostgreSQL on a cloud provider (AWS RDS, Google Cloud SQL, Supabase, Neon), your underlying storage is almost certainly SSD-based, and you should set `random_page_cost` between `1.0` and `1.5`. The default of `4.0` is a holdover from the era of spinning disks.

## Chapter 7: How to Diagnose — `EXPLAIN ANALYZE` Is Your Microscope

Every time you are investigating a query performance issue in PostgreSQL, there is one tool you must use before drawing any conclusions: `EXPLAIN ANALYZE`. This command does not just return a query plan — it actually runs the query and gives you both the planner's predictions and the actual measured results.

```sql
-- Basic plan (estimates only, query does NOT run):
EXPLAIN SELECT * FROM orders WHERE user_id = 123;

-- Full analysis (query RUNS, you see actual times and row counts):
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123;

-- The most informative version — includes buffers and timing:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE user_id = 123;
```

Learning to read `EXPLAIN ANALYZE` output is one of the most valuable skills a backend developer working with PostgreSQL can develop. The output looks like this:

```
-- Without index (Sequential Scan):
Seq Scan on orders  (cost=0.00..42580.00 rows=8000000 width=72)
                    (actual time=0.021..38420.551 rows=8000000 loops=1)
  Filter: (user_id = 123)
  Rows Removed by Filter: 7999999
Planning Time: 0.3 ms
Execution Time: 38421.2 ms    ← 38 seconds!

-- With index (Index Scan):
Index Scan using idx_orders_user_id on orders
                    (cost=0.56..8.58 rows=3 width=72)
                    (actual time=0.043..0.051 rows=2 loops=1)
  Index Cond: (user_id = 123)
Planning Time: 0.4 ms
Execution Time: 0.1 ms        ← 0.1 milliseconds
```

The key things to look for are: the word **"Seq Scan"** (tells you the planner chose a sequential scan), **"Index Scan"** or **"Bitmap Index Scan"** (tells you the index was used), the **"Rows Removed by Filter"** line (a very large number here on a Seq Scan is a red flag), and the gap between **estimated** and **actual** rows (a large gap indicates stale statistics).

You can also check which indexes are actually being used across your entire database through system views:

```sql
-- Check index usage statistics:
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,       -- how many times this index has been used
    idx_tup_read,   -- rows read via this index
    idx_tup_fetch   -- live rows fetched
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;  -- indexes at the top have NEVER been used
```

Any index with `idx_scan = 0` that has been in your database for a meaningful period of time is a candidate for investigation. It is either not needed, or something is preventing it from being used.

## Chapter 8: The Solution for Low Selectivity — Partial Indexes

We established in Chapter 2 that a regular index on `is_active` will not be used for `WHERE is_active = true` because 98% of rows match. But what if you need to query active users frequently? Is there no hope?

There is. PostgreSQL supports something called a **partial index** — an index that only includes rows matching a specific condition. Instead of indexing all ten million rows, you index only the subset of rows that matter for your queries.

In the `is_active` example, the far more interesting query in most applications is not "give me all active users" — it is the queries that filter on _other_ things within the active user population. But if you do need to query inactive users specifically (the 2% minority), a partial index on just those rows is extremely efficient:

```sql
-- Partial index: only indexes rows where is_active = false
-- This covers only 200,000 rows instead of 10,000,000
CREATE INDEX idx_users_inactive ON users(id)
WHERE is_active = false;

-- This query now uses the partial index (touches only 200,000 rows):
SELECT * FROM users WHERE is_active = false;

-- This query ignores the partial index (correctly):
SELECT * FROM users WHERE is_active = true;
-- (PostgreSQL still seq scans this — 9.8M rows, index won't help)
```

A more practical example involves a task queue — a `jobs` table where the vast majority of jobs have `status = 'completed'`, but your application constantly queries for `status = 'pending'` to find work to process:

```sql
-- Only index the pending jobs (a tiny minority):
CREATE INDEX idx_jobs_pending ON jobs(created_at)
WHERE status = 'pending';

-- This query is now blazing fast because it only indexes
-- the small fraction of rows that are pending:
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY created_at ASC
LIMIT 10;
```

A partial index is smaller (uses less disk space and memory), is faster to maintain on insert/update/delete, and has much higher selectivity than the full-column index would. It is the correct solution for any boolean or low-cardinality column where you only care about one specific value.

## Chapter 9: The Complete Diagnostic Flowchart

When you encounter an index that is not being used, work through this sequence methodically rather than guessing:

```
START: Index exists but query uses Seq Scan
              │
              ▼
    Run EXPLAIN ANALYZE on the query
              │
              ├──► Are estimated rows wildly off from actual rows?
              │           │
              │           YES → Run ANALYZE on the table
              │                 Re-run EXPLAIN ANALYZE
              │
              ├──► What is the WHERE clause selectivity?
              │           │
              │           HIGH (>10-20% of rows match) → Normal behavior
              │           Consider a partial index for the minority value
              │
              ├──► Is there a function applied to the column?
              │           │

              │           │

              │                 OR create expression index on DATE(col)

```

## Chapter 10: The Lesson That Changes How You Think

Most developers approach indexing as a binary activity: either an index exists or it does not. If it exists, the problem is solved. This case study should fundamentally change that mental model.

Creating an index is not a solution. It is a **hypothesis** — a hypothesis that says _"I believe the query planner will find this index useful for my query pattern."_ And like any hypothesis, it must be verified. The verification tool is `EXPLAIN ANALYZE`. Always run it. Never assume.

The query planner is a sophisticated piece of software with many factors influencing its decisions: the freshness of statistics, the distribution of values in a column, the actual selectivity of the condition, the physical characteristics of your storage hardware, and the size of the table. Ignoring any of these factors leads to silent index failures — indexes that sit in your database consuming space, providing false confidence, and doing nothing to help query performance.

The mature engineering practice is to treat every index as a living decision that must be periodically reviewed. Use `pg_stat_user_indexes` to identify indexes with zero or near-zero `idx_scan` values. Use `EXPLAIN ANALYZE` to verify that new indexes actually change query plans. Tune `random_page_cost` to match your hardware. Run `ANALYZE` after bulk data loads. Create partial indexes for low-selectivity columns.

An index that exists but is never used is not a performance optimization — it is a maintenance burden. It slows down inserts and updates (because every write must update every index on the table), consumes disk space and memory in the shared buffer pool, and gives developers a false sense of security. A thoughtfully verified, actively-used index is a completely different thing — it is one of the most powerful tools in a database engineer's toolkit.

```
Summary of All Causes and Their Fixes:

┌─────────────────────────┬──────────────────────────────────────────┐
│ Cause                   │ Fix                                      │
├─────────────────────────┼──────────────────────────────────────────┤
│ Low selectivity         │ Partial index on the minority value      │
│ (98% rows match)        │ e.g. WHERE is_active = false             │
├─────────────────────────┼──────────────────────────────────────────┤
│ Stale statistics        │ Run ANALYZE on the table                 │
│ (planner sees 1K rows,  │ Tune autovacuum thresholds for large     │
│  reality is 50M)        │ fast-growing tables                      │
├─────────────────────────┼──────────────────────────────────────────┤
│ Implicit type cast      │ Ensure query value type matches column   │
│ (col::text = '123')     │ type, OR use expression index on         │
│                         │ the function/cast itself                 │
├─────────────────────────┼──────────────────────────────────────────┤
│ Table too small         │ Not a problem — seq scan IS faster here  │
│ (<1,000-10,000 rows)    │ Validate with production data volumes    │
├─────────────────────────┼──────────────────────────────────────────┤

```

## Conclusion: The Senior Engineer's Discipline

If the previous case study taught you _"always create an index on foreign key columns,"_ then this case study teaches you the follow-up discipline: **always verify that the index you created is actually doing something.**

The database will not tell you when an index is being ignored. It will not send you a warning message. It will not mark the index as unused in your schema viewer. It will simply continue running sequential scans while your index silently accumulates dust. The only way to know is to look — with `EXPLAIN ANALYZE`, with `pg_stat_user_indexes`, and with an understanding of why a planner might rationally choose to ignore an index even when one exists.

Every index you create is a trade-off: faster reads in exchange for slower writes and more storage. If the index is never used, you pay the write-performance and storage cost with zero benefit. That is the worst possible trade. The discipline of verifying index usage is not optional — it is what separates a developer who has added indexes from an engineer who has actually improved database performance.
