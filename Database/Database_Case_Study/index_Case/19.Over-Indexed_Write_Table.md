# The Over-Indexed Write Table

### A PostgreSQL Performance Case Study — Explained for Beginners

---

## Introduction: Good Intentions, Compounding Consequences

There is a particular flavor of database performance problem that is built not from negligence but from an abundance of caution — from engineers doing what feels responsible, methodical, and thorough. This case study is about that kind of problem.

Imagine a new feature is being built: a search screen that filters orders by status. A developer adds an index on `status`. A week later, another developer needs to sort orders by `created_at`. They add an index on `created_at`. A month after that, a data analyst asks for a way to quickly query by `customer_id`. Index added. Then someone notices that queries filtering by both `status` and `region` are slow, so a composite index goes in. Then another index for the admin panel. Then one "just in case" the reporting team needs it. Then a few more over the following quarters, each with a perfectly valid reason at the time, each approved and merged without ever revisiting the ones that came before.

Eighteen months later, the `orders` table has fifteen indexes. Nobody remembers why half of them exist. Nobody has ever audited whether any of them are still used. And the on-call engineer is being paged at 2am because write throughput on the orders table has collapsed — INSERTs that used to complete in two milliseconds are now taking forty, and the order processing pipeline is backed up with hundreds of thousands of pending rows that cannot be written fast enough.

This is the over-indexed write table. It is assembled gradually, by well-meaning engineers, one small decision at a time, and it can bring a production system to its knees with the same effectiveness as any more dramatic failure — while leaving far fewer clues about what went wrong.

## Chapter 1: What an Index Costs on Every Write

To understand why too many indexes destroy write performance, you need to build a precise understanding of what PostgreSQL must physically do every single time a row is inserted, updated, or deleted on a table that has indexes.

When you insert a row into a table with no indexes, PostgreSQL does one thing: it writes the new row to the appropriate page in the table heap. This is a single, sequential write operation. It is fast, it is cheap, and it scales linearly with the number of rows being inserted.

When that same table has indexes, the story changes dramatically. For every index that exists on the table, PostgreSQL must also locate the correct position in that index's B-Tree structure for the new row's values, and insert a new index entry there. If the B-Tree page where the entry should go is already full, PostgreSQL must perform a **page split** — it allocates a new page, moves half the existing entries to the new page, and then inserts the new entry. Page splits are expensive and generate substantial write-ahead log (WAL) volume.

This means that the cost of a single `INSERT` is not a flat cost. It is `1 + N` operations, where `N` is the number of indexes on the table. With fifteen indexes, every single INSERT requires sixteen write operations instead of one — and each of those additional fifteen operations involves navigating a B-Tree, potentially splitting pages, and updating the WAL to make the operation durable. The cost is not additive in a simple arithmetic sense; it is additive in the sense of real disk I/O, real CPU cycles, real lock acquisitions, and real WAL bytes generated.

```
Cost of INSERT on orders table:

  ┌────────────────────────────────────────────────────────────────┐
  │  INSERT INTO orders (id, status, created_at, customer_id, ...) │
  │  VALUES (...)                                                  │
  └─────────────────────────────────────┬──────────────────────────┘
                                        │
                    ┌───────────────────▼────────────────────────┐
                    │  Mandatory: Write row to table heap        │
                    │  Cost: 1 write operation                   │
                    └───────────────────┬────────────────────────┘
                                        │
            ┌───────────────────────────▼─────────────────────────────┐
            │  For EACH of the 15 indexes, PostgreSQL must:           │
            │                                                         │
            │  idx_orders_status          → B-Tree update + WAL      │
            │  idx_orders_created_at      → B-Tree update + WAL      │
            │  idx_orders_customer_id     → B-Tree update + WAL      │
            │  idx_orders_region          → B-Tree update + WAL      │
            │  idx_orders_status_region   → B-Tree update + WAL      │
            │  idx_orders_amount          → B-Tree update + WAL      │
            │  idx_orders_updated_at      → B-Tree update + WAL      │
            │  idx_orders_payment_method  → B-Tree update + WAL      │
            │  ... (8 more indexes) ...   → B-Tree update + WAL      │
            │                                                         │
            │  15 additional write operations per INSERT              │
            └─────────────────────────────────────────────────────────┘

  1 index:   1 heap write + 1 index write  = 2 total operations
  15 indexes: 1 heap write + 15 index writes = 16 total operations

  The table with 15 indexes does 8× more work per INSERT.
  At 10,000 inserts/second: 160,000 write operations per second
  vs. 20,000 with just 1 index — for the exact same business logic.
```

This cost exists for updates too, but updates are especially punishing because they may require changes to multiple indexes even when only one column changes. If you update `status` on an orders row, PostgreSQL must update every index that includes the `status` column. If you update `updated_at`, every index covering `updated_at` must be maintained. The more indexes you have, the more likely any given update is to touch multiple ones.

Deletes are equally affected — every deleted row must have its entry removed from every index on the table.

## Chapter 2: The WAL — The Hidden Tax Collector

Beyond the direct cost of updating B-Tree structures, there is a second layer of write overhead that becomes alarming at scale: the **Write-Ahead Log**, universally known as **WAL**.

WAL is PostgreSQL's durability mechanism. Before any data is considered committed — before it is safe to tell the client "yes, your INSERT succeeded" — every change must be written to the WAL first. The WAL is an append-only log file that records exactly what changed: which bytes on which pages were modified. If PostgreSQL crashes, it replays the WAL from the last checkpoint to recover to a consistent state. Without WAL, PostgreSQL could not guarantee durability.

Every index maintenance operation — every B-Tree update, every page split, every new index entry — generates WAL records. With fifteen indexes, a single INSERT generates fifteen times more WAL records than the same INSERT would with one index. At high write throughput, this produces an enormous volume of WAL bytes per second.

WAL volume has cascading consequences across the entire PostgreSQL infrastructure. If you are running streaming replication — which any production system with a standby replica will be doing — every byte of WAL must be transmitted to the replica and applied there. An over-indexed write table can saturate the replication channel, causing **replication lag** to grow: the replica falls behind the primary, and any queries running on the replica are reading increasingly stale data.

WAL also directly impacts **checkpoint** frequency. PostgreSQL periodically flushes all dirty (modified) pages from memory to disk during a process called a checkpoint. If WAL volume is very high, checkpoints happen more frequently, causing periodic spikes in disk I/O. Frequent checkpoints can cause visible "stuttering" in write latency — queries that usually complete in two milliseconds occasionally spike to fifty milliseconds when they happen to coincide with a checkpoint flush.

```
WAL Volume and Its Downstream Effects (15 indexes vs. 3 indexes):

                       3 indexes          15 indexes
  ─────────────────────────────────────────────────────────
  WAL per INSERT:      ~4 KB              ~20 KB
  WAL/sec at 5K ins:   ~20 MB/s           ~100 MB/s
  Replication lag:     Near-zero          Growing (seconds)
  Checkpoint freq:     Every 5 min        Every 1 min
  Write latency:       2 ms avg           40 ms avg + spikes
  Disk I/O:            Moderate           High (near saturation)
  ─────────────────────────────────────────────────────────

  Every additional index is also a replication tax,
  a checkpoint tax, and a disk I/O tax on every write.
```

When a team notices that WAL generation is "much higher than expected" — as described in the symptoms of this case study — they are often attributing it to increased traffic or data volume. In reality, the driver is frequently index count, because WAL volume grows not just with row count but with index count multiplied by row count. This is the hidden tax collector: invisible in development, manageable at moderate traffic, disastrous at scale.

## Chapter 3: How This Happens — The Psychology of Index Accumulation

Understanding the technical mechanism of why over-indexing is harmful is only half the picture. The other half is understanding why it happens so reliably in real engineering teams, because it does not happen through carelessness — it happens through a series of individually rational decisions that aggregate into an irrational outcome.

The first mechanism is **reactive indexing**. A developer notices a slow query. They identify the missing index. They add it. The query speeds up. This is correct behavior — exactly what a responsible developer should do. The problem is that this process has no corresponding cleanup step. The index was added to solve a specific query at a specific moment in time. But queries change. Features get removed. The admin screen that required a particular filter is redesigned and that filter is gone. The old index remains, silently consuming write overhead, because no mechanism exists to notice that the query it served no longer exists.

The second mechanism is **index hoarding as insurance**. Developers sometimes add indexes that no current query requires, reasoning that "we might need this someday" or "better to have it and not need it." This thinking treats indexes like documentation or code comments — harmless artifacts that do not cost anything to have around. As this case study makes clear, that intuition is completely wrong. An index that is never read still imposes its full cost on every write. There is no such thing as a "free" index on a write-heavy table.

The third mechanism is **absence of ownership**. In a team environment, indexes are often added by whoever is working on a given feature at a given time, with no central review or audit process. Three months later, no individual engineer has a complete mental model of why all fifteen indexes exist. Asking "can we delete this one?" is unanswerable without research, and under deadline pressure, the safe default is always "leave it — it might be there for a reason." The index persists through inertia alone.

```
The Lifecycle of an Accidental Index Collection:

  Month 0:   Table created. 2 indexes (primary key + one query).
             Write throughput: excellent.

  Month 3:   Feature added. 2 new indexes.
             Total: 4 indexes. Write throughput: excellent.

  Month 6:   Analytics needed. 3 indexes added.
             Total: 7 indexes. Write throughput: good.

  Month 9:   Feature redesign. Old feature removed.
             2 old indexes now serve zero queries.
             New feature adds 3 more indexes.
             Total: 10 indexes. Write throughput: acceptable.

  Month 12:  "Just in case" indexes added by 3 different engineers.
             Total: 13 indexes. Write throughput: degrading.

  Month 14:  Peak traffic period. System struggles.
             Total: 15 indexes. Write throughput: collapsing.

  Month 15:  2am incident. Engineer paged.
             Root cause investigation begins.
             Finds 7 indexes with idx_scan = 0.
             Team realizes: nobody knew about these.
```

The lesson here is not that individual engineers made wrong decisions. It is that the absence of a process — for reviewing new indexes before they are added, and for auditing existing indexes regularly — made the accumulation of harm inevitable. Processes that only add, and never remove, will always drift toward excess over time.

## Chapter 4: Reading the Evidence — `pg_stat_user_indexes`

When investigating write performance problems on a table suspected of over-indexing, the first tool to reach for is `pg_stat_user_indexes`. This system view maintains cumulative statistics about how often each index has been used since the last statistics reset (or since the database was started, if statistics have never been reset).

The most important column for this investigation is `idx_scan` — the number of times the query planner has chosen to use this index to answer a query. An index with `idx_scan = 0` after weeks or months of production traffic is an index that has never been used. An index with `idx_scan = 12` over six months is an index used twice a month — which almost certainly does not justify the cost it imposes on every INSERT.

```sql
-- Full audit of indexes on a specific table:
SELECT
    indexrelname                              AS index_name,
    idx_scan                                  AS times_used,
    idx_tup_read                              AS tuples_read_via_index,
    idx_tup_fetch                             AS live_tuples_fetched,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY idx_scan ASC;  -- unused indexes float to the top

-- Example output showing the problem clearly:
-- index_name                    | times_used | index_size
-- ──────────────────────────────────────────────────────
-- idx_orders_payment_method     |          0 | 892 MB    ← DROP THIS
-- idx_orders_region_amount      |          0 | 1.1 GB    ← DROP THIS
-- idx_orders_admin_filter       |          3 | 445 MB    ← Investigate
-- idx_orders_status_region      |         17 | 678 MB    ← Investigate
-- idx_orders_updated_at         |        891 | 234 MB    ← Keep
-- idx_orders_customer_id        |     45,231 | 312 MB    ← Definitely keep
-- idx_orders_status             |    891,002 | 189 MB    ← Core index
-- orders_pkey                   |  3,400,129 | 156 MB    ← Primary key
```

One important caveat about using `idx_scan = 0` as a deletion criterion: you must ensure that the observation window is **representative**. If you check `idx_scan` three days after a statistics reset, an index used only for quarterly reporting will appear completely unused. PostgreSQL statistics can be reset manually with `pg_stat_reset()`, and are also reset when the database is restarted. Before drawing conclusions from `idx_scan = 0`, verify when statistics were last reset:

```sql
-- Check when statistics collection started:
SELECT stats_reset
FROM pg_stat_bgwriter;

-- Check per-table statistics reset time:
SELECT relname, stats_reset
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

If statistics have been accumulating for at least three months of representative production traffic — covering peak periods, month-end processing, any regular batch jobs — then `idx_scan = 0` is a reliable signal that the index is genuinely unused and can be safely dropped.

## Chapter 5: The Correct Way to Drop Indexes — Safely and Concurrently

Once the audit has identified indexes that are candidates for removal, the mechanics of dropping them safely are straightforward but carry one critical rule: never use plain `DROP INDEX` on a live production table.

Plain `DROP INDEX` acquires an **exclusive lock** on the table for the duration of the operation. Even though dropping an index is typically fast (it is mostly a metadata operation), any exclusive lock on a high-write table causes all concurrent INSERTs, UPDATEs, and DELETEs to queue behind it. The same principle that makes `REINDEX` dangerous applies here.

PostgreSQL provides `DROP INDEX CONCURRENTLY` for this reason. The concurrent variant marks the index as invalid (preventing the planner from using it) while allowing writes to continue, then gradually removes the index structure in the background without taking an exclusive lock.

```sql
-- NEVER do this on a live production table with ongoing writes:
DROP INDEX idx_orders_payment_method;
-- ↑ Takes exclusive lock. All writes to orders table STOP
--   until this completes. Even for a "fast" drop, this can
--   queue thousands of writes during a high-traffic period.


-- The correct approach — always use CONCURRENTLY in production:
DROP INDEX CONCURRENTLY idx_orders_payment_method;
-- ↑ Safe. Ongoing writes continue uninterrupted.
--   Index is gradually removed in the background.
--   Slightly slower than plain DROP INDEX, but production-safe.


-- If you have multiple indexes to drop, do them one at a time.
-- DROP INDEX CONCURRENTLY cannot run inside a transaction block:
-- BEGIN; DROP INDEX CONCURRENTLY ...; COMMIT;  ← This will FAIL.
-- Run each DROP INDEX CONCURRENTLY as a standalone statement.
```

A sensible precautionary approach — especially if there is any uncertainty about whether a given index might be needed — is to go through an intermediate step before dropping permanently. PostgreSQL allows you to mark an index as **invalid** without dropping it, by using a `REINDEX CONCURRENTLY` that is then intentionally not cleaned up, or more practically, by simply monitoring `idx_scan` for one additional week after deciding to drop. If the monitoring reveals that a query suddenly started using the index after all, the decision to drop can be revisited before it becomes irreversible.

## Chapter 6: Establishing a Process — Index Reviews Before Merge

The most effective solution to the over-indexed write table is not the cleanup — it is preventing the accumulation in the first place. This requires treating index creation as a decision that deserves deliberate review, not a reflex response to a slow query.

A mature index review process asks several questions before any new index is merged into production. The first question is: **what specific query does this index serve?** An index without a specific answerable query it is designed to accelerate has no business being created. "Might be useful for analytics" is not an answer. The exact query, the table size, and the expected query frequency are the answer.

The second question is: **is this query's selectivity high enough to benefit from an index?** As the previous case study established, an index on a low-selectivity column (`is_active`, `status` with only three values, any boolean) may never be used by the planner. Creating it adds write overhead with no read benefit.

The third question is: **what is the write rate on this table?** An additional index on a table that receives fifty inserts per day is essentially free. An additional index on a table that receives fifty thousand inserts per second is a meaningful and lasting performance commitment that should be sized and approved accordingly.

The fourth question, and the most commonly skipped: **can an existing index serve this query?** Often, a composite index that already exists on `(status, created_at)` can serve a query that filters on `status` alone, because PostgreSQL can use the leftmost prefix of a composite index. A new single-column index on `status` would be redundant.

```
Index Review Checklist (to be applied before every new index):

  1. Which specific query does this index accelerate?
     Write the exact SQL. If you cannot write it, reconsider.

  2. What is the table's approximate write rate?
     Low (<1K writes/day)   → Low concern.
     Medium (1K–100K/day)   → Moderate concern, justify clearly.
     High (>100K/day)       → High concern, requires strong justification.

  3. What is the selectivity of the indexed column(s)?
     High cardinality (email, UUID, timestamp) → Usually safe.
     Low cardinality (boolean, status, region) → Use partial index
                                                  or reconsider.

  4. Does any existing index already cover this query?
     Check if an existing composite index has a compatible prefix.
     Check pg_stat_user_indexes for a similar index.

  5. What is the plan to remove this index if the query changes?
     Link the index to the feature ticket.
     Set a calendar reminder to audit it after 90 days.
```

The fifth item in that checklist — linking the index to the feature and scheduling a future audit — is the one that actually prevents gradual accumulation. Every index should have a documented reason for existence and a scheduled review. Without this, the accretion of "permanent temporary" indexes is inevitable.

## Chapter 7: Composite Indexes as a Consolidation Strategy

One of the most effective techniques for reducing index count on an over-indexed table is **index consolidation through composite indexes**. A composite index — an index covering multiple columns — can often serve several different queries that would otherwise each require their own single-column index.

The fundamental rule of composite index design is called the **leftmost prefix rule**: a composite index on `(A, B, C)` can serve queries that filter on `A` alone, queries that filter on `A` and `B`, and queries that filter on `A`, `B`, and `C`. It cannot serve queries that filter on `B` alone, `C` alone, or `B` and `C` without `A`.

```sql
-- Instead of three separate indexes:
CREATE INDEX idx_orders_status     ON orders(status);
CREATE INDEX idx_orders_customer   ON orders(customer_id);
CREATE INDEX idx_orders_status_cust ON orders(status, customer_id);

-- Consider whether a single composite index can replace two:
-- If most queries filter by customer_id AND status together,
-- and some filter by customer_id alone, but few filter by
-- status alone — one index can serve all of them:
CREATE INDEX idx_orders_customer_status ON orders(customer_id, status);
-- This serves:
--   WHERE customer_id = 123             → uses leftmost prefix
--   WHERE customer_id = 123 AND status = 'pending' → full index
--   ORDER BY customer_id, status        → index scan
-- This does NOT serve:
--   WHERE status = 'pending'            → no leftmost prefix
```

Consolidation is not always possible — some queries genuinely require separate access patterns that cannot be served by any single composite index. But a careful audit of which queries are actually being run and in what combinations frequently reveals opportunities to replace three single-column indexes with one well-designed composite index. This can dramatically reduce index count — and therefore write overhead — while preserving or improving read performance for the queries that matter.

## Chapter 8: Recognizing the Symptoms Before the Crisis

A recurring theme across this entire series is that the most dangerous database problems are the ones that accumulate slowly and silently. Write overhead from excessive indexes follows this pattern exactly. The symptoms appear gradually, and each individual symptom is ambiguous enough that it can be misattributed to other causes — increased traffic, slower hardware, application bugs — before the true cause is identified.

The characteristic symptom pattern of an over-indexed write table, in roughly the order they become visible, proceeds as follows. First, average write latency begins to creep upward — from two milliseconds to five, over a period of weeks. This is easy to miss in monitoring unless you are tracking percentiles carefully, because the 50th percentile (median) may look fine while the 95th percentile is already elevated.

Second, WAL generation rate — visible in monitoring dashboards that track the size of WAL files written per unit of time, or through `pg_stat_bgwriter` — rises faster than traffic volume would explain. If traffic grew by 20% but WAL volume grew by 60%, something other than traffic volume is driving the WAL.

Third, replication lag begins to appear on standby replicas. The replica's WAL receiver can no longer keep up with the volume of WAL being generated by the primary. Queries on the replica start returning increasingly stale data.

Fourth, checkpoint warnings start appearing in the PostgreSQL log — `LOG: checkpoint occurring too frequently` or `LOG: checkpoint request 10 seconds after previous checkpoint`. These indicate that the checkpoint completion target is not being met, which means the system is spending too much time flushing dirty pages.

Finally — and this is the stage at which incidents usually occur — the write latency on the high-churn table becomes high enough that application-level timeouts begin firing. Queue depths grow. The pipeline stalls.

```sql
-- Monitoring query: Write latency by table (requires pg_stat_statements):
SELECT
    query,
    calls,
    ROUND(mean_exec_time::numeric, 2)  AS avg_ms,
    ROUND(total_exec_time::numeric, 2) AS total_ms
FROM pg_stat_statements
WHERE query ILIKE '%INSERT INTO orders%'
   OR query ILIKE '%UPDATE orders%'
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Monitoring query: WAL generation rate:
SELECT
    checkpoints_timed                    AS scheduled_checkpoints,
    checkpoints_req                      AS forced_checkpoints,  -- should be low
    buffers_checkpoint / (
        EXTRACT(EPOCH FROM (NOW() - stats_reset)) / 60
    )                                    AS buffers_per_minute,
    stats_reset
FROM pg_stat_bgwriter;
-- High forced_checkpoints is a red flag for excessive WAL volume.

-- Monitoring query: Replication lag (run on primary):
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    (sent_lsn - replay_lsn)             AS lag_bytes,
    replay_lag
FROM pg_stat_replication;
```

Catching these signals at the "write latency creep" stage — the first symptom — allows the problem to be addressed during a planned maintenance window at low cost. Catching it at the "pipeline stalled, incident in progress" stage turns a routine maintenance task into an emergency that carries real business consequences.

## Chapter 9: The Complete Remediation Playbook

When the diagnosis has been confirmed — an over-indexed write table is causing write performance degradation — the remediation follows a clear sequence of steps. The order matters because some steps provide immediate relief while others provide lasting prevention.

The first step is the audit, conducted using `pg_stat_user_indexes` as described in Chapter 4. The goal is to categorize every index on the table into one of three buckets: clearly unused (drop immediately), infrequently used (investigate before deciding), and actively used (keep, no further action).

The second step is dropping the clearly unused indexes using `DROP INDEX CONCURRENTLY`, one at a time, during business hours if write rates are moderate, or during a low-traffic window if the table is under extreme write pressure. Each dropped index provides an immediate, measurable improvement to write throughput — you can observe the latency drop in real time after each DROP completes.

The third step is investigating the infrequently used indexes. This involves identifying which specific application code path generates the query that would use each index. If that code path is still active and meaningful — a weekly report, a monthly billing run — the index should be kept but documented. If the code path no longer exists, the index is a ghost from a removed feature and should be dropped.

The fourth step is index consolidation: reviewing whether any remaining indexes can be replaced by a smaller number of composite indexes that serve the same queries.

The fifth step — and the most important for long-term health — is establishing the index review process described in Chapter 6, so that this situation does not recur.

```
Complete Remediation Sequence:

  Phase 1: Audit (1–2 hours)
  ──────────────────────────────────────────────────────────────
  Run pg_stat_user_indexes audit
  Verify statistics window is representative (3+ months)
  Categorize all indexes: Unused / Infrequent / Active

  Phase 2: Immediate Relief (same day or low-traffic window)
  ──────────────────────────────────────────────────────────────
  DROP INDEX CONCURRENTLY for all idx_scan = 0 indexes
  Observe write latency improvement after each drop
  Monitor WAL generation rate — should drop proportionally

  Phase 3: Investigation and Consolidation (1 week)
  ──────────────────────────────────────────────────────────────
  Identify application code behind infrequent indexes
  Drop indexes for removed features
  Design composite indexes to consolidate remaining ones
  REINDEX CONCURRENTLY any indexes with high bloat ratio

  Phase 4: Prevention (ongoing)
  ──────────────────────────────────────────────────────────────
  Implement index review checklist in PR process
  Schedule quarterly pg_stat_user_indexes audit
  Add write latency and WAL rate to monitoring dashboards
  Document every index with purpose and owning feature
```

## Chapter 10: The Tax Analogy That Changes How You Think

The closing mental model of this case study is the one embedded in the lesson statement: _every index is a tax on every write._

The word "tax" is precise and deliberate. A tax is not a cost you pay only when you use the taxed thing — it is a cost you pay regardless of whether you benefit. A tax on income is paid whether the income was spent wisely or wasted. A tax on an index is paid whether the index is used by a single query or sits idle for its entire existence.

This reframes the entire question of index creation. The question is not "does this index help?" — it is "does this index help enough to justify the tax it imposes on every INSERT, UPDATE, and DELETE for the entire lifetime of the table?" For a high-read, low-write table, that tax is negligible and the question is almost always yes. For a high-write table like an orders processor, an event log, or a job queue, the tax is real and significant, and the question deserves a serious answer before the index is created.

The corollary is equally important: _an index you are not paying attention to is a tax you forgot you were paying._ Every index on a high-write table that has zero `idx_scan` over three months of production traffic is a hidden deduction — you are paying the full write cost, the full WAL overhead, the full replication bandwidth, and the full maintenance cost (bloat accumulation, vacuum overhead) for an index that provides exactly zero benefit to any query.

```
The Index Tax at Different Write Rates:

  Table: orders (10 extra, zero-use indexes)

  Write Rate        Write Tax Per Index     Total Tax (10 indexes)
  ─────────────────────────────────────────────────────────────────
  100 inserts/day   Negligible              Negligible
  10,000/day        Small but measurable    Noticeable overhead
  100,000/day       Significant             Major performance drag
  1,000,000/day     Critical overhead       System destabilizing
  ─────────────────────────────────────────────────────────────────

  The same 10 unused indexes that cost nothing at 100 rows/day
  can collapse write throughput at 1,000,000 rows/day.

  This is why the problem is invisible at development scale
  and catastrophic at production scale.
```

When you internalize that every index is a permanent tax on every write, index creation stops feeling like a free optimization and starts feeling like what it actually is: a deliberate architectural decision with real, ongoing costs that must be justified by real, ongoing benefits.

## Conclusion: The Discipline of Purposeful Indexing

The first case study in this series taught you that every foreign key column needs an index. This case study teaches the corrective counterforce: not every column needs an index, and not every column that needs an index today will still need that same index next year.

Purposeful indexing is a discipline, not a checklist. It requires knowing the write rate of your tables, the selectivity of your columns, the actual access patterns of your application, and the cost-benefit trade-off of each individual index. It requires a review process before indexes are added and an audit process to remove the ones that have outlived their purpose. It requires monitoring write latency and WAL volume as first-class metrics alongside the more commonly tracked query latency metrics.

The engineers who build databases that remain fast under production scale are not the ones who add the most indexes. They are the ones who have the most precise understanding of why each index exists, and the discipline to remove the ones whose reasons have expired.

An over-indexed write table is not a sign of an incompetent team. It is a sign of a team that has been adding things without ever taking anything away — which is the natural tendency of any engineering team under forward pressure. The corrective is not less indexing enthusiasm; it is a structured process that applies the same rigor to removing an index as to adding one.
