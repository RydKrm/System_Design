# Case Study 03 — The Long-Running Transaction Lock Escalation

---

## The Setup — One Transaction, An Entire System Held Hostage

Imagine a backend engineer is asked to add a new feature: when a payroll batch is processed, the system should call an external tax-calculation API for each employee, then write the results back to the database, all wrapped inside a single transaction so it is "safe." The engineer writes the code, tests it locally with five employees, and it works perfectly — the whole thing completes in under a second. The code ships to production. Nobody thinks about it again.

Three weeks later, on payroll processing day, the company now has 800 employees. The batch job runs. It opens a database transaction, begins iterating through employees, and for each one, it makes an HTTP call to the external tax API — which sometimes takes 2 to 3 seconds per call. Eight hundred employees, two to three seconds each: the transaction runs for **25 to 40 minutes**. And for every one of those 40 minutes, it is holding row-level locks on the payroll table, the employee table, and the accounts table. Other application endpoints — the leave management system, the attendance tracking, the employee profile pages — all of which touch those same tables, begin piling up behind these locks. Connection slots fill. The application stops responding. Every user in the company gets error screens. Nobody can do anything.

This is **lock escalation from a long-running transaction**, and it is one of the most dramatic and easiest-to-cause failures in relational database systems. It requires no bug in the traditional sense — the code does exactly what it was designed to do. The design itself is the bug.

---

## Understanding Transactions and Locks — The Foundation

To understand why a long-running transaction is so dangerous, you must first understand what a transaction actually does to the data it touches. Most developers learn that a transaction provides **ACID guarantees** — Atomicity, Consistency, Isolation, and Durability — and understand at a conceptual level that this means "either all the changes happen, or none of them do." What is less often taught is the mechanical reality of how the database enforces the isolation property: **locks**.

When a transaction reads data with `SELECT ... FOR UPDATE`, or modifies data with `INSERT`, `UPDATE`, or `DELETE`, PostgreSQL acquires locks on the affected rows and tables. These locks serve as a coordination mechanism between concurrent transactions. They ensure that two transactions cannot simultaneously modify the same row in conflicting ways, that a transaction's reads are consistent with its writes, and that the database remains in a valid state at all times.

The critical rule of database locks is: **a lock is held for the entire duration of the transaction that acquired it**. Not for the duration of the individual query. Not until the next statement. For the entire transaction, from the moment the lock is acquired until the transaction commits or rolls back. This is not a design flaw — it is the fundamental mechanism that makes transactional isolation possible. But it has a profound implication that every engineer must internalize deeply: **the length of your transaction directly determines how long other transactions must wait**.

```
Lock Ownership Timeline:
======================================================================

  Time -->  0s    5s    10s   15s   20s   25s   30s   35s   40min
            |     |     |     |     |     |     |     |     |
  Txn A:    [BEGIN]---[UPDATE row 42]---[API call...]--..---[COMMIT]
  Locks:         ######################################## (row 42 locked)

  Txn B (wants to read row 42):
            waiting waiting waiting waiting ... ... ...
                    [BLOCKED: waiting for Txn A's lock to release]

  Txn C (wants to update row 42):
                  waiting waiting waiting waiting ... ... ...
                          [BLOCKED: waiting for Txn A's lock to release]

  Txn D, E, F, G... all queue up behind B and C.

  Every second Txn A runs = every waiter waits one more second.
  40 minutes of Txn A = 40 minutes of cascading blockage.
======================================================================
```

## The Anatomy of a Lock — What PostgreSQL Actually Holds

PostgreSQL uses a sophisticated locking system with multiple lock modes at multiple levels. Understanding the two main categories — **table-level locks** and **row-level locks** — helps you reason about why long-running transactions can paralyze seemingly unrelated operations.

**Table-level locks** are acquired when you run DDL statements (like `ALTER TABLE`) or when the database needs to coordinate access at the table granularity. The most relevant to this case study is the `AccessShareLock` acquired by ordinary `SELECT` statements, and the `RowExclusiveLock` acquired by `INSERT`, `UPDATE`, and `DELETE` statements. Most read-write operations use `RowExclusiveLock`, which is surprisingly permissive — multiple transactions can hold this lock simultaneously because it only conflicts with schema-changing operations, not with each other.

**Row-level locks** are what primarily concern us here. When a transaction modifies a row — via `UPDATE` or `DELETE` — it acquires an exclusive row-level lock on that specific row. No other transaction can modify or acquire an exclusive lock on that same row until the first transaction releases it (by committing or rolling back). If another transaction tries, it enters a **lock wait** state — it suspends execution and sits inside PostgreSQL, holding its connection open, consuming memory and a connection slot, doing nothing except waiting.

This waiting behavior is what turns a single slow transaction into a system-wide cascade. Each waiting transaction holds its own database connection. As more transactions queue up waiting for the long-running transaction's locks, more connections are consumed by the wait queue. Eventually, the connection pool fills entirely with waiting transactions. New requests from the application cannot get a connection from the pool, and the entire application effectively stops.

```
The Lock Cascade — How One Slow Transaction Blocks Everything:
======================================================================

  Database Table: employees (simplified)
  +--------+----------+-----------+----------+
  | emp_id | name     | salary    | dept_id  |
  +--------+----------+-----------+----------+
  | 001    | Alice    | 75,000    | HR       |  <- LOCKED by Txn A
  | 002    | Bob      | 82,000    | Finance  |  <- LOCKED by Txn A
  | 003    | Charlie  | 91,000    | Tech     |  <- LOCKED by Txn A
  |  ...   |  ...     |  ...      |  ...     |  <- LOCKED by Txn A
  | 800    | Zara     | 68,000    | Admin    |  <- LOCKED by Txn A
  +--------+----------+-----------+----------+
  (800 rows locked by the payroll batch transaction)

  Consequences:
  Txn B: "UPDATE employees SET manager = X WHERE emp_id = 001"
    -> BLOCKED. Waiting for Txn A to release lock on emp_id=001.
    -> Connection slot occupied. Request hanging.

  Txn C: "SELECT * FROM employees FOR UPDATE WHERE dept_id = 'HR'"
    -> BLOCKED. Waiting for Txn A.
    -> Another connection slot gone.

  Txn D, E, F...: All blocked, all holding connection slots.

  Connection Pool State:
  [Txn A - running]  [Txn B - waiting] [Txn C - waiting]
  [Txn D - waiting]  [Txn E - waiting] [Txn F - waiting]
  [Txn G - waiting]  [Txn H - waiting] [Txn I - waiting]
  [Txn J - waiting]  [              ] <- last free slot
  [New requests from app: cannot get a connection -> ERROR]
======================================================================
```

## The Real Patterns — Three Ways Engineers Create This Failure

The long-running transaction problem surfaces in several distinct but related patterns. Each is common, each is understandable in isolation, and each is catastrophic at scale.

### Pattern One: External API Calls Inside a Transaction

This is the payroll batch scenario from our opening. The engineer wraps the entire batch in a transaction for safety, then makes external HTTP calls within that transaction. External API calls are fundamentally unpredictable in their duration — they can take milliseconds or minutes, depending on network conditions, the upstream service's load, and rate limiting. Putting any external I/O inside a database transaction creates an unbounded lock-holding window. The transaction will hold its locks for exactly as long as the slowest API call takes, multiplied by the number of calls made sequentially, with no ceiling. This is never acceptable in a production system.

```go
// CATASTROPHIC PATTERN: External API call inside a DB transaction
func ProcessPayrollBatch(db *sql.DB, employeeIDs []int) error {
    tx, err := db.Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()

    for _, empID := range employeeIDs {
        // Step 1: Read employee data (acquires row lock)
        var salary float64
        tx.QueryRow("SELECT salary FROM employees WHERE id = $1 FOR UPDATE", empID).Scan(&salary)

        // Step 2: !! CALL EXTERNAL API WHILE HOLDING THE LOCK !!
        // This could take 0ms or 30 seconds. You have no control.
        // For 800 employees: potentially 800 * 2s = 26 minutes of lock holding.
        taxRate, err := externalTaxAPI.Calculate(empID, salary)  // NEVER DO THIS
        if err != nil {
            return err
        }

        // Step 3: Write result back
        tx.Exec("UPDATE payroll SET tax_rate = $1 WHERE emp_id = $2", taxRate, empID)
    }

    return tx.Commit()
    // Locks held for the ENTIRE duration above. Catastrophic.
}
```

### Pattern Two: Analytics Queries Inside a Transaction

Developers sometimes wrap analytical read queries in transactions to ensure they see a consistent snapshot of the data. The intent is correct — `REPEATABLE READ` isolation requires a transaction — but the consequence is that any locks acquired during a long-running analytical query are held for the entire duration of the analysis. An OLAP-style query that JOINs multiple large tables and runs for 10 minutes inside a transaction can block all writes to those tables for 10 minutes, even if the transaction is read-only, because other transactions waiting for schema-level locks or row-level access are forced to queue.

### Pattern Three: Forgetting to Commit

This is perhaps the simplest and most embarrassing cause: a developer writes code that opens a transaction, does some writes, and then — due to a code path bug, an exception that is swallowed, or simply an oversight — never commits. The application continues running, responding to other requests, seemingly fine. But that open transaction is sitting there, holding all its locks, forever (or until the connection is closed or the application restarts). This is the overlap zone between a connection leak (Case Study 02) and lock escalation — an uncommitted transaction is both a leaked connection and a lock escalation bomb.

## The Symptoms — Reading the Evidence in `pg_stat_activity`

When lock escalation is in progress, the evidence in PostgreSQL's system views is unambiguous once you know what to look for. The `pg_stat_activity` view becomes your primary diagnostic instrument, and the `pg_locks` view reveals the exact lock relationships.

The first symptom in `pg_stat_activity` is a connection with `state = 'idle in transaction'` or `state = 'active'` that has a very old `xact_start` timestamp — meaning its transaction has been running for minutes, not milliseconds. This is the "root cause" connection — the long-running transaction at the head of the problem.

The second symptom is multiple connections with `wait_event_type = 'Lock'` and `wait_event = 'relation'` or `'tuple'` — these are the victims, the transactions queued behind the long-running one, each holding a connection slot while waiting for a lock to be released.

```sql
-- Identify the long-running transaction (the root cause):
SELECT
    pid,
    usename,
    application_name,
    state,
    wait_event_type,
    wait_event,
    now() - xact_start   AS transaction_age,
    now() - query_start   AS query_age,
    left(query, 100)      AS current_query
FROM pg_stat_activity
WHERE datname = current_database()
  AND xact_start IS NOT NULL
ORDER BY transaction_age DESC;

-- A result showing transaction_age of '00:40:00' (40 minutes) is your culprit.
-- The query column shows what it last executed — your clue to the source in code.

-- Find all connections WAITING for a lock:
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    now() - query_start AS waiting_for,
    left(query, 100)    AS blocked_query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
ORDER BY waiting_for DESC;

-- The most powerful query: show the full blocking relationship
-- (which pid is blocking which other pid)
SELECT
    blocked.pid                     AS blocked_pid,
    blocked.query                   AS blocked_query,
    blocker.pid                     AS blocker_pid,
    blocker.query                   AS blocker_query,
    now() - blocker.xact_start      AS blocker_transaction_age
FROM pg_stat_activity AS blocked
JOIN pg_locks         AS blocked_locks  ON blocked.pid = blocked_locks.pid
JOIN pg_locks         AS blocker_locks  ON blocker_locks.locktype = blocked_locks.locktype
                                       AND blocker_locks.relation = blocked_locks.relation
                                       AND blocker_locks.granted = true
                                       AND blocked_locks.granted = false
JOIN pg_stat_activity AS blocker        ON blocker.pid = blocker_locks.pid
WHERE NOT blocked_locks.granted;

-- This query directly shows you: "pid X is blocking pid Y because pid X holds a lock
-- that pid Y needs." The blocker_transaction_age tells you exactly how long
-- the blocking transaction has been running.
```

What you will see in the monitoring dashboard during this failure is deliberately confusing: the database CPU and disk I/O are low (the blocking transaction may not even be running a query — it could be `idle in transaction` waiting for an API call), but application latency across every endpoint that touches the locked tables is spiking to timeout levels. The database is healthy. The locks are the disease.

## The Solutions — Three Pillars of Prevention and Recovery

Solving long-running transaction lock escalation requires changes at three levels: the PostgreSQL server configuration enforces hard limits, the application architecture prevents the bad patterns, and the code discipline ensures transactions are closed as quickly as possible.

### Pillar One — Server-Level Timeout Enforcement

The most immediately actionable change is configuring PostgreSQL timeouts that automatically terminate transactions and statements that run beyond acceptable limits. These are your safety nets — they do not prevent bad code from being written, but they prevent bad code from running unchecked forever:

```sql
-- In postgresql.conf (or via ALTER SYSTEM, or per-role via ALTER ROLE):

-- Terminate any single SQL statement that runs longer than 30 seconds.
-- This prevents a single runaway query from blocking everything indefinitely.
-- Your application will receive an error: "ERROR: canceling statement due to statement timeout"
statement_timeout = '30s'

-- Terminate any connection that has been in 'idle in transaction' state
-- for more than 60 seconds. This is the "forgot to commit" killer.
idle_in_transaction_session_timeout = '60s'

-- Set per-role for application users, not globally, to avoid affecting maintenance jobs:
ALTER ROLE app_user SET statement_timeout = '30s';
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '60s';

-- For batch jobs that legitimately need longer, use a separate DB role with relaxed limits:
ALTER ROLE batch_user SET statement_timeout = '300s';  -- 5 minutes max
ALTER ROLE batch_user SET idle_in_transaction_session_timeout = '120s';
```

The `lock_timeout` setting is another critical addition — it tells PostgreSQL to abandon a transaction that has been waiting for a lock for too long, rather than waiting indefinitely:

```sql
-- Terminate any transaction that waits more than 10 seconds for a lock.
-- This prevents the wait queue from growing indefinitely.
-- The waiting transaction gets an error; it can retry if appropriate.
lock_timeout = '10s'

-- Set in Go application code for fine-grained control:
// At connection or transaction setup time:
_, err = db.ExecContext(ctx, "SET lock_timeout = '10s'")
_, err = db.ExecContext(ctx, "SET statement_timeout = '30s'")
```

### Pillar Two — Architectural Discipline: Open Late, Close Early

The most important architectural rule for transactions is often called **"open late, close early."** A transaction should be opened at the absolute last moment before the first database write is needed, and it should be committed or rolled back at the absolute earliest moment possible after the last write. Everything that does not directly require database consistency — calling external APIs, performing complex calculations, building data structures, formatting output — must happen either before the transaction opens or after it closes, never inside it.

This principle completely rewrites our payroll batch example:

```go
// THE CORRECT ARCHITECTURE: Open Late, Close Early

func ProcessPayrollBatch(db *sql.DB, employeeIDs []int) error {
    // PHASE 1: Gather all external data BEFORE opening any transaction.
    // This phase can take as long as it needs. No locks are held.
    taxRates := make(map[int]float64)
    for _, empID := range employeeIDs {
        // Step 1: Read employee data in a short, separate, committed query.
        // This read does NOT use FOR UPDATE — it is informational.
        var salary float64
        err := db.QueryRow(
            "SELECT salary FROM employees WHERE id = $1", empID,
        ).Scan(&salary)
        if err != nil {
            return fmt.Errorf("reading employee %d: %w", empID, err)
        }

        // Step 2: Call the external API with no DB connection held.
        // This can take 2-3 seconds. That is fine — no locks are held.
        rate, err := externalTaxAPI.Calculate(empID, salary)
        if err != nil {
            return fmt.Errorf("tax API for employee %d: %w", empID, err)
        }
        taxRates[empID] = rate
    }

    // PHASE 2: Now that ALL external work is done, open the transaction
    // and execute all writes as fast as possible.
    // This transaction should complete in milliseconds.
    tx, err := db.Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()

    for empID, rate := range taxRates {
        // Pure DB writes. No external I/O. No calculations. Just writes.
        _, err := tx.Exec(
            "UPDATE payroll SET tax_rate = $1, updated_at = NOW() WHERE emp_id = $2",
            rate, empID,
        )
        if err != nil {
            return fmt.Errorf("writing payroll for employee %d: %w", empID, err)
        }
    }

    // Transaction committed in milliseconds. Locks held for microseconds.
    return tx.Commit()
}
```

In this refactored version, the database transaction is open for only as long as it takes to execute 800 `UPDATE` statements — which, in a well-configured PostgreSQL database, should take roughly 50 to 200 milliseconds, not 40 minutes. The external API calls are all completed before a single lock is acquired. The total wall-clock time for the batch job might still be 40 minutes, but the lock-holding window is reduced from 40 minutes to a fraction of a second.

### Pillar Three — Transaction Scope Discipline in Go Code

Beyond the architectural pattern, Go code should apply consistent discipline to ensure transactions are always properly scoped and never accidentally expanded:

```go
// Pattern: Use a context with deadline for every transaction
func WithTransaction(ctx context.Context, db *sql.DB, fn func(*sql.Tx) error) error {
    // Create a context with a maximum transaction duration.
    // If the transaction takes longer than this, it will be cancelled.
    txCtx, cancel := context.WithTimeout(ctx, 10*time.Second)
    defer cancel()

    tx, err := db.BeginTx(txCtx, nil)
    if err != nil {
        return fmt.Errorf("begin transaction: %w", err)
    }
    defer tx.Rollback()

    if err := fn(tx); err != nil {
        return err
    }

    return tx.Commit()
}

// Usage: clean, bounded, safe transactions
err = WithTransaction(ctx, db, func(tx *sql.Tx) error {
    // Only pure DB operations here. No external calls. No long loops.
    _, err := tx.ExecContext(ctx, "UPDATE accounts SET balance = $1 WHERE id = $2", newBal, accID)
    return err
})

// Rule: If you find yourself wanting to put a for-loop with 1000 iterations
// inside a WithTransaction call, stop. Redesign. Use PHASE 1 / PHASE 2 pattern.
```

## The Impact of `lock_timeout` — Failing Fast Instead of Waiting Forever

One of the most effective mitigation strategies is configuring `lock_timeout` in your PostgreSQL settings or in your application connection setup. Without `lock_timeout`, a transaction waiting for a lock will wait **forever** — or until its connection is dropped for another reason. This means a single long-running transaction can hold an arbitrarily large queue of waiting connections hostage for its entire duration.

With `lock_timeout = '10s'`, a transaction that cannot acquire a lock within 10 seconds will be **aborted** with an error rather than continuing to wait. This is the "fail fast" principle applied to locks. The queued transaction gets an error — `ERROR: canceling statement due to lock timeout` — but it releases its connection slot immediately. This slot is now available for other work. The application receives an error it can handle (retry, return a user-facing message, etc.), rather than a connection-pool-exhaustion outage.

```
WITH lock_timeout = '10s':
======================================================================

  t = 00:00   Txn A starts. Holds locks.
  t = 00:05   Txn B arrives. Wants the same lock. Starts waiting.
  t = 00:15   Txn B has waited 10 seconds. lock_timeout fires.
              Txn B receives: ERROR: canceling statement due to lock timeout
              Txn B's connection is RETURNED to the pool immediately.
              Application handles the error: logs it, returns 503 to user.

  t = 00:15   Txn C arrives. Same story — waits 10s, gets an error, releases slot.
  t = 00:25   Txn D arrives. Same.

  Pool state throughout:  [Txn A: running] [          ] <- Pool never exhausts
  Users: Some requests fail with "service temporarily unavailable" (handleable)
         Most requests on other tables: unaffected.
         System degrades gracefully rather than catastrophically.

WITHOUT lock_timeout:
======================================================================
  Txn B, C, D, E, F... all wait indefinitely.
  Pool fills up. All users get errors. Complete outage.
======================================================================
```

The trade-off is clear: `lock_timeout` turns a full outage into a partial, gracefully-degraded service. Some requests fail with an error that the application can communicate to users, but the system continues serving other requests and does not collapse entirely.

## Monitoring — Building Alerts That Catch This Before the Outage

Reactive diagnosis is valuable, but the real goal is catching this problem before it causes an outage. The following monitoring queries, run periodically and compared against thresholds, will alert you in the early stages — when Txn A has been running for 5 minutes but the pool is not yet exhausted:

```sql
-- Alert 1: Long-running transactions (should fire at 1-2 minutes, not 40)
SELECT count(*)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND now() - xact_start > interval '1 minute'
  AND state != 'idle';
-- ALERT if count > 0

-- Alert 2: Lock waits accumulating (early warning of lock escalation)
SELECT count(*)
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
-- ALERT if count > 2

-- Alert 3: Transactions with very old xact_start (the root cause detector)
SELECT pid, state, now() - xact_start AS age, left(query, 80) AS last_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND now() - xact_start > interval '2 minutes'
ORDER BY age DESC;
-- ALERT and page on-call if any result appears

-- Emergency termination of the blocking transaction:
-- ONLY use this after confirming which pid is the root cause blocker.
SELECT pg_terminate_backend(<blocking_pid>);
-- This will rollback the blocking transaction and release all its locks.
-- All waiting transactions will then proceed.
-- The batch job will need to be re-run, ideally with the correct architecture.
```

## Key Takeaways — The Principles to Carry Forward

The long-running transaction lock escalation teaches perhaps the single most important lesson in database-backed application design: **a transaction is not just a unit of atomicity — it is a unit of time during which locks are held, and every millisecond of that time costs every other operation that touches the same data.**

Think of a database transaction like a conversation in a shared office meeting room. When you reserve the room, other meetings cannot happen there. A five-minute meeting is reasonable. A five-hour meeting blocks the room all day and everyone else's work piles up outside. And a meeting where half the time is spent waiting on a phone call to an outside party — while still holding the room reservation — is simply inconsiderate and operationally broken.

The "open late, close early" principle is not a performance optimization — it is a correctness requirement for any system that serves concurrent users. External API calls, complex calculations, file I/O, message queue operations — none of these things belong inside a database transaction. They belong before the transaction opens or after it closes. The transaction itself should contain only the minimum set of pure database reads and writes required to maintain atomicity, executed as rapidly as possible.

Configure `statement_timeout`, `idle_in_transaction_session_timeout`, and `lock_timeout` on every production PostgreSQL database you operate. These timeouts are not pessimistic — they are a disciplined acknowledgment that in a complex system, things go wrong, and the database should not allow a single bad actor to hold the entire system hostage indefinitely. Fail fast, fail loudly, release resources, and let the rest of the system continue.
