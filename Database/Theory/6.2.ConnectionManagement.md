# Connection Management
### A Deep, Conceptual Journey from the Ground Up

> *A database connection is not a free resource. Every one you open costs something, and every one you leave open idle is a tax the entire system pays.*

---

## Preface: The Problem Nobody Talks About in Tutorials

Every database tutorial shows you the same thing: open a connection, run a query, close the connection. It is clean, simple, and completely wrong for production systems. In a real application serving hundreds or thousands of concurrent users, opening a new database connection for every request would collapse the system within seconds — not because of the queries themselves, but because of the cost of establishing the connections.

This is one of the most underappreciated performance problems in backend engineering. Developers spend enormous effort optimizing SQL queries — adding indexes, rewriting joins, tuning aggregations — while leaving the connection strategy entirely unconsidered. But a poorly managed connection strategy can cause more latency, more errors, and more system instability than a badly-written query ever could.

This guide is about understanding why connections are expensive, how pooling solves that problem, how to size a pool correctly using both theory and empirical measurement, and how prepared statements interact with the entire picture. These topics are not glamorous, but they are foundational to building backend systems that actually hold up under real load.

## Chapter 1: Connection Overhead — The True Cost of a Database Connection

### What Actually Happens When You Open a Connection

When your application calls `db.connect()` or establishes a new database connection, you might imagine something simple happening — a socket opens, the database acknowledges it, and you are ready to query. In reality, establishing a PostgreSQL connection is a surprisingly expensive multi-step process that involves the operating system, the network stack, the database process model, and cryptographic negotiation.

Understanding each step is what makes the cost tangible, not just theoretical.

```
The Full Connection Establishment Sequence (PostgreSQL):

  Application                    PostgreSQL Server
      │                                │
      │──── TCP SYN ──────────────────►│  1. TCP handshake begins
      │◄─── TCP SYN-ACK ───────────────│     (3-way handshake)
      │──── TCP ACK ──────────────────►│
      │                                │     ~0.1–1ms (local network)
      │──── TLS ClientHello ──────────►│  2. TLS handshake (if SSL)
      │◄─── TLS ServerHello ───────────│     Certificate exchange
      │──── TLS Finished ─────────────►│     Key derivation
      │◄─── TLS Finished ───────────────│     ~1–10ms
      │                                │
      │──── StartupMessage ───────────►│  3. PostgreSQL startup message
      │     (user, database, params)   │     Server validates credentials
      │◄─── AuthenticationRequest ─────│
      │──── Password / SCRAM ─────────►│  4. Authentication
      │◄─── AuthenticationOK ──────────│     ~0.5–5ms
      │◄─── ParameterStatus ───────────│  5. Server sends configuration:
      │◄─── BackendKeyData ────────────│     server_version, TimeZone,
      │◄─── ReadyForQuery ─────────────│     DateStyle, client_encoding...
      │                                │     Backend process is now ready
      │                                │     ~0.2–1ms
      │                                │
      Total time: 2–20ms (local), 10–100ms+ (cross-datacenter)
      Total cost: see below
```

Each step has a real cost measured in time, CPU, memory, and file descriptors:

**TCP handshake:** Three network round-trips before a single byte of PostgreSQL data is exchanged. On a local network this is fast (fractions of a millisecond), but latency compounds across datacenters.

**TLS negotiation:** If SSL is enabled (and it should be in production), the TLS handshake requires certificate verification, asymmetric cryptographic operations for key exchange, and additional round-trips. This alone can add 2–10ms.

**PostgreSQL process fork:** PostgreSQL uses a process-per-connection model. When a new connection arrives, the postmaster (the PostgreSQL master process) forks a new backend process to handle it. `fork()` is not free — it copies the process's memory pages (using copy-on-write, but the page table itself is copied), initializes the new process's stack, and registers it with the OS scheduler.

**Memory allocation per connection:** Each backend process in PostgreSQL has its own private memory. The `work_mem` parameter (default 4MB) is the maximum memory a single query operation can use, and a complex query with many sort and hash operations can use multiples of `work_mem`. Each connection also allocates memory for its session state, prepared statement cache, and lock table entries. The base overhead per connection in PostgreSQL is typically 5–10MB of shared and private memory.

**Shared memory structures:** Each connection occupies a slot in PostgreSQL's shared memory — the lock table, the process array, the WAL sender array. These are finite resources with hard limits.

```
Per-Connection Resource Cost (approximate, PostgreSQL):

  Time to establish:    2–20ms (local network with SSL)
  Memory per process:   5–10MB (base, before any query work_mem)
  Shared memory slots:  1 lock table entry + 1 process array slot
  OS file descriptors:  2–3 (socket + pipe + signal pipe)
  OS process:           1 (PostgreSQL uses process-per-connection)
  CPU cost to fork:     Measurable — 0.1–1ms of CPU time

  At 100 connections:   ~500MB–1GB memory consumed by connections alone
  At 500 connections:   ~2.5GB–5GB memory — often the limiting factor
  At max_connections:   PostgreSQL default is 100 (tunable, but not without cost)
```

### The Per-Query Connection Overhead

Beyond the one-time establishment cost, maintaining a connection has ongoing costs even when it is idle. An idle connection still occupies a slot in the process array, still holds a lock table entry, still consumes an OS file descriptor, and still represents a process that the OS scheduler must consider (even if it is sleeping). Idle connections are not free; they are just cheaper than active ones.

In a naive application architecture where each incoming HTTP request opens a new connection, executes its queries, and closes the connection, the cost compounds dramatically:

```
Naive "Connect per Request" Architecture:

  Each request:
    Open connection:   5ms    ← pure overhead, zero business value
    Execute query:     2ms    ← actual work
    Close connection:  1ms    ← overhead
    Total:             8ms

  Connection overhead: 75% of total request time.

  At 1,000 requests/second:
    1,000 TCP handshakes/second
    1,000 TLS negotiations/second
    1,000 PostgreSQL process forks/second
    1,000 process destructions/second

  The database server is spending more time managing connections
  than executing queries. This is the connection storm problem.
```

The connection storm is a real failure mode. When an application restarts after a crash or deployment, all instances simultaneously attempt to reconnect to the database. Hundreds of connections arrive at once, each requiring a process fork, memory allocation, and TLS negotiation. The database server CPU spikes, memory spikes, and the very load of establishing connections delays the first queries — which time out — which cause retries — which add more connections — which cascade into a thundering herd that can take minutes to stabilize.

### The max_connections Wall

PostgreSQL's `max_connections` parameter sets an absolute upper limit on concurrent connections. The default is 100. Raising it sounds like an easy fix, but it is not free: each additional allowed connection reserves a slot in shared memory structures, even when that slot is unused. The shared memory allocation happens at startup, based on `max_connections`, and it does not scale down when connections are idle.

More critically, PostgreSQL's process-per-connection model means that with 500 simultaneous connections, there are 500 OS processes competing for CPU. Context-switching between 500 processes has measurable overhead. Studies have shown that PostgreSQL's throughput actually decreases when connection count exceeds roughly 2–4× the number of CPU cores, because the scheduler overhead outweighs the parallelism benefit.

```
PostgreSQL Throughput vs. Connection Count (conceptual):

  Throughput
     │
     │          ╭──────────╮
     │        ╭╯            ╰─────────────────── (degradation)
     │      ╭╯
     │    ╭╯
     │  ╭╯
     │╭╯
     └──────────────────────────────────────► Connection Count
          ↑              ↑
     Sweet spot       Saturation point
    (≈ 2-4× CPUs)    (diminishing returns begin)

  Adding connections beyond the sweet spot does not increase throughput —
  it DECREASES it due to scheduler overhead and memory pressure.
  Connection pooling keeps connection count near the sweet spot.
```

This is the foundational argument for connection pooling: not just "connections are expensive to open," but "having too many simultaneous connections actively harms database performance, regardless of what those connections are doing."

## Chapter 2: Connection Pooling — The Solution

### What a Connection Pool Is

A **connection pool** is a cache of database connections that are kept open and reused across multiple requests, rather than being opened and closed per request. The pool maintains a set of live connections to the database. When your application needs a connection, it borrows one from the pool. When it is done, it returns the connection to the pool — the connection is not closed, just made available for the next borrower.

From the database's perspective, the connections in the pool look like long-lived clients that send many queries over time. From the application's perspective, getting a connection from the pool is nearly instant (microseconds instead of milliseconds) because the TCP, TLS, and authentication negotiation already happened when the pool was initialized.

```
Connection Pool Architecture:

  ┌─────────────────────────────────────────────────────────────────┐
  │                    APPLICATION LAYER                            │
  │  Request 1  Request 2  Request 3  ... Request N (hundreds)      │
  └──────┬──────────┬──────────┬──────────────┬────────────────────┘
         │          │          │              │
         ▼          ▼          ▼              ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │                    CONNECTION POOL                              │
  │                                                                 │
  │  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐           │
  │  │ Conn  1  │ │ Conn  2  │ │ Conn  3  │ │ Conn  4  │  ...      │
  │  │ [BUSY]   │ │ [IDLE]   │ │ [BUSY]   │ │ [IDLE]   │           │
  │  └──────────┘ └──────────┘ └──────────┘ └──────────┘           │
  │                                                                 │
  │  Pool size: N connections (e.g., 20)                            │
  │  Hundreds of app requests share these N connections             │
  └─────────────┬──────────────────────────────────────────────────┘
                │  N persistent connections (e.g., 20)
                │  (never closed, always authenticated)
                ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │                   PostgreSQL Server                             │
  │   20 backend processes, each handling one connection            │
  │   (instead of hundreds of processes — one per request)          │
  └─────────────────────────────────────────────────────────────────┘
```

The multiplexing effect is the key: N application requests share P pool connections, where P << N. If your application serves 500 concurrent HTTP requests but the average query takes 5ms, then at any given moment only a small fraction of those requests are actually executing a query — the rest are doing application-layer work (parsing, serialization, business logic). A pool of 20 connections can serve hundreds of requests per second because the connections are reused in rapid succession.

### The Pooling Mode Question: Where Does the Pool Live?

There are two fundamentally different architectures for connection pooling: **client-side pooling** (the pool lives inside the application process) and **server-side pooling** (the pool is a separate proxy process between the application and the database). Understanding the difference matters for scaling multi-process or multi-instance applications.

```
Client-Side Pooling:

  App Instance 1 (pool: 20 conns) ─┐
  App Instance 2 (pool: 20 conns) ─┼──► PostgreSQL (60 connections total)
  App Instance 3 (pool: 20 conns) ─┘

  Each app instance has its own pool.
  With 3 instances × 20 connections = 60 total DB connections.
  With 10 instances × 20 connections = 200 total DB connections.
  With 50 instances × 20 connections = 1,000 total DB connections → problem.

  Client-side pooling does not help when you have many app instances.
  The total DB connections grow linearly with app instances.

Server-Side Pooling (e.g., PgBouncer):

  App Instance 1 (pool: 20 conns) ─┐
  App Instance 2 (pool: 20 conns) ─┼──► PgBouncer ──► PostgreSQL (20 connections)
  App Instance 3 (pool: 20 conns) ─┘       (proxy)

  All app instances connect to PgBouncer, not directly to PostgreSQL.
  PgBouncer maintains a fixed pool to PostgreSQL.
  No matter how many app instances exist,
  PostgreSQL only sees PgBouncer's pool (e.g., 20 connections).
  The total DB connections are decoupled from the number of app instances.
```

For horizontally-scaled applications (multiple pods in Kubernetes, multiple EC2 instances, serverless functions), server-side pooling is essential. Without it, each new application instance adds its full pool to the database connection count, eventually hitting `max_connections`.

## Chapter 3: PgBouncer — The PostgreSQL Connection Proxy

### What PgBouncer Is

**PgBouncer** is a lightweight, single-purpose connection pooler designed specifically for PostgreSQL. It sits between your application servers and PostgreSQL, acting as a proxy that accepts connections from the application side (potentially thousands) and maintains a smaller pool of real connections to PostgreSQL. It was created in 2007 and remains the most widely deployed PostgreSQL connection pooler.

PgBouncer is written in C, single-threaded, uses an event loop (like Nginx or Redis), and is extraordinarily efficient — it can handle thousands of client connections with negligible CPU and memory overhead (typically a few MB of RAM and <1% CPU under heavy load).

### PgBouncer's Three Pooling Modes

The most important concept in PgBouncer is its **pooling mode**, which determines when a server-side connection is assigned to a client-side connection and when it is returned to the pool. The three modes represent a fundamental trade-off between compatibility and connection efficiency.

**Session Mode:** A server connection is assigned to a client when the client connects and held for the client's entire session — until the client disconnects. This is the safest mode (full compatibility with all PostgreSQL features) but provides the least pooling benefit. The number of server connections equals the number of active client connections.

```
Session Mode:

  Client connects   → Server connection assigned immediately
  Client queries    → Uses its server connection
  Client idles      → Still holds the server connection
  Client disconnects → Server connection returned to pool

  Useful for: applications that use session-level features like
  SET, temporary tables, advisory locks, prepared statements.
  Less useful for: high-frequency short-lived connections.
```

**Transaction Mode:** A server connection is assigned to a client only for the duration of a transaction. Between transactions, the client holds no server connection — other clients can use the pool. This is the most popular mode for web applications and provides the greatest connection multiplexing benefit.

```
Transaction Mode:

  Client connects        → No server connection assigned yet
  Client BEGIN           → Server connection assigned
  Client queries (in tx) → Uses its server connection
  Client COMMIT/ROLLBACK → Server connection returned to pool
  Client idles           → No server connection held

  Multiplexing: 1000 client connections can share 20 server connections
  if transactions are short and clients spend time between transactions
  doing application-layer work.

  Restrictions: Session-level features are NOT safe:
  - SET commands (session variables reset when connection returns to pool)
  - Temporary tables (destroyed when connection is reassigned)
  - Advisory locks (released when connection returns to pool)
  - Named prepared statements (not tracked across pool reassignment)
  - LISTEN/NOTIFY (not compatible with transaction mode)
```

**Statement Mode:** A server connection is assigned only for the duration of a single SQL statement. After each statement, the connection returns to the pool. This is the most aggressive pooling but requires that all queries are single-statement (no multi-statement transactions). In practice this mode is rarely used for regular applications — it does not support transactions at all.

```
PgBouncer Pooling Mode Comparison:

  Mode        │ Server Conn Held For │ Multiplexing │ Feature Compatibility
  ────────────┼──────────────────────┼──────────────┼──────────────────────
  Session     │ Entire client session│ Low          │ Full — all features work
  Transaction │ Duration of one tx   │ High ✓       │ Medium — no session features
  Statement   │ Duration of one stmt │ Maximum      │ Low — no transactions
```

### PgBouncer Configuration

PgBouncer is configured through a `.ini` file. The critical parameters are:

```ini
; pgbouncer.ini

[databases]
; Map incoming database names to the real PostgreSQL server
; "myapp" is what clients connect to, forwarded to 127.0.0.1:5432
myapp = host=127.0.0.1 port=5432 dbname=myapp_production

[pgbouncer]
; Network settings
listen_addr = 0.0.0.0
listen_port = 6432         ; clients connect here (not to Postgres directly)

; Pooling
pool_mode = transaction    ; the most common production setting

; Pool size (server-side connections to PostgreSQL)
max_client_conn = 10000    ; maximum client connections PgBouncer accepts
default_pool_size = 20     ; server connections per database+user combination

; Overflow handling
reserve_pool_size = 5      ; extra connections allowed briefly during spikes
reserve_pool_timeout = 3   ; seconds before using reserve pool

; Idle connection management
server_idle_timeout = 600  ; close idle server connections after 10 min
client_idle_timeout = 0    ; never disconnect idle clients (0 = disabled)

; Query timeout (prevent hung queries from blocking the pool)
query_timeout = 30         ; abort queries running longer than 30 seconds
query_wait_timeout = 15    ; abort if a client waits this long for a server conn

; Authentication
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

; Logging
logfile = /var/log/pgbouncer/pgbouncer.log
pidfile = /var/run/pgbouncer/pgbouncer.pid
```

### The Transaction Mode Restriction Problem and Its Solutions

The biggest operational challenge with PgBouncer in transaction mode is that session-level features break. The most painful of these is **named prepared statements** — when your application creates a named prepared statement (`PREPARE stmt1 AS SELECT ...`), the statement is stored in the PostgreSQL backend process's memory. If PgBouncer reassigns that connection to a different client, the new client does not have that prepared statement, but the session state may be confused.

The solutions are:

```
Handling Prepared Statements in Transaction Mode:

Option 1: Disable named prepared statements in the application driver.
  In Go pgx: pgx.ParseConfig().DefaultQueryExecMode = pgx.QueryExecModeSimpleProtocol
  In Node.js pg: { statement_timeout: false } or use simple query mode
  In Java HikariCP: configure PrepStmtCacheSize = 0 when behind PgBouncer

Option 2: Use PgBouncer in Session mode (loses multiplexing benefit).
  Acceptable when your app has few app instances or short-lived connections.

Option 3: Use Prepared Statement tracking (PgBouncer 1.21+).
  PgBouncer can now optionally track named prepared statements
  and ensure they are re-created when connections are reassigned.
  This lifts the restriction but adds overhead.

Option 4: Use protocol-level prepared statements (extended query protocol)
  without naming them — these are per-query and not session-persistent.
  Most modern drivers do this transparently.
```

## Chapter 4: HikariCP — The Java Connection Pool

### What HikariCP Is

**HikariCP** (named after the Japanese word for "light") is the de facto standard JDBC connection pool for Java and Kotlin applications, and is the default pool in Spring Boot. It is a client-side pool — it lives inside the JVM process — and it is renowned for being both extremely fast and extremely reliable. HikariCP's design philosophy is "simplicity and speed above all," and it achieves this by doing less than its predecessors (C3P0, Apache DBCP) rather than more.

HikariCP uses a lock-free `ConcurrentBag` data structure for its connection pool, which gives sub-microsecond connection acquisition times for the common case where an idle connection is immediately available. Its failure detection is aggressive — it actively tests connections and removes broken ones before they are handed to application code.

### HikariCP Configuration

```java
// Java / Spring Boot HikariCP configuration

HikariConfig config = new HikariConfig();

// Database connection details
config.setJdbcUrl("jdbc:postgresql://db-host:5432/myapp");
config.setUsername("app_user");
config.setPassword("secret");

// Pool sizing (critical — see Chapter 5 for the formula)
config.setMaximumPoolSize(20);         // maximum connections in the pool
config.setMinimumIdle(5);             // minimum idle connections to maintain

// Timeout settings (all in milliseconds)
config.setConnectionTimeout(30_000);  // max time to wait for a connection from pool
config.setIdleTimeout(600_000);       // close idle connections after 10 min
config.setMaxLifetime(1_800_000);     // max lifetime of a connection (30 min)
                                      // always set lower than DB/firewall timeout!

// Connection health testing
config.setConnectionTestQuery("SELECT 1"); // for drivers that need it
config.setKeepaliveTime(60_000);      // send keepalive every 60s to prevent
                                      // firewalls from killing idle connections

// Performance settings
config.setAutoCommit(false);          // control transactions explicitly
config.addDataSourceProperty("cachePrepStmts", "true");
config.addDataSourceProperty("prepStmtCacheSize", "250");
config.addDataSourceProperty("prepStmtCacheSqlLimit", "2048");
config.addDataSourceProperty("useServerPrepStmts", "true");

// Pool naming (appears in JMX metrics, thread names, logs)
config.setPoolName("MyApp-DB-Pool");

HikariDataSource ds = new HikariDataSource(config);
```

### HikariCP's maxLifetime: The Critical Parameter

The `maxLifetime` parameter is one of the most important and most frequently misconfigured in HikariCP. It controls the maximum lifetime of a connection in the pool. When a connection reaches its maximum lifetime, HikariCP retires it and creates a new one in its place.

Why does this matter? Database servers, firewalls, load balancers, and network devices all have their own idle connection timeouts. If a connection sits in your pool for longer than the database server's `tcp_keepalives_idle` or a firewall's connection timeout, the connection is silently killed on the infrastructure side — but your pool does not know this. The next application request to borrow that connection gets a "broken pipe" or "connection reset" error.

`maxLifetime` prevents this by proactively recycling connections before they can be killed by infrastructure. The rule is: set `maxLifetime` to several minutes less than the database server's connection timeout (PostgreSQL's `tcp_keepalives_idle`, or any intermediate proxy timeout).

```
maxLifetime Rule of Thumb:

  PostgreSQL server timeout (e.g., idle_in_transaction_session_timeout) = 30 min
  Firewall/NAT timeout (often the binding constraint) = 20 min

  Set maxLifetime to: 18 minutes (several minutes less than the minimum timeout)
  Set idleTimeout to:  10 minutes (retire idle connections before maxLifetime)

  maxLifetime (18m) < firewall timeout (20m) < Postgres timeout (30m)
  ↑ HikariCP recycles the connection before anything else kills it silently.
```

### HikariCP Metrics Integration

HikariCP integrates with Micrometer (the de facto metrics library for Spring Boot) and exposes pool metrics to Prometheus, Grafana, Datadog, and others:

```yaml
# application.yml (Spring Boot)
management:
  metrics:
    enable:
      hikaricp: true

# Key metrics exposed (prefixed with hikaricp.connections.*):
# hikaricp.connections.active    — currently borrowed connections
# hikaricp.connections.idle      — connections sitting in pool, unused
# hikaricp.connections.pending   — threads waiting for a connection
# hikaricp.connections.acquire   — histogram of time waiting for connection
# hikaricp.connections.usage     — histogram of time connection was borrowed
# hikaricp.connections.creation  — histogram of time to create new connection
# hikaricp.connections.timeout.total — count of connection timeout errors
```

The most important metric to monitor is `hikaricp.connections.pending` — the number of threads waiting for a connection because the pool is fully busy. If this is consistently above zero, your pool is undersized for your load, and you will see `Connection is not available, request timed out` errors under peak load.

## Chapter 5: pgx Pool — Go's Native PostgreSQL Pool

### What pgx Is

**pgx** (PostgreSQL eXtended) is the most feature-complete PostgreSQL driver for Go. Unlike `database/sql` (Go's standard database interface), pgx is a PostgreSQL-specific driver that exposes PostgreSQL-native features: binary protocol, COPY, logical replication, extended query protocol, listen/notify, and fine-grained connection pool control. For Go applications that use PostgreSQL seriously, pgx is the standard choice.

pgx includes `pgxpool` — a built-in, production-ready connection pool that is designed specifically around Go's concurrency model (goroutines and channels) and PostgreSQL's wire protocol.

### pgxpool Configuration

```go
package main

import (
    "context"
    "time"
    "github.com/jackc/pgx/v5/pgxpool"
)

func NewPool(ctx context.Context, connString string) (*pgxpool.Pool, error) {
    config, err := pgxpool.ParseConfig(connString)
    if err != nil {
        return nil, err
    }

    // Pool sizing
    config.MaxConns = 20             // maximum connections in pool
    config.MinConns = 5              // minimum connections to maintain
                                     // (pre-warm the pool at startup)

    // Timeout settings
    config.MaxConnLifetime = 30 * time.Minute  // max age of a connection
    config.MaxConnIdleTime = 10 * time.Minute  // max idle time before closing
    config.HealthCheckPeriod = 1 * time.Minute // how often to health-check idle conns

    // Connection acquisition timeout
    // If no connection is available within this duration, return an error
    // (not a pgxpool config field — use context.WithTimeout when acquiring)

    // Lifecycle hooks: run code when connections are created/destroyed
    config.BeforeAcquire = func(ctx context.Context, conn *pgx.Conn) bool {
        // Return false to discard the connection before giving it to the caller.
        // Useful for validating connection health or applying session settings.
        return true
    }

    config.AfterRelease = func(conn *pgx.Conn) bool {
        // Return false to destroy the connection instead of returning to pool.
        // Useful for cleaning up session state (RESET ALL) or discarding
        // connections that had errors.
        return true
    }

    config.BeforeConnect = func(ctx context.Context, cfg *pgx.ConnConfig) error {
        // Modify connection config just before a new connection is established.
        // Useful for dynamic credentials (e.g., from a secrets manager).
        return nil
    }

    pool, err := pgxpool.NewWithConfig(ctx, config)
    if err != nil {
        return nil, err
    }

    // Verify pool is healthy at startup
    if err := pool.Ping(ctx); err != nil {
        pool.Close()
        return nil, err
    }

    return pool, nil
}
```

### Using pgxpool in Application Code

```go
// Correct pattern: always use context with timeout for pool acquisition
func getUserByID(ctx context.Context, pool *pgxpool.Pool, userID int) (*User, error) {
    // Acquire a connection from the pool (with context for timeout)
    // If pool is exhausted, this blocks until a connection is available
    // or the context is cancelled/times out.
    conn, err := pool.Acquire(ctx)
    if err != nil {
        return nil, fmt.Errorf("acquiring connection: %w", err)
    }
    defer conn.Release() // always release back to pool, even on error

    var user User
    err = conn.QueryRow(ctx,
        "SELECT id, name, email FROM users WHERE id = $1",
        userID,
    ).Scan(&user.ID, &user.Name, &user.Email)
    if err != nil {
        return nil, fmt.Errorf("querying user: %w", err)
    }
    return &user, nil
}

// For simple single-query operations, use pool directly (auto acquire+release):
func getUserByIDSimple(ctx context.Context, pool *pgxpool.Pool, userID int) (*User, error) {
    var user User
    err := pool.QueryRow(ctx,
        "SELECT id, name, email FROM users WHERE id = $1",
        userID,
    ).Scan(&user.ID, &user.Name, &user.Email)
    if err != nil {
        return nil, fmt.Errorf("querying user: %w", err)
    }
    return &user, nil
}

// For transactions: acquire once, use throughout the transaction
func transferFunds(ctx context.Context, pool *pgxpool.Pool,
    fromID, toID int, amount decimal.Decimal) error {

    conn, err := pool.Acquire(ctx)
    if err != nil {
        return err
    }
    defer conn.Release()

    tx, err := conn.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx) // no-op if committed

    _, err = tx.Exec(ctx,
        "UPDATE accounts SET balance = balance - $1 WHERE id = $2",
        amount, fromID,
    )
    if err != nil {
        return err
    }

    _, err = tx.Exec(ctx,
        "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
        amount, toID,
    )
    if err != nil {
        return err
    }

    return tx.Commit(ctx)
}
```

## Chapter 6: Pool Sizing — The Formula

### Why Pool Sizing Is Not Obvious

The most common mistake engineers make with connection pools is setting the pool size too large. The intuition is: "more connections = more parallelism = faster." This is wrong. A connection pool that is too large actually degrades performance — because you are pushing more concurrent connections to PostgreSQL than it can handle efficiently, triggering the scheduler overhead and memory pressure described in Chapter 1.

The correct pool size is a function of the database server's capacity, not the application's demand. Adding more connections to a pool does not give the database more capacity — it just changes how that capacity is distributed among requesters.

### The Formula

The most influential work on connection pool sizing for PostgreSQL comes from Brett Wooldridge (the author of HikariCP) and the PostgreSQL community. The foundational formula is:

```
Pool Size Formula:

  connections = (core_count × 2) + effective_spindle_count

  Where:
    core_count            = number of CPU cores available to PostgreSQL
    effective_spindle_count = number of disk spindles (HDDs) actively serving I/O
                             (use 1 for SSDs, as they have no spindle)

  For a server with 4 CPU cores and SSD storage:
    connections = (4 × 2) + 1 = 9 ≈ 10 connections

  For a server with 8 CPU cores and SSD storage:
    connections = (8 × 2) + 1 = 17 ≈ 20 connections

  For a server with 16 CPU cores and 2 SSD arrays:
    connections = (16 × 2) + 2 = 34 ≈ 35 connections
```

This formula emerged from empirical observation: a PostgreSQL backend process spends time alternating between CPU-bound work (parsing, planning, executing) and I/O-bound work (waiting for disk reads). During the I/O wait, the CPU is free — and another backend process can use it. The formula accounts for this overlap: with N CPU cores, you can productively have 2N connections because at any moment roughly half of them are doing CPU work and half are waiting on I/O, keeping all CPUs busy without thrashing.

The `effective_spindle_count` adds headroom for disk parallelism — HDDs can physically seek to multiple locations if multiple requests are queued, but SSDs have such high parallelism internally that they effectively present as one "spindle" from the OS scheduler's perspective. For most modern cloud-hosted PostgreSQL (using SSD storage), the spindle count is 1.

### Why the Formula Gives Such Small Numbers

The result often surprises engineers: a powerful server with 8 cores should have only ~20 connections? Yes. And this is correct.

The confusion comes from conflating "concurrent connections to the database" with "concurrent requests my application handles." These are very different numbers. An application serving 10,000 requests per second does not need 10,000 database connections — because most of those requests are not executing database queries at any given moment. They are parsing HTTP headers, running business logic, serializing JSON, waiting on network I/O to the client. The fraction of time a request actively needs a database connection is small.

```
Why 20 Connections Can Serve Thousands of Requests/Second:

  Scenario:
    Application handles 5,000 requests/second
    Each request executes 2 database queries
    Each query takes 2ms to execute

    Time spent in DB per request: 2 queries × 2ms = 4ms
    Total request time: 20ms (4ms DB + 16ms other work)

    Fraction of time needing a DB connection: 4ms / 20ms = 20%

    At steady state, of 5,000 concurrent requests:
    5,000 × 20% = 1,000 requests actively using DB at any moment

    But those 1,000 are distributed over time:
    Each connection serves 1 query in 2ms → 500 queries/second/connection
    5,000 requests × 2 queries = 10,000 queries/second needed
    10,000 queries/second ÷ 500 queries/second/connection = 20 connections

    20 connections. For 5,000 requests/second.
    This is Little's Law applied to connection pools.
```

### Little's Law and the Queuing Theory Behind Pool Sizing

The calculation above is an application of **Little's Law** from queuing theory: in a stable system, the average number of items in the system (L) equals the average arrival rate (λ) times the average time an item spends in the system (W):

```
Little's Law: L = λ × W

  L = average number of connections in use (pool size needed)
  λ = query arrival rate (queries per second)
  W = average query execution time (seconds)

  Example:
    λ = 5,000 queries/second
    W = 2ms = 0.002 seconds
    L = 5,000 × 0.002 = 10 connections

    At peak, you need 10 connections to handle 5,000 queries/second
    with 2ms average latency. A pool of 20 gives comfortable headroom.

  Key insight: halving query execution time (through indexing, query
  optimization) halves the number of connections needed for the same
  throughput. Better queries reduce pool requirements.
```

Little's Law shows that **query optimization and pool sizing are linked**. A slow query (100ms) needs 50× more connections for the same throughput as a fast query (2ms). Optimizing queries reduces both latency and connection count simultaneously.

### Beyond the Formula: Empirical Calibration

The formula gives a starting point. Real production systems require calibration through measurement. The process is:

```
Pool Sizing Calibration Process:

  Step 1: Start with the formula result.
    8 CPU cores → initial pool size = 17 ≈ 20 connections

  Step 2: Instrument the pool.
    Monitor: active connections, idle connections, wait queue depth,
    connection acquisition latency, query throughput, query latency

  Step 3: Load test with realistic traffic.
    Run load at expected peak. Ramp up gradually.
    Watch for the inflection point where adding more connections
    INCREASES latency instead of decreasing it.

  Step 4: Find the optimal pool size.

    Pool too small (under-provisioned):
    Signs: high wait queue depth, connection acquisition latency > 1ms,
           frequent "connection pool timeout" errors, linear latency
           increase under load even at moderate connection utilization.

    Pool too large (over-provisioned):
    Signs: increasing query latency as pool grows (PostgreSQL overwhelmed),
           high idle connection count, memory pressure on DB server,
           diminishing throughput returns as pool grows.

    Optimal point: maximum throughput with minimum query latency.
    This is typically near (2 × CPU_cores) + 1.

  Step 5: Set pool size to optimal + 20% headroom.
    If optimal is 18, set pool to 20-22.
    The headroom absorbs short traffic spikes.
    Do NOT set it to 100 "just to be safe" — that defeats the purpose.

  Step 6: Monitor in production and re-calibrate quarterly.
    As query patterns change, traffic grows, or server specs change,
    the optimal pool size changes.
```

### The pool_size × instances Problem

In a horizontally-scaled deployment, pool size must be considered per-instance AND in aggregate:

```
Aggregate Connection Planning:

  Formula result: 20 connections optimal for this PostgreSQL server
  Application instances: 10 Kubernetes pods

  Option A: Each pod has pool size 20 → 10 × 20 = 200 total connections
            PostgreSQL is overwhelmed. Performance degrades.

  Option B: Each pod has pool size 2 → 10 × 2 = 20 total connections
            Too small per pod. Pods spend time waiting for connections.

  Option C: Use PgBouncer.
            Each pod connects to PgBouncer with pool size 50 (client connections).
            PgBouncer maintains 20 server connections to PostgreSQL.
            Total PostgreSQL connections: 20 (optimal).
            Total client connections PgBouncer handles: 10 × 50 = 500 (fine for PgBouncer).

  The correct answer when horizontal scaling:
    Total server-side connections = formula result (≈ 20)
    Use PgBouncer (or similar) to multiplex all app instances into that budget.
    Per-app-instance pool size is a client-side concern only.
```

## Chapter 7: Prepared Statements — Query Plans as Reusable Assets

### What a Prepared Statement Is

Every SQL query you send to PostgreSQL goes through five phases before a single row of data is touched: **parse** (tokenize and build a parse tree), **analyze** (resolve table and column names against the schema), **rewrite** (apply rules), **plan** (choose indexes and join strategies — the expensive phase), and **execute** (actually fetch the data). For a query you send once, all five phases are necessary. For a query you send a thousand times with different parameter values — the same SELECT with different WHERE conditions — the first four phases produce exactly the same result every time. You are paying for the same planning work repeatedly.

A **prepared statement** is a mechanism for caching the result of the first four phases (parse, analyze, rewrite, plan) and reusing it across multiple executions with different parameter values. The query is prepared once and executed many times, with only the execute phase repeating.

```
Without Prepared Statements (each query is a full round trip):

  App → PostgreSQL: "SELECT * FROM users WHERE id = 42"
  PostgreSQL: parse → analyze → rewrite → plan → execute
  PostgreSQL → App: [result]

  App → PostgreSQL: "SELECT * FROM users WHERE id = 17"
  PostgreSQL: parse → analyze → rewrite → plan → execute (again!)
  PostgreSQL → App: [result]

  Each query incurs full planning overhead.

With Prepared Statements:

  App → PostgreSQL: PREPARE user_by_id AS
                    "SELECT * FROM users WHERE id = $1"
  PostgreSQL: parse → analyze → rewrite → plan
                    (plan is stored in session memory)

  App → PostgreSQL: EXECUTE user_by_id(42)
  PostgreSQL: execute (reusing cached plan)
  PostgreSQL → App: [result]

  App → PostgreSQL: EXECUTE user_by_id(17)
  PostgreSQL: execute (reusing cached plan again)
  PostgreSQL → App: [result]

  Planning done once. Execution repeated cheaply.
```

### Server-Side vs. Client-Side Prepared Statements

There are two distinct levels at which prepared statements operate, and confusing them is a frequent source of bugs, especially when connection pooling is involved.

**Server-side (named) prepared statements** are named on the PostgreSQL server using the `PREPARE` SQL command. The prepared plan lives in the memory of a specific PostgreSQL backend process. It is session-scoped — it exists for the lifetime of the connection. This is the traditional form.

**Protocol-level (extended query) prepared statements** are a feature of PostgreSQL's wire protocol. When a client uses the extended query protocol (send a Parse message, then a Bind message with parameters, then an Execute message), PostgreSQL prepares and executes the statement in one logical operation. The driver can cache the prepared plan on the server, referenced by a statement name (or unnamed if each execution generates a fresh plan). This is what modern drivers like pgx and libpq use transparently.

```
Named Prepared Statements (SQL PREPARE):

  PREPARE user_by_id (INT) AS
    SELECT id, name, email FROM users WHERE id = $1;

  EXECUTE user_by_id(42);
  EXECUTE user_by_id(17);

  DEALLOCATE user_by_id;  -- free the plan

  Lives in: one specific backend process's memory.
  Scope: the current session/connection.
  Problem: if PgBouncer reassigns your connection (transaction mode),
           the new connection does not have this prepared statement.
           EXECUTE user_by_id fails with "prepared statement not found."

Extended Query Protocol (driver-level, transparent):

  The driver sends: Parse + Bind + Execute messages per query.
  The server parses and plans the Parse message.
  The driver can optionally name the plan for caching.

  pgx uses this protocol by default. The driver manages statement
  names and caching internally. Application code just calls:

  rows, err := pool.Query(ctx, "SELECT * FROM users WHERE id = $1", 42)

  pgx internally handles whether to prepare this statement or not,
  using cached plans when possible.
```

### How pgx Handles Prepared Statements

pgx has a sophisticated automatic prepared statement cache. By default, it uses the extended query protocol and caches prepared plans automatically, keyed by the SQL string. On the first execution of a query string, pgx sends a Parse message to PostgreSQL to prepare it. On subsequent executions of the same query string, pgx reuses the cached plan (sending only Bind + Execute messages, skipping Parse).

```go
// pgx automatically prepares and caches — no explicit PREPARE needed:
rows, err := conn.Query(ctx,
    "SELECT id, name FROM users WHERE department_id = $1",
    departmentID,
)
// First call: Parse + Bind + Execute (prepare and execute)
// Subsequent calls with same SQL: Bind + Execute (reuse plan)

// pgx's query execution modes:
config.DefaultQueryExecMode = pgx.QueryExecModeCacheStatement
// (default) — auto-prepare and cache statements server-side

config.DefaultQueryExecMode = pgx.QueryExecModeSimpleProtocol
// — use simple query protocol (no server-side caching)
// Required when using PgBouncer in transaction mode!

config.DefaultQueryExecMode = pgx.QueryExecModeDescribeExec
// — describe once per session, execute via extended protocol
// Does not create server-side prepared statements (compatible with PgBouncer)
```

### Prepared Statements and PgBouncer: The Compatibility Matrix

This is where the two features interact in ways that cause subtle production bugs:

```
Compatibility Matrix:

  PgBouncer Mode │ Named Prepared Stmts │ Extended Query Protocol
  ───────────────┼──────────────────────┼────────────────────────
  Session        │ ✓ Fully compatible   │ ✓ Fully compatible
                 │   (connection held   │
                 │   for entire session)│
  ───────────────┼──────────────────────┼────────────────────────
  Transaction    │ ✗ BROKEN             │ ✓/✗ Depends on driver
                 │   (connection        │   pgx: use SimpleProtocol
                 │   reassigned after   │   or DescribeExec mode
                 │   each transaction — │   HikariCP: disable server
                 │   prepared statement │   prep stmts
                 │   lost)              │
  ───────────────┼──────────────────────┼────────────────────────
  Statement      │ ✗ BROKEN             │ ✗ Limited compatibility
```

The standard advice for applications using PgBouncer in transaction mode (the most common production setup) is:

```go
// Go: configure pgx to be PgBouncer-compatible
connConfig, _ := pgx.ParseConfig(connString)
connConfig.DefaultQueryExecMode = pgx.QueryExecModeSimpleProtocol
// OR
connConfig.DefaultQueryExecMode = pgx.QueryExecModeDescribeExec
// (describes column types once per session, but does not create server-side
//  prepared statements — compatible with transaction mode pooling)
```

```java
// Java: disable server-side prepared statements when behind PgBouncer
HikariConfig config = new HikariConfig();
// Use "simple" query mode for PostgreSQL JDBC driver:
config.addDataSourceProperty("prepareThreshold", "0");
// prepareThreshold=0 means: never use server-side prepared statements.
// The JDBC driver will use simple queries (compatible with PgBouncer).
```

### The Query Planning Benefit in Detail

The performance gain from prepared statements depends heavily on query complexity. Simple queries (a primary key lookup) have trivial planning costs — the optimizer's decision is obvious. Complex queries (multi-table joins with subqueries, aggregations, correlated conditions) can have significant planning overhead.

```
Query Planning Time Examples:

  Query Type                    │ Parse+Plan Time │ Execute Time │ Prep Benefit
  ──────────────────────────────┼─────────────────┼──────────────┼─────────────
  Simple PK lookup              │ 0.1ms           │ 0.1ms        │ ~50% savings
  Single table filter           │ 0.2ms           │ 0.5ms        │ ~29% savings
  3-table JOIN with indexes     │ 1ms             │ 2ms          │ ~33% savings
  Complex analytical query      │ 10ms            │ 50ms         │ ~17% savings
  Simple insert                 │ 0.1ms           │ 0.1ms        │ ~50% savings

  For high-frequency simple queries (>10,000/sec), the cumulative
  planning overhead becomes significant:
  10,000 queries/sec × 0.1ms planning = 1 second of pure planning
  per second — the database is spending 100% of one CPU core just
  planning queries it has already planned thousands of times before.
```

### Generic Plans vs. Custom Plans

PostgreSQL makes a subtle but important decision when you use prepared statements: should it create a **custom plan** (one optimized for the specific parameter values of this execution) or a **generic plan** (one that works for all possible parameter values, possibly less optimal for any specific value)?

For the first five executions of a prepared statement, PostgreSQL always creates a custom plan (re-planning with the actual parameter values). On the sixth execution, PostgreSQL compares the cost of the generic plan against the average cost of the custom plans so far. If the generic plan is close in cost, it switches to always using the generic plan (saving re-planning time). If the generic plan would be significantly more expensive (because the data is skewed — e.g., 95% of users have `active=TRUE` and the query filters on `active=TRUE`, making an index scan always optimal), PostgreSQL continues using custom plans.

```sql
-- You can inspect which plan type PostgreSQL chose:
EXPLAIN (ANALYZE, BUFFERS) EXECUTE user_by_id(42);

-- Force generic plan (for testing):
SET plan_cache_mode = 'force_generic_plan';

-- Force custom plan (for highly skewed data):
SET plan_cache_mode = 'force_custom_plan';
-- Default (auto-select after 5 executions):
SET plan_cache_mode = 'auto';
```

The practical implication: for queries with highly skewed parameter distributions (e.g., `WHERE status = 'active'` where 99% of rows are active), prepared statements may sometimes produce worse plans than ad-hoc queries. In these cases, disabling prepared statements for those specific queries and using literal values instead (so the planner always sees the actual value) can be beneficial — at the cost of losing plan caching for them.

                                 ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │                  POSTGRESQL PRIMARY                             │

  The math works:
  - 10 pods, each handling hundreds of goroutines/threads
  - Each pod has 50 "client" connections to PgBouncer
  - PgBouncer multiplexes all of these into 20 PostgreSQL connections
  - PostgreSQL sees 20 connections — near its optimal sweet spot
  - Throughput is maximized; overhead is minimized

### The Checklist for Production Connection Management

```
Production Connection Management Checklist:

  Connection Pooling:
  □ Are you using a connection pool? (never raw connections per request)

  □ Is PgBouncer in transaction mode for maximum multiplexing?
  □ Have you disabled named prepared statements for PgBouncer compat?

  □ Active connections tracked?

```

## Epilogue: The Connection Is Infrastructure

A database connection is infrastructure, not plumbing. Plumbing you use and forget. Infrastructure you design, size, monitor, and maintain. Every architectural decision about your connection pool — the size, the mode, the timeouts, the placement of PgBouncer, the prepared statement strategy — has a direct, measurable impact on your system's throughput, latency, and reliability under load.

The engineer who treats connections as throwaway details — "just set the pool size to 100 and move on" — will eventually face mysterious performance degradation under load, connection exhaustion errors in production, and database servers consuming gigabytes of memory just holding idle connections. These are not mysterious. They are the predictable consequences of treating infrastructure casually.

The engineer who understands connection overhead, who sizes pools from first principles and validates with measurement, who knows why PgBouncer's transaction mode breaks named prepared statements and how to configure the driver accordingly, who monitors wait queue depth and connection lifetime metrics — that engineer's systems work correctly at scale, and keep working correctly as scale grows.

Connections are the first thing your application touches when it talks to the database. Getting them right is getting the foundation right. Everything else — queries, indexes, normalization — is built on top of this foundation. A cracked foundation undermines everything above it, no matter how carefully those upper layers were built.
