# Table Partitioning

### A Deep, Conceptual Journey from the Ground Up

> _Partitioning is not about splitting a table — it is about teaching the database which part of the table it does not need to look at._

---

## Preface: The Table That Became Too Heavy to Move

Imagine a table called `events` that has been accumulating user activity records for four years. It now contains three billion rows, consumes 2.4 terabytes of disk space, and holds indexes that are themselves hundreds of gigabytes. Running `VACUUM` on it takes twelve hours. Adding a new index takes days and locks out all writes during that window. A routine query that filters on the `created_at` column — even with a perfect index — takes several seconds because the index itself is so large that navigating it requires many I/O operations. And when January's data is legally required to be deleted after three years, the `DELETE FROM events WHERE created_at < '2021-01-01'` statement runs for six hours, generates enormous amounts of WAL, and causes visible latency spikes across the entire application.

Every one of these problems has the same root cause: the table is a single, monolithic structure. The database has no choice but to treat it as one giant object. Vacuum runs on the whole thing. Indexes span the whole thing. Queries must search the whole thing. Deletions must be written row-by-row through the whole thing.

**Partitioning** is the solution. It is the practice of dividing one logically large table into multiple physically smaller tables — called **partitions** — each containing a defined subset of the data. From the application's perspective, nothing changes: queries still target the parent table by name. But under the hood, PostgreSQL routes each query, insert, update, and delete to the appropriate partition, and can often skip partitions entirely when it knows they cannot contain relevant data.

The table that was too heavy to move becomes a collection of manageable pieces — each small enough to vacuum quickly, index efficiently, query fast, and drop instantly when its time comes.

## Chapter 1: The Concept of Partitioning

### What Partitioning Actually Is

In PostgreSQL's declarative partitioning system (introduced in PostgreSQL 10 and substantially improved through versions 11–14), a **partitioned table** is a special kind of table that acts as a logical parent. It has a schema — columns, data types, constraints — but it stores no data itself. All data lives in **partition tables**, which are child tables that each cover a specific range of the partition key's values.

The **partition key** is one or more columns whose values determine which partition a given row belongs to. Every row in the table is routed to exactly one partition based on its partition key value. PostgreSQL enforces this routing automatically: an `INSERT` into the parent table goes to the correct partition, an `UPDATE` that changes the partition key value moves the row to the new correct partition, and a query that filters on the partition key can skip all partitions that cannot possibly contain matching rows.

```
Partitioning Conceptual Model:

  Logical view (what the application sees):
  ┌──────────────────────────────────────────┐
  │          events (parent table)            │
  │  id │ user_id │ event_type │ created_at  │
  │  No data stored here — schema only       │
  └──────────────────────────────────────────┘
                     │
       ┌─────────────┼─────────────┐
       │             │             │
       ▼             ▼             ▼
  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │events_  │  │events_  │  │events_  │
  │2022     │  │2023     │  │2024     │
  │(real    │  │(real    │  │(real    │
  │ data)   │  │ data)   │  │ data)   │
  └─────────┘  └─────────┘  └─────────┘
  Rows where    Rows where    Rows where
  created_at    created_at    created_at
  is in 2022    is in 2023    is in 2024

  Physical reality (what the database sees):
  Three separate heap files, three separate index files.
  Each one manageable independently.
```

### The Partition Key and the Partition Bound

Every partition is defined by its **partition bound** — the rule that specifies which values of the partition key belong to this partition. For range partitioning, the bound is an interval (`FROM '2022-01-01' TO '2023-01-01'`). For list partitioning, it is a set of values (`IN ('US', 'CA', 'MX')`). For hash partitioning, it is a remainder (`MODULUS 4 REMAINDER 0`).

The partition bounds of all partitions within a partitioned table must collectively be **non-overlapping** (no row can belong to two partitions) and, depending on the partitioning strategy, may need to cover all possible values (though a `DEFAULT` partition can catch anything that does not fit another partition).

### Why Partitioning Helps: The Four Benefits

Understanding why you partition something — not just how — makes the design decisions that follow much clearer.

**Partition pruning (query performance):** When a query includes a filter on the partition key, PostgreSQL can eliminate entire partitions from consideration at planning time. If you query for events from 2024 and you have twelve monthly partitions, PostgreSQL can instantly determine that eleven of those partitions cannot possibly contain 2024 data — and skip them entirely. The query touches only the relevant partition(s), with proportionally smaller indexes and less I/O.

**Maintenance efficiency:** `VACUUM`, `ANALYZE`, `REINDEX`, and `CLUSTER` operations run per-table. On a partitioned table, they can be run on individual partitions independently — during off-peak hours, in parallel, on a rotating schedule. A `VACUUM` on a 50GB partition takes a fraction of the time it would take on a 2.4TB monolithic table.

**Instant data lifecycle management:** Dropping or archiving old data is operationally painful on a monolithic table (row-by-row DELETE generates enormous WAL, causes replication lag, and takes hours). With range-partitioned time-series data, dropping an entire month of old data is a metadata operation: `DROP TABLE events_2021_01` (or `DETACH PARTITION`) takes milliseconds, generates negligible WAL, and does not impact ongoing queries.

**Parallel operations:** PostgreSQL can parallelize queries across partitions, running scans on multiple partitions simultaneously using parallel workers. For analytical queries that touch many partitions, this can provide substantial speedup on multi-core servers.

## Chapter 2: Range Partitioning

### The Most Natural Partitioning Strategy for Time-Series Data

**Range partitioning** divides data based on a column (or combination of columns) whose values fall into non-overlapping, ordered intervals. Each partition owns a specific range: "from this value, up to but not including that value." Range partitioning is the most intuitive and the most commonly used strategy, particularly for time-series data where rows are naturally ordered by timestamp.

The key insight of range partitioning is that it aligns the physical organization of data with the temporal or sequential nature of queries. Most queries against time-series data filter by time: "give me everything from last week," "show me today's events," "calculate monthly revenue for Q3." When the data is range-partitioned by time, these queries touch only the partitions that cover the requested time range — everything else is invisible to the query planner.

### Creating a Range-Partitioned Table

```sql
-- Step 1: Create the parent (partitioned) table
-- PARTITION BY RANGE declares the partitioning strategy and key column
CREATE TABLE events (
    id          BIGSERIAL,
    user_id     BIGINT          NOT NULL,
    event_type  VARCHAR(100)    NOT NULL,
    payload     JSONB,
    created_at  TIMESTAMPTZ     NOT NULL,
    -- Note: PRIMARY KEY must include the partition key (created_at)
    -- because uniqueness can only be enforced within each partition
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- Step 2: Create individual partition tables
-- Each partition specifies its range with FROM ... TO ...
-- The range is inclusive of FROM, exclusive of TO (half-open interval)

CREATE TABLE events_2024_q1 PARTITION OF events
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');

CREATE TABLE events_2024_q2 PARTITION OF events
    FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');

CREATE TABLE events_2024_q3 PARTITION OF events
    FOR VALUES FROM ('2024-07-01') TO ('2024-10-01');

CREATE TABLE events_2024_q4 PARTITION OF events
    FOR VALUES FROM ('2024-10-01') TO ('2025-01-01');

-- Step 3: Create indexes
-- Indexes on the parent table are automatically created on all current
-- and FUTURE partitions (PostgreSQL 11+)
CREATE INDEX idx_events_user_id    ON events (user_id);
CREATE INDEX idx_events_event_type ON events (event_type);
CREATE INDEX idx_events_created_at ON events (created_at);
-- These three index CREATE statements create 4 indexes each
-- (one per partition) — 12 indexes total, each on a small partition

-- Step 4: Optional — a DEFAULT partition to catch out-of-range values
-- Without this, inserting a row with created_at outside all defined
-- partition bounds raises an error
CREATE TABLE events_default PARTITION OF events DEFAULT;
```

### Range Partitioning in Action

```sql
-- INSERT is automatically routed to the correct partition:
INSERT INTO events (user_id, event_type, created_at)
VALUES (42, 'page_view', '2024-07-15 10:30:00+00');
-- This row goes to events_2024_q3 (July is in Q3 range)

-- The application never needs to know which partition:
SELECT COUNT(*) FROM events
WHERE created_at BETWEEN '2024-07-01' AND '2024-07-31';
-- PostgreSQL plans this against events_2024_q3 ONLY
-- events_2024_q1, events_2024_q2, events_2024_q4 are PRUNED

-- Verify partition pruning with EXPLAIN:
EXPLAIN (ANALYZE, COSTS OFF)
SELECT COUNT(*) FROM events
WHERE created_at >= '2024-07-01' AND created_at < '2024-08-01';

-- Output shows:
-- Aggregate
--   ->  Append
--         ->  Seq Scan on events_2024_q3
--               Filter: (created_at >= '2024-07-01' AND created_at < '2024-08-01')
-- (events_2024_q1, q2, q4 do NOT appear — they are pruned)
```

### Range Partitioning on Non-Timestamp Columns

Range partitioning is not limited to timestamps. Any ordered data type can be the partition key:

```sql
-- Range partitioning on integer ranges (e.g., order ID ranges):
CREATE TABLE orders (
    order_id    BIGINT          NOT NULL,
    customer_id BIGINT          NOT NULL,
    total       NUMERIC(12,2)   NOT NULL,
    status      VARCHAR(20)     NOT NULL,
    PRIMARY KEY (order_id)
) PARTITION BY RANGE (order_id);

CREATE TABLE orders_0_to_1m    PARTITION OF orders
    FOR VALUES FROM (1)         TO (1000001);
CREATE TABLE orders_1m_to_2m   PARTITION OF orders
    FOR VALUES FROM (1000001)   TO (2000001);
CREATE TABLE orders_2m_to_3m   PARTITION OF orders
    FOR VALUES FROM (2000001)   TO (3000001);

-- Range partitioning on text (alphabetical ranges — less common):
CREATE TABLE customers (
    id      BIGINT NOT NULL,
    surname VARCHAR(100) NOT NULL,
    PRIMARY KEY (id, surname)
) PARTITION BY RANGE (surname);

CREATE TABLE customers_a_m  PARTITION OF customers
    FOR VALUES FROM ('A') TO ('N');
CREATE TABLE customers_n_z  PARTITION OF customers
    FOR VALUES FROM ('N') TO (MAXVALUE);
```

### Handling the Partition Boundary Carefully

The range bound is a half-open interval: `FROM` value is **inclusive**, `TO` value is **exclusive**. A row with `created_at = '2024-04-01 00:00:00'` belongs to `events_2024_q2` (which starts at `'2024-04-01'`), not `events_2024_q1` (which ends at `'2024-04-01'`). This is the correct and intuitive behavior for date ranges — the end of one quarter is exactly the start of the next, with no gap and no overlap.

```
Range Boundary Visualization:

  events_2024_q1:  [ '2024-01-01' ──────────────── '2024-04-01' )
  events_2024_q2:                [ '2024-04-01' ──────────────── '2024-07-01' )
  events_2024_q3:                               [ '2024-07-01' ──────────────── '2024-10-01' )

  Row with created_at = '2024-04-01 00:00:01'  → goes to events_2024_q2 ✓
  Row with created_at = '2024-03-31 23:59:59'  → goes to events_2024_q1 ✓
  Row with created_at = '2024-04-01 00:00:00'  → goes to events_2024_q2 ✓
  (The TO bound is exclusive — '2024-04-01' itself belongs to q2)
```

## Chapter 3: List Partitioning

### Partitioning by Discrete, Named Values

**List partitioning** divides data based on specific, enumerated values of the partition key. Instead of ranges, each partition owns an explicit list of values: "this partition contains rows where `region = 'US'` or `region = 'CA'`." List partitioning is the natural fit when your data divides into distinct, named categories — geographic regions, status codes, product types, tenant identifiers.

The fundamental difference from range partitioning is that list partition values are not ordered. There is no sense in which 'US' comes before 'EU' the way January comes before February. List partitions group rows by categorical identity, not by position in a sequence.

### Creating a List-Partitioned Table

```sql
-- Multi-tenant SaaS: partition by region for data residency requirements
CREATE TABLE user_profiles (
    id          BIGINT          NOT NULL,
    tenant_id   BIGINT          NOT NULL,
    username    VARCHAR(100)    NOT NULL,
    email       VARCHAR(255)    NOT NULL,
    region      VARCHAR(10)     NOT NULL,   -- 'US', 'EU', 'APAC', 'LATAM'
    created_at  TIMESTAMPTZ     NOT NULL,
    PRIMARY KEY (id, region)
) PARTITION BY LIST (region);

-- Each partition owns specific values
CREATE TABLE user_profiles_us PARTITION OF user_profiles
    FOR VALUES IN ('US', 'CA', 'MX');       -- North American users

CREATE TABLE user_profiles_eu PARTITION OF user_profiles
    FOR VALUES IN ('GB', 'DE', 'FR', 'NL', 'SE', 'IT', 'ES', 'PL');

CREATE TABLE user_profiles_apac PARTITION OF user_profiles
    FOR VALUES IN ('JP', 'AU', 'SG', 'KR', 'IN', 'CN', 'NZ');

CREATE TABLE user_profiles_latam PARTITION OF user_profiles
    FOR VALUES IN ('BR', 'AR', 'CL', 'CO', 'PE');

-- Default partition for any region not explicitly listed:
CREATE TABLE user_profiles_other PARTITION OF user_profiles DEFAULT;
```

### List Partitioning for Status or Type Columns

```sql
-- Order processing: partition by order status
-- (different statuses have very different query and access patterns)
CREATE TABLE order_events (
    id          BIGSERIAL       NOT NULL,
    order_id    BIGINT          NOT NULL,
    event_type  VARCHAR(50)     NOT NULL,
    status      VARCHAR(20)     NOT NULL,
    occurred_at TIMESTAMPTZ     NOT NULL,
    PRIMARY KEY (id, status)
) PARTITION BY LIST (status);

CREATE TABLE order_events_active PARTITION OF order_events
    FOR VALUES IN ('pending', 'confirmed', 'processing', 'shipped');
-- Frequently queried, frequently updated — kept on fast SSD storage

CREATE TABLE order_events_terminal PARTITION OF order_events
    FOR VALUES IN ('delivered', 'cancelled', 'refunded', 'returned');
-- Rarely updated, mostly read — can be on cheaper storage
-- (PostgreSQL tablespaces allow per-partition storage tiers)

-- Verify which partition a value routes to:
EXPLAIN SELECT * FROM order_events WHERE status = 'pending';
-- Shows: Seq Scan on order_events_active
-- (order_events_terminal is pruned — 'pending' is not in its list)
```

### The Key Consideration: Value Exclusivity

Each value can appear in exactly one partition's list. If you add 'MX' to both `user_profiles_us` and a hypothetical `user_profiles_latam_mx` partition, PostgreSQL raises an error at partition creation time:

```sql
-- This FAILS:
CREATE TABLE user_profiles_test PARTITION OF user_profiles
    FOR VALUES IN ('MX', 'BR');  -- 'MX' is already in user_profiles_us
-- ERROR: partition "user_profiles_test" would overlap partition "user_profiles_us"
-- DETAIL: Partition constraint: ((region IS NOT NULL) AND
--         (region = ANY (ARRAY['US', 'CA', 'MX'])))

-- To move a value from one partition to another, you must:
-- 1. Detach the old partition
-- 2. Migrate the rows with the value to the new partition
-- 3. Reattach with updated bounds
-- OR recreate with a migration window
```

## Chapter 4: Hash Partitioning

### When You Have No Natural Partitioning Dimension

Range partitioning requires an ordered key (timestamps, IDs, numbers). List partitioning requires a categorical key (status, region, type). But sometimes your data has neither — it is uniformly distributed with no natural division that would make some partitions busier than others, and no obvious categorical grouping. In these cases, **hash partitioning** distributes data evenly across a fixed number of partitions based on a hash of the partition key.

Hash partitioning computes `hash(key) % N` for each row, where N is the total number of partitions (the modulus). Each partition owns one specific remainder value. Because hash functions distribute values uniformly, the data is spread roughly evenly across all partitions regardless of the key's actual distribution.

### When Hash Partitioning Makes Sense

Hash partitioning is primarily useful for:

**Distributing large lookup tables evenly:** A `users` table with 500 million rows and no natural ordering dimension. Hash partition on `user_id` — queries that filter on `user_id` (the most common access pattern) will always hit exactly one partition.

**Reducing index and vacuum contention:** When many concurrent transactions update different rows, they compete for shared buffers and lock table entries. Partitioning by hash distributes this contention across multiple smaller heap files and index structures.

**Pre-sharding for future horizontal distribution:** Applications planning to move to a distributed database (Citus, Greenplum) can pre-shard data using hash partitioning that aligns with the distributed system's approach.

```sql
-- Hash partitioning: distribute users evenly across 8 partitions
CREATE TABLE users (
    id          BIGINT          NOT NULL,
    username    VARCHAR(100)    NOT NULL UNIQUE,  -- note: UNIQUE across all partitions
    email       VARCHAR(255)    NOT NULL,
    created_at  TIMESTAMPTZ     NOT NULL,
    PRIMARY KEY (id)            -- hash key must be in PK for global uniqueness
) PARTITION BY HASH (id);

-- MODULUS = total number of partitions
-- REMAINDER = which partition (0 to MODULUS-1)
CREATE TABLE users_p0 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE users_p1 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 1);
CREATE TABLE users_p2 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 2);
CREATE TABLE users_p3 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 3);
CREATE TABLE users_p4 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 4);
CREATE TABLE users_p5 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 5);
CREATE TABLE users_p6 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 6);
CREATE TABLE users_p7 PARTITION OF users
    FOR VALUES WITH (MODULUS 8, REMAINDER 7);

-- Query by the hash key — only ONE partition is scanned:
EXPLAIN SELECT * FROM users WHERE id = 12345;
-- PostgreSQL computes hash(12345) % 8 = 5 (hypothetically)
-- Output: Seq Scan on users_p5
-- All other 7 partitions are pruned.

-- Query WITHOUT the hash key — ALL partitions must be scanned:
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
-- Output: Append → Seq Scan on users_p0
--                → Seq Scan on users_p1
--                → ...all 8 partitions
-- No pruning possible — hash does not help non-hash-key queries.
```

### The Critical Limitation of Hash Partitioning

Hash partitioning only prunes partitions when the query filter is on the exact partition key with an equality condition. Range queries (`WHERE id BETWEEN 1000 AND 2000`) and filters on non-key columns touch all partitions. This is fundamentally different from range partitioning, where range queries on the key column naturally prune many partitions.

```
Hash Partitioning Pruning Behavior:

  Query: WHERE id = 12345          → 1 partition scanned  ✓ (pruned 7)
  Query: WHERE id IN (1, 2, 3)     → 3 partitions scanned ✓ (pruned 5, if remainders differ)
  Query: WHERE id > 10000          → ALL 8 partitions     ✗ (no pruning — range on hash)
  Query: WHERE email = 'alice@...' → ALL 8 partitions     ✗ (no pruning — not the hash key)
  Query: (no WHERE clause)         → ALL 8 partitions     ✗ (full table scan)
```

### Adding Hash Partitions Later: The Modulus Challenge

Hash partitioning has a significant operational limitation that does not exist for range or list: **you cannot add partitions without resharding the entire table**. With range partitioning, adding a new time period partition is trivial — it simply covers a future range that did not exist before. With hash partitioning, if you want to go from 8 to 16 partitions, the `MODULUS` changes, and every existing row must be re-evaluated and potentially moved to a different partition.

This means the number of hash partitions must be chosen carefully upfront, with future growth in mind. Choose a number that provides enough parallelism and size control now (8, 16, 32 are common choices), but accept that increasing it later is a significant migration project.

## Chapter 5: Composite Partitioning

### Partitioning on Multiple Dimensions Simultaneously

**Composite partitioning** (also called sub-partitioning) is the practice of applying one partitioning strategy to a table, and then applying a second partitioning strategy to each resulting partition. This creates a two-level partition tree: the top level divides by one dimension, and the second level divides each top-level partition by a second dimension.

Composite partitioning is appropriate when data has two strong, independent partitioning dimensions — where filtering on both together yields dramatically smaller scan sets than filtering on either one alone.

### The Classic Composite: Range-then-Hash or Range-then-List

The most common composite pattern is **range at the top level** (partitioned by time) with **hash or list at the second level** (partitioned by tenant or category):

```sql
-- Range (by month) + List (by region):
-- Useful for a multi-regional SaaS with data residency requirements
-- AND time-based data lifecycle management

-- Step 1: Create parent table with top-level range partitioning by month:
CREATE TABLE metrics (
    id          BIGSERIAL       NOT NULL,
    tenant_id   BIGINT          NOT NULL,
    metric_name VARCHAR(100)    NOT NULL,
    value       NUMERIC(20,6)   NOT NULL,
    region      VARCHAR(10)     NOT NULL,
    recorded_at TIMESTAMPTZ     NOT NULL,
    PRIMARY KEY (id, recorded_at, region)
) PARTITION BY RANGE (recorded_at);

-- Step 2: Create monthly partitions (top level) — each is itself partitioned:
CREATE TABLE metrics_2024_01 PARTITION OF metrics
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01')
    PARTITION BY LIST (region);   -- sub-partition by region

CREATE TABLE metrics_2024_02 PARTITION OF metrics
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01')
    PARTITION BY LIST (region);

-- Step 3: Create second-level partitions within each monthly partition:
CREATE TABLE metrics_2024_01_us PARTITION OF metrics_2024_01
    FOR VALUES IN ('US', 'CA', 'MX');

CREATE TABLE metrics_2024_01_eu PARTITION OF metrics_2024_01
    FOR VALUES IN ('GB', 'DE', 'FR', 'NL');

CREATE TABLE metrics_2024_01_apac PARTITION OF metrics_2024_01
    FOR VALUES IN ('JP', 'AU', 'SG', 'KR');

CREATE TABLE metrics_2024_02_us PARTITION OF metrics_2024_02
    FOR VALUES IN ('US', 'CA', 'MX');

CREATE TABLE metrics_2024_02_eu PARTITION OF metrics_2024_02
    FOR VALUES IN ('GB', 'DE', 'FR', 'NL');
-- ... and so on

-- Total leaf partitions: 12 months × 3 regions = 36 leaf tables

-- Query with both filters applied:
EXPLAIN SELECT * FROM metrics
WHERE recorded_at >= '2024-01-01' AND recorded_at < '2024-02-01'
  AND region = 'US';
-- PostgreSQL prunes to: metrics_2024_01_us ONLY
-- 35 out of 36 partitions are skipped entirely.
```

### Range-then-Hash: Uniform Distribution Within Time Periods

Another valuable composite is **range-then-hash**, which distributes data evenly within each time period to avoid hot spots on the most recent partition:

```sql
-- Orders partitioned by quarter (range), then by hash of order_id
-- Prevents the current quarter's partition from being a write hot spot

CREATE TABLE orders (
    order_id    BIGINT          NOT NULL,
    customer_id BIGINT          NOT NULL,
    total       NUMERIC(12,2)   NOT NULL,
    created_at  TIMESTAMPTZ     NOT NULL,
    PRIMARY KEY (order_id, created_at)
) PARTITION BY RANGE (created_at);

-- Create quarterly range partitions, each sub-partitioned by hash:
CREATE TABLE orders_2024_q1 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01')
    PARTITION BY HASH (order_id);

-- 4 hash sub-partitions per quarter:
CREATE TABLE orders_2024_q1_p0 PARTITION OF orders_2024_q1
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE orders_2024_q1_p1 PARTITION OF orders_2024_q1
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE orders_2024_q1_p2 PARTITION OF orders_2024_q1
    FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE orders_2024_q1_p3 PARTITION OF orders_2024_q1
    FOR VALUES WITH (MODULUS 4, REMAINDER 3);

-- Query pruning:
-- WHERE created_at IN Q1 AND order_id = 12345
-- → Prunes to 1 leaf partition (correct quarter + correct hash remainder)
-- 15 of 16 leaf partitions are pruned
```

### When to Use Composite Partitioning

Composite partitioning adds complexity — more partition objects, more naming conventions, more maintenance steps. It is worth the overhead only when both dimensions genuinely matter for query performance or data lifecycle:

```
Composite Partitioning Decision:

  Good fit:
  ✓ "Find all metrics for tenant X in month Y" — both dimensions filter heavily
  ✓ "Delete all data for region EU for 2022" — drop one regional sub-partition per month
  ✓ Write-heavy workloads where hash sub-partitioning reduces contention

  Poor fit:
  ✗ Queries almost always filter on only one dimension (just use simple partitioning)
  ✗ You do not need sub-partition-level lifecycle management
  ✗ The resulting leaf partition count is very large (>100s) and
    planning overhead becomes measurable
```

## Chapter 6: Partition Pruning

### The Engine That Makes Partitioning Worthwhile

Partition pruning is the optimizer's ability to eliminate partitions from a query plan when it can prove that those partitions cannot contain rows matching the query's conditions. Without pruning, every query against a partitioned table would scan all partitions — which would often be slower than a monolithic table because of the overhead of the `Append` node that combines results from multiple child scans.

Pruning is what transforms the overhead of partition management into a performance benefit. A query that touches 1 out of 100 partitions is, effectively, a query against a table that is 1% the size of the full dataset — with proportionally smaller indexes, fewer I/O operations, and lower memory pressure.

### Static Pruning vs. Runtime Pruning

PostgreSQL performs two types of pruning at different stages of query execution:

**Static pruning (planning time):** The optimizer examines the query's WHERE clause at plan time. If the filter includes a literal value or a stable function (like `NOW()` or `CURRENT_DATE`) that can be evaluated at plan time, PostgreSQL immediately determines which partitions are relevant and includes only those in the plan. Pruned partitions do not appear in the EXPLAIN output at all.

**Runtime pruning (execution time, PostgreSQL 11+):** When the filter value is not known at plan time — for example, when the partition key is compared to a function parameter or a parameterized query placeholder (`$1`) — PostgreSQL cannot prune at plan time. But PostgreSQL 11 introduced runtime pruning: partition elimination that happens at execution time, when the actual parameter values are available. This allows prepared statements and stored procedures to benefit from pruning even though the query is planned once and executed many times with different parameter values.

```sql
-- Static pruning (value known at plan time):
EXPLAIN SELECT * FROM events WHERE created_at >= '2024-07-01';
-- The literal '2024-07-01' is known at plan time.
-- PostgreSQL immediately eliminates Q1 and Q2 partitions.
-- Plan includes: events_2024_q3, events_2024_q4 (and default)

-- Runtime pruning (value not known at plan time):
PREPARE find_events AS
    SELECT * FROM events WHERE created_at >= $1;
EXPLAIN EXECUTE find_events('2024-07-01');
-- Parameter $1 is evaluated at runtime.
-- PostgreSQL uses runtime pruning: eliminates partitions at execution time.
-- Plan shows runtime filter, not compile-time elimination.
-- (enable_partition_pruning must be ON — the default)

-- Verify pruning is enabled:
SHOW enable_partition_pruning;   -- should be 'on'

-- Force disable pruning (for testing/comparison only):
SET enable_partition_pruning = off;
EXPLAIN SELECT * FROM events WHERE created_at >= '2024-07-01';
-- Now shows ALL partitions — demonstrates the cost without pruning.
SET enable_partition_pruning = on;
```

### What Prevents Pruning: Common Gotchas

Understanding what breaks pruning is just as important as understanding what enables it. Several common mistakes prevent the optimizer from pruning:

**Using a function that wraps the partition key:**

```sql
-- BAD: Function on the partition key prevents pruning
EXPLAIN SELECT * FROM events
WHERE DATE_TRUNC('month', created_at) = '2024-07-01';
-- DATE_TRUNC() wraps created_at — PostgreSQL cannot see through it.
-- ALL partitions are scanned. No pruning.

-- GOOD: Keep the partition key bare, transform the constant instead
EXPLAIN SELECT * FROM events
WHERE created_at >= '2024-07-01' AND created_at < '2024-08-01';
-- created_at is bare. Constants are on the other side of the comparison.
-- Only the July-containing partition is scanned. Pruning works. ✓
```

**Implicit type coercion on the partition key:**

```sql
-- BAD: The partition key is TIMESTAMPTZ but the constant is DATE
-- Some databases coerce the column, preventing pruning
EXPLAIN SELECT * FROM events
WHERE created_at::DATE = '2024-07-15';
-- ::DATE cast on the column prevents pruning.

-- GOOD: Cast the constant, not the column
EXPLAIN SELECT * FROM events
WHERE created_at >= '2024-07-15'::TIMESTAMPTZ
  AND created_at <  '2024-07-16'::TIMESTAMPTZ;
-- No cast on the column. Pruning works. ✓
```

**Joining on the partition key without providing a constant:**

```sql
-- A join where the partition key is compared to another table's column
-- cannot be pruned at plan time (the value is not a constant).
-- Runtime pruning may apply in some cases, but not always.
EXPLAIN SELECT e.* FROM events e
JOIN date_ranges dr ON e.created_at BETWEEN dr.start_date AND dr.end_date
WHERE dr.range_name = 'Q3_2024';
-- Without knowing dr.start_date and dr.end_date at plan time,
-- PostgreSQL may not prune effectively.
-- Prefer: resolve the date range in application code, pass as literals.
```

### The Partition Pruning Report in EXPLAIN

Reading EXPLAIN output for partitioned tables requires knowing what to look for:

```sql
EXPLAIN (ANALYZE, VERBOSE, FORMAT TEXT)
SELECT COUNT(*) FROM events
WHERE created_at >= '2024-07-01' AND created_at < '2024-10-01';

-- Output (simplified):
-- Aggregate
--   ->  Append
--         Subplans Removed: 3      ← THIS LINE shows pruning happened
--         ->  Seq Scan on events_2024_q3
--               Filter: (created_at >= '2024-07-01' AND created_at < '2024-10-01')
--               Rows Removed by Filter: 0
-- Planning Time: 2.1 ms
-- Execution Time: 45.2 ms

-- "Subplans Removed: 3" means 3 partitions were pruned.
-- Only events_2024_q3 was scanned (July through September).
```

## Chapter 7: Partition Maintenance

### Adding New Partitions

For time-partitioned tables, adding new partitions is a regular operational task — typically done weekly or monthly, creating the next period's partition before data starts arriving for it.

```sql
-- Add a new quarterly partition before the quarter begins:
CREATE TABLE events_2025_q1 PARTITION OF events
    FOR VALUES FROM ('2025-01-01') TO ('2025-04-01');
-- Instant operation — creates metadata only. No data movement.

-- The new partition immediately inherits all indexes defined on the parent:
-- idx_events_user_id, idx_events_event_type, idx_events_created_at
-- are all created on events_2025_q1 automatically (PostgreSQL 11+)

-- Automate partition creation with a stored procedure:
CREATE OR REPLACE PROCEDURE create_monthly_partition(
    partition_date DATE
)
LANGUAGE plpgsql AS $$
DECLARE
    partition_name TEXT;
    start_date     DATE;
    end_date       DATE;
BEGIN
    partition_name := 'events_' || TO_CHAR(partition_date, 'YYYY_MM');
    start_date     := DATE_TRUNC('month', partition_date);
    end_date       := DATE_TRUNC('month', partition_date) + INTERVAL '1 month';

    EXECUTE format(
        'CREATE TABLE %I PARTITION OF events
         FOR VALUES FROM (%L) TO (%L)',
        partition_name, start_date, end_date
    );

    RAISE NOTICE 'Created partition: % (% to %)',
        partition_name, start_date, end_date;
END;
$$;

-- Usage: call once a month (via pg_cron, cron job, or application scheduler)
CALL create_monthly_partition('2025-02-01');
-- Creates events_2025_02 covering February 2025
```

### The DEFAULT Partition and Its Implications

A DEFAULT partition catches any row whose value does not match any other partition's bound. It is valuable insurance against missing partitions (rows do not fail to insert just because you forgot to create next month's partition), but it has an important operational implication: **you cannot add a new range partition if the DEFAULT partition might contain rows that would belong to the new partition**.

```sql
-- Scenario: default partition has accumulated rows from November 2024
-- (because the November partition was never created)

-- Attempting to add November partition FAILS:
CREATE TABLE events_2024_11 PARTITION OF events
    FOR VALUES FROM ('2024-11-01') TO ('2024-12-01');
-- ERROR: updated partition constraint for default partition "events_default"
-- would be violated by some row

-- Correct process:
-- Step 1: Move November rows from default to the new partition
BEGIN;
  -- Create the new partition
  CREATE TABLE events_2024_11 (LIKE events);  -- standalone table with same schema
  -- Move data from default partition to new table
  INSERT INTO events_2024_11
    SELECT * FROM events_default
    WHERE created_at >= '2024-11-01' AND created_at < '2024-12-01';
  -- Delete moved rows from default
  DELETE FROM events_default
    WHERE created_at >= '2024-11-01' AND created_at < '2024-12-01';
COMMIT;

-- Step 2: Attach the new table as a partition
ALTER TABLE events ATTACH PARTITION events_2024_11
    FOR VALUES FROM ('2024-11-01') TO ('2024-12-01');
-- ATTACH validates that all rows in events_2024_11 satisfy the bound.
-- This requires a SHARE UPDATE EXCLUSIVE lock but no full table lock.
```

### Detaching Partitions — The Power of Instant Data Separation

**Detaching** a partition removes it from the partitioned table hierarchy without deleting any data. The detached partition becomes an independent, ordinary table. This is one of the most powerful partition maintenance operations because it is nearly instantaneous — it is a metadata change, not a data movement.

Detaching is useful for:

- **Archiving:** Move old data to cold storage (a different tablespace or a compressed format) while keeping it queryable.
- **Point-in-time recovery staging:** Detach a partition, copy it to another location, reattach.
- **Bulk export:** Detach a partition to run `pg_dump` on it without locking the whole parent table.
- **Bulk migration:** Move data between PostgreSQL instances partition-by-partition.

```sql
-- Detach January 2022's partition (it is now 3 years old and rarely accessed):
ALTER TABLE events DETACH PARTITION events_2022_01;
-- Duration: milliseconds.
-- events_2022_01 is now a standalone table.
-- Queries against the parent 'events' no longer scan events_2022_01.

-- The data is still there and fully queryable:
SELECT COUNT(*) FROM events_2022_01;  -- works fine

-- Options after detaching:
-- Option A: Archive to a tablespace with cheap storage
ALTER TABLE events_2022_01 SET TABLESPACE cold_storage_tablespace;

-- Option B: Compress the data (pg_compress extension or pg_dump then restore compressed)

-- Option C: Export and delete
COPY events_2022_01 TO '/archive/events_2022_01.csv' WITH CSV HEADER;
DROP TABLE events_2022_01;

-- Option D: Re-attach later if needed for historical queries
ALTER TABLE events ATTACH PARTITION events_2022_01
    FOR VALUES FROM ('2022-01-01') TO ('2022-02-01');
-- Re-attachment requires constraint validation (see below)

-- CONCURRENT detach (PostgreSQL 14+): avoids long locks
ALTER TABLE events DETACH PARTITION events_2022_01 CONCURRENTLY;
-- Takes only lightweight locks during finalization.
-- Safer for high-traffic production tables.
```

### Dropping Partitions — Instant Bulk Delete

**Dropping** a partition is the fastest way to delete large amounts of old data. It is a metadata operation that removes the partition file entirely, with no row-by-row deletion, no index updates, and minimal WAL generation. A partition containing billions of rows can be dropped in milliseconds.

This is the primary advantage of range partitioning for time-series data: instead of running `DELETE FROM events WHERE created_at < '2022-01-01'` (which might take hours and generate gigabytes of WAL), you simply drop the old partition tables.

```sql
-- Drop January 2022's partition (data is permanently deleted):
DROP TABLE events_2022_01;
-- Duration: milliseconds, regardless of how many rows it contained.
-- Generates minimal WAL (just the table drop metadata).
-- No row-by-row deletion. No index cleanup per row.
-- The disk space is reclaimed immediately (or returned to OS asap).

-- The contrast with DELETE:
-- DELETE FROM events WHERE created_at < '2022-02-01';
-- If events_2022_01 has 500 million rows:
--   Duration: hours
--   WAL generated: potentially hundreds of gigabytes
--   VACUUM required afterward to reclaim dead space
--   Replication lag during the operation: significant
--
-- DROP TABLE events_2022_01:
--   Duration: milliseconds
--   WAL generated: negligible
--   No VACUUM needed
--   Minimal replication impact

-- Standard data retention pattern (run monthly via pg_cron):
-- Keep 24 months of data. Drop anything older.
DO $$
DECLARE
    cutoff_date DATE := DATE_TRUNC('month', NOW() - INTERVAL '24 months');
    partition_name TEXT;
BEGIN
    -- Construct the partition name for the oldest month to delete
    partition_name := 'events_' || TO_CHAR(cutoff_date, 'YYYY_MM');
    -- Check if it exists before dropping
    IF EXISTS (
        SELECT 1 FROM pg_class WHERE relname = partition_name
    ) THEN
        EXECUTE format('DROP TABLE %I', partition_name);
        RAISE NOTICE 'Dropped partition: %', partition_name;
    END IF;
END;
$$;
```

### Attaching Existing Tables as Partitions

Sometimes you want to add data to a partitioned table from an existing standalone table — for example, loading a month of historical data that was prepared elsewhere, or re-attaching a previously detached partition.

```sql
-- Prepare historical data in a standalone table:
CREATE TABLE events_2023_06_staging (LIKE events INCLUDING ALL);
-- Load data (from backup, CSV, another database, etc.):
COPY events_2023_06_staging FROM '/data/events_2023_06.csv' WITH CSV HEADER;

-- Validate the data before attaching (optional but recommended):
SELECT MIN(created_at), MAX(created_at) FROM events_2023_06_staging;
-- Should show: 2023-06-01 to 2023-06-30

-- Attach as a partition:
ALTER TABLE events ATTACH PARTITION events_2023_06_staging
    FOR VALUES FROM ('2023-06-01') TO ('2023-07-01');
-- PostgreSQL validates that ALL rows in the staging table satisfy the bound.
-- This requires scanning the entire staging table to verify no out-of-range rows.

-- For very large tables, this validation can be slow.
-- Speed it up by pre-adding a CHECK constraint that matches the partition bound:
ALTER TABLE events_2023_06_staging
    ADD CONSTRAINT check_june_2023
    CHECK (created_at >= '2023-06-01' AND created_at < '2023-07-01')
    NOT VALID;   -- NOT VALID skips scanning existing rows

ALTER TABLE events_2023_06_staging
    VALIDATE CONSTRAINT check_june_2023;
-- This validation CAN run concurrently with reads and writes (no full table lock)

-- Now ATTACH is fast because it trusts the validated CHECK constraint:
ALTER TABLE events ATTACH PARTITION events_2023_06_staging
    FOR VALUES FROM ('2023-06-01') TO ('2023-07-01');
-- Skips row-by-row validation — uses the CHECK constraint as proof.
```

### Partition Indexes and Constraints

Understanding how indexes and constraints work across partitioned tables is essential for correct schema design:

```sql
-- Indexes on the parent table propagate to all current AND future partitions:
CREATE INDEX ON events (user_id, created_at);
-- Creates index on events_2024_q1, events_2024_q2, etc.
-- AND will auto-create on events_2025_q1 when it is created.

-- Indexes can also be created on individual partitions:
CREATE INDEX ON events_2024_q3 (event_type) WHERE event_type = 'purchase';
-- This partial index exists only on events_2024_q3.
-- Queries that filter by event_type = 'purchase' AND are in Q3 use it.

-- PRIMARY KEY on a partitioned table must include the partition key:
-- If partition key is created_at, the PK must be (id, created_at)
-- This is because uniqueness is enforced per-partition, not globally.
-- Two rows in different partitions CAN have the same 'id' value
-- (though this is usually not what you want).

-- UNIQUE constraints have the same requirement:
ALTER TABLE events ADD CONSTRAINT events_uuid_unique
    UNIQUE (event_uuid, created_at);  -- must include created_at (partition key)

-- FOREIGN KEYS referencing a partitioned table:
-- The referencing FK column must include the partition key
-- OR the referenced partitioned table must have a UNIQUE index on the FK column
-- that includes the partition key. This is often awkward and may require
-- a different data model.

-- CHECK constraints on the parent propagate to all partitions:
ALTER TABLE events ADD CONSTRAINT events_positive_id CHECK (id > 0);
-- This constraint applies to all current and future partitions.
```

## Chapter 8: Partition Design Decisions and Anti-Patterns

### Choosing Partition Granularity

The granularity of partitions — daily, weekly, monthly, quarterly, yearly — involves a trade-off between pruning precision and management overhead:

```
Partition Granularity Trade-offs:

  Too fine (daily partitions for 5 years = 1,825 partitions):
  ✗ PostgreSQL planner overhead grows with partition count
    (planning time increases as it evaluates each partition's relevance)
  ✗ Maximum connections that can hold partition locks simultaneously is limited
  ✗ Table open overhead: each partition is a separate file descriptor
  ✗ pg_class, pg_index bloat: more rows in system catalogs

  Too coarse (annual partitions for 5 years = 5 partitions):
  ✗ Pruning is less precise: "give me January data" must scan all of the year
  ✗ Single partitions become large — maintenance operations still slow
  ✗ Dropping old data requires waiting a full year

  Sweet spot (monthly partitions for 5 years = 60 partitions):
  ✓ Queries filtering by day/week/month hit 1-2 partitions
  ✓ Drop old data month-by-month (gradual, manageable)
  ✓ Vacuum, reindex per partition is fast
  ✓ Planner overhead is manageable (<100 partitions)

  Rule of thumb:
  Choose granularity so that:
  1. The most common query filter aligns well with one or a few partitions
  2. The data lifecycle unit (drop quarterly? monthly?) matches the partition
  3. Total live partition count stays under ~100 for OLTP workloads
     (analytical workloads can tolerate more with enable_partition_pruning)
```

### The Hot Partition Problem

With time-based range partitioning, the most recent partition is always the hottest — it receives all new inserts and most recent reads. This concentrates write pressure on one partition. Hash sub-partitioning within time partitions (the composite approach from Chapter 5) distributes this pressure. Alternatively, simply accepting that the current partition is hot and ensuring it is well-sized and on fast storage (NVMe SSD) is often the pragmatic choice.

### Partitioning Is Not a Replacement for Indexing

A common misconception is that partitioning replaces the need for indexes. It does not. Partitioning helps the query planner skip entire partitions — but within the remaining partition, the query still needs indexes for efficient row lookup. Partition pruning reduces the number of blocks that must be scanned; indexes within a partition reduce the fraction of that partition that must be scanned.

```
Correct understanding of the interaction:

  Query: WHERE user_id = 42 AND created_at >= '2024-07-01'

  Partition pruning: eliminates all but events_2024_q3
  ↓
  Now searching events_2024_q3 for user_id = 42

  Without index on user_id: full scan of events_2024_q3 (still slow if large)
  With index on user_id: index seek directly to rows where user_id = 42 ✓

  Partitioning + Indexing work together:
  Partitioning reduces WHICH PARTITION is searched.
  Indexes reduce HOW MUCH of that partition is searched.
```

## Epilogue: Partitioning as Architecture

Table partitioning is one of the highest-leverage architectural decisions in PostgreSQL schema design. Getting it right — choosing the partition key that aligns with both your query patterns and your data lifecycle requirements, picking the right granularity, automating partition creation and dropping, monitoring partition health — makes the difference between a database that degrades gracefully as it grows and one that becomes increasingly painful to operate every month.

The engineer who designs a partitioned schema is making a bet: that the dimension they chose for partitioning will remain the dominant query and lifecycle dimension for the lifetime of the table. Time is almost always a safe bet for event and transaction data. Regional data residency is a safe bet for multi-tenant SaaS. Pure hash is a safe bet when you genuinely have no dominant query dimension and just need distributed write pressure.

What partitioning cannot fix is a fundamentally unclear data model or an application that queries in patterns that have no relationship to the partition key. If every query on your events table must scan all time ranges because it filters only on `user_id` and `event_type`, then time-based range partitioning adds overhead without benefit. In that case, the better solution is better indexing, better query design, or a different partitioning key entirely.

Partitioning is a tool that amplifies the existing natural structure of your data. When the partition key aligns with how the data is used, partitioning is one of the most powerful performance and operational tools in the PostgreSQL ecosystem. When it does not align, it is expensive structural overhead that makes every query touch more files than it needs to.

Understand your data's shape before you partition it. Then partition along the grain.
