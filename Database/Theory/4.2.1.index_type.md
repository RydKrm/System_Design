# Index Types — A Deep Study Guide

> *"Not all indexes are created equal. Just as a carpenter reaches for a different tool depending on whether they are cutting, drilling, or sanding, a skilled database engineer selects an index type based on the precise shape of the data they are indexing and the precise shape of the queries they need to serve. The right index type makes a query fly. The wrong one does nothing at all."*

In the previous chapter, we studied the internal mechanics of the B-Tree — the most fundamental and widely used index structure in relational databases. But the B-Tree, for all its brilliance, is not the right tool for every problem. What do you do when you need to search for all documents containing a specific word? Or find all points within a geographic radius? Or index a column containing arrays of tags? These problems require fundamentally different data structures with different internal geometries.

This chapter is a guided tour through five distinct index types — each invented to solve a class of problems that the others cannot. We will understand not just how each works, but *why* its internal structure makes it uniquely suited to certain query patterns, and precisely where it falls short.

## 1. B-Tree Index (Default)

### The Universal Workhorse

When you write `CREATE INDEX` in PostgreSQL, MySQL, SQL Server, or Oracle without specifying a type, you get a B-Tree index. It is the default not because database vendors are lazy, but because the B-Tree solves the broadest possible range of common indexing problems better than any other single structure. It is the Swiss Army knife of indexes — not the absolute best at any single thing, but remarkably competent at almost everything.

We studied the internal mechanics of the B-Tree in the previous chapter, so here we focus on its capabilities as an index type and the specific query patterns it supports. The B-Tree maintains all of its keys in **sorted order**, and this sorted order is the source of its power. Because the keys are sorted, the B-Tree can efficiently handle not just equality lookups but the full family of comparison operators: less than, greater than, less than or equal to, greater than or equal to, and BETWEEN. It can also handle prefix matching (`LIKE 'abc%'`) because a prefix is just a range of values starting with those characters.

```
  B-TREE INDEX SUPPORTED OPERATIONS:

  Query Type          | Operator        | Supported? | Performance
  ──────────────────────────────────────────────────────────────────
  Equality lookup     | =               |    YES     | ★★★★★ O(log N)
  Range scan          | <, >, <=, >=    |    YES     | ★★★★★ O(log N + K)
  Between             | BETWEEN a AND b |    YES     | ★★★★★ O(log N + K)
  Prefix match        | LIKE 'abc%'     |    YES     | ★★★★☆ O(log N + K)
  Suffix match        | LIKE '%xyz'     |    NO      | ✗ Full scan
  Substring match     | LIKE '%abc%'    |    NO      | ✗ Full scan
  NULL check          | IS NULL         |    YES     | ★★★★☆
  ORDER BY            | (implicit sort) |    YES     | ★★★★★ Free sort!
  Full-text search    | @@              |    NO      | ✗ Use GIN instead
  Geometric containm. | @>              |    NO      | ✗ Use GiST instead

  K = number of rows returned in a range scan
```

One subtle but enormously practical benefit of the B-Tree's sorted structure is that it can serve an `ORDER BY` clause **for free**. When the database retrieves rows through a B-Tree index, those rows are already in sorted order (because the leaf pages are in sorted order and linked as a list). If your query both filters and sorts by the indexed column, the database can scan the index in order and return rows sorted without a separate sort operation — which can be a significant performance win for large result sets.

### A Concrete Example

Imagine we have an `employees` table with millions of rows. We frequently run queries that look up employees by their `last_name` or retrieve all employees whose salary falls within a certain range. These are quintessential B-Tree use cases.

```sql
-- The table
CREATE TABLE employees (
    id          SERIAL PRIMARY KEY,
    first_name  VARCHAR(100),
    last_name   VARCHAR(100),
    salary      NUMERIC(10, 2),
    department  VARCHAR(100),
    hired_at    DATE
);

-- B-Tree index on last_name (equality + prefix matching)
CREATE INDEX idx_emp_last_name ON employees (last_name);

-- B-Tree index on salary (range queries)
CREATE INDEX idx_emp_salary ON employees (salary);

-- Composite B-Tree index (department + salary — covers both filtering and sorting)
CREATE INDEX idx_emp_dept_salary ON employees (department, salary DESC);
```

```
  B-TREE TRAVERSAL for: SELECT * FROM employees WHERE last_name = 'Smith'

  Root Page: [ 'Johnson' | 'Rodriguez' | 'Williams' ]
                              |
                    (Smith > Rodriguez, < Williams)
                              |
              Internal Page: [ 'Shaw' | 'Stone' ]
                              |
                    (Smith < Shaw)
                              |
              Leaf Page: [ Smith(row ptr 1) | Smith(row ptr 2) | Snyder ]
                              |
                    Found! Return rows for all 'Smith' entries.

  For: SELECT * FROM employees WHERE salary BETWEEN 50000 AND 80000
       → Find leaf with 50000 → walk linked list forward until > 80000
       → Returns all salary entries in that range, already sorted by salary
```

The B-Tree index is the right default choice whenever your columns are queried with comparison operators, sorted, or filtered with prefix patterns. If you are unsure which index type to use, start with B-Tree. Only reach for a different type when you have a specific, clear reason.

## 2. Hash Index

### The Specialist for Pure Equality

The Hash index is built on a conceptually simple and ancient idea: the **hash function**. A hash function takes any input value — a string, a number, a date — and produces a fixed-size integer called a **hash code**. If you know the hash code of a value, you can compute exactly which "bucket" it belongs to, jump directly to that bucket, and find (or not find) the value in a single operation. No traversal, no comparison, no levels to navigate. Just compute and jump.

The internal structure of a Hash index is an **array of buckets**. When you insert a key into the index, the database computes `hash(key) % number_of_buckets` to find the target bucket and stores the key and its row pointer there. When you search for a key, the database performs the same computation — hashes the search value, goes directly to the correct bucket, and looks for the matching entry. This makes equality lookups conceptually O(1) — constant time, independent of the number of rows in the table.

```
  HASH INDEX INTERNAL STRUCTURE

  Key value → hash function → bucket number → row pointer(s)

  hash('alice@example.com') = 7823
  7823 % 1024 (buckets) = 751

  Bucket Array:
  ┌────────┬────────────────────────────────────────────┐
  │ Bucket │ Contents                                   │
  ├────────┼────────────────────────────────────────────┤
  │  ...   │                                            │
  │  749   │ ['bob@example.com' → row ptr 8812]         │
  │  750   │ (empty)                                    │
  │  751   │ ['alice@example.com' → row ptr 3421]       │  ← Found!
  │  752   │ ['carol@example.com' → row ptr 9012]       │
  │  ...   │                                            │
  └────────┴────────────────────────────────────────────┘

  Lookup for 'alice@example.com':
  1. Compute hash('alice@example.com') = 7823
  2. 7823 % 1024 = 751
  3. Go directly to bucket 751
  4. Compare: 'alice@example.com' matches → return row ptr 3421
  Total: 1 hash computation + 1 bucket lookup. No tree traversal.
```

### What Hash Indexes Cannot Do

The limitation of a Hash index flows directly from its internal structure: **hash functions destroy all ordering information**. When 'alice@example.com' becomes 7823 and 'bob@example.com' becomes perhaps 3211, there is no relationship between those numbers that reflects the alphabetical order of the original strings. The hash values are essentially random-looking integers.

This means that a Hash index is completely blind to ordering. It cannot answer "give me all users whose email is greater than 'm'", because the concept of "greater than" does not exist in hash space. It cannot serve an `ORDER BY`. It cannot handle range queries or prefix matching. It can do precisely one thing, and one thing only: answer the question "does this exact value exist in the index, and if so, where is the row?" For that one operation, it is superb. For everything else, it is useless.

```
  HASH INDEX: What works and what does not

  Query                                  | Supported?
  ──────────────────────────────────────────────────────
  WHERE email = 'alice@example.com'      |  YES ★★★★★
  WHERE id = 42                          |  YES ★★★★★
  WHERE id > 42                          |  NO  ✗ (no ordering)
  WHERE salary BETWEEN 50000 AND 80000   |  NO  ✗ (no ordering)
  WHERE name LIKE 'Ali%'                 |  NO  ✗ (no ordering)
  ORDER BY email                         |  NO  ✗ (no ordering)
  WHERE email IS NULL                    |  NO  ✗ (NULLs not hashed)
  ──────────────────────────────────────────────────────
  HASH INDEX IS ONLY FOR: exact equality (=) lookups
```

### A Concrete Example

In practice, Hash indexes are most useful for large tables where you have a column that is *always* queried with pure equality — never sorted, never range-filtered — and where equality lookup performance is so critical that you want the fastest possible O(1) access. A session token lookup table is a classic example: you always look up sessions by their exact token string, never by range or order.

```sql
-- Session store table: always looked up by exact token string
CREATE TABLE user_sessions (
    token       VARCHAR(128) PRIMARY KEY,
    user_id     INTEGER      NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL,
    expires_at  TIMESTAMPTZ  NOT NULL
);

-- Hash index: perfect for this use case (exact equality only)
CREATE INDEX idx_session_token_hash ON user_sessions USING HASH (token);

-- This query is the ONLY type of query this table ever runs:
SELECT user_id, expires_at
FROM user_sessions
WHERE token = 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...';
-- → Hash lookup: O(1). Extremely fast. Index is ideal here.

-- This query would IGNORE the hash index (no range support):
SELECT * FROM user_sessions WHERE expires_at < NOW();
-- → Would need a separate B-Tree index on expires_at for this.
```

> **Important note on PostgreSQL history:** Before PostgreSQL 10, Hash indexes were not crash-safe (they were not WAL-logged). Since PostgreSQL 10, they are fully crash-safe and production-ready. In older versions of MySQL, Hash indexes are only available for the MEMORY storage engine. For InnoDB tables, MySQL uses B-Trees even when you might prefer a Hash — though InnoDB does maintain an **adaptive hash index** in memory automatically for frequently accessed B-Tree pages, giving you some of the benefits of hash lookups transparently.

## 3. GiST — Generalized Search Tree

### When Your Data Has a Shape

The B-Tree and Hash index are both designed for **scalar values** — numbers, strings, dates — simple one-dimensional data where "less than" and "greater than" have obvious meanings. But the real world is full of data that has *shape* — geometric points and polygons, IP address ranges, time ranges that overlap, full-text lexemes, and more. For this class of data, the **GiST (Generalized Search Tree)** was created.

GiST is not a single index algorithm — it is a **framework** for building index structures. It provides the scaffolding (tree structure, insertion, deletion, search), while the actual comparison and containment logic for each data type is plugged in separately as a set of user-defined **operator classes**. This makes GiST extraordinarily extensible: the same underlying tree machinery can index 2D geometric shapes, 3D objects, IP network ranges, or any custom data type you define, as long as you provide functions that tell GiST how to compare and group values of your type.

### How GiST Works Internally

The key insight of GiST is that internal pages do not store exact separator keys (like B-Tree does). Instead, they store **bounding predicates** — a summary or "bounding box" that represents the *union* of all the values in the subtree below. During a search, the database checks whether the search predicate **intersects** with the bounding predicate of each internal page. If it does, it descends into that subtree. If it does not, the entire subtree is skipped. This is called **predicate-based pruning**.

```
  GiST INDEX FOR GEOMETRIC DATA (2D rectangles)

  Stored shapes (simplified to bounding boxes):
  Shape A: Rectangle at x(10-30), y(20-40)
  Shape B: Rectangle at x(50-80), y(10-35)
  Shape C: Rectangle at x(15-25), y(50-70)
  Shape D: Rectangle at x(60-90), y(55-80)

  GiST Tree (internal nodes store BOUNDING BOXES of subtrees):
  ┌────────────────────────────────────────┐
  │  Root: BBox(x:10-90, y:10-80)         │  ← Union of ALL shapes
  └────────────────┬───────────────────────┘
                   │
       ┌───────────┴──────────────┐
       │                          │
  ┌─────────────────┐      ┌─────────────────────┐
  │ BBox(x:10-30,   │      │ BBox(x:50-90,       │
  │      y:20-70)   │      │      y:10-80)        │
  └────────┬────────┘      └──────────┬───────────┘
           │                          │
      ┌────┴────┐                ┌────┴────┐
   Shape A   Shape C          Shape B   Shape D

  Query: "Find all shapes that overlap with rectangle x(20-60), y(30-60)"

  Step 1: Check root bbox → intersects? YES (20-60 overlaps 10-90) → descend
  Step 2: Check left bbox (10-30, 20-70) → intersects? YES → descend → Check A: YES, C: YES
  Step 3: Check right bbox (50-90, 10-80) → intersects? YES → descend → Check B: YES, D: ?
           D is at (60-90, 55-80): Does (20-60,30-60) overlap (60-90,55-80)? x:60=60 → barely.
  Result: {A, B, C, D} depending on exact overlap (GiST may return false positives, 
           application re-checks)
```

Notice that GiST may return "false positives" — entries that the bounding box suggests might match, but don't actually satisfy the query. This is acceptable because GiST is designed to guarantee **no false negatives** (it never misses a true match), while the application or a final filter step eliminates the false positives.

### A Concrete Example: Geospatial Proximity Search

GiST is the engine behind PostGIS (PostgreSQL's geospatial extension), enabling efficient geographic queries. Imagine a restaurant discovery app that must find all restaurants within 5 km of a user's current location. Without an index, this requires computing the distance from every restaurant in the table to the user — potentially millions of calculations. With a GiST index on the restaurant's geographic location, the database can skip entire regions of the earth that are obviously too far away, examining only those that might plausibly be within range.

```sql
-- Enable the PostGIS extension (provides geometric types and operators)
CREATE EXTENSION IF NOT EXISTS postgis;

-- Restaurants table with geographic location
CREATE TABLE restaurants (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(200)  NOT NULL,
    cuisine     VARCHAR(100),
    location    GEOGRAPHY(POINT, 4326)  -- Latitude/Longitude point
);

-- GiST index on the geographic location column
CREATE INDEX idx_restaurants_location
ON restaurants USING GIST (location);

-- Insert some restaurants
INSERT INTO restaurants (name, cuisine, location) VALUES
    ('Bella Italia', 'Italian', ST_MakePoint(90.4125, 23.8103)::geography),
    ('Dragon Palace', 'Chinese', ST_MakePoint(90.4200, 23.8150)::geography),
    ('Burger House', 'American', ST_MakePoint(90.4500, 23.7800)::geography);

-- Find all restaurants within 5 km of a user at (90.4125, 23.8103)
SELECT name, cuisine,
       ST_Distance(location, ST_MakePoint(90.4125, 23.8103)::geography) AS dist_meters
FROM restaurants
WHERE ST_DWithin(
    location,
    ST_MakePoint(90.4125, 23.8103)::geography,
    5000  -- 5000 meters = 5 km
)
ORDER BY dist_meters;

-- The GiST index makes this query fast even with millions of restaurants.
-- Without it: calculate distance for every row → O(N)
-- With GiST:  prune entire geographic regions → O(log N + K)
```

GiST is also used for **range types** in PostgreSQL (date ranges, integer ranges), **full-text search** (as a less optimal alternative to GIN), and **network address** indexing (`inet`, `cidr` types). Whenever your data has a spatial, overlapping, or containment-based relationship, GiST is worth considering.

## 4. GIN — Generalized Inverted Index

### When One Column Contains Many Things

The B-Tree index is built on the assumption that each row contributes exactly one key value to the index. A user has one email address; an order has one status code; a product has one price. But what about a blog post that has *multiple* tags? Or a document that contains *thousands* of words? Or a JSON object with *many* nested fields? In these cases, a single row needs to be indexed under multiple keys simultaneously, and the B-Tree is not designed for this.

This is precisely the problem that the **GIN (Generalized Inverted Index)** was designed to solve. The word "inverted" is the key: in a normal (forward) index, you go from a row to its key value. In an **inverted index**, you go the other direction — from a key value to all the rows that contain it. GIN builds a mapping of every distinct "element" (word, tag, array item, JSON key) to the list of all row IDs that contain that element.

```
  GIN INDEX CONCEPT — An Inverted Mapping

  Data (blog posts with tags):
  ┌────┬─────────────────────────────────────────────┐
  │ id │ tags (array)                                │
  ├────┼─────────────────────────────────────────────┤
  │  1 │ {python, database, tutorial}                │
  │  2 │ {javascript, tutorial, web}                 │
  │  3 │ {database, sql, performance}                │
  │  4 │ {python, machine-learning, ai}              │
  └────┴─────────────────────────────────────────────┘

  GIN Index (element → list of row IDs that contain it):
  ┌────────────────────┬────────────────────────┐
  │ Element (Key)      │ Posting List (Row IDs)  │
  ├────────────────────┼────────────────────────┤
  │ ai                 │ {4}                    │
  │ database           │ {1, 3}                 │
  │ javascript         │ {2}                    │
  │ machine-learning   │ {4}                    │
  │ performance        │ {3}                    │
  │ python             │ {1, 4}                 │
  │ sql                │ {3}                    │
  │ tutorial           │ {1, 2}                 │
  │ web                │ {2}                    │
  └────────────────────┴────────────────────────┘

  Query: WHERE tags @> ARRAY['python', 'tutorial']
         (Find posts containing BOTH 'python' AND 'tutorial')

  Step 1: Look up 'python'   → posting list: {1, 4}
  Step 2: Look up 'tutorial' → posting list: {1, 2}
  Step 3: Intersect: {1, 4} ∩ {1, 2} = {1}
  Result: Row 1 matches. 2 GIN lookups + 1 set intersection. Very fast!
```

The "posting list" for each element is internally stored as a sorted list of row IDs, which makes set operations (AND = intersect, OR = union, NOT = complement) extremely efficient. GIN is able to answer multi-element containment queries by looking up each element separately and then combining the posting lists with set arithmetic.

### GIN for Full-Text Search

The most widely used application of GIN in PostgreSQL is **full-text search**. When you want to find all documents that contain a particular word or phrase, you need an inverted index over the words (technically called *lexemes* after stemming and normalization) in each document. GIN is the natural home for this.

```sql
-- Articles table for a news website
CREATE TABLE articles (
    id          SERIAL PRIMARY KEY,
    title       TEXT           NOT NULL,
    body        TEXT           NOT NULL,
    published   BOOLEAN        DEFAULT false,
    created_at  TIMESTAMPTZ    DEFAULT NOW(),

    -- A computed column storing the pre-parsed text search vector
    -- (combining title with higher weight 'A', body with weight 'B')
    search_vector TSVECTOR
        GENERATED ALWAYS AS (
            setweight(to_tsvector('english', title), 'A') ||
            setweight(to_tsvector('english', body),  'B')
        ) STORED
);

-- GIN index on the pre-computed search vector
CREATE INDEX idx_articles_search ON articles USING GIN (search_vector);

-- Insert some articles
INSERT INTO articles (title, body) VALUES
    ('Database Indexing Explained',
     'This article explains how B-Tree and GIN indexes work in PostgreSQL.'),
    ('Introduction to Machine Learning',
     'Machine learning models require large datasets and careful feature engineering.');

-- Full-text search: find articles containing 'index' or related forms
SELECT title, ts_rank(search_vector, query) AS relevance
FROM articles,
     to_tsquery('english', 'index | database') AS query
WHERE search_vector @@ query
ORDER BY relevance DESC;

-- Without GIN index: every row's text is parsed and compared → O(N), very slow
-- With GIN index:    look up 'index' in posting list → O(1) lookup → O(K) result
```

### GIN for JSONB and Arrays

GIN also powers efficient querying of JSONB columns and array columns — two data types where a single cell can contain multiple queryable values.

```sql
-- Product catalog with flexible JSONB attributes
CREATE TABLE products (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(255)  NOT NULL,
    attributes  JSONB
);

-- GIN index on the JSONB column
-- This indexes every JSON key and value, enabling queries like:
-- "find all products where attributes contains key 'color' with value 'blue'"
CREATE INDEX idx_products_attrs ON products USING GIN (attributes);

-- Insert products
INSERT INTO products (name, attributes) VALUES
    ('Sony TV', '{"brand":"Sony","screen_size":55,"color":"black","4k":true}'),
    ('LG TV',   '{"brand":"LG","screen_size":65,"color":"silver","4k":true}'),
    ('Samsung',  '{"brand":"Samsung","screen_size":55,"color":"black","4k":false}');

-- Query: find all products that are 55 inches AND black
SELECT name, attributes
FROM products
WHERE attributes @> '{"screen_size": 55, "color": "black"}';
-- GIN finds rows where JSONB contains ALL of the specified key-value pairs.
-- Result: Sony TV, Samsung (both match screen_size=55 AND color=black)

-- Query: find all products that have the key '4k' (regardless of value)
SELECT name FROM products WHERE attributes ? '4k';
-- GIN index is used for the '?' (key exists) operator too.
```

### Write Cost of GIN

One important characteristic of GIN to understand is that it is **write-expensive**. Because each inserted or updated row may contribute many elements to the index (a blog post with 100 words contributes 100 entries to the GIN), insertions and updates are significantly slower than with a B-Tree. PostgreSQL mitigates this with a feature called the **GIN pending list** (controlled by `gin_pending_list_limit`): new index entries are initially written to a small, fast pending list rather than immediately merged into the main GIN structure. Periodically (or when the list grows large enough), the pending list is merged into the main index in bulk. This amortizes the expensive merge operations and makes individual writes much faster, at the cost of slightly higher read latency until the merge occurs.

## 5. BRIN — Block Range Index

### The Featherweight Champion of Append-Only Data

All of the index types we have studied so far — B-Tree, Hash, GiST, GIN — share one thing in common: they store an entry for every indexed row. For a table with 100 million rows, the index itself contains 100 million entries. While the index is much smaller than the table (because it only stores the key and a pointer, not all the data), it can still consume significant disk space and memory. For certain very large tables, even reading the index is expensive.

The **BRIN (Block Range Index)** takes a radically different approach: instead of indexing individual rows, it indexes **ranges of physical disk blocks**. The table is divided into sequential groups of consecutive pages (called **block ranges**), and for each block range, the BRIN index stores only a single summary — the minimum and maximum value of the indexed column within that range. The entire index is extraordinarily small — potentially just a few kilobytes for a multi-billion-row table.

```
  BRIN INDEX CONCEPT — Summarizing block ranges, not individual rows

  Table on disk (each block = 8KB, holding ~100 rows):
  ┌──────────────────────────────────────────────────────────────┐
  │ Block 1-128 (pages 1-128)   → rows 1 to ~12,800            │
  │ Block 129-256 (pages 129-256) → rows ~12,801 to ~25,600    │
  │ ...                                                          │
  └──────────────────────────────────────────────────────────────┘

  BRIN Index (pages_per_range = 128):
  ┌──────────────┬───────────────┬──────────────────────────────┐
  │ Block Range  │ Min Value     │ Max Value                    │
  ├──────────────┼───────────────┼──────────────────────────────┤
  │ Pages 1-128  │ 2024-01-01    │ 2024-01-15   (Jan 1-15)     │
  │ Pages 129-256│ 2024-01-15    │ 2024-01-31   (Jan 15-31)    │
  │ Pages 257-384│ 2024-02-01    │ 2024-02-14   (Feb 1-14)     │
  │ Pages 385-512│ 2024-02-14    │ 2024-02-28   (Feb 14-28)    │
  │ ...          │ ...           │ ...                          │
  └──────────────┴───────────────┴──────────────────────────────┘

  Size of entire BRIN index: a few KB to a few MB (vs. GB for B-Tree!)

  Query: WHERE created_at BETWEEN '2024-02-01' AND '2024-02-14'

  BRIN checks each range summary:
  ✗ Pages 1-128:   2024-01-01 to 2024-01-15 → No overlap → SKIP entirely
  ✗ Pages 129-256: 2024-01-15 to 2024-01-31 → No overlap → SKIP entirely
  ✓ Pages 257-384: 2024-02-01 to 2024-02-14 → OVERLAP → Scan these 128 pages
  ✗ Pages 385-512: 2024-02-14 to 2024-02-28 → No overlap → SKIP
  Result: Only 128 pages read instead of all 512!
```

### The Critical Requirement: Physical Correlation

BRIN's effectiveness depends entirely on one condition: **the values in the indexed column must be physically correlated with the order of rows on disk**. In other words, rows with similar values must be stored in nearby blocks. If rows are in random order on disk (which happens when many updates and deletes cause rows to be stored in random pages), BRIN provides no benefit at all — the min/max range of every block range would be almost identical, and no ranges could be skipped.

The good news is that certain very common patterns naturally satisfy this requirement perfectly:

The most natural case is an **append-only table with a timestamp column**. When rows are always inserted at the end of the table in chronological order, rows from January are physically stored on the first pages, rows from February on the next pages, and so on. The correlation between the timestamp value and the physical position on disk is essentially perfect. BRIN is tailor-made for this scenario.

Similarly, a **serial or auto-incrementing ID column** is perfectly correlated with physical order, because rows are inserted in order of their IDs and therefore older (lower-ID) rows live at the start of the table and newer (higher-ID) rows at the end.

```
  CORRELATION REQUIREMENT ILLUSTRATED:

  GOOD for BRIN (append-only, chronological inserts):
  ┌─────────┬──────────────┐
  │ page 1  │ Jan 1-5 data │  ← Low timestamps at physical start
  │ page 2  │ Jan 5-10 data│
  │ page 3  │ Jan 10-15    │
  │ page 4  │ Jan 15-20    │
  │ page 5  │ Jan 20-31    │  ← High timestamps at physical end
  └─────────┴──────────────┘
  Min/max per block range is tight → Many ranges can be skipped

  BAD for BRIN (random inserts, updates, deletes):
  ┌─────────┬──────────────────────────────────────┐
  │ page 1  │ Jan 5, Mar 15, Feb 3, Dec 8, Jun 22  │
  │ page 2  │ Aug 11, Jan 3, Sep 30, Apr 17, Nov 5 │
  │ page 3  │ Jul 28, Feb 14, May 6, Oct 19, Jan 9 │
  └─────────┴──────────────────────────────────────┘
  Min=Jan, Max=Dec for almost every block range → Nothing can be skipped!
  BRIN index is completely useless in this case.
```

### A Concrete Example: IoT Sensor Data

BRIN is the ideal index for large IoT sensor data tables, server metric logs, financial tick data, or any time-series scenario where data is written chronologically and never updated. In these scenarios, a B-Tree index on the timestamp column would be enormous (hundreds of GB for a multi-billion-row table), expensive to maintain, and slow to insert into. A BRIN index achieves 95%+ of the filtering benefit at a tiny fraction of the cost.

```sql
-- IoT sensor readings table (billions of rows, append-only)
CREATE TABLE sensor_readings (
    reading_id  BIGSERIAL     PRIMARY KEY,
    sensor_id   INTEGER       NOT NULL,
    recorded_at TIMESTAMPTZ   NOT NULL,
    temperature NUMERIC(5, 2),
    humidity    NUMERIC(5, 2),
    pressure    NUMERIC(7, 2)
);

-- BRIN index on the timestamp (data is inserted chronologically)
-- pages_per_range=128: each summary covers 128 pages (~102,400 rows)
CREATE INDEX idx_sensor_brin_time
ON sensor_readings USING BRIN (recorded_at)
WITH (pages_per_range = 128);

-- Optional: also BRIN on reading_id (auto-increment = perfect correlation)
CREATE INDEX idx_sensor_brin_id
ON sensor_readings USING BRIN (reading_id);

-- Query: Last 24 hours of readings from a specific sensor
SELECT sensor_id, recorded_at, temperature, humidity
FROM sensor_readings
WHERE recorded_at >= NOW() - INTERVAL '24 hours'
  AND sensor_id = 42
ORDER BY recorded_at DESC;

-- BRIN skips all block ranges whose max(recorded_at) < NOW()-24hours.
-- For a 3-year dataset, BRIN skips ~99.9% of the table.
-- Only the most recent few block ranges are scanned.

-- Compare index sizes for a table with 1 billion rows:
-- B-Tree on recorded_at:  ~40 GB (one entry per row)
-- BRIN on recorded_at:    ~100 KB (one summary per 128 pages!)
-- That's a 400,000x size reduction.
```

### BRIN Limitations

BRIN's extreme compactness comes with important limitations beyond the physical correlation requirement. Because BRIN only stores a range summary per block range (not exact row pointers), it cannot perform exact equality lookups efficiently — it can only narrow down the set of pages that *might* contain a matching row, after which a sequential scan of those pages is required. This makes BRIN a **lossy index** in the sense that it always requires a final verification step (re-checking the actual rows in the candidate pages). For queries that match a small fraction of a single block range, BRIN might still have to scan that entire block range — whereas a B-Tree would jump directly to the exact row.

BRIN is also not useful for random-access patterns. If you need to find a single row by its exact timestamp, B-Tree is far better. BRIN shines specifically when you are filtering time-based data across large ranges and the majority of the table can be excluded by range elimination.

## Summary: Choosing the Right Index Type

The five index types we have studied represent a diverse toolkit, each with a distinct sweet spot. The art of database indexing lies in matching the geometry of your data and the shape of your queries to the index type whose internal structure is designed for exactly that combination.

```
  INDEX TYPE SELECTION GUIDE

  ┌────────────────┬───────────────────────────────┬───────────────────────────┐
  │  Index Type    │  Best For                     │  Avoid When               │
  ├────────────────┼───────────────────────────────┼───────────────────────────┤
  │  B-Tree        │  General purpose: equality,   │  Full-text, arrays, JSON  │
  │  (Default)     │  ranges, sorting, prefix match│  containment queries      │
  ├────────────────┼───────────────────────────────┼───────────────────────────┤
  │  Hash          │  Pure equality lookups only.  │  Any range, sort, or      │
  │                │  Session tokens, cache keys   │  prefix query             │
  ├────────────────┼───────────────────────────────┼───────────────────────────┤
  │  GiST          │  Geometric/spatial data,      │  Simple scalar equality   │
  │                │  IP ranges, overlapping ranges│  or range queries (B-Tree)│
  ├────────────────┼───────────────────────────────┼───────────────────────────┤
  │  GIN           │  Arrays, JSONB, full-text     │  Write-heavy workloads    │
  │                │  search (tsvector), multi-key │  (writes are expensive)   │
  ├────────────────┼───────────────────────────────┼───────────────────────────┤
  │  BRIN          │  Very large append-only tables│  Random insert/update     │
  │                │  with natural sort order:     │  patterns; point lookups  │
  │                │  timestamps, serial IDs, IoT  │  needing exact row        │
  └────────────────┴───────────────────────────────┴───────────────────────────┘

  QUICK DECISION TREE:

  What kind of data are you indexing?
  │
  ├─► Scalar (numbers, strings, dates)?
  │      │
  │      ├─► Only ever queried with = (equality)? → Hash Index
  │      └─► Ranges, sorting, prefix needed?      → B-Tree Index (default)
  │
  ├─► Spatial / geometric / overlapping ranges?   → GiST Index
  │
  ├─► Array, JSONB, or full-text document?        → GIN Index
  │
  └─► Append-only table, billions of rows,
      naturally sorted column (timestamp, ID)?    → BRIN Index
```

The most important rule to carry away from this chapter is that the **default B-Tree covers 90% of all indexing needs**. Reach for the other types only when you have a specific, clear requirement that B-Tree provably cannot satisfy efficiently. And when you do reach for them, remember that each one trades something — GIN trades write speed, BRIN trades point-lookup precision, Hash trades range capability — and understanding those trade-offs is what separates an engineer who uses indexes from one who truly masters them.
