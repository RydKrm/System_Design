# Advanced SQL

### A Deep, Conceptual Journey from the Ground Up

> _Advanced SQL is not about memorizing syntax — it is about gaining new tools to express ideas that would otherwise require application-layer code._

---

## Preface: What Makes SQL "Advanced"?

Every developer who has written SQL knows the basics: `SELECT`, `FROM`, `WHERE`, `JOIN`, `GROUP BY`. These are the vocabulary of relational thinking. But SQL is a far richer language than its basics suggest. The features explored in this guide are "advanced" not because they are difficult, but because they solve problems that beginners typically solve in the wrong place — in application code, in multiple round-trips to the database, or with awkward workarounds.

The hallmark of an advanced SQL practitioner is recognizing that the database is not just a storage mechanism. It is a computation engine. The closer you push your logic to the data — inside the database — the less data travels over the wire, the fewer round-trips your application makes, and the more the database's optimizer can help you. This guide is about learning to push more.

## Chapter 1: UNION, INTERSECT, EXCEPT

### Set Operations: Thinking in Collections

Before relational databases, mathematicians spent centuries developing **set theory** — the study of collections of objects and operations on them. SQL's set operators (`UNION`, `INTERSECT`, `EXCEPT`) are direct implementations of three fundamental set operations: union (combining collections), intersection (finding what is common), and difference (finding what is in one but not the other). Understanding them geometrically, as overlapping circles, is the clearest path to intuition.

```
Set A = {customers who bought in 2023}
Set B = {customers who bought in 2024}

         A ∪ B (UNION)              A ∩ B (INTERSECT)         A − B (EXCEPT)
    ┌──────────────────┐          ┌──────────────────┐      ┌──────────────────┐
    │  ╔═══╗   ╔═══╗   │          │      ╔═══╗       │      │  ╔═══╗           │
    │  ║ A ╠═══╣ B ║   │          │      ║A∩B║       │      │  ║A-B║   B       │
    │  ╚═══╝   ╚═══╝   │          │      ╚═══╝       │      │  ╚═══╝           │
    │ bought in either │          │ bought in both   │      │ 2023 only (not   │
    │  2023 or 2024    │          │  2023 and 2024   │      │ repeated in 2024)│
    └──────────────────┘          └──────────────────┘      └──────────────────┘
```

### The Rules of Set Operations

All three operators share one strict requirement: **the two queries being combined must produce the same number of columns, with compatible data types, in the same order**. The column names in the final result are taken from the first query. The database merges the result sets based on column position, not column name.

```sql
-- Both queries must have the same shape:
-- Column 1: user identifier (integer)
-- Column 2: name (text)
-- Column 3: source label (text)

SELECT id, name, 'active'   AS source FROM active_users
UNION
SELECT id, name, 'archived' AS source FROM archived_users;
```

### UNION: Combining Results, Removing Duplicates

`UNION` takes the result sets of two queries and returns all rows from both, **removing duplicate rows**. Two rows are considered duplicates if every column value is identical. This deduplication step requires the database to sort or hash all combined rows — it is not free, and on large result sets it can be expensive.

`UNION ALL` is the sibling that skips the deduplication step entirely. It returns every row from both queries, including exact duplicates. Because there is no deduplication, `UNION ALL` is almost always faster. You should use `UNION ALL` by default and reach for `UNION` only when you genuinely need to eliminate duplicates.

```sql
-- Scenario: build a unified activity feed from multiple event tables

SELECT user_id, 'order'   AS activity_type, created_at, order_id   AS ref_id
FROM orders

UNION ALL

SELECT user_id, 'review'  AS activity_type, created_at, review_id  AS ref_id
FROM product_reviews

UNION ALL

SELECT user_id, 'support' AS activity_type, created_at, ticket_id  AS ref_id
FROM support_tickets

ORDER BY created_at DESC
LIMIT 50;
```

Notice that the `ORDER BY` at the end applies to the entire combined result, not to any individual query. This is the correct way to sort a `UNION` result. You cannot put `ORDER BY` inside individual member queries (except in PostgreSQL, where it is allowed but effectively meaningless without a `LIMIT`).

A subtler use of `UNION ALL` is **data migration validation** — proving that two tables contain exactly the same rows:

```sql
-- Prove that table_a and table_b contain identical data
-- If this query returns zero rows, the tables are identical

SELECT * FROM table_a
EXCEPT
SELECT * FROM table_b

UNION ALL

SELECT * FROM table_b
EXCEPT
SELECT * FROM table_a;
```

If both `EXCEPT` queries return empty sets, the `UNION ALL` of two empty sets is empty — meaning the tables are identical. If any rows appear, they represent discrepancies.

### INTERSECT: What They Have in Common

`INTERSECT` returns only the rows that appear in **both** query results. Like `UNION`, it removes duplicates by default. `INTERSECT ALL` preserves duplicates (a row appearing twice in both queries appears twice in the result).

```sql
-- Find customers who placed orders in BOTH January AND February 2024
-- (retained customers who were active across both months)

SELECT user_id FROM orders WHERE DATE_TRUNC('month', created_at) = '2024-01-01'
INTERSECT
SELECT user_id FROM orders WHERE DATE_TRUNC('month', created_at) = '2024-02-01';
```

The same result could be achieved with a self-join or with `GROUP BY ... HAVING COUNT(DISTINCT month) = 2`, but `INTERSECT` expresses the intent directly: "show me what is common between these two populations."

```sql
-- Find products that appear in ALL of three separate discount campaigns
-- (products eligible for the combined deal)

SELECT product_id FROM campaign_products WHERE campaign_id = 'SUMMER_SALE'
INTERSECT
SELECT product_id FROM campaign_products WHERE campaign_id = 'CLEARANCE'
INTERSECT
SELECT product_id FROM campaign_products WHERE campaign_id = 'LOYALTY';
```

Multiple `INTERSECT` operations chain naturally — the result is the intersection of all three sets.

### EXCEPT: What One Has That the Other Does Not

`EXCEPT` (called `MINUS` in Oracle) returns rows that appear in the **first** query but **not** in the second. It is directional — `A EXCEPT B` is not the same as `B EXCEPT A`. This makes it the natural tool for "find what is missing" and "find what changed" problems.

```sql
-- Find users who were active last month but NOT this month (potential churners)

SELECT user_id FROM orders
WHERE created_at >= DATE_TRUNC('month', NOW() - INTERVAL '1 month')
  AND created_at <  DATE_TRUNC('month', NOW())

EXCEPT

SELECT user_id FROM orders
WHERE created_at >= DATE_TRUNC('month', NOW());
```

```sql
-- Schema drift check: find columns in the production table
-- that are missing from the staging table

SELECT column_name FROM information_schema.columns
WHERE table_name = 'production_users'

EXCEPT

SELECT column_name FROM information_schema.columns
WHERE table_name = 'staging_users';
```

### Operator Precedence

When mixing multiple set operators, `INTERSECT` has higher precedence than `UNION` and `EXCEPT` — just like multiplication has higher precedence than addition in arithmetic. Use parentheses to make the intended grouping explicit:

```sql
-- This evaluates INTERSECT first, then UNION:
(SELECT ... INTERSECT SELECT ...) UNION SELECT ...

-- Without parentheses, same result due to precedence, but less readable:
SELECT ... INTERSECT SELECT ... UNION SELECT ...
```

## Chapter 2: PIVOT and UNPIVOT

### Rotating Data: Rows to Columns and Back

Data in a relational database is stored in a **normalized, tall format** — one observation per row. But reports and dashboards typically want data in a **wide format** — one entity per row, with multiple measurements spread across columns. The process of rotating rows into columns is called **pivoting**. The reverse — rotating columns back into rows — is **unpivoting**.

```
Tall (normalized) format:           Wide (pivoted) format:
  month   | product | revenue          product | Jan    | Feb    | Mar
----------+---------+---------         --------+--------+--------+------
  Jan     | Widget  | 1200             Widget  | 1200   | 1500   | 1100
  Feb     | Widget  | 1500             Gadget  | 800    | 950    | 1200
  Mar     | Widget  | 1100
  Jan     | Gadget  |  800      →  Each product is now one row,
  Feb     | Gadget  |  950         each month is now a column.
  Mar     | Gadget  | 1200
```

### Pivoting in PostgreSQL: The FILTER + Conditional Aggregation Approach

PostgreSQL does not have a native `PIVOT` keyword (unlike SQL Server or Oracle). Instead, PostgreSQL achieves pivoting through **conditional aggregation** — using `CASE WHEN` or the `FILTER` clause inside aggregate functions to selectively aggregate only rows that match certain conditions.

```sql
-- Pivot: monthly revenue per product as columns

SELECT
    product,
    SUM(revenue) FILTER (WHERE month = 'Jan') AS jan_revenue,
    SUM(revenue) FILTER (WHERE month = 'Feb') AS feb_revenue,
    SUM(revenue) FILTER (WHERE month = 'Mar') AS mar_revenue
FROM monthly_sales
GROUP BY product
ORDER BY product;

-- Equivalent using CASE WHEN (works in all SQL databases):
SELECT
    product,
    SUM(CASE WHEN month = 'Jan' THEN revenue ELSE 0 END) AS jan_revenue,
    SUM(CASE WHEN month = 'Feb' THEN revenue ELSE 0 END) AS feb_revenue,
    SUM(CASE WHEN month = 'Mar' THEN revenue ELSE 0 END) AS mar_revenue
FROM monthly_sales
GROUP BY product;
```

The `FILTER (WHERE condition)` syntax, available in PostgreSQL and modern SQL, is cleaner and more explicit than `CASE WHEN`. It means: "aggregate, but only over rows where this condition is true." The `GROUP BY product` collapses all months for each product into one row, and the filtered aggregates distribute the values across the monthly columns.

### Dynamic Pivoting with crosstab()

The limitation of conditional aggregation is that you must hardcode the column names. If you have 12 months, you write 12 `FILTER` clauses. If a new month arrives, you modify the query. This is static pivoting. For truly dynamic pivoting — where the column names are determined by the data itself — PostgreSQL provides the `crosstab()` function from the `tablefunc` extension.

```sql
-- First, enable the extension (once per database):
CREATE EXTENSION IF NOT EXISTS tablefunc;

-- Dynamic pivot: one row per product, one column per month, automatically
SELECT *
FROM crosstab(
    -- Query 1: the source data, ordered by row key then category
    'SELECT product, month, revenue
     FROM monthly_sales
     ORDER BY product, month',

    -- Query 2: the distinct column values (defines column names and order)
    'SELECT DISTINCT month FROM monthly_sales ORDER BY month'
) AS pivot_result(
    product TEXT,
    jan NUMERIC,
    feb NUMERIC,
    mar NUMERIC
);
```

`crosstab()` is more flexible but requires pre-declaring the output column names in the `AS` clause — which means full dynamism (not knowing the columns at query-write time) still requires dynamic SQL generation in your application.

### UNPIVOT: Rotating Columns Back to Rows

Unpivoting is the reverse operation — taking a wide table with many columns and converting it into a tall table with repeated rows. This is frequently needed when importing data from spreadsheets (which humans love to make wide) into a normalized database.

PostgreSQL does not have a native `UNPIVOT` keyword, but the combination of `UNION ALL` and static column references achieves it cleanly:

```sql
-- Wide table: one row per product, one column per month
-- Unpivot: convert to tall format (one row per product-month combination)

SELECT product, 'Jan' AS month, jan_revenue AS revenue FROM wide_sales
UNION ALL
SELECT product, 'Feb' AS month, feb_revenue AS revenue FROM wide_sales
UNION ALL
SELECT product, 'Mar' AS month, mar_revenue AS revenue FROM wide_sales
ORDER BY product, month;
```

Each `SELECT` in the `UNION ALL` picks one column from the wide table, labels it with the month name, and produces one row per product. The `UNION ALL` stacks all three into the tall format.

For a more elegant approach with many columns, PostgreSQL's `json_each()` or `jsonb_each_text()` combined with `row_to_json()` can be used to unpivot dynamically — but this is an advanced technique that trades readability for flexibility.

## Chapter 3: Grouping Sets — GROUPING SETS, ROLLUP, CUBE

### The Problem with Multiple GROUP BY Queries

Imagine you are building a sales report that needs subtotals at three levels: per department, per product, and a grand total. With standard SQL, you would need three separate queries, each with a different `GROUP BY`, then combine them with `UNION ALL`. This is verbose, repetitive, and potentially slow — the database scans the same table three times.

**Grouping sets** are a SQL feature that lets you specify multiple grouping combinations in a single query. The database computes all the requested groupings in one pass, and the results are stacked into a single result set. The three variants — `GROUPING SETS`, `ROLLUP`, and `CUBE` — differ only in how you specify which combinations you want.

### GROUPING SETS: Explicit Multi-Level Aggregation

`GROUPING SETS` is the most explicit form. You list exactly which grouping combinations you want, and the database computes each one independently and combines them.

```sql
-- Compute revenue grouped by (region, product), by (region), and as a grand total

SELECT
    region,
    product,
    SUM(revenue) AS total_revenue
FROM sales
GROUP BY GROUPING SETS (
    (region, product),   -- group by both region AND product
    (region),            -- group by region only
    ()                   -- no grouping = grand total
);

-- Result:
-- region | product | total_revenue
-- -------+---------+--------------
-- East   | Widget  | 4500          ← (region, product) group
-- East   | Gadget  | 3200          ← (region, product) group
-- West   | Widget  | 5100          ← (region, product) group
-- West   | Gadget  | 2800          ← (region, product) group
-- East   | NULL    | 7700          ← (region) group: East total
-- West   | NULL    | 7900          ← (region) group: West total
-- NULL   | NULL    | 15600         ← () group: grand total
```

The columns that are not part of a particular grouping set appear as `NULL` in the result. This is how you identify which level a row belongs to: a row with `NULL` for `product` but a value for `region` is a regional subtotal; a row with `NULL` for both is the grand total.

But this creates an ambiguity: what if your actual data has `NULL` values in those columns? You cannot tell whether a `NULL` in the result means "this column was not part of the grouping" or "the original data was NULL." The `GROUPING()` function resolves this:

```sql
SELECT
    region,
    product,
    SUM(revenue)    AS total_revenue,
    GROUPING(region)  AS is_region_subtotal,   -- 1 if region is NOT in this grouping
    GROUPING(product) AS is_product_subtotal   -- 1 if product is NOT in this grouping
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());
```

`GROUPING(column)` returns `1` when the column is not part of the current grouping (i.e., its `NULL` is a grouping `NULL`, not a data `NULL`), and `0` when the column is part of the grouping. This lets you distinguish the two types of `NULL` unambiguously.

### ROLLUP: Hierarchical Subtotals

`ROLLUP` is a shorthand for a specific, extremely common pattern: hierarchical grouping from most granular to least granular, accumulating subtotals at each level of the hierarchy. `ROLLUP(a, b, c)` is equivalent to:

```
GROUPING SETS (
    (a, b, c),   ← most granular
    (a, b),
    (a),
    ()           ← grand total
)
```

It takes the list of columns and generates all "prefix" combinations — all columns, then all but the last, then all but the last two, down to the empty set.

```sql
-- Sales report with subtotals at each geographic level:
-- country → region → city → grand total

SELECT
    country,
    region,
    city,
    SUM(revenue) AS revenue,
    GROUPING(country) AS gc,
    GROUPING(region)  AS gr,
    GROUPING(city)    AS gci
FROM sales
GROUP BY ROLLUP (country, region, city)
ORDER BY gc, gr, gci, country, region, city;

-- Result:
-- country | region | city     | revenue  | gc | gr | gci
-- --------+--------+----------+----------+----+----+----
-- USA     | East   | New York |  50000   |  0 |  0 |  0   ← city level
-- USA     | East   | Boston   |  30000   |  0 |  0 |  0
-- USA     | East   | NULL     |  80000   |  0 |  0 |  1   ← region subtotal
-- USA     | West   | LA       |  45000   |  0 |  0 |  0
-- USA     | West   | NULL     |  45000   |  0 |  0 |  1   ← region subtotal
-- USA     | NULL   | NULL     | 125000   |  0 |  1 |  1   ← country subtotal
-- NULL    | NULL   | NULL     | 125000   |  1 |  1 |  1   ← grand total
```

`ROLLUP` is the foundation of every "drill-down" report in business intelligence — where you have a total, click to see by country, click again to see by region, click again to see by city.

### CUBE: All Possible Combinations

`CUBE` generates every possible combination of the specified columns. `CUBE(a, b, c)` is equivalent to `GROUPING SETS` with all 2³ = 8 combinations:

```
GROUPING SETS (
    (a, b, c),
    (a, b),
    (a, c),
    (b, c),
    (a),
    (b),
    (c),
    ()
)
```

```sql
-- Full cross-tabular analysis: subtotals for every combination of
-- year, region, and product category

SELECT
    year,
    region,
    category,
    SUM(revenue) AS revenue
FROM sales
GROUP BY CUBE (year, region, category)
ORDER BY year NULLS LAST, region NULLS LAST, category NULLS LAST;
```

`CUBE` produces an enormous number of rows for many columns (2^n grouping combinations), but it is the natural choice for OLAP-style analysis where a user might want to slice and dice data by any combination of dimensions. Data warehouses use this heavily for pre-computing multi-dimensional summaries.

### Partial ROLLUP and Mixing Sets

`GROUPING SETS` can mix and match — including mixing with `ROLLUP` and `CUBE` nested inside:

```sql
-- Rollup within each year (year is fixed, then rollup over region and product)
GROUP BY year, ROLLUP(region, product)

-- Equivalent to:
GROUP BY GROUPING SETS (
    (year, region, product),
    (year, region),
    (year)
)
```

This generates hierarchical subtotals within each year but never collapses across years — a common need in annual business reports.

## Chapter 4: JSON Functions and Operators

### Why SQL Needs JSON

The relational model and the document model were, for decades, treated as fundamentally separate. You chose one or the other. But modern applications are messy — a product catalog might be mostly structured (name, price, category) but have a wildly variable attributes field (a t-shirt has size and color, a laptop has RAM and CPU and screen size). Storing this in separate tables requires complex schema gymnastics. Storing it as a JSON column in a relational table is often the pragmatic answer.

PostgreSQL's JSON support is among the deepest of any relational database. It offers two types: `JSON` (stored as-is, preserving whitespace and key order) and `JSONB` (stored in a decomposed binary format that is slower to input but faster to query and supports indexing). In virtually all practical cases, you want `JSONB`.

### The Core Operators

PostgreSQL provides a set of operators for navigating JSON structures. The most important ones are the arrow operators:

```
Operator  │ Returns    │ Meaning
──────────┼────────────┼──────────────────────────────────────────
->        │ jsonb      │ Get JSON object field by key, or array element by index
->>       │ text       │ Get JSON object field as text (not JSON)
#>        │ jsonb      │ Get nested element by path (array of keys)
#>>       │ text       │ Get nested element by path, as text
@>        │ boolean    │ Does the left JSON contain the right JSON? (containment)
<@        │ boolean    │ Is the left JSON contained in the right?
?         │ boolean    │ Does the key/element exist?
?|        │ boolean    │ Do ANY of these keys exist?
?&        │ boolean    │ Do ALL of these keys exist?
```

```sql
-- Sample data: a products table with a JSONB attributes column
-- {
--   "color": "blue",
--   "size": "M",
--   "specs": { "weight_kg": 0.5, "material": "cotton" },
--   "tags": ["casual", "summer"]
-- }

-- Get a top-level field as JSON:
SELECT attributes -> 'color' FROM products;
-- Result: "blue"  (with quotes — it is JSON text)

-- Get a top-level field as plain text:
SELECT attributes ->> 'color' FROM products;
-- Result: blue  (no quotes — it is a SQL text type)

-- Get a nested field using path:
SELECT attributes #>> '{specs, material}' FROM products;
-- Result: cotton

-- Get an array element (0-indexed):
SELECT attributes -> 'tags' -> 0 FROM products;
-- Result: "casual"

-- Filter: find all blue products:
WHERE attributes ->> 'color' = 'blue'

-- Filter using containment (JSONB only, very efficient with GIN index):
WHERE attributes @> '{"color": "blue", "size": "M"}'
-- Returns products where the JSON contains at least these key-value pairs

-- Filter: find products that have a 'discount' key:
WHERE attributes ? 'discount'
```

### JSON Construction Functions

PostgreSQL can build JSON from relational data — extremely useful for API response generation directly in SQL, avoiding multiple round trips:

```sql
-- Build a JSON object for each product
SELECT
    id,
    json_build_object(
        'id',       id,
        'name',     name,
        'price',    price,
        'category', category_name
    ) AS product_json
FROM products
JOIN categories ON products.category_id = categories.id;

-- Aggregate rows into a JSON array — perfect for one-query API responses
SELECT
    u.id,
    u.name,
    json_agg(
        json_build_object(
            'order_id', o.id,
            'amount',   o.amount,
            'date',     o.created_at
        ) ORDER BY o.created_at DESC
    ) AS orders
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- Result: each user row has an embedded JSON array of all their orders
-- {
--   "id": 1,
--   "name": "Alice",
--   "orders": [
--     {"order_id": 42, "amount": 150.00, "date": "2024-08-15T10:00:00Z"},
--     {"order_id": 38, "amount":  29.99, "date": "2024-08-10T14:30:00Z"}
--   ]
-- }
```

### Expanding JSON into Rows

The inverse of aggregation — expanding a JSON array into individual rows — is done with `json_array_elements()` or `jsonb_array_elements()`:

```sql
-- Expand a JSON array field into individual rows

SELECT
    p.id     AS product_id,
    p.name   AS product_name,
    tag.value::TEXT AS tag
FROM products p,
     jsonb_array_elements(p.attributes -> 'tags') AS tag;

-- Result:
-- product_id | product_name | tag
-- ---------- +--------------+---------
-- 1          | Blue T-Shirt | casual
-- 1          | Blue T-Shirt | summer
-- 2          | Red Hoodie   | casual
-- 2          | Red Hoodie   | winter
```

`jsonb_each()` expands a JSON object into key-value rows, which is how you can unpivot JSON keys dynamically:

```sql
-- Expand a JSON object's keys and values into rows
SELECT
    product_id,
    attr.key,
    attr.value
FROM products,
     jsonb_each(attributes) AS attr;
```

### JSON Path Queries (jsonpath)

PostgreSQL 12 introduced `jsonpath` — a language for querying JSON structures with filter expressions, similar to XPath for XML:

```sql
-- Find products where the nested weight is less than 1 kg
SELECT name
FROM products
WHERE jsonb_path_exists(
    attributes,
    '$.specs.weight_kg ? (@ < 1)'
);

-- Extract all tag values that start with 's'
SELECT jsonb_path_query_array(
    attributes,
    '$.tags[*] ? (@ starts with "s")'
) FROM products;
```

### Indexing JSON for Performance

The true power of JSONB over JSON is its ability to be indexed. A **GIN (Generalized Inverted Index)** on a JSONB column makes containment (`@>`) and existence (`?`) queries extremely fast:

```sql
-- Create a GIN index on the entire JSONB column (supports @>, ?, ?|, ?&)
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);

-- Create a B-tree index on a specific extracted field (supports =, <, >, BETWEEN)
CREATE INDEX idx_products_color ON products ((attributes ->> 'color'));

-- Now this query hits the index, not a full table scan:
SELECT * FROM products WHERE attributes @> '{"color": "blue"}';
```

## Chapter 5: Full-Text Search in SQL

### Full-Text Search as a Native Database Feature

Most developers' first instinct for search is to reach for Elasticsearch. But PostgreSQL has a remarkably capable built-in full-text search engine that is sufficient for many use cases — and it integrates directly with your relational data, eliminating the need for a separate search infrastructure, synchronization pipelines, and operational complexity.

PostgreSQL's full-text search is built on two special data types: `tsvector` (a sorted, deduplicated list of lexemes — normalized word forms) and `tsquery` (a search query with boolean operators). The `@@` operator checks whether a `tsquery` matches a `tsvector`.

### tsvector and tsquery: The Core Types

A `tsvector` is the preprocessed, searchable representation of a document. When you call `to_tsvector('english', 'Noise-cancelling wireless headphones for travel')`, the database applies the English text analysis pipeline — tokenizing, lowercasing, stemming, and removing stop words — and produces a sorted list of lexemes with their positions:

```sql
SELECT to_tsvector('english', 'Noise-cancelling wireless headphones for travel');
-- Result:
-- 'cancel':2 'headphon':4 'nois':1 'travel':6 'wireless':3
--
-- Notice:
-- 'for' is removed (stop word)
-- 'cancelling' → 'cancel' (stemmed)
-- 'headphones' → 'headphon' (stemmed)
-- Numbers after ':' are the positions in the original text
```

A `tsquery` is a search expression. `to_tsquery('english', 'wireless & headphones')` produces a query that requires both stems to be present. You can use `&` (AND), `|` (OR), `!` (NOT), and `<->` (phrase search — words must be adjacent):

```sql
SELECT to_tsquery('english', 'wireless & headphone');
-- Result: 'wireless' & 'headphon'  (both stems required)

SELECT to_tsquery('english', 'wireless | bluetooth');
-- Result: 'wireless' | 'bluetooth'  (either stem)

SELECT to_tsquery('english', 'noise <-> cancelling');
-- Result: 'nois' <-> 'cancel'  (phrase: "noise" must immediately precede "cancelling")
```

`plainto_tsquery()` and `websearch_to_tsquery()` are more user-friendly variants that accept natural language input and convert it to a query automatically — ideal for search boxes where users type free-form text:

```sql
-- websearch_to_tsquery understands Google-like syntax:
-- quotes for phrases, minus for exclusion, OR for alternatives
SELECT websearch_to_tsquery('english', '"noise cancelling" -gaming');
-- Result: 'nois' <-> 'cancel' & !'gaming'
```

### Setting Up Full-Text Search

The most efficient approach is to precompute the `tsvector` for each row and store it in a dedicated column, kept up to date with a trigger:

```sql
-- Add a search vector column
ALTER TABLE products ADD COLUMN search_vector TSVECTOR;

-- Populate it (combining name, description, and tags with different weights)
UPDATE products
SET search_vector =
    SETWEIGHT(to_tsvector('english', COALESCE(name, '')),        'A') ||
    SETWEIGHT(to_tsvector('english', COALESCE(description, '')), 'B') ||
    SETWEIGHT(to_tsvector('english', COALESCE(tags_text, '')),   'C');

-- A = highest weight, B = medium, C = lower — affects ranking

-- Create a GIN index for fast search
CREATE INDEX idx_products_search ON products USING GIN (search_vector);

-- Create a trigger to auto-update the vector on insert/update
CREATE OR REPLACE FUNCTION update_product_search_vector()
RETURNS TRIGGER AS $$
BEGIN
    NEW.search_vector :=
        SETWEIGHT(to_tsvector('english', COALESCE(NEW.name, '')),        'A') ||
        SETWEIGHT(to_tsvector('english', COALESCE(NEW.description, '')), 'B');
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER products_search_vector_update
BEFORE INSERT OR UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION update_product_search_vector();
```

### Searching and Ranking

With the vector column and index in place, searching is fast and the results can be ranked by relevance:

```sql
-- Search for "wireless headphones" with relevance ranking

SELECT
    id,
    name,
    ts_rank(search_vector, query)           AS rank,
    ts_rank_cd(search_vector, query)        AS rank_cover_density
FROM
    products,
    websearch_to_tsquery('english', 'wireless headphones') AS query
WHERE
    search_vector @@ query
ORDER BY
    rank DESC
LIMIT 20;
```

`ts_rank()` scores based on how frequently query terms appear in the document. `ts_rank_cd()` uses "cover density" — it also considers how close together the query terms appear. Both return a float between 0 and 1, with higher meaning more relevant.

### Highlighting Search Results

A polished search UI shows snippets of matching text with the search terms highlighted. `ts_headline()` does this automatically:

```sql
SELECT
    name,
    ts_headline(
        'english',
        description,
        websearch_to_tsquery('english', 'wireless headphones'),
        'MaxWords=20, MinWords=5, StartSel=<b>, StopSel=</b>'
    ) AS snippet
FROM products
WHERE search_vector @@ websearch_to_tsquery('english', 'wireless headphones');

-- Result:
-- name: BlueTech Pro Headphones
-- snippet: Premium <b>wireless headphones</b> with active <b>noise</b> cancelling...
```

## Chapter 6: Upsert Patterns — INSERT ... ON CONFLICT

### The Concurrency Problem at the Heart of Upsert

Every application eventually needs to perform an "upsert" — insert a row if it does not exist, or update it if it does. The naive approach is to check first (`SELECT`), then insert or update based on the result. But this approach has a **race condition**: two concurrent transactions can both check, both find no existing row, and both attempt to insert — causing a duplicate key error. Upsert solves this at the database level, atomically, without any race condition.

PostgreSQL's `INSERT ... ON CONFLICT` clause is one of the cleanest upsert mechanisms in any SQL database.

### ON CONFLICT DO NOTHING: Idempotent Inserts

The simplest form is `ON CONFLICT DO NOTHING` — "try to insert; if there is a conflict on the specified constraint, silently skip the row." No error is raised, no update happens. The insert is idempotent.

```sql
-- Insert a tag; silently skip if it already exists (unique name constraint)
INSERT INTO tags (name, slug)
VALUES ('PostgreSQL', 'postgresql')
ON CONFLICT (slug) DO NOTHING;

-- Bulk insert events from a stream; skip duplicates (idempotent ingestion)
INSERT INTO events (event_id, user_id, event_type, occurred_at)
VALUES
    ('evt_001', 1, 'page_view', '2024-08-15T10:00:00Z'),
    ('evt_002', 2, 'click',     '2024-08-15T10:01:00Z'),
    ('evt_001', 1, 'page_view', '2024-08-15T10:00:00Z')  -- duplicate
ON CONFLICT (event_id) DO NOTHING;
-- Inserts evt_001 and evt_002; silently skips the second evt_001
```

This pattern is invaluable for **at-least-once message processing** — when your message queue (like RabbitMQ) might deliver the same message twice, `DO NOTHING` ensures duplicate messages do not cause errors or double-processing.

### ON CONFLICT DO UPDATE: True Upsert

`ON CONFLICT DO UPDATE` specifies what to do when a conflict occurs: update the existing row. The `SET` clause inside `DO UPDATE` uses a special pseudo-table called `EXCLUDED` to refer to the row that was proposed for insertion (but conflicted). `EXCLUDED.column` gives you the value from the failed insert.

```sql
-- Upsert a user's profile: insert if new, update if existing

INSERT INTO user_profiles (user_id, display_name, bio, avatar_url, updated_at)
VALUES (42, 'Alice J.', 'Backend developer', 'https://cdn.example.com/alice.jpg', NOW())
ON CONFLICT (user_id)
DO UPDATE SET
    display_name = EXCLUDED.display_name,
    bio          = EXCLUDED.bio,
    avatar_url   = EXCLUDED.avatar_url,
    updated_at   = EXCLUDED.updated_at;
-- EXCLUDED refers to the row that was attempted to be inserted
```

The `ON CONFLICT (user_id)` specifies which constraint or column to check for conflicts. You can also reference a named constraint:

```sql
ON CONFLICT ON CONSTRAINT user_profiles_user_id_key DO UPDATE SET ...
```

### Selective Updates with WHERE in DO UPDATE

You can add a `WHERE` clause to `DO UPDATE` to conditionally decide whether to apply the update. This is powerful for versioned data — only update if the incoming data is newer:

```sql
-- Only update product price if the incoming price was set more recently
INSERT INTO products (sku, name, price, price_updated_at)
VALUES ('WIDGET-001', 'Premium Widget', 29.99, '2024-08-15T12:00:00Z')
ON CONFLICT (sku)
DO UPDATE SET
    price            = EXCLUDED.price,
    price_updated_at = EXCLUDED.price_updated_at
WHERE EXCLUDED.price_updated_at > products.price_updated_at;
-- Only update if the new price is newer than what we already have
```

### Increment Counters and Accumulate Values

A particularly elegant pattern: using upsert to maintain running counters or accumulated totals without separate SELECT → UPDATE logic:

```sql
-- Increment a page view counter; create the counter if it does not exist

INSERT INTO page_view_counts (page_slug, views, last_viewed_at)
VALUES ('about-us', 1, NOW())
ON CONFLICT (page_slug)
DO UPDATE SET
    views          = page_view_counts.views + 1,
    last_viewed_at = NOW();
-- page_view_counts.views refers to the CURRENT value in the table
-- EXCLUDED.views would be 1 (the proposed insert value)
-- We want current + 1, so we reference the table, not EXCLUDED
```

```sql
-- Upsert daily sales summary: add to existing total if the day already exists

INSERT INTO daily_sales_summary (sale_date, total_revenue, order_count)
VALUES ('2024-08-15', 1500.00, 12)
ON CONFLICT (sale_date)
DO UPDATE SET
    total_revenue = daily_sales_summary.total_revenue + EXCLUDED.total_revenue,
    order_count   = daily_sales_summary.order_count   + EXCLUDED.order_count;
```

### Multi-Row Upsert: Bulk Operations

`ON CONFLICT` works with multi-row `INSERT` statements, making it ideal for bulk upsert operations — syncing an entire dataset in one statement:

```sql
-- Sync a batch of product prices from an external feed

INSERT INTO products (sku, name, price, stock_quantity, updated_at)
VALUES
    ('SKU-001', 'Widget A', 9.99,  150, NOW()),
    ('SKU-002', 'Widget B', 14.99,  75, NOW()),
    ('SKU-003', 'Widget C', 24.99, 200, NOW())
ON CONFLICT (sku)
DO UPDATE SET
    price          = EXCLUDED.price,
    stock_quantity = EXCLUDED.stock_quantity,
    updated_at     = EXCLUDED.updated_at
WHERE products.updated_at < EXCLUDED.updated_at;
-- Only update rows where the incoming data is newer
```

This replaces what would otherwise be a complex application loop of individual SELECT-then-INSERT-or-UPDATE operations with a single, atomic, race-condition-free database statement.

## Chapter 7: The RETURNING Clause (PostgreSQL)

### Getting Data Back from Write Operations

In most SQL databases, `INSERT`, `UPDATE`, and `DELETE` are write-only operations. They modify data and return only a count of affected rows. But applications almost always need to know more: after inserting a new order, you need the database-generated `id` to return to the client. After updating a user's status, you need the new `updated_at` timestamp. After deleting expired sessions, you want to log which sessions were removed.

Without `RETURNING`, you must execute a write statement and then immediately execute a `SELECT` to retrieve the data — two round trips, with a potential race condition in between (another transaction could modify the row between your write and your read). PostgreSQL's `RETURNING` clause eliminates both problems: it returns data from the affected rows **as part of the write operation itself**, in a single atomic step.

### RETURNING After INSERT

The most common use case is retrieving the auto-generated primary key after an insert:

```sql
-- Insert a new user and immediately get back the generated id and created_at

INSERT INTO users (name, email, password_hash)
VALUES ('Alice Johnson', 'alice@example.com', 'hashed_password_here')
RETURNING id, created_at;

-- Result:
-- id  | created_at
-- ----+---------------------------
-- 42  | 2024-08-15T10:30:00.000Z
```

You can `RETURNING *` to get every column of the inserted row — useful when the table has columns with default values, computed values, or triggers that modify the data:

```sql
INSERT INTO orders (user_id, product_id, quantity)
VALUES (1, 7, 3)
RETURNING *;

-- Returns all columns, including:
-- - id (auto-generated sequence)
-- - total_price (computed by a trigger from quantity × product price)
-- - status (default value 'pending')
-- - created_at (DEFAULT NOW())
```

### RETURNING After UPDATE

`RETURNING` after `UPDATE` gives you the state of the row **after** the update was applied — invaluable for cache invalidation, audit logging, and returning fresh data to clients:

```sql
-- Update a user's subscription tier and return the full updated record

UPDATE users
SET
    subscription_tier = 'premium',
    subscription_start = NOW(),
    updated_at = NOW()
WHERE id = 42
RETURNING id, name, email, subscription_tier, subscription_start, updated_at;
```

You can also reference both the old and new values by joining the `RETURNING` result to the original table — though a simpler approach is to store the old value in a CTE:

```sql
-- Capture both before and after values using a CTE with RETURNING

WITH updated AS (
    UPDATE account_balances
    SET balance = balance - 500.00,
        updated_at = NOW()
    WHERE account_id = 101
    RETURNING account_id, balance AS new_balance, updated_at
)
INSERT INTO transaction_log (account_id, old_balance, new_balance, change_amount, logged_at)
SELECT
    u.account_id,
    ab.balance + 500.00  AS old_balance,   -- reverse-compute old balance
    u.new_balance,
    -500.00              AS change_amount,
    u.updated_at
FROM updated u
JOIN account_balances ab ON u.account_id = ab.account_id;
```

### RETURNING After DELETE

`RETURNING` after `DELETE` captures the deleted rows before they disappear — a powerful pattern for soft-delete conversions, audit trails, and message queue processing:

```sql
-- Archive expired sessions: delete them and insert into archive in one atomic operation

WITH deleted_sessions AS (
    DELETE FROM active_sessions
    WHERE last_active < NOW() - INTERVAL '24 hours'
    RETURNING *
)
INSERT INTO archived_sessions
SELECT *, NOW() AS archived_at
FROM deleted_sessions;
```

```sql
-- Process the "next available" job from a queue in a concurrency-safe way
-- (only one worker gets each job, even with many workers running simultaneously)

WITH claimed_job AS (
    DELETE FROM job_queue
    WHERE id = (
        SELECT id FROM job_queue
        WHERE status = 'pending'
        ORDER BY priority DESC, created_at ASC
        LIMIT 1
        FOR UPDATE SKIP LOCKED   -- skip rows locked by other workers
    )
    RETURNING *
)
SELECT * FROM claimed_job;
```

This last pattern is a complete, concurrency-safe job queue implementation in pure SQL. `FOR UPDATE SKIP LOCKED` ensures that two workers cannot claim the same job. `DELETE ... RETURNING` atomically removes the job from the queue and returns it to the worker — no job is ever processed twice, and no job is ever lost.

### Combining RETURNING with ON CONFLICT

`RETURNING` works seamlessly with `ON CONFLICT`, giving you the final state of a row regardless of whether it was inserted or updated:

```sql
-- Upsert a user session and always get back the current session data

INSERT INTO user_sessions (user_id, session_token, expires_at, created_at)
VALUES (42, 'tok_abc123', NOW() + INTERVAL '7 days', NOW())
ON CONFLICT (session_token)
DO UPDATE SET
    expires_at = EXCLUDED.expires_at,
    last_active = NOW()
RETURNING session_token, expires_at, last_active;

-- Whether the session was new (INSERT path) or refreshed (UPDATE path),
-- you always get back the current state of the session row.
```

### RETURNING in Batch Operations

`RETURNING` works with multi-row operations — when you insert, update, or delete multiple rows at once, `RETURNING` gives you all the affected rows:

```sql
-- Bulk-insert new products and get back all their generated IDs
-- (useful for linking to other tables immediately after)

INSERT INTO products (name, price, category_id)
VALUES
    ('Widget Alpha', 9.99,  1),
    ('Widget Beta',  14.99, 1),
    ('Widget Gamma', 24.99, 2)
RETURNING id, name;

-- Result:
-- id  | name
-- ----+-------------
-- 101 | Widget Alpha
-- 102 | Widget Beta
-- 103 | Widget Gamma
```

In a Go or Node.js application, this is gold — you can insert an entire slice/array of records in one query and get back all the generated IDs in one result set, without N+1 queries.

## Chapter 8: Composing Advanced Features Together

The features in this guide become exponentially more powerful when combined. Here is a realistic example that weaves together upsert, RETURNING, JSON functions, and CTEs in a single operation — the kind of thing that would otherwise require four separate queries and application-layer coordination:

```sql
-- Scenario: A product sync from an external API.
-- 1. Upsert each product (insert or update by SKU).
-- 2. For each upserted product, insert a sync audit record.
-- 3. Return a JSON summary of what was inserted vs. updated.

WITH
  -- Step 1: upsert all products, capture what changed
  upserted AS (
      INSERT INTO products (sku, name, price, attributes, synced_at)
      VALUES
          ('SKU-A', 'Widget Alpha', 9.99,  '{"color":"red"}',  NOW()),
          ('SKU-B', 'Widget Beta',  14.99, '{"color":"blue"}', NOW()),
          ('SKU-C', 'Widget Gamma', 24.99, '{"color":"green"}',NOW())
      ON CONFLICT (sku)
      DO UPDATE SET
          name       = EXCLUDED.name,
          price      = EXCLUDED.price,
          attributes = EXCLUDED.attributes,
          synced_at  = EXCLUDED.synced_at,
          version    = products.version + 1
      RETURNING id, sku, name, price,
                (xmax = 0) AS was_inserted   -- xmax=0 means it was an INSERT, not UPDATE
  ),

  -- Step 2: log the sync operation
  audit AS (
      INSERT INTO sync_audit (product_id, action, synced_at)
      SELECT
          id,
          CASE WHEN was_inserted THEN 'INSERT' ELSE 'UPDATE' END,
          NOW()
      FROM upserted
      RETURNING product_id, action
  )

-- Step 3: return a JSON summary
SELECT json_build_object(
    'total',    COUNT(*),
    'inserted', COUNT(*) FILTER (WHERE was_inserted),
    'updated',  COUNT(*) FILTER (WHERE NOT was_inserted),
    'skus',     json_agg(sku ORDER BY sku)
) AS sync_summary
FROM upserted;

-- Result:
-- {"total":3,"inserted":1,"updated":2,"skus":["SKU-A","SKU-B","SKU-C"]}
```

A single SQL statement that upserts products, logs an audit trail, and returns a structured JSON summary. In application code, this is one database round trip, fully atomic, race-condition-free.

## Epilogue: SQL as an Expressive Language

The features explored in this guide — set operations, pivoting, grouping sets, JSON functions, full-text search, upsert, and RETURNING — reveal that SQL is a far more expressive language than its reputation suggests. It is not merely a query language for fetching rows. It is a language for expressing complex data transformations, hierarchical aggregations, text search, document operations, and atomic multi-step mutations — all declaratively, all close to the data, all optimizable by the engine.

The principle that underlies all advanced SQL is the same one that underlies good backend engineering: push complexity to where it can be handled most efficiently. The database is not just a storage layer to be queried from outside. It is a computation engine, and the closer your logic lives to the data, the less that travels over the wire, the fewer round-trips your application makes, and the more the optimizer can do on your behalf.

Learning these features is not about memorizing syntax. It is about expanding your vocabulary for expressing what you want — so that when you encounter a problem, you recognize its shape and reach for the right tool.
