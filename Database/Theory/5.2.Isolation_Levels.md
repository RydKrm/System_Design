# Isolation Levels

### A Deep, Conceptual Journey from the Ground Up

> _Isolation is not a binary choice between "safe" and "fast" — it is a precise dial with named positions, each one a different contract about what concurrent transactions are allowed to see._

---

## Preface: The Illusion of Solitude

When you write a database transaction, you write it as if you are the only person in the world talking to the database. You read a value, you modify it, you write it back. The code is clean, the logic is clear. But in production, your transaction is never alone. Hundreds of transactions may be running simultaneously — other users placing orders, background jobs updating caches, analytics queries scanning millions of rows — and all of them are reading and writing the same tables, sometimes the same rows, at the same time as your transaction.

The question that isolation levels answer is: **what is your transaction allowed to see from this concurrent activity, and what is it protected from?** The answer to that question is not a single setting — it is a spectrum. At one end, your transaction sees everything, including half-finished work from other transactions that may yet be undone. At the other end, your transaction sees a perfectly frozen snapshot of the database as it was the moment you began, and the database guarantees that your results are identical to what you would have gotten if every transaction in the system had run one at a time, in some serial order.

Between those two extremes lie named positions — the four standard isolation levels — each one a deliberate trade-off between how much protection you get and how much concurrency the database allows. And understanding them requires first understanding, in full and painful detail, the specific things that can go wrong when isolation is absent or weak. Those things have names: dirty reads, non-repeatable reads, phantom reads, write skew, and lost updates.

This guide is the deep exploration of all of it — the phenomena, the levels, the mechanisms, and the engineering judgment about which to use when.

---

## Chapter 1: The Phenomena — What Goes Wrong Without Isolation

### Why We Must Understand the Problems Before the Solutions

Every isolation level is defined by which phenomena it prevents and which it allows. If you do not understand the phenomena — what they are, why they happen, and why they matter — the isolation levels are just names. But if you understand each phenomenon as a concrete failure mode with real consequences, the isolation levels become logical responses to those failure modes, and you can reason about which level you need for any given situation.

There are five phenomena to understand. The SQL standard formally defines the first three. The last two — write skew and lost updates — are not in the original SQL standard but are recognized in the database research literature and are critically important for real-world application design.

---

### Phenomenon 1: Dirty Read

A **dirty read** occurs when Transaction B reads data that Transaction A has written but not yet committed. The word "dirty" means uncommitted — the data is provisional, tentative, not yet real. Transaction A might roll back at any moment, undoing those changes entirely. But Transaction B has already read them and may have made decisions based on data that, from the database's official perspective, never existed.

The word "dirty" is apt in another sense: A's transaction is "contaminating" B's view of the world with its private, unfinished work.

```
Dirty Read — Step by Step:

  Time │  Transaction A                         │  Transaction B
  ─────┼────────────────────────────────────────┼──────────────────────────────────
   1   │  BEGIN;                                │
   2   │  UPDATE accounts                       │
   3   │    SET balance = balance - 10000       │
   4   │    WHERE id = 'alice';                 │
   5   │  -- A's change is in memory,           │
   6   │  -- NOT committed. Not yet real.       │  BEGIN;
   7   │                                        │  SELECT balance
   8   │                                        │    FROM accounts
   9   │                                        │    WHERE id = 'alice';
  10   │                                        │  -- B READS: $0 (from A's dirty write)
  11   │                                        │  -- B decides: Alice cannot afford anything
  12   │  ROLLBACK;                             │
  13   │  -- A's change undone. Alice: $10,000  │
  14   │                                        │  -- B's decision was based on data
  15   │                                        │  -- that officially NEVER EXISTED.
  16   │                                        │  -- Alice was wrongly blocked.

Why it matters:
  B made a real-world decision (blocking Alice's purchase) based on
  provisional data that was subsequently retracted. The database's
  official history contains no moment where Alice had $0 — B read
  a ghost.
```

Dirty reads are the most severe phenomenon. They allow one transaction to be polluted by the private, potentially-to-be-cancelled work of another. In a banking system, a dirty read could show a balance transfer in progress and trigger fraud alerts for money that was never actually moved. In an inventory system, a dirty read could show stock being reserved by a transaction that will later fail, causing legitimate purchases to be incorrectly rejected.

---

### Phenomenon 2: Non-Repeatable Read

A **non-repeatable read** occurs when Transaction B reads the same row twice within the same transaction and gets different values because Transaction A committed a change to that row between B's two reads. The read is "non-repeatable" because doing it again within the same transaction does not repeat the same result.

This is a subtler problem than dirty reads. Transaction B is only reading committed data — there are no ghosts, no provisional values. But the committed state of the database has changed between two reads within the same transaction, and B is now working with an inconsistent view of the world.

```
Non-Repeatable Read — Step by Step:

  Scenario: An airline booking system. B is preparing to show Alice
  a seat map and then confirm her selection.

  Time │  Transaction B (Alice's session)       │  Transaction A (Bob's session)
  ─────┼────────────────────────────────────────┼──────────────────────────────────
   1   │  BEGIN;                                │
   2   │  SELECT price FROM flights             │
   3   │    WHERE id = 'FL001';                 │
   4   │  -- B reads: $299                      │  BEGIN;
   5   │  -- B displays: "Your fare is $299"    │  UPDATE flights
   6   │                                        │    SET price = $399
   7   │                                        │    WHERE id = 'FL001';
   8   │                                        │  COMMIT; ← price is now $399
   9   │  -- User thinks about it for a minute  │
  10   │  SELECT price FROM flights             │
  11   │    WHERE id = 'FL001';                 │
  12   │  -- B reads: $399  ← DIFFERENT!        │
  13   │  -- B charges Alice $399 after showing │
  14   │  -- her $299.                          │

Why it matters:
  B showed Alice one price, then charged her a different one.
  Within a single logical interaction, the "fact" of the price changed.
  B's view of the world was not stable across its own transaction.
  This breaks the assumption that the world does not change beneath you
  while you are in the middle of processing it.
```

Non-repeatable reads are particularly dangerous in any flow where you read a value, perform some logic or show it to a user, and then act on the result of that read. The gap between "read" and "act" is where another transaction can change the data, making the action inconsistent with the read.

---

### Phenomenon 3: Phantom Read

A **phantom read** occurs when Transaction B executes the same range query twice within the same transaction and gets different sets of rows — because Transaction A inserted or deleted rows that match the query's predicate between the two executions. New rows appear like phantoms, or existing rows vanish.

The key distinction from non-repeatable reads is the scope: a non-repeatable read is about a single row changing its values, while a phantom read is about the set of rows matching a condition changing entirely — new rows appearing or existing rows disappearing from a range query.

```
Phantom Read — Step by Step:

  Scenario: A conference room booking system.
  B wants to book the last available room for 2:00 PM.

  Time │  Transaction B (booking)               │  Transaction A (another booking)
  ─────┼────────────────────────────────────────┼──────────────────────────────────
   1   │  BEGIN;                                │
   2   │  SELECT COUNT(*) FROM bookings         │
   3   │    WHERE room_date = '2024-08-15'      │
   4   │    AND time_slot = '14:00';            │
   5   │  -- B reads: 2 bookings out of 3 rooms │  BEGIN;
   6   │  -- B concludes: 1 room available      │  INSERT INTO bookings
   7   │                                        │    (room_id, room_date, time_slot)
   8   │                                        │    VALUES (3, '2024-08-15', '14:00');
   9   │                                        │  COMMIT; ← now all 3 rooms are booked
  10   │  SELECT COUNT(*) FROM bookings         │
  11   │    WHERE room_date = '2024-08-15'      │
  12   │    AND time_slot = '14:00';            │
  13   │  -- B reads: 3 bookings ← PHANTOM ROW  │
  14   │  -- The "available room" B was about   │
  15   │  -- to book no longer exists.          │

Why it matters:
  B was making a decision based on a count of rows — a set-level
  fact, not a single-row fact. The set changed beneath B.
  In the worst case: B checked, found 1 available room, then
  proceeded to book it — potentially double-booking the last room.
  Phantom reads affect any query that uses WHERE, HAVING, or
  aggregates over a set of rows. They are extremely common in
  inventory checks, capacity planning, and scheduling systems.
```

---

### Phenomenon 4: Lost Update

A **lost update** occurs when two transactions read the same value, both compute a new value based on what they read, and both write back — with the second write silently overwriting the first. The first transaction's update is "lost" — it happened, it committed, and then it was erased by the second transaction's write, which did not know about the first.

Lost updates are the classic **read-modify-write race condition**, and they are more dangerous than they look because they do not generate errors. Both transactions succeed. Both commit cleanly. And yet the net effect is wrong.

```
Lost Update — Step by Step:

  Scenario: Two support agents simultaneously close tickets for the same
  account, and each decrements the "open tickets" counter.

  Initial state: open_tickets = 5

  Time │  Transaction A (Agent 1)               │  Transaction B (Agent 2)
  ─────┼────────────────────────────────────────┼──────────────────────────────────
   1   │  BEGIN;                                │ BEGIN;
   2   │  SELECT open_tickets FROM accounts     │ SELECT open_tickets FROM accounts
   3   │    WHERE id = 1;                       │    WHERE id = 1;
   4   │  -- A reads: 5                         │  -- B reads: 5
   5   │  -- A computes: 5 - 1 = 4              │  -- B computes: 5 - 1 = 4
   6   │  UPDATE accounts                       │
   7   │    SET open_tickets = 4                │
   8   │    WHERE id = 1;                       │
   9   │  COMMIT; ← A wrote 4                   │
  10   │                                        │  UPDATE accounts
  11   │                                        │    SET open_tickets = 4
  12   │                                        │    WHERE id = 1;
  13   │                                        │  COMMIT; ← B also wrote 4

  Final state: open_tickets = 4

  Expected state: open_tickets = 3 (two tickets were closed)

  One full decrement was lost. Two agents closed tickets. Only one
  decrement was recorded. The data is now silently wrong, and no
  error was ever raised.

The safe alternative: atomic update (no read needed):
  UPDATE accounts SET open_tickets = open_tickets - 1 WHERE id = 1;
  -- This is a single atomic operation. No read-modify-write cycle.
  -- No race condition possible.
```

Lost updates are preventable at the application level (using atomic SQL operations like `SET col = col - 1` instead of read-then-write), at the database level (using `SELECT FOR UPDATE` to lock the row before reading), or by using REPEATABLE READ isolation (which detects the conflict and aborts one transaction). The danger is that they are silent — they corrupt data without raising any error.

### Phenomenon 5: Write Skew

**Write skew** is the most subtle of all the phenomena and the one that catches even experienced engineers off guard. It occurs when two transactions each read a set of rows, make decisions based on what they read, and write to different rows — yet their combined effect violates a constraint that neither transaction individually violated.

Write skew is not about two transactions writing to the same row (that is the lost update scenario). It is about two transactions writing to different rows, where each write is individually valid, but the combination of both writes leaves the database in an invalid state that neither transaction could have detected on its own.

```
Write Skew — Step by Step:

  Scenario: A hospital system requires that at least ONE doctor
  is always on call. Two doctors simultaneously try to go off call.

  Business Invariant: COUNT(on_call = TRUE) >= 1 at all times.

  Initial state:
    Doctor Alice: on_call = TRUE
    Doctor Bob:   on_call = TRUE
    (2 doctors on call — invariant satisfied)

  Time │  Transaction A (Alice going off call)  │  Transaction B (Bob going off call)
  ─────┼────────────────────────────────────────┼──────────────────────────────────
   1   │  BEGIN;                                │  BEGIN;
   2   │  SELECT COUNT(*) FROM doctors          │  SELECT COUNT(*) FROM doctors
   3   │    WHERE on_call = TRUE;               │    WHERE on_call = TRUE;
   4   │  -- A reads: 2 on-call doctors         │-- B reads: 2 on-call doctors
   5   │  -- A concludes: safe to go off call   │-- B concludes:safe to go off call
   6   │  -- (count will be 1, still ≥ 1)       │-- (count will be 1, still ≥ 1)
   7   │  UPDATE doctors                        │
   8   │    SET on_call = FALSE                 │
   9   │    WHERE name = 'Alice';               │
  10   │  COMMIT;                               │  UPDATE doctors
  11   │                                        │    SET on_call = FALSE
  12   │                                        │    WHERE name = 'Bob';
  13   │                                        │  COMMIT;

  Final state:
    Doctor Alice: on_call = FALSE
    Doctor Bob:   on_call = FALSE
    COUNT(on_call = TRUE) = 0  ← INVARIANT VIOLATED

  Neither transaction was wrong on its own:
  - A read 2 on-call doctors, correctly concluded removing one leaves 1.
  - B read 2 on-call doctors, correctly concluded removing one leaves 1.
  - Both transactions wrote to DIFFERENT rows (Alice vs Bob).
  - Neither transaction's individual action violated the invariant.
  - Yet their combined effect does.

  This is write skew: a constraint that spans multiple rows is
  violated by the combination of two individually-valid transactions.
```

Write skew is the reason why REPEATABLE READ isolation is sometimes not enough, even though it prevents dirty reads, non-repeatable reads, and phantom reads. The two transactions in the hospital example each have a consistent snapshot of the data — neither sees the other's write. But because the invariant spans multiple rows and the transactions write to different rows, REPEATABLE READ cannot detect the conflict. Only SERIALIZABLE isolation, which tracks the dependency between the two transactions' reads and writes, can detect and prevent write skew.

```
More Write Skew Examples:

  Meeting Room Double-Booking:
    Both users read "room is available at 3 PM"
    Both conclude it is safe to book it
    Both write bookings for the same room at 3 PM
    (same pattern — different meeting IDs written, same room overbooked)

  Username Uniqueness Race:
    Both users check "is username 'alice123' taken?" → both read: no
    Both conclude it is safe to register with that username
    Both write a user record with username 'alice123'
    (UNIQUE constraint catches this one — but not all invariants have DB constraints)

  Budget Overspending:
    Two departments simultaneously check remaining budget: $1000
    Both conclude they can spend $800
    Both write their expenditure
    Total spent: $1600 — $600 over budget
    (A real problem when the constraint is "total spending ≤ budget")
```

Write skew is the phenomenon that motivates using SERIALIZABLE isolation for any business logic that involves "check a condition across multiple rows, then act based on the result." If the condition could be affected by a concurrent transaction writing to the rows being checked, and if your transaction writes to rows that affect other transactions' conditions, you have a potential write skew scenario.

### The Complete Phenomena Summary

```
Five Concurrency Phenomena:

  ┌─────────────────────┬──────────────────────────────────────────────────────┐
  │ Phenomenon          │ What Happens                                         │
  ├─────────────────────┼──────────────────────────────────────────────────────┤
  │ Dirty Read          │ You read another transaction's uncommitted            │
  │                     │ (possibly-to-be-rolled-back) data.                   │
  ├─────────────────────┼──────────────────────────────────────────────────────┤
  │ Non-Repeatable Read │ You read the same row twice and get different values  │
  │                     │ because another transaction committed a change        │
  │                     │ between your two reads.                               │
  ├─────────────────────┼──────────────────────────────────────────────────────┤
  │ Phantom Read        │ You run the same range query twice and get a          │
  │                     │ different set of rows because another transaction     │
  │                     │ inserted or deleted matching rows between your reads. │
  ├─────────────────────┼──────────────────────────────────────────────────────┤
  │ Lost Update         │ Two transactions read the same value, both compute    │
  │                     │ a new value, both write back — the second write       │
  │                     │ silently overwrites the first. Both commit cleanly.   │
  ├─────────────────────┼──────────────────────────────────────────────────────┤
  │ Write Skew          │ Two transactions each read a set of rows, make        │
  │                     │ individually-valid decisions, and write to different  │
  │                     │ rows — yet their combined writes violate a            │
  │                     │ multi-row invariant that neither could see alone.     │
  └─────────────────────┴──────────────────────────────────────────────────────┘

  Severity (roughly):
  Dirty Read          → Most dangerous (reading ghost data)
  Lost Update         → Dangerous (silent data corruption, no error raised)
  Write Skew          → Dangerous (silent invariant violation, very hard to debug)
  Phantom Read        → Moderate (set-level inconsistency)
  Non-Repeatable Read → Moderate (single-row inconsistency within transaction)
```

## Chapter 2: READ UNCOMMITTED — The Open Door

### What It Is

READ UNCOMMITTED is the lowest isolation level. At this level, the database places essentially no restriction on what a transaction can see. A transaction running at READ UNCOMMITTED can read data written by other transactions that have not yet committed — it can read dirty data. Every phenomenon is possible: dirty reads, non-repeatable reads, phantom reads, lost updates, and write skew.

### Why It Exists

If READ UNCOMMITTED allows all anomalies, why does it exist at all? The answer is performance. With no isolation restrictions, the database does not need to take read locks or maintain version information for reads. Reads go directly to whatever the current in-memory state is, with no overhead. In scenarios where approximate data is acceptable and maximum throughput is the goal, READ UNCOMMITTED can be significantly faster.

```
READ UNCOMMITTED Characteristics:

  What you CAN see:          Other transactions' uncommitted writes
  What you CANNOT see:       Nothing is hidden from you

  Protections provided:      None for reads
  Performance:               Maximum read throughput (no read blocking)
  Risk:                      Reading data that never officially existed

  Phenomena prevented:       None (all five are possible)
  Phenomena allowed:         Dirty read, non-repeatable read, phantom read,
                             lost update, write skew
```

### In PostgreSQL: A Historical Note

PostgreSQL does not actually implement READ UNCOMMITTED in the traditional sense. When you set a transaction's isolation level to READ UNCOMMITTED in PostgreSQL, it silently treats it as READ COMMITTED. This is a deliberate design decision: PostgreSQL's MVCC architecture makes dirty reads unnecessary to support. The data version system always serves consistent committed data efficiently, so there is never a performance advantage to allowing dirty reads. READ UNCOMMITTED exists in PostgreSQL only for SQL standard compliance — so that applications setting this level do not crash — but it provides READ COMMITTED behavior.

```sql
-- In PostgreSQL, these behave identically:
BEGIN TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- Both give you READ COMMITTED semantics in PostgreSQL
```

### When READ UNCOMMITTED Is Used (In Databases That Support It)

In databases like MySQL (InnoDB) or SQL Server that do implement dirty reads at READ UNCOMMITTED, the level is occasionally used for:

**Approximate reporting:** Queries that scan huge tables for approximate counts or totals, where a small inaccuracy due to in-flight transactions is acceptable, and waiting for locks would cause unacceptable latency.

**Debugging and diagnostics:** A database administrator needs to quickly inspect what is happening inside a long-running transaction without waiting for it to commit or release locks.

**Log tailing:** A background process reading an append-only log table where the most recent uncommitted entries are acceptable to read because they will almost certainly commit (and even if they roll back, the reader will just ignore that entry next time).

In all these cases, the application explicitly accepts the risk of reading provisional data in exchange for not blocking on locks. It is a conscious choice, not an oversight.

## Chapter 3: READ COMMITTED — The Practical Default

### What It Is

READ COMMITTED is the default isolation level in PostgreSQL, Oracle, and SQL Server. At this level, a transaction can only read data that has been committed by other transactions — no dirty reads. But within a single transaction, each SQL statement gets a fresh view of the database as of the moment that statement executes. This means the view can change between statements: a value read by one statement may have changed by the time a second statement in the same transaction reads it.

```
READ COMMITTED Characteristics:

  What you CAN see:          Only committed data (no dirty reads)
  What you CANNOT see:       Uncommitted data from other transactions

  Protections provided:      Dirty reads → PREVENTED
  Phenomena still possible:  Non-repeatable read, phantom read,
                             lost update, write skew

  When the snapshot is taken: At the START of each individual STATEMENT
                              (not at the start of the transaction)

  Performance:               Good — reads never block on writer locks
                             in PostgreSQL's MVCC implementation
```

### How READ COMMITTED Works in PostgreSQL (MVCC)

In PostgreSQL's MVCC implementation, READ COMMITTED works by taking a new snapshot at the beginning of each statement within the transaction. This snapshot includes all transactions that were committed before the statement began executing.

```
READ COMMITTED Snapshot Model:

  Transaction B (READ COMMITTED):

  BEGIN;                        ← No snapshot taken yet

    Statement 1: SELECT ...     ← Snapshot 1 taken NOW
                                   Sees: everything committed before this moment
                                   Executes against Snapshot 1

    [Time passes. Other transactions commit changes.]

    Statement 2: SELECT ...     ← Snapshot 2 taken NOW (fresh!)
                                   Sees: everything committed before THIS moment
                                   Including commits that happened after Snapshot 1
                                   Executes against Snapshot 2

  COMMIT;

  Each statement sees the world as of when IT started.
  The transaction does not have a consistent view across statements.
  This is the source of non-repeatable reads and phantoms.
```

### The Non-Repeatable Read Under READ COMMITTED

Because each statement takes a fresh snapshot, reading the same row twice in two different statements within the same READ COMMITTED transaction can give different results if another transaction committed a change between the two reads.

```sql
-- Session A (READ COMMITTED — the default):
BEGIN;
  SELECT price FROM products WHERE id = 1;
  -- Returns: 100

  -- Meanwhile, Session B: UPDATE products SET price = 200 WHERE id = 1; COMMIT;

  SELECT price FROM products WHERE id = 1;
  -- Returns: 200 ← Non-repeatable read. Different value in same transaction.

COMMIT;
```

This is not a bug in PostgreSQL — it is the defined behavior of READ COMMITTED. The second statement takes a fresh snapshot, so it sees Session B's committed update.

### When READ COMMITTED Is Sufficient

READ COMMITTED is sufficient for the vast majority of web application operations. If each HTTP request is its own short transaction that performs a simple task — insert an order, update a profile, read a list — the lack of cross-statement consistency rarely matters because transactions are short enough that concurrent changes are unlikely to cause problems.

READ COMMITTED is particularly appropriate for:

**Simple CRUD operations:** Inserting, reading, updating, or deleting a single entity in one transaction. No multi-statement decision logic.

**Independent reads:** Reading data for display purposes where showing slightly stale data is acceptable (e.g., a product listing page — if a price changes mid-page-load, showing the old price is not catastrophic).

**High-throughput write workloads:** Because READ COMMITTED does not hold read locks between statements, write operations from other transactions do not block reads, allowing very high concurrency.

```sql
-- READ COMMITTED is fine for this:
BEGIN;
  INSERT INTO orders (customer_id, total) VALUES (1, 150.00);
  INSERT INTO order_items (order_id, product_id, qty) VALUES (lastval(), 42, 2);
COMMIT;
-- Both inserts are the writer's own data — no concurrent read-then-act logic.
```

### When READ COMMITTED Is NOT Sufficient

READ COMMITTED is dangerous for any pattern that reads a value and then makes a decision or computation based on that read, especially when that decision depends on the value remaining stable:

```sql
-- DANGEROUS under READ COMMITTED:
-- "If the account has enough balance, deduct the amount"

BEGIN;
  SELECT balance FROM accounts WHERE id = 1;
  -- Reads: $500. Sufficient for a $300 purchase.

  -- [Another transaction deducts $400. Balance is now $100.]

  UPDATE accounts SET balance = balance - 300 WHERE id = 1;
  -- This succeeds! Balance is now -$200. Overdraft!
  -- The SELECT saw $500 but the UPDATE happened on the real current $100.

COMMIT;
```

The SELECT and the UPDATE are two separate statements with two separate snapshots under READ COMMITTED. The SELECT saw the old balance; the UPDATE happened against the current state. The decision logic broke.

The fix here is not to change isolation levels but to use an atomic update: `UPDATE accounts SET balance = balance - 300 WHERE id = 1 AND balance >= 300`. This is a single statement that reads and writes atomically. No gap for concurrent changes.

## Chapter 4: REPEATABLE READ — The Stable Snapshot

### What It Is

REPEATABLE READ gives a transaction a consistent snapshot of the database taken at the moment the transaction begins. Every read within the transaction — no matter how many statements, no matter how much time passes — sees the database as it was at that single frozen moment. Concurrent commits by other transactions are invisible to the current transaction. The snapshot is stable for the lifetime of the transaction.

```
REPEATABLE READ Characteristics:

  What you CAN see:          Only data committed before YOUR transaction began
  What you CANNOT see:       Any commits by other transactions after you began

  Snapshot taken:            Once, at the START of the transaction
                             (not at the start of each statement)

  Phenomena prevented:       Dirty read ✓
                             Non-repeatable read ✓
                             Phantom read ✓ (in PostgreSQL's implementation)
                             Lost update ✓ (PostgreSQL detects & aborts)

  Phenomena still possible:  Write skew ✗ (not prevented)
                             Lost update ✗ (in standard SQL — PostgreSQL prevents it)

  Performance:               Slightly lower than READ COMMITTED
                             (snapshot maintained for transaction duration)
```

### The Per-Transaction Snapshot Model

The fundamental change from READ COMMITTED to REPEATABLE READ is when the snapshot is taken. Under READ COMMITTED, each statement gets a fresh snapshot. Under REPEATABLE READ, one snapshot is taken at the very beginning of the transaction, and every statement throughout the transaction uses that same snapshot.

```
REPEATABLE READ Snapshot Model:

  BEGIN;  ← SNAPSHOT TAKEN HERE. Frozen point-in-time.

    Statement 1: SELECT ...   ← Uses the opening snapshot
    Statement 2: SELECT ...   ← Uses the same opening snapshot
    Statement 3: SELECT ...   ← Uses the same opening snapshot
    ...
    Statement N: SELECT ...   ← STILL the same opening snapshot

  COMMIT;

  No matter how many other transactions committed during this time,
  all reads within this transaction see the world as it was at BEGIN.
  The world is frozen for you.
```

```sql
-- REPEATABLE READ example:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

  SELECT price FROM products WHERE id = 1;
  -- Returns: 100

  -- Meanwhile, another transaction: UPDATE products SET price = 200; COMMIT;

  SELECT price FROM products WHERE id = 1;
  -- Returns: 100 ← SAME. The snapshot is frozen at transaction start.
  -- The other transaction's commit is invisible to us.

COMMIT;
```

### Phantom Read Behavior in PostgreSQL

The SQL standard says REPEATABLE READ allows phantom reads — new rows inserted by other transactions can appear in range queries. But PostgreSQL's MVCC implementation actually prevents phantom reads at REPEATABLE READ as well, because the snapshot covers the entire database state at transaction start, including what rows exist. New rows inserted after the snapshot point are invisible to the transaction's queries, just as changed column values are.

```sql
-- PostgreSQL REPEATABLE READ — phantom prevention:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

  SELECT COUNT(*) FROM orders WHERE status = 'pending';
  -- Returns: 5

  -- Meanwhile: INSERT INTO orders (status) VALUES ('pending'); COMMIT;

  SELECT COUNT(*) FROM orders WHERE status = 'pending';
  -- Returns: 5 ← Still 5. The new row is invisible (post-snapshot).
  -- PostgreSQL's implementation prevents phantoms at REPEATABLE READ.

COMMIT;
```

This is one area where PostgreSQL's behavior is stronger than the SQL standard requires for REPEATABLE READ. It is a consequence of the MVCC snapshot system, not a special feature.

### Lost Update Detection in PostgreSQL

PostgreSQL's REPEATABLE READ goes one step further than most databases: it detects lost updates and aborts one of the conflicting transactions rather than silently allowing the data corruption.

The scenario: two transactions both read a value, both compute a new value based on the read, and both try to write back. In PostgreSQL at REPEATABLE READ, the second transaction to commit detects that the row it read has been modified since its snapshot was taken, and raises an error: `ERROR: could not serialize access due to concurrent update`.

```
Lost Update Prevention at REPEATABLE READ (PostgreSQL):

  Initial: counter = 0

  Transaction A:              Transaction B:
  BEGIN (REPEATABLE READ)     BEGIN (REPEATABLE READ)
  SELECT counter → 0          SELECT counter → 0
  -- compute: 0 + 1 = 1       -- compute: 0 + 1 = 1
  UPDATE counter = 1
  COMMIT                      UPDATE counter = 1
                              ERROR: could not serialize access
                              due to concurrent update
                              → Transaction B must ROLLBACK and RETRY

  Final: counter = 1 (correct — only one update succeeded)

  Without this detection (standard SQL REPEATABLE READ):
  Final: counter = 1 (wrong — two increments, only one recorded)
```

This detection is crucial. It turns a silent data corruption (the classical lost update) into a visible error that the application can handle by retrying. It is not perfect — write skew is still possible — but it catches the most common read-modify-write race condition.

### When REPEATABLE READ Is the Right Choice

REPEATABLE READ is the appropriate level for:

**Multi-statement decisions based on stable data:** When your transaction reads multiple values and makes a decision that depends on all of them remaining consistent — like "check available inventory, calculate shipping, then place the order" — REPEATABLE READ ensures the inventory count does not change between your check and your order placement.

**Long-running read transactions:** Report generation, data exports, and backups that scan large amounts of data and need a consistent snapshot across many queries. READ COMMITTED would give you an inconsistent view as other transactions commit during your long scan.

**Any read-modify-write pattern on a single row:** PostgreSQL's lost update detection at REPEATABLE READ makes single-row read-modify-write patterns safe. Two transactions cannot both successfully increment the same counter — one will be forced to retry.

```sql
-- Safe read-modify-write at REPEATABLE READ:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

  SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
  -- (FOR UPDATE still useful to signal intent and order lock acquisition)

  UPDATE accounts SET balance = balance - 300 WHERE id = 1;
  -- If another transaction modified this row since our BEGIN,
  -- PostgreSQL will abort this transaction with a serialization error.
  -- We must retry. But we will never silently corrupt the data.

COMMIT;
```

## Chapter 5: SERIALIZABLE — The Gold Standard

### What It Is

SERIALIZABLE is the highest isolation level and the only one that completely eliminates all concurrency phenomena, including write skew. A transaction at the SERIALIZABLE level is guaranteed to produce results that are identical to what it would have produced if it had been the only transaction running — or more precisely, as if all concurrent transactions had been executed serially (one at a time, in some order), even though they actually ran concurrently.

```
SERIALIZABLE Characteristics:

  What you CAN see:          Only data committed before YOUR transaction began
  What you CANNOT see:       Any interference from concurrent transactions

  Phenomena prevented:       ALL five — dirty read, non-repeatable read,
                             phantom read, lost update, write skew ← ALL

  The guarantee:             Your results are identical to what you would get
                             if transactions ran one at a time, in some order.

  Performance:               Lowest throughput — some transactions may be
                             aborted with serialization errors and must retry.

  PostgreSQL implementation:  Serializable Snapshot Isolation (SSI) —
                             optimistic, track-and-detect approach
                             (not traditional lock-based serialization)
```

### The Write Skew Problem and Why REPEATABLE READ Cannot Solve It

Recall the on-call doctor scenario. Two doctors simultaneously check the count of on-call doctors, both see 2, both decide it is safe to go off call, and both update their own row. Neither transaction's individual action is wrong. But together they violated the invariant.

At REPEATABLE READ, both transactions see a stable snapshot — they each see 2 on-call doctors throughout their transaction. But the snapshot does not prevent them from both writing to different rows based on that snapshot. The snapshot prevents you from seeing concurrent changes; it does not prevent concurrent transactions from making conflicting decisions based on the same snapshot.

SERIALIZABLE is the only level that catches this. It does so by tracking what data each transaction read and what it wrote, then detecting whether the combined pattern of reads and writes could have occurred in any serial order. If not, one transaction is aborted.

```
Write Skew Under SERIALIZABLE:

  Transaction A reads on-call count → 2
  Transaction B reads on-call count → 2

  Transaction A writes: Alice.on_call = FALSE
  Transaction B writes: Bob.on_call = FALSE

  At SERIALIZABLE, the database detects:
  "A read the on-call count, which depends on Bob's row.
   B changed Bob's row. Therefore A's read is invalidated by B's write.
   These transactions cannot be serialized. Abort one."

  ERROR: could not serialize access due to read/write dependencies
  among transactions

  → One transaction aborts. The other succeeds.
  → The surviving transaction ran alone (serially), so the invariant holds.
```

### Serializable Snapshot Isolation (SSI) — PostgreSQL's Implementation

PostgreSQL implements SERIALIZABLE using **Serializable Snapshot Isolation (SSI)**, introduced in PostgreSQL 9.1 based on research by Cahill et al. (2008). SSI is a profoundly clever algorithm that achieves full serializability without blocking reads with write locks.

Traditional serializable implementations (used by databases like MySQL InnoDB at SERIALIZABLE level) use **two-phase locking (2PL)**: every read takes a shared lock, every write takes an exclusive lock, and no lock is released until the transaction commits. This prevents all anomalies but allows essentially no concurrency — a reading transaction blocks all writers, and vice versa.

SSI takes a completely different approach: **optimistic concurrency with dependency tracking**. Transactions run concurrently without blocking each other. But the database tracks two kinds of dependencies between transactions:

- **rw-dependencies (read-write anti-dependencies):** Transaction A read a set of rows. Transaction B wrote to those rows (or inserted rows that would have matched A's predicate). B "anti-depends" on A.
- **wr-dependencies (write-read dependencies):** Transaction B read rows that Transaction A had written.

SSI's key insight, proven by the research, is that if you find a cycle of rw-anti-dependencies among concurrent transactions, those transactions cannot be serialized, and at least one must be aborted. Specifically, a dangerous pattern called an **anti-dependency cycle** — where A rw-anti-depends on B and B rw-anti-depends on A (or a longer cycle) — always indicates a potential serialization failure.

```
SSI Dependency Tracking:

  Doctor Scenario:
  A reads: on_call_count (SELECT COUNT WHERE on_call=TRUE) → depends on Bob's row
  B reads: on_call_count (SELECT COUNT WHERE on_call=TRUE) → depends on Alice's row
  A writes: Alice.on_call = FALSE → affects B's read (Alice's row)
  B writes: Bob.on_call = FALSE → affects A's read (Bob's row)

  Dependency graph:
    A ──rw──► B  (A's write of Alice's row affects B's read of on_call_count)
    B ──rw──► A  (B's write of Bob's row affects A's read of on_call_count)

  CYCLE DETECTED: A → B → A

  One transaction is aborted. No invariant violation. ✓

SSI's advantages over 2PL:
  ✓ Readers never block writers
  ✓ Writers never block readers
  ✗ Some transactions abort that would not abort under 2PL
    (SSI may over-abort: abort safe transactions that looked like
     they might be in a cycle but were not actually conflicting)
  → Applications must implement retry logic
```

### The Retry Requirement

SERIALIZABLE transactions at PostgreSQL can fail with `ERROR: could not serialize access due to read/write dependencies among transactions` (SQLSTATE 40001). This is not an application error — it is the database correctly detecting a potential serialization violation and aborting one transaction to preserve correctness. The aborted transaction must be retried from the beginning.

This retry requirement is the primary operational complexity of SERIALIZABLE isolation. Your application must be designed to handle these errors gracefully:

```go
// Node.js example with retry logic for SERIALIZABLE transactions
async function withSerializable(client, fn) {
    const MAX_RETRIES = 5;

    for (let attempt = 0; attempt < MAX_RETRIES; attempt++) {
        await client.query('BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE');
        try {
            const result = await fn(client);
            await client.query('COMMIT');
            return result;
        } catch (err) {
            await client.query('ROLLBACK');
            // PostgreSQL serialization failure error code: 40001
            if (err.code === '40001' && attempt < MAX_RETRIES - 1) {
                // Exponential backoff before retry
                await new Promise(r => setTimeout(r, Math.pow(2, attempt) * 10));
                continue; // retry the entire transaction
            }
            throw err; // non-retryable error, or max retries exceeded
        }
    }
    throw new Error('Max serialization retries exceeded');
}

// Usage:
await withSerializable(client, async (tx) => {
    const doctors = await tx.query(
        'SELECT COUNT(*) FROM doctors WHERE on_call = TRUE'
    );
    if (doctors.rows[0].count <= 1) {
        throw new Error('Cannot go off call: you are the last on-call doctor');
    }
    await tx.query(
        'UPDATE doctors SET on_call = FALSE WHERE id = $1',
        [doctorId]
    );
});
// If write skew is detected, this entire function is retried automatically.
```

### When SERIALIZABLE Is Essential

SERIALIZABLE isolation is the right choice when your business logic involves reading a set of rows and making a decision based on that set, then writing rows that affect the same condition — and the business invariant must always hold, with no exceptions.

**Financial operations with complex invariants:** "Transfer funds only if the source account has sufficient balance AND the destination account is not frozen AND the daily transfer limit has not been exceeded." These conditions span multiple tables and must all be checked atomically.

**Scheduling and booking systems:** "Book this slot only if it is not already booked by someone else in the same time window." The phantom read and write skew risks are both present.

**Inventory allocation:** "Reserve these items only if enough stock is available, considering all concurrent reservations." A phantom read of the reservation table combined with a write to add a new reservation is exactly the write skew scenario.

**Any "check-then-act" across multiple rows:** The general pattern is: if you read multiple rows to make a decision, and that decision determines what you write, and the correctness of the system requires that the decision was made on a stable view of the data that no concurrent transaction could invalidate — use SERIALIZABLE.

## Chapter 6: The Complete Isolation Level Map

### Phenomena vs. Isolation Levels

```
Standard SQL Definition:

                      │ Dirty │ Non-Rep. │ Phantom │ Lost   │ Write  │
  Isolation Level     │ Read  │ Read     │ Read    │ Update │ Skew   │
  ────────────────────┼───────┼──────────┼─────────┼────────┼────────┤
  READ UNCOMMITTED    │  ✗    │   ✗      │   ✗     │  ✗     │  ✗    │
  READ COMMITTED      │  ✓    │   ✗      │   ✗     │  ✗     │  ✗    │
  REPEATABLE READ     │  ✓    │   ✓      │   ✗*    │  ✗*    │  ✗    │
  SERIALIZABLE        │  ✓    │   ✓      │   ✓     │  ✓     │  ✓    │

  ✓ = Prevented   ✗ = Possible (may occur)

PostgreSQL Actual Behavior:

                      │ Dirty │ Non-Rep. │ Phantom │ Lost   │ Write  │
  Isolation Level     │ Read  │ Read     │ Read    │ Update │ Skew   │
  ────────────────────┼───────┼──────────┼─────────┼────────┼────────┤
  READ UNCOMMITTED    │  ✓    │   ✗      │   ✗     │  ✗     │  ✗    │ (same as RC)
  READ COMMITTED      │  ✓    │   ✗      │   ✗     │  ✗     │  ✗    │
  REPEATABLE READ     │  ✓    │   ✓      │   ✓**   │  ✓**   │  ✗    │
  SERIALIZABLE        │  ✓    │   ✓      │   ✓     │  ✓     │  ✓    │

  *  Standard SQL says REPEATABLE READ allows these.
  ** PostgreSQL's MVCC and lost-update detection prevent these even at RR.
     This is stronger than the standard requires.
```

### Choosing the Right Level: A Decision Framework

```
Decision Framework for Isolation Level:

  START: What does my transaction do?
  │
  ├── Simple single-statement read (SELECT for display, no decision logic)
  │   → READ COMMITTED (default). Fine.
  │
  ├── Simple single-statement write (INSERT, UPDATE, DELETE one thing)
  │   → READ COMMITTED (default). Fine.
  │
  ├── Multi-statement transaction, but reads and writes are independent
  │   (e.g., write to table A, then write to table B, no condition on reads)
  │   → READ COMMITTED. Fine.
  │
  ├── Read a single row, compute something, write back to SAME row
  │   (classic read-modify-write on one row)
  │   → REPEATABLE READ or SELECT FOR UPDATE at READ COMMITTED.
  │     PostgreSQL's RR detects lost updates on the same row.
  │
  ├── Read multiple rows to make a decision, then write based on that decision
  │   ├── Writes go to the SAME rows you read?
  │   │   → REPEATABLE READ is often sufficient.
  │   │     PostgreSQL detects the conflict and aborts one writer.
  │   │
  │   └── Writes go to DIFFERENT rows than you read?
  │       (Classic write skew scenario)
  │       → SERIALIZABLE. Only level that prevents write skew.
  │
  └── Long-running read transaction (report, export, backup)
      needs consistent snapshot across many queries
      → REPEATABLE READ. Stable snapshot for the whole transaction.
```

## Chapter 7: Practical Patterns and Application Strategies

### Pattern 1: The Optimistic Locking Alternative

For applications that cannot afford the retry overhead of SERIALIZABLE transactions, **optimistic locking** is an application-level strategy that prevents lost updates and some write skew scenarios without relying on database isolation levels. Each row has a `version` column. When you read a row, you note its version. When you write it back, you assert that the version has not changed. If it has, someone else modified it — you retry.

```sql
-- Optimistic locking: version-based conflict detection

-- Step 1: Read with version
SELECT balance, version FROM accounts WHERE id = 1;
-- Returns: balance=1000, version=5

-- Step 2: Write back with version assertion
UPDATE accounts
SET balance = 700, version = version + 1
WHERE id = 1 AND version = 5;  -- ← the assertion
-- If another transaction changed version to 6, this UPDATE affects 0 rows.
-- Application checks rows affected: if 0, conflict detected → retry.
```

Optimistic locking works well when conflicts are rare — the optimistic assumption is that you will usually succeed on the first try. When conflicts are frequent, pessimistic locking (SELECT FOR UPDATE) or SERIALIZABLE isolation is more appropriate, because optimistic locking retries on every conflict, potentially causing thrashing.

### Pattern 2: Explicit Locking with SELECT FOR UPDATE

`SELECT FOR UPDATE` is a middle ground: it reads rows and immediately acquires exclusive write locks on them, preventing any other transaction from modifying or locking the same rows until you commit. This is **pessimistic locking** — you assume a conflict might happen, so you lock preemptively.

```sql
-- Correct inventory decrement with pessimistic locking
BEGIN;

  SELECT stock_quantity FROM products
  WHERE id = 42
  FOR UPDATE;  -- ← Lock this row NOW. Others must wait.
  -- Returns: 5

  -- No other transaction can change product 42's row until we commit.
  -- The count is stable. We can safely decrement.

  UPDATE products
  SET stock_quantity = stock_quantity - 1
  WHERE id = 42;

COMMIT;  -- lock released here
```

`SELECT FOR UPDATE SKIP LOCKED` is a variant used in queue processing: lock available rows but skip any that are already locked by other transactions. This allows multiple workers to process a queue concurrently without competing for the same item:

```sql
-- Concurrent queue processing with SKIP LOCKED
BEGIN;

  SELECT id, payload FROM job_queue
  WHERE status = 'pending'
  ORDER BY created_at ASC
  LIMIT 1
  FOR UPDATE SKIP LOCKED;  -- ← Grab one job that nobody else has locked
  -- Returns: one unclaimed job

  UPDATE job_queue SET status = 'processing' WHERE id = $returned_id;

COMMIT;
-- The job is now claimed by this worker. Other workers get different jobs.
```

### Pattern 3: Advisory Locks for Application-Level Serialization

PostgreSQL provides **advisory locks** — application-defined locks that are not attached to any particular row or table but are managed by the application using named or numbered identifiers. They are useful for serializing access to a logical resource that does not map neatly to a single row.

```sql
-- Advisory lock: serialize access to a logical resource
-- pg_try_advisory_xact_lock returns FALSE if the lock is already held
BEGIN;

  SELECT pg_try_advisory_xact_lock(hashtext('user_action:' || user_id::text));
  -- Returns TRUE if we got the lock, FALSE if another session holds it

  -- If FALSE: raise error or return "try again later"
  -- If TRUE: proceed with the operation, lock is held until COMMIT

  -- ... perform the operation ...

COMMIT;  -- advisory lock automatically released at transaction end
```

## Chapter 8: Monitoring and Diagnosing Isolation Problems

### Seeing Isolation Level in Action

PostgreSQL provides several tools for understanding what is happening with transactions and isolation:

```sql
-- See your current transaction's isolation level
SHOW transaction_isolation;

-- See all transactions currently running and their isolation levels
SELECT pid, usename, application_name, state,
       isolation_level, wait_event_type, wait_event,
       query_start, query
FROM pg_stat_activity
WHERE state != 'idle';

-- Find transactions that have been waiting for locks a long time
SELECT pid, now() - pg_stat_activity.query_start AS duration,
       query, state, wait_event_type, wait_event
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
  AND (now() - query_start) > INTERVAL '30 seconds';

-- Find what lock a waiting transaction is waiting for
SELECT blocked_locks.pid     AS blocked_pid,
       blocking_locks.pid    AS blocking_pid,
       blocked_activity.query AS blocked_statement,
       blocking_activity.query AS current_statement_in_blocking_process
FROM  pg_catalog.pg_locks  blocked_locks
JOIN  pg_catalog.pg_stat_activity blocked_activity
      ON blocked_activity.pid = blocked_locks.pid
JOIN  pg_catalog.pg_locks  blocking_locks
      ON blocking_locks.locktype = blocked_locks.locktype
      AND blocking_locks.pid != blocked_locks.pid
      AND blocking_locks.granted
JOIN  pg_catalog.pg_stat_activity blocking_activity
      ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

### Serialization Failure Rate Monitoring

If you use SERIALIZABLE isolation, tracking serialization failure rates tells you how often your application is retrying and whether contention is excessive:

```sql
-- Count of transactions that were rolled back due to serialization failures
-- (compare to total commits to understand the retry overhead)
SELECT schemaname, relname,
       n_live_tup, n_dead_tup,
       seq_scan, idx_scan
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- Application-level: log and count serialization failures (SQLSTATE 40001)
-- If your retry rate exceeds ~5%, consider whether SERIALIZABLE is necessary
-- for all operations or only specific high-risk ones.
```

## Epilogue: The Right Level for the Right Moment

Isolation levels are not a global setting you pick once for your entire application. They are per-transaction choices, and the right choice depends on what that specific transaction is trying to do.

Most of your application's transactions can run safely at READ COMMITTED — simple reads, simple writes, short-lived operations where the window for concurrent interference is small. A subset of your transactions — those that read multiple rows to make decisions — need REPEATABLE READ to ensure the snapshot is stable across their decision logic. A small but critical subset — those where the correctness of the business logic depends on no concurrent transaction changing the conditions your decision was based on — need SERIALIZABLE, and they need retry logic.

The mistake most developers make is one of two extremes: either they run everything at READ COMMITTED and accept silent bugs that manifest as rare, hard-to-reproduce data anomalies, or they run everything at SERIALIZABLE and then wonder why their throughput is lower than expected and their logs are full of retry noise. Neither extreme is right. The discipline is in identifying which transactions need which level — and that discipline requires knowing, precisely and concretely, what the five phenomena are, which level prevents each one, and what your specific transaction is actually doing.

An engineer who can look at a `SELECT ... WHERE ... ; UPDATE ...` transaction and immediately recognize it as a read-modify-write pattern that is vulnerable to lost updates at READ COMMITTED — and knows to add `FOR UPDATE` or escalate to REPEATABLE READ — is worth more than one who knows all the isolation level names but does not feel what they protect against in their bones.

That feeling, that instinct for concurrency hazards, is what this guide was trying to build.
