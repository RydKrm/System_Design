## 1. Introduction — What Are System Design Patterns?

When engineers build large-scale systems, they quickly discover that many problems are not unique. The challenge of preventing a single user from making ten thousand API calls per second is a problem that every public API has faced. The challenge of delivering a new post to ten million followers in near-real-time is a problem that every social platform grapples with. The challenge of taking a long, unwieldy URL and producing a short, shareable alias is a problem that dozens of companies have solved — in broadly similar ways, with broadly similar trade-offs.

A **system design pattern** is a reusable architectural solution to a category of recurring problems. Just as software design patterns (like the Observer pattern or the Factory pattern) describe solutions at the code level, system design patterns describe solutions at the infrastructure and architecture level — how data flows between services, how state is managed under load, how consistency is preserved when many things happen at once.

Learning these patterns is not about memorizing diagrams to reproduce in interviews. It is about building an intuition for how forces like scale, latency, and consistency interact with each other, and how certain structural choices elegantly resolve the tensions between those forces. The three patterns examined in this document — URL shortening, rate limiting, and notification fan-out — are among the most instructive examples in the field, because each one reveals a different fundamental tension in distributed system design and offers a different lens through which to understand it.

## 2. URL Shortener — Hash Storage and Redirect Counters

### 2.1 The Problem — Making Long URLs Short and Measurable

The URL shortener is one of the most beloved introductory system design problems precisely because it is deceptively simple on the surface and surprisingly rich beneath it. The core requirement seems almost trivial: given a long URL like `https://www.example.com/articles/2024/how-to-learn-system-design-from-scratch?ref=newsletter&utm_source=email`, produce a short alias like `https://short.ly/aB3xQk` that, when visited, redirects the user to the original long URL. But hidden within this simple description are a cascade of interesting engineering decisions that touch on hashing, database design, caching, counter management, and distributed system behavior.

Before designing anything, a thoughtful engineer asks: what are the actual scale requirements? A URL shortener for a small internal team is a fundamentally different engineering problem from one serving hundreds of millions of users. For the purposes of this discussion, let us imagine a service that must handle a substantial public workload — say, one hundred million shortened URLs created in total, with ten thousand new URLs created per day and one hundred million redirect requests served per day. At this scale, reads (redirects) vastly outnumber writes (URL creation) — roughly ten thousand reads for every one write — making this an intensely read-heavy system. This ratio will shape every design decision that follows.

### 2.2 Generating the Short Code — The Hashing Strategy

The central algorithmic challenge of a URL shortener is generating a short code — typically six to eight alphanumeric characters — that maps uniquely to a long URL. Using the characters A-Z, a-z, and 0-9 gives us 62 possible characters. Six characters in base-62 gives us 62⁶ = approximately 56 billion possible codes. Eight characters gives us approximately 218 trillion. Even six characters is sufficient for hundreds of billions of unique URLs, far more than any foreseeable service would need.

There are two broad approaches to generating this code. The first is **hash-based generation**: take the long URL (or a unique identifier), pass it through a hashing function like MD5 or SHA-256, and take the first six characters of the resulting hexadecimal or base-62 encoding. This approach is deterministic — the same long URL always produces the same code — which is appealing because if two users try to shorten the same URL, they receive the same short code, avoiding duplication.

The second approach is **ID-based generation**: use a globally unique auto-incrementing integer identifier (the database's primary key) and encode it in base-62. The first URL stored gets ID 1, which encodes to `"1"`. The millionth URL stored gets ID 1,000,000, which encodes to `"4c92"`. This approach is entirely collision-free by construction — every entry in the database has a unique ID, and therefore every short code is unique — but different URLs always get different codes even if they are identical, which may or may not be desirable.

```
ID-to-Short-Code Encoding — Base-62 Conversion
=================================================

  Characters: "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"
  Index:       0         1         2         3         4         5         6

  Example: Encode ID = 1,000,000

  1,000,000 / 62 = 16,129 remainder 2   --> character[2]  = '2'
  16,129    / 62 = 260    remainder 9   --> character[9]  = '9'
  260       / 62 = 4      remainder 12  --> character[12] = 'C'
  4         / 62 = 0      remainder 4   --> character[4]  = '4'

  Read remainders bottom-to-top: "4C92"

  short code for ID 1,000,000 = "4C92"
  short code for ID 1,000,001 = "4C93"
  short code for ID 1,000,062 = "4C9A"

  6-character base-62 can represent up to 62^6 = 56.8 billion unique URLs.
```

The hash-based approach introduces a complication: **hash collisions**. Two different long URLs may produce the same first six characters of their hash output. In practice, this is statistically rare with a good hash function over a modest corpus, but it is not impossible. The engineering solution is straightforward: when generating a code, check the database to verify the code does not already exist. If a collision is detected, append a salt (a small random string) to the input before hashing again, and repeat until a unique code is found. With six-character base-62 codes and a database of even hundreds of millions of entries, the probability of collision is low enough that this retry loop terminates almost immediately in the overwhelming majority of cases.

### 2.3 The Database Schema — Simplicity by Design

The database backing a URL shortener is refreshingly simple. At its core, the system needs a single table that maps short codes to long URLs, with some additional metadata for analytics and management.

```
URL Shortener — Core Database Schema (PostgreSQL)
===================================================

  Table: urls
  +----------------+------------------+---------------------------+
  | Column         | Type             | Description               |
  +----------------+------------------+---------------------------+
  | id             | BIGSERIAL PK     | Auto-incrementing ID      |
  |                |                  | (used for base-62 encode) |
  | short_code     | VARCHAR(8) UNIQUE| The short alias ("aB3xQk")|
  | long_url       | TEXT             | The original long URL     |
  | created_at     | TIMESTAMPTZ      | When the link was created |
  | expires_at     | TIMESTAMPTZ NULL | Optional expiration time  |
  | user_id        | BIGINT NULL FK   | Who created it (nullable) |
  +----------------+------------------+---------------------------+

  Indexes:
  - PRIMARY KEY on id (for fast lookups by ID)
  - UNIQUE INDEX on short_code (for fast redirect lookups)
  - INDEX on user_id (for listing a user's links)
  - INDEX on expires_at (for periodic cleanup of expired links)

  Table: redirect_events (for analytics)
  +----------------+------------------+---------------------------+
  | Column         | Type             | Description               |
  +----------------+------------------+---------------------------+
  | id             | BIGSERIAL PK     | Event ID                  |
  | short_code     | VARCHAR(8)       | Which link was clicked    |
  | clicked_at     | TIMESTAMPTZ      | When the click happened   |
  | referrer       | TEXT NULL        | Where the click came from |
  | country_code   | CHAR(2) NULL     | GeoIP-derived country     |
  | device_type    | VARCHAR(20) NULL | mobile / desktop / tablet |
  +----------------+------------------+---------------------------+
```

The critical index is the `UNIQUE INDEX on short_code`. Every redirect request arrives with a short code, and the database must resolve that code to a long URL as fast as possible. A unique B-tree index on `short_code` turns this into an O(log n) lookup — essentially constant-time in practice for any realistic dataset size.

### 2.4 The Redirect Flow — Speed Is Everything

When a user clicks `https://short.ly/aB3xQk`, the system must resolve the short code to the long URL and issue an HTTP redirect as quickly as possible. Latency here matters enormously: users and search engines expect redirects to complete in under 100 milliseconds. Every additional millisecond of redirect latency is a friction point that erodes trust in the service.

```
URL Shortener — Complete Redirect Architecture
===============================================

  User's Browser
       |
       | HTTP GET /aB3xQk
       v
  +--------------------+
  |    Load Balancer   |
  | (distributes req.) |
  +--------+-----------+
           |
           v
  +--------------------+
  |    App Server      |
  | (Go / Node / etc.) |
  +--------+-----------+
           |
           | 1. Check Redis cache
           v
  +--------------------+
  |     Redis Cache    |
  | key: "url:aB3xQk" |
  | val: "https://..." |
  +--------+-----------+
       |         |
   HIT |         | MISS
       |         v
       |  +--------------------+
       |  |    PostgreSQL      |
       |  | SELECT long_url    |
       |  | FROM urls WHERE    |
       |  | short_code='aB3xQk'|
       |  +--------+-----------+
       |           |
       |           | Store in Redis
       |           | (TTL: 24 hours)
       |           |
       v           v
  +--------------------+
  |   HTTP 301/302     |
  |   Location:        |
  |   https://www...   |
  | (Redirect to user) |
  +--------------------+

  Response time target:
  Cache HIT:  ~1-2ms  (Redis lookup + HTTP response)
  Cache MISS: ~5-15ms (Redis miss + PostgreSQL + Redis store + HTTP)
```

One important design decision on the redirect is the HTTP status code. A **301 redirect** tells browsers and search engines that the redirect is permanent — the browser may cache it and never contact the short URL server again for future clicks. This is maximally efficient for server load but means redirect clicks cannot be counted (because the browser skips the server). A **302 redirect** is temporary — browsers always contact the server for each click, allowing accurate click counting. For analytics-focused URL shorteners, 302 is the standard choice despite the slightly higher server load.

### 2.5 Counting Redirects — The Counter Problem

Click counting presents its own interesting engineering challenge. The naive approach — executing `UPDATE urls SET click_count = click_count + 1 WHERE short_code = 'aB3xQk'` on every redirect — works at low traffic but becomes a serious bottleneck at high traffic. Imagine a viral link receiving one million clicks per hour. That is nearly 278 clicks per second, all trying to update the same row in the database simultaneously. Row-level locking in PostgreSQL prevents these updates from being truly concurrent, turning them into a queue, adding latency to every redirect in the process.

The elegant solution is to use **Redis atomic increment operations** to batch count. Redis provides an `INCR` command that atomically increments a counter in O(1) time, handling enormous concurrency without locks. Instead of writing to PostgreSQL on every click, the application increments a Redis counter: `INCR click:aB3xQk`. A background job then periodically — every minute, every five minutes — reads these Redis counters and flushes the accumulated count to PostgreSQL in a single bulk update. The PostgreSQL row is updated infrequently in batches rather than thousands of times per second.

```
Redirect Counter Architecture — Redis Batching
================================================

  Per-click (100,000s/sec):
  App --> INCR click:aB3xQk  (atomic, ~0.1ms, no locking)
  App --> INCR click:xZ9mPq
  App --> INCR click:aB3xQk  (Redis accumulates: aB3xQk=5,432)
  ...

  Background job (every 60 seconds):
  Job --> Redis GETDEL click:aB3xQk  --> 5,432
  Job --> Redis GETDEL click:xZ9mPq  --> 1,201
  Job --> PostgreSQL:
          UPDATE urls SET click_count = click_count + 5432
          WHERE short_code = 'aB3xQk';
          UPDATE urls SET click_count = click_count + 1201
          WHERE short_code = 'xZ9mPq';
  Job --> Done. (2 database writes served 6,633 user clicks)

  The database write pressure is reduced by 3,300x.
  Minor trade-off: counts are up to 60 seconds stale in PostgreSQL.
  Redis always has the real-time running total.
```

For detailed analytics beyond simple click counts — tracking per-click device type, country, referrer, and timestamp — the approach shifts to **event streaming**. Rather than trying to count in-place, each redirect event is published to a message queue like Kafka as a small event record. Downstream analytics pipelines consume these events asynchronously and store them in a columnar analytics database (like ClickHouse or BigQuery) optimized for aggregation queries. This completely decouples the high-frequency redirect path from the analytics storage layer.

## 3. Rate Limiter — Redis Sliding Window and Token Bucket

### 3.1 The Problem — Protecting Systems from Excessive Traffic

A rate limiter is a system that controls how frequently a user, a client application, or an IP address can perform an action within a given time period. Without rate limiting, a public API is defenseless against a remarkable variety of attacks and accidents. A malicious actor can write a script that hammers an endpoint millions of times per minute, exhausting the server's capacity and denying service to legitimate users — a denial-of-service attack. A poorly written client application might accidentally enter an infinite retry loop, making thousands of requests per second. A legitimate user might simply use the API more aggressively than the infrastructure can handle, degrading service for everyone else.

Rate limiting is also a commercial necessity: API businesses typically offer different usage tiers with different allowed request volumes, and the rate limiter is the enforcement mechanism that ensures customers do not accidentally or deliberately exceed their purchased limits.

The engineering challenge is that rate limiting must itself be extremely fast. It sits in the critical path of every API request — every request must be checked against the rate limiter before being processed. If the rate limiter adds 50 milliseconds of overhead to every request, it defeats its own purpose by degrading the user experience even when traffic is perfectly legitimate. Redis, with its microsecond-level operation latency, is the natural choice for implementing rate limiting state.

### 3.2 The Token Bucket Algorithm — A Leaky Reservoir of Permission

The **token bucket** is one of the oldest and most intuitive rate limiting algorithms, and understanding it requires nothing more than imagining a bucket that holds tokens. The bucket has a maximum capacity — say, 100 tokens. Tokens are added to the bucket at a fixed rate — say, 10 tokens per second. When a request arrives, it must consume one token from the bucket to be allowed through. If the bucket has tokens available, the request is served and one token is removed. If the bucket is empty, the request is rejected (or queued, in some implementations).

```
Token Bucket Algorithm — Visual Explanation
=============================================

  Bucket capacity: 100 tokens
  Refill rate:     10 tokens/second
  Cost per request: 1 token

  t=0:  [##########] 100 tokens  (full bucket, burst allowed)
  t=0:  3 rapid requests arrive -> 97 tokens remaining
  t=0:  7 more requests arrive  -> 90 tokens remaining
  t=1:  +10 tokens added        -> 100 tokens (capped at max)
  t=1:  50 requests arrive      -> 50 tokens remaining
  t=2:  +10 tokens added        -> 60 tokens remaining
  ...
  t=5:  60 rapid requests arrive -> 10 tokens remaining
  t=5:  15 more requests arrive
        -> 10 allowed, 5 REJECTED (bucket empty)

  Key properties:
  - Allows short bursts up to the bucket capacity
  - Enforces a long-term average rate (refill rate)
  - Excess requests are immediately rejected (no queuing)

  Redis Implementation:
  +--------------------------------------------------+
  | Key:   rate_limit:{user_id}                      |
  | Fields:                                          |
  |   tokens:      current token count (float)       |
  |   last_refill: timestamp of last refill (ms)     |
  |                                                  |
  | On each request (Lua script for atomicity):      |
  |   1. Compute elapsed = now - last_refill         |
  |   2. tokens += elapsed * refill_rate             |
  |   3. tokens = min(tokens, capacity)              |
  |   4. If tokens >= 1: tokens -= 1, ALLOW          |
  |      Else: DENY                                  |
  |   5. SET rate_limit:{user_id} {tokens} {now}     |
  +--------------------------------------------------+
```

The token bucket's most important characteristic is its treatment of **bursts**. A user who has been idle for ten seconds will have a full bucket of 100 tokens and can make 100 requests in rapid succession. This is intentional and desirable behavior — a developer who runs a batch of API calls should not be penalized for the fact that they ran them all at once rather than one per second. The token bucket allows bursts up to the bucket capacity while enforcing the long-term average rate. This makes it feel "fair" to users: you are borrowing against your accumulated allowance, not being throttled to a rigid per-second maximum.

Implementing the token bucket in Redis requires careful attention to atomicity. The read-compute-write sequence (read current tokens, compute new token count based on elapsed time, write updated count) must happen atomically — otherwise, two concurrent requests could both read the same token count, both conclude there are enough tokens, both consume a token, and both be allowed through when only one should have been. Redis provides **Lua scripting** to execute sequences of commands atomically on the server side, eliminating this race condition entirely.

### 3.3 The Sliding Window Algorithm — Counting Without Bias

The fixed window counter is perhaps the simplest rate limiting approach: count the number of requests in the current one-minute window, and reject requests if the count exceeds the limit. But this approach has a well-known weakness: a user could make requests at the very end of one window and the very start of the next, effectively making twice the allowed number of requests in a short span.

```
Fixed Window Problem — The Boundary Exploit
=============================================

  Window 1: 00:00 - 01:00    Window 2: 01:00 - 02:00
  Limit: 100 requests/minute

  t=00:50  User makes 100 requests (uses full window 1 quota)
  t=01:10  User makes 100 requests (uses full window 2 quota)

  In a 20-second span (00:50 to 01:10), the user made 200
  requests -- double the intended rate! The fixed window
  boundary creates an exploitable seam.

Sliding Window Solves This:
  +---------+----------+
  | Past 60s | Current |  <-- The window slides continuously
  | requests | request |      No fixed boundary to exploit
  +---------+----------+
  At any point in time, the count of requests in the
  LAST 60 SECONDS must be below the limit.
```

The **sliding window** algorithm solves the boundary problem by maintaining a continuous, rolling window of time rather than discrete fixed buckets. The most Redis-friendly implementation uses a **sorted set** (Redis's `ZSET` data structure) where each request is stored as a member with its timestamp as the score. To check if a new request is allowed, the algorithm removes all members with scores (timestamps) older than the window duration, counts the remaining members, and allows the request only if the count is below the limit.

```
Sliding Window Rate Limiter — Redis ZSET Implementation
=========================================================

  Key: sliding_window:{user_id}
  Data structure: ZSET (sorted set, scored by timestamp)

  Scenario: Limit = 5 requests per 10 seconds

  t=1000ms: Request arrives
    ZREMRANGEBYSCORE key 0 (1000-10000)  -- remove entries > 10s old
    ZADD key 1000 "req-uuid-1"           -- add current request
    ZCARD key                            -- count = 1, ALLOW

  t=2000ms: Request arrives
    ZREMRANGEBYSCORE key 0 990           -- remove old entries
    ZADD key 2000 "req-uuid-2"
    ZCARD key = 2, ALLOW

  t=9000ms: Requests 3,4,5 arrive
    ZCARD key = 5, ALLOW all three

  t=9500ms: Request 6 arrives
    ZREMRANGEBYSCORE key 0 (9500-10000)  -- nothing to remove yet
    ZCARD key = 5 (at limit), REJECT

  t=11500ms: Request 7 arrives
    ZREMRANGEBYSCORE key 0 1500          -- removes req-1 (t=1000)
    ZADD key 11500 "req-uuid-7"
    ZCARD key = 5 (5 requests from t=2000 to t=9000 + new one)
    ALLOW! (the oldest request has aged out of the window)

  Visual timeline:
  |--10 second window--|
  [1000][2000][7000][8000][9000]  <- 5 requests in window -> DENY at t=9500
       [2000][7000][8000][9000][11500]  <- after t=11500, 1000 aged out -> ALLOW
```

Each entry in the sorted set occupies a small amount of memory. For a rate limit of 1,000 requests per minute, the sorted set for an active user will contain at most 1,000 entries. The entire sorted set for one user might consume a few kilobytes of Redis memory — a negligible amount. Entries older than the window are automatically cleaned up by the `ZREMRANGEBYSCORE` command on every request check, so the memory footprint stays bounded.

The sliding window implementation in Redis should also use a Lua script to ensure that the `ZREMRANGEBYSCORE`, `ZADD`, and `ZCARD` commands execute atomically. Additionally, the key should be given a TTL slightly larger than the window duration (for example, 70 seconds for a 60-second window), so that Redis automatically expires the key entirely for users who have been inactive — preventing the accumulation of stale rate limit keys for millions of inactive users.

### 3.4 Choosing Between Token Bucket and Sliding Window

Both algorithms are correct and battle-tested; the choice between them comes down to the characteristics of the workload and the user experience you want to deliver. The token bucket is more forgiving of bursty traffic — it rewards users who have been under their limit by allowing them to spend accumulated tokens quickly. This is the better choice when clients are real human beings using a mobile app or a dashboard who naturally produce irregular, bursty patterns of activity.

The sliding window is more strictly uniform. It prevents any boundary exploits and provides a very precise guarantee: at no point in time shall the request count in the last N seconds exceed the limit. This is better suited for machine-to-machine API clients, automated pipelines, or scenarios where the fairness of the rate limit across all users is more important than accommodating natural burstiness.

Many production systems implement a **hybrid approach**: a token bucket at the individual user level (to handle burst behavior gracefully) combined with a sliding window at the global API level (to protect the infrastructure from aggregate overload regardless of whether individual limits are being respected).

## 4. Notification System — Fan-Out on Write vs Fan-Out on Read

### 4.1 The Problem — Delivering Content to Many People

The notification and feed delivery problem is arguably the most architecturally complex of the three patterns examined in this document, and it is the one that exposes the most profound tension between two competing engineering values: **freshness** and **scalability**. The problem can be stated simply: when a user creates a post, a photo, a tweet, or any other piece of content, how do we ensure that all of that user's followers see it in their feeds in a timely manner?

The naive answer is also the one that immediately fails at scale. You might imagine that when a user opens their feed, the application simply queries the database: "find all content created by users that this user follows, sorted by time, and return the most recent fifty items." This is a completely sensible relational database query, and it works beautifully when your platform has a few hundred users. But consider a user who follows 2,000 other accounts. The database must find all recent posts from 2,000 different users, merge them, sort them, and return a paginated result. At every single feed load, for every single user. Now multiply this by fifty million concurrent users each loading their feed several times per day, and the database is executing a catastrophically expensive join and sort operation hundreds of millions of times per day. No database in the world can sustain this efficiently.

The fundamental tension is this: you must either do expensive work **at write time** (when a post is created) or at **read time** (when a feed is requested). There is no free lunch. Moving the work to write time is called **fan-out on write**. Keeping the work at read time is called **fan-out on read** (also called pull-on-read). Each has profound consequences for the system's architecture, scalability characteristics, and behavior under certain edge cases.

### 4.2 Fan-Out on Write — Pre-computing Every Feed

In the **fan-out on write** approach, the moment a user publishes a post, the system immediately delivers that post to the pre-computed feed of every single one of that user's followers. Rather than computing "what posts should be in Alice's feed?" when Alice opens the app, the system has already answered that question by the time any of Alice's followed accounts posted anything. Alice's feed is a pre-built list, sitting ready in fast storage (typically Redis sorted sets), waiting to be read.

```
Fan-Out on Write — Architecture
==================================

  Step 1: User publishes a post
  +-------------+
  |   Alice     |  "Just posted a photo!"
  | (Publisher) |
  +------+------+
         |
         | Write post to database
         v
  +-------------------+
  |     PostgreSQL    |
  | INSERT INTO posts |
  | (post_id=9999,    |
  |  user_id=alice,   |
  |  content=...)     |
  +--------+----------+
           |
           | Enqueue fan-out task
           v
  +-------------------+
  |   Message Queue   |
  |   (Kafka Topic:   |
  |   "new-posts")    |
  +--------+----------+
           |
           | Fan-out workers consume the message
           v
  +-------------------+
  |   Fan-Out Workers |
  | (Reads Alice's    |
  |  10,000 followers)|
  +--------+----------+
           |
           | For each follower, push post_id into their feed
           |
  +--------v----------+
  |   Redis Feed      |
  |   (Sorted Sets)   |
  |                   |
  | feed:bob    [9999, 9998, 9995, ...]  <- Bob's feed (ZADD)
  | feed:carol  [9999, 9990, 9985, ...]  <- Carol's feed
  | feed:dave   [9999, 9992, 9988, ...]  <- Dave's feed
  | ... x 10,000 followers ...           |
  +-------------------+

  Step 2: Follower reads their feed
  +----------+
  |   Bob    |  Opens his feed
  +----+-----+
       |
       | ZREVRANGE feed:bob 0 49  (top 50 posts)
       v
  +----------+
  |  Redis   |  Returns [9999, 9998, 9995, ...]
  +----+-----+
       |
       | Fetch post details by IDs (batch GET from cache or DB)
       v
  Bob sees his complete, sorted feed instantly.
  No joins. No expensive computation. Pure key lookups.
```

The read experience with fan-out on write is extraordinary — loading a feed is a single Redis sorted set lookup, returning a list of post IDs in perfect chronological or engagement-ranked order, followed by a batch fetch of the post content for those IDs. The entire operation completes in a few milliseconds regardless of how many people the user follows, because all the sorting and merging work was done at write time.

The write cost, however, is substantial and deserves careful examination. When Alice — who has 10,000 followers — publishes a post, the fan-out system must write Alice's post ID into 10,000 separate Redis sorted sets. If done synchronously (before acknowledging the post to Alice), this would make posting feel extremely slow. If done asynchronously via a message queue (the standard approach), the post is immediately confirmed to Alice, and the fan-out happens in the background. Alice's post might take a few seconds to appear in all followers' feeds, but Alice sees an immediate success response.

### 4.3 The Celebrity Problem — When Fan-Out on Write Breaks Down

Fan-out on write works superbly for most users, but it contains a catastrophic failure mode known as the **celebrity problem** or **hot user problem**. Consider a public figure — a musician, a politician, an athlete — who has fifty million followers. When they publish a single post, the fan-out system must write that post ID into fifty million Redis sorted sets. At a generous throughput of one million writes per second, this takes fifty seconds to complete. During those fifty seconds, millions of followers who open the app will not see the post in their feed — a staleness problem of nearly a minute for a highly anticipated piece of content. Worse, this fifty-million-write tsunami of Redis operations competes with all other fan-out operations happening simultaneously, potentially degrading the feed experience for every user on the platform.

```
The Celebrity Problem
========================

  Normal user (1,000 followers):
  Post published -> 1,000 feed writes -> completes in ~1ms
  [OK] Acceptable. Followers see it almost immediately.

  Celebrity (50 million followers):
  Post published -> 50,000,000 feed writes
  -> At 1M writes/sec = 50 SECONDS to complete fan-out
  -> For 50 seconds, followers have an empty/stale feed

  +--------------------------------------------------+
  |  The Hybrid Solution                             |
  |                                                  |
  |  IF user.follower_count < threshold (e.g. 10k): |
  |    --> Fan-out on WRITE (push to all feeds)      |
  |                                                  |
  |  IF user.follower_count >= threshold:            |
  |    --> Fan-out on READ  (pull on demand)         |
  |                                                  |
  |  Regular users get fast pre-built feeds.         |
  |  Celebrity posts are fetched dynamically and     |
  |  merged at read time -- but this only happens    |
  |  for a tiny fraction of accounts.               |
  +--------------------------------------------------+
```

### 4.4 Fan-Out on Read — Computing Feeds on Demand

In the **fan-out on read** approach (sometimes called pull model), no pre-computation is done at write time. When a user opens their feed, the system dynamically computes what that feed should contain at that exact moment. The computation involves looking up all the users that the requesting user follows, fetching recent posts from each of those followed users, merging all those posts together, sorting them, and returning the result.

```
Fan-Out on Read — Architecture
================================

  Step 1: User publishes a post (simple write)
  +-------------+
  |   Alice     |  "Just posted a photo!"
  | (Publisher) |
  +------+------+
         |
         | Write post to database ONLY
         v
  +-------------------+
  |     PostgreSQL    |
  | INSERT INTO posts |
  | Done. Nothing     |
  | else happens.     |
  +-------------------+
  (Write cost: 1 database insert. Always O(1).)

  Step 2: Follower reads their feed (expensive computation)
  +----------+
  |   Bob    |  Opens his feed (follows 2,000 users)
  +----+-----+
       |
       v
  +---------------------+
  |     App Server      |
  | 1. Fetch Bob's      |
  |    following list   |
  |    (2,000 user IDs) |
  |                     |
  | 2. For each user,   |
  |    fetch their      |
  |    recent posts     |
  |    (or use index)   |
  |                     |
  | 3. Merge all posts  |
  |    into sorted list |
  |                     |
  | 4. Return top 50    |
  +---------------------+
       |
       v
  +-------------------+
  |    PostgreSQL     |
  | SELECT * FROM     |
  | posts WHERE       |
  | user_id IN (2000  |
  | ids) ORDER BY     |
  | created_at DESC   |
  | LIMIT 50          |
  +-------------------+
  (Read cost: large IN query + sort. Scales with following count.)
```

The write experience with fan-out on read is trivially simple — publishing a post is a single database insert, always O(1) regardless of how many followers the publisher has. A celebrity with fifty million followers costs exactly the same to write as a new user with zero followers. There is no fan-out infrastructure, no message queue, no background workers. The architecture is dramatically simpler.

The read experience, however, degrades as the user's following count grows. A user who follows 5,000 accounts has an expensive feed query — the database must consider recent posts from 5,000 different sources, sort them, and paginate. Caching helps significantly here: if the computed feed is cached in Redis with a short TTL (say, 30 seconds), the expensive computation happens at most once every 30 seconds per user, regardless of how many times that user refreshes their feed. But even so, the cold query (cache miss) is slow, and for a platform with millions of active users all refreshing their feeds every few minutes, cache misses happen constantly and at enormous scale.

### 4.5 The Hybrid Model — The Industry Standard

In practice, the world's most sophisticated social platforms use a **hybrid model** that applies fan-out on write to ordinary users and fan-out on read to celebrity accounts, blending the benefits of both approaches while mitigating the weaknesses of each.

The implementation is elegant: each user account carries a flag or is classified by follower count into a category (regular vs. celebrity, where the threshold might be ten thousand followers or one hundred thousand — chosen by experimentation). When Bob opens his feed, the system does two things in parallel. First, it reads Bob's pre-built Redis feed (populated via fan-out on write from all the regular users Bob follows). Second, for each celebrity account Bob follows, it fetches that celebrity's recent posts directly from the database or a dedicated celebrity post cache. Finally, it merges these two streams — the pre-built feed and the freshly-fetched celebrity posts — sorts them together by timestamp or engagement score, and returns the result.

```
Hybrid Fan-Out — The Industry Standard
=========================================

  When Bob loads his feed:
  +----------------------------------------------------------+
  |                     App Server                           |
  |                                                          |
  |  Stream A:                      Stream B:               |
  |  Bob's pre-built Redis feed     Celebrity posts          |
  |  (fan-out on write results)     (fan-out on read)        |
  |                                                          |
  |  feed:bob in Redis              SELECT * FROM posts      |
  |  [post:9999, post:9995, ...]    WHERE user_id IN         |
  |  (from regular followed users)  (celebrity IDs Bob       |
  |                                  follows)                |
  |  ~1ms to fetch                  ~5ms to fetch           |
  |                                                          |
  |  [Merge + Sort Streams A and B by timestamp]             |
  |                                                          |
  |  Return unified, complete feed to Bob                    |
  +----------------------------------------------------------+

  Result:
  - Regular users: fast fan-out on write (Redis pre-built feed)
  - Celebrities: no write-time fan-out (no fifty-million-write storms)
  - Bob's feed: seamlessly merged, always fresh, always fast
```

This hybrid model also gracefully handles edge cases. When a new user follows a celebrity account, their feed immediately includes that celebrity's posts (because they are fetched at read time). When a user unfollows someone, their pre-built Redis feed may still contain that person's posts until the cached feed entries expire — a minor staleness issue that is acceptable in the context of feed freshness expectations. The TTL on Redis feed entries serves as the natural cleanup mechanism.

### 4.6 Storing and Serving Notification Payloads

Beyond the feed itself, notification systems must also deliver **push notifications** — the alerts that appear on a mobile device or desktop browser when someone likes your post, mentions you in a comment, or starts following you. The architecture for push notifications is distinct from the feed architecture but equally important.

When an action occurs — a like, a comment, a follow — the system generates a notification event and routes it through a notification service. This service first writes the notification to a persistent store (a PostgreSQL `notifications` table, so the user can see their notification history) and simultaneously dispatches a push notification payload to the appropriate mobile notification gateway (Apple Push Notification Service for iOS, Firebase Cloud Messaging for Android). The notification service must be designed for extreme throughput — on a platform with tens of millions of users, hundreds of thousands of notification events may be generated per second at peak time — which is why the dispatch path is typically decoupled from the trigger via a message queue, allowing the notification service to consume events at its own pace without blocking the action that generated them.

```
Notification Delivery Pipeline
================================

  Action: Alice likes Bob's post
       |
       v
  +-----------------+
  |   Action API    |
  | (records like)  |
  +-------+---------+
          |
          | Publish to Kafka: "like-events"
          v
  +-----------------+
  |   Kafka Topic   |
  | "like-events"   |
  +-------+---------+
          |
          | Notification service consumes
          v
  +-----------------+     +------------------+
  | Notification    |---->| PostgreSQL       |
  | Service         |     | notifications    |
  |                 |     | table (persist)  |
  |                 |     +------------------+
  |                 |
  |                 |---->+------------------+
  |                 |     | APNs (iOS Push)  |
  |                 |     +------------------+
  |                 |
  |                 |---->+------------------+
  |                       | FCM (Android     |
  |                       | Push)            |
  |                       +------------------+

  Bob receives: a push notification on his phone AND
               a red badge in the app's notification inbox,
               backed by the PostgreSQL record.
```

The notification system, the feed architecture, and the underlying database choices all form a coherent ecosystem where each component is optimized for its specific job. The feed storage in Redis is optimized for fast sorted set operations. The post content in PostgreSQL is optimized for ACID storage and flexible querying. The event pipeline through Kafka is optimized for high-throughput, durable message delivery. And the push notification gateways are optimized for reaching mobile devices at global scale. No single technology handles all of these requirements; the power of the architecture lies in how the components are composed.

## Summary

The three patterns explored in this document each illuminate a different dimension of the fundamental challenge of system design: how to build systems that are simultaneously fast, correct, and scalable.

The URL shortener teaches the discipline of designing for the dominant workload characteristic — in this case, a heavily read-biased system where Redis caching and ID-based encoding dramatically reduce database load, while the counter problem demonstrates why direct database updates do not scale and why Redis atomic counters with periodic batch flushing is the correct solution.

The rate limiter teaches the art of state management under extreme concurrency — where the choice of data structure (Redis sorted sets for sliding windows, floating-point counters for token buckets) and the guarantee of atomic execution via Lua scripting are the critical details that separate a correct implementation from a subtly broken one.

The notification and feed system teaches the most profound lesson: that there is no universally correct architecture, only trade-offs, and that the right answer often lies not in choosing one approach over another but in compositing them — fan-out on write for the ordinary case, fan-out on read for the celebrity case — such that the system's behavior is optimal across the entire spectrum of its users. This insight — that real-world systems live in the space between clean theoretical patterns — is perhaps the most important thing a budding system designer can internalize.
