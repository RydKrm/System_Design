## 1. What is Consistency, and Why Does It Matter?

Before diving into the different flavours of consistency, it is important that you build a mental model of what consistency even means in the world of databases and distributed systems.

Imagine you have a notebook. You write something in it, and then you immediately read it back — you see exactly what you wrote. Simple. Now imagine ten people sharing that same notebook, but the notebook is actually ten copies spread across ten different cities. One person in Dhaka writes something. One second later, a person in Tokyo reads from their copy. Do they see the update? Maybe. Maybe not. That "maybe" is the entire problem that consistency models exist to solve.

In a single-machine database like a local SQLite file, consistency is trivial. There is one copy of the data, and every read and write talks to that one copy. But the moment you introduce replication — meaning multiple copies of your data on multiple machines — you enter the distributed systems world, and now you must define: **what guarantee does the system give you about what a reader sees after a writer writes?**

A **consistency model** is a formal contract between the database system and the developer. It tells you: "Here is what you can assume about the order and visibility of reads and writes." Different models offer different strengths of that contract. A stronger model is easier to reason about but harder to build and slower to operate. A weaker model is faster and more available but places more burden on the developer to reason about data correctness.

Think of it like this: a bank promises that when you transfer money, the balance is immediately correct everywhere. A social media app promises that your post will eventually show up for everyone, but maybe not instantly. These are different consistency contracts for different use cases.

Now let us walk through each model, from the strongest to the weakest, so you can understand both the guarantee and the trade-off.

---

## 2. Strong Consistency

Strong consistency, also called **linearizability**, is the gold standard of consistency models. It is the model that most closely resembles the behaviour of a single machine with a single copy of data. Under strong consistency, the system behaves as if there is only one copy of the data, even if internally it has ten copies spread across ten data centres.

The formal definition says: every operation — read or write — must appear to take effect **instantaneously at some single point in time**, and this point must be between when the operation started and when it finished. Furthermore, all operations must appear in a single global timeline that every single node in the system agrees upon.

Let us break that down with a story. Suppose you have two people — Alice and Bob — and they are both connected to a distributed database that has three nodes: Node A, Node B, and Node C.

```
Alice writes: x = 10   at time T1
Bob reads:    x         at time T2 (where T2 > T1)
```

Under strong consistency, Bob is guaranteed to read `x = 10` or any later value, never a stale value that predates Alice's write. The system ensures that Alice's write is fully propagated and acknowledged before it is considered complete, and that no read can go back in time to see an older value.

Here is a visual of how linearizability works:

```
Timeline ──────────────────────────────────────────────────────────────►

Alice:  [Write x=10]───────────────────────[Done]
                              │
                              │ Write acknowledged to ALL nodes first
                              │
Bob:                          [Read x]──►  Sees x=10  ✓
Carol:                             [Read x]──► Sees x=10  ✓

Even if Bob and Carol read from different nodes, they both see x=10
because the system coordinated a global agreement before acknowledging
Alice's write.
```

The price of this guarantee is **coordination overhead**. When Alice writes, the system must contact a quorum of nodes (or sometimes all nodes), get acknowledgement, and only then tell Alice her write succeeded. This round-trip communication across the network takes time. In a geographically distributed system — where nodes might be in different countries — this latency can be significant. If any node goes down and quorum cannot be achieved, the system may refuse to accept writes at all, sacrificing availability for correctness.

This is why strongly consistent systems are excellent for financial transactions, inventory management, or any domain where seeing stale data causes real harm. PostgreSQL with synchronous replication, Google Spanner, and etcd all operate under strong consistency. Your primary PostgreSQL instance in a single-node setup is also strongly consistent, because there is only one copy of truth.

**Key Insight:** Strong consistency is the most expensive guarantee because it requires network coordination before every operation completes. You pay in latency and availability, but you get the simplest mental model.

---

## 3. Sequential Consistency

Sequential consistency is one step weaker than strong consistency, and understanding the difference is crucial. The model was originally defined by Leslie Lamport in 1979, and it remains one of the most referenced models in distributed systems literature.

Under sequential consistency, the system guarantees two things. First, all operations appear to execute in some total order — meaning there is a global timeline that the system agrees upon. Second, the operations of any single process (or thread, or client) appear in that global timeline in the same order they were issued by that process. What sequential consistency does **not** guarantee, however, is that this global order corresponds to real-world time.

Let us make this concrete with a story. Imagine Alice writes `x = 1`, then writes `x = 2`. Bob reads x twice. Under sequential consistency:

- Bob must see Alice's writes in the order she issued them: he will never see `x = 2` and then see `x = 1` in a subsequent read.
- But Bob might see `x = 0` (the initial value) even after Alice has already written both values, if there is a delay in propagation.
- However, all clients will agree on the same order of operations.

The critical difference from strong consistency is this: **sequential consistency allows the appearance of operations to be reordered in time**, as long as the final global order is consistent with every individual client's program order.

```
Real Wall-Clock Time ──────────────────────────────────────────────────►
                T1          T2          T3          T4

Alice:    [Write x=1]                [Write x=2]
Bob:                    [Read x]                 [Read x]

Under STRONG consistency:
  Bob's read at T2 sees x=1  (real-time enforced)

Under SEQUENTIAL consistency:
  Bob's read at T2 might still see x=0  (propagation delay allowed)
  Bob's read at T4 might see x=1 or x=2
  BUT: Bob will NEVER see x=2 before x=1 across any two reads,
  because Alice's write order is preserved in the global order.
```

The subtle but important thing here is that sequential consistency says: "The global order of all operations is consistent with the order each client issued its operations." It does not say this global order matches the real clock on the wall. This relaxation allows the system to be slightly more available than a strongly consistent system, because it does not need to perfectly synchronise with real time.

In practice, this model is extremely useful for systems where multiple clients must agree on a consistent history of events, but where the system cannot afford the cost of strict real-time ordering. Systems like Apache ZooKeeper implement sequential consistency for their coordination operations. Many distributed lock services and leader election algorithms rely on sequential consistency to function correctly.

**Key Insight:** Sequential consistency preserves the program order of each individual client and ensures a globally agreed-upon order, but it does not guarantee that this order matches real-world time. It is slightly more relaxed than strong consistency and therefore more achievable in practice.

## 4. Causal Consistency

Causal consistency is a beautifully intuitive model that is rooted in a very human concept: **cause and effect**. The central idea is that if one operation causally depends on another — meaning one operation was influenced by the result of another — then every node in the system must observe these operations in their causal order. Operations that are causally independent, however, can be observed in any order.

To understand causality in the context of databases, consider this: if Alice reads a value `x = 5`, and then based on that reading, she writes `y = x + 1 = 6`, then her write of `y = 6` is causally dependent on her read of `x = 5`. Any system implementing causal consistency must ensure that if Bob sees Alice's write of `y = 6`, he must also be able to see (or must have seen) the state of `x = 5` that caused it. The system tracks these dependencies and ensures they are delivered in order.

```
Causal Chain Example:

Alice reads: x = 5
               │ (causes)
               ▼
Alice writes: y = x + 1 = 6
               │ (causes)
               ▼
Bob reads: y  →  sees y = 6
               │ (must also be able to see)
               ▼
Bob reads: x  →  must see x = 5 (or newer), NOT an older value

─────────────────────────────────────────────────────────────────────

Operations with NO causal relationship:

Carol writes: z = 99  (independent of Alice's writes)
Dave writes:  w = 42  (independent of Alice's writes)

Under causal consistency, Bob might see z=99 before or after w=42.
Their order is not guaranteed because they are causally unrelated.
```

The system tracks causality using a mechanism called **vector clocks** or **version vectors**. Each write carries metadata about which previous writes it depends upon, and nodes use this metadata to ensure they do not deliver a write to a client until all its causal predecessors have also been delivered.

The power of causal consistency becomes apparent in collaborative applications. Consider a Google Docs-style editor where Alice writes a comment, and Bob replies to that comment. Causal consistency ensures that every client who sees Bob's reply will also see Alice's original comment, because Bob's reply is causally dependent on Alice's comment. Without causal consistency, someone might see Bob's reply floating in the air without the comment it responds to — which would be confusing and incorrect.

MongoDB (with certain configurations), Cosmos DB (with session consistency), and academic systems like COPS and Bolt-on Causal Consistency implement this model. It strikes a compelling balance: it is stronger than eventual consistency (because it enforces causal ordering) but weaker than sequential consistency (because causally unrelated operations can be reordered), which makes it more achievable in geo-distributed systems.

**Key Insight:** Causal consistency tracks the "happens-before" relationship between operations. If A caused B, then everyone sees A before B. Unrelated operations can arrive in any order. This model is powerful for collaborative tools and social applications where the narrative structure of data matters.

## 5. Eventual Consistency

Eventual consistency is the most relaxed, the most widely deployed, and arguably the most misunderstood consistency model. It is the model that powers much of the modern internet — your social media feed, DNS lookups, Amazon shopping carts, and many NoSQL databases all operate under eventual consistency.

The formal definition is deceptively simple: if no new updates are made to a given piece of data, then eventually all replicas of that data will converge to the same value. The key word here is "eventually" — the model makes no promise about how quickly convergence will happen. It could be milliseconds. It could be seconds. In theory, it could be longer. The model also makes no promise about what an individual read will return during the convergence period.

```
Eventual Consistency — Convergence over Time:

         Node A          Node B          Node C
Time 0:  x = 0           x = 0           x = 0
         │
Time 1:  Write x=10      (not yet synced) (not yet synced)
         x = 10           x = 0           x = 0
         │
Time 2:  x = 10          Syncing...       x = 0
                          x = 10
         │
Time 3:  x = 10           x = 10          Syncing...
                                           x = 10
         │
Time 4:  x = 10           x = 10          x = 10  ← Converged ✓

A read at Time 2 from Node C would return x=0, even though the
"true" value is x=10. This is the eventual consistency trade-off.
```

What makes eventual consistency powerful is what it gives up in exchange for this relaxation. Because nodes do not need to coordinate before accepting a write, and because reads do not need to consult all nodes before returning a value, the system can be extremely fast and extremely available. A write succeeds even if some nodes are temporarily unreachable. A read returns immediately without waiting for global agreement. This is why Amazon DynamoDB, Apache Cassandra, CouchDB, and many Redis use cases default to eventual consistency — it lets them serve millions of requests per second across geographically distributed data centres.

However, eventual consistency is not the wild west that it is sometimes portrayed as. Modern eventually consistent systems come with specific **conflict resolution** mechanisms. When two clients write different values to the same key on different nodes simultaneously, the system must decide which value "wins" when the nodes eventually sync. Common strategies include Last-Write-Wins (LWW, where the write with the newer timestamp prevails), vector clocks (which track concurrent writes explicitly), and application-level merge functions (like CRDTs — Conflict-free Replicated Data Types — which mathematically guarantee convergence regardless of write order).

In your Go backend with Redis, for instance, when you use Redis in a cluster mode and a node fails over, there is a window where some reads might return stale data. Redis prioritises availability over consistency. Understanding this is critical for designing systems correctly.

**Key Insight:** Eventual consistency says: "All nodes will agree eventually, but right now, different nodes might disagree." It trades correctness-in-the-moment for extreme availability and performance. It is ideal for data where staleness is acceptable and convergence is more important than instantaneous accuracy.

## 6. Session Guarantees — The Practical Layer

Now we arrive at something critically practical: **session guarantees**. These are not full system-wide consistency models — rather, they are client-centric guarantees that sit on top of a weaker model (like eventual consistency) and provide stronger guarantees within the context of a single client's session.

Think of it this way: global strong consistency is expensive and hard. But do you always need the entire world to agree on data simultaneously? Often, what you actually need is much more modest. You need _your_ client to have a coherent view of the world — to not see the data going backward or contradicting itself from your perspective. Session guarantees deliver this.

These concepts were formalized by Terry et al. in the 1994 paper "Session Guarantees for Weakly Consistent Replicated Data," and they remain the backbone of how modern databases tune consistency for clients.

---

### 6.1 Read-Your-Writes

Read-Your-Writes (also called **Read-Your-Own-Writes**) is the most fundamental session guarantee, and it is the one whose absence is most immediately noticeable to users. The guarantee states: within a single session, if a client writes a value, any subsequent read by that same client will reflect that write.

This sounds so obvious that you might wonder why it needs to be stated at all. The reason is that in an eventually consistent distributed system, your write might land on Node A, but your subsequent read might be routed to Node B, which has not yet received the replication of your write. Without this guarantee, you could submit a form, be redirected to a page that shows your data, and see the old version because the read hit a different replica.

```
WITHOUT Read-Your-Writes:

Client ──► [Write "bio = Developer"] ──► Node A (write accepted)
Client ──► [Read "bio"]              ──► Node B (not yet replicated)
                                         Returns "bio = " (empty!) ✗
                                         
WITH Read-Your-Writes:

Client ──► [Write "bio = Developer"] ──► Node A  (write accepted)
                                              │
                                         System ensures next read
                                         goes to Node A, OR waits
                                         for Node B to sync first
                                              │
Client ──► [Read "bio"]              ──► Returns "bio = Developer" ✓
```

Systems implement this guarantee in several ways. One common approach is session stickiness — the client is always routed to the same replica for both reads and writes within a session. Another approach uses **tokens or version numbers**: when a write succeeds, the system returns a token representing the write's version, and subsequent reads on any node block until that version has been replicated to them.

MongoDB's sessions implement read-your-writes by default for operations within a session. In PostgreSQL with a single primary, this is trivially true. In Redis Cluster, you need to be more careful because replicated reads from replicas might not yet have the latest writes from the primary.

As a backend developer, this is perhaps the most critical session guarantee to reason about when building user-facing features. Profile updates, settings changes, post creation — any scenario where a user acts and then immediately sees the result — requires read-your-writes to avoid a jarring inconsistency.

---

### 6.2 Monotonic Reads

Monotonic reads is a guarantee that states: within a single session, if a client reads a value, any subsequent read will return that same value or a more recent one. In other words, **time never goes backward** from the client's perspective.

Without monotonic reads, you could have a deeply confusing scenario. Imagine you load a webpage and see that a counter shows 150 orders. You refresh the page, and it shows 140 orders. Then you refresh again, and it shows 155. This "flickering" effect — where the data appears to jump backward — is the symptom of a system that lacks monotonic reads. It happens because different reads get routed to different replicas that are at different points in their replication progress.

```
WITHOUT Monotonic Reads:

Request 1 → Node A (synced to version 5): Returns x = 50
Request 2 → Node C (synced to version 3): Returns x = 30  ← Going BACK! ✗
Request 3 → Node B (synced to version 7): Returns x = 70

The client sees: 50, 30, 70 — data appears to bounce up and down.

──────────────────────────────────────────────────────────────────────

WITH Monotonic Reads:

Request 1 → Any Node: Returns x = 50  (client records: "I've seen version 5")
Request 2 → Any Node: Must return version ≥ 5.
                       If routed to a stale node, either wait for sync
                       or reroute to a more up-to-date node.
                       Returns x = 50 or x = 70  ✓

The client sees: 50, 50, 70  OR  50, 70, 70 — always moving forward. ✓
```

The implementation typically involves the client carrying a **read timestamp** or a **version vector** in its session state. When it issues a read, this token travels with the request, and the server only services the read from a replica that has advanced to at least that version. If no such replica is locally available, the read may need to wait or be forwarded to a replica that is sufficiently up-to-date.

Cassandra implements monotonic reads at the session level using its "LOCAL_SERIAL" and similar consistency levels. DynamoDB offers this through strongly consistent reads (at extra cost). Understanding monotonic reads becomes critical when you are building dashboards, feed views, or any UI where the user is continuously polling or refreshing — you do not want them to feel like the data is unreliable.

---

### 6.3 Monotonic Writes

Monotonic writes is the guarantee that a client's writes are executed on the system in the same order the client issued them. If a client writes A, then writes B, the system will apply A before B. No replica will ever see B applied before A from the same client.

At first glance this seems too obvious to need stating. In a single-node database, of course writes happen in order — they are processed sequentially by one machine. But in a distributed, multi-primary (or eventually consistent) system, writes from a single client can arrive at different nodes and be replicated in different orders. Without monotonic writes, write B might propagate faster than write A and "beat" it to some nodes, leading to an inconsistent final state.

```
WITHOUT Monotonic Writes (problematic scenario):

Client sends in order:  Write A → "Set account status = ACTIVE"
Client sends in order:  Write B → "Set account status = SUSPENDED"

Network chaos: Write B arrives at Node 2 first.
               Write A arrives at Node 2 second.

Node 2 ends up with: status = ACTIVE  (Wrong! Should be SUSPENDED) ✗

──────────────────────────────────────────────────────────────────────

WITH Monotonic Writes:

The system ensures:
  Write A must be applied on all nodes BEFORE Write B is applied.
  The client's causal chain is respected.

Final state on all nodes: status = SUSPENDED  ✓
```

A more real-world example: in a text editor, you type "Hello" and then immediately type " World". These are two separate writes. Monotonic writes ensures that the database sees "Hello" applied before " World," resulting in "Hello World." Without this guarantee, in a distributed system under network chaos, some replica might see " World" applied first, leading to corrupted state.

Monotonic writes are closely related to the concept of write ordering in replication logs. Databases that use a write-ahead log (WAL) — like PostgreSQL — inherently maintain monotonic writes on a single primary. In multi-primary systems (like multi-master MySQL or active-active Cassandra), monotonic writes must be explicitly enforced through sequence numbers, logical clocks, or session affinity.

**Combined Session Guarantee Mental Model:**

```
A single client session over time:

   Time ──────────────────────────────────────────────────────────────►

   Client Writes:  [W1: x=5]──[W2: x=10]──[W3: x=15]
   
   Monotonic Writes:  W1 before W2 before W3  (write order preserved)
   
   Client Reads:   [R1]──────────────[R2]────────────────[R3]
   
   Monotonic Reads:  R1 ≤ R2 ≤ R3  (reads never go backward in time)
   
   Read-Your-Writes:
     If R1 comes after W1, R1 must return at least x=5.
     If R2 comes after W2, R2 must return at least x=10.
```

## 8. Real-World Examples in Your Stack

Since you work with Go, PostgreSQL, MongoDB, Redis, and Cassandra-style systems, let us tie these concepts directly to your daily tools.

**PostgreSQL (single primary)** operates under strong consistency by default. Every read sees the latest committed write. When you add a read replica and route some reads to it, you drop down to eventual consistency with read-your-writes violations possible, unless you use synchronous replication and sticky session routing. This is a very common architectural gotcha in production systems.

**MongoDB** offers multiple consistency levels depending on your read preference and write concern settings. With `writeConcern: "majority"` and `readConcern: "majority"`, you get strong consistency. With `readPreference: "secondaryPreferred"`, you get eventual consistency with potential staleness on reads. MongoDB's client sessions (introduced in 4.0) provide causal consistency automatically, meaning read-your-writes and monotonic reads are guaranteed within a session.

**Redis in Cluster mode** is eventually consistent by design. When you write to a primary shard and immediately read from a replica, you may see a stale value. Redis Sentinel and Cluster do not guarantee strong consistency. When a failover happens, writes acknowledged by the old primary but not yet replicated to the new primary can be lost. Your Go services using Redis must be designed with this in mind — Redis is a cache and a fast store, not a consistency-critical source of truth.

**RabbitMQ** message delivery ordering is a form of sequential consistency within a single queue — messages are delivered in the order they were enqueued. However, with multiple consumers, parallel processing breaks ordering. This is why partitioned queues or topic exchanges with single consumers are used when ordering matters.

**PostgreSQL with logical replication to a read replica** gives you eventual consistency with a replication lag. If your Go service writes to primary and reads from replica, you might read stale data for the duration of the replication lag, which can range from milliseconds to seconds under heavy write load.

## 9. The CAP Theorem — Why You Cannot Have Everything

No discussion of consistency models is complete without the CAP theorem, which provides the fundamental reason why these trade-offs exist.

The CAP theorem, proven by Eric Brewer and formally established by Gilbert and Lynch in 2002, states that any distributed data store can provide at most **two of the following three guarantees** simultaneously:

```
                        CONSISTENCY
                      (Every read returns
                       the most recent write)
                             /\
                            /  \
                           /    \
                          /      \
                         /   CA   \
                        /  systems \
                       /────────────\
                      / CP  │  AP   \
                     /      │        \
                    /────────────────\
         PARTITION          │         AVAILABILITY
         TOLERANCE          │       (Every request gets
       (System works    CAP LIMIT     a response, even if
        despite network              it might be stale)
        partitions)
        

CA Systems: Sacrifice partition tolerance. 
            Only work in a single-node or perfectly reliable network.
            Example: Traditional single-server RDBMS.

CP Systems: Sacrifice availability when network partition occurs.
            Prefer correctness over serving requests.
            Example: HBase, etcd, Zookeeper, PostgreSQL (sync replication).

AP Systems: Sacrifice consistency when network partition occurs.
            Prefer availability over correctness.
            Example: CouchDB, Cassandra, DynamoDB, Redis Cluster.
```

A **network partition** is when two nodes in a distributed system cannot communicate with each other — a dropped network link, a firewall, a crashed node. Partitions are not theoretical — they happen in production regularly. The CAP theorem says: when a partition happens, you must choose — do you stop serving requests (maintain consistency, sacrifice availability), or do you keep serving requests knowing some reads might be stale (maintain availability, sacrifice consistency)?

This is precisely why strong consistency is expensive in distributed systems. To guarantee that every read returns the latest write, you need coordination across nodes. But coordination requires network communication, and if the network is partitioned, you are stuck. A strongly consistent system will refuse to serve requests rather than return potentially stale data.

An eventually consistent system, on the other hand, says: "We will keep serving requests even if some nodes are cut off from the rest. They will sync up when the partition heals." This is why Cassandra and DynamoDB can achieve 99.99% availability — they never refuse a request, even during partitions. The cost is that different clients might see different values temporarily.

├──────────────────────┼────────────────────────────────────────────────┤
│ Strong Consistency   │ Every read sees the absolute latest write,     │
│ (Linearizability)    │ across all nodes, in real time.                │
├──────────────────────┼────────────────────────────────────────────────┤
│ Sequential           │ All operations appear in a global order        │
│ Consistency          │ consistent with each client's program order,   │
│                      │ but not necessarily real wall-clock time.      │
├──────────────────────┼────────────────────────────────────────────────┤
│ Causal Consistency   │ If A caused B, everyone sees A before B.       │
│                      │ Unrelated operations can appear in any order.  │
├──────────────────────┼────────────────────────────────────────────────┤
│ Eventual Consistency │ All replicas will converge to the same value   │
│                      │ eventually. No ordering guarantee during       │
│                      │ convergence.                                   │
├──────────────────────┼────────────────────────────────────────────────┤
│ Read-Your-Writes     │ (Session) My own writes are always visible     │
│                      │ to my own subsequent reads.                    │
├──────────────────────┼────────────────────────────────────────────────┤
│ Monotonic Reads      │ (Session) My reads never travel backward.      │
│                      │ Once I've seen version V, I'll never see       │
│                      │ anything older than V again.                   │
├──────────────────────┼────────────────────────────────────────────────┤
│ Monotonic Writes     │ (Session) My writes are applied in the order   │
│                      │ I sent them. Write 1 always precedes Write 2.  │
└──────────────────────┴────────────────────────────────────────────────┘

CHOOSING THE RIGHT MODEL:
┌──────────────────────────────────────────────────────────────────────┐
│ Use Case                              │ Recommended Model            │
├───────────────────────────────────────┼──────────────────────────────┤
│ Financial transactions, banking       │ Strong Consistency           │
│ Inventory / stock levels              │ Strong Consistency           │
│ Distributed coordination / locks      │ Sequential Consistency       │
│ Collaborative editing, social posts   │ Causal Consistency           │
│ DNS, CDN, caching, social feeds       │ Eventual Consistency         │
│ User profile update → view own page  │ Read-Your-Writes             │
│ Paginated feed, dashboard polling     │ Monotonic Reads              │
│ Order of operations from one client   │ Monotonic Writes             │
└───────────────────────────────────────┴──────────────────────────────┘

_This guide covers the theoretical foundations and practical implications of database consistency models. The field continues to evolve — modern systems like Google Spanner (TrueTime), CockroachDB, and YugabyteDB push the boundaries of what is achievable by leveraging atomic clocks and tightly controlled infrastructure to deliver strong consistency at global scale. The trade-offs, however, remain fundamentally the same: correctness costs coordination, and coordination costs time._
