## 1. Understanding SQL Injection — The Attack in Depth

SQL injection is possible for one reason and one reason alone: **the application constructs a SQL query by concatenating user-supplied input directly into the query string, without separating the data from the SQL syntax.** When you concatenate user input into a SQL string, the database has no way to distinguish between the SQL code you wrote and the SQL code the attacker smuggled in through the input field.

To understand why this is a structural problem and not just a "bad input" problem, you must understand how a database parses a query. When the database receives a query string, it goes through a **parse phase** where it reads the string and interprets it as SQL syntax. At this point, the database has no idea which parts of the string came from the developer and which parts came from the user. It sees one undifferentiated string and parses it in its entirety as SQL. If the user's input contained SQL keywords, operators, and string delimiters, those become part of the SQL syntax — because the parser cannot tell them apart from the developer's intended SQL.

```
THE ANATOMY OF SQL INJECTION — Step by Step:

Vulnerable Go code:
  userID := r.URL.Query().Get("id")
  query := "SELECT name, email FROM users WHERE id = " + userID
  rows, _ := db.Query(query)

Normal request:   ?id=42
  Query becomes:  SELECT name, email FROM users WHERE id = 42
  Result:         Returns Alice's row. ← Expected behaviour.

Malicious request: ?id=42 OR 1=1
  Query becomes:  SELECT name, email FROM users WHERE id = 42 OR 1=1
  Result:         Returns ALL rows in the table! ← Data breach.

Malicious request: ?id=0 UNION SELECT username, password FROM admin_users--
  Query becomes:  SELECT name, email FROM users WHERE id = 0
                  UNION SELECT username, password FROM admin_users--
  Result:         Returns admin usernames and password hashes. ← Breach.

Malicious request: ?id=1; DROP TABLE users;--
  Query becomes:  SELECT name, email FROM users WHERE id = 1;
                  DROP TABLE users;--
  Result:         Executes two statements. users table destroyed. ← Catastrophic.

─────────────────────────────────────────────────────────────────────

THE PARSER'S PERSPECTIVE — Why It Cannot Tell Them Apart:

What the developer intended:
  ┌──────────────────────────────────┬───────┐
  │  SQL SYNTAX (developer's code)   │ DATA  │
  │  SELECT name, email FROM users   │  42   │
  │  WHERE id =                      │       │
  └──────────────────────────────────┴───────┘

What the database actually receives (string concatenation):
  "SELECT name, email FROM users WHERE id = 42 OR 1=1"
  │──────────────────────────────────────────────────│
                One undifferentiated string.
         The parser sees ALL of this as SQL syntax.
         There is no boundary between developer code and user data.
         The attacker erased that boundary by injecting SQL syntax.
```

SQL injection attacks fall into several categories of increasing sophistication, and understanding them all is necessary because your defenses must cover the full spectrum.

**In-band SQL injection** is the most common and most visible type. The attacker retrieves data directly through the same channel used to inject the SQL — the response to the HTTP request contains the leaked data. The `UNION`-based attack above is an example: the attacker injects a `UNION SELECT` that appends rows from a different table to the normal result set.

**Error-based SQL injection** exploits database error messages to extract information. If your application returns database error messages to the user (which it should never do in production), an attacker can deliberately cause type conversion errors or constraint violations that include sensitive data in the error message. For example: `CAST((SELECT password FROM users WHERE username='admin') AS INTEGER)` will fail with a type cast error, but the error message will contain the password value as part of the error.

**Blind SQL injection** is used when the application does not return query results or error messages. The attacker cannot see the data directly, but they can ask yes/no questions and infer information from the application's behaviour. **Boolean-based blind** injection changes the query's WHERE clause with conditions that are either true or false and observes whether the application returns results or not. **Time-based blind** injection uses `SLEEP()` or `pg_sleep()` to cause a delay in the response — if the query takes 5 seconds to respond, the condition was true; if it responds immediately, it was false. Either way, the attacker can extract one bit of information per request and reconstruct the entire database schema and data over thousands of requests.

```
BLIND SQL INJECTION — Extracting Data Without Seeing It:

Application endpoint: GET /users?id=42
  Normal:   Returns user data or empty (never error messages)
  Attacker: Cannot see query results. But can observe behaviour.

Boolean-based blind (is the first character of the admin password 'a'?):
  ?id=42 AND SUBSTRING((SELECT password FROM users WHERE id=1),1,1)='a'
  → If user data returned: YES, first char is 'a'
  → If no data returned:   NO, first char is not 'a'

  Attacker loops through every character, every position:
  ?id=42 AND SUBSTRING((SELECT password FROM users WHERE id=1),1,1)='a' → NO
  ?id=42 AND SUBSTRING((SELECT password FROM users WHERE id=1),1,1)='b' → NO
  ...
  ?id=42 AND SUBSTRING((SELECT password FROM users WHERE id=1),1,1)='s' → YES
  → First character is 's'

  Continue for position 2, 3, 4... Eventually: full password extracted.
  Tools like sqlmap automate this completely. Takes minutes, not hours.

Time-based blind (even if application returns identical responses):
  ?id=42; SELECT CASE WHEN (1=1) THEN pg_sleep(5) ELSE pg_sleep(0) END--
  → Response takes 5 seconds: condition is TRUE
  → Response is immediate: condition is FALSE

  Works even if the application returns HTTP 200 with identical body
  for found and not-found cases. The timing difference is detectable.
```

The critical lesson from understanding the full attack surface is this: **SQL injection is not prevented by filtering out "bad" characters or "bad" keywords.** Attackers use encoding tricks, alternate representations, case variations, and multi-step attacks to bypass filters. The only complete prevention is to eliminate the structural vulnerability — the mixing of code and data — by using parameterised queries. Every other technique is a supplement, not a replacement.

## 2. Parameterized Queries and Prepared Statements

Parameterized queries (also called prepared statements) are the single most important defense against SQL injection, and they are the primary recommendation of every security authority including OWASP, NIST, and the PCI Security Standards Council. They work not by filtering input but by fundamentally changing how the database processes queries — by separating the SQL code from the data values at the protocol level.

When you use a parameterised query, you send the database two separate things. First, you send the **query template** — the SQL structure with placeholder symbols (`$1`, `$2`, `?`) where the data values will go. The database parses this template, builds an execution plan, and stores it. At this point, the parsing is done. The database knows exactly what SQL this query will execute. Second, you send the **parameter values** — the actual data. At this stage, the parsing is already complete. The database treats the parameter values as pure data, not as SQL to be parsed. No matter what the parameter value contains — single quotes, semicolons, `DROP TABLE`, or anything else — it is treated as a string of bytes to be compared, not as SQL syntax to be interpreted.

```
HOW PREPARED STATEMENTS PREVENT INJECTION — The Protocol Level:

Step 1: Application sends query TEMPLATE to database:
  "SELECT name, email FROM users WHERE id = $1"

  Database parses this. Builds execution plan.
  The parse phase is COMPLETE.
  Database knows: "This is a SELECT on the users table,
                   filtering on id, which will be provided later."

Step 2: Application sends parameter VALUE:
  $1 = "42 OR 1=1"   ← Attacker's malicious input

  Database receives "42 OR 1=1" as the VALUE for parameter $1.
  It does NOT re-parse the query.
  It treats "42 OR 1=1" as the literal value to compare against id.
  SQL execution: WHERE id = '42 OR 1=1'
  → id column (integer) compared to string '42 OR 1=1'
  → 0 rows returned. Attack failed. ✓

WHAT THE DATABASE DOES WITH THE PARAMETER:
  Parameterized:   WHERE id = $1           ← sql structure
                   $1 = '42 OR 1=1'        ← treated as data value
                   Executed as: WHERE id = '42 OR 1=1'
                   Result: no rows (type mismatch on integer column)

  Concatenated:    WHERE id = 42 OR 1=1   ← parsed as sql structure
                   Result: returns all rows! ← injection succeeds

The key insight: in a prepared statement, the SQL syntax is FIXED
before any user input is involved. User input arrives AFTER parsing.
The database is incapable of misinterpreting data as code at this point.
```

In Go, both the standard `database/sql` package and the `pgx` library (the most common PostgreSQL driver) implement prepared statements. The `database/sql` API uses `?` placeholders (for MySQL, SQLite) or `$1, $2` placeholders (for PostgreSQL via the driver). The `db.Query()`, `db.QueryRow()`, and `db.Exec()` functions accept parameters as variadic arguments after the query string — these are always parameterised, never concatenated.

```go
// ─────────────────────────────────────────────────────────────────────
// VULNERABLE CODE — String Concatenation (NEVER DO THIS):
// ─────────────────────────────────────────────────────────────────────

func getUserVulnerable(db *sql.DB, userID string) (*User, error) {
    // VULNERABLE: userID is concatenated directly into SQL
    query := "SELECT id, name, email FROM users WHERE id = " + userID
    // If userID = "1 OR 1=1", query becomes:
    // SELECT id, name, email FROM users WHERE id = 1 OR 1=1
    // → Returns all rows!
    row := db.QueryRow(query)
    // ...
}

// ─────────────────────────────────────────────────────────────────────
// SAFE CODE — Parameterized Query (database/sql):
// ─────────────────────────────────────────────────────────────────────

func getUserSafe(db *sql.DB, userID int64) (*User, error) {
    // SAFE: $1 is a placeholder. userID is passed as a separate argument.
    // The database driver sends query and parameter separately.
    query := "SELECT id, name, email FROM users WHERE id = $1"
    row := db.QueryRow(query, userID) // userID is data, never parsed as SQL

    var u User
    err := row.Scan(&u.ID, &u.Name, &u.Email)
    if err != nil {
        if errors.Is(err, sql.ErrNoRows) {
            return nil, ErrUserNotFound
        }
        return nil, fmt.Errorf("getUserSafe: %w", err)
    }
    return &u, nil
}

// ─────────────────────────────────────────────────────────────────────
// SAFE CODE — Multiple Parameters (pgx):
// ─────────────────────────────────────────────────────────────────────

func searchUsers(pool *pgxpool.Pool, name string, minAge int, limit int) ([]*User, error) {
    ctx := context.Background()
    // $1, $2, $3 are positional parameters — all user input is parameterized
    query := `
        SELECT id, name, email, date_of_birth
        FROM users
        WHERE name ILIKE $1
          AND EXTRACT(YEAR FROM AGE(date_of_birth)) >= $2
          AND deleted_at IS NULL
        ORDER BY created_at DESC
        LIMIT $3`

    // name, minAge, limit are all passed as separate args — never concatenated
    rows, err := pool.Query(ctx, query,
        "%"+name+"%", // Wildcard wrapping is safe — it is still a parameter value
        minAge,
        limit,
    )
    if err != nil {
        return nil, fmt.Errorf("searchUsers query: %w", err)
    }
    defer rows.Close()

    var users []*User
    for rows.Next() {
        var u User
        if err := rows.Scan(&u.ID, &u.Name, &u.Email, &u.DOB); err != nil {
            return nil, fmt.Errorf("searchUsers scan: %w", err)
        }
        users = append(users, &u)
    }
    return users, rows.Err()
}
```

There is an important nuance about the ILIKE example above: wrapping user input in wildcard characters (`"%"+name+"%"`) is safe because the concatenation happens on the application side before the entire resulting string is passed as a single parameter value. The database receives `%alice%` as a data value, not as SQL. This is fundamentally different from concatenating into the SQL string itself. The distinction is: concatenation into the **parameter value** is safe; concatenation into the **SQL string** is not.

The `database/sql` package also supports explicit prepared statement caching via `db.Prepare()`, which sends the query template to the database once and returns a `*sql.Stmt` that can be executed repeatedly with different parameter values. This has a performance advantage: the database parses and plans the query only once, and subsequent executions reuse the plan. For queries that run thousands of times per second, this can be significant. However, `pgx` automatically caches prepared statements at the connection level, so explicitly calling `db.Prepare()` is less necessary with `pgx` than with MySQL drivers.

```go
// ─────────────────────────────────────────────────────────────────────
// EXPLICIT PREPARED STATEMENT — Performance Optimisation:
// ─────────────────────────────────────────────────────────────────────

type UserRepository struct {
    db           *sql.DB
    getByIDStmt  *sql.Stmt
    updateStmt   *sql.Stmt
}

func NewUserRepository(db *sql.DB) (*UserRepository, error) {
    // Prepare statements once at startup — parsed and planned once:
    getByID, err := db.Prepare(
        "SELECT id, name, email FROM users WHERE id = $1 AND deleted_at IS NULL",
    )
    if err != nil {
        return nil, fmt.Errorf("prepare getByID: %w", err)
    }

    update, err := db.Prepare(
        "UPDATE users SET name = $1, email = $2, updated_at = NOW() WHERE id = $3",
    )
    if err != nil {
        getByID.Close()
        return nil, fmt.Errorf("prepare update: %w", err)
    }

    return &UserRepository{
        db:          db,
        getByIDStmt: getByID,
        updateStmt:  update,
    }, nil
}

func (r *UserRepository) GetByID(ctx context.Context, id int64) (*User, error) {
    // Reuses the prepared statement — no re-parsing:
    row := r.getByIDStmt.QueryRowContext(ctx, id)
    var u User
    if err := row.Scan(&u.ID, &u.Name, &u.Email); err != nil {
        return nil, err
    }
    return &u, nil
}

func (r *UserRepository) Close() {
    r.getByIDStmt.Close()
    r.updateStmt.Close()
}
```

There is one class of SQL where parameterisation is not applicable and requires special care: **dynamic SQL elements that cannot be parameterised.** SQL parameters only work for data values — the content of a WHERE clause, a value being inserted, a value being compared. They cannot be used for SQL structural elements like table names, column names, ORDER BY directions, or SQL keywords. When these must be dynamic — for instance, an API that allows the client to choose which column to sort by — you cannot use a parameter, and you must use an alternative safe approach.

The safe approach for dynamic structural elements is an **allowlist**. You define the complete set of permitted values in your application code, and you map user input to one of those permitted values before building the SQL. You never interpolate user input directly — you look up user input in a map and use only the pre-approved SQL fragment.

```go
// ─────────────────────────────────────────────────────────────────────
// DYNAMIC SQL ELEMENTS — Cannot Be Parameterized, Must Use Allowlist:
// ─────────────────────────────────────────────────────────────────────

// Table names, column names, ORDER BY direction cannot be $1 parameters.
// The following is STILL VULNERABLE even though it uses Sprintf
// to build a string — user input is still touching SQL structure:
//
// WRONG:
// query := fmt.Sprintf("SELECT * FROM users ORDER BY %s %s", sortCol, sortDir)
// → Attack: sortCol = "name; DROP TABLE users;--"
//

// CORRECT: Allowlist approach
var allowedSortColumns = map[string]string{
    "name":       "name",
    "email":      "email",
    "created_at": "created_at",
    "updated_at": "updated_at",
}

var allowedSortDirections = map[string]string{
    "asc":  "ASC",
    "desc": "DESC",
}

func listUsers(
    db *pgxpool.Pool,
    sortCol string,
    sortDir string,
    limit int,
) ([]*User, error) {
    // Look up in allowlist — if not found, use safe default:
    col, ok := allowedSortColumns[strings.ToLower(sortCol)]
    if !ok {
        col = "created_at" // safe default
    }

    dir, ok := allowedSortDirections[strings.ToLower(sortDir)]
    if !ok {
        dir = "DESC" // safe default
    }

    // col and dir are now ONLY values from our allowlist.
    // They were never directly from user input.
    // This format string is safe because col and dir
    // cannot contain SQL injection:
    query := fmt.Sprintf(
        `SELECT id, name, email FROM users
         WHERE deleted_at IS NULL
         ORDER BY %s %s
         LIMIT $1`,
        col, dir, // ← from allowlist, not from user
    )

    // limit is still parameterized:
    rows, err := db.Query(context.Background(), query, limit)
    // ...
}
```

## 3. ORM-Level Protection — and Its Gaps

Object-Relational Mappers (ORMs) — libraries that let you interact with databases through language-native objects rather than raw SQL — provide a significant layer of SQL injection protection for the vast majority of common database operations. When you use an ORM correctly, you never write SQL at all, and therefore you never have the opportunity to make the mistake of string concatenation. The ORM generates parameterised queries internally, invisibly.

In the Go ecosystem, the most commonly used ORMs and query builders are GORM, sqlc (technically a type-safe query generator rather than an ORM), Squirrel (a query builder), and Ent. Each takes a different philosophy toward query construction, and each has different implications for SQL injection safety.

**GORM** is the most popular full ORM for Go. Its basic CRUD operations — `db.Create(&user)`, `db.Find(&users)`, `db.Save(&user)`, `db.Delete(&user)` — all generate parameterised SQL internally. When you use GORM's query builder methods like `Where()`, `Select()`, `Order()`, and `Joins()`, the library generates prepared statements automatically.

However, GORM has several injection vectors that are not immediately obvious, and understanding them is critical because they are responsible for many real-world vulnerabilities in GORM-based applications.

```go
// ─────────────────────────────────────────────────────────────────────
// GORM — SAFE PATTERNS:
// ─────────────────────────────────────────────────────────────────────

// Safe: struct conditions (automatically parameterized)
db.Where(&User{Name: userName, Active: true}).Find(&users)
// Generated: SELECT * FROM users WHERE name = $1 AND active = $2

// Safe: map conditions (automatically parameterized)
db.Where(map[string]interface{}{"name": userName, "active": true}).Find(&users)

// Safe: positional placeholders with ?
db.Where("name = ? AND active = ?", userName, true).Find(&users)
// Generated: SELECT * FROM users WHERE name = $1 AND active = $2

// Safe: named placeholders
db.Where("name = @name AND age > @age",
    sql.Named("name", userName),
    sql.Named("age", minAge),
).Find(&users)

// ─────────────────────────────────────────────────────────────────────
// GORM — DANGEROUS PATTERNS (injection vectors):
// ─────────────────────────────────────────────────────────────────────

// DANGER: Raw SQL string with user input directly embedded:
db.Where("name = '" + userName + "'").Find(&users)
// → userName = "alice' OR '1'='1" → injection succeeds!

// DANGER: Raw() with string formatting:
db.Raw("SELECT * FROM users WHERE name = '" + userName + "'").Scan(&users)
// → Direct injection vector. Identical to the raw db.Query vulnerability.

// DANGER: Order() with unsanitized user input:
db.Order(userSortInput).Find(&users)
// → userSortInput = "name; DROP TABLE users;--" → injection succeeds!
// GORM's Order() does not sanitize — it passes the string to SQL directly.

// DANGER: Table() with user input:
db.Table(userTableName).Find(&results)
// → Table names cannot be parameterized. Never use user input here.

// ─────────────────────────────────────────────────────────────────────
// GORM — SAFE ALTERNATIVES for Dynamic Elements:
// ─────────────────────────────────────────────────────────────────────

// Safe Order: allowlist before passing to GORM:
allowedOrders := map[string]string{
    "name_asc":        "name ASC",
    "name_desc":       "name DESC",
    "created_at_desc": "created_at DESC",
}
safeOrder, ok := allowedOrders[userSortInput]
if !ok {
    safeOrder = "created_at DESC"
}
db.Order(safeOrder).Find(&users) // safeOrder is from allowlist, not user input

// Safe Raw: use ? placeholders even in Raw():
db.Raw("SELECT * FROM users WHERE name = ?", userName).Scan(&users)
// → Parameterized even in raw SQL. ✓
```

**sqlc** takes a completely different and arguably safer approach. You write SQL queries in `.sql` files, and `sqlc` generates type-safe Go functions from those queries at compile time. Because the SQL is static and written by the developer (never constructed at runtime from user input), there is no opportunity for SQL injection in the generated code. User input is always passed as arguments to the generated functions, which use parameterised queries internally. The only injection risk is if you write your SQL files with dynamic concatenation — which `sqlc` does not support, making it structurally injection-safe.

**Squirrel** is a query builder rather than a full ORM. It provides a fluent API for constructing SQL programmatically, and all value placeholders are automatically parameterised. However, like GORM's Order(), Squirrel's `OrderBy()` and `Column()` methods pass strings directly to the SQL, so dynamic column and table names still require allowlisting.

```go
// ─────────────────────────────────────────────────────────────────────
// SQUIRREL — Safe Query Building:
// ─────────────────────────────────────────────────────────────────────

import sq "github.com/Masterminds/squirrel"

// Safe: all WHERE values are parameterized automatically:
users, err := sq.Select("id", "name", "email").
    From("users").
    Where(sq.Eq{"name": userName}).           // parameterized ✓
    Where(sq.Gt{"age": minAge}).              // parameterized ✓
    Where(sq.Like{"email": "%@example.com"}). // parameterized ✓
    OrderBy("created_at DESC").               // static string — safe ✓
    Limit(10).
    RunWith(db).
    Query()

// Still dangerous if user input reaches OrderBy directly:
// .OrderBy(userInput)  ← NEVER do this without allowlisting
```

The fundamental lesson about ORMs is that they protect you by default for value parameters, but they cannot protect you when you bypass their parameterisation mechanisms. Every ORM has raw query escape hatches — `Raw()` in GORM, `Exec()` with format strings, custom SQL fragments. These escape hatches exist because ORMs cannot express every possible SQL query. When you reach for them — and sometimes you legitimately must — you take back full responsibility for SQL injection prevention. The ORM's protection ends the moment you start writing SQL strings.

## 4. Stored Procedures as a Defense Layer

Stored procedures — named, precompiled SQL routines stored inside the database — are a meaningful additional layer of SQL injection defense, though one that is frequently misunderstood and sometimes oversold. Understanding precisely what stored procedures protect against, and what they do not protect against, is essential for using them correctly.

A stored procedure is defined in the database once, at development or deployment time. The SQL inside the procedure is parsed, validated, and often partially optimised when the procedure is created — not when it is called. When your application calls a stored procedure, it passes only parameter values, not SQL text. The database executes the pre-defined procedure with those parameter values, treating them as data. This is structurally similar to a prepared statement: the SQL structure is fixed at definition time, and user input arrives later as parameters.

```sql
-- DEFINING A STORED PROCEDURE IN POSTGRESQL:

CREATE OR REPLACE FUNCTION get_user_by_id(
    p_user_id BIGINT
)
RETURNS TABLE (
    id        BIGINT,
    name      TEXT,
    email     TEXT,
    created_at TIMESTAMPTZ
)
LANGUAGE SQL
STABLE   -- Declares that this function doesn't modify data
AS $$
    SELECT id, name, email, created_at
    FROM users
    WHERE id = p_user_id
      AND deleted_at IS NULL;
$$;

-- The SQL inside is parsed and stored in the DB when CREATE runs.
-- No SQL parsing happens when the procedure is called.
-- p_user_id is ALWAYS treated as data, never as SQL syntax.
```

```go
// CALLING A STORED PROCEDURE FROM GO — pgx:

func getUserByID(pool *pgxpool.Pool, userID int64) (*User, error) {
    ctx := context.Background()

    // Calling the stored procedure — userID is a parameter value,
    // never part of the SQL string:
    row := pool.QueryRow(ctx,
        "SELECT id, name, email, created_at FROM get_user_by_id($1)",
        userID,
    )

    var u User
    if err := row.Scan(&u.ID, &u.Name, &u.Email, &u.CreatedAt); err != nil {
        if errors.Is(err, pgx.ErrNoRows) {
            return nil, ErrNotFound
        }
        return nil, fmt.Errorf("getUserByID: %w", err)
    }
    return &u, nil
}
```

Stored procedures provide several benefits beyond SQL injection prevention. They **encapsulate business logic** in the database, ensuring that the same validation and access rules apply regardless of which application connects to the database. A stored procedure that validates that a user can only update their own records enforces that rule even for direct DBA connections and admin scripts. They also provide **privilege isolation**: you can grant a role `EXECUTE` privilege on a specific procedure without granting that role direct `SELECT`, `INSERT`, or `UPDATE` privileges on the underlying tables. The procedure runs with the privileges of its definer (by default in PostgreSQL, with the `SECURITY DEFINER` attribute), meaning the calling role needs only `EXECUTE`, not direct table access.

```sql
-- PRIVILEGE ISOLATION VIA STORED PROCEDURES:

-- The transfer_funds procedure enforces business rules:
CREATE OR REPLACE FUNCTION transfer_funds(
    p_from_account BIGINT,
    p_to_account   BIGINT,
    p_amount       NUMERIC(15,2),
    p_performed_by BIGINT
)
RETURNS VOID
LANGUAGE PLPGSQL
SECURITY DEFINER   -- Runs with the privileges of the function creator
AS $$
BEGIN
    -- Business rule enforcement (not bypassable by calling app):
    IF p_amount <= 0 THEN
        RAISE EXCEPTION 'Transfer amount must be positive';
    END IF;

    IF p_from_account = p_to_account THEN
        RAISE EXCEPTION 'Cannot transfer to the same account';
    END IF;

    -- Check balance:
    IF (SELECT balance FROM accounts WHERE id = p_from_account FOR UPDATE) < p_amount THEN
        RAISE EXCEPTION 'Insufficient funds';
    END IF;

    -- Execute transfer:
    UPDATE accounts SET balance = balance - p_amount WHERE id = p_from_account;
    UPDATE accounts SET balance = balance + p_amount WHERE id = p_to_account;

    -- Audit log:
    INSERT INTO transfer_log (from_acct, to_acct, amount, performed_by, performed_at)
    VALUES (p_from_account, p_to_account, p_amount, p_performed_by, NOW());
END;
$$;

-- Grant ONLY execute to the application role:
GRANT EXECUTE ON FUNCTION transfer_funds TO app_service;

-- Revoke direct table access from app_service:
REVOKE INSERT, UPDATE ON TABLE accounts FROM app_service;
-- Now app_service can ONLY transfer funds via this procedure,
-- which enforces all business rules. Direct table manipulation blocked.
```

However, stored procedures are not a silver bullet. There is a common and dangerous misconception that "using stored procedures prevents SQL injection." This is false when stored procedures themselves construct dynamic SQL internally using concatenation. A PostgreSQL `PLPGSQL` function that uses `EXECUTE 'SELECT ... WHERE id = ' || p_id` is just as vulnerable as application code doing the same thing — the injection just happens inside the database rather than in the application. The defence only works when the stored procedure itself uses parameterised internal queries.

```sql
-- VULNERABLE STORED PROCEDURE — Dynamic SQL with Concatenation:
-- (YES, stored procedures can themselves be injection vectors!)

CREATE OR REPLACE FUNCTION search_users_VULNERABLE(
    p_column TEXT,
    p_value  TEXT
)
RETURNS SETOF users
LANGUAGE PLPGSQL AS $$
BEGIN
    -- VULNERABLE: concatenating user input into dynamic SQL
    RETURN QUERY EXECUTE
        'SELECT * FROM users WHERE ' || p_column || ' = ''' || p_value || '''';
    -- If p_column = "1=1 OR name", injection succeeds inside the DB.
END;
$$;

-- SAFE STORED PROCEDURE — Parameterized Dynamic SQL:
CREATE OR REPLACE FUNCTION search_users_SAFE(
    p_column TEXT,
    p_value  TEXT
)
RETURNS SETOF users
LANGUAGE PLPGSQL AS $$
DECLARE
    safe_column TEXT;
BEGIN
    -- Allowlist validation inside the stored procedure:
    IF p_column NOT IN ('name', 'email', 'phone') THEN
        RAISE EXCEPTION 'Invalid column name: %', p_column;
    END IF;
    safe_column := p_column; -- Now safe — only from our allowlist

    -- Use USING clause for parameterised dynamic SQL:
    RETURN QUERY EXECUTE
        'SELECT * FROM users WHERE ' || safe_column || ' = $1'
        USING p_value; -- $1 is parameterized! p_value is never parsed as SQL.
END;
$$;
```

## 5. Input Validation — The Complementary Layer

Input validation is the practice of verifying that user-supplied data conforms to expected formats, types, lengths, and value ranges before processing it. It is a complementary layer of defence — not a replacement for parameterised queries, but an important additional barrier that catches bad data early, reduces the attack surface, and improves the robustness of the system in ways that extend beyond security.

The relationship between input validation and SQL injection prevention must be clearly understood: **input validation alone does not prevent SQL injection, and it should never be your primary defence.** A comprehensive filter that blocks semicolons, single quotes, and SQL keywords can be bypassed through encoding tricks, double encoding, Unicode normalisation attacks, and second-order injection. Parameterised queries are the primary defence. Input validation is the second line, providing defence in depth and catching other categories of bugs.

That said, input validation serves several important security functions. It enforces **type safety** — if a field is expected to be an integer, reject anything that is not an integer before it ever reaches the database layer. An integer parameter cannot contain SQL injection, by definition. It enforces **length limits** — a field that should contain a name (maximum 100 characters) should reject input of 10,000 characters, not only for security but because an excessively long value might indicate a buffer overflow attempt or a denial-of-service attempt against processing pipelines. It enforces **format constraints** — a field that should contain an email address should be validated against an email format; a phone number should match a phone number pattern; a UUID should match UUID format.

```go
// ─────────────────────────────────────────────────────────────────────
// INPUT VALIDATION IN GO — Layered Approach:
// ─────────────────────────────────────────────────────────────────────

import (
    "regexp"
    "unicode/utf8"
    "github.com/go-playground/validator/v10"
)

// Validation struct with tags — declarative validation:
type CreateUserRequest struct {
    Name     string `json:"name"    validate:"required,min=1,max=100,printascii"`
    Email    string `json:"email"   validate:"required,email,max=254"`
    Phone    string `json:"phone"   validate:"omitempty,e164"`   // E.164 format
    Age      int    `json:"age"     validate:"required,min=0,max=150"`
    Role     string `json:"role"    validate:"required,oneof=user admin moderator"`
}

var validate = validator.New()

func validateCreateUserRequest(req *CreateUserRequest) error {
    if err := validate.Struct(req); err != nil {
        return fmt.Errorf("validation failed: %w", err)
    }
    return nil
}

// ─────────────────────────────────────────────────────────────────────
// CUSTOM VALIDATORS — Business Logic Constraints:
// ─────────────────────────────────────────────────────────────────────

// Allowlist validator for sort column:
func validateSortColumn(column string) (string, error) {
    allowed := map[string]bool{
        "name": true, "email": true, "created_at": true,
    }
    if !allowed[column] {
        return "created_at", nil // Safe default, not an error
    }
    return column, nil
}

// Strict UUID validator (no SQL special characters possible in a UUID):
var uuidRegex = regexp.MustCompile(
    `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`,
)
func validateUUID(id string) error {
    if !uuidRegex.MatchString(strings.ToLower(id)) {
        return errors.New("invalid UUID format")
    }
    return nil
}

// ─────────────────────────────────────────────────────────────────────
// VALIDATION MIDDLEWARE — Apply at the HTTP Handler Level:
// ─────────────────────────────────────────────────────────────────────

func CreateUserHandler(w http.ResponseWriter, r *http.Request) {
    var req CreateUserRequest

    // 1. Decode JSON:
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        http.Error(w, "invalid JSON", http.StatusBadRequest)
        return
    }

    // 2. Validate BEFORE any database interaction:
    if err := validateCreateUserRequest(&req); err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest)
        return
    }

    // 3. At this point, we know:
    //    - name is 1-100 printable ASCII characters
    //    - email is valid format, max 254 chars
    //    - age is 0-150 integer
    //    - role is one of {user, admin, moderator}
    //    Even if parameterized queries weren't used, injection
    //    would be significantly harder (but still use parameterized queries!)

    // 4. Database operation — parameterized query (primary defense):
    if err := userRepo.Create(r.Context(), &req); err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }

    w.WriteHeader(http.StatusCreated)
}
```

One critical aspect of input validation that is often missed is **output encoding** — not injecting SQL in, but preventing XSS (Cross-Site Scripting) attacks when user data is later rendered in HTML. While XSS is not SQL injection, it shares the same root cause: failure to separate data from code at the output boundary. A comprehensive input validation strategy considers both the database boundary (parameterised queries) and the HTML boundary (HTML encoding of output). Go's `html/template` package handles HTML encoding automatically for template variables; using `text/template` instead is a common mistake that creates XSS vulnerabilities.

Input validation also serves as a powerful **fail-fast mechanism**. Rejecting invalid input at the API boundary, before it travels to the service layer, reaches the database, or gets logged, reduces system complexity and prevents corruption of data at rest. A phone number field that should contain digits and hyphens but contains a JavaScript payload should be rejected immediately at the HTTP handler, not cleaned up after the fact deeper in the system.

## 6. Second-Order SQL Injection — The Hidden Attack

Second-order SQL injection (also called stored SQL injection or persistent SQL injection) is the most insidious form of the attack because it exploits a temporal disconnect between input and execution that makes it invisible to straightforward security reviews. Understanding it is essential for any engineer who believes their system is safe because it uses parameterised queries for all inserts.

In a second-order injection attack, the malicious payload is submitted to the system in one request and stored safely — using a parameterised query, causing no immediate harm. The injection succeeds not at storage time but later, when the stored data is retrieved and used to construct a new SQL query without being treated as untrusted input, because the developer assumed that data already in the database is safe.

```
SECOND-ORDER INJECTION — The Attack in Stages:

Stage 1 — Malicious data stored safely (parameterized INSERT):

  Attacker registers with username: admin'--
  Application uses parameterized query:
    INSERT INTO users (username, password)
    VALUES ($1, $2)
    → $1 = "admin'--", $2 = "attackerpassword"
  Database stores the literal string "admin'--" in the username column.
  No injection. The single quote is stored as data. ✓

─────────────────────────────────────────────────────────────────────

Stage 2 — Stored data used unsafely in a new query (VULNERABLE):

  Password reset feature retrieves username from session:
    storedUsername = "admin'--"   ← retrieved from DB (trusted naively!)

  Application constructs password update SQL (VULNERABLE):
    query = "UPDATE users SET password = '" + newPassword +
            "' WHERE username = '" + storedUsername + "'"
    →  UPDATE users SET password = 'newpass'
       WHERE username = 'admin'--'
    →  The -- comments out the rest: WHERE username = 'admin'
    →  The attacker has changed the ADMIN's password! ← Injection succeeds!

─────────────────────────────────────────────────────────────────────

WHY IT IS MISSED IN REVIEWS:

  Developer reviewing the password reset code thinks:
  "storedUsername comes from the database, which means
   it was already validated and stored safely. I can trust it."

  This reasoning is WRONG.
  Data from the database is not automatically safe for SQL concatenation.
  Once an attacker has written data containing SQL syntax into the DB,
  that data remains a SQL injection payload for any future query
  that naively concatenates it.

─────────────────────────────────────────────────────────────────────

THE RULE: Treat ALL data as untrusted when constructing SQL,
          regardless of where it came from:

  Untrusted: HTTP request parameters     → Always parameterize
  Untrusted: HTTP headers and cookies    → Always parameterize
  Untrusted: File contents              → Always parameterize
  Untrusted: Data retrieved from DB     → Always parameterize ← Easy to miss!
  Untrusted: Data from external APIs    → Always parameterize
  Untrusted: Data from message queues   → Always parameterize
```

The defense against second-order injection is simple to state but requires constant discipline: **parameterise all queries, always, regardless of where the data came from.** There is no category of data that is "trusted enough" to concatenate directly into SQL. Data retrieved from a database is not safe for SQL concatenation any more than data from an HTTP request is. The origin of data does not determine its safety in a SQL context — only parameterisation does.

Second-order injection is particularly dangerous in systems where data flows through multiple layers: data stored by one microservice is read by another, which uses it in queries; data stored in a queue is consumed by a worker, which uses it in database operations; data imported from CSV files is stored and later used in reports. Each handoff between systems is an opportunity for a developer to make the "this came from our system, it must be safe" reasoning error.

## 7. Defense in Depth — Combining All Layers

SQL injection prevention is not a single technique — it is a layered defense where each layer catches what the previous layer might miss. No single layer is infallible in every scenario, but the combination creates a system where the attacker must simultaneously defeat multiple independent defenses.

```
DEFENSE IN DEPTH — All Layers Together:

LAYER 1: Parameterized Queries (PRIMARY — eliminates the structural vuln)
  What it does:    Separates SQL code from data at the protocol level.
  What it catches: All direct SQL injection via data values.
  What it misses:  Dynamic structural elements (table/column names).
                   Cannot protect itself if the developer bypasses it.

LAYER 2: Input Validation (Fail-Fast + Type Enforcement)
  What it does:    Rejects malformed input before it reaches the DB.
  What it catches: Type violations, length violations, format violations.
                   Injection attempts via unexpected characters.
  What it misses:  Valid-format payloads. Cannot prevent all injection.
                   Not a substitute for Layer 1.

LAYER 3: Stored Procedures + Allowlists (Structural Isolation)
  What it does:    Limits what SQL can be executed through application.
                   Allowlists prevent arbitrary SQL structure.
  What it catches: Injection via dynamic SQL elements.
                   Privilege escalation through direct table access.
  What it misses:  Injection inside poorly-written stored procedures.
                   Does not protect against application-layer logic bugs.

LAYER 4: Least-Privilege DB User (Damage Limitation)
  What it does:    Application DB user has only required permissions.
  What it catches: Limits blast radius if injection somehow succeeds.
  What it catches: Prevents DROP, TRUNCATE, schema changes via injection.
  What it misses:  Cannot prevent reads on tables the user needs access to.

LAYER 5: WAF / Query Analysis (Detection + Blocking)
  What it does:    Web Application Firewall detects injection patterns.
  What it catches: Known injection patterns in HTTP requests.
  What it misses:  Encoded attacks, second-order injection.
                   High false-positive rate can block legitimate traffic.

LAYER 6: Audit Logging (Detection After the Fact)
  What it does:    Records every query, allowing breach detection.
  What it catches: Unusual query patterns, anomalous data access.
  What it misses:  Does not prevent injection — only detects it.
                   Detection may come after data is already exfiltrated.

─────────────────────────────────────────────────────────────────────

WHAT EACH ATTACK TYPE IS STOPPED BY:

Attack Type              │ L1 │ L2 │ L3 │ L4 │ L5 │ L6 │
─────────────────────────┼────┼────┼────┼────┼────┼────┤
Basic string injection   │ ✓  │ ✓  │ ✓  │    │ ✓  │ ✓  │
UNION-based injection    │ ✓  │    │ ✓  │ ✓  │ ✓  │ ✓  │
Boolean blind injection  │ ✓  │    │    │    │    │ ✓  │
Time-based blind         │ ✓  │    │    │    │    │ ✓  │
Dynamic col/table inject │    │ ✓  │ ✓  │    │    │ ✓  │
Second-order injection   │ ✓  │    │    │    │    │ ✓  │
DROP / DDL injection     │ ✓  │    │    │ ✓  │ ✓  │ ✓  │

L1 = Parameterized queries    L4 = Least privilege
L2 = Input validation         L5 = WAF
L3 = Stored procs/allowlist   L6 = Audit logging
```

## 8. Real-World Patterns in Your Go Stack

Let us make every concept concrete with production-ready Go patterns that you can adapt directly.

The most important architectural pattern for SQL injection prevention in a Go service is the **repository pattern with a strict interface**. All database access goes through repository structs, the repository methods never accept SQL strings or raw query fragments as parameters, and the only way to query the database is through well-defined methods that internally use parameterised queries. This pattern makes it structurally difficult to introduce injection vulnerabilities because there is simply no API surface for passing raw SQL from the business logic layer.

```go
// ─────────────────────────────────────────────────────────────────────
// REPOSITORY PATTERN — Complete, Production-Ready Example:
// ─────────────────────────────────────────────────────────────────────

package repository

import (
    "context"
    "errors"
    "fmt"
    "strings"
    "time"

    "github.com/jackc/pgx/v5"
    "github.com/jackc/pgx/v5/pgxpool"
)

var (
    ErrNotFound      = errors.New("record not found")
    ErrInvalidInput  = errors.New("invalid input")
)

type User struct {
    ID        int64
    Name      string
    Email     string
    Role      string
    CreatedAt time.Time
}

// ListFilter holds typed, validated filter options.
// Note: no SQL strings, no raw query fragments — only Go types.
type ListFilter struct {
    NameContains string   // Validated string — passed as param value
    Role         string   // Validated against allowlist
    SortBy       string   // Validated against allowlist
    SortDesc     bool     // Boolean — cannot contain SQL
    Limit        int      // Integer — cannot contain SQL
    Offset       int      // Integer — cannot contain SQL
}

// Allowlists defined once, used everywhere:
var allowedSortColumns = map[string]string{
    "name":       "u.name",
    "email":      "u.email",
    "created_at": "u.created_at",
}
var allowedRoles = map[string]bool{"user": true, "admin": true, "moderator": true}

type UserRepository struct {
    pool *pgxpool.Pool
}

func NewUserRepository(pool *pgxpool.Pool) *UserRepository {
    return &UserRepository{pool: pool}
}

// GetByID — single parameterized query, no dynamic SQL:
func (r *UserRepository) GetByID(ctx context.Context, id int64) (*User, error) {
    const query = `
        SELECT id, name, email, role, created_at
        FROM users
        WHERE id = $1
          AND deleted_at IS NULL`

    var u User
    err := r.pool.QueryRow(ctx, query, id).
        Scan(&u.ID, &u.Name, &u.Email, &u.Role, &u.CreatedAt)
    if err != nil {
        if errors.Is(err, pgx.ErrNoRows) {
            return nil, ErrNotFound
        }
        return nil, fmt.Errorf("UserRepository.GetByID: %w", err)
    }
    return &u, nil
}

// List — dynamic query built safely with allowlists:
func (r *UserRepository) List(ctx context.Context, f ListFilter) ([]*User, error) {
    // 1. Validate and resolve sort column from allowlist:
    sortCol, ok := allowedSortColumns[f.SortBy]
    if !ok {
        sortCol = "u.created_at" // Safe default
    }

    sortDir := "ASC"
    if f.SortDesc {
        sortDir = "DESC" // Boolean input, not user string — safe
    }

    // 2. Apply validated role filter:
    if f.Role != "" && !allowedRoles[f.Role] {
        return nil, fmt.Errorf("%w: role must be one of user/admin/moderator", ErrInvalidInput)
    }

    // 3. Build query with placeholders — NO user input touches SQL structure:
    args := []interface{}{}
    conditions := []string{"u.deleted_at IS NULL"}
    argIdx := 1

    if f.NameContains != "" {
        conditions = append(conditions, fmt.Sprintf("u.name ILIKE $%d", argIdx))
        args = append(args, "%"+f.NameContains+"%")
        argIdx++
    }

    if f.Role != "" {
        conditions = append(conditions, fmt.Sprintf("u.role = $%d", argIdx))
        args = append(args, f.Role) // role is validated against allowlist ✓
        argIdx++
    }

    // Apply limit and offset as parameters:
    args = append(args, f.Limit, f.Offset)
    limitIdx := argIdx
    offsetIdx := argIdx + 1

    // SQL structure uses ONLY allowlist values and static strings:
    // sortCol and sortDir come from our allowlists, not from user input.
    query := fmt.Sprintf(`
        SELECT id, name, email, role, created_at
        FROM users u
        WHERE %s
        ORDER BY %s %s
        LIMIT $%d OFFSET $%d`,
        strings.Join(conditions, " AND "), // conditions built from static strings + $N
        sortCol,                           // from allowlist ✓
        sortDir,                           // from boolean ✓
        limitIdx,
        offsetIdx,
    )

    rows, err := r.pool.Query(ctx, query, args...)
    if err != nil {
        return nil, fmt.Errorf("UserRepository.List: %w", err)
    }
    defer rows.Close()

    var users []*User
    for rows.Next() {
        var u User
        if err := rows.Scan(&u.ID, &u.Name, &u.Email, &u.Role, &u.CreatedAt); err != nil {
            return nil, fmt.Errorf("UserRepository.List scan: %w", err)
        }
        users = append(users, &u)
    }
    return users, rows.Err()
}

// Create — parameterized INSERT:
func (r *UserRepository) Create(ctx context.Context, name, email, role string) (*User, error) {
    const query = `
        INSERT INTO users (name, email, role, created_at)
        VALUES ($1, $2, $3, NOW())
        RETURNING id, name, email, role, created_at`

    var u User
    err := r.pool.QueryRow(ctx, query, name, email, role).
        Scan(&u.ID, &u.Name, &u.Email, &u.Role, &u.CreatedAt)
    if err != nil {
        return nil, fmt.Errorf("UserRepository.Create: %w", err)
    }
    return &u, nil
}

// BulkCreate — batch parameterized INSERT using pgx's CopyFrom:
func (r *UserRepository) BulkCreate(ctx context.Context, users []User) error {
    // pgx's CopyFrom uses the COPY protocol — fully parameterized,
    // SQL injection is structurally impossible at the protocol level:
    _, err := r.pool.CopyFrom(
        ctx,
        pgx.Identifier{"users"}, // table name via pgx.Identifier (safe)
        []string{"name", "email", "role"}, // column names (static, not from user)
        pgx.CopyFromSlice(len(users), func(i int) ([]interface{}, error) {
            return []interface{}{users[i].Name, users[i].Email, users[i].Role}, nil
        }),
    )
    if err != nil {
        return fmt.Errorf("UserRepository.BulkCreate: %w", err)
    }
    return nil
}
```

│   Safe:    sortCol = allowlist[userInput]; use sortCol in fmt.Sprintf│
│   Unsafe:  fmt.Sprintf("ORDER BY %s", userInput)                    │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘

QUICK INJECTION CHECKLIST — Code Review:
  □ Does every db.Query() / db.Exec() use placeholders ($1, $2, ?)?
  □ Is there ANY fmt.Sprintf() / string concatenation touching SQL?
  □ Are ORDER BY / GROUP BY / table names from allowlists only?
  □ Do GORM Raw() calls use ? placeholders?
  □ Do stored procedures use USING clause for dynamic SQL?
  □ Is data retrieved from DB treated as untrusted in new queries?
  □ Are integer/UUID params parsed to their types before use?
  □ Does the DB user have only minimum required privileges?
  □ Is pgaudit logging all writes (catches exploitation attempts)?

ATTACK DETECTION SIGNALS (from audit logs):
  • Queries with unusual UNION keywords from app service users
  • Queries referencing system tables (information_schema, pg_tables)
  • Queries with SLEEP() or pg_sleep() calls
  • Unusually large result sets from normally small queries
  • Failed queries with type mismatch errors (blind injection probing)
  • Queries at unusual times or from unusual IPs
  → Alert on these patterns in your SIEM / pgaudit log analysis.

---

_SQL injection is a solved problem. The solution has been known for twenty-five years and it is simple: use parameterised queries. Every other technique in this guide — input validation, stored procedures, ORMs, allowlists — is either built on top of this foundation or supplements it in specific scenarios. The fact that SQL injection remains in the OWASP Top 10 after a quarter century is not because the solution is unknown. It is because developers who understand the solution in theory still write string concatenation in practice, often under time pressure, with the belief that "this particular piece of input couldn't contain SQL."_

_It always can. Parameterize everything. Every time. Without exception._

_The discipline required is not technical — it is habitual. When you have parameterized queries so deeply embedded in your working patterns that reaching for string concatenation feels physically wrong, you have internalised this correctly. Until then, every code review should include one question: where is the SQL coming from, and is it built with parameters or with strings?_
