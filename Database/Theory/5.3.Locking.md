# Locking — A Deep Study Guide

> *"Concurrency without coordination is chaos. When two transactions reach for the same piece of data at the same moment, the database must decide: who goes first, who waits, and how to ensure that when both are done, the data is still correct. Locking is the database's answer to this coordination problem — a system of agreements and enforced turns that allows hundreds or thousands of transactions to interleave safely, each believing for a moment that it has the database to itself."*

A relational database is not a single-user system. At any given moment in a busy production environment, dozens, hundreds, or even thousands of transactions are executing simultaneously — reading, writing, updating, and deleting rows across the same tables. Without a mechanism to coordinate this simultaneous access, the results would be catastrophic: one transaction might read a value that another is in the middle of changing; two transactions might both try to update the same account balance and produce a result that reflects neither change correctly; or a transaction might delete a row that another was counting on for its join condition. Locking is the mechanism that prevents all of these disasters.

This chapter is a deep exploration of how databases use locks to maintain correctness under concurrency. We will study the different types of locks, the different granularities at which they are applied, the special case of advisory locks, and the most dangerous failure mode of the locking system — deadlock. We will then examine how to control lock waiting behavior with timeouts and how lock escalation affects system behavior under pressure.

## 1. Shared (Read) Lock vs Exclusive (Write) Lock

### The Two Fundamental Lock Modes

Before a transaction can access a piece of data — a row, a page, or a table — it must first acquire a **lock** on that resource. A lock is a formal declaration of intent: it tells every other concurrent transaction what this transaction plans to do with the resource, and it establishes the rules for who must wait for whom. At the heart of the locking system lie two fundamental lock modes that define the entire system's behavior: the **Shared Lock** and the **Exclusive Lock**.

A **Shared Lock** (also called a **Read Lock**, often abbreviated as **S Lock**) is acquired by a transaction that wants to *read* a resource. The name "shared" is precise and meaningful: multiple transactions can hold a shared lock on the same resource simultaneously. This makes intuitive sense — if Transaction A and Transaction B both want to read the same row, they can do so at the same time without any risk of corrupting the data. Reading is inherently safe to do concurrently; no transaction is changing anything, so no transaction can see anything incorrect. The fundamental rule is: **a shared lock is compatible with other shared locks**.

An **Exclusive Lock** (also called a **Write Lock**, abbreviated as **X Lock**) is acquired by a transaction that wants to *modify* a resource — whether through INSERT, UPDATE, or DELETE. The name "exclusive" is equally precise: only one transaction can hold an exclusive lock on a resource at any given time, and while that exclusive lock is held, no other transaction can hold either a shared lock or another exclusive lock on the same resource. The writing transaction needs a guarantee that no one else is reading the old value (which it is about to change) and no one else is writing (which would conflict). The fundamental rule is: **an exclusive lock is incompatible with all other locks**.

```
  LOCK COMPATIBILITY MATRIX

  The cell shows whether the REQUESTED lock (column) can be granted
  when the HELD lock (row) is already active on the resource:

            │ Requested: Shared (S) │ Requested: Exclusive (X)
  ──────────┼───────────────────────┼──────────────────────────
  Held: S   │   ✓  COMPATIBLE       │   ✗  WAIT (conflict)
            │   (many readers OK)   │   (writer must wait for all readers)
  ──────────┼───────────────────────┼──────────────────────────
  Held: X   │   ✗  WAIT (conflict)  │   ✗  WAIT (conflict)
            │   (reader must wait   │   (second writer must wait
            │    for writer to done)│    for first writer to finish)

  SUMMARY:
  S + S = OK   (multiple readers simultaneously)
  S + X = WAIT (writer waits for all readers, or reader waits for writer)
  X + X = WAIT (only one writer at a time)
  X + S = WAIT (same as S + X, order does not matter)
```

### How Locks Are Held and Released

In all major relational databases, locks acquired during a transaction are held until the transaction completes — either through a `COMMIT` or a `ROLLBACK`. This is called **two-phase locking (2PL)**: the "growing phase" where locks are acquired, and the "shrinking phase" where all locks are released at once when the transaction ends. Releasing locks before the transaction commits would allow other transactions to see intermediate, inconsistent states — which would violate isolation.

```
  LOCK LIFECYCLE THROUGH A TRANSACTION

  Transaction A: UPDATE accounts SET balance = balance - 100 WHERE id = 42;

  Time →
  ─────────────────────────────────────────────────────────────────────────
  T1: BEGIN
  T2: Database acquires Exclusive lock on row (id=42)
  T3: Read current balance (e.g., $500)
  T4: Write new balance ($400)
  T5: COMMIT
  T6: Exclusive lock on row (id=42) is RELEASED
  ─────────────────────────────────────────────────────────────────────────

  Concurrent Transaction B: SELECT balance FROM accounts WHERE id = 42;
  (runs between T2 and T6)

  Without isolation (no locking): B reads $400 during T4 (dirty read!) WRONG
  With S/X locking: B requests Shared lock on row (id=42)
                    → Exclusive lock already held by A
                    → B WAITS until T6 (A commits and releases X lock)
                    → B acquires S lock, reads $400 (the committed value)
                    ✓ CORRECT: B sees only committed data
```

### The Update Lock — Preventing Upgrade Deadlocks

Many databases introduce a third lock mode between Shared and Exclusive: the **Update Lock** (U Lock). The Update Lock solves a specific deadlock pattern that arises when a transaction intends to first read a resource and then modify it — a very common pattern in `SELECT ... FOR UPDATE` or `UPDATE ... WHERE ...` operations.

Without the Update Lock, two transactions following the pattern "acquire shared lock to read, then upgrade to exclusive to write" can deadlock each other: both acquire shared locks, both decide to upgrade, but neither can upgrade because the other's shared lock is blocking the upgrade. The Update Lock is compatible with shared locks (it can coexist with readers) but incompatible with other update locks (only one transaction at a time can be in the "intending to write" state). This breaks the upgrade deadlock by serializing the intent to upgrade.

```
  THE UPGRADE DEADLOCK (without Update Lock):

  Time  Transaction A                    Transaction B
  ─────────────────────────────────────────────────────────────
  T1    Acquire S-lock on row X          Acquire S-lock on row X
  T2    Read row X (S+S: both allowed)  Read row X (S+S: both allowed)
  T3    Try to upgrade S→X              Try to upgrade S→X
        "I need X, but B holds S"        "I need X, but A holds S"
  T4    A waits for B to release S      B waits for A to release S
        ← DEADLOCK: each waits for the other →

  WITH Update Lock (U Lock):

  Time  Transaction A                    Transaction B
  ─────────────────────────────────────────────────────────────
  T1    Acquire U-lock on row X         (runs concurrently)
        (U is compatible with S, but
         only one U-lock allowed)
  T2    Read row X                      Tries to acquire U-lock
                                        → WAIT (A holds U-lock)
  T3    Upgrade U→X (succeeds, no       (still waiting)
        competing U-lock exists)
  T4    Write row X
  T5    COMMIT, release X-lock          B acquires U-lock
  T6                                    B reads row X (sees committed value)
  T7                                    B upgrades U→X, writes, commits
  → NO DEADLOCK: serialized through the Update Lock
```

## 2. Row-Level vs Table-Level vs Page-Level Locking

### The Concept of Lock Granularity

Locks can be applied at different levels of the data hierarchy — from an individual row all the way up to an entire table (or even the entire database). This concept is called **lock granularity**. Choosing the right granularity involves a fundamental trade-off: finer-grained locks (row-level) allow more concurrent access because locking one row does not block access to other rows; coarser-grained locks (table-level) consume fewer system resources because a single lock covers many rows, but they block more concurrent operations. Understanding this trade-off is essential for designing systems that are both correct and performant under concurrency.

```
  LOCK GRANULARITY HIERARCHY

  Database Level
      │
      ▼
  Table Level      ← Coarsest practical granularity
      │                One lock protects ALL rows in the table.
      ▼                High contention. Rare in OLTP.
  Page Level
      │                One lock protects all rows on a disk page (~8KB).
      ▼                Middle ground. Used by SQL Server and older systems.
  Row Level        ← Finest practical granularity
                       One lock protects one row only.
                       Maximum concurrency. Used by PostgreSQL, InnoDB, Oracle.

  Trade-off:
  ┌──────────────────┬───────────────────────────┬───────────────────────┐
  │ Granularity      │ Concurrency               │ Lock Overhead         │
  ├──────────────────┼───────────────────────────┼───────────────────────┤
  │ Row-level        │ ★★★★★ Maximum             │ ★★★★★ Highest         │
  │                  │ (one lock per row)         │ (many lock objects)   │
  ├──────────────────┼───────────────────────────┼───────────────────────┤
  │ Page-level       │ ★★★☆☆ Medium              │ ★★★☆☆ Medium          │
  │                  │ (one lock per page ~80 rows│ (fewer lock objects)  │
  ├──────────────────┼───────────────────────────┼───────────────────────┤
  │ Table-level      │ ★☆☆☆☆ Minimum             │ ★☆☆☆☆ Lowest         │
  │                  │ (lock entire table)        │ (one lock object)     │
  └──────────────────┴───────────────────────────┴───────────────────────┘
```

### Row-Level Locking

**Row-level locking** is the granularity used by modern OLTP databases — PostgreSQL, MySQL InnoDB, Oracle, and SQL Server. A row-level lock protects a single row in a single table. When Transaction A updates row 42, only row 42 is locked. Transactions updating rows 43, 44, 100, or 1,000,000 in the same table proceed without any conflict or waiting. This fine-grained approach maximizes concurrency — thousands of transactions can simultaneously modify different rows of the same table.

In PostgreSQL specifically, row-level locking works in conjunction with the MVCC (Multi-Version Concurrency Control) model. When a transaction updates a row, it does not physically modify the row in place — it creates a new version of the row and marks the old version as dead. This means that **readers never block writers and writers never block readers** in PostgreSQL's model. The `xmin` and `xmax` fields on each tuple serve as the lock mechanism — a transaction reading the row sees the version that was committed before the reader's transaction started. Only concurrent writers compete with each other through row-level locks.

```
  ROW-LEVEL LOCKING IN ACTION

  orders table:
  ┌──────────┬─────────────┬────────────┬──────────┐
  │ order_id │ customer_id │ status     │ total    │
  ├──────────┼─────────────┼────────────┼──────────┤
  │     1001 │          42 │ pending    │   249.99 │  ← Txn A: UPDATE (X lock)
  │     1002 │          88 │ shipped    │    89.00 │  ← Txn B: UPDATE (X lock)
  │     1003 │          55 │ delivered  │   432.50 │  ← Txn C: SELECT (S lock)
  │     1004 │          42 │ pending    │   129.00 │  ← Txn D: UPDATE (waiting for Txn A? NO!)
  └──────────┴─────────────┴────────────┴──────────┘

  Row-level locking: Txn A locks ONLY row 1001.
  ✓ Txn B can update row 1002 simultaneously (different row)
  ✓ Txn C can read row 1003 simultaneously (readers don't block on MVCC)
  ✓ Txn D can update row 1004 simultaneously (different row)
  ✗ If Txn E tries to UPDATE row 1001, it must WAIT for Txn A.

  SELECT ... FOR UPDATE (explicit row-level exclusive lock):
  SELECT * FROM orders WHERE order_id = 1001 FOR UPDATE;
  → Acquires an explicit X lock on row 1001
  → Other transactions trying to SELECT FOR UPDATE or UPDATE row 1001 must wait
  → Read-only SELECTs (without FOR UPDATE) can still read old version (MVCC)

  SELECT ... FOR SHARE (explicit row-level shared lock):
  SELECT * FROM orders WHERE order_id = 1001 FOR SHARE;
  → Acquires an explicit S lock on row 1001
  → Multiple FOR SHARE transactions can coexist
  → FOR UPDATE and UPDATE transactions must wait
```

### Table-Level Locking

A **table-level lock** protects an entire table. While any individual transaction that acquires a table lock blocks access for all other transactions to every row in that table, table-level locks are used in specific and important situations — particularly for DDL (Data Definition Language) operations that structurally modify the table itself, or for bulk operations where it is more efficient to lock the entire table than to manage thousands of individual row locks.

PostgreSQL exposes its table-level lock modes explicitly through the `LOCK TABLE` command and through the implicit locks taken by various SQL operations. PostgreSQL's lock hierarchy is more nuanced than a simple "read/write" binary — it has 8 distinct table-level lock modes, each allowing different combinations of concurrent operations.

```
  POSTGRESQL TABLE-LEVEL LOCK MODES (ordered by strength)

  ┌────────────────────────────────┬────────────────────────────────────┐
  │ Lock Mode                      │ Acquired By                        │
  ├────────────────────────────────┼────────────────────────────────────┤
  │ ACCESS SHARE                   │ SELECT (lightest lock)             │
  │ (compatible with almost all)   │ Does not block anything except     │
  │                                │ ACCESS EXCLUSIVE (DDL operations)  │
  ├────────────────────────────────┼────────────────────────────────────┤
  │ ROW SHARE                      │ SELECT FOR UPDATE, SELECT FOR SHARE│
  ├────────────────────────────────┼────────────────────────────────────┤
  │ ROW EXCLUSIVE                  │ INSERT, UPDATE, DELETE             │
  │                                │ (allows concurrent reads & writes  │
  │                                │  on different rows)                │
  ├────────────────────────────────┼────────────────────────────────────┤
  │ SHARE UPDATE EXCLUSIVE         │ VACUUM, ANALYZE, CREATE INDEX      │
  │                                │ CONCURRENTLY                       │
  ├────────────────────────────────┼────────────────────────────────────┤
  │ SHARE                          │ CREATE INDEX (non-concurrent)      │
  │                                │ Blocks all writes during indexing  │
  ├────────────────────────────────┼────────────────────────────────────┤
  │ SHARE ROW EXCLUSIVE            │ CREATE TRIGGER, some ALTER TABLE   │
  ├────────────────────────────────┼────────────────────────────────────┤
  │ EXCLUSIVE                      │ REFRESH MATERIALIZED VIEW          │
  │                                │ (with CONCURRENTLY)                │
  ├────────────────────────────────┼────────────────────────────────────┤
  │ ACCESS EXCLUSIVE               │ DROP TABLE, TRUNCATE, ALTER TABLE  │
  │ (strongest, blocks EVERYTHING) │ (non-concurrent), VACUUM FULL,     │
  │                                │ LOCK TABLE (explicit)              │
  └────────────────────────────────┴────────────────────────────────────┘

  WHY THIS MATTERS:
  ALTER TABLE orders ADD COLUMN notes TEXT;
  → Acquires ACCESS EXCLUSIVE lock on 'orders' table
  → Blocks ALL concurrent reads AND writes until ALTER completes!
  → On a table with millions of rows, this can cause minutes of downtime
  → Solution: ALTER TABLE ... ADD COLUMN with DEFAULT in PostgreSQL 11+
    or use tools like pg_repack, online schema change tools
```

### Page-Level Locking

**Page-level locking** sits between row and table level — it locks an entire disk page, which typically holds 8 KB of data and perhaps 80-200 rows depending on row size. This granularity is primarily used by **SQL Server** (in certain situations) and was the dominant approach in older database systems before row-level locking was efficiently implemented.

PostgreSQL does use brief page-level locks internally during index operations (pin locks on buffer pages), but these are infrastructure-level mechanisms not directly visible to application developers. For practical application design, page-level locking is mostly a historical and SQL Server-specific concept.

```
  PAGE-LEVEL LOCKING (SQL Server example)

  Table pages on disk:
  ┌──────────────────────────────────────────────────────────────┐
  │ Page 1 (rows 1-80):   [row1][row2][row3]...[row80]           │
  │ Page 2 (rows 81-160): [row81][row82]...[row160]              │
  │ Page 3 (rows 161-240):[row161]...[row240]                    │
  └──────────────────────────────────────────────────────────────┘

  Transaction A: UPDATE where id = 5 (page 1)
  → Acquires page-level lock on Page 1
  → Blocks access to rows 1-80 for ALL other transactions
  → Transaction B wanting to update row 42 must WAIT even though row 42
    is completely different from row 5!

  Row-level lock comparison:
  → Transaction A: X lock on row 5 only
  → Transaction B: X lock on row 42 → NO CONFLICT, proceeds immediately

  Page-level locking is coarser → more false conflicts → less concurrency
  But: fewer lock objects to manage → lower memory overhead per transaction
```

### Intent Locks — The Glue Between Granularities

A critical mechanism that makes multi-granularity locking work correctly is the **Intent Lock**. Consider the following problem: if Transaction A holds a row-level exclusive lock on row 42, and Transaction B requests a table-level exclusive lock (e.g., for DDL), how does Transaction B know it must wait? It cannot check every row in a million-row table to see if any row-level locks exist. That would be impossibly expensive.

The solution is that when a transaction acquires a row-level lock, it also acquires an **Intent Exclusive (IX)** lock on the table containing that row. This intent lock signals to any transaction attempting a table-level lock: "Someone inside this table has a row-level lock. Check for conflicts before proceeding." The table-level lock request checks only the table's intent lock — a single lookup — rather than scanning every row.

## 3. Advisory Locks

### Application-Controlled Locks Beyond the Data Model

The shared and exclusive locks we have studied so far are automatically managed by the database engine — acquired and released as part of regular SQL operations. But there is a category of coordination problems that falls outside the data model entirely: situations where you need to ensure that only one process at a time executes a specific piece of application code, not because it is modifying a specific row, but because the work itself must be serialized.

**Advisory Locks** (called Application Locks in SQL Server) are user-defined locks that the application acquires and releases explicitly. They have no connection to any specific table, row, or index. They are simply a named, globally-recognized lock within a database session or transaction, identified by a programmer-chosen integer or string key. The database enforces their mutual exclusion, but it is the application that decides what the lock key means and when to acquire or release it.

Advisory locks solve coordination problems like: "Only one worker process should run the nightly email digest job at a time, even if multiple servers are running workers." Or: "While performing a multi-step financial reconciliation that involves reading and writing across 10 different tables, prevent any other reconciliation process from running concurrently." These are not row-level locking problems — they are application-level coordination problems that happen to be solvable using the database as a coordination service.

### Session-Level vs Transaction-Level Advisory Locks

PostgreSQL provides two variants of advisory locks with different lifetime semantics.

**Session-level advisory locks** are held for the entire duration of the database session, independent of transaction boundaries. They are not released when a transaction commits or rolls back. They must be explicitly released with the corresponding unlock function. This makes them suitable for long-running background jobs where the lock should persist across multiple transactions.

**Transaction-level advisory locks** are automatically released when the transaction that acquired them commits or rolls back — just like regular data locks. This makes them simpler to manage (no risk of forgetting to release) and suitable for within-transaction coordination.

```
  ADVISORY LOCK USAGE PATTERNS

  ─────────────────────────────────────────────────────────────────
  PATTERN 1: Ensuring only one cron job runs at a time
  ─────────────────────────────────────────────────────────────────

  Job Process 1 (first to run):
  -- Try to acquire advisory lock with key 12345 (session-level)
  SELECT pg_try_advisory_lock(12345);
  -- Returns: TRUE (lock acquired successfully)
  -- Proceed with the job...
  -- When job is done:
  SELECT pg_advisory_unlock(12345);

  Job Process 2 (starts while Process 1 is still running):
  SELECT pg_try_advisory_lock(12345);
  -- Returns: FALSE (lock is held by Process 1)
  -- Process 2 knows: another instance is already running → EXIT

  -- If you want to WAIT instead of returning immediately:
  SELECT pg_advisory_lock(12345);  -- blocks until lock is available
  -- Use pg_try_advisory_lock for "skip if running", pg_advisory_lock for "queue up"

  ─────────────────────────────────────────────────────────────────
  PATTERN 2: Transaction-level advisory lock (auto-released on commit/rollback)
  ─────────────────────────────────────────────────────────────────

  BEGIN;
  SELECT pg_advisory_xact_lock(42);  -- Acquired for this transaction only
  -- Do work within the transaction...
  COMMIT;  -- Lock is automatically released here
  -- No need to manually call pg_advisory_unlock!

  ─────────────────────────────────────────────────────────────────
  PATTERN 3: Per-entity advisory lock (lock on a specific user's account)
  ─────────────────────────────────────────────────────────────────

  -- Prevent concurrent modification of the same user's financial records
  -- Use the user_id as the lock key (must be an integer or pair of integers)

  -- In application code (pseudo-code):
  -- user_id = 42
  -- SELECT pg_try_advisory_xact_lock(42);
  -- If TRUE: proceed with financial operation
  -- If FALSE: another process is working on user 42 → retry or error

  SELECT pg_advisory_xact_lock_shared(user_id);  -- Shared variant (multiple readers OK)
  SELECT pg_advisory_xact_lock(user_id);          -- Exclusive (only one at a time)

  ─────────────────────────────────────────────────────────────────
  PATTERN 4: Using text key (hash to integer automatically)
  ─────────────────────────────────────────────────────────────────

  -- Lock using a descriptive string name (hashed to bigint internally)
  SELECT pg_try_advisory_lock(hashtext('nightly_report_job'));
  -- Returns: TRUE or FALSE based on lock availability

  ─────────────────────────────────────────────────────────────────
  INSPECT current advisory locks:
  ─────────────────────────────────────────────────────────────────

  SELECT pid, locktype, objid, mode, granted
  FROM pg_locks
  WHERE locktype = 'advisory';
  -- Shows all currently held advisory locks across all sessions
```

### Advisory Locks vs Application Mutex (Redis, etc.)

Advisory locks have a significant advantage over application-level mutex solutions like Redis or ZooKeeper: they are **scoped to the database connection**. If the application process crashes or the connection drops, the database automatically detects the lost session and releases all session-level advisory locks held by that session. There is no risk of a "zombie lock" where a process dies while holding a lock, permanently blocking other processes. For coordination scenarios where the work being coordinated is primarily database work, advisory locks are often simpler, faster, and more reliable than external distributed locks.

## 4. Deadlock — Detection and Prevention

### When Transactions Wait for Each Other

A **deadlock** is a situation in which two or more transactions are each waiting for the other to release a lock, creating a circular dependency from which no transaction can escape without outside intervention. No transaction involved in a deadlock can proceed — each is blocked waiting for a resource held by another transaction in the cycle. Without detection and resolution, all transactions in a deadlock would wait forever.

Deadlocks are not bugs in the database — they are an inherent consequence of having multiple concurrent transactions each acquiring locks in potentially different orders. The database does not prevent them; it detects them and resolves them.

```
  DEADLOCK ILLUSTRATION

  Two transactions, two rows:

  Time  Transaction A                         Transaction B
  ──────────────────────────────────────────────────────────────────────
  T1    BEGIN                                 BEGIN

  T2    UPDATE accounts SET balance=          (thinking/doing other work)
        balance-100 WHERE id=1;
        → Acquires X lock on Row 1

  T3    (doing other work)                    UPDATE accounts SET balance=
                                              balance+100 WHERE id=2;
                                              → Acquires X lock on Row 2

  T4    UPDATE accounts SET balance=          (still working)
        balance+100 WHERE id=2;
        → Wants X lock on Row 2
        → B holds X lock on Row 2
        → A WAITS for B

  T5    (A is waiting)                        UPDATE accounts SET balance=
                                              balance-100 WHERE id=1;
                                              → Wants X lock on Row 1
                                              → A holds X lock on Row 1
                                              → B WAITS for A

  T6    ← DEADLOCK DETECTED →
        A waits for B  (for Row 2)
        B waits for A  (for Row 1)
        Circular dependency → neither can proceed

  Wait-for graph:
  A ──── waits for ───→ B
  B ──── waits for ───→ A
  (A cycle exists → DEADLOCK)

  For 3 transactions:
  A → B → C → A (all waiting in a circle)
```

### Deadlock Detection

PostgreSQL detects deadlocks by periodically examining the **wait-for graph** — a directed graph where each node is a transaction and each edge represents "this transaction is waiting for a lock held by that transaction." A deadlock exists if and only if this graph contains a **cycle**. PostgreSQL runs its deadlock detection algorithm whenever a lock wait exceeds the `deadlock_timeout` parameter (default: 1 second). This means a deadlock is not detected instantly — the waiting transaction waits for at least `deadlock_timeout` milliseconds before the database checks whether it is part of a deadlock.

When a deadlock is detected, PostgreSQL must choose one transaction to **abort** — the **victim**. The victim's transaction is rolled back, its locks are released, and the other transaction(s) in the deadlock are free to proceed. PostgreSQL's choice of victim is based on the cost of rolling back: it generally picks the transaction that will be cheapest to roll back (the one that has done the least work so far).

```
  DEADLOCK DETECTION AND RESOLUTION TIMELINE

  T0: Transaction A acquires X lock on Row 1
  T1: Transaction B acquires X lock on Row 2
  T2: Transaction A requests X lock on Row 2 → WAITS
  T3: Transaction B requests X lock on Row 1 → WAITS
  T4: deadlock_timeout (1 second) elapses
  T5: Deadlock detector runs → builds wait-for graph → finds cycle
  T6: Chooses Transaction B as victim (less work done)
  T7: Transaction B receives error:
      "ERROR: deadlock detected
       DETAIL: Process 12345 waits for ShareLock on transaction 67890;
               blocked by process 54321.
               Process 54321 waits for ShareLock on transaction 12345;
               blocked by process 12345.
       HINT: See server log for query details."
  T8: Transaction B is rolled back automatically
  T9: Transaction B's X lock on Row 2 is released
  T10: Transaction A acquires X lock on Row 2 → proceeds
  T11: Transaction A completes and commits

  APPLICATION RESPONSIBILITY:
  When your application receives a deadlock error,
  it MUST retry the entire transaction from scratch.
  The deadlock error is not a permanent failure —
  it is a signal to retry.
```

### Deadlock Prevention Strategies

While the database handles deadlock detection and resolution automatically, deadlocks are expensive — they cause at least one transaction to be rolled back and retried, introducing latency and wasted work. In high-throughput systems, frequent deadlocks can significantly degrade performance. The best approach is to design your application to minimize or eliminate deadlocks rather than simply relying on detection.

The single most effective strategy is **consistent lock ordering**: ensure that all transactions that need to lock multiple rows or tables always lock them in the same global order. If all transactions that update both `accounts(id=1)` and `accounts(id=2)` always lock the lower ID first, the deadlock scenario we illustrated is impossible — both transactions would try to lock Row 1 first, one would wait while the other proceeds, and there would be no circular dependency.

```
  DEADLOCK PREVENTION STRATEGIES

  ─────────────────────────────────────────────────────────────────
  STRATEGY 1: Consistent lock ordering (most important)
  ─────────────────────────────────────────────────────────────────

  DEADLOCK-PRONE (each transaction locks in different order):
  Transaction A: Lock row 1, then lock row 2
  Transaction B: Lock row 2, then lock row 1  ← Different order!

  DEADLOCK-FREE (always lock in ascending ID order):
  Transaction A: Lock row 1 (lower ID first), then lock row 2
  Transaction B: Lock row 1 (lower ID first), then lock row 2
  → B waits for A to release row 1 → no circular dependency possible

  In practice:
  -- Always update multiple rows in a consistent order:
  UPDATE accounts SET balance=balance-100 WHERE id = LEAST(1,2)   RETURNING id;
  -- Then:
  UPDATE accounts SET balance=balance+100 WHERE id = GREATEST(1,2) RETURNING id;

  ─────────────────────────────────────────────────────────────────
  STRATEGY 2: Lock all needed rows upfront (SELECT FOR UPDATE)
  ─────────────────────────────────────────────────────────────────

  -- Acquire all needed row locks at the start of the transaction
  -- before doing any actual work:
  BEGIN;
  SELECT id FROM accounts
  WHERE id IN (1, 2)
  ORDER BY id                -- Consistent order!
  FOR UPDATE;                -- Lock both rows immediately
  -- Now do the work:
  UPDATE accounts SET balance=balance-100 WHERE id=1;
  UPDATE accounts SET balance=balance+100 WHERE id=2;
  COMMIT;
  -- By locking both rows at the start in consistent order,
  -- you cannot get into a partial-lock state that enables deadlocks.

  ─────────────────────────────────────────────────────────────────
  STRATEGY 3: Keep transactions short
  ─────────────────────────────────────────────────────────────────

  The longer a transaction holds locks, the longer the window during
  which another transaction can arrive and create a deadlock situation.
  Move all non-database work (API calls, file I/O, user input) OUTSIDE
  of transaction boundaries. A transaction should:
  1. Read all needed data.
  2. Process it (in memory, outside the transaction if possible).
  3. Write results.
  4. Commit immediately.

  ─────────────────────────────────────────────────────────────────
  STRATEGY 4: SELECT FOR UPDATE SKIP LOCKED (non-blocking work queues)
  ─────────────────────────────────────────────────────────────────

  -- Multiple workers processing a job queue without deadlocking:
  BEGIN;
  SELECT * FROM jobs
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED;  -- Skip any row already locked by another worker
  -- If row found: process it, UPDATE status='done', COMMIT
  -- If no row found: nothing to do, ROLLBACK
  -- SKIP LOCKED prevents deadlocks in queue processing entirely.
```

## 5. Lock Wait Timeouts

### Bounding the Wait to Prevent Cascade Failures

When a transaction requests a lock that is currently held by another transaction, it enters a **wait queue** — it suspends execution and waits until the lock becomes available. In normal operation, this wait is brief (milliseconds), because the blocking transaction finishes its work and releases the lock quickly. But in abnormal situations — a slow transaction, a long-running ETL job that forgot to release locks, or an application bug that holds a lock indefinitely — a waiting transaction can be stuck for seconds, minutes, or even hours.

This lock wait problem becomes catastrophic under concurrency: if one slow transaction holds a lock, all transactions that need that lock begin to queue up. Their requests pile up. The connection pool fills with waiting connections. The application's response time increases. New requests continue to arrive but cannot proceed. Within seconds or minutes, the entire application can become unresponsive — not because of the slow transaction itself, but because of the cascade of waiting transactions blocking behind it. This is a **lock wait cascade**, and it is one of the most common root causes of production database incidents.

**Lock wait timeouts** are the circuit breaker for this problem. They set a maximum amount of time a transaction is willing to wait for a lock before giving up and raising an error. Rather than waiting indefinitely, the waiting transaction fails fast, allowing the application to handle the error gracefully — logging it, retrying, or surfacing an appropriate error to the user.

```
  LOCK WAIT CASCADE: Why Timeouts Are Critical

  Slow Transaction (holds X lock on table 'reports' for 3 minutes due to bug):
  ─────────────────────────────────────────────────────────────────────────────
  Without timeouts:

  T0: Slow Txn holds X lock on 'reports'
  T5s: Request 1 arrives, needs lock → WAITS (connection occupied)
  T10s: Request 2 arrives → WAITS
  T30s: Requests 3-50 arrive → ALL WAITING
  T60s: Connection pool (50 connections) FULL
  T65s: Request 51 arrives → "Connection pool exhausted" error
  T70s: ALL new requests fail immediately → Application DOWN
  T3m: Slow Txn finishes, lock released
  T3m+: 50 waiting transactions rush forward → spike load → possible crash

  With lock_timeout = 5s:

  T0: Slow Txn holds X lock
  T5s: Request 1 arrives, waits 5 seconds → TIMEOUT ERROR → connection released
  T10s: Request 2 → TIMEOUT → released
  ...
  All requests fail fast with a meaningful error.
  Connection pool stays available for non-blocking requests.
  Application continues serving other routes.
  Slow Txn finishes → remaining requests succeed.
  CONTROLLED DEGRADATION instead of total failure.
```

### lock_timeout vs statement_timeout: Understanding Both

PostgreSQL provides two distinct timeout parameters that are often confused with each other. Understanding the difference is important.

`lock_timeout` sets the maximum time a statement will wait to acquire a lock. If the lock cannot be acquired within this time, the **statement** (not the transaction) fails with an error. The transaction is still open; the application can catch the error and decide what to do.

`statement_timeout` sets the maximum total execution time for any single statement, including any lock wait time. If the statement runs for longer than this duration (from the moment it starts, including time spent waiting for locks), it is cancelled.

`idle_in_transaction_session_timeout` sets the maximum time a session can remain in a transaction without executing any statement. This catches the dangerous pattern of an application that opens a transaction and then crashes or hangs before committing, holding locks indefinitely.

```sql
-- ─────────────────────────────────────────────────────────────────
-- lock_timeout: Fail fast if lock cannot be acquired
-- ─────────────────────────────────────────────────────────────────
-- Set for the current session:
SET lock_timeout = '5s';    -- Fail if lock wait exceeds 5 seconds
SET lock_timeout = '500ms'; -- Fail if lock wait exceeds 500 milliseconds
SET lock_timeout = 0;       -- No timeout (wait forever) — DEFAULT, dangerous!

-- Set globally (postgresql.conf):
-- lock_timeout = '10s'

-- Example usage: Non-blocking DDL attempt
SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN notes TEXT;
-- If other transactions are using the orders table:
-- After 3 seconds → ERROR: "canceling statement due to lock timeout"
-- → Schedule for maintenance window or use online schema change tool

-- ─────────────────────────────────────────────────────────────────
-- statement_timeout: Limit total query execution time
-- ─────────────────────────────────────────────────────────────────
SET statement_timeout = '30s'; -- Kill any statement running longer than 30s
-- Protects against: accidental full-table scans, runaway reports,
--                   forgotten queries holding locks for hours

-- ─────────────────────────────────────────────────────────────────
-- idle_in_transaction_session_timeout: Kill zombie transactions
-- ─────────────────────────────────────────────────────────────────
-- Set in postgresql.conf:
-- idle_in_transaction_session_timeout = '5min'
-- If a session is in a transaction (BEGIN issued) but has not
-- executed a statement in 5 minutes → connection is terminated
-- → Prevents locks held by crashed/hung application processes from
--   blocking the database indefinitely

-- ─────────────────────────────────────────────────────────────────
-- PRACTICAL: Per-transaction timeout for critical operations
-- ─────────────────────────────────────────────────────────────────
BEGIN;
SET LOCAL lock_timeout = '2s';      -- Only for this transaction
SET LOCAL statement_timeout = '10s'; -- Only for this transaction
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
-- If row 42 is locked: wait at most 2s, then fail
COMMIT;

-- Monitoring current lock waits:
SELECT
    pid,
    now() - pg_stat_activity.query_start AS wait_duration,
    query,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE state = 'active'
  AND wait_event_type = 'Lock'
ORDER BY wait_duration DESC;
-- Shows: which queries are waiting for locks, how long, and what they are waiting on
```

### Choosing Good Timeout Values

The right timeout values depend on your application's requirements and SLA. OLTP applications serving end-user HTTP requests typically should not wait more than 1-5 seconds for any lock. Background batch jobs might tolerate 30-60 seconds. DDL operations should use the shortest lock_timeout that still allows the operation to succeed during a low-traffic window. The general principle is: **fail fast and retry rather than fail slowly and cascade**.

## 6. Lock Escalation

### When Fine-Grained Locks Become Too Expensive

**Lock escalation** is the process by which a database engine automatically converts many fine-grained locks (row-level or page-level) into a single coarser-grained lock (table-level) when the number of fine-grained locks exceeds a threshold. It is a memory management strategy: maintaining a large number of individual lock objects consumes significant memory in the lock manager's data structures. When a single transaction acquires locks on thousands or millions of rows, the overhead of tracking each individual lock becomes prohibitive — it can exhaust the lock manager's memory budget and slow down the system for all concurrent transactions.

**SQL Server** and **Sybase** implement explicit lock escalation. By default in SQL Server, when a single transaction has acquired more than 5,000 lock objects on a single table, the lock manager triggers escalation: it releases all those row-level or page-level locks and replaces them with a single table-level exclusive lock. The transaction still protects its data — it just does so with a coarser lock that also inadvertently blocks every other transaction from accessing any part of the table.

**PostgreSQL** and **Oracle** do not perform automatic lock escalation in the traditional sense. Instead, they rely on their MVCC architecture to reduce the need for many simultaneous row-level read locks (readers never acquire locks in MVCC — they read the appropriate version without locking). However, operations like `VACUUM FULL`, `TRUNCATE`, and `DROP TABLE` do acquire table-level locks explicitly.

```
  LOCK ESCALATION IN SQL SERVER

  Transaction processes 5,000+ rows in a single table:

  Before escalation:
  ┌─────────────────────────────────────────────────────────────────┐
  │ Lock Manager Memory:                                            │
  │ [X-lock row 1] [X-lock row 2] [X-lock row 3] ... [X-lock 5001] │
  │ Memory: 5001 lock objects × ~64 bytes = ~320 KB per transaction │
  │ With 100 concurrent transactions: 32 MB just for lock objects!  │
  └─────────────────────────────────────────────────────────────────┘

  Lock escalation triggers (threshold exceeded):
  ┌─────────────────────────────────────────────────────────────────┐
  │ Release: 5001 individual row-level X-locks                      │
  │ Acquire: 1 table-level X-lock (replaces all)                    │
  │ Memory:  1 lock object × 64 bytes = 64 bytes                    │
  └─────────────────────────────────────────────────────────────────┘

  CONSEQUENCE:
  Before: Only the 5001 specific rows are locked. Other rows accessible.
  After:  ENTIRE TABLE is locked. No other transaction can read OR write
          any row — even rows the escalating transaction never touched!

  ─────────────────────────────────────────────────────────────────
  IMPACT DIAGRAM:

  [Concurrent Transaction reads row 10,000 — row never touched by escalating txn]
  Before escalation: ✓ Reads freely (row is unlocked)
  After escalation:  ✗ BLOCKED by table-level X-lock!
  ─────────────────────────────────────────────────────────────────
```

### Problems Caused by Lock Escalation

Lock escalation is a double-edged sword. It solves the memory problem but creates a concurrency problem: a table-level lock blocks every concurrent read and write on the entire table, turning a potentially minor contention scenario into a complete table blockage. In a high-concurrency OLTP system, unexpected lock escalation can cause widespread timeouts and failures even though the individual row-level operation that triggered the escalation was perfectly routine.

The most dangerous scenario is an escalation that occurs **mid-transaction** in a busy system. The transaction has been running for a while, has locked thousands of rows, triggers escalation, and suddenly holds a table-level exclusive lock. Every concurrent transaction that needs the table is now waiting. The queue of blocked transactions grows until the escalating transaction commits and releases the table lock — potentially leaving hundreds of waiting requests in its wake.

```
  PREVENTING UNWANTED LOCK ESCALATION

  ─────────────────────────────────────────────────────────────────
  APPROACH 1: Process in batches (most effective)
  ─────────────────────────────────────────────────────────────────
  -- Instead of one giant UPDATE that locks millions of rows:
  -- BAD:
  UPDATE orders SET status = 'archived' WHERE created_at < '2023-01-01';
  -- This might lock 2,000,000 rows → lock escalation → table blocked!

  -- GOOD: Process in small batches
  DO $$
  DECLARE
    batch_size INT := 1000;
    rows_updated INT;
  BEGIN
    LOOP
      UPDATE orders
      SET status = 'archived'
      WHERE id IN (
          SELECT id FROM orders
          WHERE status != 'archived'
            AND created_at < '2023-01-01'
          LIMIT batch_size
          FOR UPDATE SKIP LOCKED  -- Skip rows locked by others
      );
      GET DIAGNOSTICS rows_updated = ROW_COUNT;
      EXIT WHEN rows_updated = 0;  -- Done when no more rows to update
      PERFORM pg_sleep(0.1);        -- Brief pause between batches
    END LOOP;
  END $$;
  -- Each batch: max 1000 row locks → well below escalation threshold
  -- Pauses between batches allow concurrent transactions to proceed

  ─────────────────────────────────────────────────────────────────
  APPROACH 2: Disable escalation for a specific table (SQL Server)
  ─────────────────────────────────────────────────────────────────
  -- In SQL Server, you can disable lock escalation per-table:
  ALTER TABLE orders SET (LOCK_ESCALATION = DISABLE);
  -- Use only when you've measured that escalation is causing problems.
  -- Trade-off: higher memory consumption for lock objects.

  -- Or use table-level escalation only (not row→page→table chain):
  ALTER TABLE orders SET (LOCK_ESCALATION = TABLE);

  ─────────────────────────────────────────────────────────────────
  APPROACH 3: Use TABLOCK or TABLOCKX hints explicitly (SQL Server)
  ─────────────────────────────────────────────────────────────────
  -- If you KNOW you will process the entire table, explicitly request
  -- a table lock from the start, rather than letting escalation happen
  -- mid-transaction unpredictably:
  UPDATE orders WITH (TABLOCKX)
  SET status = 'archived'
  WHERE created_at < '2023-01-01';
  -- Known lock scope from the beginning → predictable blocking behavior
  -- Better than unpredictable mid-transaction escalation

  ─────────────────────────────────────────────────────────────────
  MONITORING lock escalation events (SQL Server):
  ─────────────────────────────────────────────────────────────────
  -- SQL Server Extended Events to track escalations:
  -- CREATE EVENT SESSION [LockEscalation] ON SERVER
  -- ADD EVENT sqlserver.lock_escalation
  -- Watch for: tables frequently escalating → candidates for batch processing
```

## Summary: The Complete Locking Picture

Locking is the invisible coordination layer that makes concurrent database access safe. Every query, every transaction, every schema change you execute is participating in this system — acquiring locks, waiting for locks, and releasing locks in a carefully orchestrated dance that allows many concurrent actors to share the same data without corrupting it.

```
  COMPLETE LOCKING REFERENCE

  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Concept             │ Key Points                                   │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Shared Lock (S)     │ Multiple readers can coexist.                │
  │                     │ Incompatible with Exclusive locks.           │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Exclusive Lock (X)  │ Only one writer at a time.                   │
  │                     │ Incompatible with ALL other locks.           │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Row-Level Lock      │ Finest granularity. Maximum concurrency.     │
  │                     │ Used by PostgreSQL, InnoDB, Oracle.          │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Table-Level Lock    │ DDL operations require ACCESS EXCLUSIVE.     │
  │                     │ Blocks everything. Use CONCURRENTLY options. │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Advisory Lock       │ Application-controlled. Key-based.           │
  │                     │ Session or transaction scope.                │
  │                     │ Auto-released on session drop (crash-safe).  │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Deadlock            │ Circular lock dependency. DB detects & kills │
  │                     │ one victim. App must retry.                  │
  │                     │ Prevention: consistent ordering, short txns. │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Lock Timeout        │ lock_timeout: max wait for a lock.           │
  │                     │ statement_timeout: max total query time.     │
  │                     │ idle_in_transaction: kills zombie txns.      │
  │                     │ Set all three in production. Fail fast.      │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ Lock Escalation     │ SQL Server: row→table when >5000 locks.      │
  │                     │ Causes surprise table locks. Use batches.    │
  │                     │ PostgreSQL: no auto-escalation (MVCC).       │
  └─────────────────────┴──────────────────────────────────────────────┘

  PRODUCTION HEALTH CHECKLIST:
  [ ] Set lock_timeout on all application connections (2-10s)
  [ ] Set statement_timeout on all connections (10-60s)
  [ ] Set idle_in_transaction_session_timeout in postgresql.conf (5min)
  [ ] Ensure consistent lock ordering in all multi-row transactions
  [ ] Monitor pg_stat_activity for long lock waits
  [ ] Process bulk updates in batches to avoid escalation
  [ ] Use SELECT FOR UPDATE SKIP LOCKED for queue processing
  [ ] Add retry logic in application for deadlock errors (sqlstate 40P01)
  [ ] Run EXPLAIN before DDL on large tables to estimate lock duration
```

Understanding locking at this depth is what separates engineers who react to production incidents from those who prevent them. The locks are always there, working invisibly. When they work well, you never notice them. When they work badly — when a deadlock cascade freezes your application at 2 AM — the engineer who understands what is happening can diagnose the cause in minutes, not hours. This chapter has given you that understanding.
