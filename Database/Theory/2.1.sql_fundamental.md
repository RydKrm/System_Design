## 1. What is SQL and Why Does It Matter?

Imagine you own a library with millions of books. You need to find all books written after 1990 by authors from France. Without a system, you would have to walk through every single shelf, pick up every single book, look at the cover, and decide whether to keep or discard it. That is precisely what a computer would do without SQL — it would be chaotic, slow, and error-prone.

SQL, which stands for **Structured Query Language**, is the standardized language that allows you to talk to a **Relational Database Management System (RDBMS)** — systems like PostgreSQL, MySQL, Microsoft SQL Server, Oracle, and SQLite. It was first developed by IBM in the early 1970s based on the relational model proposed by Dr. Edgar F. Codd, and it became an ANSI (American National Standards Institute) standard in 1986.

A relational database stores data in the form of **tables** — much like spreadsheets you see in Microsoft Excel — where each table is a collection of **rows** (records) and **columns** (attributes). What makes relational databases powerful is that these tables can be **related** to one another through keys, allowing you to represent complex, real-world information in a structured, consistent, and efficient manner.

SQL is the tool that lets you define those tables, pour data into them, retrieve data from them, modify existing data, and most importantly, control the entire lifecycle of your data — all using human-readable sentences that are surprisingly close to plain English.

## 2. The Architecture of SQL — Four Pillars

SQL as a language is divided into four distinct sub-languages, each serving a specific purpose. Think of SQL as a house: DDL builds the structure of the house, DML fills the house with furniture, DQL lets you find and look at any piece of furniture, and TCL ensures that if something goes wrong while you're rearranging furniture, you can restore everything to its previous state.

```
+------------------------------------------------------------------+
|                          SQL Language                            |
+------------------+------------------+------------------+---------+
|       DDL        |       DML        |       DQL        |   TCL   |
|   (Structure)    |    (Content)     |    (Reading)     | (Ctrl)  |
+------------------+------------------+------------------+---------+
|  CREATE          |  INSERT          |  SELECT          |  BEGIN  |
|  ALTER           |  UPDATE          |                  |  COMMIT |
|  DROP            |  DELETE          |                  |  ROLLBK |
|  TRUNCATE        |  MERGE/UPSERT    |                  |  SAVEPT |
+------------------+------------------+------------------+---------+
```

Each of these four pillars is responsible for a completely different dimension of working with data. Together, they form a complete and self-sufficient system for managing information at scale.

## 3. DDL — Data Definition Language

Data Definition Language is the foundational layer of SQL. Before you can store a single piece of data, you must first define *where* and *how* that data will live. DDL is the language of architects — it deals with creating the schema, altering the structure of existing objects, and removing structures when they are no longer needed.

The most important characteristic of DDL statements is that they are **auto-committed** in most database systems. This means that once you execute a DDL command, the change is permanent and cannot be rolled back using standard transaction controls (with some exceptions in PostgreSQL and certain other systems). This is why DDL commands must be used with great care in production environments.

---

### 3.1 CREATE

The `CREATE` statement is the very first thing you will ever write in a new database. It is responsible for bringing new database objects into existence. The most common object you will create is a **table**, but `CREATE` can also be used to build **databases**, **views**, **indexes**, **sequences**, **schemas**, **functions**, and **stored procedures**.

When you define a table, you are essentially writing a contract with the database. You are saying: "Every row in this table must have these specific columns, and each column will hold data of this specific type, subject to these specific rules." Those rules are called **constraints**.

Let us build a small but realistic example. Imagine we are building a system for a university. We need to store information about students.

```sql
-- First, we create the database itself
CREATE DATABASE university_db;

-- Now we switch to it (syntax varies by RDBMS)
USE university_db;  -- MySQL / SQL Server
-- \c university_db -- PostgreSQL

-- Now we create the students table
CREATE TABLE students (
    student_id    INT           NOT NULL AUTO_INCREMENT,
    first_name    VARCHAR(50)   NOT NULL,
    last_name     VARCHAR(50)   NOT NULL,
    email         VARCHAR(100)  NOT NULL UNIQUE,
    date_of_birth DATE          NOT NULL,
    enrollment_date DATE        NOT NULL DEFAULT CURRENT_DATE,
    gpa           DECIMAL(3, 2) CHECK (gpa >= 0.0 AND gpa <= 4.0),
    is_active     BOOLEAN       NOT NULL DEFAULT TRUE,
    department_id INT,

    CONSTRAINT pk_students PRIMARY KEY (student_id),
    CONSTRAINT fk_department
        FOREIGN KEY (department_id)
        REFERENCES departments(department_id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);
```

Let us walk through this declaration very carefully, because there is a great deal of wisdom packed into just these few lines.

The column `student_id` is declared as `INT` (an integer number) and `NOT NULL` (it can never be empty). `AUTO_INCREMENT` tells the database to automatically generate the next sequential number each time a new row is inserted — so you never have to manually provide a student ID. The `CONSTRAINT pk_students PRIMARY KEY (student_id)` line declares `student_id` as the **Primary Key**, which means it uniquely identifies every row in this table. No two students can ever share the same `student_id`.

The `email` column has a `UNIQUE` constraint, which means although `email` is not the primary key, the database will still refuse to let two students register with the same email address. This is a business rule enforced at the database level.

The `gpa` column uses a `CHECK` constraint — a powerful mechanism that allows you to write a boolean condition that every new or updated value in that column must satisfy. If someone tries to insert a GPA of 5.0, the database will immediately reject the operation.

The `FOREIGN KEY` constraint on `department_id` creates a relationship between the `students` table and a `departments` table. It tells the database: "The value stored in `department_id` must exist in the `department_id` column of the `departments` table, or it must be `NULL`." The `ON DELETE SET NULL` clause means that if a department is deleted, instead of also deleting all the students in it, the database will simply set their `department_id` to `NULL`. The `ON UPDATE CASCADE` means that if a department's ID changes, all the student rows that reference it will automatically be updated too.

You can also create an **index** using `CREATE INDEX`, which is essentially a separate data structure that the database maintains alongside the table to make lookups faster — much like the index at the back of a textbook.

```sql
-- Create an index on last_name to speed up name-based searches
CREATE INDEX idx_students_last_name ON students (last_name);

-- Create a composite index on multiple columns
CREATE INDEX idx_students_name ON students (last_name, first_name);
```

And you can create a **view**, which is a stored SQL query that you can treat as if it were a table:

```sql
-- A view showing only active students with their departments
CREATE VIEW active_students_view AS
SELECT
    s.student_id,
    s.first_name,
    s.last_name,
    d.department_name,
    s.gpa
FROM students s
JOIN departments d ON s.department_id = d.department_id
WHERE s.is_active = TRUE;
```

A view does not store data itself. Every time you query `active_students_view`, the database silently executes the underlying query and returns the result. Views are extremely valuable for security (you can give users access to a view without exposing the underlying tables), for simplifying complex queries, and for maintaining backward compatibility when the underlying table structure changes.

### 3.2 ALTER

Once a table has been created and is in use, you will inevitably need to change it. Perhaps the business requires a new column, or an existing column needs a different data type, or a constraint needs to be added or removed. The `ALTER TABLE` statement is your tool for making these structural modifications to an existing table without destroying it and starting over.

Think of `ALTER` as renovating a house that people are still living in. You can add a new room, knock down a wall, change the dimensions of a door — all while leaving the existing furniture and residents untouched.

```sql
-- Adding a new column to the students table
ALTER TABLE students
ADD COLUMN phone_number VARCHAR(20);

-- Adding a column with a NOT NULL constraint requires a DEFAULT
-- because existing rows must immediately satisfy the constraint
ALTER TABLE students
ADD COLUMN semester_count INT NOT NULL DEFAULT 1;

-- Changing the data type of a column (syntax varies)
-- MySQL / MariaDB:
ALTER TABLE students
MODIFY COLUMN phone_number VARCHAR(15);

-- PostgreSQL:
ALTER TABLE students
ALTER COLUMN phone_number TYPE VARCHAR(15);

-- Renaming a column (PostgreSQL / MySQL 8+)
ALTER TABLE students
RENAME COLUMN phone_number TO mobile_number;

-- Dropping (removing) a column entirely
ALTER TABLE students
DROP COLUMN mobile_number;

-- Adding a new constraint to an existing column
ALTER TABLE students
ADD CONSTRAINT chk_semester CHECK (semester_count BETWEEN 1 AND 12);

-- Dropping an existing constraint
ALTER TABLE students
DROP CONSTRAINT chk_semester;

-- Renaming the table itself
ALTER TABLE students RENAME TO university_students;
ALTER TABLE university_students RENAME TO students;
```

A very important thing to understand about `ALTER TABLE` is that it can be an expensive operation on large tables. When you add a column, especially one with a `NOT NULL` constraint and no default value, the database may need to rewrite every single row in the table to accommodate the new column. On a table with hundreds of millions of rows, this can take hours and lock the table, making it inaccessible to users. In production systems, database administrators use specialized techniques — such as adding a nullable column first, then backfilling it, and only then adding the NOT NULL constraint — to minimize downtime.

### 3.3 DROP

The `DROP` statement is the most destructive command in DDL. When you drop a table, it is gone — the structure, all the data within it, all the indexes associated with it, and all the constraints referencing it. There is no recycle bin, no undo button, no confirmation dialog. The data simply ceases to exist.

```sql
-- Dropping a single table
DROP TABLE students;

-- If you're not sure whether the table exists (avoids an error)
DROP TABLE IF EXISTS students;

-- Dropping a view
DROP VIEW IF EXISTS active_students_view;

-- Dropping an index
DROP INDEX idx_students_last_name ON students; -- MySQL
DROP INDEX idx_students_last_name;             -- PostgreSQL

-- Dropping an entire database (extremely destructive!)
DROP DATABASE university_db;
```

The `IF EXISTS` clause is a safe practice. Without it, if you try to drop a table that doesn't exist, the database throws an error and your script stops executing. With `IF EXISTS`, the database simply ignores the command if the object is not found, allowing your script to continue. This is particularly valuable when writing deployment or migration scripts that may be run multiple times.

The `DROP` command also needs to respect **referential integrity**. If table A has a foreign key pointing to table B, you cannot drop table B without first either dropping table A, dropping the foreign key constraint, or using a special `CASCADE` option.

```sql
-- DROP with CASCADE will automatically drop all dependent objects
DROP TABLE departments CASCADE; -- PostgreSQL
```

### 3.4 TRUNCATE

`TRUNCATE` is a command that sits in an interesting middle ground. Like `DROP`, it removes all data from a table. But unlike `DROP`, it preserves the table structure — the columns, constraints, and indexes all remain perfectly intact. Think of it as completely emptying a filing cabinet while keeping the cabinet and all its labeled drawers in place.

```sql
-- Remove all rows from the students table, but keep the table structure
TRUNCATE TABLE students;

-- In some databases, you can truncate multiple tables at once
TRUNCATE TABLE students, enrollments, grades;
```

The most important distinction between `TRUNCATE` and `DELETE` (which is a DML command) is how they work internally. `DELETE` removes rows one at a time and logs each deletion, making it slow on large tables but allowing a rollback. `TRUNCATE`, on the other hand, deallocates entire data pages — it is essentially telling the storage engine "forget that all of this existed" without logging individual rows. This makes `TRUNCATE` dramatically faster on large datasets.

```
+------------------------------------------------------------------+
|          Comparison: DROP vs TRUNCATE vs DELETE                  |
+---------------------+---------------+---------------+------------+
| Feature             | DROP          | TRUNCATE      | DELETE     |
+---------------------+---------------+---------------+------------+
| Removes Data        | YES           | YES           | YES        |
| Removes Structure   | YES           | NO            | NO         |
| Can be Rolled Back  | NO (usually)  | NO (usually)  | YES        |
| Resets Auto-Incr.   | YES           | YES           | NO         |
| Speed on Big Data   | Fast          | Very Fast     | Slow       |
| WHERE clause        | NO            | NO            | YES        |
| Fires Triggers      | NO            | NO            | YES        |
+---------------------+---------------+---------------+------------+
```

Another key difference is that `TRUNCATE` resets the `AUTO_INCREMENT` counter back to 1, whereas `DELETE` does not. This matters when the IDs in your table carry business significance.

## 4. DML — Data Manipulation Language

If DDL is the architecture, then DML is the life of the building — the constant flow of activity. Data Manipulation Language is the set of commands that control the actual data living inside your tables. Every time a user creates an account, places an order, updates their profile, or deletes a post, some form of DML is quietly being executed behind the scenes.

Unlike DDL, DML operations are logged in detail and participate fully in transactions, meaning every DML operation can be rolled back if something goes wrong. This is the safety net that makes database systems trustworthy.

---

### 4.1 INSERT

The `INSERT` statement is how new rows of data enter a table. It is the birth certificate of every record in your database. There are several forms of `INSERT`, each appropriate for different situations.

The simplest form inserts a single row by specifying both the column names and the values in a corresponding, ordered list.

```sql
-- Inserting a single student record (explicit column list — best practice)
INSERT INTO students (first_name, last_name, email, date_of_birth, department_id)
VALUES ('Alice', 'Johnson', 'alice.johnson@uni.edu', '2001-05-14', 3);

-- You can omit column names if you provide values for ALL columns in order
-- (Not recommended — fragile if table structure changes)
INSERT INTO students
VALUES (DEFAULT, 'Bob', 'Smith', 'bob.smith@uni.edu', '2000-11-22',
        CURRENT_DATE, 3.75, TRUE, 2);
```

The explicit column list approach — naming each column before providing its value — is always preferred. It makes your code self-documenting, it is immune to problems if columns are ever reordered in the table, and it allows you to omit columns that have default values.

For inserting multiple rows at once, SQL provides a very efficient syntax:

```sql
-- Inserting multiple rows in a single statement (much faster than multiple singles)
INSERT INTO students (first_name, last_name, email, date_of_birth, department_id)
VALUES
    ('Carol', 'Williams', 'carol.w@uni.edu', '2002-03-07', 1),
    ('David', 'Brown',    'david.b@uni.edu', '2001-09-18', 2),
    ('Eve',   'Davis',    'eve.d@uni.edu',   '2003-01-30', 1),
    ('Frank', 'Miller',   'frank.m@uni.edu', '2000-07-12', 3);
```

Inserting multiple rows in a single `INSERT` statement is significantly faster than executing four separate `INSERT` statements, because the database only needs to parse, plan, and execute one command, and only needs to write to the transaction log once.

A particularly powerful variant is `INSERT INTO ... SELECT`, which allows you to populate a table with the results of a query from another table:

```sql
-- Insert all graduated students into an alumni table
INSERT INTO alumni (first_name, last_name, email, graduation_year)
SELECT first_name, last_name, email, YEAR(CURRENT_DATE)
FROM students
WHERE is_active = FALSE AND gpa >= 2.0;
```

This is how data pipelines often work: querying one table and inserting the results into another, potentially with transformations along the way.

---

### 4.2 UPDATE

The `UPDATE` statement modifies existing data in one or more rows of a table. It is one of the most dangerous DML commands to write carelessly, because without a `WHERE` clause, it will modify every single row in the table simultaneously.

```sql
-- Update a specific student's GPA
UPDATE students
SET gpa = 3.85
WHERE student_id = 1;

-- Update multiple columns at once
UPDATE students
SET
    gpa            = 3.90,
    is_active      = TRUE,
    semester_count = semester_count + 1
WHERE student_id = 1;
```

Notice the expression `semester_count = semester_count + 1` — this is a self-referential update. You are saying "take whatever the current value is, add one to it, and store the result back in the same column." This is a common pattern for incrementing counters.

The `WHERE` clause in `UPDATE` works identically to `WHERE` in `SELECT`, and can be as complex as needed:

```sql
-- Give all students in department 1 a 0.1 GPA bump if they are active
UPDATE students
SET gpa = gpa + 0.1
WHERE department_id = 1
  AND is_active = TRUE
  AND gpa <= 3.9;  -- Prevents GPA from exceeding 4.0
```

A professional practice before running any destructive `UPDATE` or `DELETE` is to first write the equivalent `SELECT` to see exactly which rows will be affected:

```sql
-- Step 1: Verify which rows would be affected
SELECT student_id, first_name, gpa
FROM students
WHERE department_id = 1 AND is_active = TRUE AND gpa <= 3.9;

-- Step 2: Once satisfied, run the UPDATE
UPDATE students
SET gpa = gpa + 0.1
WHERE department_id = 1 AND is_active = TRUE AND gpa <= 3.9;
```

Many databases also support `UPDATE ... JOIN` (or `UPDATE ... FROM` in PostgreSQL), allowing you to update rows in one table based on matching data from another:

```sql
-- PostgreSQL: Update student GPA based on grade data from another table
UPDATE students s
SET gpa = g.calculated_gpa
FROM grade_calculations g
WHERE s.student_id = g.student_id;
```

### 4.3 DELETE

The `DELETE` statement removes rows from a table. Like `UPDATE`, the absence of a `WHERE` clause will delete every row in the table — which is why some experienced database professionals have a personal rule of always writing the `WHERE` clause first before writing `DELETE FROM tablename`.

```sql
-- Delete a specific student by their primary key
DELETE FROM students
WHERE student_id = 5;

-- Delete all inactive students whose enrollment was more than 10 years ago
DELETE FROM students
WHERE is_active = FALSE
  AND enrollment_date < CURRENT_DATE - INTERVAL '10 years';

-- The catastrophic mistake: delete without WHERE (deletes ALL rows)
-- DELETE FROM students;   <-- DO NOT RUN without a WHERE clause!
```

Unlike `TRUNCATE`, `DELETE` fires database triggers (if any are defined on the table), processes cascades through foreign key relationships, and logs each deleted row individually. This makes `DELETE` slower but more flexible and controllable.

The `RETURNING` clause in PostgreSQL is a very useful extension to `DELETE` (and `UPDATE` and `INSERT`). It allows you to retrieve the data of the affected rows at the same time as you delete them:

```sql
-- PostgreSQL: Delete and immediately retrieve the deleted records
DELETE FROM students
WHERE is_active = FALSE
RETURNING student_id, first_name, last_name, email;
```

This is immensely useful for audit logging — you can capture what was deleted and store it in an audit table in a single, atomic operation.

### 4.4 MERGE / UPSERT

`MERGE` is one of the most sophisticated and powerful DML statements in SQL. It solves a problem that developers encounter constantly: "I have some incoming data, and I need to insert it if it doesn't already exist in my table, or update it if it does." This operation is commonly called an **UPSERT** (a portmanteau of "UPDATE" and "INSERT").

Without `MERGE`, you would typically have to write something cumbersome: first query to check if the row exists, then either insert or update based on the result. This approach is not only verbose but also potentially dangerous in concurrent environments — two processes running simultaneously might both find the row missing and both try to insert it, causing a conflict.

`MERGE` solves this elegantly in a single, atomic statement:

```sql
-- SQL Standard MERGE syntax (supported by SQL Server, Oracle, DB2)
MERGE INTO students AS target
USING incoming_student_data AS source
ON target.email = source.email  -- The join condition that determines a match

WHEN MATCHED THEN
    UPDATE SET
        target.first_name = source.first_name,
        target.last_name  = source.last_name,
        target.gpa        = source.gpa

WHEN NOT MATCHED BY TARGET THEN
    INSERT (first_name, last_name, email, date_of_birth, department_id)
    VALUES (source.first_name, source.last_name, source.email,
            source.date_of_birth, source.department_id)

WHEN NOT MATCHED BY SOURCE THEN
    DELETE;  -- Remove rows in target that no longer exist in source
```

In the `MERGE` statement above, we first define the **target** (the table we want to modify) and the **source** (the new incoming data). The `ON` clause specifies the matching condition — in this case, we consider two records to be the same if they share the same email address. The `WHEN MATCHED THEN UPDATE` block handles students who already exist. The `WHEN NOT MATCHED BY TARGET THEN INSERT` block handles brand-new students. The optional `WHEN NOT MATCHED BY SOURCE THEN DELETE` handles students in our target who are gone from the source.

Since `MERGE` is not uniformly supported across all database systems, each system has developed its own shorthand:

```sql
-- PostgreSQL: INSERT ... ON CONFLICT (the preferred upsert syntax)
INSERT INTO students (email, first_name, last_name, gpa)
VALUES ('alice.johnson@uni.edu', 'Alice', 'Johnson', 3.95)
ON CONFLICT (email)
DO UPDATE SET
    first_name = EXCLUDED.first_name,
    last_name  = EXCLUDED.last_name,
    gpa        = EXCLUDED.gpa;

-- The special EXCLUDED keyword refers to the row proposed for insertion
-- but rejected due to the conflict.
```

```sql
-- MySQL: INSERT ... ON DUPLICATE KEY UPDATE
INSERT INTO students (email, first_name, last_name, gpa)
VALUES ('alice.johnson@uni.edu', 'Alice', 'Johnson', 3.95)
ON DUPLICATE KEY UPDATE
    first_name = VALUES(first_name),
    last_name  = VALUES(last_name),
    gpa        = VALUES(gpa);
```

Understanding `MERGE` / UPSERT is critical for any data pipeline, ETL (Extract-Transform-Load) process, or synchronization scenario where you regularly push fresh data into a table that may already contain older versions of the same records.

## 5. DQL — Data Query Language

If all of SQL were compressed into a single statement, it would be `SELECT`. The `SELECT` statement is the engine of data retrieval — it is, by an enormous margin, the most written SQL statement in the world. Every report, every dashboard, every search result, every filtered list of products, every social media feed — all of them are powered by some form of `SELECT`.

The `SELECT` statement is deceptively simple on the surface but reveals extraordinary complexity and power as you explore its full range of clauses. A mastery of `SELECT` is what separates a beginner from a professional data engineer.

---

### 5.1 The Full Anatomy of SELECT

Before we dive into individual clauses, let us first lay out the complete, ordered anatomy of a `SELECT` statement. This is the canonical clause order — you must write the clauses in this order, and understanding what each clause does is the foundation of all SQL querying.

```
+----------------------------------------------------------------------+
|              Full SELECT Statement — Written Order                   |
+--------+-------------------------------------------------------------+
| Clause | Purpose                                                     |
+--------+-------------------------------------------------------------+
| SELECT | Choose which columns (or expressions) to include in output |
| FROM   | Declare the source table(s)                                 |
| JOIN   | Combine additional tables based on a condition              |
| WHERE  | Filter individual rows before any grouping                  |
| GROUP  | Collapse rows into groups by a shared column value          |
| BY     |                                                             |
| HAVING | Filter groups after aggregation                             |
| ORDER  | Sort the final result set                                   |
| BY     |                                                             |
| LIMIT  | Restrict the number of rows returned                        |
| OFFSET | Skip a number of rows (used for pagination)                 |
+--------+-------------------------------------------------------------+
```

A complete, fully-featured `SELECT` statement looks like this:

```sql
SELECT
    d.department_name,
    COUNT(s.student_id)    AS total_students,
    AVG(s.gpa)             AS average_gpa,
    MAX(s.gpa)             AS highest_gpa,
    MIN(s.gpa)             AS lowest_gpa
FROM students s
JOIN departments d ON s.department_id = d.department_id
WHERE s.is_active = TRUE
  AND s.enrollment_date >= '2020-01-01'
GROUP BY d.department_name
HAVING AVG(s.gpa) >= 3.0
ORDER BY average_gpa DESC
LIMIT 5;
```

This single query, despite fitting comfortably on one screen, draws on five different clauses, two tables, four aggregate functions, and multiple filter conditions. Let us understand each piece deeply.

---

### 5.2 FROM and JOIN

The `FROM` clause declares the data source — which table (or tables) the query will draw its data from. The real power emerges when you combine multiple tables using `JOIN`.

A `JOIN` is the mechanism for combining rows from two or more tables based on a related column between them. This is the heart of the relational database model.

```
        TABLE: students                  TABLE: departments
   +----+---------+--------+          +----+------------------+
   | id | name    |dept_id |          | id | dept_name        |
   +----+---------+--------+          +----+------------------+
   |  1 | Alice   |   1    |          |  1 | Computer Science |
   |  2 | Bob     |   2    |          |  2 | Mathematics      |
   |  3 | Carol   |   3    |    X     |  4 | Biology          |
   +----+---------+--------+          +----+------------------+
       (Carol's dept_id=3, no match)
       (Biology id=4, no match in students)

 INNER JOIN   --> Alice(CS), Bob(Math)            [only matched]
 LEFT JOIN    --> Alice(CS), Bob(Math), Carol(?)  [all students]
 RIGHT JOIN   --> Alice(CS), Bob(Math), ?(Bio)    [all depts]
 FULL JOIN    --> Alice(CS), Bob(Math), Carol(?), ?(Bio)
```

Let us write each join type:

```sql
-- INNER JOIN: Returns only students who HAVE a matching department
SELECT s.first_name, s.last_name, d.department_name
FROM students s
INNER JOIN departments d ON s.department_id = d.department_id;

-- LEFT JOIN: Returns ALL students, even those with no department
-- (NULL appears for department_name if no match exists)
SELECT s.first_name, s.last_name, d.department_name
FROM students s
LEFT JOIN departments d ON s.department_id = d.department_id;

-- RIGHT JOIN: Returns ALL departments, even those with no students
SELECT s.first_name, s.last_name, d.department_name
FROM students s
RIGHT JOIN departments d ON s.department_id = d.department_id;

-- FULL OUTER JOIN: All students and all departments, matched where possible
SELECT s.first_name, s.last_name, d.department_name
FROM students s
FULL OUTER JOIN departments d ON s.department_id = d.department_id;

-- Self JOIN: Joining a table to itself
-- Find pairs of students in the same department
SELECT
    a.first_name AS student_1,
    b.first_name AS student_2,
    a.department_id
FROM students a
JOIN students b ON a.department_id = b.department_id
WHERE a.student_id < b.student_id; -- Avoids duplicates and self-pairs
```

You can chain multiple joins together to combine three or more tables in a single query:

```sql
SELECT
    s.first_name,
    s.last_name,
    d.department_name,
    c.course_name,
    e.grade
FROM students s
JOIN enrollments e ON s.student_id  = e.student_id
JOIN courses     c ON e.course_id   = c.course_id
JOIN departments d ON s.department_id = d.department_id
WHERE s.is_active = TRUE;
```

---

### 5.3 WHERE

The `WHERE` clause is the filter. It examines each row produced by the `FROM` and `JOIN` phases and discards any row that does not satisfy the condition. Only the surviving rows move forward to the next phase of processing.

The `WHERE` clause supports a rich vocabulary of operators and conditions:

```sql
-- Comparison operators
WHERE gpa > 3.0
WHERE gpa >= 3.5
WHERE gpa = 4.0
WHERE gpa <> 3.0     -- Not equal (also written as !=)

-- Logical operators: AND, OR, NOT
WHERE is_active = TRUE AND gpa >= 3.0
WHERE department_id = 1 OR department_id = 2
WHERE NOT (is_active = FALSE)

-- BETWEEN: Inclusive range check
WHERE gpa BETWEEN 3.0 AND 4.0
WHERE enrollment_date BETWEEN '2020-01-01' AND '2022-12-31'

-- IN: Check membership in a list
WHERE department_id IN (1, 2, 5)
WHERE last_name IN ('Johnson', 'Smith', 'Williams')

-- NOT IN: Exclusion from a list
WHERE department_id NOT IN (3, 4)

-- LIKE: Pattern matching using wildcards
--  %  matches zero or more characters
--  _  matches exactly one character
WHERE email      LIKE '%@uni.edu'   -- Ends with @uni.edu
WHERE first_name LIKE 'A%'          -- Starts with A
WHERE last_name  LIKE '_ohnson'     -- Exactly one char before 'ohnson'
WHERE email      LIKE '%alice%'     -- Contains 'alice' anywhere

-- IS NULL / IS NOT NULL
WHERE department_id IS NULL      -- Students with no department
WHERE department_id IS NOT NULL  -- Students who have a department

-- EXISTS: Check if a subquery returns any rows
WHERE EXISTS (
    SELECT 1
    FROM enrollments e
    WHERE e.student_id = s.student_id
)
```

A critical concept to understand about `WHERE` is how it handles `NULL`. In SQL, `NULL` represents the absence of a value — it is not zero, it is not an empty string, it is simply "unknown." Because of this, comparing `NULL` with any operator other than `IS NULL` returns `NULL`, which is treated as false in a `WHERE` clause.

```sql
-- This will NOT find rows where department_id is NULL:
WHERE department_id = NULL   -- WRONG! Always evaluates to UNKNOWN

-- This is the correct way:
WHERE department_id IS NULL  -- CORRECT
```

---

### 5.4 GROUP BY and HAVING

The `GROUP BY` clause is where SQL transitions from looking at individual rows to looking at **groups** of rows. When you apply `GROUP BY`, you instruct the database to collect all rows that share the same value in the specified column(s) and collapse them into a single summary row. Once rows have been grouped, you apply **aggregate functions** to each group.

```
Before GROUP BY (individual rows):
+------------+-----------------+------+
| student_id | department      | gpa  |
+------------+-----------------+------+
|     1      | Computer Sci.   | 3.80 |
|     2      | Mathematics     | 3.50 |
|     3      | Computer Sci.   | 3.95 |
|     4      | Mathematics     | 3.20 |
|     5      | Computer Sci.   | 3.60 |
+------------+-----------------+------+

After GROUP BY department:
+-----------------+-------+----------+
| department      | COUNT | AVG(gpa) |
+-----------------+-------+----------+
| Computer Sci.   |   3   |  3.783   |
| Mathematics     |   2   |  3.350   |
+-----------------+-------+----------+
```

The most commonly used aggregate functions are:
- `COUNT(*)` — counts all rows, including NULLs
- `COUNT(column)` — counts only non-NULL values
- `SUM(column)` — adds all values
- `AVG(column)` — computes the average of non-NULL values
- `MAX(column)` — finds the highest value
- `MIN(column)` — finds the lowest value

```sql
-- Count students and compute average GPA per department
SELECT
    department_id,
    COUNT(student_id)  AS total_students,
    AVG(gpa)           AS avg_gpa,
    MAX(gpa)           AS top_gpa,
    MIN(gpa)           AS lowest_gpa
FROM students
WHERE is_active = TRUE
GROUP BY department_id;
```

Once you have groups, you may want to filter them — keep only the groups that satisfy some condition. This is where `HAVING` comes in. The key distinction is:

- `WHERE` filters **individual rows** before grouping
- `HAVING` filters **groups** after grouping

```sql
-- Find departments where the average GPA is 3.0 or higher
-- and there are at least 5 active students
SELECT
    department_id,
    COUNT(student_id)  AS total_students,
    AVG(gpa)           AS avg_gpa
FROM students
WHERE is_active = TRUE         -- Filter rows BEFORE grouping
GROUP BY department_id
HAVING AVG(gpa) >= 3.0         -- Filter GROUPS after aggregation
   AND COUNT(student_id) >= 5;
```

You cannot use `WHERE` to filter on the result of an aggregate function like `AVG(gpa) >= 3.0`. This is because at the time `WHERE` runs, groups don't exist yet — they are formed later by `GROUP BY`. `HAVING` was designed specifically for this purpose.

---

### 5.5 ORDER BY and LIMIT

The `ORDER BY` clause sorts the result set before it is returned to the user. Without `ORDER BY`, the database returns rows in an undefined order. If the order of results matters to you (and it almost always does), you must always specify `ORDER BY` explicitly.

```sql
-- Sort by a single column ascending (default)
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa;          -- ASC is the default

-- Sort descending (highest GPA first)
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa DESC;

-- Sort by multiple columns: first by department, then by GPA within it
SELECT department_id, first_name, gpa
FROM students
ORDER BY department_id ASC, gpa DESC;

-- Sort by a computed alias defined in SELECT
SELECT first_name, last_name, (gpa * 25) AS score
FROM students
ORDER BY score DESC;

-- Handling NULLs in sorting (PostgreSQL)
ORDER BY gpa DESC NULLS LAST;   -- Put NULL values at the end
ORDER BY gpa DESC NULLS FIRST;  -- Put NULL values at the beginning
```

The `LIMIT` clause restricts how many rows are returned. It is almost always paired with `ORDER BY`, because without an explicit sort order, "the first n rows" is meaningless.

```sql
-- Get the top 10 students by GPA
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa DESC
LIMIT 10;

-- Pagination: get the second page of results (rows 11-20)
-- Page 1: LIMIT 10 OFFSET 0
-- Page 2: LIMIT 10 OFFSET 10
-- Page 3: LIMIT 10 OFFSET 20
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa DESC
LIMIT 10 OFFSET 10;

-- SQL Server equivalent
SELECT TOP 10 first_name, last_name, gpa
FROM students
ORDER BY gpa DESC;

-- SQL Standard (ISO)
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa DESC
FETCH FIRST 10 ROWS ONLY;
```

`OFFSET` is the basis of **pagination** — the technique of breaking a large result set into pages. However, deep pagination (large offsets) can be slow on large tables, because the database still has to generate and then discard all rows before the offset point. For high-performance pagination, keyset pagination (cursor-based) is preferred.

### 5.6 Subqueries and CTEs

A **subquery** is a query nested inside another query. The inner query runs first, produces a result, and then the outer query uses that result. Subqueries allow you to express very complex logic in a readable, modular way.

```sql
-- Scalar subquery: Returns a single value
-- Find all students with a GPA above the overall class average
SELECT first_name, last_name, gpa
FROM students
WHERE gpa > (SELECT AVG(gpa) FROM students);

-- Subquery in FROM (derived table / inline view)
SELECT dept_stats.department_id, dept_stats.avg_gpa
FROM (
    SELECT department_id, AVG(gpa) AS avg_gpa
    FROM students
    WHERE is_active = TRUE
    GROUP BY department_id
) AS dept_stats
WHERE dept_stats.avg_gpa > 3.2;

-- Correlated subquery: the inner query references the outer query's row
-- Find the top student in each department
SELECT s.first_name, s.last_name, s.gpa
FROM students s
WHERE s.gpa = (
    SELECT MAX(gpa)
    FROM students
    WHERE department_id = s.department_id  -- Correlated to outer query
);
```

A correlated subquery runs once for each row of the outer query. For each student row `s`, it asks: "what is the maximum GPA in this student's department?" and then checks if the student's GPA equals that maximum. Correlated subqueries can be elegant but slow on large datasets because of repeated execution.

**Common Table Expressions (CTEs)** are a more modern, readable alternative to subqueries. They allow you to define named temporary result sets at the top of your query and then reference them by name as if they were tables.

```sql
-- CTE using the WITH keyword
WITH department_averages AS (
    -- Step 1: Compute average GPA per department
    SELECT department_id, AVG(gpa) AS avg_gpa
    FROM students
    WHERE is_active = TRUE
    GROUP BY department_id
),
top_departments AS (
    -- Step 2: Keep only departments averaging 3.5+
    SELECT department_id, avg_gpa
    FROM department_averages
    WHERE avg_gpa >= 3.5
)
-- Step 3: Find students who exceed their department's average
SELECT
    s.first_name,
    s.last_name,
    s.gpa,
    td.avg_gpa AS department_avg
FROM students s
JOIN top_departments td ON s.department_id = td.department_id
WHERE s.gpa >= td.avg_gpa;
```

In this example, we define two CTEs: `department_averages` computes the average GPA for each department, and `top_departments` filters that result. The main query then uses `top_departments` like any other table. CTEs make complex multi-step logic dramatically more readable.

CTEs can also be **recursive** — they can reference themselves, making it possible to traverse hierarchical data such as organizational charts or bill-of-materials structures.

```sql
-- Recursive CTE: Find all subordinates of a manager
WITH RECURSIVE subordinates AS (
    -- Base case: start with the target manager
    SELECT employee_id, manager_id, name, 1 AS level
    FROM employees
    WHERE employee_id = 42

    UNION ALL

    -- Recursive case: find everyone who reports to someone already in the set
    SELECT e.employee_id, e.manager_id, e.name, s.level + 1
    FROM employees e
    JOIN subordinates s ON e.manager_id = s.employee_id
)
SELECT * FROM subordinates ORDER BY level, name;
```

## 6. TCL — Transaction Control Language

We now arrive at perhaps the most philosophically important part of SQL: the language of **transactions**. Understanding transactions is what separates a programmer who *writes* SQL from an engineer who truly *understands* databases.

A **transaction** is a unit of work — a sequence of one or more SQL statements that are treated as a single, indivisible operation. Either all of the statements in a transaction succeed and are permanently saved, or none of them are. There is no middle ground.

To understand why transactions exist, consider this classic scenario. You are building a banking application. A user wants to transfer $500 from their savings account to their checking account. This requires two separate `UPDATE` statements:

```
Statement 1: Deduct $500 from savings account
Statement 2: Add $500 to checking account
```

Imagine your server crashes after Statement 1 executes but before Statement 2 runs. Without transactions, $500 has been permanently subtracted from savings, but never added to checking. The money has simply vanished. Transactions prevent this by treating both statements as a single unit — if anything goes wrong, the entire operation is reversed.

This guarantee is formalized through a set of properties known by the acronym **ACID**:

```
+----------------------------------------------------------------------+
|                    ACID Properties of Transactions                   |
+--------------+-------------------------------------------------------+
| Atomicity    | The transaction is "all or nothing." Either all       |
|              | statements commit, or none of them do.                |
+--------------+-------------------------------------------------------+
| Consistency  | A transaction brings the database from one valid      |
|              | state to another. Constraints are never violated.     |
+--------------+-------------------------------------------------------+
| Isolation    | Concurrent transactions cannot see each other's       |
|              | uncommitted changes. They appear serial.               |
+--------------+-------------------------------------------------------+
| Durability   | Once committed, changes are permanent, even if the    |
|              | system crashes immediately afterward.                  |
+--------------+-------------------------------------------------------+
```

---

### 6.1 BEGIN

The `BEGIN` statement marks the starting point of a new transaction. Every statement that follows `BEGIN` is part of the transaction until a `COMMIT` or `ROLLBACK` is issued.

In many databases, a connection operates in **autocommit mode** by default — every individual SQL statement automatically commits the moment it finishes. Calling `BEGIN` temporarily suspends autocommit and places you in manual transaction mode.

```sql
-- PostgreSQL / MySQL:
BEGIN;

-- SQL Standard / SQL Server:
BEGIN TRANSACTION;

-- The statements that follow are now part of the transaction:
UPDATE accounts SET balance = balance - 500 WHERE account_id = 101;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 202;

-- These changes are NOT yet permanent. They are visible to this session
-- but other sessions may not see them (depends on isolation level).
```

---

### 6.2 COMMIT

`COMMIT` is the instruction that tells the database: "I am satisfied with all the work done in this transaction. Please make all changes permanent."

When the database processes a `COMMIT`, it writes all the transaction's changes to durable storage (typically the Write-Ahead Log on disk), makes those changes visible to other transactions, and releases any locks held by the transaction.

```sql
BEGIN;

UPDATE accounts SET balance = balance - 500 WHERE account_id = 101;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 202;

-- Verify the results before committing (good practice)
SELECT account_id, balance FROM accounts WHERE account_id IN (101, 202);

-- Everything looks correct — make the changes permanent
COMMIT;
-- After this point, there is no going back.
```

---

### 6.3 ROLLBACK

`ROLLBACK` is the emergency exit. It tells the database: "Something went wrong. Undo everything that happened since the last `BEGIN` and restore the database to the state it was in before this transaction started."

```sql
BEGIN;

UPDATE accounts SET balance = balance - 500 WHERE account_id = 101;
-- Oops! We discover that account 202 is frozen and cannot receive funds.

-- Abort the entire transaction and reverse the deduction.
ROLLBACK;

-- The database is now exactly as it was before BEGIN.
-- Account 101 still has its original, untouched balance.
```

In application code, `ROLLBACK` is typically called in an error handler — a try/catch block or equivalent. The universal pattern is:

```
BEGIN;
    [DML statement 1]
    [DML statement 2]
    [DML statement 3]
    -- If any error is detected: ROLLBACK;
    -- If all succeed: COMMIT;
```

Most database client libraries support this natively, automatically issuing a `ROLLBACK` if the connection drops or an exception is thrown before a `COMMIT` is reached.

---

### 6.4 SAVEPOINT

A `SAVEPOINT` is a bookmark within a transaction. It allows you to **partially rollback** — undoing only the work done after the savepoint, while preserving the work done before it.

Imagine a long transaction with ten steps. If something goes wrong on step 7, you don't necessarily want to lose all the work from steps 1 through 6. By placing a savepoint after step 6, you can roll back just steps 7 through 10 and either retry them or continue with different logic.

```sql
BEGIN;

-- Step 1: Enroll student in course
INSERT INTO enrollments (student_id, course_id) VALUES (1, 101);

-- Step 2: Record the payment
INSERT INTO payments (student_id, amount) VALUES (1, 500.00);

-- Create a savepoint after the first two steps
SAVEPOINT after_enrollment;

-- Step 3: Try to assign a seat in the classroom
UPDATE classroom_seats
SET student_id = 1
WHERE seat_id = 45 AND student_id IS NULL;

-- Step 4: Update the seat count in the course
UPDATE courses SET enrolled_count = enrolled_count + 1 WHERE course_id = 101;

-- If seat 45 was already taken, we can undo ONLY steps 3 and 4:
ROLLBACK TO SAVEPOINT after_enrollment;
-- Steps 1 and 2 are preserved. Only steps 3 and 4 are undone.

-- Try an alternative seat:
UPDATE classroom_seats
SET student_id = 1
WHERE seat_id = 67 AND student_id IS NULL;

UPDATE courses SET enrolled_count = enrolled_count + 1 WHERE course_id = 101;

-- Release the savepoint (optional cleanup)
RELEASE SAVEPOINT after_enrollment;

-- Commit everything
COMMIT;
```

The flow of a transaction with savepoints can be visualized like this:

```
BEGIN
  |
  +-- INSERT enrollment          <-- Step 1
  |
  +-- INSERT payment             <-- Step 2
  |
  +--[SAVEPOINT after_enrollment] <-- Bookmark placed here
  |
  +-- UPDATE seat assignment     <-- Step 3
  |
  +-- UPDATE course count        <-- Step 4
  |
  |   (Error: seat already taken)
  |
  +-- ROLLBACK TO SAVEPOINT      <-- Steps 3 & 4 undone
  |   after_enrollment               Steps 1 & 2 preserved
  |
  +-- UPDATE seat (retry #67)    <-- New Step 3
  |
  +-- UPDATE course count        <-- New Step 4
  |
COMMIT                           <-- All changes permanently saved
```

Savepoints are particularly valuable in complex business transactions — such as order processing, multi-step financial operations, or batch imports — where you want granular error recovery without sacrificing all the work that was successfully completed before the failure point.

## 7. The Logical Query Processing Order

This is one of the most important concepts in SQL, and yet it is rarely taught in introductory courses. When you write a `SELECT` statement, you write the clauses in a specific order (SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY). But the database does **not** execute them in that written order. It processes them in a completely different order, known as the **Logical Query Processing Order**.

Understanding this order is the key to answering questions like:
- "Why can't I use my `SELECT` alias in a `WHERE` clause?"
- "Why can I use an aggregate function in `HAVING` but not in `WHERE`?"

```
+--------+-----------+--------------------------------------------------+
| Phase  | Clause    | What happens                                     |
+--------+-----------+--------------------------------------------------+
|   1    | FROM      | Identify source tables, perform all JOINs.       |
|        | + JOINs   | Produces a virtual intermediate table (VT1).     |
+--------+-----------+--------------------------------------------------+
|   2    | WHERE     | Filter rows from VT1. Row-level filter.          |
|        |           | Aggregates do NOT exist yet. Produces VT2.       |
+--------+-----------+--------------------------------------------------+
|   3    | GROUP BY  | Group the rows in VT2 by shared column values.   |
|        |           | Produces VT3. Aggregate functions are now valid. |
+--------+-----------+--------------------------------------------------+
|   4    | HAVING    | Filter groups from VT3 using aggregate results.  |
|        |           | Produces VT4.                                    |
+--------+-----------+--------------------------------------------------+
|   5    | SELECT    | Evaluate column expressions and assign aliases.  |
|        |           | Produces VT5. This is where aliases are DEFINED. |
+--------+-----------+--------------------------------------------------+
|   6    | DISTINCT  | Remove duplicate rows (if DISTINCT specified).   |
|        |           | Produces VT6.                                    |
+--------+-----------+--------------------------------------------------+
|   7    | ORDER BY  | Sort VT6. Can use SELECT aliases because         |
|        |           | SELECT (phase 5) has already been processed.     |
+--------+-----------+--------------------------------------------------+
|   8    | LIMIT/    | Return only the specified number of rows.        |
|        | OFFSET    | Produces the final result set.                   |
+--------+-----------+--------------------------------------------------+
```

Now observe the consequences of this processing order. **Why can't you use a SELECT alias in WHERE?** Because `WHERE` runs at phase 2, and `SELECT` aliases are not defined until phase 5. The database literally does not know what the alias means yet.

```sql
-- WRONG: Cannot use alias in WHERE (alias doesn't exist yet)
SELECT (gpa * 25) AS score
FROM students
WHERE score > 75;  -- Error: column "score" does not exist

-- CORRECT: Repeat the expression in WHERE
SELECT (gpa * 25) AS score
FROM students
WHERE (gpa * 25) > 75;

-- Or use a CTE or subquery:
SELECT score
FROM (
    SELECT (gpa * 25) AS score FROM students
) AS sub
WHERE score > 75;
```

**Why can't you use an aggregate in WHERE?** Because `WHERE` runs at phase 2, before `GROUP BY` at phase 3. Aggregates summarize groups, but groups don't exist during `WHERE` processing. That is why `HAVING` — which runs at phase 4, after grouping — exists.

```sql
-- WRONG: Aggregate function in WHERE
SELECT department_id, AVG(gpa) FROM students
WHERE AVG(gpa) > 3.0   -- Error: aggregate not allowed in WHERE
GROUP BY department_id;

-- CORRECT: Use HAVING
SELECT department_id, AVG(gpa) AS avg_gpa
FROM students
GROUP BY department_id
HAVING AVG(gpa) > 3.0;
```

**Why can you use a SELECT alias in ORDER BY?** Because `ORDER BY` runs at phase 7, *after* `SELECT` at phase 5. By the time the database reaches `ORDER BY`, the aliases are already defined and available.

```sql
-- This works perfectly
SELECT first_name, (gpa * 25) AS score
FROM students
ORDER BY score DESC;  -- 'score' alias is known here
```

## 8. Putting It All Together — A Real-World Scenario

Let us now synthesize everything we have learned into a single, cohesive, realistic example. We will build a small university database from scratch, populate it with data, query it with complex questions, and demonstrate transaction management.

**Step 1: Creating the Schema (DDL)**

```sql
-- Create departments first (referenced by students)
CREATE TABLE departments (
    department_id   INT          NOT NULL AUTO_INCREMENT,
    department_name VARCHAR(100) NOT NULL UNIQUE,
    building        VARCHAR(50),
    CONSTRAINT pk_departments PRIMARY KEY (department_id)
);

-- Create courses
CREATE TABLE courses (
    course_id     INT          NOT NULL AUTO_INCREMENT,
    course_name   VARCHAR(150) NOT NULL,
    credits       INT          NOT NULL DEFAULT 3 CHECK (credits BETWEEN 1 AND 6),
    department_id INT          NOT NULL,
    CONSTRAINT pk_courses     PRIMARY KEY (course_id),
    CONSTRAINT fk_course_dept FOREIGN KEY (department_id)
        REFERENCES departments(department_id)
);

-- Create students
CREATE TABLE students (
    student_id      INT            NOT NULL AUTO_INCREMENT,
    first_name      VARCHAR(50)    NOT NULL,
    last_name       VARCHAR(50)    NOT NULL,
    email           VARCHAR(100)   NOT NULL UNIQUE,
    gpa             DECIMAL(3, 2)  CHECK (gpa BETWEEN 0.0 AND 4.0),
    department_id   INT,
    enrollment_date DATE           NOT NULL DEFAULT CURRENT_DATE,
    CONSTRAINT pk_students  PRIMARY KEY (student_id),
    CONSTRAINT fk_stu_dept  FOREIGN KEY (department_id)
        REFERENCES departments(department_id) ON DELETE SET NULL
);

-- Create the enrollments junction table
CREATE TABLE enrollments (
    enrollment_id INT    NOT NULL AUTO_INCREMENT,
    student_id    INT    NOT NULL,
    course_id     INT    NOT NULL,
    grade         CHAR(2),
    CONSTRAINT pk_enrollments  PRIMARY KEY (enrollment_id),
    CONSTRAINT fk_enr_student  FOREIGN KEY (student_id) REFERENCES students(student_id),
    CONSTRAINT fk_enr_course   FOREIGN KEY (course_id)  REFERENCES courses(course_id),
    CONSTRAINT uq_enrollment   UNIQUE (student_id, course_id)
);
```

**Step 2: Populating the Data (DML)**

```sql
-- Insert departments
INSERT INTO departments (department_name, building) VALUES
    ('Computer Science', 'Tech Hall'),
    ('Mathematics',      'Science Wing'),
    ('Physics',          'Science Wing'),
    ('Literature',       'Arts Building');

-- Insert students
INSERT INTO students (first_name, last_name, email, gpa, department_id) VALUES
    ('Alice',  'Johnson', 'alice@uni.edu',  3.90, 1),
    ('Bob',    'Smith',   'bob@uni.edu',    3.10, 1),
    ('Carol',  'Lee',     'carol@uni.edu',  3.75, 2),
    ('David',  'Kim',     'david@uni.edu',  2.80, 2),
    ('Eve',    'Brown',   'eve@uni.edu',    3.50, 3),
    ('Frank',  'Davis',   'frank@uni.edu',  NULL, NULL); -- Undeclared major
```

**Step 3: A Safe Transaction (DML + TCL)**

```sql
-- Enroll Alice in a course within a transaction
BEGIN;

    INSERT INTO enrollments (student_id, course_id)
    VALUES (1, 1);

    UPDATE enrollments SET grade = 'A' WHERE student_id = 1 AND course_id = 1;
    UPDATE students    SET gpa   = 3.95 WHERE student_id = 1;

    -- Everything looks good — commit
COMMIT;
```

**Step 4: Answering Business Questions (DQL)**

```sql
-- Q1: Top 3 students by GPA in Computer Science
SELECT
    s.first_name,
    s.last_name,
    s.gpa
FROM students s
JOIN departments d ON s.department_id = d.department_id
WHERE d.department_name = 'Computer Science'
  AND s.gpa IS NOT NULL
ORDER BY s.gpa DESC
LIMIT 3;

-- Q2: Which departments have an average GPA above 3.2?
SELECT
    d.department_name,
    COUNT(s.student_id)   AS total_students,
    ROUND(AVG(s.gpa), 2)  AS avg_gpa
FROM students s
JOIN departments d ON s.department_id = d.department_id
WHERE s.gpa IS NOT NULL
GROUP BY d.department_name
HAVING AVG(s.gpa) > 3.2
ORDER BY avg_gpa DESC;

-- Q3: Which students have a GPA above their department's average?
WITH dept_avg AS (
    SELECT department_id, AVG(gpa) AS avg_gpa
    FROM students
    WHERE gpa IS NOT NULL
    GROUP BY department_id
)
SELECT
    s.first_name,
    s.last_name,
    s.gpa,
    ROUND(da.avg_gpa, 2) AS dept_avg_gpa
FROM students s
JOIN dept_avg da ON s.department_id = da.department_id
WHERE s.gpa > da.avg_gpa
ORDER BY s.last_name;
```

**Step 5: Schema Evolution (DDL)**

```sql
-- Track when a student last updated their profile
ALTER TABLE students
ADD COLUMN last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP;

-- Enforce grade validity at the database level
ALTER TABLE enrollments
ADD CONSTRAINT chk_grade
    CHECK (grade IN ('A', 'B', 'C', 'D', 'F', 'W', 'I'));
```

## Summary — The Complete Picture

SQL is the language through which human intention meets structured data. Its four sub-languages form a complete, self-reinforcing system:

**DDL** defines the world — the tables, constraints, indexes, and views that give shape to your data. It is the blueprint. Once you define it carefully, the database enforces your rules automatically, saving you from countless bugs.

**DML** animates the world — inserting new facts, correcting old ones, removing what is no longer needed, and intelligently merging incoming data with what already exists. DML is the heartbeat of every living application.

**DQL** illuminates the world — the `SELECT` statement, with its rich vocabulary of joins, filters, aggregations, subqueries, and common table expressions, is the lens through which all stored knowledge becomes visible and useful.

**TCL** protects the world — wrapping multiple operations in atomic transactions, ensuring that partial failures leave no damage behind, and providing the savepoint mechanism for nuanced, recoverable error handling.

Together, they give you the power not just to store data, but to reason about it, to trust it, and to build systems upon it that are robust, consistent, and scalable across years of real-world use.
