## 1. Introduction — From SQL to Execution

When you write a SQL query that joins four tables, you are expressing your intention at a very high level of abstraction. You are saying, in plain terms, "I want a result that combines information from tables A, B, C, and D, linked by these conditions." What you are *not* saying — and what you do not have to say — is *how* the database should produce that result. The order in which it reads the tables, the order in which it compares rows, the data structures it builds in memory, the algorithms it uses to find matches — all of this is determined by the database engine on your behalf.

This delegation is both a great convenience and a source of confusion. When a query performs well, you may never think about it. But when a query runs for thirty seconds instead of thirty milliseconds, the answer is almost always found somewhere in the details of *how* the engine executed the join — which algorithm it chose, which order it joined the tables, and what intermediate results it had to create and store.

This chapter peels back the curtain on that invisible machinery. We will take a concrete, four-table query and trace it, step by step and row by row, through the exact physical process that the database engine uses to produce the final answer. By the end, you will have a clear mental model of what actually happens when you press execute.

## 2. The Working Example — Four Tables: A, B, C, D

We will use a scenario from an order management system. The four tables represent the natural chain of data: a customer places an order, the order contains line items, and each line item references a product.

```sql
CREATE TABLE customers (        -- Table A
    customer_id   INT PRIMARY KEY,
    customer_name VARCHAR(100),
    country       VARCHAR(50)
);

CREATE TABLE orders (           -- Table B
    order_id      INT PRIMARY KEY,
    customer_id   INT REFERENCES customers(customer_id),
    order_date    DATE,
    status        VARCHAR(20)
);

CREATE TABLE order_items (      -- Table C
    item_id       INT PRIMARY KEY,
    order_id      INT REFERENCES orders(order_id),
    product_id    INT,
    quantity      INT,
    unit_price    DECIMAL(10,2)
);

CREATE TABLE products (         -- Table D
    product_id    INT PRIMARY KEY,
    product_name  VARCHAR(100),
    category      VARCHAR(50),
    cost_price    DECIMAL(10,2)
);
```

Sample data — small and concrete so every step is traceable:

```

+-------------+-------------------+---------+
| customer_id | customer_name     | country |
+-------------+-------------------+---------+
|      1      | Alice Corp        | USA     |
|      2      | Bob Ltd           | UK      |
|      3      | Carol Inc         | USA     |
+-------------+-------------------+---------+

TABLE B: orders
+----------+-------------+------------+----------+
| order_id | customer_id | order_date | status   |
+----------+-------------+------------+----------+
|   1001   |      1      | 2024-01-10 | SHIPPED  |
|   1002   |      1      | 2024-02-15 | PENDING  |
|   1003   |      2      | 2024-01-20 | SHIPPED  |
|   1004   |      3      | 2024-03-01 | SHIPPED  |
+----------+-------------+------------+----------+

TABLE C: order_items
+---------+----------+------------+----------+------------+
| item_id | order_id | product_id | quantity | unit_price |
+---------+----------+------------+----------+------------+
|    1    |   1001   |    501     |    2     |   50.00    |
|    2    |   1001   |    502     |    1     |  120.00    |
|    3    |   1002   |    501     |    3     |   50.00    |
|    4    |   1003   |    503     |    5     |   30.00    |
|    5    |   1004   |    502     |    2     |  120.00    |
+---------+----------+------------+----------+------------+

+------------+--------------+-------------+------------+
| product_id | product_name | category    | cost_price |
+------------+--------------+-------------+------------+
|    501     | Widget Alpha | Electronics |   35.00    |

+------------+--------------+-------------+------------+
```

The query we are going to execute and trace:

```sql
SELECT
    a.customer_name,
    b.order_id,
    b.order_date,
    c.quantity,
    c.unit_price,
    d.product_name,
    d.category,
    (c.quantity * c.unit_price)                  AS line_total,
    (c.quantity * c.unit_price - c.quantity * d.cost_price) AS profit
FROM customers   AS a          -- Table A
JOIN orders      AS b ON a.customer_id = b.customer_id   -- A → B
JOIN order_items AS c ON b.order_id    = c.order_id      -- B → C
JOIN products    AS d ON c.product_id  = d.product_id    -- C → D
WHERE b.status = 'SHIPPED';
```

This is the query we will dissect from every possible angle.

## 3. The Core Concept — Joins Are Always Binary

Before we trace the execution, there is one fundamental truth you must internalize: **the database engine can only join two tables at a time**. SQL allows you to write `A JOIN B JOIN C JOIN D` in a single query, but internally, the engine always breaks this into a sequence of binary (two-input) join operations.

The result of each binary join becomes a new, temporary "virtual table" — often called an **intermediate result set** — which is then used as one of the two inputs for the next binary join. The final result set is produced only after all binary joins have been completed.

This means that a four-table join like `A JOIN B JOIN C JOIN D` is actually executed as three successive two-table joins:

```
Multi-table join decomposed into binary operations:

Your SQL:  A JOIN B JOIN C JOIN D

Engine's execution plan:

  Step 1:  A  JOIN  B  ─────────────────>  intermediate result AB
                                                      |
  Step 2:            AB  JOIN  C  ────────>  intermediate result ABC
                                                      |
  Step 3:                      ABC  JOIN  D  ──────>  FINAL RESULT

Each step is a binary join.
Each step's output feeds the next step as its left input.
```

This sequential structure is called a **Left-Deep Join Tree**, which we will explore in depth shortly. The important thing to understand right now is that the engine never "sees" all four tables at once. It processes them two at a time, building up towards the final answer like a carpenter assembling parts of a structure one piece at a time.

## 4. The Join Tree — How the Engine Structures the Work

A **join tree** is a visual representation of the order and structure of binary join operations that the engine will perform. There are several possible tree shapes, and the shape the optimizer chooses has a profound effect on performance.

**Left-Deep Tree** (most common, and what sequential `JOIN` syntax produces):

```
Left-Deep Tree for A JOIN B JOIN C JOIN D:

        JOIN (final result)
       /         \
    JOIN          D
   /     \
 JOIN      C
/    \
A      B

Execution order:
  (1) Join A with B  → result AB
  (2) Join AB with C → result ABC
  (3) Join ABC with D → final result
```

In a left-deep tree, the left input of every join node is always the output of another join (or the initial table at the leaf). The right input is always a "base" table read directly from disk. This structure is efficient because it is pipeline-friendly: the engine can start producing rows from the first join even before it has finished reading all of table B, feeding those rows immediately into the second join.

**Right-Deep Tree** (less common):

```
Right-Deep Tree for A JOIN B JOIN C JOIN D:

  JOIN (final result)
 /         \
A          JOIN
          /     \
         B      JOIN
               /    \
              C       D

Execution order:
  (1) Join C with D  → result CD
  (2) Join B with CD → result BCD
  (3) Join A with BCD → final result
```

A right-deep tree is sometimes chosen when the optimizer wants to use pipelined hash joins, building hash tables from the entire right side before probing from the left.

**Bushy Tree** (used when multiple independent join paths exist):

```
Bushy Tree (e.g., for a query with independent sub-joins):

      JOIN (final result)
     /         \
  JOIN           JOIN
 /    \         /    \
A       B      C       D

Execution order:
  (1) Join A with B  → result AB  (in parallel with step 2)
  (2) Join C with D  → result CD  (in parallel with step 1)
  (3) Join AB with CD → final result
```

A bushy tree allows independent joins to be executed in parallel, which is why it is favored in systems that support parallel query execution. For our four-table query with a strict chain relationship (`A→B→C→D`), the bushy tree is less natural, but it can appear when there are no dependencies between the join branches.

For our query, the optimizer will almost certainly choose the **left-deep tree**, because the tables form a natural chain: orders reference customers, items reference orders, products are referenced by items. There is no meaningful way to join C and D before joining B and C, since `product_id` in C must have come from the join with B (to know which order's items we care about after the `WHERE b.status = 'SHIPPED'` filter).

## 5. Step-by-Step: How A → B → C → D Is Executed

Now let us trace the complete execution of our query, row by row, through all three binary join operations.

---

### 5.1 Step 1: Joining A and B → Intermediate Result AB

The engine begins by joining `customers` (A) and `orders` (B) on the condition `a.customer_id = b.customer_id`.

```
INPUT — Table A (customers):                INPUT — Table B (orders):
+----+---------------+---------+            +------+----+------------+----------+
| id | name          | country |            |oid   | id | order_date | status   |
+----+---------------+---------+            +------+----+------------+----------+
|  1 | Alice Corp    | USA     |            | 1001 |  1 | 2024-01-10 | SHIPPED  |
|  2 | Bob Ltd       | UK      |            | 1002 |  1 | 2024-02-15 | PENDING  |
|  3 | Carol Inc     | USA     |            | 1003 |  2 | 2024-01-20 | SHIPPED  |
+----+---------------+---------+            | 1004 |  3 | 2024-03-01 | SHIPPED  |
                                            +------+----+------------+----------+

JOIN CONDITION: a.customer_id = b.customer_id
ADDITIONAL FILTER: b.status = 'SHIPPED' (applied by optimizer at this step)

How the engine finds matches (Hash Join assumed):

  BUILD PHASE — smaller table A becomes the hash table:
  ┌────────────────────────────────────────────────────────┐
  │  Hash Table (keyed on customer_id from A):            │
  │  hash(1) → bucket_01 → [Alice Corp, USA]              │
  │  hash(2) → bucket_07 → [Bob Ltd, UK]                  │
  │  hash(3) → bucket_07 → [Carol Inc, USA] (chained)     │
  └────────────────────────────────────────────────────────┘

  PROBE PHASE — scan table B, probe the hash table:
  Row (1001, cust=1, SHIPPED):
      hash(1) → bucket_01 → finds Alice Corp → MATCH
      status='SHIPPED' → KEEP
      → Emit row: (Alice Corp, USA, 1001, 2024-01-10, SHIPPED)

  Row (1002, cust=1, PENDING):
      hash(1) → bucket_01 → finds Alice Corp → MATCH
      status='PENDING' → FILTERED OUT by WHERE clause
      → Discard

  Row (1003, cust=2, SHIPPED):
      hash(2) → bucket_07 → finds Bob Ltd → MATCH
      status='SHIPPED' → KEEP
      → Emit row: (Bob Ltd, UK, 1003, 2024-01-20, SHIPPED)

  Row (1004, cust=3, SHIPPED):
      hash(3) → bucket_07 → finds Carol Inc → MATCH
      status='SHIPPED' → KEEP
      → Emit row: (Carol Inc, USA, 1004, 2024-03-01, SHIPPED)
```

The output of Step 1 is **Intermediate Result AB** — a virtual table that exists in memory (or a temporary buffer). Notice that order 1002 (PENDING) was eliminated here by the optimizer pushing the `WHERE b.status = 'SHIPPED'` filter down to this early join stage. This is called **predicate pushdown**, and it is one of the most important optimizer techniques: filter as early as possible to reduce the size of intermediate result sets.

```
INTERMEDIATE RESULT AB (3 rows, down from 4 orders):
+---------------+---------+----------+------------+----------+
| customer_name | country | order_id | order_date | status   |
+---------------+---------+----------+------------+----------+
| Alice Corp    | USA     |   1001   | 2024-01-10 | SHIPPED  |
| Bob Ltd       | UK      |   1003   | 2024-01-20 | SHIPPED  |
| Carol Inc     | USA     |   1004   | 2024-03-01 | SHIPPED  |
+---------------+---------+----------+------------+----------+
```

This intermediate result exists nowhere on disk. It lives in memory, and the engine immediately uses it as the left input of the next join.

### 5.2 Step 2: Joining AB with C → Intermediate Result ABC

Now the engine takes the 3-row intermediate result AB and joins it with `order_items` (C) on the condition `b.order_id = c.order_id`.

```
LEFT INPUT — Intermediate Result AB:        RIGHT INPUT — Table C (order_items):
+----------+---------+                      +---------+----------+------------+----------+----------+
| order_id | cust... |                      | item_id | order_id | product_id | quantity | price    |
+----------+---------+                      +---------+----------+------------+----------+----------+
|   1001   | Alice.. |                      |    1    |   1001   |    501     |    2     |  50.00   |
|   1003   | Bob...  |                      |    2    |   1001   |    502     |    1     | 120.00   |
|   1004   | Carol.. |                      |    3    |   1002   |    501     |    3     |  50.00   |
+----------+---------+                      |    4    |   1003   |    503     |    5     |  30.00   |
                                            |    5    |   1004   |    502     |    2     | 120.00   |
                                            +---------+----------+------------+----------+----------+

JOIN CONDITION: AB.order_id = C.order_id

How the engine finds matches:
(Optimizer may choose Hash Join again, or Nested Loop if AB is small enough
 and C has an index on order_id)

  Strategy: Hash Join — build on smaller left input (AB, 3 rows):
  ┌─────────────────────────────────────────────────────────────────┐
  │  Hash Table (keyed on order_id from AB):                       │
  │  hash(1001) → bucket_X → [Alice Corp, USA, 2024-01-10,...]    │
  │  hash(1003) → bucket_Y → [Bob Ltd, UK, 2024-01-20,...]        │
  │  hash(1004) → bucket_Z → [Carol Inc, USA, 2024-03-01,...]     │
  └─────────────────────────────────────────────────────────────────┘

  PROBE PHASE — scan table C, probe the hash table:

  Item (1, order=1001, prod=501, qty=2, price=50.00):
      hash(1001) → bucket_X → finds Alice Corp row → MATCH
      → Emit: (Alice Corp, USA, 1001, 2024-01-10, 1, 501, 2, 50.00)

  Item (2, order=1001, prod=502, qty=1, price=120.00):
      hash(1001) → bucket_X → finds Alice Corp row → MATCH
      → Emit: (Alice Corp, USA, 1001, 2024-01-10, 2, 502, 1, 120.00)

  Item (3, order=1002, prod=501, qty=3, price=50.00):
      hash(1002) → no bucket entry → NO MATCH
      → Order 1002 was filtered out in Step 1! Discarded.

  Item (4, order=1003, prod=503, qty=5, price=30.00):
      hash(1003) → bucket_Y → finds Bob Ltd row → MATCH
      → Emit: (Bob Ltd, UK, 1003, 2024-01-20, 4, 503, 5, 30.00)

  Item (5, order=1004, prod=502, qty=2, price=120.00):
      hash(1004) → bucket_Z → finds Carol Inc row → MATCH
      → Emit: (Carol Inc, USA, 1004, 2024-03-01, 5, 502, 2, 120.00)
```

Notice something crucial here: Item 3 (for order 1002) was silently discarded because order 1002 was already filtered out by the `WHERE status = 'SHIPPED'` in Step 1. The hash table in Step 2 contains no entry for order 1002, so item 3 simply finds no match and is dropped. This is the cascade effect of predicate pushdown — a filter applied early cascades its eliminating effect through all subsequent joins.

```
INTERMEDIATE RESULT ABC (4 rows):
+---------------+----------+----------+------------+----------+------------+
| customer_name | order_id | order_dt | product_id | quantity | unit_price |
+---------------+----------+----------+------------+----------+------------+
| Alice Corp    |   1001   |2024-01-10|    501     |    2     |   50.00    |
| Alice Corp    |   1001   |2024-01-10|    502     |    1     |  120.00    |
| Bob Ltd       |   1003   |2024-01-20|    503     |    5     |   30.00    |
| Carol Inc     |   1004   |2024-03-01|    502     |    2     |  120.00    |
+---------------+----------+----------+------------+----------+------------+
```

Alice Corp now appears twice — once for each item in her order 1001. This is the natural one-to-many expansion that occurs when joining a table with multiple matching rows on the right side.

### 5.3 Step 3: Joining ABC with D → Final Result ABCD

The engine takes the 4-row intermediate result ABC and joins it with `products` (D) on the condition `c.product_id = d.product_id`.

```
LEFT INPUT — Intermediate Result ABC:       RIGHT INPUT — Table D (products):
+----+----------+------------+              +------------+--------------+----------+----------+
|....| product_id| quantity  |              | product_id | product_name | category | cost     |
+----+----------+------------+              +------------+--------------+----------+----------+
|....| 501      |    2       |              |    501     | Widget Alpha | Electron | 35.00    |
|....| 502      |    1       |              |    502     | Widget Beta  | Electron | 80.00    |
|....| 503      |    5       |              |    503     | Gadget Pro   | Gadgets  | 20.00    |
|....| 502      |    2       |              |    504     | Gadget Mini  | Gadgets  | 15.00    |
+----+----------+------------+              +------------+--------------+----------+----------+

JOIN CONDITION: ABC.product_id = D.product_id

  Strategy: Hash Join — build on D (right table, 4 rows):
  ┌───────────────────────────────────────────────────────────────┐
  │  Hash Table (keyed on product_id from D):                    │
  │  hash(501) → bucket_A → [Widget Alpha, Electronics, 35.00]  │
  │  hash(502) → bucket_B → [Widget Beta,  Electronics, 80.00]  │
  │  hash(503) → bucket_C → [Gadget Pro,   Gadgets,     20.00]  │
  │  hash(504) → bucket_D → [Gadget Mini,  Gadgets,     15.00]  │
  └───────────────────────────────────────────────────────────────┘

  PROBE PHASE — scan ABC rows, probe the hash table:

  Row 1 (Alice Corp, prod=501, qty=2, price=50.00):
      hash(501) → bucket_A → finds Widget Alpha → MATCH
      Compute: line_total = 2 × 50.00 = 100.00
      Compute: profit     = 100.00 - (2 × 35.00) = 30.00
      → FINAL ROW EMITTED

  Row 2 (Alice Corp, prod=502, qty=1, price=120.00):
      hash(502) → bucket_B → finds Widget Beta → MATCH
      Compute: line_total = 1 × 120.00 = 120.00
      Compute: profit     = 120.00 - (1 × 80.00) = 40.00
      → FINAL ROW EMITTED

  Row 3 (Bob Ltd, prod=503, qty=5, price=30.00):
      hash(503) → bucket_C → finds Gadget Pro → MATCH
      Compute: line_total = 5 × 30.00 = 150.00
      Compute: profit     = 150.00 - (5 × 20.00) = 50.00
      → FINAL ROW EMITTED

  Row 4 (Carol Inc, prod=502, qty=2, price=120.00):
      hash(502) → bucket_B → finds Widget Beta → MATCH
      Compute: line_total = 2 × 120.00 = 240.00
      Compute: profit     = 240.00 - (2 × 80.00) = 80.00
      → FINAL ROW EMITTED

  Product 504 (Gadget Mini) — hash bucket_D is never probed.
  It exists in the hash table but no ABC row has product_id=504.
  It is silently excluded (INNER JOIN behavior).
```

The final result:

```
FINAL RESULT — ABCD (4 rows, returned to client):
+---------------+----------+------------+----------+----------+--------------+----------+------------+--------+
| customer_name | order_id | order_date | quantity | unit_price| product_name | category | line_total | profit |
+---------------+----------+------------+----------+----------+--------------+----------+------------+--------+
| Alice Corp    |   1001   | 2024-01-10 |    2     |  50.00   | Widget Alpha | Electron |  100.00   |  30.00 |
| Alice Corp    |   1001   | 2024-01-10 |    1     | 120.00   | Widget Beta  | Electron |  120.00   |  40.00 |
| Bob Ltd       |   1003   | 2024-01-20 |    5     |  30.00   | Gadget Pro   | Gadgets  |  150.00   |  50.00 |
| Carol Inc     |   1004   | 2024-03-01 |    2     | 120.00   | Widget Beta  | Electron |  240.00   |  80.00 |
+---------------+----------+------------+----------+----------+--------------+----------+------------+--------+
```

## 6. How Rows Are Matched — The Physical Comparison Process

The previous section showed *what* happens at each step in abstract terms. Now let us go even deeper and look at the *mechanical process* by which each join algorithm actually compares rows to determine a match.

---

### 6.1 Nested Loop: Row-by-Row Probing

The Nested Loop algorithm is the most intuitive to understand because it mirrors what you would do if you were solving the problem manually. Imagine you have two physical stacks of paper, each representing a table. You pick up the first sheet from the left stack, then you walk through every sheet in the right stack looking for one that matches. When you find a match, you staple them together and put the pair in a new "result" pile. Then you pick up the second sheet from the left stack and repeat the entire right-side walk. You continue until every sheet in the left stack has been compared against every sheet in the right stack.

```
Nested Loop — Matching A (3 rows) against B (4 rows):

OUTER LOOP (over every row in A):
|
+-- A-row: Alice Corp (customer_id=1)
|   |
|   INNER LOOP (over every row in B):
|   +-- B-row: order 1001 (customer_id=1)  -->  1 = 1  --> MATCH! Emit pair.
|   +-- B-row: order 1002 (customer_id=1)  -->  1 = 1  --> MATCH! Emit pair.
|   +-- B-row: order 1003 (customer_id=2)  -->  1 = 2  --> NO MATCH. Skip.
|   +-- B-row: order 1004 (customer_id=3)  -->  1 = 3  --> NO MATCH. Skip.
|
+-- A-row: Bob Ltd (customer_id=2)
|   |
|   INNER LOOP (over every row in B):
|   +-- B-row: order 1001 (customer_id=1)  -->  2 = 1  --> NO MATCH. Skip.
|   +-- B-row: order 1002 (customer_id=1)  -->  2 = 1  --> NO MATCH. Skip.
|   +-- B-row: order 1003 (customer_id=2)  -->  2 = 2  --> MATCH! Emit pair.
|   +-- B-row: order 1004 (customer_id=3)  -->  2 = 3  --> NO MATCH. Skip.
|
+-- A-row: Carol Inc (customer_id=3)
    |
    INNER LOOP (over every row in B):
    +-- B-row: order 1001 (customer_id=1)  -->  3 = 1  --> NO MATCH. Skip.
    +-- B-row: order 1002 (customer_id=1)  -->  3 = 1  --> NO MATCH. Skip.
    +-- B-row: order 1003 (customer_id=2)  -->  3 = 2  --> NO MATCH. Skip.
    +-- B-row: order 1004 (customer_id=3)  -->  3 = 3  --> MATCH! Emit pair.

Total comparisons performed: 3 × 4 = 12
Matches found: 4 (Alice×1001, Alice×1002, Bob×1003, Carol×1004)
```

When there is an **index** on the inner table's join column (`customer_id` in `orders`), the inner loop does not need to scan every row of B. Instead, it does a fast index lookup:

```
Index Nested Loop (with B-tree index on orders.customer_id):

OUTER LOOP (over every row in A):
|
+-- A-row: Alice Corp (customer_id=1)
|   INDEX LOOKUP: "Find all rows in B where customer_id = 1"
|   B-tree traversal: root → branch → leaf → [order 1001, order 1002]
|   → Emit pair with 1001. Emit pair with 1002.
|   Comparisons: O(log 4) ≈ 2  (not 4!)
|
+-- A-row: Bob Ltd (customer_id=2)
|   INDEX LOOKUP: customer_id = 2 → [order 1003]
|   → Emit pair with 1003.
|
+-- A-row: Carol Inc (customer_id=3)
    INDEX LOOKUP: customer_id = 3 → [order 1004]
    → Emit pair with 1004.

Total comparisons: 3 × O(log 4) ≈ 6   (vs 12 without index)
As B grows to 1,000,000 rows, this becomes: 3 × O(log 1M) ≈ 3 × 20 = 60
Without index it would be: 3 × 1,000,000 = 3,000,000
```

The index transforms an `O(m × n)` operation into `O(m × log n)` — a dramatic improvement when `n` (the inner table) is large.

---

### 6.2 Hash Join: Build and Probe

The Hash Join eliminates the repeated inner-table scan by converting one table into a random-access data structure — a hash table — that can answer the question "does a match for this key exist?" in approximately O(1) time.

The algorithm works in two distinct phases. In the **Build Phase**, the database reads the smaller of the two tables entirely into memory, running each row's join key through a hash function and storing the row in a bucket corresponding to its hash value. In the **Probe Phase**, the database reads the larger table row by row, computes the hash of each row's join key, and checks the corresponding bucket in the hash table for any matching rows.

```
Hash Join — Matching A (3 rows) against B (4 rows):

==== BUILD PHASE (read smaller table A into hash table) ====

Hash function: h(customer_id) % 4  (simplified; real hash functions are more complex)

Row: Alice Corp (customer_id=1)  → h(1) % 4 = 1 → bucket[1]
Row: Bob Ltd    (customer_id=2)  → h(2) % 4 = 2 → bucket[2]
Row: Carol Inc  (customer_id=3)  → h(3) % 4 = 3 → bucket[3]

Hash table state in memory:
┌───────────────────────────────────────────────────────────┐
│ bucket[0]: (empty)                                        │
│ bucket[1]: → [customer_id=1, "Alice Corp", "USA"]         │
│ bucket[2]: → [customer_id=2, "Bob Ltd",   "UK"]           │
│ bucket[3]: → [customer_id=3, "Carol Inc", "USA"]          │
└───────────────────────────────────────────────────────────┘
Build phase cost: 1 full scan of A (3 rows read)

==== PROBE PHASE (scan larger table B, probe hash table) ====

Row: order 1001 (customer_id=1)
  h(1) % 4 = 1 → check bucket[1]
  bucket[1] contains customer_id=1? YES
  Compare: 1 = 1 → EXACT MATCH
  Combine: (Alice Corp, USA) + (1001, 2024-01-10, SHIPPED) → emit row

Row: order 1002 (customer_id=1)
  h(1) % 4 = 1 → check bucket[1]
  bucket[1] contains customer_id=1? YES
  Compare: 1 = 1 → EXACT MATCH
  Combine: (Alice Corp, USA) + (1002, 2024-02-15, PENDING) → emit row

Row: order 1003 (customer_id=2)
  h(2) % 4 = 2 → check bucket[2]
  bucket[2] contains customer_id=2? YES
  Compare: 2 = 2 → EXACT MATCH
  Combine: (Bob Ltd, UK) + (1003, 2024-01-20, SHIPPED) → emit row

Row: order 1004 (customer_id=3)
  h(3) % 4 = 3 → check bucket[3]
  bucket[3] contains customer_id=3? YES
  Compare: 3 = 3 → EXACT MATCH
  Combine: (Carol Inc, USA) + (1004, 2024-03-01, SHIPPED) → emit row

Total meaningful comparisons: 4 (one per probe, O(1) each)
vs Nested Loop: 12 comparisons
```

**Hash Collisions** — when two different keys hash to the same bucket — are handled by chaining: each bucket is a linked list, so the engine checks each entry in the chain for an exact key match.

```
Hash Collision Example:
  If customer_id=1 and customer_id=5 both hash to bucket[1]:

  bucket[1]: → [cust_id=1, Alice Corp] → [cust_id=5, Eve Ltd] → NULL

  When probing with customer_id=5:
  h(5) % 4 = 1 → check bucket[1]
  First entry: cust_id=1, compare: 5 = 1? NO → follow chain
  Second entry: cust_id=5, compare: 5 = 5? YES → MATCH

  Collision adds O(chain_length) to lookup, but well-designed
  hash functions keep chains short (usually 1-2 entries).
```

### 6.3 Merge Join: Synchronized Scanning

The Merge Join is the most elegant of the three algorithms. It requires that both inputs be sorted on the join key, and then it advances two pointers through the sorted lists in lock-step — much like the merge step of merge sort. Because both inputs are sorted, any matching rows must be adjacent in their respective sorted sequences.

```
Merge Join — Matching A (sorted by customer_id) against B (sorted by customer_id):

Sorted A:                        Sorted B:
+-----------+----+               +------+----+
| Alice Corp|  1 |  ← ptr_A     | 1001 |  1 |  ← ptr_B
| Bob Ltd   |  2 |               | 1002 |  1 |
| Carol Inc |  3 |               | 1003 |  2 |
+-----------+----+               | 1004 |  3 |
                                 +------+----+

==== MERGE PHASE ====

Iteration 1:
  ptr_A points to Alice (cust_id=1)
  ptr_B points to order 1001 (cust_id=1)
  Compare: 1 = 1 → MATCH!
  Emit: (Alice Corp, 1001)
  But do NOT advance ptr_A yet! There may be more B rows with cust_id=1.
  Advance ptr_B only.

Iteration 2:
  ptr_A still at Alice (cust_id=1)
  ptr_B now at order 1002 (cust_id=1)
  Compare: 1 = 1 → MATCH!
  Emit: (Alice Corp, 1002)
  Advance ptr_B only.

Iteration 3:
  ptr_A still at Alice (cust_id=1)
  ptr_B now at order 1003 (cust_id=2)
  Compare: 1 < 2 → A is behind. Advance ptr_A.

Iteration 4:
  ptr_A now at Bob Ltd (cust_id=2)
  ptr_B still at order 1003 (cust_id=2)
  Compare: 2 = 2 → MATCH!
  Emit: (Bob Ltd, 1003)
  Advance ptr_B.

Iteration 5:
  ptr_A still at Bob Ltd (cust_id=2)
  ptr_B now at order 1004 (cust_id=3)
  Compare: 2 < 3 → A is behind. Advance ptr_A.

Iteration 6:
  ptr_A now at Carol Inc (cust_id=3)
  ptr_B still at order 1004 (cust_id=3)
  Compare: 3 = 3 → MATCH!
  Emit: (Carol Inc, 1004)
  Advance both (ptr_B at end; ptr_A can advance too).

ptr_B is exhausted. Join complete.

Total iterations: 6   (vs 12 for naive Nested Loop)
Each pointer moved forward only — no backtracking.
O(m + n) total work, assuming both are pre-sorted.
```

When both inputs are not pre-sorted, the engine must sort them first. Sorting costs `O(m log m)` and `O(n log n)`. The optimizer compares this combined cost against the cost of a Hash Join to decide which to use.

## 7. Mixed Algorithms in a Single Query

A real four-table query almost never uses the same algorithm for all three binary join steps. The optimizer evaluates each binary join independently and may choose a different algorithm for each one based on the characteristics of the inputs at that step.

```
Realistic Mixed-Algorithm Execution Plan for A → B → C → D:

Step 1: A JOIN B
  - A (customers): 3 rows, small
  - B (orders): 4 rows, small, has index on customer_id
  - Optimizer chooses: INDEX NESTED LOOP
    (A is tiny; index on B makes inner lookup O(log n))
    Cost estimate: very low

                  ↓
         Intermediate AB (3 rows)

Step 2: AB JOIN C
  - AB: 3 rows (tiny), just produced in memory
  - C (order_items): 10,000 rows, index on order_id
  - Optimizer chooses: INDEX NESTED LOOP
    (AB is tiny; each AB row probes C's index for its items)
    Cost estimate: 3 × O(log 10000) ≈ 3 × 13 = 39 index lookups

                  ↓
         Intermediate ABC (variable rows, likely small
         due to SHIPPED filter cascading)

Step 3: ABC JOIN D
  - ABC: maybe 400 rows in memory
  - D (products): 50,000 rows, index on product_id
  - Optimizer chooses: HASH JOIN
    (Build hash table from D — 50k rows — once;
    probe with each of the 400 ABC rows)
    OR: INDEX NESTED LOOP (if 400 probes × log(50k) < hash build cost)

                  ↓
         FINAL RESULT (returned to client)
```

This illustrates an important principle: **the optimizer reasons about each join stage separately**, using the estimated size of intermediate results to guide its choices. After Step 1 and Step 2, the intermediate result is small because the `WHERE b.status = 'SHIPPED'` filter was pushed down. A small intermediate result changes the calculus for Step 3 — a Nested Loop with index lookups becomes viable even against a large products table.

## 8. The Query Optimizer — Choosing the Join Order

The join order we have been following (`A → B → C → D`) is the one implied by the written order of the `JOIN` clauses in our SQL. However, the query optimizer is not obligated to follow this order. It has complete freedom to reorder the joins if it believes a different order will produce a faster result — as long as the final output is logically equivalent.

The optimizer's job is to find the join order (and algorithm choices) that minimize the total cost, typically measured in terms of disk I/O and CPU time. It does this by estimating the cost of many possible execution plans and selecting the cheapest one.

Consider the possible orderings of four tables:

```
Number of possible join orderings for N tables:
  N=2:  1   ordering
  N=3:  6   orderings (3! = 6)
  N=4:  24  orderings (4! = 24)
  N=5:  120 orderings
  N=8:  40,320 orderings
  N=10: 3,628,800 orderings

For complex queries with many joins, the optimizer uses heuristics
and dynamic programming (not brute-force) to find a good plan.
```

The optimizer uses **table statistics** — collected by commands like `ANALYZE` (PostgreSQL) or `UPDATE STATISTICS` (SQL Server) — to estimate the number of rows each table contains, the distribution of values in each column, and how selective each join condition is. These statistics allow it to estimate the size of each intermediate result set and thereby estimate the cost of each possible ordering.

```
How the Optimizer Reasons About Join Order:

Option 1: A → B → C → D  (the written order)
  After A→B: estimated 4 rows (1 customer has ~1.3 orders average)
  Apply SHIPPED filter: ≈ 3 rows
  After AB→C: ≈ 3 × 1.5 items/order ≈ 4.5 rows
  After ABC→D: ≈ 4.5 rows (1:1 match)
  Total intermediate rows generated: 4 + 4.5 + 4.5 ≈ 13 rows

Option 2: C → D → B → A  (start from the most selective filter)
  C has 5 rows. D has 4 rows.
  After C→D: 5 rows (each item matches a product)
  B (orders) with SHIPPED filter: reduces B first
  After filtered B → CD: matches order_ids → ≈ 4 rows
  After BCDA → A: ≈ 3 rows
  Total intermediate rows: 5 + 4 + 3 ≈ 12 rows

Option 3: Start with D (largest table, 50,000 rows)
  After D → C: 5 matches (C has only 5 rows)
  ...but reading all 50,000 rows of D first is expensive!

The optimizer weighs: smaller intermediate results = less memory,
less CPU. But it also considers index availability and algorithm
compatibility. Option 1 or 2 will likely win.
```

You can influence the optimizer's choices by:

- **Creating indexes** on join columns, which change the algorithm available (enabling Index Nested Loop)
- **Running `ANALYZE`** to refresh statistics so the optimizer has accurate row count estimates
- **Using hints** (in databases that support them, like Oracle's `/*+ USE_HASH(e d) */` or SQL Server's `OPTION (HASH JOIN)`) to force a specific algorithm
- **Rewriting the query** to make filters explicit and help the optimizer with predicate pushdown

## 9. How to Read the EXPLAIN Plan

The best way to verify and understand what the optimizer actually decided to do is to run `EXPLAIN` (or `EXPLAIN ANALYZE` for real execution stats) before your query. The output is a tree structure that maps directly to the join tree we have been discussing.

```sql
-- PostgreSQL
EXPLAIN ANALYZE
SELECT a.customer_name, b.order_id, c.quantity, d.product_name
FROM customers   a
JOIN orders      b ON a.customer_id = b.customer_id
JOIN order_items c ON b.order_id    = c.order_id
JOIN products    d ON c.product_id  = d.product_id
WHERE b.status = 'SHIPPED';
```

A typical output might look like:

```
EXPLAIN output (simplified):

Hash Join  (cost=... rows=4 ...)              ← Step 3: ABC JOIN D
  Hash Cond: (c.product_id = d.product_id)
  ->  Hash Join  (cost=... rows=4 ...)        ← Step 2: AB JOIN C
        Hash Cond: (b.order_id = c.order_id)
        ->  Hash Join  (cost=... rows=3 ...)  ← Step 1: A JOIN B
              Hash Cond: (a.customer_id = b.customer_id)
              ->  Seq Scan on customers a     ← Read all of A
              ->  Hash                        ← Build hash from B
                    ->  Seq Scan on orders b  ← Read B, apply filter
                          Filter: (b.status = 'SHIPPED')
        ->  Hash                              ← Build hash from C
              ->  Seq Scan on order_items c   ← Read all of C
  ->  Hash                                    ← Build hash from D
        ->  Seq Scan on products d            ← Read all of D
```

Reading this tree from the inside out gives you the execution order:

```
How to read the EXPLAIN tree (inside-out = execution order):

Deepest indent first:
  1. Seq Scan on customers    (read A)
  2. Seq Scan on orders       (read B, filter SHIPPED)
  3. Hash Join → A + B        = intermediate AB
  4. Seq Scan on order_items  (read C)
  5. Hash Join → AB + C       = intermediate ABC
  6. Seq Scan on products     (read D)
  7. Hash Join → ABC + D      = FINAL RESULT
```

Key terms you will encounter in EXPLAIN output:

```
+----------------------+-----------------------------------------------+
| Term in EXPLAIN      | What it means                                 |
+----------------------+-----------------------------------------------+
| Seq Scan             | Full sequential read of the table (no index)  |
| Index Scan           | Use B-tree index to find rows                 |
| Index Only Scan      | Entire answer found in the index itself       |
| Bitmap Index Scan    | Index used but rows fetched in heap order     |
| Hash Join            | Hash Join algorithm chosen                    |
| Nested Loop          | Nested Loop algorithm chosen                  |
| Merge Join           | Sort-Merge Join algorithm chosen              |
| Hash                 | A hash table is being built from this input   |
| Sort                 | The input is being sorted (for Merge Join)    |
| cost=X..Y            | X=startup cost, Y=total estimated cost        |
| rows=N               | Estimated number of rows produced             |
| actual rows=N        | (ANALYZE only) Real rows produced at runtime  |
| actual time=X..Y     | (ANALYZE only) Real execution time in ms      |
| Buffers: hit=N       | (ANALYZE) N pages found in the buffer cache   |
| Buffers: read=N      | (ANALYZE) N pages read from disk              |
+----------------------+-----------------------------------------------+
```

When `estimated rows` differ dramatically from `actual rows`, it means the optimizer's statistics are stale and it made a poor decision. Run `ANALYZE tablename` to update statistics and re-run `EXPLAIN` to see if the plan improves.

## 10. Summary — The Complete Mental Model

Let us now bring every concept together into one final, unified picture that you can carry in your mind every time you write a multi-table JOIN.

```
THE COMPLETE MENTAL MODEL for A JOIN B JOIN C JOIN D:

Your SQL Query
      |
      v
+------------------+
|  Query Parser    | Validates syntax, builds parse tree
+------------------+
      |
      v
+------------------+
|  Query Rewriter  | Applies view expansions, subquery unnesting
+------------------+
      |
      v
+------------------+
|  Query Optimizer | The critical phase:
|                  |   1. Enumerate possible join orderings
|                  |   2. Estimate cost of each using statistics
|                  |   3. Choose the cheapest join order
|                  |   4. Choose algorithm per join (NL/Hash/Merge)
|                  |   5. Apply predicate pushdown (filter early)
|                  |   6. Produce an execution plan (join tree)
+------------------+
      |
      v
+------------------+
| Execution Engine | Runs the plan, step by step:
|                  |
|  Step 1: A ⋈ B  |  Algorithm: NL/Hash/Merge
|        ↓         |  Output: Intermediate result AB (in memory)
|  Step 2: AB ⋈ C |  Algorithm: NL/Hash/Merge (may differ!)
|        ↓         |  Output: Intermediate result ABC (in memory)
|  Step 3: ABC ⋈ D|  Algorithm: NL/Hash/Merge (may differ again!)
|        ↓         |  Output: Final result set
+------------------+
      |
      v
+------------------+
|  Result Buffer   | ORDER BY, LIMIT applied here
+------------------+
      |
      v
   Client receives rows
```

Every join you write, no matter how many tables it involves, follows this pipeline. The database never joins all tables simultaneously — it always works in binary steps, one pair at a time, each intermediate result feeding the next stage. The optimizer tries to arrange those steps so that the most selective filters happen earliest, producing small intermediate results that keep the subsequent join steps fast and memory-efficient.

When you understand this model, you gain new intuition about performance:

- A query that joins in a poor order (starting with two large, unfiltered tables) can be one hundred times slower than the same query executed in the optimal order. Write your filters early and make sure indexes exist on join columns.

- A missing index on a join column forces a sequential scan of the entire inner table at every iteration of a Nested Loop, turning an `O(m × log n)` operation into `O(m × n)`. On large tables, this is the difference between milliseconds and hours.

- Stale statistics lead to poor plan choices. When the optimizer believes a table has 1,000 rows and it actually has 10,000,000, it will choose a Nested Loop where a Hash Join was needed. Regular `ANALYZE` keeps statistics fresh and plans optimal.

- The `EXPLAIN ANALYZE` command is the single most powerful diagnostic tool available to you. It tells you not just what the optimizer planned, but what actually happened — including where the plan was wrong and why.

---

*"A JOIN is a promise you make to the database. An execution plan is the database's answer to that promise — its best attempt, given what it knows, to fulfill your request as efficiently as possible."*
