# Schema-Level Performance — A Deep Study Guide

> *"Performance begins at design time, not at query time. The choices you make when defining a table — what data type to use for each column, whether to partition the table, how frequently to refresh the planner's statistics — are choices whose consequences compound silently for years. A column defined as TEXT when CHAR(2) would suffice wastes bytes on every row, in every index, and in every network packet for the lifetime of the system. A table that should have been partitioned but was not becomes progressively slower as its row count grows, until one day the weekly report that used to take 3 seconds takes 4 minutes — and the engineer who is called to fix it must choose between an expensive migration or an increasingly painful workaround. Schema-level performance is the discipline of making the right choices when it is still cheap to make them."*

Indexing gets all the attention. Query rewriting gets the sophisticated reputation. But some of the most durable and impactful performance improvements in database engineering come from decisions made at the schema level — decisions about data types, table structure, statistics, and physical organization. These decisions are made once, they rarely change, and their effects are felt in every single query the system executes. This chapter examines four of the most consequential schema-level performance tools: choosing data types correctly, using partitioning as a performance mechanism, understanding how the planner's statistics work and how to maintain them, and managing table bloat proactively.

## 1. Data Type Choices — Using the Smallest Correct Type

### Why Data Types Are a Performance Decision

The choice of data type for a column is not merely a semantic decision about what values the column holds — it is a performance decision with real, measurable consequences. Every row in a table is a physical sequence of bytes on disk. Every index entry is a copy of the indexed column's bytes. Every sort operation compares those bytes. Every network response transmits those bytes to the application. A column that stores a two-digit country code as `VARCHAR(255)` instead of `CHAR(2)` uses more storage per row, wastes space in every index on that column, requires more memory in `shared_buffers` to hold the same number of rows, and generates larger network payloads. At a billion rows, these differences become enormous.

Beyond storage size, the data type determines what operations the database can perform efficiently. Using an integer for a value that is always an integer allows the database to use integer comparison (one machine instruction). Using a string for that same value requires string comparison (multiple instructions, locale-aware, variable-length). Using `TEXT` for a value that should be a timestamp prevents index range scans using `BETWEEN` on date ranges. Type choices shape what indexes work, what comparisons are possible, and what query plans the optimizer can generate.

### Integer Types: Right-Sizing the Range

PostgreSQL and MySQL both offer multiple integer types. The choice between them should be driven by the range of values the column will hold — not by habit, laziness, or "just to be safe." Using `BIGINT` for a column that will never exceed 10,000 wastes 4 bytes per row compared to `SMALLINT`. At 100 million rows with an index, those 4 bytes become 800 MB of wasted disk space, 800 MB of wasted cache, and 800 MB of additional network I/O over the lifetime of the table.

```

  PostgreSQL / MySQL:

  │              │           │                                        │ ratings   │
  ├──────────────┼───────────┼────────────────────────────────────────┼───────────┤

  │              │           │                                        │ counts    │
  ├──────────────┼───────────┼────────────────────────────────────────┼───────────┤

    String comparison is slower than integer comparison for every WHERE clause.
```

### Character Types: CHAR vs VARCHAR vs TEXT

The three character types in PostgreSQL behave differently in storage and comparison, and choosing correctly matters for both correctness and performance.

`CHAR(n)` — fixed-length character string, always stored as exactly n characters (padded with spaces if shorter). Because every value has the same length, comparison is very fast (compare fixed-length buffers). Appropriate for codes with exactly fixed length: country codes (`CHAR(2)`), currency codes (`CHAR(3)`), status codes of fixed width.

`VARCHAR(n)` — variable-length string, up to n characters. The database stores only as many characters as the value actually contains (plus a 1-4 byte length header). No padding. For most string data that has a meaningful maximum length (email addresses, names), `VARCHAR(n)` is appropriate.

`TEXT` — variable-length string with no limit. In PostgreSQL, `TEXT` and `VARCHAR` with no limit are functionally identical in storage and performance — the difference is purely semantic. However, using `TEXT` for a column that should have a meaningful length limit removes a database-level constraint, allowing garbage data to accumulate.

```
  CHARACTER TYPE STORAGE AND PERFORMANCE

  ┌──────────────┬───────────────────────────────────────────────────────┐
  │ Type         │ Storage                                               │
  ├──────────────┼───────────────────────────────────────────────────────┤
  │ CHAR(n)      │ Exactly n bytes (padded with spaces). Stored inline.  │
  │              │ For n > 2000 bytes: stored out-of-line (TOAST).       │
  ├──────────────┼───────────────────────────────────────────────────────┤
  │ VARCHAR(n)   │ 1-4 byte length header + actual content bytes.        │
  │              │ Only stores what is actually in the value.            │
  ├──────────────┼───────────────────────────────────────────────────────┤
  │ TEXT         │ Same physical storage as VARCHAR. No performance       │
  │              │ difference vs VARCHAR in PostgreSQL.                  │
  │              │ In MySQL: TEXT is stored out-of-line; use VARCHAR.    │
  └──────────────┴───────────────────────────────────────────────────────┘

  EXAMPLES OF CORRECT CHOICES:

  country_code   CHAR(2)          -- Always exactly 2 characters (ISO 3166)
  currency_code  CHAR(3)          -- Always exactly 3 characters (ISO 4217)
  phone_number   VARCHAR(20)      -- Varies, but bounded
  email          VARCHAR(320)     -- Maximum email length per RFC 5321
  description    TEXT             -- Genuinely unbounded long text
  status         SMALLINT         -- Use integer + lookup table, not VARCHAR
  zip_code       CHAR(10)         -- Fixed format (e.g., US ZIP+4: '12345-6789')

  CRITICAL MISTAKE: Using VARCHAR(255) everywhere as a default
  -- VARCHAR(255) is chosen because 255 is a "safe big number."
  -- It provides no performance benefit over VARCHAR(50) for values
  -- that will never exceed 50 characters.
  -- BUT: CHAR(2) IS faster than VARCHAR(2) for fixed-length codes
  --      because CHAR avoids the length header overhead.
  -- For index-heavy columns with short, fixed-length values: use CHAR(n).

  -- In MySQL specifically: VARCHAR vs TEXT has a performance difference.
  -- VARCHAR: stored inline in the row (up to 65,535 bytes).
  -- TEXT:    stored out-of-line (pointer in row, data in separate page).
  -- Out-of-line storage requires an extra I/O read per row for TEXT columns.
  -- Use VARCHAR for columns < 64KB that need to be frequently read.
  -- Use TEXT only for genuinely large text (articles, descriptions).
```

### Numeric Types: Precision vs Performance

The choice between exact numeric types (`NUMERIC`/`DECIMAL`) and floating-point types (`FLOAT`/`DOUBLE PRECISION`) is one of the most consequential and most frequently made incorrectly.

`NUMERIC(precision, scale)` stores exact decimal values. It is implemented in software (no CPU hardware instruction), making arithmetic operations 5-20× slower than floating-point. But it never accumulates rounding error — `0.1 + 0.2 = 0.3` exactly. This is mandatory for money, financial calculations, and anything where exactness is a business requirement.

`FLOAT` and `DOUBLE PRECISION` use the CPU's hardware floating-point unit — operations are single-instruction and extremely fast. But they accumulate rounding error: `0.1 + 0.2 = 0.30000000000000004` in IEEE 754. Acceptable for scientific measurements, statistics, and calculations where small rounding errors are irrelevant.

```
  NUMERIC vs FLOAT: WHEN TO USE EACH

  ┌───────────────────┬──────────────────┬──────────────────────────────┐
  │ Type              │ Storage          │ Use for                      │
  ├───────────────────┼──────────────────┼──────────────────────────────┤
  │ NUMERIC(10,2)     │ Variable:        │ MONEY, financial amounts,    │
  │ DECIMAL(10,2)     │ ~10 bytes for    │ tax rates, prices,           │
  │                   │ 10-digit value   │ ANY calculation where        │
  │                   │                  │ exactness is required.       │
  │                   │ SLOW: software   │                              │
  │                   │ arithmetic       │                              │
  ├───────────────────┼──────────────────┼──────────────────────────────┤
  │ REAL              │ 4 bytes          │ Scientific measurements,     │
  │ (FLOAT4)          │ FAST: hardware   │ statistics, ML features,     │
  │                   │ arithmetic       │ GPS coordinates (with care)  │
  ├───────────────────┼──────────────────┼──────────────────────────────┤
  │ DOUBLE PRECISION  │ 8 bytes          │ Higher-precision float:      │
  │ (FLOAT8)          │ FAST: hardware   │ scientific, geospatial,      │
  │                   │ arithmetic       │ time-series sensor data      │
  ├───────────────────┼──────────────────┼──────────────────────────────┤
  │ MONEY             │ 8 bytes          │ Avoid in PostgreSQL —        │
  │ (PostgreSQL)      │                  │ locale-dependent, hard to    │
  │                   │                  │ exchange across systems.     │
  │                   │                  │ Use NUMERIC(19,4) instead.  │
  └───────────────────┴──────────────────┴──────────────────────────────┘

  CRITICAL RULE: Never store money as FLOAT.
  Example of the float money disaster:
  SELECT 0.1::FLOAT + 0.2::FLOAT;
  → 0.30000000000000004  (not 0.30!)
  If 10 million such transactions accumulate: total errors add up.

  Correct for money:
  price   NUMERIC(19, 4)  -- Up to 15 digits before decimal, 4 after
  tax     NUMERIC(10, 6)  -- Tax rates need more precision
  amount  NUMERIC(19, 4)  -- Financial transfer amounts
```

### Timestamp and Date Types

Time-related columns are a frequent source of both correctness bugs and performance problems when the wrong type is chosen.

```
  TIMESTAMP TYPE COMPARISON (PostgreSQL)

  ┌─────────────────────────┬──────────┬──────────────────────────────────────┐
  │ Type                    │ Storage  │ Behavior                             │
  ├─────────────────────────┼──────────┼──────────────────────────────────────┤
  │ TIMESTAMPTZ             │ 8 bytes  │ Stores UTC internally. Displays in   │
  │ (timestamp with TZ)     │          │ session's timezone. ALWAYS use this  │
  │                         │          │ for event times, created_at, etc.    │
  ├─────────────────────────┼──────────┼──────────────────────────────────────┤
  │ TIMESTAMP               │ 8 bytes  │ No timezone info. Stores the literal │
  │ (without TZ)            │          │ value as-is. Dangerous for global    │
  │                         │          │ systems — 2024-03-01 12:00:00 means  │
  │                         │          │ different things in different places. │
  ├─────────────────────────┼──────────┼──────────────────────────────────────┤
  │ DATE                    │ 4 bytes  │ Date only (no time). For birthdays,  │
  │                         │          │ reporting periods, financial dates.  │
  ├─────────────────────────┼──────────┼──────────────────────────────────────┤
  │ TIME WITH TZ            │ 12 bytes │ Rarely correct. Avoid.               │
  ├─────────────────────────┼──────────┼──────────────────────────────────────┤
  │ INTERVAL                │ 16 bytes │ Duration between timestamps. Use for │
  │                         │          │ durations, not for storing start+end.│
  └─────────────────────────┴──────────┴──────────────────────────────────────┘

  -- CRITICAL RULE: Always use TIMESTAMPTZ for event timestamps.
  -- Using TIMESTAMP (no TZ) in a global system causes silent bugs:
  -- An event recorded as '2024-03-15 08:00:00' by a server in Dhaka
  -- and queried by an application in London will be interpreted
  -- incorrectly unless both always agree on the implicit timezone.

  -- Performance: TIMESTAMPTZ and TIMESTAMP have identical storage (8 bytes)
  -- and identical index performance. Choose TIMESTAMPTZ for correctness,
  -- not for performance — they are equivalent in that dimension.

  -- UNIX epoch integers (INT or BIGINT) for timestamps:
  -- Occasionally seen in legacy systems. Avoid in new designs.
  -- Cannot use date functions directly. Cannot index date ranges
  -- without conversion. Cannot be read by humans in pg_dump output.
  -- No benefit over TIMESTAMPTZ in PostgreSQL.

  -- Practical: storing only the date (no time) for birthday, hire date:
  birth_date  DATE      -- 4 bytes, correct for date-only values
  -- vs. the mistake:
  birth_date  TIMESTAMPTZ  -- 8 bytes, stores midnight unnecessarily
```

### UUID vs BIGSERIAL: Primary Key Type Choice

The choice of primary key data type is one of the most impactful schema-level performance decisions, because the primary key appears in every secondary index as a pointer and in every foreign key in child tables.

```
  PRIMARY KEY TYPE COMPARISON

  BIGSERIAL (8-byte integer, sequential):
  ┌─────────────────────────────────────────────────────────────────┐
  │ Pros:                                                           │
  │ + 8 bytes (vs 16 bytes for UUID) → smaller indexes, less I/O   │
  │ + Sequential: new rows insert at the end of the B-tree index    │
  │   → no index page splits (hot-spot inserts are efficient)       │
  │ + Human-readable (easier to debug, log, discuss with team)      │
  │ + Sortable by default (ORDER BY id = chronological order)       │
  │                                                                 │
  │ Cons:                                                           │
  │ - Predictable (enumerable): id=1, id=2 exposes business metrics │
  │ - Requires a single sequence generator → potential bottleneck   │
  │   in distributed, multi-master write scenarios                  │
  └─────────────────────────────────────────────────────────────────┘

  UUID v4 (16-byte random identifier):
  ┌─────────────────────────────────────────────────────────────────┐
  │ Pros:                                                           │
  │ + Globally unique without coordination between systems          │
  │ + Safe to generate client-side (no server round-trip needed)    │
  │ + Not enumerable (hides business information from URLs)         │
  │                                                                 │
  │ Cons:                                                           │
  │ - 16 bytes: indexes are 2× the size of BIGSERIAL indexes        │
  │ - RANDOM insertion order: every INSERT causes index page splits  │
  │   (the new UUID is scattered randomly across the B-tree)        │
  │   → "Index bloat from fragmentation" → 30-60% larger indexes    │
  │   → More I/O for index maintenance                              │
  │ - Not human-readable                                            │
  └─────────────────────────────────────────────────────────────────┘

  UUID v7 (16-byte time-ordered identifier — PostgreSQL 17+ native):
  ┌─────────────────────────────────────────────────────────────────┐
  │ Pros:                                                           │
  │ + Globally unique (same benefit as v4)                          │
  │ + TIME-ORDERED: new UUIDs are monotonically increasing in time  │
  │   → Sequential-like insertion into B-tree → no random splits    │
  │   → Index performance close to BIGSERIAL                        │
  │ + Embeds timestamp → can extract creation time from the UUID    │
  │                                                                 │
  │ Cons:                                                           │
  │ - Still 16 bytes (2× BIGSERIAL)                                 │
  │ - Not yet universally supported (use gen_random_uuid() for v4;  │
  │   uuidv7() available in PostgreSQL 17+, or use extension)       │
  └─────────────────────────────────────────────────────────────────┘

  RECOMMENDATION:
  → Single-database OLTP system: BIGSERIAL (best performance)
  → Multi-service / microservices needing client-generated IDs: UUID v7
  → Never use UUID v4 for a high-write table's primary key if performance
    matters — the random index fragmentation is a silent killer.

  -- PostgreSQL: generate UUID v7 (available PG 17+):
  SELECT uuidv7();  -- e.g., '018e4a00-7e5c-7000-a123-456789abcdef'
  -- First 48 bits = millisecond timestamp → monotonic ordering

  -- For PG < 17, use pg_uuidv7 extension:
  -- CREATE EXTENSION pg_uuidv7;
  -- SELECT uuid_generate_v7();
```

### Boolean and Enumeration Types

```sql
  -- BOOLEAN: always use boolean instead of SMALLINT or CHAR(1) for flags
  is_active   BOOLEAN NOT NULL DEFAULT TRUE   -- 1 byte, semantically clear
  -- vs wrong:
  is_active   SMALLINT  -- 2 bytes, allows values other than 0/1 (data integrity risk)
  is_active   CHAR(1)   -- 'Y'/'N' values require application-level mapping

  -- CHECK constraint for enumerated values (prefer over VARCHAR for small enums):
  status      SMALLINT NOT NULL
              CHECK (status IN (1, 2, 3, 4, 5))  -- constrained at DB level
  -- For human-readable status: use a lookup table + FK + SMALLINT, not VARCHAR

  -- PostgreSQL ENUM type: creates a named type with allowed values
  CREATE TYPE order_status AS ENUM ('pending', 'confirmed', 'shipped', 'delivered', 'cancelled');
  ALTER TABLE orders ADD COLUMN status order_status NOT NULL DEFAULT 'pending';

  -- ENUM pros: type-safe, compact storage (4 bytes), readable, constraint-enforced
  -- ENUM cons: adding a new value requires ALTER TYPE (fast in PG 9.1+, but is DDL)
  -- For stable, small sets of values (< 20): ENUM is excellent
  -- For frequently-changing sets: lookup table + FK is more flexible
```

## 2. Partitioning as a Performance Tool

### What Partitioning Is and Why It Exists

**Partitioning** is the division of a single logical table into multiple physical pieces called **partitions**, each storing a subset of the table's rows. From the application's perspective, the partitioned table looks and behaves like a single table — queries are written against it as normal, and the database routes rows to the correct partition transparently. But physically, each partition is a separate file on disk with its own heap pages, its own indexes, and its own autovacuum lifecycle.

Partitioning is a performance tool for tables that suffer from one or more of three specific problems: they are too large to fit their hot working set in memory (so queries scan pages unnecessarily), they accumulate historical data that is rarely queried but degrades the performance of current-data queries, or they have so many dead tuples from frequent updates that autovacuum cannot keep up. Partitioning is not a universal optimization — it introduces overhead for queries that span partitions, adds planning complexity, and complicates some operations. Used for the right problems, it is transformative. Used indiscriminately, it harms performance.

### Partition Pruning: The Core Performance Mechanism

The reason partitioning improves query performance is **partition pruning** — the query planner's ability to eliminate entire partitions from consideration before the query even begins. If a table is partitioned by `created_at` month, and a query filters `WHERE created_at >= '2024-03-01' AND created_at < '2024-04-01'`, the planner knows that only the March 2024 partition can possibly contain matching rows. It accesses only that partition, completely ignoring all other partitions. For a table with 5 years of monthly partitions (60 partitions), a single-month query accesses 1/60th of the data — a 60× reduction in I/O.

```
  PARTITION PRUNING IN ACTION

  orders table: 600 million rows over 5 years
  Partitioned by: RANGE on created_at (monthly partitions = 60 partitions)

  Without partitioning:
  SELECT * FROM orders WHERE created_at >= '2024-03-01' AND created_at < '2024-04-01';
  → Sequential Scan on orders (600M rows) → reads entire 480 GB table
  → Execution time: minutes

  With monthly partitions:
  SELECT * FROM orders WHERE created_at >= '2024-03-01' AND created_at < '2024-04-01';
  → Planner: "Only orders_y2024m03 partition can match this WHERE clause"
  → Sequential Scan on orders_y2024m03 (10M rows, 8 GB)
  → Execution time: seconds
  → 60× less data read!

  Partition pruning visualization:

  ┌──────────────────────────────────────────────────────────────────┐
  │ orders (partitioned table — logical view)                         │
  ├────────────┬────────────┬────────────┬─────────────┬────────────┤
  │ 2020-01    │ 2020-02    │ ...        │ 2024-03     │ 2024-04    │
  │ EXCLUDED   │ EXCLUDED   │ EXCLUDED   │ ▼ SCANNED   │ EXCLUDED   │
  │ by pruning │ by pruning │ by pruning │ (matches    │ by pruning │
  │            │            │            │  WHERE)     │            │
  └────────────┴────────────┴────────────┴─────────────┴────────────┘

  KEY REQUIREMENT for pruning: the partition key MUST appear in the
  WHERE clause with a literal or parameter value (not a function result
  on the column). The planner must be able to statically determine
  which partitions to access at plan time.

  Pruning-friendly:    WHERE created_at >= '2024-03-01'   ← literal ✓
  Pruning-unfriendly:  WHERE DATE(created_at) = '2024-03-01'  ← function ✗
                       (planner cannot determine which partitions to skip)
```

### Partition Types in PostgreSQL

PostgreSQL supports three partitioning strategies, each suited to different data distributions and access patterns.

**RANGE Partitioning** divides rows by a range of values in one or more columns — most commonly a date or timestamp column. It is the most widely used strategy for time-series data, log tables, audit tables, and any table where data has a natural time dimension. New rows always go to the most recent partition. Old partitions are rarely touched. Queries filtered by date benefit dramatically from pruning.

**LIST Partitioning** divides rows by specific values of a column — for example, partitioning a multi-tenant table by `tenant_id`, or an international table by `country_code`. Queries filtered by the partition key (specific tenant or country) access only the relevant partition.

**HASH Partitioning** divides rows by computing a hash of the partition key column, distributing rows evenly across a fixed number of partitions. It does not provide partition pruning for range or equality queries (because the hash function distributes values unpredictably), but it is useful for distributing data and index load evenly — reducing index contention on high-write tables and allowing parallel query execution across partitions.

```sql
  -- ─────────────────────────────────────────────────────────────────
  -- RANGE PARTITIONING: time-series data (most common)
  -- ─────────────────────────────────────────────────────────────────
  CREATE TABLE orders (
      id          BIGSERIAL,
      customer_id BIGINT       NOT NULL,
      total       NUMERIC(19,4) NOT NULL,
      status      SMALLINT     NOT NULL,
      created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()
  ) PARTITION BY RANGE (created_at);

  -- Create monthly partitions:
  CREATE TABLE orders_y2024m01 PARTITION OF orders
      FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

  CREATE TABLE orders_y2024m02 PARTITION OF orders
      FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

  CREATE TABLE orders_y2024m03 PARTITION OF orders
      FOR VALUES FROM ('2024-03-01') TO ('2024-04-01');

  -- Each partition has its own indexes:
  CREATE INDEX ON orders_y2024m01 (customer_id, created_at);
  CREATE INDEX ON orders_y2024m02 (customer_id, created_at);
  CREATE INDEX ON orders_y2024m03 (customer_id, created_at);
  -- PostgreSQL 11+: create indexes on the parent → automatically created on all partitions
  CREATE INDEX ON orders (customer_id, created_at);  -- propagates to all existing and future partitions

  -- Automate partition creation (pg_partman extension):
  -- SELECT partman.create_parent('public.orders', 'created_at', 'range', 'monthly');
  -- This automatically creates new partitions and manages retention.

  -- ─────────────────────────────────────────────────────────────────
  -- LIST PARTITIONING: multi-tenant data
  -- ─────────────────────────────────────────────────────────────────
  CREATE TABLE events (
      id          BIGSERIAL,
      tenant_id   INTEGER      NOT NULL,
      event_type  VARCHAR(50)  NOT NULL,
      payload     JSONB,
      created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()
  ) PARTITION BY LIST (tenant_id);

  CREATE TABLE events_tenant_1 PARTITION OF events FOR VALUES IN (1);
  CREATE TABLE events_tenant_2 PARTITION OF events FOR VALUES IN (2);
  CREATE TABLE events_tenant_3 PARTITION OF events FOR VALUES IN (3);
  -- Default partition: catch-all for new tenants before their partition is created
  CREATE TABLE events_default  PARTITION OF events DEFAULT;

  -- Tenant-specific query: accesses only events_tenant_1
  SELECT * FROM events WHERE tenant_id = 1 AND created_at > NOW() - INTERVAL '1 day';
  -- EXPLAIN: Seq Scan on events_tenant_1 (partitions 2 and 3 pruned)

  -- ─────────────────────────────────────────────────────────────────
  -- HASH PARTITIONING: even distribution for write-heavy tables
  -- ─────────────────────────────────────────────────────────────────
  CREATE TABLE sessions (
      id           UUID         NOT NULL DEFAULT gen_random_uuid(),
      user_id      BIGINT       NOT NULL,
      session_data JSONB,
      expires_at   TIMESTAMPTZ  NOT NULL
  ) PARTITION BY HASH (user_id);

  -- 8 partitions for even distribution:
  CREATE TABLE sessions_p0 PARTITION OF sessions FOR VALUES WITH (MODULUS 8, REMAINDER 0);
  CREATE TABLE sessions_p1 PARTITION OF sessions FOR VALUES WITH (MODULUS 8, REMAINDER 1);
  CREATE TABLE sessions_p2 PARTITION OF sessions FOR VALUES WITH (MODULUS 8, REMAINDER 2);
  -- ... through p7
  CREATE TABLE sessions_p7 PARTITION OF sessions FOR VALUES WITH (MODULUS 8, REMAINDER 7);
  -- Rows for user_id 42: hash(42) % 8 = 2 → goes to sessions_p2
  -- No pruning possible for range queries, but each partition is 1/8 the size.
```

### Partition Maintenance: The Drop-Old-Data Benefit

One of the most operationally valuable aspects of range partitioning is the ability to **drop old partitions instantly**. Deleting old data from a non-partitioned table requires a DELETE statement that creates millions of dead tuples, triggers autovacuum, and logs every deleted row in the WAL. Dropping an old partition is an instantaneous DDL operation — it simply removes the partition's file from disk. No WAL records for individual rows. No dead tuples. No autovacuum. A data retention policy that would take hours with DELETE takes milliseconds with partitioning.

```sql
  -- Data retention with partitioning: drop old data in milliseconds

  -- Traditional approach (non-partitioned):
  DELETE FROM orders WHERE created_at < '2023-01-01';
  -- Deletes potentially millions of rows → creates millions of dead tuples
  -- → WAL writes for every deleted row → autovacuum must process all dead tuples
  -- → Takes hours, creates massive I/O, degrades concurrent performance

  -- Partitioned approach:
  DROP TABLE orders_y2022m12;  -- Drops the entire December 2022 partition
  -- → Instant (file deletion)
  -- → Zero dead tuples
  -- → Zero WAL records for individual rows
  -- → Zero autovacuum work

  -- Alternatively: DETACH and archive the partition
  ALTER TABLE orders DETACH PARTITION orders_y2022m12;
  -- orders_y2022m12 is now a regular standalone table
  -- Archive it: COPY to cold storage, then DROP TABLE orders_y2022m12;

  -- Partition lifecycle management (with pg_partman):
  -- Pre-create future partitions: automatic
  -- Drop past partitions: configure retention_keep_table = false
  -- SELECT partman.run_maintenance('public.orders');
  -- → Creates next month's partition, drops partitions older than retention period
```

### When NOT to Partition

Partitioning adds overhead and should not be used indiscriminately. The planner must evaluate partition constraints for every query, even when pruning eliminates all partitions. Cross-partition queries (queries without a partition key filter) are slower than equivalent queries on a non-partitioned table, because the planner must generate a plan for each partition and combine them. For small-to-medium tables, partitioning adds complexity without benefit.

```
  PARTITIONING: WHEN TO USE vs WHEN TO AVOID

  USE PARTITIONING WHEN:
  ✓ Table has > 50-100 million rows (pruning benefit outweighs overhead)
  ✓ Queries almost always filter by the partition key
  ✓ Old data is regularly deleted (instant DROP PARTITION replaces slow DELETE)
  ✓ Autovacuum struggles to keep up (smaller partitions = faster vacuum)
  ✓ Large-scale parallel queries can benefit from partition-wise joins/aggregates

  AVOID PARTITIONING WHEN:
  ✗ Table is small (< 10 million rows) — overhead exceeds benefit
  ✗ Most queries span all partitions (no pruning → worse than non-partitioned)
  ✗ Partition key is not frequently used in WHERE clauses
  ✗ Table is insert-heavy but rarely queried by partition key (use sharding instead)
  ✗ Primary key or unique constraint must include a non-partition-key column
     (PostgreSQL requires partition key to be part of primary/unique keys)
```

## 3. Table Statistics and ANALYZE Frequency

### What Statistics Are and Why They Matter

The PostgreSQL query planner is a **cost-based optimizer** — it does not use intuition or rules of thumb to choose between a sequential scan and an index scan, between a hash join and a nested loop. It calculates the estimated cost of each candidate plan in units of "disk page reads" and chooses the cheapest. These cost estimates depend entirely on **statistics** — data about the distribution of values in each table's columns, stored in the `pg_statistic` system table and accessible through `pg_stats`.

Without accurate statistics, the planner makes wrong assumptions: it might assume that 50% of `orders` rows have `status = 'shipped'` when in reality only 2% do. This incorrect estimate causes it to choose a sequential scan (appropriate for 50% selectivity) when an index scan would be much faster (appropriate for 2% selectivity). The query is not slow because the index is missing or the query is written poorly — it is slow because the planner does not know the truth about the data, and stale statistics are the reason.

```
  HOW STATISTICS AFFECT PLAN CHOICE

  Table: orders (10 million rows)
  Column: status (values: 1=pending(2%), 2=confirmed(3%), 3=shipped(90%), 4=cancelled(5%))
  Index: idx_orders_status ON orders(status)

  Query: SELECT * FROM orders WHERE status = 1;  -- find 'pending' orders (2% of table)

  ─────────────────────────────────────────────────────────────────
  WITH ACCURATE STATISTICS (MCV table knows status=1 is 2%):
    Estimated rows: 10,000,000 × 0.02 = 200,000 rows
    Sequential Scan cost: 10M reads → expensive
    Index Scan cost: 200,000 reads (index + heap) → cheaper
    Planner chooses: INDEX SCAN ✓

  WITH STALE STATISTICS (stats still think all values are equally common):
    Default assumption (no MCV): 1 / n_distinct values = 1/4 = 25%
    Estimated rows: 10,000,000 × 0.25 = 2,500,000 rows (wildly wrong!)
    Planner thinks: "2.5 million rows is a lot — sequential scan is cheaper
    than 2.5M random index reads."
    Planner chooses: SEQUENTIAL SCAN ✗ (10M reads instead of 200K!)

  THE COST OF WRONG STATISTICS: a query that should take 0.5 seconds
  takes 50 seconds because the planner chose the wrong plan.
  The fix: run ANALYZE → statistics are updated → planner chooses correctly.
  ─────────────────────────────────────────────────────────────────
```

### What ANALYZE Collects

`ANALYZE` scans a random sample of each table's rows (controlled by `default_statistics_target`) and computes several statistical summaries that the planner uses for cardinality estimation.

```
  STATISTICS COLLECTED BY ANALYZE

  pg_stats view (one row per column per table):

  ┌─────────────────────────────────────────────────────────────────────┐
  │ n_distinct:                                                         │
  │   Estimated number of distinct values in the column.               │
  │   Positive: absolute count. Negative: fraction of rows.            │
  │   n_distinct = -0.1 means 10% of rows have a unique value.         │
  │   Planner uses this for GROUP BY and selectivity estimation.        │
  │                                                                     │
  │ correlation:                                                        │
  │   Statistical correlation between column values and physical row    │
  │   order (-1 to +1). Near +1 or -1: physical order matches index    │
  │   order → index scan is efficient (few random I/Os).               │
  │   Near 0: random physical ordering → index scan causes many        │
  │   random I/Os → sequential scan may be preferred.                  │
  │   For auto-incrementing PKs: correlation ≈ 1.0 (always written     │
  │   in order → sequential access via index is fast).                 │
  │                                                                     │
  │ most_common_vals (MCV):                                             │
  │   Array of the most common values in the column.                   │
  │   Stored with most_common_freqs: the fraction of rows with         │
  │   each MCV. E.g.: {shipped, pending, cancelled} with {0.90, 0.02,  │
  │   0.08}. Planner uses this directly for equality selectivity.      │
  │                                                                     │
  │ histogram_bounds:                                                   │
  │   Array of values dividing the non-MCV values into equal-sized     │
  │   buckets. Used for range selectivity estimation.                  │
  │   E.g.: {1, 50, 200, 500, 1000} means equal fractions of the      │
  │   non-MCV rows fall between each pair of bounds.                   │
  └─────────────────────────────────────────────────────────────────────┘
```

```sql
  -- Inspect statistics for a specific column:
  SELECT
      tablename,
      attname                     AS column_name,
      n_distinct,
      correlation,
      most_common_vals,
      most_common_freqs,
      histogram_bounds,
      null_frac                   AS fraction_null
  FROM pg_stats
  WHERE tablename = 'orders'
    AND attname   = 'status';

  -- Practical interpretation:
  -- n_distinct = 5 → column has 5 unique values (like status codes)
  -- correlation = 0.98 → rows are nearly physically sorted by this column
  --   (index scan will be efficient — sequential heap reads)
  -- correlation = 0.01 → random physical order
  --   (index scan causes many random I/Os — planner may prefer seq scan)
  -- most_common_vals = {3, 1, 4, 2, 5} (shipped most common)
  -- most_common_freqs = {0.90, 0.02, 0.05, 0.02, 0.01}
  --   → planner knows exactly: WHERE status=3 returns 90% of rows (seq scan!)
  --                            WHERE status=1 returns 2% of rows (index scan!)
```

### Controlling Statistics Granularity: statistics_target

The `default_statistics_target` parameter controls how many values are sampled and stored for MCV and histogram. A higher target produces more detailed statistics (better plan choices for complex queries) at the cost of more time for `ANALYZE` to run and more space in `pg_statistic`. The default is 100 (100 MCV entries, 100 histogram buckets).

```sql
  -- Default statistics target (affects all columns globally):
  -- postgresql.conf:
  default_statistics_target = 100   -- default: reasonable for most columns

  -- Per-column override for columns with complex value distributions:
  -- (useful when the planner consistently makes wrong choices for a column)
  ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 500;
  -- Now ANALYZE will collect 500 MCV entries for customer_id.
  -- Better selectivity estimates for queries filtering by specific customers.
  -- Run ANALYZE after changing statistics target:
  ANALYZE orders (customer_id);

  -- When to increase statistics_target for a column:
  -- 1. The column has many distinct values AND queries filter on specific values.
  -- 2. EXPLAIN ANALYZE shows: "Rows=50000 (actual rows=200)" — large estimate error.
  -- 3. The planner chooses seq scan but index scan would be faster.

  -- Check current statistics targets:
  SELECT attname, attstattarget
  FROM pg_attribute
  WHERE attrelid = 'orders'::regclass
    AND attnum > 0;
  -- attstattarget = -1 means use default_statistics_target.

  -- Extended statistics: for correlated column combinations
  -- (when WHERE clause on two columns together is more selective than each alone)
  CREATE STATISTICS orders_status_customer_stats
      ON status, customer_id
      FROM orders;
  -- PostgreSQL 10+: collects ndistinct (how many distinct combinations exist)
  -- PostgreSQL 12+: also collects MCV for column combinations
  -- After creating: ANALYZE orders;
  -- Planner uses this for queries filtering both status AND customer_id.
```

### ANALYZE Frequency and Timing

`ANALYZE` is run automatically by autovacuum (as `AUTOANALYZE`) when a table's data changes significantly. The trigger condition is:

```
  AUTOANALYZE TRIGGER:
  n_mod_since_analyze > autovacuum_analyze_threshold
                      + (autovacuum_analyze_scale_factor × n_live_tuples)

  Default: threshold=50, scale_factor=0.10
  For a 1M row table: trigger at 50 + 100,000 = 100,050 changes.
  → Statistics updated once per 10% table change. Usually adequate.

  WHEN TO TRIGGER ANALYZE MANUALLY:
  1. After a large bulk load (millions of rows inserted).
     ANALYZE tablename;  -- update stats immediately, don't wait for autoanalyze

  2. After a large DELETE (distribution of remaining values has changed).
     DELETE FROM orders WHERE created_at < '2023-01-01';
     ANALYZE orders;  -- stats for status, customer_id etc. may have changed

  3. Before running a critical slow query that you suspect has a bad plan.
     ANALYZE orders;  -- fresh stats → planner has accurate information

  4. After creating a new index (index stats need to be current).
     CREATE INDEX idx_orders_status ON orders(status);
     ANALYZE orders;  -- ensure planner knows index statistics immediately

  5. After VACUUM FULL (entire table was rewritten — all page estimates stale).
     VACUUM FULL orders;
     ANALYZE orders;  -- VACUUM FULL does not update row statistics
```

```sql
  -- Monitor tables with stale statistics:
  SELECT
      schemaname,
      relname                       AS table_name,
      n_live_tup                    AS live_rows,
      n_mod_since_analyze           AS rows_changed_since_analyze,
      ROUND(100.0 * n_mod_since_analyze /
            NULLIF(n_live_tup, 0), 2) AS pct_changed,
      last_analyze,
      last_autoanalyze,
      EXTRACT(EPOCH FROM NOW() - COALESCE(last_analyze, last_autoanalyze)) / 3600
                                    AS hours_since_analyze
  FROM pg_stat_user_tables
  WHERE n_mod_since_analyze > 1000
  ORDER BY pct_changed DESC NULLS LAST;
  -- Tables with pct_changed > 10% and no recent analyze: stale statistics risk.
  -- Tables where hours_since_analyze > 24 AND pct_changed > 5%: analyze manually.
```

## 4. Bloat Management

### What Bloat Is and How It Forms

**Bloat** is the accumulation of unused space within database files — space that was once occupied by live data but has been freed by deletes and updates, yet cannot be returned to the operating system or reused without a VACUUM. Bloat has two dimensions: **table bloat** (dead tuples and empty space in heap pages) and **index bloat** (index entries pointing to dead tuples, and partially-empty index pages left after deletions).

Both forms of bloat degrade performance in the same fundamental way: the database must read more physical disk pages to find the same number of live rows. A table that stores 10 million live rows in 100,000 pages (10% full pages, 90% empty space due to bloat) requires the same disk I/O as a table with 100 million rows — because the read head has no way to skip empty space within pages. Every sequential scan, every bitmap heap scan, every index scan that fetches heap pages pays the full I/O cost of the bloated pages.

```
  BLOAT FORMATION OVER TIME

  Initial state (table fully packed, all pages used efficiently):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Page 1   │ Page 2   │ Page 3   │ Page 4   │ Page 5   │ Page 6   │
  │ ████████ │ ████████ │ ████████ │ ████████ │ ████████ │ ████████ │
  │ (8 rows) │ (8 rows) │ (8 rows) │ (8 rows) │ (8 rows) │ (8 rows) │
  └──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
  Total live rows: 48. Total pages read for full scan: 6.

  After many updates (each update leaves a dead tuple):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Page 1   │ Page 2   │ Page 3   │ Page 4   │ Page 5   │ Page 6   │
  │ ██░░░░░░ │ ░░░░████ │ ██░░░░░░ │ ░░░░████ │ ██░░░░░░ │ ░░░░████ │
  │ (2 live, │ (2 live, │ (2 live, │ (2 live, │ (2 live, │ (2 live, │
  │  6 dead) │  6 dead) │  6 dead) │  6 dead) │  6 dead) │  6 dead) │
  └──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
  Total live rows: still 48 (same data!). Dead rows: 36.
  Pages read for full scan: still 6 (same I/O for 1/4 the useful data!)
  Effective page utilization: 25%. Table is 75% bloated.

  After VACUUM (marks dead space as reusable, does NOT compact):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Page 1   │ Page 2   │ Page 3   │ Page 4   │ Page 5   │ Page 6   │
  │ ██[FREE] │ [FREE]██ │ ██[FREE] │ [FREE]██ │ ██[FREE] │ [FREE]██ │
  └──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
  Dead tuples are gone. Space is marked FREE (reusable).
  But pages still exist! File size unchanged. New inserts can reuse space.
  Full scan: still 6 pages (file not compacted — space just marked reusable).

  After VACUUM FULL (rewrites entire table — compacts):
  ┌────────────────┐
  │ Page 1         │
  │ ████████████   │  ← All 48 live rows fit in 1 fully-packed page
  └────────────────┘
  Full scan: 1 page (6× fewer reads). File size shrunk by 83%.
  COST: Exclusive lock on table during entire rewrite. Not free!
```

### Measuring Bloat

The standard approach to measuring bloat in PostgreSQL uses the statistics in `pg_stat_user_tables` combined with page-level analysis. The key query uses the expected vs actual page counts to estimate the wasted space.

```sql
  -- ─────────────────────────────────────────────────────────────────
  -- Table bloat estimation (approximate but fast):
  -- ─────────────────────────────────────────────────────────────────
  SELECT
      schemaname,
      tablename,
      pg_size_pretty(pg_relation_size(schemaname||'.'||tablename))
                                              AS table_size,
      pg_size_pretty(
          pg_relation_size(schemaname||'.'||tablename)
          - (n_live_tup * avg_row_len)
      )                                       AS estimated_bloat,
      ROUND(100.0 * (1 - (n_live_tup * avg_row_len)::NUMERIC /
            NULLIF(pg_relation_size(schemaname||'.'||tablename), 0)), 2)
                                              AS bloat_pct
  FROM (
      SELECT
          schemaname,
          tablename,
          n_live_tup,
          (SELECT AVG(pg_column_size(t.*))  -- estimate average row size
           FROM (SELECT * FROM pg_class WHERE relname = tablename LIMIT 100) t
          ) AS avg_row_len
      FROM pg_stat_user_tables
  ) stats
  WHERE n_live_tup > 1000
  ORDER BY bloat_pct DESC NULLS LAST;

  -- More accurate bloat analysis: pgstattuple extension
  CREATE EXTENSION IF NOT EXISTS pgstattuple;

  -- Per-table bloat details:
  SELECT
      table_len,
      tuple_count,
      tuple_len,
      dead_tuple_count,
      dead_tuple_len,
      ROUND(dead_tuple_percent, 2)            AS dead_pct,
      free_space,
      ROUND(free_percent, 2)                  AS free_pct,
      ROUND(dead_tuple_percent + free_percent, 2) AS total_bloat_pct
  FROM pgstattuple('orders');
  -- dead_pct:    space occupied by dead tuples (needs VACUUM)
  -- free_pct:    previously vacuumed free space (ready for new inserts)
  -- total_bloat_pct: total wasted space (target for VACUUM FULL or pg_repack)

  -- Index bloat analysis:
  SELECT * FROM pgstattuple('idx_orders_status');
  -- Also: leaf_fragmentation: fraction of index leaf pages that are not full
  -- leaf_fragmentation > 30%: index is fragmented, REINDEX may help

  -- Quick bloat overview for all tables:
  SELECT
      schemaname,
      relname,
      n_live_tup,
      n_dead_tup,
      ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1)
                                              AS dead_pct
  FROM pg_stat_user_tables
  WHERE n_dead_tup > 10000
  ORDER BY dead_pct DESC;
  -- Threshold: dead_pct > 10% → VACUUM recommended
  --            dead_pct > 20% → urgent VACUUM
  --            dead_pct > 50% → manual VACUUM + investigate autovacuum settings
```

### Bloat Remediation Strategies

The correct remediation strategy depends on the severity of bloat and the operational constraints (downtime tolerance, table size, write volume).

```
  BLOAT REMEDIATION DECISION TREE

  How severe is the bloat?
  │
  ├── Mild (dead_pct 5-20%):
  │   VACUUM tablename;
  │   → Marks dead space as reusable. Fast. No lock. No file shrinkage.
  │   → Sufficient if autovacuum will prevent re-accumulation.
  │   → After: tune autovacuum settings for this table.
  │
  ├── Moderate (dead_pct 20-40%):
  │   VACUUM ANALYZE tablename;
  │   → Vacuum + refresh statistics. More thorough.
  │   → If table is write-heavy: check autovacuum cost settings.
  │
  └── Severe (dead_pct > 40% OR file size >> expected size):
      Can you take a maintenance window?
      │
      ├── YES (can take downtime):
      │   VACUUM FULL tablename;
      │   → Rewrites entire table. Acquires exclusive lock.
      │   → Physically compacts the file. Returns space to OS.
      │   → After: ANALYZE tablename; REINDEX TABLE tablename;
      │   → Downtime required for table access during rewrite.
      │
      └── NO (cannot take downtime — production 24/7):
          pg_repack --table tablename dbname
          → Third-party tool. Rewrites table without exclusive lock.
          → Uses triggers to capture concurrent writes during rebuild.
          → Zero downtime. Same result as VACUUM FULL.
          → Install: CREATE EXTENSION pg_repack;
          → Run: pg_repack -h host -U user -d dbname -t tablename
```

```sql
  -- ─────────────────────────────────────────────────────────────────
  -- INDEX BLOAT: REINDEX strategies
  -- ─────────────────────────────────────────────────────────────────

  -- Rebuild a single index (blocks reads and writes on the index):
  REINDEX INDEX idx_orders_status;

  -- Rebuild concurrently (no locks on production — PostgreSQL 12+):
  REINDEX INDEX CONCURRENTLY idx_orders_status;
  -- Builds new index in background, swaps atomically, drops old index.
  -- Takes longer but does not block any queries. ALWAYS prefer this.

  -- Rebuild all indexes on a table:
  REINDEX TABLE CONCURRENTLY orders;

  -- After REINDEX: the new index is fully packed (no fragmentation).
  -- Schedule REINDEX CONCURRENTLY for heavily-fragmented indexes
  -- (leaf_fragmentation > 30% from pgstattuple).

  -- ─────────────────────────────────────────────────────────────────
  -- FILLFACTOR: Prevent update bloat proactively
  -- ─────────────────────────────────────────────────────────────────

  -- PostgreSQL's fillfactor controls what fraction of each heap/index page
  -- is filled when rows are initially written. Space left by a lower fillfactor
  -- is available for row updates on the SAME page (HOT updates).

  -- HOT (Heap Only Tuple) update: if an updated row version fits on the SAME
  -- page as the old version, the index does NOT need to be updated —
  -- only the heap is modified. This dramatically reduces index bloat
  -- from frequent updates.

  -- Set fillfactor on a high-update table:
  CREATE TABLE orders (
      id         BIGSERIAL PRIMARY KEY,
      status     SMALLINT NOT NULL,
      updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
  ) WITH (fillfactor = 80);
  -- 80% fill: each page has 20% space reserved for in-place updates.
  -- When status is updated: new tuple goes to same page (HOT update).
  -- No new index entry needed. Index stays compact.

  -- Adjust fillfactor on existing table:
  ALTER TABLE orders SET (fillfactor = 80);
  -- Note: takes effect for NEW pages written going forward.
  -- To apply to existing pages: VACUUM FULL orders (rewrites with new fillfactor).

  -- Recommended fillfactor values:
  -- ┌─────────────────────────────┬─────────────────┐
  -- │ Table access pattern        │ fillfactor      │
  -- ├─────────────────────────────┼─────────────────┤
  -- │ Append-only (insert only)   │ 100 (default)   │
  -- │ Infrequent updates          │ 90              │
  -- │ Moderate updates            │ 80              │
  -- │ Frequent in-place updates   │ 70              │
  -- │ Very frequent hot updates   │ 60-70           │
  -- └─────────────────────────────┴─────────────────┘

  -- Check current fillfactor:
  SELECT relname, reloptions
  FROM pg_class
  WHERE relname = 'orders';
  -- reloptions: {fillfactor=80}
```

### Bloat Prevention Through Schema Design

The ultimate bloat management strategy is proactive: design schemas that minimize the conditions that create bloat in the first place.

```
  SCHEMA-LEVEL BLOAT PREVENTION

  1. AVOID wide rows that are frequently partially updated.
     A row with 100 columns where only 5 are updated each time:
     → Each update writes a full new 100-column tuple (even unchanged columns)
     → Dead 100-column tuple left behind
     → Vertical splitting (table decomposition) reduces row width:
        orders(id, customer_id, total, status)   ← frequently updated columns
        order_details(order_id, shipping_addr, notes, ...)  ← rarely updated

  2. USE TIMESTAMPTZ created_at NOT updated_at for immutable records.
     Append-only tables (event logs, audit trails) have ZERO dead tuples.
     Design for append-only where business logic permits.

  3. FOR HIGH-UPDATE TABLES: tune fillfactor (see above).
     HOT updates eliminate index bloat entirely for in-page updates.

  4. PARTITION time-series tables.
     Drop old partitions instead of deleting rows.
     Zero dead tuples. Zero bloat. Instant data removal.

  5. MONITOR dead_pct continuously.
     Alert when dead_pct > 10% for large tables.
     Investigate autovacuum settings before bloat becomes severe.
     Prevention is always cheaper than remediation.
```

```
  │ ✓ Autovacuum tuned aggressively for high-write tables               │
  │ ✓ Append-only design preferred for event/audit tables               │
  └──────────────────────────────────────────────────────────────────────┘
```

The discipline of schema-level performance is ultimately the discipline of thinking about the future. The data type you choose today will be encoded in hundreds of millions of rows that will exist for years. The table you fail to partition today will require a painful live migration when it reaches 500 million rows. The statistics you fail to analyze after a bulk load will cause bad query plans until the next autoanalyze cycle. The bloat you allow to accumulate will slow every sequential scan until the next VACUUM FULL maintenance window. These are not dramatic failures — they are slow, invisible degradations that compound over time, and preventing them requires the habit of making deliberate schema decisions from the very beginning.
