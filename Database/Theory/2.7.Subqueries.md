## 1. Introduction — The Concept of a Subquery

Every SQL query you write is essentially a question directed at the database. "What are the names of all customers?" — simple, one-part question. "What are the names of all customers who spent more than the average customer?" — now you have a two-part question. The second part ("more than the average") cannot be answered without first answering a preliminary question: "what is the average customer spend?" And that preliminary answer must feed into the main question.

This is the fundamental motivation for subqueries. A **subquery** (also called a nested query or inner query) is a complete SQL `SELECT` statement written inside another SQL statement. The inner query runs first and produces a result, and that result is then used by the outer query to complete its own execution. The outer query treats the inner query's result as if it were a value, a row, or a table — depending on how the subquery is written and where it is placed.

Subqueries can appear in many locations within a SQL statement:

```
Places a subquery can appear:

  SELECT  [scalar subquery here]
  FROM    [table subquery / derived table here]
  JOIN    [table subquery here]
  WHERE   [scalar / row / table subquery here]
  HAVING  [scalar subquery here]
  ORDER BY [scalar subquery here]
```

The subquery's behavior — what type of result it may return and how the outer query uses it — depends entirely on where it appears. This chapter explores each placement and each type of subquery systematically, from the simplest (a scalar value) to the most complex (a correlated subquery that executes once for every row of the outer query).

## 2. The Working Schema

We continue with the e-commerce system from the previous chapters. All examples in this chapter use the following tables:

CREATE TABLE customers (

    region       VARCHAR(50),

CREATE TABLE orders (

## 3. Scalar Subqueries — Returning a Single Value

A scalar subquery is the most fundamental form of a nested query. It returns exactly one row and exactly one column — a single value. Wherever a scalar value is valid in SQL, a scalar subquery is also valid: in the `SELECT` list, in a `WHERE` condition, in a `HAVING` condition, in an `ORDER BY` clause, and even as a default value in some contexts.

The database executes the inner query first, extracts the single value it returns, and then substitutes that value into the outer query as if you had typed the value literally. If the inner query returns more than one row, the database throws an error. If it returns no rows (empty result), it returns `NULL`.

---

### 3.1 Scalar Subquery in WHERE

The most common use of a scalar subquery is in the `WHERE` clause as the right-hand side of a comparison operator. This allows you to filter rows by comparing a column value against a dynamically computed threshold.

```sql
-- Find all customers whose total spend exceeds the overall average spend
-- (Without subquery, you'd need two separate queries)

-- First, let's see what the average looks like as a standalone query:
SELECT AVG(total_spend) FROM (
    SELECT customer_id, SUM(oi.quantity * oi.unit_price) AS total_spend
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status = 'COMPLETED'
    GROUP BY customer_id
) AS spend_summary;
-- Suppose this returns: 425.00

-- Now, using a scalar subquery to embed this into the filter:
SELECT
    c.customer_id,
    c.name,
    SUM(oi.quantity * oi.unit_price) AS total_spend
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY c.customer_id, c.name
HAVING SUM(oi.quantity * oi.unit_price) > (
    -- Scalar subquery: returns a single number (the average spend)
    SELECT AVG(customer_total)
    FROM (
        SELECT SUM(oi2.quantity * oi2.unit_price) AS customer_total
        FROM orders o2
        JOIN order_items oi2 ON o2.order_id = oi2.order_id
        WHERE o2.status = 'COMPLETED'
        GROUP BY o2.customer_id
    ) AS averages
);
```

The power here is that the threshold — the average — is computed dynamically every time the query runs. You do not need to know the average in advance, hardcode it, or run a separate query to find it. The database handles both computations together.

```sql
-- More examples of scalar subqueries in WHERE:

-- Find orders placed after the very first order in the system
SELECT order_id, order_date, status
FROM orders
WHERE order_date > (SELECT MIN(order_date) FROM orders)
ORDER BY order_date;

-- Find products priced above the average list price in their category
SELECT product_name, category, list_price
FROM products
WHERE list_price > (
    SELECT AVG(list_price) FROM products
    -- Note: this subquery returns the OVERALL average, not per-category.
    -- For per-category average, you'd need a correlated subquery (covered later).
)
ORDER BY list_price DESC;

-- Find the customer who placed the most recent order
SELECT customer_id, name
FROM customers
WHERE customer_id = (
    SELECT customer_id
    FROM orders
    ORDER BY order_date DESC
    LIMIT 1     -- Ensures exactly ONE row is returned
);
```

The `LIMIT 1` in the last example is an important technique. When you write a scalar subquery, the database will throw an error if the inner query returns more than one row. Using `ORDER BY ... LIMIT 1` is a common way to guarantee scalar behavior when you want "the one customer with the highest X."

---

### 3.2 Scalar Subquery in SELECT

A scalar subquery placed directly in the `SELECT` list computes an additional column for every row in the result. The inner query is evaluated for the context of each outer row, and its single returned value becomes the value of that column.

```sql
-- For each customer, show their total spend alongside the overall average spend
SELECT
    c.name,
    SUM(oi.quantity * oi.unit_price)       AS my_total_spend,
    (
        -- Scalar subquery: same value repeated for every row
        SELECT AVG(sub.customer_total)
        FROM (
            SELECT SUM(oi2.quantity * oi2.unit_price) AS customer_total
            FROM orders o2
            JOIN order_items oi2 ON o2.order_id = oi2.order_id
            WHERE o2.status = 'COMPLETED'
            GROUP BY o2.customer_id
        ) AS sub
    )                                       AS overall_avg_spend,
    SUM(oi.quantity * oi.unit_price) -
    (
        SELECT AVG(sub.customer_total)
        FROM (
            SELECT SUM(oi2.quantity * oi2.unit_price) AS customer_total
            FROM orders o2
            JOIN order_items oi2 ON o2.order_id = oi2.order_id
            WHERE o2.status = 'COMPLETED'
            GROUP BY o2.customer_id
        ) AS sub
    )                                       AS spend_vs_average
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY c.customer_id, c.name;

-- Simpler example: show each product alongside the category's average price
SELECT
    p.product_name,
    p.category,
    p.list_price,
    (SELECT AVG(p2.list_price)
     FROM products p2
     WHERE p2.category = p.category)   AS category_avg_price
FROM products p
ORDER BY p.category, p.list_price;
```

The last example in the block above is interesting — the subquery references `p.category` from the outer query. This makes it a **correlated subquery**, which we will explore in depth in Section 6.

---

### 3.3 Scalar Subquery in HAVING

Just as `WHERE` can use a scalar subquery to filter rows, `HAVING` can use one to filter groups. The subquery provides a dynamic threshold against which the group's aggregate value is compared.

```sql
-- Find categories whose total revenue exceeds the average category revenue
SELECT
    oi.category,
    SUM(oi.quantity * oi.unit_price) AS category_revenue
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
WHERE o.status = 'COMPLETED'
GROUP BY oi.category
HAVING SUM(oi.quantity * oi.unit_price) > (
    -- Scalar subquery: compute average revenue across ALL categories
    SELECT AVG(cat_rev)
    FROM (
        SELECT SUM(oi2.quantity * oi2.unit_price) AS cat_rev
        FROM order_items oi2
        JOIN orders o2 ON oi2.order_id = o2.order_id
        WHERE o2.status = 'COMPLETED'
        GROUP BY oi2.category
    ) AS category_revenues
)
ORDER BY category_revenue DESC;
```

## 4. Row Subqueries — Returning a Single Row

A row subquery returns exactly one row but potentially multiple columns. It is compared against a **row constructor** — a tuple of values written in parentheses — using comparison operators. Row subqueries are less common than scalar subqueries but are valuable in specific scenarios, particularly when you need to match on multiple columns simultaneously.

```sql
-- Row subquery: find the order_item that matches the most recent order
-- AND the highest-priced item in a single compound condition

-- Row constructor syntax: (col1, col2) = (subquery returning two columns)
SELECT item_id, order_id, unit_price
FROM order_items
WHERE (order_id, unit_price) = (
    SELECT o.order_id, MAX(oi.unit_price)
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.order_date = (SELECT MAX(order_date) FROM orders)
    GROUP BY o.order_id
    LIMIT 1
);

-- More practical row subquery: find the customer+channel combination
-- that most recently placed a COMPLETED order
SELECT c.name, o.channel, o.order_date
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE (o.customer_id, o.order_date) = (
    SELECT customer_id, MAX(order_date)
    FROM orders
    WHERE status = 'COMPLETED'
    GROUP BY customer_id
    ORDER BY MAX(order_date) DESC
    LIMIT 1
);
```

Row subqueries are supported by PostgreSQL and MySQL but have varying support in other databases. They are most naturally expressed as a comparison of a row constructor on the left side of the `=` operator against a subquery that returns exactly one row.

## 5. Table Subqueries — Derived Tables

A table subquery (also called a **derived table** or **inline view**) is a subquery that appears in the `FROM` clause or as part of a `JOIN`. Unlike scalar and row subqueries, a table subquery can return any number of rows and any number of columns. The outer query treats it exactly as if it were a real, named table stored in the database.

Table subqueries are enormously useful for solving a class of problems that cannot be expressed cleanly in a single-level query — particularly problems involving aggregation at one level followed by filtering or further aggregation at another level.

---

### 5.1 Subquery in FROM (Derived Table / Inline View)

When a subquery appears in the `FROM` clause, it must be given an alias (a name). The outer query then references that alias as if it were a table. The inner query is evaluated first, produces a complete result set, and then the outer query operates on that result set.

```sql
-- Problem: Find customers whose average order value is above $200.
-- This requires two levels of aggregation:
--   Level 1: compute each order's total value (SUM over order_items)
--   Level 2: compute each customer's average order value (AVG over Level 1)

-- Without a derived table, you CANNOT average a SUM directly in one GROUP BY.
-- WITH a derived table:

SELECT
    customer_id,
    ROUND(AVG(order_total), 2) AS avg_order_value
FROM (
    -- Derived table: one row per order with its total value
    SELECT
        o.customer_id,
        o.order_id,
        SUM(oi.quantity * oi.unit_price) AS order_total
    FROM orders      o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status = 'COMPLETED'
    GROUP BY o.customer_id, o.order_id
) AS order_totals          -- The alias: outer query calls this "order_totals"
GROUP BY customer_id
HAVING AVG(order_total) > 200
ORDER BY avg_order_value DESC;
```

The derived table `order_totals` solves the "double aggregation" problem elegantly. The inner query produces one row per (customer, order) with the order's total value. The outer query then groups by customer and averages those per-order totals to get the average order value per customer.

```
Execution flow for derived table query:

  Inner query executes first:
  +-------------+----------+-------------+
  | customer_id | order_id | order_total |
  +-------------+----------+-------------+
  |      1      |   1001   |   420.00    |
  |      2      |   1002   |   200.00    |
  |      3      |   1004   |   275.00    |
  |      3      |   1006   |    80.00    |
  |      4      |   1007   |   120.00    |
  +-------------+----------+-------------+
  This result is named "order_totals"

  Outer query executes against "order_totals":
  GROUP BY customer_id → average the order_total column per customer
  HAVING AVG > 200 → keep only customers above threshold

  Final result:
  +-------------+-----------------+
  | customer_id | avg_order_value |
  +-------------+-----------------+
  |      1      |    420.00       | ← Only one order, so avg = that order
  |      3      |    177.50       | ← (275 + 80) / 2 — below 200, excluded
  +-------------+-----------------+
```

### 5.2 Subquery in JOIN

A subquery can also appear as the right-hand side of a `JOIN` clause, just like a regular table. This is particularly useful when you need to join against a computed or pre-filtered set of rows rather than a full table.

```sql
-- Join customers against a derived table of their spending metrics
SELECT
    c.name,
    c.tier,
    spend.total_revenue,
    spend.order_count,
    spend.avg_order_value
FROM customers AS c
JOIN (
    -- Derived table: revenue metrics per customer
    SELECT
        o.customer_id,
        COUNT(DISTINCT o.order_id)               AS order_count,
        SUM(oi.quantity * oi.unit_price)         AS total_revenue,
        ROUND(AVG(oi.quantity * oi.unit_price), 2) AS avg_order_value
    FROM orders      o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status = 'COMPLETED'
    GROUP BY o.customer_id
) AS spend ON c.customer_id = spend.customer_id
ORDER BY spend.total_revenue DESC;

-- Join a filtered product list against order items
-- (Only join items for products in the 'Electronics' category)
SELECT oi.order_id, oi.quantity, oi.unit_price, p.product_name
FROM order_items oi
JOIN (
    SELECT product_id, product_name
    FROM products
    WHERE category = 'Electronics'
) AS electronics ON oi.product_id = electronics.product_id;
```

---

### 5.3 Why Derived Tables Matter

Derived tables solve a specific class of problems where the query requires reasoning at multiple levels of granularity simultaneously. SQL processes a single `GROUP BY` at one level — you cannot apply two different `GROUP BY` operations in a single flat query. But by nesting a subquery in the `FROM` clause, you effectively create a two-level computation:

```
Multi-level aggregation (what derived tables enable):

Problem: "What is the average number of line items per order, per customer?"

This requires:
  Step 1: Count line items per order (GROUP BY order_id)
  Step 2: Average those counts per customer (GROUP BY customer_id)

Flat SQL (IMPOSSIBLE in one level):
  SELECT customer_id, AVG(COUNT(*)) FROM order_items
  GROUP BY customer_id, order_id   ← This doesn't give you what you want

With derived table:
  SELECT customer_id, AVG(item_count) AS avg_items_per_order
  FROM (
      SELECT o.customer_id, o.order_id, COUNT(*) AS item_count
      FROM orders o
      JOIN order_items oi ON o.order_id = oi.order_id
      GROUP BY o.customer_id, o.order_id
  ) AS order_item_counts
  GROUP BY customer_id;
```

## 6. Correlated Subqueries — Row-by-Row Execution

A correlated subquery is a subquery that references one or more columns from the outer query. This reference creates a **correlation** — a dependency between the inner and outer queries — that fundamentally changes how the inner query executes. Instead of running once and producing a fixed result, a correlated subquery runs once for every row of the outer query, each time using the current outer row's values.

---

### 6.1 How Correlation Works

To understand the difference between a regular (uncorrelated) subquery and a correlated one, consider the following:

```
UNCORRELATED subquery:
  Runs ONCE, produces a fixed result, is substituted into the outer query.

  SELECT * FROM orders
  WHERE order_date > (SELECT MIN(order_date) FROM orders);
                     ^
                     This subquery runs ONCE.
                     It sees all orders, computes MIN date.
                     Result (say: '2024-01-05') is substituted.
                     Outer query then filters: order_date > '2024-01-05'

CORRELATED subquery:
  Runs ONCE PER ROW of the outer query.
  References outer row's column values.

  SELECT * FROM orders o_outer
  WHERE o_outer.order_date > (
      SELECT MIN(o_inner.order_date)           ← references o_outer.customer_id!
      FROM orders o_inner
      WHERE o_inner.customer_id = o_outer.customer_id
  );
  ^
  For each row in orders (outer):
    Run inner query with customer_id = THIS ROW'S customer_id
    Get the MIN date for THAT customer specifically
    Compare: is THIS row's date > that customer's MIN date?
```

The correlated version answers a completely different question: "Is this order later than the very first order this specific customer ever placed?" The uncorrelated version asks: "Is this order later than the very first order ever placed by anyone?" The correlation fundamentally changes the semantics of the query.

---

### 6.2 Correlated Subquery in WHERE

Correlated subqueries in `WHERE` are used to filter rows based on a condition that depends on each row's own values — particularly its relationship to other rows in the same or a related table.

```sql
-- Find orders that are NOT the customer's first order
-- (i.e., orders placed after the customer's earliest order date)
SELECT o_outer.order_id, o_outer.customer_id, o_outer.order_date
FROM orders AS o_outer
WHERE o_outer.order_date > (
    SELECT MIN(o_inner.order_date)
    FROM orders AS o_inner
    WHERE o_inner.customer_id = o_outer.customer_id  -- Correlation!
)
ORDER BY o_outer.customer_id, o_outer.order_date;

-- For each step of the outer query (each order row):
-- Inner query runs with: WHERE customer_id = [current outer row's customer_id]
-- It asks: "What is the first order date for THIS customer?"
-- Outer query keeps the row only if this order's date > that first date.
```

```
Correlated subquery execution trace (3 outer rows shown):

Outer row: order_id=1001, customer_id=1, date=2024-01-05
  Inner query: SELECT MIN(date) FROM orders WHERE customer_id=1
  Inner result: 2024-01-05 (order 1001 is Alice's first!)
  Compare: 2024-01-05 > 2024-01-05? → FALSE → row excluded

Outer row: order_id=1003, customer_id=1, date=2024-02-01
  Inner query: SELECT MIN(date) FROM orders WHERE customer_id=1
  Inner result: 2024-01-05
  Compare: 2024-02-01 > 2024-01-05? → TRUE → row INCLUDED

Outer row: order_id=1002, customer_id=2, date=2024-01-12
  Inner query: SELECT MIN(date) FROM orders WHERE customer_id=2
  Inner result: 2024-01-12 (order 1002 is Bob's first!)
  Compare: 2024-01-12 > 2024-01-12? → FALSE → row excluded

...and so on for every row in the outer table.
```

```sql
-- Find each product whose price is above average for its own category
-- (The subquery computes the average per category, not the overall average)
SELECT product_id, product_name, category, list_price
FROM products AS p_outer
WHERE list_price > (
    SELECT AVG(list_price)
    FROM products AS p_inner
    WHERE p_inner.category = p_outer.category  -- Correlation: same category
)
ORDER BY category, list_price DESC;

-- Find customers who have placed more orders than the average customer
SELECT c.name, COUNT(o.order_id) AS order_count
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
HAVING COUNT(o.order_id) > (
    SELECT AVG(cnt)
    FROM (
        SELECT COUNT(*) AS cnt
        FROM orders
        GROUP BY customer_id
    ) AS customer_counts
);
```

---

### 6.3 Correlated Subquery in SELECT

A correlated subquery in the `SELECT` clause computes a per-row value that depends on the current outer row's context. This is one of the most expressive places to use correlation — it lets you compute complex per-row metrics that would require multiple queries or window functions otherwise.

```sql
-- For each customer, show their total spend AND what percentage
-- of the overall total revenue they represent
SELECT
    c.name,
    c.region,
    -- The correlated part: spend for THIS customer
    (
        SELECT SUM(oi.quantity * oi.unit_price)
        FROM orders o
        JOIN order_items oi ON o.order_id = oi.order_id
        WHERE o.customer_id = c.customer_id    -- Correlation: current customer
          AND o.status = 'COMPLETED'
    ) AS my_spend,
    -- The non-correlated part: overall total (runs once, same for every row)
    (
        SELECT SUM(oi.quantity * oi.unit_price)
        FROM orders o
        JOIN order_items oi ON o.order_id = oi.order_id
        WHERE o.status = 'COMPLETED'
    ) AS total_revenue
FROM customers c
ORDER BY my_spend DESC NULLS LAST;

-- For each order, show the number of PREVIOUS orders by the same customer
SELECT
    o_outer.order_id,
    o_outer.customer_id,
    o_outer.order_date,
    (
        SELECT COUNT(*)
        FROM orders o_inner
        WHERE o_inner.customer_id = o_outer.customer_id    -- Same customer
          AND o_inner.order_date  < o_outer.order_date     -- BEFORE this order
    ) AS prior_order_count
FROM orders AS o_outer
ORDER BY o_outer.customer_id, o_outer.order_date;
```

### 6.4 Performance of Correlated Subqueries

The defining characteristic of a correlated subquery — that it runs once per row of the outer query — is also its primary performance liability. If the outer query produces 1,000,000 rows, the correlated subquery executes 1,000,000 times. If the inner query itself touches 10,000 rows each time, that is 10,000,000,000 row reads in total. On large tables, naive correlated subqueries can run for hours.

```
Performance comparison: Correlated subquery vs equivalent JOIN/CTE

Query: "Find each customer's total spend"

Approach 1: Correlated subquery in SELECT
  SELECT c.name,
         (SELECT SUM(oi.qty * oi.price)
          FROM orders o JOIN order_items oi ON o.order_id = oi.order_id
          WHERE o.customer_id = c.customer_id) AS spend
  FROM customers c;

  Execution: For 1,200 customers → subquery runs 1,200 times
  Each inner run: touches potentially all orders for that customer
  Total: ~1,200 × (avg orders per customer × avg items per order)
  On a large system: can be very slow.

Approach 2: JOIN (equivalent result, far more efficient)
  SELECT c.name, SUM(oi.quantity * oi.unit_price) AS spend
  FROM customers c
  LEFT JOIN orders o ON c.customer_id = o.customer_id
  LEFT JOIN order_items oi ON o.order_id = oi.order_id
  GROUP BY c.customer_id, c.name;

  Execution: ONE pass through all tables, one GROUP BY
  No repeated execution.
  Typically 10x–1000x faster.

Rule of thumb: If a correlated subquery can be rewritten as a JOIN
or a CTE + JOIN, prefer the JOIN version for performance.
Reserve correlated subqueries for cases where no JOIN equivalent exists.
```

Modern query optimizers (PostgreSQL, SQL Server, Oracle) can often detect certain patterns of correlated subqueries and automatically rewrite them as joins internally — a technique called **subquery unnesting**. However, you should not rely on this happening. Write efficient queries deliberately rather than hoping the optimizer rescues a poorly structured query.

---

## 7. EXISTS and NOT EXISTS

The `EXISTS` operator is a special predicate that takes a subquery as its argument and evaluates to `TRUE` if the subquery returns at least one row, and `FALSE` if the subquery returns no rows. It is almost always used with a correlated subquery, and it has unique performance characteristics that make it ideal for a specific class of problems.

---

### 7.1 EXISTS — The Semi-Join

The `EXISTS` pattern is known as a **semi-join** — it asks the question "does a qualifying record exist in another table?" without actually returning any data from that other table. The outer query returns its own columns; the inner query's role is purely to check for existence.

```sql
-- Find all customers who have placed at least one COMPLETED order
SELECT c.customer_id, c.name, c.tier
FROM customers AS c
WHERE EXISTS (
    SELECT 1                            -- The value '1' is conventional;
    FROM orders AS o                    -- EXISTS only cares whether a row exists,
    WHERE o.customer_id = c.customer_id -- not what value that row contains.
      AND o.status = 'COMPLETED'
);
```

The convention of writing `SELECT 1` (or `SELECT *` or `SELECT NULL`) inside an `EXISTS` subquery is meaningful. Since `EXISTS` only tests for the presence or absence of rows and ignores all column values, the specific value you select inside it is completely irrelevant to the result. `SELECT 1` communicates clearly to the reader that we are not interested in the content of the inner query's rows — only in whether any exist.

```
EXISTS execution trace:

Outer row: customer_id=1 (Alice)
  Inner query: SELECT 1 FROM orders WHERE customer_id=1 AND status='COMPLETED'
  Finds order 1001 (COMPLETED). At the FIRST row found, EXISTS returns TRUE.
  ← Short-circuit: does NOT read remaining matching rows!
  Result: include Alice in output.

Outer row: customer_id=2 (Bob)
  Inner query: SELECT 1 FROM orders WHERE customer_id=2 AND status='COMPLETED'
  Finds order 1002 (COMPLETED). EXISTS returns TRUE immediately.
  Result: include Bob.

Outer row: customer_id=5 (hypothetical: Eve with no orders)
  Inner query: SELECT 1 FROM orders WHERE customer_id=5 AND status='COMPLETED'
  Finds no rows. EXISTS returns FALSE.
  Result: exclude Eve.
```

The short-circuit behavior of `EXISTS` is an important performance advantage: as soon as the inner query finds one qualifying row, it stops reading and returns `TRUE`. This makes `EXISTS` efficient even when the inner table is large, as long as the qualifying row is found early.

```sql
-- Find customers who have ordered from at least two different channels
SELECT c.name
FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o1
    WHERE o1.customer_id = c.customer_id AND o1.channel = 'web'
) AND EXISTS (
    SELECT 1 FROM orders o2
    WHERE o2.customer_id = c.customer_id AND o2.channel = 'mobile'
);

-- Find products that have been ordered at least once
SELECT p.product_name, p.category, p.list_price
FROM products p
WHERE EXISTS (
    SELECT 1
    FROM order_items oi
    WHERE oi.product_id = p.product_id
);
```

---

### 7.2 NOT EXISTS — The Anti-Join

`NOT EXISTS` is the complement of `EXISTS`. It returns `TRUE` when the subquery returns no rows — that is, when the qualifying record does NOT exist in the related table. The `NOT EXISTS` pattern is known as an **anti-join**: it finds rows in the outer table that have no matching rows in the inner table.

```sql
-- Find customers who have NEVER placed any order at all
SELECT c.customer_id, c.name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.customer_id
);

-- Find products that have NEVER been ordered
SELECT p.product_id, p.product_name, p.list_price
FROM products AS p
WHERE NOT EXISTS (
    SELECT 1
    FROM order_items AS oi
    WHERE oi.product_id = p.product_id
);

-- Find customers who ordered in January 2024 but NOT in February 2024
SELECT c.name
FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.order_date BETWEEN '2024-01-01' AND '2024-01-31'
) AND NOT EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.order_date BETWEEN '2024-02-01' AND '2024-02-29'
);
```

`NOT EXISTS` is frequently the correct tool for the "find all A that have no matching B" question — a pattern that appears constantly in data analysis, such as finding churned customers (ordered before but not after a date), finding unused resources, or identifying gaps in a time series.

---

### 7.3 EXISTS vs JOIN vs IN — Choosing the Right Tool

All three — `EXISTS`, `JOIN`, and `IN` — can often express the same logical question, but they have different characteristics:

```
Comparison: EXISTS vs JOIN vs IN for "customers with at least one COMPLETED order"

Using EXISTS:
  SELECT c.name FROM customers c
  WHERE EXISTS (SELECT 1 FROM orders o
                WHERE o.customer_id = c.customer_id AND o.status = 'COMPLETED');
  → Returns each customer ONCE (no duplicates from multiple matching orders)
  → Short-circuits: stops as soon as first match is found
  → Best for: "does a match exist?" questions

Using JOIN:
  SELECT DISTINCT c.name FROM customers c
  JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'COMPLETED';
  → WITHOUT DISTINCT: returns one row per matching order (Alice appears twice
    if she has 2 completed orders)
  → WITH DISTINCT: same as EXISTS result, but at higher cost (deduplication needed)
  → Best for: when you also need columns from the joined table

Using IN:
  SELECT c.name FROM customers c
  WHERE c.customer_id IN (SELECT o.customer_id FROM orders o
                          WHERE o.status = 'COMPLETED');
  → Logically equivalent to EXISTS in this case
  → Potential issues with NULLs (covered in NOT IN section)
  → Some optimizers handle IN less efficiently than EXISTS
  → Best for: simple membership tests against a pre-computed list
```

The general guidance is:
- Use **EXISTS / NOT EXISTS** when you only care about the *presence* or *absence* of a match, not the matched data itself. It is the cleanest and most semantically precise expression of "does a related record exist?"
- Use **JOIN** when you need columns from both tables in your output.
- Use **IN** for simple membership tests against a small, fixed, or pre-computed list.

---

## 8. ANY, ALL, IN, NOT IN — Set Comparisons

SQL provides a family of operators for comparing a value against a set of values returned by a subquery: `IN`, `NOT IN`, `ANY`, and `ALL`. Each expresses a different kind of set relationship, and understanding their semantics precisely is critical for writing correct queries.

---

### 8.1 IN — Membership Test

The `IN` operator tests whether a value is a member of a set. When used with a subquery, it checks whether the left-hand value appears anywhere in the single column returned by the subquery. It is equivalent to testing equality against each member of the set and combining with `OR`.

```sql
-- Find all orders placed by customers in the 'vip' tier
SELECT order_id, order_date, status
FROM orders
WHERE customer_id IN (
    SELECT customer_id
    FROM customers
    WHERE tier = 'vip'
)
ORDER BY order_date;

-- This is logically equivalent to:
-- WHERE customer_id = [id1] OR customer_id = [id2] OR customer_id = [id3] ...
-- but far more readable when the set is computed dynamically.

-- Find order items for products in the Electronics category
SELECT oi.item_id, oi.order_id, oi.quantity, oi.unit_price
FROM order_items oi
WHERE oi.product_id IN (
    SELECT product_id
    FROM products
    WHERE category = 'Electronics'
);

-- IN with a static list (no subquery needed — just write the values directly)
WHERE status IN ('COMPLETED', 'SHIPPED', 'DELIVERED')
```

When the subquery returns a large set of values, some database optimizers internally convert `IN (subquery)` into a `JOIN` or a hash lookup, making it efficient. When the set is small and static, writing the values directly is faster and clearer.

---

### 8.2 NOT IN — Exclusion Test (and the NULL Trap)

`NOT IN` tests whether a value is NOT a member of a set. It appears to be the straightforward complement of `IN`, and for small lists of literal values it is perfectly safe. However, `NOT IN` with a subquery contains one of the most notorious and dangerous traps in all of SQL — the **NULL gotcha** — that causes experienced developers to get wrong answers without any error message.

```sql
-- Find products that have NEVER been ordered
SELECT product_id, product_name
FROM products
WHERE product_id NOT IN (
    SELECT product_id FROM order_items
);
-- This LOOKS correct. But...
```

The problem arises because of SQL's three-valued logic. When a set contains even one `NULL` value, the entire `NOT IN` expression evaluates to `NULL` (unknown) for every row, causing no rows to be returned at all — even rows that clearly do not appear in the set.

```
The NOT IN NULL Trap, explained:

Suppose order_items contains these product_ids: [501, 502, NULL]
(One item was somehow inserted with a NULL product_id)

Testing product_id = 506:
  506 NOT IN (501, 502, NULL)
  Expands to: 506 != 501 AND 506 != 502 AND 506 != NULL
  Evaluates to: TRUE AND TRUE AND UNKNOWN
  Result: UNKNOWN → treated as FALSE!
  → product 506 is EXCLUDED from results even though it was never ordered!

The NULL in the set "contaminates" the entire NOT IN evaluation.
The database cannot be certain that 506 is not equal to NULL
(since NULL = anything is UNKNOWN).
Therefore the whole expression is UNKNOWN, which is treated as FALSE.
```

```sql
-- The NOT IN NULL trap in action:
SELECT product_id, product_name FROM products
WHERE product_id NOT IN (SELECT product_id FROM order_items);
-- If ANY row in order_items has a NULL product_id → returns ZERO rows!
-- No error, no warning — just silently wrong results.

-- Safe alternative 1: Add IS NOT NULL to the subquery
SELECT product_id, product_name FROM products
WHERE product_id NOT IN (
    SELECT product_id FROM order_items
    WHERE product_id IS NOT NULL  -- Exclude NULLs from the set
);

-- Safe alternative 2: Use NOT EXISTS instead (immune to NULLs)
SELECT p.product_id, p.product_name
FROM products p
WHERE NOT EXISTS (
    SELECT 1 FROM order_items oi
    WHERE oi.product_id = p.product_id
);
-- NOT EXISTS: if inner query finds no rows → TRUE (correctly)
-- NULL in order_items: inner query still finds "no match for this product_id"
-- → NOT EXISTS handles NULLs correctly by design.

-- Safe alternative 3: Use LEFT JOIN + IS NULL (anti-join pattern)
SELECT p.product_id, p.product_name
FROM products p
LEFT JOIN order_items oi ON p.product_id = oi.product_id
WHERE oi.product_id IS NULL;
```

The professional rule is: **never use `NOT IN` with a subquery unless you are absolutely certain the subquery cannot return NULL values**. When in doubt, use `NOT EXISTS` or the `LEFT JOIN + IS NULL` pattern instead. Both are NULL-safe and produce correct results regardless of the data.

---

### 8.3 ANY — At Least One Match

The `ANY` operator (also written as `SOME`, which is a synonym) combines a comparison operator with a subquery. The expression `value operator ANY (subquery)` evaluates to `TRUE` if the comparison is true for **at least one** value returned by the subquery. It is like an `OR` across all the returned values.

```sql
-- Find orders whose total value is greater than AT LEAST ONE customer's average spend
SELECT order_id, order_date
FROM orders
WHERE order_id = ANY (
    SELECT order_id FROM order_items
    WHERE unit_price > 100
);
-- Reads: "order_id matches any of the order_ids that have an item priced over $100"
-- Equivalent to IN in this case (IN is syntactic sugar for = ANY)

-- A more illustrative example with a non-equality operator:
-- Find products priced HIGHER than at least one product in Books category
SELECT product_id, product_name, list_price
FROM products
WHERE list_price > ANY (
    SELECT list_price FROM products WHERE category = 'Books'
)
AND category <> 'Books';
-- Means: price > at least one Books product's price
-- Practically: price > MIN(Books prices)
-- If Books has prices [25, 30], any product > 25 qualifies

-- > ANY is equivalent to > MIN of the set:
-- p.list_price > ANY (SELECT list_price FROM ... WHERE category='Books')
-- is the same as:
-- p.list_price > (SELECT MIN(list_price) FROM ... WHERE category='Books')
```

```
ANY semantics with different operators:

  value > ANY (set)   ↔   value > MIN(set)    "greater than at least one"
  value < ANY (set)   ↔   value < MAX(set)    "less than at least one"
  value = ANY (set)   ↔   value IN (set)      "equal to at least one"
  value <> ANY (set)  ↔   value NOT IN (set)? NO — this is "not equal to at least one"
                           (Different from NOT IN! <> ANY is true if set has multiple values)
```

---

### 8.4 ALL — Every Member Must Match

The `ALL` operator is the universal counterpart to `ANY`. The expression `value operator ALL (subquery)` evaluates to `TRUE` only if the comparison is true for **every** value returned by the subquery. It is like an `AND` across all returned values.

```sql
-- Find products priced higher than ALL products in the Books category
-- (i.e., more expensive than the most expensive Book)
SELECT product_id, product_name, category, list_price
FROM products
WHERE list_price > ALL (
    SELECT list_price FROM products WHERE category = 'Books'
)
AND category <> 'Books';
-- > ALL is equivalent to > MAX(set)
-- If Books prices are [25, 30], only products with price > 30 qualify

-- Find customers who have spent more on every order than Bob's minimum order
SELECT DISTINCT o.customer_id
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.customer_id, o.order_id
HAVING SUM(oi.quantity * oi.unit_price) > ALL (
    SELECT SUM(oi2.quantity * oi2.unit_price)
    FROM orders o2
    JOIN order_items oi2 ON o2.order_id = oi2.order_id
    WHERE o2.customer_id = 2          -- Bob's customer_id
    GROUP BY o2.order_id
);
```

```
ALL semantics with different operators:

  value > ALL (set)   ↔   value > MAX(set)    "greater than every member"
  value < ALL (set)   ↔   value < MIN(set)    "less than every member"
  value = ALL (set)   ↔   All values in set are the same as value
                           (Only true if set has one distinct value = this value)
  value <> ALL (set)  ↔   value NOT IN (set)  "not equal to any member"

Special cases:
  ANY against empty set:  FALSE  (no match possible in empty set)
  ALL against empty set:  TRUE   (vacuously true — no counterexample exists)
  ANY with NULL in set:   might return UNKNOWN
  ALL with NULL in set:   might return UNKNOWN

The empty-set behavior of ALL is mathematically correct but counterintuitive:
"All products in this category are cheaper than mine" is vacuously true
if the category has zero products. Watch for this in production data.
```

## 9. Subqueries vs JOINs vs CTEs — Choosing the Right Approach

For many queries, there are multiple equivalent ways to express the same logic. The choice between subqueries, JOINs, and CTEs affects readability, performance, and maintainability.

```
Decision Framework:

  Question you are answering:
    "Does a related record exist?"
    → Use EXISTS / NOT EXISTS (cleanest, most semantically precise)

  Question:
    "Is this value a member of a computed set?"
    → Use IN with a subquery (simple, readable)
    → Avoid NOT IN if the subquery might return NULLs

  Question:
    "I need data from multiple tables in the output"
    → Use JOIN (returns columns from all tables)
    → Subquery in SELECT works too but repeats execution

  Question:
    "I need to aggregate at multiple levels (avg of sums, etc.)"
    → Use derived table (subquery in FROM)
    → Or CTE (named, reusable, same performance)

  Question:
    "I have a complex query that I want to modularize"
    → Use CTE (WITH clause) — named, testable, reusable within the query
    → CTEs are derived tables with names and readability

  Question:
    "I need a per-row computed value that depends on the current row"
    → Use correlated subquery (if correctness requires it)
    → Rewrite as JOIN or window function if possible (better performance)

Performance hierarchy (generally, best to worst for large tables):
  1. Simple JOIN                   (single pass, optimizer-friendly)
  2. Non-correlated subquery       (runs once, result reused)
  3. EXISTS / NOT EXISTS           (short-circuits, efficient)
  4. Derived table / CTE           (same as non-correlated, but organized)
  5. Correlated subquery           (runs N times — use sparingly on large tables)
```

## 10. Putting It All Together

The following query synthesizes every subquery type from this chapter into a single, realistic analytical report. It answers: "For each customer, show their profile alongside their performance metrics, flagging those who outperform average, and listing their product categories — excluding any customer who has had a refunded order."

```sql
WITH customer_spend AS (
    -- Pre-compute total spend per customer (non-correlated, runs once)
    SELECT
        o.customer_id,
        SUM(oi.quantity * oi.unit_price)    AS total_spend,
        COUNT(DISTINCT o.order_id)           AS order_count,
        MIN(o.order_date)                    AS first_order_date,
        MAX(o.order_date)                    AS last_order_date
    FROM orders      o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status = 'COMPLETED'
    GROUP BY o.customer_id
)
SELECT
    c.customer_id,
    c.name,
    c.tier,
    c.region,
    cs.total_spend,
    cs.order_count,
    cs.first_order_date,

    -- Scalar subquery: overall average spend (runs once, same for all rows)
    (SELECT ROUND(AVG(total_spend), 2) FROM customer_spend) AS avg_spend_all,

    -- Correlated scalar subquery: region average spend
    (
        SELECT ROUND(AVG(cs2.total_spend), 2)
        FROM customer_spend cs2
        JOIN customers c2 ON cs2.customer_id = c2.customer_id
        WHERE c2.region = c.region           -- Correlation: match this customer's region
    ) AS avg_spend_same_region,

    -- CASE using scalar subquery comparison
    CASE
        WHEN cs.total_spend > (SELECT AVG(total_spend) FROM customer_spend)
        THEN 'Above Average'
        ELSE 'Below Average'
    END AS performance_vs_avg,

    -- EXISTS: flag whether they have placed any store orders
    CASE WHEN EXISTS (
        SELECT 1 FROM orders o
        WHERE o.customer_id = c.customer_id AND o.channel = 'store'
    ) THEN 'Yes' ELSE 'No' END AS has_store_orders

FROM customers c
JOIN customer_spend cs ON c.customer_id = cs.customer_id

-- NOT EXISTS: exclude customers with ANY refunded order
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'REFUNDED'
)
-- IN: only include customers in specific tiers
AND c.tier IN (
    SELECT DISTINCT tier FROM customers WHERE tier <> 'standard'
)

ORDER BY cs.total_spend DESC;
```

## Summary

Subqueries are the mechanism by which SQL gains the ability to express multi-level reasoning — the capacity to answer a question whose formulation depends on the answer to another question. Each type of subquery addresses a different structural need.

The **scalar subquery** returns a single value and slots cleanly into any position where a literal value is expected — in `WHERE`, `SELECT`, or `HAVING` — allowing dynamic thresholds and per-row computed columns. The **row subquery** returns a single multi-column row, enabling compound tuple comparisons that would otherwise require multiple conditions. The **table subquery** (derived table) returns a full result set that the outer query treats as a table, solving the double-aggregation problem and enabling multi-level computation.

The **correlated subquery** is the most powerful and the most expensive: it runs once per row of the outer query, using that row's values to parameterize its execution. Its power lies in its ability to compute per-row contextual values — "this row's value compared to the average for its own group" — that cannot be expressed without that per-row dependency. Its cost lies in that same dependency, which prevents the optimizer from reusing results and forces repeated execution.

`EXISTS` and `NOT EXISTS` are the cleanest expression of the semi-join and anti-join patterns — checking for the presence or absence of related records without pulling any data from those records. Their short-circuit evaluation makes them efficient, and their correct handling of `NULL` makes them more reliable than `NOT IN`. The set comparison operators — `IN`, `NOT IN`, `ANY`, and `ALL` — provide a vocabulary for comparing values against dynamically computed sets, with `NOT IN`'s NULL trap being the most important pitfall to understand and avoid.

Together, these tools form a complete language for nested, multi-level, context-sensitive data retrieval — the full expressive power that makes SQL capable of answering questions of arbitrary complexity.

---

*"The difference between a developer who knows SQL and one who has mastered it often comes down to one thing: the mastery of the subquery — knowing not just how to write it, but when to use it, when to avoid it, and what the database does with it when you do."*
