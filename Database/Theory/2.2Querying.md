## 1. Introduction — The Art of Asking the Right Question

A database is, at its core, a vast reservoir of facts. A table with a million rows contains a million facts, but most of the time, you do not need all one million of them. You need *some* of them — those that satisfy a particular condition, arranged in a particular order, limited to a manageable number, and perhaps expressed in a form that is more readable than the raw stored values.

This is the essence of querying: the act of precisely describing *which* data you want, *how* you want it arranged, and *in what shape* you want it presented. SQL gives you a rich set of tools for each of these dimensions. The clauses covered in this chapter — `WHERE`, `ORDER BY`, `LIMIT/OFFSET`, `DISTINCT`, aliases, expressions, `CASE`, and `NULL` handling — are the everyday vocabulary of SQL. They appear in virtually every query you will ever write in a professional context, and mastering them is what transforms someone who can *copy* SQL into someone who can *think* in SQL.

Throughout this chapter, we will use a consistent example: a company's `employees` table, along with a `departments` table and a `salary_history` table.

```sql
-- Our working example schema
CREATE TABLE departments (
    dept_id   INT          PRIMARY KEY,
    dept_name VARCHAR(100) NOT NULL,
    location  VARCHAR(50)
);

CREATE TABLE employees (
    emp_id      INT            PRIMARY KEY,
    first_name  VARCHAR(50)    NOT NULL,
    last_name   VARCHAR(50)    NOT NULL,
    email       VARCHAR(100)   UNIQUE,
    dept_id     INT            REFERENCES departments(dept_id),
    job_title   VARCHAR(100),
    salary      DECIMAL(10, 2),
    hire_date   DATE           NOT NULL,
    is_active   BOOLEAN        DEFAULT TRUE,
    manager_id  INT            REFERENCES employees(emp_id)
);

CREATE TABLE salary_history (
    history_id  INT            PRIMARY KEY,
    emp_id      INT            REFERENCES employees(emp_id),
    old_salary  DECIMAL(10,2),
    new_salary  DECIMAL(10,2),
    changed_on  DATE           NOT NULL
);
```

Sample data to visualize our queries:

## 2. WHERE — The Filter Clause

The `WHERE` clause is the gatekeeper of every query. Once the database has identified the source table (via `FROM`) and performed any joins, `WHERE` is the first thing it applies to narrow down the rows. It examines each row individually and asks a single question: "Does this row satisfy the condition?" If the answer is yes, the row is kept and passes through to the next stage of processing. If the answer is no, the row is discarded immediately and plays no further part in the result.

The condition in a `WHERE` clause is always a boolean expression — something that evaluates to either `TRUE`, `FALSE`, or `NULL`. Only rows for which the condition evaluates to `TRUE` are retained. Rows where the condition evaluates to `FALSE` or the special value `NULL` (unknown) are both discarded. This subtlety with `NULL` is extremely important and will be explored in depth in the dedicated NULL section.

---

### 2.1 Comparison Operators

The most fundamental building block of a `WHERE` clause is the comparison operator. These operators compare one value to another and produce a boolean result.

```sql
-- Equality: find employees with exactly this salary
SELECT first_name, last_name, salary
FROM employees
WHERE salary = 95000.00;

-- Greater than: find employees earning more than 70,000
SELECT first_name, last_name, salary
FROM employees
WHERE salary > 70000;

-- Greater than or equal to
SELECT first_name, last_name, hire_date
FROM employees
WHERE hire_date >= '2020-01-01';

-- Less than: junior employees with lower salaries
SELECT first_name, last_name, salary
FROM employees
WHERE salary < 50000;

-- Not equal to: everyone who is NOT an Intern
SELECT first_name, job_title
FROM employees
WHERE job_title <> 'Intern';   -- <> and != are equivalent in most databases
```

```
+------------------------------------------------------------------+
|            Standard Comparison Operators                         |
+----------+-------------------------------------------------------+
| Operator | Meaning                                               |
+----------+-------------------------------------------------------+
|   =      | Equal to                                              |
|  <> / != | Not equal to                                          |
|   >      | Greater than                                          |
|   <      | Less than                                             |
|   >=     | Greater than or equal to                              |
|   <=     | Less than or equal to                                 |
+----------+-------------------------------------------------------+
```

---

### 2.2 Logical Operators: AND, OR, NOT

In real-world queries, a single comparison is rarely sufficient. You almost always need to combine multiple conditions. SQL provides three logical operators for this purpose: `AND`, `OR`, and `NOT`.

`AND` requires that *both* conditions on either side of it must be true for a row to pass through. Think of it as the intersection of two conditions — the row must satisfy condition A and condition B simultaneously.

`OR` requires that *at least one* of the conditions on either side must be true. Think of it as the union of two conditions — if the row satisfies either condition A or condition B (or both), it passes through.

`NOT` simply inverts the boolean result of whatever condition follows it. A row that would have been kept becomes discarded, and a row that would have been discarded is kept.

```sql
-- AND: employees in dept 1 who earn over 60,000
SELECT first_name, last_name, dept_id, salary
FROM employees
WHERE dept_id = 1
  AND salary > 60000;
-- Only Alice (95000) and Bob (62000) qualify — both are in dept 1 and earn > 60,000

-- OR: employees in dept 1 OR dept 3
SELECT first_name, last_name, dept_id
FROM employees
WHERE dept_id = 1
   OR dept_id = 3;

-- NOT: all active employees who are NOT interns
SELECT first_name, job_title
FROM employees
WHERE is_active = TRUE
  AND NOT job_title = 'Intern';

-- Combining all three — use parentheses to control evaluation order
-- Find active employees who are either in dept 1 earning > 60k,
-- or in dept 3 earning > 100k
SELECT first_name, last_name, dept_id, salary
FROM employees
WHERE is_active = TRUE
  AND (
      (dept_id = 1 AND salary > 60000)
      OR
      (dept_id = 3 AND salary > 100000)
  );
```

The parentheses in the last query are critically important. Without them, the `AND` and `OR` operators follow **operator precedence** — `AND` is evaluated before `OR`, just like multiplication is evaluated before addition in arithmetic. This can produce completely different results from what you intended. When in doubt, use parentheses liberally to make your intent explicit and unambiguous.

---

### 2.3 BETWEEN, IN, LIKE, EXISTS

SQL provides several higher-level filtering operators that express common conditions more concisely than raw comparisons.

**BETWEEN** tests whether a value falls within an inclusive range. It is equivalent to writing `value >= lower AND value <= upper`, but considerably more readable.

```sql
-- Employees hired between two dates (both dates inclusive)
SELECT first_name, last_name, hire_date
FROM employees
WHERE hire_date BETWEEN '2019-01-01' AND '2021-12-31';

-- Employees earning between 50,000 and 80,000
SELECT first_name, salary
FROM employees
WHERE salary BETWEEN 50000 AND 80000;

-- NOT BETWEEN: employees outside a salary range
SELECT first_name, salary
FROM employees
WHERE salary NOT BETWEEN 50000 AND 80000;
```

**IN** tests whether a value matches any member of a provided list. It is essentially a compact and more readable alternative to writing multiple `OR` conditions.

```sql
-- Employees in dept 1 or dept 3 (equivalent to: dept_id = 1 OR dept_id = 3)
SELECT first_name, dept_id
FROM employees
WHERE dept_id IN (1, 3);

-- Filter by multiple job titles
SELECT first_name, job_title
FROM employees
WHERE job_title IN ('Senior Engineer', 'Marketing Manager', 'Sales Director');

-- NOT IN: exclude certain departments
SELECT first_name, dept_id
FROM employees
WHERE dept_id NOT IN (2, 3);
```

> **Important Warning about NOT IN and NULL:** If the list passed to `NOT IN` contains even a single `NULL` value, the entire `NOT IN` expression evaluates to `NULL` (unknown) for every row, and no rows will be returned. This is a notorious SQL gotcha. When using `NOT IN` with a subquery, always ensure the subquery cannot return `NULL` values (for example, by adding `WHERE column IS NOT NULL` inside the subquery).

**LIKE** enables pattern-based string matching using two wildcard characters. The percent sign `%` matches any sequence of zero or more characters. The underscore `_` matches exactly one character, whatever it may be.

```sql
-- All employees whose last name starts with 'S'
SELECT first_name, last_name
FROM employees
WHERE last_name LIKE 'S%';
-- Matches: Smith

-- All employees whose email contains 'corp'
SELECT first_name, email
FROM employees
WHERE email LIKE '%corp%';

-- All employees whose first name is exactly 5 characters
SELECT first_name FROM employees
WHERE first_name LIKE '_____';   -- Five underscores

-- All employees whose first name starts with 'A' and ends with 'e'
SELECT first_name FROM employees
WHERE first_name LIKE 'A%e';
-- Matches: Alice

-- Case-insensitive LIKE: use ILIKE in PostgreSQL
SELECT first_name FROM employees
WHERE first_name ILIKE 'alice';  -- PostgreSQL only
```

**EXISTS** is a powerful operator that checks whether a subquery returns at least one row. It does not care about *which* rows or *what values* the subquery returns — it only cares about whether *any* rows exist. As soon as the inner query finds one matching row, `EXISTS` short-circuits and returns `TRUE` without processing any more rows, making it very efficient.

```sql
-- Find employees who have AT LEAST ONE salary history record
SELECT e.first_name, e.last_name
FROM employees e
WHERE EXISTS (
    SELECT 1                          -- '1' is conventional; the value doesn't matter
    FROM salary_history sh
    WHERE sh.emp_id = e.emp_id        -- Correlated to the outer query
);

-- Find employees who have NEVER had a salary change (no history records)
SELECT e.first_name, e.last_name
FROM employees e
WHERE NOT EXISTS (
    SELECT 1
    FROM salary_history sh
    WHERE sh.emp_id = e.emp_id
);
```

## 3. ORDER BY — Sorting the Result Set

Without `ORDER BY`, a SQL query returns rows in no guaranteed order whatsoever. The database is free to return them in any sequence it finds convenient — which might be the order they were physically stored on disk, the order they were processed by a query plan, or something entirely different. This order can change from one execution to the next, even on the same data. If the sequence of your results matters — and for any user-facing output, it almost certainly does — you must use `ORDER BY` to state your sorting intent explicitly.

The `ORDER BY` clause sits near the end of a query, after `HAVING` but before `LIMIT`. It is processed last in the logical query execution order (before `LIMIT`), which means it has access to all column aliases defined in the `SELECT` clause.

---

### 3.1 Single and Multi-Column Sorting

In its simplest form, `ORDER BY` takes a column name and an optional direction keyword — `ASC` for ascending (the default, smallest to largest) or `DESC` for descending (largest to smallest).

```sql
-- Sort employees by salary from lowest to highest (ASC is the default)
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary;

-- Sort by salary from highest to lowest
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary DESC;

-- Sort alphabetically by last name
SELECT first_name, last_name
FROM employees
ORDER BY last_name ASC;
```

When you specify multiple columns in `ORDER BY`, the database applies them as a hierarchy: rows are first sorted by the primary column, and among rows that share the same value in the primary column, they are then sorted by the secondary column, and so on. This is called **multi-column sorting**, and it is the key to producing well-organized reports.

```sql
-- Sort by department first, then by salary (highest earner in each dept first)
SELECT first_name, last_name, dept_id, salary
FROM employees
ORDER BY dept_id ASC, salary DESC;
```

The result of this query would look like:

```
+------------+-----------+--------+-----------+
| first_name | last_name | dept_id| salary    |
+------------+-----------+--------+-----------+
| Alice      | Johnson   |   1    | 95000.00  |  <-- dept 1, highest salary
| Bob        | Smith     |   1    | 62000.00  |  <-- dept 1, second
| Frank      | Davis     |   1    | 28000.00  |  <-- dept 1, lowest
| Carol      | Lee       |   2    | 78000.00  |  <-- dept 2, highest
| David      | Kim       |   2    | 55000.00  |  <-- dept 2, lowest
| Eve        | Brown     |   3    | 110000.00 |  <-- dept 3, highest
| Grace      | Wilson    |   3    | 48000.00  |  <-- dept 3, lowest
+------------+-----------+--------+-----------+
```

Notice how within each department, employees are arranged from highest to lowest salary. Henry (dept_id is NULL) would appear either at the beginning or end depending on the database's NULL handling, which we will discuss shortly.

---

### 3.2 Sorting with Expressions and Aliases

You can sort by expressions or computed values, not just plain column names. More importantly, because `ORDER BY` is logically processed after `SELECT`, you can reference column aliases defined in the `SELECT` clause directly — a convenience not available in `WHERE` or `HAVING`.

```sql
-- Sort by a computed expression: annual bonus (10% of salary)
SELECT first_name, salary, salary * 0.10 AS annual_bonus
FROM employees
ORDER BY annual_bonus DESC;

-- Sort using the alias directly (ORDER BY runs after SELECT, so the alias is known)
SELECT
    first_name,
    last_name,
    CONCAT(last_name, ', ', first_name) AS full_name
FROM employees
ORDER BY full_name ASC;  -- Alphabetical by "Last, First" format

-- Sort by the position number of the column in the SELECT list
-- Column 3 is 'salary' in this query:
SELECT first_name, last_name, salary
FROM employees
ORDER BY 3 DESC;
-- This works but is fragile — if you reorder SELECT columns, the sort changes.
-- It is generally discouraged in production code. Use column names instead.
```

---

### 3.3 Handling NULL in ORDER BY

When you sort a column that contains `NULL` values, the database must decide where to place those nulls — at the very beginning of the result set or at the very end. Different databases have different default behaviors, and SQL provides explicit control through `NULLS FIRST` and `NULLS LAST`.

```
Default NULL Behavior in Common Databases:
+--------------------+-------------------+-------------------+
| Database           | ASC default       | DESC default      |
+--------------------+-------------------+-------------------+
| PostgreSQL         | NULLS LAST        | NULLS FIRST       |
| MySQL / MariaDB    | NULLS FIRST       | NULLS LAST        |
| SQL Server         | NULLS FIRST       | NULLS LAST        |
| Oracle             | NULLS LAST        | NULLS FIRST       |
+--------------------+-------------------+-------------------+
```

```sql
-- PostgreSQL: Explicit NULL placement
-- Show employees sorted by salary DESC, with NULLs at the end
SELECT first_name, salary
FROM employees
ORDER BY salary DESC NULLS LAST;

-- Show employees sorted by salary ASC, with NULLs at the beginning
SELECT first_name, salary
FROM employees
ORDER BY salary ASC NULLS FIRST;

-- MySQL: Use ISNULL() trick to push NULLs to the end
SELECT first_name, salary
FROM employees
ORDER BY ISNULL(salary) ASC, salary DESC;
-- ISNULL() returns 1 for NULL and 0 otherwise, so NULLs sort to the bottom
```

## 4. LIMIT and OFFSET — Controlling Volume and Pagination

When a query could potentially return thousands or millions of rows, you almost never want to retrieve all of them at once. Retrieving unnecessarily large result sets wastes network bandwidth, consumes memory in your application, and degrades database performance. The `LIMIT` clause is your mechanism for restricting how many rows the database actually sends back to you.

`LIMIT` is always paired conceptually with `ORDER BY`. Without a defined sort order, "the first 10 rows" is a meaningless concept — the database could return any 10 rows in any order. Always specify `ORDER BY` before using `LIMIT`.

```sql
-- Get the 5 highest-paid employees
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary DESC
LIMIT 5;

-- Get the single highest-paid employee
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary DESC
LIMIT 1;
```

`OFFSET` tells the database to skip a certain number of rows before starting to return results. It is the companion to `LIMIT` that makes **pagination** possible — the technique of breaking a large dataset into manageable pages, much like pages in a book.

```sql
-- Page 1: rows 1-5 (skip 0, return 5)
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary DESC
LIMIT 5 OFFSET 0;

-- Page 2: rows 6-10 (skip 5, return 5)
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary DESC
LIMIT 5 OFFSET 5;

-- Page 3: rows 11-15 (skip 10, return 5)
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary DESC
LIMIT 5 OFFSET 10;
```

The general formula for pagination is: `OFFSET = (page_number - 1) * page_size`.

```
Pagination Visualization (page_size = 3):

All rows sorted by salary DESC:
+----+-----------+-----------+
| #  | name      | salary    |
+----+-----------+-----------+
| 1  | Eve       | 110000    | <-- Page 1 (OFFSET 0, LIMIT 3)
| 2  | Alice     | 95000     | <-- Page 1
| 3  | Carol     | 78000     | <-- Page 1
+----+-----------+-----------+
| 4  | Bob       | 62000     | <-- Page 2 (OFFSET 3, LIMIT 3)
| 5  | David     | 55000     | <-- Page 2
| 6  | Grace     | 48000     | <-- Page 2
+----+-----------+-----------+
| 7  | Frank     | 28000     | <-- Page 3 (OFFSET 6, LIMIT 3)
| 8  | Henry     | NULL      | <-- Page 3
+----+-----------+-----------+
```

The equivalent syntax in other database systems:

```sql
-- SQL Server: TOP keyword (does not support OFFSET without FETCH)
SELECT TOP 5 first_name, last_name, salary
FROM employees
ORDER BY salary DESC;

-- SQL Server: Pagination with OFFSET-FETCH (SQL Standard compliant)
SELECT first_name, last_name, salary
FROM employees
ORDER BY salary DESC
OFFSET 5 ROWS
FETCH NEXT 5 ROWS ONLY;

-- Oracle (before 12c): ROWNUM subquery trick
SELECT * FROM (
    SELECT first_name, salary, ROWNUM AS rn
    FROM employees
    ORDER BY salary DESC
) WHERE rn BETWEEN 6 AND 10;
```

One important performance caveat about large offsets: when you write `LIMIT 10 OFFSET 1000000`, the database does not magically jump to row 1,000,001. It generates all 1,000,010 rows, discards the first million, and returns the last ten. For very deep pagination, this becomes prohibitively slow. In such cases, **keyset pagination** (also called cursor-based pagination) is preferred: instead of using `OFFSET`, you record the last value seen on the previous page and filter from there.

```sql
-- Keyset pagination: faster for deep pages
-- "Give me the next 10 employees after the last one I saw (salary was 62000, emp_id was 2)"
SELECT first_name, last_name, salary, emp_id
FROM employees
WHERE (salary < 62000)
   OR (salary = 62000 AND emp_id > 2)  -- Tiebreaker for equal salaries
ORDER BY salary DESC, emp_id ASC
LIMIT 10;
```

## 5. DISTINCT — Eliminating Duplicates

When you query data from a table, you might sometimes find that the result contains multiple rows with identical values in the columns you selected. This typically happens when you select only a subset of a table's columns — because while each full row is unique (guaranteed by the primary key), two rows might happen to share the same values in the particular columns you are interested in.

`DISTINCT` is the keyword that instructs the database to remove duplicate rows from the result set, returning only one representative row for each unique combination of values.

```sql
-- Without DISTINCT: shows the dept_id for every employee (duplicates expected)
SELECT dept_id
FROM employees;
-- Result: 1, 1, 2, 2, 3, 1, 3, NULL  (8 rows, with repeats)

-- With DISTINCT: shows each dept_id only once
SELECT DISTINCT dept_id
FROM employees;
-- Result: 1, 2, 3, NULL  (4 rows, each unique value once)

-- DISTINCT on multiple columns: unique combinations of job_title and dept_id
SELECT DISTINCT dept_id, job_title
FROM employees
ORDER BY dept_id, job_title;
-- Each unique (dept_id, job_title) pair appears exactly once
```

It is important to understand that when `DISTINCT` is applied to multiple columns, the database considers the **combination** of all specified columns together, not each column independently. A row is considered a duplicate only if all its selected column values match another row's values exactly.

```sql
-- Example: finding all unique cities employees come from
-- (Assuming employees table had a city column)
SELECT DISTINCT location
FROM departments
ORDER BY location;
```

`DISTINCT` also interacts with aggregate functions. The `COUNT(DISTINCT column)` pattern is particularly common and useful — it counts how many unique values exist in a column:

```sql
-- How many different departments have at least one employee?
SELECT COUNT(DISTINCT dept_id) AS departments_with_employees
FROM employees
WHERE dept_id IS NOT NULL;

-- How many different job titles exist in the company?
SELECT COUNT(DISTINCT job_title) AS unique_job_titles
FROM employees;
```

One performance note: `DISTINCT` is not free. The database has to sort or hash the entire result set to identify and eliminate duplicates. On very large datasets, this can be expensive. If you find yourself using `DISTINCT` frequently, it is worth examining whether there is a JOIN or schema design issue causing the duplicates in the first place.

## 6. Aliases — Giving Things Readable Names

An alias is a temporary, alternative name that you assign to a column or a table within a query. Aliases exist only for the duration of that single query execution — they are not stored in the database and have no permanent effect on the schema. Their purpose is entirely practical: to make queries more readable, to give meaningful names to computed expressions, and to shorten long table names when writing complex queries involving many joins.

---

### 6.1 Column Aliases

Column aliases are defined in the `SELECT` clause using the `AS` keyword, followed by the name you want to use. The `AS` keyword is optional in most databases — you can just write the alias name directly after the column expression — but including `AS` makes the intent crystal clear and is therefore strongly recommended as a professional practice.

```sql
-- Giving a computed column a meaningful name
SELECT
    first_name,
    last_name,
    salary,
    salary * 0.10          AS annual_bonus,
    salary * 12            AS annual_cost_to_company,
    hire_date
FROM employees;

-- Without the alias, the column header would be the raw expression: "salary * 0.10"
-- The alias makes the output self-documenting.

-- Aliases for aggregate functions
SELECT
    dept_id,
    COUNT(*)               AS headcount,
    AVG(salary)            AS average_salary,
    MAX(salary)            AS highest_salary,
    MIN(salary)            AS lowest_salary,
    SUM(salary)            AS total_payroll
FROM employees
GROUP BY dept_id;

-- Aliases with spaces: use double quotes (SQL Standard) or backticks (MySQL)
SELECT
    first_name   AS "First Name",
    last_name    AS "Last Name",
    salary       AS "Annual Salary (USD)"
FROM employees;
```

A very important rule to remember is that column aliases are defined in the `SELECT` phase of logical query processing, which runs *after* `WHERE`, `GROUP BY`, and `HAVING`. Therefore, you cannot reference a `SELECT` alias in your `WHERE` or `HAVING` clauses. You *can* use it in `ORDER BY`, because that runs after `SELECT`.

```sql
-- WRONG: WHERE cannot see 'annual_bonus' because it's defined in SELECT (which runs later)
SELECT salary * 0.10 AS annual_bonus
FROM employees
WHERE annual_bonus > 5000;  -- Error!

-- CORRECT: Repeat the expression in WHERE
SELECT salary * 0.10 AS annual_bonus
FROM employees
WHERE salary * 0.10 > 5000;

-- CORRECT: Use a subquery or CTE to make the alias visible
WITH computed AS (
    SELECT first_name, salary * 0.10 AS annual_bonus
    FROM employees
)
SELECT * FROM computed
WHERE annual_bonus > 5000;
```

---

### 6.2 Table Aliases

Table aliases assign a short, convenient name to a table within a query. They are particularly valuable in two situations: when writing `JOIN` queries (where you need to prefix column names with their source table to avoid ambiguity) and when writing self-joins (where a table must be referenced twice under two different names to distinguish the two instances).

```sql
-- Without table aliases (verbose and harder to read)
SELECT employees.first_name, employees.last_name, departments.dept_name
FROM employees
JOIN departments ON employees.dept_id = departments.dept_id;

-- With table aliases (concise, professional)
SELECT e.first_name, e.last_name, d.dept_name
FROM employees   AS e
JOIN departments AS d ON e.dept_id = d.dept_id;

-- Table aliases in self-joins: REQUIRED to distinguish the two instances
-- Find each employee and the name of their direct manager
SELECT
    emp.first_name   AS employee_name,
    mgr.first_name   AS manager_name
FROM employees AS emp
LEFT JOIN employees AS mgr ON emp.manager_id = mgr.emp_id;
-- 'emp' and 'mgr' are both the same physical table, but treated as two separate sources
```

In the self-join example above, table aliases are not just convenient — they are *required*. Without them, the database would have no way to know which `employees` table you are referring to when you write `employees.emp_id` in the `ON` clause.

Once you define a table alias, you **must** use that alias for all column references to that table within the same query. You cannot mix `employees.first_name` and `e.last_name` in the same query if you defined `e` as the alias for `employees`.

## 7. Arithmetic and String Expressions

SQL is not merely a tool for retrieving data as it is stored. It is also a tool for computing new values from stored data, on the fly. Every `SELECT` clause can contain not just column references but also arbitrary **expressions** — computations involving numbers, text, dates, and functions — whose results become new, temporary columns in the output.

---

### 7.1 Arithmetic Expressions

SQL supports all standard arithmetic operations: addition (`+`), subtraction (`-`), multiplication (`*`), division (`/`), and modulo (`%` or `MOD()`). These operations work on numeric columns and numeric literals, and they follow the standard mathematical order of operations.

```sql
-- Basic arithmetic on salary
SELECT
    first_name,
    last_name,
    salary                          AS base_salary,
    salary * 0.10                   AS bonus_10_percent,
    salary + (salary * 0.10)        AS total_compensation,
    salary / 12                     AS monthly_salary,
    salary - 5000                   AS salary_after_deduction
FROM employees
WHERE salary IS NOT NULL;

-- Modulo: check which employees have salaries divisible by 1000
SELECT first_name, salary
FROM employees
WHERE salary % 1000 = 0;   -- Or: MOD(salary, 1000) = 0

-- Division gotcha: INTEGER division in some databases truncates the decimal
-- To ensure decimal division, cast to a decimal type
SELECT 7 / 2;           -- Returns 3 in some databases (integer division)
SELECT 7.0 / 2;         -- Returns 3.5 (decimal division)
SELECT CAST(7 AS DECIMAL) / 2;  -- Explicit cast to force decimal division

-- Computing years of service for each employee
SELECT
    first_name,
    hire_date,
    DATEDIFF(CURRENT_DATE, hire_date) / 365   AS approx_years_of_service  -- MySQL
FROM employees;

-- PostgreSQL equivalent using EXTRACT or DATE_PART
SELECT
    first_name,
    hire_date,
    EXTRACT(YEAR FROM AGE(CURRENT_DATE, hire_date)) AS years_of_service
FROM employees;
```

Arithmetic expressions are fully composable — you can nest them, combine them, and use them in `WHERE`, `ORDER BY`, and `HAVING` clauses, just as you can in `SELECT`.

```sql
-- Find employees whose annual bonus (10%) would exceed 8,000
SELECT first_name, salary, salary * 0.10 AS bonus
FROM employees
WHERE salary * 0.10 > 8000;

-- Order by computed total compensation
SELECT first_name, salary, salary * 0.10 AS bonus
FROM employees
ORDER BY (salary + salary * 0.10) DESC;
```

---

### 7.2 String Expressions and Functions

String manipulation is another area where SQL expressions shine. Databases provide a rich library of built-in string functions that allow you to format, transform, search, and extract data from text columns. While the exact function names vary somewhat between database vendors, the concepts are universal.

**Concatenation** is the most fundamental string operation: joining two or more strings into one.

```sql
-- Concatenation using CONCAT() function (works in MySQL, PostgreSQL, SQL Server)
SELECT CONCAT(first_name, ' ', last_name) AS full_name
FROM employees;

-- PostgreSQL also supports the || operator for concatenation
SELECT first_name || ' ' || last_name AS full_name
FROM employees;

-- SQL Server uses + for string concatenation
SELECT first_name + ' ' + last_name AS full_name
FROM employees;

-- Build a formatted greeting
SELECT
    CONCAT('Dear ', first_name, ' ', last_name, ',') AS greeting,
    CONCAT('Your current salary is $', salary, '.') AS salary_message
FROM employees;
```

Beyond concatenation, here is a curated set of the most important and universally useful string functions:

```sql
-- UPPER and LOWER: change case
SELECT UPPER(first_name) AS upper_name, LOWER(last_name) AS lower_name
FROM employees;
-- Result: ALICE johnson

-- LENGTH / LEN: count characters
SELECT first_name, LENGTH(first_name) AS name_length    -- PostgreSQL, MySQL
FROM employees;

SELECT first_name, LEN(first_name) AS name_length       -- SQL Server
FROM employees;

-- TRIM, LTRIM, RTRIM: remove whitespace
SELECT TRIM('   hello   ') AS trimmed;       -- 'hello'
SELECT LTRIM('   hello   ') AS left_trimmed; -- 'hello   '
SELECT RTRIM('   hello   ') AS right_trimmed;-- '   hello'

-- SUBSTRING / SUBSTR: extract a portion of a string
-- SUBSTRING(column, start_position, length)
SELECT SUBSTRING(email, 1, 5) AS email_prefix   -- First 5 characters
FROM employees
WHERE email IS NOT NULL;

-- REPLACE: replace all occurrences of a substring
SELECT REPLACE(email, '@corp.com', '@newcorp.com') AS new_email
FROM employees;

-- LIKE in expressions: same as in WHERE, useful in SELECT for visibility
SELECT
    first_name,
    email,
    CASE WHEN email LIKE '%@corp.com' THEN 'Internal' ELSE 'External' END AS email_type
FROM employees;

-- LEFT and RIGHT: extract characters from the start or end
SELECT LEFT(first_name, 1) AS initial   -- First character of first name
FROM employees;

SELECT RIGHT(email, 8) AS domain_end    -- Last 8 characters
FROM employees
WHERE email IS NOT NULL;

-- POSITION / INSTR: find the position of a substring
SELECT
    email,
    POSITION('@' IN email) AS at_sign_position  -- PostgreSQL, MySQL
FROM employees
WHERE email IS NOT NULL;
```

String functions can be combined to build powerful data transformations in a single query:

```sql
-- Extract the username part of an email (everything before @)
-- PostgreSQL:
SELECT
    email,
    LEFT(email, POSITION('@' IN email) - 1) AS username
FROM employees
WHERE email IS NOT NULL;

-- MySQL:
SELECT
    email,
    SUBSTRING(email, 1, INSTR(email, '@') - 1) AS username
FROM employees
WHERE email IS NOT NULL;

-- Format employee names as "Last, F." (Last Name, First Initial with period)
SELECT
    CONCAT(last_name, ', ', LEFT(first_name, 1), '.') AS formatted_name
FROM employees
ORDER BY last_name;
```

## 8. CASE Expressions — Conditional Logic in SQL

The `CASE` expression is SQL's way of embedding `if-then-else` logic directly inside a query. It allows you to produce different output values based on different conditions — dynamically transforming raw data into categorized, classified, or formatted results, all without touching the application code.

`CASE` is not a statement (something you execute in a procedural sequence) — it is an **expression** (something that produces a value). This means you can use it anywhere a value is expected: in `SELECT`, in `WHERE`, in `ORDER BY`, in `GROUP BY`, and even inside aggregate functions.

There are two syntactic forms of `CASE`: the **Simple CASE** and the **Searched CASE**. Both produce the same kinds of results but are suited to different situations.

---

### 8.1 Simple CASE

The Simple `CASE` compares a single expression to a list of possible values. You provide the expression once at the top, and then list `WHEN value THEN result` pairs. It is essentially a clean, readable `switch` or `match` statement.

```sql
-- Translate dept_id numbers into human-readable department names
SELECT
    first_name,
    last_name,
    dept_id,
    CASE dept_id
        WHEN 1 THEN 'Engineering'
        WHEN 2 THEN 'Marketing'
        WHEN 3 THEN 'Sales'
        ELSE 'Unknown / Unassigned'    -- ELSE handles all non-matching values, including NULL
    END AS department_name
FROM employees;

-- Result:
-- Alice   | Johnson | 1 | Engineering
-- Bob     | Smith   | 1 | Engineering
-- Carol   | Lee     | 2 | Marketing
-- David   | Kim     | 2 | Marketing
-- Eve     | Brown   | 3 | Sales
-- Frank   | Davis   | 1 | Engineering
-- Grace   | Wilson  | 3 | Sales
-- Henry   | Moore   |NULL| Unknown / Unassigned
```

The `ELSE` clause is optional, but if you omit it and no `WHEN` condition matches, the `CASE` expression returns `NULL`. It is generally safer to include an explicit `ELSE` to handle unexpected values.

---

### 8.2 Searched CASE

The Searched `CASE` is more powerful and flexible than the Simple form. Instead of comparing a single expression to fixed values, each `WHEN` clause contains a full boolean condition — any expression that evaluates to `TRUE` or `FALSE`. The database evaluates each `WHEN` condition in sequence from top to bottom and returns the result of the first condition that evaluates to `TRUE`.

```sql
-- Classify employees into salary bands
SELECT
    first_name,
    last_name,
    salary,
    CASE
        WHEN salary IS NULL          THEN 'Not Disclosed'
        WHEN salary < 40000          THEN 'Entry Level'
        WHEN salary BETWEEN 40000
                      AND 69999      THEN 'Mid Level'
        WHEN salary BETWEEN 70000
                      AND 99999      THEN 'Senior Level'
        WHEN salary >= 100000        THEN 'Executive Level'
        ELSE 'Uncategorized'
    END AS salary_band
FROM employees
ORDER BY salary DESC NULLS LAST;
```

The result of this query would be:

```
+------------+-----------+-----------+-----------------+
| first_name | last_name | salary    | salary_band     |
+------------+-----------+-----------+-----------------+
| Eve        | Brown     | 110000.00 | Executive Level |
| Alice      | Johnson   |  95000.00 | Senior Level    |
| Carol      | Lee       |  78000.00 | Senior Level    |
| Bob        | Smith     |  62000.00 | Mid Level       |
| David      | Kim       |  55000.00 | Mid Level       |
| Grace      | Wilson    |  48000.00 | Mid Level       |
| Frank      | Davis     |  28000.00 | Entry Level     |
| Henry      | Moore     |  NULL     | Not Disclosed   |
+------------+-----------+-----------+-----------------+
```

Notice that the `WHEN salary IS NULL THEN 'Not Disclosed'` condition appears *first*. This is deliberate. Because `CASE` evaluates conditions from top to bottom and stops at the first match, placing the `NULL` check first ensures it is caught correctly. If it were placed after the numeric comparisons, any `NULL` salary would fall through all the number comparisons (which all return `NULL` for `NULL` values) and end up hitting the `ELSE` clause.

---

### 8.3 CASE in SELECT, ORDER BY, and Aggregations

One of the most powerful aspects of `CASE` is its versatility — you can embed it in virtually any part of a query.

**CASE in ORDER BY** allows you to implement custom sort orders that cannot be expressed with simple `ASC`/`DESC`.

```sql
-- Sort employees with a custom priority order: Sales first, then Engineering, then others
SELECT first_name, dept_id, job_title
FROM employees
ORDER BY
    CASE dept_id
        WHEN 3 THEN 1    -- Sales: highest priority
        WHEN 1 THEN 2    -- Engineering: second
        WHEN 2 THEN 3    -- Marketing: third
        ELSE 4           -- Everything else: last
    END ASC,
    last_name ASC;       -- Secondary sort: alphabetical within each group
```

**CASE in aggregate functions** is an extremely powerful pattern that lets you perform conditional aggregation — counting or summing only the rows that meet specific criteria, all within a single query. This is often called a **pivot** operation.

```sql
-- Count employees in each salary band in a single query (conditional aggregation)
SELECT
    COUNT(*)                                      AS total_employees,
    COUNT(CASE WHEN salary < 40000 THEN 1 END)   AS entry_level_count,
    COUNT(CASE WHEN salary BETWEEN 40000 AND 69999 THEN 1 END) AS mid_level_count,
    COUNT(CASE WHEN salary >= 70000 THEN 1 END)  AS senior_plus_count,
    COUNT(CASE WHEN salary IS NULL THEN 1 END)   AS undisclosed_count
FROM employees;

-- Total payroll broken out by department in a single row
SELECT
    SUM(CASE WHEN dept_id = 1 THEN salary ELSE 0 END) AS engineering_payroll,
    SUM(CASE WHEN dept_id = 2 THEN salary ELSE 0 END) AS marketing_payroll,
    SUM(CASE WHEN dept_id = 3 THEN salary ELSE 0 END) AS sales_payroll
FROM employees
WHERE salary IS NOT NULL;
```

This conditional aggregation pattern is extremely common in reporting dashboards and analytical queries where you want to produce a summary row that breaks data down into multiple categories simultaneously.

## 9. NULL Handling — IS NULL, COALESCE, NULLIF

`NULL` is one of the most misunderstood and mishandled concepts in all of SQL. It appears simple at first — it just means "no value" or "missing" — but its behavior under comparison, arithmetic, and logic is subtle enough to cause genuine bugs in production systems written by experienced developers. Mastering `NULL` handling is an essential mark of SQL proficiency.

---

### 9.1 Understanding NULL

`NULL` in SQL does not mean zero. It does not mean an empty string. It does not mean `FALSE`. It means "unknown" — the value is absent, undefined, or not applicable. This "unknown" semantics is what causes `NULL` to behave so differently from all other values.

The foundational rule is this: **any arithmetic or comparison operation involving NULL produces NULL**. And in a boolean context, `NULL` is treated as neither `TRUE` nor `FALSE` — it is a third logical state called `UNKNOWN`. Rows that produce `UNKNOWN` in a `WHERE` condition are discarded, just like rows that produce `FALSE`.

```
The three-valued logic of SQL:

TRUE  AND TRUE  = TRUE
TRUE  AND FALSE = FALSE
TRUE  AND NULL  = NULL    <-- UNKNOWN, not TRUE
FALSE AND NULL  = FALSE   <-- FALSE wins here

TRUE  OR FALSE = TRUE
TRUE  OR NULL  = TRUE     <-- TRUE wins here
FALSE OR NULL  = NULL     <-- UNKNOWN

NOT TRUE  = FALSE
NOT FALSE = TRUE
NOT NULL  = NULL          <-- Inverting UNKNOWN is still UNKNOWN
```

This three-valued logic leads to the most common NULL trap in SQL: using `=` or `<>` to compare with NULL.

```sql
-- These NEVER return any rows, regardless of what's in the table:
WHERE salary = NULL      -- NULL = NULL evaluates to NULL (not TRUE)
WHERE salary != NULL     -- NULL != NULL evaluates to NULL (not TRUE)

-- The ONLY way to test for NULL:
WHERE salary IS NULL
WHERE salary IS NOT NULL
```

Arithmetic involving NULL also produces NULL:

```sql
SELECT NULL + 100;       -- NULL
SELECT NULL * 50;        -- NULL
SELECT 'hello' || NULL;  -- NULL  (concatenating with NULL = NULL in most databases)
SELECT NULL = NULL;      -- NULL  (not TRUE!)
```

---

### 9.2 IS NULL and IS NOT NULL

`IS NULL` and `IS NOT NULL` are the only correct and reliable ways to test whether a column's value is `NULL`. They are special operators, not regular comparison operators, and they are designed specifically to interact with the three-valued logic of SQL.

```sql
-- Find employees who have NOT been assigned to any department
SELECT first_name, last_name
FROM employees
WHERE dept_id IS NULL;
-- Result: Henry Moore (dept_id is NULL)

-- Find employees who HAVE been assigned to a department
SELECT first_name, last_name, dept_id
FROM employees
WHERE dept_id IS NOT NULL;

-- Find employees with no recorded email address
SELECT first_name, last_name
FROM employees
WHERE email IS NULL;
-- Result: Frank Davis

-- Combining NULL checks with other conditions
SELECT first_name, salary
FROM employees
WHERE salary IS NOT NULL
  AND salary < 60000;

-- A subtle real-world example:
-- Find employees who are NOT in department 1
-- (This correctly handles the case where dept_id is NULL)
SELECT first_name, dept_id
FROM employees
WHERE dept_id <> 1 OR dept_id IS NULL;
-- Without the 'OR dept_id IS NULL', Henry (whose dept_id is NULL) would be excluded
-- because NULL <> 1 evaluates to NULL, not TRUE
```

---

### 9.3 COALESCE — The Fallback Chain

`COALESCE` is one of the most practically useful functions in SQL. It accepts a list of two or more arguments and returns the first argument in the list that is not `NULL`. If all arguments are `NULL`, it returns `NULL`.

Think of `COALESCE` as a fallback chain: "Try the first value; if it's NULL, try the second; if that's also NULL, try the third," and so on.

```sql
-- Syntax: COALESCE(value1, value2, value3, ...)
-- Returns the first non-NULL value in the list.

-- Replace NULL salary with a default display value
SELECT
    first_name,
    COALESCE(salary, 0)             AS salary_or_zero,
    COALESCE(salary, 0) * 12        AS annual_cost
FROM employees;
-- Henry's NULL salary becomes 0 for computation purposes

-- Provide a fallback display text for NULL values
SELECT
    first_name,
    COALESCE(email, 'No email on file') AS contact_email
FROM employees;
-- Frank's NULL email becomes: 'No email on file'

-- Use the first available contact method (email, then phone, then 'Unknown')
-- (Assuming we had a phone column)
SELECT
    first_name,
    COALESCE(email, phone_number, 'No contact info') AS best_contact
FROM employees;

-- COALESCE in a JOIN to handle NULLs from LEFT JOINs
SELECT
    e.first_name,
    COALESCE(d.dept_name, 'Unassigned') AS department
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;
-- Employees with no department (like Henry) show 'Unassigned' instead of NULL
```

`COALESCE` is also the SQL Standard function. Some databases also provide `ISNULL(value, replacement)` (SQL Server) and `IFNULL(value, replacement)` (MySQL) as two-argument shorthand — but `COALESCE` is preferred because it is portable across all major databases.

```sql
-- All three are equivalent but only COALESCE is portable:
SELECT COALESCE(salary, 0) FROM employees;  -- SQL Standard (works everywhere)
SELECT ISNULL(salary, 0)   FROM employees;  -- SQL Server only
SELECT IFNULL(salary, 0)   FROM employees;  -- MySQL only
SELECT NVL(salary, 0)      FROM employees;  -- Oracle only
```

---

### 9.4 NULLIF — Turning a Value into NULL

`NULLIF` is the inverse of `COALESCE`. While `COALESCE` replaces `NULL` with a real value, `NULLIF` replaces a real value with `NULL` under certain conditions.

`NULLIF(expression1, expression2)` compares the two expressions. If they are equal, it returns `NULL`. If they are not equal, it returns `expression1` unchanged.

```sql
-- Syntax: NULLIF(expression1, expression2)
-- If expression1 = expression2, returns NULL.
-- Otherwise, returns expression1.

-- Avoid division by zero errors by converting 0 to NULL
-- (Dividing by NULL produces NULL, which is safe. Dividing by 0 causes an error.)
SELECT
    dept_id,
    total_salary / NULLIF(employee_count, 0) AS avg_salary
FROM department_summary;
-- If employee_count is 0, NULLIF converts it to NULL, and the division returns NULL
-- instead of throwing a "division by zero" error.

-- Convert sentinel/placeholder values to proper NULL
-- Imagine a legacy system that stores 'N/A' or 'UNKNOWN' as the "no value" indicator
SELECT
    first_name,
    NULLIF(job_title, 'N/A')     AS clean_job_title,
    NULLIF(job_title, 'UNKNOWN') AS verified_title
FROM employees;

-- Comparing COALESCE and NULLIF together
-- Use NULLIF to normalize, then COALESCE to provide a default
SELECT
    first_name,
    COALESCE(NULLIF(TRIM(email), ''), 'No email provided') AS clean_email
FROM employees;
-- This handles: NULL email, empty string email, whitespace-only email
-- all normalized to 'No email provided'
```

```
+------------------------------------------------------------------+
|             NULL Handling Functions Summary                      |
+------------+-----------------------------------------------------+
| Function   | What it does                                        |
+------------+-----------------------------------------------------+
| IS NULL    | Tests if a value is NULL (use in WHERE/HAVING)      |
| IS NOT NULL| Tests if a value is not NULL                        |
| COALESCE   | Returns first non-NULL from a list of values        |
| NULLIF     | Returns NULL if two expressions are equal           |
| NVL        | Oracle-only shorthand for 2-arg COALESCE            |
| ISNULL     | SQL Server 2-arg shorthand for COALESCE             |
| IFNULL     | MySQL 2-arg shorthand for COALESCE                  |
+------------+-----------------------------------------------------+
```

## 10. Putting It All Together

Let us now write a set of queries that draw on every concept covered in this chapter simultaneously. These are the kinds of queries you will write in real production systems — they look complex at first glance, but each part is familiar once you know the individual building blocks.

**Query 1: Employee Report with Full Formatting**

```sql
-- A comprehensive employee report demonstrating aliases, expressions,
-- CASE, COALESCE, and ORDER BY together
SELECT
    e.emp_id,
    CONCAT(e.last_name, ', ', e.first_name)   AS full_name,
    COALESCE(d.dept_name, 'Unassigned')        AS department,
    COALESCE(e.job_title, 'Not Specified')     AS position,
    COALESCE(e.salary, 0)                      AS salary,
    ROUND(COALESCE(e.salary, 0) * 0.10, 2)    AS estimated_bonus,
    CASE
        WHEN e.salary IS NULL       THEN 'Undisclosed'
        WHEN e.salary < 40000       THEN 'Entry'
        WHEN e.salary < 70000       THEN 'Mid'
        WHEN e.salary < 100000      THEN 'Senior'
        ELSE                             'Executive'
    END AS salary_band,
    CASE e.is_active
        WHEN TRUE  THEN 'Active'
        WHEN FALSE THEN 'Inactive'
    END AS status
FROM employees   AS e
LEFT JOIN departments AS d ON e.dept_id = d.dept_id
WHERE e.is_active = TRUE
ORDER BY
    d.dept_name ASC NULLS LAST,
    e.salary DESC NULLS LAST;
```

**Query 2: Department Summary with Conditional Aggregation**

```sql
-- Department-level summary with NULLs handled and salary bands computed
SELECT
    COALESCE(d.dept_name, 'No Department')   AS department,
    COUNT(e.emp_id)                           AS total_employees,
    COUNT(e.salary)                           AS employees_with_salary,
    COALESCE(ROUND(AVG(e.salary), 2), 0)     AS avg_salary,
    SUM(CASE WHEN e.salary < 50000          THEN 1 ELSE 0 END) AS under_50k,
    SUM(CASE WHEN e.salary BETWEEN 50000
                            AND 99999       THEN 1 ELSE 0 END) AS mid_range,
    SUM(CASE WHEN e.salary >= 100000        THEN 1 ELSE 0 END) AS over_100k
FROM employees   AS e
LEFT JOIN departments AS d ON e.dept_id = d.dept_id
GROUP BY d.dept_name
HAVING COUNT(e.emp_id) > 0
ORDER BY avg_salary DESC NULLS LAST;
```

**Query 3: Top Earners Per Page (Pagination)**

```sql
-- Get page 2 (employees ranked 6-10 by salary), with clean output
SELECT
    ROW_NUMBER() OVER (ORDER BY salary DESC NULLS LAST) AS rank_number,
    CONCAT(first_name, ' ', last_name)                  AS employee_name,
    COALESCE(job_title, 'Role Not Assigned')             AS role,
    COALESCE(CAST(salary AS VARCHAR), 'Confidential')    AS salary_display
FROM employees
WHERE is_active = TRUE
ORDER BY salary DESC NULLS LAST
LIMIT 5 OFFSET 5;  -- Page 2: skip first 5, return next 5
```

## Summary

The six topics covered in this chapter are not isolated features — they are the fundamental building blocks of every practical SQL query, woven together in combinations that express real business logic.

**WHERE** narrows the universe of rows you work with, using a rich vocabulary of comparison and logical operators that can express almost any imaginable filtering condition. **ORDER BY** brings order out of chaos, giving your results a predictable, meaningful sequence, with full control over ascending, descending, and NULL placement. **LIMIT and OFFSET** make large datasets manageable, and together they enable the pagination pattern that powers virtually every list, feed, and table in modern applications.

**DISTINCT** cleanses your output of redundant repetition, extracting the unique values or combinations that actually matter. **Aliases** lend your queries clarity and expressiveness, giving computed columns meaningful names and giving long table names short, readable handles. **Arithmetic and string expressions** extend SQL from a mere retrieval tool into a transformation engine, capable of deriving new facts from stored ones.

**CASE expressions** bring the full power of conditional logic into the query itself, enabling classification, pivoting, and custom ordering without touching application code. And finally, the trio of **IS NULL, COALESCE, and NULLIF** arms you with the tools to tame SQL's most famously subtle concept — the `NULL` value — turning potential bugs and surprises into controlled, predictable, readable behavior.

Master these tools together, and you will find that almost any data question you need to answer can be expressed clearly, concisely, and correctly in SQL.
