# Index Pitfalls — A Deep Study Guide

> *"The road to a slow database is paved with good intentions — and too many indexes. Every index you add in the name of performance carries a hidden bill that you will pay on every write, on every vacuum, on every disk read of a bloated page. The engineer who understands indexing's costs as deeply as its benefits is the one whose systems age gracefully, while others scramble to understand why their perfectly indexed table is slower than the one with no indexes at all."*

We have spent the previous chapters learning how indexes work, what types exist, and how to design them strategically. Now we turn to the darker side of the same knowledge: the ways that indexes can silently harm your system rather than help it. The pitfalls of indexing are especially treacherous precisely because they are quiet. A misconfigured index does not throw an error. It does not refuse to work. It simply performs its maintenance duty at a cost you did not expect, or fails to be used by the optimizer in a query where you assumed it would be, or grows larger and slower over months until your once-fast table has become a burden. Understanding these failure modes deeply is as essential as understanding index mechanics — because you cannot navigate safely around a danger you cannot see.

## 1. Over-Indexing — Write Overhead

### The Law of Diminishing Returns, Compounded

There is a natural human tendency, once you understand that indexes make reads faster, to index everything — to add an index to every column that might ever appear in a WHERE clause, just in case. This is one of the most damaging mistakes in database engineering, and it stems from failing to internalize one of the most fundamental truths about indexes: **every index you add to a table is paid for on every write to that table, forever**.

When you insert a new row into a table that has ten indexes, the database does not perform one write — it performs eleven writes: one to the table's data pages (the heap or clustered index), and one to each of the ten index structures. Each of these is a B-Tree insertion, potentially involving a page split if the target page is full. When you update a row and the updated column is part of an index, the database must delete the old index entry and insert a new one — two write operations per indexed column changed. When you delete a row, the database must remove the entry from every index. All of this happens synchronously, within the same transaction, before the commit is acknowledged.

```
  WRITE AMPLIFICATION: The Hidden Cost of Over-Indexing

  Table: orders with 10 indexes

  Single INSERT operation:
  ┌─────────────────────────────────────────────────────────────────┐
  │  1. Write new row to table heap/clustered index                  │
  │  2. Insert entry into idx_orders_customer_id                     │
  │  3. Insert entry into idx_orders_status                          │
  │  4. Insert entry into idx_orders_created_at                      │
  │  5. Insert entry into idx_orders_region                          │
  │  6. Insert entry into idx_orders_total                           │
  │  7. Insert entry into idx_orders_product_category               │
  │  8. Insert entry into idx_orders_payment_method                  │
  │  9. Insert entry into idx_orders_shipping_carrier               │
  │ 10. Insert entry into idx_orders_priority                        │
  │ 11. Insert entry into idx_orders_status_customer_composite       │
  └─────────────────────────────────────────────────────────────────┘
  11 write operations per row inserted.

  At 10,000 inserts/second:
  Table has 2 indexes:   20,000 writes/sec  ← comfortable
  Table has 10 indexes: 110,000 writes/sec  ← under pressure
  Table has 20 indexes: 210,000 writes/sec  ← disk I/O saturated

  UPDATE that changes 5 indexed columns:
  2 indexes untouched (unchanged columns): no update needed
  5 indexes touched: each requires DELETE old entry + INSERT new entry
  = 10 index write operations + 1 table write = 11 total for one UPDATE!

  The more indexes you have, the more your write throughput
  is consumed by index maintenance rather than actual data.
```

### The Cascading Effects on Write Throughput

The write overhead of over-indexing cascades in ways that are not immediately obvious. Each index write is not just a write — it may cause a **page split**, requiring allocation of a new page, writing two pages instead of one, and updating the parent page with a new separator key. Under heavy write load, page splits cascade through the tree and consume more I/O than the original writes. Furthermore, all these write operations must be logged to the **Write-Ahead Log (WAL)** for crash recovery purposes. A table with 20 indexes generates 20 times more WAL data than the same table with 1 index, which saturates the I/O bandwidth available for WAL writes and increases the time to replicate changes to standby servers.

The lock implications are equally serious. In many databases, modifying an index page requires a lock on that page. Under concurrent write workloads, multiple transactions trying to write to the same index page simultaneously cause **lock contention** — each transaction must wait for the others to release the page lock. With more indexes, there are more lock points, and contention becomes more likely across the board.

### How to Audit for Over-Indexing

Every major database provides system catalog views that track how often each index is actually used. An unused index is pure cost — it consumes space, slows writes, and provides zero read benefit. Regularly auditing these statistics is one of the most valuable maintenance habits you can develop.

```sql
-- PostgreSQL: Find unused or rarely used indexes
-- (pg_stat_user_indexes is reset by server restart or pg_stat_reset())
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan        AS times_index_was_used,
    idx_tup_read    AS rows_read_via_index,
    idx_tup_fetch   AS rows_fetched_via_index,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC, pg_relation_size(indexrelid) DESC;

-- Red flags to investigate:
-- idx_scan = 0      → Index has NEVER been used since last reset. Drop candidate.
-- idx_scan < 100    → Used very rarely. Is it worth its write overhead?
-- Large index_size + low idx_scan → Expensive to maintain, barely ever used.

-- Cross-reference with table write activity:
SELECT
    tablename,
    n_tup_ins AS inserts,
    n_tup_upd AS updates,
    n_tup_del AS deletes
FROM pg_stat_user_tables
WHERE tablename = 'orders';
-- If inserts+updates+deletes >> reads via index, the index costs more than it earns.
```

The discipline of over-indexing prevention is an ongoing practice, not a one-time design decision. As your application evolves, queries change, new features are added, and old queries retire. An index that served a critical query six months ago may be completely unused today because the query was refactored or the feature was removed. Regular index audits — every few months on active systems — ensure you are only paying for the indexes you are actually using.

## 2. Index Bloat

### How Indexes Grow Fat Over Time

An index, like a database table, does not automatically reclaim space when data is deleted or updated. In a B-Tree index, when an entry is removed (because the corresponding row was deleted or updated), the space that entry occupied is marked as "available for reuse" within that page — but it is not returned to the operating system. If new entries happen to fit into those freed slots, they will be reused. But if the freed slots accumulate faster than new entries arrive, or if the new entries have different sizes than the freed ones, the index pages gradually become partially empty — a phenomenon called **index bloat**.

Index bloat is not just a storage problem. A bloated index is a **performance problem**. When index pages are only 40% or 50% full (where they should be 80-90% full), the same number of active index entries spans twice as many pages as necessary. This means more page reads to scan a range of index entries, a larger index footprint in the buffer pool cache (displacing other useful data), and more time to traverse the tree. An index that was once 500 MB and fast becomes a 1.2 GB index that is slower — not because it has grown in the number of meaningful entries, but because it has grown in wasted space.

```
  INDEX BLOAT ILLUSTRATED

  Healthy index page (80% utilized):
  ┌─────────────────────────────────────────────────────────────────┐
  │ [Entry 01][Entry 02][Entry 03][Entry 04][Entry 05][Entry 06]    │
  │ [Entry 07][Entry 08][Entry 09][Entry 10][  FREE  ][  FREE  ]    │
  └─────────────────────────────────────────────────────────────────┘
  10 live entries, 2 free slots. 83% utilized. Efficient.

  Bloated index page (40% utilized) — after heavy deletes/updates:
  ┌─────────────────────────────────────────────────────────────────┐
  │ [Entry 01][  DEAD  ][  DEAD  ][Entry 04][  DEAD  ][  DEAD  ]    │
  │ [  DEAD  ][Entry 08][  DEAD  ][  DEAD  ][  DEAD  ][  DEAD  ]    │
  └─────────────────────────────────────────────────────────────────┘
  Only 3 live entries occupy a full page. 25% utilized. Wasteful.
  To read 10 live entries, the DB now reads ~4 pages instead of ~1.

  BLOAT OVER TIME (table with heavy update/delete activity):

  Month 1:  Index size = 500 MB  (95% utilized, healthy)
  Month 3:  Index size = 600 MB  (80% utilized, still fine)
  Month 6:  Index size = 850 MB  (55% utilized, degrading)
  Month 12: Index size = 1.4 GB  (35% utilized, significantly bloated)
  Month 18: Index size = 2.1 GB  (25% utilized, severe bloat)

  The number of actual index entries may have barely changed.
  The bloat is pure waste — empty and dead space within the index.
```

### What Causes Bloat

The primary driver of index bloat is **updates to indexed columns**. In most database implementations (particularly PostgreSQL's MVCC model), an UPDATE does not modify a row in place — it writes a new version of the row and marks the old version as dead. For each indexed column whose value changed, the old index entry pointing to the old row version must be "deleted" (marked dead), and a new entry pointing to the new row version must be inserted. This effectively doubles the number of index entries per update: one dead entry (not yet reclaimed) and one live entry. If your application frequently updates indexed columns, the index accumulates dead entries faster than they can be reclaimed.

Secondary causes of bloat include **bulk deletes** (deleting a large number of rows leaves many dead index entries), and **sequential inserts followed by deletions** (inserting millions of rows and then deleting a significant fraction of them leaves the index partially full throughout).

### Detecting and Fixing Index Bloat

PostgreSQL provides the `pgstattuple` extension for measuring exact bloat statistics. Without that extension, you can estimate bloat by comparing the index's actual size with its theoretical minimum size based on the number of live tuples.

```sql
-- Install the extension (requires superuser)
CREATE EXTENSION IF NOT EXISTS pgstattuple;

-- Measure exact bloat of a specific index
SELECT
    index_size,
    leaf_pages,
    leaf_density,   -- How full are leaf pages? Ideal: 80-100%
    dead_leaf_pages,
    dead_tuple_count,
    dead_tuple_percent
FROM pgstatindex('idx_orders_customer_id');

-- Interpretation:
-- leaf_density < 50%: significant bloat, consider rebuilding
-- dead_tuple_percent > 20%: VACUUM needed, or autovacuum is falling behind

-- Simple estimate of bloat (no extension needed):
SELECT
    pg_relation_size('idx_orders_customer_id') AS current_size,
    -- Theoretical minimum: avg entry size × number of live tuples / page_size
    -- compared to actual size:
    pg_size_pretty(pg_relation_size('idx_orders_customer_id')) AS current_pretty;
-- If current_size >> expected, bloat is present.

-- ─────────────────────────────────────────────────────────────────
-- FIXING INDEX BLOAT: Two approaches
-- ─────────────────────────────────────────────────────────────────

-- APPROACH 1: REINDEX (rebuilds the index from scratch — LOCKS table!)
-- Traditional: acquires ShareLock — blocks all writes during rebuild
REINDEX INDEX idx_orders_customer_id;  -- DANGEROUS on production: blocks writes!

-- Modern PostgreSQL 12+: CONCURRENTLY rebuilds without blocking writes
REINDEX INDEX CONCURRENTLY idx_orders_customer_id;
-- Slower (runs in background), but safe for production systems.

-- APPROACH 2: DROP and recreate CONCURRENTLY
-- More flexible — you can change index definition during the rebuild
DROP INDEX CONCURRENTLY idx_orders_customer_id;
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders (customer_id);

-- APPROACH 3: For the whole table at once (pg_repack — third party tool)
-- pg_repack rebuilds table AND all indexes with zero downtime:
-- pg_repack --table orders mydb
-- This is the gold standard for production bloat remediation.
```

The prevention of index bloat is more elegant than its cure. Tuning **autovacuum** to run more frequently on heavily-updated tables (we will cover this in the next section), using an appropriate **fill factor** (leaving deliberate free space in index pages so that updates can slide into existing pages without splitting them), and avoiding unnecessary updates to indexed columns all contribute to keeping index bloat under control.

## 3. Index Invalidation — Implicit Type Casts and Functions on Columns

### The Index That Is There But Does Nothing

Perhaps the most insidious category of index pitfall is **index invalidation** — the situation where an index exists and is perfectly well-formed, the query is filtering on the indexed column, and yet the query optimizer refuses to use the index. The query runs as a full table scan as if no index existed. No error is thrown. No warning is issued. The index silently fails to help, and without examining the query plan, you would never know.

Index invalidation almost always occurs because the query is not actually comparing the raw column value to the search parameter. Instead, the database is implicitly or explicitly transforming one or both sides of the comparison — applying a function to the column, implicitly casting the column to a different type, or comparing the column to a value of a different type that requires coercion. Any of these transformations breaks the index lookup because the index is built on the raw, untransformed column values, not on the results of the transformation.

### Cause 1: Explicit Functions Applied to the Column

The most straightforward case is when a developer applies a function to an indexed column in the WHERE clause. As we discussed in the Expression Index chapter, the solution to case-insensitive search is `WHERE LOWER(email) = LOWER($1)` — but only if you have defined an expression index on `LOWER(email)`. If you have a regular index on `email` (the raw values) and your query uses `LOWER(email)`, the regular index is completely bypassed. The function transforms the column value, and the index — which is sorted by untransformed values — has no way to efficiently locate the transformed results.

```
  INDEX INVALIDATION BY FUNCTION ON COLUMN

  Index on: email  (raw column, mixed-case values)
  Index stores: 'Alice@Example.COM', 'BOB@GMAIL.COM', 'carol@yahoo.com'
                sorted lexicographically by original value

  Query A: WHERE email = 'alice@example.com'
  → Looks up 'alice@example.com' in the index (exact match on raw value)
  ✓ USES index → O(log N) lookup
  (Finds nothing because 'alice@example.com' ≠ 'Alice@Example.COM')

  Query B: WHERE LOWER(email) = 'alice@example.com'
  → The database CANNOT look up LOWER(email)='alice@example.com' in the
    raw email index. The index has no concept of lowercased values.
  → Must scan EVERY row, apply LOWER() to each email, compare result.
  ✗ INDEX BYPASSED → full table scan!

  Query C: WHERE email ILIKE 'alice@example.com'  (case-insensitive LIKE)
  → ILIKE internally applies case folding → same problem
  ✗ INDEX BYPASSED → full table scan!

  SOLUTION: Expression index → CREATE INDEX ON users (LOWER(email))
  Now Query B uses the expression index → O(log N) ✓
```

The same problem occurs with date manipulation. A query like `WHERE DATE(created_at) = '2024-03-15'` applies the `DATE()` function to strip the time component from a timestamp. A regular index on `created_at` is useless for this query. The correct approaches are either to rewrite the query as a range condition (`WHERE created_at >= '2024-03-15' AND created_at < '2024-03-16'`) — which the regular index can serve perfectly — or to create an expression index on `DATE(created_at)`.

### Cause 2: Implicit Type Casting

This is the most dangerous form of index invalidation because it is invisible in the query itself. It happens when the data type of the column and the data type of the comparison value do not match, and the database must perform an implicit type conversion to make the comparison possible. The direction of this conversion matters enormously.

If the database converts the **parameter value** to match the column's type (parameter → column type), the index can still be used, because the column itself remains untransformed. But if the database converts the **column value** to match the parameter's type (column → parameter type), it must evaluate the conversion for every row — which is equivalent to applying a function to the column — and the index is bypassed.

```
  IMPLICIT TYPE CAST: The Invisible Index Killer

  Table definition:
  CREATE TABLE users (
      id          BIGSERIAL PRIMARY KEY,
      account_no  VARCHAR(20) NOT NULL,  -- stored as TEXT
      ...
  );
  CREATE INDEX idx_users_account_no ON users (account_no);

  Case 1: Parameter matches column type → INDEX USED
  Query: WHERE account_no = '12345678'
  → '12345678' is a string literal → matches VARCHAR column type
  ✓ Index lookup: finds '12345678' in the index → O(log N)

  Case 2: Integer parameter vs. VARCHAR column → INDEX BYPASSED
  Query: WHERE account_no = 12345678   (integer literal, no quotes!)
  → Column is VARCHAR, parameter is INTEGER.
  → Database must convert account_no from VARCHAR to INTEGER for comparison.
  → This is like applying a function to the column: CAST(account_no AS INTEGER)
  → Index on (account_no) has no idea what CAST(account_no AS INTEGER) looks like.
  ✗ Full table scan — applies CAST() to every row!

  This is a COMMON bug in application code where:
    - The column is VARCHAR but stores numeric-looking values
    - The application sends an integer parameter instead of a string
    - In some ORMs, parameters may be sent without quotes in the SQL

  SOLUTION: Ensure the parameter type matches the column type.
  In application code: send '12345678' (string) not 12345678 (integer)
  In parameterized queries: use VARCHAR binding, not integer binding.
```

Another extremely common implicit cast scenario occurs with date/time types. A `TIMESTAMPTZ` (timestamp with time zone) column and a comparison against a plain `DATE` or `TIMESTAMP` value may trigger a cast, depending on the database and session timezone settings. PostgreSQL handles many of these casts gracefully (comparing a DATE to a TIMESTAMPTZ will often use the index by treating the DATE as a range), but explicit casts in the wrong direction can still break index usage.

### Cause 3: Collation Mismatches and Encoding Issues

A subtler form of index invalidation occurs when the **collation** (the rules for sorting and comparing strings) of the comparison parameter does not match the collation used when the index was built. An index is physically sorted according to a specific collation rule. If a query compares a string value using a different collation, the index's sort order is irrelevant to the query, and the optimizer cannot use it.

```sql
-- HOW TO DETECT INDEX INVALIDATION

-- Always use EXPLAIN to verify your index is being used:
EXPLAIN (ANALYZE, FORMAT TEXT)
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';

-- Good output (index is used):
-- Index Scan using idx_users_email_lower on users
--   Index Cond: (lower((email)::text) = 'alice@example.com'::text)

-- Bad output (index is bypassed):
-- Seq Scan on users
--   Filter: (lower((email)::text) = 'alice@example.com'::text)
-- "Seq Scan" = full sequential scan = index not used!

-- Checking for type mismatch issues:
-- Run EXPLAIN on your query and look for:
-- "Filter" (instead of "Index Cond") on an indexed column → index bypassed
-- "Seq Scan" on a table where you expect an Index Scan → index bypassed

-- To force the planner to use an index (for testing/debugging only):
-- SET enable_seqscan = OFF;
-- (Never use this in production — it tells you what plan the index WOULD give,
--  which is useful for understanding why the planner prefers seq scan)
```

## 4. Dead Tuples and VACUUM (PostgreSQL)

### PostgreSQL's MVCC Model and the Problem It Creates

PostgreSQL uses a concurrency control mechanism called **MVCC (Multi-Version Concurrency Control)**. The core idea of MVCC is elegant: rather than locking rows when a transaction reads or modifies them, PostgreSQL creates a new *version* of the row for each modification, keeping the old version alive for the benefit of concurrent transactions that started before the modification and need to see the old state. This allows readers and writers to proceed concurrently without blocking each other — a major advantage for high-concurrency systems.

However, MVCC creates a physical reality that must be actively managed: **dead tuples**. When a row is updated, the old version of the row remains physically on disk — it is not overwritten. It is simply marked with an `xmax` (transaction ID of the transaction that deleted or superseded it). Once every transaction that could possibly need to see this old version has completed, the old version is "dead" — it is no longer visible to any active transaction, it serves no purpose, and it is consuming disk space. Similarly, when a row is deleted, the row is not immediately removed from disk — it is just marked dead by setting its `xmax`. The physical removal of these dead versions is the job of **VACUUM**.

```
  MVCC AND DEAD TUPLES: What happens inside a PostgreSQL page

  BEFORE UPDATE (row version 1 is live):
  Table page:
  ┌────────────────────────────────────────────────────────────┐
  │ Tuple 1: xmin=100, xmax=0    (live) | id=42, name='Alice'  │
  │ Tuple 2: xmin=101, xmax=0    (live) | id=43, name='Bob'    │
  └────────────────────────────────────────────────────────────┘

  AFTER UPDATE (Alice → Alice Smith) by transaction 200:
  ┌────────────────────────────────────────────────────────────┐
  │ Tuple 1: xmin=100, xmax=200  (DEAD)  | id=42, name='Alice' │  ← Old version
  │ Tuple 2: xmin=101, xmax=0    (live)  | id=43, name='Bob'   │
  │ Tuple 3: xmin=200, xmax=0    (live)  | id=42, name='Alice  │  ← New version
  │                               Smith'                       │
  └────────────────────────────────────────────────────────────┘
  Tuple 1 is now DEAD — no transaction needs it.
  But it is still PHYSICALLY on disk, consuming space.

  Index state:
  B-Tree index on 'id':
  ┌────────────────────────────────────┐
  │ id=42 → ptr to Tuple 1 (DEAD!)     │  ← Index still points to dead tuple
  │ id=42 → ptr to Tuple 3 (live)      │  ← Index also points to new version
  │ id=43 → ptr to Tuple 2 (live)      │
  └────────────────────────────────────┘
  Index has a "dead" entry pointing to the old row version.
  This causes index bloat AND forces extra heap checks on every lookup.
```

### The Role of VACUUM

**VACUUM** is PostgreSQL's process for reclaiming space occupied by dead tuples and cleaning up dead index entries. It is the maintenance operation that keeps the database from accumulating an ever-growing pile of discarded row versions. Without regular VACUUM, three specific and serious problems emerge.

The first problem is **table and index bloat**: dead tuples accumulate on data pages and in index pages, consuming disk space and forcing the database to read more pages to find live data. The second problem is **query degradation**: as pages fill with dead tuples, the ratio of live data to page capacity drops, and the optimizer's statistics (which estimate how many rows a query will return) become inaccurate, leading to suboptimal query plans. The third and most catastrophic problem is **transaction ID wraparound**: PostgreSQL uses 32-bit transaction IDs, which wrap around after approximately 2 billion transactions. If VACUUM does not run often enough to advance the "relfrozenxid" (the oldest transaction ID that is considered frozen/old), the database will eventually stop accepting new transactions and force an emergency autovacuum — a scenario that causes downtime.

```
  VACUUM WORKFLOW

  Before VACUUM:
  Table page (50% dead):
  ┌──────────────────────────────────────────────────────────────┐
  │ [DEAD][LIVE][DEAD][LIVE][DEAD][DEAD][LIVE][DEAD][DEAD][LIVE] │
  └──────────────────────────────────────────────────────────────┘
  Index pages:
  ┌──────────────────────────────────────┐
  │ [ptr→DEAD][ptr→LIVE][ptr→DEAD]...    │
  └──────────────────────────────────────┘

  VACUUM runs (not VACUUM FULL):
  Step 1: Scan table, identify dead tuples.
  Step 2: For each dead tuple, remove corresponding index entries.
  Step 3: Mark dead tuple space as "free" (available for reuse).
  Step 4: Update visibility map (marks pages where all tuples are visible
          to all transactions → enables index-only scans in the future).
  Step 5: Update pg_stat for accurate query planning.

  After VACUUM (regular, not FULL):
  Table page (free space reclaimed, but file size unchanged):
  ┌──────────────────────────────────────────────────────────────┐
  │ [FREE][LIVE][FREE][LIVE][FREE][FREE][LIVE][FREE][FREE][LIVE] │
  └──────────────────────────────────────────────────────────────┘
  Space is marked FREE for REUSE — not returned to OS yet.
  Index entries for dead tuples have been removed.

  VACUUM FULL (aggressive — returns space to OS, but locks table!):
  Rewrites the entire table and all indexes with only live data.
  File size shrinks. Table is LOCKED during the operation.
  Use only during maintenance windows; never on a live production table.
  Prefer pg_repack for zero-downtime compaction.
```

### Autovacuum: The Automatic Maintenance Engine

PostgreSQL includes **autovacuum**, a background daemon that automatically triggers VACUUM on tables when they accumulate enough dead tuples. The thresholds that trigger autovacuum are controlled by configuration parameters:

```
  AUTOVACUUM TRIGGER FORMULA:

  autovacuum_vacuum_threshold    (default: 50 rows)  = minimum dead rows to trigger
  autovacuum_vacuum_scale_factor (default: 0.2)      = 20% of table row count

  Autovacuum triggers when:
  dead_rows > autovacuum_vacuum_threshold + (autovacuum_vacuum_scale_factor × live_rows)
  dead_rows > 50 + (0.2 × live_rows)

  For a table with 100 rows:    threshold = 50 + 20 = 70 dead rows → VACUUM
  For a table with 10,000 rows: threshold = 50 + 2,000 = 2,050 dead rows → VACUUM
  For a table with 1,000,000 rows: threshold = 50 + 200,000 = 200,050 dead rows

  PROBLEM: The default scale_factor is too generous for large tables!
  A table with 10M rows must accumulate 2,000,050 dead rows before autovacuum fires.
  That's 2 million dead tuples degrading your queries before cleanup begins.
```

For large, heavily-updated tables, the default autovacuum settings are dangerously conservative. You must tune the autovacuum parameters per-table to ensure timely cleanup:

```sql
-- Check current dead tuple accumulation across all tables:
SELECT
    relname              AS table_name,
    n_live_tup           AS live_rows,
    n_dead_tup           AS dead_rows,
    ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
    last_autovacuum      AS last_autovacuum_ran,
    last_autoanalyze     AS last_autoanalyze_ran
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- Red flags:
-- dead_pct > 10-20%:  autovacuum not keeping up → tune thresholds
-- last_autovacuum very old on a busy table → autovacuum is misconfigured

-- Tune autovacuum for a specific high-traffic table:
-- Lower thresholds so autovacuum fires more aggressively on this table
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor    = 0.01,   -- Fire when 1% of rows are dead
    autovacuum_vacuum_threshold       = 100,    -- Or when 100 rows are dead (min)
    autovacuum_analyze_scale_factor   = 0.005,  -- Re-analyze when 0.5% changed
    autovacuum_vacuum_cost_delay      = 2       -- Less sleep between work cycles
);

-- Verify the setting took effect:
SELECT relname, reloptions FROM pg_class WHERE relname = 'orders';
```

### The Visibility Map and Index-Only Scans

There is a subtle but important connection between VACUUM, the visibility map, and the **Index-Only Scan** performance we discussed in the covering index chapter. An Index-Only Scan succeeds — returning rows purely from index pages without reading table pages — only when the database can guarantee that the index entries are current and the rows they point to are visible. This guarantee is provided by the **visibility map**: a compact bitmap that PostgreSQL maintains alongside each table, where each bit indicates whether a given page contains only tuples that are visible to all current and future transactions (i.e., no dead tuples and no tuples in unfinished transactions).

VACUUM updates the visibility map as it processes each page. Pages that are fully vacuumed get their visibility map bit set, which immediately enables Index-Only Scans for queries that touch those pages. A table that is never vacuumed has no visibility map bits set, and every "Index-Only Scan" must actually check the table heap anyway — defeating the purpose of the covering index. This is why regular VACUUM is not just a space-reclamation concern — it is a **query performance concern** that directly affects whether your carefully designed covering indexes can achieve their full potential.

## 5. When the Planner Ignores Your Index

### The Query Optimizer Is (Usually) Right

When you discover through `EXPLAIN` that your carefully created index is being ignored in favor of a full table scan, the natural first instinct is frustration: "I built this index! Why isn't it being used?" The important thing to understand before taking any action is that the query optimizer is a sophisticated piece of software that has access to statistical information you may not — and in the majority of cases where it chooses a sequential scan over an index scan, **it is making the right decision**. The optimizer's job is to find the cheapest execution plan, and "cheapest" in terms of total I/O cost sometimes means not using an index.

However, the optimizer is not infallible. It makes decisions based on **cost estimates**, and those estimates depend on the accuracy of the statistics it has gathered about your data. When the statistics are stale, outdated, or simply not representative of the actual data distribution, the optimizer can make poor decisions — choosing a full table scan when an index would be dramatically faster, or vice versa. Understanding the reasons the optimizer might ignore your index, and knowing how to distinguish "correctly ignored" from "incorrectly ignored," is one of the most valuable diagnostic skills in database engineering.

### Reason 1: Low Selectivity (The Optimizer Is Right)

The most common and most correct reason for a planner to ignore an index is **low selectivity** — the index lookup would return a large fraction of the table's rows. As we established in Chapter 4.1, when the optimizer estimates that a query will return more than roughly 5-10% of the table's rows, the cost of random I/O through the index (one page read per matching row) exceeds the cost of a sequential scan (reading all pages in large sequential chunks). In this case, ignoring the index is the correct behavior.

```
  LOW SELECTIVITY: Planner correctly ignores index

  Table: orders (1,000,000 rows)
  Index: idx_orders_status ON orders (status)
  Status distribution: 'active'=800,000 (80%), 'closed'=200,000 (20%)

  Query A: WHERE status = 'active'  → matches 800,000 rows (80%)
  EXPLAIN shows: Seq Scan on orders  ← CORRECT! 800K random reads > seq scan

  Query B: WHERE status = 'closed'  → matches 200,000 rows (20%)
  EXPLAIN might show: Seq Scan on orders  ← Still possibly correct
  (200K random I/Os may still cost more than a 1M-row sequential scan)

  Query C: WHERE status = 'suspended'  → matches 100 rows (0.01%)
  EXPLAIN shows: Index Scan using idx_orders_status  ← CORRECT! Very selective.

  KEY INSIGHT: The same index on the same column is used for some values
  and not for others, based on the ESTIMATED SELECTIVITY of each specific value.
  The optimizer consults the histogram in pg_stats to estimate per-value frequency.
```

### Reason 2: Stale Statistics (The Optimizer Is Wrong)

The second reason — and the one where the optimizer is making a mistake — is **stale or inaccurate statistics**. The optimizer's cost estimates are only as good as the statistics it has. In PostgreSQL, statistics are stored in `pg_statistic` and are updated by the `ANALYZE` command (run automatically by autovacuum, or manually). If a table has undergone significant changes since the last ANALYZE — a large bulk import, a mass delete, or a major shift in the data distribution — the statistics may be badly outdated, causing the optimizer to dramatically misjudge selectivity.

```sql
-- Scenario: A new table was just bulk-loaded with 5M rows.
-- Autovacuum hasn't run ANALYZE yet. pg_stats shows 0 rows.
-- The optimizer has no statistics → assumes very small table → seq scan.

-- SYMPTOMS: An index scan EXPLAIN shows "rows=1" estimate, seq scan shows actual
-- Returns thousands of rows. Estimate is wildly off → statistics are stale.

-- DIAGNOSIS: Check when statistics were last updated:
SELECT relname, last_analyze, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- SOLUTION: Run ANALYZE to refresh statistics
ANALYZE orders;            -- Analyzes just the orders table
ANALYZE;                   -- Analyzes all tables in the database
VACUUM ANALYZE orders;     -- Vacuum + Analyze in one operation

-- After ANALYZE, run EXPLAIN again — the planner may now choose the index.

-- Check the statistics the planner is now using:
SELECT
    attname,
    n_distinct,
    correlation,     -- How well the physical order matches the index order (1.0=perfect)
    most_common_vals,
    most_common_freqs
FROM pg_stats
WHERE tablename = 'orders'
  AND attname = 'status';
```

### Reason 3: Poor Physical Correlation (Sequential Scan Wins on Old Data)

The `correlation` statistic in `pg_stats` measures how well the physical storage order of rows matches the sort order of the indexed column. A correlation of 1.0 means rows are physically sorted in exactly the same order as the index — every index lookup lands on a page that is sequential with the previous lookup, enabling efficient prefetching. A correlation of 0.0 means rows are in completely random order relative to the index — every index lookup lands on a completely different page, making each lookup a separate random I/O.

When correlation is poor and the query returns more than a handful of rows, random I/O through the index becomes dramatically more expensive than a sequential scan, and the optimizer correctly prefers the sequential scan. The solution is either to accept the sequential scan (if the table is read infrequently on this column) or to cluster the table by this index to restore physical ordering.

```
  CORRELATION AND ITS EFFECT ON INDEX USEFULNESS

  Table: orders (1,000,000 rows), indexed by created_at

  Case A: Table was loaded chronologically (correlation ≈ 1.0)
  Physical page layout:
  [Jan rows...] [Feb rows...] [Mar rows...] [Apr rows...]
  Index lookup for March orders → consecutive pages → prefetchable → FAST
  Optimizer: USE INDEX (random I/O is almost sequential here)

  Case B: Table has been heavily updated/inserted randomly (correlation ≈ 0.1)
  Physical page layout:
  [Jan/Aug/Mar mixed] [May/Jan/Dec mixed] [Feb/Sep/Nov mixed]
  Index lookup for March orders → scattered across all pages → random I/O
  For 30,000 March rows: up to 30,000 separate page reads!
  Optimizer: SKIP INDEX, use Sequential Scan instead (1M rows seq is faster)

  SOLUTION if you need fast indexed access despite poor correlation:
  CLUSTER orders USING idx_orders_created_at;
  -- Rewrites the table in index order → restores correlation to ~1.0
  -- NOTE: CLUSTER acquires an exclusive lock! Schedule during maintenance.
  -- pg_repack can cluster without locking.
```

### Reason 4: Parallel Sequential Scan

Modern databases can execute **parallel sequential scans** by splitting the table across multiple worker processes, each reading a different portion. A sequential scan that might take 10 seconds serially might complete in 2 seconds with 5 parallel workers. When the optimizer knows that parallelism is available and the query would benefit from it, a parallel sequential scan can outperform a single-threaded index scan — even when the index scan would win in a serial comparison.

### Reason 5: Very Small Tables

For tables with a small number of rows — typically fewer than a few hundred to a few thousand rows depending on the database's configuration — the overhead of traversing an index (reading index pages, following row pointers) is greater than simply reading all the table's pages directly. The optimizer knows this and correctly prefers sequential scans on small tables. This is not a problem — it is correct behavior. Do not add indexes to small tables hoping to speed them up; for small tables, no index will help.

### How to Force the Planner to Use an Index (For Debugging Only)

When you believe the optimizer is making the wrong decision (due to stale statistics or a specific edge case), you can temporarily disable sequential scans to see what the index-based plan looks like — this is purely a diagnostic tool, not a production setting:

```sql
-- DIAGNOSTIC ONLY: Force the planner to consider index scans
-- Do NOT use this in production; it overrides the optimizer's cost model
SET enable_seqscan = OFF;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'active';

-- If the forced index plan is actually faster (lower actual runtime),
-- the issue is stale statistics → run ANALYZE to fix it.
-- If the forced index plan is slower, the optimizer was RIGHT to seq scan.

-- Reset to normal:
SET enable_seqscan = ON;

-- Other useful settings for debugging planner decisions:
SET enable_indexscan     = OFF;   -- Force seq scan (test if index really helps)
SET enable_bitmapscan    = OFF;   -- Disable bitmap index scans
SET enable_nestloop      = OFF;   -- Force hash join or merge join (join testing)

-- Check planner cost estimates (understand WHY it chose seq scan):
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE customer_id = 42;
-- Look at "rows=" estimate vs "actual rows=" — big discrepancy = stale stats
-- Look at "cost=" for Index Scan path vs Seq Scan path to understand the math
```

## Summary: The Index Pitfall Diagnostic Checklist

The five pitfalls we have studied represent a complete taxonomy of the ways indexes can fail you in production. Understanding them transforms your approach from reactive ("why is this query slow?") to proactive ("what could go wrong with this index, and how do I prevent it?").

```
  INDEX PITFALL DIAGNOSTIC CHECKLIST

  SYMPTOM: Writes are slow / throughput has degraded
  ┌────────────────────────────────────────────────────────────────┐
  │ Check: How many indexes does this table have?                  │
  │ Check: Are any indexes never or rarely used? (pg_stat_user_   │
  │        indexes where idx_scan = 0)                            │
  │ Action: Drop unused indexes. Consolidate redundant indexes.    │
  └────────────────────────────────────────────────────────────────┘

  SYMPTOM: Table/index is larger than expected
  ┌────────────────────────────────────────────────────────────────┐
  │ Check: Dead tuple count (pg_stat_user_tables n_dead_tup)       │
  │ Check: Index bloat via pgstatindex leaf_density                │
  │ Action: VACUUM ANALYZE the table. Tune autovacuum thresholds.  │
  │         REINDEX CONCURRENTLY if index bloat > 50%.            │
  └────────────────────────────────────────────────────────────────┘

  SYMPTOM: Index exists but query still does full scan
  ┌────────────────────────────────────────────────────────────────┐
  │ Check 1: Run EXPLAIN — is it "Seq Scan" or "Index Scan"?       │
  │ Check 2: Is the WHERE clause applying a function to the column? │
  │          → Use expression index or rewrite query               │
  │ Check 3: Is there a type mismatch between column and parameter? │
  │          → Fix parameter type in application code              │
  │ Check 4: Are statistics stale? (last_autoanalyze very old)     │
  │          → Run ANALYZE orders;                                 │
  │ Check 5: Is selectivity genuinely low? (many rows returned)    │
  │          → Optimizer is probably RIGHT — consider partial index │
  └────────────────────────────────────────────────────────────────┘

  SYMPTOM: Index-Only Scan returning to heap (Heap Fetches > 0)
  ┌────────────────────────────────────────────────────────────────┐
  │ Check: Is autovacuum keeping the visibility map current?       │
  │ Check: pg_stat_user_tables n_dead_tup for the table           │
  │ Action: Run VACUUM ANALYZE to update visibility map            │
  └────────────────────────────────────────────────────────────────┘

  SYMPTOM: Performance degrades slowly over weeks/months
  ┌────────────────────────────────────────────────────────────────┐
  │ Check: Index bloat (leaf_density declining over time)          │
  │ Check: Autovacuum frequency (is it running often enough?)      │
  │ Check: New unused indexes added by developers chasing perf     │
  │ Action: Schedule regular index audits. Tune autovacuum.        │
  │         Use pg_repack for zero-downtime bloat removal.        │
  └────────────────────────────────────────────────────────────────┘
```

The deepest lesson of this chapter is that an index is not a passive decoration — it is a living structure that must be designed with care, monitored with diligence, and maintained with intention. The database does not manage your indexes for you. It maintains their structural integrity (ensuring they remain valid B-Trees), but it cannot tell you when you have too many, when they have grown bloated, when a query is accidentally bypassing them, or when autovacuum has fallen behind. That knowledge lives here, with you. And now that you have it, you can build systems that remain fast not just on the day they are launched, but for the years that follow.
