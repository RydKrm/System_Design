## 1. What the WAL Actually Is — The Intuition

Before we can talk about recovery, we must understand with great clarity what the Write-Ahead Log is, why it exists, and what problem it was designed to solve. Without this foundation, the recovery procedures will feel like magic rituals rather than logical consequences of an elegant design.

Imagine you are a bank teller. A customer walks in and asks you to transfer $10,000 from Account A to Account B. You must do two things: subtract $10,000 from Account A, and add $10,000 to Account B. Now imagine that after you subtract from Account A, the power goes out. When the power returns, Account A has been debited, but Account B has never been credited. The money has vanished from the system. This is the fundamental problem that the WAL solves — not just for bank transfers, but for every write operation in a database.

The solution the WAL provides is deceptively simple in concept: **before you touch anything, write down what you are about to do**. This written record — the log — must itself be safely on disk before you make any change to the actual data. If the power then cuts out at any moment, you can always look at the log to know exactly what was in progress, what was completed, and what needs to be undone or redone.

The word "Write-Ahead" in the name captures this idea perfectly. You always write to the log _ahead_ of — meaning before — writing to the actual data files. This single rule is the bedrock upon which all crash recovery is built.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    THE WRITE-AHEAD PRINCIPLE                            │
│                                                                         │
│   WITHOUT WAL (dangerous):                                              │
│                                                                         │
│   Transaction: UPDATE users SET balance = 900 WHERE id = 1             │
│                                                                         │
│   Step 1: Modify page in buffer pool (RAM) ────────► CRASH HERE?       │
│   Step 2: Write modified page to disk                                   │
│                                                                         │
│   Result after crash: Data file is half-written. Corrupted. Lost.      │
│                                                                         │
│   ─────────────────────────────────────────────────────────────────     │
│                                                                         │
│   WITH WAL (safe):                                                      │
│                                                                         │
│   Step 1: Write WAL record ("I will change page 7, slot 3              │
│            from balance=1000 to balance=900") ─► flush to disk         │
│   Step 2: Modify page in buffer pool (RAM) ────────► CRASH HERE?       │
│   Step 3: Eventually write modified page to disk (checkpoint)          │
│                                                                         │
│   Result after crash: WAL is safe on disk. Recovery replays            │
│   the WAL record. Balance becomes 900. No data lost. Ever.             │
└─────────────────────────────────────────────────────────────────────────┘
```

The WAL achieves something profound: it decouples the **logical guarantee** (your transaction committed and its effects are permanent) from the **physical reality** (the actual data page on disk may not yet reflect the change). As long as the WAL record is on disk, the commitment is real — even if the data file itself has not yet been updated.

## 2. The Anatomy of a WAL Record

The WAL is not a vague journal. Every entry — every WAL record — has a precise, structured format that contains exactly the information needed to reproduce or undo the change it describes.

```
┌────────────────────────────────────────────────────────────────────────┐
│                    STRUCTURE OF A SINGLE WAL RECORD                    │
│                                                                        │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │  HEADER (fixed size)                                             │  │
│  │                                                                  │  │
│  │  ┌──────────────┬─────────────┬────────────┬───────────────┐     │  │
│  │  │     LSN      │   XID       │  Resource  │   Prev LSN    │     │  │
│  │  │ (Log Seq Num)│ (Trans. ID) │  Manager   │ (back pointer)│     │  │
│  │  │  8 bytes     │  4 bytes    │  1 byte    │   8 bytes     │     │  │
│  │  └──────────────┴─────────────┴────────────┴───────────────┘     │  │
│  │                                                                  │  │
│  │  ┌─────────────┬────────────────────────────────────────────┐    │  │
│  │  │   Record    │   CRC Checksum                             │    │  │
│  │  │    Type     │   (detects corruption)                     │    │  │
│  │  │  (1 byte)   │   (4 bytes)                                │    │  │
│  │  └─────────────┴────────────────────────────────────────────┘    │  │
│  └──────────────────────────────────────────────────────────────────┘  │
│                                                                        │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │  PAYLOAD (variable size — the actual change description)         │  │
│  │                                                                  │  │
│  │  For a row UPDATE, payload contains:                             │  │
│  │  - Which relation (table OID)                                    │  │
│  │  - Which block (page number)                                     │  │
│  │  - The before-image (old data, for UNDO)                         │  │
│  │  - The after-image  (new data, for REDO)                         │  │
│  └──────────────────────────────────────────────────────────────────┘  │
│                                                                        │
│  LSN = Log Sequence Number                                             │
│  A globally unique, ever-increasing 64-bit integer.                    │
│  Every WAL record gets a unique LSN. LSN is the primary identity       │
│  of every event in the database's history.                             │
└────────────────────────────────────────────────────────────────────────┘
```

The **Log Sequence Number (LSN)** is the most important concept here. It is a 64-bit, ever-increasing number that uniquely identifies every WAL record ever written. It is the database's internal clock — not time-based, but sequence-based. Every page in the database also stores the LSN of the last WAL record that modified it. During recovery, the engine compares the LSN of a WAL record against the LSN stored in the page: if the WAL record's LSN is newer than what the page has recorded, the change described by the WAL record has not yet been applied to that page, and must be replayed. If the page's LSN is already equal to or newer than the WAL record's LSN, the change has already been applied and must not be replayed again. This is how recovery is made **idempotent** — safe to run multiple times without producing incorrect results.

WAL records are initially written into a small in-memory area called the **WAL buffer** (typically 64 MB in PostgreSQL). The WAL Writer background process periodically flushes these buffers to the WAL segment files on disk. When a transaction commits, PostgreSQL ensures the WAL buffer is flushed to disk immediately before returning success to the client — this is the fundamental durability guarantee.

## 3. How WAL Is Written — The Full Flow

To understand recovery, you must first understand the complete flow of a write operation, from the moment a transaction begins to the moment data is safely on disk.

```
┌─────────────────────────────────────────────────────────────────────────┐
│              COMPLETE WRITE FLOW WITH WAL                               │
│                                                                         │
│  BEGIN TRANSACTION                                                      │
│         │                                                               │
│         ▼                                                               │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │  1. Engine requests page from Buffer Pool                       │    │
│  │     (loads from disk if not already in RAM)                     │    │
│  └────────────────────────────┬────────────────────────────────────┘    │
│                               │                                         │
│                               ▼                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │  2. Engine constructs WAL record describing the change          │    │
│  │     Writes it into the WAL buffer (in RAM)                      │    │
│  └────────────────────────────┬────────────────────────────────────┘    │
│                               │                                         │
│                               ▼                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │  3. Engine modifies the page in the buffer pool (RAM only)      │    │
│  │     Page is now "dirty" — changed in RAM, not yet on disk       │    │
│  │     Page's LSN is updated to match the WAL record's LSN         │    │
│  └────────────────────────────┬────────────────────────────────────┘    │
│                               │                                         │
│                               ▼                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │  4. COMMIT issued by application                                │    │
│  │     WAL buffer is immediately flushed to WAL segment file       │    │
│  │     on disk (fsync). This is the durability guarantee.          │    │
│  │     SUCCESS is returned to the client ONLY after this flush.    │    │
│  └────────────────────────────┬────────────────────────────────────┘    │
│                               │                                         │
│                               ▼                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │  5. (Later, asynchronously) Checkpointer writes dirty pages     │    │
│  │     from buffer pool to the actual heap data files on disk.     │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  KEY INSIGHT:                                                           │
│  The WAL is on disk at step 4.                                          │
│  The data page may not reach disk until step 5, which could be          │
│  seconds or minutes later.                                              │
│  But the database is SAFE the moment step 4 completes.                  │
└─────────────────────────────────────────────────────────────────────────┘
```

This flow reveals something important: at any given moment, the WAL files on disk represent the most up-to-date and authoritative record of what has happened. The actual data files (heap files) may be behind — they may not yet reflect all committed transactions. This gap between the WAL's knowledge and the data file's knowledge is precisely what crash recovery must bridge.

WAL records are written into **WAL segment files** — each segment is typically 16 MB in size and lives in the `pg_wal` directory (called `pg_xlog` in older versions). These segments have names like `000000010000000000000001`, `000000010000000000000002`, and so on — sequential, ever-increasing filenames that encode their position in the WAL stream. Old segments are recycled or archived once they are no longer needed for recovery.

## 4. Checkpoints — The Anchor Points of Recovery

A **checkpoint** is one of the most important concepts in WAL-based recovery. Without checkpoints, recovery after a crash would require replaying the entire WAL from the very beginning of the database's history — which could be years of records. Checkpoints give the recovery process a known-good starting point.

A checkpoint is a moment in time at which PostgreSQL guarantees that all dirty pages in the buffer pool have been written to their corresponding data files on disk. After a checkpoint, the engine can safely say: "Everything before this point is captured in the data files. Recovery only needs to replay WAL records from this checkpoint forward."

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    WHAT A CHECKPOINT DOES                               │
│                                                                         │
│   WAL Stream (time flows →)                                             │
│                                                                         │
│   ──────●────────────────────────────●────────────────────────●───►     │
│          │                           │                         │        │
│      Checkpoint 1               Checkpoint 2             CRASH!         │
│      (LSN: 100)                 (LSN: 500)                              │
│                                                                         │
│   At Checkpoint 1 (LSN 100):                                            │
│   All dirty pages up to LSN 100 are written to disk.                    │
│   Recovery from this point needs WAL from LSN 100 onward.               │
│                                                                         │
│   At Checkpoint 2 (LSN 500):                                            │
│   All dirty pages up to LSN 500 are written to disk.                    │
│   Recovery from this point needs WAL from LSN 500 onward.               │
│                                                                         │
│   After the crash:                                                      │
│   PostgreSQL reads pg_control → finds last checkpoint at LSN 500        │
│   Recovery starts at LSN 500, NOT at the beginning of all history.      │
│   Only WAL records from LSN 500 to the crash point are replayed.        │
│                                                                         │
│   RESULT: Recovery is always bounded and fast, regardless of how        │
│   long the database has been running.                                   │
└─────────────────────────────────────────────────────────────────────────┘
```

The checkpoint process itself follows a careful sequence. First, PostgreSQL writes a **checkpoint WAL record** — a special WAL entry that records the current LSN and signals the beginning of a checkpoint. Then it scans the buffer pool and writes all dirty pages to disk, using background I/O to avoid overwhelming the storage system. Finally, it writes another special WAL record — the **checkpoint completion record** — and updates the `pg_control` file with the LSN of this checkpoint.

The `pg_control` file is the index to the checkpoint system. It records the LSN of the most recent checkpoint, the LSN of the previous checkpoint, the database state (in production, in crash recovery, in archive recovery), and the WAL segment and offset where the last checkpoint's WAL record lives. When PostgreSQL starts after a crash, the very first thing it reads is `pg_control` to find out where to begin recovery.

Two configuration parameters govern when checkpoints happen automatically. `checkpoint_timeout` (default: 5 minutes) triggers a checkpoint every five minutes regardless of activity. `max_wal_size` (default: 1 GB) triggers a checkpoint when the WAL has grown to 1 GB since the last checkpoint. In production, both parameters must be tuned carefully — too frequent checkpoints cause excessive disk I/O; too infrequent checkpoints mean longer recovery times after a crash.

## 5. Crash Recovery — The Complete Theory

Now we arrive at the heart of the matter. When PostgreSQL starts after a crash — whether the crash was a power failure, a kernel panic, an OOM kill, a Docker container being force-stopped, or any other ungraceful termination — it performs a three-phase recovery process called **ARIES** (Algorithm for Recovery and Isolation Exploiting Semantics). Understanding these three phases will make every recovery case that follows feel logical rather than mysterious.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                THE THREE PHASES OF CRASH RECOVERY (ARIES)               │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │  PHASE 1: ANALYSIS                                               │   │
│  │                                                                  │   │
│  │  Start at the last checkpoint LSN (from pg_control).             │   │
│  │  Scan forward through the WAL to the end.                        │   │
│  │  Build a complete picture of:                                    │   │
│  │  - Which transactions were active at the time of crash           │   │
│  │  - Which transactions committed after the checkpoint             │   │
│  │  - Which transactions were in-flight (never committed)           │   │
│  │  - Which pages were modified (the "dirty page table")            │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                               │                                         │
│                               ▼                                         │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │  PHASE 2: REDO                                                   │   │
│  │                                                                  │   │
│  │  Start from the earliest LSN identified in the Analysis phase.   │   │
│  │  Scan forward through the WAL again.                             │   │
│  │  For each WAL record, check: Has this change already been        │   │
│  │  applied to the data file? (Compare WAL LSN vs page LSN)         │   │ 
│  │  If NO → apply the change. This is the REDO operation.           │   │
│  │  If YES → skip. The page already has this update.                │   │
│  │                                                                  │   │
│  │  After REDO: every committed transaction is now reflected        │   │
│  │  in the data files. Exactly as if no crash occurred.             │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                               │                                         │
│                               ▼                                         │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │  PHASE 3: UNDO                                                   │   │
│  │                                                                  │   │
│  │  From the Analysis phase, take the list of transactions that     │   │
│  │  were in-flight at crash time (never committed, never aborted).  │   │
│  │  Walk backwards through the WAL using the "prev LSN" pointer     │   │
│  │  in each record to find all changes made by these transactions.  │   │
│  │  Apply the reverse (undo) of each change to the data files.      │   │
│  │                                                                  │   │
│  │  After UNDO: every uncommitted transaction is fully reversed.    │   │
│  │  The database is in a clean, consistent state.                   │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                               │                                         │
│                               ▼                                         │
│               Database opens for connections.                           │
└─────────────────────────────────────────────────────────────────────────┘
```

The elegance of this three-phase approach is that it handles every possible combination of committed and uncommitted transactions, partially written pages, and interrupted checkpoints. The REDO phase ensures no committed work is lost. The UNDO phase ensures no uncommitted work pollutes the database. Together, they restore ACID guarantees from whatever state the crash left the system in.

PostgreSQL's implementation is slightly simpler than the full ARIES algorithm in one respect: because of MVCC (Multi-Version Concurrency Control), PostgreSQL does not actually need to physically undo changes. Old row versions are left in place (they are visible to no one and will be cleaned by VACUUM). For practical purposes, however, the conceptual model of REDO + UNDO is the correct mental model.

Now let us walk through every crash scenario you will encounter in production.

## 6. Case 1 — Crash Before Any WAL Was Written

This is the simplest case, and the most benign. It occurs when a crash happens before a transaction even has a chance to write any WAL records — for example, during the connection handshake, during query parsing, or in the very earliest moments of a transaction before it has modified any data.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CASE 1: CRASH BEFORE WAL IS WRITTEN                                    │
│                                                                         │
│  Timeline:                                                              │
│                                                                         │
│  [Last Checkpoint]──────[Transaction Begins]──[CRASH]                  │
│         │                       │                │                      │
│      LSN: 500               LSN: 500         No WAL written            │
│   (on disk, safe)        (no changes yet)   for this txn               │
│                                                                         │
│  WAL Stream:                                                            │
│  ─────────────────────────────[500]────────────────────────────►       │
│                                 ↑                                       │
│                           Last checkpoint                               │
│                           Nothing after this.                           │
│                                                                         │
│  Recovery Steps:                                                        │
│  ─────────────────────────────────────────────────────────────────      │
│  Step 1: PostgreSQL reads pg_control                                    │
│          → Last checkpoint at LSN 500                                   │
│                                                                         │
│  Step 2: Analysis phase scans WAL from LSN 500 forward                 │
│          → Finds no WAL records after checkpoint                        │
│          → No transactions were in-flight                               │
│                                                                         │
│  Step 3: REDO phase — nothing to redo                                   │
│                                                                         │
│  Step 4: UNDO phase — nothing to undo                                   │
│                                                                         │
│  Step 5: Database marks pg_control as "clean"                          │
│                                                                         │
│  Step 6: Database opens for connections                                 │
│                                                                         │
│  OUTCOME: Instant recovery. No data affected. The transaction           │
│  that was in progress simply never happened — as if it was              │
│  never started. The application receives a connection error             │
│  and must retry.                                                        │
└─────────────────────────────────────────────────────────────────────────┘
```

From the application's perspective, the connection simply dropped. A properly written Go service with connection pooling and retry logic will reconnect automatically and retry the operation. No data is lost because no data was ever changed. This case is essentially a non-event from the database's perspective.

**Recovery time: Milliseconds to seconds (just reading pg_control and scanning a tiny WAL segment).**

## 7. Case 2 — Crash After WAL Written But Before Checkpoint

This is the most common crash case in production, and the one the WAL was primarily designed to handle. The transaction committed — the WAL was flushed to disk, and success was returned to the application — but the checkpointer has not yet written the dirty pages to the data files. The crash occurs in this window.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CASE 2: CRASH AFTER WAL WRITTEN, BEFORE CHECKPOINT                     │
│                                                                         │
│  Timeline:                                                              │
│                                                                         │
│  [Checkpoint]──[Txn Commits]──[WAL on disk]──[CRASH]──[No checkpoint]  │
│      │               │               │           │                      │
│   LSN:500         LSN:600         LSN:600     LSN:600                  │
│  (data safe)    (WAL flushed)  (WAL safe)   (heap file                 │
│                 SUCCESS→app               still has old data)           │
│                                                                         │
│  State of files at crash:                                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  WAL file:  [chkpt@500]...[UPDATE users SET bal=900 @LSN:600]   │   │
│  │                                  ↑ safely on disk               │   │
│  │  Heap file: Page 7, Slot 3 still has bal=1000 (old value)       │   │
│  │                                  ↑ NOT yet updated on disk       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Recovery Steps:                                                        │
│  ─────────────────────────────────────────────────────────────────      │
│  Step 1: PostgreSQL reads pg_control                                    │
│          → Last checkpoint at LSN 500                                   │
│          → pg_control state = "in production" (not clean)              │
│          → Crash recovery mode activated                                │
│                                                                         │
│  Step 2: Analysis phase                                                 │
│          → Scans WAL from LSN 500 to end                               │
│          → Finds UPDATE record at LSN 600                              │
│          → Finds COMMIT record at LSN 601                              │
│          → Transaction 42 committed. Must be redone.                   │
│                                                                         │
│  Step 3: REDO phase                                                     │
│          → Reads WAL record at LSN 600                                 │
│          → Reads Page 7 from heap file: page LSN = 500                 │
│          → WAL LSN (600) > page LSN (500) → change not yet applied     │
│          → Applies: SET bal=900 on Page 7, Slot 3                      │
│          → Page 7 now has bal=900, page LSN updated to 600             │
│          → Writes Page 7 back to disk                                   │
│                                                                         │
│  Step 4: UNDO phase — transaction committed, nothing to undo            │
│                                                                         │
│  Step 5: Database opens for connections                                 │
│                                                                         │
│  OUTCOME: The committed transaction is fully recovered.                 │
│  The application sees exactly the data it committed.                   │
│  No data loss whatsoever.                                              │
└─────────────────────────────────────────────────────────────────────────┘
```

This case demonstrates the core value proposition of the WAL with perfect clarity. The application received "SUCCESS" for its transaction. The database crashed. The data file was out of date. And yet, upon restart, the database recovered to exactly the correct state — because the WAL record was durably on disk. The WAL's promise was kept.

**Recovery time: Proportional to the amount of WAL written since the last checkpoint. With default settings (checkpoint every 5 minutes, max_wal_size 1 GB), recovery typically takes 30 seconds to a few minutes.**

## 8. Case 3 — Crash During a Checkpoint

This case is more nuanced because the crash occurs while the checkpointer itself is in the middle of writing dirty pages to disk. This means some pages have been checkpointed (written to disk) and some have not — a partially completed checkpoint.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CASE 3: CRASH DURING A CHECKPOINT                                      │
│                                                                         │
│  Timeline:                                                              │
│                                                                         │
│  [Old Chkpt]──[New Chkpt Starts]──[Half pages written]──[CRASH]        │
│      │                │                    │                │           │
│   LSN:400          LSN:500            Pages 1–50        LSN:600        │
│  (complete)     (chkpt begins)       written to disk     (crash)       │
│                                    Pages 51–100 NOT       mid-chkpt    │
│                                    yet written             written      │
│                                                                         │
│  State of files at crash:                                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  WAL: [old chkpt@400]...[new chkpt START@500]...[records]...    │   │
│  │       Note: chkpt COMPLETION record never written (crash)       │   │
│  │                                                                  │   │
│  │  Heap file: Pages 1–50: updated (LSN reflects post-500 state)   │   │
│  │             Pages 51–100: old state (LSN still pre-500)         │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Recovery Steps:                                                        │
│  ─────────────────────────────────────────────────────────────────      │
│  Step 1: PostgreSQL reads pg_control                                    │
│          → pg_control records the OLD completed checkpoint at LSN 400  │
│          → The new checkpoint at LSN 500 never completed              │
│          → (pg_control is only updated when a checkpoint COMPLETES)    │
│                                                                         │
│  Step 2: Recovery starts at LSN 400 (the last COMPLETED checkpoint)    │
│          Scans WAL from LSN 400 forward                                │
│                                                                         │
│  Step 3: REDO phase                                                     │
│          → For pages 1–50 (already written by partial checkpoint):     │
│            Compare WAL LSN vs page LSN. If page LSN ≥ WAL LSN → skip  │
│          → For pages 51–100 (NOT yet written):                          │
│            WAL LSN > page LSN → apply the change                       │
│          → The LSN comparison makes REDO safe for ALL pages            │
│                                                                         │
│  Step 4: UNDO any uncommitted transactions                              │
│                                                                         │
│  Step 5: Database opens for connections                                 │
│                                                                         │
│  OUTCOME: Complete recovery. The partial checkpoint is handled         │
│  transparently. The LSN comparison mechanism ensures that pages        │
│  already updated by the partial checkpoint are not double-applied.     │
└─────────────────────────────────────────────────────────────────────────┘
```

The brilliance of the LSN comparison mechanism shines in this case. Even though some pages were updated mid-checkpoint and some were not, the REDO phase correctly distinguishes between them without any special handling of the "partial checkpoint" scenario. A page that was already updated by the checkpoint has a newer LSN than the WAL record that describes the same change — so the REDO skips it. A page that was not yet updated by the checkpoint has an older LSN — so the REDO applies the change. The algorithm handles this seamlessly.

**Recovery time: Must replay from the previous completed checkpoint, so slightly longer than Case 2. Typically 1 to 5 minutes in a well-configured production system.**

## 9. Case 4 — Crash After Checkpoint But Mid-Transaction

This case introduces the UNDO phase. Here, a transaction was in progress but had not yet committed when the crash occurred. Some of its WAL records were written (because WAL records are written as changes happen, not just at commit time), but the COMMIT record was never written.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CASE 4: CRASH DURING AN UNCOMMITTED TRANSACTION                        │
│                                                                         │
│  Scenario: A transaction is updating 1000 rows. It has updated 600     │
│  rows and written their WAL records. Then the server crashes.           │
│  The transaction never reached COMMIT.                                  │
│                                                                         │
│  Timeline:                                                              │
│                                                                         │
│  [Checkpoint]──[Txn Begins]──[600 rows updated]──[CRASH]               │
│      │               │              │                │                  │
│   LSN:500         LSN:501       LSN:501–599       LSN:600              │
│                  (txn start)   (WAL records)   (NO COMMIT record)      │
│                                                                         │
│  WAL Stream:                                                            │
│  ──[chkpt@500]──[BEGIN txn99@501]──[UPDATE row1@502]──...              │
│    ──[UPDATE row600@599]──[CRASH — no COMMIT record]                   │
│                                                                         │
│  Recovery Steps:                                                        │
│  ─────────────────────────────────────────────────────────────────      │
│  Step 1: Reads pg_control → last checkpoint at LSN 500                 │
│                                                                         │
│  Step 2: Analysis phase (LSN 500 → end of WAL)                         │
│          → Sees BEGIN for transaction 99                                │
│          → Sees 600 UPDATE records for transaction 99                  │
│          → Sees NO COMMIT or ABORT for transaction 99                  │
│          → Conclusion: Transaction 99 was in-flight. Must be undone.   │
│                                                                         │
│  Step 3: REDO phase                                                     │
│          → Replays all 600 UPDATE WAL records                           │
│          → WHY REDO before UNDO?                                        │
│            Because some of these pages may have been written to disk   │
│            by the buffer pool, and the old data no longer exists in   │
│            RAM. REDO brings the system to the exact state it was in   │
│            at the moment of crash — even for uncommitted transactions. │
│            Only then can UNDO safely reverse them.                     │
│                                                                         │
│  Step 4: UNDO phase                                                     │
│          → Walks backwards through WAL using "prev LSN" pointers       │
│          → Finds all 600 UPDATE records for transaction 99              │
│          → For each: applies the before-image (restores old value)     │
│          → Writes a COMPENSATION LOG RECORD (CLR) for each undo step  │
│            (so if UNDO itself is interrupted by another crash,         │
│            it can continue from where it left off)                     │
│          → Writes ABORT record for transaction 99                       │
│                                                                         │
│  Step 5: Database opens for connections                                 │
│                                                                         │
│  OUTCOME: The uncommitted transaction is completely reversed.           │
│  All 600 rows are back to their original values.                       │
│  The application that started the transaction gets a connection        │
│  error and must retry.                                                 │
└─────────────────────────────────────────────────────────────────────────┘
```

The question that naturally arises here is: why does REDO happen before UNDO? Why replay the changes of an uncommitted transaction only to immediately undo them? The answer is subtle and important. When the crash happened, some of those 600 modified pages may have been flushed to disk by the buffer pool's eviction process (remember, dirty pages can be written to disk at any time — not just at checkpoints). The original data for those rows no longer exists anywhere in the system. REDO must first reconstruct the exact state of the database at the moment of crash, including all the changes of the in-flight transaction, so that UNDO has the correct state to work against when reversing them.

**Recovery time: Depends heavily on how many rows the in-flight transaction had modified. A transaction that had been running for hours and modified millions of rows could require significant UNDO time. This is one reason long-running transactions are dangerous in production.**

## 10. Case 5 — Disk Corruption (The Hardest Case)

All previous cases assumed that the disk itself is healthy — the files are intact, just possibly out of date. Disk corruption is fundamentally different: the data files themselves are damaged. Sectors have gone bad, the filesystem is inconsistent, or partial writes have left pages with invalid checksums. This is the case that requires proper **backup infrastructure**.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CASE 5: DISK CORRUPTION                                                │
│                                                                         │
│  Symptoms you will see:                                                 │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ERROR: invalid page in block 42 of relation base/16384/12345   │   │
│  │  ERROR: checksum failure for block 42                           │   │
│  │  ERROR: unexpected data beyond EOF in file base/16384/12345     │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  WAL alone CANNOT fix disk corruption.                                  │
│  WAL can only replay changes on top of a valid data file.              │
│  If the data file itself is damaged, you need a physical backup.       │
│                                                                         │
│  RECOVERY STRATEGY:                                                     │
│  ─────────────────────────────────────────────────────────────────      │
│                                                                         │
│  Option A: Restore from a base backup + replay WAL (PITR)              │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │                                                                  │   │
│  │  [Base Backup]──────────────────────────[Corruption]            │   │
│  │       │                                       │                 │   │
│  │   t=Yesterday                             t=Today               │   │
│  │   (clean copy                                                    │   │
│  │   of data dir)                                                   │   │
│  │                                                                  │   │
│  │  Step 1: Restore the base backup to the data directory          │   │
│  │  Step 2: Configure recovery.conf (or postgresql.conf) to        │   │
│  │          replay WAL from the archive up to the point just       │   │
│  │          before corruption occurred                              │   │
│  │  Step 3: Start PostgreSQL → it replays archived WAL             │   │
│  │  Step 4: Database arrives at the state just before corruption   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Option B: If only ONE page is corrupt (pg_filedump + surgery)         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Step 1: Enable zero_damaged_pages = on in postgresql.conf      │   │
│  │          (allows PostgreSQL to treat damaged pages as empty,    │   │
│  │          so the rest of the database stays accessible)          │   │
│  │  Step 2: Find out which rows were in the corrupted page         │   │
│  │          using pg_filedump to inspect the page structure        │   │
│  │  Step 3: Restore just those rows from backup                    │   │
│  │  Step 4: Disable zero_damaged_pages when done                   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  PREVENTION (more important than cure):                                 │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Enable page checksums at initdb time:                          │   │
│  │  initdb --data-checksums                                         │   │
│  │                                                                  │   │
│  │  This adds a CRC checksum to every page. PostgreSQL detects     │   │
│  │  corruption the moment a corrupted page is read, rather than   │   │
│  │  silently returning wrong data to your application.             │   │
│  │  Enable this on ALL production databases.                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────┘
```

The lesson from disk corruption is that WAL alone is not a complete backup strategy. WAL is a _recovery_ mechanism for crash scenarios. A full backup infrastructure — consisting of periodic base backups of the entire data directory plus continuous WAL archiving — is the only defense against disk corruption, accidental data deletion, or catastrophic storage failure.

## 11. Case 6 — Point-in-Time Recovery (PITR)

Point-in-Time Recovery is one of the most powerful capabilities that WAL archiving enables. It allows you to restore a database to _any specific moment in its past_ — not just to the most recent state, but to any second within the window for which you have WAL archives. This is invaluable when a developer accidentally runs `DELETE FROM orders WHERE id > 0` or when you need to restore a database to the state it was in before a bad deployment.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CASE 6: POINT-IN-TIME RECOVERY (PITR)                                  │
│                                                                         │
│  Scenario: Developer runs DROP TABLE users at 14:32:45.                 │
│  You need to recover the database to 14:32:44 — one second before.     │
│                                                                         │
│  Prerequisites:                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  1. wal_level = replica (or logical) in postgresql.conf         │   │
│  │  2. archive_mode = on                                           │   │
│  │  3. archive_command = 'cp %p /wal-archive/%f'                   │   │
│  │     (copies each completed WAL segment to archive storage)      │   │
│  │  4. Regular base backups (pg_basebackup)                        │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  WAL Archive:                                                           │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │                                                                  │   │
│  │  Base Backup          WAL Archive Segments                      │   │
│  │  (taken at 02:00)     (covering 02:00 → 14:32)                  │   │
│  │       │                    │                                    │   │
│  │   /backup/           /wal-archive/                              │   │
│  │   base.tar.gz        000...001  000...002  ...  000...247       │   │
│  │                                                                  │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Recovery Steps:                                                        │
│  ─────────────────────────────────────────────────────────────────      │
│                                                                         │
│  Step 1: Stop the current (damaged) PostgreSQL instance                │
│          systemctl stop postgresql                                      │
│          (or docker stop postgres-container)                            │
│                                                                         │
│  Step 2: Rename or move the damaged data directory                      │
│          mv /var/lib/postgresql/data /var/lib/postgresql/data.broken    │
│                                                                         │
│  Step 3: Restore the base backup to the data directory                 │
│          tar -xzf /backup/base.tar.gz -C /var/lib/postgresql/data      │
│                                                                         │
│  Step 4: Create recovery configuration                                  │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  In PostgreSQL 12+, add to postgresql.conf:                     │   │
│  │                                                                  │   │
│  │  restore_command = 'cp /wal-archive/%f %p'                      │   │
│  │  recovery_target_time = '2024-01-15 14:32:44'                   │   │
│  │  recovery_target_action = 'promote'                             │   │
│  │                                                                  │   │
│  │  Also create an empty file named recovery.signal                │   │
│  │  touch /var/lib/postgresql/data/recovery.signal                 │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 5: Start PostgreSQL                                               │
│          PostgreSQL enters archive recovery mode.                       │
│          It runs restore_command to fetch each WAL segment from        │
│          the archive, replays it, and repeats until it reaches         │
│          the target timestamp.                                          │
│                                                                         │
│  Step 6: PostgreSQL reaches 14:32:44 in the WAL stream                 │
│          It stops replaying, promotes itself to a primary,             │
│          deletes recovery.signal, and opens for connections.           │
│                                                                         │
│  OUTCOME: Database is restored to 14:32:44.                            │
│  The DROP TABLE at 14:32:45 never happened in this timeline.           │
│  Users table is intact.                                                │
│                                                                         │
│  ⚠  WARNING: All transactions between 14:32:44 and the recovery       │
│  point are lost. This is the data loss you accept for the recovery.   │
└─────────────────────────────────────────────────────────────────────────┘
```

PITR is why you should _always_ enable WAL archiving in production. The cost is modest — WAL segments are typically 16 MB each, and a moderately busy database might generate a few gigabytes of WAL per day. The benefit is the ability to recover from almost any disaster with minimal data loss.

## 12. Case 7 — Standby / Replica Recovery (Streaming Replication)

This case covers a different kind of recovery — not recovering a crashed primary, but promoting a standby replica to become the new primary when the primary is lost entirely. This is the highest-availability scenario, where recovery time is measured in seconds rather than minutes.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CASE 7: STREAMING REPLICATION AND STANDBY PROMOTION                    │
│                                                                         │
│  Normal operation:                                                      │
│                                                                         │
│  ┌──────────────────┐    WAL stream    ┌──────────────────────────┐    │
│  │   PRIMARY        │ ──────────────► │   STANDBY (replica)      │    │
│  │  (read+write)    │   (real-time)    │   (read-only)            │    │
│  │                  │                 │                            │    │
│  │  pg_wal/         │                 │  replays WAL in real time  │    │
│  │  000...001...    │                 │  always ~seconds behind   │    │
│  └──────────────────┘                 └──────────────────────────┘    │
│                                                                         │
│  Primary crashes or becomes unreachable:                               │
│                                                                         │
│  ┌──────────────────┐                 ┌──────────────────────────┐    │
│  │   PRIMARY        │    ✗ DOWN ✗     │   STANDBY                │    │
│  │  (unreachable)   │                 │   (has WAL up to LSN X)  │    │
│  └──────────────────┘                 └──────────────────────────┘    │
│                                                                         │
│  Promotion steps:                                                       │
│  ─────────────────────────────────────────────────────────────────      │
│                                                                         │
│  Step 1: Detect primary failure                                         │
│          (Patroni, repmgr, or manual detection)                        │
│                                                                         │
│  Step 2: Ensure no "split-brain" — fence the old primary               │
│          (STONITH: Shoot The Other Node In The Head)                   │
│          This step is CRITICAL. If old primary is still running       │
│          and accepting writes, you will have two primaries and         │
│          data divergence — a catastrophic situation.                   │
│                                                                         │
│  Step 3: On the standby, run:                                           │
│          pg_ctl promote -D /var/lib/postgresql/data                     │
│          OR: touch /var/lib/postgresql/data/promote.signal             │
│                                                                         │
│  Step 4: Standby replays any remaining WAL it received before         │
│          the primary went down                                          │
│                                                                         │
│  Step 5: Standby generates a new timeline history file                 │
│          This records the branch point — the LSN where this           │
│          standby diverged from the old primary's history               │
│                                                                         │
│  Step 6: Standby becomes the new primary — accepts read+write          │
│                                                                         │
│  Step 7: Other standbys (if any) reattach to the new primary          │
│          and switch to following the new timeline                       │
│                                                                         │
│  DATA LOSS WINDOW:                                                      │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Synchronous replication: ZERO data loss                        │   │
│  │  (commit waits for standby to confirm WAL receipt)             │   │
│  │  postgresql.conf: synchronous_commit = on                       │   │
│  │  synchronous_standby_names = 'standby1'                         │   │
│  │                                                                  │   │
│  │  Asynchronous replication: Small data loss possible             │   │
│  │  (standby may be seconds behind at time of primary crash)       │   │
│  │  Typically 0–100ms of transactions lost.                        │   │
│  └─────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────┘
```

Streaming replication is the gold standard for high-availability in production. With a properly configured replica and an orchestration tool like Patroni (the most widely used solution), failover can happen automatically in under 30 seconds, with near-zero or zero data loss depending on your replication mode.

## 13. Step-by-Step Recovery Playbook for Production

This section gives you the exact, concrete commands to execute for each recovery scenario in a Docker-based PostgreSQL environment — the kind you are using.

### Playbook A — Standard Crash Recovery (Cases 1–4)

```
┌─────────────────────────────────────────────────────────────────────────┐
│  PLAYBOOK A: STANDARD CRASH RECOVERY                                    │

```

### Playbook B — PITR Recovery (Case 6)

```
┌─────────────────────────────────────────────────────────────────────────┐
│  PLAYBOOK B: POINT-IN-TIME RECOVERY                                     │
│  (Accidental DELETE/DROP, bad migration)                                │
│                                                                         │
│  Prerequisites check:                                                   │
│  ─────────────────────                                                  │
│  # Verify you have base backup                                          │
│  ls -la /backup/postgres/base/                                          │
│                                                                         │
│  # Verify WAL archives exist                                            │
│  ls -la /backup/postgres/wal-archive/ | tail -20                       │
│                                                                         │
│  Step 1: Stop current PostgreSQL                                        │
│  ──────────────────────────────                                         │
│  docker stop postgres-container                                         │
│                                                                         │
│  Step 2: Backup the damaged data directory (safety copy)                │
│  ─────────────────────────────────────────────────────                  │
│  docker run --rm \                                                      │
│    -v postgres_data:/source \                                           │
│    -v postgres_data_broken:/dest \                                      │
│    busybox cp -a /source/. /dest/                                       │
│                                                                         │
│  Step 3: Restore base backup                                            │
│  ───────────────────────────                                            │
│  # Clear the data directory                                             │
│  docker run --rm -v postgres_data:/data busybox rm -rf /data/*          │
│                                                                         │
│  # Restore from backup                                                  │
│  docker run --rm \                                                      │
│    -v /backup/postgres/base/base.tar.gz:/backup.tar.gz \               │
│    -v postgres_data:/data \                                             │
│    busybox tar -xzf /backup.tar.gz -C /data                            │
│                                                                         │
│  Step 4: Configure recovery settings                                    │
│  ────────────────────────────────                                       │
│  # Append to postgresql.conf inside the data volume                    │
│  docker run --rm -v postgres_data:/data busybox sh -c "                │
│    echo \"restore_command = 'cp /wal-archive/%f %p'\" >> /data/postgresql.conf
│    echo \"recovery_target_time = '2024-01-15 14:32:44'\" >> /data/postgresql.conf
│    echo \"recovery_target_action = 'promote'\" >> /data/postgresql.conf
│  "                                                                      │
│                                                                         │
│  # Create recovery signal file                                          │
│  docker run --rm -v postgres_data:/data busybox touch /data/recovery.signal
│                                                                         │
│  Step 5: Mount the WAL archive and start                                │
│  ─────────────────────────────────────                                  │
│  docker run -d \                                                        │
│    --name postgres-recovery \                                           │
│    -v postgres_data:/var/lib/postgresql/data \                          │
│    -v /backup/postgres/wal-archive:/wal-archive:ro \                   │
│    postgres:16                                                          │
│                                                                         │
│  Step 6: Monitor recovery progress                                      │
│  ─────────────────────────────────                                      │
│  docker logs -f postgres-recovery                                       │
│  # Watch for: "recovery stopping before commit of transaction..."      │
│  # And: "database system is ready to accept connections"               │
│                                                                         │
│  Step 7: Verify recovery landed at the right point                     │
│  ──────────────────────────────────────────────────                    │
│  psql -U postgres -c "SELECT now();"                                    │
│  psql -U postgres -c "SELECT count(*) FROM users;"  -- table should exist
│  psql -U postgres -c "SELECT pg_is_in_recovery();"  -- should return false
└─────────────────────────────────────────────────────────────────────────┘
```

### Playbook C — Checking WAL Health Without Recovery

```
┌─────────────────────────────────────────────────────────────────────────┐
│  PLAYBOOK C: WAL HEALTH MONITORING (Run while system is live)           │
│                                                                         │
│  Check current WAL position:                                            │
│  SELECT pg_current_wal_lsn();                                           │
│  -- Returns: 0/5A0012A8                                                 │
│                                                                         │
│  Check WAL generation rate (writes per second):                         │

│    AS total_wal_mb_generated;                                           │
│                                                                         │

│  FROM pg_stat_replication;  -- on primary, shows replica lag           │
│                                                                         │
│  Check WAL files on disk:                                               │
│  SELECT count(*) AS wal_segments,                                       │
│         pg_size_pretty(count(*) * 16 * 1024 * 1024) AS total_size      │
│  FROM pg_ls_waldir();                                                   │
│                                                                         │
│  Verify WAL archiving is working:                                       │
│  SELECT archived_count, failed_count, last_archived_wal,               │
│         last_archived_time, last_failed_wal, last_failed_time          │
│  FROM pg_stat_archiver;                                                 │
│  -- failed_count should be 0                                            │
│  -- last_archived_time should be recent (within minutes)               │
│                                                                         │
│  Validate a WAL segment manually (offline, for forensics):              │
│  pg_waldump /var/lib/postgresql/data/pg_wal/000000010000000000000001   │
│  -- Shows each WAL record: LSN, transaction ID, resource manager,      │
│  -- and a human-readable description of the change                     │
└─────────────────────────────────────────────────────────────────────────┘
```

## 14. WAL Configuration for Production

All the recovery capabilities described above depend on proper WAL configuration. Here is the complete set of parameters you should set for a production-grade PostgreSQL deployment.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                   PRODUCTION WAL CONFIGURATION                          │
│                   (postgresql.conf)                                     │
│                                                                         │
│  ── DURABILITY ──────────────────────────────────────────────────────   │
│                                                                         │
│  fsync = on                     # NEVER set to off in production        │
│                                 # Ensures WAL is physically on disk     │
│                                 # before commit returns to client       │
│                                                                         │
│  synchronous_commit = on        # Safest setting                        │
│                                 # off = up to ~wal_writer_delay ms      │
│                                 # data loss risk on crash               │
│                                                                         │
│  wal_sync_method = fdatasync    # How PostgreSQL calls fsync            │
│                                 # fdatasync is fastest on Linux         │
│                                                                         │
│  ── WAL LEVEL & ARCHIVING ───────────────────────────────────────────   │
│                                                                         │
│  wal_level = replica            # Minimum for archiving and replication │
│                                 # logical = enables logical replication  │
│                                                                         │
│  archive_mode = on              # Enable WAL archiving                  │
│                                                                         │
│  archive_command = 'test ! -f /wal-archive/%f && cp %p /wal-archive/%f'│
│                                 # %p = full path of WAL segment         │
│                                 # %f = filename only                    │
│                                 # test ! -f prevents overwriting        │
│                                                                         │
│  archive_timeout = 300          # Force archive even if WAL segment     │
│                                 # hasn't filled up. 300s = 5 minutes.  │
│                                 # Limits maximum data loss window.      │
│                                                                         │
│  ── CHECKPOINT TUNING ───────────────────────────────────────────────   │
│                                                                         │
│  checkpoint_timeout = 15min     # Max time between checkpoints          │
│                                 # Longer = less I/O, longer recovery    │
│                                 # Shorter = more I/O, faster recovery   │
│                                                                         │
│  max_wal_size = 4GB             # Max WAL before forced checkpoint      │
│                                 # Default 1GB too small for busy dbs    │
│                                                                         │
│  min_wal_size = 1GB             # Keep this many WAL files on disk      │
│                                 # Avoids constant segment creation      │
│                                                                         │
│  checkpoint_completion_target = 0.9  # Spread checkpoint I/O over 90%  │
│                                      # of checkpoint_timeout            │
│                                      # Smooths out disk write spikes   │
│                                                                         │
│  ── WAL BUFFERS ─────────────────────────────────────────────────────   │
│                                                                         │
│  wal_buffers = 64MB             # In-memory WAL buffer                  │
│                                 # Larger = fewer flushes under high load│
│                                                                         │
│  wal_compression = lz4          # Compress WAL records                  │
│                                 # Reduces WAL size and archive storage  │
│                                 # lz4 is fast; zstd gives better ratio │
│                                                                         │
│  ── PAGE CHECKSUMS ──────────────────────────────────────────────────   │
│                                                                         │
│  # Must be enabled at initdb time, not in postgresql.conf:             │
│  initdb --data-checksums -D /var/lib/postgresql/data                    │
│                                                                         │
│  # To enable on an existing cluster (PostgreSQL 12+, offline):         │
│  pg_checksums --enable -D /var/lib/postgresql/data                      │
└─────────────────────────────────────────────────────────────────────────┘
```

### Docker Compose Example for Production-Grade WAL Setup

```yaml
# docker-compose.yml

version: '3.8'

services:
  postgres:
    image: postgres:16
    container_name: postgres-primary
    restart: unless-stopped

    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: appdb

    volumes:
      # Data directory — use a named volume for persistence
      - postgres_data:/var/lib/postgresql/data

      # WAL archive destination — mount a separate volume or NFS
      - wal_archive:/var/lib/postgresql/wal-archive

      # Custom postgresql.conf with WAL settings
      - ./config/postgresql.conf:/etc/postgresql/postgresql.conf:ro

    command: >
      postgres
      -c config_file=/etc/postgresql/postgresql.conf

    # Give PostgreSQL time to shut down cleanly
    # Default is 10 seconds — WAY too short for checkpointing
    stop_grace_period: 120s

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

volumes:
  postgres_data:
    driver: local
  wal_archive:
    driver: local
```

The `stop_grace_period: 120s` setting in Docker Compose is critically important and frequently overlooked. When Docker sends a SIGTERM to the PostgreSQL container, PostgreSQL begins its graceful shutdown — which includes performing a final checkpoint. If Docker's default 10-second kill timeout expires before the checkpoint completes, Docker sends SIGKILL, causing a crash. The next startup must then do crash recovery. Setting `stop_grace_period` to 120 seconds gives PostgreSQL enough time to complete the checkpoint gracefully, making the next startup instant.

## The Mental Map of WAL and Recovery

To close this guide, here is the complete mental model of how all the pieces connect:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    THE COMPLETE WAL ECOSYSTEM                           │
│                                                                         │
│  ┌────────────┐   write WAL   ┌──────────────┐  flush   ┌───────────┐ │
│  │ Transaction│ ────────────► │  WAL Buffer  │ ───────► │ WAL Segs  │ │
│  │  (commit)  │               │   (in RAM)   │ (fsync)  │ (on disk) │ │
│  └────────────┘               └──────────────┘          └─────┬─────┘ │
│                                                                │       │
│                                              archive_command   │       │
│                                                    │           │       │
│                                                    ▼           │       │
│                                            ┌──────────────┐   │       │
│                                            │ WAL Archive  │   │       │
│                                            │ (S3, NFS,    │   │       │
│                                            │  local disk) │   │       │
│                                            └──────┬───────┘   │       │
│                                                   │           │       │
│    ┌──────────┐  replays WAL  ┌──────────────┐   │ used for  │       │
│    │ Standby  │ ◄──────────── │  Streaming   │   │   PITR    │       │
│    │ Replica  │               │  Replication │   │           │       │
│    └──────────┘               └──────────────┘   │           │       │
│                                                   │           │       │
│    ┌──────────────────────────────────────────────┘           │       │
│    │                                                           │       │
│    │  PITR Recovery:                                           │       │
│    │  Base Backup + Archived WAL ──────────────────────────►  │       │
│    │  Restore to any point in time                            │       │
│    └───────────────────────────────────────────────────────── ┘       │
│                                                                │       │
│    Crash Recovery:                                             │       │
│    pg_control ──► last checkpoint LSN ──► replay WAL segs ────┘       │
│    (analysis)     (REDO committed txns)   (UNDO uncommitted txns)      │
│                                                                         │
│    Everything flows from the WAL.                                       │
│    The WAL is the single source of truth about what happened.          │
└─────────────────────────────────────────────────────────────────────────┘
```

The WAL is not a feature of PostgreSQL. It is the foundation upon which every guarantee PostgreSQL makes — durability, crash safety, replication, point-in-time recovery — is built. To understand the WAL is to understand why databases can be trusted with the most critical data in the world.
