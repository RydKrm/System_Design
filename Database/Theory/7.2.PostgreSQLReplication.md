# PostgreSQL Replication

### A Deep, Conceptual Journey from the Ground Up

> _Understanding PostgreSQL replication means understanding the WAL — because everything PostgreSQL does to replicate data is, at its heart, shipping the WAL from one machine to another._

---

## Preface: One Log to Rule Them All

In the previous chapter, we established the conceptual foundations of replication: why it exists, what synchronous and asynchronous mean, and how RPO and RTO give us precise language for recovery objectives. Now we descend into the specific, concrete mechanisms that PostgreSQL uses to implement those concepts.

Every PostgreSQL replication mechanism, without exception, is built on the Write-Ahead Log. The WAL is a sequential, append-only record of every change made to the database. It was designed primarily for crash recovery — but engineers noticed that if you can replay the WAL to recover a crashed database on the same machine, you can also replay it on a different machine to build an identical copy. That observation is the entire conceptual foundation of PostgreSQL replication.

But as simple as that observation is, the engineering details matter enormously. How does the WAL get from primary to replica? In what format? With what latency? What happens when the connection drops? Can you replicate only part of the database? What if the replica falls so far behind that the primary has deleted the WAL it needs? What if you want to chain replicas together? Each of these questions has a specific answer in PostgreSQL's replication architecture, and understanding those answers is what this guide is about.

---

## Chapter 1: Streaming Replication — WAL Shipping in Real Time

### The Two Eras of WAL-Based Replication

Before streaming replication existed in PostgreSQL 9.0 (2010), there was **WAL file shipping** — a simpler but coarser mechanism. The primary would finish writing a WAL segment file (typically 16MB), then copy that entire file to the replica using a script (typically `rsync` or `scp`) triggered by PostgreSQL's `archive_command`. The replica would apply each WAL file after it arrived.

WAL file shipping worked, but it had a significant limitation: the replica was always at least one WAL file behind — typically seconds to minutes, sometimes longer. A WAL file would not be shipped until it was completely written, which might not happen until many transactions had accumulated. This made the replication lag unpredictable and sometimes large.

**Streaming replication** solved this by shipping WAL records — individual change records — continuously, as they are written, rather than waiting for an entire WAL file to fill. The replica connects to the primary over a persistent TCP connection, and the primary streams WAL records to the replica in real time, typically within milliseconds of each commit. The lag is measured in milliseconds rather than seconds or minutes.

### The Streaming Replication Protocol

At the wire protocol level, streaming replication works through a dedicated **replication connection** — a special PostgreSQL connection that uses the replication protocol rather than the normal query protocol. The replica connects to the primary with a connection string that includes `replication=true` (or `replication=database` for logical replication), authenticates, and then issues a `START_REPLICATION` command:

```
Streaming Replication Connection Sequence:

  Replica                           Primary
     │                                 │
     │──── TCP Connect ───────────────►│  Standard PostgreSQL TCP connection
     │──── Authenticate ──────────────►│  pg_hba.conf: host replication replica_user ...
     │◄─── AuthenticationOK ───────────│
     │                                 │
     │──── START_REPLICATION ─────────►│  "Start streaming from LSN 0/1A3F28B0"
     │     (LSN = Log Sequence Number) │
     │                                 │
     │◄─── XLogData (WAL record 1) ────│  Primary streams WAL records
     │◄─── XLogData (WAL record 2) ────│  as they are written
     │◄─── XLogData (WAL record 3) ────│  (one TCP message per WAL record)
     │──── StandbyStatusUpdate ───────►│  Replica sends periodic ACK:
     │     (write_lsn, flush_lsn,      │  "I have written, flushed, and
     │      apply_lsn)                 │  applied up to this LSN"
     │                                 │
     │◄─── XLogData (continues...) ────│  Stream continues indefinitely
     │◄─── PrimaryKeepalive ───────────│  Primary sends heartbeats every
     │                                 │  wal_sender_timeout/2
```

The **LSN (Log Sequence Number)** is PostgreSQL's position pointer within the WAL stream — a 64-bit integer that uniquely identifies every byte position in the WAL. When a replica acknowledges `flush_lsn = 0/1A3F28B0`, it is saying "I have durably written all WAL up to position 0/1A3F28B0 to my local disk." This is what the primary uses to track replication progress and (in synchronous mode) to decide when to acknowledge a commit to the application.

### Physical Replication: Byte-for-Byte Identical

Streaming replication is, by default, **physical replication** — the WAL records being shipped describe low-level physical changes to data pages: "write these bytes at this offset in this file." The replica applies these changes byte-for-byte, producing a data directory that is physically identical to the primary's at the block level.

This has profound implications:

```
Physical Replication Characteristics:

  What is replicated:    Everything — all databases, all tables,
                         all indexes, all sequences, all system catalogs.
                         Every byte in every data file is replicated.

  Granularity:           Cannot replicate just one database or one table.
                         It is all-or-nothing at the cluster level.

  Schema changes:        Automatically replicated (DDL changes write WAL too).
                         No special handling needed.

  Replica usability:     Replicas can serve READ-ONLY queries (hot standby)
                         but cannot accept writes — they are applying WAL
                         continuously, and a write would conflict with that.

  PostgreSQL version:    Primary and replica must run the same PostgreSQL
                         major version. WAL format is version-specific.
                         (Minor version differences are usually OK.)

  Architecture:          Primary and replica must have the same CPU
                         architecture (x86_64 to x86_64, not x86_64 to ARM).
                         WAL encodes physical file offsets which are
                         architecture-dependent.
```

### Setting Up Streaming Replication

The configuration spans both the primary and replica sides:

```
PRIMARY CONFIGURATION (postgresql.conf):

  # Enable WAL archiving and replication
  wal_level = replica          # minimum for replication (or 'logical' for logical rep)
  max_wal_senders = 10         # max concurrent WAL sender processes (one per replica)
  wal_keep_size = 1024         # keep 1GB of WAL segments locally
                               # (prevents replica from falling too far behind)

  # Synchronous replication (optional — for zero data loss)
  synchronous_standby_names = 'FIRST 1 (replica1)'
  synchronous_commit = on

  # Replication authentication (pg_hba.conf):
  # TYPE   DATABASE     USER         ADDRESS          METHOD
  host     replication  replicator   replica_ip/32    scram-sha-256

PRIMARY ROLE CREATION:
  CREATE USER replicator
    WITH REPLICATION
    LOGIN
    PASSWORD 'strongpassword';

REPLICA CONFIGURATION (postgresql.conf + postgresql.auto.conf):

  # The replica is told about the primary via a connection string:
  primary_conninfo = 'host=primary_ip port=5432 user=replicator
                      password=strongpassword application_name=replica1'

  # Tell PostgreSQL this is a standby server:
  # (In PostgreSQL 12+, create a file named 'standby.signal' in data directory)
  # (In PostgreSQL <12, create 'recovery.conf' with standby_mode = on)

  # How far behind can the replica be before it tells the primary to wait?
  recovery_min_apply_delay = 0   # 0 = apply immediately (normal hot standby)
                                 # or e.g. '5min' for delayed replica (disaster recovery)
```

### The WAL Sender and WAL Receiver Processes

Internally, streaming replication runs through two dedicated processes:

```
Internal Process Architecture:

  PRIMARY SERVER:
  ┌─────────────────────────────────────────────────────┐
  │  postmaster (main PostgreSQL process)                │
  │  ├── Backend process 1 (user query)                  │
  │  │     └── Writes WAL records to WAL buffer          │
  │  ├── Backend process 2 (user query)                  │
  │  │     └── Writes WAL records to WAL buffer          │
  │  ├── WALwriter process                               │
  │  │     └── Flushes WAL buffer → WAL files on disk    │
  │  └── WalSender process (one per replica)            │
  │        └── Reads WAL from disk/buffer                │
  │            └── Streams WAL records → Replica         │
  └─────────────────────────────────────────────────────┘

  REPLICA SERVER:
  ┌─────────────────────────────────────────────────────┐
  │  postmaster                                          │
  │  ├── WalReceiver process                            │
  │  │     └── Receives WAL from Primary WalSender      │
  │  │     └── Writes received WAL to replica's disk    │
  │  │     └── Signals Startup process that WAL arrived │
  │  └── Startup process                               │
  │        └── Reads WAL from disk                      │
  │        └── Applies WAL records to data files        │
  │        └── Tracks apply position (LSN)              │
  └─────────────────────────────────────────────────────┘

  The WalReceiver and WalSender maintain a persistent connection.
  If it drops (network issue), WalReceiver reconnects automatically.
  While disconnected, the replica falls behind (lag increases).
  When reconnected, it requests WAL from where it left off.
```

### Monitoring Streaming Replication

```sql
-- On the PRIMARY: check all connected replicas
SELECT
    pid,
    application_name,
    client_addr,
    state,              -- 'streaming', 'catchup', 'backup', 'stopped'
    sent_lsn,           -- WAL position sent to replica
    write_lsn,          -- WAL position replica has written to disk
    flush_lsn,          -- WAL position replica has fsync'd
    replay_lsn,         -- WAL position replica has applied to data files
    write_lag,          -- lag for write_lsn (time-based, PostgreSQL 10+)
    flush_lag,          -- lag for flush_lsn
    replay_lag,         -- lag for replay_lsn ← most meaningful for RPO
    sync_state          -- 'sync', 'async', 'potential', 'quorum'
FROM pg_stat_replication
ORDER BY application_name;

-- Lag in bytes (useful for monitoring absolute data volume at risk):
SELECT
    application_name,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes,
    replay_lag
FROM pg_stat_replication;

-- On the REPLICA: check own receive and apply position
SELECT
    status,             -- 'streaming', 'paused', 'stopped'
    receive_start_lsn,
    received_lsn,       -- WAL received from primary
    last_msg_send_time, -- when primary last sent data
    last_msg_receipt_time, -- when we last received from primary
    latest_end_lsn,
    latest_end_time
FROM pg_stat_wal_receiver;

-- On the REPLICA: is this server a standby?
SELECT pg_is_in_recovery();  -- TRUE on replica, FALSE on primary
```

### The WAL Sender Timeout: Detecting Dead Replicas

The primary tracks replica liveness through the `wal_sender_timeout` parameter. If the replica does not send a status update (StandbyStatusUpdate message) within this interval, the primary considers the replica dead and terminates the WAL sender process. The replica's WalReceiver will then reconnect and restart streaming.

This heartbeat mechanism is important for synchronous replication: if the synchronous replica silently disappears (network partition, not a clean disconnect), the primary needs to detect it and either wait indefinitely or fall back to asynchronous mode, depending on configuration.

## Chapter 2: Logical Replication — Replicating Meaning, Not Bytes

### The Limitation That Logical Replication Solves

Physical streaming replication is powerful but inflexible. It replicates everything, byte-for-byte, from primary to replica. You cannot replicate just one database, just one table, or to a different PostgreSQL major version. You cannot use a replica for anything but read-only queries. You cannot replicate in both directions (primary can write, so can replica — multi-primary is impossible with physical replication).

**Logical replication**, introduced in PostgreSQL 10, takes a fundamentally different approach. Instead of shipping physical WAL records (raw byte changes to data pages), it ships **logical change records** — decoded messages that describe changes in terms of the data model: "a row was inserted into table `users` with these column values," "a row in table `orders` was updated — these columns changed from these old values to these new values."

The key mechanism that makes this possible is **logical decoding** — the process of reading the physical WAL and translating it into a stream of logical, data-level changes.

### Logical Decoding: Reading the WAL for Meaning

At the core of logical replication is the **logical decoding** subsystem. It reads WAL records and, using the current schema (stored in the system catalogs), reconstructs the high-level changes that produced those WAL records. A WAL record that says "write bytes 0x4A3B... at offset 1024 in file base/16384/12345" is translated into "INSERT INTO users (id, name, email) VALUES (42, 'Alice', 'alice@example.com')".

Logical decoding uses a **plugin** (written in C) to format the decoded changes. PostgreSQL ships with a built-in plugin called `pgoutput` (used for built-in logical replication) and `test_decoding` (for debugging). Third-party plugins like `wal2json` (outputs JSON), `decoderbufs` (outputs Protocol Buffers), and `pglogical` (advanced replication) also exist.

```
Logical Decoding Pipeline:

  Physical WAL:
  [INSERT record: page 0x3F, offset 24, tuple bytes: 0x00002A...]
            │
            ▼
  Logical Decoding (reads WAL + system catalogs):
  "Table OID 16385 = users table"
  "Tuple bytes decode to: id=42, name='Alice', email='alice@example.com'"
            │
            ▼
  Output Plugin (pgoutput):
  "Relation: public.users"
  "INSERT: id[int4]:42 name[text]:'Alice' email[text]:'alice@example.com'"
            │
            ▼
  Subscriber (another PostgreSQL):
  "INSERT INTO users (id, name, email) VALUES (42, 'Alice', 'alice@example.com')"
  (re-executed on the subscriber as a normal write operation)
```

### Publication and Subscription: The Logical Replication Model

PostgreSQL's built-in logical replication follows a **publish/subscribe model**:

**The Publisher** (the source database) creates a **publication** — a named object that defines what changes to expose. A publication can include all tables, specific tables, or (in PostgreSQL 15+) specific rows and columns within tables.

**The Subscriber** (the destination database) creates a **subscription** — a named object that connects to a publication and receives the change stream, applying changes to local tables.

```sql
-- ON THE PUBLISHER (source database):

-- Step 1: Ensure wal_level = logical in postgresql.conf
-- (logical replication requires more WAL detail than physical replication)
-- ALTER SYSTEM SET wal_level = 'logical'; -- then restart PostgreSQL

-- Step 2: Create a publication
-- Publish all tables in the database:
CREATE PUBLICATION my_pub FOR ALL TABLES;

-- Publish specific tables only:
CREATE PUBLICATION orders_pub FOR TABLE orders, order_items, products;

-- Publish with row filter (PostgreSQL 15+):
CREATE PUBLICATION active_users_pub
    FOR TABLE users
    WHERE (status = 'active');

-- Publish specific columns only (PostgreSQL 15+):
CREATE PUBLICATION users_pub
    FOR TABLE users (id, name, email);  -- excludes password_hash, etc.

-- View existing publications:
SELECT * FROM pg_publication;
SELECT * FROM pg_publication_tables;

-- ON THE SUBSCRIBER (destination database):

-- Step 1: The tables must exist on the subscriber (schema is NOT auto-created)
-- Create the tables manually or copy schema:
-- pg_dump --schema-only publisher_db | psql subscriber_db

-- Step 2: Create the subscription
CREATE SUBSCRIPTION my_sub
    CONNECTION 'host=publisher_host port=5432 dbname=myapp user=replicator password=secret'
    PUBLICATION my_pub;
-- PostgreSQL automatically:
-- 1. Copies existing data (initial table sync)
-- 2. Begins streaming changes going forward

-- View subscription status:
SELECT * FROM pg_stat_subscription;
-- Key columns: received_lsn, last_msg_send_time, latency

-- Alter subscription (add/remove publications):
ALTER SUBSCRIPTION my_sub ENABLE;
ALTER SUBSCRIPTION my_sub DISABLE;  -- pause the subscription
ALTER SUBSCRIPTION my_sub REFRESH PUBLICATION;  -- detect new tables
DROP SUBSCRIPTION my_sub;
```

### What Logical Replication Enables That Physical Cannot

The publish/subscribe model unlocks use cases that physical replication fundamentally cannot support:

**Cross-version replication:** The subscriber and publisher are independent PostgreSQL instances — they can run different major versions. This makes logical replication the standard mechanism for **zero-downtime major version upgrades**: run the new version as a subscriber, let it catch up, then promote it. Physical replication requires both primary and replica to run the same major version.

```
Zero-Downtime Major Version Upgrade with Logical Replication:

  Phase 1: Set up logical replication from old to new version
  PostgreSQL 15 (primary) ──logical replication──► PostgreSQL 16 (subscriber)

  Phase 2: Wait for subscriber to catch up (lag ≈ 0)

  Phase 3: Point-in-time cutover
  - Application stops writing to PG15 (or enters maintenance mode briefly)
  - Verify subscriber has applied all changes (pg_stat_subscription)
  - Promote PG16 subscriber to standalone (DROP SUBSCRIPTION)
  - Update application connection string to PG16
  - Downtime: seconds (just the connection string change)
```

**Selective table replication:** Replicate only the tables needed for a specific use case — analytics, reporting, a downstream service. Physical replication is all-or-nothing at the cluster level.

**Multi-directional replication:** Since both sides are full PostgreSQL instances that can write, logical replication can flow in both directions — or even form a mesh. This enables **multi-primary** (bidirectional) setups, though conflict resolution must be handled carefully (PostgreSQL's built-in logical replication does not provide automatic conflict resolution — that requires tools like BDR or Citus).

**Different schema on subscriber:** The subscriber can have additional columns (with defaults), different indexes, or different partitioning. As long as the replicated columns match, logical replication works. This enables use cases like "replicate production data to an analytics database with additional computed columns and different indexing."

### Logical Replication Limitations

Logical replication does not support everything:

```
What Logical Replication Does NOT Replicate:

  DDL changes:      CREATE TABLE, ALTER TABLE, DROP TABLE are NOT replicated.
                    Schema changes must be applied manually on the subscriber
                    before the corresponding data change arrives.
                    (This is the most significant operational burden.)

  Sequences:        Sequence values are not replicated. If you replicate
                    a table with a SERIAL or BIGSERIAL column, the subscriber's
                    sequence is not kept in sync. IDs inserted on the publisher
                    arrive on the subscriber as data, but the subscriber's own
                    sequence for that table is not updated. If the subscriber
                    later generates its own IDs, conflicts can occur.

  Large Objects:    pg_largeobject is not replicated.

  Unlogged tables:  Tables created with UNLOGGED do not write WAL and
                    therefore cannot be replicated (logical or physical).

  Truncate:         TRUNCATE is replicated in PostgreSQL 11+ but only to
                    tables in the same publication.

  Partitioned:      Partitioned tables replicate data through their leaf
                    partitions. The partition structure may differ between
                    publisher and subscriber.
```

## Chapter 3: Replication Slots — Ensuring No WAL Is Lost

### The Problem Replication Slots Solve

Streaming replication has a subtle but critical operational problem. The primary continuously generates WAL records and, after a while, recycles old WAL segment files — it deletes WAL that is no longer needed for crash recovery. But "no longer needed for crash recovery" does not mean "no longer needed by replicas."

If a replica falls behind — due to a network outage, a slow disk, a heavy maintenance operation — the primary might delete WAL segments that the replica still needs to catch up. When the replica reconnects and asks for WAL starting from its last applied position, the primary discovers it no longer has that WAL. The replica cannot catch up. It must be re-initialized from scratch — a slow and operationally painful process for large databases.

The `wal_keep_size` parameter (PostgreSQL 13+, `wal_keep_segments` in older versions) partially mitigates this by keeping more WAL than strictly necessary, but it is a blunt instrument — you are keeping WAL "just in case" without knowing exactly what the replica needs.

**Replication slots** solve this precisely. A replication slot is a server-side persistent object that tracks what WAL a specific replica has consumed. The primary guarantees to retain all WAL from the slot's `confirmed_flush_lsn` onward — the primary will never delete WAL that a slot still needs, regardless of how long the replica is disconnected.

```
Replication Slot Mechanics:

  Without a slot:
  Primary WAL:  [seg 001][seg 002][seg 003][seg 004][seg 005]
                ↑ deleted (old)              ↑ replica needs from here
                Replica reconnects: "I need WAL from position in seg 002"
                Primary: "Seg 002 is deleted. Start over."
                Replica must be re-initialized. ← Operational pain.

  With a slot:
  Primary WAL:  [seg 001][seg 002][seg 003][seg 004][seg 005]
                          ↑ SLOT SAYS: "keep from here"
                          Primary cannot delete seg 002 or later.
                Replica reconnects: "I need WAL from position in seg 002"
                Primary: "Seg 002 is here. Here you go."
                Replica catches up seamlessly. ← Correct behavior.
```

### Creating and Managing Replication Slots

```sql
-- Create a physical replication slot (for streaming replication):
SELECT pg_create_physical_replication_slot('replica1_slot');

-- Create a logical replication slot (for logical replication):
SELECT pg_create_logical_replication_slot(
    'my_logical_slot',   -- slot name
    'pgoutput'           -- output plugin
);

-- View all replication slots:
SELECT
    slot_name,
    plugin,              -- NULL for physical, plugin name for logical
    slot_type,           -- 'physical' or 'logical'
    database,            -- NULL for physical, database name for logical
    active,              -- TRUE if a replica is currently connected using this slot
    active_pid,          -- PID of connected WAL sender (if active)
    restart_lsn,         -- Primary must keep WAL from this LSN onward
    confirmed_flush_lsn, -- Last LSN the consumer confirmed consuming (logical only)
    wal_status,          -- 'reserved', 'extended', 'unreserved', 'lost'
    safe_wal_size        -- bytes of WAL available before slot becomes unsafe
FROM pg_replication_slots;

-- Drop a slot (CRITICAL: do this when decommissioning a replica):
SELECT pg_drop_replication_slot('replica1_slot');
```

### The Disk Bloat Danger of Inactive Slots

Replication slots are one of the most dangerous configurations in PostgreSQL if not managed carefully. Because the primary guarantees to retain all WAL from a slot's restart_lsn onward, **an inactive slot — one whose consumer has stopped — causes WAL to accumulate indefinitely**. The primary's WAL directory grows without bound until the disk is full, at which point PostgreSQL stops accepting writes — the entire primary is down.

```
The Inactive Slot Disaster:

  Day 1:  Slot 'replica1_slot' created. Replica is streaming fine.
  Day 3:  Replica server dies (hardware failure). Slot becomes inactive.
  Day 3:  Primary begins accumulating WAL (cannot delete any since Day 3).
  Day 7:  4 days × 10GB/day WAL = 40GB accumulated.
          Nobody notices (monitoring not configured).
  Day 10: WAL directory is 70GB. Disk is 80GB.
          PostgreSQL cannot write WAL → ERROR: could not write to file "pg_wal/..."
          ALL WRITES TO THE PRIMARY FAIL.
          PRIMARY IS DOWN.
          Entire production system is down because of a forgotten replica slot.

Prevention:
  1. Set max_slot_wal_keep_size in postgresql.conf:
     max_slot_wal_keep_size = 10GB
     -- Primary will drop WAL beyond this limit even if slot needs it.
     -- Slot becomes 'lost' state. Replica must be re-initialized.
     -- This is safer than a full disk killing the primary.

  2. Monitor pg_replication_slots for inactive slots:
     SELECT slot_name, active, restart_lsn,
            pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS lag_bytes
     FROM pg_replication_slots
     WHERE NOT active;
     -- Alert if any inactive slot has lag_bytes > threshold (e.g., 5GB)

  3. Drop slots immediately when decommissioning a replica:
     SELECT pg_drop_replication_slot('replica1_slot');
     -- Add this to your replica decommission runbook.
```

### Slots for Logical Replication (Subscriptions)

When you create a logical replication subscription with `CREATE SUBSCRIPTION`, PostgreSQL automatically creates a logical replication slot on the publisher. The slot ensures the publisher retains all WAL needed by the subscriber. Dropping the subscription automatically drops the slot. The same disk bloat danger applies if the subscription is dropped on the subscriber side but the slot is not cleaned up on the publisher (which can happen if the DROP SUBSCRIPTION fails mid-way).

```sql
-- Check if a subscription's slot is healthy:
SELECT s.subname, s.subslotname, rs.active, rs.wal_status,
       pg_wal_lsn_diff(pg_current_wal_lsn(), rs.restart_lsn) AS lag_bytes
FROM pg_subscription s
JOIN pg_replication_slots rs ON s.subslotname = rs.slot_name;

-- If the subscription is dropped but the slot remains (orphaned):
-- On the PUBLISHER:
SELECT pg_drop_replication_slot('orphaned_slot_name');
```

## Chapter 4: Cascading Replicas — Chains of Replication

### The Problem: Too Many Replicas Overloading the Primary

Each replica in a standard streaming replication setup requires one WAL sender process on the primary. If you have 10 replicas, you have 10 WAL sender processes running on the primary, each reading WAL from disk and sending it over a network connection. For a write-heavy primary with high WAL generation, this WAL sender overhead is measurable — especially on network bandwidth.

If you want many replicas (for geographic distribution, read scaling, or analytics isolation), or if some replicas are in different datacenters with limited bandwidth, the burden on the primary grows proportionally.

**Cascading replication** solves this by allowing replicas to stream WAL to other replicas, rather than all replicas connecting directly to the primary. A replica that serves as a WAL source for other replicas is called an **intermediate standby** or **cascading standby**.

### How Cascading Replication Works

In cascading replication, an intermediate standby acts as a WAL relay. It receives WAL from the primary (via streaming replication), applies it locally (as a normal replica does), and simultaneously streams it to downstream replicas. The downstream replicas connect to the intermediate standby's WAL sender, not the primary's.

```
Cascading Replication Topology:

  Standard (all replicas connect to primary):
  ┌──────────┐  WAL ──► Replica 1 (New York)
  │ Primary  │  WAL ──► Replica 2 (London)
  │ (8 WAL   │  WAL ──► Replica 3 (Singapore)
  │  senders)│  WAL ──► Replica 4 (Tokyo)
  └──────────┘  WAL ──► Replica 5 (Sydney)
                         ... (8 WAL senders = 8× bandwidth to primary)

  Cascading (replicas relay WAL to downstream replicas):
  ┌──────────┐
  │ Primary  │  WAL ──► Replica 1 (US-East)  ──► Replica 3 (US-West)
  │ (2 WAL   │                                ──► Replica 4 (Canada)
  │  senders)│  WAL ──► Replica 2 (EU)       ──► Replica 5 (London)
  └──────────┘                                ──► Replica 6 (Frankfurt)

  Primary now has only 2 WAL sender processes.
  Each regional hub (Replica 1, Replica 2) handles distribution within its region.
  Primary's WAL bandwidth: 2× (instead of 6×).
```

### Configuring Cascading Replication

Configuring cascading replication from a downstream replica's perspective is nearly identical to configuring it from the primary — the downstream replica just points its `primary_conninfo` at the intermediate standby instead of the primary:

```
Intermediate Standby Configuration:

  This server is BOTH a replica (of the primary) AND a source (for downstream).
  No special configuration needed beyond normal standby configuration.
  PostgreSQL automatically allows WAL sender processes on standby servers
  (controlled by max_wal_senders, which applies to all servers).

Downstream Replica Configuration (postgresql.conf):

  # Points to the INTERMEDIATE STANDBY, not the primary:
  primary_conninfo = 'host=intermediate_standby_ip port=5432
                      user=replicator password=secret
                      application_name=downstream_replica1'

  # Standby signal file must exist (PostgreSQL 12+):
  # touch $PGDATA/standby.signal

  Everything else is identical to connecting to the primary.
  The downstream replica cannot tell the difference between connecting
  to the primary and connecting to an intermediate standby.
```

### Cascading Replication Lag

The obvious trade-off of cascading replication is **compounded lag**. If the intermediate standby is 5ms behind the primary, and the downstream replica is 5ms behind the intermediate standby, the downstream replica is at least 10ms behind the primary. In a deep cascade (primary → relay 1 → relay 2 → leaf replica), lag compounds at each hop.

```
Cascade Lag Accumulation:

  Primary commit at T=0
  │
  ├── T=1ms:  Intermediate standby receives WAL
  │           T=2ms: Intermediate standby applies WAL (replay_lsn advances)
  │           T=2ms: Intermediate standby begins streaming to downstream
  │
  └── T=3ms:  Downstream replica receives WAL
              T=4ms: Downstream replica applies WAL

  Downstream replica lag from primary: ~4ms (2× single-hop lag)

  For deeply nested cascades, lag can become significant.
  Rule of thumb: limit cascade depth to 2-3 hops maximum.
  Monitor replay_lag at each level independently.
```

### When to Use Cascading Replication

Cascading replication makes sense when:

**You need many geographically distributed replicas** and want to limit the bandwidth burden on the primary. Instead of 10 replicas pulling WAL from the primary, you have 3 regional hubs each with 3-4 local replicas.

**You need analytics or ETL replicas** that require significant resources (CPU for heavy queries, memory for large sorts) and you do not want analytics workloads competing with the primary's WAL sender resources.

**You have limited bandwidth from the primary** (e.g., the primary is in an on-premises datacenter with limited WAN bandwidth to cloud regions) and you want a cloud-based intermediate standby to handle further distribution.

## Chapter 5: Standby and Hot Standby — Reading from Replicas

### The Two Modes of a Standby Server

A PostgreSQL standby server can operate in one of two modes: **warm standby** or **hot standby**. The difference is whether the replica is accessible for read queries while it is in recovery mode.

**Warm standby** (the historical default, before PostgreSQL 9.0): The replica is exclusively applying WAL. It cannot serve any connections — not even read-only ones. It is "warm" because it is ready to be promoted quickly (all WAL is applied, data is current), but it is invisible to users. Warm standbys exist purely for failover. They are not used for read scaling.

**Hot standby** (the modern default, enabled with `hot_standby = on`): The replica applies WAL and simultaneously accepts read-only connections from clients. Users can query a hot standby as if it were a regular PostgreSQL instance, with the constraint that all queries are read-only — no writes, no DDL. Hot standbys serve dual purpose: failover readiness and read scaling.

```
Warm Standby vs. Hot Standby:

  WARM STANDBY:
  ┌──────────────────────────────────────┐
  │  Standby Server                      │
  │  State: IN RECOVERY (applying WAL)   │
  │  User connections: REJECTED          │
  │  Error to client:                    │
  │  "server is not accepting connections"│
  └──────────────────────────────────────┘
  Use: Failover only. No read traffic.

  HOT STANDBY (hot_standby = on):
  ┌──────────────────────────────────────┐
  │  Standby Server                      │
  │  State: IN RECOVERY (applying WAL)   │
  │  User connections: ACCEPTED (reads)  │
  │  Reads: work normally                │
  │  Writes: rejected with error:        │
  │  "cannot execute INSERT in a         │
  │   read-only transaction"             │
  └──────────────────────────────────────┘
  Use: Failover + read scaling.
```

### Configuring Hot Standby

Hot standby is controlled by a single parameter on the replica:

```
Replica postgresql.conf:

  hot_standby = on    # Allow read-only connections during recovery
                      # (default: on in PostgreSQL 10+)

  # How many concurrent connections to allow on the standby:
  max_connections = 200  # Can be same or different from primary

  # Behavior when a read query conflicts with WAL application:
  hot_standby_feedback = on   # Tell primary what queries are running
                               # Primary delays vacuuming rows the standby needs
                               # Prevents query cancellation but can slow vacuum

  max_standby_streaming_delay = 30s  # How long to wait before cancelling
                                     # a conflicting read query
                                     # (to let WAL application proceed)
  max_standby_archive_delay = 30s    # Same but for WAL archive recovery
```

### Query Conflicts on Hot Standby

Hot standby introduces a subtle but important operational phenomenon: **query conflicts**. The primary is continuously modifying data — including running VACUUM, which removes old row versions (dead tuples). When the primary vacuums a table, it writes WAL records saying "row version X is no longer needed." When the replica applies these WAL records, it must remove those row versions from its data files.

But what if a read query on the hot standby is currently reading those exact row versions? The WAL application (which must proceed to keep the replica current) and the read query (which needs the old row versions for its snapshot) are in conflict.

PostgreSQL resolves this conflict in favor of WAL application — the replica will cancel the read query to let WAL application proceed:

```
Hot Standby Query Conflict Example:

  Standby is applying WAL from primary.
  Primary's VACUUM wrote WAL: "row 42 in table 'orders' is dead, reclaim it"

  Simultaneously on the standby:
  Read query: "SELECT * FROM orders WHERE status = 'completed'"
  This query's snapshot includes row 42 (it was alive when the query started).

  The WAL application must process the "reclaim row 42" record.
  But the read query is currently holding row 42 in its snapshot.

  CONFLICT: WAL application vs. read query.

  PostgreSQL's resolution (controlled by max_standby_streaming_delay):
  1. Wait up to max_standby_streaming_delay (default: 30s).
  2. If the read query finishes within that window: no problem.
  3. If the read query is still running after 30s:
     Cancel the read query.
     ERROR: canceling statement due to conflict with recovery

  Client receives this error and must retry the query.

Solutions:
  hot_standby_feedback = on:
    Standby tells primary "I have an active query that needs rows up to this snapshot."
    Primary delays vacuuming rows the standby needs.
    Eliminates query cancellations, but can delay vacuum on the primary
    (accumulating dead rows = table bloat).

  Increase max_standby_streaming_delay:
    Give read queries more time before cancellation.
    Accepts more lag in WAL application during conflicts.

  Query timeout on standby reads:
    Application sets a short statement_timeout on standby connections.
    Queries are unlikely to run long enough to conflict.
```

### Hot Standby Restrictions

Read-only queries on hot standby work well for most use cases, but there are specific SQL constructs that are not permitted:

```sql
-- These work on hot standby (read-only operations):
SELECT * FROM users WHERE id = 42;
SELECT COUNT(*) FROM orders WHERE status = 'pending';
EXPLAIN ANALYZE SELECT ...;  -- reads query plan + executes read-only
BEGIN;
  SELECT * FROM products FOR KEY SHARE;  -- only if primary allows
COMMIT;

-- These FAIL on hot standby (write operations):
INSERT INTO users ...;
UPDATE orders SET status = 'shipped' WHERE id = 1;
DELETE FROM sessions WHERE expired = TRUE;
CREATE TABLE temp_table ...;
SET search_path = myschema;  -- session-modifying (some restrictions)

-- Explicit error message on write attempt:
-- ERROR: cannot execute INSERT in a read-only transaction
-- HINT: In a parallel worker, the query is not running in a transaction.
```

### Promoting a Hot Standby to Primary

When the primary fails and the hot standby must take over, **promotion** is the process of transitioning the standby from recovery mode to primary mode. After promotion, the former standby accepts writes and is no longer applying WAL from the old primary — it is now the source of truth.

```
Promotion Methods:

  Method 1: pg_ctl promote (command-line, PostgreSQL 12+)
  $ pg_ctl promote -D /var/lib/postgresql/data
  LOG: received promote request
  LOG: redo in progress, current LSN 0/3A1F2000, consistent LSN 0/3A1F1000
  LOG: pausing at the end of recovery
  LOG: the database system is ready to accept connections

  Method 2: pg_promote() SQL function (remote promotion, PostgreSQL 12+)
  SELECT pg_promote();  -- run on the standby server
  -- Returns TRUE when promotion is complete.

  Method 3: Trigger file (historical, PostgreSQL < 12)
  $ touch /var/lib/postgresql/data/promote.trigger
  -- Standby detects the file, promotes, and removes the file.

  What happens internally during promotion:
  1. Standby stops accepting WAL from the old primary.
  2. Standby applies all WAL it has already received (finishes recovery).
  3. Standby writes a new WAL timeline (timeline ID increments).
  4. Standby begins accepting read/write connections.
  5. Standby generates its own WAL going forward (it is now the primary).

  After promotion:
  - Update application connection strings to point to new primary.
  - Update DNS / load balancer / virtual IP.
  - Old primary (when recovered) becomes a replica of the new primary.
    (It must be "rewound" to diverge from the new timeline: pg_rewind)
```

### pg_rewind: Recovering the Old Primary as a Replica

After a failover, the old primary has WAL records that the new primary does not — the transactions that were committed on the old primary after the split (the ones that caused the failover). The new primary has a different WAL history from that divergence point onward (it started a new timeline).

To make the old primary a replica of the new primary, you cannot just point it at the new primary — their WAL histories have diverged. `pg_rewind` solves this by comparing the two servers' data directories, finding the divergence point, and rewinding the old primary's data directory to the divergence point — essentially undoing the changes that only the old primary has, putting it back in sync with the new primary's history. After `pg_rewind`, the old primary can start as a replica of the new primary.

```bash
# After failover: recover old primary as replica of new primary

# On the OLD PRIMARY (now being converted to replica):
pg_rewind \
    --target-pgdata=/var/lib/postgresql/data \
    --source-server='host=new_primary_ip user=replicator' \
    --progress

# pg_rewind will:
# 1. Find the divergence point between old primary and new primary
# 2. Fetch data files from new primary that differ
# 3. Rewind old primary's data directory to the common point
# 4. Allow new primary's WAL to be applied going forward

# Then configure as standby:
# Add primary_conninfo to postgresql.conf pointing to new primary
# touch standby.signal
# pg_ctl start

# pg_rewind requires:
# wal_log_hints = on  OR  data checksums enabled (on the old primary)
# The new primary must have the replicator user with REPLICATION privilege
```

## Chapter 6: Replication in Practice — Full Architecture Reference

### Choosing the Right Replication Type

```
Decision Guide: Physical vs. Logical Replication

  Physical Streaming Replication — choose when:
  ✓ You need a complete standby for failover (HA requirement)
  ✓ You want to replicate everything (full cluster copy)
  ✓ You need the simplest possible setup
  ✓ Major version is the same on primary and replica
  ✓ You want read scaling with the same data as primary

  Logical Replication — choose when:
  ✓ You need to replicate specific tables or databases only
  ✓ You are doing a major version upgrade (cross-version replication)
  ✓ You need the subscriber to have a different schema (extra columns, indexes)
  ✓ You want to replicate to a non-PostgreSQL system (via logical decoding plugins)
  ✓ You need bidirectional or multi-primary replication
  ✓ You need to filter rows or columns

  Use Both Together — for comprehensive coverage:
  Physical replication for HA hot standby (failover + read scaling)
  +
  Logical replication for cross-version upgrades, analytics databases,
  or selective downstream consumers (event streaming, microservices)
```

### The Complete Configuration for a Production Setup

```
Production Replication Architecture for a 3-Server Setup:

  Server 1: Primary (writes + some reads)
  Server 2: Synchronous Hot Standby (HA failover + reads)
  Server 3: Asynchronous Hot Standby (read scaling, analytics)

PRIMARY postgresql.conf:
  wal_level = replica          # or 'logical' if logical rep also needed
  max_wal_senders = 10
  max_replication_slots = 10
  wal_keep_size = 2048         # 2GB WAL kept locally
  synchronous_standby_names = 'FIRST 1 (standby1)'
  synchronous_commit = on
  # Monitoring:
  wal_sender_timeout = 60s

PRIMARY pg_hba.conf:
  host  replication  replicator  standby1_ip/32  scram-sha-256
  host  replication  replicator  standby2_ip/32  scram-sha-256

STANDBY 1 (synchronous) postgresql.conf:
  hot_standby = on
  primary_conninfo = 'host=primary_ip port=5432 user=replicator
                      password=secret application_name=standby1'
  hot_standby_feedback = on
  max_standby_streaming_delay = 30s
  recovery_min_apply_delay = 0   # no delay — stay current for failover

STANDBY 2 (asynchronous, read replica) postgresql.conf:
  hot_standby = on
  primary_conninfo = 'host=primary_ip port=5432 user=replicator
                      password=secret application_name=standby2'
  hot_standby_feedback = off    # analytics queries are long — don't block primary vacuum
  max_standby_streaming_delay = 5min  # tolerate more delay for long analytics queries
  # recovery_min_apply_delay = 30min  # optional: delayed replica for DR against mistakes

REPLICATION SLOTS (on primary):
  SELECT pg_create_physical_replication_slot('standby1_slot');
  SELECT pg_create_physical_replication_slot('standby2_slot');

  -- Tell each standby to use its slot:
  -- Add to primary_conninfo on each standby:
  -- primary_slot_name = 'standby1_slot'  (in standby1's postgresql.conf)
  -- primary_slot_name = 'standby2_slot'  (in standby2's postgresql.conf)
```

### Key Replication Monitoring Queries

```sql
-- === ON PRIMARY ===

-- Complete replication status dashboard:
SELECT
    application_name,
    client_addr,
    state,
    sync_state,
    pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn)   AS not_yet_sent_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), write_lsn)  AS not_yet_written_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), flush_lsn)  AS not_yet_flushed_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS not_yet_replayed_bytes,
    write_lag,     -- time-based lag to write position
    flush_lag,     -- time-based lag to flush position
    replay_lag     -- time-based lag to replay position (most meaningful for RPO)
FROM pg_stat_replication
ORDER BY replay_lag DESC NULLS LAST;

-- Replication slot health (ALERT if inactive slots exist):
SELECT
    slot_name,
    slot_type,
    active,
    wal_status,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    ) AS retained_wal
FROM pg_replication_slots
ORDER BY restart_lsn;

-- === ON REPLICA ===

-- Is this server a replica?
SELECT pg_is_in_recovery();

-- Current recovery position:
SELECT
    pg_last_wal_receive_lsn()  AS received_lsn,  -- what we have received
    pg_last_wal_replay_lsn()   AS replayed_lsn,  -- what we have applied
    pg_last_xact_replay_timestamp()              -- timestamp of last applied tx
;

-- How far behind is this replica?
SELECT
    now() - pg_last_xact_replay_timestamp() AS replication_delay;

-- === PGBOUNCER / APPLICATION ===
-- Direct writes to primary, reads to replica:
-- connection string for writes: host=primary_ip
-- connection string for reads:  host=standby1_ip,standby2_ip  (libpq chooses)
-- Or use a load balancer / HAProxy targeting standbys for reads.
```

## Chapter 7: Patroni — Automated Failover Orchestration

### Why Manual Failover Is Not Enough for Production

Everything we have discussed so far — streaming replication, slots, hot standby, pg_promote — describes the mechanisms. But none of it is automatic. If the primary dies at 3 AM, someone must notice, decide which replica to promote, run `pg_ctl promote`, update DNS, and notify applications. This manual process takes minutes even for an experienced engineer.

For systems with RTO requirements of under 60 seconds, manual failover is simply not viable. This is where **Patroni** — the most widely adopted PostgreSQL HA solution — enters the picture.

Patroni is an open-source HA framework (written in Python, originally by Zalando) that automates the entire failover lifecycle: health monitoring, leader election, automatic promotion, and configuration management. It uses a distributed consensus store (etcd, Consul, or ZooKeeper) to coordinate which server is currently the primary.

```
Patroni Architecture:

  ┌─────────────────────────────────────────────────────────────────┐
  │                    Patroni Cluster                              │
  │                                                                 │
  │  ┌─────────────────┐   ┌─────────────────┐  ┌───────────────┐  │
  │  │  Node 1         │   │  Node 2         │  │  Node 3       │  │
  │  │  Patroni agent  │   │  Patroni agent  │  │  Patroni agent│  │
  │  │  PostgreSQL     │   │  PostgreSQL     │  │  PostgreSQL   │  │
  │  │  PRIMARY  ◄─────┼───┼─ replica       │  │  replica      │  │
  │  │  (Leader)       │   │  (Follower)     │  │  (Follower)   │  │
  │  └────────┬────────┘   └────────┬────────┘  └───────┬───────┘  │
  │           │                     │                   │          │
  │           └─────────────────────┴───────────────────┘          │
  │                                 │                              │
  │                                 ▼                              │
  │  ┌─────────────────────────────────────────────────────────┐   │
  │  │  Distributed Consensus Store (etcd / Consul / ZooKeeper)│   │
  │  │  "Node 1 is the leader. Leader lease expires in 30s."   │   │
  │  │  "Node 1 last heartbeat: 5s ago."                       │   │
  │  └─────────────────────────────────────────────────────────┘   │
  └─────────────────────────────────────────────────────────────────┘

  How automatic failover works:
  1. Patroni agent on each node heartbeats to consensus store every 10s.
  2. Leader holds a "leader lease" in the consensus store (TTL ~30s).
  3. If primary fails: leader lease expires (not renewed within TTL).
  4. Remaining agents race to acquire the leader lease.
  5. Winner: promotes its local PostgreSQL to primary.
  6. Losers: reconfigure their PostgreSQL to follow the new primary.
  7. HAProxy / load balancer: detects new primary via Patroni REST API.
  8. Total time: typically 15-30 seconds.
```

Patroni is the production standard for managed PostgreSQL HA and is used by Zalando, GitHub, and most serious PostgreSQL deployments. Cloud providers' managed PostgreSQL services (AWS RDS Multi-AZ, Google Cloud SQL HA) implement similar orchestration internally.

## Epilogue: Replication as a Living System

PostgreSQL replication is not a "set it and forget it" configuration. It is a living system that requires ongoing attention: monitoring lag metrics, watching slot sizes, testing failover procedures, managing the operational overhead of cross-version upgrades with logical replication, and understanding the subtle interactions between hot standby query conflicts and vacuum on the primary.

The engineer who sets up streaming replication, confirms it is working, and never looks at it again will eventually be surprised — by a replica that fell so far behind the slot has filled the disk, by a failover that takes ten minutes because the pg_rewind procedure was never tested, by a logical replication subscriber that stopped receiving changes because the publication was accidentally dropped.

Replication is reliable precisely because it is understood and monitored, not because it is resilient to neglect. The WAL keeps flowing, slot positions keep advancing, lag metrics keep reporting — and the engineer who watches those signals and responds to deviations has a replication system that actually protects the data it was built to protect.

Physical replication keeps the data safe and the system available. Logical replication keeps the data moving to where it needs to be. Replication slots keep the WAL from vanishing before the replica needs it. Cascading replicas distribute the load. Hot standby makes idle replicas productive. And understanding how all of these fit together — that is what transforms a working replication setup into a production-grade one.
