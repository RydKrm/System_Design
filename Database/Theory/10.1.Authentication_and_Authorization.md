## 1. Authentication vs Authorization — The Fundamental Distinction

Before diving into the specifics of database security, you must have absolute clarity on the distinction between authentication and authorization, because these two concepts are often conflated and that conflation leads to poorly designed systems.

**Authentication** answers the question: _"Who are you?"_ It is the process of verifying identity. When your Go application connects to PostgreSQL with a username and password, the database authenticates that connection — it verifies that the credentials presented correspond to a known identity. Authentication can be done through passwords (the most common), certificate-based authentication (TLS client certificates), LDAP or Active Directory integration, Kerberos, or other identity providers. Once authentication succeeds, the database knows _who_ is making requests. Before authentication, the database refuses to do anything.

**Authorization** answers the question: _"What are you allowed to do?"_ It is the process of checking permissions. Once the database knows who you are (authentication), it must decide whether _this particular identity_ is allowed to perform _this particular operation_ on _this particular object_. Can this user read this table? Can they update this column? Can they delete rows from this table? These checks happen on every single query, every single time, completely independent of whether authentication succeeded one second ago or one hour ago.

```
THE FLOW — Authentication Then Authorization:

Client (Go App)
     │
     │  "I am 'app_user', password: 'secret123'"
     ▼
┌─────────────────────────────────────────────────────────────┐
│                     PostgreSQL Engine                       │
│                                                             │
│  Step 1: AUTHENTICATION                                     │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Does 'app_user' exist?              → YES           │   │
│  │  Is the password correct?            → YES           │   │
│  │  Is the connection from allowed IP?  → YES (pg_hba)  │   │
│  │  Identity confirmed: 'app_user'                      │   │
│  └──────────────────────────────────────────────────────┘   │
│                          │                                  │
│                          ▼                                  │
│  Step 2: AUTHORIZATION (on every query)                     │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Query: SELECT * FROM orders WHERE user_id = 42      │   │
│  │                                                      │   │
│  │  Does 'app_user' have SELECT on table 'orders'? YES  │   │
│  │  Are there Row-Level Security policies?  → Check...  │   │
│  │  Is column access allowed?               → Check...  │   │
│  │                                                      │   │
│  │  → Query ALLOWED. Execute and return result.         │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                             │
│  If ANY check fails → ERROR: permission denied              │
└─────────────────────────────────────────────────────────────┘
```

In PostgreSQL specifically, authentication is configured in a file called `pg_hba.conf` (HBA stands for Host-Based Authentication). This file defines rules about which users can connect from which hosts using which authentication methods. Authorization, by contrast, is configured through SQL commands (`GRANT`, `REVOKE`) and is stored in system catalog tables within the database itself.

This distinction is also critical when you think about your application architecture. Your Go application might have its own user authentication system — login forms, JWT tokens, session management. That is application-level authentication. But the database has its own separate authentication and authorization system. These two systems can and should work together, but they operate at different layers. A user might be authenticated in your application but the database still enforces what that application's service account is allowed to do. An attacker who bypasses your application's authentication cannot bypass the database's, if the database's authorization is properly configured.

## 2. Database Users and Roles — The Identity System

In modern databases, particularly PostgreSQL, the concepts of "user" and "role" have been unified into a single concept, and understanding this unification is the starting point for everything else in this guide.

Historically, databases had users (identities that could log in) and groups (collections of users that shared permissions). PostgreSQL, from version 8.1 onward, replaced both concepts with the single notion of a **role**. A role is the fundamental unit of identity in PostgreSQL. A role can be configured to log in (making it behave like a traditional user), it can have other roles granted to it (making it behave like a traditional group), or it can do both. In effect, users and groups are just roles with specific properties.

When you execute `CREATE USER` in PostgreSQL, it is literally identical to executing `CREATE ROLE ... WITH LOGIN` — the `CREATE USER` command is syntactic sugar that adds the `LOGIN` attribute automatically. Understanding this equivalence is important because it means every concept we discuss about roles applies equally to users.

A role has a set of **attributes** — properties that govern what the role itself is capable of, independent of any specific object permissions. The most important attributes are as follows. The `LOGIN` attribute allows the role to establish a database connection — without this, a role cannot authenticate. The `SUPERUSER` attribute is the nuclear option: a superuser bypasses all authorization checks entirely. Never grant superuser to an application role. The `CREATEDB` attribute allows the role to create new databases. The `CREATEROLE` attribute allows the role to create and manage other roles — a powerful privilege that should be granted sparingly. The `INHERIT` attribute (the default) causes the role to automatically inherit the permissions of any role granted to it, which is the key mechanism behind role hierarchies. The `CONNECTION LIMIT` attribute caps how many concurrent connections this role can make, protecting against runaway connection pools.

```
ROLE ATTRIBUTES — The Role's Own Capabilities:

CREATE ROLE app_user WITH
  LOGIN                        -- Can connect to the database
  PASSWORD 'hashed_secret'     -- Authentication credential
  CONNECTION LIMIT 50          -- Max 50 concurrent connections
  VALID UNTIL '2027-01-01';    -- Credential expiry (optional)

CREATE ROLE reporting_user WITH
  LOGIN
  PASSWORD 'report_secret'
  CONNECTION LIMIT 10;

CREATE ROLE readonly_role WITH
  -- NO LOGIN                  -- Cannot connect directly (it's a group role)
  INHERIT;                     -- Will inherit permissions from roles granted to it

CREATE ROLE admin_role WITH
  CREATEDB                     -- Can create databases
  CREATEROLE;                  -- Can create other roles

-- Superuser (use ONLY for maintenance, never for applications):
CREATE ROLE dba_admin WITH
  SUPERUSER
  LOGIN
  PASSWORD 'very_secure_password';

─────────────────────────────────────────────────────────────────────
ROLE HIERARCHY — How Roles Nest:

                  ┌──────────────────┐
                  │  readonly_role   │  (no login, group role)
                  │  GRANT: SELECT   │  (has SELECT on all tables)
                  │  on all tables   │
                  └────────┬─────────┘
                           │ GRANT readonly_role TO...
              ┌────────────┼───────────────┐
              │            │               │
              ▼            ▼               ▼
      ┌────────────┐ ┌────────────┐ ┌────────────┐
      │ app_user   │ │reporting_  │ │ analyst_   │
      │ (LOGIN)    │ │ user       │ │ user       │
      │ INHERITS   │ │ (LOGIN)    │ │ (LOGIN)    │
      │ readonly   │ │ INHERITS   │ │ INHERITS   │
      │ privileges │ │ readonly   │ │ readonly   │
      └────────────┘ └────────────┘ └────────────┘

All three users automatically have SELECT on all tables
because they all inherit from readonly_role.
Grant once on the role → applies to all members automatically.
```

PostgreSQL also maintains several important built-in roles that exist by default. The `postgres` role is the initial superuser created during database installation. You should almost never use this role for application connections. PostgreSQL also comes with predefined group roles like `pg_read_all_data` (can read all tables, views, and sequences), `pg_write_all_data` (can insert, update, delete in all tables), and `pg_monitor` (can access monitoring views). These predefined roles are useful starting points that reduce the boilerplate of setting up common permission patterns.

MySQL's approach is slightly different: it separates users and roles more explicitly, and user identities include the hostname from which the user connects (so `'app_user'@'localhost'` and `'app_user'@'192.168.1.%'` are completely different identities). MongoDB uses its own role-based system with roles defined at the database level and a set of built-in roles like `read`, `readWrite`, `dbAdmin`, and `userAdmin`. The conceptual model is the same across all these systems — the syntax differs.

## 3. Privileges — The Permission Vocabulary

A privilege is a specific type of operation that a role is allowed to perform on a specific database object. In PostgreSQL, privileges exist for every type of object — databases, schemas, tables, columns, sequences, functions, and more. The full vocabulary of privileges is large, but the core set that you will use in every application is manageable.

On **tables and views**, the fundamental privileges are `SELECT` (read rows), `INSERT` (add rows), `UPDATE` (modify existing rows), `DELETE` (remove rows), `TRUNCATE` (empty the entire table, which is faster than DELETE), `REFERENCES` (create foreign keys that reference this table), and `TRIGGER` (create triggers on this table). In almost every application, your application's database user needs only `SELECT`, `INSERT`, `UPDATE`, and sometimes `DELETE` on the tables it uses. Granting `TRUNCATE` or `TRIGGER` to an application user is rarely necessary and expands the attack surface.

On **sequences** (which PostgreSQL uses for auto-incrementing columns via `SERIAL` or `BIGSERIAL`), the privilege you need is `USAGE` (to call `nextval()`) and `UPDATE` (to advance the sequence). Without `USAGE` on the relevant sequence, a user cannot insert a row into a table that uses a sequence for its primary key, even if they have `INSERT` on the table.

On **schemas** (the namespaces that organise tables within a database), the privileges are `USAGE` (allows the role to access objects within the schema, see their definitions, query them if they have the necessary table-level privilege) and `CREATE` (allows creating new objects within the schema). The schema `USAGE` privilege is a common source of confusion: even if you grant a user `SELECT` on a table, they cannot query it unless they also have `USAGE` on the schema that contains the table. PostgreSQL has a two-level check — schema first, then object.

On **databases**, the `CONNECT` privilege determines whether a role can connect to that database at all. The `CREATE` privilege on a database allows the role to create new schemas within it. The `TEMP` privilege allows the role to create temporary tables.

```
PRIVILEGE HIERARCHY — Two Levels of Access Control:

To access table public.orders, a user needs ALL of the following:
                                                                
Level 1: DATABASE privileges
  CONNECT on database 'mydb'
  (Can I even enter this database?)

           │
           ▼

Level 2: SCHEMA privileges
  USAGE on schema 'public'
  (Can I see and access objects in this schema?)

           │
           ▼

Level 3: TABLE privileges
  SELECT / INSERT / UPDATE / DELETE on table 'orders'
  (Can I perform this specific operation on this table?)

           │
           ▼ (if applicable)

Level 4: COLUMN privileges (optional, most restrictive)
  SELECT (column_name) / UPDATE (column_name)
  (Can I access this specific column?)

ALL FOUR LEVELS must pass for the query to succeed.
A failure at any level → "permission denied"

─────────────────────────────────────────────────────────────────────
COMMON MISTAKE — Missing Schema USAGE:

-- This seems correct but will fail:
GRANT SELECT ON TABLE public.orders TO app_user;
-- ↑ app_user has table-level SELECT

-- But app_user CANNOT use it without:
GRANT USAGE ON SCHEMA public TO app_user;
-- Without this, query returns: ERROR: permission denied for schema public

-- Correct setup:
GRANT CONNECT ON DATABASE mydb TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
GRANT SELECT ON TABLE public.orders TO app_user;
-- NOW it works ✓
```

There is also a special concept called the **owner** of an object. When you create a table, your role becomes its owner. The owner has all privileges on that object automatically, without needing explicit GRANT statements. Changing the owner is done with `ALTER TABLE ... OWNER TO ...`. In a well-designed system, the owner of tables is typically a dedicated "schema owner" role that is not used for application connections — the application uses a separate role with carefully limited privileges granted by the schema owner.

Another important concept is `ALL PRIVILEGES` — a shorthand that grants every applicable privilege on an object in one statement. `GRANT ALL PRIVILEGES ON TABLE orders TO admin_role` is convenient but dangerous for application users. Reserve `ALL PRIVILEGES` for administrative roles and schema owners, not for roles that applications connect as.

## 4. GRANT and REVOKE — Giving and Taking Permissions

`GRANT` and `REVOKE` are the SQL commands through which all privilege management happens. They are declarative — you describe what should be permitted (or not), and the database enforces it from that point forward on every subsequent query.

The `GRANT` command has two distinct forms that serve very different purposes and it is critical that you understand both. The first form grants a **privilege on an object** to a role. The second form grants **membership in one role** to another role. These are fundamentally different operations: the first gives permission to perform a database operation, while the second creates an inheritance relationship where one role gains all the permissions of another.

```sql
-- FORM 1: Grant object privilege
-- "Allow app_user to SELECT from the orders table"
GRANT SELECT ON TABLE orders TO app_user;

-- FORM 2: Grant role membership
-- "Make app_user a member of the readonly_role group"
GRANT readonly_role TO app_user;
-- Now app_user INHERITS all privileges that readonly_role has
```

The `GRANT` command supports several modifiers that significantly alter its behaviour. The most important is `WITH GRANT OPTION`, which allows the recipient of a privilege to in turn grant that same privilege to other roles. This is powerful and dangerous — it means privilege can propagate transitively through your system in ways that can be hard to track. Use `WITH GRANT OPTION` only when genuinely necessary and with full awareness of the implications.

Another critical modifier is `WITH ADMIN OPTION` (used when granting role membership, not object privileges). It allows the role that was granted membership to in turn grant that role membership to others. Again, use sparingly.

PostgreSQL also provides a shorthand called `ALL TABLES IN SCHEMA`, which grants a privilege on every table currently in a schema in one statement. Note carefully the word "currently" — this does NOT affect tables created in the future. For future tables to automatically have the right permissions, you need `ALTER DEFAULT PRIVILEGES`, which is a separate and frequently overlooked command.

```sql
-- Grant SELECT on all CURRENT tables in public schema:
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_role;
-- This grants on tables that exist RIGHT NOW.
-- Tables created TOMORROW will NOT have this grant.

-- Fix with DEFAULT PRIVILEGES:
-- "For any table that schema_owner creates in public schema,
--  automatically grant SELECT to readonly_role"
ALTER DEFAULT PRIVILEGES FOR ROLE schema_owner
  IN SCHEMA public
  GRANT SELECT ON TABLES TO readonly_role;

-- Now ALL future tables created by schema_owner in public
-- will automatically have SELECT granted to readonly_role ✓
```

`REVOKE` is the mirror image of `GRANT`. It removes a privilege that was previously granted. Importantly, you can only revoke privileges that were granted by the same grantor — if user A granted a privilege and user B also granted the same privilege, user A revoking it will not fully remove the privilege if user B's grant is still in place. The database tracks grants by grantor, and a privilege is fully removed only when all grants of it are revoked.

There is also a `CASCADE` option for `REVOKE`. If you revoke a privilege that was granted with `WITH GRANT OPTION`, and the recipient used that grant option to grant the same privilege to others, `REVOKE ... CASCADE` will follow the chain and revoke all downstream grants. Without `CASCADE`, the revocation fails if dependent grants exist.

```sql
-- Simple revoke:
REVOKE SELECT ON TABLE orders FROM app_user;

-- Revoke with cascade (removes downstream grants too):
REVOKE SELECT ON TABLE orders FROM manager_role CASCADE;
-- This revokes the privilege from manager_role AND from any role
-- that manager_role previously granted it to (if using GRANT OPTION)

-- Revoke role membership:
REVOKE readonly_role FROM app_user;
-- app_user no longer inherits readonly_role's privileges

-- Revoke ALL privileges on an object:
REVOKE ALL PRIVILEGES ON TABLE orders FROM app_user;
```

A subtle but important nuance: `REVOKE` removes explicitly granted privileges, but it does not affect privileges derived from ownership. If a role owns a table, revoking their SELECT privilege on it does nothing — they still have full access as the owner. To remove an owner's access, you must change the ownership of the object first.

The discipline of privilege management — always granting the minimum necessary, always revoking when access is no longer needed, auditing grants regularly — is what security professionals call the **Principle of Least Privilege**. It means every role has exactly the permissions it needs to do its job and nothing more. This principle is not pedantry — it is the difference between an attacker who has compromised your application being able to read one table versus being able to read every table, update financial records, and drop your entire database.

## 5. Role-Based Access Control (RBAC)

Role-Based Access Control is not a specific SQL feature — it is a **design pattern** for organising and managing permissions. It is the answer to a practical problem: in a real system with dozens of database users and hundreds of database objects, managing permissions user-by-user becomes unmanageable. If you have 20 application microservices and you want them all to have the same read access to the `products` table, you do not grant SELECT 20 times — you create a role with that permission and grant the role to all 20 service accounts.

The RBAC model has three core components that work together. **Roles** are named collections of permissions that correspond to a job function, a service type, or an access pattern — not to individual users. Examples: `readonly_role`, `orders_writer`, `billing_admin`, `analytics_reader`. **Users** (or service accounts) are the identities that actually authenticate and connect to the database. Each user is assigned one or more roles. **Permissions** are granted to roles, not to users directly. Users inherit permissions through role membership.

This indirection is powerful. When a new microservice needs the same database access as an existing one, you grant it the existing role — one command instead of twenty grants. When a permission needs to change for a category of users, you modify the role — one change affects every user assigned to that role. When an employee leaves or a service is decommissioned, you revoke their role membership or drop their user account — the role and its permissions remain intact for others.

```
RBAC DESIGN — A Multi-Service Application:

ROLES (permission blueprints):

readonly_role:
  GRANT SELECT ON ALL TABLES IN SCHEMA public;

orders_writer_role:
  GRANT INSERT, UPDATE ON TABLE orders;
  GRANT USAGE, UPDATE ON SEQUENCE orders_id_seq;

products_manager_role:
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE products;
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE product_categories;

billing_reader_role:
  GRANT SELECT ON TABLE invoices, payments, subscriptions;

admin_role:
  GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public;

─────────────────────────────────────────────────────────────────

USERS (service accounts):

catalog_service_user:     GRANT readonly_role, products_manager_role
order_service_user:       GRANT readonly_role, orders_writer_role
billing_service_user:     GRANT readonly_role, billing_reader_role
analytics_service_user:   GRANT readonly_role (read-only access)
migration_user:           GRANT admin_role (only during deployments)
reporting_user:           GRANT readonly_role, billing_reader_role

─────────────────────────────────────────────────────────────────

EFFECTIVE PERMISSIONS (what each user can actually do):

                     | SELECT | INSERT | UPDATE | DELETE | billing |
                     | all    | orders | orders |products| data    |
─────────────────────┼────────┼────────┼────────┼────────┼─────────┤
catalog_service_user │  ✓     │        │        │  ✓/✓   │         │
order_service_user   │  ✓     │  ✓     │  ✓     │        │         │
billing_service_user │  ✓     │        │        │        │  ✓      │
analytics_service_   │  ✓     │        │        │        │         │
user                 │        │        │        │        │         │
─────────────────────┴────────┴────────┴────────┴────────┴─────────┘

Each service has EXACTLY what it needs. Nothing more.
```

Implementing RBAC in PostgreSQL involves the following concrete steps. First, you create your group roles — these are roles without the `LOGIN` attribute, pure permission containers. Then you grant object privileges to these group roles, not to individual users. Then you create your user roles (with `LOGIN`) for each application service account. Then you grant the appropriate group roles to each user role. Finally, you configure your connection strings in each service to use the corresponding user role credentials.

One particularly important aspect of RBAC design is the **separation of the schema owner role from the application user role**. A common mistake is using the same database user to run migrations (which need DDL privileges like CREATE TABLE, ALTER TABLE) and to run application queries (which need only DML privileges like SELECT, INSERT, UPDATE). These should always be separate roles. The migration role needs elevated permissions temporarily, during a deployment. The application role needs only the minimum DML permissions at all times. If your application user can DROP TABLE, a SQL injection attack can destroy your entire database. If the migration user is separate and its credentials are only used during deployments, the blast radius of any compromise is dramatically reduced.

## 6. Row-Level Security (RLS) — PostgreSQL

Row-Level Security is one of PostgreSQL's most powerful and underappreciated features. It elevates database authorization from the object level (can this role access this table?) to the row level (can this role access this specific row in this table?). With RLS, the database itself enforces data isolation between different tenants, users, or organisations — not application code.

To understand why RLS is so important, consider a multi-tenant SaaS application. You have a `documents` table that stores documents for many different companies. Without RLS, your application must include `WHERE company_id = $1` in every single query, relying on application code to prevent Company A from reading Company B's documents. If a developer forgets this clause in one query — even a seldom-used internal API endpoint — Company A can read all of Company B's data. One forgotten WHERE clause in thousands of lines of code is a catastrophic data breach waiting to happen.

With RLS, the database enforces this constraint automatically. Even if a query is sent without a `WHERE company_id = $1` clause, the database silently adds the constraint based on the active RLS policy before executing the query. The application cannot bypass it, a developer cannot accidentally forget it, and an attacker who has compromised the application cannot circumvent it — because it operates at a layer below the application.

Enabling RLS on a table is a two-step process. First, you enable RLS on the table with `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`. Once enabled, the table becomes completely invisible to all non-owner roles unless at least one policy is defined — by default, RLS with no policies denies access to everyone (the "default deny" principle). Second, you create one or more policies using `CREATE POLICY`. Each policy defines a `USING` clause (which rows can be read) and optionally a `WITH CHECK` clause (which rows can be inserted or updated).

```sql
-- Step 1: Create the table with tenant isolation:
CREATE TABLE documents (
  id          BIGSERIAL PRIMARY KEY,
  company_id  INTEGER NOT NULL,
  title       TEXT NOT NULL,
  content     TEXT,
  owner_user  TEXT NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Step 2: Enable RLS on the table:
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- Step 3: Create a policy.
-- app_user can only see rows where company_id matches
-- the current session's app.current_company_id setting:
CREATE POLICY tenant_isolation ON documents
  FOR ALL                                       -- Applies to SELECT, INSERT, UPDATE, DELETE
  TO app_user                                   -- Applies to this role
  USING (
    company_id = current_setting('app.current_company_id')::INTEGER
  )
  WITH CHECK (
    company_id = current_setting('app.current_company_id')::INTEGER
  );
-- USING  → filters rows on READ  (SELECT, UPDATE, DELETE)
-- WITH CHECK → filters rows on WRITE (INSERT, UPDATE)
-- Both must pass for a row to be accessible.
```

The `current_setting()` function is the key mechanism for making RLS policies dynamic. It reads a session-level setting that your application sets at the beginning of each database connection or transaction. Your Go application, upon receiving a request from a user at Company 42, would execute:

```sql
-- At the start of every request, set the context:
SET LOCAL app.current_company_id = '42';
-- (SET LOCAL applies for the duration of the current transaction)

-- Now ALL subsequent queries automatically filter to company_id = 42:
SELECT * FROM documents;
-- Silently becomes: SELECT * FROM documents WHERE company_id = 42
-- The application developer does not need to write this WHERE clause!

INSERT INTO documents (company_id, title, content, owner_user)
VALUES (42, 'Q4 Report', 'Content here...', 'alice@company42.com');
-- WITH CHECK ensures company_id = 42. Attempting to insert
-- with company_id = 99 (a different tenant) would be REJECTED:
-- ERROR: new row violates row-level security policy for table "documents"
```

PostgreSQL also allows you to use `current_user` (the connected role name) directly in policies, which is useful for user-specific access patterns. You can create policies based on any expression that evaluates per-row, including subqueries and function calls.

```sql
-- User-specific policy: users can only see their own documents
CREATE POLICY user_owns_document ON documents
  FOR ALL
  TO app_user
  USING (owner_user = current_user);

-- Department-based policy using a subquery:
CREATE POLICY department_access ON documents
  FOR SELECT
  TO employee_role
  USING (
    department_id IN (
      SELECT department_id FROM employees WHERE username = current_user
    )
  );
```

There are several important nuances to RLS that you must understand for production use. **Superusers bypass RLS entirely** — this is by design, allowing database administrators to always access all data. **Table owners also bypass RLS by default**, but this can be changed with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`, which makes even the owner subject to policies. You should use `FORCE ROW LEVEL SECURITY` on multi-tenant tables to prevent accidental privilege escalation.

You can also create **separate policies for different operations** by specifying `FOR SELECT`, `FOR INSERT`, `FOR UPDATE`, or `FOR DELETE` instead of `FOR ALL`. This allows fine-grained control — for instance, allowing users to read all rows in a table but only update rows they own.

```sql
-- Separate policies for different operations:

-- Anyone can read published documents:
CREATE POLICY read_published ON documents
  FOR SELECT
  TO app_user
  USING (status = 'published' OR owner_user = current_user);

-- Users can only insert documents for themselves:
CREATE POLICY insert_own ON documents
  FOR INSERT
  TO app_user
  WITH CHECK (owner_user = current_user);

-- Users can only update their own documents:
CREATE POLICY update_own ON documents
  FOR UPDATE
  TO app_user
  USING (owner_user = current_user)
  WITH CHECK (owner_user = current_user);

-- Users cannot delete (no DELETE policy → DELETE is denied for app_user):
-- (Default deny — no policy for DELETE means DELETE is blocked)
```

RLS has a performance consideration worth understanding. The policy's `USING` clause is essentially appended to every query's `WHERE` clause. If the expression in the `USING` clause is complex or involves subqueries, it can add significant overhead to every query. Ensure that columns used in RLS policies are indexed — particularly `company_id`, `user_id`, `owner_user`, and similar filtering columns. PostgreSQL's query planner is generally good at pushing RLS conditions into index scans, but you should verify this with `EXPLAIN ANALYZE` on queries in tables with RLS enabled.

```
RLS — HOW IT TRANSFORMS QUERIES UNDER THE HOOD:

Application sends:
  SELECT id, title FROM documents;

PostgreSQL rewrites to:
  SELECT id, title FROM documents
  WHERE company_id = current_setting('app.current_company_id')::INTEGER;
  -- RLS USING clause silently appended

Application sends:
  UPDATE documents SET title = 'New Title' WHERE id = 123;

PostgreSQL rewrites to:
  UPDATE documents SET title = 'New Title'
  WHERE id = 123
    AND company_id = current_setting('app.current_company_id')::INTEGER;
  -- Both USING (read check) and WITH CHECK (write check) must pass.
  -- If id=123 belongs to a different company, the UPDATE affects 0 rows
  -- (silently ignored, not an error — unless you check rows affected)

The developer never writes the WHERE clause.
The database always enforces it.
This is the power of RLS.
```

## 7. Column-Level Permissions

Column-level permissions extend the privilege model from the table level down to individual columns. While table-level privileges answer "can this role access this table?", column-level permissions answer "can this role access this specific column in this table?" This is the most granular level of access control that SQL databases support natively.

Column-level permissions are most commonly used for sensitive data fields — salary information, social security numbers, credit card numbers (though you should never store raw card numbers), personal identification information, medical data, or any field that only specific roles should be able to see or modify. Rather than putting this data in a separate table (which is a valid architectural choice), column-level permissions allow you to keep it in the same row as non-sensitive data while hiding it from roles that should not see it.

In PostgreSQL, column-level privileges are granted and revoked with the same `GRANT` and `REVOKE` syntax, but with a column list specified. Only `SELECT` and `UPDATE` make sense at the column level — `INSERT`, `DELETE`, and other privileges remain table-level operations. When a column-level `SELECT` privilege exists for a role, that role can only select the permitted columns from the table; attempting to reference a restricted column in a query produces a permission error.

```sql
-- Scenario: employees table with sensitive salary data

CREATE TABLE employees (
  id          BIGSERIAL PRIMARY KEY,
  name        TEXT NOT NULL,
  department  TEXT NOT NULL,
  job_title   TEXT NOT NULL,
  email       TEXT NOT NULL,
  salary      NUMERIC(10, 2),     -- SENSITIVE
  ssn         TEXT,               -- SENSITIVE
  start_date  DATE NOT NULL
);

-- Grant table-level SELECT to the general app role
-- (but NOT on salary and ssn columns yet):
GRANT SELECT ON TABLE employees TO app_user;

-- Now app_user can query the table but tries to read salary:
-- SELECT name, salary FROM employees;
-- ERROR: permission denied for column "salary"

-- Grant column-level SELECT on non-sensitive columns only:
GRANT SELECT (id, name, department, job_title, email, start_date)
  ON TABLE employees
  TO app_user;
-- app_user can now SELECT only these specific columns.

-- Grant full SELECT (including salary) to HR role only:
GRANT SELECT ON TABLE employees TO hr_role;
-- hr_role can SELECT all columns, including salary and ssn.

-- Grant UPDATE on salary column to compensation team only:
GRANT UPDATE (salary) ON TABLE employees TO compensation_role;
-- Only compensation_role can UPDATE the salary column.
-- app_user cannot UPDATE salary even if they had UPDATE on the table.
```

The interaction between table-level and column-level privileges follows a specific rule in PostgreSQL: a role can access a column if it has either a table-level privilege that covers the column OR a column-level privilege on that specific column. So if `app_user` has table-level `SELECT` on `employees`, they can select all columns — you must explicitly revoke the table-level privilege and use only column-level grants to restrict access. This means column-level restrictions only work cleanly when the role does NOT have a table-level SELECT grant. The typical pattern is to grant column-level SELECT on specific columns instead of table-level SELECT.

There is also an important distinction with `UPDATE`. A role needs table-level `SELECT` to update a row (because the database must read the row to apply the update), but needs either table-level or column-level `UPDATE` privilege on each column being modified. A role can have column-level `UPDATE` on `salary` without having table-level `UPDATE`, and this works correctly.

```
COLUMN-LEVEL PERMISSION MATRIX — Example System:

Table: employees
Columns: id, name, department, job_title, email, salary, ssn, start_date

Role              │ id │name│dept│title│email│salary│ ssn │ start │
──────────────────┼────┼────┼────┼─────┼─────┼──────┼─────┼───────┤
app_user          │ R  │ R  │ R  │  R  │  R  │      │     │   R   │
hr_role           │ R  │ R  │ R  │  R  │  R  │  R   │  R  │   R   │
compensation_role │ R  │ R  │ R  │  R  │  R  │  R/W │     │   R   │
compliance_role   │ R  │ R  │ R  │  R  │  R  │      │  R  │   R   │
admin_role        │R/W │R/W │R/W │ R/W │ R/W │  R/W │ R/W │  R/W  │

R = SELECT, W = UPDATE, blank = no access

SQL to implement this:
-- app_user: column-level SELECT on non-sensitive columns only
REVOKE ALL ON TABLE employees FROM app_user;
GRANT SELECT (id, name, department, job_title, email, start_date)
  ON TABLE employees TO app_user;

-- hr_role: full table-level SELECT (all columns)
GRANT SELECT ON TABLE employees TO hr_role;

-- compensation_role: SELECT all + UPDATE salary only
GRANT SELECT ON TABLE employees TO compensation_role;
GRANT UPDATE (salary) ON TABLE employees TO compensation_role;

-- compliance_role: SELECT all + also sees SSN
GRANT SELECT ON TABLE employees TO compliance_role;
-- (SSN visible because full table SELECT is granted)

-- admin_role: full control
GRANT ALL PRIVILEGES ON TABLE employees TO admin_role;
```

An alternative — and often better — architectural pattern for column-level access is the use of **views**. Instead of column-level grants on the base table, you create views that project only the permitted columns, grant SELECT on the views to the appropriate roles, and deny direct table access. This approach has several advantages: views can be more expressive than column-level grants (they can apply transformations, masks, and joins), they are easier to reason about, and they centralise the definition of what each role can see in one place.

```sql
-- Create a view for app_user that excludes sensitive columns:
CREATE VIEW employees_public AS
  SELECT id, name, department, job_title, email, start_date
  FROM employees;

-- Grant access to the view (not the base table):
GRANT SELECT ON employees_public TO app_user;

-- Create a view for HR that shows salary but masks SSN:
CREATE VIEW employees_hr AS
  SELECT
    id, name, department, job_title, email, start_date, salary,
    CONCAT('***-**-', RIGHT(ssn, 4)) AS ssn_masked  -- partial mask
  FROM employees;

GRANT SELECT ON employees_hr TO hr_role;

-- Revoke direct table access from all application roles:
REVOKE ALL ON TABLE employees FROM app_user, hr_role;
-- Only admin_role and schema_owner can access the base table.
-- All others go through views. ✓
```

## 8. Putting It All Together — A Real-World Design

Let us now synthesise everything we have learned into a complete, production-grade database security design for a multi-tenant SaaS application. This is the kind of setup you would implement as a backend engineer on a team that takes security seriously.

The application is a project management tool. Companies can sign up, and each company has multiple users. The database has tables for `companies`, `users`, `projects`, and `tasks`. The application runs as a single Go backend service connecting to PostgreSQL. There are also background jobs for sending notifications and an analytics service for generating reports.

```sql
-- ─────────────────────────────────────────────────────────────────
-- STEP 1: CREATE GROUP ROLES (no LOGIN — permission templates)
-- ─────────────────────────────────────────────────────────────────

-- Base read access (all non-sensitive tables)
CREATE ROLE base_reader;

-- Write access for core application operations
CREATE ROLE app_writer;

-- Analytics: read-only, includes aggregated data
CREATE ROLE analytics_reader;

-- Background job role: limited write access
CREATE ROLE job_worker;

-- Migration role: DDL privileges (used only during deployments)
CREATE ROLE migrator;


-- ─────────────────────────────────────────────────────────────────
-- STEP 2: CREATE USER ROLES (WITH LOGIN — actual service accounts)
-- ─────────────────────────────────────────────────────────────────

CREATE ROLE app_service WITH LOGIN PASSWORD 'app_strong_pass'
  CONNECTION LIMIT 100;

CREATE ROLE analytics_service WITH LOGIN PASSWORD 'analytics_pass'
  CONNECTION LIMIT 20;

CREATE ROLE job_service WITH LOGIN PASSWORD 'job_strong_pass'
  CONNECTION LIMIT 20;

CREATE ROLE migration_user WITH LOGIN PASSWORD 'mig_pass'
  CONNECTION LIMIT 2;


-- ─────────────────────────────────────────────────────────────────
-- STEP 3: GRANT DATABASE AND SCHEMA ACCESS
-- ─────────────────────────────────────────────────────────────────

GRANT CONNECT ON DATABASE projectapp TO
  app_service, analytics_service, job_service, migration_user;

GRANT USAGE ON SCHEMA public TO
  base_reader, app_writer, analytics_reader, job_worker;

GRANT CREATE ON SCHEMA public TO migrator;


-- ─────────────────────────────────────────────────────────────────
-- STEP 4: GRANT TABLE-LEVEL PRIVILEGES TO GROUP ROLES
-- ─────────────────────────────────────────────────────────────────

-- base_reader: read all tables
GRANT SELECT ON ALL TABLES IN SCHEMA public TO base_reader;
ALTER DEFAULT PRIVILEGES FOR ROLE migration_user IN SCHEMA public
  GRANT SELECT ON TABLES TO base_reader;

-- app_writer: write access to core tables
GRANT INSERT, UPDATE ON TABLE projects, tasks TO app_writer;
GRANT USAGE, UPDATE ON ALL SEQUENCES IN SCHEMA public TO app_writer;

-- job_worker: specific write access for notifications/events
GRANT INSERT ON TABLE notification_log, job_queue TO job_worker;
GRANT UPDATE ON TABLE job_queue TO job_worker;

-- migrator: full DDL control
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO migrator;
GRANT ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA public TO migrator;


-- ─────────────────────────────────────────────────────────────────
-- STEP 5: ASSIGN GROUP ROLES TO USER ROLES
-- ─────────────────────────────────────────────────────────────────

GRANT base_reader, app_writer TO app_service;
GRANT base_reader, analytics_reader TO analytics_service;
GRANT base_reader, job_worker TO job_service;
GRANT migrator TO migration_user;


-- ─────────────────────────────────────────────────────────────────
-- STEP 6: ENABLE ROW-LEVEL SECURITY (multi-tenancy isolation)
-- ─────────────────────────────────────────────────────────────────

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;
ALTER TABLE projects FORCE ROW LEVEL SECURITY;
ALTER TABLE tasks FORCE ROW LEVEL SECURITY;

-- Policy: app_service can only see rows for the current company
CREATE POLICY company_isolation ON projects
  FOR ALL TO app_service
  USING (company_id = current_setting('app.company_id')::INTEGER)
  WITH CHECK (company_id = current_setting('app.company_id')::INTEGER);

CREATE POLICY company_isolation ON tasks
  FOR ALL TO app_service
  USING (
    project_id IN (
      SELECT id FROM projects
      WHERE company_id = current_setting('app.company_id')::INTEGER
    )
  );


-- ─────────────────────────────────────────────────────────────────
-- STEP 7: COLUMN-LEVEL RESTRICTIONS (sensitive fields)
-- ─────────────────────────────────────────────────────────────────

-- Restrict billing_details column on companies table:
-- analytics_service should never see billing data
REVOKE SELECT ON TABLE companies FROM base_reader;
GRANT SELECT (id, name, plan, created_at, is_active)
  ON TABLE companies TO base_reader;

-- app_service needs billing_details but only for its own company
-- → handled by RLS policy on companies table + full column access
GRANT SELECT ON TABLE companies TO app_service;


-- ─────────────────────────────────────────────────────────────────
-- STEP 8: Go application code sets session context per request
-- ─────────────────────────────────────────────────────────────────
-- In your Go handler, for every request:
--   BEGIN;
--   SET LOCAL app.company_id = '42';
--   SET LOCAL app.user_id = '1001';
--   -- ... run all queries (automatically filtered by RLS) ...
--   COMMIT;
```

This design achieves the following security guarantees. The `app_service` account, which every API request uses, can only read and write rows for the currently authenticated company — enforced by the database, not just application code. The `analytics_service` account has read-only access and cannot see billing data. The `job_service` account can only write to specific logging and queue tables and cannot read sensitive company data. Migrations are performed by `migration_user`, which has DDL privileges, but this account is never used for application queries. An attacker who compromises the application server and gains access to the `app_service` credentials can only see data for whichever company's context they can manipulate — not the entire database.

PRINCIPLE OF LEAST PRIVILEGE — THE GOVERNING RULE:

  Every role gets exactly the permissions it needs to do its job.
  Nothing more.

  Application service user:   SELECT, INSERT, UPDATE on specific tables.
  Background job user:        INSERT on queue/log tables only.
  Analytics user:             SELECT only, no sensitive columns.
  Migration user:             ALL PRIVILEGES, used only during deploys.
  Superuser (postgres):       Never used by applications. Ever.

SECURITY LAYER MAP — Defense in Depth:

  Layer 1: Network    → pg_hba.conf restricts which IPs can connect
  Layer 2: Auth       → Password/cert validates identity on connect
  Layer 3: Roles      → Role attributes limit capabilities (no SUPERUSER)
  Layer 4: Schema     → USAGE controls schema access
  Layer 5: Table      → GRANT controls table-level operations
  Layer 6: Column     → GRANT (col) or views restrict column visibility
  Layer 7: Row (RLS)  → Policies filter rows on every query
  Layer 8: App Code   → Final sanity checks in your Go service

An attacker who bypasses Layers 8 must still face Layers 1-7.
An attacker who bypasses Layer 8 with SQL injection finds
  Layer 7 (RLS) still limiting them to one tenant's data.
This is defense in depth done right.

_Security is not something you add to a database after it is built — it is something you design from the first line of schema creation. The pattern is always the same: authenticate identities carefully, grant the minimum necessary privileges, organise those privileges into roles that reflect your organisation's actual access patterns, enforce data boundaries at the row level with RLS for multi-tenant systems, and hide sensitive columns behind column-level grants or views. Every additional layer of database-level security is a layer that works even when your application code has bugs, your developers make mistakes, or an attacker has already compromised your application tier._

_The difference between a company that survives a breach and one that does not is often not in how they prevented initial access — breaches happen — but in how little damage could be done once inside. Database-level authorization, designed with least privilege and layered defenses, is how you limit that damage._
