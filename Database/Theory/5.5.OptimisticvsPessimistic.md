# Optimistic vs Pessimistic Concurrency Control — A Deep Study Guide

> *"The choice between optimistic and pessimistic concurrency control is, at its heart, a bet about human behavior — or more precisely, about how often your users will collide with each other. The pessimist assumes conflict is likely and guards against it in advance, paying the cost of coordination upfront. The optimist assumes conflict is rare and proceeds without protection, paying a recovery cost only when the unlikely collision actually occurs. Getting this bet right — calibrating it to your actual workload — is one of the most consequential decisions in concurrent system design."*

Every concurrent system must answer the same fundamental question: when two operations want to interact with the same piece of data at the same time, how should the system handle it? The previous chapters examined locking and MVCC — mechanisms that the database manages internally. This chapter examines the strategies that application developers implement to coordinate concurrent access at the application level. These strategies are called **concurrency control protocols**, and the two fundamental philosophies are **Optimistic Concurrency Control (OCC)** and **Pessimistic Concurrency Control (PCC)**. Understanding both, and knowing which to reach for in which situation, is the mark of a mature database engineer.

## 1. Optimistic Concurrency Control — Version Columns and Compare-and-Swap

### The Optimist's Assumption

Optimistic Concurrency Control is built on a single, powerful assumption: **conflicts between concurrent transactions are rare**. In many real-world systems, the probability that two users will try to modify the exact same record at the exact same moment is very low. A product catalog might have millions of rows; two users updating the exact same product simultaneously is an uncommon event. An e-commerce site might have millions of users; two users buying the last item of the same product simultaneously is possible but infrequent.

Given this assumption, OCC reasons that it is wasteful to acquire locks at the beginning of every operation, making all operations pay the cost of coordination regardless of whether a conflict actually occurs. Instead, OCC allows transactions to proceed **without any locks**, reading and preparing their changes optimistically. Only at the very end — at commit time — does the system verify that the data the transaction read has not been changed by anyone else during its execution. If verification passes, the transaction commits successfully. If verification fails (someone else modified the data first), the transaction is rolled back and retried. The cost of conflict resolution is paid only when conflict actually occurs, which — under the optimistic assumption — is rare.

### The Version Column Mechanism

The most common and practical implementation of OCC in relational databases is the **version column** (also called a row version, optimistic lock column, or `version_number` field). Every row in the table contains an additional column — typically an integer counter or a timestamp — that is incremented (or updated) on every modification. This version column is the "fingerprint" of the row's current state. If you read a row and see version 7, and then try to update it, you include `WHERE version = 7` in your UPDATE statement. If the row has been modified by someone else in the meantime (version is now 8), your WHERE clause matches nothing — zero rows updated — and you know a conflict occurred.

```
  VERSION COLUMN MECHANISM — Step by Step

  Table: products
  ┌────┬─────────────────┬─────────┬────────────┬─────────┐
  │ id │ name            │ stock   │ price      │ version │
  ├────┼─────────────────┼─────────┼────────────┼─────────┤
  │  1 │ Wireless Mouse  │    50   │   29.99    │    7    │
  └────┴─────────────────┴─────────┴────────────┴─────────┘

  ─────────────────────────────────────────────────────────────────
  SCENARIO 1: No conflict (happy path)
  ─────────────────────────────────────────────────────────────────

  Time  User A                              User B (not modifying)
  ──────────────────────────────────────────────────────────────────
  T1    SELECT id, stock, price, version
        FROM products WHERE id=1;
        → Reads: stock=50, version=7
  T2    (User A reviews, decides to reduce stock by 5)
  T3    UPDATE products
        SET stock = 45, version = version + 1
        WHERE id = 1 AND version = 7;   ← THE KEY CHECK
        → Rows affected: 1 ✓ (version was still 7)
        → Product now: stock=45, version=8
  T4    COMMIT — SUCCESS ✓

  ─────────────────────────────────────────────────────────────────
  SCENARIO 2: Conflict detected (two users modify simultaneously)
  ─────────────────────────────────────────────────────────────────

  Time  User A                              User B
  ──────────────────────────────────────────────────────────────────
  T1    SELECT ..., version FROM products   SELECT ..., version
        WHERE id=1;                         FROM products WHERE id=1;
        → Reads: stock=50, version=7        → Reads: stock=50, version=7
  T2    (Both users are reading and processing, neither has written yet)
  T3    UPDATE products                     (still processing)
        SET stock=45, version=version+1
        WHERE id=1 AND version=7;
        → Rows affected: 1 ✓
        → DB now: stock=45, version=8
  T4    COMMIT ✓                            UPDATE products
                                            SET stock=48, version=version+1
                                            WHERE id=1 AND version=7;
                                            → Rows affected: 0 ✗
                                              version is now 8, not 7!
  T5                                        DETECT CONFLICT:
                                            rows_affected == 0 means
                                            someone else modified this row.
                                            → ROLLBACK (or retry from T1)
  T6                                        Re-read row (stock=45, version=8)
                                            Recalculate, retry UPDATE with version=8
```

### Compare-and-Swap: The Atomic Foundation

The version column technique is an application-level implementation of a fundamental computer science concept called **Compare-and-Swap (CAS)** — a hardware-level atomic instruction that reads a value, compares it to an expected value, and writes a new value only if the comparison succeeded. The database's `UPDATE ... WHERE version = N` is exactly CAS applied to database rows:

- **Compare**: `WHERE version = 7` — is the current value what I expected?
- **Swap**: `SET stock = 45, version = 8` — if so, atomically replace with new value
- **Check**: `rows_affected = 0` means compare failed (value changed) → retry

This pattern is safe even without any database-level locks because the database guarantees that each individual SQL statement is atomic. Two concurrent `UPDATE ... WHERE version = 7` statements cannot both succeed — one will update the row (changing version to 8) and the other will find that the row no longer matches its WHERE clause.

```
  COMPARE-AND-SWAP: WHY IT IS ATOMIC

  Two concurrent UPDATE attempts racing:

  Transaction A:  UPDATE products SET stock=45, version=8 WHERE id=1 AND version=7;
  Transaction B:  UPDATE products SET stock=48, version=8 WHERE id=1 AND version=7;

  Even without explicit locks, the database serializes these writes:
  ┌─────────────────────────────────────────────────────────────────────┐
  │ Database's internal serialization:                                   │
  │                                                                     │
  │ Step 1: Txn A's UPDATE acquires implicit X-lock on row (id=1)       │
  │ Step 2: Txn A checks version=7 → matches → writes stock=45,v=8     │
  │ Step 3: Txn A releases X-lock on commit                             │
  │                                                                     │
  │ Step 4: Txn B's UPDATE now acquires X-lock on row (id=1)            │
  │ Step 5: Txn B checks version=7 → MISMATCH (version is now 8)       │
  │ Step 6: Txn B's WHERE matches 0 rows → update affects nothing      │
  │                                                                     │
  │ ONE transaction wins. The other detects the miss. No corruption.    │
  │ No explicit SELECT FOR UPDATE needed.                                │
  └─────────────────────────────────────────────────────────────────────┘

  The CRITICAL GUARANTEE: The check (WHERE version=7) and the write
  (SET version=8) happen atomically within a single SQL statement.
  There is no window between "check" and "write" where another
  transaction could sneak in.
```

### Full Implementation: Version Columns in Practice

```sql
-- ─────────────────────────────────────────────────────────────────
-- Schema design with version column
-- ─────────────────────────────────────────────────────────────────

CREATE TABLE products (
    id          BIGSERIAL    PRIMARY KEY,
    name        VARCHAR(200) NOT NULL,
    stock       INTEGER      NOT NULL DEFAULT 0,
    price       NUMERIC(10,2) NOT NULL,
    version     INTEGER      NOT NULL DEFAULT 1,  -- OCC version counter
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- Alternative: use updated_at timestamp as the version
-- (works but integer version is more reliable — clock skew on updated_at)

-- ─────────────────────────────────────────────────────────────────
-- Application pattern (pseudo-code + SQL)
-- ─────────────────────────────────────────────────────────────────

-- STEP 1: Read the row (no lock needed!)
SELECT id, name, stock, price, version
FROM products
WHERE id = $product_id;
-- Application stores: current_version = 7

-- STEP 2: Process (outside the database, in application memory)
-- User sees stock=50, decides to reduce by 5 → new_stock = 45

-- STEP 3: Attempt optimistic update
UPDATE products
SET
    stock      = $new_stock,      -- 45
    version    = version + 1,     -- 8
    updated_at = NOW()
WHERE id      = $product_id       -- 1
  AND version = $current_version; -- 7  ← THE OPTIMISTIC LOCK CHECK

-- STEP 4: Check result
-- IF rows_affected == 1: SUCCESS → commit
-- IF rows_affected == 0: CONFLICT → retry from STEP 1

-- ─────────────────────────────────────────────────────────────────
-- Full PostgreSQL function with retry loop
-- ─────────────────────────────────────────────────────────────────

CREATE OR REPLACE FUNCTION reduce_stock(
    p_product_id BIGINT,
    p_reduce_by  INTEGER,
    p_max_retries INTEGER DEFAULT 3
) RETURNS BOOLEAN AS $$
DECLARE
    v_current_stock  INTEGER;
    v_current_version INTEGER;
    v_rows_updated   INTEGER;
    v_attempt        INTEGER := 0;
BEGIN
    LOOP
        v_attempt := v_attempt + 1;
        IF v_attempt > p_max_retries THEN
            RETURN FALSE;  -- Give up after max retries
        END IF;

        -- Read current state (no lock)
        SELECT stock, version
        INTO v_current_stock, v_current_version
        FROM products
        WHERE id = p_product_id;

        IF v_current_stock < p_reduce_by THEN
            RAISE EXCEPTION 'Insufficient stock';
        END IF;

        -- Attempt optimistic update
        UPDATE products
        SET stock   = v_current_stock - p_reduce_by,
            version = version + 1,
            updated_at = NOW()
        WHERE id      = p_product_id
          AND version = v_current_version;  -- OCC check

        GET DIAGNOSTICS v_rows_updated = ROW_COUNT;

        IF v_rows_updated = 1 THEN
            RETURN TRUE;  -- SUCCESS
        END IF;

        -- CONFLICT: rows_updated = 0, retry after brief pause
        PERFORM pg_sleep(0.01 * v_attempt);  -- Exponential backoff
    END LOOP;
END;
$$ LANGUAGE plpgsql;
```

### Timestamp-Based Optimistic Locking

An alternative to the integer version counter is using a **timestamp** column (`updated_at`) as the version token. Instead of comparing `version = 7`, the application reads the timestamp and then checks `WHERE updated_at = '2024-03-15 10:30:00.123456'`. This works but has a subtle pitfall: if two writes happen within the same clock tick (millisecond or microsecond resolution), both might read the same timestamp and both might pass the WHERE check, resulting in a lost update. For this reason, an **integer monotonic version counter** is generally more reliable than a timestamp-based version token.

### When OCC Excels and When It Struggles

Optimistic Concurrency Control is most effective when:
- **Conflicts are genuinely rare** — most reads do not result in conflicting writes
- **Operations are short** — the time between reading and writing is brief, reducing the window for conflicts
- **The cost of retry is low** — re-reading and reprocessing is cheap
- **Read-heavy workloads** — OCC avoids any locking on reads, which are the dominant operation

OCC performs poorly when:
- **Conflicts are frequent** — high contention on specific rows leads to many failed retries and wasted work (a "retry storm" under heavy concurrent load)
- **Processing is expensive** — if reprocessing after a conflict retry requires significant computation or user interaction, retrying is painful
- **Operations are long** — a long-running transaction increases the window during which another writer might arrive

```
  OCC PERFORMANCE UNDER DIFFERENT CONTENTION LEVELS

  Low contention (rare conflicts):
  Success rate: ~99%   Retry rate: ~1%
  Throughput:   ★★★★★  No lock overhead on reads → maximum concurrency
  Latency:      ★★★★★  Rare retries have negligible impact

  Medium contention:
  Success rate: ~80%   Retry rate: ~20%
  Throughput:   ★★★★☆  20% wasted work but still good
  Latency:      ★★★★☆  Occasional retries add latency spikes

  High contention (frequent conflicts on same rows):
  Success rate: ~40%   Retry rate: ~60%
  Throughput:   ★★☆☆☆  Most work is wasted → worse than pessimistic!
  Latency:      ★★☆☆☆  Retry storms, exponential backoff, timeouts

  RULE: If you expect >10-20% conflict rate on a particular operation,
  switch to pessimistic locking (SELECT FOR UPDATE) for that operation.
```

## 2. Pessimistic Concurrency Control — SELECT FOR UPDATE and SELECT FOR SHARE

### The Pessimist's Assumption

Where the optimist proceeds without protection and checks for conflict at the end, the **pessimist acquires protection upfront** — before reading the data, a lock is acquired that prevents any conflicting access for the duration of the transaction. The pessimist does not gamble on the rarity of conflict; instead, it guarantees that no conflict can occur, at the cost of reduced concurrency (others must wait while the lock is held).

Pessimistic Concurrency Control is the right choice when conflicts are frequent, when the cost of detecting and retrying conflicts is high, or when the operation's correctness requires that the data not change between the time it is read and the time it is written. It is the "conservative but correct" approach, trading some concurrency for absolute protection against lost updates and race conditions.

### SELECT FOR UPDATE: The Exclusive Read-Lock

`SELECT FOR UPDATE` is the primary pessimistic locking statement in SQL. It reads rows and simultaneously acquires an **exclusive row-level lock** on each row returned by the query. This lock prevents any other transaction from modifying, deleting, or acquiring its own `FOR UPDATE` lock on the same rows until the locking transaction either commits or rolls back. It is semantically equivalent to "read this row, and also stake my claim that I am about to modify it — hold it for me."

The crucial behavioral difference from optimistic locking is the timeline: with OCC, a conflict is detected at commit time (after all the work is done). With `SELECT FOR UPDATE`, the conflict is detected at read time — the second transaction simply waits at the `SELECT FOR UPDATE` statement until the first transaction finishes. There is no retry, no lost update, no racing condition. The price is the wait.

```
  SELECT FOR UPDATE: Pessimistic Lock Timeline

  Time  Transaction A                       Transaction B
  ──────────────────────────────────────────────────────────────────
  T1    BEGIN;
        SELECT stock, price, version
        FROM products
        WHERE id = 1
        FOR UPDATE;                         BEGIN;
        → Acquires X lock on row (id=1)
        → Returns: stock=50, version=7
  T2    (processing in application memory)  SELECT stock, price, version
                                            FROM products
                                            WHERE id = 1
                                            FOR UPDATE;
                                            → Wants X lock on row (id=1)
                                            → A holds X lock
                                            → B WAITS HERE ↙
  T3    UPDATE products                     (B is suspended, waiting)
        SET stock = 45, version = 8
        WHERE id = 1;
        COMMIT;
        → X lock released
  T4                                        → B acquires X lock NOW
                                            → Returns: stock=45, version=8
                                            (sees A's committed changes!)
  T5                                        (B processes with updated stock=45)
  T6                                        UPDATE products
                                            SET stock = 43, version = 9
                                            WHERE id = 1;
                                            COMMIT;
  ──────────────────────────────────────────────────────────────────
  RESULT: No lost updates. B saw A's change and worked with it.
  B's update (43) correctly reflects both A's reduction (−5) and B's (−2).
  If OCC had been used without FOR UPDATE, B might have overwritten A's change.

  LOST UPDATE WITHOUT LOCKING (for contrast):
  ─────────────────────────────────────────────
  T1: A reads stock=50         B reads stock=50
  T2: A computes: 50-5=45      B computes: 50-2=48
  T3: A writes stock=45        B writes stock=48
  T4: FINAL: stock=48          ← A's reduction of 5 is LOST!
      (Should be 50-5-2=43, but B overwrote A's write with 48)
```

### SELECT FOR UPDATE in Practice

```sql
-- ─────────────────────────────────────────────────────────────────
-- Basic SELECT FOR UPDATE: Lock one row, update it, commit
-- ─────────────────────────────────────────────────────────────────
BEGIN;

SELECT id, stock, price
FROM products
WHERE id = 1
FOR UPDATE;          -- Exclusive lock acquired immediately
                     -- Other FOR UPDATE on same row → WAIT
                     -- Other plain SELECT → reads old MVCC version (no wait!)
                     -- Other UPDATE → WAIT

-- Application processes...

UPDATE products
SET stock = stock - 5
WHERE id = 1;

COMMIT;              -- Lock released

-- ─────────────────────────────────────────────────────────────────
-- Locking multiple rows (consistent ordering to prevent deadlock!)
-- ─────────────────────────────────────────────────────────────────
BEGIN;

-- Transfer between two accounts: lock BOTH rows upfront
-- ORDER BY id ensures consistent lock order → prevents deadlock
SELECT id, balance
FROM accounts
WHERE id IN (1, 2)
ORDER BY id          -- CRITICAL: Always same order to avoid deadlock
FOR UPDATE;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;

-- ─────────────────────────────────────────────────────────────────
-- OF clause: Lock only specific tables in a JOIN
-- ─────────────────────────────────────────────────────────────────
BEGIN;

SELECT o.id, o.total, c.credit_limit
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.id = 42
FOR UPDATE OF o;     -- Lock only the orders row, NOT the customers row
                     -- Reduces contention on the customers table

UPDATE orders SET status = 'processing' WHERE id = 42;
COMMIT;
```

### SELECT FOR SHARE: Shared Read Lock

`SELECT FOR SHARE` (also called `SELECT LOCK IN SHARE MODE` in MySQL) acquires a **shared row-level lock** on the selected rows. It is weaker than `FOR UPDATE`: it prevents other transactions from *modifying* the locked rows, but it allows other transactions to also acquire a `FOR SHARE` lock on the same rows. In other words, multiple readers can coexist with `FOR SHARE`, but no writer can proceed while any `FOR SHARE` lock is held.

`FOR SHARE` is used when you need to read a row and guarantee that it will not be modified before you use its value — but you yourself do not plan to modify it. A common use case is reading a parent row to verify a constraint before inserting a child row. You want to ensure the parent is not deleted between your check and your insert, but you do not need to update the parent.

```sql
-- SELECT FOR SHARE: Prevent modification, allow concurrent sharing

-- Use case: Insert an order_item while verifying the order is still 'active'
BEGIN;

SELECT id, status
FROM orders
WHERE id = 42
FOR SHARE;           -- Lock: others can also FOR SHARE, but no one can
                     -- UPDATE or DELETE this order while we hold the lock

-- Verify status is 'active' (if not, rollback)
-- Insert the order item (parent row is guaranteed to not be deleted)
INSERT INTO order_items (order_id, product_id, quantity)
VALUES (42, 7, 3);

COMMIT;

-- ─────────────────────────────────────────────────────────────────
-- Comparison: FOR UPDATE vs FOR SHARE
-- ─────────────────────────────────────────────────────────────────

-- Lock compatibility with concurrent transactions:
-- (+ = compatible/allowed, X = blocked/must wait)

--                   Concurrent   Concurrent   Concurrent
--                   Plain SELECT FOR SHARE   FOR UPDATE
-- Holder: FOR SHARE     +             +           X
-- Holder: FOR UPDATE    +             X           X

-- Plain SELECT (no FOR clause) is ALWAYS allowed (MVCC snapshot read)
-- FOR SHARE blocks FOR UPDATE but not other FOR SHARE holders
-- FOR UPDATE blocks everything (other FOR UPDATE, FOR SHARE)
```

## 3. SKIP LOCKED — The Job Queue Pattern

### The Problem with Naive Queue Processing

Consider a very common application pattern: a background job queue table in the database, where workers pull rows with `status = 'pending'`, process them, and mark them as `status = 'done'`. A naive implementation might look like `SELECT * FROM jobs WHERE status = 'pending' LIMIT 1 FOR UPDATE`, and then the worker updates the fetched row's status to 'processing'. This approach has a severe problem under concurrent workers.

When Worker 1 fetches a job with `FOR UPDATE`, it acquires an exclusive lock on that job's row. When Worker 2 simultaneously tries to fetch a pending job, it also selects the same row (it is still the first pending row in order) — and then blocks, waiting for Worker 1's lock to be released. Worker 2 is effectively idle, waiting for Worker 1 to finish processing a job that Worker 2 has no business touching. If there are 10 workers, 9 of them might be stacked up waiting for Worker 1, even though there are 1,000 pending jobs in the queue. This is a queue bottleneck caused by lock contention on the same rows.

### SKIP LOCKED: The Elegant Solution

`SKIP LOCKED` is a modifier to `SELECT FOR UPDATE` and `SELECT FOR SHARE` that changes the lock-failure behavior: instead of waiting when it encounters a locked row, the query simply **skips** that row and continues to the next unlocked one. A worker using `SKIP LOCKED` will never wait for another worker — it just moves past any rows that are already being processed and picks the next available one.

This transforms the queue processing problem from a single-file queue (all workers waiting for the same row) into a truly parallel system where each worker independently finds and processes a different job simultaneously.

```
  SKIP LOCKED: Before and After

  NAIVE APPROACH (without SKIP LOCKED):

  jobs table (100 pending jobs):
  ┌─────┬────────────┬──────────────────┐
  │ id  │ status     │ payload          │
  ├─────┼────────────┼──────────────────┤
  │   1 │ pending    │ "send email..."  │  ← Row 1: lowest id = picked FIRST
  │   2 │ pending    │ "gen report..."  │  ← Row 2: same position for all workers
  │   3 │ pending    │ "resize image.." │
  │ ... │ ...        │ ...              │
  └─────┴────────────┴──────────────────┘

  Worker 1: SELECT ... WHERE status='pending' LIMIT 1 FOR UPDATE → locks Row 1
  Worker 2: SELECT ... WHERE status='pending' LIMIT 1 FOR UPDATE → wants Row 1 → WAITS
  Worker 3: SELECT ... WHERE status='pending' LIMIT 1 FOR UPDATE → wants Row 1 → WAITS
  Worker 4: SELECT ... WHERE status='pending' LIMIT 1 FOR UPDATE → wants Row 1 → WAITS

  9 workers idle, waiting for Worker 1 to finish job 1. Rows 2-100 untouched!

  ─────────────────────────────────────────────────────────────────
  WITH SKIP LOCKED:

  Worker 1: SELECT ... WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED
            → locks Row 1, returns Row 1

  Worker 2: SELECT ... WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED
            → Sees Row 1 locked → SKIP IT
            → Locks Row 2, returns Row 2

  Worker 3: → Skips Row 1 (locked by W1) and Row 2 (locked by W2)
            → Locks Row 3, returns Row 3

  Worker 4: → Skips Rows 1,2,3 → locks Row 4 → processes Row 4

  ALL 4 workers processing DIFFERENT jobs SIMULTANEOUSLY.
  Zero waiting. Maximum parallelism. ✓
```

### Full Job Queue Implementation

```sql
-- ─────────────────────────────────────────────────────────────────
-- Job queue schema
-- ─────────────────────────────────────────────────────────────────
CREATE TABLE jobs (
    id           BIGSERIAL    PRIMARY KEY,
    status       VARCHAR(20)  NOT NULL DEFAULT 'pending',
                              -- 'pending', 'processing', 'done', 'failed'
    job_type     VARCHAR(100) NOT NULL,
    payload      JSONB        NOT NULL,
    priority     INTEGER      NOT NULL DEFAULT 5,  -- 1=highest, 10=lowest
    attempts     INTEGER      NOT NULL DEFAULT 0,
    max_attempts INTEGER      NOT NULL DEFAULT 3,
    scheduled_at TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    processed_at TIMESTAMPTZ,
    error_msg    TEXT
);

-- Index for efficient queue polling:
CREATE INDEX idx_jobs_queue
ON jobs (priority ASC, scheduled_at ASC)
WHERE status = 'pending';  -- Partial index: only pending jobs indexed!

-- ─────────────────────────────────────────────────────────────────
-- Worker polling query (the critical pattern)
-- ─────────────────────────────────────────────────────────────────
BEGIN;

-- Atomically: find the next available job AND claim it
-- SKIP LOCKED: skip any job already claimed by another worker
WITH claimed_job AS (
    SELECT id
    FROM jobs
    WHERE status = 'pending'
      AND scheduled_at <= NOW()         -- Only jobs due now or overdue
      AND attempts < max_attempts       -- Haven't exceeded retry limit
    ORDER BY priority ASC, scheduled_at ASC  -- Process high-priority first
    LIMIT 1
    FOR UPDATE SKIP LOCKED              -- THE KEY: skip locked rows
)
UPDATE jobs
SET status = 'processing',
    attempts = attempts + 1
WHERE id = (SELECT id FROM claimed_job)
RETURNING id, job_type, payload, attempts;

-- IF returned row exists: a job was claimed → process it
-- IF no row returned: queue is empty (all pending jobs are being processed)
-- In either case: no waiting, no blocking

COMMIT;

-- ─────────────────────────────────────────────────────────────────
-- After processing: mark as done or failed
-- ─────────────────────────────────────────────────────────────────

-- On success:
UPDATE jobs
SET status = 'done',
    processed_at = NOW()
WHERE id = $job_id;

-- On failure (with retry):
UPDATE jobs
SET status = CASE
               WHEN attempts >= max_attempts THEN 'failed'
               ELSE 'pending'              -- Re-queue for retry
             END,
    error_msg = $error_message,
    scheduled_at = NOW() + INTERVAL '1 minute' * attempts  -- Backoff
WHERE id = $job_id;

-- ─────────────────────────────────────────────────────────────────
-- Batch claiming: one worker claims N jobs at once
-- ─────────────────────────────────────────────────────────────────
WITH claimed_jobs AS (
    SELECT id
    FROM jobs
    WHERE status = 'pending'
    ORDER BY priority ASC, scheduled_at ASC
    LIMIT 10                              -- Claim up to 10 jobs at once
    FOR UPDATE SKIP LOCKED
)
UPDATE jobs
SET status = 'processing', attempts = attempts + 1
WHERE id IN (SELECT id FROM claimed_jobs)
RETURNING id, job_type, payload;

-- Monitor queue health:
SELECT
    status,
    job_type,
    COUNT(*)                         AS count,
    MIN(scheduled_at)                AS oldest,
    AVG(EXTRACT(EPOCH FROM NOW() - scheduled_at)) AS avg_age_seconds
FROM jobs
GROUP BY status, job_type
ORDER BY status, job_type;
```

### Why SKIP LOCKED Is Better Than Application-Level Solutions

Before `SKIP LOCKED` existed, developers used application-level workarounds for concurrent queue processing: random row selection (non-deterministic and inefficient), status-to-'processing' update before the SELECT (race conditions), or separate locking tables (complex and fragile). `SKIP LOCKED` is superior to all of these because it is **atomic at the database level** — the lock acquisition and the skip behavior happen in a single atomic operation. There is no window between "check if locked" and "acquire lock" where another worker could sneak in. The result is a perfectly correct, highly efficient concurrent queue implementation with zero application-level complexity.

## 4. NOWAIT — Non-Blocking Lock Acquisition

### Failing Fast Instead of Waiting

`NOWAIT` is the sibling of `SKIP LOCKED` for situations where you want to attempt to acquire a lock but not wait if it is unavailable. While `SKIP LOCKED` skips the locked row and moves to the next one, `NOWAIT` immediately raises an **error** if any requested lock cannot be acquired instantly. The entire `SELECT FOR UPDATE NOWAIT` statement fails immediately rather than blocking.

The behavioral difference is important: `SKIP LOCKED` works on individual rows — it can skip some locked rows and return others. `NOWAIT` works on the entire statement — if *any* row in the result set is locked, the entire statement fails immediately with no partial result returned. This makes `NOWAIT` appropriate when you want to lock a specific, known row and need an immediate answer about whether it is available, rather than scanning for any available row.

```
  SKIP LOCKED vs NOWAIT: Behavioral Comparison

  jobs table: 5 pending rows. Row 1 is locked by Worker A.

  SELECT * FROM jobs WHERE status='pending' LIMIT 3 FOR UPDATE SKIP LOCKED:
  → Row 1: LOCKED → SKIP (move to next)
  → Row 2: available → lock and include in result
  → Row 3: available → lock and include in result
  → Row 4: available → lock and include in result
  → Returns: [Row 2, Row 3, Row 4]
  → Behavior: returns whatever unlocked rows are available

  SELECT * FROM jobs WHERE status='pending' LIMIT 3 FOR UPDATE NOWAIT:
  → Row 1: LOCKED → FAIL IMMEDIATELY
  → Returns: ERROR: could not obtain lock on row in relation "jobs"
  → Behavior: either lock ALL requested rows instantly, or fail entirely

  ─────────────────────────────────────────────────────────────────
  When to use each:

  SKIP LOCKED: "Give me any available work to do"
  → Job queue workers
  → Any scenario where alternatives exist and you want the best available

  NOWAIT: "Give me THIS specific item or tell me it's unavailable"
  → Trying to lock a specific resource (e.g., a specific user's record)
  → Non-blocking UI operations ("This record is being edited by someone else")
  → Time-sensitive operations where waiting is unacceptable
```

### NOWAIT in Practice: The "Already Being Edited" Pattern

The canonical use case for `NOWAIT` is in **collaborative editing** scenarios — a web application where one user begins editing a record (an invoice, a customer profile, a document) and you want to prevent another user from simultaneously editing the same record. Rather than using OCC (which would detect the conflict at save time, after both users have done their editing work), `NOWAIT` detects the conflict immediately when the second user tries to open the record for editing.

```sql
-- ─────────────────────────────────────────────────────────────────
-- NOWAIT: Detect "already being edited" without waiting
-- ─────────────────────────────────────────────────────────────────

-- User A opens invoice #500 for editing:
BEGIN;

SELECT id, invoice_number, amount, status
FROM invoices
WHERE id = 500
FOR UPDATE NOWAIT;   -- If locked: fail immediately (do not wait)

-- If successful: User A has the lock. No one else can edit.
-- Keep this transaction open while user A is editing.
-- (Use idle_in_transaction_session_timeout to protect against
--  users who open the form and walk away!)

-- User A saves:
UPDATE invoices SET amount = 1200.00, status = 'revised' WHERE id = 500;
COMMIT;  -- Lock released, other users can now edit.

-- ─────────────────────────────────────────────────────────────────
-- Handling the NOWAIT error in application code
-- ─────────────────────────────────────────────────────────────────

-- In PostgreSQL, NOWAIT failure raises:
-- SQLSTATE 55P03 (lock_not_available)
-- The application catches this specific error and responds appropriately.

-- Application pseudocode:
-- try:
--     BEGIN;
--     SELECT ... FOR UPDATE NOWAIT;
--     -- proceed with edit session
-- catch (SQLSTATE == '55P03'):  -- lock_not_available
--     ROLLBACK;
--     show_user("This record is currently being edited by another user. Try again shortly.")

-- ─────────────────────────────────────────────────────────────────
-- NOWAIT with DDL: Non-blocking schema changes
-- ─────────────────────────────────────────────────────────────────

-- Attempt a schema change without blocking if the table is busy:
SET lock_timeout = '3s';    -- Alternative to NOWAIT for DDL
ALTER TABLE orders ADD COLUMN notes TEXT;
-- If lock cannot be acquired within 3 seconds → error
-- More useful for DDL than explicit NOWAIT (which isn't available for DDL)

-- ─────────────────────────────────────────────────────────────────
-- NOWAIT in a complete "try-lock" function
-- ─────────────────────────────────────────────────────────────────
CREATE OR REPLACE FUNCTION try_lock_invoice(p_invoice_id BIGINT)
RETURNS JSONB AS $$
DECLARE
    v_invoice invoices%ROWTYPE;
BEGIN
    SELECT *
    INTO v_invoice
    FROM invoices
    WHERE id = p_invoice_id
    FOR UPDATE NOWAIT;

    -- Success: return the invoice data
    RETURN jsonb_build_object(
        'success', true,
        'invoice', row_to_json(v_invoice)
    );

EXCEPTION
    WHEN lock_not_available THEN  -- SQLSTATE 55P03
        RETURN jsonb_build_object(
            'success', false,
            'error', 'Invoice is currently being edited by another user'
        );
END;
$$ LANGUAGE plpgsql;
```

### Combining NOWAIT with Application-Level Logic

`NOWAIT` is most powerful when combined with application-level lock management that provides user feedback. Rather than just failing silently, a well-designed system using `NOWAIT` can:

1. Attempt the `FOR UPDATE NOWAIT` lock
2. On failure, query `pg_stat_activity` or an `active_edits` tracking table to identify *who* has the lock
3. Display a meaningful message: "This invoice is currently being edited by John Smith (started 5 minutes ago)"
4. Optionally notify the locking user that someone else is waiting

```sql
-- Application-level edit session tracking table
CREATE TABLE active_edits (
    resource_type   VARCHAR(50)  NOT NULL,
    resource_id     BIGINT       NOT NULL,
    user_id         BIGINT       NOT NULL,
    user_name       VARCHAR(200) NOT NULL,
    started_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ  NOT NULL,  -- Auto-expire after inactivity
    PRIMARY KEY (resource_type, resource_id)
);

-- When user opens a record for editing:
BEGIN;
SELECT * FROM invoices WHERE id = $id FOR UPDATE NOWAIT;
-- If success:
INSERT INTO active_edits (resource_type, resource_id, user_id, user_name, expires_at)
VALUES ('invoice', $id, $current_user_id, $current_user_name, NOW() + INTERVAL '30 minutes')
ON CONFLICT (resource_type, resource_id)
DO UPDATE SET user_id=EXCLUDED.user_id, user_name=EXCLUDED.user_name,
              started_at=NOW(), expires_at=EXCLUDED.expires_at;
-- Keep transaction open while user edits...

-- If NOWAIT fails:
-- SELECT user_name, started_at FROM active_edits
-- WHERE resource_type='invoice' AND resource_id=$id;
-- → "Invoice is being edited by [user_name] since [started_at]"
```

## Summary: Concurrency Control Strategy Selection

The four mechanisms we have studied in this chapter form a complete toolkit for managing concurrent access at the application level. They are not mutually exclusive — a well-designed system often uses all four in different contexts, each chosen for the specific concurrency problem it solves best.

```
  CONCURRENCY CONTROL COMPLETE REFERENCE

  ┌──────────────────────┬─────────────────────────────────────────────────┐
  │ Mechanism            │ Best Used For                                   │
  ├──────────────────────┼─────────────────────────────────────────────────┤
  │ OCC (version column) │ Low-conflict scenarios. User-facing forms where │
  │                      │ human "think time" separates read and write.    │
  │                      │ Cross-service coordination (no shared locks).   │
  │                      │ Read-heavy workloads.                           │
  ├──────────────────────┼─────────────────────────────────────────────────┤
  │ SELECT FOR UPDATE    │ High-conflict, safety-critical writes.          │
  │ (pessimistic)        │ Financial transfers, inventory reservations,    │
  │                      │ sequential number generation.                   │
  │                      │ Short operations (lock released quickly).       │
  ├──────────────────────┼─────────────────────────────────────────────────┤
  │ FOR UPDATE           │ Collaborative editing where you want to KNOW    │
  │ NOWAIT               │ immediately if a record is in use, not wait.   │
  │                      │ Non-blocking queue processing where "no job     │
  │                      │ available" is a valid fast-path response.       │
  ├──────────────────────┼─────────────────────────────────────────────────┤
  │ FOR UPDATE           │ Concurrent job queue workers. Any scenario      │
  │ SKIP LOCKED          │ where you want to process any available item,   │
  │                      │ not a specific one. Maximum parallelism with    │
  │                      │ zero blocking between workers.                  │
  └──────────────────────┴─────────────────────────────────────────────────┘

  DECISION FLOW:

  Do you need to modify a SPECIFIC known row?
  │
  ├── YES: Will conflicts be frequent?
  │        │
  │        ├── YES: Use SELECT FOR UPDATE (wait in line, no lost updates)
  │        └── NO:  Use OCC (version column, retry on conflict)
  │                 OR SELECT FOR UPDATE if retry cost is unacceptable
  │
  └── NO:  Are you looking for ANY available row?
           │
           ├── YES: Use SELECT FOR UPDATE SKIP LOCKED (job queue)
           └── NO:  Do you want to know immediately if THE row is locked?
                    │
                    ├── YES: Use SELECT FOR UPDATE NOWAIT
                    └── NO:  Re-examine your requirements

  ANTI-PATTERNS TO AVOID:

  ✗ SELECT FOR UPDATE inside a long user-facing request
    (Locks held while user thinks → long wait queues)

  ✗ OCC without retry logic
    (Detecting conflict but not recovering from it → data loss)

  ✗ FOR UPDATE without ORDER BY in multi-row scenarios
    (Deadlock risk if lock order varies between transactions)

  ✗ NOWAIT without proper error handling
    (Silent failures → confusing user experience)

  ✗ SKIP LOCKED without a status column
    (Worker crashes mid-job → job stuck in 'processing' forever)
    (Solution: add 'processing' status + timeout + retry logic)
```

The choice of concurrency control strategy is ultimately a design decision that reflects your understanding of the workload. Measure your actual conflict rates. Observe the actual wait times under production load. Design for the real behavior of your users, not for a theoretical worst case. An optimistic system under high conflict becomes slower than a pessimistic one; a pessimistic system under low conflict wastes concurrency unnecessarily. The system that fits your workload precisely — not the one that is theoretically safer or more concurrent — is the one that performs best in production.
