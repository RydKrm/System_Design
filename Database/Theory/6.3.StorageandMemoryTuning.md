# Storage and Memory Tuning — A Deep Study Guide

> *"A database runs on hardware. Every byte of data it reads must come from somewhere — a CPU register, an L1 cache line, a DRAM page, a filesystem buffer, or a disk block. The speed of each of these sources differs by orders of magnitude: registers are measured in nanoseconds, DRAM in tens of nanoseconds, SSDs in microseconds, and spinning disks in milliseconds. Database memory tuning is the art of arranging your working set so that the data you query most frequently lives in the fastest storage tier. Get this right and queries return in microseconds. Get it wrong and the same query, seeking identical data, waits milliseconds for a disk read — a difference of one thousand times."*

When a database is installed and started with its default configuration, it is configured conservatively — safe to run on almost any hardware, from a developer's laptop with 4 GB of RAM to a production server with 512 GB. "Safe" means not assuming any specific hardware. But "safe" also means grossly underperforming on the hardware you actually have. The default `shared_buffers` in PostgreSQL is 128 MB — appropriate for a system with 512 MB of RAM, absurdly small on a server with 128 GB. The default `innodb_buffer_pool_size` in MySQL is 128 MB for the same reason. Out-of-the-box, your database is configured for a machine that does not exist in your data center.

This chapter is about understanding what each major configuration parameter controls, why it matters, and how to tune it for your specific workload and hardware. These parameters are not knobs to be twisted randomly — each one controls a specific part of the database's memory architecture, and their interactions are as important as their individual values.

## 1. PostgreSQL Memory Parameters

### How PostgreSQL Uses Memory: The Architecture

Before tuning individual parameters, it is essential to understand how PostgreSQL's memory is organized. PostgreSQL does not use a single unified memory cache. Instead, it has several distinct memory areas, each serving a specific purpose, each configured independently.

```
  POSTGRESQL MEMORY ARCHITECTURE

  ┌──────────────────────────────────────────────────────────────────────┐
  │                  OPERATING SYSTEM LAYER                              │
  │  OS Page Cache (filesystem buffer cache)                             │
  │  Size: whatever RAM is left after PostgreSQL + OS + app processes    │
  │  Stores: filesystem blocks read/written by PostgreSQL data files     │
  └──────────────────────────────────────────────────────────────────────┘
                        ▲                ▲
                        │                │
  ┌─────────────────────┴─-─┐   ┌─────────┴──────────────────────────────┐
  │  SHARED MEMORY          │   │       PER-PROCESS MEMORY               │
  │  (shared between ALL    │   │  (private to each backend process)     │
  │   backend processes)    │   │                                        │
  │                         │   │  work_mem      (per sort/hash op)      │
  │  shared_buffers         │   │  maintenance_work_mem (VACUUM, CREATE  │
  │  WAL buffers            │   │                        INDEX)          │
  │  Lock table             │   │  temp_buffers  (per-session temp tbls) │
  │  Commit log (clog)      │   │  Stack memory                          │
  │  Process array          │   │  Session state                         │
  └─────────────────────────┘   └────────────────────────────────────────┘

  effective_cache_size is NOT a memory allocation —
  it is a HINT to the planner about how much total cache
  (shared_buffers + OS page cache) is available.
```

### shared_buffers — The Database's Primary Cache

`shared_buffers` is the most important memory parameter in PostgreSQL. It is the size of PostgreSQL's own dedicated buffer cache — a region of shared memory that holds database pages (8 KB blocks of table and index data) in RAM. When PostgreSQL needs to read a row, it first looks in `shared_buffers`. If the page is there (a **cache hit**), the data is returned from RAM — taking microseconds. If the page is not there (a **cache miss**), PostgreSQL must read it from disk into `shared_buffers` — taking milliseconds on spinning disk or tens of microseconds on NVMe SSD. The entire purpose of `shared_buffers` is to maximize cache hits by keeping frequently-accessed pages in RAM.

```
  SHARED_BUFFERS: HOW IT WORKS

  PostgreSQL data file (on disk):
  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
  │ Blk0 │ Blk1 │ Blk2 │ Blk3 │ Blk4 │ Blk5 │ Blk6 │ Blk7 │  (8 KB each)
  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘

  shared_buffers (in RAM, shared across all backend processes):
  ┌──────┬──────┬──────┬──────┬──────────────────────────────┐
  │ Blk0 │ Blk3 │ Blk5 │ Blk7 │  ... (cached hot pages)      │
  └──────┴──────┴──────┴──────┴──────────────────────────────┘

  Query: SELECT * FROM orders WHERE id = 42
  Backend process:
    1. Compute which disk block contains id=42 (via index)
    2. Check shared_buffers for that block
    3a. CACHE HIT: block is there → read row → return result (microseconds)
    3b. CACHE MISS: block not there → read from disk → load into shared_buffers
        → read row → return result (milliseconds)
    If shared_buffers is full: evict a rarely-used page (LRU/Clock algorithm)
    to make room for the new block.

  Buffer cache hit ratio: the fraction of page reads served from cache.
  Target: > 99% for a well-tuned OLTP system.
  Below 95%: shared_buffers is too small for your working set.
```

The **working set** is the concept that determines the correct `shared_buffers` size: the set of pages that your queries access frequently. If your working set fits entirely in `shared_buffers`, cache hit ratio approaches 100%. If the working set is larger than `shared_buffers`, some frequently-accessed pages are constantly evicted to make room for others, and cache hit ratio drops.

```
  SIZING shared_buffers

  The conventional rule: set shared_buffers to 25% of total system RAM.
  This is the standard starting point, justified by several constraints:

  1. PostgreSQL also relies on the OS page cache (see effective_cache_size).
     Giving PostgreSQL 100% of RAM would starve the OS cache, which is also
     used by PostgreSQL's WAL files and other data files.
  2. Each backend process needs RAM for work_mem, stack, and session state.
     With 100 connections and 4MB work_mem each, that is 400MB minimum for
     process memory alone.
  3. The OS itself needs RAM for its kernel structures and file buffers.

  PRACTICAL SIZING:

  System RAM    │ shared_buffers         │ Reasoning
  ──────────────┼────────────────────────┼──────────────────────────────
  4 GB          │ 512 MB – 1 GB          │ Leave 3 GB for OS + processes
  8 GB          │ 2 GB                   │ 25% rule
  16 GB         │ 4 GB                   │ 25% rule
  32 GB         │ 8 GB                   │ 25% rule
  64 GB         │ 16 GB                  │ 25% rule
  128 GB        │ 32 GB (but consider    │ Above ~8 GB, returns diminish
                │ up to 40 GB if DB is   │ as OS cache picks up the rest
                │ the only workload)     │
  512 GB        │ 64-128 GB              │ 25% still, but verify hit ratio

  CEILING CONSIDERATION:
  On Linux, shared memory uses huge pages if huge_pages=on in postgresql.conf.
  Without huge pages, allocating very large shared_buffers (> 8 GB) can cause
  TLB pressure. Enable huge pages for shared_buffers > 8 GB.

  PostgreSQL configuration (postgresql.conf):
  shared_buffers = '8GB'              # for a 32 GB server
  huge_pages = on                     # use OS huge pages (2MB per page)
  # Requires: sysctl -w vm.nr_hugepages=4096 (or calculate: shared_buffers ÷ 2MB)
```

**Monitoring the cache hit ratio:**

```sql
  -- Buffer cache hit ratio (should be > 99%):
  SELECT
      sum(heap_blks_read)             AS heap_disk_reads,
      sum(heap_blks_hit)              AS heap_cache_hits,
      ROUND(
          100.0 * sum(heap_blks_hit) /
          NULLIF(sum(heap_blks_hit) + sum(heap_blks_read), 0),
          2
      )                               AS heap_hit_ratio_pct,
      sum(idx_blks_read)              AS index_disk_reads,
      sum(idx_blks_hit)               AS index_cache_hits,
      ROUND(
          100.0 * sum(idx_blks_hit) /
          NULLIF(sum(idx_blks_hit) + sum(idx_blks_read), 0),
          2
      )                               AS index_hit_ratio_pct
  FROM pg_statio_user_tables;

  -- Overall buffer hit rate across all blocks:
  SELECT
      ROUND(
          100.0 * blks_hit / NULLIF(blks_hit + blks_read, 0),
          2
      ) AS overall_buffer_hit_pct
  FROM pg_stat_database
  WHERE datname = current_database();

  -- Per-table cache hit ratio (find tables with low hit rate):
  SELECT
      relname,
      heap_blks_read,
      heap_blks_hit,
      ROUND(100.0 * heap_blks_hit /
            NULLIF(heap_blks_hit + heap_blks_read, 0), 2) AS hit_ratio_pct
  FROM pg_statio_user_tables
  WHERE heap_blks_hit + heap_blks_read > 1000  -- Only tables with significant reads
  ORDER BY hit_ratio_pct ASC;
  -- Tables at the bottom of this list are candidates for increased shared_buffers
  -- or for partitioning to fit the hot partition in cache.
```

### work_mem — Memory Per Sort and Hash Operation

`work_mem` is the maximum amount of memory that a single query operation — a sort or a hash — can use before it must spill to temporary disk files. The critical distinction from `shared_buffers` is that `work_mem` is **per operation, per query, per session**. A single complex query might have 10 sort and hash operations simultaneously active (in parallel branches of a complex plan), each using up to `work_mem`. If you have 200 concurrent sessions, each running a complex query, the total memory in use for sorts can be: `200 sessions × 10 operations × work_mem`.

This multiplicative nature is the most important — and most dangerous — aspect of `work_mem`. Setting `work_mem = 256MB` on a system with 200 concurrent complex queries means a theoretical maximum of `200 × 10 × 256MB = 512GB` of memory just for sort operations, which would immediately trigger OOM (Out Of Memory) on any real server. The default is 4MB precisely because it must be safe in this worst-case scenario.

```
  WORK_MEM: WHY THE MULTIPLICATION MATTERS

  postgresql.conf: work_mem = 64MB

  Query 1 (complex analytical query):
  ┌─────────────────────────────────────────────────────────────────┐
  │ Hash Join                                                       │
  │   → Hash table build: uses up to 64MB                          │
  │   Sort for ORDER BY: uses up to 64MB                           │
  │   Sort for GROUP BY: uses up to 64MB                           │
  │   Hash aggregate:    uses up to 64MB                           │
  │   Total for this ONE query: up to 4 × 64MB = 256MB             │
  └─────────────────────────────────────────────────────────────────┘

  With 50 concurrent sessions running this query:
  50 × 256MB = 12.8 GB of work_mem memory potentially in use!

  If server has 16 GB RAM with 4 GB shared_buffers:
  Available for work_mem: 16 - 4 - 2 (OS/apps) = 10 GB
  12.8 GB needed > 10 GB available → OOM killer activates!

  ─────────────────────────────────────────────────────────────────
  CORRECT APPROACH: Set work_mem conservatively globally,
  use SET LOCAL work_mem = 'XYZ' per-session for heavy queries.

  postgresql.conf:
  work_mem = '4MB'              # safe global default for concurrent OLTP

  For a specific heavy analytical query:
  SET LOCAL work_mem = '256MB'; -- Only for this session/transaction
  EXPLAIN ANALYZE SELECT ... ORDER BY ...; -- Run the expensive query
  RESET work_mem; -- Back to default

  OR per-user:
  ALTER ROLE analyst_user SET work_mem = '128MB';
  -- Analyst role gets 128MB work_mem automatically on login.
  -- Regular app user keeps 4MB.
```

**When work_mem is too small:** The most visible symptom is **temporary file creation** — when a sort or hash operation exceeds `work_mem`, PostgreSQL writes the excess data to temporary files on disk and merges them in a multi-pass external sort. This is enormously slower than in-memory sorting, often 10-100× slower.

```sql
  -- Detect work_mem spills to disk (temporary files):

  -- Per-session temp file usage:
  SELECT pid, usename, query_start,
         temp_files, temp_bytes,
         pg_size_pretty(temp_bytes) AS temp_size,
         LEFT(query, 100) AS query_preview
  FROM pg_stat_activity
  JOIN pg_stat_statements ON TRUE  -- requires pg_stat_statements
  WHERE temp_bytes > 0
  ORDER BY temp_bytes DESC;

  -- Database-wide temp file statistics:
  SELECT datname,
         temp_files,
         pg_size_pretty(temp_bytes) AS temp_data_written
  FROM pg_stat_database
  WHERE datname = current_database();
  -- If temp_files is large and growing → work_mem too small for some queries.

  -- In EXPLAIN ANALYZE: look for Sort Method: external merge
  EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders ORDER BY total DESC;
  -- "Sort Method: external merge  Disk: 48000kB" ← spill to disk!
  -- "Sort Method: quicksort  Memory: 2048kB"      ← in memory ✓
```

**Practical work_mem tuning:**

```sql
  -- Formula for maximum safe work_mem:
  -- work_mem_max = (Available RAM - shared_buffers - OS overhead)
  --                ÷ (max_connections × max_operations_per_query)

  -- For a server with 32GB RAM:
  -- Available = 32GB - 8GB shared_buffers - 4GB OS = 20GB
  -- max_connections = 100, max_ops_per_query ≈ 5 (conservative)
  -- work_mem_max = 20GB ÷ (100 × 5) = 40MB

  -- Start conservatively (4-8MB), identify queries spilling to disk,
  -- increase work_mem for those specific queries via SET LOCAL.

  work_mem = '8MB'                  # global safe default (OLTP)
  # For analytical / reporting workloads: 64MB - 256MB globally is fine
  # because fewer concurrent queries are expected.
```

### effective_cache_size — A Hint, Not an Allocation

`effective_cache_size` is perhaps the most misunderstood parameter in PostgreSQL. It is critically important — it can change whether the query planner uses an index or does a sequential scan — but it does not allocate any memory. It is a **hint to the query planner** about the total amount of data that is likely to be cached by the combined effect of `shared_buffers` and the OS page cache.

The planner uses `effective_cache_size` when estimating the cost of index scans vs. sequential scans. An index scan requires random I/O (accessing pages in arbitrary order, one per index entry). A sequential scan reads pages linearly. On cold storage (no cache), sequential scans are cheap (sequential disk reads are fast) and index scans are expensive (random reads). But when data is cached, random access is as fast as sequential access — and index scans win because they fetch fewer total pages.

```
  HOW effective_cache_size CHANGES PLANNER DECISIONS

  Query: SELECT * FROM orders WHERE customer_id = 42;
  Index: idx_orders_customer_id
  orders table: 500,000 rows, 50,000 pages (400MB total)
  Pages matching customer_id=42: 500 pages (4MB)

  Planner's cost estimate (simplified):
  ─────────────────────────────────────────────────────────────────
  Sequential Scan cost:
    random_page_cost × 0  +  seq_page_cost × 50,000 pages
    = 0 + 1.0 × 50,000 = 50,000 units

  Index Scan cost:
    Each of 500 pages: estimated as RANDOM if not likely cached
                      OR SEQUENTIAL if likely cached
    Probability cached = min(1, effective_cache_size / table_size)

  Case 1: effective_cache_size = 4GB (not enough to cache 400MB table):
    Caching probability = 4GB-of-other-data / large-system
    Planner treats 500 pages as random I/O
    Index Scan cost ≈ random_page_cost × 500 = 4.0 × 500 = 2,000 units
    → Planner chooses Index Scan (2,000 < 50,000) ✓

  Case 2: effective_cache_size = 128MB (too small):
    Planner thinks cache is small → treats all reads as expensive random I/O
    Index Scan cost ≈ 4.0 × 500 = 2,000 (same)
    Sequential Scan: 50,000 (same)
    → Still chooses Index Scan.
    BUT: for a query returning MANY rows, wrong effective_cache_size
    causes planner to prefer seq scan when index scan would be better,
    or vice versa.

  THE KEY INSIGHT:
  Setting effective_cache_size correctly tells the planner how much
  "free caching" the OS will provide. A higher value biases the planner
  toward index scans (trusting that data will be cached).
  Too low: planner over-estimates I/O cost → avoids index scans → slow.
  Too high: planner under-estimates I/O cost → chooses index when seq
            scan is better → wrong plan for large result sets.
```

```
  SIZING effective_cache_size

  Rule: shared_buffers + (available OS page cache)

  Typical guidance: set to 75% of total system RAM.
  Reasoning: PostgreSQL's shared_buffers holds 25%, the remaining 75%
  is potentially in the OS page cache (though not guaranteed).

  System RAM    │ effective_cache_size   │ shared_buffers
  ──────────────┼────────────────────────┼─────────────────
  4 GB          │ 3 GB                   │ 1 GB
  8 GB          │ 6 GB                   │ 2 GB
  16 GB         │ 12 GB                  │ 4 GB
  32 GB         │ 24 GB                  │ 8 GB
  64 GB         │ 48 GB                  │ 16 GB
  128 GB        │ 96 GB                  │ 32 GB

  postgresql.conf:
  shared_buffers      = '8GB'
  effective_cache_size = '24GB'   # = 75% of 32GB total RAM
  work_mem            = '8MB'
```

### maintenance_work_mem — For Background Operations

A parameter often forgotten alongside the three main ones is `maintenance_work_mem` — the memory budget for maintenance operations like `VACUUM`, `CREATE INDEX`, `REINDEX`, and `ALTER TABLE ADD FOREIGN KEY`. These operations are typically run infrequently but benefit enormously from additional memory. `VACUUM` with more `maintenance_work_mem` can hold a larger map of dead tuple locations, reducing the number of heap passes needed. `CREATE INDEX` with large `maintenance_work_mem` can build a bigger in-memory sort buffer, potentially building the entire index without any disk spillage.

```
  maintenance_work_mem — Practical Values

  Default: 64MB (far too small for large databases)
  Recommended: 512MB – 2GB for production systems

  postgresql.conf:
  maintenance_work_mem = '1GB'

  # Or set per-session for large index builds:
  SET maintenance_work_mem = '4GB';
  CREATE INDEX CONCURRENTLY idx_orders_large ON orders (customer_id, created_at);
  RESET maintenance_work_mem;

  # For autovacuum specifically:
  autovacuum_work_mem = '512MB'  # overrides maintenance_work_mem for autovacuum
                                 # (-1 means use maintenance_work_mem)
```

## 2. MySQL — innodb_buffer_pool_size

### The InnoDB Buffer Pool: MySQL's Primary Cache

In MySQL's InnoDB storage engine, the **buffer pool** is the single most important memory structure — equivalent to PostgreSQL's `shared_buffers` but even more central to performance. While PostgreSQL also relies heavily on the OS page cache (which is why `effective_cache_size` matters so much), InnoDB's buffer pool is designed to be the primary cache for all data access, with the OS page cache playing a supporting role.

The InnoDB buffer pool stores three types of data pages: **table data pages** (rows from InnoDB tables), **index pages** (B-tree index nodes), and **change buffer pages** (deferred secondary index writes — discussed below). When a query needs a page, InnoDB checks the buffer pool first. A hit returns the data from RAM; a miss triggers a read from the InnoDB data file (`.ibd` file) into the buffer pool. The buffer pool evicts pages using a modified LRU algorithm when it is full.

```
  INNODB BUFFER POOL ARCHITECTURE

  Buffer Pool (one large memory region):
  ┌──────────────────────────────────────────────────────────────────┐
  │  LRU List (most to least recently used)                          │
  │  ┌──────────────────────────┬─────────────────────────────────┐  │
  │  │   Young (New) Sublist    │   Old Sublist                   │  │
  │  │   (5/8 of buffer pool)   │   (3/8 of buffer pool)          │  │
  │  │                          │                                  │  │
  │  │  Hot pages —             │  Pages just inserted from disk   │  │
  │  │  recently re-accessed    │  Promoted to Young after         │  │
  │  │  multiple times          │  innodb_old_blocks_time (1s)     │  │
  │  │                          │  if accessed again               │  │
  │  └──────────────────────────┴─────────────────────────────────┘  │
  │                                                ▲                  │
  │  Eviction from tail of Old list ←──────────────┘                 │
  │                                                                   │
  │  Also contains:                                                   │
  │  - Free list (pages available for new reads)                      │
  │  - Flush list (dirty pages awaiting write to disk)                │
  │  - Adaptive hash index (auto-built hash index for hot pages)      │
  └──────────────────────────────────────────────────────────────────┘

  The Young/Old split prevents full table scans from polluting the cache:
  A sequential scan reads pages into the Old list.
  If those pages are not re-accessed within innodb_old_blocks_time,
  they are evicted without ever entering the Young list.
  Hot frequently-accessed pages in the Young list are protected.
```

### Sizing innodb_buffer_pool_size

The rule for InnoDB is more aggressive than PostgreSQL because MySQL relies less on the OS page cache and more on InnoDB's own buffer pool for all data access. The standard recommendation is to set `innodb_buffer_pool_size` to **70-80% of total system RAM** when MySQL is the primary workload on the server.

```
  SIZING innodb_buffer_pool_size

  System RAM    │ innodb_buffer_pool_size  │ Notes
  ──────────────┼──────────────────────────┼──────────────────────────────
  4 GB          │ 2–3 GB                   │ Leave 1 GB for OS + MySQL overhead
  8 GB          │ 5–6 GB                   │ 70% rule
  16 GB         │ 12 GB                    │ 75% rule
  32 GB         │ 24 GB                    │ 75% rule
  64 GB         │ 48 GB                    │ 75% rule
  128 GB        │ 96 GB                    │ 75% rule — monitor OS pressure

  my.cnf configuration:
  [mysqld]
  innodb_buffer_pool_size = 24G         # for a 32 GB server

  # Multiple buffer pool instances (reduces mutex contention):
  # One instance per ~1GB of buffer pool. For 24GB pool: 8 instances.
  innodb_buffer_pool_instances = 8
  # Each instance has its own LRU list and mutex.
  # Multiple threads writing/reading to different instances do not contend.
  # Minimum for production: innodb_buffer_pool_size / 1GB instances.

  # Online resize (MySQL 5.7+): can resize buffer pool without restart!
  SET GLOBAL innodb_buffer_pool_size = 32 * 1024 * 1024 * 1024;
  -- MySQL progressively resizes in chunks. Monitor: SHOW STATUS LIKE 'Innodb_buffer_pool_resize%';
```

### Monitoring the InnoDB Buffer Pool

```sql
  -- Buffer pool hit ratio (should be > 99%):
  SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
  -- Innodb_buffer_pool_read_requests: total logical reads (from pool or disk)
  -- Innodb_buffer_pool_reads: physical disk reads (cache misses)
  -- Hit ratio = 1 - (reads / read_requests)

  SELECT
      (1 - (
          variable_value /
          (SELECT variable_value FROM performance_schema.global_status
           WHERE variable_name = 'Innodb_buffer_pool_read_requests')
      )) * 100 AS buffer_pool_hit_pct
  FROM performance_schema.global_status
  WHERE variable_name = 'Innodb_buffer_pool_reads';

  -- Detailed buffer pool usage:
  SHOW STATUS LIKE 'Innodb_buffer_pool_%';
  -- Innodb_buffer_pool_pages_total: total pages in buffer pool
  -- Innodb_buffer_pool_pages_data:  pages containing data (tables/indexes)
  -- Innodb_buffer_pool_pages_dirty: pages modified but not yet flushed to disk
  -- Innodb_buffer_pool_pages_free:  pages available for new data
  -- Innodb_buffer_pool_bytes_dirty: bytes in dirty pages

  -- If Innodb_buffer_pool_pages_free ≈ 0 consistently:
  -- Buffer pool is full — working set exceeds buffer pool size.
  -- Consider increasing innodb_buffer_pool_size.

  -- Buffer pool wait ratio:
  SHOW STATUS LIKE 'Innodb_buffer_pool_wait_free';
  -- Non-zero: pool was full and query had to wait for a page to be evicted.
  -- Growing value: pool severely undersized.

  -- InnoDB status (comprehensive):
  SHOW ENGINE INNODB STATUS\G
  -- Look for "Buffer pool hit rate: X / 1000"
  -- Values below 950/1000 (95%) indicate memory pressure.
```

## 3. Checkpoint Tuning

### What a Checkpoint Is

A **checkpoint** is a moment when the database guarantees that all dirty pages — pages in the buffer cache that have been modified but not yet written to the actual data files on disk — are flushed to disk. After a checkpoint completes, the database knows that the data files on disk are consistent and complete up to that point. This matters for recovery: after a crash, PostgreSQL only needs to replay WAL records created after the most recent checkpoint, not the entire WAL history.

Without checkpoints, dirty pages would accumulate in memory indefinitely. After a crash, recovery would require replaying potentially enormous amounts of WAL, taking hours. Checkpoints bound the recovery time: the more frequent the checkpoints, the shorter the post-crash recovery time (fewer WAL records to replay), but the more I/O overhead during normal operation (more frequent disk flushes).

```
  CHECKPOINT MECHANICS

  Timeline:
  ──────────────────────────────────────────────────────────────────────────►
  Checkpoint C1         (operations)         Checkpoint C2   Crash!  Recovery
     │                                            │              │      │
     │◄──────────────── dirty pages ─────────────►│              │      │
     │                  accumulate in cache        │              │      │
     │                                            │ flush ALL    │      │
     │                                            │ dirty pages  │      │
     │                                            │ to disk      │      │
     │                                            │              │ Crash │
     │                                                           │      │
     │                                                           │ Replay WAL from C2
     │                                                           │ to crash point only
     │                                                           │ (not from C1!)
     │                                                           │
     Recovery time ∝ distance between C2 and Crash

  CHECKPOINT GOALS:
  1. Write all dirty shared_buffers pages to data files
  2. fsync the data files (ensure OS buffer writes reach disk platters)
  3. Update the checkpoint record in pg_control
  4. Advance the WAL recycle point (old WAL segments can be recycled)

  I/O BURST PROBLEM:
  Naively, a checkpoint would flush ALL dirty pages simultaneously,
  causing a massive I/O burst. PostgreSQL's checkpoint spreading prevents
  this by writing dirty pages gradually throughout the checkpoint interval.
```

### PostgreSQL Checkpoint Parameters

```
  CHECKPOINT CONFIGURATION PARAMETERS

  checkpoint_timeout:
    Maximum time between automatic checkpoints.
    Default: 5 minutes. Too frequent = too much I/O. Too infrequent =
    long crash recovery time.
    Production range: 15–60 minutes for write-heavy workloads.

  max_wal_size:
    Maximum WAL size the system will allow to accumulate between
    checkpoints. If WAL grows beyond this, a checkpoint is triggered
    immediately, regardless of checkpoint_timeout.
    Default: 1 GB. Severely limiting for write-heavy workloads.
    Production range: 4 GB – 64 GB depending on write volume.
    The checkpoint triggered by max_wal_size is called a "forced checkpoint"
    and is the most common cause of unplanned I/O spikes in PostgreSQL.

  min_wal_size:
    Minimum WAL disk space to retain (recycle old segments rather than delete).
    Keeps WAL space reserved so it doesn't need to be pre-allocated later.
    Default: 80 MB. Production: 1 GB – 4 GB to avoid WAL pre-allocation cost.

  checkpoint_completion_target:
    The fraction of the checkpoint interval over which dirty page writes
    should be spread. 0.9 means: complete the checkpoint by using 90% of
    the interval between checkpoints, spreading I/O smoothly.
    Default: 0.9 (already good — keep this value).
    Value of 0.0 would write all dirty pages immediately at checkpoint start
    (causes massive I/O spike). 0.9 spreads the I/O over 90% of the interval.
```

```sql
  -- postgresql.conf checkpoint tuning for a write-heavy production database:

  checkpoint_timeout          = '30min'  -- Check every 30 minutes (max)
  max_wal_size                = '16GB'   -- Allow up to 16GB WAL between checkpoints
  min_wal_size                = '2GB'    -- Keep 2GB reserved
  checkpoint_completion_target = 0.9     -- Spread I/O over 90% of interval

  -- Monitor checkpoints to detect forced checkpoints (problems):
  SELECT
      checkpoints_timed,                 -- checkpoints triggered by checkpoint_timeout
      checkpoints_req,                   -- FORCED checkpoints (triggered by max_wal_size!)
      ROUND(100.0 * checkpoints_req /
            NULLIF(checkpoints_timed + checkpoints_req, 0), 2)
                                        AS forced_checkpoint_pct,
      checkpoint_write_time / 1000.0    AS write_time_seconds,
      checkpoint_sync_time  / 1000.0    AS sync_time_seconds,
      buffers_checkpoint                 AS pages_written_at_checkpoints,
      buffers_clean                      AS pages_written_by_bgwriter,
      buffers_backend                    AS pages_written_by_backends,
      -- pages_written_by_backends indicates backends doing their own I/O
      -- (pool full, checkpoint falling behind) — should be low
      maxwritten_clean                   AS bgwriter_stopped_early
  FROM pg_stat_bgwriter;

  -- If checkpoints_req >> checkpoints_timed:
  -- max_wal_size is too small — increase it.
  -- Forced checkpoints cause I/O spikes that degrade query performance.

  -- If checkpoint_sync_time is very high (seconds):
  -- The fsync phase is slow — disk I/O bottleneck.
  -- Consider: faster storage, full_page_writes optimization.
```

### The Background Writer (bgwriter)

PostgreSQL has a background process called the **bgwriter** (background writer) whose job is to proactively write dirty pages to disk between checkpoints. This prevents the situation where a backend process needs to write a dirty page to disk urgently (because `shared_buffers` is full and no free page is available) — instead, the bgwriter has already written that page, and a clean page is available immediately.

```sql
  -- postgresql.conf bgwriter tuning:
  bgwriter_lru_maxpages  = 100    -- max dirty pages written per round
  bgwriter_lru_multiplier = 2.0  -- multiplier for how many pages to clean ahead
  bgwriter_delay         = 200ms  -- sleep between rounds

  -- Key metric: buffers_backend in pg_stat_bgwriter
  -- If this number is large and growing: bgwriter is not keeping up.
  -- Backends are having to write their own dirty pages → latency spikes.
  -- Increase bgwriter_lru_maxpages to make bgwriter more aggressive.
```

## 4. WAL Configuration

### What the Write-Ahead Log Is and Why It Exists

The **Write-Ahead Log (WAL)** — called the **redo log** in MySQL/InnoDB — is the foundation of durability in relational databases. The fundamental principle is: **before any change is made to a data file, a record of that change must be written to the WAL**. When a write occurs, the database does not immediately update the data file on disk. Instead, it writes a compact WAL record describing the change, then modifies the page in the buffer cache (in RAM). Later, the checkpoint process writes the modified pages to the actual data files.

This design is crucial for durability and performance. Durability: if the system crashes after a WAL record is written but before the data page is flushed to the data file, the WAL record allows the database to reconstruct the change during recovery. Performance: sequential WAL writes are dramatically faster than random data file writes, because WAL is written sequentially to a dedicated area of disk, while data file writes are scattered across the filesystem.

```
  WAL WRITE PATH

  Client:  INSERT INTO orders VALUES (...)
              │
              ▼
  Backend:  Modify page in shared_buffers (fast, in RAM)
              │
              ▼
  WAL:      Write WAL record (sequential write to WAL file)
  ─────────────────────────────────────────────────────────────
  WAL file: [record][record][record][record][record]...
                                                    ← append-only, sequential

  The WAL write MUST complete (and be fsync'd) before the
  INSERT is acknowledged to the client.
  The data page write (to the actual table file) happens LATER,
  at checkpoint time, asynchronously.

  WHY THIS IS FASTER:
  Sequential write to WAL:   ~200 MB/s (HDD), ~3 GB/s (SSD)
  Random write to data file: ~50 MB/s (HDD), ~500 MB/s (SSD)
  WAL is 4-6× faster than random data writes.
  The database trades one sequential WAL write for one deferred random write.
```

### PostgreSQL WAL Configuration Parameters

```sql
  -- ─────────────────────────────────────────────────────────────────
  -- WAL Level: controls what information is recorded in WAL
  -- ─────────────────────────────────────────────────────────────────

  wal_level = replica        -- DEFAULT in production
  -- Options:
  -- minimal:  only enough for crash recovery (no replication support)
  -- replica:  supports streaming replication and base backups
  -- logical:  supports logical replication and logical decoding
  -- Always use 'replica' or 'logical' in production.
  -- 'minimal' prevents setting up any form of replication.

  -- ─────────────────────────────────────────────────────────────────
  -- Durability vs Performance: synchronous_commit
  -- ─────────────────────────────────────────────────────────────────

  synchronous_commit = on    -- DEFAULT: guarantees durability
  -- When ON: COMMIT does not return to client until WAL is fsync'd to disk.
  -- Absolute guarantee: if the server says "committed," the transaction
  -- survived even a power failure at that exact moment.

  -- When OFF (synchronous_commit = off):
  -- COMMIT returns immediately. WAL is written to OS buffer but not fsync'd.
  -- WAL is flushed to disk within wal_writer_delay (default 200ms) asynchronously.
  -- Risk: if the server crashes in that 200ms window, the last few committed
  --       transactions can be LOST (though the database remains consistent,
  --       just without those transactions).
  -- Benefit: 2-3× higher write throughput, dramatically lower commit latency.

  -- Use synchronous_commit = off for:
  -- ✓ Logging tables (losing last 200ms of logs is acceptable)
  -- ✓ Analytics event tables (eventual durability is fine)
  -- ✓ Session state tables (can be rebuilt)
  -- Use synchronous_commit = on (default) for:
  -- ✓ Financial transactions (money)
  -- ✓ Order placements
  -- ✓ Any data where loss of last N records is unacceptable

  -- Per-transaction override:
  BEGIN;
  SET LOCAL synchronous_commit = off;  -- only this transaction is async
  INSERT INTO event_log VALUES (...);
  COMMIT;                               -- fast commit, slightly risky

  -- ─────────────────────────────────────────────────────────────────
  -- fsync: the nuclear option
  -- ─────────────────────────────────────────────────────────────────

  fsync = on    -- NEVER turn this off in production!
  -- When OFF: PostgreSQL does not call fsync() on data files.
  -- The OS may buffer writes indefinitely without flushing to disk.
  -- A power failure can cause DATA CORRUPTION (not just data loss —
  -- the database can be left in an internally inconsistent state that
  -- requires backup restoration to fix).
  -- The only legitimate use of fsync=off is for bulk data loading
  -- into a throwaway database that will be restored from backup anyway.

  -- ─────────────────────────────────────────────────────────────────
  -- WAL Compression and Full-Page Writes
  -- ─────────────────────────────────────────────────────────────────

  full_page_writes = on    -- DEFAULT: required for consistency
  -- After a checkpoint, the FIRST write to any page is recorded in WAL
  -- as a complete page image (not just the change).
  -- Reason: if the system crashes during a partial page write, the
  -- page on disk is torn (half old, half new data). The full-page
  -- image in WAL allows recovery to restore the complete page before
  -- applying the change record.
  -- Cost: WAL size can double during the burst after a checkpoint.
  -- Never disable unless using a filesystem with atomic page writes (ZFS).

  wal_compression = on     -- Compress full-page images in WAL (PostgreSQL 9.5+)
  -- Reduces WAL size by 30-80% (highly effective for full-page images).
  -- Small CPU cost for compression/decompression.
  -- Almost always worth enabling. Set to 'on' or 'zstd' (PostgreSQL 15+).

  wal_compression = zstd   -- PostgreSQL 15+: zstd is faster than LZ4 at equal ratio

  -- ─────────────────────────────────────────────────────────────────
  -- WAL Writer and Buffers
  -- ─────────────────────────────────────────────────────────────────

  wal_buffers = '64MB'    -- in-memory buffer for WAL before writing to WAL file
  -- Default: auto (-1), which sets to 1/32 of shared_buffers, max 64MB.
  -- 64MB is usually fine. Only increase if wal_write_time in pg_stat_wal is high.

  wal_writer_delay = 200ms  -- how often the WAL writer wakes up to flush
  -- With synchronous_commit=off, this bounds the maximum data loss window.

  -- ─────────────────────────────────────────────────────────────────
  -- Monitor WAL activity
  -- ─────────────────────────────────────────────────────────────────

  SELECT
      wal_records,                        -- total WAL records generated
      wal_fpi,                            -- full-page images written
      pg_size_pretty(wal_bytes)           AS wal_volume,
      wal_buffers_full,                   -- times WAL buffer was full (bad: increase wal_buffers)
      wal_write,                          -- number of WAL writes
      wal_sync,                           -- number of WAL fsyncs
      wal_write_time                      AS write_time_ms,
      wal_sync_time                       AS sync_time_ms
  FROM pg_stat_wal;

  -- If wal_sync_time >> wal_write_time: fsync is the bottleneck (disk I/O)
  -- If wal_buffers_full is nonzero: wal_buffers too small
  -- If wal_fpi is very high: many full-page images → consider wal_compression
```

## 5. Autovacuum Tuning

### The Problem Autovacuum Solves

As covered in the MVCC chapter, every UPDATE and DELETE in PostgreSQL leaves dead tuples — old row versions that are no longer visible to any transaction — behind in the heap. These dead tuples consume disk space, slow down sequential scans (the database must read and skip them), bloat indexes (dead index entries pointing to dead tuples), and — if left unchecked for millions of transactions — trigger the catastrophic XID wraparound condition.

**Autovacuum** is PostgreSQL's background maintenance daemon that monitors all tables and automatically triggers `VACUUM` and `ANALYZE` when they accumulate enough dead tuples or stale statistics. It runs as a configurable number of worker processes, each handling one table at a time, designed to run constantly in the background with minimal impact on normal operations.

The challenge with autovacuum is that its default configuration is deliberately conservative — tuned to minimize its I/O impact even on a developer laptop — and therefore far too gentle for production tables with millions of rows and thousands of writes per second.

### The Trigger Formula

Autovacuum triggers VACUUM for a table when:

```
  AUTOVACUUM TRIGGER CONDITION

  VACUUM triggered when:
    n_dead_tuples > autovacuum_vacuum_threshold + (autovacuum_vacuum_scale_factor × n_live_tuples)

  Default values:
    autovacuum_vacuum_threshold   = 50      (trigger after at least 50 dead tuples)
    autovacuum_vacuum_scale_factor = 0.20  (plus 20% of total rows)

  EXAMPLE CALCULATION:

  Small table (10,000 rows):
    Threshold = 50 + (0.20 × 10,000) = 2,050 dead tuples
    → Very reasonable. Autovacuum runs when 20% of the table is dead.

  Medium table (1,000,000 rows):
    Threshold = 50 + (0.20 × 1,000,000) = 200,050 dead tuples
    → 200,000 dead tuples before VACUUM triggers! That's a lot of bloat.

  Large table (100,000,000 rows):
    Threshold = 50 + (0.20 × 100,000,000) = 20,000,050 dead tuples
    → 20 MILLION dead tuples before cleanup! Completely unacceptable.
    → A table receiving 1,000 updates/second takes 5.5 hours to trigger
      autovacuum once. In those 5.5 hours: massive table bloat.

  THE PROBLEM: scale_factor = 0.20 is catastrophically wrong for large tables.
  The scale factor must be reduced dramatically for large tables.

  ANALYZE triggered when:
    n_mod_since_analyze > autovacuum_analyze_threshold + (autovacuum_analyze_scale_factor × n_live_tuples)

  Default:
    autovacuum_analyze_threshold    = 50
    autovacuum_analyze_scale_factor = 0.10
  Same problem for large tables: statistics become stale long before ANALYZE runs.
```

### Tuning Autovacuum Per-Table

The most important autovacuum tuning technique is configuring aggressive settings on a **per-table basis** for large, frequently-written tables, rather than changing the global defaults (which might overwhelm small tables).

```sql
  -- ─────────────────────────────────────────────────────────────────
  -- Per-table autovacuum tuning (most important production technique)
  -- ─────────────────────────────────────────────────────────────────

  -- Aggressively tune autovacuum for a large, frequently-updated table:
  ALTER TABLE orders SET (
      autovacuum_vacuum_scale_factor    = 0.01,  -- Trigger at 1% dead rows (not 20%)
      autovacuum_vacuum_threshold       = 100,   -- Or at minimum 100 dead rows
      autovacuum_analyze_scale_factor   = 0.005, -- Re-analyze at 0.5% change (not 10%)
      autovacuum_analyze_threshold      = 50,    -- Analyze after at least 50 changes
      autovacuum_vacuum_cost_delay      = 2,     -- Sleep 2ms between I/O bursts (default: 20ms)
                                                  -- Lower = more aggressive (faster, more I/O)
      autovacuum_vacuum_cost_limit      = 400    -- More I/O work per burst (default: 200)
  );

  -- Very high-traffic table: even more aggressive
  ALTER TABLE events SET (
      autovacuum_vacuum_scale_factor    = 0.005,
      autovacuum_vacuum_threshold       = 50,
      autovacuum_analyze_scale_factor   = 0.002,
      autovacuum_vacuum_cost_delay      = 0,    -- No sleeping! Run as fast as possible.
      autovacuum_vacuum_cost_limit      = 800
  );

  -- Verify current per-table settings:
  SELECT relname, reloptions
  FROM pg_class
  WHERE relname IN ('orders', 'events', 'order_items');

  -- ─────────────────────────────────────────────────────────────────
  -- Global autovacuum tuning (affects all tables not specifically tuned)
  -- ─────────────────────────────────────────────────────────────────

  # postgresql.conf global settings:
  autovacuum                     = on          # never turn off!
  autovacuum_max_workers         = 6           # default 3; increase for many tables
  autovacuum_naptime             = 30s         # default 60s; how often to wake up
                                               # and scan tables for work

  autovacuum_vacuum_threshold    = 50          # fine as global default
  autovacuum_vacuum_scale_factor = 0.05        # 5% is better than 20% globally
  autovacuum_analyze_threshold   = 50
  autovacuum_analyze_scale_factor = 0.02       # 2% is better than 10% globally

  autovacuum_vacuum_cost_delay   = 2ms         # less sleeping = more I/O = faster
                                               # default: 2ms (already updated in PG 13+)
  autovacuum_vacuum_cost_limit   = 400         # default: 200; double for busy servers

  autovacuum_freeze_max_age      = 200000000   # trigger anti-wraparound VACUUM at 200M XIDs
                                               # (default 200M — fine, don't increase)
  vacuum_freeze_min_age          = 50000000    # freeze tuples older than 50M XIDs
  vacuum_freeze_table_age        = 150000000   # whole-table freeze scan at 150M XIDs

  autovacuum_work_mem            = '512MB'     # memory for autovacuum workers
                                               # -1 means use maintenance_work_mem
```

### Monitoring Autovacuum Effectiveness

```sql
  -- ─────────────────────────────────────────────────────────────────
  -- The comprehensive autovacuum health dashboard
  -- ─────────────────────────────────────────────────────────────────

  -- 1. Dead tuple accumulation — which tables need attention?
  SELECT
      schemaname,
      relname                                     AS table_name,
      n_live_tup                                  AS live_rows,
      n_dead_tup                                  AS dead_rows,
      ROUND(100.0 * n_dead_tup /
            NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
      last_vacuum,
      last_autovacuum,
      last_analyze,
      last_autoanalyze,
      n_mod_since_analyze                         AS rows_changed_since_analyze,
      vacuum_count + autovacuum_count             AS total_vacuums
  FROM pg_stat_user_tables
  WHERE n_dead_tup > 1000
  ORDER BY dead_pct DESC NULLS LAST;
  -- Tables at the top have the most dead tuple pressure.
  -- dead_pct > 10%: attention needed (tune autovacuum for this table).
  -- dead_pct > 20%: urgent — VACUUM manually then tune settings.

  -- 2. Is autovacuum currently running? What is it doing?
  SELECT pid, usename,
         query_start,
         NOW() - query_start                   AS duration,
         LEFT(query, 100)                      AS activity
  FROM pg_stat_activity
  WHERE query LIKE 'autovacuum:%'
  ORDER BY query_start;

  -- 3. XID wraparound risk — the most critical health check
  SELECT
      datname,
      age(datfrozenxid)                         AS xid_age,
      2000000000 - age(datfrozenxid)            AS xids_until_warning,
      ROUND(age(datfrozenxid) / 2000000000.0 * 100, 1) AS pct_of_danger_zone
  FROM pg_database
  ORDER BY age(datfrozenxid) DESC;
  -- Alert threshold: xid_age > 1,500,000,000 (75% of danger zone)
  -- Emergency: xid_age > 1,800,000,000 — manual VACUUM FREEZE required immediately!

  -- 4. Per-table XID age (tables, not just databases):
  SELECT
      schemaname,
      relname,
      age(relfrozenxid)                         AS table_xid_age,
      2000000000 - age(relfrozenxid)            AS xids_remaining
  FROM pg_class c
  JOIN pg_namespace n ON n.oid = c.relnamespace
  WHERE relkind = 'r'
    AND n.nspname NOT IN ('pg_catalog', 'information_schema')
  ORDER BY age(relfrozenxid) DESC
  LIMIT 20;
  -- A specific table with very high age needs manual VACUUM FREEZE:
  -- VACUUM FREEZE VERBOSE my_old_table;

  -- 5. Autovacuum cost throttling — is autovacuum being too gentle?
  SHOW autovacuum_vacuum_cost_delay;   -- if 20ms, autovacuum is very conservative
  SHOW autovacuum_vacuum_cost_limit;   -- if 200, autovacuum is very conservative

  -- 6. Table bloat estimate:
  SELECT
      tablename,
      pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size,
      pg_size_pretty(pg_relation_size(schemaname||'.'||tablename)) AS table_size,
      pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename) -
                     pg_relation_size(schemaname||'.'||tablename)) AS index_size,
      n_dead_tup
  FROM pg_stat_user_tables
  JOIN pg_tables USING (tablename, schemaname)
  ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
  LIMIT 20;
```

### Manual VACUUM Strategies

Despite autovacuum running automatically, there are situations where manual VACUUM is essential: after a large batch delete or update (which creates far more dead tuples than autovacuum's threshold expects), before creating a large index (to ensure no dead tuples interfere), or when XID wraparound is approaching for a specific table.

```sql
  -- Standard VACUUM: reclaim space, does not shrink file, allows concurrent access
  VACUUM VERBOSE orders;
  -- VERBOSE shows which pages were cleaned, how many dead tuples removed.

  -- VACUUM ANALYZE: vacuum + refresh statistics in one pass
  VACUUM ANALYZE orders;
  -- Use after large bulk operations that change data distribution significantly.

  -- VACUUM FULL: rewrites entire table (shrinks file, requires exclusive lock!)
  -- WARNING: blocks ALL reads and writes to the table for the duration!
  -- Use only in a maintenance window after massive data deletion.
  VACUUM FULL orders;
  -- After this: run ANALYZE to rebuild statistics for the compacted table.
  ANALYZE orders;

  -- VACUUM FREEZE: force-freeze all eligible tuples (anti-wraparound)
  VACUUM FREEZE VERBOSE orders;
  -- Use when a specific table's XID age is approaching the danger threshold.

  -- Online alternative to VACUUM FULL (no exclusive lock):
  -- pg_repack (third-party extension): rewrites table without blocking
  -- pg_repack --table orders mydb
```

Set up dashboards for cache hit ratio, dead tuple accumulation, checkpoint frequency, and XID age from day one, and respond to their signals before they become incidents.
