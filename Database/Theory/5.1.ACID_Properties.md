# ACID Properties

### A Deep, Conceptual Journey from the Ground Up

> _ACID is not a feature you enable — it is a promise the database makes to you, every time, about the integrity of your data._

---

## Preface: The World Without Guarantees

Picture this scenario. You are running a bank. Your application processes a money transfer: subtract $500 from Account A, add $500 to Account B. Two simple SQL statements. Now imagine the server crashes — a power failure, a kernel panic, a network dropout — right after the debit from Account A but before the credit to Account B. When the server comes back online, $500 is simply gone. It is not in Account A anymore. It never arrived in Account B. Five hundred dollars has vanished from the universe.

Or imagine two customers simultaneously trying to purchase the last item in your inventory. Both applications read the stock count, both see "1 item remaining," both proceed to sell it, both decrement the counter. Now your inventory shows -1 items, and two customers have paid for an item only one of them can receive.

Or imagine your application updates a customer's email address, but something in the validation logic fires halfway through and the database is left with a half-updated record — the email changed in one table but not in the audit log table that is supposed to stay in sync.

These are not theoretical edge cases. They are the everyday hazards of a multi-user, concurrent, failure-prone computing environment. And they would be routine catastrophes if database systems did not make — and keep — a specific set of promises about how they behave.

Those promises have a name: **ACID**. The acronym stands for Atomicity, Consistency, Isolation, and Durability. Coined by Andreas Reuter and Theo Härder in 1983, the term formalizes the four properties that together define what it means for a database to handle transactions correctly. Understanding ACID deeply — not just the definitions, but the mechanisms behind them and the trade-offs they entail — is foundational for every backend engineer who builds systems that must not lose or corrupt data.

This guide explores each property as a living concept, not a vocabulary term.

## Chapter 1: The Transaction — The Unit of ACID

### Before ACID, There Must Be a Transaction

ACID properties do not apply to individual SQL statements in isolation. They apply to **transactions** — groups of one or more operations that the database treats as a single, indivisible unit of work. A transaction begins explicitly (with `BEGIN` or implicitly when a statement starts), contains one or more operations, and ends with either a `COMMIT` (make all changes permanent) or a `ROLLBACK` (undo all changes as if they never happened).

Every ACID property is a statement about what the database guarantees with respect to transactions. Understanding a transaction first makes every ACID property immediately intuitive.

```
Transaction Lifecycle:

  BEGIN;                          ← transaction starts
    UPDATE accounts
      SET balance = balance - 500
      WHERE id = 'A';             ← operation 1

    UPDATE accounts
      SET balance = balance + 500
      WHERE id = 'B';             ← operation 2

  COMMIT;                         ← transaction ends: all changes become permanent

  -- OR, if something goes wrong:
  ROLLBACK;                       ← transaction ends: all changes are undone
```

Inside a transaction, changes are visible to the current session but are not yet permanent. The database holds them in a kind of provisional state. Only at `COMMIT` do they become durable and visible to other sessions. Only at `ROLLBACK` (or on failure) are they completely discarded. The four ACID properties describe the rules governing this lifecycle precisely.

## Chapter 2: Atomicity — All or Nothing

### The Indivisibility Guarantee

**Atomicity** is the property that guarantees a transaction is treated as a single, indivisible unit. Either all of its operations succeed and are committed, or none of them are. There is no middle ground, no partial success, no half-committed state. The database can never end up in a situation where some operations of a transaction have taken effect and others have not.

The word "atomic" comes from the Greek "atomos," meaning indivisible. In physics, an atom was once thought to be the smallest indivisible unit of matter. In database theory, a transaction is the indivisible unit of work — it cannot be split into parts where some parts happened and others did not.

This is the property that saves you from the bank transfer disaster described in the preface. The debit and the credit are wrapped in one transaction. If the server crashes after the debit but before the credit, the database's recovery mechanism rolls back the entire transaction on restart — the debit is undone, Account A's balance is restored, and it is as if the transaction never began. No money disappears.

```
Atomicity in Action:

  BEGIN;
    UPDATE accounts SET balance = balance - 500 WHERE id = 'A';
    -- [server crashes HERE]
    UPDATE accounts SET balance = balance + 500 WHERE id = 'B';
  COMMIT; ← never reached

  On restart:
    Database reads its WAL (Write-Ahead Log).
    Finds a transaction that started but never committed.
    Rolls back the debit automatically.
    Account A is restored to its original balance.
    Account B is untouched.
    The database is in the exact state it was before BEGIN.

  Result: No money lost. No partial transfer. Clean state.
```

### How Atomicity Is Implemented: The Write-Ahead Log (WAL)

Atomicity is not magic — it is engineering. The mechanism that makes it possible is the **Write-Ahead Log (WAL)**, also called the redo/undo log or journal. The core principle of WAL is simple but profound: **before any change is written to the actual data pages on disk, a record of that change — and enough information to undo it — is written to a sequential log file first**.

The WAL is a sequential, append-only file. Appending to a sequential file is extremely fast — much faster than random writes to data pages scattered across disk. This is why WAL does not kill performance: the actual data pages can be updated lazily (in memory, flushed to disk later), while the log provides the authoritative record of what happened.

```
WAL Structure (simplified):

  Log entry format:
  [LSN][Transaction ID][Operation Type][Table][Before Value][After Value]

  During a transfer transaction:

  LSN 1001: [TxID:42] [BEGIN]
  LSN 1002: [TxID:42] [UPDATE] accounts.A balance: 1000 → 500  (before: 1000, after: 500)
  LSN 1003: [TxID:42] [UPDATE] accounts.B balance: 200 → 700   (before: 200, after: 700)
  LSN 1004: [TxID:42] [COMMIT]

  The COMMIT log entry is what makes the transaction permanent.
  If we crash before LSN 1004 is written:
    → Recovery finds TxID:42 with no COMMIT entry
    → Uses "before" values to UNDO operations 1002 and 1003
    → Database returns to pre-transaction state

  If we crash after LSN 1004 but before data pages are flushed:
    → Recovery finds TxID:42 with COMMIT entry
    → Uses "after" values to REDO operations 1002 and 1003 if needed
    → Changes are durable even though data pages were not flushed
```

The WAL makes two guarantees simultaneously: **Atomicity** (uncommitted transactions can be rolled back using the "before" values) and **Durability** (committed transactions can be replayed using the "after" values, even if the data pages were not yet written to disk). The same mechanism serves both properties.

### Explicit Rollback: Application-Driven Atomicity

Atomicity applies not only to crashes but also to deliberate `ROLLBACK` calls by the application. If your application detects an error mid-transaction — a validation failure, a business rule violation, an exception thrown by a third-party service — it can call `ROLLBACK` and the database undoes every operation performed since `BEGIN`, as cleanly as if they had never happened.

```go
// Go example: atomicity via explicit rollback on error
func transferFunds(db *sql.DB, fromID, toID string, amount float64) error {
    tx, err := db.Begin()
    if err != nil {
        return err
    }
    // defer Rollback: if Commit is called first, Rollback becomes a no-op.
    // If anything panics or returns early, Rollback fires automatically.
    defer tx.Rollback()

    _, err = tx.Exec(
        "UPDATE accounts SET balance = balance - $1 WHERE id = $2",
        amount, fromID,
    )
    if err != nil {
        return err // defer fires → Rollback → no partial debit
    }

    _, err = tx.Exec(
        "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
        amount, toID,
    )
    if err != nil {
        return err // defer fires → Rollback → debit is undone
    }

    return tx.Commit() // only here does anything become permanent
}
```

The `defer tx.Rollback()` pattern is the idiomatic way to guarantee atomicity in Go application code. It is insurance: if anything goes wrong at any point between `Begin()` and `Commit()`, the rollback fires and the database returns to a clean state.

### Savepoints: Partial Rollback Within a Transaction

PostgreSQL (and most major databases) support **savepoints** — named checkpoints within a transaction that allow you to roll back to a specific point without abandoning the entire transaction. This gives you fine-grained atomicity control for complex, multi-step operations where you want to attempt something and undo only that part if it fails.

```sql
BEGIN;

  INSERT INTO orders (customer_id, total) VALUES (1, 150.00);
  -- order_id 501 is generated

  SAVEPOINT after_order;  ← checkpoint

  INSERT INTO order_items (order_id, product_id, qty) VALUES (501, 42, 2);
  -- This fails: product 42 is discontinued

  ROLLBACK TO SAVEPOINT after_order;  ← undo only the item insert
  -- The order itself (id=501) still exists in the transaction

  INSERT INTO order_items (order_id, product_id, qty) VALUES (501, 17, 2);
  -- This succeeds with an alternative product

COMMIT;  ← order + item (product 17) committed together
```

Savepoints are atomicity within atomicity — they let you structure complex transactions with internal recovery points while preserving the outer transaction's all-or-nothing guarantee.

## Chapter 3: Consistency — Invariants Preserved

### The Contract Between Application and Database

**Consistency** is the property that guarantees a transaction brings the database from one **valid state** to another **valid state**. A valid state is one that satisfies all defined constraints, rules, and invariants — every foreign key points to a real row, every `NOT NULL` column has a value, every `CHECK` constraint is satisfied, every `UNIQUE` constraint holds.

Consistency is subtly different from the other three ACID properties in an important way. Atomicity, Isolation, and Durability are properties that the **database engine** enforces on its own, through WAL, locks, and other mechanisms. Consistency is a **shared responsibility**: the database enforces the constraints you define, but you — the application designer — are responsible for defining the right constraints in the first place.

If you define no constraints, the database can still guarantee atomicity, isolation, and durability. But it cannot guarantee consistency on its own, because it does not know what "valid" means for your domain. You tell it what valid means through your schema design.

```
Consistency = Database Constraints + Application Logic

  Database-enforced consistency rules:
  ├── PRIMARY KEY: every row is uniquely identifiable
  ├── FOREIGN KEY: references always point to real rows
  ├── NOT NULL: critical fields always have values
  ├── UNIQUE: no duplicate values where uniqueness is required
  ├── CHECK: domain-specific value constraints
  └── Triggers: complex invariants expressed as procedural logic

  Application-enforced consistency rules (the database cannot know these):
  ├── Business rules: "an order total must equal the sum of its items"
  ├── Domain invariants: "a user cannot have more than 5 active sessions"
  ├── Cross-system invariants: "inventory count must match warehouse system"
  └── Semantic rules: "a cancelled order cannot be shipped"
```

### What Consistency Actually Means

It is tempting to think of consistency as "data is correct." But that is too vague. More precisely, consistency means that the database's defined invariants are never violated. An invariant is a rule that must always be true, regardless of what operations are performed.

Consider a simple invariant: "an order's `total_amount` must always equal the sum of `quantity × unit_price` across all its line items." This is a genuine business invariant. A database with `total_amount = 150` in the orders table but line items that sum to `142` is in an inconsistent state — not because of data corruption, but because the data violates a rule about how these values must relate.

Ensuring this invariant means either: computing `total_amount` dynamically from the items (never storing it, so it can never be stale), enforcing it with a trigger that recalculates it on every item change, or accepting that the application layer is responsible for keeping them in sync and using transactions to ensure both tables are always updated together.

```
Consistency Example: Account Balance Invariant

  Business Rule: Total of all account balances must not change
                 during a transfer (money is conserved).

  Before transfer:
    Account A: $1,000
    Account B: $200
    System total: $1,200

  During transfer (mid-transaction):
    Account A: $500   ← deducted
    Account B: $200   ← not yet credited
    System total: $700  ← INCONSISTENT (momentarily)

  After COMMIT:
    Account A: $500
    Account B: $700
    System total: $1,200  ← consistent again

  Key insight: Consistency is a guarantee about the START and END states.
  During a transaction, intermediate states may be temporarily inconsistent.
  That is acceptable — the guarantee is that no other transaction ever
  SEES the intermediate state (that is Isolation's job).
  After COMMIT, consistency is fully restored.
```

### Database Constraints as Consistency Enforcers

Let us look at how the database mechanically enforces consistency through its constraint system. Every constraint is a rule that the database checks at the appropriate moment — on INSERT, UPDATE, DELETE, or at the end of the transaction — and refuses to commit if the rule is violated.

```sql
CREATE TABLE accounts (
    id           SERIAL         PRIMARY KEY,
    owner_id     INT            NOT NULL REFERENCES customers(id),  -- FK: owner must exist
    balance      NUMERIC(15,2)  NOT NULL DEFAULT 0,
    account_type VARCHAR(20)    NOT NULL CHECK (account_type IN ('checking', 'savings')),
    -- Invariant: balance cannot go negative for checking accounts
    CONSTRAINT no_negative_checking
        CHECK (account_type != 'checking' OR balance >= 0)
);

CREATE TABLE order_items (
    order_id    INT           NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    product_id  INT           NOT NULL REFERENCES products(id),
    quantity    INT           NOT NULL CHECK (quantity > 0),  -- must be positive
    unit_price  NUMERIC(10,2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);
```

If any transaction tries to insert a negative `quantity`, violate the foreign key by referencing a non-existent customer, or set a checking account balance below zero, the database raises an error and the transaction is rolled back. Consistency is maintained not by hope but by enforcement.

### Deferred Constraints: Consistency at Commit Time

Sometimes enforcing a constraint row-by-row is impossible — you need to complete a sequence of operations before the constraint can be checked. PostgreSQL allows certain constraints to be `DEFERRABLE INITIALLY DEFERRED`, meaning they are checked at `COMMIT` time rather than at each statement.

```sql
-- Example: circular reference problem
-- employees.manager_id references employees.id
-- The CEO has no manager (NULL), but all others must reference a valid employee.
-- When you first insert the CEO row, there are no employees yet,
-- so a non-deferred FK would fail immediately.

ALTER TABLE employees
    ALTER CONSTRAINT employees_manager_id_fkey
    DEFERRABLE INITIALLY DEFERRED;

BEGIN;
  -- Insert CEO with a self-reference (temporarily violates FK)
  INSERT INTO employees (id, name, manager_id) VALUES (1, 'CEO', 1);
  -- FK check is DEFERRED — not checked yet

  -- Insert other employees
  INSERT INTO employees (id, name, manager_id) VALUES (2, 'VP', 1);
  INSERT INTO employees (id, name, manager_id) VALUES (3, 'Manager', 2);

COMMIT;
-- FK constraints are checked HERE at commit time — all pass now
```

Deferred constraints let you perform complex multi-step operations that temporarily violate invariants, as long as the invariants are fully satisfied by the time the transaction commits. The database does not require consistency at every intermediate step — only at the boundaries (before the transaction and after the commit).

## Chapter 4: Isolation — Concurrent Transactions Don't Interfere

### The Most Complex ACID Property

If Atomicity and Durability are about a single transaction's reliability, and Consistency is about data validity, then **Isolation** is about what happens when multiple transactions are running at the same time. It is the most nuanced of the four properties, and the one with the most profound impact on how you write application code.

**Isolation** guarantees that concurrent transactions execute as if they were running serially — one after the other — even though they are actually running simultaneously. Each transaction should be unaware of, and unaffected by, other transactions that are executing concurrently.

Perfect isolation — full serializability — is expensive. Achieving it requires restricting concurrency, which reduces throughput. For this reason, databases offer a spectrum of **isolation levels**, each one a different trade-off between isolation strength and concurrency. Understanding this spectrum requires first understanding the problems that insufficient isolation causes.

### The Three Read Phenomena: What Weak Isolation Allows

The SQL standard defines three phenomena that can occur when isolation is insufficient. Each phenomenon represents a way that one transaction can be disrupted by another concurrent transaction.

**Dirty Read** — A transaction reads data that another transaction has modified but not yet committed. The reading transaction is consuming provisional data that might be rolled back at any moment. If the writing transaction rolls back, the reading transaction has made decisions based on data that never officially existed.

```
Dirty Read Example:

  Time │  Transaction 1 (T1)          │  Transaction 2 (T2)
  ─────┼──────────────────────────────┼─────────────────────────────────
   1   │  BEGIN;                      │
   2   │  UPDATE accounts             │
   3   │    SET balance = 0           │
   4   │    WHERE id = 'A';           │  BEGIN;
   5   │  -- T1 not yet committed     │  SELECT balance FROM accounts
   6   │                              │    WHERE id = 'A';
   7   │                              │  -- T2 reads: 0  ← DIRTY READ
   8   │                              │  -- T2 decides: Account A is broke!
   9   │  ROLLBACK; ← T1 undone       │
  10   │  -- Account A balance = 1000 │  -- T2 made a decision based on
   11  │  -- (restored)              │  -- data that never existed!
```

**Non-Repeatable Read** — A transaction reads the same row twice within the same transaction and gets different values because another transaction committed a change to that row in between the two reads. The same question asked twice gets a different answer within the same transaction.

```
Non-Repeatable Read Example:

  Time │  Transaction 1 (T1)          │  Transaction 2 (T2)
  ─────┼──────────────────────────────┼─────────────────────────────────
   1   │  BEGIN;                      │
   2   │  SELECT balance FROM accounts│
   3   │    WHERE id = 'A';           │
   4   │  -- T1 reads: 1000           │  BEGIN;
   5   │                              │  UPDATE accounts SET balance = 500
   6   │                              │    WHERE id = 'A';
   7   │                              │  COMMIT; ← T2 committed
   8   │  SELECT balance FROM accounts│
   9   │    WHERE id = 'A';           │
  10   │  -- T1 reads: 500  ← DIFFERENT!
  11   │  -- Same query, same transaction, different result.
  12   │  -- T1's world shifted beneath it.
  13   │  COMMIT;                     │
```

**Phantom Read** — A transaction executes a query that returns a set of rows, and when it executes the same query again within the same transaction, a different set of rows appears — because another transaction inserted or deleted rows that match the query's condition in between.

```
Phantom Read Example:

  Time │  Transaction 1 (T1)          │  Transaction 2 (T2)
  ─────┼──────────────────────────────┼─────────────────────────────────
   1   │  BEGIN;                      │
   2   │  SELECT COUNT(*) FROM orders │
   3   │    WHERE status = 'pending'; │
   4   │  -- T1 reads: 5 orders       │  BEGIN;
   5   │                              │  INSERT INTO orders
   6   │                              │    (status) VALUES ('pending');
   7   │                              │  COMMIT;
   8   │  SELECT COUNT(*) FROM orders │
   9   │    WHERE status = 'pending'; │
  10   │  -- T1 reads: 6 orders ← PHANTOM!
  11   │  -- A new row appeared that did not exist before.
  12   │  -- T1 is now working with an inconsistent count.
  13   │  COMMIT;                     │
```

### The Four Isolation Levels

The SQL standard defines four isolation levels, each one preventing a different subset of the read phenomena. Moving up the levels provides stronger guarantees but reduces concurrency and throughput.

```
Isolation Level    │ Dirty Read │ Non-Repeatable │ Phantom Read
───────────────────┼────────────┼────────────────┼─────────────
READ UNCOMMITTED   │  Possible  │    Possible    │   Possible
READ COMMITTED     │ Prevented  │    Possible    │   Possible
REPEATABLE READ    │ Prevented  │   Prevented    │   Possible*
SERIALIZABLE       │ Prevented  │   Prevented    │   Prevented

* PostgreSQL's REPEATABLE READ also prevents phantoms in practice,
  due to its MVCC implementation. Standard SQL says it allows phantoms.
```

**READ UNCOMMITTED** allows dirty reads. It is the weakest level and essentially provides no isolation beyond what you would have without any transaction at all. Almost no serious application uses this level. PostgreSQL does not even implement it — READ UNCOMMITTED behaves like READ COMMITTED in PostgreSQL.

**READ COMMITTED** (the default in PostgreSQL and most databases) prevents dirty reads. Each statement within a transaction sees a fresh snapshot of the database as of the moment that statement begins. This means the data you read is always from committed transactions, never provisional. However, if you execute two identical queries within the same transaction, the second might return different data than the first (non-repeatable reads), because committed changes by other transactions are visible to each new statement.

**REPEATABLE READ** prevents both dirty reads and non-repeatable reads. The transaction takes a snapshot of the database at the moment it begins, and all subsequent reads within that transaction see the world as it was at that snapshot time — even if other transactions commit changes. This is what makes reads "repeatable": the same query returns the same result every time within the transaction.

**SERIALIZABLE** is the strongest level. It prevents all three read phenomena, including phantoms. Transactions are guaranteed to produce results as if they had been executed serially (one after the other), even though they may be running concurrently. This is achieved through predicate locking or optimistic concurrency control with validation.

```sql
-- Setting isolation level in PostgreSQL:
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  -- all reads within this transaction see a consistent snapshot
  -- and the transaction will either complete as if it ran alone
  -- or fail with a serialization failure error that the app must retry
COMMIT;
```

### How Isolation Is Implemented: MVCC

The mechanism behind modern isolation levels in PostgreSQL (and many other databases) is **Multi-Version Concurrency Control (MVCC)**. The key insight of MVCC is that instead of making readers wait for writers and writers wait for readers by using locks on the same rows, the database keeps **multiple versions of each row** simultaneously. Readers see an old version while writers create a new version. Writers never block readers; readers never block writers.

Each transaction is assigned a **transaction ID** when it begins. Each row version is stamped with the transaction ID that created it (`xmin`) and the transaction ID that deleted or updated it (`xmax`). A transaction can see a row version if:

- The `xmin` of that version is committed and older than the transaction's snapshot time, AND
- The `xmax` is either not set (the row has not been deleted) or is not yet committed (the deletion is still in progress from another transaction's perspective)

```
MVCC — Multiple Row Versions:

  accounts table (internal view with version stamps):

  id │ balance │ xmin (created by) │ xmax (deleted by) │ Visible to...
  ───┼─────────┼───────────────────┼───────────────────┼──────────────
  A  │  1000   │  TxID: 10         │  TxID: 42         │ Txns before 42
  A  │   500   │  TxID: 42         │  (none)           │ Txns from 42 onward

  Transaction 41 (started before 42): sees balance = 1000 (old version)
  Transaction 43 (started after 42):  sees balance = 500  (new version)
  Transaction 42 (the writer):        sees its own change = 500

  T41 and T43 can run simultaneously.
  Neither blocks the other.
  Each sees the version appropriate to its snapshot.
```

MVCC is what allows PostgreSQL to offer REPEATABLE READ without requiring the entire database to be locked for the duration of a long transaction. The transaction simply holds on to its snapshot (the transaction IDs that were committed when it began), and all reads use that snapshot to decide which row versions are visible.

The trade-off of MVCC is that old row versions accumulate and must be cleaned up periodically. In PostgreSQL, this is the job of `VACUUM` — the process that marks old row versions as reclaimable space. If VACUUM does not run frequently enough in a write-heavy database, table and index bloat can become a performance problem.

### Write-Write Conflicts and Locking

While MVCC handles read-write concurrency elegantly, **write-write conflicts** — two transactions trying to modify the same row — still require traditional locking. When Transaction 1 updates a row, it takes an exclusive lock on that row. Transaction 2, attempting to update the same row, must wait for Transaction 1 to commit or roll back before it can proceed.

```
Write-Write Conflict: One must wait.

  T1: UPDATE accounts SET balance = 500 WHERE id = 'A';
      → Takes exclusive row lock on Account A

  T2: UPDATE accounts SET balance = 900 WHERE id = 'A';
      → Tries to take exclusive row lock on Account A
      → Account A is locked by T1 — T2 WAITS

  T1: COMMIT;  → lock released
  T2: → now acquires lock, sees T1's committed value (500)
      → executes: SET balance = 900
  T2: COMMIT;

  Result: Account A = 900. No data corruption. One transaction waited.
```

At SERIALIZABLE level, PostgreSQL uses **Serializable Snapshot Isolation (SSI)** — a technique that tracks dependencies between concurrent transactions and detects when a set of concurrent transactions could not have produced their results if they had run serially. When such a conflict is detected, one transaction is rolled back with a `ERROR: could not serialize access due to concurrent update` message, and the application must retry.

### Deadlocks: When Two Transactions Wait for Each Other

A **deadlock** occurs when two (or more) transactions are each waiting for the other to release a lock, creating a cycle of dependency that neither can break. Without intervention, both transactions would wait forever.

```
Deadlock Example:

  T1 holds lock on Account A, waiting for Account B
  T2 holds lock on Account B, waiting for Account A

  Time │  Transaction 1               │  Transaction 2
  ─────┼──────────────────────────────┼───────────────────────────────
   1   │  BEGIN;                      │  BEGIN;
   2   │  UPDATE accounts             │
   3   │    SET balance = balance - 500
   4   │    WHERE id = 'A';  ← LOCKS A│
   5   │                              │  UPDATE accounts
   6   │                              │    SET balance = balance - 200
   7   │                              │    WHERE id = 'B';  ← LOCKS B
   8   │  UPDATE accounts             │
   9   │    SET balance = balance + 500
  10   │    WHERE id = 'B';  ← WAITS  │  UPDATE accounts
  11   │    (B is locked by T2)       │    SET balance = balance + 200
  12   │                              │    WHERE id = 'A'; ← WAITS
  13   │                              │    (A is locked by T1)
  14   │  ← DEADLOCK: T1 and T2 wait for each other forever

  Database detects the cycle and kills one transaction:
  ERROR: deadlock detected — T2 is rolled back.
  T1 proceeds and commits successfully.
  T2's application must retry.
```

Databases detect deadlocks by periodically looking for cycles in the lock dependency graph and aborting one of the involved transactions (typically the "youngest" or "cheapest" one). The application receives an error and is expected to retry. The best defense against deadlocks in application code is to always acquire locks in a consistent order — if every transaction always locks Account A before Account B, the deadlock above can never occur.

## Chapter 5: Durability — Committed Data Survives Crashes

### The Permanence Guarantee

**Durability** is the property that guarantees once a transaction has been committed, it remains committed — permanently — regardless of what happens afterward. Power failures, operating system crashes, hardware failures, even disk corruption (within reasonable limits) cannot cause a committed transaction to disappear. When the database tells your application "your transaction was committed," it is making a solemn promise: that data is safe.

Durability is the hardest property to implement correctly, because it must survive the boundary between volatile memory (RAM, which loses all content on power loss) and persistent storage (disk, which retains content across power cycles). Without careful engineering, a "committed" transaction that was in RAM at the moment of a power failure would simply evaporate.

### The WAL Makes Durability Possible

The Write-Ahead Log, which we introduced in the Atomicity chapter as the mechanism for rollback, is also the mechanism for durability. Recall the WAL principle: before any data page is modified on disk, the change is first written to the sequential WAL log and the log is flushed to disk (using `fsync` — a system call that guarantees the data reaches the physical storage medium, not just the OS buffer cache).

The crucial moment is the **fsync of the COMMIT record**. When a transaction commits, PostgreSQL writes a COMMIT record to the WAL and calls `fsync` before returning "success" to the application. Once that `fsync` returns, the COMMIT record is physically on disk. Even if the power fails the next millisecond, the COMMIT record survives. On restart, the recovery process reads the WAL, finds the COMMIT record, and replays any changes that were not yet reflected in the data files.

```
Durability Through WAL — The Commit Protocol:

  Application calls COMMIT;
  │
  ├── 1. Database writes COMMIT record to WAL buffer in memory
  │
  ├── 2. Database calls fsync() on the WAL file
  │       → OS flushes WAL buffer to disk
  │       → Physical storage medium has the COMMIT record
  │       → This is the durability point
  │
  ├── 3. Database returns "SUCCESS" to the application
  │       → Application knows the data is permanent
  │
  └── 4. Data pages are updated lazily (may still be in memory)
         → That's okay — WAL can replay them on crash recovery

  If power fails between step 2 and step 4:
  → WAL has COMMIT record (on disk, safe)
  → Data pages may be stale (not yet written)
  → Recovery REPLAYS the WAL to bring data pages up to date
  → Data is durable

  If power fails before step 2:
  → No COMMIT record in WAL
  → Transaction is treated as uncommitted (rolled back on recovery)
  → Atomicity kicks in — no partial changes remain
```

### fsync and the Danger of Disabling It

The `fsync` call is what separates genuine durability from an illusion of durability. Without `fsync`, the OS may buffer WAL writes in its own page cache and not actually write them to the physical disk for seconds or minutes. If the OS crashes (not just the application), that buffer is lost — along with your "committed" transactions.

PostgreSQL's `fsync` setting is one of the most dangerous configuration parameters in the entire system. Setting `fsync = off` disables the fsync calls, making the database dramatically faster (writes to sequential memory instead of disk), but at the cost of complete durability. If the OS crashes with `fsync = off`, the database can end up in a corrupted state — not just losing recent commits, but potentially with partially written pages that corrupt the entire database cluster. This setting should never be disabled in production.

```
fsync = on  (default, required for production):
  → Every COMMIT is physically on disk before returning success
  → ~2,000–10,000 transactions/second (depends on disk hardware)
  → Complete durability guarantee

fsync = off (DANGEROUS, testing only):
  → COMMITs are in OS buffer — not physically on disk
  → ~50,000–200,000 transactions/second
  → If OS crashes: database corruption, data loss
  → NEVER use in production

synchronous_commit = off (middle ground, sometimes acceptable):
  → COMMIT returns before WAL is flushed to disk
  → Recent transactions (up to ~100ms) may be lost on OS crash
  → But database is never CORRUPTED (only loses recent data)
  → Acceptable for high-throughput logging where losing a few
    recent writes is tolerable (not for financial transactions)
```

### Replication as Additional Durability

Single-server durability — the WAL on one machine's disk — protects against power failures and OS crashes. But it does not protect against disk hardware failure (a dying hard drive can lose all data including the WAL). For protection against hardware failure, databases use **replication** — continuously streaming the WAL to one or more standby servers.

In PostgreSQL's streaming replication, the primary server sends WAL records to replica servers in real time. With **synchronous replication**, the primary waits for at least one replica to confirm it has received and written the WAL record before returning "success" to the application. This means the transaction is durable on two separate physical machines. Even if the primary's disk fails completely, the replica has all the committed data.

```
Synchronous Replication — Durability Across Machines:

  Application: COMMIT;
  │
  Primary DB:
  ├── Write COMMIT record to local WAL
  ├── Stream WAL record to Replica
  │       Replica: write WAL record to its own disk
  │       Replica: acknowledge receipt → PRIMARY GETS ACK
  ├── fsync local WAL  (AND/OR rely on replica's ACK)
  └── Return SUCCESS to application

  Now the COMMIT is on TWO separate disks.
  Primary disk failure → Replica has all data → Promote replica.
  Zero data loss. True durability.

  Asynchronous replication (common for read replicas):
  → Primary commits without waiting for replica
  → Small window of data loss if primary fails before replica catches up
  → Acceptable for read replicas; not for HA failover
```

### Checkpoints: Periodically Catching Data Pages Up to the WAL

The WAL grows continuously as transactions commit. If data pages are never updated on disk, eventually the WAL would be enormous and recovery would take an impractically long time (replaying millions of log entries). **Checkpoints** solve this by periodically flushing all dirty (in-memory-modified) data pages to disk.

At a checkpoint:

1. All dirty data pages in memory are written to their on-disk locations.
2. A checkpoint record is written to the WAL noting the position.
3. On recovery after a crash, the database only needs to replay WAL entries from the most recent checkpoint — not from the beginning of time.

```
Checkpoints and Recovery Time:

  WAL:  [Chkpt1]─────[Chkpt2]─────[Chkpt3]──[CRASH]
                              ↑
                         Last checkpoint

  Recovery only needs to replay WAL from [Chkpt3] onward.
  Earlier entries are irrelevant — their data pages are already on disk.

  checkpoint_completion_target: how much of the checkpoint_timeout
  to spread the checkpoint work over (avoids I/O spikes).

  Tuning trade-off:
  More frequent checkpoints → faster recovery after crash
                           → more I/O during normal operation
  Less frequent checkpoints → less I/O normally
                           → longer recovery time after crash
```

## Chapter 6: ACID Together — The Unified Picture

### How the Four Properties Interlock

ACID is not four independent features that happen to share an acronym. The four properties form an interlocking system where each one depends on the others to deliver a coherent guarantee. Removing any one of them breaks the whole.

```
ACID as an Interlocking System:

  ┌─────────────────────────────────────────────────────────────┐
  │                      A TRANSACTION                          │
  │                                                             │
  │  ATOMICITY ensures:                                         │
  │  The transaction either fully commits or fully rolls back.  │
  │  No partial effects survive.                                │
  │         │                                                   │
  │         ▼                                                   │
  │  CONSISTENCY ensures:                                       │
  │  The committed state satisfies all defined invariants.      │
  │  (Atomicity makes consistency possible — if partial commits │
  │   were allowed, consistency would be uncheckable)           │
  │         │                                                   │
  │         ▼                                                   │
  │  ISOLATION ensures:                                         │
  │  The committed state is not contaminated by concurrent      │
  │  transactions' intermediate states.                         │
  │  (Consistency requires isolation — seeing another           │
  │   transaction's partial state could violate invariants)     │
  │         │                                                   │
  │         ▼                                                   │
  │  DURABILITY ensures:                                        │
  │  The committed state survives permanently.                  │
  │  (All three other properties are meaningless if the         │
  │   committed state can evaporate on a crash)                 │
  └─────────────────────────────────────────────────────────────┘

  Each property is a prerequisite for the next to matter.
```

### The Cost of ACID and When to Accept Less

ACID properties are not free. Each one carries a performance cost:

**Atomicity** requires the WAL, which adds sequential I/O to every write operation. Without WAL, writes go directly to data pages — faster, but no rollback capability.

**Consistency** requires constraint checking, which adds CPU overhead on every write. Complex constraints (triggers, deferred checks) add more.

**Isolation** requires MVCC (storing multiple row versions, running VACUUM), lock management, deadlock detection, and at SERIALIZABLE level, serialization conflict tracking. All of this reduces concurrency and adds overhead.

**Durability** requires `fsync` — the most expensive operation. `fsync` on a spinning hard disk can take 5–10 milliseconds, limiting transactions to a few hundred per second without batching. Even on SSDs, `fsync` limits throughput.

This is why NoSQL databases and some new SQL databases offer **configurable ACID guarantees** — letting you trade off some properties for performance in contexts where the trade-off is acceptable.

```
ACID Trade-offs in Practice:

  Relaxing Durability (synchronous_commit = off):
  → Risk: lose up to ~100ms of recent commits on OS crash
  → Gain: 5–10× higher write throughput
  → Acceptable for: event logging, telemetry, metrics collection

  Relaxing Isolation (READ COMMITTED instead of SERIALIZABLE):
  → Risk: non-repeatable reads, phantom reads
  → Gain: significantly higher concurrency
  → Acceptable for: most web application reads that are not
    part of a multi-step decision process

  Relaxing Consistency (application-level validation only):
  → Risk: invalid states if application code has bugs
  → Gain: schema flexibility, faster writes
  → Acceptable for: document stores, event sourcing, prototype apps
    where schema is not yet stable

  NEVER acceptable to relax:
  → Atomicity + Durability for financial transactions
  → Isolation for inventory decrement (phantom reads cause overselling)
  → Consistency for referential integrity in relational systems
```

### BASE: The Alternative Philosophy

In distributed systems, particularly large-scale NoSQL systems, the ACID philosophy is sometimes replaced by **BASE**: **B**asically **A**vailable, **S**oft state, **E**ventually consistent. BASE is not a formalized standard like ACID — it is a rough description of the design philosophy of systems that prioritize availability over consistency.

A BASE system says: "We will always respond to requests (basically available), even if our data is temporarily inconsistent across nodes (soft state), and given enough time, all nodes will converge to the same value (eventual consistency)." DNS is a classic example — a DNS record update does not immediately propagate to every server in the world, but eventually all servers agree on the current value.

BASE is not simply "bad ACID." It is a different trade-off, appropriate for different problems:

```
ACID vs BASE:

  ACID systems (PostgreSQL, MySQL, SQL Server):
  → Strong consistency guarantees
  → Transactions succeed or fail atomically
  → All users see the same data at the same time
  → Better for: financial systems, inventory, anything requiring
    strong correctness guarantees

  BASE systems (Cassandra, DynamoDB in eventual consistency mode):
  → High availability: system responds even during network partitions
  → Writes always succeed (conflict resolution happens later)
  → Users may temporarily see stale or conflicting data
  → Better for: social media feeds, shopping cart additions, DNS,
    any system where temporary inconsistency is tolerable and
    availability is paramount

  The choice between ACID and BASE is NOT about which is "better."
  It is about which trade-off matches your domain's requirements.
  A bank transfer demands ACID. A "likes" counter on a social post
  can tolerate BASE.
```

## Chapter 7: ACID in Your Application Code

### Writing ACID-Aware Application Logic

Understanding ACID at the conceptual level is only half the skill. The other half is writing application code that works correctly with ACID guarantees — and that means structuring your transactions thoughtfully.

**Keep transactions short.** A transaction holds locks for its entire duration. A long-running transaction (one that takes seconds or minutes to complete) holds locks for that entire time, blocking other transactions from accessing the same rows. Keep the operations inside a transaction to only what must be atomic. Do not make external API calls inside a transaction — if the API hangs, your transaction hangs, and the locks hang with it.

```go
// BAD: External API call inside transaction
func processOrder(db *sql.DB, orderID int) error {
    tx, _ := db.Begin()
    defer tx.Rollback()

    tx.Exec("UPDATE orders SET status = 'processing' WHERE id = $1", orderID)
    // This API call might take 5 seconds. Your UPDATE lock hangs for 5 seconds.
    result := externalPaymentAPI.Charge(orderID) // ← NEVER do this inside a tx
    tx.Exec("UPDATE orders SET status = 'paid' WHERE id = $1", orderID)

    return tx.Commit()
}

// GOOD: Do external work outside the transaction
func processOrder(db *sql.DB, orderID int) error {
    // Step 1: Mark as processing (short transaction)
    if err := markProcessing(db, orderID); err != nil {
        return err
    }

    // Step 2: External call — outside any transaction
    result, err := externalPaymentAPI.Charge(orderID)
    if err != nil {
        markFailed(db, orderID) // another short transaction
        return err
    }

    // Step 3: Mark as paid (short transaction)
    return markPaid(db, orderID, result.TransactionID)
}
```

**Choose the right isolation level for each operation.** Not every operation needs SERIALIZABLE isolation. A read-only report query can safely use READ COMMITTED. A read-modify-write operation that must be exact (like decrementing inventory) needs at least REPEATABLE READ or explicit `SELECT FOR UPDATE` locking.

```sql
-- SELECT FOR UPDATE: explicit row-level locking within a transaction
-- Use when you read a value and need to ensure nobody changes it
-- before you write back.

BEGIN;
  SELECT stock_quantity FROM products WHERE id = 42
  FOR UPDATE;  -- ← takes an exclusive lock on this row RIGHT NOW

  -- Now we know nobody else can update this row until we commit.
  -- We can safely decrement without race conditions.
  UPDATE products
    SET stock_quantity = stock_quantity - 1
    WHERE id = 42 AND stock_quantity > 0;

COMMIT;
```

**Handle serialization failures with retries.** At SERIALIZABLE isolation level, PostgreSQL may abort a transaction and return `ERROR: could not serialize access due to concurrent update`. This is not a bug — it is the database correctly detecting a conflict. Your application must be prepared to retry the entire transaction from scratch.

```go
// Retry loop for serializable transactions
func withSerializableRetry(db *sql.DB, fn func(*sql.Tx) error) error {
    for attempt := 0; attempt < 5; attempt++ {
        tx, err := db.BeginTx(ctx, &sql.TxOptions{
            Isolation: sql.LevelSerializable,
        })
        if err != nil {
            return err
        }

        err = fn(tx)
        if err != nil {
            tx.Rollback()
            // Check if it's a serialization failure (PostgreSQL error code 40001)
            if isSerializationFailure(err) {
                time.Sleep(time.Duration(attempt*attempt) * time.Millisecond) // backoff
                continue // retry
            }
            return err // non-retryable error
        }

        if err = tx.Commit(); err != nil {
            if isSerializationFailure(err) {
                continue // retry
            }
            return err
        }
        return nil // success
    }
    return errors.New("too many serialization failures")
}
```

## Epilogue: The Promise and the Price

ACID properties represent a promise — a contract between the database engine and every application that depends on it. When you write `COMMIT;` and the database responds with success, you are entitled to trust that the data is safe, that the constraints are satisfied, that concurrent transactions did not corrupt your view of the world, and that a power failure in the next millisecond cannot erase what you just wrote.

This promise is not cheap. It requires the Write-Ahead Log, `fsync`, MVCC, lock management, deadlock detection, and careful recovery code. Every committed transaction is the product of significant engineering work, invisible to the application.

Understanding that work — knowing why the WAL exists, what MVCC does, why `fsync` matters, what isolation levels trade off — makes you a more capable engineer. You can look at a performance problem and know whether it is an fsync bottleneck (durability cost), a lock contention problem (isolation cost), or a constraint checking overhead (consistency cost). You can make informed decisions about which properties to relax in which contexts, and which to hold sacred.

The deepest lesson of ACID is this: correctness and performance are always in tension, and ACID is one of the most carefully engineered resolutions to that tension in all of software engineering. When you understand the mechanisms behind the four letters, you understand not just a database feature, but one of the foundational ideas of building reliable systems.
