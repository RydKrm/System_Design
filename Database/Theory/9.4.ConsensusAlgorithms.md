## 1. Why Consensus is Hard — The Setup

Before we can appreciate the elegance of these algorithms, you need to feel the weight of the problem they solve. So let me paint you a picture.

Imagine you are managing a bank. You have three database servers — let us call them Server A, Server B, and Server C — and they all hold a copy of the account balance for a customer. A client sends a request: "Transfer $500 from account X to account Y." For this to work correctly, all three servers must agree that this transaction happened, in what order it happened relative to other transactions, and what the resulting balances are. If even one server disagrees, your data is corrupted.

Now introduce reality. Networks drop packets. Servers crash mid-operation. A server might be slow and appear dead but then come back to life. A server might even receive the same message twice. Two clients might send conflicting requests at the exact same millisecond. How do you make all three servers agree on what happened, in what order, when the very act of communicating between them is unreliable?

This is the **consensus problem**, and it has a formal definition: a group of nodes in a distributed system must agree on a single value (or a sequence of values), even in the presence of failures, and the following three properties must hold simultaneously.

```
┌────────────────────────────────────────────────────────────────┐
│               THE THREE PROPERTIES OF CONSENSUS                │
├────────────────┬───────────────────────────────────────────────┤
│  AGREEMENT     │ All correct (non-crashed) nodes decide on     │
│                │ the same value. No two correct nodes can      │
│                │ decide differently.                           │
├────────────────┼───────────────────────────────────────────────┤
│  VALIDITY      │ The decided value must be a value that was    │
│                │ actually proposed by some node. The system    │
│                │ cannot invent a value out of thin air.        │
├────────────────┼───────────────────────────────────────────────┤
│  TERMINATION   │ Every correct node eventually decides on some │
│                │ value. The system does not get stuck forever. │
└────────────────┴───────────────────────────────────────────────┘
```

There is a famous theoretical result called the **FLP Impossibility Theorem** (Fischer, Lynch, Paterson, 1985) which proves that no deterministic algorithm can guarantee all three properties simultaneously in an asynchronous network where even one node can fail. This sounds like a dead end, but in practice, systems get around it by introducing a small amount of timing assumption — essentially saying "a leader is considered dead if it does not respond within a timeout" — which makes the problem solvable in the real world.

The other foundational concept you must understand before we proceed is the **quorum**. In a group of N nodes, a quorum is any majority — that is, any group of more than half the nodes. The magic of a quorum is that any two quorums share at least one node in common. This is the mathematical bedrock upon which every consensus algorithm is built. If two different decisions require a quorum to agree, and any two quorums overlap, then both decisions must have at least one node in common, which prevents contradictory decisions from being committed.

```
Example with 5 nodes: A, B, C, D, E
Quorum size = 3 (majority of 5)

Quorum 1: {A, B, C}
Quorum 2: {C, D, E}
Overlap:  {C}   ← Node C is in BOTH quorums

This overlap node is the "witness" that connects both groups
and prevents two contradictory values from being decided.

┌───┐  ┌───┐  ┌───┐  ┌───┐  ┌───┐
│ A │  │ B │  │ C │  │ D │  │ E │
└───┘  └───┘  └─┬─┘  └───┘  └───┘
                 │
            Overlap node
       (appears in every quorum pair)
```

With this foundation in place, let us study the first and most famous consensus algorithm ever devised.

## 2. Paxos — The Original Algorithm

### 2.1 Basic Paxos

Paxos was invented by Leslie Lamport and first described in a paper he submitted in 1989, though it was so unusual that reviewers rejected it, and it was not published until 1998 under the title "The Part-Time Parliament." Lamport framed it as an analogy about a parliament on a Greek island whose members kept leaving and returning, trying to pass laws consistently. The algorithm is brilliant, foundational, and famously difficult to understand. Lamport himself later wrote a follow-up paper called "Paxos Made Simple," which is an extraordinary piece of literature — it derives the entire algorithm from first principles.

Let us build the understanding from scratch, the way a DBA mentor would explain it to an intern over coffee.

The core question Paxos asks is: given a set of nodes that can all propose values, how do we get them to agree on exactly one value that will never change? Basic Paxos solves this for a single decision — agreeing on one value. Think of it as a single vote in a parliament.

There are three roles in Paxos, and a single node can play multiple roles simultaneously. The **Proposer** is the node that initiates the process and champions a particular value. The **Acceptor** is the node that receives proposals and votes on them. The **Learner** is the node that learns the final decided value and can act on it.

Paxos operates in two distinct phases. Understanding these two phases is everything.

**Phase 1 — Prepare and Promise.** The Proposer begins by choosing a unique, monotonically increasing number called a **proposal number** (sometimes called a ballot number). This number is crucial. The Proposer sends a `Prepare(n)` message to a quorum of Acceptors, where `n` is its proposal number. This message says, in essence: "I am about to propose something with number `n`. I need you to promise me that you will not accept any proposal with a number less than `n`."

Each Acceptor, upon receiving a `Prepare(n)` message, checks its own history. If the Acceptor has never made a promise with a number greater than or equal to `n`, it responds with a `Promise` message. This Promise does two things: it commits the Acceptor to ignoring any future `Prepare` messages with lower numbers, and it also tells the Proposer about the highest-numbered proposal the Acceptor has already accepted, if any. That second piece of information is critical and is what makes Paxos safe.

```
PHASE 1 — PREPARE / PROMISE:

Proposer                 Acceptors (A, B, C)
   │                         │    │    │
   │── Prepare(n=5) ─────────►│    │    │
   │── Prepare(n=5) ──────────────►│    │
   │── Prepare(n=5) ───────────────────►│
   │                         │    │    │
   │◄─ Promise(n=5,          │    │    │
   │   accepted=null) ───────│    │    │
   │◄─ Promise(n=5,          │    │    │
   │   accepted={n=3,v=X})───────►│    │  ← B already accepted (3, X)!
   │◄─ Promise(n=5,          │    │    │
   │   accepted=null) ───────────────-►│
   │                         │    │    │
   │  Proposer now knows:              │
   │  - Quorum (A, B, C) promised      │
   │  - Highest prior accepted value   │
   │    is X (from B, proposal n=3)    │
   │  - Proposer MUST propose X, not   │
   │    its own value!                 │
```

Now here is the most important rule in all of Paxos, and the one that makes it correct: **if any Acceptor reports back that it has already accepted a value, the Proposer must abandon its own proposed value and instead propose the value associated with the highest proposal number reported.** This rule is what prevents two conflicting values from ever being decided. If a value was previously accepted by a quorum (or even partially accepted), the new Proposer inherits it and ensures the same value wins again.

**Phase 2 — Accept and Learn.** Once the Proposer has received Promises from a quorum of Acceptors, it proceeds to Phase 2. It sends an `Accept(n, v)` message to that same quorum, where `v` is either the value it learned from Phase 1 (if any Acceptor had previously accepted something) or its own value (if the slate was clean). This message says: "I hereby formally propose value `v` with proposal number `n`. Please accept it."

Each Acceptor, upon receiving `Accept(n, v)`, checks whether it has since made a Promise to a higher-numbered proposal. If not, it accepts the proposal and responds with an `Accepted(n, v)` message. If a quorum of Acceptors respond with `Accepted`, the value `v` is considered **chosen** — it has been decided by consensus. The Proposer then notifies the Learners of the decided value.

```
PHASE 2 — ACCEPT / CHOSEN:

Proposer                 Acceptors (A, B, C)
   │                         │    │    │
   │  (Must propose X because │    │    │
   │   B previously accepted  │    │    │
   │   X with n=3)            │    │    │
   │── Accept(n=5, v=X) ──────►│    │    │
   │── Accept(n=5, v=X) ───────────►│    │
   │── Accept(n=5, v=X) ────────────────►│
   │                         │    │    │
   │◄─ Accepted(n=5, v=X) ───│    │    │
   │◄─ Accepted(n=5, v=X) ────────►│    │
   │◄─ Accepted(n=5, v=X) ──────────────►│
   │                         │    │    │
   │  Quorum accepted! Value X is CHOSEN ✓
   │
   │── Notify Learners: "Value X is decided" ──────────────────►
```

The elegance of Paxos lies entirely in Phase 1. By forcing a Proposer to first survey the landscape of prior acceptances before proposing, the algorithm ensures that if any value was already on its way to being decided, it stays on that path. No new Proposer can derail a previously committed decision.

However, Basic Paxos has a significant limitation: it only decides one value. Real systems need to decide an entire sequence of values — a log of commands. This is where Multi-Paxos comes in.

---

### 2.2 Multi-Paxos

A database does not need to agree on one thing; it needs to agree on every single operation in its history, in order. "Insert row X. Then update row Y. Then delete row Z." This is a **replicated log** — an ordered sequence of commands that every node must agree upon and execute identically, so that every node ends up in the same state. If you can replicate a log perfectly, you can replicate any state machine. This insight is the foundation of all modern distributed databases.

Multi-Paxos extends Basic Paxos to decide a sequence of values efficiently. The naive approach would be to run a full Basic Paxos instance (both phases) for every single log entry. This would be catastrophically slow — every entry would require two network round trips. Multi-Paxos optimises this with one elegant observation: **if a single Proposer wins Phase 1 for a high enough proposal number, it can act as the leader for all subsequent Phase 2 rounds without repeating Phase 1.**

```
NAIVE APPROACH (Full Paxos per entry — very slow):

Log Entry 1:  [Phase 1 (2 round trips)] + [Phase 2 (1 round trip)]  = 3 RTT
Log Entry 2:  [Phase 1 (2 round trips)] + [Phase 2 (1 round trip)]  = 3 RTT
Log Entry 3:  [Phase 1 (2 round trips)] + [Phase 2 (1 round trip)]  = 3 RTT
...

MULTI-PAXOS APPROACH (Leader elected once):

Election:     [Phase 1 — ONE TIME ONLY]                             = 2 RTT
Log Entry 1:  [Phase 2 only]                                        = 1 RTT
Log Entry 2:  [Phase 2 only]                                        = 1 RTT
Log Entry 3:  [Phase 2 only]                                        = 1 RTT
...

As long as the leader stays alive, every subsequent log entry
costs just ONE round trip!
```

The stable leader in Multi-Paxos is called the **Distinguished Proposer**. Once elected, it can process client requests directly and immediately append entries to the log by broadcasting `Accept` messages — skipping Phase 1 entirely. The other nodes act as Acceptors and apply entries to their logs as they are accepted by a quorum. If the leader crashes, a new node runs Phase 1 to elect itself as the new leader, and the process continues.

Multi-Paxos sounds clean in theory, but implementing it correctly is notoriously difficult. There are gaps in Lamport's description that practitioners must fill in: How do you handle leader changes and ensure the new leader learns about all previously committed entries? How do you ensure the log has no gaps? How do you handle the transition period when the old leader and new leader are both alive and trying to process entries simultaneously? These gaps are why Paxos, despite being the theoretical foundation of consensus, is rarely implemented exactly as described. Most production systems implement something closer to Raft, which we will study next.

## 3. Raft — Consensus Made Understandable

Raft was published in 2014 by Diego Ongaro and John Ousterhout in a paper titled "In Search of an Understandable Consensus Algorithm." The paper's opening line captures its philosophy perfectly: "Paxos is notoriously difficult to understand." Raft was designed from the ground up with understandability as a first-class goal. It makes strong design choices that Paxos leaves unspecified, decomposing the problem into three relatively independent sub-problems: **leader election, log replication, and safety.**

The central architectural decision in Raft is that there is always exactly one leader at a time, and all client requests go through this leader. The leader is the single source of truth about what goes into the log and in what order. This is a significant constraint compared to Paxos (which, in theory, allows any node to propose values), but it makes the system dramatically easier to understand and implement correctly.

Time in Raft is divided into **terms**, which are logical epochs. Each term begins with an election. If the election succeeds, one leader serves for the rest of the term. If the election fails (because no candidate wins a majority), a new term begins immediately with another election. Terms are numbered with monotonically increasing integers, and every node knows the current term number. If a node ever receives a message from a node claiming a higher term, it immediately updates its own term and reverts to a follower state. This term mechanism is Raft's way of detecting stale leaders.

```
RAFT TERMS — The Timeline:

  Term 1     Term 2    Term 3          Term 4
┌─────────┬──────────┬──────────────┬───────────────────────► Time
│ Leader  │ Election │   Leader     │       Leader
│ Node A  │ fails    │   Node B     │       Node C
│ serves  │ (split   │   serves     │       serves
│         │  vote)   │              │
└─────────┴──────────┴──────────────┴───────────────────────

Each node maintains its current term number.
When a new leader is elected, it serves for that term.
If a leader receives a message with a higher term number,
it immediately steps down.
```

### 3.1 Leader Election

Every node in Raft begins life as a **Follower**. Followers are passive — they receive messages from leaders and candidates but do not initiate anything on their own. A follower expects to receive periodic **heartbeat** messages from the current leader. These heartbeat messages are essentially empty log entries sent at regular intervals (often every 150–300 milliseconds) to signal "I am alive, I am still the leader, do not start an election."

If a follower does not hear from the leader within a timeout period (called the **election timeout**, typically randomised between 150 and 300 milliseconds), it concludes that the leader has crashed. The follower then transitions to the **Candidate** state and begins an election. Randomising the election timeout is a beautiful trick: it ensures that different nodes' timeouts expire at different times, so typically only one node becomes a candidate first, avoiding split votes.

The candidate increments its term number by one, votes for itself, and sends `RequestVote` messages to all other nodes. Each `RequestVote` message includes the candidate's current term and information about the last entry in the candidate's log. A follower will grant its vote to a candidate if and only if two conditions are satisfied: first, the candidate's term number must be at least as large as the follower's current term; second, the candidate's log must be at least as up-to-date as the follower's log. This second condition is the key safety mechanism — it ensures that only a candidate with a sufficiently complete log can become leader.

```
LEADER ELECTION FLOW:

Initial State (Leader A is running):
┌──────────┐     heartbeat      ┌──────────┐     heartbeat      ┌──────────┐
│  Node A  │ ──────────────────►│  Node B  │                    │  Node C  │
│ (Leader) │◄────────────────── │(Follower)│                    │(Follower)│
└──────────┘                    └──────────┘                    └──────────┘

Node A crashes. Heartbeat timeout expires on B and C.
Node B's randomised timeout expires FIRST:

Step 1: B becomes Candidate (Term 2)
┌──────────┐                    ┌──────────┐                    ┌──────────┐
│  Node A  │                    │  Node B  │ RequestVote(T=2)   │  Node C  │
│ (Crashed)│                    │(Candidate)│──────────────────►│(Follower)│
└──────────┘                    └──────────┘                    └──────────┘

Step 2: C responds with VoteGranted (B's log is up to date)
Step 3: B has votes from itself + C = MAJORITY (2/3)
Step 4: B becomes Leader for Term 2

┌──────────┐     heartbeat      ┌──────────┐     heartbeat      ┌──────────┐
│  Node A  │                    │  Node B  │ ──────────────────►│  Node C  │
│ (Crashed)│                    │ (Leader) │◄────────────────── │(Follower)│
└──────────┘                    └──────────┘                    └──────────┘
```

If a candidate receives votes from a majority of the cluster, it wins the election and becomes the leader for that term. If two candidates tie and split the vote (a "split vote"), the term ends without a leader, and a new election begins with a new, higher term. Because election timeouts are randomised, this situation is temporary — one node will always time out first and win the next election before the others even start.

### 3.2 Log Replication

Once a leader is elected, it begins accepting client requests and replicating them to the follower nodes. This is the core job of the leader: to maintain a consistent, ordered log of operations across all nodes in the cluster.

When a client sends a request to the leader — for instance, "Set x = 10" — the leader appends this command to its own log as a new entry, tagged with the current term number. The entry starts in a **tentative** (uncommitted) state. The leader then sends `AppendEntries` messages to all followers in parallel, carrying the new log entry along with some crucial metadata: the index and term of the entry that immediately precedes the new one. This metadata is what allows followers to verify that their log is consistent with the leader's log up to that point.

```
LOG REPLICATION — Normal Operation:

Client Request: "Set x = 10"

        Leader (Node B) Log:             Follower Logs:
        ┌───┬───┬───┬──────┐             Node C:  ┌───┬───┬───┐
Index:  │ 1 │ 2 │ 3 │  4   │             Index:   │ 1 │ 2 │ 3 │  (behind by 1)
Term:   │ 1 │ 1 │ 2 │  2   │             Term:    │ 1 │ 1 │ 2 │
Cmd:    │set│del│upd│set   │             Cmd:     │set│del│upd│
        │x=1│ y │ z │x=10  │             └───┴───┴───┘
        └───┴───┴───┴──────┘
               │  ↑ New entry, NOT yet committed
               │
               │  AppendEntries(prevIndex=3, prevTerm=2, entry=[idx=4,t=2,set x=10])
               ├──────────────────────────────────────────────────► Node C
               ├──────────────────────────────────────────────────► Node D (if exists)
               │
               │  Node C checks: "Do I have entry at index 3 with term 2?" YES.
               │  Node C appends entry 4.
               │  Node C responds: Success
               │
               │  Leader receives Success from quorum (itself + C)
               │  Leader marks entry 4 as COMMITTED
               │
               ▼
        ┌───┬───┬───┬──────┐
Index:  │ 1 │ 2 │ 3 │  4   │  ← Entry committed (applied to state machine)
        │   │   │   │  ✓   │
        └───┴───┴───┴──────┘
               │
               │  Next AppendEntries heartbeat carries
               │  updated commitIndex, telling followers
               │  they can now also commit entry 4.
```

A follower, upon receiving an `AppendEntries` message, performs a **consistency check**: it verifies that its own log contains an entry at the stated previous index with the stated previous term. If the check passes, the follower appends the new entry and replies with success. If the check fails — meaning the follower's log is inconsistent with the leader's — the follower rejects the message and replies with failure, and the leader will then back up and try sending the entry at an earlier index, probing until it finds the point where the logs diverge and then replaying all subsequent entries. This retry mechanism ensures that followers eventually converge to match the leader's log exactly.

Once the leader has received success responses from a majority of nodes (including itself), the log entry is considered **committed**. The leader applies the committed command to its local state machine, returns the result to the client, and subsequently informs followers of the new commit index via the next heartbeat, allowing them to apply the entry to their own state machines. The commit index only moves forward — it never goes backward — which is why Raft guarantees that committed entries are never lost.

### 3.3 Safety

The safety property in Raft is the guarantee that no two nodes can ever commit different values at the same log index. This is enforced through two mechanisms working in concert.

The first is the **Election Restriction**. As we discussed in the leader election section, a candidate can only win if its log is at least as up-to-date as a majority of nodes. "More up-to-date" is defined precisely: if the candidate's last log entry has a higher term than the voter's last entry, the candidate is more up-to-date; if they have the same last term, whichever has the longer log is more up-to-date. Since committed entries must have been accepted by a majority, and the election requires a majority, the winning candidate's log must contain all committed entries. A leader can never be elected if it is missing committed entries, because it cannot win votes from the nodes that have those entries.

The second mechanism is the **Commitment Rule for Previous Terms**. This is a subtler but critical safety guarantee. A new leader might find entries in its log from previous terms that have not yet been formally committed. Raft's rule is that a new leader must not mark entries from previous terms as committed directly — it must wait until it commits at least one entry from the current term, and only then does that implicitly commit all prior entries. This prevents a tricky edge case where an entry that was accepted by a majority in a previous term gets overwritten by a new leader that is simultaneously accepted by a different majority.

```
SAFETY — The Election Restriction Visualised:

Cluster: A, B, C, D, E (5 nodes)
Committed entries must appear on a majority (3+ nodes).

Scenario: Entry at index 5 is committed (3+ nodes have it).

         Index: 1  2  3  4  5  6
Node A:  [T1][T1][T2][T2][T3][ ]   ← Has index 5
Node B:  [T1][T1][T2][T2][T3][ ]   ← Has index 5
Node C:  [T1][T1][T2][T2][T3][ ]   ← Has index 5
Node D:  [T1][T1][T2][ ][ ][ ]     ← Missing indexes 4 and 5
Node E:  [T1][T1][T2][ ][ ][ ]     ← Missing indexes 4 and 5

If A crashes, can D become leader?
D asks: B, C, E for votes.
B votes NO: D's log ends at index 3, B's log ends at index 5. B is more up-to-date.
C votes NO: Same reason.
E votes YES: E also only has index 3.

D gets only 2 votes (D + E). Cannot reach majority of 3.

D CANNOT become leader ✓
Only A, B, or C (nodes with full log) can become leader.
The committed entry at index 5 is SAFE.
```

The beauty of Raft is that these two mechanisms together make the algorithm provably safe: committed entries can never be lost, and no two leaders can ever be elected in the same term. Every decision made by the system is permanent, and every correct node will eventually learn about it.

## 4. Viewstamped Replication

Viewstamped Replication (VSR) is the algorithm that very few people know by name but that many know by influence. It was developed by Barbara Liskov and Brian Oki in 1988 — one year before Paxos — and it independently arrived at many of the same insights. In fact, VSR and Paxos are mathematically equivalent at their core, but VSR's framing is much more directly oriented toward the **replicated state machine** model, which is how real databases think about their operation.

Where Paxos talks about "proposers," "acceptors," and "choosing values," Viewstamped Replication talks about "replicas," "views," and "operations." This terminological difference reflects a philosophical one: VSR was designed from the start to be the foundation for a replicated service, not just a theoretical consensus mechanism.

The central concept in VSR is the **view**, which is analogous to Raft's term. A view is an epoch during which a specific node acts as the **primary** (equivalent to Raft's leader). When the primary fails, the system undergoes a **view change**, which increments the view number and elects a new primary. Every operation the system processes is tagged with the view number in which it was processed, and this view number serves as the logical clock that orders events in the system's history.

```
VSR ARCHITECTURE — The Three Roles:

┌─────────────────────────────────────────────────────────────────┐
│                         CLUSTER (3 nodes)                       │
│                                                                 │
│   ┌─────────────┐       ┌─────────────┐       ┌─────────────┐  │

│   │             │       │             │       │             │  │
│   │ op-number:5 │       │ op-number:5 │       │ op-number:4 │  │
│   │ view: 3     │       │ view: 3     │       │ view: 3     │  │

```

The VSR normal operation protocol works as follows. When the primary receives a client request, it increments a monotonically increasing **op-number**, appends the operation to its own log, and sends a `Prepare` message to all replicas. This message contains the view number, the operation, the op-number, and the current commit number. Each replica, upon receiving a `Prepare` message, checks that the view number matches its own (rejecting messages from nodes it considers stale), appends the operation to its log, and responds with a `PrepareOK` message. Once the primary has received `PrepareOK` from a quorum of replicas (a majority, including itself), it considers the operation committed, executes it against its local state machine, sends a `Commit` message to replicas, and returns the result to the client.

The **view change** protocol in VSR is where the algorithm shows its depth. When a replica suspects the primary has failed — because it has not received a message from the primary within a timeout — it broadcasts a `StartViewChange` message to all other replicas, advertising a new, higher view number. When a replica receives `StartViewChange` messages from a quorum (indicating a majority has reached the same conclusion about the primary's failure), it sends a `DoViewChange` message to the node that should be the new primary in the new view (typically determined by a simple formula like `new_primary = new_view_number mod cluster_size`). The `DoViewChange` message includes the replica's full log and its knowledge of the commit point.

```
VSR VIEW CHANGE — When Primary Fails:

Old View 3: Primary = Node 1 (crashed)

Step 1: Node 2 and Node 3 time out, suspect Node 1 is dead.
        They send: StartViewChange(view=4) to all nodes.

Step 2: When a quorum (2 nodes) have sent StartViewChange(view=4),
        each sends DoViewChange(view=4, log=[...], commitNum=N)
        to Node 2 (new primary, since 4 mod 3 = 1 → Node at index 1 = Node 2)

         DoViewChange(v=4, log=[op1..op5], commit=4)
Node 2 ◄──────────────────────────────────────────────── Node 3

Step 3: Node 2 receives DoViewChange from quorum.
        Node 2 selects the MOST COMPLETE LOG among all received logs.
        (Most up-to-date = highest op-number, breaking ties by view number)
        Node 2 sets its log to that most complete log.
        Node 2 sends: StartView(view=4, log=[...], opNumber=5, commitNum=4)
        to all other replicas.

Step 4: Node 3 replaces its log with Node 2's log.
        All nodes are now in View 4 with Node 2 as primary.
        Normal operation resumes.
```

The critical subtlety of VSR's view change is the **log selection rule**: the new primary must adopt the most complete log among all logs it receives in `DoViewChange` messages. "Most complete" is defined as the log with the highest op-number (breaking ties by preferring the highest view number). This rule mirrors Raft's election restriction — it ensures that the new primary starts with all operations that were committed under any previous view, so no committed operation is lost.

One of VSR's distinctive contributions is its treatment of **recovery**. When a crashed node comes back online, it does not immediately rejoin the cluster — it enters a recovery protocol where it asks other replicas for their current state and log, catches up, and only then participates in normal operation. This explicit recovery protocol ensures that a recovering node never acts on stale state.

Viewstamped Replication is the intellectual ancestor of Zookeeper's ZAB protocol and influenced Raft's design significantly. Understanding VSR deepens your understanding of the whole family of consensus algorithms.

## 5. ZooKeeper's ZAB Protocol

You have almost certainly used ZooKeeper indirectly, even if you did not know it. ZooKeeper is the coordination service that underlies Kafka's broker registration and consumer group coordination (historically), Hadoop's HDFS NameNode high availability, HBase's master election, and many other distributed systems. Its consistency model — the ZooKeeper Atomic Broadcast protocol, known as **ZAB** — is the algorithm that makes all of this reliable.

ZAB is specifically designed not as a general-purpose consensus algorithm but as a **total order broadcast protocol** tailored for the ZooKeeper use case. The distinction matters: while Paxos and Raft are designed to agree on individual values, ZAB is designed to ensure that all updates to ZooKeeper's state tree are delivered to all nodes in the **same total order**. This total order is what gives ZooKeeper its strong consistency semantics — any client can read from any ZooKeeper node and get a consistent view of the state.

ZAB distinguishes between two modes of operation: **Broadcast mode** (normal operation) and **Recovery mode** (leader election and log synchronisation after a failure). Understanding these two modes is the key to understanding ZAB.

In **Broadcast mode**, ZAB operates very similarly to Multi-Paxos and Raft. There is a single designated **leader** that receives all write requests. When the leader receives a write request, it assigns it a **zxid** (ZooKeeper transaction ID), which is a 64-bit number composed of two parts: the high 32 bits are the **epoch** (analogous to Raft's term), and the low 32 bits are a monotonically increasing **counter** within that epoch. The leader sends a `Proposal` message to all followers, which is equivalent to Raft's `AppendEntries`. Followers acknowledge with an `Ack` message. Once the leader receives `Ack` from a quorum, it sends a `Commit` message to followers, and both the leader and followers apply the transaction to their state.

```
ZAB ZXID — The Transaction ID Structure:

zxid is a 64-bit number:

 63         32  31          0
┌──────────────┬──────────────┐
│    EPOCH     │   COUNTER    │
│  (32 bits)   │  (32 bits)   │
└──────────────┴──────────────┘

Example:
  Epoch 3, Transaction 7:  zxid = (3 << 32) | 7 = 12884901895

When a new leader is elected (new epoch), the epoch increments,
and the counter resets to 0. This means:
- All zxids from epoch 3 are LESS THAN all zxids from epoch 4.
- Within an epoch, transactions are totally ordered by counter.
- Globally, transactions are totally ordered by zxid.

This global total order is the core ZAB guarantee.
```

ZAB's **Recovery mode** is where its design shines most distinctly. When the current leader crashes, followers detect the failure via timeout and enter Recovery mode. Recovery in ZAB has two phases. The first phase is **Leader Election**: all nodes run an election protocol (ZAB uses a variant called FastLeaderElection) to elect a new leader. The candidate with the highest zxid wins — meaning the candidate with the most up-to-date log. This is analogous to Raft's log completeness check and ensures the new leader has all committed transactions.

The second phase of Recovery is **Synchronisation**, and this is ZAB's most distinctive contribution. Once a new leader is elected, it does not immediately begin processing new transactions. Instead, it must first synchronise all followers to have identical logs before the system can resume. The new leader sends its entire log to all followers and ensures they are brought to exactly the same state. Only after a quorum of followers have confirmed synchronisation does the leader transition back to Broadcast mode and begin processing new transactions.

```
ZAB — FULL LIFECYCLE:

┌─────────────────────────────────────────────────────────────────────┐
│                    ZAB PROTOCOL LIFECYCLE                           │
│                                                                     │
│  ┌─────────────┐        failure         ┌─────────────────────┐   │
│  │             │ ──────────────────────► │                     │   │
│  │  BROADCAST  │                         │   RECOVERY          │   │
│  │   (Normal   │◄────────────────────── │                     │   │
│  │  Operation) │   sync complete +       │   Phase 1:          │   │
│  │             │   quorum achieved       │   Leader Election   │   │
│  │ Leader      │                         │   (FastLeaderElect) │   │
│  │ sends:      │                         │                     │   │
│  │ Proposal ─► │                         │   Phase 2:          │   │
│  │ quorum Ack  │                         │   Synchronisation   │   │
│  │ Commit  ─►  │                         │   (New leader sends │   │
│  │             │                         │   log to followers) │   │
│  └─────────────┘                         └─────────────────────┘   │
└─────────────────────────────────────────────────────────────────────┘

The explicit synchronisation phase is ZAB's key design choice:
no new transactions until all followers are in sync with the new leader.
This is more conservative than Raft, which begins serving requests
as soon as the new leader is elected, bringing followers up to date
lazily via AppendEntries.
```

One architectural difference that sets ZAB apart from Raft is ZAB's notion of **Primary Order Guarantee** — a guarantee that is stronger than simple log replication. ZAB guarantees that if a transaction T1 was broadcast before T2, then any server that delivers T2 must also have already delivered T1. This is the "atomic broadcast" in the name: transactions are delivered atomically in the same total order to all surviving nodes. This guarantee is enforced by the leader's use of FIFO TCP channels to communicate with followers — since TCP preserves ordering, and all proposals from a single leader share the same FIFO channel, followers receive proposals in exactly the order the leader sent them.

ZAB also handles a subtle but important edge case: **orphaned transactions**. If the old leader proposed a transaction (sent `Proposal` messages) but crashed before it received enough `Ack` messages to commit it, that transaction is "orphaned" — it exists in some followers' logs but was never committed. When the new leader synchronises followers, it must identify these orphaned transactions and decide their fate. ZAB's rule is that if an orphaned transaction has a zxid from the old leader's epoch, the new leader will explicitly tell followers to delete it — to roll it back — unless the new leader itself has that transaction in its log (which would mean it was accepted by a quorum and should be committed). This rollback mechanism ensures that uncommitted transactions from dead leaders never haunt the system.

The most practically significant comparison is between **Raft and ZAB**, since these are the two algorithms you are most likely to encounter in production infrastructure. Both use a strict leader model. Both use quorum-based commits. Both guarantee total order of operations. The key difference is in their recovery philosophy: Raft is **optimistic** (start processing immediately, catch up followers lazily), while ZAB is **conservative** (synchronise all followers completely before processing any new requests). ZAB's approach means slightly longer recovery time after a leader failure, but it provides stronger ordering guarantees and simpler reasoning about state after a view change.

## 7. Real-World Connections to Your Stack

As a Go backend developer, you interact with consensus algorithms every day, even if transparently. Let us make these connections concrete so the theory never feels abstract again.

**etcd** is the distributed key-value store that Kubernetes uses to store all cluster state — which pods are running, which services exist, which nodes are healthy. etcd implements Raft. Every time Kubernetes schedules a pod, updates a deployment, or records a ConfigMap, that operation goes through Raft consensus across the etcd cluster. If you run a Kubernetes cluster and you lose the etcd quorum (more than half your etcd nodes), Kubernetes stops functioning entirely — this is the cost of strong consistency.

**Apache ZooKeeper** with ZAB is what has historically coordinated Kafka brokers. In older versions of Kafka (pre-2.8), every Kafka broker registered itself in ZooKeeper, and the Kafka controller used ZooKeeper watches to detect broker failures and trigger partition leader elections. When ZooKeeper's quorum was lost, Kafka's control plane stopped working even if the brokers themselves were healthy. This is why Kafka eventually developed **KRaft** (Kafka Raft) — its own Raft-based metadata management system — to eliminate the ZooKeeper dependency and have consensus built directly into Kafka.

**PostgreSQL's Patroni** — a widely used high-availability solution for PostgreSQL — uses etcd or Consul (both Raft-based) as its distributed configuration store. Patroni uses these stores to elect a PostgreSQL leader and prevent split-brain scenarios where two PostgreSQL instances both think they are the primary. The consensus algorithm in etcd or Consul is what makes Patroni's leader election safe.

**MongoDB's replica sets** do not use Paxos or Raft directly, but their election protocol — where nodes vote for a primary based on their replication state and oplog position — is inspired by these algorithms. A MongoDB primary is elected when it receives votes from a majority of the replica set members, which is the quorum requirement of consensus.

Understanding these connections transforms how you think about your infrastructure. When you run `patronictl switchover`, you are triggering a controlled leader change in an etcd-backed consensus group. When you lose a Kafka ZooKeeper node, you are shrinking your quorum. When you design your etcd cluster with 3 nodes vs. 5 nodes, you are choosing how many simultaneous failures your consensus algorithm can tolerate (1 vs. 2, respectively).

_The study of consensus algorithms is the study of how humans teach machines to agree in the face of uncertainty — perhaps the most elegant problem in distributed computing. Paxos proved it was possible. Viewstamped Replication built it for real services. ZAB tailored it for broadcast semantics. And Raft taught the rest of us how to understand it. Each algorithm is a different answer to the same fundamental question: in a world where anything can fail, how do we build something reliable?_

_As you grow as an engineer, you will move from using these systems to configuring them, and eventually to understanding their failure modes deeply enough to debug them at 3 AM in production.
