# SQL Window Functions

### A Deep, Conceptual Journey from the Ground Up

> _Window functions are not just a feature — they are a completely different way of thinking about rows._

---

## Preface: The Problem Window Functions Solve

To truly understand window functions, you must first feel the pain they eliminate. Imagine you have a table of employee salaries, and you want to see each employee's salary alongside the average salary of their department — without collapsing the rows into a summary.

With a regular `GROUP BY`, you collapse every department's employees into a single summary row. You lose the individual employees entirely. You could then `JOIN` that summary back to the original table, but this is verbose, inefficient, and inelegant. You are essentially computing an aggregate and then _un-aggregating_ it back to row level.

Window functions solve this tension directly. They let you compute an aggregate — or a rank, or a comparison to a neighboring row — **without collapsing the rows**. Every row survives. Every row gets the computed value attached to it. The rows remain intact; only a new computed column is added.

This is the fundamental promise of a window function: **compute something across a set of related rows, but report that result on each individual row**.

The word "window" is the key metaphor. For each row, the database opens a conceptual "window" — a subset of the rows that are considered "related" to the current row for the purpose of this computation. The function is applied within that window, and the result is placed on the current row. Then the window slides (or shifts) to the next row, and the process repeats.

---

## Chapter 1: The OVER Clause — The Heart of Everything

### Nothing Happens Without OVER

Every window function — whether it is a ranking function, an offset function, or an aggregate — is activated by the `OVER` clause. If you write `SUM(amount)` in a query, it is a regular aggregate (used with `GROUP BY`). If you write `SUM(amount) OVER (...)`, it becomes a window function. The `OVER` clause is what transforms a regular function into a window function. It is the syntactic signal to the database: _apply this function across a window of rows, not as a collapsing aggregate_.

```sql
-- Regular aggregate: collapses rows, returns ONE row per group
SELECT department_id, SUM(salary)
FROM employees
GROUP BY department_id;

-- Window function: does NOT collapse rows, returns ONE row PER EMPLOYEE
SELECT name, department_id, salary,
       SUM(salary) OVER (PARTITION BY department_id) AS dept_total
FROM employees;
```

The second query returns every employee row, and every row has a `dept_total` column showing the sum of all salaries in that employee's department. No rows are lost.

### The Three Components of OVER

Inside the `OVER` clause, you have three independent but combinable components: `PARTITION BY`, `ORDER BY`, and the **frame specification**. Understanding each one, and how they interact, is the entire game.

```sql
function_name() OVER (
    PARTITION BY  column_a, column_b   -- Divide rows into groups
    ORDER BY      column_c DESC        -- Sort rows within each group
    ROWS BETWEEN  UNBOUNDED PRECEDING  -- Define the frame boundary
              AND CURRENT ROW
)
```

### PARTITION BY: Dividing the World

`PARTITION BY` is the most intuitive component. It divides all the rows in your result set into groups called **partitions** — analogous to the groups in a `GROUP BY`. The window function is applied independently within each partition, as if each partition were its own small table.

If you `PARTITION BY department_id`, then every window function computation restarts fresh for each department. An employee in Engineering is only compared to other Engineering employees; a Finance employee is only compared to Finance employees.

```
Without PARTITION BY: one window spans ALL rows

  +----------+--------+--------+
  | emp      | dept   | salary |
  +----------+--------+--------+
  | Alice    | Eng    | 90000  | ← window = all 6 rows
  | Bob      | Eng    | 85000  | ← window = all 6 rows
  | Carol    | Fin    | 75000  | ← window = all 6 rows
  | Dave     | Fin    | 80000  | ← window = all 6 rows
  | Eve      | Mkt    | 70000  | ← window = all 6 rows
  | Frank    | Mkt    | 72000  | ← window = all 6 rows
  +----------+--------+--------+

With PARTITION BY department_id: separate windows per dept

  +----------+--------+--------+
  | Alice    | Eng    | 90000  | ← window = {Alice, Bob}
  | Bob      | Eng    | 85000  | ← window = {Alice, Bob}
  +----------+--------+--------+
  | Carol    | Fin    | 75000  | ← window = {Carol, Dave}
  | Dave     | Fin    | 80000  | ← window = {Carol, Dave}
  +----------+--------+--------+
  | Eve      | Mkt    | 70000  | ← window = {Eve, Frank}
  | Frank    | Mkt    | 72000  | ← window = {Eve, Frank}
  +----------+--------+--------+
```

If you omit `PARTITION BY` entirely, the window spans all rows in the result set. This is perfectly valid — it means "compute this function across every row globally."

### ORDER BY: Giving Rows a Position

`ORDER BY` inside an `OVER` clause does two things at once, and conflating them causes confusion. First, it establishes a **logical ordering** of rows within each partition. Second — and this is subtle — it implicitly defines a **running frame** for certain functions.

When `ORDER BY` is present, many window functions switch from "look at all rows in the partition" to "look at all rows from the start of the partition up to and including the current row." This running-total behavior is the default frame that `ORDER BY` implies, and we will explore it thoroughly in the frame chapter.

```sql
-- ORDER BY changes the behavior of SUM:

-- Without ORDER BY in OVER → total sum of entire partition
SUM(salary) OVER (PARTITION BY department_id)
-- → Every row in a dept gets the SAME value: the dept's total salary

-- With ORDER BY in OVER → running/cumulative sum
SUM(salary) OVER (PARTITION BY department_id ORDER BY hire_date)
-- → Each row gets the sum of salaries from the first hire up to THIS hire
--   (a running total that grows with each row)
```

This distinction — static aggregate vs. running aggregate — is one of the most important things to internalize about window functions. `ORDER BY` inside `OVER` is NOT the same as `ORDER BY` at the end of the query. The one inside `OVER` defines the order _within the window for computational purposes_. The one at the end of the query defines the _output row order_.

### The Full Picture Together

Here is how all three components interact in a real query, showing each employee's salary, their department total, their rank within their department by salary, and their cumulative salary sum in hire order:

```sql
SELECT
    name,
    department_id,
    salary,
    hire_date,

    -- No ORDER BY: entire partition is the frame → static total
    SUM(salary) OVER (PARTITION BY department_id)
        AS dept_total_salary,

    -- With ORDER BY: running frame (start to current row) → cumulative sum
    SUM(salary) OVER (PARTITION BY department_id ORDER BY hire_date)
        AS running_salary_sum,

    -- Ranking: ORDER BY salary descending → rank by pay within dept
    RANK() OVER (PARTITION BY department_id ORDER BY salary DESC)
        AS salary_rank_in_dept

FROM employees;
```

## Chapter 2: Ranking Functions — ROW_NUMBER, RANK, DENSE_RANK, NTILE

### What Ranking Functions Have in Common

All ranking functions require an `ORDER BY` inside the `OVER` clause — because ranking is inherently about _position_, and position requires order. They produce an integer for each row indicating its position within the partition. They differ only in how they handle **ties** — rows that have the same value on the `ORDER BY` column.

Let us use a concrete dataset throughout this chapter:

```
Table: sales_reps
+--------+--------+--------+
| name   | region | sales  |
+--------+--------+--------+
| Alice  | East   | 9500   |
| Bob    | East   | 8200   |
| Carol  | East   | 8200   |  ← tie with Bob
| Dave   | East   | 7100   |
| Eve    | West   | 11000  |
| Frank  | West   | 9800   |
| Grace  | West   | 9800   |  ← tie with Frank
| Hank   | West   | 8500   |
+--------+--------+--------+
```

### ROW_NUMBER: Strict Sequential Numbering

`ROW_NUMBER` assigns a unique, sequential integer to every row, starting at 1. Ties are broken **arbitrarily** — if two rows have identical `ORDER BY` values, one will get a lower number than the other, but the choice of which one is not guaranteed to be consistent. No two rows ever share the same row number within a partition.

```sql
SELECT name, region, sales,
    ROW_NUMBER() OVER (PARTITION BY region ORDER BY sales DESC) AS rn
FROM sales_reps;

-- Result for East region:
-- name  | sales | rn
-- ------+-------+----
-- Alice | 9500  |  1
-- Bob   | 8200  |  2   ← Bob and Carol are tied at 8200,
-- Carol | 8200  |  3   ← but they get different row numbers (arbitrarily)
-- Dave  | 7100  |  4
```

`ROW_NUMBER` is the right choice when you need **exactly one row per rank** — for example, fetching the single top-selling rep per region (where ties are broken by some secondary criterion or simply by arbitrary selection). It is also the foundation of the "Top N per group" pattern:

```sql
-- Fetch the TOP 2 sales reps per region

WITH ranked AS (
    SELECT name, region, sales,
        ROW_NUMBER() OVER (PARTITION BY region ORDER BY sales DESC) AS rn
    FROM sales_reps
)
SELECT name, region, sales
FROM ranked
WHERE rn <= 2;

-- East: Alice (1st), Bob OR Carol (2nd) — one of them arbitrarily
-- West: Eve (1st), Frank OR Grace (2nd) — one of them arbitrarily
```

### RANK: Ties Share a Rank, Then a Gap

`RANK` handles ties by giving tied rows the **same rank**, then **skipping** the next rank(s) to account for the tie. Think of it as "position in a race" — if two runners tie for 2nd, the next runner is 4th (not 3rd), because the 3rd-place slot is considered "used up" by both tied runners.

```sql
SELECT name, region, sales,
    RANK() OVER (PARTITION BY region ORDER BY sales DESC) AS rnk
FROM sales_reps;

-- Result for East region:
-- name  | sales | rnk
-- ------+-------+-----
-- Alice | 9500  |  1
-- Bob   | 8200  |  2   ← tie: both get rank 2
-- Carol | 8200  |  2   ← tie: both get rank 2
-- Dave  | 7100  |  4   ← gap: rank 3 is skipped
```

The gap (the skipped rank) is the defining characteristic of `RANK`. It preserves the meaning of the rank number: if rank 4 exists, it means there are exactly 3 rows ranked above it. `RANK` is the natural choice for competition-style rankings where gaps have meaning — "this player finished 4th because there were three above them, including two who tied."

### DENSE_RANK: Ties Share a Rank, No Gap

`DENSE_RANK` also gives tied rows the same rank, but it does **not skip** the next rank. After a tie at rank 2, the next row gets rank 3 — not rank 4. The ranks are always consecutive integers, with no gaps.

```sql
SELECT name, region, sales,
    DENSE_RANK() OVER (PARTITION BY region ORDER BY sales DESC) AS dr
FROM sales_reps;

-- Result for East region:
-- name  | sales | dr
-- ------+-------+----
-- Alice | 9500  |  1
-- Bob   | 8200  |  2   ← tie: both get rank 2
-- Carol | 8200  |  2   ← tie: both get rank 2
-- Dave  | 7100  |  3   ← no gap: next rank is 3

-- Result for West region:
-- name  | sales | dr
-- ------+-------+----
-- Eve   | 11000 |  1
-- Frank |  9800 |  2   ← tie: both get rank 2
-- Grace |  9800 |  2   ← tie: both get rank 2
-- Hank  |  8500 |  3   ← no gap: next rank is 3
```

`DENSE_RANK` is the right choice when the rank number itself needs to be a count of distinct "levels" above the current row — for example, for percentile-like reasoning ("this score is at the 3rd distinct performance level").

### Comparing All Three Side by Side

```
Sales: 9500, 8200, 8200, 7100

+-------+------------+------+------------+
| sales | ROW_NUMBER | RANK | DENSE_RANK |
+-------+------------+------+------------+
|  9500 |     1      |  1   |     1      |
|  8200 |     2      |  2   |     2      |
|  8200 |     3      |  2   |     2      |  ← ties
|  7100 |     4      |  4   |     3      |  ← gap vs. no gap
+-------+------------+------+------------+

ROW_NUMBER: Always unique.    No tie handling.  Arbitrary for ties.
RANK:       Ties share rank.  Gap after ties.   Position = count above.
DENSE_RANK: Ties share rank.  No gap.           Rank = count of levels.
```

### NTILE: Dividing into Buckets

`NTILE(n)` is conceptually different from the other ranking functions. Instead of assigning a position to each row, it **divides the rows into `n` roughly equal buckets** and assigns a bucket number (1 through n) to each row. It is the SQL way of computing quartiles, quintiles, deciles, or any other quantile division.

```sql
-- Divide sales reps into 4 quartiles by their sales amount

SELECT name, region, sales,
    NTILE(4) OVER (ORDER BY sales DESC) AS quartile
FROM sales_reps;

-- Result (8 rows → 4 buckets of 2 rows each):
-- name  | sales | quartile
-- ------+-------+---------
-- Eve   | 11000 |    1      ← top 25% (Q1)
-- Frank |  9800 |    1
-- Grace |  9800 |    2      ← Q2
-- Alice |  9500 |    2
-- Bob   |  8200 |    3      ← Q3
-- Hank  |  8500 |    3
-- Carol |  8200 |    4      ← bottom 25% (Q4)
-- Dave  |  7100 |    4
```

When the number of rows is not perfectly divisible by `n`, `NTILE` distributes the extra rows into the earlier buckets (earlier buckets may have one more row than later ones). `NTILE(100)` gives you percentile ranks. `NTILE(4)` gives quartiles. This function is invaluable for segmenting customers, scoring distributions, or splitting a dataset for analysis.

## Chapter 3: Offset Functions — LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE

### Reaching Beyond the Current Row

All the functions in this chapter share a common characteristic: they allow a row to **look at the value of a different row** within the same window. This is something no other SQL construct allows without a self-join. Offset functions let a row peer backward (LAG) or forward (LEAD) in the ordered sequence, or reach to the absolute beginning (FIRST_VALUE) or end (LAST_VALUE) or any specific position (NTH_VALUE) of its partition.

### LAG: Looking Backward

`LAG(expression, offset, default)` returns the value of `expression` from the row that is `offset` rows **before** the current row in the partition's order. The `offset` defaults to 1 (the immediately preceding row). The `default` value is returned when there is no preceding row (for the first row in a partition).

```sql
-- For each sales rep, show their sales and the sales of the
-- previous rep in the ranking (to compute the gap between them)

SELECT
    name,
    sales,
    LAG(sales, 1, 0) OVER (ORDER BY sales DESC) AS prev_sales,
    sales - LAG(sales, 1, 0) OVER (ORDER BY sales DESC) AS gap_from_prev
FROM sales_reps;

-- Result:
-- name  | sales | prev_sales | gap_from_prev
-- ------+-------+------------+--------------
-- Eve   | 11000 |     0      |   11000   ← first row, no previous, default=0
-- Frank |  9800 |   11000    |   -1200
-- Grace |  9800 |    9800    |       0   ← tied with Frank
-- Alice |  9500 |    9800    |    -300
-- ...
```

The canonical use case for `LAG` is **period-over-period comparison** — comparing this month's revenue to last month's, or today's stock price to yesterday's, or this year's sales to last year's. With LAG, you do not need a self-join; you just reach back one row.

```sql
-- Month-over-month revenue change

WITH monthly_revenue AS (
    SELECT
        DATE_TRUNC('month', created_at) AS month,
        SUM(amount) AS revenue
    FROM orders
    GROUP BY DATE_TRUNC('month', created_at)
)
SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
    revenue - LAG(revenue) OVER (ORDER BY month) AS change,
    ROUND(
        100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
               / LAG(revenue) OVER (ORDER BY month),
        2
    ) AS pct_change
FROM monthly_revenue
ORDER BY month;
```

### LEAD: Looking Forward

`LEAD(expression, offset, default)` is the mirror image of `LAG` — it returns the value from the row that is `offset` rows **ahead** of the current row. It is useful when you want to compute the gap between the current event and the next one, or to preview what comes next in a sequence.

```sql
-- For each order, show when the same customer's NEXT order was placed
-- (to compute the gap between orders — useful for churn analysis)

SELECT
    user_id,
    order_id,
    created_at,
    LEAD(created_at) OVER (PARTITION BY user_id ORDER BY created_at)
        AS next_order_date,
    LEAD(created_at) OVER (PARTITION BY user_id ORDER BY created_at)
        - created_at
        AS days_until_next_order
FROM orders
ORDER BY user_id, created_at;

-- Result:
-- user_id | order_id | created_at  | next_order_date | days_until_next_order
-- --------+----------+-------------+-----------------+----------------------
--    1    |   101    | 2024-01-05  |   2024-01-20    |   15 days
--    1    |   102    | 2024-01-20  |   2024-02-10    |   21 days
--    1    |   103    | 2024-02-10  |     NULL        |   NULL ← last order
--    2    |   104    | 2024-01-08  |   2024-03-01    |   53 days
```

Customers whose last order has a `NULL` for `next_order_date` are candidates for churn analysis — they have not returned since their last order. `LEAD` makes this query trivially simple.

### FIRST_VALUE and LAST_VALUE: Anchoring to Extremes

`FIRST_VALUE(expression)` returns the value of `expression` from the **first row** of the current window frame. `LAST_VALUE(expression)` returns the value from the **last row** of the frame. Both require an `ORDER BY` to establish which row is first or last.

```sql
-- For each employee, show their salary alongside
-- the highest-paid person in their department

SELECT
    name,
    department_id,
    salary,
    FIRST_VALUE(name) OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
    ) AS highest_paid_in_dept,
    FIRST_VALUE(salary) OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
    ) AS highest_salary_in_dept
FROM employees;
```

`LAST_VALUE` has a well-known gotcha that catches many developers. Because the default frame when `ORDER BY` is present is `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, `LAST_VALUE` by default returns the value of the _current row itself_ (since the current row is the last row of the frame). To get the true last row of the entire partition, you must explicitly expand the frame:

```sql
-- WRONG: returns current row's salary (the default frame stops at CURRENT ROW)
LAST_VALUE(salary) OVER (PARTITION BY department_id ORDER BY salary DESC)

-- CORRECT: explicitly extend the frame to the end of the partition
LAST_VALUE(salary) OVER (
    PARTITION BY department_id
    ORDER BY salary DESC
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
)
```

This is one of the most common bugs in window function code. Always specify the frame explicitly when using `LAST_VALUE`.

### NTH_VALUE: Pinpoint Any Position

`NTH_VALUE(expression, n)` returns the value of `expression` from the **nth row** of the current window frame (counting from 1). It generalizes `FIRST_VALUE` (which is `NTH_VALUE(expr, 1)`) to any arbitrary position.

```sql
-- For each employee, show the salary of the 2nd highest earner
-- in their department (for benchmarking purposes)

SELECT
    name,
    department_id,
    salary,
    NTH_VALUE(salary, 2) OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS second_highest_salary
FROM employees;
```

Like `LAST_VALUE`, `NTH_VALUE` requires you to be thoughtful about the frame — if the nth row falls outside the default frame boundary, it returns `NULL`. Expanding the frame to `UNBOUNDED FOLLOWING` is the safe approach when you want to reference any position in the full partition.

## Chapter 4: Aggregates as Window Functions

### The Original Pain Point, Solved

Recall the problem from the Preface: you want each employee's salary alongside their department's average salary. This is the canonical aggregate-as-window-function problem, and it is where window functions began historically.

Any standard aggregate function — `SUM`, `AVG`, `COUNT`, `MIN`, `MAX`, `STRING_AGG`, and others — can be used as a window function simply by appending an `OVER` clause. The aggregate is computed over the window (the current partition, or a frame within it) and the result appears on each row without collapsing anything.

```sql
SELECT
    name,
    department_id,
    salary,

    -- Each employee sees their dept's total, average, count, min, max
    SUM(salary)   OVER (PARTITION BY department_id) AS dept_total,
    AVG(salary)   OVER (PARTITION BY department_id) AS dept_avg,
    COUNT(*)      OVER (PARTITION BY department_id) AS dept_headcount,
    MIN(salary)   OVER (PARTITION BY department_id) AS dept_min,
    MAX(salary)   OVER (PARTITION BY department_id) AS dept_max,

    -- Salary as percentage of dept total
    ROUND(100.0 * salary / SUM(salary) OVER (PARTITION BY department_id), 2)
        AS pct_of_dept_total

FROM employees;
```

Every row survives. Every row gets the department-level values. You can now do row-level comparisons against department-level benchmarks in a single query.

### Running Totals: The Power of ORDER BY in Aggregates

When you add `ORDER BY` to an aggregate window function, the frame (by default) becomes `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — meaning "from the very first row up to and including the current row." This produces a **running (cumulative) aggregate**.

```sql
-- Running total of revenue, ordered by date

SELECT
    order_date,
    daily_revenue,
    SUM(daily_revenue) OVER (ORDER BY order_date)
        AS cumulative_revenue,
    AVG(daily_revenue) OVER (ORDER BY order_date)
        AS running_avg_revenue
FROM daily_sales
ORDER BY order_date;

-- Result:
-- date       | daily_rev | cumulative_rev | running_avg
-- -----------+-----------+----------------+------------
-- 2024-08-01 |   1200    |     1200       |  1200.00
-- 2024-08-02 |   1500    |     2700       |  1350.00
-- 2024-08-03 |    800    |     3500       |  1166.67
-- 2024-08-04 |   2100    |     5600       |  1400.00
-- 2024-08-05 |   1700    |     7300       |  1460.00
```

The cumulative sum grows with each row. The running average smooths out the daily fluctuations. Both are a direct consequence of `ORDER BY` implying a running frame.

### Sliding Window Aggregates: Moving Averages

One of the most powerful applications is the **moving average** — computing an aggregate over a sliding window of a fixed number of preceding rows. This is used everywhere in financial analysis (the 7-day moving average of stock prices), in smoothing noisy sensor data, and in computing rolling metrics in product analytics.

```sql
-- 7-day moving average of daily revenue

SELECT
    order_date,
    daily_revenue,
    AVG(daily_revenue) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW  -- current + 6 before = 7 days
    ) AS moving_avg_7d
FROM daily_sales
ORDER BY order_date;
```

The `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` frame specification is what makes this a moving window rather than a running total. As the current row advances, the window slides forward, always spanning 7 rows — the current row and the 6 before it.

```
Moving average window visualization:

Date       | Revenue |  Window spans             | 7d avg
-----------+---------+---------------------------+--------
Aug 01     |  1200   | [Aug01]                   |  1200.0  (only 1 row available)
Aug 02     |  1500   | [Aug01, Aug02]            |  1350.0  (2 rows)
...
Aug 07     |  1900   | [Aug01–Aug07]             |  1542.9  (full 7-day window)
Aug 08     |  2100   | [Aug02–Aug08]  ← slides!  |  1628.6  (Aug01 dropped)
Aug 09     |  1300   | [Aug03–Aug09]  ← slides!  |  1600.0  (Aug02 dropped)
```

## Chapter 5: Frame Specifications — ROWS vs RANGE vs GROUPS

### The Most Misunderstood Part of Window Functions

Frame specifications are the least understood aspect of window functions, yet they are the most precise and expressive. The frame is the subset of rows within a partition that the window function actually operates on for any given row. While `PARTITION BY` divides all rows into partitions, the **frame** carves out a portion of those partitioned rows around the current row.

The frame specification has two parts: the **frame mode** (`ROWS`, `RANGE`, or `GROUPS`) and the **frame boundaries** (`BETWEEN ... AND ...`). Together, they define, for each row, exactly which rows are "in the window."

### Frame Boundaries: The Vocabulary

Before distinguishing between ROWS, RANGE, and GROUPS, we need to learn the boundary vocabulary, since it is shared by all three modes:

```
Frame boundary keywords:

UNBOUNDED PRECEDING  → from the very first row of the partition
n PRECEDING          → n rows/ranges/groups before the current row
CURRENT ROW          → the current row itself
n FOLLOWING          → n rows/ranges/groups after the current row
UNBOUNDED FOLLOWING  → to the very last row of the partition

Common frame specifications:

ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  → Running total: from the first row up to and including the current row

ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  → Entire partition: same as omitting the frame entirely

ROWS BETWEEN 2 PRECEDING AND 2 FOLLOWING
  → Sliding window: current row + 2 before + 2 after = 5 rows

ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
  → Only the current row and the immediately preceding row
```

### The Default Frame: A Source of Confusion

The default frame depends on whether `ORDER BY` is present:

```
If ORDER BY is ABSENT:
  Default frame = ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  (entire partition — all rows are in the frame for every row)

If ORDER BY is PRESENT:
  Default frame = RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  (running frame — from the start of the partition to the current row)
```

This is why `SUM(salary) OVER (PARTITION BY dept)` returns the total salary for the whole department (entire partition), while `SUM(salary) OVER (PARTITION BY dept ORDER BY hire_date)` returns a running total (only rows up to the current one). The `ORDER BY` implicitly changed the frame.

### ROWS Mode: Physical Row Counting

In `ROWS` mode, the frame boundaries are defined by **physical row positions** — counting actual rows before or after the current row in the partition's order. This is the simplest and most intuitive mode.

```sql
-- 3-row centered moving average: current row + 1 before + 1 after

SELECT
    order_date,
    daily_revenue,
    AVG(daily_revenue) OVER (
        ORDER BY order_date
        ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
    ) AS centered_3day_avg
FROM daily_sales;
```

For any given row, the frame contains exactly the preceding row, the current row, and the following row — three physical rows. If the current row is the first row of the partition, there is no preceding row, so the frame contains only the current row and the following row.

```
ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING:

Row 1 (Aug01):  Frame = {Aug01, Aug02}           (no Aug00 exists)
Row 2 (Aug02):  Frame = {Aug01, Aug02, Aug03}    (full 3-row window)
Row 3 (Aug03):  Frame = {Aug02, Aug03, Aug04}    (full 3-row window)
...
Last row:       Frame = {prev, last}             (no following row)
```

### RANGE Mode: Logical Value-Based Grouping

In `RANGE` mode, the frame boundaries are defined not by counting rows, but by **the value of the ORDER BY expression**. A row is included in the frame if its ORDER BY value falls within a certain _range of values_ relative to the current row's ORDER BY value.

The critical difference from `ROWS`: in `RANGE` mode, all rows that are **tied** on the ORDER BY value are treated as if they are the same row. They are all either included or excluded together.

```
ROWS vs RANGE — the tie-handling difference:

Data (ordered by sales DESC):
  Row 1: Frank, sales=9800
  Row 2: Grace, sales=9800  ← tied with Frank
  Row 3: Alice, sales=9500

With RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW:
  For Row 2 (Grace): CURRENT ROW in RANGE means "all rows with sales = 9800"
  → Frame includes Row 1 (Frank) AND Row 2 (Grace)
  → SUM would include BOTH Frank and Grace's sales

With ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW:
  For Row 2 (Grace): CURRENT ROW means exactly this physical row
  → Frame includes Row 1 (Frank) AND Row 2 (Grace)  ← same here
  → SUM includes Frank and Grace

  For Row 1 (Frank): CURRENT ROW is just Row 1
  → Frame includes only Row 1 (Frank)
  → SUM is just Frank's sales

  But with RANGE:
  For Row 1 (Frank): CURRENT ROW in RANGE means all rows with sales=9800
  → Frame includes BOTH Row 1 and Row 2
  → SUM includes both Frank AND Grace
```

This is the essence of RANGE: all rows with the same ORDER BY value are considered part of the same logical "position" and are included or excluded as a group. RANGE is the reason the default frame with ORDER BY produces "correct" running totals for tied values — it ensures all tied rows get the same running total (since they are all in each other's frame).

For numeric RANGE boundaries (like `RANGE BETWEEN 100 PRECEDING AND CURRENT ROW`), the database literally checks if the ORDER BY value is within [current_value - 100, current_value]. This is useful for value-based sliding windows:

```sql
-- For each product price, compute the average price of all products
-- whose price is within $50 of the current product's price

SELECT
    product_name,
    price,
    AVG(price) OVER (
        ORDER BY price
        RANGE BETWEEN 50 PRECEDING AND 50 FOLLOWING
    ) AS avg_price_within_50
FROM products;
```

This computes a true value-range-based neighborhood — not a fixed number of rows before/after, but all rows whose price falls within a $50 band around the current product's price. The window expands or contracts based on how many products fall within that value range, not a fixed row count.

### GROUPS Mode: Peer Group Counting

`GROUPS` mode is the newest of the three (added in SQL:2011, supported in PostgreSQL 11+). It is a middle ground between ROWS and RANGE. In GROUPS mode, the frame boundary `n PRECEDING` means "n peer groups before the current peer group" — where a **peer group** is defined as all rows that are tied (have the same ORDER BY value).

```
GROUPS vs ROWS vs RANGE — conceptual comparison:

Data (ordered by sales):
  Peer Group 1: {Bob, Carol} — both have sales=8200
  Peer Group 2: {Alice}      — sales=9500
  Peer Group 3: {Frank, Grace} — both have sales=9800
  Peer Group 4: {Eve}        — sales=11000

ROWS BETWEEN 1 PRECEDING AND CURRENT ROW:
  For Grace (group 3, row 6 physically):
    Frame = {Frank (row 5), Grace (row 6)} → 2 physical rows

RANGE BETWEEN CURRENT ROW AND CURRENT ROW:
  For Grace (group 3):
    Frame = {Frank, Grace} → all rows tied at 9800

GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW:
  For Grace (group 3):
    Frame = {peer group 2 (Alice), peer group 3 (Frank, Grace)}
          = {Alice, Frank, Grace} → 3 rows (2 groups)
```

GROUPS is most useful when your data has natural peer groups (tied values) and you want to include entire peer groups in the frame, while still being able to say "the previous N distinct groups" rather than "the previous N rows."

```sql
-- For each sales value, compute the average including the current
-- and previous distinct sales tier (peer group)

SELECT
    name,
    sales,
    AVG(sales) OVER (
        ORDER BY sales
        GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW
    ) AS avg_with_prev_tier
FROM sales_reps;
```

```

      (peer groups: {A,B}, {C}, {D,E}, {F})
```

## Chapter 6: Putting It All Together — Real-World Patterns

### Pattern: The Classic Dashboard Query

A single query that computes multiple window-function-based metrics for a business dashboard, demonstrating how you compose PARTITION BY, ORDER BY, ranking, offsets, and aggregates together:

```sql
WITH monthly_sales AS (
    SELECT
        rep_name,
        region,
        DATE_TRUNC('month', sale_date)  AS month,
        SUM(amount)                     AS revenue
    FROM sales
    GROUP BY rep_name, region, DATE_TRUNC('month', sale_date)
)
SELECT
    rep_name,
    region,
    month,
    revenue,

    -- Rank within region by revenue this month
    RANK() OVER (
        PARTITION BY region, month
        ORDER BY revenue DESC
    ) AS rank_in_region,

    -- Running total of this rep's revenue over time
    SUM(revenue) OVER (
        PARTITION BY rep_name
        ORDER BY month
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS cumulative_revenue,

    -- Month-over-month change for this specific rep
    revenue - LAG(revenue, 1, 0) OVER (
        PARTITION BY rep_name
        ORDER BY month
    ) AS mom_change,

    -- 3-month moving average for this rep
    AVG(revenue) OVER (
        PARTITION BY rep_name
        ORDER BY month
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS moving_avg_3m,

    -- Percentage of region's total revenue this month
    ROUND(
        100.0 * revenue / SUM(revenue) OVER (PARTITION BY region, month),
        2
    ) AS pct_of_region

FROM monthly_sales
ORDER BY region, month, rank_in_region;
```

This single query delivers, for each sales rep in each month: their absolute revenue, their rank within their region, their cumulative all-time revenue, their month-over-month change, their 3-month smoothed average, and their share of regional revenue. Without window functions, this would require at least four separate queries and multiple joins.

### Pattern: Identifying Consecutive Groups (Gaps and Islands)

A classic SQL puzzle: identify consecutive sequences in data (contiguous "islands" of rows that meet a condition, separated by "gaps" that do not). Window functions make this tractable.

```sql
-- Find consecutive date ranges where a product was in stock

WITH stock_status AS (
    SELECT
        product_id,
        status_date,
        in_stock,
        ROW_NUMBER() OVER (PARTITION BY product_id ORDER BY status_date)
            - ROW_NUMBER() OVER (PARTITION BY product_id, in_stock ORDER BY status_date)
            AS group_id   -- rows in the same consecutive group get the same group_id
    FROM daily_stock_status
),
grouped AS (
    SELECT
        product_id,
        in_stock,
        MIN(status_date) AS range_start,
        MAX(status_date) AS range_end
    FROM stock_status
    GROUP BY product_id, in_stock, group_id
)
SELECT *
FROM grouped
WHERE in_stock = TRUE
ORDER BY product_id, range_start;
```

The trick — `ROW_NUMBER() OVER (...) - ROW_NUMBER() OVER (PARTITION BY ..., in_stock ...)` — produces a constant value for all consecutive rows in the same state. Rows that share a state consecutively will have identical differences, revealing the "islands."

### Pattern: Sessionization

In analytics, a **session** is a group of user events separated by no more than a certain time gap (commonly 30 minutes of inactivity). Window functions make sessionization elegant:

```sql
WITH event_gaps AS (
    SELECT
        user_id,
        event_time,
        event_type,
        -- Compute time since previous event for this user
        event_time - LAG(event_time) OVER (
            PARTITION BY user_id ORDER BY event_time
        ) AS gap_from_prev
    FROM user_events
),
session_starts AS (
    SELECT
        user_id,
        event_time,
        event_type,
        -- A new session starts when gap > 30 min or it's the user's first event
        CASE
            WHEN gap_from_prev > INTERVAL '30 minutes' OR gap_from_prev IS NULL
            THEN 1 ELSE 0
        END AS is_session_start
    FROM event_gaps
),
sessions AS (
    SELECT
        user_id,
        event_time,
        event_type,
        -- Session ID = cumulative count of session starts up to this event
        SUM(is_session_start) OVER (
            PARTITION BY user_id
            ORDER BY event_time
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS session_id
    FROM session_starts
)
SELECT user_id, session_id,
       MIN(event_time) AS session_start,
       MAX(event_time) AS session_end,
       COUNT(*)        AS event_count
FROM sessions
GROUP BY user_id, session_id
ORDER BY user_id, session_id;
```

The elegant insight is that the session ID is the **running count of "session start" events** up to each row. Since `SUM` with a running frame accumulates, each new session start increments the session counter for all subsequent events, until the next session start resets it again.

## Epilogue: The Window as a Mental Model

The window function is the most expressive feature SQL has for thinking about rows _in relation to each other_. Every time you find yourself writing a self-join to compare a row to its neighbors, or a subquery to compute a per-group aggregate on a per-row basis, or a complex derived table to compute rankings — pause and ask: can this be expressed as a window function?

The answer, more often than not, is yes. And the window function version will almost always be cleaner, more readable, and often faster (since the database can compute all window functions in a single pass over the data, rather than multiple scans for multiple self-joins).

The deepest skill is learning to recognize the **shape** of a problem: "this row needs to know something about its neighbors" is a LAG/LEAD problem. "This row needs to know its standing among all rows in its group" is a ranking problem. "This row needs a value that accumulates as you walk forward in time" is a running-aggregate problem. "This row needs an aggregate over a sliding value-based neighborhood" is a RANGE frame problem.

Build these shapes into your intuition, and window functions become not a complex feature to be looked up, but a natural language for expressing ideas about data.
