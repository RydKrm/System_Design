## The Problem We Are Solving

Before we can appreciate the elegance of Change Data Capture, the Outbox Pattern, or Materialized Views, we must first understand the problem that gave birth to all of them. Imagine you are building an e-commerce system. When a customer places an order, several things need to happen simultaneously. The order must be saved to the database. An email confirmation must be sent. The inventory system must be updated. The analytics dashboard must reflect the new sale. The fraud detection service must inspect the order.

In a simple world, you might try to do all of these things one by one in a single function. But this is fragile. What if the database write succeeds but the email service is down? What if the inventory update fails halfway through? You now have inconsistent state scattered across multiple systems — a nightmare to debug and even harder to recover from.

This is the fundamental challenge of distributed systems: **how do you keep multiple systems consistent when any one of them can fail at any moment?** The technologies we are about to explore are the industry's best answers to this question. Each one builds upon the previous, and together they form the backbone of modern, large-scale, real-time data architectures.

## Change Data Capture (CDC)

### What Is Change Data Capture?

Change Data Capture is exactly what its name suggests — it is the discipline of _capturing the changes_ that happen to data in a database and making those changes available to other systems in near real-time. Think of it like a surveillance camera installed not on the outside of a building, but inside a database — watching every row that is inserted, every value that is updated, and every record that is deleted, and then broadcasting those observations to whoever is listening.

The fundamental insight behind CDC is this: **your database already knows about every change it makes.** It keeps detailed internal records of every modification because it needs to recover from crashes. CDC simply taps into that existing record-keeping mechanism and exposes it as a stream of events. Instead of you writing code that periodically polls the database asking "what changed in the last five minutes?", CDC says "I will tell you what changed the moment it happens."

This is a profound shift in thinking. Rather than treating your database as a static repository of current state, CDC teaches you to treat it as an ordered, time-stamped ledger of events — much like a bank statement, which does not only show your current balance, but shows every transaction that led to that balance.

### How Databases Record Changes Internally

To truly understand CDC, you must first understand how databases keep track of their own changes. Every major database system — PostgreSQL, MySQL, MongoDB, SQL Server — maintains what is essentially a journal or log of all the operations it performs. This is not for your benefit as a developer; it is for the database's own survival.

Consider what happens when you run an `UPDATE` statement against PostgreSQL. Before the database actually modifies the data on disk, it writes a record to its internal log saying "I am about to change this row, and here is what it looked like before, and here is what it will look like after." This log entry is written to disk _before_ the actual data change is applied. This is why, if the database crashes mid-operation and then restarts, it can read its log and either complete the operation or reverse it — ensuring that your data is never left in a half-written, corrupted state.

This internal log is called the **Write-Ahead Log**, or WAL. It is the crown jewel of database reliability, and it is also the secret that makes CDC possible.

### The Write-Ahead Log (WAL)

The Write-Ahead Log is a sequential, append-only file on disk. Every single write operation — every `INSERT`, `UPDATE`, `DELETE`, and even schema changes — is first recorded in the WAL before the actual table data is modified. The word "write-ahead" means _write to the log ahead of writing to the actual data_.

```
Physical WAL Structure (Conceptual)

  LSN (Log Sequence Number)
  │
  ▼
┌─────────────────────────────────────────────────────┐
│  LSN: 0/1A3C2F10  │ BEGIN TRANSACTION               │
├─────────────────────────────────────────────────────┤
│  LSN: 0/1A3C2F28  │ INSERT INTO orders               │
│                   │   (id=101, user_id=5, total=99)  │
├─────────────────────────────────────────────────────┤
│  LSN: 0/1A3C2F50  │ UPDATE inventory                 │
│                   │   SET qty=qty-1 WHERE product=42  │
├─────────────────────────────────────────────────────┤
│  LSN: 0/1A3C2F74  │ COMMIT TRANSACTION               │
└─────────────────────────────────────────────────────┘
         │
         ▼
  Each entry has a globally unique position called an LSN
  (Log Sequence Number). Think of it as an address in the log.
```

The WAL is inherently ordered by time. Each entry has a unique, monotonically increasing identifier called a **Log Sequence Number (LSN)** in PostgreSQL (other databases have similar concepts). This LSN is like a page number in a book — it tells you not just what happened, but exactly when it happened relative to everything else.

For a long time, the WAL was a private, internal implementation detail of the database. You could not easily read it as an external consumer. PostgreSQL changed this with the introduction of **Logical Replication** and the **logical decoding** feature. Logical decoding allows external consumers to read the WAL in a human-friendly format — not the raw binary that the database uses internally, but a decoded representation that says "row with ID 42 was updated, and here are the old and new values." The tool that performs this decoding is called a **logical replication plugin**.

### pgoutput — PostgreSQL's Native Logical Replication Plugin

PostgreSQL ships with a built-in logical replication plugin called `pgoutput`. This plugin was introduced in PostgreSQL 10 and has been the standard ever since. To understand what `pgoutput` does, you must first understand what a _publication_ and a _slot_ are in PostgreSQL's replication model.

A **publication** is a declaration you make in PostgreSQL that says "I want to make the changes from these specific tables available for external consumption." You can think of it like a television broadcast — you are publishing the changes on a channel. You create a publication with a simple SQL command:

```sql
-- Create a publication for all tables
CREATE PUBLICATION my_publication FOR ALL TABLES;

-- Or for specific tables
CREATE PUBLICATION orders_publication FOR TABLE orders, order_items;
```

A **replication slot** is a bookmark that PostgreSQL maintains on behalf of a specific consumer. It remembers "this consumer has read up to LSN X, so I must not delete WAL entries before X, even if disk space is running low." The slot guarantees that no change will be lost, even if the consumer is temporarily offline. You create a slot like this:

```sql
-- Create a logical replication slot using the pgoutput plugin
SELECT pg_create_logical_replication_slot(
  'my_consumer_slot',
  'pgoutput'
);
```

With a publication and a slot in place, `pgoutput` will decode the binary WAL entries into a structured stream of messages: `BEGIN`, `RELATION` (table schema), `INSERT`, `UPDATE`, `DELETE`, and `COMMIT`. These messages flow out of PostgreSQL and into whatever consumer is connected to the slot. In practice, you almost never interact with `pgoutput` directly — tools like Debezium handle this connection for you.


### Debezium — The CDC Powerhouse

If `pgoutput` is the mechanism that makes PostgreSQL's changes available, then **Debezium** is the sophisticated consumer that reads those changes and broadcasts them to the rest of your ecosystem. Debezium is an open-source CDC platform built by Red Hat, and it is the industry standard tool for implementing CDC in production systems.

Debezium is not just a simple reader. It is a full-featured CDC platform that handles many of the hard problems you would encounter if you tried to build this yourself. It handles **initial snapshots** — when you first connect Debezium to a table that already has millions of rows, it can take a consistent snapshot of the entire table before it starts streaming changes, so that your consumer can start with a complete picture of the data rather than only seeing future changes. It handles **schema changes** — if you add a column to a table, Debezium detects this and adjusts its output accordingly. It handles **failures and restarts** — because of PostgreSQL's replication slots, Debezium knows exactly where it left off and will resume from the right position after a crash, never missing an event and never sending the same event twice (under normal circumstances).

Debezium is built on top of **Apache Kafka Connect**, which is a framework for building reliable, scalable data pipelines between systems. This is important architectural context: Debezium is not a standalone application you run directly — it runs as a _connector_ inside a Kafka Connect worker process. This means it inherits all of Kafka Connect's strengths: distributed execution, fault tolerance, REST API for management, and native integration with Kafka topics.

### What a Debezium Event Looks Like

Every change that Debezium captures is wrapped in what it calls an **envelope** — a structured JSON (or Avro) document that contains not just the new data, but rich context about the change: what operation was performed, when it happened, what the data looked like _before_ the change, and metadata about the source (which database, which table, which transaction). Here is what an event looks like for our order insertion:

```json
{
  "schema": { ... },
  "payload": {
    "before": null,
    "after": {
      "id": 101,
      "user_id": 5,
      "total": 99.00,
      "status": "placed",
      "created_at": 1725000000000000
    },
    "source": {
      "version": "2.5.0.Final",
      "connector": "postgresql",
      "name": "mydb",
      "ts_ms": 1725000000123,
      "db": "ecommerce",
      "schema": "public",
      "table": "orders",
      "txId": 7823,
      "lsn": 440622864,
      "xmin": null
    },
    "op": "c",
    "ts_ms": 1725000000456
  }
}
```

The `op` field is particularly important. It tells you what kind of operation occurred: `"c"` for create (INSERT), `"u"` for update (UPDATE), `"d"` for delete (DELETE), and `"r"` for read (from an initial snapshot). For an `"u"` (update) event, both the `before` and `after` fields are populated, giving you the complete picture of what changed. This is something a simple polling approach could never give you — you would only see the current state, not what it was before.

## The Outbox Pattern

### The Dual-Write Problem

Now we arrive at one of the most insidious problems in distributed systems, known as the **dual-write problem**. Understanding this problem in depth is essential, because the Outbox Pattern exists solely to solve it.

Imagine you are writing a service that handles order creation. When a user places an order, you need to do two things: save the order to the database, and publish an `OrderPlaced` event to a message broker (like Kafka or RabbitMQ) so that other services can react to it. Your code might look something like this:

```go
// The naive, dangerous approach
func PlaceOrder(order Order) error {
    // Step 1: Save to database
    err := db.Save(order)
    if err != nil {
        return err
    }

    // Step 2: Publish event to Kafka
    err = kafka.Publish("orders", OrderPlacedEvent{OrderID: order.ID})
    if err != nil {
        // The database was already written!
        // The order exists in the DB but no event was published.
        // Other services will NEVER know about this order.
        return err
    }

    return nil
}
```

Do you see the problem? These are two separate operations against two separate systems. There is no way to make them atomic — that is, there is no way to guarantee that either both succeed or both fail together. At any moment between step 1 and step 2, the process can crash, the network can fail, Kafka can be unavailable. If the database write succeeds but the Kafka publish fails, you have an order in the database that no other service knows about. The email was never sent. The inventory was never decremented. The fraud check was never run.

What if you reverse the order — publish to Kafka first, then save to the database? Now if the Kafka publish succeeds but the database write fails, other services will react to an order that does not actually exist in the database. Even worse.

What about using a distributed transaction, coordinating between the database and Kafka in a two-phase commit? This is technically possible with some systems, but it is extremely complex, carries significant performance overhead, and ties your two systems together in a way that makes both less available — if one is slow, the entire transaction becomes slow.

The dual-write problem has no perfect solution — but the Outbox Pattern is the closest thing to one.

### What Is the Outbox Pattern?

The Outbox Pattern solves the dual-write problem by eliminating the dual write entirely. Instead of writing to two systems, you write only to one — the database — and let the database be the single source of truth. The key insight is deceptively simple: **store the message you want to send in the same database as your business data, inside the same transaction.**

You create a special table in your database called the **outbox table**. When your business logic runs, instead of simultaneously writing to the database AND sending a message to Kafka, you write to the database AND insert a row into the outbox table — all within a single, atomic database transaction. Then, a separate process (the _relay_) reads from the outbox table and publishes those rows to the message broker. If the relay fails, it simply retries — the rows are still safely sitting in the outbox table, waiting to be published.

Here is what the outbox table typically looks like:

```sql
CREATE TABLE outbox (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_id  UUID         NOT NULL,   -- Which entity is this about? (e.g., order ID)
    aggregate_type VARCHAR(255) NOT NULL,   -- What kind of entity? (e.g., "Order")
    event_type    VARCHAR(255) NOT NULL,   -- What happened? (e.g., "OrderPlaced")
    payload       JSONB        NOT NULL,   -- The full event data
    created_at    TIMESTAMPTZ  DEFAULT NOW(),
    processed     BOOLEAN      DEFAULT FALSE,
    processed_at  TIMESTAMPTZ
);

-- Index for the relay to efficiently find unprocessed messages
CREATE INDEX idx_outbox_unprocessed 
    ON outbox (created_at) 
    WHERE processed = FALSE;
```

### How the Outbox Pattern Solves Dual-Write

Let us revisit the order creation code, now redesigned with the Outbox Pattern:

```go
func PlaceOrder(order Order) error {
    // Begin a SINGLE database transaction
    tx, err := db.Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // Write 1: Save the order to the orders table
    err = tx.Save(order)
    if err != nil {
        return err
    }

    // Write 2: Insert into the outbox table (SAME transaction!)
    err = tx.InsertOutbox(OutboxMessage{
        AggregateID:   order.ID,
        AggregateType: "Order",
        EventType:     "OrderPlaced",
        Payload: map[string]interface{}{
            "order_id": order.ID,
            "user_id":  order.UserID,
            "total":    order.Total,
        },
    })
    if err != nil {
        return err
    }

    // Both writes commit together, or both fail together.
    // There is NO possibility of partial success.
    return tx.Commit()
}
```

```
The Outbox Pattern — Atomicity Guarantee

  Application
       │
       │ BEGIN TRANSACTION
       │
       ├──▶ INSERT INTO orders (id, user_id, total) VALUES (...)
       │                          ✓
       │
       ├──▶ INSERT INTO outbox (aggregate_id, event_type, payload) VALUES (...)
       │                          ✓
       │
       │ COMMIT  ──── Both succeed or both fail. Nothing in between.
       │
       ▼
  Database now contains:
  ┌────────────────┐    ┌──────────────────────────────────────────┐
  │  orders table  │    │             outbox table                  │
  │                │    │                                          │
  │ id=101         │    │ id=UUID-XYZ                              │
  │ user_id=5      │    │ aggregate_id=101                         │
  │ total=99.00    │    │ event_type="OrderPlaced"                 │
  │ status=placed  │    │ payload={order_id:101, total:99.00}      │
  └────────────────┘    │ processed=false                          │
                        └──────────────────────────────────────────┘
                                          │
                                          │ (Separate process reads this)
                                          ▼
                               ┌────────────────────┐
                               │   Message Relay    │
                               │                    │
                               │ 1. Read unprocessed│
                               │ 2. Publish to Kafka│
                               │ 3. Mark processed  │
                               └────────────────────┘
```

Now the atomicity guarantee is iron-clad. Either the order is saved AND the outbox entry is created (commit), or neither of them happen (rollback). There is no possible state where the order exists without a corresponding outbox entry. The message relay can fail a hundred times; the outbox entry will be there waiting for it every time it restarts.

### The Polling Publisher

The simplest implementation of the message relay is called a **Polling Publisher**. It is a background process that periodically queries the outbox table for unprocessed rows, publishes them to the message broker, and then marks them as processed.

```go
func StartPollingPublisher(db *sql.DB, producer kafka.Producer) {
    ticker := time.NewTicker(500 * time.Millisecond)
    
    for range ticker.C {
        rows, err := db.Query(`
            SELECT id, aggregate_id, event_type, payload
            FROM outbox
            WHERE processed = FALSE
            ORDER BY created_at ASC
            LIMIT 100
        `)
        if err != nil {
            log.Error(err)
            continue
        }

        for rows.Next() {
            var msg OutboxMessage
            rows.Scan(&msg.ID, &msg.AggregateID, &msg.EventType, &msg.Payload)

            // Publish to Kafka
            err := producer.Publish(msg.EventType, msg.Payload)
            if err != nil {
                log.Error("Failed to publish, will retry:", err)
                continue
            }

            // Only mark as processed AFTER successful publish
            db.Exec("UPDATE outbox SET processed=TRUE, processed_at=NOW() WHERE id=$1", msg.ID)
        }
    }
}
```

The Polling Publisher is simple but has a key drawback: **latency**. If you poll every 500 milliseconds, your events can be up to 500ms late. For some use cases this is fine. For others, you need something faster. This is where CDC enters the picture and combines with the Outbox Pattern in a beautiful way.

## Transactional Outbox with Kafka

### Why Kafka Enters the Picture

The Polling Publisher approach has three weaknesses that become painful at scale. First, the latency introduced by polling intervals — even 100ms can be too slow for real-time systems. Second, the continuous database polling adds load to your database, even when there are no new messages. Third, marking rows as processed involves additional writes to the outbox table, adding more database load.

There is a far more elegant approach: use Debezium to watch the outbox table. When Debezium monitors the outbox table through CDC, it detects new rows the moment they are committed to the WAL — with sub-millisecond latency. There is no polling. There is no additional database load from the relay process. And there is no need for the `processed` column at all, because Debezium tracks its position in the WAL using the replication slot, not by marking rows.

This combination — the Transactional Outbox Pattern, with Debezium reading the outbox table and publishing to Kafka — is one of the most powerful and widely-used patterns in modern microservices architecture. Debezium even has first-class support for this pattern with a feature called the **Outbox Event Router**, which transforms the generic Debezium CDC events into the proper event format expected by downstream consumers.

### Exactly-Once Semantics and Idempotency

One of the most important questions in any messaging system is: can a message be delivered more than once? The honest answer with the Transactional Outbox + Debezium + Kafka combination is: **yes, under certain failure scenarios, a message might be delivered more than once.** This is called **at-least-once delivery**, and it is the default guarantee of most real-world systems.

Consider this scenario: Debezium reads an outbox row and successfully publishes it to Kafka. Before it can record that the LSN has been committed (saved its progress), the Debezium process crashes. When it restarts, it sees that the last recorded LSN was _before_ that row, so it reads and publishes the row again. Kafka now has two copies of the same event.

This is why consumer services must be designed to be **idempotent** — meaning that processing the same message twice has the same effect as processing it once. There are several ways to achieve this. The simplest is to use a **deduplication table** in the consumer's database, keyed by the event ID. Before processing a message, the consumer checks if it has already been processed. If so, it discards it. If not, it processes it and records the event ID in the deduplication table, atomically, in the same transaction as the business logic.

```go
func ConsumeOrderPlaced(event OrderPlacedEvent) error {
    tx, _ := db.Begin()
    defer tx.Rollback()

    // Check if we have already processed this event
    var count int
    tx.QueryRow("SELECT COUNT(*) FROM processed_events WHERE event_id=$1", 
        event.ID).Scan(&count)
    
    if count > 0 {
        // Already processed — this is a duplicate. Safe to ignore.
        return tx.Commit()
    }

    // Process the business logic
    err := decrementInventory(tx, event.ProductID, event.Quantity)
    if err != nil {
        return err
    }

    // Record that we processed this event
    tx.Exec("INSERT INTO processed_events (event_id, processed_at) VALUES ($1, NOW())", 
        event.ID)

    return tx.Commit()
}
```

This technique — where the consumer's processing is both atomic (through a database transaction) and deduplicated (through the processed events table) — is one of the most reliable patterns in distributed systems. It effectively upgrades your at-least-once system to behave like an exactly-once system from the consumer's perspective.

### Schema Evolution and the Outbox

One subtle but important concern with the Transactional Outbox Pattern is **schema evolution** — what happens when you need to change the structure of your events over time? If you change the format of the `payload` field in your outbox events, older consumers that have not been updated yet will fail to parse the new format.

The industry standard solution for managing schema evolution in event-driven systems is a **Schema Registry** (the most popular being Confluent Schema Registry) combined with a serialization format like **Apache Avro** or **Protocol Buffers**. The Schema Registry acts as a central catalog of all event schemas. When a producer publishes an event, it registers the schema and includes only a small schema ID in the message. When a consumer reads the message, it fetches the schema from the registry and uses it to deserialize the data. The Schema Registry enforces compatibility rules — for example, you can add new optional fields (backward compatible), but you cannot remove fields that consumers might depend on (breaking change), without explicitly marking the change as a breaking version.

For smaller systems, JSON with careful versioning (including a `version` field in your payload and having consumers handle multiple versions) can be sufficient. The right choice depends on the scale and the number of teams consuming your events.

## Materialized Views for Real-Time Dashboards

### The Problem with Plain Views

Before we can understand Materialized Views, we must first understand regular **views** — and specifically, their limitation. A regular database view is essentially a saved SQL query. When you query a view, the database executes the underlying SQL query at that moment and returns the results. There is no pre-computed result stored anywhere; the view is just a named shortcut for a query.

```sql
-- A regular view
CREATE VIEW order_summary AS
SELECT 
    DATE(created_at) as order_date,
    COUNT(*) as total_orders,
    SUM(total) as total_revenue,
    AVG(total) as average_order_value
FROM orders
GROUP BY DATE(created_at)
ORDER BY order_date DESC;
```

Every time someone queries this view, PostgreSQL executes the `GROUP BY` aggregation over the entire `orders` table. If you have ten million orders, this query might take several seconds. In a dashboard that refreshes every 30 seconds, you are hammering your database with an expensive aggregation query 2,880 times per day. At some point, your database begins to buckle under the pressure, and the rest of your application — which needs that same database for its normal operations — starts to slow down.

This is the limitation of regular views: they are convenient for code organization, but they offer no performance benefit. The query runs fresh every time.

### What Is a Materialized View?

A **Materialized View** solves this problem with a conceptually simple idea: **pre-compute the query result and store it physically on disk, just like a regular table.** When you query a materialized view, you are reading pre-computed, cached data from disk — not running the aggregation query. The result comes back in milliseconds, regardless of how expensive the underlying query is.

```sql
-- A materialized view — the result is stored on disk
CREATE MATERIALIZED VIEW order_summary_mv AS
SELECT 
    DATE(created_at) as order_date,
    COUNT(*) as total_orders,
    SUM(total) as total_revenue,
    AVG(total) as average_order_value
FROM orders
GROUP BY DATE(created_at)
ORDER BY order_date DESC;

-- You can index a materialized view just like a table!
CREATE INDEX idx_order_summary_date ON order_summary_mv (order_date);
```

Querying `order_summary_mv` now returns instantly because the data is physically stored. The expensive aggregation was only computed once (when the view was created or last refreshed). You can even add indexes to a materialized view, making lookups even faster.

The trade-off is obvious: the data in the materialized view is a **snapshot** of the underlying data at the time it was last refreshed. It is not real-time. If a new order comes in, the `order_summary_mv` does not immediately reflect it — you must refresh the view to update it.

```
Regular View vs Materialized View

REGULAR VIEW: Query happens at read time
────────────────────────────────────────
  User Query ──▶ View ──▶ Executes SQL ──▶ Scans 10M rows ──▶ 3 seconds
  User Query ──▶ View ──▶ Executes SQL ──▶ Scans 10M rows ──▶ 3 seconds
  User Query ──▶ View ──▶ Executes SQL ──▶ Scans 10M rows ──▶ 3 seconds

MATERIALIZED VIEW: Query reads cached data
──────────────────────────────────────────
  REFRESH (scheduled) ──▶ Executes SQL ──▶ Stores result on disk ──▶ 3 seconds
                                │
  User Query ──▶ Materialized View ──▶ Reads stored data ──▶ 2ms
  User Query ──▶ Materialized View ──▶ Reads stored data ──▶ 2ms
  User Query ──▶ Materialized View ──▶ Reads stored data ──▶ 2ms
```

### Refreshing Materialized Views

Refreshing a materialized view means re-running the underlying query and updating the stored result. PostgreSQL gives you two options.

The first is `REFRESH MATERIALIZED VIEW`, which locks the view while refreshing. During the refresh, no one can read from the view — they get blocked until the refresh is complete. For views that take a long time to refresh, this means your dashboard could freeze for seconds or minutes while the data is being updated. This is rarely acceptable in production.

The second is `REFRESH MATERIALIZED VIEW CONCURRENTLY`, which refreshes the view in the background without locking readers. While the new data is being computed, old data is still readable. Once the computation is complete, PostgreSQL atomically swaps the old data for the new. This requires that the view has at least one unique index:

```sql
-- Must have a unique index for CONCURRENTLY to work
CREATE UNIQUE INDEX idx_order_summary_mv_unique 
    ON order_summary_mv (order_date);

-- Now we can refresh without blocking readers
REFRESH MATERIALIZED VIEW CONCURRENTLY order_summary_mv;
```

You can automate refreshes using PostgreSQL's `pg_cron` extension, which allows you to schedule SQL commands like cron jobs:

```sql
-- Refresh every 5 minutes (requires pg_cron extension)
SELECT cron.schedule(
    'refresh-order-summary',
    '*/5 * * * *',
    'REFRESH MATERIALIZED VIEW CONCURRENTLY order_summary_mv'
);
```

But here is the truth: scheduled refreshes make the stale data problem worse than you might think. If you refresh every 5 minutes, your dashboard could show data that is up to 5 minutes old. For many operational dashboards, this is unacceptable. A customer support agent looking at a dashboard wants to see order activity from the last 60 seconds, not 5 minutes ago.

This is where the combination of CDC and Materialized Views becomes genuinely exciting.

### Real-Time Dashboards with CDC + Materialized Views

The most sophisticated approach to real-time dashboards combines everything we have learned so far. Rather than refreshing a materialized view on a schedule, you use CDC to trigger a refresh _precisely when the underlying data changes_. The result is a system where the dashboard updates within seconds of any meaningful data change, without the continuous polling overhead.

However, even smarter architects have moved beyond PostgreSQL's native materialized views for real-time use cases. They use **stream processing** tools like **Apache Flink** or **ksqlDB** (which runs on top of Kafka) to maintain materialized views that are updated in real-time as events flow through Kafka. These tools treat a Kafka topic as an infinite stream and maintain a continuously updated table (a "table" in ksqlDB, or a "Table API result" in Flink) that reflects the current aggregate state at all times.


In this architecture, there is no scheduled refresh at all. When a new order is inserted in PostgreSQL, Debezium captures it within milliseconds and publishes it to the Kafka `orders` topic. ksqlDB or Flink, which has been continuously listening to this topic, immediately incorporates the new event into the running aggregate. The dashboard, connected via WebSocket or polling the stream processor's output, sees the change almost instantaneously.

ksqlDB, in particular, makes this remarkably concise with its SQL-like syntax:

```sql
-- Create a stream from the Kafka topic
CREATE STREAM orders_stream (
    order_id    BIGINT,
    user_id     BIGINT,
    total       DOUBLE,
    created_at  BIGINT
) WITH (
    KAFKA_TOPIC = 'mydb.public.orders',
    VALUE_FORMAT = 'JSON',
    TIMESTAMP = 'created_at'
);

-- Create a continuously updated materialized view
CREATE TABLE daily_order_summary AS
SELECT
    DATETOSTRING(WINDOWSTART, 'yyyy-MM-dd') AS order_date,
    COUNT(*) AS total_orders,
    SUM(total) AS total_revenue,
    AVG(total) AS average_order_value
FROM orders_stream
WINDOW TUMBLING (SIZE 1 DAY)
GROUP BY DATETOSTRING(WINDOWSTART, 'yyyy-MM-dd')
EMIT CHANGES;
```

With `EMIT CHANGES`, ksqlDB produces an updated result row every time the aggregation changes — which is every time a new order arrives. This continuously updated table is itself stored in a Kafka topic, and a backend service can subscribe to it and push updates to dashboard clients in real-time.

## Common Pitfalls and How to Avoid Them

Understanding the theory is only half the battle. Production systems reveal nuances that textbooks often omit. Here are the most important pitfalls you will encounter, and how to navigate them.

**The replication slot and WAL accumulation problem** is perhaps the most dangerous operational hazard with Debezium and CDC in PostgreSQL. A replication slot prevents PostgreSQL from cleaning up WAL files that have not been consumed by the slot's consumer. If Debezium goes down for an extended period — say, a few hours — and your system generates a high volume of writes, PostgreSQL will accumulate WAL files indefinitely, filling up your disk. When the disk is full, PostgreSQL stops accepting writes entirely. Your entire application grinds to a halt. The solution is to monitor WAL lag closely, set `max_slot_wal_keep_size` in PostgreSQL to cap WAL retention, and configure proper alerts so you know if Debezium falls behind.

**Outbox table growth** is another operational concern. If your polling publisher or Debezium relay processes messages correctly, outbox rows get marked as processed and can be periodically cleaned up. But if cleanup is neglected, the outbox table can grow to hundreds of millions of rows, making the index scans for unprocessed rows expensive. You should have a scheduled job that deletes processed outbox rows older than a certain age (say, 7 days, to give you a window for debugging if something goes wrong).

**Consumer lag and backpressure** arise when downstream services cannot keep up with the rate of events on Kafka. If the fraud detection service starts processing slowly, its consumer group offset falls behind, and Kafka must retain more and more data. Every service in a Kafka-based architecture should have lag monitoring, with alerts when consumer lag exceeds a threshold. If a service is consistently falling behind, you may need to scale it horizontally by adding more consumer instances.

**Event ordering guarantees** are a frequent source of confusion. Kafka guarantees ordering _within a single partition_. Since Debezium uses the `aggregate_id` (e.g., order ID) as the Kafka message key, all events for a given order will always go to the same partition, and therefore be processed in order by any single consumer. However, if you have multiple partitions and a consumer reading from all of them, events for _different_ orders may arrive interleaved. Design your consumers to handle interleaving gracefully — do not assume global ordering, only per-key ordering.

**Schema evolution without a registry** is a trap that many teams fall into early in a project. When you start, JSON without a Schema Registry seems simple and sufficient. But as your system grows, you will inevitably need to change event schemas. Without a Schema Registry enforcing compatibility rules, it is very easy to accidentally deploy a producer change that breaks consumers — especially in the middle of a rolling deployment where old and new versions of a service are running simultaneously. Introducing Confluent Schema Registry early, even if you start with just JSON schema validation, is a worthwhile investment.

**Clock skew and timestamp ordering** is a subtle problem in distributed systems. When you look at the `ts_ms` field in a Debezium event, it reflects the time on the database server. When your consumer records its own timestamp, it reflects the time on its server. These clocks are not perfectly synchronized. Never use timestamps as a basis for event ordering — always rely on Kafka offsets within a partition, or on the LSN from the Debezium source metadata, which is strictly monotonic and guaranteed to reflect true database ordering.
