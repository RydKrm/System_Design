# Index Strategies — A Deep Study Guide

> *"Creating an index is easy. Creating the right index — the one that serves your specific queries without burdening your writes, without wasting your storage, and without confusing your query optimizer — that is the craft. The difference between a database that crawls and one that flies is often not the hardware, not the query itself, but the precise strategic thinking that went into which columns to index, in what order, and under what conditions."*

An index is a promise you make to the database: "I will pay the cost of maintaining this structure on every write, in exchange for fast reads on the queries I care about." Like all promises, this one must be made deliberately and selectively. A table drowning in redundant, poorly designed indexes is often slower than a table with no indexes at all — because every INSERT, UPDATE, and DELETE must maintain every index on the table, turning write operations into a cascade of structural updates. Understanding index strategy is understanding *which promise to make*, and *precisely how to phrase it*, so that the database can keep it on your behalf as efficiently as possible.

This chapter explores four essential index strategies, moving from the simplest (single-column) through increasingly sophisticated designs (composite, covering, partial) that each solve a specific class of problem with increasing precision and economy.

## 1. Single-Column Index

### The Foundation of All Indexing

The single-column index is the most basic and most commonly used indexing strategy. As the name suggests, it places an index on exactly one column of a table, creating a B-Tree (or other structure) that is sorted by the values of that one column and contains a pointer from each indexed value to the corresponding table row. Everything we have discussed about B-Tree mechanics in the previous chapters applies directly here: looking up a value requires traversing the tree from root to leaf, which takes a small fixed number of page reads regardless of how many rows the table contains.

The single-column index is the natural first response whenever you identify a query that is filtering, sorting, or joining on a specific column and running slowly. It is simple to create, simple to reason about, and the query optimizer understands it perfectly. For many workloads and many tables, well-chosen single-column indexes are all you need.

### What Makes a Column a Good Candidate?

Not every column deserves an index, and understanding why requires revisiting the concept of selectivity from Chapter 4.1. A single-column index is most valuable when the column has **high cardinality** — many distinct values — so that a lookup for any given value returns a small fraction of the total rows. A primary key column (`user_id`, `order_id`) is the extreme case: every value is unique, so an index lookup returns exactly one row. An indexed column with medium cardinality (`city`, `last_name`) returns a small set of rows. These are excellent index candidates.

Conversely, a column with very low cardinality (`gender`, `is_active`, `status` with only 3-5 values) is a poor candidate for a single-column index, because any given lookup returns a large fraction of the table — large enough that the query optimizer will often prefer a full table scan over paying the cost of random I/O to fetch individual rows through the index.

```
  SINGLE-COLUMN INDEX CANDIDATE EVALUATION

  Table: orders (5,000,000 rows)

  ┌──────────────────┬──────────────┬─────────────────┬───────────────────┐
  │ Column           │ Cardinality  │ Avg rows/lookup  │ Index Value       │
  ├──────────────────┼──────────────┼─────────────────┼───────────────────┤
  │ order_id (PK)    │ 5,000,000    │ 1               │ ★★★★★ Essential    │
  │ customer_id      │ 500,000      │ 10              │ ★★★★★ Excellent    │
  │ email            │ ~5,000,000   │ 1               │ ★★★★★ Excellent    │
  │ created_at       │ ~4,500,000   │ ~1              │ ★★★★☆ Great (range)│
  │ product_id       │ 100,000      │ 50              │ ★★★☆☆ Good         │
  │ country          │ 180          │ ~27,778         │ ★★☆☆☆ Marginal     │
  │ status           │ 5            │ ~1,000,000      │ ★☆☆☆☆ Usually poor │
  │ is_deleted       │ 2            │ ~2,500,000      │ ✗ Useless alone    │
  └──────────────────┴──────────────┴─────────────────┴───────────────────┘

  The index is most useful when average rows per lookup is SMALL.
  "Small" in practice means less than roughly 1-5% of total rows.
```

### The Write Cost You Are Always Paying

It is crucial to internalize that every single-column index you create comes with a perpetual maintenance cost. Every time a row is inserted into the table, the database must also insert an entry into every index on that table. Every time a row is updated and the indexed column's value changes, the database must delete the old index entry and insert a new one. Every time a row is deleted, the corresponding index entries must be removed.

For a table with 5 single-column indexes, a single INSERT operation results in 6 write operations: one to the table and one to each index. For a table with 20 indexes, it results in 21 write operations. This write amplification is the reason you should index selectively, not exhaustively. The goal is to create exactly the indexes your queries need — no more, no fewer.

```sql
-- SINGLE-COLUMN INDEX: Creation and Usage

-- The table
CREATE TABLE orders (
    order_id    BIGINT        PRIMARY KEY,
    customer_id BIGINT        NOT NULL,
    status      VARCHAR(20)   NOT NULL,
    created_at  TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    total       DECIMAL(10,2) NOT NULL
);

-- Good single-column index: high cardinality, frequently queried
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
CREATE INDEX idx_orders_created_at  ON orders (created_at);

-- How these indexes are used:

-- Uses idx_orders_customer_id (lookup one customer's orders)
SELECT * FROM orders WHERE customer_id = 42;

-- Uses idx_orders_created_at (range scan by date)
SELECT * FROM orders
WHERE created_at >= '2024-01-01'
  AND created_at <  '2024-02-01'
ORDER BY created_at;  -- ORDER BY is FREE: index is already sorted!

-- Will NOT use an index on 'status' alone (low selectivity):
SELECT * FROM orders WHERE status = 'active';
-- → Full table scan is faster because ~80% of orders are 'active'
```

### When to Reach Beyond Single-Column Indexes

Single-column indexes are powerful for single-condition queries, but the moment a query has two or more filter conditions, you begin to face limitations. The database might use one single-column index to narrow the result and then filter the remaining rows in memory — but this is often less efficient than an index designed for both conditions together. This is where the composite index enters the picture.

## 2. Composite (Multi-Column) Index and Column Order

### Thinking in Multiple Dimensions

A **composite index** (also called a **multi-column index** or **compound index**) is an index built on two or more columns together. The indexed entries are sorted first by the first column, then by the second column *within each group of equal first-column values*, then by the third column within each group of equal first-and-second-column values, and so on. This nested sort order is the key to understanding both the immense power of composite indexes and their occasionally non-obvious limitations.

The most important concept in composite index design is the **left-prefix rule**: the database can use a composite index to answer queries that filter on any *left-contiguous prefix* of the indexed columns, but it cannot efficiently use the index if the leading (leftmost) columns are absent from the filter. If you have an index on `(a, b, c)`, the database can use it for queries filtering on `a`, on `(a, b)`, or on `(a, b, c)`. It cannot efficiently use it for queries filtering only on `b`, or only on `c`, or only on `(b, c)`.

### Visualizing the Internal Sort Order

To truly understand the left-prefix rule, you must visualize what a composite index actually looks like in its leaf pages. Imagine a composite index on `(department, salary)` for an employees table. The leaf entries are sorted first alphabetically by `department`, and then within each department, they are sorted numerically by `salary`. This is exactly like a phone book that sorts first by last name and then by first name within each last name group.

```
  COMPOSITE INDEX on (department, salary)
  Leaf pages shown in sorted order:

  ┌─────────────────────────────────────────────────────────────────┐
  │  (department='Engineering', salary=55000) → row ptr to employee │
  │  (department='Engineering', salary=72000) → row ptr             │
  │  (department='Engineering', salary=85000) → row ptr             │
  │  (department='Engineering', salary=95000) → row ptr             │
  │  (department='HR',          salary=48000) → row ptr             │
  │  (department='HR',          salary=51000) → row ptr             │
  │  (department='HR',          salary=63000) → row ptr             │
  │  (department='Marketing',   salary=58000) → row ptr             │
  │  (department='Marketing',   salary=71000) → row ptr             │
  │  (department='Marketing',   salary=79000) → row ptr             │
  └─────────────────────────────────────────────────────────────────┘

  The index is one continuous sorted sequence, sorted FIRST by department,
  THEN by salary within each department.

  QUERY A: WHERE department = 'Engineering' AND salary > 80000
  → Find 'Engineering' in the index (fast, B-Tree lookup) → scan forward
    within 'Engineering' group for salary > 80000 → returns 1 row.
  ✓ USES index efficiently. Both columns are in the query.

  QUERY B: WHERE department = 'HR'
  → Find 'HR' in the index → return all HR entries.
  ✓ USES index efficiently. First column (left prefix) is in the query.

  QUERY C: WHERE salary > 80000   (no department filter)
  → The index is NOT sorted globally by salary.
    salary=79000(Marketing), 85000(Engineering), 95000(Engineering) are scattered.
  ✗ CANNOT efficiently use this index. Must scan entire index or do full table scan.
  (A separate index on just (salary) would be needed for this query.)
```

This diagram makes the left-prefix rule feel intuitive rather than arbitrary: because the index is sorted primarily by `department`, you can jump directly to any specific department. But once you remove the department filter, there is no sorted starting point — salary values are interleaved across all departments and you have no shortcut.

### The Art of Column Ordering in Composite Indexes

Deciding the order of columns in a composite index is one of the most subtle and consequential decisions in database design. The wrong order renders the index useless for some of your most important queries. The right order makes a single index serve multiple queries efficiently. Several principles guide this decision.

The first principle is to place **equality conditions before range conditions**. If one column is filtered with `=` and another with `>` or `<`, put the equality column first. When the database evaluates an equality condition on the first column, it can jump directly to the narrow set of entries matching that value and then scan through the range on the second column. If you reverse the order (range column first), the database must scan the entire range of the first column and then filter by equality on the second — which is far less efficient because the range result set is much larger.

```
  COLUMN ORDER: Equality Before Range

  Query: WHERE department = 'Engineering' AND salary > 80000

  Index on (department, salary) — CORRECT order:
  ┌─────────────────────────────────────┐
  │ Engineering, 55000  │               │
  │ Engineering, 72000  │               │
  │ Engineering, 85000  │ ← Scan starts │ After jumping to
  │ Engineering, 95000  │   here        │ 'Engineering'
  │ HR, ...             │               │
  └─────────────────────────────────────┘
  Step 1: Jump to 'Engineering' (equality, O(log N))
  Step 2: Scan forward for salary > 80000 (range within the group)
  Pages read: very few. FAST!

  Index on (salary, department) — WRONG order for this query:
  ┌──────────────────────────────────────────────────────┐
  │ HR,48000  │ HR,51000  │ HR,63000  │ Mkt,58000  │ ... │
  │ Mkt,71000 │ Mkt,79000 │ Eng,55000 │ Eng,72000  │ ... │
  │ Eng,85000 │ Eng,95000 │ ...                          │
  └──────────────────────────────────────────────────────┘
  Step 1: Scan for salary > 80000 (large range, scattered across all departments)
  Step 2: Filter for department='Engineering' from the large result set
  Pages read: many more. SLOWER!

  RULE: Put equality columns FIRST, range columns LAST.
```

The second principle is to place **higher-cardinality columns before lower-cardinality ones**, when both are filtered with equality. A column with more distinct values narrows the search more aggressively. If you have a composite index on `(country, city, street)` where country has 180 values, city has 10,000 values, and street has 500,000 values, the most efficient query filter order is `street` first (most selective), but the most common query pattern may be `country, city` — so you design around query pattern, not just cardinality alone. Cardinality ordering matters most when you expect queries that use only some of the columns — placing higher-cardinality columns first maximizes the utility of the left-prefix rule for partial-column queries.

The third principle concerns **ORDER BY and GROUP BY**. A composite index can eliminate a sort operation if the query's `ORDER BY` clause matches the index column order. This is a free performance win — the index is already sorted, so the database can return rows in the requested order without an additional sort step. Design your composite indexes with your most common ORDER BY patterns in mind.

```sql
-- orders table: the full picture
CREATE TABLE orders (
    order_id    BIGINT        PRIMARY KEY,
    customer_id BIGINT        NOT NULL,
    status      VARCHAR(20)   NOT NULL,
    region      VARCHAR(50)   NOT NULL,
    created_at  TIMESTAMPTZ   NOT NULL,
    total       DECIMAL(10,2) NOT NULL
);

-- Scenario: Your most common query pattern is:
-- "All orders for a specific customer, filtered by status, sorted by date"
SELECT order_id, status, created_at, total
FROM orders
WHERE customer_id = 42
  AND status = 'shipped'
ORDER BY created_at DESC;

-- WRONG index ordering (range/sort column before equality columns):
CREATE INDEX idx_wrong ON orders (created_at, status, customer_id);
-- 'created_at' is first → can only use the leftmost column efficiently.
-- After scanning all created_at entries (the whole table!), filter by status, customer_id.

-- CORRECT index ordering (equality columns first, range/sort column last):
CREATE INDEX idx_correct ON orders (customer_id, status, created_at DESC);
-- Step 1: Jump to customer_id = 42 (equality → exact position in index)
-- Step 2: Within that group, jump to status = 'shipped' (equality → narrow further)
-- Step 3: Read created_at entries in descending order (already sorted!)
-- Step 4: ORDER BY created_at DESC is SATISFIED BY THE INDEX → no sort step needed!
-- Pages read: tiny. FAST. And ORDER BY is free!
```

### One Index Serving Many Queries

A beautifully designed composite index can serve multiple distinct query patterns through the power of the left-prefix rule. This is one of the most economical aspects of composite index design — rather than maintaining five separate single-column indexes, a single well-ordered composite index might serve all five query patterns at once, with lower total maintenance overhead.

```
  ONE COMPOSITE INDEX, MANY QUERY PATTERNS

  Index: (customer_id, status, created_at)
  ┌──────────────────────────────────────────────────────────────┐
  │ Queries this index can serve efficiently:                     │
  │                                                              │
  │ WHERE customer_id = 42                                       │ ← Prefix (1 col)
  │ WHERE customer_id = 42 AND status = 'shipped'                │ ← Prefix (2 cols)
  │ WHERE customer_id = 42 AND status = 'shipped'                │
  │   AND created_at > '2024-01-01'                              │ ← Prefix (3 cols)
  │ WHERE customer_id = 42 ORDER BY status                       │ ← Prefix + sort
  │ WHERE customer_id = 42 AND status = 'shipped'                │
  │   ORDER BY created_at DESC                                   │ ← Full prefix + sort
  │                                                              │
  │ Queries this index CANNOT efficiently serve:                 │
  │                                                              │
  │ WHERE status = 'shipped'            (no leading customer_id) │
  │ WHERE created_at > '2024-01-01'     (no leading customer_id) │
  │ WHERE status = 'shipped' AND created_at > '2024-01-01'       │
  │   (both conditions present but leading column missing)       │
  └──────────────────────────────────────────────────────────────┘
  For the "cannot serve" patterns, a separate index would be needed.
```

## 3. Covering Index (Index-Only Scans)

### The Goal: Never Touching the Table

In previous chapters, we introduced the concept of the **Key Lookup** — the additional step required when a non-clustered index finds matching row pointers but the query needs columns that are not stored in the index itself. For a query returning 2 rows, 2 key lookups are trivial. For a query returning 50,000 rows, 50,000 key lookups — each potentially a separate random I/O — can make an otherwise well-indexed query painfully slow.

The **Covering Index** (also called an **Index-Only Scan** in PostgreSQL, or an index with **included columns** in SQL Server) is the strategy that eliminates key lookups entirely. A covering index is one that contains every column the query needs — both the columns used for filtering (in the index key, driving the tree traversal) and the columns being selected (stored in the leaf pages). When the query optimizer recognizes that all needed data is available in the index itself, it performs an **index-only scan** — reading only index pages and never touching the underlying table at all.

The performance improvement from an index-only scan can be extraordinary. Index leaf pages are much smaller than table data pages (they store only key values and included columns, not the full row). More index entries fit in each page. More index pages fit in the buffer pool cache. The entire working set for a frequent query might fit entirely in memory once the index is cached — making subsequent runs of the same query nearly free.

### Building a Covering Index

Understanding what makes an index "covering" requires you to think clearly about exactly what a query needs. A query needs three things from the database: columns to filter rows (the `WHERE` clause), columns to return to the caller (the `SELECT` list), and columns to sort the result (the `ORDER BY` clause). If your index contains all of these columns, it covers the query completely.

```
  COVERING INDEX ANALYSIS

  Table: orders (5,000,000 rows, stored on ~62,500 data pages)

  Query (runs 10,000 times per day):
  SELECT customer_id, created_at, total
  FROM orders
  WHERE status = 'shipped'
    AND region  = 'APAC'
  ORDER BY created_at DESC;

  The query needs:
  ┌────────────────────────────────────────────────────────┐
  │ For filtering (WHERE):  status, region                 │
  │ For output (SELECT):    customer_id, created_at, total │
  │ For sorting (ORDER BY): created_at                     │
  │ Combined unique needs:  status, region, created_at,    │
  │                         customer_id, total             │
  └────────────────────────────────────────────────────────┘

  NON-COVERING index (status, region):
  Index leaf: (status, region) → row_pointer
  After index scan: must fetch customer_id, created_at, total from TABLE
  For 10,000 matching rows: 10,000 random I/O to table pages → SLOW

  COVERING index (status, region, created_at, customer_id, total):
  Index leaf: (status, region, created_at) → customer_id, total (included)
  After index scan: ALL needed data is RIGHT HERE in the index leaf page.
  Zero round-trips to the table. Pure index-only scan → FAST.
```

In SQL Server, the distinction between **key columns** (used for the B-Tree structure and sorting) and **included columns** (stored only in leaf pages, not in the tree structure) is explicit. You specify included columns with the `INCLUDE` clause. Key columns must be ordered carefully (because they affect how the tree is traversed). Included columns have no ordering requirement — they are just extra data hanging off the leaf entries.

```sql
-- The scenario: an orders table with frequent analytical queries
CREATE TABLE orders (
    order_id    BIGINT        PRIMARY KEY,
    customer_id BIGINT        NOT NULL,
    status      VARCHAR(20)   NOT NULL,
    region      VARCHAR(50)   NOT NULL,
    created_at  TIMESTAMPTZ   NOT NULL,
    total       DECIMAL(10,2) NOT NULL,
    notes       TEXT                       -- large column, rarely needed
);

-- EXAMPLE 1: Covering index for the specific query above
-- Key columns (drive traversal): status, region, created_at
-- Included columns (extra payload in leaf): customer_id, total
-- Notes is NOT included — the query doesn't need it, and it's large.
CREATE INDEX idx_orders_covering
ON orders (status, region, created_at DESC)
INCLUDE (customer_id, total);

-- EXAMPLE 2: Query that IS covered by this index
-- (Uses index-only scan — never touches the table)
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, created_at, total
FROM orders
WHERE status  = 'shipped'
  AND region  = 'APAC'
ORDER BY created_at DESC;
-- Look for "Index Only Scan" in the EXPLAIN output — that's the goal!
-- "Heap Fetches: 0" means zero table page reads. Pure index scan.

-- EXAMPLE 3: Query NOT covered (needs 'notes' column)
SELECT customer_id, created_at, total, notes  -- 'notes' not in index!
FROM orders
WHERE status = 'shipped'
  AND region = 'APAC';
-- → Falls back to "Index Scan" (not Index Only Scan)
-- → Must do key lookup to table for the 'notes' column
-- Solution: either add 'notes' to INCLUDE (expensive — large column)
--           or accept the key lookup for this less-frequent query.
```

### The Trade-Off: Index Size vs. Query Speed

A covering index is never completely free. Every column you add to the index — especially large ones like `TEXT` or `JSONB` — increases the size of each leaf entry, which means fewer entries fit per page, which means more pages in the index overall. A larger index takes more disk space, consumes more buffer pool memory, and takes longer to scan sequentially. The covering index is a deliberate trade: you are paying with space and write amplification to buy query speed.

The art of designing a covering index is therefore one of **precision and restraint**. Include only the columns that the query actually needs. Do not include large variable-length columns unless the query truly requires them. Do not include columns that are almost always available in the buffer pool from the clustered index anyway. And most importantly — design covering indexes for your most frequent and performance-critical queries, not for every query. A table littered with twenty covering indexes for twenty different queries will have catastrophic write performance.

```
  COVERING INDEX: SIZE vs. SPEED TRADE-OFF

  orders table: 5,000,000 rows

  Index on (status, region, created_at):
  Each leaf entry: ~50 bytes
  Total index size: 5M × 50 bytes = ~238 MB

  Covering index on (status, region, created_at) INCLUDE (customer_id, total):
  Each leaf entry: ~58 bytes (added 8 bytes for two extra columns)
  Total index size: 5M × 58 bytes = ~276 MB (+38 MB overhead)
  Benefit: eliminates key lookups for frequent query → dramatic speed gain.
  WORTH IT for a high-frequency query.

  Covering index INCLUDE (customer_id, total, notes):
  notes is TEXT, avg 500 bytes per row:
  Each leaf entry: ~558 bytes
  Total index size: 5M × 558 bytes = ~2.6 GB (11x larger!)
  Benefit: eliminates key lookup for 'notes'
  NOT WORTH IT — the index is now larger than the table itself,
  costs enormous extra RAM to cache, and slows every write.
  Include 'notes' only if this query runs millions of times per second.
```

### Recognizing Index-Only Scans in Query Plans

In PostgreSQL, you can confirm whether an index-only scan is occurring by running `EXPLAIN (ANALYZE, BUFFERS)` and looking for the text `Index Only Scan` rather than `Index Scan`. The former never touches the heap (table). The key metric to look at is `Heap Fetches: 0` in the EXPLAIN output — zero heap page reads means the query is fully covered by the index. If `Heap Fetches` is non-zero, the index is not fully covering the query and the database is making additional table page reads for at least some rows.

## 4. Partial Index (Filtered Index)

### Indexing Only What Matters

A **Partial Index** (called a **Filtered Index** in SQL Server) is perhaps the most elegant and economical of all index strategies. The core idea is beautifully simple: instead of building an index over all rows in a table, you build an index over only the subset of rows that satisfy a specific condition. Rows that do not satisfy the condition are simply not included in the index at all — as if they do not exist, from the index's perspective.

This targeted approach has profound consequences. The index is much smaller (potentially orders of magnitude smaller) than a full-table index on the same column, because it contains far fewer entries. Smaller means faster to scan, faster to load into memory, and cheaper to maintain on writes (because most inserts and updates do not touch the indexed subset). The query optimizer, when presented with a query that matches the partial index's condition, can use this small, precise index for lightning-fast retrieval of exactly the rows it cares about.

### The Motivating Problem: Skewed Data Distributions

Partial indexes shine when your data has a **highly skewed distribution** — where the vast majority of rows share one value and a small minority have another. This is one of the most common real-world patterns in database tables, and it is precisely the situation where a full-table index fails to help and a partial index excels.

Consider an `orders` table with 10 million rows. At any given time, perhaps 9.8 million orders are in a final state (`delivered`, `cancelled`, `refunded`) and only 200,000 orders are in an active, work-in-progress state (`pending`, `processing`, `shipped`). Your application's most frequent and most time-sensitive queries are those that process active orders — queries like "show me all pending orders for the warehouse team" or "find all in-flight orders for this customer." These queries are on the 200,000-row active minority. A full index on `status` is largely useless for these queries (low selectivity on the full table). But a partial index that indexes *only* the active orders is an index of just 200,000 entries — 2% of the table — with perfect selectivity for exactly the queries you care about.

```
  PARTIAL INDEX: Indexing Only the Active Minority

  orders table: 10,000,000 rows
  ┌─────────────────────────────────────────────────────────────┐
  │ Status Distribution:                                        │
  │   'delivered'  → 7,500,000 rows (75%)  ──┐                 │
  │   'cancelled'  → 1,500,000 rows (15%)    │  FINAL STATES   │
  │   'refunded'   →   800,000 rows  (8%)  ──┘  (9.8M rows)   │
  │                                                             │
  │   'pending'    →    80,000 rows (<1%)  ──┐                 │
  │   'processing' →    70,000 rows (<1%)    │  ACTIVE STATES  │
  │   'shipped'    →    50,000 rows (<1%)  ──┘  (200K rows)   │
  └─────────────────────────────────────────────────────────────┘

  FULL index on (status, created_at):
  Contains 10,000,000 entries.
  Index size: ~500 MB
  Selectivity for 'active' queries: 200K/10M = 2%
  (Still reasonably good, but the index is huge and costly to maintain)

  PARTIAL index on (status, created_at) WHERE status IN ('pending','processing','shipped'):
  Contains only 200,000 entries (2% of total rows!).
  Index size: ~10 MB  (50x smaller!)
  Selectivity: near-perfect — every entry in this index is a truly active order.
  Maintenance cost: Only inserts/updates of ACTIVE orders touch this index.
  The 9.8 million final-state rows don't touch it at all.

  Comparison diagram:

  Full index:   |████████████████████████████████████████████████|  500 MB
  Partial index:|█|                                                   10 MB
                 └── Same query performance, 50x smaller, 50x cheaper to maintain!
```

### Creating and Using Partial Indexes

The syntax for a partial index adds a `WHERE` clause to the `CREATE INDEX` statement. The condition in this `WHERE` clause defines the subset of rows to be indexed. For the database to use a partial index on a given query, the query's own `WHERE` clause must *imply* the partial index's filter condition — the optimizer must be able to prove that every row the query could return is a row that would have been included in the partial index.

```sql
-- orders table
CREATE TABLE orders (
    order_id    BIGINT        PRIMARY KEY,
    customer_id BIGINT        NOT NULL,
    status      VARCHAR(20)   NOT NULL,
    created_at  TIMESTAMPTZ   NOT NULL,
    total       DECIMAL(10,2) NOT NULL
);

-- PARTIAL INDEX 1: Index only active/in-flight orders
-- Only 200,000 of 10,000,000 rows are indexed!
CREATE INDEX idx_orders_active
ON orders (customer_id, created_at DESC)
WHERE status IN ('pending', 'processing', 'shipped');

-- This query USES the partial index (its WHERE implies the partial index condition):
SELECT order_id, status, created_at, total
FROM orders
WHERE customer_id = 42
  AND status IN ('pending', 'processing', 'shipped')
ORDER BY created_at DESC;
-- → Index scan on idx_orders_active (only 200K entries!) → VERY FAST

-- This query does NOT use the partial index (might include final-state orders):
SELECT order_id, status, created_at, total
FROM orders
WHERE customer_id = 42;  -- No status filter → optimizer cannot guarantee
                          -- result only contains 'active' rows → cannot use partial index
-- → Uses a different index (or full scan) instead

-- PARTIAL INDEX 2: Unique email only among non-deleted users (soft-delete pattern!)
-- Solves the unique constraint problem from soft-delete chapter:
CREATE UNIQUE INDEX idx_users_unique_active_email
ON users (email)
WHERE deleted_at IS NULL;
-- Meaning: No two ACTIVE users can share the same email.
-- A deleted user's email is not in this index → can be re-used by a new registration.

-- PARTIAL INDEX 3: Index only failed payment transactions (rare, high-value rows)
CREATE INDEX idx_payments_failed
ON payments (created_at, customer_id)
WHERE status = 'failed';
-- Perhaps only 0.5% of payments fail. This index is tiny.
-- Queries that investigate failed payments use this precise, fast index.
-- The 99.5% of successful payments don't burden this index at all.
```

### Partial Indexes for Unique Constraints on Subsets

One of the most elegant applications of the partial index is solving the **conditional uniqueness** problem — situations where a uniqueness constraint should apply only to a subset of rows. We encountered exactly this scenario in the soft-delete chapter: you want email addresses to be unique among active users, but deleted users' email addresses should be allowed to be "reused" by new registrations.

A full unique index on `email` enforces uniqueness across all rows, including deleted ones — making it impossible for a new user to register with an email used by a previously deleted account. A partial unique index on `email WHERE deleted_at IS NULL` enforces uniqueness only among the non-deleted rows — which is precisely the business rule you actually want. The deleted rows are simply invisible to the index, and their emails can be freely reused.

```
  PARTIAL UNIQUE INDEX: Conditional Uniqueness

  users table:
  +----+----------------------+-----------+---------------------+
  | id | email                | name      | deleted_at          |
  +----+----------------------+-----------+---------------------+
  |  1 | alice@example.com    | Alice     | 2024-01-15 10:00:00 |  ← deleted
  |  2 | bob@example.com      | Bob       | NULL                |  ← active
  |  3 | carol@example.com    | Carol     | NULL                |  ← active
  +----+----------------------+-----------+---------------------+

  FULL unique index on (email):
  Contains: alice@example.com (id=1), bob@example.com (id=2), carol@example.com (id=3)
  Attempt to insert: alice@example.com → BLOCKED! (even though original alice is deleted)

  PARTIAL unique index on (email) WHERE deleted_at IS NULL:
  Contains ONLY: bob@example.com (id=2), carol@example.com (id=3)
  (alice's row has deleted_at IS NOT NULL → not in the index!)
  Attempt to insert: alice@example.com with deleted_at=NULL → ALLOWED! ✓
  Business rule is correctly enforced: unique among active users only.
```

### Performance and Maintenance Advantages of Partial Indexes

The maintenance advantage of partial indexes deserves special emphasis. Because the index only includes rows matching the filter condition, write operations on rows *outside* that condition incur zero index maintenance cost. In the active-orders example, when a delivery worker marks an order as `delivered` (updating `status` from `shipped` to `delivered`), the row transitions from being inside the partial index's condition to being outside it. The database removes the row from the partial index — a single deletion operation. All subsequent inserts and updates to this now-delivered order cost nothing in index maintenance, because the order is no longer tracked by the partial index. For a table where 98% of rows are in a final, unchanging state, this is a massive reduction in write amplification.

```
  PARTIAL INDEX WRITE COST ANALYSIS

  Full index on (status, customer_id):
  ┌─────────────────────────────────────────────────────────────────┐
  │ Every insert → update index (10M entries total)                 │
  │ Every update to status → delete old entry + insert new entry    │
  │ Even updating a 'delivered' order (just changing notes field)   │
  │   might still require checking index for status consistency.    │
  └─────────────────────────────────────────────────────────────────┘

  Partial index on (customer_id) WHERE status IN ('pending','processing','shipped'):
  ┌─────────────────────────────────────────────────────────────────┐
  │ New order inserted as 'pending'  → Added to index (200K set)   │
  │ Order updated to 'processing'    → No index change (still in)  │
  │ Order updated to 'shipped'       → No index change (still in)  │
  │ Order updated to 'delivered'     → Removed from index          │
  │ Order is 'delivered', then notes │                             │
  │   column updated                 → Index NOT touched at all!   │
  │                                    (row is outside filter)     │
  │ 98% of writes on this table don't touch this index at all!     │
  └─────────────────────────────────────────────────────────────────┘
```

## Summary: The Four Strategies and When to Choose Each

These four index strategies are not competitors — they are complementary tools that you reach for in different situations, and the most effective database designs combine all four intelligently. A single-column index is your first line of defense for any frequently queried column. A composite index emerges when multiple columns appear together in your most important queries, and the precise column ordering becomes an art form shaped by your actual query patterns. A covering index is the decisive step you take when a query is critical and frequent enough that even the cost of key lookups is unacceptable. And a partial index is the surgical tool you deploy when your data is skewed and you want to build a small, fast, low-cost index that serves a specific, important minority of your rows with maximum efficiency.

```
  INDEX STRATEGY SELECTION GUIDE

  ┌────────────────────┬────────────────────────────────────────────────────┐
  │  Strategy          │  Choose When...                                    │
  ├────────────────────┼────────────────────────────────────────────────────┤
  │  Single-Column     │  A single high-cardinality column appears in WHERE │
  │  Index             │  or JOIN. The simplest and most common case.       │
  ├────────────────────┼────────────────────────────────────────────────────┤
  │  Composite Index   │  Two or more columns appear together in frequent   │
  │  (Multi-Column)    │  WHERE, JOIN, or ORDER BY. Order columns: equality │
  │                    │  first, range/sort last. Serves multiple queries   │
  │                    │  via left-prefix rule.                             │
  ├────────────────────┼────────────────────────────────────────────────────┤
  │  Covering Index    │  A high-frequency query still requires key lookups │
  │  (Index-Only Scan) │  even after having a good filtering index. Add     │
  │                    │  SELECT and ORDER BY columns to INCLUDE clause to  │
  │                    │  achieve zero table reads. Use with restraint.     │
  ├────────────────────┼────────────────────────────────────────────────────┤
  │  Partial Index     │  Data is skewed: a small, high-value subset needs  │
  │  (Filtered Index)  │  fast access while the majority of rows are in a  │
  │                    │  final/inactive state. Also for conditional unique │
  │                    │  constraints (soft delete + uniqueness).           │
  └────────────────────┴────────────────────────────────────────────────────┘

  DESIGN CHECKLIST for any new index:

  [ ] What queries does this index serve? (Be specific)
  [ ] What is the cardinality of each indexed column?
  [ ] Are equality columns placed before range columns?
  [ ] Does the ORDER BY pattern match the index key order?
  [ ] Should this be a partial index? (Is the data skewed?)
  [ ] Should this be a covering index? (Are key lookups still happening?)
  [ ] How many writes per second hit this table? (Write amplification)
  [ ] How much storage will this index consume?
  [ ] Is this index actually being used? (Check pg_stat_user_indexes)
```

The deepest truth about index strategy is this: indexes are not decorations you sprinkle on a table hoping they will help. They are structural decisions with real costs and real benefits, and the best database engineers treat each one as a deliberate engineering commitment — designed for a specific query pattern, measured against real workload data, and revisited as the application and its data evolve. An index that was perfect on day one may be obsolete or harmful on day one thousand. The discipline of indexing is a living, ongoing practice, not a one-time design task.
