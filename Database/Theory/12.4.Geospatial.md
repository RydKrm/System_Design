## A Letter from Your DBA Mentor Before We Begin

Most backend developers have written location-based features without truly understanding what they were doing. They stored latitude and longitude as two separate `FLOAT` columns, computed distances with a formula they copied from Stack Overflow, and built queries that scan every row in the table to find the nearest restaurant. It works, barely, until the table has a million rows, the distance formula turns out to be subtly wrong at certain latitudes, and someone discovers that "within 5 kilometres" means different things near the equator versus near the poles.

Today we fix all of that. We are going to study PostGIS — the PostgreSQL extension that turns your database into a full geographic information system — and understand it at the level where you know not just what to call but why it works, what the performance characteristics are, and where the traps are.

PostGIS is used in production by some of the most geospatially intensive applications on earth: OpenStreetMap stores the world's roads, buildings, and borders in PostgreSQL with PostGIS. Uber and Lyft calculate driver-to-rider proximity at scale using PostGIS or PostGIS-inspired approaches. Food delivery platforms, real estate applications, logistics systems, and ride-hailing services all rely on the same concepts we will study today.

The crucial thing to understand before we start: **the Earth is not flat, and treating it as flat causes real errors.** A coordinate system that works in a flat plane does not work on a sphere. The distance between two points expressed as latitude/longitude is not what a flat-plane formula says it is, especially at high latitudes or over long distances. PostGIS handles all of this correctly, and understanding how is the foundation of everything else in this guide.

## 1. Setting Up PostGIS

PostGIS is a PostgreSQL extension — it extends the database with new data types, functions, and operators for working with spatial data. It must be installed at the operating system level first, then enabled per-database.

```sql
-- INSTALLATION (OS-level, then per-database):
-- Ubuntu/Debian:  apt-get install postgresql-16-postgis-3
-- macOS (brew):   brew install postgis
-- Docker: use image postgis/postgis:16-3.4

-- Enable in each database that needs spatial features:
CREATE EXTENSION postgis;

-- Verify installation:
SELECT PostGIS_Full_Version();
-- Returns: POSTGIS="3.4.0 ..." PGSQL="160" GEOS="3.12.0"
--          PROJ="9.3.0" LIBXML="2.10.3" LIBJSON="0.17"

-- Optional extensions (useful for specific use cases):
CREATE EXTENSION postgis_topology;  -- Topological data structures
CREATE EXTENSION postgis_raster;    -- Raster (grid/satellite image) data
CREATE EXTENSION address_standardizer;  -- Address normalisation
CREATE EXTENSION fuzzystrmatch;     -- Needed for soundex-based address matching

-- Check spatial_ref_sys table (coordinate reference systems):
SELECT COUNT(*) FROM spatial_ref_sys;
-- Should return: 8500+ (all standard coordinate reference systems)
```

## 2. How Spatial Data is Represented — The Conceptual Foundation

Before touching any PostGIS function, you need a solid understanding of how spatial data is structured. PostGIS implements the **OGC Simple Features** standard — a widely adopted specification that defines how geometric shapes are represented and manipulated in databases. Every spatial object in PostGIS is one of a small set of fundamental geometry types, composable into collections.

A **Point** is the most fundamental spatial object — a single location in space, defined by an X coordinate (longitude), a Y coordinate (latitude), and optionally a Z coordinate (elevation) and an M coordinate (measure, like time along a route). When you store a restaurant's location, a user's GPS position, or a sensor's placement, you store a Point.

A **LineString** is an ordered sequence of Points connected by straight line segments. Roads, rivers, routes, and paths are all LineStrings. The line between any two consecutive points in a LineString is a straight line in the coordinate system — which on a sphere means a great circle arc if you are using geographic coordinates.

A **Polygon** is a closed ring of line segments enclosing an area, optionally with interior rings (holes). A city boundary, a building footprint, a delivery zone, a national park boundary — all are Polygons. The first and last point of a Polygon's exterior ring must be identical (closing the ring). Interior rings (holes) represent areas excluded from the polygon, like a lake inside a park.

**Multi-geometry types** — MultiPoint, MultiLineString, MultiPolygon, GeometryCollection — allow grouping multiple geometries of the same or mixed types into a single value. France's territory includes overseas territories scattered across the globe; its border cannot be represented as a single Polygon, but a MultiPolygon captures it correctly.

```
POSTGIS GEOMETRY HIERARCHY — The Type System:

Geometry (abstract base)
├── Point                    → Single location: POINT(88.3517 23.7807)
├── LineString               → Sequence of points: LINESTRING(0 0, 1 1, 2 0)
├── Polygon                  → Closed ring + optional holes:
│                              POLYGON((0 0, 4 0, 4 4, 0 4, 0 0))
│                              POLYGON((0 0, 10 0, 10 10, 0 10, 0 0),
│                                      (2 2, 2 4, 4 4, 4 2, 2 2))  ← with hole
├── MultiPoint               → Group of points
├── MultiLineString          → Group of linestrings
├── MultiPolygon             → Group of polygons (e.g., France)
└── GeometryCollection       → Mixed types in one value

TEXT REPRESENTATION FORMATS:

WKT (Well-Known Text) — human readable:
  'POINT(88.3517 23.7807)'
  'LINESTRING(88.35 23.78, 88.36 23.79, 88.37 23.80)'
  'POLYGON((88.35 23.78, 88.40 23.78, 88.40 23.83, 88.35 23.83, 88.35 23.78))'

WKB (Well-Known Binary) — efficient binary encoding for storage:
  Bytes: 0101000000... (hex-encoded binary)
  Used internally by PostGIS and in wire protocol

EWKT (Extended WKT) — PostGIS extension with SRID prefix:
  'SRID=4326;POINT(88.3517 23.7807)'
  Includes the coordinate reference system identifier

GeoJSON — web-standard format, compatible with JavaScript/Leaflet/Mapbox:
  { "type": "Point", "coordinates": [88.3517, 23.7807] }
  { "type": "Polygon", "coordinates": [[[88.35,23.78],...]] }
```

## 3. Geometry vs Geography — The Most Important Choice You Make

This is the most consequential decision in PostGIS schema design, and it is misunderstood far more often than any other aspect of spatial databases. Getting it wrong means your distance calculations are subtly incorrect, your radius queries include or exclude wrong results, and the errors grow larger as the distances involved increase.

### 3.1 The Geometry Type — Flat Earth Mathematics

The `geometry` type treats coordinates as points in a **flat, two-dimensional Cartesian plane** (or three-dimensional, for 3D geometry). Distance, area, and length calculations are done with Euclidean geometry — the same formulas that work on a flat piece of paper. The coordinate values themselves can be anything: longitude/latitude in degrees, UTM coordinates in metres, or a completely arbitrary coordinate system for something like a building floor plan.

When you use `geometry` with longitude/latitude coordinates and compute `ST_Distance(a, b)`, PostGIS returns the distance in degrees — not kilometres, not miles, but degrees of arc. This is often not what you want. Furthermore, a degree of longitude represents very different physical distances depending on latitude: one degree of longitude at the equator is about 111 kilometres, but at 60° north latitude it is only 55 kilometres. The flat-earth calculation ignores this entirely.

### 3.2 The Geography Type — Curved Earth Mathematics

The `geography` type treats coordinates as points on the surface of a **spheroid** (specifically the WGS84 ellipsoid — the model the GPS system uses for the Earth's shape). Distance, area, and length calculations account for the Earth's curvature. `ST_Distance` returns metres. `ST_DWithin` takes a radius in metres. `ST_Area` returns square metres. Everything is in real-world units.

The downside of `geography` is that spheroidal calculations are significantly more computationally expensive than flat-plane calculations. The mathematics of geodesy is complex. Most spatial functions work correctly with `geography`, but some advanced operations (certain polygon intersections, for example) must be cast to `geometry` first, which adds the flat-earth approximation error for that specific operation.

```
GEOMETRY vs GEOGRAPHY — Visual Intuition:

Geometry (flat):
  ┌────────────────────────────────────┐
  │  (0°,0°)         (90°,0°)         │  ← The plane
  │                                   │
  │  ●────────────────●               │
  │  London           Mumbai           │
  │  Distance = √((90-0)² + (19-51)²)│
  │           = √(8100 + 1024)        │
  │           = 95.5°                 │   ← Meaningless in km without conversion
  │           (approximately 10,600km │
  │            if you multiply by 111,│
  │            but wrong at this scale)
  └────────────────────────────────────┘

Geography (spheroid):
            .''''.
        .''        ''`.
      .'  ●London     '.        ← On the actual curved Earth surface
     /   (0°W, 51°N)   \
    |                   |       The shortest path between London and Mumbai
     \   (72°E, 19°N)  /        is a great circle arc (curved on the map,
      `.   ●Mumbai   .'         straight on the sphere)
        `'.        .''
            ''''''
  ST_Distance returns: 7,202,000 metres (7,202 km)  ← Correct geodetic distance
```

```sql
-- ─────────────────────────────────────────────────────────────────
-- CREATING GEOMETRY COLUMNS:

CREATE TABLE locations_geometry (
    id      BIGSERIAL PRIMARY KEY,
    name    TEXT NOT NULL,
    -- SRID 4326 = WGS84 longitude/latitude (but using FLAT MATH):
    location GEOMETRY(Point, 4326)
);

-- Insert with ST_MakePoint(longitude, latitude):
-- IMPORTANT: PostGIS convention is LONGITUDE FIRST, then LATITUDE
-- (X = longitude, Y = latitude — same as mathematical (x,y) order)
INSERT INTO locations_geometry (name, location)
VALUES ('Dhaka', ST_SetSRID(ST_MakePoint(90.4125, 23.8103), 4326));
-- Or using WKT:
INSERT INTO locations_geometry (name, location)
VALUES ('London', ST_GeomFromText('POINT(-0.1276 51.5074)', 4326));

-- ─────────────────────────────────────────────────────────────────
-- CREATING GEOGRAPHY COLUMNS:

CREATE TABLE locations_geography (
    id       BIGSERIAL PRIMARY KEY,
    name     TEXT NOT NULL,
    -- geography type always uses WGS84 (SRID 4326 implied):
    location GEOGRAPHY(Point, 4326)
);

INSERT INTO locations_geography (name, location)
VALUES ('Dhaka',  ST_MakePoint(90.4125, 23.8103)::GEOGRAPHY);
INSERT INTO locations_geography (name, location)
VALUES ('London', ST_MakePoint(-0.1276, 51.5074)::GEOGRAPHY);

-- ─────────────────────────────────────────────────────────────────
-- THE DIFFERENCE IN DISTANCE CALCULATION:

-- Distance using geometry (flat-earth):
SELECT ST_Distance(
    ST_GeomFromText('POINT(90.4125 23.8103)', 4326),   -- Dhaka
    ST_GeomFromText('POINT(-0.1276 51.5074)', 4326)    -- London
);
-- Returns: 91.9° (degrees of arc — useless without conversion!)

-- Distance using geography (spheroid — correct geodetic distance):
SELECT ST_Distance(
    ST_GeogFromText('POINT(90.4125 23.8103)'),         -- Dhaka
    ST_GeogFromText('POINT(-0.1276 51.5074)')          -- London
);
-- Returns: 8,228,814 metres = 8,229 km  ← Correct!

-- Geography with unit conversion:
SELECT
    ST_Distance(
        ST_GeogFromText('POINT(90.4125 23.8103)'),
        ST_GeogFromText('POINT(-0.1276 51.5074)')
    ) / 1000 AS distance_km,

    ST_Distance(
        ST_GeogFromText('POINT(90.4125 23.8103)'),
        ST_GeogFromText('POINT(-0.1276 51.5074)')
    ) / 1609.344 AS distance_miles;
```

### 3.3 The Decision Rule

Use `geography` when your coordinates are longitude/latitude (WGS84) and you are working with distances that matter in real-world units — restaurant radius search, driver-to-rider proximity, delivery zone coverage, anything where accuracy over distances greater than a few kilometres matters.

Use `geometry` when: you are working in a local projected coordinate system (UTM, State Plane) where distances are already in metres and the flat-earth approximation is accurate within your area; you need operations that `geography` does not support (certain topological operations); you need maximum performance and you are already applying a flat-earth correction yourself; or you are working with non-geographic data (building floor plans, game maps, image coordinates).

```
DECISION GUIDE:

Your use case                          │ Type      │ Why
───────────────────────────────────────┼───────────┼──────────────────────────
Restaurant/store proximity (lat/lng)   │ geography │ Correct distance in metres
Driver location tracking (GPS data)    │ geography │ Real-world accuracy needed
City/country boundary polygons         │ geography │ Areas span significant arc
Delivery zone radius (5km circle)      │ geography │ 5km means 5km everywhere
Building floor plan coordinates        │ geometry  │ Flat, local coordinate system
Local neighbourhood (<10km area)       │ geometry  │ Flat-earth error negligible
Country that uses UTM projection       │ geometry  │ Already in metres, flat OK
GeoJSON from web APIs (lat/lng)        │ geography │ WGS84 input → spheroid calc
Game world coordinates                 │ geometry  │ Not Earth, no curvature
Satellite imagery pixel coordinates    │ geometry  │ Not Earth surface points
```

## 4. Coordinate Reference Systems — The Language of Location

A coordinate like (90.4125, 23.8103) is meaningless without knowing what coordinate system it belongs to. Is it longitude/latitude in degrees? Is it a grid coordinate in metres? Is it a position on a local city map? A **Spatial Reference ID (SRID)** is a numeric code that identifies a specific coordinate reference system (CRS), defining exactly how to interpret the numbers.

The SRID that virtually all modern applications use is **4326**, which refers to the **WGS84** system — the coordinate system used by GPS, Google Maps, OpenStreetMap, and essentially every modern geographic application. WGS84 expresses positions as longitude (−180° to +180°) and latitude (−90° to +90°) on the WGS84 ellipsoidal model of the Earth.

```sql
-- ─────────────────────────────────────────────────────────────────
-- QUERYING SPATIAL_REF_SYS — Understanding coordinate systems:

-- WGS84 (the standard for GPS/Google Maps):
SELECT srid, srtext, proj4text
FROM spatial_ref_sys
WHERE srid = 4326;
-- srtext: GEOGCS["WGS 84",DATUM["WGS_1984",...],
--          PRIMEM["Greenwich",0],UNIT["degree",0.0174532925199433]]
-- proj4text: +proj=longlat +datum=WGS84 +no_defs

-- Web Mercator (used by Google Maps/OpenStreetMap for DISPLAY tiles):
SELECT srid, srtext FROM spatial_ref_sys WHERE srid = 3857;
-- Note: SRID 3857 projects the spherical Earth onto a flat plane in metres.
-- Useful for display but distorts areas (Greenland looks as big as Africa).
-- DO NOT use for distance calculations — use 4326 geography instead.

-- UTM Zone 45N (covers Bangladesh — distances in metres, flat-earth):
SELECT srid FROM spatial_ref_sys WHERE srtext LIKE '%UTM zone 45N%';
-- SRID = 32645

-- ─────────────────────────────────────────────────────────────────
-- CHECKING AND CONVERTING BETWEEN SRIDS:

-- Get the SRID of an existing geometry:
SELECT ST_SRID(location) FROM locations_geometry WHERE id = 1;
-- Returns: 4326

-- Transform from WGS84 to UTM Zone 45N (Bangladesh):
SELECT ST_Transform(
    ST_SetSRID(ST_MakePoint(90.4125, 23.8103), 4326),  -- WGS84 point
    32645                                               -- Transform to UTM 45N
);
-- Returns geometry in UTM coordinates (metres from UTM origin)
-- Useful when you need precise metre-based calculations in a local area.
```

## 5. Spatial Indexes — GiST and BRIN

Without spatial indexes, every spatial query requires a full table scan — computing the spatial relationship between the query geometry and every row in the table. For a table with one million locations, finding which ones are within 5 kilometres of a given point would require one million distance calculations. A spatial index reduces this to a handful of index lookups.

### 5.1 GiST — The Standard Spatial Index

The **Generalised Search Tree (GiST)** is PostgreSQL's extensible index framework that PostGIS uses for spatial indexing. A GiST spatial index is built on **minimum bounding rectangles (MBRs)** — the smallest axis-aligned rectangle that completely contains each geometry. The index organises these bounding boxes in a hierarchical tree structure where parent boxes contain all their children's boxes, allowing the query engine to prune entire branches of the tree when the branch's bounding box does not intersect the query region.

This bounding-box approach means a GiST spatial index involves two phases: the **index scan phase** finds all rows whose bounding box intersects the query region (fast), and the **refinement phase** applies the precise spatial predicate to the candidates returned by the index scan (slower, but far fewer candidates than a full table scan). This two-phase architecture is why spatial queries in PostGIS are fast even for complex polygons — the expensive exact computation only runs on a small set of candidates.

```sql
-- ─────────────────────────────────────────────────────────────────
-- CREATING SPATIAL INDEXES:

-- Standard GiST index on geometry column (most common):
CREATE INDEX idx_restaurants_location
    ON restaurants
    USING GIST (location);
-- Equivalent for geography columns:
CREATE INDEX idx_drivers_location
    ON drivers
    USING GIST (location::geometry);
-- geography uses GIST too; PostGIS handles it transparently.

-- GiST directly on geography type:
CREATE INDEX idx_drivers_location_geo
    ON drivers
    USING GIST (location);
-- Works directly for geography columns — PostGIS handles the spheroid math.

-- 3D GiST index (for 3D geometries with elevation):
CREATE INDEX idx_flights_position
    ON flights
    USING GIST (position gist_geometry_ops_nd);
-- nd = n-dimensional; enables 3D spatial queries.

-- Partial GiST index (only active/visible features):
CREATE INDEX idx_active_restaurants
    ON restaurants
    USING GIST (location)
    WHERE deleted_at IS NULL AND is_active = TRUE;
-- Smaller index, faster for the common case (searching active restaurants).

-- ─────────────────────────────────────────────────────────────────
-- HOW THE INDEX WORKS — Understanding the Two-Phase Query:

EXPLAIN (ANALYZE, BUFFERS)
SELECT name FROM restaurants
WHERE ST_DWithin(location::geography,
                 ST_MakePoint(90.4125, 23.8103)::geography,
                 5000);  -- 5000 metres

-- Plan:
-- Bitmap Heap Scan on restaurants  (exact filter applied here)
--   Recheck Cond: (location && ...)
--   Filter: ST_DWithin(location::geography, '...', 5000)
--   ->  Bitmap Index Scan on idx_restaurants_location
--         Index Cond: (location && ...)   ← Bounding box filter (fast!)
--
-- PHASE 1 (Index Scan): Find all rows whose bounding box intersects
--         the 5km radius bounding box. Returns ~1.2x the actual matches
--         due to bounding box approximation.
-- PHASE 2 (Heap Scan + Recheck): Apply exact ST_DWithin to the candidates.
--         Eliminates the bounding-box false positives (corners of the square).

-- ─────────────────────────────────────────────────────────────────
-- GiST INDEX TUNING:

-- fillfactor: lower fill factor leaves room for updates
-- (spatial data that moves frequently, like vehicle locations):
CREATE INDEX idx_vehicles_location
    ON vehicles
    USING GIST (location)
    WITH (fillfactor = 70);  -- 70% fill, more room for in-place updates

-- CLUSTER: physically re-order table rows by spatial proximity.
-- Dramatically speeds up range queries by improving buffer cache locality:
CLUSTER restaurants USING idx_restaurants_location;
-- Warning: CLUSTER acquires an ACCESS EXCLUSIVE lock and rewrites the table.
-- Run during maintenance windows. Must be re-run periodically as data changes.
```

### 5.2 BRIN — Block Range Index for Spatial Data

The **BRIN (Block Range Index)** stores the bounding box of all spatial values in each physical block (group of pages) of the table. It is an extremely small index — often 1,000× smaller than a GiST index — but it is only effective when the table's spatial data has **natural physical ordering** (rows that are geographically near each other are also stored near each other in the table's physical layout).

```sql
-- BRIN SPATIAL INDEX:
CREATE INDEX idx_orders_pickup_brin
    ON orders
    USING BRIN (pickup_location)
    WITH (pages_per_range = 32);  -- Group 32 pages per BRIN entry (default: 128)

-- BRIN is appropriate when:
-- 1. Data is inserted in roughly geographic order (e.g., logs from a single city
--    that are inserted as events happen in a known geographic flow)
-- 2. Table is extremely large (100M+ rows) and GiST would be too large
-- 3. The data is rarely updated (BRIN accuracy degrades as unordered inserts occur)
-- 4. You are pre-processing and loading data sorted by spatial grid cells

-- BRIN is INAPPROPRIATE for:
-- 1. Point-of-interest tables (restaurants, hotels — geographically scattered)
-- 2. User/driver location tables (constantly updating, no geographic order)
-- 3. Any table where you need precision on small radius queries

-- CHECKING INDEX SIZE COMPARISON:
SELECT
    indexname,
    pg_size_pretty(pg_relation_size(indexname::REGCLASS)) AS size,
    indexdef
FROM pg_indexes
WHERE tablename = 'restaurants';
-- GiST index: ~120MB for 1M restaurants
-- BRIN index: ~100KB for same table (1200x smaller, but much less precise)
```

## 6. Common Spatial Queries

### 6.1 Within Radius / Distance Filter

Finding all features within a specified distance of a point is the most common spatial query in applications — "find restaurants within 2 km", "find drivers within 500 metres", "find all orders within 10 km of this depot".

```sql
-- ─────────────────────────────────────────────────────────────────
-- RADIUS SEARCH — Using geography (correct distance in metres):

-- Find all restaurants within 2 km of the user's location:
SELECT
    r.id,
    r.name,
    r.cuisine,
    r.rating,
    ST_Distance(
        r.location::geography,
        ST_MakePoint(90.4125, 23.8103)::geography
    ) AS distance_metres
FROM restaurants r
WHERE ST_DWithin(
    r.location::geography,
    ST_MakePoint(90.4125, 23.8103)::geography,  -- User's position (lng, lat)
    2000                                          -- Radius in METRES (geography!)
)
ORDER BY distance_metres ASC
LIMIT 20;

-- ST_DWithin on geography: uses GIST index efficiently.
-- Returns distances in metres. Accurate on the spheroid.
-- Accounts for Earth's curvature — 2000m means 2000m everywhere.

-- ─────────────────────────────────────────────────────────────────
-- THE WRONG WAY — Geometry with degree-based distance (common mistake):

-- WRONG: This does NOT use the index correctly and distance is in DEGREES
SELECT * FROM restaurants
WHERE ST_DWithin(
    location,                                    -- geometry, not geography
    ST_MakePoint(90.4125, 23.8103),
    0.018                                        -- Approximate degrees for 2km
);
-- Problems:
-- 1. 0.018° is approximately 2km at the equator but varies by latitude
-- 2. The GiST index IS used but with a bounding box in degrees (imprecise)
-- 3. Still requires expensive ST_DWithin calculation on candidates
-- 4. Results slightly wrong due to flat-earth assumption

-- ─────────────────────────────────────────────────────────────────
-- RADIUS SEARCH with distance included in result:

WITH user_location AS (
    SELECT ST_MakePoint(90.4125, 23.8103)::geography AS point
)
SELECT
    r.id,
    r.name,
    r.cuisine,
    r.rating,
    r.average_delivery_time_mins,
    ROUND(
        (ST_Distance(r.location::geography, u.point) / 1000)::NUMERIC,
        2
    )  AS distance_km,
    -- Rough walking time estimate:
    ROUND(
        (ST_Distance(r.location::geography, u.point) / 83.3)::NUMERIC
    ) AS walk_minutes  -- ~5 km/h = 83.3 m/minute
FROM restaurants r
CROSS JOIN user_location u
WHERE r.is_active = TRUE
  AND r.deleted_at IS NULL
  AND ST_DWithin(r.location::geography, u.point, 2000)
ORDER BY distance_km ASC;

-- ─────────────────────────────────────────────────────────────────
-- RADIUS SEARCH with dynamic radius (variable by user preference):

CREATE OR REPLACE FUNCTION find_nearby_restaurants(
    p_longitude  FLOAT,
    p_latitude   FLOAT,
    p_radius_km  FLOAT DEFAULT 2.0,
    p_cuisine    TEXT  DEFAULT NULL,
    p_limit      INT   DEFAULT 20
)
RETURNS TABLE (
    restaurant_id BIGINT,
    name          TEXT,
    cuisine       TEXT,
    rating        NUMERIC,
    distance_km   NUMERIC
)
LANGUAGE SQL STABLE AS $$
    SELECT
        r.id,
        r.name,
        r.cuisine,
        r.rating,
        ROUND(
            (ST_Distance(
                r.location::geography,
                ST_MakePoint(p_longitude, p_latitude)::geography
            ) / 1000)::NUMERIC, 2
        ) AS distance_km
    FROM restaurants r
    WHERE r.is_active = TRUE
      AND r.deleted_at IS NULL
      AND ST_DWithin(
            r.location::geography,
            ST_MakePoint(p_longitude, p_latitude)::geography,
            p_radius_km * 1000                  -- Convert km to metres
          )
      AND (p_cuisine IS NULL OR r.cuisine = p_cuisine)
    ORDER BY distance_km ASC
    LIMIT p_limit;
$$;

SELECT * FROM find_nearby_restaurants(90.4125, 23.8103, 3.0, 'Italian');
```

### 6.2 Bounding Box Queries

A bounding box query finds all features within a rectangular geographic area defined by minimum and maximum longitude/latitude values. This is the underlying operation for map viewport queries — "load all restaurants visible in the current map view."

```sql
-- ─────────────────────────────────────────────────────────────────
-- BOUNDING BOX QUERY — Map viewport:

-- User is viewing a map. The visible area spans:
-- SW corner: (90.38, 23.79) — min longitude, min latitude
-- NE corner: (90.44, 23.84) — max longitude, max latitude

SELECT
    id, name, cuisine, rating,
    ST_X(location::geometry) AS longitude,
    ST_Y(location::geometry) AS latitude
FROM restaurants
WHERE location && ST_MakeEnvelope(
    90.38, 23.79,    -- xmin (min longitude), ymin (min latitude)
    90.44, 23.84,    -- xmax (max longitude), ymax (max latitude)
    4326             -- SRID
)
AND is_active = TRUE;

-- The && operator is the bounding box intersection operator.
-- It uses the GiST index directly — this is the index operator.
-- Equivalent but slightly longer form:
WHERE location && ST_SetSRID(ST_MakeBox2D(
    ST_MakePoint(90.38, 23.79),
    ST_MakePoint(90.44, 23.84)
), 4326)

-- ─────────────────────────────────────────────────────────────────
-- MAP VIEWPORT QUERY WITH CLUSTERING:
-- For large numbers of markers, cluster nearby points to avoid
-- overwhelming the map with thousands of individual markers:

SELECT
    -- Snap coordinates to a grid (for clustering):
    ROUND(ST_X(location::geometry)::NUMERIC, 2) AS cluster_lng,
    ROUND(ST_Y(location::geometry)::NUMERIC, 2) AS cluster_lat,
    COUNT(*) AS restaurant_count,
    AVG(rating) AS avg_rating,
    -- Return the exact location only when count=1 (single restaurant):
    CASE WHEN COUNT(*) = 1 THEN MAX(id) END AS restaurant_id,
    CASE WHEN COUNT(*) = 1 THEN MAX(name) END AS restaurant_name
FROM restaurants
WHERE location && ST_MakeEnvelope(90.38, 23.79, 90.44, 23.84, 4326)
  AND is_active = TRUE
GROUP BY
    ROUND(ST_X(location::geometry)::NUMERIC, 2),
    ROUND(ST_Y(location::geometry)::NUMERIC, 2);
-- Rounding to 2 decimal places (~1.1km resolution) groups nearby restaurants.
-- Adjust precision based on zoom level.
```

### 6.3 Nearest Neighbour Search

The nearest neighbour query finds the K closest features to a given point, ordered by distance. This is the query behind "sort by distance" — finding the five nearest available drivers, the ten closest pharmacies, the nearest hospital to an emergency location.

```sql
-- ─────────────────────────────────────────────────────────────────
-- K-NEAREST NEIGHBOUR (KNN) — The <-> Distance Operator:

-- Find the 5 nearest active drivers to a pickup point:
SELECT
    d.id,
    d.name,
    d.vehicle_type,
    d.location <-> ST_MakePoint(90.4125, 23.8103)::geography AS distance
FROM drivers d
WHERE d.is_available = TRUE
ORDER BY d.location <-> ST_MakePoint(90.4125, 23.8103)::geography
LIMIT 5;

-- The <-> operator is the DISTANCE ORDERING OPERATOR.
-- PostGIS uses it with the GiST index for efficient KNN search.
-- The GiST index handles the ORDER BY <-> with an index scan,
-- fetching candidates in distance order without computing all distances.

-- CRUCIAL: The <-> operator returns APPROXIMATE bounding-box distance
-- when used in ORDER BY with geography. For exact geodetic ordering,
-- use ST_Distance() in the ORDER BY clause instead:

SELECT
    d.id,
    d.name,
    ST_Distance(d.location::geography,
                ST_MakePoint(90.4125, 23.8103)::geography) AS exact_distance_m
FROM drivers d
WHERE d.is_available = TRUE
ORDER BY d.location <-> ST_MakePoint(90.4125, 23.8103)::geography  -- Index uses this
LIMIT 5;
-- The trick: use <-> in ORDER BY for the index benefit,
--            compute ST_Distance separately for the accurate value to display.
-- The top-5 by <-> are typically the same as top-5 by ST_Distance,
-- with only occasional differences at the margin.

-- ─────────────────────────────────────────────────────────────────
-- TRUE EXACT KNN — When you need perfect ordering:

-- For cases where exact order matters (emergency dispatch, legal compliance):
SELECT
    d.id,
    d.name,
    ST_Distance(d.location::geography,
                ST_MakePoint(90.4125, 23.8103)::geography) AS distance_m
FROM drivers d
WHERE d.is_available = TRUE
  AND ST_DWithin(                                -- Pre-filter with index first!
        d.location::geography,
        ST_MakePoint(90.4125, 23.8103)::geography,
        10000                                    -- Look within 10km (bounding box)
      )
ORDER BY ST_Distance(d.location::geography,
                     ST_MakePoint(90.4125, 23.8103)::geography)
LIMIT 5;

-- Pattern: ST_DWithin narrows to a manageable candidate set using the GiST index.
-- Then exact ST_Distance sorts within that candidate set.
-- Without ST_DWithin, ORDER BY ST_Distance requires computing distances
-- for all rows — a full table scan without index benefit.

-- ─────────────────────────────────────────────────────────────────
-- NEAREST WITH REAL-TIME FILTERING:
-- Find nearest available driver of a specific vehicle type:

SELECT
    d.id,
    d.driver_name,
    d.vehicle_type,
    d.rating,
    ST_Distance(
        d.current_location::geography,
        ST_MakePoint(90.4125, 23.8103)::geography
    ) / 1000 AS distance_km,
    -- Estimated arrival time (assuming 25 km/h average city speed):
    CEIL(
        ST_Distance(
            d.current_location::geography,
            ST_MakePoint(90.4125, 23.8103)::geography
        ) / 1000 / 25.0 * 60
    ) AS eta_minutes
FROM drivers d
WHERE d.status = 'available'
  AND d.vehicle_type = 'motorcycle'
  AND ST_DWithin(
        d.current_location::geography,
        ST_MakePoint(90.4125, 23.8103)::geography,
        5000   -- 5km search radius
      )
ORDER BY d.current_location <-> ST_MakePoint(90.4125, 23.8103)::geography
LIMIT 10;
```

### 6.4 Containment and Intersection

Beyond distance-based queries, PostGIS excels at **topological relationships** — determining whether geometries contain, overlap, touch, or intersect each other. These operations are essential for zone-based queries: is this delivery address within our service area? Is this new restaurant in an already saturated zone? Does this bus route pass through this neighbourhood?

```sql
-- ─────────────────────────────────────────────────────────────────
-- CONTAINMENT — Is a point inside a polygon?

-- Check if a delivery address is within the service area:
SELECT
    a.id,
    a.street_address,
    z.zone_name,
    z.delivery_fee
FROM addresses a
JOIN delivery_zones z ON ST_Within(a.location, z.boundary)
WHERE a.id = 12345;

-- ST_Within(geom_a, geom_b): returns TRUE if geom_a is completely
-- inside geom_b. For point-in-polygon: is the point inside the polygon?

-- ST_Contains(geom_a, geom_b) is the inverse: is geom_a the container?
-- ST_Contains(polygon, point) ≡ ST_Within(point, polygon)

-- ─────────────────────────────────────────────────────────────────
-- Find which zone a given point falls in:

SELECT zone_name, zone_type, pricing_tier
FROM zones
WHERE ST_Contains(boundary, ST_MakePoint(90.4125, 23.8103))
LIMIT 1;  -- Should only match one zone if zones don't overlap

-- ─────────────────────────────────────────────────────────────────
-- INTERSECTION — Do two geometries overlap?

-- Find all delivery zones that intersect a given neighbourhood polygon:
SELECT z.zone_name
FROM delivery_zones z
JOIN neighbourhoods n ON ST_Intersects(z.boundary, n.boundary)
WHERE n.name = 'Gulshan';

-- ST_Intersects(a, b): returns TRUE if a and b share any points
-- (including just touching at the border)

-- ─────────────────────────────────────────────────────────────────
-- THE OPERATOR SHORTHAND:
-- && = bounding box overlap (fast, uses index, may have false positives)
-- ~  = bounding box of A contains bounding box of B
-- @  = bounding box of A is contained by bounding box of B

-- Always combine && with exact predicate for correctness:
SELECT * FROM zones
WHERE boundary && ST_MakePoint(90.4125, 23.8103)       -- Index filter (fast)
  AND ST_Within(ST_MakePoint(90.4125, 23.8103), boundary);  -- Exact check

-- ─────────────────────────────────────────────────────────────────
-- SPATIAL RELATIONSHIP FUNCTIONS — Reference:

-- ST_Equals(a, b)      → geometrically identical
-- ST_Disjoint(a, b)    → no points in common (opposite of ST_Intersects)
-- ST_Intersects(a, b)  → share at least one point
-- ST_Touches(a, b)     → share only boundary points (not interior)
-- ST_Crosses(a, b)     → interiors intersect, but neither contains the other
-- ST_Overlaps(a, b)    → partial overlap (same dimension, neither contains)
-- ST_Contains(a, b)    → a contains b completely
-- ST_Covers(a, b)      → a covers b (b is within a, including boundary)
-- ST_Within(a, b)      → a is completely within b (inverse of Contains)
-- ST_CoveredBy(a, b)   → a is within b including boundary (inverse of Covers)
```

## 7. Spatial Joins — The Power Feature

A spatial join is a JOIN between two tables where the join condition is a spatial relationship rather than an equality of IDs. This is the operation that makes PostGIS genuinely transformative: "for every restaurant in my table, find which delivery zone it belongs to" is a spatial join that the GiST index makes fast.

```sql
-- ─────────────────────────────────────────────────────────────────
-- SPATIAL JOIN — Assign zone to every restaurant:

-- Which delivery zone does each restaurant belong to?
SELECT
    r.id           AS restaurant_id,
    r.name         AS restaurant_name,
    r.cuisine,
    z.zone_name,
    z.delivery_fee,
    z.avg_delivery_minutes
FROM restaurants r
JOIN delivery_zones z
  ON ST_Within(r.location, z.boundary)     -- Spatial join condition
WHERE r.is_active = TRUE
ORDER BY r.name;
-- GiST indexes on both r.location and z.boundary dramatically speed this up.

-- ─────────────────────────────────────────────────────────────────
-- SPATIAL AGGREGATION — Count restaurants per zone:

SELECT
    z.zone_name,
    z.zone_type,
    COUNT(r.id) AS restaurant_count,
    AVG(r.rating) AS avg_rating,
    COUNT(DISTINCT r.cuisine) AS cuisine_variety
FROM delivery_zones z
LEFT JOIN restaurants r
  ON ST_Within(r.location, z.boundary) AND r.is_active = TRUE
GROUP BY z.zone_name, z.zone_type
ORDER BY restaurant_count DESC;

-- ─────────────────────────────────────────────────────────────────
-- REVERSE GEOCODING — Find address from coordinates:

-- Which neighbourhood is this point in?
SELECT
    n.name AS neighbourhood,
    d.name AS district,
    c.name AS city
FROM neighbourhoods n
JOIN districts d ON ST_Within(n.boundary, d.boundary)
JOIN cities c ON ST_Within(d.boundary, c.boundary)
WHERE ST_Within(
    ST_SetSRID(ST_MakePoint(90.4125, 23.8103), 4326),
    n.boundary
);

-- ─────────────────────────────────────────────────────────────────
-- TRIP SEGMENT ANALYSIS — Which zones does a route pass through?

-- A delivery route as a LineString:
WITH route AS (
    SELECT ST_GeomFromText(
        'LINESTRING(90.4125 23.8103, 90.4200 23.8150, 90.4280 23.8200)',
        4326
    ) AS path
)
SELECT DISTINCT z.zone_name, z.toll_applies
FROM delivery_zones z, route r
WHERE ST_Intersects(z.boundary, r.path)
ORDER BY z.zone_name;
-- Finds all delivery zones the route passes through — useful for
-- calculating tolls, checking service agreements, or routing constraints.
```

## 8. Practical Schema Design for Location Data

Real applications need more than just spatial columns — they need schemas that efficiently support the full range of location-based operations at scale.

```sql
-- ─────────────────────────────────────────────────────────────────
-- RESTAURANTS TABLE — Production-Ready Spatial Schema:

CREATE TABLE restaurants (
    id                      BIGSERIAL PRIMARY KEY,
    name                    TEXT NOT NULL,
    cuisine                 TEXT NOT NULL,
    description             TEXT,
    phone                   TEXT,

    -- Spatial location (geography for accurate distance calculations):
    location                GEOGRAPHY(Point, 4326) NOT NULL,

    -- Denormalised for fast non-spatial filtering:
    -- (Avoids spatial joins for common filter-by-address queries)
    address_street          TEXT,
    address_city            TEXT,
    address_country         CHAR(2) NOT NULL DEFAULT 'BD',
    address_postal_code     TEXT,

    -- Zone assignment (updated by spatial join, cached for query performance):
    delivery_zone_id        BIGINT REFERENCES delivery_zones(id),

    -- Business attributes:
    rating                  NUMERIC(3,2) CHECK (rating BETWEEN 0 AND 5),
    review_count            INT NOT NULL DEFAULT 0,
    price_range             CHAR(4) CHECK (price_range IN ('$', '$$', '$$$', '$$$$')),
    average_delivery_time   INT,                    -- Minutes
    minimum_order_amount    NUMERIC(10,2),

    -- Operational:
    is_active               BOOLEAN NOT NULL DEFAULT TRUE,
    opens_at                TIME,
    closes_at               TIME,
    created_at              TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at              TIMESTAMPTZ,

    -- Service radius — restaurant's own delivery radius:
    delivery_radius_metres  INT NOT NULL DEFAULT 3000
);

-- Spatial index (most critical):
CREATE INDEX idx_restaurants_location
    ON restaurants USING GIST (location);

-- Partial spatial index (active restaurants only — the common search case):
CREATE INDEX idx_restaurants_location_active
    ON restaurants USING GIST (location)
    WHERE is_active = TRUE AND deleted_at IS NULL;

-- Supporting B-Tree indexes for non-spatial filters:
CREATE INDEX idx_restaurants_cuisine      ON restaurants (cuisine);
CREATE INDEX idx_restaurants_zone         ON restaurants (delivery_zone_id);
CREATE INDEX idx_restaurants_country      ON restaurants (address_country);

-- ─────────────────────────────────────────────────────────────────
-- DRIVER LOCATION TABLE — High-Frequency Update Pattern:

-- Driver locations update every few seconds. This is a write-heavy table.
-- Separate it from driver profile data to minimise table bloat.

CREATE TABLE driver_locations (
    driver_id           BIGINT PRIMARY KEY REFERENCES drivers(id),
    -- geography type for accurate distance:
    current_location    GEOGRAPHY(Point, 4326) NOT NULL,
    heading_degrees     NUMERIC(5,2),               -- 0-360 direction of travel
    speed_kmh           NUMERIC(5,2),
    accuracy_metres     NUMERIC(8,2),               -- GPS accuracy
    location_updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    -- Status for filtering (most queries filter by this):
    status              TEXT NOT NULL
                        CHECK (status IN ('available', 'on_trip', 'offline'))
);

CREATE INDEX idx_driver_locations_location
    ON driver_locations USING GIST (current_location);

CREATE INDEX idx_driver_locations_status_location
    ON driver_locations USING GIST (current_location)
    WHERE status = 'available';    -- The most common search: available drivers

-- For high-frequency location updates, consider UNLOGGED table
-- (much faster writes, lost on crash — acceptable for ephemeral location data):
-- CREATE UNLOGGED TABLE driver_locations (...);
-- Use a separate persistent table for location history if needed.

-- ─────────────────────────────────────────────────────────────────
-- DELIVERY ZONES TABLE — Polygon Features:

CREATE TABLE delivery_zones (
    id                  BIGSERIAL PRIMARY KEY,
    zone_name           TEXT NOT NULL UNIQUE,
    zone_type           TEXT NOT NULL CHECK (zone_type IN ('inner', 'outer', 'premium')),

    -- The zone boundary polygon:
    boundary            GEOMETRY(Polygon, 4326) NOT NULL,
    -- OR MultiPolygon for non-contiguous zones:
    -- boundary         GEOMETRY(MultiPolygon, 4326) NOT NULL,

    -- Derived spatial properties (computed, stored for quick access):
    centroid            GEOMETRY(Point, 4326) GENERATED ALWAYS AS (
                            ST_Centroid(boundary)
                        ) STORED,
    area_km2            NUMERIC(10,4) GENERATED ALWAYS AS (
                            ST_Area(boundary::geography) / 1000000.0
                        ) STORED,

    -- Business attributes:
    delivery_fee        NUMERIC(6,2) NOT NULL DEFAULT 30.00,
    min_order_amount    NUMERIC(8,2) NOT NULL DEFAULT 0,
    is_active           BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE INDEX idx_delivery_zones_boundary
    ON delivery_zones USING GIST (boundary);
```

## 9. Calling PostGIS from Go

Integrating PostGIS with Go requires handling the `geography` and `geometry` types, which the standard `pgx` driver does not understand natively. The most common approach is to work with WKT (Well-Known Text) strings or to use the `pgeo` package.

```go
package spatial

import (
    "context"
    "fmt"
    "github.com/jackc/pgx/v5/pgxpool"
)

// Restaurant represents a restaurant with location data.
type Restaurant struct {
    ID           int64
    Name         string
    Cuisine      string
    Rating       float64
    Longitude    float64
    Latitude     float64
    DistanceKm   float64
}

// ─────────────────────────────────────────────────────────────────
// APPROACH 1: Extract coordinates using ST_X/ST_Y (simplest):

func FindNearbyRestaurants(
    ctx context.Context,
    db *pgxpool.Pool,
    longitude, latitude float64,
    radiusKm float64,
    limit int,
) ([]*Restaurant, error) {
    query := `
        SELECT
            r.id,
            r.name,
            r.cuisine,
            r.rating,
            -- Extract coordinates from geography column:
            ST_X(r.location::geometry)  AS longitude,
            ST_Y(r.location::geometry)  AS latitude,
            -- Compute distance in km:
            ROUND(
                (ST_Distance(
                    r.location::geography,
                    ST_MakePoint($1, $2)::geography
                ) / 1000.0)::NUMERIC, 2
            ) AS distance_km
        FROM restaurants r
        WHERE r.is_active = TRUE
          AND r.deleted_at IS NULL
          AND ST_DWithin(
                r.location::geography,
                ST_MakePoint($1, $2)::geography,
                $3 * 1000           -- Convert km to metres
              )
        ORDER BY
            r.location <-> ST_MakePoint($1, $2)::geography  -- Index-friendly ORDER
        LIMIT $4`

    rows, err := db.Query(ctx, query, longitude, latitude, radiusKm, limit)
    if err != nil {
        return nil, fmt.Errorf("FindNearbyRestaurants: %w", err)
    }
    defer rows.Close()

    var restaurants []*Restaurant
    for rows.Next() {
        r := &Restaurant{}
        if err := rows.Scan(
            &r.ID, &r.Name, &r.Cuisine, &r.Rating,
            &r.Longitude, &r.Latitude, &r.DistanceKm,
        ); err != nil {
            return nil, fmt.Errorf("FindNearbyRestaurants scan: %w", err)
        }
        restaurants = append(restaurants, r)
    }
    return restaurants, rows.Err()
}

// ─────────────────────────────────────────────────────────────────
// APPROACH 2: Insert/update location using ST_MakePoint:

func UpdateDriverLocation(
    ctx context.Context,
    db *pgxpool.Pool,
    driverID int64,
    longitude, latitude float64,
    status string,
) error {
    _, err := db.Exec(ctx, `
        INSERT INTO driver_locations (driver_id, current_location, status, location_updated_at)
        VALUES ($1, ST_MakePoint($2, $3)::geography, $4, NOW())
        ON CONFLICT (driver_id) DO UPDATE SET
            current_location    = EXCLUDED.current_location,
            status              = EXCLUDED.status,
            location_updated_at = EXCLUDED.location_updated_at`,
        driverID, longitude, latitude, status,
    )
    if err != nil {
        return fmt.Errorf("UpdateDriverLocation: %w", err)
    }
    return nil
}

// ─────────────────────────────────────────────────────────────────
// APPROACH 3: Using WKT for complex geometries (polygons, linestrings):

func CreateDeliveryZone(
    ctx context.Context,
    db *pgxpool.Pool,
    name string,
    // Polygon as WKT string: "POLYGON((lng lat, lng lat, ...))"
    boundaryWKT string,
    deliveryFee float64,
) (int64, error) {
    var zoneID int64
    err := db.QueryRow(ctx, `
        INSERT INTO delivery_zones (zone_name, boundary, delivery_fee)
        VALUES (
            $1,
            ST_GeomFromText($2, 4326),   -- Parse WKT with SRID 4326
            $3
        )
        RETURNING id`,
        name, boundaryWKT, deliveryFee,
    ).Scan(&zoneID)
    if err != nil {
        return 0, fmt.Errorf("CreateDeliveryZone: %w", err)
    }
    return zoneID, nil
}

// ─────────────────────────────────────────────────────────────────
// APPROACH 4: Returning GeoJSON for API responses:

func GetRestaurantAsGeoJSON(
    ctx context.Context,
    db *pgxpool.Pool,
    restaurantID int64,
) (string, error) {
    var geoJSON string
    err := db.QueryRow(ctx, `
        SELECT json_build_object(
            'type', 'Feature',
            'geometry', ST_AsGeoJSON(location::geometry)::json,
            'properties', json_build_object(
                'id',      id,
                'name',    name,
                'cuisine', cuisine,
                'rating',  rating
            )
        )::TEXT
        FROM restaurants
        WHERE id = $1`,
        restaurantID,
    ).Scan(&geoJSON)
    if err != nil {
        return "", fmt.Errorf("GetRestaurantAsGeoJSON: %w", err)
    }
    return geoJSON, nil
}

// ─────────────────────────────────────────────────────────────────
// GeoJSON FeatureCollection for map rendering:

func GetRestaurantsGeoJSON(
    ctx context.Context,
    db *pgxpool.Pool,
    minLng, minLat, maxLng, maxLat float64,
) (string, error) {
    var geoJSON string
    err := db.QueryRow(ctx, `
        SELECT json_build_object(
            'type', 'FeatureCollection',
            'features', COALESCE(json_agg(
                json_build_object(
                    'type', 'Feature',
                    'geometry', ST_AsGeoJSON(location::geometry)::json,
                    'properties', json_build_object(
                        'id',      id,
                        'name',    name,
                        'cuisine', cuisine,
                        'rating',  rating
                    )
                )
            ), '[]')
        )::TEXT
        FROM restaurants
        WHERE location && ST_MakeEnvelope($1, $2, $3, $4, 4326)
          AND is_active = TRUE`,
        minLng, minLat, maxLng, maxLat,
    ).Scan(&geoJSON)
    if err != nil {
        return "", fmt.Errorf("GetRestaurantsGeoJSON: %w", err)
    }
    return geoJSON, nil
}

│                          │ <-> = distance ordering (index-friendly). │
│                          │ For exact results: combine with ST_DWithin│
│                          │ then ORDER BY ST_Distance.                │
├──────────────────────────┼───────────────────────────────────────────┤
│ Distance                 │ ST_Distance(a::geography, b::geography)   │
│                          │ Returns metres for geography type.        │
│                          │ Divide by 1000 for km.                   │
│                          │ NOT index-friendly in WHERE — use         │
│                          │ ST_DWithin for filtering instead.         │
├──────────────────────────┼───────────────────────────────────────────┤
│ Containment              │ ST_Within(point, polygon) → true/false    │
│                          │ ST_Contains(polygon, point) → same thing  │
│                          │ ST_Intersects(a, b) → share any points   │
│                          │ Use && first for index, then exact check. │
├──────────────────────────┼───────────────────────────────────────────┤
│ Coordinate Extraction    │ ST_X(geom) → longitude                   │
│                          │ ST_Y(geom) → latitude                    │
│                          │ ST_AsText(geom) → WKT string             │
│                          │ ST_AsGeoJSON(geom) → GeoJSON string      │
└──────────────────────────┴───────────────────────────────────────────┘

MOST COMMON MISTAKES:
  ✗ Using geometry when geography is needed (wrong distance units)
  ✗ Longitude and latitude in wrong order (lat,lng instead of lng,lat)
  ✗ ST_Distance in WHERE clause (can't use index — use ST_DWithin)
  ✗ SRID 3857 (Web Mercator) for distance calculations (use 4326)
  ✗ Treating degrees as metres (1° ≠ 111km everywhere)
  ✗ No GiST index on location column (full table scan on every query)

PRODUCTION CHECKLIST:
  □ Use geography(Point, 4326) for GPS/user location data
  □ Column: location GEOGRAPHY(Point, 4326) NOT NULL
  □ Index: CREATE INDEX ON table USING GIST (location)
  □ Partial index for active-only queries
  □ ST_DWithin for radius filter (not ST_Distance in WHERE)
  □ ST_MakePoint(longitude, latitude) — longitude FIRST
  □ CLUSTER table by spatial index after bulk load
  □ Separate high-frequency update table (drivers) from profile table
  □ Cache zone assignment (delivery_zone_id) to avoid repeated spatial joins
  □ ST_AsGeoJSON for API responses to JavaScript map clients

SPATIAL QUERY TEMPLATE:
  -- Nearby search with distance:
  SELECT id, name,
    ST_Distance(location::geography,
                ST_MakePoint($lng, $lat)::geography) / 1000 AS km
  FROM table
  WHERE is_active = TRUE
    AND ST_DWithin(location::geography,
                   ST_MakePoint($lng, $lat)::geography,
                   $radius_m)
  ORDER BY location <-> ST_MakePoint($lng, $lat)::geography
  LIMIT $k;
```

---

_Geography is not a feature — it is a lens through which data acquires meaning. A phone number is just digits. A name is just characters. A coordinate is just two numbers. But the moment you can ask "what is near this coordinate", "what zone does this point fall in", "what is the distance from here to there" — the data becomes a map of the world and your database becomes a geographic information system._

_PostGIS gives you that power within PostgreSQL — without an additional service, without a synchronisation pipeline, without a new operational burden. A restaurant table with a GiST-indexed geography column and a well-written `ST_DWithin` query will serve hundreds of thousands of "find nearby" requests per day from a single database node, with millisecond latency._

_Start with `geography`. Index it with GiST. Filter with `ST_DWithin`. Order with `<->`. Everything else — zones, spatial joins, reverse geocoding — builds naturally from this foundation. The Earth is curved, but your queries do not have to be complicated._
