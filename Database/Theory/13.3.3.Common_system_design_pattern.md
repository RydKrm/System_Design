## 1. Search — Elasticsearch + PostgreSQL Dual Write

### 1.1 The Problem — Why Databases Are Not Search Engines

Every non-trivial application eventually needs to let users search for things. An e-commerce platform lets users search for products by name, category, price range, and brand. A job board lets candidates search for positions by title, location, required skills, and salary. A document management system lets employees search for files by content, author, and date. These are deeply human, natural-language-flavored queries, and they share a set of requirements that relational databases were simply not designed to fulfill well.

Consider what happens when a user types "wireless bluetooth headphones noise cancelling" into a search box. They want results that are relevant, ranked by how closely they match the query, and they expect the search to be tolerant of variations — "bluetooth" should match documents that contain "Bluetooth" or even "BT," "headphones" should match "headphone" (singular), and the results should give more weight to documents where the search terms appear in the product title than in a distant description field. They also expect this to complete in under 200 milliseconds, across a catalog of potentially millions of products.

A SQL `LIKE '%wireless%'` query does none of this gracefully. It requires a full table scan (because the leading `%` wildcard prevents index usage), it is case-sensitive by default in many configurations, it does not rank results by relevance, it cannot handle stemming (matching "run" to "running"), and it becomes catastrophically slow on large datasets. PostgreSQL's built-in full-text search (`tsvector` and `tsquery`) is significantly better — it creates an inverted index, supports stemming and ranking, and performs admirably for many use cases. But it lacks the advanced features that users of modern applications have come to expect: fuzzy matching (finding "headphone" even if the user typed "headfone"), faceted search (filtering by multiple attributes simultaneously while showing counts for each filter option), auto-complete suggestions, synonym handling, and the ability to index and search across nested or complex data structures.

**Elasticsearch** is a search engine built specifically to answer all of these requirements. It is built on top of Apache Lucene, one of the most battle-tested full-text search libraries in existence, and it adds to Lucene's capabilities a distributed, scalable architecture, a rich REST API, and an enormous ecosystem of features for analytics, visualization, and complex query construction. Understanding when and how to use Elasticsearch alongside PostgreSQL is one of the most practically valuable architectural skills a backend engineer can develop.

### 1.2 How Elasticsearch Works — The Inverted Index

The foundational data structure of Elasticsearch (and all search engines built on Lucene) is the **inverted index**. To understand why this structure is so powerful for search, you must first understand the problem it solves.

In a conventional database, data is organized by record: record 1 contains fields A, B, and C with their values; record 2 contains fields A, B, and C with different values; and so on. To find all records where field B contains the word "bluetooth," the database must examine field B in every record — a process that scales linearly with the number of records. An index on field B helps, but only for exact matches and prefix matches, not for full-text relevance-ranked search.

An inverted index flips this organization. Instead of mapping records to their words, it maps words to the records that contain them. When a document is indexed in Elasticsearch, the text of each field is passed through an **analysis pipeline**: it is tokenized (split into individual words), lowercased, stemmed (reduced to a root form — "running" becomes "run"), filtered to remove common stopwords ("the," "a," "is"), and potentially expanded with synonyms. The resulting tokens are then stored in the inverted index: a dictionary mapping each token to a list of all documents that contain it, along with the position of each occurrence and a frequency count.

```
Inverted Index — How Search Works
====================================

  Three product documents indexed in Elasticsearch:
  Doc 1: "Sony WH-1000XM5 Wireless Bluetooth Headphones Noise Cancelling"
  Doc 2: "Bose QuietComfort 45 Bluetooth Wireless Headphones"
  Doc 3: "Apple AirPods Pro Wireless Earbuds Noise Cancellation"

  After analysis (tokenize, lowercase, stem, remove stopwords):
  Doc 1 tokens: [sony, wh1000xm5, wireless, bluetooth, headphone, noise, cancel]
  Doc 2 tokens: [bose, quietcomfort, 45, bluetooth, wireless, headphone]
  Doc 3 tokens: [appl, airpod, pro, wireless, earbud, nois, cancel]

  Inverted Index (simplified):
  +-------------+------------------------+
  | Token       | Documents (with scores)|
  +-------------+------------------------+
  | wireless    | Doc1(tf=1), Doc2(tf=1), Doc3(tf=1)
  | bluetooth   | Doc1(tf=1), Doc2(tf=1)
  | headphone   | Doc1(tf=1), Doc2(tf=1)
  | noise       | Doc1(tf=1)
  | cancel      | Doc1(tf=1), Doc3(tf=1)
  | sony        | Doc1(tf=1)
  | bose        | Doc2(tf=1)
  | earbud      | Doc3(tf=1)
  | wireless    | Doc1, Doc2, Doc3
  +-------------+------------------------+

  Query: "wireless bluetooth headphones noise cancelling"
  Tokens: [wireless, bluetooth, headphone, noise, cancel]

  Step 1: Look up each token's document list
  Step 2: Score each document by how many tokens match
          and how prominently they appear (TF-IDF / BM25)

  Doc 1: matches wireless + bluetooth + headphone + noise + cancel = 5/5 -> highest score
  Doc 2: matches wireless + bluetooth + headphone = 3/5 -> second score
  Doc 3: matches wireless + cancel = 2/5 -> third score

  Results returned: [Doc1, Doc2, Doc3] (ranked by relevance score)
  Response time: < 10ms (even for millions of documents)
```

This is why search engines are so dramatically faster and more capable than `LIKE` queries. The work of analyzing and indexing the text happens once, at write time. At query time, the search engine simply looks up each query token in the pre-built inverted index — an O(1) dictionary lookup — and then ranks and merges the results. The query-time work is proportional to the number of unique query tokens, not the number of documents in the index.

### 1.3 The Dual Write Architecture — PostgreSQL as Truth, Elasticsearch as Search

The critical architectural insight behind the Elasticsearch + PostgreSQL pattern is the recognition that these two systems serve different, complementary purposes. PostgreSQL is your **system of record** — the authoritative, ACID-compliant database where all business logic executes, where transactional integrity is enforced, and where data is stored durably and correctly. It is the foundation you trust absolutely. Elasticsearch is your **search index** — an optimized, denormalized replica of a subset of your PostgreSQL data, specifically structured to answer search queries with the speed and richness of a search engine.

Because Elasticsearch is a search index rather than a primary database, it comes with certain accepted trade-offs: it is eventually consistent with PostgreSQL (changes take a fraction of a second to propagate), it does not support multi-document ACID transactions, and its consistency guarantees in the event of partial failure are weaker than PostgreSQL's. These trade-offs are entirely acceptable because the data in Elasticsearch is not the authoritative copy — it is a derived view, and if it ever becomes inconsistent with PostgreSQL, it can be rebuilt from PostgreSQL's data.

```
Dual Write Architecture — Overview
=====================================

  +----------------------------------------------------------+
  |                     Application                          |
  +---+------------------------+----------------------------+-+
      |                        |                            |
      | Writes                 | Search queries             |
      v                        v                            v
  +-----------+          +------------------+         +----------+
  | PostgreSQL|          |  Elasticsearch   |         |  Other   |
  | (Primary  |          |  (Search Index)  |         |  reads   |
  |  Source   |          |                  |         |          |
  |  of Truth)|          | Inverted Index   |         |          |
  |           |          | Relevance ranking|         |          |
  | ACID txns |          | Fuzzy matching   |         |          |
  | Durable   |          | Faceted search   |         |          |
  | Relational|          | Auto-complete    |         |          |
  +-----------+          +------------------+         +----------+

  Synchronization between PostgreSQL and Elasticsearch:
  Three strategies (covered in detail below)
```

There are three primary strategies for keeping Elasticsearch synchronized with PostgreSQL, and each involves a different set of trade-offs between complexity, consistency, and reliability.

### 1.4 Strategy One — Synchronous Dual Write

The simplest synchronization strategy is **synchronous dual write**: whenever the application writes to PostgreSQL, it also writes to Elasticsearch within the same request handler, before returning the response. When a new product is created, the application inserts a row into the PostgreSQL `products` table and simultaneously sends a document to Elasticsearch's products index. The response is returned only after both writes have completed.

```
Synchronous Dual Write — Request Flow
========================================

  App Server
      |
      |-- User creates product "Sony Headphones"
      |
      |  Step 1: Write to PostgreSQL
      |  +-------------------+
      |  | INSERT INTO       |
      |  | products(name,    |
      |  | price, category)  |
      |  | VALUES(...)       |
      |  | --> returns id=42 |
      |  +-------------------+
      |
      |  Step 2: Write to Elasticsearch
      |  +-------------------+
      |  | PUT /products/_doc|
      |  | /42               |
      |  | {name:"Sony...",  |
      |  | price: 349.99,    |
      |  | category:"audio"} |
      |  +-------------------+
      |
      |-- Return 201 Created to user
          (only after BOTH writes confirm)

  Failure modes:
  [1] PostgreSQL write fails:
      --> Return error to user. Nothing written. Consistent.

  [2] PostgreSQL succeeds, Elasticsearch FAILS:
      --> PostgreSQL has the record. Elasticsearch does not.
          The product exists but is not searchable.
          INCONSISTENCY. Application must handle this.

  Solution for [2]: Retry the Elasticsearch write.
  If retries fail: Flag the record for a background sync job.
```

Synchronous dual write is easy to understand and implement, but it introduces a reliability problem that must be addressed explicitly. Because the write involves two independent systems, there is no single transaction that spans both. If PostgreSQL succeeds but the Elasticsearch write fails (due to a network blip, a temporary Elasticsearch overload, or a node failure), the two systems are now inconsistent: the product exists in PostgreSQL but is invisible to search. The application code must handle this case explicitly — typically by implementing a retry loop with exponential backoff for the Elasticsearch write, and by maintaining a queue of "pending sync" records for items that could not be indexed after multiple retries.

### 1.5 Strategy Two — Asynchronous Sync via Change Data Capture

A more robust and architecturally elegant approach is **Change Data Capture (CDC)**, which decouples the Elasticsearch synchronization entirely from the application write path. Instead of the application writing to Elasticsearch directly, a CDC system monitors PostgreSQL's transaction log (the Write-Ahead Log, or WAL) and streams every change — every insert, update, and delete — to a message queue, from which a dedicated indexer service picks them up and applies them to Elasticsearch.

```
CDC-Based Synchronization (Recommended for Production)
=========================================================

  Application Layer:
  App writes ONLY to PostgreSQL (simple, clean, single responsibility)
  +-------------------+
  | INSERT INTO       |
  | products VALUES   |
  | (...)             |
  +--------+----------+
           |
           | PostgreSQL WAL (Write-Ahead Log)
           | records every change automatically
           v
  +-------------------+
  |  PostgreSQL WAL   |
  | (transaction log) |
  +--------+----------+
           |
           | CDC Tool (Debezium) reads the WAL
           | and publishes change events to Kafka
           v
  +-------------------+
  |   Kafka Topic:    |
  | "postgres.products|
  | .changes"         |
  | {op:"c",          |  op = create/update/delete
  |  after:{id:42,    |
  |  name:"Sony..."}} |
  +--------+----------+
           |
           | Elasticsearch Indexer Service
           | consumes from Kafka, transforms,
           | and indexes into Elasticsearch
           v
  +-------------------+
  |  Elasticsearch    |
  | PUT /products/42  |
  | {name:"Sony...",  |
  | price: 349.99}    |
  +-------------------+

  Properties:
  - Application writes to ONE system (PostgreSQL). Simple, reliable.
  - Elasticsearch is always eventually consistent (typically < 1 second lag)
  - If Elasticsearch is down, Kafka buffers the changes.
    Once Elasticsearch recovers, it catches up from Kafka.
  - If the indexer crashes, it resumes from its last Kafka offset.
  - Zero data loss (Kafka is durable, PostgreSQL WAL is durable).
```

The CDC approach, popularized by tools like **Debezium** (an open-source CDC platform), is the industry standard for production-grade Elasticsearch synchronization. It has several important advantages over synchronous dual write. The application code is dramatically simpler — it writes to PostgreSQL only, with no awareness of Elasticsearch at all. The Elasticsearch sync is resilient to failures in a way that application-level dual write is not: if Elasticsearch is temporarily unavailable, Kafka durably buffers the change events, and the indexer replays them when Elasticsearch recovers, with no data loss and no manual intervention required. The Kafka consumer offset mechanism also provides an exact position in the change stream, so if the indexer crashes and restarts, it picks up exactly where it left off.

The trade-off is operational complexity: CDC requires running and maintaining Debezium (or a similar tool) and a Kafka cluster, which adds infrastructure. For early-stage applications, this overhead may not be justified. For applications where search data must be reliably synchronized with the database even in the presence of partial system failures, CDC is the appropriate investment.

### 1.6 Designing the Elasticsearch Document — Denormalize for Search

One of the most important design decisions in the dual write architecture is what the Elasticsearch document should contain. In PostgreSQL, data is normalized — a product row contains just the product's own attributes, and the category name is stored in a separate `categories` table, joined at query time. In Elasticsearch, joins are expensive and generally avoided. The recommended approach is to **denormalize** the document at index time: embed the category name, the brand name, the tag list, and any other attributes that should be searchable or displayable directly into the product document, even though this data lives in separate PostgreSQL tables.

This denormalization means that when a category is renamed in PostgreSQL, the Elasticsearch documents for all products in that category must be re-indexed with the new category name. This is a reindexing challenge that must be planned for, but it is a manageable one — either through CDC (the category update triggers a cascade of product change events) or through periodic bulk reindexing jobs. The performance benefit of denormalization in Elasticsearch is so substantial that this operational cost is almost always worth accepting.

## 2. Audit Log — Append-Only Table + Kafka

### 2.1 The Problem — The Immutable History of Everything

An audit log is a chronological record of everything that has happened in a system — every action taken, by whom, on what, and when. The need for audit logs arises from several distinct but overlapping motivations. In regulated industries — finance, healthcare, legal — audit logs are a legal requirement: if a patient's medical record is accessed, the law may require that access to be recorded permanently. In security-conscious environments, audit logs are the foundation of forensic investigation: when a breach is discovered, the audit log tells you what the attacker accessed and what they changed. In operational contexts, audit logs are a debugging tool: when something in the database is wrong, the audit trail shows the sequence of events that led to the corruption.

All of these motivations converge on a single set of requirements that distinguishes audit logs from all other kinds of data storage. Audit log records must be **immutable** — once written, they can never be modified or deleted, because a modified or deleted audit record is worse than no audit record at all (it creates a false sense of security). They must be **complete** — every relevant action must be captured without exception; a partial audit log is an unreliable one. They must be **tamper-evident** — it should be detectable if someone has attempted to alter historical records. And they must be **queryable over long time horizons** — you may need to answer the question "who accessed this record in the past seven years?" with complete accuracy.

### 2.2 The Append-Only Table — Immutability by Convention and Design

The most straightforward implementation of an audit log in a relational database is an **append-only table** — a table to which rows are only ever inserted, never updated or deleted. The application treats this table with a strict discipline: audit records flow into it in one direction only, like water into a reservoir, and they never flow back out through modification.

```
Audit Log — PostgreSQL Schema
================================

  Table: audit_log
  +------------------+------------------+-----------------------------------+
  | Column           | Type             | Description                       |
  +------------------+------------------+-----------------------------------+
  | id               | BIGSERIAL PK     | Unique event identifier           |
  | event_id         | UUID DEFAULT     | Globally unique event ID          |
  |                  | gen_random_uuid()| (for deduplication across systems)|
  | event_type       | VARCHAR(100)     | "user.login", "order.created",    |
  |                  |                  | "record.accessed", "role.changed" |
  | actor_id         | BIGINT           | Who performed the action          |
  | actor_type       | VARCHAR(50)      | "user", "admin", "system",        |
  |                  |                  | "api_key"                         |
  | actor_ip         | INET NULL        | IP address of the actor           |
  | target_type      | VARCHAR(100)     | What was acted upon:              |
  |                  |                  | "patient_record", "order", "user" |
  | target_id        | BIGINT NULL      | ID of the target entity           |
  | action           | VARCHAR(100)     | "read", "create", "update",       |
  |                  |                  | "delete", "export", "login"       |
  | before_state     | JSONB NULL       | Snapshot of data BEFORE change    |
  | after_state      | JSONB NULL       | Snapshot of data AFTER change     |
  | metadata         | JSONB NULL       | Extra context (browser, version)  |
  | occurred_at      | TIMESTAMPTZ      | Exact timestamp (microseconds)    |
  +------------------+------------------+-----------------------------------+

  Critical constraints that enforce immutability:
  - NO UPDATE privilege granted to application database user
  - NO DELETE privilege granted to application database user
  - Only INSERT is permitted (enforced at the database role level)
  - Partitioned by month (audit_log_2024_01, audit_log_2024_02, ...)
    for manageable storage and efficient time-range queries

  Row-Level Security (optional, for extra tamper resistance):
  - A separate "audit_writer" role has INSERT only
  - No application role has UPDATE or DELETE at all
  - Even a compromised application cannot modify past audit records
```

The design of the `before_state` and `after_state` columns deserves particular attention. Storing just the fact that "user 456 updated order 789" is a minimal audit record, but it does not tell you what changed. If a price was altered, you need to know what it was before and what it became. By capturing a JSON snapshot of the relevant data before and after the modification, the audit log becomes a complete historical ledger — you can reconstruct the exact state of any audited record at any point in its history by replaying the sequence of before/after state transitions. This is particularly valuable in regulated industries where demonstrating precisely what information was visible to a specific user at a specific time may be legally required.

### 2.3 Partitioning — Managing Growth Over Time

Audit logs grow without bound. In a moderately active application, generating thousands of audit events per second, the audit log table can accumulate billions of rows over a few years. A single PostgreSQL table with billions of rows is manageable, but querying it for historical records — "show me all actions performed on patient record 12345 between January 2020 and March 2021" — becomes increasingly slow as the table grows, because even indexed queries must navigate a large B-tree.

PostgreSQL's **table partitioning** feature is the solution. The audit log table is declared as a partitioned table, with each partition covering a specific time range — typically one month. New partitions are created automatically (via a scheduled job or the `pg_partman` extension) before the end of the current period. When a query specifies a time range in its `WHERE` clause, PostgreSQL's query planner uses **partition pruning** to scan only the relevant partitions rather than the entire table, dramatically reducing the volume of data examined.

```
Partitioned Audit Log — Time-Based Organization
==================================================

  Parent table: audit_log (partitioned by occurred_at)

  Partitions (created monthly):
  +---------------------+----------------------------------+
  | Partition           | Covers                           |
  +---------------------+----------------------------------+
  | audit_log_2024_01   | 2024-01-01 to 2024-01-31         |
  | audit_log_2024_02   | 2024-02-01 to 2024-02-28         |
  | audit_log_2024_03   | 2024-03-01 to 2024-03-31         |
  | audit_log_2024_04   | 2024-04-01 to 2024-04-30         |
  | ...                 | ...                              |
  | audit_log_2024_12   | 2024-12-01 to 2024-12-31         |
  +---------------------+----------------------------------+

  Query: Find all actions on patient:789 in Q1 2024
  SELECT * FROM audit_log
  WHERE target_type = 'patient_record'
    AND target_id = 789
    AND occurred_at BETWEEN '2024-01-01' AND '2024-03-31';

  PostgreSQL PRUNES partitions automatically:
  Only audit_log_2024_01, _02, _03 are scanned.
  audit_log_2024_04 through _12 are entirely skipped.

  Benefits:
  - Queries are fast regardless of total table size
  - Old partitions (e.g., 7+ years old) can be archived to
    cold storage (S3 / Glacier) and detached from the table
  - Each partition can have its own indexes without affecting others
```

For data that must be retained for regulatory reasons but is rarely queried (records older than a certain number of years), detached partitions can be exported to cold object storage like Amazon S3 as Parquet files and queried through tools like Amazon Athena or Google BigQuery. This keeps the hot, frequently-queried audit data in PostgreSQL where query performance is optimal, while the cold, archival data lives in cheap object storage that costs a fraction of database-hosted storage.

### 2.4 Kafka — Decoupling the Write Path from the Audit Record

Writing to the audit log directly from application code, synchronously within the business transaction, creates a coupling that has both performance and reliability consequences. If the application is writing audit records for every single database operation — every read, every write, every login — the audit writes add latency to every one of those operations. More subtly, if the application writes the business operation and the audit record in the same database transaction, any rollback of the business operation also rolls back the audit record — which is exactly wrong for security audit purposes. (If a transaction is rolled back due to an error, you may still want an audit record of the failed attempt.)

**Apache Kafka** solves both of these problems by introducing an asynchronous, durable buffer between the event that triggers an audit record and the persistence of that record in the audit log. When an auditable action occurs, the application publishes an audit event to a Kafka topic — this is a non-blocking, microsecond operation. The business transaction proceeds and commits independently. A dedicated audit log consumer service reads from the Kafka topic and writes audit records to PostgreSQL. The two operations — the business transaction and the audit record — are now decoupled in time and in failure mode.

```
Kafka-Backed Audit Log — Full Architecture
============================================

  Various Event Sources:
  +-----------+ +-----------+ +-----------+ +-----------+
  | Web App   | | Admin UI  | | API Server| | Scheduler |
  | (user ops)| |(admin ops)| |(api calls)| |(jobs)     |
  +-----+-----+ +-----+-----+ +-----+-----+ +-----+-----+
        |               |               |              |
        |   Publish audit events (async, non-blocking)
        |               |               |              |
        v               v               v              v
  +--------------------------------------------------------------+
  |                   Kafka: "audit-events" topic                |
  |                                                              |
  | Partition 0: user events         Partition 1: admin events  |
  | Partition 2: api events          Partition 3: system events  |
  |                                                              |
  | Messages are durable (retained for 7 days by default)       |
  | High throughput (millions of events/sec)                     |
  | Ordered within each partition                                |
  +--------------------------------------------------------------+
             |
             | Audit Log Consumer Service
             | (reads from Kafka, writes to PostgreSQL)
             v
  +------------------------------+
  |  Audit Consumer Service      |
  |                              |
  |  1. Read batch from Kafka    |
  |  2. Validate event schema    |
  |  3. Enrich (add metadata,    |
  |     resolve IDs to names)    |
  |  4. Batch INSERT into        |
  |     PostgreSQL audit_log     |
  |  5. Commit Kafka offset      |
  |     (acknowledge processed)  |
  +------------------------------+
             |
             v
  +------------------------------+
  |  PostgreSQL audit_log        |
  |  (partitioned, append-only,  |
  |   immutable, indexed)        |
  +------------------------------+

  Failure scenarios handled gracefully:
  [A] Application server crashes after publishing to Kafka:
      -> Kafka retains the event. Consumer processes it. No loss.

  [B] Audit Consumer crashes mid-batch:
      -> Kafka offset not yet committed. Consumer restarts,
         re-reads from last committed offset.
         INSERT uses ON CONFLICT DO NOTHING on event_id (UUID)
         to handle re-processing safely. Idempotent.

  [C] PostgreSQL audit DB is temporarily unavailable:
      -> Kafka buffers all events until PostgreSQL recovers.
         Consumer catches up. No event lost.
```

The idempotency of the consumer's writes deserves special mention. Because Kafka's at-least-once delivery guarantee means a consumer may occasionally process the same message more than once (particularly after a crash and restart), the INSERT into the audit log table must be designed to be **idempotent** — processing the same message twice must produce the same result as processing it once. This is achieved through the `event_id` UUID column (generated by the publisher and included in the Kafka message) and a `ON CONFLICT (event_id) DO NOTHING` clause on the INSERT. If the same event is received twice, the second insert simply does nothing, because the event_id already exists in the table. The UUID's global uniqueness ensures that genuinely different events never collide.

### 2.5 Tamper Evidence and Cryptographic Integrity

For the highest-security audit log implementations — in financial systems, in cryptographic custody chains, in systems where regulators may demand proof that records have not been tampered with — simple database immutability (preventing UPDATE and DELETE through privilege restrictions) is not sufficient. A sufficiently privileged database administrator can still modify records. The audit log must be made tamper-evident in a way that survives even insider threats.

The standard cryptographic technique for this is a **hash chain**, directly analogous to the data structure that underlies blockchain systems. Each audit record contains a hash of its own content concatenated with the hash of the previous audit record. If any record in the chain is modified, its hash changes, which breaks the chain — the next record's "previous hash" no longer matches, and the inconsistency is detectable by anyone who re-computes the chain. This transforms the audit log from a collection of independent records into a cryptographically linked sequence where any tampering is mathematically detectable.

```
Hash Chain Audit Log — Cryptographic Integrity
================================================

  Record 1:
  +--------------------------------------------------+
  | event_id: uuid-1                                 |
  | event_type: "user.login"                         |
  | actor_id: 123                                    |
  | occurred_at: 2024-01-15T10:00:00Z               |
  | prev_hash: "0000000000000000" (genesis)          |
  | this_hash: SHA256(all fields + prev_hash)        |
  |          = "a3f8b2c1d9e4f6..."                   |
  +--------------------------------------------------+
           |
           | this_hash becomes prev_hash for Record 2
           v
  Record 2:
  +--------------------------------------------------+
  | event_id: uuid-2                                 |
  | event_type: "record.accessed"                    |
  | actor_id: 123                                    |
  | target_id: 456                                   |
  | occurred_at: 2024-01-15T10:01:00Z               |
  | prev_hash: "a3f8b2c1d9e4f6..." (from Record 1)  |
  | this_hash: SHA256(all fields + prev_hash)        |
  |          = "d7e2a9b4c1f3e8..."                   |
  +--------------------------------------------------+

  If an attacker modifies Record 1 (e.g., to hide a login):
  - Record 1's content changes
  - Record 1's this_hash must be recomputed -> "XXXXXXXX..."
  - But Record 2's prev_hash is still "a3f8b2c1d9e4f6..."
  - These no longer match -> TAMPERING DETECTED

  Verification: recompute the chain and check every hash.
  If all hashes chain correctly: log is intact.
  If any hash breaks the chain: the exact tampered record
  can be identified.
```

In practice, full hash-chain verification is computationally expensive for very long audit logs and is typically run periodically (daily or weekly) rather than on every read. Some organizations publish periodic "checkpoint hashes" — the hash of the chain up to a specific record — to a public immutable ledger (such as a public blockchain or a certificate transparency log), making it impossible to retroactively alter historical records without being detected.

### 2.6 Long-Term Retention and the Regulatory Archive

A final dimension of the audit log design is long-term retention. Many regulations — HIPAA in healthcare, PCI-DSS in payments, GDPR in European data protection, SOX in financial reporting — specify how long audit records must be retained. A healthcare system may be required to retain audit records for seven years. A financial institution may need to keep records for ten years or more. Storing seven to ten years of high-volume audit data in PostgreSQL, even partitioned, can result in tables containing hundreds of billions of rows and storing tens of terabytes of data — manageable but expensive.

The standard architectural approach is a two-tier retention strategy. Warm, recent audit data — records from the past one to two years — lives in PostgreSQL, where it is indexed and quickly queryable through the application's audit search interface. Older records are archived to object storage (Amazon S3, Google Cloud Storage) in a compressed, columnar format like Parquet. These archived records can be queried through serverless analytics tools (Amazon Athena, BigQuery) at dramatically lower cost than keeping them in PostgreSQL, though with higher query latency. The transition from warm to cold storage happens automatically through a scheduled archival job that exports old partitions, compresses them, uploads them to object storage, and detaches the partition from the PostgreSQL table.

```
Tiered Audit Log Retention
============================

  Hot tier (last 90 days): PostgreSQL (fast, expensive)
  +--------------------+
  | audit_log_2024_10  |  Current month   -> Active writes
  | audit_log_2024_09  |  Last month      -> Frequent queries
  | audit_log_2024_08  |  2 months ago    -> Occasional queries
  +--------------------+
  Query time: < 100ms (indexed PostgreSQL queries)

  Warm tier (90 days - 2 years): PostgreSQL, compressed partitions
  +--------------------+
  | audit_log_2024_07  |
  | ...                |  Compliance queries, investigations
  | audit_log_2022_10  |
  +--------------------+
  Query time: < 1 second (indexed but cold data)

  Cold tier (2+ years): Amazon S3 as Parquet files
  +--------------------+
  | s3://audit-archive |
  | /2022/01/*.parquet |  Regulatory archive, rare access
  | /2021/01/*.parquet |
  | ...                |
  +--------------------+
  Query tool: Amazon Athena (serverless SQL over S3)
  Query time: 5-30 seconds (full scan, no indexes)
  Cost: ~$5/TB queried (vs. $hundreds/month for PostgreSQL storage)

  Archival job (runs monthly):
  1. Export audit_log_<old_month> to S3 as compressed Parquet
  2. Verify Parquet file integrity (row count matches)
  3. DETACH partition from PostgreSQL
  4. DROP partition (data is safe in S3)
  -> Old partition is gone from PostgreSQL, query via Athena
```

## Summary

The two patterns covered in this document represent the most demanding ends of the data architecture spectrum — one optimizing for the speed and sophistication of data retrieval, the other optimizing for the permanence and trustworthiness of data recording.

The Elasticsearch plus PostgreSQL dual write pattern is a study in using specialization to overcome the inherent limitations of general-purpose tools. PostgreSQL is magnificent at what it does — ACID transactions, relational integrity, complex joins — but full-text search relevance ranking and fuzzy matching are not among its core competencies. Elasticsearch fills that gap with an architecture (the inverted index) specifically designed for the access pattern of search. The dual write pattern, and the more robust CDC approach, are the mechanisms by which these two systems are kept synchronized, each serving the role it was designed for.

The audit log pattern is a study in designing for permanence, immutability, and the long arc of time. By combining PostgreSQL's reliability and queryability with Kafka's decoupling and buffering capability, the pattern achieves an audit system that is both highly concurrent (Kafka absorbs write spikes without burdening the main application) and highly trustworthy (the append-only table, the idempotent consumer, and optionally the hash chain together guarantee that audit records accurately and permanently reflect the history of the system). The partitioning strategy and tiered retention model ensure that this permanent record remains practically manageable and economically viable over the years and decades that regulatory compliance may demand.

Together, search and audit logging represent two of the most architecturally consequential features in any serious application — and the patterns described here reflect the hard-won wisdom of the industry's most demanding production systems.
