# Sharding

### A Deep, Conceptual Journey from the Ground Up

> _Sharding is what you do when you have exhausted every other option — and understanding why that is true is the beginning of understanding sharding itself._

---

## Preface: The Wall You Cannot Scale Over

Every database has a ceiling. It is determined by the hardware it runs on — the number of CPU cores that can execute queries in parallel, the amount of RAM available to cache hot data, the throughput of the storage subsystem, and the bandwidth of the network interface. On a single machine, all of these resources are finite and fixed.

For most applications, that ceiling is far above where the application ever reaches. You optimize queries, add indexes, tune configuration, add read replicas, and the single primary server handles everything comfortably for years. This is the right approach. Vertical scaling — upgrading to a larger machine — and read replicas handle the vast majority of real-world growth stories.

But some applications hit a ceiling that no single machine can solve. Not just a performance ceiling, but a fundamental capacity ceiling: the data itself is too large to fit on one machine's disk, or the write throughput exceeds what one machine's storage subsystem can sustain, or the rate of incoming writes exceeds what a single WAL writer can flush to disk, or compliance requirements mandate that different users' data cannot physically coexist on the same server.

When you hit that wall — and only when you hit that wall — **sharding** is the answer.

Sharding is the practice of distributing data across multiple, independent database servers (called **shards**) such that each server holds only a subset of the total data. No single machine holds everything. Queries are routed to the shard that holds the relevant data. The capacity of the system grows by adding more shards.

This guide is about understanding sharding deeply: what it truly is, why the shard key selection is the most consequential technical decision in any distributed database architecture, how the different sharding strategies work, what goes wrong when they go wrong, and what the real operational costs of cross-shard queries, hotspots, and resharding look like.

## Chapter 1: What Sharding Is and Why It Exists

### The Fundamental Problem: One Machine Is Not Enough

Before discussing sharding, it is worth being precise about what problem it actually solves — because sharding is often proposed as a solution to problems that have cheaper, simpler solutions.

There are four distinct capacity problems that sharding genuinely solves:

**Write throughput ceiling:** A single PostgreSQL primary can sustain roughly 10,000–100,000 simple writes per second on modern hardware, depending on write size and disk type. Read replicas do not help with writes — they only replicate what the primary writes. If your application genuinely needs to sustain more writes than one primary can handle, you need multiple primaries, which means sharding.

**Storage capacity ceiling:** A single disk array or cloud volume has a maximum capacity. For datasets that grow past what one machine's storage can hold (or past what is economically feasible to store in one place), distributing storage across multiple machines is the only option.

**Working set exceeds RAM:** Databases are fast when their "hot" data fits in RAM (the buffer pool). When working set size exceeds available RAM, cache miss rates climb and disk I/O becomes a bottleneck. Splitting the dataset across machines so that each machine's hot set fits in its RAM can restore cache hit rates.

**Regulatory data isolation:** Some jurisdictions require that data about their citizens not leave the country. A single global database violates this. Sharding by geography, with each geographic shard in the required jurisdiction, is one solution to data residency requirements.

### What Sharding Is Not

Equally important is understanding what sharding does not solve — because one of the most common architectural mistakes is applying sharding to a problem that has a better solution:

```
Sharding Does NOT Help With:

  Slow read queries:
  → Add indexes, optimize queries, use read replicas.
  → Sharding means cross-shard queries are SLOWER, not faster.

  High read throughput:
  → Add read replicas (cheaper, simpler, no complexity penalty).
  → One primary with 10 read replicas handles read traffic well.

  Large but cold datasets:
  → Archive old data to cheaper storage (S3, cold tablespace, partitioning).
  → Sharding a cold archive is unnecessary complexity.

  Database slowness from bad schema design:
  → Fix the schema, add indexes, normalize properly.
  → Sharding a slow, poorly-designed database gives you
    multiple slow, poorly-designed databases.

  The rule: Exhaust all single-machine optimizations first.
  Sharding is a last resort, not a first response to scale.
```

### The Architecture of a Sharded System

A sharded system has three logical components: the **shards** themselves, the **routing layer**, and the **application code** that understands it is talking to a sharded system.

```
Sharded Architecture — Three Components:

  ┌───────────────────────────────────────────────────────────────┐
  │                    APPLICATION                                │
  │  "I want to write user_id=12345's order"                      │
  │  "I want to read all orders for user_id=12345"                │
  └──────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
  ┌───────────────────────────────────────────────────────────────┐
  │                  ROUTING LAYER                                │
  │  "user_id=12345 belongs to Shard 2"                           │
  │                                                               │
  │  Options:                                                     │
  │  ├── Application-side routing (application knows the logic)   │
  │  ├── Proxy-based routing (e.g., Vitess, Citus, ProxySQL)      │
  │  └── Service-based routing (a dedicated routing service)      │
  └──────┬────────────────────┬────────────────────┬─────────────┘
         │                    │                    │
         ▼                    ▼                    ▼
  ┌────────────┐       ┌────────────┐       ┌────────────┐
  │  Shard 0   │       │  Shard 1   │       │  Shard 2   │
  │ PostgreSQL │       │ PostgreSQL │       │ PostgreSQL │
  │ users 0–3M │       │ users 3–6M │       │ users 6–9M │
  │ (+ replicas│       │ (+ replicas│       │ (+ replicas│
  │  for HA)   │       │  for HA)   │       │  for HA)   │
  └────────────┘       └────────────┘       └────────────┘

  Each shard is a complete, independent PostgreSQL instance
  with its own primary and replicas for high availability.
  No shard knows about or communicates with other shards.
```

The routing layer is the brain of the system. It knows which shard owns which data and directs every query to the correct shard. It can be implemented in the application itself (the application includes logic like "for user_id X, connect to database host Y"), in a smart proxy (Vitess, Citus, pgpool-II), or in a dedicated microservice.

### The Core Trade-off Sharding Forces

Sharding is not a free lunch. Every benefit it provides comes with a cost:

```
Sharding Benefits vs. Costs:

  Benefit: Horizontal write scalability
  Cost:    Transactions that span two shards require distributed transactions
           (or you sacrifice atomicity for performance)

  Benefit: Storage beyond one machine
  Cost:    Queries that need data from multiple shards require scatter-gather
           (fan out to all shards, collect results, merge — expensive)

  Benefit: Fault isolation (one shard's failure doesn't take down others)
  Cost:    Operational complexity multiplies with the number of shards
           (N shards = N sets of backups, monitoring, upgrades, failovers)

  Benefit: Geographic distribution
  Cost:    Joins across shards are either impossible or extremely expensive

  Benefit: Independent scaling of shards
  Cost:    No global uniqueness constraints, no global foreign keys,
           no global transactions with ACID semantics

  The honest summary:
  Sharding makes the write scaling problem go away.
  It makes every other database problem harder.
  This is why you only shard when you must.
```

## Chapter 2: Shard Key Selection — The Most Critical Decision

### Why the Shard Key Is Everything

The shard key is the attribute (or combination of attributes) that determines which shard a given piece of data lives on. It is the single most important architectural decision in a sharded system, and it is also the decision that is most difficult to change later. Getting it wrong means either rewriting the application, performing a massively expensive resharding operation, or living with severe performance problems permanently.

The shard key shapes everything: which queries can be served from a single shard (fast), which require scatter-gather across all shards (slow), whether write load is distributed evenly or concentrated on one shard (hotspot), whether transactions can be kept single-shard (simple) or require cross-shard coordination (complex), and whether adding new shards requires moving data (expensive) or not.

A perfect shard key has five properties:

```
Properties of an Ideal Shard Key:

  1. High cardinality:
     Many distinct values, so data distributes across many shards.
     A shard key with only 3 possible values can only have 3 shards.
     Example: user_id (millions of values) ✓
     Example: user_type ('free', 'paid', 'enterprise') — only 3 values ✗

  2. Even distribution:
     The values are spread roughly uniformly, so shards end up with
     similar amounts of data. A key whose values are highly skewed
     (most rows have value X) concentrates data on one shard.
     Example: user_id (uniformly distributed IDs) ✓
     Example: country_code ('US' = 70% of users) ✗

  3. Query locality:
     The most common queries filter on the shard key, so most queries
     touch only one shard. If queries almost never filter on the key,
     sharding does not help those queries.
     Example: user_id for a social app (most queries are "for user X") ✓
     Example: product_category for an e-commerce order table
              (orders are queried by user, not by category) ✗

  4. Immutability:
     The shard key value for a row should not change. Changing a shard
     key value requires moving the row to a different shard — a DELETE
     on the old shard and an INSERT on the new shard, potentially across
     a distributed transaction. Immutable keys (auto-generated IDs) are
     far safer than mutable ones (email addresses, usernames).
     Example: auto-generated user_id ✓
     Example: email (users change emails) ✗

  5. Transaction co-location:
     The business transactions that must be ACID-compliant should involve
     data that lives on the same shard (same shard key value). If your
     most important business transaction spans multiple users' data,
     user_id is a poor shard key for that transaction.
     Example: user_id for a social app (most operations are per-user) ✓
     Example: user_id for a bank transfer between two users (spans two shards) ✗
```

### The Tenant ID Pattern: The Most Common Correct Answer

For multi-tenant SaaS applications, the `tenant_id` (or `organization_id`, `company_id`) is almost always the right shard key. Here is why it satisfies all five properties:

- **High cardinality:** Potentially thousands to millions of tenants.
- **Even distribution:** If tenants are roughly similar in size, data distributes evenly (with hotspot risk for very large tenants — discussed later).
- **Query locality:** Almost every query in a SaaS application is scoped to a single tenant ("show me all orders for tenant X's users"). These queries touch only one shard.
- **Immutability:** Tenants do not change their IDs.
- **Transaction co-location:** All of a tenant's data is on one shard, so transactions within a tenant's scope are single-shard and fully ACID-compliant.

```
Tenant-Sharded SaaS Architecture:

  Tenant ID: determines the shard
  All of a tenant's data lives on one shard:
    users (for that tenant)
    orders (for that tenant)
    products (for that tenant)
    invoices (for that tenant)
    audit_logs (for that tenant)

  Shard 0: Tenants 1–1000    (small tenants)
  Shard 1: Tenants 1001–2000 (small tenants)
  Shard 2: Tenant 2001       (large tenant, owns a whole shard)

  Query: "Get all invoices for tenant 1500"
  → Route to Shard 1. One network hop. ACID compliant. ✓

  Query: "Get all invoices across all tenants"
  → Scatter to all shards. Merge results. Slow. ✗
  (Cross-tenant analytics: run offline, use a separate analytics system)
```

### When There Is No Perfect Shard Key

Sometimes no single attribute makes a perfect shard key. A social graph, for example, involves interactions between users — and a query like "show me all posts liked by users that Alice follows" spans many users' data. There is no single shard key that keeps all relevant data co-located for all queries.

In these cases, the correct approach is to identify the dominant query pattern and optimize the shard key for that pattern, accepting that secondary query patterns will require scatter-gather. For a social feed, `user_id` as the shard key optimizes for "show me my feed" (single shard) at the cost of "show me who liked this post across all users" (scatter-gather). The dominant query wins.

## Chapter 3: Range-Based Sharding

### Dividing Data Along Ordered Intervals

**Range-based sharding** assigns a contiguous range of shard key values to each shard. Shard 0 owns keys 0–999,999, Shard 1 owns 1,000,000–1,999,999, and so on. The routing layer maintains a map of these ranges and directs each query to the shard whose range contains the relevant key value.

The conceptual relationship between range-based sharding and range-based partitioning (from the previous chapter) is direct: they are the same idea applied at different scales. Partitioning distributes data across multiple tables on one machine. Range-based sharding distributes data across multiple machines.

```
Range-Based Sharding — Key Routing:

  Shard Range Map (maintained by routing layer):
  ┌─────────────┬──────────────────────────┬────────────────────────┐
  │  Shard ID   │  Key Range               │  Host                  │
  ├─────────────┼──────────────────────────┼────────────────────────┤
  │  Shard 0    │  user_id: 0 – 999,999    │  db0.internal.example  │
  │  Shard 1    │  user_id: 1M – 1,999,999 │  db1.internal.example  │
  │  Shard 2    │  user_id: 2M – 2,999,999 │  db2.internal.example  │
  │  Shard 3    │  user_id: 3M – ∞         │  db3.internal.example  │
  └─────────────┴──────────────────────────┴────────────────────────┘

  Routing logic:
  user_id = 500,000  → Shard 0 (0 ≤ 500,000 < 1,000,000)
  user_id = 1,500,000 → Shard 1 (1,000,000 ≤ 1,500,000 < 2,000,000)
  user_id = 2,100,000 → Shard 2 (2,000,000 ≤ 2,100,000 < 3,000,000)
```

### The Strengths of Range-Based Sharding

**Range queries are efficient.** If your application often asks "give me all orders for users between ID 1,000,000 and 2,000,000," range sharding means that query might touch only one or two shards — because contiguous ranges of the key are co-located. Hash sharding scatters those rows across all shards.

**Flexible splitting without full resharding.** When a range becomes too large, you can split it — assign the upper half to a new shard — without moving data from other shards. Only the data in the split range moves.

**Time-ordered data works naturally.** For keys that are time-based (timestamps, auto-incrementing IDs that grow with time), range sharding naturally keeps recent data together. Recent data is almost always hotter than old data, so recent data lands on the newest shard while older data stays on older shards.

### The Critical Weakness: Sequential Hotspots

The most severe problem with range-based sharding on sequential keys is that all new writes go to the same shard — the one holding the highest current range. If your `user_id` is a sequential auto-increment, every new user registration goes to the last shard. Every new order ID goes to the last shard. The most recent (and often most frequently accessed) data is concentrated on a single machine, defeating the purpose of distributing write load.

```
Sequential Key Hotspot Under Range Sharding:

  Time ──────────────────────────────────────────────────────►
  user_id: 1  2  3  4  5  ...  999999 | 1000000  1000001  ...

  Shard 0 (0–999,999):                 │
  All new registrations up to 1M       │  Then shard is FULL.
                                       │  All writes moved to Shard 1.
  Shard 1 (1M–2M):                     │
                                       │  Shard 0: COLD (no new writes)
  Shard 1: ALL new writes              │  Shard 1: RED HOT (all new writes)
  ████████████████████████████████████►│  Shard 2+: EMPTY (waiting)

  Result: 100% of write load on the newest shard.
          Other shards are either cold (old data) or empty (future).
          This is the "last shard hotspot" — the most common
          failure mode of range sharding on sequential keys.

  Solutions:
  1. Use non-sequential keys (UUIDs, hash-derived IDs)
     so new rows land on all shards, not just the last.
  2. Use time-based key with pre-allocation:
     Assign multiple future ranges to different shards,
     so sequential writes cycle across shards.
  3. Combine with hash sharding (see composite sharding).
```

### Range-Based Sharding: When It Fits

Range sharding is the right choice when:

- **Range queries on the shard key are common** ("users registered between date A and date B," "orders with IDs in range X to Y").
- **The key values are not sequentially generated** (UUIDs, or user-provided values with natural distribution).
- **Data archival by range is important** (drop Shard 0 when the oldest user cohort's data expires).
- **You need split/merge granularity control** (can split one range without affecting others).

## Chapter 4: Hash-Based Sharding

### Distributing Data Uniformly by Design

**Hash-based sharding** applies a hash function to the shard key value and uses the result (modulo the number of shards) to determine which shard a row belongs to. Because hash functions distribute values uniformly and pseudorandomly, data is spread evenly across shards regardless of the key's distribution.

```
Hash-Based Sharding — Key Routing:

  Routing formula: shard_id = hash(shard_key) % num_shards

  Example with 4 shards (num_shards = 4):
  user_id = 1      → hash(1) % 4 = 1      → Shard 1
  user_id = 2      → hash(2) % 4 = 2      → Shard 2
  user_id = 3      → hash(3) % 4 = 3      → Shard 3
  user_id = 4      → hash(4) % 4 = 0      → Shard 0
  user_id = 5      → hash(5) % 4 = 1      → Shard 1
  user_id = 1000   → hash(1000) % 4 = 0   → Shard 0
  user_id = 9999   → hash(9999) % 4 = 3   → Shard 3

  The distribution is uniform: each shard gets roughly 25% of rows.
  Sequential IDs (1, 2, 3, 4, 5) are scattered across all 4 shards.
  No hotspot on the last shard.
```

### Consistent Hashing: The Production-Grade Version

Simple modulo hashing (`hash(key) % N`) has a fatal problem: when you change N (add or remove a shard), almost every row maps to a different shard. Adding Shard 4 to a 4-shard cluster means `hash(key) % 5` gives different results than `hash(key) % 4` for almost all keys. You have to move nearly every row in the database — a catastrophic operation.

**Consistent hashing** solves this by mapping both shard keys and shard identifiers onto a virtual "hash ring" — a circular number space from 0 to 2^32 (or 2^64). Each shard owns an arc of the ring. A row belongs to the shard whose position on the ring is the nearest clockwise successor of the row's hashed key position.

```
Consistent Hashing Ring (simplified):

                         0
                    _____|_____
                   /     |     \
                  /   Shard A   \
     315 ────────●               ●──────── 45
                  \             /
              270  \           / 90
    Shard D   ───── ●─────────● ──── Shard B
                    |         |
              225   |  Shard C |  135
                    ●─────────●
                         180

  user_id=5 hashes to position 30 → nearest clockwise shard: A (at 45)
  user_id=9 hashes to position 92 → nearest clockwise shard: C (at 180)
  user_id=2 hashes to position 318 → nearest clockwise shard: A (at 45, wraps around)

  Adding Shard E between A and B (at position 67):
  Only rows that were going to Shard B (90–180) and whose hash falls
  between 45 and 67 need to move to Shard E.
  Everything else stays exactly where it is.

  Without consistent hashing (simple modulo):
  Going from 4 to 5 shards → ~80% of all rows move.
  With consistent hashing:
  Going from 4 to 5 shards → ~20% of rows move (1/N of the ring).
```

Virtual nodes (vnodes) make consistent hashing even more uniform: each physical shard is assigned multiple positions on the ring (100–200 vnodes per shard is common). This prevents any single shard from owning a disproportionately large arc of the ring.

### Hash Sharding's Strengths and Limitations

```
Hash-Based Sharding Strengths:

  ✓ Uniform distribution — no hotspots from sequential keys
  ✓ Simple routing — a pure function, no lookup table needed
  ✓ Scales write load linearly — each new shard absorbs a proportional share
  ✓ No coordination between shards needed for routing

Hash-Based Sharding Limitations:

  ✗ Range queries are impossible to shard-local:
    "Give me all users registered this week" requires hitting ALL shards.
    The hash of a timestamp has no relationship to the timestamp itself.

  ✗ Ordering within the shard key is lost:
    "Give me the next 100 users after user_id=5000" requires scatter-gather.

  ✗ Adding shards requires data movement (even with consistent hashing):
    ~1/N of data moves when adding the Nth shard.
    For a large cluster, 1/N can still be enormous amounts of data.

  ✗ Cannot exploit data locality for related entities:
    If users and their orders are on different shards (because they
    have different IDs), joining user profile with order data requires
    cross-shard communication.
```

## Chapter 5: Directory-Based Sharding

### A Lookup Table as the Routing Brain

**Directory-based sharding** (also called lookup-based sharding) maintains an explicit mapping table — the **shard directory** or **shard catalog** — that records exactly which shard each entity (or group of entities) belongs to. Instead of computing the shard from the key value algorithmically (as in hash or range sharding), the routing layer looks up the answer in the directory.

```
Directory-Based Sharding Architecture:

  Shard Directory (a dedicated, highly-available metadata store):
  ┌──────────────┬──────────────┬────────────────────────────────┐
  │  tenant_id   │  shard_id    │  metadata                      │
  ├──────────────┼──────────────┼────────────────────────────────┤
  │  1 (Netflix) │  Shard 5     │  {"size":"large", "tier":"A"}  │
  │  2 (Shopify) │  Shard 2     │  {"size":"xlarge","tier":"A"}  │
  │  3 (Acme)    │  Shard 0     │  {"size":"small", "tier":"B"}  │
  │  4 (Globex)  │  Shard 1     │  {"size":"medium","tier":"B"}  │
  │  5 (Initech) │  Shard 3     │  {"size":"small", "tier":"B"}  │
  │  6 (Umbrella)│  Shard 5     │  {"size":"medium","tier":"A"}  │
  └──────────────┴──────────────┴────────────────────────────────┘

  Routing:
  Query for tenant_id=2 → look up directory → Shard 2 → db2.example.com
  Query for tenant_id=6 → look up directory → Shard 5 → db5.example.com
```

### Why Directory-Based Sharding Exists

The directory approach exists to solve problems that algorithmic sharding cannot:

**Moving individual entities without resharding:** In hash or range sharding, moving a large tenant to a dedicated shard requires either resharding (expensive) or maintaining a special-case exception map (which is essentially a directory). Directory sharding makes this the default: update one row in the directory, and the routing changes instantly.

**Heterogeneous shard sizes:** Large tenants can be given their own dedicated shard (or even multiple shards). Small tenants can be packed many-to-a-shard. The directory records this explicitly, and the routing handles it transparently.

**Metadata-driven routing:** The directory can store rich metadata alongside the shard assignment — tier information, geographic location, feature flags, maintenance status. The routing layer can make intelligent decisions based on this metadata, not just the shard ID.

```
Directory Sharding — Moving a Tenant:

  Before: tenant_id=2 (Shopify) is on Shard 2 (shared with 1000 other tenants)
          Shopify has grown and needs a dedicated shard.

  Old directory entry:
  tenant_id=2 → Shard 2 (shared)

  New directory entry (after migration):
  tenant_id=2 → Shard 7 (dedicated for Shopify only)

  Migration process:
  1. Copy all of Shopify's data from Shard 2 to Shard 7 (while live).
  2. Keep Shard 7 synchronized with new writes to Shard 2 (via CDC).
  3. When Shard 7 is caught up, update the directory entry (one row update).
  4. New queries for Shopify go to Shard 7. Old queries drain from Shard 2.
  5. Clean up Shopify's data from Shard 2.

  Zero downtime. One directory update. No disruption to other tenants.
  This is impossible without a directory — hash and range sharding
  do not support per-entity migration.
```

### The Operational Challenge: Directory Availability

The shard directory is the most critical component of the system. Every query must consult it (or use a cached copy). If the directory is unavailable, routing fails and the entire system is down — even if all shards are healthy.

This creates a reliability requirement for the directory that is even stricter than for the shards themselves. Solutions include:

```
Making the Shard Directory Highly Available:

  Option 1: Replicated metadata database
  Directory lives in a highly-available database (replicated PostgreSQL,
  CockroachDB, or Spanner). Reads from replicas, writes to primary.
  Read latency: ~1ms (local replica). Availability: 99.99%+.

  Option 2: Distributed cache
  Directory is preloaded into Redis or Memcached clusters.
  Cache is invalidated and refreshed when directory changes.
  Read latency: <1ms. Availability: Redis Sentinel/Cluster for HA.

  Option 3: Client-side caching
  Each application server caches the directory in memory.
  Refreshes periodically (every 60 seconds) or on cache miss.
  Read latency: <1μs (in-process memory). Stale window: up to 60 seconds.

  Most production systems use Option 2 or 3:
  The directory is a slow-changing, small dataset (one row per tenant).
  Client caching means almost no directory queries at runtime —
  only on cache miss or directory update.
  The cache miss penalty (one database round-trip) is rare.
```

## Chapter 6: The Hotspot Problem

### When One Shard Becomes the Entire System

A **hotspot** is a shard that receives a disproportionately large fraction of the system's read or write traffic. In an extreme case, one shard handles 90% of all queries while all others sit mostly idle. When this happens, the theoretical horizontal scalability of sharding collapses: the bottleneck shard is effectively the entire system's bottleneck, and adding more shards to the cluster does nothing to relieve it.

Hotspots arise from a mismatch between the shard key and the actual distribution of access. The data might be distributed evenly, but if one entity or one range of entities is accessed far more frequently than others, the shard holding that entity becomes hot.

### Types of Hotspots

```
Hotspot Taxonomy:

  Type 1: Sequential write hotspot (range sharding on auto-increment key)
  ─────────────────────────────────────────────────────────────────────
  New user_ids are always the largest current value.
  Range sharding puts them all on the last shard.
  100% of new user writes hit the same shard.
  Symptom: most recent shard has 10× the write rate of others.

  Type 2: Celebrity / whale hotspot (one entity is extremely popular)
  ─────────────────────────────────────────────────────────────────────
  Elon Musk's Twitter account gets millions of reads per second.
  His shard (determined by his user_id) receives all those reads.
  The shard cannot handle that volume even if perfectly sized.
  All other 9 shards are lightly loaded.
  Symptom: one shard at 100% CPU, others at 5%.

  Type 3: Geographic or temporal hotspot (event-driven traffic spike)
  ─────────────────────────────────────────────────────────────────────
  A viral event (Super Bowl, product launch, breaking news) causes
  a sudden spike in writes/reads for specific entities or time ranges.
  The shards holding those entities/ranges are overwhelmed.
  Symptom: sudden spike on specific shards correlated with external events.

  Type 4: Skewed key distribution (non-uniform data)
  ─────────────────────────────────────────────────────────────────────
  List sharding on country_code: 'US' = 70% of users.
  The 'US' shard holds 70% of data and receives 70% of traffic.
  Symptom: one shard significantly larger and busier than others.
```

### Mitigation Strategies for Hotspots

Different hotspot types require different mitigations:

**For sequential write hotspots:** Stop using sequential keys. Use UUIDs (random 128-bit values) or time-ordered but non-sequential IDs like ULIDs or Twitter Snowflake IDs. These distribute naturally across all shards under hash routing. If you must use sequential IDs, pre-split ranges and pre-assign them to different shards so sequential inserts cycle across shards.

**For celebrity / whale hotspots (read-heavy):** Add read replicas to the hot shard. Since the celebrity problem is usually read-heavy (many people reading the same data), read replicas scale out reads without requiring data movement. This is actually the most effective solution for read hotspots: the hot entity stays on its shard, but its shard has 10 replicas instead of 2.

```
Celebrity Read Hotspot Mitigation:

  Before: @elonmusk's shard has 1 primary + 2 replicas
          Traffic: 1M reads/second → shard at capacity

  After: @elonmusk's shard has 1 primary + 20 replicas
         Traffic: 1M reads/second → 50K reads/second per replica → comfortable

  Application-side: route read traffic to replicas based on shard-level load.
  Directory: store replica count per shard for routing decisions.
  Cost: 18 additional replica servers for the hot shard.
        But: this is far cheaper than redesigning the entire shard key.
```

**For write-heavy celebrity hotspots:** This is the hardest problem. Options include:

- **Write buffering:** Accumulate writes in a high-throughput queue (Kafka, RabbitMQ) and apply them to the hot shard in batches.
- **Counter sharding:** For highly-contested counters (like count, view count), maintain per-shard partial counters and aggregate them at read time.
- **Application-layer caching:** Cache the hot entity's data aggressively, so most reads are served from cache and the database sees only a fraction of the true traffic.

```
Counter Sharding for Write-Heavy Hotspots:

  Problem: A viral post receives 10,000 "likes" per second.
           All writes hit the single shard holding that post's like_count.
           That shard cannot sustain 10,000 writes/second on one row.

  Solution: Distributed counters across all shards.

  Instead of:
  post_id=42: like_count = 5,000,000

  Store partial counts on ALL shards:
  Shard 0: post_id=42, partial_likes = 1,250,000
  Shard 1: post_id=42, partial_likes = 1,250,000
  Shard 2: post_id=42, partial_likes = 1,250,000
  Shard 3: post_id=42, partial_likes = 1,250,000

  Each like randomly goes to any shard (1/4 load per shard).
  Reading total likes: sum all shards' partial_likes = 5,000,000.

  Write load: 2,500 writes/second per shard instead of 10,000.
  Read cost: must query all shards and sum (scatter-gather for one count).
  Trade-off: writes are cheap; reads are a scatter-gather. Acceptable for
  analytics-style reads (can be cached); unacceptable for real-time display.
```

## Chapter 7: Cross-Shard Queries and Distributed Joins

### The Price of Sharding: Scatter-Gather

When a query requires data from multiple shards — because the filtering condition is not on the shard key, or because it spans multiple entities that live on different shards — the routing layer must execute a **scatter-gather** operation: send the query (or a version of it) to all shards, collect all results, and merge them in the application or middleware layer.

Scatter-gather is the most expensive operation in a sharded system. It is not merely "slower" — it is qualitatively different from a single-shard query in several ways:

```
Scatter-Gather vs. Single-Shard Query:

  Single-shard query:
  ┌──────────────────────────────────────────────────────┐
  │  App → Routing Layer → Shard 2 → Result              │
  │  Latency: 1 network hop + query time                 │
  │  e.g., 5ms total                                     │
  └──────────────────────────────────────────────────────┘

  Scatter-gather (4 shards):
  ┌──────────────────────────────────────────────────────┐
  │  App → Routing Layer → Shard 0 ──► Partial Result 0  │
  │                      → Shard 1 ──► Partial Result 1  │
  │                      → Shard 2 ──► Partial Result 2  │
  │                      → Shard 3 ──► Partial Result 3  │
  │                                                      │
  │  Routing Layer: merge, sort, paginate partial results │
  │                                                      │
  │  Latency: 1 network hop × N shards (parallel) + query│
  │  time on each shard + merge time                     │
  │  e.g., 50ms total (10× slower)                       │
  │                                                      │
  │  And: as you add more shards, scatter-gather gets    │
  │  proportionally slower (more partial results to merge)│
  └──────────────────────────────────────────────────────┘

  The crueler truth: with 100 shards, a scatter-gather query is
  not just slow — it is 100 concurrent queries against 100 database
  servers, each consuming resources. The aggregate resource cost is
  100× a single query even if the wall-clock time is similar.
```

### Cross-Shard Joins: The Hardest Problem

If scatter-gather is expensive, **cross-shard joins** are catastrophic. In a single-database join, both tables are accessible in the same query context, the optimizer can choose the optimal join algorithm, and indexes on both sides can be exploited. In a sharded system, the tables are on different servers with no shared query context.

```
Cross-Shard Join Problem:

  Scenario: users are sharded by user_id. Orders are also sharded by user_id.
            user_id=1000 → Shard 0. user_id=2000 → Shard 1.

  Query: "Find all orders over $500, with the customer's name and email"
  SELECT u.name, u.email, o.total
  FROM orders o JOIN users u ON o.user_id = u.user_id
  WHERE o.total > 500;

  Single database: trivial join. One query. Optimizer handles it.

  Sharded:
  Option A: Scatter-gather (expensive):
    Step 1: Send "SELECT * FROM orders WHERE total > 500" to ALL shards.
    Step 2: Collect all matching orders (potentially millions).
    Step 3: For each order, look up the user's name/email:
            → Determine which shard holds that user_id.
            → Query that shard for the user.
    Step 4: This is N queries to potentially N different shards.
    Result: N+1 query problem at the shard level. Catastrophically slow.

  Option B: Application-side join (better but still expensive):
    Step 1: Get all orders > $500 from all shards (scatter-gather).
    Step 2: Collect unique user_ids from the results.
    Step 3: Group user_ids by their shard.
    Step 4: Send batched user lookups to each shard.
    Step 5: Merge results in application memory.
    Result: Manageable if the result set is small. Breaks for large result sets.

  Option C: Duplicate the users table to all shards (denormalization):
    Each shard has a complete copy of the users table.
    Orders join to the local copy of users.
    Joins work locally.
    Cost: users data is replicated N times. Updates must propagate to all copies.
    Acceptable for small, read-heavy reference data (user profiles rarely change).

  Option D: Choose a shard key that co-locates the joined data:
    If user_id is the shard key for both users AND orders,
    then user 1000's profile AND user 1000's orders are on the SAME shard.
    The join is LOCAL. No cross-shard communication.
    This is the correct architectural answer: co-locate data that joins together.
```

### Designing to Avoid Cross-Shard Queries

The best mitigation for cross-shard queries is to design the data model so they rarely occur:

**Co-location:** When entity A regularly joins to entity B, ensure they share the same shard key. In Citus (PostgreSQL-based distributed database), this is called **co-location** and is a first-class concept: if orders and order_items both use `tenant_id` as the shard key, all of a tenant's orders and their line items are on the same shard. Joins between them are local.

**Denormalization of reference data:** Small, read-heavy, rarely-changed reference tables (country codes, product categories, configuration) can be replicated to every shard. Joins against them are always local, at the cost of maintaining N copies.

**Materialized views and pre-aggregations:** If a cross-shard query represents a recurring analytical need ("total revenue across all tenants"), pre-compute and cache the result in a separate aggregation table that lives outside the sharded data. The cross-shard computation happens in a background job, not on the critical path.

**Accept the limitation:** Some queries are genuinely cross-shard in nature — global analytics, compliance reports, audit queries. Accept that these queries are slow (or offline), design the shard key for the fast path (transactional queries), and use a separate system (data warehouse, read replicas of all shards, change data capture into an analytics store) for global analytics.

## Chapter 8: Resharding and Rebalancing

### The Inevitability of Change

No matter how carefully you choose your initial shard count and shard key, the system will eventually need to change. Data grows unevenly. Business requirements shift. Some shards become hot; others go cold. New features require different data access patterns. A shard's disk fills. The system needs to scale from 4 shards to 16. All of these scenarios require **resharding** — redistributing data across a different set of shards — and it is one of the most operationally challenging tasks in distributed systems.

The difficulty of resharding is, in fact, a major argument for using managed distributed databases (CockroachDB, Vitess, Citus, Amazon Aurora Sharding, Google Cloud Spanner) rather than hand-rolled sharding: these systems handle resharding automatically and continuously, while hand-rolled sharding makes it a manual, painful, high-risk operation.

### What Resharding Involves

```
Resharding: The Full Process

  Starting state: 4 shards, each holding 25% of data
  Target state:   8 shards, each holding 12.5% of data

  Naive approach (wrong): take down the system, split each shard in two,
  update routing, bring the system back up.
  Problem: potentially hours of downtime during data copy.
  Unacceptable for production systems.

  Online resharding process (correct):

  Phase 1: Prepare new shards
    Spin up 4 new shard servers (Shard 4, 5, 6, 7).
    Initialize empty databases.
    Set up replication slots or CDC (Change Data Capture) on old shards.

  Phase 2: Initial data copy
    For each old shard, copy half its data to the corresponding new shard.
    e.g., Shard 0 (users 0–999,999) → copy users 500,000–999,999 to Shard 4.
    This copy can take hours or days. System remains live throughout.
    All writes continue going to the old shards.
    New shard receives a full historical snapshot.

  Phase 3: Catch up with CDC
    While the initial copy was running, new writes arrived on old shards.
    Apply these new writes to the new shard using CDC (Change Data Capture)
    or WAL streaming.
    New shard approaches real-time with old shard.

  Phase 4: Cutover (the brief critical window)
    When new shard lag is <1 second from old shard:
    → Pause writes to the splitting range (very brief — seconds).
    → Apply the last few WAL records to new shard.
    → Update routing directory: users 500K–999K now route to Shard 4.
    → Resume writes.
    Downtime: seconds (for the specific key range being split).

  Phase 5: Cleanup
    Delete the migrated data from old Shard 0 (now holds only users 0–499,999).
    Old Shard 0 is now half its original size. Shard 4 is a new shard.
    Repeat for other shards.

  Total user-visible downtime: seconds per split range.
  Total operation time: hours to days (running in background).
```

### Consistent Hashing and Minimal Data Movement

With simple modulo hashing (`hash(key) % N`), going from 4 to 5 shards requires remapping almost all keys — 80% of the data moves. Consistent hashing, by contrast, limits data movement to approximately 1/N of the total data when adding one shard to an N-shard cluster.

```
Data Movement: Modulo vs. Consistent Hashing

  4 shards → 5 shards:

  Simple modulo:
    hash(key) % 4 vs hash(key) % 5 give different results for 80% of keys.
    80% of ALL DATA must move to a different shard.
    For a 10TB dataset: move 8TB of data. Catastrophic.

  Consistent hashing:
    Adding Shard E at position 50 on the ring (between A at 45 and B at 90):
    Only keys that hash to positions 45–50 (owned by Shard A) move to Shard E.
    That is 1/5 of Shard A's data, which is 1/5 × 1/4 = 5% of total data.
    For a 10TB dataset: move ~500GB. Manageable.

  Virtual nodes amplify this benefit:
  With 100 vnodes per shard, adding a new shard takes ownership of
  100/100×N positions across the ring, spreading data movement across all
  existing shards rather than one. Data movement is both minimal AND balanced.
```

### Rebalancing Without Full Resharding

Sometimes the problem is not total capacity but imbalance: some shards are too large or too hot while others are underutilized. **Rebalancing** moves specific key ranges or entities from hot/large shards to cool/small shards without changing the total number of shards.

```
Shard Rebalancing Scenario:

  Before rebalancing:
  Shard 0: 800GB (tenant A=600GB, tenant B=200GB)  ← overloaded
  Shard 1: 150GB (tenant C=80GB, tenant D=70GB)    ← underutilized
  Shard 2: 400GB (tenant E=400GB)                  ← balanced
  Shard 3: 50GB  (tenant F=50GB)                   ← very light

  Rebalancing action:
  Move tenant B (200GB) from Shard 0 to Shard 1:
  Update directory: tenant B → Shard 1

  After rebalancing:
  Shard 0: 600GB (tenant A) ← still large but manageable
  Shard 1: 350GB (tenant B + C + D) ← now better utilized
  Shard 2: 400GB (tenant E) ← unchanged
  Shard 3: 50GB  (tenant F) ← unchanged

  Move tenant A (600GB) from Shard 0 to a new dedicated Shard 4:
  Shard 0 becomes nearly empty (can be decommissioned or filled with new tenants)
  Shard 4: 600GB (tenant A, dedicated)

  Directory-based sharding makes rebalancing straightforward.
  Hash and range sharding make it much harder (key space is fixed).
```

### The Operational Cost of Resharding: An Honest Assessment

Even with careful planning and tooling, resharding is one of the most expensive operational undertakings in database engineering:

```
True Cost of Resharding:

  Engineering time:
  → Planning the resharding strategy: weeks
  → Building and testing the migration scripts: weeks to months
  → Running and monitoring the migration in production: weeks
  → Total: 2–6 months of engineering effort for a large cluster

  Infrastructure cost:
  → Temporary infrastructure for new shards during migration: 1–2× current cost
  → Network bandwidth for data movement: can be terabytes
  → Extended monitoring and on-call during migration window

  Risk:
  → Data loss if migration has bugs (mitigated by shadow mode + verification)
  → Performance impact during migration (replication lag, increased I/O)
  → Bugs in routing logic during the cutover window
  → Operational complexity for weeks or months during the migration

  The honest conclusion:
  The best resharding is the resharding you never have to do.
  Right-size your shard count initially (shard 2× what you need now).
  Use consistent hashing to minimize future movement.
  Use directory-based sharding if per-entity migration flexibility is important.
  Or: use a managed distributed database that handles this for you.
```

## Chapter 9: Sharding in the Real World — Tools and Managed Solutions

### Application-Level Sharding vs. Middleware vs. Managed Databases

There are three broad approaches to implementing sharding, each with different cost, flexibility, and operational complexity trade-offs:

**Application-level sharding:** The application itself contains all routing logic. It knows which shard holds which data and connects directly to the correct shard for each query. This gives maximum flexibility and zero proxy overhead but places the routing complexity inside application code. Every new query must be written with shard awareness. Complex queries (cross-shard) must be explicitly handled. Used by large companies (Uber, Instagram before migrating to Vitess) who need maximum control.

**Middleware / proxy-based sharding:** A transparent proxy (Vitess for MySQL, Citus for PostgreSQL, ProxySQL, pgpool-II) sits between the application and the database servers. The application thinks it is talking to one database; the proxy handles routing, scatter-gather, and result merging. The application is largely shard-unaware. Citus extends PostgreSQL natively (runs in-process as a PostgreSQL extension), making it the most PostgreSQL-native sharding solution.

**Managed distributed databases:** CockroachDB, Google Spanner, Amazon Aurora with sharding, TiDB, and YugabyteDB handle sharding, resharding, replication, and failover automatically. The application uses a standard SQL interface; the database handles distribution internally. Maximum operational simplicity, least control, highest cost.

```
Sharding Implementation Trade-offs:

                   App-Level  │  Middleware  │  Managed DB
  ─────────────────────────────┼──────────────┼────────────────────
  Operational complexity  High │  Medium      │  Low
  Application complexity  High │  Low         │  Very Low
  Flexibility             Max  │  High        │  Limited
  Cost                    Low  │  Medium      │  High (licensing/cloud)
  Resharding              Manual│  Semi-auto  │  Automatic
  Cross-shard queries     Manual│  Handled    │  Handled
  PostgreSQL compatibility Full │  High (Citus)│  Varies
  Best for                Large │  Mid-to-large│  Teams that prefer
                          teams │  teams       │  managed ops
```

## Epilogue: Sharding Is a Last Resort With a Very High Price

Every chapter of this guide has circled back to the same truth: sharding is not a performance upgrade. It is a fundamental architectural transformation that trades the simplicity of a single-database system — with its global transactions, its natural joins, its trivial schema changes, its single backup, its unified monitoring — for the ability to scale writes and storage beyond a single machine.

That trade is worth making when you have genuinely exhausted all other options. When your single primary cannot sustain the write throughput your application demands, and you have already optimized queries, sized hardware correctly, used partitioning for data management, and confirmed that the write bottleneck is fundamental and not just a symptom of poor design — then sharding is the answer.

But it comes with a price that must be paid continuously, not just once at migration time. Every new feature must be written with shard awareness. Every analytical query that crosses shard boundaries is slow. Every schema migration must be applied to N databases instead of one. Every outage investigation now involves N sets of logs. Every backup strategy must cover N independent databases. Every resharding effort is a major engineering project.

The engineers who succeed with sharded systems are not the ones who reached for sharding early — they are the ones who delayed it as long as possible, understood exactly what they were trading away when they finally did it, chose a shard key that their application can live with for years, and built tooling that makes the ongoing cost of the distributed system manageable.

Shard late. Shard thoughtfully. And never forget what it cost.
