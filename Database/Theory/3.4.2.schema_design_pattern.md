# Schema Design Patterns — Volume II: Advanced Patterns

> *"The architecture of a database is like the architecture of a city. You can build a city without a plan — people have done it — but then you spend the next hundred years tearing down buildings and rerouting roads. A little planning at the beginning saves an enormous amount of suffering later."*

This second volume continues our deep study of schema design patterns, turning now to four advanced topics that arise in the most demanding real-world systems. Multi-tenancy patterns govern how you share — or isolate — a database across multiple customers. Hierarchical data patterns solve the ancient problem of representing trees and nested structures in a flat, tabular world. Time-series design tackles the unique challenges of data that arrives as a relentless stream of timestamped events. And event sourcing reimagines the very nature of a database, treating it not as a record of current state, but as an immutable log of everything that has ever happened. Each of these patterns represents a significant architectural commitment, and each deserves to be understood deeply before you adopt it.

## 1. Multi-Tenancy Patterns

### The Core Problem of Serving Many Masters

When you build a Software-as-a-Service (SaaS) application — something like a project management tool, a CRM, or an accounting platform — you are building it for many different customers, not just one. Each customer is called a **tenant**. The word "tenant" is borrowed from real estate: just as multiple families can rent different units in the same apartment building, multiple businesses can be customers of the same software platform. The critical question that every SaaS architect must answer is: *How do we physically store the data for all these different tenants in a way that is isolated, secure, cost-effective, and performant?*

This is the multi-tenancy problem, and it is one of the most consequential architectural decisions you will make. Get it wrong, and you risk catastrophic data leaks between tenants, nightmarish migration costs when a tenant wants to leave, or poor performance as your system scales. The database world has converged on three primary strategies for handling this, each representing a different point on the spectrum between maximum sharing and maximum isolation.

---

### 1.1 Shared Schema (Row-Level Tenancy)

#### The Idea

The most economical and operationally simple approach is to put every tenant's data into the same tables, in the same database schema. The key to keeping tenant data separate is a single column added to every table: `tenant_id`. Every row in every table belongs to exactly one tenant, and this is enforced purely through application logic and careful query filtering.

```
+---------------------------------------------------------------------+
|                    projects  (Shared Table)                          |
+-----+----------+------------------+----------------+----------------+
| id  |tenant_id | name             | status         | created_at     |
+-----+----------+------------------+----------------+----------------+
|  1  |   101    | Website Redesign | active         | 2024-01-15     |
|  2  |   101    | Mobile App       | planning       | 2024-02-01     |
|  3  |   202    | Q4 Campaign      | active         | 2024-01-20     |
|  4  |   202    | Budget Review    | done           | 2024-01-05     |
|  5  |   303    | Onboarding Flow  | active         | 2024-03-10     |
+-----+----------+------------------+----------------+----------------+
     ^
     |
  This single column separates ALL tenants' data.
  Tenant 101 must NEVER see rows belonging to Tenant 202 or 303.

  The query EVERY application query must include:
  SELECT * FROM projects WHERE tenant_id = 101 AND status = 'active';
```

This approach scales beautifully from an infrastructure perspective. You have one database, one set of tables, and one schema to maintain. Adding a new tenant is as simple as inserting a new row into a `tenants` table — no infrastructure changes, no schema migrations, no new databases to provision. Thousands of tenants can coexist in the same database without any extra operational overhead.

#### The Dangers You Must Never Forget

The elegance of this approach conceals a terrifying risk: if any developer writes a query that forgets to include the `WHERE tenant_id = ?` filter, they could accidentally expose Tenant A's data to Tenant B. This is not a hypothetical concern — it is a real, recurring nightmare in SaaS applications, and the consequences (regulatory violations, loss of customer trust, potential lawsuits) are severe.

The mitigation strategy is to enforce tenant isolation at the framework level, not the developer level. Most mature ORM frameworks support **global query scopes** or **row-level security** that automatically appends the `tenant_id` filter to every query for certain models. PostgreSQL, in particular, has a powerful feature called **Row-Level Security (RLS)** that enforces tenant isolation at the database level, making it impossible for any query — no matter what the application code says — to read another tenant's rows.

```sql
-- PostgreSQL Row-Level Security (RLS) — the gold standard for shared schema
-- Step 1: Enable RLS on the table
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;

-- Step 2: Create a policy — each session can only see rows matching its tenant
CREATE POLICY tenant_isolation_policy ON projects
    USING (tenant_id = current_setting('app.current_tenant_id')::INTEGER);

-- Now, if your app sets: SET LOCAL app.current_tenant_id = '101';
-- Then: SELECT * FROM projects;
-- Automatically returns ONLY rows where tenant_id = 101.
-- It is physically impossible to read another tenant's data.
```

This design also makes large tenant migrations harder. If one of your tenants grows so large that they need their own dedicated database, moving them out of the shared schema requires a complex data extraction and migration process.

---

### 1.2 Separate Schemas

#### The Idea

The second approach occupies the middle ground on the isolation spectrum. Here, all tenants share the same physical database server, but each tenant gets their own **database schema** — a named namespace within the database that contains its own private copy of all the tables. In PostgreSQL, schemas are first-class citizens; in MySQL, a "schema" is essentially synonymous with a database, so this model is more commonly applied using separate databases in MySQL.

```
Single Database Server
|
+-- Database: saas_platform
    |
    +-- Schema: tenant_acme              +-- Schema: tenant_globex
    |   +-- projects                     |   +-- projects
    |   +-- tasks                        |   +-- tasks
    |   +-- users                        |   +-- users
    |   +-- invoices                     |   +-- invoices
    |                                    |
    +-- Schema: tenant_initech           +-- Schema: public (shared)
        +-- projects                         +-- tenants
        +-- tasks                            +-- subscription_plans
        +-- users
        +-- invoices

  Each tenant has their OWN copy of every table, with NO shared rows.
  Tenant ACME's projects are in tenant_acme.projects.
  Tenant Globex's projects are in tenant_globex.projects.
  They cannot physically touch each other's tables.
```

This approach provides strong isolation — a bug in the application code that accidentally queries the wrong schema would return no results (or a table-not-found error), not another tenant's data. Backup and restore per-tenant becomes straightforward (just dump and restore one schema). You can also apply different configurations, indexes, or even data retention policies on a per-tenant basis.

#### The Operational Cost

The price of this isolation is **operational complexity**. Every time you onboard a new tenant, you must run a schema creation process — executing all your DDL (CREATE TABLE) statements in the new schema. Every time you deploy a schema migration (adding a column, creating a new index), you must run that migration against every single tenant's schema. If you have 500 tenants, that is 500 separate schema migrations to execute and track. This is manageable with good tooling, but it represents a genuinely significant operational burden that grows linearly with your tenant count.

---

### 1.3 Separate Databases

#### The Idea

The most isolated approach of all is to give each tenant their own completely separate database — their own files on disk, their own connection pool, their own server if needed. This is sometimes called the **Silo Model**. It represents the maximum possible isolation and is typically chosen when tenants have strict data sovereignty requirements, regulatory compliance needs (certain industries require that customer data be physically isolated), or contractual obligations for dedicated infrastructure.

```
+-------------------+   +-------------------+   +-------------------+
|  Database:        |   |  Database:        |   |  Database:        |
|  tenant_acme_db   |   |  tenant_globex_db |   |  tenant_initech_db|
|                   |   |                   |   |                   |
|  projects         |   |  projects         |   |  projects         |
|  tasks            |   |  tasks            |   |  tasks            |
|  users            |   |  users            |   |  users            |
|  invoices         |   |  invoices         |   |  invoices         |
+-------------------+   +-------------------+   +-------------------+
        |                       |                       |
        +----------+------------+                       |
                   |                                    |
         +---------+                                    |
         | App routing layer: maps                      |
         | tenant_id ──► connection string              |
         +----------------------------------------------+

  Your application maintains a routing table:
  ACME    --> postgresql://acme-db.internal/tenant_acme_db
  Globex  --> postgresql://globex-db.internal/tenant_globex_db
```

This model is operationally the most expensive — you are provisioning, monitoring, backing up, and migrating potentially hundreds or thousands of separate databases. However, it also offers benefits that the other models cannot: each tenant can be on a different version of the schema (if you need to stagger migrations), each can be hosted in a different geographic region (for data residency laws), and each can be scaled independently based on that tenant's usage patterns.

---

### 1.4 Comparing the Three Approaches

The choice between these three patterns is not about finding the "best" one in the abstract — it is about understanding your specific constraints around cost, isolation requirements, tenant count, and operational maturity.

```
+-------------------+-------------------+-------------------+-------------------+
| Dimension         | Shared Schema     | Separate Schemas  | Separate Databases|
|                   | (Row-Level)       |                   |                   |
+-------------------+-------------------+-------------------+-------------------+
| Isolation Level   | Low (logical)     | Medium (namespace)| High (physical)   |
+-------------------+-------------------+-------------------+-------------------+
| Data Leak Risk    | High (app bug)    | Low               | Very Low          |
+-------------------+-------------------+-------------------+-------------------+
| Cost (Infra)      | Lowest            | Low-Medium        | Highest           |
+-------------------+-------------------+-------------------+-------------------+
| Onboarding Speed  | Instant (INSERT)  | Seconds (DDL run) | Minutes (new DB)  |
+-------------------+-------------------+-------------------+-------------------+
| Migration Effort  | One migration     | N migrations      | N migrations      |
+-------------------+-------------------+-------------------+-------------------+
| Best For          | Startups, SMBs,   | Mid-market SaaS,  | Enterprise, Gov,  |
|                   | high tenant count | compliance needs  | regulated sectors |
+-------------------+-------------------+-------------------+-------------------+
```

Many mature SaaS companies adopt a **hybrid strategy**: small or free-tier tenants are packed into a shared-schema database for cost efficiency, while large enterprise customers who pay premium prices (and whose contracts demand it) get their own dedicated database. This gives you the operational simplicity of shared-schema at scale while still being able to offer the isolation guarantee that your most important customers require.

## 2. Hierarchical Data Patterns

### The Ancient Problem of Trees in Tables

Relational databases are extraordinarily good at representing flat, tabular data — rows and columns, plain and simple. But the real world is full of **hierarchical structures**: an organization chart where every employee reports to exactly one manager, a file system where every file lives inside exactly one folder, a product category tree where "Electronics" contains "Computers" which contains "Laptops," a comment thread where comments can have replies which themselves can have replies. All of these are **trees** — a universal data structure — and storing them in a relational database has been a subject of creative design for decades.

The fundamental tension is this: a tree is a recursive structure, but a relational table is not. A row in a table cannot "contain" other rows the way a folder contains files. Over time, database practitioners have developed four distinct patterns for representing hierarchical data, each with radically different trade-offs in terms of query complexity, read performance, write performance, and correctness guarantees. We will study all four.

For all examples, we will use the same family tree / organizational hierarchy:

```
                          Alice (CEO)
                         /           \
               Bob (CTO)              Carol (CFO)
              /         \                    \
        Dave (Dev)    Eve (Dev)            Frank (Analyst)
              \
           Grace (Intern)
```

---

### 2.1 Adjacency List

#### The Idea

The Adjacency List is the most natural, intuitive representation of a hierarchy in a relational table. The idea is almost embarrassingly simple: each row stores its own ID and the ID of its **parent**. That is all. If a row is the root of the tree (has no parent), its `parent_id` is NULL.

```
+--------------------------------------------------+
|                  employees  Table                 |
+----+-----------+-----------+--------------------+
| id | name      | parent_id | role               |
+----+-----------+-----------+--------------------+
|  1 | Alice     | NULL      | CEO                |
|  2 | Bob       | 1         | CTO                |
|  3 | Carol     | 1         | CFO                |
|  4 | Dave      | 2         | Developer          |
|  5 | Eve       | 2         | Developer          |
|  6 | Frank     | 3         | Analyst            |
|  7 | Grace     | 4         | Intern             |
+----+-----------+-----------+--------------------+

  Alice (id=1, parent=NULL)  <-- Root
    ├── Bob (id=2, parent=1)
    │     ├── Dave (id=4, parent=2)
    │     │     └── Grace (id=7, parent=4)
    │     └── Eve (id=5, parent=2)
    └── Carol (id=3, parent=1)
          └── Frank (id=6, parent=3)

  parent_id is a self-referencing FOREIGN KEY to the same table (employees.id)
```

This design is immediately understandable, and many common operations are trivially simple. Finding the direct children of Alice requires a single query: `SELECT * FROM employees WHERE parent_id = 1`. Moving a subtree from one parent to another requires a single UPDATE: `UPDATE employees SET parent_id = 3 WHERE id = 2`. Inserting a new node requires a single INSERT.

#### The Fundamental Weakness: Querying Deep Hierarchies

The Achilles' heel of the Adjacency List is retrieving **all descendants** of a node — the entire subtree rooted at that node. Finding Alice's entire organization requires not just her direct reports (a single query), but their direct reports, and their reports, and so on down to arbitrary depth. In traditional SQL, this requires either recursive queries (using the `WITH RECURSIVE` clause, which is supported by PostgreSQL, SQL Server, MySQL 8+, and SQLite) or multiple round-trips to the database from application code.

```sql
-- Finding all descendants of Alice (id=1) using a recursive CTE
WITH RECURSIVE org_tree AS (
    -- Base case: start with the root node
    SELECT id, name, parent_id, role, 0 AS depth
    FROM employees
    WHERE id = 1

    UNION ALL

    -- Recursive case: join each level's children
    SELECT e.id, e.name, e.parent_id, e.role, ot.depth + 1
    FROM employees e
    INNER JOIN org_tree ot ON e.parent_id = ot.id
)
SELECT * FROM org_tree ORDER BY depth;

-- Result:
-- Alice (depth 0), Bob (depth 1), Carol (depth 1),
-- Dave (depth 2), Eve (depth 2), Frank (depth 2), Grace (depth 3)
```

Recursive CTEs work well and are reasonably performant for trees of moderate depth. However, on very deep trees with millions of nodes, recursive queries can become slow. The Adjacency List is the right choice when your hierarchy is **not too deep**, when you frequently need to move nodes between parents, and when recursive CTE support is available in your database.

---

### 2.2 Nested Sets

#### The Idea

The Nested Sets model, introduced by Joe Celko, takes a completely different philosophical approach. Instead of storing parent-child relationships as direct pointers, it encodes the entire tree structure as a set of **numeric intervals**. Each node is assigned two numbers: `lft` (left) and `rgt` (right). The rule is that a node is an **ancestor** of another node if and only if its `lft` is less than the descendant's `lft` and its `rgt` is greater than the descendant's `rgt`. In other words, an ancestor's interval *contains* its descendant's interval.

To understand how the numbers are assigned, imagine walking around the tree, touching each node twice — once on the left side as you go down, and once on the right side as you come back up. The counter value at each touch becomes that node's `lft` or `rgt` value.

```
  Assigning lft/rgt values — imagine a DFS traversal touching each side:

                    Alice
                  /1      14\
              Bob              Carol
            /2    7\          /8    13\
          Dave      Eve    Frank(empty)
        /3    6\  /5  6\   /9   10\
       Grace             (nothing)
       /4   5\

  Wait, let me show the correct numbering clearly:

  Alice:  lft=1,  rgt=14
  Bob:    lft=2,  rgt=9
  Carol:  lft=10, rgt=13
  Dave:   lft=3,  rgt=6
  Eve:    lft=7,  rgt=8
  Frank:  lft=11, rgt=12
  Grace:  lft=4,  rgt=5

+----+-----------+-----+-----+--------------------+
| id | name      | lft | rgt | role               |
+----+-----------+-----+-----+--------------------+
|  1 | Alice     |  1  |  14 | CEO                |
|  2 | Bob       |  2  |   9 | CTO                |
|  3 | Carol     | 10  |  13 | CFO                |
|  4 | Dave      |  3  |   6 | Developer          |
|  5 | Eve       |  7  |   8 | Developer          |
|  6 | Frank     | 11  |  12 | Analyst            |
|  7 | Grace     |  4  |   5 | Intern             |
+----+-----------+-----+-----+--------------------+

Verify the rule: Is Grace a descendant of Bob?
  Bob: lft=2, rgt=9.  Grace: lft=4, rgt=5.
  Is 2 < 4 AND 9 > 5?  Yes! Grace is inside Bob's interval. ✓

Is Frank a descendant of Bob?
  Bob: lft=2, rgt=9.  Frank: lft=11, rgt=12.
  Is 2 < 11 AND 9 > 12?  9 > 12 is FALSE. Frank is NOT under Bob. ✓
```

#### The Power of Nested Sets: Blazing Fast Reads

What makes this model extraordinary is the performance of ancestor and descendant queries. Finding all descendants of Bob requires no recursion whatsoever — it is a simple range query:

```sql
-- All descendants of Bob (lft=2, rgt=9)
SELECT * FROM employees
WHERE lft > 2 AND rgt < 9;
-- Returns Dave, Eve, Grace in a single, highly indexable query.

-- All ancestors of Grace (lft=4, rgt=5)
SELECT * FROM employees
WHERE lft < 4 AND rgt > 5;
-- Returns Alice and Bob — again, no recursion, just a range query.

-- Count of descendants (without even fetching them)
SELECT (rgt - lft - 1) / 2 AS descendant_count
FROM employees WHERE id = 2;  -- Bob: (9 - 2 - 1) / 2 = 3
```

These queries run on indexed numeric columns and are extremely fast even on enormous trees. The Nested Sets model is the performance champion for read-heavy hierarchies where the tree structure rarely changes.

#### The Painful Cost of Writes

The devastating weakness of Nested Sets is that **inserting or moving any node requires renumbering a large portion of the tree**. If you want to add a new employee under Dave, you must update the `lft` and `rgt` values of Dave, Alice, Bob, and every other node whose interval needs to shift to make room. On a large tree, this can mean updating millions of rows just to add one new leaf node. This is why Nested Sets is almost exclusively used for **static or infrequently modified hierarchies** — product category trees, geographic regions, or taxonomies that are loaded once and rarely changed.

### 2.3 Closure Table

#### The Idea

The Closure Table pattern is often considered the most elegant and principled solution to hierarchical data storage. It separates the concerns of *what the data is* from *what its position in the hierarchy is*, storing them in two separate tables. The main table (`employees`) remains beautifully clean, containing only the node's own data, with no structural information at all. A separate `employee_paths` table (the "closure table") records every ancestor-descendant relationship that exists in the tree, including a node's relationship with itself.

```
employees table (just data, no hierarchy columns):
+----+-----------+--------------------+
| id | name      | role               |
+----+-----------+--------------------+
|  1 | Alice     | CEO                |
|  2 | Bob       | CTO                |
|  3 | Carol     | CFO                |
|  4 | Dave      | Developer          |
|  5 | Eve       | Developer          |
|  6 | Frank     | Analyst            |
|  7 | Grace     | Intern             |
+----+-----------+--------------------+

employee_paths table (the Closure Table — ALL ancestor/descendant pairs):
+-----------+------------------+-------+
| ancestor  | descendant       | depth |
+-----------+------------------+-------+
|     1     |        1         |   0   |  <- Alice is ancestor of herself
|     1     |        2         |   1   |  <- Alice -> Bob (1 level)
|     1     |        3         |   1   |  <- Alice -> Carol
|     1     |        4         |   2   |  <- Alice -> Dave (2 levels)
|     1     |        5         |   2   |  <- Alice -> Eve
|     1     |        6         |   2   |  <- Alice -> Frank
|     1     |        7         |   3   |  <- Alice -> Grace (3 levels)
|     2     |        2         |   0   |  <- Bob is ancestor of himself
|     2     |        4         |   1   |  <- Bob -> Dave
|     2     |        5         |   1   |  <- Bob -> Eve
|     2     |        7         |   2   |  <- Bob -> Grace
|     3     |        3         |   0   |
|     3     |        6         |   1   |
|     4     |        4         |   0   |
|     4     |        7         |   1   |  <- Dave -> Grace
|     5     |        5         |   0   |
|     6     |        6         |   0   |
|     7     |        7         |   0   |
+-----------+------------------+-------+

  The closure table contains one row for EVERY (ancestor, descendant) pair.
  Depth=0 rows represent a node's relationship with itself (required!).
```

#### Why the Closure Table Wins on Both Reads and Writes

The beauty of this pattern is that it handles both reads and writes gracefully — far better than either Adjacency List (slow reads for deep trees) or Nested Sets (catastrophically slow writes). Finding all descendants of Bob is a single indexed lookup: `SELECT descendant FROM employee_paths WHERE ancestor = 2 AND depth > 0`. Finding all ancestors of Grace is equally simple: `SELECT ancestor FROM employee_paths WHERE descendant = 7 AND depth > 0`. No recursion. No range queries. Just simple JOIN or lookup operations on a well-indexed table.

Inserting a new node, say "Henry" as a child of Eve (id=5), requires inserting one row into `employees` for Henry's data, and then inserting new rows into `employee_paths` — one row for every ancestor of Eve (including Eve herself), each paired with Henry as the descendant:

```sql
-- Insert Henry as employee
INSERT INTO employees (id, name, role) VALUES (8, 'Henry', 'Intern');

-- Insert closure rows for Henry:
-- For every ancestor of Eve (id=5), add a path to Henry
INSERT INTO employee_paths (ancestor, descendant, depth)
    SELECT ancestor, 8, depth + 1
    FROM employee_paths
    WHERE descendant = 5   -- all ancestors of Eve (including Eve)
UNION ALL
    SELECT 8, 8, 0;        -- Henry is his own ancestor (depth=0 self-reference)
```

The storage cost is the trade-off: the closure table stores O(N²) rows in the worst case (where N is the number of nodes), because a fully connected tree of depth D has many more ancestor-descendant pairs than just N. In practice, for trees that are broad rather than deep, this storage cost is very manageable. The Closure Table is often the best all-around choice when you need both efficient reads and efficient writes on a moderately sized hierarchy.

### 2.4 Materialized Path

#### The Idea

The Materialized Path pattern (also called the **Path Enumeration** pattern) takes inspiration from the way file systems represent paths. Each node stores the complete path from the root down to itself as a string, with node IDs separated by a delimiter character (typically `/`, `.`, or `,`). If you have ever seen a file path like `/home/alice/documents/report.pdf`, you already intuitively understand this model.

```
+----+-----------+---------------------------+--------------------+
| id | name      | path                      | role               |
+----+-----------+---------------------------+--------------------+
|  1 | Alice     | /1/                       | CEO                |
|  2 | Bob       | /1/2/                     | CTO                |
|  3 | Carol     | /1/3/                     | CFO                |
|  4 | Dave      | /1/2/4/                   | Developer          |
|  5 | Eve       | /1/2/5/                   | Developer          |
|  6 | Frank     | /1/3/6/                   | Analyst            |
|  7 | Grace     | /1/2/4/7/                 | Intern             |
+----+-----------+---------------------------+--------------------+

  The depth of any node = (number of slashes in path) - 1
  Alice: depth 0,  Bob: depth 1,  Grace: depth 3

  Finding all descendants of Bob (/1/2/):
  SELECT * FROM employees WHERE path LIKE '/1/2/%';
  --> Returns Dave, Eve, Grace (all paths starting with /1/2/)

  Finding all ancestors of Grace (/1/2/4/7/):
  We know her ancestors are /1/, /1/2/, /1/2/4/
  SELECT * FROM employees WHERE '/1/2/4/7/' LIKE path || '%';
  --> Returns Alice, Bob, Dave
```

The Materialized Path has an appealing simplicity: querying descendants is just a `LIKE` prefix search, which databases can optimize using indexes (especially prefix indexes or full-text indexes). It is also very human-readable — you can see the entire ancestry of a node just by reading its path string. Adding a new node is a simple INSERT that computes the path by appending the new node's ID to its parent's path.

#### The Weaknesses to Keep in Mind

The Materialized Path has several weaknesses worth understanding. The first is that **moving a subtree is expensive** — when you move Bob and all his reports to report to Carol instead of Alice, you must update the `path` column of every single node in Bob's subtree (Bob, Dave, Eve, Grace), changing their prefix from `/1/2/` to `/1/3/2/`. The second weakness is that the path string can become long for deeply nested hierarchies, and `LIKE` queries (though indexable for prefix searches) are generally slower than pure equality lookups. The third issue is that the path column stores redundant information — the ancestry is both encoded in the `parent_id` (if you keep it) and in the path string, creating a potential for inconsistency.

Despite these limitations, the Materialized Path is extremely popular in practice because of its conceptual simplicity and the ease with which humans can read and debug the data. Many popular systems — including nested comment threads, category trees in CMSs, and organizational charts in HR software — use this pattern successfully.

---

### Choosing the Right Hierarchy Pattern

The four patterns we have studied exist on different points of the read-write trade-off spectrum. Understanding this spectrum is the key to choosing wisely.

```
READ PERFORMANCE vs. WRITE COMPLEXITY TRADE-OFF:

WRITES Easy  |  Adjacency List      Materialized Path
             |  (recursive CTE      (LIKE prefix query,
             |   needed for reads)   easy inserts)
             |
             |  Closure Table       Nested Sets
             |  (fast reads AND      (FASTEST reads,
WRITES Hard  |   manageable writes)  TERRIBLE writes)
             +----------------------------------------------
               Reads Harder                   Reads Faster

RECOMMENDED CHOICES:
  - General purpose, moderate depth:  Closure Table
  - Static taxonomies, fast reads:    Nested Sets
  - Simple, shallow hierarchies:      Adjacency List
  - Human-readable paths, CMS trees:  Materialized Path
```

## 3. Time-Series Schema Design

### Data That Never Stands Still

There is a special category of data that is fundamentally different from the records we have discussed so far. In a typical database, you store entities — customers, orders, products — that are relatively stable and change occasionally. But in many domains, you must store measurements that arrive as a **continuous stream** of timestamped values: server CPU usage measured every 10 seconds, a patient's heart rate measured every second, stock prices ticking by the millisecond, IoT sensor readings from thousands of devices, or user click events flowing in from a busy web application. This is **time-series data**, and it has characteristics that make it a fundamentally different design problem.

The defining features of time-series data are: it is **append-only** (you add new measurements, you rarely update old ones), it is **time-ordered** (the timestamp is the primary dimension of interest), it arrives at **high velocity** (potentially millions of writes per second), and it is queried in **time ranges** (you almost always filter by "give me all readings between time X and time Y"). These characteristics call for a schema design that is very different from a typical transactional database.

### The Naive Approach and Its Problems

The most natural instinct when first encountering time-series data is to model it as a simple table with a timestamp column:

```
+-------------------------------------------------------------+
|                     server_metrics  (Naive)                  |
+-----------+----------------------+----------+--------+-------+
| id (BIGINT| timestamp            | server   | cpu_%  | mem_% |
+-----------+----------------------+----------+--------+-------+
| 1         | 2024-01-15 10:00:00  | web-01   | 45.2   | 62.1  |
| 2         | 2024-01-15 10:00:10  | web-01   | 46.8   | 62.3  |
| 3         | 2024-01-15 10:00:00  | web-02   | 23.1   | 41.5  |
| ...       | ...                  | ...      | ...    | ...   |
| 86400000  | ...                  | ...      | ...    | ...   |  <- After 1 day!
+-----------+----------------------+----------+--------+-------+

  At 10-second intervals across 100 servers:
  100 servers × 6 readings/minute × 60 minutes × 24 hours = 864,000 rows/day
  × 365 days = 315,360,000 rows/year
```

This naive design runs into serious trouble at scale. A single table with hundreds of millions of rows is slow to query and catastrophically slow to maintain. Indexes on this table become enormous and slow to insert into. Deleting old data (say, you only want to keep 1 year of data) requires scanning and deleting millions of rows, causing massive index fragmentation and locking issues.

### Core Design Principles for Time-Series Schemas

The first and most powerful technique for managing time-series data at scale is **table partitioning**. Instead of one giant table, you physically divide the data into many smaller tables (partitions) based on time ranges — one partition per day, week, or month. From the application's perspective, you query one table; the database engine transparently routes the query to only the relevant partitions. More importantly, when it is time to purge old data, you simply **DROP** the old partition — an instantaneous operation that does not touch any other data.

```sql
-- PostgreSQL: Partitioned time-series table
CREATE TABLE server_metrics (
    measured_at   TIMESTAMPTZ     NOT NULL,
    server_id     VARCHAR(50)     NOT NULL,
    cpu_percent   NUMERIC(5,2),
    mem_percent   NUMERIC(5,2),
    disk_io_mbps  NUMERIC(8,2)
) PARTITION BY RANGE (measured_at);

-- Create monthly partitions
CREATE TABLE server_metrics_2024_01
    PARTITION OF server_metrics
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE server_metrics_2024_02
    PARTITION OF server_metrics
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Dropping old data = DROP TABLE (instant! no row scanning)
DROP TABLE server_metrics_2023_01;  -- Instantly frees space for all of Jan 2023
```

The second key technique is understanding **what to index** and what not to. In a time-series table, the timestamp is almost always in the primary index. A composite index on `(server_id, measured_at)` is often the right choice because your queries are almost always scoped to both a specific entity (which server?) and a time range (which time period?). Conversely, you should avoid indexing every column — time-series tables write far more than typical tables, and every index you add slows down every write.

### The Schema Pattern for Sensor / Metric Data

A well-designed time-series schema typically follows a pattern of separating the **metadata** about what you are measuring from the **measurements** themselves:

```
+----------------------------+
|       servers  (Metadata)  |
+----------+-----------------+
| id       | hostname        |
+----------+-----------------+
| web-01   | web01.corp.com  |
| web-02   | web02.corp.com  |
| db-01    | db01.corp.com   |
+----------+-----------------+
          |
          | (server_id FK)
          |
+-----------------------------------------------------------------+
|                   server_metrics  (Time-Series Facts)           |
+----------------------+-----------+------------+-----------+-----+
| measured_at          | server_id | cpu_percent| mem_percent| ... |
+----------------------+-----------+------------+-----------+-----+
| 2024-01-15 10:00:00  | web-01    | 45.2       | 62.1       |     |
| 2024-01-15 10:00:10  | web-01    | 46.8       | 62.3       |     |
| 2024-01-15 10:00:00  | web-02    | 23.1       | 41.5       |     |
+----------------------+-----------+------------+-----------+-----+

PRIMARY KEY: (measured_at, server_id)  -- Clustered by time + entity
INDEX: (server_id, measured_at)        -- For "all metrics for server X in window"

PARTITIONED BY RANGE (measured_at):    -- One partition per month
  server_metrics_2024_01
  server_metrics_2024_02
  ...
```

### Continuous Aggregates and Downsampling

A powerful optimization technique for time-series data is **downsampling** — creating pre-aggregated summaries at coarser time resolutions. If users often ask "what was the average CPU usage per hour over the last 30 days?", running that query over 30 × 24 × 6 = 4,320 raw 10-second readings per server is expensive. Instead, you maintain a separate table of **hourly summaries** that pre-computes averages, mins, maxes, and counts:

```
+---------------------------------------------------------------+
|               server_metrics_hourly  (Downsampled)            |
+--------------+----------+---------+---------+---------+-------+
| hour_bucket  | server_id| avg_cpu | max_cpu | min_cpu | count |
+--------------+----------+---------+---------+---------+-------+
| 2024-01-15   | web-01   | 47.3    | 89.1    | 12.4    | 360   |
| 10:00:00     |          |         |         |         |       |
| 2024-01-15   | web-01   | 52.1    | 95.2    | 23.1    | 360   |
| 11:00:00     |          |         |         |         |       |
+--------------+----------+---------+---------+---------+-------+

  Instead of querying 360 raw rows per server-hour,
  you query 1 aggregated row.
  For a 30-day report: 30×24 = 720 rows instead of 259,200 rows.
```

Purpose-built time-series databases like **TimescaleDB** (a PostgreSQL extension), **InfluxDB**, **Prometheus**, and **ClickHouse** automate this entire process with features called "continuous aggregates" or "materialized views" that update incrementally as new data arrives. If your time-series workload is large and performance-critical, these tools are worth serious consideration over a general-purpose relational database.

## 4. Event Sourcing Schema

### Rethinking What a Database Is For

Every pattern we have studied so far has shared a common assumption: the purpose of a database is to store the **current state** of things. A `users` table stores what each user looks like right now. An `orders` table stores each order's present status. Even our soft delete and audit table patterns are fundamentally augmentations of this state-centric model. Event sourcing is a radical departure from this assumption. It says: *what if we stored not the current state, but every event that ever happened? What if the current state was just something we computed from that history?*

This is not as strange as it sounds. Think of a bank account. Your bank does not store your "current balance" as a single number in a database — at least not as the primary source of truth. Instead, it records every transaction: you deposited $500 on Monday, you withdrew $200 on Tuesday, an interest payment of $1.23 posted on Wednesday. The "current balance" is the mathematical sum of all these transactions from the beginning of time. The transaction log is the source of truth; the balance is a computed view of that truth. Event sourcing applies this same principle to your entire application domain.

### The Core Structure of an Event Store

In an event sourcing architecture, the database is called an **event store**. It contains one primary table (or stream) of events — immutable, append-only facts about things that have happened in the system. Each event has a name that describes what happened in the past tense ("OrderPlaced", "OrderShipped", "CustomerAddressUpdated"), the ID of the entity it relates to (the **aggregate**), a sequential version number within that aggregate's history, a timestamp, and a JSON payload containing all the relevant details of that event.

```
+-----------------------------------------------------------------------------------------------+
|                                   events  (The Event Store)                                   |
+------+------------------+-------------------+-------+------------------------+----------------+
| id   | aggregate_type   | aggregate_id      | ver   | event_type             | occurred_at    |
|      |                  |                   |       |                        |                |
+------+------------------+-------------------+-------+------------------------+----------------+
|  1   | Order            | order-abc-123     |  1    | OrderPlaced            | 2024-01-15     |
|      |                  |                   |       |                        | 10:00:00       |
|  2   | Order            | order-abc-123     |  2    | PaymentReceived        | 2024-01-15     |
|      |                  |                   |       |                        | 10:05:32       |
|  3   | Order            | order-abc-123     |  3    | OrderShipped           | 2024-01-16     |
|      |                  |                   |       |                        | 09:14:22       |
|  4   | Customer         | cust-xyz-456      |  1    | CustomerRegistered     | 2024-01-14     |
|      |                  |                   |       |                        | 08:30:00       |
|  5   | Customer         | cust-xyz-456      |  2    | AddressUpdated         | 2024-01-15     |
|      |                  |                   |       |                        | 11:20:00       |
|  6   | Order            | order-abc-123     |  4    | OrderDelivered         | 2024-01-18     |
|      |                  |                   |       |                        | 14:55:00       |
+------+------------------+-------------------+-------+------------------------+----------------+

  payload (JSONB) for event id=1 (OrderPlaced):
  {
    "customer_id": "cust-xyz-456",
    "items": [{"sku": "LAPTOP-001", "qty": 1, "price": 1299.99}],
    "shipping_address": "123 Main St, Springfield",
    "total": 1299.99
  }

  payload for event id=3 (OrderShipped):
  {
    "carrier": "FedEx",
    "tracking_number": "7489283749",
    "estimated_delivery": "2024-01-18"
  }
```

Notice several things about this schema. First, it is **append-only** — you never UPDATE or DELETE rows from the events table. Events are facts that happened in the past, and the past cannot be changed. If a mistake was made, you record a *corrective event* (e.g., "OrderCancelled" or "AddressCorrectionApplied") — you do not erase history. Second, the `version` column is critical for **optimistic concurrency control**: when you load the history of order `order-abc-123`, you see it is at version 4. When you process a new event and try to append it as version 5, the database can check that no other process has already written a version 5 for this aggregate. If they have, you have a conflict and must retry.

### Rebuilding Current State from Events (Replay)

The process of computing the current state of an entity by processing its events in order is called **replaying** or **projecting** the event stream. For each aggregate type, you write a **projection function** (sometimes called a reducer) that takes the current state and an event and returns the new state after applying that event.

```
Replaying Order order-abc-123:

Initial State: {}  (empty)

Apply Event 1 (OrderPlaced):
  State = { id: "order-abc-123", status: "placed", total: 1299.99,
            customer: "cust-xyz-456", items: [...] }

Apply Event 2 (PaymentReceived):
  State = { ..., status: "paid", payment_ref: "pay-001" }

Apply Event 3 (OrderShipped):
  State = { ..., status: "shipped", tracking: "7489283749",
            carrier: "FedEx" }

Apply Event 4 (OrderDelivered):
  State = { ..., status: "delivered", delivered_at: "2024-01-18T14:55:00" }

Final State: { id: "order-abc-123", status: "delivered", ... }
  This is the same as what a traditional database would store directly.
  In event sourcing, it is COMPUTED from the event log.
```

### Snapshots: Avoiding Full Replay Every Time

If an aggregate accumulates thousands of events over its lifetime (imagine a customer account with years of transaction history), replaying all of them every time you need the current state becomes expensive. The solution is the **snapshot** pattern: periodically, you serialize the current computed state of an aggregate and save it alongside the event log. When you next need the state, you load the most recent snapshot and replay only the events that occurred after that snapshot was taken.

```
events table:           snapshots table:
+----+----------+---+   +-----------+----------+---------+-------------------+
| id | agg_id   |ver|   | agg_id    | version  | payload | created_at        |
+----+----------+---+   +-----------+----------+---------+-------------------+
|  1 | order-1  | 1 |   | order-1   |    50    | { ... } | 2024-01-15        |
|... | ...      |...|   +-----------+----------+---------+-------------------+
| 50 | order-1  |50 |
| 51 | order-1  |51 |   To get current state of order-1:
| 52 | order-1  |52 |   1. Load snapshot at version 50  (one row)
| 53 | order-1  |53 |   2. Load events 51, 52, 53 (three rows)
+----+----------+---+   3. Replay events 51-53 on top of snapshot
                        Instead of replaying all 53 events from scratch.
```

### Read Models and the CQRS Connection

A system built on event sourcing almost always pairs with a pattern called **CQRS** (Command Query Responsibility Segregation). The insight is that a raw event log is not easy to query directly. If you want to display "all delivered orders for customer X sorted by date," you cannot efficiently answer that question by scanning the event table — you would need to replay every order's history to find which ones ended up with a "delivered" status.

The solution is to maintain separate **read models** (also called **projections** or **query models**) — purpose-built, denormalized tables that listen to the event stream and update themselves to support specific query patterns. These are separate from the event store and are entirely **disposable**: if you ever need a different view of your data, you can drop the old read model and rebuild it from scratch by replaying the entire event history.

```
EVENT SOURCING ARCHITECTURE OVERVIEW:

  [Command] --> [Aggregate] --> [Append Event to Event Store]
                                         |
                              [Event Store: events table]
                                    (append-only)
                                         |
                    +--------------------+--------------------+
                    |                    |                    |
                    v                    v                    v
          [Order Summary        [Customer Orders       [Analytics
           Read Model]           Read Model]            Read Model]
          (orders_view table)   (cust_orders table)    (metrics table)
                    |
                    v
               [Query / API]
               (fast reads from
                denormalized view)

  Write path:  Commands --> Events  (normalized, immutable)
  Read path:   Queries --> Read Models  (denormalized, queryable)
```

### When Event Sourcing Is Worth It — And When It Is Not

Event sourcing solves genuinely hard problems. It provides a **complete, immutable audit log** for free — you never need to build a separate audit table because the entire history is the database. It enables **temporal queries** by design — you can reconstruct the state of any entity at any point in time by replaying events up to that timestamp. It enables **retroactive features** — if you decide to build a new feature that requires data from the past, you replay the event history with new projection logic and your read model is populated with historical data instantly. It also enables powerful debugging — when a bug occurs in production, you can replay the exact sequence of events that led to it in a test environment.

However, event sourcing comes with significant costs. The system is architecturally complex — maintaining event schemas, managing projections, handling snapshot strategies, implementing CQRS — all of this requires sophisticated engineering. Queries against the raw event store are awkward and require read models for every query pattern. Teams unfamiliar with the pattern face a steep learning curve. And for simple CRUD applications where none of the above benefits apply, event sourcing is heavy machinery brought to solve a light problem.

The honest advice is this: use event sourcing when your domain genuinely requires a complete history of all changes, when business requirements demand the ability to "replay" or audit past states, or when you are building a financial, legal, or compliance-heavy system where immutability is a hard requirement. For most standard business applications, a traditional state-based schema with an audit table is simpler, cheaper to build, and easier to maintain.

## Summary: The Patterns at a Glance

```
+----------------------+---------------------------------------------------+
| PATTERN              | CORE IDEA & BEST USE CASE                         |
+----------------------+---------------------------------------------------+
| Shared Schema        | All tenants in one schema, separated by tenant_id. |
| (Multi-tenancy)      | Best for: high tenant count, cost-conscious SaaS   |
+----------------------+---------------------------------------------------+
| Separate Schemas     | One schema namespace per tenant, same DB server.  |
| (Multi-tenancy)      | Best for: medium isolation needs, mid-market SaaS  |
+----------------------+---------------------------------------------------+
| Separate Databases   | One full database per tenant.                     |
| (Multi-tenancy)      | Best for: enterprise, regulated, data-sovereign    |
+----------------------+---------------------------------------------------+
| Adjacency List       | Each node stores parent_id. Simple, recursive CTE.|
| (Hierarchy)          | Best for: shallow trees, frequent node moves       |
+----------------------+---------------------------------------------------+
| Nested Sets          | lft/rgt intervals encode ancestry. No recursion.  |
| (Hierarchy)          | Best for: read-heavy, rarely-changed taxonomies    |
+----------------------+---------------------------------------------------+
| Closure Table        | Separate table with all ancestor-descendant pairs. |
| (Hierarchy)          | Best for: general purpose, balanced read/write     |
+----------------------+---------------------------------------------------+
| Materialized Path    | Each node stores its full path string (/1/2/4/).  |
| (Hierarchy)          | Best for: human-readable paths, CMS category trees |
+----------------------+---------------------------------------------------+
| Time-Series Schema   | Partitioned by time, downsampled aggregates.       |
|                      | Best for: metrics, IoT, monitoring, analytics      |
+----------------------+---------------------------------------------------+
| Event Sourcing       | Append-only event log; state is computed (replayed)|
|                      | Best for: audit-critical, financial, CQRS systems  |
+----------------------+---------------------------------------------------+
```

The deeper you go into database design, the more you appreciate that every pattern is a negotiation — between simplicity and power, between isolation and cost, between flexibility and performance. The patterns in this volume are not just academic exercises; they are the tools that senior engineers reach for when the standard approaches begin to creak under the weight of real-world requirements. Learning them is not just about memorizing solutions — it is about developing the judgment to recognize which class of problem you are facing, and which tool is sharp enough to cut through it cleanly.
