## 1. Leaderboard — Sorted Sets in Redis + Periodic Sync to PostgreSQL

### 1.1 The Problem — Ranking Things in Real Time

Leaderboards are everywhere in modern software: a gaming platform ranks players by their total score, an e-commerce site ranks products by the number of purchases, a coding challenge platform ranks participants by how many problems they have solved, a food delivery app ranks restaurants by their average rating. The unifying challenge in all of these cases is the same — given a large, constantly changing collection of entities (players, products, restaurants), how do you efficiently answer the question "what is the current rank of entity X?" and "give me the top one hundred entities right now?" in real time, while scores are being updated by thousands of concurrent operations every second?

The naive relational database approach — storing scores in a PostgreSQL table and running `ORDER BY score DESC` to compute rankings on demand — works for small datasets. But the moment you have millions of entities and thousands of score updates per second, this query becomes expensive enough to be impractical. Even with an index on the score column, sorting and paginating tens of millions of rows on every leaderboard request introduces latency that users notice and resent. The leaderboard data structure needs something purpose-built, and Redis provides exactly that in the form of the **sorted set**.

### 1.2 The Redis Sorted Set — A Data Structure Built for Rankings

The Redis **sorted set** (accessed via the `Z` family of commands, hence often called a ZSET) is one of the most ingenious data structures in common use. It maintains a collection of unique members — player names, user IDs, product identifiers — each associated with a floating-point **score**. The members are always kept in sorted order by their score, and this ordering is maintained automatically and atomically on every insert or update. You can add a member, update a score, and query the top N members, or find the rank of a specific member, all in O(log N) time — extraordinarily fast even for sets containing tens of millions of members.

```
Redis Sorted Set — Leaderboard Operations
==========================================

  Leaderboard key: "leaderboard:global"

  Adding/Updating scores:
  ZADD leaderboard:global 9850  "alice"   --> alice  = 9850
  ZADD leaderboard:global 12400 "bob"     --> bob    = 12400
  ZADD leaderboard:global 7100  "carol"   --> carol  = 7100
  ZADD leaderboard:global 15200 "dave"    --> dave   = 15200
  ZADD leaderboard:global 9850  "eve"     --> eve    = 9850

  Internal state (always sorted by score):
  +------+-------+------+
  | Rank | Score | Name |
  +------+-------+------+
  |  1   | 15200 | dave |
  |  2   | 12400 | bob  |
  |  3   |  9850 | alice|  <-- Tied scores are ordered
  |  4   |  9850 | eve  |      lexicographically
  |  5   |  7100 | carol|
  +------+-------+------+

  Key queries:
  ZREVRANK leaderboard:global "alice"
  --> 2  (0-indexed, rank #3 in 1-indexed terms)

  ZREVRANGE leaderboard:global 0 9 WITHSCORES
  --> Top 10 players with their scores

  ZINCRBY leaderboard:global 500 "carol"
  --> carol's score becomes 7600 (atomic increment)
      Sorted set re-orders internally: O(log N)

  ZREVRANGEBYSCORE leaderboard:global +inf 10000
  --> All players with score >= 10000
      (bob and dave in this example)
```

The power of this data structure is the combination of two properties that are ordinarily in tension. First, it provides O(1) rank lookup — you can ask "what is Alice's current rank?" and get an answer in microseconds, regardless of whether there are ten thousand or ten million other players. Second, it provides O(log N) range queries — you can ask "give me the top 100 players" and get a perfectly sorted result without any explicit sort operation, because the data structure keeps everything sorted at all times. For comparison, achieving both of these properties simultaneously in a relational database would require a dense rank window function over a large indexed table — workable, but nowhere near as fast.

### 1.3 The Periodic Sync to PostgreSQL — Durability and History

Redis is fast, but it is primarily an in-memory store. While Redis supports persistence mechanisms (RDB snapshots and AOF logging), treating Redis as the sole source of truth for leaderboard data introduces durability risk — if the Redis instance fails before its in-memory state is persisted, score data could be lost. More importantly, PostgreSQL provides capabilities that Redis cannot: complex analytical queries, historical records, joins with other tables (such as associating a player's score with their account details, subscription tier, or geographic region), and long-term archival.

The architectural pattern, therefore, is a two-tier system. Redis is the **live, operational layer** — it holds the current state of the leaderboard and handles all real-time updates and reads with microsecond latency. PostgreSQL is the **durable, historical layer** — it holds authoritative records of scores, is the system of record for audit and compliance purposes, and powers the complex analytics queries that the leaderboard itself does not need but the business does.

```
Leaderboard — Two-Tier Architecture
======================================

  Score Update Events (thousands/second):
  Game Server --> ZINCRBY leaderboard:global 100 "alice"
  Game Server --> ZINCRBY leaderboard:global 250 "bob"
  ...
  (All updates go to Redis instantly. PostgreSQL is NOT touched.)

  Real-time reads:
  App --> ZREVRANGE leaderboard:global 0 99 WITHSCORES
  --> Top 100 returned in < 1ms. PostgreSQL NOT involved.

  Periodic Sync Job (every 60 seconds):
  +----------------------------------------------------+
  |  Sync Worker                                       |
  |  1. ZRANGE leaderboard:global 0 -1 WITHSCORES     |
  |     (fetch ALL members with scores from Redis)     |
  |                                                    |
  |  2. Batch upsert to PostgreSQL:                    |
  |     INSERT INTO leaderboard_scores                 |
  |       (user_id, score, recorded_at)               |
  |     VALUES ($1, $2, NOW()), ($3, $4, NOW()), ...   |
  |     ON CONFLICT (user_id)                          |
  |     DO UPDATE SET score = EXCLUDED.score,          |
  |                   recorded_at = NOW();             |
  |                                                    |
  |  3. Also insert into leaderboard_history:          |
  |     (snapshot for time-series analysis)            |
  +----------------------------------------------------+

  PostgreSQL powers:
  - Historical rank tracking ("was Alice ever rank #1?")
  - Cross-table analytics ("top players by country")
  - Long-term score trends and reporting
  - Data recovery if Redis is lost

  +--------------------+     +---------------------+
  |      Redis         |     |     PostgreSQL       |
  | leaderboard:global |     | leaderboard_scores   |
  |                    |     | leaderboard_history  |
  | Real-time scores   |     | Durable archive      |
  | Rank in <1ms       |     | Analytics & joins    |
  | In-memory speed    |     | ACID guarantees      |
  +--------------------+     +---------------------+
         ^  Live read/write          ^ Periodic sync
         |                          |
         +----------+---------------+
                    |
              Application
```

### 1.4 Sharding the Leaderboard — Handling Global Scale

A single Redis sorted set can comfortably hold tens of millions of members and still perform at microsecond speed. For the vast majority of leaderboard use cases, a single sorted set per leaderboard is entirely sufficient. However, there are scenarios — very large gaming platforms, global financial markets, massive multiplayer games — where even the Redis throughput limit on a single key becomes a bottleneck.

When a single key receives so many concurrent `ZINCRBY` operations that the Redis server's CPU becomes the limiting factor (typically above a few hundred thousand operations per second on a single key), **leaderboard sharding** becomes necessary. The leaderboard is split into N shards: `leaderboard:shard:0`, `leaderboard:shard:1`, ..., `leaderboard:shard:N-1`. Each user is assigned to a shard by a hash of their user ID. Score updates go to that user's assigned shard, distributing the write load across N Redis keys (potentially on N different Redis nodes). Reading the global top 100 requires reading the top 100 from each shard and merging the results — a merge of N sorted lists, which is a well-understood algorithmic problem solvable in O(N * 100) time.

Another common pattern is maintaining **tiered leaderboards**: a global leaderboard, regional leaderboards (top players in North America, top players in Europe), and friend-group leaderboards ("your rank among your friends"). Each tier is a separate sorted set. Updating a score means updating all relevant sorted sets for that user — a small write amplification factor that is entirely manageable and provides a dramatically richer user experience.

## 2. Job / Task Queue — SKIP LOCKED in PostgreSQL or Redis Streams

### 2.1 The Problem — Processing Work Asynchronously

Nearly every non-trivial application has work that should not be done synchronously during an HTTP request. When a user registers, you want to send them a welcome email — but the user should not have to wait for the email delivery network to respond before they receive the "registration successful" page. When an order is placed, you want to generate a PDF invoice, update inventory counts, and notify the warehouse — but the customer should receive their order confirmation immediately, not after all of those downstream operations complete. When a video is uploaded to a streaming platform, transcoding it into multiple resolutions and bitrates could take minutes or hours — you cannot hold the HTTP request open for that duration.

The architectural solution is a **job queue** (also called a task queue or work queue). Instead of performing work immediately in the request handler, the handler creates a job record — a description of the work to be done, with all the necessary parameters — and places it in a queue. The HTTP response is returned immediately. One or more **worker processes** run in the background, continuously pulling jobs from the queue and executing them. The user experiences a snappy, immediate response, and the actual work happens asynchronously behind the scenes.

```
Job Queue — The Core Flow
===========================

  WITHOUT a job queue (synchronous, blocking):
  +----------+    +----------+    +----------+    +----------+
  |  User    |    |   API    |    |  Email   |    |   PDF    |
  |  clicks  |    | Handler  |    | Service  |    | Generator|
  +----+-----+    +----+-----+    +----+-----+    +----+-----+
       |               |               |               |
       |---POST /order>|               |               |
       |               |---send email>-|               |
       |               |               |   (3 seconds) |
       |               |<-email sent---|               |
       |               |--gen PDF-------------------->-|
       |               |                   (8 seconds) |
       |               |<-PDF done---------------------|
       |<-200 OK-------|
       |  (11 seconds later! Bad UX)

  WITH a job queue (async, non-blocking):
  +----------+    +----------+    +----------+    +----------+
  |  User    |    |   API    |    |   Queue  |    | Workers  |
  +----+-----+    +----+-----+    +----+-----+    +----+-----+
       |               |               |               |
       |---POST /order>|               |               |
       |               |--enqueue jobs>|               |
       |               |  (instant)    |               |
       |<-200 OK-------|               |               |
       | (< 50ms!)     .               |<--pull job----|
                       .               |<--pull job----|
                       .   (background)|   (workers process
                                       |    asynchronously)
```

### 2.2 PostgreSQL as a Job Queue — The SKIP LOCKED Approach

Many engineers reaching for a job queue immediately think of dedicated messaging systems like RabbitMQ, Kafka, or Sidekiq with Redis. These are excellent tools. But for a large number of use cases, the database you already have — PostgreSQL — is perfectly capable of serving as a reliable, transactional job queue, without introducing the operational complexity of an additional system. This approach is so well-established that it has libraries built around it (such as `pgqueue` in Go, `good_job` in Ruby on Rails, and `pg-boss` in Node.js).

The key insight is simple: a job queue is, at its heart, just a table with a `status` column. Workers query the table for `pending` jobs, claim one, execute it, and mark it `completed`. The challenge is making this claim step safe under concurrency — if ten workers are all trying to claim jobs simultaneously, you need to ensure that each job is claimed by exactly one worker, not multiple. In traditional SQL, this would require careful use of transactions and row locks, but a naive implementation creates a problem: when Worker A locks a row to claim a job, Workers B through J are blocked waiting for that lock, even though there are nine other unclaimed jobs they could be working on.

This is precisely the problem that PostgreSQL's `SKIP LOCKED` clause solves. When a worker queries for the next pending job using `SELECT ... FOR UPDATE SKIP LOCKED`, PostgreSQL will skip over any rows that are currently locked by another transaction and return the first row that is free to lock. Each worker immediately gets its own job without waiting for other workers, and no two workers ever claim the same job.

```
PostgreSQL Job Queue — Schema and SKIP LOCKED
==============================================

  Table: jobs
  +--------------+----------------------+-----------------------------+
  | Column       | Type                 | Description                 |
  +--------------+----------------------+-----------------------------+
  | id           | BIGSERIAL PK         | Job identifier              |
  | job_type     | VARCHAR(100)         | "send_email", "gen_pdf" etc.|
  | payload      | JSONB                | All parameters for the job  |
  | status       | VARCHAR(20)          | pending/running/done/failed |
  | priority     | INTEGER DEFAULT 0    | Higher = processed first    |
  | attempts     | INTEGER DEFAULT 0    | How many times tried        |
  | max_attempts | INTEGER DEFAULT 3    | Give up after N failures    |
  | run_at       | TIMESTAMPTZ          | Not before this time        |
  | created_at   | TIMESTAMPTZ          | When job was enqueued       |
  | locked_at    | TIMESTAMPTZ NULL     | When a worker claimed it    |
  | locked_by    | VARCHAR(100) NULL    | Which worker claimed it     |
  | error        | TEXT NULL            | Last error message          |
  +--------------+----------------------+-----------------------------+

  Index: ON (status, priority DESC, run_at ASC)
  (Allows workers to efficiently find the next job to run)


  Worker claims a job (atomic, concurrency-safe):
  --------------------------------------------------
  BEGIN;

  SELECT id, job_type, payload
  FROM jobs
  WHERE status = 'pending'
    AND run_at <= NOW()
  ORDER BY priority DESC, run_at ASC
  LIMIT 1
  FOR UPDATE SKIP LOCKED;   -- <-- The magic clause

  -- If a row is returned, claim it:
  UPDATE jobs
  SET status    = 'running',
      locked_at = NOW(),
      locked_by = 'worker-pod-7',
      attempts  = attempts + 1
  WHERE id = <returned_id>;

  COMMIT;

  -- Now the worker processes the job outside the transaction.
  -- On success:
  UPDATE jobs SET status = 'completed' WHERE id = <id>;
  -- On failure:
  UPDATE jobs SET status = 'failed', error = '...' WHERE id = <id>;


  How SKIP LOCKED enables concurrency:
  Jobs table:  [job:1 LOCKED] [job:2] [job:3] [job:4]
  Worker A:     claimed job:1 (locked it)
  Worker B:     sees job:1 locked, SKIPS IT, claims job:2
  Worker C:     sees job:1 and job:2 locked, SKIPS BOTH, claims job:3
  Worker D:     claims job:4
  All workers active simultaneously. No blocking. No contention.
```

The tremendous advantage of the PostgreSQL job queue approach is **transactional enqueueing**. Because the job is inserted into the database within the same transaction as the business operation that generates it, either both the operation and the job succeed together, or neither does. If a user places an order and the transaction commits, the send-invoice job is guaranteed to exist in the queue. If the transaction rolls back (for any reason), the job is also rolled back — you will never have a situation where the order was not actually placed but the invoice-sending job is in the queue, or where the order was placed but no job was created. This atomic coupling between the work and the trigger is a property that external message queues (like RabbitMQ or Kafka) require significant additional engineering to replicate.

### 2.3 Handling Failures and Retries

A production job queue must be designed around the assumption that jobs will fail. Network calls time out. External services go down. Unexpected data triggers edge cases in code. A robust job queue treats failures as first-class events rather than exceptional accidents.

The standard approach is **exponential backoff with a maximum retry count**. When a job fails, instead of immediately retrying (which might worsen an overload condition on a downstream service), the system schedules the retry at an increasing delay: first retry after 30 seconds, second retry after 2 minutes, third retry after 10 minutes, and so on. This is implemented by updating the `run_at` column to a future timestamp when marking a job as failed. The worker query's `WHERE run_at <= NOW()` clause naturally excludes these delayed retries until their time comes.

After `max_attempts` failures, the job is moved to a `dead` status (sometimes called a dead-letter state). Dead jobs are never automatically retried; they require manual investigation and intervention. A monitoring dashboard that tracks the count of dead jobs is an essential operational tool — a sudden spike in dead jobs is a reliable early warning signal of a downstream service failure or a code bug affecting a specific job type.

### 2.4 Redis Streams — A Modern Alternative for High-Throughput Queues

While the PostgreSQL job queue excels at transactional correctness and simplicity for moderate workloads (tens of thousands of jobs per day), there are scenarios where the volume of jobs is so high — hundreds of thousands or millions per day — that the PostgreSQL approach struggles. Every job enqueue is a database write, every job claim is a database read and write, and every job completion is another database write. At very high throughput, this creates substantial database write pressure and contention on the jobs table.

**Redis Streams**, introduced in Redis 5.0, provide a purpose-built, high-throughput message stream data structure that is well-suited for high-volume job queues. A Redis Stream is a persistent, append-only log of messages, similar conceptually to Apache Kafka but living inside Redis and therefore benefiting from Redis's extreme speed. Streams support **consumer groups** — a feature that allows multiple worker processes to consume from the same stream, with Redis tracking which messages each consumer has acknowledged, ensuring that each message is processed by exactly one consumer and that unacknowledged messages can be re-delivered after a timeout.

```
Redis Streams — Job Queue Architecture
========================================

  Producers (API servers enqueue jobs):
  XADD jobs:email * type "send_welcome" user_id 123 template "welcome"
  XADD jobs:email * type "send_invoice" order_id 456 amount 99.99
  XADD jobs:pdf   * type "gen_invoice" order_id 456
  ...
  (Each XADD appends a message to the stream with a unique ID)

  Stream state:
  jobs:email stream:
  1694500001000-0: {type:"send_welcome", user_id:123, ...}
  1694500002000-0: {type:"send_invoice", order_id:456, ...}
  1694500003000-0: {type:"send_reset",   user_id:789, ...}

  Consumer Group "email-workers":
  (Tracks which messages have been acknowledged by workers)

  Worker claims a message:
  XREADGROUP GROUP email-workers worker-1
    COUNT 1 BLOCK 5000 STREAMS jobs:email >
  --> Returns next undelivered message (the ">" means undelivered)
  --> Message is now "pending" for worker-1

  Worker processes the job, then acknowledges:
  XACK jobs:email email-workers 1694500001000-0
  --> Message removed from pending list. Never re-delivered.

  If worker crashes without ACKing:
  After a timeout, XAUTOCLAIM can reassign the message
  to another worker, ensuring no job is lost.

  Redis Streams vs PostgreSQL SKIP LOCKED:
  +------------------------+---------------------------+
  | Redis Streams          | PostgreSQL SKIP LOCKED    |
  +------------------------+---------------------------+
  | ~1M msgs/sec/node      | ~10K jobs/sec (typical)   |
  | Sub-millisecond latency| ~5ms per job cycle        |
  | Not transactional      | Fully transactional       |
  | Separate from DB       | Same DB, no extra infra   |
  | Good for high volume   | Good for moderate volume  |
  | Fire-and-forget style  | Atomic with business ops  |
  +------------------------+---------------------------+
```

The choice between PostgreSQL SKIP LOCKED and Redis Streams is ultimately a choice between transactional correctness and raw throughput. If your jobs are tightly coupled to database transactions and you cannot afford to lose a single job even in the event of a system crash, PostgreSQL SKIP LOCKED is the safer choice. If you are processing enormous volumes of lightweight jobs — sending push notifications, logging analytics events, processing sensor readings — where losing an occasional message is acceptable and maximum throughput is the priority, Redis Streams is the better tool.

Many mature systems use both: PostgreSQL SKIP LOCKED for critical, transactional jobs (financial operations, account changes) and Redis Streams for high-volume, fault-tolerant background tasks (notifications, event processing, cache warming). The two systems coexist, each doing what it does best.

## 3. Session Store — Redis with TTL

### 3.1 The Problem — Remembering Who You Are

Every web application faces the fundamental challenge of HTTP's statelessness. The HTTP protocol, by design, treats every request as an independent event with no memory of previous requests. From the server's perspective, the request "give me Alice's account settings" carries no inherent indication that it comes from Alice rather than any other user — unless the request includes some form of credential or identifier that the server can verify.

The traditional solution to this statelessness problem is the **session**. When a user successfully authenticates (by providing a correct username and password), the server creates a session — a temporary record that says "this browser, identified by this token, belongs to Alice and was authenticated at this time." The session token is sent to the browser as a cookie. On every subsequent request, the browser sends that cookie back to the server, and the server looks up the session to determine who is making the request, without requiring the user to re-enter their credentials on every page load.

The question of where to store session data is not trivial. Sessions must be readable on every single authenticated request — potentially millions of times per second across a high-traffic application. They must be retrievable in milliseconds. They must expire automatically after a period of inactivity. And they must be accessible from any application server (since a load balancer might route different requests from the same user to different servers). These requirements point unmistakably toward Redis.

### 3.2 Redis as a Session Store — The Natural Fit

Redis is the overwhelmingly dominant choice for session storage in modern web applications, and the reasons are tightly connected to Redis's fundamental properties. Every session lookup is a key-value read: "given this session token, return the session data." Redis is, at its core, a key-value store with microsecond-level read latency — this is precisely the operation it was designed to excel at. A single Redis node can handle hundreds of thousands of session reads per second, dwarfing what a relational database could provide for the same operation with its heavier parsing and indexing overhead.

The TTL (Time-To-Live) feature of Redis is the other critical ingredient. Sessions should expire after a period of inactivity — both for security (preventing sessions from remaining valid indefinitely after a user walks away from their computer) and for memory management (preventing the session store from accumulating stale sessions for users who never explicitly logged out). Redis's native TTL support means that session expiration is entirely handled by the infrastructure: you store the session, set a TTL, and Redis automatically evicts it after the specified duration. No cleanup jobs, no scheduled queries, no garbage collection logic in application code.

```
Redis Session Store — Complete Flow
======================================

  Step 1: User logs in
  +----------+     +----------+     +----------+
  |  Browser |     |   API    |     |  Redis   |
  +----+-----+     +----+-----+     +----+-----+
       |                |                |
       |--POST /login-->|                |
       |   (user+pass)  |                |
       |                |  Verify creds  |
       |                |  in PostgreSQL |
       |                |                |
       |                | Generate token:|
       |                | "sess_7f3a9b..."
       |                |                |
       |                |--SETEX sess_7f3a9b... 86400 { -->|
       |                |  user_id: 123,                   |
       |                |  email: "alice@example.com",     |
       |                |  roles: ["user"],                |
       |                |  created_at: "2024-01-01...",    |
       |                |  last_seen: "2024-01-01..."      |
       |                | }                               |
       |                |<-- OK --------------------------|
       |                |                |
       |<--Set-Cookie---|                |
       |  session=sess_7f3a9b...        |
       |  (HttpOnly, Secure, SameSite)  |


  Step 2: Every subsequent authenticated request
  +----------+     +----------+     +----------+
  |  Browser |     |   API    |     |  Redis   |
  +----+-----+     +----+-----+     +----+-----+
       |                |                |
       |--GET /dashboard|                |
       |  Cookie: sess_7f3a9b...--->|   |
       |                |                |
       |                |--GET sess_7f3a9b... -->|
       |                |                |
       |                |<-- {user_id:123, email:..., roles:[...]}-|
       |                |                |
       |                |  Refresh TTL:  |
       |                |--EXPIRE sess_7f3a9b... 86400 -->|
       |                |  (sliding window TTL)           |
       |                |                |
       |                | Load dashboard data             |
       |                | for user_id 123 from PostgreSQL |
       |                |                |
       |<--200 OK + HTML|                |


  Step 3: User logs out
  +----------+     +----------+     +----------+
  |  Browser |     |   API    |     |  Redis   |
  +----+-----+     +----+-----+     +----+-----+
       |                |                |
       |--POST /logout->|                |
       |  Cookie: sess_7f3a9b...        |
       |                |--DEL sess_7f3a9b... -->|
       |                |                |
       |                |<-- OK ---------|
       |                |  (session is now gone,
       |                |   token is worthless)
       |<--Clear Cookie-|
```

### 3.3 Designing the Session Data — What to Store

The session object in Redis should contain exactly what the application needs to know about the user on every request, without requiring a database query. If the application needs to know the user's ID, email, display name, roles, and subscription tier on every page load, all of those fields should be in the session. If loading these fields requires a database query on every request — because they are not in the session — you have not fully realized the performance benefit of the session cache.

However, the session should not become a dumping ground for all user data. There is a practical size limit to consider: a Redis session is typically stored as a serialized JSON string, and every authenticated request fetches the entire session. If the session contains a user's full profile, all their preferences, and their entire permission set, the session object might grow to dozens of kilobytes. Fetching dozens of kilobytes from Redis on every request, deserializing it, and passing it through your application is not as trivially cheap as it might seem at high request rates. The guiding principle is to store in the session only what is needed for the authorization decision and basic personalization on every request, and to fetch additional user details from the database or a separate cache only when they are actually needed.

```
Session Data — What to Include
================================

  Minimal, Efficient Session Payload (~200 bytes):
  {
    "user_id":    123,
    "email":      "alice@example.com",
    "display_name": "Alice Smith",
    "roles":      ["user", "editor"],
    "tier":       "premium",
    "created_at": "2024-01-15T10:00:00Z",
    "last_seen":  "2024-01-15T14:23:00Z"
  }
  --> Available on every request without a DB query.
  --> Powers authorization ("is this user a premium member?")
  --> Powers basic personalization ("Hello, Alice!")

  What NOT to put in the session:
  - Full user profile (bio, avatar URL, contact info)  <- Fetch from cache
  - User's activity history                            <- Fetch from DB
  - Large preference objects                           <- Fetch on demand
  - Any data that changes frequently                   <- Stale data risk

  Session size guidelines:
  - Under 1KB:   Excellent. Negligible bandwidth cost.
  - 1-10KB:      Acceptable for most applications.
  - Over 10KB:   Reconsider what you are storing.
```

### 3.4 Sliding Window Expiration — Keeping Active Sessions Alive

There are two philosophically different approaches to session TTL management: **absolute expiration** and **sliding window expiration**. Understanding the difference is important for designing the right user experience.

In absolute expiration, the session is given a TTL at creation time and that TTL is never extended. If you set a 24-hour TTL, the session expires exactly 24 hours after it was created, even if the user has been actively using the application for the entire 24 hours. This is simple and predictable, but it creates an infuriating user experience where a user who has been actively working in an application for 23 hours and 59 minutes is suddenly logged out and loses their unsaved work.

In sliding window expiration, the TTL is refreshed on every request. When the user makes a request, the application calls Redis `EXPIRE sess_{token} 86400` (or uses `SETEX` to re-store with the new TTL), resetting the countdown from the moment of the most recent activity. A session expires only if the user has been genuinely inactive for the TTL duration. This matches the user's intuition: "I should be logged out if I close my laptop and come back a day later, but not if I am actively using the application." Sliding window expiration is the industry standard for general-purpose web application sessions.

### 3.5 Security Considerations — Sessions as Credentials

A session token stored in a cookie is, functionally, a credential. Anyone who possesses a valid session token can make requests as the user it belongs to. This makes session tokens high-value targets for attackers, and the security of the session store and session token design requires careful attention.

Session tokens must be **cryptographically random** and long enough to be unguessable. A 128-bit or 256-bit token generated by a cryptographically secure random number generator is standard practice. Sequential or predictable session IDs (like `session_1`, `session_2`) are trivially guessable and represent a severe security vulnerability. The token should be sent to the browser with the `HttpOnly` attribute (preventing JavaScript from reading it, which defeats cross-site scripting attacks that try to steal cookies), the `Secure` attribute (ensuring it is only sent over HTTPS connections), and an appropriate `SameSite` policy (protecting against cross-site request forgery).

When a user changes their password, or when a security team detects a compromised account, the ability to **immediately invalidate all sessions for a specific user** is a critical capability. With Redis, this is straightforward: store sessions using a key naming convention that includes the user ID — such as `sess:{user_id}:{token}` — and use Redis's key scanning or a secondary set that tracks all session keys for a given user. When you need to log Alice out of all her devices simultaneously, you delete all keys matching `sess:123:*`. This is far more powerful than token-based authentication schemes where invalidation requires maintaining a blocklist.

```
Session Security Architecture
================================

  Token Generation (must be cryptographically random):
  token = crypto.RandomBytes(32).hex()
  --> "7f3a9b2c8d1e4f6a0b5c9d3e7f2a1b4c..."
  --> 64 hex chars = 256 bits of entropy
  --> Probability of guessing: 1 in 2^256 (effectively zero)

  Cookie security flags:
  Set-Cookie: session=7f3a9b...; HttpOnly; Secure; SameSite=Strict;
              Path=/; Max-Age=86400

  HttpOnly  --> JavaScript cannot read cookie (XSS protection)
  Secure    --> Only sent over HTTPS (no plaintext interception)
  SameSite  --> Cookie not sent on cross-site requests (CSRF protection)

  Key structure for bulk invalidation:
  Redis key: "sess:{user_id}:{token}"
  e.g.:      "sess:123:7f3a9b..."

  User's active sessions tracked in a Redis Set:
  Key: "user_sessions:123"
  Members: ["7f3a9b...", "2c4e1f...", "9a8b7c..."]
  (Alice logged in from laptop, phone, and tablet)

  Invalidate all sessions (e.g., password change):
  1. SMEMBERS user_sessions:123
     --> ["7f3a9b...", "2c4e1f...", "9a8b7c..."]
  2. DEL sess:123:7f3a9b...
     DEL sess:123:2c4e1f...
     DEL sess:123:9a8b7c...
  3. DEL user_sessions:123
  --> Alice is now logged out from all devices instantly.

  Session rotation (preventing fixation attacks):
  On successful login, always generate a NEW session token.
  Never reuse or accept tokens from the pre-login state.
```

### 3.6 Scaling the Session Store — Redis Cluster for High Availability

For applications at significant scale, a single Redis instance handling all session data introduces a single point of failure: if that Redis instance goes down, every authenticated user in the application is effectively logged out simultaneously, because their session tokens can no longer be validated. This is a severe and visible outage.

The solution is to run Redis in a **cluster or replicated configuration**. With Redis Sentinel (for simpler deployments), a primary Redis instance is continuously monitored by a set of Sentinel processes. If the primary fails, Sentinel automatically promotes a replica to become the new primary and reconfigures all clients to use the new primary. From the application's perspective, there is a brief interruption (typically a few seconds during the failover) but then automatic recovery. Sessions that were stored on the primary before the failure are available on the replica, because replicas continuously mirror the primary's state.

For very large applications, Redis Cluster distributes session data across multiple primary nodes. Each session key is hashed to one of 16,384 hash slots, and each node in the cluster is responsible for a subset of those slots. Sessions for different users are distributed across different nodes, so no single node holds all sessions, and the load is naturally balanced. This allows the session store to scale horizontally — adding more nodes to the cluster increases both the total capacity and the total throughput — while maintaining the sub-millisecond latency that makes Redis so effective as a session store.

```
Redis High Availability for Sessions
=======================================

  Redis Sentinel (simple, automatic failover):

  +----------+    replicates to    +----------+
  | Primary  |-------------------> | Replica 1|
  | (all     |-------------------> | Replica 2|
  |  writes) |                     +----------+
  +----------+
       |
       | Sentinel monitors primary health
       v
  +-----------+
  |  Sentinel |  If primary fails:
  |  Cluster  |  1. Detect failure
  |  (3 nodes)|  2. Elect new primary from replicas
  +-----------+  3. Redirect all clients to new primary
                 4. Old primary joins as replica on recovery

  Redis Cluster (distributed, for large scale):

  16,384 hash slots distributed across nodes:

  +----------+   Slots 0-5460     +----------+   Slots 5461-10921
  | Primary A|                    | Primary B|
  | + replica|                    | + replica|
  +----------+                    +----------+

                    Slots 10922-16383
                    +----------+
                    | Primary C|
                    | + replica|
                    +----------+

  sess:123:7f3a... --> hash slot 4821 --> routed to Primary A
  sess:456:2c4e... --> hash slot 9103 --> routed to Primary B
  sess:789:9a8b... --> hash slot 14200--> routed to Primary C

  Each user's session lives on exactly one node.
  Failure of one node only affects ~1/3 of sessions.
  Other sessions continue uninterrupted.
```

## Summary

The three patterns examined in this document each represent a domain where Redis's specific capabilities — sorted sets, streams, key-value storage with TTL — provide solutions that are fundamentally better suited to the problem than what a general-purpose relational database can offer.

The leaderboard pattern demonstrates the power of purpose-built data structures. The Redis sorted set's ability to maintain a perfectly ranked ordering of millions of members, with O(log N) updates and O(1) rank lookups, makes it not just faster than a SQL-based approach but architecturally simpler and more natural. The periodic sync to PostgreSQL completes the design by providing durability, historical tracking, and analytical capability that Redis alone cannot offer.

The job queue pattern reveals the tension between two values — transactional safety and raw throughput — and shows how different tools resolve that tension differently. PostgreSQL's SKIP LOCKED approach offers the strongest possible correctness guarantee (the job cannot be lost because it lives in the same ACID transaction as the work that created it) at the cost of moderate throughput. Redis Streams offers extraordinary throughput at the cost of weaker delivery guarantees. The wise architect chooses based on the criticality of the work being queued, not on habit or fashion.

The session store pattern illuminates the cascade of requirements that flows from a seemingly simple problem. Storing session data in Redis is not just a performance optimization — it is also the foundation for sliding window expiration, bulk session invalidation, distributed session access across load-balanced servers, and the high-availability infrastructure that ensures users stay logged in even when individual Redis nodes fail. Every design decision in the session store, from the key naming convention to the cookie security flags to the cluster topology, serves the ultimate goal of making authentication feel invisible and instant to the user while remaining secure and resilient to failure.
