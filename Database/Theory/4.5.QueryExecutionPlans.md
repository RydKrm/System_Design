# Query Execution Plans — A Deep Study Guide

> *"Reading a query execution plan is like reading an X-ray. To the untrained eye, it is a collection of strange labels and numbers that conveys nothing. To the practitioner who understands what they are looking at, it is a precise, complete description of what the database engine is doing on your behalf — every step, every cost, every decision. Learning to read execution plans is learning to see inside the database, and once you can see, you can heal."*

When you submit a SQL query to a relational database, you are not issuing a command — you are asking a question. The database's job is to figure out the best possible *method* for answering that question given the data it has, the indexes available, and the hardware resources at its disposal. This decision-making process is carried out by the **query planner** (also called the query optimizer), and the result of its deliberations is an **execution plan**: a tree of operations that describes, step by step, exactly how the database intends to execute your query.

The execution plan is the single most important diagnostic tool in database performance tuning. Every slow query has a story, and the execution plan is how that story is told. Without the ability to read and interpret execution plans, you are debugging performance problems blindfolded — guessing at causes, applying random fixes, and hoping for improvement. With that ability, you can see exactly what the database is doing, understand precisely why it is doing it, and make informed changes that target the actual bottleneck. This chapter teaches you everything you need to read that story fluently.

## 1. EXPLAIN and EXPLAIN ANALYZE

### The Two Levels of Query Introspection

PostgreSQL provides two closely related commands for examining query execution: `EXPLAIN` and `EXPLAIN ANALYZE`. Understanding the difference between them is the starting point for all query plan analysis.

`EXPLAIN` alone asks the query planner to produce its execution plan and show you the *estimated* costs and row counts, but to do nothing else. The query is **not actually executed**. The planner runs its optimization algorithm, determines the cheapest plan it can find given its statistical knowledge of the data, and outputs a description of that plan. Because the query does not run, `EXPLAIN` is completely safe to use on INSERT, UPDATE, and DELETE statements without any risk of actually modifying data. The cost numbers in a plain `EXPLAIN` output are **estimates** — the planner's educated guesses about how expensive each operation will be, derived from the statistics in the system catalog.

`EXPLAIN ANALYZE`, on the other hand, actually **executes the query** and reports both the estimated costs (what the planner predicted) and the actual runtime measurements (what really happened). This is the command you use for serious performance diagnosis, because it shows you not just what the planner planned to do, but what it actually did and how long each step took. The critical insight is in the comparison between estimates and actuals: large discrepancies between estimated rows and actual rows are the fingerprint of stale statistics, and they often explain why the planner chose a suboptimal plan.

```
  EXPLAIN vs EXPLAIN ANALYZE: Key Differences

  EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
  ┌──────────────────────────────────────────────────────────────────────┐
  │ Output: ESTIMATED plan only                                          │
  │ Query:  NOT executed                                                 │
  │ Safe:   YES — no data modification, no I/O                           │
  │ Use:    Quick plan check, safe on INSERT/UPDATE/DELETE               │
  └──────────────────────────────────────────────────────────────────────┘

  EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;
  ┌──────────────────────────────────────────────────────────────────────┐
  │ Output: ESTIMATED plan + ACTUAL runtime measurements                 │
  │ Query:  ACTUALLY EXECUTED (read-only queries: safe; writes: careful!)│
  │ Safe:   For SELECT yes. For INSERT/UPDATE/DELETE: USE A TRANSACTION! │
  │         BEGIN; EXPLAIN ANALYZE INSERT...; ROLLBACK;                  │
  │ Use:    Real performance diagnosis — compares estimate vs actual     │
  └──────────────────────────────────────────────────────────────────────┘
```

### Anatomy of an EXPLAIN Output

Every node in a PostgreSQL execution plan tree follows the same format. Understanding each field is essential before you can read any plan meaningfully.

### Reading the Plan Tree (Bottom-Up)

A PostgreSQL execution plan is a tree, and it is executed **bottom-up**: the leaf nodes execute first and feed their results upward to their parent nodes. Reading the plan from the deepest indentation outward reveals the order of operations. In the example above, the execution order is:

```
  EXECUTION ORDER (bottom-up):

  Step 1: Seq Scan on customers      → reads all 10,000 customer rows
  Step 2: Hash (of customers)        → builds a hash table of customers in memory
  Step 3: Index Scan on orders       → retrieves 12,450 'shipped' orders from Jan 2024+
  Step 4: Hash Join                  → for each order row, looks up customer in hash table
  Step 5: Sort                       → sorts the joined result by created_at DESC
  Step 6: Limit                      → takes the top 20 rows from the sorted result
  Output: 20 rows returned to client

  Tree structure:
                    Limit (Step 6)
                       |
                     Sort (Step 5)
                       |
                  Hash Join (Step 4)
                  /            \
          Index Scan         Hash (Step 2)
          on orders (Step 3)    |
                           Seq Scan on
                           customers (Step 1)
```

### The BUFFERS Option: Seeing I/O Reality

For production performance diagnosis, always add `BUFFERS` to your EXPLAIN ANALYZE:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE customer_id = 42;

-- BUFFERS output adds:
-- Buffers: shared hit=5 read=2
-- "hit"  = pages found in the buffer pool cache (memory) — FREE, no disk I/O
-- "read" = pages read from disk — EXPENSIVE, causes actual I/O wait

-- The ratio of hits to reads tells you:
-- High hits: data is in cache → query is I/O efficient
-- High reads: data is not cached → adding RAM or fixing query patterns may help
-- Example: "shared hit=1000 read=50000" → 98% cache miss → I/O bound query
```

## 2. Seq Scan vs Index Scan vs Index Only Scan vs Bitmap Scan

### The Four Fundamental Ways PostgreSQL Reads a Table

When PostgreSQL needs to retrieve rows from a table, it has four fundamental strategies available. Each strategy has a different internal mechanism, different performance characteristics, and different conditions under which it is the optimal choice. The query planner chooses among them based on its cost model estimates. Understanding each strategy deeply is what allows you to look at a plan and immediately understand the performance implications of what you are seeing.

### Strategy 1: Sequential Scan (Seq Scan)

The **Sequential Scan** is the simplest and most brute-force strategy: read every single page of the table from start to finish, evaluate each row against the query's filter conditions, and return matching rows. There is no index involved. The database simply sweeps through the heap in physical page order.

Despite its apparent crudeness, the Sequential Scan is often the fastest option for queries that return a large fraction of the table. The reason lies in I/O physics: sequential reads from disk are dramatically faster than random reads. The operating system's read-ahead mechanism can predict that you will need the next page and pre-fetches it before you ask for it. Multiple pages can be read in a single large I/O operation. For a large table stored on spinning disk, a sequential scan can read at 500 MB/s, while random reads through an index might manage only 5-10 MB/s (due to seek times). The sequential scan's 100:1 I/O speed advantage can easily overcome its disadvantage in reading more total data.

```
  SEQUENTIAL SCAN — Physical I/O Pattern

  Table heap (rows stored in physical order on disk):
  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
  │ Pg 1 │ Pg 2 │ Pg 3 │ Pg 4 │ Pg 5 │ Pg 6 │ Pg 7 │ Pg 8 │
  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
       ↑                                                  ↑
  Start here → read forward continuously → end here

  I/O pattern: SEQUENTIAL, large blocks, OS prefetches ahead
  Speed: Very fast I/O, reads ALL pages regardless of filter match
  Works well when: >5-10% of rows match the WHERE clause
  Does not use: any index

  EXPLAIN output identifier: "Seq Scan on tablename"
  Key fields to check:
  - rows= estimate vs actual rows= (stale stats if very different)
  - Filter: (the WHERE clause applied AFTER reading the page)
  - Rows Removed by Filter: X  (how many rows were read but discarded)
```

### Strategy 2: Index Scan

The **Index Scan** uses a B-Tree (or other) index to locate rows, then fetches each matching row from the table heap by following the row pointer stored in the index. It is a two-step process: traverse the index to find matching entries, then for each entry, perform a **heap fetch** — a random I/O to the table page where that row lives.

The Index Scan is optimal when the query is highly selective — returning a small number of rows. In that case, the number of random heap fetches is small (perhaps 1-20), and the cost of traversing the index plus a few random reads is much lower than reading the entire table sequentially. As selectivity decreases (more rows match), the number of random heap fetches grows, and eventually the many random reads become more expensive than a sequential scan would have been.

```
  INDEX SCAN — Two-step I/O Pattern

  Step 1: Traverse B-Tree index (fast, sequential within index pages)
  B-Tree index pages:
  ┌──────────────────────────────────────────────────────────────┐
  │ Root → Internal pages → Leaf pages with matching entries     │
  │ Leaf: (cust_id=42, ptr→pg7/slot3) (cust_id=42, ptr→pg2/slot1)│
  └──────────────────────────────────────────────────────────────┘

  Step 2: Heap fetch — follow each pointer to the table page (RANDOM I/O)
  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
  │ Pg 1 │ Pg 2 │ Pg 3 │ Pg 4 │ Pg 5 │ Pg 6 │ Pg 7 │ Pg 8 │
  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
                  ↑                              ↑
       Fetch row from Pg2/slot1          Fetch row from Pg7/slot3
       (random jump)                     (another random jump)

  I/O pattern: RANDOM — each row may be on a different page
  Heap fetches: one per matching row (worst case)
  Works best when: <1-5% of rows match (few random fetches needed)
  Output: rows returned in INDEX order (by indexed column value)

  EXPLAIN output identifier: "Index Scan using indexname on tablename"
  Key fields:
  - Index Cond: (the filter applied at the INDEX level — very efficient)
  - Filter: (applied AFTER fetching from heap — less efficient)
  - Rows Removed by Filter: X (if non-zero, your index could be more selective)
```

### Strategy 3: Index Only Scan

The **Index Only Scan** is the most efficient of all scanning strategies when applicable. As we studied in the covering index chapter, it retrieves all needed data directly from the index pages, without ever touching the table heap. There are no heap fetches — no random I/O to the table at all. All columns required by the query are present in the index's leaf entries (as key columns or `INCLUDE`d columns).

The critical prerequisite for an Index Only Scan is that the **visibility map** for the relevant table pages must have its visibility bit set — meaning VACUUM has confirmed that all tuples in those pages are visible to all transactions. If the visibility map bit is not set for a page, the database must still check the table heap to verify tuple visibility, even if all needed data is in the index — which is reported as a "heap fetch" in the ANALYZE output. Regular VACUUM keeps the visibility map current and ensures Index Only Scans achieve their full potential.

```
  INDEX ONLY SCAN — No Heap Access

  Covering index leaf pages (all needed columns are HERE):
  ┌─────────────────────────────────────────────────────────────────────┐
  │ (status='shipped', cust_id=17, date=2024-01-05, total=$249)  ← ALL │
  │ (status='shipped', cust_id=42, date=2024-01-07, total=$89)   ← DATA│
  │ (status='shipped', cust_id=88, date=2024-01-09, total=$432)  ← HERE│
  └─────────────────────────────────────────────────────────────────────┘
  Table heap: NOT ACCESSED AT ALL (visibility map allows this)

  I/O pattern: SEQUENTIAL within index pages only
  Heap fetches: 0 (ideal) or small number (if visibility map not current)
  Works when: index contains ALL columns the query needs (covering index)
              AND visibility map is current (VACUUM ran recently)
  Fastest when: the index fits in the buffer pool (all pages cached)

  EXPLAIN output identifier: "Index Only Scan using indexname on tablename"
  Key diagnostic field:
  - Heap Fetches: 0   ← IDEAL. Zero table page reads.
  - Heap Fetches: 500 ← Problem! Visibility map not current. Run VACUUM.
```

### Strategy 4: Bitmap Scan

The **Bitmap Scan** is a hybrid strategy that bridges the gap between an Index Scan and a Sequential Scan. It addresses the fundamental weakness of the Index Scan — that random heap fetches are expensive when many rows match — by converting a potentially large number of random reads into a more organized, nearly sequential pattern.

A Bitmap Scan operates in two distinct phases. In the first phase (**Bitmap Index Scan**), it traverses the index and collects all matching row pointers, but instead of immediately fetching the rows, it builds a **bitmap in memory** where each bit represents one table page, and the bit is set to 1 if that page contains at least one matching row. In the second phase (**Bitmap Heap Scan**), it reads only the pages whose bits are set in the bitmap, in **physical page order** — not the random order in which the index encounters them. Reading pages in physical order converts what would have been random I/O into something much more sequential, enabling OS prefetching and dramatically reducing seek overhead on spinning disks.

```
  BITMAP SCAN — Two-Phase Hybrid Strategy

  Phase 1: Bitmap Index Scan
  Traverse index, collect row locations:
  matching rows found: pg2/slot3, pg7/slot1, pg2/slot8, pg15/slot2, pg7/slot9
  Build bitmap:
  ┌─────────────────────────────────────────────────────────────────────┐
  │ Bitmap: page 1=0, page 2=1, page 3=0, ..., page 7=1, ..., page 15=1│
  │         (1 = "this page has at least one matching row")             │
  └─────────────────────────────────────────────────────────────────────┘

  Phase 2: Bitmap Heap Scan
  Read ONLY the flagged pages, IN PHYSICAL ORDER (not index order):
  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┬───┬──────┐
  │ Pg 1 │ Pg 2 │ Pg 3 │ ...  │ Pg 7 │ ...  │ Pg 15│       │
  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┴───┴──────┘
  Skip: 1  Read: 2  Skip: many  Read: 7  Skip  Read: 15
  (Re-check each row in the page against the WHERE condition — "Recheck Cond")

  I/O pattern: NEARLY SEQUENTIAL (reads flagged pages in disk order)
  Better than Index Scan for: medium selectivity (5-20% of rows)
  Better than Seq Scan for: up to ~30-50% selectivity
  Works best when: many rows match but still a minority of total pages

  EXPLAIN output identifier:
  -> Bitmap Heap Scan on tablename
     Recheck Cond: (status = 'shipped')   ← Must re-verify rows in each page
     ->  Bitmap Index Scan on idx_orders_status
         Index Cond: (status = 'shipped')

  Special case: "Lossy" Bitmap Scan
  If too many pages are flagged and the bitmap won't fit in work_mem:
  - Bitmap becomes LOSSY: stores page granularity, not row granularity
  - All rows in a flagged page must be rechecked
  - "Rows Removed by Index Recheck: N" appears in EXPLAIN output
  - Solution: increase work_mem for the session
```

### Choosing Among the Four Strategies: The Selectivity Spectrum

The four scan strategies exist on a spectrum defined by the selectivity of the query. Understanding where each strategy wins is the key to predicting and interpreting what you will see in execution plans.

```
  SCAN STRATEGY SELECTION SPECTRUM

  Fraction of table rows returned by the query:

  0%      0.1%       1%        5%       15%      50%     100%
  ┌────────┬─────────┬──────────┬─────────┬────────┬──────────┐
  │        │         │          │         │        │          │
  │ Empty  │   Index │  Index   │ Bitmap  │ Bitmap │   Seq    │
  │ result │   Only  │  Scan    │  Scan   │  Scan  │  Scan    │
  │        │  Scan   │ (if cov) │(hybrid) │  or    │  always  │
  │        │  or     │  or Idx  │         │  Seq   │  wins    │
  │        │  Index  │  Only    │         │  Scan  │          │
  │        │  Scan   │  Scan    │         │        │          │
  └────────┴─────────┴──────────┴─────────┴────────┴──────────┘
  <- Very selective                          Less selective ->

  MEMORY AID:
  1 row     → Index Scan or Index Only Scan (point lookup)
  ~100 rows → Index Scan (few random fetches OK)
  ~10K rows → Bitmap Scan (too many random fetches → use bitmap)
  ~100K rows→ Seq Scan (just scan everything, it's faster now)
```

## 3. Cost Model — seq_page_cost and random_page_cost

### The Language of the Query Planner

When the query planner evaluates different execution strategies, it does not measure time in milliseconds or seconds. Instead, it thinks in an abstract unit of **cost** — a dimensionless number that represents the relative expense of an operation. The entire cost model is calibrated relative to a single baseline value: the cost of reading one sequential page from disk, which is defined as `seq_page_cost = 1.0`.

Every other cost in the system is expressed as a multiple of this baseline. Reading one random page costs `random_page_cost` (default: 4.0, meaning random reads are estimated to be 4× more expensive than sequential reads). Processing one row in CPU costs `cpu_tuple_cost` (default: 0.01). Evaluating one operator or function costs `cpu_operator_cost` (default: 0.0025). These numbers are the vocabulary the planner uses to compare plans.

The total cost of a plan node is computed as the sum of I/O costs (pages read × page cost) plus CPU costs (rows processed × cpu cost). The planner generates multiple candidate plans and selects the one with the lowest total estimated cost.

```
  COST MODEL PARAMETERS (PostgreSQL defaults)

  ┌─────────────────────────┬──────────┬─────────────────────────────────┐
  │ Parameter               │ Default  │ Meaning                         │
  ├─────────────────────────┼──────────┼─────────────────────────────────┤
  │ seq_page_cost           │ 1.0      │ Cost of reading one sequential  │
  │                         │          │ page. THE baseline unit.        │
  ├─────────────────────────┼──────────┼─────────────────────────────────┤
  │ random_page_cost        │ 4.0      │ Cost of reading one random page  │
  │                         │          │ (index heap fetch). 4× seq cost. │
  ├─────────────────────────┼──────────┼─────────────────────────────────┤
  │ cpu_tuple_cost          │ 0.01     │ Cost of processing one row in    │
  │                         │          │ CPU (filtering, projecting).     │
  ├─────────────────────────┼──────────┼─────────────────────────────────┤
  │ cpu_index_tuple_cost    │ 0.005    │ Cost of processing one index     │
  │                         │          │ entry during index traversal.    │
  ├─────────────────────────┼──────────┼─────────────────────────────────┤
  │ cpu_operator_cost       │ 0.0025   │ Cost of evaluating one operator  │
  │                         │          │ or function in a WHERE clause.   │
  ├─────────────────────────┼──────────┼─────────────────────────────────┤
  │ parallel_tuple_cost     │ 0.1      │ Extra cost of passing rows       │
  │                         │          │ between parallel workers.        │
  ├─────────────────────────┼──────────┼─────────────────────────────────┤
  │ effective_cache_size    │ 4GB      │ Planner's estimate of how much   │
  │                         │          │ OS + DB cache is available. Used │
  │                         │          │ to estimate cache hit likelihood. │
  └─────────────────────────┴──────────┴─────────────────────────────────┘
```

### How the Cost Model Calculates Plan Costs

Let us walk through a concrete cost calculation to demystify the numbers you see in EXPLAIN output. This will make every `cost=X..Y` pair in a plan feel transparent rather than mysterious.

```
  COST CALCULATION EXAMPLE

  Table: orders
  Total pages in table: 10,000 pages
  Total rows: 1,000,000 rows
  Matching rows for our query: 100 rows (0.01% selectivity)

  OPTION A: Sequential Scan
  I/O cost:  10,000 pages × seq_page_cost(1.0)    = 10,000.0
  CPU cost:  1,000,000 rows × cpu_tuple_cost(0.01) = 10,000.0
  Total cost = 20,000.0

  OPTION B: Index Scan (100 matching rows → 100 heap fetches)
  Index traversal: ~4 pages × random_page_cost(4.0) = 16.0
  Heap fetches: 100 rows × random_page_cost(4.0)    = 400.0
  CPU (index): 100 entries × cpu_index_tuple_cost    = 0.5
  CPU (rows):  100 rows × cpu_tuple_cost             = 1.0
  Total cost = 417.5

  COMPARISON:
  Seq Scan cost = 20,000  ← very expensive for only 100 rows
  Index Scan cost = 417   ← 48× cheaper!
  Planner correctly chooses Index Scan.

  Now, what if 300,000 rows match (30% selectivity)?

  OPTION B revised: Index Scan (300,000 heap fetches)
  Index traversal: ~4 pages × 4.0    = 16.0
  Heap fetches: 300,000 × 4.0        = 1,200,000.0  ← ENORMOUS
  CPU: negligible
  Total cost ≈ 1,200,016

  OPTION A: Sequential Scan = 20,000  ← NOW the seq scan wins!
  Planner correctly switches to Seq Scan at high selectivity.
```

### Tuning random_page_cost for SSDs

The default `random_page_cost = 4.0` reflects the physical reality of **spinning hard disk drives (HDDs)**, where random reads (requiring a physical seek to move the disk head) are genuinely 4-10× slower than sequential reads. On **Solid State Drives (SSDs)**, however, there are no moving parts. Random reads are much closer in speed to sequential reads — the ratio might be 1.1:1.0 to 1.5:1.0 rather than 4:1. On modern NVMe SSDs, random read performance can be within 10-20% of sequential read performance.

If your database runs on SSDs (which most modern cloud and on-premises production databases do), using the default `random_page_cost = 4.0` causes the planner to dramatically **overestimate** the cost of random reads, making index scans look more expensive than they really are. The practical consequence is that the planner will prefer sequential scans in situations where an index scan would actually be faster. This is one of the most common misconfiguration problems on modern SSD-based PostgreSQL deployments.

```sql
-- Tuning random_page_cost for your storage type:

-- For traditional spinning HDD:
SET random_page_cost = 4.0;  -- Default (correct for HDD)

-- For SATA SSD:
SET random_page_cost = 1.5;  -- Random reads only ~50% more costly than seq

-- For NVMe SSD (modern fast storage):
SET random_page_cost = 1.1;  -- Random reads nearly as fast as sequential

-- Apply globally (in postgresql.conf):
-- random_page_cost = 1.1
-- seq_page_cost = 1.0

-- Apply per-session (for testing without affecting other queries):
SET LOCAL random_page_cost = 1.1;
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;
-- After this change, the planner may now prefer index scans it previously avoided.

-- How to determine the right value for your hardware:
-- 1. Run pgbench to measure actual random vs sequential read throughput
-- 2. Calculate ratio: ratio = random_read_time / sequential_read_time
-- 3. Set random_page_cost = ratio × seq_page_cost

-- Verify impact: compare EXPLAIN output before and after tuning
-- Look for queries that switched from Seq Scan to Index Scan after lowering
-- random_page_cost — if those queries are now faster, the tuning was correct.
```

### effective_cache_size: Helping the Planner Understand Your Memory

The `effective_cache_size` parameter tells the planner how much memory (OS page cache + PostgreSQL shared_buffers combined) is typically available for caching data. The planner uses this to estimate the probability that a given page is already in cache. If `effective_cache_size` is large relative to the table size, the planner assumes a high cache hit rate and reduces the estimated cost of reads accordingly — which makes index scans look cheaper and encourages their use for mid-selectivity queries.

This parameter does not actually allocate memory — it is purely a hint to the planner. Setting it too low causes the planner to underestimate cache effectiveness and prefer sequential scans more than warranted. The recommended value is typically 50-75% of total RAM on a dedicated database server.

## 4. Statistics — pg_statistic and ANALYZE

### The Foundation of Every Good Plan

Every cost calculation we examined in the previous section depends on knowing how many rows a query will return — the **row count estimate**. If the planner estimates that a WHERE clause will return 100 rows but it actually returns 100,000, the cost comparison between a Sequential Scan and an Index Scan is completely wrong. The planner chose based on a 100-row world; it executes in a 100,000-row world. The wrong plan is chosen, and performance suffers.

Row count estimates come from **statistics** that PostgreSQL maintains about the data in each column of each table. These statistics are stored in the system catalog table `pg_statistic` (and the more readable view `pg_stats`) and are computed by the `ANALYZE` command. Understanding what these statistics capture — and what they do not — is the key to understanding why planners sometimes make poor choices.

### What pg_statistic Contains

For each column of each table, `pg_statistic` stores a set of statistical summaries, each designed to answer a specific kind of question about the data distribution.

```
  pg_stats VIEW — ANNOTATED FIELD GUIDE

  SELECT * FROM pg_stats WHERE tablename='orders' AND attname='status';

  ┌─────────────────────┬────────────────────────────────────────────────┐
  │ Field               │ Meaning                                        │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ tablename           │ 'orders'                                       │
  │ attname             │ 'status'                                       │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ null_frac           │ 0.02  ← 2% of rows have NULL in this column   │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ avg_width           │ 8     ← average byte width of column value     │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ n_distinct          │ 5     ← 5 distinct values in this column       │
  │                     │ (negative means ratio: -0.8 = 80% of rows     │
  │                     │ are distinct, used for high-cardinality cols)  │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ most_common_vals    │ {'active','shipped','delivered','cancelled',   │
  │                     │  'pending'}                                    │
  │                     │ ← The N most frequent values                  │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ most_common_freqs   │ {0.45, 0.25, 0.18, 0.08, 0.04}               │
  │                     │ ← Fraction of rows with each most_common_val  │
  │                     │ 'active' appears in 45% of rows!              │
  │                     │ 'pending' appears in only 4% of rows          │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ histogram_bounds    │ (NULL for low-cardinality columns like status) │
  │                     │ For high-cardinality: array of bucket          │
  │                     │ boundaries dividing values into equal-freq     │
  │                     │ buckets. Planner interpolates within buckets.  │
  ├─────────────────────┼────────────────────────────────────────────────┤
  │ correlation         │ 0.12  ← Physical sort order correlation.       │
  │                     │ 1.0 = perfectly correlated with physical order │
  │                     │ 0.0 = completely random physical order         │
  │                     │ Used to estimate cost of heap fetches in index │
  │                     │ scans (high correlation → cheaper heap fetch)  │
  └─────────────────────┴────────────────────────────────────────────────┘
```

### How Statistics Drive Selectivity Estimates

When the planner encounters a condition like `WHERE status = 'active'`, it looks up the `most_common_vals` and `most_common_freqs` for the `status` column in `pg_stats`. It finds that `'active'` appears with frequency 0.45, meaning 45% of rows have `status = 'active'`. The planner multiplies this fraction by the total row count to get its row estimate: `0.45 × 1,000,000 = 450,000 rows`. With 450,000 rows, a sequential scan will almost certainly be cheaper than an index scan — and the planner correctly plans accordingly.

For a condition like `WHERE status = 'pending'` (frequency 0.04), the estimate is `0.04 × 1,000,000 = 40,000 rows`. The planner might choose a Bitmap Scan at this scale. For `WHERE status = 'suspended'` (not in `most_common_vals` at all), the planner uses the "other" selectivity estimate, which is `(1.0 - sum_of_all_mcf_values) / (n_distinct - length_of_mcv_list)`.

### The Statistics Target and ANALYZE

The `default_statistics_target` parameter controls how much statistical detail PostgreSQL collects for each column. The default is 100, which means:
- Up to 100 most-common values (MCVs) are tracked
- The histogram has up to 100 buckets

A higher statistics target gives the planner more precise information, which leads to better estimates, which leads to better plans — but it also makes ANALYZE slower and `pg_statistic` larger. For columns whose estimates are consistently wrong (causing bad plans), increasing the statistics target for that specific column is often the right fix.

```sql
-- Check current statistics and estimates

-- See all stats for a table
SELECT attname, n_distinct, correlation,
       most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'orders'
ORDER BY attname;

-- Diagnose bad estimates by comparing EXPLAIN estimate vs actual:
EXPLAIN (ANALYZE, FORMAT TEXT)
SELECT * FROM orders WHERE status = 'active';
-- Look for: rows=450000 estimate vs actual rows=450000 → stats are good
-- If: rows=100 estimate vs actual rows=450000 → stats are BAD → run ANALYZE

-- Run ANALYZE to refresh statistics:
ANALYZE orders;               -- Single table
ANALYZE orders (status);      -- Just one column
ANALYZE;                      -- All tables in current database

-- Increase statistics target for a column with poor estimates:
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
-- Now ANALYZE will collect up to 500 MCVs and a 500-bucket histogram
-- for the 'status' column, giving the planner finer-grained estimates.
ANALYZE orders (status);      -- Collect the new statistics immediately

-- Monitor when autovacuum last ran ANALYZE:
SELECT relname, last_analyze, last_autoanalyze,
       n_mod_since_analyze  -- rows modified since last ANALYZE
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- If n_mod_since_analyze is very high, statistics are stale.
-- Run ANALYZE orders; to refresh immediately.
```

### The Extended Statistics Problem: Column Correlations

One significant limitation of the basic per-column statistics is that they treat each column **independently**. When you filter on two columns simultaneously (`WHERE status = 'shipped' AND region = 'APAC'`), the planner estimates the combined selectivity by simply multiplying the individual selectivities: `0.25 × 0.15 = 0.0375`. But this independence assumption is wrong if the columns are correlated — perhaps 80% of all shipped orders are in APAC because your main market is there. The true combined selectivity might be 0.20, not 0.0375. A 5× underestimate means the planner thinks the result set is much smaller than it is, and may choose an index scan when a seq scan would be faster.

PostgreSQL 10+ introduced **Extended Statistics** to address this:

```sql
-- Create extended statistics that models correlation between two columns:
CREATE STATISTICS orders_status_region_stats (dependencies)
ON status, region
FROM orders;

-- Re-run ANALYZE to populate the new statistics:
ANALYZE orders;

-- Now the planner uses the extended statistics to estimate
-- multi-column filter selectivity more accurately.
-- Check extended statistics:
SELECT * FROM pg_statistic_ext_data;
```

## 5. Planner Hints and Forcing Plans

### When the Optimizer Needs Guidance

The PostgreSQL query planner is one of the most sophisticated pieces of software in the database, and in the vast majority of cases it makes excellent decisions. However, there are situations where it makes poor choices — usually due to stale statistics, unusual data distributions, or limitations in its cost model. When you have identified through careful analysis (not just intuition) that the planner is choosing a suboptimal plan, you have several tools available to steer its decisions.

It is critically important to approach these tools with discipline and humility. Forcing a specific plan overrides the optimizer's judgment, which is based on a mathematical model of your data. If you force an index scan when the optimizer wanted a sequential scan, and you have not verified through careful measurement that the index scan is genuinely faster, you may make the query slower. Additionally, a forced plan that is good today may be terrible next month when the data distribution changes. Planner hints should be used sparingly, documented carefully, and revisited regularly.

### Method 1: GUC Parameter Toggles (The Standard Approach)

PostgreSQL provides a set of `enable_*` configuration parameters that can be set per-session to disable specific plan node types. When a node type is disabled (but not prohibited outright), its cost is multiplied by a very large number, making the optimizer strongly prefer other options. This is the standard, officially supported mechanism for overriding plan choices.

```sql
-- PLAN-FORCING TOOLKIT (session-level GUC parameters)

-- ─────────────────────────────────────────────────────────────────
-- Disable Sequential Scans (force index usage):
SET enable_seqscan = OFF;
-- Use: Testing whether an index scan would be faster for a specific query.
-- Risk: If no index is available, the planner must still seq scan (no error).
-- Production: Almost never. Use only for diagnosis.

-- ─────────────────────────────────────────────────────────────────
-- Disable Index Scans:
SET enable_indexscan = OFF;
-- Use: Testing whether seq scan is actually better (confirm optimizer was right).

-- ─────────────────────────────────────────────────────────────────
-- Disable Bitmap Scans:
SET enable_bitmapscan = OFF;
-- Use: Force choice between pure index scan and pure seq scan for diagnosis.

-- ─────────────────────────────────────────────────────────────────
-- Disable Nested Loop Joins (force hash or merge join):
SET enable_nestloop = OFF;
-- Use: When a nested loop join on a large table is causing poor performance.

-- ─────────────────────────────────────────────────────────────────
-- Disable Hash Joins:
SET enable_hashjoin = OFF;

-- ─────────────────────────────────────────────────────────────────
-- Disable Merge Joins:
SET enable_mergejoin = OFF;

-- ─────────────────────────────────────────────────────────────────
-- Disable Parallel Query:
SET max_parallel_workers_per_gather = 0;
-- Use: When you suspect parallelism overhead is causing problems.

-- SAFE PATTERN: Use these per-session and reset afterward
BEGIN;
SET LOCAL enable_seqscan = OFF;     -- Affects only this transaction
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;
ROLLBACK;  -- or COMMIT — SET LOCAL reverts when transaction ends

-- Check current plan-related settings:
SHOW enable_seqscan;
SHOW enable_indexscan;
SHOW random_page_cost;
```

### Method 2: Rewriting the Query

Often the most sustainable and correct approach to a bad plan is not to force a different plan but to rewrite the query so that the optimizer naturally discovers the better plan. This is especially true for index invalidation issues (applying functions to columns), for subqueries vs. CTEs, or for join order problems.

```sql
-- EXAMPLE: Rewrite to avoid function on column (enables index use)

-- BAD (index on created_at is bypassed by DATE() function):
SELECT * FROM orders WHERE DATE(created_at) = '2024-03-15';

-- GOOD (rewritten as range query — uses index on created_at naturally):
SELECT * FROM orders
WHERE created_at >= '2024-03-15'
  AND created_at  < '2024-03-16';

-- ─────────────────────────────────────────────────────────────────
-- EXAMPLE: CTE fencing to prevent subquery push-down
-- (PostgreSQL 12+ default: CTEs are "optimized away" — treated as subqueries)
-- (Pre-PostgreSQL 12 default: CTEs are "fenced" — optimization barriers)

-- In PostgreSQL 12+, to force a CTE to be materialized (act as barrier):
WITH expensive_subquery AS MATERIALIZED (
    SELECT customer_id, SUM(total) AS lifetime_value
    FROM orders
    GROUP BY customer_id
)
SELECT c.name, esq.lifetime_value
FROM customers c
JOIN expensive_subquery esq ON esq.customer_id = c.id
WHERE esq.lifetime_value > 10000;
-- MATERIALIZED forces the CTE to execute once and cache results.
-- Useful when the CTE is referenced multiple times (avoids re-execution).
-- Can also prevent the planner from "pushing down" filters into the CTE
-- in ways that cause problems.
```

### Method 3: pg_hint_plan (Third-Party Extension)

For situations where you need precise control over the plan — specifying exactly which index to use, which join method to apply, or what scan type to use for each table — the `pg_hint_plan` extension provides a hint mechanism similar to Oracle's `/*+ HINT */` syntax. Hints are embedded as SQL comments in the query and are interpreted by the extension.

```sql
-- Install pg_hint_plan (requires superuser and extension availability):
CREATE EXTENSION pg_hint_plan;

-- Using hints to force specific plan choices:

-- Force an index scan using a specific index:
/*+ IndexScan(orders idx_orders_customer_id) */
SELECT * FROM orders WHERE customer_id = 42;

-- Force a sequential scan (override index preference):
/*+ SeqScan(orders) */
SELECT * FROM orders WHERE customer_id = 42;

-- Force index-only scan:
/*+ IndexOnlyScan(orders idx_orders_covering) */
SELECT customer_id, created_at, total FROM orders WHERE status = 'shipped';

-- Force a specific join method:
/*+ HashJoin(orders customers) */
SELECT o.order_id, c.name
FROM orders o JOIN customers c ON c.id = o.customer_id;

-- Force join ORDER (tell optimizer which table to use as the outer table):
/*+ Leading(customers orders) */
SELECT o.order_id, c.name
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE c.region = 'APAC';

-- Combine multiple hints:
/*+ IndexScan(orders idx_orders_customer_id) HashJoin(orders customers) */
SELECT o.order_id, c.name
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.customer_id = 42;
```

### Method 4: plan_cache_mode and Prepared Statement Plan Stability

A subtle but important source of plan variability is **prepared statements**. When you prepare a statement, PostgreSQL generates a generic plan (after 5 executions) that works for all possible parameter values, rather than a plan optimized for the specific value being passed. This generic plan may be suboptimal for extreme parameter values (very high or very low selectivity).

```sql
-- Control how prepared statements are planned:
SET plan_cache_mode = 'force_custom_plan';
-- Always plan per-parameter-value (fresh plan for each execution)
-- Cost: planning overhead on every execution
-- Benefit: always gets the optimal plan for the specific parameter value

SET plan_cache_mode = 'force_generic_plan';
-- Always use a single generic plan regardless of parameter values
-- Cost: may be suboptimal for specific values
-- Benefit: zero planning overhead, stable and predictable plan

SET plan_cache_mode = 'auto';  -- Default
-- Uses generic plan after 5 executions if it's not too much worse
-- than the average custom plan cost. Usually the right choice.
```

### The Responsible Approach to Plan Forcing

Before applying any of these techniques in a production system, you should complete a structured diagnostic process. First, identify the slow query and examine its EXPLAIN ANALYZE output in detail. Second, check whether the estimates match the actuals — if not, run ANALYZE and re-examine. Third, check whether `random_page_cost` is tuned appropriately for your hardware. Fourth, check whether there is a missing index, an index invalidation issue, or a covering index that could help. Only after these steps have been exhausted — and the optimizer is provably making the wrong choice given accurate statistics — should you resort to plan forcing.

```
  PLAN OPTIMIZATION DECISION TREE

  Query is slow
       |

       |

              Fix query (use expression
              index or rewrite condition)
                  |
                  v

              (SET enable_X, pg_hint_plan)

```

## Summary: Reading a Query Plan Like a Pro

The ability to read execution plans fluently is the single most powerful diagnostic skill in database engineering. It is the difference between guessing about performance and understanding it. The complete mental model requires all the pieces we have assembled in this chapter: EXPLAIN gives you the plan; EXPLAIN ANALYZE gives you the truth; the scan types (Seq, Index, Index Only, Bitmap) tell you how rows are being retrieved; the cost model tells you why the planner chose each operation; the statistics tell you what the planner knows about your data; and the plan-forcing tools let you test alternatives when the planner's choice seems wrong.

```
  QUICK-REFERENCE EXECUTION PLAN READING GUIDE

  What to look for first:
  1. The BOTTOM-MOST node: this is what runs first (leaf nodes = data sources)
  2. "Seq Scan" on a large table with low selectivity: look for missing indexes
  3. Estimated rows= vs actual rows=: large discrepancy → stale statistics → ANALYZE
  4. "loops=N" on a node: actual time and rows are PER LOOP, multiply for totals
  5. "Filter:" (not "Index Cond:"): rows are fetched then filtered → index is not tight
  6. "Rows Removed by Filter: N": your index is not selective enough for the query
  7. "Heap Fetches: N" on Index Only Scan: visibility map not current → run VACUUM
  8. "Sort Method: external merge Disk: NkB": sort spilled to disk → increase work_mem
  9. Planning Time >> Execution Time: query is planned well but parsed slowly
  10. Buffers: shared read=N vs hit=N: high reads = low cache hit rate → add RAM

  Key diagnostic commands:
  EXPLAIN (ANALYZE, BUFFERS)   → the full picture
  ANALYZE tablename            → refresh statistics
  VACUUM ANALYZE tablename     → clean dead tuples + refresh statistics
  SET enable_seqscan = OFF     → test if index would help (diagnostic only)
  pg_stats WHERE tablename=... → inspect what the planner knows
  pgstatindex('indexname')     → measure index bloat
```

The database speaks to you through its execution plans. Learning its language is not a luxury for database administrators alone — it is an essential skill for every engineer who writes SQL in a production system. The query plan is always there, waiting to be asked, filled with precise information about exactly what is happening and exactly why. All you need to know is how to read it.
