## 1. The Observability Philosophy — Metrics, Baselines, and Alerts

Before looking at a single metric or a single PostgreSQL view, you need the right mental model for what monitoring is trying to accomplish. Monitoring is not about collecting numbers. It is about answering three questions at any point in time: Is the system healthy right now? Is it trending toward a problem? And when something is wrong, what is causing it?

These three questions correspond to three types of monitoring signals. The first is **health signals** — metrics that directly reflect whether the database is available and performing correctly. Connection count, query throughput, and error rate fall here. The second is **utilisation signals** — metrics that show how close the database is to its operational limits. CPU, memory, disk I/O, and connection pool saturation fall here. The third is **performance signals** — metrics that reveal the quality of the database's execution. Latency percentiles, cache hit ratios, and lock wait times fall here.

A critical concept that separates useful monitoring from metric collection is the **baseline**. A number without context is nearly meaningless. "Replication lag is 500 milliseconds" — is that alarming? It depends entirely on what is normal for your system. If your lag is normally under 50ms, 500ms is a five-fold increase and deserves investigation. If your system normally runs at 400ms lag during business hours, 500ms is unremarkable. You must observe your system under normal conditions, across different times of day and different days of the week, to establish baselines against which anomalies become visible.

The alerting philosophy that follows from this is equally important. Alerts should fire not when a metric reaches a static threshold, but when a metric deviates significantly from its baseline in a way that is likely to indicate a real problem. Paging an on-call engineer for every minor fluctuation creates alert fatigue — the most dangerous state a monitoring system can reach, because engineers start ignoring alerts. Every alert should be actionable, which means it should point to something that a human must decide about and that cannot be handled automatically.

```
THE MONITORING PYRAMID — From Data to Action:

                    ┌──────────────────┐
                    │    ALERTING      │  ← Only critical deviations.
                    │  (Wake someone   │    Every alert is actionable.
                    │   up for this)   │    Avoid alert fatigue.
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │   DASHBOARDS     │  ← Visual baselines.
                    │  (Show me the    │    Trends over time.
                    │   story)         │    Drill-down capability.
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │    METRICS       │  ← Raw time-series numbers.
                    │  (Collect        │    Scraped every 15-60 seconds.
                    │   everything)    │    Retained for weeks/months.
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │   DATA SOURCES   │  ← pg_stat_* views,
                    │  (PostgreSQL     │    system catalogs,
                    │   internals)     │    OS metrics, app metrics
                    └──────────────────┘

The bottom two layers are always on, collecting silently.
The dashboard layer is for human review and investigation.
The alert layer fires only when human attention is genuinely needed.
```

## 2. Key Metrics — Understanding Each One Deeply

### 2.1 QPS — Queries Per Second

Queries Per Second is the most fundamental throughput metric for a database. It tells you how many SQL statements the database is executing each second. Understanding QPS correctly requires knowing that "a query" in this context means any SQL statement — a SELECT, an INSERT, an UPDATE, a DELETE, even a BEGIN or COMMIT. Some systems count these individually; others count only DML statements.

QPS matters for several reasons. First, it is your **baseline throughput measurement** — you know your system normally processes 3,000 QPS on a weekday morning, and this number lets you detect both under-performance (something is wrong and queries aren't being processed) and over-performance (a runaway process or traffic spike is generating unexpected load). Second, QPS combined with latency tells you your system's **efficiency**: if QPS is 3,000 and your average latency is 5ms, your system is using roughly 15 seconds of total CPU time per second of wall time, which means 15 CPU cores worth of query processing at full efficiency.

In PostgreSQL, QPS is derived from the `pg_stat_database` view rather than being directly exposed:

```sql
-- QPS calculation from pg_stat_database:
-- Run this twice, N seconds apart, and compute the rate:

SELECT
    datname AS database_name,
    xact_commit + xact_rollback AS total_transactions,
    -- Total queries: blks_hit + blks_read is a proxy for read activity
    -- For true QPS, use pg_stat_statements:
    blks_hit + blks_read AS block_reads,
    xact_commit           AS committed_transactions,
    xact_rollback         AS rolled_back_transactions,
    conflicts,
    deadlocks,
    -- Calculate rates in your monitoring system (T2 - T1) / seconds
    stats_reset           AS stats_last_reset
FROM pg_stat_database
WHERE datname = current_database();

-- Better QPS from pg_stat_statements (requires the extension):
-- Sum of calls across all statement types gives total query count:
SELECT
    SUM(calls) AS total_query_calls_since_reset,
    SUM(calls) / EXTRACT(EPOCH FROM (NOW() - stats_reset))
        AS avg_qps_since_reset
FROM pg_stat_statements
CROSS JOIN pg_stat_statements_reset_time()  -- hypothetical; use stats_reset
;

-- Practical: Prometheus scrapes this every 15s and computes rate():
-- rate(pg_stat_statements_calls_total[5m])
-- → Gives you real-time QPS averaged over 5 minutes
```

QPS spikes are normal — traffic patterns follow human behaviour, peaking at business hours, dropping overnight. What is abnormal is a sudden sustained spike with no corresponding user activity change (possible runaway query or DDoS), or a sudden drop in QPS when user traffic is still high (possible connection pool exhaustion or database unavailability).

### 2.2 TPS — Transactions Per Second

Transactions Per Second measures how many database transactions the system completes each second. A transaction may contain one or many queries, making TPS different from QPS. TPS is particularly important for applications with explicit transaction management — banking systems where every transfer is a transaction, e-commerce systems where order creation involves multiple tables within one transaction, and similar ACID-critical workloads.

The relationship between TPS and QPS reveals your **average transaction size** in queries: `average_queries_per_transaction = QPS / TPS`. If QPS is 6,000 and TPS is 1,000, each transaction contains an average of 6 queries. This is useful for understanding whether a sudden QPS spike is driven by more transactions (more users or more load) or by more queries per transaction (a slow query running extra queries, perhaps an N+1 problem that has emerged under load).

```sql
-- TPS from pg_stat_database:
SELECT
    datname,
    xact_commit   AS committed_transactions,
    xact_rollback AS rolled_back_transactions,
    xact_commit + xact_rollback AS total_transactions,

    -- Rollback rate reveals application errors or intentional rollbacks:
    CASE
        WHEN xact_commit + xact_rollback = 0 THEN 0
        ELSE ROUND(
            100.0 * xact_rollback / (xact_commit + xact_rollback), 2
        )
    END AS rollback_rate_pct,

    -- A high rollback rate indicates errors, deadlocks, or
    -- intentional savepoint usage — worth investigating if > 1%
    deadlocks AS deadlock_count
FROM pg_stat_database
WHERE datname = current_database();
```

The **rollback rate** deserves special attention. A small number of rollbacks is normal — they arise from user-triggered cancellations, intentional `ROLLBACK` statements in error handling paths, and serialization failures in serializable isolation. A rollback rate above 1-2% usually indicates a problem: high deadlock frequency, application errors being handled with transaction rollback, or serialization failures on a heavily contended table. Each rollback wastes the work done during the transaction and potentially triggers locking conflicts with other transactions that were waiting for its locks to release.

### 2.3 Latency Percentiles

Latency is the time taken to complete a database operation — from the moment the query is received to the moment the result is returned. It is perhaps the single most important user-facing performance metric, because latency directly determines how fast your application responds to users. But the way latency is measured and reported matters enormously, and the difference between average latency and percentile latency is one of the most important concepts in performance monitoring.

**Average (mean) latency** is computed by summing all query durations and dividing by the count. It sounds like a sensible summary, but it is deeply misleading in practice. A thousand queries taking 5ms each plus one query taking 5,000ms produces an average of about 9.9ms — which sounds almost normal, but one user just waited 5 seconds. The average hides the outlier.

**Latency percentiles** give you a more honest picture. The P50 (50th percentile, or median) is the latency that 50% of queries complete within — half are faster, half are slower. P95 is the latency that 95% of queries complete within — only 5% take longer. P99 is the latency that 99% of queries complete within. P99.9 is where only 0.1% of queries exceed the threshold. In a system processing 3,000 QPS, the P99.9 still represents 3 queries per second experiencing the worst latency — at scale, outliers are not rare.

```
LATENCY PERCENTILE EXAMPLE — Why Average Misleads:

1,000 query latencies (in milliseconds):
  990 queries: 4ms each
  9 queries:   12ms each
  1 query:     1,500ms (slow query / lock wait / full table scan)

Average latency:  (990*4 + 9*12 + 1*1500) / 1000 = 5.508ms
  → "Our average query is 5.5ms" sounds excellent.

P50 (median):   4ms    → Half of queries complete in 4ms ✓
P95:            5ms    → 95% complete within 5ms ✓
P99:            12ms   → 99% complete within 12ms — acceptable
P99.9:        1500ms   → The worst 0.1% wait 1.5 seconds ← PROBLEM

The average completely hides the P99.9 problem.
If you process 3,000 QPS, P99.9 = 3 users per second experiencing
1.5-second response times. That is not an edge case — it is your
worst 10,800 users per hour experiencing terrible performance.

In SLO (Service Level Objective) terms:
  A 99.9% availability SLA on latency means:
  "We promise 99.9% of queries complete within X milliseconds."
  P99.9 is the metric that tells you whether you are meeting that SLA.
```

PostgreSQL does not expose latency percentiles directly in its statistics views (because computing percentiles requires storing every individual query duration, which is prohibitively expensive). Instead, `pg_stat_statements` provides total execution time and call count per query pattern, from which you can compute average execution time per query type. True percentile monitoring requires either sampling (collecting a statistical sample of query durations) or histogram buckets (recording how many queries fall into each duration bucket), which is what Prometheus-based monitoring provides.

```sql
-- Average execution time per query from pg_stat_statements:
-- (Not a percentile, but identifies the slowest query types)
SELECT
    LEFT(query, 80) AS query_preview,
    calls,
    ROUND((total_exec_time / calls)::NUMERIC, 2) AS avg_exec_ms,
    ROUND(total_exec_time::NUMERIC, 2)           AS total_exec_ms,
    ROUND(mean_exec_time::NUMERIC, 2)            AS mean_exec_ms,
    ROUND(stddev_exec_time::NUMERIC, 2)          AS stddev_exec_ms,
    -- High stddev relative to mean = inconsistent performance = investigate
    rows
FROM pg_stat_statements
WHERE calls > 100   -- Only statistically significant queries
ORDER BY avg_exec_ms DESC
LIMIT 20;
```

For SLO tracking, the standard targets are: P50 < 5ms, P95 < 50ms, P99 < 200ms for a well-tuned OLTP database. These numbers vary enormously by workload — analytical queries legitimately take seconds, while OLTP point lookups should be sub-millisecond. The critical thing is that you define your own targets based on your workload and track whether you are meeting them.

### 2.4 Cache Hit Ratio

The cache hit ratio measures what percentage of data read requests were served from PostgreSQL's **shared buffer cache** (in-memory) rather than from disk (physical storage). This is one of the most consequential performance metrics because memory access is roughly 100x to 1000x faster than disk I/O. A cache hit ratio of 99% means 99 out of every 100 page reads are served from RAM; 1% require going to disk. When the ratio drops — say, to 90% — the proportion of slow disk reads has increased tenfold.

PostgreSQL's shared buffer cache is the pool of memory (configured via `shared_buffers` in `postgresql.conf`, typically set to 25% of total RAM) that PostgreSQL uses to cache data pages in memory. Every time a query needs a data page, it first checks the shared buffer. If the page is there, it is a **buffer hit** (fast). If not, PostgreSQL reads it from disk into the buffer, potentially evicting an older page to make room — this is a **buffer miss** (slow, disk I/O required).

```sql
-- CACHE HIT RATIO — Per Database:
SELECT
    datname AS database,
    blks_hit                            AS buffer_hits,
    blks_read                           AS disk_reads,
    blks_hit + blks_read                AS total_reads,
    CASE
        WHEN blks_hit + blks_read = 0 THEN 100.0
        ELSE ROUND(
            100.0 * blks_hit / (blks_hit + blks_read), 4
        )
    END AS cache_hit_ratio_pct
FROM pg_stat_database
WHERE datname = current_database();

-- Expected output:
-- database    | buffer_hits | disk_reads | cache_hit_ratio_pct
-- production  | 9,847,203   | 92,441     | 99.0657

-- ─────────────────────────────────────────────────────────────────
-- CACHE HIT RATIO — Per Table (more granular diagnosis):
SELECT
    schemaname,
    relname AS table_name,
    heap_blks_hit                                  AS buffer_hits,
    heap_blks_read                                 AS disk_reads,
    CASE
        WHEN heap_blks_hit + heap_blks_read = 0 THEN NULL
        ELSE ROUND(
            100.0 * heap_blks_hit /
            NULLIF(heap_blks_hit + heap_blks_read, 0), 2
        )
    END AS table_cache_hit_pct,
    idx_blks_hit                                   AS index_buffer_hits,
    idx_blks_read                                  AS index_disk_reads,
    CASE
        WHEN idx_blks_hit + idx_blks_read = 0 THEN NULL
        ELSE ROUND(
            100.0 * idx_blks_hit /
            NULLIF(idx_blks_hit + idx_blks_read, 0), 2
        )
    END AS index_cache_hit_pct
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC  -- Tables with most disk reads first
LIMIT 20;
```

A cache hit ratio below 99% in an OLTP database is cause for investigation. Between 95% and 99%, performance is degraded but manageable — you are doing more disk I/O than ideal. Below 95%, something is significantly wrong: either `shared_buffers` is too small for your working set, a large table scan is flooding the cache (blowing out cached pages that other queries need), or your working set has grown beyond what can fit in memory. The first response is to check which tables have low individual cache hit ratios (the per-table query above), which identifies whether one "hot" table is missing its cache or whether the problem is general.

### 2.5 Replication Lag

Replication lag is the delay between when a write is committed on the primary database and when that write is visible on a replica. It is measured in bytes (how far behind in the WAL stream the replica is) and in time (how old is the most recent data the replica has applied). Both measurements are useful because a replica that is 50MB behind in a system generating 50MB/s of WAL is only 1 second behind, whereas 50MB behind in a system generating 1MB/s means 50 seconds of lag.

Replication lag matters for several reasons. If your application reads from replicas, lagging replicas return stale data, which can cause read-your-writes violations and business logic errors. If your primary fails and you need to fail over to a replica, the replica's lag determines how much data is lost (the Recovery Point Objective, or RPO). A replica that is 30 seconds behind the primary will lose the last 30 seconds of committed data if the primary fails before those writes are replicated.

```sql
-- REPLICATION LAG — Query on Primary:
SELECT
    application_name,
    client_addr,
    state,
    sync_state,

    -- WAL positions (LSN = Log Sequence Number):
    sent_lsn,     -- How far primary has sent to replica
    write_lsn,    -- How far replica has written to its WAL
    flush_lsn,    -- How far replica has flushed to disk
    replay_lsn,   -- How far replica has applied (replayed)

    -- Lag calculations in bytes:
    pg_wal_lsn_diff(sent_lsn, write_lsn)  AS write_lag_bytes,
    pg_wal_lsn_diff(sent_lsn, flush_lsn)  AS flush_lag_bytes,
    pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_lag_bytes,

    -- Lag in time (most human-readable):
    write_lag    AS write_lag_time,
    flush_lag    AS flush_lag_time,
    replay_lag   AS replay_lag_time    -- This is the most important one

FROM pg_stat_replication
ORDER BY replay_lag DESC NULLS LAST;

-- Expected output when healthy:
-- application_name | state     | replay_lag
-- replica-1        | streaming | 00:00:00.012   (12 milliseconds lag)
-- replica-2        | streaming | 00:00:00.089   (89 milliseconds lag)

-- Expected output when problematic:
-- replica-1        | streaming | 00:00:45.203   (45 SECONDS lag — investigate!)
-- replica-2        | catchup   | NULL            (NULL = disconnected!)
```

Understanding the difference between `write_lag`, `flush_lag`, and `replay_lag` is important for diagnosing the source of lag. If `write_lag` is low but `replay_lag` is high, the replica is receiving WAL quickly but applying it slowly — perhaps the replica's disk I/O is saturated or it is running complex conflict resolution. If `write_lag` is high, the network between primary and replica is the bottleneck, or the replica is overloaded and not acknowledging received WAL quickly enough.

### 2.6 Lock Wait Time

Lock contention is one of the most common performance problems in production databases, and it is among the most difficult to debug without the right metrics. When a transaction needs a lock on a resource that another transaction already holds, it must wait — and during that wait, it is consuming a connection, holding any locks it has already acquired (potentially blocking other transactions), and not making progress. A cascade of lock waits can bring an entire database to a standstill even while CPU and disk I/O appear normal.

PostgreSQL uses a sophisticated multi-level locking system with different lock modes for different operations. Ordinary `SELECT` queries take a very weak lock (AccessShareLock) that does not conflict with other reads or even most writes. `UPDATE` and `DELETE` take RowExclusiveLock. `ALTER TABLE` takes AccessExclusiveLock, which conflicts with everything — it must wait for all existing transactions to finish and blocks all new transactions until it completes. This is why `ALTER TABLE` on a busy production table can cause an outage.

```sql
-- CURRENT LOCK WAITS — What is blocked and by what:
SELECT
    blocked.pid                  AS blocked_pid,
    blocked_activity.usename     AS blocked_user,
    blocked_activity.query       AS blocked_query,
    blocked_activity.wait_event  AS blocked_wait_event,

    blocking.pid                 AS blocking_pid,
    blocking_activity.usename    AS blocking_user,
    blocking_activity.query      AS blocking_query,

    -- How long has the blocked query been waiting?
    NOW() - blocked_activity.query_start AS blocked_duration

FROM pg_locks AS blocked
JOIN pg_stat_activity AS blocked_activity
    ON blocked.pid = blocked_activity.pid
JOIN pg_locks AS blocking
    ON blocking.relation = blocked.relation
    AND blocking.granted = TRUE
    AND blocked.granted = FALSE
JOIN pg_stat_activity AS blocking_activity
    ON blocking.pid = blocking_activity.pid
WHERE NOT blocked.granted   -- Only show queries that are WAITING
ORDER BY blocked_duration DESC;

-- ─────────────────────────────────────────────────────────────────
-- LOCK WAIT HISTORY — From pg_stat_activity (long-running waits):
SELECT
    pid,
    usename,
    application_name,
    wait_event_type,
    wait_event,
    state,
    query_start,
    NOW() - query_start AS running_for,
    LEFT(query, 100) AS query_preview
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'   -- Currently waiting on a lock
ORDER BY query_start ASC;        -- Oldest waits first

-- ─────────────────────────────────────────────────────────────────
-- DEADLOCK COUNT (from pg_stat_database):
SELECT
    datname,
    deadlocks,
    -- A deadlock count > 0 per day indicates application-level
    -- transaction ordering problems that need fixing in code:
    conflicts
FROM pg_stat_database
WHERE datname = current_database();
```

Lock wait time in aggregate (total time queries spent waiting for locks) is a key metric for understanding contention. The alert threshold should be: if any query waits more than 5 seconds for a lock, investigate immediately. If your overall lock wait time is growing over weeks, it indicates increasing contention that will eventually cause incidents.

### 2.7 Connection Count

PostgreSQL uses a **process-per-connection model** — every client connection creates a new OS process on the database server. This is fundamentally different from thread-per-connection or event-loop models. Each PostgreSQL backend process consumes roughly 5-10MB of RAM, plus the memory used by its queries. At 200 connections, that is 1-2GB of memory consumed just for connection overhead, before any query memory is counted.

This architecture has a hard limit: `max_connections` in `postgresql.conf` (typically 100-500 in production). Once this limit is reached, new connection attempts fail with "FATAL: remaining connection slots are reserved for non-replication superuser connections." This is an immediate outage for your application. Unlike most database resource limits, connection exhaustion fails instantly and completely — there is no graceful degradation.

```sql
-- CONNECTION COUNT AND STATUS:
SELECT
    -- Total connections by state:
    COUNT(*)                                            AS total_connections,
    COUNT(*) FILTER (WHERE state = 'active')            AS active,
    COUNT(*) FILTER (WHERE state = 'idle')              AS idle,
    COUNT(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_transaction,
    -- Idle in transaction is dangerous — see below
    COUNT(*) FILTER (WHERE state = 'idle in transaction (aborted)') AS idle_in_txn_aborted,

    -- Max connections configured:
    (SELECT setting::INT FROM pg_settings WHERE name = 'max_connections')
        AS max_connections,

    -- What percentage of connections are in use:
    ROUND(
        100.0 * COUNT(*) /
        (SELECT setting::INT FROM pg_settings WHERE name = 'max_connections'),
        2
    ) AS connection_usage_pct

FROM pg_stat_activity
WHERE pid <> pg_backend_pid();   -- Exclude this monitoring query itself

-- Expected output (healthy):
-- total | active | idle | idle_in_txn | max_connections | usage_pct
-- 87    | 12     | 74   | 1           | 200             | 43.50%

-- Expected output (problem):
-- total | active | idle | idle_in_txn | max_connections | usage_pct
-- 199   | 8      | 120  | 71          | 200             | 99.50% ← CRITICAL
```

The **idle in transaction** state is particularly dangerous and deserves special attention. A connection is idle in transaction when it has opened a transaction (`BEGIN`) but has not yet committed or rolled back, and is currently not executing a query. This happens when application code opens a transaction, does some non-database work (like calling an external API), and has not yet committed. During this time, the connection holds all locks acquired within the transaction, consumes a connection slot, and blocks other transactions that need those locks. If your application crashes or network connection drops while in this state, PostgreSQL will eventually detect the dead connection and roll back — but the `idle_in_transaction_session_timeout` parameter (which you should set in production) controls how long PostgreSQL waits before doing so.

```sql
-- SET TIMEOUT FOR IDLE-IN-TRANSACTION (postgresql.conf or per-role):
-- idle_in_transaction_session_timeout = '30s'
-- → Automatically terminate connections idle in transaction > 30 seconds

-- IDENTIFY LONG-RUNNING IDLE IN TRANSACTION:
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    query_start,
    state_change,
    NOW() - state_change AS idle_in_txn_duration,
    LEFT(query, 100) AS last_query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY state_change ASC
LIMIT 20;
```

Because of PostgreSQL's process-per-connection limitation, production systems almost always use a **connection pooler** — PgBouncer being by far the most common. PgBouncer maintains a smaller pool of actual PostgreSQL connections and multiplexes a larger number of application connections onto them. An application might have 500 connection pool threads across its pods, but PgBouncer maintains only 100 actual PostgreSQL connections. This makes connection count monitoring two-layered: you need to track both PgBouncer's client connections (from your application) and its server connections (to PostgreSQL).

## 3. pg_stat_activity — The Live Session View

`pg_stat_activity` is your real-time window into what is happening inside the PostgreSQL database right now. It shows one row per current backend process (each connection), with detailed information about the query it is executing, its state, and what it is waiting for. This is the first view you open during a performance incident.

```sql
-- THE COMPLETE pg_stat_activity DIAGNOSTIC QUERY:
SELECT
    pid,
    usename                             AS user,
    application_name                    AS app,
    client_addr,
    backend_start                       AS connected_since,
    NOW() - backend_start               AS connection_age,

    state,
    -- wait_event_type: Lock, LWLock, IO, Client, Extension, Timeout, etc.
    wait_event_type,
    wait_event,

    query_start,
    NOW() - query_start                 AS query_running_for,
    state_change,
    NOW() - state_change                AS in_current_state_for,

    -- The actual SQL — note this shows the LAST query, even for idle:
    LEFT(query, 200)                    AS query_preview,

    -- backend_type: client backend, autovacuum worker, walsender, etc.
    backend_type

FROM pg_stat_activity
WHERE pid <> pg_backend_pid()          -- Exclude this query
  AND backend_type = 'client backend'  -- Only client connections
ORDER BY query_start ASC NULLS LAST;   -- Oldest queries first

-- ─────────────────────────────────────────────────────────────────
-- QUERIES RUNNING LONGER THAN 5 SECONDS (likely problematic):
SELECT
    pid,
    usename,
    NOW() - query_start AS running_for,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state = 'active'
  AND query_start < NOW() - INTERVAL '5 seconds'
  AND pid <> pg_backend_pid()
ORDER BY query_start ASC;

-- ─────────────────────────────────────────────────────────────────
-- TERMINATE A SPECIFIC QUERY (use during incidents):
-- Soft kill — sends cancellation signal (query stops, connection stays):
SELECT pg_cancel_backend(pid);

-- Hard kill — terminates the backend process (connection dropped):
SELECT pg_terminate_backend(pid);

-- Kill all idle-in-transaction older than 10 minutes:
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND NOW() - state_change > INTERVAL '10 minutes';
```

The `wait_event` and `wait_event_type` columns are your most powerful diagnostic tools in `pg_stat_activity`. When a query is not making progress (it is active but slow), it is almost always waiting for something. The wait event tells you exactly what.

```
WAIT EVENTS — What They Tell You:

wait_event_type │ wait_event          │ Meaning & Action
────────────────┼─────────────────────┼────────────────────────────────────────
Lock            │ relation            │ Waiting for a table-level lock.
                │                     │ Find the locking query and investigate.
────────────────┼─────────────────────┼────────────────────────────────────────
Lock            │ tuple               │ Waiting for a row-level lock.
                │                     │ Another transaction holds a row lock.
────────────────┼─────────────────────┼────────────────────────────────────────
LWLock          │ WALWrite            │ Waiting to write to WAL.
                │                     │ Possible WAL disk I/O bottleneck.
────────────────┼─────────────────────┼────────────────────────────────────────
LWLock          │ BufferMapping       │ Contention on shared buffer pool.
                │                     │ May need to increase shared_buffers.
────────────────┼─────────────────────┼────────────────────────────────────────
IO              │ DataFileRead        │ Waiting to read from data files.
                │                     │ Cache miss — disk I/O bottleneck.
────────────────┼─────────────────────┼────────────────────────────────────────
IO              │ WALSync             │ Waiting for WAL fsync.
                │                     │ Disk I/O bottleneck on WAL writes.
────────────────┼─────────────────────┼────────────────────────────────────────
Client          │ ClientRead          │ Waiting for client to send next query.
                │                     │ Normal for idle connections.
────────────────┼─────────────────────┼────────────────────────────────────────
NULL            │ NULL                │ Query is ACTIVE — running on CPU/IO.
                │                     │ Not waiting. This is normal execution.
```

## 4. pg_stat_statements — The Query Performance Registry

`pg_stat_statements` is arguably the most valuable performance diagnostic tool in the entire PostgreSQL ecosystem. It tracks the execution statistics of every distinct SQL statement executed since the last statistics reset, normalised to remove literal parameter values (so `WHERE id = 1` and `WHERE id = 2` are counted as the same query pattern). This normalisation is what makes it usable — instead of millions of individual query records, you get hundreds of distinct query patterns with aggregated statistics.

The extension must be enabled explicitly. Add `pg_stat_statements` to `shared_preload_libraries` in `postgresql.conf`, restart PostgreSQL, and then run `CREATE EXTENSION pg_stat_statements` in each database where you want it active.

```sql
-- ─────────────────────────────────────────────────────────────────
-- TOP 20 SLOWEST QUERIES BY TOTAL TIME CONSUMED:
-- (Total time = where your database is spending its time)
SELECT
    ROUND(total_exec_time::NUMERIC, 2)          AS total_exec_ms,
    calls,
    ROUND(mean_exec_time::NUMERIC, 2)           AS avg_ms_per_call,
    ROUND(stddev_exec_time::NUMERIC, 2)         AS stddev_ms,
    rows,
    ROUND(rows::NUMERIC / NULLIF(calls, 0), 0) AS avg_rows_returned,

    -- Cache efficiency for this specific query:
    shared_blks_hit,
    shared_blks_read,
    ROUND(
        100.0 * shared_blks_hit /
        NULLIF(shared_blks_hit + shared_blks_read, 0), 2
    ) AS query_cache_hit_pct,

    -- Temp disk usage (spills to disk during sort/hash operations):
    temp_blks_written,
    -- High temp_blks_written = needs more work_mem or query optimisation

    LEFT(query, 120) AS query_preview

FROM pg_stat_statements
WHERE calls > 50                  -- Minimum call count for statistical significance
  AND query NOT LIKE '%pg_stat%'  -- Exclude monitoring queries themselves
ORDER BY total_exec_time DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- TOP 20 QUERIES BY AVERAGE EXECUTION TIME (slowest per call):
SELECT
    ROUND(mean_exec_time::NUMERIC, 2)   AS avg_ms_per_call,
    calls,
    ROUND(total_exec_time::NUMERIC, 2)  AS total_exec_ms,
    LEFT(query, 120)                    AS query_preview
FROM pg_stat_statements
WHERE calls > 100
ORDER BY mean_exec_time DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- HIGH VARIABILITY QUERIES (unpredictable performance — bad for SLOs):
SELECT
    ROUND(mean_exec_time::NUMERIC, 2)   AS avg_ms,
    ROUND(stddev_exec_time::NUMERIC, 2) AS stddev_ms,
    -- Coefficient of variation: stddev/mean. High = unpredictable.
    ROUND((stddev_exec_time / NULLIF(mean_exec_time, 0))::NUMERIC, 2)
                                        AS cv_ratio,
    calls,
    LEFT(query, 120)                    AS query_preview
FROM pg_stat_statements
WHERE calls > 100
  AND mean_exec_time > 1              -- At least 1ms average
ORDER BY cv_ratio DESC
LIMIT 20;
-- A CV ratio > 5 means the query sometimes takes 5x longer than average.
-- These are prime candidates for performance investigation.

-- ─────────────────────────────────────────────────────────────────
-- QUERIES CAUSING MOST DISK I/O (cache unfriendly):
SELECT
    shared_blks_read AS disk_reads,
    ROUND(mean_exec_time::NUMERIC, 2) AS avg_ms,
    calls,
    LEFT(query, 120) AS query_preview
FROM pg_stat_statements
WHERE shared_blks_read > 1000     -- Significant disk reads
ORDER BY shared_blks_read DESC
LIMIT 10;

-- ─────────────────────────────────────────────────────────────────
-- RESET STATISTICS (do this after resolving a performance issue
-- to get a clean baseline going forward):
SELECT pg_stat_statements_reset();
-- WARNING: This loses all historical data. Do it intentionally.
```

## 5. pg_stat_user_tables — The Table Health Dashboard

`pg_stat_user_tables` is the view that tells you how individual tables are being used — how many sequential scans versus index scans, how many rows have been inserted/updated/deleted, how much dead tuple bloat has accumulated, and when autovacuum last ran. This view is essential for detecting tables that need index optimisation, that are accumulating bloat, or that autovacuum is struggling to keep up with.

```sql
-- ─────────────────────────────────────────────────────────────────
-- TABLES WITH HIGH SEQUENTIAL SCAN RATE (missing index candidates):
SELECT
    schemaname,
    relname AS table_name,
    seq_scan              AS sequential_scans,
    seq_tup_read          AS rows_read_by_seq_scan,
    idx_scan              AS index_scans,
    idx_tup_fetch         AS rows_fetched_by_index,

    -- Ratio: if idx_scan << seq_scan and table is large → missing index
    CASE
        WHEN idx_scan + seq_scan = 0 THEN NULL
        ELSE ROUND(
            100.0 * idx_scan / (idx_scan + seq_scan), 2
        )
    END AS index_scan_pct,

    n_live_tup            AS live_rows,
    n_dead_tup            AS dead_rows,

    -- Dead tuple ratio: if > 10%, autovacuum may be struggling:
    CASE
        WHEN n_live_tup + n_dead_tup = 0 THEN NULL
        ELSE ROUND(
            100.0 * n_dead_tup / (n_live_tup + n_dead_tup), 2
        )
    END AS dead_tuple_pct,

    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze

FROM pg_stat_user_tables
WHERE n_live_tup > 10000          -- Only non-trivial tables
ORDER BY seq_scan DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- TABLE BLOAT — Dead tuples consuming disk space:
SELECT
    schemaname,
    relname AS table_name,
    n_live_tup    AS live_rows,
    n_dead_tup    AS dead_rows,
    ROUND(
        100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2
    ) AS dead_pct,
    last_autovacuum,
    last_vacuum,
    -- When did autovacuum last touch this table?
    GREATEST(last_autovacuum, last_vacuum) AS last_vacuumed_at
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000     -- Tables with significant dead tuples
ORDER BY n_dead_tup DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- WRITE ACTIVITY BY TABLE (find the highest-churn tables):
SELECT
    relname AS table_name,
    n_tup_ins AS inserts,
    n_tup_upd AS updates,
    n_tup_del AS deletes,
    n_tup_ins + n_tup_upd + n_tup_del AS total_writes,
    n_tup_hot_upd AS hot_updates,   -- HOT updates avoid index maintenance
    ROUND(
        100.0 * n_tup_hot_upd / NULLIF(n_tup_upd, 0), 2
    ) AS hot_update_pct
    -- High hot_update_pct is GOOD — means updates aren't touching indexed cols
FROM pg_stat_user_tables
ORDER BY total_writes DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- UNUSED INDEXES — Candidates for removal (reduce write overhead):
SELECT
    s.schemaname,
    s.relname AS table_name,
    s.indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(s.indexrelid)) AS index_size,
    s.idx_scan AS times_used,
    s.idx_tup_read,
    s.idx_tup_fetch
FROM pg_stat_user_indexes s
JOIN pg_index i ON s.indexrelid = i.indexrelid
WHERE s.idx_scan = 0          -- Never been used since last stats reset
  AND NOT i.indisprimary       -- Not the primary key
  AND NOT i.indisunique        -- Not a unique constraint
ORDER BY pg_relation_size(s.indexrelid) DESC;
-- Remove unused indexes → reduces write overhead on INSERT/UPDATE/DELETE
```

## 6. INFORMATION_SCHEMA and System Catalog Queries

The `INFORMATION_SCHEMA` is the SQL-standard namespace that provides metadata about the database structure — tables, columns, constraints, views, and more. PostgreSQL also exposes a richer, PostgreSQL-specific set of system catalog tables prefixed with `pg_` that provide information not available in the standard schema. Both are invaluable for monitoring and auditing.

```sql
-- ─────────────────────────────────────────────────────────────────
-- TABLE SIZES — Which tables consume the most space:
SELECT
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename))
        AS total_size,
    pg_size_pretty(pg_relation_size(schemaname||'.'||tablename))
        AS table_size,
    pg_size_pretty(
        pg_total_relation_size(schemaname||'.'||tablename) -
        pg_relation_size(schemaname||'.'||tablename)
    ) AS index_size
FROM information_schema.tables
WHERE table_schema NOT IN ('pg_catalog', 'information_schema')
  AND table_type = 'BASE TABLE'
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- INDEX HEALTH — Bloated or duplicate indexes:
SELECT
    schemaname,
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexname::REGCLASS)) AS index_size,
    indexdef
FROM pg_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexname::REGCLASS) DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- LONG-RUNNING TRANSACTIONS (from system catalog):
SELECT
    pid,
    usename,
    datname,
    xact_start,
    NOW() - xact_start AS transaction_age,
    query_start,
    state,
    LEFT(query, 100) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND NOW() - xact_start > INTERVAL '5 minutes'
ORDER BY xact_start ASC;
-- Long transactions hold locks, inflate WAL, prevent vacuum from
-- cleaning up dead tuples. They are a common cause of bloat and lag.

-- ─────────────────────────────────────────────────────────────────
-- VACUUM AND ANALYZE STATUS (when did each table last get maintained):
SELECT
    schemaname,
    relname AS table_name,
    n_live_tup AS live_rows,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze,
    vacuum_count,
    autovacuum_count,

    -- Tables approaching autovacuum threshold:
    n_dead_tup AS dead_tuples,
    -- autovacuum triggers when dead tuples exceed:
    -- autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * n_live_tup
    ROUND(
        50 + 0.2 * n_live_tup  -- default threshold formula
    ) AS approx_autovacuum_threshold

FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

## 7. Prometheus Exporters — postgres_exporter and mysqld_exporter

Prometheus is the de-facto standard for metrics collection in modern infrastructure, and its pull-based model (Prometheus scrapes exporters periodically) works naturally with database monitoring. The exporters are small sidecar processes that connect to your database, query its statistics views, and expose the results in Prometheus's text-based format over HTTP. Prometheus then scrapes these endpoints every 15-60 seconds and stores the time-series data.

**postgres_exporter** (by Prometheus Community, `github.com/prometheus-community/postgres_exporter`) is the standard PostgreSQL exporter. It connects to PostgreSQL using a dedicated monitoring user and collects metrics from the `pg_stat_*` views we have discussed throughout this guide.

```yaml
# ─────────────────────────────────────────────────────────────────
# DOCKER-COMPOSE SETUP — postgres_exporter with PostgreSQL:

version: '3.8'
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: secret
    volumes:
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql
    ports:
      - "5432:5432"

  postgres_exporter:
    image: prometheuscommunity/postgres-exporter:latest
    environment:
      # Connection string for the monitoring user:
      DATA_SOURCE_NAME: "postgresql://monitoring:monpass@postgres:5432/myapp?sslmode=disable"
      # Enable pg_stat_statements collection:
      PG_EXPORTER_INCLUDE_DATABASES: "myapp"
    ports:
      - "9187:9187"    # Prometheus scrapes this port
    depends_on:
      - postgres
```

```sql
-- ─────────────────────────────────────────────────────────────────
-- MONITORING USER SETUP (minimum required privileges):
-- Run on your PostgreSQL instance:

CREATE USER monitoring WITH PASSWORD 'monpass';

-- Required for all pg_stat_* views:
GRANT pg_monitor TO monitoring;
-- pg_monitor is a built-in role that grants access to all monitoring views.
-- It is the safe, minimal privilege set for monitoring.

-- For pg_stat_statements specifically:
GRANT pg_read_all_stats TO monitoring;

-- Connect to each database you want to monitor:
\c myapp
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
GRANT EXECUTE ON FUNCTION pg_stat_statements_reset() TO monitoring;
```

```yaml

global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: 'postgres'
    static_configs:
      - targets: ['postgres_exporter:9187']
    metrics_path: /metrics
    scrape_interval: 30s   # DB metrics don't need sub-15s resolution

The postgres_exporter exposes hundreds of metrics. The most important ones to know by name, because you will use them in Prometheus queries and Grafana panels, are:

```
KEY PROMETHEUS METRICS — postgres_exporter:

pg_up                               → 1 if DB is reachable, 0 if down
                                      Alert: pg_up == 0

pg_stat_database_xact_commit_total  → Counter: committed transactions
pg_stat_database_xact_rollback_total → Counter: rolled back transactions
  TPS = rate(pg_stat_database_xact_commit_total[5m])
  Rollback rate = rate(rollback) / (rate(commit) + rate(rollback))

pg_stat_database_blks_hit_total     → Counter: shared buffer hits
pg_stat_database_blks_read_total    → Counter: disk reads
  Cache hit ratio = blks_hit / (blks_hit + blks_read)

pg_stat_activity_count              → Gauge: connections by state
  {state="active"}                  → Currently executing queries
  {state="idle"}                    → Idle connections
  {state="idle in transaction"}     → Idle in transaction (danger)

pg_replication_lag                  → Gauge: seconds of replication lag
  Alert: pg_replication_lag > 30

pg_stat_statements_seconds_total    → Counter: total exec time per query
pg_stat_statements_calls_total      → Counter: calls per query
  Avg latency = rate(seconds) / rate(calls)

pg_locks_count                      → Gauge: locks by type and mode
pg_stat_database_deadlocks_total    → Counter: deadlocks
  Alert: rate(deadlocks[5m]) > 0

pg_database_size_bytes              → Gauge: database size in bytes
pg_table_bloat_bytes                → Gauge: dead tuple bloat (custom query)
```

For MySQL, **mysqld_exporter** (`github.com/prometheus-community/mysqld_exporter`) follows the same pattern, connecting to MySQL and exposing metrics from `SHOW STATUS`, `SHOW VARIABLES`, `SHOW SLAVE STATUS`, and `information_schema` tables. Key MySQL metrics include `mysql_global_status_queries` (total queries), `mysql_global_status_threads_connected` (connection count), `mysql_slave_status_seconds_behind_master` (replication lag), and `mysql_global_status_innodb_buffer_pool_read_requests` and `mysql_global_status_innodb_buffer_pool_reads` for cache hit ratio.

Grafana is the visualisation layer that transforms raw Prometheus time-series data into the dashboards that let you see your database's health at a glance. Grafana connects to Prometheus as a data source and renders queries written in PromQL (Prometheus Query Language) as graphs, gauges, tables, and alert conditions.

sum(rate(pg_stat_statements_calls_total[5m]))

pg_stat_activity_count{datname="myapp", state="idle"}
pg_stat_activity_count{datname="myapp", state="idle in transaction"}

100 * (
  pg_stat_activity_count{datname="myapp"}
  /
  pg_settings_max_connections
)

# Replication lag in seconds:
pg_replication_lag

# Rollback rate (should be near 0):
rate(pg_stat_database_xact_rollback_total{datname="myapp"}[5m])
/

  + rate(pg_stat_database_xact_rollback_total{datname="myapp"}[5m])
)

# Deadlock rate:
rate(pg_stat_database_deadlocks_total{datname="myapp"}[5m])

# Temp file bytes written (query spills):
rate(pg_stat_database_temp_bytes_total{datname="myapp"}[5m])
```

Prometheus alerting rules belong in a YAML file that Prometheus evaluates. These alerts fire when conditions are met and send notifications via Alertmanager to your chosen channel (PagerDuty, Slack, email).

```yaml
# PROMETHEUS ALERTING RULES — database_alerts.yml:

groups:
  - name: postgresql
    rules:
      # Database is unreachable:
      - alert: PostgreSQLDown
        expr: pg_up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "PostgreSQL is down"
          description: "PostgreSQL on {{ $labels.instance }} has been down for more than 1 minute."

      # Cache hit ratio dropped below 98%:
      - alert: PostgreSQLLowCacheHitRatio
        expr: |
          100 * rate(pg_stat_database_blks_hit_total[5m])
          / (rate(pg_stat_database_blks_hit_total[5m]) + rate(pg_stat_database_blks_read_total[5m]))
          < 98
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "PostgreSQL cache hit ratio below 98%"
          description: "Cache hit ratio is {{ $value }}%. Consider increasing shared_buffers."

      # Replication lag > 30 seconds:
      - alert: PostgreSQLReplicationLag
        expr: pg_replication_lag > 30
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "PostgreSQL replication lag is high"
          description: "Replica {{ $labels.application_name }} is {{ $value }}s behind primary."

      # Connection usage above 80%:
      - alert: PostgreSQLConnectionsHigh
        expr: |
          100 * sum(pg_stat_activity_count) by (instance)
          / pg_settings_max_connections
          > 80
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "PostgreSQL connections approaching limit"
          description: "{{ $value }}% of max connections in use. Risk of connection exhaustion."

      # Any deadlocks in last 5 minutes:
      - alert: PostgreSQLDeadlocks
        expr: rate(pg_stat_database_deadlocks_total[5m]) > 0
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "PostgreSQL deadlocks detected"
          description: "Deadlocks detected. Review transaction ordering in application code."

      # Long-running queries (detected via pg_stat_activity custom metric):
      - alert: PostgreSQLLongRunningQuery
        expr: pg_stat_activity_max_tx_duration{state="active"} > 300
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "Long-running query detected"
          description: "A query has been running for {{ $value }}s."
```

## 9. A Complete Monitoring Runbook

This section is your practical reference for the most common monitoring scenarios — what to look at first, what queries to run, and what actions to take.

```
INCIDENT SCENARIO 1: Application reports slow responses, no errors

Step 1: Open Grafana → check TPS and latency panels.
  → TPS dropped? Or TPS normal but latency spiked?

Step 2: If latency spiked:
  SELECT pid, usename, wait_event_type, wait_event,
         NOW() - query_start AS duration, LEFT(query, 100)
  FROM pg_stat_activity
  WHERE state = 'active' AND wait_event_type IS NOT NULL
  ORDER BY query_start ASC;
  → Find what queries are waiting for (lock? IO? LWLock?)

Step 3: If IO waits: check cache hit ratio.
  SELECT ... FROM pg_stat_database;
  → Cache hit < 99%? → Large table scan may have evicted cache pages.
  → Find the culprit in pg_stat_statements by shared_blks_read DESC.

Step 4: If lock waits: find the blocker.
  → Run the lock wait query from Section 2.6.
  → Kill the blocking transaction if appropriate: pg_cancel_backend(pid)

─────────────────────────────────────────────────────────────────────
INCIDENT SCENARIO 2: Application cannot connect to database

Step 1: Check pg_up in Grafana.
  → 0: Database process is down. Check OS-level PostgreSQL status.
  → 1: Database is up. Connection pool exhausted?

Step 2: Check connection count:
  SELECT state, COUNT(*) FROM pg_stat_activity GROUP BY state;
  → Total near max_connections? Connection pool exhausted.
  → Many idle-in-transaction? Application holding transactions open.

Step 3: Check PgBouncer (if used):
  SHOW POOLS;   -- In psql connected to PgBouncer's admin interface
  → cl_waiting > 0: clients waiting for a pool connection.
  → sv_idle = 0: no idle server connections — all in use.

Step 4: Kill idle-in-transaction connections > 10 minutes:
  SELECT pg_terminate_backend(pid) FROM pg_stat_activity
  WHERE state = 'idle in transaction'
    AND NOW() - state_change > INTERVAL '10 minutes';

─────────────────────────────────────────────────────────────────────
INCIDENT SCENARIO 3: Replica falling behind (replication lag growing)

Step 1: Check replication lag:
  SELECT application_name, replay_lag, state
  FROM pg_stat_replication ORDER BY replay_lag DESC;

Step 2: Check replica's own load:
  → Is the replica overloaded with read queries?
    → Route some read traffic away from this replica temporarily.
  → Is WAL generation rate on primary very high?
    → Check for bulk INSERT/UPDATE/DELETE operations on primary.

Step 3: Check network between primary and replica:
  → write_lag high but flush_lag low? Network is the bottleneck.
  → flush_lag high but replay_lag low? Replica disk is the bottleneck.

Step 4: If replica is stuck (state = 'catchup' for hours):
  → Check replica's PostgreSQL log for conflict or replication errors.
  → May need to rebuild replica from a fresh base backup.

─────────────────────────────────────────────────────────────────────
WEEKLY HEALTH CHECK — Run These Queries Every Week:

1. Top 10 slowest queries (pg_stat_statements by avg_exec_time)
2. Tables with dead tuple % > 10% (pg_stat_user_tables)
3. Tables with sequential scan % > 50% and > 100k rows (missing indexes?)
4. Unused indexes consuming space (pg_stat_user_indexes where idx_scan = 0)
5. Database size growth rate (pg_database_size, trend from Grafana)
6. Deadlock count this week (pg_stat_database)
7. Replication lag P95 this week (from Grafana/Prometheus history)
```

THE FIRST 5 QUERIES TO RUN DURING ANY DB INCIDENT:
  1. SELECT state, COUNT(*) FROM pg_stat_activity GROUP BY state;
     → What is the connection distribution? Any idle-in-txn surge?

  2. SELECT pid, wait_event, wait_event_type, NOW()-query_start, LEFT(query,80)
     FROM pg_stat_activity WHERE state='active' ORDER BY query_start;
     → What are active queries waiting for?

  3. SELECT blks_hit, blks_read, deadlocks, xact_rollback
     FROM pg_stat_database WHERE datname = current_database();
     → Cache hit ratio? Deadlocks? Rollback spikes?

  4. SELECT application_name, replay_lag, state
     FROM pg_stat_replication;
     → How far behind are replicas?

  5. SELECT LEFT(query,80), calls, mean_exec_time, total_exec_time
     FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
     → Which queries are consuming the most total database time?

_The engineers who maintain healthy databases are not the ones who know the most SQL. They are the ones who know their database's normal behaviour so thoroughly that deviations are immediately visible. They have built the habit of reading dashboards before incidents rather than only during them. They know their P99 latency on a Tuesday morning, their peak TPS on a Monday after a release, and their typical cache hit ratio across seasons and traffic patterns._

_Start with the five incident queries. Memorise them. Then build the Grafana dashboard. Set the six alerts. And then — this is the part most people skip — watch the dashboard for two weeks during normal operation. Learn what normal looks like. Because the day something goes wrong, that knowledge is worth more than any runbook._

_Observability is not a feature you add to a system. It is a practice you maintain about a system. And like all practices, it compounds — the engineer who has watched their database metrics for a year will diagnose incidents in minutes that take the inexperienced engineer hours._
