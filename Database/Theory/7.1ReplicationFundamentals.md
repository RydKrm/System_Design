# Replication Fundamentals

### A Deep, Conceptual Journey from the Ground Up

> _Replication is not a backup strategy. It is not a performance trick. It is the fundamental acknowledgment that a single machine will eventually fail, and that your data must outlive any single machine._

---

## Preface: The Single Point of Failure

Every database that runs on a single server is, by definition, one hardware failure away from being completely unavailable. A spinning disk develops a bad sector. A power supply fails. A memory module starts flipping bits. A kernel bug causes a panic. A network switch loses its configuration. A datacenter floods. An overzealous engineer runs `DROP TABLE` in production.

None of these are hypotheticals. They happen. The question is never "will my database server fail?" — it is "when it fails, what happens to my application, and what happens to my data?"

A system with no replication has only one answer to both questions: the application goes down, and the data is at risk. The application goes down until the hardware is repaired or replaced and the database is restored from backup — which might take hours, or days. The data is at risk because the most recent backup might be hours old, meaning hours of real user activity could be permanently lost.

Replication changes both answers. It is the practice of maintaining one or more copies of the database — on separate machines, in separate racks, in separate datacenters, on separate continents — so that the failure of any single component does not spell the end of either availability or data. It is the engineering acknowledgment that redundancy is not waste; it is the cost of reliability.

This guide explores why replication exists, how it works at the conceptual level, the fundamental trade-off between synchronous and asynchronous approaches, and the precise language that the industry uses to talk about recovery goals — RPO and RTO. These concepts form the foundation for understanding any specific replication technology, from PostgreSQL streaming replication to MySQL Group Replication to distributed systems like Cassandra or CockroachDB.

## Chapter 1: Why Replicate — The Three Pillars

### Replication Is Never About Just One Thing

Replication serves three distinct purposes, and it is important to understand all three separately — because each one has different requirements, different trade-offs, and different design implications. Engineers sometimes deploy replication for one reason without fully appreciating the other two, and end up with a system that is better in one dimension but still fragile in the others.

The three pillars are: **durability** (protecting data from loss), **read scaling** (handling more query traffic), and **high availability** (keeping the system online through failures). A properly architected replication strategy serves all three simultaneously, but the degree of emphasis on each shapes the specific design.

---

### Pillar 1: Durability — Protecting Data from Loss

**Durability** in the context of replication means that committed data survives not just a process crash or power failure on a single machine — which WAL and fsync already handle — but the complete physical destruction or loss of an entire server, disk array, or datacenter.

The WAL and fsync guarantee we discussed in the ACID chapter protect you from software crashes and power loss on a single machine. But they do not protect you from:

- A disk failure that corrupts or destroys the data files and the WAL simultaneously (a bad disk controller can corrupt both)
- A fire or flood in the datacenter that physically destroys all storage
- A ransomware attack that encrypts all local files including database files and WAL
- A catastrophic hardware failure that takes out multiple components simultaneously
- Human error at the infrastructure level — accidentally deleting the volume, reformatting the disk, terminating the wrong cloud instance

Replication protects against all of these by ensuring that committed data exists on at least two physically separate machines. "Physically separate" is the crucial phrase. Two replicas on the same rack share the same power circuit, the same network switch, and are vulnerable to the same physical events. Two replicas in different datacenters in different cities share almost nothing — they are as independent as two machines can be.

```
Durability Through Geographic Separation:

  Single Server:
  ┌─────────────────────────────────────────┐
  │  Datacenter A (New York)                │
  │  ┌───────────────┐                      │
  │  │  PostgreSQL   │ ← single copy of data│
  │  │  Primary      │                      │
  │  └───────────────┘                      │
  │                                         │
  │  If datacenter floods: DATA LOST        │
  └─────────────────────────────────────────┘

  Replicated Across Datacenters:
  ┌─────────────────────────────────────────┐
  │  Datacenter A (New York)                │
  │  ┌───────────────┐                      │
  │  │  PostgreSQL   │ ── WAL stream ──►    │
  │  │  Primary      │                      │
  │  └───────────────┘                      │
  └─────────────────────────────────────────┘
                  │ continuous replication
                  ▼
  ┌─────────────────────────────────────────┐
  │  Datacenter B (Virginia)                │
  │  ┌───────────────┐                      │
  │  │  PostgreSQL   │ ← identical copy     │
  │  │  Replica      │                      │
  │  └───────────────┘                      │
  │                                         │
  │  If Datacenter A floods:                │
  │  Datacenter B has all committed data.   │
  │  Promote replica → service continues.  │
  └─────────────────────────────────────────┘
```

The durability pillar is about **protecting the past** — ensuring that every transaction that was committed and acknowledged to a user or an application is permanently preserved, regardless of what physical disasters befall the hardware that received that commit.

---

### Pillar 2: Read Scaling — Distributing Query Load

**Read scaling** is the practice of directing read-only queries to replica servers, reducing the load on the primary server and increasing the system's total read throughput.

The motivation is straightforward: for many applications, the vast majority of database operations are reads — a typical web application might be 80–95% reads and only 5–20% writes. If all reads hit the primary server, the primary is doing far more work than necessary, even though replicas are sitting idle. Replicas that are maintained for durability reasons are, from a query perspective, wasted capacity.

Read scaling allows the total read capacity of the system to scale horizontally: add more replicas, get more read throughput. In theory, you can serve an order of magnitude more read traffic with ten replicas than with one primary — each replica handles one-tenth of the read traffic, and the primary handles only writes and the most latency-sensitive reads.

```
Read Scaling Architecture:

  Without Read Replicas:
  ┌──────────────────────────────────────────────────────────┐
  │                   Application                            │
  │  All reads + All writes ──────────────────────────────►  │
  └──────────────────────────────┬───────────────────────────┘
                                 │
                                 ▼
                      ┌──────────────────┐
                      │  Primary DB      │
                      │  (overloaded —   │
                      │  reads + writes  │
                      │  competing)      │
                      └──────────────────┘

  With Read Replicas:
  ┌──────────────────────────────────────────────────────────┐
  │                   Application                            │
  │  Writes ─────────────────────────────────────────────►   │
  │  Reads (product listings) ────────────────────────────►  │
  │  Reads (user profiles) ───────────────────────────────►  │
  └────┬────────────────────┬──────────────┬─────────────────┘
       │                    │              │
       ▼                    ▼              ▼
  ┌──────────┐       ┌──────────┐  ┌──────────┐
  │ Primary  │◄─WAL─►│ Replica 1│  │ Replica 2│
  │ (writes  │       │ (reads)  │  │ (reads)  │
  │ + some   │       └──────────┘  └──────────┘
  │ reads)   │
  └──────────┘

  Read capacity: 3× (primary + 2 replicas for reads)
  Write capacity: unchanged (all writes still go to primary)
```

But read scaling comes with an important caveat: **replicas may serve stale data**. Because replication has latency — even milliseconds — a replica's data is always slightly behind the primary. A user who writes a record and immediately reads it back might, if their read is directed to a replica, not see the record they just wrote. This is called **replication lag**, and managing it is a central challenge of read scaling architectures.

The application must decide, for each read operation: does this read need to see the absolute latest committed data (in which case it must go to the primary), or is slightly stale data acceptable (in which case it can go to a replica)?

```
Replication Lag and Stale Reads:

  Timeline:
    T=0.000: User writes: "INSERT INTO posts (title) VALUES ('Hello')"
             → Primary commits.
             → WAL record created.

    T=0.001: WAL record sent to Replica 1.
    T=0.002: Replica 1 applies the WAL record.

    T=0.001: User's next request reads: "SELECT * FROM posts ORDER BY id DESC LIMIT 1"
             → Query routed to Replica 1.
             → Replica 1 has NOT YET applied the WAL record.
             → User does NOT see their own post. ← Stale read.

    T=0.002: Query routed to Replica 1 now.
             → Replica 1 has applied the WAL record.
             → User sees their post. ← Fresh read.

  The 1ms replication lag caused a stale read.
  For most applications (product listings, analytics, dashboards):
    → Stale reads are acceptable. Route to replicas freely.

  For post-write reads (profile updates, shopping cart):
    → Must read from primary, or use "read-your-writes" consistency.
```

### Pillar 3: High Availability — Surviving Failures Without Downtime

**High availability (HA)** is the property of a system that continues to function — serving requests, accepting writes — even when components fail. In a non-replicated database, any failure of the primary server causes complete unavailability. In a replicated system with HA configured, a failure of the primary triggers a **failover** — one of the replicas is promoted to become the new primary, and the system continues operating, often within seconds.

High availability is fundamentally about **reducing downtime**. The metric for how long the system is down is called **availability**, expressed as a percentage of time the system is operational:

```
Availability and the "Nines":

  Availability  │  Annual Downtime    │  Description
  ──────────────┼─────────────────────┼──────────────────────────────
  90%           │  36.5 days/year     │  No serious system
  99%           │  87.6 hours/year    │  Acceptable for internal tools
  99.9%         │  8.76 hours/year    │  "Three nines" — decent baseline
  99.99%        │  52.6 minutes/year  │  "Four nines" — good production
  99.999%       │  5.26 minutes/year  │  "Five nines" — carrier grade
  99.9999%      │  31.5 seconds/year  │  Extremely rare, very expensive

  A non-replicated database:
    Every planned maintenance requires downtime → ~99% at best
    Any hardware failure → hours of downtime → well below 99%

  A replicated database with automatic failover:
    Failover time: 10–30 seconds → targets 99.99%
    Zero-downtime rolling upgrades possible → targets 99.999%
```

The HA pillar is about **protecting the future** — ensuring that when a failure occurs (and it will), the system recovers fast enough that users either do not notice or experience only a brief interruption.

High availability requires not just replication but also:

**Automatic failure detection:** Something must notice that the primary has failed. This is harder than it sounds — network partitions can make a healthy primary look unavailable from some vantage points.

**Automatic promotion:** Once a replica is chosen to become the new primary, the promotion must happen without manual intervention. Manual failover takes minutes; automatic failover takes seconds.

**Client reconnection:** Application connections to the old primary must be redirected to the new primary. This requires either a connection endpoint that always points to the current primary (a virtual IP or a load balancer) or smart client drivers that can detect the new primary through service discovery.

```
High Availability Failover Sequence:

  Normal operation:
    Primary ← writes from all app servers
    Replica ← WAL stream from Primary

  T=0: Primary server fails (hardware failure, OOM kill, etc.)

  T=1s: Monitoring system detects: Primary is unresponsive.
        (health checks: ping, query "SELECT 1", OS-level checks)

  T=5s: Failover decision: Replica is the most up-to-date standby.
        Promote Replica to Primary.
        Replica stops receiving WAL (it is now writing, not reading WAL).
        Replica begins accepting write connections.

  T=10s: Virtual IP or DNS entry updated to point to new Primary.
         Load balancer health checks see new Primary is live.

  T=15s: Application connections from app servers are redirected
         to new Primary (either by reconnect logic or load balancer).

  T=15s onward: System is fully operational on new Primary.
         Old Primary (if recoverable) becomes a new Replica.

  Total downtime: ~15 seconds.
  Data lost: depends on replication mode (see Chapter 2).
```

---

### The Three Pillars Together

The three pillars are not mutually exclusive — a well-designed replication architecture serves all three simultaneously. But they do pull in different directions when it comes to implementation choices:

```
How the Three Pillars Pull in Different Directions:

  DURABILITY demands:
  → Multiple copies, geographically separated
  → Synchronous replication (ensures replicas have the data before commit)
  → Strong durability guarantees trump performance

  READ SCALING demands:
  → Many replicas (more replicas = more read capacity)
  → Asynchronous replication (replicas need not be perfectly in sync)
  → Performance and throughput over strict consistency

  HIGH AVAILABILITY demands:
  → At least one replica, ideally in a separate failure domain
  → Fast replication lag (replicas need to be close to current)
  → Automated failover and detection

  The tension:
  More replicas (read scaling) → more replication overhead (durability cost)
  Synchronous replication (durability) → higher write latency (performance cost)
  Geographic distribution (durability) → higher replication lag (HA cost)

  Every replication design is a negotiation among these three.
```

## Chapter 2: Synchronous vs. Asynchronous Replication

### The Most Important Trade-off in All of Replication

If you had to identify the single most consequential design decision in any replication architecture, it is this one: **synchronous or asynchronous replication?** Everything else — topology, conflict resolution, lag management — is secondary to this fundamental question. And the answer is not universally one or the other; it depends on what you value more: durability or performance.

The question is: when does the primary consider a transaction committed and return "success" to the application? Does it wait until at least one replica has confirmed it received and persisted the data? Or does it commit locally and return success immediately, letting the replica catch up asynchronously?

---

### Asynchronous Replication: Performance First

In **asynchronous replication**, the primary commits the transaction, writes the WAL to its local disk, calls `fsync`, and immediately returns "success" to the application. It then sends the WAL record to replicas as a background task — but it does not wait for any acknowledgment from the replicas before returning success.

From the application's perspective, the transaction is committed. From the replica's perspective, it might not know about this transaction yet. There is a window of time — however brief — during which the primary has committed data that the replica does not have.

```
Asynchronous Replication — Timeline:

  T=0ms: Application: COMMIT;
  T=0ms: Primary: Write WAL record to local disk. fsync. ← LOCAL COMMIT
  T=0ms: Primary → Application: "Commit successful." ← RETURNS IMMEDIATELY
  T=1ms: Primary → Replica: Send WAL record (background stream)
  T=2ms: Replica: Receive WAL record.
  T=3ms: Replica: Apply WAL record. Write to local disk.

  Between T=0ms and T=3ms:
    Primary: committed, durable locally.
    Replica: does NOT have this transaction.
    If Primary dies at T=1ms: the transaction is LOST.
    (WAL record was sent but Replica had not yet received or applied it.)

  Application-perceived commit latency: ~0ms (just local fsync)
  Durability risk window: 1–5ms (typical) to seconds (if replica is lagging)
```

**The performance advantage of async replication is real and significant.** The application does not pay the round-trip latency to a remote replica on every write. For replicas in different datacenters, that round-trip might be 5ms, 20ms, or 100ms depending on geographic distance. With async replication, writes are as fast as they can be on the local primary — typically sub-millisecond for simple transactions. For systems with high write throughput requirements, this is the only viable mode.

**The durability risk of async replication is also real.** If the primary fails before the replica has applied the WAL records, those transactions are lost. They were acknowledged to the application, they were committed on the primary, and they are gone. This is not a theoretical risk — it is the expected behavior of async replication when the primary fails while the replica is lagging. The amount of data at risk at any moment is called the **replication lag**, and it can range from milliseconds (in a well-tuned local cluster) to minutes or more (in a degraded or high-latency cross-datacenter setup).

```
Asynchronous Replication — The Failure Scenario:

  Primary has processed: Transactions 1, 2, 3, 4, 5
  Replica has received:  Transactions 1, 2, 3       ← lag: 2 transactions

  Primary fails catastrophically.
  Failover: Replica is promoted to Primary.

  Result:
  Transactions 1, 2, 3: SAFE (on both primary and replica)
  Transactions 4, 5: LOST (primary had them, replica did not)

  Users who committed transactions 4 and 5 received "success."
  Their data is gone. The database does not know it ever happened.
  From the new primary's perspective, those transactions never existed.
```

This data loss on failover is the defining characteristic and the central limitation of asynchronous replication. It is acceptable in many systems — if you are replicating a product catalog or a logging system, losing a few seconds of data on a primary failure is tolerable. It is completely unacceptable in financial systems, medical records, or any system where the application's "commit successful" must be an absolute guarantee.

---

### Synchronous Replication: Durability First

In **synchronous replication**, the primary does not return "success" to the application until at least one replica has confirmed that it received and persisted the WAL record. The primary waits — holds the application's commit call open — until it gets this acknowledgment. Only then does it complete the commit from the application's perspective.

```
Synchronous Replication — Timeline:

  T=0ms:  Application: COMMIT;
  T=0ms:  Primary: Write WAL record to local disk. fsync.
  T=0ms:  Primary → Replica: Send WAL record. ← WAITS FOR ACK
  T=5ms:  Replica: Receive WAL record.
  T=5ms:  Replica: Write WAL record to local disk. fsync.
  T=5ms:  Replica → Primary: "WAL record received and persisted." ← ACK
  T=5ms:  Primary → Application: "Commit successful." ← RETURNS

  The application waited 5ms for the remote replica to acknowledge.
  But now: if Primary dies at T=5ms, the Replica has the data.
  ZERO DATA LOSS is guaranteed.

  Application-perceived commit latency: 5ms+ (one network round trip minimum)
  Durability risk window: ZERO (data is on at least 2 machines before ACK)
```

**The durability guarantee of synchronous replication is absolute within its defined scope.** If the system is configured to require acknowledgment from one synchronous replica, then at the moment "commit successful" is returned to the application, the data exists on at least two separate machines. Even if the primary fails the next nanosecond, the replica has the data. Failover results in zero data loss.

**The performance cost is real and inescapable.** Every write must wait for at least one network round-trip to a replica. If the replica is in the same datacenter, this might be 0.5–2ms of added latency per transaction. If the replica is in a different city or country, the round-trip is determined by the speed of light through fiber — typically 5ms (same country), 20ms (same continent), or 80–200ms (cross-continental). For a system doing thousands of transactions per second, even 5ms of added latency per write is a significant throughput reduction.

```
Synchronous Replication — Geographic Latency Impact:

  Primary location: New York
  Synchronous replica locations and round-trip latencies:

  New Jersey (same datacenter campus):   ~0.5ms per commit
  Virginia (AWS us-east-1):              ~2ms   per commit
  Chicago:                               ~8ms   per commit
  London:                                ~70ms  per commit
  Tokyo:                                 ~170ms per commit
  Sydney:                                ~200ms per commit

  At 10,000 writes/second and 70ms sync latency (London replica):
  The primary can commit at most: 1,000ms / 70ms = ~14 writes/second
  per connection (serial writes). Parallelism helps, but the latency
  fundamentally limits throughput.

  This is the speed-of-light tax on synchronous cross-datacenter replication.
  It is physics, not a bug. It cannot be optimized away.
```

### The Hybrid Approach: Semi-Synchronous Replication

Most production systems use neither pure synchronous nor pure asynchronous replication across the board. Instead, they use a **hybrid approach** that applies synchronous replication where durability is non-negotiable and asynchronous replication for additional replicas where read scaling is the goal.

PostgreSQL calls this **synchronous commit with multiple standby servers**:

```
PostgreSQL Hybrid Replication Configuration:

  synchronous_standby_names = 'FIRST 1 (replica_dc1, replica_dc2)'
  -- "Wait for acknowledgment from at least 1 of these standby servers"
  -- (trying replica_dc1 first, then replica_dc2)

  synchronous_commit = on   -- default: wait for sync replica
  -- OR --
  synchronous_commit = remote_write  -- wait for replica to receive but not fsync
  -- OR --
  synchronous_commit = remote_apply  -- wait for replica to apply (not just receive)

  Topology:
  ┌──────────────────────────────────────────────────────┐
  │  Primary (New York)                                  │
  │  synchronous: replica_dc1 (New Jersey) — 1ms round  │
  │  asynchronous: replica_dc2 (Ireland) — 70ms round   │
  │  asynchronous: replica_dc3 (Singapore) — 170ms round│
  └──────────────────────────────────────────────────────┘

  Result:
  Write latency: +1ms (New Jersey sync acknowledgment only)
  Zero data loss: guaranteed (data is on Primary + replica_dc1 before ACK)
  Read scaling: replica_dc2 and replica_dc3 serve reads globally
  Geographic durability: data in 4 locations across 3 continents
  Failover: replica_dc1 can be promoted instantly with zero data loss
```

This is the architecture that major cloud providers use for their managed PostgreSQL services (AWS RDS Multi-AZ, Google Cloud SQL HA, Azure Database for PostgreSQL HA). One synchronous replica in a nearby availability zone ensures zero data loss on primary failure, while additional asynchronous replicas serve read traffic or provide geographic coverage.

### The Synchronous Standby Failure Problem

Synchronous replication introduces a new failure mode: **what happens if the synchronous replica becomes unavailable?**

In strict synchronous mode, if the synchronous standby goes offline, writes block indefinitely — the primary cannot commit because it cannot get the required acknowledgment. The system trades write availability for durability. This is the correct behavior if you are unwilling to accept any data loss, but it means a replica failure causes a write outage.

PostgreSQL handles this with configurable behavior:

```
PostgreSQL Synchronous Commit Behavior on Replica Loss:

  synchronous_commit = on (default strict behavior):
    If synchronous replica is unavailable:
    → Writes BLOCK waiting for replica to return.
    → No data loss risk, but write availability is compromised.
    → Writes resume when replica reconnects and catches up.

  synchronous_commit = local (fallback to async on replica loss):
    If synchronous replica is unavailable:
    → Primary commits locally (asynchronously).
    → Writes continue. Write availability is preserved.
    → Data loss risk exists during replica-down period.
    → Resumes synchronous mode when replica reconnects.

  The operator must choose: which is more important?
  → Zero data loss at the cost of possible write unavailability
     (use synchronous_commit = on)
  → Write availability at the cost of possible data loss on failure
     (use synchronous_commit = local as fallback)

  This is the fundamental CAP theorem trade-off in practice:
  Consistency vs. Availability under Partition (network failure = partition).
```

## Chapter 3: RPO and RTO — The Language of Recovery

### Why We Need Precise Language

Before replication, a database failure had only one outcome: downtime and potential data loss. The only questions were "how long until we are back up?" and "how much data did we lose?" These are important questions, but without precise answers, they cannot drive engineering decisions. "We will be back up soon" and "we might lose some data" are not acceptable design specifications.

The industry has developed precise terms for both quantities: **RPO** for data loss and **RTO** for recovery time. These terms transform vague disaster scenarios into measurable, designable engineering objectives. They are the language of reliability engineering, and every replication architecture should be designed against explicit RPO and RTO targets.

---

### RPO — Recovery Point Objective

**RPO (Recovery Point Objective)** is the maximum amount of data loss — measured in time — that is acceptable in the event of a failure. It answers the question: "When we recover from a failure, how far back in time can we tolerate our data being from the moment of failure?"

An RPO of zero means no data loss is acceptable — every committed transaction must survive any failure. An RPO of one hour means the organization accepts losing up to one hour of committed transactions in a worst-case failure. An RPO of one day means that as long as last night's backup exists, data loss of up to 24 hours is acceptable.

RPO is not about how long recovery takes — that is RTO. RPO is purely about **what data is at risk of permanent loss**.

```
RPO Visualized on a Timeline:

  Past ──────────────────────────────────────────────────► Present
                                                   ↑
                                            System fails here

  RPO = 0 (synchronous replication):
       No data at risk. Replica has every committed transaction.
       ────────────────────────────────────────────────────────►
                                                   ↑
                                        Replica is here (same as primary)

  RPO = 5 minutes (async replication, 5min lag):
       Last 5 minutes of commits are at risk.
       ───────────────────────────────────────────────────────►
                                               ↑
                                    Replica is here (5 min behind)
       ◄────── 5 min data at risk ─────────────────────────────

  RPO = 24 hours (daily backups, no replication):
       Up to 24 hours of commits are at risk.
       ───────────────────────────────────────────────────────►
       ↑
  Last backup is here (yesterday)
       ◄──────────── up to 24 hours at risk ──────────────────

  The RPO defines the maximum gap between "what the replica (or backup) has"
  and "what the primary had at the moment of failure."
```

RPO is determined by your replication strategy:

```
Replication Strategy and RPO:

  Strategy                          │ Typical RPO
  ──────────────────────────────────┼──────────────────────────────
  Synchronous replication           │ 0 seconds (zero data loss)
  Asynchronous (same datacenter)    │ Milliseconds to seconds
  Asynchronous (cross-datacenter)   │ Seconds to minutes
  Point-in-time recovery (backups)  │ Minutes to hours (backup interval)
  Daily backups only                │ Up to 24 hours
  No backup strategy                │ Potentially everything (infinite RPO)
```

### Setting the Right RPO

RPO is not a technical decision — it is a **business decision** that engineering must then implement. The correct question to ask is: "How much data loss is acceptable, and what is the cost of data loss versus the cost of preventing it?"

For a financial trading system processing millions of dollars of transactions per second, even one second of RPO means potentially millions of dollars of unrecoverable data — the RPO must be zero, and synchronous replication is non-negotiable regardless of the performance cost.

For a social media feed where posts are cached on the client and re-sent on retry, losing a few seconds of data on a failure might mean a small number of posts need to be re-submitted by users — an RPO of 5–30 seconds is probably acceptable.

For a data analytics pipeline that processes events from other systems and can re-process from the event source if needed, the database might have a high RPO (hours) because the source data is preserved elsewhere.

```
RPO Decision Framework:

  What data flows through this system?
  │
  ├── Financial transactions, medical records, legal data
  │   → RPO = 0. Every commit is irreplaceable.
  │     → Synchronous replication mandatory.
  │
  ├── User-generated content (posts, comments, uploads)
  │   → RPO = seconds to minutes acceptable for most cases.
  │     → Asynchronous replication to nearby standby.
  │     → Consider: can the user re-submit if their post is lost?
  │
  ├── Application state derived from other systems
  │   (e.g., analytics tables populated from event streams)
  │   → RPO = hours may be acceptable.
  │     → Data can be rebuilt by reprocessing the source events.
  │     → Daily backups may be sufficient.
  │
  ├── Ephemeral / cache data
  │   → RPO = infinite acceptable.
  │     → Data can be regenerated from primary source.
  │     → No replication needed.
  │
  Business cost per unit of data loss:
    High ($$$) → Lower RPO target → Synchronous replication
    Low ($)    → Higher RPO acceptable → Async or backups only
```

### RTO — Recovery Time Objective

**RTO (Recovery Time Objective)** is the maximum amount of time the system can be unavailable — measured from the moment of failure to the moment the system is fully operational again. It answers the question: "When a failure occurs, how long is acceptable before the system is back up and serving requests?"

RTO and RPO are independent. A system can have a low RPO (almost no data loss) but a high RTO (takes hours to bring back online after data is recovered). Or it can have a low RTO (back online in seconds) but a higher RPO (some data was lost during the fast failover). Or — with the right architecture — it can have both low RPO and low RTO simultaneously, at the cost of significant infrastructure investment.

```
RTO Visualized on a Timeline:

  System fails
  ↓
  ─────────────────────────────────────────────────────────────────
  │  DETECTION   │  DECISION   │  RECOVERY   │  VERIFICATION      │
  │  Is it down? │  What do    │  Restore or │  Is it working?    │
  │  (10s-5min)  │  we do?     │  failover   │  (1-10min)         │
  │              │  (10s-2min) │  (10s-hours)│                    │
  ─────────────────────────────────────────────────────────────────
                                              ↑
                                        System restored
  ◄──────────────────── RTO ──────────────────────────────────────►

  RTO = time from failure to restoration of full service.

  Components of RTO:
  1. Detection time: how quickly is the failure discovered?
     (automated monitoring: seconds; manual discovery: minutes to hours)
  2. Decision time: who decides what to do? automated or manual?
     (automated failover: seconds; manual process: minutes)
  3. Recovery time: how long does the actual recovery take?
     (failover to hot standby: seconds; restore from backup: hours)
  4. Verification time: how long to confirm system is healthy?
     (automated health checks: seconds; manual testing: minutes)
```

### What Drives RTO

RTO is determined by the recovery mechanism:

```
Recovery Mechanism and RTO:

  Mechanism                        │ Typical RTO
  ─────────────────────────────────┼────────────────────────────────────
  Automatic failover to hot standby│ 15–60 seconds
  (replica promoted automatically) │ (detection + promotion + DNS update)
  ─────────────────────────────────┼────────────────────────────────────
  Manual failover to warm standby  │ 5–30 minutes
  (human decides, scripts run)     │ (human response + runbook execution)
  ─────────────────────────────────┼────────────────────────────────────
  Restore from recent backup       │ 30 minutes to several hours
  (backup + WAL replay to current) │ (depends on backup size and WAL volume)
  ─────────────────────────────────┼────────────────────────────────────
  Restore from daily backup        │ Several hours to a full day
  (cold restore from previous day) │ (large backup + full day of WAL replay)
  ─────────────────────────────────┼────────────────────────────────────
  Rebuild from scratch             │ Hours to days
  (no backup, reconstruct from     │ (depends on data volume and source)
  application logs or source data) │
```

### The Business Cost of RTO

Like RPO, RTO should be driven by business requirements. The key question is: "What does one minute (or one hour, or one day) of downtime cost the business?"

For an e-commerce site, downtime during peak hours might mean thousands of lost sales per minute. The business cost of a 10-minute RTO might be $50,000 in lost revenue — justifying significant investment in automatic failover infrastructure.

For an internal analytics dashboard used by 20 employees, a 4-hour RTO might be entirely acceptable — employees can do other work during the outage, and the cost of building automatic failover infrastructure exceeds the productivity cost of the occasional hours-long outage.

```
RTO Decision Framework:

  Revenue impact per minute of downtime?
  │
  ├── High ($thousands+/minute) — e-commerce, financial services, SaaS
  │   → RTO target: < 60 seconds
  │   → Requires: hot standby + automatic failover + virtual IP / DNS
  │   → Investment: significant (dedicated standby + monitoring + automation)
  │
  ├── Moderate ($hundreds/minute) — B2B tools, internal-facing services
  │   → RTO target: < 30 minutes
  │   → Requires: warm standby + semi-automated failover runbook
  │   → Investment: moderate (standby + monitoring)
  │
  ├── Low ($tens/minute) — internal tools, dev environments
  │   → RTO target: < 4 hours
  │   → Requires: regular backups + restore procedure
  │   → Investment: minimal (automated backups only)
  │
  Contractual SLA obligations?
  └── SLA: 99.99% uptime = 52 minutes/year downtime budget
      Any single incident exceeding 52 minutes violates the SLA.
      → RTO must be < ~10 minutes to stay within annual budget
        while allowing for occasional incidents.
```

### Measuring Current RPO and RTO

RPO and RTO are not just targets — they should be measured and verified:

```
Measuring RPO in a Live Replication Setup:

  Replication lag = current RPO (approximately)

  PostgreSQL: measure replication lag from primary:
  SELECT
      client_addr,
      application_name,
      state,
      -- WAL location on primary
      pg_current_wal_lsn() AS primary_lsn,
      -- WAL location replica has written to its disk
      write_lsn,
      -- WAL location replica has flushed to disk (fsync'd)
      flush_lsn,
      -- WAL location replica has applied (replayed into data files)
      replay_lsn,
      -- Lag expressed as time (PostgreSQL 10+)
      write_lag,
      flush_lag,
      replay_lag
  FROM pg_stat_replication;

  -- Lag in bytes (another view):
  SELECT
      application_name,
      pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
  FROM pg_stat_replication;

  -- If replay_lag = 3 seconds → current RPO ≈ 3 seconds
  -- If replay_lag = 0 → current RPO ≈ 0 (synchronous or very fast async)

Measuring RTO: Game Day / Chaos Engineering
  The only reliable way to measure RTO is to practice the actual failover:
  - Kill the primary (in a test environment, or during planned maintenance)
  - Time how long until the system is fully operational on the replica
  - Identify bottlenecks: detection time? promotion time? DNS propagation?
  - Optimize each component and re-measure

  Organizations with serious RTO requirements run "game days" —
  planned, rehearsed failure drills that validate the RTO can be met.
  An untested failover procedure is not a procedure — it is a hope.
```

## Chapter 4: Putting It Together — A Replication Architecture Decision

### From Requirements to Architecture

Armed with the understanding of why we replicate, how synchronous and asynchronous replication differ, and what RPO and RTO mean, we can now design a replication architecture for a specific set of requirements.

**Scenario: A SaaS B2B Platform**

The platform has the following requirements:

- Application serves 500 business customers who use it during business hours
- Revenue impact of downtime: ~$5,000/minute
- Financial transaction data (subscription billing, invoices) is critical
- User activity data (page views, feature usage events) is important but can be regenerated from application logs
- SLA commitment: 99.99% uptime (52 minutes downtime budget per year)
- Team size: 5 engineers, not a 24/7 on-call rotation

```
Requirements Analysis:
  Financial data:       RPO = 0, any data loss is a compliance issue
  Activity data:        RPO = 5 minutes acceptable (regenerable from logs)
  SLA (99.99%):         52 min/year budget → RTO target < 30 seconds
                        (allows a few incidents per year without breach)
  Team size:            Automated failover required (no 24/7 on-call for manual)
  Revenue impact:       $5k/minute → invest significantly in low RTO

Architecture Decision:

  Primary (us-east-1a AZ):
    PostgreSQL with WAL enabled
    synchronous_standby_names = 'FIRST 1 (hot_standby)'

  Hot Standby (us-east-1b AZ):  ← synchronous, same region
    Receives WAL synchronously.
    Automatically promoted on primary failure.
    RPO: 0 (synchronous replication)
    RTO: 15–30 seconds (automatic failover via Patroni or RDS Multi-AZ)
    Network latency: ~1ms (same region, different AZ)
    Write latency overhead: +1ms per commit (acceptable)

  Read Replica (us-west-2):     ← asynchronous, different region
    Receives WAL asynchronously.
    Serves read traffic from west-coast users.
    Provides geographic disaster recovery.
    RPO: seconds (async lag typically 1–5 seconds across regions)
    Cannot promote automatically to primary without potential data loss.

  Backup (S3, daily + WAL archiving):
    Daily base backups to S3.
    Continuous WAL archiving to S3.
    Enables point-in-time recovery to any second in the past 30 days.
    RPO: 0 (using WAL replay to the moment of failure)
    RTO: 2–4 hours (backup restore + WAL replay for point-in-time)
    Use case: recovery from logical corruption (accidental DROP TABLE)
              where the replica also has the corruption.

  Summary:
    Normal operation: Primary + Sync Hot Standby + Async Read Replica
    Primary failure:  Automatic failover to Hot Standby (RTO: 30s, RPO: 0)
    Region failure:   Manual promotion of Read Replica (RTO: 30min, RPO: seconds)
    Logical corruption: Point-in-time recovery from backup (RTO: hours, RPO: 0)
```

## Epilogue: Replication Is an Act of Humility

There is a certain engineering humility required to build a replicated system. You are acknowledging, in concrete and expensive infrastructure, that your primary database server will fail. Not might fail — will fail. You do not know when, you do not know how, but you know it with as much certainty as any engineering fact can be known.

Building replication is the practice of deciding, in advance and without urgency, what happens when that failure occurs. RPO is your decision about how much of your users' trust you are willing to risk — because every committed transaction that is lost is a promise you made to a user that you could not keep. RTO is your decision about how much of your users' time you are willing to consume — because every minute of downtime is minutes of productivity, revenue, and goodwill spent.

The systems that handle failures gracefully are not the ones that were lucky. They are the ones whose engineers sat down before any failure occurred and asked: "When this breaks — and it will — what should happen?" They chose a replication mode. They set an RPO. They set an RTO. They built the architecture to meet those targets. They tested it. And then, when the failure came, it was not a crisis — it was a rehearsed procedure executing exactly as designed.

That is the engineering discipline that replication represents. Not the avoidance of failure, but the mastery of it.
