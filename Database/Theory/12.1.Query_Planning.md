> _"The query planner is the most intelligent piece of software in your database. It reads your SQL — a declaration of what you want — and invents a program for how to get it. Getting that invention right, every time, for every possible combination of data and hardware, is the hardest problem in database engineering."_ — Every database researcher who has stared at a bad query plan at 2 AM

## A Letter from Your DBA Mentor Before We Begin

You have written thousands of SQL queries in your career. `SELECT`, `JOIN`, `WHERE`, `GROUP BY` — you know the vocabulary. But here is something most developers never think about: **the SQL you write is not what the database executes.** Not directly.

When you write `SELECT * FROM orders JOIN customers ON orders.customer_id = customers.id WHERE customers.country = 'BD'`, you are making a declaration. You are saying "I want the orders belonging to customers from Bangladesh." You are saying nothing about how to find them. Should the database scan all orders and look up each customer? Should it find the matching customers first, then look for their orders? Should it use an index on `country`? What if there are a million orders but only fifty customers from Bangladesh?

Every time you run a query, the **query planner** answers these questions. It considers dozens or hundreds of possible execution strategies, estimates the cost of each one, and chooses the plan it believes will be fastest. Get this right and your query runs in 2 milliseconds. Get it wrong and it runs for 45 seconds — on the exact same data, with the exact same query, just a different plan.

Understanding the query planner is what separates engineers who add an index and hope for the best from engineers who read an execution plan, understand exactly why the planner made each decision, and know precisely what to change to get a better one. It is the difference between treating the database as a black box and treating it as a system you deeply understand.

In this guide, we will study the query planner from the inside out — the statistics it uses to make decisions, the algorithms it uses to search for the best plan, the special modes it falls back to under complexity, and the modern features (parallel execution and JIT compilation) that give it superpowers on modern hardware. By the end, `EXPLAIN ANALYZE` output will be a language you read fluently.

## 1. How the Query Planner Works — The Big Picture

Before diving into the individual components of the planner, you need a clear mental model of the entire process — from the SQL string you write to the execution plan the database runs. This pipeline has four distinct stages, and understanding what happens at each stage is the foundation for understanding why plans are good or bad.

**Stage 1 — Parsing.** The raw SQL string is parsed by a lexer and parser into an **abstract syntax tree (AST)** — a tree data structure representing the grammatical structure of the query. At this stage, the database is only checking that your SQL is syntactically valid. It has not yet looked at whether your tables exist, whether your column names are correct, or what the data in those tables looks like. Syntax errors are caught here.

**Stage 2 — Analysis and Rewriting.** The AST is resolved against the database's system catalog — the internal metadata store that knows about every table, column, type, constraint, view, and function. Column names are resolved to specific table columns. Type mismatches are identified. Views are expanded into their underlying queries (view expansion). Row-Level Security policies are injected into the query tree. The result is a **query tree** — an enriched representation of the query with all ambiguities resolved. The query rewriter may also transform the query tree, for instance converting a `NOT IN` subquery into a `NOT EXISTS` for better planning.

**Stage 3 — Planning and Optimisation.** This is the stage we will study in depth. The query tree is handed to the planner, which must produce an **execution plan** — a tree of physical operations describing exactly how to retrieve the data. For each relation in the query, the planner considers all applicable access methods (sequential scan, index scan, bitmap index scan). For each join, it considers all applicable join algorithms (nested loop, hash join, merge join) and all possible orderings of the join. It estimates the cost of each combination using statistics about the data and the hardware, and selects the combination with the lowest estimated total cost.

**Stage 4 — Execution.** The chosen plan is executed by the executor, which walks the plan tree and calls each node's execution function. Results flow from leaf nodes (table scans) through intermediate nodes (joins, sorts, aggregates) to the root node, which delivers rows to the client.

```
QUERY PIPELINE — From SQL to Results:

SQL String: "SELECT name FROM customers c
             JOIN orders o ON c.id = o.customer_id
             WHERE c.country = 'BD' AND o.total > 100"

                    │
                    ▼
         ┌──────────────────────┐
         │  STAGE 1: PARSING    │
         │  SQL → AST           │
         │  Syntax check only   │
         └──────────┬───────────┘
                    │
                    ▼
         ┌──────────────────────┐
         │  STAGE 2: ANALYSIS   │
         │  AST → Query Tree    │
         │  Resolve: columns,   │
         │  types, views, RLS   │
         └──────────┬───────────┘
                    │
                    ▼
         ┌──────────────────────┐
         │  STAGE 3: PLANNING   │  ← This is what we study today
         │  Query Tree → Plan   │
         │  Consider all paths, │
         │  estimate costs,     │
         │  choose the cheapest │
         └──────────┬───────────┘
                    │
                    ▼
         ┌──────────────────────┐
         │  STAGE 4: EXECUTION  │
         │  Walk plan tree,     │
         │  fetch rows, return  │
         │  to client           │
         └──────────────────────┘

PLAN TREE EXAMPLE (simplified):
                    Nested Loop Join
                   /               \
         Index Scan                 Seq Scan
         customers                  orders
         (country = 'BD')           (total > 100)
         → uses index on country    → no useful index

The planner chose:
  1. Use the index on customers.country to find ~50 Bangladeshi customers.
  2. For each customer, scan orders and filter on total.
  3. Nested loop because the outer result (50 rows) is small.
```

The cost model that drives all planner decisions is based on two types of operations: **I/O operations** (reading data pages from disk or buffer cache) and **CPU operations** (processing rows, applying filters, computing expressions). Each operation type has a cost constant: `seq_page_cost` (default 1.0) is the base unit for reading a sequential page, `random_page_cost` (default 4.0) means reading a random page costs four times as much as a sequential page, and `cpu_tuple_cost`, `cpu_index_tuple_cost`, and `cpu_operator_cost` are fractions of 1.0 representing the relative cost of CPU operations. These constants can be tuned for your specific hardware — on SSDs, `random_page_cost` is often reduced to 1.1 or 1.5 because the random-vs-sequential penalty is much lower than on spinning disks.

## 2. Planner Statistics and Histograms

The query planner's ability to choose a good execution plan depends entirely on the accuracy of its estimates. An estimate is a prediction: "approximately how many rows will remain after applying this filter?" or "approximately how many distinct values does this column have?" The planner does not look at the actual data when planning — that would be too slow. Instead, it consults a set of **pre-computed statistics** maintained by the ANALYZE command and the autovacuum daemon.

These statistics live in the `pg_statistic` system catalog (exposed through the friendlier `pg_stats` view) and contain several types of information about each column in each table. Understanding these statistics is the key to understanding why the planner makes the decisions it makes — and why it sometimes makes the wrong ones.

### 2.1 The Statistics Vocabulary

**n_distinct** is an estimate of the number of distinct values in a column. A column with `n_distinct = 50` has about 50 unique values. A negative value means it is expressed as a fraction of total rows: `n_distinct = -0.05` means approximately 5% of rows have distinct values (so in a 1 million-row table, about 50,000 distinct values). This statistic is used to estimate the selectivity of equality conditions — `WHERE status = 'active'` on a column with 4 distinct values is estimated to return 25% of rows.

**null_frac** is the fraction of column values that are NULL. A column with `null_frac = 0.1` has 10% NULLs. This matters for IS NULL and IS NOT NULL filters and for certain join types.

**avg_width** is the average byte width of column values — the average number of bytes required to store one value. Used for estimating memory requirements for operations like sorting and hashing.

**most_common_vals (MCV) and most_common_freqs** are parallel arrays listing the most frequently occurring values and their frequencies. If `status` has values `'active'`, `'pending'`, `'archived'` with frequencies 0.70, 0.25, 0.05, the planner knows that `WHERE status = 'active'` will return 70% of rows, `WHERE status = 'pending'` will return 25%, and `WHERE status = 'archived'` will return 5%. This is dramatically more accurate than a naive `1/n_distinct = 33%` estimate for each value.

**histogram_bounds** is an array of values dividing the non-MCV data into approximately equal-frequency buckets. The histogram gives the planner a way to estimate how many rows satisfy range conditions like `WHERE price BETWEEN 100 AND 200` or `WHERE created_at > '2026-01-01'`. The histogram has `statistics_target` bins (default 100).

```sql
-- VIEWING TABLE STATISTICS:

SELECT
    attname         AS column_name,
    n_distinct,     -- Estimated distinct values
    null_frac,      -- Fraction of NULLs
    avg_width,      -- Average byte width

    -- Most common values and their frequencies (parallel arrays):
    most_common_vals,
    most_common_freqs,

    -- Histogram for range query estimation:
    histogram_bounds

FROM pg_stats
WHERE schemaname = 'public'
  AND tablename  = 'orders'
  AND attname IN ('status', 'total_amount', 'customer_id')
ORDER BY attname;

-- EXAMPLE OUTPUT:

-- column_name   | n_distinct | null_frac | most_common_vals          | most_common_freqs
-- status        | 4          | 0.00      | {active,pending,shipped,  | {0.68,0.22,0.07,
--               |            |           |  cancelled}               |  0.03}
-- total_amount  | -0.98      | 0.02      | {0.00,9.99}               | {0.05,0.03}
--               | (98% unique)|           | histogram_bounds →        |
--               |            |           | {0.01,12.50,24.99,...,    |
--               |            |           |  9999.99}                 |
-- customer_id   | 45231      | 0.00      | NULL                      | NULL
--               |            |           | (no MCVs — all roughly    |
--               |            |           |  equally frequent)        |
```

### 2.2 The Statistics Target

The `statistics_target` parameter controls how much information is collected per column. The default value of 100 means ANALYZE collects up to 100 most-common values and divides the histogram into 100 buckets. A higher target produces more accurate statistics at the cost of longer ANALYZE time and more memory. For columns with complex distributions that the planner frequently estimates incorrectly, increasing the target is often the cheapest and most effective fix.

```sql
-- CHECK CURRENT STATISTICS TARGET:
SELECT attname, attstattarget
FROM pg_attribute
WHERE attrelid = 'orders'::regclass
  AND attnum > 0;
-- attstattarget = -1 means "use the default" (default_statistics_target = 100)

-- INCREASE STATISTICS TARGET FOR A SPECIFIC COLUMN:
-- When the planner consistently underestimates or overestimates
-- rows for a particular column's conditions:

ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 500;
-- Now ANALYZE will collect 500 MCV + 500 histogram bins for this column.
-- Better estimates for queries filtering on customer_id.

-- Run ANALYZE to apply the new statistics:
ANALYZE orders;

-- INCREASE GLOBALLY (affects all future ANALYZE runs):
-- In postgresql.conf:
-- default_statistics_target = 200
-- Doubles the default quality of statistics at the cost of more ANALYZE time.
```

### 2.3 Extended Statistics — Multi-Column Correlations

A critical limitation of per-column statistics is that they assume columns are **statistically independent**. If a WHERE clause has `country = 'US' AND state = 'TX'`, the planner estimates the selectivity as `(fraction for country='US') × (fraction for state='TX')`. But state and country are not independent — if country is 'US', the fraction of 'TX' among those rows is much higher than the fraction of 'TX' in the entire table. The planner's independence assumption causes it to dramatically underestimate the number of rows satisfying the combined condition.

**Extended statistics** (`CREATE STATISTICS`) solve this by collecting statistics about combinations of columns. PostgreSQL supports three types: `ndistinct` (number of distinct value combinations), `dependencies` (functional dependencies, like city → zip code), and `mcv` (most common value combinations).

```sql
-- EXTENDED STATISTICS — Correlated Columns:

-- Problem: planner underestimates rows for
--   WHERE country = 'US' AND state = 'TX'
-- because it treats country and state as independent.

-- Solution: Create extended statistics on the combination:
CREATE STATISTICS customers_country_state_stats (dependencies, mcv)
    ON country, state
    FROM customers;

-- Run ANALYZE to populate the statistics:
ANALYZE customers;

-- Now the planner uses the joint distribution of (country, state)
-- instead of assuming independence. Estimates become accurate.

-- VIEW EXTENDED STATISTICS:
SELECT stxname, stxkeys, stxkind, stxdependencies
FROM pg_statistic_ext
WHERE stxrelid = 'customers'::regclass;

-- EXTENDED STATISTICS FOR THREE COLUMNS:
CREATE STATISTICS order_status_date_stats (mcv)
    ON status, DATE_TRUNC('month', created_at), customer_id
    FROM orders;
-- Useful when queries frequently filter on multiple of these columns together.
```

### 2.4 How the Planner Uses Statistics to Estimate Rows

Let us trace through a concrete example of how the planner uses these statistics to estimate row counts, because understanding this process is what lets you diagnose misestimates when they occur.

```
ROW ESTIMATION WALKTHROUGH:

Table: orders (1,000,000 rows)
Column statistics:
  status:       MCV = {active:0.68, pending:0.22, shipped:0.07, cancelled:0.03}
  total_amount: histogram with 100 bins, covering [0.01, 9999.99]
                approximately 10,000 rows per bin (1M / 100)
  customer_id:  n_distinct = 45,231

Query: WHERE status = 'pending' AND total_amount > 500.00

Step 1: Estimate selectivity for status = 'pending'
  status is in MCV → frequency = 0.22
  Estimated rows from this condition: 1,000,000 × 0.22 = 220,000

Step 2: Estimate selectivity for total_amount > 500.00
  500.00 is not in MCV → consult histogram.
  Suppose histogram_bounds shows 500.00 falls at the 45th bin boundary.
  Fraction above 500.00 = (100 - 45) / 100 = 0.55
  Estimated rows from this condition: 1,000,000 × 0.55 = 550,000

Step 3: Combine conditions (independence assumption):
  Combined selectivity = 0.22 × 0.55 = 0.121
  Estimated rows = 1,000,000 × 0.121 = 121,000

Step 4: Use this estimate to choose plan:
  121,000 rows expected → significant fraction of table →
  sequential scan might be cheaper than index scan + random I/O.

IF the estimate is wrong (say actual rows = 1,200, not 121,000):
  The planner chose sequential scan expecting 121,000 rows.
  Actual result: 1,200 rows.
  A targeted index scan would have been much faster.
  The misestimate → wrong plan → slow query.
  Fix: Update statistics target, create extended statistics,
       or verify that ANALYZE has been run recently.
```

## 3. Join Ordering and Dynamic Programming

When a query joins multiple tables together, the query planner must decide in what order to perform those joins. This is the **join ordering problem**, and it is one of the fundamental hard problems in query optimisation. The reason it is hard is combinatorial: with N tables to join, there are N! (N factorial) possible join orderings. For 5 tables: 120 orderings. For 8 tables: 40,320 orderings. For 10 tables: 3,628,800 orderings. For 15 tables: over a trillion. You cannot simply try all of them.

PostgreSQL's planner solves the join ordering problem using **dynamic programming (DP)** — a technique that avoids redundant work by storing and reusing the results of subproblems. The key insight that makes DP work for join ordering is the **principle of optimality**: if the best plan for joining tables {A, B, C, D} has a specific plan for joining {A, B, C} as one component, then that component must also be the best plan for joining {A, B, C} independently. This means we can build up optimal join plans for increasingly large subsets of tables, reusing the results computed for smaller subsets.

### 3.1 The Dynamic Programming Algorithm

The DP algorithm works bottom-up. It first computes the cheapest single-table access plan for each table in isolation (choosing between sequential scan, index scan, bitmap index scan, etc.). Then, for each pair of tables, it computes the cheapest two-table join using the pre-computed single-table plans. Then, for each group of three tables, it computes the cheapest three-way join using the pre-computed two-table plans. This continues until it has computed the plan for all N tables together.

```
DYNAMIC PROGRAMMING JOIN ORDERING — Example with 4 Tables:

Tables: A (orders), B (customers), C (products), D (categories)
Query: A JOIN B ON A.cust_id=B.id JOIN C ON A.prod_id=C.id JOIN D ON C.cat_id=D.id

STEP 1: Single-table plans (the base cases):
  plan(A) = cheapest access for orders           → SeqScan, cost=1000
  plan(B) = cheapest access for customers        → SeqScan, cost=200
  plan(C) = cheapest access for products         → SeqScan, cost=50
  plan(D) = cheapest access for categories       → IndexScan(cat_id), cost=5

STEP 2: Two-table plans (build on Step 1):
  plan(A,B) = best join of A and B
    Try: NestedLoop(A,B) = 1000 + 200 × rows(A) = expensive
    Try: HashJoin(A,B)   = 1000 + 200 + hash_overhead = 1300
    Try: MergeJoin(A,B)  = sort(A) + sort(B) + merge = 1800
    Best: HashJoin, cost=1300

  plan(A,C) = best join of A and C
    HashJoin(A,C): 1000 + 50 = 1100

  plan(C,D) = best join of C and D
    D is small (5 rows from IndexScan). NestedLoop is fast.
    NestedLoop(C,D): 50 + 5 × rows(C) = 50 + 5×500 = 2550
    HashJoin(C,D): 50 + 5 = 60 ← D is tiny, hash it!
    Best: HashJoin, cost=60

  ... (compute all C(4,2) = 6 two-table plans)

STEP 3: Three-table plans (build on Step 2):
  plan(A,B,C):
    Try: Join plan(A,B) with C: HashJoin(plan(A,B), C) = 1300 + 50 = 1360
    Try: Join plan(A,C) with B: HashJoin(plan(A,C), B) = 1100 + 200 = 1310
    Try: Join plan(B,C) with A: ... (if B,C join is meaningful)
    Best for (A,B,C): 1310

  plan(A,C,D):
    Try: Join plan(A,C) with D: HashJoin(plan(A,C), D) = 1100 + 5 = 1106
    Try: Join plan(C,D) with A: HashJoin(plan(C,D), A) = 60 + 1000 = 1065
    Best for (A,C,D): 1065  ← build (C,D) first because D is tiny!

  ... (compute all C(4,3) = 4 three-table plans)

STEP 4: Final four-table plan (build on Step 3):
  plan(A,B,C,D):
    Try: Join plan(A,B,C) with D: 1310 + 5 = 1316
    Try: Join plan(A,C,D) with B: 1065 + 200 = 1265
    Try: Join plan(A,B,D) with C: ...
    Try: Join plan(B,C,D) with A: ...
    Best: Join(plan(A,C,D), B) at cost 1265

  The key insight: joining C and D first (where D is tiny and indexed)
  dramatically reduces the intermediate result size for subsequent joins.
  DP found this optimal ordering automatically.

TOTAL WORK: 4 (size-1) + 6 (size-2) + 4 (size-3) + 1 (size-4) = 15 subproblems
Compare to brute force: 4! = 24 orderings (some redundancy, but DP is asymptotically better)
For N=10: DP considers 2^10 = 1024 subsets vs 10! = 3,628,800 orderings
```

The DP approach considers not just different orderings but also different **join algorithm choices** (nested loop, hash join, merge join) for each subproblem. For each two-table subproblem, it evaluates all applicable algorithms and keeps the cheapest. This means the total search space is (number of join orderings) × (number of algorithm choices per join), and DP explores it efficiently by memoising intermediate results.

### 3.2 Join Algorithms — When Each is Chosen

The planner has three join algorithms to choose from, and understanding when each is appropriate helps you understand why the planner made a specific choice.

**Nested Loop Join** works by iterating over every row in the outer (left) table and, for each row, finding matching rows in the inner (right) table. If the inner table has an index on the join column, the inner lookup is an index scan — extremely fast for point lookups. Without an index, the inner table is scanned completely for each outer row. Nested loop is ideal when the outer result set is small (a few hundred to a few thousand rows) and the inner table has a suitable index.

**Hash Join** builds a hash table from the smaller of the two tables (the build side), then scans the larger table (the probe side), looking up each row in the hash table. Hash join requires both tables to fit in memory (specifically, in `work_mem`) for optimal performance. If the hash table exceeds `work_mem`, it spills to disk (a temp file), which is dramatically slower. Hash join is ideal for large-to-large joins where neither table has a useful sort order or index that would benefit merge join.

**Merge Join** requires both inputs to be sorted on the join key. It then performs a single linear scan through both sorted inputs simultaneously, like merging two sorted lists. If both inputs are already sorted (e.g., coming from index scans that return data in index order), merge join is essentially free in terms of setup cost. If sorting is required, the sort cost may outweigh the merge join benefit. Merge join is ideal for large-to-large joins on sorted or sortable keys, particularly when the join produces a large output that will itself need to be sorted.

```
JOIN ALGORITHM DECISION GUIDE:

Scenario                          │ Best Algorithm      │ Why
──────────────────────────────────┼─────────────────────┼──────────────────────
Outer: 100 rows (post-filter)     │ Nested Loop         │ Few outer iterations;
Inner: 1M rows with index         │                     │ index makes inner fast
──────────────────────────────────┼─────────────────────┼──────────────────────
Outer: 100k rows                  │ Hash Join           │ Build hash of smaller;
Inner: 50k rows                   │                     │ both fit in work_mem
Both: no useful sort order        │                     │
──────────────────────────────────┼─────────────────────┼──────────────────────
Both outputs already sorted on    │ Merge Join          │ No sort cost; linear
join key (from prior index scans) │                     │ merge is cheap
──────────────────────────────────┼─────────────────────┼──────────────────────
Outer: 1M rows                    │ Hash Join           │ NL would be N×M
Inner: 500k rows                  │ (with disk spill    │ Hash amortizes setup
No indexes, no sort               │ if needed)          │ cost over all rows
──────────────────────────────────┼─────────────────────┼──────────────────────
Inequality join: a.ts BETWEEN     │ Merge Join or NL    │ Hash can't do ranges;
b.start AND b.end                 │                     │ merge works if sorted
```

## 4. Genetic Query Optimizer (GEQO)

Dynamic programming is optimal — for a manageable number of tables. Once the join count reaches a certain threshold (configurable via `geqo_threshold`, defaulting to 12), the 2^N subproblems that DP must solve become prohibitively expensive. A query joining 12 tables requires evaluating 4,096 subsets; a 20-table join requires 1,048,576. The planning phase itself would take longer than most queries.

PostgreSQL's answer for queries exceeding the DP threshold is the **Genetic Query Optimizer (GEQO)** — a heuristic search algorithm based on evolutionary computation. GEQO does not guarantee the optimal plan, but it finds a very good plan in much less time than exhaustive DP would require. Understanding GEQO is important both for knowing when it activates and for knowing why large multi-join queries sometimes behave unexpectedly.

GEQO represents each possible join order as a **gene** — a permutation of the table identifiers. A population of many random genes (join orders) is created, each one evaluated for its plan cost. Then, evolutionary operations are applied repeatedly: **selection** (better-cost genes survive), **crossover** (two parent genes combine to create a child gene with segments from both parents), and **mutation** (small random changes to a gene's sequence). Each generation produces a new population that tends to contain better join orders than the previous one, converging toward a near-optimal solution after a configurable number of generations.

```
GEQO — HOW EVOLUTION FINDS A GOOD JOIN ORDER:

Tables to join: A, B, C, D, E, F, G, H, I, J, K, L (12 tables)
Each gene = a permutation = a join order = a candidate plan

INITIAL POPULATION (generation 0):
  Gene 1: [B, F, A, L, G, D, H, I, C, J, E, K]  → plan cost: 8,420
  Gene 2: [A, C, G, B, J, E, K, F, L, D, H, I]  → plan cost: 6,100
  Gene 3: [L, A, B, C, G, H, D, E, F, I, J, K]  → plan cost: 11,300
  ...100 more random genes...

SELECTION: Keep the 50 best genes (lowest cost).

CROSSOVER (Gene 2 × Gene 7):
  Gene 2: [A, C, G, B | J, E, K, F, L, D, H, I]
  Gene 7: [J, D, F, B | A, C, G, H, I, E, K, L]
  Child:  [A, C, G, B | A, C, G, H, I, E, K, L]  ← prefix from parent 1
  (Fix duplicates via ordered crossover operator)
  Result: [A, C, G, B, J, D, F, H, I, E, K, L]   → plan cost: 5,800

MUTATION (rare random swap):
  Gene:   [A, C, G, B, J, D, F, H, I, E, K, L]
  Swap positions 3 and 8:
  Result: [A, C, H, B, J, D, F, G, I, E, K, L]   → plan cost: 5,600

GENERATION 50 (after 50 rounds of evolution):
  Best gene: [D, L, B, G, A, C, F, J, K, H, I, E] → plan cost: 4,100

GEQO found a plan with cost 4,100 in ~50ms.
DP would have required 2^12 = 4,096 subproblems, taking much longer.
The GEQO plan may not be the global optimum, but it is usually within
10-30% of optimal, which is acceptable for such complex queries.
```

Key GEQO configuration parameters in `postgresql.conf`:

```ini
# GEQO CONFIGURATION:

# Number of tables before GEQO takes over from DP:
geqo_threshold = 12               # Default: 12 tables

# GEQO population size (more = better search, slower planning):
geqo_pool_size = 0                # 0 = automatic (scales with #tables)
                                  # Typically 100-200 for 12+ tables

# Number of generations to run:
geqo_generations = 0              # 0 = automatic (= pool_size)

# Selection pressure: higher = exploit good solutions more, explore less:
geqo_selection_bias = 2.0         # Range: 1.5 to 2.0

# Random seed for reproducible planning (0 = random each time):
geqo_seed = 0.0                   # 0.0 = random seed

# DISABLING GEQO (use DP even for large join counts):
# Only do this if planning time is acceptable and you need optimal plans:
geqo = off                        # Disable GEQO entirely
# OR: raise the threshold for specific sessions:
SET geqo_threshold = 20;          -- Use DP for queries with up to 20 tables
```

An important practical implication of GEQO: because it is a stochastic algorithm (uses random numbers), running the same large-join query twice may produce different plans if `geqo_seed = 0.0`. This can be surprising — the same query produces different execution times on different runs not because of data changes but because GEQO found a different join order each time. For reproducible behaviour in testing, set `geqo_seed` to a fixed value.

For very complex queries with 20+ joins (which typically arise from ORM-generated queries or highly normalised schemas), the planning time from GEQO itself can become significant. If query planning is taking 100ms or more, consider: caching prepared statements (which reuse the plan), simplifying the query by breaking it into CTEs (which in PostgreSQL 12+ are planning boundaries by default with `MATERIALIZED`), or denormalising the schema to reduce join count.

## 5. Parallel Query Execution

Modern servers have many CPU cores, but a single query in a traditional database uses only one of them. For long-running queries — analytical workloads, large aggregations, table scans over hundreds of millions of rows — single-core execution leaves the majority of the server's computational power idle. **Parallel query execution** solves this by dividing the work of a single query among multiple CPU cores, potentially reducing a 60-second query to 10 seconds on a 6-core server.

PostgreSQL's parallel query framework, introduced in version 9.6 and progressively improved, works by splitting the execution of specific plan nodes across multiple **worker processes**. The original backend process becomes the **leader**, and it spawns one or more **parallel workers** from a pre-allocated process pool (`max_parallel_workers`, `max_parallel_workers_per_gather`). Workers scan portions of the data and send results to the leader through a shared-memory message queue. The leader collects results from all workers and completes the final steps of the plan.

```
PARALLEL QUERY ARCHITECTURE:

Query: SELECT status, SUM(total_amount) FROM orders GROUP BY status

Without parallel:
  Single backend process:
    Seq Scan → 1,000,000 rows → Aggregate → Result
    Time: 45 seconds

With parallel (4 workers):
  ┌────────────────────────────────────────────────────────────┐
  │                   GATHER node (leader)                     │
  │          Collects and merges partial results               │
  │          from all workers                                  │
  └──────────────┬────────────┬────────────┬──────────────────┘
                 │            │            │
        ┌────────▼──┐  ┌──────▼───┐  ┌───▼─────┐  ┌──────────┐
        │ Worker 1  │  │ Worker 2 │  │ Worker 3│  │ Worker 4 │
        │ Scan rows │  │ Scan rows│  │ Scan    │  │ Scan     │
        │ 0-250k    │  │ 250k-500k│  │ 500k-   │  │ 750k-    │
        │ Partial   │  │ Partial  │  │ 750k    │  │ 1M rows  │
        │ Aggregate │  │ Aggregate│  │ Partial │  │ Partial  │
        │           │  │          │  │ Aggr.   │  │ Aggr.    │
        └───────────┘  └──────────┘  └─────────┘  └──────────┘

Each worker scans ~250k rows and computes a partial GROUP BY.
Leader merges the four partial aggregates into the final result.
Time: ~12 seconds (approximate 4× speedup, minus overhead).

EXPLAIN output shows this plan:
  Finalize GroupAggregate
    -> Gather
         Workers Planned: 4
         Workers Launched: 4
         -> Partial HashAggregate
              -> Parallel Seq Scan on orders
```

The parallelism decision is made by the planner based on the estimated cost of the query and several configuration parameters. The planner computes a parallel plan only if it believes parallelism will be beneficial — which it typically is for queries with high estimated row counts and expensive operations (sorts, aggregates, hash joins).

```ini
# PARALLEL QUERY CONFIGURATION:

# Maximum total parallel workers for all queries:
max_parallel_workers = 8                  # Should be ≤ CPU cores
# (Pool defined by max_worker_processes)

# Maximum workers per single query:
max_parallel_workers_per_gather = 4       # Each Gather node gets max 4 workers
                                          # A query with 2 Gather nodes = 8 workers max

# Minimum table size before parallel scan is considered:
min_parallel_table_scan_size = 8MB        # Only parallelize if table > 8MB

# Minimum index size before parallel index scan considered:
min_parallel_index_scan_size = 512kB

# Cost reduction for parallel plan (workers are "free" beyond this):
parallel_tuple_cost = 0.1                 # Cost per tuple transferred to leader
parallel_setup_cost = 1000               # Fixed overhead for spawning workers
                                          # Lower = planner prefers parallel plans
                                          # Higher = planner avoids parallel plans

# Force parallel for testing (bypass cost threshold):
SET max_parallel_workers_per_gather = 4;
SET force_parallel_mode = on;             # Force parallel even for small queries
```

### 5.1 Parallel-Safe Operations

Not all operations can be parallelised. PostgreSQL classifies every function and operation as **parallel-safe** (can run inside a parallel worker), **parallel-restricted** (can run in the leader but not a worker), or **parallel-unsafe** (prevents parallelism entirely). User-defined functions are assumed parallel-unsafe by default unless explicitly declared otherwise with `CREATE FUNCTION ... PARALLEL SAFE`.

```sql
-- CHECKING PARALLEL SAFETY:
SELECT proname, proparallel
FROM pg_proc
WHERE proname IN ('count', 'sum', 'array_agg', 'string_agg', 'now');
-- proparallel: 's' = safe, 'r' = restricted, 'u' = unsafe

-- DECLARING A USER FUNCTION AS PARALLEL SAFE:
CREATE OR REPLACE FUNCTION calculate_discount(price NUMERIC, rate NUMERIC)
RETURNS NUMERIC
LANGUAGE SQL
IMMUTABLE       -- Result depends only on inputs (no side effects)
PARALLEL SAFE   -- Safe to run in parallel workers
AS $$
    SELECT price * (1.0 - rate);
$$;

-- A function that reads from tables is usually parallel-safe if it uses
-- read-only transactions, but must be declared explicitly:
CREATE OR REPLACE FUNCTION get_customer_tier(customer_id INT)
RETURNS TEXT
LANGUAGE SQL
STABLE          -- Result is stable within a transaction
PARALLEL SAFE   -- Will be run inside parallel workers
AS $$
    SELECT tier FROM customer_tiers WHERE id = customer_id;
$$;
-- WARNING: Only declare PARALLEL SAFE if the function truly has no
-- side effects and does not depend on session-level state.
```

### 5.2 Operations That Benefit Most from Parallelism

Parallel query execution provides the greatest benefit for operations that are both expensive and naturally divisible across workers: large sequential scans, large aggregations, large hash joins, and large sorts. It provides no benefit (and adds overhead) for small queries, queries that return few rows, or queries whose bottleneck is a single-row index lookup.

```sql
-- QUERY TYPES THAT BENEFIT FROM PARALLELISM:

-- 1. Large aggregate (GROUP BY over entire table):
SELECT
    DATE_TRUNC('month', created_at) AS month,
    COUNT(*)                        AS order_count,
    SUM(total_amount)               AS revenue
FROM orders
GROUP BY DATE_TRUNC('month', created_at)
ORDER BY month;
-- 1M-row table → benefits from 4-8 workers on parallel seq scan + partial agg

-- 2. Large hash join:
SELECT c.country, COUNT(o.id), SUM(o.total_amount)
FROM customers c
JOIN orders o ON c.id = o.customer_id
GROUP BY c.country;
-- Both large tables → parallel hash join dramatically reduces time

-- 3. Large sort:
SELECT * FROM orders ORDER BY created_at DESC;
-- Parallel sort (each worker sorts its segment, leader merges) is faster

-- CHECKING IF PARALLELISM WAS USED:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT status, SUM(total_amount) FROM orders GROUP BY status;

-- Look for in output:
-- "Gather" → parallel query with workers
-- "Workers Planned: 4" → planner requested 4 workers
-- "Workers Launched: 4" → 4 workers actually started (check this matches!)
-- If Workers Launched < Workers Planned → not enough worker processes available
-- → increase max_parallel_workers
```

## 6. JIT Compilation — PostgreSQL

PostgreSQL 11 introduced **Just-In-Time (JIT) compilation** — a technique borrowed from virtual machine implementations (Java's JVM, .NET's CLR, JavaScript engines) that compiles parts of the query execution into native machine code at runtime, replacing the interpreted row-by-row execution with code that runs directly on the CPU without interpretation overhead.

To understand why JIT matters, you need to understand the cost of the traditional execution model. Without JIT, the PostgreSQL executor processes each tuple (row) through a generic, interpreted evaluation loop. For an expression like `WHERE status = 'active' AND total_amount > 100`, the executor calls a general-purpose expression evaluation function that reads the expression tree node by node, calls the appropriate comparison functions, handles NULL checks, and assembles the boolean result. This generic machinery is flexible (it works for any expression) but has high overhead per tuple — function call overhead, pointer dereferences, branch mispredictions, and cache misses accumulate when processing millions of tuples.

JIT replaces this with **native machine code** generated specifically for the expressions in your query. Instead of a generic tree-walking evaluator, the JIT compiler uses LLVM (Low-Level Virtual Machine) to generate a native function that evaluates `status = 'active' AND total_amount > 100` directly — a few assembly instructions that the CPU can execute at full hardware speed without any interpreter overhead. The compilation takes time at query start, but for queries that process millions of rows, the savings per tuple outweigh the compilation cost many times over.

```
JIT COMPILATION — What Gets Compiled and Why:

WITHOUT JIT (interpreted execution):
  For each of 1,000,000 rows:
    → Call ExecEvalExpr() [function call overhead]
    → Navigate expression tree node by node [pointer dereferences]
    → Call operator function (text_eq for '=', numeric_gt for '>') [more overhead]
    → Handle NULLs generically [branch prediction failures]
    → Return boolean [register copy]
  × 1,000,000 = enormous cumulative overhead

  Approximate CPU cost: 500ns per tuple × 1M = 500ms just for expression evaluation

WITH JIT (compiled native code):
  LLVM generates this native function ONCE at query start:
    cmp [row.status_offset], 'active'   ; compare status bytes directly
    jne next_row                        ; skip if not equal
    movsd xmm0, [row.amount_offset]     ; load total_amount into register
    ucomisd xmm0, 100.0                 ; compare with threshold
    jbe next_row                        ; skip if ≤ 100
    ; row passes filter → emit it

  Cost: ~10ns per tuple × 1M = 10ms just for expression evaluation
  JIT provides ~50× speedup on expression evaluation for long queries.

  Compilation overhead: ~20-100ms (amortized over 1M rows → negligible)
```

JIT is not beneficial for all queries — only for those that process enough rows to amortize the compilation cost. PostgreSQL controls JIT with several parameters:

```ini
# JIT CONFIGURATION (postgresql.conf):

# Enable JIT globally:
jit = on                          # Default: on (PostgreSQL 11+)

# Minimum cost threshold for JIT to activate:
jit_above_cost = 100000           # JIT kicks in if query cost > 100,000
                                  # (Default cost units; roughly corresponds
                                   # to queries processing ~100k+ rows)

# Cost threshold for inlining functions:
jit_inline_above_cost = 500000    # Inline function calls above this cost

# Cost threshold for compiler optimisation (O2 level):
jit_optimize_above_cost = 500000  # Apply aggressive optimisations above this

# PostgreSQL uses LLVM for code generation:
# Requires PostgreSQL built with --with-llvm
# Check: SELECT pg_jit_available();
```

JIT compilation targets four specific execution components: **expression evaluation** (WHERE clauses, computed columns, function calls), **tuple deforming** (unpacking the internal binary representation of a row into usable field values), **tuple insertion into sort/hash structures**, and **aggregate function calls**. Of these, expression evaluation and tuple deforming provide the greatest speedup.

```sql
-- OBSERVING JIT IN EXPLAIN ANALYZE:
EXPLAIN (ANALYZE, BUFFERS)
SELECT status, SUM(total_amount), COUNT(*)
FROM orders
WHERE created_at > '2025-01-01'
GROUP BY status;

-- JIT section in output:
-- JIT:
--   Functions: 11
--   Options: Inlining true, Optimization true, Expressions true, Deforming true
--   Timing: Generation 15.243 ms, Inlining 7.891 ms,
--            Optimization 38.124 ms, Emission 22.087 ms, Total 83.345 ms

-- Interpreting JIT timing:
-- Generation: Time to generate LLVM IR (intermediate representation)
-- Inlining: Time to inline called functions into the compiled code
-- Optimization: Time for LLVM to apply optimisations (loop unrolling, etc.)
-- Emission: Time to generate native machine code from optimised IR
-- Total: 83ms compilation overhead → justified if query saves seconds

-- DISABLING JIT FOR SPECIFIC QUERIES (if compilation overhead hurts short queries):
SET jit = off;
-- Or globally for a session:
-- SET jit_above_cost = 1e15;  -- Effectively never triggers
```

JIT's benefit is most pronounced in analytical (OLAP) queries processing millions of rows. For typical OLTP queries that process tens or hundreds of rows, JIT adds compilation overhead with no benefit. PostgreSQL's cost-based JIT activation threshold (`jit_above_cost`) prevents JIT from activating for short queries — but if the cost estimator overestimates a query's cost, JIT may activate unnecessarily. For this reason, some teams disable JIT for their OLTP databases and enable it only for analytical workloads or data warehouse databases.

## 8. Diagnosing and Fixing Bad Plans

Armed with understanding of the planner, let us examine the most common bad plan scenarios and their systematic fixes.

### Misestimate: Planner Thinks Few Rows, Gets Many

The planner chooses a nested loop join because it estimates the outer table returns 50 rows. Actually it returns 50,000. The nested loop performs 50,000 index lookups on the inner table when a hash join would have been much faster.

```sql
-- SYMPTOM: Query slower than expected, planner chose Nested Loop
-- DIAGNOSIS: Check estimated vs actual rows at each node
EXPLAIN (ANALYZE) SELECT ...;
-- Find: "rows=50" (estimate) vs "rows=50000" (actual)

-- ROOT CAUSE INVESTIGATION:
SELECT tablename, attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'customer_id';
-- If n_distinct is far from reality, statistics are stale or target is too low.

-- FIXES:
-- 1. Run ANALYZE to refresh statistics:
ANALYZE orders;

-- 2. If statistics are fresh but wrong, increase target:
ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 500;
ANALYZE orders;

-- 3. If two correlated columns cause the misestimate:
CREATE STATISTICS orders_cust_status (mcv, dependencies)
    ON customer_id, status FROM orders;
ANALYZE orders;

-- 4. Emergency: force a specific join type for a session:
SET enable_nestloop = off;  -- Disable nested loop (force hash or merge)
-- DANGEROUS: Only use in testing to verify plan choice hypothesis
```

### Planner Chooses Sequential Scan Despite Index Existing

```sql
-- SYMPTOM: Seq scan when index exists and should be used
-- COMMON CAUSES:
-- 1. Low selectivity: the index isn't helpful because > 10-20% of rows match
-- 2. random_page_cost too high relative to data being cached
-- 3. Table statistics show wrong row counts

-- CHECK: Is the condition actually selective?
SELECT COUNT(*) FROM orders WHERE status = 'active';  -- If 680,000/1,000,000 → seq scan is CORRECT
SELECT COUNT(*) FROM orders WHERE status = 'archived'; -- If 5,000/1,000,000 → index should be used

-- FIX 1: For SSD storage, lower random_page_cost:
-- postgresql.conf:
-- random_page_cost = 1.1   (SSDs: random vs sequential penalty is ~10%, not 400%)
-- effective_cache_size = 12GB  (tell planner how much data is in OS cache)

-- FIX 2: Force index use for testing (never in production permanently):
SET enable_seqscan = off;
EXPLAIN SELECT ... ;  -- Shows index plan that would be chosen without seq scan
SET enable_seqscan = on;

-- FIX 3: Partial index for selective queries:
CREATE INDEX idx_orders_archived
    ON orders (created_at)
    WHERE status = 'archived';
-- This index only covers 5% of rows. Much smaller → planner prefers it
-- for queries with WHERE status = 'archived'.
```

### Work_mem Too Small — Spilling to Disk

```sql
-- SYMPTOM: EXPLAIN shows Sort Method: external merge  Disk: 12345kB
-- or HashAggregate Batches: 8 (spilling to disk)

-- CHECK current work_mem:
SHOW work_mem;  -- Default: 4MB. Often too low for complex analytical queries.

-- FIX: Increase work_mem for the session (not globally — risky):
SET work_mem = '256MB';
-- Then re-run the query. If sort changes to "quicksort" and Batches=1, success.

-- GLOBAL FIX (postgresql.conf):
-- work_mem = 64MB  -- Increase cautiously.
-- CAUTION: work_mem is allocated PER SORT/HASH OPERATION PER QUERY.
-- A query with 3 sort nodes and 4 parallel workers uses:
-- 3 × 4 × work_mem = 12 × work_mem simultaneously.
-- At 64MB: 12 × 64 = 768MB from a single complex parallel query!
-- Monitor memory usage carefully after increasing work_mem.
```

```
  • "Rows Removed by Filter: 999,000" on a 1M table → missing index
  • "Sort Method: external merge  Disk: NNNkB" → increase work_mem
  • "Batches: 8" in HashAggregate/Hash → increase work_mem
  • "Workers Launched: 0" when parallel expected → workers exhausted
  • JIT total time > 100ms on a 200ms query → JIT overhead not worth it

COMMON FIXES SUMMARY:
  Stale statistics     → ANALYZE tablename;
  Wrong statistics     → ALTER TABLE t ALTER COLUMN c SET STATISTICS 500;
  Correlated columns   → CREATE STATISTICS s (dependencies) ON c1,c2 FROM t;
  Seq scan on SSD      → random_page_cost = 1.1 in postgresql.conf
  Hash/sort spill      → SET work_mem = '256MB'; (per session)
  Large join too slow  → Check GEQO threshold; break into CTEs
  No parallelism       → Check max_parallel_workers; PARALLEL SAFE funcs
  JIT overhead         → SET jit = off; for OLTP sessions

KEY POSTGRESQL.CONF TUNING PARAMS:
  default_statistics_target = 200    # Better stats quality (default: 100)
  random_page_cost = 1.1             # For SSD storage (default: 4.0)
  effective_cache_size = 12GB        # OS + PG cache size hint
  work_mem = 64MB                    # Per-sort/hash memory
  max_parallel_workers = 8           # Total parallel worker pool
  max_parallel_workers_per_gather = 4 # Per-query max
  jit = on                           # JIT compilation (default: on)
  jit_above_cost = 100000            # JIT activation threshold
  geqo_threshold = 12                # Tables before GEQO kicks in
```

---

_The query planner is the smartest part of your database — and it is doing its best with incomplete information. It does not know the actual distribution of your data at planning time; it knows the summary statistics that ANALYZE last computed. It does not know your hardware characteristics exactly; it knows the cost constants you have configured. It does not know that your two WHERE clause columns are correlated; it assumes independence unless you tell it otherwise._

_Every time the planner makes a bad choice — choosing a sequential scan when an index would be faster, choosing a nested loop when a hash join would scale better, underestimating rows and building too small a work table — the answer is almost always the same: give it better information. Run ANALYZE. Increase the statistics target. Create extended statistics for correlated columns. Tune the cost constants for your actual hardware._

_The planner is not your adversary. It is your most powerful ally — when you give it what it needs to make the right choices. The engineers who master EXPLAIN ANALYZE output, who understand what each plan node means and what each mismatch between estimates and actuals implies, are the ones who turn 45-second queries into 200-millisecond ones without changing a single line of SQL._

_That transformation — from slow to fast, from guessing to understanding — is what makes query planning worth studying deeply._
