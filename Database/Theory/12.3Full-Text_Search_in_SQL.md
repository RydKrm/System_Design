> _"Full-text search is the gap between what users type and what data means. The quality of that gap determines whether your search feels like a librarian who understands you or a filing cabinet that doesn't."_ — Every product manager who has watched users abandon a search box in frustration

## A Letter from Your DBA Mentor Before We Begin

Let me tell you about the two ways most applications handle search. The first way is the `LIKE` operator: `WHERE description LIKE '%payment gateway%'`. This works, barely, for toy applications. It is slow (cannot use a standard B-Tree index), it is brittle (a user searching for "payment gateways" with a plural gets nothing), it is ignorant (it treats "running", "ran", and "runs" as completely different words), and it is clumsy (it ranks all results identically, as if finding "payment gateway" in the first sentence of a product description is the same as finding it buried in paragraph twelve).

The second way is to reach immediately for Elasticsearch — a dedicated search engine — bolt it on as an external dependency, build a synchronisation pipeline to keep it in sync with your database, debug the synchronisation failures, manage two systems' worth of operational overhead, and then discover that Elasticsearch's powerful features come with a steep learning curve and operational complexity that may not be justified by your actual search requirements.

There is a third way that most engineers never consider: **PostgreSQL's native full-text search**. Built directly into the database engine, requiring no external service, no synchronisation pipeline, and no additional operational overhead, it is sophisticated enough to handle the search requirements of a large proportion of real production applications. It handles stemming (matching "run" to "running"), stop word filtering (ignoring "the", "and", "a"), multiple languages, custom dictionaries, phrase search, proximity search, weighted fields, and result ranking — all with GIN index performance that makes large-scale search practical.

This guide covers everything you need to design, implement, and tune full-text search in PostgreSQL: the data types and query syntax, the text processing pipeline, ranking algorithms, indexing strategy, and a clear-eyed assessment of when PostgreSQL's capabilities are sufficient and when Elasticsearch's additional power is genuinely necessary.

## 1. The Full-Text Search Problem — Beyond LIKE

To appreciate what full-text search solves, you must first understand the specific, concrete failures of the naive approach. These are not theoretical concerns — they are the exact frustrations users experience every day with poorly implemented search.

**The Morphology Problem.** A user searching for "payments" should find documents containing "payment", "paying", and "paid". These are morphologically related — they share the same root word. A `LIKE '%payments%'` query will miss "payment" (singular), "paying" (present participle), and "paid" (past tense) entirely. Full-text search uses a process called **stemming** to reduce words to their root form before indexing and searching, ensuring that all morphological variants match.

**The Stop Word Problem.** Words like "the", "a", "an", "is", "in", and "of" appear in virtually every document and contribute nothing to the meaning of a search. If a user searches for "the best payment gateway", the word "the" and "best" (if configured as a stop word) should be ignored — only "payment" and "gateway" carry semantic weight. `LIKE` treats all words equally; full-text search can filter out high-frequency noise words.

**The Ranking Problem.** When ten thousand documents mention "payment gateway", which ones should appear first? The one where "payment gateway" appears in the title is probably more relevant than the one where it appears once in the fifth paragraph. A document that mentions the phrase frequently is probably more relevant than one that mentions it once. `LIKE` returns all matches with no ranking; full-text search computes relevance scores and sorts by them.

**The Performance Problem.** `LIKE '%term%'` with a leading wildcard cannot use any standard B-Tree index — it must scan every row, examining every character. On a table with one million rows and long text columns, this can take minutes. Full-text search with a GIN index can find matches across millions of documents in milliseconds.

```
COMPARISON — LIKE vs Full-Text Search:

Query: find documents about "running payment processes"

─────────────────────────────────────────────────────────────────────
LIKE approach:
  WHERE description LIKE '%running payment processes%'

  Misses:
  ✗ "run payment processing"     (different form of "running")
  ✗ "payments are processed"     (different word order + form)
  ✗ "Payment Process Runner"     (all words present, different order)
  ✗ "processing of payments"     (rearranged)

  Finds:
  ✓ Only exact phrase "running payment processes"

  Performance: Full table scan. 1M rows → minutes on cold cache.
  Ranking: None. All matches are equal.

─────────────────────────────────────────────────────────────────────
Full-Text Search:
  WHERE to_tsvector('english', description) @@ to_tsquery('english',
        'running & payment & process')

  After stemming by 'english' configuration:
  "running" → stem "run"
  "payment" → stem "payment"  (already base form)
  "process" → stem "process"

  Now matches documents containing ANY combination of:
  "run", "running", "runs", "ran" → all share stem "run"
  "payment", "payments"           → share stem "payment"
  "process", "processes",         → share stem "process"
  "processing", "processed"

  Finds:
  ✓ "running payment processes"
  ✓ "run payment processing"
  ✓ "payments are processed"
  ✓ "Payment Process Runner"
  ✓ "processing of payments"

  Performance: GIN index lookup. 1M rows → milliseconds.
  Ranking: ts_rank assigns relevance scores. Title matches > body matches.
```

## 2. tsvector — The Document Representation

A `tsvector` is PostgreSQL's internal representation of a text document prepared for full-text searching. When you convert a text string to a `tsvector`, the database applies the full text processing pipeline: tokenisation (splitting text into words), normalisation (lowercasing), stop word removal (eliminating common words), and stemming (reducing words to their root). The result is a compact, sorted list of **lexemes** (normalised word roots) with their positions in the original text.

Understanding `tsvector` deeply — what it contains and what it discards — is fundamental to understanding the capabilities and limitations of PostgreSQL full-text search.

```sql
-- ─────────────────────────────────────────────────────────────────
-- CONVERTING TEXT TO TSVECTOR:

SELECT to_tsvector('english', 'The quick brown fox jumps over the lazy dog');
-- Result: 'brown':3 'dog':9 'fox':4 'jump':5 'lazi':8 'quick':2

-- What happened:
-- "The"    → stop word → REMOVED (articles are noise)
-- "quick"  → lexeme 'quick' at position 2
-- "brown"  → lexeme 'brown' at position 3
-- "fox"    → lexeme 'fox' at position 4
-- "jumps"  → stemmed to 'jump' at position 5 (3rd-person dropped)
-- "over"   → stop word → REMOVED
-- "the"    → stop word → REMOVED
-- "lazy"   → stemmed to 'lazi' at position 8 (British English stem)
-- "dog"    → lexeme 'dog' at position 9

-- Positions are preserved in the original text numbering even when
-- stop words are removed. This enables phrase and proximity search.

-- MULTIPLE COLUMN DOCUMENTS — Concatenating fields:
SELECT to_tsvector('english',
    COALESCE(title, '') || ' ' ||
    COALESCE(description, '') || ' ' ||
    COALESCE(tags, '')
)
FROM products
WHERE id = 1;

-- ─────────────────────────────────────────────────────────────────
-- WEIGHTED TSVECTORS — Different fields carry different importance:

-- Weights: 'A' (highest) > 'B' > 'C' > 'D' (lowest)
SELECT
    setweight(to_tsvector('english', COALESCE(title, '')),       'A') ||
    setweight(to_tsvector('english', COALESCE(subtitle, '')),    'B') ||
    setweight(to_tsvector('english', COALESCE(description, '')), 'C') ||
    setweight(to_tsvector('english', COALESCE(tags, '')),        'B')
AS search_vector
FROM articles
WHERE id = 1;

-- Resulting tsvector tags each lexeme with its source field's weight:
-- 'database':1A 'postgresql':2A 'performance':5B 'query':8C 'index':9C
-- ↑ from title (A)  ↑ from title (A)  ↑ from subtitle(B)  ↑ from description(C)

-- The ts_rank function uses these weights to compute relevance scores:
-- A match in the title contributes more to the score than a description match.
```

### 2.1 Inspecting tsvector Contents

Understanding what the text processing pipeline produces is essential for debugging unexpected search behaviour. Several utility functions let you inspect the processing at each stage.

```sql
-- ─────────────────────────────────────────────────────────────────
-- INSPECT TOKENISATION (before stemming and stop word removal):
SELECT * FROM ts_debug('english', 'PostgreSQL database running efficiently');

-- Output:
-- alias    | description    | token        | dictionaries  | dictionary | lexemes
-- asciiword| Word, all ASCII| PostgreSQL   | {english_stem}| english_stem| {postgresql}
-- blank    | Space symbols  |              | {}            |            | NULL
-- asciiword| Word, all ASCII| database     | {english_stem}| english_stem| {databas}
-- blank    | Space symbols  |              | {}            |            | NULL
-- asciiword| Word, all ASCII| running      | {english_stem}| english_stem| {run}
-- asciiword| Word, all ASCII| efficiently  | {english_stem}| english_stem| {effici}

-- This shows you:
-- The token type (asciiword, url, email, integer, etc.)
-- Which dictionaries were consulted (english_stem)
-- What lexeme was produced (the normalised form for indexing)

-- ─────────────────────────────────────────────────────────────────
-- SEE ALL TOKEN TYPES:
SELECT * FROM ts_token_type('default');
-- Lists: asciiword, word, numword, email, url, host, sfloat,
--        version, hword_numpart, hword_part, hword_asciipart,
--        numhword, asciihword, hword, url_path, file, float,
--        int, uint, entity

-- Understanding token types matters when you want to search for
-- URLs, email addresses, version numbers, or compound words.
```

### 2.2 Storing tsvector in the Table

For production use, you should store the pre-computed `tsvector` in a dedicated column rather than computing it on every query. This trades storage space for query performance — computing `to_tsvector()` on the fly adds CPU overhead to every search query and cannot be efficiently indexed in the same way a stored column can.

```sql
-- ADD A GENERATED TSVECTOR COLUMN (PostgreSQL 12+ with GENERATED ALWAYS AS):

ALTER TABLE articles ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (
        setweight(to_tsvector('english', COALESCE(title, '')),       'A') ||
        setweight(to_tsvector('english', COALESCE(subtitle, '')),    'B') ||
        setweight(to_tsvector('english', COALESCE(body, '')),        'C') ||
        setweight(to_tsvector('english', COALESCE(author_name, '')), 'D')
    ) STORED;
-- PostgreSQL automatically maintains this column on INSERT and UPDATE.
-- No trigger needed. No manual maintenance.

-- CREATE THE GIN INDEX on the stored column (covered in Section 6):
CREATE INDEX idx_articles_search ON articles USING GIN (search_vector);

-- NOW SEARCH IS SIMPLE AND FAST:
SELECT id, title, ts_rank(search_vector, query) AS rank
FROM articles, to_tsquery('english', 'postgresql & performance') query
WHERE search_vector @@ query
ORDER BY rank DESC
LIMIT 20;
```

Alternatively, for older PostgreSQL versions or more complex update logic, a trigger can maintain the `tsvector` column:

```sql
-- TRIGGER-MAINTAINED TSVECTOR (pre-PostgreSQL 12 approach):

ALTER TABLE articles ADD COLUMN search_vector tsvector;

CREATE OR REPLACE FUNCTION update_articles_search_vector()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector('english', COALESCE(NEW.title, '')),       'A') ||
        setweight(to_tsvector('english', COALESCE(NEW.subtitle, '')),    'B') ||
        setweight(to_tsvector('english', COALESCE(NEW.body, '')),        'C') ||
        setweight(to_tsvector('english', COALESCE(NEW.author_name, '')), 'D');
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_articles_search_vector
    BEFORE INSERT OR UPDATE OF title, subtitle, body, author_name
    ON articles
    FOR EACH ROW
    EXECUTE FUNCTION update_articles_search_vector();

-- Backfill existing rows:
UPDATE articles SET search_vector = (
    setweight(to_tsvector('english', COALESCE(title, '')),       'A') ||
    setweight(to_tsvector('english', COALESCE(subtitle, '')),    'B') ||
    setweight(to_tsvector('english', COALESCE(body, '')),        'C') ||
    setweight(to_tsvector('english', COALESCE(author_name, '')), 'D')
);
```

## 3. tsquery — The Search Expression

A `tsquery` represents a search expression — the query that you match against a `tsvector`. Where `tsvector` is the representation of a document, `tsquery` is the representation of a search intent. Both undergo the same normalisation (stemming, stop word removal) when created with language-aware functions, ensuring that "running" in the query matches "run" in the document.

PostgreSQL provides three functions for creating `tsquery` values, each with different rules for parsing user input. Understanding which one to use in each context is critical for both correctness and security.

```sql
-- ─────────────────────────────────────────────────────────────────
-- to_tsquery() — For programmatic queries with precise syntax control:

-- Operators must be explicit:
SELECT to_tsquery('english', 'postgresql & performance');
-- Searches for documents containing BOTH "postgresql" AND "performance"
-- After stemming: 'postgresql' & 'perform'

SELECT to_tsquery('english', 'postgresql | mysql');
-- OR: documents containing EITHER "postgresql" OR "mysql"

SELECT to_tsquery('english', '!oracle');
-- NOT: documents NOT containing "oracle"

SELECT to_tsquery('english', 'payment & !credit & processing');
-- Complex: contains "payment" AND "processing" but NOT "credit"

-- PHRASE search (words must appear in order, adjacent or with specified gap):
SELECT to_tsquery('english', 'payment <-> gateway');
-- Matches documents where "payment" is immediately followed by "gateway"
-- <-> means "followed by" (distance of 1 word)

SELECT to_tsquery('english', 'payment <2> gateway');
-- "payment" and "gateway" within 2 words of each other

-- Grouping:
SELECT to_tsquery('english', '(postgresql | mysql) & performance');
-- (postgresql OR mysql) AND performance

-- PREFIX search (matches any word starting with this prefix):
SELECT to_tsquery('english', 'data:*');
-- Matches: database, databases, datastore, datagram, etc.
-- The :* suffix enables prefix matching (bypasses stemming)

-- IMPORTANT: to_tsquery() raises an error for invalid syntax.
-- Never pass raw user input to to_tsquery() without sanitisation!
-- User types "payment &" → ERROR: syntax error in tsquery

-- ─────────────────────────────────────────────────────────────────
-- plainto_tsquery() — Safe for raw user input (AND semantics):

SELECT plainto_tsquery('english', 'postgresql performance tuning');
-- Result: 'postgresql' & 'perform' & 'tune'
-- Treats all words as AND. No operator syntax. User input is safe.

SELECT plainto_tsquery('english', 'payment & gateway -- drop table');
-- Result: 'payment' & 'gateway' & 'drop' & 'tabl'
-- The "--" and SQL operators are treated as plain text separators.
-- No SQL injection risk — input is not parsed as SQL.

-- ─────────────────────────────────────────────────────────────────
-- phraseto_tsquery() — Phrase search from raw input:

SELECT phraseto_tsquery('english', 'payment gateway processing');
-- Result: 'payment' <-> 'gateway' <-> 'process'
-- All words must appear in this exact order (phrase search)

-- ─────────────────────────────────────────────────────────────────
-- websearch_to_tsquery() — User-friendly syntax (PostgreSQL 11+):
-- The BEST choice for user-facing search boxes:

SELECT websearch_to_tsquery('english', 'postgresql performance -oracle');
-- Parses Google-style syntax:
-- + "postgresql performance -oracle" = postgresql AND performance NOT oracle
-- Result: 'postgresql' & 'perform' & !'oracl'

SELECT websearch_to_tsquery('english', '"payment gateway" processing');
-- Quoted phrases become phrase queries:
-- Result: 'payment' <-> 'gateway' & 'process'

SELECT websearch_to_tsquery('english', 'postgresql OR mysql');
-- OR keyword:
-- Result: 'postgresql' | 'mysql'

-- websearch_to_tsquery() NEVER raises errors on malformed input.
-- Invalid syntax is handled gracefully — perfect for user search boxes.

-- ─────────────────────────────────────────────────────────────────
-- THE MATCH OPERATOR — @@:

-- tsvector @@ tsquery: does the document match the query?
SELECT 'quick brown fox'::tsvector @@ 'fox'::tsquery;   -- true
SELECT 'quick brown fox'::tsvector @@ 'cat'::tsquery;   -- false

-- In a real query:
SELECT id, title
FROM articles
WHERE search_vector @@ websearch_to_tsquery('english', user_search_input)
ORDER BY ts_rank(search_vector,
                 websearch_to_tsquery('english', user_search_input)) DESC
LIMIT 20;
```

## 4. Text Search Configurations and Dictionaries

When you call `to_tsvector('english', ...)`, the string `'english'` refers to a **text search configuration** — a named collection of rules that governs the entire text processing pipeline: which dictionaries to use, which stop words to remove, and how to tokenise the input. Understanding configurations is what lets you extend full-text search beyond the defaults to support multiple languages, custom domain-specific terminology, and specialised normalisation.

A text search configuration is composed of three layers working in sequence.

**The Parser** is responsible for tokenisation — splitting the input text into tokens and categorising each one (word, number, email address, URL, etc.). PostgreSQL's default parser handles most Latin-script text correctly, including URLs, email addresses, and hyphenated compound words. The parser is rarely modified in practice.

**The Dictionaries** are applied to each token type to normalise and filter them. A dictionary either accepts a token and returns a lexeme (the normalised form for indexing) or rejects it (passing it to the next dictionary in the pipeline). The `simple` dictionary lowercases and accepts every word. The `english_stem` dictionary applies the Snowball English stemming algorithm and filters stop words. A `synonym` dictionary maps words to configured alternatives ("payment" → "payment, transfer, remittance"). Dictionaries are applied in order; the first one that accepts the token wins.

**The Configuration** binds token types to dictionary chains — it says "for asciiword tokens, consult english_stem; for integers, consult simple; for URLs, consult simple."

```sql
-- ─────────────────────────────────────────────────────────────────
-- VIEWING BUILT-IN CONFIGURATIONS:

SELECT cfgname, cfgparser, cfgowner
FROM pg_ts_config
ORDER BY cfgname;
-- Lists: arabic, danish, dutch, english, finnish, french, german,
--        greek, hungarian, indonesian, irish, italian, lithuanian,
--        nepali, norwegian, portuguese, romanian, russian, simple,
--        spanish, swedish, tamil, turkish

-- VIEWING A CONFIGURATION'S DICTIONARY CHAIN:
SELECT * FROM ts_debug('english', 'running databases efficiently');
-- Shows which dictionaries processed each token

-- ─────────────────────────────────────────────────────────────────
-- CREATING A CUSTOM CONFIGURATION — Domain-specific search:

-- Scenario: A product catalog that needs to:
-- 1. Stem words normally (english_stem)
-- 2. Map product abbreviations: "DB" → "database", "PG" → "postgresql"
-- 3. Treat product names as unstemmed (preserve "PostgreSQL" exactly)

-- Step 1: Create a synonym file at $PGDATA/global/product_synonyms.syn
-- Contents of product_synonyms.syn:
-- DB       database
-- DBMS     database management system
-- PG       postgresql
-- psql     postgresql

-- Step 2: Create the synonym dictionary:
CREATE TEXT SEARCH DICTIONARY product_synonyms (
    TEMPLATE = synonym,
    SYNONYMS = product_synonyms     -- References product_synonyms.syn file
);

-- Step 3: Create a new configuration based on 'english':
CREATE TEXT SEARCH CONFIGURATION product_search (COPY = english);

-- Step 4: Map token type 'asciiword' to our synonym dict FIRST,
-- then fall through to english_stem:
ALTER TEXT SEARCH CONFIGURATION product_search
    ALTER MAPPING FOR asciiword
    WITH product_synonyms, english_stem;

-- Step 5: Verify:
SELECT * FROM ts_debug('product_search', 'PG database performance');
-- 'PG' → product_synonyms → 'postgresql'
-- 'database' → english_stem → 'databas'
-- 'performance' → english_stem → 'perform'

-- Step 6: Use in queries:
SELECT id, title
FROM products
WHERE to_tsvector('product_search', description) @@
      to_tsquery('product_search', 'PG & performance');
-- Matches documents containing "postgresql" even if they never say "PG"

-- ─────────────────────────────────────────────────────────────────
-- MULTI-LANGUAGE SEARCH — Different configurations per row:

-- If your content can be in different languages, store the language
-- with each document and use it when creating the tsvector:

ALTER TABLE articles ADD COLUMN language REGCONFIG DEFAULT 'english';
ALTER TABLE articles ADD COLUMN search_vector tsvector;

CREATE OR REPLACE FUNCTION update_multilang_search_vector()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector(NEW.language, COALESCE(NEW.title, '')), 'A') ||
        setweight(to_tsvector(NEW.language, COALESCE(NEW.body, '')),  'C');
    RETURN NEW;
END;
$$;

-- Each document's tsvector is computed with its own language config:
-- A French article uses 'french' (different stop words, different stemmer)
-- A German article uses 'german' (handles compound words differently)

-- ─────────────────────────────────────────────────────────────────
-- STOP WORDS — Adding and removing:

-- View current English stop words:
SELECT word FROM pg_get_stopwords('english') ORDER BY word;
-- Lists: a, about, above, after, again, against, all, am, an, and, ...

-- Custom stop word list (for domain-specific content):
-- Create $PGDATA/tsearch_data/my_stop_words.stop with words, one per line.
-- Then reference it in a custom dictionary:
CREATE TEXT SEARCH DICTIONARY my_simple (
    TEMPLATE = pg_catalog.simple,
    STOPWORDS = my_stop_words       -- References my_stop_words.stop
);

-- For a legal database, you might stop "whereas", "hereinafter", "thereof"
-- For a medical database, "patient", "health" might be too common to index
```

## 5. Ranking — ts_rank and ts_rank_cd

Finding documents that match a query is only half the battle. In any non-trivial dataset, many documents will match, and the order in which they are presented to the user determines the quality of the search experience. A search result where the most relevant document appears on page three is effectively broken from the user's perspective.

PostgreSQL provides two ranking functions: `ts_rank` and `ts_rank_cd`. Both compute a floating-point relevance score for a `(tsvector, tsquery)` pair, but they use different algorithms and are sensitive to different aspects of the document.

### 5.1 ts_rank — Frequency-Based Ranking

`ts_rank` computes relevance based primarily on the **frequency** of matching lexemes in the document — how often the search terms appear relative to the total document length. A document that mentions "payment gateway" fifteen times in a short description is ranked higher than one that mentions it once in a thousand-word article.

```sql
-- ─────────────────────────────────────────────────────────────────
-- ts_rank SYNTAX:
-- ts_rank(tsvector, tsquery [, normalization_option])
-- ts_rank(weights[], tsvector, tsquery [, normalization_option])

-- Basic usage:
SELECT
    id,
    title,
    ts_rank(search_vector, to_tsquery('english', 'payment & gateway')) AS rank
FROM articles
WHERE search_vector @@ to_tsquery('english', 'payment & gateway')
ORDER BY rank DESC
LIMIT 10;

-- WITH WEIGHTS — Different field contributions:
-- weights[] = [D_weight, C_weight, B_weight, A_weight] in this order!
-- Default: {0.1, 0.2, 0.4, 1.0} means:
--   A-weighted match (title) = 1.0x contribution
--   B-weighted match (subtitle/tags) = 0.4x contribution
--   C-weighted match (description) = 0.2x contribution
--   D-weighted match (author) = 0.1x contribution

SELECT
    id,
    title,
    ts_rank(
        '{0.05, 0.2, 0.5, 1.0}',   -- Custom D, C, B, A weights
        search_vector,
        to_tsquery('english', 'payment & gateway')
    ) AS rank
FROM articles
WHERE search_vector @@ to_tsquery('english', 'payment & gateway')
ORDER BY rank DESC;

-- ─────────────────────────────────────────────────────────────────
-- NORMALISATION OPTIONS — Adjusting for document length bias:

-- Without normalisation, longer documents rank higher simply because
-- they have more opportunities for the query term to appear.
-- The normalization parameter adjusts for this.

-- normalization is a bitmask (values can be OR'd together with |):
-- 0 (default) = no normalisation
-- 1 = divide by (1 + log of document length)
-- 2 = divide by document length
-- 4 = divide by mean harmonic distance between extents
-- 8 = divide by number of unique words
-- 16 = divide by 1 + log of number of unique words
-- 32 = divide rank by itself + 1 (ranks between 0 and 0.5)

SELECT
    ts_rank(search_vector, query, 1)   AS rank_log_norm,
    ts_rank(search_vector, query, 2)   AS rank_length_norm,
    ts_rank(search_vector, query, 32)  AS rank_bounded_0_to_05,
    ts_rank(search_vector, query, 1|4) AS rank_combined  -- log + harmonic
FROM articles, to_tsquery('english', 'payment') query
WHERE search_vector @@ query;
```

### 5.2 ts_rank_cd — Cover Density Ranking

`ts_rank_cd` uses the **cover density** algorithm, which considers how closely matching terms are clustered together in the document. A document where "payment" and "gateway" appear consecutively in the same sentence is ranked higher than a document where "payment" appears in paragraph one and "gateway" appears in paragraph twenty. Cover density is generally more sophisticated than simple frequency and tends to produce better rankings for multi-term queries.

```sql
-- ts_rank_cd — Better for multi-term queries:
SELECT
    id,
    title,
    ts_rank_cd(search_vector, query) AS cd_rank
FROM articles,
     to_tsquery('english', 'payment & gateway & processing') query
WHERE search_vector @@ query
ORDER BY cd_rank DESC
LIMIT 10;

-- ts_rank_cd considers:
-- 1. How many of the query terms appear in the document
-- 2. How close together the matching terms are
-- 3. The weight class of each matching lexeme (A/B/C/D)
-- 4. Optionally, document length normalisation

-- Comparing ts_rank vs ts_rank_cd on the same query:
SELECT
    id,
    title,
    ts_rank(search_vector, query)    AS freq_rank,
    ts_rank_cd(search_vector, query) AS cover_rank,
    -- Length of document (proxy for word count):
    LENGTH(body) AS doc_length
FROM articles,
     to_tsquery('english', 'payment & gateway') query
WHERE search_vector @@ query
ORDER BY cover_rank DESC;
-- You will often find that ts_rank_cd surfaces shorter, more focused
-- documents higher, while ts_rank surfaces longer documents with more
-- total occurrences of the terms.
```

### 5.3 Combining Ranking with Other Signals

Pure text relevance ranking is rarely sufficient for a great search experience. Production search systems combine text relevance with other signals — recency, popularity, user personalisation — using a composite scoring expression.

```sql
-- COMPOSITE RANKING — Combining text relevance with business signals:

SELECT
    a.id,
    a.title,
    a.published_at,
    a.view_count,

    -- Pure text relevance:
    ts_rank_cd(a.search_vector, query)          AS text_rank,

    -- Recency decay: documents lose relevance as they age
    -- EXP(-age_in_days / 30) gives ~37% weight loss after 30 days
    EXP(-EXTRACT(EPOCH FROM (NOW() - a.published_at)) / (86400 * 30))
                                                AS recency_score,

    -- Popularity signal (log to prevent domination by viral articles):
    LOG(GREATEST(a.view_count, 1) + 1)          AS popularity_score,

    -- COMPOSITE SCORE: weighted combination of all signals:
    (
        0.6 * ts_rank_cd(a.search_vector, query)
        +
        0.3 * EXP(-EXTRACT(EPOCH FROM (NOW() - a.published_at)) / (86400 * 30))
        +
        0.1 * (LOG(GREATEST(a.view_count, 1) + 1) / 10.0)  -- normalise to ~0-1
    ) AS composite_score

FROM articles a,
     websearch_to_tsquery('english', 'payment gateway') query
WHERE a.search_vector @@ query
ORDER BY composite_score DESC
LIMIT 20;

-- The weights (0.6, 0.3, 0.1) encode your business priorities:
-- 60% of the score comes from text relevance
-- 30% from recency (newer content preferred)
-- 10% from popularity (high-traffic content slightly boosted)
-- Tune these weights based on your users' behaviour patterns.
```

## 6. GIN Indexes for Full-Text Search

Without an index, full-text search requires computing `to_tsvector()` for every row in the table on every query — a full table scan that grows linearly with table size. On a million-row table, this is unacceptably slow. The **GIN (Generalised Inverted Index)** is the standard index type for full-text search in PostgreSQL, enabling sub-millisecond search even on tables with millions of documents.

A GIN index for full-text search works as an **inverted index** — the same structure that powers every serious search engine. Instead of mapping from document to content (like a forward index), an inverted index maps from each lexeme to the list of documents containing it. When you search for "payment", the GIN index immediately returns the list of document IDs that contain the lexeme "payment" — without scanning any actual document content. For a two-term query ("payment & gateway"), the index returns the intersection of both lists. This intersection operation on sorted ID lists is extremely fast.

```sql
-- ─────────────────────────────────────────────────────────────────
-- CREATING A GIN INDEX:

-- On a stored tsvector column (preferred — fastest queries):
CREATE INDEX idx_articles_fts
    ON articles
    USING GIN (search_vector);
-- This is the recommended approach. Build the tsvector once (stored column),
-- index the stored column. Queries are fast and simple.

-- On an expression (compute tsvector inline — not cached):
CREATE INDEX idx_articles_fts_expression
    ON articles
    USING GIN (to_tsvector('english', title || ' ' || body));
-- The index stores the computed tsvectors. PostgreSQL recomputes the
-- expression for comparison when checking index validity during writes.
-- Less flexible than a stored column but valid for simpler cases.

-- PARTIAL GIN INDEX — Index only a subset of rows:
CREATE INDEX idx_articles_fts_published
    ON articles
    USING GIN (search_vector)
    WHERE published = TRUE AND deleted_at IS NULL;
-- Index is smaller (only published, non-deleted articles).
-- Queries that include the same WHERE conditions can use this index.
-- For most search boxes, users only want published content anyway.

-- ─────────────────────────────────────────────────────────────────
-- GIN vs GiST FOR FULL-TEXT:

-- GIN (Generalised Inverted Index):
--   Index size: LARGER (stores all lexemes explicitly)
--   Build time: SLOWER (more work to build)
--   Query time: FASTER (exact lookups)
--   Update cost: HIGHER (index must be updated on every document change)
--   Best for: Read-heavy search (most production scenarios)

-- GiST (Generalised Search Tree):
--   Index size: SMALLER (uses signatures / lossy compression)
--   Build time: FASTER
--   Query time: SLOWER (may have false positives requiring heap check)
--   Update cost: LOWER
--   Best for: Write-heavy tables where search is secondary concern

-- For full-text search: almost always use GIN.
-- GiST's false positives add extra heap lookups that negate its advantages
-- for most search workloads.

-- ─────────────────────────────────────────────────────────────────
-- GIN INDEX MAINTENANCE:

-- fastupdate: GIN accumulates updates in a pending list before merging
-- into the main index structure. This makes writes faster at the cost
-- of slightly slower reads until cleanup runs.

CREATE INDEX idx_articles_fts
    ON articles
    USING GIN (search_vector)
    WITH (fastupdate = on);         -- Default: on
-- fastupdate = off: writes are slower but reads are consistently fast.
-- Disable if you observe periodic query slowdowns during index merges.

-- GIN index pending list size (default 4MB):
-- SET gin_pending_list_limit = '64MB';  -- Reduce merge frequency
-- Larger pending list = less frequent merges = less write interruption

-- CHECKING INDEX SIZE:
SELECT
    indexname,
    pg_size_pretty(pg_relation_size(indexname::REGCLASS)) AS index_size
FROM pg_indexes
WHERE tablename = 'articles';

-- CHECKING IF THE INDEX IS BEING USED:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM articles
WHERE search_vector @@ to_tsquery('english', 'payment & gateway');
-- Look for "Bitmap Index Scan on idx_articles_fts" in the plan.
-- If you see "Seq Scan" instead, the planner chose not to use the index
-- (possible for very broad queries returning > 10-20% of the table).
```

## 7. Building a Complete Search System

Let us assemble everything into a production-ready full-text search implementation for a typical content platform — a product with articles, products, and documentation pages, all searchable from a unified search box.

```sql
-- ─────────────────────────────────────────────────────────────────
-- SCHEMA — Search-Ready Articles Table:

CREATE TABLE articles (
    id              BIGSERIAL PRIMARY KEY,
    title           TEXT NOT NULL,
    subtitle        TEXT,
    body            TEXT NOT NULL,
    author_name     TEXT NOT NULL,
    tags            TEXT[],             -- Array of tags
    category        TEXT,
    language        REGCONFIG NOT NULL DEFAULT 'english',
    published       BOOLEAN NOT NULL DEFAULT FALSE,
    view_count      BIGINT NOT NULL DEFAULT 0,
    published_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at      TIMESTAMPTZ,

    -- Pre-computed search vector (maintained automatically):
    search_vector   TSVECTOR GENERATED ALWAYS AS (
        setweight(to_tsvector(language, COALESCE(title, '')),       'A') ||
        setweight(to_tsvector(language, COALESCE(subtitle, '')),    'B') ||
        setweight(to_tsvector(language,
            COALESCE(ARRAY_TO_STRING(tags, ' '), '')),              'B') ||
        setweight(to_tsvector(language, COALESCE(category, '')),    'B') ||
        setweight(to_tsvector(language, COALESCE(body, '')),        'C') ||
        setweight(to_tsvector(language, COALESCE(author_name, '')), 'D')
    ) STORED
);

-- GIN INDEX on the stored vector:
CREATE INDEX idx_articles_fts
    ON articles
    USING GIN (search_vector);

-- PARTIAL INDEX for the common case (published, not deleted):
CREATE INDEX idx_articles_fts_published
    ON articles USING GIN (search_vector)
    WHERE published = TRUE AND deleted_at IS NULL;

-- B-Tree indexes for filtering/sorting (separate from FTS):
CREATE INDEX idx_articles_published_at ON articles (published_at DESC);
CREATE INDEX idx_articles_category     ON articles (category);
CREATE INDEX idx_articles_language     ON articles (language);

-- ─────────────────────────────────────────────────────────────────
-- SEARCH FUNCTION — Complete search with all features:

CREATE OR REPLACE FUNCTION search_articles(
    p_query          TEXT,
    p_category       TEXT       DEFAULT NULL,
    p_language       REGCONFIG  DEFAULT 'english',
    p_limit          INT        DEFAULT 20,
    p_offset         INT        DEFAULT 0,
    p_min_rank       FLOAT4     DEFAULT 0.01      -- Filter out very low relevance
)
RETURNS TABLE (
    article_id    BIGINT,
    title         TEXT,
    subtitle      TEXT,
    author_name   TEXT,
    category      TEXT,
    published_at  TIMESTAMPTZ,
    view_count    BIGINT,
    text_rank     FLOAT4,
    composite_rank FLOAT4,
    headline      TEXT    -- Highlighted snippet with matching terms
)
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
    v_query tsquery;
BEGIN
    -- Parse user input safely:
    v_query := websearch_to_tsquery(p_language, p_query);

    -- Handle empty query (all results, no ranking):
    IF v_query IS NULL OR p_query = '' THEN
        RETURN QUERY
        SELECT
            a.id, a.title, a.subtitle, a.author_name, a.category,
            a.published_at, a.view_count,
            0::FLOAT4 AS text_rank,
            0::FLOAT4 AS composite_rank,
            ''         AS headline
        FROM articles a
        WHERE a.published = TRUE
          AND a.deleted_at IS NULL
          AND (p_category IS NULL OR a.category = p_category)
        ORDER BY a.published_at DESC
        LIMIT p_limit OFFSET p_offset;
        RETURN;
    END IF;

    RETURN QUERY
    SELECT
        a.id,
        a.title,
        a.subtitle,
        a.author_name,
        a.category,
        a.published_at,
        a.view_count,

        -- Pure text relevance (cover density):
        ts_rank_cd(a.search_vector, v_query, 4)::FLOAT4 AS text_rank,

        -- Composite score (text + recency + popularity):
        (
            0.65 * ts_rank_cd(a.search_vector, v_query, 4)
            +
            0.25 * EXP(-EXTRACT(EPOCH FROM (NOW() - COALESCE(a.published_at, a.created_at)))
                        / (86400.0 * 90))   -- 90-day half-life
            +
            0.10 * LEAST(LOG(a.view_count + 1) / 10.0, 1.0)
        )::FLOAT4 AS composite_rank,

        -- Generate highlighted snippet with matching terms:
        ts_headline(
            p_language::TEXT,
            a.body,
            v_query,
            'StartSel=<mark>, StopSel=</mark>, MaxWords=35, MinWords=15, '
            'ShortWord=3, HighlightAll=false, MaxFragments=2, '
            'FragmentDelimiter=<br/>…<br/>'
        ) AS headline

    FROM articles a
    WHERE a.published = TRUE
      AND a.deleted_at IS NULL
      AND a.language = p_language
      AND (p_category IS NULL OR a.category = p_category)
      AND a.search_vector @@ v_query                    -- FTS match (uses GIN)
      AND ts_rank_cd(a.search_vector, v_query) >= p_min_rank
    ORDER BY composite_rank DESC
    LIMIT p_limit
    OFFSET p_offset;
END;
$$;

-- USAGE:
SELECT * FROM search_articles('postgresql performance tuning');
SELECT * FROM search_articles('payment gateway', 'technology', 'english', 10, 0);
SELECT * FROM search_articles('"machine learning" optimization');
```

## 8. Advanced Search Patterns

### 8.1 ts_headline — Search Result Snippets

`ts_headline` generates a highlighted text snippet showing the context in which the search terms appear. This is the "results preview" text you see in every search engine — the sentence fragment with the matching terms highlighted.

```sql
-- ts_headline — Highlighted Snippets:

SELECT
    title,
    ts_headline(
        'english',                      -- text search configuration
        body,                           -- the text to generate headline from
        to_tsquery('english', 'payment & gateway'),  -- the query
        -- Options:
        'StartSel=<b>, '               -- wrap match start with <b>
        'StopSel=</b>, '               -- wrap match end with </b>
        'MaxWords=30, '                -- max words in snippet
        'MinWords=15, '                -- min words in snippet
        'ShortWord=4, '                -- words shorter than this are not highlighted
        'HighlightAll=false, '         -- don't highlight entire document
        'MaxFragments=3, '             -- return up to 3 separate fragments
        'FragmentDelimiter= ... '      -- separate fragments with " ... "
    ) AS snippet
FROM articles
WHERE search_vector @@ to_tsquery('english', 'payment & gateway')
LIMIT 5;

-- Example output for snippet:
-- "Configure your <b>payment</b> <b>gateway</b> by navigating to ... 
--  the <b>payment</b> settings panel and entering your <b>gateway</b> credentials"
```

### 8.2 Prefix Search and Autocomplete

A common requirement is autocomplete — returning suggestions as the user types. Full-text search handles this through the prefix operator (`:*`).

```sql
-- PREFIX SEARCH — Autocomplete as user types:

-- User has typed "paym" — show suggestions:
SELECT id, title
FROM articles
WHERE search_vector @@ to_tsquery('english', 'paym:*')
ORDER BY ts_rank(search_vector, to_tsquery('english', 'paym:*')) DESC
LIMIT 5;
-- Matches: payment, payments, payment-gateway, paymaster, paymail, etc.

-- NOTE: to_tsquery with :* does not stem the prefix.
-- 'paym:*' matches any lexeme starting with 'paym', as-is.
-- This is intentional — you want to match all prefix variants.

-- BETTER AUTOCOMPLETE — Distinct suggestions from a dictionary table:
-- For high-quality autocomplete, maintain a separate suggestions table
-- populated by the most common search queries and product names,
-- then use prefix search on THAT table:

CREATE TABLE search_suggestions (
    id          BIGSERIAL PRIMARY KEY,
    suggestion  TEXT NOT NULL,
    frequency   BIGINT NOT NULL DEFAULT 1,
    search_vec  TSVECTOR GENERATED ALWAYS AS (
        to_tsvector('simple', suggestion)   -- 'simple' = no stemming for exact prefix
    ) STORED
);

CREATE INDEX idx_suggestions_fts ON search_suggestions USING GIN (search_vec);
CREATE INDEX idx_suggestions_freq ON search_suggestions (frequency DESC);

-- Autocomplete query:
SELECT suggestion, frequency
FROM search_suggestions
WHERE search_vec @@ to_tsquery('simple', LOWER(user_prefix) || ':*')
ORDER BY frequency DESC
LIMIT 10;
```

### 8.3 Similarity Search with pg_trgm

Sometimes users misspell search terms. PostgreSQL's `pg_trgm` extension provides **trigram-based similarity search** — comparing sequences of three consecutive characters to measure how similar two strings are. This handles typos and fuzzy matching that full-text search cannot.

```sql
-- TRIGRAM SIMILARITY — Fuzzy matching for typos:

CREATE EXTENSION pg_trgm;

-- Find articles with titles similar to a misspelled query:
SELECT title, similarity(title, 'postgresq databas')  AS sim_score
FROM articles
WHERE similarity(title, 'postgresq databas') > 0.2    -- Threshold: 0-1
ORDER BY sim_score DESC
LIMIT 5;
-- Matches: "PostgreSQL Database Administration", "PostgreSQL Tutorial", etc.
-- even though both words are misspelled.

-- GiST index for fast trigram search:
CREATE INDEX idx_articles_title_trgm ON articles USING GiST (title gist_trgm_ops);
-- OR GIN index (faster for equality/similarity, larger size):
CREATE INDEX idx_articles_title_trgm ON articles USING GIN (title gin_trgm_ops);

-- COMBINING FTS AND TRIGRAM — Best of both worlds:
SELECT
    id,
    title,
    GREATEST(
        ts_rank(search_vector, websearch_to_tsquery('english', query_text)),
        similarity(title, query_text)
    ) AS best_score
FROM articles,
     LATERAL (SELECT 'postgresq performance' AS query_text) q
WHERE
    -- Match via FTS (handles stemming and boolean operators):
    search_vector @@ websearch_to_tsquery('english', q.query_text)
    OR
    -- Match via trigram (handles typos):
    title % q.query_text                          -- % = similarity threshold operator
ORDER BY best_score DESC
LIMIT 10;
```

## 9. When to Reach for Elasticsearch Instead

PostgreSQL's full-text search is genuinely powerful and covers the needs of many real production applications. But there are specific scenarios where its limitations become significant enough to justify the operational overhead of a dedicated search engine like Elasticsearch. Making this decision incorrectly in either direction is costly — choosing Elasticsearch prematurely adds significant complexity; staying with PostgreSQL too long creates a poor search experience at scale.

Here is an honest, criterion-by-criterion analysis of where each solution belongs.

```
POSTGRESQL FTS vs ELASTICSEARCH — Decision Framework:

CRITERION              │ PostgreSQL FTS      │ Elasticsearch
───────────────────────┼─────────────────────┼──────────────────────────────

                       │ with good GIN perf  │ (distributed by design)
───────────────────────┼─────────────────────┼──────────────────────────────

                       │ QPS on single node  │ search requests
───────────────────────┼─────────────────────┼──────────────────────────────
Search Latency         │ 10-200ms typical    │ 1-20ms with caching and
                       │ (depends on doc     │ distributed execution
                       │ count and query)    │
───────────────────────┼─────────────────────┼──────────────────────────────
Relevance Tuning       │ ts_rank, ts_rank_cd │ BM25, field boosting, script
                       │ + composite scoring │ scoring, learning-to-rank
                       │ Good for basic needs│ (sophisticated ML ranking)
───────────────────────┼─────────────────────┼──────────────────────────────
Faceted Search         │ Possible with GROUP │ Native, fast, deeply
                       │ BY + subqueries     │ integrated with search
                       │ (can be slow)       │

                       │ based setup)        │ runtime updateable

Autocomplete           │ Prefix search       │ Dedicated completion

───────────────────────┼─────────────────────┼──────────────────────────────
Geospatial Search      │ PostGIS (excellent!)│ Geo queries (good)

```

**Choose PostgreSQL FTS when:** your dataset is under 10 million documents, search is one feature among many (not the core product), you need transactional consistency between data changes and search (a new product is immediately searchable after INSERT commits), your ranking requirements are straightforward (relevance + recency + popularity is enough), and your team does not have dedicated search engineering expertise.

**Choose Elasticsearch when:** search is the core product or a primary user-facing feature that materially affects revenue and retention; your dataset exceeds 10-20 million documents and is growing; you need sub-10ms search latency at high concurrency; you need sophisticated ranking features like machine-learning-based relevance scoring, per-field per-analyzer synonym management, or semantic search via vector embeddings; you need rich faceted navigation with real-time facet counts; or you need to search across data from multiple databases and systems (Elasticsearch as a search layer over many data sources).

**The hybrid approach** is often the right answer for growing systems: start with PostgreSQL FTS (it will handle your needs for longer than you expect), instrument search quality metrics (are users finding what they need? What queries produce zero results?), and migrate to Elasticsearch only when you hit a concrete, measurable limitation — not in anticipation of growth that may not materialise. The synchronisation pipeline you build when migrating (change data capture from PostgreSQL to Elasticsearch via Debezium or a similar CDC tool) is non-trivial, but it is a well-understood pattern.

```
MIGRATION PATH — PostgreSQL FTS → Elasticsearch:

Phase 1: PostgreSQL FTS (current)
  ┌─────────────────────────────────────────────────────────┐
  │  PostgreSQL                                             │
  │  Data + search_vector column + GIN index               │
  │  Application queries PostgreSQL directly                │
  └─────────────────────────────────────────────────────────┘

Phase 2: Dual-write (transition)
  ┌─────────────────┐     ┌─────────────────────────────────┐
  │  PostgreSQL     │────►│  Elasticsearch (via Debezium    │
  │  (source of     │ CDC │  or direct indexing)            │
  │  truth)         │     │                                 │
  └─────────────────┘     └─────────────────────────────────┘
  Both systems have the data. Test Elasticsearch quality.
  Still use PostgreSQL for search (safety net).

Phase 3: Elasticsearch primary
  Application routes search queries to Elasticsearch.
  PostgreSQL remains source of truth for data.
  Sync pipeline (CDC) keeps Elasticsearch updated.
  PostgreSQL FTS index can be dropped to save space.
```

│                          │ % operator: above threshold match        │
│                          │ GIN/GiST index on column gin_trgm_ops   │
│                          │ Complements FTS — handles misspellings.  │

PRODUCTION FULL-TEXT SEARCH CHECKLIST:
  □ Store tsvector as GENERATED ALWAYS AS STORED column
  □ Use setweight() for title(A), tags(B), body(C), author(D)
  □ Create GIN index on stored tsvector column
  □ Consider partial GIN index for active/published rows
  □ Use websearch_to_tsquery() for user-facing search boxes (never to_tsquery)
  □ Use ts_rank_cd() for multi-term ranking (better than ts_rank)
  □ Add recency and popularity to composite score
  □ Use ts_headline() for result snippets
  □ Add pg_trgm for fuzzy/autocomplete if needed
  □ Set text_search_config for your primary language in postgresql.conf
  □ Test with EXPLAIN ANALYZE to confirm GIN index is used

QUICK SEARCH QUERY TEMPLATE:
  SELECT
      id, title,
      ts_rank_cd(search_vector, q) AS rank,
      ts_headline('english', body, q,
          'StartSel=<mark>, StopSel=</mark>, MaxFragments=2') AS snippet
  FROM articles,
       websearch_to_tsquery('english', :user_input) q
  WHERE published = TRUE
    AND search_vector @@ q
  ORDER BY rank DESC
  LIMIT 20;

USE POSTGRESQL FTS WHEN:
  ✓ < 10M documents
  ✓ Search is one feature, not the core product
  ✓ Need transactional consistency (new data immediately searchable)
  ✓ Team has no dedicated search engineering expertise
  ✓ Basic relevance ranking is sufficient

USE ELASTICSEARCH WHEN:
  ✓ > 10-20M documents or very high search QPS
  ✓ Search is the core product (significant revenue impact)
  ✓ Need ML-based ranking or semantic/vector search
  ✓ Need rich faceted navigation with fast aggregations
  ✓ Need advanced synonym/analyzer management per-field
  ✓ Sub-10ms latency requirement at high concurrency

---

_The best search experience is not the most technically sophisticated one — it is the one that returns the right document first, every time, for every user. PostgreSQL's full-text search, properly configured with weights, composite ranking, and a GIN index, can achieve this for most applications. Its greatest virtue is not raw power but integration: the search index lives in the same transaction as the data, there is no synchronisation to break, no eventual consistency to reason about, and no additional system to operate._

_When you find yourself genuinely hitting PostgreSQL's limits — when ten million documents starts feeling slow, when users need faceted search with real-time counts, when your ranking requirements have grown to include machine-learned relevance signals — then Elasticsearch earns its operational overhead. But treat that migration as a consequence of success, not a prerequisite for it._

_Start with what you have. Make it excellent. Complicate only when forced to._
