# Database Logging — A Deep Study Guide

> _"Logs are the black box of your database. You will never need them — right up until the moment you need them desperately, and then they are the only thing standing between you and complete darkness."_ — Every incident commander who has ever said "pull the logs" and heard "we don't have those"

---

## A Letter from Your DBA Mentor Before We Begin

In the previous guide, we talked about metrics — numbers that tell you the current state of your database in aggregate. Metrics answer "how many" and "how fast" and "what percentage." They are invaluable for dashboards and alerts.

But metrics cannot tell you _why_. When a query is slow, your latency P99 metric tells you it is slow. It does not tell you which specific query, what it was doing, which table scan it performed, what index it missed, or what it was waiting for. When a deadlock occurs, your deadlock counter increments. It does not tell you which two transactions deadlocked, what rows they were fighting over, or which line of application code caused the conflict.

Logs are the narrative that metrics cannot provide. They are the detailed, chronological record of events — each entry a complete story of something that happened: a query that exceeded a time threshold, an error that the database encountered, a lock that two transactions fought over until one of them died. Logs answer the "why" that metrics can only hint at.

The problem with database logs is that they are voluminous. A production PostgreSQL instance processing three thousand queries per second, if it logged every single query, would generate gigabytes of log data per hour. Storing, transmitting, and querying that much data is expensive. The art of database logging is choosing exactly what to log — enough to diagnose every problem you will ever encounter, but not so much that the logging system itself becomes the problem.

Today we will study each category of database log, understand what it captures and why, learn to configure it correctly, and build the pipeline that ships these logs to a centralised system where they can be searched, correlated, and alerted upon. By the end, you will never again be in an incident wondering "but why did this query run slowly?" — because the slow query log will have already written down the answer.

## 1. The Logging Philosophy — Signal Without Noise

Before configuring a single log parameter, you must understand the fundamental tension that governs every logging decision: **every log entry has a cost, and every missing log entry has a different cost.** Logging too much degrades database performance, fills disks, and drowns your team in noise until they stop reading logs at all. Logging too little means that when an incident occurs, you are investigating blind.

The resolution of this tension is not a fixed formula — it is a set of principles that you apply to your specific workload, your storage budget, and your operational requirements.

The first principle is **log events, not volume.** You do not need a log entry for every query that runs normally. You need a log entry for every query that behaves abnormally — that takes longer than expected, that produces an error, that causes a lock conflict. Normal behaviour should be visible only through metrics (the aggregate numbers). Abnormal behaviour should be visible through logs (the specific details of each incident).

The second principle is **log at the boundary of acceptable performance.** The slow query log threshold is your statement of what "too slow" means. Setting it correctly requires knowing your SLO (Service Level Objective). If your P99 latency target is 200ms, your slow query threshold might be 100ms — queries that take longer than half your SLO budget deserve investigation. Threshold calibration is the most consequential decision in slow query log configuration.

The third principle is **log context, not just content.** A log entry that says "slow query: 450ms" is almost useless. A log entry that says "slow query: 450ms, user: app_service, client: 10.0.1.5, statement: SELECT * FROM orders WHERE customer_id = 42 AND status = 'pending', rows returned: 12847, seq scan on orders: 5.2M rows examined" tells you everything you need to know to diagnose and fix the problem. The `log_line_prefix` and auxiliary log parameters are what turn the first kind of entry into the second.

```
THE LOGGING DECISION FRAMEWORK:

For every potential log event, ask three questions:

1. Will I need this to diagnose a problem I cannot predict in advance?
   YES → Log it.
   NO  → Skip it (metrics cover normal behaviour).

2. Is this event rare enough that its log volume is manageable?
   YES → Log it at full detail.
   NO  → Log it at reduced detail, or sample it, or raise the threshold.

3. Does this event contain information not available anywhere else?
   YES → Log it immediately, never lose it.
   NO  → Consider whether metrics alone are sufficient.

─────────────────────────────────────────────────────────────────────
WHAT EACH LOG TYPE TELLS YOU THAT METRICS CANNOT:

Metric: P99 query latency = 450ms (↑ from baseline 12ms)
  → Something is slower than usual. What? Where?

Slow Query Log: Captures the specific query, parameters, plan info.
  → "SELECT * FROM orders WHERE customer_id = $1 AND status = $2
     took 450ms, sequential scan, 5.2M rows examined, customer_id
     has no index when combined with status filter."
  → Diagnosis: missing composite index on (customer_id, status).
  → Fix: CREATE INDEX CONCURRENTLY ON orders (customer_id, status).

─────────────────────────────────────────────────────────────────────

Metric: Deadlock counter = 3 in last hour (↑ from 0 baseline)
  → Deadlocks are happening. Between what?

Deadlock Log: Captures both transactions, the rows they fought over.
  → "Process 12345 (UPDATE orders SET status='shipped' WHERE id=101)
     deadlocked with Process 12346 (UPDATE inventory SET qty=qty-1
     WHERE product_id=88). Waiting for ShareLock on tuple (0,42)."
  → Diagnosis: Two code paths acquire locks on orders and inventory
     in opposite orders.
  → Fix: Standardise lock acquisition order in both code paths.
```

## 2. Slow Query Log — Finding the Queries That Hurt You

The slow query log is the single most valuable operational tool in database performance management. It is a record of every query that exceeded a configurable duration threshold, with enough contextual detail to diagnose why the query was slow and how to fix it. Every production database should have a slow query log configured and actively monitored.

In PostgreSQL, slow query logging is controlled primarily by `log_min_duration_statement` — a parameter that specifies the minimum execution time (in milliseconds) for a query to be written to the log. Any query that takes longer than this threshold is logged. Set it to `0` and every query is logged (useful briefly for debugging but never for production due to volume). Set it to `-1` and slow query logging is disabled entirely. In production, a value between 100ms and 1000ms is typical, calibrated to your SLO as discussed above.

```ini
# ─────────────────────────────────────────────────────────────────
# postgresql.conf — SLOW QUERY LOG CONFIGURATION:

# Minimum execution time to log (milliseconds):
# -1 = disabled, 0 = log everything, 100 = log queries taking >100ms
log_min_duration_statement = 100        # Log queries taking > 100ms

# Log parameters (values substituted for $1, $2 placeholders):
log_min_duration_sample = 0             # Sample all queries for duration
log_parameter_max_length = 1024         # Max parameter value length in log
log_parameter_max_length_on_error = 64  # Shorter on error messages

# What to include in every log line:
# %t = timestamp, %p = PID, %u = user, %d = database,
# %r = remote host:port, %a = application name, %i = command tag
# %e = SQL error code, %c = session ID, %l = line number in session
log_line_prefix = '%t [%p] %u@%d %r %a %i '

# Log duration of ALL statements (complement to min_duration):
log_duration = off                      # off in production (too verbose)

# Log statement text for specific categories:
log_statement = 'none'                  # none, ddl, mod, all
# 'ddl' = log all DDL (CREATE, ALTER, DROP) — recommended for audit
# 'mod' = DDL + DML that modify data
# 'all' = every statement (only for short debugging sessions)
# For slow query log, 'none' here — log_min_duration_statement handles it

# Auto-explain: log query PLAN for slow queries (invaluable for diagnosis):
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = 100     # Same threshold as slow query log
auto_explain.log_analyze = true         # Include EXPLAIN ANALYZE output
auto_explain.log_buffers = true         # Include buffer usage in plan
auto_explain.log_timing = true          # Include per-node timing
auto_explain.log_triggers = false       # Skip trigger stats (too verbose)
auto_explain.log_nested_statements = false  # Skip statements in functions
auto_explain.log_format = 'text'        # text or json (json for parsing)

# Log destination:
log_destination = 'stderr'             # stderr (captured by systemd/Docker)
logging_collector = on                 # Collect logs into files
log_directory = 'pg_log'              # Log directory (relative to data dir)
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'  # Rotate daily
log_rotation_age = 1d                  # New file each day
log_rotation_size = 100MB              # Also rotate when file hits 100MB
log_truncate_on_rotation = off         # Don't truncate when rotating by age
```

A slow query log entry in PostgreSQL, with the configuration above including `auto_explain`, looks like this:

```
2026-09-05 14:23:01.847 UTC [12345] app_service@production 10.0.1.5:54321 OrderService SELECT
  duration: 450.231 ms
  statement: SELECT id, customer_id, status, total_amount, created_at
             FROM orders
             WHERE customer_id = $1 AND status = $2
             ORDER BY created_at DESC
             LIMIT 50
  parameters: $1 = '42', $2 = 'pending'

2026-09-05 14:23:01.847 UTC [12345] app_service@production 10.0.1.5:54321 OrderService
  Query Text: SELECT id, customer_id, status, ...
  Query Plan:
    Limit  (cost=12.45..62.45 rows=50 width=57)
           (actual time=0.089..450.124 rows=50 loops=1)
      ->  Sort  (cost=12.45..112.45 rows=40000 width=57)
                (actual time=0.086..448.891 rows=50 loops=1)
            Sort Key: created_at DESC
            Sort Method: top-N heapsort  Memory: 30kB
          ->  Seq Scan on orders
                (cost=0.00..8.00 rows=40000 width=57)
                (actual time=0.024..310.442 rows=40000 loops=1)
                Buffers: shared read=8192
                Filter: ((customer_id = 42) AND (status = 'pending'))
                Rows Removed by Filter: 5160000
  Planning Time: 0.219 ms
  Execution Time: 450.231 ms
```

This single log entry tells you everything: the query, the parameters, the execution plan, that it did a sequential scan reading 8,192 data blocks (disk I/O), that it examined 5,200,000 rows and discarded all but 40,000, and then sorted 40,000 rows to find the top 50. The fix is obvious from the plan: a composite index on `(customer_id, status, created_at DESC)` would let this query use an index scan and skip the sort entirely.

For MySQL, the slow query log is controlled by similarly named parameters in `my.cnf`:

```ini
# ─────────────────────────────────────────────────────────────────
# my.cnf — MySQL SLOW QUERY LOG CONFIGURATION:

[mysqld]
slow_query_log = 1                      # Enable slow query log
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 0.1                   # 100ms threshold (in seconds)

# Log queries that do NOT use indexes (always worth logging):
log_queries_not_using_indexes = 1
log_throttle_queries_not_using_indexes = 60  # Max 60 such logs/minute

# Log slow admin statements (OPTIMIZE TABLE, REPAIR TABLE, etc.):
log_slow_admin_statements = 1

# Log slow replica SQL thread queries:
log_slow_replica_statements = 1

# Output format: FILE (default) or TABLE (mysql.slow_log table):
log_output = FILE

# Include full query with parameters (vs. normalised query):
# MySQL's slow log includes actual parameter values by default

# Performance Schema alternative (more granular, queryable):
performance_schema = ON
# SELECT * FROM performance_schema.events_statements_history_long
# WHERE TIMER_WAIT > 100000000000;  -- > 100ms in picoseconds
```

A powerful tool for analysing slow query log files after the fact is **pgBadger** for PostgreSQL and **pt-query-digest** (part of Percona Toolkit) for MySQL. These tools parse log files and produce aggregated reports showing the top slow queries by total time, average time, and call count — exactly the same information as `pg_stat_statements`, but derived from log files rather than in-database statistics. This is valuable when you need to analyse a historical period, a specific time window, or logs from an instance where `pg_stat_statements` was not installed.

```bash
# PGBADGER — Analyse PostgreSQL slow query logs:
# Installation: apt-get install pgbadger  OR  brew install pgbadger

# Analyse a single log file, generate HTML report:
pgbadger /var/log/postgresql/postgresql-2026-09-05.log \
  --outfile report-2026-09-05.html \
  --format stderr \
  --prefix '%t [%p] %u@%d %r %a %i '

# Analyse last 7 days of logs:
pgbadger /var/log/postgresql/postgresql-*.log \
  --outfile weekly-report.html \
  --begin "2026-09-01 00:00:00" \
  --end "2026-09-07 23:59:59"

# PT-QUERY-DIGEST — Analyse MySQL slow query logs:
# Installation: apt-get install percona-toolkit

pt-query-digest /var/log/mysql/slow.log \
  --since "2026-09-05 00:00:00" \
  --until "2026-09-05 23:59:59" \
  --output report \
  --limit 20 \
  > slow_query_report.txt
# Output: Top 20 queries by total time, with sample slow query,
#         fingerprint (normalised form), execution count, timing percentiles
```

## 3. Error Log — The Database's Complaint Department

The error log is the database's primary communication channel for everything that goes wrong: connection failures, authentication errors, constraint violations, out-of-memory conditions, corrupt data pages, file I/O errors, and any other event that the database considers noteworthy enough to record. Unlike the slow query log, which you configure based on performance thresholds, the error log captures events based on their severity — and you control which severity levels get written.

PostgreSQL uses a hierarchy of severity levels: `DEBUG5`, `DEBUG4`, `DEBUG3`, `DEBUG2`, `DEBUG1` (increasingly verbose debug information), `INFO` (informational messages from queries like `VACUUM VERBOSE`), `NOTICE` (messages about implicit type casts, index creation progress, etc.), `WARNING` (non-fatal abnormalities), `ERROR` (errors that caused the current transaction to fail), `LOG` (operational messages like checkpoints and autovacuum activity), `FATAL` (errors that caused the current session to terminate), and `PANIC` (server-wide failures that cause a crash and restart). In production, you typically log at `WARNING` and above, capturing everything that is not routine.

```ini
# ─────────────────────────────────────────────────────────────────
# postgresql.conf — ERROR LOG CONFIGURATION:

# Minimum severity level to log:
# DEBUG5, DEBUG4, DEBUG3, DEBUG2, DEBUG1, INFO, NOTICE, WARNING,
# ERROR, LOG, FATAL, PANIC
log_min_messages = WARNING              # Log WARNING and above in production
                                        # Use INFO during debugging periods
                                        # Use DEBUG1..5 only in development

# Minimum level for error details in client messages:
log_min_error_statement = ERROR         # Log SQL of failed statements

# Log checkpoints (important for I/O monitoring and recovery time):
log_checkpoints = on
# Output: "checkpoint complete: wrote 1847 buffers (11.3%);
#          0 WAL file(s) added, 0 removed, 1 recycled;
#          write=0.842 s, sync=0.003 s, total=0.873 s;
#          sync files=14, longest=0.001 s, average=0.000 s;
#          distance=15406 kB, estimate=16008 kB"
# Why it matters: frequent checkpoints = high write load or too-small buffers

# Log connection attempts (authentication events):
log_connections = on                    # Log successful connections
log_disconnections = on                 # Log disconnections with session duration

# Log hostname (requires DNS lookup — adds small latency):
log_hostname = off                      # Keep off in production for performance

# Log authentication failures (always important for security):
# These are logged at FATAL level → covered by log_min_messages = WARNING

# Log autovacuum when it runs on a table (useful for maintenance tracking):
log_autovacuum_min_duration = 1000      # Log autovacuum runs taking > 1 second
                                        # Set to 0 to log all, -1 to disable

# Log temporary file usage (spill to disk during sorts/hashes):
log_temp_files = 10240                  # Log temp files larger than 10MB
                                        # These indicate work_mem may be too small

# Log lock timeouts (if a query waits too long for a lock):
lock_timeout = '30s'                    # Terminate queries waiting > 30s for lock
log_lock_waits = on                     # Log when a lock wait occurs
deadlock_timeout = '1s'                 # Wait 1s before declaring deadlock
                                        # After deadlock_timeout, log + resolve

# Log duration for ALL statements at WARNING level:
# (This catches edge cases where auto_explain misses short-but-frequent queries)
```

The error log entries you should know by sight — because you will see them in production — are:

```
COMMON POSTGRESQL ERROR LOG ENTRIES — What Each Means:

FATAL: password authentication failed for user "app_service"
  → Wrong password or the user does not exist.
  → Check pg_hba.conf and application connection string.
  → SECURITY: Alert on > 3 per minute from the same IP (brute force).

FATAL: remaining connection slots are reserved for non-replication superuser connections
  → max_connections reached. No more connections can be accepted.
  → Immediately check connection count. Consider PgBouncer or kill idle connections.
  → This causes application outage until connections are freed.

ERROR: deadlock detected
  → Two transactions locked each other out. One was killed.
  → See deadlock log for details (Section 4).
  → Application's retry logic should handle this (pgx returns a specific error code).

ERROR: canceling statement due to conflict with recovery
  → A replica is applying WAL that conflicts with a long-running query on the replica.
  → Caused by: DDL on primary (ALTER TABLE) while replica has long SELECT running.
  → Fix: max_standby_streaming_delay = '30s' to give queries more time.

WARNING: out of shared memory
  → shared_buffers is too small for the current workload.
  → Increase shared_buffers in postgresql.conf.

ERROR: value too long for type character varying(255)
  → Application is sending data that exceeds a column's length constraint.
  → This is an application bug. Validate input lengths before DB operations.

LOG: checkpoint complete: wrote 18472 buffers (100%)
  → A checkpoint wrote ALL dirty shared buffers.
  → If this happens frequently (every few seconds), max_wal_size is too small
    or write load is extremely high. Checkpoints every 5 minutes are healthy.

LOG: autovacuum: found 52345 removable, 1024000 nonremovable row versions
  in 4096 out of 16384 pages of relation "public"."orders"
  → Dead tuples accumulating. Normal if autovacuum keeps up.
  → If dead tuple count keeps growing despite autovacuum, consider:
    autovacuum_vacuum_scale_factor, autovacuum_max_workers tuning.

PANIC: could not write to file "pg_wal/000000010000000100000067": No space left on device
  → CRITICAL: WAL disk is full. Database has stopped accepting writes.
  → Requires immediate disk space recovery. A full WAL disk is a crisis.
```

For MySQL, the error log is configured via `log_error` in `my.cnf` and captures server startup/shutdown messages, critical errors, and significant warnings. MySQL's error log format is simpler than PostgreSQL's but follows the same principles:

```ini
# my.cnf — MySQL ERROR LOG:
[mysqld]
log_error = /var/log/mysql/error.log
log_error_verbosity = 2   # 1=errors only, 2=errors+warnings, 3=notes too
log_error_services = "log_filter_internal; log_sink_internal"

# Log warnings about deprecated features, aborted connections:
log_warnings = 2

# Log aborted connections (important for connection pool debugging):
# Appears in error log as:
# "Aborted connection 1234 to db: 'mydb' user: 'app' host: '10.0.1.5'"
# This usually means the application dropped the connection without proper close.
```

## 4. Deadlock Logging — Capturing Lock Conflicts

Deadlocks deserve their own section because they are among the most frustrating production problems to diagnose without proper logging, and among the easiest to diagnose with it. A deadlock occurs when two or more transactions are each waiting for a lock held by the other, creating a circular dependency that can never resolve itself. PostgreSQL detects deadlocks by running a deadlock detection algorithm after a configurable timeout (`deadlock_timeout`, typically 1 second), then kills one of the conflicting transactions (the "victim") to break the cycle.

Without deadlock logging, all you know is that a transaction failed with a deadlock error. With deadlock logging, you see the exact SQL statements of all parties to the deadlock, the specific rows they were contending over, and the lock modes they were holding and waiting for. This information is usually sufficient to diagnose the root cause and fix the code.

```ini
# postgresql.conf — DEADLOCK LOGGING:

# How long to wait before checking for deadlocks (default 1s):
# Lower = faster deadlock detection, higher CPU overhead for lock checks
# Higher = less overhead but transactions wait longer before detection
deadlock_timeout = 1s

# log_lock_waits logs when ANY lock wait exceeds deadlock_timeout:
# This catches potential deadlock scenarios even before they deadlock.
log_lock_waits = on

# Deadlocks are always logged at ERROR level — covered by
# log_min_messages = WARNING (WARNING < ERROR, so ERROR is captured)
```

When a deadlock occurs, PostgreSQL writes a detailed entry to the log. Reading and understanding this entry is a skill worth developing:

```
REAL POSTGRESQL DEADLOCK LOG ENTRY — Annotated:

2026-09-05 14:47:23.112 UTC [12345] app_service@production
ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 789012;
        blocked by process 67890.
        Process 67890 waits for ShareLock on transaction 456789;
        blocked by process 12345.
HINT:   See server log for query details.
CONTEXT: while updating tuple (0,42) in relation "orders"

2026-09-05 14:47:23.112 UTC [12345] app_service@production
DETAIL: Process 12345: UPDATE orders SET status = 'shipped'
                        WHERE id = $1
                        Parameters: $1 = '101'
        Process 67890: UPDATE inventory SET quantity = quantity - $1
                        WHERE product_id = $2
                        Parameters: $1 = '1', $2 = '88'

─────────────────────────────────────────────────────────────────────
READING THE DEADLOCK LOG — Step by Step:

Process 12345 (shipping service):
  1. Acquired lock on inventory row (product_id=88) first.
  2. Now waiting for lock on orders row (id=101).
  3. Cannot proceed: orders row is held by Process 67890.

Process 67890 (order service):
  1. Acquired lock on orders row (id=101) first.
  2. Now waiting for lock on inventory row (product_id=88).
  3. Cannot proceed: inventory row is held by Process 12345.

CIRCULAR DEPENDENCY:
  12345 → waiting for → orders(101) → held by → 67890
  67890 → waiting for → inventory(88) → held by → 12345
  Neither can proceed → DEADLOCK.

DIAGNOSIS:
  Shipping service acquires locks in order: inventory → orders
  Order service acquires locks in order:   orders → inventory
  Opposite lock acquisition order = deadlock guaranteed under concurrent load.

FIX:
  Both code paths must acquire locks in the same order.
  Standardise on: always lock orders first, then inventory.
  OR: Use SELECT ... FOR UPDATE in the same order in both paths.
  OR: Use application-level ordering (sort IDs before locking).
```

For MySQL, deadlock logging is controlled by `innodb_print_all_deadlocks` in `my.cnf`. When enabled, every deadlock is written to the error log in full detail. You can also query the most recent deadlock from InnoDB's status:

```sql
-- MySQL: view most recent deadlock details:
SHOW ENGINE INNODB STATUS\G
-- Look for the "LATEST DETECTED DEADLOCK" section.
-- It shows both transactions, the locks they held, and the locks they waited for.

-- Enable full deadlock logging to error log:
-- my.cnf: innodb_print_all_deadlocks = ON
-- (Without this, only the most recent deadlock is accessible via SHOW ENGINE INNODB STATUS)
```

One operational pattern worth building is a deadlock alerting pipeline that fires whenever a deadlock is logged, sends the full log entry to a Slack channel or PagerDuty alert, and creates a ticket for the engineering team to investigate. Deadlocks should never be silently swallowed by application retry logic and forgotten — each one represents a code path problem that will worsen as the application scales and contention increases.

## 5. Log Formats — Structured Logging for Machine Parsing

The raw format of database logs — unstructured text lines with timestamps and messages — served the era of engineers `grep`-ing through log files in a terminal. In modern infrastructure, logs are shipped to centralised systems (ELK, Loki, Splunk, CloudWatch) where they are ingested by machines, parsed, indexed, and searched. For this machine parsing to work reliably, log entries must have a predictable, structured format.

PostgreSQL supports **CSV log format**, which formats each log entry as a comma-separated values line with fields in a fixed order. This is significantly easier to parse than the default text format because each field is in a known position with no need for complex regex parsing. PostgreSQL 15 and later also support **JSON log format**, which is even more machine-friendly.

```ini
# postgresql.conf — STRUCTURED LOG FORMAT:

# CSV format (good for file-based shipping with Filebeat):
log_destination = 'csvlog'
logging_collector = on
log_directory = 'pg_log'
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'

# JSON format (PostgreSQL 15+, ideal for direct JSON parsing):
log_destination = 'jsonlog'
# Each line is a valid JSON object — no parsing regex needed.

# Example JSON log entry:
# {
#   "timestamp": "2026-09-05 14:23:01.847 UTC",
#   "pid": 12345,
#   "session_id": "64f8b2c9.3039",
#   "line_num": 1,
#   "ps": "SELECT",
#   "session_start": "2026-09-05 14:20:01 UTC",
#   "txid": 0,
#   "error_severity": "LOG",
#   "message": "duration: 450.231 ms statement: SELECT ...",
#   "backend_type": "client backend",
#   "query_id": -8374628374,
#   "user": "app_service",
#   "dbname": "production",
#   "remote_host": "10.0.1.5",
#   "remote_port": "54321",
#   "application_name": "OrderService"
# }

# BOTH simultaneously (for backward compatibility during migration):
log_destination = 'stderr,csvlog'
```

When using the default stderr format (which is what Docker captures from container stdout/stderr), the `log_line_prefix` becomes critical for machine parsing. A well-structured prefix that includes consistent, parseable fields allows log shippers like Filebeat and Fluentd to extract structured fields using pattern matching:

```ini
# log_line_prefix for maximum machine parseability with stderr format:
# Format: timestamp pid user@database host:port app command_tag
log_line_prefix = '%m [%p] user=%u db=%d host=%h port=%r app=%a cmd=%i '

# Example output with this prefix:
# 2026-09-05 14:23:01.847 UTC [12345] user=app_service db=production
#   host=10.0.1.5 port=54321 app=OrderService cmd=SELECT
#   LOG:  duration: 450.231 ms  statement: SELECT ...

# Filebeat pattern to parse this:
# pattern: '%{TIMESTAMP_ISO8601:timestamp} \[%{INT:pid}\]
#   user=%{WORD:user} db=%{WORD:database} host=%{IP:client_host}
#   port=%{INT:client_port} app=%{GREEDYDATA:app_name}
#   cmd=%{WORD:command} %{GREEDYDATA:message}'
```

## 6. Log Shipping to Centralised Systems

A log that lives only on the database server is a log that exists only as long as the database server exists, and only as long as disk space allows, and only accessible to engineers who can SSH to that server. Centralised log management solves all three problems: logs are preserved even if the database server is destroyed, retained according to policy regardless of local disk pressure, and queryable by any team member with appropriate access without requiring production server access.

### 6.1 The ELK Stack

The ELK Stack — **Elasticsearch** (search and storage), **Logstash** or **Filebeat** (collection and shipping), and **Kibana** (visualisation and querying) — is the most widely deployed centralised logging platform. For database log shipping, Filebeat is the recommended log collector: it is lightweight, runs as a sidecar alongside the database, tails log files, and ships entries to Elasticsearch with low overhead and reliable delivery.

The architecture is: PostgreSQL writes logs → Filebeat tails the log file on the same host → Filebeat parses, enriches, and ships each entry to Elasticsearch → Kibana provides search, dashboards, and alerts over the indexed logs.

```yaml
# ─────────────────────────────────────────────────────────────────
# filebeat.yml — Shipping PostgreSQL logs to Elasticsearch:

filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /var/lib/postgresql/data/pg_log/*.log
    # Tell Filebeat this is a multiline log (query plans span multiple lines):
    multiline.pattern: '^\d{4}-\d{2}-\d{2}'  # Lines starting with date
    multiline.negate: true
    multiline.match: after
    # This groups continuation lines with the preceding timestamped line.
    # Without this, EXPLAIN plan output becomes hundreds of separate events.

    # Tags for filtering in Kibana:
    tags: ["postgresql", "database", "production"]

    # Add fields to every event:
    fields:
      environment: production
      service: postgresql
      host_role: primary           # or replica
    fields_under_root: true

  # MySQL slow query log:
  - type: log
    enabled: true
    paths:
      - /var/log/mysql/slow.log
    multiline.pattern: '^# Time:'
    multiline.negate: true
    multiline.match: after
    tags: ["mysql", "slow-query", "production"]

# Processing pipeline — parse PostgreSQL log format:
processors:
  - dissect:
      tokenizer: '%{timestamp} [%{pid}] user=%{db_user} db=%{db_name} host=%{client_host} port=%{client_port} app=%{app_name} cmd=%{command} %{severity}: %{message}'
      field: "message"
      target_prefix: "pg"
      ignore_failure: true   # Don't fail on lines that don't match pattern

  - timestamp:
      field: pg.timestamp
      layouts:
        - '2006-01-02 15:04:05.000 UTC'
        - '2006-01-02 15:04:05 UTC'
      target: "@timestamp"
      ignore_failure: true

  - add_fields:
      target: ''
      fields:
        # Classify the log entry type for easier filtering in Kibana:
        log_type: >-
          ${pg.message} contains "duration:" ? "slow_query" :
          ${pg.message} contains "deadlock" ? "deadlock" :
          ${pg.message} contains "ERROR" ? "error" : "general"

output.elasticsearch:
  hosts: ["https://elasticsearch:9200"]
  username: "filebeat_writer"
  password: "${ELASTICSEARCH_PASSWORD}"    # From environment variable
  index: "postgresql-logs-%{+yyyy.MM.dd}" # Daily indices for easy retention
  pipeline: "postgresql-enrichment"       # Ingest pipeline for further parsing

# ILM (Index Lifecycle Management) — auto-delete old logs:
setup.ilm.enabled: true
setup.ilm.rollover_alias: "postgresql-logs"
setup.ilm.policy_name: "postgresql-logs-policy"
# Policy: hot for 7 days, warm for 30 days, delete after 90 days

setup.kibana:
  host: "https://kibana:5601"
  username: "kibana_system"
  password: "${KIBANA_PASSWORD}"
```

Once logs are in Elasticsearch, Kibana provides the search interface. The most valuable Kibana queries for database log analysis are:

```
KIBANA QUERIES — Common Log Analysis Patterns:

# Find all slow queries taking > 500ms:
pg.severity: "LOG" AND pg.message: "duration:*" AND pg.duration_ms: >500

# Find all deadlock events in the last hour:
tags: "postgresql" AND pg.message: "deadlock detected" AND @timestamp: [now-1h TO now]

# Find connection failures (authentication errors):
pg.severity: "FATAL" AND pg.message: "authentication failed"

# Find queries from a specific application:
pg.app_name: "OrderService" AND pg.command: "SELECT"

# Find all errors for a specific database user:
pg.db_user: "app_service" AND pg.severity: "ERROR"

# Find autovacuum runs that took > 10 seconds:
pg.message: "automatic vacuum*" AND pg.message: "*10*"

# Trend: slow query count per hour (for time-series chart):
filter: pg.message: "duration:*"
group by: date_histogram(@timestamp, interval=1h)
```

### 6.2 Grafana Loki

**Grafana Loki** is a horizontally scalable log aggregation system designed by Grafana Labs as a "logs-as-metrics" complement to Prometheus. Where Elasticsearch indexes the full content of every log entry (powerful but expensive), Loki indexes only the labels (metadata) attached to log streams and stores the log content as compressed chunks. This makes Loki dramatically cheaper to operate than Elasticsearch for log storage, at the cost of slightly slower full-text search on non-indexed fields.

Loki's design philosophy aligns naturally with Prometheus: if Prometheus collects your database metrics and Grafana visualises them, adding Loki for logs means you can correlate metrics and logs in the same Grafana dashboards — clicking a latency spike on a Prometheus panel can open the corresponding slow query log entries from Loki in the same time range.

The log collector for Loki is **Promtail** (the Prometheus-native choice) or **Grafana Agent** (the more modern, unified agent). Both work on the same principle: tail log files, attach labels, and push log streams to Loki's HTTP API.

```yaml
# ─────────────────────────────────────────────────────────────────
# promtail.yml — Shipping PostgreSQL logs to Loki:

server:
  http_listen_port: 9080
  grpc_listen_port: 0

positions:
  filename: /tmp/positions.yaml   # Tracks how far through each log file Promtail has read

clients:
  - url: http://loki:3100/loki/api/v1/push

scrape_configs:
  # ── PostgreSQL Logs ──────────────────────────────────────────────
  - job_name: postgresql
    static_configs:
      - targets:
          - localhost
        labels:
          job: postgresql
          environment: production
          host_role: primary          # Label: used for filtering in LogQL
          __path__: /var/lib/postgresql/data/pg_log/*.log

    pipeline_stages:
      # Handle multiline log entries (EXPLAIN plans span many lines):
      - multiline:
          firstline: '^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}'
          max_wait_time: 3s

      # Parse the log_line_prefix pattern into structured labels:
      - regex:
          expression: '^(?P<timestamp>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d+ UTC) \[(?P<pid>\d+)\] user=(?P<db_user>\S+) db=(?P<db_name>\S+) host=(?P<client_host>\S+) port=(?P<client_port>\d+) app=(?P<app_name>\S+) cmd=(?P<command>\S+) (?P<severity>\w+):\s+(?P<log_message>.*)'

      # Promote parsed fields to Loki labels (only low-cardinality fields!):
      - labels:
          severity:    # LOG, ERROR, FATAL, WARNING, etc.
          db_name:     # production, staging, etc.
          db_user:     # app_service, analytics_service, etc.
          command:     # SELECT, INSERT, UPDATE, etc.
          # NOTE: Do NOT label high-cardinality fields like pid or client_host.
          #       Loki creates a new stream per unique label combination.
          #       Too many streams = performance problems.

      # Extract slow query duration as a metric label:
      - regex:
          expression: 'duration: (?P<duration_ms>[\d.]+) ms'
          source: log_message

      # Drop routine LOG messages that are not errors or slow queries:
      # (Reduces volume without losing important events)
      - drop:
          expression: '(?i)checkpoint (starting|complete)'
          # Drop checkpoint messages — covered by Prometheus metrics

  # ── MySQL Slow Query Log ─────────────────────────────────────────
  - job_name: mysql_slow
    static_configs:
      - targets:
          - localhost
        labels:
          job: mysql
          log_type: slow_query
          environment: production
          __path__: /var/log/mysql/slow.log

    pipeline_stages:
      - multiline:
          firstline: '^# Time:'
          max_wait_time: 3s
      - regex:
          expression: '^# User@Host: (?P<db_user>\S+).*\n# Query_time: (?P<query_time>[\d.]+)'
      - labels:
          db_user:
```

```
LOGQL — Querying Loki Logs (Grafana's Log Query Language):

# All PostgreSQL slow queries in last 1 hour:
{job="postgresql", severity="LOG"} |= "duration:"

# Only errors from production:
{job="postgresql", environment="production", severity="ERROR"}

# Deadlocks only:
{job="postgresql"} |= "deadlock detected"

# Slow queries taking > 500ms (regex filter on log content):
{job="postgresql"} |= "duration:" | regexp "duration: (?P<ms>[\\d.]+) ms" | ms > 500

# Connection failures in last 30 minutes:
{job="postgresql", severity="FATAL"} |= "authentication failed"
| rate [30m]

# Log volume by severity (for dashboard panel):
sum by (severity) (
  count_over_time({job="postgresql"}[5m])
)

# Rate of slow queries per minute (correlatable with Prometheus metrics):
sum(rate({job="postgresql"} |= "duration:" [1m]))
```

Loki's integration with Grafana is seamless because both are Grafana Labs products. In a Grafana dashboard, you can place a Prometheus panel showing latency P99 directly above a Loki panel showing the slow query log entries from the same time range. When you see a latency spike at 14:23 UTC, you click that time on the Prometheus graph and Loki automatically filters to show log entries from that exact window. This time-correlated view of metrics and logs in the same interface is Loki's killer feature and the reason it has become the preferred logging backend for teams already using Prometheus and Grafana.

## 7. Log Retention, Rotation, and Archival

Log retention policy is where legal requirements, storage costs, and operational needs intersect. Different types of logs have different retention requirements, and the right policy is not the same for every organisation.

Security and audit logs (which include database error logs and connection logs) typically need to be retained for regulatory compliance. GDPR requires evidence of how personal data was accessed, which means logs covering PII access must be retained for as long as you might need to produce them in a compliance investigation — often 2-3 years. PCI-DSS requires audit log retention for 12 months minimum, with 3 months immediately accessible. SOC 2 audits typically cover a 12-month window. Your legal and compliance team owns the final retention policy, but as the database engineer, you must implement it.

Performance logs (slow query logs) have a shorter useful life — a slow query log from six months ago is rarely useful for diagnosis today. 30 to 90 days is a reasonable retention window for performance logs in most organisations.

```ini
# postgresql.conf — LOG ROTATION:

# Rotate log files daily:
log_rotation_age = 1d

# Also rotate when a log file exceeds 100MB (prevents runaway single files):
log_rotation_size = 100MB

# Keep the last N log files on disk (older ones deleted automatically):
# PostgreSQL's built-in rotation does NOT auto-delete old files.
# Use logrotate (Linux) or a cron job for deletion.
```

```bash
# /etc/logrotate.d/postgresql — Automated log rotation and deletion:

/var/lib/postgresql/data/pg_log/*.log {
    daily                    # Rotate daily
    rotate 30                # Keep last 30 files (30 days of logs)
    compress                 # Compress old logs with gzip
    delaycompress            # Keep most recent rotated log uncompressed
    missingok                # Don't error if log file is missing
    notifempty               # Don't rotate empty files
    sharedscripts
    postrotate
        # Signal PostgreSQL to open new log file after rotation:
        # (PostgreSQL logging_collector handles its own rotation,
        #  but if using stderr + system capture, use this)
        /usr/bin/pg_ctlcluster 16 main reload
    endscript
}

# MySQL slow query log rotation:
/var/log/mysql/slow.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    sharedscripts
    postrotate
        # Flush MySQL logs to start new file after rotation:
        mysql -u root -p${MYSQL_ROOT_PASSWORD} -e 'FLUSH SLOW LOGS;'
    endscript
}
```

For centralised log systems (Elasticsearch, Loki), retention is managed by the system's own lifecycle policies rather than by the database server's log rotation. In Elasticsearch, **Index Lifecycle Management (ILM)** policies automatically move indices through hot → warm → cold → delete phases based on age. In Loki, the `retention_period` configuration in `loki-config.yml` controls how long log data is kept.

## 8. A Complete Logging Configuration for Production

Let us assemble everything into a single reference configuration that you can adapt for a production PostgreSQL deployment. This represents the configuration choices explained throughout this guide, combined into one coherent policy.

```ini
# ═══════════════════════════════════════════════════════════════════
# postgresql.conf — COMPLETE PRODUCTION LOGGING CONFIGURATION
# ═══════════════════════════════════════════════════════════════════

# ── WHERE TO WRITE LOGS ───────────────────────────────────────────

# For containerised deployments (Docker/Kubernetes):
#   log_destination = 'stderr'   → stdout/stderr captured by container runtime
#   logging_collector = off      → Don't write separate log files

# For bare-metal/VM deployments:
log_destination = 'stderr,csvlog'    # Both for backward compat + structured
logging_collector = on
log_directory = 'pg_log'
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'
log_file_mode = 0640                 # rw-r----- (owner + group readable)
log_rotation_age = 1d
log_rotation_size = 100MB
log_truncate_on_rotation = off       # Don't truncate on age-based rotation

# ── LOG LINE FORMAT ───────────────────────────────────────────────

# Rich prefix for machine parsing:
log_line_prefix = '%m [%p] user=%u db=%d host=%h port=%r app=%a cmd=%i '
# %m = timestamp with milliseconds
# %p = PID
# %u = username
# %d = database name
# %h = client hostname/IP
# %r = client IP:port
# %a = application name
# %i = command tag (SELECT, INSERT, etc.)

# ── WHAT TO LOG ───────────────────────────────────────────────────

# Error severity threshold:
log_min_messages = WARNING

# Log the SQL of failed statements:
log_min_error_statement = ERROR

# Slow query log (THE most important performance diagnostic):
log_min_duration_statement = 100     # Log queries taking > 100ms

# Auto-explain: attach query plan to slow query log entries:
# (Requires pg_auto_explain in shared_preload_libraries)
auto_explain.log_min_duration = 100  # Same as log_min_duration_statement
auto_explain.log_analyze = on        # Include actual timing (EXPLAIN ANALYZE)
auto_explain.log_buffers = on        # Include buffer hit/miss stats
auto_explain.log_format = text       # text or json

# Log DDL statements (for audit trail and change tracking):
log_statement = 'ddl'                # Log CREATE, ALTER, DROP, TRUNCATE

# Connection events (for security monitoring):
log_connections = on                 # Log new connections
log_disconnections = on              # Log disconnections + session duration
log_hostname = off                   # No DNS lookups (performance)

# Lock and deadlock events:
deadlock_timeout = 1s                # Deadlock detection after 1 second
log_lock_waits = on                  # Log all lock waits > deadlock_timeout

# Autovacuum activity (for maintenance monitoring):
log_autovacuum_min_duration = 1000   # Log autovacuum runs > 1 second

# Temporary file creation (spill-to-disk events):
log_temp_files = 10240               # Log temp files > 10MB (work_mem concern)

# Checkpoint activity (for write load and recovery time monitoring):
log_checkpoints = on

# ── PERFORMANCE IMPACT ESTIMATION ────────────────────────────────
# log_min_duration_statement = 100ms with 3000 QPS:
#   Assuming 0.1% of queries exceed 100ms → ~3 log entries/second
#   At ~500 bytes per entry → ~1.5 KB/second → ~130 MB/day
#   After gzip compression → ~15-20 MB/day ← manageable

# ── EXTENSIONS ────────────────────────────────────────────────────
shared_preload_libraries = 'pg_stat_statements,auto_explain'
pg_stat_statements.track = all       # Track all statements (top + nested)
pg_stat_statements.max = 10000       # Track top 10000 unique query shapes

# ── TIMEOUTS ──────────────────────────────────────────────────────
statement_timeout = 30000            # 30s: kill queries running > 30 seconds
lock_timeout = 30000                 # 30s: fail rather than wait > 30s for lock
idle_in_transaction_session_timeout = 30000  # 30s: kill idle-in-txn sessions
```
