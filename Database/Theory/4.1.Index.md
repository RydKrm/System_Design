# Index Internals — A Deep Study Guide

> *"An index in a database is much like an index at the back of a book. Without it, finding a specific piece of information means reading every page from the first to the last. With it, you jump directly to exactly where you need to be. The genius lies not in the concept, but in how elegantly the structure is built to make that jump possible."*

This chapter takes you deep into the internal machinery of database indexes — not just what they do, but precisely *how* they do it. We will build a complete mental model of the B-Tree, the data structure that powers the index in virtually every major relational database in the world. We will follow data as it is looked up, inserted, and deleted, watching the tree adapt and rebalance itself with a kind of mechanical grace. And we will then examine the critical concepts of selectivity and cardinality — the ideas that tell you when an index will save your queries and when it will do nothing at all. By the end of this chapter, indexes will no longer feel like magical black boxes. They will feel like a beautifully engineered mechanism that you can reason about, predict, and design with confidence.

## 1. B-Tree Structure — Pages, Branching Factor, Height

### Why We Need a Special Data Structure

Before we can understand what a B-Tree is, we need to understand *why* it exists — what problem it was invented to solve. When you want to store millions of records on disk and retrieve them quickly, you face a fundamental physical constraint: reading from a hard disk (or even from an SSD) is orders of magnitude slower than reading from RAM. A database cannot keep all of its data in memory — there is simply too much of it. So it must read data from disk in chunks, and the goal of any good index structure is to minimize the number of disk reads required to find a record.

A simple binary search tree (the kind you learn in a computer science course) has each node holding one key and two pointers. This sounds fine in memory, but on disk it is catastrophic. If you have a million records, a binary tree might be 20 levels deep. Finding a record could require 20 separate disk reads — 20 round-trips to the disk — each one potentially taking milliseconds. That is unacceptably slow. The B-Tree was invented in 1970 by Rudolf Bayer and Edward McCreight specifically to solve this problem, and its insight is elegant: instead of making each node hold just one key, make each node hold *many* keys. This dramatically reduces the depth of the tree, which directly translates to fewer disk reads per query.

### What Is a Page?

The fundamental unit of storage in a B-Tree is the **page** (also called a **block** or **node**). A page is a fixed-size chunk of memory or disk space — in PostgreSQL, MySQL (InnoDB), and most other databases, the default page size is **8 KB or 16 KB**. Every read from disk retrieves exactly one page. Every write to disk writes exactly one page. The size of a page is important because it directly determines how many keys a B-Tree node can hold, which in turn determines the shape and height of the entire tree.

When you ask the database to read a value from the index, it does not read individual bytes — it reads entire pages. So the strategy of a good index structure is to pack as much useful information as possible into each page, so that each disk read moves you as far as possible toward your destination.

### The Anatomy of a B-Tree Page

A B-Tree has two types of pages: **internal pages** (sometimes called branch pages or internal nodes) and **leaf pages**. They serve different purposes and contain different kinds of information.

An **internal page** acts as a router. It contains a sorted list of **keys** and **pointers** (references) to child pages. The keys act as dividers — they tell you which child page to follow to find a given search key. If you are looking for a key `K`, and an internal page contains keys `[20, 50, 80]`, then: if `K < 20`, follow the leftmost pointer; if `20 ≤ K < 50`, follow the second pointer; if `50 ≤ K < 80`, follow the third pointer; if `K ≥ 80`, follow the rightmost pointer. The internal page does not store the actual data — it only stores enough information to navigate the tree.

A **leaf page** is where the actual index entries live. Each entry in a leaf page contains the indexed key value and either (a) a pointer to the actual table row on disk (in a secondary index) or (b) the full table row itself (in a clustered/primary index). Leaf pages also contain pointers to the next and previous leaf pages, forming a **doubly linked list** across the bottom of the tree. This linked list is what makes range queries efficient — once you find the first matching key in a range, you can walk forward through the leaf pages without going back up the tree.

```
  B-TREE STRUCTURE (simplified, order=3 meaning max 3 keys per node)

                    [ROOT — Internal Page]
                    |      50      |
                   /               \
     [Internal Page]            [Internal Page]
     |  20  |  35  |            |  65  |  80  |
    /    |      \               /    |      \
   /     |       \             /     |       \
[Leaf] [Leaf]  [Leaf]       [Leaf] [Leaf]  [Leaf]
[10,15][20,28] [35,42]      [50,60][65,72] [80,91]
  |<───────────────────────────────────────────►|
              Leaf pages linked as a list

  Legend:
  - [ ] = One page (physical disk block, e.g. 8KB)
  - Numbers inside = keys stored in that page
  - Arrows between leaves = doubly linked list for range scans
```

### The Branching Factor

The **branching factor** (also called the **order** or **fan-out**) of a B-Tree is the maximum number of children an internal page can have. This is determined by how many keys and child pointers fit inside one page. If the keys are integers (4 bytes each) and pointers are 6 bytes each, and each page is 8 KB, then you can fit several hundred keys per page. A typical branching factor in a real database is between **100 and 500** or even higher for integer keys.

This branching factor is the secret to the B-Tree's power. Let us trace what happens as the branching factor grows. With a branching factor of 2 (a binary tree), a tree of height 30 can hold roughly one billion records — but requires 30 disk reads per lookup. With a branching factor of 200, a tree of height 3 can hold `200³ = 8,000,000` records, and a tree of height 4 can hold `200⁴ = 1,600,000,000` — 1.6 billion records — reachable in just 4 disk reads. That is the power of a high branching factor.

```
  BRANCHING FACTOR COMPARISON

  Binary Tree (factor=2):
  Height 1: 2 records max
  Height 10: 1,024 records
  Height 20: 1,048,576 records
  Height 30: 1,073,741,824 records  (1 billion, needs 30 reads)

  B-Tree (factor=200, typical DB):
  Height 1: 200 records max
  Height 2: 40,000 records
  Height 3: 8,000,000 records       (8 million, needs 3 reads!)
  Height 4: 1,600,000,000 records   (1.6 billion, needs 4 reads!)

  A database with a BILLION rows can be searched in just 4 disk reads.
  That is the miracle of the B-Tree.
```

### Tree Height

The **height** of a B-Tree is the number of levels from the root page to the leaf pages. Because of the high branching factor, real-world B-Trees are almost always very shallow — typically 3 to 5 levels deep, even for tables with hundreds of millions of rows. This is a profoundly important property. It means that regardless of how large your table grows, the number of disk reads required to find any single record via an index remains effectively constant — bounded by a tiny number like 4 or 5. This is what gives indexed lookups their O(log N) time complexity, and in practice, because log base-200 of 1 billion is only about 4, it feels almost like O(1) — constant time — from a human perspective.

The root page is special: the database always keeps it in memory (in the buffer pool), because it is accessed on every single index lookup. The next level of internal pages is also frequently accessed and tends to stay cached. In most workloads, only the leaf page lookup actually requires a disk read — which is why a B-Tree lookup that takes 4 theoretical levels often results in just 1 actual disk I/O in practice.

## 2. How a B-Tree Lookup Works

### The Search Algorithm

A B-Tree lookup is a beautifully simple process: starting from the root, you perform a binary search within each page to find the right child pointer, then follow that pointer down to the next level, and repeat until you reach a leaf page. At the leaf page, you perform a final binary search to find the exact key you are looking for (or determine it does not exist).

Let us trace a complete lookup through a concrete example. Suppose we have the following B-Tree with a branching factor of 3 (we keep it small for clarity), and we want to find the record with key value `42`.

```
  LOOKUP EXAMPLE: Find key = 42

  LEVEL 0 (Root):
  +-------------------+
  |    [ 30 | 60 ]    |   <-- We arrive at the root
  +-------------------+
    /         |        \
   P1         P2        P3

  Step 1: Binary search within root page.
          42 > 30 and 42 < 60 → Follow pointer P2 (middle child)

  LEVEL 1 (Internal Page P2):
  +-------------------+
  |    [ 38 | 45 ]    |   <-- We arrive at this internal page
  +-------------------+
    /         |        \
   P4         P5        P6

  Step 2: Binary search within this internal page.
          42 > 38 and 42 < 45 → Follow pointer P5 (middle child)

  LEVEL 2 (Leaf Page P5):
  +---------------------------+
  | [38,ptr] [42,ptr] [44,ptr]|   <-- We arrive at the leaf
  +---------------------------+
  prev <──────────────────────────► next

  Step 3: Binary search within leaf page.
          Found key = 42! Follow the row pointer to retrieve the actual data.

  Total pages read: 3 (root → internal → leaf)
  Result: The record for key 42 is returned.
```

Notice that at each level we perform a **binary search** within the page. Because a page is sorted and fits entirely in memory (once loaded), a binary search within it is extremely fast — it costs only CPU time, not disk time. The expensive operations are the page loads themselves, and we minimize those by navigating the tree vertically.

### Range Lookups

One of the most powerful features of the B-Tree is its support for **range queries** — queries like `WHERE age BETWEEN 25 AND 35` or `WHERE created_at > '2024-01-01'`. Once you find the first key in the range using the normal top-down traversal, you simply walk forward along the linked list of leaf pages until you exit the range. You never need to go back up to the internal nodes.

```
  RANGE LOOKUP: Find all keys between 38 and 65

  Step 1: Traverse the tree to find the leaf containing key 38.
          (Same process as point lookup above)

  Step 2: Arrive at Leaf Page P4 (contains keys 30, 35, 38)
          Found 38! Start collecting records.

  Step 3: Walk forward using the linked list:
  +-------------+    +-------------+    +-------------+    +--
  | [30, 35, 38]| →→ | [42, 44, 48]| →→ | [52, 60, 65]| →→ |...
  +-------------+    +-------------+    +-------------+    +--
  Collect: 38        Collect: 42,44,48  Collect: 52,60,65   Stop: next > 65

  Total I/O: 1 traversal + 3 leaf page reads.
  No need to ever return to the root or internal pages.
```

This is why **B-Trees are fundamentally range-query-friendly**. A hash index (another type of index) can find a single key very fast, but it is completely useless for range queries because hashing destroys the ordering of keys. The B-Tree preserves key order, which makes it the dominant index structure for general-purpose database usage.

## 3. How a B-Tree Insert Works

### The Basic Insert Process

Inserting a new key into a B-Tree always begins the same way as a lookup: you traverse from the root down to the appropriate leaf page. Once you arrive at the correct leaf page (the page where the new key belongs, based on its value relative to its neighbors), you insert the new key into that page in sorted order.

If the leaf page has enough free space to accommodate the new entry without exceeding its capacity, the insert is complete — a single page is modified and written back to disk. This is the happy path, and it is common when the table is lightly loaded or when inserts are spread across many different pages.

```
  INSERT key = 41 (simple case — leaf has room)

  Before insert:                     After insert:
  +---------------------------+       +---------------------------+
  | [38,ptr] [42,ptr] [44,ptr]|  →→   | [38,ptr] [41,ptr] [42,ptr]|
  +---------------------------+       +---------------------------+
                                      (44 moved to make room, key 41 inserted)

  Only ONE page was modified. Cheap!
```

The challenging and interesting case occurs when the target leaf page is **full** — it cannot accept another key without exceeding its capacity. This triggers a process called a **page split**, which is the B-Tree's mechanism for growing and maintaining its structure. We will examine this in detail in the next section.

### The Role of the Fill Factor

Most databases allow you to configure a parameter called the **fill factor** for an index. The fill factor (expressed as a percentage) controls how full each leaf page is allowed to be when it is initially written. A fill factor of 100% means pages are packed completely full. A fill factor of 70% means each page is only filled to 70% capacity, leaving 30% free space.

Why would you intentionally waste space? Because if you know your table will receive many inserts over time, leaving free space in each leaf page means future inserts can slide into an existing page without triggering a page split. Page splits are expensive (they require writing multiple pages and updating the parent page), so reducing their frequency by accepting a slightly larger index size is often a worthwhile trade-off for write-heavy workloads.

```
  FILL FACTOR TRADE-OFF:

  Fill Factor = 100%:
  +──────────────────────────────────+
  | KEY KEY KEY KEY KEY KEY KEY KEY  |  ← Completely packed
  +──────────────────────────────────+
  Any new insert → IMMEDIATE PAGE SPLIT (expensive)

  Fill Factor = 70%:
  +──────────────────────────────────+
  | KEY KEY KEY KEY KEY KEY [empty]  |  ← 30% free
  +──────────────────────────────────+
  New inserts fit right in → NO SPLIT needed (cheap)
  Cost: Index is larger on disk. Worth it for write-heavy tables.
```

## 4. How a B-Tree Delete Works

### The Basic Delete Process

Deleting a key from a B-Tree begins identically to a lookup: traverse from root to the appropriate leaf page, find the key, and remove it from the page. If the leaf page still has enough entries after the deletion (above the minimum occupancy threshold, typically 50% full), the delete is complete — only the one leaf page is modified.

```
  DELETE key = 42 (simple case — leaf stays above half-full)

  Before delete:                         After delete:
  +-------------------------------+       +-----------------------------+
  | [38,ptr] [42,ptr] [44,ptr]    |  →→   | [38,ptr] [44,ptr]           |
  +-------------------------------+       +-----------------------------+
  Page still has 2 entries (above minimum). Done. Only 1 page modified.
```

### Underflow and Rebalancing

The interesting case occurs when, after deletion, a leaf page falls **below the minimum occupancy threshold**. This state is called **underflow**. A B-Tree with pages that are less than half full is unbalanced — it wastes space and degrades performance. The tree must take corrective action, and it has two strategies available.

The first strategy is **borrowing from a sibling**. The database checks whether the adjacent sibling page (the leaf page immediately to the left or right in the linked list) has enough entries to share — more than the minimum. If it does, the database moves one entry from the sibling to the underfull page, and updates the parent's separator key to reflect the new boundary between the two pages. The tree remains balanced with the same number of pages.

```
  DELETE — Underflow handled by BORROWING from sibling:

  Before (min occupancy = 2 entries per leaf):
  Parent:  [ 40 | 70 ]
            /        \
  Leaf A: [25, 38]   Leaf B: [42, 55, 65]  ← Sibling has 3 (can spare one)

  Delete 25 from Leaf A → Leaf A has only 1 entry (UNDERFLOW!)

  Fix: Borrow smallest key from Leaf B (key=42) and move to Leaf A.
       Update parent separator from 40 to 42.

  After:
  Parent:  [ 42 | 70 ]
            /        \
  Leaf A: [38, 42]   Leaf B: [55, 65]   ← Both pages now above minimum
```

The second strategy, used when the sibling is also at minimum occupancy and cannot spare an entry, is **page merging**. The two pages are merged into a single page. The separator key from the parent that divided them is pulled down into the merged page (for internal nodes) or simply removed (for leaf nodes). The parent page then has one fewer child pointer, which may itself cause the parent to underflow — and the same process propagates upward through the tree levels until it resolves or reaches the root. If the root is left with zero keys and one child, the tree decreases in height by one level.

```
  DELETE — Underflow handled by MERGING with sibling:

  Before (min occupancy = 2 entries per leaf):
  Parent:  [ 40 | 70 ]
            /        \
  Leaf A: [25, 38]   Leaf B: [42, 43]  ← Sibling is at MINIMUM (cannot borrow)

  Delete 25 from Leaf A → Leaf A has only 1 entry (UNDERFLOW!)
  Leaf B cannot spare any entries.

  Fix: MERGE Leaf A and Leaf B into a single page.
       Remove separator key 40 from Parent.

  After:
  Parent:  [ 70 ]
             |
  Merged:  [38, 42, 43]   ← Single merged leaf page, parent has one fewer key

  If Parent now underflows, the same process repeats upward.
```

In practice, many databases perform **lazy deletion** — they mark entries as deleted within the page without immediately rebalancing, and periodically run a background **VACUUM** or **reorganization** process to reclaim space and restore balance. PostgreSQL's VACUUM, for example, reclaims space from dead tuples and can clean up index pages. This lazy approach avoids the cost of immediate rebalancing on every delete while still preventing permanent fragmentation.

## 5. Page Splits and Tree Rebalancing

### The Page Split in Detail

A **page split** is one of the most significant operations in a B-Tree's lifecycle. It occurs when an insert needs to go into a page that is already completely full. The database cannot simply overwrite the existing data — instead, it must create a new page, divide the existing page's contents between the old page and the new page, and then insert a new separator key into the parent page to inform it of the new child. This cascading update is what makes splits expensive.

Let us trace through a complete page split step by step, starting with a full leaf page.

```
  PAGE SPLIT SCENARIO: Insert key = 47 into a full leaf

  BEFORE (leaf is full — max 4 keys per page):
  Parent Internal Page:
  +-------------------------------+
  |      [  35   |   60   ]       |
  +------+--------+---------------+
         |        |
         v        v
  Leaf A (FULL):           Leaf B:
  +----------------------+  +------------------+
  | [38] [42] [45] [50]  |  | [62] [70] [78]   |
  +----------------------+  +------------------+
  (Key 47 needs to go here, but page is FULL!)
```

**Step 1 — Allocate a new page.** The database allocates a brand new, empty leaf page (let's call it Leaf A2).

**Step 2 — Split the keys.** The keys in the full page are divided (usually roughly in half) between the old page and the new page. The first half stays in the original Leaf A; the second half moves to the new Leaf A2.

**Step 3 — Insert the new key** into whichever half-page it belongs to based on its value.

**Step 4 — Propagate the split upward.** The median key (the first key of the new right page) must be inserted into the parent internal page as a new separator, along with a pointer to the new Leaf A2. If the parent page is also full, *it* also splits — and this can cascade all the way up to the root.

```
  PAGE SPLIT: Step-by-step

  STEP 1 & 2: Allocate new page, split existing leaf's keys:
  Leaf A (old):            Leaf A2 (NEW):
  +------------------+     +------------------+
  | [38] [42] [45]   |     | [50]             |   ← 50 moved here
  +------------------+     +------------------+

  STEP 3: Insert key 47 into correct half (47 goes in Leaf A):
  Leaf A:                  Leaf A2:
  +------------------+     +------------------+
  | [38] [42] [45][47]|    | [50]             |
  +------------------+     +------------------+

  STEP 4: Push separator key (50) up to parent:
  Parent Internal Page (AFTER):
  +--------------------------------------+
  |      [  35   |   50   |   60   ]     |  ← 50 inserted as new separator
  +------+--------+--------+--------------+
         |        |        |
         v        v        v
  Leaf A       Leaf A2   Leaf B
  [38,42,45,47] [50]     [62,70,78]

  RESULT: 3 pages were written (Leaf A, new Leaf A2, Parent).
          The tree remains balanced and sorted.
```

### Root Splits and Tree Height Growth

The most dramatic type of split is a **root split** — what happens when the root page itself is full and must be split. This is the only mechanism by which a B-Tree grows taller. When the root splits, the database allocates two new pages for the two halves of the old root's content, then writes a brand new root page containing just the single median key that divides them. The tree has grown by one level.

```
  ROOT SPLIT: The tree grows taller

  BEFORE (root is full, max 2 keys):
  Root: [ 30 | 60 ]
       /      |     \
  L1[10,20] L2[35,45] L3[70,80]

  Insert 50 — propagates up, causes root to split:

  AFTER:
  NEW Root: [ 45 ]          ← New root with just one separator
             /     \
  Internal: [30]   Internal: [60]   ← Old root split into two internals
           /  \           /   \
      L1[10,20] L2[35,45] L2b[50] L3[70,80]

  Tree height increased from 2 to 3.
  This is the ONLY way a B-Tree grows taller.
  Insertions always happen at the leaf level; height grows upward.
```

### Why B-Trees Are Always Balanced

A remarkable property of the B-Tree is that it is **always perfectly height-balanced** — meaning every leaf page is at exactly the same depth from the root. This is guaranteed by the structure of the split and merge operations. Splits always happen at the leaf level and propagate upward. Merges happen at the leaf level and propagate upward. Height changes only happen at the root level. Since every path from root to leaf passes through the same number of levels, every lookup takes the same number of disk reads — no matter which key you are looking for. This predictability is one of the most valued properties of the B-Tree in production systems.

## 6. Index Selectivity and Cardinality

### The Critical Question: Will This Index Actually Help?

Creating an index on a column does not automatically make queries on that column fast. Whether an index helps or hurts depends critically on a property called **selectivity**, which in turn is closely related to a measurement called **cardinality**. Understanding these concepts is the key to making intelligent decisions about which columns to index, and it is also the key to understanding why the database's query optimizer sometimes makes the seemingly counterintuitive decision to *ignore* an index you have created.

### What Is Cardinality?

**Cardinality** is simply the number of distinct values in a column (or in a combination of columns). A column with high cardinality has many distinct values; a column with low cardinality has few distinct values.

Consider a `users` table with one million rows. The `user_id` column (a primary key) has one million distinct values — its cardinality is 1,000,000. The `country` column might have 200 distinct country codes — its cardinality is 200. The `gender` column might have 3 distinct values (`M`, `F`, `N`) — its cardinality is 3. The `is_active` column has 2 distinct values (`true`, `false`) — its cardinality is 2.

```
  CARDINALITY EXAMPLES (users table with 1,000,000 rows):

  Column          | Distinct Values | Cardinality | Category
  ────────────────────────────────────────────────────────────
  user_id         | 1,000,000       | 1,000,000   | Very High
  email           | ~1,000,000      | ~1,000,000  | Very High
  last_name       | ~50,000         | 50,000      | High
  city            | ~10,000         | 10,000      | Medium
  country         | ~200            | 200         | Low-Medium
  subscription_   | 4 (free,basic,  | 4           | Low
  plan            |  pro, enterprise)|            |
  is_active       | 2 (true/false)  | 2           | Very Low
  ────────────────────────────────────────────────────────────
```

### What Is Selectivity?

**Selectivity** is the ratio of distinct values to total rows, expressed as a fraction between 0 and 1 (or as a percentage). It tells you "for a given value, what fraction of the table will be returned by a lookup?" More precisely, it measures how well an index can narrow down the search.

The formula is: `Selectivity = Cardinality / Total Rows`

A **high selectivity** index (selectivity close to 1.0) is one where most values are unique. Looking up a specific value in a high-selectivity index returns very few rows — ideally just one. This is excellent: the index is able to skip the vast majority of the table and deliver a tiny result set.

A **low selectivity** index (selectivity close to 0.0) is one where many rows share the same value. Looking up a specific value in a low-selectivity index returns a large fraction of the table. This is problematic: the index cannot meaningfully narrow the search.

```
  SELECTIVITY CALCULATION AND INTERPRETATION:

  Column        | Cardinality | Total Rows | Selectivity | Index Value
  ──────────────────────────────────────────────────────────────────────
  user_id       | 1,000,000   | 1,000,000  | 1.0 (100%)  | ★★★★★ Excellent
  email         | 1,000,000   | 1,000,000  | 1.0 (100%)  | ★★★★★ Excellent
  last_name     | 50,000      | 1,000,000  | 0.05 (5%)   | ★★★★☆ Good
  city          | 10,000      | 1,000,000  | 0.01 (1%)   | ★★★☆☆ Decent
  country       | 200         | 1,000,000  | 0.0002      | ★★☆☆☆ Poor
  subscription  | 4           | 1,000,000  | 0.000004    | ★☆☆☆☆ Terrible
  is_active     | 2           | 1,000,000  | 0.000002    | ★☆☆☆☆ Terrible

  INTERPRETATION:
  If selectivity for 'is_active' = TRUE is ~0.9 (90% of users are active),
  an index on is_active is nearly USELESS for queries like:
  WHERE is_active = TRUE
  The database would rather do a full table scan — it's faster!
```

### Why Low Selectivity Indexes Are Useless (or Harmful)

This is one of the most important insights in database performance tuning, and it surprises many beginners: **a database query optimizer will often refuse to use an index it considers too low in selectivity, and it is correct to do so.** Here is why.

Using an index involves two steps: first, reading index pages to find the row pointers; second, following each row pointer to fetch the actual table row from disk. This second step — called a **random I/O** — is expensive because each row might be on a different page, requiring a separate disk read.

If your query for `WHERE is_active = TRUE` matches 900,000 rows out of 1,000,000, using the index would require 900,000 random I/O operations to fetch 900,000 rows from the table. A **full table sequential scan**, on the other hand, reads the entire table from start to finish in large sequential chunks — which is far faster on spinning disks and competitive even on SSDs. The query optimizer knows this, and it will perform the calculation: "Is it cheaper to scan the index and do many random lookups, or to just scan the table directly?" If the index lookup requires reading more than roughly 10-20% of the table's rows, a full scan is almost always faster.

```
  INDEX vs. FULL SCAN DECISION:

  Query: SELECT * FROM users WHERE is_active = TRUE
  Table: 1,000,000 rows, 900,000 have is_active = TRUE

  OPTION A: Use index on is_active
  ┌────────────────────────────────────────────────────────────┐
  │ 1. Read index pages to get 900,000 row pointers            │
  │ 2. For EACH pointer, do a random disk read (900,000 reads) │
  │ 3. Total: potentially 900,000 random I/O operations        │
  │    Estimated time: VERY SLOW (random I/O is expensive)     │
  └────────────────────────────────────────────────────────────┘

  OPTION B: Full table sequential scan
  ┌────────────────────────────────────────────────────────────┐
  │ 1. Read the table sequentially from page 1 to last page    │
  │ 2. Disk reads: ~125,000 pages (8KB pages, 8 rows/page avg) │
  │ 3. Sequential reads are fast (OS prefetching helps)        │
  │    Estimated time: MUCH FASTER                             │
  └────────────────────────────────────────────────────────────┘

  Query optimizer CHOOSES Option B. The index is ignored.
  Creating an index on is_active was a waste of space.
```

### The Sweet Spot: When Selectivity Makes an Index Powerful

The flip side of this coin is that **high-selectivity indexes are extraordinarily powerful**. An index on `user_id` (unique values) allows the database to find any single user out of a million in approximately 3-4 page reads. Without the index, finding that user would require reading all ~125,000 pages of the table. The index reduces the work by a factor of roughly 30,000. This is the magic of a well-chosen, high-selectivity index.

The general rule of thumb that most experienced DBAs use is: an index becomes *potentially* useful when a query is expected to return less than roughly 5-10% of the total rows. Below that threshold, the index lookup plus random I/O is almost certainly faster than a full table scan. Above that threshold, question whether the index will actually be used.

### Composite Index Selectivity

When you create an index on multiple columns together (a **composite index**), the selectivity of the combined index is what matters — and it is typically much higher than the selectivity of any individual column alone. This is because the combination of values is more unique than any single value.

Imagine a `orders` table where `status` has a cardinality of 5 and `customer_id` has a cardinality of 100,000. An index on just `status` has poor selectivity. An index on just `customer_id` has good selectivity. But a composite index on `(customer_id, status)` has excellent selectivity — among all orders placed by Customer X, filtering for those with status "shipped" may return just a handful of rows.

```
  COMPOSITE INDEX SELECTIVITY:

  orders table (1,000,000 rows):

  Index on (status):
    Cardinality = 5
    Selectivity = 5 / 1,000,000 = 0.000005
    Average rows per lookup: 200,000 → USELESS

  Index on (customer_id):
    Cardinality = 100,000
    Selectivity = 100,000 / 1,000,000 = 0.1
    Average rows per lookup: 10 → GOOD

  Composite Index on (customer_id, status):
    Cardinality ≈ 100,000 × 5 = 500,000 (distinct combinations)
    Selectivity ≈ 500,000 / 1,000,000 = 0.5
    Average rows for specific customer+status: 2 → EXCELLENT

  Query: WHERE customer_id = 42 AND status = 'shipped'
  Composite index narrows to ~2 rows. Single → No brainer!
```

### How the Query Optimizer Uses Cardinality Statistics

The database does not leave index selection up to guesswork. The query optimizer maintains **statistics** about each column — including the number of distinct values, the distribution of values (a histogram), and the total number of rows. These statistics are gathered by the database's statistics collector (ANALYZE in PostgreSQL, ANALYZE TABLE in MySQL, UPDATE STATISTICS in SQL Server) and are stored in the system catalog.

When you run a query, the optimizer consults these statistics to **estimate** how many rows each condition will filter. Based on these estimates, it calculates the cost of various execution plans — using this index, that index, or no index at all — and chooses the plan with the lowest estimated cost. This is why it is critical to keep your statistics up to date, especially on tables that undergo significant changes (large inserts, mass deletes, or bulk updates). Stale statistics lead to poor cost estimates, which lead to bad query plans — and suddenly a query that was fast starts running slowly for no apparent reason.

```
  HOW THE OPTIMIZER USES STATISTICS:

  System Catalog (pg_stats in PostgreSQL):
  ┌──────────────┬─────────────┬────────────────────────────────────┐
  │ column_name  │ n_distinct  │ histogram_bounds                   │
  ├──────────────┼─────────────┼────────────────────────────────────┤
  │ user_id      │ -1 (unique) │ [1, 100000, 200000, ..., 1000000]  │
  │ country      │ 195         │ ['AU','BR','CA','CN',...,'US']     │
  │ is_active    │ 2           │ ['false', 'true']                  │
  ├──────────────┼─────────────┼────────────────────────────────────┤
  │ (also stores the fraction of rows with each value)              │
  │ is_active=true:  90%  ← optimizer knows to skip this index      │
  │ is_active=false: 10%  ← might use index for this!               │
  └──────────────┴─────────────┴────────────────────────────────────┘

  WHERE is_active = TRUE  →  90% of rows → Full scan (no index)
  WHERE is_active = FALSE → 10% of rows → May use index
  WHERE user_id = 42      →   1 row      → Definitely use index
```

This last point is subtle and worth highlighting: even a low-cardinality column can benefit from an index **for the rare values**. If 90% of users are active and 10% are inactive, an index on `is_active` is useless for `WHERE is_active = TRUE` (90% of rows, full scan wins), but it might be useful for `WHERE is_active = FALSE` (10% of rows, index might win). The optimizer, with good statistics, knows the difference. This is the principle behind **partial indexes** — indexes built only on a subset of rows that match a condition:

```sql
-- A partial index: only index the inactive users (rare, high value)
CREATE INDEX idx_inactive_users
ON users (last_login_date)
WHERE is_active = FALSE;

-- This index is tiny (only 10% of rows) but extremely fast for:
SELECT * FROM users WHERE is_active = FALSE ORDER BY last_login_date;
```

## Summary: The Complete Mental Model

The B-Tree is not just a data structure — it is an elegant, self-maintaining organism that adapts to the data flowing through it. Its genius lies in three interlocking properties: the high branching factor that keeps it shallow (and thus fast to traverse); the balanced structure that guarantees consistent, predictable performance for any key; and the leaf-level linked list that enables efficient range scans. Together, these properties make it the foundation of indexed data access in virtually every relational database in the world.

```
  COMPLETE B-TREE INDEX INTERNALS — QUICK REFERENCE

  STRUCTURE:
  ┌───────────────────┐
  │  Root Page        │  ← Always in memory (buffer pool)
  │  (Internal)       │  ← Contains separator keys + child pointers
  └────────┬──────────┘
           │
  ┌────────┴──────────┐
  │  Internal Pages   │  ← Usually cached (hot)
  │  (Branch)         │  ← Binary search within page, follow pointer
  └────────┬──────────┘
           │
  ┌────────┴──────────┐
  │  Leaf Pages       │  ← 1 disk read (usually)
  │                   │  ← Contain actual index entries + row pointers
  │  ←→ Linked List → │  ← Enables efficient range scans
  └───────────────────┘

  KEY OPERATIONS:
  Lookup   → Traverse root→internal→leaf (O log N ≈ 3-4 disk reads)
  Insert   → Find leaf, insert in sorted order; split if full
  Delete   → Find leaf, remove; borrow or merge if underflow
  Range    → Find start key, walk linked list forward

  SELECTIVITY RULES:
  Selectivity = Cardinality / Total Rows
  > 0.9 (very high uniqueness)  → Index is extremely valuable
  0.1 to 0.9                    → Index probably useful
  0.05 to 0.1                   → Evaluate case by case
  < 0.05 (many rows per value)  → Index likely ignored by optimizer
  Single boolean column         → Almost never worth indexing alone
```

Understanding these internals transforms you from a developer who merely *uses* indexes into one who can reason about them — predicting when they will help, diagnosing why they are being ignored, and designing them with the precision of someone who knows exactly what is happening inside the pages of that tree.
