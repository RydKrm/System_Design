# Index Strategies — Volume II: Advanced Query Pattern Indexes

> *"A truly skilled database practitioner does not merely index columns. They index the patterns by which their application reaches for data. The column is a physical thing — a name, a number, a date. The query pattern is an intent — a question the application asks again and again. The best indexes are not answers to columns; they are answers to questions. And the more precisely you can articulate the question, the more precisely you can craft the index that answers it."*

This second volume of index strategies turns to four specialized techniques that together handle some of the most important and recurring query pattern problems in real-world database engineering. The Partial Index, explored at a deeper level than in the previous chapter, reveals new angles when viewed specifically through the lens of query patterns. The Expression Index (also called the Functional Index) solves the problem of queries that filter not on a column's raw value, but on a computed or transformed version of it. The Unique Index is more than a constraint — it is a powerful query optimization tool with important design implications. And the Index on Foreign Keys is one of the most frequently forgotten indexes in database design, whose absence silently causes devastating performance problems that appear only under load.

## 1. Partial Index (Filtered Index) — Query Pattern Perspective

### Aligning the Index with the Application's Intent

We introduced the Partial Index in the previous chapter, where we examined its structural advantages — the dramatic size reduction and lower write cost when indexing only a subset of rows. In this chapter we approach the same concept from a different angle: the **query pattern perspective**. This perspective asks not "which rows should be indexed?" but rather "what is my application repeatedly asking for, and how do I build an index that answers precisely that question without indexing anything else?"

Every application has a set of queries that are asked constantly — the operational heartbeat of the system. In an e-commerce platform, it is queries like "what are the pending orders for this warehouse shift?" In a task management tool, it is "what are the open tasks assigned to this user?" In a messaging platform, it is "what are the unread messages for this user?" Notice that in each of these cases, the query has an **implicit permanent filter**: pending orders, open tasks, unread messages. The "other" rows — delivered orders, closed tasks, read messages — are rarely queried in operations; they are archive data. And yet, without a partial index, these dormant rows sit inside a full-table index, consuming space and maintenance cost, waiting for queries that almost never come.

The partial index is the direct translation of this operational reality into index design. You are telling the database: "Index the rows that my application actually queries. Leave the rest out."

### Pattern 1: The "Hot" Data Pattern

The most common motivating pattern for a partial index is what we can call the **Hot Data Pattern** — a table where a small, active "hot" portion of the data is queried constantly, while a large "cold" portion is rarely accessed. This pattern appears in almost every serious production database.

```
  THE HOT DATA PATTERN

  tickets table in a support system (2,000,000 rows):

  Status Distribution:
  'open'        →     8,000 rows  (0.4%)  ← HOT: queried thousands of times/day
  'in_progress' →     5,000 rows  (0.25%) ← HOT: same
  'resolved'    → 1,700,000 rows (85%)   ← COLD: rarely queried
  'closed'      →   287,000 rows (14.35%)← COLD: rarely queried

  WITHOUT partial index:
  Full index on (status, assignee_id):
  ┌──────────────────────────────────────────────────────────────────────┐
  │ 2,000,000 entries — mostly cold rows dragging down index performance │
  │ Index size: ~100 MB                                                  │
  │ Write cost: Every ticket status change → two index updates           │
  │ Query for 'open' tickets: fast, but navigating 100MB of index        │
  └──────────────────────────────────────────────────────────────────────┘

  WITH partial index on hot data only:
  Partial index on (assignee_id, created_at) WHERE status IN ('open','in_progress'):
  ┌──────────────────────────────────────────────────────────────────────┐
  │ Only 13,000 entries (0.65% of total rows)                           │
  │ Index size: ~650 KB (150x smaller than full index!)                  │
  │ Fits ENTIRELY in the database buffer pool cache → zero disk I/O!     │
  │ Write cost: Only tickets entering/leaving 'open'/'in_progress'       │
  │             touch this index. 'resolved'/'closed' updates: free.    │
  └──────────────────────────────────────────────────────────────────────┘

  For the most frequent operational queries, this index is essentially
  a pure in-memory lookup — no disk involved at all.
```

### Pattern 2: The NULL-Exclusion Pattern

A second valuable query pattern for partial indexes involves columns that are frequently NULL. In many tables, a NULL value in a column carries the semantic meaning of "not yet processed" or "not yet assigned." Think of an `email_sent_at` column in a notifications table: NULL means the email has not been sent yet, and a timestamp means it has been sent. Your job queue processor queries `WHERE email_sent_at IS NULL` constantly to find unsent notifications. But the vast majority of rows have already been sent (have a non-NULL timestamp) and will never be queried this way again.

```sql
-- notifications table: 50 million rows, only 10,000 need processing
CREATE TABLE notifications (
    id             BIGINT      PRIMARY KEY,
    user_id        BIGINT      NOT NULL,
    message        TEXT        NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL,
    email_sent_at  TIMESTAMPTZ             -- NULL = not yet sent
);

-- PROBLEM: Full index on (email_sent_at) has 50M entries.
-- Selectivity for NULL check is excellent (only 0.02% of rows),
-- but index maintenance on 50M entries is expensive.

-- SOLUTION: Partial index that only indexes the unsent notifications
-- PostgreSQL note: B-Tree indexes do store NULLs, but the partial
-- index limits the set of rows to only the actionable ones.
CREATE INDEX idx_notifications_pending
ON notifications (created_at ASC)  -- Process oldest first
WHERE email_sent_at IS NULL;       -- Only unprocessed rows

-- This index has ~10,000 entries instead of 50,000,000.
-- When an email is sent, the row is REMOVED from this index
-- (its email_sent_at changes from NULL to a timestamp → no longer matches WHERE).
-- New notifications are ADDED to this index as they are created.
-- The index stays tiny and fast permanently.

-- Query from the job processor:
SELECT id, user_id, message
FROM notifications
WHERE email_sent_at IS NULL
ORDER BY created_at ASC
LIMIT 100;  -- Process 100 at a time
-- → Uses the partial index (10K entries) → sub-millisecond response
-- Without partial index: scans through 50M rows to find 10K matches → SLOW
```

### Pattern 3: The Conditional Uniqueness Pattern

The third important query pattern for partial indexes is one we touched on in the previous chapter but that deserves fuller treatment here: **conditional uniqueness**. Many real-world business rules express uniqueness over a subset of rows, not across the entire table. A partial unique index enforces exactly such a rule.

```sql
-- Job scheduling: at most one 'active' job of each type should run at once
CREATE TABLE background_jobs (
    id          BIGSERIAL     PRIMARY KEY,
    job_type    VARCHAR(100)  NOT NULL,
    status      VARCHAR(20)   NOT NULL,   -- 'active', 'completed', 'failed'
    started_at  TIMESTAMPTZ,
    finished_at TIMESTAMPTZ
);

-- Rule: Only one 'active' job of each type can exist at a time.
-- (Multiple 'completed' or 'failed' jobs of the same type are fine — historical records)
CREATE UNIQUE INDEX idx_jobs_one_active_per_type
ON background_jobs (job_type)
WHERE status = 'active';

-- This prevents:
-- Job 'email_digest' status='active' (row 1) +
-- Job 'email_digest' status='active' (row 2)  → BLOCKED by unique partial index

-- This allows:
-- Job 'email_digest' status='completed' (row 1) +
-- Job 'email_digest' status='completed' (row 2) → ALLOWED (not in partial index)
-- Job 'email_digest' status='active'    (row 3) → ALLOWED (only one active exists)
```

## 2. Expression / Functional Index

### The Problem: Queries That Transform Data Before Filtering

There is a category of query that trips up even experienced developers: queries that apply a function or transformation to a column before comparing it. These queries are written innocently, with good reason — perhaps the data is stored in one format but must be searched in another — but they have a devastating effect on index usage. Unless the database has been specifically told about this transformation pattern, it will be unable to use any index on the underlying column, because the index is built on the raw column values, not the transformed ones.

The classic example is case-insensitive string matching. Email addresses in a database might be stored as entered (`Alice@Example.COM`), but searches should be case-insensitive (`alice@example.com`, `ALICE@EXAMPLE.COM`, and `Alice@Example.COM` should all find the same user). The natural SQL expression is `WHERE LOWER(email) = LOWER($1)` or `WHERE email ILIKE $1`. But a regular B-Tree index on `email` is built on the original mixed-case values and is completely useless for `LOWER(email) = 'alice@example.com'` — the optimizer would have to scan every row, apply `LOWER()` to each one, and then compare. The index is bypassed entirely.

The **Expression Index** (also called a **Functional Index**) solves this by pre-computing the expression and building the index on the *result* of the expression rather than on the raw column value. When the query uses the same expression in its `WHERE` clause, the optimizer recognizes the match and uses the index on the pre-computed values.

### How Expression Indexes Work Internally

An expression index is structurally a perfectly ordinary B-Tree (or other type) index. The difference is in what is stored in the index entries. Instead of storing the raw value of the column, the database evaluates the specified expression for each row at index creation time and stores the *result* in the index. For a `LOWER(email)` index, the entry for `Alice@Example.COM` is stored as `alice@example.com` in the index. For a `EXTRACT(YEAR FROM created_at)` index, the entry for `2024-03-15 10:30:00` is stored as `2024`. From that point on, the index is just a sorted list of pre-computed expression results, indistinguishable from a regular column index.

When a query contains a `WHERE` clause that matches the indexed expression exactly, the optimizer computes the expression on the query's parameter (which is fast — it's just one value) and then looks up the result in the index, finding all matching rows in O(log N) time.

```
  EXPRESSION INDEX INTERNALS

  Table: users (500,000 rows)
  Column: email (stored as-entered, mixed case)
  Expression indexed: LOWER(email)

  Raw email values in table:
  'Alice@Example.COM'    → stored in table as-is
  'BOB.SMITH@GMAIL.COM'  → stored in table as-is
  'carol@yahoo.com'      → stored in table as-is

  Expression Index (LOWER(email)):
  Evaluates LOWER() for each row at index-build time:
  ┌─────────────────────────────────┬─────────────────┐
  │ Index Key (pre-computed)        │ Row Pointer      │
  ├─────────────────────────────────┼─────────────────┤
  │ 'alice@example.com'             │ → row 1          │
  │ 'bob.smith@gmail.com'           │ → row 2          │
  │ 'carol@yahoo.com'               │ → row 3          │
  └─────────────────────────────────┴─────────────────┘

  Query: WHERE LOWER(email) = 'alice@example.com'
  Step 1: Compute LOWER('alice@example.com') = 'alice@example.com' (already lower)
  Step 2: Look up 'alice@example.com' in the expression index → O(log N) → FOUND!
  ✓ Uses index. Zero full-table scan needed.

  Query: WHERE email = 'alice@example.com'  (no LOWER() call)
  → Does NOT use the LOWER(email) expression index!
  → Regular index on (email) would be needed for this exact-case query.
  → The expression must match EXACTLY between index definition and query.
```

### Common and Important Use Cases

The expression index is applicable in a surprisingly wide range of scenarios. Understanding the pattern that triggers each use case will help you recognize when to reach for this tool in your own work.

**Case-insensitive string matching** is the most common case, as already discussed. Any application that accepts user input for searching names, emails, usernames, or product codes must grapple with case sensitivity. The expression index on `LOWER(column)` is the standard solution.

**Date/time component extraction** is the second most common case. When you store full timestamps but frequently query by year, month, day-of-week, or hour, a query like `WHERE EXTRACT(MONTH FROM created_at) = 3` cannot use a regular index on `created_at`. An expression index on `EXTRACT(MONTH FROM created_at)` makes this query fast. This is especially valuable for reporting queries that aggregate data by calendar period.

**JSON field extraction** is increasingly important as JSONB columns become common. A JSONB column storing product attributes might be queried frequently by a specific nested field, like `WHERE attributes->>'brand' = 'Sony'`. Without an expression index, every row's JSONB must be parsed and the 'brand' field extracted. An expression index on `(attributes->>'brand')` pre-computes and indexes this field.

**Computed business logic** covers a wide range of cases: an index on `(total_price * tax_rate)` for tax-inclusive pricing searches, an index on `(first_name || ' ' || last_name)` for full-name searches, an index on `DATE_TRUNC('day', created_at)` for day-level grouping, or an index on `UPPER(country_code)` for normalized lookups.

```sql
-- EXPRESSION INDEX EXAMPLES

-- ─────────────────────────────────────────────────────────
-- Case 1: Case-insensitive email lookup
-- ─────────────────────────────────────────────────────────
CREATE TABLE users (
    id       BIGSERIAL PRIMARY KEY,
    email    VARCHAR(255) NOT NULL,
    username VARCHAR(100) NOT NULL,
    name     VARCHAR(200) NOT NULL
);

-- Expression index: store LOWER(email) in the index
CREATE UNIQUE INDEX idx_users_email_lower ON users (LOWER(email));

-- These queries NOW use the expression index:
SELECT * FROM users WHERE LOWER(email) = LOWER('Alice@Example.COM');
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';

-- ─────────────────────────────────────────────────────────
-- Case 2: Query by year/month extracted from a timestamp
-- ─────────────────────────────────────────────────────────
CREATE TABLE events (
    id         BIGSERIAL   PRIMARY KEY,
    name       VARCHAR(200),
    event_date TIMESTAMPTZ NOT NULL
);

-- Expression index on the YEAR portion of the timestamp
CREATE INDEX idx_events_year ON events (EXTRACT(YEAR FROM event_date));

-- This query uses the expression index:
SELECT * FROM events WHERE EXTRACT(YEAR FROM event_date) = 2024;
-- Without this index: evaluates EXTRACT() for every row → full scan
-- With this index:    looks up pre-computed year=2024 values → O(log N)

-- ─────────────────────────────────────────────────────────
-- Case 3: JSONB field indexing
-- ─────────────────────────────────────────────────────────
CREATE TABLE products (
    id         BIGSERIAL PRIMARY KEY,
    name       VARCHAR(255),
    attributes JSONB
);

-- Expression index on a specific JSONB field
CREATE INDEX idx_products_brand
ON products ((attributes->>'brand'));  -- Note: extra parentheses required for expressions

-- This query uses the index:
SELECT name, attributes
FROM products
WHERE attributes->>'brand' = 'Sony';

-- ─────────────────────────────────────────────────────────
-- Case 4: Full-name search with concatenation
-- ─────────────────────────────────────────────────────────
-- Expression index for searching by full name
CREATE INDEX idx_users_fullname
ON users (LOWER(name));

-- Enables: WHERE LOWER(name) LIKE 'alice%'  (prefix search on full name)
-- Note: LIKE with leading wildcard ('%alice%') STILL cannot use B-Tree.
-- For substring search, use full-text index (GIN) instead.
```

### The Critical Requirement: Expression Must Match Exactly

The most important rule to internalize about expression indexes is that the expression in your query must **match the expression in the index definition exactly** — character for character, function for function. The database compares expressions structurally, not semantically. `LOWER(email)` and `lower(email)` may be equivalent in meaning, but the query optimizer in most databases compares the expression text or AST (Abstract Syntax Tree) structure. In practice, this means: use the exact same function name, the exact same argument order, and the exact same expression structure in both the index definition and the query. When in doubt, run `EXPLAIN` and check whether the index is actually being used.

## 3. Unique Index

### More Than Just a Constraint

Most developers encounter the Unique Index as a mechanism for enforcing data integrity — ensuring that no two rows share the same value in a column (or combination of columns). This is correct and important, but it understates the significance of the Unique Index as a query optimization tool. The database's knowledge that a column is unique is not just a constraint it enforces — it is **structural information that the query optimizer exploits** to make fundamentally better query plans.

When the optimizer knows that a predicate like `WHERE email = 'alice@example.com'` can match *at most one row* (because there is a unique index on `email`), it can make a crucial optimization: it does not need to continue scanning the index after finding the first match. It finds the matching entry, retrieves the row, and stops — immediately and with certainty. This is called a **unique probe** or **point lookup with guaranteed single-row result**, and it is the fastest possible way to retrieve a row from a table. No range scan, no multiple-row iteration, no aggregation — just one index page traversal and one table row retrieval.

Compare this with a non-unique index on a high-cardinality column like `last_name`. Even if only one row actually has the value `'Zuckerberg'`, the optimizer cannot *know* this without examining the index. It must perform a range scan to find all entries with that value, because theoretically there could be many. With a unique index, the optimizer knows with certainty before the query even runs that at most one row will match.

```
  UNIQUE INDEX: Optimizer Certainty Advantage

  Table: users (1,000,000 rows)

  Query: SELECT * FROM users WHERE email = 'alice@example.com'

  NON-UNIQUE index on email (even if email is de facto unique in the data):
  ┌─────────────────────────────────────────────────────────┐
  │ Optimizer thinks: "email might have multiple matches"   │
  │ Action: Scan index from 'alice@example.com' FORWARD     │
  │         until the key value changes (range scan)        │
  │ Cost: Slightly higher (reads beyond the match "just     │
  │        in case" there are more matching entries)        │
  └─────────────────────────────────────────────────────────┘

  UNIQUE index on email:
  ┌─────────────────────────────────────────────────────────┐
  │ Optimizer KNOWS: "email can have AT MOST ONE match"     │
  │ Action: Traverse B-Tree to find 'alice@example.com'     │
  │         If found → return it. STOP IMMEDIATELY.         │
  │         If not found → return empty. STOP IMMEDIATELY.  │
  │ Cost: Minimally possible. One index probe, one row.     │
  └─────────────────────────────────────────────────────────┘

  In query plans: look for "Index Scan using unique index" vs
  "Index Scan using non-unique index" — the unique version has
  lower estimated cost, enabling better join strategies upstream.
```

### Unique Indexes and JOIN Optimization

The optimizer's knowledge of uniqueness has a particularly powerful effect on `JOIN` queries. When joining Table A to Table B on Table B's unique key, the optimizer knows that each row of Table A can match *at most one* row in Table B. This means the join result cannot produce more rows than Table A itself — a property called a **cardinality-preserving join**. The optimizer uses this knowledge to choose more efficient join algorithms (nested loop join with index lookup is often optimal here) and to estimate result set sizes accurately, which in turn enables better decisions further up the query plan.

```sql
-- Unique indexes in practice

-- Table setup
CREATE TABLE customers (
    id       BIGSERIAL    PRIMARY KEY,     -- Implicit unique index (PK)
    email    VARCHAR(255) NOT NULL,
    username VARCHAR(100) NOT NULL,
    phone    VARCHAR(20)
);

-- Explicit unique index on email (one account per email address)
CREATE UNIQUE INDEX idx_customers_email ON customers (email);

-- Explicit unique index on username (unique usernames across the platform)
CREATE UNIQUE INDEX idx_customers_username ON customers (username);

-- Conditional unique index: unique phone only when phone is NOT NULL
-- (some customers may not provide a phone number — NULLs are excluded)
CREATE UNIQUE INDEX idx_customers_phone_unique
ON customers (phone)
WHERE phone IS NOT NULL;
-- Multiple NULL phone values are allowed (NULL is not equal to NULL in SQL).
-- Two customers with phone '01712345678' are NOT allowed.

-- ─────────────────────────────────────────────────────────
-- The optimizer exploits uniqueness in JOINs:

-- orders references customers(id) [a unique/PK column]
CREATE TABLE orders (
    order_id    BIGSERIAL PRIMARY KEY,
    customer_id BIGINT REFERENCES customers(id),
    total       DECIMAL(10,2)
);

-- Join query: optimizer knows each order maps to AT MOST one customer
SELECT o.order_id, o.total, c.email, c.username
FROM orders o
JOIN customers c ON c.id = o.customer_id  -- c.id is unique (PK)!
WHERE o.total > 500;

-- EXPLAIN output will show:
-- "Nested Loop" join (efficient for this pattern)
-- "Index Scan using customers_pkey on customers" (unique probe per row)
-- Estimated rows = rows in filtered orders (no row explosion possible)
-- If c.id were NOT unique, optimizer would fear a row explosion and
-- might choose a slower Hash Join or Merge Join algorithm instead.
```

### Composite Unique Indexes

Unique indexes can span multiple columns, enforcing that no two rows have the same *combination* of values across those columns. This is used to model **composite natural keys** — uniqueness rules that are inherently multi-dimensional in the business domain.

```sql
-- Team membership: each user can belong to each team at most once
CREATE TABLE team_members (
    id         BIGSERIAL PRIMARY KEY,
    team_id    BIGINT    NOT NULL REFERENCES teams(id),
    user_id    BIGINT    NOT NULL REFERENCES users(id),
    role       VARCHAR(50),
    joined_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Unique index: (team_id, user_id) combination must be unique
-- Meaning: User 42 can be in Team 5 at most once.
-- User 42 CAN be in Team 5 AND Team 8 (different team_id → different composite key)
CREATE UNIQUE INDEX idx_team_members_unique
ON team_members (team_id, user_id);

-- Attempt to insert:
-- (team_id=5, user_id=42) → succeeds (first time)
-- (team_id=5, user_id=42) → BLOCKED: duplicate composite key
-- (team_id=8, user_id=42) → succeeds (different team)

-- Bonus: the unique index also serves as a regular B-Tree index for queries:
-- WHERE team_id = 5                          → uses left prefix (team_id)
-- WHERE team_id = 5 AND user_id = 42         → uses full composite key
-- → This query gets the "unique probe" optimization (at most one row!)
```

## 4. Index on Foreign Keys

### The Silent Performance Killer

Of all the indexing mistakes that appear in production databases, the single most common and most damaging is this: **failing to index foreign key columns**. It is an error that is easy to make because it is an error of omission — you create the foreign key constraint (which creates nothing except the constraint itself in most databases), and you do not separately create an index on the referencing column. The database lets you do this without complaint. No warning is issued. The schema looks fine. Tests pass. And then, under production load, certain queries begin performing dozens of times slower than expected, and certain delete operations — which should be instantaneous — cause the database to crawl.

Understanding why this happens requires understanding what a foreign key constraint actually does at query time, and why the database needs an index on the referencing column to do it efficiently.

### What a Foreign Key Constraint Actually Does

A foreign key constraint establishes a referential integrity relationship between two tables. When you define `orders.customer_id REFERENCES customers(id)`, you are making three promises to the database: you promise that every value in `orders.customer_id` refers to an existing row in `customers`; you promise that you will not delete a customer who still has orders (without explicitly handling it via `ON DELETE CASCADE` or similar); and you promise that you will not insert an order for a customer who does not exist.

The database enforces these promises with checks. When you **insert a new order**, the database checks that the `customer_id` value exists in `customers.id`. When you **delete a customer**, the database checks that no orders currently reference that customer. These checks require looking up values in either the referenced or referencing table. The `customers.id` column is a primary key and thus always indexed. But `orders.customer_id` — the referencing column — has no automatic index. Without an index on `orders.customer_id`, the database must perform a **sequential scan of the entire orders table** every time you delete a customer, to check whether any orders reference that customer.

```
  FOREIGN KEY WITHOUT INDEX: The Delete Problem

  customers table (primary key = id, always indexed):
  +----+----------+
  | id | name     |
  +----+----------+
  | 42 | Alice    |  ← DELETE this customer
  +----+----------+

  orders table (5,000,000 rows, customer_id has NO index):
  +─────────────────────────────────────────────────────────────────────┐
  │ row 1:    customer_id=17   order_id=1001  total=49.99               │
  │ row 2:    customer_id=42   order_id=1002  total=129.99  ← Check!   │
  │ row 3:    customer_id=83   order_id=1003  total=9.99                │
  │ row 4:    customer_id=42   order_id=1004  total=249.00  ← Check!   │
  │ ...                                                                 │
  │ row 5M:   customer_id=101  order_id=6001  total=89.00              │
  └─────────────────────────────────────────────────────────────────────┘

  To check if Alice can be deleted, the database must scan ALL 5,000,000 rows!
  Because: without an index on customer_id, it has no shortcut.
  This DELETE operation that should take microseconds takes SECONDS.

  DELETE FROM customers WHERE id = 42;
  → Internally: "Scan orders table checking customer_id=42 for each row..."
  → 5,000,000 row reads just for a FK constraint check!
  → Under concurrent load, this locks the orders table → kills performance.

  WITH index on orders.customer_id:
  → Index lookup: customer_id=42 → finds 2 matching rows instantly
  → Checks: 2 rows exist → constraint violated → DELETE blocked (or cascade)
  → Total: O(log N + 2) → effectively instantaneous
```

### The Full Impact: Joins Are Also Affected

The foreign key index problem extends beyond constraint checking. The most common query in any relational database application is a JOIN — and JOINs almost always join on foreign key relationships. When your application retrieves "all orders for customer 42," the query joins `orders` on `customers.id = orders.customer_id`. The optimizer traverses `customers` to find customer 42 (fast, using the primary key index), and then looks in `orders` for all rows where `customer_id = 42`. Without an index on `orders.customer_id`, this requires a sequential scan of all 5 million orders — for every single customer lookup.

```
  FOREIGN KEY WITHOUT INDEX: The JOIN Problem

  Query: SELECT * FROM orders WHERE customer_id = 42;
  (or equivalently: JOIN orders ON customers.id = orders.customer_id WHERE customers.id = 42)

  ┌──────────────────────────────────────────────────────────────────┐
  │ WITHOUT index on orders.customer_id:                             │
  │                                                                  │
  │  Full sequential scan of orders table (5,000,000 rows)          │
  │  For EACH customer lookup, 5M rows are examined.                │
  │  If your app fetches orders for 100 customers per second:        │
  │  500,000,000 row reads per second → system collapses under load  │
  │                                                                  │
  │ WITH index on orders.customer_id:                                │
  │                                                                  │
  │  B-Tree lookup: customer_id=42 → finds matching entries          │
  │  Only 10-20 rows examined (for a typical customer)              │
  │  For 100 customer lookups/sec: 1,000-2,000 row reads per second │
  │  500x less I/O. The system breathes easily.                      │
  └──────────────────────────────────────────────────────────────────┘

  Visual representation of the JOIN with and without index:

  WITHOUT index (Nested Loop = disaster):        WITH index (Nested Loop = fast):
  For each customer row →                        For each customer row →
    scan ALL orders rows →                         B-Tree lookup on orders.customer_id →
    check customer_id match                        retrieve only matching rows
  Cost: O(customers × orders)                   Cost: O(customers × log(orders) + matches)
  For 1000 customers, 5M orders: 5 billion ops  For 1000 customers: ~50,000 ops
```

### Why Databases Don't Create These Indexes Automatically

You might reasonably wonder: if indexes on foreign key columns are so important, why doesn't the database create them automatically when you define a foreign key constraint? The answer is nuanced. The referenced column (the primary key end) is already indexed — the primary key index serves this purpose. The referencing column (the foreign key end) is the one that needs a manual index. The database does not create it automatically because the decision involves trade-offs the database cannot make on your behalf: the index costs space and write performance, and in some cases (very narrow tables with infrequent joins) the cost might outweigh the benefit. The database leaves this judgment to the database designer. Unfortunately, the default behavior is the dangerous one: no index, no warning.

PostgreSQL, unlike MySQL, will actually warn you about missing foreign key indexes when you run certain diagnostic queries, and tools like `pg_missing_indexes` or the `pg_fk_indexes` views can help identify them. SQL Server's Database Engine Tuning Advisor will also recommend missing FK indexes. But the responsibility for creating them ultimately lies with you.

### Creating Foreign Key Indexes: The Full Pattern

The pattern for properly indexing a schema with foreign key relationships is straightforward: **every foreign key column should have an index, unless you have a specific and justified reason to omit it**. The index should be created on the referencing column (the one that contains the FK value), and it is often worth making it a composite index that includes other columns frequently used to filter alongside the FK.

```sql
-- A properly indexed schema with foreign key relationships

CREATE TABLE customers (
    id         BIGSERIAL    PRIMARY KEY,
    email      VARCHAR(255) NOT NULL,
    name       VARCHAR(200) NOT NULL,
    region     VARCHAR(50)  NOT NULL
);

CREATE TABLE orders (
    order_id    BIGSERIAL    PRIMARY KEY,
    customer_id BIGINT       NOT NULL REFERENCES customers(id),
    status      VARCHAR(20)  NOT NULL DEFAULT 'pending',
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    total       DECIMAL(10,2) NOT NULL
);

CREATE TABLE order_items (
    id          BIGSERIAL PRIMARY KEY,
    order_id    BIGINT    NOT NULL REFERENCES orders(order_id),
    product_id  BIGINT    NOT NULL REFERENCES products(id),
    quantity    INTEGER   NOT NULL,
    unit_price  DECIMAL(10,2) NOT NULL
);

-- ── CRITICAL INDEXES ON FOREIGN KEY COLUMNS ────────────────────────────

-- 1. Index on orders.customer_id (FK → customers.id)
--    Required for: "all orders for customer X" JOINs, DELETE cascade checks
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

-- Better: composite index including status and created_at
-- (since common queries are "all pending orders for customer X, newest first")
CREATE INDEX idx_orders_customer_status_date
ON orders (customer_id, status, created_at DESC);
-- This replaces the simple FK index above AND serves composite queries.

-- 2. Index on order_items.order_id (FK → orders.order_id)
--    Required for: "all items in order X" JOINs, DELETE cascade on orders
CREATE INDEX idx_order_items_order_id ON order_items (order_id);

-- 3. Index on order_items.product_id (FK → products.id)
--    Required for: "all orders containing product X", product delete checks
CREATE INDEX idx_order_items_product_id ON order_items (product_id);

-- ── WHAT THESE INDEXES ENABLE ──────────────────────────────────────────

-- Fast: "All pending orders for customer 42, newest first"
SELECT order_id, status, created_at, total
FROM orders
WHERE customer_id = 42
  AND status = 'pending'
ORDER BY created_at DESC;
-- Uses idx_orders_customer_status_date → index-only range scan

-- Fast: "All items in order 1001"
SELECT product_id, quantity, unit_price
FROM order_items
WHERE order_id = 1001;
-- Uses idx_order_items_order_id → instant B-Tree lookup

-- Fast: "Delete customer 42 (even with 50 orders)"
DELETE FROM customers WHERE id = 42;
-- FK check on orders: uses idx_orders_customer_id → 2 index reads
-- FK check on order_items: cascades through order_id → 2 more reads
-- Total: O(log N) instead of O(N). Completes in microseconds.

-- ── HOW TO FIND MISSING FK INDEXES IN POSTGRESQL ───────────────────────
-- Run this diagnostic query to find unindexed foreign keys:
SELECT
    tc.table_name       AS referencing_table,
    kcu.column_name     AS referencing_column,
    ccu.table_name      AS referenced_table,
    ccu.column_name     AS referenced_column,
    'CREATE INDEX idx_' || tc.table_name || '_' || kcu.column_name
    || ' ON ' || tc.table_name || ' (' || kcu.column_name || ');'
    AS suggested_index
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
    ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage ccu
    ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
  AND NOT EXISTS (
      SELECT 1 FROM pg_indexes pi
      WHERE pi.tablename  = tc.table_name
        AND pi.indexdef LIKE '%(' || kcu.column_name || ')%'
  );
-- Returns a list of all FK columns lacking an index, plus the CREATE INDEX
-- statement you should run to fix them.
```

### When You Might Intentionally Skip an FK Index

There are rare situations where omitting an FK index is a conscious and correct decision. If the referencing table is very small (say, fewer than 1,000 rows), a sequential scan is so fast that an index would add write overhead with negligible read benefit. If the FK relationship is one that is never traversed in the "many" direction (you never query orders by customer_id, only customers by order data), the join index may not be needed. And if the referencing column is already the leading column in a composite index (as in our `idx_orders_customer_status_date` example above), you do not need a separate single-column FK index — the composite index already covers the FK lookup via the left-prefix rule. In each case, the omission is a deliberate judgment, not an oversight.

## Summary: Four Strategies for Precise Query Pattern Matching

The four strategies in this chapter share a common philosophy: they are not general-purpose indexes — they are precision instruments designed to match the exact shape of specific, important query patterns. The Partial Index matches the query pattern of "only the active/hot subset matters." The Expression Index matches the query pattern of "I always transform this column before searching." The Unique Index matches the query pattern of "I expect exactly one result" and extracts optimizer certainty from that expectation. The Foreign Key Index matches the universal query pattern of "I navigate relationships" — and its absence is the most reliably damaging mistake in database design.

```
  STRATEGY SUMMARY: MATCHING INDEXES TO QUERY PATTERNS

  ┌────────────────────────┬───────────────────────────────────────────────┐
  │ Strategy               │ Query Pattern It Matches                      │
  ├────────────────────────┼───────────────────────────────────────────────┤
  │ Partial Index          │ WHERE status = 'active' (hot minority)        │
  │ (Filtered)             │ WHERE processed_at IS NULL (pending queue)    │
  │                        │ Conditional uniqueness (soft delete + unique) │
  ├────────────────────────┼───────────────────────────────────────────────┤
  │ Expression / Functional│ WHERE LOWER(email) = $1 (case-insensitive)   │
  │ Index                  │ WHERE EXTRACT(YEAR FROM created_at) = 2024    │
  │                        │ WHERE attributes->>'brand' = 'Sony' (JSONB)  │
  │                        │ WHERE computed_expression = value             │
  ├────────────────────────┼───────────────────────────────────────────────┤
  │ Unique Index           │ WHERE email = $1 (guaranteed single result)   │
  │                        │ JOIN on unique column (no row explosion)       │
  │                        │ Conditional uniqueness via partial unique idx  │
  ├────────────────────────┼───────────────────────────────────────────────┤
  │ Index on Foreign Keys  │ WHERE customer_id = $1 (all orders for user)  │
  │                        │ DELETE FROM customers (cascade check)          │
  │                        │ Any JOIN on a FK relationship                  │
  │                        │ ON DELETE CASCADE / ON DELETE RESTRICT check   │
  └────────────────────────┴───────────────────────────────────────────────┘

  THE GOLDEN RULES:
  1. Index every foreign key column (or lead a composite index with it).
  2. If your query applies a function to a column, index the function result.
  3. If a unique constraint exists, declare it — don't just rely on the data.
  4. If your table has "hot" vs "cold" rows, use a partial index for the hot ones.
```

The discipline of indexing is, at its deepest level, a discipline of listening — listening carefully to what your application is asking, how frequently it is asking, and what subset of the data it cares about. The indexes in this chapter are not techniques you apply mechanically. They are answers you craft in response to the specific, concrete questions your application poses to the database, day after day, millions of times. The more precisely you listen to those questions, the more precisely you can answer them — with an index so well-fitted to the query pattern that the query becomes not just fast, but inevitable.
