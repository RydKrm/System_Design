# Distributed Transactions — A Deep Study Guide

> *"A transaction across a single database is a solved problem — the database's ACID guarantees handle everything. A transaction across multiple databases, multiple services, or multiple machines is one of the hardest problems in distributed systems. It requires coordinating entities that can fail independently, communicate over unreliable networks, and yet must produce a result that looks as if everything happened atomically. The history of distributed transactions is a history of increasingly clever compromises between safety, availability, and complexity."*

In a monolithic application backed by a single relational database, transactions are elegantly simple. The database's transaction manager coordinates everything: it locks the rows, writes the data, and ensures that either the entire transaction commits or nothing does. But modern architectures have shattered this simplicity. Microservices split business logic across dozens of independently deployed services, each with its own database. A single business operation — "place an order" — might involve debiting a payment service, reserving inventory in a warehouse service, and creating a shipment in a logistics service. Each of these operations lives in a different database, potentially running on a different machine in a different data center. The question of how to ensure that all three either succeed together or fail together — atomically, across the entire distributed system — is the problem of **distributed transactions**.

This chapter is a deep study of the major approaches to distributed transactions: the classical Two-Phase Commit and Three-Phase Commit protocols, the modern Saga pattern that has largely superseded them in microservice architectures, and the XA standard that provides a common interface for distributed transaction management.

## 1. Two-Phase Commit (2PC)

### The Problem That 2PC Solves

Imagine a bank transfer between two accounts that live in two different databases — perhaps even owned by two different banks. The operation requires two writes: debit $100 from Account A in Database 1, and credit $100 to Account B in Database 2. If we perform these as two independent operations (debit first, then credit), we face a terrible failure scenario: the debit succeeds but then the network fails before the credit executes. The customer has lost $100 from their account, and it has materialized nowhere. The databases are inconsistent.

A simple two-step approach without coordination cannot solve this, because either database might succeed while the other fails — and there is no way to "un-do" the first operation once the second one fails, unless we have a coordination mechanism. Two-Phase Commit is that mechanism.

### The Protocol: Voting, Then Deciding

Two-Phase Commit involves a special node called the **Coordinator** (also called the transaction manager) and multiple **Participants** (also called resource managers) — the individual databases or services that hold the data being modified. The protocol proceeds in exactly two phases, as the name suggests.

**Phase 1 — The Prepare Phase (Voting):** The Coordinator sends a `PREPARE` message to every Participant, asking: "Are you ready to commit? Do you have all the resources you need, and can you guarantee that you will commit if I ask you to?" Each Participant must respond with either `VOTE-YES` (I am prepared, I can commit) or `VOTE-NO` (I cannot commit, perhaps due to a constraint violation, resource unavailability, or timeout). Critically, a Participant that votes YES must durably record this vote — it must guarantee that it will eventually commit no matter what failures occur (including a crash and restart), because it has made a promise.

**Phase 2 — The Commit Phase (Decision):** If ALL Participants voted YES, the Coordinator sends a `COMMIT` message to all Participants. If ANY Participant voted NO (or failed to respond within a timeout), the Coordinator sends an `ABORT` message to all Participants. Each Participant that receives `COMMIT` applies its changes and releases its locks. Each Participant that receives `ABORT` rolls back its prepared changes and releases its locks. The Coordinator records the final decision durably (in a transaction log) before sending messages, so it can recover the decision and re-send it in case of failure.

```
  TWO-PHASE COMMIT PROTOCOL TIMELINE

  Coordinator                  Participant A           Participant B
  (Transaction Manager)        (Database 1)            (Database 2)
  ────────────────────────────────────────────────────────────────────────

  ┌── PHASE 1: PREPARE (Voting) ──────────────────────────────────────┐
  │                                                                    │
  │ BEGIN DISTRIBUTED TRANSACTION                                      │
  │ (Coord writes "BEGIN" to tx log)                                   │
  │                                                                    │
  │ ──── PREPARE ──────────────────────────────────────────────────→   │
  │ (Write your changes to disk;      ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ →   │
  │  hold your locks; be ready)                                        │
  │                                                                    │
  │          ← ─ ─ ─ ─ VOTE-YES ─ ─ ─ ─                               │
  │ (A has written changes to wal,  ─ ─ ─ ─ ─ VOTE-YES ─ ─ ─ ─ ─ ←  │
  │  holds locks, ready to commit)                                     │
  │                                                                    │
  │ (Coord records "COMMIT DECISION" to tx log — durably!)             │
  └── PHASE 1 COMPLETE: All voted YES → proceed to commit ────────────┘

  ┌── PHASE 2: COMMIT (Decision) ─────────────────────────────────────┐
  │                                                                    │
  │ ──── COMMIT ───────────────────────────────────────────────────→   │
  │                          ─ ─ ─ ─ ─ ─ ─ ─ COMMIT ─ ─ ─ ─ ─ ─ →   │
  │                                                                    │
  │          ← ─ ─ ─ ─ ACK ─ ─ ─ ─                                    │
  │ (A commits changes,     ─ ─ ─ ─ ─ ─ ─ ─ ACK ─ ─ ─ ─ ─ ─ ─ ←     │
  │  releases locks)                                                   │
  │                                                                    │
  │ (Coord records "COMPLETE" to tx log)                               │
  │ TRANSACTION DONE ✓                                                 │
  └── PHASE 2 COMPLETE ────────────────────────────────────────────────┘

  ABORT SCENARIO: Participant B votes NO in Phase 1

  PHASE 1:
  Coord ── PREPARE → A → VOTE-YES
  Coord ── PREPARE → B → VOTE-NO (constraint violation, out of stock, etc.)
  (Coord records "ABORT DECISION")

  PHASE 2:
  Coord ── ABORT → A → A rolls back, releases locks
  Coord ── ABORT → B → B rolls back (was never prepared anyway)
  TRANSACTION ABORTED ✗ — no change committed anywhere ✓ (atomicity preserved)
```

### The Durability Guarantee of Prepared Participants

The most important concept in 2PC is what happens when a Participant votes YES. Voting YES is not just an optimistic statement — it is a **durable promise**. Before sending `VOTE-YES`, a Participant must:
1. Write all its pending changes to durable storage (the Write-Ahead Log / redo log)
2. Flush those writes to disk (fsync) to survive a crash
3. Record its prepared state (the fact that it voted YES for this specific transaction)
4. Hold all locks on the affected data (it cannot release them until it hears the final decision)

This is why after a Participant votes YES, it enters what is called the **uncertain period** — it has committed to committing, it holds locks, it has done the work, but it cannot make the final decision on its own. It must wait for the Coordinator to send the final `COMMIT` or `ABORT` message. And here lies the fundamental weakness of 2PC.

### The 2PC Problem: Coordinator Failure in the Uncertain Period

The catastrophic failure scenario in 2PC is the **Coordinator crashing after all Participants have voted YES but before the Coordinator sends the COMMIT message**. The Participants are all in the prepared state — holding locks, with changes durably written but not yet committed. They are waiting for a decision that may not come for a very long time.

```
  2PC FAILURE: COORDINATOR CRASHES AT THE WORST MOMENT

  Phase 1 completes: A votes YES, B votes YES
  Coordinator records COMMIT decision... [COORDINATOR CRASHES HERE]

  State of the world:
  ┌──────────────────────────────────────────────────────────────────┐
  │ Coordinator: DEAD. Has committed decision in its log, but the    │
  │              COMMIT message never reached the participants.      │
  │                                                                  │
  │ Participant A: PREPARED state. Locks held. Changes on disk but   │
  │               not committed. Cannot commit or abort on its own.  │
  │               Waiting for Coordinator.                           │
  │                                                                  │
  │ Participant B: PREPARED state. Same situation as A.              │
  └──────────────────────────────────────────────────────────────────┘

  CONSEQUENCES:
  - A and B hold their locks → all other transactions that need
    those rows are BLOCKED until Coordinator recovers
  - Coordinator might be down for seconds, minutes, or hours
  - If Coordinator data is permanently lost, A and B are stuck
    FOREVER — they cannot decide independently
    (if A commits and B aborts, or vice versa, we get inconsistency)

  This is called the "BLOCKING" problem of 2PC:
  The protocol can block indefinitely when the Coordinator fails
  during the uncertain period.

  TIME BLOCKED ≈ Coordinator recovery time
  In practice: minutes to hours for coordinator failover/restart
```

### 2PC in Practice

Despite its blocking weakness, 2PC is widely used because in practice, Coordinator failures are rare, and the recovery time is typically short (seconds to minutes for a standby coordinator to take over). The protocol is implemented in many database systems as **XA transactions** (discussed later), in message brokers, and in distributed databases.

```
  2PC PERFORMANCE CHARACTERISTICS

  ┌────────────────────────────┬─────────────────────────────────────────┐
  │ Characteristic             │ Value/Impact                            │
  ├────────────────────────────┼─────────────────────────────────────────┤
  │ Round trips (happy path)   │ 2 (prepare + commit) per participant    │
  │ Minimum latency            │ 2 × max_network_latency (sequential RTTs)│
  │ Lock hold duration         │ Phase 1 + Phase 2 (locks held through   │
  │                            │ both phases → high contention risk)     │
  │ Coordinator failure impact │ Participants BLOCK until recovery        │
  │ Coordinator SPOF           │ YES — coordinator failure = potential   │
  │                            │ system-wide blockage                    │
  │ Participant failure        │ Coordinator can abort (if pre-prepare)  │
  │ (before/during Phase 1)    │ or must wait (if post-prepare)          │
  │ Throughput under load      │ Moderate — 2 RTTs per transaction +     │
  │                            │ lock contention during uncertain period  │
  └────────────────────────────┴─────────────────────────────────────────┘
```

## 2. Three-Phase Commit (3PC)

### Solving the Blocking Problem of 2PC

The Three-Phase Commit protocol was designed by Dale Skeen in 1982 specifically to address the blocking problem of 2PC — the fact that 2PC can block indefinitely if the Coordinator crashes during the uncertain period. 3PC adds a third phase between the prepare phase and the final commit phase, and more importantly, it adds the concept of **timeouts at the Participant level** that allow Participants to make progress (by aborting) even without hearing from the Coordinator.

The key insight of 3PC is the introduction of a **pre-commit phase** that separates the "I am prepared to commit" state from the "I have been told to commit" state. By ensuring that no Participant ever reaches a state where it has committed locally while another Participant might not know about the commit decision, 3PC eliminates the scenario where Participants are stuck in uncertainty.

### The Three Phases

**Phase 1 — CanCommit (Voting):** Identical to 2PC's prepare phase. The Coordinator asks every Participant: "Can you commit?" Participants respond with YES or NO (this is just a check — no durable changes are written yet).

**Phase 2 — PreCommit (Acknowledgment):** If all Participants voted YES in Phase 1, the Coordinator sends `PRE-COMMIT` to all Participants. Each Participant that receives `PRE-COMMIT` durably records that it has been informed of the pending commit (writes its pre-commit state to durable storage), and acknowledges. If any Participant voted NO in Phase 1, the Coordinator sends `ABORT`.

**Phase 3 — DoCommit (Final Commit):** The Coordinator sends `DO-COMMIT` to all Participants. Each Participant commits its changes and releases its locks.

```
  THREE-PHASE COMMIT PROTOCOL

  Coordinator                  Participant A           Participant B
  ───────────────────────────────────────────────────────────────────────

  ┌── PHASE 1: CanCommit (Voting — lightweight check) ────────────────┐
  │ ── CanCommit? ─────────────────────────────────────────────────→  │
  │                                  ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ →      │
  │           ← ─ Yes ─ ─ ─ ─                                         │
  │                         ─ ─ ─ ─ ─ Yes ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ←       │
  └───────────────────────────────────────────────────────────────────┘

  ┌── PHASE 2: PreCommit (Acknowledgment — durably record intent) ─────┐
  │ ── PreCommit ──────────────────────────────────────────────────→   │
  │                                  ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ →       │
  │ (A writes changes to disk,                                         │
  │  records "pre-committed" state,                                    │
  │  holds locks)                                                      │
  │           ← ─ ACK ─ ─ ─                                            │
  │                         ─ ─ ─ ─ ─ ACK ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ←        │
  └────────────────────────────────────────────────────────────────────┘

  ┌── PHASE 3: DoCommit (Final commit) ───────────────────────────────┐
  │ ── DoCommit ───────────────────────────────────────────────────→  │
  │                                  ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ →      │
  │           ← ─ ACK ─ ─ ─                                           │
  │                         ─ ─ ─ ─ ─ ACK ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ←       │
  │ TRANSACTION DONE ✓                                                │
  └───────────────────────────────────────────────────────────────────┘

  WHY THIS HELPS WITH COORDINATOR FAILURE:

  If Coordinator crashes AFTER sending PreCommit to all Participants:
  → Every Participant knows that ALL others received PreCommit
    (because Coord sent PreCommit to everyone before crashing)
  → Participants can elect a new Coordinator (or use timeouts)
  → New Coordinator can safely send DoCommit to all
    (since all are in PreCommit state, committing is safe)

  If Coordinator crashes BEFORE sending PreCommit:
  → Some Participants may not have received PreCommit
  → Participants with timeout: "I never got PreCommit → ABORT"
  → Safe to abort because no Participant has committed yet
```

### The Non-Blocking Property and Its Limits

The critical property that 3PC adds over 2PC is **non-blocking under coordinator failure**: Participants can, in theory, make progress without the Coordinator by using timeouts and by consulting each other (through a recovery protocol). If a Participant times out waiting for `PRE-COMMIT`, it assumes the Coordinator is dead and can safely abort. If a Participant times out waiting for `DO-COMMIT` but has received `PRE-COMMIT`, it knows all other Participants are also in the pre-commit state, and a new Coordinator can be elected to drive the commit forward.

However, 3PC has a critical limitation that makes it rarely used in practice: **it assumes a synchronous network model** — that messages are delivered within a bounded time, and that a timeout means the sender is dead (not merely slow). In real asynchronous networks, a network partition can make a live Coordinator appear dead to Participants. A Participant that times out on a `PRE-COMMIT` and aborts might be wrong — the Coordinator was alive but the network was slow. Meanwhile, another Participant (on the other side of the partition) might have received `PRE-COMMIT` and committed. The result is inconsistency.

```
  3PC vs 2PC: COMPARISON TABLE

  ┌──────────────────────────┬─────────────────────────┬─────────────────────────┐
  │ Property                 │ 2PC                     │ 3PC                     │
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Number of phases         │ 2                       │ 3                       │
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Network round trips      │ 2                       │ 3 (higher latency)      │
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Coordinator failure      │ BLOCKS until recovery   │ Non-blocking (in theory)│
  │ handling                 │                         │                         │
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Works on async networks? │ YES (blocks but correct)│ NO (timeouts can cause  │
  │                          │                         │ split-brain)            │
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Used in practice?        │ YES (widely, via XA)    │ RARELY (too complex,    │
  │                          │                         │ network assumptions fail)│
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Implementation           │ Moderate                │ Very complex            │
  │ complexity               │                         │                         │
  ├──────────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Lock hold duration       │ Phases 1+2              │ Phases 1+2+3 (longer!)  │
  └──────────────────────────┴─────────────────────────┴─────────────────────────┘

  PRACTICAL CONCLUSION:
  3PC is mostly a theoretical construct. In real distributed systems,
  the network assumption failures make 3PC less safe than 2PC in practice.
  Modern systems have largely abandoned both in favor of:
  - 2PC for tightly coupled systems (XA)
  - Saga pattern for loosely coupled microservices
  - Consensus algorithms (Raft, Paxos) for distributed databases
```

## 3. Saga Pattern — Choreography and Orchestration

### The Microservices Alternative to 2PC

The Saga pattern emerged as the practical answer to a specific insight: **2PC is fundamentally incompatible with the principles of microservice architecture**. Microservices are independently deployable, independently scalable, and independently owned by different teams. They communicate over HTTP or message queues. For 2PC to work, all Participants must hold locks and wait for a Coordinator — potentially for minutes during failure recovery. This creates tight coupling between services, violates service autonomy, and makes the entire system only as available as its least available participant. For high-traffic systems with dozens of microservices, 2PC is an availability disaster.

The Saga pattern was first described by Hector Garcia-Molina and Kenneth Salem in 1987 as a way to manage long-lived transactions in a single database. In the microservices era, it has been repurposed as the primary mechanism for multi-service transactions. The core idea is radical in its simplicity: **instead of one atomic transaction spanning all services, break the business operation into a sequence of smaller, independent local transactions, each in its own service's database, with a corresponding compensating transaction that can undo each step's effects if something later goes wrong**.

### The Fundamental Mechanics of a Saga

A Saga is a sequence of steps T₁, T₂, T₃, ... Tₙ where each Tᵢ is a local transaction in one service. Each step also has a corresponding **compensating transaction** Cᵢ that semantically reverses the effects of Tᵢ. If step Tₖ fails, the Saga executes the compensating transactions Cₖ₋₁, Cₖ₋₂, ... C₁ in reverse order, undoing the work done by all previous successful steps.

It is crucial to understand that compensating transactions are **semantic undos, not transactional rollbacks**. A compensating transaction is a new, positive action that reverses the business effect of the previous step — it is not a database-level ROLLBACK. If T₁ debited $100 from an account, the compensation C₁ credits $100 back. If T₂ reserved an airline seat, C₂ unreserves it. Each compensation is itself a database transaction that can fail and must be retried until it succeeds. Compensations are designed to be **idempotent** — safe to execute multiple times — because they may be retried in the event of a failure or network issue.

```
  SAGA MECHANICS: Happy Path vs Failure with Compensation

  Business operation: "Place an Order"
  Services: Payment, Inventory, Shipping

  ─────────────────────────────────────────────────────────────────
  HAPPY PATH (all steps succeed):

  T1: Payment Service    → Debit $150 from customer account
      ✓ Success
  T2: Inventory Service  → Reserve 2 units of Product #42
      ✓ Success
  T3: Shipping Service   → Create shipment for Order #999
      ✓ Success
  SAGA COMPLETE ✓ — Order placed successfully

  ─────────────────────────────────────────────────────────────────
  FAILURE PATH (T3 fails — e.g., shipping not available to address):

  T1: Payment Service    → Debit $150 from customer ✓
  T2: Inventory Service  → Reserve 2 units ✓
  T3: Shipping Service   → Create shipment ✗ FAILED

  Compensation runs in REVERSE order:
  C2: Inventory Service  → Un-reserve 2 units (reverse T2)
  C1: Payment Service    → Refund $150 to customer (reverse T1)
  SAGA COMPLETE (with compensation) — Order rolled back

  Diagram:
  ┌─────────────────────────────────────────────────────────────────┐
  │ T1 ──→ T2 ──→ T3 (FAIL)                                        │
  │                   │                                             │
  │                   └──→ C2 ──→ C1 (compensation cascade)        │
  │                                   │                             │
  │                                   └──→ SAGA COMPLETE (rolled back)│
  └─────────────────────────────────────────────────────────────────┘

  IMPORTANT: Between T1 succeeding and C1 completing, the system is in
  an INCONSISTENT state (money debited, no order created yet).
  This is acceptable — Sagas trade strong consistency for availability.
  The system is "eventually consistent" — it will converge to a
  consistent state, but not instantaneously.
```

### Saga Implementation: Choreography

There are two fundamental architectural approaches to implementing Sagas: **Choreography** and **Orchestration**. They differ in *who knows about the overall Saga flow* and *how services communicate*.

In the **Choreography** approach, there is no central coordinator. Each service listens for domain events published by the previous step, performs its local transaction when triggered, and publishes a new event indicating its result. The Saga "choreographs" itself through the chain of event reactions — like a dance where each dancer knows their own moves and their cue, without a director telling everyone what to do.

```
  CHOREOGRAPHY-BASED SAGA (Event-Driven)

  Order Placed →
  ┌─────────────────────────────────────────────────────────────────────┐
  │                     MESSAGE BROKER (e.g., Kafka, RabbitMQ)          │
  └──┬──────────────────────────────┬────────────────────────────────┬──┘
     │ "order.created" event        │                                │
     ▼                              │                                │
  ┌─────────────────────┐           │                                │
  │  Payment Service    │           │                                │
  │  Listens: order.    │           │                                │
  │  created            │           │                                │
  │  Does: Debit $150   │           │                                │
  │  Publishes:         │           │                                │
  │  "payment.success"  │           │                                │
  │  OR "payment.failed"│           │                                │
  └─────────────────────┘           │                                │
     │ "payment.success" event      │                                │
     ▼                              │                                │
  ┌─────────────────────┐           │                                │
  │  Inventory Service  │           │                                │
  │  Listens: payment.  │           │                                │
  │  success            │           │                                │
  │  Does: Reserve stock│           │                                │
  │  Publishes:         │           │                                │
  │  "inventory.reserved"│          │                                │
  │  OR "inventory.failed"│         │                                │
  └─────────────────────┘           │                                │
     │ "inventory.reserved"         │                                │
     ▼                              │                                │
  ┌─────────────────────┐           │                                │
  │  Shipping Service   │           │                                │
  │  Listens: inventory.│           │                                │
  │  reserved           │           │                                │
  │  Does: Create shipmt│           │                                │
  │  Publishes:         │           │                                │
  │  "shipment.created" │           │                                │
  │  OR "shipping.failed"│          │                                │
  └─────────────────────┘           │                                │

  COMPENSATION (if shipping fails):
  Shipping publishes "shipping.failed"
  → Inventory Service listens "shipping.failed" → unreserves stock →
    publishes "inventory.released"
  → Payment Service listens "inventory.released" → refunds $150 →
    publishes "payment.refunded"
  → Order Service listens "payment.refunded" → marks order CANCELLED
```

**Advantages of Choreography:**
- No single point of failure (no coordinator to crash)
- Services are truly decoupled — each only knows about the events it cares about
- Easy to add new services by subscribing to existing events

**Disadvantages of Choreography:**
- The overall Saga flow is implicit — distributed across multiple services and event handlers
- Very difficult to understand and debug end-to-end (which service handles which failure?)
- Risk of **cyclic dependencies** (Service A listens to Service B which listens to Service A)
- Monitoring and observability require correlating events across services

### Saga Implementation: Orchestration

In the **Orchestration** approach, a central **Saga Orchestrator** (or coordinator) is responsible for the entire flow. It knows all the steps, sends explicit commands to each service to perform its step, waits for the response, and decides what to do next (proceed or compensate). Each individual service is "dumb" — it only knows how to perform its specific local transaction when told to do so. All the Saga logic lives in the orchestrator.

```
  ORCHESTRATION-BASED SAGA (Central Coordinator)

  ┌──────────────────────────────────────────────────────────────────┐
  │                    SAGA ORCHESTRATOR                              │
  │  (dedicated service/process that manages the entire Saga flow)   │
  │                                                                  │
  │  State machine for "Place Order Saga":                           │
  │  PENDING → PAYMENT_PENDING → INVENTORY_PENDING →                 │
  │            SHIPPING_PENDING → COMPLETED                          │
  │  (or at any point → COMPENSATING → CANCELLED)                   │

         │
         │ 1. Send "Debit Customer" command
         ▼
  ┌─────────────────┐    2. "Payment Success"    ┌─────────────────┐
  │  Payment Service│ ─────────────────────────→ │  Orchestrator   │
  └─────────────────┘                            │  updates state  │
                                                 │  to INVENTORY_  │
                                                 │  PENDING        │
                                                 └────────┬────────┘
                                                          │
                                                          │ 3. Send "Reserve Stock" command
                                                          ▼
                                                 ┌─────────────────┐
                                                 │Inventory Service│
                                                 └────────┬────────┘
                                                          │ 4. "Inventory Reserved"
                                                          ▼
                                                 ┌─────────────────┐
                                                 │  Orchestrator   │

                                                 │ Shipping Service │
                                                 └────────┬────────┘

                                                 │  COMPENSATING   │
                                                 │  state          │

                                                 │  Payment Service│

                                                 [ORDER CANCELLED — Saga complete]
```

**Advantages of Orchestration:**
- The entire Saga flow is explicit and visible in one place (the orchestrator)
- Easier to debug, monitor, and reason about
- Natural place to implement retry logic, timeouts, and alerting
- State machine makes the current status of any Saga instance clear

**Disadvantages of Orchestration:**
- The orchestrator is a potential single point of failure (mitigated by making it durable/replicated)
- Creates coupling between the orchestrator and each service
- More infrastructure required (the orchestrator itself must be a reliable, persistent service)

### Choreography vs Orchestration: Choosing

```
  CHOREOGRAPHY vs ORCHESTRATION: DECISION GUIDE

  ├──────────────────────────────┼───────────────────────┼──────────────────────────┤
```

## 4. XA Transactions

### The Standard Interface for 2PC

**XA** is a specification published by The Open Group (formerly X/Open) in 1991 that defines a standard interface between a **Transaction Manager (TM)** and **Resource Managers (RMs)** — typically databases, message queues, or other transactional resources. XA is not a new protocol — it is a standardized implementation of the Two-Phase Commit protocol. It provides a common API that allows a single transaction manager to coordinate multiple, heterogeneous resources (e.g., a MySQL database, a PostgreSQL database, and a JMS message queue) using a standard interface.

The name "XA" comes from "eXtended Architecture" — the X/Open Distributed Transaction Processing (DTP) model. In this model, the components are:
- **Application Program (AP)**: The application code that initiates transactions
- **Transaction Manager (TM)**: The coordinator that drives 2PC (e.g., Java's JTA, IBM MQ, Bitronix, Atomikos)
- **Resource Manager (RM)**: The databases or other transactional resources being coordinated
- **Communication Resource Manager (CRM)**: Network infrastructure for multi-machine coordination

```
  XA TRANSACTION ARCHITECTURE

  ┌───────────────────────────────────────────────────────────────┐
  │                  APPLICATION PROGRAM (AP)                     │
  │  tx_begin("xa_txn_001")                                       │
  │  // Do work across multiple resources                         │
  │  tx_commit()  or  tx_rollback()                              │
  └───────────────────────────────────────────────────────────────┘
           │              │              │
           │ xa_start     │ xa_start     │ xa_start
           │ xa_end       │ xa_end       │ xa_end
           │ xa_prepare   │ xa_prepare   │ xa_prepare
           │ xa_commit    │ xa_commit    │ xa_commit
           ▼              ▼              ▼
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │   MySQL DB  │  │ PostgreSQL  │  │   JMS Queue │
  │   (RM 1)    │  │   (RM 2)    │  │   (RM 3)    │
  └─────────────┘  └─────────────┘  └─────────────┘

  All coordinated by:
  ┌──────────────────────────────────┐
  │    TRANSACTION MANAGER (TM)      │
  │  (e.g., Atomikos, Bitronix,      │
  │   Java EE JTA, Spring TM)        │
  │  Drives 2PC across all RMs       │
  └──────────────────────────────────┘
```

### The XA Interface Functions

The XA specification defines a set of functions that every Resource Manager must implement:

```
  XA FUNCTION REFERENCE

  xa_open(info, rmid, flags)
    → Open a connection to the Resource Manager
    → Called once when the RM is first used

  xa_close(info, rmid, flags)
    → Close the connection to the Resource Manager

  xa_start(xid, rmid, flags)
    → Begin an XA branch for transaction XID on this RM
    → The XID (Transaction ID) identifies the distributed transaction
    → All work on this RM during this call is part of this XA branch

  xa_end(xid, rmid, flags)
    → End the association of the current thread with the XA branch
    → Work on this RM is "done" for now (can be resumed with xa_start later)

  xa_prepare(xid, rmid, flags)
    → Phase 1 of 2PC: prepare to commit
    → RM writes all changes to durable storage
    → RM records prepared state
    → Returns XA_OK (ready to commit) or XA_RDONLY (no writes, skip commit)

  xa_commit(xid, rmid, flags)
    → Phase 2 of 2PC: commit the prepared transaction
    → RM applies the changes and releases locks

  xa_rollback(xid, rmid, flags)
    → Phase 2 of 2PC: roll back the prepared transaction
    → RM discards prepared changes and releases locks

  xa_recover(xids, count, rmid, flags)
    → CRITICAL for recovery: returns list of all transactions
      that are currently in the PREPARED state on this RM
    → Used by TM after a crash to recover in-doubt transactions
    → TM calls xa_recover on each RM, then xa_commit or xa_rollback
      for each recovered transaction based on its own transaction log
```

### XA Transactions in PostgreSQL and MySQL

Both PostgreSQL and MySQL implement the XA interface natively, allowing them to participate in externally coordinated distributed transactions.

```sql
-- ─────────────────────────────────────────────────────────────────
-- XA Transactions in PostgreSQL
-- ─────────────────────────────────────────────────────────────────

-- Prepare a distributed transaction:
BEGIN;
-- (do work: INSERT, UPDATE, DELETE)
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- Prepare (Phase 1 of 2PC):
PREPARE TRANSACTION 'txn_transfer_20240315_001';
-- At this point: changes are on disk, locks still held,
-- transaction is in "prepared" state.
-- PostgreSQL will NOT allow connection to close until committed/rolled back.

-- Commit the prepared transaction (Phase 2 of 2PC):
COMMIT PREPARED 'txn_transfer_20240315_001';

-- OR Roll back:
ROLLBACK PREPARED 'txn_transfer_20240315_001';

-- List all currently prepared transactions (recovery tool):
SELECT gid, prepared, owner, database
FROM pg_prepared_xacts;
-- If any rows appear here after a crash, the TM must decide:
-- COMMIT PREPARED or ROLLBACK PREPARED for each.
-- Orphaned prepared transactions hold locks indefinitely!

-- ─────────────────────────────────────────────────────────────────
-- XA Transactions in MySQL (using XA syntax directly)
-- ─────────────────────────────────────────────────────────────────

-- Start an XA transaction with a specific XID:
XA START 'txn_transfer_20240315_001';
-- (do work)
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- End the XA branch (suspend work):
XA END 'txn_transfer_20240315_001';

-- Phase 1: Prepare:
XA PREPARE 'txn_transfer_20240315_001';

-- Phase 2: Commit or Rollback:
XA COMMIT 'txn_transfer_20240315_001';
-- OR:
XA ROLLBACK 'txn_transfer_20240315_001';

-- Recovery: list all prepared XA transactions:
XA RECOVER;
-- Returns all in-doubt XA transactions that need coordinator decision.
```

### The XA Recovery Problem: Orphaned Prepared Transactions

The most dangerous operational aspect of XA is the **orphaned prepared transaction**. If the Transaction Manager crashes after sending `xa_prepare` to all Resource Managers but before sending `xa_commit`, the Resource Managers are left with prepared transactions that hold locks and occupy log space indefinitely. These orphans can only be resolved by a Transaction Manager recovery process that:

1. Reads the TM's own transaction log to determine the intended decision (commit or rollback)
2. Calls `xa_recover` on each RM to find all in-doubt transactions
3. Issues the appropriate `xa_commit` or `xa_rollback` for each

```
  XA ORPHANED TRANSACTION DANGER

  TM crashes after xa_prepare, before xa_commit:

  MySQL DB (RM 1):   [PREPARED 'txn_001'] ← holds row locks!
  PostgreSQL (RM 2): [PREPARED 'txn_001'] ← holds row locks!

  Impact:
  - Both databases hold locks on their prepared rows
  - All transactions needing those rows: BLOCKED
  - Locks held until TM recovers (seconds to hours or forever)

  Detection (run on each RM):
  PostgreSQL: SELECT * FROM pg_prepared_xacts;
  MySQL:      XA RECOVER;

  Manual resolution (when TM cannot recover automatically):
  COMMIT PREPARED 'txn_001';    -- if you know TM intended to commit
  ROLLBACK PREPARED 'txn_001';  -- if you know TM intended to rollback
  -- WARNING: incorrect resolution causes data inconsistency!
  -- Always check TM logs before manually resolving!

  Prevention:
  - Use TM software with robust recovery (Atomikos, Bitronix, Narayana)
  - Set max_prepared_transactions high enough in PostgreSQL
  - Monitor pg_prepared_xacts and XA RECOVER for stale prepared txns
  - Set alert: any prepared transaction older than 5 minutes needs attention
```

### XA vs Saga: When to Use Each

```
  XA TRANSACTIONS vs SAGA PATTERN

  ┌─────────────────────────┬────────────────────────┬───────────────────────────┐
  │ Factor                  │ XA Transactions         │ Saga Pattern              │
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Consistency model       │ Strong (ACID across     │ Eventual (BASE model)     │
  │                         │ all resources)          │                           │
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Performance             │ Lower (locks held,      │ Higher (no global locks)  │
  │                         │ 2-3 RTTs, blocking)     │                           │
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Network partitions      │ Blocks or fails         │ Continues (compensates)   │
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Service heterogeneity   │ All RMs must support XA │ Any service (REST, async) │
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Rollback mechanism      │ Automatic (TM drives)  │ Manual (compensating txns)│
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Intermediate visibility │ Hidden (locked, not     │ Visible (T1 done, T2      │
  │ of partial state        │ visible to others)      │ not yet, world can see)   │
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Failure recovery        │ Complex (orphaned        │ Simpler (retry/compensate)│
  │                         │ prepared txns)          │                           │
  ├─────────────────────────┼────────────────────────┼───────────────────────────┤
  │ Suitable for            │ Legacy enterprise       │ Microservices, cloud-     │
  │                         │ systems, same-vendor    │ native, high availability │
  │                         │ databases, ERP          │ systems                   │
  └─────────────────────────┴────────────────────────┴───────────────────────────┘

  DECISION RULE:
  → Need absolute ACID consistency across services? → XA (with its costs)
  → Building microservices for high availability?   → Saga
  → Mixing heterogeneous resources (DB + MQ)?      → XA (if all support it)
  → Long-running business processes?               → Saga (XA holds locks too long)
  → Financial transactions where partial state     → XA (or Saga with careful
    must never be visible?                           compensating design)
```

## Summary: The Distributed Transaction Landscape

```
  DISTRIBUTED TRANSACTION APPROACHES — FINAL REFERENCE

  ┌──────────────────┬──────────────────────────────────────────────────────┐
  │ Approach         │ Summary                                              │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ Two-Phase Commit │ Coordinator sends PREPARE → participants vote →      │
  │ (2PC)            │ all vote YES: COMMIT; any NO: ABORT.                 │
  │                  │ Atomic but BLOCKING on coordinator failure.          │
  │                  │ Used in XA, distributed databases.                   │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ Three-Phase      │ Adds PRE-COMMIT phase to allow non-blocking          │
  │ Commit (3PC)     │ recovery. Theoretically non-blocking, but            │
  │                  │ requires synchronous network (impractical).          │
  │                  │ Rarely used in practice.                             │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ Saga             │ Sequence of local transactions T1..Tn each in one    │
  │ (Choreography)   │ service. Failures compensated by C(n-1)..C1.         │
  │                  │ Choreography: event-driven, no central coordinator.  │
  │                  │ Orchestration: central state machine drives flow.    │
  │                  │ Eventually consistent. No global locks.              │
  │                  │ The preferred pattern for microservices.             │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ XA Transactions  │ Standard interface (X/Open) for 2PC across           │
  │                  │ heterogeneous resources (DBs, MQs).                  │
  │                  │ Transaction Manager coordinates; RMs implement xa_*. │
  │                  │ PostgreSQL: PREPARE/COMMIT/ROLLBACK TRANSACTION.     │
  │                  │ MySQL: XA START/END/PREPARE/COMMIT/ROLLBACK.         │
  │                  │ Risk: orphaned prepared transactions hold locks.     │
  └──────────────────┴──────────────────────────────────────────────────────┘

  THE FUNDAMENTAL TRADE-OFF (CAP Theorem reflection):

  Stronger consistency (2PC/XA):
  → Better: atomic across all participants
  → Worse: lower availability (blocks on failure), lower performance
  → Best for: tightly coupled systems, absolute ACID required

  Weaker consistency (Saga):
  → Better: higher availability, higher performance, resilient to failure
  → Worse: intermediate states are visible, compensation logic is complex
  → Best for: microservices, cloud-native, high-traffic systems

  There is no free lunch in distributed transactions.
  Every approach makes a different compromise.
  The art is choosing the compromise that fits your actual requirements.
```

The world of distributed transactions is, in many ways, the hardest frontier in database engineering — the place where the clean abstractions of a single ACID database give way to the messy, probabilistic reality of networks, partial failures, and distributed state. Understanding these protocols deeply — not just their mechanics but their failure modes, their performance characteristics, and the contexts in which each is appropriate — is what enables you to design systems that are both correct and alive in the presence of the inevitable failures of distributed computing.
