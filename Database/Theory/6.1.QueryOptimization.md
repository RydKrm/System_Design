# Query Optimization — A Deep Study Guide

> *"A poorly written query is not merely slow — it is a misunderstanding made permanent in code. Every query you write is an instruction to the database about what data you want. But it is also, implicitly, a plan for how to get it. The query optimizer does its best to find the fastest plan for what you have written, but it cannot overcome a fundamentally inefficient approach. The engineer who understands how to write queries that cooperate with the optimizer — who thinks not just about what they want but about how the database will retrieve it — writes code that ages gracefully, performing well not just at small scale but under the full weight of production data."*

In the previous chapters, we studied the machinery of the database: indexes, execution plans, locking, and transactions. In this chapter, we turn to the craft of writing queries — the application-level decisions that determine whether all that machinery is used efficiently or wastefully. Query optimization at the application level is not about tuning knobs on the database server; it is about understanding the behavioral consequences of the SQL you write, recognizing patterns that cause systematic performance problems, and replacing them with patterns that achieve the same results far more efficiently.

## 1. Rewriting Queries for the Planner

### The Planner Is Smart, But It Needs Your Help

The PostgreSQL query planner is a sophisticated piece of software, but it operates within constraints. It evaluates a finite set of candidate plans, uses statistical models to estimate costs, and makes decisions based on what it can mathematically analyze. Some query structures are fundamentally opaque to the planner — they prevent it from pushing filters down, using indexes, or eliminating unnecessary work. Rewriting queries is the art of expressing the same logical intent in a form that the planner can optimize more effectively.

The most impactful rewrites target three broad problems: queries that apply transformations to indexed columns (preventing index use), queries that force the planner to materialize large intermediate results unnecessarily, and queries where the structure prevents the planner from understanding the selectivity and cardinality of intermediate steps.

### Rewrite 1: Move Functions Off Columns

As we discussed in the indexing chapters, applying a function to a column in a WHERE clause prevents the use of a regular index on that column. The rewrite is to push the function to the right-hand side (the literal/parameter) or to reformulate the condition without a function.

```sql
-- ─────────────────────────────────────────────────────────────────
-- BAD: Function applied to the column → index on created_at bypassed
-- ─────────────────────────────────────────────────────────────────
SELECT * FROM orders
WHERE DATE(created_at) = '2024-03-15';
-- DATE() strips the time component from every row → full table scan
-- Even with an index on created_at, this query cannot use it!

-- EXPLAIN:  Seq Scan on orders
--           Filter: (date(created_at) = '2024-03-15')

-- GOOD: Reformulate as a range — no function on the column
SELECT * FROM orders
WHERE created_at >= '2024-03-15 00:00:00'
  AND created_at  < '2024-03-16 00:00:00';
-- EXPLAIN: Index Scan using idx_orders_created_at on orders
--          Index Cond: ((created_at >= '2024-03-15') AND (created_at < '2024-03-16'))

-- ─────────────────────────────────────────────────────────────────
-- BAD: YEAR() function prevents index use
SELECT * FROM orders WHERE EXTRACT(YEAR FROM created_at) = 2024;
-- GOOD: Range over the whole year
SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';

-- ─────────────────────────────────────────────────────────────────
-- BAD: LOWER() on column → case-insensitive search bypasses index
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
-- GOOD: Create expression index on LOWER(email), then query as-is
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com'; -- NOW uses index!

-- ─────────────────────────────────────────────────────────────────
-- BAD: Implicit type cast → index bypassed
-- (column is VARCHAR but parameter is INTEGER — DB casts the column)
SELECT * FROM accounts WHERE account_no = 12345678;  -- integer literal!
-- GOOD: Match the parameter type to the column type
SELECT * FROM accounts WHERE account_no = '12345678'; -- string literal ✓
```

### Rewrite 2: Subquery vs JOIN — Understanding What the Planner Can Optimize

Correlated subqueries — subqueries that reference columns from the outer query — are one of the most common sources of accidental N+1 behavior at the SQL level. In a correlated subquery, the inner query is re-executed for every row of the outer query. The planner cannot always "decorrelate" (unnest) these subqueries into equivalent JOINs, which means some correlated subqueries become O(N) individual database operations inside a single SQL statement.

```sql
-- ─────────────────────────────────────────────────────────────────
-- BAD: Correlated subquery — executed once per row of orders
-- ─────────────────────────────────────────────────────────────────
SELECT
    o.id,
    o.total,
    (SELECT name FROM customers WHERE id = o.customer_id) AS customer_name
FROM orders o
WHERE o.status = 'shipped';
-- For 10,000 shipped orders → 10,000 individual customer lookups!
-- Even with an index on customers.id, this is 10,000 separate
-- index lookups executed serially. Planners sometimes unnest this
-- to a hash join, but behavior is unpredictable.

-- GOOD: Explicit JOIN — planner knows the cardinality, plans join strategy
SELECT
    o.id,
    o.total,
    c.name AS customer_name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'shipped';
-- Planner chooses: Hash Join (build hash of customers, probe for each order)
-- OR Nested Loop with index lookup (if few shipped orders)
-- Either way: one pass, optimal strategy chosen by planner.

-- ─────────────────────────────────────────────────────────────────
-- Correlated subquery for existence check — BAD
SELECT * FROM orders o
WHERE (SELECT COUNT(*) FROM order_items WHERE order_id = o.id) > 3;
-- COUNT(*) subquery executed for every order row!

-- GOOD: Use EXISTS or JOIN
SELECT o.* FROM orders o
WHERE EXISTS (
    SELECT 1 FROM order_items oi
    WHERE oi.order_id = o.id
      AND oi.id IN (
          SELECT id FROM order_items WHERE order_id = o.id LIMIT 4
      )
);

-- EVEN BETTER: JOIN with HAVING
SELECT o.*
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id
HAVING COUNT(oi.id) > 3;
```

### Rewrite 3: EXISTS vs IN vs JOIN for Existence Checks

When you need to filter rows based on whether a related row exists in another table, the choice between `EXISTS`, `IN`, and `JOIN` matters — both for correctness (when NULL values are involved) and for performance (what plan the planner generates).

```sql
-- Scenario: Find all customers who have placed at least one order.

-- APPROACH 1: IN (subquery)
SELECT * FROM customers
WHERE id IN (SELECT customer_id FROM orders);
-- Performance: varies. Planner may convert to a hash semi-join internally.
-- Correctness trap: if customer_id can be NULL in orders, NULL values
-- cause subtle bugs (nothing matches NULL with IN).

-- APPROACH 2: EXISTS (usually preferred for existence checks)
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders WHERE customer_id = c.id);
-- EXISTS stops as soon as ONE matching row is found (short-circuit).
-- NULL-safe: EXISTS never returns false due to NULLs.
-- Planner often produces the same plan as IN for simple cases.

-- APPROACH 3: JOIN + DISTINCT
SELECT DISTINCT c.*
FROM customers c
JOIN orders o ON o.customer_id = c.id;
-- Correct but DISTINCT adds a sort/hash step.
-- If customer can appear in orders many times → more rows before DISTINCT.
-- Generally the worst of the three for this use case.

-- APPROACH 4: LEFT JOIN + IS NOT NULL (anti-pattern, avoid!)
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NOT NULL;
-- Functionally correct but creates a full join before filtering.
-- More expensive than EXISTS for existence checks.

-- VERDICT:
-- EXISTS: best for existence checks (semantically clear, NULL-safe, efficient)
-- IN: fine for small, non-nullable subquery results
-- JOIN: best when you also need columns from the joined table

-- Finding customers who have NO orders (anti-join):
-- GOOD: LEFT JOIN IS NULL (efficient anti-join)
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- ALSO GOOD: NOT EXISTS
SELECT * FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders WHERE customer_id = c.id);

-- BAD: NOT IN (NULL trap — if ANY order has NULL customer_id, nothing matches!)
SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM orders);
-- If customer_id has even ONE NULL in orders → result is empty! Bug!
```

### Rewrite 4: CTEs — Materialization vs Optimization Fence

Common Table Expressions (CTEs, written with `WITH`) are powerful tools for code organization, but in PostgreSQL 12+ their optimization behavior changed significantly, and understanding this is crucial.

```sql
-- PostgreSQL 12+ default: CTEs are "inlined" (optimized away as subqueries)
-- The planner can push filters INTO the CTE and optimize across the boundary.

-- Example: This CTE is inlined — the planner pushes WHERE into it
WITH recent_orders AS (
    SELECT * FROM orders WHERE created_at >= '2024-01-01'
)
SELECT * FROM recent_orders WHERE customer_id = 42;
-- Planner sees this as: SELECT * FROM orders WHERE created_at >= '2024-01-01'
--                                                 AND customer_id = 42;
-- Uses index on (customer_id, created_at) if available. ✓

-- MATERIALIZED: Force the CTE to execute once and cache (like a temp table)
WITH recent_orders AS MATERIALIZED (
    SELECT * FROM orders WHERE created_at >= '2024-01-01'
)
SELECT * FROM recent_orders WHERE customer_id = 42;
-- CTE executes FULLY first (all recent orders), then filters by customer_id.
-- Use MATERIALIZED when:
-- 1. CTE is referenced multiple times (avoid re-execution)
-- 2. CTE has side effects (e.g., INSERT ... RETURNING inside CTE)
-- 3. You want the CTE to act as an optimization fence intentionally

-- NOT MATERIALIZED: Explicitly inline (equivalent to default in PG12+)
WITH recent_orders AS NOT MATERIALIZED (
    SELECT * FROM orders WHERE created_at >= '2024-01-01'
)
SELECT * FROM recent_orders WHERE customer_id = 42;
```

## 2. Avoiding N+1 Patterns

### The Most Common Performance Killer in Application Code

The **N+1 query problem** is arguably the single most common cause of database performance degradation in application-layer code. It occurs when an application loads a list of N records in one query, and then — in a loop — executes an additional query for each of those N records to load related data. The name comes from the count: 1 initial query to load the list, plus N queries (one per record) to load the details. What should be O(1) database operations becomes O(N) operations, and as N grows, the application drowns in database round trips.

```
  N+1 PATTERN: WHAT HAPPENS IN PRACTICE

  Application code (pseudo-code):
  orders = db.query("SELECT * FROM orders WHERE status='shipped' LIMIT 50")
  // → 1 database query, returns 50 orders

  for each order in orders:
      customer = db.query("SELECT * FROM customers WHERE id = ?", order.customer_id)
      // → 1 database query PER order = 50 more queries!

  TOTAL: 1 + 50 = 51 queries to display 50 orders with customer names.

  Cost breakdown:
  ┌──────────────────────────────────────────────────────────────────┐
  │ Query 1 (the list):                                              │
  │   Network latency: 1ms                                           │
  │   DB execution: 2ms                                              │
  │   Total: 3ms                                                     │
  │                                                                  │
  │ Queries 2-51 (N+1):                                             │
  │   50 queries × (1ms network + 0.1ms execution) = 55ms           │
  │                                                                  │
  │ Grand total: 3ms + 55ms = 58ms                                   │
  │ With JOIN approach: 3ms + 2ms = 5ms  (12× faster!)              │
  │                                                                  │
  │ At N=1000 (1000 orders on a page):                               │
  │   N+1: 1001 × 1ms = 1001ms  ≈ 1 second                          │
  │   JOIN: 5ms                  (200× faster!)                      │
  └──────────────────────────────────────────────────────────────────┘
```

### The JOIN Solution

The most straightforward solution to the N+1 problem is to use a JOIN that fetches all the needed data in a single query. Instead of fetching orders and then looking up each customer individually, fetch orders and customers together.

```sql
-- N+1 PROBLEM:
-- Query 1: SELECT * FROM orders WHERE status='shipped' LIMIT 50;
-- Query 2..51: SELECT * FROM customers WHERE id = ?; (once per order)

-- SOLUTION 1: JOIN — fetch everything in one query
SELECT
    o.id            AS order_id,
    o.total,
    o.created_at,
    c.id            AS customer_id,
    c.name          AS customer_name,
    c.email         AS customer_email
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'shipped'
ORDER BY o.created_at DESC
LIMIT 50;
-- ONE query, returns all needed columns for all 50 orders.
-- No application-level loop of database calls needed.

-- ─────────────────────────────────────────────────────────────────
-- Multiple levels of N+1 (nested N+1 — even more dangerous)
-- ─────────────────────────────────────────────────────────────────

-- BAD (pseudo-code):
-- orders = fetch 50 orders      → 1 query
-- for each order:               → 50 queries for customers
--   customer = fetch customer
--   for each order:             → 50 queries for order_items
--     items = fetch items       → 50 × 10 = 500 queries for products
--     for each item:
--       product = fetch product
-- TOTAL: 1 + 50 + 50 + 500 = 601 queries!

-- SOLUTION: Multi-level JOIN
SELECT
    o.id            AS order_id,
    o.total,
    c.name          AS customer_name,
    oi.id           AS item_id,
    oi.quantity,
    p.name          AS product_name,
    p.price
FROM orders o
JOIN customers c    ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
WHERE o.status = 'shipped'
ORDER BY o.created_at DESC, oi.id
LIMIT 500;  -- Note: LIMIT applies to rows, not orders (join inflation)

-- Application reassembles the flat rows into nested objects
-- (group by order_id, then items per order)
```

### The Batch Load Solution (When JOIN Is Not Appropriate)

Sometimes a JOIN is not the right tool — perhaps the related data lives in a different service, a different database, or the JOIN would produce a combinatorial explosion of rows. In these cases, the **batch load** pattern replaces the N individual queries with a single query that fetches all needed related records at once using an `IN` clause.

```sql
-- Pattern: Collect all needed IDs first, then fetch all at once

-- BAD (N+1 in application):
-- Step 1: SELECT id, customer_id, total FROM orders WHERE status='shipped' LIMIT 50;
-- Step 2..51: SELECT * FROM customers WHERE id = ?;  (50 times!)

-- GOOD (batch load):
-- Step 1: SELECT id, customer_id, total FROM orders WHERE status='shipped' LIMIT 50;
-- Step 2: Collect all customer_ids from the result = [1, 4, 7, 22, ...]
-- Step 3: ONE query to fetch all needed customers:
SELECT * FROM customers WHERE id IN (1, 4, 7, 22, ...);
-- Application joins results in memory by customer_id

-- TOTAL: 2 queries regardless of N (1 for orders + 1 for customers)

-- When to use batch load over JOIN:
-- ✓ Related data is in a separate database or service
-- ✓ JOIN would cause row explosion (many-to-many with many rows)
-- ✓ You need to call different services for different associations
-- ✗ Do NOT use if JOIN is simple and all data is in the same DB
--   (JOIN is more efficient than two round trips + IN clause)

-- ─────────────────────────────────────────────────────────────────
-- ORM-level N+1: The hidden danger in frameworks
-- ─────────────────────────────────────────────────────────────────

-- In ORMs (Django, Rails, GORM, Hibernate), N+1 often appears silently:

-- Django (BAD — N+1):
-- orders = Order.objects.filter(status='shipped')[:50]
-- for order in orders:
--     print(order.customer.name)  # ← each .customer access is a query!

-- Django (GOOD — eager loading with select_related):
-- orders = Order.objects.filter(status='shipped').select_related('customer')[:50]
-- # ONE query with JOIN: no N+1

-- Rails (BAD — N+1):
-- orders = Order.where(status: 'shipped').limit(50)
-- orders.each { |o| puts o.customer.name }  # N+1!

-- Rails (GOOD — eager loading):
-- orders = Order.includes(:customer).where(status: 'shipped').limit(50)
-- # ONE query or batch load (includes automatically chooses strategy)

-- GORM (Go — BAD — N+1):
-- db.Limit(50).Where("status = ?", "shipped").Find(&orders)
-- for _, order := range orders {
--     db.First(&customer, order.CustomerID)  // N queries!
-- }

-- GORM (Go — GOOD — Preload):
-- db.Preload("Customer").Limit(50).Where("status = ?", "shipped").Find(&orders)
-- // Two queries: orders + all customers in one IN query
```

## 3. Pagination — OFFSET vs Keyset (Cursor-Based) Pagination

### The Universal Requirement and Its Hidden Costs

Almost every application that displays lists of data requires pagination — showing a subset of results at a time, with the ability to navigate to subsequent pages. The simplest implementation, reaching for `OFFSET` and `LIMIT`, seems perfectly natural and is almost universally misused at scale. Understanding *why* OFFSET-based pagination degrades is essential for building applications that remain fast as their data grows.

### OFFSET Pagination and Its Fundamental Problem

`OFFSET N LIMIT M` tells the database: "Skip the first N rows and return the next M." The problem is in how the database implements this instruction. It cannot teleport to row N — it must read and count rows from the beginning until it has counted N of them, then start returning rows. Even if only M rows are ultimately returned, the database must touch N + M rows in total. As the user navigates deeper into the result set, OFFSET grows, and the work the database must do grows with it.

```
  OFFSET PAGINATION: PERFORMANCE DEGRADATION

  Table: articles (5,000,000 rows), ordered by created_at DESC
  Page size: 20 articles

  Page 1:  SELECT * FROM articles ORDER BY created_at DESC LIMIT 20 OFFSET 0
           → Reads rows 1-20, returns 20. Fast. ✓

  Page 2:  SELECT * FROM articles ORDER BY created_at DESC LIMIT 20 OFFSET 20
           → Reads rows 1-40, returns rows 21-40. Still fast.

  Page 100: SELECT * FROM articles ORDER BY created_at DESC LIMIT 20 OFFSET 1980
            → Reads 2,000 rows, discards 1,980, returns 20.

  Page 1000: LIMIT 20 OFFSET 19980
             → Reads 20,000 rows, discards 19,980, returns 20.

  Page 10000: LIMIT 20 OFFSET 199980
              → Reads 200,000 rows, discards 199,980, returns 20.
              → This is a 200,000-row scan to show 20 articles!

  COST GROWTH:
  ┌───────────────┬─────────────────┬──────────────────────────────────┐
  │ Page number   │ Rows read by DB │ Rows returned to application     │
  ├───────────────┼─────────────────┼──────────────────────────────────┤
  │ Page 1        │ 20              │ 20                               │
  │ Page 100      │ 2,000           │ 20  (99% of work is wasted!)     │
  │ Page 1,000    │ 20,000          │ 20  (99.9% wasted!)              │
  │ Page 10,000   │ 200,000         │ 20  (99.99% wasted!)             │
  │ Page 100,000  │ 2,000,000       │ 20  (full table scan territory!) │
  └───────────────┴─────────────────┴──────────────────────────────────┘

  Additional problem: Phantom rows
  If new rows are inserted between page 1 and page 2, OFFSET-based
  pagination will show the same row twice (if it pushed a previous row
  to the next page) or skip a row entirely. The pages are not stable.
```

### Keyset Pagination (Cursor-Based Pagination)

**Keyset pagination** — also known as **cursor-based pagination** or the **seek method** — eliminates the OFFSET problem by not skipping rows at all. Instead of telling the database "skip N rows," it tells the database "start from after this specific row." The "cursor" is the value of the ordering column(s) of the last row seen on the previous page. The query uses `WHERE (order_column > last_value)` rather than `OFFSET N`.

Because the index on the ordering column can directly position to the row after the cursor, this query performs the same amount of work regardless of which "page" you are on — whether you are viewing page 1 or page 1,000,000, the database does the same O(log N + page_size) work.

```
  KEYSET PAGINATION: O(log N + page_size) ALWAYS

  Table: articles, ordered by created_at DESC
  Index: idx_articles_created_at ON articles(created_at DESC)

  Page 1 (first page, no cursor):
  SELECT id, title, created_at
  FROM articles
  ORDER BY created_at DESC
  LIMIT 20;
  → Last row returned: id=1050, created_at='2024-03-15 10:30:00'
  → Client stores cursor: '2024-03-15 10:30:00' (and optionally id=1050)

  Page 2 (using cursor from page 1):
  SELECT id, title, created_at
  FROM articles
  WHERE created_at < '2024-03-15 10:30:00'  -- CURSOR: after last seen row
  ORDER BY created_at DESC
  LIMIT 20;
  → Index seek directly to '2024-03-15 10:30:00'
  → Read exactly 20 rows. DONE. No skipping!

  Page 1000 (using cursor from page 999):
  SELECT id, title, created_at
  FROM articles
  WHERE created_at < '2024-02-20 08:15:00'  -- Cursor from page 999
  ORDER BY created_at DESC
  LIMIT 20;
  → SAME plan as page 2. Index seek → read 20 rows. DONE.

  COST: IDENTICAL regardless of page number!
  ┌───────────────┬─────────────────────────────────────┐
  │ Page number   │ Rows read by DB                     │
  ├───────────────┼─────────────────────────────────────┤
  │ Page 1        │ 20 (always!)                        │
  │ Page 100      │ 20 (always!)                        │
  │ Page 1,000    │ 20 (always!)                        │
  │ Page 100,000  │ 20 (always!)                        │
  └───────────────┴─────────────────────────────────────┘
```

### Handling Ties: Composite Cursor

A critical detail of keyset pagination is handling ties — rows where the ordering column has identical values. If multiple articles share the same `created_at` timestamp, `WHERE created_at < last_created_at` might skip some of them or include some twice, depending on how many fit on a page boundary. The solution is a **composite cursor** using a secondary column (typically the primary key) to break ties.

```sql
-- ─────────────────────────────────────────────────────────────────
-- COMPOSITE CURSOR: Handle ties with a secondary sort column
-- ─────────────────────────────────────────────────────────────────

-- Index to support composite cursor:
CREATE INDEX idx_articles_pagination ON articles (created_at DESC, id DESC);

-- Page 1:
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC, id DESC  -- Secondary sort by id breaks ties
LIMIT 20;
-- Last row: created_at='2024-03-15 10:30:00', id=1050
-- Cursor: {created_at: '2024-03-15 10:30:00', id: 1050}

-- Page 2 (composite cursor condition):
SELECT id, title, created_at
FROM articles
WHERE (created_at, id) < ('2024-03-15 10:30:00', 1050)
   -- PostgreSQL supports row-value comparison: (a,b) < (x,y)
   -- Equivalent to: (created_at < x) OR (created_at = x AND id < y)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- For databases without row-value comparison (MySQL before 8.0):
WHERE created_at < '2024-03-15 10:30:00'
   OR (created_at = '2024-03-15 10:30:00' AND id < 1050)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────
-- KEYSET PAGINATION FOR APIs (practical implementation)
-- ─────────────────────────────────────────────────────────────────

-- First page request (no cursor):
SELECT id, title, created_at, author_id
FROM articles
WHERE status = 'published'
ORDER BY created_at DESC, id DESC
LIMIT 21;  -- Fetch one extra row to know if there is a next page!
-- If 21 rows returned: hasNextPage = true, return only first 20
-- If ≤ 20 rows returned: hasNextPage = false (last page)

-- API response includes:
-- { data: [...20 articles], nextCursor: "2024-03-15T10:30:00Z_1050" }

-- Subsequent page request (cursor provided by client):
-- Parse cursor: created_at='2024-03-15 10:30:00', id=1050
SELECT id, title, created_at, author_id
FROM articles
WHERE status = 'published'
  AND (created_at, id) < ('2024-03-15 10:30:00', 1050)
ORDER BY created_at DESC, id DESC
LIMIT 21;

-- ─────────────────────────────────────────────────────────────────
-- OFFSET vs KEYSET: When to use each
-- ─────────────────────────────────────────────────────────────────

-- USE OFFSET when:
-- ✓ User needs to jump to arbitrary page number ("Go to page 47")
-- ✓ Total row count is needed ("Showing 23 of 4,521 results")
-- ✓ Data set is small (< 10,000 rows total — OFFSET cost is negligible)
-- ✓ UI requires numbered page navigation

-- USE KEYSET when:
-- ✓ Infinite scroll / "Load more" UI pattern
-- ✓ API pagination (REST/GraphQL with cursor)
-- ✓ Large data sets (100K+ rows)
-- ✓ Consistent, non-duplicating pages (no phantom rows from inserts)
-- ✓ Feed-style content (Twitter timeline, news feeds)
-- ✗ Cannot jump to arbitrary page number
-- ✗ Cannot easily show total count
```

## 4. Batch Inserts and Bulk Operations

### The Overhead of Individual Statements

Every SQL statement — regardless of how trivial — incurs a fixed overhead: it must be parsed, planned, and its execution must be wrapped in a transaction (implicit if not explicit). For a single INSERT of one row, this overhead is negligible. But when an application needs to insert thousands or millions of rows, executing individual INSERT statements in a loop multiplies this overhead by N — and the cumulative cost can be enormous.

The overhead per statement includes: network round trip (client sends query, server responds), query parsing and planning, transaction begin and commit overhead, WAL (Write-Ahead Log) flush (if autocommit is on, each INSERT triggers its own fsync to durable storage), and index update for each individual row. At high insert volumes, the WAL flush alone can become the bottleneck — each individual INSERT forces a disk sync.

```
  INDIVIDUAL INSERT vs BATCH INSERT: Cost Comparison

  Scenario: Insert 10,000 product records

  INDIVIDUAL INSERTS (application loop):
  for product in products:
      db.execute("INSERT INTO products VALUES (?)", product)
      # Each insert: 1 network RTT + 1 plan + 1 WAL flush + 1 index update

  Cost per insert: ~5ms (1ms network + 4ms overhead on spinning disk)
  Total: 10,000 × 5ms = 50 seconds!

  SINGLE MULTI-VALUE INSERT:
  INSERT INTO products (name, price, stock) VALUES
      ('Widget A', 9.99,  100),
      ('Widget B', 14.99,  50),
      ('Widget C', 4.99,  200),
      -- ... 10,000 rows in one statement
  ;
  Cost: 1 network RTT + 1 plan + 1 WAL flush + batch index update
  Total: ~0.5 seconds (100× faster!)

  WRAPPED IN ONE TRANSACTION (separate statements but one commit):
  BEGIN;
  INSERT INTO products VALUES (...);  -- row 1
  INSERT INTO products VALUES (...);  -- row 2
  ...  -- 10,000 individual INSERTs but ONE transaction
  COMMIT;
  Cost: 10,000 plans + 1 WAL flush (at COMMIT)
  Total: ~5 seconds (10× faster than individual commits, 10× slower than multi-value)
```

### Multi-Value INSERT: The Single Statement Approach

```sql
-- ─────────────────────────────────────────────────────────────────
-- MULTI-VALUE INSERT: Insert many rows in one statement
-- ─────────────────────────────────────────────────────────────────

-- Standard multi-value syntax (works in all major databases):
INSERT INTO products (name, price, stock, category_id)
VALUES
    ('Wireless Mouse',    29.99,  50, 3),
    ('Mechanical Keyboard', 79.99, 30, 3),
    ('USB-C Hub',        39.99, 100, 4),
    ('Laptop Stand',     49.99,  25, 4),
    ('Monitor Arm',      89.99,  15, 5);
-- One network round trip. One transaction. One WAL flush. ✓

-- PostgreSQL: INSERT ... SELECT (from another table or CTE)
INSERT INTO products_archive (name, price, stock, archived_at)
SELECT name, price, stock, NOW()
FROM products
WHERE last_sold < NOW() - INTERVAL '1 year';
-- Moves entire result set in one operation — no round trip per row

-- ─────────────────────────────────────────────────────────────────
-- UPSERT (INSERT OR UPDATE) — Batch with conflict handling
-- ─────────────────────────────────────────────────────────────────
-- PostgreSQL: INSERT ... ON CONFLICT
INSERT INTO products (id, name, price, stock)
VALUES
    (1, 'Wireless Mouse',  29.99, 50),
    (2, 'Keyboard',        79.99, 30),
    (3, 'New Product',     19.99, 200)
ON CONFLICT (id) DO UPDATE
SET
    name  = EXCLUDED.name,
    price = EXCLUDED.price,
    stock = EXCLUDED.stock;
-- Inserts new rows; updates existing ones. All in one atomic statement.

-- MySQL equivalent:
INSERT INTO products (id, name, price, stock)
VALUES
    (1, 'Wireless Mouse', 29.99, 50),
    (2, 'Keyboard',       79.99, 30)
ON DUPLICATE KEY UPDATE
    name  = VALUES(name),
    price = VALUES(price),
    stock = VALUES(stock);

-- ─────────────────────────────────────────────────────────────────
-- BULK UPDATE: Update many rows efficiently
-- ─────────────────────────────────────────────────────────────────

-- BAD: Individual updates in a loop (N round trips)
-- for (id, new_price) in updates:
--     UPDATE products SET price = ? WHERE id = ?;

-- GOOD: Bulk update using VALUES CTE
UPDATE products
SET price = bulk.new_price
FROM (VALUES
    (1, 34.99),
    (2, 84.99),
    (3, 44.99),
    (4, 54.99)
) AS bulk(id, new_price)
WHERE products.id = bulk.id;
-- One query updates all rows. ✓

-- Alternative: Temporary table for very large bulk updates
CREATE TEMP TABLE price_updates (id BIGINT, new_price NUMERIC);
-- Batch load prices into temp table (COPY for large datasets):
COPY price_updates FROM STDIN;  -- Stream data without SQL overhead
UPDATE products
SET price = pu.new_price
FROM price_updates pu
WHERE products.id = pu.id;
DROP TABLE price_updates;

-- ─────────────────────────────────────────────────────────────────
-- COPY: The fastest bulk insert mechanism
-- ─────────────────────────────────────────────────────────────────
-- COPY bypasses the SQL parser and planner for data loading.
-- It streams raw data directly into the table.
-- Fastest method for loading millions of rows.

-- From a CSV file:
COPY products (name, price, stock, category_id)
FROM '/path/to/products.csv'
WITH (FORMAT csv, HEADER true, DELIMITER ',');

-- From application (streaming):
-- In Go: pgx COPY protocol
-- In Python: psycopg2 copy_from()
-- In Java: JDBC copyIn()

-- COPY performance:
-- Multi-value INSERT: ~100,000 rows/second
-- COPY:              ~500,000-1,000,000 rows/second (5-10× faster!)

-- ─────────────────────────────────────────────────────────────────
-- BATCH PROCESSING: Avoid locking the entire table
-- ─────────────────────────────────────────────────────────────────

-- For large updates/deletes: process in batches
-- (prevents lock escalation, reduces replication lag, allows vacuuming)

DO $$
DECLARE
    batch_size  INT := 5000;
    rows_done   INT;
BEGIN
    LOOP
        DELETE FROM logs
        WHERE id IN (
            SELECT id FROM logs
            WHERE created_at < NOW() - INTERVAL '90 days'
            LIMIT batch_size
        );
        GET DIAGNOSTICS rows_done = ROW_COUNT;
        EXIT WHEN rows_done = 0;
        PERFORM pg_sleep(0.05);  -- Brief pause to let replication catch up
    END LOOP;
END $$;
```

## 5. Avoiding Unnecessary ORDER BY

### The Hidden Cost of Sorting

`ORDER BY` is one of the most expensive operations in a query — and one of the most frequently applied unnecessarily. Sorting requires the database to either find a pre-sorted data source (an index whose order matches the sort request) or to perform an in-memory or on-disk sort of the entire result set before returning rows. When the result set is large and no suitable index exists, `ORDER BY` requires sorting all matching rows — an O(N log N) operation that can dwarf the cost of every other part of the query.

The key question to ask before every `ORDER BY` is: "Does this result set actually need to be in a specific order for the application to function correctly?" In many cases, the answer is no — the developer added `ORDER BY` out of habit or for visual tidiness during development, not because the application requires it.

```
  ORDER BY COST ANALYSIS

  Query: SELECT * FROM orders WHERE status = 'shipped' ORDER BY id DESC;
  Matching rows: 500,000

  Case 1: Index on (status, id DESC) exists:
  → Index scan returns rows in DESC id order naturally
  → No additional sort needed!
  → Cost: O(log N + result_size) — index provides ordering for free
  EXPLAIN: Index Scan Backward using idx_orders_status_id on orders

  Case 2: Only index on (status) exists, no index on id:
  → Index scan on status (returns 500,000 rows in random order)
  → Database must sort 500,000 rows by id DESC
  → If result fits in work_mem: in-memory quicksort (expensive but OK)
  → If result exceeds work_mem: ON-DISK MERGE SORT (very expensive!)
  EXPLAIN: Sort (cost=180,000..182,000 rows=500000 width=120)
             Sort Key: id DESC
             Sort Method: external merge Disk: 48000kB ← disk sort!
           → Seq Scan / Index Scan on orders

  Disk sort: reads and writes to temporary files repeatedly.
  For 500,000 rows at ~500 bytes/row = 250MB disk I/O just for sort!

  ─────────────────────────────────────────────────────────────────
  WHEN ORDER BY IS UNNECESSARY:
  ─────────────────────────────────────────────────────────────────
  1. COUNT, SUM, AVG aggregations — order doesn't affect result
  2. EXISTS subquery — order of the first-found row doesn't matter
  3. Results that will be reordered in application memory anyway
  4. Intermediate CTEs used in joins (not final output)
  5. INSERT INTO ... SELECT where destination has no required order
  6. Any SELECT whose results are not displayed to a user in order
```

### Common Unnecessary ORDER BY Patterns

```sql
-- ─────────────────────────────────────────────────────────────────
-- BAD: ORDER BY inside a subquery that is then aggregated
-- The outer aggregate doesn't care about order!
-- ─────────────────────────────────────────────────────────────────
SELECT COUNT(*) FROM (
    SELECT * FROM orders WHERE status = 'shipped' ORDER BY id  -- POINTLESS!
) sub;

-- GOOD:
SELECT COUNT(*) FROM orders WHERE status = 'shipped';

-- ─────────────────────────────────────────────────────────────────
-- BAD: ORDER BY in INSERT ... SELECT — destination has no order
-- ─────────────────────────────────────────────────────────────────
INSERT INTO order_archive (id, customer_id, total)
SELECT id, customer_id, total
FROM orders
WHERE created_at < '2023-01-01'
ORDER BY id;  -- Completely pointless! Tables have no inherent order.

-- GOOD:
INSERT INTO order_archive (id, customer_id, total)
SELECT id, customer_id, total
FROM orders
WHERE created_at < '2023-01-01';

-- ─────────────────────────────────────────────────────────────────
-- BAD: ORDER BY on a join that is only used for COUNT
-- ─────────────────────────────────────────────────────────────────
SELECT c.id, c.name, COUNT(o.id) AS order_count
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY c.name;  -- Needed? Only if displaying sorted to user!

-- If result is processed programmatically (not displayed), remove ORDER BY.
-- If it IS displayed, it's needed. But consider: can the application sort?
-- Application-level sorting of small result sets is free and removes DB cost.

-- ─────────────────────────────────────────────────────────────────
-- WHEN ORDER BY IS REQUIRED but slow: Add a covering index
-- ─────────────────────────────────────────────────────────────────

-- Query: Latest 20 published articles per category
SELECT id, title, created_at, category_id
FROM articles
WHERE status = 'published'
ORDER BY created_at DESC
LIMIT 20;
-- Without index: sort 1M articles, then take 20
-- SOLUTION: Index that provides ordering for free:
CREATE INDEX idx_articles_status_date
ON articles (status, created_at DESC)
INCLUDE (id, title);
-- With this index: index range scan on status='published' already in
-- DESC created_at order → planner uses index, no sort needed → fast!

-- ─────────────────────────────────────────────────────────────────
-- work_mem: Increase to prevent disk sorts
-- ─────────────────────────────────────────────────────────────────
-- When ORDER BY cannot be avoided and no index provides ordering:
SET work_mem = '64MB';  -- Allow larger in-memory sorts
-- Each sort operation can use up to work_mem of RAM before spilling to disk.
-- Set per-session for specific heavy queries, not globally.
-- Warning: work_mem is per sort operation, per query.
-- A query with multiple sorts can use 2-3× work_mem simultaneously.
```

## 6. Short-Circuit Evaluation

### Conditions That Eliminate Work Early

**Short-circuit evaluation** is the principle of arranging query conditions so that the cheapest, most selective conditions are evaluated first — failing fast and avoiding expensive operations for rows that would be filtered out anyway. In SQL, this manifests in WHERE clause ordering, CASE expression ordering, and the use of conditions that can eliminate large amounts of work before expensive operations are performed.

Most SQL databases evaluate WHERE conditions in an order determined by the query optimizer, not necessarily the order you write them. However, there are important cases where the developer's arrangement does matter — particularly in CASE expressions, COALESCE chains, and certain function calls where evaluation order is guaranteed by the language semantics.

```
  SHORT-CIRCUIT IN WHERE CLAUSES

  The query optimizer rearranges WHERE conditions based on estimated cost and
  selectivity — it usually applies the cheapest, most selective condition first.
  But you can help by writing queries that make selectivity obvious.

  Example: Filtering orders that are 'shipped' AND have total > 1000
  orders table: 1,000,000 rows
  'shipped' orders: 250,000 (25% of table)
  total > 1000: 50,000 (5% of table)

  If evaluated LEFT-TO-RIGHT literally:
  Step 1: status = 'shipped' → 250,000 rows pass to step 2
  Step 2: total > 1000       → 50,000 rows pass (of the 250,000 from step 1)
  → Better: apply most selective first

  If 'total > 1000' evaluated first:
  Step 1: total > 1000       → 50,000 rows (5% of table)
  Step 2: status = 'shipped' → narrowed further
  → Fewer rows pass through the more expensive step

  The planner handles this automatically in most cases.
  But with complex function calls or expensive predicates,
  you can help the planner by annotating cost or using CASE:
```

### Short-Circuiting Expensive Function Calls

The most important application of short-circuit evaluation at the query level is protecting expensive operations (regex matching, full-text search, JSON parsing, external function calls) behind cheap, selective conditions that will eliminate most rows before the expensive operation runs.

```sql
-- ─────────────────────────────────────────────────────────────────
-- CASE EXPRESSION: Guaranteed short-circuit (SQL standard)
-- ─────────────────────────────────────────────────────────────────

-- In a CASE expression, conditions are evaluated LEFT TO RIGHT.
-- Once a condition matches, subsequent WHEN clauses are NOT evaluated.
-- Put cheapest/most-common cases FIRST.

-- BAD: Expensive operation (regex) evaluated for every row
SELECT id,
    CASE
        WHEN description ~ '^[A-Z]{3}-\d{4}-.*'  -- Regex: expensive!
             THEN 'SKU format'
        WHEN type = 'product'                      -- Cheap: column compare
             THEN 'Product'
        ELSE 'Other'
    END AS category
FROM items;

-- GOOD: Cheap condition first — regex only runs for 'product' type rows
SELECT id,
    CASE
        WHEN type = 'product'                      -- Cheap: filters most rows
             THEN 'Product'
        WHEN description ~ '^[A-Z]{3}-\d{4}-.*'  -- Expensive: only for non-product
             THEN 'SKU format'
        ELSE 'Other'
    END AS category
FROM items;

-- ─────────────────────────────────────────────────────────────────
-- WHERE clause: Protect expensive operations with cheap guards
-- ─────────────────────────────────────────────────────────────────

-- BAD: Regex applied to ALL rows (no cheap pre-filter)
SELECT * FROM articles
WHERE description ~ 'complex.*regex.*pattern';
-- Full table scan + regex evaluation for every row!

-- GOOD: Cheap filter first reduces rows before regex runs
SELECT * FROM articles
WHERE status = 'published'           -- Cheap: index lookup, eliminates 80% of rows
  AND description ~ 'complex.*regex.*pattern';  -- Regex only for published rows
-- (Planner pushes status check first automatically in most cases)

-- EVEN BETTER: Use full-text search index instead of regex
CREATE INDEX idx_articles_fts ON articles USING gin(to_tsvector('english', description));
SELECT * FROM articles
WHERE status = 'published'
  AND to_tsvector('english', description) @@ to_tsquery('english', 'pattern');
-- Index-based text search: O(log N) instead of O(N) regex scan

-- ─────────────────────────────────────────────────────────────────
-- COALESCE: Short-circuits on first non-NULL value
-- ─────────────────────────────────────────────────────────────────
-- COALESCE evaluates arguments LEFT TO RIGHT and returns the first non-NULL.
-- Put cheapest / most-commonly-non-NULL expressions first.

-- BAD: Expensive function called first, even when column is non-null
SELECT COALESCE(get_computed_price(id), price, 0.0) FROM products;
-- get_computed_price() is an expensive UDF called for EVERY row!

-- GOOD: Cheap column check first — expensive function only when column is NULL
SELECT COALESCE(price, get_computed_price(id), 0.0) FROM products;
-- If price is non-null (99% of rows): returns immediately, no UDF call!
-- UDF only called for the rare rows where price IS NULL.

-- ─────────────────────────────────────────────────────────────────
-- Avoid unnecessary function calls in SELECT
-- ─────────────────────────────────────────────────────────────────

-- BAD: Expensive calculation for every row, even when not needed
SELECT
    id,
    name,
    calculate_discount(id, customer_id, promo_code),  -- UDF called for ALL rows
    total
FROM orders
WHERE status = 'pending';

-- GOOD: Only call expensive function when business logic requires it
SELECT
    id,
    name,
    CASE
        WHEN promo_code IS NOT NULL
         AND promo_code != ''
        THEN calculate_discount(id, customer_id, promo_code)  -- Only when promo exists
        ELSE 0
    END AS discount,
    total
FROM orders
WHERE status = 'pending';

-- ─────────────────────────────────────────────────────────────────
-- NOT NULL checks: Short-circuit joins
-- ─────────────────────────────────────────────────────────────────

-- BAD: Joins an optional table even when the FK is NULL
SELECT o.id, o.total, c.name
FROM orders o
LEFT JOIN campaigns c ON c.id = o.campaign_id;
-- Every order attempts the LEFT JOIN lookup, even if campaign_id IS NULL.

-- GOOD: Short-circuit NULL foreign keys before joining
SELECT o.id, o.total, c.name
FROM orders o
LEFT JOIN campaigns c ON c.id = o.campaign_id AND o.campaign_id IS NOT NULL;
-- The IS NOT NULL condition tells the planner to skip the join
-- for rows where campaign_id is NULL. Reduces join probe operations.

-- OR restructure if campaigns are rarely set:
SELECT o.id, o.total, NULL AS campaign_name
FROM orders o WHERE o.campaign_id IS NULL
UNION ALL
SELECT o.id, o.total, c.name
FROM orders o
JOIN campaigns c ON c.id = o.campaign_id
WHERE o.campaign_id IS NOT NULL;
```

## Summary: The Query Optimization Mindset

Query optimization is not a collection of tricks — it is a way of thinking. Every query you write is a contract between your application and the database, specifying not just what you want but implicitly how the database will retrieve it. The engineer who thinks about selectivity, about index usage, about round trips, about sort costs — before writing the query — writes queries that perform well at every scale.

```
  QUERY OPTIMIZATION CHECKLIST

  ┌───────────────────────────────────────────────────────────────────┐
  │ BEFORE WRITING: Think about the data                              │
  │ ✓ How many rows will this query touch?                            │
  │ ✓ Which condition is most selective? (eliminates the most rows)   │
  │ ✓ Is there an index that covers this query?                       │
  │ ✓ Do I need all columns? (SELECT * vs SELECT columns)             │
  └───────────────────────────────────────────────────────────────────┘

  ┌───────────────────────────────────────────────────────────────────┐
  │ REWRITING FOR THE PLANNER                                         │
  │ ✓ No functions applied to indexed columns in WHERE                │
  │ ✓ Type of parameter matches column type (no implicit cast)        │
  │ ✓ Correlated subqueries replaced with JOINs where possible        │
  │ ✓ EXISTS preferred over COUNT(*) for existence checks             │
  │ ✓ NOT IN replaced with NOT EXISTS (NULL safety + performance)     │
  └───────────────────────────────────────────────────────────────────┘

  ┌───────────────────────────────────────────────────────────────────┐
  │ N+1 PREVENTION                                                    │
  │ ✓ All related data fetched in one JOIN or batch-load              │
  │ ✓ ORM eager loading configured (Preload, select_related, include) │
  │ ✓ EXPLAIN run on ORM-generated queries to check for N+1           │
  └───────────────────────────────────────────────────────────────────┘

  ┌───────────────────────────────────────────────────────────────────┐
  │ PAGINATION                                                        │
  │ ✓ Large result sets use keyset/cursor pagination, not OFFSET      │
  │ ✓ OFFSET used only for small datasets or jump-to-page UIs         │
  │ ✓ Composite cursor handles ties in ordering column                │
  │ ✓ Fetch page_size + 1 rows to detect hasNextPage efficiently      │
  └───────────────────────────────────────────────────────────────────┘

  ┌───────────────────────────────────────────────────────────────────┐
  │ BULK OPERATIONS                                                   │
  │ ✓ Multi-value INSERT for batch inserts(not loop of single INSERTs)│
  │ ✓ Batch updates using VALUES CTE or temp table                    │
  │ ✓ COPY command for large data loads (5-10× faster than INSERT)    │
  │ ✓ Large deletes/updates batched to avoid lock escalation          │
  │ ✓ Multiple single-row writes wrapped in one explicit transaction  │
  └───────────────────────────────────────────────────────────────────┘

  ┌───────────────────────────────────────────────────────────────────┐
  │ ORDER BY                                                          │
  │ ✓ ORDER BY only present when result order genuinely matters       │
  │ ✓ Removed from subqueries and aggregations where order is ignored │
  │ ✓ Index provides ordering where possible (no extra sort step)     │
  │ ✓ work_mem increased for unavoidable large sorts                  │
  └───────────────────────────────────────────────────────────────────┘

  ┌───────────────────────────────────────────────────────────────────┐
  │ SHORT-CIRCUIT & EFFICIENCY                                        │
  │ ✓ Cheap, selective conditions before expensive operations         │
  │ ✓ CASE WHEN: cheapest condition listed first                      │
  │ ✓ COALESCE: most-likely-non-NULL expression listed first          │
  │ ✓ Expensive UDFs guarded by NULL checks or CASE conditions        │
  │ ✓ EXPLAIN ANALYZE run on all new queries before deployment        │
  └───────────────────────────────────────────────────────────────────┘
```

The discipline of query optimization pays compound interest. A query written thoughtlessly today will be executed billions of times over the lifetime of the application. A query written well — one that cooperates with indexes, avoids unnecessary work, eliminates round trips, and sorts only when needed — will serve the system efficiently whether the table holds a thousand rows or a billion.
