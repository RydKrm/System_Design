# Multi-Version Concurrency Control (MVCC) — A Deep Study Guide

> *"The fundamental problem of database concurrency is this: how do you allow many transactions to read and write simultaneously without letting them interfere with each other? The traditional answer was locking — readers and writers take turns, each waiting for the other to finish. MVCC offers a more elegant answer: instead of taking turns, give everyone their own consistent view of the past. Writers create new versions. Readers consult old versions. No one waits for anyone. The database becomes, in a sense, a time machine — every transaction seeing the world as it was at the precise moment it started."*

In the previous chapter on locking, we studied how databases use locks to coordinate concurrent access to shared data. Locking works, but it has a fundamental limitation: it creates contention. When a writer holds a lock, readers must wait. When a reader holds a lock, writers must wait. In a high-concurrency OLTP system, this contention can become a severe bottleneck — not because the hardware is slow, but because transactions are constantly waiting for each other to release locks.

**Multi-Version Concurrency Control (MVCC)** is the architectural alternative to lock-based concurrency that almost every modern relational database has adopted. Rather than making readers and writers share a single "current" version of each row and coordinating access to it with locks, MVCC maintains **multiple versions** of each row simultaneously. A write operation creates a new version rather than overwriting the old one. Readers consult the version that was current at the time their transaction started, regardless of what has been written since. The result is a system where **readers never block writers, and writers never block readers** — a property that dramatically increases throughput in read-heavy workloads.

## 1. How MVCC Avoids Read Locks

### The Core Insight: Time Travel Instead of Waiting

To understand how MVCC eliminates read locks, we first need to understand why read locks exist in the first place. In a lock-based system, a reader must hold a shared lock on a row to prevent a writer from modifying it mid-read — because if the writer changes the row while the reader is using it, the reader might see a half-written, inconsistent state. The shared lock is the reader's way of saying: "Freeze this row in its current state for me while I read it."

MVCC makes this unnecessary by offering the reader something better than freezing the row: a **guaranteed consistent snapshot of the past**. Instead of preventing the row from changing (which requires a lock), MVCC lets the row change freely — the writer creates a new version — while the reader continues to see the old version that existed when its transaction began. The reader does not need a lock because it is not reading the current "live" version of the row. It is reading a specific historical version that belongs to it and to it alone, and no future write can retroactively alter that historical version.

```
  LOCK-BASED SYSTEM: Readers and writers contend

  Time →
  ┌──────────────────────────────────────────────────────────────────┐
  │  Reader A: ← needs S-lock → WAITS ←─────────────────────────    │
  │  Writer B:  ───── holds X-lock ────── writes ──── releases ──→   │
  │                                                                  │
  │  Reader A cannot proceed until Writer B finishes.                │
  │  Writer B cannot start until Reader A finishes.                  │
  │  HIGH CONTENTION: throughput is limited by lock wait queues.     │
  └──────────────────────────────────────────────────────────────────┘

  MVCC SYSTEM: Readers and writers proceed simultaneously

  Time →
  ┌──────────────────────────────────────────────────────────────────┐
  │  Reader A: ──── reads version 1 (old) ─────────────────────────→ │
  │  Writer B: ──── writes version 2 (new) ────────────────────────→ │
  │                                                                  │
  │  Both proceed at the SAME TIME with ZERO conflict.               │
  │  Reader A sees version 1 (existed when A started).               │
  │  Future readers (starting after B commits) see version 2.        │
  │  NO READ LOCKS NEEDED. NO WAITING.                               │
  └──────────────────────────────────────────────────────────────────┘
```

### What MVCC Still Needs Locks For

It is important to understand that MVCC does not eliminate *all* locking — it eliminates **read locks specifically**. Write operations still need to be coordinated with each other. Two transactions that both want to update the same row must still be serialized — one must wait for the other. In PostgreSQL, this is handled through the tuple's `xmax` field (discussed in the next section), which effectively acts as a per-row write lock. What MVCC removes is the need for readers to acquire any lock at all, which is the dominant operation in most read-heavy workloads.

Additionally, SELECT FOR UPDATE and SELECT FOR SHARE explicitly request row-level locks — because the application is signaling that it wants to read a row *and then write it*, and it needs the row to not change between the read and the write. These are not read locks in the MVCC sense; they are explicit application-level coordination mechanisms.

```
  WHAT MVCC LOCKS AND WHAT IT DOES NOT:

  Operation              │ Acquires Lock?  │ What kind?
  ───────────────────────┼─────────────────┼────────────────────────────
  SELECT                 │ NO              │ None! Reads a snapshot.
  SELECT FOR SHARE       │ YES             │ Row-level shared lock
  SELECT FOR UPDATE      │ YES             │ Row-level exclusive lock
  INSERT                 │ YES (internal)  │ Row write lock (xmin in tuple)
  UPDATE                 │ YES             │ Row-level exclusive lock
  DELETE                 │ YES             │ Row-level exclusive lock
  DDL (ALTER TABLE etc.) │ YES             │ Table-level lock
  ───────────────────────┼─────────────────┼────────────────────────────
  Key insight: Plain SELECT acquires ZERO locks.
  In a read-heavy system (90% reads, 10% writes), MVCC eliminates
  90% of the lock contention that a lock-based system would have.
```

## 2. Version Chains and Visibility Rules

### How PostgreSQL Stores Multiple Versions In-Place

In PostgreSQL's implementation of MVCC, multiple versions of the same row are not stored in a separate "version archive" — they are stored directly in the table's heap pages, alongside current versions. Each physical tuple (the database's term for a stored row) contains additional metadata fields that identify which transactions created it and which transaction (if any) marked it as deleted or superseded. These fields are called **system columns** and they are the machinery of MVCC visibility.

The two most important system columns are:

**`xmin`** — the transaction ID (XID) of the transaction that *inserted* this tuple (created this version). A tuple is potentially visible to a reader if the reader's transaction started after the xmin transaction committed.

**`xmax`** — the transaction ID of the transaction that *deleted or updated* this tuple. When a row is deleted, its `xmax` is set to the deleting transaction's ID. When a row is updated, the old tuple's `xmax` is set to the updating transaction's ID, and a new tuple is inserted with the new values and a new `xmin`. A tuple with `xmax = 0` (or a null-equivalent) has not been deleted or superseded — it is the current live version.

```
  TUPLE STRUCTURE IN POSTGRESQL'S HEAP

  Physical tuple format (simplified):
  ┌──────────────────────────────────────────────────────────────────────┐
  │ xmin  │ xmax  │ infomask  │ ...header... │ col1 │ col2 │ col3 │ ... │
  └──────────────────────────────────────────────────────────────────────┘
    │        │
    │        └── Transaction that deleted/updated this tuple (0 if live)
    └──────────── Transaction that created this tuple (INSERT)

  Example: accounts table row for account id=42

  Initial INSERT by transaction 100 (balance = $500):
  ┌─────────────┬─────────────┬───────────────────────────┐
  │ xmin = 100  │ xmax = 0    │ id=42, balance=$500        │  ← LIVE (xmax=0)
  └─────────────┴─────────────┴───────────────────────────┘

  UPDATE by transaction 200 (balance → $400):
  ┌─────────────┬─────────────┬───────────────────────────┐
  │ xmin = 100  │ xmax = 200  │ id=42, balance=$500        │  ← OLD (superseded)
  └─────────────┴─────────────┴───────────────────────────┘
  ┌─────────────┬─────────────┬───────────────────────────┐
  │ xmin = 200  │ xmax = 0    │ id=42, balance=$400        │  ← LIVE (current)
  └─────────────┴─────────────┴───────────────────────────┘

  Both tuples exist on disk simultaneously on the same heap page.
  The new tuple does NOT overwrite the old one.
  The old tuple is marked as superseded by setting xmax = 200.
```

### The Version Chain

When a row is updated multiple times, a chain of tuple versions forms, each pointing (through xmin/xmax relationships) to the next version in time. PostgreSQL does not maintain explicit "next" pointers between versions in the heap — instead, readers navigate version chains by checking `xmax` to understand which version was superseded and when. For rows that are updated very frequently, this chain can grow long, and PostgreSQL's heap organization ensures that all versions of a row are stored in the same table file (though not necessarily on the same page).

```
  VERSION CHAIN ACROSS MULTIPLE UPDATES

  account id=42 history:
  Txn 100: INSERT (balance=$500)
  Txn 200: UPDATE (balance=$400)
  Txn 350: UPDATE (balance=$650)
  Txn 410: UPDATE (balance=$600)

  Heap pages (all versions stored in table file):

  ┌─────────────┬─────────────┬──────────────────┐
  │ xmin = 100  │ xmax = 200  │ balance = $500    │  ← Version 1 (DEAD)
  ├─────────────┼─────────────┼──────────────────┤
  │ xmin = 200  │ xmax = 350  │ balance = $400    │  ← Version 2 (DEAD)
  ├─────────────┼─────────────┼──────────────────┤
  │ xmin = 350  │ xmax = 410  │ balance = $650    │  ← Version 3 (DEAD)
  ├─────────────┼─────────────┼──────────────────┤
  │ xmin = 410  │ xmax = 0    │ balance = $600    │  ← Version 4 (LIVE/CURRENT)
  └─────────────┴─────────────┴──────────────────┘

  A reader in transaction 300 (started between txn 200's commit and txn 350's commit):
  → Needs the version that was live when txn 300 started.
  → Txn 200 committed before 300 started → version 2 ($400) was live at that moment.
  → Version 2 has xmax=350 (txn 350), but txn 350 started AFTER txn 300.
  → For reader 300, version 2 is the correct visible version: balance = $400.

  A reader in transaction 500 (started after txn 410's commit):
  → Version 4 ($600) is live (xmax=0) and xmin=410 < 500 → sees $600. ✓
```

### Visibility Rules in Detail

The visibility rules determine, for any given reader transaction, which version of a row is the correct one to return. These rules are evaluated against the reader's **snapshot** (discussed in the next section), which records which transaction IDs were active, committed, or not yet started at the moment the reader's transaction began.

The visibility rule for a tuple can be summarized as: **a tuple (xmin, xmax) is visible to a reader at snapshot S if and only if:**
1. The xmin transaction committed before snapshot S was taken (the tuple was actually inserted before the reader started), **AND**
2. Either xmax is 0 (the tuple has not been deleted) or the xmax transaction had not yet committed at the time snapshot S was taken (the deletion/update happened after the reader started, so the reader should still see this version).

```
  VISIBILITY RULE DECISION TREE

  For each tuple encountered during a scan:

  Is xmin committed AND committed before my snapshot?
  │
  ├── NO: This tuple was created by a transaction that was
  │       either still in progress or started after me.
  │       → INVISIBLE (I should not see data from uncommitted future txns)
  │
  └── YES: The tuple was definitely created before my view of the world.
           Now check xmax:
           │
           ├── xmax = 0 (no deletion):
           │   → VISIBLE (this is the current live version for me)
           │
           └── xmax != 0:
               Is xmax committed AND committed before my snapshot?
               │
               ├── YES: This version was deleted/updated BEFORE I started.
               │        → INVISIBLE (I should see the newer version)
               │
               └── NO:  This version was deleted/updated by a transaction
                        that started after me (or not yet committed).
                        → VISIBLE (for me, the deletion hasn't "happened yet")

  CONCRETE EXAMPLE:
  Snapshot S taken when committed transactions = {1..299}
  (transactions 300+ are either future or in-progress)

  Tuple A: xmin=150 (committed), xmax=0    → VISIBLE ✓  (created before S, not deleted)
  Tuple B: xmin=150 (committed), xmax=250  → INVISIBLE ✗ (deleted before S)
  Tuple C: xmin=150 (committed), xmax=350  → VISIBLE ✓  (deletion is "in the future" for me)
  Tuple D: xmin=310 (not committed yet)    → INVISIBLE ✗ (created after S)
  Tuple E: xmin=290 (committed), xmax=295 (committed) → INVISIBLE ✗ (both before S)
```

## 3. Transaction IDs and Snapshots

### The Clock of the Database: Transaction IDs

Every transaction in PostgreSQL is assigned a unique, monotonically increasing integer called a **Transaction ID (XID)**. Transaction IDs are the "timestamps" of the MVCC system — they establish a total ordering of all transactions in the history of the database. When a transaction begins, it receives an XID that is one greater than the previous transaction's XID. When it commits or rolls back, this XID is recorded in PostgreSQL's commit log (the `pg_clog` or `pg_xact` directory), marking it as committed or aborted.

Transaction IDs serve as the foundation of the visibility system: every tuple's `xmin` and `xmax` is a transaction ID, and by looking up whether a given XID has been committed in the commit log, the database can determine the visibility of any tuple.

Read-only transactions in PostgreSQL (since version 14 via `SET TRANSACTION READ ONLY`) may receive a **virtual transaction ID (vXID)** rather than a real XID, because they do not create any new tuple versions and do not need to participate in the commit log. This conserves the limited supply of 32-bit transaction IDs.

```
  TRANSACTION ID SEQUENCE

  Database timeline:
  XID: ...  98   99   100   101   102   103   104   105  ...
             │    │     │     │     │     │     │     │
          commit roll commit abort commit running commit ...
          ok   back  ok         ok           ok

  pg_xact (commit log): records for each XID:
  ┌─────┬──────────────────┐
  │ XID │ Status           │
  ├─────┼──────────────────┤
  │  98 │ COMMITTED        │
  │  99 │ ABORTED          │
  │ 100 │ COMMITTED        │
  │ 101 │ ABORTED          │
  │ 102 │ COMMITTED        │
  │ 103 │ IN PROGRESS      │
  │ 104 │ COMMITTED        │
  └─────┴──────────────────┘

  To check visibility of a tuple with xmin=102:
  Look up XID 102 in pg_xact → COMMITTED → xmin is valid.
  The tuple was definitely created (not just attempted to be created).
```

### The Snapshot: A Reader's Consistent View of the World

When a transaction begins and executes its first query, PostgreSQL captures a **snapshot** of the database's transaction state. This snapshot records three crucial pieces of information:

- **`xmin`** — the lowest XID among all currently active (in-progress) transactions at the time of snapshot. Any transaction with XID less than this is definitely already committed or aborted.
- **`xmax`** — the next XID that would be assigned at the time of snapshot. Any transaction with XID ≥ xmax was not yet started at the time of snapshot.
- **`xip_list`** (transaction in-progress list) — the list of all transaction IDs that are currently active (started but not yet committed or aborted) at the time of snapshot. These transactions are "concurrent" with the reader — their work should not be visible.

Armed with this snapshot, the reader can determine the visibility of any tuple without any communication with other transactions and without acquiring any locks. The snapshot is a self-contained description of the state of the database at a single moment in time.

```
  SNAPSHOT STRUCTURE AND HOW IT IS USED

  At the moment Transaction R (reader) takes its snapshot:
  Active transactions: {103, 107, 109}  (started but not yet committed)
  Highest committed XID so far: 110 (but 107, 109 are still in progress)
  Next XID to be assigned: 111

  Snapshot S = {
      xmin: 103    (lowest active XID — all XIDs below this are done)
      xmax: 111    (next future XID — all XIDs ≥ this haven't started yet)
      xip:  [103, 107, 109]  (these are in-progress — treat as invisible)
  }

  VISIBILITY RULES using snapshot S:

  XID < xmin (103):  Definitely committed or aborted before snapshot.
    → Check pg_xact: if committed → VISIBLE, if aborted → INVISIBLE

  xmin ≤ XID < xmax AND XID in xip [103,107,109]:
    → This XID was IN PROGRESS when snapshot was taken
    → INVISIBLE (uncommitted work is not visible)

  xmin ≤ XID < xmax AND XID NOT in xip:
    → This XID committed BEFORE snapshot was taken
    → VISIBLE

  XID ≥ xmax (111+):
    → This XID didn't even exist when snapshot was taken
    → INVISIBLE (future transactions)

  EXAMPLE evaluation for several tuple versions:

  Tuple 1: xmin=90, xmax=0    → xmin(90) < 103, committed → VISIBLE ✓
  Tuple 2: xmin=90, xmax=105  → xmin visible; xmax(105): 103≤105<111, not in xip
                                 → xmax committed before snapshot → INVISIBLE ✗
  Tuple 3: xmin=90, xmax=107  → xmin visible; xmax(107): 103≤107<111, IN xip
                                 → deletion is "in progress" for me → VISIBLE ✓
  Tuple 4: xmin=107, xmax=0   → xmin(107) IN xip → INVISIBLE ✗ (uncommitted)
  Tuple 5: xmin=115, xmax=0   → xmin(115) ≥ xmax(111) → INVISIBLE ✗ (future)
```

### Snapshot Isolation Levels

PostgreSQL's MVCC model supports two snapshot-based isolation levels that differ in *when* the snapshot is taken:

**Read Committed** (the default isolation level) takes a new snapshot for **each statement** within the transaction. This means that if Transaction A runs two SELECT queries in sequence, the second query may see changes committed between the first and second statements. This is the least strict isolation level — it prevents dirty reads (reading uncommitted data) but allows non-repeatable reads (same query returning different results within the same transaction).

**Repeatable Read** and **Serializable** both take the snapshot **once, at the start of the first statement** of the transaction, and use that same snapshot for the entire transaction's lifetime. This guarantees that all queries within the transaction see a consistent, frozen view of the database as it existed at the transaction's start — regardless of what other transactions commit during its execution.

```
  ISOLATION LEVEL vs SNAPSHOT TIMING

  Scenario: Two transactions, one bank query

  Time  Transaction A (reader)              Transaction B (writer)
  ──────────────────────────────────────────────────────────────────────
  T1    BEGIN (READ COMMITTED)
  T2    SELECT balance FROM accounts        BEGIN
        WHERE id=42;
        → Snapshot taken NOW (T2): sees $500
        → Returns $500
  T3                                        UPDATE accounts
                                            SET balance=400 WHERE id=42;
                                            COMMIT; (XID committed)
  T4    SELECT balance FROM accounts
        WHERE id=42;  (second statement!)
        → New snapshot taken NOW (T4): sees $400 (B committed at T3)
        → Returns $400  ← DIFFERENT from first query!
        (Non-repeatable read — allowed in READ COMMITTED)

  ─────────────────────────────────────────────────────────────────────
  With REPEATABLE READ:

  T1    BEGIN (REPEATABLE READ)
  T1.5  First statement → snapshot taken ONCE for entire transaction
        Snapshot sees: B's XID not yet committed → $500 is visible
  T2    SELECT → Returns $500
  T3                                        B commits (updates to $400)
  T4    SELECT balance FROM accounts
        WHERE id=42;
        → SAME snapshot from T1.5 still used!
        → B's commit is AFTER snapshot → B's changes invisible
        → Returns $500  ← SAME as first query ✓ (Repeatable)
```

### Transaction ID Wraparound: The 32-Bit Problem

Because PostgreSQL uses 32-bit transaction IDs, the XID space is finite: approximately 4.2 billion transaction IDs before wraparound. In a busy database processing thousands of transactions per second, this can be exhausted in years or even months. When XID wraparound approaches, PostgreSQL enters an emergency state where it refuses new transactions to prevent data corruption — a catastrophic incident known as **transaction ID wraparound**.

The solution is **VACUUM** (covered in the next section), which "freezes" old tuples by replacing their `xmin` with a special "frozen" XID value (`FrozenTransactionId = 2`). A frozen tuple is always considered visible to every transaction — it is permanently committed history and never needs to be evaluated through the normal snapshot mechanism again. By freezing old tuples, VACUUM prevents the XID space from being exhausted.

```
  XID WRAPAROUND CONCEPT

  32-bit XID space: 0 to 4,294,967,295 (~4.2 billion)

  PostgreSQL wraps modulo arithmetic (treats XIDs as circular):
  After XID ~2,100,000,000 are issued, future XIDs appear
  "in the past" relative to earlier tuples. A tuple with xmin=1000
  would suddenly look like it was created "in the future" → invisible!

  ┌────────────────────────────────────────────────────────────────┐
  │  XID 1         XID 2^31 (2.1B)          XID 2^32 (4.2B)      │
  │  ─────────────────────────────────────────────────────────── │
  │  "past"         "present"                "future→past wrap"   │
  │                                                               │
  │  After wraparound: old tuples from XID 1000 appear to be      │
  │  2.1 billion transactions in the "future" → INVISIBLE!        │
  │  All rows in old tables vanish! → DATA LOSS                   │
  └────────────────────────────────────────────────────────────────┘

  PostgreSQL's warnings (check pg_database.datfrozenxid):
  SELECT datname,
         age(datfrozenxid) AS xid_age,
         2000000000 - age(datfrozenxid) AS xids_remaining
  FROM pg_database
  ORDER BY age(datfrozenxid) DESC;

  -- age() > 1,500,000,000: WARNING — VACUUM needed urgently
  -- age() > 2,000,000,000: PostgreSQL enters read-only mode!
  -- age() = 2,147,483,648: WRAPAROUND IMMINENT — system shutdown!

  Solution: VACUUM regularly. autovacuum handles this automatically.
  For very large, rarely-vacuumed tables: manual VACUUM FREEZE.
  VACUUM FREEZE marks ALL tuples in the table as frozen regardless of age.
```

## 4. Dead Tuples and VACUUM in PostgreSQL

### The Accumulation of History

Every time a row is updated or deleted in PostgreSQL, the old version of the tuple is not removed — it is left in place on the heap page, marked as dead through its `xmax` field. This is the fundamental storage cost of MVCC: maintaining historical versions for concurrent readers requires keeping those versions physically present on disk until no active transaction could possibly need to see them anymore.

A **dead tuple** is an old tuple version that is no longer visible to any currently active transaction — it has been superseded by a newer version, and all transactions that could have been reading the old version have long since completed. Dead tuples serve no purpose: they consume disk space on heap pages, they slow down sequential scans (because the database must read and evaluate each dead tuple to determine it is invisible), they make index entries point to dead locations (wasting index page space), and they contribute to index bloat. The process of cleaning up dead tuples is the job of **VACUUM**.

```
  DEAD TUPLE ACCUMULATION OVER TIME

  accounts table, id=42, at different points in time:

  After 5 updates (each update creates a dead tuple):
  Heap page for id=42 region:
  ┌──────────────────────────────────────────────────────────────────┐
  │ [xmin=100, xmax=200, bal=$500]  ← DEAD (no txn needs this)      │
  │ [xmin=200, xmax=350, bal=$400]  ← DEAD                          │
  │ [xmin=350, xmax=410, bal=$650]  ← DEAD                          │
  │ [xmin=410, xmax=488, bal=$600]  ← DEAD                          │
  │ [xmin=488, xmax=0,   bal=$720]  ← LIVE (current version)        │
  └──────────────────────────────────────────────────────────────────┘

  Problems caused by 4 dead tuples on this page:
  1. Page is 80% occupied by data that serves no purpose.
  2. A Seq Scan reads all 5 tuples, evaluates visibility, discards 4.
     ("Rows Removed by Filter" grows in EXPLAIN output)
  3. Index on id=42 has 5 entries, 4 pointing to dead tuples.
     (Index bloat: each dead tuple has a dead index entry)
  4. Fewer live tuples fit per page → more pages → larger table → slower scans.

  This waste accumulates silently. A table with 1M updates/day
  accumulates millions of dead tuples if VACUUM does not run.
```

### What VACUUM Does — Step by Step

VACUUM is the maintenance process that reclaims space from dead tuples and restores the heap to a healthy, compact state. It is crucial to understand exactly what each step of VACUUM accomplishes, because the details explain both its benefits and its limitations.

```
  VACUUM EXECUTION PHASES

  Phase 1: HEAP SCAN — Identify dead tuples
  ────────────────────────────────────────────────────────────────
  VACUUM scans each page of the table.
  For each tuple it examines xmin, xmax, and the snapshot horizon:
  - snapshot horizon = oldest XID among all currently active transactions
  - A tuple with xmax < snapshot_horizon AND xmax committed is DEAD
    (no active transaction can possibly see this old version)
  - Builds an in-memory list of dead tuple locations (TIDs)

  Phase 2: INDEX VACUUM — Remove dead index entries
  ────────────────────────────────────────────────────────────────
  For each index on the table:
  - Traverse the index
  - For each index entry pointing to a dead tuple: remove the entry
  - This reclaims space in index pages and shrinks index size
  (This phase is why VACUUM on a table with many indexes takes longer)

  Phase 3: HEAP VACUUM — Mark dead space as free
  ────────────────────────────────────────────────────────────────
  For each dead tuple identified in Phase 1:
  - Mark the tuple's storage space as FREE (available for reuse)
  - The page can now accept new tuples in the reclaimed space
  NOTE: Regular VACUUM does NOT return space to the OS!
        The file size stays the same. Space is only marked
        "available for reuse" within the existing file.
        To return space to the OS: VACUUM FULL (rewrites entire table)
        or pg_repack (zero-downtime alternative)

  Phase 4: FREEZE — Prevent XID wraparound
  ────────────────────────────────────────────────────────────────
  Tuples with xmin older than vacuum_freeze_min_age (default: 50M XIDs):
  - xmin is replaced with "FrozenTransactionId" (special value)
  - Frozen tuples are always visible — no further XID evaluation needed
  - Advances datfrozenxid in pg_database, reducing wraparound risk

  Phase 5: VISIBILITY MAP — Enable Index-Only Scans
  ────────────────────────────────────────────────────────────────
  For each page where ALL tuples are now visible to all transactions:
  - Set the "all-visible" bit in the visibility map for that page
  - Pages with this bit set can be skipped entirely by future VACUUMs
  - Pages with this bit set enable Index-Only Scans (no heap check needed)
```

### Regular VACUUM vs VACUUM FULL vs VACUUM FREEZE

There are several variants of the VACUUM command, each appropriate for different situations, and understanding the differences is critical for proper database maintenance.

```sql
  -- REGULAR VACUUM: The standard maintenance operation
  VACUUM orders;
  -- ✓ Marks dead tuples as free space (reusable within file)
  -- ✓ Removes dead index entries
  -- ✓ Updates visibility map
  -- ✓ Freezes old tuples (age > vacuum_freeze_min_age)
  -- ✓ Does NOT lock table — concurrent reads and writes are allowed!
  -- ✗ Does NOT return space to OS (file size unchanged)
  -- Use for: routine maintenance, run by autovacuum automatically

  -- VACUUM ANALYZE: Vacuum + refresh statistics in one pass
  VACUUM ANALYZE orders;
  -- Same as VACUUM but also runs ANALYZE to refresh pg_stats
  -- Use for: after bulk loads, large deletes, significant data changes

  -- VACUUM FULL: Complete table rewrite
  VACUUM FULL orders;
  -- ✓ Returns space to OS (file size shrinks)
  -- ✓ Completely rewrites table (only live tuples in new file)
  -- ✗ Requires ACCESS EXCLUSIVE LOCK — blocks ALL reads and writes!
  -- ✗ Uses 2× storage temporarily (old + new file exist simultaneously)
  -- Use for: scheduled maintenance windows after massive deletes
  -- Never use on a busy production table without a maintenance window!

  -- VACUUM FREEZE: Force-freeze all tuples
  VACUUM FREEZE orders;
  -- ✓ Freezes ALL eligible tuples regardless of age threshold
  -- ✓ Maximally advances datfrozenxid → prevents wraparound
  -- Use for: tables approaching XID wraparound danger zone
  --          Before taking a physical backup that must be long-lived

  -- Monitor dead tuple accumulation and VACUUM effectiveness:
  SELECT
      relname                                     AS table_name,
      n_live_tup                                  AS live_tuples,
      n_dead_tup                                  AS dead_tuples,
      ROUND(100.0 * n_dead_tup /
            NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
      last_vacuum,
      last_autovacuum,
      last_analyze,
      n_mod_since_analyze
  FROM pg_stat_user_tables
  ORDER BY n_dead_tup DESC;

  -- Monitor XID age (wraparound risk):
  SELECT datname,
         age(datfrozenxid)                             AS xid_age,
         2000000000 - age(datfrozenxid)                AS xids_until_danger
  FROM pg_database
  ORDER BY age(datfrozenxid) DESC;
```

### Autovacuum: The Automatic VACUUM Daemon

PostgreSQL's **autovacuum** is a background daemon that monitors all tables and automatically triggers VACUUM and ANALYZE when they accumulate enough dead tuples or stale statistics. It runs as a configurable number of worker processes (default: 3) that each handle one table at a time. The trigger thresholds for autovacuum are defined by two parameters that work together:

`autovacuum_vacuum_threshold` (default: 50) sets the minimum number of dead tuples before autovacuum triggers, regardless of table size. `autovacuum_vacuum_scale_factor` (default: 0.2, meaning 20%) defines the additional threshold as a fraction of the total row count. Autovacuum runs when: `dead_tuples > threshold + (scale_factor × total_rows)`.

The critical insight is that the default `scale_factor = 0.2` is far too generous for large tables. A table with 10 million rows must accumulate 2,000,050 dead tuples before autovacuum triggers. That is 2 million dead tuples degrading performance before any cleanup begins. For large, frequently-updated tables, the autovacuum settings must be tuned per-table.

```sql
  -- Tune autovacuum for a high-traffic table:
  ALTER TABLE orders SET (
      autovacuum_vacuum_scale_factor    = 0.01,   -- Trigger at 1% dead rows
      autovacuum_vacuum_threshold       = 100,    -- Or at least 100 dead rows
      autovacuum_analyze_scale_factor   = 0.005,  -- Re-analyze at 0.5% changes
      autovacuum_vacuum_cost_delay      = 2,      -- Less sleep between I/O bursts
      autovacuum_vacuum_cost_limit      = 400     -- More I/O work per burst
  );

  -- Verify settings:
  SELECT relname, reloptions
  FROM pg_class
  WHERE relname = 'orders';
```

## 5. MVCC in MySQL (InnoDB Undo Logs)

### A Different Architecture, The Same Principle

MySQL's InnoDB storage engine also implements MVCC, but its architecture differs fundamentally from PostgreSQL's approach. While PostgreSQL stores old tuple versions directly in the heap pages alongside current versions, InnoDB stores old versions in a dedicated area called the **undo log (undo tablespace)**. This architectural difference has significant implications for how each system handles reads, writes, and garbage collection.

In InnoDB's model, the table's clustered index (primary key index) always contains the **current, latest version** of each row. When a row is updated, InnoDB modifies the row in place in the clustered index — but before overwriting the old values, it writes the old values (and the information needed to reconstruct them) to the **undo log**. A reader that needs an older version reconstructs it by starting with the current row in the clustered index and "applying" undo log entries in reverse to roll back to the version that was current at the reader's snapshot point.

```
  MYSQL INNODB MVCC ARCHITECTURE vs POSTGRESQL

  PostgreSQL approach (versions IN the heap):
  ┌────────────────────────────────────────────────────────────────┐
  │ Heap Page:                                                     │
  │ [xmin=100,xmax=200, bal=$500]  ← Old version (dead)           │
  │ [xmin=200,xmax=0,   bal=$400]  ← Current version (live)       │
  │                                                                │
  │ All versions stored together in the table file.               │
  │ Reader finds the right version by evaluating xmin/xmax.       │
  └────────────────────────────────────────────────────────────────┘

  InnoDB approach (current in clustered index, history in undo log):
  ┌────────────────────────────────────────────────────────────────┐
  │ Clustered Index (always current):                              │
  │ [id=42, balance=$400, roll_ptr→undo]  ← CURRENT version       │
  │                    │                                           │
  │                    └──→ Undo Log:                              │
  │                         [old balance=$500, roll_ptr→older]    │
  │                              │                                 │
  │                              └──→ [old balance=$700, ...]      │
  │                                                                │
  │ Reader needing old version: starts at clustered index,        │
  │ follows roll_ptr chain through undo log to find the version   │
  │ that was current at reader's snapshot time.                   │
  └────────────────────────────────────────────────────────────────┘
```

### InnoDB's Read View: The Equivalent of PostgreSQL's Snapshot

InnoDB uses a data structure called a **Read View** that serves the same purpose as PostgreSQL's snapshot — it captures the state of concurrent transactions at the moment a read begins, enabling consistent reads without locks.

When a transaction starts its first read (in REPEATABLE READ isolation) or when each statement begins (in READ COMMITTED isolation), InnoDB creates a Read View containing:
- The list of active transaction IDs at that moment
- The lowest and highest active transaction IDs (bounding the range)

When InnoDB needs to determine which version of a row is visible to a reader, it checks the row's **DB_TRX_ID** field (the ID of the transaction that last modified this row). If the DB_TRX_ID falls within the reader's Read View as a committed transaction, the current version is visible. If not, InnoDB follows the **DB_ROLL_PTR** (rollback pointer) to the undo log and reconstructs the appropriate older version.

```
  INNODB ROW FORMAT (hidden system columns)

  Each InnoDB row contains three hidden system columns:

  ┌─────────────────────────────────────────────────────────────────┐
  │ DB_TRX_ID (6 bytes)                                            │
  │   Transaction ID of the last transaction that modified this row │
  │   Used by Read View to determine visibility                     │
  │                                                                 │
  │ DB_ROLL_PTR (7 bytes)                                           │
  │   Pointer to the undo log record for the previous version       │
  │   Used to navigate the version chain backward in time           │
  │                                                                 │
  │ DB_ROW_ID (6 bytes)                                             │
  │   Auto-generated row ID (only used if table has no PK)         │
  └─────────────────────────────────────────────────────────────────┘

  Visible version reconstruction:

  Current row in clustered index:
  [id=42, bal=$400, DB_TRX_ID=200, DB_ROLL_PTR→undo_record_A]

  Reader's Read View: {active_txns=[103, 107], lo=103, hi=210}
  Is TRX_ID 200 visible? 200 < 210 and 200 not in active list → VISIBLE
  → Returns $400.

  If reader's Read View started before transaction 200 committed:
  {active_txns=[103, 200, 207], lo=103, hi=210}
  Is TRX_ID 200 visible? 200 in active_txns → NOT VISIBLE for me
  → Follow DB_ROLL_PTR to undo_record_A:
    [old bal=$500, DB_TRX_ID=100, DB_ROLL_PTR→undo_record_B]
  Is TRX_ID 100 visible? 100 < 103 and not in active_txns → VISIBLE
  → Returns $500 (the version that was current before txn 200 ran).
```

### The Undo Log and InnoDB's Garbage Collection (Purge)

InnoDB's undo log is maintained in the **undo tablespace** — a dedicated file (or set of files) separate from the table data. As transactions modify rows, undo records accumulate in this space. When a transaction commits, its undo records are not immediately deleted — they must be retained as long as any active Read View might need them to reconstruct old row versions.

InnoDB's **purge thread** is the background process responsible for cleaning up undo log records that are no longer needed by any active Read View. It is conceptually analogous to PostgreSQL's VACUUM, but it works on the undo tablespace rather than heap pages. The purge thread periodically scans for undo records whose transaction ID is older than the oldest active Read View, and removes them.

```
  INNODB UNDO LOG PURGE

  Timeline of a row modification:

  TRX=100 INSERT:  row created, no undo needed (no previous version)
  TRX=200 UPDATE:  undo record written for old value ($500→$400)
  TRX=350 UPDATE:  undo record written for old value ($400→$650)
  TRX=410 UPDATE:  undo record written for old value ($650→$600)

  Undo log:
  ┌────────────────────────────────────────────────────────────────┐
  │ [TRX=410 undo: old_bal=$650, prev→TRX=350_undo]               │
  │ [TRX=350 undo: old_bal=$400, prev→TRX=200_undo]               │
  │ [TRX=200 undo: old_bal=$500, prev→none]                        │
  └────────────────────────────────────────────────────────────────┘

  Oldest active Read View: started at TRX=400
  → Any TRX < 400 whose undo records are no longer needed:
  → TRX=200 undo (old_bal=$500) can be purged
  → TRX=350 undo (old_bal=$400) can be purged
  → TRX=410 undo might still be needed (410 > 400, in progress for some readers)

  After purge:
  ┌────────────────────────────────────────────────────────────────┐
  │ [TRX=410 undo: old_bal=$650, prev→none]                        │
  └────────────────────────────────────────────────────────────────┘

  DANGER: Long-running read transactions prevent purge!
  A Read View open for hours means ALL undo records created since that
  transaction started CANNOT be purged. The undo tablespace grows
  without bound until the long-running transaction finishes.
  This is called "undo log bloat" or the "long-running transaction problem."
```

### The Long-Running Transaction Problem in InnoDB

The most important operational implication of InnoDB's undo log architecture is the **long-running transaction problem**. A single long-running read transaction (perhaps a reporting query that runs for an hour) creates a Read View that must be maintained for the entire duration of the transaction. As other transactions continue to modify rows, their undo records must be retained — not because the reader will ever look at them, but because the purge system cannot safely remove any undo record created after the reader's Read View was captured.

The consequence is that the undo tablespace grows continuously for the duration of the long-running transaction. In extreme cases (a backup tool that holds a transaction open for hours on a heavily-updated database), the undo tablespace can grow to hundreds of gigabytes. When the long-running transaction finally completes, the purge thread has an enormous backlog to process, consuming significant I/O and potentially affecting regular query performance for minutes or hours afterward.

```
  LONG-RUNNING TRANSACTION: UNDO LOG GROWTH

  System: 1000 updates per second to orders table
  Long-running report query: holds Read View for 2 hours

  During those 2 hours:
  Undo records created: 1000 updates/sec × 7200 sec = 7,200,000 records
  Average undo record size: ~200 bytes
  Undo tablespace growth: 7,200,000 × 200 bytes = 1.44 GB

  ALL 7.2 million undo records are blocked from purge
  while the report query runs!

  After report finishes:
  Purge thread must process 7.2 million records → spike in I/O
  Normal operations compete with purge for disk bandwidth

  ─────────────────────────────────────────────────────────────────
  DETECTING THE PROBLEM:

  -- MySQL: Check undo log size and purge lag
  SELECT name, count FROM information_schema.INNODB_METRICS
  WHERE name IN ('trx_rseg_history_len', 'purge_todo_pages');
  -- trx_rseg_history_len: number of undo log records awaiting purge
  -- High value (>100,000+): purge is falling behind → investigate

  -- Show long-running transactions:
  SELECT trx_id, trx_started, trx_isolation_level,
         TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS seconds_running,
         trx_query
  FROM information_schema.INNODB_TRX
  ORDER BY seconds_running DESC;

  ─────────────────────────────────────────────────────────────────
  PREVENTION:
  1. Avoid long-running transactions in OLTP code.
  2. Use READ COMMITTED isolation (new Read View per statement,
     shorter retention requirements) for reporting queries
     when snapshot consistency for the full duration is not needed.
  3. Use pt-online-schema-change or MySQL 8 instant DDL to avoid
     long-running DDL transactions holding Read Views.
  4. Run reporting queries against a read replica that does not
     affect the primary's undo log.
```

### InnoDB MVCC vs PostgreSQL MVCC: Key Differences

Understanding the architectural differences between InnoDB and PostgreSQL's MVCC implementations helps explain their different performance characteristics, operational trade-offs, and maintenance requirements.

```
  INNODB vs POSTGRESQL MVCC: ARCHITECTURAL COMPARISON

  ┌─────────────────────────┬────────────────────────┬─────────────────────────┐
```

## Summary: The MVCC Mental Model

MVCC is one of the most elegant ideas in database engineering — a solution that seems almost too good to be true: readers and writers operating simultaneously without blocking each other, each seeing a consistent view of the world, each proceeding at full speed. The elegance is real, but it comes with a physical cost: the cost of storing multiple versions, of navigating version chains or undo logs, of periodically cleaning up the historical accumulation through VACUUM or purge threads.

```
  MVCC CORE CONCEPTS — FINAL REFERENCE

  ┌─────────────────────────┬────────────────────────────────────────────┐
  │ Concept                 │ Key Insight                                │
  ├─────────────────────────┼────────────────────────────────────────────┤
  │ Avoids read locks       │ Readers get a snapshot of the past.        │
  │                         │ No need to lock anything — they see a      │
  │                         │ guaranteed-consistent historical view.     │
  ├─────────────────────────┼────────────────────────────────────────────┤
  │ Version chains          │ Each update creates a new version, leaving │
  │ (PostgreSQL)            │ old ones in heap (xmin/xmax metadata).     │
  │                         │ Visibility evaluated per-tuple per-reader. │
  ├─────────────────────────┼────────────────────────────────────────────┤
  │ Transaction IDs &       │ Snapshot captures {xmin, xmax, xip_list}   │
  │ Snapshots               │ at transaction start (or per-statement in  │
  │                         │ READ COMMITTED). Visibility determined by  │
  │                         │ whether xmin/xmax fall inside/outside      │
  │                         │ the snapshot's view of committed history.  │
  ├─────────────────────────┼────────────────────────────────────────────┤
  │ Dead tuples & VACUUM    │ Old versions accumulate as dead tuples.    │
  │ (PostgreSQL)            │ VACUUM reclaims space, removes dead index  │
  │                         │ entries, updates visibility map, freezes   │
  │                         │ old XIDs. Autovacuum does this continuously│
  │                         │ — tune per-table for high-traffic tables.  │
  ├─────────────────────────┼────────────────────────────────────────────┤
  │ InnoDB undo logs        │ Current version in clustered index.        │
  │ (MySQL)                 │ Old versions in undo log (separate file).  │
  │                         │ Read View navigates undo chain to find     │
  │                         │ the version appropriate for the snapshot.  │
  │                         │ Purge thread removes undo records no       │
  │                         │ longer needed. Long-running txns cause     │
  │                         │ undo log growth — avoid in production.     │
  └─────────────────────────┴────────────────────────────────────────────┘

  THE PRACTICAL RULES:
  1. In PostgreSQL: configure autovacuum aggressively for busy tables.
  2. Monitor pg_stat_user_tables for dead tuple accumulation.
  3. Monitor pg_database age() for XID wraparound risk.
  4. In MySQL: monitor trx_rseg_history_len for purge lag.
  5. In both systems: NEVER leave long-running transactions idle.
  6. Run reporting queries on read replicas to protect the primary.
  7. In PostgreSQL: idle_in_transaction_session_timeout kills zombies.
  8. Understand your isolation level: READ COMMITTED takes snapshots
     per-statement; REPEATABLE READ takes one snapshot for the whole txn.
```

The elegance of MVCC lies in this insight: rather than solving the problem of concurrent access by restricting access, it solves it by being generous with history. Every reader gets its own consistent past. Every writer builds the future without disturbing that past. The database is simultaneously a time machine and a concurrency engine — and once you understand how it maintains this illusion, you can work with it rather than against it.
