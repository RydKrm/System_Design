## 1. Introduction — From Rows to Summaries

A database table is, at its most fundamental level, a collection of individual facts. Each row in the `orders` table records one purchase. Each row in the `employees` table describes one person. Each row in the `events` table logs one thing that happened at one moment in time. This granularity is exactly what makes relational databases powerful for recording information — every fact is stored precisely and independently.

But when human beings want to understand their data, they almost never want to read individual rows. A business analyst does not want to scroll through eight million order records. A marketing team does not want to examine each user event one by one. They want *summaries* — total revenue per month, average order value per customer segment, the highest-selling product category, the minimum stock level across all warehouses. They want the individual facts collapsed into patterns, totals, and statistics that reveal what the collection of facts means as a whole.

This is what **aggregation** does. Aggregation is the process of taking multiple rows, grouping them by shared characteristics, and producing a single summary row for each group. It is the bridge between raw, granular data and the summaries and reports that drive real decisions.

The SQL machinery for aggregation has four interlocking components: `GROUP BY` (which defines the groups), the aggregate functions `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` (which compute the summary values), `HAVING` (which filters groups the way `WHERE` filters rows), and the `FILTER` clause and `DISTINCT` modifier (which give you fine-grained control over what each aggregate function sees). Together, these tools allow you to answer questions of extraordinary sophistication in a single, readable SQL statement.

## 3. GROUP BY — Collapsing Rows into Groups

---

### 3.1 How GROUP BY Works Mechanically

To understand `GROUP BY` deeply, you must understand it not as a magic keyword but as a physical operation that the database engine performs on a set of rows. When the database encounters a `GROUP BY` clause, it takes all the rows that survived the `WHERE` filter and partitions them into buckets — one bucket for each unique value (or combination of values) of the grouping columns. Every row in the table goes into exactly one bucket. Once all rows are assigned, each bucket is collapsed into a single row, and the aggregate functions are applied to all the rows within each bucket to produce the summary values for that output row.

```
Visualizing GROUP BY on order_items (grouping by category):

Individual rows BEFORE GROUP BY:
+--------+-----------+----------+------------+
|item_id | category  | quantity | unit_price |
+--------+-----------+----------+------------+
|   1    |Electronics|    2     |   150.00   |
|   2    |Clothing   |    3     |    40.00   |
|   3    |Electronics|    1     |   200.00   |
|   4    |Electronics|    1     |   150.00   |
|   5    |Books      |    5     |    25.00   |
|   6    |Clothing   |    2     |    40.00   |
|   7    |Books      |    4     |    30.00   |
|   8    |Electronics|    2     |   200.00   |
+--------+-----------+----------+------------+

PARTITIONING into buckets by category:

  Bucket "Electronics": rows 1, 3, 4, 8
  +-----------+----------+------------+
  |Electronics|    2     |   150.00   |
  |Electronics|    1     |   200.00   |
  |Electronics|    1     |   150.00   |
  |Electronics|    2     |   200.00   |
  +-----------+----------+------------+

  Bucket "Clothing": rows 2, 6
  +-----------+----------+------------+
  |Clothing   |    3     |    40.00   |
  |Clothing   |    2     |    40.00   |
  +-----------+----------+------------+

  Bucket "Books": rows 5, 7
  +-----------+----------+------------+
  |Books      |    5     |    25.00   |

  +-----------+----------+------------+

  Aggregate functions operate on ALL rows within a bucket.

+-----------+-------+---------------+---------------+

+-----------+-------+---------------+---------------+

```

This is the mental model you should hold every time you write a `GROUP BY`: you are partitioning rows into labeled buckets and then summarizing the contents of each bucket with aggregate functions.

---

### 3.2 Single-Column Grouping

The simplest and most common form of `GROUP BY` groups by a single column. Every unique value in that column becomes a group, and the aggregate functions produce one summary for each unique value.

```sql
-- How many orders exist per status?
SELECT
    status,
    COUNT(*)   AS order_count
FROM orders
GROUP BY status
ORDER BY order_count DESC;

-- Result:
-- COMPLETED | 5
-- PENDING   | 1
-- CANCELLED | 1
-- REFUNDED  | 1

-- Total revenue per category (only completed orders)
SELECT
    oi.category,
    SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
WHERE o.status = 'COMPLETED'
GROUP BY oi.category
ORDER BY total_revenue DESC;

-- How many distinct products were sold in each category?
SELECT
    category,
    COUNT(DISTINCT product_id) AS unique_products_sold
FROM order_items
GROUP BY category;
```

---

### 3.3 Multi-Column Grouping

When you list multiple columns in `GROUP BY`, the database creates a separate bucket for every unique **combination** of those column values. A row belongs to a bucket only if it matches all of the grouping column values simultaneously.

```sql
-- Order count by status AND channel (every status-channel combination)
SELECT
    status,
    channel,
    COUNT(*) AS order_count
FROM orders
GROUP BY status, channel
ORDER BY status, channel;

-- Result:
-- CANCELLED | web    | 1
-- COMPLETED | mobile | 1
-- COMPLETED | store  | 2
-- COMPLETED | web    | 2
-- PENDING   | store  | 1
-- REFUNDED  | mobile | 1

-- Notice: NOT every combination exists (e.g., no CANCELLED mobile orders).
-- Only combinations that actually appear in the data produce output rows.
```

```
Multi-column GROUP BY visualization (status × channel):

            web         mobile       store
           ------       ------       ------
COMPLETED |  2 rows  |  1 row   |  2 rows  |
CANCELLED |  1 row   |  (none)  |  (none)  |
REFUNDED  |  (none)  |  1 row   |  (none)  |
PENDING   |  (none)  |  (none)  |  1 row   |

Each non-empty cell becomes one output row.
Empty cells produce no row (INNER JOIN behavior of GROUP BY).
```

Multi-column grouping is the foundation of every cross-tabulation report. When a business asks "show me sales by month AND by region," multi-column `GROUP BY` is the answer.

### 3.4 Grouping by Expressions

You are not limited to grouping by raw column values. You can group by any expression, including date-truncation functions, mathematical expressions, and `CASE` expressions. This is what enables time-series reporting (group by month, group by week, group by quarter) without needing a pre-built calendar table.

```sql
-- Group by MONTH (time series: monthly revenue)
SELECT
    DATE_TRUNC('month', o.order_date) AS revenue_month,
    SUM(oi.quantity * oi.unit_price)  AS monthly_revenue
FROM orders      o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY DATE_TRUNC('month', o.order_date)
ORDER BY revenue_month;

-- MySQL equivalent (no DATE_TRUNC — use YEAR() and MONTH())
SELECT
    YEAR(o.order_date)  AS yr,
    MONTH(o.order_date) AS mo,
    SUM(oi.quantity * oi.unit_price) AS monthly_revenue
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY YEAR(o.order_date), MONTH(o.order_date)
ORDER BY yr, mo;

-- Group by a CASE expression (customer tier classification)
SELECT
    CASE
        WHEN c.tier = 'vip'      THEN 'Tier 1 — VIP'
        WHEN c.tier = 'premium'  THEN 'Tier 2 — Premium'
        ELSE                          'Tier 3 — Standard'
    END AS customer_tier,
    COUNT(DISTINCT o.order_id)       AS order_count,
    SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY
    CASE
        WHEN c.tier = 'vip'     THEN 'Tier 1 — VIP'
        WHEN c.tier = 'premium' THEN 'Tier 2 — Premium'
        ELSE                         'Tier 3 — Standard'
    END
ORDER BY customer_tier;
```

When grouping by a `CASE` expression, you must repeat the full expression in both the `SELECT` and the `GROUP BY` clauses. Some databases (PostgreSQL in particular) allow you to use a `SELECT` column alias in the `GROUP BY`, but this is a non-standard extension and is not universally supported.

### 3.5 The Golden Rule of GROUP BY

There is an absolute rule in SQL that governs what you are allowed to put in the `SELECT` clause of a query that uses `GROUP BY`. This rule trips up beginners and even intermediate developers repeatedly, so it deserves its own section.

**The rule: Every column in the SELECT clause that is NOT wrapped inside an aggregate function MUST appear in the GROUP BY clause.**

The reason for this rule becomes obvious when you think about what `GROUP BY` does physically. After grouping, each output row represents an entire *bucket* of original rows. For an aggregated column like `SUM(quantity)`, the database knows exactly what to put in that column — it sums all the quantity values in the bucket. But for a non-aggregated column like `order_id`, the database faces an impossible question: "which of the many order_id values from this bucket should I show?" If a "Books" bucket contains 5 rows with 5 different `order_id` values, there is no coherent single value to display. The rule prevents this ambiguity by disallowing it entirely.

```sql
-- WRONG: order_id is in SELECT but not in GROUP BY
SELECT
    category,
    order_id,           -- Which order_id would this be? The bucket has many!
    SUM(quantity)
FROM order_items
GROUP BY category;
-- Error: column "order_id" must appear in the GROUP BY clause
-- or be used in an aggregate function

-- CORRECT: every non-aggregated column is in GROUP BY
SELECT
    category,
    SUM(quantity)   AS total_quantity
FROM order_items
GROUP BY category;

-- ALSO CORRECT: if you want order_id in the output, group by it too
-- (This changes the query's meaning: one row per category+order combination)
SELECT
    category,
    order_id,
    SUM(quantity)   AS items_in_this_order_and_category
FROM order_items
GROUP BY category, order_id;
```

Primary keys are special in this regard. If you group by a table's primary key, you can include any other column from that same table in `SELECT` without aggregating it — because by grouping on the primary key, each "group" contains exactly one row, so every column value is unambiguous. Some databases (MySQL with `ONLY_FULL_GROUP_BY` disabled, SQLite) allow a relaxed version of this rule, but relying on that behavior produces unpredictable results and should be avoided.

## 4. HAVING — Filtering Groups After Aggregation

---

### 4.1 HAVING vs WHERE — The Critical Distinction

Both `WHERE` and `HAVING` are filter clauses, but they filter at completely different stages of query processing. Understanding this distinction is one of the most important conceptual breakthroughs in SQL mastery.

`WHERE` filters **individual rows** before any grouping takes place. It sees the raw, ungrouped data. The aggregate functions have not been computed yet when `WHERE` runs, which is precisely why you cannot use an aggregate function inside a `WHERE` clause — the values simply do not exist yet.

`HAVING` filters **groups** after `GROUP BY` has been applied and after all aggregate functions have been computed. It sees one summary row per group, complete with all aggregated values. This is why you can use aggregate functions inside `HAVING` — by the time `HAVING` runs, those values are fully computed and available.

```
The Logical Processing Sequence:

  Raw rows
     |
     v
  [WHERE] — filter individual rows
     |       (aggregates do NOT exist yet)
     v
  Filtered rows
     |
     v
  [GROUP BY] — partition filtered rows into buckets
     |          compute aggregate functions
     v
  One row per group (with aggregate values computed)
     |
     v
  [HAVING] — filter groups
     |        (aggregates EXIST here — use them freely)
     v
  Final groups
     |
     v
  [SELECT] → [ORDER BY] → [LIMIT] → result to client
```

```sql
-- WRONG: Cannot use aggregate in WHERE (it doesn't exist yet)
SELECT category, SUM(quantity) AS total_qty
FROM order_items
WHERE SUM(quantity) > 5         -- Error! Aggregate not allowed in WHERE
GROUP BY category;

-- CORRECT: Use HAVING to filter on the aggregate result
SELECT category, SUM(quantity) AS total_qty
FROM order_items
GROUP BY category
HAVING SUM(quantity) > 5;

-- Result: only categories where the total quantity sold exceeds 5
-- Electronics: 6 → included
-- Books: 9 → included
-- Clothing: 5 → excluded (5 is not > 5, it equals 5)
```

---

### 4.2 Combining WHERE and HAVING

`WHERE` and `HAVING` are not mutually exclusive — they are complementary. In a well-crafted aggregation query, you will often use both: `WHERE` to remove irrelevant rows before they even enter the grouping phase (making it cheaper), and `HAVING` to filter the resulting groups down to only those that meet your summary-level criteria.

This combination is also a powerful performance tool. Any filtering that can be expressed in `WHERE` rather than `HAVING` should be. A `WHERE` filter reduces the number of rows that participate in the `GROUP BY` computation — fewer rows to bucket and aggregate means faster execution. `HAVING` filters after the aggregation, so all excluded rows still had to be read, bucketed, and aggregated before being discarded.

```sql
-- WHERE pre-filters rows; HAVING post-filters groups.
-- This query asks: "Among completed orders only,
-- which product categories had more than 3 items sold
-- and an average unit price above $30?"

SELECT
    oi.category,
    COUNT(*)                         AS item_count,
    SUM(oi.quantity)                 AS total_quantity,
    ROUND(AVG(oi.unit_price), 2)     AS avg_unit_price,
    SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM order_items oi
JOIN orders      o  ON oi.order_id = o.order_id
WHERE o.status = 'COMPLETED'        -- Filter rows BEFORE grouping (fast)
GROUP BY oi.category
HAVING COUNT(*) > 3                 -- Filter groups AFTER aggregation
   AND AVG(oi.unit_price) > 30      -- Both conditions applied to group summaries
ORDER BY total_revenue DESC;
```

```
Execution flow for the combined WHERE + HAVING query:

  8 order_items rows (all data)
         |
  [JOIN with orders]
         |
  [WHERE status = 'COMPLETED'] → removes items from CANCELLED, PENDING, REFUNDED orders
         |
  ~5 rows remaining
         |
  [GROUP BY category] → 3 buckets: Electronics, Clothing, Books
         |
  Compute COUNT(*), SUM(qty), AVG(price), SUM(revenue) per bucket
         |
  [HAVING COUNT(*) > 3 AND AVG(unit_price) > 30]
         |
  Only groups satisfying BOTH conditions survive → result returned
```

## 5. Aggregate Functions — COUNT, SUM, AVG, MIN, MAX

The five standard aggregate functions are the workhorses of SQL analytics. Each operates on all the rows within a group (or on all rows of the table if there is no `GROUP BY`) and produces a single summary value.

---

### 5.1 COUNT — Counting Rows and Values

`COUNT` is the most frequently used aggregate function. It counts something within each group. However, its exact behavior depends critically on what you pass to it, and the differences matter significantly.

`COUNT(*)` counts every row in the group, regardless of whether any column values are `NULL`. It is the most common form and the one you will use when you simply want to know how many rows exist in each group.

`COUNT(column)` counts only the rows where the specified column is **not NULL**. If a column has 100 rows but 20 of them are NULL, `COUNT(column)` returns 80.

`COUNT(DISTINCT column)` counts only the unique non-NULL values in the specified column. This is explored in depth in the DISTINCT section below.

```sql
-- COUNT(*): Total orders per customer (includes all statuses)
SELECT
    customer_id,
    COUNT(*) AS total_orders
FROM orders
GROUP BY customer_id
ORDER BY total_orders DESC;
-- Result:
-- customer_id=1: 2 orders (1001 COMPLETED, 1003 CANCELLED)
-- customer_id=2: 2 orders (1002 COMPLETED, 1005 REFUNDED)
-- customer_id=3: 2 orders (1004 COMPLETED, 1006 COMPLETED)
-- customer_id=4: 2 orders (1007 COMPLETED, 1008 PENDING)

-- COUNT(column): Count orders where channel is recorded (non-NULL)
SELECT
    status,
    COUNT(*)        AS total_orders,
    COUNT(channel)  AS orders_with_channel_recorded
FROM orders
GROUP BY status;
-- If some orders have NULL channel, COUNT(channel) < COUNT(*)

-- COUNT(*) with a condition (using CASE — more on this in FILTER section)
SELECT
    customer_id,
    COUNT(*)                                              AS total_orders,
    COUNT(CASE WHEN status = 'COMPLETED' THEN 1 END)    AS completed_orders,
    COUNT(CASE WHEN status = 'CANCELLED' THEN 1 END)    AS cancelled_orders
FROM orders
GROUP BY customer_id;
```

A subtle but important point: `COUNT(*)` and `COUNT(1)` are identical in behavior and performance. Both count all rows including those with NULLs. The `COUNT(1)` form was a historical performance trick in very old databases that no longer applies to any modern RDBMS. Use `COUNT(*)` for clarity.

---

### 5.2 SUM — Totalling Numeric Values

`SUM` adds together all non-NULL values of a numeric expression within each group. It is the function behind every revenue total, inventory quantity, and financial balance you will ever compute in SQL.

```sql
-- Total revenue per category
SELECT
    category,
    SUM(quantity * unit_price) AS gross_revenue,
    SUM(quantity * cost_price) AS total_cost,
    SUM(quantity * unit_price) - SUM(quantity * cost_price) AS total_profit
FROM order_items
GROUP BY category
ORDER BY gross_revenue DESC;

-- You can also write the profit as:
-- SUM(quantity * unit_price - quantity * cost_price)
-- This is mathematically equivalent because SUM distributes over addition.
-- Both approaches give the same result.

-- SUM on a filtered set of orders (completed only)
SELECT
    YEAR(o.order_date)               AS year,
    MONTH(o.order_date)              AS month,
    SUM(oi.quantity * oi.unit_price) AS completed_revenue
FROM orders      o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY YEAR(o.order_date), MONTH(o.order_date)
ORDER BY year, month;

-- Running total using SUM (window function style — previewing what's possible)
SELECT
    order_date,
    SUM(quantity * unit_price) OVER (ORDER BY order_date) AS running_total
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id;
-- (Window functions are a separate topic, but SUM is foundational to them)
```

An important edge case: `SUM` of an empty set (a group with no rows, or a group where all values are NULL) returns `NULL`, not zero. When you need zero instead of NULL, wrap `SUM` in `COALESCE`:

```sql
-- Safe SUM that returns 0 instead of NULL for empty groups
SELECT
    category,
    COALESCE(SUM(quantity * unit_price), 0) AS revenue_or_zero
FROM order_items
GROUP BY category;
```

---

### 5.3 AVG — Computing the Mean

`AVG` computes the arithmetic mean of all non-NULL values within each group. It is equivalent to `SUM(column) / COUNT(column)` (where `COUNT(column)` counts non-NULLs). This distinction — that `AVG` ignores NULL rows rather than treating them as zero — is the source of many subtle, hard-to-find bugs.

```sql
-- Average order value per channel
SELECT
    o.channel,
    ROUND(AVG(oi.quantity * oi.unit_price), 2) AS avg_item_value,
    COUNT(DISTINCT o.order_id)                  AS order_count
FROM orders      o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY o.channel
ORDER BY avg_item_value DESC;

-- Average items per order (different from average item value)
-- This uses a subquery to first compute items-per-order, then averages those
SELECT ROUND(AVG(items_per_order), 2) AS avg_items_per_order
FROM (
    SELECT order_id, COUNT(*) AS items_per_order
    FROM order_items
    GROUP BY order_id
) AS order_summary;
```

The NULL-ignoring behavior of `AVG` can produce misleading results when NULL represents "zero" in your business context:

```sql
-- Scenario: some items have NULL cost_price (cost unknown, not zero)
-- AVG(cost_price) silently ignores NULL rows

SELECT category, AVG(cost_price) AS avg_cost
FROM order_items
GROUP BY category;
-- If 3 of 10 items have NULL cost_price, AVG uses only the 7 non-NULL values.
-- This may overstate or understate the true average depending on which items have NULLs.

-- Explicit: treat NULL cost as 0 (may or may not be correct for your business)
SELECT category, AVG(COALESCE(cost_price, 0)) AS avg_cost_treating_null_as_zero
FROM order_items
GROUP BY category;

-- Explicit: document the count of nulls alongside the average
SELECT
    category,
    AVG(cost_price)                              AS avg_cost_excl_null,
    COUNT(cost_price)                            AS items_with_known_cost,
    COUNT(*) - COUNT(cost_price)                 AS items_with_unknown_cost
FROM order_items
GROUP BY category;
```

---

### 5.4 MIN and MAX — Finding Extremes

`MIN` and `MAX` find the smallest and largest values within each group respectively. They work not just on numbers but on any orderable data type: dates, strings (alphabetically), times, and even UUIDs in some databases. Like all aggregate functions, they ignore `NULL` values.

```sql
-- Earliest and latest order per customer
SELECT
    customer_id,
    MIN(order_date) AS first_order_date,
    MAX(order_date) AS last_order_date,
    MAX(order_date) - MIN(order_date) AS customer_lifetime_days,
    COUNT(*)        AS total_orders
FROM orders
GROUP BY customer_id
ORDER BY first_order_date;

-- Price range per category
SELECT
    category,
    MIN(unit_price) AS cheapest_item,
    MAX(unit_price) AS most_expensive_item,
    MAX(unit_price) - MIN(unit_price) AS price_range
FROM order_items
GROUP BY category;

-- Alphabetically first and last customer name per tier
SELECT
    c.tier,
    MIN(c.name) AS alphabetically_first,
    MAX(c.name) AS alphabetically_last
FROM customers c
GROUP BY c.tier;

-- Most recent order status per customer
-- (MIN/MAX with CASE: find the latest order_date among completed orders)
SELECT
    customer_id,
    MAX(CASE WHEN status = 'COMPLETED' THEN order_date END) AS last_completed_date
FROM orders
GROUP BY customer_id;
```

`MIN` and `MAX` are also extremely useful for finding the "record row" within each group — for example, identifying the highest-revenue order in each category. However, to retrieve all columns of that record row (not just the extreme value), you need a different technique: a self-join or a window function.

```sql
-- Find the order_id of the highest-revenue item in each category
-- (Using a subquery to match the MAX back to the row)
SELECT oi.category, oi.order_id, oi.unit_price
FROM order_items oi
WHERE oi.unit_price = (
    SELECT MAX(unit_price)
    FROM order_items
    WHERE category = oi.category  -- correlated subquery
);
```

---

### 5.5 How NULL Behaves Inside Aggregate Functions

Because NULL handling is the source of so much subtle incorrect behavior in aggregation queries, it deserves a consolidated, explicit treatment. The rule is consistent across all five functions: **all standard aggregate functions ignore NULL values entirely**.

```
NULL Behavior in Aggregate Functions — Concrete Example:

Column values in a group: [100, NULL, 200, NULL, 150]

COUNT(*):         5   (counts all rows including those with NULL)
COUNT(column):    3   (counts only non-NULL values: 100, 200, 150)
COUNT(DISTINCT):  3   (counts unique non-NULL values: 100, 200, 150)
SUM(column):    450   (100 + 200 + 150; NULLs ignored, not treated as 0)
AVG(column):    150   (450 / 3; denominator is COUNT of non-NULLs = 3, not 5)
MIN(column):    100   (minimum of non-NULL values)
MAX(column):    200   (maximum of non-NULL values)

If ALL values in the group are NULL:
COUNT(*):         2   (still counts the rows)
COUNT(column):    0   (no non-NULL values)
SUM(column):   NULL   (not 0 — NULL means "unknown total")
AVG(column):   NULL
MIN(column):   NULL
MAX(column):   NULL
```

The `AVG` behavior is the most commonly misunderstood. `AVG([100, NULL, 200])` returns `150` (the average of 100 and 200), not `100` (which is what you would get if NULL were treated as 0 and the denominator were 3). Whether ignoring NULLs is the correct behavior depends entirely on the business semantics of what NULL means in your specific column.

## 6. FILTER — Conditional Aggregation

One of the most powerful advanced aggregation techniques is **conditional aggregation**: computing multiple different aggregate values from the same set of rows in a single query, where each aggregate is restricted to a different subset of rows. This eliminates the need to run multiple separate queries and enables the construction of pivot-table-style reports directly in SQL.

---

### 6.1 The FILTER Clause (SQL Standard)

The `FILTER (WHERE condition)` clause is the SQL standard way to attach a row-level filter directly to a specific aggregate function. It tells the database: "When computing this particular aggregate, only include rows that satisfy this condition." Rows that do not satisfy the condition are excluded from that specific aggregate — but they may still be counted or summed by other aggregates in the same `SELECT` clause.

The `FILTER` clause is supported in PostgreSQL and SQLite. It is the cleanest and most readable way to express conditional aggregation.

```sql
-- Count orders by status, all in one row per customer
SELECT
    customer_id,
    COUNT(*)                                     AS total_orders,
    COUNT(*) FILTER (WHERE status = 'COMPLETED') AS completed,
    COUNT(*) FILTER (WHERE status = 'CANCELLED') AS cancelled,
    COUNT(*) FILTER (WHERE status = 'REFUNDED')  AS refunded,
    COUNT(*) FILTER (WHERE status = 'PENDING')   AS pending
FROM orders
GROUP BY customer_id
ORDER BY customer_id;

-- Result (for our sample data):
-- cust_id | total | completed | cancelled | refunded | pending
--    1    |   2   |     1     |     1     |    0     |    0
--    2    |   2   |     1     |     0     |    1     |    0
--    3    |   2   |     2     |     0     |    0     |    0
--    4    |   2   |     1     |     0     |    0     |    1

-- Revenue filtered by channel
SELECT
    DATE_TRUNC('month', o.order_date)                         AS month,
    SUM(oi.quantity * oi.unit_price)                          AS total_revenue,
    SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.channel = 'web')                      AS web_revenue,
    SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.channel = 'mobile')                   AS mobile_revenue,
    SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.channel = 'store')                    AS store_revenue
FROM orders      o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY DATE_TRUNC('month', o.order_date)
ORDER BY month;
```

The `FILTER` clause is elegant because it keeps the conditional logic attached to the specific aggregate it modifies, making the query's intent immediately clear to anyone reading it.

---

### 6.2 Conditional Aggregation with CASE

For databases that do not support the `FILTER` clause (MySQL, SQL Server, Oracle), the equivalent technique uses `CASE` expressions inside the aggregate function. The `CASE` expression returns the value when the condition is met, and `NULL` otherwise. Since all aggregate functions ignore `NULL`, the effect is identical: only rows satisfying the condition contribute to the aggregate.

```sql
-- MySQL / SQL Server equivalent of FILTER (WHERE ...):
SELECT
    customer_id,
    COUNT(*)                                              AS total_orders,
    COUNT(CASE WHEN status = 'COMPLETED' THEN 1 END)    AS completed,
    COUNT(CASE WHEN status = 'CANCELLED' THEN 1 END)    AS cancelled,
    COUNT(CASE WHEN status = 'REFUNDED'  THEN 1 END)    AS refunded,
    COUNT(CASE WHEN status = 'PENDING'   THEN 1 END)    AS pending
FROM orders
GROUP BY customer_id
ORDER BY customer_id;

-- Summing only when a condition is met:
SELECT
    oi.category,
    SUM(oi.quantity * oi.unit_price)                           AS total_revenue,
    SUM(CASE WHEN o.channel = 'web'    THEN oi.quantity * oi.unit_price END) AS web_rev,
    SUM(CASE WHEN o.channel = 'mobile' THEN oi.quantity * oi.unit_price END) AS mobile_rev,
    SUM(CASE WHEN o.channel = 'store'  THEN oi.quantity * oi.unit_price END) AS store_rev
FROM orders      o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY oi.category;
```

Notice how the `CASE` expression returns `NULL` (not `ELSE 0`) when the condition is not met. This is intentional and crucial. If you wrote `CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END` inside `COUNT(...)`, you would count every row (including non-completed ones), because `COUNT` counts non-NULLs and zero is not NULL. By letting it return `NULL`, the aggregate function naturally ignores non-qualifying rows.

---

### 6.3 Building Pivot Tables with Conditional Aggregation

The combination of `GROUP BY` and conditional aggregation produces **pivot tables** — a format where rows become columns, making cross-tabular analysis readable. This is one of the most practically valuable SQL patterns in analytics.

```sql
-- PIVOT: Revenue by category per month (each category becomes a column)
SELECT
    DATE_TRUNC('month', o.order_date)                        AS month,
    SUM(CASE WHEN oi.category = 'Electronics'
             THEN oi.quantity * oi.unit_price END)           AS electronics_rev,
    SUM(CASE WHEN oi.category = 'Clothing'
             THEN oi.quantity * oi.unit_price END)           AS clothing_rev,
    SUM(CASE WHEN oi.category = 'Books'
             THEN oi.quantity * oi.unit_price END)           AS books_rev,
    SUM(oi.quantity * oi.unit_price)                         AS total_rev
FROM orders      o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'COMPLETED'
GROUP BY DATE_TRUNC('month', o.order_date)
ORDER BY month;
```

The result would look like this:

```
+------------+----------------+-------------+-----------+-----------+
| month      | electronics_rev| clothing_rev| books_rev | total_rev |
+------------+----------------+-------------+-----------+-----------+
| 2024-01-01 |    500.00      |   120.00    |   NULL    |  620.00   |
| 2024-02-01 |    150.00      |    NULL     |  125.00   |  275.00   |
| 2024-03-01 |    NULL        |    80.00    |  120.00   |  200.00   |
+------------+----------------+-------------+-----------+-----------+
```

The `NULL` values appear where no sales occurred in that category/month combination. Wrap them in `COALESCE(..., 0)` if you prefer zeros:

```sql
COALESCE(SUM(CASE WHEN oi.category = 'Electronics' THEN oi.quantity * oi.unit_price END), 0)
AS electronics_rev
```

This pivot pattern is so common in business reporting that SQL Server provides a dedicated `PIVOT` operator for it, and PostgreSQL provides the `crosstab()` function from the `tablefunc` extension. But the manual `CASE`-based approach works in every SQL database and gives you the most control over the output format.

## 7. DISTINCT Inside Aggregates

The `DISTINCT` keyword, when placed inside an aggregate function, instructs the function to first deduplicate the values it sees before computing the aggregate. The function then operates only on the unique values within each group, rather than all values. This is different from `SELECT DISTINCT`, which deduplicates entire output rows. `DISTINCT` inside an aggregate deduplicates the input to that specific function.

---

### 7.1 COUNT(DISTINCT column)

`COUNT(DISTINCT column)` is by far the most common use of `DISTINCT` inside an aggregate function. It answers questions like "how many unique customers placed an order?" or "how many distinct products were sold in this category?" — questions about cardinality rather than simple row counts.

```sql
-- How many distinct customers placed a COMPLETED order?
SELECT COUNT(DISTINCT customer_id) AS unique_customers
FROM orders
WHERE status = 'COMPLETED';
-- Answer: 4 (customers 1, 2, 3, 4 each have at least one completed order)
-- COUNT(*) would give 5 (the total number of COMPLETED order rows)

-- Distinct customers per channel
SELECT
    channel,
    COUNT(*)                       AS total_orders,
    COUNT(DISTINCT customer_id)    AS unique_customers,
    -- The ratio tells you customer loyalty per channel:
    ROUND(COUNT(*) * 1.0 / COUNT(DISTINCT customer_id), 2) AS orders_per_customer
FROM orders
GROUP BY channel
ORDER BY unique_customers DESC;

-- Distinct products sold per category (not just total item rows)
SELECT
    category,
    COUNT(*)                       AS total_item_records,
    COUNT(DISTINCT product_id)     AS unique_products_sold
FROM order_items
GROUP BY category;
-- If Electronics had 4 item records but only products 501 and 503 were sold:
-- total_item_records = 4, unique_products_sold = 2
```

The conceptual difference between `COUNT(*)`, `COUNT(column)`, and `COUNT(DISTINCT column)` is worth crystallizing with a concrete example:

```
Example group: Electronics order_items
Rows in group:
  (item_id=1, product_id=501, quantity=2)
  (item_id=3, product_id=503, quantity=1)
  (item_id=4, product_id=501, quantity=1)  ← product 501 appears again
  (item_id=8, product_id=503, quantity=2)  ← product 503 appears again

COUNT(*):                  4   (four rows total)
COUNT(product_id):         4   (four non-NULL product_id values)
COUNT(DISTINCT product_id):2   (only 501 and 503 — two unique products)
SUM(quantity):             6   (2+1+1+2)
AVG(quantity):           1.5   (6/4)
```

---

### 7.2 SUM(DISTINCT) and AVG(DISTINCT)

While less common than `COUNT(DISTINCT)`, you can also apply `DISTINCT` to `SUM` and `AVG`. `SUM(DISTINCT column)` adds up only the unique values in the column within each group, ignoring any duplicate values. `AVG(DISTINCT column)` computes the mean of unique values.

These are mathematically correct operations, but their use cases are quite narrow. They are appropriate when your data has a specific kind of structural redundancy — for example, if you have a join that causes the same monetary amount to appear in multiple rows, and you want to sum each unique amount only once.

```sql
-- SUM(DISTINCT unit_price): sum of unique price points per category
-- (Useful for: "what is the total of all distinct prices we offer in this category?")
SELECT
    category,
    SUM(unit_price)            AS sum_all_prices,      -- counts every row
    SUM(DISTINCT unit_price)   AS sum_unique_prices     -- counts each price once
FROM order_items
GROUP BY category;

-- In Electronics: unit_prices = [150, 200, 150, 200]
-- SUM(unit_price):          150+200+150+200 = 700
-- SUM(DISTINCT unit_price): 150+200         = 350 (each unique price once)
```

Most of the time, when you find yourself reaching for `SUM(DISTINCT)`, it is a signal to re-examine your query's join structure. A `SUM(DISTINCT ...)` is often a workaround for a join that is producing duplicate rows, and fixing the root cause (the join) is usually the better solution.

---

### 7.3 Performance Implications of DISTINCT in Aggregates

`DISTINCT` inside an aggregate function is not free. The database must deduplicate the values before computing the aggregate, which requires either sorting or hashing the input values within each group. For `COUNT(DISTINCT column)` on a large dataset, this additional deduplication step can make the query significantly slower than a plain `COUNT(*)`.

```
Performance cost comparison (on a 10M row table):

COUNT(*)              → Read rows, count them → O(n) very fast
COUNT(column)         → Read rows, skip NULLs, count → O(n) fast
COUNT(DISTINCT column)→ Read rows, deduplicate, count unique
                        → O(n log n) or O(n) + hash table memory
                        → Potentially much slower on high-cardinality columns

Practical example:
  COUNT(*) on 10M rows         → 0.3 seconds
  COUNT(DISTINCT customer_id)  → 2.1 seconds (customer_id is high cardinality)
  COUNT(DISTINCT status)       → 0.4 seconds (status has only 4 values — low cardinality)
```

When you need `COUNT(DISTINCT ...)` on very large tables and performance is critical, consider pre-computing distinct counts in a CTE or using approximate counting functions like PostgreSQL's `COUNT(DISTINCT ...)` with HyperLogLog estimation (`pg_hll` extension), or `APPROX_COUNT_DISTINCT()` in Redshift and BigQuery.

```sql
-- CTE approach: pre-aggregate, then count distinct efficiently
WITH customer_order_summary AS (
    SELECT
        order_date,
        customer_id,
        COUNT(*) AS orders_that_day
    FROM orders
    GROUP BY order_date, customer_id
)
SELECT
    order_date,
    COUNT(*) AS unique_customers_that_day,  -- COUNT(*) on pre-deduplicated CTE
    SUM(orders_that_day) AS total_orders
FROM customer_order_summary
GROUP BY order_date
ORDER BY order_date;
```

## 8. Putting It All Together

Let us now write a comprehensive aggregation query that uses every concept from this chapter simultaneously: multi-column `GROUP BY`, `WHERE` pre-filtering, `HAVING` post-filtering, all five aggregate functions, the `FILTER` clause (with CASE fallback), `COUNT(DISTINCT)`, and expression grouping.

```sql
-- Comprehensive E-commerce Category Analytics Report
--
-- For each product category, in each calendar month, show:
--   - Total and unique customers
--   - Order volume by status (completed vs cancelled/refunded)
--   - Revenue, cost, and profit (completed orders only)
--   - Price range
--   - Revenue contribution: web vs mobile vs store channel
--
-- Restricts to orders placed in 2024, excludes PENDING orders.

SELECT
    DATE_TRUNC('month', o.order_date)                  AS month,
    oi.category,

    -- Volume metrics
    COUNT(DISTINCT o.order_id)                         AS total_orders,
    COUNT(DISTINCT o.customer_id)                      AS unique_customers,

    -- Status breakdown (conditional aggregation via CASE)
    COUNT(DISTINCT CASE WHEN o.status = 'COMPLETED' THEN o.order_id END)
                                                       AS completed_orders,
    COUNT(DISTINCT CASE WHEN o.status IN ('CANCELLED','REFUNDED')
                        THEN o.order_id END)           AS failed_orders,

    -- Financial metrics (completed orders only, via FILTER)
    -- PostgreSQL: use FILTER clause
    SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.status = 'COMPLETED')          AS gross_revenue,
    SUM(oi.quantity * oi.cost_price)
        FILTER (WHERE o.status = 'COMPLETED')          AS total_cost,
    SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.status = 'COMPLETED')
    - SUM(oi.quantity * oi.cost_price)
        FILTER (WHERE o.status = 'COMPLETED')          AS gross_profit,

    -- Price range
    MIN(oi.unit_price)                                 AS min_price,
    MAX(oi.unit_price)                                 AS max_price,
    ROUND(AVG(oi.unit_price), 2)                       AS avg_price,

    -- Channel breakdown (completed revenue only)
    COALESCE(SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.status = 'COMPLETED'
                  AND o.channel = 'web'), 0)           AS web_revenue,
    COALESCE(SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.status = 'COMPLETED'
                  AND o.channel = 'mobile'), 0)        AS mobile_revenue,
    COALESCE(SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.status = 'COMPLETED'
                  AND o.channel = 'store'), 0)         AS store_revenue

FROM orders      o
JOIN order_items oi ON o.order_id = oi.order_id

WHERE o.status <> 'PENDING'                -- Exclude pending (not yet resolved)
  AND o.order_date >= '2024-01-01'         -- 2024 data only
  AND o.order_date <  '2025-01-01'

GROUP BY
    DATE_TRUNC('month', o.order_date),
    oi.category

HAVING
    COUNT(DISTINCT o.order_id) >= 2        -- Only show category-months with 2+ orders
    AND SUM(oi.quantity * oi.unit_price)
        FILTER (WHERE o.status = 'COMPLETED') > 0  -- At least some completed revenue

ORDER BY
    month ASC,
    gross_revenue DESC NULLS LAST;
```

This single query delivers a complete analytics report that would otherwise require multiple separate queries and post-processing in application code.

## 9. Summary

Aggregation is the mechanism by which SQL transforms from a tool for retrieving facts into a tool for discovering meaning. The individual functions and clauses each serve a distinct, well-defined purpose, and understanding how they interlock is what makes you capable of answering any summary-level business question with a single, confident SQL query.

`GROUP BY` is the partitioning engine. It takes a sea of individual rows and organizes them into labeled buckets, one bucket for each unique combination of grouping column values. Every non-aggregated column in the `SELECT` clause must appear in the `GROUP BY` clause — this is not a limitation but a reflection of the mathematical reality that a bucket can only have one value for a grouping dimension.

The five aggregate functions — `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` — are the lenses through which each bucket is collapsed into a single summary value. They all share the same fundamental behavior: they ignore `NULL` values. This NULL-ignoring behavior is not a quirk but a design principle, and understanding it prevents an entire class of subtle analytical errors.

`WHERE` and `HAVING` are both filter clauses, but they operate at different stages. `WHERE` filters individual rows before grouping — it reduces the population that enters the grouping phase and is therefore more efficient. `HAVING` filters groups after aggregation — it is the only place where aggregate function results can be used as filter conditions.

The `FILTER` clause and its cross-platform equivalent (the `CASE`-inside-aggregate pattern) unlock **conditional aggregation** — the ability to compute multiple different aggregates from the same row set in a single query, with each aggregate restricted to a different subset. This technique is the foundation of pivot tables and dashboard-style summary reports.

Finally, `DISTINCT` inside aggregate functions addresses the cardinality dimension of aggregation — counting or summing only unique values rather than all values. `COUNT(DISTINCT column)` is one of the most commonly needed analytical operations in any data-rich system, and understanding its performance characteristics helps you use it wisely on large datasets.

Together, these tools constitute the complete vocabulary of SQL aggregation, sufficient to answer virtually any summary question that a business, application, or analyst could pose.
