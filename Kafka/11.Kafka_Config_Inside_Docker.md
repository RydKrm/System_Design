# Configuring Kafka in Docker Compose for Large-Scale Projects

_A senior engineer's walkthrough for someone who just joined the team._

---
## Before We Write a Single Line

The most common mistake engineers make when they first set up Kafka in Docker Compose is treating it like any other service — just pull an image, expose a port, and move on. That approach will work for five minutes on your laptop, and then the moment your Go service tries to produce a message, or the moment you try to run two brokers instead of one, or the moment you bring the stack up on a different machine, everything will break in strange and confusing ways.

Kafka is not like a database or a cache. It is a distributed log system with its own internal concept of networking, cluster membership, leader election, and replication. When you run it inside Docker Compose, you are essentially running a distributed system inside a network abstraction layer on top of another network abstraction layer. That creates a specific set of problems that you must understand before you can configure it correctly.

So let us slow down and build this understanding properly, the same way I would explain it to you on your first week on the team. We will start from how Kafka's networking actually works, then we will understand what ZooKeeper and KRaft mean, then we will walk through a production-grade Docker Compose file line by line, and finally we will look at what you need to change to scale from one broker to three.

---
## How Kafka's Networking Works — The Most Confusing Part

Before you can understand a single line of Kafka configuration, you need to understand one concept that trips up almost everyone: **Kafka has two separate networking concerns, and you must configure them separately.**

Think about it this way. When a Kafka broker starts up, it needs to do two things. First, it needs to tell the cluster "I am here, my address is X, please connect to me." Second, when a client — your Go producer or consumer — connects to the broker and says "I want to produce to topic orders," the broker needs to tell the client the addresses of all the brokers in the cluster so the client can connect to whichever broker is the leader for that partition.

That second step — the broker advertising its own address back to clients — is where everything goes wrong in Docker.

When your Go service runs inside a Docker Compose network, it can reach the Kafka broker at `kafka:9092` because Docker's internal DNS resolves that name. But when your Go service connects to Kafka and the broker advertises its own address, if that advertised address is `localhost:9092` or the internal Docker hostname, your client will try to reconnect to that address and fail — because `localhost` inside your Go container means your Go container itself, not the Kafka container.

To solve this, Kafka has the concept of **listeners** and **advertised listeners**, and you must configure both for every environment your Kafka will be accessed from.

A `listener` is the address Kafka actually binds to and listens on. An `advertised listener` is the address Kafka tells clients to use when redirecting them. You can have multiple listeners on different network interfaces, each with a different advertised address, and Kafka will pick the right one based on how the client initially connected.

The way this plays out in Docker Compose is that you define two listeners: one for internal Docker network traffic (your Go services talking to Kafka), and one for external traffic (your local machine, your integration tests running outside Docker, a UI tool like Offset Explorer). Each listener gets a different port and a different advertised address.

This is not optional. If you do not configure this correctly, you will spend hours debugging connection errors that look like network problems but are actually address advertisement problems.

## ZooKeeper vs KRaft — Which One Should You Use?

If you look at older Kafka Docker Compose examples online, you will see a second container called ZooKeeper sitting next to Kafka. If you look at newer examples, there is no ZooKeeper at all. This is confusing, so let me explain what is happening.

Historically, Kafka used a separate system called ZooKeeper to manage cluster metadata — which brokers are alive, which broker is the controller, what topics exist, where partitions live. ZooKeeper is a distributed coordination service that was not built specifically for Kafka; it was a general-purpose tool that Kafka borrowed. The problem is that ZooKeeper adds operational complexity. You now have two systems to manage, two sets of logs to look at when things break, two health checks to monitor, and two failure modes to understand.

Starting with Kafka 2.8 (released 2021) and reaching production readiness in Kafka 3.3 (released 2022), Kafka introduced **KRaft mode** — Kafka Raft Metadata. In KRaft mode, Kafka manages its own cluster metadata internally using the Raft consensus algorithm. No ZooKeeper is needed. One or more Kafka brokers can also act as controllers, handling all the metadata that ZooKeeper used to handle.

As of Kafka 4.0 (released 2025), **ZooKeeper mode has been completely removed**. If you are starting a new project today, you must use KRaft. You should not start a new project with ZooKeeper even if you are on an older Kafka version — there is no reason to build on a foundation that is being removed.

For Docker Compose specifically, KRaft is also simpler because you do not need to run and coordinate a separate ZooKeeper container. One fewer moving part is always better.

The guide below uses **KRaft mode exclusively**. If you are maintaining a legacy system that still uses ZooKeeper, I will show that configuration at the end as a reference, but you should plan your migration to KRaft.

## Understanding the Docker Compose File Structure

Docker Compose files have a specific structure. At the top level you have a few sections: `services` (what containers to run), `networks` (how they talk to each other), and `volumes` (where persistent data lives). For a Kafka setup you will use all three.

The version of the Compose file format used to be declared at the top with a `version: "3.8"` line, but modern Docker Compose (v2 and above) ignores this line. You can include it for backward compatibility documentation but it does nothing functional.

One more thing before we look at the actual configuration: the choice of Docker image. For KRaft mode, you have two main options. The first is `apache/kafka` — the official Apache Kafka image, first published in 2023. The second is `confluentinc/cp-kafka` — Confluent's enterprise image that includes extra tooling and has been available for much longer. In this guide we will use `apache/kafka:3.9.0` because it is the official image and has no commercial licensing concerns. The configuration properties are identical between the two images; only the environment variable naming convention differs slightly for Confluent's image, which we will note where relevant.

## The Single-Broker Development Configuration — Every Line Explained

Let us start with a single-broker setup suitable for local development and then expand it to three brokers for production-like environments. Understanding the single-broker case deeply will make the multi-broker case obvious.

```yaml
services:

  kafka:
    image: apache/kafka:3.9.0
    container_name: kafka
    restart: unless-stopped
```

`image: apache/kafka:3.9.0` pulls the official Apache Kafka image at version 3.9.0. Always pin to a specific version. If you use `latest`, your team members on different machines might pull different versions and you will have very hard-to-debug compatibility issues.

`container_name: kafka` gives this container a fixed name. Without this, Docker Compose generates a name like `myproject-kafka-1`. A fixed name means the DNS name inside the Docker network is always `kafka`, which you can hardcode in your Go service's environment variables. If you ever need to run multiple independent Compose stacks on the same machine, you will need unique container names, but for a single project this is fine.

`restart: unless-stopped` means Docker will automatically restart this container if it crashes — except if you explicitly stop it with `docker compose stop` or `docker compose down`. For development this is convenient. For production you will manage restarts at the orchestration layer (Kubernetes, ECS), not at the Docker level, but in a Docker Compose production setup this is a sensible default.

```yaml
    environment:
      # --- Node identity ---
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
```

`KAFKA_NODE_ID: 1` assigns a unique integer ID to this Kafka node. In KRaft mode, every node in the cluster — whether it acts as a broker, a controller, or both — must have a unique numeric ID. In a single-node setup this is always 1. In a multi-broker setup you assign sequential IDs: 1, 2, 3.

`KAFKA_PROCESS_ROLES: broker,controller` is the KRaft-specific setting that replaces the need for ZooKeeper. It tells this node to act as both a broker (accepting producer and consumer connections, storing messages) and a controller (managing cluster metadata, handling leader election, tracking topic configurations). In a single-node development setup, one node must do both jobs. In a large production cluster, you would separate these — dedicated controller nodes that do not handle client traffic, and dedicated broker nodes that do not participate in metadata decisions. We will see this separation in the three-broker configuration.

`KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093` tells every node in the cluster who the controller nodes are and how to reach them. The format is `nodeId@hostname:port,nodeId@hostname:port,...`. Here we are saying: node 1 is a controller, and it can be reached at `kafka:9093`. The port 9093 is conventionally used for controller-to-controller communication in KRaft mode. This must list all nodes that have the `controller` role. In a three-controller setup it would be `1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093`.

```yaml
      # --- Listeners ---
      KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093,EXTERNAL://0.0.0.0:9094
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092,EXTERNAL://localhost:9094
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT,EXTERNAL:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT
```

These five settings together solve the networking problem we discussed at the beginning. Let us go through each one carefully.

`KAFKA_LISTENERS` defines the actual network addresses Kafka binds to — the sockets it opens and waits for connections on. `0.0.0.0` means "listen on all available network interfaces." We have three listeners here. `PLAINTEXT://0.0.0.0:9092` is for internal Docker network traffic from your Go services. `CONTROLLER://0.0.0.0:9093` is for KRaft controller-to-controller communication — this is how brokers and controllers in the cluster talk to each other about metadata. `EXTERNAL://0.0.0.0:9094` is for connections from outside the Docker network — your local machine, your test suite running on the host, tools like Offset Explorer or kcat.

`KAFKA_ADVERTISED_LISTENERS` is what Kafka tells clients when it responds to a connection. Notice there are only two entries here, not three — we do not advertise the `CONTROLLER` listener because clients never connect to it. `PLAINTEXT://kafka:9092` is advertised to clients that connected on the PLAINTEXT listener — that is, internal Docker services. When your Go consumer connects to `kafka:9092`, Kafka will respond with `kafka:9092` as the broker address, and since your Go service is inside Docker it can resolve that name. `EXTERNAL://localhost:9094` is advertised to clients that connected on the EXTERNAL listener — that is, tools running on your host machine. When Offset Explorer on your laptop connects to `localhost:9094`, Kafka responds with `localhost:9094`, which your laptop can also resolve. This is the key insight: each listener advertises a different address appropriate for whoever connected on that listener.

`KAFKA_LISTENER_SECURITY_PROTOCOL_MAP` maps each listener name to its security protocol. `PLAINTEXT` means no encryption, no authentication. In production you would use `SSL` or `SASL_SSL` here. For local development, `PLAINTEXT` is fine. Every listener name you defined in `KAFKA_LISTENERS` must have an entry here.

`KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER` tells Kafka which listener name is used for controller communication. This is how KRaft knows that the `CONTROLLER` listener is special and should be used for Raft consensus messages between nodes, not for client connections.

`KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT` tells Kafka which listener name brokers use to talk to each other for data replication. When broker 2 needs to replicate a partition from broker 1, it uses the `PLAINTEXT` listener to connect. In a multi-broker setup with TLS, you would typically use a separate internal TLS listener here.

```yaml
      # --- Cluster identity ---
      KAFKA_CLUSTER_ID: "MkU3OEVBNTcwNTJENDM2Qk"
```

`KAFKA_CLUSTER_ID` is a base64-encoded UUID that uniquely identifies this Kafka cluster. In KRaft mode, this ID must be present and consistent across all nodes from the very first time the cluster starts. Every node that joins the cluster must have the same cluster ID or it will be rejected.

For development, you can generate this once with `kafka-storage.sh random-uuid` (available inside the Kafka container) or just use any valid base64 string of the right length. The value itself does not matter — what matters is that it is the same for all brokers in a cluster. Write it down, commit it to your repository, and never change it for a running cluster. If you delete your volumes and recreate the cluster, you can reuse the same ID or generate a new one, but all nodes must agree.

```yaml
      # --- Topic defaults ---
      KAFKA_NUM_PARTITIONS: 6
      KAFKA_DEFAULT_REPLICATION_FACTOR: 1
      KAFKA_MIN_INSYNC_REPLICAS: 1
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
```

`KAFKA_NUM_PARTITIONS: 6` sets the default number of partitions for new topics that are created without an explicit partition count. Why 6? Because partitions are the unit of parallelism in Kafka. If a topic has 6 partitions, you can have up to 6 consumers in a consumer group reading from it simultaneously — one consumer per partition. Choosing a number that is divisible by many common consumer group sizes (2, 3, 6 consumers) gives you flexibility later. In production this number is often higher — 12, 24, or even 48 for very high-throughput topics — but 6 is a good default.

`KAFKA_DEFAULT_REPLICATION_FACTOR: 1` means each partition has one copy — only the leader replica, no followers. For a single-broker setup this must be 1 because there is only one broker to hold replicas. For a three-broker setup, you want this to be 3, meaning each partition is copied to all three brokers so you can survive two broker failures.

`KAFKA_MIN_INSYNC_REPLICAS: 1` defines the minimum number of replicas that must acknowledge a write before the producer considers it successful (when the producer uses `acks=all`). For a single-broker setup, 1 is the only valid value. For a three-broker setup with replication factor 3, you typically set this to 2 — meaning at least 2 of the 3 replicas must confirm the write. This gives you durability even if one broker crashes, while still allowing progress if one broker is slow.

`KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1` sets the replication factor for the internal `__consumer_offsets` topic. This topic is where Kafka stores the committed offsets for all consumer groups. It is critical infrastructure — if this topic is lost, all consumer groups forget where they were reading. In production with three brokers, set this to 3.

`KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1` and `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1` control the replication of the internal `__transaction_state` topic, which tracks the state of Kafka transactions. If you are using exactly-once semantics or transactional producers in your Go service, this topic is critical. Same rule: set to 3 in production.

```yaml
      # --- Performance tuning ---
      KAFKA_LOG_RETENTION_HOURS: 168
      KAFKA_LOG_RETENTION_BYTES: -1
      KAFKA_LOG_SEGMENT_BYTES: 1073741824
      KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS: 300000
      KAFKA_COMPRESSION_TYPE: producer
      KAFKA_MESSAGE_MAX_BYTES: 1048576
```

`KAFKA_LOG_RETENTION_HOURS: 168` means Kafka will keep messages for 7 days (168 hours). After that, old log segments are deleted. This is not a per-message TTL — it is a per-segment policy. A segment is deleted when its newest message is older than the retention period. For event sourcing or audit log use cases, you might want much longer retention (30 days, 1 year, or even `KAFKA_LOG_RETENTION_BYTES: -1` combined with a very long time period). For transient processing pipelines where consumers catch up quickly, 24–48 hours might be enough.

`KAFKA_LOG_RETENTION_BYTES: -1` means there is no size-based retention limit. Kafka will keep data until the time-based retention kicks in. If you want to cap disk usage regardless of time, you can set this to something like `107374182400` (100 GB per partition). Both time and size retention are checked independently — whichever limit is hit first causes deletion.

`KAFKA_LOG_SEGMENT_BYTES: 1073741824` sets the maximum size of a single log segment file to 1 GB. Kafka writes messages to the current active segment. When the active segment reaches this size, it is closed (and becomes eligible for time-based retention checking) and a new segment is opened. Smaller segments mean retention cleanup happens more frequently but you have more files. Larger segments are more efficient for high-throughput topics. 1 GB is a solid default.

`KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS: 300000` tells Kafka how often (in milliseconds) to check whether any log segments have exceeded the retention policy and should be deleted. 300000ms is 5 minutes. This does not mean messages are deleted exactly at the retention boundary — deletion happens on the next check after the boundary is crossed. For most use cases, 5 minutes of slack is perfectly acceptable.

`KAFKA_COMPRESSION_TYPE: producer` means Kafka accepts whatever compression the producer used and stores the messages compressed. It does not re-compress. This is the most efficient setting because compression/decompression only happens at the edges (producer and consumer). Your Go producer can use Snappy, LZ4, Zstd, or GZIP — the broker will store and forward whatever it receives. Alternatively you can set this to `lz4` or `zstd` to force all messages to be compressed with that algorithm regardless of what the producer sent, but that wastes CPU re-compressing data that was already compressed.

`KAFKA_MESSAGE_MAX_BYTES: 1048576` sets the maximum size of a single message to 1 MB. If your Go producer tries to send a message larger than this, the broker will reject it with an error. If your use case involves large payloads (video thumbnails, full JSON documents, binary blobs), you may need to increase this — but think carefully before doing so. Large messages hurt throughput and increase memory pressure. Often the right solution is to store the large object in S3 or a database and put only a reference in the Kafka message.

```yaml
      # --- Consumer group settings ---
      KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 3000
      KAFKA_CONNECTIONS_MAX_IDLE_MS: 540000
      KAFKA_NUM_NETWORK_THREADS: 3
      KAFKA_NUM_IO_THREADS: 8
      KAFKA_SOCKET_SEND_BUFFER_BYTES: 102400
      KAFKA_SOCKET_RECEIVE_BUFFER_BYTES: 102400
      KAFKA_SOCKET_REQUEST_MAX_BYTES: 104857600
```

`KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 3000` tells Kafka to wait 3 seconds after the first consumer joins a group before triggering a rebalance. Why? Because when your application starts, all your consumer instances do not start at exactly the same millisecond. If the first consumer to start immediately triggers a rebalance, and then two seconds later the second consumer starts and triggers another rebalance, you waste time in back-to-back rebalances before you are even processing any messages. The delay gives all your consumers a window to join before the first rebalance happens. For large consumer groups with many instances, you might increase this to 10–30 seconds.

`KAFKA_CONNECTIONS_MAX_IDLE_MS: 540000` means idle connections are closed after 9 minutes (540,000 ms). A connection is idle if no requests have been sent on it. This prevents resource leaks from Go clients that connected and then crashed without sending a FIN packet. Your Go Kafka client will automatically reconnect when it needs to produce or consume.

`KAFKA_NUM_NETWORK_THREADS: 3` controls how many threads Kafka uses to handle network I/O — accepting connections, reading requests from sockets, writing responses back. This is separate from the threads that actually process the requests. For a development machine with limited CPU, 3 is fine. For a high-traffic production broker, you might increase this to 6–8.

`KAFKA_NUM_IO_THREADS: 8` controls how many threads handle the actual work of processing requests — reading from disk, writing to disk, handling fetch requests. I/O threads are where most of the real work happens. Setting this higher than the number of CPU cores is usually not beneficial. For production, matching it to the number of data disks or the number of CPU cores is a good starting point.

`KAFKA_SOCKET_SEND_BUFFER_BYTES: 102400` and `KAFKA_SOCKET_RECEIVE_BUFFER_BYTES: 102400` set the TCP socket buffer sizes to 100 KB. Larger buffers can improve throughput for high-volume producers and consumers by allowing more data to be in flight before the application reads it. For a high-throughput production setup on a fast network, some engineers increase these to 1 MB or more. The OS also has its own socket buffer limits (`net.core.rmem_max` on Linux) that must be at least as large as this value.

`KAFKA_SOCKET_REQUEST_MAX_BYTES: 104857600` sets the maximum size of a single request that Kafka will accept over the socket to 100 MB. This is a safety limit — it prevents a misbehaving client from sending a gigantic request and consuming all broker memory. The default is 100 MB, which is generous. Note that this is different from `KAFKA_MESSAGE_MAX_BYTES` — a single request can contain a batch of many messages, and this setting limits the entire request size.

```yaml
    ports:
      - "9092:9092"
      - "9094:9094"
    volumes:
      - kafka-data:/var/lib/kafka/data
    networks:
      - kafka-net
    healthcheck:
      test: ["CMD", "/opt/kafka/bin/kafka-broker-api-versions.sh", "--bootstrap-server", "localhost:9092"]
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 30s
```

`ports` maps container ports to host ports. We publish `9092:9092` (internal listener, also accessible from host for debugging) and `9094:9094` (external listener). We do not publish port 9093 because the controller listener should never be reached from outside the Docker network.

`volumes` mounts a named volume at `/var/lib/kafka/data`, which is where the official Apache Kafka image stores log data. Named volumes (as opposed to bind mounts) persist data between `docker compose down` and `docker compose up` — your messages and consumer offsets survive restarts. If you do `docker compose down -v`, the `-v` flag removes the volumes and you start fresh.

`networks` puts this container on a custom bridge network called `kafka-net`. Every service that needs to talk to Kafka must be on the same network. Custom networks give you DNS resolution (you can reach containers by their service name) and network isolation (containers not on `kafka-net` cannot reach Kafka at all).

`healthcheck` is critical for any Go service that depends on Kafka at startup. The `depends_on` setting in Docker Compose only waits for a container to start, not for the application inside it to be ready. Kafka takes 10–30 seconds to fully initialize in KRaft mode. If your Go service starts connecting before Kafka is ready, it will fail immediately. The health check runs `kafka-broker-api-versions.sh` against the local broker — this command succeeds only when Kafka is fully up and accepting API requests. Once the health check passes, Kafka is marked as "healthy" and dependent services can start.

## Adding Kafka UI — Essential for Development

You should always run a Kafka management UI in your development environment. Trying to debug consumer lag, inspect messages, or verify topic configurations without a UI is painful and slow. There are several good options; `provectuslabs/kafka-ui` is free, actively maintained, and has an excellent feature set.

```yaml
  kafka-ui:
    image: provectuslabs/kafka-ui:latest
    container_name: kafka-ui
    restart: unless-stopped
    depends_on:
      kafka:
        condition: service_healthy
    ports:
      - "8090:8080"
    environment:
      KAFKA_CLUSTERS_0_NAME: local
      KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: kafka:9092
      KAFKA_CLUSTERS_0_READONLY: "false"
    networks:
      - kafka-net
```

`depends_on` with `condition: service_healthy` is the correct way to express "start this service only after Kafka is healthy." Without the `condition` clause, Compose would start the UI immediately when Kafka's container starts, and the UI would crash trying to connect to a Kafka that is still initializing.

`KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: kafka:9092` tells the UI where to find Kafka. It uses the internal Docker network address — `kafka:9092` — because the UI container is on the same Docker network as Kafka. The `_0_` in the variable name is an index, allowing you to configure multiple Kafka clusters in the same UI instance.

Once your stack is running, open `http://localhost:8090` in your browser. You will see your topics, consumer groups, their current offsets, consumer lag, broker configuration, and more. This is how you verify that your Go services are actually producing and consuming correctly before writing a single unit test.

## The Schema Registry — If You Are Using Avro or Protobuf

If your team has decided to use Apache Avro or Protobuf for message serialization (a good decision for large-scale projects because it enforces a schema contract between producers and consumers), you need a Schema Registry. The Schema Registry is a separate service that stores and validates message schemas. Producers register their schema before producing, and consumers retrieve the schema to deserialize messages.

```yaml
  schema-registry:
    image: confluentinc/cp-schema-registry:7.6.0
    container_name: schema-registry
    restart: unless-stopped
    depends_on:
      kafka:
        condition: service_healthy
    ports:
      - "8081:8081"
    environment:
      SCHEMA_REGISTRY_HOST_NAME: schema-registry
      SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS: kafka:9092
      SCHEMA_REGISTRY_LISTENERS: http://0.0.0.0:8081
      SCHEMA_REGISTRY_KAFKASTORE_TOPIC_REPLICATION_FACTOR: 1
    networks:
      - kafka-net
```

`SCHEMA_REGISTRY_HOST_NAME: schema-registry` sets the hostname the Schema Registry advertises to clients. This should match the container name or service name so clients can reach it.

`SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS: kafka:9092` tells the Schema Registry where to find Kafka, because the Schema Registry stores its schema data inside a special Kafka topic called `_schemas`. The Schema Registry is not a standalone database — it uses Kafka as its storage backend.

`SCHEMA_REGISTRY_LISTENERS: http://0.0.0.0:8081` is the HTTP API that producers and consumers call to register and retrieve schemas. Your Go code using the Confluent Schema Registry client library will call this endpoint.

If you are using JSON serialization (plain `encoding/json` in Go, no schema registry), you do not need this service. But for production projects where multiple teams are producing and consuming the same topics, a schema registry is extremely valuable — it prevents a producer from changing the message format in a way that silently breaks all consumers.

## The Three-Broker Production Configuration

Running a single broker is fine for development. But for a project you call "large scale," you need multiple brokers for three reasons: fault tolerance (if one broker dies, the others keep serving), scalability (more brokers means more partitions you can spread across them, which means more parallelism), and throughput (more brokers means the write and read load is spread across more machines and more disks).

The canonical production setup for Docker Compose is three brokers. Three is the minimum for a meaningful fault-tolerant cluster — it gives you a quorum of 2, meaning the cluster can survive one broker failure and still elect leaders and accept writes.

Here is how to turn the single-broker configuration into a three-broker configuration. The key changes are: three separate service definitions with unique `KAFKA_NODE_ID` values, updating `KAFKA_CONTROLLER_QUORUM_VOTERS` to include all three nodes, updating replication factors to 3, and making sure each broker uses different host ports.

```yaml
services:

  kafka-1:
    image: apache/kafka:3.9.0
    container_name: kafka-1
    restart: unless-stopped
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093
      KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093,EXTERNAL://0.0.0.0:9094
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka-1:9092,EXTERNAL://localhost:9094
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT,EXTERNAL:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT
      KAFKA_CLUSTER_ID: "MkU3OEVBNTcwNTJENDM2Qk"
      KAFKA_NUM_PARTITIONS: 12
      KAFKA_DEFAULT_REPLICATION_FACTOR: 3
      KAFKA_MIN_INSYNC_REPLICAS: 2
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 3
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 3
```

## Volumes, Networks, and the Bottom of the File

At the bottom of your Docker Compose file, you must declare the named volumes and networks you referenced in the service definitions. Without these declarations, Docker Compose will either error or create anonymous volumes that do not persist properly.

```yaml
volumes:
  kafka-data:
    driver: local
  kafka-1-data:
    driver: local
  kafka-2-data:
    driver: local
  kafka-3-data:
    driver: local

networks:
  kafka-net:
    driver: bridge
    ipam:
      config:
        - subnet: 172.20.0.0/16
```

`driver: local` for volumes means Docker manages the volume on the local filesystem. The data lives somewhere under `/var/lib/docker/volumes/` on the host. This is the right choice for development and single-machine setups. For multi-machine production deployments, you would use a shared volume driver (like `convoy` for NFS, or cloud-specific drivers for EBS or GCS), but that is beyond Docker Compose's scope — you would be using Kubernetes with StatefulSets at that point.

`driver: bridge` for networks is Docker's default bridge network driver, which creates an isolated virtual network on your machine. All containers on the same bridge network can reach each other by service name. The `ipam` configuration with a specific subnet is optional — Docker will assign a subnet automatically if you omit it — but explicitly defining the subnet prevents Docker from picking a range that conflicts with your corporate VPN or office network. `172.20.0.0/16` is a private range unlikely to conflict with most VPN configurations.

## Connecting Your Go Services to Kafka

Your Go services are also defined in the same Docker Compose file. Here is how a typical Go microservice definition looks in relation to Kafka:

```yaml
  order-service:
    build:
      context: ./services/order
      dockerfile: Dockerfile
    container_name: order-service
    restart: unless-stopped
    depends_on:
      kafka-1:
        condition: service_healthy
      kafka-2:
        condition: service_healthy
      kafka-3:
        condition: service_healthy
    environment:
      KAFKA_BROKERS: "kafka-1:9092,kafka-2:9092,kafka-3:9092"
      KAFKA_GROUP_ID: "order-service"
      KAFKA_TOPIC_ORDERS: "orders.created"
      KAFKA_TOPIC_PAYMENTS: "payments.completed"
    networks:
      - kafka-net
```

The `depends_on` block with `condition: service_healthy` ensures your Go service does not start until all three Kafka brokers pass their health checks. This is the only correct way to handle startup ordering when one service genuinely cannot function until another is ready.

The `KAFKA_BROKERS` environment variable lists all three brokers as a comma-separated string. Your Go code should read this variable and pass it to your Kafka client's bootstrap configuration. The client will use these addresses only for initial discovery — it does not need to be able to reach all three at all times, just at least one when it first connects.

## Common Problems You Will Run Into

The single most common problem is the advertised listener issue. Your Go service connects successfully to Kafka but then immediately gets a `LEADER_NOT_AVAILABLE` or a connection refused error. This almost always means your `KAFKA_ADVERTISED_LISTENERS` is wrong. The broker connected fine for the initial handshake, but then advertised an address that the client cannot resolve or reach. Double-check that your internal listener advertises `kafka:9092` (not `localhost:9092`), and that every service connecting to Kafka is on the `kafka-net` network.

The second most common problem is the health check not passing. Kafka in KRaft mode takes a real 30–45 seconds to start on first boot because it needs to format the metadata log, elect a controller, and initialize internal topics. If your `start_period` in the health check is too short, Docker will start counting failures before Kafka is ready and mark it unhealthy prematurely. The fix is a generous `start_period: 45s` and at least 5 retries.

The third common problem is volume permission errors. If you create the volume directory manually on the host with the wrong permissions, Kafka will fail to write its log files. Let Docker manage volumes — do not create the directory yourself. If you already have a corrupted volume, `docker compose down -v` and `docker compose up` will start fresh.

The fourth problem appears when you switch from a single broker to three brokers but forget to update the `CLUSTER_ID`. Every broker in a cluster must have the same `KAFKA_CLUSTER_ID`. If you copy a single-broker configuration and add new brokers with a different cluster ID, they will refuse to join and you will see `InconsistentClusterIdException` in the logs.

## What You Do Not Configure in Docker Compose

Docker Compose is for development and simple production deployments. There are several Kafka concerns that Docker Compose cannot reasonably handle, and you should know where the boundaries are.

TLS encryption and SASL authentication — where producers and consumers authenticate with the broker using certificates or passwords — require mounting secrets into the containers and configuring Kafka with `SSL` or `SASL_SSL` protocol in the listener security protocol map. This is possible in Docker Compose using `secrets:` blocks, but it is complex enough that most teams save it for their Kubernetes or managed Kafka configuration. In development, `PLAINTEXT` is standard.

Rack awareness — configuring Kafka to spread replicas across different availability zones so that a data center failure does not take down all replicas of a partition — is a production concern that does not apply in Docker Compose where all containers run on the same machine.

Auto-creating topics in production is something you should turn off. The environment variable `KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"` prevents Kafka from automatically creating a topic the first time a producer writes to it. In development this is convenient, but in production you want topics to be created explicitly with the right partition count and replication factor. Add topic creation to your CI/CD pipeline or your service initialization code.

Log compaction — a Kafka feature where instead of deleting old messages by time, Kafka keeps only the most recent message for each key — is configured at the topic level, not the broker level. If you need compacted topics (for event sourcing or materializing the latest state of entities), you create the topic with `cleanup.policy=compact` using the Kafka admin API in your Go service, not in Docker Compose.

## Final Thought

Kafka's configuration is dense because Kafka is solving a genuinely hard problem: durable, ordered, high-throughput message delivery across a distributed cluster. Every configuration knob exists because someone in the world needed it.

When you are starting out, you do not need to understand every knob. You need to understand the listener configuration deeply — because that is what breaks most often and is the hardest to debug without knowing how it works. You need to understand replication factor and min ISR — because those determine your durability guarantees and your ability to survive broker failures. And you need to understand the health check and startup ordering — because a Go service that starts before Kafka is ready will crash, and figuring out why requires understanding that `depends_on` alone is not enough.

Everything else — compression settings, socket buffers, thread counts, retention policies — you can tune as you learn more about your specific workload. Start with the defaults in this guide, observe your system under realistic load, and adjust based on what the metrics tell you. That is how senior engineers do it. They do not guess at configuration — they measure, then tune.
