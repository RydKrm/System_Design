## Before We Touch Any Code — What Is a Kafka Consumer, Really?

Welcome to the team. Before we configure a single line, I need you to build a mental picture of what a Kafka consumer actually is, because if you don't understand the machine, you'll just be copy-pasting configs blindly and you'll break things in production.

Think of Kafka as a giant, ordered logbook that never erases itself. Every time something happens in our HR360 system — an employee joins, a payroll is processed, a leave request is submitted — that event gets written into this logbook. A Kafka consumer is a program that sits beside the logbook, reads entries, and does something useful with them. It's your job to configure how that program connects, what it reads, and how it remembers where it left off.

```
HR360 SYSTEM — EVENT FLOW
═══════════════════════════════════════════════════════════════════════

  [Employee Service]  ──► topic: employee.created
  [Payroll Service]   ──► topic: payroll.processed    ──► [ KAFKA ]
  [Leave Service]     ──► topic: leave.requested               │
  [Auth Service]      ──► topic: auth.login                    │
                                                               │
                    ┌──────────────────────────────────────────┘
                    ▼
          ┌─────────────────────────────────────────────────┐
          │         Your Kafka Consumer (franz-go)          │
          │                                                 │
          │  Connect → Subscribe → Read → Process → Commit  │
          └─────────────────────────────────────────────────┘

═══════════════════════════════════════════════════════════════════════
```

Now the `franz-go` library (`github.com/twmb/franz-go/pkg/kgo`) is what we're using. It's a pure-Go Kafka client that gives you very fine-grained control compared to `confluent-kafka-go`, and that control is exactly what a large-scale system like HR360 needs. Every configuration option we're about to walk through is a specific dial that addresses a specific real-world problem. Let's go through them one by one.

## Part 1 — Connection Configuration

### `kgo.SeedBrokers()` — The Door Into Kafka

The very first thing your consumer needs to know is: _where is Kafka?_ `SeedBrokers` is literally the list of addresses your consumer will knock on first. I want you to notice the word "seed" — these are not necessarily all the brokers. Kafka is a distributed system. You give the consumer a few addresses, it connects to one, discovers all the other brokers in the cluster through metadata, and then knows the full map. So you don't need to list every single broker, but listing at least two or three is wise so that if one broker is down during startup, your consumer still connects successfully.

In HR360, we have a three-broker Kafka cluster. During local development you're talking to a single Docker container, but in staging and production you're talking to real distributed nodes.

```
SEED BROKER DISCOVERY PROCESS
═══════════════════════════════════════════════════════════════════════

  Consumer starts
       │
       ▼
  Tries kafka-1:9092 ──► Connected!
       │
       ▼
  Asks: "Who else is in the cluster?"
       │
       ▼
  Receives metadata:
    ├── kafka-1:9092  (already connected)
    ├── kafka-2:9092  (now connects)
    └── kafka-3:9092  (now connects)
       │
       ▼
  Full cluster map known. Consumer is ready.

═══════════════════════════════════════════════════════════════════════
```

```go
package main

import (
    "github.com/twmb/franz-go/pkg/kgo"
    "log"
)

func NewHR360Consumer() (*kgo.Client, error) {
    brokers := []string{
        "kafka-1:9092",
        "kafka-2:9092",
        "kafka-3:9092",
    }

    client, err := kgo.NewClient(
        // Tell the consumer where to find Kafka.
        // Always list multiple brokers so startup survives a single node failure.
        kgo.SeedBrokers(brokers...),
    )
    if err != nil {
        return nil, err
    }

    return client, nil
}
```

The problem this solves: without this, your consumer has no idea Kafka even exists. It's as basic as giving someone a phone number before asking them to make a call.

### `kgo.ClientID()` — Giving Your Consumer a Name Tag

Every client that connects to Kafka sends an identifier string. Kafka logs this, and every monitoring tool — Grafana, Kafka UI, your broker logs — displays it. In a large system like HR360 where multiple services are all consuming from Kafka simultaneously, `ClientID` is how you tell them apart when debugging.

Without a proper `ClientID`, all your consumers show up in the broker logs as `"kgo"` (the default) and you have no idea which service is causing a lag spike at 3 AM when your on-call phone goes off.

```
KAFKA BROKER CONNECTIONS VIEW (without ClientID)
═══════════════════════════════════════════════════════════════════════

  Connected clients:
  ├── kgo  (which service is this??)
  ├── kgo  (is this the same one??)
  ├── kgo  (why are there 3??)
  └── kgo  (completely useless)

KAFKA BROKER CONNECTIONS VIEW (with ClientID)
═══════════════════════════════════════════════════════════════════════

  Connected clients:
  ├── hr360-notification-service-v2.1
  ├── hr360-payroll-consumer-v1.0
  ├── hr360-audit-logger-v3.2
  └── hr360-leave-processor-v1.5
  
  Now you know exactly what's connected and what to look at!

═══════════════════════════════════════════════════════════════════════
```

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),

    // Give this consumer a meaningful name.
    // Use your service name + version so monitoring dashboards are readable.
    kgo.ClientID("hr360-payroll-consumer-v1.0"),
)
```

### `kgo.Dialer()` — Controlling How the TCP Connection Is Made

The `Dialer` is the lower-level network dial function that franz-go uses when opening a TCP connection to a Kafka broker. Most of the time you don't need to touch this. But there are two real-world situations in HR360 where you absolutely will:

**Situation 1:** Your Kafka cluster is inside a private network and you need to connect via a bastion host or a specific network interface. You can supply a custom `net.Dialer` with a timeout, a specific source address, or even a SOCKS5 proxy.

**Situation 2:** You need TLS but you want to handle the dialing yourself rather than using `DialTLSConfig`. This gives you full control.

```go
import (
    "context"
    "crypto/tls"
    "net"
    "time"

    "github.com/twmb/franz-go/pkg/kgo"
)

func NewHR360ConsumerWithDialer() (*kgo.Client, error) {
    // Build a custom dialer with a 10-second connection timeout.
    // This is important in cloud environments where DNS or network
    // latency can cause hangs if you don't set a timeout.
    baseDialer := &net.Dialer{
        Timeout:   10 * time.Second,
        KeepAlive: 30 * time.Second,
    }

    client, err := kgo.NewClient(
        kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092"),
        kgo.ClientID("hr360-employee-consumer-v1.0"),

        // Provide the custom dialer function.
        // franz-go will use this every time it opens a new TCP connection.
        kgo.Dialer(func(ctx context.Context, network, addr string) (net.Conn, error) {
            return baseDialer.DialContext(ctx, network, addr)
        }),
    )
    return client, err
}
```

The problem this solves: default Go `net.Dial` calls can hang indefinitely if the broker address is unreachable. In production, a hanging dial means your service silently fails to start consuming, and you won't know until someone notices that messages are piling up in the topic. A proper dialer with a timeout fails fast and loudly.

### `kgo.DialTLSConfig()` — Encrypting the Connection

In any production system that handles HR data — salaries, personal information, performance records — you cannot send data over the wire unencrypted. `DialTLSConfig` is how you tell franz-go to wrap every Kafka connection in TLS. This is the standard way to do it in franz-go, and it's simpler than using a custom `Dialer` for TLS because you just hand it a `*tls.Config` and the library handles the rest.

```
TLS CONNECTION — WHAT IT LOOKS LIKE
═══════════════════════════════════════════════════════════════════════

  WITHOUT TLS:
  Consumer ──────────────────────────────────────► Kafka Broker
             raw bytes: {"salary": 85000, ...}
             (anyone on the network can read this)

  WITH TLS:
  Consumer ──────────────────────────────────────► Kafka Broker
             encrypted: x7f#@$!kL9p2...
             (only the broker can decrypt this)
             
  TLS Handshake (happens once per connection):
  Consumer:  "Here's my client certificate"
  Broker:    "Here's my server certificate"
  Both:      "Verified. Here's our shared session key."
  Now:       All messages encrypted with that session key.

═══════════════════════════════════════════════════════════════════════
```

```go
import (
    "crypto/tls"
    "crypto/x509"
    "os"
    "log"

    "github.com/twmb/franz-go/pkg/kgo"
)

func NewHR360SecureConsumer() (*kgo.Client, error) {
    // Load our CA certificate so we can verify the broker's identity.
    // Without this, we'd accept connections from fake brokers (MITM attack).
    caCert, err := os.ReadFile("/etc/ssl/kafka/ca.crt")
    if err != nil {
        log.Fatal("Cannot load CA cert:", err)
    }

    certPool := x509.NewCertPool()
    certPool.AppendCertsFromPEM(caCert)

    // Load client cert + key for mutual TLS (mTLS).
    // mTLS means BOTH sides verify each other.
    // The broker checks OUR certificate, not just us checking theirs.
    clientCert, err := tls.LoadX509KeyPair(
        "/etc/ssl/kafka/client.crt",
        "/etc/ssl/kafka/client.key",
    )
    if err != nil {
        log.Fatal("Cannot load client cert:", err)
    }

    tlsCfg := &tls.Config{
        Certificates: []tls.Certificate{clientCert},
        RootCAs:      certPool,
        // MinVersion prevents old, insecure TLS versions.
        MinVersion:   tls.VersionTLS12,
    }

    client, err := kgo.NewClient(
        // Note: port 9093 is the conventional TLS port for Kafka.
        // Your plain-text port is 9092; TLS port is 9093.
        kgo.SeedBrokers("kafka-1:9093", "kafka-2:9093", "kafka-3:9093"),
        kgo.ClientID("hr360-secure-consumer-v1.0"),

        // Hand the TLS config to franz-go.
        // Every TCP connection will now be TLS-wrapped automatically.
        kgo.DialTLSConfig(tlsCfg),
    )
    return client, err
}
```

## Part 2 — Consumer Group Configuration

### `kgo.ConsumerGroup()` — The Most Important Concept You'll Learn Today

This is the big one. Sit down and really absorb this. A consumer group is how Kafka lets multiple instances of your service share the work of reading a topic, while still ensuring every message is processed by exactly one instance.

Here's the problem it solves. Imagine HR360 gets a surge of 50,000 payroll events in one minute. A single consumer instance reading them one by one would fall behind. But if you run 5 instances of your payroll consumer, how does Kafka know which instance should read which message? Without a consumer group, every instance would read every message and your payroll processor would fire 5 times for every single employee. That's 5 duplicate salary payments. People would be very happy and you would be fired.

With a consumer group, Kafka assigns different partitions to different consumer instances. Each message lives in exactly one partition. Each partition is assigned to exactly one consumer at a time. So the work is split cleanly.

```
CONSUMER GROUP — PARTITION ASSIGNMENT
═══════════════════════════════════════════════════════════════════════

  topic: payroll.processed  (4 partitions)
  ┌──────────────┬──────────────┬──────────────┬──────────────┐
  │  Partition 0 │  Partition 1 │  Partition 2 │  Partition 3 │
  │  [msg1]      │  [msg3]      │  [msg5]      │  [msg7]      │
  │  [msg2]      │  [msg4]      │  [msg6]      │  [msg8]      │
  └──────┬───────┴───-───┬──────┴─-─────┬──────┴─-────-─┬─────┘
         │               │              │               │
         └───────┬───────┘              └───────┬───────┘
                 │                              │
         ┌───────▼───────┐              ┌───────▼───────┐
         │  Consumer #1  │              │  Consumer #2  │
         │  (instance A) │              │  (instance B) │
         └───────────────┘              └───────────────┘

  Consumer #1 handles P0 + P1   → msg1, msg2, msg3, msg4
  Consumer #2 handles P2 + P3   → msg5, msg6, msg7, msg8
  No duplicates. No missed messages. Clean split.

═══════════════════════════════════════════════════════════════════════
```

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ClientID("hr360-payroll-consumer-v1.0"),

    // Register this consumer as part of the "hr360-payroll-processors" group.
    // Every instance of your payroll service should use this SAME group ID.
    // Kafka uses this to coordinate which instance reads which partition.
    //
    // IMPORTANT: different services should have DIFFERENT group IDs.
    // Your notification service uses "hr360-notification-service" group.
    // Your audit logger uses "hr360-audit-logger" group.
    // This way BOTH services read all payroll events independently.
    kgo.ConsumerGroup("hr360-payroll-processors"),
)
```

One critical concept here: if two completely different services — say your payroll processor and your audit logger — both need to read the same `payroll.processed` topic, they must use different group IDs. Each group gets its own independent offset pointer into the topic. So both services see every message, but each handles it independently.

### `kgo.InstanceID()` — Static Membership (Your Identity Card That Never Changes)

By default, when a consumer joins a group, Kafka gives it a temporary ID that changes every time it restarts. Every time an ID changes, Kafka triggers a "rebalance" — a process where the group pauses everything and redistributes partitions among all current members. This rebalance can take 30–60 seconds and during that time nobody is consuming messages. If your HR360 payroll service restarts during the monthly payroll run, a 60-second pause is catastrophic.

`InstanceID` gives a consumer a stable, permanent identifier. When it restarts, Kafka recognizes the same ID, skips the rebalance, and immediately reassigns the same partitions back to it. The group barely hiccups.

```
RESTART BEHAVIOR — WITHOUT vs WITH InstanceID
═══════════════════════════════════════════════════════════════════════

  WITHOUT InstanceID (Dynamic Membership):
  
  Consumer-A restarts
       │
       ▼
  Gets new ID: "member-xyz-99"  (different from before)
       │
       ▼
  Kafka: "Unknown member joined! Triggering rebalance..."
       │
       ▼
  ALL consumers in the group STOP for 30–60 seconds
       │
       ▼
  Partitions redistributed. Processing resumes.
  
  ─────────────────────────────────────────────────

  WITH InstanceID (Static Membership):
  
  Consumer-A restarts
       │
       ▼
  Announces: "I am hr360-payroll-pod-1" (always the same)
       │
       ▼
  Kafka: "Welcome back! Here are your partitions."
       │
       ▼
  Processing resumes in ~2 seconds. No group pause.

═══════════════════════════════════════════════════════════════════════
```

```go
import "os"

// In Kubernetes, each pod has a stable name like "payroll-consumer-0",
// "payroll-consumer-1", etc. (StatefulSet naming).
// We use the pod name as the InstanceID so it's unique and stable.
podName := os.Getenv("POD_NAME") // e.g., "hr360-payroll-consumer-0"

client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ClientID("hr360-payroll-consumer-v1.0"),
    kgo.ConsumerGroup("hr360-payroll-processors"),

    // This pod's permanent identity in the consumer group.
    // Even after a restart, Kafka will see this same ID
    // and skip the expensive rebalance.
    kgo.InstanceID(podName),
)
```

### `kgo.Balancers()` — Choosing How Partitions Are Divided

When Kafka assigns partitions to group members, it needs an algorithm to decide who gets what. This algorithm is called a "balancer" or "partition assignment strategy." franz-go ships with several. You need to understand each because the wrong choice causes uneven load distribution.

```
PARTITION BALANCING STRATEGIES COMPARED
═══════════════════════════════════════════════════════════════════════

  Topic: hr360.events  (6 partitions)  |  3 consumers

  RoundRobin (kgo.RoundRobinBalancer()):
  Consumer-1 gets: P0, P3
  Consumer-2 gets: P1, P4
  Consumer-3 gets: P2, P5
  → Always even distribution. Simple and fair.

  Range (kgo.RangeBalancer()):
  Consumer-1 gets: P0, P1
  Consumer-2 gets: P2, P3
  Consumer-3 gets: P4, P5
  → Assigns contiguous ranges. Fine for single topics.
  → With multiple topics can cause imbalance.

  Sticky (kgo.StickyBalancer()):
  Rebalance happens. Each consumer KEEPS its old partitions
  where possible. Only moves partitions that must move.
  → Minimizes disruption during rebalances.
  → Best for stateful consumers that cache per-partition data.

  CooperativeSticky (kgo.CooperativeStickyBalancer()):
  Like Sticky, but partitions are transferred one at a time.
  Consumer never has to stop completely — it keeps consuming
  its existing partitions while new ones are being added.
  → The modern gold standard. Use this by default.

═══════════════════════════════════════════════════════════════════════
```

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-payroll-processors"),

    // CooperativeStickyBalancer is the modern best practice.
    // It allows "incremental rebalancing" — partitions are
    // handed off one at a time without stopping all consumers.
    //
    // Your consumer keeps processing during a rebalance.
    // Only the specific partition being transferred pauses briefly.
    //
    // For HR360's large-scale setup, this significantly reduces
    // the downtime impact of scaling events (adding/removing pods).
    kgo.Balancers(kgo.CooperativeStickyBalancer()),
)
```

## Part 3 — Topic Subscription

### `kgo.ConsumeTopics()` — The Simple, Direct Way to Subscribe

This is the most common way to tell your consumer which topics to read. You give it a list of topic names, and it subscribes to all of them. Within a consumer group, Kafka will assign partitions across all these topics to the group members.

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-notification-service"),

    // This consumer cares about three topics.
    // The notification service needs to send emails/SMS for all three events.
    kgo.ConsumeTopics(
        "hr360.employee.created",
        "hr360.leave.approved",
        "hr360.payroll.processed",
    ),
)
```

---

### `kgo.ConsumePartitions()` — Surgical, Partition-Level Control

Sometimes you don't want to join a consumer group at all. You want to say: "I want to read exactly partition 2 of topic `hr360.audit.events`, starting from offset 500." This is for advanced use cases like:

**Reprocessing a specific partition** after a bug was fixed. You don't want a full consumer group restart; you just want to replay one partition.

**Building an audit reader** that an admin uses to investigate a specific range of events. Consumer groups aren't appropriate here because you don't want your diagnostic tool interfering with production consumers.

```go
// ConsumePartitions does NOT use a consumer group.
// You are directly commanding: read THIS partition of THIS topic from THIS offset.
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ClientID("hr360-audit-reader-tool"),

    // Map: topic → (partition → starting offset)
    // Here we're reading partition 2 of the audit topic from the very beginning.
    kgo.ConsumePartitions(map[string]map[int32]kgo.Offset{
        "hr360.audit.events": {
            2: kgo.NewOffset().AtStart(),
        },
    }),
)
```

---

### `kgo.ConsumeRegex()` — Subscribe by Pattern

HR360 has many topics, and some follow a naming convention. The `hr360.department.*` family might have `hr360.department.engineering`, `hr360.department.finance`, `hr360.department.hr`, and new ones get created as new departments are onboarded. Subscribing to each one by name is fragile — you'd have to update code every time a new department is added.

`ConsumeRegex` tells franz-go to use the topic names you pass to `ConsumeTopics` as regular expressions. This pairs beautifully with `ConsumeTopics`.

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-department-event-processor"),

    // Turn on regex matching for topic names.
    kgo.ConsumeRegex(),

    // Now these are treated as regex patterns, not literal names.
    // "hr360\\.department\\..*" matches:
    //   hr360.department.engineering
    //   hr360.department.finance
    //   hr360.department.hr
    //   hr360.department.legal   ← added next month, still matched automatically
    kgo.ConsumeTopics(`hr360\.department\..*`, `hr360\.team\..*`),
)
```

## Part 4 — Offset Management

### Understanding Offsets Before Anything Else

An offset is simply the position of a message within a partition. It's a number that starts at 0 and goes up by 1 for every message. Your consumer keeps track of which offset it has processed so that if it restarts, it knows where to resume.

```
OFFSETS IN A PARTITION
═══════════════════════════════════════════════════════════════════════

  topic: hr360.employee.created  |  Partition 0
  
  Offset:  [0]    [1]    [2]    [3]    [4]    [5]    ...
  Message: emp-A  emp-B  emp-C  emp-D  emp-E  emp-F  ...
  
  Your consumer processed up to offset 3.
  Committed offset = 4 (next one to read).
  
  Consumer restarts → resumes from offset 4 (emp-E).
  
  AtStart()  = "Give me offset 0. Start from the very first message."
  AtEnd()    = "Give me the next NEW message. Skip history."
  At(3)      = "Give me offset 3 specifically."

═══════════════════════════════════════════════════════════════════════
```

### `kgo.ConsumeResetOffset()` — What to Do When There's No Saved Position

This is the fallback behavior. When your consumer joins a group for the very first time, or when the committed offset for a partition has expired (Kafka deletes old offsets after `offsets.retention.minutes`), there's no saved position. `ConsumeResetOffset` tells Kafka what to do in that case.

```go
// Scenario: First time hr360-payroll-processors runs against "hr360.payroll.processed".
// There's no committed offset for this group on this topic.
// What should it do?

client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-payroll-processors"),
    kgo.ConsumeTopics("hr360.payroll.processed"),

    // kgo.NewOffset().AtEnd() = "Start from the latest message."
    // This means: on first run, ignore all historical payroll events.
    // Only process NEW payrolls from this moment onward.
    //
    // Alternative: kgo.NewOffset().AtStart() = "Replay everything from the beginning."
    // Use AtStart() when you need to reprocess historical data (e.g., after a bug fix).
    kgo.ConsumeResetOffset(kgo.NewOffset().AtEnd()),
)
```

---

### `kgo.NewOffset().AtStart()`, `.AtEnd()`, `.At()`, `.AfterMilli()`, `.BeforeMilli()`

These are the offset positioning tools. They're all methods on a `kgo.Offset` value and they answer the question: "where in the partition do you want to start reading?"

```go
// All offset options demonstrated in context of HR360 use cases.

// AtStart() — Read from the very beginning.
// Use case: "We had a bug in the leave approval handler for 2 weeks.
// We fixed it. Now replay all leave events from the start to reprocess them."
fromBeginning := kgo.NewOffset().AtStart()

// AtEnd() — Read only new messages from now on.
// Use case: "Deploy a new notification service. We don't care about
// historical events, only events that happen after we go live."
fromNow := kgo.NewOffset().AtEnd()

// At(n) — Read from a specific offset number.
// Use case: "The audit report shows corruption started at offset 4821.
// Replay from exactly offset 4822 (after the bad message)."
fromSpecific := kgo.NewOffset().At(4822)

// AfterMilli(timestampMs) — Read messages AFTER a specific timestamp.
// Use case: "Something went wrong on the 15th. Replay all employee
// events that happened after midnight on the 15th."
import "time"
midnightJan15 := time.Date(2025, 1, 15, 0, 0, 0, 0, time.UTC).UnixMilli()
fromDate := kgo.NewOffset().AfterMilli(midnightJan15)

// BeforeMilli(timestampMs) — Read messages BEFORE a specific timestamp.
// Use case: "I want to audit everything that happened before the system
// upgrade at 14:00 on the 20th."
upgradeTime := time.Date(2025, 1, 20, 14, 0, 0, 0, time.UTC).UnixMilli()
beforeUpgrade := kgo.NewOffset().BeforeMilli(upgradeTime)

// Use in ConsumePartitions for direct partition access:
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092"),
    kgo.ConsumePartitions(map[string]map[int32]kgo.Offset{
        "hr360.leave.requested": {
            0: fromDate,   // Partition 0: read from Jan 15 midnight onward
            1: fromNow,    // Partition 1: only new messages
        },
    }),
)
```

## Part 5 — Auto Commit

### The Problem Auto Commit Solves

After your consumer reads a message and processes it, it needs to "commit" the offset — tell Kafka "I'm done with this one, remember my position." If your consumer crashes before committing, when it restarts it will re-read and reprocess the uncommitted messages. That's the at-least-once delivery guarantee.

Auto commit handles this automatically on a timer, so you don't have to write commit logic for every message in simple use cases.

### `kgo.AutoCommitMarks()` — Smarter Auto Commit

By default, franz-go auto-commits the _latest polled offset_, not the latest _processed_ offset. That's a subtle but dangerous difference. If your consumer polled 100 messages and is halfway through processing them when the auto-commit timer fires, Kafka will commit offset 100 — even though you've only processed 50. A crash now means you lose the 50 unprocessed messages.

`AutoCommitMarks` changes this behavior. The auto-commit only commits offsets for messages you've explicitly marked as done by calling `client.MarkCommitRecords(record)`. So your processing and your commits stay in sync.

```
REGULAR AUTO COMMIT vs AutoCommitMarks
═══════════════════════════════════════════════════════════════════════

  Regular Auto Commit (dangerous):
  
  Poll offsets 1-100
       │
       Processing...  (you're at offset 50)
       │
       Auto-commit fires → commits offset 100  ← BUG!
       │
       Crash!
       │
       Restart → resumes from 101  → offsets 51-100 LOST FOREVER

  ─────────────────────────────────────────────────────────────────

  AutoCommitMarks (safe):
  
  Poll offsets 1-100
       │
       Process offset 1  → mark it ✓
       Process offset 2  → mark it ✓
       ...
       Process offset 50 → mark it ✓
       │
       Auto-commit fires → commits offset 50  ← CORRECT!
       │
       Crash!
       │
       Restart → resumes from 51  → only need to reprocess 51-100

═══════════════════════════════════════════════════════════════════════
```

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-notification-service"),
    kgo.ConsumeTopics("hr360.employee.created"),

    // Only commit offsets for records we explicitly mark as done.
    // This prevents committing ahead of our actual processing position.
    kgo.AutoCommitMarks(),
)

// In your processing loop:
func processRecords(client *kgo.Client, records []*kgo.Record) {
    for _, record := range records {
        err := sendWelcomeEmail(record) // do your actual work
        if err != nil {
            log.Printf("Failed to process record at offset %d: %v", record.Offset, err)
            // Don't mark it. It won't be committed. It will be retried.
            continue
        }

        // Only mark after successful processing.
        // The auto-committer will include this in the next commit cycle.
        client.MarkCommitRecords(record)
    }
}
```

---

### `kgo.AutoCommitInterval()` — How Often to Commit

The auto-commit runs on a timer. `AutoCommitInterval` sets how frequently it fires. The default is 5 seconds. Shorter intervals mean less reprocessing after a crash (you lose less progress) but more network traffic to the broker. Longer intervals mean fewer commits but more reprocessing risk.

```go
import "time"

client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-audit-logger"),
    kgo.ConsumeTopics("hr360.audit.events"),
    kgo.AutoCommitMarks(),

    // Commit every 3 seconds.
    // For the audit logger, we can tolerate replaying up to 3 seconds
    // worth of events after a crash (audit logs are idempotent — logging
    // the same event twice is harmless).
    //
    // For a payroll processor that sends actual money, you'd want
    // manual commit instead (see Part 6) or a very short interval.
    kgo.AutoCommitInterval(3 * time.Second),
)
```

---

### `kgo.DisableAutoCommit()` — Full Manual Control

For critical workflows — anything that moves money, sends irreversible notifications, or modifies permanent records — you want to commit offsets yourself, exactly when you know the work is done. `DisableAutoCommit` turns off the auto-commit timer entirely and hands you full control.

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-payroll-processors"),
    kgo.ConsumeTopics("hr360.payroll.run.triggered"),

    // No automatic commits. We will commit manually after confirming
    // the bank transfer API call succeeded. This is a financial system.
    // The cost of reprocessing is low; the cost of skipping is catastrophic.
    kgo.DisableAutoCommit(),
)
```

## Part 6 — Manual Commit

### `client.CommitRecords()` — Commit Specific Records Right Now

`CommitRecords` is the most direct manual commit. You hand it one or more `*kgo.Record` values and it commits their offsets to Kafka immediately. This is a synchronous-style call (it returns an error if the commit fails) and it's what you use when you want guarantee that the commit succeeded before moving on.

```go
import (
    "context"
    "log"

    "github.com/twmb/franz-go/pkg/kgo"
)

func processPayrollBatch(ctx context.Context, client *kgo.Client) {
    fetches := client.PollFetches(ctx)
    if errs := fetches.Errors(); len(errs) > 0 {
        log.Printf("Fetch errors: %v", errs)
        return
    }

    var successfulRecords []*kgo.Record

    fetches.EachRecord(func(record *kgo.Record) {
        err := processSalaryPayment(record)
        if err != nil {
            // Log the error and handle via DLQ or retry logic.
            // We do NOT add this record to successfulRecords.
            log.Printf("Payroll processing failed for offset %d: %v", record.Offset, err)
            return
        }

        // Only collect records that were successfully processed.
        successfulRecords = append(successfulRecords, record)
    })

    if len(successfulRecords) == 0 {
        return
    }

    // Commit only the successfully processed records.
    // CommitRecords internally figures out the highest offset
    // per partition and commits that to Kafka.
    if err := client.CommitRecords(ctx, successfulRecords...); err != nil {
        // If the commit fails, log it. On restart, these records
        // will be reprocessed. Make sure your processor is idempotent!
        log.Printf("Failed to commit offsets: %v", err)
    }
}
```

---

### `client.CommitOffsets()` — Commit an Explicit Offset Map

Sometimes you don't have the `*kgo.Record` objects handy but you do know the exact offsets you want to commit. `CommitOffsets` lets you commit a `map[string]map[int32]kgo.EpochOffset` directly. This is common in batch processing pipelines where you track offsets yourself.

```go
import (
    "context"
    "log"

    "github.com/twmb/franz-go/pkg/kgo"
)

// Imagine you processed a batch and tracked the last offset per partition yourself.
func commitProcessedBatch(ctx context.Context, client *kgo.Client) {
    // Build the offset map manually.
    // The commit offset should be the NEXT offset to read (last processed + 1).
    offsets := make(map[string]map[int32]kgo.EpochOffset)
    offsets["hr360.payroll.processed"] = map[int32]kgo.EpochOffset{
        // Partition 0: we processed up to offset 1499, so commit 1500 (next to read)
        0: {Epoch: -1, Offset: 1500},
        // Partition 1: we processed up to offset 822, commit 823
        1: {Epoch: -1, Offset: 823},
    }

    // CommitOffsets commits this exact map to Kafka.
    // Use Epoch: -1 to let Kafka manage the epoch automatically.
    ch := make(chan error, 1)
    client.CommitOffsets(ctx, offsets, func(_ *kgo.Client, _ map[string]map[int32]kgo.EpochOffset, err error) {
        ch <- err
    })

    if err := <-ch; err != nil {
        log.Printf("Offset commit failed: %v", err)
    }
}
```

---

### `client.MarkCommitRecords()` — Mark Now, Commit Later

This is the companion to `AutoCommitMarks()`. You call `MarkCommitRecords` while processing, and the auto-commit timer picks up all marks and commits them together on the next cycle. It's a non-blocking mark — it doesn't trigger a network call. The commit happens asynchronously on the timer.

This is the sweet spot for high-throughput consumers: you get the safety of mark-based commits (you control what gets committed) with the efficiency of batched auto-commits (not every message triggers a network round-trip to the broker).

```go
client, err := kgo.NewClient(
    kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
    kgo.ConsumerGroup("hr360-audit-logger"),
    kgo.ConsumeTopics("hr360.audit.events"),

    // Enable mark-based auto commit.
    kgo.AutoCommitMarks(),
    kgo.AutoCommitInterval(5 * time.Second),
)

func processAuditEvents(client *kgo.Client, ctx context.Context) {
    for {
        fetches := client.PollFetches(ctx)

        fetches.EachRecord(func(record *kgo.Record) {
            // Write to audit database.
            err := writeAuditLog(record)
            if err != nil {
                // Don't mark. This record will be retried after restart.
                log.Printf("Audit write failed: %v", err)
                return
            }

            // Mark this record as done.
            // No network call happens here — this is just an in-memory mark.
            // Every 5 seconds, the auto-committer commits all marked offsets in one go.
            client.MarkCommitRecords(record)
        })
    }
}
```

## Putting It All Together — A Production-Grade HR360 Consumer

Now let me show you what a real, full configuration looks like when you combine everything we've discussed. This is the payroll processor — the most critical consumer in HR360.

```go
package consumer

import (
    "context"
    "crypto/tls"
    "crypto/x509"
    "log"
    "os"
    "time"

    "github.com/twmb/franz-go/pkg/kgo"
)

// NewPayrollConsumer builds a production-grade Kafka consumer
// for the HR360 payroll processing service.
func NewPayrollConsumer() (*kgo.Client, error) {
    // --- TLS Setup ---
    caCert, err := os.ReadFile("/etc/ssl/kafka/ca.crt")
    if err != nil {
        return nil, err
    }
    certPool := x509.NewCertPool()
    certPool.AppendCertsFromPEM(caCert)

    clientCert, err := tls.LoadX509KeyPair(
        "/etc/ssl/kafka/client.crt",
        "/etc/ssl/kafka/client.key",
    )
    if err != nil {
        return nil, err
    }

    tlsCfg := &tls.Config{
        Certificates: []tls.Certificate{clientCert},
        RootCAs:      certPool,
        MinVersion:   tls.VersionTLS12,
    }

    // --- Static Membership ---
    // In Kubernetes, pod name is stable for StatefulSets.
    podName := os.Getenv("POD_NAME")
    if podName == "" {
        podName = "hr360-payroll-consumer-standalone"
    }

    client, err := kgo.NewClient(
        // Connection
        kgo.SeedBrokers("kafka-1:9093", "kafka-2:9093", "kafka-3:9093"),
        kgo.ClientID("hr360-payroll-consumer-v2.0"),
        kgo.DialTLSConfig(tlsCfg),

        // Consumer Group
        kgo.ConsumerGroup("hr360-payroll-processors"),
        kgo.InstanceID(podName),
        kgo.Balancers(kgo.CooperativeStickyBalancer()),

        // Topic Subscription
        kgo.ConsumeTopics("hr360.payroll.run.triggered"),

        // Offset Strategy:
        // On first run (no committed offset yet), start from the end.
        // We don't want to retroactively process old payroll runs.
        kgo.ConsumeResetOffset(kgo.NewOffset().AtEnd()),

        // Commit Strategy:
        // DisableAutoCommit because payroll is financial.
        // We commit ONLY after the bank API confirms the transfer.
        kgo.DisableAutoCommit(),
    )
    return client, err
}

// RunPayrollConsumer is the main processing loop.
func RunPayrollConsumer(ctx context.Context, client *kgo.Client) {
    defer client.Close()

    for {
        fetches := client.PollFetches(ctx)

        if ctx.Err() != nil {
            log.Println("Context cancelled. Shutting down payroll consumer.")
            return
        }

        if errs := fetches.Errors(); len(errs) > 0 {
            log.Printf("Fetch errors encountered: %v", errs)
        }

        var committed []*kgo.Record

        fetches.EachRecord(func(record *kgo.Record) {
            log.Printf("Processing payroll event at partition=%d offset=%d",
                record.Partition, record.Offset)

            err := executePayrollTransfer(record)
            if err != nil {
                // Do not commit. Push to DLQ for human investigation.
                log.Printf("CRITICAL: Payroll transfer failed: %v. Sending to DLQ.", err)
                sendToDeadLetterQueue(record)
                return
            }

            committed = append(committed, record)
        })

        if len(committed) > 0 {
            if err := client.CommitRecords(ctx, committed...); err != nil {
                log.Printf("Commit failed. Records will be reprocessed on restart: %v", err)
            }
        }
    }
}

func sendToDeadLetterQueue(record *kgo.Record)          {}
```
