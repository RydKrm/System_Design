# Kafka Persistent Consumer — "My Service Was Down, Give Me Everything I Missed"

### _HR360 Edition — How Kafka Holds Your Data Until You're Ready_

---

## The Core Mental Model — Kafka Is Not a Pipe, It's a Warehouse

Before anything else, I need to fix a misunderstanding that almost every new engineer has. They think Kafka is like a network pipe — messages flow through it, and if nobody is listening, the messages just fall on the floor and disappear. That mental model is completely wrong, and that wrong picture is the reason people configure Kafka incorrectly and lose data.

Kafka is a **warehouse with a logbook**. Every message that arrives gets written into the logbook and stored on disk. That message stays there — for hours, days, or even weeks depending on your retention configuration. When your consumer comes back online after being down, it doesn't see an empty warehouse. It walks in, finds its bookmark (the last committed offset), and reads everything that was written after that bookmark, in order, without missing a single entry.

```
THE WAREHOUSE MENTAL MODEL
═══════════════════════════════════════════════════════════════════════

  WRONG PICTURE (pipe model — this is NOT how Kafka works):
  
  Producer ──► [message flows through] ──► Consumer
                         │
               Consumer is offline?
                         │
                         ▼
                  Message DROPPED ✗

  ──────────────────────────────────────────────────────────────────

  CORRECT PICTURE (warehouse model — this IS how Kafka works):
  
  Producer ──► Kafka (writes to disk, keeps it) ◄── messages
                      │
              Consumer is offline?
              No problem. Kafka holds the data.
                      │
                      │  [2 hours later]
                      │
              Consumer comes back online
                      │
                      ▼
              "Where did I stop? Offset 42."
              Reads from 43, 44, 45, 46... all the way to latest.
              Nothing was lost.

═══════════════════════════════════════════════════════════════════════
```

So the question isn't "how do I make Kafka hold my data" — Kafka already does that by design. The real question is: **how do I configure my consumer so that it correctly remembers where it stopped, and correctly resumes from that exact point when it restarts?** That is what this entire guide is about.

## Why Your Consumer Might Miss Data — The Three Failure Modes

Let me walk you through the three specific things that cause a consumer to miss messages when it comes back online. Understanding the failure modes is the only way to understand why each configuration choice matters.

```
THREE WAYS YOUR CONSUMER LOSES DATA
═══════════════════════════════════════════════════════════════════════

  FAILURE MODE 1: Wrong Reset Offset Strategy
  ────────────────────────────────────────────
  Consumer joins for the first time (no saved position yet).
  kgo.ConsumeResetOffset(kgo.NewOffset().AtEnd())  ← set to AtEnd
  
  Result: Consumer ignores all historical messages.
          It only reads new ones from this moment forward.
          Everything that happened while it was "first starting up"
          is gone from its perspective.
          
  Fix: Use AtStart() for services that must not miss any history.

  FAILURE MODE 2: Committing Before Processing
  ─────────────────────────────────────────────
  Consumer polls 100 messages.
  Auto-commit fires at 5 seconds (default behavior).
  Consumer has only processed 40 of those 100 messages.
  Auto-commit tells Kafka: "I'm done up to offset 100."
  Consumer crashes.
  Consumer restarts → resumes from 101.
  Messages 41-100 are NEVER processed.
  
  Fix: Use DisableAutoCommit() + CommitRecords() AFTER database write.

  FAILURE MODE 3: Kafka Retention Expires
  ────────────────────────────────────────
  Your consumer is offline for 8 days.
  Kafka retention is set to 7 days (default on many clusters).
  The messages from days 1-7 are deleted from Kafka.
  Consumer comes back on day 8.
  It tries to resume from its saved offset — but those segments
  are gone. Kafka resets it to the earliest available offset,
  which is day 8's data. Days 1-7 are permanently lost.
  
  Fix: Increase retention. Monitor consumer lag. Alert before
       retention window expires.

═══════════════════════════════════════════════════════════════════════
```

Every configuration we cover below directly addresses one or more of these three failure modes.

## The Full Architecture — What "Persistent Consumer" Actually Means

Let me draw the full picture of what you're building. When I say "persistent consumer," I mean a consumer that participates in a guarantee chain: Kafka holds the data → consumer reads it → consumer writes it to the database → only then does the consumer tell Kafka "I'm done." If anything in that chain breaks — service crash, database timeout, network blip — the consumer restarts, picks up where it left off, and tries again. Nothing falls through.

```
PERSISTENT CONSUMER GUARANTEE CHAIN
═══════════════════════════════════════════════════════════════════════

  KAFKA                   CONSUMER SERVICE             POSTGRESQL
  ──────                  ────────────────             ──────────
  
  topic: hr360.employee.onboarding
  
  [offset 0]  emp-A ──►  read emp-A
  [offset 1]  emp-B      process emp-A
  [offset 2]  emp-C      write emp-A to DB ──────────► INSERT emp-A ✓
  [offset 3]  emp-D      commit offset 1 ◄─ tell kafka done ✓
              emp-E      
              (arriving)  read emp-B
                          process emp-B
                          write emp-B to DB ──────────► INSERT emp-B
                          
  SERVICE CRASHES HERE ✗
  
  [Kafka still holds offset 1 (emp-B) as uncommitted for this group]
  
  SERVICE RESTARTS
                    ▼
                    Resume from offset 1 (emp-B) ← exact point
                    write emp-B to DB ──────────► INSERT emp-B ✓
                    (DB must be idempotent — ON CONFLICT DO NOTHING)
                    commit offset 1 ✓
                    read emp-C...
                    
═══════════════════════════════════════════════════════════════════════
```

Notice the key rule: **you commit the offset only after the database write succeeds**. The database write is the "work." The commit is the receipt. You never issue the receipt before the work is done.

## Part 1 — Kafka-Side Retention: Making Sure Data Survives Your Downtime

Before configuring your Go consumer, you need to make sure Kafka itself is configured to hold data long enough. This is a broker/topic-level configuration, not a consumer configuration. But it's the foundation everything else rests on.

The two settings that matter are `retention.ms` (how long Kafka keeps messages by time) and `retention.bytes` (how much data Kafka keeps by size). When either limit is hit, the oldest data is deleted. Your consumer must come back online before either limit is breached.

```
RETENTION WINDOW — YOUR SAFETY NET
═══════════════════════════════════════════════════════════════════════

  Timeline for topic: hr360.employee.onboarding
  
  Day 0    ──► Messages written (offsets 0 - 5000)
  Day 1    ──► More messages    (offsets 5001 - 12000)
  Day 2    ──► Consumer goes DOWN ✗
  Day 3    ──► Messages written (offsets 12001 - 18000)
  Day 4    ──► Messages written (offsets 18001 - 25000)
  Day 5    ──► Consumer comes back UP ✓
               Resumes from its last committed offset.
               ALL missed messages still in Kafka. Processes them.
  
  ════════ RETENTION BOUNDARY (e.g. 7 days) ════════
  Day 9    ──► Day 0 data starts being deleted
               If consumer was still offline at Day 9,
               it would miss Day 0 data permanently.
  
  Lesson: Your consumer's maximum tolerable downtime must be 
          LESS than your Kafka retention window.

═══════════════════════════════════════════════════════════════════════
```

You set this per-topic using `kafka-configs` or at topic creation time. Here's how you'd configure it for HR360's critical topics to keep data for 14 days:

```bash
# Set retention to 14 days (in milliseconds) for the employee onboarding topic.
# This gives us a comfortable buffer even if the consumer is down for a week.
kafka-configs.sh \
  --bootstrap-server kafka-1:9092 \
  --entity-type topics \
  --entity-name hr360.employee.onboarding \
  --alter \
  --add-config retention.ms=1209600000

# Also set a size cap so a traffic spike doesn't eat all disk space.
# 10GB per topic partition is a reasonable starting point for HR data.
kafka-configs.sh \
  --bootstrap-server kafka-1:9092 \
  --entity-type topics \
  --entity-name hr360.employee.onboarding \
  --alter \
  --add-config retention.bytes=10737418240
```

In your Docker Compose or Kubernetes Kafka deployment, you can set these as default broker-level configs:

```yaml
# docker-compose.yml (Kafka service environment)
environment:
  # Default retention for all topics: 14 days
  KAFKA_LOG_RETENTION_MS: 1209600000
  # Default max size per partition log: 10GB
  KAFKA_LOG_RETENTION_BYTES: 10737418240
  # Check for expired segments every 5 minutes
  KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS: 300000
```

## Part 2 — The Consumer Group: Your Bookmark in Kafka

The consumer group is the mechanism that actually stores your "I read up to here" bookmark. When your consumer commits an offset, Kafka writes that offset into a special internal topic called `__consumer_offsets`. This topic is how Kafka remembers where your consumer was, even across restarts, crashes, and service downtime.

```
HOW __consumer_offsets WORKS AS YOUR BOOKMARK
═══════════════════════════════════════════════════════════════════════

  Your consumer group: "hr360-onboarding-db-writer"
  
  Kafka internal topic: __consumer_offsets
  ┌─────────────────────────────────────────────────────────────────┐
  │  group: hr360-onboarding-db-writer                              │
  │  topic: hr360.employee.onboarding                               │
  │  ┌──────────────┬──────────────┬──────────────┬──────────────┐  │
  │  │  Partition 0 │  Partition 1 │  Partition 2 │  Partition 3 │  │
  │  │  offset: 482 │  offset: 391 │  offset: 510 │  offset: 447 │  │
  │  └──────────────┴──────────────┴──────────────┴──────────────┘  │
  └─────────────────────────────────────────────────────────────────┘
  
  Consumer goes offline. Hours pass. Messages arrive.
  Consumer comes back.
  Kafka looks up this bookmark.
  "Group hr360-onboarding-db-writer left off at P0:482, P1:391..."
  Consumer resumes from exactly those offsets.
  Zero data loss.

═══════════════════════════════════════════════════════════════════════
```

```go
package consumer

import (
    "context"
    "database/sql"
    "log"
    "time"

    "github.com/twmb/franz-go/pkg/kgo"
)

func NewPersistentOnboardingConsumer() (*kgo.Client, error) {
    client, err := kgo.NewClient(
        kgo.SeedBrokers("kafka-1:9092", "kafka-2:9092", "kafka-3:9092"),
        kgo.ClientID("hr360-onboarding-db-writer-v1.0"),

        // This group ID is your bookmark identity.
        // Kafka stores your committed offsets under this name.
        // Every instance of this service must use the SAME group ID
        // so they share a single consistent bookmark.
        //
        // If you accidentally change this string (typo, version suffix, etc.),
        // Kafka creates a BRAND NEW bookmark with no history.
        // Your consumer will reset to AtStart or AtEnd and either
        // replay everything or miss everything. Be very careful with this string.
        kgo.ConsumerGroup("hr360-onboarding-db-writer"),

        kgo.ConsumeTopics("hr360.employee.onboarding"),

        // CRITICAL for persistence:
        // When this consumer group has no saved offset yet (first run ever,
        // or the group was deleted), start from the VERY BEGINNING of the topic.
        //
        // This is the "safe default" for a DB writer service. You would rather
        // reprocess some old data (which your DB handles via idempotency)
        // than silently miss employee records that were created before you deployed.
        kgo.ConsumeResetOffset(kgo.NewOffset().AtStart()),

        // CRITICAL for persistence:
        // Turn off auto commit completely.
        // The auto-committer doesn't know if your database write succeeded.
        // It just commits on a timer regardless of what happened.
        // We need to be the one deciding when the work is truly done.
        kgo.DisableAutoCommit(),

        // Cooperative sticky balancer prevents full group pauses during
        // rolling restarts. When one pod restarts, only ITS partitions
        // are briefly paused, not the entire consumer group.
        kgo.Balancers(kgo.CooperativeStickyBalancer()),
    )
    return client, err
}
```

## Part 3 — The Processing Loop: Commit Only After The Database Confirms

This is the heart of the whole system. The loop below implements the guarantee chain I drew earlier: read → process → write to DB → commit. If any step fails, no commit happens. Kafka holds the offset as uncommitted. On restart, the consumer picks it back up.

```
THE GUARANTEE CHAIN INSIDE YOUR PROCESSING LOOP
═══════════════════════════════════════════════════════════════════════

  PollFetches()
       │
       ▼
  For each record:
       │
       ├──► Parse the Kafka message payload
       │
       ├──► Write to PostgreSQL (INSERT ... ON CONFLICT DO NOTHING)
       │         │
       │         ├── Success ──► add record to "committed" slice
       │         │
       │         └── Failure ──► log error, do NOT add to "committed"
       │                         this record stays uncommitted in Kafka
       │                         it will be retried on next poll or restart
       ▼
  CommitRecords(ctx, committed...)
       │
       ├── Success ──► Kafka moves bookmark forward ✓
       │
       └── Failure ──► log error, records will be retried ✓
                       (slightly worse: you might write to DB twice,
                        which is why you MUST have ON CONFLICT in SQL)

═══════════════════════════════════════════════════════════════════════
```

```go
// EmployeeRecord represents what we expect in the Kafka message payload.
type EmployeeRecord struct {
    EmployeeID   string    `json:"employee_id"`
    FullName     string    `json:"full_name"`
    Department   string    `json:"department"`
    StartDate    time.Time `json:"start_date"`
    Email        string    `json:"email"`
}

// RunPersistentConsumer is the main loop. It never exits unless the
// context is cancelled (graceful shutdown signal).
func RunPersistentConsumer(ctx context.Context, client *kgo.Client, db *sql.DB) {
    defer client.Close()

    log.Println("Persistent consumer started. Waiting for records from Kafka...")

    for {
        // PollFetches blocks until either:
        //   a) Records are available from Kafka
        //   b) The context is cancelled (shutdown)
        //
        // When your service was offline, Kafka queued up all uncommitted records.
        // The moment PollFetches() is called after restart, Kafka delivers them all.
        // This first fetch after a long downtime might be very large.
        fetches := client.PollFetches(ctx)

        // If context was cancelled, exit cleanly.
        if ctx.Err() != nil {
            log.Println("Shutdown signal received. Stopping consumer.")
            return
        }

        // Soft errors (e.g., a single partition leader election in progress)
        // are logged but don't stop the whole consumer.
        // PollFetches will retry those partitions automatically.
        if errs := fetches.Errors(); len(errs) > 0 {
            for _, fe := range errs {
                log.Printf("Non-fatal fetch error on topic=%s partition=%d: %v",
                    fe.Topic, fe.Partition, fe.Err)
            }
        }

        // Collect all records that were successfully written to the database.
        // Only these will be committed to Kafka.
        var toCommit []*kgo.Record

        fetches.EachRecord(func(record *kgo.Record) {
            // Parse the JSON payload from the Kafka message.
            employee, err := parseEmployeeRecord(record.Value)
            if err != nil {
                // This is a malformed message. It will never be parseable.
                // We have two choices here:
                //   1. Send to Dead Letter Queue (DLQ) and commit it anyway.
                //   2. Panic and block forever (wrong choice — never do this).
                //
                // We send to DLQ and still commit it, because retrying
                // a permanently broken message will block your consumer forever.
                log.Printf("Malformed message at offset=%d: %v. Routing to DLQ.", record.Offset, err)
                sendToDLQ(record)
                toCommit = append(toCommit, record) // Still commit — it's been handled.
                return
            }

            // Write to PostgreSQL.
            // The SQL uses ON CONFLICT DO NOTHING (shown below).
            // This is what makes your consumer "idempotent" — if Kafka delivers
            // the same message twice (because of a crash before commit), the
            // second DB write simply does nothing. No duplicate rows. No errors.
            err = upsertEmployeeToDatabase(ctx, db, employee)
            if err != nil {
                // Transient DB error — connection lost, timeout, disk full, etc.
                // Do NOT commit. Kafka will redeliver this record when the
                // consumer polls again or after a restart.
                log.Printf(
                    "DB write failed for employee=%s at offset=%d: %v. Will retry.",
                    employee.EmployeeID, record.Offset, err,
                )
                return // Do not add to toCommit
            }

            log.Printf("Successfully persisted employee=%s (offset=%d)",
                employee.EmployeeID, record.Offset)

            // Only add to commit slice after DB write confirmed.
            toCommit = append(toCommit, record)
        })

        // Nothing to commit this round (all records failed DB write).
        // Don't call CommitRecords with an empty slice.
        if len(toCommit) == 0 {
            continue
        }

        // Commit only the successfully processed records.
        // CommitRecords is synchronous — it waits for the broker to
        // acknowledge the commit before returning.
        //
        // This is the moment the bookmark moves forward in Kafka.
        // If this fails, the bookmark doesn't move. Records get retried.
        if err := client.CommitRecords(ctx, toCommit...); err != nil {
            log.Printf(
                "Offset commit failed for %d records: %v. They will be reprocessed on restart.",
                len(toCommit), err,
            )
            // Note: the DB rows for these records were already written.
            // When they're reprocessed, the ON CONFLICT clause handles duplicates.
        }
    }
}
```

## Part 4 — The Database Layer: Idempotency Is Non-Negotiable

There is a rule you must burn into your memory: **if your Kafka consumer can retry a message, your database write must be idempotent**. Idempotent means "doing it twice has the same result as doing it once." Without this, every retry creates a duplicate row.

Why will Kafka retry? Because of the exact guarantee you're building. If the DB write succeeds but the commit fails (network blip to the broker), on restart Kafka delivers the same message again. Your code will try to write the same employee to the database again. If you used a plain `INSERT`, you get a duplicate key error and your consumer crashes in a loop. If you used `INSERT ... ON CONFLICT DO NOTHING`, the second write silently succeeds without creating a duplicate. The consumer moves on.

```
IDEMPOTENCY — WHY YOU NEED ON CONFLICT
═══════════════════════════════════════════════════════════════════════

  Scenario: DB write succeeded, but commit to Kafka failed.
  
  Restart → Kafka redelivers the same record
                │
                ▼
  WITHOUT idempotency:
  INSERT INTO employees (id, name) VALUES ('E-001', 'Alice')
  ──► ERROR: duplicate key value violates unique constraint "employees_pkey"
  ──► Consumer crashes
  ──► Restarts again
  ──► Same error
  ──► Infinite crash loop ✗
  
  WITH idempotency (ON CONFLICT DO NOTHING):
  INSERT INTO employees (id, name) VALUES ('E-001', 'Alice')
  ON CONFLICT (employee_id) DO NOTHING
  ──► Query runs, finds conflict, skips the insert silently
  ──► Returns success (0 rows affected, but no error)
  ──► Consumer commits offset and moves on ✓

═══════════════════════════════════════════════════════════════════════
```

```go
import (
    "context"
    "database/sql"
    "encoding/json"
    "fmt"
    "log"

    "github.com/twmb/franz-go/pkg/kgo"
)

// upsertEmployeeToDatabase writes the employee record to PostgreSQL.
// The ON CONFLICT clause makes this safe to call multiple times
// with the same employee_id — only the first call inserts, the rest are no-ops.
func upsertEmployeeToDatabase(ctx context.Context, db *sql.DB, emp *EmployeeRecord) error {
    query := `
        INSERT INTO employees (
            employee_id,
            full_name,
            department,
            start_date,
            email,
            created_at
        ) VALUES ($1, $2, $3, $4, $5, NOW())
        
        -- ON CONFLICT means: if a row with this employee_id already exists,
        -- do absolutely nothing. No error. No update. Just skip it silently.
        -- This is what makes your consumer safe to retry.
        ON CONFLICT (employee_id) DO NOTHING
    `

    _, err := db.ExecContext(ctx, query,
        emp.EmployeeID,
        emp.FullName,
        emp.Department,
        emp.StartDate,
        emp.Email,
    )
    if err != nil {
        return fmt.Errorf("failed to upsert employee %s: %w", emp.EmployeeID, err)
    }

    return nil
}

// parseEmployeeRecord deserializes the Kafka message bytes into an EmployeeRecord struct.
func parseEmployeeRecord(data []byte) (*EmployeeRecord, error) {
    var emp EmployeeRecord
    if err := json.Unmarshal(data, &emp); err != nil {
        return nil, fmt.Errorf("JSON parse error: %w", err)
    }
    if emp.EmployeeID == "" {
        return nil, fmt.Errorf("invalid record: employee_id is empty")
    }
    return &emp, nil
}

// sendToDLQ sends a malformed or permanently-failed record to
// a separate Dead Letter Queue topic for human inspection.
func sendToDLQ(record *kgo.Record) {
    // In a real system, you'd publish this to a "hr360.employee.onboarding.dlq"
    // Kafka topic using a producer client. For now, we log it.
    log.Printf("DLQ: topic=%s partition=%d offset=%d key=%s",
        record.Topic, record.Partition, record.Offset, string(record.Key))
}
```

## Part 5 — Handling the Restart Surge: What Happens After Long Downtime

After your service has been down for several hours, the moment it restarts and polls Kafka, it will receive a potentially enormous backlog of messages — all at once. This is the "catch-up" phase. You need to handle it gracefully rather than hammering the database with thousands of individual inserts.

```
THE CATCH-UP SURGE AFTER LONG DOWNTIME
═══════════════════════════════════════════════════════════════════════

  Service was offline for 4 hours.
  4000 employee records arrived during that time.
  
  Service restarts.
  
  PollFetches() returns:
  ┌──────────────────────────────────────────────────────────────┐
  │  Fetch batch 1: 500 records  (Kafka default max per fetch)  │
  │  Fetch batch 2: 500 records                                  │
  │  ...                                                         │
  │  Fetch batch 8: 500 records  (all 4000 records, 8 batches)  │
  └──────────────────────────────────────────────────────────────┘
  
  Each batch: process all records → batch insert to DB → commit.
  
  Time to catch up: depends on your DB write speed.
  A single DB connection doing individual INSERTs: ~4000 round-trips.
  A batch INSERT (VALUES $1, $2, ... $500): 8 round-trips total.
  
  Batch inserting is 500x faster for the catch-up phase.

═══════════════════════════════════════════════════════════════════════
```

```go
// RunPersistentConsumerWithBatchInsert is the production-grade version
// that uses batch inserts for efficient catch-up after long downtime.
func RunPersistentConsumerWithBatchInsert(ctx context.Context, client *kgo.Client, db *sql.DB) {
    defer client.Close()

    for {
        fetches := client.PollFetches(ctx)

        if ctx.Err() != nil {
            log.Println("Shutdown signal. Exiting.")
            return
        }

        // Collect all records from this fetch batch.
        // A single PollFetches call can return records from multiple
        // partitions and topics, all bundled together.
        var employees []*EmployeeRecord
        var allRecords []*kgo.Record
        var malformed []*kgo.Record

        fetches.EachRecord(func(record *kgo.Record) {
            emp, err := parseEmployeeRecord(record.Value)
            if err != nil {
                log.Printf("Malformed record at offset=%d, routing to DLQ", record.Offset)
                malformed = append(malformed, record)
                return
            }
            employees = append(employees, emp)
            allRecords = append(allRecords, record)
        })

        // Handle malformed records: send to DLQ and commit them.
        // We don't want bad messages blocking the whole pipeline.
        if len(malformed) > 0 {
            for _, r := range malformed {
                sendToDLQ(r)
            }
            // Commit the malformed ones separately.
            // They've been "handled" (routed to DLQ), so we move past them.
            if err := client.CommitRecords(ctx, malformed...); err != nil {
                log.Printf("Failed to commit DLQ records: %v", err)
            }
        }

        if len(employees) == 0 {
            continue
        }

        // Batch insert all valid employees in a single SQL transaction.
        // This is dramatically faster than inserting one by one,
        // especially during the initial catch-up surge.
        if err := batchUpsertEmployees(ctx, db, employees); err != nil {
            log.Printf(
                "Batch insert failed for %d records: %v. Will retry entire batch on next poll.",
                len(employees), err,
            )
            // Do not commit. The entire batch will be retried.
            // Individual records that already succeeded will be
            // handled by ON CONFLICT DO NOTHING on retry.
            continue
        }

        log.Printf("Batch persisted %d employee records to database.", len(employees))

        // Commit all successfully written records in one shot.
        if err := client.CommitRecords(ctx, allRecords...); err != nil {
            log.Printf("Commit failed for %d records: %v. Batch will be retried.", len(allRecords), err)
        }
    }
}

// batchUpsertEmployees inserts multiple employee records in a single
// PostgreSQL transaction, using unnest() for efficient batch insertion.
func batchUpsertEmployees(ctx context.Context, db *sql.DB, employees []*EmployeeRecord) error {
    if len(employees) == 0 {
        return nil
    }

    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return fmt.Errorf("failed to begin transaction: %w", err)
    }
    defer tx.Rollback() // No-op if Commit() already called.

    // Use PostgreSQL unnest() to insert an entire slice in one query.
    // This is the fastest way to bulk insert in PostgreSQL from Go.
    ids := make([]string, len(employees))
    names := make([]string, len(employees))
    departments := make([]string, len(employees))
    emails := make([]string, len(employees))

    for i, emp := range employees {
        ids[i] = emp.EmployeeID
        names[i] = emp.FullName
        departments[i] = emp.Department
        emails[i] = emp.Email
    }

    _, err = tx.ExecContext(ctx, `
        INSERT INTO employees (employee_id, full_name, department, email, created_at)
        SELECT
            unnest($1::text[]),
            unnest($2::text[]),
            unnest($3::text[]),
            unnest($4::text[]),
            NOW()
        ON CONFLICT (employee_id) DO NOTHING
    `, ids, names, departments, emails)

    if err != nil {
        return fmt.Errorf("batch insert failed: %w", err)
    }

    return tx.Commit()
}
```

## Part 6 — Graceful Shutdown: Don't Cut the Wire Mid-Sentence

One of the most common causes of data inconsistency is an ungraceful shutdown. When your Kubernetes pod gets a `SIGTERM` signal to shut down, your consumer might be in the middle of a database write. If you just kill the process instantly, you leave the database in a half-written state and the Kafka offset uncommitted.

The fix is to listen for the OS shutdown signal, cancel the context, and let the current processing loop iteration finish naturally before the process exits.

```
GRACEFUL vs UNGRACEFUL SHUTDOWN
═══════════════════════════════════════════════════════════════════════

  UNGRACEFUL (process killed mid-processing):
  
  OS sends SIGTERM
  Process killed instantly ✗
  
  State:
  ├── DB: employees E-101 to E-150 written (half the batch)
  ├── DB: employees E-151 to E-200 NOT written
  └── Kafka: offset NOT committed (good! but we lost half the batch)
  
  On restart: E-101 to E-150 are retried (ON CONFLICT handles them).
              E-151 to E-200 are retried and written. All good eventually.
              But there was an inconsistent window.

  ──────────────────────────────────────────────────────────────────

  GRACEFUL (context cancelled, loop finishes current iteration):
  
  OS sends SIGTERM
  Context cancelled
  PollFetches(ctx) returns immediately with ctx.Err() != nil
  Current batch (if any) finishes its DB write and commit.
  Process exits cleanly. ✓
  
  State:
  ├── DB: all processed records written
  └── Kafka: offset committed for all written records

═══════════════════════════════════════════════════════════════════════
```

```go
package main

import (
    "context"
    "database/sql"
    "log"
    "os"
    "os/signal"
    "syscall"
    "time"

    _ "github.com/lib/pq" // PostgreSQL driver
)

func main() {
    // --- Database Connection ---
    db, err := sql.Open("postgres", os.Getenv("DATABASE_URL"))
    if err != nil {
        log.Fatal("Failed to connect to database:", err)
    }
    defer db.Close()

    // Set connection pool limits appropriate for a Kafka consumer.
    // You're not doing thousands of concurrent queries; you're doing
    // sequential batches. A small pool is fine.
    db.SetMaxOpenConns(5)
    db.SetMaxIdleConns(3)
    db.SetConnMaxLifetime(30 * time.Minute)

    // --- Kafka Consumer ---
    client, err := NewPersistentOnboardingConsumer()
    if err != nil {
        log.Fatal("Failed to create Kafka consumer:", err)
    }

    // --- Graceful Shutdown Setup ---
    // Create a context that gets cancelled when the OS sends SIGTERM or SIGINT.
    // Pass this context into PollFetches. When it's cancelled, PollFetches
    // returns immediately with a context.Canceled error, and the loop exits.
    ctx, cancel := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
    defer cancel()

    log.Println("HR360 Onboarding DB Writer started. Listening for employee events...")

    // Start the persistent consumer loop.
    // This blocks until the context is cancelled.
    RunPersistentConsumerWithBatchInsert(ctx, client, db)

    log.Println("Consumer shut down cleanly.")
}
```

## The Five Rules of a Persistent Consumer

Think of these as the five laws. Break any one of them and your persistence guarantee falls apart.

```
THE FIVE LAWS OF A PERSISTENT CONSUMER
═══════════════════════════════════════════════════════════════════════

  LAW 1: Kafka retention must be LONGER than your max tolerable downtime.
         If Kafka deletes messages before you come back, nothing saves you.
         Set retention.ms to at least 14 days for critical topics.

  LAW 2: NEVER commit before the database write succeeds.
         Use DisableAutoCommit(). Only call CommitRecords() AFTER
         db.ExecContext() returns nil error.

  LAW 3: ALWAYS use ON CONFLICT in your SQL.
         Kafka will redeliver messages when you retry. Your DB must be
         able to receive the same message twice without creating duplicates.

  LAW 4: Handle malformed messages via DLQ and commit them.
         A message you cannot parse will never become parseable.
         Retrying it forever blocks your entire partition. Route bad
         messages to a DLQ topic and commit past them.

  LAW 5: ConsumeResetOffset(AtStart()) for DB-writer consumers.
         If your bookmark expires or is deleted, you want to replay
         history, not silently skip it. A DB with ON CONFLICT handles
         duplicates. A DB missing records cannot fix itself.

═══════════════════════════════════════════════════════════════════════
```

This is the architecture that makes HR360's data layer bulletproof. The data flows from events into Kafka, Kafka holds it safely, your consumer picks it up in order no matter how long it was offline, and every record lands in PostgreSQL exactly once. That's the guarantee.
