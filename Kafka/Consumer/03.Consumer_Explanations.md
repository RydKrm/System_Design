## First, The Big Picture — What This Code Is Doing

Before I explain a single line, you need to understand the shape of this entire file. What you've built here is a **Handler Registry Pattern** on top of Kafka. Let me explain what that means.

The naive way to build a Kafka consumer is to write one consumer per topic. One Go service listens to `employee.created`, another listens to `leave.approved`, another listens to `payroll.processed`. Three topics, three separate consumer clients, three sets of connection config to maintain. As HR360 grows to 30 topics, you have 30 consumer clients. That's a maintenance nightmare.

The Handler Registry Pattern solves this by separating two concerns: the **infrastructure** (connecting to Kafka, polling, committing, handling errors) and the **business logic** (what to do with a specific message). You write the infrastructure once in `GroupConsumer`, and then you just plug in handlers for each topic like sockets into a power strip.

```
HANDLER REGISTRY PATTERN — THE ARCHITECTURE
═══════════════════════════════════════════════════════════════════════

  NAIVE APPROACH (one consumer per topic — do not do this):

  EmployeeConsumer ──► Kafka ──► topic: employee.created
  LeaveConsumer    ──► Kafka ──► topic: leave.approved
  PayrollConsumer  ──► Kafka ──► topic: payroll.processed

  Problems:
  ├── 3 separate Kafka connections
  ├── 3 separate poll loops
  ├── 3 separate commit strategies
  └── 30 topics = 30 consumers to maintain

  ──────────────────────────────────────────────────────────────────

  HANDLER REGISTRY APPROACH (your code — do this):

  ONE GroupConsumer
  ├── ONE Kafka connection
  ├── ONE poll loop
  ├── ONE commit strategy
  └── handlers map:
       "employee.created"   ──► handleEmployeeCreated()
       "leave.approved"     ──► handleLeaveApproved()
       "payroll.processed"  ──► handlePayrollProcessed()

  Benefits:
  ├── 1 connection, 30 handlers — same infrastructure
  ├── Add a new topic? Just RegisterHandler(). Done.
  └── Change commit strategy? Fix it in ONE place.

═══════════════════════════════════════════════════════════════════════
```

Now let's go through the code structure from the top.

## The Type Definitions

```go
type MessageHandler func(topic, key, request_id string, value []byte) error
```

This single line is actually the most important design decision in the entire file. `MessageHandler` is a function type. It defines the "contract" that every business-logic handler must follow. Every handler that plugs into this consumer — whether it handles employee onboarding, leave approvals, or payroll runs — must accept these exact four arguments and return an error.

Why these four arguments specifically?

`topic` — because you might register the same function for multiple related topics (e.g., one handler processes both `employee.created` and `employee.updated`), and the function needs to know which topic triggered it to branch its logic.

`key` — Kafka message keys carry identity information. In HR360, the key is typically the `employee_id`. Your handler uses this to look up the employee in the database without having to parse the full JSON body first.

`request_id` — this is for distributed tracing. When a REST call hits your Employee Service and it publishes a Kafka event, it attaches the original HTTP request ID as a header. Your handler receives it here and passes it through to downstream calls, so your Grafana traces show the full chain from HTTP request → Kafka event → database write.

`value []byte` — the raw message body. Your handler decides how to deserialize it (JSON, Protobuf, whatever). The consumer doesn't need to know.

The `error` return is the contract for retry behavior. Return `nil` → commit. Return `error` → do not commit, redeliver. Simple, clean, and enforced by the type system.

```go
type GroupConsumer struct {
    client      *kgo.Client
    serviceName string
    handlers    map[string]MessageHandler
    mu          sync.RWMutex
}
```

`client` is the underlying franz-go client. Only one. All topics share it.

`serviceName` is pulled from config. It gets prefixed to every log line so when you're staring at a wall of logs from 12 services, you can grep for `[hr360-employee-service]` and see only that service's consumer logs.

`handlers` is the registry itself. The map key is the topic name. The value is the `MessageHandler` function. This is the power strip.

`mu sync.RWMutex` — this is here because `RegisterHandler` might be called from a different goroutine than `Start`. For example, you might spin up the consumer in `main()`, pass it to multiple service initializers, and each initializer calls `RegisterHandler` concurrently. Without the mutex, two concurrent writes to the map would be a data race. The Go race detector would catch this and your service would crash in production. The `RWMutex` allows many concurrent readers (the poll loop reads the map constantly) while blocking when a write is happening (a new handler is being registered).

## `NewGroupConsumer` — The Constructor

```go
func NewGroupConsumer(groupID string, topics ...string) (*GroupConsumer, error) {
```

`groupID` and `topics` are the two things that change between different consumers in HR360. Everything else — the broker addresses, TLS config, session timeouts — lives in the shared config. This makes the constructor clean to call from any service.

```go
cfg, err := config.LoadConfig()
```

Config is loaded here, not passed in as arguments. This is a deliberate choice. If you passed broker addresses and service names as function arguments, every caller would need to know about them. By loading from config inside the constructor, callers only need to know what's unique to them: the group ID and the topics they care about.

```go
brokers_list := strings.Split(brokers, ",")
```

Your environment variable `KAFKA_BROKER` is a comma-separated string: `"kafka-1:9092,kafka-2:9092,kafka-3:9092"`. `strings.Split` turns it into the `[]string` that `kgo.SeedBrokers` expects. This is the standard twelve-factor app pattern for passing lists through environment variables.

```go
gc := &GroupConsumer{
    serviceName: service_name,
    handlers:    make(map[string]MessageHandler),
}
```

Notice the `client` field is NOT set here. It gets set after the `kgo.NewClient` call succeeds. This is intentional defensive programming — you don't want a `GroupConsumer` struct floating around with a half-initialized client if something goes wrong during construction.

## The `kgo.NewClient` Options — Each One Examined

Now we get to the heart of the constructor. Let me go through each option you passed and explain exactly why it exists.

```go
kgo.SeedBrokers(brokers_list...),
```

The entry point into the Kafka cluster. The `...` unpacks the slice into variadic arguments. Franz-go connects to the first available broker, fetches cluster metadata, and discovers all other brokers. You need at least two in the list so startup succeeds even if one broker is temporarily down.

```go
kgo.ClientID(service_name + "-consumer"),
```

In HR360's Grafana dashboards, the Kafka overview panel shows all connected clients. Without this, every consumer shows up as `"kgo"`. With this, you see `"hr360-employee-service-consumer"`, `"hr360-payroll-service-consumer"`, and so on. When a consumer is causing excessive lag or connection churn, you know exactly which service to look at.

```go
kgo.ConsumerGroup(groupID),
```

This is your bookmark identity in Kafka's `__consumer_offsets` internal topic. For HR360's employee service, you'd pass `"hr360-employee-service-group"`. That string is the key under which Kafka stores your committed offsets. If you restart, crash, or scale to five pods, every instance uses this same group ID, and Kafka knows they're all part of the same collective consumer. If you ever accidentally change this string, Kafka creates a fresh bookmark with no history and your reset offset strategy kicks in.

```go
kgo.ConsumeTopics(topics...),
```

The topics this consumer will read. Kafka will partition-assign these topics among all members of the consumer group. If you have four partitions and two pods, each pod gets two partitions. If you scale to four pods, each pod gets one partition. The assignment is handled automatically by the balancer.

```go
kgo.ConsumeResetOffset(kgo.NewOffset().AtEnd()),
```

This is the fallback offset for when no committed offset exists yet. You've set it to `AtEnd()`, which means: "on first run, ignore all historical messages, only process new ones from this moment forward." This is the right choice for most live services that are being deployed fresh — you don't want to replay weeks of old HR events when the notification service boots up for the first time. The important thing to understand is that this only fires when there is genuinely no committed offset. After the first successful commit, this setting is irrelevant and your real committed offsets take over.

```go
kgo.DisableAutoCommit(),
```

This is the safety pin. Without it, franz-go would commit offsets on a 5-second timer, regardless of whether your handler actually succeeded. Your handler might fail, the auto-committer fires, Kafka moves the bookmark forward, and the failed message is never retried. With `DisableAutoCommit`, YOU decide when to commit: specifically, after `handler()` returns `nil` and you've called `MarkCommitRecords`. The only way an offset gets committed in your code is if the entire processing chain succeeds.

```go
DialerOpt(brokers_list),
```

This is a custom function you've written (not shown in the snippet, but it presumably sets up TLS based on whether the broker addresses use `9093` or similar). This is where you'd apply `kgo.DialTLSConfig()` for encrypted broker connections in staging and production. In development against a local Docker Compose Kafka, this would be a no-op dialer.

## `OnPartitionsRevoked` — The Safety Net During Rebalances

```go
kgo.OnPartitionsRevoked(func(ctx context.Context, client *kgo.Client, assigned map[string][]int32) {
    log.Printf("[%s] Partitions being revoked: %v — committing offsets",
        service_name, assigned)
    if err := client.CommitUncommittedOffsets(ctx); err != nil {
        log.Printf("[%s] Commit on revoke failed: %v",
            service_name, err)
    }
}),
```

This is one of the most important callbacks in your entire setup and I want you to really understand what it guards against.

A rebalance happens whenever the consumer group membership changes — a pod scales up, a pod restarts, the `SessionTimeout` expires. During a rebalance, Kafka takes partitions away from some consumers and gives them to others. This is the "revoke" event: Kafka is saying "I'm about to take Partition 2 from you. Anything you haven't committed yet on Partition 2 will be given to a different consumer to re-process."

```
WHAT HAPPENS WITHOUT OnPartitionsRevoked
═══════════════════════════════════════════════════════════════════════

  Pod A owns Partition 2.
  Pod A processed messages at offsets 100, 101, 102.
  Pod A called MarkCommitRecords for all three.
  BUT CommitMarkedOffsets hasn't fired yet (it runs at end of poll loop).

  Rebalance triggered. Partition 2 is being moved to Pod B.
  
  WITHOUT the revoke callback:
  ├── Pod A never commits offsets 100, 101, 102
  ├── Pod B receives Partition 2 starting from offset 100
  └── Messages 100, 101, 102 are processed AGAIN by Pod B
      (If your handler is not idempotent, this causes duplicates.)

  WITH the revoke callback:
  ├── Before handing over Partition 2, Pod A calls CommitUncommittedOffsets
  ├── Offsets 100, 101, 102 are committed to Kafka
  ├── Pod B receives Partition 2 starting from offset 103
  └── No duplicates. Clean handoff.

═══════════════════════════════════════════════════════════════════════
```

`CommitUncommittedOffsets` (as opposed to `CommitMarkedOffsets`) commits everything that has been marked via `MarkCommitRecords`, even if the regular end-of-loop commit hasn't fired yet. It's a "flush everything before we lose these partitions" call.

## Session Timeout, Heartbeat, and Rebalance Timeout — The Heartbeat Triangle

These three options work together and you need to understand the relationship between them, because setting them incorrectly causes phantom rebalances that interrupt your consumers for no reason.

```go
kgo.SessionTimeout(45 * time.Second),
kgo.HeartbeatInterval(3 * time.Second),
kgo.RebalanceTimeout(60 * time.Second),
```

```
THE HEARTBEAT TRIANGLE
═══════════════════════════════════════════════════════════════════════

  HeartbeatInterval = 3s
  │
  │  Consumer sends heartbeat to Kafka group coordinator every 3 seconds.
  │  Heartbeat says: "I'm alive. Don't kick me out."
  │
  └──► Kafka receives heartbeat ──► resets the session timer

  SessionTimeout = 45s
  │
  │  If Kafka receives NO heartbeat for 45 seconds, it declares
  │  this consumer dead and triggers a rebalance to redistribute
  │  its partitions to other members.
  │
  └──► No heartbeat for 45s ──► "Consumer is dead" ──► rebalance

  RebalanceTimeout = 60s
  │
  │  Once a rebalance starts, every consumer in the group has
  │  60 seconds to finish processing its current messages,
  │  call OnPartitionsRevoked, and rejoin the group.
  │  After 60 seconds, anyone who hasn't rejoined is removed.
  │
  └──► Rebalance starts ──► 60s window to complete and rejoin

  THE RELATIONSHIP (must always hold true):
  HeartbeatInterval < SessionTimeout < RebalanceTimeout
       3s           <      45s       <      60s        ✓

═══════════════════════════════════════════════════════════════════════
```

Why 45 seconds for `SessionTimeout`? Because in HR360, some handlers do database writes that might take a few seconds under load. If `SessionTimeout` were too short — say, 10 seconds — a slow database response during a busy period would cause the heartbeat goroutine to miss enough beats that Kafka declares the consumer dead and triggers a rebalance. With 45 seconds, you have a comfortable buffer. The consumer can be "slow" for up to 45 seconds before Kafka gives up on it.

Why 3 seconds for `HeartbeatInterval`? It should be roughly `SessionTimeout / 3`. This gives you multiple heartbeat attempts within the session window. If one heartbeat packet is lost on the network, the next one arrives 3 seconds later, well within the 45-second window. You don't fail because of a single dropped packet.

Why 60 seconds for `RebalanceTimeout`? It must be longer than `SessionTimeout`. During a rebalance, your `OnPartitionsRevoked` callback commits offsets. If that commit is slow (broker is under load), you need enough time to finish before Kafka kicks you out of the group. 60 seconds is a generous, safe value.

## The Ping Call — Fail Fast at Startup

```go
pingCtx := context.Background()
if err := client.Ping(pingCtx); err != nil {
    client.Close()
    return nil, fmt.Errorf("[%s] Kafka unreachable: %w", service_name, err)
}
```

This is a "fail fast" pattern. `Ping` sends a metadata request to the broker and waits for a response. If Kafka is down, misconfigured, or the wrong address is in your environment variables, your service fails immediately at startup with a clear error message instead of silently starting and producing mysterious "no records" behavior for the next 10 minutes while someone wonders why no events are being processed.

Notice the commented-out code above it:

```go
// pingCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
// defer cancel()
```

You've left this commented out and used `context.Background()` instead. The timeout version was safer — it prevents the ping from hanging forever if the broker is unreachable but not actively refusing connections (e.g., a firewall drops packets silently). I'd recommend uncommenting the timeout version in production. A 10-second timeout is reasonable: if Kafka hasn't responded in 10 seconds, something is seriously wrong and you should fail now.

If the ping fails, you call `client.Close()` before returning the error. This is important — the client might have already opened a TCP connection to the broker before the ping failed. Closing it releases that connection. Without this, you'd leak an open file descriptor every time the service tries and fails to start.

## `RegisterHandler` — Plugging In Business Logic

```go
func (gc *GroupConsumer) RegisterHandler(topic string, h MessageHandler) {
    if gc == nil {
        log.Printf(" Consumer is nil cannot register handler ")
        return
    }

    gc.mu.Lock()
    defer gc.mu.Unlock()
    gc.handlers[topic] = h
    log.Printf("[%s] Handler registered for topic: %s", gc.serviceName, topic)
}
```

The nil check at the top is a defensive guard. If `NewGroupConsumer` returned an error and the caller didn't check, `gc` might be nil when `RegisterHandler` is called. Without this check, you'd get a nil pointer dereference panic. With it, you get a log message that makes the bug obvious.

`gc.mu.Lock()` acquires the write lock. This blocks if any goroutine is currently reading the map (the poll loop holds a read lock while looking up handlers). Once all readers are done, the write proceeds. `defer gc.mu.Unlock()` releases the lock when the function exits, even if it panics.

`gc.handlers[topic] = h` — this map write is why you need the lock. Go's built-in map is not concurrency-safe. Concurrent reads are fine, but a concurrent read and write (or two concurrent writes) causes a panic with "concurrent map read and map write."

The log line at the end is your confirmation that the handler was registered. In your service's startup logs, you'll see a clean list of all registered topics, which makes it easy to verify that your service is configured correctly before it starts consuming.

## `Start` — The Poll Loop, Explained Piece by Piece

```go
func (gc *GroupConsumer) Start(ctx context.Context) error {
    log.Printf("[%s] 👂 Poll loop started", gc.serviceName)
```

`Start` takes a `context.Context`. This is how you control the consumer's lifecycle from outside. When your main function receives `SIGTERM`, it calls `cancel()` on this context. `PollFetches` returns immediately, `ctx.Err()` is non-nil, and the loop exits cleanly. This is your graceful shutdown mechanism.

```go
fetches := gc.client.PollFetches(ctx)
```

`PollFetches` is a blocking call. It asks Kafka for the next batch of records. If there are records available, it returns them immediately. If there are none, it waits. This is not busy-polling — it doesn't spin the CPU while waiting. It blocks at the network level until Kafka has something to deliver. When your context is cancelled, the block is released and it returns with whatever it has (possibly zero records).

```go
if ctx.Err() != nil {
    log.Printf("[%s] Context cancelled, stopping poll loop: %v",
        gc.serviceName, ctx.Err())
    return nil
}
```

This is the first check after every `PollFetches`. You check the context first — before checking records — because even if `PollFetches` returned some records, you don't want to process them if you're shutting down. Processing messages during shutdown might not complete cleanly. Better to leave them uncommitted and let the next startup handle them.

```go
if fetches.IsClientClosed() {
    log.Printf("[%s] Client closed, poll loop exiting", gc.serviceName)
    return nil
}
```

`IsClientClosed` returns true if someone called `gc.client.Close()` externally. This handles the case where the client is closed through a code path other than context cancellation (e.g., a forced shutdown function). Without this check, the next `PollFetches` call on a closed client would panic.

```go
if errs := fetches.Errors(); len(errs) > 0 {
    for _, e := range errs {
        fmt.Println(" Fetch error ", " Topic - ", e.Topic, " Partition - ", e.Partition, " Error - ", e.Err)
    }
}
```

Fetch errors are per-partition, not per-consumer. A single `PollFetches` call might return records from partitions 0, 1, and 2 successfully, but partition 3 had a leader election happening and returned an error. The error handling here logs the bad partition but doesn't abort the whole loop. The good partitions' records are still processed. Franz-go will retry the failed partition automatically on the next poll.

One thing to improve here: these are currently `fmt.Println` instead of `log.Printf`. In production, you'd want `log.Printf` with the service name prefix so these errors appear in your structured log aggregator (Grafana Loki, CloudWatch, etc.) with the same format as all your other log lines.

## `fetches.EachRecord` — The Handler Dispatch

```go
fetches.EachRecord(func(record *kgo.Record) {
    gc.mu.RLock()
    handler, exists := gc.handlers[record.Topic]
    gc.mu.RUnlock()
```

`RLock` is a read lock. Multiple goroutines can hold a read lock simultaneously — so if you ever parallelize this loop, multiple goroutines can look up handlers concurrently without blocking each other. The read lock only blocks when a write lock is held (i.e., when `RegisterHandler` is being called). In steady state, `RegisterHandler` is called once at startup and never again, so the read lock is essentially free.

```go
if !exists {
    log.Printf("[%s] No handler for topic %s — skipping",
        gc.serviceName, record.Topic)
    gc.client.MarkCommitRecords(record)
    return
}
```

This is a critical design choice. If a message arrives on a topic you haven't registered a handler for, you still mark it as committed. Why? Because if you don't commit it, Kafka will redeliver it every time the consumer restarts, forever. Since you have no handler for it, it would queue up indefinitely, causing your consumer lag metric to grow without bound. Marking it committed acknowledges "yes, we saw this, we chose to ignore it." The log line gives you visibility so you know this is happening.

## Header Extraction — The Distributed Tracing Bridge

```go
headers := record.Headers
meta := map[string]string{}
for _, header := range headers {
    meta[header.Key] = string(header.Value)
}
// Map key aliases
if reqID, ok := meta["request-id"]; ok {
    meta["x-request-id"] = reqID
} else if reqID, ok := meta["x-request-id"]; ok {
    meta["request-id"] = reqID
}

metaJSON, _ := json.Marshal(meta)
requestID := string(metaJSON)
```

Kafka message headers are key-value pairs attached to a message, separate from the message body. In HR360, when the Employee Service publishes a `employee.created` event, it attaches the original HTTP request's trace ID as a header. This is how you connect a Kafka event back to the HTTP request that caused it in your Grafana traces.

The alias mapping (`request-id` ↔ `x-request-id`) is a compatibility shim. Your HTTP middleware probably uses `x-request-id` (the HTTP standard), but your internal Kafka producers might use `request-id` (shorter, internal convention). Rather than enforcing one convention and breaking the other, you normalize both directions into a single map. Any handler can use either key.

The entire meta map is then JSON-serialized and passed as the `request_id` argument to your handler. This is a slightly unusual choice — you're passing a JSON string instead of just a single ID. The upside is that your handlers receive all metadata in one argument and can extract whatever they need. The downside is that every handler has to parse the JSON. Alternatively, you could pass `meta map[string]string` directly as the fourth argument, which would be more ergonomic.

## The Commit Strategy — Mark First, Commit in Bulk

```go
if err := handler(record.Topic, string(record.Key), requestID, record.Value); err != nil {
    log.Printf("[%s]  Handler error topic=%s key=%s: %v "+
        "— will be redelivered",
        gc.serviceName, record.Topic, string(record.Key), err)
    return
}
gc.client.MarkCommitRecords(record)
```

The handler error branch returns without marking. `MarkCommitRecords` is never called. When `CommitMarkedOffsets` runs at the end of the loop, this offset is not included. Kafka keeps the bookmark behind this offset. On the next poll, Kafka redelivers this message. This is your at-least-once delivery guarantee.

`MarkCommitRecords` is an in-memory operation. It just sets a flag on the record. No network call. No latency. The actual network commit happens once, in bulk, at the end of the loop.

```go
if err := gc.client.CommitMarkedOffsets(ctx); err != nil {
    log.Printf("[%s] Commit error: %v", gc.serviceName, err)
}
```

After processing every record in the batch, commit all the marked ones in a single network call. This is dramatically more efficient than committing after every individual record. Instead of 500 network round-trips for 500 records, you make one round-trip for the entire batch.

Notice this is not the same as `CommitUncommittedOffsets` in the revoke callback. `CommitMarkedOffsets` only commits what you explicitly marked. `CommitUncommittedOffsets` commits everything that has been marked and not yet committed to the broker. They serve different purposes:

```
CommitMarkedOffsets    — regular end-of-batch commit: "commit what we just processed"
CommitUncommittedOffsets — emergency flush on revoke: "commit everything before we lose these partitions"
```

## A Full HR360 Example — Wiring It All Together

This is how you'd actually use this `GroupConsumer` in your HR360 notification service, which needs to handle events from three different topics.

```go
package main

import (
    "context"
    "log"
    "os"
    "os/signal"
    "syscall"

    "hr360/internal/kafka"
    "hr360/internal/notification"
    "hr360/internal/database"
)

func main() {
    db, err := database.Connect()
    if err != nil {
        log.Fatalf("Database connection failed: %v", err)
    }

    notifier := notification.NewService(db)

    // Create ONE consumer that handles THREE topics.
    // All three topics' messages flow through one Kafka connection,
    // one poll loop, and one commit cycle.
    consumer, err := kafka.NewGroupConsumer(
        "hr360-notification-service-group",          // group ID
        "hr360.employee.created",                    // topic 1
        "hr360.leave.approved",                      // topic 2
        "hr360.payroll.processed",                   // topic 3
    )
    if err != nil {
        log.Fatalf("Failed to create consumer: %v", err)
    }

    // Register handlers. Each is a function matching the MessageHandler signature.
    // These are your business logic — completely separate from Kafka infrastructure.
    consumer.RegisterHandler("hr360.employee.created", func(topic, key, requestID string, value []byte) error {
        // key = employee_id
        // value = JSON: {"employee_id":"E-999","name":"Riyad","email":"riyad@hr360.com",...}
        // requestID = JSON of all Kafka headers including the original HTTP trace ID

        log.Printf("New employee onboarded: employee_id=%s", key)

        // Send welcome email. If this fails (email service down),
        // we return the error. The consumer does NOT mark this record.
        // Kafka redelivers it on the next poll. We retry.
        if err := notifier.SendWelcomeEmail(key, value); err != nil {
            return fmt.Errorf("welcome email failed for employee=%s: %w", key, err)
        }

        // If SendWelcomeEmail succeeded, we return nil.
        // The consumer marks this record and it gets committed in bulk.
        return nil
    })

    consumer.RegisterHandler("hr360.leave.approved", func(topic, key, requestID string, value []byte) error {
        log.Printf("Leave approved for employee: employee_id=%s", key)
        return notifier.SendLeaveApprovalNotification(key, value)
    })

    consumer.RegisterHandler("hr360.payroll.processed", func(topic, key, requestID string, value []byte) error {
        log.Printf("Payroll processed for employee: employee_id=%s", key)
        return notifier.SendPayslipEmail(key, value)
    })

    // Graceful shutdown: cancel the context on SIGTERM or SIGINT.
    ctx, cancel := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
    defer cancel()

    // Start blocks until ctx is cancelled.
    // Returns nil on clean shutdown, error on unexpected failure.
    if err := consumer.Start(ctx); err != nil {
        log.Fatalf("Consumer exited with error: %v", err)
    }

    log.Println("Notification service shut down cleanly.")
}
```

## The Full Message Flow — One Record, End to End

```
FULL LIFECYCLE OF ONE KAFKA RECORD IN YOUR GroupConsumer
═══════════════════════════════════════════════════════════════════════

  KAFKA BROKER
  topic: hr360.employee.created, partition: 2, offset: 481
  value: {"employee_id":"E-999","name":"Riyad",...}
```

## What This Code Gets Right and What Can Be Improved

This code is solid production-grade work. Here is an honest assessment.

**What is correct and well-designed:**

The separation of infrastructure from business logic is exactly right. The `MessageHandler` type contract is clean. The `RWMutex` protecting the handlers map is correct. The `OnPartitionsRevoked` commit flush is the most important correctness guarantee and you've got it. The session timeout / heartbeat relationship is properly configured. The mark-then-bulk-commit pattern is efficient.

**What can be improved for HR360 at scale:**

The no-handler case marks the record committed and moves on — correct, but the log goes to stdout with `fmt.Println` rather than your structured logger. In production, mix of `fmt.Println` and `log.Printf` makes log aggregation messy. Standardize to one logger.

The handler error path currently does nothing except log and return. This means a failing handler will be retried forever if the underlying problem never resolves (e.g., the email service is permanently down, or the message is malformed). In a full production setup, you'd add a retry counter in the record headers, and after N failures, route the message to a Dead Letter Queue topic rather than blocking the partition indefinitely.

The `pingCtx := context.Background()` should be `context.WithTimeout(context.Background(), 10*time.Second)` as your commented-out code suggests. Use the timeout version.

The `requestID` being a JSON-serialized string of all headers, while functional, means every handler must parse JSON just to get a string ID. Consider passing the raw `map[string]string` as the fourth argument instead, or extracting the trace ID before calling the handler and passing only that.
