# Room Memory Leak — Rooms Never Cleaned Up

### A Senior Engineer's Deep Dive for the Curious Intern

---

## 1. Setting the Scene — The Conference Room Booking System That Never Frees Rooms

Picture a large corporate office building with two hundred conference rooms, each managed through a booking system. When an employee needs to host a meeting, they book a room — the room appears in the system as occupied, a nameplate appears on the door, and the room is locked from other bookings. When the meeting ends, the employee is supposed to mark the room as free so others can book it. Now imagine that over time, most employees simply walk out when the meeting ends without releasing the booking. The system shows the room as occupied. The nameplate remains. Nobody can book the room. But when you walk past, the room is entirely empty — chairs neatly arranged, lights off, nobody inside.

After a month, a hundred rooms are "occupied" with zero people in them. Employees trying to find meeting space see only forty-seven available rooms instead of two hundred. The system is consuming resources to track a hundred phantom bookings. The cleaning crew is visiting a hundred empty rooms every night expecting to find people. The building is functionally broken — not because anything crashed, but because the cleanup step that was supposed to happen at the end of every meeting was never performed.

This is the Socket.IO room memory leak. Rooms are created dynamically as users join them, the room metadata is tracked in the server's memory, and when users leave — by closing a chat window, navigating away, or switching to a different document — neither the application code nor the Socket.IO framework automatically reclaims the memory associated with the now-empty room. Over hours and days, the ghost room population grows. Memory climbs steadily despite a stable connection count. Monitoring dashboards show healthy CPU and stable connection metrics, while the server's heap slowly fills with rooms that contain zero sockets and serve zero users.

## 2. The Socket.IO Room Data Structure — What Lives in Memory

To understand the leak precisely, you need a mental model of how Socket.IO's room system is implemented internally. Every Socket.IO server instance maintains an **adapter** — the component responsible for managing room membership, routing events to rooms, and tracking which sockets belong to which rooms. In the default in-process adapter (used in single-instance deployments without the Redis adapter), this tracking is implemented using two `Map` data structures that live in the Node.js process heap.

The first structure is `rooms: Map<roomId, Set<socketId>>` — a mapping from each room identifier string to a Set containing the socket IDs of every socket currently in that room. This is the primary lookup used when `io.to(roomId).emit()` is called: the adapter looks up the room's Set, iterates over each socket ID, finds the corresponding socket object, and delivers the event. Every `socket.join(roomId)` call inserts the socket's ID into the Set for that room, creating the Set if it does not already exist.

The second structure is `sids: Map<socketId, Set<roomId>>` — the inverse mapping, recording which rooms each socket is currently in. This is used when a socket disconnects: the adapter looks up all rooms the socket belongs to, removes the socket's ID from each room's Set, and if any Set becomes empty as a result, it removes that room's key from the `rooms` Map. This automatic cleanup on disconnect is the behavior that leads many developers to believe that room cleanup is fully automatic — which it nearly is, but not completely.

```
              Socket.IO Adapter State — The Two Maps
              =========================================

  io.sockets.adapter.rooms   (Map<roomId → Set<socketId>>)
  ┌────────────────────────────────────────────────────────────┐
  │  "chat:100"  → { "abc123", "def456", "ghi789" }  (3 users)│
  │  "chat:101"  → { "jkl012" }                      (1 user) │
  │  "chat:102"  → { }                               (0 users)│← GHOST ROOM ❌
  │  "chat:103"  → { }                               (0 users)│← GHOST ROOM ❌
  │  "game:55"   → { "abc123", "mno345" }            (2 users)│
  │  "doc:9991"  → { }                               (0 users)│← GHOST ROOM ❌
  │  ... (100K more ghost rooms after 1 week)                  │
  └────────────────────────────────────────────────────────────┘

  io.sockets.adapter.sids    (Map<socketId → Set<roomId>>)
  ┌────────────────────────────────────────────────────────────┐
  │  "abc123" → { "abc123", "chat:100", "game:55" }            │
  │  "def456" → { "def456", "chat:100" }                       │
  │  "jkl012" → { "jkl012", "chat:101" }                       │
  └────────────────────────────────────────────────────────────┘

  Memory consumed by a ghost room:
  ├── Map entry: ~50 bytes (key string + pointer to Set)
  ├── Empty Set object: ~56 bytes
  ├── Application metadata (external Map): ~200-500 bytes per room
  │   (room title, created time, owner, permissions, last active...)
  └── Total per ghost room: ~300-600 bytes

  At 100,000 ghost rooms: ~30-60 MB of pure waste
  Plus: every io.sockets.adapter.rooms iteration visits ghost rooms
  → O(n) operations degrade as ghost rooms accumulate ← silent performance cost
```

The key nuance — the one that creates the leak — is in the automatic disconnect behavior. When a socket disconnects, Socket.IO correctly removes that socket's ID from every room's Set and removes empty rooms from the `rooms` Map. This sounds complete. But this automatic cleanup only operates on Socket.IO's own internal Maps. It has no knowledge of any **external metadata** your application tracks about rooms — the data your application stores in its own variables, databases, or external caches when a room is created. When you create a room and also store a record in `roomMetadata: Map<roomId, RoomInfo>` to track the room's title, its owner, its creation time, and its message history, Socket.IO's disconnect handler has no way to clean up your external `roomMetadata` map. That cleanup is your responsibility, and failing to implement it is the source of the persistent memory leak.

Furthermore, the automatic cleanup only triggers on socket **disconnect** — the event fired when the underlying TCP connection is terminated. It does not fire when a socket **leaves** a room while remaining connected. If a user is in a chat room, closes the chat window in the UI, but keeps the browser tab open (maintaining the WebSocket connection), the socket stays connected. Your application code may or may not call `socket.leave(roomId)` in response to the UI action. If it does not, the socket remains in the room forever, the room remains in memory forever, and the room's associated external metadata remains in memory forever.

## 3. The Real-World Accumulation Pattern — A Week in the Life of a Chat Application

To make the accumulation rate concrete, consider a collaborative document editing application where each document has its own Socket.IO room. Users open documents, the server calls `socket.join("doc:" + documentId)`, and the socket enters the room. When the user closes the document tab, a `beforeunload` browser event fires and the browser closes the WebSocket connection. The socket disconnects. Socket.IO automatically removes the socket from `"doc:" + documentId` and, if it was the last socket in that room, removes the empty room from its `rooms` Map.

So far, cleanup seems to work. But the application also maintains an external `documentRooms: Map<string, DocumentRoom>` object tracking each room's document title, last-modified timestamp, active collaborators list, cursor positions, and undo history buffer. This external structure is never cleaned up because the disconnect handler — which correctly handles Socket.IO's internal cleanup — does not include a call to `documentRooms.delete(roomId)`. Every document that was ever opened leaves a `DocumentRoom` object in memory permanently.

```
              Accumulation Rate — Document Editing App, Real Numbers
              =========================================================

  Application: collaborative document editor
  Users: 500 daily active users
  Avg documents opened per user per day: 8
  Avg document session duration: 25 minutes
  External metadata per room: ~800 bytes (title, timestamps, collaborator list)

  Daily new rooms created: 500 × 8 = 4,000 rooms/day
  Daily rooms properly cleaned up: 0 (bug: no cleanup on empty room)
  Net growth: +4,000 ghost rooms per day

  Week 1: 28,000 ghost rooms × 800 bytes = 22.4 MB wasted
  Week 2: 56,000 ghost rooms × 800 bytes = 44.8 MB wasted
  Week 4: 112,000 ghost rooms × 800 bytes = 89.6 MB wasted

  But memory cost is not linear — iteration cost is also growing:
  io.sockets.adapter.rooms.size: 112,000 entries to iterate for diagnostics
  io.to(room).emit() on hot paths: no ghost room impact (Set is empty)
  io.sockets.adapter.rooms.forEach(): 112,000 iterations for admin features

  Memory from Node.js process perspective:
  t=0d:    Heap: 120 MB (baseline)
  t=7d:    Heap: 142 MB (+22 MB ghost rooms)
  t=14d:   Heap: 165 MB (+45 MB)
  t=30d:   Heap: 210 MB (+90 MB)

  What monitoring shows:
  ├── Active WebSocket connections: ~stable (connected users)
  ├── CPU usage: ~stable (ghost rooms don't process events)
  ├── Memory: slowly climbing at ~3 MB/day ← suspicious but not alarming
  └── No error logs. No crashes. Just a slow, silent climb.

  Discovery method (almost always the same): an engineer notices the
  memory growth trend 3-4 weeks in and begins investigating.
```

The slow, gradual nature of the memory growth is what makes this leak so dangerous. It does not trigger alerts for days or weeks. When it finally becomes large enough to be noticed, the root cause is far removed in time from the investigation. Engineers who examine the heap dump find thousands of `DocumentRoom` objects with no obvious creation site in the current code path. Understanding that these are accumulated ghosts from weeks of room creation without cleanup requires knowing the specific leak pattern.

## 4. The Three Cleanup Scenarios — When to Clean and How

Correct room cleanup must handle three distinct scenarios, each requiring different trigger points and different cleanup logic. Missing any one of them leaves a gap through which ghost rooms can accumulate.

**Scenario 1 — Explicit Leave While Connected.** The user performs an action in the UI that indicates they are leaving a room — closing a chat panel, navigating away from a document, surrendering a game board. The socket remains connected (the browser tab is still open), but the user's relationship to the room has ended. This is the case that developers most commonly forget, because Socket.IO's disconnect handler does not fire here. The correct response is to emit a client-side event (e.g., `leave-room`) that the server handles by calling `socket.leave(roomId)` and then checking whether the room is now empty and cleaning up external metadata if so.

**Scenario 2 — Socket Disconnect.** The user closes the browser tab, navigates away from the entire application, or loses network connectivity. The browser tears down the WebSocket connection. Socket.IO fires the `disconnect` event. The socket is automatically removed from all its rooms by the adapter. However, external metadata is not cleaned. The disconnect handler must iterate the socket's rooms (captured before disconnect clears them), check each room's new occupancy, and clean up external metadata for any room that is now empty.

**Scenario 3 — Server-Side Eviction.** Administrative actions, timeout-based evictions (idle room cleanup), or server restarts may require removing all clients from a room and deleting the room. This scenario requires explicitly iterating all sockets in the room, calling `socket.leave(roomId)` for each, and then deleting external metadata.

```
              Room Cleanup State Machine
              ============================

  Room lifecycle events and required cleanup actions:

  [Room Created]
       │ socket.join(roomId) called
       │ External metadata initialized
       ▼
  [Room Active]
       │ Multiple sockets may join/leave while room remains non-empty
       │
       ├── Event: socket leaves while connected (UI action)
       │     → socket.leave(roomId)
       │     → if room now empty: cleanupRoom(roomId) ← OFTEN MISSED ❌
       │
       ├── Event: socket disconnects
       │     → Socket.IO auto-removes socket from all rooms
       │     → rooms with 0 members: Socket.IO removes from rooms Map ✅
       │     → External metadata: NOT auto-cleaned ← OFTEN MISSED ❌
       │     → Fix: disconnect handler calls cleanupRoom() for empty rooms
       │
       └── Event: server evicts room (admin/timeout)
             → Emit to all room sockets → they leave
             → cleanupRoom(roomId) ← must be explicit
             ▼
  [Room Empty]
       │ Socket.IO rooms Map: entry removed automatically ✅
       │ External metadata: must be removed manually ← your responsibility
       ▼
  [Room Deleted]
       Heap freed. Ghost room eliminated. ✅
```

## 5. The Production-Ready Implementation

The following implementation demonstrates a complete, leak-free room lifecycle for a Node.js chat application. It handles all three cleanup scenarios through a centralized `cleanupRoomIfEmpty` function that is called from every point where a room's occupancy might reach zero:

```javascript
// server.js — Complete leak-free Socket.IO room management

const { createServer } = require('http');
const { Server } = require('socket.io');

const httpServer = createServer(app);
const io = new Server(httpServer, { transports: ['websocket', 'polling'] });

// External room metadata — the application's own tracking beyond Socket.IO's Maps.
// This is what Socket.IO's adapter does NOT automatically clean up.
const roomMetadata = new Map(); // roomId → { title, createdAt, ownerId, messageHistory }

// ── Room Lifecycle Helpers ────────────────────────────────────────────────────

/**
 * Creates a room and initializes its external metadata.
 * Called when the first user joins a new room.
 */
function initRoom(roomId, options = {}) {
    if (!roomMetadata.has(roomId)) {
        roomMetadata.set(roomId, {
            title:          options.title || roomId,
            createdAt:      new Date().toISOString(),
            ownerId:        options.ownerId || null,
            messageHistory: [],
            lastActivityAt: new Date().toISOString(),
        });
        console.log(`Room created: ${roomId}. Total rooms: ${roomMetadata.size}`);
    }
}

/**
 * Checks if a room is empty and, if so, deletes all associated state.
 * This is the critical cleanup function that prevents ghost room accumulation.
 * Must be called after EVERY operation that could result in a room becoming empty.
 */
function cleanupRoomIfEmpty(roomId) {
    const room = io.sockets.adapter.rooms.get(roomId);
    const occupancy = room ? room.size : 0;

    if (occupancy === 0) {
        // Room is empty. Clean up ALL associated state.
        const meta = roomMetadata.get(roomId);
        if (meta) {
            roomMetadata.delete(roomId);
            console.log(
                `Room cleaned up: ${roomId} ` +
                `(was active for ${Date.now() - new Date(meta.createdAt).getTime()}ms). ` +
                `Remaining rooms: ${roomMetadata.size}`
            );
        }
        // Clean up any other external state keyed by roomId:
        // messageCache.delete(roomId);
        // roomPermissions.delete(roomId);
        // typingIndicators.delete(roomId);
    }
}

// ── Connection Handler ────────────────────────────────────────────────────────

io.on('connection', (socket) => {
    console.log(`Socket connected: ${socket.id}`);

    // ── Scenario 1: Explicit join ──────────────────────────────────────────────
    socket.on('join-room', async ({ roomId, title }) => {
        // Initialize room metadata if this is the first member
        initRoom(roomId, { title, ownerId: socket.data.userId });

        await socket.join(roomId);

        const occupancy = io.sockets.adapter.rooms.get(roomId)?.size || 0;
        io.to(roomId).emit('room:joined', {
            userId:    socket.data.userId,
            roomId,
            occupancy,
        });
    });

    // ── Scenario 1: Explicit leave while socket remains connected ─────────────
    // This fires when the user closes the chat panel but keeps the tab open.
    // Socket.IO does NOT handle this automatically — it is entirely app code.
    socket.on('leave-room', async ({ roomId }) => {
        await socket.leave(roomId);

        const occupancy = io.sockets.adapter.rooms.get(roomId)?.size || 0;

        // Notify remaining members
        io.to(roomId).emit('room:left', {
            userId:    socket.data.userId,
            roomId,
            occupancy,
        });

        // ← THE CRITICAL CALL: clean up if this was the last member.
        // Without this, the room persists as a ghost room forever.
        cleanupRoomIfEmpty(roomId);
    });

    // ── Scenario 2: Socket disconnect ─────────────────────────────────────────
    // Capture rooms BEFORE Socket.IO's adapter removes the socket,
    // because by the time 'disconnect' fires, the socket may have
    // already been removed from some rooms.
    // Use 'disconnecting' (note: not 'disconnect') — fires BEFORE cleanup.
    socket.on('disconnecting', (reason) => {
        // socket.rooms still contains all rooms at this moment.
        // After this event, Socket.IO removes the socket from all rooms.
        const roomsBeforeDisconnect = new Set(socket.rooms);

        // Schedule cleanup check for after the adapter has processed the disconnect.
        // We use setImmediate to run after the current event loop tick,
        // which is when Socket.IO's internal adapter cleanup completes.
        setImmediate(() => {
            for (const roomId of roomsBeforeDisconnect) {
                // Skip the socket's own personal room (every socket has one)
                if (roomId === socket.id) continue;

                // Notify remaining room members of the departure
                io.to(roomId).emit('room:left', {
                    userId:    socket.data.userId,
                    roomId,
                    occupancy: io.sockets.adapter.rooms.get(roomId)?.size || 0,
                });

                // ← THE CRITICAL CALL for Scenario 2.
                cleanupRoomIfEmpty(roomId);
            }
        });
    });

    socket.on('disconnect', (reason) => {
        console.log(`Socket disconnected: ${socket.id}, reason: ${reason}`);
    });
});
```

## 6. The `disconnecting` vs `disconnect` Event — A Critical Distinction

The implementation above uses the `disconnecting` event rather than `disconnect` for the cleanup trigger, and this distinction is critical enough to deserve explicit explanation. The `disconnecting` event fires at the moment the socket is about to be removed from all rooms but has not yet been removed. At this precise moment, `socket.rooms` still contains the full set of rooms the socket belongs to. This is the last opportunity to read the socket's room memberships before the adapter's cleanup erases them.

The `disconnect` event fires after the adapter has already completed its cleanup. By the time `disconnect` fires, `socket.rooms` may already be partially or fully cleared. If you attempt to iterate `socket.rooms` in the `disconnect` handler to find rooms that need cleanup, you may find an empty or partially-populated set, causing you to miss the cleanup of rooms that the socket vacated.

```javascript
// WRONG — using 'disconnect': socket.rooms may already be cleared
socket.on('disconnect', (reason) => {
    // At this point, Socket.IO adapter may have already cleared socket.rooms.
    // Iterating here may produce zero results even if the socket was in rooms.
    for (const roomId of socket.rooms) {  // ← potentially empty! ❌
        cleanupRoomIfEmpty(roomId);
    }
});

// CORRECT — using 'disconnecting': rooms are still populated
socket.on('disconnecting', (reason) => {
    // socket.rooms is fully populated at this moment.
    // Capture it immediately before anything clears it.
    const rooms = new Set(socket.rooms); // Capture before it changes ✅

    setImmediate(() => {
        // Now the adapter has finished cleanup. Check each room.
        for (const roomId of rooms) {
            if (roomId === socket.id) continue; // Skip personal room
            cleanupRoomIfEmpty(roomId); // ✅
        }
    });
});
```

## 7. Monitoring Room Health — Detecting the Leak Before It Matters

A small set of monitoring additions makes the room leak immediately visible in dashboards and alerts, allowing the engineering team to catch it during development or early in production before it has accumulated enough to cause memory pressure:

```javascript
// monitoring.js — Room health metrics exposure

/**
 * Returns a snapshot of room health metrics.
 * Expose this via a /metrics or /admin/rooms endpoint.
 */
function getRoomHealthMetrics() {
    const rooms = io.sockets.adapter.rooms;
    let totalRooms   = 0;
    let emptyRooms   = 0;
    let singleRooms  = 0;
    let occupiedRooms = 0;

    for (const [roomId, sockets] of rooms) {
        // Skip personal rooms (each socket has a room named after itself)
        if (sockets.has(roomId)) continue;

        totalRooms++;
        if (sockets.size === 0) emptyRooms++;
        else if (sockets.size === 1) singleRooms++;
        else occupiedRooms++;
    }

    return {
        totalRooms,
        emptyRooms,        // Should always be 0 in a leak-free implementation
        singleRooms,
        occupiedRooms,
        metadataEntries: roomMetadata.size,  // Should equal non-empty rooms
        metadataOrphanCount: roomMetadata.size - (totalRooms - emptyRooms),
        // Positive orphan count = metadata for rooms that no longer exist in adapter
    };
}

// Expose via endpoint for monitoring:
app.get('/admin/room-health', (req, res) => {
    res.json(getRoomHealthMetrics());
});

// Log metrics every 60 seconds for time-series monitoring:
setInterval(() => {
    const metrics = getRoomHealthMetrics();
    console.log('[ROOM METRICS]', JSON.stringify(metrics));
    // In production: emit to StatsD, Prometheus, or CloudWatch
}, 60_000);

// Alert condition:
// If emptyRooms > 0 consistently: cleanup logic is missing somewhere.
// If metadataOrphanCount > 0: metadata is not being cleaned alongside rooms.
// If totalRooms grows monotonically without connection growth: leak confirmed.
```

## 8. Periodic Reaper — The Safety Net for Edge Cases

Even with correct explicit cleanup in all event handlers, edge cases exist where rooms may not be cleaned up: server restarts that leave rooms orphaned in an external Redis adapter, network errors during the `disconnecting` handler, or race conditions in complex multi-step room lifecycle code. A periodic reaper — a background job that scans for empty rooms and cleans up their metadata — provides a safety net that bounds the maximum duration of any ghost room accumulation to the reaper's interval:

```javascript
// reaper.js — Periodic ghost room cleanup as a safety net

const REAPER_INTERVAL_MS = 5 * 60 * 1000; // Run every 5 minutes

function runRoomReaper() {
    let reaped = 0;

    for (const [roomId] of roomMetadata) {
        // Check if this room exists in the Socket.IO adapter
        const room = io.sockets.adapter.rooms.get(roomId);

        if (!room || room.size === 0) {
            // Room exists in our metadata but not in the adapter, or is empty.
            // This is a ghost room. Clean it up.
            roomMetadata.delete(roomId);
            reaped++;
        }
    }

    if (reaped > 0) {
        console.warn(
            `[ROOM REAPER] Cleaned ${reaped} ghost rooms. ` +
            `This indicates missing cleanup in event handlers. ` +
            `Remaining rooms: ${roomMetadata.size}`
        );
        // Alert: if reaper consistently finds ghost rooms, fix the event handler.
        // The reaper is a safety net, not the primary cleanup mechanism.
    }
}

// Run the reaper on a schedule
setInterval(runRoomReaper, REAPER_INTERVAL_MS);

// Also run once on startup to clean any rooms orphaned by a previous crash
runRoomReaper();
```

The reaper log message is intentionally a warning rather than an informational log. A reaper that finds ghost rooms is telling you that your primary cleanup logic has a gap. The reaper should find zero ghost rooms in a correctly implemented application — its only purpose is to bound the damage when something slips through. If your monitoring shows the reaper consistently cleaning up rooms, that is a signal to find and fix the missing cleanup call in your event handlers, not to rely on the reaper as the primary mechanism.

## 9. The Redis Adapter — Room Cleanup in Multi-Instance Deployments

In multi-instance Socket.IO deployments using the Redis adapter, the room lifecycle management becomes more complex because room membership state is distributed across all instances through Redis pub/sub channels. The Redis adapter maintains its own tracking of which sockets are in which rooms, synchronized across instances through Redis. The cleanup principles remain identical — empty rooms must be detected and their associated metadata deleted — but the occupancy check must account for sockets across all instances, not just the local process.

The `io.sockets.adapter.rooms` Map in a Redis adapter deployment reflects only the local instance's view of room membership. To check the true global occupancy of a room, you must use the Socket.IO admin API or a Redis-based room occupancy query:

```javascript
// Multi-instance safe occupancy check using Socket.IO's fetchSockets API
async function cleanupRoomIfEmptyMultiInstance(roomId) {
    // fetchSockets queries all instances (via Redis) for sockets in the room.
    // This gives the true global occupancy, not just the local instance's view.
    const socketsInRoom = await io.in(roomId).fetchSockets();

    if (socketsInRoom.length === 0) {
        roomMetadata.delete(roomId);
        console.log(`Global cleanup: room ${roomId} is empty across all instances.`);
    }
}
```

## 10. The Golden Rule

> Socket.IO automatically removes a socket from all its rooms when the socket disconnects, and it removes empty rooms from its internal adapter state as a consequence. This automatic cleanup is real, correct, and valuable — but it is incomplete. It covers only the Socket.IO adapter's own internal data structures. Any external state your application maintains about rooms — metadata objects, message history buffers, permission maps, cursor tracking structures, anything keyed by room ID — is entirely your responsibility to clean up. The contract is simple: whenever a room transitions from having at least one socket to having zero sockets, all state associated with that room must be deleted. Implement this cleanup in three places: in the `socket.on('leave-room')` handler for explicit leaves while connected, in the `socket.on('disconnecting')` handler for connection terminations, and in any server-side eviction path. Add a periodic reaper as a safety net. Expose room count metrics so that monotonic growth is visible before it becomes a memory crisis.

A ghost room costs almost nothing individually. A hundred thousand ghost rooms cost you your weekend.
