# The SAGA Pattern With gRPC

### gRPC vs Kafka for SAGAs — and a Complete gRPC Implementation

---

## First, The Question You Asked — gRPC or Kafka for SAGAs?

This is one of the most important architectural decisions you will make when designing a SAGA in a microservice system. Both approaches work. Both are used in production systems by serious engineering teams. But they are not interchangeable. Each one fits a specific set of requirements, and picking the wrong one creates real operational pain. Let me give you an honest answer instead of "it depends" followed by nothing.

Here is the complete comparison, and then you will know exactly which one to use in each situation.

```
gRPC vs KAFKA FOR SAGA COORDINATION — Full Comparison
──────────────────────────────────────────────────────────────────────────────

                        gRPC                        Kafka
──────────────────────────────────────────────────────────────────────────────
Communication style   Synchronous (request/reply)   Asynchronous (fire and forget)
                      Caller waits for response      Caller publishes, moves on

Latency               Very low (milliseconds)        Higher (tens of milliseconds
                      Direct TCP connection           to seconds, depends on lag)

Reliability           No built-in durability         Durable — messages survive
                      If caller crashes, the          restarts, network failures,
                      in-flight call is lost          broker restarts

Message ordering      Not guaranteed across           Guaranteed within a partition
                      retries                         (with correct key design)

Backpressure          Natural — caller blocks         Consumer-controlled —
                      if service is slow              consumer reads at its pace

Error propagation     Immediate — error comes         Delayed — error comes back
                      back in the same call           as a separate event/reply

Coupling              Caller must know callee's       Caller only knows topic name
                      address and proto contract      Consumer knows only event schema

Scalability           Limited by connection pool      Horizontally scales naturally
                      and server capacity             via consumer group partitioning

Observability         Easy — one call, one span       Harder — trace context must
                      in distributed tracing           be propagated in headers

Saga state visibility Orchestrator knows exactly       Harder to know current step
                      where it is in real time         without querying saga state DB

Long-running steps    Problematic — gRPC timeout      Natural — consumer processes
(minutes to hours)    requires very long timeout       at its own pace, no timeout

Transient failures    Must implement retry in          Kafka retries automatically
                      orchestrator code               via consumer reprocessing

Compensating txns     Easy to implement and           Need separate compensation
                      reason about (direct call)      topics + consumer logic

Infrastructure        Simple — no extra               Requires Kafka cluster,
complexity            infrastructure needed            topic management, offsets

──────────────────────────────────────────────────────────────────────────────
VERDICT:
──────────────────────────────────────────────────────────────────────────────
Use gRPC SAGA when:                  Use Kafka SAGA when:
  ✓ Steps complete in < 30 seconds     ✓ Steps can take minutes to hours
  ✓ You need immediate error           ✓ You need guaranteed delivery
    feedback to the caller               even across service restarts
  ✓ Simple linear flows                ✓ High throughput (1000s/sec)
  ✓ Small team, simple infra           ✓ Loose coupling is important
  ✓ You already use gRPC for           ✓ Steps are independent and can
    everything else                      run in any order
  ✓ Real-time user-facing flows        ✓ Batch or background processing
──────────────────────────────────────────────────────────────────────────────
```

For the HR360 system and for most user-facing SAGA flows, **gRPC is the better choice**. Here is the core reason: when an employee submits a leave application, they are sitting in front of a screen waiting for a result. They need to know if it worked within a few seconds. With a Kafka-based SAGA, the orchestrator publishes a command event, waits for a reply event, and the round trip through Kafka adds latency on every step. With a gRPC-based SAGA, each step is a direct call with an immediate response, and the orchestrator knows within milliseconds whether a step succeeded or failed.

The Kafka SAGA shines for the payroll processing use case — a manager kicks off a payroll run and goes home. The system processes thousands of salary calculations overnight. Steps might wait for approval that takes hours. There is no user sitting there waiting. Kafka's durability and async nature are perfect there.

For the rest of this guide, we build a complete gRPC-based SAGA. The example is the leave submission flow from HR360, which is a perfect user-facing SAGA that benefits from gRPC's speed and immediate error propagation.

## The Problem We Are Solving

An employee submits a leave application. This single user action must trigger four coordinated changes across four separate services, each with its own database. All four must succeed, or all must be compensated and reversed cleanly.

```
LEAVE SUBMISSION — Four Services, One Business Transaction
───────────────────────────────────────────────────────────

  Employee submits leave for 5 days (Annual Leave, March 20-26)

  Step 1: Leave Service         → Create leave record (status: PENDING)
  Step 2: Leave Balance Service → Deduct 5 days from available balance
  Step 3: Approval Service      → Create approval task for manager
  Step 4: Notification Service  → Send email to manager

  Compensation if Step 3 fails:
    ← Compensate Step 2: Restore 5 days to balance
    ← Compensate Step 1: Cancel the leave record

  All four steps succeed   → Employee sees "Leave Submitted Successfully"
  Any step fails after N   → All completed steps are undone
  retries                  → Employee sees "Submission failed, please try again"
```

## The Three-Layer Architecture of a gRPC SAGA

A well-designed gRPC SAGA has three distinct layers. Understanding these layers before writing a single line of code is what separates a clean implementation from a tangled mess.

The first layer is the **SAGA Orchestrator**. This is the brain. It knows the full sequence of steps, which service handles each step, what the compensating action is for each step, and what state the SAGA is currently in. The orchestrator lives inside the Leave Service — not as a separate service, but as a component within it. This is important: the service that owns the business process owns the orchestrator for that process.

The second layer is the **SAGA Participants**. These are the services that do the actual work — Leave Balance Service, Approval Service, Notification Service. Each participant exposes gRPC endpoints specifically designed for SAGA participation. These endpoints must be idempotent — the orchestrator may call them more than once if a response is lost.

The third layer is the **SAGA State Store**. This is a database table inside the Leave Service that records the current state of every active SAGA — which step it is on, what has already been completed, what needs to be compensated if something fails. This persistence is what allows the orchestrator to recover if it crashes mid-SAGA.

```
THREE LAYERS OF A gRPC SAGA
─────────────────────────────

  ┌─────────────────────────────────────────────────────────────────┐
  │                    Leave Service                                │
  │                                                                 │
  │  ┌──────────────────────────────────────────────────────────┐   │
  │  │              SAGA Orchestrator (Layer 1)                 │   │
  │  │                                                          │   │
  │  │  Knows: steps, order, compensations, current state       │   │
  │  │  Does: calls participants, handles failures, compensates │   │
  │  └──────────────────────────────────────────────────────────┘   │
  │                                                                 │
  │  ┌──────────────────────────────────────────────────────────┐   │
  │  │              SAGA State Store (Layer 3)                  │   │
  │  │                                                          │   │
  │  │  leave_submission_sagas table (PostgreSQL via GORM)      │   │
  │  │  Records every state transition, survives crashes        │   │
  │  └──────────────────────────────────────────────────────────┘   │
  └─────────────────────────────────────────────────────────────────┘
          │ gRPC calls (direct, immediate, synchronous)
          │
          ├───────────────────────────────────────────────────────►
          │                                               │        │
          ▼                                               ▼        ▼
  Leave Balance Service     Approval Service     Notification Service
  (Layer 2: Participant)    (Layer 2: Participant)(Layer 2: Participant)
  ExecuteSagaStep()         ExecuteSagaStep()     ExecuteSagaStep()
  CompensateSagaStep()      CompensateSagaStep()  (no compensation needed)
```

## The Proto Definition — Designing for SAGA Participation

The gRPC contract between the orchestrator and participants must be designed with SAGA requirements in mind. Every participant endpoint must accept a `saga_id` and a `command_id`. The `saga_id` ties the call to a specific SAGA instance. The `command_id` is the idempotency key — if the orchestrator retries a failed call, the participant uses this ID to detect and skip duplicate execution.

```protobuf
// proto/leave/leave_saga.proto
syntax = "proto3";
package leave.saga.v1;

import "google/protobuf/timestamp.proto";

// ── Leave Balance Service SAGA endpoints ─────────────────────────────────────

service LeaveBalanceSagaService {
    // Forward step: deduct leave days
    rpc DeductBalanceForLeave (DeductBalanceRequest) returns (DeductBalanceResponse);
    // Compensating step: restore leave days (called if a later step fails)
    rpc RestoreBalanceForLeave (RestoreBalanceRequest) returns (RestoreBalanceResponse);
}

message DeductBalanceRequest {
    string saga_id      = 1;  // identifies the SAGA this step belongs to
    string command_id   = 2;  // idempotency key — stable across retries
    string employee_id  = 3;
    string leave_id     = 4;
    int32  days         = 5;
    string leave_type   = 6;
}

message DeductBalanceResponse {
    bool   success           = 1;
    int32  remaining_balance = 2;
    string failure_reason    = 3;  // filled when success = false
}

message RestoreBalanceRequest {
    string saga_id     = 1;
    string command_id  = 2;  // different from the forward step's command_id
    string employee_id = 3;
    string leave_id    = 4;
    int32  days        = 5;
    string leave_type  = 6;
}

message RestoreBalanceResponse {
    bool success = 1;
}

// ── Approval Service SAGA endpoints ──────────────────────────────────────────

service ApprovalSagaService {
    rpc CreateLeaveApprovalTask (CreateApprovalTaskRequest) returns (CreateApprovalTaskResponse);
    rpc CancelLeaveApprovalTask (CancelApprovalTaskRequest) returns (CancelApprovalTaskResponse);
}

message CreateApprovalTaskRequest {
    string saga_id      = 1;
    string command_id   = 2;
    string leave_id     = 3;
    string employee_id  = 4;
    string manager_id   = 5;
    int32  days         = 6;
    google.protobuf.Timestamp start_date = 7;
    google.protobuf.Timestamp end_date   = 8;
}

message CreateApprovalTaskResponse {
    bool   success     = 1;
    string approval_id = 2;
    string failure_reason = 3;
}

message CancelApprovalTaskRequest {
    string saga_id    = 1;
    string command_id = 2;
    string leave_id   = 3;
}

message CancelApprovalTaskResponse {
    bool success = 1;
}

// ── Notification Service SAGA endpoints ──────────────────────────────────────

service NotificationSagaService {
    rpc SendLeaveSubmissionNotification (SendNotificationRequest) returns (SendNotificationResponse);
    // No compensation for notifications — we cannot "unsend" an email
    // Instead, we send a cancellation email if compensation is needed
    rpc SendLeaveCancellationNotification (SendNotificationRequest) returns (SendNotificationResponse);
}

message SendNotificationRequest {
    string saga_id       = 1;
    string command_id    = 2;
    string recipient_id  = 3;
    string leave_id      = 4;
    string employee_name = 5;
    string leave_type    = 6;
    int32  days          = 7;
}

message SendNotificationResponse {
    bool success = 1;
}
```

## The SAGA State Model

The state table is the most important data structure in the gRPC SAGA. It must record enough information to allow the orchestrator to resume from exactly where it left off after a crash, and to execute the correct compensations in the correct order when needed.

```go
// leave/internal/saga/state.go

package saga

// SagaStatus represents the current lifecycle phase of a SAGA
type SagaStatus string

const (
    SagaStatusStarted      SagaStatus = "STARTED"
    SagaStatusStep1Done    SagaStatus = "STEP_1_DONE"   // leave record created
    SagaStatusStep2Done    SagaStatus = "STEP_2_DONE"   // balance deducted
    SagaStatusStep3Done    SagaStatus = "STEP_3_DONE"   // approval task created
    SagaStatusCompleted    SagaStatus = "COMPLETED"     // all steps done
    SagaStatusCompensating SagaStatus = "COMPENSATING"  // rolling back
    SagaStatusFailed       SagaStatus = "FAILED"        // fully compensated
)

// LeaveSubmissionSaga is the GORM model stored in PostgreSQL
type LeaveSubmissionSaga struct {
    // Identity
    SagaID     string     `gorm:"primaryKey"`
    LeaveID    string     `gorm:"not null;uniqueIndex"`
    EmployeeID string     `gorm:"not null;index"`
    ManagerID  string     `gorm:"not null"`

    // Input data — stored so compensations have everything they need
    LeaveType  string     `gorm:"not null"`
    Days       int        `gorm:"not null"`
    StartDate  time.Time  `gorm:"not null"`
    EndDate    time.Time  `gorm:"not null"`

    // Current state
    Status     SagaStatus `gorm:"not null;index"`
    CurrentStep int       `gorm:"not null;default:0"`

    // Compensation tracking — what IDs were produced that we need to undo
    ApprovalID string     // set after Step 3, used for compensation

    // Retry tracking
    RetryCount int        `gorm:"not null;default:0"`
    LastError  string     `gorm:"type:text"`

    // Command IDs for idempotency — one per step (forward + compensation)
    // These are generated once and reused on all retries
    Step1ForwardCmdID    string `gorm:"not null"` // create leave
    Step2ForwardCmdID    string `gorm:"not null"` // deduct balance
    Step2CompensateCmdID string `gorm:"not null"` // restore balance
    Step3ForwardCmdID    string `gorm:"not null"` // create approval task
    Step3CompensateCmdID string `gorm:"not null"` // cancel approval task
    Step4ForwardCmdID    string `gorm:"not null"` // send notification
    Step4CompensateCmdID string `gorm:"not null"` // send cancellation notification

    // Timestamps
    CreatedAt   time.Time  `gorm:"not null;autoCreateTime"`
    UpdatedAt   time.Time  `gorm:"not null;autoUpdateTime"`
    CompletedAt *time.Time
}

func (LeaveSubmissionSaga) TableName() string {
    return "leave_submission_sagas"
}
```

Notice the `Step*CmdID` fields. Every single step — both forward and compensating — has its own pre-generated command ID. These are all created when the SAGA is initialized and never change. No matter how many times the orchestrator retries a step, it always uses the same command ID for that step. This is what makes retries safe — the participant sees a repeated command ID and skips the operation without error.

## The Orchestrator — The Complete Implementation

This is the heart of the gRPC SAGA. The orchestrator is a Go struct that holds gRPC clients to each participant and a reference to the database. Its `Execute` method drives the SAGA from step 1 through step 4, handling failures and compensations at each step.

```go
// leave/internal/saga/orchestrator.go

package saga

import (
    "context"
    "fmt"
    "time"

    "github.com/google/uuid"
    "google.golang.org/grpc"
    "gorm.io/gorm"

    balancepb  "hr360/proto/leave_balance"
    approvalpb "hr360/proto/approval"
    notifpb    "hr360/proto/notification"
)

// LeaveSubmissionOrchestrator drives the leave submission SAGA
type LeaveSubmissionOrchestrator struct {
    db              *gorm.DB
    balanceClient   balancepb.LeaveBalanceSagaServiceClient
    approvalClient  approvalpb.ApprovalSagaServiceClient
    notifClient     notifpb.NotificationSagaServiceClient
    logger          *slog.Logger
    maxRetries      int
    stepTimeout     time.Duration
}

func NewLeaveSubmissionOrchestrator(
    db *gorm.DB,
    balanceConn, approvalConn, notifConn *grpc.ClientConn,
    logger *slog.Logger,
) *LeaveSubmissionOrchestrator {
    return &LeaveSubmissionOrchestrator{
        db:             db,
        balanceClient:  balancepb.NewLeaveBalanceSagaServiceClient(balanceConn),
        approvalClient: approvalpb.NewApprovalSagaServiceClient(approvalConn),
        notifClient:    notifpb.NewNotificationSagaServiceClient(notifConn),
        logger:         logger,
        maxRetries:     3,
        stepTimeout:    10 * time.Second,
    }
}

// StartSagaRequest contains everything the SAGA needs to execute
type StartSagaRequest struct {
    LeaveID    string
    EmployeeID string
    ManagerID  string
    LeaveType  string
    Days       int
    StartDate  time.Time
    EndDate    time.Time
}

// Execute starts and drives the SAGA to completion (or compensation)
// Returns nil if the SAGA completed successfully
// Returns an error if the SAGA failed and was fully compensated
func (o *LeaveSubmissionOrchestrator) Execute(ctx context.Context, req StartSagaRequest) error {
    // Initialize the SAGA state — all command IDs generated upfront
    sagaID := uuid.NewString()

    saga := &LeaveSubmissionSaga{
        SagaID:     sagaID,
        LeaveID:    req.LeaveID,
        EmployeeID: req.EmployeeID,
        ManagerID:  req.ManagerID,
        LeaveType:  req.LeaveType,
        Days:       req.Days,
        StartDate:  req.StartDate,
        EndDate:    req.EndDate,
        Status:     SagaStatusStarted,
        CurrentStep: 0,
        // Generate stable command IDs for every step — done once, reused on retries
        Step1ForwardCmdID:    uuid.NewString(),
        Step2ForwardCmdID:    uuid.NewString(),
        Step2CompensateCmdID: uuid.NewString(),
        Step3ForwardCmdID:    uuid.NewString(),
        Step3CompensateCmdID: uuid.NewString(),
        Step4ForwardCmdID:    uuid.NewString(),
        Step4CompensateCmdID: uuid.NewString(),
    }

    // Persist initial state before doing anything
    if err := o.db.Create(saga).Error; err != nil {
        return fmt.Errorf("failed to initialize saga state: %w", err)
    }

    o.logger.Info("SAGA started", "saga_id", sagaID, "leave_id", req.LeaveID)

    // ─── STEP 1: Create the leave record ─────────────────────────────────────
    // Note: Step 1 is handled by the Leave Service itself (same service as the
    // orchestrator). The leave record is created before the SAGA starts, as part
    // of handling the SubmitLeave command. The SAGA takes over after that.
    // We mark it done immediately.
    if err := o.advanceTo(saga, SagaStatusStep1Done, 1); err != nil {
        return err
    }

    o.logger.Info("SAGA step 1 complete — leave record exists",
        "saga_id", sagaID, "leave_id", req.LeaveID)

    // ─── STEP 2: Deduct leave balance ────────────────────────────────────────
    if err := o.executeStep2(ctx, saga); err != nil {
        o.logger.Error("SAGA step 2 failed — beginning compensation",
            "saga_id", sagaID, "error", err)
        return o.compensateFromStep1(ctx, saga, err)
    }

    // ─── STEP 3: Create approval task ────────────────────────────────────────
    if err := o.executeStep3(ctx, saga); err != nil {
        o.logger.Error("SAGA step 3 failed — beginning compensation",
            "saga_id", sagaID, "error", err)
        return o.compensateFromStep2(ctx, saga, err)
    }

    // ─── STEP 4: Send notification ────────────────────────────────────────────
    if err := o.executeStep4(ctx, saga); err != nil {
        // Notification failure is non-fatal — we do not roll back the whole SAGA
        // because the leave record and approval task are correctly created.
        // Log the error, mark SAGA as completed with a warning.
        o.logger.Warn("SAGA step 4 (notification) failed — SAGA still completed",
            "saga_id", sagaID, "error", err)
    }

    // ─── SAGA COMPLETE ────────────────────────────────────────────────────────
    now := time.Now()
    o.db.Model(saga).Updates(map[string]interface{}{
        "status":       SagaStatusCompleted,
        "current_step": 4,
        "completed_at": &now,
    })

    o.logger.Info("SAGA completed successfully",
        "saga_id", sagaID, "leave_id", req.LeaveID)
    return nil
}

// ─── STEP EXECUTION METHODS ───────────────────────────────────────────────────

func (o *LeaveSubmissionOrchestrator) executeStep2(ctx context.Context, saga *LeaveSubmissionSaga) error {
    o.logger.Info("SAGA executing step 2 — deduct balance",
        "saga_id", saga.SagaID, "employee_id", saga.EmployeeID, "days", saga.Days)

    var lastErr error
    for attempt := 1; attempt <= o.maxRetries; attempt++ {
        if attempt > 1 {
            backoff := time.Duration(attempt*attempt) * 500 * time.Millisecond
            o.logger.Info("SAGA step 2 retry",
                "saga_id", saga.SagaID, "attempt", attempt, "backoff", backoff)
            time.Sleep(backoff)
        }

        stepCtx, cancel := context.WithTimeout(ctx, o.stepTimeout)
        resp, err := o.balanceClient.DeductBalanceForLeave(stepCtx, &balancepb.DeductBalanceRequest{
            SagaId:     saga.SagaID,
            CommandId:  saga.Step2ForwardCmdID,  // same on every retry — idempotent
            EmployeeId: saga.EmployeeID,
            LeaveId:    saga.LeaveID,
            Days:       int32(saga.Days),
            LeaveType:  saga.LeaveType,
        })
        cancel()

        if err != nil {
            lastErr = fmt.Errorf("step 2 gRPC call failed (attempt %d): %w", attempt, err)
            continue // retry
        }

        if !resp.Success {
            // Business failure (e.g. insufficient balance) — do not retry
            return fmt.Errorf("step 2 business failure: %s", resp.FailureReason)
        }

        // Success — advance SAGA state
        return o.advanceTo(saga, SagaStatusStep2Done, 2)
    }

    return fmt.Errorf("step 2 exhausted %d retries: %w", o.maxRetries, lastErr)
}

func (o *LeaveSubmissionOrchestrator) executeStep3(ctx context.Context, saga *LeaveSubmissionSaga) error {
    o.logger.Info("SAGA executing step 3 — create approval task", "saga_id", saga.SagaID)

    var lastErr error
    for attempt := 1; attempt <= o.maxRetries; attempt++ {
        if attempt > 1 {
            time.Sleep(time.Duration(attempt*attempt) * 500 * time.Millisecond)
        }

        stepCtx, cancel := context.WithTimeout(ctx, o.stepTimeout)
        resp, err := o.approvalClient.CreateLeaveApprovalTask(stepCtx, &approvalpb.CreateApprovalTaskRequest{
            SagaId:     saga.SagaID,
            CommandId:  saga.Step3ForwardCmdID,
            LeaveId:    saga.LeaveID,
            EmployeeId: saga.EmployeeID,
            ManagerId:  saga.ManagerID,
            Days:       int32(saga.Days),
            StartDate:  timestamppb.New(saga.StartDate),
            EndDate:    timestamppb.New(saga.EndDate),
        })
        cancel()

        if err != nil {
            lastErr = fmt.Errorf("step 3 gRPC call failed (attempt %d): %w", attempt, err)
            continue
        }

        if !resp.Success {
            return fmt.Errorf("step 3 business failure: %s", resp.FailureReason)
        }

        // Store the approval ID — needed for compensation
        saga.ApprovalID = resp.ApprovalId
        o.db.Model(saga).Update("approval_id", resp.ApprovalId)

        return o.advanceTo(saga, SagaStatusStep3Done, 3)
    }

    return fmt.Errorf("step 3 exhausted %d retries: %w", o.maxRetries, lastErr)
}

func (o *LeaveSubmissionOrchestrator) executeStep4(ctx context.Context, saga *LeaveSubmissionSaga) error {
    o.logger.Info("SAGA executing step 4 — send notification", "saga_id", saga.SagaID)

    stepCtx, cancel := context.WithTimeout(ctx, o.stepTimeout)
    defer cancel()

    _, err := o.notifClient.SendLeaveSubmissionNotification(stepCtx, &notifpb.SendNotificationRequest{
        SagaId:      saga.SagaID,
        CommandId:   saga.Step4ForwardCmdID,
        RecipientId: saga.ManagerID,
        LeaveId:     saga.LeaveID,
        EmployeeId:  saga.EmployeeID,
        LeaveType:   saga.LeaveType,
        Days:        int32(saga.Days),
    })

    return err
}

// ─── COMPENSATION METHODS ─────────────────────────────────────────────────────

// compensateFromStep2: Step 3 failed. Need to undo Step 2 (balance deduction).
func (o *LeaveSubmissionOrchestrator) compensateFromStep2(ctx context.Context, saga *LeaveSubmissionSaga, originalErr error) error {
    o.logger.Info("SAGA compensating from step 2", "saga_id", saga.SagaID)

    o.db.Model(saga).Updates(map[string]interface{}{
        "status":     SagaStatusCompensating,
        "last_error": originalErr.Error(),
    })

    // Compensate Step 2: restore the balance
    if err := o.compensateStep2(ctx, saga); err != nil {
        // Compensation itself failed — this is a serious problem
        // The system is in an inconsistent state: leave exists, balance is deducted,
        // but no approval task was created. Requires manual intervention.
        o.logger.Error("CRITICAL: SAGA compensation step 2 failed — manual intervention required",
            "saga_id", saga.SagaID, "error", err)
        // In production: alert on-call immediately via PagerDuty
        return fmt.Errorf("SAGA %s in inconsistent state — compensation failed: %w", saga.SagaID, err)
    }

    // Then compensate Step 1: cancel the leave record
    if err := o.compensateStep1(ctx, saga); err != nil {
        o.logger.Error("CRITICAL: SAGA compensation step 1 failed",
            "saga_id", saga.SagaID, "error", err)
        return fmt.Errorf("SAGA %s partial compensation — step 1 failed: %w", saga.SagaID, err)
    }

    // Fully compensated
    o.db.Model(saga).Updates(map[string]interface{}{
        "status": SagaStatusFailed,
    })

    o.logger.Info("SAGA fully compensated", "saga_id", saga.SagaID)
    return fmt.Errorf("leave submission failed: %s", originalErr.Error())
}

// compensateFromStep1: Step 2 failed. Only need to undo Step 1 (leave record).
func (o *LeaveSubmissionOrchestrator) compensateFromStep1(ctx context.Context, saga *LeaveSubmissionSaga, originalErr error) error {
    o.logger.Info("SAGA compensating from step 1", "saga_id", saga.SagaID)

    o.db.Model(saga).Updates(map[string]interface{}{
        "status":     SagaStatusCompensating,
        "last_error": originalErr.Error(),
    })

    if err := o.compensateStep1(ctx, saga); err != nil {
        o.logger.Error("CRITICAL: SAGA compensation step 1 failed",
            "saga_id", saga.SagaID, "error", err)
        return fmt.Errorf("SAGA %s compensation failed: %w", saga.SagaID, err)
    }

    o.db.Model(saga).Update("status", SagaStatusFailed)
    return fmt.Errorf("leave submission failed: %s", originalErr.Error())
}

// compensateStep2: Restore the leave balance
func (o *LeaveSubmissionOrchestrator) compensateStep2(ctx context.Context, saga *LeaveSubmissionSaga) error {
    for attempt := 1; attempt <= o.maxRetries; attempt++ {
        if attempt > 1 {
            time.Sleep(time.Duration(attempt) * time.Second)
        }

        stepCtx, cancel := context.WithTimeout(ctx, o.stepTimeout)
        resp, err := o.balanceClient.RestoreBalanceForLeave(stepCtx, &balancepb.RestoreBalanceRequest{
            SagaId:     saga.SagaID,
            CommandId:  saga.Step2CompensateCmdID, // different ID from forward step
            EmployeeId: saga.EmployeeID,
            LeaveId:    saga.LeaveID,
            Days:       int32(saga.Days),
            LeaveType:  saga.LeaveType,
        })
        cancel()

        if err != nil {
            o.logger.Error("compensate step 2 attempt failed",
                "attempt", attempt, "error", err)
            continue
        }

        if !resp.Success {
            return fmt.Errorf("balance restoration was rejected by service")
        }

        o.logger.Info("SAGA step 2 compensated — balance restored", "saga_id", saga.SagaID)
        return nil
    }

    return fmt.Errorf("failed to restore balance after %d attempts", o.maxRetries)
}

// compensateStep1: Cancel the leave record (marks it as CANCELLED in Leave Service DB)
func (o *LeaveSubmissionOrchestrator) compensateStep1(ctx context.Context, saga *LeaveSubmissionSaga) error {
    // This is within the Leave Service itself — direct DB call, no gRPC needed
    result := o.db.Model(&Leave{}).
        Where("id = ? AND status = ?", saga.LeaveID, "PENDING").
        Update("status", "CANCELLED")

    if result.Error != nil {
        return result.Error
    }

    o.logger.Info("SAGA step 1 compensated — leave record cancelled", "saga_id", saga.SagaID)
    return nil
}

// advanceTo persists the saga state transition to the database
func (o *LeaveSubmissionOrchestrator) advanceTo(saga *LeaveSubmissionSaga, status SagaStatus, step int) error {
    saga.Status = status
    saga.CurrentStep = step
    return o.db.Model(saga).Updates(map[string]interface{}{
        "status":       status,
        "current_step": step,
    }).Error
}
```

## The Participant — Leave Balance Service Implementation

Each participant needs to implement the SAGA gRPC endpoints with full idempotency. Here is the complete implementation for the Leave Balance Service:

```go
// balance/internal/grpc/saga_server.go

package grpc

type LeaveBalanceSagaServer struct {
    balancepb.UnimplementedLeaveBalanceSagaServiceServer
    db     *gorm.DB
    logger *slog.Logger
}

func (s *LeaveBalanceSagaServer) DeductBalanceForLeave(
    ctx context.Context,
    req *balancepb.DeductBalanceRequest,
) (*balancepb.DeductBalanceResponse, error) {

    s.logger.Info("SAGA step received: DeductBalance",
        "saga_id", req.SagaId,
        "command_id", req.CommandId,
        "employee_id", req.EmployeeId,
        "days", req.Days,
    )

    var remainingBalance int32

    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // ── IDEMPOTENCY CHECK ─────────────────────────────────────────────────
        // If we have already processed this command_id, return the stored result
        var existing ProcessedSagaCommand
        result := tx.Where("command_id = ?", req.CommandId).First(&existing)
        if result.Error == nil {
            // Already processed — return the cached response
            s.logger.Info("SAGA deduct: duplicate command, returning cached result",
                "command_id", req.CommandId)
            remainingBalance = int32(existing.ResultData)
            return nil
        }
        // ──────────────────────────────────────────────────────────────────────

        // Load the employee's current balance
        var balance EmployeeLeaveBalance
        if err := tx.Where("employee_id = ? AND leave_type = ?",
            req.EmployeeId, req.LeaveType).First(&balance).Error; err != nil {
            return fmt.Errorf("employee balance not found: %s", req.EmployeeId)
        }

        // Business rule check
        if balance.AvailableDays < int(req.Days) {
            return &InsufficientBalanceError{
                Available: balance.AvailableDays,
                Requested: int(req.Days),
            }
        }

        // Deduct the balance
        balance.AvailableDays -= int(req.Days)
        balance.UsedDays += int(req.Days)
        if err := tx.Save(&balance).Error; err != nil {
            return err
        }

        remainingBalance = int32(balance.AvailableDays)

        // Record this command as processed (idempotency record)
        return tx.Create(&ProcessedSagaCommand{
            CommandID:  req.CommandId,
            SagaID:     req.SagaId,
            CommandType: "DeductBalanceForLeave",
            ResultData: balance.AvailableDays, // store remaining balance for replay
            ProcessedAt: time.Now(),
            ExpiresAt:  time.Now().Add(7 * 24 * time.Hour),
        }).Error
    })

    if err != nil {
        var insufficientErr *InsufficientBalanceError
        if errors.As(err, &insufficientErr) {
            // Business failure — do not retry, inform orchestrator immediately
            return &balancepb.DeductBalanceResponse{
                Success:       false,
                FailureReason: fmt.Sprintf("insufficient balance: need %d days, have %d",
                    insufficientErr.Requested, insufficientErr.Available),
            }, nil
        }

        // Infrastructure error — return gRPC error so orchestrator can retry
        return nil, status.Errorf(codes.Internal, "deduct balance failed: %v", err)
    }

    return &balancepb.DeductBalanceResponse{
        Success:          true,
        RemainingBalance: remainingBalance,
    }, nil
}

func (s *LeaveBalanceSagaServer) RestoreBalanceForLeave(
    ctx context.Context,
    req *balancepb.RestoreBalanceRequest,
) (*balancepb.RestoreBalanceResponse, error) {

    s.logger.Info("SAGA compensation received: RestoreBalance",
        "saga_id", req.SagaId, "command_id", req.CommandId)

    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // Idempotency check for compensation
        var existing ProcessedSagaCommand
        if tx.Where("command_id = ?", req.CommandId).First(&existing).Error == nil {
            s.logger.Info("SAGA restore: duplicate compensation, skipping",
                "command_id", req.CommandId)
            return nil // Already compensated — safe to return success
        }

        var balance EmployeeLeaveBalance
        if err := tx.Where("employee_id = ? AND leave_type = ?",
            req.EmployeeId, req.LeaveType).First(&balance).Error; err != nil {
            return err
        }

        // Restore the balance
        balance.AvailableDays += int(req.Days)
        balance.UsedDays -= int(req.Days)
        if err := tx.Save(&balance).Error; err != nil {
            return err
        }

        return tx.Create(&ProcessedSagaCommand{
            CommandID:   req.CommandId,
            SagaID:      req.SagaId,
            CommandType: "RestoreBalanceForLeave",
            ProcessedAt: time.Now(),
            ExpiresAt:   time.Now().Add(7 * 24 * time.Hour),
        }).Error
    })

    if err != nil {
        return nil, status.Errorf(codes.Internal, "restore balance failed: %v", err)
    }

    return &balancepb.RestoreBalanceResponse{Success: true}, nil
}
```

## Integrating the SAGA Into the Leave Service Command Handler

The orchestrator is called from the Leave Service's gRPC command handler. The leave record is created first (Step 1), and then the SAGA takes over to coordinate the remaining steps.

```go
// leave/internal/grpc/command_server.go

type LeaveCommandServer struct {
    leavecmdpb.UnimplementedLeaveCommandServiceServer
    db          *gorm.DB
    orchestrator *saga.LeaveSubmissionOrchestrator
    idempotency  *idempotency.GRPCIdempotencyInterceptor
    logger       *slog.Logger
}

func (s *LeaveCommandServer) SubmitLeave(
    ctx context.Context,
    req *leavecmdpb.SubmitLeaveRequest,
) (*leavecmdpb.SubmitLeaveResponse, error) {

    leaveID := uuid.NewString()

    // Step 1 is performed here, directly in the Leave Service
    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        return tx.Create(&Leave{
            ID:         leaveID,
            EmployeeID: req.EmployeeId,
            LeaveType:  req.LeaveType,
            Days:       int(req.Days),
            StartDate:  req.StartDate.AsTime(),
            EndDate:    req.EndDate.AsTime(),
            Reason:     req.Reason,
            Status:     "PENDING",
        }).Error
    })

    if err != nil {
        return nil, status.Errorf(codes.Internal, "failed to create leave: %v", err)
    }

    // Hand off to the SAGA orchestrator for steps 2, 3, 4
    sagaErr := s.orchestrator.Execute(ctx, saga.StartSagaRequest{
        LeaveID:    leaveID,
        EmployeeID: req.EmployeeId,
        ManagerID:  req.ManagerId,
        LeaveType:  req.LeaveType,
        Days:       int(req.Days),
        StartDate:  req.StartDate.AsTime(),
        EndDate:    req.EndDate.AsTime(),
    })

    if sagaErr != nil {
        // SAGA failed — the compensation has already been executed by the orchestrator
        // The leave record has been cancelled
        // Inform the client that submission failed
        return nil, status.Errorf(codes.FailedPrecondition,
            "leave submission failed: %v", sagaErr)
    }

    return &leavecmdpb.SubmitLeaveResponse{
        LeaveId: leaveID,
        Status:  "PENDING",
        Message: "Your leave application has been submitted and is awaiting approval.",
    }, nil
}
```

## The SAGA Recovery Worker — Handling Orchestrator Crashes

If the Leave Service crashes while executing a SAGA — say it crashes between Step 2 completion and Step 3 execution — the SAGA is stuck in `STEP_2_DONE` with no progress. Nobody is driving it forward. The SAGA Recovery Worker runs as a background goroutine and finds these stuck SAGAs, then resumes them.

```go
// leave/internal/saga/recovery_worker.go

package saga

type SagaRecoveryWorker struct {
    db           *gorm.DB
    orchestrator *LeaveSubmissionOrchestrator
    stuckAfter   time.Duration  // consider a SAGA stuck if no update for this long
    scanInterval time.Duration
    logger       *slog.Logger
}

func (w *SagaRecoveryWorker) Run(ctx context.Context) error {
    ticker := time.NewTicker(w.scanInterval)
    defer ticker.Stop()

    w.logger.Info("SAGA recovery worker started",
        "stuck_threshold", w.stuckAfter,
        "scan_interval", w.scanInterval,
    )

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            w.recoverStuckSagas(ctx)
        }
    }
}

func (w *SagaRecoveryWorker) recoverStuckSagas(ctx context.Context) {
    cutoff := time.Now().Add(-w.stuckAfter)

    var stuckSagas []LeaveSubmissionSaga
    w.db.WithContext(ctx).
        Where("status IN ? AND updated_at < ?",
            []SagaStatus{
                SagaStatusStarted,
                SagaStatusStep1Done,
                SagaStatusStep2Done,
                SagaStatusStep3Done,
            },
            cutoff,
        ).
        Find(&stuckSagas)

    if len(stuckSagas) > 0 {
        w.logger.Warn("found stuck SAGAs", "count", len(stuckSagas))
    }

    for _, saga := range stuckSagas {
        w.logger.Info("recovering stuck SAGA",
            "saga_id", saga.SagaID,
            "status", saga.Status,
            "last_updated", saga.UpdatedAt,
        )

        // Resume from where it left off — the command IDs are already in the DB
        // so idempotency guarantees that already-completed steps are skipped
        go func(s LeaveSubmissionSaga) {
            resumeCtx, cancel := context.WithTimeout(ctx, 60*time.Second)
            defer cancel()

            if err := w.resumeSaga(resumeCtx, &s); err != nil {
                w.logger.Error("SAGA recovery failed",
                    "saga_id", s.SagaID, "error", err)
            }
        }(saga)
    }
}

func (w *SagaRecoveryWorker) resumeSaga(ctx context.Context, saga *LeaveSubmissionSaga) error {
    w.logger.Info("resuming SAGA from step", "saga_id", saga.SagaID, "step", saga.CurrentStep)

    // Resume from the step AFTER the last completed one
    // The already-completed steps' command IDs are already in ProcessedSagaCommand table
    // so calling them again is safe — idempotency will skip re-execution
    switch saga.Status {
    case SagaStatusStarted, SagaStatusStep1Done:
        // Need to execute steps 2, 3, 4
        if err := w.orchestrator.executeStep2(ctx, saga); err != nil {
            return w.orchestrator.compensateFromStep1(ctx, saga, err)
        }
        if err := w.orchestrator.executeStep3(ctx, saga); err != nil {
            return w.orchestrator.compensateFromStep2(ctx, saga, err)
        }
        w.orchestrator.executeStep4(ctx, saga)

    case SagaStatusStep2Done:
        // Need to execute steps 3, 4
        if err := w.orchestrator.executeStep3(ctx, saga); err != nil {
            return w.orchestrator.compensateFromStep2(ctx, saga, err)
        }
        w.orchestrator.executeStep4(ctx, saga)

    case SagaStatusStep3Done:
        // Only notification remaining
        w.orchestrator.executeStep4(ctx, saga)
    }

    now := time.Now()
    w.orchestrator.db.Model(saga).Updates(map[string]interface{}{
        "status":       SagaStatusCompleted,
        "completed_at": &now,
    })

    w.logger.Info("SAGA recovered and completed", "saga_id", saga.SagaID)
    return nil
}
```

## When gRPC SAGA Falls Short — And What To Do About It

Now that you have the full gRPC SAGA implementation, be honest about its limitations so you know when it is the wrong tool.

The gRPC SAGA is synchronous. The `SubmitLeave` gRPC call from the API Gateway to the Leave Service does not return until all four SAGA steps have completed — or until compensation has finished. If Step 3 takes 8 seconds because the Approval Service is under load, the client waits 8 seconds. If you have 100 concurrent leave submissions and each step averages 100ms, that is fine. But if any step can take more than a few seconds, you start holding goroutines open in the Leave Service and the API Gateway, which limits throughput.

The solution for long-running steps is to make the SAGA asynchronous at the API boundary. The client submits the leave and immediately gets back a `202 Accepted` with a `job_id`. The SAGA runs in the background. The client polls `GET /leaves/{id}/status` to check when it completes. The SAGA orchestrator still runs synchronously internally — using gRPC — but the client is no longer waiting.

The other limitation is that if the Leave Service crashes while the SAGA is in flight, the Recovery Worker must discover and resume the stuck SAGA. With Kafka, the orchestrator would simply republish the command event and it would be re-processed. With gRPC, the Recovery Worker adds this durability layer.

For the HR360 system, gRPC SAGAs handle the user-facing flows — leave submission, expense submission, profile updates. Kafka SAGAs handle the background batch flows — payroll processing, year-end balance carryforward, bulk employee imports. Each transport is used where it genuinely fits. That combination — not a single tool for everything — is what makes the system both fast for users and reliable for operations.
