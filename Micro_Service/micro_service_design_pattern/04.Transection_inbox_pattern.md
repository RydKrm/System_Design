# The Transactional Inbox Pattern in Microservices

### Everything You Need to Know — Explained Like You Just Joined the Team

---

## Where We Are in the Story

You have already learned two complementary patterns. The Outbox Pattern solved the problem on the publisher side — how do you guarantee that a database write and a Kafka publish happen together, atomically, without losing an event if your service crashes? The answer was to write both into the same database transaction and let a background relay handle the Kafka publishing.

Now we are on the other side of Kafka. A message has been published. It is sitting in a Kafka topic partition. Your service is a consumer. It reads the message. And now it faces the exact same class of problem, but in reverse: how do you guarantee that processing the message and updating your database happen together, atomically, without processing the message twice or losing it if your service crashes at the wrong moment?

The Transactional Inbox Pattern is the answer to that question. It is the consumer-side mirror of the Outbox Pattern. Together, the two patterns form a complete, end-to-end reliable messaging system — one that can survive crashes, network failures, and restarts at any point without losing data or producing duplicate side effects.

---

## The Problem the Inbox Pattern Solves

Let me show you the naive implementation of a Kafka consumer first, so you can feel exactly where it breaks.

```go
// Naive consumer — looks correct, but has two fatal failure modes

func (c *BalanceConsumer) ConsumeLeaveCreated(ctx context.Context) {
    for {
        msg, err := c.reader.ReadMessage(ctx)
        if err != nil {
            continue
        }

        var event LeaveCreatedEvent
        json.Unmarshal(msg.Value, &event)

        // ⚠️ FAILURE MODE 1: What if the service crashes right here?
        // The message was read but the offset has not been committed.
        // Kafka will re-deliver it. We process it twice.

        // Business logic — deduct leave balance
        err = c.deductBalance(event.EmployeeID, event.Days)

        // ⚠️ FAILURE MODE 2: What if the service crashes right here?
        // The balance was deducted but the offset has not been committed.
        // Kafka will re-deliver the message. We deduct twice.

        // Commit the offset to tell Kafka we are done with this message
        c.reader.CommitMessages(ctx, msg)

        // ⚠️ FAILURE MODE 3: What if the commit succeeds but
        // the response gets lost? Same double-processing problem.
    }
}
```

There are exactly two orderings you can try, and both of them are broken in different ways.

```
ORDERING 1: Process first, then commit offset
──────────────────────────────────────────────

  Read message from Kafka
         │
         ▼
  Deduct balance in DB  ← succeeds ✓
         │
         │  ⚡ SERVICE CRASHES HERE ⚡
         │
         ▼
  Commit Kafka offset   ← NEVER RUNS

  RESULT: Kafka thinks message was not processed.
  On restart, same message is delivered again.
  Balance is deducted a second time. ← DOUBLE CHARGE


ORDERING 2: Commit offset first, then process
───────────────────────────────────────────────

  Read message from Kafka
         │
         ▼
  Commit Kafka offset   ← succeeds ✓
         │
         │  ⚡ SERVICE CRASHES HERE ⚡
         │
         ▼
  Deduct balance in DB  ← NEVER RUNS

  RESULT: Kafka thinks message was processed.
  On restart, it moves to the next message.
  Balance is NEVER deducted. ← SILENT DATA LOSS
```

Both orderings have a crash window. Processing before committing risks double-processing. Committing before processing risks silent data loss. There is no way to make these two operations atomic with respect to each other using only Kafka's offset commit mechanism — because Kafka and your database are two separate systems, and there is no distributed transaction that spans both.

This is the same dual-write problem as before, but now it is on the consumer side. And the solution follows the same principle: collapse two separate writes into one atomic database transaction first, and then handle Kafka separately with a background process.

```
THE CORE INSIGHT
─────────────────

Naive approach: two separate systems, no atomicity
  Kafka offset commit  +  DB write  =  crash window between them

Inbox approach: collapse both into ONE database transaction first
  DB write (inbox row + business write)  =  atomic
  Kafka offset commit  =  happens after, safely
```

## What the Transactional Inbox Pattern Actually Is

The Transactional Inbox Pattern works like this. When your service reads a message from Kafka, instead of processing it immediately, it first writes the raw message into a special inbox table in its own database — in a transaction that also includes a check to ensure the message has not been seen before. A separate background processor then reads from the inbox table, processes each message, and marks it as processed — all within a single database transaction.

The Kafka offset commit happens after the message is safely stored in the inbox. From that point on, Kafka is no longer responsible for ensuring the message is processed — your database is. The inbox becomes a durable, database-backed queue that survives any crash.

```
THE TRANSACTIONAL INBOX — Core Flow
──────────────────────────────────────

  Apache Kafka
  (topic: leave.events)
         │
         │  Consumer reads message
         ▼
  ┌──────────────────────────────────────────────────┐
  │  Balance Service                                 │
  │                                                  │
  │  Step 1: Write message to inbox table            │
  │  ┌────────────────────────────────────────────┐  │
  │  │  Single DB Transaction                     │  │
  │  │  ─────────────────────────────────────     │  │
  │  │  Check: message_id already exists? ──NO──► │  │
  │  │  INSERT into inbox_messages (raw msg)       │  │
  │  │  status: PENDING                            │  │
  │  └────────────────────────────────────────────┘  │
  │         │                                        │
  │         ▼                                        │
  │  Step 2: Commit Kafka offset                     │
  │  (safe now — message is durable in DB)           │
  │                                                  │
  │  Step 3: Inbox Processor (background goroutine)  │
  │  ┌────────────────────────────────────────────┐  │
  │  │  Single DB Transaction                     │  │
  │  │  ─────────────────────────────────────     │  │
  │  │  Read PENDING message from inbox           │  │
  │  │  Execute business logic (deduct balance)   │  │
  │  │  Mark inbox message as PROCESSED           │  │
  │  └────────────────────────────────────────────┘  │
  └──────────────────────────────────────────────────┘
```

Now let us walk through every failure scenario and see that the system handles all of them correctly.

```
CRASH SAFETY ANALYSIS — EVERY FAILURE SCENARIO
────────────────────────────────────────────────────────────────────────────

Scenario 1: Crash during inbox insert (before commit)
  DB state:    inbox row ROLLED BACK — does not exist
  Kafka state: offset NOT committed
  On restart:  Kafka re-delivers message ──► insert into inbox ──► process ✓

Scenario 2: Crash after inbox insert, before Kafka offset commit
  DB state:    inbox row EXISTS (status: PENDING)
  Kafka state: offset NOT committed
  On restart:  Kafka re-delivers message ──► insert attempt fails on duplicate
               check ──► skip insert ──► commit offset ──► inbox processor
               processes existing row ✓

Scenario 3: Crash after Kafka offset commit, before inbox processing
  DB state:    inbox row EXISTS (status: PENDING)
  Kafka state: offset committed (Kafka moves on)
  On restart:  Inbox processor finds PENDING row ──► processes it ✓

Scenario 4: Crash during business logic (inside processor transaction)
  DB state:    business write ROLLED BACK, inbox row stays PENDING
  Kafka state: offset committed (does not matter — inbox owns the message now)
  On restart:  Inbox processor finds PENDING row ──► retries ✓

Scenario 5: Crash after business logic, before marking PROCESSED
  DB state:    business write ROLLED BACK (same transaction), row stays PENDING
  On restart:  Inbox processor finds PENDING row ──► retries ✓

────────────────────────────────────────────────────────────────────────────
No scenario results in silent data loss or permanent inconsistency.
In every crash scenario, the message is either safely pending in the inbox
or already processed — never lost, never permanently duplicated.
```

## The Inbox Table Schema

Just like the outbox table, the inbox table lives inside the service's own database. Every service that consumes Kafka messages should have one.

```sql
CREATE TABLE inbox_messages (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    message_id      VARCHAR(255) NOT NULL,    -- Kafka message ID or outbox-event-id header
    topic           VARCHAR(255) NOT NULL,    -- Kafka topic the message came from
    partition       INT NOT NULL,             -- Kafka partition number
    offset          BIGINT NOT NULL,          -- Kafka offset within the partition
    event_type      VARCHAR(255) NOT NULL,    -- e.g. "LeaveCreated"
    aggregate_type  VARCHAR(255) NOT NULL,    -- e.g. "Leave"
    aggregate_id    VARCHAR(255) NOT NULL,    -- e.g. the leave_id
    payload         JSONB NOT NULL,           -- the raw message body
    status          VARCHAR(50) NOT NULL DEFAULT 'PENDING',  -- PENDING, PROCESSING, PROCESSED, FAILED
    received_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    processed_at    TIMESTAMPTZ,
    retry_count     INT NOT NULL DEFAULT 0,
    last_error      TEXT,

    -- This is the critical idempotency constraint
    UNIQUE (message_id)
);

-- Index for the processor to find pending messages efficiently
CREATE INDEX idx_inbox_pending ON inbox_messages (received_at)
    WHERE status = 'PENDING';

-- Index for finding stuck PROCESSING messages (crash recovery)
CREATE INDEX idx_inbox_processing ON inbox_messages (received_at)
    WHERE status = 'PROCESSING';
```

The `UNIQUE (message_id)` constraint is the heart of the idempotency guarantee. If Kafka re-delivers a message that has already been written to the inbox, the INSERT will fail on this constraint, and the consumer knows to skip the message safely. No business logic is duplicated.

The `message_id` comes from the Kafka message headers. If the publisher used the Outbox Pattern (as we do), the outbox worker stamps every message with an `outbox-event-id` header containing the UUID of the outbox row. That UUID is globally unique and stable across re-deliveries — the same message will always have the same `outbox-event-id`. This is the perfect identifier to use as `message_id` in the inbox.

In Go with GORM:

```go
type InboxMessage struct {
    ID            uuid.UUID      `gorm:"type:uuid;primaryKey;default:gen_random_uuid()"`
    MessageID     string         `gorm:"uniqueIndex;not null"`
    Topic         string         `gorm:"not null"`
    Partition     int32          `gorm:"not null"`
    Offset        int64          `gorm:"not null"`
    EventType     string         `gorm:"not null"`
    AggregateType string         `gorm:"not null"`
    AggregateID   string         `gorm:"not null;index"`
    Payload       datatypes.JSON `gorm:"type:jsonb;not null"`
    Status        string         `gorm:"not null;default:'PENDING';index"`
    ReceivedAt    time.Time      `gorm:"not null;default:now()"`
    ProcessedAt   *time.Time
    RetryCount    int            `gorm:"not null;default:0"`
    LastError     *string
}
```

## Implementation — Part 1: The Kafka Consumer Writing to the Inbox

The first half of the Inbox Pattern is the Kafka consumer itself. Its only job is to read messages and write them to the inbox table — nothing more. It should not execute any business logic. It should not call any other services. It should just persist the raw message and move on.

```go
// inbox/consumer.go

package inbox

type KafkaInboxConsumer struct {
    db     *gorm.DB
    reader *kafka.Reader
    logger *slog.Logger
}

func (c *KafkaInboxConsumer) Run(ctx context.Context) error {
    c.logger.Info("inbox consumer started", "topic", c.reader.Config().Topic)

    for {
        // ReadMessage blocks until a message arrives or context is cancelled
        msg, err := c.reader.FetchMessage(ctx)
        if err != nil {
            if errors.Is(err, context.Canceled) {
                return nil
            }
            c.logger.Error("failed to fetch message", "error", err)
            continue
        }

        if err := c.writeToInbox(ctx, msg); err != nil {
            c.logger.Error("failed to write to inbox", "error", err,
                "topic", msg.Topic,
                "partition", msg.Partition,
                "offset", msg.Offset,
            )
            // Do NOT commit the offset — we want Kafka to re-deliver this message
            continue
        }

        // Only commit the offset AFTER the message is safely in our inbox
        if err := c.reader.CommitMessages(ctx, msg); err != nil {
            c.logger.Error("failed to commit offset", "error", err)
            // The inbox row already exists. If Kafka re-delivers, the
            // UNIQUE constraint will catch the duplicate. This is safe.
        }
    }
}

func (c *KafkaInboxConsumer) writeToInbox(ctx context.Context, msg kafka.Message) error {
    // Extract the stable message ID from headers
    messageID := extractHeader(msg.Headers, "outbox-event-id")
    if messageID == "" {
        // Fallback: construct a stable ID from topic+partition+offset
        // This uniquely identifies any Kafka message
        messageID = fmt.Sprintf("%s-%d-%d", msg.Topic, msg.Partition, msg.Offset)
    }

    eventType     := extractHeader(msg.Headers, "event-type")
    aggregateType := extractHeader(msg.Headers, "aggregate-type")

    // Parse aggregate ID from the message key (set by the outbox worker)
    aggregateID := string(msg.Key)

    inboxMsg := &InboxMessage{
        MessageID:     messageID,
        Topic:         msg.Topic,
        Partition:     msg.Partition,
        Offset:        msg.Offset,
        EventType:     eventType,
        AggregateType: aggregateType,
        AggregateID:   aggregateID,
        Payload:       msg.Value,
        Status:        "PENDING",
    }

    // Use INSERT ... ON CONFLICT DO NOTHING for idempotency
    // If the message already exists (re-delivery), silently skip
    result := c.db.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns:   []clause.Column{{Name: "message_id"}},
            DoNothing: true,
        }).
        Create(inboxMsg)

    return result.Error
}

func extractHeader(headers []kafka.Header, key string) string {
    for _, h := range headers {
        if h.Key == key {
            return string(h.Value)
        }
    }
    return ""
}
```

Notice `ON CONFLICT DO NOTHING` on the insert. This is the exact SQL equivalent of the `UNIQUE (message_id)` constraint doing its job. If Kafka re-delivers a message that is already in the inbox, this clause silently skips the insert and returns no error. The consumer then happily commits the Kafka offset and moves on. The existing inbox row — whether still PENDING or already PROCESSED — handles the rest.

## Implementation — Part 2: The Inbox Processor

The inbox processor is a background goroutine that polls the inbox table for PENDING messages and processes them one by one. This is where your actual business logic lives. The critical rule is that the business logic and the status update must happen in the same database transaction.

```go
// inbox/processor.go

package inbox

type InboxProcessor struct {
    db           *gorm.DB
    handlers     map[string]MessageHandler  // event_type ──► handler function
    pollInterval time.Duration
    batchSize    int
    logger       *slog.Logger
}

// MessageHandler is the interface each business handler must implement
type MessageHandler func(ctx context.Context, tx *gorm.DB, msg InboxMessage) error

func (p *InboxProcessor) RegisterHandler(eventType string, handler MessageHandler) {
    p.handlers[eventType] = handler
}

func (p *InboxProcessor) Run(ctx context.Context) error {
    ticker := time.NewTicker(p.pollInterval)
    defer ticker.Stop()

    p.logger.Info("inbox processor started")

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            if err := p.processBatch(ctx); err != nil {
                p.logger.Error("inbox processor batch failed", "error", err)
            }
        }
    }
}

func (p *InboxProcessor) processBatch(ctx context.Context) error {
    var messages []InboxMessage

    // Claim a batch atomically using SELECT FOR UPDATE SKIP LOCKED
    // This prevents multiple processor instances from picking the same messages
    err := p.db.WithContext(ctx).
        Where("status = ?", "PENDING").
        Where("retry_count < ?", 5).
        Order("received_at ASC").
        Limit(p.batchSize).
        Clauses(clause.Locking{Strength: "UPDATE", Options: "SKIP LOCKED"}).
        Find(&messages).Error

    if err != nil {
        return fmt.Errorf("failed to fetch pending messages: %w", err)
    }

    for _, msg := range messages {
        if err := p.processOne(ctx, msg); err != nil {
            p.logger.Error("failed to process inbox message",
                "message_id", msg.MessageID,
                "event_type", msg.EventType,
                "error", err,
            )
        }
    }

    return nil
}

func (p *InboxProcessor) processOne(ctx context.Context, msg InboxMessage) error {
    handler, ok := p.handlers[msg.EventType]
    if !ok {
        // No handler registered for this event type — mark as processed and skip
        p.logger.Warn("no handler registered for event type",
            "event_type", msg.EventType,
        )
        return p.db.Model(&msg).Updates(map[string]interface{}{
            "status":       "PROCESSED",
            "processed_at": time.Now(),
        }).Error
    }

    // CRITICAL: Mark as PROCESSING first to prevent other processor instances
    // from picking up the same message during processing
    if err := p.db.Model(&msg).Update("status", "PROCESSING").Error; err != nil {
        return err
    }

    // Execute handler + mark as PROCESSED in ONE transaction
    err := p.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // Run the actual business logic
        if err := handler(ctx, tx, msg); err != nil {
            return err
        }

        // Mark as processed inside the same transaction
        now := time.Now()
        return tx.Model(&msg).Updates(map[string]interface{}{
            "status":       "PROCESSED",
            "processed_at": &now,
        }).Error

        // If business logic fails: BOTH the business write AND the
        // status update roll back. Message stays PROCESSING.
        // Cleanup goroutine will reset it to PENDING for retry.
    })

    if err != nil {
        // Update retry count and record the error
        errMsg := err.Error()
        p.db.Model(&msg).Updates(map[string]interface{}{
            "status":      "PENDING",  // reset for retry
            "retry_count": gorm.Expr("retry_count + 1"),
            "last_error":  &errMsg,
        })
        return err
    }

    return nil
}
```

Now here is how the Balance Service registers its handler — the actual business logic:

```go
// balance/consumer_setup.go

func SetupBalanceInboxProcessor(db *gorm.DB, balanceRepo *BalanceRepository) *inbox.InboxProcessor {
    processor := inbox.NewInboxProcessor(db,
        inbox.WithPollInterval(100*time.Millisecond),
        inbox.WithBatchSize(50),
    )

    // Register handler for LeaveCreated events
    processor.RegisterHandler("LeaveCreated", func(ctx context.Context, tx *gorm.DB, msg inbox.InboxMessage) error {
        var event LeaveCreatedEvent
        if err := json.Unmarshal(msg.Payload, &event); err != nil {
            return fmt.Errorf("failed to unmarshal LeaveCreated: %w", err)
        }

        // Business logic — all using the transaction 'tx'
        var balance EmployeeLeaveBalance
        if err := tx.Where("employee_id = ?", event.EmployeeID).First(&balance).Error; err != nil {
            return fmt.Errorf("employee balance not found: %w", err)
        }

        if balance.AvailableDays < event.Days {
            // Cannot process — not enough balance
            // In a SAGA context, the orchestrator should be notified
            // That notification also goes through the outbox (combined inbox+outbox pattern)
            return fmt.Errorf("insufficient balance: need %d, have %d", event.Days, balance.AvailableDays)
        }

        balance.AvailableDays -= event.Days
        balance.UsedDays += event.Days

        if err := tx.Save(&balance).Error; err != nil {
            return fmt.Errorf("failed to save balance: %w", err)
        }

        // If we also need to publish an outgoing event (e.g. "BalanceDeducted"),
        // we write to our OWN outbox table — in this same transaction
        payload, _ := json.Marshal(BalanceDeductedPayload{
            LeaveID:    event.LeaveID,
            EmployeeID: event.EmployeeID,
            DaysUsed:   event.Days,
        })
        return tx.Create(&outbox.OutboxEvent{
            AggregateID:   event.LeaveID,
            AggregateType: "Leave",
            EventType:     "BalanceDeducted",
            Topic:         "balance.events",
            Payload:       payload,
            Published:     false,
        }).Error

        // This single transaction atomically:
        // 1. Deducts the leave balance
        // 2. Marks the inbox message as PROCESSED
        // 3. Writes the outgoing BalanceDeducted event to the outbox
        // All three, or none. No crash window anywhere.
    })

    return processor
}
```

This last example is important enough to draw out. Notice that the handler writes to its own outbox table inside the same transaction. This is the Inbox and Outbox patterns working together — the full reliable messaging loop.

```
INBOX + OUTBOX COMBINED — The Complete Reliable Messaging Loop
───────────────────────────────────────────────────────────────

  Kafka (leave.events topic)
         │
         │  Consumer reads "LeaveCreated" message
         ▼
  ┌────────────────────────────────────────────────────────────┐
  │  Balance Service                                           │
  │                                                            │
  │  Step 1: Inbox Consumer writes to inbox table             │
  │  ┌─────────────────────────────────────────────────────┐  │
  │  │  DB Transaction                                     │  │
  │  │  INSERT into inbox_messages (message_id, payload)   │  │
  │  │  ON CONFLICT DO NOTHING                             │  │
  │  └─────────────────────────────────────────────────────┘  │
  │  Commit Kafka offset                                       │
  │                                                            │
  │  Step 2: Inbox Processor (background goroutine)            │
  │  ┌─────────────────────────────────────────────────────┐  │
  │  │  Single DB Transaction                              │  │
  │  │  ─────────────────────────────────────────────      │  │

  │  │    - event.Days (business logic)                    │  │
  │  │                                                     │  │
  │  │  INSERT into balance_outbox (BalanceDeducted event) │  │
  │  │    status: PENDING                                  │  │
  │  │                                                     │  │
  │  │  UPDATE inbox_messages SET status = 'PROCESSED'     │  │
  │  │                                                     │  │
  │  │  COMMIT — all three writes are atomic               │  │
  │  └─────────────────────────────────────────────────────┘  │
  │                                                            │
  │  Step 3: Outbox Worker (background goroutine)              │
  │  Reads BalanceDeducted from outbox ──► publishes to Kafka  │
  └────────────────────────────────────────────────────────────┘
         │
         ▼
  Kafka (balance.events topic)
  "BalanceDeducted" message delivered to next consumer
```

This is the full reliable chain. A message comes in through Kafka, lands safely in the inbox, gets processed atomically with its outgoing event written to the outbox, and the outbox worker carries the outgoing event to Kafka for the next service. At no point in this chain is there a crash window where data can be silently lost or silently duplicated.

## Handling Stuck PROCESSING Messages — The Recovery Goroutine

There is one subtle failure mode in the processor that needs special handling. When the processor marks a message as PROCESSING and then crashes before completing the transaction, the message stays in the PROCESSING state forever. The next time the processor starts up, it will not pick up this message because it only queries for PENDING messages.

You need a recovery goroutine that periodically looks for messages that have been stuck in PROCESSING for too long — say, more than two minutes — and resets them to PENDING so they can be retried.

```go
// inbox/recovery.go

type RecoveryWorker struct {
    db              *gorm.DB
    stuckThreshold  time.Duration  // e.g. 2 minutes
    recoveryInterval time.Duration // e.g. 1 minute
    logger          *slog.Logger
}

func (r *RecoveryWorker) Run(ctx context.Context) error {
    ticker := time.NewTicker(r.recoveryInterval)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            cutoff := time.Now().Add(-r.stuckThreshold)

            result := r.db.WithContext(ctx).
                Model(&InboxMessage{}).
                Where("status = ? AND updated_at < ?", "PROCESSING", cutoff).
                Updates(map[string]interface{}{
                    "status":      "PENDING",
                    "retry_count": gorm.Expr("retry_count + 1"),
                    "last_error":  "recovered from stuck PROCESSING state",
                })

            if result.Error != nil {
                r.logger.Error("recovery scan failed", "error", result.Error)
                continue
            }

            if result.RowsAffected > 0 {
                r.logger.Warn("recovered stuck messages",
                    "count", result.RowsAffected,
                )
            }
        }
    }
}
```

```
STUCK MESSAGE RECOVERY FLOW
─────────────────────────────

  t=0:00  Processor marks message as PROCESSING
  t=0:00  Processor crashes during business logic

  t=1:00  Recovery worker runs, finds no stuck messages yet
          (2 minute threshold not exceeded)

  t=2:01  Recovery worker runs again
          Finds message stuck in PROCESSING for > 2 minutes
          Resets to PENDING, increments retry_count

  t=2:01  Inbox Processor picks up PENDING message
          Retries the business logic
          Succeeds this time → marks PROCESSED ✓
```

## Inbox Variant 2 — Per-Event-Type Handler Routing With a Registry

In the basic implementation, you register handlers directly on the processor with a map. As the number of event types grows — LeaveCreated, LeaveApproved, LeaveCancelled, EmployeeUpdated, ApprovalDecided — this map registration in `main.go` becomes unwieldy. The cleaner approach is a handler registry where each service registers its own handlers independently, and the processor discovers them at startup.

```go
// inbox/registry.go

type HandlerRegistry struct {
    handlers map[string]MessageHandler
    mu       sync.RWMutex
}

var globalRegistry = &HandlerRegistry{
    handlers: make(map[string]MessageHandler),
}

func Register(eventType string, handler MessageHandler) {
    globalRegistry.mu.Lock()
    defer globalRegistry.mu.Unlock()
    globalRegistry.handlers[eventType] = handler
}

func GetHandler(eventType string) (MessageHandler, bool) {
    globalRegistry.mu.RLock()
    defer globalRegistry.mu.RUnlock()
    h, ok := globalRegistry.handlers[eventType]
    return h, ok
}
```

```go
// balance/handlers.go — handlers register themselves via init()

func init() {
    inbox.Register("LeaveCreated",  handleLeaveCreated)
    inbox.Register("LeaveApproved", handleLeaveApproved)
    inbox.Register("LeaveCancelled", handleLeaveCancelled)
}

func handleLeaveCreated(ctx context.Context, tx *gorm.DB, msg inbox.InboxMessage) error {
    var event LeaveCreatedEvent
    json.Unmarshal(msg.Payload, &event)
    // ... deduct balance
    return nil
}

func handleLeaveApproved(ctx context.Context, tx *gorm.DB, msg inbox.InboxMessage) error {
    var event LeaveApprovedEvent
    json.Unmarshal(msg.Payload, &event)
    // ... update balance status to confirmed
    return nil
}

    var event LeaveCancelledEvent
    json.Unmarshal(msg.Payload, &event)
    // ... restore balance (compensating action)
    return nil
}
```

```go

    _ "yourproject/balance/handlers"  // side-effect import triggers init()

    // Registry is populated. Just start the processor.
```

This pattern scales cleanly. Adding a new event handler means adding a new function in the handlers file and registering it in `init()`. The processor itself never needs to change.

## Inbox Variant 3 — Multi-Topic Consumer With a Single Inbox Table

In our system, the Balance Service might need to consume events from multiple Kafka topics — `leave.events` for leave-related events, and perhaps `policy.events` for when leave policy rules change. Naively, you might spin up separate consumer goroutines for each topic. But then you have multiple consumers all writing to the same inbox table, which works fine. The inbox table's `topic` column records where each message came from, and the `event_type` column routes it to the right handler.

```go
// inbox/multi_consumer.go

type MultiTopicInboxConsumer struct {
    db      *gorm.DB
    readers map[string]*kafka.Reader  // topic ──► reader
    logger  *slog.Logger
}

func (m *MultiTopicInboxConsumer) Run(ctx context.Context) error {
    g, ctx := errgroup.WithContext(ctx)

    for topic, reader := range m.readers {
        topic, reader := topic, reader  // capture for goroutine
        g.Go(func() error {
            consumer := &KafkaInboxConsumer{
                db:     m.db,
                reader: reader,
                logger: m.logger.With("topic", topic),
            }
            return consumer.Run(ctx)
        })
    }

    return g.Wait()
}
```

```

  │   leave.events      │   │   policy.events     │
```

## Inbox Variant 4 — Dead Letter Inbox for Permanently Failed Messages

Some messages will fail processing repeatedly — not because of transient errors like network blips, but because of permanent problems like a malformed payload, a missing referenced entity, or a bug in the handler code. After five retries, the message should be moved to a dead letter inbox rather than retried forever.

```go
// inbox/dead_letter.go

type DeadLetterWorker struct {
    db              *gorm.DB
    maxRetries      int
    scanInterval    time.Duration
    alerter         Alerter  // sends Slack/PagerDuty alert
    logger          *slog.Logger
}

func (d *DeadLetterWorker) Run(ctx context.Context) error {
    ticker := time.NewTicker(d.scanInterval)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            d.movePermanentFailures(ctx)
        }
    }
}

func (d *DeadLetterWorker) movePermanentFailures(ctx context.Context) {
    var failed []InboxMessage

    d.db.WithContext(ctx).
        Where("status = ? AND retry_count >= ?", "PENDING", d.maxRetries).
        Find(&failed)

    for _, msg := range failed {
        // Move to dead letter table
        dlq := DeadLetterMessage{
            OriginalMessageID: msg.MessageID,
            Topic:             msg.Topic,
            EventType:         msg.EventType,
            Payload:           msg.Payload,
            LastError:         msg.LastError,
            RetryCount:        msg.RetryCount,
            MovedAt:           time.Now(),
        }

        d.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
            if err := tx.Create(&dlq).Error; err != nil {
                return err
            }
            return tx.Model(&msg).Update("status", "DEAD_LETTERED").Error
        })

        // Alert on-call engineers — this needs human attention
        d.alerter.Alert(fmt.Sprintf(
            "INBOX DLQ: message %s (type: %s) permanently failed after %d retries. Last error: %s",
            msg.MessageID, msg.EventType, msg.RetryCount, *msg.LastError,
        ))
    }
}
```

```
DEAD LETTER FLOW
──────────────────

  inbox_messages table
  ┌────────────────────────────────────────────────────┐
  │ message_id │ status  │ retry_count │ last_error    │
  ├────────────────────────────────────────────────────┤
  │ uuid-001   │ PENDING │      5      │ "employee not │
  │            │         │             │  found: E999" │
  └────────────────────────────────────────────────────┘
                       │
                       │ Dead Letter Worker finds retry_count >= 5
                       ▼
  dead_letter_messages table          Alerter
  ┌─────────────────────────┐        ┌────────────────┐
  │ original_message_id     │        │ PagerDuty /    │
```

## Inbox Cleanup — Same as Outbox, Same Reasoning

Processed inbox messages accumulate over time just like outbox rows. PROCESSED and DEAD_LETTERED rows should be archived or deleted after a retention window. The cleanup logic is identical to the outbox cleanup worker — a background goroutine running on a timer, deleting in batches, respecting a retention period for auditability.

Keep DEAD_LETTERED rows longer than PROCESSED rows. Dead-lettered messages are failure evidence. You may need to inspect the payload and replay the message after fixing a bug. A 30-day retention on dead-lettered messages and a 7-day retention on successfully processed messages is a reasonable default.

## The Mental Model That Ties It All Together

You have now learned three interconnected patterns. Let me give you the mental model that shows how they relate.

The Outbox Pattern says: when you write to your database, tell the world by writing an event into the same transaction. A background relay will carry that event to Kafka reliably.

The Transactional Inbox Pattern says: when the world tells you something via Kafka, write the raw message into your database first. A background processor will handle it reliably, exactly once.

The SAGA Pattern says: chain these reliable message deliveries together across multiple services to implement a distributed business transaction that either completes fully or compensates cleanly.

```
THE THREE PATTERNS AS ONE SYSTEM
──────────────────────────────────

  ┌─────────────────────────────────────────────────────────────┐
  │              SAGA (orchestrates the full flow)              │
  │                                                             │
  │  Service A ──────────────────────────────────► Service B    │
  │     │                                              │        │
  │  OUTBOX           Kafka           INBOX         OUTBOX      │
  │  (reliable        (transport)     (reliable     (next msg)  │
  │   publish)                         receive)                 │
  │                                                             │
  │  Guarantees:                                                │
  │  ├── No message lost between publish and Kafka   (Outbox)   │
  │  ├── No message lost between Kafka and process   (Inbox)    │
  │  └── Business transaction completes or compensates (SAGA)   │
  └─────────────────────────────────────────────────────────────┘
```

Each pattern solves exactly one problem with precision. The Outbox solves the publisher's dual-write problem. The Inbox solves the consumer's dual-write problem. The SAGA coordinates the sequence of events across services. Together they give you a distributed system that is as reliable as a monolith with a single database transaction — without sacrificing the independence, scalability, and resilience that microservices are built for.

This is what production-grade event-driven architecture looks like. Every message that flows through this system, from a leave application being submitted to a manager receiving an email three services later, does so without any possibility of silent loss or silent duplication — regardless of when or where a crash occurs.
