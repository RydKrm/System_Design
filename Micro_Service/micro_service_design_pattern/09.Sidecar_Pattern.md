# The Sidecar Pattern in Microservices

### Everything You Need to Know — Explained Like You Just Joined the Team

---

## A Story From the Road

Picture a motorcycle with a sidecar attached to it. The motorcycle is the primary vehicle — it has its own engine, its own wheels, its own steering. It does the actual work of getting from point A to point B. The sidecar does not have its own engine. It does not drive. It cannot exist on its own. But it travels everywhere the motorcycle goes, and it carries things the motorcycle cannot carry by itself — a passenger, luggage, equipment that would be awkward or impossible to attach to the motorcycle directly.

The relationship is deliberately asymmetric. The motorcycle does not need to know what is in the sidecar in order to do its job. The sidecar does not care where the motorcycle is going. The sidecar just extends the motorcycle's capabilities without changing what the motorcycle fundamentally is.

This is the Sidecar Pattern in software. Your main service is the motorcycle. The sidecar is a secondary process running alongside it — in the same deployment unit but as a separate process — that handles cross-cutting concerns so the main service does not have to. The main service focuses entirely on business logic. The sidecar handles everything else.

---

## The Problem That Sidecar Pattern Solves

To feel the problem, imagine what happens without the Sidecar Pattern in a microservice system with twelve services.

Every service needs TLS termination for encrypted communication. Every service needs to log in a structured format and ship those logs to Elasticsearch. Every service needs to expose Prometheus metrics in a specific format. Every service needs distributed tracing with OpenTelemetry span context propagation. Every service needs health check endpoints. Every service needs to handle secret rotation from Vault. Every service needs rate limiting. Every service needs retry logic and circuit breaking for outbound calls.

That is eight separate cross-cutting concerns. In a system without the Sidecar Pattern, each of these must be implemented in every single one of the twelve services — individually, often slightly differently because different engineers made different choices, using different library versions, with different bugs, maintained by different teams. When a security vulnerability is found in the TLS library, you have twelve services to patch. When the log format standard changes, you have twelve services to update. When you need to add a new cross-cutting capability — say, mutual TLS between all services — you have twelve services to modify.

## What the Sidecar Pattern Actually Is

The Sidecar Pattern is a deployment pattern where you run a secondary process alongside your main service process, co-located in the same deployment unit (a Kubernetes Pod, a Docker Compose service group, or a VM), but as a completely separate process. The sidecar and the main service share the same network namespace and the same filesystem mounts, which allows them to communicate via localhost with zero network latency, and to share configuration files or Unix domain sockets.

The sidecar handles cross-cutting infrastructure concerns. The main service only ever talks to localhost — it never directly touches the network for TLS, never directly calls a log aggregator, never directly instruments itself for Prometheus. The sidecar intercepts all of that.

```
SIDECAR DEPLOYMENT UNIT (Kubernetes Pod or Docker Compose Group)
────────────────────────────────────────────────────────────────

  ┌──────────────────────────────────────────────────────────────────┐
  │                    Single Deployment Unit                        │
  │  (shared network namespace, shared filesystem mounts)            │
  │                                                                  │
  │  ┌──────────────────────────┐   ┌──────────────────────────┐   │
  │  │     Main Service         │   │       Sidecar            │   │
  │  │  (Leave Service in Go)   │   │  (infrastructure proxy)  │   │
  │  │                          │   │                          │   │
  │  │  Listens: localhost:8080 │◄──┤  Forwards to: :8080     │   │
  │  │                          │   │  Listens: 0.0.0.0:443   │   │
  │  │  Calls: localhost:9090   ├──►│  Forwards to: remote:443│   │
  │  │  (all outbound via       │   │  Handles TLS for both   │   │
  │  │   sidecar on localhost)  │   │  directions             │   │
  │  │                          │   │                          │   │
  │  └──────────────────────────┘   └──────────────────────────┘   │
  │                                                                  │
  │  Shared volumes:                                                 │
  │    /var/run/sidecar.sock  ── Unix domain socket for IPC         │
  │    /etc/secrets/          ── Shared secret files                 │
  │    /var/log/app/          ── Shared log directory               │
  └──────────────────────────────────────────────────────────────────┘
                │
                │ External network
                ▼
          Other services,
          Kafka, databases,
          external APIs
```

The critical design rule of the Sidecar Pattern is that the main service must not be aware that the sidecar exists. From the main service's perspective, it is simply making an unencrypted HTTP call to localhost:9090 — it has no idea that the sidecar is intercepting that call, wrapping it in mTLS, injecting trace headers, recording the request for Prometheus, and then forwarding it to the actual remote destination. All of that is completely transparent.

## Sidecar in Docker Compose — Our Project Setup

In our project, we use Docker Compose for local development and staging. The sidecar pattern is implemented by adding extra containers to each service's group within the Compose file, sharing network namespace via `network_mode: service:<name>`.

```yaml
# docker-compose.yml — Leave Service with sidecar containers

services:

  # ── Main Service ──────────────────────────────────────────────────────
  leave-service:
    build:
      context: ./leave-service
      dockerfile: Dockerfile
    environment:
      # Service only knows about localhost addresses — sidecar is transparent
      - GRPC_LISTEN_ADDR=localhost:8080
      - DB_HOST=postgres
      - KAFKA_BROKERS=localhost:9092       # envoy sidecar handles Kafka proxy
      - LOG_OUTPUT=/var/log/app/app.log   # write logs to shared volume
    volumes:
      - leave-logs:/var/log/app           # shared with log-shipper sidecar
      - leave-secrets:/etc/secrets        # shared with secrets-injector sidecar
    networks:
      - internal
    # Does NOT expose ports directly — the proxy sidecar does that

  # ── Proxy Sidecar (Envoy) ─────────────────────────────────────────────
  # Handles: TLS termination, mTLS between services, traffic routing
  leave-proxy:
    image: envoyproxy/envoy:v1.28-latest
    network_mode: "service:leave-service"   # shares leave-service network namespace
    volumes:
      - ./envoy/leave-service.yaml:/etc/envoy/envoy.yaml:ro
      - leave-secrets:/etc/secrets:ro
    depends_on:
      - leave-service
    ports:
      - "50051:50051"    # gRPC port exposed to the world by the sidecar, not the service

  # ── Log Shipper Sidecar (Fluent Bit) ──────────────────────────────────
  # Handles: collecting logs from shared volume, shipping to Elasticsearch
  leave-log-shipper:
    image: fluent/fluent-bit:3.0
    network_mode: "service:leave-service"
    volumes:
      - leave-logs:/var/log/app:ro                   # reads logs written by main service
      - ./fluent-bit/leave-service.conf:/etc/fluent-bit/fluent-bit.conf:ro
    depends_on:
      - leave-service

  # ── Metrics Sidecar (OpenTelemetry Collector) ─────────────────────────
  # Handles: receiving metrics/traces from service, forwarding to Grafana/Jaeger
  leave-otel-collector:
    image: otel/opentelemetry-collector-contrib:latest
    network_mode: "service:leave-service"
    volumes:
      - ./otel/leave-collector.yaml:/etc/otel/config.yaml:ro
    command: ["--config=/etc/otel/config.yaml"]

  # ── Secrets Sidecar (Vault Agent) ─────────────────────────────────────
  # Handles: fetching secrets from Vault, writing to shared volume, rotating them
  leave-vault-agent:
    image: vault:1.15
    network_mode: "service:leave-service"
    volumes:
      - leave-secrets:/etc/secrets           # writes secrets that main service reads
      - ./vault/leave-agent.hcl:/etc/vault/agent.hcl:ro
    command: ["vault", "agent", "-config=/etc/vault/agent.hcl"]
    environment:
      - VAULT_ADDR=http://vault:8200

volumes:
  leave-logs:
  leave-secrets:

networks:
  internal:
    driver: bridge
```

Notice the main service — `leave-service` — has no knowledge of Envoy, Fluent Bit, or the OTel collector. It writes logs to a file, listens on localhost, and calls localhost addresses. Everything else is managed by the sidecars around it. This is the pattern working as intended.

## Sidecar Type 1 — The Proxy Sidecar (Envoy / Service Mesh)

The most important and widely deployed form of the Sidecar Pattern is the proxy sidecar. It intercepts all inbound and outbound network traffic for the main service and handles concerns that would otherwise live in the service itself: TLS termination, mutual TLS authentication between services, traffic routing, load balancing, retry logic, circuit breaking, and request tracing.

When you hear the term "service mesh" — Istio, Linkerd, Consul Connect — what you are hearing about is a system where a proxy sidecar (almost always Envoy) is automatically injected into every pod in a Kubernetes cluster. The collection of all these sidecars, coordinated by a control plane, forms the mesh.

```
PROXY SIDECAR — Traffic Interception
──────────────────────────────────────

  Inbound traffic flow:
  ─────────────────────
  Remote caller (Approval Service)
         │
         │  mTLS encrypted gRPC over port 50051
         ▼
  ┌────────────────────────────────────────────────────────┐
  │  Leave Service Pod                                     │
  │                                                        │
  │  ┌─────────────────────┐                               │
  │  │   Envoy Sidecar     │                               │
  │  │   (proxy)           │                               │
  │  │                     │                               │
  │  │  1. Terminate mTLS  │                               │
  │  │  2. Validate cert   │                               │
  │  │  3. Strip TLS       │                               │
  │  │  4. Inject trace    │                               │
  │  │     headers         │                               │
  │  │  5. Forward to      │                               │
  │  │     localhost:8080  │──► Leave Service (plain gRPC) │
  │  └─────────────────────┘   (no TLS handling needed)   │
  └────────────────────────────────────────────────────────┘

  Outbound traffic flow:
  ──────────────────────
  Leave Service
         │
         │  Plain HTTP/gRPC call to localhost:9090
         │  (no TLS, no retry logic, no circuit breaking)
         ▼
  ┌────────────────────────────────────────────────────────┐
  │  Leave Service Pod                                     │
  │                                                        │
  │  ┌─────────────────────┐                               │
  │  │   Envoy Sidecar     │                               │
  │  │   (proxy)           │                               │
  │  │                     │                               │
  │  │  1. Intercept call  │                               │
  │  │  2. Resolve target  │                               │
  │  │     service address │                               │
  │  │  3. Wrap in mTLS    │                               │
  │  │  4. Apply retry     │                               │
  │  │     policy          │                               │
  │  │  5. Apply circuit   │                               │
  │  │     breaker         │                               │
  │  │  6. Forward to real │                               │
  │  │     Balance Service │                               │
  │  └─────────────────────┘                               │
  └────────────────────────────────────────────────────────┘
         │
         │  mTLS encrypted gRPC
         ▼
  Balance Service (its Envoy sidecar handles the other end)
```

Here is the Envoy configuration for our Leave Service sidecar. This is the `leave-service.yaml` file referenced in the Docker Compose above:

```yaml

static_resources:

  listeners:
    # ── Inbound listener: accepts traffic from outside the pod ──────────
    - name: inbound_grpc
      address:
        socket_address: { address: 0.0.0.0, port_value: 50051 }
      filter_chains:
        - transport_socket:
            name: envoy.transport_sockets.tls
            typed_config:
              "@type": type.googleapis.com/envoy.extensions.transport_sockets.tls.v3.DownstreamTlsContext
              require_client_certificate: true   # mTLS — clients must present cert
              common_tls_context:
                tls_certificates:
                  - certificate_chain: { filename: "/etc/secrets/leave-service.crt" }
                    private_key:       { filename: "/etc/secrets/leave-service.key" }
                validation_context:
                  trusted_ca: { filename: "/etc/secrets/ca.crt" }
          filters:
            - name: envoy.filters.network.http_connection_manager
              typed_config:
                "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
                codec_type: HTTP2   # gRPC requires HTTP/2
                route_config:
                  virtual_hosts:
                    - name: local_service
                      domains: ["*"]
                      routes:
                        - match: { prefix: "/" }
                          route: { cluster: local_leave_service }
                http_filters:
                  - name: envoy.filters.http.router

    # ── Outbound listener: main service connects here for all outbound calls
    - name: outbound_egress
      address:
        socket_address: { address: 127.0.0.1, port_value: 9090 }
      filter_chains:
        - filters:
            - name: envoy.filters.network.http_connection_manager
              typed_config:
                "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
                codec_type: HTTP2
                route_config:
                  virtual_hosts:
                    - name: balance_service
                      domains: ["balance-service"]
                      routes:
                        - match: { prefix: "/" }
                          route:
                            cluster: balance_service_cluster
                            retry_policy:
                              retry_on: "unavailable,deadline-exceeded"
                              num_retries: 3
                              per_try_timeout: 5s

  clusters:
    # ── Where the main service actually listens (localhost only) ──────────
    - name: local_leave_service
      load_assignment:
        cluster_name: local_leave_service
        endpoints:
          - lb_endpoints:
              - endpoint:
                  address:
                    socket_address: { address: 127.0.0.1, port_value: 8080 }

    # ── Real address of Balance Service (with mTLS) ───────────────────────
    - name: balance_service_cluster
      load_assignment:
        cluster_name: balance_service_cluster
        endpoints:
          - lb_endpoints:
              - endpoint:
                  address:
                    socket_address: { address: balance-service, port_value: 50051 }
      transport_socket:
        name: envoy.transport_sockets.tls
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.transport_sockets.tls.v3.UpstreamTlsContext
          common_tls_context:
            tls_certificates:
              - certificate_chain: { filename: "/etc/secrets/leave-service.crt" }
                private_key:       { filename: "/etc/secrets/leave-service.key" }
            validation_context:
              trusted_ca: { filename: "/etc/secrets/ca.crt" }
```

With this sidecar in place, the Go service code that calls the Balance Service looks like this — completely unaware of TLS, retries, or circuit breaking:

```go
// leave/clients/balance_client.go
// The service calls localhost:9090 — the sidecar intercepts and handles everything

func NewBalanceClient() *BalanceClient {
    // Plain insecure connection to localhost — Envoy handles TLS on both ends
    conn, err := grpc.Dial("localhost:9090",
        grpc.WithTransportCredentials(insecure.NewCredentials()),
    )
    if err != nil {
        log.Fatalf("failed to connect to balance service via sidecar: %v", err)
    }

    return &BalanceClient{
        client: balancepb.NewBalanceServiceClient(conn),
    }
}

func (c *BalanceClient) DeductBalance(ctx context.Context, req *DeductBalanceRequest) error {
    // This plain gRPC call goes to localhost:9090 (Envoy outbound listener)
    // Envoy wraps it in mTLS, applies retry policy, applies circuit breaker
    // The Go code here knows nothing about any of that
    _, err := c.client.DeductBalance(ctx, &balancepb.DeductBalanceRequest{
        EmployeeId: req.EmployeeID,
        Days:       int32(req.Days),
    })
    return err
}
```

The result is a Go service that has zero TLS code, zero retry code, and zero circuit breaker code — and yet enjoys all of those capabilities because the sidecar provides them transparently.

## Sidecar Type 2 — The Log Shipper Sidecar

Every service generates logs. In a microservice system, you need those logs centralized — aggregated in Elasticsearch or Loki where you can search across all services at once when debugging an incident. But implementing log shipping in every service individually means every service needs to know about your log aggregation infrastructure, handle network failures to the log aggregator gracefully, buffer logs during outages, and parse and reformat log entries into the right schema.

The Log Shipper Sidecar takes all of this away from the service. The service simply writes structured JSON logs to a file or stdout. The sidecar picks those logs up, enriches them with metadata, buffers them during aggregator outages, and ships them reliably to Elasticsearch or Loki.

```
LOG SHIPPER SIDECAR — Flow
───────────────────────────

  Leave Service (Go)
  ─────────────────
  Uses slog with JSON output:

    slog.Info("leave submitted",
        "leave_id",    leave.ID,
        "employee_id", leave.EmployeeID,
        "days",        leave.Days,
    )

  Writes JSON line to /var/log/app/app.log:
  {"time":"2024-03-15T10:00:01Z","level":"INFO","msg":"leave submitted",
   "leave_id":"L001","employee_id":"EMP-42","days":5}

                     │
                     │  shared volume mount
                     ▼
  Fluent Bit Sidecar
  ──────────────────
  1. Reads from /var/log/app/app.log (tails the file)
  2. Parses JSON
  3. Enriches with:
       service_name: "leave-service"
       environment: "production"
       pod_name: "leave-service-7f8d9b-xkp2m"
       version: "v1.4.2"
  4. Buffers in memory during Elasticsearch outages
  5. Ships to Elasticsearch with retry

                     │
                     ▼
  Elasticsearch
  {
    "time": "2024-03-15T10:00:01Z",
    "level": "INFO",
    "msg": "leave submitted",
    "leave_id": "L001",
    "employee_id": "EMP-42",
    "days": 5,
    "service_name": "leave-service",       ← added by sidecar
    "environment": "production",           ← added by sidecar
    "pod_name": "leave-service-7f8d...",   ← added by sidecar
    "version": "v1.4.2"                    ← added by sidecar
  }
```

```go
// leave/logging/logger.go — the service only knows about this

package logging

import (
    "log/slog"
    "os"
)

func NewLogger(serviceName string) *slog.Logger {
    logFile := os.Getenv("LOG_OUTPUT")
    if logFile == "" {
        logFile = "stdout"
    }

    var output *os.File
    if logFile == "stdout" {
        output = os.Stdout
    } else {
        var err error
        output, err = os.OpenFile(logFile, os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)
        if err != nil {
            // Fallback to stdout if file cannot be opened
            output = os.Stdout
        }
    }

    handler := slog.NewJSONHandler(output, &slog.HandlerOptions{
        Level: slog.LevelInfo,
        // Do NOT add service_name here — the sidecar adds it
        // The service only adds business-relevant fields
    })

    return slog.New(handler)
}
```

The service never imports any Elasticsearch library. It never handles connection failures to a log aggregator. It never buffers logs. All of that complexity lives in the Fluent Bit sidecar, maintained by the platform team, consistent across all twelve services.

## Sidecar Type 3 — The Metrics and Tracing Sidecar (OTel Collector)

Our project uses OpenTelemetry for observability. Each service emits spans (for distributed tracing) and metrics (for Prometheus/Grafana). Without a sidecar, each service would need to be configured to send this data directly to Jaeger for traces and Prometheus for metrics — two different endpoints, two different protocols, both needing retry logic and buffering.

The OpenTelemetry Collector sidecar sits between the service and the observability backends. The service sends all telemetry to one place — `localhost:4317` (the OTel gRPC endpoint) — and the sidecar handles routing, batching, filtering, and forwarding to any number of backends.

```
OTEL COLLECTOR SIDECAR — Telemetry Pipeline
─────────────────────────────────────────────

  Leave Service (Go)
  ──────────────────
  Uses OTel SDK:
    - Sends traces to localhost:4317
    - Sends metrics to localhost:4317
  (no knowledge of where these eventually go)

                     │
                     │  gRPC to localhost:4317
                     ▼
  OTel Collector Sidecar
  ──────────────────────
  Receives: traces + metrics on port 4317

  Processors:
    ├── batch (group 512 spans before sending)
    ├── memory_limiter (shed load if memory pressure)
    ├── attributes (add service.name, environment)
    └── filter (drop health-check spans — not useful)

  Exporters:
    ├── Traces ──────────────────────────────► Jaeger
    ├── Metrics (Prometheus format) ─────────► Prometheus scrape endpoint
    └── Metrics + Traces ────────────────────► Grafana Cloud (OTLP)

  One service, one destination (localhost:4317).
  The sidecar handles the fan-out.
```


## Sidecar Type 4 — The Secrets Injector Sidecar (Vault Agent)

Secrets management is one of the most dangerous things to implement inconsistently across services. If each service handles its own Vault authentication, token renewal, and secret rotation differently, you end up with twelve different implementations — some with bugs that cause tokens to expire silently, some that do not handle rotation correctly and require service restarts when a secret rotates, some that log secrets accidentally.

The Vault Agent sidecar centralizes all of this. It authenticates with Vault on behalf of the service, fetches the secrets the service needs, writes them to a shared volume as files, and automatically refreshes them when they rotate — all without the service needing to know that Vault exists.

```
VAULT AGENT SIDECAR — Secret Lifecycle
────────────────────────────────────────

  Startup:
  1. Vault Agent authenticates with Vault using Kubernetes ServiceAccount token
     (or Docker: using AppRole auth)
  2. Vault Agent fetches secrets:
       - database password
       - Kafka credentials
       - JWT signing key
       - gRPC TLS certificates
  3. Writes secrets to shared volume at /etc/secrets/
       /etc/secrets/db-password     ← just the password string
       /etc/secrets/kafka-username
       /etc/secrets/kafka-password
       /etc/secrets/jwt-signing-key
       /etc/secrets/service.crt
       /etc/secrets/service.key

  Runtime (Main Service):
  4. Main service reads /etc/secrets/db-password at startup
  5. Uses it to connect to database

  Secret Rotation (at 3am, Vault rotates the DB password):
  6. Vault Agent detects the rotation via lease renewal
  7. Vault Agent writes new password to /etc/secrets/db-password
  8. Vault Agent sends SIGHUP to main service (configurable)
  9. Main service reloads the secret from file, reconnects to DB
  10. Zero downtime. No human intervention. No service restart needed.
```


```go
// leave/config/secrets.go — service reads secrets from files, never from Vault directly

package config

type Secrets struct {
    DBPassword      string
    KafkaUsername   string
    KafkaPassword   string
    JWTSigningKey   string
}

func LoadSecrets() (*Secrets, error) {
    // Read from files written by Vault Agent sidecar
    dbPassword, err := os.ReadFile("/etc/secrets/db-password")
    if err != nil {
        return nil, fmt.Errorf("failed to read db password: %w", err)
    }

    kafkaCreds, err := os.ReadFile("/etc/secrets/kafka-credentials")
    if err != nil {
        return nil, fmt.Errorf("failed to read kafka credentials: %w", err)
    }

    // Parse the kafka credentials file (username:password format)
    parts := strings.SplitN(string(kafkaCreds), ":", 2)
    if len(parts) != 2 {
        return nil, fmt.Errorf("invalid kafka credentials format")
    }

    return &Secrets{
        DBPassword:    strings.TrimSpace(string(dbPassword)),
        KafkaUsername: parts[0],
        KafkaPassword: parts[1],
    }, nil
}

// HandleSIGHUP reloads secrets when Vault Agent signals rotation
func (s *Service) HandleSIGHUP() {
    sigChan := make(chan os.Signal, 1)
    signal.Notify(sigChan, syscall.SIGHUP)

    for range sigChan {
        slog.Info("received SIGHUP — reloading secrets")
        secrets, err := config.LoadSecrets()
        if err != nil {
            slog.Error("failed to reload secrets", "error", err)
            continue
        }
        // Reconnect database with new password
        s.reconnectDB(secrets.DBPassword)
        slog.Info("secrets reloaded successfully")
    }
}
```

The service has no Vault SDK import. It has no knowledge of Vault's authentication flow. It has no concept of lease renewal or token refresh. All it knows is that when it starts up, the password is in a file, and when it gets a SIGHUP signal, it should reload that file. The sidecar handles all the Vault complexity.

## Sidecar Type 5 — The Health Check and Ambassador Sidecar

Some services expose health checks in proprietary formats. Others need health checks that require checking multiple dependencies — is the database reachable? Is Kafka reachable? Is the gRPC server responding? — and aggregating them into a single health status. The Ambassador Sidecar pattern handles this aggregation and translation.

```
AMBASSADOR / HEALTH CHECK SIDECAR
───────────────────────────────────

  External health check systems (Kubernetes liveness probe, load balancer)
  need a standard HTTP endpoint: GET /health → 200 OK or 503 Service Unavailable

  Main service exposes:
    gRPC health check at localhost:8080 (grpc.health.v1.Health)

  Ambassador Sidecar exposes:
    HTTP GET /health     ──► checks gRPC health + DB + Kafka → aggregated response
    HTTP GET /ready      ──► checks if service is ready to serve traffic
    HTTP GET /metrics    ──► Prometheus metrics (from OTel collector sidecar)
    HTTP GET /version    ──► service version info
```

```go
// sidecar/ambassador/main.go
// This is a small Go binary deployed as the ambassador sidecar

package main

type AmbassadorSidecar struct {
    grpcHealthClient healthpb.HealthClient
    dbChecker        func() error
    kafkaChecker     func() error
    logger           *slog.Logger
}

func (a *AmbassadorSidecar) RegisterRoutes(mux *http.ServeMux) {
    mux.HandleFunc("GET /health", a.handleHealth)
    mux.HandleFunc("GET /ready",  a.handleReady)
    mux.HandleFunc("GET /version", a.handleVersion)
}

func (a *AmbassadorSidecar) handleHealth(w http.ResponseWriter, r *http.Request) {
    type HealthStatus struct {
        Status     string            `json:"status"`   // "healthy" or "unhealthy"
        Components map[string]string `json:"components"`
        Timestamp  time.Time         `json:"timestamp"`
    }

    components := make(map[string]string)
    allHealthy := true

    // Check gRPC server health
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()

    grpcResp, err := a.grpcHealthClient.Check(ctx, &healthpb.HealthCheckRequest{
        Service: "leave.v1.LeaveCommandService",
    })
    if err != nil || grpcResp.Status != healthpb.HealthCheckResponse_SERVING {
        components["grpc_server"] = "unhealthy"
        allHealthy = false
    } else {
        components["grpc_server"] = "healthy"
    }

    // Check database connectivity
    if err := a.dbChecker(); err != nil {
        components["database"] = fmt.Sprintf("unhealthy: %v", err)
        allHealthy = false
    } else {
        components["database"] = "healthy"
    }

    // Check Kafka connectivity
    if err := a.kafkaChecker(); err != nil {
        components["kafka"] = fmt.Sprintf("unhealthy: %v", err)
        allHealthy = false
    } else {
        components["kafka"] = "healthy"
    }

    status := HealthStatus{
        Components: components,
        Timestamp:  time.Now(),
    }

    if allHealthy {
        status.Status = "healthy"
        w.WriteHeader(http.StatusOK)
    } else {
        status.Status = "unhealthy"
        w.WriteHeader(http.StatusServiceUnavailable)
    }

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(status)
}
```

## The Design Rules That Make Sidecar Work

There are four design rules that must be followed for the Sidecar Pattern to provide real value. Violating any of them undermines the entire pattern.

The first rule is that the main service must be completely unaware of its sidecars. If your Go service imports an Envoy SDK, reads an Envoy configuration file, or makes decisions based on whether the proxy is running, you have created a dependency that defeats the purpose. The service must only know about localhost addresses and shared filesystem paths — neutral, infrastructure-agnostic interfaces.

The second rule is that sidecars must be owned by a platform team, not by individual service teams. If each service team customizes their own sidecar, you lose consistency. The whole point is that the sidecar is the same binary, the same version, the same configuration across all services. The platform team deploys and maintains the sidecar. Service teams consume it as a black box.

The third rule is that sidecars must fail safe. If the Fluent Bit sidecar crashes, the main service must continue functioning normally — it just temporarily loses log shipping. If the OTel collector sidecar crashes, the service must continue processing requests — it just temporarily loses telemetry. The main service's availability must never depend on its sidecars.

The fourth rule is that the communication between the main service and its sidecar must be on localhost only. The sidecar is not a remote dependency — it is co-located, running on the same host, communicating through shared memory, Unix domain sockets, or the loopback interface. If your sidecar is a remote service that your main service calls over the network, you have built a different pattern — not a sidecar.

```
SIDECAR RULES SUMMARY
────────────────────────────────────────────────────────────────────────
Rule 1: Main service is UNAWARE of sidecars
        ✓ Service knows only localhost addresses and /etc/secrets/ paths
        ✗ Service imports Envoy SDK, checks if Fluent Bit is running

Rule 2: Sidecars are owned by PLATFORM TEAM
        ✓ All 12 services use the same sidecar binary, same config template
        ✗ Each service team customizes their own Envoy config

Rule 3: Sidecars FAIL SAFE
        ✓ Fluent Bit crash → service keeps running, logs buffered on disk
        ✗ Service refuses to start if OTel Collector is not ready

Rule 4: Sidecar communication is LOCALHOST ONLY
        ✓ Service connects to localhost:4317 for OTel, localhost:9090 for egress
        ✗ Service connects to otel-collector.infra.company.com:4317
────────────────────────────────────────────────────────────────────────
```

## What the Sidecar Pattern Does Not Solve

The Sidecar Pattern is an infrastructure deployment pattern, not a business logic pattern. It solves operational complexity and cross-cutting concerns. But it is worth being clear about what it cannot do.

Sidecar adds operational overhead of its own. You are now running four or five processes per service instead of one. Each sidecar needs resources (memory, CPU), needs to be monitored, needs to be updated, and can fail. A service that previously needed 256MB of RAM might now need 512MB when its sidecars are included. This overhead is generally worth paying, but it is not zero.

Sidecar does not solve latency for the main service's external calls. Since all outbound traffic still traverses the proxy sidecar on localhost, there are two additional network hops (service to Envoy, Envoy to destination) for every external call. At the speeds of localhost (sub-millisecond), this is negligible — but it is not literally zero.

Sidecar does not replace good application design. A service that is poorly structured, has memory leaks, or has bad error handling is not improved by wrapping it in sidecars. Sidecars handle infrastructure concerns. Application concerns remain the service developer's responsibility.

The Sidecar Pattern is what allows a platform team of three engineers to provide enterprise-grade observability, security, and traffic management to twelve teams building microservices — without those twelve teams needing to become infrastructure experts. Each team writes clean Go business logic that speaks plain HTTP or gRPC to localhost. The platform team ensures that plain communication is wrapped in everything a production system needs. That separation of concerns, executed cleanly, is one of the most valuable architectural decisions you can make in a microservice system.
