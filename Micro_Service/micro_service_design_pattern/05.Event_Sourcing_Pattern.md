# The Event Sourcing Pattern in Microservices

### Everything You Need to Know — Explained Like You Just Joined the Team

---

## A Story Before the Pattern

Imagine you are a bank. At the end of every day, a customer's account shows a balance of 15,000 taka. That is the current state. Now a customer calls and asks: "Why is my balance only 15,000? It was 40,000 last week." In a traditional system that only stores the current state, you have no answer. The number 15,000 is all that exists. Whatever series of transactions produced that number is gone.

Now imagine instead that the bank keeps a ledger — a journal of every single deposit and withdrawal ever made, in order, with timestamps. The balance at any point in time is calculated by replaying those entries from the beginning. If the customer calls asking why their balance dropped, you open the ledger and read: deposit 40,000, rent withdrawal 12,000, grocery withdrawal 8,000, utility bill 5,000. The current balance of 15,000 is not a fact stored somewhere. It is the natural result of the history of events. And the complete history is always there.

This is Event Sourcing. Not a metaphor for it. This is literally what Event Sourcing is, applied to software.

---

## What Traditional Systems Do (And What They Lose)

In every service we have built so far, we follow the same basic pattern. We have a `leaves` table. When an employee submits a leave, we INSERT a row. When the manager approves it, we UPDATE the `status` column from `PENDING` to `APPROVED`. When the employee cancels it, we UPDATE the `status` column to `CANCELLED`.

At any given moment, the table holds the current state of every leave application. But the history of how each leave got to that state is completely gone. The UPDATE statement overwrites the previous value. There is no record of who changed what, when, or why.

```
TRADITIONAL STATE-BASED STORAGE — What Gets Lost
──────────────────────────────────────────────────

Timeline of events for Leave #L001:
  10:00  Employee submits leave (type: Annual, days: 5)
  10:15  Manager requests more information
  10:30  Employee updates reason
  11:00  Manager rejects (reason: "peak season")
  11:05  Employee appeals
  11:20  HR overrides rejection, approves

What the database actually shows at 11:20:
┌──────────────────────────────────────────────────────┐
│  leaves table                                        │
│  id: L001                                            │
│  employee_id: 42                                     │
│  status: APPROVED                                    │
│  updated_at: 11:20                                   │
└──────────────────────────────────────────────────────┘

What is permanently lost:
  ✗  The initial submission details
  ✗  The manager's information request
  ✗  The employee's updated reason
  ✗  The original rejection and why
  ✗  The appeal
  ✗  Who specifically overrode the rejection
  ✗  The complete audit trail
  ✗  The ability to understand how the approval happened
```

This loss is not just an auditing inconvenience. It creates real business problems. Regulators ask for audit trails. Disputes arise about what was changed and when. Bugs are hard to debug because you cannot reconstruct what the state was at the moment the bug occurred. Machine learning teams want historical data that no longer exists. Temporal queries like "what was the leave balance of every employee at the end of Q1" are impossible.

Event Sourcing fixes all of this by never throwing away history.

## What Event Sourcing Actually Is

Event Sourcing is a way of persisting the state of an entity not by storing its current value, but by storing the complete sequence of events that caused it to reach that value. The current state is never stored directly. Instead, it is always derived by replaying the events from the beginning — or from a recent snapshot — up to the present moment.

The entity whose state is managed this way is called an Aggregate. In our leave management system, a `Leave` is an aggregate. An `Employee` is an aggregate. A `LeaveBalance` is an aggregate. Each aggregate has a unique ID and its own append-only event stream.

```
EVENT SOURCING — How State Is Stored and Derived
──────────────────────────────────────────────────

Event Store (append-only, never delete, never update):
┌─────────────────────────────────────────────────────────────────────┐
│  stream_id: leave-L001                                             │
│  ─────────────────────────────────────────────────────────────     │
│  seq │ event_type              │ data                  │ timestamp │
│  ─────────────────────────────────────────────────────────────     │
│   1  │ LeaveSubmitted          │ {days:5, type:Annual} │ 10:00     │
│   2  │ ManagerInfoRequested    │ {by: "Ali"}           │ 10:15     │
│   3  │ LeaveReasonUpdated      │ {reason: "wedding"}   │ 10:30     │
│   4  │ LeaveRejected           │ {by: "Ali", reason:   │ 11:00     │
│      │                         │  "peak season"}       │           │
│   5  │ LeaveAppealed           │ {by: emp-42}          │ 11:05     │
│   6  │ LeaveApprovalOverridden │ {by: HR, reason:      │ 11:20     │
│      │                         │  "valid emergency"}   │           │
└─────────────────────────────────────────────────────────────────────┘

To get current state: replay all 6 events in order.

Current state derived from replay:
┌──────────────────────────────┐
│  Leave {                     │
│    ID:        "L001"         │
│    Status:    "APPROVED"     │
│    Days:      5              │
│    Type:      "Annual"       │
│    Reason:    "wedding"      │
│    ApprovedBy: "HR"          │
│    RejectedAt: 11:00         │  ← still in history
│    ApprovedAt: 11:20         │
│  }                           │
└──────────────────────────────┘
```

The event store is the source of truth. The current state is a projection — a derived view computed from the events. This reversal of what is "primary" is the fundamental shift in thinking that Event Sourcing requires.

## The Core Vocabulary You Need to Know

Before we write any code, let us settle on the terms. These words have precise meanings in Event Sourcing, and using them correctly matters.

An **Event** is something that happened in the past. It is immutable. Events are named in the past tense: `LeaveSubmitted`, `LeaveApproved`, `BalanceDeducted`. An event describes a fact about the world that cannot be undone — only compensated for with a new event.

An **Aggregate** is the business entity whose state is managed through events. The Leave aggregate, the Employee aggregate, the LeaveBalance aggregate. Each aggregate has a unique ID and an ordered stream of events that defines its complete history.

An **Event Stream** is the ordered sequence of events for a single aggregate instance. All events for leave `L001` form one stream. All events for leave `L002` form a separate stream. Streams are identified by `aggregate_type-aggregate_id`.

The **Event Store** is the database that stores all event streams. It is append-only. Events are never updated and never deleted (except for legal compliance reasons via special mechanisms). Every write to the event store is an append of one or more new events to an existing stream.

A **Projection** (also called a Read Model) is a view of the data built by processing events. The `leaves` table showing current status is a projection. A report showing leave usage by department is a projection. Projections can be rebuilt at any time by replaying events from the beginning.

A **Snapshot** is a periodically-saved checkpoint of the aggregate's current state, used to avoid replaying thousands of events every time you need the current state of a heavily-used aggregate. Events are still the source of truth — the snapshot is just a performance optimization.

```
EVENT SOURCING VOCABULARY
───────────────────────────

  ┌──────────────────────────────────────────────────────┐
  │                    Event Store                        │
  │  (append-only, source of truth for ALL aggregates)   │
  │                                                      │
  │  Stream: leave-L001     Stream: leave-L002           │
  │  ┌────────────────┐     ┌────────────────┐           │
  │  │ LeaveSubmitted │     │ LeaveSubmitted │           │
  │  │ LeaveApproved  │     │ LeaveRejected  │           │
  │  │ LeaveTaken     │     └────────────────┘           │
  │  └────────────────┘                                  │
  │                                                      │
  │  Stream: balance-emp42  Stream: employee-emp42       │
  │  ┌────────────────┐     ┌────────────────┐           │
  │  │ BalanceGranted │     │ EmployeeHired  │           │
  │  │ BalanceDeducted│     │ DeptTransferred│           │
  │  └────────────────┘     └────────────────┘           │
  └──────────────────────────────────────────────────────┘
          │                         │
          │ Projections read        │ Projections build
          │ events and build        │ read models for
          │ current state           │ queries
          ▼                         ▼
  ┌─────────────────┐     ┌───────────────────────┐
  │  Leave Service  │     │  Reporting Service    │
  │  current_leaves │     │  leave_usage_by_dept  │
  │  (read model)   │     │  monthly_report       │
  └─────────────────┘     └───────────────────────┘
```

## The Event Store Schema

The event store is a single PostgreSQL table — in our Go/GORM stack — that holds every event for every aggregate across the entire service. It is the most important table in an event-sourced service. Every other table is derived from it.

```sql
CREATE TABLE event_store (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    stream_id       VARCHAR(255) NOT NULL,   -- e.g. "leave-L001"
    aggregate_id    VARCHAR(255) NOT NULL,   -- e.g. "L001"
    aggregate_type  VARCHAR(255) NOT NULL,   -- e.g. "Leave"
    event_type      VARCHAR(255) NOT NULL,   -- e.g. "LeaveSubmitted"
    sequence_number BIGINT NOT NULL,         -- position in this stream (1, 2, 3...)
    global_sequence BIGSERIAL NOT NULL,      -- global ordering across all streams
    payload         JSONB NOT NULL,          -- the event data
    metadata        JSONB NOT NULL DEFAULT '{}',  -- correlation_id, causation_id, user_id
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- Optimistic concurrency: prevents two writers appending at the same position
    UNIQUE (stream_id, sequence_number)
);

-- For loading a specific aggregate's events
CREATE INDEX idx_event_store_stream ON event_store (stream_id, sequence_number ASC);

-- For projections that need to process events in global order
CREATE INDEX idx_event_store_global ON event_store (global_sequence ASC);

-- For finding all events of a specific type (used by some projections)
CREATE INDEX idx_event_store_event_type ON event_store (event_type, global_sequence ASC);
```

The `sequence_number` is the position of an event within its aggregate's stream. The first event for `leave-L001` has sequence 1, the second has sequence 2, and so on. The `UNIQUE (stream_id, sequence_number)` constraint is the mechanism for optimistic concurrency control — if two processes try to append event #3 to the same stream simultaneously, only one will succeed and the other will get a unique constraint violation, telling it to reload the aggregate and retry.

The `global_sequence` is a database-assigned monotonically increasing number across all streams. Projections use this to know "I have processed all events up to global sequence 4721 — give me everything after that."

In Go with GORM:

```go
type EventStore struct {
    ID             uuid.UUID      `gorm:"type:uuid;primaryKey;default:gen_random_uuid()"`
    StreamID       string         `gorm:"not null;index:idx_stream,composite:stream_seq"`
    AggregateID    string         `gorm:"not null;index"`
    AggregateType  string         `gorm:"not null"`
    EventType      string         `gorm:"not null;index"`
    SequenceNumber int64          `gorm:"not null;index:idx_stream,composite:stream_seq;uniqueIndex:uniq_stream_seq"`
    GlobalSequence int64          `gorm:"not null;autoIncrement;index"`
    Payload        datatypes.JSON `gorm:"type:jsonb;not null"`
    Metadata       datatypes.JSON `gorm:"type:jsonb;not null;default:'{}'"`
    CreatedAt      time.Time      `gorm:"not null;default:now()"`
}
```

## The Aggregate — Where Business Logic Lives

In Event Sourcing, the aggregate is not a passive data struct that gets updated by service methods. It is an active object that receives commands, validates them, and produces events. The aggregate never directly modifies its own state in response to a command. Instead, it appends an event describing what happened, and the event itself causes the state change through an `Apply` method.

This sounds unusual at first, but the reason is precise: the `Apply` method is the only place where state is changed. This means you can replay events through `Apply` to reconstruct any past state. If the aggregate changed its state directly inside command handlers, replaying events would be impossible.

```go
// leave/aggregate.go

// Events — immutable facts about what happened
type LeaveSubmittedEvent struct {
    LeaveID    string    `json:"leave_id"`
    EmployeeID string    `json:"employee_id"`
    LeaveType  string    `json:"leave_type"`
    Days       int       `json:"days"`
    StartDate  time.Time `json:"start_date"`
    EndDate    time.Time `json:"end_date"`
    Reason     string    `json:"reason"`
}

type LeaveApprovedEvent struct {
    LeaveID    string    `json:"leave_id"`
    ApprovedBy string    `json:"approved_by"`
    ApprovedAt time.Time `json:"approved_at"`
    Comment    string    `json:"comment"`
}

type LeaveRejectedEvent struct {
    LeaveID    string `json:"leave_id"`
    RejectedBy string `json:"rejected_by"`
    Reason     string `json:"reason"`
}

type LeaveCancelledEvent struct {
    LeaveID     string    `json:"leave_id"`
    CancelledBy string    `json:"cancelled_by"`
    CancelledAt time.Time `json:"cancelled_at"`
}

// The Aggregate — holds current state + uncommitted events
type LeaveAggregate struct {
    // Identity
    ID      string
    Version int64  // current sequence_number — used for optimistic concurrency

    // Current state (derived from replaying events)
    EmployeeID string
    LeaveType  string
    Days       int
    StartDate  time.Time
    EndDate    time.Time
    Reason     string
    Status     string  // PENDING, APPROVED, REJECTED, CANCELLED
    ApprovedBy string
    RejectedBy string

    // Uncommitted events — produced during this session, not yet saved
    UncommittedEvents []interface{}
}

// ─────────────────────────────────────────────────────
// COMMAND HANDLERS — validate, then raise events
// ─────────────────────────────────────────────────────

func (a *LeaveAggregate) Submit(employeeID, leaveType, reason string, days int, start, end time.Time) error {
    // Validate the command
    if a.Status != "" {
        return fmt.Errorf("leave already exists")
    }
    if days <= 0 {
        return fmt.Errorf("days must be positive")
    }
    if end.Before(start) {
        return fmt.Errorf("end date must be after start date")
    }

    // Raise the event — do not touch state directly
    a.raise(LeaveSubmittedEvent{
        LeaveID:    a.ID,
        EmployeeID: employeeID,
        LeaveType:  leaveType,
        Days:       days,
        StartDate:  start,
        EndDate:    end,
        Reason:     reason,
    })
    return nil
}

func (a *LeaveAggregate) Approve(approvedBy, comment string) error {
    if a.Status != "PENDING" {
        return fmt.Errorf("can only approve a PENDING leave, current status: %s", a.Status)
    }

    a.raise(LeaveApprovedEvent{
        LeaveID:    a.ID,
        ApprovedBy: approvedBy,
        ApprovedAt: time.Now(),
        Comment:    comment,
    })
    return nil
}

func (a *LeaveAggregate) Reject(rejectedBy, reason string) error {
    if a.Status != "PENDING" {
        return fmt.Errorf("can only reject a PENDING leave")
    }

    a.raise(LeaveRejectedEvent{
        LeaveID:    a.ID,
        RejectedBy: rejectedBy,
        Reason:     reason,
    })
    return nil
}

func (a *LeaveAggregate) Cancel(cancelledBy string) error {
    if a.Status == "CANCELLED" {
        return fmt.Errorf("leave is already cancelled")
    }
    if a.Status == "APPROVED" && cancelledBy != a.EmployeeID {
        return fmt.Errorf("only the employee can cancel an approved leave")
    }

    a.raise(LeaveCancelledEvent{
        LeaveID:     a.ID,
        CancelledBy: cancelledBy,
        CancelledAt: time.Now(),
    })
    return nil
}

// ─────────────────────────────────────────────────────
// APPLY METHODS — the only place state is mutated
// ─────────────────────────────────────────────────────

func (a *LeaveAggregate) Apply(event interface{}) {
    switch e := event.(type) {
    case LeaveSubmittedEvent:
        a.EmployeeID = e.EmployeeID
        a.LeaveType  = e.LeaveType
        a.Days       = e.Days
        a.StartDate  = e.StartDate
        a.EndDate    = e.EndDate
        a.Reason     = e.Reason
        a.Status     = "PENDING"

    case LeaveApprovedEvent:
        a.Status     = "APPROVED"
        a.ApprovedBy = e.ApprovedBy

    case LeaveRejectedEvent:
        a.Status     = "REJECTED"
        a.RejectedBy = e.RejectedBy

    case LeaveCancelledEvent:
        a.Status = "CANCELLED"
    }

    a.Version++
}

// raise: apply the event locally + queue for persistence
func (a *LeaveAggregate) raise(event interface{}) {
    a.Apply(event)
    a.UncommittedEvents = append(a.UncommittedEvents, event)
}
```

Notice the separation of concerns. The command handler (`Submit`, `Approve`, `Reject`, `Cancel`) contains the validation logic — the business rules about what is allowed. The `Apply` method contains only state mutation — no conditions, no validation, just field assignments. This separation is essential: when replaying events to reconstruct state, you call `Apply` directly, bypassing validation, because the events already happened and do not need to be re-validated.

## The Event Repository — Loading and Saving Aggregates

The repository is responsible for two things: loading an aggregate by replaying its event stream, and saving new events produced by the aggregate during a command.

```go
// leave/repository.go

type LeaveEventRepository struct {
    db *gorm.DB
}

// Load rebuilds an aggregate from scratch by replaying all its events
func (r *LeaveEventRepository) Load(ctx context.Context, leaveID string) (*LeaveAggregate, error) {
    streamID := fmt.Sprintf("leave-%s", leaveID)

    var storedEvents []EventStore
    result := r.db.WithContext(ctx).
        Where("stream_id = ?", streamID).
        Order("sequence_number ASC").
        Find(&storedEvents)

    if result.Error != nil {
        return nil, fmt.Errorf("failed to load events: %w", result.Error)
    }

    if len(storedEvents) == 0 {
        return nil, fmt.Errorf("leave not found: %s", leaveID)
    }

    aggregate := &LeaveAggregate{ID: leaveID}

    // Replay every event through Apply to reconstruct current state
    for _, stored := range storedEvents {
        event, err := deserializeEvent(stored.EventType, stored.Payload)
        if err != nil {
            return nil, fmt.Errorf("failed to deserialize event %s: %w", stored.EventType, err)
        }
        aggregate.Apply(event)
    }

    return aggregate, nil
}

// Save appends the aggregate's uncommitted events to the event store
func (r *LeaveEventRepository) Save(ctx context.Context, aggregate *LeaveAggregate) error {
    if len(aggregate.UncommittedEvents) == 0 {
        return nil // Nothing to save
    }

    streamID := fmt.Sprintf("leave-%s", aggregate.ID)

    // The version before the current session started
    // (Version is incremented by Apply, so subtract uncommitted count)
    startingVersion := aggregate.Version - int64(len(aggregate.UncommittedEvents))

    return r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        for i, event := range aggregate.UncommittedEvents {
            payload, err := json.Marshal(event)
            if err != nil {
                return fmt.Errorf("failed to serialize event: %w", err)
            }

            eventType := reflect.TypeOf(event).Name()
            sequenceNumber := startingVersion + int64(i) + 1

            stored := EventStore{
                StreamID:       streamID,
                AggregateID:    aggregate.ID,
                AggregateType:  "Leave",
                EventType:      eventType,
                SequenceNumber: sequenceNumber,
                Payload:        payload,
                Metadata:       buildMetadata(ctx),
            }

            // The UNIQUE constraint on (stream_id, sequence_number) provides
            // optimistic concurrency — if another process wrote to this stream
            // concurrently, this insert will fail and the caller must retry
            if err := tx.Create(&stored).Error; err != nil {
                if isDuplicateKeyError(err) {
                    return ErrConcurrencyConflict
                }
                return err
            }
        }

        // Clear uncommitted events after successful save
        aggregate.UncommittedEvents = nil
        return nil
    })
}

func deserializeEvent(eventType string, payload []byte) (interface{}, error) {
    switch eventType {
    case "LeaveSubmittedEvent":
        var e LeaveSubmittedEvent
        return e, json.Unmarshal(payload, &e)
    case "LeaveApprovedEvent":
        var e LeaveApprovedEvent
        return e, json.Unmarshal(payload, &e)
    case "LeaveRejectedEvent":
        var e LeaveRejectedEvent
        return e, json.Unmarshal(payload, &e)
    case "LeaveCancelledEvent":
        var e LeaveCancelledEvent
        return e, json.Unmarshal(payload, &e)
    default:
        return nil, fmt.Errorf("unknown event type: %s", eventType)
    }
}
```

## The Service Layer — Connecting Commands to Aggregates

The service layer ties everything together. It loads the aggregate, calls the command method, and saves the result.

```go
// leave/service.go

type LeaveService struct {
    repo      *LeaveEventRepository
    publisher EventPublisher  // publishes events to Kafka via Outbox pattern
}

func (s *LeaveService) SubmitLeave(ctx context.Context, req SubmitLeaveRequest) (string, error) {
    leaveID := uuid.NewString()

    aggregate := &LeaveAggregate{ID: leaveID}

    // Execute the command — this validates and raises the event
    if err := aggregate.Submit(
        req.EmployeeID, req.LeaveType, req.Reason,
        req.Days, req.StartDate, req.EndDate,
    ); err != nil {
        return "", fmt.Errorf("submit leave failed: %w", err)
    }

    // Save the uncommitted events to the event store
    if err := s.repo.Save(ctx, aggregate); err != nil {
        return "", fmt.Errorf("failed to save leave events: %w", err)
    }

    // Publish events to Kafka for other services (via Outbox pattern)
    for _, event := range aggregate.UncommittedEvents {
        s.publisher.Publish(event)
    }

    return leaveID, nil
}

func (s *LeaveService) ApproveLeave(ctx context.Context, leaveID, approvedBy, comment string) error {
    // Load aggregate by replaying its event stream
    aggregate, err := s.repo.Load(ctx, leaveID)
    if err != nil {
        return err
    }

    // Execute command — validates business rules against current state
    if err := aggregate.Approve(approvedBy, comment); err != nil {
        return err
    }

    // Save new events
    return s.repo.Save(ctx, aggregate)
}
```

The flow for every command is always identical: Load → Command → Save. That consistency is one of the things that makes event-sourced services easy to reason about. There are no UPDATE statements buried in service methods. There are no conditional writes. Every change to the system goes through this same three-step path.

```
COMMAND FLOW IN EVENT SOURCING
────────────────────────────────

  gRPC Request: ApproveLeave(leaveID: "L001")
         │
         ▼
  Service: ApproveLeave
         │
         │  1. LOAD
         ▼
  Event Repository: Load("L001")
    ├── SELECT events WHERE stream_id = "leave-L001" ORDER BY sequence_number
    ├── Replay event 1: LeaveSubmitted ──► Apply ──► Status = PENDING
    ├── Replay event 2: ManagerInfoRequested ──► Apply
    ├── Replay event 3: LeaveReasonUpdated ──► Apply
    └── Returns aggregate with Version = 3, Status = PENDING
         │
         │  2. COMMAND
         ▼
  Aggregate: Approve("Ali", "looks good")
    ├── Validates: Status == PENDING ✓
    ├── Raises LeaveApprovedEvent
    └── Apply: Status = APPROVED, Version = 4
         │
         │  3. SAVE
         ▼
  Event Repository: Save(aggregate)
    └── INSERT event_store (stream: leave-L001, seq: 4, type: LeaveApproved)
        ON CONFLICT (stream_id, seq) ──► retry if concurrent write
```

## Projections — Answering Read Queries

The event store is optimized for writes and for loading individual aggregates. It is not optimized for queries like "give me all pending leaves for department X sorted by submission date." Running that query by replaying thousands of event streams would be prohibitively slow.

This is where projections come in. A projection is a process that reads events from the event store and builds a read-optimized view — a normal database table you can query efficiently. Projections consume the global event stream in order, applying each event to update their read model.

```go
// projections/leave_summary_projection.go

// This is the read model — a normal GORM model optimized for queries
type LeaveSummaryView struct {
    LeaveID     string    `gorm:"primaryKey"`
    EmployeeID  string    `gorm:"not null;index"`
    EmployeeName string   // denormalized from Employee events
    LeaveType   string    `gorm:"not null"`
    Days        int       `gorm:"not null"`
    StartDate   time.Time
    EndDate     time.Time
    Status      string    `gorm:"not null;index"`
    SubmittedAt time.Time `gorm:"index"`
    ApprovedBy  *string
    RejectedBy  *string
    Department  string    `gorm:"index"`  // for filtering by dept
}

type ProjectionCheckpoint struct {
    ProjectionName  string `gorm:"primaryKey"`
    LastGlobalSeq  int64
}

type LeaveSummaryProjection struct {
    db     *gorm.DB
    logger *slog.Logger
}

func (p *LeaveSummaryProjection) Run(ctx context.Context) error {
    ticker := time.NewTicker(500 * time.Millisecond)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            if err := p.processNewEvents(ctx); err != nil {
                p.logger.Error("projection processing failed", "error", err)
            }
        }
    }
}

func (p *LeaveSummaryProjection) processNewEvents(ctx context.Context) error {
    // Find where we left off
    var checkpoint ProjectionCheckpoint
    p.db.Where("projection_name = ?", "leave_summary").
        FirstOrCreate(&checkpoint, ProjectionCheckpoint{
            ProjectionName: "leave_summary",
            LastGlobalSeq: 0,
        })

    // Fetch new events since last checkpoint, across ALL streams
    var events []EventStore
    p.db.WithContext(ctx).
        Where("global_sequence > ?", checkpoint.LastGlobalSeq).
        Where("aggregate_type = ?", "Leave").
        Order("global_sequence ASC").
        Limit(500).
        Find(&events)

    if len(events) == 0 {
        return nil
    }

    for _, event := range events {
        if err := p.applyEvent(ctx, event); err != nil {
            return err
        }
        checkpoint.LastGlobalSeq = event.GlobalSequence
    }

    // Save updated checkpoint
    return p.db.Save(&checkpoint).Error
}

func (p *LeaveSummaryProjection) applyEvent(ctx context.Context, event EventStore) error {
    switch event.EventType {
    case "LeaveSubmittedEvent":
        var e LeaveSubmittedEvent
        json.Unmarshal(event.Payload, &e)
        return p.db.Create(&LeaveSummaryView{
            LeaveID:     e.LeaveID,
            EmployeeID:  e.EmployeeID,
            LeaveType:   e.LeaveType,
            Days:        e.Days,
            StartDate:   e.StartDate,
            EndDate:     e.EndDate,
            Status:      "PENDING",
            SubmittedAt: event.CreatedAt,
        }).Error

    case "LeaveApprovedEvent":
        var e LeaveApprovedEvent
        json.Unmarshal(event.Payload, &e)
        return p.db.Model(&LeaveSummaryView{}).
            Where("leave_id = ?", e.LeaveID).
            Updates(map[string]interface{}{
                "status":      "APPROVED",
                "approved_by": e.ApprovedBy,
            }).Error

    case "LeaveRejectedEvent":
        var e LeaveRejectedEvent
        json.Unmarshal(event.Payload, &e)
        return p.db.Model(&LeaveSummaryView{}).
            Where("leave_id = ?", e.LeaveID).
            Updates(map[string]interface{}{
                "status":      "REJECTED",
                "rejected_by": e.RejectedBy,
            }).Error

    case "LeaveCancelledEvent":
        return p.db.Model(&LeaveSummaryView{}).
            Where("leave_id = ?", event.AggregateID).
            Update("status", "CANCELLED").Error
    }
    return nil
}
```

Projections are independently rebuildable at any time. If you introduce a new query requirement — say, you now need to filter by department — you add the `Department` field to the view, drop and rebuild the projection from scratch by replaying all events from global sequence 0. The event store still has every event that ever happened. The new view emerges from replaying them. This is one of the most powerful properties of Event Sourcing.

## Snapshots — Solving the Performance Problem

An aggregate with a long history — a `LeaveBalance` that has been accumulating events for three years — might have thousands of events in its stream. Loading it by replaying every event on every command would become unacceptably slow.

Snapshots solve this. Periodically, after some number of events, you save a snapshot of the aggregate's current state. When loading the aggregate later, you load the most recent snapshot and then replay only the events that happened after the snapshot was taken.

```go
// snapshots/snapshot_store.go

type AggregateSnapshot struct {
    StreamID       string         `gorm:"primaryKey"`
    AggregateType  string         `gorm:"not null"`
    Version        int64          `gorm:"not null"`  // sequence_number of last event in snapshot
    State          datatypes.JSON `gorm:"type:jsonb;not null"`
    TakenAt        time.Time      `gorm:"not null;default:now()"`
}

type SnapshotRepository struct {
    db             *gorm.DB
    snapshotEvery  int  // take snapshot every N events (e.g. every 100)
}

// Load with snapshot support
func (r *SnapshotRepository) Load(ctx context.Context, leaveID string) (*LeaveAggregate, error) {
    streamID := fmt.Sprintf("leave-%s", leaveID)
    aggregate := &LeaveAggregate{ID: leaveID}
    startingSequence := int64(0)

    // Try to load the most recent snapshot first
    var snapshot AggregateSnapshot
    result := r.db.Where("stream_id = ?", streamID).First(&snapshot)
    if result.Error == nil {
        // Snapshot found — restore state from it
        json.Unmarshal(snapshot.State, aggregate)
        startingSequence = snapshot.Version
    }

    // Load only events AFTER the snapshot
    var events []EventStore
    r.db.WithContext(ctx).
        Where("stream_id = ? AND sequence_number > ?", streamID, startingSequence).
        Order("sequence_number ASC").
        Find(&events)

    // Replay only the delta since the snapshot
    for _, stored := range events {
        event, _ := deserializeEvent(stored.EventType, stored.Payload)
        aggregate.Apply(event)
    }

    return aggregate, nil
}

// Save with automatic snapshotting
func (r *SnapshotRepository) Save(ctx context.Context, aggregate *LeaveAggregate) error {
    if err := r.baseRepo.Save(ctx, aggregate); err != nil {
        return err
    }

    // Take a snapshot every N events to keep replay fast
    if aggregate.Version % int64(r.snapshotEvery) == 0 {
        r.takeSnapshot(ctx, aggregate)
    }

    return nil
}

func (r *SnapshotRepository) takeSnapshot(ctx context.Context, aggregate *LeaveAggregate) {
    state, _ := json.Marshal(aggregate)
    snapshot := AggregateSnapshot{
        StreamID:      fmt.Sprintf("leave-%s", aggregate.ID),
        AggregateType: "Leave",
        Version:       aggregate.Version,
        State:         state,
    }
    r.db.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns:   []clause.Column{{Name: "stream_id"}},
            DoUpdates: clause.AssignmentColumns([]string{"version", "state", "taken_at"}),
        }).
        Create(&snapshot)
}
```

```
SNAPSHOT + EVENT REPLAY
─────────────────────────

Event stream for leave-balance-emp42 (3 years of history):
  seq 1:    BalanceGranted (annual: 20 days)
  seq 2:    BalanceDeducted (leave L001: 3 days)
  seq 3:    BalanceDeducted (leave L002: 2 days)
  ...
  seq 100:  BalanceGranted (new year grant)   ◄── SNAPSHOT TAKEN HERE
  seq 101:  BalanceDeducted (leave L099: 1 day)
  seq 102:  BalanceDeducted (leave L100: 5 days)

Loading the aggregate today:
  1. Load snapshot at seq 100 (instant — one DB row)
     Restored state: {available: 14 days, used: 6 days}

     Apply seq 102: available = 8

```

## Event Versioning — When Your Events Need to Change

Events are immutable and permanent. But business requirements change. Six months from now, the `LeaveSubmittedEvent` might need a new field — say, `work_from_home_option`. You cannot update the old events in the store. They are history. But you need old events and new events to coexist.

The solution is event versioning and upcasting. You version your events and provide upcasters — functions that transform an old event version into the current version during deserialization.

```go
// versioning/upcaster.go

// Version 1 — original event (stored in event store for old records)
type LeaveSubmittedEventV1 struct {
    LeaveID    string    `json:"leave_id"`
    EmployeeID string    `json:"employee_id"`
    LeaveType  string    `json:"leave_type"`
    Days       int       `json:"days"`
}

// Version 2 — new event with additional field
type LeaveSubmittedEventV2 struct {
    LeaveID          string    `json:"leave_id"`
    EmployeeID       string    `json:"employee_id"`
    LeaveType        string    `json:"leave_type"`
    Days             int       `json:"days"`
    WorkFromHome     bool      `json:"work_from_home"`  // new field
    SchemaVersion    int       `json:"schema_version"`
}

// The upcaster: V1 ──► V2
func UpcastLeaveSubmittedV1ToV2(v1 LeaveSubmittedEventV1) LeaveSubmittedEventV2 {
    return LeaveSubmittedEventV2{
        LeaveID:       v1.LeaveID,
        EmployeeID:    v1.EmployeeID,
        LeaveType:     v1.LeaveType,
        Days:          v1.Days,
        WorkFromHome:  false,  // sensible default for old events
        SchemaVersion: 2,
    }
}

// Updated deserializer with upcasting
func deserializeLeaveSubmitted(payload []byte, metadata map[string]interface{}) LeaveSubmittedEventV2 {
    version, _ := metadata["schema_version"].(int)

    if version < 2 {
        var v1 LeaveSubmittedEventV1
        json.Unmarshal(payload, &v1)
        return UpcastLeaveSubmittedV1ToV2(v1)
    }

    var v2 LeaveSubmittedEventV2
    json.Unmarshal(payload, &v2)
    return v2
}
```

By adding a `schema_version` field to event metadata and writing upcasters for each version transition, you can evolve your events without ever touching the historical data in the event store. Old events get automatically upcast to the current version at read time. New events are written in the current version from the start.

## Event Sourcing + CQRS — The Natural Pairing

Event Sourcing and CQRS (Command Query Responsibility Segregation) are separate patterns, but they are so naturally complementary that they are almost always used together. The separation is clean: the write side (commands) works through aggregates and the event store. The read side (queries) works through projections.

```
EVENT SOURCING + CQRS — COMPLETE ARCHITECTURE
───────────────────────────────────────────────────────────────────────

  CLIENT
    │
    ├──────── WRITE SIDE (Commands) ─────────────────────────────────►
    │
    │  gRPC Command Handler
    │  │
    │  ▼
    │  Load Aggregate (replay from event store)
    │  │
    │  ▼
    │  Execute Command (validate + raise events)
    │  │
    │  ▼
    │  Save Events (append to event store)
    │  │
    │  ▼
    │  Publish Events to Kafka (via Outbox pattern)
    │
    │         Event Store (append-only, source of truth)
    │         │
    │         │  Projection workers read event store
    │         │  and build read models
    │         ▼
    │  ┌──────────────────────────────────────────┐
    │  │  Read Models (PostgreSQL tables)          │
    │  │  ├── leave_summary_view                  │
    │  │  ├── leave_audit_log                     │
    │  │  ├── monthly_leave_report                │
    │  │  └── employee_balance_view               │
    │  └──────────────────────────────────────────┘
    │

              gRPC Query Handler
              │
              ▼
              SELECT from read model (fast, indexed, denormalized)
              Return result to client
```

The write side never needs to be fast at reads — its job is correctness. The read side never needs to handle writes — its job is query performance. Each side is independently optimized and independently scalable.

## Publishing Events to Kafka — Event Sourcing Meets the Outbox

Events saved to the event store must also be published to Kafka so that other services can react to them. This is where Event Sourcing connects naturally to the Outbox Pattern.

The cleanest integration is to make the event store itself the outbox. Instead of a separate outbox table, you have a projection worker that reads from the event store and publishes events to Kafka. This worker tracks a checkpoint just like any other projection, and it publishes each event to Kafka exactly once (with idempotency handled by the consumer's Inbox Pattern).

```go
// kafka_relay/event_store_relay.go

type EventStoreKafkaRelay struct {
    db          *gorm.DB
    kafkaWriter KafkaWriter
    logger      *slog.Logger
}

func (r *EventStoreKafkaRelay) Run(ctx context.Context) error {
    ticker := time.NewTicker(100 * time.Millisecond)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            r.publishNewEvents(ctx)
        }
    }
}

func (r *EventStoreKafkaRelay) publishNewEvents(ctx context.Context) {
    var checkpoint ProjectionCheckpoint
    r.db.FirstOrCreate(&checkpoint, ProjectionCheckpoint{
        ProjectionName: "kafka_relay",
        LastGlobalSeq: 0,
    })

    var events []EventStore
    r.db.WithContext(ctx).
        Where("global_sequence > ?", checkpoint.LastGlobalSeq).
        Order("global_sequence ASC").
        Limit(500).
        Find(&events)

    for _, event := range events {
        topic := fmt.Sprintf("%s.events", strings.ToLower(event.AggregateType))

        err := r.kafkaWriter.WriteMessages(ctx, kafka.Message{
            Topic: topic,
            Key:   []byte(event.AggregateID),
            Value: event.Payload,
            Headers: []kafka.Header{
                {Key: "event-type",      Value: []byte(event.EventType)},
                {Key: "event-store-id",  Value: []byte(event.ID.String())},
                {Key: "stream-id",       Value: []byte(event.StreamID)},
                {Key: "sequence-number", Value: []byte(fmt.Sprintf("%d", event.SequenceNumber))},
            },
        })

        if err != nil {
            r.logger.Error("kafka relay failed", "event_id", event.ID, "error", err)
            return  // stop — retry next tick from same checkpoint
        }

        checkpoint.LastGlobalSeq = event.GlobalSequence
        r.db.Save(&checkpoint)
    }
}
```

## Temporal Queries — The Superpower of Event Sourcing

This is the capability that impresses people the most and is completely impossible in traditional state-based systems. Because every event is stored forever with its timestamp, you can reconstruct the state of any aggregate at any point in the past.

```go
// leave/repository.go — temporal query

func (r *LeaveEventRepository) LoadAtTime(ctx context.Context, leaveID string, at time.Time) (*LeaveAggregate, error) {
    streamID := fmt.Sprintf("leave-%s", leaveID)

    var events []EventStore
    // Load only events that existed at the target time
    r.db.WithContext(ctx).
        Where("stream_id = ? AND created_at <= ?", streamID, at).
        Order("sequence_number ASC").
        Find(&events)

    aggregate := &LeaveAggregate{ID: leaveID}
    for _, stored := range events {
        event, _ := deserializeEvent(stored.EventType, stored.Payload)
        aggregate.Apply(event)
    }

    return aggregate, nil
}
```

```
TEMPORAL QUERY EXAMPLE
─────────────────────────

Question: "What was the status of leave L001 on March 15th at 2pm?"

Event stream for leave-L001:
  seq 1: LeaveSubmitted         created_at: Mar 10, 09:00   ─┐
  seq 2: ManagerInfoRequested   created_at: Mar 12, 14:00   ─┤ Replay these
  seq 3: LeaveReasonUpdated     created_at: Mar 14, 10:00   ─┘ (all before Mar 15 2pm)
  seq 4: LeaveApproved          created_at: Mar 15, 16:00   ─── After target time, skip
  seq 5: LeaveTaken             created_at: Mar 20, 08:00   ─── After target time, skip

Answer: On March 15th at 2pm, leave L001 had Status = PENDING
        (the approval happened at 16:00, two hours later)

In a traditional system: impossible. The current row just shows APPROVED.
In event sourcing: trivial. Replay events up to the target timestamp.
```

This temporal query capability enables an entire class of features: "what was the balance of every employee at end-of-year for the tax report", "what did this leave application look like when the manager approved it", "reconstruct the exact state that triggered this bug". None of these are possible without the complete event history.

## What Event Sourcing Does Not Solve

Event Sourcing is not a silver bullet, and being honest about its costs is what separates a thoughtful engineer from someone who just applies patterns because they sound impressive.

The learning curve is real. The mental model of "state is derived from events, never stored directly" takes time to internalize. Every developer on the team must understand it, or you will get inconsistencies where someone writes an UPDATE statement directly to a read model thinking it is the source of truth.

Projections add operational complexity. You need to monitor projection lag — how far behind the projection is from the latest events. A slow projection means read queries return stale data. You need to handle projection rebuilds carefully in production without downtime.

Event schema evolution requires discipline. Once an event is in the event store, it is there forever. You cannot delete it. You cannot change its schema without writing an upcaster. Every change to an event type must be backward-compatible or explicitly versioned. This discipline is good practice, but it does require more upfront design thinking than just adding a column to a table.

Querying across aggregates is not natural. The event store is organized by aggregate. If you want to find all leaves where both the employee's department is "Engineering" AND the leave type is "Annual" AND the balance was less than 5 days at the time of submission — you need a projection that has joined and denormalized that data in advance. You cannot just write a SQL JOIN. This is why projection design is a first-class concern in event-sourced systems.

Use Event Sourcing when complete audit history is a core requirement, when the ability to rebuild any view of historical data matters, when temporal queries are needed, or when the business domain has rich and complex state transitions that benefit from being modeled as an explicit sequence of events. For simple CRUD-heavy services with no audit requirements and no complex state machines, the additional complexity is not justified. The pattern is powerful precisely because it is not universally applicable.
