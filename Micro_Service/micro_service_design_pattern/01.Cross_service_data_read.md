# Cross-Service Data Aggregation in Microservices

### How to Query Data That Lives in Multiple Services

---

## Welcome to One of the Hardest Problems in Microservices

So you just joined the team, and someone handed you a task that sounds simple on the surface: "Get me a list of leave applications with employee info and approval status." You open your laptop, write a join query in your head, and then you realize — the data is not in one database. Leave info lives in the Leave Service. Employee info lives in the Employee Service. Approval info lives in the Approval Service. And each of those services has its own database that no one else is supposed to touch directly.

Welcome to the cross-service data aggregation problem. This is not a bug. This is not a design mistake. This is actually the natural consequence of doing microservices correctly. But it means we need to think differently about how we fetch and combine data.

Let me walk you through what is actually happening, why it is hard, and what options we have — in the context of our actual stack: Go, GORM, Kafka, gRPC, and Socket.

---

## First, Understand Why We Cannot Just Do a SQL JOIN

In a monolithic application, all your data sits in one database. You write a JOIN query and you are done in one round trip. Life is easy. But we intentionally broke that monolith apart. Each service now owns its data completely — no other service is allowed to reach into another service's database directly.

```
MONOLITH (The Old Way)
─────────────────────
       ┌──────────────────────────────┐
       │       Single Database        │
       │                              │
       │  employees  leaves  approvals│
       │    table     table    table  │
       └──────────────────────────────┘
                      │
              One JOIN query
              gets everything



MICROSERVICES (Our Way)
────────────────────────
  ┌─────────────────┐    ┌─────────────────┐    ┌──────────────────┐
  │  Employee Svc   │    │   Leave Svc     │    │  Approval Svc    │
  │                 │    │                 │    │                  │
  │  ┌───────────┐  │    │  ┌───────────┐  │    │  ┌────────────┐  │
  │  │ employees │  │    │  │  leaves   │  │    │  │ approvals  │  │
  │  │    DB     │  │    │  │    DB     │  │    │  │     DB     │  │
  │  └───────────┘  │    │  └───────────┘  │    │  └────────────┘  │
  └─────────────────┘    └─────────────────┘    └──────────────────┘
         │                      │                        │
         └──────────────────────┴────────────────────────┘
                  No shared database. No direct JOIN possible.
```

This separation is what gives us independent deployability, independent scaling, and fault isolation. But it creates the data aggregation challenge. So now we need to solve it at the application layer, not the database layer.

---

## The Three Strategies You Will Use in This Project

There are three main ways to solve this, and in a mature system like ours, you will actually use all three depending on the situation. Let me explain each one properly.

---

## Strategy 1 — API Composition (The Orchestrator Pattern)

This is the most straightforward approach. You create one service — or a dedicated API Gateway layer — whose job is to call each individual service, collect the data, and stitch it together before returning a response to the client.

Think of it like this: imagine you are a team lead who needs to write a full report about an employee's leave. You call the HR person and ask for employee details. You call the Leave Manager and ask for the leave records. You call the Department Head and ask for the approval status. Then you sit down and write the combined report yourself. That is exactly what the Orchestrator does.

```
CLIENT (Frontend / Mobile App)
          │
          │  GET /leave-applications?employee_id=42
          ▼
┌─────────────────────────────┐
│      API Gateway / BFF      │
│   (Leave Aggregator Layer)  │
│                             │
│   1. Call Leave Service     │───────────────► Leave Service DB
│   2. Call Employee Service  │──────────────► Employee Service DB
│   3. Call Approval Service  │─────────────► Approval Service DB
│   4. Merge all data         │
│   5. Return combined result │
└─────────────────────────────┘
          │
          ▼
     Combined JSON response
     {
       leave_id: 1,
       employee_name: "Rahim",
       leave_type: "Annual",
       approval_status: "Pending"
     }
```

In our Go stack, this orchestrator would make three gRPC calls, one to each service. gRPC is perfect for this because it is fast, strongly typed with Protobuf, and supports deadlines so one slow service cannot hang the whole request.

Here is roughly how that looks in Go:

```go
func (s *AggregatorService) GetLeaveApplicationDetails(
    ctx context.Context,
    req *pb.GetLeaveRequest,
) (*pb.LeaveApplicationDetails, error) {

    // Call Leave Service via gRPC
    leave, err := s.leaveClient.GetLeave(ctx, &leavepb.GetLeaveReq{
        LeaveId: req.LeaveId,
    })
    if err != nil {
        return nil, err
    }

    // Call Employee Service via gRPC using the employee_id from the leave record
    employee, err := s.employeeClient.GetEmployee(ctx, &empb.GetEmployeeReq{
        EmployeeId: leave.EmployeeId,
    })
    if err != nil {
        return nil, err
    }

    // Call Approval Service via gRPC using the leave_id
    approval, err := s.approvalClient.GetApproval(ctx, &approvalpb.GetApprovalReq{
        LeaveId: req.LeaveId,
    })
    if err != nil {
        return nil, err
    }

    // Combine and return
    return &pb.LeaveApplicationDetails{
        LeaveId:        leave.Id,
        LeaveType:      leave.Type,
        StartDate:      leave.StartDate,
        EndDate:        leave.EndDate,
        EmployeeName:   employee.Name,
        EmployeeEmail:  employee.Email,
        Department:     employee.Department,
        ApprovalStatus: approval.Status,
        ApprovedBy:     approval.ApprovedBy,
    }, nil
}
```

Now here is an important optimization. In the code above, we are making the three calls one after another — sequentially. That is slow because we wait for Leave Service to finish before we even start calling Employee Service. A better approach when the calls are independent of each other is to fire them all at the same time using Go's goroutines and `sync.WaitGroup` or error groups.

```
Sequential (Slow — 300ms total if each takes 100ms):
─────────────────────────────────────────────────────
  ├──── Call Leave Service ────┤
                               ├──── Call Employee Service ────┤
                                                               ├──── Call Approval Service ────┤
  ◄───────────────────────── 300ms ──────────────────────────────────────────────────────────►


Parallel (Fast — ~100ms total):
────────────────────────────────
  ├──── Call Leave Service ────┤
  ├──── Call Employee Service ─┤
  ├──── Call Approval Service ─┤
  ◄──── 100ms ───────────────►
```

For the leave applications list (not just a single record), you would first fetch all the leave records, collect all unique employee IDs and leave IDs from them, then make one batched gRPC call per service — "give me employees with these IDs" and "give me approvals for these leave IDs." This avoids the N+1 problem where you would otherwise be making one gRPC call per row.

The trade-off with API Composition is that it adds network latency (you are making multiple network hops), and if one service is down, your combined query fails. You handle the second problem using circuit breakers and graceful degradation — for example, returning the leave data even if the approval service is temporarily unavailable, and just marking the approval status as "Unavailable."

## Strategy 2 — Data Denormalization via Kafka Events (The Materialized View Pattern)

The API Composition approach is great for real-time, fresh data. But when you need to run heavy queries over thousands of records — like generating a monthly leave report — making gRPC calls for each row is just too slow and puts too much load on the individual services.

This is where Kafka comes in, and it works beautifully with our existing setup.

The idea is simple: whenever something important happens in a service, that service publishes an event to a Kafka topic. Other services that care about that data listen to that topic and store a local copy of the relevant fields. This local copy is sometimes called a "read model" or "materialized view."

```
Normal Operations: Data Flows Through Kafka
────────────────────────────────────────────

Employee Service                    Kafka                   Leave Reporting Service
─────────────────    ──────────────────────────────────    ─────────────────────────
Employee updated ──► employee.updated topic               Consumes event
                                         │               Stores employee_name,
                                         └──────────────► department in local DB


Leave Service                       Kafka                   Leave Reporting Service
──────────────────   ──────────────────────────────────    ─────────────────────────
Leave submitted  ──► leave.submitted topic                Consumes event
                                         │               Stores leave_type,
                                         └──────────────► dates, employee_id


Approval Service                    Kafka                   Leave Reporting Service
─────────────────    ──────────────────────────────────    ─────────────────────────
Leave approved   ──► leave.approved topic                 Consumes event
                                         │               Updates approval_status
                                         └──────────────► in local DB


─────────────────────────────────────────────────────────────────────────────────
Client wants leave report? Leave Reporting Service answers with ONE local query!
─────────────────────────────────────────────────────────────────────────────────
```

The Leave Reporting Service maintains its own local database table that looks something like this:

```
leave_reporting_db.leave_applications_view
─────────────────────────────────────────────────────────────────────────────────
leave_id │ employee_id │ employee_name │ department │ leave_type │ approval_status
─────────────────────────────────────────────────────────────────────────────────
   1     │     42      │   Rahim Ali   │   DevOps   │   Annual   │   Approved
   2     │     17      │  Fatema Begum │    HR      │   Sick     │   Pending
   3     │     42      │   Rahim Ali   │   DevOps   │   Casual   │   Rejected
─────────────────────────────────────────────────────────────────────────────────
```

Now a query for "all leave applications with employee info and approval status" is a single fast local SELECT statement on this pre-built view. No gRPC calls needed at query time at all.

In our Go Kafka consumer, it looks roughly like this:

```go
// This runs in the Leave Reporting Service, consuming from multiple topics

func (c *LeaveReportConsumer) HandleLeaveSubmitted(msg kafka.Message) error {
    var event LeaveSubmittedEvent
    if err := json.Unmarshal(msg.Value, &event); err != nil {
        return err
    }

    // Upsert into our local read model
    return c.db.Clauses(clause.OnConflict{
        Columns:   []clause.Column{{Name: "leave_id"}},
        DoUpdates: clause.AssignmentColumns([]string{"leave_type", "start_date", "end_date"}),
    }).Create(&LeaveApplicationView{
        LeaveID:    event.LeaveID,
        EmployeeID: event.EmployeeID,
        LeaveType:  event.LeaveType,
        StartDate:  event.StartDate,
        EndDate:    event.EndDate,
    }).Error
}

func (c *LeaveReportConsumer) HandleEmployeeUpdated(msg kafka.Message) error {
    var event EmployeeUpdatedEvent
    if err := json.Unmarshal(msg.Value, &event); err != nil {
        return err
    }

    // Update the employee fields in our local view wherever this employee appears
    return c.db.Model(&LeaveApplicationView{}).
        Where("employee_id = ?", event.EmployeeID).
        Updates(map[string]interface{}{
            "employee_name": event.Name,
            "department":    event.Department,
        }).Error
}

func (c *LeaveReportConsumer) HandleLeaveApproved(msg kafka.Message) error {
    var event LeaveApprovedEvent
    if err := json.Unmarshal(msg.Value, &event); err != nil {
        return err
    }

    return c.db.Model(&LeaveApplicationView{}).
        Where("leave_id = ?", event.LeaveID).
        Updates(map[string]interface{}{
            "approval_status": event.Status,
            "approved_by":     event.ApprovedBy,
        }).Error
}
```

The big win here is query performance. The big trade-off is that this data is eventually consistent. If an employee updates their name right now, the reporting view will only reflect that change after the `employee.updated` Kafka event is consumed and processed — which typically happens within milliseconds to a few seconds, but it is not instant. For a leave report that runs once a day or once a week, this is completely acceptable. For a real-time dashboard where a manager is watching approvals happen live, you need to think carefully.

The other thing to keep in mind is that you are duplicating data across services. That is intentional in microservices — it is the price you pay for independence and query speed. The source of truth still lives in the original service. The reporting service just keeps a read-optimized copy.

## Strategy 3 — The CQRS Approach With a Dedicated Query Service

As your system grows beyond 12 services, you will notice that both Strategy 1 and Strategy 2 lead to a new kind of complexity. In Strategy 1, you have multiple aggregator services all calling the same downstream gRPC endpoints, putting load on them. In Strategy 2, you have multiple services maintaining their own local Kafka-driven copies of overlapping data.

The mature solution to this is CQRS — Command Query Responsibility Segregation. The idea is to completely separate the "write path" from the "read path."

Every service handles its own writes as it always did. But for reads — especially reads that span multiple services — you build a dedicated Query Service. Its only job is to listen to all the relevant Kafka topics, build and maintain a rich read-optimized database (often Elasticsearch, or a dedicated PostgreSQL schema), and answer complex queries efficiently.

```
WRITE PATH (Commands — each service handles its own)
─────────────────────────────────────────────────────
Client ──► Leave Service ──► writes to Leave DB ──► publishes leave.* events
Client ──► Employee Service ──► writes to Employee DB ──► publishes employee.* events
Client ──► Approval Service ──► writes to Approval DB ──► publishes approval.* events


READ PATH (Queries — goes through dedicated Query Service)
──────────────────────────────────────────────────────────
Kafka Topics
  leave.*  ────────────────────┐
  employee.* ─────────────────►│  Leave Query Service
  approval.* ─────────────────►│  (Consumes all, maintains
                               │   a rich combined read model)
                               └──────► Query DB (denormalized, optimized)
                                               │
                                         Client query ◄───────────────────────────
```

In our stack with Socket support, this Query Service is also the perfect place to push real-time updates when a leave status changes. The Kafka consumer in the Query Service processes the `leave.approved` event, updates its local read model, and then broadcasts the updated data to connected clients via Socket — all in one flow.

```
Leave Approved Event Flow With Real-Time Socket Push
──────────────────────────────────────────────────────

Approval Service                Kafka                 Leave Query Service          Client Browser
──────────────────  ──────────────────────────────  ─────────────────────────    ─────────────────
Manager approves ──► leave.approved topic           Consumer receives event
     leave                          │              Updates local read model
                                    └────────────► Emits Socket event
                                                   "leave_status_updated"        ◄──── Socket push
                                                                                  UI updates live!
```

## Choosing the Right Strategy for Each Situation

The three strategies are not mutually exclusive. A well-designed system uses all of them, picking the right one based on the situation. Here is a mental model to guide that decision:

```
                    Is this a real-time, user-facing request
                    that needs fresh data immediately?
                              │
                    ┌─────────┴──────────┐
                   YES                   NO
                    │                    │
                    ▼                    ▼
         API Composition           Is this a report or
         via gRPC calls            bulk query over many rows?
         (Strategy 1)                    │
                              ┌──────────┴──────────┐
                             YES                     NO
                              │                      │
                              ▼                      ▼
                   Kafka Denormalization        CQRS Query Service
                   + Local Read Model          with Socket push
                   (Strategy 2)                (Strategy 3)
```

In practical terms for your leave application feature:

When a manager opens a single leave application to review it in detail, use Strategy 1 — make gRPC calls to get the freshest data on that individual record. When the HR team runs a report to see all pending leaves for this month across all departments, use Strategy 2 or 3 — query the pre-built materialized view, which can answer in milliseconds regardless of how many records there are. When a manager approves a leave and the employee should see their status update instantly without refreshing the page, use Strategy 3 combined with Socket — the Query Service processes the Kafka event and pushes the update through the Socket connection.

## One Final Thing to Keep in Mind

You are going to be tempted, especially early on, to find shortcuts. Maybe you will think: "Can I just let the Leave Service query the Employee Service's database directly? Just for now?" The answer is always no, and it is important that you understand why. The moment one service reads another service's database directly, you have created a hidden coupling. Now if the Employee Service team renames a column or changes a table structure, your Leave Service breaks — and neither team knows why until production goes down. The strategies in this document exist precisely to avoid that. They are more work upfront, but they make the system maintainable and safe to evolve independently as we add more services.

Every choice in this document — gRPC for synchronous aggregation, Kafka for asynchronous data propagation, dedicated query services for complex reads — is a deliberate investment in keeping our services truly independent from each other. That independence is what makes it possible for 12 services and 12 teams to move fast without breaking each other.
