# The Outbox Pattern in Microservices

### Everything You Need to Know — Explained Like You Just Joined the Team

---

## The Problem That Made the Outbox Pattern Necessary

Before we talk about what the Outbox Pattern is, we need to sit with the problem it solves. And I want you to really feel this problem, because until you have been paged at 2am because an order was charged but never fulfilled, or a leave was approved but the manager never got notified, the solution can feel like overengineering. It is not. It is one of the most important reliability patterns you will use in this system.

Here is the situation. In any event-driven microservice, you constantly need to do two things together: write something to your database, and then publish an event to Kafka to tell the rest of the system that something happened. These two operations seem simple. But they are not atomic. There is no transaction that spans both your PostgreSQL database and Apache Kafka at the same time. They are two completely separate systems.

This means that no matter which order you do them in, there is a failure window between the two writes — and in that window, if your service crashes, your system ends up in an inconsistent state.

Let me show you both orderings and why both of them are broken.

```
ORDERING 1: Write to DB first, then publish to Kafka
──────────────────────────────────────────────────────

  Leave Service receives a "create leave" request
         │
         ▼
  ┌─────────────────────────────┐
  │  Step 1: Write to DB        │  ← succeeds ✓
  │  INSERT INTO leaves ...     │
  └─────────────────────────────┘
         │
         │  ⚡ SERVICE CRASHES HERE ⚡
         │
         ▼
  ┌─────────────────────────────┐
  │  Step 2: Publish to Kafka   │  ← NEVER RUNS ✗
  │  leave.created event        │
  └─────────────────────────────┘

RESULT:
  Database: leave record EXISTS
  Kafka: event NEVER PUBLISHED
  Balance Service: never deducted days
  Approval Service: never created approval record
  Manager: never notified
  System: permanently inconsistent ← DISASTER
```

```
ORDERING 2: Publish to Kafka first, then write to DB
──────────────────────────────────────────────────────

  Leave Service receives a "create leave" request
         │
         ▼
  ┌─────────────────────────────┐
  │  Step 1: Publish to Kafka   │  ← succeeds ✓
  │  leave.created event        │
  └─────────────────────────────┘
         │
         │  ⚡ SERVICE CRASHES HERE ⚡
         │
         ▼
  ┌─────────────────────────────┐
  │  Step 2: Write to DB        │  ← NEVER RUNS ✗
  │  INSERT INTO leaves ...     │
  └─────────────────────────────┘

RESULT:
  Kafka: event PUBLISHED ✓ (downstream services are processing it)
  Database: leave record DOES NOT EXIST ✗
  Balance Service: deducted days from a leave that doesn't exist
  Manager: got notified about a phantom leave
  System: permanently inconsistent ← ALSO A DISASTER
```

Both orderings have the same fundamental problem: between the two writes, your process can die. And in a production system, processes die all the time — deployments, out-of-memory crashes, network blips, infrastructure failures. A system design that breaks every time a process crashes is not a production-grade system.

The Outbox Pattern is the solution to this exact problem. And the insight behind it is elegant: instead of writing to two separate systems, you write everything into one system — your database — in a single atomic transaction, and then let a separate reliable process handle the Kafka publishing asynchronously.

## What the Outbox Pattern Actually Is

The core idea is this. You add a special table to your service's database called the outbox table. Whenever your service wants to publish an event to Kafka, instead of calling Kafka directly, it inserts a row into this outbox table as part of the same database transaction that contains your business write. Since both the business data and the outbox event are in the same transaction, they are committed atomically — either both succeed or neither does.

Then a separate background process, called the Outbox Worker or Message Relay, polls the outbox table for unpublished events, publishes them to Kafka, and marks them as published. If the worker crashes after publishing but before marking the row as published, it will publish the same event again on restart. This means you get at-least-once delivery — an event might be delivered more than once in edge cases, but it will never be lost.

```
THE OUTBOX PATTERN — Core Structure
─────────────────────────────────────

  Incoming Request
         │
         ▼
  ┌──────────────────────────────────────────────────┐
  │  Single Database Transaction (atomic)            │
  │                                                  │
  │  ┌───────────────────┐   ┌──────────────────┐   │
  │  │  leaves table     │   │  outbox table     │   │
  │  │                   │   │                   │   │
  │  │  INSERT new leave │   │  INSERT event row │   │
  │  │  id: "L001"       │   │  topic: leave.*   │   │
  │  │  status: PENDING  │   │  payload: {...}   │   │
  │  │                   │   │  published: false │   │
  │  └───────────────────┘   └──────────────────┘   │
  │                                                  │
  │  COMMIT — both writes happen together            │
  └──────────────────────────────────────────────────┘
                                    │
                                    │  (asynchronously)
                                    ▼
                         ┌──────────────────┐
                         │  Outbox Worker   │
                         │  (background     │
                         │   goroutine)     │
                         │                  │
                         │  1. Poll outbox  │
                         │  2. Publish to   │
                         │     Kafka        │
                         │  3. Mark         │
                         │     published    │
                         └────────┬─────────┘
                                  │
                                  ▼
                               Kafka
                          (event delivered
                           reliably)
```

Now if the service crashes anywhere — even in the middle of the transaction — you are safe. If it crashes before the commit, both writes are rolled back and neither happens. If it crashes after the commit but before the outbox worker runs, the worker will pick up the unpublished row on its next poll cycle. If the worker crashes after publishing but before marking as published, it will republish on restart — which is why downstream consumers must be idempotent, as covered in the SAGA guide. But the event will never be silently lost.

```
CRASH SAFETY ANALYSIS
──────────────────────────────────────────────────────────────────────────
Crash Point                    DB State        Kafka State    Outcome
──────────────────────────────────────────────────────────────────────────
During transaction             Rolled back     Nothing sent   ✓ Clean
After commit, before worker    Both rows exist Nothing sent   ✓ Worker retries
Worker crashes after publish   Both rows exist Event sent     ✓ Idempotent retry
Worker crashes after mark      Both rows exist Event sent     ✓ Complete
──────────────────────────────────────────────────────────────────────────
No scenario results in a permanently inconsistent state.
```

## The Outbox Table Schema

Before writing any code, let us look at what the outbox table needs to contain. You will add this table to every service in the project that needs to publish events to Kafka.

```sql
CREATE TABLE outbox_events (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_id  VARCHAR(255) NOT NULL,   -- the ID of the business entity (e.g. leave_id)
    aggregate_type VARCHAR(255) NOT NULL,  -- the type of entity (e.g. "Leave", "Employee")
    event_type    VARCHAR(255) NOT NULL,   -- the event name (e.g. "LeaveCreated")
    topic         VARCHAR(255) NOT NULL,   -- the Kafka topic to publish to
    payload       JSONB NOT NULL,          -- the event data
    published     BOOLEAN NOT NULL DEFAULT false,
    published_at  TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    retry_count   INT NOT NULL DEFAULT 0,
    last_error    TEXT
);

CREATE INDEX idx_outbox_unpublished ON outbox_events (created_at)
    WHERE published = false;
```

The partial index on `WHERE published = false` is important. As the system runs, the outbox table accumulates millions of rows. Without this index, the worker's poll query would do a full table scan every 100 milliseconds — brutal on the database. With the partial index, the query only looks at the small set of unpublished rows, which is almost always a tiny fraction of the total.

In Go, the GORM model looks like this:

```go
type OutboxEvent struct {
    ID            uuid.UUID      `gorm:"type:uuid;primaryKey;default:gen_random_uuid()"`
    AggregateID   string         `gorm:"not null;index"`
    AggregateType string         `gorm:"not null"`
    EventType     string         `gorm:"not null"`
    Topic         string         `gorm:"not null"`
    Payload       datatypes.JSON `gorm:"type:jsonb;not null"`
    Published     bool           `gorm:"not null;default:false;index"`
    PublishedAt   *time.Time
    CreatedAt     time.Time
    RetryCount    int            `gorm:"not null;default:0"`
    LastError     *string
}
```

## Implementation — Part 1: Writing to the Outbox

The first half of the pattern is the write side. Whenever a service performs a business operation that should produce a Kafka event, it writes both the business data and the outbox event in a single transaction. Let me show you a complete, production-quality implementation for our Leave Service.

```go
// outbox/publisher.go — A helper for writing outbox events within transactions

package outbox

import (
    "encoding/json"
    "gorm.io/gorm"
)

type Publisher struct{}

func (p *Publisher) Publish(tx *gorm.DB, topic, eventType, aggregateType, aggregateID string, payload interface{}) error {
    payloadBytes, err := json.Marshal(payload)
    if err != nil {
        return fmt.Errorf("outbox: failed to marshal payload: %w", err)
    }

    event := OutboxEvent{
        AggregateID:   aggregateID,
        AggregateType: aggregateType,
        EventType:     eventType,
        Topic:         topic,
        Payload:       payloadBytes,
        Published:     false,
    }

    return tx.Create(&event).Error
}
```

```go
// leave/service.go — The Leave Service using the outbox publisher

type LeaveService struct {
    db             *gorm.DB
    outboxPublisher *outbox.Publisher
}

func (s *LeaveService) CreateLeave(ctx context.Context, req CreateLeaveRequest) (*Leave, error) {
    var createdLeave *Leave

    // Everything inside this transaction is atomic
    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // Business write #1 — create the leave record
        leave := &Leave{
            ID:         uuid.NewString(),
            EmployeeID: req.EmployeeID,
            LeaveType:  req.LeaveType,
            StartDate:  req.StartDate,
            EndDate:    req.EndDate,
            Days:       req.Days,
            Status:     "PENDING",
        }
        if err := tx.Create(leave).Error; err != nil {
            return fmt.Errorf("failed to create leave: %w", err)
        }

        // Outbox write — insert event into same transaction
        if err := s.outboxPublisher.Publish(
            tx,
            "leave.events",           // Kafka topic
            "LeaveCreated",           // event type
            "Leave",                  // aggregate type
            leave.ID,                 // aggregate ID
            LeaveCreatedPayload{      // event payload
                LeaveID:    leave.ID,
                EmployeeID: leave.EmployeeID,
                LeaveType:  leave.LeaveType,
                Days:       leave.Days,
                StartDate:  leave.StartDate,
                EndDate:    leave.EndDate,
            },
        ); err != nil {
            return fmt.Errorf("failed to write outbox event: %w", err)
        }

        createdLeave = leave
        return nil
        // If anything above failed, the ENTIRE transaction rolls back.
        // Neither the leave record nor the outbox row will exist.
    })

    return createdLeave, err
}
```

Notice that the outbox publisher receives the `tx *gorm.DB` — the active transaction — not the root `s.db`. This is critical. If you accidentally use `s.db` instead of `tx` for the outbox write, the outbox event will be written in a separate implicit transaction, and you are right back to the dual-write problem.

## Implementation — Part 2: The Outbox Worker (Polling Approach)

The second half of the pattern is the relay process. This is a background goroutine that wakes up on a timer, reads unpublished rows from the outbox table, publishes them to Kafka one by one, and marks them as published. It runs inside the same service binary but independently of the request-handling path.

```go
// outbox/worker.go — The Polling Outbox Worker

package outbox

type Worker struct {
    db          *gorm.DB
    kafkaWriter KafkaWriter
    pollInterval time.Duration
    batchSize   int
    logger      *slog.Logger
}

func NewWorker(db *gorm.DB, writer KafkaWriter, opts ...WorkerOption) *Worker {
    w := &Worker{
        db:           db,
        kafkaWriter:  writer,
        pollInterval: 100 * time.Millisecond,
        batchSize:    100,
    }
    for _, opt := range opts {
        opt(w)
    }
    return w
}

func (w *Worker) Run(ctx context.Context) error {
    ticker := time.NewTicker(w.pollInterval)
    defer ticker.Stop()

    w.logger.Info("outbox worker started", "poll_interval", w.pollInterval)

    for {
        select {
        case <-ctx.Done():
            w.logger.Info("outbox worker stopped")
            return ctx.Err()
        case <-ticker.C:
            if err := w.processBatch(ctx); err != nil {
                w.logger.Error("outbox worker batch failed", "error", err)
                // Do not return — keep running, log the error, try again next tick
            }
        }
    }
}

func (w *Worker) processBatch(ctx context.Context) error {
    var events []OutboxEvent

    // Fetch a batch of unpublished events, oldest first
    result := w.db.WithContext(ctx).
        Where("published = ?", false).
        Where("retry_count < ?", 5).  // Give up after 5 retries
        Order("created_at ASC").
        Limit(w.batchSize).
        Find(&events)

    if result.Error != nil {
        return fmt.Errorf("failed to fetch outbox events: %w", result.Error)
    }

    if len(events) == 0 {
        return nil // Nothing to do this tick
    }

    w.logger.Info("processing outbox batch", "count", len(events))

    for _, event := range events {
        if err := w.publishEvent(ctx, event); err != nil {
            // Record the error but continue processing the rest of the batch
            w.logger.Error("failed to publish event",
                "event_id", event.ID,
                "error", err,
            )
            errMsg := err.Error()
            w.db.Model(&event).Updates(map[string]interface{}{
                "retry_count": gorm.Expr("retry_count + 1"),
                "last_error":  &errMsg,
            })
        }
    }

    return nil
}

func (w *Worker) publishEvent(ctx context.Context, event OutboxEvent) error {
    // Publish to Kafka
    err := w.kafkaWriter.WriteMessages(ctx, kafka.Message{
        Topic: event.Topic,
        Key:   []byte(event.AggregateID),  // Using aggregate ID as Kafka key
        Value: event.Payload,              // Raw JSON bytes
        Headers: []kafka.Header{
            {Key: "event-type", Value: []byte(event.EventType)},
            {Key: "aggregate-type", Value: []byte(event.AggregateType)},
            {Key: "outbox-event-id", Value: []byte(event.ID.String())},
        },
    })
    if err != nil {
        return fmt.Errorf("kafka write failed: %w", err)
    }

    // Mark as published — only after Kafka confirmed receipt
    now := time.Now()
    return w.db.Model(&event).Updates(map[string]interface{}{
        "published":    true,
        "published_at": &now,
    }).Error
}
```

And here is how you wire it into your service's main function so it starts alongside your gRPC server:

```go
// main.go

func main() {
    db := setupDatabase()
    kafkaWriter := setupKafkaWriter()

    outboxWorker := outbox.NewWorker(db, kafkaWriter,
        outbox.WithPollInterval(100*time.Millisecond),
        outbox.WithBatchSize(100),
    )

    // Run worker in a separate goroutine
    g, ctx := errgroup.WithContext(context.Background())

    g.Go(func() error {
        return outboxWorker.Run(ctx)
    })

    g.Go(func() error {
        return runGRPCServer(ctx, db)
    })

    if err := g.Wait(); err != nil {
        log.Fatal(err)
    }
}
```

The polling worker has a deliberate design choice: even if publishing a single event fails, it logs the error, increments the retry count, and moves on to the next event in the batch. One bad event should not block all subsequent events. After five retries, the event is left in the outbox table with `retry_count >= 5` and will not be retried automatically — it becomes a candidate for your dead-letter monitoring system, which alerts on-call engineers about events that could not be published after repeated attempts.

## The Kafka Key Is Not an Accident

Notice in the `publishEvent` function that we set the Kafka message key to `event.AggregateID` — the leave ID, employee ID, or whatever the business entity is. This is deliberate and important.

Kafka partitions messages by key. All messages with the same key go to the same partition, and within a partition, Kafka preserves ordering. This means all events related to a single leave application — "LeaveCreated", "LeaveApproved", "LeaveCancelled" — will always land on the same Kafka partition and be processed by the consumer in the correct order. Without this, a consumer could process "LeaveCancelled" before "LeaveCreated" for the same leave ID, which would produce nonsensical results.

```
KAFKA PARTITIONING BY AGGREGATE ID
────────────────────────────────────

Events in Outbox (all services combined):
  LeaveCreated  (leave_id: L001)
  LeaveCreated  (leave_id: L002)
  BalanceDeducted (leave_id: L001)
  LeaveApproved  (leave_id: L002)
  LeaveCancelled (leave_id: L001)

After Kafka partitions by key (leave_id):
  Partition 0        Partition 1        Partition 2
  ───────────        ───────────        ───────────
  L001 events        L002 events        (other IDs)
  ───────────        ───────────
  LeaveCreated       LeaveCreated
  BalanceDeducted    LeaveApproved
  LeaveCancelled

  Ordering preserved  Ordering preserved
  per leave_id        per leave_id
```

## Outbox Variant 2 — Transaction Log Tailing (CDC with Debezium)

The polling approach works well and is straightforward to implement in Go. But it has a subtle cost: every 100 milliseconds, your outbox worker is running a SELECT query against your database. In a high-throughput system with many services, this constant polling adds up and puts unnecessary read pressure on the database.

There is a more elegant approach: instead of your application code polling for changes, you let the database's own internal mechanism tell you about changes as they happen. This technique is called Change Data Capture, or CDC. The most commonly used CDC tool in Go microservice ecosystems is Debezium.

Every serious relational database — including PostgreSQL — maintains an internal write-ahead log (WAL). Every INSERT, UPDATE, and DELETE is written to this log before it touches the actual data files. The WAL is what allows databases to recover after a crash. Debezium taps into this log and streams changes to Kafka as they happen, with no polling required.

```
POLLING APPROACH vs CDC APPROACH
──────────────────────────────────────────────────────────────────────────

POLLING (What we built above):
────────────────────────────────
                              ┌────────────────┐
  Every 100ms:                │  Outbox Worker │
  Worker wakes up ───────────►│  SELECT WHERE  │──► Kafka
  and queries DB              │  published=false│
                              └────────────────┘
                                      │
                                      ▼
                               PostgreSQL DB
                              (gets queried
                               repeatedly)

  Latency: 0-100ms (depends on poll interval)
  DB load: Constant read queries


CDC with Debezium:
───────────────────
                              ┌─────────────────┐
  PostgreSQL WAL ────────────►│    Debezium     │──► Kafka
  (internal log)              │  (reads WAL,    │
  streams changes             │   no polling)   │
  automatically               └─────────────────┘

  Latency: Near-zero (milliseconds after commit)
  DB load: Near-zero (WAL reading is very lightweight)
```

When you insert a row into the outbox table, Debezium detects that INSERT in the WAL and immediately publishes a corresponding event to Kafka — typically within milliseconds. Your application code does not need a background goroutine at all. The outbox table becomes a pure durability mechanism, and Debezium handles all the Kafka publishing.

Here is what the overall architecture looks like with Debezium:

```
CDC / DEBEZIUM OUTBOX ARCHITECTURE
────────────────────────────────────

Leave Service
  │
  │  db.Transaction:
  │    INSERT into leaves      ─┐
  │    INSERT into outbox      ─┘ (one atomic transaction)
  │
  ▼
PostgreSQL WAL
  │
  │  Debezium connector reads WAL
  │  detects INSERT into outbox table
  ▼
Debezium (running as Docker container)
  │
  │  Transforms outbox row into Kafka message
  │  Routes to correct topic based on outbox.topic column
  ▼
Kafka
  │
  ▼
Downstream consumers
(Balance Service, Notification Service, Approval Service, etc.)
```

In Docker Compose, Debezium runs as a separate container alongside your services:

```yaml
# docker-compose.yml (relevant excerpt)

services:
  debezium:
    image: debezium/connect:2.4
    environment:
      BOOTSTRAP_SERVERS: kafka:9092
      GROUP_ID: 1
      CONFIG_STORAGE_TOPIC: debezium_configs
      OFFSET_STORAGE_TOPIC: debezium_offsets
      STATUS_STORAGE_TOPIC: debezium_status
    depends_on:
      - kafka
      - postgres
    ports:
      - "8083:8083"
```

And you register a connector via Debezium's REST API (this can be done from a Go init script or a curl command on startup):

```json
{
  "name": "leave-service-outbox-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "leave_service",
    "database.password": "secret",
    "database.dbname": "leave_db",
    "database.server.name": "leave_service",
    "table.include.list": "public.outbox_events",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.table.field.event.id": "id",
    "transforms.outbox.table.field.event.key": "aggregate_id",
    "transforms.outbox.table.field.event.type": "event_type",
    "transforms.outbox.table.field.event.payload": "payload",
    "transforms.outbox.route.topic.replacement": "${routedByValue}"
  }
}
```

Debezium's built-in Outbox Event Router transformation understands the outbox table structure and routes each event to the correct Kafka topic based on the `topic` column in the outbox table. Your service code does not change at all — you still write to the outbox table the same way. Only the relay mechanism changes from polling to WAL-tailing.

The trade-off is operational complexity. CDC requires configuring PostgreSQL's `wal_level` to `logical`, running and monitoring the Debezium container, and managing connector configurations. For a system with 12 services, the reduced database load and near-zero latency are almost always worth it. For a simpler setup or during early development, the polling worker is perfectly fine and much easier to get running quickly.

## Outbox Variant 3 — Per-Aggregate Outbox Tables

In the basic implementation, all services share a single `outbox_events` table. This is clean and simple, but as message volume grows, this single table becomes a hot spot. Every service is inserting into it, and the outbox worker is constantly polling it. High-throughput aggregates like leave events, approval events, and notification events all compete on the same table.

The solution is to create separate outbox tables per aggregate type. Instead of one generic `outbox_events` table, you have `leave_outbox`, `employee_outbox`, `approval_outbox`, and so on. Each has its own index, its own worker goroutine, and its own throughput characteristics.

```
SINGLE OUTBOX vs PER-AGGREGATE OUTBOX
────────────────────────────────────────

SINGLE OUTBOX (Simple but becomes a bottleneck):
──────────────────────────────────────────────────
  All events ──► outbox_events table ──► One worker ──► Kafka
                 (all aggregates mixed)   (single
                                          goroutine)


PER-AGGREGATE OUTBOX (Scalable):
──────────────────────────────────
  Leave events   ──► leave_outbox   ──► Leave Worker   ──► kafka: leave.events
  Employee events──► employee_outbox──► Employee Worker──► kafka: employee.events
  Approval events──► approval_outbox──► Approval Worker──► kafka: approval.events

  Each table has its own index.
  Each worker has its own goroutine and poll interval.
  High-volume aggregates can have shorter poll intervals.
  Low-volume aggregates can have longer ones.
```

In Go, you parameterize the worker by table name, which means one `Worker` implementation can serve all aggregate tables:

```go
func NewWorkerForAggregate(db *gorm.DB, writer KafkaWriter, tableName string) *Worker {
    return &Worker{
        db:           db,
        kafkaWriter:  writer,
        tableName:    tableName,
        pollInterval: 100 * time.Millisecond,
        batchSize:    100,
    }
}

func (w *Worker) processBatch(ctx context.Context) error {
    var events []OutboxEvent

    // Query the specific aggregate's table
    result := w.db.WithContext(ctx).
        Table(w.tableName).
        Where("published = ?", false).
        Order("created_at ASC").
        Limit(w.batchSize).
        Find(&events)

    // ... rest of processing
}

// In main.go — spawn one worker per aggregate
leaveWorker    := outbox.NewWorkerForAggregate(db, writer, "leave_outbox")
employeeWorker := outbox.NewWorkerForAggregate(db, writer, "employee_outbox")
approvalWorker := outbox.NewWorkerForAggregate(db, writer, "approval_outbox")

g.Go(func() error { return leaveWorker.Run(ctx) })
g.Go(func() error { return employeeWorker.Run(ctx) })
g.Go(func() error { return approvalWorker.Run(ctx) })
```

## Outbox Variant 4 — Distributed Lock for Multi-Instance Workers

There is one more problem you will run into when your service scales horizontally. If you have three instances of the Leave Service running (which you should in production for high availability), each instance has its own outbox worker goroutine. All three workers are polling the same outbox table, and all three will try to publish the same events — causing duplicates in Kafka.

```
THE MULTI-INSTANCE PROBLEM
────────────────────────────

  Leave Service Instance 1 ──► Outbox Worker A ──┐
  Leave Service Instance 2 ──► Outbox Worker B ──┼──► All three query the SAME
  Leave Service Instance 3 ──► Outbox Worker C ──┘     outbox table
                                                         │
                                                         ▼
                                               All three find the same
                                               unpublished rows
                                               All three publish to Kafka
                                               ► TRIPLICATE EVENTS ← BUG!
```

There are two clean solutions to this.

The first solution is optimistic locking with `SELECT FOR UPDATE SKIP LOCKED`. This is a PostgreSQL feature that lets each worker claim a batch of rows exclusively. When Worker A locks a batch of rows, Workers B and C will skip those rows entirely and only pick up other unlocked rows. This works well when you actually want multiple workers to process different batches concurrently.

```go
func (w *Worker) processBatch(ctx context.Context) error {
    var events []OutboxEvent

    // SELECT FOR UPDATE SKIP LOCKED — each worker gets exclusive rows
    result := w.db.WithContext(ctx).
        Where("published = ?", false).
        Order("created_at ASC").
        Limit(w.batchSize).
        Set("gorm:query_option", "FOR UPDATE SKIP LOCKED").
        Find(&events)

    // Now only this worker instance processes these specific rows
    // Other instances will skip these locked rows
    // ...
}
```

The second solution is using Redis distributed locks — which fits perfectly in our stack since we already use Redis. Only the instance that holds the lock runs the outbox worker. The other instances stand by as hot standby workers, ready to acquire the lock if the primary fails.

```go
// outbox/distributed_worker.go

type DistributedWorker struct {
    Worker
    redisClient  *redis.Client
    lockKey      string
    lockDuration time.Duration
}

func (w *DistributedWorker) Run(ctx context.Context) error {
    ticker := time.NewTicker(w.pollInterval)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            // Try to acquire the distributed lock
            acquired, err := w.redisClient.SetNX(ctx,
                w.lockKey,
                w.instanceID,       // store instance ID as lock value
                w.lockDuration,     // e.g. 5 seconds
            ).Result()

            if err != nil || !acquired {
                // Another instance holds the lock — skip this tick
                continue
            }

            // We have the lock — process the batch
            if err := w.processBatch(ctx); err != nil {
                w.logger.Error("batch failed", "error", err)
            }

            // Release the lock (only if we still own it)
            script := redis.NewScript(`
                if redis.call("get", KEYS[1]) == ARGV[1] then
                    return redis.call("del", KEYS[1])
                else
                    return 0
                end
            `)
            script.Run(ctx, w.redisClient, []string{w.lockKey}, w.instanceID)
        }
    }
}
```

```
DISTRIBUTED LOCK — Multi-Instance Worker Behavior
────────────────────────────────────────────────────

  Instance 1 ──► tries Redis SETNX "outbox_lock" ──► ACQUIRED ✓
               ──► processes batch
               ──► releases lock

  Instance 2 ──► tries Redis SETNX "outbox_lock" ──► FAILED (key exists)
               ──► skips this tick

  Instance 3 ──► tries Redis SETNX "outbox_lock" ──► FAILED (key exists)
               ──► skips this tick

  If Instance 1 crashes without releasing lock:
               ──► lock expires after 5 seconds (TTL)
               ──► Instance 2 acquires lock on next tick
               ──► Processing continues with no manual intervention
```

## Outbox Cleanup — The Part Everyone Forgets

Once events are published, their rows in the outbox table serve no further operational purpose. But they accumulate. In a busy system, you might insert thousands of rows per minute. Left uncleaned, the outbox table grows to tens of millions of rows, the index degrades, and query performance drops even with the partial index on unpublished events.

You need a cleanup job that periodically deletes rows that were published more than some retention window ago — say, 7 days. This retention window is not zero because you might want to inspect recent events for debugging, and because published events become evidence in your audit trail.

```go
// outbox/cleanup.go

type CleanupWorker struct {
    db              *gorm.DB
    retention       time.Duration  // e.g. 7 days
    cleanupInterval time.Duration  // e.g. 1 hour
    batchSize       int
}

func (c *CleanupWorker) Run(ctx context.Context) error {
    ticker := time.NewTicker(c.cleanupInterval)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            cutoff := time.Now().Add(-c.retention)

            result := c.db.WithContext(ctx).
                Where("published = ? AND published_at < ?", true, cutoff).
                Limit(c.batchSize).  // delete in batches to avoid locking the table
                Delete(&OutboxEvent{})

            if result.Error != nil {
                log.Printf("outbox cleanup error: %v", result.Error)
                continue
            }

            if result.RowsAffected > 0 {
                log.Printf("outbox cleanup: deleted %d published events", result.RowsAffected)
            }
        }
    }
}
```

## The Outbox Pattern and Idempotency Are Two Sides of the Same Coin

There is a relationship between the Outbox Pattern and idempotency that is worth making explicit, because understanding it will save you from nasty bugs.

The Outbox Pattern guarantees at-least-once delivery — an event will always be published, but might be published more than once in crash-and-retry scenarios. This is a deliberate trade-off: exactly-once delivery would require a distributed transaction across the database and Kafka, which is the very problem we are trying to avoid.

The outbox worker publishes the event to Kafka and marks it as published. The publish to Kafka and the mark-as-published are two separate operations. If the worker crashes between them, it will republish the event on restart. This means downstream consumers will receive the same event twice.

```
WHY IDEMPOTENCY IS REQUIRED
─────────────────────────────

Outbox Worker:
  1. Read leave_outbox: "LeaveCreated L001"
  2. Publish to Kafka ──► sent ✓
  3. ⚡ WORKER CRASHES before UPDATE published=true ⚡

Worker restarts:
  1. Read leave_outbox: "LeaveCreated L001" (published still false)
  2. Publish to Kafka ──► sent again (duplicate!) ✓
  3. UPDATE published=true ✓

Balance Service Consumer:
  Round 1: Receives "LeaveCreated L001" ──► deducts 3 days ✓
  Round 2: Receives "LeaveCreated L001" ──► deducts 3 days AGAIN ← BUG if not idempotent!

  WITH IDEMPOTENCY:
  Round 2: Checks processed_events for outbox-event-id
           Already processed ──► skips silently ✓
```

Every consumer of events produced by the Outbox Pattern must check the `outbox-event-id` header (which we set in the Kafka message headers) against a `processed_events` table before doing any work. This check should be inside the same database transaction as the work itself, so that the "mark as processed" step is atomic with the business operation.

## When to Use Polling vs CDC — A Practical Guide

You now know two ways to implement the Outbox Pattern: polling and CDC. Here is the practical guide for which to use in our project at different stages.

During local development and early iterations, use the polling approach. It requires no extra infrastructure — just a goroutine and a database table. You can get it running in an afternoon. The 100ms latency is completely acceptable for development, and the simplicity makes debugging easy.

When your system handles more than a few hundred events per second, or when you have more than five services all polling their outbox tables, the cumulative database load from constant SELECT queries becomes measurable. This is when you should introduce Debezium. Add it to your Docker Compose setup, configure one connector per service database, and gradually migrate services from polling to CDC. The application code does not change — only the relay mechanism.

```
DECISION GUIDE
────────────────────────────────────────────────────────────────────────
Stage                         Recommended Approach
────────────────────────────────────────────────────────────────────────
Development / early prod      Polling Worker (simple, fast to set up)
> 5 services, moderate load   Polling Worker with per-aggregate tables
High throughput, > 500 eps    CDC with Debezium
Multi-region / compliance     CDC with Debezium (WAL is also an audit trail)
────────────────────────────────────────────────────────────────────────
```

The important thing to understand is that the choice between polling and CDC is an operational decision, not an architectural one. The application-level code — the service writing to the outbox table in a transaction — is identical in both cases. You can start with polling and migrate to CDC later without changing a single line of business logic.

## What the Outbox Pattern Does Not Solve

The Outbox Pattern solves one specific problem with precision: it guarantees that a database write and a Kafka publish either both happen or neither happens, in a crash-safe way. But it is worth being clear about what it does not do.

It does not guarantee ordering across different services. If two different services both publish events that should be consumed in a specific order, the Outbox Pattern alone cannot enforce that order across service boundaries. Kafka partition ordering within a single aggregate ID is the mechanism for that, and you must design your aggregate keys thoughtfully.

It does not replace a dead-letter strategy. Events with permanent failures — invalid payloads, consumers with bugs that always throw exceptions — will hit their retry limit and sit in the outbox table. You need monitoring and alerting on rows where `retry_count >= 5` and `published = false`. These need human attention.

It does not eliminate the need for idempotency in consumers. As explained above, at-least-once delivery is a fundamental property of the pattern. Every consumer must be written to handle duplicates gracefully.

What the Outbox Pattern does is give you a solid, reliable foundation that you can build everything else on top of. The SAGA pattern depends on it. Your event-driven workflows depend on it. Any time your service needs to change its own data and tell the world about that change, the Outbox Pattern is the correct mechanism. It is not optional infrastructure — in a distributed system, it is the minimum bar for correctness.
