# The Dead Letter Queue Pattern in Microservices

### Everything You Need to Know — Explained Like You Just Joined the Team

---

## A Story From the Post Office

Imagine you work at a post office. Every day, thousands of letters arrive to be delivered. Most of them have clear addresses and go out to their destinations without any issue. But occasionally, a letter arrives with a smudged address that cannot be read. Or the addressee has moved and left no forwarding address. Or the envelope is torn and the contents are damaged. Or the address points to a building that was demolished three years ago.

What do you do with these letters? You cannot deliver them. You cannot throw them away — there is important content inside and the sender is expecting delivery. You cannot just leave them sitting on the sorting table forever, blocking the processing of all the normal letters behind them.

So the post office puts them in a special bin — the dead letter bin. Letters in this bin are set aside so that normal mail processing continues uninterrupted. Periodically, a clerk goes through the dead letter bin, examines each letter carefully, and tries to figure out what went wrong. Sometimes the address can be corrected and the letter redelivered. Sometimes the sender needs to be notified. Sometimes the letter is genuinely undeliverable and gets returned to sender.

The Dead Letter Queue pattern in software is this exact mechanism. It is a holding area for messages that could not be processed successfully — not thrown away, not blocking the main processing pipeline, but safely stored aside for investigation and potential recovery.

---

## The Problem That Makes Dead Letter Queues Necessary

To understand why a Dead Letter Queue is essential, you first need to understand what happens without one when a message cannot be processed.

In our leave management system, the Balance Service consumes messages from the `leave.events` Kafka topic. When it receives a `LeaveSubmitted` event, it deducts leave days from the employee's balance. Now imagine these three scenarios.

Scenario one: a `LeaveSubmitted` event arrives with a malformed payload — some upstream bug caused the JSON to be truncated. The Balance Service cannot deserialize it. It returns an error.

Scenario two: a `LeaveSubmitted` event arrives for employee ID `EMP-999`, but that employee does not exist in the Balance Service's database because the Employee Service had a data migration failure. The Balance Service cannot process it. It returns an error.

Scenario three: a `LeaveSubmitted` event arrives correctly, but at the exact moment of processing, the database is temporarily unavailable due to a brief network partition. The Balance Service fails to write. It returns an error.

These three scenarios look similar on the surface — they all produce an error — but they have fundamentally different natures. Scenario three is a transient failure that will succeed on retry a few seconds later. Scenarios one and two are permanent failures that will never succeed no matter how many times you retry them. A malformed payload does not fix itself. A missing employee record does not appear by itself.

```
THE RETRY TRAP — Without a Dead Letter Queue
──────────────────────────────────────────────

  Kafka partition 0, leave.events topic:
  ┌────────────────────────────────────────────────────┐
  │  offset 100: LeaveSubmitted (emp: EMP-001) ← good  │
  │  offset 101: LeaveSubmitted (BAD JSON)     ← poison│
  │  offset 102: LeaveSubmitted (emp: EMP-002) ← good  │
  │  offset 103: LeaveSubmitted (emp: EMP-003) ← good  │
  └────────────────────────────────────────────────────┘

  Consumer processes offset 100: ✓ success, commits offset 100
  Consumer processes offset 101: ✗ FAILS (bad JSON)

  Without DLQ — what happens next?
  ┌──────────────────────────────────────────────────────────┐
  │  Option A: Retry forever                                 │
  │  ─────────────────────────────────────────────────────   │
  │  offset 101 retried: ✗ fail                              │
  │  offset 101 retried: ✗ fail                              │
  │  offset 101 retried: ✗ fail (forever)                    │
  │  offset 102, 103, 104... NEVER PROCESSED                 │
  │  The bad message is a permanent roadblock.               │
  │  This is called the "poison pill" problem.               │
  │                                                          │
  │  Option B: Skip and commit offset                        │
  │  ─────────────────────────────────────────────────────   │
  │  offset 101 skipped: offset committed                    │
  │  Message silently lost. No record. No alert.             │
  │  Business data permanently gone.                         │
  │  ← ALSO UNACCEPTABLE                                     │
  └──────────────────────────────────────────────────────────┘

  Both options are bad. The Dead Letter Queue is the correct answer.
```

The Dead Letter Queue breaks this false dilemma. When a message cannot be processed after a configured number of retries, it is moved to a separate DLQ topic with full metadata about why it failed. The original topic's consumer commits the offset and moves on. Normal processing continues. The failed message sits in the DLQ, safely preserved, waiting for a human to investigate or an automated recovery process to replay it after the root cause is fixed.

## What a Dead Letter Queue Actually Is in Kafka

In a Kafka-based system, a Dead Letter Queue is just another Kafka topic — typically named with a `.dlq` or `.dead-letter` suffix. When a consumer fails to process a message after exhausting its retry budget, it publishes that message to the DLQ topic with enriched metadata, then commits the original offset and continues processing the next message.

```
DEAD LETTER QUEUE — Core Architecture
───────────────────────────────────────

  leave.events topic (main topic)
  ┌────────────────────────────────────────────┐
  │  offset 100: LeaveSubmitted (EMP-001)  ✓   │
  │  offset 101: LeaveSubmitted (BAD JSON) ✗✗✗│──► after N retries ──►
  │  offset 102: LeaveSubmitted (EMP-002)  ✓   │                        │
  │  offset 103: LeaveSubmitted (EMP-003)  ✓   │                        │
  └────────────────────────────────────────────┘                        │
                                                                        │
                                               leave.events.dlq topic   │
                                               ┌─────────────────────┐  │
                                               │  Original message   │◄─┘
                                               │  Failure reason     │
                                               │  Retry count        │
                                               │  Service name       │
                                               │  First failed at    │
                                               │  Last failed at     │
                                               │  Stack trace        │
                                               └─────────────────────┘
                                                          │
                                               ┌──────────┴──────────┐
                                               │                     │
                                          DLQ Monitor            DLQ Replayer
                                          (alerts on-call)       (manual/auto
                                                                   after fix)
```

The key properties of a well-designed DLQ are that it is durable — messages in the DLQ are retained for a long time (days or weeks) so they can be investigated and replayed. It is enriched — every message in the DLQ carries complete metadata about what failed, why, and how many times it was tried. It is observable — monitoring systems watch the DLQ and alert when messages start accumulating. And it is replayable — once the root cause is fixed, messages can be replayed from the DLQ back into the original topic for reprocessing.

## The DLQ Message Envelope

Every message that enters a DLQ should be wrapped in an envelope that carries both the original message and the failure metadata. This envelope is what makes DLQs useful for diagnosis and replay.

```go
// dlq/envelope.go

package dlq

type DLQEnvelope struct {
    // Original message, preserved exactly as received
    OriginalTopic     string            `json:"original_topic"`
    OriginalPartition int32             `json:"original_partition"`
    OriginalOffset    int64             `json:"original_offset"`
    OriginalKey       []byte            `json:"original_key"`
    OriginalPayload   json.RawMessage   `json:"original_payload"`
    OriginalHeaders   map[string]string `json:"original_headers"`

    // Failure information
    ServiceName       string    `json:"service_name"`        // which service failed
    HandlerName       string    `json:"handler_name"`        // which handler failed
    ErrorType         string    `json:"error_type"`          // "deserialization", "business", "infrastructure"
    ErrorMessage      string    `json:"error_message"`       // human-readable error
    StackTrace        string    `json:"stack_trace"`         // full Go stack trace
    RetryCount        int       `json:"retry_count"`         // how many times we tried
    FirstFailedAt     time.Time `json:"first_failed_at"`     // when it first failed
    LastFailedAt      time.Time `json:"last_failed_at"`      // when it last failed
    DLQVersion        int       `json:"dlq_version"`         // schema version of this envelope

    // Replay metadata (filled in when/if the message is replayed)
    ReplayedAt        *time.Time `json:"replayed_at,omitempty"`
    ReplayedBy        string     `json:"replayed_by,omitempty"`  // "auto" or operator email
    ReplayDestination string     `json:"replay_destination,omitempty"`
}

// ErrorType constants — critical for routing and monitoring
const (
    ErrorTypeDeserialization = "deserialization"  // bad JSON, wrong schema
    ErrorTypeBusiness        = "business"          // missing entity, invalid state
    ErrorTypeInfrastructure  = "infrastructure"    // DB down, network timeout
    ErrorTypeValidation      = "validation"        // message violates business rules
)
```

The `ErrorType` field deserves emphasis. Different error types should be handled differently. Infrastructure errors (database temporarily down) suggest you should replay the message soon and it will likely succeed. Deserialization errors (bad JSON) mean the message can never be processed until the consumer code is fixed — replay will not help until a code deploy happens. Business errors (missing employee) mean you need to investigate whether the missing record will be created through some other flow, or whether there is a data consistency problem. Categorizing errors correctly at the point of DLQ entry is what makes the DLQ useful for triage rather than just a black hole.

## Implementation — Part 1: The Retry-Then-DLQ Consumer

The foundation of the DLQ pattern is the consumer wrapper that handles retries with exponential backoff and, after exhausting the retry budget, publishes to the DLQ. This wrapper sits around your business handler and is reusable across all consumers in the system.

```go
// dlq/consumer_wrapper.go

package dlq

import (
    "context"
    "encoding/json"
    "fmt"
    "math"
    "runtime/debug"
    "time"

    "github.com/segmentio/kafka-go"
)

type ConsumerConfig struct {
    ServiceName   string
    HandlerName   string
    MaxRetries    int           // e.g. 5
    BaseDelay     time.Duration // e.g. 100ms
    MaxDelay      time.Duration // e.g. 30s
    DLQTopic      string        // e.g. "leave.events.dlq"
}

type Handler func(ctx context.Context, msg kafka.Message) error

type DLQConsumerWrapper struct {
    config    ConsumerConfig
    dlqWriter *kafka.Writer
    logger    *slog.Logger
}

func NewDLQConsumerWrapper(config ConsumerConfig, dlqWriter *kafka.Writer, logger *slog.Logger) *DLQConsumerWrapper {
    return &DLQConsumerWrapper{
        config:    config,
        dlqWriter: dlqWriter,
        logger:    logger,
    }
}

// Wrap takes your business handler and returns a resilient handler with retry + DLQ
func (w *DLQConsumerWrapper) Wrap(handler Handler) Handler {
    return func(ctx context.Context, msg kafka.Message) error {
        var lastErr error
        firstFailedAt := time.Time{}

        for attempt := 0; attempt <= w.config.MaxRetries; attempt++ {
            if attempt > 0 {
                // Exponential backoff with jitter between retries
                delay := w.calculateBackoff(attempt)
                w.logger.Info("retrying message",
                    "attempt", attempt,
                    "delay", delay,
                    "topic", msg.Topic,
                    "offset", msg.Offset,
                )
                select {
                case <-time.After(delay):
                case <-ctx.Done():
                    return ctx.Err()
                }
            }

            err := w.safeExecute(ctx, handler, msg)
            if err == nil {
                return nil // success
            }

            if attempt == 0 {
                firstFailedAt = time.Now()
            }

            lastErr = err
            w.logger.Warn("message processing failed",
                "attempt", attempt+1,
                "max_retries", w.config.MaxRetries,
                "error", err,
                "topic", msg.Topic,
                "offset", msg.Offset,
            )

            // Do not retry deserialization errors — they will never succeed
            if isDeserializationError(err) {
                w.logger.Error("deserialization error — skipping retries, sending to DLQ immediately",
                    "error", err,
                )
                break
            }
        }

        // Retry budget exhausted — send to DLQ
        w.logger.Error("message exceeded retry budget, sending to DLQ",
            "topic", msg.Topic,
            "offset", msg.Offset,
            "total_attempts", w.config.MaxRetries+1,
            "last_error", lastErr,
        )

        return w.sendToDLQ(ctx, msg, lastErr, firstFailedAt)
    }
}

// safeExecute runs the handler and catches panics
func (w *DLQConsumerWrapper) safeExecute(ctx context.Context, handler Handler, msg kafka.Message) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v\nstack: %s", r, debug.Stack())
        }
    }()
    return handler(ctx, msg)
}

func (w *DLQConsumerWrapper) calculateBackoff(attempt int) time.Duration {
    // Exponential backoff: base * 2^attempt, capped at maxDelay, with ±25% jitter
    delay := float64(w.config.BaseDelay) * math.Pow(2, float64(attempt-1))
    if delay > float64(w.config.MaxDelay) {
        delay = float64(w.config.MaxDelay)
    }
    jitter := delay * 0.25 * (rand.Float64()*2 - 1) // ±25%
    return time.Duration(delay + jitter)
}

func (w *DLQConsumerWrapper) sendToDLQ(ctx context.Context, msg kafka.Message, lastErr error, firstFailedAt time.Time) error {
    errorType := classifyError(lastErr)

    envelope := DLQEnvelope{
        OriginalTopic:     msg.Topic,
        OriginalPartition: msg.Partition,
        OriginalOffset:    msg.Offset,
        OriginalKey:       msg.Key,
        OriginalPayload:   json.RawMessage(msg.Value),
        OriginalHeaders:   headersToMap(msg.Headers),
        ServiceName:       w.config.ServiceName,
        HandlerName:       w.config.HandlerName,
        ErrorType:         errorType,
        ErrorMessage:      lastErr.Error(),
        StackTrace:        string(debug.Stack()),
        RetryCount:        w.config.MaxRetries,
        FirstFailedAt:     firstFailedAt,
        LastFailedAt:      time.Now(),
        DLQVersion:        1,
    }

    envelopeBytes, err := json.Marshal(envelope)
    if err != nil {
        return fmt.Errorf("failed to marshal DLQ envelope: %w", err)
    }

    dlqMsg := kafka.Message{
        Topic: w.config.DLQTopic,
        Key:   msg.Key, // preserve original key for ordering
        Value: envelopeBytes,
        Headers: []kafka.Header{
            {Key: "dlq-error-type",  Value: []byte(errorType)},
            {Key: "dlq-service",     Value: []byte(w.config.ServiceName)},
            {Key: "dlq-handler",     Value: []byte(w.config.HandlerName)},
            {Key: "original-topic",  Value: []byte(msg.Topic)},
            {Key: "original-offset", Value: []byte(fmt.Sprintf("%d", msg.Offset))},
        },
    }

    if err := w.dlqWriter.WriteMessages(ctx, dlqMsg); err != nil {
        // This is a serious failure: the message could not be processed
        // AND we could not write it to the DLQ. Log with maximum severity.
        w.logger.Error("CRITICAL: failed to write to DLQ — message will be lost",
            "dlq_topic", w.config.DLQTopic,
            "original_topic", msg.Topic,
            "original_offset", msg.Offset,
            "error", err,
        )
        return fmt.Errorf("DLQ write failed: %w", err)
    }

    w.logger.Info("message successfully sent to DLQ",
        "dlq_topic", w.config.DLQTopic,
        "original_topic", msg.Topic,
        "original_offset", msg.Offset,
        "error_type", errorType,
    )

    return nil  // return nil so the main consumer commits the offset and moves on
}

func classifyError(err error) string {
    if err == nil {
        return ""
    }

    var deserErr *DeserializationError
    if errors.As(err, &deserErr) {
        return ErrorTypeDeserialization
    }

    var bizErr *BusinessError
    if errors.As(err, &bizErr) {
        return ErrorTypeBusiness
    }

    // Default: treat as infrastructure error (DB down, network, etc.)
    return ErrorTypeInfrastructure
}

func headersToMap(headers []kafka.Header) map[string]string {
    m := make(map[string]string, len(headers))
    for _, h := range headers {
        m[h.Key] = string(h.Value)
    }
    return m
}
```

Now here is how you wire this wrapper into the actual Balance Service consumer. The business handler is completely unaware of retries or the DLQ — that is handled transparently by the wrapper:

```go
// balance/consumer.go

func SetupBalanceConsumer(db *gorm.DB, kafkaReader *kafka.Reader, dlqWriter *kafka.Writer) {
    logger := slog.Default()

    wrapper := dlq.NewDLQConsumerWrapper(dlq.ConsumerConfig{
        ServiceName: "balance-service",
        HandlerName: "HandleLeaveSubmitted",
        MaxRetries:  5,
        BaseDelay:   100 * time.Millisecond,
        MaxDelay:    30 * time.Second,
        DLQTopic:    "leave.events.dlq",
    }, dlqWriter, logger)

    // The pure business handler — knows nothing about retries or DLQ
    businessHandler := func(ctx context.Context, msg kafka.Message) error {
        var event LeaveSubmittedEvent
        if err := json.Unmarshal(msg.Value, &event); err != nil {
            // Wrap as DeserializationError so the wrapper knows not to retry
            return &dlq.DeserializationError{
                Cause:   err,
                Payload: string(msg.Value),
            }
        }

        return db.Transaction(func(tx *gorm.DB) error {
            var balance EmployeeLeaveBalance
            if err := tx.Where("employee_id = ?", event.EmployeeID).First(&balance).Error; err != nil {
                if errors.Is(err, gorm.ErrRecordNotFound) {
                    // Wrap as BusinessError — retrying will not help
                    return &dlq.BusinessError{
                        Code:    "EMPLOYEE_NOT_FOUND",
                        Message: fmt.Sprintf("employee %s has no balance record", event.EmployeeID),
                    }
                }
                // Any other DB error is an infrastructure error — retry will help
                return err
            }

            if balance.AvailableDays < event.Days {
                return &dlq.BusinessError{
                    Code:    "INSUFFICIENT_BALANCE",
                    Message: fmt.Sprintf("need %d days, have %d", event.Days, balance.AvailableDays),
                }
            }

            balance.AvailableDays -= event.Days
            return tx.Save(&balance).Error
        })
    }

    // Wrap the business handler with retry + DLQ protection
    resilientHandler := wrapper.Wrap(businessHandler)

    // Main consume loop
    for {
        msg, err := kafkaReader.FetchMessage(context.Background())
        if err != nil {
            logger.Error("failed to fetch message", "error", err)
            continue
        }

        if err := resilientHandler(context.Background(), msg); err != nil {
            // Even DLQ write failed — log at maximum severity but keep going
            logger.Error("CRITICAL: resilient handler failed", "error", err)
        }

        // Commit offset regardless — message is either processed or in DLQ
        kafkaReader.CommitMessages(context.Background(), msg)
    }
}
```

## The DLQ Monitoring Service

A DLQ without monitoring is not much better than silently dropping messages. Messages accumulate in the DLQ and nobody knows. The root cause never gets fixed. Eventually the DLQ is hundreds of thousands of messages deep and nobody knows where to start.

The DLQ Monitor is a background service that continuously watches DLQ topics, tracks accumulation rates, classifies the errors it sees, and alerts the on-call team when action is needed.

```go
// dlq/monitor.go

package dlq

type DLQMonitor struct {
    db           *gorm.DB          // stores DLQ statistics
    reader       *kafka.Reader     // reads from DLQ topic
    alerter      Alerter           // sends Slack/PagerDuty alerts
    metrics      *DLQMetrics       // OpenTelemetry metrics
    alertThreshold int             // alert if DLQ grows by this many messages per hour
    logger       *slog.Logger
}

// DLQRecord stores a record of every DLQ message for reporting and replay
type DLQRecord struct {
    gorm.Model
    MessageID         string    `gorm:"uniqueIndex"`
    OriginalTopic     string    `gorm:"not null;index"`
    OriginalPartition int32
    OriginalOffset    int64
    ServiceName       string    `gorm:"not null;index"`
    HandlerName       string    `gorm:"not null"`
    ErrorType         string    `gorm:"not null;index"`
    ErrorMessage      string    `gorm:"type:text"`
    RetryCount        int
    FirstFailedAt     time.Time
    LastFailedAt      time.Time `gorm:"index"`
    Status            string    `gorm:"not null;default:'PENDING';index"` // PENDING, REPLAYED, DISCARDED
    ReplayedAt        *time.Time
    ReplayedBy        string
    RawEnvelope       datatypes.JSON `gorm:"type:jsonb"`
}

func (m *DLQMonitor) Run(ctx context.Context) error {
    m.logger.Info("DLQ monitor started")

    for {
        msg, err := m.reader.FetchMessage(ctx)
        if err != nil {
            if errors.Is(err, context.Canceled) {
                return nil
            }
            m.logger.Error("DLQ monitor fetch failed", "error", err)
            continue
        }

        if err := m.processMessage(ctx, msg); err != nil {
            m.logger.Error("DLQ monitor process failed", "error", err)
        }

        m.reader.CommitMessages(ctx, msg)
    }
}

func (m *DLQMonitor) processMessage(ctx context.Context, msg kafka.Message) error {
    var envelope DLQEnvelope
    if err := json.Unmarshal(msg.Value, &envelope); err != nil {
        m.logger.Error("failed to unmarshal DLQ envelope", "error", err)
        return nil // skip malformed DLQ messages
    }

    // Store in database for replay and reporting
    record := &DLQRecord{
        MessageID:         fmt.Sprintf("%s-%d-%d", envelope.OriginalTopic, envelope.OriginalPartition, envelope.OriginalOffset),
        OriginalTopic:     envelope.OriginalTopic,
        OriginalPartition: envelope.OriginalPartition,
        OriginalOffset:    envelope.OriginalOffset,
        ServiceName:       envelope.ServiceName,
        HandlerName:       envelope.HandlerName,
        ErrorType:         envelope.ErrorType,
        ErrorMessage:      envelope.ErrorMessage,
        RetryCount:        envelope.RetryCount,
        FirstFailedAt:     envelope.FirstFailedAt,
        LastFailedAt:      envelope.LastFailedAt,
        Status:            "PENDING",
        RawEnvelope:       msg.Value,
    }

    result := m.db.Clauses(clause.OnConflict{
        Columns:   []clause.Column{{Name: "message_id"}},
        DoNothing: true,
    }).Create(record)
    if result.Error != nil {
        return result.Error
    }

    // Emit metrics for Grafana
    m.metrics.DLQMessageReceived(envelope.ServiceName, envelope.ErrorType)

    // Check if we should alert
    m.checkAlertThreshold(ctx, envelope)

    return nil
}

func (m *DLQMonitor) checkAlertThreshold(ctx context.Context, envelope DLQEnvelope) {
    // Count messages from this service in the last hour
    var count int64
    m.db.Model(&DLQRecord{}).
        Where("service_name = ? AND created_at > ?", envelope.ServiceName, time.Now().Add(-1*time.Hour)).
        Count(&count)

    if count >= int64(m.alertThreshold) {
        m.alerter.Alert(AlertMessage{
            Severity: SeverityHigh,
            Title:    fmt.Sprintf("DLQ ALERT: %s has %d failed messages in the last hour", envelope.ServiceName, count),
            Details:  fmt.Sprintf("Error type: %s\nLast error: %s\nHandler: %s\nOriginal topic: %s",
                envelope.ErrorType, envelope.ErrorMessage, envelope.HandlerName, envelope.OriginalTopic),
            Links: map[string]string{
                "Grafana DLQ Dashboard": "https://grafana.internal/d/dlq-dashboard",
                "Replay API":           "https://api.internal/dlq/replay",
            },
        })
    }
}
```

## The DLQ Replayer — Getting Messages Back Into Processing

After an engineer has investigated the root cause and fixed the underlying problem — redeployed the consumer with better deserialization logic, or created the missing employee record, or resolved the database issue — the messages sitting in the DLQ need to be replayed. The replayer reads from the DLQ database, extracts the original payload, and writes it back to the original Kafka topic.

```go
// dlq/replayer.go

package dlq

type ReplayRequest struct {
    ServiceName   string     `json:"service_name"`
    ErrorType     string     `json:"error_type"`  // replay all of this error type
    MessageIDs    []string   `json:"message_ids"` // or replay specific messages by ID
    DryRun        bool       `json:"dry_run"`     // if true, show what would be replayed without doing it
    ReplayedBy    string     `json:"replayed_by"` // operator email
}

type ReplayResult struct {
    Total     int `json:"total"`
    Replayed  int `json:"replayed"`
    Skipped   int `json:"skipped"`
    Failed    int `json:"failed"`
}

type DLQReplayer struct {
    db           *gorm.DB
    kafkaWriters map[string]*kafka.Writer // topic ──► writer
    logger       *slog.Logger
}

func (r *DLQReplayer) Replay(ctx context.Context, req ReplayRequest) (*ReplayResult, error) {
    query := r.db.Model(&DLQRecord{}).Where("status = ?", "PENDING")

    if req.ServiceName != "" {
        query = query.Where("service_name = ?", req.ServiceName)
    }
    if req.ErrorType != "" {
        query = query.Where("error_type = ?", req.ErrorType)
    }
    if len(req.MessageIDs) > 0 {
        query = query.Where("message_id IN ?", req.MessageIDs)
    }

    var records []DLQRecord
    if err := query.Find(&records).Error; err != nil {
        return nil, fmt.Errorf("failed to query DLQ records: %w", err)
    }

    result := &ReplayResult{Total: len(records)}

    r.logger.Info("starting DLQ replay",
        "total", result.Total,
        "dry_run", req.DryRun,
        "replayed_by", req.ReplayedBy,
    )

    for _, record := range records {
        if req.DryRun {
            r.logger.Info("DRY RUN: would replay",
                "message_id", record.MessageID,
                "original_topic", record.OriginalTopic,
                "error_type", record.ErrorType,
                "error", record.ErrorMessage,
            )
            result.Replayed++
            continue
        }

        if err := r.replayOne(ctx, record, req.ReplayedBy); err != nil {
            r.logger.Error("failed to replay message",
                "message_id", record.MessageID,
                "error", err,
            )
            result.Failed++
            continue
        }

        result.Replayed++
    }

    r.logger.Info("DLQ replay complete", "result", result)
    return result, nil
}

func (r *DLQReplayer) replayOne(ctx context.Context, record DLQRecord, replayedBy string) error {
    var envelope DLQEnvelope
    if err := json.Unmarshal(record.RawEnvelope, &envelope); err != nil {
        return fmt.Errorf("failed to unmarshal envelope: %w", err)
    }

    writer, ok := r.kafkaWriters[envelope.OriginalTopic]
    if !ok {
        return fmt.Errorf("no writer configured for topic: %s", envelope.OriginalTopic)
    }

    // Reconstruct the original message and add replay metadata in headers
    originalHeaders := make([]kafka.Header, 0)
    for k, v := range envelope.OriginalHeaders {
        originalHeaders = append(originalHeaders, kafka.Header{
            Key:   k,
            Value: []byte(v),
        })
    }

    // Add replay tracking headers
    originalHeaders = append(originalHeaders,
        kafka.Header{Key: "dlq-replayed",    Value: []byte("true")},
        kafka.Header{Key: "dlq-replayed-by", Value: []byte(replayedBy)},
        kafka.Header{Key: "dlq-replayed-at", Value: []byte(time.Now().Format(time.RFC3339))},
    )

    replayMsg := kafka.Message{
        Topic:   envelope.OriginalTopic,
        Key:     envelope.OriginalKey,
        Value:   envelope.OriginalPayload,  // original payload, unchanged
        Headers: originalHeaders,
    }

    if err := writer.WriteMessages(ctx, replayMsg); err != nil {
        return fmt.Errorf("failed to write replay message to Kafka: %w", err)
    }

    // Mark the DLQ record as replayed
    now := time.Now()
    return r.db.Model(&record).Updates(map[string]interface{}{
        "status":      "REPLAYED",
        "replayed_at": &now,
        "replayed_by": replayedBy,
    }).Error
}
```

## DLQ Variant 2 — Tiered DLQ With Auto-Retry Topics

In a high-throughput system, not every failure should go immediately to the main DLQ for manual investigation. Transient failures — brief database blips, temporary network issues — will usually resolve within seconds or minutes. You do not want an on-call alert for every ten-second database hiccup.

The tiered DLQ pattern creates a series of retry topics with increasing delays before the message reaches the final dead letter queue. This is sometimes called the "retry topic" pattern and is widely used in systems that use Kafka for messaging.

```
TIERED DLQ — Retry Topics With Increasing Delays
──────────────────────────────────────────────────

  leave.events (main topic, immediate processing)
         │
         │  FAIL (attempt 1)
         ▼
  leave.events.retry.1 (wait 30 seconds before re-consuming)
         │
         │  FAIL (attempt 2)
         ▼
  leave.events.retry.2 (wait 5 minutes before re-consuming)
         │
         │  FAIL (attempt 3)
         ▼
  leave.events.retry.3 (wait 30 minutes before re-consuming)
         │
         │  FAIL (attempt 4)
         ▼
  leave.events.dlq (final dead letter — manual intervention)

  At any tier: if processing SUCCEEDS, the message is done ✓
  The message only reaches the DLQ after failing at every tier.
```

The key mechanism is that each retry topic consumer checks the message's timestamp before processing it. If not enough time has passed since the message was last failed, the consumer pauses and waits before processing. The message stays in the Kafka topic (which has built-in durability) during the wait.

```go
// dlq/tiered_consumer.go

type RetryTier struct {
    Topic string
    Delay time.Duration
}

var RetryTiers = []RetryTier{
    {Topic: "leave.events.retry.1", Delay: 30 * time.Second},
    {Topic: "leave.events.retry.2", Delay: 5 * time.Minute},
    {Topic: "leave.events.retry.3", Delay: 30 * time.Minute},
}

type TieredRetryConsumer struct {
    currentTier  RetryTier
    nextTopic    string // next retry tier topic, or DLQ topic
    handler      Handler
    writer       *kafka.Writer
    logger       *slog.Logger
}

func (c *TieredRetryConsumer) ProcessMessage(ctx context.Context, msg kafka.Message) error {
    // Check when this message was last failed (stored in a header)
    lastFailedAt := extractTimeHeader(msg, "last-failed-at")

    if !lastFailedAt.IsZero() {
        waitUntil := lastFailedAt.Add(c.currentTier.Delay)
        if time.Now().Before(waitUntil) {
            remaining := time.Until(waitUntil)
            c.logger.Info("message not ready yet, waiting",
                "remaining", remaining,
            )
            // Pause this goroutine until the message is ready to process
            select {
            case <-time.After(remaining):
            case <-ctx.Done():
                return ctx.Err()
            }
        }
    }

    // Now try to process
    err := c.handler(ctx, msg)
    if err == nil {
        return nil // success — message done
    }

    c.logger.Warn("processing failed on retry tier",
        "tier", c.currentTier.Topic,
        "next", c.nextTopic,
        "error", err,
    )

    // Forward to next tier with updated metadata
    headers := msg.Headers
    headers = setHeader(headers, "last-failed-at", time.Now().Format(time.RFC3339))
    headers = setHeader(headers, "failed-on-tier", c.currentTier.Topic)

    return c.writer.WriteMessages(ctx, kafka.Message{
        Topic:   c.nextTopic,
        Key:     msg.Key,
        Value:   msg.Value,
        Headers: headers,
    })
}
```

```
TIERED DLQ — Example Timeline for a Transient DB Failure
──────────────────────────────────────────────────────────

  09:00:00  LeaveSubmitted message arrives on leave.events
            Balance Service DB is temporarily unavailable
            ──► FAIL, forward to leave.events.retry.1

  09:00:05  message arrives on leave.events.retry.1
            Delay: 30 seconds. Wait until 09:00:35.
            Balance Service DB is still recovering.
  09:00:35  Try processing: DB recovered ──► SUCCESS ✓
            Message never reached the DLQ.
            No alert needed. No manual intervention.

  Compare: without tiered DLQ
            After 5 retries (all within 5 seconds),
            message goes to DLQ, alert fires,
            on-call engineer woken up for a 30-second DB blip.
```

## DLQ Variant 3 — Per-Service DLQ Topics

In a system with twelve services, having one shared DLQ topic (`system.dlq`) seems simpler but creates problems at scale. Messages from all services are mixed together. Monitoring becomes noisy — a spike in Balance Service failures is hidden in the same stream as Notification Service failures. Replay logic must handle messages from many different services. Different teams cannot independently manage their own dead letters.

The clean solution is a dedicated DLQ topic per service. Each service owns its DLQ completely.

```
PER-SERVICE DLQ TOPICS
─────────────────────────

  leave.events ──────────────────────────────────────────► leave.events.dlq
                                                           (owned by Leave team)

  balance.events ─────────────────────────────────────────► balance.events.dlq
                                                             (owned by Balance team)

  employee.events ────────────────────────────────────────► employee.events.dlq
                                                             (owned by Employee team)

  approval.events ────────────────────────────────────────► approval.events.dlq
                                                             (owned by Approval team)

Benefits:
  ├── Each team monitors their own DLQ independently
  ├── Replay is scoped to one service — no risk of replaying wrong messages
  ├── Alert thresholds can be calibrated per service
  ├── Retention policies can differ per service
  └── DLQ topics can be on separate Kafka partitions for isolation
```

You can take this further and have per-event-type DLQ topics within a service, which makes automated replay logic even more precise:

```
LEAVE SERVICE — PER-EVENT-TYPE DLQ TOPICS
───────────────────────────────────────────

  leave.events topic contains multiple event types:
  ├── LeaveSubmitted  ──►  leave.LeaveSubmitted.dlq
  ├── LeaveApproved   ──►  leave.LeaveApproved.dlq
  ├── LeaveCancelled  ──►  leave.LeaveCancelled.dlq
  └── LeaveRejected   ──►  leave.LeaveRejected.dlq

  This lets you replay all "LeaveSubmitted" failures
  without touching "LeaveApproved" messages.
  Surgical precision in recovery.
```

## DLQ Variant 4 — Dead Letter Queue With the Transactional Inbox

When your consumer uses the Transactional Inbox Pattern (as we covered in the earlier guide), the DLQ lives inside your own database rather than as a separate Kafka topic. This is actually the natural and clean integration: the inbox table already tracks retry counts and error messages for each message. When a message exceeds its retry count, the inbox processor marks it as `DEAD_LETTERED` in the same database.

```go
// inbox/dead_letter_integration.go

// This extends the InboxProcessor from the Transactional Inbox guide

func (p *InboxProcessor) moveToDeadLetter(ctx context.Context, msg InboxMessage, lastErr error) error {
    errorType := dlq.ClassifyError(lastErr)

    return p.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // Create dead letter record in the same DB
        dlRecord := InboxDeadLetterRecord{
            OriginalMessageID: msg.MessageID,
            Topic:             msg.Topic,
            EventType:         msg.EventType,
            AggregateID:       msg.AggregateID,
            Payload:           msg.Payload,
            ServiceName:       p.serviceName,
            HandlerName:       p.handlerRegistry[msg.EventType],
            ErrorType:         errorType,
            LastErrorMessage:  lastErr.Error(),
            RetryCount:        msg.RetryCount,
            FirstFailedAt:     msg.ReceivedAt,
            LastFailedAt:      time.Now(),
            Status:            "PENDING_REVIEW",
        }

        if err := tx.Create(&dlRecord).Error; err != nil {
            return err
        }

        // Update inbox message status
        return tx.Model(&msg).Updates(map[string]interface{}{
            "status":     "DEAD_LETTERED",
            "last_error": lastErr.Error(),
        }).Error
    })
}
```

## The DLQ Admin HTTP API — Giving Operators Control

The DLQ is only useful if operators can interact with it easily. An admin HTTP API that exposes the DLQ database gives engineers a straightforward way to investigate, replay, and manage failed messages without direct database access.

```go
// dlq/admin_api.go

type DLQAdminAPI struct {
    db       *gorm.DB
    replayer *DLQReplayer
    logger   *slog.Logger
}

func (a *DLQAdminAPI) RegisterRoutes(mux *http.ServeMux) {
    mux.HandleFunc("GET /admin/dlq",              a.ListDeadLetters)
    mux.HandleFunc("GET /admin/dlq/{id}",         a.GetDeadLetter)
    mux.HandleFunc("POST /admin/dlq/replay",      a.ReplayMessages)
    mux.HandleFunc("POST /admin/dlq/{id}/replay", a.ReplayOne)
    mux.HandleFunc("POST /admin/dlq/{id}/discard",a.DiscardOne)
    mux.HandleFunc("GET /admin/dlq/stats",        a.Stats)
}

func (a *DLQAdminAPI) ListDeadLetters(w http.ResponseWriter, r *http.Request) {
    query := a.db.Model(&DLQRecord{}).Where("status = ?", "PENDING")

    // Support filtering by error type, service, date range
    if et := r.URL.Query().Get("error_type"); et != "" {
        query = query.Where("error_type = ?", et)
    }
    if svc := r.URL.Query().Get("service"); svc != "" {
        query = query.Where("service_name = ?", svc)
    }

    var records []DLQRecord
    query.Order("last_failed_at DESC").Limit(100).Find(&records)

    json.NewEncoder(w).Encode(records)
}

func (a *DLQAdminAPI) Stats(w http.ResponseWriter, r *http.Request) {
    type ServiceStats struct {
        ServiceName string `json:"service_name"`
        Pending     int64  `json:"pending"`
        ByErrorType map[string]int64 `json:"by_error_type"`
        OldestAt    time.Time        `json:"oldest_pending_at"`
    }

    var results []struct {
        ServiceName string
        ErrorType   string
        Count       int64
        OldestAt    time.Time
    }

    a.db.Model(&DLQRecord{}).
        Select("service_name, error_type, COUNT(*) as count, MIN(last_failed_at) as oldest_at").
        Where("status = ?", "PENDING").
        Group("service_name, error_type").
        Scan(&results)

    json.NewEncoder(w).Encode(results)
}
```

## What the DLQ Is and Is Not

The Dead Letter Queue is a safety net for production reliability, and it is worth being clear about its exact role so you do not either underuse it or misuse it.

The DLQ is not a substitute for proper error handling. If your consumer always fails for the same class of business error — say, employee not found — and you keep replaying those messages into the DLQ and then replaying them again, you are treating the symptom rather than the disease. The correct response is to investigate why the employee record is missing, fix the data consistency problem, and prevent the situation from recurring.

The DLQ is not a normal part of the processing path. Some engineers treat the DLQ as a second queue that the system eventually processes everything from. That is the wrong mental model. The DLQ should be close to empty most of the time. If it is consistently accumulating messages, something is structurally wrong and needs to be fixed, not managed.

The DLQ is not a substitute for the Transactional Inbox Pattern. The Inbox Pattern prevents messages from being lost between Kafka and your database. The DLQ handles messages that were received and stored correctly but could not be processed successfully. They solve different problems at different points in the pipeline and both are needed.

What the DLQ is, precisely, is a durable, observable, recoverable holding area for messages that the system cannot currently handle. It answers the fundamental question that every distributed messaging system must answer: what happens when a message cannot be processed? The answer is never "throw it away" and never "block forever." The answer is "store it safely, alert someone, and make recovery easy." That is the Dead Letter Queue pattern, and in a system with twelve services exchanging thousands of messages per second, having that answer ready is not optional. It is the foundation of operational confidence.
