# The CQRS Pattern in Microservices

### Everything You Need to Know — Explained Like You Just Joined the Team

---

## A Story From the Real World

Think about how a library works. There are two completely different kinds of interactions with a library. The first kind is when someone walks up to the librarian and says "I want to borrow this book" — and the librarian records the borrowing, updates the availability, and creates a transaction record. The second kind is when someone walks to the card catalog and says "show me all books about distributed systems written after 2020" — and they browse the catalog, which is organized completely differently from the actual books on the shelves, specifically to make searching fast.

Nobody would suggest that the librarian who processes transactions should also be the one answering catalog queries, and that all queries should go through the same checkout desk that handles borrowing and returning. That would create a bottleneck where someone trying to find a book has to wait behind someone returning a stack of textbooks.

The library naturally separates these two concerns. The checkout system handles mutations — borrows, returns, renewals. The card catalog handles queries — search, browse, filter. They are optimized differently because they have completely different requirements. The checkout system needs to be correct and consistent. The card catalog needs to be fast and filterable.

CQRS — Command Query Responsibility Segregation — is this exact principle applied to software systems.

---

## What Traditional Systems Do and Why It Becomes Painful

In every service we have built before learning CQRS, we follow a standard pattern. There is one data model, one database, and one service layer that handles everything — reads and writes alike. An employee submits a leave application: that is a write. A manager views all pending leaves sorted by department and date: that is a read. Both operations go through the same `LeaveService`, the same `Leave` GORM model, and the same `leaves` table.

This feels clean and simple when the system is small. But as the system grows, these two types of operations — writes and reads — develop increasingly different and often conflicting requirements. Writes need to be correct, transactional, and enforce business rules. Reads need to be fast, flexible, support multiple filter and sort combinations, handle aggregations across related tables, and serve different consumers that each want data shaped differently.

```
THE IMPEDANCE MISMATCH — One Model Trying to Do Everything
────────────────────────────────────────────────────────────

         leaves table (write-optimized, normalized)
         ┌──────────────────────────────────────────────┐
         │  id │ employee_id │ type │ days │ status │ ...│
         └──────────────────────────────────────────────┘

Write operations (simple, work well with normalized data):
  INSERT: Create a new leave ✓
  UPDATE: Approve a leave ✓
  UPDATE: Reject a leave ✓

Read operations (complex, fight against normalized data):
  ✗ "All pending leaves with employee name, department,
     team lead name, balance remaining, sorted by
     submission date, filtered by department"
  ← requires JOIN to employees, departments, balances,
    perhaps another JOIN to the org chart.
    Slow. Complex. Hard to index properly.

  ✗ "Dashboard: total leaves per type per department
     for the current month with approval rate"
  ← requires GROUP BY, COUNT, aggregations across
    multiple tables. Possibly millions of rows.
    Cannot use the same indexes as writes.

  ✗ "Manager view: all leave applications their direct
     reports have submitted, with current status, in
     the last 90 days, sorted by urgency"
  ← yet another completely different shape of the data.
    Not what the leaves table is organized to serve.
```

The deeper problem is not just performance. It is that you start making trade-offs that hurt both sides. You add denormalization to speed up reads, which makes writes more complex because now you have to update multiple places. You add indexes to support read queries, which slow down write performance because every INSERT and UPDATE must update those indexes. You keep adding columns to the `leaves` table to avoid JOIN overhead, which makes the table bloated and hard to reason about. Eventually you have a data model that serves both reads and writes adequately but serves neither excellently.

CQRS solves this by refusing the compromise. It says: do not try to serve reads and writes with the same model. Give each its own model, its own storage, its own optimization strategy.

---

## What CQRS Actually Is

CQRS stands for Command Query Responsibility Segregation. The name is precise and worth unpacking word by word.

A **Command** is an operation that changes state. It is an instruction to do something: `SubmitLeave`, `ApproveLeave`, `RejectLeave`, `CancelLeave`. Commands go through the write side, which validates business rules, enforces consistency, and persists changes to the write store. Commands do not return data — they either succeed or fail.

A **Query** is an operation that reads state. It is a request for information: `GetLeaveDetails`, `ListPendingLeaves`, `GetMonthlyLeaveReport`, `GetEmployeeLeaveHistory`. Queries go through the read side, which reads from a separate read store optimized specifically for the query. Queries do not change any state — they are pure reads.

**Responsibility Segregation** means these two sides are not just separate code paths — they are separate models with separate storage, separate services if needed, and independently scaled and optimized.

```
CQRS — The Fundamental Separation
───────────────────────────────────

  Everything that happens in the system is either:
  ┌──────────────────────────┐  or  ┌──────────────────────────┐
  │        COMMAND           │      │         QUERY            │
  │   (changes the world)    │      │   (reads the world)      │
  │                          │      │                          │
  │  SubmitLeave             │      │  GetLeaveDetails         │
  │  ApproveLeave            │      │  ListPendingLeaves       │
  │  RejectLeave             │      │  GetDashboardStats       │
  │  UpdateLeaveReason       │      │  GetLeaveHistory         │
  │  CancelLeave             │      │  ExportMonthlyReport     │
  │                          │      │                          │
  │  → validates rules       │      │  → no validation needed  │
  │  → enforces consistency  │      │  → just fetch and return │
  │  → writes to write store │      │  → reads from read store │
  │  → returns success/fail  │      │  → returns data          │
  └──────────────────────────┘      └──────────────────────────┘
            │                                    ▲
            │  state changes flow               │  read models
            │  to read store via                │  built from
            │  events / sync                    │  events / sync
            └───────────────────────────────────┘
```

The read store and write store do not have to be the same database or even the same type of database. The write store is typically a normalized relational database — PostgreSQL in our case — optimized for transactional correctness. The read store can be a denormalized PostgreSQL schema with different tables and indexes, or it can be a completely different technology: Elasticsearch for full-text search, Redis for real-time counters, a separate PostgreSQL database with materialized views pre-joined for specific query patterns.

## The Four Levels of CQRS

CQRS is not one specific implementation. It is a spectrum with four increasingly sophisticated levels. Understanding all four lets you apply the right level of complexity for the problem at hand.

```
CQRS SPECTRUM — Four Levels of Sophistication
──────────────────────────────────────────────────────────────────────────────

LEVEL 1: Same DB, Separate Code Paths
─────────────────────────────────────
  CommandHandler ──► leaves table (normalized write model)
  QueryHandler   ──► leaves table (same table, different queries)

  No separate store. Just code organization.
  Benefit: Clarity. Reads and writes are not tangled.
  Limit: Same DB contention, same model compromise.

LEVEL 2: Same DB, Separate Read Models (Views)
───────────────────────────────────────────────
  CommandHandler ──► leaves table (write model)
  QueryHandler   ──► leave_summary_view (DB view or materialized view)
                     leave_dashboard_view
                     leave_history_view

  One DB, multiple read-optimized views derived from the write table.
  Benefit: Query-specific optimization without separate infrastructure.
  Limit: Same DB still; views updated synchronously; single scaling unit.

LEVEL 3: Separate Read Store (Same Process)
────────────────────────────────────────────
  CommandHandler ──► leaves table (write DB)
                         │
                         │ events published internally
                         ▼
  Projections    ──► read_leaves table (read DB, different schema)
  QueryHandler   ──► read_leaves table

  Separate read database updated by projections.
  Benefit: Read store can be a different DB type, independently scaled.
  Limit: Same process; read-write coupling still exists at deploy time.

LEVEL 4: Fully Separated Services (True Microservice CQRS)
────────────────────────────────────────────────────────────
  Leave Command Service  ──► write DB
       │ publishes events via Kafka + Outbox
       ▼
  Kafka (leave.events topic)
       │
       ▼
  Leave Query Service    ──► read DB (independently deployed, independently scaled)
  QueryHandler          ──► read DB

  Maximum flexibility. Each service independently deployable and scalable.
  This is what we build in a 12-service microservice system.
```

Let us implement all four levels fully, starting simple and building to the production architecture.

## Level 1 — Same Database, Separated Code Paths

This is the entry point. No new infrastructure. Just discipline in how you organize the code. The key rule: query methods never call command methods, command methods never return query results.

```go
// leave/commands/command_handler.go

package commands

// All commands are plain structs with validation logic
type SubmitLeaveCommand struct {
    LeaveID    string
    EmployeeID string
    LeaveType  string
    Days       int
    StartDate  time.Time
    EndDate    time.Time
    Reason     string
}

func (c SubmitLeaveCommand) Validate() error {
    if c.Days <= 0 {
        return fmt.Errorf("days must be positive")
    }
    if c.EndDate.Before(c.StartDate) {
        return fmt.Errorf("end date must be after start date")
    }
    if c.LeaveType == "" {
        return fmt.Errorf("leave type is required")
    }
    return nil
}

type ApproveLeaveCommand struct {
    LeaveID    string
    ApprovedBy string
    Comment    string
}

// CommandHandler handles all write operations
type LeaveCommandHandler struct {
    db     *gorm.DB
    logger *slog.Logger
}

func NewLeaveCommandHandler(db *gorm.DB, logger *slog.Logger) *LeaveCommandHandler {
    return &LeaveCommandHandler{db: db, logger: logger}
}

// HandleSubmitLeave — creates a leave, returns only the ID (not the full leave)
func (h *LeaveCommandHandler) HandleSubmitLeave(ctx context.Context, cmd SubmitLeaveCommand) (string, error) {
    if err := cmd.Validate(); err != nil {
        return "", fmt.Errorf("invalid command: %w", err)
    }

    leave := &Leave{
        ID:         cmd.LeaveID,
        EmployeeID: cmd.EmployeeID,
        LeaveType:  cmd.LeaveType,
        Days:       cmd.Days,
        StartDate:  cmd.StartDate,
        EndDate:    cmd.EndDate,
        Reason:     cmd.Reason,
        Status:     "PENDING",
        CreatedAt:  time.Now(),
    }

    if err := h.db.WithContext(ctx).Create(leave).Error; err != nil {
        return "", fmt.Errorf("failed to create leave: %w", err)
    }

    h.logger.Info("leave submitted", "leave_id", leave.ID, "employee_id", cmd.EmployeeID)
    return leave.ID, nil
}

// HandleApproveLeave — approves a leave, returns only success/error
func (h *LeaveCommandHandler) HandleApproveLeave(ctx context.Context, cmd ApproveLeaveCommand) error {
    result := h.db.WithContext(ctx).
        Model(&Leave{}).
        Where("id = ? AND status = ?", cmd.LeaveID, "PENDING").
        Updates(map[string]interface{}{
            "status":      "APPROVED",
            "approved_by": cmd.ApprovedBy,
            "approved_at": time.Now(),
            "comment":     cmd.Comment,
        })

    if result.Error != nil {
        return result.Error
    }
    if result.RowsAffected == 0 {
        return fmt.Errorf("leave %s not found or not in PENDING status", cmd.LeaveID)
    }
    return nil
}
```

```go
// leave/queries/query_handler.go

package queries

// Query structs describe what data is needed and with what filters
type GetLeaveDetailsQuery struct {
    LeaveID string
}

type ListPendingLeavesQuery struct {
    Department string
    ManagerID  string
    Page       int
    PageSize   int
    SortBy     string
}

// Read models — shaped for the consumer, not for the database
type LeaveDetailView struct {
    LeaveID        string    `json:"leave_id"`
    EmployeeID     string    `json:"employee_id"`
    EmployeeName   string    `json:"employee_name"`    // denormalized from join
    Department     string    `json:"department"`        // denormalized from join
    LeaveType      string    `json:"leave_type"`
    Days           int       `json:"days"`
    StartDate      time.Time `json:"start_date"`
    EndDate        time.Time `json:"end_date"`
    Status         string    `json:"status"`
    BalanceRemaining int     `json:"balance_remaining"` // denormalized from join
    SubmittedAt    time.Time `json:"submitted_at"`
    ApprovedBy     string    `json:"approved_by,omitempty"`
}

// QueryHandler handles all read operations
type LeaveQueryHandler struct {
    db *gorm.DB
}

func (h *LeaveQueryHandler) HandleGetLeaveDetails(ctx context.Context, q GetLeaveDetailsQuery) (*LeaveDetailView, error) {
    var view LeaveDetailView

    err := h.db.WithContext(ctx).
        Table("leaves l").
        Select(`l.id as leave_id, l.employee_id, e.name as employee_name,
                e.department, l.leave_type, l.days, l.start_date, l.end_date,
                l.status, b.available_days as balance_remaining,
                l.created_at as submitted_at, l.approved_by`).
        Joins("JOIN employees e ON e.id = l.employee_id").
        Joins("LEFT JOIN leave_balances b ON b.employee_id = l.employee_id AND b.leave_type = l.leave_type").
        Where("l.id = ?", q.LeaveID).
        Scan(&view).Error

    if err != nil {
        return nil, err
    }
    return &view, nil
}

func (h *LeaveQueryHandler) HandleListPendingLeaves(ctx context.Context, q ListPendingLeavesQuery) ([]LeaveDetailView, int64, error) {
    query := h.db.WithContext(ctx).
        Table("leaves l").
        Select(`l.id as leave_id, l.employee_id, e.name as employee_name,
                e.department, l.leave_type, l.days, l.start_date, l.end_date,
                l.status, b.available_days as balance_remaining,
                l.created_at as submitted_at`).
        Joins("JOIN employees e ON e.id = l.employee_id").
        Joins("LEFT JOIN leave_balances b ON b.employee_id = l.employee_id AND b.leave_type = l.leave_type").
        Where("l.status = ?", "PENDING")

    if q.Department != "" {
        query = query.Where("e.department = ?", q.Department)
    }
    if q.ManagerID != "" {
        query = query.Where("e.manager_id = ?", q.ManagerID)
    }

    var total int64
    query.Count(&total)

    sortColumn := "l.created_at DESC"
    if q.SortBy == "days" {
        sortColumn = "l.days DESC"
    }

    var views []LeaveDetailView
    offset := (q.Page - 1) * q.PageSize
    err := query.Order(sortColumn).Offset(offset).Limit(q.PageSize).Scan(&views).Error

    return views, total, err
}
```

Even at this simplest level, you gain something important: the query handler is free to write complex JOINs and return denormalized view structs without worrying about whether that structure makes sense for writes. And the command handler is free to work with a clean normalized model without having to satisfy any read requirements.

## Level 2 — Separate Read Models in the Same Database

The next step is to create dedicated read model tables — sometimes called projection tables or materialized views — that are pre-joined and pre-shaped for specific query patterns. These tables are not the source of truth. The `leaves` table is the source of truth. The read model tables are derived views, updated whenever the source changes.

```go
// leave/read_models/leave_summary.go

// This is a read-model table — NOT a source of truth
// It exists purely for fast reads
type LeaveSummaryReadModel struct {
    LeaveID          string    `gorm:"primaryKey"`
    EmployeeID       string    `gorm:"not null;index"`
    EmployeeName     string    `gorm:"not null"`
    EmployeeEmail    string
    Department       string    `gorm:"not null;index"`
    TeamLeadName     string    // denormalized — never needs a join
    LeaveType        string    `gorm:"not null;index"`
    Days             int       `gorm:"not null"`
    StartDate        time.Time `gorm:"index"`
    EndDate          time.Time
    Status           string    `gorm:"not null;index"`
    BalanceRemaining int
    SubmittedAt      time.Time `gorm:"index"`
    ApprovedBy       string
    ApprovedAt       *time.Time
    RejectedReason   string
    // Composite indexes for common query patterns
}

// TableName forces GORM to use a specific table name
func (LeaveSummaryReadModel) TableName() string {
    return "leave_summary_read_model"
}

// Indexes for this table are designed around read patterns, not write patterns
// Migrations add:
// CREATE INDEX idx_lsrm_dept_status ON leave_summary_read_model (department, status, submitted_at DESC);
// CREATE INDEX idx_lsrm_employee_date ON leave_summary_read_model (employee_id, submitted_at DESC);
// CREATE INDEX idx_lsrm_status_type ON leave_summary_read_model (status, leave_type, start_date);
```

```go
// leave/read_models/projection.go

// The projection is the synchronization mechanism between write model and read model
type LeaveSummaryProjection struct {
    db     *gorm.DB
    logger *slog.Logger
}

// Called immediately after a command completes successfully (synchronous projection)
func (p *LeaveSummaryProjection) OnLeaveSubmitted(ctx context.Context, leave Leave, employee Employee, balance LeaveBalance) error {
    readModel := &LeaveSummaryReadModel{
        LeaveID:          leave.ID,
        EmployeeID:       leave.EmployeeID,
        EmployeeName:     employee.Name,
        EmployeeEmail:    employee.Email,
        Department:       employee.Department,
        TeamLeadName:     employee.TeamLeadName,
        LeaveType:        leave.LeaveType,
        Days:             leave.Days,
        StartDate:        leave.StartDate,
        EndDate:          leave.EndDate,
        Status:           "PENDING",
        BalanceRemaining: balance.AvailableDays - leave.Days,
        SubmittedAt:      leave.CreatedAt,
    }

    return p.db.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns:   []clause.Column{{Name: "leave_id"}},
            DoUpdates: clause.AssignmentColumns([]string{
                "employee_name", "employee_email", "department",
                "team_lead_name", "leave_type", "days",
                "start_date", "end_date", "status",
                "balance_remaining", "submitted_at",
            }),
        }).
        Create(readModel).Error
}

func (p *LeaveSummaryProjection) OnLeaveApproved(ctx context.Context, leaveID, approvedBy string, approvedAt time.Time) error {
    return p.db.WithContext(ctx).
        Model(&LeaveSummaryReadModel{}).
        Where("leave_id = ?", leaveID).
        Updates(map[string]interface{}{
            "status":      "APPROVED",
            "approved_by": approvedBy,
            "approved_at": approvedAt,
        }).Error
}

func (p *LeaveSummaryProjection) OnLeaveRejected(ctx context.Context, leaveID, reason string) error {
    return p.db.WithContext(ctx).
        Model(&LeaveSummaryReadModel{}).
        Where("leave_id = ?", leaveID).
        Updates(map[string]interface{}{
            "status":          "REJECTED",
            "rejected_reason": reason,
        }).Error
}
```

```go
// leave/commands/command_handler_with_projection.go

// Updated command handler that also maintains the read model
func (h *LeaveCommandHandler) HandleSubmitLeave(ctx context.Context, cmd SubmitLeaveCommand) (string, error) {
    if err := cmd.Validate(); err != nil {
        return "", err
    }

    var employee Employee
    var balance LeaveBalance
    var leaveID string

    err := h.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // Load employee and balance for the read model projection
        if err := tx.Where("id = ?", cmd.EmployeeID).First(&employee).Error; err != nil {
            return err
        }
        if err := tx.Where("employee_id = ? AND leave_type = ?", cmd.EmployeeID, cmd.LeaveType).
            First(&balance).Error; err != nil {
            return err
        }

        // Write model: insert into normalized leaves table
        leave := &Leave{
            ID:         cmd.LeaveID,
            EmployeeID: cmd.EmployeeID,
            LeaveType:  cmd.LeaveType,
            Days:       cmd.Days,
            StartDate:  cmd.StartDate,
            EndDate:    cmd.EndDate,
            Reason:     cmd.Reason,
            Status:     "PENDING",
        }
        if err := tx.Create(leave).Error; err != nil {
            return err
        }

        // Read model projection: insert into denormalized read model
        // Both happen in the same transaction — read model is always consistent with write
        if err := h.projection.OnLeaveSubmitted(ctx, *leave, employee, balance); err != nil {
            return err
        }

        leaveID = leave.ID
        return nil
    })

    return leaveID, err
}
```

Now the query handler never touches the normalized `leaves` table directly. It only reads from `leave_summary_read_model`, which is pre-joined, pre-indexed for all the read patterns, and never causes lock contention with write operations.

## Level 3 — Separate Read and Write Databases

At this level, we introduce a genuine second database. The write database is the authoritative source of truth — it holds normalized, transactional data. The read database is a separate PostgreSQL instance (or Redis, or Elasticsearch) containing denormalized read models. The two databases are kept in sync through an event-publishing mechanism.

```
LEVEL 3 — SEPARATE DATABASES
──────────────────────────────

  Write Path:
  ────────────
  gRPC Command ──► CommandHandler ──► Write DB (PostgreSQL — normalized)
                                           │
                                           │ publishes domain event
                                           ▼
                                      Kafka (leave.events)
                                           │
                                           ▼
  Read Path:                         Projection Worker
  ──────────                              │
  gRPC Query ──► QueryHandler ◄── Read DB (PostgreSQL — denormalized)
                                   leave_summary_view
                                   leave_dashboard_view
                                   leave_history_view

  Write DB and Read DB are separate PostgreSQL databases.
  Read DB is updated asynchronously by projection worker.
  Writes: fast, simple, normalized
  Reads:  fast, flexible, denormalized, no join overhead
```

```go
// leave/query_service/query_service.go

// This is a completely separate service with its own DB connection
// pointing to the READ database

type LeaveQueryService struct {
    readDB  *gorm.DB  // connects to read-optimized database
    logger  *slog.Logger
}

// All queries hit the read DB exclusively
func (s *LeaveQueryService) GetDashboardStats(ctx context.Context, managerID string) (*DashboardStats, error) {
    var stats DashboardStats

    // This query is only possible because the read model is pre-aggregated
    err := s.readDB.WithContext(ctx).
        Table("leave_summary_read_model").
        Select(`
            COUNT(*) FILTER (WHERE status = 'PENDING') as pending_count,
            COUNT(*) FILTER (WHERE status = 'APPROVED') as approved_count,
            COUNT(*) FILTER (WHERE status = 'REJECTED') as rejected_count,
            SUM(days) FILTER (WHERE status = 'APPROVED' AND EXTRACT(MONTH FROM start_date) = EXTRACT(MONTH FROM NOW())) as days_taken_this_month,
            COUNT(DISTINCT employee_id) as unique_employees
        `).
        Where("team_lead_name = (SELECT name FROM employees WHERE id = ?)", managerID).
        Scan(&stats).Error

    return &stats, err
}
```

```go
// leave/projections/kafka_projection_worker.go

// This worker runs in the Leave Query Service process
// It consumes events from Kafka and updates the read DB

type LeaveProjectionWorker struct {
    readDB  *gorm.DB
    reader  *kafka.Reader
    logger  *slog.Logger
}

func (w *LeaveProjectionWorker) Run(ctx context.Context) error {
    for {
        msg, err := w.reader.FetchMessage(ctx)
        if err != nil {
            if errors.Is(err, context.Canceled) {
                return nil
            }
            w.logger.Error("projection worker fetch failed", "error", err)
            continue
        }

        eventType := extractHeader(msg.Headers, "event-type")

        var processErr error
        switch eventType {
        case "LeaveSubmitted":
            processErr = w.handleLeaveSubmitted(ctx, msg)
        case "LeaveApproved":
            processErr = w.handleLeaveApproved(ctx, msg)
        case "LeaveRejected":
            processErr = w.handleLeaveRejected(ctx, msg)
        case "LeaveCancelled":
            processErr = w.handleLeaveCancelled(ctx, msg)
        case "EmployeeUpdated":
            // Cross-service event — update all read models that contain employee data
            processErr = w.handleEmployeeUpdated(ctx, msg)
        default:
            w.logger.Debug("skipping unknown event type", "event_type", eventType)
        }

        if processErr != nil {
            w.logger.Error("projection failed", "event_type", eventType, "error", processErr)
            // In production: send to DLQ, do not block the consumer
        }

        w.reader.CommitMessages(ctx, msg)
    }
}

func (w *LeaveProjectionWorker) handleLeaveSubmitted(ctx context.Context, msg kafka.Message) error {
    var event struct {
        LeaveID      string    `json:"leave_id"`
        EmployeeID   string    `json:"employee_id"`
        EmployeeName string    `json:"employee_name"`
        Department   string    `json:"department"`
        LeaveType    string    `json:"leave_type"`
        Days         int       `json:"days"`
        StartDate    time.Time `json:"start_date"`
        EndDate      time.Time `json:"end_date"`
        Reason       string    `json:"reason"`
        SubmittedAt  time.Time `json:"submitted_at"`
    }

    if err := json.Unmarshal(msg.Value, &event); err != nil {
        return fmt.Errorf("deserialization error: %w", err)
    }

    // Upsert into read model — idempotent by design
    return w.readDB.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns:   []clause.Column{{Name: "leave_id"}},
            DoUpdates: clause.AssignmentColumns([]string{
                "employee_id", "employee_name", "department",
                "leave_type", "days", "start_date", "end_date",
                "status", "submitted_at",
            }),
        }).
        Create(&LeaveSummaryReadModel{
            LeaveID:      event.LeaveID,
            EmployeeID:   event.EmployeeID,
            EmployeeName: event.EmployeeName,
            Department:   event.Department,
            LeaveType:    event.LeaveType,
            Days:         event.Days,
            StartDate:    event.StartDate,
            EndDate:      event.EndDate,
            Status:       "PENDING",
            SubmittedAt:  event.SubmittedAt,
        }).Error
}

// Cross-service projection — employee name changed, update all leave read models
func (w *LeaveProjectionWorker) handleEmployeeUpdated(ctx context.Context, msg kafka.Message) error {
    var event struct {
        EmployeeID string `json:"employee_id"`
        Name       string `json:"name"`
        Department string `json:"department"`
    }

    if err := json.Unmarshal(msg.Value, &event); err != nil {
        return err
    }

    // Update all leave read model rows for this employee
    return w.readDB.WithContext(ctx).
        Model(&LeaveSummaryReadModel{}).
        Where("employee_id = ?", event.EmployeeID).
        Updates(map[string]interface{}{
            "employee_name": event.Name,
            "department":    event.Department,
        }).Error
}
```

## Level 4 — Fully Separated CQRS Microservices

This is the architecture we build in production for our 12-service system. The write side and the read side are deployed as completely separate services with separate codebases, separate databases, separate scaling policies, and separate deployment pipelines. They communicate only through Kafka events.

## Multiple Read Models for Different Consumers

One of the most powerful consequences of CQRS is that you can have multiple read models serving different consumers, each shaped perfectly for that consumer's needs. The same Kafka events feed multiple projection workers that build different read models.

────────────────────────────────────────────

  leave.events (Kafka)
         │
         ├──────────────────────────────────────────────────────────────────►
         │                                                                   │

  ──────────────────────                                                     │

```go
// projections/leave_calendar_projection.go

// This read model explodes date ranges into individual day rows
// Making "who is on leave on 2024-03-15" a trivial point query

type LeaveCalendarEntry struct {
    Date       time.Time `gorm:"primaryKey;index"`
    EmployeeID string    `gorm:"primaryKey"`
    LeaveID    string    `gorm:"not null"`
    EmployeeName string  `gorm:"not null"`
    Department  string   `gorm:"not null;index"`
    LeaveType   string   `gorm:"not null"`
}

type LeaveCalendarProjection struct {
    readDB *gorm.DB
}

func (p *LeaveCalendarProjection) OnLeaveApproved(ctx context.Context, event LeaveApprovedEvent) error {
    // Explode the date range into individual day rows
    var entries []LeaveCalendarEntry
    current := event.StartDate

    for !current.After(event.EndDate) {
        if current.Weekday() != time.Saturday && current.Weekday() != time.Sunday {
            entries = append(entries, LeaveCalendarEntry{
                Date:         current,
                EmployeeID:   event.EmployeeID,
                LeaveID:      event.LeaveID,
                EmployeeName: event.EmployeeName,
                Department:   event.Department,
                LeaveType:    event.LeaveType,
            })
        }
        current = current.AddDate(0, 0, 1)
    }

    if len(entries) == 0 {
        return nil
    }

    return p.readDB.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns:   []clause.Column{{Name: "date"}, {Name: "employee_id"}},
            DoUpdates: clause.AssignmentColumns([]string{"leave_type", "employee_name"}),
        }).
        CreateInBatches(entries, 50).Error
}

func (p *LeaveCalendarProjection) OnLeaveCancelled(ctx context.Context, event LeaveCancelledEvent) error {
    // Remove the calendar entries when a leave is cancelled
    return p.readDB.WithContext(ctx).
        Where("leave_id = ?", event.LeaveID).
        Delete(&LeaveCalendarEntry{}).Error
}
```

Now the query for "who is on leave today" is:

```go
func (h *LeaveQueryHandler) GetTeamAbsencesToday(ctx context.Context, department string) ([]LeaveCalendarEntry, error) {
    var entries []LeaveCalendarEntry
    today := time.Now().Truncate(24 * time.Hour)

    return entries, h.readDB.
        Where("date = ? AND department = ?", today, department).
        Find(&entries).Error
    // Single index lookup. Zero JOINs. Returns in microseconds.
}
```

Without CQRS and the calendar read model, this same query would require: join leaves to employees, filter by department and status APPROVED, then check if today's date falls within (start_date, end_date). With a million leave records, that is a range scan that could take seconds.

## Handling Eventual Consistency in the API Layer

Because the read model is updated asynchronously from Kafka events, there is a brief window — typically milliseconds to a few seconds — between when a command succeeds and when the read model reflects the change. This is called eventual consistency, and it is important to handle it correctly at the API layer so clients are not confused.

```go
// api/leave_api_handler.go

// The API Gateway orchestrates commands and queries
type LeaveAPIHandler struct {
    commandClient  leavecmdpb.LeaveCommandServiceClient
    queryClient    leavequpb.LeaveQueryServiceClient
}

func (h *LeaveAPIHandler) SubmitLeave(w http.ResponseWriter, r *http.Request) {
    var req SubmitLeaveRequest
    json.NewDecoder(r.Body).Decode(&req)

    // Step 1: Send command to the write service
    cmdResp, err := h.commandClient.SubmitLeave(r.Context(), &leavecmdpb.SubmitLeaveRequest{
        EmployeeId: req.EmployeeID,
        LeaveType:  req.LeaveType,
        Days:       int32(req.Days),
    })
    if err != nil {
        http.Error(w, "command failed", http.StatusInternalServerError)
        return
    }

    // Step 2: Respond with the command result — just the ID and status
    // DO NOT try to immediately query the read model here.
    // The read model is eventually consistent — the new leave may not be there yet.
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusAccepted) // 202 Accepted — not 200 OK
    json.NewEncoder(w).Encode(map[string]interface{}{
        "leave_id": cmdResp.LeaveId,
        "status":   "PENDING",
        "message":  "Your leave application has been submitted successfully.",
        // The client should poll GET /leaves/{id} or wait for a WebSocket push
        // to see the leave in the list view
    })
}

// For reads — always go to the query service, never the command service
func (h *LeaveAPIHandler) GetLeave(w http.ResponseWriter, r *http.Request) {
    leaveID := chi.URLParam(r, "id")

    leave, err := h.queryClient.GetLeaveDetails(r.Context(), &leavequpb.GetLeaveDetailsRequest{
        LeaveId: leaveID,
    })
    if err != nil {
        http.Error(w, "not found", http.StatusNotFound)
        return
    }

    json.NewEncoder(w).Encode(leave)
}
```

```
EVENTUAL CONSISTENCY — Timeline
──────────────────────────────────

  t=0ms:   Client sends SubmitLeave command
  t=5ms:   Command service writes to write DB
  t=5ms:   Outbox event written (same transaction)
  t=5ms:   Command service responds: 202 Accepted, leave_id: L001
  t=10ms:  Outbox worker publishes LeaveSubmitted to Kafka
  t=15ms:  Query service Kafka consumer receives event
  t=20ms:  Projection worker updates read DB
  t=20ms:  Read model now reflects the new leave

  Client receives 202 Accepted at t=5ms.
  If client immediately GETs /leaves/L001 at t=6ms:
    ← read model might not have it yet (15ms lag)
    ← return "not found" or stale data

  Correct client behavior:
  ├── Show optimistic UI immediately (show the leave as PENDING based on command response)
  ├── Poll GET /leaves/L001 with a short delay (e.g. 500ms after submission)
  ├── Or: wait for WebSocket/Server-Sent-Event push when read model updates
  └── Eventually consistent — the read model WILL be updated within seconds
```

## CQRS With Optimistic Concurrency on the Write Side

When multiple users can modify the same entity concurrently — two managers both try to approve the same leave — the write side needs to protect against lost updates. CQRS does not change this requirement, but it is important to show how it is handled cleanly within the command handler.

```go
// leave/commands/approve_with_optimistic_lock.go

// The Leave write model includes a version field for optimistic concurrency
type Leave struct {
    ID         string    `gorm:"primaryKey"`
    EmployeeID string    `gorm:"not null"`
    Status     string    `gorm:"not null;default:'PENDING'"`
    Version    int       `gorm:"not null;default:0"`  // incremented on every update
    // ... other fields
}

func (h *LeaveCommandHandler) HandleApproveLeave(ctx context.Context, cmd ApproveLeaveCommand) error {
    return h.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        var leave Leave
        if err := tx.Where("id = ?", cmd.LeaveID).First(&leave).Error; err != nil {
            return err
        }

        if leave.Status != "PENDING" {
            return fmt.Errorf("leave cannot be approved: current status is %s", leave.Status)
        }

        // Optimistic lock: UPDATE only if version hasn't changed since we read it
        result := tx.Model(&Leave{}).
            Where("id = ? AND version = ? AND status = ?", cmd.LeaveID, leave.Version, "PENDING").
            Updates(map[string]interface{}{
                "status":      "APPROVED",
                "approved_by": cmd.ApprovedBy,
                "approved_at": time.Now(),
                "version":     leave.Version + 1,
            })

        if result.Error != nil {
            return result.Error
        }

        if result.RowsAffected == 0 {
            // Version changed — another process approved/rejected this leave
            // concurrently. Signal the caller to retry with fresh data.
            return ErrConcurrentModification
        }

        return nil
    })
}
```

## What CQRS Genuinely Costs

CQRS is one of the patterns that engineers fall in love with and start applying everywhere. Before you do that, understand what it actually costs, because those costs are real and not all systems need to pay them.

Operational complexity increases substantially. You now have two databases to operate, monitor, back up, and scale. You have projection workers that must be monitored for lag — a slow projection means your read models are stale. You have Kafka topics that are now part of the system's correctness boundary. When something goes wrong, diagnosing the problem now involves tracing through the command service, Kafka, and the query service, which takes longer and requires more expertise.

Eventual consistency must be designed for explicitly. Every API that combines a command with a subsequent read must account for the propagation delay. Client applications need to handle the case where they write something and then immediately read it back and it is not there yet. This is not a bug — it is the design — but it requires careful thought at every level of the stack.

The code surface area grows. What used to be one service is now two. What used to be one database schema is now two. What used to be one place to look when debugging is now five — command service, Kafka, projection worker, read database, query service.

CQRS is worth paying all of these costs when your system has genuinely asymmetric read and write requirements — which most HR, reporting, and analytics systems do. It is worth paying when different consumers need the same data shaped differently. It is worth paying when you need to scale reads and writes independently. It is not worth paying for a simple CRUD service with straightforward read patterns. The pattern is a precision instrument, not a universal solution. Use it where it fits, and when you do, build it properly as shown above rather than halfway — a half-built CQRS system often has all the costs and few of the benefits.
