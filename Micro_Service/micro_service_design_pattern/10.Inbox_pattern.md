# The Inbox and Idempotency Pattern in Microservices

### Everything You Need to Know — Explained Like You Just Joined the Team

---

## A Story From Everyday Life

Imagine you send a payment of 5,000 taka to a friend using a mobile banking app. You tap the "Send" button. The screen shows a loading spinner for a few seconds and then — nothing. The app freezes. You are not sure if the payment went through or not. So you tap the button again. And then maybe one more time just to be sure.

Now your friend receives three separate transfers of 5,000 taka each — 15,000 taka total — when you only intended to send 5,000. You accidentally sent three payments because you could not tell if the first one succeeded.

This is the duplicate operation problem. And it is not a user error. It is a system design problem. A well-designed payment system should recognize that you tapped the button three times in confusion and process only one payment, no matter how many times the request arrived. The operation should be idempotent — processing it multiple times should produce the same result as processing it once.

Now multiply this problem across a distributed system where network failures are common, services crash and restart, Kafka delivers messages at least once, and retries are everywhere. This is not an edge case. This is the normal operating condition. Idempotency is not a nice-to-have. It is a fundamental requirement of correct distributed system design.

---

## The Problem in Full Technical Depth

Let us trace exactly how duplicate operations arise in our leave management system, because they arise from multiple different sources and you need to understand all of them.

The first source is network timeouts on the client side. A client sends a `SubmitLeave` gRPC request to the Leave Service. The Leave Service receives it, writes the leave to the database, and sends back a success response. But the network drops the response packet. The client never receives the acknowledgment. From the client's perspective, the request timed out and failed. So the client retries. The Leave Service now receives the exact same request a second time and creates a duplicate leave record.

```
SOURCE 1: CLIENT-SIDE TIMEOUT AND RETRY
──────────────────────────────────────────

  Client                    Network              Leave Service
    │                                                 │
    │──── SubmitLeave (request #1) ──────────────────►│
    │                                                 │ writes leave L001
    │                                                 │ to database ✓
    │◄─ ─ ─ ─ SUCCESS response (DROPPED) ─ ─ ─ ─ ─  │
    │                                                 │
    │  (client sees timeout, decides to retry)        │
    │                                                 │
    │──── SubmitLeave (request #2, same data) ───────►│
    │                                                 │ writes leave L001 AGAIN
    │◄───────────── SUCCESS response ─────────────────│ DUPLICATE ← BUG
    │
  Client thinks only one leave was submitted.
  Database has two identical leave records.
```

The second source is Kafka's at-least-once delivery guarantee. We covered this in the Outbox Pattern and Transactional Inbox Pattern guides. Kafka guarantees that a message will be delivered at least once — which means it might be delivered more than once. A consumer that processes a message and then crashes before committing the offset will re-receive the same message on restart. Without idempotency, the business operation runs twice.

The third source is SAGA compensating transactions being replayed. When a SAGA orchestrator retries a failed step — perhaps the Approval Service was temporarily down — it sends the same command again. If the Approval Service already created the approval record on the first attempt but failed to respond, the second command will try to create a duplicate approval record.

The fourth source is gRPC retries configured in the service mesh or client code. A transient network error causes Envoy or the gRPC client to automatically retry the request. The server may have processed the first attempt successfully but the response was lost.

```
ALL SOURCES OF DUPLICATE OPERATIONS
─────────────────────────────────────────────────────────────────────

  Client retries ──────────────────────────────────────────────────►
                                                              Leave
  Kafka at-least-once ─────────────────────────────────────► Service
                                                            or any
  SAGA retry on failure ───────────────────────────────────► downstream
                                                            service
  gRPC client/proxy retry ────────────────────────────────►

  All four sources produce the same problem:
  the same logical operation arrives at a service more than once.

  Without idempotency: duplicate records, double charges, duplicate emails
  With idempotency:    first operation executes, subsequent ones skip safely
```

## What Idempotency Actually Means

An operation is idempotent if executing it multiple times produces exactly the same result as executing it once. In mathematics, multiplying by one is idempotent — doing it ten times gives the same result as doing it once. In software, a GET request is naturally idempotent — reading the same data ten times returns the same data and changes nothing. The challenge is making write operations idempotent — making INSERT and UPDATE operations safe to call multiple times.

The mechanism for achieving idempotency on write operations is the idempotency key. An idempotency key is a unique identifier that the caller assigns to a logical operation before sending it. When the server receives a request, it checks whether it has seen this idempotency key before. If it has — meaning this is a retry — it returns the result of the first execution without executing the operation again. If it has not — meaning this is a new request — it executes the operation, stores the result indexed by the idempotency key, and returns the result.

```
IDEMPOTENCY KEY MECHANISM
───────────────────────────

  First request (new operation):
  ───────────────────────────────
  Client sends: SubmitLeave { idempotency_key: "idk-abc-123", employee_id: "E42", days: 5 }
  Server checks: has "idk-abc-123" been processed before?
  Server finds: NO
  Server executes: creates leave L001, stores result under "idk-abc-123"
  Server responds: { leave_id: "L001", status: "PENDING" }

  Second request (retry, same key):
  ────────────────────────────────────
  Client sends: SubmitLeave { idempotency_key: "idk-abc-123", employee_id: "E42", days: 5 }
  Server checks: has "idk-abc-123" been processed before?
  Server finds: YES — result is { leave_id: "L001", status: "PENDING" }
  Server returns: { leave_id: "L001", status: "PENDING" } ← same result, no new operation
  Leave L001 is NOT created again. Database unchanged.

  The client receives the same response both times.
  The client cannot distinguish a first call from a retry.
  The system state is correct.
```

The idempotency key must be generated by the caller, not the server. This is critical. If the server generates the key, a new key is generated on every request and there is no deduplication. The caller — whether it is a frontend client, an API Gateway, a SAGA orchestrator, or a Kafka consumer — must generate a stable key before the first attempt and reuse that exact same key on every retry.

## The Idempotency Key Schema

Every service that accepts commands needs an idempotency key store. This is a database table that records every processed idempotency key, the result of the operation, and when it was processed.

```sql
CREATE TABLE idempotency_keys (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    key             VARCHAR(255) NOT NULL,
    service         VARCHAR(100) NOT NULL,    -- which service processed this
    operation       VARCHAR(100) NOT NULL,    -- which operation (e.g. "SubmitLeave")
    status          VARCHAR(50) NOT NULL,     -- IN_PROGRESS, COMPLETED, FAILED
    request_hash    VARCHAR(64),              -- hash of request payload for conflict detection
    response_code   INT,                      -- HTTP/gRPC status code of the response
    response_body   JSONB,                    -- serialized response for replay
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    completed_at    TIMESTAMPTZ,
    expires_at      TIMESTAMPTZ NOT NULL,     -- cleanup: remove old keys after this time

    UNIQUE (key, service, operation)
);

CREATE INDEX idx_idempotency_key_lookup ON idempotency_keys (key, service, operation);
CREATE INDEX idx_idempotency_cleanup ON idempotency_keys (expires_at)
    WHERE status IN ('COMPLETED', 'FAILED');
```

In Go with GORM:

```go
// idempotency/model.go

package idempotency

type Key struct {
    ID           uuid.UUID      `gorm:"type:uuid;primaryKey;default:gen_random_uuid()"`
    Key          string         `gorm:"not null;uniqueIndex:uniq_key_svc_op"`
    Service      string         `gorm:"not null;uniqueIndex:uniq_key_svc_op"`
    Operation    string         `gorm:"not null;uniqueIndex:uniq_key_svc_op"`
    Status       string         `gorm:"not null;default:'IN_PROGRESS'"` // IN_PROGRESS | COMPLETED | FAILED
    RequestHash  string         `gorm:"size:64"`
    ResponseCode int
    ResponseBody datatypes.JSON `gorm:"type:jsonb"`
    CreatedAt    time.Time      `gorm:"not null;autoCreateTime"`
    CompletedAt  *time.Time
    ExpiresAt    time.Time      `gorm:"not null;index"`
}

// Status constants
const (
    StatusInProgress = "IN_PROGRESS"
    StatusCompleted  = "COMPLETED"
    StatusFailed     = "FAILED"
)

// Retention: keep idempotency keys for 24 hours by default
const DefaultRetention = 24 * time.Hour
```

## Implementation — Part 1: The Idempotency Middleware for gRPC

The cleanest way to add idempotency to all gRPC command handlers is through a gRPC server interceptor — a middleware layer that runs before every handler invocation. The interceptor extracts the idempotency key from the request metadata, checks the database, and either returns a cached response or allows the handler to proceed.

```go
// idempotency/grpc_interceptor.go

package idempotency

type GRPCIdempotencyInterceptor struct {
    db        *gorm.DB
    service   string
    logger    *slog.Logger
}

func NewGRPCIdempotencyInterceptor(db *gorm.DB, serviceName string) *GRPCIdempotencyInterceptor {
    return &GRPCIdempotencyInterceptor{
        db:      db,
        service: serviceName,
        logger:  slog.Default(),
    }
}

// UnaryServerInterceptor returns a gRPC interceptor for unary calls
func (i *GRPCIdempotencyInterceptor) UnaryServerInterceptor() grpc.UnaryServerInterceptor {
    return func(
        ctx context.Context,
        req interface{},
        info *grpc.UnaryServerInfo,
        handler grpc.UnaryHandler,
    ) (interface{}, error) {

        // Extract idempotency key from gRPC metadata headers
        md, ok := metadata.FromIncomingContext(ctx)
        if !ok {
            // No metadata — proceed normally (no idempotency check)
            return handler(ctx, req)
        }

        keys := md.Get("idempotency-key")
        if len(keys) == 0 || keys[0] == "" {
            // No idempotency key provided — proceed normally
            // In production you might want to REQUIRE this for all mutation endpoints
            return handler(ctx, req)
        }

        idempotencyKey := keys[0]
        operation := extractOperationName(info.FullMethod)

        return i.handleWithIdempotency(ctx, idempotencyKey, operation, req, handler)
    }
}

func (i *GRPCIdempotencyInterceptor) handleWithIdempotency(
    ctx context.Context,
    key, operation string,
    req interface{},
    handler grpc.UnaryHandler,
) (interface{}, error) {

    // Hash the request payload to detect conflicting requests
    // (same idempotency key but different payload — that is a client bug)
    requestHash := hashRequest(req)

    // Step 1: Try to insert a new IN_PROGRESS record
    // If the key already exists, this will fail on the unique constraint
    record := &Key{
        Key:         key,
        Service:     i.service,
        Operation:   operation,
        Status:      StatusInProgress,
        RequestHash: requestHash,
        ExpiresAt:   time.Now().Add(DefaultRetention),
    }

    result := i.db.WithContext(ctx).
        Clauses(clause.OnConflict{DoNothing: true}).
        Create(record)

    if result.Error != nil {
        return nil, status.Errorf(codes.Internal, "idempotency check failed: %v", result.Error)
    }

    if result.RowsAffected == 0 {
        // Key already exists — this is a retry. Load the existing record.
        var existing Key
        if err := i.db.WithContext(ctx).
            Where("key = ? AND service = ? AND operation = ?", key, i.service, operation).
            First(&existing).Error; err != nil {
            return nil, status.Errorf(codes.Internal, "failed to load idempotency record")
        }

        // Check for conflicting request (same key, different payload)
        if existing.RequestHash != requestHash {
            return nil, status.Errorf(codes.InvalidArgument,
                "idempotency key %q was previously used with a different request payload", key)
        }

        switch existing.Status {
        case StatusCompleted:
            // Return the cached response from the first successful execution
            i.logger.Info("returning cached idempotent response",
                "key", key, "operation", operation)
            return deserializeResponse(operation, existing.ResponseBody)

        case StatusFailed:
            // Previous execution failed — allow retry by clearing the record
            // and trying again
            i.db.Delete(&existing)
            // Fall through to execute the handler

        case StatusInProgress:
            // Another request is currently processing this key
            // Return a conflict error — the client should wait and retry
            return nil, status.Errorf(codes.AlreadyExists,
                "operation with idempotency key %q is already in progress", key)
        }
    }

    // Step 2: Execute the actual handler
    resp, handlerErr := handler(ctx, req)

    // Step 3: Store the result (success or failure) for future retries
    if handlerErr != nil {
        // Handler failed — mark as FAILED so retry is allowed
        grpcStatus, _ := status.FromError(handlerErr)
        i.db.Model(&Key{}).
            Where("key = ? AND service = ? AND operation = ?", key, i.service, operation).
            Updates(map[string]interface{}{
                "status":        StatusFailed,
                "response_code": int(grpcStatus.Code()),
                "completed_at":  time.Now(),
            })
        return nil, handlerErr
    }

    // Handler succeeded — store the response for replay on future retries
    responseBytes, _ := json.Marshal(resp)
    now := time.Now()
    i.db.Model(&Key{}).
        Where("key = ? AND service = ? AND operation = ?", key, i.service, operation).
        Updates(map[string]interface{}{
            "status":        StatusCompleted,
            "response_code": int(codes.OK),
            "response_body": responseBytes,
            "completed_at":  &now,
        })

    return resp, nil
}

func extractOperationName(fullMethod string) string {
    // "/leave.command.v1.LeaveCommandService/SubmitLeave" → "SubmitLeave"
    parts := strings.Split(fullMethod, "/")
    if len(parts) > 0 {
        return parts[len(parts)-1]
    }
    return fullMethod
}

func hashRequest(req interface{}) string {
    data, _ := json.Marshal(req)
    hash := sha256.Sum256(data)
    return hex.EncodeToString(hash[:])
}
```

Registering this interceptor in your gRPC server means every handler automatically gets idempotency protection without any changes to the handler code itself:

```go
// leave/main.go

func main() {
    db := setupDatabase()

    idempotencyInterceptor := idempotency.NewGRPCIdempotencyInterceptor(db, "leave-service")

    grpcServer := grpc.NewServer(
        grpc.ChainUnaryInterceptor(
            // Idempotency runs BEFORE the handler — it may short-circuit
            idempotencyInterceptor.UnaryServerInterceptor(),
            // Other interceptors (logging, tracing, auth) can run in either order
            loggingInterceptor.UnaryServerInterceptor(),
            tracingInterceptor.UnaryServerInterceptor(),
        ),
    )

    leavecmdpb.RegisterLeaveCommandServiceServer(grpcServer, leaveCommandHandler)

    // ... server startup
}
```

The gRPC client side must generate and send the idempotency key in the request metadata:

```go
// api_gateway/leave_client.go — how the API Gateway calls the Leave Service

func (c *LeaveCommandClient) SubmitLeave(ctx context.Context, req *SubmitLeaveRequest) (*SubmitLeaveResponse, error) {
    // Generate a stable idempotency key for this logical operation
    // This key must be generated ONCE and reused on ALL retries
    // The API Gateway generates this from the user's session + operation intent
    idempotencyKey := generateIdempotencyKey(ctx, "submit-leave", req)

    // Attach the key to gRPC metadata
    md := metadata.Pairs("idempotency-key", idempotencyKey)
    ctx = metadata.NewOutgoingContext(ctx, md)

    // Retry loop — same key used on every attempt
    for attempt := 0; attempt <= 3; attempt++ {
        if attempt > 0 {
            time.Sleep(time.Duration(attempt*100) * time.Millisecond)
        }

        resp, err := c.client.SubmitLeave(ctx, &leavecmdpb.SubmitLeaveRequest{
            EmployeeId: req.EmployeeID,
            LeaveType:  req.LeaveType,
            Days:       int32(req.Days),
        })

        if err == nil {
            return &SubmitLeaveResponse{LeaveID: resp.LeaveId}, nil
        }

        // Only retry on transient errors
        if !isRetryable(err) {
            return nil, err
        }
    }

    return nil, fmt.Errorf("all retry attempts exhausted")
}

func generateIdempotencyKey(ctx context.Context, operation string, req *SubmitLeaveRequest) string {
    // Key = hash(user_id + operation + request_content)
    // This is deterministic: same user, same operation, same request → same key
    userID := extractUserID(ctx)
    content := fmt.Sprintf("%s:%s:%s:%s:%d",
        userID, operation, req.EmployeeID, req.LeaveType, req.Days)
    hash := sha256.Sum256([]byte(content))
    return fmt.Sprintf("idk-%s", hex.EncodeToString(hash[:16]))
}
```

## Implementation — Part 2: The Inbox Idempotency (Kafka Consumer Deduplication)

When the source of duplicate processing is Kafka's at-least-once delivery, the idempotency mechanism lives in the Kafka consumer. This is closely related to the Transactional Inbox Pattern we covered earlier, but here we focus specifically on the deduplication aspect in complete depth.

The key insight is that every Kafka message must have a stable, unique identity that survives re-delivery. If the publisher uses the Outbox Pattern, the `outbox-event-id` header serves this purpose — it is the UUID of the outbox row, which never changes on re-delivery. If the publisher does not use the Outbox Pattern, you construct the ID from the combination of topic + partition + offset, which is also globally unique and stable.

```go
// idempotency/kafka_deduplicator.go

package idempotency

type ProcessedMessage struct {
    MessageID   string    `gorm:"primaryKey"`
    Topic       string    `gorm:"not null;index"`
    ServiceName string    `gorm:"not null"`
    HandlerName string    `gorm:"not null"`
    ProcessedAt time.Time `gorm:"not null;autoCreateTime"`
    ExpiresAt   time.Time `gorm:"not null;index"`
}

type KafkaDeduplicator struct {
    db          *gorm.DB
    serviceName string
    retention   time.Duration
    logger      *slog.Logger
}

func NewKafkaDeduplicator(db *gorm.DB, serviceName string) *KafkaDeduplicator {
    return &KafkaDeduplicator{
        db:          db,
        serviceName: serviceName,
        retention:   7 * 24 * time.Hour, // keep dedup records for 7 days
        logger:      slog.Default(),
    }
}

// ProcessOnce executes the handler exactly once per message ID
// If the message was already processed, it returns nil without calling the handler
func (d *KafkaDeduplicator) ProcessOnce(
    ctx context.Context,
    msg kafka.Message,
    handlerName string,
    handler func(ctx context.Context, tx *gorm.DB) error,
) error {
    messageID := d.extractMessageID(msg)

    // Use a database transaction to atomically:
    // 1. Check if message was already processed
    // 2. Execute the business handler
    // 3. Record the message as processed
    // If the transaction rolls back, the dedup record is also rolled back
    // so the message can be retried safely
    return d.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // Attempt to insert the dedup record
        record := &ProcessedMessage{
            MessageID:   messageID,
            Topic:       msg.Topic,
            ServiceName: d.serviceName,
            HandlerName: handlerName,
            ExpiresAt:   time.Now().Add(d.retention),
        }

        result := tx.Clauses(clause.OnConflict{DoNothing: true}).Create(record)
        if result.Error != nil {
            return fmt.Errorf("dedup insert failed: %w", result.Error)
        }

        if result.RowsAffected == 0 {
            // Message was already processed — this is a duplicate delivery
            d.logger.Info("skipping duplicate kafka message",
                "message_id", messageID,
                "topic", msg.Topic,
                "handler", handlerName,
            )
            return nil // Return nil so the consumer commits the offset
        }

        // First time seeing this message — execute the business logic
        // The handler receives the transaction so its writes are part of the
        // same atomic unit as the dedup record insert
        if err := handler(ctx, tx); err != nil {
            // If the handler fails, the transaction rolls back
            // The dedup record is also rolled back
            // The message can be retried (dedup record will not exist)
            return err
        }

        return nil
    })
}

func (d *KafkaDeduplicator) extractMessageID(msg kafka.Message) string {
    // Prefer the outbox-event-id header (set by Outbox Pattern publisher)
    for _, h := range msg.Headers {
        if h.Key == "outbox-event-id" && len(h.Value) > 0 {
            return string(h.Value)
        }
    }

    // Fallback: construct from topic + partition + offset (always unique and stable)
    return fmt.Sprintf("%s:%d:%d", msg.Topic, msg.Partition, msg.Offset)
}
```

Here is how the Balance Service consumer uses this deduplicator:

```go
// balance/consumer.go

type BalanceConsumer struct {
    deduplicator *idempotency.KafkaDeduplicator
    reader       *kafka.Reader
    db           *gorm.DB
    logger       *slog.Logger
}

func (c *BalanceConsumer) Run(ctx context.Context) error {
    for {
        msg, err := c.reader.FetchMessage(ctx)
        if err != nil {
            if errors.Is(err, context.Canceled) {
                return nil
            }
            c.logger.Error("fetch failed", "error", err)
            continue
        }

        eventType := extractHeader(msg.Headers, "event-type")

        var processErr error
        switch eventType {
        case "LeaveSubmitted":
            processErr = c.handleLeaveSubmitted(ctx, msg)
        case "LeaveCancelled":
            processErr = c.handleLeaveCancelled(ctx, msg)
        default:
            c.logger.Debug("skipping unknown event", "event_type", eventType)
        }

        if processErr != nil {
            c.logger.Error("processing failed", "error", processErr, "event_type", eventType)
            // In production: send to DLQ after retry budget exhausted
            continue
        }

        c.reader.CommitMessages(ctx, msg)
    }
}

func (c *BalanceConsumer) handleLeaveSubmitted(ctx context.Context, msg kafka.Message) error {
    return c.deduplicator.ProcessOnce(ctx, msg, "HandleLeaveSubmitted",
        func(ctx context.Context, tx *gorm.DB) error {
            // Parse the event
            var event LeaveSubmittedEvent
            if err := json.Unmarshal(msg.Value, &event); err != nil {
                return fmt.Errorf("deserialization error: %w", err)
            }

            // Business logic — all using tx (same transaction as the dedup record)
            var balance EmployeeLeaveBalance
            if err := tx.Where("employee_id = ?", event.EmployeeID).
                First(&balance).Error; err != nil {
                return err
            }

            if balance.AvailableDays < event.Days {
                return fmt.Errorf("insufficient balance")
            }

            balance.AvailableDays -= event.Days
            if err := tx.Save(&balance).Error; err != nil {
                return err
            }

            // Also write outgoing event to outbox — same transaction
            payload, _ := json.Marshal(BalanceDeductedPayload{
                LeaveID:    event.LeaveID,
                EmployeeID: event.EmployeeID,
                DaysUsed:   event.Days,
            })

            return tx.Create(&outbox.OutboxEvent{
                AggregateID:   event.LeaveID,
                AggregateType: "Leave",
                EventType:     "BalanceDeducted",
                Topic:         "balance.events",
                Payload:       payload,
                Published:     false,
            }).Error

            // ONE TRANSACTION atomically:
            // 1. Marks message as processed (dedup record)
            // 2. Deducts the balance
            // 3. Writes outgoing BalanceDeducted event to outbox
            // If anything fails: everything rolls back, message can be retried
        },
    )
}
```

## Idempotency Variant 2 — Natural Idempotency Through Upsert

Not every operation needs an explicit idempotency key table. Some operations can be made naturally idempotent through careful use of database upsert semantics — INSERT ON CONFLICT DO UPDATE or INSERT ON CONFLICT DO NOTHING.

When the business operation itself is naturally describable as "set this entity to this state", you can use the entity's natural unique identifier as the idempotency mechanism. The duplicate request simply updates the same row to the same values — no harm done.

```go
// leave/handlers/projection_handler.go

// A projection update is naturally idempotent when expressed as an upsert
func (h *ProjectionHandler) HandleLeaveApproved(ctx context.Context, event LeaveApprovedEvent) error {
    // This upsert is naturally idempotent:
    // If called once: creates the approval record
    // If called twice: updates the same row with the same values (no-op effect)
    return h.db.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns: []clause.Column{{Name: "leave_id"}},
            DoUpdates: clause.AssignmentColumns([]string{
                "status", "approved_by", "approved_at", "comment",
            }),
        }).
        Create(&ApprovalRecord{
            LeaveID:    event.LeaveID,
            Status:     "APPROVED",
            ApprovedBy: event.ApprovedBy,
            ApprovedAt: event.ApprovedAt,
            Comment:    event.Comment,
        }).Error
}

// Similarly for balance operations — use conditional update instead of blind deduction
func (h *BalanceHandler) DeductBalance(ctx context.Context, leaveID, employeeID string, days int) error {
    // Instead of:
    //   UPDATE balances SET available_days = available_days - 5 WHERE employee_id = ?
    // Which deducts 5 days on every call (NOT idempotent), use:

    // Option A: Track which leaves have been deducted
    result := h.db.WithContext(ctx).
        Model(&EmployeeLeaveBalance{}).
        Where("employee_id = ? AND ? != ALL(deducted_leave_ids)", employeeID, leaveID).
        Updates(map[string]interface{}{
            "available_days":   gorm.Expr("available_days - ?", days),
            "deducted_leave_ids": gorm.Expr("array_append(deducted_leave_ids, ?)", leaveID),
        })

    if result.RowsAffected == 0 {
        // Either employee not found, or this leave was already deducted
        // Check which one it is
        var count int64
        h.db.Model(&EmployeeLeaveBalance{}).
            Where("employee_id = ? AND ? = ANY(deducted_leave_ids)", employeeID, leaveID).
            Count(&count)
        if count > 0 {
            // Already deducted — this is a duplicate, return success silently
            return nil
        }
        return fmt.Errorf("employee balance not found: %s", employeeID)
    }

    return result.Error
}
```

```
NATURAL IDEMPOTENCY — When the Business Logic Allows It
──────────────────────────────────────────────────────────

  NATURALLY IDEMPOTENT (safe to call multiple times):
  ─────────────────────────────────────────────────────
  "Set leave status to APPROVED"
    → UPDATE leaves SET status='APPROVED' WHERE id=? AND status='PENDING'
    → Second call: status already APPROVED, RowsAffected=0, but that's OK

  "Add 5 days to balance"
    → UPDATE balances SET available_days = available_days + 5
    → Second call: adds ANOTHER 5 days ← BUG

  "Create a new leave application"
    → INSERT INTO leaves ...
    → Second call: creates a DUPLICATE leave ← BUG

  For operations in the second category, use explicit idempotency keys.
  For operations in the first category, design them to be naturally idempotent.
```

## Idempotency Variant 3 — SAGA Idempotency (Command Deduplication)

In a SAGA, the orchestrator sends commands to participant services. When a participant times out or fails, the orchestrator retries the command. The participant must be able to receive the same command multiple times without performing the business action more than once.

SAGA commands are slightly different from Kafka messages because they are typically sent over gRPC with a specific command ID embedded in the command payload rather than in transport headers.

```go
// saga/idempotency.go

// Every SAGA command carries a command_id that is stable across retries
// The orchestrator generates this ID once when the SAGA step is created
// and reuses it on every retry

type CreateApprovalCommand struct {
    CommandID   string `json:"command_id"`    // stable across retries
    SagaID      string `json:"saga_id"`
    LeaveID     string `json:"leave_id"`
    EmployeeID  string `json:"employee_id"`
    RequiredBy  time.Time `json:"required_by"`
}

// Approval Service handler — idempotent by command_id
func (h *ApprovalCommandHandler) HandleCreateApproval(ctx context.Context, cmd CreateApprovalCommand) error {
    return h.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // Check if this command was already processed
        var existing ProcessedCommand
        result := tx.Where("command_id = ?", cmd.CommandID).First(&existing)

        if result.Error == nil {
            // Already processed — return success silently
            slog.Info("skipping duplicate SAGA command",
                "command_id", cmd.CommandID,
                "saga_id", cmd.SagaID,
            )
            return nil
        }

        if !errors.Is(result.Error, gorm.ErrRecordNotFound) {
            return result.Error
        }

        // Not yet processed — execute the business logic
        approval := &Approval{
            ID:         uuid.NewString(),
            LeaveID:    cmd.LeaveID,
            EmployeeID: cmd.EmployeeID,
            Status:     "PENDING",
            RequiredBy: cmd.RequiredBy,
        }

        if err := tx.Create(approval).Error; err != nil {
            return err
        }

        // Record that this command was processed
        return tx.Create(&ProcessedCommand{
            CommandID:   cmd.CommandID,
            SagaID:      cmd.SagaID,
            ProcessedAt: time.Now(),
            ExpiresAt:   time.Now().Add(7 * 24 * time.Hour),
        }).Error
    })
}
```

## Idempotency Variant 4 — HTTP API Idempotency for the Client-Facing Layer

The API Gateway handles requests from frontend clients — browsers and mobile apps. These clients are especially prone to duplicate submissions because users click buttons multiple times, network connections are unreliable on mobile, and the browser's back button can resubmit forms.

The HTTP idempotency pattern uses the `Idempotency-Key` request header — this is now an IETF draft standard that major payment APIs (Stripe, Braintree) have been using for years. Clients generate a UUID for each logical operation and send it in this header. The server uses it to deduplicate.

```go
// api_gateway/middleware/idempotency_middleware.go

package middleware

type HTTPIdempotencyMiddleware struct {
    store  IdempotencyStore
    logger *slog.Logger
}

func (m *HTTPIdempotencyMiddleware) Middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // Only apply to mutation methods
        if r.Method == http.MethodGet || r.Method == http.MethodHead {
            next.ServeHTTP(w, r)
            return
        }

        idempotencyKey := r.Header.Get("Idempotency-Key")
        if idempotencyKey == "" {
            // No key provided — require it for POST/PATCH/DELETE
            if r.Method == http.MethodPost {
                w.Header().Set("Content-Type", "application/json")
                w.WriteHeader(http.StatusBadRequest)
                json.NewEncoder(w).Encode(map[string]string{
                    "error": "Idempotency-Key header is required for POST requests",
                    "hint":  "Generate a UUID and include it in the Idempotency-Key header",
                })
                return
            }
            next.ServeHTTP(w, r)
            return
        }

        // Check if we have a cached response for this key
        cacheKey := fmt.Sprintf("%s:%s:%s", idempotencyKey, r.Method, r.URL.Path)
        cached, err := m.store.Get(r.Context(), cacheKey)

        if err == nil && cached != nil {
            // Return the cached response
            m.logger.Info("returning cached idempotent HTTP response",
                "key", idempotencyKey,
                "path", r.URL.Path,
            )
            w.Header().Set("Content-Type", "application/json")
            w.Header().Set("Idempotency-Key", idempotencyKey)
            w.Header().Set("X-Idempotent-Replayed", "true")
            w.WriteHeader(cached.StatusCode)
            w.Write(cached.Body)
            return
        }

        // Capture the response
        recorder := &responseRecorder{
            ResponseWriter: w,
            statusCode:     http.StatusOK,
            body:           &bytes.Buffer{},
        }

        next.ServeHTTP(recorder, r)

        // Cache the response (only cache successful responses)
        if recorder.statusCode >= 200 && recorder.statusCode < 300 {
            m.store.Set(r.Context(), cacheKey, &CachedResponse{
                StatusCode: recorder.statusCode,
                Body:       recorder.body.Bytes(),
            }, 24*time.Hour)
        }
    })
}

// responseRecorder captures the response so we can cache it
type responseRecorder struct {
    http.ResponseWriter
    statusCode int
    body       *bytes.Buffer
}

func (r *responseRecorder) WriteHeader(code int) {
    r.statusCode = code
    r.ResponseWriter.WriteHeader(code)
}

func (r *responseRecorder) Write(b []byte) (int, error) {
    r.body.Write(b)
    return r.ResponseWriter.Write(b)
}
```

The client side — whether a frontend JavaScript application or a mobile app — generates the idempotency key once per user intent and reuses it on all retries:

```javascript
// Frontend JavaScript — leave submission with idempotency

async function submitLeave(leaveData) {
    // Generate a stable key for THIS leave submission attempt
    // Store it in sessionStorage so retries use the same key
    let idempotencyKey = sessionStorage.getItem('current-leave-submission-key');
    if (!idempotencyKey) {
        idempotencyKey = crypto.randomUUID();
        sessionStorage.setItem('current-leave-submission-key', idempotencyKey);
    }

    try {
        const response = await fetch('/api/v1/leaves', {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
                'Idempotency-Key': idempotencyKey,  // same key on every retry
                'Authorization': `Bearer ${authToken}`
            },
            body: JSON.stringify(leaveData)
        });

        if (response.ok) {
            // Success — clear the key so the next submission gets a fresh one
            sessionStorage.removeItem('current-leave-submission-key');
            return await response.json();
        }

        // Handle error — the key is still in sessionStorage for retry
        throw new Error(`Submission failed: ${response.status}`);

    } catch (error) {
        // Network error — user can retry and the same key will be used
        throw error;
    }
}
```

## Idempotency Variant 5 — Conditional Updates With Optimistic Locking

Some operations need a weaker form of idempotency — not full deduplication, but protection against out-of-order or stale updates. This is achieved through conditional updates that include a version or timestamp check.

```go
// leave/handlers/conditional_update.go

// This update includes a condition that makes it safe to retry
// but also protects against applying stale updates out of order

type UpdateLeaveStatusCommand struct {
    LeaveID         string
    ExpectedStatus  string    // the status we expect the leave to be in currently
    NewStatus       string    // the status we want to transition to
    UpdatedBy       string
    Version         int       // optimistic lock version — must match current DB version
}

func (h *LeaveCommandHandler) HandleStatusUpdate(ctx context.Context, cmd UpdateLeaveStatusCommand) error {
    result := h.db.WithContext(ctx).
        Model(&Leave{}).
        Where("id = ? AND status = ? AND version = ?",
            cmd.LeaveID, cmd.ExpectedStatus, cmd.Version).
        Updates(map[string]interface{}{
            "status":     cmd.NewStatus,
            "updated_by": cmd.UpdatedBy,
            "updated_at": time.Now(),
            "version":    gorm.Expr("version + 1"),
        })

    if result.Error != nil {
        return result.Error
    }

    if result.RowsAffected == 0 {
        // Either the leave does not exist, or the status is different from expected,
        // or the version has changed (concurrent modification)
        // Check which case it is:
        var leave Leave
        if err := h.db.Where("id = ?", cmd.LeaveID).First(&leave).Error; err != nil {
            return fmt.Errorf("leave not found: %s", cmd.LeaveID)
        }

        if leave.Status == cmd.NewStatus {
            // Already in the target status — this is an idempotent retry, success
            return nil
        }

        if leave.Status != cmd.ExpectedStatus {
            return fmt.Errorf("status conflict: expected %s, found %s",
                cmd.ExpectedStatus, leave.Status)
        }

        // Version mismatch — concurrent modification
        return fmt.Errorf("version conflict: expected version %d, found %d",
            cmd.Version, leave.Version)
    }

    return nil
}
```

## The Idempotency Key Cleanup Worker

Idempotency key records accumulate over time. They serve no purpose after the retry window has closed — typically 24 hours for HTTP requests, 7 days for Kafka messages. A cleanup worker removes expired records to prevent the table from growing indefinitely.

```go
// idempotency/cleanup.go

type CleanupWorker struct {
    db              *gorm.DB
    cleanupInterval time.Duration
    batchSize       int
    logger          *slog.Logger
}

func (w *CleanupWorker) Run(ctx context.Context) error {
    ticker := time.NewTicker(w.cleanupInterval)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            w.cleanup(ctx)
        }
    }
}

func (w *CleanupWorker) cleanup(ctx context.Context) {
    // Clean idempotency keys
    keyResult := w.db.WithContext(ctx).
        Where("expires_at < ? AND status IN ?", time.Now(), []string{StatusCompleted, StatusFailed}).
        Limit(w.batchSize).
        Delete(&Key{})

    if keyResult.RowsAffected > 0 {
        w.logger.Info("cleaned up expired idempotency keys", "count", keyResult.RowsAffected)
    }

    // Clean processed message records
    msgResult := w.db.WithContext(ctx).
        Where("expires_at < ?", time.Now()).
        Limit(w.batchSize).
        Delete(&ProcessedMessage{})

    if msgResult.RowsAffected > 0 {
        w.logger.Info("cleaned up expired processed message records", "count", msgResult.RowsAffected)
    }
}
```

## The Relationship Between Idempotency and the Other Patterns

By this point in your learning journey, you have studied the Outbox Pattern, the Transactional Inbox Pattern, the SAGA Pattern, the Dead Letter Queue Pattern, and now the Idempotency Pattern. It is worth stepping back and showing exactly how these patterns depend on each other, because understanding their relationships is what lets you compose them correctly.

The Outbox Pattern guarantees that an event published to Kafka will be delivered at least once. This guarantee is what makes downstream consumers need idempotency — because "at least once" means "possibly more than once." Without idempotency in consumers, the Outbox Pattern would cause duplicate processing.

The Transactional Inbox Pattern is itself an idempotency mechanism for Kafka consumers. It uses the `ON CONFLICT DO NOTHING` approach to ensure a message is processed exactly once, even if Kafka delivers it multiple times. The Kafka Deduplicator we built in this guide is the same concept applied at the handler level rather than the inbox table level.

The SAGA Pattern relies on idempotency for its retry mechanism to be safe. When the orchestrator retries a failed step, it must be guaranteed that the participant will not perform the business action twice. Without idempotent SAGA commands, retries cause duplicate side effects — duplicate approvals, duplicate balance deductions, duplicate notifications.

The Dead Letter Queue Pattern handles the case where idempotency and retries are not enough — where a message has a permanent failure that no number of retries will fix. The DLQ is the final safety net after idempotency and retry mechanisms have been given their full opportunity.

```
HOW THE PATTERNS FIT TOGETHER
──────────────────────────────

  Outbox Pattern:        guarantees at-least-once publish to Kafka
                              │
                              │ "at-least-once" creates the need for:
                              ▼
  Idempotency Pattern:   ensures exactly-once processing despite
                         at-least-once delivery
                              │
                              │ enables safe retries, which means:
                              ▼
  SAGA Pattern:          can retry failed steps without
                         duplicate business side effects
                              │
                              │ retries eventually exhaust, so:
                              ▼
  Dead Letter Queue:     captures permanently unprocessable messages

  Transactional Inbox:   combines inbox durability + idempotency
                         in one unified mechanism for Kafka consumers
```

## The Cardinal Rules of Idempotency

There are five rules about idempotency that every engineer in this system must understand and follow. Violating any of them creates the kind of bug that is incredibly hard to diagnose in production because it only manifests under specific timing conditions.

The first rule is that idempotency keys must be generated by the caller before the first attempt and reused on every retry. A key generated by the server on receipt cannot provide deduplication because each retry generates a different key. A key that changes between retries provides no protection.

The second rule is that the idempotency check and the business operation must be atomic. If you check for duplicates before the transaction and then execute the operation inside the transaction, there is a race condition window between the check and the operation. Two concurrent retries can both pass the check and both execute the operation. Use database transactions that include both the duplicate check and the business write.

The third rule is that different operations with different payloads must not share an idempotency key. If a key is presented with a different request payload than what was originally stored, that is a client bug — not a retry. The server must reject this with a clear error. This is why we hash the request payload and store it alongside the key.

The fourth rule is that idempotency keys have an expiration window. They are not permanent. A key submitted 30 days ago should not still be blocking a new operation that happens to generate the same key by collision or user error. Set a retention period appropriate to the operation's retry window — typically 24 hours for interactive requests and 7 days for background jobs.

The fifth rule is that a failed operation should allow retry. If the business handler returns an error, the idempotency record must be marked as FAILED or deleted so the caller can retry. Storing a FAILED status and never allowing retry defeats the purpose of retries entirely. Idempotency protects against duplicate successes, not against legitimate retries after failures.

```
THE FIVE RULES — Summary
──────────────────────────────────────────────────────────────────────────
Rule 1: CALLER GENERATES KEY BEFORE FIRST ATTEMPT, REUSES ON ALL RETRIES
        ✓ Key stored in client before request sent, reused on every retry
        ✗ Server generates key from request content at receipt time

Rule 2: CHECK AND OPERATION ARE ATOMIC (SAME DB TRANSACTION)
        ✓ INSERT idempotency_keys + business write in one transaction
        ✗ Check for key existence, then open new transaction for the write

Rule 3: KEY + PAYLOAD MUST MATCH (REJECT CONFLICTING REQUESTS)
        ✓ Hash request payload, compare to stored hash, reject mismatch
        ✗ Allow same key with different payload (ambiguous intent)

Rule 4: KEYS EXPIRE AFTER RETRY WINDOW
        ✓ expires_at = now + 24 hours for HTTP, 7 days for Kafka
        ✗ Permanent records that never get cleaned up

Rule 5: FAILED OPERATIONS ALLOW RETRY
        ✓ Handler error → mark key as FAILED or delete it → retry allowed
        ✗ Handler error → key stays COMPLETED → all retries blocked forever
──────────────────────────────────────────────────────────────────────────
```

Idempotency is not glamorous. It does not appear in architecture diagrams. It does not get mentioned in system design interviews as often as it should. But in a production distributed system, it is the quiet foundation that makes everything else trustworthy. Every retry you implement, every at-least-once delivery guarantee you rely on, every SAGA step you let the orchestrator retry — all of it depends on idempotency being correct. Without it, your distributed system is a system that works correctly only when nothing goes wrong. With it, your system remains correct under exactly the conditions where distributed systems most need to be correct — when the network misbehaves, when services crash, and when users lose patience and tap the button again.
