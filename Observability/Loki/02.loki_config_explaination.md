# Understanding Loki: A Complete Configuration Guide for Microservice Distributed Logging

---

## Chapter 1 — What Problem Does Loki Solve?

Imagine your HR360 system is running ten microservices simultaneously — `employee-svc`, `payroll-svc`, `auth-svc`, `notification-svc`, and so on. Each of them is printing log lines every second. Now suppose something goes wrong at 3:47 AM and a payroll transaction fails. Without a centralized logging system, you would have to SSH into each individual container, open its log file, and manually search through thousands of lines hoping to find the error. This is neither scalable nor practical.

Loki is a **log aggregation system** built by Grafana Labs. Its job is to collect all log lines from all your microservices, store them efficiently, and let you query them in one place using a query language called **LogQL**. Think of Loki the same way you think of a library's catalogue system — the books (log lines) are physically stored on shelves (disk), but the catalogue (index) lets you find any book instantly by searching for its label (log labels like `service=payroll-svc` or `level=error`).

What makes Loki architecturally different from tools like Elasticsearch is a deliberate design choice: **Loki does not index the content of log lines**. It only indexes the labels you attach to a log stream. This makes it dramatically cheaper to operate, because indexing full text requires enormous amounts of RAM and CPU. Instead, when you search for a word inside a log line, Loki first uses the label index to narrow down which compressed files to open, and then scans through those files for your search term. This is slow for full-text search but fast enough for the way engineers actually use logs — "show me all errors from payroll-svc in the last hour."

## Chapter 2 — The Journey of a Single Log Line

Before reading the configuration, you must understand the physical journey a single log line takes from your Go service to Grafana. Knowing this journey makes every configuration option obvious in purpose.

```
┌─────────────────────────────────────────────────────────────────────┐
│                    HR360 Microservices Universe                     │
│                                                                     │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐               │
│  │ employee-svc │  │  payroll-svc │  │   auth-svc   │               │
│  │  (Go/Zap)    │  │  (Go/Zap)    │  │  (Go/Zap)    │               │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘               │
│         │                 │                  │                      │
│         └─────────────────┼──────────────────┘                      │
│                           │  stdout / log files                     │
│                           ▼                                         │
│                  ┌─────────────────┐                                │
│                  │    PROMTAIL     │   (the log collector agent)    │
│                  │                 │                                │
│                  │  Reads logs →   │                                │
│                  │  Attaches labels│                                │
│                  │  Ships to Loki  │                                │
│                  └────────┬────────┘                                │
│                           │  HTTP POST (batched log lines)          │
│                           ▼                                         │
│          ┌────────────────────────────────────┐                     │
│          │               LOKI                 │                     │
│          │                                    │                     │
│          │  ┌──────────────┐                  │                     │
│          │  │  DISTRIBUTOR │ ← receives batch │                     │
│          │  └──────┬───────┘                  │                     │
│          │         │ validates & routes       │                     │
│          │         ▼                          │                     │
│          │  ┌──────────────┐                  │                     │
│          │  │   INGESTER   │ ← holds in RAM   │                     │
│          │  │   + WAL      │  writes WAL first│                     │
│          │  └──────┬───────┘                  │                     │
│          │         │ flush after idle/full    │                     │
│          │         ▼                          │                     │
│          │  ┌──────────────┐                  │                     │
│          │  │   STORAGE    │ ← compressed     │                     │
│          │  │  (chunks on  │   .gz files      │                     │
│          │  │  filesystem) │   on disk        │                     │
│          │  └──────┬───────┘                  │                     │
│          │         │                          │                     │
│          │  ┌──────▼───────┐                  │                     │
│          │  │   COMPACTOR  │ ← merges small   │                     │
│          │  │              │   index files,   │                     │
│          │  │              │   enforces TTL   │                     │
│          │  └──────────────┘                  │                     │
│          └────────────────────────────────────┘                     │
│                           │  LogQL queries                          │
│                           ▼                                         │
│                  ┌─────────────────┐                                │
│                  │    GRAFANA      │   (the dashboard & query UI)   │
│                  └─────────────────┘                                │
└─────────────────────────────────────────────────────────────────────┘
```

The journey has five distinct phases. First, your Go service (using `zap`) writes a structured JSON log line to stdout. Second, Promtail — running as a sidecar or DaemonSet — tails that output, attaches labels like `{service="payroll-svc", env="production"}`, and ships batches of these labeled log lines to Loki's HTTP endpoint. Third, Loki's **Distributor** receives the batch and validates it — checking timestamps, rate limits, label cardinality. Fourth, the **Ingester** holds the log lines in RAM as open "chunks" and simultaneously writes them to the Write-Ahead Log (WAL) on disk for crash safety. Fifth, once a chunk is full or has been idle for a while, it is compressed and flushed to the **filesystem as a chunk file**, and the **Compactor** periodically merges the index entries and enforces your retention policy.

## Chapter 3 — Loki's Deployment Modes

Loki can be deployed in three distinct architectural modes, and understanding which mode you are in determines how you read the entire config file.

```
┌──────────────────────────────────────────────────────────────────┐
│                    THREE DEPLOYMENT MODES                        │
│                                                                  │
│  MODE 1: MONOLITHIC (Single Process)                             │
│  ┌──────────────────────────────────────┐                        │
│  │           One Loki Binary            │                        │
│  │  ┌────────┐ ┌─────────┐ ┌────────┐   │                        │
│  │  │Distrib.│ │Ingester │ │Querier │   │                        │
│  │  └────────┘ └─────────┘ └────────┘   │                        │
│  │  ┌────────┐ ┌─────────┐              │                        │
│  │  │Compact.│ │  Ruler  │              │                        │
│  │  └────────┘ └─────────┘              │                        │
│  └──────────────────────────────────────┘                        │
│  ← Your current setup. Perfect for HR360 single-node.            │
│                                                                  │
│  MODE 2: SIMPLE SCALABLE (2-3 Process Groups)                    │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐                      │
│  │  Write   │   │  Read    │   │ Backend  │                      │
│  │  Group   │   │  Group   │   │  Group   │                      │
│  └──────────┘   └──────────┘   └──────────┘                      │
│  ← Useful when reads and writes have different scaling needs.    │
│                                                                  │
│  MODE 3: MICROSERVICES (Each component is its own container)     │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐                    │
│  │Dist. │ │Inges.│ │Query │ │Compa.│ │Ruler │                    │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘                    │
│  ← For very large scale. Overkill for most teams.                │
└──────────────────────────────────────────────────────────────────┘
```

Your current configuration runs in **monolithic mode**, which means all of Loki's internal components — the distributor, the ingester, the querier, the compactor, and the ruler — run inside one single process. This is not a limitation; it is the correct and recommended approach for a single-team, single-node HR system. You get the full power of Loki without the operational complexity of coordinating multiple container groups.

## Chapter 4 — Line-by-Line Configuration Walkthrough

Now let us walk through your `loki-config.yml` from top to bottom, explaining exactly what each section does and why it is configured the way it is.

### 4.1 — `auth_enabled: false`

```yaml
auth_enabled: false
```

Loki supports multi-tenancy, which means a single Loki cluster can serve multiple completely isolated teams. When `auth_enabled` is `true`, every request to Loki must carry an `X-Scope-OrgID` HTTP header identifying which tenant's data is being written or read. This is useful for a SaaS company running one Loki for twenty customer teams who must never see each other's logs.

For HR360, you have one team and one system. Setting this to `false` tells Loki to treat all incoming data as belonging to a single implicit tenant called `fake`. This simplifies your Promtail configuration because Promtail does not need to set any tenant header. If you ever grow to multiple departments with strict log isolation requirements, you would flip this to `true` and configure Promtail with `tenant_id` labels.

---

### 4.2 — `server` block

```yaml
server:
  http_listen_port: 3100
  grpc_listen_port: 9096
  log_level: info
```

This block configures the two network listeners that Loki opens when it starts. The HTTP listener on port **3100** is the primary interface — this is where Promtail sends log lines, where Grafana sends LogQL queries, and where Loki exposes its `/ready`, `/metrics`, and `/loki/api/v1/...` endpoints. The gRPC listener on port **9096** is used for internal component communication in clustered deployments. Even in monolithic mode, keeping it open is harmless and is required if you ever scale out.

The `log_level: info` controls how verbose Loki itself is in its own operational logs — not your application logs. `info` is the right level for production; `debug` would produce enormous amounts of Loki-internal diagnostic output that is useful when troubleshooting Loki itself but otherwise just noise.

---

### 4.3 — `common` block

```yaml
common:
  instance_addr: 127.0.0.1
  path_prefix: /loki/data
  storage:
    filesystem:
      chunks_directory: /loki/data/chunks
      rules_directory: /loki/data/rules
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory
```

The `common` block is a convenience feature introduced in newer versions of Loki that lets you set shared defaults that apply across multiple subsystems. Without it, you would have to repeat the same filesystem paths and ring configuration in four or five different places.

The `instance_addr: 127.0.0.1` tells Loki which IP address to advertise when registering itself in the internal ring (the ring is a data structure that tracks which Loki nodes own which data ranges). Since you are running a single node, it registers itself at localhost.

The `path_prefix: /loki/data` sets the root directory for all of Loki's on-disk data. All the specific directories you see elsewhere in the config — chunks, WAL, index, compactor — are children of this path. When Loki runs inside Docker, this path is inside the container and must be mapped to a Docker named volume in your `docker-compose.yml` to survive container restarts.

The `replication_factor: 1` is appropriate for a single-node setup. In a cluster with replication_factor 3, each log stream would be written to three different ingesters for redundancy. With one node, there is only one ingester to write to, so replication_factor of 1 is the only valid value.

The `ring.kvstore.store: inmemory` tells Loki's internal ring system to use in-memory state rather than an external key-value store like etcd or Consul. In a real cluster, all Loki nodes would need to share ring state through an external KV store. Since you have one node, in-memory is both simpler and perfectly correct.

---

### 4.4 — `query_range` block

```yaml
query_range:
  results_cache:
    cache:
      embedded_cache:
        enabled: true
        max_size_mb: 100
```

When a Grafana dashboard loads and sends the same query for "error logs in the last 6 hours" repeatedly as the user refreshes the page, it would be wasteful to re-scan the same compressed chunk files every time. The query range cache stores the results of recently executed queries in memory. The next time the same (or overlapping) query arrives, Loki serves it from the cache without touching disk. The `max_size_mb: 100` cap ensures this cache does not consume excessive RAM. For a busy dashboard environment, you could raise this to 250–500 MB.

---

### 4.5 — `schema_config` block

```yaml
schema_config:
  configs:
    - from: 2024-01-01
      store: tsdb
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h
```

This is one of the most important blocks in the entire configuration, and it is also the one most people find confusing at first. The schema config defines how Loki stores and indexes your data. Think of it like a database migration history — it tells Loki "from this date forward, use this storage format."

```
Timeline of schema changes (example):
──────────────────────────────────────────────────────────────────
2020-01-01          2022-06-01          2024-01-01
     │                   │                   │
     ▼                   ▼                   ▼
  boltdb +            boltdb-shipper       tsdb + v13
  v11 schema          + v12 schema         ← You are here
  (old, deprecated)   (transitional)       (current best)
──────────────────────────────────────────────────────────────────
```

The `store: tsdb` tells Loki to use the **TSDB index format** for storing label metadata. TSDB stands for Time Series Database and is the same index format used by Prometheus. It is the modern, recommended format in Loki 3.x. The `schema: v13` is the specific schema version that defines how chunks are laid out and referenced — v13 is the latest and most efficient version. The `index.period: 24h` means that Loki creates a new index file every 24 hours; this makes it easy to delete old data simply by dropping old index files, which is how retention works.

---

### 4.6 — `ingester` block

```yaml
ingester:
  wal:
    enabled: true
    dir: /loki/data/wal
  lifecycler:
    ring:
      kvstore:
        store: inmemory
      replication_factor: 1
  chunk_idle_period: 5m
  chunk_retain_period: 30s
  max_chunk_age: 1h
  chunk_target_size: 1048576
```

The ingester is the component that receives log lines from the distributor, holds them in RAM as open chunks, and flushes them to disk once certain conditions are met. Understanding the ingester requires understanding what a **chunk** is.

A chunk is a compressed, in-memory buffer of log lines for one specific label set (one "stream"). For example, all log lines from `{service="payroll-svc", level="error"}` accumulate in one chunk. When the chunk meets a flush condition, it is compressed and written to disk as a `.gz` file.

```
                       INGESTER MEMORY
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  Stream: {service="employee-svc", level="info"}         │
│  ┌──────────────────────────────────────────────┐       │
│  │ chunk: [log1, log2, log3, ...log_n]          │       │
│  │ size: 850KB / 1MB target                     │       │
│  │ last write: 2 minutes ago                    │       │
│  └──────────────────────────────────────────────┘       │
│                                                         │
│  Stream: {service="payroll-svc", level="error"}         │
│  ┌──────────────────────────────────────────────┐       │
│  │ chunk: [err1, err2]                          │       │
│  │ size: 12KB / 1MB target                      │       │
│  │ last write: 6 minutes ago  ← IDLE FLUSH!     │       │
│  └──────────────────────────────────────────────┘       │
│                                                         │
│  WAL (Write-Ahead Log on disk):                         │
│  /loki/data/wal/  ← mirror of everything above          │
│                      written BEFORE RAM acknowledgement │
└─────────────────────────────────────────────────────────┘
```

The **WAL** (`wal.enabled: true`) is the most critical production safety feature. When Loki receives a log line, it does two things almost simultaneously: it writes the line to the WAL file on disk AND adds it to the in-memory chunk. Only after the WAL write succeeds does Loki acknowledge receipt to Promtail. This means if the Loki process crashes at 3:47 AM, no log lines are lost — on restart, Loki replays the WAL and reconstructs the in-memory chunks exactly as they were.

The `chunk_idle_period: 5m` means: if no new log line has arrived for a particular stream in 5 minutes, flush that chunk to disk now. This ensures that low-traffic services (like a rarely-triggered notification service) eventually persist their logs to disk rather than sitting in RAM indefinitely. The `max_chunk_age: 1h` is the absolute maximum — regardless of idle time or size, any chunk older than 1 hour is flushed. The `chunk_target_size: 1048576` (1 MB) is the target compressed size; once a chunk reaches this size it is also flushed. Larger chunks compress more efficiently and create fewer files on disk.

### 4.7 — `storage_config` block

```yaml
storage_config:
  tsdb_shipper:
    active_index_directory: /loki/data/index
    cache_location: /loki/data/index_cache
  filesystem:
    directory: /loki/data/chunks
```

While the `common` block sets defaults, the `storage_config` block provides the specific operational paths for the TSDB index shipper. The `active_index_directory` is where Loki keeps the TSDB index files that are currently being written to — these are "hot" index files for recent data. The `cache_location` is where Loki caches downloaded or decompressed index segments to speed up repeated queries. The `filesystem.directory` points to where the compressed chunk files are stored on disk.

```
/loki/data/
├── wal/          ← WAL files (crash recovery)
├── chunks/       ← Compressed chunk files (the actual log data)
├── index/        ← Active TSDB index files (hot, recent)
├── index_cache/  ← Cached decompressed index segments (query speed)
├── compactor/    ← Compactor working space
└── rules/        ← Alerting rule files
```

---

### 4.8 — `limits_config` block

```yaml
limits_config:
  reject_old_samples: true
  reject_old_samples_max_age: 168h
  ingestion_rate_mb: 16
  ingestion_burst_size_mb: 32
  max_query_series: 5000
  max_query_lookback: 720h
  retention_period: 720h
```

The limits config is your system's contract for what is acceptable. `reject_old_samples: true` with `reject_old_samples_max_age: 168h` means Loki will refuse any log line whose timestamp is more than 7 days in the past. This protects you from a clock-skewed service that starts sending ancient logs and pollutes your recent log views. If a container restarts and tries to re-send buffered logs from a week ago, Loki will reject them.

The `ingestion_rate_mb: 16` and `ingestion_burst_size_mb: 32` implement a token-bucket rate limiter. Think of a bucket that fills at 16 MB per second and can hold up to 32 MB total. Incoming log data consumes from this bucket. If a service suddenly starts logging at 100 MB/s (perhaps during a bug that causes an infinite log loop), Loki will throttle and reject the excess, protecting itself from being overwhelmed. In production, you should tune these values based on your actual log volume — if `employee-svc` regularly peaks at 20 MB/s, raise the limit.

The `retention_period: 720h` (30 days) is your storage policy. Log data older than 30 days is automatically deleted by the compactor. This is the primary mechanism controlling how much disk space Loki consumes over time. If you need to comply with regulations requiring longer log retention, increase this value and ensure your disk has sufficient capacity.

---

### 4.9 — `compactor` block

```yaml
compactor:
  working_directory: /loki/data/compactor
  compaction_interval: 10m
  retention_enabled: true
  retention_delete_delay: 2h
```

The compactor is a background worker that performs two jobs on a schedule. Its first job is **index compaction** — over time, many small TSDB index files accumulate (one per 24-hour period, plus smaller incremental files). The compactor merges these into fewer, larger files that can be read more efficiently during queries. This is analogous to how databases periodically run VACUUM or OPTIMIZE TABLE operations.

Its second job is **retention enforcement**. Every `compaction_interval` (10 minutes in your config), the compactor scans the index for chunk files whose timestamps are older than `retention_period` (30 days) and marks them for deletion. The `retention_delete_delay: 2h` means that after a chunk is marked for deletion, it waits 2 hours before actually being removed from disk. This grace period is a safety net — if you accidentally change your retention period to something too aggressive, you have a 2-hour window to notice the mistake and stop the deletion before data is permanently lost.

---

### 4.10 — `ruler` block

```yaml
ruler:
  storage:
    type: local
    local:
      directory: /loki/data/rules
  rule_path: /loki/data/rules
  ring:
    kvstore:
      store: inmemory
  enable_api: true
```

The ruler is Loki's alerting engine. Just as Prometheus has alerting rules written in PromQL, Loki has alerting rules written in LogQL. The ruler periodically evaluates these rules against your log data and can fire alerts when conditions are met. For example, you could write a rule that fires a `PayrollErrorRate` alert if the count of `level=error` logs from `payroll-svc` exceeds 50 per minute.

With `enable_api: true`, you can push and read rules via the Loki HTTP API rather than only managing them as files on disk. With `storage.type: local`, the rules are stored as YAML files in `/loki/data/rules` — a directory inside your Docker volume. In a production clustered setup, you would use an object store (S3, GCS) here so all ruler instances share the same rule files.

## Chapter 5 — Configuring Loki for a Multi-Service Environment

Here is how to structure your Docker Compose setup to wire everything together correctly. The key insight is that Loki, Promtail, and Grafana each need to be on the same Docker network so they can communicate by service name rather than IP address.

```
┌─────────────────────────────────────────────────────────────────────┐
│                    docker-compose.yml Network Layout                │
│                                                                     │
│  Network: hr360_monitoring                                          │
│                                                                     │
│  ┌────────────────┐    HTTP :3100    ┌─────────────────┐            │
│  │   PROMTAIL     │ ───────────────► │      LOKI       │            │
│  │                │                  │                 │            │
│  │  Scrapes:      │                  │  Stores logs    │            │
│  │  - /var/log/   │                  │  Answers queries│            │
│  │  - Docker sock │                  │                 │            │
│  └────────────────┘                  └────────┬────────┘            │
│                                               │                     │
│                                    HTTP :3100 │ LogQL queries       │
│                                               ▼                     │
│                                   ┌─────────────────┐               │
│                                   │     GRAFANA     │               │
│                                   │                 │               │
│                                   │  Datasource:    │               │
│                                   │  http://loki:   │               │
│                                   │  3100           │               │
│                                   └─────────────────┘               │
│                                                                     │
│  Your Microservices (on hr360_app network, bridged to monitoring):  │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐                 │

│         │                │                │                         │
│         └────────────────┴────────────────┘                         │

│              Docker log driver / /var/lib/docker/containers/        │

│                          ▼                                          │
│                     PROMTAIL reads these                            │
└─────────────────────────────────────────────────────────────────────┘
```

A production-ready `docker-compose.yml` for the monitoring stack should look like this:

```yaml
# docker-compose.monitoring.yml

version: "3.9"

networks:
  hr360_monitoring:
    driver: bridge

volumes:
  loki_data:
  grafana_data:

services:

  loki:
    image: grafana/loki:3.0.0
    container_name: hr360_loki
    restart: unless-stopped
    ports:
      - "3100:3100"
    volumes:
      - ./monitoring/loki/loki-config.yml:/etc/loki/local-config.yaml:ro
      - loki_data:/loki/data
    command: -config.file=/etc/loki/local-config.yaml
    networks:
      - hr360_monitoring
    healthcheck:
      test: ["CMD-SHELL", "wget --quiet --tries=1 --spider http://localhost:3100/ready || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 5

  promtail:
    image: grafana/promtail:3.0.0
    container_name: hr360_promtail
    restart: unless-stopped
    volumes:
      - ./monitoring/promtail/promtail-config.yml:/etc/promtail/config.yaml:ro
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro
    command: -config.file=/etc/promtail/config.yaml
    depends_on:
      loki:
        condition: service_healthy
    networks:
      - hr360_monitoring

  grafana:
    image: grafana/grafana:11.0.0
    container_name: hr360_grafana
    restart: unless-stopped
    ports:
      - "3000:3000"
    volumes:
      - grafana_data:/var/lib/grafana
      - ./monitoring/grafana/provisioning:/etc/grafana/provisioning:ro
    environment:
      - GF_SECURITY_ADMIN_PASSWORD=your_secure_password
      - GF_USERS_ALLOW_SIGN_UP=false
    depends_on:
      loki:
        condition: service_healthy
    networks:
      - hr360_monitoring
```

## Chapter 6 — Promtail Configuration for HR360

Promtail is the agent that ships logs to Loki. Its configuration is equally important because it determines what labels are attached to each log stream. Labels are the primary way you will filter and search your logs in Grafana.

```yaml
# monitoring/promtail/promtail-config.yml

server:
  http_listen_port: 9080
  grpc_listen_port: 0

# Tells Promtail where to store its position files
# (which log line it last read, so restarts don't re-send old lines)
positions:
  filename: /tmp/positions.yaml

clients:
  - url: http://loki:3100/loki/api/v1/push
    # "loki" here is the Docker service name — Docker DNS resolves it

scrape_configs:

  # This job discovers all running Docker containers automatically
  - job_name: docker_containers
    docker_sd_configs:
      - host: unix:///var/run/docker.sock
        refresh_interval: 5s
        filters:
          - name: status
            values: ["running"]

    relabel_configs:
      # Extract the container name and use it as the "service" label
      - source_labels: ["__meta_docker_container_name"]
        regex: "/(.*)"
        target_label: "service"

      # Attach the Docker image name as a label
      - source_labels: ["__meta_docker_container_image"]
        target_label: "image"

      # Attach the compose project name (useful when you have
      # multiple compose stacks running on the same host)
      - source_labels: ["__meta_docker_container_label_com_docker_compose_project"]
        target_label: "compose_project"

    pipeline_stages:
      # Parse the JSON structured logs from your Go/Zap services
      - json:
          expressions:
            level: level
            msg: msg
            ts: ts
            service: service
            trace_id: trace_id

      # Promote the "level" field from inside the JSON body
      # to become a proper Loki stream label.
      # This lets you query: {service="payroll-svc", level="error"}
      - labels:
          level:
          service:

      # Parse the timestamp from Go's Zap output so Loki
      # records the correct log time rather than arrival time
      - timestamp:
          source: ts
          format: Unix
```

## Chapter 7 — Label Strategy for Microservices

The most important operational decision when using Loki is **which fields to make labels** versus which fields to leave inside the log body. This decision has a direct impact on Loki's performance and cost.

```
┌─────────────────────────────────────────────────────────────────┐
│                   LABEL CARDINALITY SPECTRUM                    │
│                                                                 │
│  LOW CARDINALITY          │         HIGH CARDINALITY            │
│  (Safe as labels)         │    (Keep inside log body)           │
│                           │                                     │
│  service=employee-svc     │    user_id=29847265                 │
│  level=error              │    request_id=abc-def-ghi-jkl       │
│  env=production           │    ip_address=192.168.1.47          │
│  host=server-1            │    employee_name=John Doe           │
│                           │                                     │
│  ← A few dozen possible   │    ← Millions of possible values    │
│    values total              across all log lines               │
│                                                                 │
│  RULE: If the number of unique values for a field exceeds       │
│  ~50-100, do NOT make it a label. Use LogQL's line_format       │
│  or json parser to search inside the log body instead.          │
└─────────────────────────────────────────────────────────────────┘
```

For HR360, a sensible label strategy for each service stream is:

- `{service="employee-svc", level="info", env="production"}` — good
- `{service="payroll-svc", level="error", env="production"}` — good
- `{service="auth-svc", user_id="12345"}` — **bad**: user_id is high-cardinality

When you need to find logs for a specific user, you do not filter by label. Instead, you first filter by the low-cardinality labels to narrow the data set, and then use a LogQL JSON filter to search the body: `{service="auth-svc"} | json | user_id = "12345"`.

## Chapter 8 — Querying Your Logs with LogQL

Once logs are flowing into Loki, you query them using LogQL. Here are the essential patterns for a microservices environment.

```logql
# 1. Show all logs from a specific service
{service="payroll-svc"}

# 2. Filter to only error-level logs across all services
{level="error"}

# 3. Filter errors from a specific service
{service="payroll-svc", level="error"}

# 4. Search for a specific error message inside the log body
{service="payroll-svc"} |= "failed to process payroll"

# 5. Parse JSON and filter by a specific field value
{service="auth-svc"} | json | user_id = "12345"

# 6. Count error rate per minute for each service
sum by (service) (
  rate({level="error"}[1m])
)

# 7. Show logs with a specific trace_id across ALL services
# (distributed tracing correlation — very powerful)
{env="production"} | json | trace_id = "abc-def-ghi"
```

The last query is particularly valuable in a microservices system. When a user reports that a payroll transaction failed, you can take the `trace_id` from any one service's log and instantly see the entire chain of log lines across `auth-svc`, `payroll-svc`, `notification-svc`, and any other service that participated in that request — all in chronological order.

## Chapter 9 — Alerting Rules with the Ruler

The ruler lets you write LogQL-based alerting rules that fire when error conditions are detected in your logs. Store these in `/loki/data/rules/fake/rules.yml` (the `fake` directory corresponds to the implicit tenant name when `auth_enabled: false`).

```yaml
# /loki/data/rules/fake/rules.yml

groups:
  - name: hr360_alerts
    rules:

      # Alert if payroll service errors exceed 10 per minute
      - alert: PayrollServiceHighErrorRate
        expr: |
          sum(rate({service="payroll-svc", level="error"}[1m])) > 10
        for: 2m
        labels:
          severity: critical
          team: backend
        annotations:
          summary: "Payroll service is experiencing high error rate"
          description: "More than 10 errors/min detected for {{ $labels.service }}"

      # Alert if any service has been silent for more than 5 minutes
      # (could indicate the service crashed and stopped logging entirely)
      - alert: ServiceLogsSilent
        expr: |
          absent_over_time({service=~"employee-svc|payroll-svc|auth-svc"}[5m])
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "No logs received from a critical service"
```

## Summary

Loki's configuration, read holistically, tells a single coherent story: logs arrive at the **distributor**, get written to RAM and the **WAL** by the **ingester**, get flushed to compressed **chunk files** on the filesystem, get indexed by the **TSDB index** (rotated daily), get compacted and garbage-collected by the **compactor** (enforcing 30-day retention), and get queried through the **querier** (accelerated by the results cache). The **ruler** watches for alerting conditions in the background. Promtail sits outside Loki entirely, reading your microservice container logs and shipping them with the right labels. Grafana sits on the query side, sending LogQL queries and rendering dashboards.

Every configuration value in your file maps directly to one of these pipeline stages. Nothing in that file is arbitrary.
