# Understanding Promtail: The Log Collector for Microservices

---

## Chapter 1 — What Is Promtail and Why Does It Exist?

If Loki is the library that stores and indexes your logs, then Promtail is the librarian who physically walks around collecting the books and bringing them to the library. Your Go microservices do not know that Loki exists — they simply write their structured JSON log lines to standard output (stdout) and forget about them. Promtail is the dedicated agent that watches those outputs, understands what it is reading, enriches the data with contextual labels, and ships everything to Loki in efficient batches.

This separation of concerns is deliberate and elegant. Your application code has one job: emit good structured logs. Promtail has one job: collect and ship those logs. Neither needs to know the other's internal details. This means you can change your logging destination from Loki to a different backend tomorrow, and your application code does not change at all — you only reconfigure Promtail.

In the Docker environment, Promtail runs as its own container. It is given read access to the Docker daemon's socket file and to the directory where Docker writes container log files on the host filesystem. Using these two pieces of access, Promtail can automatically discover every running container, read its logs, and ship them to Loki — without you having to manually tell Promtail about each service individually.

```
┌─────────────────────────────────────────────────────────────────────┐
│                  THE PROMTAIL MENTAL MODEL                          │
│                                                                     │
│  Your Go Service                                                    │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  zap.Info("payroll processed",                               │   │
│  │    zap.String("employee_id", "EMP-007"),                     │   │
│  │    zap.Float64("amount", 85000.00),                          │   │

│  │  )                                                           │   │
│  └──────────────────────────────┬───────────────────────────────┘   │
│                                 │ writes to stdout                  │
│                                 ▼                                   │
│  Docker captures stdout and writes to host filesystem:              │
│  /var/lib/docker/containers/<id>/<id>-json.log                      │
│  {"log":"{\"level\":\"info\",\"msg\":\"payroll processed\",...}\n", │
│   "stream":"stdout",                                                │
│   "time":"2024-01-15T03:47:00Z"}                                    │
│                                 │                                   │
│                                 │ Promtail reads this file          │
│                                 ▼                                   │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │                        PROMTAIL                               │  │
│  │                                                               │  │
│  │  1. Unwrap Docker JSON envelope                               │  │
│  │  2. Parse inner Zap JSON body                                 │  │
```

## Chapter 2 — The Double-Wrapping Problem

Before reading the configuration, you must understand a subtle but critical concept: **Docker wraps your log lines in its own JSON envelope**. This is the "double-wrapping problem" and it is the reason Promtail needs two separate parsing stages.

When your Go service uses `zap.Info(...)`, Zap produces one layer of JSON:

```json
{"level":"info","timestamp":"2024-01-15T03:47:00.123Z","message":"payroll processed","trace_id":"abc-def-ghi","employee_id":"EMP-007"}
```

But Docker does not write this directly to a file. Docker wraps it in its own JSON envelope:

```json
{"log":"{\"level\":\"info\",\"timestamp\":\"2024-01-15T03:47:00.123Z\",\"message\":\"payroll processed\",\"trace_id\":\"abc-def-ghi\"}\n","stream":"stdout","time":"2024-01-15T03:47:00.124Z"}
```

```
THE DOUBLE-WRAPPING DIAGRAM

┌─────────────────────────────────────────────────────────────────┐
│                     DOCKER JSON OUTER LAYER                     │
│  {                                                              │
│    "log":    ┌──────────────────────────────────────────────┐   │
│              │         ZAP JSON INNER LAYER                 │   │
│              │  "{\"level\":\"info\",                       │   │
│              │    \"timestamp\":\"2024-01-15T03:47:00Z\",   │   │
│              │    \"message\":\"payroll processed\",        │   │
│              │    \"trace_id\":\"abc-def-ghi\"}"            │   │
│              └──────────────────────────────────────────────┘   │
│    "stream": "stdout",                                          │
│    "time":   "2024-01-15T03:47:00.124Z"   ← Docker's timestamp  │
│  }                                                              │
└─────────────────────────────────────────────────────────────────┘

To get to the actual log data, Promtail must:
  Step 1: docker{} stage → unwrap the outer Docker JSON
  Step 2: json{} stage  → parse the inner Zap JSON
```

The Promtail pipeline stages you see in the config are designed precisely to solve this problem in two sequential steps. Without understanding the double-wrapping, the pipeline_stages section looks confusing. With this knowledge, it reads like an obvious two-step recipe.

## Chapter 3 — Line-by-Line Configuration Walkthrough

### 3.1 — `server` block

```yaml
server:
  http_listen_port: 9080
  grpc_listen_port: 0
  log_level: info
```

Promtail itself exposes a small HTTP server for two purposes: serving its own operational metrics at `/metrics` (so Prometheus can scrape Promtail's health) and exposing a targets page at `/targets` that shows you which containers Promtail has discovered and what its current read position is for each. Port 9080 is the conventional choice for this. The `grpc_listen_port: 0` tells Promtail not to open a gRPC port at all — gRPC is only needed for certain advanced clustering scenarios that do not apply here. Setting it to `0` means "disabled." The `log_level: info` controls Promtail's own diagnostic output, not your application logs.

---

### 3.2 — `positions` block

```yaml
positions:
  filename: /tmp/positions.yaml
```

This is one of the most important reliability features in Promtail, and it is easy to overlook because it is just one line. ==Promtail keeps a YAML file on disk that records exactly how many bytes into each log file it has read.== Think of it as a bookmark for every single container log file it is monitoring.

When Promtail restarts (due to a container restart, a deployment update, or a crash), it opens this positions file and continues reading each log file from the exact byte offset it last reached. Without this file, every Promtail restart would cause it to re-read each log file from the beginning, shipping every historical log line to Loki again — flooding your Loki instance with duplicate data and causing confusion in dashboards.

```
HOW THE POSITIONS FILE WORKS

Promtail restart at 03:50 AM:
┌──────────────────────────────────────────────────────────────────┐
│                    /tmp/positions.yaml                           │
│                                                                  │
│  positions:                                                      │
│    /var/lib/docker/containers/abc123/abc123-json.log: "142857"   │
│    /var/lib/docker/containers/def456/def456-json.log: "98304"    │
│    /var/lib/docker/containers/ghi789/ghi789-json.log: "71680"    │
│                                                                  │
│  ↑ These byte offsets tell Promtail: "for employee-svc, you      │
│    already read 142,857 bytes. Start from byte 142,858."         │
└──────────────────────────────────────────────────────────────────┘

Without positions file:          With positions file:
Promtail reads from byte 0       Promtail reads from byte 142,858
→ Re-ships 142,857 bytes         → Ships only new log lines
→ Loki gets duplicate logs       → No duplicates
→ Dashboards show wrong counts   → Clean, accurate data
```

**Production note:** The config stores the positions file at `/tmp/positions.yaml`, which is inside the container's temporary filesystem. If the Promtail container is destroyed and recreated (not just restarted), `/tmp` is wiped. You should mount a persistent volume for this file in your Docker Compose configuration:

```yaml
# In docker-compose.yml, under the promtail service:
volumes:
  - promtail_positions:/tmp
  - /var/lib/docker/containers:/var/lib/docker/containers:ro
  - /var/run/docker.sock:/var/run/docker.sock:ro
```

### 3.3 — `clients` block

```yaml
clients:
  - url: http://loki:3100/loki/api/v1/push
    tenant_id: hr360
    batchwait: 1s
    batchsize: 1048576
    backoff_config:
      min_period: 500ms
      max_period: 5m
      max_retries: 10
```

The `clients` block tells Promtail where to send logs and how to behave as an HTTP client. The URL `http://loki:3100/loki/api/v1/push` works because both Promtail and Loki are on the same Docker network — Docker's internal DNS resolves the service name `loki` to the Loki container's IP address automatically. This is the `/push` endpoint on Loki's HTTP server, specifically designed to receive batches of log lines from collectors like Promtail.

The `tenant_id: hr360` sets the `X-Scope-OrgID` header on every HTTP request Promtail makes to Loki. Even though `auth_enabled: false` in your Loki config means Loki does not actually enforce tenant isolation, setting the tenant ID here is a good habit. It costs nothing now and makes future migration to a multi-tenant setup trivial — you would only need to change `auth_enabled` in Loki without touching Promtail.

The batching configuration — `batchwait: 1s` and `batchsize: 1048576` — controls how Promtail packages log lines before sending them. Instead of sending a separate HTTP request for every single log line (which would be enormously wasteful at high log volume), Promtail accumulates log lines in memory and sends them together. It triggers a send when either the batch reaches 1 MB in size or 1 second has elapsed since the last send — whichever happens first. This means your logs arrive in Loki with a maximum latency of 1 second, which is acceptable for all but real-time alerting scenarios.

```
BATCHING BEHAVIOR

Time →  0ms    200ms   400ms   600ms   800ms   1000ms
        │       │       │       │       │       │
        │  line │  line │  line │  line │  line │
        │  #1   │  #2   │  #3   │  #4   │  #5   │  ← log lines arrive
        └───────┴───────┴───────┴───────┴───────┘
                                                 │
                               1 second elapsed ─┘
                                                 │
                                                 ▼
                              ┌──────────────────────────────┐
                              │  HTTP POST to Loki           │
                              │  Body: lines #1, #2, #3,     │
                              │        #4, #5 as one batch   │
                              └──────────────────────────────┘

OR — if many services are logging heavily and 1MB fills before 1s:
        │  line │  line │  ... │  line │   ← 1MB reached at ~500ms
        └───────┴───────┴──────┴───────┘
                                       │
                         1MB reached ──┘
                                       │
                                       ▼
                    ┌──────────────────────────────┐
                    │  HTTP POST to Loki at 500ms  │
                    │  (early, before 1s timer)    │
                    └──────────────────────────────┘
```

The `backoff_config` handles the scenario where Loki is temporarily unavailable — perhaps because Loki is restarting, the Docker host is under memory pressure, or there is a brief network issue. When a push to Loki fails, Promtail does not immediately give up. Instead it waits 500ms and tries again. If that fails, it waits 1s, then 2s, then 4s, doubling each time (exponential backoff) up to a maximum wait of 5 minutes. It will attempt this up to 10 times before dropping the batch and moving on. This means your HR360 system can tolerate a Loki restart of up to roughly 30 minutes without losing any log lines, because Promtail will keep retrying patiently.

### 3.4 — `scrape_configs` — The Core Discovery Engine

The `scrape_configs` section is the heart of Promtail's configuration. ==It defines where Promtail looks for logs, how it discovers targets, and what transformations it applies to each log line before shipping.== Your config has one primary job named `docker_containers`, which uses Docker's service discovery API to automatically find and monitor all HR360 containers.

```
THE SCRAPE CONFIG PIPELINE

Docker Socket ──► Container Discovery ──► Relabeling ──► Pipeline Stages ──► Loki
                  (what to scrape)        (which labels  (transform the
                                           to attach)     log content)
```

---

### 3.5 — `docker_sd_configs` — Service Discovery

```yaml
docker_sd_configs:
  - host: unix:///var/run/docker.sock
    refresh_interval: 5s
    filters:
      - name: status
        values: [running]
```

This block tells Promtail to use Docker's Service Discovery mechanism. By connecting to the Docker daemon's UNIX socket at `/var/run/docker.sock`, Promtail can ask Docker: "what containers are currently running?" Docker responds with a complete list, including every container's labels, ID, name, image, and network configuration. Promtail then builds a scrape target for each container and begins reading its log file.

The `refresh_interval: 5s` means Promtail re-asks this question every 5 seconds. When you deploy a new service or scale up an existing one, Promtail discovers it within 5 seconds and automatically begins collecting its logs. When a container stops, Promtail removes it from its target list. This is why Promtail is described as having **automatic discovery** — you do not have to manually register each new service.

The `filters` section tells Docker to only return containers whose status is `running`. This is a performance optimization — without this filter, Docker would also return stopped, paused, and dead containers, and Promtail would attempt to build scrape targets for all of them.

### 3.6 — `relabel_configs` — The Labeling Pipeline

This is where the real intelligence lives. Relabeling is the process of taking the raw metadata that Docker provides about each container and transforming it into the clean, useful Loki labels that you will actually use in Grafana queries. Think of relabeling as a series of instructions that run in sequence, top to bottom, for each discovered container.

When Docker Service Discovery runs, it attaches dozens of `__meta_docker_*` internal labels to each target. These are not Loki labels yet — they are temporary metadata that Promtail uses during the relabeling process. After relabeling is complete, any label that still starts with `__` is dropped automatically (they are internal-only). Only labels without the double-underscore prefix become actual Loki stream labels.

```
RELABELING: STEP-BY-STEP TRANSFORMATION

Container discovered by Docker SD:
┌────────────────────────────────────────────────────────────────────┐
│  Raw metadata from Docker:                                         │
│  __meta_docker_container_id      = "abc123def456..."               │
│  __meta_docker_container_name    = "/hr360_payroll-svc_1"          │
│  __meta_docker_container_label_com_docker_compose_project = "hr360"│
│  __meta_docker_container_label_com_docker_compose_service = "payroll-svc" │
│  __meta_docker_container_label_env = "production"                  │
│  ... (dozens more __meta_ fields)                                  │
└────────────────────────────────────────────────────────────────────┘
                              │
           ┌──────────────────▼──────────────────┐
           │  Step 1: FILTER (keep/drop)         │
           │  Project label == "hr360"? ✓ KEEP   │
           │  Project label != "hr360"? ✗ DROP   │
           └──────────────────┬──────────────────┘
                              │
           ┌──────────────────▼──────────────────┐
           │  Step 2: EXTRACT service name       │
           │  com_docker_compose_service         │
           │         → service = "payroll-svc"   │
           └──────────────────┬──────────────────┘
                              │
           ┌──────────────────▼──────────────────┐
           │  Step 3: EXTRACT container name     │
           │  /hr360_payroll-svc_1               │
           │    → container="hr360_payroll-svc_1"│
           └──────────────────┬──────────────────┘
                              │
           ┌──────────────────▼──────────────────┐
           │  Step 4: CONSTRUCT log file path    │
           │  container_id = "abc123def456"      │
           │  → __path__ =                       │
           │  /var/lib/docker/containers/        │
           │  abc123def456/abc123def456-json.log │
           └──────────────────┬──────────────────┘
                              │
           ┌──────────────────▼──────────────────┐
           │  Step 5: EXTRACT env label          │
           │  container label "env"              │
           │         → env = "production"        │
           └──────────────────┬──────────────────┘
                              │
           ┌──────────────────▼──────────────────┐
           │  Step 6: CLEAN UP                   │
           │  Drop all __meta_* labels           │
           │  (they were only temp variables)    │
           └──────────────────┬──────────────────┘
                              │
                              ▼
Final Loki stream labels for this container:
{service="payroll-svc", container="hr360_payroll-svc_1", env="production"}
```

Each relabeling rule deserves a careful explanation.

**Rule 1 — The filter rule (`action: keep`):** This is the most important rule in the entire config. Without it, Promtail would scrape logs from every container running on your Docker host — including system containers, your Grafana container, your Loki container, and any other projects running on the same machine. The rule says: examine the Docker Compose project label on each container; if it does not exactly match the string `hr360`, discard this target entirely. This is how Promtail knows to only collect logs from your HR360 services.

**Rule 2 — Extracting the service name:** Docker Compose automatically stamps every container it creates with a label called `com.docker.compose.service` containing the service name as defined in your `docker-compose.yml`. This rule reads that label and assigns its value to a new label called `service`. This is what makes the Grafana query `{service="payroll-svc"}` work.

**Rule 3 — Extracting the container name:** Docker names containers with a leading slash (e.g. `/hr360_payroll-svc_1`). The regex `/?(.*?)` strips the leading slash and captures everything after it. This gives you a clean `container` label for cases where you have multiple replicas of the same service and need to distinguish between them.

**Rule 4 — Constructing the file path (`__path__`):** This is the mechanism that actually connects Promtail to the log file. The special label `__path__` tells Promtail the filesystem path of the log file to tail for this target. Docker stores each container's log output at the predictable path `/var/lib/docker/containers/<container_id>/<container_id>-json.log`. This rule reads the container ID from the Docker metadata and constructs that path dynamically, so Promtail knows exactly which file on disk to read for each container.

**Rule 5 — Extracting the `env` label:** This rule requires that your Docker Compose service definitions include a custom label like `labels: - "env=production"`. If that label exists on the container, its value becomes an `env` Loki label. This is useful for distinguishing between staging and production logs if they were ever to flow into the same Loki instance.

**Rule 6 — The `labeldrop` cleanup:** After all the extraction is done, this rule removes every label whose name matches the pattern `__meta_.*`. These were Docker's raw metadata fields — they served their purpose as data sources for the extraction rules above, but they must not become Loki stream labels. If they were allowed through, you would have hundreds of high-cardinality internal Docker metadata labels attached to every log line, inflating Loki's index enormously.

### 3.7 — `pipeline_stages` — Transforming the Log Content

While `relabel_configs` works on the metadata about the log target (which container, which file, which labels), `pipeline_stages` works on the actual content of each log line as it is read. The pipeline runs every log line through a sequence of stages, each transforming or enriching the line before it moves to the next stage.

```
PIPELINE STAGES: PROCESSING ONE LOG LINE

Raw file line (from Docker's JSON log file):
  {"log":"{\"level\":\"error\",\"timestamp\":\"2024-01-15T03:47:00Z\",\"message\":\"payroll failed\",\"trace_id\":\"abc\",\"employee_id\":\"EMP-007\"}\n","stream":"stdout","time":"2024-01-15T03:47:00.124Z"}

                    │
                    ▼
┌───────────────────────────────────────────────────────────────┐
│  Stage 1: docker{}                                            │
│  Unwrap the outer Docker JSON envelope                        │
│                                                               │
│  log_line becomes: {"level":"error","timestamp":...}          │
│  timestamp set to: 2024-01-15T03:47:00.124Z (Docker time)     │
└───────────────────────────────────┬───────────────────────────┘
                                    │
                    ▼
┌───────────────────────────────────────────────────────────────┐
│  Stage 2: json{}                                              │
│  Parse the inner Zap JSON                                     │
│                                                               │
│  Extracted into pipeline state (NOT labels yet):              │
│    level     = "error"                                        │
│    timestamp = "2024-01-15T03:47:00Z"                         │
│    message   = "payroll failed"                               │
│    trace_id  = "abc"                                          │
│    service   = "payroll-svc"                                  │
└───────────────────────────────────┬───────────────────────────┘
                                    │
                                    ▼
┌───────────────────────────────────────────────────────────────┐
│  Stage 3: timestamp{}                                         │
│  Override the timestamp                                       │
│                                                               │
│  BEFORE: 2024-01-15T03:47:00.124Z  (Docker's write time)      │
│  AFTER:  2024-01-15T03:47:00Z      (Zap's generation time)    │
│                                                               │
│  ← This is the correct time for log ordering in Grafana       │
└───────────────────────────────────┬───────────────────────────┘
                                    │
                                    ▼
┌───────────────────────────────────────────────────────────────┐
│  Stage 4: labels{}                                            │
│  Promote pipeline state to actual Loki stream labels          │
│                                                               │
│  level → becomes a Loki label → {level="error"}               │
│  (service was already set via relabeling)                     │
└───────────────────────────────────┬───────────────────────────┘
                                    │
                                    ▼
┌───────────────────────────────────────────────────────────────┐
│  Stage 5: output{}                                            │
│  Set the final displayed log line                             │
│                                                               │
│  BEFORE: {"level":"error","timestamp":...,"message":"payroll  │
│           failed","trace_id":"abc","employee_id":"EMP-007"}   │
│  AFTER:  "payroll failed"                                     │
│                                                               │
│  ← Grafana's log view shows "payroll failed" cleanly,         │
│    not a wall of JSON                                         │
└───────────────────────────────────┬───────────────────────────┘
                                    │
                    ▼

Final result shipped to Loki:
  Stream labels: {service="payroll-svc", level="error", env="production"}
  Timestamp:     2024-01-15T03:47:00Z
  Log line:      "payroll failed"
  (full JSON still preserved in Loki — Grafana can expand it)
```

The **`docker: {}`** stage is a convenience stage that knows exactly the structure of Docker's log envelope. It is equivalent to writing a JSON parsing stage that extracts the `log` field and a timestamp stage that reads the `time` field — but collapsed into one named stage because this pattern is so common.

The **`json: {}`** stage does not modify the log line. Instead, it reads the current log line text (now the inner Zap JSON, after the docker stage unwrapped the outer layer), parses it as JSON, and extracts the listed fields into a temporary key-value store called the "pipeline state." The field `service_field: service` means "read the `service` key from the JSON and store it in the pipeline state under the name `service_field`." These extracted values are available to later stages but are not yet Loki labels.

The **`timestamp: {}`** stage is subtle but critically important. By the time a log line reaches Loki, it has two potential timestamps: the time Docker wrote the log line to the file (from the outer envelope's `time` field), and the time your Go code actually generated the log line (from Zap's `timestamp` field). These differ by the time it took Docker and Promtail to process the line — usually milliseconds, but potentially longer if Promtail was backlogged. By overriding the timestamp with Zap's value, you ensure that logs appear in Loki in the correct chronological order relative to when events actually happened in your system. This matters enormously when you are debugging a race condition or a cascading failure across multiple services.

The **`labels: {}`** stage is the checkpoint where pipeline state becomes permanent Loki stream labels. Only the fields listed here get promoted to labels. The `level` field is explicitly listed, so it becomes a queryable Loki label. The `trace_id` is deliberately **not** listed — it has too many unique values to be a label (every request has a unique trace ID), so it stays in the log body and is accessed via `| json | trace_id = "abc"` in LogQL queries.

The **`output: {}`** stage sets what Grafana actually displays as the "log line" in its Explore view. Without this stage, Grafana would display the full raw JSON as the log line — which, while technically correct, is difficult to read when scanning through hundreds of log lines looking for the one that says "payroll failed." By setting the output to the `message` field, you get clean, human-readable log lines in Grafana's default view while still having all the structured JSON fields available when you click to expand a specific line.

## Chapter 4 — The Complete Data Flow for HR360

Now that every section is understood individually, here is the complete picture of how a single error log line from `payroll-svc` travels through the entire system:

```
COMPLETE LOG PIPELINE: PAYROLL ERROR EXAMPLE

1. Go code executes at 03:47:00.000Z
   zap.Error("payroll calculation failed", zap.String("trace_id", "abc"))

2. Zap writes to stdout at 03:47:00.001Z
   {"level":"error","timestamp":"2024-01-15T03:47:00.001Z",
    "message":"payroll calculation failed","trace_id":"abc"}

3. Docker captures stdout and writes to log file at 03:47:00.003Z
   File: /var/lib/docker/containers/def456.../def456...-json.log
   {"log":"{\"level\":\"error\",...}\n","stream":"stdout","time":"2024-01-15T03:47:00.003Z"}

4. Promtail reads new bytes from file (within milliseconds)
   Positions file: def456...-json.log → now at byte 12345

5. Promtail runs pipeline stages:
   - docker{}        → unwrap envelope, get inner Zap JSON
   - json{}          → extract level="error", timestamp, message, trace_id
   - timestamp{}     → set time to 03:47:00.001Z (Zap's time, not Docker's)
   - labels{}        → level="error" becomes a Loki label
   - output{}        → displayed line = "payroll calculation failed"

6. Promtail holds in batch buffer...
   (either waits for 1s timer or 1MB fill)

7. At 03:47:01.001Z — 1 second timer fires
   HTTP POST to http://loki:3100/loki/api/v1/push
   Stream: {service="payroll-svc", level="error", env="production"}
   Entry:  timestamp=03:47:00.001Z, line="payroll calculation failed"

8. Loki ingester receives and stores in chunk + WAL

9. In Grafana, engineer queries at 03:50:00Z:
   {service="payroll-svc", level="error"} | json | trace_id = "abc"
   → Instantly finds this exact log line and all related lines
     from other services that share trace_id="abc"
```

## Chapter 5 — What Your Zap Logger Must Output

For Promtail's `json{}` pipeline stage to successfully extract `level`, `timestamp`, `message`, and `trace_id`, your Go services must produce logs in a format that matches those field names. Here is the Zap configuration that produces the correct output:

```go
// internal/logger/logger.go

package logger

import (
    "go.uber.org/zap"
    "go.uber.org/zap/zapcore"
    "os"
    "time"
)

func New(serviceName string) (*zap.Logger, error) {
    encoderConfig := zapcore.EncoderConfig{
        // These key names MUST match the field names in Promtail's json{} stage
        TimeKey:        "timestamp",   // matches: timestamp: timestamp
        LevelKey:       "level",       // matches: level: level
        MessageKey:     "message",     // matches: message: message
        CallerKey:      "caller",
        StacktraceKey:  "stacktrace",
        EncodeLevel:    zapcore.LowercaseLevelEncoder,  // "error" not "ERROR"
        EncodeTime:     zapcore.RFC3339NanoTimeEncoder,  // matches format: RFC3339Nano
        EncodeCaller:   zapcore.ShortCallerEncoder,
    }

    core := zapcore.NewCore(
        zapcore.NewJSONEncoder(encoderConfig),
        zapcore.AddSync(os.Stdout), // must write to stdout for Docker to capture
        zapcore.InfoLevel,
    )

    logger := zap.New(core, zap.AddCaller()).With(
        zap.String("service", serviceName), // adds "service" field to every log line
    )

    return logger, nil
}
```

The field names in Zap's `EncoderConfig` must exactly match the keys in Promtail's `json{}` expressions. If Zap calls the time field `ts` (which is the default) but Promtail looks for `timestamp`, the timestamp stage will fail silently and fall back to using the ingestion time — causing subtle time-ordering bugs in your Grafana dashboards.

## Chapter 8 — Common Mistakes and How to Avoid Them

Understanding what can go wrong is just as important as understanding the happy path. Here are the most common Promtail configuration mistakes in a microservices environment and exactly why they happen.

**Mistake 1 — Positions file in an ephemeral location.** If `/tmp/positions.yaml` is not on a persistent volume, every time the Promtail container is destroyed and recreated it loses its bookmarks. The next time it starts, it re-reads every log file from byte zero and re-ships every historical log line to Loki. Loki will reject many of them (because of `reject_old_samples: true`), but the ones within the 7-day window will create duplicate entries in your log store.

**Mistake 2 — Wrong field names in `json{}` stage.** If your Zap encoder uses `ts` for the timestamp key (which is the default Go log format) but your Promtail config looks for `timestamp`, the timestamp override stage silently fails. Loki will store your logs with the ingestion time rather than the actual log generation time. This appears harmless until you are debugging an incident that happened before a service restart — all your pre-restart logs will appear at the wrong time in Grafana.

**Mistake 3 — Making trace_id a label.** If you add `trace_id` to the `labels{}` stage, you have introduced a label with essentially infinite cardinality — every single HTTP request generates a unique trace ID. Loki's index will grow enormous, query performance will degrade, and your Loki instance will eventually run out of memory. Keep trace_id inside the log body and filter it with `| json | trace_id = "..."` in LogQL queries.

**Mistake 4 — Missing the Docker socket mount.** If `/var/run/docker.sock` is not mounted into the Promtail container, the `docker_sd_configs` section cannot connect to Docker and Promtail will fail to discover any containers at all. The error is not always obvious in Promtail's logs — you may just see an empty targets list at `http://localhost:9080/targets`.

**Mistake 5 — Forgetting the project filter.** Without the `action: keep` rule that filters by `com_docker_compose_project == hr360`, Promtail will attempt to collect logs from every container on the host — including Loki itself, Grafana, and any other projects. This inflates your log volume, introduces irrelevant log streams, and can cause Promtail to ship Loki's own internal logs back to Loki in a loop.

## Summary

Promtail is not just a log forwarder — it is a structured log transformation pipeline. It solves three distinct problems simultaneously. First, it handles automatic discovery of all your microservice containers without requiring any manual configuration per service. Second, it solves the double-wrapping problem by unwrapping Docker's JSON envelope before parsing your Zap JSON payload. Third, it makes a deliberate set of labeling decisions — promoting only low-cardinality fields (`level`, `service`, `env`) to Loki labels while keeping high-cardinality fields (`trace_id`, `employee_id`, `user_id`) inside the log body where they can be searched without destroying Loki's indexing performance.

Every configuration line in `promtail-config.yml` exists to serve one of these three goals. The relabeling pipeline is about discovery and labeling. The pipeline stages are about content transformation. The client configuration is about reliable, efficient delivery. Together with your `loki-config.yml`, they form a complete, production-grade observability foundation for HR360.
