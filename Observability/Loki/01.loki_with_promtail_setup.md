# Production-Grade Distributed Logging with Loki, Promtail & Grafana

---

## The Mental Model: What Are We Actually Building?

Before we write a single line of configuration, let us take a moment to understand the philosophy behind what we are assembling. Every microservice in your HR360 system already writes structured logs to its standard output stream, courtesy of the Zap logger you have already configured. The problem is that those logs exist in isolation — buried inside individual Docker containers, inaccessible unless you are manually running `docker logs`, and completely lost the moment a container restarts. What you need is a centralised nervous system that collects every log from every service, indexes them in a way that makes searching fast, and presents them through a beautiful query interface. That is precisely what the Loki stack gives you.

The three actors in this story each play a distinct and irreplaceable role. **Promtail** is the field agent — it runs close to your services, watches their log streams, attaches labels (metadata like service name, container name, environment), and ships those labelled log lines upstream. **Loki** is the warehouse — it receives incoming log streams from Promtail, stores the raw log lines efficiently in chunks, and builds an index not of the log content itself, but of the labels attached to each stream. This is the key philosophical difference between Loki and Elasticsearch: Loki does not index the text of your logs, which is what makes it dramatically cheaper to run. **Grafana** is the analyst's desk — it provides the LogQL query language interface through which you search, filter, and visualise everything Loki has stored.

## Chapter 1: Understanding Labels — The Heart of Loki

Loki's entire efficiency story hinges on a concept called **labels**, and it is essential that you understand this before you configure anything, because poor label design is the most common mistake engineers make when adopting Loki.

A label is a key-value pair that you attach to a log stream. Think of it as a sticky note you put on a box before you put it in a warehouse. When you later want to find that box, you describe the sticky note, not the contents of the box. In Loki's case, a label might look like `service="employee-svc"` or `env="production"` or `container="hr360_employee-svc_1"`. When Promtail ships a batch of logs, it tells Loki: "here are 500 log lines, and all of them came from this particular combination of labels." Loki stores that batch as a single **stream** and indexes the label combination. Later, when you query with LogQL, you first filter by labels — which is blazingly fast because only the index is touched — and then Loki scans the raw text within the matching streams for your keyword.

The golden rule of Loki label design is this: **keep your label cardinality low**. Cardinality means the number of unique values a label can take. `service` has low cardinality because you have perhaps ten services. `user_id` has catastrophically high cardinality because it could be thousands of unique values. If you make `user_id` a label, Loki creates thousands of separate streams — one for each user — which destroys its indexing efficiency and makes it slower, not faster. Labels should describe structural properties of the source of the log (which service, which environment, which host), never properties of individual log lines.

## Chapter 2: Preparing Your Go Services

Your Zap logger is already configured, which is excellent. The single thing you must ensure is that your services log to **standard output (stdout)** in **JSON format**. Docker captures whatever a container writes to stdout and stderr, and Promtail will read those Docker log files from the host filesystem. When logs are structured JSON, Grafana can parse individual fields inside LogQL queries, giving you tremendous filtering power.

Here is what a properly configured Zap production logger should look like in your service's `main.go` or wherever you initialise your logger:

```go
// internal/logger/logger.go
package logger

import (
    "go.uber.org/zap"
    "go.uber.org/zap/zapcore"
    "os"
)

func NewProductionLogger(serviceName string) (*zap.Logger, error) {
    encoderCfg := zap.NewProductionEncoderConfig()
    encoderCfg.TimeKey = "timestamp"
    encoderCfg.EncodeTime = zapcore.ISO8601TimeEncoder
    encoderCfg.MessageKey = "message"
    encoderCfg.LevelKey = "level"
    encoderCfg.CallerKey = "caller"

    core := zapcore.NewCore(
        // JSON encoder writes structured JSON — Grafana can parse individual fields
        zapcore.NewJSONEncoder(encoderCfg),
        // Write to stdout so Docker captures it
        zapcore.AddSync(os.Stdout),
        zap.InfoLevel,
    )

    logger := zap.New(core, zap.AddCaller(), zap.AddCallerSkip(0)).
        With(
            // These fields appear on EVERY log line — invaluable for filtering
            zap.String("service", serviceName),
            zap.String("env", os.Getenv("APP_ENV")),
        )

    return logger, nil
}
```

Every log line your service writes will now be a clean JSON object, looking something like this in the container's stdout:

```json
{
  "timestamp": "2026-08-17T10:23:45.123Z",
  "level": "info",
  "caller": "employee/handler.go:87",
  "message": "Employee created successfully",
  "service": "employee-svc",
  "env": "production",
  "employee_id": "emp_001",
  "trace_id": "4bf92f3577b34da6",
  "duration_ms": 42
}
```

This JSON structure is what Promtail will ship to Loki, and what Grafana will allow you to dissect with LogQL.

## Chapter 4: Configuring Loki

Loki's configuration file is where you define how it stores data, how it accepts incoming streams, and what its retention policy looks like. The file is written in YAML, and each section controls a different subsystem of Loki's internals.

```yaml
# monitoring/loki/loki-config.yml

auth_enabled: false
# In a true multi-tenant production setup you would set this to true and pass
# X-Scope-OrgID headers from Promtail. For a single-team HR system, false is correct.

server:
  http_listen_port: 3100
  grpc_listen_port: 9096
  log_level: info

common:
  # The instance_addr is the address Loki uses to identify itself in a cluster.
  # For single-node (which is what you are running now), 127.0.0.1 is correct.
  instance_addr: 127.0.0.1
  path_prefix: /loki/data
  storage:
    filesystem:
      chunks_directory: /loki/data/chunks
      rules_directory: /loki/data/rules
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory
  # This tells Loki that all its components (ingester, querier, distributor) are
  # running inside the same process — the "monolithic" deployment mode, which is
  # perfect for a single-node production setup under moderate log volume.

query_range:
  results_cache:
    cache:
      embedded_cache:
        enabled: true
        max_size_mb: 100

schema_config:
  configs:
    - from: 2024-01-01
      # The date above is when this schema version takes effect. It is safe to
      # backdate it to before your first log line.
      store: tsdb
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h
      # TSDB (Time Series Database) is the modern Loki index store. v13 schema
      # is the recommended schema as of Loki 3.x. The index rotates daily,
      # meaning a new index file is created every 24 hours.

ingester:
  wal:
    enabled: true
    dir: /loki/data/wal
  # The Write-Ahead Log (WAL) is critical for production. When Loki receives
  # log lines, it first writes them to the WAL on disk before acknowledging
  # receipt. If Loki crashes before flushing to chunks, it replays the WAL
  # on restart — so no log lines are lost.
  lifecycler:
    ring:
      kvstore:
        store: inmemory
      replication_factor: 1
  chunk_idle_period: 5m
  # A chunk is a compressed batch of log lines for one stream. After 5 minutes
  # of no new lines arriving for a stream, the chunk is flushed to storage.
  chunk_retain_period: 30s
  max_chunk_age: 1h
  chunk_target_size: 1048576
  # Target 1MB per chunk. Larger chunks compress better; this is a good default.

storage_config:
  tsdb_shipper:
    active_index_directory: /loki/data/index
    cache_location: /loki/data/index_cache
  filesystem:
    directory: /loki/data/chunks

limits_config:
  reject_old_samples: true
  reject_old_samples_max_age: 168h
  # Reject log lines older than 7 days. This prevents clock-skewed services
  # from polluting your recent log views with ancient data.
  ingestion_rate_mb: 16
  ingestion_burst_size_mb: 32
  # Allow 16 MB/s of incoming log data, with bursts up to 32 MB/s.
  # Adjust these values upward if you have high-volume services.
  max_query_series: 5000
  max_query_lookback: 720h
  # Allow querying up to 30 days of historical logs.
  retention_period: 720h
  # Delete log data older than 30 days. This is your primary storage cost control.

compactor:
  working_directory: /loki/data/compactor
  compaction_interval: 10m
  retention_enabled: true
  retention_delete_delay: 2h
  # The compactor merges small index files together (improves query speed)
  # and enforces the retention_period by deleting old chunks.

ruler:
  storage:
    type: local
    local:
      directory: /loki/data/rules
  rule_path: /loki/data/rules
  ring:
    kvstore:
      store: inmemory
  enable_api: true
  # The ruler allows you to define alerting rules in LogQL — for example,
  # "alert me if the error rate for employee-svc exceeds 10 per minute."
  # We will add example rules later in this guide.
```

## Chapter 5: Configuring Promtail

Promtail is the most nuanced piece to configure correctly because it sits at the boundary between your application world and the observability world. Its job is to discover log sources, read them, enrich them with labels, and push them to Loki. The configuration below is designed for the Docker log collection approach, where Promtail reads Docker's log files directly from the host filesystem.

```yaml
# monitoring/promtail/promtail-config.yml

server:
  http_listen_port: 9080
  grpc_listen_port: 0
  log_level: info

positions:
  filename: /tmp/positions.yaml
  # Promtail keeps a record of how far it has read in each log file.
  # Think of it as a bookmark. If Promtail restarts, it picks up from
  # the last position rather than re-shipping every log line from the
  # beginning. In production, mount this to a persistent volume (see
  # Docker Compose below) so restarts do not cause log re-ingestion.

clients:
  - url: http://loki:3100/loki/api/v1/push
    # This is the Loki push endpoint. The hostname "loki" resolves within
    # Docker's internal network because both containers share the same
    # Docker network. Port 3100 is what we configured in loki-config.yml.
    tenant_id: hr360
    # Even with auth_enabled: false in Loki, setting a tenant_id is good
    # practice — it namespaces your data and makes migrating to multi-tenant
    # mode in the future a simple configuration change.
    batchwait: 1s
    batchsize: 1048576
    # Promtail accumulates log lines and sends them in batches. It sends a
    # batch when either 1 second has elapsed OR the batch has grown to 1MB —
    # whichever comes first. This dramatically reduces the number of HTTP
    # requests compared to sending every line individually.
    backoff_config:
      min_period: 500ms
      max_period: 5m
      max_retries: 10
    # If Loki is temporarily unavailable, Promtail will retry with exponential
    # backoff — starting at 500ms and doubling up to a 5-minute maximum,
    # retrying up to 10 times before dropping the batch.

scrape_configs:

  # ─────────────────────────────────────────────────────────────────────────
  # JOB 1: Docker container log discovery (the main job)
  # ─────────────────────────────────────────────────────────────────────────
  - job_name: docker_containers
    docker_sd_configs:
      - host: unix:///var/run/docker.sock
        refresh_interval: 5s
        # Promtail connects to the Docker daemon's UNIX socket to discover
        # running containers. Every 5 seconds it checks for new or stopped
        # containers and updates its scrape targets accordingly.
        filters:
          - name: status
            values: [running]
          # Only scrape containers that are currently running. This prevents
          # Promtail from attempting to read logs from stopped containers.

    relabel_configs:
      # ── Step 1: Only scrape HR360 containers ──────────────────────────────
      - source_labels: [__meta_docker_container_label_com_docker_compose_project]
        action: keep
        regex: hr360
        # Docker Compose automatically adds a label to every container with
        # the project name. This rule tells Promtail: if the container's
        # project label does not match "hr360", skip it entirely. This is
        # essential if your Docker host runs other unrelated containers.

      # ── Step 2: Extract the service name ─────────────────────────────────
      - source_labels: [__meta_docker_container_label_com_docker_compose_service]
        target_label: service
        # Docker Compose adds a label with the service name (e.g. "employee-svc",
        # "leave-svc"). We promote it to a Loki label so you can query with
        # {service="employee-svc"} in Grafana.

      # ── Step 3: Capture the container name ───────────────────────────────
      - source_labels: [__meta_docker_container_name]
        target_label: container
        regex: '/?(.*)'
        # Container names have a leading slash (e.g. /hr360_employee-svc_1).
        # This regex strips the slash so the label value is clean.

      # ── Step 4: Set the log source path ──────────────────────────────────
      - source_labels: [__meta_docker_container_id]
        target_label: __path__
        replacement: /var/lib/docker/containers/$1/$1-json.log
        # This constructs the path to the Docker log file on the host filesystem.
        # When you mount /var/lib/docker/containers into the Promtail container,
        # it can read these JSON log files directly.

      # ── Step 5: Add the environment label ────────────────────────────────
      - source_labels: [__meta_docker_container_label_env]
        target_label: env
        # If your Docker Compose services have a label "env=production" set,
        # Promtail will extract it as a Loki label. We will add this label
        # to our services in the Docker Compose file.

      # ── Step 6: Clean up internal Promtail metadata ──────────────────────
      - action: labeldrop
        regex: __meta_.*
        # After relabelling, drop all the raw __meta_ labels. They were only
        # needed as intermediate extraction sources; they should not become
        # Loki stream labels (that would inflate cardinality enormously).

    pipeline_stages:
      # ── Stage 1: Parse the Docker log wrapper ────────────────────────────
      - docker: {}
        # Docker wraps each log line in its own JSON envelope:
        # {"log": "actual log line\n", "stream": "stdout", "time": "..."}
        # This stage unwraps that envelope and extracts just the "log" field
        # as the line content, and uses "time" as the timestamp.

      # ── Stage 2: Parse your Zap JSON log line ────────────────────────────
      - json:
          expressions:
            level: level
            timestamp: timestamp
            message: message
            trace_id: trace_id
            service_field: service
        # This stage parses the JSON that your Zap logger produces and extracts
        # specific fields into Promtail's internal pipeline state. These are
        # NOT Loki labels yet — they are temporary variables in the pipeline.

      # ── Stage 3: Set the log timestamp ───────────────────────────────────
      - timestamp:
          source: timestamp
          format: RFC3339Nano
        # Override Promtail's ingestion timestamp with the actual timestamp
        # from your Zap log line. This ensures that log lines appear in Loki
        # at the time they were generated, not the time they were shipped.
        # Critical for debugging issues that happened before a service restart.

      # ── Stage 4: Promote the log level to a Loki label ───────────────────
      - labels:
          level:
        # Promote the "level" field (extracted in Stage 2) to an actual Loki
        # stream label. This allows you to query {level="error"} across all
        # services simultaneously. Keep this list short — only add fields
        # as labels if you will actually filter by them in queries.

      # ── Stage 5: Set the log line output ─────────────────────────────────
      - output:
          source: message
        # Use the "message" field from your Zap log as the displayed log line
        # in Grafana. Without this, Grafana would show the entire raw JSON
        # blob as the log line, which is harder to read at a glance.

  # ─────────────────────────────────────────────────────────────────────────
  # JOB 2: Static file log collection (for services logging to files)
  # ─────────────────────────────────────────────────────────────────────────
  # If any of your services write logs to files instead of stdout, add them here:
  # - job_name: static_file_logs
  #   static_configs:
  #     - targets:
  #         - localhost
  #       labels:
  #         job: static_logs
  #         service: some-legacy-service
  #         __path__: /var/log/myapp/*.log
```

## Chapter 6: Configuring Grafana

Grafana is the friendliest piece of the stack to configure because most of its setup can be done through the UI. However, for a production-grade deployment, you should provision its datasources and dashboards as code — meaning Grafana reads them from files on startup rather than requiring a human to click through the UI each time. This way, if you destroy and recreate the Grafana container, all your datasources and dashboards reappear automatically.

```yaml
# monitoring/grafana/provisioning/datasources/loki.yml

apiVersion: 1

datasources:
  - name: Loki
    type: loki
    access: proxy
    # "proxy" means Grafana itself makes the HTTP request to Loki on your behalf.
    # The alternative "browser" would make the request from your web browser,
    # which would fail because Loki is on an internal Docker network.
    url: http://loki:3100
    isDefault: true
    version: 1
    editable: false
    # editable: false prevents users from accidentally modifying this datasource
    # through the UI. Configuration is managed through files only.
    jsonData:
      maxLines: 1000
      derivedFields:
        # Derived fields allow Grafana to automatically extract and linkify
        # certain values inside your log lines. Here, we extract trace_id
        # and turn it into a clickable link to your Tempo/Jaeger trace.
        - name: TraceID
          matcherRegex: '"trace_id":"(\w+)"'
          url: "http://your-tempo-host:3000/explore?orgId=1&left=%5B%22now-1h%22,%22now%22,%22Tempo%22,%7B%22query%22:%22${__value.raw}%22%7D%5D"
          # Update this URL to point at your distributed tracing backend.
          # When you later integrate OpenTelemetry traces, every log line
          # with a trace_id will have a clickable link to its trace.
```

```ini
# monitoring/grafana/grafana.ini

[server]
http_port = 3000
domain = localhost

[security]
admin_user = admin
admin_password = ${GF_SECURITY_ADMIN_PASSWORD}
# Never hardcode passwords. Grafana reads this from an environment variable
# that you supply through Docker Compose.

[auth.anonymous]
enabled = false
# Do not allow anonymous access in production.

[users]
allow_sign_up = false
# Disable self-registration. User accounts are managed by an administrator.

[log]
mode = console
level = info

[alerting]
enabled = true

[unified_alerting]
enabled = true
```


## Chapter 7: Docker Compose — Wiring Everything Together

This is where all the pieces come together. The monitoring Docker Compose file defines the three containers and their networking relationships:

```yaml
# docker-compose.monitoring.yml

version: "3.9"

networks:
  monitoring:
    name: hr360_monitoring
    driver: bridge
  # This monitoring network is separate from your application networks.
  # Loki, Promtail, and Grafana live here. Your application services do not
  # need to be on this network — Promtail reaches them via the Docker socket.
  app_network:
    name: hr360_app
    external: true
    # If your application services are on a separate network defined in your
    # main docker-compose.yml, declare it as external here so Grafana can
    # potentially reach application-level metrics endpoints in the future.

volumes:
  loki_data:
    name: hr360_loki_data
    driver: local
  grafana_data:
    name: hr360_grafana_data
    driver: local
  promtail_positions:
    name: hr360_promtail_positions
    driver: local

services:

  # ──────────────────────────────────────────────────────────────────────────
  # LOKI — The Log Warehouse
  # ──────────────────────────────────────────────────────────────────────────
  loki:
    image: grafana/loki:3.1.0
    # Pin to a specific version. Never use "latest" in production — it can
    # introduce breaking changes silently when the container is recreated.
    container_name: hr360_loki
    restart: unless-stopped
    ports:
      - "3100:3100"
      # Expose port 3100 on the host if you want to query Loki's API directly
      # from your development machine. In a hardened production setup, you
      # would remove this and access Loki only through Grafana.
    volumes:
      - ./monitoring/loki/loki-config.yml:/etc/loki/loki-config.yml:ro
      - loki_data:/loki/data
      # The loki_data named volume persists all log data across container
      # restarts. This is the most important volume in the entire stack.
    command: -config.file=/etc/loki/loki-config.yml
    networks:
      - monitoring
    healthcheck:
      test: ["CMD-SHELL", "wget --no-verbose --tries=1 --spider http://localhost:3100/ready || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
      # Loki takes a moment to initialise on startup. The start_period gives
      # it 30 seconds before the health check begins failing. Promtail and
      # Grafana are set to depend on this health check becoming healthy.
    mem_limit: 512m
    # Cap Loki's memory usage. Loki is designed to be memory-efficient because
    # it does not index log content. 512MB is comfortable for moderate volume.
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
    labels:
      env: production
      com.docker.compose.project: hr360

  # ──────────────────────────────────────────────────────────────────────────
  # PROMTAIL — The Log Collector
  # ──────────────────────────────────────────────────────────────────────────
  promtail:
    image: grafana/promtail:3.1.0
    container_name: hr360_promtail
    restart: unless-stopped
    volumes:
      - ./monitoring/promtail/promtail-config.yml:/etc/promtail/promtail-config.yml:ro
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
        # Mount Docker's log directory in read-only mode. This is where Docker
        # writes each container's stdout/stderr as JSON log files. Promtail
        # reads these files to collect your application logs.
      - /var/run/docker.sock:/var/run/docker.sock:ro
        # Mount the Docker socket in read-only mode. Promtail uses this to
        # call the Docker API and discover container metadata (names, labels,
        # IDs) so it can construct log file paths and extract label values.
      - promtail_positions:/tmp
        # Persist Promtail's position bookmarks. Without this, every time
        # Promtail restarts it would re-read and re-ship all logs from the
        # beginning of every log file — flooding Loki with duplicates.
    command: -config.file=/etc/promtail/promtail-config.yml
    networks:
      - monitoring
    depends_on:
      loki:
        condition: service_healthy
    security_opt:
      - no-new-privileges:true
    mem_limit: 128m
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
```

```yaml
# Find the GID with: getent group docker | cut -d: -f3
```

## Chapter 9: Querying Logs in Grafana with LogQL

Open Grafana at `http://localhost:3000` and log in with the admin credentials you set. Navigate to **Explore → Select Loki datasource**. You are now ready to write LogQL queries.

LogQL has two kinds of queries. A **log query** returns matching log lines. A **metric query** derives a number (like a rate or count) from those lines.

Every LogQL query begins with a **stream selector** in curly braces. This is where labels are matched:

```logql
# All logs from the employee service
{service="employee-svc"}

# All error-level logs across the entire system
{level="error"}

# Errors in the employee service specifically
{service="employee-svc", level="error"}

# Everything from the production environment
{env="production"}
```

After the stream selector, you can add **filter expressions** that search the text content of the matching log lines:

```logql
# Find all logs containing "timeout" in the employee service
{service="employee-svc"} |= "timeout"

# Case-insensitive filter
{service="employee-svc"} |~ "(?i)timeout"

# Exclude lines containing "health check" (reduces noise)
{service="employee-svc"} != "health check"

# Parse the JSON fields and then filter by a specific field value
{service="employee-svc"}
  | json
  | employee_id = "emp_001"

# Show only logs where the operation took longer than 1 second
{service="employee-svc"}
  | json
  | duration_ms > 1000

# Find all lines matching a trace ID (useful when debugging a specific request)
{env="production"} |= "trace_id=4bf92f3577b34da6"
```

For metric queries, which allow you to build charts and configure alerts:

```logql
# Error rate per minute for the payroll service
rate({service="payroll-svc", level="error"}[1m])

# Total error count across all services, grouped by service name
sum by (service) (
  rate({level="error"}[5m])
)

# Percentage of error log lines over total log lines for each service
sum by (service) (rate({level="error"}[5m]))
/
sum by (service) (rate({env="production"}[5m]))
```

## Chapter 10: Setting Up Alerting Rules in Loki

One of Loki's most powerful production features is its ability to evaluate LogQL metric queries and fire alerts when thresholds are exceeded. Create a rules directory and define your alerting rules there:

```yaml
# monitoring/loki/rules/hr360-alerts.yml

groups:
  - name: hr360_error_alerts
    interval: 1m
    rules:

      - alert: HighErrorRate
        expr: |
          sum by (service) (
            rate({level="error"}[5m])
          ) > 0.1
        for: 2m
        # The alert only fires if the condition has been true for 2 consecutive
        # minutes. This prevents transient spikes from generating false alarms.
        labels:
          severity: warning
        annotations:
          summary: "High error rate in {{ $labels.service }}"
          description: |
            Service {{ $labels.service }} is generating more than 0.1 errors
            per second (averaged over 5 minutes). Investigate immediately.

      - alert: ServiceProducingNoLogs
        expr: |
          sum by (service) (
            rate({env="production"}[5m])
          ) == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.service }} has stopped producing logs"
          description: |
            No log lines have been received from {{ $labels.service }} for
            5 minutes. The service may have crashed or become unresponsive.

      - alert: PayrollCriticalErrors
        expr: |
          count_over_time(
            {service="payroll-svc", level="error"} [10m]
          ) > 5
        for: 0m
        labels:
          severity: critical
        annotations:
          summary: "Multiple errors in payroll service"
          description: "More than 5 errors occurred in payroll-svc within the last 10 minutes."
```

Mount this rules file into Loki by adding a volume entry to the docker-compose:

```yaml
# In the loki service, add to volumes:
- ./monitoring/loki/rules:/loki/data/rules:ro
```

## Chapter 11: Building Your First Dashboard

Once you have log data flowing into Loki, navigate to **Dashboards → New → New Dashboard** in Grafana. Add a panel, select Loki as the datasource, and use this query to build a live log tail panel for your HR360 system:

```logql
{env="production"} | json | line_format "{{.timestamp}} [{{.level}}] {{.service}}: {{.message}}"
```

The `line_format` pipe reformats each log line using Go's template syntax, pulling out specific JSON fields. This produces clean, readable output like:

```
2026-08-17T10:23:45Z [info] employee-svc: Employee created successfully
2026-08-17T10:23:46Z [error] payroll-svc: Failed to process payslip
```

For an error rate chart, add a Time series panel with this metric query:

```logql
sum by (service) (rate({level="error"}[5m]))
```

This will show you a multi-line graph, one line per service, showing how many errors per second each service is producing over time. An uptick in the payroll service is visible the moment it begins, giving you early warning before users start complaining.

## The Flow, One Last Time

To cement your understanding, read through this data flow diagram carefully. Every log line your Go service writes travels exactly this path before it appears as a searchable entry in Grafana:

```
Your Go Service (Zap Logger)
        │
        │  fmt.Fprintf(os.Stdout, json_log_line)
        ▼
Docker Container Runtime
        │
        │  Captures stdout, wraps in Docker JSON envelope
        │  {"log": "...", "stream": "stdout", "time": "..."}
        ▼
/var/lib/docker/containers/<id>/<id>-json.log   (file on host)
        │
        │  Promtail reads this file (via volume mount)
        ▼
Promtail Pipeline Stages
        │
        ├─ [docker stage]     Unwrap Docker JSON envelope
        ├─ [json stage]       Parse Zap JSON, extract fields
        ├─ [timestamp stage]  Set Loki timestamp = Zap timestamp
        ├─ [labels stage]     Promote "level" to a Loki label
        └─ [output stage]     Set display line = "message" field
        │
        │  Labels attached: {service="employee-svc", env="production", level="info"}
        │  HTTP POST to http://loki:3100/loki/api/v1/push
        ▼
Loki Ingester
        │
        ├─ Writes to WAL (crash safety)
        ├─ Appends to in-memory chunk for this label combination
        └─ Flushes chunk to /loki/data/chunks when full or idle
        │
        │  Index entry created: {service, env, level} → chunk file reference
        ▼
Loki Storage (named Docker volume)
        │
        │  LogQL query from Grafana: {service="employee-svc", level="error"}
        ▼
Loki Querier
        │
        ├─ Looks up label index → finds relevant chunk files
        ├─ Decompresses chunks
        └─ Streams matching log lines back to Grafana
        │
        ▼
Grafana (your browser)
        │
        └─ Renders log lines, highlights fields, linkifies trace IDs
```

This is the complete, production-grade Loki logging pipeline for HR360. Every architectural decision made in this guide — from the label design philosophy to the WAL configuration to the provisioning-as-code approach for Grafana — is grounded in how mature engineering teams run Loki in real production environments.
