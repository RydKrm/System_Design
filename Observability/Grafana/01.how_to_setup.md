## The Big Picture: Why Grafana Is the Final and Most Important Piece

Throughout your observability journey, you have built an extraordinary data collection infrastructure. Prometheus scrapes metrics from your Go microservices every fifteen seconds, capturing request rates, error percentages, latency distributions, goroutine counts, and memory usage. Loki receives structured log lines from your services, enriched with Trace IDs and Span IDs by the OpenTelemetry Collector. Tempo stores distributed traces that reveal the complete journey of each request across your microservice boundaries. Alertmanager routes critical alerts to the right Slack channels and email addresses when thresholds are breached. Each of these systems is a specialist — extraordinary at its particular job, but utterly useless to a human being without a way to see, query, and interpret the data it holds.

Grafana is that way. It is the lens through which your entire engineering team perceives the health, performance, and behaviour of your distributed system. Without Grafana, your observability data is like a library with no catalogue — the knowledge exists, but finding what you need when you need it (and under the pressure of a production incident at two in the morning) is nearly impossible. Grafana transforms your raw telemetry data into living, breathing dashboards that tell a story at a glance, interactive exploration panels where you can drill from a metric anomaly into the specific log line into the exact distributed trace that reveals the root cause, and automated alert visualisations that show you not just that something is wrong, but the historical context that helps you understand why.

This guide covers everything you need to configure Grafana as the unified command centre for your HR360 system. We will go far beyond the basic "add a datasource and create a panel" tutorial. We will cover provisioning-as-code (so your Grafana configuration survives container recreations), advanced datasource configuration with cross-datasource correlation, dashboard design principles that separate useful dashboards from cluttered noise, the folder and permission structure for a multi-team organisation, alert integration, and the production hardening measures that make Grafana reliable under the stress of a real incident.

## Chapter 1: Understanding Grafana's Architecture — What Runs Inside the Container

Before we configure a single file, it is important to understand what Grafana actually is under the hood, because this knowledge will inform every configuration decision we make. Grafana is a web application written in Go (for the backend) and React (for the frontend). When you start the Grafana container, the Go backend process initialises several subsystems: an HTTP server that serves the web interface and API, a **provisioning engine** that reads configuration files from disk and applies them on startup, a **datasource proxy** that relays queries from your browser to backend datasources like Prometheus and Loki, an **alerting engine** (Grafana's unified alerting system, distinct from Prometheus Alertmanager), and a **SQLite database** (or PostgreSQL/MySQL in larger deployments) that stores dashboards, users, preferences, and organisational data.

The provisioning engine is the most important subsystem for a production deployment. In a development environment, you might create datasources and dashboards by clicking through the Grafana UI. But in production, this approach is fragile — if the Grafana container is destroyed and recreated (which happens during updates, host migrations, or Docker Compose restarts), all your manually created datasources and dashboards vanish unless they were persisted to a volume. The provisioning engine solves this by reading YAML configuration files and JSON dashboard definitions from specific directories on startup, automatically creating the datasources, dashboards, alert rules, and notification channels they describe. This is configuration-as-code, and it is the only way to run Grafana in production.

```
            │   ├── hr360-infrastructure.json            ← Host & container dashboard

            │

```

Every file in this structure is mounted into the Grafana container as a read-only volume. Grafana reads them on startup, creates the resources they describe, and then leaves the files untouched. If you modify a file, restarting the Grafana container (or waiting for the provisioning engine's refresh interval) applies the changes. This means your entire Grafana configuration lives in version control alongside your application code and infrastructure configuration — reviewable, auditable, and reproducible.

## Chapter 3: Configuring grafana.ini — The Server Configuration

The `grafana.ini` file controls Grafana's core behaviour: which port it listens on, how authentication works, what security policies are enforced, and how logging is configured. This is a production-hardened configuration with detailed explanations of every setting:

```ini
# monitoring/grafana/grafana.ini

# ════════════════════════════════════════════════════════════════════
# SERVER CONFIGURATION
# ════════════════════════════════════════════════════════════════════
[server]
http_port = 3000
# The port Grafana listens on inside the container. Docker maps this
# to the host port defined in docker-compose.monitoring.yml.

domain = ${GF_SERVER_DOMAIN}
# The public-facing domain name. Used for generating correct URLs in
# email notifications, shared dashboard links, and OAuth callbacks.
# Set via environment variable in Docker Compose.

root_url = %(protocol)s://%(domain)s:%(http_port)s/
# The full URL that users type in their browser to access Grafana.
# %(protocol)s, %(domain)s, and %(http_port)s are built-in template
# variables that Grafana resolves from the settings above.

serve_from_sub_path = false
# Set to true if Grafana is served behind a reverse proxy at a
# subpath like /grafana instead of at the root. For standalone
# deployment, false is correct.

enable_gzip = true
# Compress HTTP responses with gzip. This reduces bandwidth usage
# significantly for dashboard JSON payloads and large query results.
# A dashboard JSON can be 200 KB uncompressed but 30 KB gzipped.


# ════════════════════════════════════════════════════════════════════
# SECURITY
# ════════════════════════════════════════════════════════════════════
[security]
admin_user = admin
admin_password = ${GF_SECURITY_ADMIN_PASSWORD}
# The initial admin credentials. After first login, you should create
# individual user accounts and avoid using the admin account for daily
# work. The password is injected via environment variable — NEVER
# hardcode passwords in configuration files.

secret_key = ${GF_SECURITY_SECRET_KEY}
# A random string used to sign session cookies, datasource passwords,
# and other sensitive data stored in Grafana's database. Generate
# with: openssl rand -hex 32
# If you change this after Grafana has been running, all existing
# sessions will be invalidated and encrypted datasource passwords
# will become unreadable.

disable_gravatar = true
# Gravatar is a service that provides profile pictures based on email
# addresses. Disabling it prevents Grafana from making external HTTP
# requests to gravatar.com, which is a privacy and security measure.

cookie_secure = false
# Set to true if Grafana is served over HTTPS. When true, session
# cookies are only sent over encrypted connections. For local Docker
# development over HTTP, this must be false.

cookie_samesite = lax
# Controls the SameSite attribute on cookies. "lax" provides a good
# balance between security and usability — it prevents CSRF attacks
# while still allowing normal navigation.

strict_transport_security = false
# Set to true when serving over HTTPS to enable HSTS headers, which
# tell browsers to always use HTTPS for this domain.

content_security_policy = true
# Enables Content-Security-Policy headers that prevent XSS attacks
# by restricting which scripts, styles, and resources can be loaded.


# ════════════════════════════════════════════════════════════════════
# AUTHENTICATION
# ════════════════════════════════════════════════════════════════════
[auth]
disable_login_form = false
# Keep the login form enabled. In a larger organisation, you might
# disable it and use OAuth/SAML exclusively.

login_maximum_inactive_lifetime_duration = 7d
# Sessions expire after 7 days of inactivity. Adjust based on your
# security policy. Shorter durations are more secure but force more
# frequent logins.

login_maximum_lifetime_duration = 30d
# Absolute session lifetime — even active sessions expire after 30 days.

[auth.anonymous]
enabled = false
# NEVER enable anonymous access in production. Every user must
# authenticate. Anonymous access means anyone who can reach Grafana's
# port can view all your dashboards and potentially sensitive data.

[auth.basic]
enabled = true
# HTTP Basic Authentication is used by the provisioning API and
# programmatic access. Keep this enabled.


# ════════════════════════════════════════════════════════════════════
# USERS
# ════════════════════════════════════════════════════════════════════
[users]
allow_sign_up = false
# Disable self-registration. In production, only administrators
# should be able to create new user accounts.

allow_org_create = false
# Prevent users from creating new organisations. Your HR360 system
# uses a single organisation.

auto_assign_org = true
auto_assign_org_id = 1
auto_assign_org_role = Viewer
# When a new user is created (by an admin or via OAuth), automatically
# assign them to organisation 1 with the Viewer role. Viewers can see
# dashboards but cannot edit them or change datasources. This follows
# the principle of least privilege — users get more access only when
# explicitly granted by an administrator.


# ════════════════════════════════════════════════════════════════════
# DASHBOARDS
# ════════════════════════════════════════════════════════════════════
[dashboards]
min_refresh_interval = 10s
# The minimum auto-refresh interval users can set on dashboards.
# Prevents users from setting 1-second refresh intervals that would
# overwhelm Prometheus and Loki with queries. 10 seconds is a
# reasonable floor for production.

default_home_dashboard_path = /etc/grafana/provisioning/dashboards/hr360-service-overview.json
# Set your service overview dashboard as the home page. When users
# log in, they immediately see the health of all services.


# ════════════════════════════════════════════════════════════════════
# LOGGING
# ════════════════════════════════════════════════════════════════════
[log]
mode = console
# Write Grafana's own logs to stdout (console) so Docker captures
# them. This allows you to view Grafana logs with:
#   docker compose logs grafana

level = info
# Log level. Use "debug" when troubleshooting provisioning issues
# or datasource connectivity problems, then switch back to "info".


# ════════════════════════════════════════════════════════════════════
# ALERTING
# ════════════════════════════════════════════════════════════════════
[alerting]
enabled = false
# Disable the LEGACY alerting system. Grafana has two alerting
# systems: the old one (per-panel alerts) and the new Unified
# Alerting. We use Unified Alerting exclusively.

[unified_alerting]
enabled = true
# Enable Grafana's Unified Alerting system. This is the modern
# alerting engine that supports multi-datasource alerts, alert
# grouping, silences, and contact points. It works alongside (not
# instead of) Prometheus Alertmanager — you can have alerts evaluated
# by both Prometheus and Grafana, routed through the same or
# different notification channels.

min_interval = 10s
# Minimum evaluation interval for Grafana-managed alert rules.


# ════════════════════════════════════════════════════════════════════
# FEATURE TOGGLES
# ════════════════════════════════════════════════════════════════════
[feature_toggles]
enable = traceToMetrics correlations explore2Dashboard
# traceToMetrics: When viewing a trace in Tempo, show related
#   Prometheus metrics for the service and time range.
# correlations: Enable the correlations feature that lets you
#   define links between datasources (e.g., log → trace, metric → log).
# explore2Dashboard: Convert Explore queries into dashboard panels
#   with a single click.


# ════════════════════════════════════════════════════════════════════
# DATA PROXY
# ════════════════════════════════════════════════════════════════════
[dataproxy]
timeout = 60
# Maximum seconds Grafana waits for a response from a datasource.
# Complex PromQL queries or large LogQL queries might take longer
# than the default 30 seconds. 60 seconds provides headroom for
# heavy queries during incident investigation.

keep_alive_seconds = 30
# Keep HTTP connections to datasources alive for 30 seconds between
# queries. This reuses TCP connections, reducing latency and
# connection establishment overhead.

max_idle_connections = 100
# Maximum idle connections in the connection pool for each datasource.
# 100 is generous enough for multiple users querying simultaneously.
```

## Chapter 4: Provisioning Datasources — Connecting Grafana to Your Data

The datasource provisioning file tells Grafana where to find your data and how to query it. This is the most critical provisioning file because without datasources, Grafana has nothing to display. We configure all four datasources — Prometheus, Loki, Tempo, and Alertmanager — with full cross-datasource correlation enabled:

```yaml
# monitoring/grafana/provisioning/datasources/datasources.yml

apiVersion: 1

# ════════════════════════════════════════════════════════════════════════
# DELETE DATASOURCES
# ════════════════════════════════════════════════════════════════════════
# List any datasources here that should be deleted when Grafana starts.
# This is useful for cleaning up datasources that were manually created
# through the UI during development but should not exist in production.
deleteDatasources:
  - name: Old-Prometheus
    orgId: 1

# ════════════════════════════════════════════════════════════════════════
# DATASOURCE DEFINITIONS
# ════════════════════════════════════════════════════════════════════════
datasources:

  # ──────────────────────────────────────────────────────────────────────
  # PROMETHEUS — Metrics (How much? How fast? How often?)
  # ──────────────────────────────────────────────────────────────────────
  - name: Prometheus
    type: prometheus
    access: proxy
    # "proxy" means Grafana's backend makes the HTTP request to
    # Prometheus on your behalf. The alternative "direct" would make
    # your browser connect to Prometheus directly, which would fail
    # because Prometheus is on an internal Docker network that your
    # browser cannot reach.
    url: http://prometheus:9090
    # The hostname "prometheus" resolves within Docker's DNS because
    # both Grafana and Prometheus are on the monitoring network.
    uid: prometheus
    # A unique identifier for this datasource. UIDs are used internally
    # by Grafana to reference datasources in dashboard JSON and
    # correlation configurations. Once set, never change this value —
    # it would break all dashboards that reference it.
    isDefault: true
    # Prometheus is the default datasource. When you create a new panel
    # without explicitly selecting a datasource, it uses this one.
    version: 1
    editable: false
    # editable: false prevents users from modifying this datasource
    # through the UI. All changes must go through the provisioning
    # file, which lives in version control. This is a production
    # best practice — it prevents accidental changes to infrastructure.
    jsonData:
      timeInterval: "15s"
      # Tell Grafana that Prometheus scrapes every 15 seconds. Grafana
      # uses this to set the $__interval variable, which aligns query
      # step sizes with scrape intervals for smoother, more accurate
      # graphs. Without this, Grafana might query at 1-second resolution
      # when Prometheus only has data at 15-second resolution, producing
      # jagged, misleading graphs.
      httpMethod: POST
      # Use POST for PromQL queries instead of GET. POST avoids URL
      # length limits that can truncate complex queries. Some PromQL
      # expressions for histograms or multi-service aggregations can
      # exceed the 2048-character URL limit in GET requests.
      incrementalQuerying: true
      # Incremental querying allows Grafana to cache partial query
      # results and only request new data when a dashboard refreshes.
      # This significantly reduces load on Prometheus for dashboards
      # that are left open on monitoring screens.
      exemplarTraceIdDestinations:
        - name: trace_id
          datasourceUid: tempo
          # EXEMPLAR CORRELATION: This is where metrics meet traces.
          #
          # When your Go service records a histogram observation, it can
          # attach an exemplar — a sample annotation containing the
          # trace_id of the specific request that produced that measurement.
          # In Grafana, exemplars appear as coloured dots on histogram
          # and counter graphs. Clicking a dot opens the corresponding
          # trace in Tempo.
          #
          # This gives you the ability to go from "P99 latency spiked"
          # → click the dot at the peak → see the exact trace that was
          # slow → find the root cause in the trace spans.

  # ──────────────────────────────────────────────────────────────────────
  # LOKI — Logs (What happened? What went wrong?)
  # ──────────────────────────────────────────────────────────────────────
  - name: Loki
    type: loki
    access: proxy
    url: http://loki:3100
    uid: loki
    isDefault: false
    version: 1
    editable: false
    jsonData:
      maxLines: 1000
      # Maximum number of log lines returned per query. 1000 is a good
      # default — enough to see context around an error without
      # overwhelming the browser. For full investigations, you can
      # override this per-query in the Explore panel.
      timeout: 60
      # Query timeout in seconds. Complex LogQL queries that scan
      # large time ranges can take up to a minute. Match this with
      # the dataproxy timeout in grafana.ini.
      derivedFields:
        # DERIVED FIELDS: Log-to-Trace Correlation
        #
        # Derived fields tell Grafana: "When you see a specific pattern
        # in a log line, extract a value and create a clickable link."
        # This is how trace_id values in your logs become clickable
        # links to Tempo traces.
        - name: TraceID
          matcherRegex: '"trace_id":"(\w+)"'
          url: "$${__value.raw}"
          datasourceUid: tempo
          matcherType: label
          # matcherRegex: A regular expression that matches the trace_id
          #   field inside your JSON log lines.
          # url: The extracted value is used as the Tempo trace ID.
          # datasourceUid: Tells Grafana to open this link in the Tempo
          #   datasource, not in a browser tab.
          # matcherType: "label" searches in the structured metadata
          #   that Loki stores (from OTLP ingestion), not just the raw
          #   log text.

        - name: SpanID
          matcherRegex: '"span_id":"(\w+)"'
          url: "$${__value.raw}"
          datasourceUid: tempo
          matcherType: label

  # ──────────────────────────────────────────────────────────────────────
  # TEMPO — Traces (Why did it happen? Where is the bottleneck?)
  # ──────────────────────────────────────────────────────────────────────
  - name: Tempo
    type: tempo
    access: proxy
    url: http://tempo:3200
    uid: tempo
    isDefault: false
    version: 1
    editable: false
    jsonData:
      tracesToLogsV2:
        datasourceUid: loki
        filterByTraceID: true
        filterBySpanID: true
        customQuery: true
        query: '{service_name="${__span.tags["service.name"]}"} | json | trace_id = "${__trace.traceId}"'
        # TRACE-TO-LOG CORRELATION:
        #
        # When you view a trace in Tempo, this configuration adds a
        # "Logs" button next to each span. Clicking it runs a LogQL
        # query in Loki that filters logs by the trace ID and the
        # specific service that produced the span. This means you can
        # see exactly what a service logged during the execution of
        # that particular trace — including debug messages, warnings,
        # and error details that provide context the trace alone cannot.
        #
        # The ${__span.tags["service.name"]} template variable is
        # replaced with the service name from the span's resource
        # attributes. The ${__trace.traceId} template variable is
        # replaced with the trace's ID.
        tags:
          - key: "service.name"
            tag: "service_name"

      tracesToMetrics:
        datasourceUid: prometheus
        spanStartTimeShift: "-5m"
        spanEndTimeShift: "5m"
        # TRACE-TO-METRICS CORRELATION:
        #
        # When viewing a trace, Grafana shows Prometheus metrics for
        # the service and time range of each span. The time shifts
        # (-5m and +5m) widen the metrics window to show what happened
        # before and after the span, providing broader context.
        tags:
          - key: "service.name"
            tag: "service"
        queries:
          - name: "Request Rate"
            query: 'sum(rate(http_requests_total{service="$${__tags.service}"}[5m]))'
          - name: "Error Rate"
            query: 'sum(rate(http_requests_total{service="$${__tags.service}", status=~"5.."}[5m]))'
          - name: "P99 Latency"
            query: 'histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{service="$${__tags.service}"}[5m])))'
          # These pre-defined queries appear as tabs in the trace view.
          # When you select a span from "payroll-svc", Grafana runs
          # these PromQL queries with service="payroll-svc" and shows
          # the metrics as small inline graphs next to the span.

      serviceMap:

        # your services communicate with each other, with edges coloured
```

## Chapter 5: Provisioning Dashboards — Configuration as Code

Grafana's dashboard provisioning system watches directories for JSON files and automatically imports them as dashboards. The provisioning YAML file tells Grafana which directories to watch and how to organise the dashboards it finds:

```yaml
# monitoring/grafana/provisioning/dashboards/dashboards.yml

apiVersion: 1

providers:

  - name: "HR360 Service Dashboards"
    orgId: 1
    folder: "HR360"
    # Dashboards from this provider are placed in a Grafana folder
    # called "HR360". Folders provide visual organisation and can
    # have their own permissions (e.g., only backend team can edit).
    type: file
    disableDeletion: true
    # Prevent users from deleting provisioned dashboards through the
    # UI. If they want to remove a dashboard, they must delete the
    # JSON file from the provisioning directory. This prevents
    # accidental deletion during incident investigation (when people
    # are stressed and clicking too fast).
    updateIntervalSeconds: 30
    # Check for changes to dashboard JSON files every 30 seconds.
    # During development, you can edit a dashboard in the UI, export
    # the JSON, save it to the provisioning directory, and Grafana
    # will pick it up within 30 seconds without a restart.
    allowUiUpdates: true
    # Allow users to modify provisioned dashboards through the UI.
    # Changes made through the UI are saved to Grafana's database
    # but will be OVERWRITTEN by the provisioning file on next restart.
    # This is useful during development — you edit in the UI, export
    # the final JSON, and commit it to version control.
    options:
      path: /etc/grafana/provisioning/dashboards
      foldersFromFilesStructure: false
      # If true, subdirectories within the dashboards path would
      # become Grafana folders. For simplicity, we keep all dashboards
      # in a single folder.
```

Now, let us discuss how to create dashboard JSON files. The most practical workflow is:

1. **Create the dashboard in the Grafana UI** — use the visual editor to add panels, configure queries, set time ranges, and adjust visualisation options.
2. **Export the dashboard as JSON** — go to Dashboard Settings → JSON Model → copy the entire JSON.
3. **Save the JSON to the provisioning directory** — create a `.json` file in `monitoring/grafana/provisioning/dashboards/`.
4. **Commit to version control** — the dashboard is now reproducible.

## Chapter 6: Dashboard Design Principles — What Separates a Useful Dashboard from Noise

Building dashboards is easy. Building dashboards that are actually useful during a production incident at two in the morning, when your brain is foggy and your heart is racing, is an art form. The difference between a good dashboard and a bad one is not aesthetics — it is information density, signal-to-noise ratio, and cognitive load. Let us establish the principles that govern effective dashboard design.

**The Five-Second Rule.** When an engineer opens your dashboard during an incident, they should be able to determine "is the system healthy or not?" within five seconds. This means the most important metrics — overall error rate, service availability, and P99 latency — must be in the top row, using large, colour-coded visualisations. Green means healthy. Red means broken. Yellow means degrading. No reading required.

**The Layered Approach.** Design your dashboards in layers of increasing detail. The top of the dashboard shows aggregate, system-wide health (the "at a glance" layer). The middle shows per-service breakdowns (the "which service?" layer). The bottom shows detailed metrics for investigation (the "why?" layer). An engineer reads from top to bottom, drilling deeper only as needed.

**The Four Dashboard Types.** A production system needs exactly four types of dashboards, each serving a different audience and purpose:

**Template Variables.** Every dashboard should use template variables (the dropdown menus at the top) to allow filtering by service, environment, and time range. When an engineer selects `payroll-svc` from the dropdown, every panel on the dashboard should filter to show only payroll-svc data. This eliminates the need for separate dashboards for each service.

**Annotations.** Configure Grafana annotations to mark deployments, incidents, and maintenance windows on your graphs. ## Chapter 7: The Explore Panel — Your Investigation Workbench

While dashboards are designed for monitoring (passively watching for anomalies), the **Explore** panel is designed for investigation (actively hunting for answers when something goes wrong). Explore is Grafana's most powerful feature for incident responders, and understanding how to use it effectively can cut your mean time to resolution (MTTR) from hours to minutes.

The Explore panel gives you a free-form query interface for each datasource, with features that dashboards do not have: split view (query two datasources side by side), query history (revisit previous investigations), live tail for logs (like `tail -f` but with LogQL filtering), and inline trace visualisation.

## Chapter 8: Grafana Unified Alerting — Alerts That Go Beyond Prometheus

Your Prometheus Alertmanager handles alerts that are evaluated by Prometheus against its own metrics. But there are alerts that Prometheus cannot evaluate — alerts that span multiple datasources, alerts based on log content, or alerts that combine metrics with log counts. Grafana's Unified Alerting system fills this gap by evaluating alert rules against any datasource Grafana can query.

Here is a provisioned alerting configuration for Grafana-managed alerts:

```yaml
# monitoring/grafana/provisioning/alerting/grafana-alerts.yml

apiVersion: 1

groups:
  - orgId: 1
    name: "HR360 Grafana Alerts"
    folder: "HR360"
    interval: "1m"
    rules:

      # ── Log Error Spike ───────────────────────────────────────────
      # This alert cannot be done in Prometheus because it queries LOGS,
      # not metrics. Only Grafana can query Loki and evaluate alert
      # rules against the result.
      - uid: log-error-spike
        title: "Log Error Spike"
        condition: C
        data:
          - refId: A
            datasourceUid: loki
            model:
              expr: 'sum(count_over_time({deployment_environment="production"} | json | level = "error" [5m]))'
            relativeTimeRange:
              from: 300
              to: 0
          - refId: B
            datasourceUid: "__expr__"
            model:
              type: reduce
              expression: A
              reducer: last
          - refId: C
            datasourceUid: "__expr__"
            model:
              type: threshold
              expression: B
              conditions:
                - evaluator:
                    type: gt
                    params: [50]
        for: "5m"
        labels:
          severity: warning
          source: grafana
        annotations:
          summary: "More than 50 error log lines in the last 5 minutes"
          description: |
            The total count of error-level log lines across all
            production services has exceeded 50 in the last 5 minutes.
            Open the Logs Explorer dashboard to investigate.

      # ── Cross-Pillar Alert: High Errors + No Recent Traces ────────
      # This alert combines data from Prometheus (error rate) with
      # logic about trace availability. It fires when the error rate
      # is high but no traces are being collected — indicating that
      # your OpenTelemetry pipeline may be broken while your services
      # are failing.
      - uid: errors-without-traces
        title: "High Errors But No Traces — OTel Pipeline May Be Down"
        condition: C
        data:
          - refId: A
            datasourceUid: prometheus
            model:
              expr: 'sum(rate(http_requests_total{status=~"5.."}[5m]))'
            relativeTimeRange:
              from: 300
              to: 0
          - refId: B
            datasourceUid: "__expr__"
            model:
              type: reduce
              expression: A
              reducer: last
          - refId: C
            datasourceUid: "__expr__"
            model:
              type: threshold
              expression: B
              conditions:
                - evaluator:
                    type: gt
                    params: [0.5]
        for: "10m"
        labels:
          severity: critical
          source: grafana
        annotations:
          summary: "Errors detected but OTel traces may be missing"
          description: |
            The error rate exceeds 0.5/s but this alert exists to remind
            you to verify that traces are still flowing. If the OTel
            Collector is down, you will have metrics (from Prometheus scraping)
            but no traces (because OTLP export is failing).
```

```yaml
      - "3000:3000"
      # Grafana's web UI. In production behind a reverse proxy (Nginx,
      # Traefik, Caddy), you might remove this port mapping and have

    user: "472"

    # This is the default, but being explicit prevents permission
    # issues when mounting volumes on hosts with different default UIDs.
    environment:
      # ── Security ─────────────────────────────────────────────────
      - GF_SECURITY_ADMIN_PASSWORD=${GRAFANA_ADMIN_PASSWORD}
      - GF_SECURITY_ADMIN_USER=admin
      - GF_SECURITY_SECRET_KEY=${GRAFANA_SECRET_KEY}

      - GF_SERVER_DOMAIN=${GRAFANA_DOMAIN:-localhost}

      # ── Authentication ───────────────────────────────────────────
      - GF_USERS_ALLOW_SIGN_UP=false
      - GF_AUTH_ANONYMOUS_ENABLED=false

      # ── Features ─────────────────────────────────────────────────
      - GF_FEATURE_TOGGLES_ENABLE=traceToMetrics correlations explore2Dashboard

      # ── Alerting ─────────────────────────────────────────────────

      - GF_ALERTING_ENABLED=false

      # ── Plugins ──────────────────────────────────────────────────
      - GF_INSTALL_PLUGINS=grafana-clock-panel,grafana-piechart-panel
      # Install additional panel plugins on startup. The clock panel
      # is useful for dashboards displayed on wall-mounted monitors.
      # The piechart panel provides pie/donut charts for proportional
      # data like error distribution by service.

    volumes:
      - grafana_data:/var/lib/grafana
      # Persists Grafana's SQLite database (dashboards created via UI,
      # user accounts, preferences, alert state). This is the most
      # critical volume — losing it means losing all non-provisioned
      # configuration.

      - ./monitoring/grafana/grafana.ini:/etc/grafana/grafana.ini:ro
      # The server configuration file. Mounted read-only because
      # Grafana reads it on startup and never writes to it.

      - ./monitoring/grafana/provisioning:/etc/grafana/provisioning:ro

      #   datasources/datasources.yml
      #   dashboards/dashboards.yml + *.json
      #   alerting/grafana-alerts.yml
      #   alerting/contact-points.yml
      # All mounted read-only.

    networks:
      - monitoring
      # Grafana needs to reach Prometheus, Loki, Tempo, and
      # Alertmanager — all on the monitoring network.

    depends_on:
      loki:
        condition: service_healthy
      prometheus:
        condition: service_healthy
      # Grafana starts after Loki and Prometheus are healthy. This
      # prevents provisioning errors when Grafana tries to validate
      # datasource connectivity during startup.

    healthcheck:
      test: ["CMD", "wget", "--no-verbose", "--tries=1", "--spider", "http://localhost:3000/api/health"]
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 30s
      # Grafana's /api/health endpoint returns {"commit":"...","database":"ok","version":"..."}
      # when the server is fully initialised. The start_period gives
      # Grafana 30 seconds to initialise its database, load plugins,
      # and process provisioning files before health checks begin.

    mem_limit: 256m
    # Grafana is relatively lightweight. 256 MiB is sufficient for
    # a team of 5-10 concurrent users. Increase to 512 MiB if you
    # have complex dashboards with many panels or heavy query loads.

    logging:
      driver: "json-file"

      env: production
```

## Chapter 10: Users, Roles, and Permissions — Organising Access for Your Team

In a production environment, not everyone should have the same level of access to Grafana. A junior developer investigating a bug needs to view dashboards and run queries, but should not be able to delete dashboards or modify datasources. A team lead needs to edit dashboards and create annotations, but should not change the Grafana server configuration. Only administrators should manage users, datasources, and provisioning.

Grafana's permission model is built on three concepts: **Organisations**, **Roles**, and **Folder Permissions**.

```

│  │  • Access all dashboards and folders                         │  │

│  └──────────────────────────────────────────────────────────────┘  │
│                                                                    │
```

## Chapter 11: Grafana API — Automating Everything

Grafana exposes a comprehensive REST API that allows you to automate every aspect of your observability workflow. This is invaluable for CI/CD pipelines, deployment scripts, and operational tooling.

```bash
# ════════════════════════════════════════════════════════════════════
# USEFUL GRAFANA API OPERATIONS
# ════════════════════════════════════════════════════════════════════

# ── Create an API Key for automation ────────────────────────────────
curl -X POST http://localhost:3000/api/auth/keys \
  -H "Content-Type: application/json" \
  -H "Authorization: Basic $(echo -n 'admin:YOUR_PASSWORD' | base64)" \
  -d '{"name": "ci-cd-key", "role": "Editor", "secondsToLive": 0}'
# Returns: {"id":1,"name":"ci-cd-key","key":"eyJrIj..."}
# Store this key securely — it grants Editor access to all Grafana APIs.

# ── Add a deployment annotation ─────────────────────────────────────
# Call this from your CI/CD pipeline after each deployment:
curl -X POST http://localhost:3000/api/annotations \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d "{
    \"time\": $(date +%s000),
    \"tags\": [\"deployment\", \"${SERVICE_NAME}\", \"${VERSION}\"],
    \"text\": \"Deployed ${SERVICE_NAME} ${VERSION}\"
  }"
# This creates a vertical line on all dashboard graphs at the
# deployment time, making it trivially easy to correlate metric
# changes with deployments.

# ── Export a dashboard as JSON ──────────────────────────────────────
curl -s http://localhost:3000/api/dashboards/uid/hr360-service-overview \
  -H "Authorization: Bearer YOUR_API_KEY" \
  | jq '.dashboard' > hr360-service-overview.json
# Export the dashboard JSON for version control.

# ── Check datasource health ────────────────────────────────────────
curl -s http://localhost:3000/api/datasources/proxy/uid/prometheus/api/v1/query?query=up \
  -H "Authorization: Bearer YOUR_API_KEY" \
  | jq '.data.result | length'
# Returns the number of scrape targets. Use this in health checks
# to verify that the observability pipeline is end-to-end healthy.

# ── Pause all Grafana-managed alerts ────────────────────────────────
# Useful during maintenance windows:
curl -X POST http://localhost:3000/api/v1/provisioning/alert-rules/log-error-spike \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d '{"isPaused": true}'

# ── Search dashboards ──────────────────────────────────────────────
curl -s "http://localhost:3000/api/search?query=HR360" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  | jq '.[].title'
```

## Chapter 12: Backup, Restore, and Disaster Recovery

Your Grafana instance contains two types of data: provisioned configuration (datasources and dashboards from YAML/JSON files, which live in version control) and stateful data (user accounts, preferences, manually created dashboards, alert state, annotations, and API keys, which live in the SQLite database). The provisioned configuration is safe — it is reproduced on every container creation. The stateful data must be backed up.

```bash
# ── Backup the Grafana database ─────────────────────────────────────
# The SQLite database is at /var/lib/grafana/grafana.db inside the
# container. Back it up by copying from the Docker volume:

docker compose -f docker-compose.monitoring.yml exec grafana \
  sqlite3 /var/lib/grafana/grafana.db ".backup /var/lib/grafana/grafana-backup.db"

docker cp hr360_grafana:/var/lib/grafana/grafana-backup.db \
  ./backups/grafana-backup-$(date +%Y%m%d).db

# ── Restore from backup ────────────────────────────────────────────
# Stop Grafana, replace the database, restart:
docker compose -f docker-compose.monitoring.yml stop grafana
docker cp ./backups/grafana-backup-20260818.db \
  hr360_grafana:/var/lib/grafana/grafana.db
docker compose -f docker-compose.monitoring.yml start grafana

# ── Automate daily backups with cron ────────────────────────────────
# Add to your host's crontab:
# 0 3 * * * docker exec hr360_grafana sqlite3 /var/lib/grafana/grafana.db \
#   ".backup /var/lib/grafana/grafana-backup.db" && \
#   docker cp hr360_grafana:/var/lib/grafana/grafana-backup.db \
#   /backups/grafana/grafana-$(date +\%Y\%m\%d).db
```

For a more robust production setup, consider using PostgreSQL instead of SQLite as Grafana's database backend. PostgreSQL provides proper transaction isolation, concurrent access support, and well-established backup and replication tools. To switch, add these environment variables to the Grafana service:

```yaml
# In docker-compose.monitoring.yml, add to grafana.environment:
- GF_DATABASE_TYPE=postgres
- GF_DATABASE_HOST=postgres:5432
- GF_DATABASE_NAME=grafana
- GF_DATABASE_USER=grafana
- GF_DATABASE_PASSWORD=${GRAFANA_DB_PASSWORD}
- GF_DATABASE_SSL_MODE=disable
```

## Closing Thoughts

Grafana is not just a dashboard tool — it is the interface through which your entire engineering organisation understands, investigates, and maintains your distributed system. Without Grafana, your Prometheus metrics are numbers in a database, your Loki logs are text in a warehouse, and your Tempo traces are graphs in cold storage. With Grafana, they become a living, breathing narrative of your system's behaviour that any engineer can read, navigate, and act upon.

The configuration you have built in this guide transforms Grafana from a generic visualisation tool into a purpose-built command centre for your HR360 system. Every datasource is wired for bidirectional correlation — metrics link to traces, traces link to logs, logs link back to traces. Every dashboard follows the layered design principle — aggregate health at the top, per-service breakdown in the middle, detailed investigation at the bottom. Every provisioned resource lives in version control, reproducible and auditable. And every operational aspect — backups, permissions, API automation — is production-hardened.

The four guides you have now completed — Loki for logs, OpenTelemetry for distributed telemetry, Prometheus for metrics, and Grafana for visualisation — together form a complete, production-grade observability stack. When the next production incident occurs, you will not be grepping through log files on individual servers, hoping to find a clue. You will open Grafana, see the anomaly on a dashboard, drill from the metric to the log to the trace, identify the root cause, and resolve the incident — all within minutes, from a single browser tab.
